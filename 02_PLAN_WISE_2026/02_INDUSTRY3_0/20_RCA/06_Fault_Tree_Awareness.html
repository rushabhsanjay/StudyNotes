1. Definition

Fault-tree analysis (FTA) is a systematic method for analyzing how combinations of component failures, abnormal conditions, human actions, and control weaknesses can lead to an undesired system-level event.

The analysis starts with a defined top event, such as a machine stopping unexpectedly, a robot losing safe motion control, or a CNC spindle drive tripping. It then works backward to identify the lower-level events and conditions that could produce that outcome.

Fault-tree awareness means being able to:

  • Understand the structure and purpose of a fault tree.
  • Distinguish AND and OR relationships between events.
  • Trace a system-level failure into possible causes.
  • Recognize single-point failures and combinations of failures.
  • Use evidence to validate the proposed causes.
  • Connect the analysis to troubleshooting, risk assessment, maintenance, and corrective action.

FTA is especially useful when a machine failure may involve multiple interacting conditions or when the consequences of a failure are significant.

2. Why fault-tree analysis is needed

A machine breakdown may appear to have one obvious cause, but the actual failure may depend on several conditions occurring together.

For example, a machine may stop because its PLC loses remote I/O communication. The communication failure might result from a damaged cable, a device power problem, a switch failure, or a configuration issue. Some failures may be independent, while others may share a common cause.

A fault tree helps answer:

  1. What undesired event are we investigating?
  2. What events can directly cause it?
  3. Can any one event cause the failure by itself?
  4. Are multiple events required to produce the failure?
  5. Which components or conditions are common to several failure paths?
  6. What evidence is needed to confirm the relevant paths?

The objective is to understand the failure logic, not simply create a long list of possible faults.

3. Basic fault-tree structure

A fault tree normally contains:

  • Top event: The undesired system-level outcome.
  • Intermediate events: Conditions produced by lower-level events.
  • Basic events: Component failures, external conditions, or other events treated as fundamental at the current level of analysis.
  • Logic gates: Relationships that show how lower-level events combine to produce an event above them.
  • Undeveloped events: Events not analyzed further because of limited information, scope, or analysis requirements.

Example:

Top event: Conveyor stops unexpectedly
    OR
    ├── Motor drive trips
    ├── PLC enters a stop state
    └── Required safety stop occurs

This simplified tree illustrates possible paths to the same top event. A real investigation must define the operating context and verify that each branch can actually produce the specified outcome.

A safety stop may be an intended protective response rather than a safety-system failure. The top event must distinguish an unexpected production stop from an actual failure of a safety function.

4. AND gate and OR gate

The two most important logic relationships are AND and OR.

4.1 OR gate

An OR gate means that any one of the input events can produce the output event, assuming the stated system conditions apply.

Example:

Top event: PLC loses remote I/O communication
    OR
    ├── Network cable connection fails
    ├── Remote I/O device loses power
    └── Network switch or communication path fails

If any one of these events is sufficient to cause the defined loss of communication, an OR relationship is appropriate.

The events must be defined carefully. For example, a switch failure cannot cause communication loss if the device has an independent functioning path that automatically maintains communication.

4.2 AND gate

An AND gate means that all specified input events must occur together to produce the output event under the model's assumptions.

Example:

Top event: Machine loses its required production function
    AND
    ├── Primary control path is unavailable
    └── Required backup control path is also unavailable

This relationship is appropriate only if both conditions are necessary for the defined top event.

If the backup system is not capable of supporting the required production function, or does not cover the same operating conditions, the model must reflect that limitation.

4.3 AND versus OR comparison

Feature OR gate AND gate
Relationship Any input event can produce the output All specified input events are required
Input condition At least one input occurs Every required input occurs
Typical example Cable failure or device power loss causes communication loss Two required independent conditions must occur before a specific failure
Common mistake Listing events that are not individually sufficient Treating correlated events as independent without evidence
Main question Can any one input cause the output? Are all inputs necessary for the output?

Do not select gates based on intuition alone. The actual system architecture and failure behavior determine the correct logic.

5. Fault-tree symbols and event types

Formal FTA uses standardized symbols. In an awareness-level investigation, the event relationships are more important than memorizing every symbol.

Element Purpose Example
Top event Defines the undesired outcome Robot stops unexpectedly during automatic operation
Intermediate event Describes an event caused by lower-level events Servo drive trips
Basic event Represents a failure or condition not expanded further Cooling fan fails
OR gate Any input can cause the output Fan failure or blocked airflow causes inadequate cooling
AND gate All specified inputs are required A specific hazard requires both a hazardous condition and failure of a protective measure
Undeveloped event Identifies an event that is not analyzed further Internal drive failure where detailed internal data are unavailable
House event Represents a condition treated as true or false for the analysis Machine is operating in automatic mode
Transfer symbol Connects a branch to another section of a larger tree Shared power supply analyzed in a separate branch

A basic event is not necessarily a physically indivisible component. It is an event treated as sufficiently fundamental for the chosen analysis scope.

6. Define the top event correctly

A fault tree is only as useful as its top event.

A top event should specify the function that has been lost, the equipment or system involved, and the operating context.

Weak top event Better top event
PLC fault PLC loses communication with remote I/O station R12 during automatic operation
Robot problem Robot axis loses valid position feedback during commanded movement
CNC failure CNC spindle drive trips on overtemperature during sustained machining
Machine stops Conveyor stops unexpectedly while the production run is active
Safety issue Guard interlock fails to prevent hazardous motion under the specified test conditions

The top event should not be so broad that unrelated failures are mixed together. It should also not be so narrow that important failure paths are excluded.

Before building the tree, define:

  • The equipment and function being analyzed.
  • The operating mode.
  • The failure condition.
  • The relevant system boundaries.
  • Whether the analysis concerns a production failure, safety failure, or both.
  • The assumptions about backup systems, interlocks, and operator actions.

7. Worked example 1: VFD overtemperature trip

Problem statement

A variable-frequency drive trips on overtemperature during production.

Possible causes include insufficient cooling, excessive heat generation, abnormal loading, or a temperature-sensing problem.

A simplified fault tree could be:

Top event: VFD overtemperature trip
    OR
    ├── Inadequate heat removal
    │   OR
    │   ├── Cooling fan failure
    │   ├── Restricted airflow
    │   └── Excessive cabinet ambient temperature
    ├── Excessive heat generation
    │   OR
    │   ├── Excessive operating load
    │   ├── Operation outside approved drive limits
    │   └── Internal drive defect causing abnormal losses
    └── Temperature detection or interpretation fault
        OR
        ├── Temperature sensor fault
        └── Internal measurement or diagnostic fault

This is an illustrative fault tree. The exact branches depend on the VFD's design, diagnostic method, and operating conditions.

How to investigate

  1. Record the drive alarm code, temperature data, current, load, and event timestamps.
  2. Check fan operation, airflow, heatsink condition, and cabinet temperature.
  3. Compare actual load and operating conditions with the drive's approved limits.
  4. Verify whether the reported temperature is credible using an appropriate approved diagnostic method.
  5. Check whether the fault is caused by the drive's internal temperature, an external temperature input, or another monitored condition.

Example interpretation

If the fan is not operating, the heatsink is overheating, and the drive's diagnostics confirm that cooling is inadequate, the fan branch becomes strongly supported.

If the fan operates correctly but cabinet temperature is excessive, the investigation should focus on cabinet ventilation, ambient temperature, heat load, and installation requirements.

The tree guides investigation. It does not determine the root cause without evidence.

8. Worked example 2: PLC remote I/O communication loss

Problem statement

A PLC intermittently loses communication with a remote I/O station, causing the machine sequence to stop.

A simplified fault tree:

Top event: PLC loses required remote I/O data
    OR
    ├── Physical communication path unavailable
    │   OR
    │   ├── Cable or connector failure
    │   ├── Switch or port failure
    │   └── Network link interrupted
    ├── Remote I/O station unavailable
    │   OR
    │   ├── Device power loss
    │   ├── Module failure
    │   └── Device restart or watchdog event
    └── Communication configuration or data exchange fails
        OR
        ├── Incorrect device configuration
        ├── Connection or addressing mismatch
        └── Application or communication timeout

Investigation priorities

  • Review PLC fault history and module diagnostics.
  • Compare network switch logs with PLC and remote I/O timestamps.
  • Check the remote I/O power supply and device restart history.
  • Inspect the physical connection and cable route.
  • Verify the approved network configuration and device identity.
  • Distinguish complete device loss from stale application data.

If several remote devices fail simultaneously, investigate common power, network infrastructure, or shared environmental conditions. If only one device fails, local cable, connector, device, and configuration branches may deserve greater attention.

These patterns help prioritize testing but do not prove a cause by themselves.

9. Worked example 3: Robot axis feedback fault

Problem statement

A robot axis intermittently reports invalid encoder feedback during movement.

A simplified tree:

Top event: Robot axis cannot maintain valid position feedback
    OR
    ├── Feedback signal unavailable
    │   OR
    │   ├── Encoder failure
    │   ├── Feedback cable interruption
    │   └── Connector contact failure
    ├── Feedback signal becomes unreliable
    │   OR
    │   ├── Electrical interference
    │   ├── Shielding or grounding problem
    │   └── Cable damage affecting signal integrity
    └── Feedback is rejected by the control system
        OR
        ├── Incorrect feedback configuration
        ├── Drive feedback interface fault
        └── Diagnostic or communication problem

How the tree improves troubleshooting

The tree helps separate three different situations:

  • The encoder does not produce a valid signal.
  • The encoder produces a signal, but the transmission path corrupts or interrupts it.
  • The signal reaches the drive, but the control system cannot interpret or accept it.

These situations can produce similar alarms but require different corrective actions.

Use manufacturer-approved diagnostics to establish where the signal becomes invalid. Inspect cables and connectors, review the event timing, and compare the fault with axis movement and cable motion. Do not perform hazardous movement tests without the required controls and authorization.

10. Worked example 4: Machine fails to start

Problem statement

A machine does not start in automatic mode after the operator requests a cycle.

A simplified tree:

Top event: Machine does not start automatic cycle
    OR
    ├── Start request is not accepted
    │   OR
    │   ├── Start input is not received
    │   ├── Required operating mode is not selected
    │   └── Start request is rejected by sequence logic
    ├── One or more start permissives are not satisfied
    │   OR
    │   ├── Required sensor state is missing
    │   ├── Required actuator feedback is absent
    │   └── Process condition is outside the permitted range
    └── Motion or process execution is inhibited
        OR
        ├── Drive is not ready
        ├── A protective stop is active
        └── A relevant equipment fault remains active

This tree is a first-level diagnostic model. It does not mean every possible machine has the same start logic.

Investigation sequence

  1. Confirm the selected operating mode and the exact start request.
  2. Check whether the PLC receives the start signal.
  3. Check sequence conditions and permissives.
  4. Check active alarms, drive-ready signals, and relevant interlocks.
  5. Trace the first condition preventing the cycle from starting.
  6. Determine whether the missing condition is caused by a sensor, actuator, wiring, configuration, sequence logic, or legitimate process requirement.

Never bypass a safety interlock to force a machine to start. A fault tree is a diagnostic aid, not permission to defeat a protective function.

11. Common-cause failures

A critical FTA concept is the common-cause failure.

Two components may appear to be independent, but one shared condition can disable both. If the tree assumes independence without checking the architecture, it may underestimate the likelihood of system failure.

Examples include:

  • Two power supplies fed from the same failed upstream source.
  • Multiple network devices connected to a switch that loses power.
  • Redundant sensors exposed to the same contamination.
  • Two cooling fans affected by the same blocked airflow.
  • Backup controllers using the same defective configuration.
  • Multiple devices damaged by the same electrical surge.

For example, two nominally redundant controllers do not provide full protection against a shared power failure if both depend on the same unprotected supply.

During analysis, identify shared resources, common environments, shared software or configuration, and common maintenance practices.

12. Single-point failures and redundancy

A single-point failure is a failure of one component or condition that is sufficient to cause the defined system-level failure, given the specified operating state.

A redundant arrangement can reduce vulnerability only if the redundancy genuinely supports the required function and common-cause failures are adequately controlled.

Architecture Possible concern Investigation question
Single network switch Switch failure may disconnect all attached devices Is there an independent communication path?
Two power supplies sharing one upstream feed The shared feed can disable both Are the supplies independent at the relevant failure boundary?
Redundant controller pair Shared configuration or power may affect both What failures can disable both controllers?
Two sensors mounted in the same contaminated area Common contamination may affect both Are their failure mechanisms genuinely independent?
Primary cooling fan plus standby fan Both may be ineffective if airflow is blocked Does the backup fan overcome the same restriction?

Redundancy should be assessed at the function level, not merely by counting components.

13. Basic quantitative awareness

Fault trees can be used qualitatively or quantitatively. Quantitative analysis estimates the probability or frequency of the top event using probabilities or failure rates for lower-level events.

Such calculations require reliable input data and assumptions about dependencies, mission time, repair behavior, and system configuration.

For two independent events with probabilities \(P(A)\) and \(P(B)\):

For an OR relationship:

\[ P(A \cup B)=P(A)+P(B)-P(A)P(B) \]

For an AND relationship:

\[ P(A \cap B)=P(A)P(B) \]

The simplified AND equation applies when the events are independent. If they share a common cause, the calculation must account for that dependence.

For example, if two independent events each have a probability of \(0.01\) over a defined interval, the probability that both occur during that interval is:

\[ P(A \cap B)=0.01 \times 0.01=0.0001 \]

This is a mathematical illustration, not a real machine reliability estimate. Do not multiply component failure probabilities merely because the diagram contains an AND gate. Independence and the probability model must be justified.

Important quantitative limitations

  • Failure rates must be relevant to the actual component and operating conditions.
  • Probability values must refer to compatible time intervals and definitions.
  • Repair and restoration behavior may affect system unavailability.
  • Common-cause failures can invalidate independence assumptions.
  • Diagnostic coverage and latent failures may need explicit modeling.
  • A detailed numerical result is not automatically more trustworthy than a well-supported qualitative analysis.

For ordinary maintenance troubleshooting, qualitative fault-tree awareness is often sufficient. Formal quantitative FTA is more appropriate when reliability, availability, or safety analysis requires it.

14. Fault-tree analysis versus other RCA tools

Tool Primary purpose Typical use
Fault-tree analysis Model combinations of events that produce an undesired top event Complex failures, system dependencies, redundancy
5 Whys Trace a causal path into underlying conditions Relatively clear causal chain
Fishbone analysis Organize possible causes into categories Broad investigation and brainstorming
FMEA Identify potential failure modes, effects, and risk controls Proactive equipment and process risk analysis
Event timeline Establish the sequence of events Intermittent faults and multi-device incidents
Pareto analysis Prioritize failure types by frequency, downtime, or cost Maintenance improvement planning

The methods can be combined. A fishbone diagram may generate possible causes, a fault tree may model how they combine, and a 5 Whys investigation may explore a confirmed branch in greater depth.

15. Common mistakes in fault-tree analysis

Mistake Why it matters Better approach
Defining the top event too broadly Mixes unrelated failure mechanisms Specify the equipment function, failure condition, and operating state
Using incorrect AND or OR relationships Misrepresents the actual system logic Check whether each input is individually sufficient or jointly necessary
Treating all listed events as proven Confuses hypotheses with evidence Validate significant branches
Ignoring common-cause failures Overstates the benefit of redundancy Identify shared power, network, environment, and configuration dependencies
Assuming independent events without justification Produces unreliable probability estimates Model dependencies and common causes
Expanding the tree without a clear boundary Creates an unwieldy analysis Define scope and stop at an appropriate level of detail
Ignoring operating modes May include impossible or irrelevant combinations State the mode and assumptions for each analysis
Treating every protective stop as a failure of the safety system Confuses an intended response with a defect Define whether the top event is production interruption or loss of a safety function
Using the tree as a replacement for testing Produces an unverified explanation Confirm relevant branches with diagnostic and physical evidence
Failing to update the analysis after repairs Leaves the model disconnected from actual failure behavior Record findings and revise the tree when new evidence becomes available

17. Interview questions and answers

Q1. What is fault-tree analysis?

Fault-tree analysis is a systematic method that works backward from an undesired top event to identify the component failures and conditions that could cause it.

Q2. What is the difference between AND and OR gates?

An OR gate means any one input event can produce the output. An AND gate means all specified input events must occur together to produce the output under the model's assumptions.

Q3. What is a basic event?

A basic event is a component failure or condition treated as fundamental at the current level of analysis. It does not necessarily mean that the event cannot be investigated further.

Q4. What is a common-cause failure?

A common-cause failure occurs when one shared condition affects multiple components or paths, potentially defeating redundancy.

Q5. Why is the top event important?

It defines the failure being analyzed. An unclear top event can mix different failure mechanisms and produce misleading relationships.

Q6. Can fault-tree analysis identify the root cause automatically?

No. It structures possible causal paths. Evidence and testing are needed to identify which paths actually contributed to the failure.

Q7. Can fault trees be used quantitatively?

Yes. If suitable probability or failure-rate data and valid modeling assumptions are available, the tree can support quantitative reliability or risk calculations.

Q8. How would you use a fault tree for a remote I/O communication fault?

I would define the loss of required I/O communication as the top event, examine physical network, device power, hardware, configuration, and data-exchange branches, then test the relevant hypotheses against PLC and network diagnostics.

Q9. Why can redundant equipment still fail?

Redundant equipment may share power, network infrastructure, environment, configuration, or another common dependency that can disable multiple paths simultaneously.

Q10. When should the fault tree be updated?

When testing, repairs, configuration changes, or later incidents provide new evidence that changes the proposed failure paths or their relationships.

18. Completion checklist

  • The top event is specific and clearly defined.
  • The system boundary and operating conditions are documented.
  • Intermediate and basic events are distinguished.
  • AND and OR relationships match the actual system behavior.
  • Potential single-point failures are identified.
  • Common-cause failures and shared dependencies are considered.
  • Redundancy assumptions are checked against the real architecture.
  • Important branches are supported by diagnostic or physical evidence.
  • Unconfirmed hypotheses remain clearly identified as such.
  • Quantitative calculations are used only with justified assumptions and suitable data.
  • Corrective actions address the confirmed failure paths.
  • The analysis is updated when new evidence changes the model.
  • Effectiveness is verified under representative operating conditions.
