1. Definition of a Failure Mode

A failure mode is the specific way in which an asset, component, subsystem, or process fails to perform its required function.

It describes what kind of failure occurred, rather than merely describing the symptom, identifying the root cause, or explaining the physical mechanism.

Examples:

  • A proximity sensor fails to detect a target.
  • A PLC output fails to energize an actuator.
  • A VFD trips because of an overcurrent condition.
  • A CNC spindle fails to reach the commanded speed.
  • A robot encoder provides an incorrect or intermittent position signal.
  • A network switch loses communication with remote I/O.
  • A power supply produces an unstable 24 V DC output.

Identifying the failure mode helps maintenance personnel decide what evidence to collect, which components to inspect, and what corrective actions may prevent recurrence.

2. Function, Failure, Failure Mode, Mechanism, Cause, and Effect

These terms are related but have different meanings. Confusing them produces weak troubleshooting and ineffective corrective actions.

Term Meaning Industrial example
Function What the asset must do A sensor must detect a cylinder at its extended position
Functional failure Inability to meet the required performance standard The control system does not receive confirmation that the cylinder extended
Failure mode The specific way the function is lost or degraded Sensor fails to switch when the target arrives
Failure mechanism The physical, chemical, electrical, or logical process that produces failure Internal switching component degrades
Failure cause The initiating condition or reason that led to failure Excessive temperature accelerates component degradation
Failure effect The consequence of the failure at component, machine, or production level The PLC withholds the next sequence step
Symptom An observable indication of a problem HMI displays Cylinder Extend Timeout
Root cause The underlying reason established through systematic investigation Incorrect sensor mounting allowed repeated mechanical impact and premature damage

These relationships are not always one-to-one. A single failure mode may have several possible causes, and the same cause may produce several failure modes.

Example: Remote I/O communication failure

  • Function: Remote I/O exchanges input and output data with the PLC.
  • Functional failure: The PLC cannot obtain valid remote input data.
  • Failure mode: Communication between the PLC and remote I/O is lost.
  • Possible mechanism: Ethernet link interruption or network-interface malfunction.
  • Possible causes: Damaged cable, failed switch port, incorrect configuration, power loss, or excessive network disturbance.
  • Effect: The PLC may declare the adapter faulted, inhibit the sequence, or place affected outputs into configured fault states.
  • Symptom: Communication fault alarm or stale input values.
  • Root cause: Determined only after collecting evidence and verifying the actual initiating condition.

The alarm identifies an observed condition, not automatically the failed device or root cause.

3. Failure Modes at Different System Levels

Failure modes must be described at the level appropriate to the investigation. A description can be too broad to be useful or too detailed to support the decision being made.

Plant production system
    ↓
Production line
    ↓
Machine
    ↓
Subsystem
    ↓
Component
    ↓
Internal failure mechanism

Example of a robot position-feedback problem:

Level Example description
Production line Robot station cannot complete its cycle
Machine Robot motion sequence stops
Subsystem Servo position-feedback system fails
Component Encoder feedback becomes intermittent
Mechanism Internal connection or conductor intermittently opens
Cause Repeated flexing, connector damage, contamination, or another verified condition

For a maintenance breakdown record, “robot position-feedback failure” may be a suitable mode. For a component repair investigation, “encoder signal channel intermittently opens” may be more useful.

The correct level depends on the purpose of the analysis and the available evidence.

4. Major Categories of Failure Modes

Failure modes can be classified by the function that is lost and the way the failure manifests. These categories overlap; they are not mutually exclusive.

4.1 Electrical failure modes

Failure mode Typical evidence Possible causes
Open circuit No current flow or continuity Broken conductor, loose terminal, failed fuse
Short circuit Excessive current or protective trip Insulation damage, conductive contamination
High-resistance connection Voltage drop, localized heating Loose terminal, oxidation, damaged contact
Supply voltage absent Equipment does not power up Supply failure, fuse, wiring, upstream isolation
Supply voltage unstable Resets, fluctuating readings, erratic operation Poor connection, overload, failing supply
Insulation breakdown Leakage current, ground fault Aging insulation, moisture, overheating
Protective device fails to operate Expected disconnection does not occur Mechanical or electrical failure, incorrect selection

Maintenance caution: An open circuit is a failure mode. A broken wire is a physical condition that may represent the mechanism or immediate cause, depending on the analysis level.

4.2 Electronic failure modes

Failure mode Typical evidence Possible causes
No output Expected output is absent Failed output stage, missing supply, inhibition
Incorrect output Output differs from required value Component drift, damaged circuitry, incorrect calibration
Intermittent output Signal appears and disappears Cracked solder joint, connector fault, thermal sensitivity
Excessive offset or drift Reading changes over time Aging, temperature effects, reference instability
Internal overheating Thermal shutdown or damage Cooling failure, excessive loading, degraded components
Input channel failure One input channel does not respond Damaged input circuit, wiring, configuration

For PLC modules, drives, power supplies, and electronic test equipment, a reported module fault does not prove that the module itself has failed. External wiring, supply conditions, configuration, and connected loads must also be evaluated.

4.3 Mechanical failure modes

Failure mode Typical evidence Possible causes
Fracture Broken shaft, bracket, coupling, or component Fatigue, overload, impact
Excessive wear Increased clearance, backlash, vibration Lubrication failure, contamination, misalignment
Seizure Component cannot rotate or move Lubrication loss, bearing damage, contamination
Misalignment Vibration, uneven wear, coupling heating Installation error, foundation movement
Looseness Movement, noise, changing vibration Inadequate fastening, cyclic loading
Deformation Bent shaft, distorted bracket Impact, excessive force, thermal stress
Binding Mechanism moves with excessive resistance Contamination, damage, incorrect adjustment
Leakage Fluid or lubricant escapes Seal damage, worn surfaces, excessive pressure

4.4 Thermal failure modes

Examples include:

  • Excessive motor winding temperature.
  • VFD or servo-drive overtemperature.
  • Power-supply thermal shutdown.
  • CNC spindle bearing overheating.
  • Localized heating at terminals.
  • Excessive temperature variation affecting sensor readings.
  • Failure to maintain the required process temperature.

Possible contributing conditions include blocked ventilation, failed fans, excessive load, poor heat transfer, high ambient temperature, unsuitable enclosure design, or deteriorated thermal interfaces.

Temperature alarms indicate that a monitored condition crossed a threshold. They do not independently establish the root cause.

4.5 Pneumatic and hydraulic failure modes

Failure mode Typical evidence Possible causes
Insufficient actuator force Cylinder stalls or moves slowly Low pressure, leakage, excessive load
Failure to extend or retract Cylinder does not reach the required position Valve failure, mechanical binding, supply issue
Excessive leakage Pressure loss or fluid escaping Damaged seal, fitting, hose, or valve
Pressure instability Unstable force or motion Regulator, pump, accumulator, or leakage issue
Valve fails to shift Command changes but valve state does not Coil failure, spool sticking, contamination
Slow response Excessive cycle time Restricted flow, incorrect settings, wear
Uncontrolled movement Motion occurs outside intended behavior Control-valve or safety-related failure, stored energy, leakage path

Always consider stored pneumatic or hydraulic energy during inspection and repair. Isolation, depressurization, and verification must follow the machine-specific safety procedure.

4.6 Sensor and instrumentation failure modes

Common modes include:

  • No detection.
  • False detection.
  • Delayed detection.
  • Intermittent detection.
  • Incorrect analog measurement.
  • Measurement drift.
  • Saturated output.
  • Excessive noise or unstable signal.
  • Loss of calibration.
  • Incorrect scaling or engineering-unit conversion.
  • Incorrect sensor response to the target or process variable.

Examples:

  • A proximity sensor remains ON even when the target is absent.
  • A photoelectric sensor misses a component because its detection conditions are unsuitable.
  • A 4–20 mA pressure transmitter produces a signal inconsistent with actual pressure.
  • An analog input reports the correct electrical signal but the PLC scales it incorrectly.
  • A temperature sensor responds too slowly because of poor installation or excessive thermal lag.

Do not automatically classify every incorrect reading as a failed sensor. The measurement chain includes the process, sensor, wiring, power supply, input channel, scaling, communication, and display.

4.7 PLC, software, and configuration failure modes

Failure mode Typical evidence Possible causes
Logic does not execute as intended Sequence stalls or follows an unexpected branch Logic defect, incorrect condition, wrong operating mode
Output command absent PLC output tag remains OFF Interlock, permissive, sequence condition, logic issue
Incorrect output command PLC commands an unintended state Programming error, wrong mapping, unexpected state
Timer behavior incorrect Timeout or delay differs from expectation Incorrect preset, time base, reset condition, logic
Wrong I/O mapping Logic reads or commands the wrong point Addressing or configuration error
Parameter mismatch Device behavior differs after replacement Incorrect parameter restoration or revision
Program or configuration corruption Unexpected behavior or failure to load Storage, transfer, or integrity problem
Unexpected state retention Old value persists when a new value is expected Latching, retentive data, reset behavior, software design

A program fault and a physical hardware fault can produce similar symptoms. Compare the intended logic, online state, actual I/O signals, and machine behavior before deciding which category applies.

Any software change must follow the site's authorization, backup, validation, and change-control requirements.

4.8 Communication and network failure modes

Typical modes include:

  • Complete loss of communication.
  • Intermittent communication.
  • Excessive communication latency.
  • Data updates stop while the connection appears active.
  • Corrupted or invalid data.
  • Duplicate or conflicting device identity.
  • Loss of synchronization.
  • Network congestion or excessive retries.
  • Device connection instability.
  • Communication available but application data incorrect.

Examples include a PLC losing a remote I/O adapter, a CNC losing communication with an external data service, or a SCADA screen displaying stale values.

A successful ping or an illuminated network LED does not prove that the required industrial protocol, device connection, or application data exchange is healthy.

4.9 Drive, motor, servo, and CNC failure modes

Asset Failure mode Evidence to examine
Induction motor Fails to start Supply, protection, control command, mechanical load
Induction motor Excessive vibration Bearings, alignment, mounting, load, electrical condition
VFD Trips during acceleration Load, acceleration settings, current, DC bus, motor condition
VFD Fails to produce output Enable conditions, faults, parameters, power stage
Servo system Position error exceeds limit Feedback, tuning, mechanics, load, command
Robot Position feedback becomes intermittent Encoder data, connectors, cable flexing, drive diagnostics
CNC spindle Fails to reach commanded speed Drive status, spindle feedback, load, mechanics
CNC axis Positioning accuracy degrades Backlash, compensation, feedback, mechanics
CNC machine Tool-change sequence fails Position signals, pneumatic conditions, interlocks, sequence logic

These are examples of failure modes, not guaranteed diagnoses. Multiple independent faults can create similar machine-level symptoms.

4.10 Safety-related failure modes

Safety-related failure modes require special attention because their consequences can include hazardous motion or loss of a protective function.

Examples include:

  • Emergency-stop circuit fails to interrupt the intended control path.
  • Guard interlock fails to detect an open guard.
  • Safety sensor produces an invalid or missing signal.
  • Safety relay or safety controller fails to achieve its required response.
  • Feedback monitoring fails to detect an unsafe discrepancy.
  • A safety output does not reach its intended safe state.
  • A protective function becomes unavailable after a component fault.

Distinguish between:

  • Safe failure: A failure that leads to or maintains the defined safe state for the particular function.
  • Dangerous failure: A failure that prevents the safety function from performing its required protective action.

These classifications depend on the safety function, architecture, fault response, and applicable safety requirements. A failure that stops a machine is not automatically safe in every context, and a stopped machine is not necessarily free from hazardous stored energy.

Never bypass a safety circuit to confirm a suspected failure during production. Use the approved safety-validation procedure and qualified personnel.

5. Failure Mode vs Failure Effect

A failure mode describes how a function fails. A failure effect describes what happens because of that failure.

Failure mode Local effect Machine-level effect Production-level effect
Sensor fails to detect target PLC input remains OFF Sequence cannot advance Cycle delay or line stoppage
Remote I/O communication is lost Input data becomes unavailable or invalid Machine sequence is inhibited or interrupted Production interruption
VFD fails to deliver motor torque Motor does not produce required motion Conveyor or spindle stops Output loss
CNC feedback becomes invalid Axis position cannot be trusted Axis motion is inhibited or interrupted Machining operation stops
Cooling fan fails Cooling airflow decreases Drive temperature rises or protection activates Reduced availability
Safety interlock fails to detect a guard state Protective input may be invalid Required safety response may be unavailable Personnel hazard and equipment risk

A complete analysis follows the effect through the system hierarchy. The same component failure may have different consequences depending on redundancy, machine design, operating mode, and fault-response logic.

6. Failure Mode vs Failure Cause

A failure mode is not the same as its cause.

Observation Classification Why
Motor does not start Functional failure or symptom It describes the observed outcome
Contactor fails to close Failure mode It identifies how the switching function failed
Coil winding is open Electrical condition or mechanism-level finding It describes the condition of the coil
Coil overheated due to incorrect voltage Potential cause and mechanism chain It explains a possible route to failure
Sensor does not detect the target Failure mode It describes loss of detection
Sensor bracket is loose Physical condition It may contribute to the failure but needs verification
Repeated vibration loosens the bracket Possible causal condition It explains why the looseness develops
Incorrect PLC output mapping Configuration failure mode or cause Classification depends on the system level being analyzed

The same finding can be a failure mode at one level and a cause at another. Always define the system boundary and analysis level before classifying the information.

7. Failure Modes by Performance Condition

Failure is not limited to a component being completely dead.

7.1 Complete functional failure

The required function is entirely unavailable.

Examples:

  • A 24 V DC power supply has no output.
  • A motor cannot rotate.
  • A network adapter cannot establish communication.
  • A sensor produces no usable output.

7.2 Partial or degraded failure

The function remains available but no longer meets its required performance standard.

Examples:

  • A motor operates but overheats under normal load.
  • A sensor detects targets only at an abnormally short distance.
  • A CNC axis moves but exceeds its positioning tolerance.
  • A network connection works but produces excessive latency.
  • A pressure transmitter responds but has unacceptable measurement error.

Degraded performance can be more difficult to identify because the equipment may continue operating while quality, reliability, or safety margins deteriorate.

7.3 Intermittent failure

The function is lost and later restored, either spontaneously or when operating conditions change.

Examples:

  • A robot feedback signal drops out during cable movement.
  • A PLC input changes state when a connector vibrates.
  • A communication connection repeatedly disconnects and reconnects.

Intermittent failure is covered in more detail in the next topic.

7.4 Premature failure

The component fails earlier than expected under its specified operating conditions or expected service life.

Examples:

  • A bearing fails soon after replacement.
  • A power supply repeatedly fails in the same enclosure.
  • A cable develops conductor damage after a short period of machine operation.

Premature failure is a classification relative to expectations. It does not identify the cause by itself.

7.5 Repeated or recurring failure

The same or a closely related failure mode occurs again after repair or restoration.

Examples:

  • The same VFD trips repeatedly under the same production conditions.
  • A repaired sensor cable fails again at the same bend location.
  • A CNC spindle repeatedly develops an overheating problem.

A recurrence should trigger review of repair quality, operating conditions, causal assumptions, and corrective-action effectiveness.

8. How to Identify Failure Modes Systematically

A reliable failure-mode list begins with the required function, not with a list of spare parts.

Step 1: Define the function and performance standard

Describe what the asset must do, under which conditions, and to what standard.

Weak definition: “PLC works.”

Better definition: “The PLC reads field inputs, executes the approved sequence, and updates outputs within the required response time.”

For a CNC spindle, define the required speed range, acceleration behavior, feedback validity, and operating limits where relevant.

Step 2: Establish the system boundary

Decide whether the analysis concerns the complete machine, subsystem, or component.

For example, “axis fails to move” is a machine-level observation. “Servo drive does not generate the commanded motor output” is a narrower failure mode.

Step 3: Break the system into functional elements

Use drawings, I/O lists, electrical schematics, pneumatic diagrams, network topology, manuals, and asset records.

For a PLC-controlled cylinder, relevant elements may include:

  • PLC sequence logic.
  • Digital output module.
  • Solenoid valve and coil.
  • Pneumatic supply.
  • Cylinder and mechanical load.
  • Position sensors.
  • Feedback wiring.
  • Safety and permissive conditions.

Step 4: Examine actual failure evidence

Collect available evidence before assuming a cause.

Useful evidence includes:

  • Alarm history and event timestamps.
  • PLC input/output states.
  • Drive and CNC diagnostic records.
  • Actual supply voltage and current.
  • Network status and device diagnostics.
  • Physical damage, looseness, leakage, or overheating.
  • Production conditions and machine operating mode.
  • Maintenance history and replaced-part records.
  • Operator observations of the first abnormal behavior.

Follow electrical safety requirements and approved diagnostic procedures when measuring live equipment.

Step 5: Describe the failure mode precisely

Use a description that is specific enough to guide investigation but does not claim an unverified root cause.

Weak: “Electrical problem.”

Better: “PLC digital input remains OFF while the sensor output is confirmed ON at the field device.”

Weak: “Drive problem.”

Better: “VFD trips during acceleration when commanded frequency rises above the observed threshold.”

Weak: “Robot problem.”

Better: “Robot position-feedback value becomes invalid during wrist-axis motion.”

Step 6: List plausible mechanisms and causes separately

Do not force a single cause before the evidence supports it.

For an intermittent sensor signal, possible explanations could include a loose terminal, damaged cable, unstable supply, defective sensor, or input-channel problem. Each hypothesis should be tested using a controlled, safe method.

Step 7: Verify and classify

Confirm that the proposed failure mode actually occurred. Separate confirmed observations from assumptions and unresolved hypotheses.

A useful evidence classification is:

  • Confirmed: Directly demonstrated or supported by reliable records.
  • Probable: Strongly supported but not yet conclusively demonstrated.
  • Possible: Technically plausible but not adequately tested.
  • Rejected: Contradicted by evidence.

Step 8: Record the failure consistently

Use standard asset identifiers, component tags, timestamps, failure descriptions, operating conditions, and repair records. Consistent wording makes repeated failures easier to identify.

9. Worked Example: PLC-Controlled Cylinder Does Not Extend

Reported problem

The operator reports that the machine stops because a cylinder fails to extend. The HMI displays Cylinder Extend Timeout.

Functional analysis

Required function: The cylinder must extend and reach its confirmed position within the allowed cycle time.

Item Finding or hypothesis
Symptom HMI reports cylinder extend timeout
Functional failure Cylinder position confirmation is not received within the allowed time
Candidate failure mode 1 PLC output command is absent
Candidate failure mode 2 Solenoid valve does not shift
Candidate failure mode 3 Pneumatic pressure is insufficient
Candidate failure mode 4 Cylinder or mechanism is mechanically bound
Candidate failure mode 5 Cylinder extends but the sensor fails to confirm position
Candidate failure mode 6 Sensor signal reaches the field terminal but not the PLC input
Candidate failure mode 7 Incorrect sequence condition or timer configuration
Required evidence PLC logic state, output state, valve status, pressure, physical motion, sensor state, input status, and event history

Diagnostic reasoning

  1. Check whether the sequence conditions permit extension.
  2. Check whether the PLC issues the expected command.
  3. Verify the relevant output and field-side electrical conditions using the approved procedure.
  4. Verify the valve response and pneumatic supply conditions.
  5. Observe whether the cylinder physically moves.
  6. If the cylinder reaches its position, verify the sensor response and the signal path to the PLC.
  7. If the physical behavior and electrical signals are correct, review sequence logic, input mapping, and timeout settings.

The exact sequence depends on the machine design and safety procedure. Do not bypass interlocks or force outputs to make the machine move.

Example conclusion

Suppose evidence confirms that the cylinder physically extends, the sensor indicator turns ON, but the PLC input remains OFF. The failure mode can then be narrowed to loss of the position signal between the field sensor and the PLC input, or a failure in the input channel itself.

Further testing is needed to distinguish wiring, terminal, module, and configuration faults. The HMI timeout alone does not identify the failed component.

10. Worked Example: Recurring VFD Overcurrent Trip

Reported problem

A conveyor VFD repeatedly trips on overcurrent during acceleration after maintenance clears the fault and restarts the equipment.

Analysis element Example
Symptom VFD displays an overcurrent trip
Functional failure Drive cannot complete the required acceleration
Failure mode Drive trips on overcurrent during acceleration
Possible mechanisms Excessive current demand, output-stage fault, or abnormal motor current
Possible causes Excessive mechanical load, acceleration setting, motor or cable fault, incorrect parameters, drive defect
Evidence required Fault timestamp, current trend, motor and cable checks, mechanical load, parameter comparison, supply and drive diagnostics
Corrective-action requirement Verify the actual cause and validate operation under representative conditions

Replacing the VFD immediately may restore production temporarily without correcting the underlying problem. If excessive mechanical load or an incorrect acceleration setting remains, the replacement may trip in exactly the same way.

11. Failure Modes and FMEA

Failure Modes and Effects Analysis (FMEA) is a structured method for identifying how functions or components could fail, examining the resulting effects, and prioritizing risk-reduction actions.

FMEA is useful before failures occur. Root cause analysis, by contrast, investigates a particular observed problem to establish why it happened.

Typical FMEA fields

Field Purpose
Asset or function Defines what is being analyzed
Requirement Defines expected performance
Failure mode Describes how the function can fail
Failure effect Describes local and system-level consequences
Potential cause Lists possible causal conditions
Existing controls Identifies preventive and detection controls
Severity Evaluates consequence seriousness
Occurrence Evaluates likelihood or frequency under the selected method
Detection Evaluates the effectiveness of detection controls, when the method uses this rating
Recommended action Defines risk-reduction work
Responsible person and due date Establishes ownership and completion timing
Verification Confirms that actions were completed and effective

Example FMEA entry

Field Example
Asset/function Remote I/O adapter exchanges PLC data with field modules
Failure mode Communication between PLC and remote I/O is lost
Effect Input data becomes unavailable and the machine sequence may stop
Potential causes Cable damage, adapter power loss, switch-port fault, configuration mismatch
Existing controls Communication diagnostics and HMI fault alarm
Recommended action Improve fault logging, verify network and power conditions, inspect cable routing, and validate recovery behavior
Verification Simulate or safely reproduce approved fault conditions and confirm diagnostics and machine response

This is an illustrative entry, not a completed risk assessment. Severity, occurrence, and detection ratings must follow the organization's approved criteria.

Risk Priority Number awareness

Some FMEA methods use the Risk Priority Number:

\[ RPN = S \times O \times D \]

Where:

  • \(S\) = Severity rating.
  • \(O\) = Occurrence rating.
  • \(D\) = Detection rating.

An organization's rating scale and calculation method must be followed. Not all FMEA methods use RPN; some use action-priority tables or other risk-evaluation methods.

RPN also has limitations. Different combinations of severity, occurrence, and detection can produce the same number, even though their risk profiles differ. A low overall number must not be used to dismiss a potentially catastrophic or safety-critical failure mode. Prioritize serious consequences, applicable safety requirements, and the organization's formal risk criteria.

12. Failure Modes vs RCA and Fault-Tree Analysis

These methods support each other but serve different purposes.

Method Main question Example use
Failure-mode identification How can the function fail? List possible remote I/O communication failure modes
FMEA What happens if it fails, and what should be prioritized? Rank risks and define preventive or detection actions
Root cause analysis Why did this specific failure occur? Investigate why the remote I/O connection repeatedly drops
Fault-tree analysis What combinations of events can produce the defined top event? Analyze conditions that can cause a machine to lose control-system availability

A failure mode can be used as an initiating event or intermediate event in a fault tree. However, failure-mode identification alone does not establish causal relationships or calculate system reliability.

13. How Failure Modes Improve Maintenance

Preventive maintenance

Maintenance tasks should address credible degradation and failure modes rather than being performed merely because a calendar says so.

Examples:

  • Inspect cable routing and strain relief where conductor fatigue is credible.
  • Check cooling airflow and fan condition for equipment vulnerable to overheating.
  • Inspect mechanical alignment and lubrication where wear or misalignment can occur.
  • Verify backup integrity and configuration records where recovery from data loss matters.

Predictive maintenance

Use condition indicators that are relevant to the failure mode.

Failure mode Potential condition indicator
Bearing degradation Vibration, temperature, noise, lubricant condition
Motor insulation degradation Insulation-test results and electrical condition indicators
Cooling failure Temperature trend, fan status, airflow
Mechanical misalignment Vibration pattern and alignment measurements
Network instability Link events, communication errors, latency, device diagnostics
Sensor drift Calibration checks and comparison with a trusted reference

No single indicator detects every failure mode. Choose methods appropriate to the asset, failure mechanism, operating environment, and consequences.

Spare-parts planning

Failure modes help determine which components should be stocked and what restoration resources are needed.

Consider:

  • Consequence of failure.
  • Failure history and credible frequency.
  • Component lead time.
  • Availability of approved substitutes.
  • Compatibility and configuration requirements.
  • Obsolescence risk.
  • Repairability and vendor support.
  • Required tools, test equipment, and technical expertise.

A frequently failing component is not automatically the most critical spare. A rarely failing component with a long lead time and severe production consequence may deserve higher priority.

Reliability improvement

A standardized failure-mode database supports:

  • Pareto analysis of recurring failure modes.
  • Identification of common causes across multiple machines.
  • Evaluation of design weaknesses.
  • Improved PM and condition-monitoring plans.
  • Better spare-part and obsolescence decisions.
  • More effective alarm rationalization.
  • More consistent maintenance handovers.
  • Verification of corrective-action effectiveness.

14. Failure-Mode Recording Template

Use a consistent format in maintenance reports, SAP notifications, breakdown logs, or an RCA database.

Field Example entry
Date and time Actual event timestamp
Asset ID Approved machine or equipment identifier
Component tag Actual device tag
Required function What the component must do
Failure mode Specific way the function failed
Observed symptom Alarm, noise, trip, measurement, or behavior
Operating condition Speed, load, mode, temperature, or cycle stage
Immediate action Safe action taken to restore or stabilize the system
Evidence Measurements, logs, photographs, diagnostics, or inspection findings
Confirmed cause Verified causal condition, or Not yet confirmed
Corrective action Repair or change performed
Verification Test results showing required function was restored
Recurrence status New event or recurrence of a previously recorded mode

Use the following principles when entering information:

  • Record observations separately from assumptions.
  • Avoid generic entries such as PLC fault, electrical issue, or machine problem when more precise evidence is available.
  • Record the actual failure mode even when the root cause remains unknown.
  • Do not record a component as defective solely because replacing it restored operation; consider disturbance of connections, resets, changed conditions, and other possible explanations.
  • Preserve the original alarm and diagnostic data when possible.
  • Verify the repair under representative operating conditions and within approved safety constraints.

15. Common Mistakes in Failure-Mode Analysis

  1. Treating an alarm as a failure mode without checking the function. An alarm is an indication and may describe a downstream consequence rather than the actual failure.
  2. Confusing the failure mode with its cause. “Loose terminal” may be an observed condition, while the failure mode might be loss of the control signal.
  3. Choosing a mode that is too broad. “Machine failure” does not guide diagnosis, preventive maintenance, or spare-part planning.
  4. Choosing a mode that is too detailed for the task. A component-level mechanism may be unnecessary when evaluating production-line availability.
  5. Assuming one symptom has only one cause. Similar symptoms can originate from wiring, hardware, configuration, software, process conditions, or interactions between them.
  6. Assuming the replaced part was necessarily defective. Replacement may temporarily alter the conditions that caused the problem.
  7. Ignoring degraded performance. Equipment can remain operational while measurements, cycle time, accuracy, or safety margins deteriorate.
  8. Recording only successful repairs. The failure mode, evidence, operating conditions, and unsuccessful diagnostic findings are also useful.
  9. Treating FMEA rankings as proof. Risk scores support prioritization; they do not replace technical evidence or mandatory safety controls.
  10. Failing to verify the corrective action. A machine restarting does not by itself prove that the failure has been eliminated.

16. Interview Questions and Answers

Q1. What is a failure mode?

A failure mode is the specific way an asset or function fails to meet its required performance. Examples include an open circuit, a sensor failing to detect a target, or a drive tripping during acceleration.

Q2. What is the difference between a failure mode and a failure mechanism?

The failure mode describes how the function fails. The failure mechanism describes the physical, electrical, chemical, or logical process producing that failure. For example, intermittent encoder feedback is a failure mode; conductor fatigue fracture may be the mechanism.

Q3. What is the difference between a failure mode and a root cause?

A failure mode describes what went wrong. A root cause explains the underlying condition responsible for the observed failure, established through evidence and investigation.

Q4. Is an alarm a failure mode?

Not necessarily. An alarm is an indication generated by a device or control system. It can point toward a failure mode, but it may also indicate an operating condition, an upstream problem, or a consequence of another fault.

Q5. What is FMEA?

FMEA is a structured method for identifying potential failure modes, evaluating their effects and possible causes, assessing risk, and defining actions to reduce that risk.

Q6. What is the difference between FMEA and RCA?

FMEA is generally proactive and examines potential failures. RCA investigates an actual problem to establish why it occurred and what corrective action can prevent recurrence.

Q7. How would you identify a PLC-related failure mode?

Define the PLC's required function, inspect the program and I/O configuration, compare commanded and actual field states, examine diagnostics and event history, and distinguish missing logic commands from output-module, wiring, field-device, communication, or process faults.

Q8. Why is a precise failure-mode description important?

It makes breakdown records comparable, improves troubleshooting, helps identify recurring patterns, supports appropriate PM/PdM tasks, and makes corrective-action effectiveness easier to evaluate.

Q9. Can one failure cause several failure modes?

Yes. For example, unstable control power may cause communication loss, PLC resets, sensor dropouts, and drive-control faults. The causal relationship must be established for the specific system.

Q10. What should be done when the failure mode is known but the cause is not?

Record the confirmed failure mode, preserve evidence, document unresolved hypotheses, perform controlled diagnostic tests, and avoid assigning an unverified root cause.

17. Practical Completion Checklist

Before closing a failure-mode analysis, verify the following:

  • The required function and performance standard are defined.
  • The system boundary and analysis level are clear.
  • The failure mode is specific and distinct from the symptom.
  • The effect on the component, machine, and production process is considered.
  • Potential mechanisms and causes are recorded separately.
  • Findings are supported by measurements, diagnostics, inspection, or reliable records.
  • Confirmed facts are distinguished from hypotheses.
  • Safety implications and required protective functions are considered.
  • Corrective actions address the verified problem and relevant risk.
  • Restoration is verified under appropriate operating conditions.
  • The record is standardized so recurring failures can be analyzed.
  • The effectiveness of longer-term corrective actions will be reviewed.
