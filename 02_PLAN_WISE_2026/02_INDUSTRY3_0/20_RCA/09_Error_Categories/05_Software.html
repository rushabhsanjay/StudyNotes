1. Definition of Software Error

A software error is a defect, incorrect logic, invalid data-handling behavior, missing functionality, or other weakness in a software system that causes it to behave differently from its intended or required behavior.

In industrial automation, software errors can occur in PLC programs, CNC programs, robot programs, HMI applications, SCADA systems, drive-control applications, industrial PCs, communication software, databases, and data-processing systems.

Examples include:

  • PLC logic failing to execute a required sequence.
  • A robot program selecting the wrong target position.
  • CNC code commanding an incorrect movement.
  • HMI controls displaying the wrong machine status.
  • SCADA showing stale data as if it were live.
  • An alarm failing to activate when a required condition occurs.
  • A program failing to recover after communication loss.
  • An incorrect data conversion producing a wrong engineering value.
  • A software update introducing a new machine fault.
  • A database or Node-RED flow storing incorrect tag values.

Core principle: A controller can execute software exactly as programmed while the machine still behaves incorrectly because the program itself does not meet the required functional behavior.

A software error may be the immediate cause of a breakdown, a contributing factor, or the root cause of a recurring failure. The classification depends on evidence and the causal relationship.

2. Software Error vs Other Failure Categories

Software-related symptoms can resemble hardware, wiring, and configuration failures. The distinction must be established during investigation.

Category Meaning Industrial example
Software error Program logic or application behavior is incorrect PLC sequence advances before the required condition is satisfied
Parameter error A device setting or operating value is incorrect VFD acceleration time is set incorrectly
Wiring error Physical signal or power path is defective Sensor signal does not reach the PLC input
Component error A device or internal circuit has failed PLC input channel does not respond to a valid signal
Configuration error Device or application setup is incorrect PLC is mapped to the wrong remote I/O configuration
Communication error Data exchange is disrupted or incorrect SCADA cannot receive fresh PLC values
Human error An action deviates from the required procedure An engineer downloads an unapproved program revision
Design error Requirements, architecture, or system design are inadequate The sequence specification does not define behavior after sensor failure

These categories can overlap. For example, incorrect PLC logic may be introduced by an unreviewed software change, while an unsuitable design requirement may have encouraged the original logic.

3. Where Software Errors Occur

Machine requirements
    ↓
Control and sequence design
    ↓
PLC, CNC, robot, or drive application
    ↓
HMI and SCADA applications
    ↓
Communication and data processing
    ↓
Database, historian, and reporting
    ↓
Operator interaction and machine behavior

Software faults can originate at any layer or at the interfaces between layers.

For example, a pressure transmitter may provide a correct analog value, the PLC may scale it correctly, but the SCADA application may display a stale value because it fails to handle communication-quality status.

The field instrument is not necessarily faulty. The failure may be in the data-handling software.

4. Major Categories of Software Errors

4.1 Logic errors

A logic error occurs when the program's decision-making behavior does not match the required function.

Examples:

  • Incorrect Boolean conditions.
  • Missing permissives.
  • Incorrect comparison operators.
  • Wrong sequence transitions.
  • Incorrect branch selection.
  • Incomplete interlocks.
  • Incorrect handling of simultaneous conditions.
  • A reset operation clearing a required state.
  • An output command remaining active when it should be removed.

Example:

A PLC sequence starts a clamp before confirming that the workpiece is present.

The program may execute consistently, but the sequence does not enforce the required condition.

RCA method:

  1. Identify the expected behavior.
  2. Record the actual sequence and signal states.
  3. Trace the relevant logic path.
  4. Compare the logic with the approved functional specification.
  5. Confirm whether the mismatch caused the observed failure.
  6. Test the correction under approved conditions.

4.2 Sequence and state-transition errors

Industrial machines often operate through defined states such as idle, loading, clamping, machining, unloading, and fault recovery.

A sequence error occurs when the program enters, exits, or skips a state incorrectly.

Examples:

  • The machine advances before motion completion is confirmed.
  • A step is skipped after a reset.
  • A timeout causes the sequence to advance instead of entering a fault state.
  • A fault reset resumes operation from an invalid state.
  • A restart begins with retained commands from the previous cycle.
  • Two sequence branches become active when only one should be active.

A useful way to investigate these failures is to reconstruct the sequence using timestamps, sensor states, commands, and step numbers.

Evidence Purpose
Active sequence step Establishes where the program was operating
Command output Shows what the program requested
Feedback signal Shows whether the expected response occurred
Transition condition Shows why the sequence advanced or stopped
Fault and reset history Establishes how abnormal behavior was handled
Relevant timestamps Helps reconstruct event order

Do not assume that the last alarm displayed is the first event in the failure chain.

4.3 Timing and race-condition errors

Timing errors occur when software behavior depends on event order, scan timing, task execution, communication delay, or signal duration in an unintended way.

Examples:

  • A short sensor pulse is missed by the application.
  • Two tasks access shared data without suitable coordination.
  • A sequence advances before feedback becomes valid.
  • A timer expires earlier than the real process can complete.
  • A handshake signal is cleared before the receiving device processes it.
  • A robot and PLC disagree about when an operation has completed.
  • An application assumes messages always arrive in a particular order.

A race condition occurs when the result depends on the relative timing or ordering of events that the program does not handle reliably.

For example, a PLC sequence may set a request bit and clear it before a communication task or receiving controller recognizes the request. The handshake may work under normal conditions but fail when task timing changes.

Investigation should examine the actual timing requirements, event ordering, task configuration, signal duration, and communication behavior.

4.4 Missing fault-handling logic

Software should define how the system responds to relevant abnormal conditions.

Potential errors include:

  • No timeout for a device response.
  • No detection of missing sensor feedback.
  • Failure to detect stale communication data.
  • No recovery path after a non-safety-related device fault.
  • Repeated automatic retries without a defined limit.
  • Fault status cleared before diagnostic evidence is captured.
  • Invalid data accepted as a valid measurement.
  • The application continuing after a required subsystem becomes unavailable.

A robust application distinguishes normal operation from uncertain or invalid conditions.

For example, if SCADA communication is lost, the dashboard should not continue presenting the last received value as though it were current. It should indicate that the data is stale or unavailable according to the application's requirements.

4.5 Data-handling errors

Software can process the wrong value even when the field signal and communication link are functioning correctly.

Examples include:

  • Incorrect scaling.
  • Incorrect engineering-unit conversion.
  • Integer overflow or truncation.
  • Incorrect signed or unsigned interpretation.
  • Incorrect array indexing.
  • Wrong tag mapping.
  • Data type mismatch.
  • Stale values being accepted.
  • Incorrect timestamp handling.
  • Database fields receiving values in the wrong order.

For a linear analog signal, scaling may be expressed as:

\[ EU=EU\_{\min}+\frac{Raw-Raw\_{\min}}{Raw\_{\max}-Raw\_{\min}}(EU\_{\max}-EU\_{\min}) \]

Where:

  • \(EU\) is the engineering-unit value.
  • \(Raw\) is the measured raw input.
  • \(Raw\_{\min}\) and \(Raw\_{\max}\) are the raw measurement limits.
  • \(EU\_{\min}\) and \(EU\_{\max}\) are the engineering-unit limits.

If the configured raw limits do not match the actual module representation, the resulting engineering value can be incorrect even when the transmitter is healthy.

Always verify the actual data representation and configuration for the specific PLC and module.

4.6 Alarm and diagnostic software errors

Alarm systems help operators and maintenance engineers identify abnormal conditions. Incorrect alarm logic can hide the true fault or create unnecessary downtime.

Examples:

  • Alarm conditions use the wrong tag.
  • Alarm thresholds are incorrect.
  • A required alarm is missing.
  • A fault is cleared automatically before the operator sees it.
  • Multiple secondary alarms obscure the initiating fault.
  • Alarm messages are too vague to identify the affected subsystem.
  • The application reports a communication fault as a process fault.
  • Alarm timestamps are inconsistent across devices.

An alarm flood can occur when one initiating event causes many dependent alarms. RCA should identify the first meaningful event and distinguish it from secondary consequences.

4.7 HMI and SCADA software errors

HMI and SCADA applications can mislead operators if their displays do not accurately represent the system state.

Examples:

  • A button appears enabled when the machine cannot accept the command.
  • A screen displays the wrong machine's data.
  • A tag is linked to the wrong PLC address.
  • A status indicator does not update.
  • An alarm banner hides an important message.
  • A stale value appears normal.
  • A command is sent without appropriate feedback confirmation.
  • Units are displayed incorrectly.
  • The screen fails to distinguish commanded state from actual state.

A useful distinction is:

  • Commanded state: What the software has requested.
  • Actual state: What feedback indicates the equipment is doing.
  • Data quality: Whether the feedback is current and valid.

For example, a green motor indicator should not automatically mean that the motor is physically running if it only represents the PLC's run command.

4.8 Communication and protocol-handling errors

Software may mishandle communication even when the physical network is healthy.

Examples:

  • Incorrect node or device addressing.
  • Incorrect message structure.
  • Incorrect data offsets.
  • Unsupported data types.
  • Incorrect byte or word order.
  • Improper timeout handling.
  • Missing reconnection logic.
  • Duplicate message processing.
  • Incorrect request-response association.
  • Failure to detect stale values.
  • Incorrect handling of device status or quality flags.

In a PLC-to-SCADA system, successful network connectivity does not prove that the correct tag values are being exchanged.

The investigation must distinguish between physical connectivity, protocol communication, data mapping, and application interpretation.

4.9 CNC and robot program errors

CNC and robot software errors can directly affect movement, sequence execution, production quality, and equipment condition.

Examples:

  • Incorrect coordinate selection.
  • Incorrect tool or work offset usage.
  • Wrong approach or retract sequence.
  • Incorrect robot frame or tool data selection.
  • Incorrect workpiece handling sequence.
  • Missing recovery handling.
  • Incorrect program branch selection.
  • Incorrect interpretation of a program variable.
  • Unintended motion after a restart.
  • Inadequate handling of a failed peripheral device.

For CNC systems, a suspected program error must be distinguished from incorrect offsets, machine parameters, tool condition, fixture setup, and mechanical problems.

For robot systems, distinguish program logic from mastering, frame data, payload configuration, mechanical condition, and external-axis configuration.

Never test suspected motion-program changes by bypassing guarding or safety functions.

4.10 Software version and change-management errors

A machine may begin failing after a software change even when the changed program compiles and downloads successfully.

Potential causes include:

  • Unapproved logic changes.
  • Incorrect revision downloaded.
  • Partial or incomplete download.
  • Incorrect firmware compatibility.
  • Missing configuration files.
  • Unrecorded parameter dependencies.
  • Incorrect backup restored.
  • Changes made online without updating the master copy.
  • Different program revisions used on similar machines.
  • An update altering previously working behavior.

A software change should be traceable to an approved revision, an identified requirement, a test result, and a controlled deployment record.

5. PLC Scan Cycle and Software Faults

Understanding the PLC execution cycle helps distinguish logic problems from physical signal problems.

A simplified cyclic PLC execution model is:

Read input data
    ↓
Execute program logic
    ↓
Update output data
    ↓
Perform system and communication tasks as applicable
    ↓
Repeat

Actual execution varies by PLC family, task configuration, I/O architecture, and whether inputs or outputs are updated asynchronously.

Potential scan-related issues include:

  • A signal pulse shorter than the effective sampling interval.
  • Excessive execution time.
  • Incorrect task priority or task configuration.
  • A program relying on immediate input-to-output behavior that the architecture does not guarantee.
  • Inconsistent handling of shared data.
  • Incorrect assumptions about remote I/O update timing.

If a sensor pulse is too short to be captured reliably, the solution may involve appropriate hardware input filtering, a supported pulse-capture feature, a latch, or a change to the signal-handling design. The correct choice depends on the device and functional requirements.

Do not simply increase scan timeouts or add arbitrary delays without understanding the timing relationship.

6. Software Errors vs Parameter Errors

Software and parameter errors often produce similar symptoms but require different corrective actions.

Observation Software-error possibility Parameter-error possibility
Motor accelerates incorrectly Incorrect control sequence or command logic Incorrect acceleration setting
Sensor threshold is wrong Program compares against the wrong variable Device threshold parameter is incorrect
CNC axis stops at the wrong position Incorrect coordinate or program logic Incorrect offset or machine parameter
Robot movement is incorrect Wrong program branch or motion command Incorrect frame, tool, or payload data
Analog display is incorrect Incorrect scaling or tag mapping Incorrect module range or device configuration
Communication recovery fails Application does not handle reconnection correctly Incorrect timeout or device communication setting

The distinction is not always absolute. For example, software may contain a default parameter that is wrong, or program logic may depend on a device parameter that has been changed.

The RCA should identify the specific incorrect behavior and where the responsible value or logic is defined.

7. Software Debugging and Evidence Collection

A structured debugging method helps identify the causal logic path without introducing new faults.

Step 1: Capture the original condition

Record:

  • Machine state.
  • Active sequence step.
  • Alarm and fault codes.
  • Relevant input and output states.
  • Device status.
  • Program and firmware revision.
  • Parameter/configuration revision where relevant.
  • Event timestamps.
  • Recent changes.

Step 2: Establish expected behavior

Identify the approved functional specification, sequence description, acceptance criteria, or relevant program requirement.

Step 3: Reconstruct actual behavior

Determine what the software received, what decisions it made, what commands it issued, and what feedback followed.

Step 4: Locate the first divergence

Find the earliest point at which the actual behavior differs from the required behavior.

For example:

  • The field input is correct.
  • The PLC input status is correct.
  • The PLC sequence transition condition is wrong.
  • The wrong output is activated.
  • The machine enters an unexpected state.

This evidence directs attention to the sequence logic rather than the field sensor.

Step 5: Test the hypothesis

Use approved simulation, offline review, a controlled test environment, or a safe test procedure appropriate to the equipment.

Step 6: Correct and verify

Implement the controlled change and confirm that the original failure is resolved without introducing new defects.

8. Worked Example: PLC Sequence Advances Too Early

Reported problem

A machine starts the next operation before the previous actuator has completed its movement. This causes occasional part mispositioning.

Initial hypotheses

  • Incorrect PLC sequence logic.
  • Feedback sensor intermittency.
  • Excessive actuator travel time.
  • Incorrect timer configuration.
  • Incorrect sensor placement.
  • Communication delay.
  • Mechanical obstruction.

Investigation

  1. Capture the sequence step and output command.
  2. Verify the feedback signal during the movement.
  3. Compare the feedback with the PLC input state.
  4. Review the transition condition in the program.
  5. Check the timing of the command, feedback, and transition.
  6. Compare the behavior with the approved sequence requirements.
  7. Determine whether the sequence advances because of an incorrect condition or because the physical operation is delayed.

Example finding

Suppose the sequence transitions when either the completion sensor is ON or a timeout flag is active. The timeout flag becomes active before the movement is complete under a normal permitted operating condition.

If the specification requires completion feedback before advancing, the transition logic is defective or the timeout behavior is inadequately designed.

The correction should implement the required transition and define the proper fault response when completion is not achieved. Simply extending the timeout may be insufficient if the logical condition itself is wrong.

9. Worked Example: SCADA Displays Stale PLC Data

Reported problem

A local SCADA dashboard continues displaying the last known machine value after communication with the PLC is interrupted.

Potential causes

  • No communication-quality tracking.
  • No stale-data timeout.
  • Cached values displayed without status.
  • Incorrect reconnection handling.
  • Timestamp not updated with each valid read.
  • Data collection continuing to store the previous value as a new measurement.

Investigation

  1. Confirm whether PLC communication is actually interrupted.
  2. Compare PLC-side values with the SCADA display.
  3. Check timestamps and data-quality status.
  4. Inspect the application's timeout and reconnection logic.
  5. Determine whether database writes distinguish new data from repeated stale data.
  6. Verify what the dashboard displays during invalid communication.
  7. Test recovery after communication is restored.

Example corrective action

The application should explicitly represent data quality and freshness. Depending on requirements, it may mark a tag unavailable after a defined timeout, display the timestamp of the last valid reading, and prevent stale values from being treated as new measurements.

For a production dashboard, storing repeated stale values without a quality indicator can also corrupt downtime analysis and performance reporting.

10. Software Corrective Action and Change Control

Software corrections must be managed carefully because one change can affect multiple machines or functions.

A controlled software change should include:

  • A clear problem statement.
  • Evidence supporting the cause.
  • The required behavior.
  • The affected program, function, or application.
  • The original revision and proposed revision.
  • Risk and compatibility assessment.
  • Review and authorization.
  • Defined test cases.
  • A backup and recovery plan.
  • Implementation records.
  • Post-change verification.

Verification considerations

Depending on the application, test:

  • Normal operating sequence.
  • Relevant abnormal conditions.
  • Boundary values.
  • Timeout behavior.
  • Restart and recovery behavior.
  • Communication loss and restoration.
  • Alarm generation and reset.
  • Data quality and scaling.
  • Interface behavior.
  • Regression of previously working functions.

Safety-related software changes require the appropriate safety lifecycle, authorization, and validation. Ordinary functional testing is not a substitute for required safety validation.

11. Software Testing Concepts Relevant to RCA

11.1 Unit testing

Tests a small software function or module independently.

Example: Verify that an analog scaling function converts specified raw values into the expected engineering values.

11.2 Integration testing

Checks whether connected modules or systems interact correctly.

Example: Verify that a PLC sequence, remote I/O module, and HMI exchange the correct state information.

11.3 Functional testing

Checks whether the system performs the required function.

Example: Confirm that a machine starts the next step only after the required completion feedback is received.

11.4 Regression testing

Checks whether a software change has damaged previously working functionality.

Example: After correcting a robot recovery routine, verify other relevant motion sequences and recovery scenarios.

11.5 Boundary testing

Checks behavior at the limits of the specified operating range.

Example: Test the permitted minimum and maximum analog values, timer limits, and defined communication timeout conditions.

11.6 Fault-injection testing

Introduces a controlled fault condition to verify how the system responds.

Example: In an approved test environment, simulate the loss of a non-safety-related communication signal and verify the defined timeout and recovery behavior.

Fault injection must be risk-assessed and performed under approved conditions. Do not deliberately create hazardous failures in live machinery.

14. Common Mistakes in Software Error Analysis

  1. Changing logic before capturing the original fault. The evidence needed to identify the cause may disappear.
  2. Assuming a PLC alarm proves the PLC is faulty. The controller may be correctly reporting a field or process problem.
  3. Adding delays without understanding timing. Arbitrary delays can hide the symptom and create other sequence problems.
  4. Increasing timeouts without checking the cause. A slow actuator, missing feedback, and incorrect transition logic require different actions.
  5. Treating commanded state as actual state. A command does not prove that the physical device operated.
  6. Ignoring data quality and timestamps. Stale values can look valid and mislead maintenance decisions.
  7. Downloading unverified changes to production equipment. An untested correction can introduce additional downtime or risk.
  8. Failing to compare software revisions. A recent change may be related to the onset of the failure.
  9. Ignoring configuration dependencies. Correct code may behave incorrectly with unsuitable device settings.
  10. Skipping regression testing. Correcting one fault can break another function.
  11. Treating every recurring failure as a software bug. Wiring, components, parameters, process conditions, and design requirements must also be investigated.
  12. Failing to update the master copy. The running program and controlled engineering backup can become inconsistent.

15. Interview Questions and Answers

Q1. What is a software error in industrial automation?

A software error is a defect in program logic, sequence control, data handling, communication processing, or application behavior that causes the system to deviate from its required behavior.

Q2. How do you distinguish a software fault from a wiring fault?

Compare the physical signal at the field device, the signal at the controller input, the controller's input status, the program tag, and the resulting logic decision. The first point of divergence helps isolate the fault.

Q3. What is a race condition?

A race condition occurs when program behavior depends on the relative timing or ordering of events that the application does not handle reliably.

Q4. What is the difference between verification and regression testing?

Verification checks whether the corrected software meets its specified requirements. Regression testing checks whether the change has broken previously working functionality.

Q5. Why should alarm history be captured before resetting a fault?

Alarm history, sequence state, timestamps, and diagnostic information can reveal the initiating event and the order of subsequent failures. Resetting may remove useful evidence.

Q6. What causes a PLC sequence to advance prematurely?

Possible causes include incorrect transition logic, missing interlocks, unsuitable timing assumptions, incorrect feedback, or incomplete handling of abnormal conditions.

Q7. How can stale SCADA data cause problems?

Stale data may be mistaken for a current machine condition, leading to incorrect maintenance decisions, misleading alarms, or inaccurate production and downtime reports.

Q8. Why is version control important in industrial software?

Version control establishes which revision is approved, what changed, why it changed, and how it was tested. It also supports recovery and comparison when faults begin after a modification.

Q9. What should be tested after correcting PLC logic?

Test the affected sequence, relevant boundary and abnormal conditions, recovery behavior, related interfaces, and previously working functions that could be affected by the change.

Q10. Is incorrect drive configuration always a software error?

No. A drive parameter error is generally classified as a parameter or configuration error. Software logic may also contribute if it writes, selects, or interprets that parameter incorrectly.

16. Practical Software Error Checklist

  • The expected and actual behaviors are clearly documented.
  • The original alarm and diagnostic evidence is captured.
  • Program, firmware, and configuration revisions are identified.
  • Relevant physical inputs and feedback are verified.
  • Sequence state, logic decisions, and outputs are traced.
  • Timing, task execution, and communication behavior are considered.
  • Data types, scaling, mappings, and timestamps are checked.
  • Parameter and configuration errors are distinguished from logic errors.
  • The suspected defect is supported by evidence.
  • The correction is reviewed and authorized.
  • Backups and recovery arrangements are available.
  • Relevant functional and regression tests are completed.
  • The correction is validated under approved operating conditions.
  • Controlled software records and documentation are updated.
  • Recurring faults are monitored after implementation.
