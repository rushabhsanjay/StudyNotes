The control level is the part of an industrial automation system responsible for processing input signals, executing control logic or algorithms, and generating commands that control machines and processes.

The key idea is simple: the field level senses what is happening, the control level decides what should happen, and the field actuators carry out the action.

For your Industry 3.0 study, the goal is to understand the control level's role, its hardware and software, how it interacts with field devices, and how to troubleshoot it systematically.

1. Position of the control level in industrial automation

Supervisory Level
SCADA, HMI, operator monitoring and commands
                ↕
Control Level
PLC, DCS controller, CNC controller, robot controller
                ↕
Field Level
Sensors, switches, transmitters, actuators, motors, valves
                ↕
Physical Process
Machine operation, welding, drilling, movement, production

The control level sits between the supervisory level and the field level. It receives information from field devices, processes that information according to its program or control strategy, and sends commands back to the field.

Level Primary responsibility Example
Field level Measure physical conditions and perform actions Proximity sensor detects a fixture
Control level Execute logic and control algorithms PLC checks conditions and commands a clamp
Supervisory level Allow operators to monitor and interact with the system HMI displays clamp status
Physical process The actual operation being controlled Fixture clamps a vehicle body

The boundaries can overlap in real systems. For example, a CNC controller manages machine motion, while a PLC may handle auxiliary equipment and safety-related signals.

2. Why the control level is needed

Imagine a robotic welding station with sensors, pneumatic clamps, a robot, and a conveyor.

Field devices can detect a vehicle body and report whether a clamp is closed. However, the sensors alone cannot coordinate the entire station.

The control system must determine:

  • Whether the vehicle body is present.
  • Whether the required conditions for the operation are satisfied.
  • When the clamp should operate.
  • Whether the clamp reached its expected position.
  • When the robot or next machine operation may proceed.
  • What action to take if a required condition is not achieved.

The control level coordinates these operations according to programmed logic, control algorithms, and configured operating rules.

Without a control system, the devices would still exist, but the coordinated automatic operation would not.

3. Main functions of the control level

Function What it does Industrial example
Input processing Reads field signals and values Reads a proximity sensor
Logic execution Evaluates conditions and instructions Checks whether a part is present
Sequence coordination Executes operations in the intended order Clamp, weld, unclamp
Output control Commands field devices Energizes a solenoid valve
Continuous control Adjusts an output based on measured feedback Maintains pressure at a setpoint
Motion control Coordinates position, speed, and movement Controls a servo axis
Communication Exchanges data with other controllers and supervisory systems Sends machine status to SCADA
Diagnostics Detects or reports controller and system problems Reports an I/O communication fault

These are broad control-level functions, not necessarily functions performed by one controller. A particular machine may distribute them across a PLC, robot controller, drive, safety controller, and supervisory system.

4. Main types of controllers

A controller is a device or computing system that executes control logic or algorithms to operate a machine or process.

4.1 PLC: Programmable Logic Controller

A PLC is an industrial controller commonly used for discrete machine automation, equipment coordination, and general-purpose control.

Typical applications include:

  • Conveyor systems.
  • Pneumatic fixtures and clamps.
  • Automated assembly machines.
  • Material handling systems.
  • Machine interlocks and operating sequences.
  • Communication with VFDs, robots, HMIs, and remote I/O.

Examples include Allen-Bradley CompactLogix and ControlLogix, Siemens S7-1200 and S7-1500, and Mitsubishi MELSEC controllers.

In a PLC-controlled machine, the program reads input states, evaluates logic, and updates outputs or commands other devices.

4.2 DCS controller: Distributed Control System

A DCS is designed primarily for integrated process control, particularly where many interacting loops and process variables must be controlled across a plant.

Typical applications include:

  • Chemical processing.
  • Oil and gas.
  • Power generation.
  • Water treatment.
  • Continuous temperature, pressure, flow, and level control.

DCS architectures commonly distribute control across multiple controllers and integrate them with operator stations, engineering stations, and process networks.

A DCS is not simply a PLC with a larger number of inputs. Its architecture, engineering environment, redundancy options, and plant-wide integration are designed around process-control requirements.

4.3 CNC controller

A Computer Numerical Control (CNC) controller manages programmed machine-tool operations and coordinates axes, spindle functions, and machining sequences.

Typical applications include:

  • CNC milling machines.
  • CNC lathes.
  • Machining centres.
  • Precision cutting and drilling.

A CNC controller must coordinate movement with the machining program. It therefore has specialised functions for interpreting tool paths, controlling axes, and managing machining operations.

4.4 Robot controller

A robot controller manages the robot's programmed motion, axes, and related robot-specific functions.

Typical applications include:

  • Robotic welding.
  • Pick-and-place.
  • Painting.
  • Material handling.
  • Assembly.

A PLC may coordinate the overall production station while the robot controller executes the robot's motion program. The two systems exchange commands and status information.

4.5 Motion controller and drive-based control

A motion controller coordinates axes, trajectories, position, speed, or synchronised movement. Some motion functions are integrated into PLCs, while others use dedicated controllers.

A VFD or servo drive also contains internal control functions. For example, a servo drive may regulate motor current and speed locally while receiving higher-level position or motion commands from another controller.

4.6 Safety controller

A safety PLC or safety controller performs designated safety-related control functions, such as monitoring safety devices and initiating defined safe responses.

It is designed and validated for applicable safety requirements. A standard PLC program must not be assumed to provide a safety-rated function simply because it contains logic that looks similar.

Safety architecture, hardware, configuration, validation, and applicable standards determine whether a function is suitable for its intended safety purpose.

5. Comparison of common controllers

Controller Primary purpose Typical application
PLC General industrial machine control Conveyors, fixtures, assembly
DCS controller Integrated process control Chemical and utility plants
CNC controller Machine-tool and axis coordination Milling and turning
Robot controller Robot-specific motion and operation Welding and handling

These categories are not mutually exclusive in every installation. Modern PLCs may include motion functions, and a machine may contain several controller types working together.

Not every PLC uses a modular rack. Compact PLCs may integrate the CPU, power supply, and some I/O into one unit.

6.2 Local I/O versus remote I/O

Local I/O is installed within or close to the controller's main hardware assembly.

Remote I/O is installed elsewhere in the machine or plant and communicates with the controller over an industrial network.

For example, a central PLC might control several welding stations. Rather than routing every sensor wire to the main panel, each station can have a remote I/O assembly near its field devices.

Benefits of remote I/O include:

  • Reduced long-distance field wiring.
  • Easier machine expansion and modularisation.
  • Better grouping of signals by machine or station.
  • Easier maintenance when the architecture is properly documented.

However, remote I/O introduces network dependencies. A network or adapter fault may make multiple I/O points unavailable at once.

7. How the controller executes its program

One fundamental concept is the PLC scan cycle.

Many PLCs repeatedly perform a cycle of reading inputs, executing logic, and updating outputs. The precise execution model depends on the controller, tasks, I/O architecture, and configuration.

7.1 Simplified scan cycle

  1. Read inputs: The controller obtains input data from its I/O system.
  2. Execute logic: The CPU evaluates instructions using inputs, internal tags, timers, counters, and other data.
  3. Update outputs: The controller sends output commands to the I/O system.
  4. Perform system tasks: Communication, diagnostics, scheduling, and other activities occur according to the controller's architecture.
  5. Repeat: The control program continues executing.
Read Input Data
      ↓
Execute Program Logic
      ↓
Update Output Commands
      ↓
System and Communication Tasks
      ↓
Repeat

7.2 Example of a scan cycle

Suppose a sensor detects a metal component.

  • The sensor output becomes ON.
  • The PLC receives the corresponding input state.
  • The program checks whether the machine is in the correct operating state.
  • If the required conditions are satisfied, the PLC commands a clamp valve.
  • The output system sends the command to the field device.
  • A feedback sensor may later confirm that the clamp has closed.

The controller does not automatically know that the clamp physically closed merely because it issued the output command. It needs suitable feedback to verify the result.

7.3 Scan time

Scan time is the time taken for a defined controller execution cycle. The exact meaning depends on the controller and the way its tasks are configured.

Scan time may be affected by:

  • Program size and complexity.
  • Number and type of instructions.
  • Communication and data-processing workload.
  • Task priorities and execution periods.
  • Controller model and configuration.

A short scan time can be useful for responsive machine control, but the shortest possible scan is not automatically the best design. The control requirements, task scheduling, system stability, and available resources matter.

Some controllers use periodic, event-triggered, continuous, or motion-related tasks rather than one uniform scan for everything.

8. Control logic and programming

A controller needs a program or configured control strategy to determine how the machine should operate.

8.1 Common programming languages

IEC 61131-3 defines widely used programming language approaches for programmable controllers.

Language Full name Typical use
LD Ladder Diagram Boolean logic and familiar relay-style control
FBD Function Block Diagram Connected functional blocks and control functions
ST Structured Text Text-based logic, calculations, and data processing
SFC Sequential Function Chart Representing steps and transitions in a sequence

Language availability and implementation details vary by controller and engineering software.

8.2 Ladder logic example

Consider a simple requirement: command a lamp when a sensor is ON and the machine-enable condition is true.

The logical relationship is:

\[ \text{Lamp Command}=\text{Sensor ON}\land\text{Machine Enabled} \]

Here, AND means both conditions must be true.

Sensor ON Machine enabled Lamp command
No No OFF
No Yes OFF
Yes No OFF
Yes Yes ON

This is a simplified logical example, not a complete industrial safety or machine-control design. Real machines may require additional operating conditions, fault handling, and validated safety functions.

8.3 Program logic versus physical operation

The controller's program represents the intended behaviour of the machine. The physical machine may not follow that intention if a sensor, output module, wire, valve, motor, or mechanical component fails.

For example:

  • The program commands a clamp to close.
  • The PLC output status indicates ON.
  • The solenoid coil receives no voltage because of a wiring fault.
  • The valve does not shift.
  • The clamp remains open.

The program may be behaving as written while the physical system fails to perform the commanded action.

This distinction is essential during maintenance: a correct command does not guarantee a successful physical action.

9. Digital control versus continuous control

The control level can handle both discrete machine logic and continuous process regulation.

9.1 Discrete control

Discrete control deals primarily with distinct states or events.

Examples include:

  • A sensor is ON or OFF.
  • A clamp is open or closed.
  • A conveyor is running or stopped.
  • A part is present or absent.

A PLC may use these states to coordinate equipment operations.

9.2 Continuous control

Continuous control regulates a variable such as temperature, pressure, flow, or speed.

A basic feedback loop contains:

  • Setpoint (SP): The desired value.
  • Process variable (PV): The measured value.
  • Controller: Determines the required control action.
  • Manipulated variable (MV): The output used to influence the process.

For example, a controller may compare a desired temperature of \(180^\circ C\) with the measured temperature and adjust heater output accordingly.

The control error is:

\[ e(t)=SP(t)-PV(t) \]

The controller uses this error according to its configured strategy. A simple controller may switch a heater ON or OFF, while a PID controller can adjust output more continuously.

The controller's role is to calculate or determine the control action. The actual heating still depends on the output hardware, electrical supply, heater condition, and physical process.

10. How the control level communicates with other systems

Controllers rarely operate in complete isolation. They exchange information with field devices, drives, robots, HMIs, SCADA systems, and other controllers.

Communication relationship Purpose Example
Controller to remote I/O Read inputs and command outputs PLC communicates with a remote I/O adapter
PLC to VFD Send run, stop, speed, and other commands Conveyor speed control
PLC to robot controller Exchange station commands and status Permit a robot cycle and receive completion status
PLC to HMI Display data and accept operator commands Show machine state and selected operating mode
Controller to SCADA Exchange plant data and supervisory commands Monitor equipment status across a plant
Controller to controller Coordinate different machines or process areas Transfer production-ready status

Examples of industrial communication technologies include EtherNet/IP, PROFINET, Modbus TCP, PROFIBUS, and other vendor-specific or application-specific protocols.

The correct protocol depends on the equipment, network architecture, performance requirements, and supported interfaces.

A controller can be running correctly while a communication failure prevents it from receiving data from another device. Therefore, controller execution and communication health must be distinguished during troubleshooting.

11. Industrial example: Automotive robotic welding station

Consider a robotic welding station in an automotive body shop.

The station contains a PLC, robot controller, proximity sensors, pneumatic clamps, welding equipment, and an HMI.

11.1 Division of responsibility

Component Responsibility
Proximity sensor Detects whether the component is present
PLC Coordinates station-level logic and equipment status
Output module Sends the electrical command to the designated output circuit
Solenoid valve Controls pneumatic flow to the clamp actuator
Clamp position sensor Reports the detected clamp position
Robot controller Executes the robot program and motion
HMI Displays station status and operator information

11.2 Typical operating logic

  1. The component enters the station.
  2. The PLC reads the component-presence signal.
  3. The PLC evaluates whether the required operating conditions are satisfied.
  4. The PLC commands the clamp to close.
  5. The clamp-position feedback confirms the detected closed state.
  6. The PLC and robot controller coordinate the next operation through their configured interface.
  7. The robot controller executes the welding motion.
  8. Completion status is communicated to the station controller.
  9. The station proceeds to its next configured operation.

This is a simplified example. Actual stations may have several clamps, robot zones, weld controllers, safety controllers, and more complex coordination.

The important concept is that the PLC and robot controller have related but different responsibilities. The PLC may coordinate the station, while the robot controller manages robot motion.

12. Control-level troubleshooting

For maintenance, it is useful to distinguish a controller problem from a field-device problem, a wiring problem, a communication problem, or a mechanical failure.

A systematic troubleshooting path is:

Field Device
     ↓
Electrical Signal and Wiring
     ↓
PLC Input / Output Status
     ↓
Controller Tag and Program Logic
     ↓
Communication or Output Interface
     ↓
Field Actuator
     ↓
Physical Result and Feedback

The order of investigation can change according to the symptom, but the objective is to identify where the expected behaviour stops matching actual behaviour.

12.1 Case 1: Sensor is physically activated, but PLC input remains OFF

Possible causes include:

  • Sensor has no supply voltage.
  • Sensor is damaged or incorrectly adjusted.
  • Sensor output type is incompatible with the input circuit.
  • Wiring or common-reference connection is incorrect.
  • Input channel is faulty.
  • The wrong input address or tag is being monitored.
  • Remote I/O communication is unavailable.

A sensible diagnostic progression is to verify the sensor's actual output, check the electrical signal at the input terminal, inspect the module's channel status, and then verify the controller tag mapping.

Do not jump directly to replacing the PLC. Hardware replacement is a wonderfully expensive way to avoid checking a wire.

12.2 Case 2: PLC output command is ON, but the actuator does not move

Possible causes include:

  • Output logic is not producing the expected command.
  • The monitored tag is not the physical output point.
  • Output module or channel fault.
  • Missing output supply or common connection.
  • Open circuit or damaged cable.
  • Faulty solenoid coil.
  • Pneumatic or hydraulic supply problem.
  • Jammed valve, cylinder, or mechanical assembly.

Check the logical command, physical output-channel status, electrical condition at the load, and actuator supply. Then inspect the mechanical device.

Important distinction: An output tag being ON does not necessarily mean the output terminal is supplying voltage or that the actuator is moving.

12.3 Case 3: PLC and HMI show different machine states

Possible causes include:

  • The HMI is reading a different tag.
  • The HMI value is stale or not refreshing.
  • A communication path has failed.
  • The HMI and PLC use different interpretations of a status.
  • A displayed value is calculated or mapped incorrectly.
  • The HMI is connected to the wrong controller or data source.

Compare the actual PLC tag, the HMI's configured data source, and the communication status. Verify whether the HMI displays a command, a feedback signal, or a calculated status. These are not interchangeable.

12.4 Case 4: Controller is running, but the machine does not complete its operation

Possible causes include:

  • A required input never changes state.
  • The program is waiting for another condition.
  • The machine is in the wrong operating mode.
  • A controller-to-controller communication condition is missing.
  • A timer or state transition behaves differently than expected.
  • A field actuator has failed to complete its movement.
  • A fault or stop condition is preventing progression.

Monitor the relevant tags and the program execution path to determine which expected condition is missing. Do not modify logic simply to force the machine to proceed without understanding why the condition was not satisfied.

13. Controller faults versus machine faults

A controller fault and a machine fault are different categories, although one can cause the other.

Fault category Example What to investigate
Controller hardware CPU or I/O module fault Controller diagnostics and hardware status
Program or configuration Incorrect logic or tag mapping Program, configuration, and recent changes
Field electrical Broken wire or missing supply Wiring and measured electrical conditions
Communication Lost remote I/O or robot connection Network status, device status, and configuration
Process or mechanical Clamp jammed despite a valid command Pneumatics, mechanics, load, and feedback
Instrumentation Incorrect measured value Sensor condition, scaling, wiring, and calibration

A controller fault does not always mean the CPU has failed. A communication fault, module fault, configuration problem, or program-related issue may be responsible.

Similarly, a machine stoppage does not automatically indicate a PLC problem.

14. Important concepts to distinguish

14.1 Controller versus control system

A controller is one component that executes control logic or algorithms.

A control system includes the controller and the other components required to achieve the intended behaviour, such as sensors, actuators, wiring, communication networks, software, and feedback devices.

A PLC is a controller. A PLC-controlled machine, including its field devices and associated interfaces, is part of a control system.

14.2 Command versus feedback

A command represents what the controller is requesting.

Feedback represents information about the actual or detected state of the equipment.

For example:

  • Clamp-close command: the PLC requests the clamp to close.
  • Clamp-closed feedback: a sensor reports that the clamp has reached the detected closed position.

The command can be ON while feedback remains OFF. This difference is often highly valuable during fault diagnosis.

14.3 Logic versus control algorithm

Logic commonly evaluates discrete conditions and determines actions, such as whether a machine operation may proceed.

A control algorithm calculates or adjusts a control action, such as the output required to regulate temperature or pressure.

Industrial controllers can execute both. The terms describe different aspects of the controller's work, not necessarily separate hardware.

14.4 Controller status versus process status

A controller can be in RUN mode while the machine is stopped, waiting, faulted at the process level, or unable to complete a physical action.

Controller execution status alone does not establish that the controlled equipment is operating correctly.

15. Common misconceptions

  • “The PLC is running, so the machine should work.” The PLC may be executing normally while an input, output, communication link, or mechanical device has failed.
  • “An ON output means the actuator has operated.” It indicates a command or logical state, depending on what is being monitored. It does not prove physical movement.
  • “All control is performed by the PLC.” Robot controllers, CNC controllers, drives, DCS controllers, and safety controllers may each handle specific responsibilities.
  • “The HMI controls the machine directly.” Typically, the HMI sends operator commands or displays data while a controller evaluates and executes the configured control behaviour.
  • “A controller fault always means a failed CPU.” The cause may be a module, network, configuration, program, or other system problem.
  • “The fastest scan time is always best.” Execution timing must satisfy the application requirements and remain compatible with task scheduling, controller capacity, and system design.

16. Interview questions and answers

Q1. What is the control level in industrial automation?

The control level receives field data, executes control logic or algorithms, and generates commands to coordinate machine or process operation.

Q2. What is the difference between a PLC and a DCS?

A PLC is widely used for machine control and discrete automation. A DCS is designed for integrated process control across multiple interacting loops and plant areas. Their capabilities can overlap, but their typical architectures and application priorities differ.

Q3. What is a PLC scan cycle?

It is a simplified description of repeated controller execution, commonly involving input processing, program execution, and output updating. Actual task and I/O behaviour depends on the controller architecture and configuration.

Q4. What is the difference between local I/O and remote I/O?

Local I/O is located at or near the controller's main assembly. Remote I/O is installed elsewhere and communicates with the controller through a network or other communication arrangement.

Q5. Why can a PLC output be ON while an actuator remains stationary?

The command may be correct, but the output circuit, electrical supply, wiring, solenoid, pneumatic or hydraulic supply, valve, or mechanical actuator may have failed.

Q6. What is the difference between a command and feedback?

A command indicates the requested action. Feedback indicates the detected state or result. The two must be compared to verify whether the intended action occurred.

Q7. Can a PLC perform continuous control?

Yes. Depending on its capabilities and configuration, a PLC can execute continuous-control algorithms, including PID control, as well as discrete logic.

Q8. Why is controller communication important?

It allows controllers to exchange commands and status, remote I/O to communicate with the CPU, and supervisory systems to monitor and interact with the process. Communication failure can disrupt operation even when a controller is otherwise running.

Q9. What is the difference between a controller and a control system?

The controller executes control logic or algorithms. The control system includes the controller and the relevant field devices, interfaces, communication, software, and feedback needed to control the process.

Q10. How should a technician investigate a machine that is not responding to a PLC command?

Trace the signal through the logical command, physical I/O status, electrical circuit, actuator, and physical feedback. Use controller diagnostics and the actual machine condition to isolate the failure rather than assuming the PLC itself is defective.

17. Final mental model

Remember the control level as the decision and coordination layer of industrial automation.

  • Field level: Measures conditions and performs physical actions.
  • Control level: Processes signals, evaluates logic, regulates variables, and coordinates equipment.
  • Supervisory level: Provides operator interaction, monitoring, and higher-level visibility.
  • Physical process: The actual machine or process whose behaviour must be controlled.

For maintenance, the most useful principle is this: trace the difference between what the controller expects, what it commands, and what the machine actually does. That distinction turns PLC troubleshooting from random component replacement into systematic fault isolation.
