1. Definition

A permissive is a condition that must be satisfied before a machine, device, or process is allowed to start or perform a specified operation.

In industrial automation, permissives establish whether the required conditions are available for an operation to begin.

For example, a motor may be permitted to start only when:

  • The motor is available and not faulted.
  • The required lubrication pressure is established.
  • The downstream equipment is ready.
  • The selected operating mode allows starting.
  • Any required safety functions permit operation.

If one required permissive is missing, the start request may be rejected or held until the condition is satisfied.

The key idea is that a start command requests an operation, while permissives determine whether the operation is allowed.

A permissive does not necessarily start the machine itself. It establishes permission for a separate command or sequence to proceed.

2. Why Permissives Are Required

Industrial machines depend on several conditions being correct before operation begins. Starting equipment without verifying those conditions can damage machinery, interrupt the process, or produce defective parts.

Permissives help ensure that:

  1. Required utilities are available.
  2. Equipment is in a suitable initial state.
  3. Upstream and downstream equipment are ready.
  4. The correct operating mode is selected.
  5. Required process conditions are satisfied.
  6. The machine can begin its sequence without violating defined operating requirements.

For example, a hydraulic press may require adequate hydraulic pressure before starting its production cycle. A conveyor may require the downstream conveyor to be ready to receive material.

The permissive logic makes these dependencies explicit instead of relying on an operator to remember every condition.

3. Basic Permissive Logic

Consider a motor that requires three conditions before starting:

  • Motor_Healthy
  • Lubrication_Pressure_OK
  • Downstream_Ready

A simplified PLC expression is:

Motor_Start_Permissive :=
    Motor_Healthy
    AND Lubrication_Pressure_OK
    AND Downstream_Ready;

The result is TRUE only when all three conditions are TRUE.

Motor healthy Lubrication pressure OK Downstream ready Start permissive
TRUE TRUE TRUE TRUE
FALSE TRUE TRUE FALSE
TRUE FALSE TRUE FALSE
TRUE TRUE FALSE FALSE
FALSE FALSE TRUE FALSE

When the permissive is TRUE, the start request may proceed to the next stage of the control logic.

When the permissive is FALSE, the start request must not proceed through that logic path.

This example is conceptual. Real motor control may also require feedback validation, overload protection, operating-mode checks, fault-reset conditions, and separate safety-related controls.

4. Permissive vs Interlock vs Start Command

These concepts are closely related, but they describe different parts of the control process.

Term Purpose Example
Start command Requests that equipment start Operator presses the motor START button
Permissive Establishes whether starting is allowed Lubrication pressure is sufficient
Interlock Prevents or interrupts an operation when specified conditions are not met A machine cycle is inhibited unless the fixture is clamped
Trip A fault or protective response that changes the equipment's operating state A motor drive trips on overcurrent
Alarm Notifies the operator or maintenance team of a condition Low lubrication pressure is displayed on the HMI

The distinction between a permissive and an interlock depends partly on plant terminology. A permissive can be considered a type of starting interlock in many control systems.

The practical distinction is this:

  • A permissive commonly answers, "May this operation start?"
  • An interlock more broadly answers, "Is this operation allowed under the required conditions?"
  • A trip describes a response to a fault or abnormal condition.
  • An alarm communicates information about a condition.

An interlock can also act during operation, whereas a permissive is commonly associated with start authorization.

5. Types of Permissives

5.1 Equipment-ready permissive

Confirms that the equipment is available to perform its intended operation.

Examples:

  • Motor drive ready.
  • Robot controller ready.
  • CNC machine ready.
  • Pneumatic actuator available.
  • No active fault preventing operation.

A machine may be powered but not ready. For example, a robot controller can be ON while the robot is not in a state that permits automatic operation.

5.2 Process-condition permissive

Confirms that the process conditions are suitable for starting.

Examples:

  • Hydraulic pressure within the required range.
  • Cooling flow established.
  • Required temperature reached.
  • Part correctly positioned.
  • Required vacuum level achieved.

The permitted range and confirmation method must come from the machine's design and process requirements.

5.3 Upstream-ready permissive

Confirms that the preceding equipment or material source can provide the required input.

Example: A robotic station cannot begin a production cycle until the incoming assembly is present and correctly positioned.

5.4 Downstream-ready permissive

Confirms that the next operation can receive the output, where required by the process design.

Example: A conveyor transfer is permitted only when the downstream station has space available.

Not every process requires downstream readiness before starting. Some systems allow production to continue using buffers.

5.5 Mode permissive

Confirms that the selected operating mode allows the requested operation.

Examples:

  • Automatic mode selected for automatic production.
  • Manual mode selected for an authorized manual operation.
  • Setup mode active for a defined setup procedure.

Mode selection alone does not establish that all safety conditions are satisfied.

5.6 Utility permissive

Confirms that required services are available.

Examples:

  • Compressed-air pressure sufficient.
  • Cooling-water flow established.
  • Required electrical supply available.
  • Lubrication system ready.

A missing utility permissive can prevent starting even when the main machine controller reports no fault.

5.7 Safety-related permission

A machine's operation may depend on safety functions permitting operation.

Examples include the validated safety state of a guard system or the availability of a required protective function.

However, a normal PLC permissive bit is not a substitute for a safety-rated control function. The safety system must independently meet the required safety design and performance requirements.

6. Permissives in an Automotive Robotic Welding Station

Consider a robotic welding station in an automotive body assembly line.

Before automatic production begins, the control system may require:

Condition Purpose
Robot ready Confirms the robot controller can accept the required operation
Fixture home Confirms the fixture is in the required initial position
Part present Confirms that the assembly is available
Clamp closed Confirms the required fixture state
Welding equipment ready Confirms the required welding system is available
Correct program selected Helps ensure the intended process is selected
Downstream ready Allows transfer planning where required
Required safety functions satisfied Ensures the validated safety system permits the operation

A simplified logic expression could be:

Auto_Cycle_Permissive :=
    Robot_Ready
    AND Fixture_Home
    AND Part_Present
    AND Clamp_Closed
    AND Weld_System_Ready
    AND Correct_Program_Selected
    AND Safety_System_Permits;

This is an illustrative representation, not a complete robot safety design.

If Weld_System_Ready is FALSE, the PLC may refuse to start the cycle even if the robot and fixture are otherwise ready.

The HMI should ideally identify the missing condition rather than displaying only a generic message such as "Cycle Start Not Possible."

7. Permissives and PLC Programming

In a PLC program, permissives are often combined using Boolean logic.

For conditions that must all be satisfied, AND logic is commonly used.

Start_Permissive :=
    Machine_Ready
    AND No_Start_Inhibiting_Fault
    AND Process_Conditions_OK;

For alternative conditions, OR logic may be appropriate.

For example, a cooling system might permit operation when either of two approved cooling units is available:

Cooling_Available :=
    Cooling_Unit_A_Ready
    OR Cooling_Unit_B_Ready;

This OR logic is valid only if either unit is genuinely sufficient for the required cooling duty and the system is designed to operate that way.

Control logic must reflect the real process requirements. Replacing AND with OR merely to make a machine start can create serious equipment or process problems.

Permissive versus latch logic

A permissive is a condition. A latch stores a state until a specified reset or release condition occurs.

For example:

  • Start_Permissive may be TRUE whenever all required conditions are satisfied.
  • Cycle_Active may remain TRUE throughout the production sequence after a valid start.
  • Fault_Latched may remain TRUE after a fault until an authorized reset condition is met.

These signals serve different purposes and should not be treated as interchangeable.

8. Permissive vs Continuous Monitoring

A critical design question is whether a condition is needed only at the beginning of an operation or must remain valid throughout the operation.

Start permissive

Checks whether an operation may begin.

Example: A machine cycle cannot start until the fixture is confirmed closed.

Continuous operating condition

Monitors whether a required condition remains valid while the operation is running.

Example: A process may need to stop or change state if cooling flow is lost during operation.

The required response depends on the equipment, process, and safety requirements.

A condition used to authorize starting must not automatically be assumed to provide continuous protection. The control design must specify what happens if the condition becomes FALSE after starting.

9. Permissive Troubleshooting

When a machine does not start, a missing permissive is one of the first conditions to investigate.

Step 1: Identify the requested operation

Determine exactly what is blocked:

  • Motor start.
  • Automatic cycle start.
  • Robot start.
  • CNC cycle start.
  • Conveyor transfer.
  • Hydraulic or pneumatic operation.

Step 2: Find the permissive status

Check the HMI, PLC status display, sequence diagnostics, or approved electrical documentation.

Example:

AUTO CYCLE START BLOCKED

Robot Ready             TRUE
Fixture Home            TRUE
Part Present            TRUE
Clamp Closed            TRUE
Weld System Ready       FALSE
Safety System Permits   TRUE

The missing permissive is Weld System Ready.

That identifies the immediate blocking condition, not necessarily the root cause.

Step 3: Trace the missing signal

Determine where the signal originates and how it reaches the PLC.

Physical equipment state
          |
          v
Device or controller
          |
          v
Electrical signal or network data
          |
          v
PLC input or tag
          |
          v
Permissive logic
          |
          v
Start authorization

Possible causes include:

  • The welding controller is not ready.
  • The controller has an active fault.
  • The interface signal is missing.
  • The communication link is unavailable.
  • The wrong tag or input is being monitored.
  • The controller is in an incompatible operating mode.
  • A required initialization or reset sequence is incomplete.

Step 4: Check the actual condition

If a pressure permissive is missing, verify the actual pressure and the pressure-switch or transmitter signal.

If a robot-ready permissive is missing, inspect the robot controller's status and active diagnostics.

Do not assume the sensor or signal is defective before checking whether the underlying condition is actually satisfied.

Step 5: Correct the root cause

Repair the device, restore the required process condition, correct the communication issue, or resolve the controller fault according to the approved procedure.

Do not force the permissive TRUE simply to restore production.

Step 6: Verify normal operation

Confirm that:

  • The missing condition becomes valid.
  • The intended operation can start.
  • Required conditions are monitored correctly.
  • No other faults remain.
  • The problem does not recur during appropriate verification.

10. Common Permissive Problems in Industrial Automation

Symptom Possible causes Checks
Motor will not start Drive not ready, fault active, required utility missing Drive status, fault history, process conditions
Robot automatic cycle blocked Wrong mode, robot not ready, required handshake missing Robot status, mode, interface signals
Fixture cannot begin cycle Part not present, clamp not home, pressure low Sensors, actuator state, pneumatic or hydraulic supply
Conveyor transfer blocked Downstream unavailable, transfer zone occupied Zone sensors, downstream status, handshake logic
CNC cycle start inhibited Door or clamp state not confirmed, machine not ready CNC diagnostics, fixture feedback, required operating conditions
Permissive flickers between TRUE and FALSE Unstable sensor, loose connection, fluctuating process condition, communication issue Signal trends, wiring, device diagnostics, timing
Machine starts but stops shortly afterward A continuously monitored condition becomes invalid, or another stop condition occurs Sequence transitions, operating conditions, fault history

These are possible causes, not universal diagnoses. The machine's actual control design determines which conditions apply.

11. Permissives and Production Flow

Permissives also coordinate multiple machines across a production line.

Consider two connected stations:

  • Station A produces an assembly.
  • Station B receives and processes the assembly.

A transfer permissive may depend on:

Station_A_Part_Ready
AND Station_B_Ready_To_Receive
AND Transfer_Path_Clear

When these conditions are satisfied, the transfer sequence may proceed.

If Station B is busy, Station A may retain the assembly or wait at a designated buffer.

This prevents an upstream machine from transferring a part into an occupied or unavailable destination.

However, downstream readiness should be required only where the process architecture calls for it. Well-designed lines may use buffers to allow upstream production to continue temporarily while downstream equipment is busy.

Permissive logic therefore affects not only individual machine operation but also line coordination, blocking, starvation, and throughput.

12. Common Mistakes

  1. Confusing a permissive with a start command. Permission does not itself mean the operation has been requested.
  2. Treating every missing permissive as a sensor fault. The underlying physical condition may genuinely be absent.
  3. Using OR logic when all conditions are required. This can allow an operation to proceed incorrectly.
  4. Assuming a start permissive provides continuous monitoring. The design must specify what happens if a condition becomes invalid during operation.
  5. Forcing permissive bits to restore production. This can hide faults or defeat intended process controls.
  6. Confusing a normal PLC permissive with a safety function. Safety-related control must meet the applicable requirements independently.
  7. Ignoring communication status. A missing network signal may indicate a communications or data-validity problem rather than a failed field device.
  8. Displaying only a generic start-blocked message. Clear identification of missing conditions reduces troubleshooting time.
  9. Ignoring sequence state and reset conditions. All physical conditions may be valid while the machine remains in an incompatible control state.

13. Interview Questions and Answers

Q1. What is a permissive in industrial automation?

A permissive is a condition that must be satisfied before a specified operation is allowed to start or proceed.

Q2. What is the difference between a permissive and an interlock?

A permissive commonly establishes whether starting is allowed. An interlock is a broader mechanism that prevents or interrupts operation when specified conditions are not met. In many systems, a permissive is implemented as a starting interlock.

Q3. Does a TRUE permissive automatically start a machine?

No. It indicates that the required permission conditions are satisfied. A separate start request or sequence command may still be necessary.

Q4. Why might a motor fail to start even when there is no active fault?

A required permissive may be FALSE because of a missing ready signal, unavailable utility, incompatible mode, incomplete sequence, or missing downstream condition.

Q5. How are permissives implemented in a PLC?

They are commonly implemented using Boolean logic, status signals, process measurements, controller-ready signals, and sequence conditions.

Q6. What is the difference between a permissive and a latch?

A permissive represents whether a condition is satisfied. A latch retains a state until a defined release or reset condition occurs.

Q7. Can a permissive be used for safety?

A permissive may reflect the status of a safety system, but an ordinary PLC permissive is not a substitute for a validated safety-related function.

Q8. How would you troubleshoot a missing robot-ready permissive?

Check the robot controller status, operating mode, active faults, required initialization, interface signals, and communication status. Trace the missing condition to its source and correct the underlying cause.

Q9. Why are permissives important in production-line coordination?

They ensure that equipment starts or transfers parts only when the required upstream, downstream, and process conditions are satisfied.

Q10. What happens if a permissive becomes FALSE during operation?

The response depends on the control design. The sequence may stop, pause, inhibit the next step, or initiate another defined response. Conditions requiring safety-related action must be handled by the appropriate safety function.

Remember the distinctions:

  • Command: Requests an action.
  • Permissive: Determines whether an action is allowed to start or proceed.
  • Interlock: Prevents or interrupts an operation when specified conditions are not satisfied.
  • Latch: Retains a state until a defined reset or release condition occurs.
  • Trip: A fault or protective response that changes the equipment's operating state.
  • Alarm: Communicates a condition that requires attention.

The central principle is that a permissive establishes permission, not execution. When an operation is blocked, identify the missing condition and correct its root cause rather than bypassing the logic.
