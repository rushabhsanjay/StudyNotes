1. Definition

A handshake is an exchange of signals or messages between two devices, controllers, machines, or software systems to coordinate their operations and confirm that the required conditions for communication or process progression have been met.

In industrial automation, a handshake ensures that one system knows when another system is ready, when an operation has been requested, when it has been accepted, and when it has been completed.

For example, a robot and a welding fixture may exchange signals to coordinate loading and unloading. The robot should not start loading merely because the fixture exists. It needs confirmation that the fixture is ready to receive the workpiece.

A typical handshake might involve:

  1. The fixture indicates READY.
  2. The robot checks that the required conditions are satisfied.
  3. The robot indicates REQUEST_LOAD.
  4. The fixture acknowledges the request.
  5. The robot loads the workpiece.
  6. The robot indicates LOAD_COMPLETE.
  7. The fixture acknowledges completion and proceeds with its operation.

The exact signals and order depend on the equipment and control design.

2. Why handshakes are required

Industrial automation systems frequently involve equipment manufactured by different vendors, programmed independently, and controlled by separate PLCs, robot controllers, CNCs, or supervisory systems.

Each system has its own internal logic. A handshake provides a defined method for coordinating those independent systems.

Handshakes help to:

  • Coordinate operations: Prevent two machines from attempting incompatible actions simultaneously.
  • Confirm readiness: Establish whether the receiving system can accept an operation or workpiece.
  • Acknowledge commands: Confirm that a request has been received or accepted.
  • Confirm completion: Establish that an operation has reached the required endpoint.
  • Prevent premature progression: Keep a sequence from advancing before the other system is ready.
  • Improve diagnostics: Identify which stage of an equipment-to-equipment exchange has failed.

A handshake is especially important in automated production lines where a robot, fixture, conveyor, welding controller, and PLC must operate as a coordinated system.

3. Basic handshake operation

Consider a robot transferring a workpiece to a fixture.

A simplified handshake can use four signals:

Signal Direction Meaning
FIXTURE_READY Fixture PLC → Robot controller The fixture is ready to receive the workpiece
LOAD_REQUEST Robot controller → Fixture PLC The robot requests permission to load
LOAD_ACCEPTED Fixture PLC → Robot controller The fixture has accepted the request
LOAD_COMPLETE Robot controller → Fixture PLC The robot has completed the loading operation

A simplified exchange is:

FIXTURE PLC                         ROBOT CONTROLLER

FIXTURE_READY = ON  ------------->  Check readiness

                    <-------------  LOAD_REQUEST = ON

LOAD_ACCEPTED = ON  ------------->  Confirm acceptance

                    <-------------  LOAD_COMPLETE = ON

Confirm completion
Clear or acknowledge signals

This is a conceptual example, not a universal handshake protocol. Actual systems may require additional signals for busy status, faults, cycle completion, part presence, or recovery.

Important: A handshake signal confirms only the condition defined by its logic. For example, LOAD_COMPLETE should mean that the robot has completed the defined loading operation, not merely that it has started moving toward the fixture.

4. Handshake versus sequence, interlock, and permissive

These concepts work together, but they serve different purposes.

Concept Primary purpose Example
Sequence Defines the ordered operations Pick part → transfer part → place part
Handshake Coordinates and confirms an exchange between systems Robot requests loading and fixture acknowledges
Interlock Prevents an operation when a prohibited condition exists Prevent fixture movement while the robot occupies a restricted zone
Permissive Establishes conditions required before an operation is allowed Fixture must be open before the robot starts loading
Acknowledgement Confirms receipt or acceptance of a request, according to its definition PLC acknowledges a robot request
Feedback Reports an actual or detected condition Part-present sensor is ON
Alarm Indicates an abnormal condition requiring attention Robot request was not acknowledged in time

A handshake can contain permissives, interlocks, commands, acknowledgements, and feedback signals.

The key distinction is that a handshake coordinates the relationship between systems, while a sequence defines the operations and their order.

5. Common handshake signal types

5.1 Ready

Indicates that a system is prepared to accept a request or perform a defined operation.

Examples:

  • Robot ready for automatic operation.
  • Fixture ready to receive a workpiece.
  • Conveyor ready to accept a part.
  • CNC ready to begin a machining cycle.

A ready signal must have a clear definition. A robot being powered on does not necessarily mean it is ready for automatic operation.

5.2 Request

Indicates that one system is asking another system to perform or permit an operation.

Examples:

  • Robot requests fixture loading.
  • PLC requests a CNC cycle.
  • Conveyor requests permission to transfer a workpiece.

The request may remain active until the receiving system acknowledges it, or it may use a pulse or a communication-message transaction, depending on the design.

5.3 Acknowledge or accepted

Indicates that the receiving system has recognized or accepted the request.

An acknowledgement does not always mean the requested operation is complete.

For example:

  • LOAD_ACCEPTED means the fixture has accepted the loading request.
  • LOAD_COMPLETE means the loading operation has reached its defined completion condition.

Confusing these two meanings is a common source of sequence errors.

5.4 Busy or in progress

Indicates that a system is currently performing the requested operation or is occupied with a defined task.

Examples:

  • CNC machining cycle in progress.
  • Robot executing a transfer.
  • Vision system processing an inspection.

The meaning of BUSY must be defined because it may indicate that the system is occupied with any operation, not necessarily the operation requested by the other controller.

5.5 Complete or done

Indicates that the requested operation has finished according to the defined completion criteria.

Examples:

  • Robot has placed the workpiece.
  • CNC has completed machining.
  • Vision system has completed inspection.

Completion should normally be based on appropriate feedback or controller status, rather than merely on a timer expiring.

5.6 Fault or not ready

Indicates that a system cannot accept or complete an operation.

Examples:

  • Robot controller has a fault.
  • Fixture is not in the required position.
  • CNC is in manual mode.
  • Part detection has failed.

Fault and readiness signals help the requesting system decide whether to wait, abort the transaction, or enter a fault-handling state.

6. Two common handshake patterns

6.1 Request and acknowledgement

One system requests an operation, and the other acknowledges the request.

System A                         System B

REQUEST = ON  ----------------->  Receive request

               <---------------  ACKNOWLEDGE = ON

Perform agreed operation

REQUEST = OFF ----------------->  Detect request cleared

               <---------------  ACKNOWLEDGE = OFF

This pattern is useful when one system needs explicit confirmation that the other has recognized the request.

The precise order for clearing the signals must be defined. Otherwise, one system may clear its request before the other has detected it, or the acknowledgement may remain stuck ON.

6.2 Request, busy, and complete

This pattern distinguishes accepting a job from finishing it.

REQUEST = ON
      |
      v
Receiver accepts request
      |
      v
BUSY = ON
      |
      v
Operation in progress
      |
      v
Operation complete
      |
      v
DONE = ON
      |
      v
Request acknowledged and cleared
      |
      v
BUSY = OFF, DONE cleared as defined

This is useful for CNC cycles, robot operations, vision inspections, and other tasks that take time to complete.

The actual implementation may use separate acknowledgement and completion signals, or a more compact protocol.

7. PLC implementation example

Suppose an Allen-Bradley PLC coordinates with a robot controller over digital I/O or a supported communication interface.

Example tags:

PLC or robot tag Example function
Robot_Ready Robot is ready for the defined automatic exchange
PLC_Load_Request PLC requests the robot to load a part
Robot_Load_Accepted Robot acknowledges acceptance
Robot_Load_Complete Robot reports completed loading
Robot_Fault Robot reports a relevant fault
Load_Handshake_Timeout The expected handshake stage exceeded its permitted time

A simplified logical progression could be:

Step 0: Wait for Robot_Ready
        |
        v
Step 10: Set PLC_Load_Request
        |
        v
Wait for Robot_Load_Accepted
        |
        v
Step 20: Wait for Robot_Load_Complete
        |
        v
Step 30: Clear request according to protocol
        |
        v
Confirm handshake reset
        |
        v
Step 40: Continue production sequence

The PLC must not assume that the robot has completed loading merely because Robot_Load_Accepted is ON.

Conceptual Structured Text example

CASE HandshakeStep OF

    0:
        PLC_Load_Request := FALSE;

        IF Robot_Ready AND NOT Robot_Fault THEN
            HandshakeStep := 10;
        END_IF;

    10:
        PLC_Load_Request := TRUE;

        IF Robot_Load_Accepted THEN
            HandshakeStep := 20;
        END_IF;

    20:
        IF Robot_Load_Complete THEN
            PLC_Load_Request := FALSE;
            HandshakeStep := 30;
        END_IF;

    30:
        IF NOT Robot_Load_Accepted
           AND NOT Robot_Load_Complete THEN
            HandshakeStep := 40;
        END_IF;

    40:
        HandshakeComplete := TRUE;

END_CASE;

This is an illustrative fragment, not production-ready code. A real implementation needs a defined reset for HandshakeComplete, timeout handling, start conditions, fault handling, and a complete signal-clearing protocol agreed upon by both systems.

The two controllers must agree on signal meanings and timing. Otherwise, each controller may behave correctly according to its own logic while the overall exchange fails.

8. Handshakes in industrial applications

8.1 Robot and fixture

A robot must place a part in a fixture.

Typical exchange:

  1. Fixture confirms it is ready.
  2. Robot requests loading.
  3. Fixture or PLC accepts the request.
  4. Robot loads the part.
  5. Robot confirms placement.
  6. Part-presence or other required feedback is verified.
  7. The fixture is permitted to begin its next operation.

The exact sequence must prevent incompatible motions and use the required safety controls.

8.2 PLC and CNC

A PLC requests a CNC machining cycle.

Signal Purpose
CNC_Ready CNC can accept the cycle request
Cycle_Start_Request PLC requests the cycle
Cycle_Active CNC reports that the cycle is active
Cycle_Complete CNC reports completion
CNC_Fault CNC reports a relevant fault

The PLC may use these signals to coordinate part clamping, machining, unclamping, and transfer to the next station.

8.3 Conveyor and downstream station

A conveyor transfers a workpiece to a downstream machine.

The upstream system should transfer the workpiece only when the downstream station is ready and the transfer conditions are satisfied.

Without a handshake, the upstream conveyor may keep delivering parts while the downstream station is occupied, potentially causing congestion or a jam.

8.4 Vision system and PLC

The PLC requests an inspection, and the vision system returns a result.

A common exchange involves:

  • Inspection request.
  • Request acknowledgement or inspection-busy status.
  • Inspection result available.
  • Pass/fail result.
  • Result acknowledgement or reset.

The PLC should associate the result with the correct inspection request. A stale pass result from the previous workpiece must not be accepted as the result for the current one.

8.5 PLC and VFD

A PLC can coordinate with a variable-frequency drive using run commands and status signals.

For example, the PLC issues a run request and monitors drive-ready, running, and fault status.

However, not every command/status relationship is a complete handshake. It is a handshake when the implementation defines a coordinated request-and-response exchange, including the required acknowledgement or completion conditions.

9. Handshake faults and troubleshooting

Handshake problems commonly appear as a machine waiting indefinitely at a sequence step.

Typical symptoms include:

  • Robot waiting for a fixture-ready signal.
  • PLC waiting for robot acceptance.
  • CNC cycle requested but not started.
  • Vision inspection completed, but the PLC does not advance.
  • A done signal remains ON and prevents the next transaction.
  • One controller shows ready while the other refuses to proceed.

Troubleshooting method

  1. Identify the exact handshake step where progression stopped.
  2. Identify the signal currently expected.
  3. Check the signal at its source.
  4. Check whether it reaches the receiving controller or communication interface.
  5. Verify the signal's actual definition and the logic that generates it.
  6. Check relevant permissives, interlocks, operating modes, and faults.
  7. Check whether a previous request, acknowledgement, or completion bit remains latched.
  8. Review timeout values and the sequence's fault response.
  9. Correct the underlying cause and follow the approved recovery procedure.

Example: Robot ready, but PLC does not proceed

Possible causes:

  • The robot-ready signal is not mapped to the expected PLC tag.
  • The physical input or communication data is incorrect.
  • The robot is ready for manual operation but not automatic operation.
  • The PLC requires another permissive in addition to robot readiness.
  • The signal changes too briefly for the receiving logic to detect it.
  • The PLC is waiting for a different signal, such as Robot_Load_Accepted.

Do not troubleshoot only the signal name shown on the HMI. Trace the signal from its source through the physical I/O or communication mapping into the receiving logic and the transition condition.

10. Handshake timing, timeouts, and signal clearing

Three design details deserve special attention.

10.1 Timeouts

A timeout detects that a handshake stage has taken longer than allowed.

For example, if the PLC asserts PLC_Load_Request but receives no acknowledgement within the configured time, it can generate a handshake timeout fault.

The timeout should be based on the expected equipment response and operating conditions. A timeout detects an abnormal delay; it does not identify the root cause.

10.2 Signal clearing

Signals must return to the appropriate state before another transaction begins, unless the protocol deliberately uses persistent status signals.

If Robot_Load_Complete remains ON after one workpiece, the PLC may incorrectly interpret it as completion of the next workpiece.

A well-defined handshake specifies:

  • Which system sets each signal.
  • Which system clears each signal.
  • When each signal may change state.
  • How both systems recognize that the transaction has ended.
  • What happens if the exchange is interrupted.

10.3 Stale signals and repeated requests

A request or completion signal left over from a previous cycle can create a false transition.

Robust designs use clearly defined signal lifetimes, state checks, and, where appropriate, sequence identifiers or transaction numbers. Communication protocols may also provide their own mechanisms for identifying new requests and responses.

11. Common handshake design mistakes

Mistake Possible consequence
Treating acknowledgement as completion The next operation starts too early
No timeout The machine waits indefinitely
No defined signal-clearing sequence Signals remain stuck or the next cycle fails
Stale completion signal A new operation is incorrectly treated as complete
Unclear signal ownership Both controllers may set or clear the same signal inconsistently
Different signal definitions across systems Controllers disagree about what a status means
No handling of communication loss The sequence may wait or respond incorrectly
Assuming READY means every condition is safe An operation may proceed without other required conditions
Using ordinary handshake logic as a safety function Safety requirements may not be met

A standard PLC handshake is not a substitute for safety-rated control. Emergency stops, guard monitoring, safe motion, and other safety functions must be implemented through the appropriate safety system and validated design.

12. Interview questions and answers

Q1. What is a handshake in industrial automation?

A handshake is a defined exchange of signals or messages between systems to coordinate an operation and establish that the required request, acknowledgement, readiness, or completion conditions have been met.

Q2. Why is a handshake required between a robot and a PLC?

It coordinates the robot and PLC so that each system knows when the other is ready, when a request has been accepted, and when an operation has completed.

Q3. What is the difference between acknowledgement and completion?

Acknowledgement confirms receipt or acceptance of a request according to the protocol. Completion indicates that the requested operation has reached its defined endpoint.

Q4. What happens if a handshake signal remains ON?

A stale signal can prevent a new transaction from starting or cause the controller to mistake an earlier completion for the current operation.

Q5. How do you troubleshoot a handshake timeout?

Identify the expected signal, check its source and destination, verify the I/O or communication mapping, examine the receiving logic and permissives, and determine why the expected response did not occur within the allowed time.

Q6. Is every PLC command and feedback pair a handshake?

No. A command and its status feedback may be part of a handshake, but a handshake requires a defined coordination protocol between systems, including the relevant request, response, and completion or reset behavior.

Q7. Can a handshake guarantee machine safety?

No. A handshake coordinates operations, but it does not by itself guarantee safety. Required safety functions must be implemented using suitable safety-rated components and control architecture.

13. Final mental model

A handshake answers five practical questions:

  • Ready: Can the other system participate?
  • Request: What operation is being requested?
  • Acknowledgement: Has the request been recognized or accepted?
  • Completion: Has the operation actually finished according to the defined criteria?
  • Reset: Have the signals returned to the correct state for the next transaction?

For maintenance, remember this principle: when two automated systems are waiting for each other, identify which handshake signal is expected, which controller owns it, and what condition should make it change state.
