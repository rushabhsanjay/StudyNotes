1. Definition

A recipe in industrial automation is a predefined collection of process parameters, machine settings, operating limits, and product-specific instructions used to manufacture or process a particular product.

A recipe allows a machine to change its operating configuration for different products without requiring an engineer to manually modify every parameter in the PLC, HMI, CNC, robot controller, or other automation equipment.

For example, an automotive production line may manufacture several variants of a component. Each variant may require different welding parameters, clamping settings, robot programs, inspection limits, or process timings.

Instead of manually entering all these settings whenever the product changes, the operator selects the appropriate recipe. The control system loads the approved settings and verifies the conditions required to run the new product.

The central idea is that a recipe defines the required process settings for a particular product or operation.

2. Why recipes are required

In manufacturing, one machine may process multiple product variants. Manually changing every parameter increases changeover time and introduces opportunities for incorrect settings.

Recipes provide:

  • Repeatability: The same approved settings can be applied consistently.
  • Faster changeovers: Operators can select a product configuration instead of manually entering every parameter.
  • Product differentiation: Different variants can use different process settings.
  • Quality control: Parameters can be checked against approved values and limits.
  • Traceability: The selected recipe and its version can be recorded with production data.
  • Reduced operator error: Controlled selection reduces the risk of entering incorrect settings.
  • Standardization: Production equipment can use an agreed set of parameters for each product.

A recipe does not automatically guarantee product quality. The settings must be correct, the equipment must be functioning properly, and the process must be monitored.

3. What does a recipe contain?

Recipe contents depend on the machine and manufacturing process.

Recipe element Example Purpose
Product identifier BRACKET_A Identifies the product variant
Recipe identifier RCP_010 Identifies a particular configuration
Recipe version V03 Identifies the approved revision
Process parameters Welding current and time Defines process operating settings
Motion parameters Robot speed or position selection Defines product-specific motion configuration
Machine settings Clamp pressure setpoint Defines required machine conditions
Quality limits Minimum and maximum measured dimension Defines acceptance criteria
Timing parameters Hold time or dwell time Defines operation timing
Tool or program selection Approved robot program number Selects the required operation
Validation data Permitted ranges and compatibility checks Prevents invalid configurations from being applied

Not every item must physically reside in one recipe file. Some values may be stored in the PLC, others in a robot controller, CNC, vision system, or manufacturing database. The important requirement is that the recipe is defined and managed consistently across the systems that use it.

4. Recipe versus related concepts

Concept Meaning Example
Recipe Collection of product-specific process settings Welding configuration for a bracket variant
Parameter One configurable value Welding hold time
Setpoint Desired target value for a controlled variable Pressure target of 5 bar
Actual value Measured or reported operating value Actual pressure of 4.9 bar
PLC program Logic that determines how the machine operates Sequence controlling clamping and welding
Robot program Program defining robot motion and operations Robot path for a particular component
Product code Identifier for the product being manufactured BRACKET_A
Recipe version Specific revision of a recipe R03
Production order Manufacturing instruction for a quantity of a product Produce 500 units of BRACKET_A

A recipe usually supplies configuration data to a program. The program determines how the machine uses that data.

For example, a PLC program may contain the sequence:

Clamp Part
    ↓
Verify Clamp Position
    ↓
Execute Welding Operation
    ↓
Verify Process Completion
    ↓
Release Part

The recipe may define the welding parameters and other product-specific settings used during that sequence.

Changing a recipe should not require changing the PLC logic for every product variant, provided the existing program already supports those variants and their required operations.

5. Common types of recipes

5.1 Product recipe

Contains settings required to manufacture a particular product or variant.

Examples:

  • Different welding parameters for two automotive brackets.
  • Different pressure and dwell-time settings for two assembly variants.
  • Different dimensional limits for two product models.

5.2 Process recipe

Defines settings for a particular process, sometimes independently of a finished product identity.

Examples:

  • Heat-treatment temperature profile.
  • Paint-curing temperature and duration.
  • Chemical mixing ratios and process duration.

Product recipes and process recipes can overlap. The distinction depends on how the manufacturing system organizes its configuration data.

5.3 Machine recipe

Contains configuration values specific to a particular machine or station.

Examples:

  • Clamp pressure settings.
  • Conveyor speed.
  • Tool selection.
  • Sensor thresholds used for process control.

A machine recipe may form one part of a larger product recipe.

5.4 Inspection recipe

Defines product-specific inspection settings.

Examples:

  • Vision-system inspection regions.
  • Dimensional acceptance limits.
  • Camera exposure settings.
  • Inspection criteria and defect thresholds.

An inspection recipe must be controlled carefully because incorrect limits can cause good parts to be rejected or defective parts to be accepted.

5.5 Multi-step process recipe

Defines a series of process stages, each with its own parameters.

For example, a heat-treatment recipe may contain:

  1. Heating stage.
  2. Temperature stabilization stage.
  3. Soaking stage.
  4. Cooling stage.

Each stage may have different target values, duration requirements, and transition conditions.

This type of recipe is especially common in process and batch manufacturing.

6. How recipe selection works in an automated machine

Consider an automotive assembly station that can process two product variants.

  • Product A requires recipe RCP_A.
  • Product B requires recipe RCP_B.

A typical workflow is:

Product Identified
        ↓
Requested Recipe Selected
        ↓
Recipe Exists and Is Approved?
        ↓
Parameters and Version Validated
        ↓
Required Machine Configuration Applied
        ↓
Configuration Confirmed
        ↓
Required Start Conditions Satisfied?
        ↓
Production Cycle Enabled

The system should not enable production merely because a recipe was selected. It should verify that the recipe is valid, compatible with the machine and product, and applied correctly.

Depending on the equipment, additional checks may include:

  • Correct fixture or tooling installed.
  • Correct robot or CNC program selected.
  • All required parameters transferred successfully.
  • Product identity matches the selected recipe.
  • Required calibration and equipment status are valid.
  • Recipe version is approved for production.

The required checks depend on the risk and process requirements.

7. Recipe implementation in a PLC

Recipes can be implemented in different ways.

7.1 Recipe values stored in PLC data

The PLC stores predefined values for each supported product.

For example:

Parameter Recipe A Recipe B
Clamp pressure setpoint 4.0 bar 5.0 bar
Process hold time 1.5 s 2.0 s
Conveyor speed 20 m/min 15 m/min

When the operator selects a recipe, the PLC copies the approved values into the working parameters used by the machine.

These values are illustrative only. Actual values must come from the validated process specification.

7.2 Recipe values stored in an HMI

The HMI may provide a recipe-management interface for:

  • Selecting a recipe.
  • Displaying parameters.
  • Loading or transferring settings.
  • Showing recipe identity and version.
  • Restricting editing to authorized users.

The HMI may store the data locally or retrieve it from another system. The architecture depends on the platform.

7.3 Recipe values stored in a database

A manufacturing system may maintain recipes in a database and transfer the required values to the machine.

This is useful when recipes need centralized revision control, access management, production traceability, or distribution across multiple machines.

The database should not be treated as proof that the machine successfully received and applied the values. The machine-side application and validation still matter.

8. Conceptual Structured Text example

The following example illustrates selecting between two predefined recipes.

CASE SelectedRecipe OF

    1:
        RequestedClampPressure := 4.0;
        RequestedHoldTime := 1.5;
        RecipeValid := TRUE;

    2:
        RequestedClampPressure := 5.0;
        RequestedHoldTime := 2.0;
        RecipeValid := TRUE;

    ELSE
        RecipeValid := FALSE;

END_CASE;

The example maps a recipe selection to process parameters. It does not constitute a complete recipe-management system.

A production implementation should also address:

  • Validating parameter ranges and data types.
  • Separating requested parameters from active parameters.
  • Applying values at an appropriate point in the machine sequence.
  • Preventing unauthorized recipe modifications.
  • Verifying that the selected recipe is compatible with the product and machine.
  • Managing recipe versions and approved changes.
  • Handling failed or interrupted recipe transfers.
  • Recording the active recipe for traceability.

Important distinction: Selecting a recipe and applying a recipe are different events. A recipe can be selected on the HMI while the machine is still operating with the previous active settings.

9. Requested recipe versus active recipe

This distinction is particularly useful during troubleshooting.

State Meaning
Requested recipe The recipe the operator or production system wants to use
Validated recipe The requested recipe has passed the required checks
Loaded recipe The settings have been transferred to the intended controller or equipment
Active recipe The settings currently authorized for use by the running process
Recipe mismatch The selected product, recipe, version, or applied settings do not agree

For example, the HMI may display Product B, but the PLC may still be using the active settings from Product A because the transfer was unsuccessful.

If the machine is allowed to run under those conditions, the result could be a quality defect or equipment problem.

A robust design clearly displays the requested and active recipe identities and prevents production when a required configuration check fails.

10. Recipe validation and change control

A recipe can be syntactically valid but operationally incorrect.

For example, a welding recipe might contain numerical values within the PLC's permitted data range but still use the wrong settings for the selected component.

Recipe validation should therefore consider several levels:

  1. Data validation: Are values within permitted ranges and of the correct type?
  2. Product validation: Does the recipe correspond to the requested product?
  3. Equipment validation: Is the recipe compatible with the installed tooling and machine configuration?
  4. Process validation: Are the settings approved for the intended process?
  5. Application validation: Were the settings successfully applied to the relevant controllers?
  6. Version validation: Is the recipe revision approved for production?

Recipe changes should be controlled according to the organization's change-management process. Depending on the application, this may require engineering approval, revision history, testing, and release authorization.

For safety-related parameters, the applicable safety engineering and validation requirements must also be followed. A normal recipe-selection mechanism should not be used to bypass safety functions.

11. Recipe management in manufacturing

In larger manufacturing systems, recipes may be managed centrally and distributed to production equipment.

A typical arrangement is:

Production Order
       ↓
Product Identity
       ↓
Approved Recipe and Version
       ↓
Manufacturing System / Recipe Database
       ↓
PLC / CNC / Robot / Vision System
       ↓
Validation and Application
       ↓
Production
       ↓
Process Results and Traceability

The manufacturing system may be an MES, a supervisory application, or a dedicated recipe-management system. The architecture varies by plant.

Recipe management may include:

  • Recipe creation and approval.
  • Revision history.
  • User access control.
  • Distribution to multiple machines.
  • Compatibility checks.
  • Backup and restoration.
  • Audit trails.
  • Recording the recipe used for each production batch or unit.

A recipe database, PLC, and HMI should have clearly defined responsibilities. Without them, different systems can hold conflicting versions of what is supposedly the same recipe.

12. Recipe-related faults and maintenance troubleshooting

Recipe problems are not always caused by faulty sensors or actuators. Sometimes the machine is operating correctly but using incorrect configuration data.

Symptom Possible cause Diagnostic direction
Incorrect process result Wrong recipe selected Verify product identity and recipe selection
HMI shows the new recipe but machine uses old settings Recipe transfer or activation failed Compare requested, loaded, and active values
Recipe cannot be selected Invalid identifier or access restriction Check recipe availability and authorization
Some parameters update but others do not Partial transfer or mapping error Compare source data with controller parameters
Machine refuses to start after a changeover Recipe validation or compatibility check failed Inspect the specific failed condition
Vision system rejects too many parts Wrong inspection recipe or thresholds Verify recipe identity and approved inspection limits
Fault appears after recipe revision Incorrect change, incompatibility, or regression Compare revisions and validate the changed parameters
Recipe disappears after a restart Persistence, storage, or loading problem Check the configured storage and startup procedure

Practical troubleshooting procedure

  1. Confirm the actual product variant.
  2. Verify the requested recipe identifier and version.
  3. Verify the active recipe shown by the controller, not just the HMI selection.
  4. Compare critical active parameters with the approved specification.
  5. Check whether the recipe was transferred and validated successfully.
  6. Verify the selected machine, tooling, robot program, and other dependencies.
  7. Review recipe-change history and any relevant alarms.
  8. Correct the underlying cause and verify the process using the approved procedure before releasing production.

Avoid changing several parameters experimentally just to make the fault disappear. That can obscure the root cause and create a process configuration that no longer matches the approved specification.

13. Common recipe-design mistakes

Mistake Consequence
No recipe version control Unclear which configuration was approved
No validation before activation Invalid settings may reach the machine
Requested and active recipes are not distinguished Operators may believe a change was applied when it was not
Parameters are edited without authorization Uncontrolled process changes
Recipe is not linked to product identity Wrong settings may be applied to a product
Partial transfer is treated as success Different controllers may use inconsistent values
No backup or recovery procedure Approved configurations may be lost
Recipe changes are not recorded Difficult quality investigations and poor traceability
Recipe settings are assumed to guarantee safety Safety requirements may be bypassed or misunderstood

14. Interview questions and answers

Q1. What is a recipe in industrial automation?

A recipe is a predefined collection of process parameters and machine settings used to configure equipment for a particular product or operation.

Q2. What is the difference between a recipe and a PLC program?

The PLC program defines the machine's control logic and operating behavior. The recipe supplies configurable data used by that logic.

Q3. Why are recipes useful in automotive manufacturing?

They support multiple product variants, reduce changeover effort, improve repeatability, and help ensure that approved settings are used for the correct product.

Q4. What is the difference between a requested recipe and an active recipe?

The requested recipe is the desired configuration. The active recipe is the configuration currently applied and authorized for use by the process.

Q5. What is recipe validation?

Recipe validation checks that the recipe is available, approved, compatible with the product and equipment, and contains acceptable parameters before it is applied or production is enabled.

Q6. How would you troubleshoot a machine producing defective parts after a changeover?

Verify product identity, requested and active recipe versions, critical parameters, transfer status, equipment configuration, and recent recipe changes. Then confirm that the approved settings have been applied before releasing production.

Q7. Can recipes be stored in an HMI or database instead of a PLC?

Yes. Recipes may be stored in an HMI, database, PLC, or dedicated recipe-management system. The design must define how settings are validated, transferred, activated, and verified.

Q8. Why is recipe version control important?

It establishes which configuration was approved and used, supports controlled changes, and helps trace process or quality problems to a specific revision.

15. Final mental model

Think of a recipe as the approved configuration data for a product or process, while the control program defines how the machine executes the operation.

  • Product identity: What are we manufacturing?
  • Recipe: Which approved settings are required?
  • Validation: Are those settings correct and permitted?
  • Transfer: Have the settings reached the intended equipment?
  • Activation: Is the machine actually using them?
  • Traceability: Can the configuration used during production be identified later?

For maintenance, remember this principle: never assume that the recipe displayed on the HMI is the recipe currently controlling the machine. Verify the active configuration and its critical parameters.
