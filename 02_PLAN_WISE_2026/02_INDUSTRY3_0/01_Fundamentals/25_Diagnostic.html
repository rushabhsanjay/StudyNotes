1. Definition

Diagnostics is the process of collecting, interpreting, and analyzing information from a machine, control system, or device to determine its operating condition, identify abnormalities, and narrow down their possible causes.

In industrial automation, diagnostics helps engineers understand what a machine is doing, what is going wrong, where the problem may be located, and what evidence is needed to identify the root cause.

Examples:

  • A PLC diagnostic buffer identifies a controller error or module fault.
  • A VFD displays an overcurrent fault and records operating data.
  • A CNC controller reports an axis following error.
  • A robot controller identifies a servo fault or communication problem.
  • An HMI displays a sensor timeout and identifies the affected station.
  • A maintenance engineer uses input status, output status, and electrical measurements to locate a broken signal path.

Key principle: Diagnostics provides evidence about a system's condition. It does not automatically guarantee that the root cause has been identified.

2. Why diagnostics is required

Modern automated machines contain interconnected electrical, mechanical, pneumatic, hydraulic, software, and communication systems. A single failure can produce several symptoms across different components.

Diagnostics helps to:

  1. Locate problems: Identify the affected device, module, machine, or subsystem.
  2. Reduce troubleshooting time: Avoid checking unrelated components.
  3. Distinguish causes from symptoms: Identify the initiating problem rather than only its consequences.
  4. Support maintenance decisions: Determine whether a component needs inspection, repair, replacement, or configuration correction.
  5. Verify machine health: Identify abnormal conditions before they cause a production interruption.
  6. Support root-cause analysis: Provide evidence for corrective and preventive actions.
  7. Verify repairs: Confirm that the original abnormal condition has disappeared and the system behaves correctly.

For a maintenance engineer, diagnostics is the bridge between observing a machine failure and deciding what to investigate next.

3. Diagnostics versus related terms

Term Meaning Example
Monitoring Observing system variables and status Displaying motor current and temperature
Detection Identifying that an abnormal condition exists Detecting that a sensor signal is missing
Diagnostics Analyzing evidence to identify the affected component or likely cause Determining whether the missing signal is caused by a sensor, cable, or input module
Fault A detected abnormal condition Encoder feedback fault
Trip A protective action that stops or inhibits operation Drive output is disabled
Troubleshooting A practical, systematic investigation to locate and correct a problem Testing the encoder cable and feedback signals
Root-cause analysis Investigating the underlying reason a problem occurred Finding that repeated cable damage is caused by incorrect cable routing
Repair Correcting the identified problem Replacing the damaged cable and correcting its routing

These activities overlap in practice, but they are not interchangeable.

A monitoring system may show that a motor has stopped. Detection may identify a drive fault. Diagnostics may reveal an overcurrent event during acceleration. Troubleshooting may uncover a mechanically jammed conveyor. Root-cause analysis may then identify poor material-flow design that repeatedly causes the jam.

4. Where diagnostics exists in an automation system

Diagnostics is not limited to the PLC or HMI. It can exist at every level of an industrial automation architecture.

FIELD LEVEL
Sensors, actuators, transmitters, encoders
        ↓
Signal status, device indicators, wiring checks

CONTROL LEVEL
PLC, remote I/O, VFD, servo drive
        ↓
Module status, controller buffers, drive fault history

MACHINE LEVEL
CNC, robot controller, machine sequence
        ↓
Axis status, sequence step, interlock state

SUPERVISORY LEVEL
HMI, SCADA, alarm and event systems
        ↓
Alarm history, trends, timestamps, operator messages

PLANT / MAINTENANCE LEVEL
Maintenance records, downtime data, recurring-fault analysis
        ↓
Failure patterns, root-cause investigations, corrective actions

The exact division depends on the plant architecture. A drive may perform its own diagnostics, while the PLC interprets its status and the HMI presents it to the operator.

5. Types of industrial diagnostics

Diagnostic type Purpose Example
Electrical diagnostics Investigate power and signal integrity Checking a 24 V DC supply, fuse, or sensor output
Device diagnostics Interpret internal device status Reading a VFD fault code
PLC diagnostics Identify controller, program, and I/O issues Checking module faults and diagnostic buffers
Communication diagnostics Identify network or data-exchange problems Investigating EtherNet/IP or PROFINET communication loss
Sequence diagnostics Determine where a machine cycle stopped Identifying an unsatisfied transition condition
Mechanical diagnostics Investigate physical movement or loading Checking a jammed conveyor or seized bearing
Process diagnostics Determine why a process variable is abnormal Investigating low hydraulic pressure
Safety-system diagnostics Identify safety-device or safety-controller status Checking guard-switch or safety-module diagnostics
Performance diagnostics Identify degradation and recurring inefficiencies Comparing cycle time and motor current trends
Historical diagnostics Analyze recorded events and recurring patterns Finding repeated trips after a particular operation

These categories can interact. For example, a communication problem may cause a drive status to become unavailable, which then prevents a machine sequence from progressing.

6. Diagnostic information sources

Effective diagnostics depends on using the right evidence.

Information source What it can reveal Important limitation
Status LEDs Power, operating state, or fault indication Usually provide limited detail
HMI alarm message Reported abnormal condition May describe a consequence rather than the cause
PLC online monitoring Input, output, and internal logic states Depends on correct program interpretation
Controller diagnostic buffer Controller and module events May not contain every field-level failure
VFD fault history Drive protection events and related data Does not always explain the upstream mechanical cause
CNC or robot alarm history Axis, servo, program, or controller errors Alarm meaning depends on the specific controller
Multimeter or electrical tester Voltage, continuity, and electrical measurements Measurements must be taken using appropriate safe procedures
Oscilloscope or signal analyzer Signal timing, noise, and waveform behavior Requires suitable equipment and interpretation
Network diagnostics Connection status, packet errors, device availability Network health alone does not prove application-level data is correct
Trend and event logs Variable changes and event chronology Missing timestamps or sampling gaps can mislead
Maintenance records Repeated failures and prior corrective actions Records may be incomplete or inaccurate

A useful diagnostic investigation combines independent evidence rather than relying on one alarm message.

7. Diagnostic reasoning: symptom, evidence, and cause

Consider an automated fixture that fails to complete its clamping sequence.

Observed symptom: The machine remains waiting for clamp confirmation.

Possible explanations include:

  • The clamp has not physically reached its required position.
  • The proximity sensor has failed.
  • The sensor is misaligned.
  • The sensor has no power.
  • A cable or connector is damaged.
  • The PLC input module is faulty.
  • The PLC program is evaluating the wrong input.
  • The required signal is delayed or unavailable because of communication problems.

The symptom alone cannot distinguish among these possibilities.

A diagnostic process narrows the possibilities using evidence.

Machine waiting for clamp confirmation
                  ↓
Check actual clamp position
                  ↓
Check sensor indicator and output
                  ↓
Check voltage and wiring
                  ↓
Check PLC input status
                  ↓
Check sequence condition and timer
                  ↓
Identify the most likely failed component or condition
                  ↓
Verify the diagnosis with appropriate tests

The order should be adapted to the machine, the available evidence, and the safety requirements. It is not always necessary to test every item if an earlier observation conclusively identifies the problem.

8. PLC sequence diagnostics

One of the most useful diagnostic methods in automation is determining which condition is preventing the sequence from advancing.

Suppose a machine sequence is:

Step 10: Wait for part present
             ↓
Step 20: Clamp the part
             ↓
Step 30: Confirm clamp closed
             ↓
Step 40: Start machining
             ↓
Step 50: Confirm machining complete
             ↓
Step 60: Release the part

If the machine is stopped at Step 30, the diagnostic task is to determine why the clamp-closed condition has not been accepted.

The engineer should check:

  1. Whether the PLC is actually executing Step 30.
  2. Whether the clamp-close command was issued.
  3. Whether the clamp moved physically.
  4. Whether the clamp-closed sensor changed state.
  5. Whether the corresponding PLC input reflects the sensor state.
  6. Whether any additional interlock or permissive prevents progression.
  7. Whether a timeout or other fault has occurred.

This is much more effective than randomly changing timers or forcing outputs until the machine moves. Those methods can conceal the actual failure and introduce additional hazards.

9. Diagnostic logic and fault messages

A diagnostic system can evaluate conditions and generate meaningful fault information.

Illustrative Structured Text:

IF Clamp_Close_Command
   AND NOT Clamp_Closed_Feedback
   AND Clamp_Timeout_Elapsed THEN

    Clamp_Timeout_Fault := TRUE;

END_IF;

This example indicates that a clamp timeout fault is generated when the close command is active, the expected feedback has not arrived, and the timeout has elapsed.

However, the diagnostic does not prove that the clamp itself is defective. The cause could be a mechanical obstruction, pneumatic or hydraulic supply problem, sensor failure, wiring fault, or incorrect feedback.

A well-designed diagnostic message should identify the affected function and the failed expectation.

Poor message:

FAULT 102

More useful message:

Station 3: Clamp-closed feedback not received within the permitted time.

An even better diagnostic display may include:

  • Machine or station identifier.
  • Sequence step.
  • Expected signal.
  • Actual signal state.
  • Timeout duration.
  • Timestamp.
  • Relevant controller or device fault code.

Diagnostic messages should describe what the system knows, not claim a root cause that has not been established.

10. Diagnostic coverage and limitations

A diagnostic system cannot identify every possible failure. Its usefulness depends on the faults it can detect and the evidence it can collect.

Diagnostic coverage generally describes the proportion of relevant failures that a diagnostic method can detect, according to the applicable definition and system context.

For example:

  • A basic sensor input can indicate whether a signal is ON or OFF.
  • A more capable sensor may report internal faults or signal-quality information.
  • A smart drive may provide current, temperature, voltage, and fault-history information.
  • A predictive maintenance system may analyze trends to identify degradation before a conventional trip occurs.

Greater diagnostic capability can improve fault detection, but it does not eliminate uncertainty.

Common diagnostic limitations

  • A sensor may report a plausible value even when its measurement is inaccurate.
  • A PLC input can be logically correct while the physical sensor is misaligned.
  • A drive fault code may identify the electrical symptom but not the mechanical cause.
  • A network may be operational while transmitted application data is incorrect or stale.
  • An HMI alarm may appear after the original event because of communication or processing delays.
  • A diagnostic function may itself fail or become unavailable.

A diagnostic indication must be interpreted in the context of the actual equipment and its design.

11. Diagnostics and preventive or predictive maintenance

Diagnostics supports several maintenance approaches.

Maintenance approach Role of diagnostics Example
Breakdown maintenance Identify the cause after failure Find why a VFD tripped
Preventive maintenance Detect known issues during scheduled inspection Identify loose terminals or degraded connections
Condition-based maintenance Trigger maintenance based on measured condition Investigate rising bearing temperature
Predictive maintenance Estimate developing failure using trends or models Detect a gradual vibration increase
Reliability improvement Identify recurring failure patterns Find repeated encoder-cable failures across machines

Diagnostics and predictive maintenance are related, but not identical. Diagnostics determines or narrows down what is wrong. Predictive maintenance uses condition information and analysis to estimate deterioration or future failure.

12. Practical diagnostic procedure for maintenance engineers

Use a repeatable method rather than relying entirely on experience or guesswork.

  1. Confirm the symptom. Identify exactly what stopped working and under what operating conditions.
  2. Collect the available evidence. Record alarm text, timestamps, controller status, device codes, and relevant process values.
  3. Determine the affected subsystem. Separate electrical, mechanical, control, communication, and process possibilities.
  4. Identify the expected behavior. Establish what the machine should have done at that point in the sequence.
  5. Compare expected and actual states. Check commands, feedback, interlocks, permissives, timers, and device diagnostics.
  6. Form a testable hypothesis. Identify the most likely explanation supported by the evidence.
  7. Perform the appropriate test. Use approved procedures, suitable instruments, and the required isolation and safety controls.
  8. Confirm the cause. Verify the suspected problem instead of replacing parts based on an alarm label alone.
  9. Correct the problem and validate operation. Confirm that the original failure is resolved and that the machine behaves correctly under controlled conditions.
  10. Record the findings. Document the cause, evidence, repair, replaced parts, and recurrence-prevention action.

Electrical measurements, cabinet inspections, and machine tests must follow the applicable isolation, lockout/tagout, and safety procedures. Diagnostic convenience is not a reason to expose personnel to hazardous energy.

13. Common diagnostic-design mistakes

  • Displaying cryptic fault numbers without meaningful descriptions.
  • Generating one generic alarm for multiple unrelated causes.
  • Failing to preserve the original fault when subsequent events overwrite it.
  • Not recording timestamps or the sequence of events.
  • Diagnosing only from HMI messages without checking device and controller status.
  • Confusing a missing feedback signal with a failed actuator.
  • Reporting a suspected cause as a confirmed cause.
  • Ignoring communication failures and stale data.
  • Using excessively long timeouts that hide slow or degraded equipment.
  • Using excessively short timeouts that produce nuisance faults.
  • Allowing diagnostic logic to alter machine behavior unexpectedly.
  • Failing to test diagnostic messages after program changes.

Good diagnostics should help a technician answer three questions quickly: What was expected? What actually happened? What evidence distinguishes the possible causes?

14. Interview questions and answers

Q1. What is diagnostics in industrial automation?

Diagnostics is the collection and interpretation of system information to determine operating condition, detect abnormalities, and identify or narrow down their causes.

Q2. What is the difference between fault detection and fault diagnosis?

Fault detection determines that an abnormal condition exists. Fault diagnosis investigates the nature and likely location or cause of that condition.

Q3. What is the difference between troubleshooting and diagnostics?

Diagnostics produces information about system condition and possible causes. Troubleshooting is the practical investigation used to confirm the cause and correct the problem. In practice, they often occur together.

Q4. How do you diagnose a machine that is stuck in one sequence step?

Check the active step, the command issued, expected feedback, relevant inputs, interlocks, permissives, timers, and controller or device diagnostics. Compare the actual machine state with the conditions required to advance.

Q5. Why is an alarm message not always the root cause?

An alarm may report a downstream consequence. For example, a motor-stopped alarm may result from a VFD trip, which may itself have been caused by a mechanical jam.

Q6. What is first-out diagnostics?

It identifies or preserves the first detected event in a sequence of related abnormalities so that the initiating event can be distinguished from subsequent consequences.

Q7. What is diagnostic coverage?

It describes how much of a defined set of relevant failures can be detected by a diagnostic method, subject to the applicable engineering definition.

Q8. How can diagnostics reduce machine downtime?

It narrows the search area, provides relevant evidence, identifies recurring failures, and reduces unnecessary component replacement and repeated trial-and-error.

Q9. Can diagnostics guarantee that a machine is healthy?

No. Diagnostics can only evaluate the conditions and failures it is designed and able to observe. Some failures remain undetected, and diagnostic information can be incomplete or misleading.

Q10. What should be recorded in a useful diagnostic log?

The timestamp, affected equipment, fault code and description, relevant process values, sequence state, device status, corrective action, confirmed cause, and verification results.

15. Final mental model

OBSERVE
What is the machine doing?

DETECT
What abnormal condition exists?

COLLECT EVIDENCE
What do the PLC, drive, sensors, logs, and measurements show?

ANALYZE
Which explanations fit the evidence?

TEST
Which explanation can be confirmed?

CORRECT
What needs to be repaired or changed?

VERIFY
Does the system now behave as intended?

DOCUMENT
What happened, why, and how can recurrence be prevented?

For industrial maintenance, diagnostics is the discipline of turning machine behavior and recorded data into useful technical evidence. Its value is not the number of alarms a system produces, but how effectively that information helps identify the actual problem.
