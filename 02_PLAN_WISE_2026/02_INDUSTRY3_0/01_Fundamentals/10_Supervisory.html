The supervisory level is the layer of industrial automation responsible for giving operators and engineers visibility into the process, presenting equipment status and alarms, recording operational data, and allowing authorized supervisory commands.

Its main purpose is to help people understand what the automated system is doing, identify abnormal conditions, and make informed operating decisions.

The central concept is:

Field level measures and acts. Control level executes control logic. Supervisory level provides visibility, monitoring, historical context, and operator interaction.

1. Position of the supervisory level

Supervisory Level
SCADA, HMI, alarms, trends, operator monitoring
                    ↕
Control Level
PLC, DCS controllers, CNC and robot controllers
                    ↕
Field Level
Sensors, transmitters, switches, actuators
                    ↕
Physical Process
Machines, production lines, equipment and materials

The supervisory level receives operational data from controllers and presents it in a form that people can understand and use.

For example, a PLC might store the state of a conveyor as a Boolean tag, CONVEYOR_RUNNING = TRUE. A supervisory application can present that tag as a conveyor graphic with a running indication, display its speed, show relevant alarms, and record its operating history.

The supervisory level does not need to execute every machine operation itself. In a properly designed system, the PLC or dedicated controller generally handles the time-critical control logic locally.

2. What does the supervisory level do?

Function Purpose Industrial example

Visualization Presents technical data graphically Mimic diagram of a production line
Operator interaction Allows authorized commands and setpoint changes Operator requests a conveyor start
Alarm presentation Notifies operators of abnormal conditions Displays a motor fault
Event recording Records significant changes and actions Records when a station stopped
Trending Shows how values change over time Graphs motor current over a shift
Historical data Preserves process data for later analysis Reviews temperature before a failure
Reporting Converts collected data into useful summaries Produces downtime and production reports
Supervisory coordination Provides visibility across several machines or areas Monitors multiple robotic stations

These functions may be provided by one software package or distributed across several applications and servers.

3. Human-Machine Interface (HMI)

An HMI, or Human-Machine Interface, is the interface through which a person interacts with an automated machine or process.

An HMI may be a touchscreen mounted on a machine, an industrial panel PC, or a graphical interface running on an operator workstation.

Industrial automation HMI and SCADA screens

Typical HMI functions include:

  • Displaying machine status, operating mode, and process values.
  • Showing buttons and controls for authorized operator actions.
  • Displaying active faults and alarms.
  • Showing counters, setpoints, and production information.
  • Providing manual operation screens when the system is designed to support them.
  • Displaying diagnostic information useful to maintenance personnel.

Example: Conveyor HMI

A conveyor HMI might display:

Display item Example
Conveyor status Running
Motor speed 35 Hz
Production count 1,240 parts
Operating mode Automatic
Motor fault Inactive
Start command Available when permitted
Stop command Available according to the operating design

The displayed information is only as reliable as its underlying signals, tag mapping, communications, and application logic.

HMI versus physical push buttons

A physical push button sends an electrical input to a control system. An HMI button is a software-based control that normally sends a command or changes a tag through the configured communication interface.

Neither automatically guarantees that the requested operation will occur. The controller must still evaluate the applicable operating conditions and execute the command.

4. Supervisory Control and Data Acquisition (SCADA)

SCADA stands for Supervisory Control and Data Acquisition.

A SCADA system collects information from industrial controllers and devices, presents it to operators, manages supervisory functions, and often records data for historical analysis.

SCADA is commonly used when operators need to monitor multiple machines, process areas, production lines, or geographically distributed sites.

Industrial SCADA control room

Typical SCADA capabilities include:

  • Communication with PLCs, RTUs, and other industrial devices.
  • Collection and display of process tags.
  • Operator graphics and supervisory commands.
  • Alarm and event handling.
  • Historical data and trend displays.
  • Reports and integration with other operational systems.
  • Monitoring of communication and device status.

The exact features depend on the SCADA platform and system architecture. A small installation may run most functions on one industrial PC. A larger plant may use separate servers, operator clients, historians, gateways, and redundant components.

HMI versus SCADA

These terms are related, but they are not interchangeable in every context.

Aspect HMI SCADA
Primary purpose Human interaction with a machine or process Broader supervisory monitoring and data acquisition
Typical scope One machine or a limited process area Multiple machines, lines, areas, or remote sites
User interface Usually central to the product Usually includes operator interfaces
Data collection May collect data from one controller Often collects data from many controllers
Historical data May have limited logging or trends Commonly supports central historical data collection
Architecture Can be a standalone panel Often includes communication services and shared supervisory components

An HMI can be part of a SCADA system. A standalone machine HMI does not automatically constitute a complete SCADA system.

6. Tags: The basic units of supervisory data

A tag is a named data point representing a process value, equipment state, command, or other item used by an automation application.

For example, a PLC might expose these tags to SCADA:

Tag name Data type Example value Meaning
FR1010_R1_RUN Boolean TRUE Robot 1 run status
CONV01_SPEED Real 35.0 Conveyor speed
WELD_TEMP Real 182.5 Measured welding-related temperature
AIR_PRESSURE Real 5.8 Pneumatic pressure
PART_COUNT Integer 1240 Production count
MOTOR_FAULT Boolean FALSE Motor fault indication

These values are illustrative.

A tag can be associated with a PLC address, a controller variable, a calculated expression, a database value, or another data source, depending on the platform.

Important tag properties

A useful supervisory system may track more than the tag's current value. It may also track:

  • Value: The current reported state or measurement.
  • Timestamp: When the value was acquired or updated.
  • Quality: Whether the value is considered good, uncertain, or bad.
  • Description: What the tag represents.
  • Engineering unit: Such as °C, bar, mm, or Hz.
  • Limits: Values used for display, alarm, or other configured functions.
  • Source: The controller, device, or calculation supplying the value.

For instance, a pressure display showing 5.8 bar is potentially misleading if its source has lost communication and the application is still showing an old value. Good supervisory design distinguishes a current, valid measurement from a stale or unavailable one.

7. Real-time monitoring versus historical monitoring

These two functions answer different questions.

Real-time monitoring answers: What is happening now, according to the available data?

Historical monitoring answers: What happened previously, and how did the process change over time?

Consider a motor that trips during production.

The live SCADA screen may show that the motor is stopped and faulted. Historical records may show that motor current increased, conveyor speed decreased, and the fault occurred several seconds later.

The historical information can help engineers investigate the sequence of events instead of merely observing the final fault state.

Trends

A trend is a graphical representation of a value over time.

Common industrial trends include:

  • Motor current versus time.
  • Pressure versus time.
  • Temperature versus time.
  • Production count versus time.
  • Machine cycle time versus time.
  • Equipment running status versus time.

Trends help identify fluctuations, gradual degradation, abnormal operating patterns, and relationships between variables.

Historian

An industrial historian is designed to preserve process data over time. It often supports time-series storage, compression, retrieval, and historical analysis.

A historian and a conventional relational database are not the same thing, although their capabilities can overlap. A historian is purpose-built for operational time-series data, while a relational database is commonly used for structured records, transactions, and application data.

The choice depends on the required data volume, retention, query patterns, integration, and performance.

8. Alarms and events

The supervisory level commonly presents alarms and records events. These concepts are related but different.

An alarm indicates an abnormal condition that requires operator awareness or action.

An event records a significant occurrence or state change, which may or may not require immediate action.

Example Alarm or event? Reason
Hydraulic pressure exceeds its high limit Alarm An abnormal condition may require intervention
Operator logs into the SCADA system Event Records an occurrence
Robot controller loses communication Often an alarm The operator may need to respond
Production counter increases Usually a data change or event It records normal operation
Machine changes from Manual to Automatic Event Records a mode transition
Motor overload occurs Alarm Indicates a fault condition requiring attention

Exact classifications depend on the application's design and operating philosophy.

Alarm information

A useful alarm record may include:

  • Alarm description.
  • Equipment or tag identification.
  • Time of occurrence.
  • Priority.
  • Current state.
  • Acknowledgment status.
  • Return-to-normal time.
  • Operator response or related event, where configured.

An alarm acknowledgment means that an operator has acknowledged the notification. It does not necessarily mean the underlying fault has been corrected.

For example, acknowledging a low-air-pressure alarm does not restore the air supply. The physical condition must still be investigated and resolved.

Detailed alarm design and alarm-management practices are important subjects in their own right. Here, the focus is on understanding alarms as a supervisory function.

9. Supervisory commands and setpoints

The supervisory level can allow an operator to issue commands or change selected operating parameters.

Examples include:

  • Requesting a conveyor start.
  • Requesting a machine stop.
  • Selecting an operating mode where permitted.
  • Changing a temperature or pressure setpoint.
  • Selecting a production recipe.
  • Requesting a reset.
  • Enabling or disabling a function when authorized and permitted by the control design.

The supervisory application normally communicates the request to the controller. The controller evaluates the applicable conditions and determines whether and how to execute it.

Example: Starting a conveyor from SCADA

  1. The operator selects the conveyor start command.
  2. The supervisory application sends the command through the configured communication path.
  3. The PLC receives the request.
  4. The PLC evaluates the machine's operating conditions.
  5. If the required conditions are satisfied, the PLC commands the drive or output.
  6. Feedback indicates whether the conveyor actually started.
  7. SCADA displays the resulting status.

A start request and a running indication represent different information.

This distinction becomes particularly important when communication fails, a drive trips, or the controller refuses the requested operation because a required condition is missing.

Supervisory commands must not replace properly designed machine control or safety functions. Safety-related responses must be implemented in appropriate safety-related systems, not depend solely on the SCADA screen, ordinary network communication, or an operator clicking a button.

10. What happens when SCADA loses communication?

A supervisory application may lose communication with a PLC because of a network fault, failed device, communication-driver problem, controller issue, or other failure.

Possible consequences include:

  • Displayed values becoming unavailable or stale.
  • New commands failing to reach the controller.
  • Alarms and events from the disconnected device no longer updating.
  • Historical data gaps.
  • Loss of supervisory visibility for the affected equipment.

The effect on the physical machine depends on its control architecture and failure-handling design.

A properly designed controller should generally continue its required local control functions when supervisory communication is lost, provided the controller, I/O, and other required components remain healthy and the design permits it. This is not a universal guarantee: some equipment may intentionally stop or change behaviour when communication is lost.

Example

A robotic welding station is operating normally. The SCADA server loses its connection to the PLC.

  • The SCADA display may show the station's data quality as bad.
  • The operator may no longer be able to send supervisory commands.
  • The PLC may continue its configured local control logic.
  • A robot or other device may continue or stop according to the actual control and communication design.
  • The cause of the communication loss must be investigated separately from the physical state of the machine.

Never assume that a green graphic means the equipment is healthy, or that a disconnected SCADA screen means the PLC has stopped running.

11. Supervisory communication and industrial networks

The supervisory level needs a reliable way to exchange data with controllers and other systems.

Common technologies include:

Technology Typical role
EtherNet/IP Industrial communication, particularly in Rockwell Automation environments
PROFINET Industrial Ethernet communication, widely used in Siemens environments
Modbus TCP Industrial data exchange over Ethernet
OPC UA Structured industrial data exchange between compatible systems
Vendor-specific drivers Communication with supported controllers or devices
MQTT Publish/subscribe messaging often used for telemetry and integration

These technologies are not interchangeable in every application. Device support, protocol implementation, security configuration, network design, and performance requirements determine which is appropriate.

For example, SCADA may communicate with an Allen-Bradley PLC through EtherNet/IP or a supported gateway. Another system may use OPC UA to exchange structured data between automation applications.

Communication must also be designed with appropriate access control, network segmentation, and security measures. Supervisory systems are part of the operational technology environment, where an unauthorized command or a prolonged loss of visibility can have physical consequences.

12. Supervisory level versus MES, ERP, and Industry 4.0

The supervisory level often connects to systems above it, but those systems serve different purposes.

System Primary purpose Example
HMI Local human-machine interaction Operate and monitor one machine
SCADA Supervisory monitoring and data acquisition Monitor a production line or plant area
Historian Preserve and retrieve time-series process data Review motor current before a trip
MES Manage and track manufacturing execution Track production orders and work-in-process
ERP Manage business resources and transactions SAP material management and production planning
Analytics platform Analyse data to identify patterns and performance Downtime analysis and trend comparison

The boundaries vary by implementation. Modern platforms can combine some functions, and data may flow between systems in several directions.

A typical information path is:

Field Devices
      ↓
PLC / Control System
      ↓
SCADA and HMI
      ↓
Historian / Operational Database
      ↓
MES / Analytics / Reporting
      ↓
Business Systems and Management Decisions

Commands and requirements can also flow downward where the architecture permits them.

The distinction is important: SCADA primarily supervises the physical process, MES manages manufacturing execution, and ERP manages broader business resources and transactions.

13. Industrial example: Supervising an automotive robotic line

Imagine a production line with several robotic stations, conveyors, fixtures, and welding equipment.

The control system at each station handles the local equipment logic. The supervisory system presents information from the different stations in one place.

An operator or production engineer might use the supervisory system to:

  • See which stations are running, stopped, or faulted.
  • Identify where production has stopped.
  • Monitor part counts and selected cycle-time information.
  • View current alarms and recent events.
  • Review trends for relevant equipment values.
  • Identify communication failures.
  • Generate a shift report.
  • Request permitted operating actions.

A maintenance engineer might use the same system to identify when a fault occurred, compare the machine's state before and after the fault, and decide which controller, drive, field device, or mechanical component requires investigation.

The supervisory system improves visibility, but it does not automatically identify the root cause of every failure. Good diagnosis still requires understanding the actual control logic and physical equipment.

14. Practical troubleshooting of the supervisory level

Symptom Possible causes Initial checks
HMI screen is blank or unavailable Application, panel, power, or computer issue Check device power, application status, and system diagnostics
Tag value does not update Communication failure, stale data, wrong address Check tag quality, timestamp, connection status, and mapping
SCADA shows the wrong machine status Incorrect tag mapping or logic Compare the displayed value with the actual PLC tag
Alarm does not appear Alarm condition, configuration, suppression, or communication issue Verify the source condition and alarm configuration
Historical trend has gaps Historian service, storage, configuration, or communication issue Check acquisition status, logging configuration, and storage
Operator command does not work Command path, authorization, controller logic, or operating condition Trace the request through SCADA and the controller
SCADA is slow Excessive load, network delays, application performance, or database issues Check communication performance, server resources, and data-processing load
Several devices become unavailable together Shared network, gateway, server, or communication-path failure Check common infrastructure before investigating each device separately

A useful troubleshooting sequence

When a displayed value or operator command is wrong, trace the complete information path.

Physical Condition
      ↓
Sensor / Field Signal
      ↓
PLC Tag and Control Logic
      ↓
Communication Path
      ↓
SCADA Tag and Data Quality
      ↓
HMI Display or Operator Command

For a display problem, compare the real equipment condition with the PLC value and then the SCADA value. This helps isolate whether the problem is at the field device, controller, communication layer, tag configuration, or display.

For a command problem, trace in the opposite direction: operator action, SCADA command, communication, controller evaluation, output action, and physical feedback.

15. Common misconceptions

  • “SCADA controls everything directly.” SCADA can issue supervisory commands, but the controller generally executes the machine's control logic.
  • “HMI and SCADA mean exactly the same thing.” An HMI is the interface; SCADA describes a broader supervisory and data-acquisition system.
  • “A displayed value is always current.” Values can be stale or invalid. Data quality and timestamps matter.
  • “Acknowledging an alarm fixes the problem.” Acknowledgment records the operator's response to the notification; it does not necessarily correct the underlying condition.
  • “A historian is just another name for a PLC.” A historian stores and retrieves historical data; a PLC executes control logic.
  • “If SCADA goes offline, the machine must stop.” The result depends on the control architecture and failure-handling design.
  • “More screens mean better supervision.” Clear, accurate, relevant information is more useful than a wall of decorative gauges.

16. Interview questions and answers

Q1. What is the supervisory level in industrial automation?

It is the layer that collects and presents operational information, supports operator interaction, manages supervisory functions, and often records alarms, events, and historical data.

Q2. What does SCADA stand for?

Supervisory Control and Data Acquisition.

Q3. What is the difference between HMI and SCADA?

An HMI provides the human-machine interface. SCADA typically provides a broader system for supervisory monitoring, data acquisition, communication, alarms, and historical records.

Q4. What is a tag in SCADA?

A tag is a named data point representing a value, state, command, or other item used by the supervisory application.

Q5. What is a historian?

A historian is a system designed to store and retrieve historical process data, particularly time-series measurements and equipment states.

Q6. What is the difference between an alarm and an event?

An alarm indicates an abnormal condition requiring attention or action. An event records a significant occurrence or state change and may not require immediate intervention.

Q7. What happens when SCADA loses communication with a PLC?

The supervisory system may lose current data and the ability to send commands. Whether the machine continues operating depends on the controller and system design.

Q8. Can SCADA replace a PLC?

Not in the usual architecture. SCADA provides supervisory functions, while the PLC executes the configured control logic. Some products combine capabilities, but the responsibilities and timing requirements must still be addressed.

Q9. Why is data quality important in SCADA?

It helps distinguish valid, current data from stale, uncertain, or unavailable values, reducing the risk of decisions based on misleading displays.

Q10. How does SCADA help maintenance?

It provides visibility into equipment states, alarms, trends, and historical events, helping engineers narrow down when and where a problem occurred.

17. Final mental model

Remember the supervisory level as the visibility and operator-interaction layer.

  • Field level: Measures physical conditions and performs actions.
  • Control level: Executes logic and control algorithms.
  • Supervisory level: Displays process information, supports authorized commands, presents alarms, and records operational history.
  • Historian and analytics: Help engineers understand past behaviour and identify patterns.
  • MES and ERP: Support manufacturing execution and broader business operations.

For maintenance, the essential principle is that the supervisory system shows what the automation system reports. It is not automatically the source of truth for every physical condition. Compare its displayed values with controller data, communication quality, and the actual equipment before deciding where the fault lies.
