1. Definition

Migration strategy is the planned method used to move an existing industrial asset, control system, software platform, or automation architecture to a supported, maintainable, and technically suitable solution while controlling production downtime, safety risks, cost, and functional changes.

Migration may involve replacing a single obsolete component or transforming an entire machine-control architecture.

Examples include:

  • Replacing an obsolete PLC CPU with a supported controller.
  • Migrating a legacy HMI to a modern panel.
  • Replacing a discontinued VFD while retaining the motor.
  • Moving a CNC controller to a supported platform.
  • Migrating robot-controller hardware and preserving validated programs.
  • Replacing an unsupported industrial PC and operating system.
  • Converting a proprietary communication interface to a supported industrial protocol.
  • Moving historical test-bench data to a maintainable database and reporting platform.

The objective is not simply to install newer hardware. The objective is to preserve or improve required machine functions, safety, quality, maintainability, and recovery capability.

2. Why Migration Is Necessary

Migration becomes necessary when the existing system can no longer meet operational, technical, or business requirements at an acceptable level of risk.

Common triggers include:

  • Manufacturer end-of-life announcements.
  • Unavailable spare parts or repair services.
  • Repeated hardware failures.
  • Unsupported firmware or engineering software.
  • Cybersecurity vulnerabilities.
  • Incompatibility with modern networks or databases.
  • Poor diagnostics and limited maintainability.
  • Production-capacity changes.
  • Quality-system or regulatory requirements.
  • Excessive maintenance cost.
  • Dependency on one specialist or unavailable programming tools.

An old system does not automatically require immediate replacement. A stable, supportable system may remain serviceable for years. Migration priority should be determined by evidence, risk, and the cost of continued operation.

3. Migration Versus Related Activities

Activity Meaning Example
Repair Restores a failed component to service Repairing a VFD control board
Replacement Exchanges a component for another unit Installing an identical PLC CPU
Retrofit Modifies part of an existing machine Replacing an HMI while retaining the PLC
Migration Moves an application or system to a different supported platform Converting a legacy PLC application to a new controller
Modernization Improves technology, capability, or maintainability Adding diagnostics and standardized communications
Re-engineering Redesigns the system or its operating method Redesigning a test bench control architecture
Decommissioning Removes equipment or a system from service Retiring an obsolete machine controller

These activities can overlap. A migration project may include hardware replacement, software conversion, retrofit work, and modernization.

4. Major Migration Strategies

4.1 Like-for-Like Replacement

Replace failed or obsolete hardware with the same model or a compatible unit of the same product family.

Suitable when:

  • The existing architecture is acceptable.
  • Compatible hardware is available.
  • The application is stable.
  • A larger migration cannot yet be justified.

Advantages:

  • Lower engineering effort.
  • Reduced program-conversion risk.
  • Familiar maintenance procedures.
  • Potentially shorter commissioning time.

Limitations:

  • Does not eliminate the underlying obsolescence problem.
  • Compatible stock may remain scarce.
  • The replacement may have limited remaining support life.

4.2 Component-Level Migration

Replace a specific obsolete component while retaining most of the existing system.

Examples include replacing a communication card, HMI panel, network switch, or drive.

Advantages:

  • Smaller project scope.
  • Lower initial cost than full-system replacement.
  • Limited disturbance to unrelated machine functions.

Risks:

  • Interface incompatibility.
  • Parameter or driver differences.
  • New failure points at modified interfaces.
  • Hidden dependencies on the original component.

4.3 Subsystem Migration

Replace a logically connected part of the system, such as the complete PLC rack, HMI subsystem, motion-control system, or industrial-PC platform.

This strategy allows engineering to address several related obsolescence risks together.

For example, migrating a PLC rack may also require replacement of remote I/O, communication modules, power supplies, engineering software, and network configuration.

4.4 Full-System Migration

Replace the main control architecture or the complete machine-control platform.

Suitable when:

  • Multiple major components are obsolete.
  • The existing architecture is difficult to maintain.
  • Support and spare availability are poor.
  • Cybersecurity or functional risks are unacceptable.
  • Component-level migration would create excessive integration complexity.

This strategy offers the greatest opportunity for improvement but normally requires the most engineering, validation, planning, and downtime.

4.5 Parallel Operation

The old and new systems operate simultaneously for a controlled period, where the architecture permits it.

Potential uses include comparing measurements, validating calculations, or checking data processing.

Parallel operation requires particular care when outputs control real machinery. Two controllers must not independently command the same actuator unless the design explicitly supports that arrangement.

4.6 Phased Migration

Migrate equipment in planned stages, such as one machine, one line, or one production area at a time.

Benefits include:

  • Limited simultaneous exposure.
  • Reuse of lessons from earlier installations.
  • Smaller commissioning batches.
  • Easier management of training and spare requirements.

The main challenge is maintaining consistent interfaces and support arrangements while different generations of equipment coexist.

4.7 Big-Bang Migration

Replace the complete defined scope during a single shutdown or cutover window.

This may be appropriate when interfaces cannot practically coexist or when a common shutdown is available.

It requires thorough preparation because a major unresolved issue can prevent the entire production area from restarting.

5. Selecting the Appropriate Strategy

Condition Potential strategy Key consideration
Failed component, supported identical replacement available Like-for-like replacement Verify exact revision and compatibility
One obsolete HMI, supported PLC retained Component-level migration Check tags, drivers, alarms, and recipes
Obsolete PLC rack and remote I/O Subsystem migration Validate I/O mapping and communication
Multiple obsolete control subsystems Full-system migration Assess total lifecycle cost and downtime
Several similar machines Phased migration Standardize the target architecture
Strong need for controlled comparison Parallel operation Prevent conflicting control authority
Interfaces cannot coexist and shutdown is fixed Big-bang migration Prepare comprehensive cutover and rollback plans

Strategy selection should consider production criticality, technical complexity, required shutdown time, cybersecurity, safety, lifecycle cost, and available engineering skills.

6. Migration Assessment

Before selecting a strategy, establish the current system's condition and dependencies.

6.1 Hardware Assessment

Record:

  • Manufacturer, model, revision, and serial number.
  • Power-supply and electrical ratings.
  • PLC CPUs, I/O modules, and communication interfaces.
  • Drives, motors, encoders, and feedback devices.
  • Network switches, gateways, and remote I/O.
  • Safety controllers, relays, scanners, and interlocks.
  • HMI panels, industrial PCs, and storage devices.
  • Mechanical mounting, dimensions, connectors, and wiring.
  • Spare availability, repair options, and lead times.

6.2 Software Assessment

Record:

  • PLC project and firmware version.
  • HMI development and runtime versions.
  • CNC or robot programs and parameters.
  • Drive configuration files.
  • Engineering software versions and licenses.
  • Operating systems, drivers, and runtime dependencies.
  • Communication protocols and network settings.
  • Database, reporting, and historian dependencies.
  • Backup and restoration procedures.

6.3 Functional Assessment

Document the functions the existing system must continue to perform:

  • Automatic and manual operating modes.
  • Start/stop sequences and interlocks.
  • Alarm generation and recovery.
  • Motion profiles and positioning.
  • Process measurements and acceptance limits.
  • Quality-data collection.
  • Safety functions.
  • Operator permissions and recipe handling.
  • Fault recovery and restart behavior.

A migration should begin with an understanding of the machine's actual behavior, not merely a copy of its hardware inventory.

8. Migration Risk Assessment

Evaluate both the risk of retaining the legacy system and the risk introduced by migration.

Risk category Example Typical control
Production Cutover exceeds shutdown window Detailed schedule and readiness review
Electrical Different voltage or current requirements Engineering verification
Functional Converted logic changes sequence behavior Functional testing and comparison
Communication New device uses different protocol or addressing Interface testing
Safety Existing safety behavior is not preserved Formal safety assessment and validation
Quality Measurement results change Correlation study and acceptance criteria
Cybersecurity Unsupported legacy endpoint remains exposed Segmentation and controlled access
Data Historical records or tags are lost Verified backup and data migration checks
Skills Maintenance team cannot support new platform Training and controlled documentation
Supply chain New platform has long delivery time Procurement planning and approved contingencies

A risk register should include the hazard or failure scenario, cause, consequence, existing controls, required action, owner, due date, and residual risk.

9. PLC Migration

PLC migration is one of the most technically demanding industrial migration activities because it affects both software behavior and physical machine interfaces.

9.1 Preparation

  • Obtain the original project and a current controller backup.
  • Confirm whether the available source matches the running machine.
  • Record CPU, firmware, I/O modules, network configuration, and installed options.
  • Export or document tag names, addresses, alarms, and interlocks.
  • Identify proprietary instructions, libraries, and unsupported functions.
  • Record online edits and undocumented changes.
  • Preserve the original system's recovery method.

9.2 Conversion and Engineering

Review:

  • Instruction-set differences.
  • Data types and memory organization.
  • Timer and counter behavior.
  • Retentive data.
  • Interrupts and task scheduling.
  • Analog scaling and filtering.
  • Communication drivers.
  • Motion-control instructions.
  • Safety-related logic.
  • HMI tag mapping.
  • Fault handling and startup behavior.

Automatic conversion tools can reduce repetitive work, but they do not prove that the converted program behaves identically.

9.3 Validation

Verify every relevant I/O point, operating mode, interlock, alarm, and sequence step. Test failure and recovery behavior as well as normal operation.

Where possible, perform offline simulation or controlled test-bench validation before installing the replacement in production.

10. HMI and SCADA Migration

HMI migration involves more than copying screens.

Check:

  • Tag mapping and data types.
  • Communication drivers.
  • Alarm conditions, priorities, and acknowledgments.
  • Trend sampling and historical data.
  • Recipes and parameter limits.
  • User accounts and permissions.
  • Navigation and operator workflow.
  • Screen resolution and touch response.
  • Runtime licenses and software dependencies.
  • Data logging and database connectivity.

Acceptance testing should include abnormal conditions. For example, the HMI must communicate a lost PLC connection clearly rather than display stale values as if they were current.

11. VFD and Servo Migration

Drive migration can alter the dynamic behavior of a machine even when the new unit has similar nameplate ratings.

Check:

  • Input supply and motor ratings.
  • Current, overload, and duty requirements.
  • Control mode and switching frequency.
  • Acceleration and deceleration behavior.
  • Braking and regenerative-energy arrangements.
  • Encoder type, resolution, and feedback interface.
  • Fieldbus protocol and command structure.
  • Digital and analog I/O.
  • Safe Torque Off (STO) and other safety functions.
  • Parameter backup and restoration.

Commissioning should verify speed, torque, positioning, stopping behavior, fault recovery, and relevant machine-quality results.

12. CNC and Robot Migration

CNC and robot migration must preserve application-specific data and validated machine behavior.

For CNC systems, consider:

  • Part programs and macro programs.
  • Machine parameters and compensation tables.
  • Tool and work offsets.
  • Servo and spindle configuration.
  • PLC interface logic.
  • Tool changers and auxiliary functions.
  • Machine-builder software and options.

For robot systems, consider:

  • Robot programs and subroutines.
  • Mastering and calibration data.
  • Tool and work frames.
  • Payload and motion settings.
  • I/O mapping and fieldbus configuration.
  • Safety zones, interlocks, and enabling devices.
  • Peripheral equipment and cell communication.

Restoring a program does not automatically restore the machine's calibrated geometry or validate its safety functions.

13. Safety During Migration

Safety-related changes require appropriate engineering review and validation.

Key controls include:

  • Follow the site's approved isolation and lockout/tagout procedures.
  • Identify stored electrical, pneumatic, hydraulic, and mechanical energy.
  • Prevent unexpected machine movement.
  • Preserve safety-related functions and required performance.
  • Validate emergency stops, guard interlocks, scanners, enabling devices, and safe motion functions as applicable.
  • Control bypasses and temporary modifications.
  • Document test results and authorization to return to service.

A standard controller or ordinary I/O module must not be treated as an equivalent replacement for a safety-rated component unless the complete design has been properly assessed and approved.

14. Cybersecurity and Network Migration

Migration can reduce legacy-system exposure, but a newer device does not automatically make an architecture secure.

Assess:

  • Network segmentation and traffic pathways.
  • Remote-access methods and authorization.
  • User accounts and credential management.
  • Firmware and software update arrangements.
  • Supported protocols and encryption capabilities.
  • Engineering-workstation security.
  • Backup integrity and recovery procedures.
  • Logging and monitoring.
  • Vendor access and maintenance responsibilities.

Industrial control systems may require specific communication behavior and availability. Security changes should therefore be tested against machine requirements rather than applied blindly.

15. Migration Testing Strategy

Testing should be defined before the cutover, with documented acceptance criteria.

15.1 Factory Acceptance Testing

Factory Acceptance Testing (FAT) evaluates the designed system or replacement before installation, where practical.

Possible checks include:

  • Program compilation and configuration review.
  • I/O simulation.
  • Sequence and interlock testing.
  • Alarm handling.
  • Communication interfaces.
  • Data collection.
  • Backup and restoration.
  • Defined abnormal-condition tests.

15.2 Site Acceptance Testing

Site Acceptance Testing (SAT) verifies the installed system under actual site conditions.

Possible checks include:

  • Field wiring and signal verification.
  • Device communications.
  • Machine sequences.
  • Safety functions.
  • Production interfaces.
  • Quality measurements.
  • Alarm and recovery behavior.
  • Operator access and reporting.

15.3 Production Validation

After technical commissioning, validate the process using approved production or test criteria. This may include comparison against reference measurements, capability requirements, and quality acceptance limits.

Testing scope should be proportionate to the system's criticality and the change being introduced.

16. Cutover and Rollback Planning

Cutover is the controlled transition from the old system to the new system.

Before cutover, confirm:

  • Approved scope and method statement.
  • Verified backups and restoration procedures.
  • Material, tools, software, and licenses.
  • Approved wiring and network drawings.
  • Required technicians and specialists.
  • Isolation and safety arrangements.
  • Test procedures and acceptance criteria.
  • Shutdown and restart sequence.
  • Rollback decision criteria.
  • Production and quality authorization.

Rollback must be technically feasible, not merely a sentence in a project plan. If the original controller, software, wiring, or licenses have been irreversibly changed, returning to the previous state may be impossible.

17. Migration Schedule and Downtime Estimation

Break the project into measurable activities:

  1. Survey and documentation.
  2. Engineering and design.
  3. Procurement and preparation.
  4. Offline development.
  5. FAT or bench testing.
  6. Shutdown and isolation.
  7. Installation and wiring.
  8. Configuration and commissioning.
  9. Safety and process validation.
  10. Production release and closeout.

A simple estimate is:

\[ T\_{\text{total}}=\sum\_{i=1}^{n}T_i \]

This assumes activities occur sequentially. If activities can be performed in parallel, total elapsed time depends on the critical path rather than the sum of every task duration.

Include contingency for unexpected wiring differences, missing documentation, communication problems, and failed acceptance tests.

18. Migration Cost and Business Case

The comparison should include both direct and indirect costs.

Cost category Examples
Hardware Controllers, modules, panels, drives, cables
Software Engineering tools, licenses, runtime software
Engineering Design, programming, conversion, testing
Installation Electrical work, mounting, wiring, network changes
Downtime Lost production during shutdown and restart
Validation Safety, quality, performance, and acceptance testing
Training Maintenance and operator training
Inventory Transitional spares and support stock
Risk reduction Reduced exposure to obsolete parts and unsupported systems
Lifecycle cost Future maintenance, support, and replacement requirements

A business case should compare the proposed migration with continued operation, repair, and retrofit. Include expected downtime losses and residual inventory, not just the price of the new PLC.

19. Documentation and Change Management

Migration is incomplete until the installed configuration and its supporting records are updated.

Update:

  • Electrical and control drawings.
  • PLC, HMI, CNC, and robot programs.
  • Firmware and software versions.
  • I/O lists and tag databases.
  • Network architecture and IP records.
  • BOM and installed-base mapping.
  • Spare-part and successor mapping.
  • PM instructions and troubleshooting guides.
  • Backup and recovery procedures.
  • Risk assessments and safety validation records.
  • Training records and change approvals.
  • SAP material records and maintenance documentation, where applicable.

Apply version control and record the final approved configuration. Keep the original backups and migration evidence according to site policy.

20. Practical Case Study: Obsolete PLC on a Test Bench

Situation

A production test bench uses an obsolete PLC platform. Communication modules are difficult to source, and the manufacturer has announced the end of support. The machine records quality results in a database.

Assessment

  • Map the PLC, I/O, HMI, drives, test application, and database dependencies.
  • Verify the current program and preserve recoverable backups.
  • Identify the successor PLC and required I/O changes.
  • Assess software conversion and communication requirements.
  • Confirm that the test sequence and measurement processing can be preserved.
  • Evaluate migration downtime and temporary spare requirements.
  • Define FAT, SAT, safety, and process-validation criteria.
  • Prepare a rollback plan and a production-release checklist.

Selected strategy

A planned subsystem migration may be appropriate if the obsolete PLC and its communication modules are the primary lifecycle risks and the rest of the test bench can be retained safely.

Expected result

The machine gains a supported control platform while retaining validated process functions, traceability, and maintainable documentation.

21. Common Migration Mistakes

  • Starting without a complete installed-base and dependency survey.
  • Assuming a converted PLC program is functionally equivalent.
  • Ignoring firmware, licenses, drivers, and engineering-tool versions.
  • Replacing a controller without checking HMI and database interfaces.
  • Failing to preserve calibration and machine-specific parameters.
  • Treating safety testing as an ordinary functional test.
  • Underestimating shutdown and commissioning time.
  • Defining rollback without confirming it is feasible.
  • Leaving temporary bypasses or undocumented changes in place.
  • Failing to update drawings, backups, BOMs, and spare records.
  • Releasing the machine without verifying quality and process performance.

22. Interview Questions and Answers

Q1. What is migration in industrial automation?

Migration is the controlled transition of equipment, software, or an automation system to a supported platform while preserving or improving required functionality, safety, quality, and maintainability.

Q2. What factors determine the migration strategy?

Criticality, lifecycle status, compatibility, downtime, technical complexity, cybersecurity, safety, cost, support availability, and engineering resources.

Q3. What is the difference between retrofit and migration?

A retrofit modifies or replaces part of an existing system. Migration specifically involves transitioning an asset or application to another supported platform. A retrofit may form part of a migration.

Q4. Why is dependency mapping important?

It identifies interfaces and downstream functions that may be affected, preventing hidden failures in communication, data collection, safety, or machine sequencing.

Q5. Why is backup verification necessary?

A backup that cannot be restored may be useless during recovery. Restoration should be tested using an approved procedure and appropriate equipment.

Q6. What is the purpose of FAT and SAT?

FAT checks the system before installation where practical. SAT verifies the installed system under actual site conditions.

Q7. What is rollback planning?

It defines the conditions and procedures for returning to the previous operating configuration if the migration fails acceptance criteria or causes unacceptable risk.

Q8. Why can a new VFD affect machine quality?

Differences in control behavior, acceleration, deceleration, torque response, feedback, and parameter settings can change the machine's motion or process performance.

Q9. When is full-system migration justified?

When several critical subsystems are obsolete, component-level changes are too risky or costly, or the existing architecture cannot meet required support, safety, cybersecurity, or operational needs.

Q10. When is migration complete?

When the new system meets approved acceptance criteria, safety and process validation are complete, production release is authorized, recovery arrangements are verified, and the required documentation is updated.

23. Practical Competency Checklist

  • Distinguish migration, replacement, retrofit, and modernization.
  • Assess lifecycle status and installed-system condition.
  • Map hardware, software, network, and process dependencies.
  • Select an appropriate migration strategy.
  • Preserve and verify programs, parameters, and backups.
  • Assess successor hardware and software compatibility.
  • Prepare a risk register and cost estimate.
  • Define FAT, SAT, and production acceptance criteria.
  • Plan isolation, cutover, commissioning, and rollback.
  • Validate safety functions and quality performance.
  • Update drawings, asset records, BOMs, and spare mappings.
  • Train maintenance personnel and confirm recovery readiness.
