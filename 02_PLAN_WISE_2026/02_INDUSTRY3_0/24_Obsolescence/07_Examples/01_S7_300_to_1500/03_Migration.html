1. Purpose and Scope

A PLC migration is complete only when the replacement system has been engineered, tested, commissioned, documented, and released for production. Converting the program and downloading it to the new CPU are intermediate activities, not proof of a successful migration.

For an S7-300 to S7-1500 migration, the project must address three major stages:

  • Convert: Prepare the target hardware configuration, migrate the engineering project, resolve incompatibilities, and compile the application.
  • Test: Verify hardware, I/O, program behavior, communications, timing, fault handling, and safety functions.
  • Cut over: Transfer production control to the new system under an approved plan, verify operation, and retain a practical rollback path.

The objective is to minimize production downtime while protecting personnel, equipment, product quality, and process data.

2. Migration Strategy

2.1 Full replacement versus staged migration

Two common approaches are a full-system replacement and a staged migration.

Factor Full replacement Staged migration
Scope Replaces the controller system during one planned outage Replaces subsystems in planned stages
Downtime Can require a longer single outage May distribute downtime across multiple outages
Engineering Entire target system is prepared before cutover Requires interface planning between old and new subsystems
Temporary arrangements Usually limited to the outage and recovery plan May require temporary gateways or retained legacy equipment
Testing Broad integrated testing before and during commissioning Testing occurs at subsystem and integration levels
Risk Concentrated around the main cutover Distributed across multiple changes, with added interface complexity
Best fit Well-defined systems with a controlled shutdown window Large systems where phased replacement is practical

A staged migration is not automatically safer. Temporary interfaces, mixed hardware generations, and partial cutovers can create their own failure modes. The choice must be based on the plant's process, available downtime, technical constraints, and risk assessment.

2.2 Define the acceptance criteria first

Before converting the project, define what a successful migration means.

Typical acceptance criteria include:

  • Every required field signal is correctly mapped.
  • All intended machine sequences execute correctly.
  • Required cycle time and response time are achieved.
  • HMI, drives, remote I/O, and external systems communicate correctly.
  • Alarms and fault recovery operate as intended.
  • Retentive values and required recipes are preserved.
  • Safety functions are validated under the approved procedure.
  • The final project, drawings, and maintenance records are complete.
  • Production and engineering representatives approve the release.

Without acceptance criteria, commissioning tends to become an endless sequence of “it seems to work” demonstrations, which is not a particularly rigorous engineering method.

3. Phase 1: Pre-Migration Assessment

3.1 Build the installed-base inventory

Create a complete inventory of the original PLC system before changing anything.

Inventory item Required information
CPU Order number, firmware, memory, communication interfaces
Central I/O Module order numbers, channel counts, addresses
Distributed I/O Station names, interface modules, module types
Communication Protocols, device identities, network settings
HMI and SCADA Models, software versions, tags, alarms, external interfaces
Drives and motion Models, communication methods, control and feedback data
Special modules Counting, measurement, serial communication, technology functions
Safety equipment Safety CPU, safety I/O, safety relays, approved safety configuration
Engineering software STEP 7 version, libraries, licences, source files
Panel infrastructure Power supplies, mounting, wiring, network switches, earthing

Record exact order numbers rather than relying on descriptions such as “old Siemens CPU” or “16-channel input card.” Exact identification prevents incorrect successor selection.

3.2 Capture the original behavior

Record how the machine operates before the migration.

Capture:

  • Normal startup and shutdown sequences.
  • Automatic and manual modes.
  • Input/output assignments.
  • Timer presets and sequence timeouts.
  • Analog ranges, scaling, limits, and calibration constants.
  • Communication update requirements.
  • Alarm messages and fault-reset conditions.
  • Retentive data and power-recovery behavior.
  • Cycle time and critical response times.
  • Known intermittent faults and existing limitations.

This baseline distinguishes migration-induced problems from pre-existing issues.

3.3 Identify high-risk dependencies

Pay particular attention to:

  • Absolute DB offsets accessed by an HMI or PC.
  • Legacy communication processors.
  • Protected or unavailable program blocks.
  • Unsupported instructions.
  • Special-purpose modules.
  • Safety-related functions.
  • Third-party libraries.
  • Remote I/O with uncertain target compatibility.
  • External production databases and custom software.

These dependencies should be resolved during engineering, not discovered for the first time during the production outage.

4. Phase 2: Conversion and Engineering Preparation

4.1 Preserve the original project

Maintain separate copies for the original source, the conversion work, and the approved final project.

Recommended structure:

PLC_Migration/
    01_Original_Backup/
    02_Working_Conversion/
    03_Compiled_Project/
    04_Test_Evidence/
    05_Approved_Release/
    06_Rollback_Package/

The directory names are examples. The important principle is to keep the original, working, tested, and released versions distinguishable.

4.2 Convert and resolve incompatibilities

Use the supported Siemens migration route for the actual STEP 7 and TIA Portal versions.

Review and resolve:

  • Unsupported hardware references.
  • CPU and firmware compatibility.
  • Program instructions and block types.
  • Data-block layout and addressing.
  • Retentivity and initialisation.
  • Communication blocks and connections.
  • Library dependencies.
  • HMI and external application references.
  • Technology and safety-related configurations.

Record each significant correction with the reason for the change and the verification performed.

4.3 Compile and inspect

Perform the appropriate hardware and software compilation checks. Review errors and warnings rather than suppressing them without analysis.

For each issue, document:

  • The affected device or program block.
  • The original behavior or purpose.
  • The corrective action.
  • The test used to verify the correction.
  • Any remaining limitation or risk.

A clean compilation is a necessary engineering milestone, but it does not establish correct field wiring, machine timing, or functional behavior.

5. Phase 3: Test Planning

Testing should be planned before the new system is installed. Define the test cases, expected results, acceptance limits, responsible personnel, and required safety precautions.

5.1 Test levels

Test level Main purpose Typical example
Engineering review Check design and project consistency Hardware configuration and block review
Offline verification Detect engineering errors without running the machine Compile, cross-reference, and logic inspection
Hardware inspection Verify the physical installation Rail, terminals, supply, grounding, and wiring
I/O test Confirm field signal mapping Operate a sensor and verify the correct PLC tag
Subsystem test Verify individual functions Clamp control or drive interface
Integration test Verify interactions between subsystems PLC, HMI, drive, robot, and SCADA exchange
Functional test Verify complete machine behavior Full automatic production cycle
Fault test Verify abnormal-condition handling Sensor timeout or communication interruption
Safety validation Demonstrate required safety performance Approved emergency-stop and guard-function tests
Production acceptance Confirm readiness for controlled release Production trial against agreed criteria

5.2 Test traceability

Every critical requirement should map to one or more test cases.

Example:

Requirement Test case Expected result
Clamp must be confirmed before measurement Apply clamp command and verify feedback Measurement sequence starts only after valid confirmation
Pressure must be within limits Test below, within, and above limits Correct acceptance or rejection result
Communication loss must be detected Interrupt the applicable connection under controlled conditions Fault is detected and the defined safe response occurs
Cycle timeout must be detected Prevent the expected sensor transition Timeout alarm appears and the sequence responds correctly
Required values must survive a power interruption Perform the approved power-cycle test Specified retained values are restored correctly

The test procedure must not introduce uncontrolled hazards. Tests involving motion, safety functions, or energized equipment require the applicable risk controls and authorized personnel.

6. Phase 4: Hardware Installation and Verification

Before downloading the migrated program, inspect the new hardware installation.

6.1 Physical inspection

  • Confirm CPU and module order numbers against the approved design.
  • Verify mounting, clearances, ventilation, and cable routing.
  • Check 24 VDC supplies and the required power distribution.
  • Verify protective earth and shield connections.
  • Check terminal assignments against the updated drawings.
  • Verify network cables, connectors, switch ports, and device names.
  • Confirm that disconnected or unused wires are safely terminated.
  • Confirm that safety-related wiring matches the approved design.

6.2 Power-on checks

Energize the system according to the approved commissioning procedure.

Check:

  • CPU startup and operating status.
  • Module status indicators.
  • Hardware diagnostic messages.
  • Network connection status.
  • Unexpected output behavior.
  • Supply voltage and relevant power diagnostics.
  • Correct startup and initialisation behavior.

Outputs must remain in a controlled state until the machine is ready for functional testing. Never assume that a newly downloaded program will keep every output inactive during startup or fault recovery.

7. Phase 5: I/O and Communication Testing

7.1 Input testing

For each input:

  1. Identify the field device and signal tag.
  2. Confirm the terminal and channel against the wiring drawing.
  3. Operate the device under controlled conditions.
  4. Verify that the correct PLC input changes state.
  5. Confirm the corresponding program logic responds correctly.
  6. Record the result and any corrective action.

Test sensors in their real operating conditions where practical. A forced software bit can help isolate logic, but it does not verify the sensor, wiring, input module, or electrical interface.

7.2 Output testing

For each output:

  1. Confirm the output address and physical terminal.
  2. Verify the connected load and its supply.
  3. Test the output using the approved procedure.
  4. Confirm that the intended actuator responds.
  5. Verify feedback and interlocks.
  6. Confirm that output shutdown and fault behavior are correct.

Do not force outputs casually. A forced output can move a cylinder, energize a motor, release a clamp, or create unexpected motion. Use approved isolation, access controls, and test conditions.

7.3 Analog testing

For each analog channel, verify:

  • Signal type and range.
  • Correct polarity and wiring.
  • Engineering-unit scaling.
  • Zero and span behavior.
  • Measurement accuracy within the acceptance limits.
  • Wire-break and out-of-range diagnostics where supported.
  • Correct behavior of limits and alarms.

For a linear 4–20 mA signal representing 0–100 units:

\[ X = \frac{I-4}{20-4}\times100 \]

At 12 mA, the expected value is 50 units. Confirm the actual transmitter range and module configuration before applying this calculation.

7.4 Communication testing

Test each communication relationship individually before testing the complete production sequence.

Verify:

  • Device identity and addressing.
  • Connection establishment.
  • Data types and data values.
  • Read/write direction.
  • Update rate and timeout behavior.
  • Alarm and diagnostic response.
  • Recovery after communication loss.
  • Handling of stale or invalid data.

Include all relevant devices, such as HMI panels, remote I/O, drives, robots, CNC controllers, measurement instruments, SCADA systems, and PC applications.

8. Phase 6: Functional and Regression Testing

8.1 Functional sequence testing

Test every operating mode and critical sequence against the approved requirements.

For a production test bench, this may include:

  1. Power-up and machine initialisation.
  2. Manual control and maintenance mode.
  3. Part-presence and fixture checks.
  4. Clamping and confirmation.
  5. Measurement or test execution.
  6. Result evaluation and pass/fail handling.
  7. Part release and cycle completion.
  8. Fault detection, reset, and recovery.
  9. Shutdown and restart.

The exact sequence depends on the machine. The test must cover actual process behavior rather than only whether the PLC program appears to execute.

8.2 Boundary and abnormal-condition testing

Normal operation is only one part of the test plan. Check how the system behaves when expected conditions do not occur.

Examples:

  • Sensor does not switch.
  • Two interlocks disagree.
  • Analog value is below or above its allowed range.
  • Drive reports a fault.
  • Remote I/O communication is lost.
  • HMI or external PC communication is interrupted.
  • CPU restarts during an approved test condition.
  • A timeout expires.
  • A required value is missing or invalid.

For each condition, verify the expected alarm, sequence response, output state, operator message, and recovery procedure.

8.3 Timing verification

Record timing-critical behavior before and after migration.

Measurement Purpose
PLC scan time Evaluate program execution load
Input-to-output response Confirm control response
Sequence duration Confirm production cycle requirements
Communication update time Verify data freshness and coordination
Timeout behavior Confirm fault detection occurs within the required interval
Measurement trigger timing Confirm acquisition occurs at the intended point in the process

A faster CPU does not guarantee identical timing. Differences in execution, I/O updates, communication scheduling, and program structure can affect the process.

8.4 Regression test evidence

Record the expected result, actual result, pass/fail status, date, responsible person, and any corrective action for each test.

A failed test must be resolved and repeated. If the correction affects another subsystem, repeat the relevant integration or regression tests as well.

9. Phase 7: Safety Validation

Safety-related migration must be treated separately from ordinary PLC functional testing.

The replacement system must preserve the required safety functions, not merely reproduce the original sequence.

Check:

  • Emergency-stop functions.
  • Guard-door interlocks.
  • Enabling devices and operating modes.
  • Safe motion or drive-related safety functions, where applicable.
  • Fail-safe CPU and I/O configuration.
  • Safety communication.
  • Fault detection and safe-state behavior.
  • Reset and restart conditions.
  • Required documentation and validation evidence.

Do not bypass safety devices or rely on standard PLC logic as a substitute for an approved safety function. Any changes to safety hardware, software, or architecture require the applicable risk assessment, validation process, and authorized approval.

10. Cutover Planning

Cutover is the controlled transfer from the old PLC system to the new system. It should be treated as a planned production event with defined responsibilities and decision points.

10.1 Pre-cutover checklist

  • Target hardware and software are approved.
  • Required test cases have passed.
  • The final project is compiled and backed up.
  • The original project and rollback package are available.
  • Updated drawings and I/O lists are available.
  • Required replacement parts and tools are available.
  • Operators and maintenance personnel are informed.
  • Production, quality, engineering, and safety responsibilities are assigned.
  • The shutdown window and expected duration are agreed.
  • Acceptance criteria and abort conditions are defined.
  • Safety precautions and isolation requirements are approved.

10.2 Cutover sequence

Approve migration and shutdown window
    ↓
Stop production using the approved procedure
    ↓
Isolate equipment and establish safe working conditions
    ↓
Record final machine state and required process data
    ↓
Replace hardware and verify wiring
    ↓
Load the approved target project
    ↓
Check CPU, module and network diagnostics
    ↓
Verify I/O and critical communications
    ↓
Perform approved functional and safety checks
    ↓
Run controlled production trials
    ↓
Accept the system or initiate the rollback plan

The sequence must be adapted to the machine's actual design and site procedures.

10.3 Manage the cutover window

Prepare a time plan for each major task, including:

  • Shutdown and isolation.
  • Hardware removal and installation.
  • Wiring and inspection.
  • Project download and startup.
  • I/O and communication checks.
  • Critical functional tests.
  • Production trial.
  • Acceptance decision.

Assign one person to coordinate the overall cutover and ensure that task completion and unresolved issues are recorded. If a critical acceptance criterion fails, follow the predefined decision process rather than extending the outage indefinitely without control.

11. Rollback Strategy

A rollback plan defines how the plant can return to the previous operating arrangement if the new system cannot be accepted.

11.1 Rollback preparation

Preserve:

  • Original PLC hardware and its identification.
  • Verified original project and required software.
  • Original network configuration.
  • Existing wiring records and terminal labels.
  • Required machine parameters and retained data.
  • Original HMI and external-system configurations.
  • Tools, spare parts, and personnel required for restoration.

The old hardware should be retained and protected until the new system has completed the required acceptance period, subject to site policy and equipment condition.

11.2 Define rollback triggers

Possible triggers include:

  • Critical functional tests fail.
  • Required safety validation cannot be completed.
  • Unresolved communication problems prevent correct operation.
  • The machine cannot meet essential timing or quality requirements.
  • A serious hardware fault occurs.
  • The cutover exceeds the approved recovery limit.

11.3 Rollback is not always a simple swap

The new system may require different wiring, terminals, network settings, or external-device configurations. Reverting to the old CPU may therefore require restoring the original physical arrangement and configuration.

Do not assume that the original PLC can be reconnected immediately after the new hardware has been installed. The rollback method must be engineered and, where practical, rehearsed before cutover.

12. Production Acceptance and Handover

After the machine passes the agreed tests, the migration must be formally handed over to operations and maintenance.

12.1 Handover package

  • Final PLC project and version information.
  • Final hardware configuration and module list.
  • Updated electrical drawings and I/O mapping.
  • Network configuration and device inventory.
  • Test results and outstanding-issue register.
  • Safety validation records where applicable.
  • CPU and module firmware information.
  • HMI, drive, and external application project versions.
  • Recovery and backup procedures.
  • Updated troubleshooting and fault-diagnosis instructions.
  • Spare-parts and successor-component records.
  • Operator and maintenance training records.

12.2 Initial monitoring period

During the initial production period, monitor:

  • Unexpected CPU or module diagnostics.
  • Communication interruptions.
  • Repeat alarms.
  • Cycle time and machine availability.
  • Product quality and test-result consistency.
  • Operator-reported behavior.
  • Data collection and traceability.
  • Any change in startup or recovery behavior.

Investigate deviations against the original baseline and approved acceptance criteria. Do not dismiss a recurring issue simply because production continues.

13. Migration Performance Metrics

Use measurable indicators to evaluate the migration.

Metric Calculation or evaluation
Cutover duration Actual time from approved shutdown start to accepted production release
Test pass rate Passed tests divided by total executed tests, multiplied by 100
Critical defect count Number of unresolved defects classified as critical
Repeat-failure rate Frequency of repeated migration-related faults over a defined period
Availability Available operating time divided by scheduled operating time, multiplied by 100
Cycle-time deviation Difference between migrated and baseline cycle time
Data integrity Percentage of required data points verified correctly
Documentation completion Percentage of required handover documents approved

For example, if 96 of 100 executed tests pass:

\[ \text{Test pass rate} = \frac{96}{100}\times100 = 96\\% \]

A high pass rate does not justify release if one of the failed tests concerns a critical safety function or essential production requirement. Critical acceptance criteria take precedence over aggregate percentages.

14. Common Migration Failures and Corrective Actions

Failure Likely cause Corrective action
CPU will not start correctly Unsupported configuration, firmware mismatch, or hardware issue Check diagnostics, order numbers, firmware, and configuration
Input signal appears at the wrong tag Incorrect address mapping or wiring Compare the approved I/O list, channel assignment, and terminal wiring
Analog value is incorrect Range, scaling, polarity, or module configuration mismatch Verify transmitter specifications and scaling
HMI displays incorrect values Changed DB layout, tag references, or communication configuration Audit HMI tags and external data dependencies
Drive fails to communicate Interface or telegram configuration changed Verify hardware support, network setup, and data mapping
Sequence times out Changed timing behavior or missing feedback Inspect sequence logic, field signals, and measured timing
Data is lost after restart Retentivity or initialisation changed Verify required retained values and startup behavior
Intermittent network fault occurs Address conflict, wiring issue, device configuration, or network load Check physical network and diagnostic evidence
Production cycle time increases Execution or communication timing changed Measure the cycle and investigate critical paths
Rollback takes too long Original configuration or restoration steps were not prepared Improve and rehearse the recovery plan

15. Practical Example: Migrating a Test Bench

Consider a test bench that uses an S7-300 to control a fixture, monitor pressure, execute a test cycle, evaluate the result, and send production data to an external application.

A disciplined migration would follow these stages:

  1. Record the original CPU, I/O, network, program, data, and timing configuration.
  2. Define the target S7-1500 hardware and TIA Portal project.
  3. Identify any unsupported instructions, modules, or external data dependencies.
  4. Convert the project and resolve hardware and software incompatibilities.
  5. Compile the target project and inspect all relevant diagnostics.
  6. Test digital inputs, digital outputs, analog scaling, and communications.
  7. Execute the complete test sequence under controlled conditions.
  8. Verify pass/fail logic, timeout behavior, data recording, and fault recovery.
  9. Validate the applicable safety functions.
  10. Execute the approved cutover and production trial.
  11. Accept the system or follow the rollback plan.
  12. Save the final project and update the maintenance documentation.

The migration is complete only when the system meets its defined acceptance criteria and the required evidence is recorded.

16. Final Migration Checklist

Engineering

  • Original project and hardware configuration preserved.
  • Target CPU and modules verified.
  • Program conversion completed and reviewed.
  • Hardware and software compile checks completed.
  • External data and communication dependencies verified.
  • Timing and functional requirements documented.

Testing

  • Hardware and wiring inspected.
  • Digital and analog I/O tested.
  • Communication links verified.
  • Normal sequences tested.
  • Fault and recovery scenarios tested.
  • Timing and data integrity verified.
  • Required safety validation completed.

Cutover and release

  • Shutdown and cutover plan approved.
  • Rollback triggers and restoration steps defined.
  • Production trial completed.
  • Acceptance criteria met.
  • Final project and recovery backup saved.
  • Drawings, spare lists, and maintenance records updated.
  • Operations and maintenance handover completed.

Core principle: Convert the project, test the actual behavior, cut over under controlled conditions, and retain a verified recovery path. A migration is an engineering change to the whole automation system, not just a programming exercise.
