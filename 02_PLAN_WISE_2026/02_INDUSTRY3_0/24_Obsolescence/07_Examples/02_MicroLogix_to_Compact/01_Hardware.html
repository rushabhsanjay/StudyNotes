1. Purpose and Scope

Migrating an Allen-Bradley MicroLogix PLC system to CompactLogix is a hardware and control-system redesign, not a direct processor replacement. The two product families differ in controller architecture, I/O arrangement, communication interfaces, memory organisation, power requirements, and supported automation features.

MicroLogix controllers are compact, generally fixed-I/O or expansion-I/O controllers designed for smaller automation applications. CompactLogix controllers use a Logix control architecture with a controller and compatible local or distributed I/O, depending on the selected family and configuration.

The objective of this topic is to determine which parts of an existing MicroLogix installation can be retained, which must be replaced, and what must be redesigned before the machine can be recommissioned.

This topic focuses on hardware. Conversion from RSLogix 500 to Studio 5000, including program structure and instruction differences, is covered separately in the next topic.

2. Understanding the Two Controller Families

2.1 MicroLogix architecture

MicroLogix is a legacy Allen-Bradley controller family commonly found in standalone machines, small production stations, conveyors, fixtures, and older test equipment.

Examples include:

  • MicroLogix 1000.
  • MicroLogix 1100.
  • MicroLogix 1200.
  • MicroLogix 1400.
  • MicroLogix 1500.

Availability and capabilities vary by model. These controllers do not all have the same communication interfaces, memory capacity, expansion options, or I/O features.

A typical installation may contain:

  • A MicroLogix controller with built-in I/O.
  • Compatible expansion I/O modules, where supported.
  • A 24 VDC or other specified power arrangement.
  • Serial or Ethernet communication, depending on the model.
  • An HMI, drive, remote device, or PC connection.
  • Field sensors, relays, solenoid valves, and other actuators.
Machine power and field supplies
    ↓
MicroLogix controller
    ↓
Built-in I/O and supported expansion I/O
    ↓
Field sensors and actuators
    ↓
HMI / drive / other communication devices

A key characteristic is that many MicroLogix installations combine the CPU and some I/O in one compact unit. Consequently, replacing the controller can also mean replacing the physical terminals and field-wiring arrangement.

2.2 CompactLogix architecture

CompactLogix is part of the Allen-Bradley Logix controller family. It uses controller hardware with compatible local I/O arrangements and can communicate with supported distributed I/O and other network devices.

Depending on the CompactLogix generation, the installation may include:

  • A CompactLogix controller.
  • Compatible local I/O modules or a supported local expansion arrangement.
  • A chassis, backplane, or other platform-specific mounting arrangement where required by the selected family.
  • EtherNet/IP communication.
  • Additional communication or specialty modules, where supported.
  • Remote I/O, drives, HMIs, robots, and other networked equipment.
Industrial power
    ↓
CompactLogix controller and supported I/O arrangement
    ↓
EtherNet/IP or other supported interfaces
    ↓
Distributed I/O / HMI / drives / other controllers
    ↓
Sensors, actuators and machine processes

CompactLogix configurations are model-dependent. Not every controller supports every I/O family, communication option, module arrangement, or engineering-software version.

4. Controller Selection and Model Differences

4.1 Identify the exact MicroLogix model

The first step is to record the complete catalog number of the installed controller.

For example, a MicroLogix 1100 and a MicroLogix 1400 may differ in built-in I/O, Ethernet functionality, serial interfaces, expansion options, and memory. The family name alone is not sufficient for a migration assessment.

Record:

  • Complete catalog number.
  • Series and hardware revision, where applicable.
  • Firmware revision.
  • Built-in digital and analog I/O.
  • Expansion modules.
  • Available communication ports.
  • Connected devices and protocols.
  • Program size and data requirements.
  • Special instructions or hardware-dependent functions.

4.2 Select the target CompactLogix controller

Do not select a CompactLogix controller merely because it is newer or has more memory. Selection must be based on the complete application.

Selection factor What to verify
Application size Program size, tag count, data structures, and future growth
Execution requirements Task rates, periodic logic, event processing, and response times
I/O capacity Number and types of required I/O points
Network requirements EtherNet/IP devices, connection capacity, topology, and required protocols
Specialty functions High-speed counting, motion, serial communication, and other required features
Memory and data Required controller memory, retained values, and communication buffers
Firmware Supported controller firmware and engineering software
Lifecycle Product availability, support status, and planned long-term serviceability
Panel constraints Mounting, dimensions, ventilation, and wiring space
Safety requirements Whether a separate safety-rated architecture is required

4.3 CompactLogix generations

CompactLogix is not one single hardware architecture. Different generations use different controller families, I/O platforms, firmware capabilities, and engineering-software requirements.

For example, older CompactLogix families may use 1769 Compact I/O in a local arrangement, while newer families may use different local I/O platforms and support different module and network configurations.

Before selecting the target hardware, verify the controller catalog number, supported I/O family, firmware revision, and applicable product documentation.

Engineering rule: Choose the exact controller and I/O platform first, then design the hardware configuration around that documented combination.

5. Built-In I/O Versus Separate I/O

5.1 MicroLogix built-in I/O

Many MicroLogix controllers have built-in digital inputs, digital outputs, and, on selected models, analog I/O. These signals terminate directly at the controller's terminals.

This arrangement can reduce panel size and component count, but it couples the field wiring to the controller model.

When the controller is replaced, each built-in signal must be reassigned to a supported input or output on the new system.

5.2 CompactLogix I/O arrangement

CompactLogix systems commonly use separate I/O modules. Depending on the controller family, the modules may be installed locally or connected as distributed I/O over a supported network.

The new arrangement can provide greater modularity, but it introduces additional design tasks:

  • Select the compatible I/O platform.
  • Determine the required module count.
  • Choose suitable digital and analog modules.
  • Design module mounting and power distribution.
  • Map every original field signal to the new module and channel.
  • Confirm terminal blocks and wiring accessories.
  • Configure the modules in the engineering project.

5.3 Example of I/O expansion

Suppose a MicroLogix machine has 20 digital inputs, 12 digital outputs, and 4 analog inputs.

The target system must support at least those required signal functions, with appropriate electrical characteristics and sufficient capacity for any future expansion.

Do not simply choose modules whose channel counts add up to the required totals. Channel grouping, electrical ratings, isolation, field power, diagnostics, and spare capacity also matter.

Signal group Existing requirement Target design consideration
Digital inputs 20 points Select sufficient supported channels and verify sensor compatibility
Digital outputs 12 points Verify output type, load current, and protection
Analog inputs 4 points Verify signal ranges, resolution, accuracy, and isolation
Spare capacity Based on plant requirements Reserve suitable channels and physical expansion capacity

6. I/O Module Compatibility

6.1 MicroLogix expansion modules

MicroLogix expansion modules are specific to supported controller families and models. Their mechanical connections, electrical characteristics, and communication with the controller are not automatically compatible with CompactLogix.

A module from a MicroLogix installation must not be assumed to function as a local CompactLogix I/O module.

6.2 CompactLogix I/O families

CompactLogix configurations can use supported I/O platforms such as 1769 Compact I/O in applicable systems. Other CompactLogix generations support different I/O architectures.

The target module selection must be checked against the exact controller and firmware.

Review:

  • Digital input and output characteristics.
  • Analog input and output ranges.
  • Channel-to-channel isolation.
  • Module power requirements.
  • Terminal block and wiring accessory requirements.
  • Supported module placement and expansion limits.
  • Firmware and configuration support.
  • Diagnostic and fault-reporting capabilities.

6.3 Digital input compatibility

For every digital input, document:

  • Input voltage range.
  • Input current and switching thresholds.
  • Sensor type and output arrangement.
  • Common-terminal grouping.
  • Input filtering and response time.
  • Isolation and diagnostic capabilities.
  • Wiring and polarity.

For example, a three-wire PNP proximity sensor typically switches a positive voltage to the input when active. The target input must support the sensor's electrical arrangement, and the common wiring must be correct.

Do not assume a sensor can be connected to a new module simply because both systems use 24 VDC.

6.4 Digital output compatibility

For every digital output, check:

  • Output type, such as relay or transistor.
  • Rated voltage and current.
  • Maximum channel and group loading.
  • Inductive-load protection.
  • Short-circuit and overload behavior.
  • Switching delay.
  • Field power and common-terminal arrangement.

A MicroLogix relay output and a CompactLogix transistor output are not automatically equivalent. If the original output drives a contactor, solenoid, or other load, the replacement must be selected to suit that load.

6.5 Analog I/O compatibility

Analog signals require special attention because a wiring or scaling mismatch can produce plausible but incorrect values.

Check:

  • Voltage or current signal type.
  • Measurement range, such as 0–10 V or 4–20 mA.
  • Resolution and accuracy.
  • Channel isolation.
  • Wire-break and out-of-range diagnostics.
  • Loop power and reference connections.
  • Scaling and engineering units.
  • Input filtering and conversion time.

For a linear 4–20 mA transmitter representing 0–10 bar:

\[ P=\frac{I-4}{20-4}\times10 \]

At 12 mA, the expected pressure is 5 bar. The actual transmitter range and module configuration must be verified before using this conversion.

7. Power Supply and Field Power

7.1 Power architecture

A MicroLogix installation may combine the controller and I/O in a compact assembly, while a CompactLogix design may require a separate controller power supply and additional I/O or field-power arrangements.

The exact requirements depend on the selected controller, I/O platform, and modules.

Distinguish between:

  • Controller power.
  • I/O module power.
  • Field power for sensors and actuators.
  • Auxiliary power for communication devices and external equipment.

7.2 Power migration checklist

  • Record the existing supply voltage and current rating.
  • Identify all loads supplied by the original controller or I/O arrangement.
  • Determine the target controller's specified power requirements.
  • Calculate I/O and field-device loads.
  • Verify protection, grounding, and circuit segmentation.
  • Check startup and inrush current where relevant.
  • Confirm that the new installation meets the applicable electrical design requirements.

Do not assume the original MicroLogix power arrangement can supply the new CompactLogix system.

7.3 Example load calculation

If 16 sensors each draw 35 mA and 8 interface relays each draw 50 mA, the combined steady-state current is:

\[ I\_{\text{total}}=(16\times0.035)+(8\times0.05)=0.96\text{ A} \]

This is the calculated load for those devices only. Other loads, startup current, and the required design margin must also be considered before selecting the supply.

8. Communication Interfaces and Networks

8.1 MicroLogix communication capabilities

MicroLogix communication capabilities vary by model. Depending on the controller, an installation may use serial communication, Ethernet, or other supported interfaces and protocols.

Typical connected devices include:

  • HMI panels.
  • Drives.
  • Barcode scanners and printers.
  • Measurement instruments.
  • Remote devices.
  • PCs and SCADA systems.
  • Other controllers.

Record every connection before deciding which interfaces the target controller must provide.

8.2 CompactLogix and EtherNet/IP

EtherNet/IP is widely used with CompactLogix systems. However, the supported interfaces, connection capacity, topology, and network capabilities depend on the exact controller family.

The migration may require changes to:

  • IP addresses and subnet configuration.
  • Device names and network settings.
  • Network switches and cabling.
  • HMI and drive connections.
  • Remote I/O architecture.
  • Communication instructions and data structures.
  • Device configuration and fault handling.

A controller with an Ethernet port does not necessarily support every protocol or legacy communication method used by the old system.

8.3 Serial devices

If the MicroLogix installation communicates with a printer, scanner, instrument, or other device over serial communication, verify the complete interface requirements.

Check:

  • RS-232, RS-422, or RS-485 interface.
  • Connector and pin assignment.
  • Baud rate and framing.
  • Parity and stop bits.
  • Message format and termination.
  • Handshaking and timeout behavior.
  • Electrical isolation and grounding.

A serial device may require a supported communication module, a suitable gateway, or replacement. Any gateway must support the required protocol, timing, diagnostics, and failure behavior.

9. Local I/O and Distributed I/O

9.1 Local I/O

Local I/O is physically installed in the controller's supported local arrangement. Its compatibility depends on the controller family, I/O platform, and module specifications.

The migration engineer must confirm the supported module family and permitted arrangement for the chosen CompactLogix controller.

9.2 Distributed I/O

Distributed I/O is located away from the main controller and communicates over a supported industrial network.

This arrangement can reduce long field-wire runs and allow modular machine sections. However, it requires the correct network interface, device configuration, and compatible I/O hardware.

For each remote station, record:

  • Station identity.
  • Interface module and catalog number.
  • Network address and protocol.
  • Installed I/O modules.
  • Field wiring and power.
  • Required update time.
  • Communication-loss behavior.

Do not assume an existing remote I/O station can be retained simply because it uses EtherNet/IP. The exact device and controller combination must be supported.

10. Specialty Modules and High-Speed Functions

Legacy MicroLogix systems may use high-speed counters, pulse-train outputs, serial interfaces, analog modules, or other model-specific features.

The target design must preserve the required function, even if the implementation changes.

10.1 High-speed counters and encoders

Check:

  • Maximum input frequency.
  • Encoder type and signal format.
  • Count modes and direction detection.
  • Index or reference inputs.
  • Input filtering.
  • Required response time.
  • Hardware support in the target platform.

Do not assume a standard digital input can replace a dedicated high-speed counter input.

10.2 Pulse-train and motion-related functions

If the original controller produces pulse trains or controls a motion-related device, identify the exact output method and timing requirements.

Determine whether the target controller and compatible modules support the required function. The replacement may require a different motion architecture, drive interface, or controller configuration.

10.3 Other specialty functions

Also review:

  • Thermocouple and RTD measurement.
  • Weighing and load-cell interfaces.
  • Serial instrument communication.
  • Device-specific communication modules.
  • Fast event capture.
  • Interrupt-driven processing.

A function that was previously built into the MicroLogix controller may require separate hardware or a different implementation in the target system.

11. Terminal Wiring and Panel Layout

11.1 Wiring changes

Because many MicroLogix controllers have built-in I/O terminals, replacing the controller often changes the physical termination of field wiring.

Prepare an updated drawing that identifies:

  • Original controller terminals.
  • Original signal names.
  • New I/O module and channel.
  • New terminal block and pin assignment.
  • Field-device connection.
  • Field power and common wiring.
  • Shield and protective-earth connections.

11.2 Panel layout

Review the cabinet for:

  • Controller and I/O mounting.
  • Space for new modules and power supplies.
  • Cable duct capacity.
  • Terminal block requirements.
  • Ventilation and heat dissipation.
  • Network switch placement.
  • Access for diagnostics and replacement.
  • Separation of power, signal, and communication wiring where required.

A CompactLogix system may be physically larger than the original compact controller arrangement. The cabinet must accommodate the complete engineered system, not just the CPU.

12. Safety Considerations

Standard MicroLogix controllers are not substitutes for safety-rated control systems. If the original machine relies on safety relays, safety controllers, or other safety-related hardware, that architecture must be identified before migration.

The target design must preserve the required safety functions through an appropriate and validated arrangement.

Check:

  • Emergency-stop circuits.
  • Guard-door interlocks.
  • Enabling devices.
  • Safe drive or motion functions.
  • Safety relay and safety controller interfaces.
  • Restart and reset behavior.
  • Required safety performance and validation.
  • Applicable machinery and site requirements.

Do not assume that a standard CompactLogix controller automatically provides safety functionality. A safety-related migration requires the appropriate safety-rated hardware and a separate validation process.

Consider a test bench controlled by a MicroLogix controller. It reads fixture sensors, operates pneumatic valves, monitors a pressure transmitter, communicates with an HMI, and sends results to a PC.

The hardware migration assessment should include the following:

15. Hardware Migration Checklist

Existing-system assessment

  • Record the exact MicroLogix catalog number and firmware.
  • Record all built-in I/O and expansion modules.
  • Identify all field signals and terminal assignments.
  • Document power supplies and connected loads.
  • Inventory HMI, drives, serial devices, and network connections.
  • Identify specialty modules and high-speed functions.
  • Document safety-related hardware and functions.
  • Record cabinet dimensions and existing wiring routes.

Target-system design

  • Select a compatible CompactLogix controller.
  • Confirm the target I/O family and module compatibility.
  • Verify digital and analog electrical characteristics.
  • Design the new power and field-power arrangement.
  • Verify communication interfaces and network topology.
  • Confirm support for specialty functions.
  • Design the new terminal layout and wiring drawings.
  • Verify panel space, ventilation, and service access.
  • Complete the applicable safety review.

Installation and verification

  • Verify hardware against the approved design.
  • Inspect wiring, terminals, earthing, and power distribution.
  • Confirm network configuration and device compatibility.
  • Test every input and output.
  • Validate analog values and scaling.
  • Verify communication and fault recovery.
  • Test critical machine sequences and response timing.
  • Update the installed-base and spare-parts records.

16. Interview and Practical Competency Questions

1. Can a MicroLogix controller be directly replaced by a CompactLogix CPU?

No. The controller architecture, I/O arrangement, wiring, communication interfaces, and supported functions differ. The replacement requires an engineered hardware configuration.

2. Can existing MicroLogix expansion I/O be used directly with CompactLogix?

Do not assume so. The exact module and controller combination must be supported. Incompatible modules must be replaced or their functions redesigned.

3. Why is built-in I/O important during migration?

Field wiring terminates directly at the original controller. Replacing the controller may therefore require new I/O modules, terminal blocks, and wiring arrangements.

4. Why must the exact CompactLogix generation be identified?

Different generations support different controller capabilities, I/O platforms, module arrangements, firmware, and engineering-software versions.

5. Can a MicroLogix serial connection simply be replaced by Ethernet?

Not automatically. The connected device and protocol must support the new interface, or a suitable and validated communication solution must be engineered.

6. What is the most important first step?

Inventory the exact controller, all I/O, communication connections, power arrangements, specialty functions, and safety-related hardware before selecting the replacement.

17. Final Engineering Principle

A successful MicroLogix-to-CompactLogix migration preserves the required machine functions while replacing incompatible hardware with a documented and supported design.

Classify each existing component as:

  • Retain: Its use in the target architecture is documented as supported.
  • Replace: A compatible successor or alternative is selected.
  • Redesign: The function requires a different hardware or communication arrangement.
  • Validate: Compatibility or behavior must be confirmed through documented testing.

The final design must be verified against the exact Allen-Bradley controller and module catalog numbers, applicable installation manuals, firmware requirements, and engineering-software support. Product-family names alone are not enough to establish compatibility.
