1. Purpose and scope

The purpose of migrating a Mitsubishi GOT1000 HMI to a GOT2000 HMI is to replace an older operator interface with a supported, maintainable platform while preserving the required machine operation, PLC communication, alarms, recipes, trends, and operator functions.

A successful migration is not simply transferring a converted project into the replacement panel. It requires three separate activities:

  • Convert: Adapt the existing HMI project to the target GOT2000 model and its supported software features.
  • Transfer: Download the verified project to the replacement HMI and establish the correct communication settings.
  • Test: Confirm that every required function operates correctly with the PLC and the actual machine.

The main engineering objective is to preserve the machine's intended behavior without introducing incorrect commands, lost alarms, corrupted recipes, communication failures, or unsafe operating conditions.

4. Engineering software and project compatibility

4.1 GT Designer2 and GT Designer3

Mitsubishi GOT1000 projects are commonly associated with GT Designer2, while GOT2000 engineering is commonly performed using GT Designer3, supplied as part of the applicable GT Works3 environment.

The exact supported conversion route depends on the original project format, source HMI model, target model, and installed software version.

Item What to verify Why it matters
Source software GT Designer version and project format Determines whether the source project can be opened or converted directly
Target software Installed GT Designer3/GT Works3 version Determines target-model and feature support
Source panel Complete GOT1000 model number Identifies source capabilities and limitations
Target panel Complete GOT2000 model number Determines resolution, interfaces, and supported functions
Firmware Target HMI system software requirements Prevents software and firmware incompatibilities
Communication driver Supported PLC and connection type Determines whether the HMI can communicate with the controller
Options Required functions and hardware options Prevents loss of functions dependent on optional hardware or licenses

Important: Do not assume every GOT1000 project can be converted directly in one step. Follow the documented conversion procedure for the specific source and target combination.

4.2 Project recovery before conversion

Recover the original editable project from the engineering PC, approved engineering archive, or other authorized backup location.

If the original project is unavailable, investigate whether the existing GOT1000 supports retrieving project data. An upload from a running HMI may not recover all original engineering information, comments, reusable libraries, or source objects in the same form as the original editable project.

Before conversion, record:

  • GOT1000 model and system version.
  • PLC make, model, CPU type, and firmware where relevant.
  • Communication interface, driver, station number, IP address, and port settings.
  • Screen count and screen navigation.
  • PLC device addresses used by each screen.
  • Alarm configuration, recipes, trends, scripts, and logging.
  • Passwords, user permissions, and protected settings.
  • Fonts, graphics, custom objects, and installed options.
  • Current PLC program revision and associated project backup.

Never overwrite the only copy of the original project. Preserve an untouched source version and work on a separate migration copy.

5. Hardware and target-model verification

Before converting the project, confirm that the target GOT2000 can support the required application.

Verification item Required engineering action
Display size Confirm that the new display is suitable for the operator panel
Resolution Check screen dimensions and object positioning
Touch operation Verify touch technology and operator interaction requirements
Interfaces Confirm required Ethernet, serial, USB, and storage interfaces
PLC connectivity Verify the target model and supported communication driver
Power supply Confirm voltage, current requirements, and wiring
Mounting Verify panel cutout, depth, gasket, and mounting clamps
Environmental rating Confirm suitability for dust, moisture, vibration, and temperature
Storage Check requirements for logging, recipes, and backup storage
Options Verify required licenses, accessories, and model-specific features

A mechanically compatible panel is not necessarily functionally compatible. The replacement must also support the required communication, storage, and software features.

6. Converting the project

6.1 Recommended conversion procedure

  1. Create a dedicated migration folder.
  2. Copy the original project into the migration folder without altering the source.
  3. Record the source project version and source GOT model.
  4. Open or import the project using the documented Mitsubishi conversion procedure.
  5. Select the exact target GOT2000 model.
  6. Configure the target display resolution and orientation.
  7. Review the conversion report, warnings, and errors.
  8. Reconfigure communication drivers, PLC connections, and interface settings as necessary.
  9. Inspect unsupported objects and features that require manual replacement.
  10. Verify all screen layouts, fonts, graphics, scripts, and numerical formats.
  11. Check alarm, recipe, trend, logging, and security settings.
  12. Validate or compile the converted project using the target software.
  13. Save the converted project under a new name and revision.

Example project organization:

GOT_MIGRATION/
    SOURCE_GOT1000/
        Original_Project
        Source_Configuration
        Source_Backup
    WORKING_CONVERSION/
        Converted_Project
        Conversion_Report
        Engineering_Notes
    TARGET_GOT2000/
        Final_Project
        Transfer_Settings
        Test_Records
        Approved_Backup

This organization separates the original evidence from the converted project and the released production version. It also prevents a common maintenance disaster: discovering that the only copy of the old project was overwritten during an experiment.

6.2 Conversion warnings and errors

Finding Meaning Required action
Unsupported object An object cannot be reproduced exactly on the target Replace or redesign the object and test its behavior
Font substitution A font is unavailable or rendered differently Select a supported font and verify readability
Resolution mismatch Objects may be displaced or clipped Adjust layout and test on the target display
Communication warning The driver or connection settings require attention Verify the target PLC driver and interface
Script warning Script syntax or functionality may differ Inspect the script and validate its execution
Option dependency A function depends on hardware or software options Verify availability and configure the supported alternative
Address warning A device assignment may be invalid or altered Compare against the source project and PLC program
Resource warning A target resource or project limit may be exceeded Reduce usage or redesign within supported limits

A project that opens successfully is not necessarily a project that operates correctly. Conversion reports must be reviewed, and every critical warning must have a documented disposition.

7. Screen layout and object verification

A GOT1000 screen may not render identically on a GOT2000, even when the logical function is unchanged.

7.1 Objects requiring inspection

Object or function Verification requirement Typical failure
Navigation buttons Confirm destination screens and touch response Incorrect screen opens
Numeric displays Verify digit count, decimal places, sign, and units Value appears truncated
Numeric input Verify input limits and write behavior Incorrect value is written to PLC
Bit switches Verify ON/OFF behavior and interlocks Unintended machine command
Word switches Verify assigned device and written value Wrong operating mode selected
Lamps Verify device assignment and ON/OFF indication Incorrect machine status
Alarm display Verify alarm text, priority, and acknowledgement Important alarm is missing
Trend graph Verify sampling interval, scale, and history Misleading or incomplete trend
Recipe screen Verify recipe selection, transfer, and confirmation Wrong process settings loaded
Numeric keypad Verify data format and range limits Invalid operator entry
User login Verify user levels and protected functions Unauthorized operation becomes possible
Graphic objects Verify position, size, and readability Labels overlap or disappear
Scripts Verify triggers, calculations, and execution Required action does not occur

7.2 Display and numeric format checks

Suppose the PLC stores a temperature as an integer scaled by ten.

For example, a PLC value of 253 represents \(25.3\\,^\circ\mathrm{C}\) if the agreed scaling factor is ten.

The displayed value is:

\[ T=\frac{253}{10}=25.3\\,^\circ\mathrm{C} \]

During migration, verify that the target HMI preserves the original scaling, decimal position, signedness, engineering units, and allowable input range.

A display that shows 253 °C instead of 25.3 °C is not a cosmetic problem. It can lead an operator to make an incorrect process decision.

7.3 Touch and navigation checks

Test every screen transition, including less frequently used maintenance screens.

  • Confirm that all buttons are visible and accessible.
  • Check that touch targets are sufficiently large for normal operator use.
  • Verify screen return, home, popup, and window-closing behavior.
  • Check whether overlapping objects intercept touch inputs.
  • Verify that popup windows do not hide critical machine information.
  • Confirm that protected screens remain protected.
  • Compare important screens with approved screenshots or the source project.

8. PLC communication migration

The HMI is an operator interface, but its commands and displayed information depend on correct PLC communication. A successful download does not prove that the communication path works.

8.1 Communication parameters

Parameter What to verify
PLC manufacturer Must match the actual connected controller
PLC CPU model Must be supported by the selected driver
Driver/protocol Must match the intended communication method
Physical interface Ethernet, serial, or another supported interface
IP address Must match the planned network configuration
Subnet mask Must be compatible with the network design
Gateway Must be correct if routed communication is required
Station number Must match the applicable communication configuration
Serial settings Baud rate, parity, data bits, and stop bits where applicable
Device addressing Confirm the correct PLC device types and address ranges
Connection timeout Must be appropriate for the network and controller
Write permissions Confirm which operator actions can write to the PLC

Not every GOT2000 model supports every interface or protocol. Verify the exact model's documentation and the supported PLC connection method.

8.2 Device address validation

For a Mitsubishi PLC, examples of commonly encountered device types include:

  • X: input devices.
  • Y: output devices.
  • M: internal bit devices.
  • D: data registers.

The actual available device ranges and addressing rules depend on the PLC family and configuration. Other manufacturers use different conventions, and a device name must never be assumed to have identical meaning across PLC platforms.

Create a device-validation list containing the screen object, source address, target address, data type, access direction, scaling, and test result.

HMI function Example device Expected behavior
Auto mode indication M100 Indicates the verified automatic-mode status
Production count D200 Displays the count with the correct numerical format
Alarm reset command M150 Executes only under approved machine conditions
Temperature display D300 Displays the correctly scaled engineering value
Recipe number D400 Shows the active recipe identifier

These are illustrative addresses, not actual machine assignments. They must be replaced with addresses confirmed from the production PLC program and the approved I/O or device list.

8.3 Read and write verification

Test reads and writes separately.

Read verification:

  1. Select a known PLC device.
  2. Confirm its value in the PLC programming environment or an approved diagnostic method.
  3. Compare the PLC value with the HMI display.
  4. Change the source value under controlled conditions.
  5. Confirm that the HMI updates correctly.

Write verification:

  1. Identify the target PLC device and its purpose.
  2. Confirm that the write is permitted by the machine's operating and safety procedures.
  3. Test using a controlled, approved test condition.
  4. Verify the written value at the PLC.
  5. Confirm that the PLC logic responds as intended.
  6. Confirm that invalid values or unauthorized commands are rejected where required.

Do not test arbitrary writes against production outputs, motion commands, interlocks, or safety-related signals. Use a simulation, test PLC, or approved controlled test procedure where possible.

9. Alarms, recipes, logging, and special functions

9.1 Alarm migration

Check all alarm configuration and operator response behavior.

  • Alarm trigger devices and conditions.
  • Alarm messages, numbering, and priority.
  • Active, historical, and acknowledged alarm states.
  • Alarm reset and acknowledgement behavior.
  • Alarm history retention and storage.
  • Time stamps and clock configuration.
  • System alarms and communication-failure indications.

Acknowledge and reset are not automatically equivalent. Confirm that the migrated interface preserves the original machine logic and the intended meaning of each action.

9.2 Recipe migration

Recipe migration deserves special attention because recipes can contain machine settings, process limits, and production-specific parameters.

Verify:

  • Recipe names and identifiers.
  • Number of recipes and data items.
  • PLC device mapping.
  • Data types, signedness, and scaling.
  • Minimum and maximum allowed values.
  • Recipe selection and confirmation sequence.
  • Transfer direction between HMI and PLC.
  • Save, load, and restore behavior.
  • Storage medium and retention after power loss.

Where recipes affect product quality or machine safety, compare representative recipe data against an approved baseline before releasing the replacement HMI.

9.3 Trends and data logging

Confirm that the migrated project preserves the required sampling and retention behavior.

Item Test
Sampling interval Confirm the intended interval
Data source Verify the correct PLC device or tag
Engineering scale Check axis limits and units
Historical data Confirm the actual retention capability
Storage medium Verify supported storage and capacity
Export function Test only if required by the application
Time stamps Check clock and time-zone configuration
Restart behavior Verify what happens after power loss or reboot

Do not assume historical data stored on the old HMI automatically transfers to the new HMI. Treat historical records and configuration as separate migration items.

9.4 Scripts and custom functionality

For each script or custom function, document:

  • Trigger condition.
  • Input devices and variables.
  • Output devices and variables.
  • Execution order and dependencies.
  • Error handling.
  • Expected result.
  • Test evidence.

Revalidate any function involving indirect device addressing, arithmetic, string handling, external equipment, barcode readers, or conditional writes. A script that compiles may still behave differently when its timing, trigger, or dependencies change.

10. Transferring the converted project

10.1 Pre-transfer checks

Before connecting the engineering PC to the target GOT2000:

  • Confirm the exact target HMI model.
  • Confirm the approved converted project revision.
  • Confirm the target software and firmware compatibility.
  • Review conversion warnings and validation results.
  • Verify the PLC driver and communication parameters.
  • Record the target HMI network configuration.
  • Confirm the permitted transfer interface.
  • Back up any existing target project and configuration.
  • Obtain the required production or maintenance authorization.
  • Confirm that the machine is in an approved condition for testing.

10.2 Transfer procedure

  1. Connect the engineering PC using an interface supported by the exact target model.
  2. Verify the PC-to-HMI connection.
  3. Select the correct target GOT model and project.
  4. Confirm the transfer settings and data to be transferred.
  5. Download the project using the documented procedure.
  6. Wait for transfer completion and any required restart.
  7. Confirm that the target HMI starts without project or system errors.
  8. Check the displayed project revision.
  9. Verify PLC communication.
  10. Record the transfer date, software version, project revision, and result.

USB, Ethernet, serial, and storage-card transfer options vary by model and configuration. Use the applicable Mitsubishi manual rather than assuming that the replacement panel supports the same transfer method as the old one.

10.3 Transfer versus PLC download

Transferring an HMI project and downloading a PLC program are different operations.

  • HMI transfer: Installs the operator-interface project and its supported HMI configuration.
  • PLC download: Changes the controller program or configuration.

A GOT1000-to-GOT2000 HMI migration does not inherently require modifying the PLC program. Any proposed PLC change must be separately justified, reviewed, approved, backed up, and tested.

11. Testing strategy: FAT and SAT

Testing must demonstrate that the replacement HMI behaves correctly, not merely that it powers on.

11.1 Factory Acceptance Test (FAT)

FAT should be performed in an engineering environment or controlled test setup before the production cutover wherever practical.

Test category Test procedure Acceptance criteria
Startup Power-cycle the target HMI Project starts without unexpected errors
Screen navigation Visit all required screens Correct screens open and close
Numeric display Compare displayed values with PLC values Values, signs, units, and scaling match
Numeric entry Enter approved test values Correct values are written and invalid values are handled correctly
PLC communication Monitor known PLC devices Required data updates correctly
Alarm operation Generate approved test conditions Correct alarms appear and clear as designed
Recipe operation Load and verify approved test recipes Correct parameters are transferred
Trend operation Change a test value over time Trend samples and scales are correct
User security Test authorized and unauthorized access Permissions match approved requirements
Communication loss Interrupt communication in a controlled test Fault indication and recovery behave correctly
Power recovery Restart the HMI and restore the test setup Required configuration and operation recover correctly
Performance Test navigation and screen updates Response is acceptable for the application
Storage Test required logging and retention Required data is retained within supported limits

11.2 Site Acceptance Test (SAT)

SAT confirms the migrated system operates correctly in the actual machine installation.

  • Verify panel mounting, power supply, grounding, and network connections.
  • Confirm PLC communication using the production configuration.
  • Test machine-status indications against actual conditions.
  • Verify operator permissions and protected maintenance functions.
  • Test alarms and acknowledgement using approved procedures.
  • Validate representative production or maintenance sequences.
  • Confirm that machine interlocks and safety functions remain effective.
  • Check communication recovery after an approved interruption.
  • Obtain sign-off from maintenance, controls engineering, production, and other required stakeholders.

HMI testing does not replace validation of machine safety functions. Emergency stops, safety relays, safety PLCs, guards, and other protective systems must be verified under the applicable safety procedures.

11.3 Test evidence

Maintain a test record for each critical function.

Field Example
Test ID HMI-COM-001
Test description Verify PLC temperature read
Expected result HMI displays the correct scaled value
Actual result Recorded during testing
Status Pass, fail, or blocked
Evidence Screenshot, PLC observation, or approved test record
Defect reference Linked corrective-action record if failed
Tested by Responsible engineer or technician
Date Actual test date
Approval Required reviewer or authority

Never mark a test as passed solely because the related screen is visible.

12. Cutover and rollback planning

12.1 Before cutover

  • Back up the original GOT1000 project.
  • Record existing communication and network settings.
  • Preserve the original HMI, cables, and mounting accessories where practical.
  • Confirm the target GOT2000 project has passed required testing.
  • Approve the installation and shutdown window.
  • Confirm the target panel fits the enclosure and wiring arrangement.
  • Verify that the PLC program and configuration have not been unintentionally changed.
  • Prepare the rollback procedure and required tools.
  • Identify responsible personnel and escalation contacts.

12.2 Cutover execution

  1. Place the machine in the approved shutdown state.
  2. Apply the required isolation and lockout/tagout procedures.
  3. Verify the absence of hazardous energy before electrical work.
  4. Remove the old HMI using the approved installation procedure.
  5. Install the GOT2000 and verify wiring, power, grounding, and mounting.
  6. Apply power under the authorized commissioning procedure.
  7. Confirm HMI startup and PLC communication.
  8. Execute the approved SAT checklist.
  9. Obtain the required production-release authorization.
  10. Monitor the machine during the agreed observation period.

12.3 Rollback conditions

Rollback may be necessary if:

  • Critical PLC communication cannot be restored.
  • A required alarm or operator command fails.
  • Recipe values or process parameters are incorrect.
  • A critical screen or protected function is unavailable.
  • Unexpected behavior affects machine operation.
  • Required acceptance tests cannot be completed.

The rollback procedure must specify how to restore the previous system and verify the machine's condition afterward. Do not reinstall or reconnect equipment without following electrical isolation, compatibility, and commissioning requirements.

14. Practical industrial example

Scenario

A production machine uses a GOT1000 HMI connected to a Mitsubishi PLC. The panel displays machine status, production count, fault alarms, and a recipe-selection screen. The HMI is being replaced with a compatible GOT2000.

Migration requirements

  • Preserve existing PLC device assignments where supported.
  • Retain production-count display and scaling.
  • Preserve alarm messages and acknowledgement behavior.
  • Ensure recipe selection writes the correct parameters.
  • Maintain operator access restrictions.
  • Avoid unnecessary changes to the production PLC program.
  • Preserve the ability to restore the original HMI configuration if acceptance fails.

Example migration record

PLC communication Existing approved driver and connection Driver and connection tested
Production count Existing device and display format Value and scaling compared
Alarms Existing alarm definitions Trigger, message, and acknowledgement tested
Recipes Existing recipe configuration Representative approved recipes verified
User permissions Existing access levels All required access levels tested

15. Documentation and maintenance handover

A migration is incomplete until the resulting system can be maintained by another engineer without depending on the person who performed the conversion.

Retain the following records:

  • Original GOT1000 project and backup.
  • Converted GOT2000 project and final released revision.
  • Source and target model numbers.
  • Engineering software and firmware versions.
  • Conversion warnings and their resolutions.
  • PLC communication settings and device mapping.
  • Screen, alarm, recipe, trend, and security test results.
  • Transfer records and final project identification.
  • FAT and SAT results.
  • Updated drawings, wiring information, and installed-base records.
  • Approved rollback procedure.
  • Required passwords and access information stored under plant security procedures.
  • Spare-part details and compatibility information.
  • Training or handover notes for maintenance personnel.

Store backups in approved locations with suitable access controls and revision management. Do not store passwords in plain-text project notes or general-purpose maintenance logs.

16. Migration checklist

Project preparation

  • Exact source and target HMI models identified.
  • Original editable project recovered.
  • Original project preserved unchanged.
  • Software versions and supported conversion path verified.
  • PLC program revision and communication settings recorded.
  • Required HMI functions inventoried.

Conversion and validation

  • Target model selected correctly.
  • Conversion warnings reviewed and resolved or formally accepted.
  • Screen layouts and fonts checked.
  • PLC addresses and data types verified.
  • Scripts and special functions tested.
  • Alarm and recipe behavior verified.
  • Project validated using the target engineering software.

Transfer and commissioning

  • Existing target configuration backed up where applicable.
  • Correct project revision transferred.
  • HMI startup verified.
  • PLC communication verified.
  • FAT completed as required.
  • SAT completed as required.
  • Machine safety functions verified through the applicable procedures.
  • Rollback method confirmed.
  • Final documentation and approvals completed.

17. Interview questions and technical answers

1. What is the difference between conversion and transfer?

Conversion adapts the source project to the target HMI's supported project format and features. Transfer installs the validated project on the physical target HMI.

2. Can every GOT1000 project be converted directly to GOT2000?

No. The supported path depends on the source model, project format, target model, and engineering software version. Some functions may require manual reconfiguration or redesign.

3. Why is a successful conversion not enough?

Conversion can leave unsupported objects, changed layouts, incorrect device mappings, or altered function behavior. The converted project must be validated and tested against the original requirements.

4. Does replacing GOT1000 with GOT2000 require changing the PLC program?

Not necessarily. If the target HMI can use the existing PLC communication protocol, addresses, and required functions, the PLC program may remain unchanged. Any required PLC modification must be assessed and tested separately.

5. Why must recipes be checked separately?

Recipes contain groups of process parameters. Incorrect mapping, scaling, or transfer direction can result in the wrong settings being applied to a machine.

6. What is the difference between FAT and SAT?

FAT verifies the migrated project in a controlled test environment. SAT verifies the installation and behavior in the actual machine environment.

7. What should be backed up before migration?

At minimum, the original editable HMI project, available runtime backup, communication settings, target configuration, relevant PLC backup, and supporting engineering records.

8. What is the most important condition before releasing the replacement HMI?

All critical functions must pass the approved acceptance criteria, the machine must be in a safe operating condition, the rollback method must be available, and the required personnel must authorize release.

9. How should unsupported objects be handled?

Identify the affected function, determine whether a supported equivalent exists, implement the approved replacement, and test both its normal behavior and relevant fault conditions.

10. Why preserve the original GOT1000 project after migration?

It provides traceability, supports comparison during troubleshooting, and helps recover the previous configuration if a migration defect is discovered later.

18. Final engineering principle

Treat a GOT1000-to-GOT2000 migration as a controlled engineering change rather than a simple HMI replacement. Preserve the original project, verify compatibility, document every meaningful conversion change, test PLC communication and operator functions, retain rollback capability, and release the new panel only after the required acceptance checks are complete.
