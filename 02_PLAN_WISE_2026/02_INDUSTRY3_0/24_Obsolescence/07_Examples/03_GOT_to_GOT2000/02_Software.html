1. Purpose and Scope

Migrating a Mitsubishi GOT1000 HMI project to a GOT2000 HMI requires more than opening the old project and pressing Save As. The project must be converted into a format supported by the target engineering software, configured for the new GOT model, and verified for screen behavior, PLC communication, device addresses, alarms, recipes, data logging, security, and other application functions.

The objective is to preserve the original machine operation while taking advantage of the new HMI hardware without introducing production risks.

Typical migration scenario:

  • Existing HMI: Mitsubishi GOT1000.
  • Replacement HMI: Mitsubishi GOT2000.
  • Legacy engineering software: GT Designer2 or a version appropriate for the original project.
  • Target engineering software: GT Designer3, supplied through the applicable GT Works3 package.
  • Connected equipment: PLC, VFDs, servo drives, robots, CNC equipment, barcode readers, or other supported devices.

The exact conversion path depends on the original GOT model, target GOT model, source project format, engineering software version, firmware, and required communication drivers. Not every GOT1000 feature has a direct one-to-one equivalent on every GOT2000 model.

2. GT Designer2, GT Designer3, and Project Compatibility

GT Designer is the engineering environment used to create and maintain Mitsubishi GOT projects. GT Designer2 is associated with many legacy GOT1000 projects, while GT Designer3 is used for GOT2000 engineering.

Item GT Designer2 / legacy project GT Designer3 / GOT2000 project
Primary role Create or maintain supported legacy GOT projects Configure supported GOT2000 models and projects
Project compatibility Depends on the original GOT family and software version Depends on GT Designer3 version and supported conversion paths
Target hardware Original supported GOT1000 models Selected supported GOT2000 model
Screen layout Based on the original model's display characteristics Must be checked against the target resolution and screen dimensions
Communication Original driver and port configuration Must be confirmed for the target GOT and connected equipment
Special functions Depends on legacy project and GOT capabilities Must be checked for support and behavior on the target model
Migration risk Missing or unavailable original source data Conversion warnings, unsupported objects, altered behavior, or configuration differences

Important distinction: A project that opens successfully is not necessarily a project that operates correctly. Opening, converting, compiling, transferring, and functionally validating are separate activities.

3. Understand the Original Project Before Conversion

Before modifying the project, establish exactly what is running on the existing machine.

3.1 Identify the Existing Configuration

Record the following information:

  • Complete GOT model number and display resolution.
  • GOT firmware or OS version, where available.
  • GT Designer software version used to create or maintain the project.
  • Project file location, file format, and last known approved revision.
  • PLC manufacturer, CPU model, and firmware.
  • PLC communication driver and protocol.
  • Communication interface, cable type, port, station number, and network parameters.
  • Number of screens, windows, pop-ups, and navigation paths.
  • Alarm configuration, trend graphs, data logging, recipes, security levels, and scripts.
  • External devices, such as barcode readers, printers, or supported third-party controllers.
  • Special GOT functions and any installed options or storage media.

3.2 Obtain a Reliable Source Project

Use the approved engineering project from the maintenance or controls repository whenever possible. If the project must be retrieved from the existing GOT, verify whether the unit and software support the required upload or project-transfer operation.

A running GOT does not guarantee that its complete editable engineering project can be recovered. Depending on the transfer method and project configuration, source comments, library data, editable objects, scripts, or other engineering information may not be available in a usable form.

Keep these items separately:

  1. Original editable project.
  2. Backup of the existing GOT configuration, where supported.
  3. Screenshots or records of critical screens and settings.
  4. PLC program backup and relevant communication configuration.
  5. Approved machine operating procedure and functional test records.

Never treat a runtime backup as automatically equivalent to the original engineering source.

4. Preserve the Original Project and Establish Revision Control

Before conversion, create a controlled copy of the original project.

Example folder structure:

GOT_MIGRATION/
    01_ORIGINAL_GOT1000/
    02_CONVERSION_WORKING/
    03_GOT2000_TARGET/
    04_TEST_REPORTS/
    05_APPROVED_RELEASE/
    06_ROLLBACK_BACKUP/

Use clear filenames that identify the machine, GOT model, revision, and purpose.

MachineA_GOT1000_Original_Rev03
MachineA_GOT2000_Conversion_Working_Rev01
MachineA_GOT2000_FAT_Approved_Rev01

The original project should remain unchanged. Conversion experiments, object replacements, and target-specific edits must be performed in a separate working copy.

Record every material change, including the reason for the change, the affected screen or function, the test performed, and the result.

5. Prepare the Target GOT2000 Project

Before converting, identify the exact replacement model. Selecting a vaguely similar GOT model is not a valid engineering shortcut.

Check:

  • Supported display resolution and orientation.
  • Available communication interfaces.
  • Ethernet, serial, and USB capabilities for the exact model.
  • Supported storage media and external-device functions.
  • Available memory and performance limitations.
  • Touchscreen and front-panel characteristics.
  • Required firmware or OS compatibility.
  • Support for the required PLC driver and communication protocol.
  • Availability of any required options or licenses.

Use the target model's applicable hardware and software manuals. GOT2000 product families differ, so features available on one GT27 or GT25 model should not automatically be assumed available on every GT23, GT21, GS21, or other model.

6. General GT Designer Conversion Procedure

The exact menu labels and conversion commands vary with software version. Follow the documented conversion path for the installed GT Designer2 and GT Designer3 versions.

  1. Open the original project using a compatible legacy engineering environment. Confirm that the project is readable and that the original screens and settings are present.
  2. Run the supported conversion or project migration procedure. Use the applicable GT Designer3 conversion workflow rather than assuming the legacy project can be used directly.
  3. Select the exact target GOT2000 model. Verify the full model designation.
  4. Review conversion warnings and errors. Record every unsupported object, replaced function, missing resource, and configuration change.
  5. Save the converted project under a new filename. Do not overwrite the original.
  6. Inspect project-wide settings. Check screen size, display settings, communication drivers, device assignments, security, storage, and supported options.
  7. Inspect every screen and window. Look for altered alignment, clipped text, missing graphics, changed object behavior, and invalid references.
  8. Reconfigure target-specific features. Replace unsupported functions only after determining their original purpose and required behavior.
  9. Compile or verify the project. Resolve errors and investigate warnings instead of dismissing them.
  10. Perform offline review and controlled functional testing. Successful conversion is only the beginning of validation.

A conversion log should identify each warning, its impact, the corrective action, and the test evidence used to close it.

7. Screen Resolution, Layout, and Object Compatibility

The GOT2000 display may differ from the original GOT1000 in resolution, usable display area, object rendering, or supported graphical functions. Even when the physical panel dimensions are similar, screen layout must be verified independently.

7.1 Screen Layout Checks

Inspect every screen for:

  • Objects extending beyond screen boundaries.
  • Text that wraps, overlaps, or becomes truncated.
  • Buttons that are too small or too close together.
  • Misaligned graphics, labels, numeric displays, and indicators.
  • Changed font size, font availability, or text spacing.
  • Incorrect pop-up window positions.
  • Missing background images or library graphics.
  • Objects that obscure alarms, machine status, or operator instructions.
  • Touch areas that no longer match the visible button graphics.

7.2 Object Compatibility

Object or function Conversion risk Required verification
Push buttons Action or touch behavior may differ Verify the actual PLC command and interlocks
Bit lamps Incorrect device assignment or display state Test ON, OFF, and communication-loss behavior
Numeric displays Data type, signedness, or formatting differences Test minimum, maximum, zero, and invalid values
Numeric input Entry limits or write behavior may change Verify permitted range and PLC-side validation
Bar graphs Scaling or limits may be incorrect Compare displayed values with PLC values
Trend graphs Sampling or history settings may differ Verify live values, time axis, and stored history
Alarm displays Trigger, acknowledgment, or history behavior may change Test active, cleared, acknowledged, and historical alarms
Recipe controls Storage or transfer configuration may differ Verify selection, transfer, confirmation, and error handling
Security objects Access restrictions may differ Test every intended user level
Scripts and expressions Functions or syntax may not be fully compatible Review conversion messages and validate actual execution
Pop-up windows Size, placement, or navigation may change Test opening, closing, layering, and screen transitions

Do not validate only the screens used during normal operation. Maintenance screens, manual-mode screens, recipe screens, alarm history, password pages, and rarely used diagnostic windows can contain critical machine functions.

8. PLC Device Addresses and Communication Configuration

A correctly displayed HMI screen can still be unsafe or ineffective if it reads or writes the wrong PLC device. Communication configuration is therefore one of the highest-priority conversion checks.

8.1 Verify the PLC Connection

Confirm all of the following:

  • PLC manufacturer and CPU model.
  • Correct communication driver for the target GOT and software version.
  • Correct PLC station, network, and routing configuration.
  • Ethernet IP address, subnet, port, and other required parameters.
  • Serial communication settings, where applicable.
  • Correct interface and cable type.
  • Correct PLC device addresses and supported data types.
  • Correct read/write permissions and command-handshake behavior.
  • Appropriate timeout and communication-error handling.

For a Mitsubishi PLC, the project may reference devices such as D100, M100, X10, or Y10. These are examples only. Device notation, address availability, and behavior depend on the PLC family, CPU, and configured driver.

For non-Mitsubishi PLCs, confirm the supported protocol and driver for the exact GOT model and GT Designer3 version. Do not assume that a driver supported by the original GOT1000 is automatically available or behaves identically on the replacement.

8.2 Verify Data Types and Scaling

Check the interpretation of each important value:

  • Bit versus word.
  • Signed versus unsigned integer.
  • 16-bit versus 32-bit value.
  • Floating-point representation.
  • Word order and byte order where relevant.
  • Decimal placement and engineering-unit scaling.
  • Indirect addressing and index registers.
  • Multiword data consistency.
  • PLC-side limits and command validation.

Example: a PLC stores temperature as an integer representing tenths of a degree.

\[ T\_{\text{display}}=\frac{D100}{10} \]

If D100 = 253, the HMI should display 25.3 °C. If conversion changes the numeric format or scaling, the HMI might display 253 °C even though communication is functioning normally.

8.3 Verify Command Handshakes

An HMI command should not be considered successful merely because the operator touched a button.

Example:

Operator presses START
    ↓
HMI writes the start request
    ↓
PLC checks mode, interlocks, and permissives
    ↓
PLC accepts or rejects the request
    ↓
PLC updates the acknowledgement and machine state
    ↓
HMI displays the actual result

The exact sequence must follow the existing machine control design. Preserve PLC interlocks and safety logic. An HMI conversion must not bypass safeguards by changing command addresses or substituting direct output writes for the original handshake.

9. Special Functions That Require Separate Validation

9.1 Alarms and Events

Check:

  • Alarm trigger devices and conditions.
  • Alarm messages and priorities.
  • Active-alarm and historical-alarm behavior.
  • Acknowledgment and reset operations.
  • Alarm timestamps and history retention.
  • Alarm display filters and navigation.
  • Behavior when PLC communication is lost.

Test the entire alarm lifecycle, not merely whether the message appears.

9.2 Trends and Data Logging

Check:

  • Source devices and data types.
  • Sampling interval and trigger conditions.
  • Historical retention and storage capacity.
  • Time and date settings.
  • Graph scaling and engineering units.
  • Data export or retrieval method.
  • Behavior when storage is full or unavailable.
  • Recovery after power loss or restart, where required.

A trend graph showing live data does not prove that historical data is being saved correctly.

9.3 Recipes

Check:

  • Recipe names, identifiers, and record counts.
  • Parameter-to-PLC-device mapping.
  • Minimum and maximum permitted values.
  • Selection and transfer sequences.
  • Operator confirmation requirements.
  • Write permissions and recipe access control.
  • Behavior when a transfer fails or is interrupted.
  • Validation of machine-compatible parameter combinations.

For production equipment, confirm that a recipe cannot accidentally load parameters intended for another product or machine configuration.

9.4 Security and Operator Permissions

Test each configured access level, including:

  • Operator.
  • Maintenance technician.
  • Engineer.
  • Administrator, if used.

Verify screen access, protected writes, password handling, automatic logout, and any required audit or access-history functions. Do not assume that converted security settings retain identical behavior without testing.

9.5 Scripts, External Devices, and Special Options

Review scripts, indirect device references, barcode interfaces, printers, remote monitoring, transparent communication, external storage, and other special functions present in the original project.

Availability depends on the target model, installed software version, supported options, and connected hardware. Any unsupported function requires an engineered replacement or a documented decision to remove it. Replacing an object visually without recreating its operational behavior is not a complete conversion.

10. Compilation, Transfer, and Runtime Verification

10.1 Project Verification

Before transferring the project:

  • Confirm the target GOT model.
  • Resolve compilation errors.
  • Review every conversion warning.
  • Confirm that required resources are present.
  • Verify PLC driver and communication settings.
  • Inspect all screens and pop-up windows.
  • Check project options and storage configuration.
  • Save the verified target project and record its revision.

A warning should be closed only after its meaning and operational impact have been assessed.

10.2 Transfer Preparation

Before downloading to the GOT:

  1. Obtain authorization for the maintenance or engineering activity.
  2. Back up the current GOT project and configuration where supported.
  3. Confirm that the correct replacement panel is connected.
  4. Confirm the transfer method and compatible cable or network.
  5. Check the target GOT firmware and project compatibility.
  6. Prevent unintended PLC writes or machine movement during testing.
  7. Confirm the rollback procedure and availability of the original panel or project.

Use the transfer procedure specified for the exact GOT model and GT Designer3 version. USB, Ethernet, serial, and removable-media methods are not universally available across every model.

10.3 Initial Runtime Checks

After transfer, verify:

  • The GOT starts without unexpected errors.
  • The correct project and startup screen load.
  • Screen navigation and touch input work.
  • PLC values update correctly.
  • Communication errors are detected and displayed appropriately.
  • Numeric input and command buttons behave as intended.
  • Alarms, trends, recipes, and security work correctly.
  • Power cycling does not unexpectedly lose required configuration or data.

Do not test production commands on an operating machine unless the test has been risk-assessed and specifically authorized.

11. FAT and SAT Test Plan

FAT means Factory Acceptance Test. SAT means Site Acceptance Test. For an HMI replacement, the FAT can be performed offline or on a controlled test setup, while the SAT confirms correct operation in the installed machine environment.

Test ID Test Expected result Evidence
T01 Startup and initial screen Correct project loads without unexpected errors Startup record
T02 Screen navigation All required screens and windows open correctly Screen checklist
T03 Touch operation Buttons respond in the intended locations Functional test record
T04 PLC data display Values match known PLC values Address comparison
T05 Numeric entry Valid inputs are accepted and invalid inputs are rejected Input test record
T06 Machine commands PLC accepts commands only when permitted Handshake and interlock test
T07 Alarm generation Correct message and priority appear Alarm test record
T08 Alarm acknowledgment Acknowledgment and clearing follow the designed logic Alarm lifecycle record
T09 Trend and logging Correct values, sampling, timestamps, and retention Trend and data record
T10 Recipe transfer Correct parameters transfer with validation Recipe test record
T11 Security Unauthorized access and writes are blocked Access test record
T12 Communication loss Fault is detected and recovery is handled correctly Communication test record
T13 Restart and power cycle Required settings and data behave as specified Restart test record
T14 External-device functions Supported devices operate correctly Interface test record
T15 Performance Screen updates and operator response meet requirements Timing observations

Every test should have a pass/fail result, actual observation, corrective action if needed, and approval where required. A test marked as passed without evidence is merely optimism wearing a maintenance form.

12. Common Conversion Problems and Troubleshooting

Symptom Possible cause Corrective action
Project cannot be opened Unsupported source format or incompatible software version Identify the source format and use the documented conversion path
Target model is unavailable Incorrect software version or unsupported model selection Verify GT Designer3 version and model support
Objects are missing Unsupported object or unavailable resource Inspect conversion warnings and replace the function appropriately
Text or graphics are misaligned Resolution, font, or layout differences Correct layout and verify on the target display
PLC values remain unchanged Wrong driver, address, network settings, or connection Check communication configuration and compare with PLC values
Displayed numbers are incorrect Wrong data type, signedness, or scaling Verify the PLC data representation and HMI formatting
Buttons appear to work but machine does not respond Wrong command address, missing handshake, or PLC interlock Trace the command through the PLC logic and acknowledgement
Alarms do not appear Incorrect trigger mapping or changed alarm configuration Verify the trigger device, condition, and alarm settings
Historical data is missing Storage configuration, sampling, or retention mismatch Check logging configuration and storage support
Recipe transfer produces incorrect parameters Mapping, data type, or record mismatch Compare recipe fields against PLC devices and approved values
Protected screens behave differently Security configuration or access-level differences Reconfigure and test each required access level
External device fails Driver, interface, or target-model limitation Confirm supported device compatibility and connection settings
Project works offline but fails on the machine Runtime configuration, hardware, network, or firmware mismatch Compare the engineering configuration with the installed equipment

13. Practical Industrial Example

Consider a machine using a GOT1000 HMI connected to a Mitsubishi PLC. The operator can select an automatic cycle, view cylinder sensors, acknowledge alarms, enter a recipe, and monitor cycle time.

The GOT1000 is to be replaced with a supported GOT2000 model.

13.1 Before Conversion

Record the following:

  • Automatic-mode status and cycle-start handshake.
  • Cylinder extended and retracted sensor addresses.
  • Alarm trigger devices and acknowledgment sequence.
  • Recipe parameter addresses and valid limits.
  • Cycle-time data source and engineering units.
  • Maintenance screen access levels.
  • PLC communication settings and the approved original project revision.

13.2 During Conversion

Convert a separate copy of the legacy project using the documented engineering workflow. Select the exact GOT2000 target model, review conversion warnings, inspect all screens, and verify every critical device reference.

For example, suppose the original screen displays:

Function Example PLC reference Required behavior
Automatic mode M100 Displays the actual automatic-mode status
Cycle start request M110 Requests a cycle through the existing PLC logic
Cylinder extended sensor X10 Displays the actual input state
Recipe parameter D200 Displays or edits the approved parameter
Cycle time D300 Displays the correctly scaled cycle time

These addresses are illustrative only and must be replaced with the actual machine addresses. Their meanings must be confirmed from the PLC program and electrical documentation.

13.3 After Conversion

  • Confirm that all screen objects reference the intended PLC devices.
  • Compare displayed values with the PLC online monitor.
  • Verify that cycle start is rejected when required permissives are absent.
  • Simulate or safely test sensor changes under the approved procedure.
  • Trigger and acknowledge alarms.
  • Load an approved test recipe and compare the resulting PLC values.
  • Verify cycle-time scaling.
  • Test maintenance access permissions.
  • Record results and retain the approved project and rollback backup.

The conversion is complete only when the target HMI reproduces the required machine behavior and all identified differences have been resolved or formally accepted.

14. Engineering Checklist

Source and software

  • Original editable project preserved.
  • Original GOT model and software version recorded.
  • Target GOT2000 model confirmed.
  • GT Designer3 version and conversion path verified.
  • Original project remains unchanged.
  • Conversion warnings and errors documented.

Project functionality

  • All required screens and pop-ups checked.
  • Fonts, graphics, and touch areas verified.
  • PLC addresses and data types verified.
  • Communication drivers and network settings verified.
  • Command handshakes and interlocks preserved.
  • Alarms, trends, recipes, and logging tested.
  • Security and special functions tested.
  • External-device compatibility confirmed.

Transfer and release

  • Target project compiles or passes the applicable project verification.
  • Transfer procedure and machine safeguards confirmed.
  • FAT and SAT results recorded as applicable.
  • Backup and rollback procedure verified.
  • Approved revision stored in the controlled repository.
  • Final project and change records handed over to maintenance.

15. Interview Questions and Answers

Q1. Can a GOT1000 project be used directly on a GOT2000?

Not universally. The project must follow the supported conversion path for the source format, engineering software version, and target model. Converted objects and settings require verification.

Q2. What is the difference between project conversion and project transfer?

Conversion adapts the engineering project to the target environment. Transfer downloads the prepared project to the GOT. Successful transfer does not prove that the application operates correctly.

Q3. Why must the target GOT model be selected accurately?

Different models can have different resolutions, interfaces, memory capabilities, supported functions, and firmware requirements. Incorrect selection can cause incompatibility or incorrect runtime behavior.

Q4. What is the highest-risk software issue during an HMI migration?

There is no universal single highest-risk issue. Incorrect PLC addressing, altered command behavior, missing interlocks, and incorrect recipe or parameter handling can directly affect machine operation and therefore require particular attention.

Q5. How can an engineer verify that the converted project is correct?

Compare the original and converted projects, resolve conversion warnings, inspect all screens and device references, verify PLC communication, execute a documented functional test plan, and preserve evidence of the results.

Q6. What should happen if an original HMI function is unsupported on the target model?

Determine the function's purpose, identify an approved compatible alternative, implement it in the target project, and validate equivalent behavior. If equivalence cannot be demonstrated, document the limitation and obtain the required engineering approval before release.

Q7. Why should the original project never be overwritten during conversion?

The original provides the reference for comparison and the basis for rollback. Keeping it intact also allows engineers to investigate differences and recover if the conversion or deployment fails.
