1. Definition and Purpose

PLC communication is the exchange of data between a Programmable Logic Controller (PLC) and other devices, systems, or engineering tools through supported physical interfaces and communication protocols.

Communication enables a PLC to exchange commands, status information, measurements, alarms, diagnostic data, configuration information, and production data with equipment across an industrial automation system.

Typical communication partners include:

  • Human-Machine Interfaces (HMIs).
  • Supervisory Control and Data Acquisition (SCADA) systems.
  • Variable Frequency Drives (VFDs).
  • CNC controllers.
  • Remote I/O stations.
  • Robots and robot controllers.
  • Other PLCs.
  • Industrial Ethernet switches.
  • Industrial PCs and data-acquisition systems.
  • Manufacturing execution systems and historians.
  • Engineering workstations and programming software.

Communication is essential when a machine must coordinate multiple controllers or when production data must be collected for monitoring, diagnostics, quality, and traceability.

2. Basic Communication Architecture

A typical industrial automation communication architecture may contain several layers.

Enterprise and Business Systems
          ↕
MES / Historian / Reporting / Database
          ↕
SCADA / Industrial PC / Data Gateway
          ↕
Industrial Ethernet Network
          ↕
PLC / CNC / Robot Controller / VFD / Remote I/O
          ↕
Physical I/O and Field Devices

This is a conceptual architecture, not a mandatory network topology. Some devices communicate directly with each other, while others exchange data through gateways or supervisory systems.

For example, an Allen-Bradley ControlLogix PLC may exchange data with remote I/O over EtherNet/IP, provide status information to an HMI, and send selected production data through Node-RED to a SQL database and Grafana dashboard.

Each connection has its own physical requirements, protocol, configuration, and failure modes.

3. Why PLC Communication Is Required

Purpose Example
Operator control HMI sends a permitted start request to a PLC
Drive control PLC sends a speed reference to a VFD
Status monitoring VFD reports ready, running, and fault status
Remote I/O PLC reads sensor states from a remote I/O rack
Machine coordination PLC exchanges handshake signals with a CNC

Production monitoring PLC provides cycle count and machine status to SCADA
Traceability Controller data is recorded with a part or batch identifier
Diagnostics Engineering software reads controller status and fault information

Communication does not replace every hardwired signal. Some signals remain hardwired because of response-time, diagnostic, compatibility, or safety requirements.

4. Physical Interface Versus Protocol

These two concepts must be distinguished.

A physical interface defines how devices are electrically or physically connected. A communication protocol defines how information is exchanged and interpreted.

Physical interface or medium Example protocols or uses
Ethernet copper cable EtherNet/IP, PROFINET, Modbus TCP
Fiber-optic Ethernet Industrial Ethernet over optical links
RS-232 serial interface Supported serial protocols and vendor interfaces
RS-485 serial interface Modbus RTU and other supported serial protocols
USB Programming, configuration, or service connection
Proprietary backplane Internal communication between PLC modules
Dedicated fieldbus cable PROFIBUS and other supported fieldbus systems

Ethernet is not itself the same thing as EtherNet/IP or PROFINET. Ethernet describes the underlying network technology, while those industrial protocols define additional communication behavior.

Similarly, RS-485 defines electrical signaling characteristics, not a complete application protocol.

A cable can be physically connected while communication still fails because the protocol, address, baud rate, network configuration, or device settings are incorrect.

5. Communication Types

5.1 Serial Communication

Serial communication transfers information sequentially over a serial interface.

Common industrial interfaces include RS-232 and RS-485.

Typical applications include:

  • Legacy PLC connections.
  • Instrument communication.
  • Barcode readers.
  • Older VFD interfaces.
  • Weighing systems.
  • Serial gateways.

RS-232 is commonly used for point-to-point connections over relatively short distances according to the equipment specification.

RS-485 supports differential signaling and can support multidrop networks when the devices and protocol are designed for that arrangement.

Important serial parameters include:

  • Baud rate.
  • Data bits.
  • Parity.
  • Stop bits.
  • Device address.
  • Wiring polarity.
  • Termination.
  • Biasing.
  • Protocol-specific timing.

For example, a Modbus RTU device configured for 9,600 baud, even parity, and one stop bit may fail to communicate with a master configured for a different serial format.

The exact settings must match the devices and network design.

5.2 Industrial Ethernet

Industrial Ethernet uses Ethernet-based networking for industrial control and data exchange.

Advantages include:

  • High data throughput.
  • Integration with industrial PCs and supervisory systems.
  • Flexible network topology.
  • Support for diagnostics and device configuration.
  • Integration with modern PLCs, drives, robots, and remote I/O.

Common industrial Ethernet protocols include:

  • EtherNet/IP.
  • PROFINET.
  • Modbus TCP.
  • OPC UA over supported network transports.
  • Manufacturer-specific Ethernet protocols.

The protocol must be supported and correctly configured on both communicating devices or through a compatible gateway.

5.3 Fieldbus Communication

Fieldbus systems provide communication between controllers and distributed automation equipment.

Examples include PROFIBUS and other manufacturer- or industry-specific fieldbus systems.

Fieldbus systems may use specialized cabling, connectors, addressing, termination, and diagnostic procedures.

A legacy fieldbus installation may continue to operate reliably for years, but maintenance personnel should understand its configuration and replacement constraints.

5.4 Backplane Communication

In modular PLC systems, the CPU communicates with I/O and specialty modules through the manufacturer's internal backplane or module bus.

This communication is separate from the external plant network.

A CPU may communicate normally over Ethernet while a local I/O module has a backplane, configuration, or hardware fault.

6. Common Industrial Communication Protocols

Protocol Typical application Important characteristic

Protocol availability depends on the exact CPU, communication module, firmware, licensing, and configuration. A protocol's presence in a manufacturer's product range does not mean every PLC model supports it.

7. PLC Communication Parameters

Communication parameters vary by protocol, but several categories appear repeatedly.

7.1 Device Identity

Each device must be identifiable within the communication system.

Depending on the protocol, this may involve:

  • IP address.
  • MAC address.
  • Device name.
  • Node address.
  • Station number.
  • Unit identifier.
  • Serial slave address.
  • Controller or device path.

Incorrect or duplicate addressing can prevent communication or cause data to be exchanged with the wrong device.

7.2 Network Parameters

For IP-based networks, check:

  • IP address.
  • Subnet mask.
  • Default gateway, where required.
  • VLAN configuration, where used.
  • Routing.
  • Firewall rules.
  • Port availability.
  • Duplicate IP addresses.
  • Network segmentation.

A default gateway is not necessarily required for communication between devices on the same subnet. It is needed when communication must cross an IP network boundary and the routing design requires it.

7.3 Serial Parameters

For serial communication, check:

  • Baud rate.
  • Data bits.
  • Parity.
  • Stop bits.
  • Electrical interface.
  • Device address.
  • Cable polarity.
  • Termination and biasing.
  • Master/slave or client/server roles, as applicable.

7.4 Protocol Parameters

Depending on the protocol, additional settings may include:

  • Connection type.
  • Requested packet interval.
  • Update period.
  • Timeout.
  • Retry count.
  • Watchdog.
  • Produced/consumed data configuration.
  • Input/output assembly or data mapping.
  • Register addresses.
  • Data types and byte order.
  • Device name and controller configuration.
  • Security certificates and authentication.

Do not change parameters randomly to see what works. Compare the configured values with the actual device settings and approved project documentation.

8. IP Addressing in PLC Networks

An IP address identifies a network interface within an IP network.

For example, a PLC might use 192.168.10.10, while an HMI uses 192.168.10.20.

If both use a compatible subnet configuration, they may communicate directly, provided the physical network, protocol, and access configuration are correct.

A duplicate IP address can cause intermittent or confusing behavior because two devices may respond for the same address.

Example

Device Example IP address Purpose
PLC 192.168.10.10 Machine control
HMI 192.168.10.20 Operator interface
Engineering PC 192.168.10.30 Programming and diagnostics
Data gateway 192.168.10.40 Data collection

These are illustrative addresses, not recommended defaults for every plant.

Before connecting an engineering laptop, verify the machine's approved addressing plan. Connecting a device with a duplicate or conflicting address can disrupt production.

9. Communication Models

9.1 Client-Server

In a client-server model, a client requests data or a service from a server.

Examples include a supervisory application requesting data from a supported OPC UA server or an application querying a database.

The server may be hosted by a PLC, gateway, industrial PC, or separate server, depending on the system.

9.2 Producer-Consumer

In a producer-consumer model, one device produces data and one or more configured consumers receive it.

This model is used in some industrial protocols, including EtherNet/IP.

The data exchange may be configured for periodic or event-related behavior, depending on the implementation.

9.3 Master-Slave and Client-Server Terminology

Legacy protocols commonly use master/slave terminology, while newer systems often use client/server or controller/device terminology.

The roles determine who initiates requests, who responds, and how data exchange is scheduled.

Use the terminology and role definitions specified by the actual protocol.

9.4 Cyclic and Acyclic Data

Cyclic communication transfers data at regular intervals or according to a configured update mechanism.

Typical examples include:

  • Remote I/O states.
  • Drive status words.
  • Drive command words.
  • Periodic control data.

Acyclic communication transfers data on demand or when required rather than as part of a continuously repeated cyclic data exchange.

Typical examples include:

  • Device parameters.
  • Diagnostic records.
  • Configuration information.
  • Non-periodic identification data.

A system may use both types of communication simultaneously.

10. Communication Timing and Performance

Communication performance is important when control logic depends on data received from another device.

10.1 Update Time

Update time is the interval at which data is refreshed or exchanged under a particular communication configuration.

An update interval that is too slow may cause delayed status updates or control responses.

An unnecessarily aggressive update interval may increase network load and device processing requirements.

10.2 Latency

Latency is the time taken for information to travel through the relevant communication path.

It may include device processing, network transmission, switching, queuing, and application handling.

10.3 Timeout

A timeout occurs when expected communication or a response is not received within the configured period.

Possible causes include:

  • Network interruption.
  • Device overload.
  • Incorrect timeout configuration.
  • Slow device response.
  • Protocol mismatch.
  • Excessive traffic.
  • Faulty device or gateway.

10.4 Jitter

Jitter is variation in message timing or arrival intervals.

It matters when a control application expects data at consistent intervals.

10.5 Watchdog

A watchdog monitors whether expected activity occurs within an allowed interval.

Depending on the device and configuration, a watchdog may trigger a fault, mark data invalid, or initiate a defined fallback response.

The application must specify what happens when communication is lost. Continuing to use stale data without detecting its age can create dangerous or incorrect machine behavior.

11. PLC Communication With an HMI

An HMI exchanges data with the PLC to display machine status and accept operator commands.

Typical data includes:

  • Machine mode.
  • Cycle status.
  • Alarm and fault information.
  • Sensor states.
  • Setpoints.
  • Production counters.
  • Recipe values.
  • Operator commands.

A communication failure may result in frozen values, stale alarms, unavailable commands, or an HMI communication warning.

Diagnostic approach

  1. Check HMI power and communication indicators.
  2. Verify the physical link and switch port.
  3. Confirm PLC and HMI addresses.
  4. Check protocol configuration and controller path.
  5. Inspect HMI communication diagnostics.
  6. Confirm that the PLC is executing and the relevant data tags are valid.
  7. Check whether other devices on the same network are affected.

An HMI can display stale data even after communication has failed. A displayed value should not be assumed current unless the application indicates communication quality or data freshness.

12. PLC Communication With a VFD

A PLC may communicate with a VFD over an industrial network or use hardwired signals.

Network-based control may exchange:

  • Run and stop commands.
  • Speed references.
  • Direction commands.
  • Drive status.
  • Actual speed or frequency.
  • Current and torque data.
  • Fault codes.
  • Ready and running states.

The communication data map and drive parameter configuration must match the PLC project.

Example: Drive Runs Locally but Not From the PLC

Possible causes include:

  • The drive is configured for local control.
  • The drive command source is set incorrectly.
  • The network connection is unavailable.
  • The PLC output data is mapped incorrectly.
  • The drive has an active fault or missing permissive.
  • The communication watchdog has expired.
  • The PLC program is not issuing the expected command.

Check the drive's command source, reference source, status word, and fault diagnostics before assuming the network cable is defective.

Safety note: Communication commands must not bypass the drive's intended safety functions. Safe Torque Off and other safety functions must be implemented and validated according to the drive and machine safety design.

13. PLC Communication With Remote I/O

Remote I/O allows field signals to be connected at a location away from the main PLC rack.

A remote I/O station usually requires:

  • Suitable power supply.
  • Communication interface.
  • Correct network connection.
  • Device identification and configuration.
  • Compatible I/O modules.
  • Correct data mapping.

If a remote I/O station disappears, check the station power, network link, device status, configuration, and controller diagnostics.

A network fault may affect multiple remote stations, while a local power or module fault may affect only one station.

Do not assume that all missing I/O points indicate failed sensors. The signals may be unavailable because the remote I/O adapter or network connection has failed.

14. PLC Communication With CNC and Robot Controllers

14.1 CNC Integration

A PLC and CNC may exchange machine sequencing information through hardwired I/O or a supported network interface.

Typical information includes:

  • Machine-ready state.
  • Cycle-start request.
  • Cycle-active state.
  • Cycle-complete indication.
  • Alarm status.
  • Door and fixture conditions.
  • Tool-change coordination.

The exact signal behavior is machine-builder-specific.

14.2 Robot Integration

A PLC may exchange handshake information with a robot controller.

Typical signals include:

  • Robot ready.
  • Program selected.
  • Start request.
  • Robot busy.
  • Cycle complete.
  • Robot fault.
  • Part-present confirmation.

Communication failures can interrupt the handshake and stop the machine sequence.

14.3 Troubleshooting Handshake Problems

When a robot or CNC sequence stops:

  1. Identify the last expected handshake state.
  2. Check the PLC's command and status tags.
  3. Check the corresponding robot or CNC signals.
  4. Verify network status or hardwired I/O.
  5. Review alarms on both controllers.
  6. Confirm that the expected transition conditions are satisfied.
  7. Check for stale data, timeouts, and incorrect data mapping.

Do not bypass a missing handshake or interlock simply to force the next sequence step.

15. Modbus RTU and Modbus TCP

Modbus is widely used for industrial data exchange.

15.1 Modbus RTU

Modbus RTU is commonly used over serial interfaces such as RS-485.

Important configuration items include:

  • Slave address.
  • Baud rate.
  • Parity.
  • Stop bits.
  • Register mapping.
  • Serial wiring polarity.
  • Termination and biasing where required.

The master/client sends a request, and the addressed device responds according to the protocol.

15.2 Modbus TCP

Modbus TCP uses Modbus messaging over TCP/IP, commonly over Ethernet.

Important configuration items include:

  • IP address.
  • TCP connectivity.
  • Server availability.
  • Unit identifier where relevant to the architecture.
  • Register addresses.
  • Function codes.
  • Data types and word order for multi-register values.

15.3 Register Mapping

A Modbus register address must be interpreted according to the device's documentation.

Documentation may use reference numbers such as 40001, while software interfaces may expect a zero-based offset such as 0. The correct mapping depends on the device and client implementation.

A common troubleshooting mistake is using the right register number in the wrong addressing convention.

15.4 Common Modbus Faults

  • Incorrect serial settings.
  • Wrong slave address.
  • Incorrect register offset.
  • Unsupported function code.
  • Incorrect data type.
  • Incorrect word order.
  • Missing server or slave response.
  • Wiring polarity or termination issue.
  • Incorrect TCP address or port.
  • Device register unavailable in the selected operating mode.

16. EtherNet/IP and CIP

EtherNet/IP is an industrial Ethernet protocol that uses the Common Industrial Protocol (CIP).

It is widely used in Allen-Bradley automation systems and compatible industrial devices.

Typical applications include:

  • PLC-to-remote-I/O communication.
  • PLC-to-VFD communication.
  • PLC-to-robot communication.
  • Data exchange between controllers.
  • Device diagnostics and configuration.

Important configuration elements may include:

  • Device IP address.
  • Electronic keying and device compatibility.
  • Controller I/O tree configuration.
  • Requested Packet Interval (RPI).
  • Connection parameters.
  • Assembly or data mapping.
  • Device firmware compatibility.
  • Network load and connection limits.

Troubleshooting

  • Verify the device is powered and reachable.
  • Check the controller's module or connection status.
  • Confirm the configured device type and revision.
  • Verify the IP address and network path.
  • Check connection parameters and RPI.
  • Inspect device and controller diagnostics.
  • Confirm that the expected input and output data are mapped correctly.

An EtherNet/IP device can respond to basic network diagnostics while its configured I/O connection remains unavailable. Network reachability alone does not prove that the cyclic control connection is healthy.

17. PROFINET

PROFINET is an industrial Ethernet communication system widely used with Siemens PLCs and compatible devices.

Typical applications include:

  • Distributed I/O.
  • Drives.
  • Field devices.
  • Industrial controllers.
  • Device diagnostics and topology information.

Important configuration elements may include:

  • Device name.
  • IP address.
  • Hardware configuration.
  • Device identity.
  • Network topology.
  • Controller-device relationship.
  • Real-time communication settings.
  • Device and module diagnostics.

For a PROFINET device that is unavailable, check power, cable and port status, device name, configuration, and diagnostic messages.

A device name mismatch can prevent the expected controller-device relationship even when the physical Ethernet link is working.

18. OPC UA and Industrial Data Integration

OPC UA is used for structured and secure data exchange between compatible industrial applications and devices.

Possible applications include:

  • PLC data to SCADA.
  • PLC data to an industrial gateway.
  • Machine data to a historian.
  • Data exchange between automation and higher-level applications.

Depending on the implementation, OPC UA can support structured data, information models, authentication, encryption, and certificates.

Common configuration issues include:

  • Incorrect endpoint URL.
  • Incorrect security policy or message-security configuration.
  • Authentication failure.
  • Certificate trust problems.
  • Incorrect namespace or node identifier.
  • User permissions.
  • Firewall restrictions.
  • Server not enabled or not available.

A successful TCP connection does not necessarily mean that the OPC UA session is established or that the requested node is readable.

19. Communication Fault Diagnosis

19.1 Establish the Scope

Determine whether the fault affects:

  • One signal.
  • One device.
  • One remote I/O station.
  • Several devices on one switch.
  • An entire subnet.
  • The PLC and its programming software.
  • A supervisory data path only.

The scope helps narrow the investigation.

19.2 Check Power and Physical Link

Inspect device power, network port indicators, cables, connectors, and switch status.

Where permitted, verify the device supply voltage and inspect any fault LEDs.

19.3 Verify Addressing

Check IP addresses, subnet masks, device names, node addresses, and duplicate-address conditions.

Compare the actual configuration with the approved network plan.

19.4 Verify Protocol Configuration

Check the communication role, protocol, device configuration, register mapping, I/O mapping, baud rate, timeout, and other protocol-specific parameters.

19.5 Review Diagnostics

Read the PLC's diagnostic buffer, module status, communication error counters, drive diagnostics, and HMI or gateway logs.

Record the exact error text and time before resetting or clearing the fault.

19.6 Check Data Quality

A communication connection may be active while the application receives incorrect or stale data.

Verify:

  • Correct tag or register.
  • Correct data type.
  • Correct scaling.
  • Correct byte and word order.
  • Validity or quality status.
  • Timestamp or data age where available.
  • Correct device and source mapping.

19.7 Verify Recovery

After correcting the cause, verify that:

  • Communication status is healthy.
  • The intended data is changing correctly.
  • No unexpected stale values remain.
  • Required machine handshakes complete.
  • Diagnostics no longer report the original fault.
  • The machine or process behaves correctly under the approved test conditions.

20. Common Communication Faults

21. Communication With Node-RED, SQL Server, and Grafana

In an industrial data-acquisition architecture, a PLC may provide data to Node-RED, which then processes selected tags and stores values in SQL Server for reporting or visualization in Grafana.

A simplified arrangement is:

PLC
  ↓
Industrial Protocol Driver
  ↓
Node-RED
  ↓
Data Validation and Tag Processing
  ↓
SQL Server
  ↓
Grafana Dashboard

Each layer introduces its own failure modes.

PLC-to-Node-RED

Check:

  • PLC communication status.
  • Driver configuration.
  • Correct PLC address and route.
  • Tag names and data types.
  • Controller access settings.
  • Connection and read errors.
  • Whether the driver supports the controller and protocol.

Node-RED Processing

Check:

  • Whether messages are arriving.
  • Whether the expected tag values are present.
  • Whether data types are correct.
  • Whether values are being converted or rejected.
  • Whether error handling or filtering suppresses updates.
  • Whether the flow is using the correct configuration.

Node-RED-to-SQL Server

Check:

  • SQL Server availability.
  • Correct server and database selection.
  • Authentication and permissions.
  • Connection errors.
  • Table and column definitions.
  • Data type compatibility.
  • Insert or update errors.
  • Transaction behavior.

SQL Server-to-Grafana

Check:

  • Data source configuration.
  • Database connectivity.
  • Query correctness.
  • Table and column names.
  • Time-column handling.
  • Dashboard time range.
  • Data freshness.

A blank Grafana panel does not automatically mean the PLC has stopped communicating. The fault could exist at any layer between the controller and the dashboard.

22. OT Network Reliability and Security

Operational Technology (OT) networks support equipment that directly monitors or controls physical processes.

Communication engineering must consider both availability and cybersecurity.

Important practices include:

  • Maintain an approved network diagram and IP address plan.
  • Use managed switches where the design requires them.
  • Segment networks according to operational and security requirements.
  • Restrict engineering and supervisory access to authorized users.
  • Apply firewall rules appropriate to the required communication flows.
  • Avoid connecting unknown devices to production networks.
  • Control software and firmware changes.
  • Maintain configuration backups.
  • Monitor network and device diagnostics.
  • Follow approved remote-access procedures.
  • Coordinate network changes with production and maintenance.
  • Preserve safety-related independence where required by the design.

Do not perform unapproved port scans, network reconfiguration, or device resets on a live production network. Even a seemingly harmless change can interrupt real-time control or create unexpected device behavior.

23. Communication Maintenance and Documentation

A reliable maintenance system should document not only the PLC but also its communication dependencies.

Recommended records include:

  • PLC model, CPU, and firmware.
  • Communication module and firmware.
  • Protocols in use.
  • Device names and IP addresses.
  • Serial parameters.
  • Network topology and switch ports.
  • Device configuration files.
  • I/O and data mappings.
  • HMI, drive, CNC, and robot communication dependencies.
  • Gateway and driver settings.
  • Known error codes and diagnostic procedures.
  • Approved replacement devices.
  • Backup location and configuration revision.
  • Recent network changes and fault history.

Sensitive credentials and secrets should not be stored in ordinary maintenance notes. Follow the site's approved credential-management process.

24. SAP PM and Communication Fault Records

For communication-related downtime, record enough detail to separate a network problem from a device, configuration, or application problem.

Useful information includes:

  • Functional location and equipment number.
  • Affected PLC, remote I/O, drive, robot, or network switch.
  • Fault time and production impact.
  • Exact diagnostic message.
  • Communication protocol.
  • Affected network segment or connection.
  • Relevant device addresses and identifiers, where permitted.
  • Results of physical and configuration checks.
  • Confirmed root cause.
  • Corrective action.
  • Software or configuration changes.
  • Functional verification.
  • Repeat-failure status.

For example:

  • Symptom: Remote I/O station became unavailable during automatic production.
  • Cause: The station lost its required network connection because of a damaged connector.
  • Corrective action: Replaced the connector using the approved connector and termination procedure.
  • Verification: Confirmed the station returned to normal status, I/O data updated correctly, and the machine completed the required operating test.

If the cause is not confirmed, record it as unresolved or suspected rather than documenting a guess as fact.

25. Practical Industrial Example

Scenario: PLC Shows Connected, but Robot Values Are False or Null

An Allen-Bradley GuardLogix controller communicates with robot-related equipment. The data-collection application reports that the controller is connected, but the robot tags remain false or null.

Possible causes

  • The connection is established, but the selected tags are incorrect.
  • The configured driver does not support the required tag path or data type.
  • The robot data is not exposed through the selected communication interface.
  • The controller's tag structure differs from the expected mapping.
  • The program is not updating the values.
  • The data-collection application is connected to the wrong controller or program.
  • The data is invalid, stale, or being converted incorrectly.
  • Access permissions or communication configuration restrict the requested data.

Diagnostic sequence

  1. Confirm which controller and communication endpoint the application is using.
  2. Verify the controller's communication status and diagnostic messages.
  3. Inspect the exact tag names, data types, and paths.
  4. Compare the application values with the values in the controller's engineering software, using approved access.
  5. Confirm that the relevant program logic updates the tags.
  6. Check driver support for the controller and tag structure.
  7. Review the application logs for read errors, unsupported data types, or mapping failures.
  8. Validate the value through a second approved diagnostic method when available.
  9. Correct the configuration and verify data freshness.

The key distinction is that a connected session does not prove that every requested tag is valid or readable. Diagnose the communication session, tag mapping, and application data path separately.

26. Performance Indicators

Indicator What it measures Engineering value
Communication-related downtime Production loss associated with communication faults Quantifies operational impact
Communication fault count Number of recorded failures Identifies recurring devices or networks
Repeat-fault rate Frequency of recurrence Measures corrective-action effectiveness
Recovery time Time required to restore communication Supports downtime reduction
Network availability Proportion of time the defined network service is available Helps assess reliability
Timeout frequency Number of communication timeouts Helps identify intermittent problems
Data freshness Age of the latest valid data Supports reliable monitoring
Configuration compliance Agreement between actual and approved configuration Reduces undocumented changes
Backup coverage Availability of required configuration backups Supports recovery after failures

The measurement method and scope should be defined consistently. A PLC-to-HMI connection, a remote I/O network, and a database reporting path have different availability requirements and should not be combined without a clear measurement definition.

27. Practical Checklist

Before troubleshooting

  • Identify the affected devices and exact symptoms.
  • Review the network diagram and electrical drawings.
  • Record diagnostic messages and timestamps.
  • Check the device power and physical link.
  • Identify the protocol and communication path.
  • Confirm the approved IP or serial configuration.

During diagnosis

  • Verify device addresses and names.
  • Check cable, connector, and switch status.
  • Review PLC and device diagnostics.
  • Verify protocol configuration and data mapping.
  • Check tag names, data types, and register offsets.
  • Confirm that the received data is current and valid.
  • Separate physical, network, protocol, and application faults.
  • Avoid unapproved changes on a live production network.

After repair

  • Confirm normal communication status.
  • Verify correct data exchange.
  • Check machine handshake and sequence behavior.
  • Confirm the original fault is resolved.
  • Record root cause and corrective action.
  • Update approved network or device documentation.
  • Save configuration changes according to site procedures.

28. Key Engineering Principles

  • Physical connectivity, network reachability, protocol communication, and valid application data are separate conditions.
  • Diagnose from the physical layer upward.
  • Verify the exact protocol and device configuration rather than relying on assumptions based on the manufacturer.
  • Correct data mapping and data types are as important as a working network link.
  • Monitor communication quality and data freshness, not only connection status.
  • Preserve the required machine safety behavior during communication failures.
  • Treat OT network changes as controlled engineering changes.
  • Record diagnostics, confirmed root causes, and configuration changes.
  • Validate the complete data path after repairs.
