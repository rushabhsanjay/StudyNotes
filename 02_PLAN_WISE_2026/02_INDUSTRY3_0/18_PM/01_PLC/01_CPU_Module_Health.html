1. Definition

CPU and module health monitoring is the process of checking the operating condition, diagnostic status, communication status, and functional integrity of a PLC CPU and its associated modules to identify faults, degradation, or abnormal conditions before they cause production interruptions.

A PLC system may continue running while some modules, communication paths, or diagnostic functions are degraded. Therefore, maintenance must evaluate the health of the complete control system rather than checking only whether the CPU is in RUN mode.

CPU and module health monitoring is part of preventive maintenance (PM) because it helps identify developing faults, verify system availability, and reduce unexpected breakdowns.

The topic applies to PLC systems such as Siemens SIMATIC, Allen-Bradley ControlLogix and CompactLogix, Mitsubishi MELSEC, and other industrial controllers.

2. Objectives of CPU and Module Health Monitoring

  • Confirm that the CPU is operating in the expected state.
  • Detect CPU faults, watchdog events, memory errors, and abnormal operating conditions.
  • Verify the status of digital and analog I/O modules.
  • Detect missing, failed, or incorrectly configured modules.
  • Check remote I/O communication and network health.
  • Identify power-supply, backplane, and rack-related problems.
  • Verify module configuration against the approved hardware configuration.
  • Identify recurring diagnostic events and intermittent faults.
  • Reduce unplanned downtime through early fault detection.
  • Maintain reliable diagnostic information for troubleshooting and maintenance planning.
  • Confirm that critical control and safety functions remain within their approved operating conditions.

3. Basic PLC Hardware Architecture

A typical PLC control system contains several hardware elements.

Industrial Power Supply
        ↓
PLC Rack or Backplane
        ↓
CPU / Controller
        ↓
Local I/O Modules
        ↓
Sensors and Actuators

CPU / Controller
        ↓
Communication Interface
        ↓
Industrial Network
        ↓
Remote I/O / Drives / HMI / Other Controllers

The exact arrangement depends on the PLC platform. Some controllers integrate the CPU and communication interfaces, while others use separate modules. Compact PLCs may have integrated I/O and no traditional rack backplane.

Component Primary function Important health indicators
CPU Executes the control program and manages controller functions RUN/STOP state, fault status, memory, watchdog, diagnostic events
Power supply Provides operating power to the controller and associated modules Output status, voltage, temperature, overload indications
Backplane or rack Provides module interconnection and communication Rack faults, module recognition, connection or bus errors
Digital input module Reads discrete field signals Channel status, module fault, field-supply condition
Digital output module Controls discrete field devices Output status, channel diagnostics, overload or short-circuit indication where supported
Analog input module Measures analog signals Channel diagnostics, range status, configuration and conversion errors
Analog output module Generates analog control signals Channel status, range diagnostics, output configuration
Communication module Connects the PLC to industrial networks and devices Link status, connection faults, error counters, device availability
Remote I/O adapter Connects remote I/O to the controller or network Adapter status, network connection, module faults
Motion or technology module Performs specialized control functions Module status, configuration, synchronization, axis or technology faults

Not every module provides every diagnostic indicator. Available diagnostics depend on the model, firmware, configuration, and engineering software.

4. PLC CPU Health

The CPU is the central execution and coordination component of a PLC system. Its health must be checked against the manufacturer's diagnostic information and the machine's approved operating requirements.

4.1 CPU operating states

Common controller states include:

State Meaning Maintenance interpretation
RUN The controller is executing the application Confirm that no significant diagnostic faults or functional problems remain
STOP The controller is not executing the normal application Determine whether the state is intentional, fault-induced, or part of maintenance
Startup or initialization The controller is starting or initializing its system Check whether startup completes normally
Faulted or major fault The controller has detected a serious condition Retrieve diagnostics and follow the platform-specific recovery procedure
Redundant or standby state A redundant controller is operating in a designated role Verify the expected role, synchronization, and redundancy health

These state names and their precise meanings vary by manufacturer and controller family.

Important: RUN status does not prove that the entire machine is healthy. A controller may be executing its program while a remote I/O rack is unavailable, an analog input is invalid, or an output channel has failed.

4.2 CPU diagnostic indicators

Common indicators include:

  • RUN indicator: Shows the controller's execution state.
  • ERROR or FAULT indicator: Indicates a detected controller or system fault.
  • MAINT or maintenance indicator: May indicate a maintenance requirement or diagnostic condition.
  • BATTERY indicator: Present on platforms that use a battery for supported backup functions.
  • COMM indicator: May indicate communication activity or status.
  • MEMORY or storage indication: Available on some platforms for memory or storage-related status.

The meaning of each LED must be checked in the exact hardware manual. LED colors and blink patterns are not universal across PLC families.

4.3 CPU fault conditions

Typical conditions to investigate include:

  • Application or configuration errors.
  • Watchdog or execution-time faults.
  • Memory or storage errors.
  • Firmware-related faults.
  • Internal hardware diagnostics.
  • Power interruption or unstable supply.
  • Communication-related faults.
  • Incorrect hardware configuration.
  • Startup failures.
  • Excessive task execution time, where the platform monitors it.

A fault message should be interpreted using the manufacturer's diagnostic information. Do not replace a CPU simply because a generic fault indicator is active.

5. CPU Scan Cycle and Execution Health

A PLC repeatedly executes its control logic according to its architecture and configured task model.

For a typical cyclic PLC task, the simplified sequence is:

Read or Update Inputs
        ↓
Execute Control Logic
        ↓
Update Outputs
        ↓
Perform System and Communication Tasks
        ↓
Repeat

Modern PLCs may use cyclic, periodic, event-driven, interrupt-driven, and asynchronous tasks. Actual execution order and I/O update behavior vary by platform.

5.1 Scan time

Scan time is the time required for a defined PLC execution cycle or task cycle.

Abnormally high or variable execution time may indicate:

  • Increased program complexity.
  • Additional communication or data-processing load.
  • Inefficient logic.
  • Excessive diagnostic or data-handling activity.
  • Interrupt or task scheduling effects.
  • An application that has approached its configured execution limit.

The exact meaning of scan time differs across platforms and task types.

5.2 Watchdog monitoring

A watchdog monitors whether execution or a specified task completes within its permitted time.

If the applicable time limit is exceeded, the controller may generate a fault, stop execution, or take another configured action.

Maintenance checks should include:

  • Current and maximum execution times, where available.
  • Configured task limits.
  • Watchdog or execution-time events.
  • Changes in application execution time over time.
  • Recent software modifications.

Do not increase a watchdog limit merely to suppress a fault. First determine why the execution requirement is not being met and verify the effect of any proposed change.

5.3 CPU load and resource utilization

Depending on the PLC, useful indicators may include:

  • CPU utilization.
  • Task execution time.
  • Memory usage.
  • Communication load.
  • Number of active connections.
  • Diagnostic buffer capacity.
  • Available storage or retained-data capacity.

A CPU with high utilization is not necessarily faulty. The important question is whether the controller remains within its design limits while meeting the required control performance.

6. CPU Memory and Program Integrity

CPU memory may contain the operating system, application program, data areas, configuration, retained variables, and other platform-specific information.

6.1 Memory-related checks

  • Confirm that the application is the approved version.
  • Check available memory and resource limits.
  • Review memory or storage diagnostic messages.
  • Verify that required retained data behaves as designed.
  • Confirm that the correct project and hardware configuration are available for recovery.
  • Check whether removable storage or memory cards are present and healthy where required.
  • Confirm that program changes follow the approved change-control process.

6.2 Backup verification

A backup is useful only if it is correct, accessible, and suitable for restoration.

Verify:

  • Correct machine and CPU identification.
  • Project version and backup date.
  • Hardware configuration.
  • Firmware compatibility.
  • Required device parameters.
  • Relevant safety configuration and authorization controls.
  • Availability of the engineering project and necessary software.
  • Integrity of the backup file.
  • A controlled restoration and validation procedure.

For safety-related controllers, use the applicable approved safety-project management and verification process. A standard PLC backup procedure must not be assumed sufficient for a safety controller.

7. PLC Power-Supply Health

Power problems can produce symptoms that resemble CPU or module failures.

7.1 Typical failure indicators

  • CPU restarts unexpectedly.
  • Several modules report faults at the same time.
  • Remote I/O repeatedly disconnects.
  • Module LEDs cycle during operation.
  • Power-supply diagnostic alarms occur.
  • Faults appear during high load or temperature.
  • Output devices behave abnormally because field power is unavailable.

7.2 Inspection points

  • Check the supply's diagnostic indicators.
  • Verify the input supply condition using approved procedures.
  • Verify output voltage under appropriate operating conditions.
  • Check terminal tightness according to the manufacturer's requirements and safe work procedures.
  • Inspect for overheating, contamination, or physical damage.
  • Check loading against the rated capacity.
  • Review the condition of redundant supplies where fitted.
  • Confirm that module and field power requirements are met.

Never measure or inspect exposed energized circuits without the required authorization, competence, instruments, and electrical safety controls.

7.3 Avoid confusing control power with field power

A PLC may remain operational even when a sensor or actuator's field supply has failed.

For example, the CPU may show RUN while several digital inputs remain OFF because the associated field supply is missing. This is not necessarily a CPU problem.

Diagnosis must separate controller power, module electronics power, and field-device power.

8. Rack, Backplane, and Module Recognition

The rack or backplane provides the physical and electrical interconnection between the CPU and installed modules on systems that use this architecture.

8.1 Typical symptoms of rack or module problems

  • A module is reported as missing.
  • The CPU detects a hardware configuration mismatch.
  • Multiple modules become unavailable.
  • Rack or bus diagnostic messages appear.
  • Module communication is intermittent.
  • A module is not recognized after replacement.
  • Faults occur after maintenance or rack modifications.

8.2 Maintenance checks

  • Compare the installed hardware with the approved configuration.
  • Verify the module's exact part number and position.
  • Check the manufacturer's module compatibility requirements.
  • Inspect approved power and interconnection points under safe conditions.
  • Review the CPU's hardware diagnostics.
  • Confirm that any required configuration changes are approved.
  • Check whether a module replacement requires configuration download or other commissioning steps.

Do not remove or insert modules under power unless the exact hardware and procedure explicitly support that operation. Hot-swapping is platform-specific, not a universal PLC feature.

9. Digital Input Module Health

Digital input modules receive discrete signals such as ON/OFF states from sensors, limit switches, pushbuttons, and auxiliary contacts.

9.1 Typical symptoms

  • An input remains OFF when the field device should be active.
  • An input remains ON unexpectedly.
  • Several channels fail together.
  • The input LED disagrees with the PLC tag.
  • The module reports a diagnostic fault.
  • Input states change intermittently.

9.2 Diagnostic sequence

  1. Confirm the expected physical condition of the sensor or switch.
  2. Compare the field-device indication with the module channel LED, where provided.
  3. Compare the module status with the PLC input tag.
  4. Check field power, common connections, and wiring according to the circuit design.
  5. Check module and channel diagnostics.
  6. Verify the input configuration and electrical compatibility.
  7. Investigate wiring, sensor, terminal, or module failure based on evidence.

9.3 Interpreting observations

Observation Possible interpretation
Sensor indicator OFF and PLC input OFF Sensor may not be actuated, or sensor power may be missing
Sensor indicator ON but module channel LED OFF Possible wiring, field-supply, terminal, or module issue
Module channel LED ON but PLC tag OFF Possible configuration, addressing, data mapping, or application issue
Several inputs fail together Check common power, common wiring, module supply, or shared hardware
Input changes intermittently Investigate loose connections, unstable sensor output, electrical noise, or mechanical actuation

These are diagnostic clues rather than definitive conclusions. Input LED behavior and internal diagnostics depend on the module design.

10. Digital Output Module Health

Digital output modules control devices such as contactor coils, solenoid valves, indicator lamps, and other discrete loads.

10.1 Typical symptoms

  • The PLC output command is ON but the device does not operate.
  • The output command is OFF but the device remains energized.
  • The module reports overload or short-circuit diagnostics.
  • Several output channels fail together.
  • Output operation is intermittent.
  • The module's channel indication disagrees with the expected device condition.

10.2 Diagnostic sequence

  • Verify the PLC output command and relevant interlocks.
  • Check the output channel status.
  • Verify field power and the load circuit using approved procedures.
  • Inspect protective devices and wiring under safe conditions.
  • Check for an open circuit, short circuit, overloaded output, or failed load.
  • Review module diagnostic messages and channel protection behavior.
  • Confirm that the output type and load are compatible.
  • Determine whether the fault lies in the program, module, wiring, power supply, or field device.

10.3 Important distinction

A PLC output command being ON does not guarantee that the physical output is delivering the expected voltage or current.

Likewise, an output LED does not necessarily prove that the connected actuator has operated. Feedback from the field device may be required to confirm the physical result.

Never force an output merely to test whether an actuator operates without checking machine state, interlocks, hazards, and the approved test procedure.

11. Analog Input Module Health

Analog input modules measure signals such as:

  • 4–20 mA.
  • 0–20 mA.
  • 0–10 V.
  • Other voltage or current ranges supported by the module.
  • Temperature or resistance signals through compatible specialized modules.

11.1 Typical symptoms

  • Reading is fixed at zero.
  • Reading is at full scale.
  • Reading is outside the expected range.
  • Value fluctuates excessively.
  • Channel reports wire-break or range diagnostics.
  • Multiple channels show similar abnormal values.
  • HMI values disagree with independent measurements.

11.2 Diagnostic checks

  • Verify the sensor's supply and operating condition.
  • Confirm the configured input type and range.
  • Check polarity, wiring, shielding, and grounding as appropriate.
  • Review channel diagnostic status.
  • Confirm scaling and engineering-unit conversion.
  • Compare the raw input value with the scaled application value.
  • Use a suitable calibrator or measurement instrument when authorized.
  • Check whether the signal is outside the module's configured range.

11.3 Example: 4–20 mA signal

Suppose a pressure transmitter uses a 4–20 mA signal for a range of 0–10 bar.

The ideal linear conversion is:

\[ P = \frac{I-4}{20-4}\times 10 \]

Where:

  • \(P\) is pressure in bar.
  • \(I\) is the measured current in mA.

At 12 mA:

\[ P = \frac{12-4}{16}\times 10 = 5\text{ bar} \]

This assumes correct transmitter operation, wiring, channel configuration, and linear scaling.

A reading of zero may indicate a real zero-scale value only if the signal and scaling support that interpretation. In a 4–20 mA system, a current near 0 mA can indicate a loop fault rather than zero pressure.

The module's configured fault detection and transmitter specifications determine how such conditions should be interpreted.

12. Analog Output Module Health

Analog outputs generate reference signals for devices such as VFDs, control valves, and proportional actuators.

12.1 Common symptoms

  • Commanded output differs from the expected process response.
  • Output remains at zero or full scale.
  • Channel diagnostic fault appears.
  • Output signal fluctuates.
  • Connected device does not respond.
  • Several channels show similar abnormalities.

12.2 Diagnostic sequence

  • Confirm the PLC's requested output value.
  • Check application scaling and limits.
  • Verify module configuration.
  • Review channel diagnostics.
  • Check field power and wiring according to the circuit design.
  • Measure the signal using approved methods.
  • Verify the connected device's input range and configuration.
  • Confirm the resulting process response using suitable feedback.

A correct PLC command does not prove that the output signal reaches the device. Similarly, a correct electrical signal does not prove that a VFD, valve, or actuator is operating correctly.

13. Communication Module and Remote I/O Health

Industrial PLC systems often rely on communication networks to exchange data with remote I/O, drives, HMIs, robots, and other controllers.

13.1 Common communication faults

  • Loss of communication with a remote I/O rack.
  • Device connection timeout.
  • Network link failure.
  • Incorrect addressing or configuration.
  • Device replacement without corresponding configuration updates.
  • Intermittent network disconnection.
  • Excessive communication errors.
  • Duplicate or conflicting network addresses.
  • Failed switch, cable, connector, or communication module.

13.2 Health checks

  • Check the communication module's status.
  • Verify the physical link and device availability.
  • Review controller and network diagnostics.
  • Check the expected device configuration.
  • Identify whether one device or an entire network segment is affected.
  • Review recent changes to cabling, switches, addresses, and device configuration.
  • Check error counters and network performance indicators where available.
  • Confirm that the application's response to communication loss is appropriate.

13.3 Communication health versus process health

A device may be reachable over the network but still have a process fault. Conversely, the remote device may be operating locally while the PLC cannot receive its data.

Separate these conditions:

  • Network health: Can devices communicate?
  • Device health: Is the device functioning correctly?
  • Data health: Is the information valid and current?
  • Process health: Is the controlled process behaving correctly?

This separation is essential when troubleshooting PLC, HMI, SCADA, and remote I/O problems.

14. Redundant PLC and Power-Supply Health

Some critical control systems use redundant CPUs, communication paths, or power supplies to improve availability.

14.1 Redundancy checks

  • Verify the active and standby controller states.
  • Check synchronization status where applicable.
  • Confirm that the standby system is ready to assume control.
  • Review redundancy-related diagnostics.
  • Verify the status of redundant communication paths.
  • Check power-supply load sharing or redundancy indicators where provided.
  • Review recent switchover events.
  • Confirm that redundancy monitoring and alarms are functioning.

14.2 Important limitations

Redundancy does not eliminate all failure modes.

Both systems may be affected by a shared power source, network, software defect, environmental condition, or incorrect configuration. Redundant hardware may also remain unavailable because of a failed synchronization or communication path.

Do not initiate a redundancy switchover merely to test the system unless the test is authorized and the applicable procedure confirms that the process can tolerate it.

15. PLC Health Monitoring in Siemens, Allen-Bradley, and Mitsubishi Systems

The diagnostic concepts are similar across manufacturers, but the terminology, tools, and recovery procedures differ.

Platform Typical engineering environment Relevant health checks
Siemens S7-1200/S7-1500 TIA Portal CPU operating state, diagnostic buffer, module diagnostics, online/offline comparison, communication status
Siemens legacy S7 systems STEP 7, depending on generation CPU diagnostics, module information, diagnostic buffer, hardware configuration
Allen-Bradley ControlLogix/CompactLogix Studio 5000 Logix Designer Controller status, module faults, I/O connection status, task execution, major/minor faults
Mitsubishi MELSEC GX Works2 or GX Works3, depending on family CPU diagnostics, module diagnostics, error history, parameter configuration, communication status

Exact diagnostic names and available functions depend on the controller family, firmware, module type, and software version.

15.1 Siemens S7-1500 example

Typical checks in TIA Portal may include:

  • Online CPU operating state.
  • Diagnostic buffer entries.
  • Module and rack status.
  • Hardware configuration consistency.
  • Online device and communication diagnostics.
  • Relevant task or cycle-time information.
  • Firmware and module identification.

A diagnostic entry should be interpreted using its event details and the corresponding Siemens documentation.

15.2 Allen-Bradley ControlLogix example

Typical checks in Studio 5000 may include:

  • Controller status and fault information.
  • Module properties and connection status.
  • I/O tree diagnostics.
  • Controller and task execution information.
  • Major and minor fault details.
  • Communication status and relevant module error codes.

A module fault may originate from the module itself, its power, its network path, or a configuration mismatch. The fault details help separate these possibilities.

15.3 Mitsubishi MELSEC example

Depending on the CPU and engineering software, useful checks may include:

  • CPU diagnostics.
  • Error history.
  • Module diagnostics.
  • Parameter and hardware configuration.
  • Network and remote I/O status.
  • Relevant scan and execution information.

Always confirm the exact menu names and diagnostic functions for the installed Mitsubishi CPU and software version.

16. Preventive Maintenance Inspection Schedule

The inspection interval should be based on equipment criticality, manufacturer recommendations, operating conditions, site history, and applicable procedures.

Frequency Typical activity Purpose
Each shift or daily, where justified Review critical alarms, CPU state, and major communication faults Detect significant abnormalities early
Weekly or monthly, depending on criticality Review recurring faults, module diagnostics, and network stability Identify developing or intermittent problems
During scheduled PM Inspect approved physical conditions, ventilation, power indications, and mounting where safe Identify environmental or installation issues
During planned maintenance Verify configuration, approved backups, hardware inventory, and recovery readiness Improve restoration capability
After a module or CPU replacement Verify configuration, diagnostics, communication, and required functions Confirm correct installation and commissioning
After a major fault Preserve evidence, review diagnostics, and perform appropriate follow-up Prevent recurrence
During an approved system test Test specified redundancy or recovery functions Verify readiness without introducing uncontrolled risk

Do not open energized panels or disturb PLC hardware solely because a calendar-based PM interval has arrived. Physical inspections must follow the appropriate electrical safety and equipment procedures.

17. PLC Module Replacement Procedure

Module replacement is a controlled maintenance activity, not simply the act of pulling one component out and pushing another in.

17.1 Before replacement

  • Identify the exact failed module and slot.
  • Record the CPU, rack, and module details.
  • Capture diagnostic information.
  • Verify the replacement part number and compatibility.
  • Confirm whether the module supports hot-swapping.
  • Review the approved replacement procedure.
  • Confirm required isolation and production controls.
  • Verify configuration and recovery requirements.
  • Check whether any required parameter or calibration information must be preserved.

17.2 During replacement

  • Apply the required energy-control procedure.
  • Confirm the correct module and physical position.
  • Inspect connectors and terminals according to the procedure.
  • Avoid electrostatic discharge damage.
  • Use approved handling and installation methods.
  • Verify that the module is seated and secured correctly.

17.3 After replacement

  • Confirm that the CPU recognizes the module.
  • Check module and channel diagnostics.
  • Verify configuration compatibility.
  • Complete any required approved configuration or parameterization.
  • Verify communication and relevant I/O states.
  • Test affected functions under controlled conditions.
  • Confirm that required interlocks and protective functions remain operational.
  • Record the replacement and final status.

A replacement module may require compatible firmware, parameterization, calibration, or hardware configuration. Physical compatibility alone does not guarantee correct operation.

18. Module Health Versus Process Health

A critical principle in automation maintenance is that healthy hardware does not automatically mean a healthy process.

Hardware or diagnostic observation Possible process implication
CPU in RUN The application is executing, but process conditions may still be abnormal
Digital input module healthy Sensor wiring or mechanical actuation may still be incorrect
Analog input channel healthy The transmitter may be calibrated incorrectly or measuring an abnormal process value
Digital output module healthy The contactor, solenoid, or actuator may still have failed
Analog output channel healthy The control valve or drive may not respond correctly
Network connection healthy Data may be stale, incorrectly mapped, or invalid
Redundant CPU available Shared infrastructure or common application defects may still affect both controllers

A complete investigation combines controller diagnostics with field-device, process, and application checks.

Suggested fields include:

20. Common Mistakes in CPU and Module Health Checks

Mistake Why it is a problem Correct approach
Checking only the CPU RUN LED Misses module, field, and communication faults Review the complete diagnostic state
Replacing the CPU first May not address power, wiring, network, or configuration faults Diagnose the system and confirm the failed component
Ignoring intermittent faults The system may be approaching a recurring failure Review event history and operating conditions
Clearing diagnostics before recording them Removes useful troubleshooting evidence Preserve relevant evidence before clearing
Assuming an input LED proves sensor correctness Electrical indication does not establish process accuracy Compare the physical sensor, module, tag, and process
Assuming an output command proves actuator operation The field circuit or actuator may be defective Verify the electrical output and physical response
Using an incompatible replacement module Can cause configuration, firmware, or functional problems Verify exact compatibility
Downloading a PLC project without authorization May stop or alter machine operation Follow change-control and recovery procedures
Performing an unapproved hot-swap Can damage hardware or interrupt the process Verify platform-specific support and procedures
Ignoring backup quality Recovery may be impossible or restore the wrong version Validate backup identity and usability
Treating communication faults as CPU faults Leads to unnecessary replacement and downtime Separate CPU, network, device, and data health

21. Practical Example: Remote I/O Module Fault on a Production Machine

A machine's PLC remains in RUN, but several sensors connected to a remote I/O station appear unavailable.

Initial observations

  • CPU RUN indicator is active.
  • The HMI shows multiple sensor-related alarms.
  • Several PLC input tags remain OFF.
  • The remote I/O station reports a communication or module diagnostic fault.

Investigation

  1. Confirm the machine's safe state and production impact.
  2. Record the active CPU and remote I/O diagnostics.
  3. Determine whether the entire station or only selected channels are affected.
  4. Check the remote station's power and network status.
  5. Verify the hardware configuration and module identification.
  6. Inspect the relevant power and communication connections using approved procedures.
  7. Compare field-device indications, module LEDs, and PLC input values.
  8. Identify the failed component or connection using the evidence.

Corrective action

Suppose the investigation identifies a failed remote I/O power supply. The team replaces it with a compatible approved unit using the required isolation procedure.

Verification

  • Confirm that the station is recognized.
  • Verify that module diagnostics are clear or understood.
  • Confirm communication stability.
  • Check affected input channels.
  • Verify the required machine sequence and protective functions.
  • Conduct the required controlled functional test.
  • Record the failure, replacement, and findings.

The CPU itself did not need replacement. Checking only the RUN indicator would have missed the actual failure.

22. Standards and Technical References

The following standards and manufacturer resources may be relevant, depending on the application and jurisdiction:

  • IEC 61131 series: PLC programming languages and programmable controller concepts.
  • IEC 60204-1: Electrical equipment of machinery, including relevant electrical safety requirements.
  • IEC 61508: Functional safety of electrical, electronic, and programmable electronic safety-related systems.
  • IEC 62061: Functional safety of machinery control systems.
  • IEC 62443 series: Industrial automation and control system cybersecurity.
  • ISO 55000 series: Asset management principles and framework.
  • Manufacturer hardware manuals, diagnostic references, firmware compatibility documents, and approved engineering procedures.

These references serve different purposes. Not every standard applies to every PLC installation, and a general-purpose PLC must not be assumed suitable for a safety function simply because it supports diagnostics.

23. Final CPU and Module Health Checklist

  • CPU operating state is correct for the intended machine condition.
  • Active CPU faults and diagnostic events have been reviewed.
  • Relevant execution-time and resource indicators are within acceptable limits.
  • Power-supply status is satisfactory.
  • Rack, backplane, and installed-module configuration are consistent.
  • Digital and analog I/O diagnostics have been checked.
  • Communication modules and remote I/O stations are healthy.
  • Critical field signals and output responses have been verified where required.
  • Redundancy status has been checked where applicable.
  • Approved program and configuration backups are available and verified.
  • Any replacement hardware is compatible and correctly configured.
  • Required functional tests have been completed after maintenance.
  • Outstanding faults and restrictions have been documented.
  • Follow-up actions have been assigned and tracked.

Core principle: Monitor the CPU, modules, power supplies, communication paths, field signals, and application behavior as one control system. The objective is not merely to confirm that the PLC is running, but to establish that the system is operating within its required technical and functional limits.
