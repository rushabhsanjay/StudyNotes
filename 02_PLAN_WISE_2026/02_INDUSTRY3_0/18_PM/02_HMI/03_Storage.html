1. Definition

HMI storage refers to the memory and storage resources used by a Human-Machine Interface (HMI) to store its application, configuration, runtime files, historical data, recipes, alarm records, logs, and other information required for operation and recovery.

In industrial automation, storage is important because an HMI may continue to operate only if its application and required data remain accessible. Storage failure, corruption, insufficient capacity, or incorrect configuration can cause application startup failures, loss of historical records, or inability to restore the panel after replacement.

HMI storage may be built into the panel or provided by removable memory cards, USB devices, industrial PCs, network storage, or connected servers.

Important distinction: HMI application storage, operating-system storage, runtime memory, and historical-data storage are different resources. A panel can have sufficient free storage but still fail because it has insufficient RAM or a corrupted runtime application.

2. Purpose of HMI storage

HMI storage supports several functions:

  • Application execution: Provides access to the HMI project and runtime files.
  • Configuration retention: Preserves communication settings, display configuration, and other supported parameters.
  • Recipe management: Stores product recipes and process settings where the application uses local storage.
  • Alarm history: Retains alarm events and acknowledgement information according to the application design.
  • Data logging: Stores trends, production values, and diagnostic records.
  • Backup and restoration: Provides a location for project archives or recovery packages.
  • User management: Stores supported user configuration and related application data.
  • Diagnostics: Retains logs that help identify application faults and storage problems.
  • Data exchange: Allows approved import and export of recipes, reports, and configuration files.

Not every HMI stores all these items locally. Some applications store historical records on a server, while the panel stores only the runtime application and a limited amount of configuration data.

3. Main types of storage

Storage type Description Typical use
Internal flash Non-volatile memory integrated into the panel Runtime, operating-system files, and configuration
SSD or industrial storage drive Persistent storage used in industrial PCs or advanced HMI systems Applications, logs, archives, and larger datasets
RAM Volatile working memory Running applications, temporary data, and runtime operations
Removable memory card Manufacturer-supported removable storage Project transfer, application recovery, or data storage where supported
USB storage Removable external storage Approved project transfer, exports, and backups
Network storage Storage accessed through an approved network connection Centralized backups, files, or shared data
Database server A database service storing structured records Production history, alarms, trends, and reports
Cloud storage Remote storage accessed through an authorized service Selected enterprise data and offsite retention where permitted

3.1 Internal flash storage

Internal flash is commonly used for persistent application and configuration files in panel HMIs.

Its advantages include compact size, no moving parts, and persistence across normal power cycles. However, flash storage has finite write endurance, and its failure can affect the availability of the application or stored data.

Frequent unnecessary writes, power interruption during critical operations, filesystem corruption, and aging hardware can contribute to storage-related faults.

3.2 RAM

RAM is used while the HMI application and operating system are running.

RAM typically holds:

  • Active application data.
  • Display and screen objects.
  • Communication buffers.
  • Runtime variables and temporary calculations.
  • Cached values and other working data.

RAM is generally volatile, meaning its contents are lost when power is removed unless the platform provides a separate persistence mechanism.

Insufficient RAM may cause slow screen changes, application instability, or runtime failure even when substantial flash storage remains available.

3.3 Removable storage

Some HMIs support SD cards, USB devices, or proprietary memory cards for specific tasks.

Possible uses include:

  • Loading or transferring an approved HMI project.
  • Storing exported recipes and reports.
  • Supporting manufacturer-defined restoration procedures.
  • Collecting diagnostic information.

Support varies by panel model and firmware. A removable card should not be assumed to contain a complete restorable image merely because it can store project files.

4. What HMI data may be stored?

Data category Examples Recovery consideration
HMI project Screens, navigation, graphics, scripts, and objects Preserve the native project and its dependencies
Runtime files Compiled application and runtime resources Confirm compatibility with the target panel
System configuration Network settings, regional settings, and device configuration May require separate export or reconfiguration
PLC communication settings Controller addresses, tag mappings, and communication parameters Validate against the actual machine configuration
Recipes Product-specific process parameters Verify which values are approved for restoration
Alarm history Alarm occurrences, timestamps, and acknowledgements Historical data may be stored separately from the project
Trends and logs Process values, diagnostic information, and event records Confirm retention period and storage destination
User configuration Roles, permissions, and user accounts Follow the platform's approved backup and security procedures
License information Runtime or feature licensing data Confirm transfer and recovery requirements
Diagnostic logs Runtime errors, communication failures, and system events Useful for troubleshooting intermittent faults

A normal project backup may not include all runtime history, current recipe values, user data, or licensing information. Define the required recovery scope before creating the backup.

5. Storage architecture in an industrial HMI system

A typical architecture separates the local HMI application from centrally stored operational data.

Operator
   ↓
HMI Display and Runtime
   ↓
Local Storage
   ├── HMI project and runtime files
   ├── Configuration
   ├── Local recipes and logs
   └── Temporary files
   ↓
Industrial Network
   ├── PLC and machine devices
   ├── SCADA or historian
   └── Database or approved file server

The actual architecture depends on the system. An advanced HMI may run on an industrial PC and use network databases, whereas a compact panel may store its project and selected records entirely on internal flash.

Centralized storage can simplify retention and reporting, but it introduces network, server, access-control, and backup dependencies. Local storage can improve independence from the network, but it may offer limited capacity and can be lost when the panel fails.

6. Storage capacity and sizing

Storage capacity must be sufficient for the runtime application, configuration, logs, recipes, temporary files, and the expected growth of stored data.

A useful planning relationship is:

\[ S\_{\text{required}} = S\_{\text{application}} + S\_{\text{configuration}} + S\_{\text{logs}} + S\_{\text{recipes}} + S\_{\text{temporary}} + S\_{\text{reserve}} \]

Where each term represents the expected storage allocation for that category.

The reserve provides capacity for future changes, temporary operations, and unexpected data growth. The required reserve depends on the platform and application.

Example

Assume a panel has the following estimated storage requirements:

Data category Estimated size
HMI application 250 MB
Configuration and dependencies 100 MB
Local logs and history 500 MB
Recipes and exports 150 MB
Temporary working space 100 MB
Reserved free capacity 400 MB
Total required capacity 1,500 MB

The panel would require at least 1,500 MB of usable storage for this estimate. The selected storage device must also account for the operating system, manufacturer-reserved partitions, filesystem overhead, and other files not included in the example.

A device advertised as having a particular capacity may expose less usable space. Always assess the actual free capacity reported by the system.

7. Data logging and storage growth

HMI applications may log alarms, process values, operator actions, and production information. Logging can gradually consume available storage if retention and cleanup are not configured correctly.

For fixed-size records, approximate storage growth can be estimated as:

\[ S = R \times T \times N \]

Where:

  • \(S\) is the estimated storage consumed.
  • \(R\) is the average storage used per record.
  • \(T\) is the number of records generated per unit of time.
  • \(N\) is the total time period expressed in matching units.

For example, if an application stores 1,000 records per day at an average of 2 KB per record, the approximate raw record storage is:

\[ 1{,}000 \times 2\text{ KB} = 2\text{ MB/day} \]

Over 90 days, this is approximately 180 MB before indexing, filesystem overhead, metadata, and other storage costs.

Actual database and log sizes may be higher. Some logging systems also use compression, circular buffers, or fixed retention limits.

Storage growth controls

  • Set appropriate retention periods.
  • Configure circular logging where supported and suitable.
  • Archive records to an approved server when required.
  • Avoid excessive sampling frequencies without a clear operational need.
  • Monitor available space and growth trends.
  • Confirm that log rotation and deletion policies work as intended.
  • Preserve required records before clearing storage.

Deleting logs can remove evidence needed for fault investigation, quality analysis, or audit purposes. Follow retention requirements before performing cleanup.

8. Storage performance and reliability

Capacity alone does not determine storage suitability. Read/write performance, reliability, temperature, power quality, and compatibility also matter.

Parameter Meaning Possible impact
Read speed Rate at which stored data can be retrieved Application loading and report access
Write speed Rate at which data can be saved Logging delays and file operations
Write endurance Expected ability to withstand repeated writes Long-term reliability of flash storage
Available capacity Remaining usable storage Risk of write failures and application problems
Filesystem integrity Consistency of the storage structure File access, boot, or runtime failures
Power-loss behavior How storage handles unexpected power interruption Risk of incomplete writes or corruption
Environmental rating Suitability for temperature, vibration, and other conditions Reliability in the installed location

Use storage devices approved for the target HMI. Consumer memory cards or USB drives may not be suitable for continuous industrial operation.

9. Common HMI storage faults

Symptom Possible causes Checks
HMI application will not start Corrupted project, missing runtime files, full storage, or system fault Check startup messages, available space, and application integrity
Storage-full alarm Excessive logging, large exports, temporary files, or insufficient capacity Inspect usage by category and verify retention settings
Recipes cannot be saved Full storage, write permissions, damaged filesystem, or application error Check free space, permissions, and recipe-storage configuration
Historical data is missing Retention cleanup, incorrect storage destination, logging failure, or database issue Check log configuration, server availability, and retention policy
Application loads slowly Slow storage, excessive file access, low RAM, or heavy runtime workload Separate storage performance from processor and memory limitations
Project transfer fails Unsupported media, insufficient space, incompatible files, or access restrictions Verify supported transfer method and target compatibility
Files become corrupted Power interruption, storage degradation, or filesystem problems Check system diagnostics and use approved recovery procedures
HMI repeatedly restarts System fault, application crash, power instability, or storage issue Examine startup logs and power diagnostics before concluding storage is responsible
USB or memory card is not detected Unsupported format, faulty media, connector damage, or configuration issue Verify approved media requirements and hardware status

Do not immediately format a storage device when a fault appears. Formatting may permanently destroy the application, configuration, logs, and recovery data needed to restore the panel.

10. HMI storage troubleshooting procedure

  1. Confirm the symptom. Determine whether the problem concerns application startup, file saving, historical data, slow performance, or media detection.
  2. Check system diagnostics. Review storage warnings, runtime logs, operating-system messages, and available capacity.
  3. Inspect storage usage. Identify large logs, exports, temporary files, and other unexpected growth.
  4. Check application configuration. Verify storage destinations, write permissions, retention policies, and logging rates.
  5. Check the hardware. Inspect removable media, connectors, and power conditions according to the manufacturer's procedure.
  6. Protect existing data. Back up the application and preserve required logs before making destructive changes.
  7. Correct the cause. Adjust retention, repair configuration, replace failed media, or restore approved files as appropriate.
  8. Verify operation. Confirm application startup, recipe saving, logging, alarm handling, and communication with the PLC.
  9. Document the result. Record the fault, corrective action, affected files, and any replaced components.

If storage errors continue after cleanup, investigate hardware degradation, filesystem integrity, power quality, and runtime faults rather than repeatedly deleting files.

11. Backup and restoration

HMI storage management must include a defined backup and restoration method.

A recovery package may include:

  • Native HMI engineering project.
  • Required libraries and project dependencies.
  • Runtime files where supported.
  • Panel model and firmware information.
  • HMI runtime and engineering software versions.
  • Communication settings and tag configuration.
  • Recipe data and required historical records.
  • User configuration and licensing requirements handled securely.
  • Instructions for restoring and validating the application.

Before restoring

  • Verify the replacement panel model and supported runtime.
  • Confirm project compatibility.
  • Identify which data is included in the backup and which data requires separate recovery.
  • Preserve the existing panel data where possible and authorized.
  • Confirm the approved restoration method.

After restoring

  • Confirm the HMI starts correctly.
  • Verify screen navigation and touch operation.
  • Check PLC communication and tag updates.
  • Validate recipes, alarms, trends, and required historical records.
  • Confirm user permissions and other required settings.
  • Test the relevant machine functions under the approved commissioning procedure.

A successful project transfer does not prove that the complete HMI configuration has been restored.

12. Security and data integrity

HMI storage may contain sensitive machine information, production records, user data, and network configuration.

Recommended controls include:

  • Restrict access to authorized users.
  • Store backups in approved repositories.
  • Protect credentials and security-sensitive configuration.
  • Verify files before restoring them to production equipment.
  • Use approved removable media and transfer procedures.
  • Protect central storage with suitable access control and backup policies.
  • Maintain traceability for project and configuration changes.
  • Follow the site's retention and deletion requirements.
  • Avoid connecting unknown USB devices to industrial HMIs.

Removable media can introduce malware as well as transfer files. Use the organization's OT cybersecurity process for all file transfers.

13. Preventive maintenance checklist

Routine checks

  • Check available storage capacity.
  • Review storage-full warnings and system diagnostics.
  • Confirm that logging and retention settings are appropriate.
  • Verify that recipes and required records can be saved.
  • Inspect removable media and connectors where applicable.
  • Check for repeated runtime or filesystem errors.
  • Verify the availability of the approved HMI project backup.

Periodic checks

  • Review storage growth trends.
  • Verify that required historical records are retained.
  • Confirm that backups can be opened and restored using the supported procedure.
  • Review storage-device lifecycle and replacement availability.
  • Check that HMI firmware and runtime records are current.
  • Record findings in the approved maintenance system.

14. Practical industrial example

Consider an HMI that displays a storage-full alarm. Operators can still navigate the screens, but new recipes cannot be saved and historical trends stop updating.

A structured investigation finds that the local alarm and trend logs have grown continuously because retention limits were not configured correctly.

The appropriate response is to:

  1. Confirm the current storage usage and identify the files consuming space.
  2. Check the plant's retention requirements for alarms and production records.
  3. Preserve required records in an approved destination.
  4. Configure suitable retention or archival behavior.
  5. Remove only data approved for deletion.
  6. Verify that free space has increased.
  7. Test recipe saving and historical logging.
  8. Record the root cause and corrective action.

The long-term correction is to manage storage growth, not merely clear the alarm every few weeks. Otherwise, the same failure will return on schedule, as if the machine were following a maintenance plan nobody actually wrote.

15. Key principles

  • HMI storage includes application files, configuration, recipes, logs, and other persistent data.
  • RAM, internal flash, removable media, and server storage perform different roles.
  • Available capacity, storage performance, write endurance, and data integrity all affect reliability.
  • Logging and retention policies must be designed to prevent uncontrolled storage growth.
  • Backups must cover the actual recovery requirements, not just the main project file.
  • Destructive actions such as formatting or deleting historical data require appropriate authorization and data protection.
  • Storage faults must be diagnosed separately from application, processor, power, and PLC communication faults.
