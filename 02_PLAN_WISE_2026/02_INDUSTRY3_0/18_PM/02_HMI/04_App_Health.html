1. Definition

HMI application health is the condition of the HMI software, runtime environment, configuration, and supporting resources that determine whether the operator interface functions correctly, reliably, and consistently.

An HMI can have a working display and responsive touchscreen while its application is unhealthy. For example, screens may open normally, but PLC values may be stale, alarms may not update, recipes may fail to save, or the application may repeatedly freeze.

Application health monitoring helps maintenance engineers identify software-related problems before they cause production delays, incorrect operator decisions, or loss of required process information.

The objective is to verify that the HMI application is running correctly, displaying valid information, processing operator actions, communicating with connected devices, and maintaining required data.

2. What constitutes a healthy HMI application?

A healthy HMI application should satisfy several conditions:

  • Runtime health: The HMI application starts and remains operational.
  • Screen health: Screens, navigation, graphics, and controls behave correctly.
  • Data health: Displayed values correspond to valid and sufficiently recent data.
  • Communication health: Required PLC and device connections remain functional.
  • Command health: Operator requests are processed and their outcomes are displayed correctly.
  • Alarm health: Alarms are generated, displayed, updated, and acknowledged according to the application design.
  • Storage health: Required configuration, recipes, and records can be accessed and saved.
  • Performance health: Screen updates and user interactions occur within acceptable time limits.
  • Security health: Access controls and permissions function as intended.
  • Recovery health: The application can be restored using the approved project and recovery procedure.

A green status indicator alone does not establish application health. It may represent only one subsystem, such as communication status, rather than the complete HMI application.

3. HMI application architecture

A typical HMI application depends on multiple layers working together.

Operator
   ↓
Display and Touchscreen
   ↓
HMI Application and Runtime
   ├── Screens and Navigation
   ├── Tags and Data Processing
   ├── Alarms and Events
   ├── Recipes and Data Logging
   └── User Management
   ↓
Communication Driver
   ↓
Industrial Network
   ↓
PLC and Connected Devices

The HMI may also depend on an operating system, local storage, databases, license services, network infrastructure, and time synchronization.

A fault in any layer can affect application behavior. Effective troubleshooting therefore requires identifying the failing layer instead of treating every visible problem as an HMI hardware failure.

4. Runtime and application startup health

The HMI runtime is the environment that executes the HMI application on the panel or industrial PC.

Runtime-related problems may include:

  • Application fails to start.
  • Application starts and then closes unexpectedly.
  • Runtime repeatedly restarts.
  • Screens remain blank or partially rendered.
  • Application freezes during startup.
  • Required libraries or components are missing.
  • Project files are incompatible with the installed runtime.
  • A license or activation requirement prevents normal operation.

Diagnostic checks

  1. Confirm that the HMI operating system or panel has completed startup.
  2. Check whether the runtime application is running.
  3. Review error messages and available diagnostic logs.
  4. Verify the installed runtime version and the project's compatibility.
  5. Check available RAM and storage capacity.
  6. Confirm that required files, libraries, and configuration are present.
  7. Review recent changes, including project downloads, software updates, and configuration modifications.
  8. Restore or reinstall application components only through an approved procedure.

Repeatedly restarting an application without identifying the cause can hide useful diagnostic evidence and leave the underlying fault unresolved.

5. Screen and navigation health

Screen health concerns the correct presentation and operation of the HMI's visual elements.

Common issues include missing graphics, incorrect text, broken navigation, overlapping objects, invisible controls, and screens that fail to refresh.

Symptom Possible cause Diagnostic approach
Blank screen area Missing object, rendering problem, or incorrect visibility condition Check object properties and runtime diagnostics
Incorrect value displayed Wrong tag mapping, stale data, or scaling error Verify the tag source, value, units, and update status
Navigation button does nothing Incorrect event configuration or navigation target Check the button action and destination screen
Screen changes slowly Heavy graphics, excessive scripts, or runtime resource limitations Examine application workload and runtime performance
Text or graphics are clipped Resolution, scaling, or layout mismatch Verify display resolution and object positioning
Object appears only sometimes Visibility conditions or state-dependent logic Inspect the conditions controlling object visibility
Controls overlap Incorrect screen layout or resolution conversion Review screen dimensions and object coordinates

A visually correct screen can still contain a serious functional defect. For example, a displayed motor status may be mapped to the wrong PLC tag. Screen verification must include both appearance and data correctness.

6. Tag and data health

An HMI tag connects an application object to a data source, such as a PLC variable, internal HMI variable, or database field.

Data health means that the displayed value is correct, valid, current, and interpreted using the correct engineering units.

Common data-quality problems

  • Incorrect PLC address or symbolic tag mapping.
  • Tag name changed in the PLC project without updating the HMI.
  • Data type mismatch.
  • Incorrect scaling or engineering-unit conversion.
  • Stale values after communication loss.
  • Invalid values displayed as if they were current.
  • Internal HMI variables not updated as intended.
  • Incorrect array indexing or data-block offsets.
  • Excessive polling that increases communication or runtime load.

Example: Analog scaling

Suppose a PLC receives a 4–20 mA signal representing a pressure range of 0–10 bar.

The normalized pressure is:

\[ P = \frac{I-4}{20-4}\times 10 \]

Where \(I\) is the measured current in mA and \(P\) is the pressure in bar.

If the current is 12 mA:

\[ P = \frac{12-4}{16}\times 10 = 5\text{ bar} \]

If the HMI displays 50 bar, the problem could be incorrect scaling, a wrong tag, an incorrect engineering range, or a mismatch between the PLC's value representation and the HMI's interpretation.

The displayed value must be checked against the PLC value, signal range, and intended units.

7. Data freshness and stale values

A displayed value is not necessarily current merely because it remains visible on the screen.

For example, a motor's running indicator may remain green after communication with the PLC has failed if the HMI does not invalidate stale data.

Application health should therefore include the validity and freshness of data.

Useful checks include:

  • Communication status for the relevant device.
  • Last successful data update, where supported.
  • Tag quality or validity indicators.
  • Configured communication timeout.
  • Whether the HMI distinguishes current, invalid, and stale values.
  • Whether communication recovery refreshes the displayed state correctly.

A robust application should make communication failures visible and avoid presenting old values as confirmed current conditions.

8. Alarm and event health

HMI alarms communicate abnormal operating conditions, equipment faults, and events requiring operator attention.

Application health requires more than checking whether an alarm screen opens. The complete alarm lifecycle must behave correctly.

Typical checks include:

  • Alarm conditions are mapped to the correct PLC tags.
  • Alarm activation and clearing follow the intended logic.
  • Alarm text identifies the actual equipment and fault.
  • Alarm priority is assigned appropriately.
  • Timestamps are meaningful and consistent.
  • Acknowledgement works as designed.
  • Historical alarm records are retained where required.
  • Communication failures do not silently suppress important indications.
  • Alarm lists and filters display the correct events.

Important distinctions

Term Meaning
Alarm condition The process or equipment state that triggers an alarm
Alarm activation The HMI or alarm system registers the alarm condition
Acknowledgement An operator confirms awareness of the alarm
Alarm clearing The underlying alarm condition returns to the configured normal state
Alarm history A retained record of alarm occurrences and relevant events

Acknowledging an alarm does not necessarily clear the underlying fault. The HMI should represent these states correctly.

9. HMI-to-PLC command health

An HMI button typically generates a request that is transmitted to the PLC. The PLC then evaluates the request according to its logic, interlocks, operating mode, and current machine state.

A command can fail at several different points:

  1. The touchscreen does not register the input.
  2. The HMI application does not execute the configured action.
  3. The command is not written to the intended PLC tag.
  4. The PLC receives the command but rejects it because a permissive is missing.
  5. The PLC issues an output command, but the connected device does not respond.
  6. The device operates, but feedback does not return correctly to the HMI.

For example, a conveyor Start button may work correctly while the PLC refuses to start the conveyor because a guard-door interlock is open.

The HMI must distinguish between command requested, command accepted, and machine operation confirmed.

Safety-related actions must follow the approved safety architecture. A normal HMI command must not be used to bypass safety interlocks or substitute for a safety-rated function.

10. Performance and responsiveness

Application performance describes how quickly and consistently the HMI responds to operator actions and updates process information.

Factors affecting performance include:

  • CPU utilization on the HMI or industrial PC.
  • Available RAM.
  • Storage speed and free capacity.
  • Number of active screens and graphical objects.
  • Script execution time.
  • Tag polling frequency.
  • Communication latency.
  • Alarm and trend processing workload.
  • Database or network dependencies.
  • Operating-system and runtime faults.

Performance indicators

Indicator What it measures Why it matters
Runtime availability Whether the application remains operational Identifies crashes and unexpected restarts
Screen response time Time taken for a screen or navigation action to complete Measures operator-interface responsiveness
Tag update latency Delay between a source value changing and the HMI reflecting it Identifies stale or delayed process information
Communication error rate Frequency of failed or timed-out exchanges Highlights connectivity or configuration problems
CPU utilization Processor workload Helps identify resource saturation
RAM usage Working memory consumption Helps identify memory pressure
Free storage Remaining usable persistent storage Identifies risk of failed writes or startup problems
Application restart count Number of unexpected restarts over a period Highlights instability
Alarm processing delay Delay between the source condition and the expected alarm indication Helps evaluate alarm responsiveness

Targets should be defined according to the machine's requirements and the HMI manufacturer's specifications. There is no single response-time threshold appropriate for every HMI application.

11. Storage and data persistence health

HMI application health also depends on whether required information can be stored and retrieved correctly.

Potential problems include:

  • Full internal storage.
  • Corrupted application or configuration files.
  • Failed recipe writes.
  • Missing historical records.
  • Database connection failures.
  • Incorrect log-retention configuration.
  • Storage-device degradation.
  • Power interruption during a critical write.

Maintenance checks should verify that required recipes can be saved, application configuration is preserved, and logs are available according to the retention policy.

Before deleting files, clearing logs, formatting media, or reinstalling the runtime, preserve required data and follow the approved recovery procedure.

12. User access and application security

The HMI may expose machine commands, production settings, maintenance functions, and administrative controls.

Application health includes ensuring that these functions are accessible only to the intended users.

Verify that:

  • User roles and permissions operate correctly.
  • Unauthorized users cannot access restricted functions.
  • Administrative access is controlled.
  • Default or obsolete accounts are handled according to site policy.
  • User-management configuration is backed up securely where supported.
  • Application changes are traceable.
  • Security-related faults are recorded and investigated.

An application can be technically operational while still being unhealthy from a security perspective if unauthorized users can change machine parameters or access maintenance controls.

13. HMI application health monitoring

Monitoring can be performed through built-in diagnostics, engineering software, operating-system tools, event logs, and external monitoring systems.

A practical monitoring structure is:

HMI Health Monitoring
        ↓
Runtime Status
        ↓
Screen and Tag Diagnostics
        ↓
PLC Communication Status
        ↓
Alarms and Event Processing
        ↓
Storage and Resource Usage
        ↓
Health Record and Corrective Action

Possible monitoring methods include:

  • Manufacturer-provided runtime diagnostics.
  • HMI system alarms and logs.
  • Engineering software online diagnostics.
  • Operating-system performance monitoring for PC-based HMIs.
  • PLC communication status tags.
  • Database and historian connectivity checks.
  • Centralized maintenance dashboards.

External monitoring must not overload the HMI, interfere with production, or expose control-system services unnecessarily.

14. Systematic troubleshooting procedure

When an HMI application behaves abnormally, isolate the fault before changing the project.

Step 1: Define the symptom

Record the exact behavior, affected screens, time of occurrence, error messages, and whether the fault is continuous or intermittent.

Step 2: Check the basic system state

Verify panel power, runtime status, display response, available storage, and system diagnostics.

Step 3: Check application behavior

Test navigation, screen objects, scripts, alarms, recipes, and other functions that do not depend on the PLC where possible.

Step 4: Check data and communication

Verify PLC connection status, tag mappings, data quality, update behavior, and communication errors.

Step 5: Check PLC-side behavior

If a command reaches the PLC, inspect permissives, interlocks, mode conditions, output commands, and feedback. Follow the required authorization and safety procedures.

Step 6: Check recent changes

Review application downloads, project revisions, firmware changes, network modifications, operating-system updates, and configuration changes.

Step 7: Correct and verify

Apply the approved correction, test the affected functions, confirm that unrelated functions remain operational, and record the result.

Do not immediately reload the HMI project or reboot the complete system. Either action may remove useful evidence, disrupt production, or conceal the underlying fault.

15. Practical industrial example

Consider a production-line HMI that displays conveyor speed, motor status, and fault alarms. Operators report that the screen is responsive, but the speed value remains unchanged even while the conveyor speed varies.

A structured diagnosis proceeds as follows:

  1. Confirm whether the physical conveyor speed is actually changing.
  2. Check the corresponding PLC variable online using the approved engineering tool.
  3. Compare the PLC value with the HMI tag mapping.
  4. Check whether the HMI tag is updating and whether its data quality is valid.
  5. Verify scaling, engineering units, and display formatting.
  6. Inspect communication diagnostics if the PLC value is correct but the HMI remains stale.
  7. Correct the identified mapping, scaling, or communication issue.
  8. Verify that the HMI updates correctly over the required operating range.

If the PLC value changes correctly but the HMI tag points to an obsolete address, the fault is in the HMI configuration, not the sensor or drive.

This distinction avoids unnecessary replacement of healthy field equipment.

16. Preventive maintenance checklist

Routine application checks

  • Confirm that the HMI runtime starts and remains operational.
  • Verify screen navigation and essential operator controls.
  • Check that displayed values are current and correctly scaled.
  • Verify PLC communication and tag quality.
  • Check alarm activation, acknowledgement, and clearing.
  • Confirm recipe saving and required data logging.
  • Review runtime errors and unexpected restarts.
  • Check free RAM and persistent storage where supported.

Periodic engineering checks

  • Compare the installed application with the approved project revision.
  • Verify HMI project backups and recovery documentation.
  • Check firmware, runtime, and engineering-software compatibility.
  • Review user permissions and application security.
  • Check performance trends and recurring faults.
  • Document changes and corrective actions in the approved maintenance system.

17. Key principles

  • HMI application health covers runtime, screens, data, communication, alarms, storage, performance, and security.
  • A responsive display does not prove that process information is current or correct.
  • HMI requests, PLC acceptance, and actual machine feedback must be distinguished.
  • Troubleshooting should isolate the display, application, communication, PLC logic, and field-device layers.
  • Project restoration and application changes must follow backup, authorization, and validation procedures.
  • Effective application health monitoring reduces avoidable downtime and helps prevent misleading operator indications.
