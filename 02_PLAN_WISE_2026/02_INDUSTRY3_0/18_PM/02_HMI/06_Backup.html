1. Definition

HMI backup is the process of creating and maintaining recoverable copies of the HMI application, configuration, communication settings, runtime-related files, and other required system data so that the HMI can be restored after hardware failure, software corruption, accidental modification, cyber incident, or equipment replacement.

In industrial maintenance, an HMI backup is not simply a copy of a project file. A useful backup must contain the correct version of the application and all necessary supporting information to restore the intended functionality on compatible hardware and software.

For example, if an HMI panel controlling an automotive assembly station fails, maintenance should be able to replace the panel, restore the approved project, re-establish PLC communication, verify alarms and operator commands, and return the station to service through an authorized recovery procedure.

The objective is recoverability, not merely file storage. A backup that cannot be restored is just a collection of files with an inflated sense of importance.

2. Purpose of HMI backup

HMI backups protect against several types of failure:

  • HMI hardware failure or replacement.
  • Corrupted runtime application or operating system.
  • Accidental deletion or modification of screens, tags, scripts, or recipes.
  • Incorrect communication settings.
  • Failed firmware updates or software migrations.
  • Loss of user accounts or configuration.
  • Malware, ransomware, or unauthorized changes.
  • Loss of historical data or locally stored recipes, where these are within the backup scope.
  • Vendor software upgrades that introduce incompatibility.
  • Loss of the original engineering computer or project files.

A controlled backup also supports troubleshooting, change comparison, audit readiness, disaster recovery, and the long-term maintenance of obsolete industrial equipment.

3. What must be backed up?

The backup scope depends on the HMI model, operating system, engineering software, and application architecture.

Backup item Typical contents Why it matters
Engineering project Screens, tags, scripts, navigation, object properties Allows application editing and redevelopment
Deployable runtime Compiled or downloadable application files May be required to restore the running application
Communication configuration PLC addresses, driver settings, protocol parameters Restores data exchange with controllers
Alarm configuration Alarm definitions, priorities, messages, limits Restores alarm behavior and presentation
Recipe data Production recipes, setpoints, parameter sets Prevents loss of production configuration
User configuration Accounts, roles, permissions, security settings Restores approved access controls
Runtime settings Startup behavior, application parameters, supported system settings Helps reproduce the original operating environment
Historical data Locally stored alarm logs, trends, or databases Preserves records when required by the application
Device configuration Panel settings, network settings, supported OS configuration Reduces replacement and commissioning effort
Version information Software versions, firmware, driver versions, licenses Helps identify a compatible restoration environment
Supporting documentation Drawings, tag lists, communication maps, recovery procedures Supports correct restoration and verification

Not every item can be backed up through the same mechanism. Some data belongs to the engineering project, some to the deployed panel, and some to an external server or database.

For example, backing up an HMI project does not automatically back up a separate SQL database or the alarm history stored on a SCADA server.

4. Types of HMI backup

4.1 Engineering project backup

An engineering project backup preserves the editable application in the appropriate development environment.

It may include:

  • Screen definitions and navigation.
  • HMI tag definitions.
  • Alarm configuration.
  • Scripts and macros.
  • Communication driver configuration.
  • User-interface objects.
  • Recipes or application-level data definitions.
  • Project-level security configuration.

This is usually the most useful backup for long-term maintenance because it allows authorized engineers to modify and rebuild the application.

However, the exact contents depend on the engineering platform and project structure. External libraries, scripts, databases, and linked files may need separate collection.

4.2 Runtime backup

A runtime backup preserves the deployed application or its runtime representation.

Depending on the platform, it may contain a compiled application, a deployable image, or a vendor-specific transfer package.

A runtime backup can be useful when the original engineering project is unavailable, but it may not allow full editing or reconstruction.

Important distinction: A runtime upload from a panel is not guaranteed to recreate the original editable engineering project. Some platforms do not support reverse engineering, or they may omit comments, source files, scripts, or other engineering information.

4.3 Full-device backup

A full-device backup attempts to capture a broader set of device contents or configuration.

Depending on the HMI, this might include:

  • Application files.
  • Supported operating-system settings.
  • Device configuration.
  • Persistent data.
  • System image or recovery image.

This type of backup is hardware- and vendor-dependent. A standard project export should not be assumed to be a complete device image.

4.4 Data backup

A data backup protects information stored separately from the engineering application, such as:

  • Recipes.
  • Operator-entered parameters.
  • Local historical records.
  • Alarm history.
  • Trend data.
  • Audit records.
  • User-managed files.

Some of this data changes continuously. Its backup method and frequency must account for data consistency and retention requirements.

4.5 Version-control backup

Version control preserves identifiable application revisions and the history of approved changes.

It can help answer:

  • Which project version is installed?
  • What changed between two revisions?
  • Who approved a modification?
  • Which revision was operating before a fault?
  • Which version should be restored?

Version control complements backups but does not replace off-device recovery copies or a tested restoration process.

5. Backup architecture

A robust backup arrangement separates the working copy from recoverable copies.

Engineering Workstation
        ↓
Approved HMI Project
        ↓
Versioned Backup Copy
        ↓
Controlled Network Repository
        ↓
Separate Recovery Copy
        ↓
Periodic Restore Verification

A production HMI should not be the only location containing its application. A failed panel, corrupted storage device, or compromised workstation could otherwise eliminate the only available copy.

A practical arrangement may include:

  • A controlled engineering workstation.
  • A versioned project repository.
  • A secured maintenance file server.
  • An independent recovery copy.
  • A documented restoration procedure.
  • A record of the latest successful restoration test.

Where the plant supports offline or immutable backups, these can improve recovery from ransomware and accidental deletion. Access must be restricted according to the site's OT cybersecurity policy.

6. Backup methods

6.1 Upload from the HMI

The engineering tool retrieves an application or supported project representation from the deployed HMI.

Advantages:

  • Can recover a copy when the original engineering workstation is unavailable.
  • May capture the actual deployed application.
  • Can help compare the installed application with the approved project.

Limitations:

  • The panel may not support uploading.
  • The uploaded package may be runtime-only.
  • Source code, comments, libraries, or external data may be missing.
  • The deployed application may already contain undocumented changes.
  • Access credentials or compatible software may be required.

Before using an uploaded project as the master copy, verify its completeness and compare it against the approved baseline.

6.2 Download from the engineering project

The approved project is transferred from the engineering environment to the HMI.

This is normally a deployment operation rather than a backup operation. The source project should be backed up before deployment.

Downloading a project may overwrite the existing application or affect production. Use the approved change procedure, confirm the correct target device, and arrange a controlled downtime window where required.

6.3 Removable storage backup

Some HMI panels support project export, device backup, or data export to an approved removable storage device.

Important controls include:

  • Verify compatibility with the panel.
  • Use authorized, malware-checked media.
  • Confirm the exported files are complete.
  • Record the date, version, and source device.
  • Copy the backup to controlled storage.
  • Avoid leaving sensitive files on unprotected removable media.

Do not assume that copying files from a USB port creates a complete HMI backup. Use the manufacturer's supported procedure.

6.4 Automated backup

Some engineering environments and device-management systems support scheduled or automated backups.

Automation may reduce missed backups, but it must account for:

  • Project file consistency.
  • Version identification.
  • Access permissions.
  • Failed jobs and missing files.
  • Storage capacity.
  • Retention rules.
  • Backup integrity checks.
  • Recovery testing.

A scheduled job that silently fails every night is not a backup strategy. It is a recurring administrative decoration.

7. Backup procedure

A controlled backup should follow a repeatable process.

Step 1: Identify the HMI

Record the equipment and software details before starting.

  • HMI manufacturer and model.
  • Equipment ID and production line.
  • Panel serial number, where required.
  • Firmware or operating-system version.
  • Engineering software and version.
  • Runtime version.
  • Installed application version.
  • Communication driver information.

These details help determine which files and tools are needed for restoration.

Step 2: Confirm the approved source

Determine which project is the authorized baseline.

Possible sources include:

  • The approved engineering repository.
  • A controlled project on the engineering workstation.
  • A verified upload from the installed HMI.
  • A previous approved backup with a known version.

Do not overwrite the master project with an unverified upload from a live panel. First preserve the existing baseline and investigate any differences.

Step 3: Check the current application state

Where supported, confirm:

  • The application is running normally.
  • There are no active backup-related errors.
  • The project can be opened by the appropriate engineering software.
  • Required external files and libraries are available.
  • Recipe or historical data requiring a separate backup is identified.

For databases or continuously changing data, use an application-consistent export or supported database backup method.

Step 4: Create the backup

Use the supported engineering software or vendor procedure.

Include the required project, runtime, data, and configuration components identified in the backup scope.

If the system requires a shutdown or transfer mode, obtain the necessary production authorization before proceeding.

Step 5: Assign a version and metadata

Each backup should have a unique and meaningful identity.

Example filename:

LINE1059_HMI_STATION03_2026-10-16_V1.4.2_PROJECT.zip

The example is a naming convention only. Use the site's approved format.

Record:

  • Equipment ID.
  • Application name.
  • Version or revision.
  • Backup date and time.
  • Source device or workstation.
  • Engineering software version.
  • Firmware/runtime version.
  • Person or role performing the backup.
  • Backup type.
  • Verification result.

Avoid vague filenames such as final.zip, final_new.zip, or final_really_final.zip. Human beings have a long history of making those filenames less final with every edit.

Step 6: Store the backup securely

Store the backup in the designated repository and ensure that a separate recovery copy exists when required.

Apply:

  • Appropriate access controls.
  • Encryption where required.
  • Approved retention rules.
  • Malware scanning.
  • Separation from the production HMI.
  • Protection against accidental overwrite.
  • Independent recovery storage where supported.

Step 7: Verify backup integrity

Check that:

  • The backup operation completed successfully.
  • The expected files exist.
  • The archive or package can be opened.
  • File sizes are plausible.
  • The version metadata matches the record.
  • Checksums match where the site uses them.
  • Required dependencies are present.

A checksum can help detect accidental corruption or unintended file changes, but it does not prove that the application is functionally correct.

Step 8: Verify recoverability

Where practical, restore the backup in a suitable test environment or compatible spare panel.

Confirm that the project opens and that its required dependencies are available. Functional testing should verify screens, tag mapping, communication, alarms, recipes, permissions, and application startup.

A production download should not be used as an improvised backup-validation experiment.

8. Backup frequency and retention

The required backup frequency depends on how often the HMI changes, the criticality of the equipment, and the time required to recover production.

Event or condition Recommended backup action
Initial commissioning Create and verify the approved baseline
Before an approved modification Preserve the current approved version
After a successful modification Back up the new approved version
After firmware or runtime upgrade Preserve project and relevant compatibility information
After HMI replacement Back up the verified restored configuration
After recipe or data changes Back up data according to its change rate and business importance
Periodic maintenance Verify backup availability and integrity
Before decommissioning an engineering workstation Confirm that all required project files are transferred
After a recovery test Record the result and any corrective actions

A backup policy should define both frequency and retention. Keeping only the latest backup can be inadequate if a defect or malicious change remains undetected for a long time.

A useful approach is to retain:

  • The current approved version.
  • The previous known-good version.
  • Relevant change-point backups.
  • Periodic recovery copies according to the site's retention policy.

Retention must balance recoverability, storage capacity, legal or quality requirements, and cybersecurity.

9. Recovery Time Objective and Recovery Point Objective

Two important concepts help define backup requirements.

Recovery Time Objective (RTO) is the target time within which the system or process should be restored after a disruption.

Recovery Point Objective (RPO) is the maximum acceptable amount of data loss measured in time.

For example, suppose a production station requires restoration within 60 minutes and recipe changes must not be lost beyond the last 15 minutes of operation.

  • RTO: 60 minutes.
  • RPO: 15 minutes for the specified recipe data.

These are illustrative targets, not universal industrial requirements. The plant must define appropriate values based on production impact, data criticality, and recovery capability.

The RTO must account for the complete restoration process, including hardware replacement, software availability, licensing, network configuration, download, and functional validation. Copying the project file may take only minutes while restoring the station takes much longer.

10. HMI restoration procedure

Restoration is the process of returning the HMI to a verified operational state using an approved backup.

Step 1: Assess the failure

Determine whether the failure is caused by:

  • HMI hardware.
  • Corrupted application files.
  • Operating-system or firmware failure.
  • Communication configuration.
  • A recent application change.
  • Network or PLC-side problems.
  • External data storage.

Do not assume that a frozen screen always requires a full project restoration.

Step 2: Confirm compatibility

Verify that the replacement HMI or recovery environment supports the selected project.

Check:

  • Hardware model and display resolution.
  • Firmware and operating-system version.
  • Runtime version.
  • Engineering software version.
  • Communication drivers.
  • Required licenses.
  • Application dependencies.
  • Supported transfer and conversion paths.

A project from a newer engineering environment may not run on an older panel without conversion or modification.

Step 3: Select the correct backup

Use the latest approved, verified version that matches the target equipment and required configuration.

If the latest backup is suspected to contain the fault, use an earlier known-good version and investigate the differences.

Step 4: Prepare the target

Follow the manufacturer's replacement and recovery procedure.

Confirm power, network interfaces, storage, device identity, and approved network settings.

Where device replacement requires a new IP address or other identity change, update the controlled configuration records and verify the impact on other connected systems.

Step 5: Restore the application

Transfer or install the project using the supported engineering or recovery tool.

Restore any required external configuration and data separately.

Do not overwrite PLC programs or unrelated machine configurations unless explicitly required by an approved recovery plan.

Step 6: Verify communication

Confirm that the HMI communicates with the intended PLCs and devices.

Check:

  • Correct endpoints and protocol settings.
  • Valid tag values.
  • Communication status and quality.
  • Appropriate data update behavior.
  • Correct scaling and engineering units.

Step 7: Perform functional validation

Verify the following before authorizing return to production:

  • Screen navigation.
  • Equipment status indicators.
  • Alarm display and acknowledgment behavior.
  • Recipe access and critical parameters.
  • User roles and permissions.
  • Operator command and acknowledgment behavior.
  • Trends and historical data, where applicable.
  • Communication-loss and recovery indications.
  • Application startup after a controlled restart.

Test machine functions only under the approved commissioning and production-safety procedure. Never bypass safety interlocks to accelerate restoration.

Step 8: Record recovery and close the maintenance activity

Document the backup version used, failed component, replacement details, restoration actions, test results, downtime, and unresolved issues.

Update the master backup only after the restored application has been verified and formally approved.

11. Practical industrial example: HMI panel failure

Consider an HMI panel on an automotive assembly station that no longer boots.

The maintenance team has the following:

  • An approved editable project.
  • A deployable runtime package.
  • The PLC communication configuration.
  • The relevant firmware and software compatibility information.
  • A documented recovery procedure.

A controlled recovery proceeds as follows:

  1. Confirm the panel failure and rule out an external power or network issue.
  2. Replace the failed panel with a compatible approved spare.
  3. Restore the approved application and required configuration.
  4. Verify PLC communication and critical tag values.
  5. Validate alarms, recipes, user permissions, and operator controls.
  6. Confirm that safety-related functions remain under the intended safety system.
  7. Conduct the approved functional checks.
  8. Record the recovery time, backup revision, replacement details, and test results in SAP PM or the site's maintenance system.

If the only available backup is a runtime package that cannot be restored to the replacement panel, the recovery process may require additional engineering work. This is why backup compatibility must be established before a failure occurs.

12. Common HMI backup failures

Problem Likely cause Corrective action
Backup file cannot be opened Corruption, incomplete transfer, unsupported format Retrieve another verified copy and inspect integrity
Project opens but cannot compile Missing libraries, software mismatch, unsupported project version Restore dependencies and use a compatible engineering environment
Restored HMI cannot communicate with PLC Incorrect IP address, driver, endpoint, or tag configuration Compare against approved communication records
Application runs but screens are missing Incomplete project or missing external resources Recover the complete project and its dependencies
Recipes are missing after restoration Recipe data stored separately from the project Restore the recipe dataset using the supported procedure
Historical alarms are missing History stored in a separate database or local storage Restore the appropriate data source if records are recoverable
HMI requests an unavailable license License not included in the backup or not transferable Follow the vendor's approved licensing procedure
Backup is older than the installed project Backup schedule missed or change control not followed Compare revisions and establish a controlled current baseline
Replacement panel rejects the project Hardware, firmware, runtime, or software incompatibility Verify the supported migration or restoration path
Restored application has incorrect permissions User configuration was not included or is device-specific Restore and validate access controls using approved methods

13. Vendor-specific considerations

The exact backup method differs between HMI platforms.

Platform Engineering environment or family Important consideration
Siemens HMI WinCC and supported TIA Portal environments Project version, panel generation, runtime version, and transfer method must be compatible
Rockwell Automation FactoryTalk View and PanelView families Backup procedure differs between terminal models and application types
Mitsubishi Electric GOT/GOT2000 and GT Designer3 Project transfer, panel data, and supported backup functions depend on the GOT model
PC-based HMI Vendor-specific runtime on Windows or another supported OS Project files, runtime configuration, licenses, operating system, and external services may need separate protection
Web-based HMI Browser or server-hosted application Server-side project, client configuration, certificates, identity services, and external data sources may need separate backup

Do not apply a backup procedure from one HMI family to another without checking the manufacturer's documentation.

14. Cybersecurity and backup protection

HMI backups may contain network addresses, operational details, scripts, account configuration, and sensitive production information.

Protect them accordingly:

  • Restrict write access to approved personnel.
  • Keep recovery copies separate from production systems.
  • Use approved encryption and access controls.
  • Scan files obtained from removable media.
  • Avoid storing passwords in plain-text project notes.
  • Protect backup repositories from unauthorized deletion.
  • Retain records of approved changes.
  • Validate restored applications before reconnecting them to production.
  • Follow the site's procedures for suspected malware or compromised backups.

A backup from a compromised system may contain the same malicious changes as the live application. In a cybersecurity incident, select a known-good revision, verify its provenance, and follow the incident-response process before restoration.

15. HMI backup checklist

Before backup

  • Confirm the HMI equipment ID and application.
  • Identify the approved project version.
  • Record the engineering software, runtime, and firmware versions.
  • Identify external libraries, databases, recipes, and other dependencies.
  • Confirm that the operation is authorized and will not disrupt production.

During backup

  • Use the supported vendor procedure.
  • Include all required project and configuration components.
  • Capture separate data stores when they are in scope.
  • Assign a clear version and backup date.
  • Store the backup in the approved repository.

After backup

  • Confirm the backup operation completed.
  • Verify that the files can be opened and inspected.
  • Check file integrity and metadata.
  • Confirm that a separate recovery copy exists where required.
  • Record the backup in the maintenance or configuration register.
  • Perform restoration testing according to the approved schedule.

16. HMI restoration checklist

  • Confirm the root cause and scope of the failure.
  • Verify the target HMI hardware and software compatibility.
  • Select an approved known-good backup.
  • Restore the application using the supported method.
  • Restore required communication settings and external data.
  • Verify PLC communication and tag quality.
  • Test screens, alarms, recipes, permissions, and commands.
  • Complete approved functional and safety-related verification.
  • Record the backup revision and restoration results.
  • Update the approved baseline after successful validation.

17. Key principles

  • An editable engineering project and a deployable runtime are not necessarily equivalent.
  • HMI backups must include all required dependencies and separately stored data.
  • Backups should be versioned, secured, verified, and stored independently of the production panel.
  • Compatibility must be confirmed before a restoration is needed.
  • A successful file copy does not prove that a backup can restore a functioning machine.
  • Periodic restoration testing is essential for demonstrating recoverability.
  • The final restored HMI must undergo functional validation before return to production.
  • Backup management is part of industrial maintenance, configuration control, and OT cybersecurity.
