1. Definition

HMI communication is the exchange of data between a Human-Machine Interface (HMI) and connected systems such as PLCs, remote I/O, drives, CNC controllers, SCADA servers, databases, and other industrial devices.

Communication allows the HMI to display live process values, show equipment status, receive alarms, and transmit operator commands to the control system.

For example, in an automotive production line, an HMI may communicate with a Siemens S7-1500 PLC over PROFINET or an Allen-Bradley ControlLogix PLC over EtherNet/IP. The HMI reads motor status, conveyor speed, interlock conditions, and fault codes, then sends authorized operator requests to the PLC.

The central maintenance principle is that HMI communication must be evaluated in terms of connectivity, data validity, update performance, and command behavior. A connected device does not automatically mean that all its tags are updating correctly.

2. Purpose of HMI communication

HMI communication supports the following functions:

  • Reading PLC tags and process variables.
  • Displaying machine modes, sequence states, and equipment feedback.
  • Sending operator requests such as Start, Stop, Reset, and mode selection.
  • Displaying alarms, diagnostics, and fault codes.
  • Reading and writing recipes and setpoints.
  • Exchanging data with SCADA, historians, databases, or production systems.
  • Supporting maintenance diagnostics and machine troubleshooting.
  • Synchronizing relevant data across connected industrial systems.

Communication design must also preserve machine safety. Safety functions must be implemented through the required safety-rated hardware and logic, not assumed to be protected simply because an HMI communicates with a PLC.

3. HMI communication architecture

A common industrial architecture is:

Operator
   ↓
HMI Application
   ↓
HMI Communication Driver
   ↓
Industrial Ethernet or Serial Network
   ↓
PLC / CNC / VFD / Remote I/O
   ↓
Sensors, Actuators and Machines

A larger system may include additional layers:

Local HMI
   ↓
PLC Network
   ↓
SCADA Server
   ↓
Historian / SQL Database
   ↓
Production Reporting / Analytics

Each connection is a potential failure point. For example, a local HMI may communicate correctly with its PLC while the SCADA server fails to receive data because of a separate network or server issue.

Troubleshooting must identify which connection and data path are actually affected.

4. Communication types

HMI communication can be classified by physical medium, protocol, and communication pattern.

4.1 Physical communication media

Medium Common application Main considerations
Industrial Ethernet HMI-to-PLC and HMI-to-SCADA communication Network configuration, switches, cabling, addressing, latency
Serial RS-232 Point-to-point legacy equipment connections Limited distance, baud rate, wiring and grounding
Serial RS-485 Multidrop connections to compatible industrial devices Termination, biasing, topology, device addressing
USB Engineering, transfer, or supported peripheral connections Compatibility, access control, connector condition
Fiber optic Ethernet Long-distance or electrically noisy industrial networks Optical transceivers, fiber condition, link status
Wireless Ethernet Mobile terminals and selected industrial applications Coverage, interference, roaming, security, reliability

The medium and the protocol are different concepts. Ethernet describes the network technology and physical/data-link behavior, while protocols such as EtherNet/IP and Modbus TCP define how devices exchange application data.

4.2 Communication protocols

Protocol Typical use Important characteristic
PROFINET Siemens and other compatible industrial automation devices Industrial Ethernet communication with different performance and real-time capabilities
EtherNet/IP Allen-Bradley/Rockwell Automation and compatible devices Uses the Common Industrial Protocol over Ethernet and IP
Modbus TCP PLCs, meters, drives, and industrial instruments Uses client/server communication and register-based data access
Modbus RTU Serial-connected industrial devices Uses serial framing, device addresses, and register-based data access
OPC UA Industrial data exchange between supported systems Structured information models and configurable security mechanisms
OPC DA Legacy Windows-based data exchange COM/DCOM-based technology
Mitsubishi MC Protocol Mitsubishi PLC communication in supported configurations Device access depends on PLC model and communication settings
Siemens S7 communication Siemens PLC communication using supported drivers and configurations Supported access depends on CPU, firmware, configuration, and driver
Vendor-specific protocols OEM machines and specialized equipment May require a dedicated driver, gateway, or engineering package

Protocol support varies by HMI model, PLC family, firmware, driver license, and configuration. Never assume that two Ethernet-equipped devices can communicate directly merely because they share the same connector.

5. Client/server and communication patterns

An HMI usually initiates or maintains communication according to its configured driver and protocol.

Common patterns include:

  • Client/server: One system requests data or services from another. Modbus TCP and many HMI driver connections follow this general pattern.
  • Cyclic or periodic exchange: Data is updated according to a configured interval or communication cycle.
  • Subscription-based exchange: A client subscribes to data changes or monitored values, as supported by protocols such as OPC UA.
  • Producer/consumer exchange: Data is produced by one device and consumed by one or more subscribers. EtherNet/IP supports this model for appropriate connection types.
  • Request/response: A request is sent and a corresponding response is returned.

A particular protocol can support more than one communication pattern. The correct behavior depends on the protocol service, device implementation, and configuration.

A communication connection typically requires several parameters to match the actual system.

7. IP addressing and subnet configuration

For Ethernet communication, the HMI and PLC must have compatible network configurations and a valid path between them.

For example:

Device IP address Subnet mask
HMI 192.168.10.10 255.255.255.0
PLC 192.168.10.20 255.255.255.0
Engineering PC 192.168.10.30 255.255.255.0

These devices are in the same IPv4 subnet, assuming the mask is configured correctly and the network is connected.

Common addressing faults

  • Duplicate IP addresses.
  • Incorrect subnet mask.
  • Incorrect gateway where routing is required.
  • Wrong destination IP in the HMI project.
  • Incorrect VLAN assignment.
  • Disabled switch port.
  • Incorrect physical network connection.
  • Firewall rules blocking required traffic.
  • Device replacement without updating the approved address record.

A successful ping can establish basic IP reachability, but it does not prove that the application protocol, PLC driver, tag mapping, or write operations are functioning.

8. PLC tag addressing and data types

HMI tags must reference the intended PLC data points and interpret their values correctly.

For example, an HMI might display the following PLC information:

HMI tag PLC source Data type Purpose
Conveyor_Run_FB PLC running feedback BOOL Displays running state
Conveyor_Speed PLC speed value REAL Displays speed
Drive_Fault_Code PLC diagnostic value INT Displays fault information
Conveyor_Start_Req PLC command interface BOOL or structured command Requests a start operation

The exact PLC address or symbolic tag depends on the controller platform and program design.

Common tag-mapping problems

  • HMI tag points to the wrong PLC variable.
  • PLC variable name or data structure changed.
  • Incorrect array index or structure member.
  • Wrong data type.
  • Incorrect signed or unsigned interpretation.
  • Incorrect byte order or word order for mapped data.
  • Incorrect scaling or units.
  • Read access works, but write access is restricted.
  • PLC optimization or access settings prevent the configured driver from reading a tag.

A tag must be verified at both ends: the intended PLC value and the HMI's interpretation of that value.

9. Read and write communication

Read communication

The HMI obtains data from the PLC or another source and displays it.

Examples include:

  • Motor running feedback.
  • Pressure and temperature.
  • Machine cycle status.
  • VFD frequency feedback.
  • Alarm codes.
  • Production counts.

Write communication

The HMI sends a value or request to a connected device.

Examples include:

  • Operator setpoint entry.
  • Recipe selection.
  • Manual-mode request.
  • Reset request.
  • Start or stop request.

Read and write permissions may be configured differently. An HMI can successfully display PLC data while failing to write commands because of access restrictions, incorrect tag configuration, unsupported services, or PLC logic.

A successful write does not necessarily mean that the machine has performed the requested action. The PLC may reject the request, an interlock may remain active, or the physical device may fail to respond.

A robust design uses separate command, acceptance, status, and fault information where appropriate.

10. Communication update rate and polling

The update rate determines how frequently data is refreshed, requested, or reported.

For example, an HMI may read a motor status more frequently than a slow-changing maintenance counter. The appropriate rate depends on the process, protocol, number of tags, PLC capacity, and network load.

Communication loading

Increasing polling frequency can improve responsiveness, but it also increases communication workload.

The impact depends on factors such as:

  • Number of subscribed or polled tags.
  • Number of connected HMIs.
  • Size of each data request.
  • Protocol overhead.
  • PLC communication capacity.
  • Network traffic.
  • Driver scheduling and batching behavior.
  • Runtime processing and screen updates.

For a simplified periodic polling model, the number of requests per second can be estimated as:

\[ R = \frac{N}{T} \]

Where:

  • \(R\) = requests per second.
  • \(N\) = number of independent requests.
  • \(T\) = polling interval in seconds.

If 20 independent requests are each sent every 0.5 seconds:

\[ R = \frac{20}{0.5} = 40 \]

This simplified estimate assumes one request per configured item per interval. Real drivers may combine multiple tags into one request, use subscriptions, or employ other scheduling methods, so the actual network load may differ substantially.

Do not reduce all polling intervals indiscriminately to fix slow screens. First identify whether the bottleneck is the network, PLC, driver, runtime, or application design.

11. Timeout, retry, and reconnect behavior

Communication timeouts and retries determine how the HMI responds when a device fails to reply.

  • Timeout: Maximum permitted wait for a response.
  • Retry: An additional attempt after an unsuccessful request.
  • Reconnect: Attempt to re-establish a failed communication session.
  • Communication-loss indication: A visible or recorded indication that communication is unavailable.
  • Recovery validation: Confirmation that valid data is flowing again after reconnection.

A timeout that is too short may produce nuisance communication alarms during temporary delays. A timeout that is too long may delay fault detection.

Excessive retries can increase network load during a fault. Reconnect behavior should therefore be configured according to vendor recommendations and operational requirements.

When communication recovers, the HMI should refresh values and restore valid status indications without incorrectly presenting old data as current.

12. Communication diagnostics

Communication diagnostics help distinguish between physical network faults, protocol failures, configuration errors, and tag-level problems.

Useful diagnostic information

  • Device connection state.
  • Driver status and error codes.
  • Request timeout count.
  • Failed transaction count.
  • Last successful communication time, where available.
  • Tag quality and validity.
  • PLC connection diagnostics.
  • Network link status.
  • Switch-port errors and packet statistics.
  • Serial communication errors.
  • OPC UA session and subscription status, where applicable.

Diagnostic tools

Tool Main purpose Limitation
Ping Checks basic IP reachability Does not verify application data exchange
Engineering software Checks PLC state and controller-side diagnostics May require authorized access and can affect live systems if used carelessly
HMI diagnostics Shows driver and application communication faults Detail varies by vendor
Switch diagnostics Shows link, port, and traffic conditions Does not establish that PLC tags are correct
Packet capture Examines network traffic and protocol exchanges Requires expertise, authorization, and correct capture location
Protocol test client Checks supported protocol services and responses Can introduce risk if it performs writes or unsupported requests
Serial diagnostic tool Checks serial settings and communication behavior Must use compatible electrical interfaces and safe connection practices

Diagnostic testing should follow site cybersecurity and operational procedures. Avoid unauthorized scans, disruptive traffic generation, or writes to production equipment.

13. Troubleshooting HMI communication faults

Step 1: Identify the scope

Determine whether the issue affects:

  • One tag.
  • One screen.
  • One HMI.
  • One PLC.
  • Multiple devices on the same network.
  • The entire HMI-to-PLC connection.

The scope often narrows the likely fault domain.

Step 2: Verify the physical connection

Check the relevant Ethernet link indicators, cables, connectors, switch ports, power supplies, and serial wiring where applicable.

Do not disconnect live industrial network connections without following the approved procedure.

Step 3: Verify addressing and routing

Check the configured device address, subnet mask, gateway, VLAN, and routing path as applicable.

Confirm that the HMI is targeting the intended PLC, particularly after equipment replacement or panel migration.

Step 4: Verify protocol and driver configuration

Confirm that the selected protocol, PLC family, endpoint, port, rack/slot, serial parameters, and required driver components match the installed devices.

Step 5: Check controller-side diagnostics

Use approved engineering tools to confirm that the PLC is running as expected, the relevant communication interface is healthy, and the required data is accessible.

Step 6: Check tag mappings and permissions

Compare HMI tags against the approved PLC program and data definitions. Verify data types, addresses, scaling, and read/write access.

Step 7: Evaluate communication performance

Review timeouts, failed requests, latency, connection limits, network errors, and polling load.

Step 8: Verify recovery

After correcting the cause, confirm that data updates correctly, alarms behave as intended, operator commands receive the expected responses, and the fault does not recur.

Record the root cause and corrective action in the approved maintenance record.

14. Common symptoms and likely causes

Symptom Possible causes First checks
Entire PLC connection is lost Cable, switch, power, IP configuration, PLC interface, driver fault Link status, addressing, PLC diagnostics
One tag shows an incorrect value Wrong address, data type, scaling, or mapping Compare PLC value and HMI tag configuration
Values freeze but connection appears active Stale cache, partial communication fault, tag subscription issue, application fault Tag quality, update timestamp, driver diagnostics
Read works but write fails Access restrictions, incorrect write mapping, PLC logic, protocol limitation Permissions, target tag, PLC command handling
Communication is intermittent Loose connection, network errors, duplicate IP, resource load, unstable device Switch counters, cabling, device logs
HMI updates slowly Excessive polling, network load, slow PLC response, overloaded runtime Driver metrics, PLC workload, application resources
Multiple HMIs lose the same PLC PLC-side fault, common switch, shared network path, PLC connection limit Common network components and PLC diagnostics
One HMI loses several PLCs HMI network interface, local switch, configuration, runtime or driver issue HMI interface, local network, runtime diagnostics
Values recover after restart but fail again Underlying resource, driver, network, or configuration problem Preserve logs and investigate recurrence
Serial device fails to communicate Incorrect baud rate, parity, wiring, termination, addressing Verify serial settings and physical topology

These are diagnostic starting points, not definitive fault identifications.

15. Practical industrial example: Allen-Bradley PLC and HMI

Consider an HMI connected to a ControlLogix PLC through EtherNet/IP. The operator can see the machine status, but the Reset button does not clear the displayed fault.

A disciplined diagnosis is:

  1. Confirm whether the displayed fault corresponds to the actual PLC fault state.
  2. Check whether the Reset button changes the intended HMI command tag.
  3. Check whether the PLC receives the reset request.
  4. Inspect the PLC logic to determine whether the request is accepted.
  5. Verify whether a required permissive or reset condition is missing.
  6. Check the actual device feedback and whether the fault-clearing condition is satisfied.
  7. Confirm that the HMI displays the updated status after the PLC processes the request.

If the PLC receives the reset request but rejects it because a guard-door condition is not satisfied, the communication link may be completely healthy. The issue is in the control conditions, not necessarily the HMI or network.

The operator must never be instructed to bypass a safety condition merely to clear an HMI indication.

16. Practical industrial example: Modbus TCP drive communication

Suppose an HMI reads speed and fault information from a VFD over Modbus TCP.

The speed value displays correctly, but the fault code is wrong.

Check the following:

  • Correct drive IP address and Modbus TCP endpoint.
  • Correct register address and addressing convention.
  • Correct register width and data type.
  • Whether the register is read-only or requires a particular access method.
  • Whether the value requires signed interpretation or scaling.
  • Whether the drive manual defines a different register for the fault code.
  • Whether the HMI is displaying the correct tag.

Some manuals use zero-based register offsets while others display human-readable register numbers. An offset mismatch can cause a valid communication response containing the wrong data.

The solution is to verify the manufacturer's register map and the HMI driver's addressing convention rather than assuming the network is faulty.

17. Industrial network reliability and cybersecurity

HMI communication must be reliable without weakening the security of the operational technology network.

Recommended practices include:

  • Separate OT networks from enterprise networks according to the approved architecture.
  • Use firewalls and controlled communication paths between network zones.
  • Restrict access to required protocols and endpoints.
  • Maintain accurate IP address, device, and switch-port records.
  • Use managed switches and appropriate network diagnostics.
  • Disable unused services and ports where supported and approved.
  • Control engineering access and remote connections.
  • Use approved firmware and communication-driver versions.
  • Back up network and communication configurations.
  • Monitor recurring errors and unexplained configuration changes.

Industrial protocols may not provide encryption or authentication in every implementation. Security controls must therefore account for the capabilities and limitations of the specific protocol and device.

Avoid making network changes on a live production line without authorization, impact assessment, and a recovery plan.

18. Preventive maintenance checklist

Routine checks

  • Verify communication status for critical PLCs and connected devices.
  • Check whether critical HMI values update and remain valid.
  • Review communication alarms and recurring timeouts.
  • Inspect visible network link indicators and relevant connections.
  • Confirm that operator commands receive the expected PLC responses.
  • Review unresolved communication faults.

Periodic engineering checks

  • Compare HMI communication settings against approved documentation.
  • Verify IP addresses, protocol settings, device addresses, and tag mappings.
  • Review switch-port errors and network utilization where available.
  • Confirm driver and firmware compatibility.
  • Check communication timeout and retry settings.
  • Verify recovery behavior after an approved communication interruption test.
  • Back up the HMI project and relevant configuration before approved changes.
  • Record recurring faults, root causes, and corrective actions in SAP PM or the site's maintenance system.

Communication interruption tests must be planned and authorized. Do not deliberately disconnect production-critical equipment without the required operational safeguards.

19. Maintenance records and performance indicators

For each significant communication fault, record:

  • Equipment ID and HMI/PLC identification.
  • Date, time, and affected production area.
  • Protocol and affected connection.
  • Symptoms and affected tags.
  • Driver error codes and available logs.
  • Network and controller diagnostic findings.
  • Root cause.
  • Corrective action.
  • Functional verification results.
  • Downtime and recurrence status.

Useful performance indicators include:

KPI Purpose
Communication availability Measures the time that required connections are operational
Timeout rate Identifies failed or delayed requests
Communication recovery time Measures time required to restore valid communication
Stale-data duration Tracks periods when displayed data is not current
Repeat fault frequency Identifies recurring network, driver, or configuration problems
Command success rate Measures whether expected command processing succeeds, using a clearly defined success condition

A KPI must have a consistent measurement method. For example, communication availability should distinguish planned maintenance from unplanned failures and should define which devices and operating periods are included.

20. Common mistakes to avoid

  • Assuming a successful ping proves that PLC communication is healthy.
  • Assuming an online status means every tag is current.
  • Increasing polling frequency without measuring the impact.
  • Changing IP addresses without updating documentation.
  • Treating a rejected PLC command as a communication failure.
  • Rebooting the HMI before preserving useful diagnostics.
  • Testing writes using an unauthorized diagnostic client.
  • Ignoring stale values after a communication interruption.
  • Replacing healthy hardware before checking configuration and network conditions.
  • Modifying live PLC or HMI communication settings without authorization and a rollback plan.

21. Key principles

  • HMI communication depends on compatible devices, correct configuration, valid data mapping, and a functioning communication path.
  • Physical connectivity, protocol connectivity, tag validity, and command execution are separate diagnostic layers.
  • A connected HMI can still display stale or incorrect information.
  • Read and write communication must be verified independently.
  • Communication faults should be diagnosed systematically, beginning with scope and evidence rather than speculative component replacement.
  • Reliable maintenance requires documented configurations, controlled changes, tested recovery procedures, and recorded root causes.
