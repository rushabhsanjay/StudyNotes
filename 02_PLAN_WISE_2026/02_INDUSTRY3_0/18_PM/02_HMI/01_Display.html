1. Definition

An HMI (Human-Machine Interface) display is the visual interface through which an operator observes machine conditions, process values, alarms, operating modes, and production information.

In industrial automation, an HMI display connects the operator with the control system. It presents information received from PLCs, controllers, drives, sensors, and other connected systems, and may provide authorized controls for operating the machine.

Examples include:

  • A Siemens Comfort Panel displaying a machine's operating status.
  • A Mitsubishi GOT2000 displaying PLC inputs, outputs, alarms, and production counters.
  • An Allen-Bradley PanelView displaying a machine sequence and fault messages.
  • An industrial PC running SCADA screens for an entire production line.

An HMI display is not simply a screen attached to a PLC. Its usefulness depends on the quality of its information, readability, alarm design, communication reliability, and suitability for the operator's actual tasks.

2. Purpose of an HMI display

The primary purpose is to help operators understand the current machine state and take appropriate actions.

  • Process monitoring: Display temperatures, pressures, speeds, positions, counts, and other values.
  • Machine status: Show whether equipment is running, stopped, idle, faulted, or in a maintenance state.
  • Alarm notification: Identify abnormal conditions and communicate their severity.
  • Operator control: Provide approved start, stop, reset, jog, and mode-selection commands where appropriate.
  • Fault diagnosis: Present useful fault descriptions, device identities, and diagnostic information.
  • Production monitoring: Display cycle counts, target quantities, downtime, and production status.
  • Setup and adjustment: Allow authorized users to enter recipes or change approved process parameters.
  • Maintenance support: Help technicians identify failed devices, interlock conditions, and communication problems.

A well-designed display reduces the time needed to understand a fault. A poorly designed display merely relocates confusion from the machine to a rectangular piece of glass.

3. HMI display architecture

A typical industrial HMI architecture contains the following elements:

Operator
   ↓
HMI Display and Runtime Application
   ↓
Communication Driver or Industrial Network
   ↓
PLC or Process Controller
   ↓
Sensors, Actuators, Drives, and Machine Equipment

The information path may be bidirectional. The HMI reads values from the controller and sends authorized operator commands back to it.

Typical components include:

  • Display hardware: LCD or other screen technology, backlight, protective glass, and associated electronics.
  • HMI runtime: Executes screens, animations, alarms, trends, navigation, and user interactions.
  • Engineering software: Used to develop, configure, download, and maintain the HMI project.
  • Communication interface: Ethernet, serial communication, or another supported interface.
  • Tags or variables: Named references to PLC data or internal HMI values.
  • PLC logic: Validates commands and executes machine control.
  • User access system: Applies authentication and permissions where supported.

The HMI should not be the sole authority for machine safety. Critical interlocks and safety functions must be implemented in the appropriate control and safety systems.

A touchscreen is one method of interacting with a display, not a separate category of process information. Display technology and operator-input technology should be evaluated independently.

5. Common screen types

An HMI project typically contains multiple screens, each designed for a specific operator task.

Screen Main purpose Typical content
Overview or home Show the overall machine state Running status, production count, active alarms, navigation
Process screen Monitor process operation Process values, equipment symbols, operating sequence
Manual operation Support authorized individual-device operation Jog commands, actuator status, selected manual controls
Automatic operation Show automatic sequence progress Current step, cycle state, permissives, completion status
Alarm screen Display active and historical alarms Alarm text, timestamp, priority, acknowledgement state
Trend screen Show how values change over time Pressure, temperature, speed, position, or cycle-time trends
Diagnostic screen Support maintenance troubleshooting I/O states, device health, communication status, fault codes
Recipe or setup Enter or select approved process parameters Recipe identity, setpoints, parameter limits

Screen availability depends on the machine, HMI platform, and user permissions. A small standalone machine does not need the same screen architecture as a multi-station automotive production line.

6. HMI tags and displayed values

An HMI tag is a named variable used by the HMI to obtain or store a value. Depending on the platform, it may refer directly to a PLC address, a symbolic PLC tag, or an internal HMI variable.

Examples:

HMI tag Example value Meaning
Machine_Running TRUE Machine running indication
Auto_Mode TRUE Automatic mode selected
Part_Count 1250 Accumulated production count
Motor_Speed 1450 rpm Displayed motor speed
Air_Pressure 5.8 bar Pneumatic supply pressure
Cycle_Time 12.4 s Measured cycle duration
Fault_Code 203 Application-defined fault identifier
PLC_Communication_OK TRUE Communication diagnostic indication

The names and values above are illustrative. Actual PLC data types, addresses, units, and scaling must match the machine configuration.

Data types

Common HMI data types include:

  • Boolean: On/off or true/false states.
  • Integer: Whole-number values such as counts or fault codes.
  • Real or floating-point: Values such as temperature, pressure, speed, or position.
  • String: Text such as recipe names, messages, or device identifiers.
  • Date/time: Timestamps for events and production records.
  • Arrays and structures: Groups of related values supported by the platform.

Incorrect data-type mapping can produce invalid values, misleading indications, communication errors, or unintended command behavior.

7. Displaying analog values correctly

Analog values often require engineering-unit scaling before being displayed.

For example, a PLC analog input may represent a pressure transmitter's signal as a raw count. The HMI may display the corresponding pressure in bar.

For linear scaling:

\[ EU = \frac{Raw-Raw\_{\min}}{Raw\_{\max}-Raw\_{\min}}(EU\_{\max}-EU\_{\min})+EU\_{\min} \]

Where:

  • \(EU\) is the engineering-unit value.
  • \(Raw\) is the measured raw value.
  • \(Raw\_{\min}\) and \(Raw\_{\max}\) are the configured raw limits.
  • \(EU\_{\min}\) and \(EU\_{\max}\) are the engineering-unit limits.

For a transmitter configured for 0 to 10 bar, if the valid raw range is 0 to 27648 and the raw value is 13824:

\[ EU=\frac{13824}{27648}\times10=5\text{ bar} \]

This example assumes a zero-based raw range and a correctly configured linear input. Actual PLC modules may use different raw ranges, signed values, diagnostics, or channel-specific scaling.

Best practice: Perform scaling in a clearly defined location, commonly the PLC application or a dedicated data-processing layer, and avoid accidentally scaling the same value twice in the HMI.

The display should also handle invalid, out-of-range, disconnected, or bad-quality data explicitly. Showing a plausible number when the source is invalid can be more dangerous than showing no number at all.

8. Display design and readability

An HMI screen should communicate machine condition quickly, even when an operator is under pressure or a maintenance technician is troubleshooting a breakdown.

Layout principles

  • Place the most important operating information where it can be found quickly.
  • Keep navigation consistent across screens.
  • Group related values, controls, and status indicators.
  • Use readable text sizes and adequate contrast.
  • Avoid unnecessary decorative graphics, excessive animation, and crowded layouts.
  • Use consistent units, decimal precision, tag names, and equipment symbols.
  • Keep frequently used controls separate from rarely used configuration functions.
  • Provide clear feedback after an operator command.
  • Use layouts that remain readable at the actual viewing distance and screen resolution.

Color conventions

Color should convey a consistent meaning across the machine.

Visual treatment Typical meaning Design consideration
Red Fault, trip, or emergency-related state Use according to the plant's established standards
Yellow or amber Warning or abnormal condition Distinguish warnings from critical faults
Green Running, active, or healthy state Define the exact meaning for each indicator
Gray Inactive, unavailable, or neutral state Avoid using the same gray for unrelated conditions
Blue Information, selection, or a defined operating state Use consistently with site conventions
Flashing indication A condition requiring attention Reserve for meaningful events and follow site standards

Color alone should not communicate a critical condition. Combine color with text, symbols, status labels, or other accessible visual cues.

Avoid making every object green during normal operation and every object red during a fault without providing meaningful context. Operators need to identify what failed, not simply discover that the screen has become a festive warning sign.

9. Machine symbols and animations

Graphic symbols represent machine components such as motors, cylinders, valves, conveyors, robots, pumps, and sensors.

Examples of useful display behavior include:

  • A motor symbol changes state according to verified running feedback.
  • A valve symbol indicates its confirmed position.
  • A conveyor symbol shows whether the equipment is running or stopped.
  • A sensor indicator displays the corresponding input state.
  • A robot or CNC status area shows the available operating state and relevant fault information.

The displayed state should reflect the actual feedback or an explicitly defined calculated status. A command to run a motor is not proof that the motor is running.

For example:

PLC information HMI presentation
Motor run command is ON Run command requested
Motor running feedback is ON Motor confirmed running
Motor overload input is ON Overload fault indication
Drive reports a fault Drive fault and diagnostic code
Feedback is unavailable Unknown or communication-loss state

This distinction is essential for troubleshooting. Otherwise, an HMI may confidently display a running motor that is physically sitting motionless.

10. HMI alarms and status indications

An alarm informs the operator about an abnormal condition that may require attention. A status message describes a condition without necessarily requiring an alarm response.

Examples:

  • Alarm: Hydraulic Pressure Low
  • Alarm: Robot Communication Fault
  • Status: Automatic Mode Selected
  • Status: Waiting for Downstream Machine
  • Status: Cycle Complete

A useful alarm record generally contains:

  • Clear, actionable alarm text.
  • Relevant equipment or device identification.
  • Timestamp and priority where supported.
  • Active, cleared, and acknowledged states where applicable.
  • Diagnostic details or a reference to the troubleshooting procedure.
  • A defined response for the operator or maintenance technician.

Alarm acknowledgement does not mean the fault has been corrected. It usually means that the operator has acknowledged the notification. The underlying condition must still be resolved and verified.

Alarm priorities, colors, audible indications, and acknowledgement behavior should follow the site's alarm-management standards.

11. Trends and historical displays

A trend screen plots process values against time. It can help identify intermittent faults, gradual degradation, process instability, and abnormal machine behavior.

Typical trend variables include:

  • Motor current and speed.
  • Hydraulic or pneumatic pressure.
  • Temperature and flow.
  • Servo position and following error.
  • Cycle time.
  • Production rate.
  • Analog sensor measurements.

Trend interpretation depends on sample rate, timestamp accuracy, retention, and data quality. A slow trend cannot reliably capture a very brief fault that occurs between samples.

For example, a pressure trend that gradually falls before a cylinder-position timeout may suggest an air-supply problem. The trend helps narrow the investigation, but it does not prove the cause without further checks.

An HMI trend may display live data only, while historical data may be stored in a historian, SCADA database, or other approved data system. The engineering design must specify which is required.

12. HMI communication and refresh behavior

The HMI communicates with the PLC through a supported driver and protocol. It periodically reads configured tags and, when authorized, writes values to the controller.

Important terms:

  • Update rate: How frequently the HMI refreshes a value.
  • Communication timeout: The period allowed before a missing response is treated as a failure.
  • Data quality: An indication of whether a value is valid and current.
  • Polling: A method in which a client requests values from a device.
  • Subscription: A mechanism in which updates are provided according to a configured subscription or event model.
  • Reconnect behavior: How communication is re-established after an interruption.

Actual behavior depends on the protocol and HMI platform.

Practical considerations

  • Use suitable update rates for the variable's operational importance.
  • Avoid excessively frequent polling of large numbers of tags without assessing controller and network load.
  • Display communication failure clearly.
  • Do not present stale values as though they are current.
  • Configure communication diagnostics and timeouts according to the system design.
  • Verify that the HMI is connected to the intended PLC.
  • Ensure that communication recovery does not automatically trigger unsafe or unintended commands.

A pressure value used for operator awareness may not require the same refresh rate as a rapidly changing motion diagnostic. The correct update rate depends on the process and the intended use of the information.

13. Operator controls and command feedback

HMI controls can initiate machine actions, but the PLC should validate commands against the machine's control logic and permissives.

Common controls include:

  • Start and stop.
  • Reset.
  • Auto/manual mode selection.
  • Jog or inching commands.
  • Recipe selection.
  • Approved setpoint entry.
  • Device enable or disable functions.

A robust command design includes:

  1. Clear identification of the command and its target equipment.
  2. Permission checks where required.
  3. PLC-side validation of operating mode and permissives.
  4. Appropriate handling of command duration and repeated inputs.
  5. Feedback showing whether the command was accepted, rejected, or completed.
  6. Defined behavior when communication is lost.
  7. Appropriate protection against unintended or duplicate commands.

For example, pressing Start may request a cycle, but the PLC should determine whether guards, interlocks, pressure, downstream readiness, and other required conditions are satisfied.

An HMI button should never be treated as a substitute for a safety-rated device or safety function. Emergency-stop functions and other safety controls must follow the applicable machine-safety design.

14. Display faults and troubleshooting

HMI display problems may originate in the screen hardware, application, tag mapping, PLC, network, or data source.

Symptom Possible causes Checks
Blank screen Loss of power, failed display, startup failure, or backlight problem Check approved power supply, status indicators, and hardware diagnostics
HMI starts but project does not load Missing runtime, damaged project, storage fault, or software mismatch Check runtime status and project compatibility
Values remain frozen Communication failure, stale data, stalled runtime, or incorrect tag configuration Verify PLC communication and data-quality indicators
Incorrect analog reading Wrong scaling, data type, engineering units, or source mapping Compare the raw PLC value with the displayed value
Buttons do not operate Permission restriction, wrong tag, PLC interlock, or communication failure Check command status, access rights, and PLC permissives
Alarm does not appear Incorrect trigger logic, alarm configuration, deadband, or acknowledgement behavior Verify the PLC alarm condition and HMI alarm configuration
Screen changes slowly Excessive graphics, too many tags, overloaded runtime, or network delays Inspect runtime performance and communication load
Touch areas do not respond correctly Touch calibration, surface damage, or hardware fault Follow the manufacturer's approved diagnostic procedure
Communication repeatedly drops Network instability, power issues, addressing errors, or device faults Check device diagnostics, network path, and connection parameters
Displayed state disagrees with machine Incorrect tag mapping, misleading logic, or missing feedback Compare the HMI tag with the actual PLC signal and physical condition

Troubleshooting sequence

  1. Confirm the symptom and identify the affected screen or function.
  2. Determine whether the problem affects one tag, one screen, the whole HMI, or the physical machine.
  3. Check HMI power, runtime status, and available diagnostics.
  4. Verify communication with the intended PLC.
  5. Compare the displayed value with the PLC's actual value.
  6. Check tag mapping, data type, scaling, and update behavior.
  7. Review relevant alarms and recent changes.
  8. Test corrective actions only under approved maintenance procedures.
  9. Confirm correct operation and document the cause and resolution.

Do not restart, download, or reset the HMI or PLC as the first troubleshooting action. Preserve diagnostic evidence before disturbing the system, especially when the fault is intermittent.

15. HMI display hardware and environmental requirements

Industrial HMI panels operate in environments that can be much harsher than an office or a home computer setup.

Important hardware considerations include:

  • Screen size and resolution: Must suit the information density and viewing distance.
  • Brightness: Must support visibility under the actual factory lighting conditions.
  • Viewing angle: Must permit the operator to read the screen from the intended position.
  • Operating temperature: Must remain within the manufacturer's specified range.
  • Ingress protection: The enclosure and front panel must meet the environmental requirements for dust, water, and cleaning.
  • Vibration and shock: Must be suitable for the installation location.
  • Electrical noise: Power and communication installation must follow the manufacturer's requirements.
  • Glove compatibility: Relevant when operators use protective gloves.
  • Chemical resistance: The screen surface and enclosure must tolerate approved cleaning agents.
  • Serviceability: Replacement availability, mounting dimensions, connectors, and project compatibility should be considered.

A display's IP rating applies to specified parts of the equipment under defined test conditions. It does not mean the complete installation is protected against every type of liquid, chemical, or cleaning method.

16. HMI display development and commissioning

When developing a new HMI or modifying an existing display, use a controlled engineering process.

  1. Identify operator and maintenance requirements.
  2. Define the required screens, alarms, trends, navigation, and controls.
  3. Establish tag names, data types, units, and scaling.
  4. Create a consistent layout and visual convention.
  5. Configure communication drivers and PLC connections.
  6. Configure access permissions and protected functions.
  7. Test normal, abnormal, fault, and communication-loss conditions.
  8. Verify every displayed value against the PLC or approved data source.
  9. Test command behavior, permissives, and feedback.
  10. Validate alarm messages, priorities, timestamps, and acknowledgement behavior.
  11. Conduct an operator review and document deficiencies.
  12. Obtain approval before deployment to production.
  13. Save the approved HMI project and create a verified backup.
  14. Record the revision and update the maintenance documentation.

Testing should include more than confirming that the screen looks correct. The displayed information must be accurate, and the controls must behave correctly under both normal and abnormal conditions.

17. HMI display security and access control

An HMI can expose important process information and provide access to machine commands. Its configuration should therefore follow the plant's OT cybersecurity requirements.

  • Assign user roles according to operational responsibilities.
  • Restrict engineering and configuration functions to authorized personnel.
  • Protect sensitive setpoints and maintenance functions where appropriate.
  • Use approved authentication and password-management procedures.
  • Disable unused services and interfaces when required by the security design.
  • Maintain approved project backups and change records.
  • Avoid connecting unauthorized devices to the HMI or its network.
  • Ensure that user-interface restrictions do not replace required PLC-side access controls or safety functions.

A hidden button is not a security control by itself. If an action must be restricted, the relevant permissions and command validation must be enforced by the appropriate system.

19. Practical industrial example

Consider an automated test station with a PLC, HMI, VFD, pressure sensor, and a pneumatic actuator.

The main HMI screen should display:

  • Machine operating mode.
  • Automatic cycle status.
  • Actuator command and confirmed position.
  • Air pressure in bar.
  • VFD running status and fault state.
  • Parts tested, accepted, and rejected.
  • Active alarms and communication health.

Suppose the actuator fails to reach its required position.

A useful HMI should allow the technician to distinguish among several possibilities:

  • The PLC has not issued the actuator command.
  • The command has been issued, but the solenoid output is not active.
  • The solenoid is active, but pneumatic pressure is inadequate.
  • The actuator has moved, but the position sensor has not changed state.
  • The PLC is not receiving the expected feedback.
  • The HMI is displaying stale or incorrectly mapped information.

The display should expose the relevant evidence without pretending to determine the root cause automatically. The technician can then check PLC logic, electrical outputs, the solenoid valve, pneumatic supply, sensors, and communication as appropriate.

20. HMI display maintenance checklist

Routine inspection

  • Check the screen for damage, discoloration, and unreadable areas.
  • Confirm that all required screens open correctly.
  • Verify that displayed values are current and plausible.
  • Check date and time information where used for alarms or production records.
  • Confirm that active alarms and communication faults are visible.
  • Check navigation and authorized operator controls.
  • Inspect the panel enclosure and installation environment.
  • Clean the screen using the manufacturer's approved method.

During troubleshooting or modification

  • Record the symptom and affected screen.
  • Verify PLC communication and tag mapping.
  • Compare displayed values with their actual data sources.
  • Check scaling, units, and data types.
  • Review recent project or configuration changes.
  • Preserve the current approved project before modification.
  • Test affected screens, alarms, and controls.
  • Save the approved revision and update maintenance records.

21. Key principles

  • An HMI display is an operator interface, not the source of truth for every machine condition.
  • Displayed states should reflect verified feedback or clearly defined calculated conditions.
  • Accurate tags, scaling, units, and communication diagnostics are essential.
  • Alarms must explain abnormal conditions and support appropriate action.
  • Operator commands must be validated by the control system.
  • Safety functions must not depend solely on ordinary HMI graphics or buttons.
  • Readability, environmental suitability, cybersecurity, and maintainability are all part of HMI design.
  • A display that looks attractive but shows incorrect or stale information is a defective interface, regardless of how polished it appears.
