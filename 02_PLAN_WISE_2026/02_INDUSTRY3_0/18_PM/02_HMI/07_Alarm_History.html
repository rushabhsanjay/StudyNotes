1. Definition

HMI alarm history is the recorded chronological history of alarm events and their associated state changes within an HMI, PLC, SCADA system, or connected alarm-management service.

It allows maintenance and production personnel to investigate past faults, identify recurring problems, correlate alarms with machine behavior, and determine why production stopped.

An alarm history may record events such as:

  • Motor overload.
  • VFD fault.
  • PLC communication failure.
  • Low pneumatic pressure.
  • Safety circuit interruption.
  • Sensor signal failure.
  • High temperature.
  • Machine cycle timeout.
  • Emergency-stop activation.
  • Operator acknowledgment and alarm return to normal.

For example, if a conveyor stops unexpectedly, the current HMI screen may show no active fault because the original fault has already cleared. Alarm history can reveal that a drive fault occurred first, followed by a conveyor sequence timeout and then a production-stop alarm.

Alarm history is evidence for troubleshooting, not automatic proof of root cause. Events must be interpreted in the context of the control sequence, timestamps, machine feedback, and operating conditions.

2. Purpose of alarm history

Alarm history supports several maintenance and operational activities.

  • Fault investigation: Determine which alarms occurred before, during, and after a breakdown.
  • Root-cause analysis: Identify the earliest relevant fault and distinguish primary faults from consequential alarms.
  • Recurring-fault analysis: Identify repeated alarms on a specific machine, device, or process.
  • Downtime analysis: Establish fault timing and support production-loss investigations.
  • Preventive maintenance: Identify developing issues such as repeated overheating, communication loss, or low pressure.
  • Process improvement: Find nuisance alarms, poor alarm thresholds, and unnecessary operator interventions.
  • Audit and traceability: Preserve records of alarm occurrence and acknowledgment where required.
  • Shift handover: Communicate unresolved faults and events that occurred during the previous shift.

Alarm history is particularly valuable when the original fault disappears after the machine stops, an operator resets the equipment, or the control system automatically clears a condition.

3. Alarm, event, and alarm history

These terms are related but have different meanings.

Term Meaning Example
Alarm An abnormal condition requiring operator awareness or action VFD overload
Event A recorded occurrence or state change Operator switches machine to manual
Alarm occurrence The point when an alarm condition becomes active Motor overload bit changes to active
Alarm acknowledgment An operator or authorized system confirms awareness of an alarm Operator acknowledges the overload
Alarm return to normal The triggering condition is no longer active Overload signal clears
Alarm history Chronological record of configured alarm-related occurrences and state changes Overload, acknowledgment, and return-to-normal records

An alarm is not necessarily the same as an event. A machine mode change may be recorded as an event without representing an abnormal condition.

Similarly, an alarm can remain active even after it has been acknowledged. Acknowledgment indicates awareness; it does not necessarily clear the fault.

4. Typical alarm lifecycle

A common alarm lifecycle is:

Normal condition
      ↓
Alarm condition becomes active
      ↓
Alarm displayed and recorded
      ↓
Operator acknowledgment, if required
      ↓
Physical or logical fault condition clears
      ↓
Alarm returns to normal
      ↓
History retains the configured records

The exact sequence depends on the alarm configuration.

Some alarms are acknowledged before the condition clears. Others clear automatically when the condition returns to normal. Some systems separately record acknowledgment, return to normal, shelving, suppression, or operator actions.

A properly configured history should distinguish these states rather than treating them as a single event.

5. Alarm occurrence, acknowledgment, and clearance

Consider a motor overload alarm.

Time Event Interpretation
10:15:12 Motor overload alarm activates The configured overload condition becomes true
10:15:25 Operator acknowledges alarm The operator confirms awareness
10:18:40 Overload condition clears The triggering signal returns to its normal state
10:18:40 or later Alarm returns to normal in history The system records the configured clearance event

The example timestamps are illustrative.

The motor may still require inspection, reset, or a permitted restart sequence even after the overload signal clears. Alarm clearance does not establish that the equipment is safe or ready for operation.

6. Information stored in alarm history

The information available depends on the HMI platform and alarm architecture.

Field Purpose
Timestamp Records when the event occurred
Alarm ID Provides a stable identifier for the alarm
Alarm message Describes the abnormal condition
Equipment or tag name Identifies the affected device or process
Alarm class or priority Supports categorization and response planning
Event type Identifies activation, acknowledgment, return to normal, or another recorded state
Current or recorded state Describes the alarm state represented by the record
User identity Identifies the acknowledging or acting user when supported
Value at occurrence Records a process value associated with the alarm when configured
Source Identifies the HMI, PLC, server, or alarm subsystem that generated the record
Additional details May include area, location, alarm group, or diagnostic information

Not every system stores every field. Some information must be configured explicitly, and some depends on whether the source device or server provides it.

7. Alarm timestamp and time synchronization

Correct timestamps are essential for reconstructing a breakdown.

If the HMI clock is several minutes ahead of the PLC clock, an alarm may appear to have occurred before its actual triggering condition. This can lead maintenance teams toward the wrong component.

Important considerations include:

  • HMI and PLC clock configuration.
  • SCADA server and historian clock configuration.
  • Time zone and daylight-saving settings where applicable.
  • Network Time Protocol (NTP) or another approved time-synchronization method.
  • Timestamp resolution and precision.
  • Whether the recorded timestamp represents source time or receipt time.
  • Behavior during communication outages and buffered event uploads.

For example, a PLC may record a drive fault at 10:15:12 while the HMI receives the event at 10:15:15. Both timestamps may be valid for different stages of the communication process.

For high-speed or tightly sequenced events, determine which timestamp is being displayed and whether the event source supports sufficiently precise time recording.

8. Alarm history versus active alarm list

The active alarm list and alarm history serve different purposes.

Feature Active alarm list Alarm history
Primary purpose Shows current alarm conditions Shows recorded past alarm events
Typical contents Active and possibly unacknowledged alarms Occurrences and configured alarm state changes
Main use Immediate operator response Troubleshooting and historical analysis
Changes over time Changes as alarm states change Retains records according to storage and retention settings
Acknowledgment Often allows acknowledgment Usually records acknowledgment if configured
Fault investigation Useful for current faults Essential for reconstructing earlier faults

A machine may have no active alarms while its history contains several faults from the previous shift.

Conversely, an alarm can be active now but missing from the expected history because of a logging configuration problem, storage failure, or a source-specific limitation.

9. Alarm history versus event log

An event log may include many kinds of system activity, while alarm history focuses on alarm-related information.

Record type Example Typical purpose
Alarm history Low air pressure Investigate abnormal conditions
Operator event Mode changed from Auto to Manual Understand operator actions
System diagnostic log HMI communication driver disconnected Diagnose application and communication faults
Audit trail User changed a setpoint Trace controlled changes
Process historian Conveyor speed was 1.2 m/s Analyze historical process behavior

These records may be stored in separate systems. A complete root-cause investigation may require all of them.

For example, an alarm history may show a low-pressure alarm, while a process historian shows pressure gradually declining over several minutes and an audit trail shows that a setpoint was changed earlier.

10. Alarm history architecture

A typical architecture for PLC-based alarm recording is:

Sensors and Equipment
        ↓
PLC Logic and Alarm Conditions
        ↓
HMI or SCADA Alarm Subsystem
        ↓
Alarm Event Storage
        ↓
Historical Alarm Viewer and Reports

The actual architecture can vary.

  • The PLC may provide alarm bits or structured alarm information.
  • The HMI may generate alarms from PLC tags and store history locally.
  • A SCADA server may centralize alarm processing and storage.
  • A historian or database may store records for reporting.
  • An external reporting system may summarize alarm counts and durations.

A local HMI history is not automatically a centralized plant-wide alarm database. If the HMI is replaced or its storage fails, locally stored records may be lost unless they are separately exported or replicated.

11. Alarm storage and retention

Alarm history can be stored in several ways:

  • Local HMI memory.
  • Removable storage supported by the device.
  • Local files or databases.
  • A centralized SCADA alarm server.
  • A historian or enterprise database.
  • An approved archival system.

Each method has different capacity, retention, reliability, and recovery characteristics.

Storage considerations

  • Maximum history capacity.
  • Record size and event frequency.
  • Retention period.
  • Database or file-system limits.
  • Storage wear and device endurance.
  • Behavior when storage becomes full.
  • Backup and recovery procedures.
  • Network disconnection and event buffering.
  • Access permissions and data integrity.

If a system retains a fixed number of records, new records may overwrite old records when capacity is reached. Other systems stop logging, raise a storage alarm, or apply a configured retention policy.

The actual behavior must be known and tested.

Estimating storage requirements

A simplified estimate is:

\[ S = E \times B \times D \]

Where:

  • \(S\) = approximate storage requirement.
  • \(E\) = average recorded events per day.
  • \(B\) = average stored bytes per event.
  • \(D\) = retention period in days.

Suppose a system records 12,000 events per day, averaging 500 bytes per stored record, for 90 days:

\[ S = 12{,}000 \times 500 \times 90 \]
\[ S = 540{,}000{,}000\text{ bytes} \]

This is approximately 540 MB using decimal units, before database indexes, metadata, transaction logs, replication, and other overhead.

Actual requirements should be measured or calculated from the storage platform's documented behavior.

12. Alarm history filters and search

A useful alarm history interface allows users to narrow records to a relevant period and equipment group.

Common filters include:

  • Start and end date/time.
  • Equipment or machine ID.
  • Alarm ID or tag name.
  • Alarm message.
  • Alarm priority.
  • Alarm class.
  • Alarm state or event type.
  • Operator identity, where available.
  • Production area or line.
  • Acknowledgment status.

For example, to investigate a station that stopped between 10:00 and 10:30, filter history to that interval and the relevant equipment group. Then identify the earliest meaningful alarm and correlate it with PLC diagnostics, drive fault records, and process trends.

Do not filter only for high-priority alarms if lower-priority events may explain the initiating failure.

13. Alarm priority and severity

Alarm priority indicates the relative importance or urgency of an alarm according to the site's alarm philosophy.

A common arrangement is:

Priority level Illustrative meaning Example
Critical Immediate action may be required to prevent a major consequence Critical process condition requiring immediate response
High Prompt operator intervention required Production-critical drive fault
Medium Timely investigation or corrective action required Persistent sensor fault affecting sequence readiness
Low Lower urgency condition requiring attention under defined procedures Noncritical equipment condition

These are illustrative labels. Priority names, colors, response times, and escalation rules must follow the site's approved alarm-management standard.

Priority should be based on consequence and required response, not merely on how often a condition occurs or how dramatic its message sounds.

An alarm flood containing hundreds of poorly prioritized messages reduces the visibility of genuinely important conditions.

14. First-out alarms and consequential alarms

When a machine stops, several alarms may appear in quick succession.

Consider an automated conveyor:

  1. A VFD trips due to an internal drive fault.
  2. The PLC detects loss of motor-running feedback.
  3. The conveyor sequence times out.
  4. A downstream station reports that material is unavailable.
  5. The line controller stops production.

The VFD fault may be the initiating fault, while the remaining alarms are consequences.

First-out analysis attempts to identify the earliest relevant fault that initiated the abnormal sequence.

However, the earliest timestamp is not always the root cause. The first displayed alarm could be caused by a sensor fault, communication delay, or unrelated condition. Timestamp precision and the control sequence must be considered.

Useful evidence includes:

  • PLC event logs.
  • VFD fault history.
  • HMI alarm timestamps.
  • Motor-running feedback.
  • Interlock states.
  • Process trends.
  • Sequence-state transitions.

15. Alarm duration and frequency analysis

Alarm history can be used to identify persistent or recurring problems.

Alarm duration

For an alarm with a recorded activation and return-to-normal time:

\[ T\_{\text{duration}} = T\_{\text{return}} - T\_{\text{activation}} \]

If a low-pressure alarm activates at 10:00:00 and returns to normal at 10:02:30, the recorded duration is 150 seconds.

This measures the alarm's active duration. It does not necessarily equal production downtime or the total time required to repair the problem.

Alarm frequency

Alarm frequency is the number of occurrences within a defined interval.

For example:

  • Sensor fault occurred 18 times in one shift.
  • Drive communication fault occurred 42 times in one week.
  • Overtemperature alarm occurred 9 times after maintenance.

Frequency should be analyzed alongside duration, operating conditions, and consequence. A brief recurring alarm may indicate an intermittent connection, while a single long-duration alarm may indicate a persistent failure.

Useful analysis measures

Measure What it helps identify
Alarm count by equipment Repeatedly problematic assets
Alarm count by shift Time-dependent or operating-condition-related patterns
Total active duration Persistent abnormal conditions
Repeated alarm intervals Intermittent faults or unstable control behavior
Alarm count by priority Distribution of operational urgency
Alarm count after maintenance Possible installation or configuration issues
Alarm flood frequency Poor alarm design or major process disturbances
Time from activation to acknowledgment Operator response patterns, interpreted in context

16. Alarm floods and nuisance alarms

Alarm flood

An alarm flood occurs when a large number of alarms are generated in a short period, potentially overwhelming the operator.

Common causes include:

  • A major process upset.
  • PLC communication failure.
  • Loss of a common power supply.
  • A shared sensor or network fault.
  • Poorly designed alarm dependencies.
  • Incorrect alarm thresholds.

Nuisance alarm

A nuisance alarm repeatedly activates without providing useful operational information.

Common causes include:

  • Alarm thresholds set too close to normal operating values.
  • No appropriate deadband or hysteresis.
  • Poor signal quality.
  • Incorrect debounce or delay configuration.
  • An alarm generated for a condition that is already expected during a sequence.
  • Repeated alarms caused by unstable communication.

Possible improvements include correcting the physical cause, reviewing thresholds, applying approved deadband or delay logic, and designing suitable alarm suppression or shelving behavior.

Any change must follow the site's alarm-management and change-control procedures. Do not suppress an alarm merely because it is inconvenient.

17. Alarm deadband, delay, and latching

These configuration features influence how alarms behave.

Deadband

Deadband prevents repeated switching when a measured value fluctuates near an alarm threshold.

For example, a high-temperature alarm may activate at 80°C and clear only after temperature falls below 77°C. The 3°C difference provides hysteresis.

The actual thresholds must be engineered for the process. Deadband must not delay detection of a dangerous condition.

Alarm delay

A delay requires a condition to remain true for a configured period before the alarm activates.

For example, a low-pressure alarm might require the pressure to remain below a threshold for 2 seconds to reject a brief transient.

Delays must not compromise required response time or safety-related functions.

Alarm latching

A latched alarm remains recorded or active according to its logic until a defined reset or acknowledgment condition is met.

Latching can preserve evidence of intermittent faults, but the HMI display, PLC alarm bit, and underlying physical condition must be understood separately.

A reset must not bypass required permissives or clear a fault record that the site's procedures require to be retained.

18. Alarm history troubleshooting procedure

Step 1: Define the failure window

Record the approximate breakdown time, affected equipment, production state, and operator observations.

Include a reasonable time interval before and after the reported stop.

Step 2: Filter alarm history

Filter by equipment, time interval, and relevant alarm classes. Preserve the original records when required by the site's investigation procedure.

Step 3: Identify the earliest relevant event

Separate likely initiating alarms from alarms caused by sequence interruption or downstream effects.

Step 4: Correlate other evidence

Compare alarm records against:

  • PLC diagnostics.
  • VFD fault history.
  • CNC or robot diagnostics.
  • HMI communication logs.
  • Sensor and actuator feedback.
  • Process historian trends.
  • Operator actions and audit records.

Step 5: Verify the actual fault

Use authorized diagnostic methods to inspect the suspected device and control sequence. An alarm message indicates a configured condition, which may or may not identify the failed physical component directly.

Step 6: Correct the cause

Repair the component, wiring, communication path, configuration, or control logic as appropriate. Follow the approved isolation, safety, and change-control procedures.

Step 7: Validate recovery

Confirm that the alarm condition clears correctly, the relevant feedback returns to the expected state, and the equipment operates under the approved test procedure.

Step 8: Document the findings

Record the initiating fault, consequential alarms, root cause, corrective action, downtime, and recurrence-prevention measures.

19. Practical industrial example: intermittent proximity sensor

An automotive station intermittently stops because a fixture-position sensor is not detected.

The alarm history shows:

Time Recorded event Initial interpretation
14:21:03 Fixture-position sensor timeout Potential initiating fault
14:21:05 Sequence step timeout Likely consequence
14:21:06 Station cycle aborted Sequence response
14:21:10 Operator acknowledges alarms Operator action
14:22:15 Station reset event Recovery attempt

The investigation should not immediately conclude that the sensor itself is defective.

Check:

  • Sensor supply voltage.
  • Sensor alignment and mounting.
  • Target position and mechanical repeatability.
  • Connector and cable condition.
  • PLC input status.
  • Input filtering and sequence timing.
  • Whether the sensor changes state at the expected point in the cycle.

If the PLC input intermittently drops when the fixture vibrates, the root cause could be a loose connector, damaged cable, poor mounting, or inadequate mechanical positioning.

After repair, verify the sensor state across repeated approved cycles and confirm that the timeout does not recur.

20. Alarm history maintenance checklist

Routine checks

  • Confirm that new alarm events are being recorded.
  • Check that timestamps are plausible and synchronized.
  • Verify that active alarms and historical records behave as expected.
  • Review repeated faults on critical equipment.
  • Check for storage-capacity or logging errors.
  • Verify that alarm history filters return the expected records.

Periodic checks

  • Confirm the configured retention period.
  • Review alarm storage and database health.
  • Check backup and recovery arrangements for alarm records.
  • Investigate recurring communication-loss and device-fault alarms.
  • Review nuisance alarms and alarm floods.
  • Verify priority and message configuration against approved standards.
  • Confirm that relevant alarms can be correlated with PLC and drive diagnostics.
  • Document corrective actions in SAP PM or the site's maintenance system.

After HMI replacement or software changes

  • Verify that new alarm events are recorded.
  • Check occurrence, acknowledgment, and return-to-normal behavior.
  • Confirm timestamp correctness.
  • Verify alarm messages, priorities, and equipment identifiers.
  • Confirm that required historical records remain available or have been archived.
  • Test the approved recovery procedure.

21. Common mistakes to avoid

  • Assuming an acknowledged alarm means the fault has cleared.
  • Treating every alarm displayed after a machine stop as an independent root cause.
  • Assuming the earliest timestamp automatically proves causation.
  • Ignoring clock synchronization and event timestamp sources.
  • Treating alarm history and active alarm lists as interchangeable.
  • Assuming a local HMI stores the complete plant-wide alarm history.
  • Deleting historical records to make the interface easier to use.
  • Suppressing recurring alarms without investigating their cause.
  • Using alarm duration as an exact measure of production downtime without defining the relationship.
  • Restoring an HMI without verifying its alarm configuration and logging behavior.

22. Key principles

  • Alarm history provides chronological evidence for troubleshooting and continuous improvement.
  • Alarm occurrence, acknowledgment, return to normal, and reset are distinct concepts.
  • Timestamp quality is critical when reconstructing event sequences.
  • The initiating fault must be distinguished from consequential alarms.
  • Alarm storage, retention, backup, and time synchronization require planned maintenance.
  • Alarm count alone is not a sufficient measure of operational risk.
  • Correct alarm configuration improves operator response and maintenance diagnosis.
  • Historical records should be preserved and interpreted alongside PLC, drive, process, and operator-event data.
