1. Definition and Purpose

An industrial robot controller is the central control system that interprets robot programs, calculates motion trajectories, coordinates robot axes, manages peripheral equipment, monitors faults, and communicates with other automation systems.

It is the robot's motion-control and supervisory computing platform. It combines hardware, real-time software, motion-control algorithms, communication interfaces, safety-related functions, and programming tools to execute automated tasks accurately and repeatedly.

Examples of industrial robot controller platforms include:

  • KUKA: KR C2, KR C4, and KR C5 controller families.
  • FANUC: R-J3, R-30iA, R-30iB, and related controller generations.
  • ABB: IRC5 and OmniCore controller families.
  • Yaskawa Motoman: DX100, DX200, and YRC1000 controller families.
  • Mitsubishi Electric: CR-series robot controllers.
  • Universal Robots: Integrated controller architecture in collaborative robot systems.

Controller capabilities, programming languages, safety architecture, and hardware arrangements vary by manufacturer and generation. A procedure for one controller must not automatically be applied to another.

2. Main Functions of a Robot Controller

The controller performs several functions simultaneously.

Function Purpose Industrial example
Motion planning Calculates the robot's movement between programmed positions Moving a welding torch along a seam
Servo control Commands joint motors and processes feedback Maintaining axis position during movement
Program execution Executes robot instructions and logic Running a spot-welding sequence
Coordinate transformation Converts tool and workpiece coordinates into joint movement Moving a tool along a defined path
I/O processing Reads sensors and controls outputs Checking a fixture clamp before welding
Sequence coordination Coordinates robot actions with machine cycles Waiting for a CNC machine to finish
Fault monitoring Detects controller, drive, communication, and motion faults Reporting a servo or encoder alarm
Communication Exchanges data with PLCs, HMIs, networks, and peripherals Receiving a production start request
Safety-related control Implements supported protective and monitored functions Responding to a protective stop
Diagnostics Provides status, alarm history, and maintenance information Investigating an intermittent robot fault

The controller does not independently guarantee that the complete robotic cell is safe. Cell safety also depends on the robot installation, guarding, external safety systems, end-of-arm tooling, fixtures, and the validated risk-reduction measures.

3. Robot Controller Architecture

A typical industrial robot control system contains the following major components:

    ↓

    ↓

    ↓

    ↓
Servo Amplifiers
    ↓

Controller ↔ PLC / Industrial Network

This is a conceptual architecture. Some components are integrated, and others are physically separate. Safety-related control may use dedicated hardware, safety-rated software, or a validated combination of components.

4. Physical Components of a Robot Controller Cabinet

4.1 Main CPU or controller computer

The CPU executes the robot operating system, user program, motion-planning algorithms, communication tasks, and diagnostic functions.

Depending on the controller generation, the CPU platform may use an industrial computer, dedicated processor, or a combination of processing modules.

Possible CPU-related faults include:

  • Controller startup failure.
  • Software or configuration corruption.
  • Memory errors.
  • Processor or internal communication faults.
  • Unexpected controller resets.
  • Excessive internal temperature.

Before replacing the CPU, inspect the alarm history, power supply, cooling, storage, internal connections, and applicable diagnostic indicators.

4.2 Servo amplifiers

Servo amplifiers supply controlled electrical power to the robot's joint motors.

Depending on the architecture, the controller may contain separate amplifiers for individual axes or integrated multi-axis drive modules.

Drive functions commonly include:

  • Motor-current control.
  • Torque production.
  • Velocity and position control functions.
  • Feedback processing.
  • Overcurrent and overload protection.
  • Overtemperature monitoring.
  • Communication with the robot controller.

Some control loops are implemented in the servo drive, while others are coordinated by the main controller. The division depends on the manufacturer and hardware generation.

4.3 Power supply

The controller power supply converts incoming electrical power into the DC or other supply rails required by the control electronics.

Separate power stages may supply servo drives and motors.

Maintenance checks include:

  • Incoming supply condition.
  • Correct voltage and phase configuration.
  • Protective devices and fuses.
  • Power-supply status indicators.
  • DC bus and supply alarms where applicable.
  • Grounding and protective bonding.
  • Signs of overheating or damaged connections.

Electrical measurements and internal inspections must follow the controller's safety procedures. DC bus capacitors may remain charged after the incoming supply has been disconnected.

4.4 Communication and interface modules

Communication modules connect the controller to external automation equipment.

Common interfaces include:

  • Industrial Ethernet.
  • EtherNet/IP.
  • PROFINET.
  • PROFIBUS on supported legacy systems.
  • EtherCAT on supported systems.
  • Serial communication on selected platforms.
  • Discrete digital and analog I/O.
  • Manufacturer-specific motion and peripheral buses.

The supported interfaces depend on the controller, installed options, and configured network architecture.

A communication failure may originate from a cable, connector, network switch, device power supply, configuration mismatch, duplicate address, or failed interface module.

4.5 Storage and memory

Controllers may use internal flash storage, solid-state drives, memory cards, or other manufacturer-specific storage arrangements.

Stored information can include:

  • Robot programs.
  • Position and coordinate data.
  • System configuration.
  • Calibration-related data.
  • I/O configuration.
  • Application settings.
  • Error and diagnostic records.
  • System software and options.

Memory architecture and retention differ by platform. Never assume that removing a storage device or replacing a controller module preserves all robot-specific data.

4.6 Cooling system

Cooling maintains controller components within their specified operating temperatures.

Depending on the design, cooling may use cabinet fans, filters, heat exchangers, air conditioning, or other thermal-management arrangements.

Common failure mechanisms include:

  • Blocked air filters.
  • Failed fans.
  • Obstructed ventilation.
  • Excessive ambient temperature.
  • Dust accumulation.
  • Faulty temperature sensors.
  • Heat-exchanger or air-conditioning failure.

Cooling problems can cause intermittent faults, reduced component life, thermal alarms, or unexpected shutdowns.

5. Teach Pendant and Operator Interface

The teach pendant is the primary human interface for many industrial robot systems. It allows authorized users to teach positions, edit programs, jog axes, inspect status, acknowledge faults, and perform approved setup operations.

Typical pendant functions include:

  • Robot program editing.
  • Joint and Cartesian jogging.
  • Position recording.
  • Tool and work-frame configuration.
  • Program selection and execution.
  • Alarm and event-history display.
  • I/O monitoring.
  • Manual and automatic mode selection.
  • Access to diagnostic and configuration screens.

The pendant may include an enabling device and other mode-dependent controls. Their exact functions depend on the system.

Safety principle: An enabling device is not permission to enter a hazardous area without following the approved setup and isolation procedure. Manual operation still presents crushing, trapping, impact, and unexpected-motion hazards.

Pendant connection faults may result from damaged cables, connector problems, communication errors, incorrect configuration, or hardware failure. Diagnose these conditions using the controller's documented procedure.

6. Robot Controller Operating Modes

Robot controllers commonly support manual teaching, automatic execution, and other service or test modes.

Mode Typical purpose Main consideration
Manual or teach Teach positions and perform setup Restricted speed and enabling-device requirements may apply
Automatic Execute production programs Cell interlocks and production permissives must be satisfied
T1 or equivalent Manual teaching at a specified reduced-speed limit Exact limits and conditions depend on the robot system
T2 or equivalent Higher-speed manual testing on systems that support it Availability and restrictions are controller-specific
External automatic Accept production commands from a PLC or cell controller Requires correct external-start and safety configuration
Service or maintenance Perform authorized diagnostics and configuration Access and operation are restricted by procedure

Mode names and available functions vary by manufacturer. T1 and T2 should not be assumed to exist on every robot.

Before changing modes, verify the robot's position, tool and workpiece condition, cell status, operating procedure, and the personnel's authorized access.

7. Robot Controller Software and Configuration

The controller's software determines how the robot interprets programs, plans motion, processes I/O, and communicates with external devices.

Relevant software and configuration elements may include:

  • Operating system and controller firmware.
  • Robot application software.
  • Motion-control software.
  • Robot model and axis configuration.
  • Tool and work coordinate frames.
  • Robot mastering or calibration-related data.
  • Digital and analog I/O assignments.
  • Industrial network configuration.
  • PLC communication settings.
  • Safety-related configuration.
  • Application-specific options.
  • User programs and supporting data.

The exact terminology and storage locations differ by manufacturer.

A software upgrade or controller replacement may require compatible application files, option licenses, calibration data, and machine-specific configuration. A robot that starts successfully after a software change may still have incorrect application or calibration data.

8. Robot Programming Environment

Robot programming systems use manufacturer-specific languages and tools.

Manufacturer Common programming environment or language General purpose
KUKA KRL and WorkVisual Robot programs, configuration, and engineering
FANUC TP programs and KAREL on supported systems Robot programming and application logic
ABB RAPID and RobotStudio Robot applications and simulation
Yaskawa Motoman INFORM and supported offline programming tools Robot motion and sequence programming
Mitsubishi Electric MELFA BASIC and supported engineering tools Robot programming and setup
Universal Robots PolyScope and URScript Robot setup and program execution

Language support varies with controller model, software revision, and installed options.

The programming environment typically supports:

  • Motion instructions.
  • Position and coordinate data.
  • Conditional logic.
  • Wait and synchronization instructions.
  • I/O commands.
  • Subprograms and reusable routines.
  • Error handling and recovery logic.
  • Application-specific instructions.

A robot controller may execute the motion program while a PLC coordinates the wider production sequence. The two programs must agree on handshake signals, timing, fault handling, and recovery behavior.

9. Coordinate Systems and Controller Calculations

The controller converts programmed Cartesian positions into coordinated joint movement through kinematic calculations.

Common coordinate concepts include:

  • Joint coordinates: Individual robot-axis positions.
  • World coordinates: A coordinate system related to the cell or installation.
  • Base or user frame: A reference associated with the robot base, fixture, or workpiece.
  • Tool frame: The position and orientation of the tool relative to the robot flange.
  • Work-object frame: A reference for the workpiece or manufacturing task.

Frame names and conventions vary by manufacturer.

An incorrect tool frame can cause a welding torch, gripper, or other tool to follow an incorrect path. An incorrect base or work frame can shift the programmed path relative to the fixture.

Controller calculations also depend on the robot model, mastering or calibration state, joint limits, and the selected motion type.

10. Robot Controller and PLC Integration

The robot controller and the cell PLC have different but interconnected responsibilities.

The robot controller typically handles:

  • Robot motion.
  • Robot program execution.
  • Joint and tool-position control.
  • Robot-specific diagnostics.
  • Robot application functions.

The PLC typically handles or coordinates:

  • Production sequence.
  • Machine permissives.
  • Fixture and clamp sequencing.
  • Conveyor control.
  • Part-present checks.
  • Cycle start and completion.
  • External fault handling.
  • Cell-level coordination.

The actual allocation depends on the system design.

10.1 Typical handshake signals

Signal Example purpose
Robot ready Indicates the robot is ready for the defined operation
Cycle start request Requests the robot to begin an operation
Program running Indicates program execution is active
Cycle complete Confirms completion of the defined operation
Robot fault Reports an active robot fault
Reset request Requests a defined fault-reset procedure
Fixture clamped Confirms the required fixture condition
Part present Confirms that a workpiece is detected
Safe position reached Confirms a defined position or state, where implemented and validated

Signal names, electrical polarity, and handshake semantics must be verified in the actual I/O list and PLC program.

A Robot Ready signal does not necessarily mean the robot is clear of every hazard or that a person may enter the cell. Safety permissions must come from the validated safety architecture.

11. Robot Controller Safety Functions

Industrial robot cells may use safety-related functions implemented by the robot controller, dedicated safety hardware, external safety PLCs, or a validated combination.

Depending on the system, supported functions may include:

  • Emergency-stop handling.
  • Protective-stop functions.
  • Guard-door monitoring.
  • Enabling-device monitoring.
  • Safely limited speed.
  • Safe position or space monitoring.
  • Safe torque off.
  • Safe motion functions supported by the installed controller.

Availability and safety ratings are system-specific.

Important distinctions:

  • Emergency stop is intended to respond to an emergency situation; it is not a substitute for isolation during maintenance.
  • Protective stop may be initiated by a protective device or condition, depending on the installation.
  • Safe torque off (STO) prevents the drive from producing torque as specified by the implemented safety function. It does not necessarily remove all electrical energy or prevent movement caused by gravity or external forces.
  • Software jogging or ordinary position commands are not, by themselves, safety-rated protective functions.

Never bypass a guard, force a safety input, or modify safety parameters merely to keep production running. Changes to safety-related configuration require the appropriate authorization, validation, and documented testing.

12. Common Robot Controller Faults

Symptom Possible causes Initial diagnostic checks
Controller does not power up Incoming supply issue, failed power supply, internal fault Supply status, protective devices, documented startup diagnostics
Controller starts but robot is unavailable Active alarm, missing permissive, safety condition, drive not ready Alarm history, safety status, drive status
Teach pendant does not communicate Cable, connector, pendant, or interface fault Connection status and manufacturer diagnostics
Robot servo fault Drive fault, feedback problem, overload, mechanical resistance Exact alarm, affected axis, drive diagnostics
Robot program will not start Wrong mode, program selection, missing permissive, active alarm Mode, program status, I/O and interlocks
External start does not work Handshake mismatch, PLC condition, communication issue I/O monitor, PLC logic, network diagnostics
Robot stops during movement Protective stop, motion fault, process condition, collision detection Alarm sequence, stop reason, event history
Position accuracy is poor Mastering or calibration issue, frame error, mechanical problem Position data, calibration records, mechanical checks
Controller overheats Blocked filter, failed fan, high ambient temperature Temperature diagnostics, airflow, cooling equipment
Communication with PLC is lost Network fault, device power loss, configuration issue Network status, switch, cable, device diagnostics
Application software fails to load Incompatible files, missing options, configuration corruption Software revision, application package, backup records
Repeated unexplained resets Supply instability, thermal issue, internal fault Event timestamps, supply diagnostics, controller logs

These are starting points for investigation, not automatic diagnoses. Use the exact controller and robot documentation before replacing components or changing configuration.

13. Controller Preventive Maintenance

The controller cabinet should be included in the robot's preventive maintenance plan.

Routine inspection

  • Check controller alarm history and recurring faults.
  • Inspect cabinet condition and ventilation.
  • Check filters and cooling equipment according to the manufacturer's schedule.
  • Inspect accessible connectors and cable entries for damage.
  • Review power-supply and drive diagnostic indicators.
  • Check for abnormal temperature, dust, or signs of overheating.
  • Review network and remote I/O communication faults.
  • Verify that required backups are current and accessible.
  • Check controller software and configuration records.
  • Confirm that no unauthorized modifications have been made.

Maintenance precautions

  • Follow the manufacturer's electrical safety and isolation procedure.
  • Confirm whether capacitors or other components retain hazardous energy after isolation.
  • Do not open energized equipment unless the task is specifically authorized and the required controls are in place.
  • Do not use compressed air or cleaning chemicals unless permitted by the manufacturer.
  • Avoid disturbing configuration switches, wiring, and connectors without a documented reason.
  • Perform functional checks after maintenance where required.

14. Controller Backup and Recovery

Before a major controller repair, software upgrade, or replacement, identify the full recovery requirements.

Depending on the platform, relevant data may include:

  • Robot programs and subprograms.
  • Robot model and axis configuration.
  • Tool and work frames.
  • Mastering or calibration-related data.
  • I/O and communication configuration.
  • Safety-related configuration.
  • Application software and installed options.
  • External PLC interface data.
  • Controller and drive parameters.
  • Relevant alarm and diagnostic records.

The backup process must follow the manufacturer-specific method. A program export alone may not preserve the complete robot configuration.

Before restoring a backup, verify that it matches the robot model, controller generation, software version, and machine installation.

After restoration or replacement, perform the required configuration checks, mastering or calibration verification, I/O checks, safety validation, and controlled motion tests before returning the cell to production.

16. Practical Troubleshooting Example

Problem: The robot controller shows the robot as unavailable, and the PLC does not receive the expected ready signal.

A structured investigation is:

  1. Record the exact controller alarm and the time of occurrence.
  2. Check whether the robot is in the required operating mode.
  3. Inspect active controller, servo, and safety-related statuses.
  4. Determine whether the robot controller is ready internally but unable to complete the external handshake.
  5. Monitor the relevant PLC and robot I/O signals.
  6. Check the PLC logic for the condition preventing the ready signal or cycle start.
  7. Inspect the relevant communication status if the signals are exchanged over a network.
  8. Correct the confirmed cause using the approved procedure.
  9. Validate the robot and PLC handshake in the intended operating mode.
  10. Confirm that the cell returns to the approved operating state and document the findings.

Do not force the ready signal or bypass a missing permissive. The missing signal may be correctly preventing an unsafe or invalid sequence.

17. Key Engineering Principles

  • The robot controller coordinates robot motion, program execution, diagnostics, and communication with the wider automation system.
  • Controller hardware and software architecture vary by manufacturer and generation.
  • The teach pendant is an engineering interface, not a replacement for safe cell procedures.
  • Robot, PLC, and safety-related functions must be understood as separate but interconnected control layers.
  • Robot accuracy depends on correct configuration, mastering or calibration, frames, tooling, and mechanical condition.
  • Alarm history should be examined before replacing controller components.
  • Configuration changes and software upgrades require verified backups and compatibility checks.
  • Safety-related settings must never be bypassed to clear a fault or accelerate production.
  • Preventive maintenance should include cooling, electrical condition, diagnostics, backups, and configuration traceability.
