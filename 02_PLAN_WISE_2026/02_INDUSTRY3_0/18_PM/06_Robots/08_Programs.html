1. Definition and Purpose

An industrial robot program is a set of instructions that defines how a robot moves, operates its tooling, interacts with external equipment, and completes a manufacturing task.

A program may control robot motion, gripper operation, welding or dispensing processes, signal exchanges with a PLC, waiting conditions, error handling, and movement between production stations.

In preventive maintenance, robot programs must be maintained because a software-related problem can cause downtime, incorrect part handling, collisions, process defects, or unsafe machine behavior.

The objective is not merely to ensure that the program runs. It is to ensure that the correct approved program runs, its logic and position data remain valid, its interfaces operate correctly, and its behavior is verified after maintenance or modification.

Typical maintenance responsibilities include:

  • Inspecting program status and identifying the active production program.
  • Reviewing alarms, program faults, and sequence interruptions.
  • Checking program revisions and unauthorized changes.
  • Verifying motion points, speed settings, and tool or frame references.
  • Checking robot-to-PLC and robot-to-equipment signal exchanges.
  • Inspecting error handling, timeout logic, and recovery sequences.
  • Testing the program after repairs, tooling changes, or controller work.
  • Maintaining program documentation and approved copies.

2. Robot Program Architecture

A robot application usually consists of more than one program file. The complete behavior may depend on a main program, subprograms, shared data, controller settings, PLC logic, and external process equipment.

Robot Application
   ↓
Main Production Program
   ├── Initialization and checks
   ├── Robot motion sequence
   ├── Tool and process commands
   ├── PLC and equipment handshakes
   ├── Calls to subprograms
   ├── Fault handling and recovery
   └── Cycle completion
          ↓
Shared Program Data
   ├── Positions and registers
   ├── Variables and parameters
   ├── Tool and work-frame data
   └── Speed and process settings
          ↓
Robot Controller
   ├── Motion control
   ├── Servo drives and feedback
   ├── I/O and communication
   └── Safety and operating-mode logic
          ↓
Robot, Tooling, PLC, and Process Equipment

The exact structure differs between robot manufacturers and controller generations. Some systems store positions within motion instructions; others use separate position registers, data files, or shared variables.

3. Main Types of Robot Programs

Program type Purpose Typical example
Main program Coordinates the overall production cycle Load a component, unload a finished part, and return to standby
Motion subprogram Executes a reusable movement sequence Approach and retreat from a fixture
Tool-control routine Operates an end effector Open or close a gripper
Process routine Controls the manufacturing process Welding, dispensing, painting, or inspection sequence
Initialization routine Checks or prepares required data and states Validate selected recipe and reset permitted process flags
Recovery routine Handles defined fault-recovery conditions Move to an approved recovery position after a process interruption
Service or maintenance routine Supports authorized maintenance functions Controlled positioning for inspection
Diagnostic routine Displays or checks defined system conditions Check a sensor response or communication status

Program names are not standardized. A routine called HOME, for example, must not automatically be assumed to move the robot to a safe position. Its actual instructions and operating conditions must be inspected.

4. Common Program Instructions

Robot controllers provide instructions for motion, logic, data processing, I/O, and program flow.

Instruction category Function Maintenance concern
Joint or point-to-point motion Moves toward a target using coordinated joint movement Joint configuration, speed, and collision clearance
Linear motion Commands a Cartesian path toward a target TCP, frame, orientation, and path clearance
Circular motion Commands a circular path through defined points Correct geometry and valid intermediate points
Speed setting Defines commanded movement speed Process requirements, load, and safe operating limits
Blending or zone setting Defines how transitions between motions are handled Accuracy and clearance at intermediate points
Digital output Commands a device or process signal Correct output mapping and device response
Wait condition Waits for a signal or condition Missing feedback and timeout behavior
Conditional branch Selects logic based on a condition Incorrect state evaluation or unexpected branch
Timer Measures or delays a sequence Excessive delays and missing timeout protection
Subprogram call Executes another routine Missing routine, wrong version, or unintended recursion
Register or variable operation Reads, stores, or modifies data Incorrect values, unintended overwrites, or data-type errors
Program termination or return Ends a routine or returns control Incorrect cycle completion or unexpected program exit

Instruction names and syntax vary by manufacturer. The function must be understood before making a change.

5. Robot Motion Commands and Their Maintenance Impact

5.1 Joint or point-to-point motion

Joint motion moves the robot toward a target through coordinated movement of its axes. The tool path between the start and target may not be a straight line.

Typical uses include travel between stations, approach positions, and movements where the exact intermediate tool path is not the process requirement.

Maintenance checks include:

  • Correct target data.
  • Valid joint configuration and posture.
  • Adequate clearance for the full movement.
  • Appropriate speed and blending settings.
  • Absence of joint-limit or singularity-related issues.

5.2 Linear motion

Linear motion commands the tool to follow a straight Cartesian path under the controller's defined motion model.

Typical uses include insertion, welding, dispensing, and controlled approach or retreat.

Maintenance checks include:

  • Correct TCP.
  • Correct tool and work-frame selection.
  • Suitable target orientation.
  • Clearance along the complete path, not just at the endpoints.
  • Valid speed, acceleration, and transition settings.

5.3 Circular motion

Circular motion follows an arc defined by the controller's required start, intermediate, and endpoint information.

Maintenance checks include:

  • Valid geometric relationship between the points.
  • Correct orientation behavior.
  • No collision along the arc.
  • Correct tool and frame definitions.
  • Appropriate process speed and transition behavior.

5.4 Blending and exact-stop behavior

Blending allows motion between targets without necessarily stopping exactly at every programmed point. Exact-stop or fine-positioning instructions require a more precise stop according to the controller's motion definition.

Incorrect settings can cause a robot to pass too close to a fixture, miss a process-critical position, or waste cycle time by stopping unnecessarily.

Never increase blending or speed merely to improve cycle time without validating the actual path and process requirements.

6. Program Sequence and Interlocks

A robot program often relies on the PLC and other equipment to confirm that each stage of the process is ready.

For example, a robot loading a CNC machine may need confirmation that:

  • The machine door is in the required state.
  • The spindle or other relevant equipment is in the required condition.
  • The fixture is ready for loading.
  • The gripper has picked up the component.
  • The component is correctly seated.
  • The machine cycle has completed.
  • The robot is permitted to leave the loading area.

A command signal and its feedback signal are different things. Sending a command to close a gripper does not prove that the gripper has closed.

Example sequence

Check machine-ready condition
   ↓
Check robot and cell permissives
   ↓
Move to pickup approach
   ↓
Pick up component
   ↓
Confirm grip or part-present feedback
   ↓
Move to machine loading position
   ↓
Load component and confirm required state
   ↓
Request machine cycle
   ↓
Wait for machine-complete condition
   ↓
Unload or continue production sequence
   ↓
Report cycle completion

This is a conceptual sequence, not executable robot code. The actual implementation must follow the cell's approved PLC, robot, and safety design.

7. Robot-to-PLC Communication

Robot programs commonly exchange status and command signals with a PLC. The exchange may use hardwired digital I/O, industrial Ethernet, fieldbus, or a manufacturer-supported communication interface.

Typical signals include:

  • Robot ready.
  • Robot busy.
  • Cycle start request.
  • Cycle complete.
  • Program running.
  • Fault active.
  • Part present.
  • Gripper open or closed.
  • Machine ready.
  • Machine cycle complete.
  • Request for process equipment operation.

7.1 Handshake faults

Symptom Possible cause Investigation
Robot waits indefinitely for machine ready PLC sequence not satisfied, missing signal, communication fault Check robot input status and the corresponding PLC condition
PLC waits indefinitely for robot complete Robot program stopped, completion bit not set, wrong routine running Check robot state, program flow, and completion logic
Gripper command occurs but no part is picked Gripper fault, air supply issue, incorrect output mapping, missing feedback Check the output command and physical feedback
Cycle starts twice Inadequate start-signal handling or repeated trigger Review edge detection, reset logic, and sequence ownership
Robot and PLC show conflicting states Mapping, update timing, communication, or sequence logic issue Compare corresponding signals and diagnostic timestamps
Program advances before a process finishes Missing wait, incorrect condition, or incorrect timeout handling Review sequence dependencies and feedback validation

A signal that appears ON at the robot does not automatically prove that the intended physical device operated. Verify the complete signal path and device feedback.

8. Program Data: Positions, Registers, Variables, and Parameters

A robot program depends on data as much as it depends on instructions. An unchanged program can behave differently if a referenced position, register, tool definition, frame, or process parameter changes.

8.1 Position data

Position data defines robot targets. Depending on the controller, a target may include joint coordinates, Cartesian coordinates, orientation, configuration information, and external-axis positions.

Maintenance checks:

  • Confirm that the expected target is being used.
  • Check whether a point is shared by multiple programs.
  • Verify the correct tool and work frame.
  • Review recent point modifications.
  • Confirm that the target remains clear of fixtures, machine doors, and other equipment.

8.2 Registers and variables

Registers and variables store values used by the program. They may represent counters, part types, recipe numbers, positions, timers, or process conditions.

Examples include:

  • Current production variant.
  • Number of completed parts.
  • Selected station.
  • Grip confirmation status.
  • Process timeout.
  • Error or recovery state.

A program may run incorrectly if a register contains an unexpected value, is reset at the wrong time, or is overwritten by another routine.

8.3 Parameters and shared configuration

Some settings are stored outside the main program. Examples include speed limits, tool data, user frames, payload values, communication settings, and controller-specific motion parameters.

Before changing a parameter, establish:

  1. Which functions depend on it.
  2. Whether the parameter is shared across multiple programs.
  3. Whether the value is documented and approved.
  4. Whether a change requires testing or a backup.
  5. How to restore the previous approved configuration.

9. Program Faults and Error Handling

A robust robot program should account for expected abnormal conditions. Examples include missing part confirmation, a gripper timeout, machine-not-ready status, failed communication, or a process device not completing its operation.

9.1 Common error-handling features

  • Timeouts for conditions that should not wait indefinitely.
  • Alarm messages that identify the failed step.
  • Controlled interruption when required feedback is missing.
  • Defined recovery states.
  • Prevention of unintended duplicate commands.
  • Reset logic that does not hide the original fault.
  • Operator instructions for approved recovery.
  • Return-to-service checks after a fault.

Safety functions must remain within the approved safety architecture. Ordinary robot program logic must not be treated as a replacement for safety-rated interlocks or protective devices.

9.2 Timeout example

A robot commands a gripper to close and waits for a gripper-closed input.

A sound sequence design should define what happens if confirmation does not arrive within the permitted time. Depending on the cell design, the robot may stop the sequence, set a diagnostic condition, and request operator intervention.

A poor design might wait forever, continue without confirmation, or repeatedly actuate the gripper without investigating the cause.

9.3 Recovery considerations

Before resuming a program after an interruption, determine:

  • Which instruction was active.
  • Whether the tool is holding a part.
  • Whether an external machine is still running.
  • Whether the current robot position is valid for the intended next movement.
  • Whether outputs remain energized.
  • Whether a sequence step may be repeated safely.
  • Whether the PLC and robot agree on the current process state.

Restarting at the wrong point can cause duplicate operations, dropped parts, collisions, or damage to process equipment.

10. Program Modification and Change Control

Program changes may be needed after fixture changes, tooling replacement, process improvement, fault correction, or product-variant updates. Every change should have a defined reason, authorization, and verification method.

Recommended change process

  1. Record the original program name and revision.
  2. Identify the problem or approved change request.
  3. Review the program and its dependencies.
  4. Preserve the approved version and relevant configuration data.
  5. Make the smallest justified change.
  6. Check syntax, references, and program flow.
  7. Test the changed logic using the approved method.
  8. Validate the robot path and relevant equipment handshakes.
  9. Confirm product quality and required cycle behavior.
  10. Obtain the required approval before production release.
  11. Update the revision record and maintenance documentation.
  12. Retain the rollback version and document how to restore it.

Changes that require particular care

  • Editing motion points near fixtures or machine openings.
  • Changing speed, acceleration, or blending.
  • Modifying tool or work-frame data.
  • Changing output commands that operate process equipment.
  • Altering wait conditions or timeout values.
  • Changing program-start, reset, or recovery logic.
  • Editing shared registers or variables.
  • Changing communication mappings or safety-related configuration.

A small-looking change can affect several stations if it modifies shared data or a commonly called subprogram.

11. Program Revision and Version Management

A production cell may contain several programs with similar names for different products, stations, or robot variants. Running the wrong version can create process defects even when the program itself is valid.

A useful revision record should identify:

  • Robot and controller.
  • Program name.
  • Revision identifier.
  • Date and reason for the change.
  • Person who made the change.
  • Person who approved it.
  • Relevant tool, frame, and configuration changes.
  • Test results and release status.
  • Location of the approved backup.
  • Previous revision and rollback procedure.

Do not rely solely on a filename or a timestamp to determine which program is approved. Use the site's controlled revision and release process.

12. Program Inspection During Preventive Maintenance

Program PM is not necessarily a full line-by-line code review during every scheduled visit. The scope should be defined by the maintenance plan, application risk, fault history, and manufacturer's guidance.

12.1 Routine checks

  • Confirm the correct approved program is selected for production.
  • Review active and historical program-related alarms.
  • Check for unexpected program stops or repeated sequence faults.
  • Review recent program modifications and approvals.
  • Confirm that required subprograms and shared data are available.
  • Verify that relevant tool and frame selections are correct.
  • Check critical I/O commands and corresponding feedback.
  • Review timeout and recovery behavior where included in the PM scope.
  • Check whether recent tooling, fixture, or process changes require revalidation.
  • Confirm that the approved program copy and revision record are available.

12.2 Functional checks

  • Verify the permitted start and stop behavior.
  • Check representative motion paths using the approved test procedure.
  • Confirm that required external equipment handshakes operate correctly.
  • Verify that missing feedback produces the expected controlled response.
  • Confirm that cycle-complete and fault-status signals are correct.
  • Validate product handling and process quality.
  • Record any deviation and the resulting corrective action.

Do not deliberately create a dangerous fault or bypass an interlock merely to test error handling. Fault simulation must use an approved test method appropriate to the cell.

Robot stops at a wait instruction Required input is absent or the condition is incorrect Check the signal, its source, and the program condition
Robot misses a fixture position Incorrect target, TCP, frame, mastering issue, or mechanical change Check references and measure the actual deviation

Robot repeats a process action Trigger handling, reset logic, or sequence-state problem Inspect start and completion logic

14. Practical Industrial Example: Robot and CNC Handshake

A robot loads a component into a CNC machine. Following maintenance, the robot reaches the machine but remains stopped before unloading the finished part.

Initial observations

  • Robot motion reaches the expected loading area.
  • The robot program is waiting for a machine-ready or cycle-complete condition.
  • The CNC machine appears operational.
  • The production sequence does not continue.

Investigation

  1. Record the active robot instruction and displayed alarm or wait condition.
  2. Identify the exact input or communication bit being awaited.
  3. Verify the corresponding signal at the robot controller.
  4. Check the matching PLC or CNC status and determine whether the signal is actually being generated.
  5. Review the handshake sequence, including signal reset and re-trigger logic.
  6. Check whether the machine completed its cycle but the completion signal was not reset or transferred correctly.
  7. Verify the program revision and any recent PLC or robot changes.

Corrective action

If the PLC fails to generate the required signal, investigate the PLC sequence and its input conditions. If the signal is present at the PLC but absent at the robot, investigate the I/O mapping or communication path. If the signal is available but the robot still waits, verify the program's condition, data type, and referenced signal.

Do not remove the wait instruction merely to make the robot continue. That may allow it to enter the CNC machine before the machine is ready.

Validation

  • Confirm the correct handshake at both controllers.
  • Run the approved functional sequence.
  • Verify that loading, machining, unloading, and cycle-complete states occur in the intended order.
  • Confirm correct part handling and process quality.
  • Document the root cause and test results.

15. Robot Program Troubleshooting Method

Use a repeatable diagnostic sequence to avoid making several unrelated changes during a breakdown.

  1. Capture evidence: Record the alarm, program name, active instruction, robot position, and relevant I/O states.
  2. Identify the failure layer: Determine whether the problem is motion, program logic, shared data, I/O, communication, or external equipment.
  3. Check recent changes: Review program edits, tooling changes, controller restoration, and maintenance activity.
  4. Trace dependencies: Inspect called subprograms, position references, registers, and external signals.
  5. Verify the physical condition: Confirm the tool, fixture, sensors, actuators, and machine state.
  6. Form a specific diagnosis: Identify the condition that explains the observed failure.
  7. Apply an authorized correction: Change only what is justified by the evidence.
  8. Validate safely: Check program flow, motion clearance, handshake behavior, and product quality.
  9. Preserve the result: Save the approved revision and retain the previous version for rollback.
  10. Document the outcome: Record the cause, corrective action, verification, and release approval.

16. Program Backup and Recovery Readiness

Program maintenance and program backup are closely related, but they are separate activities. A program can be running correctly today and still be difficult to recover after a controller failure if its approved revision and required data have not been preserved.

A robot application may require more than the main program file. Depending on the controller, recovery may also depend on subprograms, position data, registers, tool and frame definitions, configuration parameters, I/O mappings, and version-specific files.

During program PM:

  • Verify that the approved program revision is identifiable.
  • Confirm that the required backup exists in the designated location.
  • Check whether recent approved modifications have been included.
  • Record dependencies that are stored separately from the program.
  • Ensure that recovery instructions are available to authorized personnel.
  • Avoid testing a restoration on a production controller without an approved plan.

The dedicated backup topic will cover backup scope, storage, version control, restoration, and recovery validation in detail.

17. Safety Considerations During Program Testing

Robot program testing can introduce risk even when the change is limited to software.

  • Follow the cell's approved maintenance and testing procedure.
  • Confirm the selected operating mode and permitted speed.
  • Check the entire movement path, including the tool, workpiece, fixtures, and neighboring equipment.
  • Keep safety-rated protective functions operational.
  • Do not bypass guards, interlocks, emergency stops, or enabling devices.
  • Do not assume a program's HOME or SAFE_POSITION routine is safe without reviewing its actual behavior.
  • Verify outputs that operate grippers, clamps, welders, dispensers, or other machinery.
  • Consider stored energy and unexpected movement of external equipment.
  • After editing motion instructions, validate the approach, process, and retreat paths.
  • Use authorized procedures for testing abnormal conditions and recovery logic.

A robot program is not a safety system merely because it contains an instruction named SAFE_STOP or RECOVERY. Safety functions must be implemented and validated according to the cell's approved safety architecture.

18. Maintenance Records and SAP PM Traceability

Program-related maintenance should leave enough evidence for another technician to understand the failure and the exact change made.

Record the following where applicable:

Record field Information to capture
Asset identification Robot, cell, controller, and associated machine
Program identification Main program, affected subprogram, and revision
Failure details Alarm code, active instruction, observed behavior, and timestamp
Related signals Relevant I/O states, PLC conditions, and communication status
Root cause Confirmed logic, data, motion, configuration, or interface issue
Corrective action Program correction, data correction, hardware repair, or other approved action
Change control Change request, authorization, revision, and approver
Verification Functional test, motion validation, handshake check, and process-quality result
Recovery information Approved program copy, backup location, and rollback revision
Work-order traceability Technician, work order, date, and release approval

In SAP PM, use the site's established notification, work-order, equipment, and documentation procedures. Record the actual fault and correction rather than entering only “program checked” or “robot OK.”

Repeated program-related failures should be analyzed for recurring causes, such as faulty sensors, unstable communication, inadequate timeout handling, incorrect change control, or a poorly designed recovery sequence.

19. Common Mistakes to Avoid

  • Assuming that a program running without an alarm means the process is correct.
  • Editing production code before capturing the original state and fault evidence.
  • Changing multiple variables at once without verifying which change resolved the problem.
  • Deleting wait instructions to overcome missing feedback.
  • Increasing speed or blending without checking motion clearance and process requirements.
  • Changing shared position data without identifying every dependent program.
  • Treating ordinary program logic as a replacement for safety-rated control.
  • Resetting a sequence without checking whether the robot or machine is holding a part.
  • Restoring a program without checking its revision and related data.
  • Failing to validate robot-to-PLC handshakes after an approved change.
  • Releasing a modified program without documented testing and approval.
