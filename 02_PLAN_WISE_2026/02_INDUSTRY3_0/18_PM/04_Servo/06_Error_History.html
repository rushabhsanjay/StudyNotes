1. Definition and Purpose

Servo error history is the diagnostic record maintained by a servo drive, motion controller, CNC controller, or connected automation system that stores information about faults, alarms, warnings, and abnormal operating events.

It helps maintenance engineers determine what happened, when it happened, under which operating conditions it occurred, and whether the event is recurring.

Error history is especially useful for intermittent servo faults that disappear after a reset or power cycle. The machine may start working again, but the original failure mechanism may remain. Resetting the alarm is not the same as correcting the cause.

The primary objectives of error-history analysis are:

  • Identify the first fault that initiated a machine stoppage.
  • Distinguish the root cause from secondary alarms.
  • Correlate faults with machine position, speed, load, temperature, and operating sequence.
  • Identify recurring failures and deteriorating components.
  • Reduce troubleshooting time and unnecessary component replacement.
  • Support root cause analysis (RCA), corrective and preventive action (CAPA), and preventive maintenance.
  • Build a reliable maintenance history for critical production equipment.

2. Where Error History Is Stored

A servo-controlled machine may store diagnostic information in several locations. Each location provides a different view of the failure.

Storage location Typical information Main use
Servo drive Drive faults, warnings, internal diagnostic codes Drive, motor, feedback, power, and protection faults
CNC or motion controller Axis alarms, following errors, motion-command faults Axis behavior and motion-control diagnosis
PLC Interlocks, sequence faults, enable conditions, machine alarms Machine logic and permissive analysis
HMI Operator-facing alarms and timestamps Understanding what operators observed
Industrial network diagnostics Communication interruptions, device loss, synchronization faults Network and controller communication troubleshooting
SCADA or historian Time-series values, events, trends Correlating failures with operating conditions
Maintenance system such as SAP PM Work orders, failure codes, repairs, spare consumption Long-term reliability analysis

A single physical event can appear in several of these systems. For example, a broken encoder cable may produce a servo feedback alarm, a CNC axis alarm, a PLC sequence timeout, and an HMI machine-stoppage message.

These are not necessarily four independent failures. They may be four consequences of one underlying problem.

3. Fault, Alarm, Warning, and Event

These terms are related but should not be treated as interchangeable. Exact terminology varies by manufacturer.

Term Meaning Typical example
Fault A condition that prevents or interrupts normal operation Motor feedback failure
Alarm A reported abnormal condition requiring attention Servo drive alarm active
Warning A condition that may permit continued operation but requires investigation Temperature approaching a configured limit
Event A recorded state change or occurrence Servo enable command changed to OFF
Trip A protective action that interrupts operation Drive disables output after an overcurrent condition
Reset An action that clears a resettable fault state Resetting an acknowledged drive alarm

A warning can precede a fault, but not every warning develops into a failure. Similarly, a fault reset does not prove that the underlying condition has been eliminated.

4. Typical Servo Error-History Information

Depending on the equipment, each recorded event may contain some or all of the following fields.

Field Purpose
Error code Manufacturer-specific identifier for the event
Error description Text describing the reported condition
Timestamp Date and time of occurrence
Event sequence Relative order in which events were recorded
Axis identification Identifies the affected axis or drive
Severity Distinguishes warnings, faults, and critical events
Operating state Indicates whether the drive was enabled, moving, or stopped
Motor speed Helps determine whether the event occurred during motion
Position Identifies where the fault occurred, if available
Torque or current Helps assess loading and electrical conditions
DC bus voltage Helps investigate supply or regenerative events
Temperature Helps investigate thermal conditions
Reset information Indicates whether the fault was acknowledged or cleared
Communication status Helps correlate faults with network interruptions

Not every servo drive records all these details. Some maintain a compact list of error codes, while advanced motion controllers may retain extensive diagnostic information.

5. Error History Versus Current Alarm Status

The current alarm display and the historical event list serve different purposes.

Current alarm status indicates the conditions that are active now.

Error history records conditions that occurred previously, including faults that may no longer be active.

For example, a servo drive may currently show no alarm because an operator reset it. The error history may still contain a feedback alarm from several minutes earlier.

A proper investigation should therefore capture both the current status and the historical record.

Important considerations:

  • The current alarm may be a consequence of an earlier fault.
  • A cleared alarm may recur if the original problem remains.
  • A power cycle may clear some status information without correcting the cause.
  • Error-history capacity may be limited.
  • Some events may be overwritten when the buffer fills.
  • Some records may be lost after power removal, depending on the device.
  • Controller and drive clocks may not be synchronized.

For intermittent problems, capture the available records before resetting or power cycling equipment whenever it is safe to do so.

6. Understanding Primary and Secondary Faults

One of the most important skills in error-history analysis is identifying the initiating fault.

A single failure can trigger several downstream alarms.

Example:

Encoder Cable Interruption
        ↓
Servo Feedback Fault
        ↓
Drive Stops Producing Torque
        ↓
CNC Axis Motion Aborted
        ↓
PLC Sequence Timeout
        ↓
HMI Machine Stoppage Alarm

The actual sequence depends on the machine design. This example illustrates why the first event in a reliable chronological record is often more useful than the final alarm displayed to the operator.

However, the earliest recorded event is not automatically the root cause. It may be a symptom of an earlier event that was not captured. Use event order, diagnostic evidence, machine behavior, and physical inspection together.

7. Common Servo Fault Categories

7.1 Overcurrent

An overcurrent event indicates that current exceeded a defined limit or protection threshold.

Possible causes include:

  • Motor cable short circuit or ground fault.
  • Motor winding fault.
  • Excessive acceleration or deceleration demand.
  • Mechanical binding or a jammed axis.
  • Incorrect motor or drive configuration.
  • Defective drive power electronics.
  • Incorrect or unstable control conditions.

Useful diagnostic evidence:

  • Whether the fault occurs at enable, startup, acceleration, deceleration, or steady motion.
  • Motor current and torque demand before the trip.
  • Mechanical condition of the axis.
  • Motor and cable inspection results.
  • Drive-specific alarm details.

Do not conclude that the drive is defective simply because it reports an overcurrent fault. The cause may be external to the drive.

7.2 Overvoltage

An overvoltage event can occur when the DC bus voltage exceeds its permitted range.

Possible causes include:

  • Regenerative energy during deceleration.
  • Excessive deceleration rate.
  • High inertia or an unbalanced load.
  • Incorrect braking resistor configuration.
  • Braking resistor circuit failure.
  • Supply voltage outside the permitted range.
  • A fault in the regenerative or braking system.

If the fault consistently occurs during deceleration, investigate regenerative energy and braking configuration. If it occurs while stationary or immediately after energization, supply conditions and drive-specific diagnostics may be more relevant.

7.3 Undervoltage

Undervoltage indicates that the supply or DC bus voltage has fallen below a permitted level.

Possible causes include:

  • Supply interruption.
  • Phase loss or supply imbalance.
  • Loose supply terminals.
  • Undersized or overloaded supply arrangements.
  • Upstream contactor or protection-device problems.
  • Excessive supply disturbance during machine operation.

Compare the fault timestamp with other machines, supply-monitoring records, and plant electrical events where available.

7.4 Encoder or Feedback Fault

Feedback faults occur when the drive cannot obtain valid position or speed information, or when the feedback interface reports an abnormal condition.

Possible causes include:

  • Damaged feedback cable.
  • Loose connector or damaged pins.
  • Encoder supply failure.
  • Incorrect feedback configuration.
  • Incompatible motor or encoder replacement.
  • Electrical interference.
  • Encoder or drive feedback-interface failure.

A feedback fault that appears only during movement should prompt inspection of the moving cable route and connectors. Correlation with a specific axis position can be especially valuable.

7.5 Following Error

Following error is the difference between commanded position and actual measured position.

\[ e(t)=x\_{\text{commanded}}(t)-x\_{\text{actual}}(t) \]

A following error may occur when the axis cannot follow the requested trajectory within the permitted limit.

Possible causes include:

  • Mechanical obstruction.
  • Excessive load or inertia.
  • Incorrect motion tuning.
  • Excessive acceleration or jerk demand.
  • Insufficient motor torque.
  • Feedback problems.
  • Mechanical backlash or coupling problems.
  • Incorrect motion parameters.

Check whether the error occurs at a specific point in the trajectory, at high speed, during acceleration, or under a particular load. These patterns help narrow the investigation.

7.6 Overtemperature

Overtemperature indicates that the drive, motor, or another monitored component has exceeded a defined temperature threshold.

Possible causes include:

  • Excessive duty cycle.
  • High continuous torque demand.
  • Blocked ventilation.
  • High cabinet ambient temperature.
  • Cooling fan failure.
  • Incorrect motor sizing.
  • Poor electrical connections.
  • Excessive switching or braking losses.

A temperature alarm that gradually develops over a production shift suggests a different pattern from an immediate temperature fault at startup. Trend data can help distinguish gradual thermal loading from sensor or configuration problems.

7.7 Communication Fault

Communication faults may occur between the PLC, CNC controller, motion controller, and servo drive.

Possible causes include:

  • Damaged network cable.
  • Loose connector.
  • Network switch or port failure.
  • Incorrect device addressing.
  • Configuration mismatch.
  • Controller or drive restart.
  • Network overload or timing problems.
  • Device or firmware compatibility issues.

Determine whether the drive itself reported the fault or whether the controller reported that the drive became unavailable. These are related but distinct observations.

8. Reading Error Codes Correctly

Error codes are manufacturer-specific. The same numerical code can mean different things on different drive families.

When interpreting an error code, record:

  1. Manufacturer and exact drive model.
  2. Firmware or hardware revision when relevant.
  3. Full error code, including any prefix or subcode.
  4. Exact displayed description.
  5. The operating condition at the time of the event.
  6. The applicable manual section or manufacturer's diagnostic guidance.

Do not rely on a generic online code list without verifying that it matches the installed model and firmware.

A useful maintenance record should preserve the original error code and wording rather than replacing them with a broad description such as "servo problem."

9. Correct Procedure for Capturing Error History

For a non-emergency fault, use a consistent evidence-preservation procedure.

  1. Make the machine safe and follow the applicable safety procedure.
  2. Record the machine number, axis, drive identification, and time of failure.
  3. Photograph or export the active alarm and complete error-history list.
  4. Record the event order and timestamps.
  5. Capture the PLC, CNC, HMI, and network alarms that occurred at approximately the same time.
  6. Record operating conditions such as speed, load, position, and cycle stage, if available.
  7. Preserve relevant trend data and diagnostic buffers.
  8. Only then perform the authorized reset or recovery procedure, when appropriate.
  9. Verify whether the fault recurs after corrective action.
  10. Record the findings and final verification results.

If there is an immediate safety risk, prioritize safe shutdown and isolation over evidence collection.

10. Chronological Analysis

Chronological analysis means arranging recorded events in the order in which they occurred and determining how the events relate to one another.

Example:

Time Recorded event Initial interpretation
10:42:15.120 Network communication warning Possible communication disturbance
10:42:15.240 Servo enable status lost Drive may have become unavailable
10:42:15.310 CNC axis motion aborted Motion interruption follows
10:42:15.500 PLC sequence timeout Machine sequence did not complete

This sequence suggests investigating the network warning first, but it does not prove that the network caused the failure.

The drive and PLC may use different clocks or timestamp resolutions. Before relying on milliseconds of apparent ordering, check clock synchronization and event-buffer behavior.

When precise timestamps are unavailable, use sequence numbers, alarm order, operating records, and controller diagnostics to reconstruct the sequence as accurately as possible.

11. Fault Frequency and Recurrence Analysis

Repeated errors may indicate an unresolved fault, a recurring operating condition, or a component approaching failure.

Useful measures include:

Fault count: Number of occurrences within a defined period.

\[ \text{Fault Count}=\text{Number of recorded occurrences} \]

Fault rate: Number of occurrences divided by operating time.

\[ \text{Fault Rate}=\frac{\text{Fault Occurrences}}{\text{Operating Hours}} \]

Mean time between failures (MTBF): A reliability measure commonly estimated from operating time and failure count for a defined population or repairable system.

\[ \text{MTBF}=\frac{\text{Total Operating Time}}{\text{Number of Failures}} \]

These measures are meaningful only when the counting method and observation period are defined consistently. A warning recorded repeatedly is not necessarily equivalent to a functional failure, and a machine-level stoppage may involve several alarm records.

Practical use

If an axis develops repeated feedback faults, compare fault counts across weeks and examine whether they correlate with operating hours, movement cycles, or specific positions. This can help prioritize inspection of the encoder cable, connectors, and cable carrier.

12. Error History and Trend Data

Error history records discrete events. Trend data records changing values over time.

Using both is often more effective than using either alone.

Error history Trend data
Records the occurrence of a fault Records changing process or diagnostic values
Provides event codes and descriptions Provides values such as current, torque, speed, or temperature
Helps establish event sequence Helps establish the conditions leading up to the event
Useful for identifying recurring alarms Useful for identifying gradual deterioration or transient conditions

For example, a servo drive may record an overtemperature fault. Trend data may show that motor current had gradually increased during several hours of production. That trend could suggest increased mechanical loading, a process change, or a deteriorating mechanical component.

The trend is evidence to investigate, not proof of one specific cause.

13. Error History in PLC, CNC, HMI, and SCADA

A complete investigation should compare the diagnostic records across the control system.

PLC

Review:

  • Sequence state before the stoppage.
  • Enable commands and permissives.
  • Relevant input and output states.
  • Interlock transitions.
  • Timeout and communication logic.
  • PLC task or controller faults, if any.

CNC or motion controller

Review:

  • Axis-specific alarm history.
  • Commanded and actual position.
  • Following error.
  • Motion block or program step.
  • Speed and acceleration conditions.
  • Axis enable and interlock status.

HMI

Review:

  • Operator alarm messages.
  • Alarm acknowledgement time.
  • Sequence step or machine mode.
  • Operator observations.
  • Whether the displayed alarm is primary or consequential.

SCADA and historian

Review:

  • Available time-series values.
  • Event timestamps.
  • Drive and PLC status tags.
  • Repeated stoppage patterns.
  • Correlation with other machine events.

If a Node-RED and SQL Server monitoring system is used, relevant fault records can be stored with the machine ID, axis, alarm code, event timestamp, operating state, and source device. Grafana can then help visualize recurrence and correlate events with available trends.

However, a custom monitoring system must not be assumed to replace the drive's internal diagnostics or any required safety-related monitoring.

14. Practical Example: Recurring Following Error

Situation

A servo-driven fixture intermittently stops during the production cycle. The HMI reports an axis following error.

Investigation

  1. Capture the servo drive and controller error histories.
  2. Determine the sequence of events before the following-error alarm.
  3. Compare commanded and actual position where available.
  4. Check whether the error occurs at a consistent position or during acceleration.
  5. Inspect the fixture, guideways, coupling, and transmission for mechanical resistance.
  6. Review motor current or torque trends.
  7. Check feedback cable condition if the evidence suggests intermittent feedback.
  8. Review relevant motion parameters only after the mechanical and feedback checks.

Possible finding

The fixture develops increased mechanical resistance at one section of travel. The servo cannot follow the commanded trajectory within the permitted error limit and generates a fault.

Corrective action

Correct the verified mechanical problem, inspect the affected components, and perform the required controlled motion and repeatability checks.

Increasing the following-error limit without identifying the underlying cause may hide a developing mechanical problem and reduce the protection intended by the original configuration.

15. Practical Example: Encoder Fault After a Power Cycle

Situation

A servo axis reports an encoder fault after restart. Resetting the drive restores operation, but the fault returns intermittently.

Investigation

  • Record the complete fault history before another reset.
  • Compare the fault timing with drive startup and feedback initialization.
  • Verify the encoder model and compatibility.
  • Inspect connector seating and pin condition after safe isolation.
  • Check feedback cable continuity using an approved procedure.
  • Review the drive's feedback diagnostics and configuration.
  • Determine whether other faults, such as undervoltage or communication loss, occurred first.

Possible causes

  • Intermittent feedback connector contact.
  • Damaged feedback cable.
  • Incorrect feedback configuration.
  • Encoder supply instability.
  • An underlying drive or encoder defect.

Corrective action

Repair or replace the confirmed defective component, restore the approved configuration, and validate operation over the required operating range.

Repeatedly resetting the fault without preserving evidence can make an intermittent issue harder to diagnose.

16. Practical Example: Overvoltage During Deceleration

Situation

A servo axis runs normally at constant speed but trips with an overvoltage fault during rapid deceleration.

Investigation

  1. Verify the exact drive alarm and when it occurs.
  2. Review the deceleration profile and load characteristics.
  3. Examine available DC bus and regenerative diagnostics.
  4. Verify braking resistor installation and configuration, if applicable.
  5. Check whether the mechanical load or duty cycle has changed.
  6. Compare the configured deceleration behavior with the manufacturer's limits.
  7. Verify any corrective adjustment through an approved commissioning process.

Possible finding

The deceleration profile produces more regenerative energy than the installed braking arrangement can handle under the current operating conditions.

Corrective action

Apply a manufacturer-approved correction, such as adjusting the motion profile or correcting the braking arrangement, after confirming the actual cause.

Do not install an arbitrary resistor or alter drive protection settings without verifying compatibility and the manufacturer's requirements.

17. Error History and Maintenance Management

Error-history analysis becomes more valuable when linked to maintenance records and machine reliability data.

For each significant fault, maintain:

  • Machine and axis identification.
  • Drive and motor model.
  • Error code and exact description.
  • Occurrence date and time.
  • Operating conditions and related events.
  • Investigation and test results.
  • Confirmed root cause, if established.
  • Corrective action and replacement parts.
  • Verification results.
  • Recurrence status.
  • Relevant drawing, parameter backup, or diagnostic-file revision.

In SAP PM, these details can support notifications, maintenance orders, failure coding, repair history, and recurring-problem analysis.

The purpose is not merely to count alarms. It is to identify patterns that justify a targeted inspection, engineering modification, spare-parts strategy, or preventive-maintenance change.

18. Preventive Maintenance Checklist

Routine review

  • Review recurring servo alarms.
  • Identify faults that appear after startup, during motion, or during deceleration.
  • Check whether alarms repeatedly occur on the same axis.
  • Review warnings that consistently precede functional failures.
  • Confirm that important faults are being captured in the maintenance record.
  • Check the availability of approved drive and controller diagnostic manuals.

After a significant failure

  • Capture current alarms and error history before reset, where safe.
  • Preserve relevant PLC, CNC, HMI, and network records.
  • Confirm the event sequence and timestamp reliability.
  • Separate the first observed fault from downstream alarms.
  • Use measurements and inspection to verify the suspected cause.
  • Record corrective actions and the evidence supporting the diagnosis.
  • Verify operation after repair.
  • Update the maintenance record and track recurrence.

19. Common Mistakes in Error-History Analysis

  • Resetting before capturing evidence: The diagnostic context may be lost or become harder to reconstruct.
  • Replacing the component named in the alarm: The alarm identifies a detected condition, not necessarily the failed component.
  • Treating every alarm as an independent failure: Several alarms may be consequences of one initiating event.
  • Ignoring event order: A downstream PLC timeout may distract from an earlier drive or network fault.
  • Using the wrong error-code reference: Codes can vary by manufacturer, model, and firmware.
  • Ignoring operating conditions: A fault limited to high speed or one axis position provides useful diagnostic evidence.
  • Changing parameters before checking hardware: Configuration changes can conceal mechanical, electrical, or feedback problems.
  • Assuming a cleared alarm means the fault is fixed: Intermittent faults can disappear temporarily.
  • Ignoring clock differences: Incorrect timestamp alignment can produce a false event sequence.
  • Failing to document the repair: Repeated investigations waste time when previous findings cannot be retrieved.

20. Key Engineering Principles

  • Error history is evidence for diagnosis, not a substitute for testing.
  • Preserve fault records before resetting whenever safe and practical.
  • Identify the earliest credible event and distinguish it from secondary alarms.
  • Compare drive, CNC, PLC, HMI, and network records.
  • Use the exact manufacturer-specific error description and diagnostic procedure.
  • Correlate faults with motion state, axis position, speed, load, temperature, and operating sequence.
  • Use trend data to investigate conditions leading up to the event.
  • Verify the root cause before replacing components or changing parameters.
  • Record the confirmed cause, corrective action, and verification result.
  • Use recurring-error data to improve preventive maintenance and equipment reliability.
