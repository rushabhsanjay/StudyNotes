1. Definition

SCADA stands for Supervisory Control and Data Acquisition. It is an industrial system used to monitor processes, collect data, present alarms and trends, and support supervisory control of machines and production systems.

SCADA architecture describes how PLCs, communication drivers, servers, operator clients, databases, and other components work together.

In a manufacturing plant, a SCADA system might collect status and production data from multiple PLCs, display it on an operator workstation, record process values in a database, and make historical information available to maintenance and production teams.

The important thing is understanding not just what each component does, but where data originates, how it travels, where it is stored, and which component is responsible for each operation.

2. What Is SCADA Architecture?

A typical SCADA system can be represented as follows:

         Operator / Maintenance Engineer
                       |
                       v
               SCADA Client
           Screens, alarms, trends
                       |
                       v
                SCADA Server
        Application and data services
                       |
                       v
            Communication Driver
          Protocol and data exchange
                       |
                       v
                PLC / Controller
                       |
                       v
            Sensors and Actuators
                       |
                       v
                Physical Machine

Additional components can connect to this architecture:

  • Industrial historians for long-term process data.
  • SQL databases for structured records.
  • Engineering workstations for configuration and maintenance.
  • Reporting and analytics systems.
  • Industrial network infrastructure.
  • Redundant servers for availability.
  • Gateways for exchanging data between networks or systems.

This is a conceptual architecture. Actual products may combine multiple functions in one computer or distribute them across several computers.

3. SCADA Versus HMI Versus PLC

These terms are related, but they describe different roles.

Component Main responsibility Example
PLC Executes control logic and interacts with field I/O ControlLogix controlling a robotic station
HMI Provides an operator interface to a machine or process PanelView showing station status
SCADA Provides supervisory monitoring and data acquisition across equipment or processes Monitoring several production stations
SCADA server Hosts configured application services and coordinates data access A PC running a SCADA application server
SCADA client Provides a user interface to the SCADA system An operator workstation
Driver Exchanges data using a supported protocol or communication interface A driver communicating with an Allen-Bradley PLC
Database Stores structured records SQL Server storing production values
Historian Stores time-series process data for historical analysis An industrial process historian

An HMI can be part of a SCADA system, but a single machine HMI is not automatically a complete SCADA system.

Likewise, a database is not automatically a historian, and a SCADA server does not automatically perform every data-storage and communication function.

4. The Main SCADA Components

4.1 PLC or controller

The PLC is responsible for executing its control program, processing inputs, updating outputs, and managing the programmed machine sequence.

Typical data includes:

  • Machine operating state.
  • Sensor feedback.
  • Actuator commands and feedback.
  • Fault conditions.
  • Production counts.
  • Process values.
  • Cycle status.

For example, a PLC at a robotic station may publish a station-ready bit, a robot-fault bit, and a cycle counter.

The PLC remains responsible for the control logic. A SCADA application should not be treated as a replacement for real-time PLC control or safety-rated functions.

4.2 Communication driver

A communication driver enables a SCADA application or data service to exchange data with a supported controller or device.

It handles the communication mechanism required by the configured protocol, which may include reading data, writing permitted values, and reporting communication errors.

Examples of industrial communication technologies include:

  • EtherNet/IP.
  • Siemens S7 communication.
  • Mitsubishi SLMP or compatible Mitsubishi communication methods.
  • Modbus TCP and Modbus RTU.
  • OPC UA, where supported.

These are not interchangeable protocols. The controller, driver, network, and configuration must support the selected communication method.

4.3 SCADA server

A SCADA server provides configured application services. Depending on the product, these may include:

  • Access to process data.
  • Alarm processing and distribution.
  • Application configuration and runtime services.
  • Client connections.
  • Data logging or interfaces to external storage.
  • User and application services.

Not every SCADA product places all these functions on one server. Some systems use separate data servers, alarm servers, historians, or redundant server pairs.

4.4 SCADA client

A SCADA client is the user-facing application used to interact with the SCADA system.

It can provide:

  • Overview screens.
  • Equipment detail screens.
  • Alarm summaries.
  • Trends.
  • Production information.
  • Authorized supervisory commands.
  • Diagnostic views.

A client may receive data from a server rather than communicating directly with every PLC. However, some architectures support direct client-to-controller communication for particular functions.

4.5 Database and historian

These components store information for later use, but they are not necessarily the same thing.

A relational database such as SQL Server can store structured records, including production counts, events, maintenance records, and selected process values.

A historian is specifically designed for time-series process data and may provide compression, retention management, and efficient historical queries.

A SCADA application can use one or both, depending on the requirements.

5. How Data Travels Through SCADA

Understanding the direction of data flow is one of the most important SCADA fundamentals.

5.1 Read path: PLC to operator screen

Suppose a PLC contains a Boolean tag indicating that a station is ready.

PLC tag: Station_Ready
          |
          v
Communication driver reads the tag
          |
          v
SCADA data service updates the value
          |
          v
SCADA client receives or accesses the value
          |
          v
Screen displays READY or NOT READY

The exact route depends on the software architecture. The driver may run on the SCADA server, an OPC server, or another configured computer.

5.2 Write path: operator command to PLC

Suppose an authorized operator requests a machine cycle.

Operator presses Start
          |
          v
SCADA client sends configured request
          |
          v
SCADA service and driver process the write
          |
          v
PLC receives the command
          |
          v
PLC validates operating conditions
          |
          v
PLC executes the permitted sequence
          |
          v
Feedback returns to SCADA

The PLC should validate the command and control the sequence. The SCADA client should not bypass the PLC's interlocks or safety functions.

5.3 Data is not the same as data quality

A displayed value can be incorrect, stale, or unavailable even when the screen itself appears normal.

A robust system should distinguish between:

  • Value: The reported process value.
  • Timestamp: When the value was acquired or updated.
  • Quality: Whether the value is considered valid.
  • Communication state: Whether the data source is reachable and responding.
  • Freshness: Whether the value is recent enough for its intended use.

For example, a screen displaying Station_Ready = TRUE after communication has failed may mislead an operator if the application does not indicate that the value is stale.

A good SCADA design handles communication loss explicitly rather than leaving old values looking trustworthy.

6. Single-Computer Versus Client-Server Architecture

SCADA systems can be deployed in different physical arrangements.

6.1 Standalone architecture

In a standalone configuration, a single computer may run the SCADA runtime, communicate with PLCs, display screens, and store selected data.

       Operator
           |
           v
    SCADA Computer
    +-------------+
    | Client      |
    | Runtime     |
    | Driver      |
    | Logging     |
    +-------------+
           |
           v
          PLC

Advantages:

  • Simpler deployment.
  • Fewer computers and network dependencies.
  • Suitable for small applications.

Limitations:

  • The computer can become a single point of failure.
  • Scaling to many clients or controllers can become difficult.
  • Maintenance or restart may interrupt several functions at once.

6.2 Client-server architecture

In a client-server arrangement, the SCADA server provides shared application services while client computers provide operator interfaces.

 Operator A                  Operator B
     |                           |
     v                           v
 SCADA Client A              SCADA Client B
     |                           |
     +-------------+-------------+
                   |
                   v
              SCADA Server
                   |
                   v
             PLC Driver / Data
                   |
                   v
              PLC Controllers

Advantages:

  • Multiple clients can access shared data and application services.
  • Application management can be centralized.
  • Operator interfaces can be separated from server functions.
  • The architecture can be expanded as requirements grow.

Limitations:

  • More configuration and administration.
  • Dependence on server and network availability.
  • Greater need for access control, backups, monitoring, and cybersecurity.

A client-server system is not automatically redundant. If one server provides an essential service and has no failover arrangement, that server can still be a single point of failure.

7. Distributed SCADA Architecture

Larger plants may distribute functions across several computers and services.

For example, an installation might include:

  • An HMI or visualization server.
  • One or more operator clients.
  • A communication or OPC server.
  • A historian.
  • A SQL database.
  • An engineering workstation.
  • Reporting and analytics services.

A conceptual arrangement is:

                  Operator Clients
                         |
                         v
                 Visualization Server
                         |
              +----------+----------+
              |                     |
              v                     v
        Data / OPC Server      Alarm Services
              |
              v
       Industrial Controllers
              |
              v
        Machines and I/O

        Visualization / Data Services
                    |
                    v
             Historian / SQL
                    |
                    v
            Reports / Analytics

The diagram separates logical responsibilities, not necessarily physical computers. One computer can host several services, or each service can run on a separate machine.

Why distribute components?

Distribution can improve scalability, simplify separation of responsibilities, and support different retention or reporting requirements.

However, it introduces additional dependencies. A failure in DNS, time synchronization, network routing, authentication, a shared data service, or storage can affect multiple applications even when the PLCs themselves continue controlling the machines.

8. Communication Drivers and Protocols

A communication protocol defines how devices exchange messages. A driver implements the communication behavior required by a particular application or service.

For example, a SCADA system may use an EtherNet/IP-capable driver to access data from a compatible Allen-Bradley controller.

The driver must be configured with the correct device, address, communication settings, and data references.

Technology Typical role
EtherNet/IP Industrial communication commonly used with Allen-Bradley systems
Siemens S7 communication Communication with supported Siemens PLCs
Mitsubishi SLMP Communication with supported Mitsubishi controllers
Modbus TCP Industrial data exchange over TCP/IP
Modbus RTU Serial communication using Modbus
OPC UA Standardized industrial data access and exchange between supported applications
OPC Classic / DA Legacy Windows-based industrial data access technology found in older installations

Support depends on the specific driver, device, product version, and configuration.

Direct driver versus OPC server

Direct driver approach:

SCADA application
       |
       v
Built-in / configured driver
       |
       v
PLC

The SCADA application uses its own supported driver to communicate with the PLC.

OPC-based approach:

SCADA application
       |
       v
OPC client interface
       |
       v
OPC server
       |
       v
PLC

The OPC server provides a data interface to the SCADA application and communicates with the PLC through its supported driver or connection.

An OPC server can make data available to multiple compatible clients, but that does not mean every OPC server supports every PLC or every feature.

Why this distinction matters

If the SCADA application uses an OPC server and the displayed values are invalid, the fault may be in the SCADA tag configuration, OPC client connection, OPC server, PLC driver, or controller communication.

Troubleshooting becomes easier when the architecture identifies which component owns each connection.

9. PLCs and the SCADA Data Model

A SCADA application needs a consistent way to identify data across connected controllers.

For example, a plant may contain several PLCs, each with its own internal device addresses or controller tags.

PLC_Station_1010
    Station_Ready
    Station_Fault
    Cycle_Count

PLC_Station_1030
    Station_Ready
    Station_Fault
    Cycle_Count

PLC_Station_1050
    Station_Ready
    Station_Fault
    Cycle_Count

The same tag name can exist in multiple PLCs. Therefore, a complete reference must identify the correct data source as well as the tag.

A SCADA application may expose these values under a hierarchy such as:

Plant
  |
  +-- Robotic_Line
        |
        +-- Station_1010
        |      +-- Station_Ready
        |      +-- Station_Fault
        |
        +-- Station_1030
        |      +-- Station_Ready
        |      +-- Station_Fault
        |
        +-- Station_1050
               +-- Station_Ready
               +-- Station_Fault

This hierarchy is a logical organization of data. It does not necessarily match the physical network topology or the PLC program structure.

A well-designed data model helps operators navigate the plant and helps maintenance engineers trace a displayed value back to its source.

10. Polling, Update Rates, and System Performance

SCADA applications do not necessarily read every PLC value continuously or at the same rate.

Data acquisition may use polling, subscriptions, event-driven updates, or a combination, depending on the protocol and product.

Important timing concepts include:

Term Meaning
PLC scan time Time taken by the controller to execute its program cycle or relevant task
Driver polling interval Configured interval for a driver to request data, where polling is used
HMI refresh interval How frequently the application updates a displayed object
Logging interval How frequently values are recorded, where interval-based logging is used
Network latency Time required for data to travel through the communication path
Data age Time elapsed since the source value was acquired or updated

These intervals are not interchangeable.

A screen refreshing every 250 ms does not prove that the PLC is being read every 250 ms. The screen may repeatedly display the most recent cached value.

Example

Suppose:

  • The driver updates a tag every 1 second.
  • The client refreshes its screen every 250 ms.
  • Historical data is recorded every 5 seconds.

The screen may refresh four times between driver updates, while the database receives one record every 5 seconds, assuming those configurations are implemented as stated.

Common performance problems

  • Too many tags being polled too frequently.
  • Excessive clients or redundant requests.
  • Slow or unreliable networks.
  • Unnecessary high-frequency logging.
  • Database writes taking too long.
  • Large screens with many continuously updated objects.
  • Excessive alarm or event activity.

The correct update rates depend on the application. A machine-status display, a fast motion-control signal, and a long-term energy trend do not necessarily require the same acquisition interval.

SCADA monitoring must not be used as a substitute for time-critical PLC control.

11. Redundancy and Availability

A SCADA system may use redundancy to reduce the impact of a component failure.

Possible arrangements include:

  • Primary and standby SCADA servers.
  • Redundant communication paths.
  • Redundant network infrastructure.
  • Replicated or highly available data storage.
  • Backup operator workstations.

A simplified redundant-server arrangement is:

             SCADA Clients
                   |
                   v
            Active SCADA Server
                   |
          Failover / synchronization
                   |
                   v
            Standby SCADA Server
                   |
                   v
             PLC Controllers

This is conceptual. Actual failover behavior depends on the SCADA product and architecture.

Redundancy must be engineered and tested. Two servers do not automatically provide uninterrupted service if their configurations are inconsistent, they share a failed dependency, or the failover process is not working.

Also distinguish availability from data integrity. A system may continue running but lose some historical records or experience a gap during failover.

12. SCADA Network Architecture and Cybersecurity

Industrial networks should be designed so that access to controllers is controlled and unnecessary exposure is minimized.

A common approach separates the industrial control network from enterprise IT networks and uses controlled communication between zones.

Enterprise IT Network
          |
          v
   Controlled Boundary
   / Industrial DMZ \
          |
          v
   SCADA / Operations
          |
          v
   Industrial Control
          |
          v
       PLCs / I/O

The exact arrangement depends on the site's cybersecurity architecture.

Important practices include:

  • Segmenting networks according to operational and security requirements.
  • Restricting access to PLCs and SCADA servers.
  • Using appropriate authentication and authorization.
  • Managing remote access through approved secure mechanisms.
  • Maintaining software and configuration backups.
  • Monitoring system health and communication failures.
  • Controlling changes to drivers, PLC programs, and SCADA applications.
  • Maintaining an inventory of computers, controllers, software versions, and network dependencies.

Do not expose PLCs or SCADA services directly to untrusted networks merely to make remote viewing convenient. Convenience is not a cybersecurity architecture.

13. SCADA Versus MES, ERP, and Historian

These systems can exchange data, but they have different primary responsibilities.

System Primary purpose
PLC Real-time control of equipment
HMI Operator interface for a machine or process
SCADA Supervisory monitoring, control, alarms, and data acquisition
Historian Time-series process-data storage and retrieval
MES Manufacturing execution, production tracking, and operations management
ERP Business processes such as materials, finance, purchasing, and planning
SQL database Structured data storage for supported applications

For example, a PLC may count completed cycles, SCADA may display and record the count, MES may associate production with an order, and ERP may manage the relevant material and production planning.

These systems can be integrated, but integration does not make them the same thing.

14. Practical Example: Automotive Robotic Line

Consider a production line with three robotic stations. Each station has a PLC, and a SCADA system monitors the line.

System requirements

  • Display each station's ready and fault status.
  • Show selected cycle counters.
  • Provide an alarm overview.
  • Record selected process values.
  • Store production-related records in SQL Server.
  • Allow authorized personnel to inspect historical trends.

Architecture

PLC - Station 1010 ----+
                       |
PLC - Station 1030 ----+---- Industrial Network
                       |            |
PLC - Station 1050 ----+            v
                               SCADA Driver
                                    |
                                    v
                              SCADA Server
                               /         \
                              v           v
                       SCADA Client    Data Logging
                                            |
                                            v
                                       SQL Server
                                            |
                                            v
                                      Reports

This is an illustrative arrangement. Depending on the selected software, the driver, SCADA server, and logging services might be combined or deployed separately.

Data flow

  1. Each PLC executes its machine-control program.
  2. The communication layer acquires configured PLC data.
  3. The SCADA application makes the data available to its clients.
  4. Operators see machine states and configured alarms.
  5. Selected values or events are logged.
  6. SQL Server stores structured records.
  7. Reports use stored data for production and maintenance analysis.

Maintenance investigation

Suppose Station 1030 shows a fault, but Station 1010 appears normal.

A maintenance engineer can investigate:

  1. Whether the Station 1030 PLC reports the fault.
  2. Whether the driver can read the relevant PLC tag.
  3. Whether the SCADA server receives a valid, recent value.
  4. Whether the client displays the correct state.
  5. Whether the alarm is configured to identify the underlying condition.
  6. Whether the physical equipment or process is actually faulty.

This separates the machine fault from a communication or visualization fault.

A SCADA screen reporting a fault does not automatically mean SCADA caused the fault. It may simply be the first place the problem became visible.

15. Common SCADA Architecture Faults

Symptom Possible architectural cause Investigation
All PLC values are unavailable Shared driver, network, or server failure Check the shared communication path
One PLC is unavailable Controller-specific connection or network problem Check that PLC and its configured connection
Client cannot connect Client/server communication or application configuration Check the client connection and server status
Multiple clients show stale values Shared data service or driver issue Check source updates and data quality
Only one screen shows incorrect data Client object or tag mapping problem Trace the specific object and reference
Alarms appear late Acquisition, processing, communication, or display delay Trace the alarm from its source to the client
Historical records are missing Logging service, storage, or database problem Check acquisition, logging, and database writes
SCADA becomes slow Excessive polling, client load, or resource constraints Review update rates and system performance
System fails during server maintenance Missing or ineffective redundancy Review availability design and recovery procedures
Values look valid after communication loss Stale-value handling is inadequate Check quality indicators and stale-data behavior
PLC responds but SCADA does not Driver, data mapping, or server configuration problem Verify the configured communication and data references

Troubleshooting principle

Trace the failure from the source toward the display.

For a missing PLC value, investigate the PLC, network, driver, data service, and client in sequence. For a missing historical record, also inspect the logging path and storage system.

Changing an HMI object before establishing where the data path failed is often wasted work.

16. Interview Questions and Answers

Q1. What is SCADA?

SCADA stands for Supervisory Control and Data Acquisition. It provides supervisory monitoring, data acquisition, alarms, visualization, and configured control functions for industrial processes.

Q2. What is the difference between a SCADA server and a client?

A server provides configured application services and data access. A client provides the user interface through which an operator interacts with the system.

Q3. What is a communication driver?

A driver implements communication with a supported device or protocol so that an application can exchange process data.

Q4. What is an OPC server?

An OPC server provides a standardized data interface to compatible clients and obtains data through its configured device connections or other data sources.

Q5. What is the difference between a SCADA server and a database?

A SCADA server provides application and monitoring services. A database stores structured records. A SCADA system may write data to a database without the database itself acting as the SCADA server.

Q6. Why can a SCADA screen show stale values?

The application may continue displaying the last acquired value after communication fails unless it detects the failure and handles data quality appropriately.

Q7. What is the difference between polling and screen refresh?

Polling requests or acquires data from a source. Screen refresh updates the displayed interface. The display can refresh more frequently than new data arrives.

Q8. What is the purpose of SCADA redundancy?

Redundancy reduces the impact of selected component failures by providing alternate services or paths, subject to the design and tested failover behavior.

Q9. Why separate SCADA clients from servers?

It allows multiple operator interfaces to use shared services and can simplify application management and expansion.

Q10. Why is network segmentation important?

It limits unnecessary connectivity between network zones and helps control access to industrial controllers and supervisory systems.

Q11. Is SCADA a replacement for PLC control?

No. The PLC normally executes the machine-control logic. SCADA provides supervisory monitoring and configured commands.

Q12. What is the difference between a historian and SQL Server?

A historian is optimized for time-series process data. SQL Server is a relational database platform that can store structured records, including time-stamped process values, depending on the application design.

17. Practical Exercises

Use a development environment or an approved test system.

  1. Draw the architecture of a standalone SCADA system.
  2. Draw a client-server SCADA architecture with two clients and one PLC.
  3. Identify where the communication driver runs in an existing installation.
  4. Trace one PLC value from the source tag to the operator screen.
  5. Distinguish the PLC scan time, acquisition interval, screen refresh interval, and logging interval.
  6. Identify the database or historian used by an existing application.
  7. Determine what happens when one PLC becomes unavailable.
  8. Determine what happens when the SCADA server becomes unavailable.
  9. Check how stale values and communication failures are indicated.
  10. Identify the shared components that could affect several clients.
  11. Draw the data path from a PLC through SCADA logging to SQL Server.
  12. Prepare a troubleshooting checklist for a system where the PLC is operating normally but the SCADA client displays invalid values.

Remember the role of each component:

  • PLC: Controls the machine.
  • Driver: Communicates with the controller.
  • Server: Provides configured application services.
  • Client: Presents the operator interface.
  • Database: Stores structured records.
  • Historian: Stores and serves historical process data.
  • Network: Connects the components and introduces its own failure modes.
  • SCADA architecture: Defines how these components communicate, share responsibilities, and recover from faults.

The most useful SCADA maintenance skill is understanding the complete path from the physical process to the displayed value and, where applicable, from an operator command back to the PLC.
