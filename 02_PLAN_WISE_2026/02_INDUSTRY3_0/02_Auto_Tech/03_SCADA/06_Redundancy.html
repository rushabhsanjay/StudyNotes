1. Definition

Redundancy is the use of additional components, connections, or systems so that a failure in one component does not necessarily cause the entire system to lose its required function.

In industrial SCADA, redundancy is used to improve availability when servers, network connections, communication services, or other critical components fail.

For example, a SCADA system monitoring an automotive robotic line may use two SCADA servers. If the active server fails, a standby server can take over, provided the system is designed and configured to support that transition.

Redundancy is not simply installing two computers and hoping they cooperate. The system must detect failures, determine which component should take control, preserve or recover the required data, and avoid conflicting active systems.

2. Why Redundancy Is Required

Industrial systems can experience failures involving:

  • SCADA server hardware.
  • Operating systems or SCADA services.
  • Network switches.
  • Network cables or fiber links.
  • PLC communication paths.
  • OPC servers and communication gateways.
  • Database servers.
  • Power supplies.
  • Storage devices.
  • Cooling systems and other supporting infrastructure.

A single component whose failure interrupts an important function is a potential single point of failure.

For example, if every SCADA client depends on one server and that server becomes unavailable, the clients may lose monitoring and supervisory functions even if the PLCs continue controlling the machines.

Redundancy aims to reduce the operational impact of such failures.

Its objectives may include:

  1. Maintaining monitoring and visualization.
  2. Reducing interruption to operator supervision.
  3. Preserving alarm and process data.
  4. Maintaining communication availability.
  5. Supporting recovery with minimal disruption.
  6. Reducing production risk caused by infrastructure failure.

The required level of availability depends on the consequences of failure, the process design, and the organization's recovery requirements.

3. What Is a Single Point of Failure?

A single point of failure (SPOF) is a component or dependency whose failure can interrupt a required system function because no suitable alternative is available.

Consider a basic SCADA architecture:

Single Network Switch

Single SCADA Server
     |

Operator Clients

Potential single points of failure include:

  • The network switch.
  • The SCADA server.
  • A single communication gateway.
  • A single network connection to a critical device.

If the SCADA server fails, clients may lose SCADA services. If the switch fails, the server may lose connectivity to the PLC network.

The PLCs may continue their local control programs, but this depends on the control architecture and failure conditions. Loss of SCADA does not automatically mean either that production stops or that production can safely continue.

5. Types of Redundancy

5.1 Server redundancy

Two or more servers provide the same critical service, with an active/standby or other supported arrangement.

Examples:

  • Redundant SCADA servers.
  • Redundant OPC or communication servers.
  • Redundant application services.

The standby system must have the required configuration, software, licenses, connections, and data synchronization to perform the intended role.

5.2 Network redundancy

Multiple communication paths are provided so that a cable, switch, or link failure does not necessarily isolate the system.

Examples:

  • Redundant Ethernet paths.
  • Supported ring topologies.
  • Redundant industrial network interfaces.
  • Redundant switches and uplinks.

Network redundancy depends on the topology and protocol. Two cables do not automatically create a functioning redundant network.

5.3 Communication redundancy

A device or application can communicate through an alternative supported communication path or interface.

For example, a SCADA data service may be configured to use a secondary communication path when the primary path becomes unavailable.

The controller, driver, network, and application must all support the intended arrangement.

5.4 Power redundancy

Critical equipment uses redundant power supplies or separate power sources where supported.

A redundant server connected to a single failed power distribution point may still lose power. The upstream power architecture matters.

5.5 Storage redundancy

Storage systems may use RAID, replicated storage, or other technologies to reduce the impact of particular storage failures.

Storage redundancy does not replace backups. RAID, for example, does not protect against every form of data loss, such as accidental deletion, corruption replicated across a system, or ransomware.

5.6 Database redundancy

A database architecture may use replication, clustering, or supported high-availability mechanisms.

This helps preserve access to historical or transactional data when a database component fails.

However, database failover must account for connection handling, committed transactions, data consistency, and application reconnection.

6. Active/Standby and Active/Active Architectures

6.1 Active/standby

One system performs the active role while another is prepared to take over.

Normal operation:

PLC Data ---> Server A [ACTIVE]
             Server B [STANDBY]

After Server A fails:

PLC Data ---> Server B [ACTIVE]
             Server A [FAILED]

Advantages:

  • Clear ownership of the active role.
  • Potentially simpler workload and state management.
  • Often suitable for supervisory services.

Considerations:

  • The standby system must remain ready.
  • Configuration and relevant state must be synchronized.
  • Failover may interrupt clients or data acquisition.
  • A failed primary may not return automatically to service.

Some products support warm standby, where the secondary remains initialized and synchronized. Others may require a more substantial startup process.

6.2 Active/active

Multiple systems perform active work simultaneously.

Examples may include distributed SCADA servers or services sharing workloads.

Advantages:

  • Workload can be distributed.
  • Some failures may have less effect on capacity.
  • Resources may be used more efficiently.

Considerations:

  • Workload distribution and service ownership must be defined.
  • Data consistency becomes more complex.
  • Clients must know which service or node to use.
  • Simultaneous writes or commands must be controlled.
  • Failure of one node can overload the remaining nodes.

Active/active is not automatically more reliable than active/standby. It depends on the application and the way shared state is managed.

7. How Server Failover Works

Failover usually involves several stages.

  1. Failure detection: The system identifies that the active service is unavailable or unhealthy.
  2. Role decision: The redundancy mechanism determines whether the standby should take over.
  3. Promotion: The standby becomes active for the relevant service.
  4. Client reconnection: Clients connect to the active service, using the product's supported mechanism.
  5. Data recovery: The system resumes data acquisition and logging, with any required reconciliation.
  6. Status verification: Operators and administrators verify that the service is operating correctly.

Example: SCADA server failure

Suppose Server A is actively acquiring PLC data and serving operator clients. Server B is synchronized and on standby.

If Server A fails, the redundancy mechanism may promote Server B. Clients then resume using the active server.

The actual result depends on the product. There may be a brief interruption, missing samples, client reconnection delays, or a need for manual intervention.

Failover does not guarantee zero interruption or zero data loss. Those are design targets that must be verified under realistic failure tests.

8. Heartbeats and Failure Detection

A heartbeat is a periodic indication that a component or service is available.

A redundancy system may use:

  • Network heartbeat messages.
  • Service health checks.
  • Application-level status checks.
  • Controller or device communication diagnostics.
  • Dedicated monitoring paths.

If expected heartbeats are not received, the system may classify a node as unavailable.

Why failure detection is not always simple

A missed heartbeat does not necessarily prove that the server has failed.

Possible causes include:

  • Server failure.
  • Network partition.
  • Switch failure.
  • Temporary congestion.
  • A stalled application service.
  • A blocked monitoring path.

If the system incorrectly promotes a standby while the original server is still operating, both may become active.

This condition is called split-brain.

Preventing split-brain

Depending on the architecture, prevention mechanisms may include:

  • Quorum or voting mechanisms.
  • Witness services.
  • Fencing or isolation of the failed node.
  • Leases or controlled ownership of shared resources.
  • A supported redundancy protocol.

A system should not rely on the assumption that only one server can ever believe it is active. Networks have an irritating habit of failing in ways that violate assumptions.

9. Network Redundancy and Failover

Network redundancy aims to preserve communication when a link or network component fails.

9.1 Single-path network

SCADA Server
     |
     v
  Switch A
     |
     v
    PLC

If the only switch or link fails, communication may be interrupted.

9.2 Redundant paths

                +---- Switch A ----+
                |                  |
SCADA Server ---+                  +--- PLC Network
                |                  |
                +---- Switch B ----+

This is only conceptual. Actual redundant network topologies must avoid loops, define link-selection behavior, and use protocols supported by the network devices.

Common network redundancy approaches

Redundant links: Alternative connections between network devices.

Ring topologies: Devices are connected in a ring, with supported mechanisms to restore communication around a failed link.

Spanning Tree protocols: Ethernet switching protocols that prevent loops and can reconfigure paths after certain failures.

Industrial redundancy protocols: Protocols designed for specific industrial network requirements, depending on the devices and topology.

Redundant network interfaces: A device or server uses multiple supported network interfaces.

These approaches are not interchangeable. Selection depends on device compatibility, topology, recovery-time requirements, network design, and configuration.

Important caution

Connecting two network cables between the same devices without the correct supported configuration can create an Ethernet loop, duplicate paths, or unexpected traffic behavior.

Network redundancy must be engineered and tested, not improvised during a production shift.

10. Redundancy in SCADA Data Acquisition

A redundant SCADA server must be able to acquire the required PLC data after taking over.

The design must consider:

  • Which server owns each active PLC connection.
  • Whether both servers can communicate with the PLC.
  • Whether the PLC or driver supports multiple simultaneous clients.
  • Whether communication ownership changes during failover.
  • How tag values and data quality are initialized.
  • Whether alarms are duplicated or missed.
  • Whether historical logging resumes correctly.
  • How the clients locate the active server.

Some PLCs and communication interfaces have connection limits or specific redundancy requirements. Confirm the supported architecture before enabling simultaneous communication from multiple servers.

Example

Suppose a line has 150 robots and stations monitored by a SCADA server. The standby server has the same tag configuration but is not actively acquiring every value.

After failover, the standby may need to establish communication sessions and refresh its tag values.

If its connection capacity or startup behavior has not been tested, the system may technically fail over while still delivering incomplete or delayed monitoring.

A redundancy test must therefore verify service quality, not merely confirm that a server icon changes from standby to active.

11. Redundancy and Historical Data

Failover can affect logging in several ways.

Potential problems include:

  • Duplicate records during transition.
  • Missing samples.
  • Gaps in event history.
  • Conflicting timestamps.
  • Incomplete alarm transitions.
  • Interrupted database connections.
  • Loss of buffered data.

The design should define which server or service is responsible for writing records and how duplicate or incomplete records are handled.

Example

Server A fails at 10:00:00. Server B takes over at 10:00:04.

If the acquisition service does not buffer data during the transition, records may be missing for that interval. If both servers write the same data simultaneously, duplicate records may be created.

Possible design controls include:

  • A clearly defined active logging owner.
  • Persistent local buffering where supported.
  • Unique event identifiers.
  • Duplicate detection.
  • Consistent timestamp conventions.
  • Recovery and reconciliation procedures.

The correct solution depends on the data type and the consequences of missing or duplicated records.

12. Redundancy Versus Backup

Redundancy and backup solve different problems.

Feature Redundancy Backup
Primary purpose Maintain service when a component fails Recover data or configuration after loss or corruption
Typical mechanism Standby server, alternate network path, replicated service Backup copies and recovery procedures
Recovery speed May be automatic or near-automatic Often requires a restore or recovery process
Protects against server hardware failure Potentially, if designed for it May allow recovery, but not necessarily immediate continuity
Protects against accidental deletion Not necessarily Yes, if a suitable recoverable copy exists
Protects against ransomware Not necessarily Can, if backups are protected and recoverable
Replaces the other? No No

If an incorrect configuration is replicated to both servers, redundancy may simply ensure that the incorrect configuration remains available.

Backups should be independent enough to protect against the failures they are intended to address. Recovery tests are required to verify that backup files and procedures actually work.

13. Availability, MTBF, MTTR, and Recovery Targets

Redundancy planning often uses reliability and recovery metrics.

Mean Time Between Failures (MTBF)

MTBF is the average operating time between failures for a repairable system or component, under a defined measurement method.

Mean Time To Repair (MTTR)

MTTR commonly represents the average time required to restore a failed item to service, though organizations may define its start and end points differently.

Availability

A common steady-state approximation is:

\[ A=\frac{MTBF}{MTBF+MTTR} \]

where:

  • \(A\) is availability as a fraction.
  • MTBF is mean time between failures.
  • MTTR is mean time to repair or restore service.

For example, if a service has an MTBF of 1,000 hours and an MTTR of 1 hour:

\[ A=\frac{1000}{1000+1}\approx0.9990 \]

That corresponds to approximately 99.90% availability under the assumptions of this simplified model.

Real systems may have planned downtime, common-cause failures, dependencies, and maintenance windows that this simple formula does not capture.

Recovery Time Objective (RTO)

The RTO is the target maximum time within which a service or function should be restored after a disruption.

Recovery Point Objective (RPO)

The RPO defines the acceptable data-loss window, expressed as a period of time.

For example, a system with an RPO of 5 minutes is designed so that the amount of lost data does not exceed the agreed equivalent of that five-minute window, subject to the recovery design and measurement rules.

RTO and RPO are especially important for historical databases and reporting systems. They are not substitutes for safety or real-time control requirements.

15. Redundancy Testing and Commissioning

Redundancy is not complete when the configuration screen shows a green status. It is complete only after the intended failure cases have been tested and the results documented.

A controlled test plan should include:

Server tests

  1. Confirm the active and standby roles.
  2. Verify configuration and data synchronization.
  3. Test a planned active-server failure using an approved procedure.
  4. Measure the interruption and recovery time.
  5. Verify client reconnection.
  6. Confirm PLC data updates and quality indicators.
  7. Verify alarm handling and historical logging.
  8. Test recovery and failback according to the approved procedure.

Network tests

  1. Confirm the intended network topology.
  2. Verify redundant paths and protocol status.
  3. Test a link failure under controlled conditions.
  4. Confirm communication recovery.
  5. Check for loops, duplicate addressing, or unexpected traffic.
  6. Verify communication with all required devices.
  7. Record actual recovery time and any data gaps.

Data integrity tests

  1. Check for duplicate event records.
  2. Check for missing process samples.
  3. Verify timestamp continuity.
  4. Confirm that alarm transitions are recorded correctly.
  5. Verify recovery from any temporary logging or database interruption.

Testing must follow the site's change-control and production-safety procedures. Do not deliberately disconnect live industrial infrastructure without authorization and an approved test plan.

16. Practical Automotive Manufacturing Example

Consider a SCADA system monitoring stations FR1010 through FR1050.

The system uses:

  • A primary SCADA server.
  • A standby SCADA server.
  • A managed industrial Ethernet network.
  • PLC communication drivers.
  • A historical data service.
  • Operator clients.

Normal operation

The primary server acquires PLC data and serves the clients. The standby monitors the primary and maintains the configuration or state required for takeover.

Primary server failure

The redundancy mechanism detects that the primary server is unavailable. The standby takes over, clients reconnect, and data acquisition resumes.

What must be verified

  • Do all required station values update?
  • Are communication and stale-data conditions displayed correctly?
  • Are alarms still generated and recorded?
  • Does historical logging continue?
  • Is there a measurable gap in the data?
  • Can the failed server return without creating a split-brain condition?
  • Does the recovery process require operator or administrator intervention?

Network switch failure

If the architecture includes a properly configured redundant path, communication may recover through the alternative path.

If both paths depend on the same failed switch or power source, redundancy may not provide the expected protection.

This example demonstrates why redundancy must be designed across the entire service path rather than at only one component.

17. Interview Questions and Answers

Q1. What is redundancy in industrial automation?

Providing alternative components, systems, or communication paths so that a single failure does not necessarily interrupt the required function.

Q2. What is failover?

The transfer of a service or active role to an alternative component after a failure or defined availability condition.

Q3. What is failback?

Returning the service to its preferred or original component after recovery, according to the system's failback policy.

Q4. What is the difference between active/standby and active/active?

Active/standby assigns one component the active role while another waits to take over. Active/active allows multiple components to perform active work simultaneously.

Q5. What is a single point of failure?

A component or dependency whose failure interrupts a required function because a suitable alternative is unavailable.

Q6. What is split-brain?

A condition in which multiple nodes incorrectly believe they should both be active, potentially causing conflicting operations or inconsistent data.

Q7. What is the purpose of a heartbeat?

To help a redundancy system monitor the availability or health of another component.

Q8. Does server redundancy guarantee zero data loss?

No. Data loss depends on acquisition, buffering, replication, storage, and recovery design. The system must be tested against defined requirements.

Q9. What is the difference between redundancy and backup?

Redundancy aims to maintain service during particular failures. Backup preserves recoverable copies of data or configuration for restoration after loss or corruption.

Q10. What is network redundancy?

Providing alternative communication paths or network components to reduce the effect of a link or device failure.

Q11. What are RTO and RPO?

RTO is the target time to restore a service. RPO defines the acceptable data-loss window.

Q12. Why must redundancy be tested?

Configuration alone cannot establish actual recovery time, client behavior, data integrity, or correct role switching during failure.

Q13. Can two redundant servers share the same single network switch?

They can, but that switch remains a shared dependency and potential single point of failure for communication through it.

Q14. Why might a redundant SCADA server fail to provide useful monitoring after takeover?

It may have incomplete synchronization, insufficient connection capacity, failed data acquisition, stale tags, client reconnection problems, or configuration differences.

18. Practical Exercises

Use a development environment or an approved test system.

  1. Draw a SCADA architecture with one server and identify its single points of failure.
  2. Redesign it using active/standby servers.
  3. Identify the remaining shared dependencies in the redesigned architecture.
  4. Draw a network with redundant paths and identify how a failed link should be handled.
  5. Explain how a heartbeat can fail even when the monitored server is still running.
  6. Define expected failover behavior for operator clients.
  7. Prepare a test checklist for server failover.
  8. Define an RTO and RPO for a hypothetical historical database, based on stated business requirements.
  9. Explain how duplicate fault events might arise during failover.
  10. Design a method to detect missing samples and duplicate records after recovery.
  11. Distinguish failover from failback and backup restoration.
  12. Document a controlled test that verifies monitoring, alarm handling, and logging after a server transition.

Remember the five central principles:

  1. Redundancy reduces the impact of specified failures.
  2. Failover must be detected, coordinated, and tested.
  3. Shared dependencies can defeat otherwise redundant components.
  4. Redundancy is not a substitute for backups or recovery procedures.
  5. Successful failover means the required service works correctly, not merely that another server becomes active.
