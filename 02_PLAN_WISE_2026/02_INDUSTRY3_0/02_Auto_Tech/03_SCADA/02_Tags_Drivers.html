1. Definition

In SCADA, tags represent process data, while communication drivers provide the connection through which applications access that data from PLCs and other industrial devices.

A tag can represent a machine state, sensor value, production counter, alarm condition, or operator command. A driver communicates with the data source using a supported protocol and makes the data available to the configured application.

For example, a SCADA system monitoring an automotive robotic line might use tags for:

  • Station ready.
  • Robot fault.
  • Clamp position.
  • Cycle count.
  • Actual process pressure.
  • Production cycle start request.

The SCADA application uses those tags to display values, trigger configured alarms, plot trends, and perform authorized operations.

The essential relationship is:

Physical Process
      |
      v
PLC program and data
      |
      v
Communication driver
      |
      v
SCADA data source / tag configuration
      |
      v
SCADA screens, alarms, trends, and logging

The exact path depends on the SCADA product. Some systems use built-in drivers, while others use an external OPC server or another data service.

2. What Is a SCADA Tag?

A tag is a named data item that represents a value used by an application.

A tag usually has a name and data type. Depending on the platform, it may also have a source address, description, engineering units, access permissions, update settings, quality information, and other configuration.

Examples:

Tag name Data type Meaning
Station_Ready Boolean Station is ready
Station_Fault Boolean Station has a fault
Robot_Auto_Mode Boolean Robot automatic mode is active
Clamp_Closed Boolean Clamp-closed feedback
Cycle_Count Integer Number of completed cycles
Pressure_Actual Floating-point Actual pressure
Temperature_Actual Floating-point Actual temperature
Start_Request Boolean Configured request to start a cycle

These are illustrative names, not standard tags provided automatically by SCADA software.

A tag should represent one clearly defined piece of information. Naming a tag M100 tells you its address in a particular context, but naming it Station_Ready communicates its intended meaning more clearly.

In a well-maintained project, the engineering documentation records both the meaningful tag name and its actual source reference.

3. Types of SCADA Tags

Different SCADA products classify tags differently, but the following categories are useful for understanding the concepts.

3.1 External or controller tags

These obtain their values from a PLC, controller, or another external device.

Examples:

  • Station_Ready
  • Robot_Fault
  • Pressure_Actual
  • Cycle_Count

The source might be an Allen-Bradley controller tag, a Mitsubishi PLC device, a Siemens PLC data block, or a supported OPC data item.

3.2 Internal tags

These are maintained within the SCADA application rather than being directly read from a PLC device.

Possible uses include:

  • Storing a temporary operator selection.
  • Managing an application display state.
  • Holding an intermediate calculation.
  • Remembering a navigation selection.

Internal tags are useful for application logic, but they should not be confused with the authoritative state of a physical machine.

3.3 Derived or calculated tags

These are calculated from other values.

For example:

Cycle_Time = Cycle_End_Time - Cycle_Start_Time

Other examples include:

  • Production rate.
  • Percentage utilization.
  • Difference between actual and target pressure.
  • Number of stations currently faulted.
  • Calculated energy consumption, when the required measurements are available.

The calculation may be performed in SCADA, a PLC, a database, or another system. The correct location depends on timing requirements, ownership of the calculation, reliability needs, and the application design.

3.4 System and diagnostic tags

These represent application or communication information rather than ordinary process values.

Examples include:

  • Driver connection status.
  • Communication error state.
  • Data quality.
  • Last successful update time.
  • Application health.

The exact system tags available depend on the SCADA product and driver.

3.5 Command tags

Command tags represent permitted requests from an operator or application.

Examples:

  • Cycle_Start_Request
  • Reset_Request
  • Recipe_Select_Request

Command tags require careful design. The PLC should validate the request, check the required operating conditions, and manage the actual machine sequence.

A command tag is not proof that the requested action occurred.

4. Tag Addressing: Connecting a Tag to PLC Data

A SCADA tag must refer to the correct source data.

The addressing method depends on the controller family and communication interface.

PLC family Example reference General meaning
Allen-Bradley Logix Station_Ready Symbolic controller tag
Mitsubishi M100 Internal relay device
Mitsubishi D100 Data register
Siemens S7 DB10.DBX0.0 Bit reference in a data block
Siemens S7 DB10.DBD4 Double-word location in a data block, subject to the configured data representation
Modbus device Holding register address Register reference defined by the device and driver

These examples use different addressing conventions. They cannot be copied interchangeably between PLC families.

Example: Allen-Bradley Logix

A controller might define a Boolean tag named Station_Ready.

The SCADA configuration identifies the controller and references that tag using the supported communication path.

Controller: PLC_Station_1010
Tag:        Station_Ready
Type:       Boolean
Purpose:    Station ready status

The controller name and tag name must match the actual system configuration.

Example: Mitsubishi PLC

A Mitsubishi PLC might use M100 for a station-ready state.

The SCADA driver must support the selected Mitsubishi PLC family and device addressing, and the connection must point to the correct controller.

Example: Siemens PLC

A Siemens PLC might expose a value through a data block, symbolic tag, or another supported reference, depending on the PLC, driver, and configuration.

For all three examples, the same principle applies: the SCADA tag must resolve to the intended source value, not merely to an address that looks plausible.

5. What Is a Communication Driver?

A communication driver is a software component that implements communication with a supported controller, device, or protocol.

It enables a SCADA application or data service to read process data and, where permitted, write values to the connected device.

A driver may handle:

  • Establishing and maintaining a device connection.
  • Reading configured data items.
  • Writing permitted values.
  • Translating between application data references and protocol requests.
  • Reporting communication errors.
  • Updating data quality or connection status.
  • Managing supported polling or subscription mechanisms.

The exact features depend on the driver, protocol, and SCADA platform.

Typical communication path

SCADA tag
    |
    v
SCADA data service
    |
    v
Communication driver
    |
    v
Industrial network
    |
    v
PLC communication interface
    |
    v
PLC data

In some architectures, an OPC server or another intermediary sits between the SCADA application and the PLC.

Driver versus protocol

These are different concepts.

  • Protocol: Defines how communication messages and data exchange work.
  • Driver: Implements communication for an application or device using a supported protocol.
  • Connection configuration: Defines which device to contact and how to reach it.
  • Tag mapping: Defines which data item the application wants to access.

For example, EtherNet/IP is a communication technology. A compatible driver implements the necessary communication behavior, while the configured connection identifies the intended controller.

6. Direct Drivers Versus OPC

SCADA systems can connect to PLCs through different data-access architectures.

6.1 Direct driver

SCADA Application
        |
        v
Built-in / Configured Driver
        |
        v
       PLC

The SCADA application uses a driver that directly supports the target controller or protocol.

This approach can be straightforward when the SCADA platform provides a suitable driver.

6.2 OPC-based communication

SCADA Application
        |
        v
OPC Client Interface
        |
        v
      OPC Server
        |
        v
PLC Driver / Connection
        |
        v
       PLC

The OPC server exposes data through an OPC interface. The SCADA application accesses that data as an OPC client.

OPC UA is a modern platform-independent standard for industrial data exchange and related services. OPC Classic technologies, including OPC Data Access (DA), are found in many legacy Windows-based systems.

Do not assume OPC UA and OPC DA are interchangeable. They differ in architecture, security mechanisms, interfaces, and configuration.

Why use OPC?

An OPC server can provide a common data interface for multiple compatible applications and controllers. For example, a SCADA application and a separate monitoring application may consume data through a shared OPC server.

However, OPC does not eliminate the need for correct PLC communication, tag mapping, access control, or network configuration.

7. Linking a SCADA Tag to PLC Data

A typical configuration process follows these steps. The names of menus and settings vary by SCADA software.

Step 1: Identify the PLC

Record the controller family, model, IP address or other connection identifier, and relevant communication settings.

Step 2: Configure the driver or data source

Select a compatible driver or OPC connection. Configure the target device and the required connection parameters.

Step 3: Test communication

Use the platform's diagnostic or connection-status tools to determine whether the data source is reachable and communicating.

A successful network connection alone does not prove that the driver can read the intended PLC data.

Step 4: Create or configure the tag

Define the tag's name, source reference, data type, and other settings required by the platform.

For example:

Property Example
Tag name Station_Ready
Data source PLC_Station_1010
PLC reference Station_Ready
Data type Boolean
Access Read-only
Description Station-ready feedback

All values are illustrative.

Step 5: Verify the source value

Compare the value shown by the SCADA data service or tag monitor with the actual PLC value using an appropriate engineering tool.

If the PLC value is TRUE but SCADA reports FALSE, check the reference, data type, connection, and value quality before changing the screen.

Step 6: Bind the tag to an object

Assign the configured tag to a screen object, alarm, trend, or other function that requires the value.

Step 7: Test normal and abnormal conditions

Verify that the displayed value changes as expected and that communication failures are identified appropriately.

For write-enabled tags, test only in an approved environment and verify the PLC-side validation and recovery behavior.

8. Data Types, Scaling, and Engineering Units

Correct tag mapping involves more than entering an address.

The SCADA configuration must interpret the source data correctly.

Data type Common use Important consideration
Boolean ON/OFF status Confirm polarity and intended meaning
Integer Counts and whole-number values Check signedness and range
Floating-point Analog process values Check numeric representation and precision
String Text or identifiers Check length, encoding, and source format
Array or structure Groups of related values Check driver and platform support

Not every SCADA driver supports every PLC data type or structure in the same way.

Scaling example

Suppose a PLC stores 235 to represent a pressure of 23.5 bar, using a scale factor of 10.

The intended conversion is:

Displayed pressure = PLC raw value / 10

PLC raw value = 235
Displayed value = 23.5 bar

If SCADA displays 235 bar, the communication may be working perfectly while the displayed engineering value is wrong.

Check the source data definition, scaling factor, engineering units, and display format.

Word order and multi-register values

Some devices represent a larger value across multiple registers. The driver and application must interpret the registers using the device's documented data representation.

Incorrect register order, word order, or data type can produce implausible numbers even when communication succeeds.

Do not change byte or word ordering based on guesswork. Verify the device documentation and compare against a known test value.

9. Read-Only, Read/Write, and Command Tags

Tags should have access permissions appropriate to their purpose.

Read-only tags

Used to monitor the machine without changing the source value.

Examples:

  • Station ready.
  • Robot fault.
  • Actual pressure.
  • Cycle count.
  • Clamp-closed feedback.

Read/write tags

Used when an application is authorized to modify a process value.

Examples:

  • An approved setpoint.
  • A recipe parameter.
  • A selected operating parameter.

These tags require appropriate permissions and validation.

Command tags

Used to request an action, such as cycle start or fault reset.

A preferred control path is:

Operator action
      |
      v
SCADA command request
      |
      v
PLC validates request
      |
      v
PLC controls machine sequence
      |
      v
Feedback confirms result
      |
      v
SCADA displays actual state

For commands, consider whether the application needs a momentary request, a maintained state, a request/acknowledgement handshake, or a timeout and error response. The correct design depends on the machine and PLC program.

Never assume that making a tag writable is sufficient to make the operation safe. The PLC must retain responsibility for validating commands and enforcing the required control and safety boundaries.

10. Polling, Subscriptions, and Update Rates

A SCADA driver needs a strategy for acquiring current values from the PLC.

Polling

The driver requests data at a configured interval.

For example, a driver might poll a group of tags every 500 ms, depending on the application and configuration.

Subscription or change-based updates

Where supported, the client or data service subscribes to updates. The source or server can report changes or provide updates according to configured conditions.

This can reduce unnecessary requests, but it does not guarantee that every change is delivered instantaneously. Update rates, deadbands, communication limits, and platform behavior matter.

Important timing terms

Term Meaning
PLC scan time Time taken by the PLC to execute a program cycle or task
Driver polling interval Configured interval between data requests where polling is used
Subscription update rate Configured or negotiated rate for receiving updates
HMI refresh interval How frequently a screen object refreshes
Logging interval How frequently data is recorded when interval-based logging is used
Network latency Time taken for data to travel across the network
Data age Time elapsed since the source value was acquired or updated

These are separate measurements.

Suppose a driver acquires a value every 1 second while the screen refreshes every 250 ms. The screen may redraw four times between acquisitions without receiving any new PLC value.

Choosing update rates

Consider the purpose of the tag.

  • Machine status may not require extremely frequent updates.
  • An operator-facing analog value may need a moderate refresh rate.
  • A historical energy trend may need a much slower acquisition rate.
  • Time-critical motion and safety control belong in the appropriate controller architecture, not in SCADA polling.

Excessive polling can increase communication load, server resource usage, and network traffic without providing useful additional information.

11. Data Quality and Communication Status

A robust SCADA tag should not be treated as just a number or Boolean value.

Where supported, its quality or communication status helps the application determine whether the value can be trusted.

Possible conditions include:

  • Valid and current.
  • Uncertain.
  • Bad or unavailable.
  • Stale because the source has not updated recently.
  • Invalid because the reference or data source cannot be resolved.

The exact quality states depend on the SCADA platform and protocol.

Example: stale station-ready status

Suppose the PLC reports Station_Ready = TRUE, then communication fails.

If SCADA keeps showing TRUE without any indication of communication loss, the operator may incorrectly believe the station is still ready.

A better display distinguishes the reported process state from the validity of the data:

Station ready:       TRUE
Communication:      FAILED
Data freshness:     STALE

This is an illustrative representation. The application should use the quality and diagnostic mechanisms supported by its platform.

A last-known value may be useful for diagnosis, but it should not be presented as a confirmed current state when the source is unavailable.

One tag is invalid Incorrect reference or unsupported data item Check the tag against the controller project
Boolean state is reversed Incorrect mapping or interpretation Verify source value and object configuration
Numeric value is implausible Data type, scaling, or word-order issue Compare with a known source value

Reads work but writes fail Access restriction, wrong write target, or PLC-side logic Verify permissions and PLC conditions

13. Systematic Troubleshooting Procedure

When a tag is wrong, investigate from the data source toward the screen.

Step 1: Verify the PLC source

Use the appropriate PLC engineering tool to confirm the actual value and the tag or device reference.

Step 2: Verify controller communication

Confirm that the driver or data service can communicate with the intended PLC.

Step 3: Verify the driver configuration

Check the target controller, communication method, connection settings, and available diagnostic messages.

Step 4: Verify the tag reference

Confirm that the configured item points to the intended source, not a similarly named tag or a device in another PLC.

Step 5: Verify the data type and value interpretation

Check Boolean polarity, integer format, signedness, scaling, units, and register representation as applicable.

Step 6: Verify data quality and freshness

Determine whether the source is updating and whether the application recognizes communication failures.

Step 7: Verify the screen object

If the underlying tag is correct, inspect the object binding, display states, formatting, scaling, and refresh behavior.

Step 8: Verify writes separately

For a command or writable parameter, confirm the target, access permissions, PLC-side conditions, and expected feedback. Perform write tests only under approved conditions.

This process separates source-data faults, communication faults, mapping faults, and display faults.

14. Practical Example: SCADA Tags for an Automotive Robotic Station

Consider a SCADA application monitoring an automotive robotic station. The station PLC provides status, process values, and permitted command interfaces.

Example tag register

SCADA tag Source reference Type Access Purpose
FR1010_Station_Ready Verified PLC status tag Boolean Read-only Station readiness
FR1010_Station_Fault Verified PLC fault tag Boolean Read-only Station fault
FR1010_Robot_Ready Verified PLC status tag Boolean Read-only Robot readiness
FR1010_Clamp_Closed Verified feedback tag Boolean Read-only Clamp position feedback
FR1010_Cycle_Count Verified PLC counter tag Integer Read-only Production cycle count
FR1010_Pressure_Actual Verified process-value tag Numeric Read-only Actual pressure
FR1010_Start_Request Approved PLC command interface Boolean Controlled write Cycle-start request

The names are illustrative. The actual PLC references and types must be taken from the approved controller project.

How the tags are used

  • The overview screen uses the ready and fault tags.
  • The diagnostic screen uses robot and clamp feedback.
  • The production screen displays the cycle count.
  • The process screen displays actual pressure.
  • The authorized operator interface sends the start request through the approved command mechanism.
  • The PLC validates the request and controls the machine sequence.

Example fault

The SCADA screen reports that the clamp is not closed, while the close command is active.

The engineer should compare the PLC's command and feedback values, verify communication quality, and inspect the PLC sequence and physical equipment.

If the PLC reports the correct values but SCADA displays the wrong state, investigate the driver, tag mapping, or screen object.

This is the practical value of separating tags, drivers, and visualization: each layer can be tested independently.

15. Interview Questions and Answers

Q1. What is a SCADA tag?

A named data item representing a process value, state, command, or other information used by the SCADA application.

Q2. What is a communication driver?

Software that implements communication with a supported device or protocol so an application can exchange data.

Q3. What is the difference between a tag and an address?

A tag is the application's data reference or named item. An address identifies the underlying source location where applicable. Some systems use symbolic controller tags rather than traditional fixed addresses.

Q4. What is the difference between a driver and a protocol?

A protocol defines communication rules. A driver implements the communication behavior required by an application or device using a supported protocol.

Q5. What is OPC?

OPC is a family of industrial interoperability technologies that enables compatible applications to exchange data through standardized interfaces.

Q6. Why can a tag be invalid even when the PLC is online?

The source reference may be incorrect, the driver may not support the item, access may be restricted, or the application may be using the wrong data source or data type.

Q7. Why might a numerical value be incorrect despite successful communication?

Possible causes include scaling errors, incorrect data types, signedness, units, or multi-register representation.

Q8. What is the difference between polling and HMI refresh?

Polling acquires data from the source. HMI refresh redraws or updates the displayed object. A screen can refresh several times while displaying the same acquired value.

Q9. What is stale data?

Data that has not been updated recently enough to be trusted as a current representation of the source.

Q10. Why should command tags be controlled carefully?

They can affect machine operation. Access restrictions, PLC-side validation, interlocks, and suitable feedback are required according to the application's design.

Q11. How do you troubleshoot a tag that reads correctly in the PLC but incorrectly in SCADA?

Check the driver and data source, tag reference, data type, scaling, data quality, and screen-object configuration in sequence.

Q12. What is the difference between a direct driver and an OPC server?

A direct driver lets the SCADA application communicate through its supported driver. An OPC-based architecture uses an OPC server to expose data to compatible clients.

16. Practical Exercises

Use a development environment or approved test system.

  1. Create a list of ten SCADA tags for a hypothetical robotic station.
  2. Classify each tag as external, internal, derived, diagnostic, or command-related.
  3. Record the source PLC, reference, data type, access mode, description, and units.
  4. Trace one PLC tag from the controller to a SCADA screen object.
  5. Compare the PLC value with the SCADA tag-monitor value.
  6. Simulate an invalid tag reference and identify the diagnostic indication.
  7. Test a numeric scaling calculation using a known raw value.
  8. Compare driver polling interval with screen refresh interval.
  9. Determine how the application indicates stale data or communication failure.
  10. Draw a direct-driver architecture and an OPC-based architecture.
  11. Diagnose a case where the SCADA tag is correct but the screen object is wrong.
  12. Write a troubleshooting procedure for a tag that reads successfully but rejects writes.

17. Final Mental Model

PLC Data
   |
   v
Communication Driver
   |
   v
Data Source / OPC Interface
   |
   v
SCADA Tag Mapping
   |
   v
Data Type + Scaling + Quality
   |
   v
Screens / Alarms / Trends / Logging

For every SCADA value, be able to answer five questions:

  1. Where does the value originate?
  2. Which driver or data interface acquires it?
  3. Which tag reference identifies it?
  4. Is the value correctly interpreted and current?
  5. Which screen, alarm, trend, or database uses it?

If these five points are understood, many SCADA communication and display faults become straightforward to isolate.
