1. Definition

A SCADA screen is a graphical interface used to monitor an industrial process, understand machine conditions, inspect process values, and perform authorized operator actions.

A SCADA screen connects process data to a visual representation that operators and maintenance engineers can understand.

For example, in an automotive robotic line, a screen might display:

  • Production line status.
  • Station ready or faulted.
  • Robot operating state.
  • Clamp and fixture feedback.
  • Cycle count and cycle time.
  • Process values such as pressure.
  • Communication health.
  • Navigation to detailed diagnostic pages.

The purpose is not to make the plant look like a video game. It is to communicate the machine's actual condition clearly enough that people can make correct decisions under production pressure.

2. Purpose of SCADA Screens

SCADA screens serve several operational purposes.

Monitoring: Display the current state of machines, PLCs, robots, sensors, and process values.

Fault identification: Help operators identify which station or equipment has stopped or entered an abnormal condition.

Diagnosis: Provide detailed status, feedback, interlock information, and relevant fault details.

Process supervision: Display actual values, setpoints, operating modes, and process trends.

Operator interaction: Provide authorized controls for requests such as reset, start, stop, and approved parameter changes.

Production visibility: Display counters, cycle status, throughput, and other production information.

Maintenance support: Help maintenance engineers identify whether a problem originates from a sensor, actuator, PLC sequence, robot, communication link, or another subsystem.

A screen should help answer three questions quickly:

  1. What is happening?
  2. Where is it happening?
  3. What information is needed to understand the problem?

3. Overview Screens Versus Detail Screens

The most important design principle is to separate the information needed for line-wide supervision from the information needed for detailed troubleshooting.

3.1 Overview screen

An overview screen provides a high-level picture of a complete line, area, or process.

It typically displays:

  • Overall line status.
  • Major stations and equipment.
  • Station-by-station ready, running, stopped, or faulted states.
  • Production counts and cycle information.
  • Major active faults.
  • Communication or controller status.
  • Navigation to individual station screens.

Example: a robotic body-in-white line overview showing stations FR1010, FR1030, FR1040, and FR1050.

The operator should be able to identify which station needs attention without opening every station individually.

3.2 Detail screen

A detail screen focuses on one station, machine, or subsystem.

It can display:

  • Operating mode.
  • Sequence step.
  • PLC and robot states.
  • Sensor feedback.
  • Actuator commands and feedback.
  • Interlocks and permissives.
  • Actual process values.
  • Fault codes and diagnostic information.
  • Approved operator controls.

For example, the FR1010 detail screen might show the robot's state, fixture-clamp feedback, station sequence, and the reason the station is not ready.

3.3 Comparison

Feature Overview screen Detail screen
Primary purpose Line-wide supervision Station-level diagnosis
Scope Multiple stations or systems One station or subsystem
Information density Low to moderate Moderate to high
Equipment representation Simplified More detailed
Fault information Summary and location Detailed status and cause
Controls Usually limited Authorized station-specific controls
Typical user Operator or production supervisor Operator or maintenance engineer
Navigation Links to details Links back to overview and related diagnostics

A detail screen should add diagnostic value rather than merely enlarging the overview diagram.

4. Common SCADA Screen Types

4.1 Line overview

This is the main entry point for supervising a production line.

It may contain:

  • Line name and production status.
  • Station status tiles.
  • Active fault summary.
  • Current production count.
  • Target versus actual production.
  • Navigation buttons.
  • Data-source or communication health.

Example layout:

+----------------------------------------------------------+
| ROBOTIC LINE OVERVIEW              LINE STATUS: STOPPED  |
+----------------------------------------------------------+
| FR1010       FR1030       FR1040       FR1050             |
| RUNNING      READY        FAULTED      WAITING            |
|              READY        ROBOT FAULT                    |
+----------------------------------------------------------+
| PRODUCTION COUNT: 425       TARGET: 500                  |
| ACTIVE FAULTS: 1            COMMUNICATION: HEALTHY       |
+----------------------------------------------------------+
| [FR1010]     [FR1030]       [FR1040]      [FR1050]        |
+----------------------------------------------------------+

This is a conceptual layout, not a representation of a specific SCADA product.

The overview should communicate the affected station and the reason for concern without requiring the operator to interpret a mass of tiny symbols.

4.2 Station detail

A station detail page shows the operating condition of a single station.

+----------------------------------------------------------+
| FR1040 STATION DETAIL                                    |
+----------------------------------------------------------+
| MODE: AUTO            STATE: FAULTED                     |
| SEQUENCE STEP: WAITING FOR CLAMP FEEDBACK                |
+----------------------------------------------------------+
| ROBOT                 FIXTURE                             |
| Ready: TRUE           Clamp Command: TRUE                |
| Fault: FALSE          Clamp Feedback: FALSE             |
+----------------------------------------------------------+
| INTERLOCKS / PERMISSIVES                                 |
| Station Ready: FALSE                                    |
| Clamp Closed: FALSE                                     |
+----------------------------------------------------------+
| ACTIVE FAULT: Clamp closed feedback not received         |
+----------------------------------------------------------+
| [OVERVIEW]       [DIAGNOSTICS]       [ALARMS]             |
+----------------------------------------------------------+

The exact reason for a stopped station must come from the PLC sequence, alarm logic, and equipment design. The displayed explanation should not invent a diagnosis merely because two signals appear inconsistent.

4.3 Equipment detail

An equipment page focuses on an individual component or subsystem, such as:

  • Robot.
  • Servo axis.
  • Welding controller.
  • Hydraulic power pack.
  • Pneumatic fixture.
  • Conveyor.
  • CNC machine.
  • VFD-controlled motor.

Useful information includes device state, actual and commanded values, fault codes, operating mode, and relevant feedback.

4.4 Diagnostic screen

A diagnostic screen is designed to help locate the cause of a fault.

It may include:

  • Sensor and actuator feedback.
  • Sequence step.
  • Permissive status.
  • Interlock status.
  • Device communication status.
  • PLC fault or diagnostic information.
  • Robot or drive fault codes.
  • Relevant timestamps.

Diagnostic screens should distinguish between a failed condition and a condition that is simply not currently satisfied.

For example, Clamp_Closed = FALSE does not necessarily mean the clamp is defective. It might be open intentionally, the sequence might not have requested closure, or the sensor or communication path might have failed.

4.5 Production screen

A production screen focuses on manufacturing performance.

It may display:

  • Good parts.
  • Rejected parts.
  • Target versus actual production.
  • Cycle time.
  • Downtime.
  • Throughput.
  • Production shift or order information.

The source and calculation method for each metric should be documented. A count from a PLC, a count derived in SCADA, and a count from a manufacturing execution system may differ if their definitions and reset rules are different.

4.6 Trend screen

A trend screen displays values over time, such as:

  • Pressure.
  • Temperature.
  • Cycle time.
  • Motor current.
  • Energy consumption.
  • Production rate.

Trends help reveal changes and patterns that cannot be understood from a single current value.

Alarm and trend functionality is covered in the next study topic, 04_Alarms_Trends.

5. Screen Navigation and Hierarchy

A well-designed SCADA project gives users a predictable path from the line overview to the specific equipment they need to inspect.

A common hierarchy is:

Line Overview
      |
      +---- Station Detail
      |          |
      |          +---- Equipment Detail
      |          |
      |          +---- Station Diagnostics
      |
      +---- Production Summary
      |
      +---- Alarm Summary
      |
      +---- Trends
      |
      +---- System / Communication Status

For example:

  1. The operator sees FR1040 faulted on the overview.
  2. The operator opens the FR1040 detail page.
  3. The page identifies that the station is waiting for clamp feedback.
  4. The operator opens diagnostics to inspect the relevant command, feedback, and permissives.
  5. After the issue is corrected and the PLC sequence permits recovery, the operator verifies the station's actual state.

Navigation should preserve context. If an operator opens a station detail page, the station identity should remain visible.

Common navigation controls

  • Overview or Home.
  • Previous page or Back.
  • Station selection.
  • Equipment detail.
  • Diagnostics.
  • Alarm summary.
  • Trends.
  • Production summary.
  • User or system status.

Use consistent placement and naming. Operators should not have to rediscover the location of the Back button every time they encounter a different station.

6. SCADA Screen Objects and Their Functions

Screens are constructed from graphical objects connected to data tags or application logic.

Object Function Example
Numeric display Displays a numeric value Actual pressure
Status indicator Shows a discrete state Robot ready
Text label Identifies equipment or value FR1040
Equipment graphic Represents a device or process Conveyor or clamp
Push button Requests an authorized action Fault reset request
Navigation button Opens another page Station diagnostics
Bar or gauge Shows a numeric range Tank level
Trend chart Shows values over time Pressure history
Alarm summary Displays alarm conditions Active station faults
Data table Presents multiple values Production counts
Communication indicator Shows connection health PLC connection status

The object should communicate the value's meaning, not merely decorate the screen.

For example, a numeric display of FALSE is technically valid for a Boolean tag but usually less useful than a clearly labelled status such as Clamp Closed: NO.

7. Dynamic Objects and Tag Binding

A dynamic object changes according to a tag or configured expression.

For example:

PLC Tag: FR1040_Station_Fault

If value = FALSE:
    Display station as not faulted

If value = TRUE:
    Display station as faulted

The actual visual treatment depends on the project's standards and the SCADA platform.

Other dynamic behaviors include:

  • Showing an actual pressure value.
  • Changing a status label when a robot enters automatic mode.
  • Enabling or disabling an authorized control based on conditions.
  • Displaying a message when a station is waiting for a permissive.
  • Showing a communication warning when data quality becomes bad.

Correct binding procedure

  1. Identify the required PLC or SCADA tag.
  2. Confirm its meaning and data type.
  3. Bind the object to the correct tag.
  4. Configure display formatting and state behavior.
  5. Test the object against known source values.
  6. Test what the screen displays when communication is lost.

A visually correct object can still be wrong if it is bound to the wrong tag. Screens must be verified against the actual source data.

8. Screen Design Principles

8.1 Design for the task

A line overview should prioritize line status and fault location. A diagnostic page should prioritize information needed to identify the cause.

Do not place every available PLC tag on the overview. That produces a data dump with a background image.

8.2 Use a consistent visual hierarchy

Use larger or more prominent elements for information that deserves immediate attention. Keep supporting details secondary.

A typical hierarchy is:

  1. Overall line or station state.
  2. Active fault or abnormal condition.
  3. Equipment status.
  4. Key process values.
  5. Secondary diagnostics and historical information.

8.3 Use color consistently

Define a documented color convention and apply it throughout the project.

An illustrative convention might be:

Visual state Example interpretation
Green Running or normal, when defined by the project
Red Fault or abnormal condition requiring attention
Yellow or amber Warning or attention required
Gray Inactive or stopped
Blue Information or selected state, if defined by the project

These meanings are not universal standards. The project must define them clearly and account for the SCADA product, site conventions, and applicable human-machine-interface standards.

Never rely on color alone. Pair color with text, symbols, or another clear indication so that the state remains understandable to users with color-vision deficiencies and in difficult viewing conditions.

A stopped station should not automatically be displayed as faulty. A station can be stopped normally during a changeover or production break.

8.4 Use meaningful labels and units

Prefer:

  • Pressure Actual: 5.8 bar
  • Cycle Count: 425
  • Robot State: Automatic
  • Clamp Closed: No

Avoid unexplained labels such as PV1, M100, or D100 on operator-facing screens unless the address is specifically relevant to a technical diagnostic page.

8.5 Avoid unnecessary animation

Animation should communicate a meaningful process state. Excessive blinking, movement, and decorative effects make important changes harder to notice.

Use animation only when it adds operational value and is consistent with the project's design standards.

8.6 Keep critical information visible

Operators should not have to scroll through several screens to discover a significant fault or the affected station.

Place key information where it can be found quickly, and use navigation for deeper detail.

9. Screen Controls and Machine Safety

A screen control sends a request to the underlying control system. It should not be treated as a replacement for PLC logic.

For example, a Cycle Start button may write a command request or invoke a supported command mechanism.

The PLC must determine whether the request is valid for the current machine state.

Relevant conditions may include:

  • Correct operating mode.
  • No blocking fault.
  • Required guards and safety conditions satisfied.
  • Necessary permissives present.
  • Equipment available.
  • Sequence state permits the action.

The specific safety functions must remain in the appropriate safety-rated architecture. An ordinary SCADA screen, standard PLC tag, or HMI button is not a substitute for a safety-rated function.

Command versus feedback

Keep these signals distinct.

Signal Meaning
Clamp_Close_Request Closure has been requested
Clamp_Closed_Feedback The PLC reports that the closed condition is satisfied
Cycle_Start_Request A cycle start has been requested
Cycle_Running The PLC reports that the cycle is running
Reset_Request A reset has been requested
Fault_Active The fault condition is reported as active

A command indicates intent. Feedback indicates a reported condition.

A screen must not show Clamp Closed merely because the close command is ON. That would be equivalent to declaring a repair complete because someone picked up a screwdriver.

Reset and acknowledgement

Alarm acknowledgement, fault reset, and fault correction are separate concepts.

  • Acknowledgement: An operator has recognized an alarm.
  • Fault reset: A request is made to clear a resettable fault or restore a permitted state.
  • Fault correction: The underlying condition is resolved.

The SCADA project should not imply that acknowledging an alarm fixes the machine.

10. Screen Design and Data Quality

Screen information is only as reliable as the data feeding it.

Consider three situations:

Situation A: Normal data

The PLC reports the station ready, the communication is healthy, and the tag is current. The screen may display the station as ready.

Situation B: Actual fault

The PLC reports a fault and the data is current. The screen should identify the station as faulted and provide the available diagnostic information.

Situation C: Communication failure

The SCADA application can no longer verify the station state. It should indicate communication failure or stale data rather than presenting the last-known ready state as definitely current.

This distinction is especially important in a line overview. A station that is genuinely ready and a station whose status cannot be read are not equivalent.

11. Performance and Screen Refresh

Screen performance depends on more than the number of graphical objects.

Factors include:

  • Number of displayed tags.
  • Driver acquisition rate.
  • PLC and network load.
  • Screen refresh behavior.
  • Complexity of expressions and scripts.
  • Number of simultaneously active clients.
  • Historical queries and database activity.
  • Rendering capability of the operator workstation.

Practical example

Suppose the driver updates station status every 500 ms, while the screen refreshes every 200 ms.

The screen may redraw several times between new data acquisitions. Increasing screen refresh frequency does not necessarily make the PLC data arrive faster.

For good performance:

  • Keep overview pages focused.
  • Avoid unnecessarily rapid polling.
  • Group tags according to operational needs.
  • Use efficient graphics and expressions.
  • Avoid repeatedly retrieving large historical datasets for a simple current-status display.
  • Test performance on the intended operator workstation.

12. Common SCADA Screen Faults

Symptom Possible cause Diagnostic approach
Wrong station status Incorrect tag binding or source logic Compare the object with the tag monitor and PLC value
Status never changes Stale data, failed communication, or wrong tag Verify source value, quality, and driver status
Station looks faulted when stopped normally Incorrect visual-state mapping Review state definitions and PLC conditions
Numeric value has the wrong units Incorrect scaling or display formatting Compare raw value and engineering conversion
Button does nothing Incorrect event binding, access restrictions, or PLC rejection Check button configuration, command status, and PLC diagnostics
Button appears to work but machine does not move Request rejected or feedback not achieved Inspect PLC conditions and actual feedback
Overview and detail disagree Different bindings, different refresh behavior, or stale data Compare the underlying tags and data quality
Screen loads slowly Excessive objects, complex expressions, slow queries, or resource limits Profile the page and its data dependencies
Communication failure looks like a normal stop Missing or unclear quality indication Separate process state from communication state
Navigation opens the wrong station Incorrect navigation target or parameter Verify page routing and station identification

13. Recommended Screen Development Workflow

Developing screens systematically reduces rework and commissioning errors.

Step 1: Define the user and purpose

Identify who uses the screen and what decision or action it supports.

Step 2: Define the information requirements

List the required station states, process values, alarms, production metrics, and diagnostic information.

Step 3: Confirm tag availability

Verify the source tags, data types, meanings, units, and data quality behavior.

Step 4: Create a screen hierarchy

Define the overview, station detail, equipment detail, diagnostics, and supporting pages.

Step 5: Establish a visual standard

Define layout, navigation, labels, colors, units, status indications, and control behavior.

Step 6: Build and bind the objects

Create the graphics and connect each dynamic object to its intended data source.

Step 7: Test normal conditions

Verify that values and visual states match the source data.

Step 8: Test abnormal conditions

Test faults, missing feedback, unavailable devices, stale data, and communication failure in a safe test environment.

Step 9: Test controls

Verify authorization, PLC-side validation, command acknowledgement, timeouts, and feedback.

Step 10: Commission and maintain

Document the screen behavior, back up the project, verify version control, and update the documentation whenever PLC tags or screen logic change.

14. FAT and SAT Checks for SCADA Screens

Screen verification should be part of Factory Acceptance Testing (FAT) and Site Acceptance Testing (SAT), where applicable.

Test Expected result
Station ready changes Correct station state updates
Station fault becomes active Fault is indicated correctly
PLC communication is interrupted in a test setup Data unavailability is clearly indicated
Numeric source value changes Correct value and units appear
Operator opens station details Correct station page opens
Navigation returns to overview Correct overview appears
Unauthorized user attempts a restricted command Command is denied as designed
Authorized command is rejected by PLC conditions Rejection or resulting status is communicated clearly
Command succeeds Actual machine state is confirmed by feedback
Displayed tag is invalid The application does not misleadingly present it as verified current data

FAT verifies the configured behavior before installation or formal site acceptance. SAT verifies behavior in the installed environment. The exact scope depends on the project's acceptance plan.

15. Interview Questions and Answers

Q1. What is a SCADA screen?

A graphical interface that presents process information and provides authorized operator interaction with an industrial control system.

Q2. What is the difference between an overview and a detail screen?

An overview summarizes multiple stations or systems. A detail screen provides deeper status and diagnostic information for a specific station or subsystem.

Q3. What is a dynamic screen object?

A graphical object whose displayed value, appearance, or behavior depends on a tag or configured expression.

Q4. What is tag binding?

Connecting a screen object or function to a data tag so that it can display a value or use that value to determine behavior.

Q5. Why should command and feedback signals be separate?

A command indicates a requested action. Feedback indicates the reported result or equipment condition. They can differ when an action is rejected, delayed, or unsuccessful.

Q6. Why is communication status important on an overview screen?

Because a missing or stale value must not be mistaken for a verified current machine state.

Q7. Why should a stopped station not always be shown as faulted?

A station may be stopped normally, waiting for production, in changeover, or in another non-fault state.

Q8. What makes a good diagnostic screen?

It presents relevant device states, commands, feedback, interlocks, permissives, sequence information, and diagnostic details in a way that helps isolate the cause.

Q9. Why might an HMI button not operate a machine?

The button may be incorrectly configured, the user may lack permission, the PLC may reject the request, required conditions may be missing, or the command interface may be incorrect.

Q10. What is the difference between alarm acknowledgement and fault reset?

Acknowledgement indicates that an alarm has been recognized. Reset requests a defined recovery action. Neither automatically guarantees that the underlying fault has been corrected.

Q11. How do you test a SCADA screen?

Compare screen objects with verified source values, test normal and abnormal states, verify navigation and access controls, test communication failure behavior, and confirm that commands and feedback behave as designed.

Q12. Why is consistent navigation important?

It reduces the time and effort required to find equipment information, particularly during production interruptions and troubleshooting.

16. Practical Exercises

Use a development project or an approved simulation environment.

  1. Design an overview for four hypothetical robotic stations.
  2. Create a station-detail layout for one station.
  3. Select ten tags needed for the overview and ten additional tags for the detail page.
  4. Define a consistent state convention for running, stopped, faulted, and communication-unavailable conditions.
  5. Bind a Boolean tag to a status object and verify its behavior.
  6. Display a numeric process value with the correct engineering units.
  7. Design a diagnostic area that separates command, feedback, interlock, and permissive states.
  8. Draw the navigation hierarchy from the line overview to equipment diagnostics.
  9. Test what the screen displays when a data source becomes unavailable.
  10. Document the expected behavior of a Cycle Start request and its feedback.
  11. Prepare a FAT checklist for the overview and detail screens.
  12. Diagnose a hypothetical case where the PLC tag is correct but the screen displays the wrong state.

A useful SCADA screen connects five things:

  • Purpose: What decision must the user make?
  • Data: Which PLC or SCADA tags provide the information?
  • Presentation: How is the information communicated clearly?
  • Interaction: Which authorized requests can the user make?
  • Verification: How does the application distinguish actual machine state from stale, invalid, or unconfirmed data?

When these five elements are designed correctly, screens become practical tools for supervision and troubleshooting rather than decorative pictures of a factory.
