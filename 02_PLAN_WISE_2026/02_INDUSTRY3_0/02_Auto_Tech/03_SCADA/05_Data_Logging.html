1. Definition

SCADA data logging is the process of collecting, timestamping, and storing industrial data so it can be reviewed, analyzed, reported, and used for troubleshooting after the original event has passed.

A SCADA screen shows what is happening now. Data logging preserves information about what happened earlier.

In an automotive manufacturing line, useful logged data may include:

  • Production counts and completed cycles.
  • Machine cycle times.
  • Station downtime and fault occurrences.
  • PLC, robot, CNC, and drive status.
  • Pressure, temperature, current, and other process values.
  • Quality measurements and rejection results.
  • Operator actions and approved parameter changes.
  • Communication failures and equipment diagnostic events.
  • Energy consumption and equipment utilization.

For example, if a robotic station repeatedly stops during a fixture-clamping operation, logged data can help establish when the stoppages occurred, how long they lasted, whether pressure dropped, and whether the fault recurred after maintenance.

Without reliable historical records, troubleshooting becomes a reconstruction exercise based on memory, which is a fairly unreliable industrial data-storage technology.

2. Why Data Logging Is Required

Data logging serves several purposes.

2.1 Production monitoring

Records production counts, cycle times, throughput, and rejected parts.

2.2 Fault investigation

Preserves relevant values and events around a breakdown.

2.3 Maintenance improvement

Helps identify frequently failing devices, recurring stoppages, and deterioration over time.

2.4 Quality traceability

Connects production results with the relevant process measurements, timestamps, station, or product identifier where required.

2.5 Performance analysis

Supports analysis of downtime, availability, cycle-time variation, and bottlenecks.

2.6 Energy monitoring

Stores energy measurements for comparison by shift, machine, production quantity, or operating condition.

2.7 Audit and reporting

Provides records for operational reviews, internal audits, quality investigations, and other applicable requirements.

The required records and retention periods depend on the organization's process, quality system, legal obligations, and data-governance rules.

3. What Data Should Be Logged?

Not every PLC tag needs to be stored at the same frequency. First identify what each record is intended to support.

Data category Examples Typical logging method
Production Good count, rejected count, completed cycles Event-based or periodic
Machine state Running, stopped, idle, faulted State-change events
Fault information Fault code, station, activation time Event-based
Process values Pressure, temperature, current Periodic or change-based
Cycle information Start time, end time, duration Cycle event records
Quality results Measurement, pass/fail, product identifier Per part or inspection
Operator actions Recipe changes, authorized commands Audit/event records
Communication health Connection loss and restoration Event-based
Energy Power, energy counter, consumption Periodic or meter events
Maintenance Repair start/end, component replacement Maintenance-system records or integrated events

The logging method should match the data's purpose.

For example, a production counter may need to be recorded after each completed cycle, while a slowly changing temperature might be recorded every few seconds or minutes.

4. Types of Data Logging

4.1 Periodic logging

Data is recorded at a configured interval.

Example:

10:00:00  Pressure = 5.8 bar
10:00:05  Pressure = 5.7 bar
10:00:10  Pressure = 5.6 bar
10:00:15  Pressure = 5.8 bar

Useful for:

  • Process monitoring.
  • Historical trends.
  • Energy and utility monitoring.
  • Slowly changing values.

The interval must be short enough to capture the behavior of interest. A five-second interval cannot reliably preserve a transient that lasts only 100 milliseconds.

4.2 Event-based logging

A record is created when a defined event occurs.

Examples:

  • Station enters the running state.
  • Robot fault activates.
  • Cycle completes.
  • Operator changes a setpoint.
  • PLC communication is lost.

Event-based logging is useful when the occurrence and timing of a change matter more than continuously recording the same state.

4.3 Change-based logging

A value is recorded when it changes sufficiently according to the configured acquisition rule.

For example, pressure might be logged when it changes by more than a defined amount.

This can reduce unnecessary records, but the deadband must be selected carefully. A deadband that is too large can hide meaningful process changes.

4.4 Transaction or cycle-based logging

A record is created for each production cycle, part, batch, or inspection.

Example fields:

  • Part or cycle identifier.
  • Station identifier.
  • Cycle start timestamp.
  • Cycle completion timestamp.
  • Cycle duration.
  • Process result.
  • Quality result.
  • Fault or rejection reason, where applicable.

This method is especially useful for automotive production traceability and cycle-time analysis.

4.5 Audit logging

Records important user or configuration actions.

Examples:

  • User logged in or out.
  • Recipe or setpoint changed.
  • A command was requested.
  • A configuration was modified.
  • A maintenance action was recorded.

Audit records may require stricter access control, retention, and integrity protection than ordinary operational data.

5. The Data Logging Architecture

A typical architecture separates data acquisition, processing, storage, and reporting.

Sensors / Drives / Robots
           |
           v
          PLC
           |
           v
  SCADA Driver / OPC
           |
           v
    SCADA / Node-RED
           |
           v
   Logging / Validation
           |
           v
      SQL Database
           |
           +------------------+
           |                  |
           v                  v
    Reports / Power BI    Grafana / Trends

This is a conceptual architecture. Actual deployments may log directly from SCADA to a historian, use an OPC server, use an edge gateway, or send data to another approved storage platform.

Layer responsibilities

PLC: Executes control logic and provides process data.

Communication driver or OPC interface: Transfers data between the controller and the acquiring application.

SCADA or edge application: Collects values, identifies events, validates data, and prepares records.

Database or historian: Stores records for retrieval and analysis.

Reporting and visualization tools: Query the stored data and present trends, summaries, and metrics.

The database should not be treated as the control system. A temporary SQL failure should not compromise the PLC's ability to execute its required control and safety functions.

6. SCADA Database Versus Historian

Both databases and historians store data, but they are often designed for different workloads.

Feature General-purpose SQL database Industrial historian
Typical data Production records, faults, quality results, transactions High-volume time-series process data
Data model Tables, rows, relationships Time-series or tag-oriented storage
Common queries Production reports, joins, counts, downtime Trends, time windows, signal history
Data compression Depends on schema and database design Often optimized for historical time-series data
Event storage Suitable with a good event schema Supported by some platforms, often alongside process values
Flexibility High for structured business data High for continuous industrial history
Best fit Transactional and relational records Large volumes of timestamped process measurements

These are general distinctions, not absolute limitations. SQL databases can store time-series data, and historians may support event and production records.

The choice depends on data volume, query patterns, retention, performance, reliability, integration requirements, and existing infrastructure.

7. Designing a Useful Logging Record

Every record should contain enough information to interpret it later.

A typical record may include:

  • Equipment or station identifier.
  • Tag or event name.
  • Value or event details.
  • Timestamp.
  • Data type or unit, where needed.
  • Data quality or validity information.
  • Production cycle or part identifier, when applicable.
  • Source system.
  • Relevant fault code or result.

For example:

Timestamp Station Signal Value Unit
10:00:00 FR1010 Pressure actual 5.8 bar
10:00:05 FR1010 Pressure actual 5.7 bar
10:00:10 FR1010 Pressure actual 5.6 bar

The timestamps and measurements are illustrative.

For meaningful comparisons, store timestamps consistently and document whether they represent source acquisition time, server receipt time, or database insertion time.

8. Production Data Logging

Production logging records the events and measurements required to understand manufacturing output.

Common production metrics

Total cycles: Number of recorded production cycles.

Good parts: Parts accepted by the defined quality process.

Rejected parts: Parts classified as rejected under the applicable quality rules.

Cycle time: Time taken by a defined production cycle.

Throughput: Quantity produced per unit of time.

Downtime: Time during which equipment is unavailable for its intended production function, according to the agreed definition.

These metrics need clear definitions. A station cycle count, a line output count, and the number of completed vehicle bodies are not necessarily equivalent.

Example: cycle record

Suppose station FR1010 starts a cycle at 10:15:00 and completes it at 10:15:42.

Station:       FR1010
Cycle start:   10:15:00
Cycle end:     10:15:42
Cycle duration: 42 seconds
Result:        Pass

The cycle duration is calculated as:

\[ \text{Cycle duration}=\text{End time}-\text{Start time} \]

A practical production table might contain:

Field Purpose
Cycle_ID Unique cycle record identifier
Station_ID Identifies the station
Start_Time Cycle start timestamp
End_Time Cycle end timestamp
Cycle_Time_S Recorded or calculated duration
Result Pass, reject, or another defined result
Part_ID Product identifier, where available and required

A unique record identifier helps prevent duplicate records from being mistaken for additional production.

9. Fault and Downtime Logging

Fault logging should capture more than the alarm message.

A useful fault record may include:

  • Unique event identifier.
  • Station or device.
  • Fault code.
  • Fault description.
  • Activation timestamp.
  • Clear timestamp.
  • Duration.
  • Acknowledgement details, if available and required.
  • Relevant operating mode.
  • Production cycle identifier, if available.
  • Corrective action or maintenance reference, where recorded.

Example fault history

Station Fault Start Clear Duration
FR1040 Clamp feedback timeout 10:14:32 10:16:05 93 s
FR1010 Robot fault 10:32:10 10:35:40 210 s

The example records are hypothetical.

Fault duration is calculated as:

\[ \text{Fault duration}=\text{Clear time}-\text{Start time} \]

This calculation is valid only if the timestamps represent the same event and the same time basis.

If a fault remains active, its clear time is not yet known. A report may show it as active rather than incorrectly assigning a zero or fabricated duration.

Fault logging versus downtime logging

A fault and a downtime interval are related, but not identical.

A fault may occur without stopping production. Conversely, production may stop because a station is starved, blocked, waiting for a downstream process, or intentionally paused.

A robust system defines how downtime begins and ends, which states count as downtime, and how overlapping faults are handled.

10. Data Quality and Validation

Historical data is useful only when its meaning and validity are understood.

Common data-quality problems include:

  • Missing samples.
  • Duplicate cycle records.
  • Incorrect timestamps.
  • Incorrect units or scaling.
  • Stale values recorded as current.
  • Invalid data recorded without a quality indication.
  • Counter resets or rollover.
  • Lost events during communication interruptions.
  • Records from the wrong station or controller.

Recommended validation rules

  1. Confirm the source and meaning of each signal.
  2. Validate data type, units, and range.
  3. Record appropriate timestamps and source identity.
  4. Detect duplicates using a suitable unique key or event identifier.
  5. Identify missing or stale data where possible.
  6. Preserve invalid-data indicators rather than silently converting invalid values into plausible measurements.
  7. Handle controller restarts, counter resets, and communication recovery explicitly.

For example, if a PLC counter resets after a controller restart, a simple difference between consecutive values may appear negative. The logging application needs a defined method to detect resets or use a more reliable cycle-event source.

11. Database Design for SCADA Logging

A useful database separates different kinds of records instead of placing every possible field into one enormous table.

A simple design might include:

SCADA Database
      |
      +---- Process_Samples
      |
      +---- Production_Cycles
      |
      +---- Fault_Events
      |
      +---- Equipment_Master
      |
      +---- Data_Quality_Events

11.1 Process samples

Stores timestamped measurements.

Typical columns:

  • Sample_ID
  • Timestamp
  • Equipment_ID
  • Tag_Name
  • Value
  • Quality

A production-grade schema may use separate typed columns or a normalized tag model rather than storing every value as a generic floating-point number.

11.2 Production cycles

Stores cycle-level records and results.

Typical columns:

  • Cycle_ID
  • Station_ID
  • Start_Time
  • End_Time
  • Cycle_Time_S
  • Result
  • Part_ID

11.3 Fault events

Stores alarm or fault lifecycle records.

Typical columns:

  • Event_ID
  • Station_ID
  • Fault_Code
  • Fault_Message
  • Start_Time
  • Clear_Time
  • Acknowledged_Time
  • Status

If the system must preserve every activation, acknowledgement, and clear transition, an event-history table may be preferable to overwriting a single current-state record.

11.4 Equipment master

Stores equipment reference information, such as:

  • Equipment identifier.
  • Station name.
  • PLC or controller reference.
  • Line or area.
  • Equipment type.
  • Relevant configuration version.

This helps maintain consistent equipment identity across production and fault records.

12. Example SQL Table Design

The following is an illustrative SQL Server schema for a basic fault-event table.

CREATE TABLE dbo.Fault_Events
(
    Event_ID BIGINT IDENTITY(1,1) PRIMARY KEY,
    Station_ID VARCHAR(30) NOT NULL,
    Fault_Code VARCHAR(50) NOT NULL,
    Fault_Message VARCHAR(250) NOT NULL,
    Start_Time DATETIME2(3) NOT NULL,
    Clear_Time DATETIME2(3) NULL,
    Status VARCHAR(20) NOT NULL
);

This table stores one record per fault occurrence, with a nullable clear time for a fault that has not yet cleared.

Example query to retrieve recent fault records:

SELECT
    Event_ID,
    Station_ID,
    Fault_Code,
    Fault_Message,
    Start_Time,
    Clear_Time,
    Status
FROM dbo.Fault_Events
WHERE Start_Time >= DATEADD(DAY, -1, SYSDATETIME())
ORDER BY Start_Time DESC;

This query uses the SQL Server's local system time. In a multi-system production environment, define a consistent timestamp convention, preferably using an agreed time basis, and adjust query boundaries accordingly.

A real implementation should also validate status values, define duplicate-event handling, establish indexes appropriate to its queries, and define retention and access policies.

13. Sampling Frequency and Storage Requirements

The logging interval has a direct effect on storage usage.

Suppose 100 tags are logged every second.

\[ 100 \times 60 \times 60 \times 24 =8{,}640{,}000 \]

That produces 8.64 million samples per day, assuming all 100 tags are recorded once per second without gaps.

Over 30 days:

\[ 8{,}640{,}000 \times 30 =259{,}200{,}000 \]

That is approximately 259.2 million sample records in 30 days, before accounting for indexes, metadata, backups, and database overhead.

A useful design must consider:

  • Number of tags.
  • Acquisition interval.
  • Event frequency.
  • Record size.
  • Indexes and database overhead.
  • Retention duration.
  • Query workload.
  • Backup and recovery requirements.

Practical logging strategy

  • Record important discrete state transitions as events.
  • Record cycle results at the cycle level.
  • Use appropriate intervals for analog process values.
  • Avoid recording duplicate values unnecessarily when change-based logging is suitable.
  • Retain high-resolution data where required for fault analysis.
  • Archive or purge records according to an approved retention policy.

Do not reduce logging resolution blindly just to save disk space. If the data is too coarse to explain the fault, the storage saving may simply purchase a more expensive troubleshooting exercise later.

14. Data Buffering and Communication Failure

A logging system may temporarily lose connectivity to the database or upstream data source.

A robust design considers what happens during the interruption.

Example architecture

PLC
 |
 v
SCADA / Edge Application
 |
 +---- Database connection healthy
 |              |
 |              v
 |          Store record
 |
 +---- Database unavailable
                |
                v
          Local buffer
                |
                v
       Connection restored
                |
                v
       Retry / replay records

This behavior must be explicitly supported and configured. A local buffer should not be assumed to exist merely because the application can connect to a database.

Important considerations

  • How long can data be buffered locally?
  • What happens when the buffer is full?
  • Are timestamps assigned at acquisition or later?
  • How are duplicates prevented during replay?
  • Are records replayed in the correct order?
  • How are unrecoverable records reported?
  • Does the logging failure generate a diagnostic event?
  • Can the PLC continue operating safely and normally if the logging service is unavailable?

A database outage should not automatically cause production control to fail. The architecture should separate process control from noncritical reporting and historical storage.

15. Using Logged Data for Maintenance Analysis

Data logging becomes particularly valuable when different records can be correlated.

Example: recurring station downtime

Suppose FR1040 experiences repeated stoppages over a week.

A maintenance engineer can analyze:

  • Fault occurrences by code.
  • Total time spent in each fault condition.
  • Average time between failures, where the data supports that calculation.
  • Repair duration.
  • Pressure and process values before faults.
  • Cycle time before and after maintenance.
  • Whether the same fault recurs after a component replacement.

This can help prioritize improvement work.

Important distinction: fault duration versus repair time

Fault duration measures how long the defined fault condition remains active.

Repair time measures the time spent performing the defined maintenance activity, according to the organization's measurement rules.

Downtime measures production unavailability under the agreed downtime definition.

These may differ substantially.

For example, a fault may stop production for 15 minutes, but maintenance may spend only 6 minutes actively repairing the equipment. The remaining time may include diagnosis, waiting for access, recovery, or verification.

The metric definitions must be consistent before comparing stations or shifts.

16. Common Data Logging Problems

Symptom Possible cause First diagnostic step
No records are being stored Logging disabled, failed connection, or database error Check logging status and database connectivity
Duplicate production cycles Retry behavior, missing unique key, or duplicate event delivery Check event identity and duplicate handling
Gaps in process history Acquisition failure, buffer overflow, or source communication loss Inspect data quality and logging diagnostics
Fault duration is incorrect Missing transition, inconsistent timestamps, or wrong calculation Verify start and clear events
Cycle time is negative Incorrect time source, ordering, or counter reset Check timestamps and event sequencing
Database grows too quickly Excessive sampling or retention, or large record/index overhead Measure record volume and review the logging strategy
Records appear out of order Clock differences or delayed buffering and replay Check timestamp source and replay behavior
Stored value differs from the PLC Wrong mapping, scaling, conversion, or acquisition time Compare source data and recorded value
Reports disagree with production counts Different counting definitions, resets, duplicates, or incomplete events Reconcile source and reporting rules
Logging stops after database failure No persistent buffer or retry/recovery mechanism Verify outage handling and recovery behavior

17. Interview Questions and Answers

Q1. What is SCADA data logging?

The collection and storage of timestamped industrial data for historical review, troubleshooting, production reporting, and analysis.

Q2. What is the difference between periodic and event-based logging?

Periodic logging stores values at configured intervals. Event-based logging stores records when defined events occur.

Q3. What is the difference between a SCADA database and a historian?

A general-purpose database commonly stores structured operational and transactional records. A historian is typically optimized for high-volume historical process data. The actual capabilities depend on the platform.

Q4. Why should timestamps be stored with process data?

They establish when a value or event occurred and allow it to be correlated with other equipment and production records.

Q5. Why are cycle-level records useful?

They allow cycle duration, production results, and relevant process conditions to be analyzed for individual production cycles.

Q6. What is the difference between fault duration and downtime?

Fault duration measures the period of a defined fault condition. Downtime measures production unavailability according to the agreed operational definition.

Q7. Why might database records be duplicated?

Retries, repeated event delivery, missing unique identifiers, or incorrect replay behavior can cause duplicate records.

Q8. How can excessive data logging affect a system?

It can increase database storage, write load, network traffic, backup duration, and query latency.

Q9. Why is data buffering useful?

It can temporarily retain records during a database or network interruption so that data may be delivered after connectivity returns, provided the application supports the required behavior.

Q10. Why should data quality be recorded?

It helps distinguish valid current measurements from missing, stale, uncertain, or otherwise invalid values.

Q11. How can logged data help prevent recurring faults?

It reveals recurring patterns, operating conditions, fault frequencies, and changes before or after failures, supporting evidence-based maintenance improvements.

Q12. Should a PLC depend on SQL Server to execute its control logic?

Normally, no. Essential control and safety functions should remain in the appropriate controller architecture. Historical storage and reporting should be designed so that their failure does not compromise required machine control.

18. Practical Exercises

Use a development system or an approved test environment.

  1. Define the data required to monitor a four-station robotic line.
  2. Separate the requirements into process samples, production cycles, fault events, and audit records.
  3. Design a production-cycle table with start time, end time, duration, result, and station identifier.
  4. Design a fault-event table with activation and clear timestamps.
  5. Calculate the daily sample volume for 250 tags logged every two seconds.
  6. Define a retention policy for high-resolution process data and production records.
  7. Investigate a hypothetical duplicate cycle record and propose a prevention mechanism.
  8. Design a method to detect missing or stale process samples.
  9. Document how the logging system should behave during a database outage.
  10. Correlate a fault record with pressure and clamp-feedback history.
  11. Define the difference between fault duration, repair time, and production downtime for a maintenance report.
  12. Prepare a SQL query that retrieves all fault events for a selected station during a defined period.

For every logged record, be able to answer these questions:

  1. What does the record represent?
  2. Which device or system produced the data?
  3. When was the value acquired or event detected?
  4. Is the record valid, complete, and correctly interpreted?
  5. How will the record be stored, retrieved, and retained?
  6. What decision or analysis will use it?
