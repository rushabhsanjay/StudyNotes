A Function Block (FB) is a reusable PLC programming unit that combines executable logic with its own associated data or internal state.

Function blocks allow engineers to build standardized control functions instead of repeatedly writing the same logic throughout a PLC program.

For example, an industrial plant may contain hundreds of motors. Each motor may require start/stop control, fault handling, permissives, feedback monitoring, and operating-status information. Rather than developing every motor's logic independently, engineers can create a reusable motor-control function block and configure a separate instance for each motor.

The central idea is write the control logic once, reuse it for multiple devices, and maintain each device's operating data separately.

1. Why Function Blocks Are Used

Consider a manufacturing line with 40 motors.

Each motor may need:

  • A run command.
  • A stop command.
  • A drive-ready signal.
  • A running feedback signal.
  • A fault input.
  • A timeout alarm.
  • An operating mode.
  • A status output for the HMI.

Without reusable structures, engineers may create similar logic separately for every motor. This introduces duplicated code and increases the effort required to maintain consistency.

With a function block, the engineer defines a common interface and behavior, then creates individual instances for the motors.

Typical applications include:

  • Motor and drive control.
  • Valve and cylinder control.
  • Conveyor control.
  • Analog signal processing.
  • Alarm handling.
  • Communication interfaces.
  • Robot handshakes.
  • Machine sequence modules.
  • Equipment status monitoring.

2. What Does a Function Block Contain?

A typical function block contains three major elements:

  1. Inputs: Information supplied to the block.
  2. Internal logic and state: Processing, calculations, timers, and stored values.
  3. Outputs: Results produced by the block.

Conceptually:

                 FUNCTION BLOCK
          +--------------------------+
Inputs -->|                          |--> Outputs
          |     Control Logic        |
          |                          |
          |     Internal State       |
          |                          |
          +--------------------------+

For a motor-control function block:

Element Example Purpose
Input StartRequest Requests motor operation
Input StopRequest Requests stopping
Input DriveReady Indicates drive readiness
Input FaultActive Indicates a fault
Internal state RunLatched Remembers the run-command state
Internal state StartTimer Tracks elapsed starting time
Output RunCommand Commands the drive or motor-control circuit
Output RunningStatus Reports running status
Output FaultStatus Reports a detected fault

The precise interface depends on the function block's design and the controller platform.

3. Function Block Definition Versus Function Block Instance

This is one of the most important concepts in function-block programming.

A function block definition describes the logic and interface. A function block instance is a particular use of that definition, with its own associated data.

Think of the definition as a design template and each instance as an individual device using that template.

Suppose a line has three conveyors.

FB_MOTOR  --> Motor-control logic definition

Instance 1: FB_MOTOR_Conveyor_01
Instance 2: FB_MOTOR_Conveyor_02
Instance 3: FB_MOTOR_Conveyor_03

All three instances may use the same logic definition, but each has its own commands, feedback, timer state, and status information, as supported by the implementation.

Property Function block definition Function block instance
Purpose Defines reusable behavior Represents one use of that behavior
Logic Contains the reusable implementation Executes the defined logic
Data Defines data requirements Holds instance-associated values
Example FB_MOTOR FB_MOTOR_Conveyor_01
Modification Changes the shared implementation Changes the configuration or data of one use, depending on the platform

A change to the shared definition may affect every instance that uses it. Therefore, modifications to widely used function blocks require proper testing and change control.

4. Instance Data and Retained State

Function blocks commonly store internal data between executions. This enables them to remember information that cannot be derived solely from the current input values.

For example, a motor function block may store:

  • Whether a run command has been latched.
  • Whether a start sequence is in progress.
  • Elapsed timer values.
  • Previous signal states.
  • Fault history or internal status flags.

Suppose FB_MOTOR_Conveyor_01 starts a motor and maintains its run state. The instance may remember that state after the start request returns to FALSE.

A second instance, FB_MOTOR_Conveyor_02, maintains its own state independently.

FB_MOTOR Definition
       |
       +--> Instance: Conveyor_01
       |       +--> Run state
       |       +--> Timer state
       |       +--> Status
       |
       +--> Instance: Conveyor_02
               +--> Run state
               +--> Timer state
               +--> Status

Important distinction: Internal state persisting between program executions does not automatically mean it survives a PLC power cycle or restart. That depends on the variable's memory configuration, retentivity settings, and platform behavior.

5. Function Blocks Versus Functions

PLC environments may provide both ordinary functions and function blocks. Their differences matter when selecting the appropriate programming structure.

Characteristic Function Function block
Main purpose Performs a calculation or operation Implements a reusable behavior, often with state
Internal state Generally does not maintain instance state between calls Commonly maintains instance-associated state
Stored data Usually depends on inputs and returned results Can include internal memory, timers, and status
Repeated use Can be called from different program locations Can have multiple independent instances
Typical example Convert a raw analog value to engineering units Control a motor with start/stop and fault monitoring

The distinction depends partly on the programming language and manufacturer. Some platforms use different terminology or impose different restrictions.

Example

A mathematical function may convert a raw analog value into pressure:

\[ P=\frac{R-R\_{\min}}{R\_{\max}-R\_{\min}} (P\_{\max}-P\_{\min})+P\_{\min} \]

A pressure-control function block might use that pressure value, compare it with a setpoint, maintain controller state, apply output limits, and generate an output command.

The function performs a calculation. The function block can manage a complete control behavior.

6. Function Blocks in Ladder Logic

Function blocks are not limited to one programming language. They can be used within graphical programming environments, including ladder-based programs, depending on the PLC platform.

A function block may appear as a rectangular instruction with input and output parameters.

Conceptually:

                 FB_MOTOR
          +--------------------+
Start ----| StartRequest       |
Stop -----| StopRequest        |
Ready ----| DriveReady         |
Fault ----| FaultActive        |
          |                    |
          | RunCommand --------|----> Motor command
          | RunningStatus -----|----> Status indication
          | FaultStatus -------|----> Fault alarm
          +--------------------+

The surrounding ladder logic can connect physical input tags, internal sequence conditions, and output tags to the function block.

This allows the main program to remain readable while detailed device-control logic resides inside the block.

For example:

Robot Sequence
      |
      v
Start Request
      |
      v
FB_MOTOR_Conveyor_01
      |
      +--> Run command
      +--> Running status
      +--> Fault status

The function block does not eliminate the need for understanding the underlying logic. It organizes that logic into a reusable unit.

7. Example: Motor-Control Function Block

Consider a simplified motor-control block with the following requirements:

  • Start the motor when a start request is active.
  • Permit operation only when the drive is ready.
  • Prevent operation when a fault is active.
  • Stop when a stop request is received.
  • Maintain the run command after the start request is released.
  • Provide running and fault status outputs.

Interface

Type Tag Meaning
Input StartRequest Start request
Input StopRequest Stop request
Input DriveReady Drive ready feedback
Input FaultActive Fault indication
Input RunningFeedback Actual running feedback
Output RunCommand Run command
Output RunningStatus Running indication
Output FaultStatus Fault indication
Internal RunLatched Stored run-command state

Conceptual behavior

Start Request
      |
      v
Check Stop Request
      |
      v
Check Drive Ready
      |
      v
Check Fault Status
      |
      v
Maintain or Clear Run State
      |
      +--> Run Command
      +--> Running Status
      +--> Fault Status

A simplified logical rule for the run-state request could be expressed as:

\[ RunLatched\_{next} = \begin{cases} 0, & StopRequest \lor FaultActive \lor \neg DriveReady\\\ 1, & StartRequest\\\ RunLatched\_{previous}, & \text{otherwise} \end{cases} \]

This equation illustrates the intended state behavior, not a complete implementation for any specific PLC. Actual logic must define the priority of stop, fault, and start conditions, as well as startup behavior and feedback handling.

Notice that the block separates the command from the actual running status. A run command being TRUE does not prove that the motor is physically running.

8. Function Blocks and Timers

Function blocks are especially useful when a control operation needs a timer or other internal state.

For example, a cylinder-control block may:

  1. Receive an extend request.
  2. Command the valve.
  3. Start a timeout timer.
  4. Monitor the extended-position sensor.
  5. Report completion when the expected sensor activates.
  6. Report a timeout fault if the sensor does not activate in time.
  7. Handle command cancellation or reset according to its defined behavior.
Extend Request
      |
      v
Command Valve
      |
      +----> Start Timeout Timer
      |
      v
Check Extended Sensor
      |
      +---- Sensor ON ----> Complete
      |
      +---- Timer Done ---> Timeout Fault

If the block is instantiated for several cylinders, each instance needs its own timer state and relevant device data. Otherwise, one cylinder's timing activity could interfere with another's control logic.

9. Reusability and Standardization

Function blocks help create consistent equipment-control standards across a plant.

For example, an engineering team could develop standard blocks for:

  • Direct-on-line motors.
  • Variable-frequency drives.
  • Pneumatic cylinders.
  • Analog transmitters.
  • Conveyor sections.
  • Robot interface signals.
  • Equipment fault reporting.

Each block can have a documented interface, expected behavior, fault response, and commissioning procedure.

Benefits include:

  • Less duplicated logic.
  • More consistent behavior between machines.
  • Easier program review.
  • Faster commissioning.
  • More structured diagnostics.
  • Easier maintenance and upgrades.
  • Better opportunities for testing and version control.

However, a reusable block is only as good as its design. Reusing a poorly designed block across 100 devices simply distributes the same problem 100 times, which is impressively efficient in exactly the wrong direction.

10. Function Blocks and Object-Oriented Concepts

Function blocks have similarities to object-oriented programming concepts, although they are not identical across all PLC environments.

Object-oriented concept Related function-block concept
Class or reusable type Function block definition or type
Object or instance Function block instance
Instance data Internal and associated instance variables
Methods or behavior Executable logic inside the block
Interface Defined input and output parameters

For example, a FB_MOTOR type can describe the behavior of a motor-control object. Separate instances can represent different motors.

This structure helps organize large programs into manageable units.

Not every PLC function block supports all object-oriented features. The comparison is conceptual rather than a claim that every PLC implements a full object-oriented language.

11. Function Blocks Across PLC Platforms

Platform General concept
Siemens SIMATIC Function blocks commonly use associated instance data blocks in supported programming environments
Rockwell Automation Logix Add-On Instructions can provide reusable instruction definitions with parameters and local data; they are similar in purpose to function blocks, but are not identical to IEC function blocks in every respect
Mitsubishi MELSEC Function blocks and structured programming features are available depending on the CPU family and engineering environment

The names, instance-storage mechanisms, parameter-passing rules, and supported languages differ. Always check the relevant platform documentation when working with actual controller code.

12. Common Function-Block Design Mistakes

Mistake Possible consequence Better practice
Reusing a block without understanding its behavior Unexpected machine operation Review the block's interface and logic
Incorrect input mapping Wrong device receives a command Verify every parameter connection
Confusing command with feedback Program reports operation that never occurred Separate command, feedback, and status
Shared state between independent devices One device affects another's behavior Use appropriate independent instances
Poor reset behavior Faults or commands remain active unexpectedly Define reset and startup behavior explicitly
Unclear output semantics HMI or sequence logic misinterprets status Document the meaning of each output
Changing a common block without regression testing Multiple machines may be affected Test all relevant instances and use version control
Assuming state survives power loss Unexpected restart or sequence behavior Verify retentivity and startup initialization
Hiding too much logic inside the block Troubleshooting becomes difficult Document internal behavior and expose useful diagnostics

13. How to Troubleshoot a Function Block

Suppose a conveyor motor does not start even though the main ladder rung appears TRUE.

Use the following sequence:

  1. Identify the function-block instance used for the conveyor.
  2. Verify the instance's input parameters, including start request, drive ready, stop request, and fault state.
  3. Inspect its outputs, especially the run command and fault status.
  4. Check internal state and timer values where the programming environment exposes them.
  5. Open the block definition and trace the logic determining the output.
  6. Confirm that the output tag is mapped to the intended drive or output circuit.
  7. Verify drive status and physical feedback.
  8. Check whether another part of the program writes to the same command tag.
  9. Compare the observed behavior with the block's documented requirements.

The key is to distinguish three separate conditions:

  • The calling program requests an action.
  • The function block accepts that request and produces a command.
  • The physical device executes the command and provides feedback.

A failure at any stage can produce the same visible symptom.

14. Interview Questions and Answers

Q1. What is a function block in PLC programming?

A reusable programming unit that combines executable logic with associated data and commonly maintains internal state between executions.

Q2. What is a function-block instance?

A specific use of a function-block definition, with its own associated instance data.

Q3. Why are function blocks useful in industrial automation?

They reduce duplicated code, standardize equipment behavior, improve readability, and simplify testing and maintenance.

Q4. What is the difference between a function and a function block?

A function generally performs an operation or calculation without maintaining instance state between calls. A function block commonly has associated state and is suited to reusable control behavior.

Q5. Can multiple motors use the same function block?

Yes. Multiple instances can use the same definition while maintaining independent instance data, provided the block is designed and configured correctly.

Q6. What is instance data?

Data associated with a particular function-block instance, such as its internal state, timer values, and status information.

Q7. Does function-block state always survive a power cycle?

No. Power-cycle persistence depends on the platform's memory and retentivity configuration.

Q8. Why should command and feedback be separate?

Because issuing a command does not prove that the physical device has completed the requested action.

Q9. Can a function block be used in ladder logic?

Yes, where the PLC platform and programming environment support calling or inserting function blocks within ladder programs.

Q10. What should be checked when a function block does not behave as expected?

Inspect the correct instance, input parameters, internal state, outputs, execution context, tag mapping, and physical feedback.

15. Practical Study Exercise

In an offline project or approved training environment, design a reusable FB_MOTOR interface.

Include:

  • StartRequest
  • StopRequest
  • DriveReady
  • FaultActive
  • RunningFeedback
  • RunCommand
  • RunningStatus
  • FaultStatus
  • Internal run state
  • A starting timeout or feedback-monitoring timer

Then create two instances:

  • FB_MOTOR_Conveyor_01
  • FB_MOTOR_Conveyor_02

Verify that each instance responds to its own inputs and maintains its own internal state. Test starting, stopping, drive-not-ready, fault, and timeout conditions.

Document the expected behavior before implementing it. That makes it possible to distinguish a design error from a programming error.

Do not test modified motor-control logic on live production equipment without the approved change-control and safety process.

16. Final Mental Model

  • Function block definition: The reusable control design.
  • Instance: One configured use of that design.
  • Inputs: Information entering the block.
  • Internal state: Data retained between executions as defined by the implementation.
  • Outputs: Commands, calculated values, and status information produced by the block.
  • Reusability: One standardized implementation can serve many devices.
  • Instance independence: Each instance should maintain its own state when independent device behavior is required.
  • Diagnostics: The block's interface and internal behavior must remain understandable enough to troubleshoot.

The practical principle is that function blocks turn repeated control logic into standardized, testable building blocks. They are particularly valuable when a plant contains many devices that behave similarly but must operate independently.
