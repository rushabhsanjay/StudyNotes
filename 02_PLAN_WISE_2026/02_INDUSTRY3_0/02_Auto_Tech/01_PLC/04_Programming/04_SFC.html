1. Definition

Sequential Function Chart (SFC) is a graphical method used to design, organize, and execute industrial control sequences using steps, transitions, and actions.

It is particularly useful when a machine must perform operations in a defined order, where each operation starts only after specific conditions are satisfied.

Examples include:

  • Robot loading, welding, and unloading cycles.
  • Pneumatic clamping and unclamping sequences.
  • CNC machine operating cycles.
  • Conveyor transfer sequences.
  • Automatic assembly and inspection stations.
  • Batch processes involving filling, mixing, heating, and discharging.

In industrial automation, SFC helps engineers understand which stage of a sequence is active, what the machine should do at that stage, and what condition allows it to move to the next stage.

SFC is defined within the IEC 61131-3 PLC programming framework. Exact implementation, action qualifiers, and execution behavior depend on the PLC platform and programming software.

SFC can coordinate actions implemented using Ladder Logic, Structured Text, Function Blocks, or other supported programming methods.

2. Why SFC is needed

Consider a robot welding station. Its automatic cycle might require the following operations:

  1. Wait for a start request.
  2. Verify that a component is present.
  3. Clamp the component.
  4. Confirm that the clamp is closed.
  5. Request the robot to execute its welding cycle.
  6. Wait for the robot to finish.
  7. Unclamp the component.
  8. Confirm that the clamp is open.
  9. Mark the cycle complete.

If all these operations are implemented without a clear sequence structure, the program can become difficult to understand and troubleshoot.

For example, the robot could receive a cycle request before clamping is complete, or the unclamp command could be issued before welding finishes.

SFC makes the intended operating order visible.

3. Core elements of SFC

3.1 Step

A step represents a stage or state of the machine sequence.

Examples:

  • S0_IDLE
  • S10_VERIFY_PART
  • S20_CLAMP_PART
  • S30_ROBOT_WELD
  • S40_UNCLAMP_PART
  • S50_CYCLE_COMPLETE

A step can have associated actions that operate while the step is active or according to its configured action behavior.

The initial step establishes the starting stage of the sequence.

Important points:

  • A step represents where the sequence currently is.
  • A step can remain active while the PLC waits for a transition condition.
  • A step is not necessarily equivalent to the physical state of a machine component.
  • Multiple steps can be active simultaneously in an SFC that uses parallel branches.

For example, the sequence might be at S20_CLAMP_PART while waiting for the clamp-closed sensor to turn ON.

3.2 Transition

A transition is a condition that permits the sequence to move from one step or group of steps to another.

A transition condition is typically a Boolean expression.

Examples:

  • StartRequest
  • PartPresent
  • ClampClosed
  • RobotCycleComplete
  • ClampOpen
  • NOT FaultActive

A transition is evaluated in the context of the preceding active step and the SFC execution rules.

Conceptually, when the preceding step is active and its outgoing transition evaluates TRUE, the sequence advances according to the chart's transition semantics.

For example:

[S20_CLAMP_PART]
        |
        | ClampClosed = TRUE
        v
[S30_ROBOT_WELD]

The sequence does not advance merely because a clamp command was issued. It advances when the configured transition condition becomes true. This is why commands and feedback signals must be distinguished.

3.3 Action

An action is the operation associated with a step.

Examples:

  • Activate a clamp command.
  • Request a robot cycle.
  • Start a timer.
  • Enable a conveyor.
  • Calculate an analog setpoint.
  • Call a function block.
  • Set an internal status flag.

An action can be implemented using Ladder Logic, Structured Text, Function Blocks, or the action mechanisms supported by the target PLC.

An important distinction: an action is not automatically a one-time instruction. Depending on its qualifier and implementation, it may execute repeatedly while its step is active.

For example, if the action continuously commands a clamp while S20_CLAMP_PART is active, that may be intentional. If the action sends a one-time trigger to a robot, repeated execution may be undesirable.

3.4 Directed links and sequence flow

Directed links show the intended flow between steps and transitions.

A basic sequential chart can be represented as follows:

       [S0_IDLE]
           |
           | StartRequest
           v
    [S10_VERIFY_PART]
           |
           | PartPresent
           v
     [S20_CLAMP_PART]
           |
           | ClampClosed
           v
      [S30_ROBOT_WELD]
           |
           | RobotCycleComplete
           v
     [S40_UNCLAMP_PART]
           |
           | ClampOpen
           v
    [S50_CYCLE_COMPLETE]

This is a simplified text representation. Actual SFC editors typically represent steps as boxes and transitions as separate transition elements, often drawn as bars between steps.

4. Step, transition, and action: the critical distinction

Element Main purpose Robot station example
Step Defines the current sequence stage S20_CLAMP_PART
Transition Determines when the sequence can advance ClampClosed = TRUE
Action Defines what the sequence does at a stage Command the clamp to close
Initial step Establishes the starting stage S0_IDLE
Directed link Defines sequence flow Clamp stage leads to robot stage

Remember this relationship:

  • Step: Where is the sequence?
  • Action: What should happen at this stage?
  • Transition: What must become true before advancing?

These are separate concepts. Mixing them up creates the industrial equivalent of a machine trying to leave a room before the door is open.

5. Detailed example: robot welding station

Assume a station has these signals:

Signal Meaning
StartRequest Operator or upstream system requests a cycle
AutoMode Automatic operating mode is selected
CyclePermissive Required process conditions are satisfied
PartPresent Component is detected
ClampCommand Command to close the clamp
ClampClosed Clamp-closed feedback is confirmed
RobotStartRequest Request sent to the robot controller
RobotCycleComplete Robot reports completion
UnclampCommand Command to open the clamp
ClampOpen Clamp-open feedback is confirmed

CyclePermissive is an application-level condition, not a substitute for independently implemented safety functions.

5.1 Sequence design

Step Purpose and action Exit condition
S0_IDLE Wait for a new cycle request StartRequest AND AutoMode AND CyclePermissive
S10_VERIFY_PART Confirm the component is present PartPresent
S20_CLAMP_PART Command the clamp to close ClampClosed
S30_ROBOT_WELD Request the robot cycle and monitor completion RobotCycleComplete
S40_UNCLAMP_PART Command the clamp to open ClampOpen
S50_CYCLE_COMPLETE Set completion status or notify the upstream system Completion handling finished
S90_FAULT Stop normal sequence progression and manage the fault state Fault recovery conditions satisfied

The exact return-to-idle and reset design depends on the machine's operating requirements. A cycle-complete step might wait for a reset, an acknowledgement, or a new cycle request.

Safety requirement: Emergency stops, guard interlocks, safe robot stopping, and other safety functions must be implemented and validated through appropriate safety-rated hardware and control systems. An ordinary SFC transition is not a safety function.

6. How an SFC advances

Consider the clamp step.

  1. S20_CLAMP_PART becomes active.
  2. Its action commands the clamp to close.
  3. The PLC continues executing the sequence according to the configured task and SFC semantics.
  4. The clamp-closed input becomes TRUE after the physical clamp reaches its confirmed position.
  5. The outgoing transition evaluates TRUE while the preceding step is active.
  6. The sequence advances to the robot-welding step according to the implementation's transition and step-activation rules.

The important point is that the command requests an operation, while feedback confirms its result.

For a real station, the transition might require additional conditions:

ClampClosed
AND PartPresent
AND NOT FaultActive

Whether those extra conditions belong in the transition, an equipment function block, or another part of the program depends on the design architecture.

Also, do not assume every platform evaluates transitions, executes actions, and activates steps in precisely the same way. Consult the target platform's documentation for detailed execution semantics.

7. Action qualifiers

Action qualifiers define how an action behaves relative to the activation and deactivation of a step.

The IEC SFC notation includes commonly encountered qualifiers, but availability and exact behavior can vary by PLC platform and programming environment.

Qualifier General meaning Typical use
N Non-stored action associated with the active step Maintain a command while the step is active
S Set or store an action Set a flag that remains set until reset
R Reset a stored action Clear a previously stored flag
P Pulse action according to the platform's defined pulse semantics Trigger a one-time event
L Time-limited action Run an action for a defined duration
D Delayed action Start an action after a defined delay

These are general descriptions, not a guarantee that every editor supports every qualifier or implements them identically.

7.1 Non-stored action: N

A non-stored action is associated with the active step.

Example:

Active step: S20_CLAMP_PART
Action:      ClampCommand = TRUE

When the step becomes inactive, the action is no longer active under the normal non-stored behavior. However, the resulting output behavior still depends on how the action writes the output and how the PLC program manages it.

Do not assume that leaving a step automatically clears every physical output in every program architecture.

7.2 Stored action: S and reset action: R

A stored action sets a flag or action state that persists beyond the normal active period of its originating step. A corresponding reset action clears it.

Conceptual example:

Step S50_CYCLE_COMPLETE:
    Set CycleComplete

Later reset condition:
    Reset CycleComplete

This can be useful for status flags or handshakes, but it requires a clear reset strategy. Otherwise, an old completion flag can remain active during the next cycle.

7.3 Pulse action: P

A pulse-type action is useful when an event should be initiated once rather than continuously requested.

Examples include:

  • Sending a one-shot trigger.
  • Incrementing an event counter.
  • Issuing a command that the receiving system expects as a pulse.

The precise pulse timing and triggering rules depend on the platform and the specific qualifier. If the receiving device needs a rising edge, confirm that the implementation actually produces one.

7.4 Delayed and time-limited actions

A delayed action may wait for a configured time before activating. A time-limited action may remain active only for a specified duration.

These mechanisms are not substitutes for process feedback.

For example, waiting two seconds after commanding a clamp does not prove the clamp is closed. A proper sequence should still use the appropriate position feedback and fault monitoring.

8. Alternative branching and simultaneous branching

SFC supports different kinds of branching for more complex sequences.

8.1 Alternative branching: OR

An alternative branch selects one path from multiple possible paths.

Example: a station processes either a standard part or a special part.

                 [S10_CLASSIFY_PART]
                          |
                    PartType check
                      /       \
               Standard       Special
                  |              |
                  v              v
          [S20_STANDARD]  [S30_SPECIAL]
                  |              |
                  +------\ /-----+
                         |
                         v
                  [S40_NEXT_STEP]

The diagram is simplified. A real chart must define the branch transitions and convergence correctly in the target editor.

Important design points:

  • Branch conditions should be complete.
  • If paths are intended to be mutually exclusive, ensure the conditions are mutually exclusive or define the supported priority behavior.
  • Define what happens if no branch condition is true.
  • Define what happens if more than one condition is true.

Otherwise, a sequence may stall or select an unintended path.

8.2 Simultaneous branching: AND

A simultaneous branch activates multiple sequence paths in parallel.

Example: after a component is clamped, the station might request a robot operation while an independent system performs a permitted status check.

                    [S20_CLAMPED]
                          |
                    Parallel split
                      /       \
                     v         v
             [S30_ROBOT]  [S40_STATUS_CHECK]
                     |         |
             RobotComplete   CheckComplete
                     |         |
                     v         v
                    Parallel convergence
                          |
                          v
                   [S50_NEXT_STEP]

The next stage should only be reached according to the chart's synchronization rules. In a conventional parallel convergence, all required incoming branches must complete.

Multiple active steps are therefore possible in a parallel SFC.

Do not confuse SFC parallel branching with parallel branches in Ladder Logic. Ladder branches generally describe alternative logical paths within a rung. SFC parallel branching describes simultaneous sequence paths with their own active steps and synchronization behavior.

9. Step actions do not always execute only once

This is one of the most important practical distinctions.

Suppose a robot request is associated with a step that remains active for several PLC scans. If the action repeatedly writes RobotStartRequest = TRUE, the request may remain asserted or be repeatedly processed, depending on the implementation and receiving system.

Whether that is correct depends on the robot handshake.

For example:

  • A maintained request may remain TRUE until the robot acknowledges it.
  • A pulse request may need to turn ON briefly and then OFF.
  • A request may need to remain ON until RobotBusy or another acknowledgement becomes TRUE.

These are different handshake designs.

Before programming an action, establish whether the target signal is expected to be:

  • A maintained command.
  • A one-shot pulse.
  • A set/reset state.
  • A request that remains active until acknowledgement.

Use the appropriate action qualifier, edge detection, or handshake logic. Do not assume that an action executes once simply because it is associated with one step.

10. SFC versus Ladder Logic, Structured Text, and Function Blocks

Method Main strength Typical application
SFC Makes sequence order and branching visible Machine-cycle coordination
Ladder Logic Visual Boolean and discrete control logic Interlocks, permissives, output control
Structured Text Calculations, algorithms, arrays, data handling Scaling, calculations, complex conditions
Function Blocks Encapsulates reusable control behavior and data Motors, valves, drives, alarms

These methods are complementary, not competitors in a programming-language cage match.

A useful industrial architecture is:

                 SFC
          Sequence coordination
                   |
        +----------+----------+
        |          |          |
        v          v          v
   Clamp logic  Robot logic  Conveyor logic
   Function     Function    Function
   Block        Block       Block
        |          |          |
        v          v          v
     Outputs    Handshake   Outputs
     Feedback   Feedback    Feedback

For example, the SFC decides that the clamp should close. A clamp function block manages the command, position feedback, timeout, and fault status. The SFC advances when the required confirmation condition is satisfied.

This separation makes the program easier to maintain and retrofit.

11. Sequence timeouts and fault recovery

A sequence timeout detects that an expected operation has not completed within an allowed time.

Examples:

  • Part detection timeout.
  • Clamp-closed timeout.
  • Robot-cycle timeout.
  • Clamp-open timeout.

Suppose the clamp is commanded to close, but ClampClosed never becomes TRUE.

The sequence should not wait forever without reporting the problem.

A conceptual approach is:

Step S20_CLAMP_PART becomes active
            |
            v
Start or enable step timer
            |
            v
ClampClosed becomes TRUE?
       /           \
     Yes            No
      |              |
      v              v
Advance         Timeout reached?
                     |
                 +---+---+
                 |       |
                No      Yes
                 |       |
              Continue   v
                       S90_FAULT

The actual timer implementation must account for step entry, step exit, timer reset, and the selected PLC's execution behavior.

Sequence timeout versus watchdog

Feature Sequence timeout PLC watchdog
Purpose Detect a process operation taking too long Detect excessive program execution time
Example Clamp fails to close within the allowed interval PLC task or scan exceeds its execution limit
Typical response Set process fault and enter recovery handling Controller may report a watchdog fault or take platform-defined action

A process timeout monitors machine behavior. A watchdog monitors controller execution. They solve different problems.

Fault recovery design

A fault step should define:

  • Which commands must be removed or maintained.
  • Which equipment feedback signals must be checked.
  • Whether automatic restart is permitted.
  • Which reset or acknowledgement is required.
  • Whether the sequence must return to idle or perform a controlled recovery operation.
  • Whether the fault requires manual intervention.

A reset must not simply force the sequence forward while the machine remains in an invalid physical condition.

12. Common SFC faults and troubleshooting

Symptom Possible cause What to check
Sequence is stuck at a step Outgoing transition is FALSE Check the live transition expression and input values
Action does not operate Wrong action association or qualifier Check the active step and action configuration
Sequence skips an operation Transition condition is already TRUE or step logic is incorrect Check step activation, transition timing, and initial values
Two alternative steps activate unexpectedly Branch design or transition semantics are incorrect Inspect alternative-branch conditions and configuration
Parallel sequence never rejoins One branch is incomplete Identify which required branch has not reached convergence
Output remains ON after step exit Stored action or another program section maintains the output Trace all writers and reset conditions
Robot receives repeated start requests Request is continuously asserted or pulse handling is incorrect Check the handshake and action qualifier
Sequence never restarts Completion flag or reset condition is missing Check the return-to-idle transition
Timeout occurs immediately Timer is not initialized or reset correctly Check timer enable, reset, and step-entry logic
Sequence resumes in an invalid state after restart Initialization and retained-state behavior are not handled Check startup logic and the platform's retentivity rules

Recommended troubleshooting order

  1. Identify the currently active step.
  2. Identify the outgoing transition from that step.
  3. Evaluate each Boolean term in the transition.
  4. Verify actual field feedback, not only output commands.
  5. Check the action qualifier and associated action logic.
  6. Trace whether another program section writes the same output or status tag.
  7. Check timers, fault branches, reset conditions, and startup behavior.
  8. Confirm the controller's actual SFC execution semantics if the observed behavior is unexpected.

This sequence of checks prevents unnecessary code changes when the real problem is a missing sensor signal or an unmet permissive.

13. SFC design best practices

  • Use meaningful step names such as S20_CLAMP_PART, not vague names such as STEP_3.
  • Use a consistent numbering convention so additional steps can be inserted later.
  • Give each step one main operational purpose.
  • Make transition conditions explicit and readable.
  • Distinguish commands from feedback.
  • Use action qualifiers intentionally, especially for one-shot events and stored states.
  • Provide timeouts for operations that can fail or take too long.
  • Design fault recovery and restart behavior before commissioning.
  • Avoid multiple uncontrolled writers for the same physical output.
  • Keep reusable equipment control inside well-defined function blocks or routines where appropriate.
  • Test normal, alternative, parallel, timeout, reset, and restart paths.
  • Validate behavior after power interruption and controller restart according to the intended machine requirements.
  • Keep safety functions independent of ordinary SFC sequence logic.

SFC should make sequence behavior easier to understand. If every step hides hundreds of lines of unrelated logic, the chart is technically graphical but has achieved approximately nothing.

14. Platform differences

SFC availability and implementation depend on the controller family, firmware, programming software, and supported language features.

Platform ecosystem What to understand
Siemens SFC-related programming and GRAPH sequencing features vary by PLC family and engineering environment; SCL can be used for supported textual logic
Rockwell Automation Sequential Function Chart support and behavior depend on controller and software capabilities; verify support for the specific Logix platform
Mitsubishi Electric Available sequence-programming features and implementation patterns depend on CPU family and engineering software

Do not assume that an SFC chart, action qualifier, or execution detail will transfer unchanged between platforms. The IEC framework provides common concepts, but platform manuals define the actual implementation.

15. Interview questions and answers

Q1. What is SFC?

SFC is a graphical method for representing and controlling sequential processes using steps, transitions, and actions.

Q2. What is the difference between a step and a transition?

A step represents a stage of the sequence. A transition is the condition that permits the sequence to move from that stage to the next one.

Q3. What is an action in SFC?

An action defines the operation associated with a step. Depending on its qualifier and implementation, it may execute while the step is active, persist after the step, or operate according to other defined timing behavior.

Q4. Can multiple steps be active simultaneously?

Yes. Parallel branching can activate multiple steps at once. The chart's synchronization logic determines when the paths can converge.

Q5. What is the difference between alternative and simultaneous branching?

Alternative branching selects a path from available alternatives. Simultaneous branching activates multiple paths in parallel.

Q6. Why might an SFC sequence get stuck?

A transition may never become TRUE because a sensor is missing, a permissive is FALSE, a timer is incorrect, or the action did not produce the expected result.

Q7. How do you execute an action only once?

Use an appropriate pulse or edge-triggered mechanism, or another supported one-shot implementation. Verify the actual platform semantics and the receiving device's handshake requirements.

Q8. What is the purpose of a sequence timeout?

It detects an operation that has not completed within the allowed time and initiates fault handling or recovery.

Q9. Is SFC a safety-rated function by itself?

No. An ordinary SFC sequence does not become safety-rated merely because it contains safety-related conditions. Required safety functions must use suitable safety-rated components and validated designs.

Q10. Why combine SFC with Function Blocks?

SFC organizes the sequence, while function blocks can encapsulate the behavior of equipment such as clamps, motors, valves, and robot handshakes.

16. Practical exercise

Create an offline training sequence for a simulated robot welding station.

Required steps:

  1. S0_IDLE
  2. S10_VERIFY_PART
  3. S20_CLAMP_PART
  4. S30_REQUEST_ROBOT
  5. S40_WAIT_WELD_COMPLETE
  6. S50_UNCLAMP_PART
  7. S60_CYCLE_COMPLETE
  8. S90_FAULT

Define the following transition conditions:

  • Start request, automatic mode, and cycle permissive.
  • Part-present confirmation.
  • Clamp-closed feedback.
  • Robot-cycle completion.
  • Clamp-open feedback.
  • Cycle completion acknowledgement or restart condition.
  • Timeout and fault-recovery conditions.

Test these scenarios using simulated signals:

  • Normal cycle.
  • Part never detected.
  • Clamp never reaches closed position.
  • Robot never reports completion.
  • Clamp never reaches open position.
  • Fault reset and recovery.
  • Controller or application restart.

Record the active step, transition status, action status, timer value, and fault state for each test. This provides a simple method to validate the sequence before connecting it to real equipment.

17. Final mental model

SFC represents a machine process as a sequence of operational stages.

  • Step: Defines the current stage.
  • Action: Defines what happens at that stage.
  • Transition: Defines when the sequence can advance.
  • Branch: Defines alternative or simultaneous paths.
  • Timeout: Detects an operation that takes too long.
  • Fault recovery: Defines how the machine returns to a valid operating state.

For industrial maintenance, SFC is particularly useful when diagnosing why a robot, clamp, conveyor, or automatic station has stopped at a particular stage. Instead of searching the entire program randomly, identify the active step, inspect its actions, and evaluate its outgoing transition.
