Structured Text (ST) is a high-level, text-based PLC programming language used to implement industrial control logic, calculations, conditional operations, loops, data processing, and algorithms.

It is one of the programming languages defined by IEC 61131-3 for programmable controllers. Compared with Ladder Diagram, Structured Text expresses logic through written statements rather than graphical contacts and coils.

For example, a motor command can be written as:

IF StartRequest AND DriveReady AND NOT FaultActive THEN
    RunCommand := TRUE;
ELSE
    RunCommand := FALSE;
END_IF;

This program evaluates the conditions and assigns a value to RunCommand.

Structured Text becomes particularly useful when logic involves many calculations, repeated data operations, arrays, loops, complex conditions, or mathematical algorithms that would become difficult to read as a large ladder diagram.

1. Why Structured Text Is Used

Industrial automation often requires more than simple ON/OFF control.

Consider a manufacturing station that must:

  • Convert raw analog values into engineering units.
  • Calculate production rates.
  • Compare actual values against limits.
  • Process data from multiple sensors.
  • Search an array for a particular device.
  • Calculate an average or deviation.
  • Validate recipes and parameter ranges.
  • Process communication data.
  • Perform calculations for a machine sequence.

Structured Text can express these operations compactly.

Typical applications include:

  • Analog signal scaling.
  • Mathematical calculations.
  • Data conversion and validation.
  • Array and structure processing.
  • Recipe management.
  • Production counters and statistics.
  • Communication data handling.
  • Algorithmic control.
  • Complex state and sequence logic.

Ladder Logic remains valuable for graphical troubleshooting and discrete control. Structured Text complements it rather than automatically replacing it.

2. Basic Structure of a Structured Text Program

A Structured Text program consists of statements that the PLC executes according to the program organization and scheduling rules.

A basic assignment uses the := operator.

RunCommand := TRUE;

This assigns TRUE to the variable RunCommand.

A numeric calculation might look like this:

PressureDifference := PressureActual - PressureSetpoint;

A conditional operation uses IF, THEN, ELSE, and END_IF.

IF PressureActual > PressureLimit THEN
    HighPressureAlarm := TRUE;
ELSE
    HighPressureAlarm := FALSE;
END_IF;

The condition is evaluated, and the appropriate assignment is executed.

Common syntax elements

Element Purpose Example
:= Assignment Count := 10;
= Equality comparison IF State = 2 THEN
<> Not equal IF State <> 0 THEN
> Greater than IF Pressure > 8.0 THEN
< Less than IF Speed < 100.0 THEN
>= Greater than or equal to IF Count >= 10 THEN
<= Less than or equal to IF Temperature <= 80.0 THEN
AND Logical AND A AND B
OR Logical OR A OR B
NOT Logical inversion NOT FaultActive
; Terminates a statement in common ST syntax RunCommand := TRUE;

Exact syntax, supported operators, and extensions depend on the PLC platform.

Important distinction: := assigns a value, while = generally tests equality in an expression. Confusing them can produce incorrect code.

3. Variables and Data Types

Structured Text uses variables to represent physical signals, commands, internal states, measurements, and calculated values.

The data type determines what kind of information a variable can hold.

Data type Purpose Example
BOOL Boolean TRUE/FALSE value MotorReady
SINT Small signed integer SmallOffset
INT Signed integer PartCount
DINT Wider signed integer TotalProduction
UINT Unsigned integer RecipeNumber
REAL Floating-point number PressureActual
LREAL Wider floating-point representation on supported platforms CalculatedValue
TIME Time duration StartTimeout
STRING Character string MachineName
Array Collection of indexed elements SensorValues[1]
Structure or user-defined type Collection of related fields Motor.Status

Available types and their exact ranges vary by platform.

Example: Variable declarations

A declaration section in a common IEC-style environment may look like this:

VAR
    StartRequest       : BOOL;
    DriveReady         : BOOL;
    FaultActive        : BOOL;
    RunCommand         : BOOL;
    PressureActual     : REAL;
    PressureSetpoint   : REAL;
    PressureDifference : REAL;
    PartCount          : DINT;
END_VAR

This example illustrates common declaration syntax. The exact location and format of declarations depend on the engineering environment and program type.

Why data types matter

Suppose an encoder reports a count of 75,000, but the program stores the value in a data type whose range is too small.

The result may overflow, be rejected, or behave differently depending on the platform and operation.

Similarly, mixing integer and floating-point calculations may cause rounding, conversion, or precision issues.

Always verify the data type, range, signedness, and conversion behavior when troubleshooting numeric problems.

4. Conditional Logic: IF, ELSIF, and ELSE

Conditional statements allow the program to choose which operations to execute.

Example: Motor permission

IF FaultActive THEN
    RunCommand := FALSE;
ELSIF NOT DriveReady THEN
    RunCommand := FALSE;
ELSIF StartRequest THEN
    RunCommand := TRUE;
ELSE
    RunCommand := FALSE;
END_IF;

The program evaluates the conditions in sequence.

  1. If a fault is active, the command is FALSE.
  2. Otherwise, if the drive is not ready, the command is FALSE.
  3. Otherwise, if a start request exists, the command is TRUE.
  4. Otherwise, the command is FALSE.

The order matters because an ELSIF branch is evaluated only when earlier conditions are FALSE.

This example implements a non-latching command. If StartRequest becomes FALSE, the command also becomes FALSE. A holding circuit or state machine would require additional logic.

Multiple independent IF statements

Consider:

IF ConditionA THEN
    OutputValue := 10;
END_IF;

IF ConditionB THEN
    OutputValue := 20;
END_IF;

If both conditions are TRUE, both assignments can execute. In this example, the later assignment can determine the final value.

This is important when multiple conditions write the same variable. Structured Text does not automatically resolve conflicting assignments according to the engineer's intentions.

5. CASE Statements

A CASE statement selects an execution path based on the value of a variable.

It is useful for representing machine sequence states.

CASE MachineState OF

    0:
        MotorCommand := FALSE;
        ClampCommand := FALSE;

    10:
        MotorCommand := TRUE;
        ClampCommand := FALSE;

    20:
        MotorCommand := FALSE;
        ClampCommand := TRUE;

    30:
        MotorCommand := FALSE;
        ClampCommand := FALSE;

ELSE
    MotorCommand := FALSE;
    ClampCommand := FALSE;

END_CASE;

In this example:

  • State 0 represents an idle condition.
  • State 10 commands the motor.
  • State 20 commands the clamp.
  • State 30 commands neither device.
  • Any other state follows the ELSE branch.

This illustrates state-dependent output assignment. It does not by itself define how the machine moves between states.

State transitions

A separate section of logic can determine when the machine changes state.

IF MachineState = 0 AND StartRequest THEN
    MachineState := 10;
END_IF;

IF MachineState = 10 AND PartDetected THEN
    MachineState := 20;
END_IF;

This is a simplified example. A complete sequence must account for state-transition priority, fault handling, initialization, sensor behavior, and what happens if multiple transition conditions are TRUE.

6. Loops: FOR, WHILE, and REPEAT

Loops repeat operations. They are especially useful for processing arrays and collections of data.

However, loops must be designed carefully in PLC programs because an unexpectedly long or unbounded loop can consume excessive execution time.

A. FOR loop

A FOR loop repeats a block for a defined index range.

FOR Index := 1 TO 10 DO
    Total := Total + SensorValues[Index];
END_FOR;

This example adds ten array elements to Total.

For a correct average calculation, Total should be initialized before the loop:

Total := 0.0;

FOR Index := 1 TO 10 DO
    Total := Total + SensorValues[Index];
END_FOR;

AverageValue := Total / 10.0;

The array bounds and index data type must be valid for the target PLC.

B. WHILE loop

A WHILE loop repeats while its condition remains TRUE.

WHILE Index <= 10 DO
    Total := Total + SensorValues[Index];
    Index := Index + 1;
END_WHILE;

The index must be initialized correctly before entering the loop, and the loop condition must eventually become FALSE.

If the index never advances or the exit condition can never be met, execution may not complete normally.

C. REPEAT loop

A REPEAT loop evaluates its exit condition after executing the loop body.

REPEAT
    Index := Index + 1;
UNTIL Index >= 10
END_REPEAT;

This structure guarantees at least one execution of the body, assuming normal execution and supported syntax.

Practical rule for loops

  • Prefer a bounded FOR loop when the number of iterations is known.
  • Ensure WHILE and REPEAT loops have valid exit conditions.
  • Consider the worst-case execution time.
  • Avoid large or unbounded loops in time-critical tasks.
  • Verify loop support and execution behavior on the actual PLC.

A loop that works in a desktop program may be unsuitable for a time-sensitive controller task.

7. Boolean Operations

Structured Text supports Boolean expressions similar to those used in Ladder Logic.

MotorPermit := DriveReady AND NOT FaultActive AND SafetyPermit;

This expression requires all three conditions to evaluate appropriately:

  • DriveReady must be TRUE.
  • FaultActive must be FALSE.
  • SafetyPermit must be TRUE.

A parallel logical condition can be expressed as:

StartRequest := LocalStart OR RemoteStart;

Complex conditions should be written clearly, using parentheses where they improve readability.

For example:

RunRequest := (LocalStart OR RemoteStart)
              AND DriveReady
              AND NOT FaultActive;

Parentheses make the intended grouping explicit and reduce ambiguity when expressions become more complicated.

A standard PLC Boolean variable is not automatically a safety-rated signal. Safety-related logic must be implemented using the appropriate validated safety system.

8. Timers and Function Blocks in Structured Text

Structured Text can call function blocks, including timer function blocks, where supported by the programming environment.

A common IEC-style on-delay timer example is:

StartTimer(
    IN := StartRequest,
    PT := T#3s
);

IF StartTimer.Q THEN
    StartTimeoutAlarm := TRUE;
ELSE
    StartTimeoutAlarm := FALSE;
END_IF;

This illustrates a timer call with an enable input and a preset duration of three seconds.

For a typical on-delay timer:

  • IN enables timing.
  • PT specifies the preset time.
  • Q indicates that the timer has elapsed while enabled.

The exact timer interface and behavior depend on the PLC implementation.

Important: This example means that the timer output becomes TRUE after the start request remains active for the preset duration. It does not automatically prove that a motor failed to start.

A proper starting-timeout alarm would normally also consider whether the expected running feedback has arrived, for example:

IF StartTimer.Q AND NOT RunningFeedback THEN
    StartTimeoutAlarm := TRUE;
ELSE
    StartTimeoutAlarm := FALSE;
END_IF;

The complete implementation must define timer reset behavior, command cancellation, and alarm latching or reset requirements.

9. Analog Scaling and Engineering Calculations

Structured Text is useful for converting raw sensor values into engineering units.

Suppose an analog input represents a pressure transmitter measuring 0 to 10 bar. The controller supplies a raw numeric value corresponding to the configured input range.

A linear scaling relationship is:

\[ EngineeringValue = \frac{RawValue-RawMin}{RawMax-RawMin} (EngMax-EngMin)+EngMin \]

For a hypothetical input range of 0 to 27648 representing 0 to 10 bar:

\[ Pressure = \frac{RawValue}{27648}\times 10 \]

An ST implementation could be:

PressureBar :=
    (REAL(RawValue) / 27648.0) * 10.0;

The conversion syntax may differ between PLC environments.

Before using this calculation, verify the actual module configuration and raw-data range. Some analog modules use different numeric ranges, scaling conventions, or diagnostic values.

A robust implementation should also handle out-of-range data and distinguish a valid zero-pressure measurement from a signal fault where the hardware supports that distinction.

10. Arrays and Structured Data

Arrays store multiple values of the same declared type.

For example, a system may monitor temperatures from eight stations.

VAR
    Temperature : ARRAY[1..8] OF REAL;
    Index       : INT;
    HighestTemp : REAL;
END_VAR

A loop can find the highest temperature:

HighestTemp := Temperature[1];

FOR Index := 2 TO 8 DO
    IF Temperature[Index] > HighestTemp THEN
        HighestTemp := Temperature[Index];
    END_IF;
END_FOR;

This approach avoids writing eight separate comparison statements.

For larger automation systems, structures or user-defined data types can group related information for each device.

A motor data structure might contain:

Motor
    StartRequest
    StopRequest
    RunCommand
    RunningFeedback
    FaultActive
    OperatingState

The actual declaration syntax and supported data structures depend on the PLC platform.

11. Function Blocks and Structured Text

Structured Text is a programming language. A function block is a reusable program unit. They are related but different concepts.

A function block can contain Structured Text code, ladder logic, or another supported implementation, depending on the engineering environment.

For example:

FB_MOTOR
    |
    +--> Inputs
    |
    +--> Internal State
    |
    +--> Structured Text Logic
    |
    +--> Outputs

The block defines the behavior, while Structured Text expresses the operations inside it.

This distinction helps when reading an existing project: determine whether you are looking at a language, a program organization unit, or an instance of a reusable control block.

12. Structured Text Versus Ladder Logic

Feature Structured Text Ladder Logic
Representation Written statements Graphical rungs and instructions
Boolean logic Expressions and conditions Contacts and branches
Calculations Often compact and readable Can become visually complex
Loops and arrays Natural fit for many operations Support depends on instructions and platform
Discrete control Suitable Often especially readable
Troubleshooting Requires reading statements and variables Conditions are visually traceable
Reusable logic Can implement or call reusable blocks Can implement or call reusable blocks
Best use Complex calculations, data handling, algorithms Discrete control, interlocks, and visual logic tracing

Neither language is universally superior. Well-designed programs often combine languages according to the function being implemented and the maintenance team's needs.

14. How to Troubleshoot Structured Text

When an output or calculation behaves unexpectedly:

  1. Identify the variable producing the incorrect result.
  2. Find every statement that writes to that variable.
  3. Check the values of all input variables at the time of the problem.
  4. Trace the relevant IF, CASE, or loop path.
  5. Verify data types, array indices, arithmetic operations, and conversions.
  6. Check timer instances and retained internal state if function blocks are involved.
  7. Confirm execution order and task scheduling.
  8. Compare the actual result with the expected result using a small test case.
  9. Verify that the corrected behavior does not introduce unintended effects elsewhere.

For example, if PressureBar displays an incorrect value, do not immediately change the HMI display. Verify the raw input, scaling formula, conversion, engineering units, and the tag being displayed.

15. Interview Questions and Answers

Q1. What is Structured Text?

A high-level, text-based PLC programming language used for calculations, conditional logic, loops, data processing, and algorithms.

Q2. What is the difference between := and =?

:= is the assignment operator in common ST syntax. = is generally used to test equality in an expression.

Q3. When is Structured Text preferable to Ladder Logic?

It is often preferable for complex calculations, array processing, loops, mathematical algorithms, and extensive data handling.

Q4. What is a CASE statement used for?

It selects an execution path based on the value of an expression, making it useful for state-dependent logic.

Q5. What is the risk of an infinite loop in a PLC?

The program may fail to complete normally, consume excessive execution time, or trigger a task or controller fault, depending on the platform.

Q6. Why are data types important?

They determine the values a variable can represent and affect arithmetic, memory use, precision, and conversion behavior.

Q7. Can Structured Text call a function block?

Yes, supported programming environments allow function-block instances to be called from Structured Text.

Q8. Why can a variable have the wrong final value even when each statement is correct?

Because multiple statements may write to it, and execution order determines which assignment occurs last.

Q9. Can Structured Text be used for analog scaling?

Yes. It can implement scaling formulas, unit conversions, limits, and validation checks.

Q10. Does Structured Text automatically make a PLC program faster?

No. Execution time depends on the code, controller, task scheduling, data handling, and implementation. Performance should be measured on the target system.

16. Practical Study Exercise

In an offline PLC simulator or training project, create a program that processes pressure data.

Requirements:

  • Read a simulated raw analog value.
  • Convert it to a pressure value in bar.
  • Calculate the difference between actual pressure and a setpoint.
  • Set a high-pressure alarm when the value exceeds a defined limit.
  • Use a CASE statement to represent three operating states: idle, running, and fault.
  • Use an array containing several simulated sensor readings and calculate the highest value.
  • Test normal values, boundary values, and invalid input conditions.

Document the expected output for each test case before executing the program.

This exercise combines assignments, Boolean expressions, conditional logic, numeric conversion, arrays, loops, and state-based processing.

Do not deploy training code directly into a production PLC without platform-specific verification, review, and approved commissioning.

17. Final Mental Model

  • Structured Text: The language used to express operations as written statements.
  • Variables and data types: Define the information being processed.
  • Assignments: Store calculated or commanded values.
  • IF statements: Select behavior based on conditions.
  • CASE statements: Select behavior based on a state or value.
  • Loops: Repeat operations over a defined range or condition.
  • Function blocks: Provide reusable behavior and may maintain internal state.
  • Arrays and structures: Organize larger quantities of related data.
  • Execution order: Determines which statements execute and which values are ultimately written.

The main skill is learning to translate a control requirement into clear statements, verify the data and execution path, and confirm that the resulting behavior matches the machine's functional requirements.
