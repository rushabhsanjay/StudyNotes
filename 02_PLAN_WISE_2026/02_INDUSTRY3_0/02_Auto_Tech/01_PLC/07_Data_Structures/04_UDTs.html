1. Definition

A UDT (User-Defined Data Type) is a data type created by the programmer to group related data fields into one reusable structure.

A UDT allows a programmer to define the information associated with an object, such as a motor, robot, conveyor, sensor, drive, or production station.

For example, a motor may require several different types of data:

  • Start command: BOOL
  • Running feedback: BOOL
  • Fault status: BOOL
  • Speed feedback: REAL
  • Cycle count: DINT
  • Fault code: INT

Instead of maintaining unrelated variables for every motor, these fields can be grouped into a motor structure.

Conceptually:

Motor_Data
    Start_Command       : BOOL
    Running_Feedback    : BOOL
    Fault_Active        : BOOL
    Speed_RPM           : REAL
    Cycle_Count         : DINT
    Fault_Code          : INT

This defines the structure of the data. It does not, by itself, implement motor-control logic.

The exact terminology differs across PLC platforms. Siemens commonly uses PLC data types, Rockwell Logix uses user-defined data types, and Mitsubishi environments have their own mechanisms for structured data and labels.

2. Why Are UDTs Needed?

Consider a production line with 20 conveyor motors. Each motor requires a command, running status, fault status, speed, and cycle count.

Without a UDT, the program might use separate variables:

Conveyor01_Start_Command
Conveyor01_Running
Conveyor01_Fault
Conveyor01_Speed
Conveyor01_Cycle_Count

Conveyor02_Start_Command
Conveyor02_Running
Conveyor02_Fault
Conveyor02_Speed
Conveyor02_Cycle_Count

The same pattern would be repeated for every conveyor. Human beings have apparently never met a repetitive declaration they couldn't turn into a maintenance problem.

A UDT allows the common fields to be defined once and reused.

Conveyor01 : Motor_UDT
Conveyor02 : Motor_UDT
Conveyor03 : Motor_UDT

Each variable is an instance of the same user-defined type.

Benefits include:

  • Consistent data organization.
  • Less repetitive variable declaration.
  • Clearer program structure.
  • Easier reuse across similar equipment.
  • More systematic HMI and SCADA interfaces.
  • Easier maintenance and expansion.
  • Better integration with reusable function blocks.

A UDT does not automatically make the control logic reusable. It organizes the data. Reusable behavior is commonly implemented through functions, function blocks, routines, or other platform-specific program structures.

3. UDT vs Basic Data Type vs Array

These three concepts solve different problems.

3.1 Basic Data Type

A basic data type describes one value.

Examples:

Motor_Running : BOOL
Part_Count    : DINT
Pressure_Bar  : REAL

Each variable stores one value of its declared type.

3.2 Array

An array stores multiple elements of the same element type.

Example:

Motor_Running[0..19] : ARRAY OF BOOL

Conceptually, this represents the running status of 20 motors.

An array is useful when a collection contains repeated values of the same type.

3.3 UDT

A UDT defines multiple named fields that can have different data types.

Example:

Motor_UDT
    Start_Command    : BOOL
    Running_Feedback : BOOL
    Fault_Active     : BOOL
    Speed_RPM        : REAL
    Cycle_Count      : DINT

A UDT is useful when multiple fields describe one object.

3.4 Array of UDTs

These approaches can be combined.

Motors[0..19] : ARRAY OF Motor_UDT

Conceptually, this represents 20 motors, each with its own command, feedback, fault status, speed, and cycle count.

Concept Organizes Example
Basic type One value Motor_Running : BOOL
Array Repeated elements of one type Motor_Running[0..19]
UDT Different fields belonging to one object Motor_UDT
Array of UDTs Multiple objects with the same fields Motors[0..19]

This distinction is fundamental to structured PLC programming.

4. Anatomy of a UDT

Consider the following illustrative structure:

Motor_UDT
    Start_Command       : BOOL
    Stop_Command        : BOOL
    Running_Feedback    : BOOL
    Fault_Active        : BOOL
    Speed_Setpoint_RPM  : REAL
    Speed_Feedback_RPM  : REAL
    Cycle_Count         : DINT
    Fault_Code          : INT

A UDT has several important characteristics.

4.1 Type Name

Motor_UDT is the name of the type definition.

It identifies the common data layout that can be reused across multiple motor instances.

4.2 Members or Fields

Each named item within the structure is a member or field.

For example:

Speed_Feedback_RPM : REAL

This member stores a floating-point speed value.

4.3 Member Data Types

Each field has its own data type.

Member Type Purpose
Start_Command BOOL Start request
Stop_Command BOOL Stop request
Running_Feedback BOOL Running status
Fault_Active BOOL Fault indication
Speed_Setpoint_RPM REAL Requested speed
Speed_Feedback_RPM REAL Measured speed
Cycle_Count DINT Accumulated cycle count
Fault_Code INT Numeric fault code

4.4 Instances

A UDT definition describes the structure. An instance is a variable created using that type.

For example:

Motor01 : Motor_UDT
Motor02 : Motor_UDT
Motor03 : Motor_UDT

Each instance has its own set of member values.

Changing Motor01.Speed_Feedback_RPM does not automatically change Motor02.Speed_Feedback_RPM.

The instances are separate data objects, although a program could deliberately copy or share data between them.

5. Accessing UDT Members

A member is usually accessed through the instance name followed by the member name, using the syntax supported by the PLC language.

Conceptually:

Motor01.Start_Command
Motor01.Running_Feedback
Motor01.Speed_Feedback_RPM
Motor01.Cycle_Count

This form makes it clear which equipment and which property are being referenced.

For example, an HMI could display:

Motor01.Speed_Feedback_RPM
Motor02.Speed_Feedback_RPM
Motor03.Speed_Feedback_RPM

Alternatively, a program can pass the entire structure to a suitable function or function block if the platform supports that interface.

The exact member-access syntax differs by environment. The concept remains the same: an instance identifies the object, and a member identifies a field within that object.

6. UDTs in Different PLC Platforms

6.1 Siemens TIA Portal

Siemens supports PLC data types that can define structures containing multiple members.

A user-defined PLC data type can be reused to declare variables in data blocks, program interfaces, and other supported locations.

Conceptually:

Motor_UDT
    Start_Command       : BOOL
    Running_Feedback    : BOOL
    Speed_Feedback_RPM  : REAL
    Cycle_Count         : DINT

Instances can be declared using this data type.

Siemens programming commonly combines structured data with FBs and their instance data. This allows a reusable motor-control FB to process a well-defined set of motor parameters and status fields.

Important distinction: A UDT defines the data layout. An FB defines executable behavior and can maintain state through its instance data. They complement each other rather than replacing one another.

6.2 Rockwell Automation / Allen-Bradley Logix

Rockwell Logix controllers support User-Defined Data Types.

A UDT can group BOOL, integer, floating-point, and other supported fields into one structured tag.

For example, a controller tag could be declared using a type such as Motor_UDT.

Conceptually:

Motor01.Start_Command
Motor01.Running_Feedback
Motor01.Speed_Feedback_RPM
Motor01.Cycle_Count

Rockwell projects often use UDTs alongside Add-On Instructions (AOIs), which provide reusable behavior.

The UDT describes the data structure. An AOI defines reusable instruction behavior and its associated parameters and local data.

6.3 Mitsubishi PLCs

Mitsubishi PLC programming environments support structured data and user-defined data mechanisms, with exact capabilities depending on the PLC family and engineering software.

Labels can provide symbolic names, while structures can group related members where supported.

Do not assume that a structure definition, memory layout, or member-access syntax is identical between Mitsubishi, Siemens, and Rockwell platforms.

6.4 Platform Comparison

Feature Siemens Rockwell Logix Mitsubishi
Structured data PLC data types and structures User-Defined Data Types Supported structured data mechanisms, depending on platform
Reusable behavior FBs and functions AOIs, routines, and other program structures Platform-specific program and function mechanisms
Instance-based organization Common with FBs and DBs Common with structured tags and AOIs Depends on the selected platform
Exact syntax TIA Portal and CPU dependent Studio 5000 and controller dependent Engineering software and PLC family dependent

The transferable skill is understanding how to design and use structured data. Syntax and implementation details must be learned for the actual controller.

7. UDTs and Reusable Function Blocks

A UDT becomes particularly useful when paired with reusable control logic.

Suppose a standard motor-control function block needs these inputs:

  • Start request.
  • Stop request.
  • Fault feedback.
  • Reset request.

And these outputs:

  • Run command.
  • Running status.
  • Fault status.

The data associated with each motor can be organized into a structure, while the function block implements the control behavior.

Conceptually:

Motor01_Data : Motor_UDT
Motor02_Data : Motor_UDT

Motor_Control_FB
    processes Motor01_Data

Motor_Control_FB
    processes Motor02_Data

This illustrates the architectural idea, not a universal calling syntax.

The advantages include:

  • A consistent interface for similar equipment.
  • Less duplicated logic.
  • Easier testing of the control routine.
  • Easier expansion when another motor is added.
  • Better separation between data organization and control behavior.

The design must still specify which fields are inputs, outputs, retained states, or diagnostic values. Grouping them in a UDT does not automatically establish those responsibilities.

8. Practical Example: Conveyor Motor

Consider a conveyor motor with the following data requirements:

Member Type Purpose
Start_Request BOOL Request to start
Stop_Request BOOL Request to stop
Running_Feedback BOOL Motor running indication
Drive_Fault BOOL Drive fault indication
Speed_Setpoint_RPM REAL Requested speed
Speed_Feedback_RPM REAL Measured speed
Cycle_Count DINT Accumulated cycles
Fault_Code INT Fault identifier

Define a reusable type named Conveyor_Motor_UDT containing these fields.

Create instances:

CV1010_Motor : Conveyor_Motor_UDT
CV1020_Motor : Conveyor_Motor_UDT
CV1030_Motor : Conveyor_Motor_UDT

Now each conveyor has a consistent data structure.

For example:

CV1010_Motor.Speed_Setpoint_RPM = 1200.0
CV1020_Motor.Speed_Setpoint_RPM = 950.0
CV1030_Motor.Speed_Setpoint_RPM = 1100.0

The values are independent.

An HMI, diagnostic routine, or suitable reusable control block can reference the members associated with each conveyor.

In a real application, define whether the speed setpoint is expressed in motor RPM, drive frequency, percentage, or another engineering unit. A name and a REAL type alone do not establish the physical meaning of the value.

9. Nested Structures

Some PLC platforms support structures containing other structures.

For example:

Motor_UDT
    Command
        Start_Request
        Stop_Request
        Reset_Request

    Status
        Running
        Faulted
        Ready

    Measurements
        Speed_RPM
        Current_A

    Diagnostics
        Fault_Code
        Cycle_Count

This is a conceptual layout. Exact syntax and supported nesting depth vary by platform.

Nested structures can group fields by purpose:

  • Commands.
  • Status.
  • Measurements.
  • Diagnostics.

Member references become conceptually hierarchical:

Motor01.Command.Start_Request
Motor01.Status.Running
Motor01.Measurements.Speed_RPM
Motor01.Diagnostics.Fault_Code

This can improve readability for complex devices.

However, excessive nesting can make online monitoring, HMI configuration, or troubleshooting cumbersome. Use enough structure to express the system clearly, not enough to recreate a bureaucratic organization chart inside the PLC.

10. Arrays of UDTs

A powerful pattern is to create an array whose elements are UDT instances.

Suppose a line contains 12 similar motors.

Conceptually:

Motors[0..11] : ARRAY OF Motor_UDT

Each element contains all the fields defined by Motor_UDT.

For example:

Motors[0].Status.Running
Motors[0].Measurements.Speed_RPM

Motors[1].Status.Running
Motors[1].Measurements.Speed_RPM

The benefits are:

  • Repeated devices share one common data definition.
  • A single routine can process multiple instances.
  • The data layout remains consistent.
  • Device-level diagnostics become more systematic.
  • Expansion becomes easier when the number of similar devices changes.

The main engineering challenge is mapping each index to the correct physical device and ensuring the same type is appropriate for all instances.

If some motors have significantly different capabilities or interfaces, a single generic structure may need optional fields, separate types, or a different design.

11. UDTs and HMI/SCADA Integration

UDTs can simplify data exchange by organizing related values into a consistent object.

For example, a SCADA-facing motor record might contain:

Motor_UDT
    Commanded
    Running
    Faulted
    Speed_RPM
    Cycle_Count
    Fault_Code

A monitoring system can use these fields to present a consistent motor faceplate or dashboard.

However, several issues must be checked.

11.1 Data Type Compatibility

The receiving system must interpret each field using a compatible type.

For example, a DINT counter should not be treated as a 16-bit integer if its range can exceed the receiver's capacity.

11.2 Member Naming and Paths

Some communication methods expose structured members by symbolic paths. Others require a specific protocol mapping, data block layout, register mapping, or explicit serialization.

Do not assume that a UDT in one PLC automatically appears as the same structure in another system.

11.3 Layout and Versioning

Adding, removing, or reordering members may affect external interfaces, depending on how the data is exposed.

A change to a UDT used by HMI, SCADA, or robot communication should be treated as an interface change when it affects consumers.

Test dependent systems after modifying a shared type.

11.4 Engineering Units

A member named Speed_RPM should consistently represent RPM. A member named Pressure_Bar should represent bar.

Document units and scaling so that the same field is not interpreted differently by the PLC, HMI, SCADA, or database.

12. UDT Versioning and Change Management

UDTs are reusable definitions. Changing a shared definition can affect many variables and program blocks.

Suppose Motor_UDT is used by 30 motors and several HMI screens.

Adding a new member such as:

Maintenance_Required : BOOL

may require changes to:

  • The type definition.
  • The relevant control logic.
  • The initialization logic.
  • HMI or SCADA displays.
  • Communication mappings.
  • Test procedures.
  • Documentation.

The precise impact depends on the PLC environment and how the structure is used.

Good practice includes:

  1. Identify all instances and consumers of the type.
  2. Review data-layout and compatibility implications.
  3. Update dependent logic and interfaces.
  4. Compile and resolve errors.
  5. Test representative instances.
  6. Perform regression testing on affected functions.
  7. Document the change and deploy it using the site's change-control process.

A shared type is a useful engineering abstraction, but it also creates a dependency that must be managed.

13. Memory Considerations

A UDT consumes memory according to its members and the PLC's storage and alignment rules.

For a simple estimate, suppose a structure contains:

  • Four BOOL fields.
  • Two REAL fields.
  • One DINT field.
  • One INT field.

On a platform using 32-bit REAL and DINT, 16-bit INT, and allocating four Boolean fields in a total of four bytes, the approximate total would be:

  • Four BOOL fields: 4 bytes under this illustrative allocation.
  • Two REAL fields: 8 bytes.
  • One DINT field: 4 bytes.
  • One INT field: 2 bytes.

The sum is 18 bytes before any additional padding or alignment.

Actual memory usage may differ. Some platforms pack Boolean fields more efficiently; others impose alignment or additional storage requirements.

For an array of 100 such structures, the total memory footprint can become significant, especially when structures contain large buffers, strings, or nested arrays.

Use the controller's tools or documentation to verify the actual layout when memory use or external data layout matters.

14. Common UDT Design Mistakes

Mistake Consequence Prevention
Creating a generic type with unclear fields Developers interpret values differently Use meaningful names and descriptions
Mixing unrelated equipment data Structure becomes difficult to reuse Group fields by one device or functional purpose
Putting control behavior inside assumptions about the type Data organization is confused with executable logic Separate the UDT from the control routine or FB
Using incorrect member data types Overflow, precision loss, or invalid calculations Verify ranges, units, and data requirements
Modifying a shared UDT without impact analysis Dependent programs or interfaces break Review all instances and consumers
Using an array of UDTs without a documented index map Wrong device data is selected Document index-to-equipment mapping
Duplicating nearly identical UDT definitions Maintenance effort increases Reuse a common type when the devices genuinely share a schema
Over-nesting fields Online monitoring and troubleshooting become difficult Keep the hierarchy practical
Treating a UDT as a communication protocol External systems interpret the data incorrectly Define and verify the actual interface format
Omitting units and scaling rules Values are misunderstood by HMI or SCADA Document engineering units and representation

15. Best Practices

  • Create a UDT when multiple related fields describe one object or device.
  • Use consistent naming conventions for types and members.
  • Select data types based on the value's range, precision, and intended meaning.
  • Separate data organization from executable control behavior.
  • Use UDTs with reusable FBs or AOIs where supported and appropriate.
  • Consider arrays of UDTs for repeated devices with a common data model.
  • Define commands, feedback, status, diagnostics, and measurements clearly.
  • Document engineering units and scaling.
  • Keep structures focused rather than grouping unrelated data merely for convenience.
  • Assess compatibility before changing shared type definitions.
  • Verify the actual memory layout when external interfaces depend on offsets or data size.
  • Test representative instances and affected consumers after modifying a shared type.
  • Maintain clear ownership of fields, especially when several routines or tasks can write to the same structure.
  • Keep safety-related data and control functions within the required safety architecture and validation process.

16. Interview Questions and Answers

Q1. What is a UDT in PLC programming?

A UDT is a programmer-defined data type that groups related fields, potentially with different data types, into one reusable structure.

Q2. What is the difference between a UDT and an array?

An array stores repeated elements of one element type. A UDT defines a group of named fields that may use different data types.

Q3. What is an instance of a UDT?

An instance is a variable declared using the UDT definition. Each instance has its own member values.

Q4. What is the difference between a UDT and a function block?

A UDT defines data organization. A function block implements behavior and may maintain internal state. They are often used together.

Q5. Why use an array of UDTs?

It represents multiple similar objects, each with the same set of fields. This supports consistent data organization and reusable processing.

Q6. Can a UDT contain different data types?

Yes, subject to the PLC platform's supported structure features. For example, a motor structure may contain BOOL, INT, DINT, and REAL members.

Q7. What happens when a shared UDT changes?

The impact depends on the platform and how the type is used. Instances, program blocks, HMI/SCADA interfaces, and communication mappings may require updates and regression testing.

Q8. Does a UDT automatically control the equipment?

No. It organizes data. Executable logic must read and write the fields according to the control design.

Q9. Can a UDT be used in HMI and SCADA communication?

Often yes, but the interface must support the structure or provide an appropriate mapping. Type compatibility, member paths, data layout, and units must be verified.

Q10. When should a programmer avoid creating a UDT?

A UDT may be unnecessary for a single isolated value or when the proposed structure groups unrelated fields without a clear common purpose. Use structure when it improves consistency, reuse, and understanding.

17. Practical Exercises

Exercise 1: Create a Motor UDT

Create a simulated motor type with:

  • Start command: BOOL.
  • Running feedback: BOOL.
  • Fault status: BOOL.
  • Speed setpoint: REAL.
  • Speed feedback: REAL.
  • Cycle count: DINT.
  • Fault code: INT.

Create three instances and verify that each instance has independent values.

Exercise 2: Build an Array of UDTs

Create an array of five motor instances.

Assign different speeds, running states, and cycle counts. Use indexed access to read each motor's values and confirm that the indexes map to the intended simulated motors.

Exercise 3: Combine a UDT with Reusable Logic

Create a simple simulated motor-control routine that receives a start request and fault status and produces an appropriate command or status result.

Keep the data definition separate from the control behavior. Test normal, stopped, and faulted conditions in the simulator.

Exercise 4: Add a Diagnostic Member

Add a maintenance or diagnostic field to the motor structure.

Identify which program blocks, displays, and external interfaces must change. Compile and test the affected logic.

Exercise 5: Design a SCADA-Facing Structure

Create a structure containing motor status, speed, cycle count, and fault code.

Document the type, units, range, and source of every field. Verify that the intended receiving system can interpret the data correctly.

18. Final Mental Model

  • Basic data type: Defines one value.
  • Array: Stores multiple elements of one element type.
  • UDT: Defines a reusable group of named fields.
  • UDT instance: Holds the actual values for one object.
  • Array of UDTs: Organizes multiple similar objects using a common structure.
  • FB or AOI: Implements reusable behavior that can process structured data.

A well-designed UDT gives every similar device a consistent data model. Combined with reusable control logic, it makes large PLC applications easier to expand, troubleshoot, test, and maintain.
