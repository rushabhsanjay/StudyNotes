1. Definition

Data movement in a PLC is the process of transferring values between tags, registers, memory locations, arrays, or structures. Data conversion changes a value from one data type or representation to another.

These instructions operate primarily on data stored in the controller's memory. They do not directly change a physical process, although the transferred data may later be used to control motors, valves, robots, test equipment, or other devices.

For example, a PLC may receive a raw analog input, convert it to a floating-point value, scale it into bar, and transfer the result to a tag used by an HMI.

The three fundamental operations are:

  • Move: Transfer a value from one source to one destination.
  • Copy: Duplicate a value or a block of data from one memory area to another.
  • Convert: Change the data type or representation of a value.

2. Why Data Movement Is Required

Industrial PLC programs frequently need to move and convert data between different parts of a machine or control system.

Common applications include:

  • Transferring a part count into a batch counter.
  • Loading recipe parameters into an active production buffer.
  • Copying machine status values for diagnostics or reporting.
  • Converting integer analog input values into real numbers for calculations.
  • Transferring operator-entered setpoints from HMI tags into control tags.
  • Preparing values for communication with another PLC, a robot, a CNC, or a supervisory system.
  • Saving a snapshot of process values for fault investigation.

Example:

HMI_Setpoint
     |
     v
Validate_Setpoint
     |
     v
Active_Setpoint
     |
     v
Control_Logic

The PLC should not blindly apply every value received from an HMI or another controller. Validation matters because machines are very good at following incorrect instructions precisely.

3. The MOVE Instruction

3.1 What MOVE Does

A MOV or MOVE instruction transfers the value of a source operand into a destination operand.

General representation:

MOV(Source, Destination)

Example:

Source:      PartCount = 125
Destination: BatchCount = 0

Execute MOV

Result:
PartCount  = 125
BatchCount = 125

The source remains unchanged. The destination is overwritten with the source value whenever the instruction executes.

3.2 Important Characteristics

  • Normally transfers one scalar value per instruction.
  • The source is read and the destination is written.
  • The destination's previous value is replaced.
  • Source and destination data types must be compatible according to the PLC platform's rules.
  • Execution depends on the instruction's programming environment and conditions.
  • Moving a value does not automatically scale it, validate it, or make it physically meaningful.

For example, moving a raw analog value of 13824 into another integer tag produces 13824. It does not automatically convert that value into a pressure reading.

3.3 Ladder Logic Example

Suppose a machine has a completed-part counter and must capture its value when the batch is completed.

|----[ Batch_Complete ]----[ MOV PartCount BatchCount ]----|

When Batch_Complete enables the instruction:

PartCount  = 500
BatchCount = 500

If the instruction executes again after PartCount becomes 501, BatchCount becomes 501.

This is an important distinction: MOV is not inherently a one-time capture instruction. If the value must be captured only once, use an appropriate one-shot or edge-triggered condition, or another explicit sequence-control mechanism.

3.4 Common Applications

  • Transfer a completed-part count.
  • Apply a validated setpoint.
  • Copy a calculated value into a reporting tag.
  • Initialize a working variable.
  • Transfer a machine state or recipe identifier.

4. The COPY Instruction

4.1 What COPY Does

A copy operation duplicates data from a source memory area into a destination memory area. Depending on the PLC platform, it may copy a single value, an array, a structure, or a block of memory.

Example:

Source array:
Recipe_1 = [10, 20, 30, 40]

Destination array before copy:
Active_Recipe = [0, 0, 0, 0]

After copy:
Active_Recipe = [10, 20, 30, 40]

The source remains unchanged, while the corresponding destination elements are overwritten.

4.2 MOV Versus COP

On Rockwell Logix platforms, MOV is commonly used to transfer one value, while COP copies a specified amount of data from a source to a destination.

Feature MOV COP
Main purpose Transfer a value Copy a block of data
Typical use One count, setpoint, or state Arrays, structures, grouped data
Source modified? No No
Destination modified? Yes Yes
Length parameter Typically not required Required on Rockwell COP
Data compatibility Governed by instruction and operand types Governed by platform-specific copy and memory-layout rules

The distinction is not identical across every PLC brand. IEC Structured Text assignment, Siemens instructions, Mitsubishi instructions, and Rockwell instructions have different syntax and behavior.

4.3 Understanding COPY Length

On Rockwell Logix, COP uses a Length parameter. Its interpretation depends on the instruction and data types involved. For many Logix COP applications, the length represents the number of destination elements, not a byte count. Consult the controller's instruction reference before using it with mixed or structured data.

Consider this conceptual example:

Source array:
Recipe_Source[0..9]

Destination array:
Recipe_Active[0..9]

Requested copy:
10 elements

The destination must have sufficient capacity for the requested copy.

Common mistakes include:

  • Copying more elements than the destination can hold.
  • Using an incorrect length.
  • Assuming length always means bytes.
  • Copying between incompatible or differently laid-out data types.
  • Overlapping source and destination memory regions without checking the platform's rules.

A wrong length can cause incorrect values to be transferred or produce controller-specific errors. Never guess this parameter.

4.4 Copying a Recipe

Imagine a robotic station with a recipe containing weld parameters:

Recipe_Source:
    Weld_Current
    Weld_Time
    Clamp_Delay
    Robot_Program_ID

Active_Recipe:
    Weld_Current
    Weld_Time
    Clamp_Delay
    Robot_Program_ID

When the operator selects a recipe, the PLC can validate the selected recipe and copy its parameters into an active buffer.

A sensible sequence is:

Recipe_Selected
       |
       v
Check_Recipe_ID
       |
       v
Validate_Parameters
       |
       v
Copy_To_Active_Buffer
       |
       v
Confirm_Recipe_Ready

This avoids changing active machine parameters using an invalid or incomplete recipe.

4.5 Other Block Operations

Some platforms provide additional data-handling instructions.

  • BLKMOV: A block-move instruction name used in certain PLC environments. Its exact behavior is platform-specific.
  • FLL: On supported Rockwell Logix platforms, fills a specified number of destination elements with the same source value. It is not a normal copy of different source elements.
  • CPS: On supported Rockwell Logix platforms, performs a synchronous copy intended to help preserve data consistency when data may change asynchronously. Its availability and exact behavior depend on the controller and instruction reference.

These instructions are not interchangeable. A block copy, a fill operation, and a synchronous copy solve different problems.

5. Data Conversion

5.1 What Conversion Means

A conversion instruction changes how a value is represented or stored, such as converting an integer into a real number.

Common PLC data types include:

Data type General meaning Example
BOOL Boolean value TRUE, FALSE
SINT Small signed integer -10
INT Signed integer 250
DINT Wider signed integer 100000
UINT Unsigned integer 250
UDINT Wider unsigned integer 100000
REAL Floating-point number 12.5
LREAL Wider floating-point number on platforms that support it 12.123456789

The supported types, bit widths, ranges, and instruction names depend on the PLC family.

An integer normally stores whole-number values. A real type can represent fractional values, subject to floating-point precision limits.

5.2 Common Conversion Operations

Conversion Purpose Important consideration
INT to REAL Enable fractional calculations Large integers may not be represented exactly by the target floating-point type
DINT to REAL Use a wider integer value in real calculations Floating-point precision is finite
REAL to INT Convert a fractional value to an integer Rounding or truncation depends on the instruction
REAL to DINT Convert a real value to a wider integer Check rounding and range behavior
Signed to unsigned Change integer interpretation or representation Negative values require special attention
Integer to Boolean Convert or interpret data as a logical state Exact behavior is platform-specific

Illustrative Structured Text syntax on platforms supporting these conversion functions:

PressureReal := INT_TO_REAL(RawPressure);

Another example:

CountReal := DINT_TO_REAL(PartCount);

These function names are examples, not universal PLC syntax. For example, Rockwell Logix often uses instruction-based conversions or type handling that differs from Siemens SCL or other IEC programming environments.

5.3 Truncation and Rounding

Suppose:

ValueReal = 12.8

Converting this value to an integer may produce a different result depending on the instruction.

  • Truncation discards the fractional part, producing 12 for positive 12.8.
  • Rounding selects an integer according to the instruction's rounding rules, commonly producing 13 for 12.8.

Do not assume that every REAL-to-integer conversion rounds in the same way. Some instructions truncate, some round, and some provide separate operations.

Test the exact instruction used by the target controller.

5.4 Signed and Unsigned Conversion

Signed integers can represent negative and positive values. Unsigned integers represent non-negative values within their supported range.

For example:

Signed value:   -10
Unsigned type:  cannot represent -10 as a normal non-negative value

A conversion may reject the value, report an error, or produce a platform-specific result. Never rely on an out-of-range conversion to behave safely.

Also distinguish a numerical conversion from reinterpreting the same memory bits. These operations can produce very different results.

5.5 Overflow and Precision

Conversion can fail to preserve the original numerical value when the destination type has a smaller range or less precision.

Examples:

  • Converting a large DINT to a narrower integer can exceed the destination range.
  • Converting REAL to an integer can discard fractional information.
  • Converting a large integer to REAL can lose exact integer precision.
  • Converting a negative signed value to an unsigned type can produce unexpected results or an error.

The exact outcome depends on the PLC, instruction, and data types.

Best practice: validate the value against the destination's permitted range before converting it, especially for operator-entered values, recipe parameters, and data received over a network.

6. Conversion Is Not Scaling

This distinction is essential in analog processing.

Conversion changes the data type or representation. Scaling changes the numerical range or meaning of a value.

Suppose a pressure transmitter is connected to an analog input module. The PLC receives an illustrative raw value of 13824, where the configured raw range is 0 to 27648 for a pressure range of 0 to 10 bar.

Step 1: Convert the raw integer

RawPressure : INT = 13824

RawPressureReal := INT_TO_REAL(RawPressure);

The result is:

RawPressureReal = 13824.0

Only the data type has changed. The pressure is not yet 5 bar.

Step 2: Scale into engineering units

The general linear scaling equation is:

\[ EU = \frac{Raw - Raw\_{\min}}{Raw\_{\max}-Raw\_{\min}} \times (EU\_{\max}-EU\_{\min}) + EU\_{\min} \]

For the illustrative ranges above:

\[ PressureBar = \frac{13824-0}{27648-0}\times 10 \]
\[ PressureBar = 5.0 \]

Illustrative Structured Text:

RawPressureReal := INT_TO_REAL(RawPressure);

PressureBar :=
    (RawPressureReal / 27648.0) * 10.0;

The syntax of the conversion function may differ by platform, but the mathematical principle remains the same.

Why convert before dividing?

If the calculation uses integer operands, integer division may discard the fractional part.

For example:

13824 / 27648

In an integer-arithmetic context, this may evaluate to 0, depending on the language and operand types. Multiplying that result by 10 would give an incorrect pressure value.

By converting to a floating-point type and using floating-point constants, the calculation can preserve the fractional ratio.

Engineering precautions

  • Confirm the analog module's actual raw range and configuration.
  • Check for under-range, over-range, wire-break, and module-fault conditions where supported.
  • Validate the raw value before using it.
  • Use suitable numerical precision.
  • Decide deliberately whether an out-of-range value should be rejected, alarmed, or clamped.
  • Do not automatically clamp diagnostic data if doing so would hide a sensor or wiring fault.

The example range is illustrative. Actual module values vary by hardware, configuration, and signal type.

7. Data Movement in Different PLC Programming Environments

7.1 Ladder Logic

In ladder logic, a movement or conversion instruction typically executes when its enabling logic is satisfied.

Conceptually:

|----[ Recipe_Valid ]----[ MOV HMI_Setpoint Active_Setpoint ]----|

If the rung is true, the instruction executes according to the platform's semantics.

A continuously true rung may execute repeatedly. If another part of the program writes a different value to Active_Setpoint, the final value may depend on execution order and which instruction writes last.

7.2 Structured Text

In IEC-style Structured Text, simple assignment is often sufficient:

BatchCount := PartCount;

An explicit conversion may look like:

PressureReal := INT_TO_REAL(RawPressure);

A scaling calculation can then use the converted value.

Unlike a conditionally enabled ladder instruction, a Structured Text assignment runs whenever execution reaches that statement. If it is inside a continuously executing task, it may execute every scan or task cycle.

7.3 Vendor Examples

Platform or environment Typical concepts Important note
Rockwell Logix MOV, COP, CPS, FLL, conversion instructions, CPT Verify instruction availability and exact operand/length rules for the controller
Siemens S7 / TIA Portal MOVE, SCL assignment, conversion functions, block/array operations Exact syntax and supported instructions depend on CPU and programming environment
Mitsubishi PLCs Data transfer and conversion instructions, device/register operations Mnemonics and operand rules vary by CPU family and software
IEC Structured Text Assignment using :=, typed conversion functions Function names and implicit conversion rules vary by implementation

Do not assume that identical-looking instruction names have identical behavior across vendors.

8. Data Consistency and Synchronous Copying

A copy operation can transfer data while another task, controller, or communication process is updating the source.

Imagine a structure containing:

Machine_Status:
    Cycle_Number
    Robot_Ready
    Fault_Code
    Part_ID

If these fields are updated at different times, a copy might capture a mixture of old and new values, depending on the platform, data layout, and execution context.

This matters when copying:

  • Structures containing related status fields.
  • Data updated by another task or communication connection.
  • Controller-produced data used by an HMI or another PLC.
  • Recipe parameters that must be applied as a consistent set.

COP and CPS on Rockwell Logix

On supported Rockwell Logix controllers, COP and CPS differ in how the copy operation handles consistency in the presence of asynchronous updates. CPS is designed to provide a synchronous copy for supported cases, reducing the risk of obtaining inconsistent data during the copy.

However, it is not a universal instruction or a blanket guarantee that every multi-step application is transactionally consistent. Check the specific controller manual and data-update mechanism.

For other platforms, use the corresponding documented mechanism, such as a suitable synchronization method, sequence handshake, validated buffer, or platform-specific consistent-data operation.

9. Retentive Data and Restart Behavior

Moving or copying a value does not itself determine whether that value survives a power cycle or controller restart.

Retention depends on factors such as:

  • PLC memory and tag configuration.
  • Retentive versus non-retentive variables.
  • Startup initialization logic.
  • Controller mode and restart behavior.
  • Download, reset, or project-change procedures.
  • Platform-specific memory rules.

Example:

Batch_Target := 500;

Even if this value is transferred successfully, the value after a restart depends on the destination's retention settings and startup logic.

For critical production parameters, define the intended behavior explicitly:

  • Should the active recipe be retained?
  • Should a batch counter resume or reset?
  • Should setpoints be restored from a validated saved recipe?
  • Should machine outputs remain inhibited until initialization and validation are complete?

Do not assume that a value remains valid merely because it was valid before the restart.

11. Common Faults and Troubleshooting

Symptom Likely cause What to check
Destination does not change Instruction is not enabled or executed Rung condition, task execution, mode, and instruction status
Destination changes repeatedly Instruction executes every scan or task cycle Execution conditions and event-trigger logic
Correct source, incorrect destination Wrong type, conversion, or copy length Source and destination declarations
Fractional value disappears Integer arithmetic or conversion truncation Operand types and conversion instruction
Negative value becomes unexpected Signed/unsigned mismatch Data type and conversion rules
Values exceed the permitted range Overflow or out-of-range conversion Source limits and destination capacity
Recipe fields are mixed or inconsistent Source changes during the copy Update timing, buffer strategy, and synchronization
Array values appear shifted or incomplete Wrong length, indexing, or layout Element count, array bounds, and structure layout
Destination unexpectedly returns to an old value Another instruction writes to the same tag Cross-reference all writers and inspect execution order
Engineering value is incorrect Wrong scaling range, units, or raw input configuration Raw range, engineering range, and formula
Value changes after restart Retention or initialization behavior Memory configuration and startup logic

Practical troubleshooting sequence

  1. Monitor the source tag online.
  2. Confirm that the instruction's execution condition is satisfied.
  3. Monitor the destination immediately before and after execution.
  4. Verify the source and destination data types.
  5. Check conversion rules, numerical limits, and scaling units.
  6. For block operations, verify length, element types, array bounds, and structure layout.
  7. Search for other instructions or routines writing to the same destination.
  8. Test restart and retention behavior separately from normal execution.

This sequence isolates the cause without changing five unrelated things at once, a popular industrial troubleshooting tradition that solves little and creates new mysteries.

12. Best Practices

  • Use descriptive tag names that indicate purpose, data type where helpful, and engineering units where relevant.
  • Use explicit type conversion before calculations when implicit conversions could produce incorrect results.
  • Validate values before transferring them into active control parameters.
  • Check destination limits before converting to a narrower or unsigned data type.
  • Confirm the meaning of the copy-length parameter in the relevant PLC manual.
  • Avoid copying large arrays or structures unnecessarily every scan.
  • Keep ownership of destination tags clear. Prefer one deliberate writer for each control value wherever practical.
  • Use a temporary buffer and a controlled commit sequence when applying multi-parameter recipes.
  • Add validity checks, range checks, and suitable fault handling to data received from HMIs, robots, CNCs, and other controllers.
  • Verify retention and startup behavior rather than assuming memory will preserve a value.
  • Use safety-rated logic and communication where required. Ordinary data movement is not a substitute for a safety-rated function.
  • Test conversions at normal, boundary, negative, and out-of-range values before commissioning.

13. Interview Questions and Answers

Q1. What is the difference between MOV and COP?

MOV typically transfers one value from a source to a destination. On Rockwell Logix, COP copies a specified amount of data and is commonly used for arrays and structures. Exact behavior depends on the PLC platform.

Q2. Does MOV change the source value?

No. A normal move operation reads the source and writes the destination. The source remains unchanged unless another instruction modifies it.

Q3. What happens when MOV executes repeatedly?

The destination is overwritten each time the instruction executes. If the source changes, the destination can follow the source.

Q4. What is data conversion?

Data conversion changes the data type or representation of a value, such as converting an integer to a floating-point number.

Q5. What is the difference between conversion and scaling?

Conversion changes the data type or representation. Scaling mathematically maps a value from one range to another, often from raw sensor counts to engineering units.

Q6. Why convert an integer to REAL before scaling?

To allow fractional arithmetic and avoid unintended integer division or loss of fractional information.

Q7. What can happen when REAL is converted to INT?

The fractional component may be truncated or rounded according to the specific instruction. Out-of-range values can also produce platform-specific results or errors.

Q8. Why might a copied structure contain inconsistent data?

The source may be updated asynchronously while the copy occurs. A suitable synchronous copy, validated buffer, or synchronization strategy may be required.

Q9. Why is copy length important?

The length determines how much data is copied. An incorrect value can result in incomplete or unintended data transfer and may cause errors depending on the platform.

Q10. Does MOV guarantee that a value survives a power cycle?

No. Retention depends on the memory or tag configuration and startup behavior, not merely on the move instruction.

Q11. What is the difference between copying and filling?

Copying transfers the source data pattern into the destination. A fill operation writes the same value repeatedly into multiple destination elements.

Q12. How would you troubleshoot a destination tag that keeps changing unexpectedly?

Monitor the tag online, identify all instructions and routines that write to it, check their execution conditions and order, and determine whether another writer or startup routine is overwriting the value.

14. Practical Exercises

Perform these exercises in a PLC simulator or a safe offline test project before applying the logic to a live machine.

Exercise 1: Move a batch target

Create these tags:

HMI_Batch_Target : INT
Active_Batch_Target : INT

Test the following:

  • Set HMI_Batch_Target to 500.
  • Execute a move into Active_Batch_Target.
  • Change the HMI value to 600.
  • Observe whether the destination updates again.
  • Add a validation condition that permits only an acceptable target range.

Exercise 2: Copy recipe data

Create a source array and a destination array with several simulated recipe values.

  • Copy the source into the destination.
  • Change one source element and verify that the copied destination does not change until the copy executes again.
  • Test an incorrect copy length in a safe simulator.
  • Verify the actual length semantics for the chosen PLC platform.

Exercise 3: Convert and scale pressure

Create:

RawPressure : INT
RawPressureReal : REAL
PressureBar : REAL

Use simulated raw values corresponding to the illustrative 0 to 27648 range.

Raw input Expected pressure
0 0 bar
6912 2.5 bar
13824 5 bar
20736 7.5 bar
27648 10 bar

Test values below 0 and above 27648 as well. Decide how the program should distinguish an invalid sensor value from a valid value that is merely outside the nominal range.

Exercise 4: Test execution and retention

  • Execute a move under a continuously true condition.
  • Change the source value and observe the destination.
  • Introduce a second writer in the test project and identify which write determines the final value.
  • Test restart behavior and inspect the configured retention and initialization logic.

15. Final Mental Model

Remember these distinctions:

  • MOV: Transfer a value into a destination.
  • COPY: Duplicate a block or collection of data.
  • CONVERT: Change a value's data type or representation.
  • SCALE: Change the numerical range or engineering meaning.
  • VALIDATE: Decide whether a value is acceptable for its intended use.
  • SYNCHRONIZE: Ensure related data is captured or applied consistently.

A robust PLC program does not simply move data. It moves the correct data, with compatible types, within valid ranges, at the correct time, into a clearly owned destination.
