1. Definition

Timers and counters are PLC instructions used to monitor elapsed time and count events. They allow a PLC program to respond not only to whether a condition is TRUE, but also to how long it remains TRUE or how many times an event occurs.

Timers are used for operations such as:

  • Delaying a conveyor start.
  • Detecting a clamp that takes too long to close.
  • Keeping a cooling fan running after a machine stops.
  • Monitoring robot cycle duration.
  • Generating time-based alarms.

Counters are used for operations such as:

  • Counting components passing a sensor.
  • Counting completed welding cycles.
  • Tracking rejected parts.
  • Counting machine operations for maintenance.
  • Stopping a batch after a specified production quantity.

The four fundamental instructions in this topic are:

Instruction Full name Primary purpose
TON Timer On-Delay Delays the timer's done condition after its input becomes TRUE
TOF Timer Off-Delay Delays the timer's done condition turning FALSE after its input becomes FALSE
CTU Count Up Increments a count when qualifying count-up events occur
CTD Count Down Decrements a count when qualifying count-down events occur

Instruction names and exact behavior can vary across PLC platforms. The principles below describe common IEC-style and industrial PLC implementations.

2. Understanding a PLC timer

A timer measures elapsed time according to its configured timing behavior.

Common timer parameters include:

Parameter Meaning
IN or rung condition Condition that enables or controls the timer
PT or preset Configured time interval
ET or accumulated time Elapsed time measured by the timer
Q or DN Done status, indicating the timer's completion condition
RESET Clears timer state when supported or required by the implementation

Not every PLC uses the same names. For example, IEC-style timers commonly use IN, PT, ET, and Q, while Allen-Bradley Logix timers commonly expose members such as PRE, ACC, EN, TT, and DN.

Example

Assume a conveyor should start only after a sensor remains active for three seconds.

  • Preset: 3 seconds.
  • Timer input: sensor active.
  • Done condition: timer has completed its delay.

Conceptually:

Sensor becomes TRUE
        |
        v
Timer starts accumulating
        |
        | 3 seconds elapsed
        v
Timer done = TRUE
        |
        v
Conveyor start permitted

If the sensor becomes FALSE before the timer finishes, a TON timer normally resets its elapsed time and done status. This behavior is useful for filtering brief signals, but it is not automatically a substitute for a properly engineered input filter or safety function.

3. TON: Timer On-Delay

TON delays the activation of its done condition after its input becomes TRUE.

It is one of the most frequently used PLC timer instructions.

3.1 Operating sequence

Assume:

  • Timer preset = 5 seconds.
  • Input becomes TRUE at time \(t=0\).
Elapsed time since input activation Timer input Accumulated time Done status
0 seconds TRUE Starts at 0 FALSE
1 second TRUE Approximately 1 second FALSE
3 seconds TRUE Approximately 3 seconds FALSE
4.9 seconds TRUE Approximately 4.9 seconds FALSE
5 seconds or later TRUE Reaches preset TRUE

The exact timing resolution and update behavior depend on the controller, task execution, and timer implementation.

If the input becomes FALSE before the preset is reached, a conventional non-retentive TON resets.

3.2 Conceptual Ladder Logic

|----[ SensorActive ]----[ TON T1, PRE = 5 s ]----|

|----[ T1.DN ]--------------------( ConveyorPermit )----|

The diagram is conceptual. Actual timer instruction placement and syntax depend on the PLC platform.

3.3 Practical industrial applications

Application A: Conveyor start delay

After a start request, wait two seconds before enabling the conveyor.

Purpose: allow an upstream process or associated equipment to prepare.

Application B: Clamp timeout

After commanding a clamp to close, start a timer. If ClampClosed does not become TRUE within the allowed interval, raise a fault.

Important: a timeout must detect failure. It must not simply force the sequence forward as if the clamp had closed.

Application C: Signal qualification

Require a sensor signal to remain active for a specified interval before accepting it.

This can reject brief fluctuations, but excessive delay may hide legitimate short events.

3.4 TON timing versus watchdog timing

A TON timer measures an application-level interval. A PLC watchdog monitors controller execution time.

They are different mechanisms and should not be confused.

4. TOF: Timer Off-Delay

TOF delays the deactivation of its done condition after its input becomes FALSE.

A common use is keeping an output active for a period after the initiating condition disappears.

4.1 Operating sequence

Assume a TOF preset of 10 seconds.

  1. Timer input becomes TRUE.
  2. Done status becomes TRUE according to the timer's normal operating behavior.
  3. Timer input becomes FALSE.
  4. The off-delay interval begins.
  5. Done status remains TRUE during the interval.
  6. When the interval expires, done status becomes FALSE.

Conceptually:

Timer input:  ____|----------------|____________
                                Input becomes FALSE

Timer done:   ____|----------------------|______
                                10-second delay

This is a simplified timing diagram. It illustrates the common TOF behavior, not every vendor's exact execution semantics.

4.2 Conceptual Ladder Logic

|----[ MachineRunning ]----[ TOF T2, PRE = 10 s ]----|

|----[ T2.DN ]--------------------( CoolingFanCommand )----|

Under the illustrated behavior, the cooling fan command remains active for the off-delay interval after MachineRunning becomes FALSE.

4.3 Practical applications

  • Cooling fan run-on after a machine stops.
  • Exhaust ventilation run-on after a process ends.
  • Maintaining an indicator briefly after an event.
  • Delayed deactivation of a non-safety process command.

TOF is not suitable as a substitute for a required immediate safety stop. Safety-related stopping behavior must be designed through the appropriate safety system.

5. TON versus TOF

Feature TON TOF
Main behavior Delays done-status activation Delays done-status deactivation
When input becomes TRUE Timing begins Done status normally becomes TRUE
When input becomes FALSE Conventional non-retentive timer resets Off-delay interval begins
Typical application Start delay, qualification, timeout monitoring Fan run-on, delayed process deactivation
Key question Has the input remained TRUE long enough? Has enough time passed since the input became FALSE?

A simple memory aid:

  • TON: Wait before turning the done condition ON.
  • TOF: Wait before turning the done condition OFF.

Always verify the target PLC's timer behavior, particularly when translating programs between IEC-style timers and vendor-specific instructions.

6. Timer status bits and accumulated time

Timers often expose status information that helps diagnose sequence problems.

In an Allen-Bradley Logix-style timer, common members include:

  • PRE: preset value.
  • ACC: accumulated value.
  • EN: enable status.
  • TT: timer timing status.
  • DN: done status.

In IEC-style timer function blocks, common members include:

  • IN: input condition.
  • PT: preset time.
  • ET: elapsed time.
  • Q: output status.

The names are not interchangeable without checking the platform.

Example: clamp timeout

Assume the clamp should close within four seconds.

Signal Expected behavior
ClampCommand Becomes TRUE when the clamp step starts
ClampClosed Becomes TRUE when closed position is confirmed
ClampTimer Accumulates time while the close operation is waiting
ClampTimer.DN or equivalent Indicates the timer has reached its preset
ClampTimeoutFault Becomes TRUE if timeout occurs before successful confirmation

The fault condition should distinguish between a successful closure and a timeout. For example, a timeout fault may be evaluated when the timer expires while ClampClosed remains FALSE.

A production implementation also needs correct timer reset behavior and a defined fault recovery strategy.

7. CTU: Count Up

CTU increments a count when it detects a qualifying count-up event.

Typical applications include:

  • Counting components on a conveyor.
  • Counting completed production cycles.
  • Counting robot operations.
  • Tracking rejected parts.
  • Counting maintenance events.

7.1 Common counter parameters

Parameter Meaning
CU or count input Input used to increment the counter
PV or preset Target count
CV or accumulated count Current count
Q or DN Status indicating the preset condition has been reached
R or reset Clears the accumulated count according to the implementation

Some platforms use names such as PRE, ACC, and DN instead.

7.2 Example: count 100 components

Assume a photoelectric sensor detects each component passing a conveyor.

Photoelectric sensor
        |
        v
Qualifying count event
        |
        v
CTU counter increments
        |
        v
Current count reaches 100
        |
        v
BatchComplete = TRUE

Conceptual instruction:

CTU:
    CountInput = PartDetected
    Preset      = 100
    CurrentCount = accumulated value
    Done         = TRUE when preset is reached

This is pseudocode, not portable PLC syntax.

7.3 Why edge detection matters

A sensor may remain TRUE while a component is in front of it for several PLC scans.

A counter should normally count the intended event, not every scan during which the sensor remains active.

Many PLC counters increment on a qualifying false-to-true transition of their count input. Other implementations or programming patterns may differ.

For a typical edge-triggered CTU:

Sensor:  ______|‾‾‾‾‾‾‾|________
               Rising edge

Count:   0     1                  1

The sensor remains active for several scans, but only one qualifying rising edge increments the count.

If two components pass without the sensor signal returning FALSE between them, the counter may register only one event. Sensor placement, signal conditioning, pulse capture, and high-speed counting requirements must be considered.

8. CTD: Count Down

CTD decrements a count when it detects a qualifying count-down event.

It is commonly used when tracking a remaining quantity.

Examples:

  • Counting down components remaining in a batch.
  • Tracking items remaining in a transfer sequence.
  • Counting remaining operations before maintenance.
  • Managing a defined number of cycles.

8.1 Example: remaining batch quantity

Suppose a production order requires 50 components.

Initial remaining quantity:

\[ RemainingCount=50 \]

Each qualifying component event decrements the count.

Completed components Remaining count
0 50
1 49
10 40
25 25
49 1
50 0

When the configured zero or terminal condition is reached, the program can indicate that the required quantity has been processed.

The exact done-status behavior depends on the counter instruction and platform.

8.2 Important distinction

CTD behavior is not identical across every PLC implementation. Some IEC-style and vendor-specific counters initialize or evaluate their values differently, and the count input may use edge detection.

Do not assume every CTD automatically begins at its preset. Initialize its starting value explicitly according to the target platform's documented behavior.

9. CTU versus CTD

Feature CTU CTD
Main operation Increments count Decrements count
Typical purpose Track completed events Track remaining quantity
Example Components produced Components remaining
Input behavior Often counts qualifying rising edges Often decrements on qualifying count events
Initialization Define starting count and reset behavior Define starting count and load behavior
Terminal condition Preset reached or exceeded, depending on implementation Zero or another configured terminal condition

A CTU is often useful for answering, "How many have we produced?"

A CTD is often useful for answering, "How many remain?"

10. Counter reset and initialization

Counter initialization is a common source of mistakes.

Consider a production counter with a preset of 100 components.

Questions that must be answered in the design:

  • Does the counter start at zero?
  • When does a new batch begin?
  • Which condition resets the count?
  • Can an operator reset the counter during production?
  • What happens after a PLC restart?
  • Is the count retained in memory?
  • Can a sensor event be counted twice?
  • What happens if the sensor stays TRUE across a reset?

A reset should be controlled by a clearly defined condition.

Conceptual example:

IF NewBatchConfirmed THEN
    ResetProductionCounter
END_IF

This is pseudocode. Actual reset instructions differ by platform.

For a production system, protect batch resets against accidental activation and maintain a separate production record if the count is important for traceability.

11. Combining timers and counters

Timers and counters are frequently used together.

Example A: count components and stop after a batch

Requirements:

  • Count each component.
  • Stop the batch after 100 components.
  • Allow a short delay before deactivating a process command.

Conceptual sequence:

Component detected
       |
       v
CTU increments
       |
       v
Count reaches 100
       |
       v
BatchComplete = TRUE
       |
       v
TON or TOF handles the required process delay
       |
       v
Process command changes state

The choice between TON and TOF depends on whether the required delay is before activation or after deactivation.

Example B: detect a stalled conveyor

Requirements:

  • Conveyor is commanded to run.
  • A sensor should detect components within a defined interval.
  • If no qualifying event occurs in time, generate a fault.

Conceptual approach:

  1. Start or enable a monitoring timer when the conveyor runs.
  2. Reset or restart the monitoring interval when the expected event occurs.
  3. If the interval expires without the event, set a stall or no-product fault.
  4. Define the required fault response and recovery.

This pattern must be designed carefully. A production gap does not necessarily indicate a conveyor fault if the process legitimately has no components to transfer.

Example C: maintenance interval

A counter tracks completed machine cycles. When the configured count is reached, a maintenance-due flag is set.

For example:

CycleComplete rising edge
          |
          v
Maintenance CTU increments
          |
          v
Count reaches configured limit
          |
          v
MaintenanceDue = TRUE

A maintenance counter should have an explicit reset or acknowledgement procedure and appropriate retention behavior.

12. Timer and counter accuracy

Timer and counter instructions are software constructs, but their accuracy depends on the controller and the signals being monitored.

Timer considerations

  • PLC task period and scheduling.
  • Timer resolution and update behavior.
  • Input filtering.
  • Whether the timer is retentive or non-retentive.
  • Whether the timer resets when the enabling condition becomes FALSE.
  • Correct handling of step entry and exit.

Counter considerations

  • Sensor pulse duration.
  • Scan time and input update rate.
  • Edge-detection behavior.
  • Input filtering and debounce.
  • Counter range and data type.
  • High-speed input requirements.
  • Counter reset and initialization behavior.

For high-speed production counting, a standard scan-based counter may not reliably detect every short pulse. A high-speed counter module or appropriate hardware-supported feature may be necessary.

13. Common timer and counter faults

Symptom Possible cause What to check
TON never completes Input does not remain TRUE long enough Monitor input, accumulated time, and reset behavior
TON resets unexpectedly Enabling condition briefly becomes FALSE Check sensor stability and all conditions feeding the timer
TOF output turns OFF too early Incorrect configuration or misunderstanding of the instruction semantics Verify input transition, preset, and timer status
Timer completes immediately Preset is zero, wrong time units, or accumulated state is unexpected Check preset, units, initialization, and instruction type
CTU counts multiple times Input signal repeatedly transitions or counting logic is not edge-qualified Monitor sensor waveform and count input
CTU misses parts Pulses are too short or multiple parts do not create separate edges Check sensor placement, filtering, scan time, and high-speed counter requirements
CTD starts with an unexpected value Initial value or load behavior is incorrect Check initialization and documented counter semantics
Counter does not reset Reset condition is FALSE or reset instruction is not executing Monitor reset logic and counter state
Count changes after restart Retentive behavior or startup logic differs from expectations Check memory configuration and initialization
Batch completes at the wrong quantity Wrong preset, incorrect count source, duplicate events, or reset race Verify the preset and trace each qualifying event

14. Best practices

  • Use meaningful timer and counter names, such as ClampCloseTimer, RobotCycleTimer, and ProductionCount.
  • Document the preset value, units, and engineering reason for each timer.
  • Use feedback signals to confirm physical operations.
  • Treat a timeout as a fault-detection condition, not proof that the operation completed.
  • Check whether a counter counts rising edges, level conditions, or another qualifying event.
  • Define reset and initialization behavior explicitly.
  • Avoid resetting production counts without authorization and traceability.
  • Consider hardware-supported high-speed counting for fast sensor pulses.
  • Test timers and counters under normal operation, signal loss, restart, and fault recovery.
  • Verify platform-specific timer and counter behavior before porting code between PLC families.

15. Interview questions and answers

Q1. What is TON?

TON is an on-delay timer. It delays its done condition becoming TRUE until the configured interval has elapsed while its enabling condition remains satisfied.

Q2. What is TOF?

TOF is an off-delay timer. It delays the done condition becoming FALSE after its input becomes FALSE.

Q3. What is the difference between TON and TOF?

TON delays activation of the done condition. TOF delays deactivation of the done condition.

Q4. What is CTU?

CTU is a count-up instruction that increments a counter on qualifying count events.

Q5. What is CTD?

CTD is a count-down instruction that decrements a counter on qualifying count events.

Q6. Why is edge detection important for counters?

A sensor can remain TRUE across multiple PLC scans. Edge-based counting prevents a single sustained signal from being counted repeatedly, provided the signal produces the required transitions.

Q7. Why might a PLC miss components on a fast conveyor?

The input pulses may be too short for the configured scan-based logic, or the sensor may not return FALSE between consecutive parts. Input filtering, scan timing, sensor geometry, and high-speed counter support must be checked.

Q8. What is the difference between a timer timeout and a completed operation?

A timeout indicates that a time limit has been reached. Operation completion must be confirmed by the required feedback or completion condition.

Q9. What is the difference between accumulated time and preset time?

Preset time is the configured target interval. Accumulated time is the elapsed time measured by the timer.

Q10. Why must timer and counter initialization be designed explicitly?

Incorrect initialization or retention behavior can cause premature timeouts, incorrect production counts, or unexpected machine behavior after restart.

16. Practical exercise

Build an offline training program for a conveyor that produces a batch of 20 components.

Required tags:

  • ConveyorCommand
  • PartSensor
  • BatchStart
  • BatchComplete
  • ProductionCount
  • RemainingCount
  • ConveyorStartTimer
  • NoPartTimeout
  • ProcessFault

Test these scenarios:

  1. Use TON to delay the conveyor command by two seconds after a valid start request.
  2. Use TOF to keep a simulated cooling fan command active for five seconds after the conveyor stops.
  3. Use CTU to count 20 components.
  4. Use CTD to track the remaining quantity from 20 down to zero.
  5. Reset the counters when a new batch is confirmed.
  6. Simulate a sensor that remains TRUE for several scans and verify that one component is counted only once.
  7. Simulate a missing component event and generate a timeout fault.
  8. Simulate a PLC restart and verify the intended timer, counter, and batch initialization behavior.

Record the input state, timer accumulated value, timer done status, counter value, and fault status for each test.

17. Final mental model

  • TON: Wait before the done condition becomes TRUE.
  • TOF: Wait before the done condition becomes FALSE.
  • CTU: Count qualifying events upward.
  • CTD: Count qualifying events downward.
  • Preset: The configured time or count target.
  • Accumulated value: The current elapsed time or count.
  • Done status: Indicates that the instruction's completion condition has been reached.
  • Reset and initialization: Determine how the instruction returns to its starting state.
  • Edge detection: Helps count discrete events instead of repeatedly counting a sustained signal.
  • Timeout: Detects that an expected event has not occurred within the permitted interval.

For maintenance work, the most useful diagnostic habit is to monitor the timer or counter's input, preset, accumulated value, and status together. That quickly distinguishes a bad sensor signal from incorrect timer configuration or faulty sequence logic.
