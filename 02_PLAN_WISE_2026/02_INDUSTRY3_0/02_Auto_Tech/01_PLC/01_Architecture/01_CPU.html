1. Definition

A Central Processing Unit (CPU) is the processing unit of a Programmable Logic Controller (PLC). It executes the control program, evaluates logic, processes data, manages operating modes, and coordinates communication with the PLC's I/O modules and other devices.

In industrial automation, the CPU determines how the PLC responds to field signals, sequence conditions, timers, counters, alarms, and commands.

For example, in a robotic welding line, the CPU may evaluate whether a part is present, the fixture is clamped, the robot is ready, and the safety system permits operation before allowing the next sequence step.

The CPU executes the control logic, but it cannot guarantee that the physical machine behaves as commanded. Sensors, wiring, I/O modules, actuators, drives, networks, and mechanical systems must also operate correctly.

2. Main functions of a PLC CPU

Function Description Industrial example
Program execution Executes the user control program Runs conveyor sequencing logic
Input processing Makes input states available to the control program Reads clamp-closed confirmation
Logic evaluation Evaluates Boolean conditions, instructions, and expressions Checks robot-ready and fixture-clamped conditions
Output control Updates output commands according to program execution and platform behavior Commands a contactor or solenoid
Data processing Performs calculations and manipulates variables Scales a pressure measurement
Timing and counting Executes timer and counter instructions Monitors conveyor dwell time
Diagnostics Detects and reports supported hardware, program, and communication faults Reports an I/O module fault
Communication Exchanges data with HMIs, drives, remote I/O, robots, and supervisory systems Receives drive status over EtherNet/IP
Mode management Controls whether the user program executes and whether modifications are permitted RUN versus PROGRAM mode

The exact functions, scheduling, and execution behavior depend on the PLC family and configuration.

4. How the CPU executes a PLC program

Many PLCs use a cyclic execution model, often called the scan cycle. However, modern controllers can also execute periodic, event-triggered, interrupt-driven, and independently scheduled tasks.

A simplified cyclic model is:

START SCAN
    |
    v
READ / UPDATE INPUT DATA
    |
    v
EXECUTE CONTROL PROGRAM
    |
    v
UPDATE OUTPUT DATA
    |
    v
COMMUNICATIONS AND SYSTEM TASKS
    |
    v
REPEAT

The exact order varies by controller. Some systems update I/O asynchronously, use immediate I/O instructions, or execute multiple tasks at different priorities.

Step 1: Input processing

The controller obtains the input information used by the program.

Example:

  • PART_PRESENT = TRUE
  • CLAMP_CLOSED = TRUE
  • ROBOT_READY = FALSE

These values represent the controller's available signal states, not necessarily independent proof of the physical conditions.

Step 2: Program execution

The CPU executes the configured program and evaluates the conditions that govern machine operation.

Illustrative logic:

IF PART_PRESENT
AND CLAMP_CLOSED
AND ROBOT_READY
AND SAFETY_PERMISSIVE
THEN
    ALLOW_WELD_SEQUENCE
END_IF

This is conceptual pseudocode, not valid syntax for every PLC platform. Actual safety functions must be implemented in the approved safety architecture rather than relying on an ordinary Boolean condition alone.

Step 3: Output update

The controller updates output commands according to its execution model.

For example:

  • Turn on a valve command.
  • Request a conveyor run.
  • Set a robot handshake bit.
  • Send a speed reference to a drive.

The output command is only one stage in the physical response. Electrical output hardware and the receiving device must operate correctly.

Step 4: Repeat execution

The CPU continues executing its scheduled tasks while operating normally.

If a controller completes a particular cyclic task every 10 ms, that task's cycle time is 10 ms. This does not mean that every signal, network update, or physical response occurs exactly every 10 ms.

5. Scan time and execution time

Scan time is the time taken to execute a particular cyclic control task or scan, according to the controller's terminology.

It can be affected by:

  • Program size and complexity.
  • Number and type of instructions.
  • Communication and system-task load.
  • Number of scheduled tasks and their priorities.
  • Interrupts and event-triggered execution.
  • I/O update architecture.
  • Controller model and performance.
Term Meaning
Scan time Duration of a scan or cyclic task execution
Task period Configured interval at which a periodic task is scheduled
Input update time Time required for a new physical input state to become available to the program
Output update time Time required for an output command to be applied at the relevant output interface
End-to-end response time Time from a physical event to the corresponding system response

These values are related but not identical.

For example, a sensor may change state immediately after the relevant input data has been sampled. The CPU may not evaluate the new state until the next applicable execution opportunity. The output module, network, actuator, and mechanical system add their own delays.

For high-speed applications, use the controller's task configuration, I/O architecture, timing documentation, and measured diagnostics rather than assuming that scan time equals total machine response time.

6. What are PLC operating modes?

PLC operating modes determine whether the user program executes, whether modifications are allowed, and how the controller manages its operation.

Common concepts include RUN, STOP, PROGRAM, REMOTE RUN, REMOTE PROGRAM, and test or debugging modes. Exact names and behavior vary by manufacturer and model.

RUN mode

In RUN mode, the controller normally executes its configured control program.

Typical behavior:

  • Control tasks execute according to their schedules.
  • Inputs are processed.
  • Outputs are updated according to the configured execution model.
  • Communication and diagnostics operate according to configuration.
  • The machine can respond to program commands and field signals.

RUN does not mean the machine is necessarily running. The PLC can be in RUN mode while the machine is stopped because of a missing permissive, an active fault, an operator stop request, or an incomplete sequence.

STOP mode

In STOP mode, the controller generally stops normal execution of the user control program or the relevant tasks.

Depending on the platform and configuration:

  • Program execution may stop.
  • Communication and diagnostics may remain active.
  • Outputs may turn OFF, hold their previous state, or follow configured behavior.
  • Some system tasks may continue running.
  • Certain outputs or specialized functions may have distinct stop-state behavior.

Never assume that all outputs automatically turn OFF in every STOP condition. Output behavior depends on the controller, module, configuration, and application design. Verify the manufacturer's documentation and the approved machine design.

PROGRAM mode

On some PLC families, PROGRAM mode is used for program editing, downloading, configuration, or other engineering activities. Normal user-program execution is generally stopped.

PROGRAM and STOP are not universally interchangeable terms. Their exact behavior depends on the controller family.

REMOTE RUN and REMOTE PROGRAM

Some controllers support remote mode selection, allowing authorized software or supervisory mechanisms to select an operating mode.

The precise mode names and permitted actions depend on the platform and controller configuration.

Remote mode control is operationally important because a controller can be changed from an engineering workstation without directly operating the physical key switch.

Test or debugging modes

Some PLC environments provide modes for testing, online monitoring, simulation, or debugging. These may alter how logic, I/O, or program modifications behave.

They should not be treated as ordinary production modes. Confirm the exact behavior before using them on live equipment.

8. Examples from industrial maintenance

Example A: PLC in RUN, machine not running

A conveyor is stopped, but the PLC shows RUN mode.

Possible causes:

  • Stop command remains active.
  • Safety system has not granted permission.
  • Drive-ready feedback is missing.
  • A sequence permissive is FALSE.
  • A fault is latched.
  • An operator has not initiated the cycle.
  • The PLC output command is not being generated.

Correct troubleshooting approach:

  1. Confirm the controller's mode and health.
  2. Check the relevant input and status tags.
  3. Check active faults and alarms.
  4. Examine the sequence conditions.
  5. Verify the output command.
  6. Follow the electrical circuit and drive diagnostics.

Do not switch the CPU to STOP merely because the machine has stopped. A stopped machine and a stopped controller are different conditions.

Example B: PLC in STOP, outputs behave unexpectedly

Suppose the PLC enters STOP mode during troubleshooting, but a device remains energized.

Possible explanations include:

  • The output module is configured to hold its last state.
  • An output is supplied through a circuit independent of the PLC.
  • A different controller or relay is commanding the device.
  • Stored energy or a separate power supply is maintaining the condition.
  • The observed signal is not the output assumed to be under CPU control.

Treat this as a safety-critical condition. Follow the approved isolation procedure, identify the actual energy source, and verify the circuit rather than assuming the CPU mode guarantees a safe machine state.

Example C: CPU fault or watchdog fault

A controller may detect an execution or system fault and stop or alter program execution according to its design.

Potential causes can include:

  • Excessive execution time.
  • Task watchdog expiration.
  • Invalid program operations.
  • Hardware or firmware problems.
  • Memory or configuration faults.
  • Communication or module faults that affect controller operation.

The correct investigation is to retrieve the controller's diagnostic information, identify the exact fault code and task context, review recent program or configuration changes, and follow the manufacturer's troubleshooting instructions.

Do not assume every CPU fault has the same cause or that cycling power is an acceptable corrective action.

9. RUN/STOP modes and machine safety

Operating mode is not the same thing as the machine's safety state.

For example:

  • A CPU in RUN may control a machine that is safely stopped by a safety system.
  • A CPU in STOP may leave certain outputs energized, depending on configuration.
  • A standard PLC output may not be an approved safety function.
  • A machine can contain stored electrical, pneumatic, hydraulic, gravitational, or mechanical energy even when the PLC is not executing its program.

Before working on equipment, apply the applicable lockout/tagout or energy-isolation procedure, control stored energy, and verify the safe state.

Never use the CPU's operating mode as the sole method of isolating hazardous energy.

10. Common PLC CPU indicators

Many PLCs provide LEDs or diagnostic displays that indicate controller state.

Indicator Possible meaning
RUN Controller is executing the user program or is in its run state
STOP or PROG Controller is not in normal RUN mode
OK or SYS General controller health or system status
FAULT or ERR A controller or system fault is present
I/O I/O-related status, where supported
COMM or NET Communication status
BAT Battery-related status on platforms that use a battery

Indicator labels, colors, and flashing patterns vary by manufacturer and model. A single LED is not enough to diagnose the fault reliably.

For maintenance, record the exact LED pattern, controller model, diagnostic code, operating mode, and relevant software status before changing anything.

11. CPU troubleshooting checklist

When investigating a PLC-related breakdown, proceed systematically.

  1. Identify the controller. Record manufacturer, model, firmware, and project identity.
  2. Check the operating mode. Confirm whether it is RUN, STOP, PROGRAM, or another platform-specific mode.
  3. Check controller health. Inspect diagnostic indicators, fault codes, task status, and available logs.
  4. Check I/O status. Confirm that expected input and output states are visible in the correct module and tag.
  5. Check program execution. Review task status, sequence state, active conditions, and relevant logic.
  6. Check communication. Verify the status of required drives, robots, remote I/O, and HMI connections.
  7. Check recent changes. Review program downloads, hardware changes, network modifications, and configuration updates.
  8. Verify physical behavior. Use approved electrical and mechanical diagnostic procedures to confirm whether the hardware responds as expected.

Avoid unnecessary mode changes, power cycles, or program downloads before recording diagnostic evidence. Those actions can erase useful fault context or introduce additional risk.

12. Interview questions and answers

Q1. What is the function of a PLC CPU?

The CPU executes the control program, processes data, coordinates scheduled tasks, manages operating modes, and supports diagnostics and communication.

Q2. What is a PLC scan cycle?

A scan cycle is a repeated execution process in which the controller processes input information, executes control logic, and updates outputs according to its architecture and configuration.

Q3. What is the difference between RUN and STOP mode?

RUN mode normally allows the user program to execute. STOP mode generally interrupts normal user-program execution. The exact output behavior and other functions depend on the controller and its configuration.

Q4. If the CPU is in RUN, why might a motor remain stopped?

The program may not be issuing a run command because a permissive is missing, a fault is active, the sequence is incomplete, or the required input condition has not been satisfied. Electrical, drive, and mechanical faults are also possible.

Q5. Does STOP mode guarantee that all PLC outputs are OFF?

No. Output behavior depends on the PLC family, module configuration, and application design. Some outputs may hold their state, follow a configured stop value, or be affected by external circuits.

Q6. What is a watchdog fault?

A watchdog fault occurs when an execution or system operation exceeds a defined time limit or fails to meet the controller's expected timing requirements. The exact response depends on the PLC platform and fault configuration.

Q7. Why should the PLC mode be checked before troubleshooting?

The mode determines whether the user program is executing normally. Without knowing the operating mode, it is difficult to distinguish a logic problem from a controller-state or execution problem.

13. Practical exercise

Use a training PLC, simulation environment, or approved test setup.

  • Identify the PLC CPU model and firmware version.
  • Locate its operating-mode selector or software mode indication.
  • Record the meaning of its RUN, STOP, and fault indicators from the manual.
  • Observe the controller in RUN mode.
  • Monitor one input, one internal program tag, and one output.
  • Observe the effect of a normal input-state change on the program.
  • Study the manufacturer's documented behavior when the controller enters STOP.
  • Identify the configured output behavior in STOP mode.
  • Locate the controller's diagnostic and fault-history information.
  • Record the difference between CPU mode, machine state, and safety state.

Do not change modes or test output behavior on a production machine without authorization and an approved test procedure.

14. Final mental model

The CPU is the execution engine of the PLC. Its operating mode determines whether normal control logic is executing, while the actual machine response depends on the program, I/O, communication, electrical circuits, and physical equipment.
