1. Definition

PLC memory is the storage used to hold the control program, hardware configuration, process data, internal variables, diagnostic information, and values that may need to survive a power interruption.

Memory determines what the PLC knows, what instructions it can execute, what data it can retain, and what information remains available after a restart.

For industrial maintenance, understanding PLC memory is important when troubleshooting lost setpoints, unexpected counter resets, retained fault states, program downloads, controller replacement, and recovery after power failure.

Three important memory concepts are:

  • Load memory: Stores the program and associated data in a form used for loading or restoring the controller's software.
  • Work memory: Holds the program and data used during execution, according to the PLC architecture.
  • Retentive memory: Preserves selected values across specified events, such as a restart or power loss.

These are related concepts, but they are not three mutually exclusive physical memory chips in every PLC. Some platforms implement them as distinct memory areas; others use different terminology and storage arrangements.

2. Why PLC memory matters

Consider a production line that uses a PLC to control a robotic fixture.

The controller may need to store:

  • The PLC program and configuration.
  • Current sensor states and output commands.
  • The active sequence step.
  • The selected production recipe.
  • A part counter.
  • Calibration values.
  • Alarm and diagnostic information.
  • Values that must survive a restart.

If memory behavior is misunderstood, a power interruption or program download can lead to lost data, unexpected sequence behavior, or the need to restore configuration from a backup.

The key maintenance question is not merely, "Where is the value stored?" It is also, "What happens to the value when the CPU restarts, loses power, downloads a program, or is replaced?"

3. Load memory

Load memory stores the program and associated information required to load or restore the controller's executable application.

Depending on the PLC family, it may contain:

  • User program or executable code.
  • Hardware configuration.
  • Program blocks and related data.
  • Persistent project information.
  • Other application components required by the platform.

Load memory is often implemented using nonvolatile storage, such as flash memory or another persistent storage technology.

Example

A maintenance engineer downloads an approved PLC program to a controller.

The controller stores the application in its supported program storage. The CPU can then use the appropriate execution memory and configuration to run the application.

If the controller loses power, the stored program will generally remain available when the controller restarts, provided the storage is healthy and the program was saved or downloaded correctly.

Important distinction

A program being present in load memory does not necessarily mean that it is currently executing. A controller can contain a valid program while in STOP or PROGRAM mode.

Also, a saved project on an engineering computer is not the same thing as the application stored inside the PLC. The two can differ if changes were made online or if a newer project was never downloaded.

4. Work memory

Work memory is the memory used to support program execution and working data, according to the controller architecture.

Depending on the PLC family, it may hold or support:

  • Executable instructions used by the CPU.
  • Temporary variables.
  • Intermediate calculation results.
  • Current program data.
  • Runtime structures and execution-related information.

Some controllers distinguish program work memory from data work memory. Others use different names or storage architectures.

Example: Fixture-clamping sequence

Suppose a PLC evaluates the following conditions:

PART_PRESENT = TRUE
CLAMP_CLOSED = TRUE
ROBOT_READY = TRUE

The program evaluates the conditions and determines whether the next sequence step can execute.

During this process, the CPU uses program and data storage to execute instructions, evaluate logic, and maintain the relevant runtime state.

The variables may represent inputs, outputs, internal states, or calculated values. Their exact storage location depends on the PLC family and program configuration.

Why work memory matters

Insufficient program or data memory can prevent an application from being downloaded or executed, or can restrict the available program capacity.

Memory diagnostics may therefore be relevant when:

  • A large program cannot be downloaded.
  • A project exceeds the controller's supported capacity.
  • A firmware or hardware change affects memory requirements.
  • Runtime memory errors or allocation-related faults occur.
  • A controller replacement requires a different model with adequate capacity.

Do not assume that every internal variable is lost on power failure simply because it is associated with work memory. Retention behavior is determined by the controller's memory architecture and configuration.

5. Retentive memory

Retentive memory preserves selected data across specified events that would otherwise clear or reinitialize it.

Common examples of data that may be configured as retentive include:

  • Production counters.
  • Calibration constants.
  • Selected recipe values.
  • Machine configuration parameters.
  • Certain alarm or fault-history values.
  • Sequence-recovery information, where specifically designed.

Retention may be implemented using nonvolatile memory, battery-backed storage, or other platform-specific mechanisms.

Retentive does not automatically mean permanent. A value may survive a power cycle but be cleared by a memory reset, program download, initialization routine, firmware procedure, or an explicit program command.

Example: Production counter

A machine counts completed parts.

Event Possible behavior
Normal program execution Counter increases when the counting condition is met
CPU restart Counter may retain its value if configured for retention
Power loss Counter may retain its value if the storage mechanism and configuration support it
Program download Behavior depends on the PLC, download type, and data-preservation settings
Memory reset Retained data may be erased
CPU replacement Data must usually be restored or transferred unless a supported migration method is used

The exact behavior must be verified in the controller manual and project configuration.

6. Comparison: Load, work and retentive memory

Feature Load memory Work memory Retentive memory
Main purpose Store application information for loading or restoration Support program execution and runtime data Preserve selected values across specified events
Typical contents Program, configuration, application blocks Executable program and working data, depending on architecture Selected counters, settings, recipes, and other persistent data
Used during execution Supplies or supports the application, depending on platform Directly supports execution and runtime operations Supplies preserved values when needed
Power-loss behavior Usually persistent when implemented in nonvolatile storage Depends on memory architecture and data-retention configuration Designed to preserve designated values across specified events
Can be cleared or changed? Yes, through supported engineering or memory operations Yes, during execution or initialization, depending on the data Yes, through configured operations, resets, downloads, or other platform-specific events

These categories describe functions, not a universal physical layout. A particular PLC may combine, subdivide, or rename them.

7. Volatile versus nonvolatile memory

Memory retention is easier to understand when two additional terms are distinguished.

Volatile memory

Volatile memory generally requires power to preserve its contents.

When power is removed, its contents may be lost unless the controller provides another mechanism to preserve them.

Examples can include runtime working areas and temporary execution data.

Nonvolatile memory

Nonvolatile memory preserves its contents without continuous power, within the limits of the storage technology and device.

Examples include flash memory and other persistent storage technologies.

Nonvolatile storage is commonly used for application programs, configuration, and selected persistent data.

Property Volatile memory Nonvolatile memory
Requires continuous power to retain contents Generally yes No
Typical role Runtime data and temporary storage Programs, configuration, and persistent data
Contents survive power loss Not inherently Generally, if properly stored
Data can still be erased or changed Yes Yes

Do not treat volatile versus nonvolatile as a complete substitute for load, work, and retentive memory. The terms describe different properties: one describes persistence technology, while the other describes the function or use of the memory.

8. Understanding retentive and non-retentive variables

A PLC application may contain both retentive and non-retentive variables.

Consider a conveyor system.

Variable Example Possible retention requirement
Current sensor state PART_PRESENT Usually reflects the current input state rather than a saved historical state
Motor run command CONVEYOR_RUN_CMD Must follow the approved restart and safety design
Production count PART_COUNT May need to survive a power interruption
Selected recipe ACTIVE_RECIPE May need to be preserved, depending on process requirements
Temporary calculation TEMP_SPEED_VALUE Often does not need retention
Sequence step SEQUENCE_STEP Depends on whether automatic recovery is intentionally supported
Fault history FAULT_HISTORY May need persistent diagnostic storage

The retention requirements should be decided from the machine's functional requirements and risk assessment, not merely from convenience.

For example, preserving a production count may be useful, but automatically resuming an interrupted motion sequence may be unsafe if the physical machine state is no longer known.

9. What happens during a PLC restart?

A restart is not a single universal event. The result depends on the PLC family, startup configuration, data-retention settings, and program initialization logic.

A typical conceptual sequence is:

POWER RESTORED
      |
      v
CPU AND HARDWARE INITIALIZATION
      |
      v
LOAD APPLICATION AND CONFIGURATION
      |
      v
INITIALIZE OR RESTORE DATA
      |
      v
CHECK CONTROLLER AND SYSTEM STATUS
      |
      v
ENTER CONFIGURED OPERATING MODE
      |
      v
EXECUTE PROGRAM IF PERMITTED

This is a simplified conceptual sequence. Actual controller startup behavior and mode transitions differ.

During startup, some variables may be restored, some may be initialized to configured values, and others may be updated from physical inputs or communication partners.

A robust industrial application should define what happens after a restart, including:

  • Whether automatic restart is permitted.
  • How outputs behave during initialization.
  • Whether retained sequence state is trusted.
  • Whether safety and process permissives must be re-established.
  • Whether the operator must acknowledge faults or request a new cycle.
  • How production counts and recipes are restored.

10. First scan and initialization logic

Many PLC applications use startup or first-scan logic to initialize selected variables and prepare the application for operation.

Examples include:

  • Resetting temporary calculation values.
  • Initializing internal flags.
  • Loading default parameters when required.
  • Verifying configuration.
  • Setting the sequence to a safe initial state.
  • Clearing specific non-retentive diagnostic flags.

The implementation differs by PLC platform. Some systems provide dedicated first-scan bits or startup events; others use organization blocks, startup routines, or equivalent mechanisms.

Example

A machine stores its completed-part count as a retentive value but initializes temporary sequence variables at startup.

This means the production count can survive a restart while the machine's active sequence is reinitialized.

That behavior may be desirable, but it must be deliberately designed and tested. A counter that survives restart does not automatically make it safe to resume the interrupted machine cycle.

11. Practical maintenance scenarios

Scenario A: Production count resets after a power interruption

Possible causes:

  • The counter was configured as non-retentive.
  • Startup logic explicitly reset it.
  • The project uses a different variable than the one being monitored.
  • The controller's data-retention mechanism failed or was not configured as expected.
  • A download or reset operation changed the value.

Investigation:

  1. Identify the exact counter tag.
  2. Check its memory and retention properties.
  3. Review startup and initialization logic.
  4. Check controller-specific retention rules.
  5. Examine recent downloads and maintenance activities.
  6. Test the behavior in an approved environment.

Scenario B: Recipe values disappear after a restart

Possible causes:

  • The recipe was stored only in temporary runtime variables.
  • The HMI or SCADA system was responsible for restoring the recipe.
  • The values were not saved to persistent storage.
  • A startup routine loaded default values.
  • The controller's data-retention configuration did not preserve the intended values.

Investigation should cover the PLC, HMI, recipe-management system, and any external database or file used for recipe storage.

Scenario C: PLC program is present, but the controller does not run

Possible causes include:

  • The CPU is in STOP or PROGRAM mode.
  • A controller fault prevents execution.
  • The application is invalid or incompatible with the configured hardware or firmware.
  • A required module or configuration is missing.
  • The controller has a task or system fault.

Check the CPU mode, diagnostics, project identity, firmware compatibility, hardware configuration, and relevant fault records.

Do not assume that a program being present in load memory guarantees that the controller can execute it.

Scenario D: A retained sequence step causes unexpected restart behavior

A sequence variable may preserve its value while the physical machine loses its original position or process conditions.

For example, a controller may remember that a fixture was halfway through a clamping sequence, but after a power interruption, the actual cylinder position may be uncertain.

The correct design may require position verification, renewed permissives, recovery logic, operator confirmation, or a safe return to a defined state.

Retaining a variable is a data-storage decision, not proof that resuming the machine is safe.

12. Memory, program backup, and controller replacement

Memory inside the PLC and backup files outside the PLC serve different purposes.

Item Purpose
PLC load or program storage Holds the application according to the controller architecture
Runtime memory Supports current execution and data processing
Retentive data Preserves designated values across specified events
Engineering project backup Provides a recoverable copy of the application and configuration
Controller upload Retrieves available project information from the installed controller
External recipe or database backup Preserves data managed outside the PLC

A controller upload may not recover every original engineering detail, comment, external file, library, or project artifact. This depends on the PLC platform and how the application was originally downloaded.

Before replacing a CPU, verify:

  • Controller model and firmware compatibility.
  • Available and approved program backup.
  • Hardware configuration and module arrangement.
  • Network settings and device identities.
  • Retentive values that need to be preserved.
  • Required safety signatures or configuration, where applicable.
  • Startup behavior and commissioning requirements.

Never assume that replacing a CPU automatically transfers its retentive data or restores the complete machine configuration.

13. Common mistakes

  • Treating load, work, and retentive memory as three universally separate physical chips.
  • Assuming all data in work memory is lost on every power interruption.
  • Assuming every value in nonvolatile storage can never be erased.
  • Assuming retentive data always survives a program download or memory reset.
  • Assuming the saved engineering project is identical to the application running in the PLC.
  • Failing to distinguish PLC memory from HMI, SCADA, and database storage.
  • Retaining sequence variables without designing and validating restart recovery.
  • Assuming that a valid stored program guarantees the CPU can enter RUN mode.
  • Replacing a controller without considering configuration and retained data.
  • Failing to test power-loss and restart behavior during commissioning.

14. Interview questions and answers

Q1. What is load memory?

Load memory stores the user application and related information required for loading or restoring the controller's program, according to the PLC architecture.

Q2. What is work memory?

Work memory supports program execution and runtime data operations. Its precise contents and organization depend on the PLC family.

Q3. What is retentive memory?

Retentive memory or retentive data storage preserves selected values across specified events, such as a restart or power loss, according to the controller's retention mechanisms and configuration.

Q4. What is the difference between volatile and nonvolatile memory?

Volatile memory generally requires power to preserve its contents. Nonvolatile memory can preserve its contents without continuous power. These terms describe persistence, not necessarily the functional purpose of the memory.

Q5. Why might a production counter reset after a restart?

It may be non-retentive, explicitly initialized by startup logic, cleared by an engineering operation, or stored in a system that did not preserve it as expected.

Q6. Should a PLC always resume the previous sequence step after a power interruption?

No. Resumption depends on the machine's design, the validity of the retained state, physical position verification, safety requirements, and recovery logic.

Q7. Does a PLC backup guarantee that every retained value is restored?

No. Program backups and runtime retained data are separate concerns. The required data must be identified and preserved through the platform's supported backup and restoration procedures.

15. Practical exercise

Using a training PLC, a simulation, or the documentation for a controller you maintain:

  • Identify the PLC's memory types and terminology from the manufacturer's manual.
  • Determine how the controller stores the application and configuration.
  • Identify variables configured for retention.
  • Find the startup or first-scan logic.
  • Identify one production counter, one recipe value, and one temporary variable.
  • Record the expected behavior of each variable after a restart.
  • Determine what happens to retained values during a program download or memory reset.
  • Identify the approved method for backing up and restoring the application.
  • Review how the machine establishes a safe state after power restoration.
  • Document the results without experimenting on production equipment outside an approved test procedure.

16. Final mental model

LOAD MEMORY
    |
    +---- Stores application and related information
    |
    v
WORK MEMORY
    |
    +---- Supports execution and runtime data
    |
    v
PLC PROGRAM EXECUTION
    |
    +---- Uses current input and internal data
    |
    +---- Produces output commands
    |
    v
RETENTIVE DATA
    |
    +---- Preserves selected values across defined events

This diagram represents functional relationships, not a universal physical memory layout.

The essential distinction is that load memory supports application storage, work memory supports execution, and retentive storage preserves selected data across defined events. Correct retention and startup design are essential for reliable recovery after a power interruption, controller restart, or maintenance activity.
