1. Definition

Going online means establishing communication between PLC engineering software and a real PLC controller or supported simulator so that the engineer can observe the controller's live status, tag values, logic execution, diagnostics, and program state.

Examples of engineering software include:

  • Rockwell Automation: Studio 5000 Logix Designer
  • Siemens: TIA Portal
  • Mitsubishi: GX Works2 / GX Works3

When online, an engineer can monitor a motor-start rung, check whether a permissive is satisfied, inspect timer values, observe sequence progression, and diagnose controller faults.

Important: Going online does not automatically mean the PLC is in RUN mode, and it does not necessarily mean that the online project matches the project saved on the engineering computer.

2. Offline, Online and Controller Operating Modes

These terms describe different things and must not be confused.

Term Meaning Example
Offline Engineering software is working with a local project without a live controller connection. Editing a PLC program on a laptop at a desk.
Online Engineering software is communicating with the controller. Monitoring a motor-start rung on a connected PLC.
RUN Controller executes its control program. The PLC evaluates logic and updates outputs according to its configuration.
PROGRAM / STOP Controller is not executing its normal application logic in the usual RUN manner. Exact behavior depends on platform and mode. Logic is being prepared or a controller is stopped for maintenance.
Remote RUN On supported controllers, the operating mode can be controlled remotely through authorized software or a mode selector. An authorized engineer changes the controller to RUN from engineering software.
Monitor / Status Software displays live execution states and values. A ladder rung is highlighted as true or false.

The key distinction is:

  • Online status: Is the engineering computer communicating with the controller?
  • Operating mode: What is the controller doing?
  • Program state: Which project or program is loaded and executing?
  • Monitoring state: What live information is the software displaying?

A controller can be online while stopped. It can also be running while the engineer is offline.

3. Why Going Online Is Necessary

Online monitoring is used for several practical maintenance and commissioning tasks.

Purpose What the engineer checks
Troubleshooting Which condition prevents a sequence from progressing.
Input diagnosis Whether the controller recognizes a sensor signal.
Output diagnosis Whether the PLC output command is active.
Interlock diagnosis Which safety-related or process permissive is unsatisfied.
Timer diagnosis Preset, accumulated value, timing state and completion bit.
Counter diagnosis Current count, preset and completion status.
Sequence monitoring Current step, transition conditions and next-step request.
Communication diagnosis Whether the controller can communicate with remote I/O, drives, robots or other devices.
Fault diagnosis Controller faults, module faults and diagnostic-buffer messages.
Program verification Whether the connected controller program matches the intended project.
Commissioning Whether logic behaves as expected under approved test conditions.
Performance analysis Scan time, task execution and other available performance indicators.

For industrial maintenance, online monitoring helps identify where a signal path stops behaving as expected, rather than replacing components based on guesswork.

4. Basic Online Connection Workflow

The exact software buttons vary by manufacturer and version, but the engineering process is broadly similar.

Step 1: Identify the correct controller

Confirm the machine, line, PLC name, controller type, IP address, rack or chassis, and communication path.

For example:

Machine: FR1010
Controller family: Allen-Bradley ControlLogix
Controller IP: Verified machine-specific address
Communication path: Engineering PC -> Ethernet network -> PLC

Never assume that an IP address or controller path is correct merely because it worked during a previous job.

Step 2: Verify authorization and machine conditions

Before connecting, confirm that the connection and intended activity are permitted by the site's rules.

  • Identify whether the machine is operating in production.
  • Follow applicable change-control and maintenance procedures.
  • Use read-only monitoring by default.
  • Obtain authorization before changing modes, editing logic, downloading programs, writing values or forcing signals.
  • Follow machine-specific safety procedures.

Connecting for observation is not the same as permission to change the machine.

Step 3: Check the network connection

Verify:

  • Correct Ethernet cable, switch port or approved network connection.
  • Correct engineering-computer network adapter.
  • Correct IP address and subnet.
  • Appropriate routing when the controller is on another subnet.
  • Correct communication driver or PG/PC interface.
  • No conflicting IP address.
  • Controller accessibility and security permissions.

A successful ping only indicates that an IP endpoint responds to ICMP, when ICMP is enabled. It does not prove that the PLC programming protocol is available or that the engineering software can establish a session.

Step 4: Open the correct engineering project

Open the project for the correct machine and controller.

Check the controller type, firmware or device version, program revision and relevant configuration. A project belonging to a similar machine is not automatically suitable for the target controller.

Step 5: Select the controller and connect

Browse for the controller or select the configured communication path.

Examples:

  • Rockwell: Select the controller through the communication browse/path workflow, commonly using Who Active, then choose the applicable online operation.
  • Siemens: Select the appropriate PG/PC interface, find the device through online access, and use the supported online connection workflow.
  • Mitsubishi: Configure the connection destination and communication interface, then use the applicable online connection or monitoring command.

Exact menu labels differ between versions. The goal is to connect to the verified target, not merely the first device that appears in a browse list.

Step 6: Confirm the online identity and program state

After connecting, verify the controller identity, operating mode, faults and project comparison status.

If the software reports that the local and controller programs differ, stop before making changes. Determine which version is authoritative.

Step 7: Monitor live logic and tags

Observe relevant ladder rungs, tags, timers, counters, sequence steps and diagnostics.

Record actual values and states. Do not force a signal or write a value simply to make a sequence proceed.

Step 8: Document and disconnect appropriately

Record findings, changes made under authorization, test results and any unresolved fault.

Disconnect the engineering session when appropriate, and leave the machine and controller in the state required by the approved procedure.

5. Go Online vs Upload vs Download vs Compare vs Verify vs Save

These operations are related but are not interchangeable.

Operation Direction or purpose Main use Main risk or limitation
Go Online Engineering software connects to the controller. Live monitoring and supported online operations. Connecting alone does not prove that the local project matches the controller.
Upload Controller to engineering computer. Retrieve the program or supported data from the controller. Comments, symbols, source files and project documentation may not be recoverable if they were never stored in the controller or its backup.
Download Engineering computer to controller. Transfer a project or supported changes to the PLC. May stop execution, change controller state or alter machine behavior.
Compare Compare local and controller versions. Identify program or configuration differences. Comparison scope and detail depend on the software and available project metadata.
Verify / Compile Check program syntax, consistency and other supported requirements. Find errors before deployment. A program that compiles successfully is not necessarily safe or functionally correct.
Save Store the project on the engineering computer or project storage. Preserve the local engineering work. Saving locally does not mean the controller has received the changes.

Example

Suppose the engineering computer contains revision R12, while the PLC contains revision R10.

Engineering computer: R12
PLC controller:       R10

Go Online:
    Establish communication.

Compare:
    Identify differences.

Upload:
    Retrieve supported controller contents into the engineering environment.

Download:
    Transfer the selected engineering project to the controller.

The correct action depends on which revision is approved and authoritative. Downloading R12 just because it is newer could overwrite valid production logic with unapproved or incomplete changes.

Practical rule: Compare before making deployment decisions. Back up the authoritative project before approved changes.

6. What Live Logic Monitoring Shows

Online monitoring displays the current state of the control program. The visual representation depends on the engineering software and the selected programming language.

For example, consider this motor-start logic:

Start_PB
    AND Auto_Mode
    AND Drive_Ready
    AND Safety_Permissive
    AND NOT Fault_Active
        |
        v
    Motor_Run_Request

During online monitoring, the engineer may see:

  • Start_PB = FALSE
  • Auto_Mode = TRUE
  • Drive_Ready = TRUE
  • Safety_Permissive = TRUE
  • Fault_Active = FALSE
  • Motor_Run_Request = FALSE

The start condition is not satisfied because Start_PB is false.

If the start request becomes true but the motor command remains false, the engineer can inspect the actual logic and its dependencies.

A highlighted rung or energized-looking path is a software representation of logic state. It does not prove that a contactor has physically closed or that a motor is rotating.

7. Understanding the Signal Path

A useful way to monitor a machine is to trace the complete path from the physical device to the final action.

Physical Sensor or Pushbutton
            |
            v
      Input Module
            |
            v
      PLC Input Tag
            |
            v
      Program Conditions
            |
            v
      PLC Output Command
            |
            v
      Output Module
            |
            v
      Contactor / Drive / Valve
            |
            v
      Physical Machine Response
            |
            v
      Feedback Sensor or Status

Each stage answers a different diagnostic question.

Stage Diagnostic question
Physical sensor Is the sensor actually detecting the target?
Input module Is the module receiving the electrical signal?
PLC input tag Does the controller recognize the input?
Program conditions Are all required conditions satisfied?
PLC output command Has the program requested the action?
Output module Is the module applying the intended output signal?
Field device Is the contactor, drive, valve or other device responding?
Feedback Does the controller receive confirmation of the physical response?

This sequence prevents a common diagnostic mistake: replacing a sensor when the actual problem is an unsatisfied interlock, a failed output channel or a drive fault.

8. PLC Tag Monitoring and Watch Tables

A watch table or tag monitor is a view used to observe selected variables while the controller is online.

Names differ by software, but the purpose is similar.

A practical watch list might contain:

Tag Data type What to observe
Start_Request BOOL Whether a start request is present.
Auto_Mode BOOL Whether automatic operation is selected.
Drive_Ready BOOL Whether the drive reports readiness.
Fault_Active BOOL Whether the relevant fault condition is active.
Motor_Run_Request BOOL Whether the program requests motor operation.
Motor_Running_FB BOOL Whether running feedback is present.
Start_Delay TIMER / timer structure Preset, accumulated value and completion status, where applicable.
Current_Step INT / DINT / enum-like value The active sequence step.

The exact timer representation depends on the PLC platform. Some systems expose timer members such as preset, accumulated value and done status; others use different data structures or instructions.

Good watch-table practice

  • Monitor a small group of relevant tags first.
  • Include the request, permissives, command and feedback.
  • Check data types and tag scope.
  • Observe values over time rather than relying on a single snapshot.
  • Use trends or traces when timing and intermittent faults matter.
  • Confirm that the displayed data is updating.
  • Avoid unnecessarily large tag lists that make the important variables difficult to find.

A watch table is for observing state. It is not automatically a safe place to modify values.

9. Monitoring Timers, Counters and Sequences

Timers

For a timer-controlled action, inspect:

  • Timer enable condition.
  • Preset time.
  • Accumulated time.
  • Completion status.
  • Reset condition.
  • Conditions that may repeatedly interrupt timing.

Example:

Sensor_Detected = TRUE
        |
        v
Start_Delay enabled
        |
        v
Elapsed time reaches preset
        |
        v
Timer_Done = TRUE
        |
        v
Next sequence condition evaluated

If the timer never completes, check whether its enable condition remains true, whether the preset is correct, and whether another part of the logic resets it.

Counters

Observe the count value, preset, completion status and reset conditions. If the count unexpectedly returns to zero or advances multiple times, investigate the event signal and the counter's triggering behavior.

Sequence steps

Suppose a machine uses these steps:

Step 10: Wait for part
Step 20: Clamp part
Step 30: Verify clamp
Step 40: Start process
Step 50: Verify process complete
Step 60: Release part

If the machine remains at Step 30, monitor:

  • Whether Step 30 is active.
  • Whether clamp feedback is present.
  • Whether the transition condition is true.
  • Whether a timer or fault prevents the transition.
  • Whether the next step is permitted.
  • Whether a reset or abort condition is active.

The active step identifies where the sequence is waiting. The transition conditions explain why it is waiting.

10. Cross-Reference and Live Monitoring Are Different

Cross-reference identifies where a tag is used in the program. Online monitoring shows its current value or logic state.

Both are useful, but they answer different questions.

Tool Question answered
Search Where is this tag or instruction named?
Cross-reference Where is the tag read, written or referenced?
Tag monitor What is the current value?
Ladder monitoring Which conditions are currently true or false?
Diagnostic buffer What faults or events has the controller recorded?
Trend / trace How did the value change over time?

If Motor_Run_Request is false, cross-reference can help locate every place that writes or uses the tag. Online monitoring then helps determine which conditions prevent it from becoming true.

Multiple writers, alias tags, mapped I/O, program scope and indirect addressing can complicate the search. Do not assume that the first occurrence found is the only place affecting the signal.

11. Reading Physical I/O Correctly

A displayed PLC input value is not necessarily a perfect representation of the physical condition.

For example, a sensor may detect a part, but the controller's input tag may still appear false because of:

  • Sensor power or wiring failure.
  • Incorrect input-channel mapping.
  • A failed or inhibited module.
  • Incorrect tag mapping.
  • Communication delays or stale data.
  • Input filtering or update timing.
  • Incorrect assumptions about normally open and normally closed signal logic.

Likewise, an output command may be true while the machine remains stationary because the output module, wiring, contactor, drive, motor or mechanical system has a problem.

Never use a PLC screen alone to prove that hazardous energy is absent. Follow the applicable isolation, lockout/tagout, electrical testing and machine-safety procedures.

13. Troubleshooting Online Connection Problems

Problem Possible causes First checks
Controller not found Wrong subnet, wrong NIC, cable issue, unavailable device or incorrect browse settings. Verify the target IP, adapter, physical link and network path.
Ping works, but software cannot connect PLC protocol unavailable, incorrect driver, access restrictions or wrong communication path. Verify the engineering software's protocol configuration, permissions and controller path.
Wrong controller appears Multiple devices, duplicate IPs or incorrect browsing scope. Verify controller identity and machine-specific network documentation.
Online connection fails after selecting a device Firmware or software incompatibility, access restriction or path configuration problem. Check controller family, firmware support, driver and security configuration.
Offline and online projects differ Local project is outdated, controller was modified or the wrong file is open. Compare revisions and establish the authoritative version before changing anything.
Values do not update Monitoring is inactive, communication is interrupted or the displayed data is stale. Check online status, tag path, update status and communication diagnostics.
Logic looks correct, but machine does not move Output path, drive fault, feedback problem, mechanical issue or another control layer. Trace the command through the output module to the field device and feedback.
Upload or download warning appears Version mismatch, unsupported configuration, project differences or potential controller-state change. Read the complete warning and determine its implications before proceeding.
Cannot monitor the expected block or routine Wrong project, unsupported monitoring context, missing access or incorrect program selection. Verify the loaded program, routine/block, target controller and permissions.
Connection drops intermittently Network instability, cabling, switch issues, overloaded communications or device faults. Inspect link status, error counters, controller diagnostics and network health.

Do not repeatedly try random connection settings. Identify the failing layer and test it systematically.

14. Project Comparison and Version Control

Online work is only reliable when the engineer understands which project is actually running.

A controller may contain a different program from the latest file stored on the engineering computer. This can happen after emergency repairs, vendor interventions, undocumented online edits or incomplete backups.

A disciplined process is:

  1. Identify the controller and its current project state.
  2. Open the approved engineering project.
  3. Compare the project with the controller where supported.
  4. Investigate meaningful differences.
  5. Back up the authoritative version.
  6. Make only approved changes.
  7. Verify and test the change using the applicable platform workflow.
  8. Document the resulting revision and test outcome.

An upload may recover the program logic and supported configuration, but it may not recover all original comments, symbols, external documentation or source files. Preserve the original engineering project and revision history whenever possible.

15. Online Editing: Important Distinction

Some PLC platforms support editing logic while connected to the controller. The exact workflow and execution behavior depend on the platform and operation.

Online editing may involve stages such as:

  • Creating or preparing an edit.
  • Checking or verifying the change.
  • Testing the edit.
  • Accepting, assembling or committing the change.
  • Confirming the final controller and project state.

These stages are not identical across manufacturers. Some changes may affect execution immediately; others require a specific confirmation or deployment step.

Online editing is not simply an easier version of offline programming. A change can alter a live sequence, disable a permissive, affect timing or trigger an unexpected action.

Before an approved online change, establish the expected behavior, potential hazards, rollback plan, backup and verification method. Use the site's change-control process.

16. Forcing and Modifying Values: Preview of the Next Topic

A force and an ordinary value write are different operations.

  • Force: Overrides or substitutes a signal or I/O behavior according to the PLC platform's forcing mechanism.
  • Value modification / write: Changes a variable's value through a supported engineering operation.
  • Normal program execution: The PLC evaluates the logic according to its instructions, configuration and current inputs.

Forcing can make a program behave differently from the actual physical inputs. A forced input may indicate a condition that the sensor has not physically detected. Depending on the implementation, a forced output can create an unexpected machine action.

Therefore:

  • Do not force production I/O merely to make a sequence advance.
  • Do not write live tag values without authorization.
  • Check active forces and their status before and after approved testing.
  • Remove approved temporary forces after the test and verify the final force state.
  • Never bypass safety circuits or defeat safety functions as a troubleshooting shortcut.

The next topic, 02_Force_Modify, will cover this distinction and the associated safe procedures in detail.

17. Security and Change Governance

Online access can expose live control logic and, on authorized systems, permit changes. Treat it as privileged access to an industrial control system.

Good practices include:

  • Use approved engineering workstations and communication paths.
  • Follow controller access controls and role permissions.
  • Prefer read-only observation when diagnosing a fault.
  • Keep backups and version-controlled project files.
  • Record who made a change, why it was needed and how it was tested.
  • Follow production change-control and approval procedures.
  • Use approved network segmentation and avoid unauthorized network connections.
  • Do not bypass controller passwords or access restrictions.
  • Apply additional safeguards for safety controllers and safety-related programs.

18. Practical Motor-Start Troubleshooting Example

Situation

An operator presses Start, but the motor does not run.

The intended logic is:

Start_Request
    AND Auto_Mode
    AND Drive_Ready
    AND Interlocks_OK
    AND NOT Fault_Active
            |
            v
      Motor_Run_Request
            |
            v
      Drive_Run_Command
            |
            v
      Motor_Running_Feedback

Online diagnostic procedure

  1. Monitor Start_Request and confirm whether the PLC recognizes the start request.
  2. Check Auto_Mode and confirm that the machine is permitted to operate automatically.
  3. Check Drive_Ready and inspect drive status or diagnostics if it is false.
  4. Check each relevant interlock and identify the first unsatisfied condition.
  5. Check Fault_Active and identify the associated fault source.
  6. If the run request becomes true, check whether the drive command is issued.
  7. If the command is issued but running feedback remains false, trace the output path and inspect drive, wiring, contactor and feedback diagnostics as appropriate.
  8. Record the observed values and the identified failure point.

Do not force Drive_Ready, bypass Interlocks_OK or write Motor_Run_Request to make the motor run. Those actions can hide the actual fault and create a hazard.

Example observation record

Signal Observed value Interpretation
Start_Request TRUE PLC recognizes the start request.
Auto_Mode TRUE Automatic mode condition is satisfied.
Drive_Ready TRUE Drive-ready signal is present.
Interlocks_OK FALSE At least one required interlock is unsatisfied, assuming this tag is correctly implemented.
Fault_Active FALSE The monitored fault flag is not active.
Motor_Run_Request FALSE The program has not issued the run request.

Conclusion: Investigate the interlocks and their underlying conditions. Do not assume a PLC hardware failure when the observed logic already identifies an unsatisfied condition.

19. Online Monitoring Checklist

Before connecting

  • Correct machine and controller identified.
  • Correct network adapter, IP configuration and communication path selected.
  • Appropriate authorization obtained.
  • Correct engineering project and controller version identified.
  • Production state and applicable safety procedures checked.

After connecting

  • Controller identity confirmed.
  • Controller operating mode and fault state checked.
  • Offline and online project differences reviewed where supported.
  • Relevant tags, routines, timers and sequence steps monitored.
  • Observed values checked for plausibility and update status.
  • No unauthorized value writes, forces, mode changes or online edits performed.

Before leaving

  • Findings and relevant diagnostic messages recorded.
  • Approved changes documented and verified.
  • Temporary test conditions and forces reviewed.
  • Controller and machine left in the approved operating state.
  • Engineering project and backup revision stored appropriately.
  • Connection closed when appropriate.

21. Interview Questions and Answers

Q1. What does Go Online mean in PLC engineering software?

It establishes communication between engineering software and a controller or supported simulator, enabling live monitoring and other authorized online operations.

Q2. Does going online mean the PLC is running?

No. Online describes the communication state. RUN, PROGRAM or STOP describes the controller's operating mode, with exact mode names and behavior depending on the platform.

Q3. What is the difference between upload and download?

Upload retrieves supported controller contents to the engineering environment. Download transfers the engineering project or supported changes to the controller. Download can affect execution and must be treated as a controlled operation.

Q4. Why compare the offline and online projects before downloading?

To identify differences and prevent accidental overwriting of the approved controller program with an outdated, incomplete or incorrect project.

Q5. Why is a successful ping insufficient to prove PLC connectivity?

Ping tests IP-level reachability when ICMP is available. It does not verify the PLC programming protocol, controller access permissions, correct engineering path or compatibility.

Q6. What is a watch table?

A view used to monitor selected tags or variables, such as inputs, permissives, timers, counters, sequence steps and outputs.

Q7. How do you diagnose a sequence that is stuck?

Monitor the active step, its transition conditions, permissives, timers, faults and reset conditions. Find the first condition preventing the expected transition.

Q8. Why can an online input value differ from the physical sensor state?

Possible causes include wiring faults, module problems, mapping errors, filtering, communication delays, stale data or forcing. The electrical signal and the program's interpretation must be checked separately.

Q9. What is the difference between cross-reference and online monitoring?

Cross-reference shows where a tag is used in the program. Online monitoring shows its live value or logic state.

Q10. What precautions are required before online editing?

Confirm authorization, controller identity, project revision, machine conditions, backups, potential hazards, change-control requirements, rollback plan and verification procedure.

Q11. Can successful program verification prove that the machine is safe?

No. Verification checks supported program and configuration requirements. Safety also depends on the machine design, hardware, wiring, safety functions, validated behavior and operating procedures.

Q12. What is the safest default approach when troubleshooting online?

Start with read-only observation, trace the actual signal path, identify the first failing condition, document evidence and make only authorized changes.

22. Practical Exercises

Perform these exercises in a simulator, training rack or approved test system, not by experimenting with live production outputs.

  1. Establish an online connection: Identify the controller, select the correct communication interface and confirm the controller identity.
  2. Monitor a Boolean signal: Observe a test input and the associated ladder logic as the input changes.
  3. Monitor a timer: Record the preset, accumulated value and completion state.
  4. Build a watch table: Include a start request, mode bit, permissive, fault flag, output command and feedback.
  5. Trace a blocked sequence: Identify which transition condition prevents the next step.
  6. Compare project versions: Use a test project to identify differences between local and controller versions.
  7. Inspect diagnostics: Locate controller or module diagnostic information and correlate it with an observed fault.
  8. Trace a motor command: Follow the logic from the request to the output command and feedback without forcing signals or creating hazardous motion.
