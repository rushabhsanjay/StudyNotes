1. Definition

PLC program structure defines how control logic is organized, when it executes, and how different sections of the program interact.

A PLC project can contain hundreds or thousands of instructions. Putting everything into one enormous program would make troubleshooting, testing, modification, and maintenance unnecessarily difficult. Program structure divides the logic into manageable sections with defined responsibilities.

The main concepts are:

  • Task: Defines when and how a group of program logic executes on platforms that use a task-based execution model.
  • Main cycle: The repeated execution cycle of a cyclic PLC program.
  • Program Organization Block (OB): Siemens terminology for an organizational unit that controls or responds to a particular execution event.
  • Function (FC): A reusable logic unit that generally does not retain its own instance-specific internal state between calls.
  • Function Block (FB): A reusable logic unit that uses instance data to retain state between calls.
  • Routine or subroutine: A named section of logic called or scheduled by another part of the program, depending on the PLC platform.

These terms are related, but they are not interchangeable across all PLC brands.

2. Why Program Structure Matters

Consider a robotic production line with several stations. Each station may require:

  • Input processing.
  • Automatic sequence control.
  • Robot communication.
  • Interlocks and permissives.
  • Fault detection.
  • Timers and counters.
  • HMI communication.
  • Diagnostics and recovery logic.

A poorly structured program mixes all these responsibilities together. A well-structured program separates them into logical units.

Example:

PLC APPLICATION
|
+-- Main Execution
|   |
|   +-- Read and process machine inputs
|   +-- Execute station sequences
|   +-- Update outputs
|   +-- Update machine status
|
+-- Station Logic
|   |
|   +-- Station 1
|   +-- Station 2
|   +-- Station 3
|
+-- Common Functions
|   |
|   +-- Scaling
|   +-- Alarm evaluation
|   +-- Data validation
|   +-- Equipment calculations
|
+-- Diagnostics
    |
    +-- Fault detection
    +-- Timeout monitoring
    +-- Diagnostic records

This is a conceptual architecture, not a universal PLC execution order. Actual scheduling depends on the controller and project configuration.

3. The Main PLC Cycle

3.1 What Is a Scan Cycle?

In a typical cyclic PLC application, the controller repeatedly executes logic in a defined sequence.

A simplified model is:

+---------------------------+
| Read or update inputs     |
+-------------+-------------+
              |
              v
+---------------------------+
| Execute control logic     |
+-------------+-------------+
              |
              v
+---------------------------+
| Update physical outputs   |
+-------------+-------------+
              |
              v
+---------------------------+
| Communication and system  |
| processing as applicable  |
+-------------+-------------+
              |
              +-----------> Repeat

This is a teaching model. Real controllers may update inputs and outputs asynchronously, use process-image mechanisms, execute multiple tasks, and perform communication or housekeeping at different points in the cycle.

3.2 What Happens During a Scan?

Suppose a PLC controls a conveyor motor.

At the beginning of a logic execution, the program reads or accesses the relevant input data. It evaluates the start command, safety and process interlocks, and stop conditions. The resulting logic determines the commanded output.

Example:

Start_PB       = TRUE
Stop_PB        = FALSE
Safety_OK      = TRUE
Drive_Fault    = FALSE

Conceptually:

Motor_Command =
    Start_PB
    AND NOT Stop_PB
    AND Safety_OK
    AND NOT Drive_Fault

The logic evaluates to TRUE, so the program can command the motor output, subject to the actual control design and the controller's execution semantics.

A standard PLC logic condition must not replace required safety-rated control functions.

3.3 Scan Time

Scan time is the time taken to execute a particular cyclic program or cycle, as defined by the platform.

For example, if a cyclic program takes 8 ms to execute, it may complete approximately 125 executions per second under stable conditions, provided that the 8 ms represents the complete relevant cycle and no scheduling constraints interfere.

\[ \text{Execution rate} \approx \frac{1}{\text{Cycle time}} \]

For an 8 ms cycle:

\[ \frac{1}{0.008}=125\text{ executions/second} \]

A shorter cycle generally allows faster response to changes, but actual response time also depends on input filtering, I/O update timing, task scheduling, communication, and output hardware.

3.4 Why Execution Order Matters

Consider two operations in the same execution path:

Operation 1:
Batch_Count := Part_Count

Operation 2:
Part_Count := Part_Count + 1

If Operation 1 executes first, Batch_Count receives the old count. If the increment executes first, the copied value may be the new count.

Similarly, if multiple routines write to the same destination, the final result may depend on execution order.

Maintenance implication: When a PLC value behaves unexpectedly, inspect not only the instruction itself but also where and when that instruction executes.

4. Tasks

4.1 What Is a Task?

A task is a controller scheduling mechanism used by PLC platforms that support task-based execution. It determines when associated programs execute, according to configured triggers, priorities, and scheduling rules.

Common task types include:

Task type General purpose Example
Continuous Repeated execution whenever processor time is available for that task General machine control
Periodic Execution at a configured interval Control logic requiring a regular execution rate
Event-triggered Execution in response to a configured event Processing a supported event or input trigger

The exact task types and behavior depend on the PLC family.

4.2 Continuous Task

A continuous task executes repeatedly when scheduled. Its cycle time can vary depending on program workload, other tasks, and controller resources.

Typical uses include general machine logic that does not require a fixed periodic execution interval.

4.3 Periodic Task

A periodic task is scheduled to execute at a configured interval.

For example:

Task interval = 10 ms

This requests execution every 10 ms, subject to the controller's supported configuration and scheduling behavior.

Periodic execution is useful when a specific control process requires a defined update interval. However, a task that takes longer than its allowed interval may cause an overrun or other platform-specific fault.

4.4 Event-Triggered Task

An event-triggered task runs when a configured event occurs, if the controller supports that event source.

Potential applications include:

  • Processing supported input events.
  • Responding to specific controller events.
  • Handling certain high-priority operations.

Not every physical input or event can trigger a task on every PLC. Hardware capability and configuration must be checked.

4.5 Task Priority

Some PLCs allow tasks to have different execution priorities.

A higher-priority task may interrupt or pre-empt a lower-priority task, depending on the controller's scheduling rules.

For example:

Higher priority:
Fast control or time-critical logic

Lower priority:
Non-critical reporting or slower supervisory calculations

This is a conceptual example, not a universal recommended configuration. Poorly chosen priorities can delay other work, increase jitter, or cause overruns.

4.6 Tasks in Rockwell and Siemens

Concept Rockwell Logix Siemens S7
Scheduling mechanism Tasks Operating-system execution events and OBs
Main cyclic execution Commonly a continuous task, if configured Commonly cyclic OB execution
Periodic execution Periodic tasks Time-driven cyclic interrupt OBs, where supported
Event-driven execution Supported event tasks, depending on controller Event-associated OBs, depending on CPU
Logic organization Programs and routines OBs, FCs, FBs, and associated data blocks

Do not assume that a Rockwell task and a Siemens OB are equivalent objects. They serve related scheduling or organizational purposes, but their execution models differ.

5. Siemens Program Organization Blocks (OBs)

5.1 What Is an OB?

In Siemens S7 PLCs, an Organization Block (OB) is an interface between a particular operating-system event and the user's control program.

An OB determines the circumstances under which its associated logic is executed. Depending on the OB type and CPU, this may include cyclic execution, startup, time-driven events, hardware interrupts, or error handling.

5.2 Common OB Categories

OB category General purpose
Cyclic program OB, such as OB1 on supported S7 CPUs Main cyclic program execution
Startup OBs Execute during supported startup events
Cyclic interrupt OBs Execute at a configured time interval
Hardware interrupt OBs Respond to supported hardware events
Time-error or diagnostic OBs Handle particular execution or diagnostic events, where supported

Exact OB numbers, availability, priority, and behavior vary by S7 CPU family and firmware.

5.3 OB1 and the Main Cycle

On many Siemens S7 systems, OB1 is the main cyclic program organization block.

A simplified call structure is:

OB1
 |
 +-- FC_Main_Sequence
 |
 +-- FB_Conveyor
 |     |
 |     +-- Instance data
 |
 +-- FC_Alarm_Processing
 |
 +-- FC_Data_Processing

This illustrates a possible structure. Actual calls and execution order are determined by the configured program and the instructions inside each block.

If OB1 calls several blocks sequentially, those calls execute in the order encountered, subject to the CPU's execution model and any interruptions by higher-priority events.

5.4 Startup OBs

Startup logic can initialize variables, prepare internal states, or establish a known program condition.

However, startup code must distinguish between values that should be initialized and values that should be retained.

For example, automatically resetting a batch count on every startup may destroy required production continuity. Conversely, blindly restoring an old machine state can be unsafe.

Startup behavior must be designed deliberately, with appropriate validation and machine-state checks.

6. FC, FB, and Instance Data

The detailed distinction between FCs and FBs is important enough to receive a dedicated topic next, but the basic architecture belongs here.

6.1 Function (FC)

An FC is a callable logic block. In Siemens S7 programming, an FC does not have its own instance data block in the same way an FB does.

An FC is suitable for operations such as:

  • Calculating a scaled engineering value.
  • Evaluating a range.
  • Converting or validating data.
  • Calculating a derived machine status.
  • Performing reusable logic that does not require instance-specific retained state.

Example:

FC_Scale_Pressure
    Input: Raw_Value
    Input: Raw_Min
    Input: Raw_Max
    Output: Pressure_Bar

This is a conceptual interface. The actual block interface depends on the programming environment.

6.2 Function Block (FB)

An FB is a callable logic block that uses associated instance data on Siemens S7 systems. That data can retain values between calls according to the block's declaration and memory behavior.

Examples include:

  • Conveyor control.
  • Motor control.
  • Valve sequencing.
  • Robot handshake management.
  • A station-level sequence controller.

Conceptually:

FB_Conveyor
    Inputs:
        Start_Request
        Stop_Request
        Safety_OK

    Outputs:
        Running
        Faulted

    Internal state:
        Start_Timer
        Sequence_State
        Fault_Latched

Each instance can maintain its own state, allowing the same FB design to control multiple conveyors with different parameters and operating conditions.

For example:

FB_Conveyor_1 + Instance_Data_1
FB_Conveyor_2 + Instance_Data_2
FB_Conveyor_3 + Instance_Data_3

The three instances share the same general logic design but have separate instance data.

6.3 Rockwell Routines and Programs

Rockwell Logix uses a different organizational model.

A simplified structure is:

Task
 |
 +-- Program
       |
       +-- Main Routine
       |
       +-- Other Routines

A routine contains executable logic. A program groups routines and associated tags. A task schedules programs for execution.

Rockwell's Add-On Instructions can provide reusable logic with parameters and internal behavior, but they are not simply identical to Siemens FBs in every implementation detail.

6.4 Mitsubishi PLCs

Mitsubishi PLC projects also organize logic into program units and reusable components, with the exact terminology and execution model depending on the CPU series and engineering software.

The transferable principle is to distinguish:

  • What schedules execution.
  • What groups logic.
  • What contains reusable behavior.
  • What stores instance-specific state.

The labels differ between manufacturers. The underlying architectural questions remain useful.

7. Program Calls and Execution Flow

A block can exist in the project without executing. It must be called or scheduled through the configured program structure, unless it is an event-associated unit that executes through its own trigger mechanism.

Consider:

Main_Program
    |
    +-- Call FC_Sequence
    |
    +-- Call FB_Conveyor
    |
    +-- Call FC_Alarm_Check

If FC_Sequence is never called, its logic will not execute merely because it exists in the project.

Likewise, a routine that is called only under a condition may execute intermittently rather than every scan.

This creates a common troubleshooting problem: a tag may be correct, and the block may contain correct logic, but the block may not be executing when expected.

Three questions for any block

  1. Who calls or schedules it?
  2. Under what conditions does it execute?
  3. What data does it read, modify, or retain?

These questions often narrow down a program-structure fault faster than inspecting every instruction in the block.

8. Data Scope and State

Program structure also determines how data is organized and accessed.

Common categories include:

  • Local data: Used within a block or routine.
  • Interface data: Passed into or out of a block.
  • Instance data: Stored separately for a particular function-block instance, where supported.
  • Global data: Available to multiple parts of the program under the platform's scope rules.
  • I/O data: Represents or accesses physical input and output channels or process-image data.

Example:

Global:
    Machine_Mode

Conveyor instance:
    Conveyor_1.Running
    Conveyor_1.Faulted
    Conveyor_1.Sequence_State

Conveyor 2 instance:
    Conveyor_2.Running
    Conveyor_2.Faulted
    Conveyor_2.Sequence_State

Instance-style names are illustrative. Exact addressing and tag access depend on the platform.

Good data scope reduces unintended coupling. If every routine can modify every important variable, tracking ownership becomes unnecessarily difficult.

9. Program Structure and Machine Response

The structure of the program affects how quickly and predictably the machine responds.

Suppose a robot sends a Cycle_Complete signal. The PLC must detect it, update the station sequence, and issue the next command.

A conceptual flow is:

Robot_Cycle_Complete
          |
          v
Input / Communication Update
          |
          v
Robot_Interface_Logic
          |
          v
Station_Sequence
          |
          v
Next_Command
          |
          v
Output / Communication Update

The total response time depends on more than the program's scan time. It may include:

  • Input filtering and update intervals.
  • Network or fieldbus update time.
  • Task scheduling and priority.
  • Execution time of the relevant logic.
  • Output update and device response time.
  • Handshake logic and timeout settings.

For maintenance, this distinction matters. A slow response does not automatically mean the PLC processor is slow. The delay may be in a network, a remote I/O update, a robot handshake, or the program's execution path.

10. Common Program-Structure Faults

Symptom Possible cause Investigation
Logic never executes Block is not called or its event is not triggered Trace the call or scheduling path
Logic executes less often than expected Conditional call, task interval, or scheduling issue Check task configuration and call conditions
Response is delayed Task loading, long execution path, I/O or communication delay Measure timing at each stage
One machine works but another does not Incorrect instance data or parameter assignment Compare instances and their interfaces
State unexpectedly resets Initialization or state-management logic Check startup code and block state
Values are overwritten Multiple writers or incorrect call order Cross-reference destinations and execution order
Task or cycle overrun occurs Execution exceeds available time or configured limits Check controller diagnostics and execution time
Startup causes unexpected motion or loss of count Inappropriate startup initialization or restored state Review startup behavior and permissives
Alarm logic works intermittently Logic executes conditionally or is scheduled incorrectly Trace the alarm routine's execution path

11. Practical Maintenance Method

When troubleshooting an unfamiliar PLC program, use this sequence:

  1. Identify the PLC make, CPU model, firmware, and engineering software.
  2. Find the main execution mechanism: cyclic OB, continuous task, or another configured entry point.
  3. Trace the execution path to the machine or station logic.
  4. Identify the block or routine responsible for the affected function.
  5. Check its execution conditions and any calls that may be skipped.
  6. Monitor its inputs, outputs, internal state, and relevant timers.
  7. Check for multiple writers, startup resets, and interactions with other tasks.
  8. Inspect task or cycle diagnostics if timing is suspected.
  9. Make controlled changes only after understanding the execution path and the machine's safe state.

Do not force a signal or modify a running production sequence simply to prove a theory. Use a simulator, a controlled test condition, or an approved maintenance procedure whenever possible.

12. Best Practices for Program Structure

  • Give blocks and routines names that reflect their responsibilities.
  • Separate machine sequences, device control, communications, diagnostics, and calculations where practical.
  • Keep execution paths easy to trace.
  • Define clear interfaces between reusable logic units.
  • Avoid unnecessary dependencies on global variables.
  • Establish clear ownership for important state and output tags.
  • Monitor task execution time and overruns.
  • Use instance-specific state when multiple devices require independent sequences.
  • Document startup behavior and retained values.
  • Avoid putting time-critical control logic into a low-priority or unpredictable execution path.
  • Follow the platform's rules for task scheduling, data consistency, and interrupt behavior.
  • Keep safety-related functions within the required safety architecture.

13. Interview Questions and Answers

Q1. What is a PLC scan cycle?

A repeated execution cycle in which the controller processes program logic and updates or accesses I/O according to its execution model.

Q2. What is the difference between a task and a routine?

A task schedules execution on platforms that use a task-based model. A routine is a section of executable logic. A task may schedule programs that contain multiple routines.

Q3. What is OB1 in Siemens PLCs?

On many Siemens S7 systems, OB1 is the main cyclic program organization block. Its availability and exact behavior depend on the CPU family.

Q4. What is the difference between an FC and an FB?

In Siemens S7 programming, an FC does not have its own instance data block like an FB. An FB uses associated instance data, which can retain instance-specific state between calls.

Q5. Does creating a block make it execute automatically?

Not necessarily. It generally must be called by an executing block or scheduled through a configured execution mechanism.

Q6. What is a periodic task?

A task configured to execute at a specified interval, subject to the controller's scheduling and execution constraints.

Q7. Why can two instances of the same FB behave differently?

They may have different input parameters, instance data, initial conditions, or execution conditions.

Q8. What causes a task overrun?

The task takes longer than the configured interval or permitted execution time, depending on the controller's definitions and diagnostics.

Q9. Why does execution order matter?

One routine may read a value before another routine updates it, or a later instruction may overwrite an earlier result.

Q10. How do you find logic that is not executing?

Trace it back to the main execution mechanism, inspect its calls and conditions, and verify that the relevant task or event is actually running.

14. Practical Exercises

Use a simulator or an offline project.

Exercise 1: Trace the Main Cycle

Create a simple program that:

  • Reads a simulated start input.
  • Evaluates a run permissive.
  • Updates a simulated motor command.
  • Calculates a running status.
  • Updates a diagnostic tag.

Draw the call sequence and identify where each operation executes.

Exercise 2: Compare Conditional and Repeated Execution

Create a routine that copies one tag into another.

  • Call it every cycle.
  • Observe how the destination follows the source.
  • Then execute the call only when a simulated event occurs.
  • Compare the behavior and identify when the destination changes.

Exercise 3: Use Multiple Instances

Create two simulated conveyor instances using the platform's reusable block mechanism.

Give each instance different:

  • Start requests.
  • Timeout settings.
  • Fault states.
  • Sequence states.

Verify that one instance's internal state does not unintentionally control the other.

Exercise 4: Investigate Timing

Record the relevant task interval or cyclic execution time available in the simulator or diagnostic tools.

Compare it with a simulated process response. Identify which parts of the response are caused by program execution and which depend on I/O or communication timing.

15. Final Mental Model

Think of PLC program structure as an execution hierarchy:

Execution mechanism
        |
        v
Task or organization block
        |
        v
Program or main logic
        |
        v
Routines, FCs, FBs, or equivalent blocks
        |
        v
Instructions and data operations
        |
        v
Control decisions and machine response

The exact hierarchy differs by vendor, but the questions remain the same: what triggers execution, what logic runs, what state is retained, and how does the result reach the machine?
