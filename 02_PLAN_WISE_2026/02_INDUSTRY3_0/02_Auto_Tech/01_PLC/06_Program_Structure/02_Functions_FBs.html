1. Definition

Functions and function blocks are reusable units of PLC logic. Instead of writing the same control logic repeatedly for every motor, conveyor, valve, robot interface, or machine station, the programmer develops a common logic unit and reuses it with different inputs, outputs, and parameters.

The main benefits are:

  • Reduced duplicate code.
  • Consistent machine behavior.
  • Easier testing and troubleshooting.
  • Faster commissioning of similar equipment.
  • Easier maintenance and future modification.
  • Better separation between machine logic and individual device logic.

The central principle is write the logic once, define its interface clearly, and reuse it wherever the same behavior is required.

2. Why Reusable Logic Is Needed

Consider a production line with 20 conveyors. Each conveyor needs some combination of:

  • Start and stop commands.
  • Run feedback.
  • Fault feedback.
  • Start permissives.
  • Start timeout monitoring.
  • Fault handling.
  • Running status.

One approach is to write the complete logic separately for every conveyor. That creates duplicated code and makes future changes difficult.

Suppose a start-timeout requirement changes from 3 seconds to 4 seconds. With duplicated logic, the programmer may have to modify 20 separate sections and verify every modification.

A reusable design instead creates one common conveyor-control block and instantiates it for each conveyor.

Common Conveyor Logic
        |
        +-- Conveyor 1 instance
        |
        +-- Conveyor 2 instance
        |
        +-- Conveyor 3 instance
        |
        +-- ...
        |
        +-- Conveyor 20 instance

The common logic is shared, but each conveyor has its own input signals, output signals, and required operating state.

Important: Reuse does not mean that every device must behave identically. Device-specific differences should be handled through parameters, clearly defined options, or separate specialized logic.

3. Function (FC)

3.1 What Is a Function?

In Siemens S7 programming, a Function (FC) is a reusable logic block that can receive inputs, perform calculations or logic operations, and return outputs.

An FC does not have its own instance data block in the same way an FB does. It can use local variables during execution, and its outputs can be used by the calling program.

Typical applications include:

  • Analog scaling.
  • Engineering-unit conversion.
  • Range checking.
  • Mathematical calculations.
  • Data validation.
  • Generating a derived status.
  • Evaluating a set of inputs against defined conditions.

3.2 Example: Pressure Scaling Function

Suppose multiple machines use pressure transmitters with the same configured raw range and engineering range.

Instead of implementing the scaling formula separately for each sensor, create a reusable function.

Conceptual interface:

FC_Scale_Pressure

Inputs:
    Raw_Value
    Raw_Min
    Raw_Max
    EU_Min
    EU_Max

Output:
    Pressure_Bar

The function implements the linear scaling equation:

\[ EU = \frac{Raw-Raw\_{\min}}{Raw\_{\max}-Raw\_{\min}} \times(EU\_{\max}-EU\_{\min})+EU\_{\min} \]

Each sensor can use the same function with its own raw value and configured limits.

For example:

Pressure_Station_1 =
    FC_Scale_Pressure(Raw_Pressure_1, ...)

Pressure_Station_2 =
    FC_Scale_Pressure(Raw_Pressure_2, ...)

This is conceptual pseudocode, not exact vendor syntax.

The implementation must handle invalid ranges, such as Raw_Max = Raw_Min, and should validate raw values and sensor-fault conditions as required.

3.3 Characteristics of an FC

  • Encapsulates a specific calculation or logic operation.
  • Accepts inputs and produces outputs through its interface.
  • Can be called from multiple locations.
  • Does not have its own Siemens FB-style instance data block.
  • Is useful when instance-specific retained state is not required.

An FC can still read or modify external/global data if its implementation allows it. That is technically possible, but excessive reliance on global state makes reusable logic harder to test and maintain.

4. Function Block (FB)

4.1 What Is a Function Block?

In Siemens S7 programming, a Function Block (FB) is a reusable logic unit that operates with associated instance data.

That instance data can retain internal values between calls according to the data declarations, CPU behavior, and memory configuration.

An FB is particularly useful when equipment must maintain its own operating state.

Examples include:

  • Motor control.
  • Conveyor sequencing.
  • Valve control.
  • Robot handshake management.
  • Pneumatic-cylinder sequencing.
  • Machine-station control.
  • Fault and timeout management.

4.2 Example: Conveyor Control FB

Consider a conveyor that requires a start command, stop command, run feedback, and start timeout.

A conceptual interface might be:

FB_Conveyor

Inputs:
    Start_Request
    Stop_Request
    Run_Feedback
    Drive_Fault
    Permissive_OK

Parameters:
    Start_Timeout

Outputs:
    Run_Command
    Running
    Faulted

Internal state:
    Start_Timer_State
    Sequence_State
    Fault_Latched

The FB contains the reusable control logic. Each conveyor instance receives its own signals and has its own associated state.

For example:

FB_Conveyor_1 + Instance_Data_1
FB_Conveyor_2 + Instance_Data_2
FB_Conveyor_3 + Instance_Data_3

The three conveyors can use the same logic while maintaining separate operating states.

4.3 Why Instance Data Matters

Imagine that Conveyor 1 is waiting for run feedback while Conveyor 2 is already running.

If both conveyors use the same timer state and fault latch, one conveyor's behavior could interfere with the other.

Separate instance data allows each conveyor to retain its own:

  • Timer state.
  • Sequence step.
  • Fault latch.
  • Previous operating state.
  • Internal diagnostic information.

This is one of the most important reasons to use FBs for equipment control.

4.4 Does an FB Automatically Retain Everything?

No. An FB's associated instance data allows state to persist between calls, but persistence across a power cycle or restart depends on the variable declarations, retention settings, startup logic, and controller behavior.

Three concepts must be kept separate:

  • Persistence between calls: Internal values can remain available when the FB is called again.
  • Persistence between scans: Values may remain stored while the program executes repeatedly.
  • Persistence across restart: Values survive a controller restart or power interruption only when the relevant memory and initialization behavior support it.

Do not assume that every internal value is automatically retained through a power cycle.

5. FC Versus FB

Feature FC FB
Main purpose Reusable calculations or logic Reusable logic that may maintain instance-specific state
Siemens instance DB Not required Normally associated with an instance DB or supported instance-data arrangement
Internal state between calls No dedicated instance data of its own Can retain state in instance data
Typical examples Scaling, comparison, calculations Motor, conveyor, valve, sequence control
Multiple instances Can be called repeatedly with different inputs Each instance can maintain separate state
Best suited for Stateless or externally managed operations Stateful equipment behavior

The choice is not simply based on block size. A small timer-based controller may need an FB because it requires independent state, while a large calculation may be perfectly suitable for an FC.

6. Rockwell, Siemens, and Mitsubishi Terminology

The general engineering concept is portable, but the exact implementation differs by vendor.

Concept Siemens S7 / TIA Portal Rockwell Logix Mitsubishi PLCs
Reusable calculation FC Routine, Add-On Instruction, or other reusable logic arrangement Function or reusable program component where supported
Reusable stateful control FB with instance data Add-On Instruction with its parameters and internal data, or another structured design Function block where supported
Execution organization OBs call FCs and FBs Tasks schedule programs; routines and instructions execute within them Depends on CPU family and project structure
Instance-specific state FB instance data AOI instance data and other supported tag structures Depends on the function-block or program implementation

A Siemens FB and a Rockwell Add-On Instruction have related purposes, but they are not identical in their execution model, data handling, interface rules, or programming behavior.

When maintaining an existing machine, use the native design conventions of its PLC platform rather than translating every term literally.

7. Inputs, Outputs, Parameters, and Internal Variables

A reusable block is only as useful as its interface.

A well-designed interface separates the information entering the block, the results leaving it, and the internal data used to manage its behavior.

7.1 Inputs

Inputs provide information to the block.

For a motor-control block, these might include:

  • Start request.
  • Stop request.
  • Drive fault.
  • Run feedback.
  • Permissive status.

Inputs should have clear meanings. For example, Permissive_OK should have a documented definition rather than being a mysterious Boolean that someone created during commissioning at 2 a.m.

7.2 Outputs

Outputs communicate the block's results.

Examples include:

  • Run command.
  • Running status.
  • Fault status.
  • Start timeout.
  • Ready status.

A block should define whether an output represents a request, a command, a physical feedback signal, or a calculated status. Those concepts are not interchangeable.

7.3 Parameters

Parameters configure behavior without changing the core logic.

For example:

Start_Timeout = 3.0 seconds

Two conveyors might use the same FB with different timeout settings.

Parameters may also define operating limits, scaling ranges, modes, and other configuration values. Whether a parameter can change during execution depends on the platform and its interface semantics.

7.4 Internal Variables

Internal variables support the block's implementation.

Examples include:

  • Current sequence step.
  • Timer state.
  • Previous input state.
  • Internal fault latch.
  • Temporary calculation result.

Internal variables should not be exposed unnecessarily. A clear interface helps other programmers use the block without needing to understand every implementation detail.

8. Designing a Reusable Motor-Control Block

Consider a motor driven by a VFD.

The control block should not merely switch a Boolean output. It should define how requests, permissives, feedback, and faults interact.

A conceptual interface:

FB_Motor

Inputs:
    Start_Request
    Stop_Request
    Permissive_OK
    Drive_Fault
    Run_Feedback

Parameters:
    Start_Timeout

Outputs:
    Run_Command
    Running
    Start_Timeout_Fault
    Faulted

A simplified control relationship could be:

Run_Command =
    Start_Request
    AND NOT Stop_Request
    AND Permissive_OK
    AND NOT Drive_Fault
    AND NOT Faulted

This is an illustrative Boolean relationship, not a complete motor-control design. Real implementations must account for stop priorities, command latching, feedback timeouts, restart behavior, drive interfaces, operating modes, and the machine's safety architecture.

Expected behavior

Condition Expected response
Start requested, permissives valid, no fault Start command may be issued
Stop requested Stop command takes priority according to the design
Permissive lost Command is removed or the defined response is initiated
Drive fault active Normal run command is inhibited
Run feedback does not arrive in time Start timeout is detected
Fault is cleared Restart behavior follows the documented reset and permissive rules

Why reuse helps

The same control block can be used for multiple motors, while each instance has separate feedback, timeout state, and fault information.

If the timeout logic needs improvement, the common block can be updated and validated instead of manually editing a dozen duplicated implementations.

However, a change to a common block can affect every instance that uses it. Reusable logic reduces duplication, but it also increases the importance of regression testing.

9. Stateful Logic and Scan Execution

A common mistake is to assume that a reusable block executes only once when called.

In many PLC architectures, a block called from cyclic logic executes on each call. If its caller runs every cycle, the block can execute repeatedly.

For a timer-based sequence, repeated execution may be exactly what is required.

For an event-driven operation, the block may need an edge detector or an explicit state transition to prevent repeated actions.

Example:

Cycle_Complete
      |
      v
Detect rising edge
      |
      v
Increment completed-cycle count

Without edge detection or equivalent logic, a signal that remains true for several scans could increment a counter repeatedly, depending on the counter logic.

Similarly, if a block writes an output every scan, another block writing to the same output can create unexpected behavior.

Best practice: Define the execution conditions and output ownership of every reusable block.

10. Reusable Logic for Machine Stations

A manufacturing line can use a common station-control design.

FB_Station
    |
    +-- Station 1 instance
    |
    +-- Station 2 instance
    |
    +-- Station 3 instance

Each station can have its own:

  • Operating mode.
  • Sequence state.
  • Timeout monitoring.
  • Fault state.
  • Equipment-ready status.
  • Cycle-complete status.

However, stations may have different hardware or process requirements. A station that controls a clamp and a robot may need specialized logic beyond the common station template.

A practical architecture often combines common reusable blocks with station-specific sequence logic.

11. Common Design Mistakes

Mistake Consequence Better approach
Reusing logic without separate instance state Devices interfere with one another Use independent instance data where required
Putting every variable in global scope Hidden dependencies and difficult troubleshooting Use clear interfaces and suitable data scope
Creating one enormous universal block Excessive complexity and many special cases Divide logic by responsibility
Duplicating identical logic everywhere Inconsistent behavior after modifications Use reusable blocks where appropriate
Changing a shared block without testing instances Unexpected effects across many devices Perform regression testing
Unclear input and output names Incorrect block integration Use explicit names and documented meanings
Assuming FB data always survives restart Unexpected initialization or retained states Verify retention and startup configuration
Calling logic under unexpected conditions Missing or repeated state transitions Trace call conditions and execution order
Using ordinary control logic as a safety function Inadequate safety protection Use the required safety-rated architecture

12. Testing Reusable Logic

A reusable block should be tested independently where practical, then tested again in the context of the complete machine.

Stage 1: Interface testing

Verify that the block accepts the correct inputs and produces the expected outputs.

Stage 2: Normal-operation testing

Test the expected sequence with valid inputs and feedback.

Stage 3: Boundary testing

Test values at configured limits, timeout boundaries, and transitions between states.

Stage 4: Fault testing

Simulate missing feedback, invalid data, lost permissives, and fault signals.

Stage 5: Multi-instance testing

Run multiple instances simultaneously. Confirm that one instance's state does not affect another.

Stage 6: Integration testing

Test the block within the complete station or line, including HMI commands, PLC-to-PLC communication, drives, robots, and relevant interlocks.

Stage 7: Regression testing

After modifying a shared block, repeat the tests that verify its existing behavior across all relevant instances.

For industrial equipment, simulation and offline validation should be followed by approved commissioning tests under controlled conditions.

13. Interview Questions and Answers

Q1. What is reusable logic in a PLC?

Logic developed once and used in multiple places through a defined interface, reducing duplication and promoting consistent behavior.

Q2. What is the main difference between an FC and an FB in Siemens S7?

An FC does not have its own instance data block like an FB. An FB uses associated instance data and is suitable for logic requiring instance-specific state.

Q3. Why use an FB for a motor or conveyor?

The block can manage the equipment's operating logic, timer state, sequence state, and fault information independently for each instance.

Q4. Can the same FB control several motors?

Yes. Multiple instances can use the same block logic while maintaining separate instance data and receiving different signals and parameters.

Q5. Does a reusable block execute automatically?

Not simply because it exists. It must be called or scheduled through the program's configured execution mechanism.

Q6. What happens if a common block is modified?

The modification may affect all instances using that block. Regression testing is necessary to verify that existing applications continue to behave correctly.

Q7. What is an instance data block?

In Siemens S7 programming, it stores data associated with an FB instance, including its instance-specific variables and state according to the block's declarations.

Q8. Why are clear interfaces important?

They define what data a block needs and what results it produces, reducing hidden dependencies and making testing and integration easier.

Q9. What is the difference between reusable logic and a library?

Reusable logic is the logic itself and its implementation. A library is an organized collection of reusable components, types, templates, or related engineering assets.

Q10. Are Siemens FBs and Rockwell Add-On Instructions identical?

No. They address related reuse requirements, but their programming models, interfaces, execution behavior, and data-handling rules differ.

14. Practical Exercises

Complete these exercises in a simulator or offline project.

Exercise 1: Create a reusable scaling function

Create a function that accepts a raw analog value and range parameters and returns an engineering-unit value.

Test:

  • Minimum and maximum inputs.
  • Midpoint values.
  • Invalid ranges.
  • Values outside the configured range.

Exercise 2: Create a motor-control FB

Develop a motor-control block with simulated start and stop requests, permissive status, drive fault, run feedback, and start timeout.

Test:

  • Normal start and stop.
  • Missing run feedback.
  • Fault during operation.
  • Loss of permissive.
  • Reset and restart behavior.

Exercise 3: Create multiple instances

Use the same block for three simulated motors.

Give each motor different inputs and timeout parameters. Confirm that each motor maintains its own operating state and that a fault on one motor does not automatically fault the others unless the designed interlock requires it.

Exercise 4: Modify and regression-test

Change a shared timeout or fault-handling rule. Repeat the tests for all three instances and verify that the change has not introduced unintended behavior.

15. Final Mental Model

Think of reusable PLC logic as a separation between a common design and each equipment instance.

Reusable logic design
        |
        +-- Instance 1 + its data
        |
        +-- Instance 2 + its data
        |
        +-- Instance 3 + its data
  • FC: Reusable logic, commonly suited to calculations and operations without its own instance-specific state.
  • FB: Reusable logic with associated instance data, suited to stateful equipment behavior.
  • Interface: Defines inputs, outputs, and parameters.
  • Instance: A particular use of the reusable logic with its own associated data.
  • Testing: Verifies the block itself and every relevant application that uses it.

The goal is not to create the fewest blocks possible. It is to create blocks that are understandable, independently testable, and reusable without hiding important machine behavior.
