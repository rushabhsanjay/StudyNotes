1. Definition

PLC troubleshooting is the systematic process of identifying, isolating, verifying, and correcting faults in a control system by tracing symptoms to their actual causes.

A PLC-controlled machine may fail to operate because of a problem in any part of the automation system, including:

  • Electrical power and control circuits.
  • Sensors, switches, and field wiring.
  • PLC inputs, outputs, and program logic.
  • Communication networks and remote I/O.
  • Drives, motors, actuators, and pneumatic or hydraulic systems.
  • HMI, SCADA, CNC, and robot interfaces.
  • Mechanical components and process conditions.

The objective is not simply to make the machine run again. It is to identify the actual cause, restore operation safely, verify the correction, and prevent recurrence where possible.

For industrial maintenance, troubleshooting should follow evidence, not assumptions. Replacing a sensor because its associated alarm is active is not a diagnosis. The sensor might be healthy while its cable, power supply, PLC mapping, or mechanical target is faulty.

2. The basic troubleshooting model

A useful troubleshooting sequence is:

Machine Symptom
      |
      v
Confirm the Actual Problem
      |
      v
Check Safety and Operating Conditions
      |
      v
Identify the Affected Equipment and Function
      |
      v
Trace Signals from Field to PLC Logic
      |
      v
Find the First Point Where Expected Behavior Fails
      |
      v
Verify the Root Cause
      |
      v
Correct the Fault
      |
      v
Test the Complete Function
      |
      v
Record the Findings

The most important step is finding the first point where expected behavior differs from actual behavior.

For example, if a motor does not start, do not immediately conclude that the PLC output is faulty. Determine whether the start request exists, whether the permissives are satisfied, whether the PLC issues the run command, whether the drive receives it, and whether the motor responds.

Each stage narrows the fault location.

Before troubleshooting, understand how the command and feedback travel through the system.

        |
        v

        |
        v

        |

A fault at any point can produce the same visible symptom: the conveyor does not move.

The technician must identify which stage first fails to behave as expected.

Stage Example fault What to investigate

Input path PLC does not see the button Wiring, input module, communication

4. Troubleshooting categories

4.1 Electrical faults

Examples:

  • Missing 24 VDC control supply.
  • Blown fuse or tripped breaker.
  • Loose terminal.
  • Broken cable.
  • Failed relay or contactor.
  • Short circuit or ground fault.
  • Incorrect polarity.
  • Damaged connector.

Typical checks include supply voltage, protective-device status, wiring continuity when safely isolated, terminal condition, and the relevant electrical drawing.

Never use a resistance or continuity measurement on an energized circuit unless the measuring method and equipment are specifically rated and suitable for that condition. Follow isolation and lockout procedures before working on hazardous electrical circuits.

4.2 Sensor and input faults

Examples:

  • Proximity sensor does not detect the target.
  • Limit switch remains permanently ON.
  • Photoelectric sensor is obstructed.
  • Analog sensor produces an invalid value.
  • Sensor power is missing.
  • Input module channel has failed.
  • PLC input is mapped to the wrong tag.

The investigation should separate three questions:

  1. Is the physical condition actually present?
  2. Is the sensor detecting that condition?
  3. Is the PLC receiving and interpreting the signal correctly?

These are different failure points.

4.3 PLC logic faults

Examples:

  • An interlock condition remains FALSE.
  • A timer is continually reset.
  • A sequence transition condition is never satisfied.
  • A latch is not reset.
  • A tag is assigned the wrong value.
  • Two routines write to the same output.
  • A program change introduces incorrect behavior.

The main tools are online monitoring, cross-reference searches, logic tracing, tag monitoring, timer status, and examination of the sequence's current state.

4.4 Output and actuator faults

Examples:

  • PLC output command is TRUE but the output channel remains OFF.
  • Output channel is ON but the solenoid does not energize.
  • Relay contacts are damaged.
  • Solenoid coil is open-circuit.
  • Valve shifts but the cylinder does not move.
  • Output wiring is disconnected.
  • A force or override changes the expected behavior.

Separate the PLC command from the electrical output state and the physical actuator response.

4.5 Drive, robot, and CNC faults

Examples:

  • VFD is not ready.
  • Servo drive reports a fault.
  • Robot is waiting for an acknowledgment.
  • CNC cycle start is inhibited.
  • Axis reference is invalid.
  • Device communication is unavailable.
  • Controller mode does not permit the requested operation.

Read the device's own diagnostics. The PLC may show only a general Drive_Fault or Robot_Not_Ready status while the device itself provides the specific reason.

4.6 Communication faults

Examples:

  • PLC-to-robot connection lost.
  • Remote I/O adapter unavailable.
  • HMI displays stale values.
  • Device IP address or subnet is incorrect.
  • Network switch or cable fault.
  • Protocol configuration mismatch.
  • PLC tag updates stop while the last value remains displayed.

Do not assume a displayed value is current merely because it looks plausible. Check connection status, data quality, timestamps, and the device's actual status.

5. The first principle: verify the symptom

Before changing anything, establish what is actually wrong.

Suppose an operator reports:

The conveyor is not working.

This statement could mean:

  • The motor does not start.
  • The motor starts but trips.
  • The motor rotates but the belt does not move.
  • The conveyor moves but the PLC does not detect movement.
  • The conveyor runs in Manual but not in Automatic.
  • The conveyor works locally but not through the HMI.

Each case has a different diagnostic path.

A good initial investigation records:

  • Exact machine or station.
  • Operating mode.
  • Current sequence step.
  • Command state.
  • Feedback state.
  • Active alarms and faults.
  • Whether the problem is continuous or intermittent.
  • Whether the problem began after maintenance, a program change, or a device replacement.

Do not clear the fault history before capturing useful diagnostic evidence.

6. Troubleshooting using the PLC scan and signal path

The PLC program executes repeatedly, so the technician must understand where the expected condition disappears.

For a simple motor-start function, monitor these signals:

Start_Request
Drive_Ready
Drive_Fault
Interlocks_OK
Start_Allowed
Run_Request
Run_Feedback

A useful diagnostic table is:

Signal Expected condition If incorrect
Start_Request TRUE when a valid request is made Check operator input and request logic
Drive_Ready TRUE when the drive permits operation Check drive status and fault codes
Drive_Fault FALSE during normal operation Investigate the drive fault
Interlocks_OK TRUE when required conditions are satisfied Identify the individual blocking condition
Start_Allowed TRUE when all start conditions are satisfied Check the combined logic
Run_Request TRUE when the PLC commands operation Check sequence state, latches, and command logic
Run_Feedback TRUE when running is confirmed Check drive response, motor, sensor, and feedback mapping

This approach prevents unnecessary replacement of hardware.

7. Troubleshooting digital inputs

Digital inputs typically represent two logical states: TRUE and FALSE.

Examples include:

  • Pushbuttons.
  • Limit switches.
  • Proximity sensors.
  • Pressure switches.
  • Guard-position signals.
  • Drive-ready signals.

Diagnostic sequence

  1. Confirm the physical condition.
  2. Check the sensor's local indicator, if available.
  3. Verify the supply and field signal according to the device wiring.
  4. Check the relevant PLC input channel online.
  5. Confirm the channel-to-tag mapping.
  6. Verify that the PLC logic uses the correct polarity and tag.

Example: Clamp-closed sensor

The clamp physically closes, but the PLC continues waiting for Clamp_Closed.

Observation Possible cause
Clamp does not reach the closed position Mechanical obstruction, pressure issue, actuator fault
Clamp reaches the position but sensor indicator remains OFF Sensor alignment, sensor failure, incorrect target
Sensor indicator is ON but PLC input is OFF Wiring, power, input channel, connector
PLC input is ON but Clamp_Closed is FALSE Incorrect mapping, logic inversion, wrong tag
PLC tag is TRUE but sequence does not advance Wrong step, additional transition condition, program execution issue

The important lesson is that a physical sensor and the PLC tag representing it are not automatically equivalent.

Normally open and normally closed terminology

Distinguish between:

  • The electrical contact arrangement.
  • The logical state of the PLC tag.
  • The state expected by the program.

A normally closed electrical contact does not necessarily mean that the corresponding PLC tag should be TRUE during normal operation. Wiring design, input circuitry, and program logic determine the actual interpretation.

For safety-related circuits, follow the approved electrical drawings and safety documentation. Do not bypass a safety input as a troubleshooting shortcut.

8. Troubleshooting analog inputs

Analog signals represent measured values such as temperature, pressure, speed, flow, or position.

Common signal types include:

  • 0 to 10 V.
  • 1 to 5 V.
  • 4 to 20 mA.
  • Device-specific digital measurements over a field network.

Typical faults

  • Incorrect sensor range.
  • Wrong input-channel configuration.
  • Open current loop.
  • Short circuit.
  • Missing transmitter power.
  • Incorrect scaling.
  • Engineering-unit conversion error.
  • Sensor value outside the configured range.
  • Noise or grounding problems.

Example: 4 to 20 mA pressure transmitter

Suppose a transmitter measures 0 to 10 bar using a 4 to 20 mA signal.

The engineering value can be calculated as:

\[ P = \frac{I-4}{20-4}\times 10 \]

where:

  • \(P\) is pressure in bar.
  • \(I\) is measured current in mA.

For a measured current of 12 mA:

\[ P = \frac{12-4}{16}\times 10 = 5\text{ bar} \]

If the PLC displays 10 bar when the physical pressure is 5 bar, investigate the raw input value, channel configuration, scaling formula, and transmitter range.

The formula is valid for this specified linear range. Actual transmitter fault behavior and out-of-range diagnostics depend on the device and input module.

9. Troubleshooting PLC outputs

An output fault requires separating the command from the actual electrical and physical response.

For example:

PLC Logic Command
       |
       v
Output Tag
       |
       v
Physical Output Channel
       |
       v
Relay / Contactor / Solenoid
       |
       v
Machine Response

If the PLC output tag is TRUE but the actuator does not operate, possible causes include:

  • Output module fault.
  • Missing output supply.
  • Blown fuse.
  • Open wire.
  • Failed relay or contactor.
  • Damaged solenoid.
  • Mechanical or pneumatic problem.
  • A downstream device refusing the command.

If the output tag is FALSE when the command should be active, investigate the program logic first.

Output troubleshooting table

Observation Investigation
Output tag remains FALSE Check sequence, interlocks, logic, and command generation
Output tag TRUE, module indicator OFF Check output mapping, module status, channel configuration, and hardware diagnostics
Module indicator ON, actuator inactive Check field supply, wiring, load, and actuator
Solenoid energized, cylinder does not move Check valve operation, pressure, tubing, obstruction, and cylinder
Output remains ON after step completion Check latch logic, other writers, output mapping, and forcing
Output cycles rapidly Check oscillating logic, feedback chatter, repeated state changes, and timer behavior

Do not force an output simply to see whether the machine moves. Unexpected motion can injure people or damage tooling. Any controlled output test must follow the approved procedure, with the equipment in an appropriate state and the hazards assessed.

10. Troubleshooting sequence logic

A sequence fault often presents as a machine that is stuck, skips a step, or repeats an operation.

Use the current step as the starting point.

Example:

STEP_IDLE
    |
    v
STEP_CLAMP
    |
    v
STEP_TEST
    |
    v
STEP_UNCLAMP
    |
    v
STEP_COMPLETE

If the machine is stuck in STEP_CLAMP, identify the exact transition condition required to enter STEP_TEST.

For example:

Clamp_Closed
AND Clamp_Timer_Not_Expired
AND Required_Conditions_OK

The actual transition may differ, so inspect the implemented logic rather than assuming the condition from the state name.

Sequence troubleshooting table

Symptom Likely cause Checks
Sequence stuck in one step Transition condition FALSE Monitor every condition in the transition
Sequence skips a step Multiple transitions evaluated or condition already TRUE Check state evaluation order and transition logic
Sequence repeats the same step Completion or transition logic resets incorrectly Check step entry, exit, and feedback
Sequence returns to Idle unexpectedly Reset, abort, or fault logic overrides the step Cross-reference all assignments to the state variable
Timer never expires Timer is reset, disabled, or incorrectly enabled Check timer input, reset, preset, and accumulated value
Machine starts a second cycle automatically Start request remains active Check edge detection and restart logic
Fault reset is rejected Fault cause remains present Check reset permissives and active fault conditions
Sequence resumes after power restoration unexpectedly Retained state or output restoration behavior Check startup initialization and recovery strategy

A useful design practice is to record both the current step and the reason the next transition is blocked.

11. Troubleshooting timers and counters

Timers and counters are frequent sources of control-logic faults.

Timer faults

Common causes include:

  • Timer enable never becomes TRUE.
  • Timer is reset every scan.
  • Timer is enabled in the wrong step.
  • Preset value is incorrect.
  • Time base or data type is misunderstood.
  • Timer-done bit is used incorrectly.
  • The timer is reinitialized during every program execution.

For a timer that should run during a clamp step, monitor:

  • Current step.
  • Timer enable.
  • Timer reset.
  • Preset value.
  • Accumulated value.
  • Timer-done status.

If the accumulated value continually returns to zero, find which instruction or routine is resetting the timer.

Counter faults

Common causes include:

  • Counting on a continuously TRUE signal rather than a rising edge.
  • Incorrect counter reset conditions.
  • Duplicate counting logic.
  • Counter preset mismatch.
  • Counter value being overwritten elsewhere.
  • Sensor chatter causing multiple counts.

For a part counter, verify whether one physical part produces exactly one intended count event. If the sensor remains ON for several PLC scans, edge detection or appropriate event handling may be required.

12. Troubleshooting PLC communication and remote I/O

A PLC may execute its logic correctly while failing to receive fresh data from a remote device.

Examples include:

  • Remote I/O adapter offline.
  • Robot controller communication lost.
  • HMI values frozen.
  • Drive status unavailable.
  • Ethernet cable or switch fault.
  • IP address conflict.
  • Incorrect subnet or route.
  • Wrong protocol or device configuration.
  • Connection timeout or excessive network load.

Diagnostic order

  1. Check the controller's communication diagnostics.
  2. Check the device's power and network status.
  3. Verify the configured IP address and network settings.
  4. Inspect the relevant switch, port, and cable status.
  5. Confirm the correct device path, connection parameters, and protocol configuration.
  6. Check whether the data is updating rather than merely displaying a previous value.
  7. Verify the control system's response to communication loss.

A successful network ping does not prove that the PLC application connection is working correctly. It confirms only a limited aspect of network reachability.

Similarly, a green communication indicator does not prove that the received data is logically correct.

13. Troubleshooting VFDs, servo drives, robots, and CNCs

When a device rejects a command, inspect its own status before modifying PLC logic.

Variable-frequency drive

Check:

  • Drive-ready status.
  • Active fault code.
  • Control mode.
  • Command source.
  • Reference source.
  • Run command.
  • Output frequency or speed reference.
  • Motor and drive protection status.
  • Relevant communication diagnostics.

A drive can be healthy but configured to accept commands from its keypad rather than the PLC. In that case, the PLC may be issuing a correct command that the drive is not configured to use.

Servo system

Check:

  • Servo-ready status.
  • Alarm code.
  • Enable and reset conditions.
  • Axis reference or homing status.
  • Motion command and target.
  • Position limits.
  • Feedback and following-error diagnostics.

Do not assume that a missing movement command is a failed servo motor. The controller may be correctly refusing movement because the axis is not referenced or a required condition is missing.

Robot controller

Check:

  • Robot mode.
  • Robot-ready and busy status.
  • Active robot fault.
  • Program state.
  • Start-request and acknowledgment sequence.
  • Safety-system status as reported through the approved interface.
  • Communication health.
  • Position and recovery requirements.

A robot handshake can remain blocked because the PLC and robot disagree about which signal should be reset first.

CNC controller

Check:

  • Controller mode.
  • Cycle-start permission.
  • Active CNC alarm.
  • Machine-ready status.
  • Axis reference state.
  • Interlocks and auxiliary equipment.
  • Program and tool conditions.
  • PLC-to-CNC interface signals.

Use the controller's diagnostics and approved documentation before changing parameters or clearing faults.

14. Troubleshooting HMI and SCADA problems

A machine may be operating correctly while the HMI displays incorrect or stale information.

Typical causes include:

  • Incorrect tag address.
  • Wrong PLC connection.
  • HMI object bound to the wrong tag.
  • Communication loss.
  • Incorrect scaling or engineering units.
  • Cached or stale values.
  • Incorrect alarm configuration.
  • Operator authorization or command logic.
  • A display update problem.

Example

The conveyor is physically running, but the HMI shows Stopped.

Investigate:

  1. Is the drive running?
  2. Is the PLC receiving run feedback?
  3. Is the PLC tag mapped correctly?
  4. Is the HMI reading the intended tag?
  5. Is the HMI connection updating?
  6. Is the display using the correct Boolean interpretation?

Do not change the PLC program simply because an HMI indication is wrong. First identify which layer contains the discrepancy.

15. Online monitoring and logic tracing

Online monitoring allows the technician to observe the PLC program while the controller is running.

Useful functions include:

  • Monitoring Boolean states.
  • Watching timer and counter values.
  • Inspecting current sequence steps.
  • Viewing input and output status.
  • Checking controller diagnostics.
  • Cross-referencing tag usage.
  • Tracing a condition through multiple routines.
  • Comparing actual values with expected values.

Online monitoring can show whether a condition is TRUE, but it does not always explain why it is TRUE or FALSE. The technician still needs to understand the logic and the physical process.

Important: Monitoring, modifying logic, downloading programs, forcing I/O, and changing controller modes have different risks. Use the permissions and procedures appropriate to the task. Do not make online changes to production equipment without authorization and a clear recovery plan.

16. Root-cause analysis

A symptom is the observed problem. A root cause is the underlying reason that produced it.

Example:

  • Symptom: The robot does not start.
  • Immediate cause: Robot_Ready is FALSE.
  • Underlying cause: The robot controller is waiting for a reference operation.
  • Root cause of the production issue: A recovery procedure left the robot unreferenced after a previous interruption.

The correct solution is not necessarily to force Robot_Ready TRUE. It is to identify why the robot is not ready and restore the required condition.

Five Whys method

The Five Whys technique repeatedly asks why a problem occurred.

Example:

  1. Why did the conveyor stop? The drive reported a fault.
  2. Why did the drive fault? Its internal protection detected an abnormal condition.
  3. Why did the abnormal condition occur? The motor current exceeded the expected operating range.
  4. Why was the motor current excessive? The conveyor was mechanically overloaded.
  5. Why was the conveyor overloaded? A recurring material jam was not being cleared or prevented effectively.

This investigation suggests that the final corrective action may involve the conveyor mechanism, material flow, or operating procedure rather than a PLC code change.

Five Whys is a starting technique, not proof by itself. Confirm conclusions with evidence, measurements, fault history, and physical inspection.

17. Fault, cause, correction, and prevention

A useful maintenance record distinguishes the different stages of the investigation.

Field Example
Symptom Conveyor stops during automatic operation
Fault indication VFD overcurrent fault
Immediate cause Drive protection activated
Verified root cause Conveyor mechanism obstructed by accumulated material
Correction Remove obstruction and inspect affected components
Functional verification Run the conveyor through the approved test procedure
Preventive action Address the source of material accumulation
Evidence Drive fault history, inspection findings, test results

This structure prevents a maintenance record from ending with an unhelpful statement such as “Reset drive and machine OK.”

Resetting the fault may restore operation, but it does not explain why the fault occurred.

18. Troubleshooting priority and safety

Not all faults should be investigated in the same order. The investigation must account for risk, equipment condition, and production impact.

A reasonable priority is:

  1. Protect people and stabilize the equipment.
  2. Confirm the machine's actual state.
  3. Check safety-related indications and the approved recovery procedure.
  4. Identify the affected equipment and function.
  5. Check the most likely and easiest-to-verify causes.
  6. Trace the relevant control signals.
  7. Verify the root cause before making a correction.
  8. Test the complete function after repair.

Safety rules

  • Follow the site's lockout/tagout and isolation procedures.
  • Verify the absence of hazardous energy before work requiring isolation.
  • Consider electrical, pneumatic, hydraulic, gravitational, thermal, and stored mechanical energy.
  • Do not bypass interlocks or safety devices as a diagnostic shortcut.
  • Do not assume that a PLC output being OFF means the equipment is safe.
  • Treat online forces, overrides, and program changes as controlled actions.
  • Restore temporary test configurations and verify the final condition.
  • Follow approved procedures for robot, CNC, drive, and high-energy equipment recovery.

A troubleshooting method is only useful if it does not create a more serious problem than the one being investigated.

19. Common troubleshooting mistakes

Mistake Why it causes problems Better approach
Replacing parts immediately The failed component may not be the root cause Verify the fault at the component and signal level
Resetting faults without recording them Useful diagnostic evidence may be lost Capture fault codes, timestamps, and machine state first
Changing several parameters at once It becomes difficult to identify which change mattered Make controlled, documented changes
Forcing an input or output Can hide the real fault and cause unexpected operation Verify the physical signal and use approved test procedures
Assuming the PLC is faulty The fault may be in wiring, device configuration, or mechanics Trace the complete control path
Ignoring operating mode Automatic logic may be blocked by a valid mode condition Verify mode and command source
Assuming an ON signal is current Communication data may be stale Check data freshness and connection status
Clearing a fault before capturing evidence The original condition may no longer be visible Record diagnostic information before resetting
Making undocumented program changes Future troubleshooting becomes harder Use version control and approved change management
Testing only one successful cycle Intermittent and recovery faults may remain Test relevant abnormal and recovery scenarios

20. Troubleshooting examples

Example A: Motor does not start

Observed symptom: The conveyor motor does not start in Automatic mode.

Check Result Interpretation
Start request TRUE The request reaches the monitored logic
Automatic mode TRUE Mode condition is satisfied
Drive ready FALSE Start may be blocked
Drive fault TRUE A device fault is present
Run request FALSE PLC logic may correctly be withholding the command

Next, inspect the drive's actual fault code and the conditions that caused it. Do not force the run request TRUE merely to test whether the motor starts.

Example B: Clamp sequence is stuck

Observed symptom: The machine remains in the clamp step.

Check Result Interpretation
Current step STEP_CLAMP Sequence has not advanced
Clamp command TRUE PLC is requesting closure
Clamp-closed sensor FALSE Required feedback is missing
Clamp timer Expired Expected operation exceeded the allowed time
Fault code Clamp timeout The sequence detected the failure

Investigate the physical clamp, pneumatic supply, valve, sensor position, wiring, and PLC input mapping. Once the cause is corrected, follow the defined recovery procedure.

Example C: Robot does not accept a start request

Observed symptom: PLC start request is TRUE, but the robot does not begin the operation.

Check:

  • Robot-ready signal.
  • Robot mode.
  • Active robot fault.
  • Robot program state.
  • Request edge or acknowledgment requirements.
  • Communication health.
  • Required station conditions.

If the robot expects a new rising edge but the request has remained TRUE from a previous cycle, the request may not be accepted as a new command. Verify the interface specification before changing the handshake.

Example D: HMI shows a false temperature

Observed symptom: The HMI shows a temperature twice the expected value.

Check the transmitter range, raw PLC input, scaling formula, engineering units, and HMI tag binding.

If the raw value is correct but the displayed value is wrong, the problem may be scaling or display configuration rather than the sensor itself.

21. Troubleshooting checklist

Use this checklist during an investigation.

  • Confirm the exact symptom and affected equipment.
  • Check operating mode and machine state.
  • Capture active faults, alarms, and timestamps.
  • Identify the current PLC sequence step.
  • Monitor the command and feedback signals.
  • Identify the first point where expected behavior fails.
  • Verify the field device and wiring as appropriate.
  • Check PLC logic, interlocks, timers, and tag mappings.
  • Check drive, robot, CNC, or communication diagnostics where applicable.
  • Verify the root cause before correcting it.
  • Test the complete function after the correction.
  • Confirm normal fault recovery and restart behavior.
  • Record the cause, correction, verification, and preventive action.

22. Interview questions and answers

Q1. What is PLC troubleshooting?

It is the systematic identification and correction of faults in the PLC, field devices, control logic, communication system, and associated machinery.

Q2. What is the first step when a machine stops?

Establish the actual symptom, ensure the equipment is in an appropriate condition for investigation, and capture relevant alarms and diagnostic information.

Q3. How do you troubleshoot a sensor that does not appear in the PLC?

Verify the physical condition, sensor indication, supply and signal wiring, PLC input channel, tag mapping, and logic interpretation.

Q4. How do you troubleshoot an output that is ON but the actuator does not move?

Separate the PLC command from the physical output channel, field supply, actuator response, and mechanical condition.

Q5. How do you troubleshoot a sequence stuck in one step?

Monitor the current step and identify the exact transition condition that has not been satisfied. Trace that condition to its source.

Q6. Why should fault history be captured before resetting a drive?

Resetting may clear or change diagnostic information needed to identify the initiating cause.

Q7. What is the difference between a symptom and a root cause?

A symptom is the observed problem. A root cause is the underlying reason that produced it.

Q8. Why is forcing an output risky?

It can bypass normal command logic, produce unexpected movement, conceal the original fault, or create hazardous conditions.

Q9. How do you troubleshoot a communication problem?

Check device power, network connectivity, addressing, controller diagnostics, protocol configuration, connection status, and whether the received data is current.

Q10. What is the difference between correcting a fault and preventing recurrence?

Correction restores the affected function. Prevention addresses the underlying cause or conditions that could produce the same fault again.

Q11. Why might a drive be ready but still refuse to run?

Possible causes include an incorrect command source, missing enable, mode mismatch, absent run command, active application restriction, or a condition required by the drive configuration.

Q12. What should be included in a good troubleshooting report?

The symptom, equipment identification, diagnostic evidence, root cause, correction, verification results, and any preventive action.

23. Practical exercises

Exercise 1: Motor-start fault

Build a simulated motor-control circuit with Start_Request, Drive_Ready, Drive_Fault, Interlocks_OK, and Run_Request.

Introduce one fault at a time and identify which condition blocks the run request.

Exercise 2: Sensor signal tracing

Simulate a clamp-closed sensor that remains FALSE.

Trace the fault through the physical condition, sensor signal, PLC input, tag mapping, and sequence transition. Record the first point where expected behavior fails.

Exercise 3: Timer fault

Create a clamp timeout and deliberately introduce a timer-reset error in a non-production simulator.

Identify why the timer never expires and correct the reset logic.

Exercise 4: Robot handshake

Simulate a robot that never acknowledges a start request.

Monitor request, ready, busy, complete, and fault signals. Add a timeout and a diagnostic message that identifies the missing acknowledgment.

Exercise 5: Analog scaling fault

Configure a simulated 4 to 20 mA input for a 0 to 10 bar range. Introduce an incorrect scaling formula and determine why the displayed pressure is wrong.

Exercise 6: Root-cause report

For each simulated fault, document:

  • Symptom.
  • Immediate cause.
  • Verified root cause.
  • Corrective action.
  • Functional test.
  • Preventive action.

24. Final mental model

Effective troubleshooting follows a simple principle:

Trace the fault from the observed symptom to the first point where actual behavior differs from expected behavior, then verify the cause before changing the system.

Use the complete control path:

  • Operator command.
  • PLC input or received data.
  • Program logic.
  • Sequence, permissives, and interlocks.
  • Output command.
  • Field device.
  • Physical machine response.
  • Feedback and diagnostics.

Once the cause is verified, correct it, test the complete function, confirm recovery behavior, and document the result.
