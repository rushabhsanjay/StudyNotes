1. Definition

PLC sequencing is the control of a machine or process through a defined order of steps, where each step performs specific actions and transition conditions determine when the sequence moves forward.

A sequence defines:

  • What must happen first, next, and last.
  • Which outputs should be active during each step.
  • What feedback must be received before advancing.
  • What happens if an operation takes too long or a fault occurs.
  • How the machine starts, completes, stops, and recovers.

For example, an automated clamping and testing station might follow this order:

Machine Ready
    |
    v
Accept Start Command
    |
    v
Clamp the Component
    |
    v
Confirm Clamp Position
    |
    v
Perform the Test
    |
    v
Confirm Test Completion
    |
    v
Release the Clamp
    |
    v
Confirm Clamp Released
    |
    v
Cycle Complete
    |
    v
Return to Ready

The PLC does not simply switch every output on and off independently. It controls the machine according to its current state and the conditions required for the next state.

Industrial example: A test bench must not start testing before the component is clamped correctly. Sequencing enforces that order.

2. Important terminology

These terms are related, but they describe different aspects of control logic.

Term Meaning Industrial example
Sequence The complete ordered operation Clamp, test, release
Step One operation in the sequence Clamp the component
State The machine's current operating condition Waiting for clamp confirmation
Action An operation performed during a step Energize the clamp valve
Transition The condition that permits movement to another step Clamp sensor becomes ON
Event Something that occurs and may trigger logic Start button pressed
Permissive A condition that must be satisfied before an operation is allowed Air pressure is adequate
Interlock A condition that prevents or stops an operation when required Prevent motion when a guard is open
Mode The selected way of operating the machine Manual or automatic
Fault recovery The defined procedure for returning to an operable condition Clear the fault, verify position, reset

An interlock and a permissive influence the sequence, but they are not the sequence itself. We will study interlocks separately in the next topic.

3. The basic structure of a PLC sequence

A well-designed sequence contains four fundamental elements.

  1. Current step: Identifies what the machine is doing now.
  2. Step actions: Defines what should happen while that step is active.
  3. Transition condition: Determines when the step is complete and the next step can begin.
  4. Fault handling: Defines what happens when the expected operation cannot be completed.

Consider a pneumatic clamp.

Current step Action Transition condition Next step
Idle Keep clamp command OFF Valid start and required conditions satisfied Clamp
Clamp Command clamp valve ON Clamp-closed sensor ON Test
Test Execute test operation Test-complete feedback ON Unclamp
Unclamp Command clamp valve OFF Clamp-open sensor ON Complete
Complete Mark cycle complete Completion handling finished Idle

The table is the sequence specification. The PLC program implements it.

A common engineering mistake is to start programming before defining the sequence. That often produces a collection of timers, latches, and conditions that technically runs but is difficult to troubleshoot.

4. Step-based control and state machines

A state machine is a control structure in which the system occupies a defined state and changes state when specified conditions are met.

For a simple sequential machine, a state variable identifies the current step.

Example symbolic states:

STEP_IDLE
STEP_CLAMP
STEP_TEST
STEP_UNCLAMP
STEP_COMPLETE
STEP_FAULT

The state variable might be an integer internally, but meaningful names should be used in the program.

For example:

Current_Step = STEP_CLAMP

This is much clearer than:

Current_Step = 20

unless the number has a documented mapping.

How a state machine operates

Read Inputs
    |
    v
Evaluate Current State
    |
    v
Execute State Actions
    |
    v
Check Transition Conditions
    |
    v
Change State if Conditions Are Satisfied
    |
    v
Update Outputs
    |
    v
Repeat on Next PLC Scan

The exact execution order depends on the program structure and PLC platform.

One active step at a time

For a simple sequential process, one authoritative step should define the current state. Avoid having several independent step bits become active simultaneously unless the design intentionally supports parallel operations.

If two conflicting steps become active, the machine might receive contradictory commands, such as clamp and unclamp simultaneously.

Parallel sequences are valid when deliberately designed and synchronized. They should not arise accidentally from poorly managed step bits.

5. Example: Clamp, test, and release sequence

Assume an automated test station contains:

  • Start_Request: Operator requests a cycle.
  • Permissives_OK: All required operating conditions are satisfied.
  • Clamp_Closed: Clamp-closed sensor.
  • Test_Complete: Test equipment reports completion.
  • Clamp_Open: Clamp-open sensor.
  • Clamp_Close_Command: PLC command to close the clamp.
  • Test_Start_Command: PLC command to initiate testing.
  • Fault_Active: A sequence fault is present.

Sequence definition

Step Name Action Advance condition
0 Idle Wait for a cycle request Start request and permissives valid
10 Clamp Command clamp closed Clamp-closed feedback
20 Test Initiate or maintain test operation as designed Test complete
30 Unclamp Command clamp open Clamp-open feedback
40 Complete Register cycle completion Completion handling finished
90 Fault Apply the defined fault response Recovery conditions satisfied

The step numbers are illustrative. Their purpose is identification, not a requirement to use these particular numbers.

Illustrative pseudocode

The following shows the logic conceptually. It is not directly executable code for every PLC platform.

IF Initialization_Required THEN
    Current_Step := STEP_IDLE;
END_IF;

CASE Current_Step OF

    STEP_IDLE:
        IF Start_Request AND Permissives_OK THEN
            Current_Step := STEP_CLAMP;
        END_IF;

    STEP_CLAMP:
        Clamp_Close_Command := TRUE;

        IF Clamp_Closed THEN
            Current_Step := STEP_TEST;
        END_IF;

    STEP_TEST:
        IF Test_Complete THEN
            Current_Step := STEP_UNCLAMP;
        END_IF;

    STEP_UNCLAMP:
        IF Clamp_Open THEN
            Current_Step := STEP_COMPLETE;
        END_IF;

    STEP_COMPLETE:
        Cycle_Complete := TRUE;
        Current_Step := STEP_IDLE;

    STEP_FAULT:
        Fault_Active := TRUE;

END_CASE;

This pseudocode illustrates the state transitions, but it is not a complete machine-control program. Production logic must also define output defaults, timer handling, start-command behavior, fault detection, reset logic, initialization, and the response to lost permissives.

For example, if Clamp_Close_Command is assigned TRUE during the clamp step, the program must also ensure that the command becomes FALSE when the step ends or when the defined fault response requires it.

A dedicated output-mapping section or a clear state-to-output mapping can help prevent outputs from remaining unintentionally ON.

6. Sequence initiation and start-command handling

A sequence normally starts only when the machine is ready and the required conditions are satisfied.

Typical start conditions include:

  • Automatic mode selected.
  • Machine in the idle or ready state.
  • No active sequence fault.
  • Required operating permissives satisfied.
  • Previous cycle completed or reset appropriately.
  • Start command accepted.

Why a held start button can cause problems

Suppose the operator presses and holds Start. The PLC completes one cycle and returns to Idle while Start is still ON.

If the idle transition checks only:

IF Start_Request THEN
    Current_Step := STEP_CLAMP;
END_IF;

the next cycle may begin immediately without a fresh operator action.

The solution depends on the intended machine behavior. Common methods include:

  • Detecting a rising edge of the start signal.
  • Requiring the start button to be released before another cycle can begin.
  • Using a cycle-request latch that is accepted only under defined conditions.

A rising-edge detector recognizes the change from OFF to ON rather than treating a continuously ON signal as a new event every scan.

Important distinction: A start request is not the same as a running sequence. Once accepted, the sequence should be governed by its state logic, not by requiring the operator to keep holding Start.

7. Transition conditions and transition priority

A transition should have a clear, testable condition.

Examples:

  • Clamp step to test step: clamp-closed feedback is ON.
  • Test step to unclamp step: test-complete signal is ON.
  • Unclamp step to complete step: clamp-open feedback is ON.
  • Any operating step to fault state: a defined fault condition occurs.

A transition should not depend on vague assumptions such as “the clamp should be closed by now.”

Multiple conditions becoming TRUE

Suppose both the normal completion condition and a fault condition become TRUE during the same scan. The program must define which takes priority.

A common design principle is to give faults and required stop responses priority over normal progression, subject to the machine's risk assessment and control architecture.

Other transition-design rules:

  • Define which condition advances each step.
  • Avoid transitions that can occur without the required feedback.
  • Avoid conditions that are permanently TRUE and cause immediate repeated transitions.
  • Ensure every normal step has a valid exit path.
  • Define what happens when an expected transition never occurs.
  • Ensure invalid or unknown state values are handled explicitly.

Avoiding skipped steps

If the program allows the next step to be evaluated immediately after changing the current step, several transitions might occur during one PLC scan.

For example:

IDLE -> CLAMP -> TEST -> UNCLAMP

If all transition conditions are already TRUE, a poorly structured implementation might advance through multiple steps almost instantly.

Possible controls include:

  • Evaluating only the state that was active at the start of the scan.
  • Using a one-transition-per-scan design.
  • Using entry conditions or step-entry flags where appropriate.
  • Ensuring transitions depend on meaningful feedback or events.

One transition per scan is not mandatory for every application, but the behavior must be deliberate and predictable.

8. Feedback confirmation and step timeouts

A PLC should normally advance after receiving evidence that an operation has completed, rather than relying solely on a fixed delay.

Consider a clamp command.

Timer-only approach:

Command clamp
Wait 2 seconds
Assume clamp is closed
Start test

Feedback-based approach:

Command clamp
Wait for Clamp_Closed feedback
Start test after confirmation
Generate a timeout fault if confirmation does not arrive

The second approach accounts for real operating conditions such as low air pressure, mechanical obstruction, valve failure, or sensor problems.

Why use a timeout?

Suppose the clamp-closed sensor never turns ON. Without a timeout, the sequence may remain in the clamp step indefinitely.

A step timeout defines the maximum allowed time for the operation.

Conceptually:

IF Current_Step = STEP_CLAMP THEN
    Run_Clamp_Timer := TRUE;

    IF Clamp_Closed THEN
        Current_Step := STEP_TEST;
    ELSIF Clamp_Timer_Expired THEN
        Fault_Code := FAULT_CLAMP_TIMEOUT;
        Current_Step := STEP_FAULT;
    END_IF;
END_IF;

The example shows the decision logic, not a complete timer implementation.

The timer must be configured and reset correctly for the PLC platform. If its enable condition is accidentally reset every scan, the timer may never finish timing.

Timeout scenario Possible cause
Clamp does not close Low air pressure, failed valve, obstruction
Test never completes Test equipment fault or missing completion signal
Robot never becomes ready Robot fault, handshake mismatch, communication loss
Conveyor does not reach position Failed sensor, jam, drive problem

Timeout values should be based on measured cycle times, expected variation, equipment specifications, and the consequences of a delayed operation. They should not be chosen arbitrarily.

9. Sequence completion, reset, abort, hold, and resume

These commands serve different purposes and must not be treated as interchangeable.

Function Meaning
Complete The sequence has reached its intended end
Reset Clears defined fault or sequence conditions when reset requirements are satisfied
Acknowledge Confirms that an operator has recognized a fault or message
Abort Terminates the active sequence according to the defined abort behavior
Hold/Pause Temporarily suspends sequence progression according to the design
Resume Continues from a validated state after a hold
Single-step Advances through sequence steps under deliberate operator control

Reset does not mean start

A fault reset should not automatically initiate a new automatic cycle.

A typical recovery flow is:

Fault Detected
    |
    v
Defined Fault Response
    |
    v
Fault Cause Removed
    |
    v
Required Conditions Verified
    |
    v
Operator Acknowledges or Resets
    |
    v
Sequence Returns to a Defined Ready State
    |
    v
New Start Command Required

The exact recovery procedure depends on the machine. Some equipment requires rehoming, checking part position, removing a jam, or verifying robot position before a new cycle is permitted.

Hold versus abort

A hold may preserve the current step and allow a controlled resume. An abort usually terminates the active sequence and may require a new start from a known safe state.

Neither command automatically defines how physical outputs should behave. That behavior must be specified according to the equipment, process, and risk assessment.

10. Operating modes and their effect on sequencing

A sequence should operate within a clearly defined machine mode.

Mode Purpose Sequence behavior
Manual Operator controls individual operations Automatic progression is normally disabled
Jog Controlled movement while a command is applied Motion follows defined jog logic
Automatic Machine runs the programmed cycle Sequence advances automatically
Setup Preparation, adjustment, or tooling work Restricted operations are permitted under defined conditions
Recovery Return equipment to a known state after interruption or fault Only defined recovery actions are permitted
Maintenance Inspection, repair, and servicing Control authority and safeguards depend on the equipment and task

The mode-selection logic must define how transitions between modes are handled.

For example, changing from Automatic to Manual while the clamp step is active must not leave the clamp output unintentionally energized or allow the automatic sequence to resume unexpectedly.

Manual mode is not permission to bypass safeguards. Safety-related functions must be implemented using appropriately designed and validated safety-rated hardware and control systems. Ordinary PLC sequencing logic must not replace required safety functions.

11. Fault handling and recovery design

A sequence needs a deliberate response when an expected operation fails.

A useful fault-handling structure includes:

  1. Detect the fault condition.
  2. Record the fault code and relevant step.
  3. Apply the required output response.
  4. Prevent normal progression while the fault remains active.
  5. Display useful diagnostic information.
  6. Require the cause to be corrected and recovery conditions to be satisfied.
  7. Return to a defined state.
  8. Require a separate start command if another automatic cycle is intended.

Record the step at the time of failure

For troubleshooting, retain diagnostic information such as:

  • Current step when the fault occurred.
  • Fault code.
  • Time of occurrence.
  • Relevant sensor states.
  • Commands issued to actuators.
  • Communication or drive status, where applicable.

For example:

Fault_Code       = FAULT_CLAMP_TIMEOUT
Fault_Step       = STEP_CLAMP
Clamp_Command    = TRUE
Clamp_Closed     = FALSE
Air_Pressure_OK  = TRUE

This information is much more useful than a generic “Sequence Error” message. Humans have spent decades inventing automation, only to make the machine report that something went wrong without explaining what.

Should the PLC retain the active step after a fault?

There is no universal answer.

  • Retain the step: May be appropriate when the machine can safely pause and resume after validating the physical state.
  • Return to a defined recovery state: May be appropriate when the current process state is uncertain.
  • Return to Idle: Appropriate only when the machine's physical condition and restart behavior make that safe and valid.

After a power loss, the PLC's retained memory and the machine's physical condition may no longer agree. A retained STEP_TEST value does not prove that the test fixture is still clamped or that the part is still present.

Recovery must validate the real machine state rather than blindly trusting a saved step number.

12. Step actions, entry actions, and exit actions

Some actions should remain active throughout a step. Others should occur only once when entering or leaving it.

Action type Meaning Example
Continuous step action Remains active while the step is active Maintain a clamp command
Entry action Occurs once when entering a step Start a test transaction
Exit action Occurs once when leaving a step Store a completion timestamp
Transition action Occurs as part of a state change Set a result-valid flag

This distinction is important for counters, timers, communications, and command pulses.

For example, sending a robot-start command continuously for the entire robot step may not match the robot interface specification. The interface may require a rising-edge request that remains latched until the robot acknowledges it.

Entry and exit actions, one-shot flags, and state-transition logic must be implemented in a way that matches the PLC platform and scan behavior.

13. Implementing sequences in different PLC programming styles

The same sequence can be implemented using different programming approaches.

Method Typical implementation Strength Limitation
Ladder Diagram (LD) Step bits, contacts, coils, timers, comparisons Familiar to maintenance technicians Complex sequences can become difficult to follow
Structured Text (ST) State variable and CASE or equivalent logic Clear state-based structure Requires disciplined code organization
Sequential Function Chart (SFC) Steps, transitions, and actions Visually represents sequence flow Availability and execution details vary by platform
Function blocks or routines Separate logic for sequence sections Supports modular design Interfaces and state ownership must be clearly defined

Ladder Diagram

A ladder implementation might use a dedicated step bit for each state:

STEP_IDLE
STEP_CLAMP
STEP_TEST
STEP_UNCLAMP

Transition logic deactivates the current step and activates the next step. Interlocking conditions are added to prevent incompatible commands.

A major concern is ensuring that two step bits cannot become active simultaneously through overlapping or poorly reset logic.

Structured Text

Structured Text can represent the same process using a state variable and a CASE statement.

This is often convenient when a sequence contains many steps, multiple transition conditions, and diagnostic handling.

Sequential Function Chart

SFC expresses the sequence graphically using steps and transitions. It can be particularly useful when the order of operations is the main subject of the program.

SFC behavior, action qualifiers, and implementation details differ between PLC platforms, so the programmer must understand the actual controller's execution rules.

14. Sequential operations versus parallel operations

A sequential operation completes one stage before moving to the next.

A parallel sequence allows independent operations to proceed at the same time.

Consider a machine that must clamp a part while a robot moves to a separate permitted position.

                    START
                      |
              +-------+-------+
              |               |
              v               v
         Clamp Part       Robot Positioning
              |               |
              v               v
         Clamp Confirmed  Robot Position Confirmed
              |               |
              +-------+-------+
                      |
                      v
                Continue Process

The diagram is conceptual. Parallel actions are permissible only when the machine design allows them.

The joining point must wait for all required operations to finish. For example:

IF Clamp_Confirmed AND Robot_Position_Confirmed THEN
    Continue_Process := TRUE;
END_IF;

Potential problems include:

  • One branch completes while another remains stuck.
  • A shared output is controlled by more than one branch.
  • A fault in one branch is ignored by the other.
  • One branch resets shared data while another still needs it.

Concurrent sequences need defined synchronization, fault propagation, and ownership of shared outputs and data.

15. PLC scan-cycle considerations

PLC sequencing operates within the controller's execution cycle.

A simplified model is:

Read or Update Inputs
        |
        v
Execute Program Logic
        |
        v
Update Outputs
        |
        v
Repeat

Actual I/O updates and task scheduling vary by controller and configuration.

Why scan behavior matters

Suppose the PLC changes Current_Step from STEP_CLAMP to STEP_TEST during program execution.

Depending on the code structure, the test-step logic may execute during the same scan or wait until the next scan.

This affects:

  • Output timing.
  • One-shot execution.
  • Timer activation.
  • Transition priority.
  • Whether multiple steps can be processed during one scan.

Design the sequence so that the intended behavior is clear. Avoid relying on accidental program-order effects.

For faster processes, task periods, I/O update behavior, communication delays, and controller execution time may all influence whether the sequence meets its timing requirements.

16. Industrial example: conveyor indexing

A conveyor must move a component from an entry sensor to a processing station, stop at the correct position, and report completion.

Assume the following signals:

  • Part_At_Entry
  • Station_Position_OK
  • Conveyor_Drive_Ready
  • Conveyor_Run_Command
  • Cycle_Request
  • Fault_Active
Step Action Transition condition Timeout response
Idle Wait for a new request Cycle request, part present, drive ready Not applicable
Convey Command conveyor movement Station position confirmed Conveyor positioning fault
Process Permit the defined station operation Process complete Process timeout
Release Release the part or permit downstream transfer Part-clear confirmation Part-clear timeout
Complete Report cycle completion Completion handling finished Application-dependent

The position sensor, encoder, or other positioning method must be appropriate for the required accuracy.

A timer can supervise the travel time, but it should not replace position feedback when actual position confirmation is required.

17. Industrial example: robot handshake

A PLC and robot frequently exchange signals to coordinate their operations.

Typical signals include:

  • Robot_Ready
  • Robot_Start_Request
  • Robot_Busy
  • Robot_Complete
  • Robot_Fault

A simplified handshake may look like this:

PLC Confirms Conditions
        |
        v
Robot_Ready = TRUE
        |
        v
PLC Issues Start Request
        |
        v
Robot Acknowledges or Becomes Busy
        |
        v
Robot Performs Operation
        |
        v
Robot_Complete = TRUE
        |
        v
PLC Accepts Completion
        |
        v
PLC and Robot Reset Handshake Signals as Defined

The exact order and signal semantics must match the robot program and interface specification.

Important handshake rules

  • Do not assume that a signal automatically resets itself.
  • Define who owns each request and acknowledgment.
  • Define when a request is set and when it is cleared.
  • Avoid clearing the request before the receiving system has recognized it.
  • Include timeouts for expected acknowledgments and completion.
  • Handle robot faults and communication loss explicitly.
  • Define what happens if completion arrives unexpectedly or remains ON from the previous cycle.

A common failure is a request that remains ON while the receiving system expects a fresh OFF-to-ON transition. The PLC then waits indefinitely even though its own command appears active.

18. Sequence testing and commissioning

A sequence is not proven merely because one normal cycle succeeds. It must be tested under expected failure conditions too.

Test What to verify
Normal cycle Every step and transition occurs in the correct order
Missing sensor feedback The sequence waits and eventually reports the appropriate timeout
Sensor stuck ON The program detects or prevents an invalid transition where required
Interlock or permissive lost The defined response occurs at each relevant step
Start button held An unintended repeat cycle does not occur
Fault reset Reset does not unexpectedly start automatic operation
Abort or hold Outputs and state behavior match the specification
Power cycle Restart behavior is defined and does not blindly resume an invalid state
Communication loss Handshake timeouts and recovery work as designed
Single-step mode Only the permitted step advances
Parallel operation Branches synchronize correctly and failures are handled
Invalid state value The controller enters the defined error-handling path

During commissioning, useful diagnostic tools include:

  • Current-step monitoring.
  • Transition-condition monitoring.
  • Step-entry and step-exit timestamps.
  • Timeout status.
  • Fault code and fault-step registers.
  • Sequence trace or event logs.
  • Monitoring of actual feedback alongside commanded outputs.

19. Common sequencing problems and troubleshooting

Symptom Likely cause Checks
Sequence stuck in one step Transition condition never becomes TRUE Check sensor state, permissives, signal mapping, and timer
Sequence skips a step Multiple transitions evaluated in one scan or condition already TRUE Review state evaluation order and transition conditions
Sequence repeats continuously Start remains active or completion immediately restarts the cycle Check edge detection, request latching, and idle-state logic
Output remains ON after leaving a step Output latch not reset or another routine controls it Trace all writers and output assignments
Timer never expires Timer is reset or disabled every scan Check timer enable, reset logic, and preset
Reset starts the machine Reset logic also sets the start request or activates the first action Separate reset, ready-state, and start logic
Robot handshake hangs Request/acknowledgment mismatch or stale signal Monitor all handshake signals and timeout status
Two steps are active Conflicting step-bit logic or incomplete transition reset Check step activation and deactivation logic
Machine resumes unexpectedly after power loss Retained step or command restores without validating physical conditions Review startup initialization and recovery strategy
Sequence advances before the mechanism moves Transition uses command status or a delay instead of required feedback Verify the transition uses the correct physical confirmation
Cycle complete never appears Completion state is skipped or completion flag is cleared too early Check state transition order and flag ownership

Troubleshooting order

  1. Identify the current step.
  2. Identify the exact condition required for the next transition.
  3. Check whether that condition is TRUE in the PLC.
  4. Verify the underlying input, communication signal, or equipment feedback.
  5. Check timers, reset conditions, and competing logic.
  6. Review the fault history and the step in which the sequence stopped.

This approach is usually faster than inspecting the entire program without first identifying where progression stopped.

20. Best practices for sequence design

  • Use meaningful state names rather than unexplained numeric constants.
  • Define the sequence before writing the program.
  • Give every normal step a clear transition condition.
  • Use real feedback when physical confirmation is necessary.
  • Apply step-specific timeouts to operations that can fail to complete.
  • Define fault priority and recovery behavior.
  • Separate reset, acknowledge, abort, hold, and start functions.
  • Define startup and power-recovery behavior explicitly.
  • Ensure each output has clear ownership.
  • Avoid unintended simultaneous active steps.
  • Make robot and device handshakes explicit.
  • Record the fault code and current step for diagnostics.
  • Test missing feedback, stuck signals, communication failures, and interrupted cycles.
  • Ensure output behavior during faults and mode changes follows the machine's risk assessment.
  • Implement safety-related functions using the required safety-rated architecture and validation process, not ordinary sequence logic alone.
  • Document transitions in a table or sequence diagram so maintenance technicians can diagnose faults without reverse-engineering the entire program.

21. Interview questions and answers

Q1. What is PLC sequencing?

PLC sequencing is the control of machine operations in a defined order using steps, actions, transition conditions, and fault-handling logic.

Q2. What is the difference between a step and a transition?

A step defines the current operation. A transition defines the condition that allows the sequence to move to another step.

Q3. What is the difference between sequencing and interlocking?

Sequencing defines the order of operations. Interlocking prevents or stops an operation when a specified condition requires it.

Q4. Why is a state machine useful?

It provides a clear representation of the machine's current state, the actions associated with that state, and the conditions for changing states.

Q5. Why should a sequence use sensor feedback instead of only timers?

Feedback confirms that the physical operation actually occurred. Timers alone cannot prove that a clamp closed, a part arrived, or a robot completed its movement.

Q6. Why are step timeouts required?

They detect operations that fail to complete within an acceptable time and help prevent indefinite waiting.

Q7. How can a programmer prevent skipped steps?

Use well-defined transition conditions, controlled state evaluation, and deliberate scan behavior. Prevent unintended multiple transitions in a single scan when the application requires it.

Q8. What is the difference between reset and acknowledge?

Acknowledge records that the operator has recognized a message or fault. Reset clears defined fault or sequence conditions when the required reset conditions are met. Neither should automatically imply a new start.

Q9. How does a PLC and robot handshake work?

The PLC and robot exchange defined request, ready, busy, completion, and fault signals. Both sides must agree on when each signal is asserted and cleared.

Q10. What should happen after a power failure during a sequence?

The system should enter a defined startup or recovery path, validate the physical equipment state, and permit restart only when the required conditions are satisfied. Blindly resuming from a retained step is not sufficient.

Q11. What is the difference between sequential and parallel sequences?

A sequential sequence performs operations in an ordered progression. Parallel sequences allow independent operations to run concurrently and require defined synchronization before dependent work continues.

Q12. Why should each output have a clear owner?

Multiple competing writers can produce unpredictable commands, cause outputs to remain ON, or make troubleshooting difficult.

  • Prevent an unintended repeat cycle while Start remains held.

  • Require clamp-open feedback before cycle completion.
  • Record the current step for troubleshooting.

Add a separate timeout for clamp closure, test completion, and clamp opening.

Verify that each timeout produces a distinct fault code and identifies the step that failed.

Create separate logic for:

  • Fault acknowledgment.
  • Fault reset.
  • Sequence abort.
  • New cycle start.

Verify that clearing a fault does not initiate another cycle automatically.

Exercise 5: Robot handshake

Simulate Robot_Ready, Robot_Start_Request, Robot_Busy, Robot_Complete, and Robot_Fault.

Test a missing acknowledgment, a missing completion signal, and a stale completion signal.

Exercise 6: Single-step operation

Allow the operator to advance one sequence step at a time in a test environment. Verify that each advance checks the relevant conditions and that single-step operation cannot bypass required safeguards.

23. Final mental model

A PLC sequence can be understood through five questions:

  1. Where am I? The current step or state.
  2. What should happen here? The actions associated with that state.
  3. What must be true to move forward? The transition condition.
  4. What if the operation fails? The timeout, fault, and recovery logic.
  5. Is the machine allowed to perform this operation? The applicable mode, permissives, interlocks, and safety-related controls.

Together, these questions turn a collection of PLC instructions into a controlled, diagnosable machine process.
