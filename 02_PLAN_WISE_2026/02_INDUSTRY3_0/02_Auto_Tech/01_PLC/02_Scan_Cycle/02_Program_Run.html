1. Definition

Program execution is the stage in which the PLC executes its control logic using available input data, internal variables, timers, counters, and other program information to determine the required control actions.

In a traditional cyclic PLC, program execution follows the input-read stage and precedes the output-update stage.

During execution, the CPU evaluates instructions according to the controller's execution rules. These instructions may examine input conditions, evaluate interlocks, advance sequences, perform calculations, operate timers, and determine output commands.

For example, in an automotive fixture, the PLC may check whether a component is present, the clamp is closed, and the required pressure is available before permitting the next manufacturing operation.

The program does not physically move the clamp or robot by itself. It calculates the required commands, which are then transferred to the relevant output interfaces or communication systems.

The important distinction is that input read acquires data, program execution evaluates logic, and output write communicates the resulting commands to the outputs.

3. What happens during program execution?

A PLC program may perform several types of operations during execution.

Operation Purpose Example
Boolean logic Evaluates TRUE/FALSE conditions Check PART_PRESENT
Interlock evaluation Determines whether an action is permitted Verify the guard condition
Sequence control Determines the current machine step and next transition Move from clamping to welding
Timer processing Tracks elapsed time or timing conditions Detect a clamp timeout
Counter processing Tracks events or quantities Count completed parts
Arithmetic Calculates numerical values Scale pressure or calculate position
Data handling Reads or updates internal variables and structures Store the current recipe
Output-command calculation Determines desired output states Set CLAMP_SOLENOID to ON
Diagnostics Detects or records abnormal conditions Set a timeout fault

Not every PLC executes all these operations in one simple, uninterrupted scan. Some systems use multiple tasks, interrupts, periodic execution, motion-control tasks, or event-triggered routines.

4. Understanding execution order

The order in which instructions execute can affect machine behavior.

Consider this simplified sequence:

RUNG 1: Check whether a part is present
RUNG 2: Check whether the clamp is closed
RUNG 3: Evaluate whether the next step is permitted
RUNG 4: Set the next-step command
RUNG 5: Update sequence status

The controller follows the applicable execution rules of the programming language and task structure. It does not necessarily evaluate every instruction simultaneously.

However, execution order is not identical across all PLC programming languages. Ladder logic, function block diagrams, structured text, sequential function charts, and vendor-specific execution models have different rules.

Even within one project, routines may execute in a configured order, while separate tasks may execute according to priority and scheduling rules.

5. Example: simple Boolean logic

Suppose a machine may command a clamp only when a part is present and the guard condition is satisfied.

Define the input tags:

PART_PRESENT = TRUE
GUARD_CLOSED  = TRUE

The program evaluates:

\[ CLAMP\\\_PERMIT = PART\\\_PRESENT \land GUARD\\\_CLOSED \]

Since both conditions are TRUE:

\[ CLAMP\\\_PERMIT = TRUE \]

The program may then generate a clamp command, provided the rest of the control sequence and all required conditions permit it.

This equation is an illustrative logic example, not a complete safety design. Safety-related functions must use the appropriate safety-rated architecture and validated logic.

Truth table

PART_PRESENT GUARD_CLOSED CLAMP_PERMIT
FALSE FALSE FALSE
FALSE TRUE FALSE
TRUE FALSE FALSE
TRUE TRUE TRUE

The logic is evaluated using the values available to the program at that point in execution.

6. Program execution in ladder logic

Ladder logic commonly represents control logic as rungs containing contacts, coils, instructions, and function blocks.

For example, a simplified conceptual rung could be:

|----[ PART_PRESENT ]----[ CLAMP_PERMIT ]----( CLAMP_SOLENOID )----|

Interpretation:

  • PART_PRESENT represents the part-detection condition.
  • CLAMP_PERMIT represents the required permission condition.
  • CLAMP_SOLENOID represents the desired output command.

If the conditions evaluate as satisfied, the logic may set the command TRUE.

This is conceptual notation, not a complete, vendor-specific program. Actual ladder instructions and tag behavior depend on the PLC platform.

A further distinction matters: a ladder contact instruction referencing a Boolean tag does not physically inspect a contact inside the PLC. It evaluates the value of that tag or data reference.

7. Program execution does not mean every output changes immediately

Suppose a rung sets:

Some PLC architectures and output mechanisms update data differently, so the precise timing must be verified for the installed system.

8. Internal variables versus physical I/O

During program execution, the CPU may modify internal program data without changing any physical output.

Data type Example Physical effect by itself?
Physical input representation PART_PRESENT No direct control action by itself
Internal Boolean variable CLAMP_PERMIT No
Timer state CLAMP_TIMER No direct actuator movement by itself
Counter value PART_COUNT No
Output command tag CLAMP_SOLENOID Represents a command; physical action is not guaranteed
Physical output circuit Output module channel Can drive a compatible load when the circuit operates correctly

For example, the program might calculate CLAMP_PERMIT = TRUE while leaving CLAMP_SOLENOID = FALSE because the machine sequence has not reached the clamping step.

A permission condition is not the same as an action command.

This distinction becomes important in large machine programs, where permissives, interlocks, sequence states, and final output logic are often separated.

9. Timers and counters during execution

Timers and counters are common PLC instructions used to track time and events.

Timer example

Suppose the PLC commands a clamp to close and expects confirmation within a configured period.

Clamp command
     |
     v
Start or enable timer
     |
     v
Check CLAMP_CLOSED
     |
     +---- Confirmed in time ----> Continue sequence
     |
     +---- Timeout reached ------> Set fault

A timer instruction's exact behavior depends on the PLC platform and instruction type. The timer may accumulate elapsed time while its enabling condition is satisfied, retain values under certain conditions, or reset according to the logic and instruction rules.

Do not assume all PLC timers behave identically.

Counter example

A production counter may increment when the program detects a valid part-completion event.

The program must define what counts as one event. If the increment condition remains TRUE across multiple executions, an incorrectly designed counter may count repeatedly unless the instruction or logic uses suitable edge detection or other controls.

This is one reason to understand execution order and state changes rather than merely recognizing instruction symbols.

10. Why execution order can create unexpected behavior

Consider two program operations:

Operation A: Set MACHINE_READY = TRUE
Operation B: Evaluate MACHINE_READY and advance the sequence

If Operation A executes before Operation B within the same applicable execution context, Operation B may see the updated value.

If the order is reversed, Operation B may evaluate the previous value and only advance on a later execution.

The actual result depends on the language's execution semantics, data-update model, and task scheduling.

Other common causes of unexpected behavior include:

  • A tag being written by multiple routines.
  • A later instruction overwriting a value calculated earlier.
  • A timer being reset before the expected condition is evaluated.
  • A sequence-state variable changing in more than one place.
  • Different tasks accessing shared data.
  • Asynchronous I/O data updating during program activity.
  • Conditional routines not executing when expected.

When a PLC behaves differently from the intended sequence, examine the execution order and all writers to the relevant tags before assuming the CPU is faulty.

11. Scan time and program execution time

These terms are related but distinct.

  • Program execution time: The time spent executing program logic within a defined execution context.
  • Scan time: The time associated with completing a controller scan in a cyclic execution model.
  • Task period: The configured interval for a periodic task, where applicable.
  • Response time: The elapsed time from a physical event to the resulting machine response.

A controller's scan time may vary with program complexity, communications, diagnostics, task activity, and platform behavior.

More program logic can increase execution time, but adding one instruction does not always produce a predictable, fixed increase across every controller.

Why this matters

In high-speed equipment, the timing of input acquisition, program execution, and output updates can affect whether an event is detected and how quickly the machine responds.

If an input pulse is shorter than the effective detection capability of the input architecture, simply making the logic more efficient may not be enough. A suitable high-speed input or event-capture mechanism may be required.

12. Common program-execution faults

Symptom Possible cause What to investigate
Input tag is correct, but output command never becomes TRUE Logic conditions are not satisfied Monitor permissives, interlocks, sequence state, and branch conditions
Output command becomes TRUE briefly, then FALSE Another instruction overwrites the tag or a condition changes Search for all writers, examine execution order, monitor transitions
Timer never reaches its preset Enable condition drops out, timer resets, or instruction is used incorrectly Check timer instruction semantics and its enabling/reset logic
Counter increments repeatedly Event condition remains TRUE across executions Check edge detection and counter-increment conditions
Sequence skips or repeats a step State-transition logic or execution order is incorrect Examine state variables, transition conditions, and all writers
Program appears delayed Scan time, task scheduling, filtering, or communication delay Check timing diagnostics and the complete I/O-to-output path
Online logic appears correct but the machine does not move Output command may not reach or operate the physical actuator Verify output data, module state, field circuit, and actuator

Use online monitoring, cross-reference tools, trend data, and controller diagnostics where available. Any online test or logic change must follow the approved controls for the production system.

13. Practical example: automotive clamp sequence

Assume a fixture requires a component to be present, the relevant guard condition to be satisfied, and air pressure to be acceptable before a clamp command can be issued.

The input data available to the program is:

PART_PRESENT   = TRUE
GUARD_CLOSED   = TRUE
AIR_PRESSURE_OK = TRUE

The program then evaluates its logic:

1. Verify required conditions.
2. Confirm that the sequence is in the clamping step.
3. Set the clamp output command.
4. Monitor the clamp-closed feedback.
5. Continue if confirmation is received.
6. Raise a fault if the required confirmation times out.

This is an illustrative control sequence, not a complete production or safety design.

Notice that each stage has a separate purpose:

  • Input data reports what the controller has acquired.
  • Logic decides whether the action is permitted.
  • Sequence logic decides whether the action should happen now.
  • Output-command logic requests the action.
  • Feedback logic checks whether the expected response occurred.

A clamp output command being TRUE does not establish that the clamp has physically closed. That requires suitable feedback and diagnostic logic.

14. Practical troubleshooting method

When an input is correct but the machine does not perform the expected action, trace the program in this order:

  1. Verify the input data. Confirm the actual input tag and its freshness where applicable.
  2. Check every required condition. Identify which permissive or interlock is preventing the action.
  3. Check the sequence state. Confirm that the program is in the step that should issue the command.
  4. Trace the command logic. Identify where the output command is set and whether another instruction changes it.
  5. Check timers and transitions. Confirm that timeout, reset, and state-transition conditions behave as intended.
  6. Verify output data. Confirm whether the controller actually generated the required output command.
  7. Trace the physical output path. If the command is correct, investigate output update behavior, module diagnostics, wiring, supply, and the actuator.

For a retrofit or development project, document the intended sequence and the conditions for each transition. This makes later troubleshooting much easier than trying to reconstruct the designer's intentions from hundreds of rungs.

15. Interview questions

Q1. What happens during PLC program execution?

The controller executes configured control logic, evaluates conditions, processes internal data, and determines the required commands according to the platform's execution model.

Q2. Does the PLC execute every instruction simultaneously?

No. Instructions execute according to the programming language's rules, program organization, and task scheduling. Some operations can occur concurrently or asynchronously in supported architectures.

Q3. Why does program order matter?

A value written earlier may be read by a later instruction during the same execution context. Reversing the order can change which value is observed and when a sequence advances.

Q4. What is the difference between a permissive and an output command?

A permissive indicates that a required condition is satisfied. An output command requests an action. A satisfied permissive does not necessarily mean the action should occur immediately.

Q5. Why might a timer never finish?

Its enabling condition may drop out, it may be reset repeatedly, or its instruction may not be used according to its platform-specific behavior.

Q6. What is the difference between program execution time and end-to-end response time?

Program execution time describes logic processing in a defined execution context. End-to-end response time includes the entire path from the physical event through input acquisition, program execution, output transfer, and physical response.

Q7. How should a technician investigate a correct input and an inactive output command?

Trace the permissives, interlocks, sequence state, timer conditions, command logic, and all program instructions that write to the output tag.

The central principle is that the PLC program calculates what should happen; the output system then communicates the command to the physical equipment. Understanding the order of logic execution, state changes, timers, and interlocks is essential for diagnosing why a machine does not perform an expected action.
