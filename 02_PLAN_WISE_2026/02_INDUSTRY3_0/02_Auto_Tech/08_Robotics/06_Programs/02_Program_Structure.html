Program Structure: Main, Subprograms, and Calls

1. Introduction to Robot Program Structure

A robot program is an organized sequence of instructions that controls robot motion, tool operation, process execution, and interaction with other automation equipment.

In an industrial robot cell, a program rarely consists of motion commands alone. It may need to verify that a component is present, operate a gripper, wait for a PLC handshake, execute a process, handle faults, and signal cycle completion.

A well-structured program separates these responsibilities into manageable sections.

The main concepts are:

  • Main program: The primary entry point that coordinates the production cycle.
  • Subprogram: A separate program containing a reusable or logically grouped sequence of instructions.
  • Program call: An instruction that transfers execution to another program or routine.
  • Return: The mechanism that resumes execution in the calling program after a subprogram finishes.
  • Program state: The current execution status, including active routine, instruction pointer, variables, and relevant controller state.

The exact terminology varies by robot manufacturer and programming environment, but these structural concepts are common across industrial automation.

2. Why Program Structure Matters

A poorly structured robot program can become difficult to troubleshoot, modify, test, and maintain. Repeated code increases the chance that a correction will be applied in one place but missed elsewhere.

A structured program provides:

  • Better readability.
  • Reusable motion and process routines.
  • Easier fault diagnosis.
  • Reduced duplication.
  • Consistent handling of tools and fixtures.
  • Easier testing of individual operations.
  • Clearer coordination with PLCs and peripheral equipment.
  • Better version control and change management.

For a maintenance engineer, program structure is particularly useful when diagnosing a robot that stops during a cycle. Instead of examining an entire large program at once, the engineer can identify the active routine and isolate the failing operation.

3. Main Program

3.1 Definition

The main program is the primary routine responsible for starting and coordinating the robot's intended operation.

It commonly handles initialization, cycle sequencing, calls to supporting routines, completion checks, and final status reporting.

A main program may be started manually, by a production command, or through a controller-specific interface. The exact startup behavior depends on the robot system and cell architecture.

3.2 Typical Responsibilities

A main program may:

  • Confirm that the robot is in an appropriate starting state.
  • Verify the selected tool and required configuration.
  • Check the cell's production permissives.
  • Move to the required starting position.
  • Call pickup, transfer, assembly, welding, dispensing, or inspection routines.
  • Coordinate with the PLC.
  • Handle operation results.
  • Signal cycle completion or a fault condition.
  • Return to a defined state or wait for the next cycle.

Not every main program should perform every task directly. Repetitive or complex operations are usually separated into subprograms.

3.3 Simplified Main Program Example

The following is controller-neutral pseudocode, not executable syntax for a specific robot brand.

MAIN_PROGRAM
    INITIALIZE
    CHECK_START_CONDITIONS

    CALL PICK_COMPONENT
    CALL TRANSFER_COMPONENT
    CALL PROCESS_COMPONENT
    CALL PLACE_COMPONENT

    VERIFY_CYCLE_COMPLETE
    SIGNAL_CYCLE_COMPLETE
END_PROGRAM

The example illustrates program organization only. Real programs must include the required signal handshakes, fault responses, motion validation, and safe recovery behavior.

4. Subprograms

4.1 Definition

A subprogram is a separately defined sequence of instructions that performs a particular operation and can be executed from another program.

Subprograms help divide a complex production cycle into logical, reusable units.

Examples include:

  • PICK_COMPONENT
  • PLACE_COMPONENT
  • HOME_POSITION
  • GRIPPER_CONTROL
  • WELD_PATH_A
  • DISPENSE_SEALANT
  • VERIFY_PART_PRESENT

These names are illustrative. Naming conventions depend on the engineering standard and controller.

4.2 Why Subprograms Are Used

A subprogram can encapsulate a well-defined task. If the same task is required at multiple points in a program, a single maintained routine can often be called from each location.

Benefits include:

  • Less duplicated code.
  • Easier updates.
  • Clearer separation of responsibilities.
  • More focused testing.
  • Easier fault isolation.
  • Better program readability.

However, excessive fragmentation can also make a program harder to understand. A routine should represent a meaningful operation rather than splitting every trivial instruction into a separate program.

4.3 Example: Reusable Gripper Routine

SUBPROGRAM CLOSE_GRIPPER
    COMMAND_GRIPPER_CLOSE
    WAIT_FOR_GRIPPER_CLOSED
    VERIFY_PART_SECURED
    RETURN
END_SUBPROGRAM

The example represents a reusable gripper operation. A real implementation must define timeouts, signal validity, fault behavior, and the response when the part is not secured.

A command output becoming active does not necessarily prove that the gripper physically closed or that the part was successfully grasped.

5. Program Calls

5.1 Definition

A program call transfers execution from the current program to another routine or program.

When the called routine completes normally, execution usually returns to the instruction following the call. This is the common call-and-return model, although exact behavior depends on the controller and call type.

Example:

MAIN_PROGRAM
    INITIALIZE
    CALL PICK_COMPONENT
    CALL PLACE_COMPONENT
    END_PROGRAM

If PICK_COMPONENT returns normally, the main program proceeds to CALL PLACE_COMPONENT.

5.2 Call-and-Return Sequence

Main program
    ↓
CALL PICK_COMPONENT
    ↓
Execute pickup subprogram
    ↓
Subprogram completes
    ↓
RETURN to main program
    ↓
Execute next instruction

The call transfers control; it does not automatically guarantee that the physical operation succeeded. The program needs appropriate checks to confirm completion.

5.3 Call Stack

When one routine calls another, the controller must track where execution should resume.

This execution context is commonly managed through a call stack or an equivalent controller mechanism.

For example:

MAIN_PROGRAM
    ↓ calls
PROCESS_COMPONENT
    ↓ calls
CHECK_TOOL_STATUS

The active execution sequence is nested. When CHECK_TOOL_STATUS returns, execution resumes inside PROCESS_COMPONENT. When PROCESS_COMPONENT returns, execution resumes in MAIN_PROGRAM.

Nested calls are useful, but uncontrolled recursion or excessive call depth can exceed controller limits or make program behavior difficult to diagnose.

6. Main Program, Subprogram, and Call Compared

Concept Purpose Example
Main program Coordinates the overall cycle MAIN_PROGRAM
Subprogram Performs a defined operation PICK_COMPONENT
Program call Invokes another routine CALL PICK_COMPONENT
Return Resumes the caller after completion RETURN
Call stack Tracks nested routine execution Main → Process → Check
Program end Terminates a program according to controller rules Controller-specific end instruction

A call is an instruction, not a separate type of program. A subprogram is the routine being called.

7. Sequential Execution and Branching

A simple program executes instructions in sequence. Real robot programs also use conditional branches, loops, and waits.

Examples include:

  • If a part is present, proceed with pickup.
  • If a gripper confirmation is missing, enter fault handling.
  • Repeat an operation for each part in a batch.
  • Wait until the PLC grants permission to enter a station.
  • Select one of several process routines according to product type.

Simplified pseudocode:

IF PART_PRESENT
    CALL PICK_COMPONENT
ELSE
    CALL HANDLE_MISSING_PART
END_IF

The condition must be based on valid input or status data. A robot should not assume that a part is present merely because a previous cycle normally placed one there.

8. Parameters and Shared Data

Some robot programming environments allow data to be passed into and out of subprograms. Others rely more heavily on global variables, registers, position variables, or controller-specific data structures.

Parameters can make reusable routines more flexible.

For example, a generic placement routine might receive:

  • A target position.
  • A tool or process selection.
  • A placement mode.
  • A completion or result variable.

Conceptual pseudocode:

CALL PLACE_COMPONENT(
    TARGET_POSITION,
    PLACEMENT_MODE,
    RESULT_STATUS
)

This is illustrative, not universal robot syntax.

Local and Global Variables

Variable type Typical visibility Main consideration
Local variable Limited to a routine or defined scope Reduces unintended interference
Global variable Accessible across multiple routines Requires clear ownership and control
Position variable Stores a robot pose or target Must use the correct coordinate and configuration conventions
Input/output register Exchanges data with external equipment Requires defined mapping and handshake rules
Return status Reports a routine's outcome Must distinguish success, failure, and incomplete execution

Shared data is convenient but can create hidden dependencies. If several routines modify the same variable, the program's behavior may depend on execution order.

Use clear names, defined data ownership, and consistent initialization.

9. Return Status and Error Handling

A routine should have a defined outcome. Completion of the last instruction is not always equivalent to successful completion of the physical operation.

For example, a pickup routine may end in one of several states:

  • Pickup successful.
  • Part absent.
  • Gripper fault.
  • Timeout waiting for confirmation.
  • Robot motion interrupted.
  • Operation aborted by the controller.

A conceptual routine might be:

SUBPROGRAM PICK_COMPONENT
    CHECK_PICKUP_PERMISSIVES
    MOVE_TO_PICKUP_APPROACH
    MOVE_TO_PICKUP_POSITION
    COMMAND_GRIPPER_CLOSE
    WAIT_FOR_GRIPPER_CONFIRMATION

    IF GRIPPER_CONFIRMED
        SET_RESULT SUCCESS
    ELSE
        SET_RESULT FAILURE
    END_IF

    RETURN
END_SUBPROGRAM

A complete implementation must define how timeouts, motion faults, invalid signals, and interrupted execution are handled.

The calling program must inspect the result before continuing with the next operation.

CALL PICK_COMPONENT

IF RESULT = SUCCESS
    CALL TRANSFER_COMPONENT
ELSE
    CALL HANDLE_PICKUP_FAULT
END_IF

This avoids blindly executing the next process step after a failed pickup.

10. Program Structure and PLC Communication

Industrial robots frequently exchange signals with a PLC that controls conveyors, fixtures, clamps, safety-related interfaces, and station sequencing.

A typical production handshake may involve:

  • PLC cycle request.
  • Robot ready.
  • Robot busy.
  • Robot operation complete.
  • Robot fault.
  • Station permissive.
  • Part present.
  • Clamp or fixture confirmation.

A conceptual sequence is:

PLC requests cycle
    ↓
Robot validates start conditions
    ↓
Robot executes main program
    ↓
Main program calls operation routines
    ↓
Robot verifies process completion
    ↓
Robot signals cycle complete
    ↓
PLC continues station sequence

The actual handshake depends on the cell design and signal interface.

Important Engineering Rule

Define signal ownership and transition rules clearly. For example, specify which device sets and resets Cycle_Request, which device owns Robot_Busy, and how Cycle_Complete is acknowledged.

Without a defined handshake, the robot and PLC may disagree about the current cycle state. This can lead to repeated calls, missed starts, deadlocks, or unexpected restarts.

11. Wait Instructions and Timeouts

Robot programs often wait for a condition before continuing.

Examples include:

  • Waiting for a fixture to clamp.
  • Waiting for a gripper to close.
  • Waiting for the PLC to grant permission.
  • Waiting for a process-ready signal.
  • Waiting for a sensor to confirm a component's presence.

An indefinite wait can leave the robot stalled forever if the expected signal never arrives.

A robust design uses an appropriate timeout or fault-monitoring strategy where supported.

WAIT_FOR FIXTURE_CLAMPED
IF TIMEOUT
    SET_FAULT FIXTURE_NOT_CLAMPED
    CALL HANDLE_FAULT
END_IF

This is conceptual pseudocode. Actual timeout syntax and recovery behavior are controller-specific.

The timeout value should reflect the physical operation, device response time, process requirements, and expected operating variation. Arbitrary short timeouts can create nuisance faults, while excessively long timeouts delay fault detection.

12. Program Calls Versus Jumps

A program call and a jump are not interchangeable.

A call normally transfers execution to another routine while preserving a return point. A jump transfers execution to another location without necessarily creating a return relationship.

Behavior Program call Jump
Enters another routine Typically yes Not necessarily
Stores a return point Normally yes Usually no
Automatically resumes after the call Normally yes, after normal return Depends on destination and program flow
Best suited for reusable routines Yes Not generally
Risk if used carelessly Deep or unclear call nesting Unintended skipped instructions or uncontrolled flow

Some controllers provide additional branching and label mechanisms. Their exact behavior must be confirmed in the relevant programming manual.

13. Program Termination and Return Behavior

Program termination is controller-specific. The meaning of a routine's end instruction may differ depending on whether it is the main program, a subprogram, or a task running independently.

Important distinctions include:

  • Returning from a subprogram.
  • Ending the current main program.
  • Stopping program execution.
  • Pausing or holding execution.
  • Aborting the program after a fault.
  • Ending one task while other tasks continue.

Do not assume that an instruction meaning "end" always returns to the caller or always stops the entire robot program.

When maintaining existing code, confirm the behavior of the specific controller and the routine's role in the overall execution structure.

14. Program Structure for a Production Robot Cell

Consider a robot that picks a component, transfers it to a fixture, performs a process, and places the finished part on an output conveyor.

A maintainable structure might be:

MAIN_PROGRAM
    INITIALIZE
    CHECK_CELL_READY

    CALL WAIT_FOR_PART
    CALL PICK_COMPONENT
    CHECK_PICK_RESULT

    CALL TRANSFER_TO_FIXTURE
    CALL LOAD_FIXTURE
    CALL VERIFY_FIXTURE_STATE

    CALL EXECUTE_PROCESS
    CHECK_PROCESS_RESULT

    CALL UNLOAD_FIXTURE
    CALL PLACE_FINISHED_PART
    SIGNAL_CYCLE_COMPLETE

    RETURN_TO_READY_STATE

The supporting routines can be organized into categories:

  • Initialization routines: Establish required program and tool state.
  • Motion routines: Perform defined movements.
  • Handling routines: Control grippers and part transfer.
  • Process routines: Execute welding, dispensing, fastening, or inspection.
  • Communication routines: Coordinate signals with the PLC.
  • Diagnostic routines: Evaluate fault conditions and record status.
  • Recovery routines: Manage approved recovery paths.

Recovery routines must not automatically restart hazardous movement without verifying the physical state of the robot, tool, workpiece, and surrounding equipment.

15. Program Organization and Naming Standards

Consistent naming makes a robot program easier to navigate and maintain.

A practical naming scheme identifies the routine's function.

Name example Intended function
MAIN_CYCLE Overall production sequence
INIT_CELL Initialize required program state
WAIT_PART Wait for part availability
PICK_PART Execute pickup sequence
PLACE_PART Execute placement sequence
PROCESS_PART Run the process operation
CHECK_RESULT Validate the operation outcome
HANDLE_FAULT Handle a defined fault condition
RETURN_READY Return to a validated ready state

Naming rules should be consistent across the robot program, PLC interface, electrical drawings, and maintenance documentation where practical.

Avoid names such as PROGRAM_1, TEST_NEW, or FINAL_FINAL_2 for production routines. They provide little diagnostic value, despite humanity's continued dedication to creating exactly that sort of mystery.

16. Common Program-Structure Faults

Symptom Possible cause Diagnostic approach
Robot stops after a subprogram call Called routine is waiting, faulted, or never returns Identify the active routine and current instruction
Main program continues despite failed operation Return status is not checked Verify result handling before the next call
Robot executes the wrong routine Incorrect branch, call target, or selection data Trace program flow and active selection
Robot waits indefinitely Missing input, broken handshake, or absent timeout Monitor the expected signal and timeout logic
Routine works alone but fails in the full cycle Hidden dependency on global state or previous routine Compare initialization and call sequence
Robot repeats an operation unexpectedly Incorrect loop, branch, or call behavior Trace the execution path and state transitions
Changes in one routine affect unrelated operations Shared variable or global data dependency Audit variable usage and ownership
Recovery starts from an unsafe state Recovery logic assumes a known physical state Verify state checks and approved recovery procedure
Program terminates unexpectedly Incorrect end, return, abort, or task behavior Check controller-specific termination semantics

17. Troubleshooting a Robot Program Step by Step

When a robot stops during a cycle, use a structured diagnostic process.

  1. Identify the execution state. Determine the active program, routine, line or instruction, and controller status.
  2. Determine whether execution is moving, waiting, paused, or faulted. These conditions require different diagnoses.
  3. Inspect the called routine. Check whether it completed, is waiting for a signal, or encountered a motion or process fault.
  4. Check external signals. Verify PLC handshakes, sensor feedback, gripper confirmation, and fixture status.
  5. Check the result path. Confirm that the caller handles success and failure correctly.
  6. Inspect shared data. Verify global variables, position data, active tool, work frame, and routine parameters.
  7. Review termination behavior. Confirm whether the routine should return, end, pause, or transfer control.
  8. Reproduce the issue under approved conditions. Use the site's diagnostic and safety procedures.
  9. Record the root cause and corrective change. Preserve the validated program revision and relevant configuration backup.

Avoid editing a live production program without the required authorization, backup, and validation process.

18. Testing and Maintainability

A structured program supports several levels of testing.

18.1 Routine-Level Testing

Test a subprogram independently where the controller and process permit it. Verify its preconditions, execution, output state, return behavior, and failure handling.

18.2 Integration Testing

Test the interaction between routines, including the transitions from pickup to transfer, transfer to processing, and processing to placement.

18.3 Cell-Level Testing

Verify the complete robot sequence with the PLC, sensors, grippers, fixtures, process equipment, and safety system operating together.

18.4 Fault-Injection Testing

Under an approved commissioning procedure, verify the expected response to conditions such as a missing part, missing confirmation signal, process timeout, or failed peripheral device.

Fault testing must not involve bypassing safety functions or creating uncontrolled hazardous conditions.

19. Manufacturer-Specific Considerations

Robot programming environments differ in how they organize programs, routines, data, and execution.

Robot ecosystem General programming concept
FANUC Programs, subprogram calls, registers, and position data
ABB Procedures, routines, modules, and structured program execution
KUKA Programs, subprograms, data declarations, and structured execution
Yaskawa Motoman Job-based programming and job calls
Kawasaki Programs, subroutines, and controller-specific flow instructions
Universal Robots Programs, subprograms, functions, and structured control nodes

These are broad conceptual mappings. A routine in one controller is not necessarily identical to a routine in another, and syntax cannot be transferred directly between platforms.

When modifying an existing robot program, use the controller's documentation and established site conventions.

20. Interview Questions and Answers

Q1. What is a main program?

The main program is the primary routine that coordinates the overall robot operation and calls supporting routines as required.

Q2. What is a subprogram?

A subprogram is a separately defined sequence of instructions that performs a specific task and can be invoked from another program.

Q3. What happens during a program call?

Execution transfers to the called routine. After a normal return, execution typically resumes at the instruction following the call.

Q4. What is a call stack?

A call stack, or equivalent execution mechanism, tracks nested routine calls and the locations where execution should resume.

Q5. Why are subprograms useful?

They reduce duplication, improve readability, simplify testing, and allow common operations to be maintained in one place.

Q6. What is the difference between a call and a jump?

A call normally preserves a return point. A jump transfers execution to another location without necessarily creating a return relationship.

Q7. Why should a caller check a subprogram's result?

A routine may finish with a failed or incomplete physical operation. The caller must verify the outcome before continuing to avoid unsafe or invalid sequencing.

Q8. Why are global variables sometimes problematic?

Multiple routines may read or modify the same data, creating hidden dependencies, unexpected state changes, or execution-order problems.

Q9. What causes a robot to remain stuck in a subprogram?

Possible causes include waiting for an unavailable signal, a missing timeout, a motion fault, a logic condition that never becomes true, or incorrect routine flow.

Q10. Why is program structure important for maintenance?

It makes execution easier to trace, faults easier to isolate, and changes easier to test and validate.

Q11. What is the difference between program termination and returning from a subprogram?

Returning resumes the caller. Program termination follows the controller's rules for ending the current program or execution context. These behaviors must not be assumed to be identical.

Q12. Why must robot and PLC handshakes be defined clearly?

Both controllers need a consistent understanding of when an operation starts, remains active, completes, or faults. Poorly defined transitions can cause deadlocks or unintended repetition.

21. Practical Exercises

Exercise 1: Structure a Main Program

Design a main program for a robot that picks a component, loads a fixture, performs a process, unloads the fixture, and signals cycle completion.

Identify which operations should be subprograms and which checks should remain in the main sequence.

Exercise 2: Diagnose a Missing Return

A main program calls PICK_PART, but never executes the next instruction.

List the possible causes and explain how to identify whether the routine is waiting for a signal, faulted, or has incorrect termination behavior.

Exercise 3: Add Return-Status Handling

Modify a conceptual program so that a failed pickup prevents the robot from continuing to the process station.

Define the success condition, failure condition, and safe handling of the failed operation.

Exercise 4: Design a PLC Handshake

Define a sequence using Cycle_Request, Robot_Busy, Cycle_Complete, and Robot_Fault.

Specify who owns each signal, how the request is acknowledged, and how the system avoids repeating a cycle unintentionally.

Exercise 5: Improve Program Maintainability

Consider a robot program that repeats the same gripper-closing instructions in six different places.

Explain how a reusable subprogram would improve maintenance, and identify which parameters or shared data might be needed.

22. Final Mental Model

A robot program should be understood as a hierarchy of responsibilities.

The main program coordinates the overall operation. Subprograms perform specific tasks. Calls transfer execution to those routines, and returns resume the calling sequence. Conditions, status data, and error handling determine whether the process can safely continue.

A good program structure makes the robot's behavior understandable, reusable, testable, and maintainable. A good industrial program also checks whether each commanded physical operation actually succeeded before proceeding to the next one.
