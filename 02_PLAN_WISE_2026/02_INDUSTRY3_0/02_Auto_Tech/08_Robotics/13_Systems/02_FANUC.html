FANUC Robot Controllers: R-J2, R-J3, R-30iA, R-30iB, and R-30iB Plus

1. Introduction

FANUC is a major industrial automation manufacturer whose robot systems are used in automotive manufacturing, material handling, welding, machine tending, assembly, painting, and many other applications.

The robot controller is the central control system responsible for executing robot programs, coordinating axis movement, managing I/O, communicating with external equipment, and monitoring faults.

FANUC controller generations covered in this topic include:

  • R-J2: An older controller generation found on legacy industrial robot installations.
  • R-J3: A subsequent generation used in many established production systems.
  • R-30iA: A widely deployed controller family with a more modern control platform than the earlier R-J generations.
  • R-30iB: A later generation with updated hardware, software, communication, and application capabilities, depending on configuration.
  • R-30iB Plus: A later platform revision with updated controller technology and supported software options.

These generations are not interchangeable simply because they share the FANUC name. Hardware, software, memory, communication options, supported robot models, and maintenance procedures vary by generation and configuration.

For maintenance engineers, the objective is to identify the controller correctly, understand its architecture, navigate the teach pendant, interpret robot programs, diagnose faults, and manage backups and interfaces without compromising safety.

2. FANUC Robot System Architecture

A FANUC robot installation commonly consists of the following major subsystems.

Teach Pendant
     ↓
Robot Controller
     ├── Robot motion control
     ├── Robot program execution
     ├── I/O and communication
     ├── Alarm and diagnostic management
     └── Safety-related control functions
              ↓
       Servo Amplifier
              ↓
       Robot Servo Motors
              ↓
       Mechanical Robot Arm

Robot Controller
     ├── Digital I/O
     ├── Analog I/O, if installed
     ├── Fieldbus / Industrial Ethernet
     └── External equipment
              ↓
       PLC / CNC / HMI / Sensors

This is a simplified logical architecture. The actual hardware arrangement depends on the controller generation, robot model, installed options, and system integrator's design.

2.1 Main Components

Component Function Maintenance relevance
Robot controller cabinet Executes programs and coordinates robot movement Controller alarms, configuration, power, and communication
Main CPU or control board Executes control software and manages system functions Hardware faults, startup problems, and diagnostic status
Servo amplifier Drives the robot servo motors Axis alarms, amplifier faults, and power-stage diagnostics
Servo motors Produce controlled joint movement Motor, encoder, cable, and mechanical faults
Teach pendant Operator interface for programming and jogging Display, keys, enabling switch, deadman function, and mode controls
Robot connection cables Carry power, feedback, and control signals as designed Cable damage, loose connectors, and intermittent faults
I/O modules Connect the robot controller to sensors and actuators Input/output diagnosis and field wiring
Communication interfaces Exchange signals with PLCs and other systems Network status, mapping, and connection faults
Safety circuitry and functions Enforce required protective conditions Safety faults, interlocks, and approved recovery procedures
Cooling system Maintains appropriate cabinet temperature Fan failure, clogged filters, and overheating

3. Controller Generations and Practical Differences

The following is a high-level comparison. Exact features must be verified against the specific controller model and installed options.

Controller generation General characteristics Maintenance considerations
R-J2 Legacy platform Older components, software tools, backup media, and limited compatibility with modern systems
R-J3 Legacy platform with updated controller architecture compared with R-J2 Verify hardware revision, software version, available memory, and interface options
R-30iA Established digital robot controller family Commonly encountered in production cells; confirm installed options and supported software
R-30iB Later controller platform Check controller variant, communication options, software revision, and supported features
R-30iB Plus Updated R-30iB platform Verify hardware and software compatibility before maintenance or migration

Do not assume that a robot can run the same software image across all these generations. Robot-specific software, motion hardware, controller firmware, and option licenses may all affect compatibility.

3.1 Why Controller Identification Matters

Before troubleshooting, record:

  • Controller family and exact model.
  • Robot model and serial number.
  • Controller software version.
  • Teach pendant type.
  • Servo amplifier configuration.
  • Installed I/O and communication options.
  • Safety hardware and software configuration.
  • Backup availability and last known valid backup.

This information prevents the classic maintenance mistake of applying the correct procedure to the wrong generation.

4. Teach Pendant and Operator Interface

The teach pendant is the primary interface for viewing robot status, jogging axes, editing programs, teaching positions, and examining alarms.

Typical functions include:

  • Program selection and execution.
  • Joint and Cartesian jogging.
  • Position display.
  • I/O monitoring.
  • Alarm history and diagnostic information.
  • Program editing.
  • Tool and frame configuration.
  • System configuration and backup operations.

The available screens and navigation paths vary by controller generation and software version.

4.1 Operating Modes

Common operating concepts include:

  • Teach mode: Used for programming and controlled manual movement.
  • Automatic mode: Used for production execution under the required external and safety conditions.
  • Remote operation: Allows program execution to be controlled by an external system when the configuration permits it.

Mode selection, enabling devices, speed restrictions, and safety conditions must follow the specific installation's design.

4.2 Deadman or Enabling Device

A teach pendant may have an enabling device, often called a deadman switch, that permits certain manual operations while held in an appropriate position.

Its exact behavior depends on the controller and pendant.

Never bypass an enabling device or modify its circuit to restore operation. Diagnose the switch, wiring, connector, configuration, and safety system through the approved procedure.

5. FANUC Programming Fundamentals

FANUC robots commonly use the TP programming language, edited through the teach pendant. Some systems also support additional programming and integration methods, depending on installed software.

A typical TP program contains instructions for:

  • Motion.
  • I/O control.
  • Program flow.
  • Register manipulation.
  • Waiting for conditions.
  • Calling subprograms.
  • Handling faults and process sequences.

5.1 Example TP Program Structure

The following is an illustrative example of the general instruction sequence, not a validated production program. Exact instruction availability and syntax depend on the controller and configuration.

/PROG  EXAMPLE
/MN
   1:  ! Example sequence ;
   2:  WAIT DI[1]=ON ;
   3:  DO[1]=ON ;
   4:  WAIT DI[2]=ON ;
   5:  DO[1]=OFF ;
   6:  JMP LBL[100] ;
   7:  LBL[100] ;
   8:  ! Continue process ;
/END

Conceptually:

  • WAIT waits for a specified condition.
  • DI refers to a digital input.
  • DO refers to a digital output.
  • JMP transfers program execution.
  • LBL defines a program label.

The signal numbers in this example are arbitrary. In a real robot cell, each signal must be verified against the I/O mapping and electrical drawings.

5.2 Common Motion Types

Motion instruction General purpose Typical use
J Joint-interpolated movement Moving between positions using coordinated joint motion
L Linear TCP movement Approaching a fixture along a straight Cartesian path
C Circular movement Following an arc when the required points and configuration are defined

Motion instructions can have different speed and termination settings. The actual path and behavior depend on the programmed targets, active tool and frame, motion configuration, and controller implementation.

5.3 Position Data

Robot targets can contain joint-position data or Cartesian-position data.

  • Joint position: Specifies the position of each robot axis.
  • Cartesian position: Specifies TCP position and orientation relative to a selected reference frame, together with the robot configuration information required by the controller.

A Cartesian target does not uniquely guarantee a particular joint configuration. Multiple configurations may reach a similar TCP pose, and some configurations may be unreachable or restricted.

6. Coordinate Systems, Tools, and Frames

Correct coordinate configuration is essential for accurate movement.

6.1 Joint Coordinates

Joint coordinates describe the individual robot axis positions.

They are useful for:

  • Jogging individual axes.
  • Checking joint travel limits.
  • Diagnosing axis-specific motion problems.
  • Understanding robot configuration.

6.2 Cartesian Coordinates

Cartesian coordinates describe TCP position and orientation in a selected frame.

They are useful for:

  • Teaching approach and retreat points.
  • Programming machine loading paths.
  • Maintaining tool position relative to a fixture.
  • Transferring programs between properly configured cells.

6.3 Tool Center Point (TCP)

The TCP represents the programmed reference point of the active tool.

Examples include:

  • Gripper center.
  • Welding gun reference point.
  • Dispensing nozzle.
  • Spot-welding electrode reference point.

Incorrect TCP data can cause a robot to move differently from the intended physical path even when the taught Cartesian targets appear correct.

6.4 User or Work Frames

A user frame defines coordinates relative to a workpiece, fixture, machine, or other selected reference.

For example, a robot program may use a fixture frame so that component positions can be described relative to the fixture rather than the robot base.

If the fixture moves or the frame is calibrated incorrectly, the robot may approach the wrong physical location.

6.5 Troubleshooting Incorrect Positioning

When the robot reaches the wrong point, inspect the following in order:

  1. Active tool and TCP.
  2. Active user or work frame.
  3. Robot mastering and calibration status.
  4. Target position and robot configuration.
  5. Fixture and workpiece position.
  6. External-axis position and coordination.
  7. Program edits and recent configuration changes.

Do not compensate for an incorrect TCP by randomly changing multiple taught targets. Correct the underlying reference data first.

7. Digital I/O and PLC Handshake

Robot controllers commonly exchange digital signals with a PLC, CNC, safety system, and process equipment.

A machine-tending robot might use signals such as:

Signal Direction Purpose
Robot ready Robot to PLC Indicates the robot is ready under the defined sequence conditions
Robot busy Robot to PLC Indicates that a robot operation is active
Cycle complete Robot to PLC Indicates completion of a defined program step
Machine ready PLC to robot Indicates that the machine is ready for the requested operation
Part present Sensor or PLC to robot Indicates that a component is detected
Clamp open PLC or machine interface to robot Confirms the required clamp state
Load request PLC to robot Requests the robot loading sequence

These names are examples, not universal FANUC signal names.

7.1 Typical Handshake Sequence

PLC confirms machine ready
        ↓
Robot verifies required process conditions
        ↓
Robot performs loading motion
        ↓
Robot confirms component placement
        ↓
PLC controls machine clamping and cycle
        ↓
Machine reports cycle complete
        ↓
Robot unloads or proceeds to the next operation

Actual sequencing must include timeouts, fault handling, and appropriate interlocks.

7.2 Common Handshake Faults

  • PLC sends a request but the robot program is not running.
  • Robot waits indefinitely for a machine-ready input.
  • Signal mapping differs between the PLC and robot.
  • An input remains ON because of incorrect sensor state or logic.
  • The robot reports completion before the expected external condition occurs.
  • A program or controller restart leaves the two systems in inconsistent states.
  • Communication loss prevents expected signal updates.

A good troubleshooting method is to monitor the robot-side signal, PLC-side signal, and physical device state separately. This identifies whether the issue lies in the field device, wiring, PLC logic, network, I/O mapping, or robot program.

8. Servo System and Axis Faults

Robot motion depends on coordinated control of servo motors, feedback devices, amplifiers, and mechanical joints.

A typical axis control concept is:

Motion command
      ↓
Robot motion controller
      ↓
Servo amplifier
      ↓
Servo motor and gearbox
      ↓
Robot joint movement
      ↓
Encoder / feedback device
      ↓
Position and motion feedback

This is a conceptual representation. Specific controller generations may use different internal hardware arrangements.

8.1 Common Servo Fault Categories

Fault category Possible causes Initial checks
Servo amplifier fault Power-stage fault, overload, internal fault, or cooling issue Read exact alarm, check amplifier diagnostics and cabinet condition
Axis overtravel Commanded movement exceeds configured travel Identify axis, target, current position, and configured limits
Encoder or feedback fault Damaged cable, connector issue, feedback device fault, or electrical interference Inspect diagnostics and approved feedback connections
Motor overheating Excessive load, poor cooling, mechanical resistance, or motor fault Review load conditions, temperature history, and mechanical movement
Axis following error Commanded and actual motion differ beyond allowed conditions Review load, feedback, mechanical condition, and servo diagnostics
Abnormal noise or vibration Mechanical wear, loose components, collision damage, or tuning issues Stop unsafe operation and inspect according to the maintenance procedure
Intermittent axis fault Loose connections, thermal effects, cable damage, or intermittent hardware problems Review alarm history and inspect relevant hardware safely

Do not replace a servo amplifier solely because an axis fault appears. First identify the exact alarm, affected axis, diagnostic details, and whether the problem follows the amplifier, motor, feedback path, or mechanical load.

9. Alarm Diagnosis and Recovery

FANUC alarms can relate to robot motion, program execution, communication, I/O, safety conditions, servo systems, and controller hardware.

9.1 Recommended Workflow

  1. Record the complete alarm text and code.
  2. Identify the controller family and software version.
  3. Determine whether the alarm concerns program execution, motion, I/O, communication, safety, or hardware.
  4. Inspect the current robot state and active program line.
  5. Review related alarms and the sequence of events before the fault.
  6. Check the relevant signal, axis, tool, frame, or configuration.
  7. Apply the manufacturer's approved corrective procedure.
  8. Verify the cause has been resolved before resetting and restarting.
  9. Record the root cause and corrective action.

9.2 Alarm Categories

Category Examples of symptoms Likely diagnostic area
Program alarm Program stops at an instruction Syntax, invalid target, missing condition, or program logic
Motion alarm Target cannot be reached or motion is rejected Axis limits, configuration, singularity, or path restrictions
Servo alarm Axis or amplifier reports a fault Servo drive, motor, feedback, or mechanical system
I/O alarm or timeout Robot waits for a signal Sensor state, wiring, I/O mapping, PLC logic, or network
Communication fault External equipment is disconnected Network configuration, cables, interface, or PLC status
Safety-related fault Protective condition prevents operation Safety device, interlock, safety configuration, or hardware diagnostics
Controller hardware fault Startup, memory, or board diagnostic problem Controller hardware, power, storage, or software configuration

The exact alarm description is more useful than guessing based on the symptom alone.

10. Backup and Restore

A robot backup is essential for recovery after controller failure, program corruption, hardware replacement, or configuration changes.

The exact backup procedure and available media differ between R-J2, R-J3, R-30iA, R-30iB, and R-30iB Plus systems.

10.1 Backup Contents

Depending on the backup method and controller, records may include:

  • Robot programs.
  • Position and register data.
  • System configuration.
  • Tool and frame data.
  • I/O configuration.
  • Communication settings.
  • Application-specific settings.
  • Safety-related configuration and data, where supported and included by the approved method.

A backup of programs alone is not necessarily a complete controller backup.

10.2 Recommended Backup Practice

  • Identify the exact controller and robot model.
  • Record the software version and installed options.
  • Perform the appropriate full backup using the manufacturer's procedure.
  • Store the backup in an approved location.
  • Use meaningful names and timestamps.
  • Maintain a known-good version before configuration changes.
  • Protect safety-related configuration from unauthorized alteration.
  • Verify that the backup can be read and that required components are included.

Example naming convention:

ROBOT_ID_CONTROLLER_VERSION_DATE_BACKUP_TYPE

Example:

ROBOT_05_R30iB_V9_20261015_FULL

This is an example naming format, not a claim about a particular software version.

10.3 Restore Precautions

Restoring a backup can overwrite programs, configuration, calibration-related data, or other settings.

Before restoration:

  1. Confirm the target controller and robot identity.
  2. Confirm hardware and software compatibility.
  3. Identify what the restore operation will overwrite.
  4. Preserve the current state where possible.
  5. Follow the approved restoration procedure.
  6. Verify mastering, tool data, frames, I/O, communication, and safety configuration as required.
  7. Validate operation before production release.

Never assume that a backup from another robot of the same apparent model is interchangeable.

11. Communication and Industrial Integration

FANUC controllers can support various communication methods depending on generation, installed hardware, software, and licensed options.

Examples may include:

  • Digital I/O.
  • Analog I/O.
  • EtherNet/IP.
  • PROFINET.
  • DeviceNet on supported legacy configurations.
  • Serial or other legacy interfaces.
  • Manufacturer-specific or application-specific communication options.

The list is not a guarantee that every protocol is available on every controller.

11.1 EtherNet/IP and PLC Integration

In a common architecture, the PLC exchanges mapped I/O data with the robot controller over EtherNet/IP.

Typical exchanged data includes:

  • Robot command requests.
  • Program or job selection.
  • Ready, busy, and complete states.
  • Part and fixture status.
  • Fault and recovery states.
  • Process parameters.

Troubleshooting should distinguish network connectivity from application-level communication.

A working Ethernet link does not prove that the correct assemblies, connection parameters, signal mapping, or robot program are functioning correctly.

11.2 Network Diagnostic Checklist

  • Confirm the physical link and cable condition.
  • Verify the controller's network configuration.
  • Check IP addresses and subnet settings.
  • Confirm that the correct communication option is installed and configured.
  • Inspect the PLC's connection status.
  • Verify I/O mapping and data sizes.
  • Compare the robot's input/output status with the PLC's corresponding data.
  • Review connection faults and timeout diagnostics.

Do not change IP addresses or I/O mapping on a running production cell without following change-control procedures.

12. Controller Migration and Legacy Robot Support

Older controllers may remain operational for many years in manufacturing plants. Their continued use can create challenges involving obsolete hardware, software availability, replacement parts, and integration with modern systems.

12.1 Reasons to Consider Migration

  • Controller hardware is obsolete or difficult to repair.
  • Spare parts have long lead times.
  • Communication interfaces no longer meet production requirements.
  • Software tools are difficult to maintain.
  • Reliability or recovery time is unacceptable.
  • Required safety or process changes cannot be supported economically.
  • Integration with modern PLCs, data collection, or traceability systems is limited.

12.2 Migration Assessment

Before migrating a robot controller, document:

  • Robot mechanical model and condition.
  • Controller and servo hardware.
  • Motor and feedback compatibility.
  • Robot software and application options.
  • Tool and frame data.
  • Programs, macros, and background tasks.
  • PLC interface and I/O mapping.
  • Fieldbus configuration.
  • Safety hardware and safety functions.
  • Calibration and mastering requirements.
  • Production validation requirements.

A controller migration is not simply a matter of copying program files. Differences in software, motion behavior, options, safety architecture, and hardware interfaces may require substantial engineering.

12.3 Legacy Maintenance Strategy

For an older R-J2 or R-J3 installation:

  • Preserve verified backups and documentation.
  • Record hardware part numbers and revisions.
  • Maintain an approved spare-parts list.
  • Identify supported repair and replacement options.
  • Document recovery procedures.
  • Avoid undocumented modifications.
  • Develop a migration plan before the system becomes impossible to recover reliably.

13. Practical Industrial Scenarios

Scenario 1: Robot Does Not Start in Automatic Mode

Possible causes:

  • A required external permissive is missing.
  • The robot is not in the required mode.
  • A protective condition is active.
  • The PLC handshake is incomplete.
  • The selected program or production sequence is incorrect.

Diagnostic approach:

  1. Read the controller alarm screen.
  2. Verify the operating mode and required enabling conditions.
  3. Inspect safety-system status through approved diagnostics.
  4. Monitor the robot's relevant digital inputs.
  5. Compare those inputs with the PLC's state.
  6. Determine which required condition is absent before attempting recovery.

Scenario 2: Robot Reaches the Wrong Position

Possible causes:

  • Incorrect TCP.
  • Incorrect user frame.
  • Incorrect mastering.
  • Wrong target or robot configuration.
  • Fixture movement.
  • External-axis position mismatch.

Diagnostic approach:

  • Compare the target and actual position.
  • Verify the active tool and frame.
  • Check mastering and calibration records.
  • Inspect external-axis data.
  • Review recent program and fixture changes.

Scenario 3: Robot Waits Forever for a PLC Signal

Possible causes:

  • The PLC never activates the expected output.
  • The robot input mapping is incorrect.
  • The physical signal path is broken.
  • The PLC sequence is waiting for another condition.
  • Communication is disconnected.
  • The expected signal polarity or logic is wrong.

Diagnostic approach:

  1. Identify the exact WAIT condition or equivalent instruction.
  2. Monitor the robot-side input.
  3. Check the corresponding PLC output or data bit.
  4. Inspect the wiring or network path as applicable.
  5. Check PLC sequence conditions and timeouts.
  6. Correct the underlying fault rather than permanently bypassing the wait condition.

Scenario 4: Robot Reports a Servo Fault After a Collision

Possible causes:

  • Mechanical binding.
  • Damaged motor or feedback cable.
  • Gearbox or joint damage.
  • Servo amplifier fault.
  • Encoder or mastering issue.

Diagnostic approach:

  • Keep personnel clear of hazardous movement.
  • Record the exact alarm and affected axis.
  • Follow the manufacturer's recovery and inspection procedure.
  • Inspect for mechanical damage and abnormal resistance.
  • Check the relevant motor, feedback, and amplifier diagnostics.
  • Verify mastering or calibration if the approved procedure requires it.
  • Validate the robot before production release.

Scenario 5: Controller Failure Requires Backup Restoration

Diagnostic approach:

  1. Identify the failed hardware and replacement controller.
  2. Confirm model, software, and option compatibility.
  3. Select the correct known-good backup.
  4. Follow the appropriate restore procedure.
  5. Verify robot identity, mastering, frames, tools, I/O, and communication.
  6. Check safety-related configuration using the required process.
  7. Perform the prescribed functional and safety validation.

14. Preventive Maintenance Checklist

  • Record controller model, software revision, and installed options.
  • Check controller cabinet condition and cooling airflow.
  • Inspect accessible cables and connectors for damage.
  • Review alarm history and recurring faults.
  • Verify backup availability and backup integrity.
  • Confirm tool and frame data are documented.
  • Review robot and PLC handshake faults.
  • Check communication diagnostics.
  • Inspect robot mechanical condition and investigate abnormal noise.
  • Verify mastering and calibration status when required.
  • Maintain a record of replaced components and their part numbers.
  • Follow the approved safety verification procedure after relevant repairs or changes.

Electrical inspection and hardware replacement must follow the required isolation and discharge procedures. Servo drives and controller cabinets can contain hazardous electrical energy even after the main supply has been switched off.

15. Interview Questions and Answers

Q1. What is the role of a FANUC robot controller?

It executes robot programs, coordinates motion, manages I/O and communication, monitors system faults, and supports the installed safety functions.

Q2. What is the difference between R-J3 and R-30iA?

They belong to different controller generations with differences in hardware, software architecture, interfaces, and available options. Exact capabilities depend on the specific controller configuration.

Q3. What is a FANUC TP program?

A teach-pendant program written in FANUC's TP programming language. It commonly contains motion instructions, I/O control, conditional logic, waits, register operations, and program flow instructions.

Q4. What is the difference between J and L motion?

J uses joint-interpolated movement, while L commands linear TCP movement. The resulting paths differ, so the motion type must suit the process and collision-clearance requirements.

Q5. What is a TCP?

The Tool Center Point is the programmed reference point of the installed tool. Incorrect TCP data can produce inaccurate physical positioning even when the programmed coordinates have not changed.

Q6. Why is a robot backup important?

It preserves recoverable programs and configuration data, depending on the backup method. It can reduce recovery time after hardware failure, software corruption, or an authorized configuration change.

Q7. What causes a robot to wait indefinitely?

The expected condition may never become true because of a sensor, wiring, I/O mapping, PLC logic, communication, or sequence problem.

Q8. How do you troubleshoot a robot servo fault?

Record the exact alarm, identify the affected axis, inspect controller diagnostics, and investigate the amplifier, motor, feedback, cables, and mechanical load according to the approved procedure.

Q9. Can a program backup be restored to any FANUC controller?

No. Compatibility depends on the controller generation, software version, robot model, installed options, and configuration. Restoration can also overwrite critical data.

Q10. What should be checked before replacing an R-J2 or R-J3 controller?

Check hardware compatibility, robot and servo interfaces, software and option availability, backup completeness, mastering, I/O, external communication, safety functions, and the complete migration-validation plan.

16. Practical Exercises

Exercise 1: Identify the Controller

Using a real controller's nameplate and approved documentation, record:

  • Controller generation and exact model.
  • Robot model and serial number.
  • Software version.
  • Teach pendant type.
  • Servo amplifier arrangement.
  • Installed communication interfaces.
  • Backup method and backup location.

Do not infer a software version from the controller generation alone.

Exercise 2: Trace a PLC Handshake

Choose one robot sequence from a machine-tending or material-handling cell.

  • Identify the PLC request.
  • Find the corresponding robot-side input.
  • Locate the program instruction that checks the input.
  • Identify the robot completion output.
  • Trace that output back to the PLC.
  • Document timeout and fault-handling behavior.

Exercise 3: Diagnose a Program Stop

Using an existing alarm record or a simulation:

  • Record the alarm text.
  • Identify the active program and instruction.
  • Inspect the target, frame, and tool where relevant.
  • Check any expected input or motion condition.
  • Document the likely cause and evidence.
  • Record the approved recovery procedure.

Exercise 4: Prepare a Backup and Recovery Plan

Create a controller recovery record with:

  • Controller identity.
  • Software and option details.
  • Backup file identification.
  • Tool and frame records.
  • Mastering and calibration records.
  • I/O and network configuration.
  • Required post-restore validation.
  • Responsible personnel and approval process.

The goal is to make a failed robot recoverable without relying on somebody's memory of a setup performed years ago.

17. Final Mental Model

A FANUC robot system should be understood as five connected layers:

Application layer
    ↓
TP programs, targets, registers, and process sequence
    ↓
Controller layer
    ↓
Motion planning, I/O, communication, and diagnostics
    ↓
Servo and mechanical layer
    ↓
Motors, feedback, gearboxes, robot joints, and tools
    ↓
External integration and safety
    ↓
PLC, sensors, machines, protective devices, and safety functions

When a FANUC robot fails, identify which layer is responsible before changing anything. A robot that is not moving may have a program wait, a missing PLC signal, a motion-limit violation, a servo fault, a communication failure, or an active safety condition. These problems can look similar from the production floor but require different corrective actions.

For a maintenance engineer, the essential skills are controller identification, TP program interpretation, coordinate-system understanding, I/O tracing, servo diagnostics, backup management, and controlled recovery.
