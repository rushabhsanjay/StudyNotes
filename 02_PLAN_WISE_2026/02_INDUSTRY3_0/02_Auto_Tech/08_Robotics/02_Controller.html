Robot Controller: Architecture, Operation, Programming, and Troubleshooting

1. Definition and Purpose

A robot controller is the real-time industrial computer system that executes robot programs, calculates motion, coordinates robot axes, processes input/output signals, communicates with other automation equipment, and monitors operating conditions.

The robot manipulator is the mechanical structure. Motors and servo drives produce movement. The controller coordinates these components so the robot follows the commanded path and performs the intended operation.

A robot controller is not simply a PLC dedicated to a robot. It combines motion-specific computing, robot kinematics, coordinated multi-axis servo control, program execution, and robot-specific diagnostics.

2. Responsibilities of a Robot Controller

The controller typically performs these functions:

  • Program execution: Executes motion instructions, subroutines, logic, waits, and process commands.
  • Motion planning: Calculates how the robot should move between target positions while respecting configured speed, acceleration, and motion constraints.
  • Kinematic transformation: Converts positions and orientations between coordinate systems and robot joint coordinates.
  • Axis coordination: Coordinates multiple robot axes to achieve the intended tool movement.
  • Servo coordination: Sends motion commands to the servo system and monitors feedback.
  • I/O processing: Reads sensors and process signals and controls configured outputs.
  • Communication: Exchanges status, commands, and handshake signals with PLCs, HMIs, vision systems, drives, and other equipment.
  • Diagnostics: Detects and reports program, motion, drive, communication, and configuration problems.
  • Safety integration: Interfaces with the robot's safety system and enforces the configured operating restrictions.

The exact division of responsibilities varies by robot manufacturer, controller generation, and safety architecture.

5. Robot Controller vs PLC vs Servo Drive

These devices work together, but their roles are different.

Device Primary responsibility Example
Robot controller Robot-specific programming, kinematics, and coordinated motion Move a robot tool along a welding seam
PLC Machine sequencing, interlocks, cell coordination, and process logic Confirm fixture clamping before permitting robot start
Servo drive Regulates motor current, torque, speed, or position according to its control architecture Drive a robot joint motor
Safety controller Executes configured safety-related logic Evaluate guard, enabling device, and safe-stop signals
HMI or teach pendant Provides operator interaction, programming, status, and diagnostics Select a program or jog the robot
CNC controller Coordinates machining axes and machining cycles Control a milling machine's tool path

A robot controller may contain integrated PLC-like functions, and some systems allow a PLC to command robot motions through an interface. That does not mean the devices have identical responsibilities.

6. Real-Time Control and Motion Execution

Robot motion is time-sensitive. The controller must coordinate the motion commands and feedback at the rates required by its architecture.

A typical motion sequence is:

  1. The program requests a target position or motion.
  2. The controller validates the instruction and relevant motion parameters.
  3. The motion planner calculates a feasible trajectory.
  4. Kinematic calculations convert the target into the required joint movement.
  5. The controller's motion system sends commands to the servo drives.
  6. Motors move the joints.
  7. Encoders or other feedback devices report actual movement.
  8. The controller compares actual behavior with expected behavior and monitors errors.
  9. The program continues, waits, slows, stops, or reports a fault according to the system's configured behavior.
Robot program
     ↓
Target position and motion parameters
     ↓
Trajectory planning and kinematics
     ↓
Joint motion commands
     ↓
Servo drives and motors
     ↓
Actual joint movement
     ↓
Encoder feedback
     ↓
Position and motion monitoring

Important distinction: The controller's motion loop is not the same as the application sequence. A robot program may be waiting for a PLC input while the controller continues monitoring its servo system.

7. Motion Types and Path Planning

Robot programming environments commonly provide several motion types. Names and exact behavior depend on the manufacturer.

Motion type General meaning Typical application
Joint or point-to-point Coordinates the robot joints to reach a target Pick-and-place, approach movements
Linear Controls the tool's path approximately or exactly along a straight line, as defined by the controller Welding, dispensing, insertion
Circular Moves the tool along a circular arc using specified geometry Arc welding, contour processing
Spline or continuous-path Follows a smooth path through multiple points Finishing, sealing, complex contours

7.1 Joint motion

The controller plans coordinated movement of the robot's joints. The tool's resulting path in space is not necessarily a straight line.

Use joint motion where the intermediate tool path is not critical, provided collision and safety constraints are satisfied.

7.2 Linear motion

The controller calculates coordinated joint movement to achieve a specified tool path in Cartesian space. Individual joints may accelerate and decelerate differently to maintain the required tool trajectory.

Typical uses include:

  • Moving a welding torch along a seam.
  • Inserting a component into a fixture.
  • Dispensing adhesive along a defined path.
  • Moving a tool through a narrow clearance.

7.3 Circular and continuous-path motion

Circular motion requires suitable geometric definition, such as a start point, intermediate point, and endpoint, depending on the controller. Continuous-path operations may also use blending or spline functions.

The controller must balance path accuracy, speed, acceleration, joint limits, and collision constraints. A command to move at a certain speed does not guarantee that speed can be maintained everywhere.

8. Coordinate Systems and Kinematics

The robot controller relies on coordinate systems to interpret targets correctly.

Common frames include:

  • World frame: A reference for the robot cell or work area.
  • Base frame: A reference associated with the robot base.
  • Joint coordinates: Individual robot-axis positions.
  • Tool frame: The position and orientation of the tool relative to its mounting flange.
  • Work or user frame: A reference associated with a fixture, workpiece, or process area.

The controller transforms target coordinates between the relevant frames and calculates the joint positions needed to achieve the requested tool pose.

8.1 Forward and inverse kinematics

  • Forward kinematics: Calculates the tool pose from known joint positions.
  • Inverse kinematics: Calculates possible joint configurations that achieve a requested tool pose.

A requested tool position may have multiple possible joint configurations. Reachability, joint limits, configuration settings, and singularities can affect which solutions are available.

8.2 Incorrect coordinate data

If the robot reaches a position but the tool is offset from the intended point, possible causes include:

  • Incorrect tool center point (TCP).
  • Incorrect work-frame or user-frame definition.
  • Incorrect robot mastering or calibration.
  • Wrong tool selected in the program.
  • Incorrectly defined fixture or workpiece position.
  • Incorrect robot configuration or recovery data.

Do not immediately change mastering to correct a tool offset. First establish whether the problem is tool data, work-frame data, mechanical movement, or actual mastering error.

9. Program Execution and Logic

Robot programs combine motion instructions with process logic.

Typical program elements include:

  • Motion commands.
  • Digital input and output commands.
  • Wait conditions.
  • Conditional branching.
  • Loops and counters.
  • Subroutines and reusable procedures.
  • Interrupts or event handling.
  • Tool and work-frame selection.
  • Speed and acceleration settings.
  • Error handling and recovery logic.

A simplified conceptual program sequence is:

Start program
     ↓
Check required machine conditions
     ↓
Move to approach position
     ↓
Wait for process permission
     ↓
Execute working motion
     ↓
Confirm process completion
     ↓
Move to safe or home position
     ↓
Report cycle completion

This is a logical example, not executable code. Real instructions and their syntax vary between robot programming systems.

9.1 Program waits

A program may be running but not moving because it is waiting for a condition. For example, it may be waiting for:

  • Fixture-clamped confirmation.
  • Part-present confirmation.
  • A PLC handshake bit.
  • A vision-system result.
  • A process-ready signal.
  • A timer or operator command.

A waiting program is not automatically a controller failure. Inspect the active instruction, the expected condition, the actual input state, and the source of that signal.

9.2 Program interrupts and subroutines

Subroutines help avoid duplicated logic. Interrupts can allow configured events to trigger additional handling. Their behavior and restrictions are controller-specific.

An interrupt should not be assumed to provide a safety function. Safety-related stopping and protective functions must use the validated safety architecture.

10. Robot Programming Languages and Platforms

Different manufacturers provide different programming environments.

Manufacturer Common programming language or environment General note

Syntax, program structure, motion commands, variable handling, and I/O conventions differ. A program written for one manufacturer's controller generally cannot be transferred directly to another without conversion and validation.

11. Robot Controller and PLC Integration

In an automated manufacturing cell, the PLC and robot controller typically exchange a defined set of signals.

Example handshake:

PLC confirms fixture clamped
          ↓
PLC permits robot cycle
          ↓
Robot checks required conditions
          ↓
Robot executes the selected program
          ↓
Robot reports cycle complete
          ↓
PLC advances the machine sequence

A typical interface may include:

Signal Typical direction Purpose
Robot ready Robot to PLC Controller is available under defined conditions
Program running Robot to PLC Indicates program execution state
Cycle complete Robot to PLC Indicates completion of the defined operation
Robot fault Robot to PLC Reports a fault condition
Start request PLC to robot Requests a program or cycle start
Program number or selection PLC to robot Identifies the requested program, where configured
Fixture clamped PLC to robot Confirms a required fixture condition
Part present Sensor or PLC to robot Confirms a part-related condition

These signals are examples, not a universal signal list. Names, polarity, and handshake rules must be verified against the actual cell design.

Critical distinction: A normal PLC handshake signal is not a substitute for a safety-rated signal. A standard Robot Ready or Start Permit bit must not be treated as proof that personnel are protected.

11.1 Communication methods

Depending on the controller and installation, integration may use:

  • Hardwired digital I/O.
  • PROFINET.
  • EtherNet/IP.
  • PROFIBUS.
  • TCP/IP or application-specific Ethernet interfaces.
  • Manufacturer-specific communication options.

A controller may be powered and functional while its fieldbus communication is unavailable. Diagnose controller health and network health separately.

12. Controller States and Operating Modes

Controller status names differ by manufacturer. Common conceptual states include:

  • Booting or initializing.
  • Ready.
  • Program running.
  • Program stopped.
  • Hold or paused.
  • Faulted.
  • Manual operation.
  • Automatic operation.
  • Recovery or mastering-related operation.

These are not necessarily mutually exclusive categories. A robot can be in automatic mode while stopped, for example.

When diagnosing a robot that will not start, establish:

  1. Is the controller fully booted?
  2. Is a fault active?
  3. Is the correct operating mode selected?
  4. Are the configured safety conditions satisfied?
  5. Is the robot in a valid program state?
  6. Is the intended program selected and permitted to start?
  7. Are the necessary external permissions present?

Do not assume that a displayed Ready state means every application-specific start condition has been met.

13. Controller Alarms and Diagnostics

Controller diagnostics help distinguish program problems from motion, drive, network, configuration, and safety problems.

Symptom or alarm category Possible causes Initial checks
Controller does not boot Power supply, internal hardware, storage, software issue Check supply status and startup indications using approved procedures
Controller is powered but not ready Active fault, safety condition, initialization issue Read the complete diagnostic message and controller state
Program will not start Mode, program selection, start permission, active fault Check start conditions and active program state
Program waits indefinitely Missing input, PLC handshake, vision result, process-ready signal Identify the waiting instruction and trace its expected condition
Axis or servo fault Drive fault, feedback issue, mechanical obstruction, motion limit Inspect axis diagnostics and mechanical conditions
Communication fault Cable, network, fieldbus configuration, remote device, mapping Check link status, device diagnostics, configuration, and signal updates
Pendant disconnected Cable, connector, interface, pendant fault Check connection and controller diagnostics using approved procedures
Unexpected path or position Incorrect frame, TCP, mastering, program data, or mechanical change Verify configuration and calibration history before changing data
Repeated controller reset Power instability, overheating, hardware or software issue Check event history, supply, temperature, and cooling

Never diagnose from an alarm number alone without identifying the controller model, software version, and complete alarm description. Similar-looking codes can have different meanings across platforms.

14. Systematic Troubleshooting Method

Use the following sequence during a breakdown.

Step 1: Establish the symptom

Record what the robot is doing, what it should be doing, and whether the problem started after maintenance, a program change, a collision, a power interruption, or a network change.

Step 2: Read the controller status

Record the complete alarm text, timestamp if available, active program, current instruction, affected axis, and relevant drive status.

Step 3: Check operating conditions

Verify the selected mode, required start conditions, configured safety status, and external permissions. Do not defeat interlocks to make the robot run.

Step 4: Identify where execution stopped

Determine whether the controller is booting, faulted, waiting on an input, blocked by a condition, or attempting motion.

Step 5: Trace the affected signal or subsystem

For a missing input, inspect the sensor, wiring, I/O module, communication mapping, and controller tag. For a servo fault, examine the axis diagnostics and the drive's reported condition.

Step 6: Compare against the last known good state

Use approved backups and change records to identify modifications to programs, frames, payloads, mastering, network configuration, or safety settings.

Step 7: Correct and validate

Apply the approved correction, verify the fault has cleared, test under the authorized operating procedure, and confirm the complete machine sequence.

Step 8: Document the outcome

Record the root cause, corrective action, changed configuration, validation results, and preventive action.

15. Backup and Configuration Management

A robot controller contains more than its application program. Recovery may require several distinct categories of data.

Data category Examples Why it matters
Application programs Main routines, subroutines, process paths Restores intended robot behavior
Robot configuration Motion parameters, configured options Restores the intended controller setup
Tool and work frames TCP, fixture and workpiece coordinates Maintains positional accuracy
Mastering and calibration Axis reference data and calibration parameters Maintains the relationship between encoder positions and robot geometry
I/O configuration Signal names, mappings, assignments Restores PLC and equipment integration
Network configuration Addresses, fieldbus settings, device assignments Restores communications
Safety configuration Validated safety parameters and logic Preserves the designed safety functions
System software Controller software and compatible versions Supports controlled restoration and compatibility

A backup is useful only if it is valid, complete enough for the intended recovery, and compatible with the target controller.

Important practices:

  • Take an approved backup before planned changes.
  • Keep controlled copies outside the controller.
  • Record controller identity, software version, backup date, and configuration changes.
  • Follow the manufacturer's procedure for restoring data.
  • Treat safety configuration and mastering data as controlled items requiring the appropriate verification.
  • Validate motion, tool frames, PLC handshakes, and safety functions after restoration as required by the approved procedure.

A successful file restore does not, by itself, prove the robot is safe or ready for production.

16. Preventive Maintenance of the Controller

Preventive maintenance should follow the manufacturer's maintenance schedule and the plant's electrical safety procedures.

  • Inspect cabinet cooling fans, filters, ventilation paths, and signs of overheating.
  • Check for contamination, moisture, corrosion, and loose or damaged connectors during approved inspections.
  • Review recurring controller, servo, and communication alarms.
  • Confirm that backups exist and that recovery procedures are documented.
  • Inspect pendant cables and connectors for wear or damage.
  • Verify that configuration changes are recorded and authorized.
  • Check network connections and communication health.
  • Replace batteries only where applicable and according to the specified procedure.
  • Maintain software and firmware compatibility records.
  • Verify safety-related functions after relevant maintenance or changes, according to the validated procedure.

Do not open energized equipment or handle internal controller components without the required authorization, training, isolation, and precautions.

17. Safety Considerations

Robot controller software is only one part of the cell's safety architecture.

Important principles:

  • Use the designated operating mode and approved enabling device for manual work.
  • Follow the manufacturer's procedure for jogging, recovery, and testing.
  • Never bypass guards, interlocks, enabling devices, or safety-rated functions to force motion.
  • Treat unexpected robot movement as a serious hazard.
  • Use lockout/tagout and verify the required energy isolation before work that requires it.
  • Remember that an emergency stop is not necessarily energy isolation.
  • Validate safety functions after any relevant repair, configuration change, or restoration.
  • Do not assume a standard PLC input, robot program condition, or normal communication bit is safety-rated.

For troubleshooting inside the robot cell, follow the site's risk assessment, permit requirements, and machine-specific safety procedures.

18. Automotive Manufacturing Example

Consider a robot that loads a component into a test fixture.

  1. The PLC confirms that the fixture is available.
  2. The PLC sends the configured robot start request.
  3. The robot controller checks the program and required conditions.
  4. The robot moves to the loading position.
  5. The robot places the component and reports completion.
  6. The PLC checks the handshake and continues the machine sequence.

Suppose the robot stops before loading the component and its program is waiting for Fixture_Clamped.

A useful diagnostic sequence is:

  • Confirm that the active program is waiting for the expected signal.
  • Check whether the PLC's fixture-clamped condition is actually true.
  • Inspect the fixture sensor and its wiring if the condition is false.
  • If the PLC condition is true but the robot does not see it, check the I/O mapping, fieldbus health, and signal update.
  • If the robot sees the signal but remains stopped, inspect the next program condition and any active controller or safety-related status.
  • After correction, validate the entire sequence under the authorized procedure.

This avoids replacing a robot component when the real fault is a missing fixture confirmation or incorrect signal mapping.

19. Interview Questions and Answers

Q1. What is the primary function of a robot controller?

It executes robot programs, plans motion, coordinates the axes, processes I/O, communicates with other equipment, and monitors the robot system.

Q2. How is a robot controller different from a PLC?

A robot controller specializes in robot programming, kinematics, and coordinated motion. A PLC commonly manages machine sequencing, interlocks, and coordination across equipment.

Q3. What is real-time control?

Real-time control performs time-sensitive operations within the timing constraints required by the system. Correct timing matters as well as correct calculations.

Q4. What is the difference between joint motion and linear motion?

Joint motion coordinates the robot joints to reach a target, without necessarily maintaining a straight tool path. Linear motion controls the tool's trajectory along a defined straight path in Cartesian space.

Q5. Why can a robot wait indefinitely even when no major fault is active?

Its program may be waiting for a missing sensor signal, PLC handshake, process permission, or other programmed condition.

Q6. What is inverse kinematics?

It calculates possible robot joint configurations for a requested tool position and orientation.

Q7. Why should TCP data be checked before changing mastering?

A tool offset can cause positional error without indicating that the robot's axis reference data is wrong. Changing mastering unnecessarily can introduce a more serious calibration problem.

Q8. What information should be recorded when a controller fault occurs?

The complete alarm text, timestamp, active program and instruction, controller state, affected axis, relevant I/O states, recent changes, and corrective actions.

Q9. Why is a controller backup important?

It supports recovery of application programs and configuration after hardware failure, corruption, or an approved change. Backup scope and restoration requirements must be verified.

Q10. Can a robot controller's standard program logic replace safety-rated control?

No. Safety functions must be implemented and validated using the appropriate safety-rated architecture.

Q11. What is the purpose of a robot-to-PLC handshake?

It coordinates the sequence between the robot and the rest of the machine, using defined request, status, permission, and completion signals.

Q12. Why can restoring a backup still leave a robot unready for production?

The backup may be incomplete or incompatible, or the restored mastering, safety, I/O, network, or process configuration may require separate verification.

20. Practical Exercises

  • Identify the main controller, servo drives, I/O modules, network interfaces, and safety interfaces on an available robot system.
  • Find the controller's current state, active program, and diagnostic history without changing operating conditions.
  • Trace one PLC-to-robot input from its source through the I/O or network mapping to the robot program.
  • Trace one robot-to-PLC status signal in the reverse direction.
  • Compare a joint-motion instruction with a linear-motion instruction in approved documentation or a safe offline environment.
  • Review an approved backup and identify which categories of configuration it includes.
  • Build a fault record for a simulated program-wait condition, missing communication signal, and servo alarm.
  • Review the plant's recovery procedure and identify which checks are required before returning the robot to automatic production.

21. Final Mental Model

A robot controller converts a programmed task into coordinated physical movement while monitoring the robot and its connected equipment.

Program and process conditions
          ↓
Controller interprets instructions
          ↓
Motion planning and kinematics
          ↓
Coordinated axis commands
          ↓
Servo drives and motors
          ↓
Robot movement and feedback
          ↓
Status monitoring and program progression
          ↓
PLC coordination and process completion

For maintenance and retrofit work, the most important skill is to identify where the sequence stopped: program execution, a required input, motion planning, a servo axis, communication, or a safety-related condition. That distinction turns troubleshooting from guesswork into a repeatable engineering process.
