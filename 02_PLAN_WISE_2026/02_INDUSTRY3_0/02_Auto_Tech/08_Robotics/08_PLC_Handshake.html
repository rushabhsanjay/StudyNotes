PLC Handshake: Robot and PLC Coordination

1. Fundamentals

A PLC handshake is a defined sequence of signals exchanged between a PLC and a robot controller to coordinate operations, confirm status, and prevent one device from proceeding before the other is ready.

In an automated production line, the PLC typically coordinates the machine or station sequence, while the robot controller executes robot programs and manages robot motion. Both controllers must agree on when an operation can start, when it is running, when it has completed, and how faults are handled.

A handshake is not simply a collection of ON/OFF bits. It is a communication protocol with defined states, transitions, acknowledgements, and fault-handling rules.

Typical applications include:

  • Robot loading and unloading of CNC machines.
  • Robot pick-and-place stations.
  • Welding and assembly lines.
  • Conveyor tracking and pallet handling.
  • Fixture clamping and part transfer.
  • Robot-to-robot coordination.
  • Automated inspection and material handling.

2. Basic Robot-PLC Architecture

             PLC Controller
                  |
        PLC Sequence / State Logic
                  |
        Industrial Communication
        or Hardwired Digital I/O
                  |
           Robot Controller
                  |
        Robot Program / Motion
                  |
          Robot and Tooling
                  |
        Sensors / Gripper / Part

The communication may use hardwired digital I/O or industrial networks such as PROFINET, EtherNet/IP, or another supported fieldbus.

The transport mechanism can differ, but the handshake still needs clearly defined signal meanings and transition rules.

For example, the PLC may request a robot cycle, but the robot should not begin merely because the request bit is ON. It should also verify that the request is valid for the current robot state and that required start conditions are satisfied.

3. Main Handshake Signals

The following is a common conceptual signal set. Actual names and ownership must be defined by the machine's interface specification.

Signal Direction relative to robot Purpose
PLC_START_REQ PLC to robot Requests a robot cycle
PLC_AUTO_MODE PLC to robot Reports the requested or permitted operating mode
PLC_STATION_READY PLC to robot Indicates that the station is prepared for the operation
ROBOT_READY Robot to PLC Reports that the robot meets the defined readiness conditions
ROBOT_BUSY Robot to PLC Indicates that the robot cycle is executing
ROBOT_CYCLE_COMPLETE Robot to PLC Reports completion of the defined cycle
ROBOT_FAULT Robot to PLC Reports a relevant robot fault
ROBOT_ACCEPTED Robot to PLC Acknowledges acceptance of a request, if the design uses this signal
PLC_RESET_REQ PLC to robot Requests a reset operation, subject to permitted conditions
ROBOT_HOME Robot to PLC Reports that the robot satisfies the defined home-position condition

These are illustrative names, not universal robot I/O conventions.

Important: ROBOT_READY, ROBOT_HOME, ROBOT_BUSY, and ROBOT_CYCLE_COMPLETE represent different conditions. They should not be treated as interchangeable.

For example, a robot may be at its home position but still be faulted. Another robot may be ready to run while not physically at home, if the interface design permits starting from its current position.

4. Request, Acknowledgement, and Completion

Three distinct events are central to reliable handshaking.

4.1 Request

The PLC asserts a request to ask the robot to perform an operation.

Example:

PLC_START_REQ = ON

The request communicates intent. It does not prove that the robot has accepted or started the operation.

4.2 Acknowledgement

The robot indicates that it has accepted the request or reached the defined state associated with it.

Example:

ROBOT_ACCEPTED = ON

Acknowledgement confirms the protocol event defined by the interface. It does not necessarily mean that physical motion has begun.

Some systems do not use a separate acknowledgement bit. In those systems, the transition of ROBOT_BUSY or another documented status may serve as confirmation.

4.3 Completion

The robot reports that the requested operation has reached its defined completion condition.

Example:

ROBOT_CYCLE_COMPLETE = ON

Completion must have a precise meaning. It might mean that the robot has finished a programmed sequence, placed a part, returned to a transfer position, or completed a particular station operation.

The signal must not be interpreted as proof of a physical result unless the program also verifies the required feedback.

For instance, completion of a gripper command is not automatically proof that the part was successfully gripped.

5. A Typical Handshake Sequence

A simplified sequence for a robot loading a machine may be:

  1. The PLC verifies that the machine is ready for loading.
  2. The PLC asserts the robot start request.
  3. The robot validates the request and its own start conditions.
  4. The robot acknowledges or indicates that the cycle has started.
  5. The robot executes the loading sequence.
  6. The robot verifies required conditions, such as gripper feedback and the defined placement condition.
  7. The robot reports cycle completion.
  8. The PLC acknowledges the completion or advances its machine sequence.
  9. The request and completion signals are reset according to the interface protocol.

Conceptually:

 |                             |
 |---- START REQUEST --------->|
 |                             |
 |<--- ACCEPTED / BUSY --------|
 |                             |

 |                       Verify operation
 |                             |
 |<--- CYCLE COMPLETE ---------|
 |                             |

 |                             |
 |<--- COMPLETE RESET ---------|

The diagram shows one possible four-phase exchange. Some interfaces use a different number of signals or a different reset sequence. The actual protocol must be documented and implemented consistently at both ends.

6. Level-Based and Edge-Based Requests

6.1 Level-based request

A level-based request remains ON while the request is active.

The receiver evaluates the state of the request together with its other conditions.

Example:

PLC_START_REQ = ON

The request remains active until the protocol defines that it can be reset.

This can be robust when the communication system updates the signal periodically, but the logic must prevent the same request from accidentally starting multiple cycles.

6.2 Edge-based request

An edge-based request reacts to a transition, such as OFF to ON.

For example:

PLC_START_REQ: OFF → ON

The receiving logic detects the transition and triggers an operation.

Edge-based logic requires careful handling if the receiver restarts, misses a transition, or reconnects after a communication interruption. A persistent request level or a sequence counter may be more suitable in some architectures.

6.3 Why the distinction matters

Characteristic Level-based Edge-based
Trigger Signal state Signal transition
Request duration Usually held until protocol reset May be momentary or held, depending on implementation
Main risk Repeated acceptance if state logic is poor Lost or repeated event after restart or communication disruption
Typical requirement Defined acceptance and reset conditions Reliable transition detection and recovery logic

Neither method is automatically better. Choose one according to the controller interface, communication reliability, and required recovery behaviour.

7. The Four-Phase Handshake Pattern

One useful design pattern is a four-phase request and acknowledgement exchange.

The request and acknowledgement are held until the opposite controller has observed the transition. Both signals then return to OFF in a defined order.

Phase PLC request Robot acknowledgement Meaning
Idle OFF OFF No active transaction
Request ON OFF PLC requests an operation
Acknowledged ON ON Robot confirms acceptance or the specified response
Request cleared OFF ON PLC has observed the acknowledgement and clears its request
Return to idle OFF OFF Robot clears acknowledgement; next transaction may begin

This pattern is a protocol example, not a universal standard. The signal names and exact phase meanings vary by system.

A separate completion signal may be needed if the acknowledgement only confirms that the request was accepted, rather than confirming that the operation has finished.

8. Handshake State Machine

A state machine makes the sequence easier to understand, diagnose, and maintain.

Example states for a robot cycle:

State Description Example transition condition
IDLE No active robot transaction Valid start request and permitted conditions
VALIDATE Checking request and interlocks All required conditions satisfied
ACCEPTED Request accepted Cycle begins
RUNNING Robot executes the program Required operation finishes
VERIFY Checks required completion feedback Verification passes
COMPLETE Reports successful completion PLC observes completion
RESET Clears handshake state Signals return to the defined idle condition
FAULT Abnormal condition detected Approved recovery procedure succeeds

This is a conceptual model. A real robot program may use different states, and safety functions remain independent of ordinary sequence-state logic.

The key benefit is that every transition has an explicit condition. The robot should not jump from idle directly to completion merely because a request bit is active.

9. Interlocks and Start Conditions

A handshake must define the conditions under which an operation may start.

Possible conditions include:

  • Robot controller is in the required operating state.
  • Robot is not faulted.
  • The requested program or operation is valid.
  • The PLC station is ready.
  • The correct part or fixture condition is present.
  • Required gripper and tool conditions are satisfied.
  • Required machine doors and process conditions are valid.
  • The robot is in an approved starting region or position, if required by the sequence.

Not all conditions belong in the same controller. The interface design should identify which controller owns each condition and how its status is communicated.

Safety distinction: Ordinary PLC handshake bits must not replace safety-rated protective functions. A signal indicating that a guard is closed is not, by itself, proof that the safety system has permitted motion.

10. Timeouts and Fault Handling

A reliable handshake must handle cases where an expected transition never occurs.

Examples:

  • The PLC sends a start request, but the robot never accepts it.
  • The robot starts but never reports completion.
  • The robot commands a gripper, but the feedback does not arrive.
  • A fieldbus connection is lost during a cycle.
  • A required machine-ready signal drops unexpectedly.
  • A completion acknowledgement remains active indefinitely.

A timeout detects that an expected event did not occur within the permitted period.

Conceptually:

Wait for expected signal
          |
          v
Signal received before timeout?
       /          \
     Yes           No
      |             |
 Continue       Timeout fault
                    |
              Defined response

Timeout values should be based on actual machine behaviour, process requirements, and validated worst-case timing, with appropriate margin.

A timeout is not a substitute for detecting a real fault. For example, if gripper feedback is missing, the program should distinguish between a sensor or communication problem and a possible failure to hold the part when the available diagnostics allow it.

10.1 Fault response

Depending on the system design, a timeout may cause the controller to:

  • Stop advancing the normal sequence.
  • Set a diagnostic fault.
  • Notify the PLC.
  • Preserve relevant status for troubleshooting.
  • Enter a controlled recovery state.
  • Require operator intervention.

The response must be appropriate to the hazard and machine design. A normal sequence timeout must not be used as a replacement for emergency stopping or another required safety function.

11. Communication Loss and Controller Restart

PLC-robot communication can be interrupted by network failure, device reboot, power loss, or configuration problems.

The interface must define what happens if either controller restarts while a request or acknowledgement remains active.

Important design questions include:

  • Are all handshake signals reset at startup?
  • Can an old request trigger a new cycle after reconnection?
  • Does the robot retain its program state after a controller restart?
  • Does the PLC know whether the robot completed the previous operation?
  • Is the part still held by the gripper?
  • Must the system require operator confirmation before resuming?

Avoid automatically restarting a motion cycle simply because communication returns. The system must re-establish a known state and verify the physical situation before resuming.

12. Part Tracking and Transaction Identity

In simple cells, a request bit may be enough to identify an operation. In more complex systems, the interface may need additional information.

Examples include:

  • Program or recipe number.
  • Part type.
  • Station identifier.
  • Pallet or workpiece identifier.
  • Operation number.
  • Transaction counter.
  • Result code.

A transaction identifier can help distinguish a new request from stale status left over from a previous cycle.

For example, if a PLC sends recipe 12, the robot should validate that the recipe is supported and that the corresponding operation is appropriate for the current station state.

For more complex interfaces, a sequence counter or transaction number can improve recovery and traceability. The protocol must define how both controllers initialize, increment, compare, and recover the identifier.

13. Common Handshake Design Errors

Error Consequence Corrective approach
PLC request stays ON after completion Robot may accept the request again Define a request-reset condition and prevent duplicate acceptance
Robot completion bit is never reset PLC may interpret a stale completion as a new result Define explicit completion acknowledgement and reset logic
Busy and ready signals overlap without defined meaning PLC may make incorrect sequencing decisions Define each signal's exact state semantics
Command is treated as proof of physical success Faulty actuator operation may go undetected Verify physical feedback where required
No timeout exists Sequence can wait indefinitely Add justified timeout handling and diagnostics
Both controllers reset signals independently Race conditions or lost transactions Define signal ownership and reset order
Edge is too brief to detect Start or reset event may be missed Use a persistent handshake, event-capture mechanism, or suitable communication protocol
Communication recovery resumes automatically Stale requests may trigger unexpected motion Reconcile controller states and validate the physical cell before resuming
Program completion is confused with station completion PLC may advance before the station is ready Define the completion boundary and any additional machine feedback
Handshake logic is used as a safety circuit Required protective function may be absent Use the validated safety architecture for safety functions

14. Practical Industrial Example: Robot Loading a CNC Machine

Consider a robot that loads a component into a CNC machine.

14.1 PLC responsibilities

The PLC typically coordinates the machine's operating sequence and determines when the CNC station is ready to accept a part.

Possible conditions include:

  • CNC cycle has ended.
  • Machine is in the required state.
  • Door and fixture conditions are satisfied.
  • The station is ready for robot access.
  • Required protective functions permit the operation.

14.2 Robot responsibilities

The robot controller manages the robot program and motion.

Possible operations include:

  • Move to the machine approach point.
  • Enter the permitted loading region.
  • Pick up the part.
  • Place the part in the fixture.
  • Verify required gripping or placement feedback.
  • Withdraw from the machine.
  • Report completion according to the interface definition.

14.3 Sequence example

CNC cycle complete
        ↓
PLC confirms station ready
        ↓
PLC sends robot load request
        ↓
Robot validates request
        ↓
Robot performs loading operation
        ↓
Robot verifies required placement conditions
        ↓
Robot withdraws from the machine
        ↓
Robot reports load complete
        ↓
PLC confirms machine can continue

The actual sequence must include the machine's required door, fixture, access, and safety conditions. The order of those conditions depends on the machine and cell design.

A robot reporting LOAD_COMPLETE must have a documented definition. For example, the part may be placed but the robot may still be inside the machine. If so, the PLC must not interpret load completion as permission to close the door or restart the machining cycle until the separate required clearance and interlock conditions are satisfied.

15. Troubleshooting a Robot-PLC Handshake

When a cell stops waiting for a signal, trace the sequence in chronological order.

  1. Identify the state where the sequence stopped.
  2. Identify the exact signal that the controller is waiting for.
  3. Confirm which controller owns and generates that signal.
  4. Observe the signal in both PLC and robot diagnostics.
  5. Check whether the request and acknowledgement transitions occurred in the expected order.
  6. Verify relevant physical feedback and interlocks.
  7. Inspect communication and I/O mapping diagnostics.
  8. Check timeout and fault messages.
  9. Determine whether a stale signal or incorrect reset sequence caused the problem.
  10. Restore operation using the approved recovery procedure and validate the full sequence.

Example: Robot never starts

Suppose the PLC asserts PLC_START_REQ, but the robot remains idle.

Check:

  • Is the signal actually arriving at the robot controller?
  • Is the robot in the expected operating state?
  • Is the requested program available and valid?
  • Is ROBOT_READY true according to its documented definition?
  • Are required station and process conditions satisfied?
  • Is the start request being rejected because the robot is already busy or faulted?
  • Has the request been cleared before the robot can accept it?
  • Are PLC and robot using the same signal mapping and handshake definitions?

Do not force the robot to start by bypassing the conditions before identifying why the handshake failed.

16. Maintenance and Change Control

The handshake is part of the machine's functional interface. Changes to signal definitions or reset behaviour can affect the entire station.

Maintain:

  • PLC and robot I/O lists.
  • Signal ownership and direction.
  • State and transition definitions.
  • Request, acknowledgement, and completion semantics.
  • Timeout values and their rationale.
  • Fault and recovery procedures.
  • Communication configuration.
  • Program and PLC logic revisions.
  • Approved test results.
  • Relevant safety-interface documentation.

When replacing a controller, updating a robot program, or changing networked I/O, verify that both sides still agree on the interface contract.

A signal name remaining unchanged does not guarantee that its meaning or timing behaviour has remained unchanged.

17. Interview Questions and Answers

Q1. What is a PLC handshake?

A defined exchange of requests, acknowledgements, status, and completion signals that coordinates operations between a PLC and another controller, such as a robot.

Q2. What is the difference between request, acknowledgement, and completion?

A request asks for an operation. An acknowledgement confirms the defined response to that request. Completion reports that the defined operation has finished.

Q3. Why is a handshake needed if both controllers are connected through a network?

A network transports data. The handshake defines how the controllers use that data to coordinate sequence, avoid duplicate operations, detect missing transitions, and handle faults.

Q4. What is a handshake timeout?

A timeout detects that an expected signal or state transition did not occur within the permitted period.

Q5. What is the difference between level-based and edge-based triggering?

Level-based logic responds to a signal state. Edge-based logic responds to a transition, such as OFF to ON.

Q6. Why must the robot reset its completion signal?

Without a defined reset, the PLC may interpret an old completion state as the result of a new operation.

Q7. What happens if communication is lost during a cycle?

The controllers must follow the defined fault and recovery strategy. They should reconcile their states and verify the physical machine condition before continuing.

Q8. Why is ROBOT_READY different from ROBOT_HOME?

Ready describes a defined operational condition. Home describes a defined robot position or posture. A robot may satisfy one condition without satisfying the other.

Q9. How would you diagnose a robot that never acknowledges a PLC request?

Verify the request at both controllers, signal mapping, robot state, program availability, start conditions, interlocks, communication health, and any rejection or fault diagnostics.

Q10. Can ordinary PLC handshake bits provide emergency-stop protection?

No, not by themselves. Safety functions require an appropriate safety-rated design, components, configuration, and validation.

18. Practical Exercises

Exercise 1: Build a handshake signal list

Create an interface list for a robot loading station. Include the start request, robot ready, busy, cycle complete, fault, station ready, and any required acknowledgement signals.

For every signal, document its direction, owner, meaning, activation condition, and reset condition.

Exercise 2: Draw a state-transition table

Create states for IDLE, VALIDATE, RUNNING, VERIFY, COMPLETE, RESET, and FAULT.

For each transition, specify the exact condition that allows the next state and what happens if the condition does not occur.

Exercise 3: Diagnose a stuck request

Assume the PLC request remains ON after the robot has completed its cycle.

Identify how the robot might accidentally accept the same request again, then define a reset sequence that prevents duplicate execution.

Exercise 4: Diagnose a missing completion

Assume the robot is physically at its final position, but the PLC never sees ROBOT_CYCLE_COMPLETE.

Check the robot program's completion logic, physical feedback requirements, output mapping, fieldbus health, and PLC input mapping. Do not assume that reaching a position automatically sets the completion signal.

Exercise 5: Design recovery after a controller restart

Define what happens if the PLC restarts while the robot is holding a part and a request remains active.

The recovery procedure should establish a known controller state, verify the physical part and robot condition, prevent accidental duplicate execution, and require the appropriate authorization before resuming.

19. Final Mental Model

  • Request means an operation is being asked for.
  • Acknowledgement means the receiver has reached the defined response state.
  • Busy indicates that work is in progress according to the interface definition.
  • Completion means the specified operation has reached its documented completion condition.
  • Reset returns the protocol to its defined idle state.
  • Timeouts detect missing transitions.
  • Fault handling prevents normal sequencing from continuing when required conditions are not satisfied.
  • Recovery logic reconciles controller states and physical conditions after faults or communication interruptions.

The central principle is simple: both controllers must agree on the meaning, order, and reset behaviour of every handshake signal. Reliable coordination comes from explicit state transitions, verified feedback, and well-defined recovery, not from a pile of bits that happen to turn green.
