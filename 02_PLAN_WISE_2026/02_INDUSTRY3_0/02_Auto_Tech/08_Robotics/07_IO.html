Robot I/O: Digital Inputs, Digital Outputs, and Analog Signals

1. Fundamentals of Robot I/O

Robot I/O means Input/Output signals that allow the robot controller to communicate with external equipment such as PLCs, grippers, sensors, welding systems, fixtures, conveyors, and safety devices.

A robot program does not operate independently. It often needs to detect whether a part is present, command a gripper to close, confirm that the gripper has closed, and coordinate its movement with the surrounding machine.

I/O provides the signals used for these interactions.

  • Input: A signal received by the robot controller from an external device.
  • Output: A signal sent by the robot controller to an external device.
  • Digital I/O: Signals represented by discrete states, typically ON and OFF.
  • Analog I/O: Signals represented by a continuously variable numerical value within a defined range.
  • Fieldbus I/O: Signals exchanged through an industrial communication network rather than individual hardwired signal conductors.
  • Internal signal: A software-defined signal used inside a controller or program, rather than necessarily being connected to a physical terminal.

2. Basic Robot I/O Architecture

A typical industrial robot cell may contain the following components:

Sensors / Pushbuttons / Machine Signals
                 ↓
          Robot Inputs
                 ↓
          Robot Controller
                 ↓
          Robot Program
                 ↓
          Robot Outputs
                 ↓
      Gripper / Valve / Machine

For a PLC-controlled robot cell, the PLC and robot controller exchange additional signals.

             PLC Controller
             ↕           ↕
       PLC Inputs     PLC Outputs
             ↕           ↕
      Robot Outputs  Robot Inputs
             ↕           ↕
        Robot Controller
             ↓
       Robot Motion System

The exact arrangement depends on the cell architecture. A PLC may own the overall machine sequence while the robot controller executes the robot motion program. Alternatively, some equipment may communicate directly with the robot controller.

Important distinction: A robot output indicating that a command has been issued does not automatically prove that the commanded physical action has completed.

For example, a GRIP_CLOSE_CMD output may energize a valve, but a separate sensor or device status signal is normally needed to confirm successful gripping.

3. Types of Robot I/O

3.1 Digital inputs

A digital input represents a discrete state.

Common examples include:

  • Part present.
  • Gripper open.
  • Gripper closed.
  • Fixture clamped.
  • Conveyor ready.
  • Start request.
  • Reset request.
  • Process complete.
  • Fault feedback.

Example:

DI_PART_PRESENT = ON

The robot program may interpret this as permission to continue toward a pickup position, provided all other required conditions are satisfied.

Digital inputs can be implemented using hardwired electrical signals or networked I/O data.

3.2 Digital outputs

A digital output commands or signals a discrete state.

Examples include:

  • Gripper close command.
  • Gripper open command.
  • Fixture clamp request.
  • Conveyor start request.
  • Welding enable.
  • Robot cycle complete.
  • Robot fault active.
  • Part release permission.

Example:

DO_GRIP_CLOSE_CMD = ON

This means the controller has asserted the output. It does not prove that the valve, actuator, or gripper has responded correctly.

3.3 Analog inputs

Analog inputs receive variable electrical signals representing measurements or commands.

Common industrial signal ranges include:

  • 0 to 10 V.
  • 4 to 20 mA.
  • Other voltage or current ranges supported by the installed hardware.

Examples include:

  • Force or pressure feedback.
  • Distance measurement.
  • Position feedback.
  • Process temperature.
  • External speed reference.
  • Welding or dispensing process feedback.

An analog signal requires suitable scaling, engineering units, and validation. A raw input value is not automatically a meaningful engineering measurement.

3.4 Analog outputs

Analog outputs generate variable signals to control compatible equipment.

Examples include:

  • Speed reference to a drive.
  • Proportional valve command.
  • Process parameter reference.
  • Analog command to compatible welding equipment.

For example, a controller might generate a 0 to 10 V reference corresponding to a configured 0 to 100% command range. The exact relationship must be defined by the receiving device's configuration.

3.5 Internal and simulated signals

Internal signals are logical flags used within a program or controller.

Examples include:

  • PART_PICKED
  • ROBOT_AT_HOME
  • CYCLE_ACTIVE
  • RETRY_ALLOWED

They may be derived from physical I/O, program logic, communication data, or a combination of these.

Internal signals are useful for sequencing and program structure, but they must not be confused with physical feedback. A software flag named GRIPPER_CLOSED is not proof of actual gripper closure unless it is derived from valid feedback.

4. Signal Naming and Documentation

Good signal names describe the function and, where necessary, the signal direction.

A practical convention is to include the equipment, function, and signal role.

Signal name Meaning Direction relative to robot
DI_PART_PRESENT Part detected Input
DI_GRIP_OPEN_FB Gripper open feedback Input
DI_GRIP_CLOSED_FB Gripper closed feedback Input
DO_GRIP_OPEN_CMD Request gripper opening Output
DO_GRIP_CLOSE_CMD Request gripper closing Output
DO_ROBOT_READY Robot reports ready Output
DO_CYCLE_COMPLETE Robot reports cycle complete Output
DI_PLC_START_REQ PLC requests cycle start Input
AI_FORCE_FEEDBACK Measured force signal Analog input
AO_SPEED_REFERENCE Speed reference command Analog output

These names are illustrative. A production system should follow the plant's established naming convention.

Document at least the following for each physical signal:

  • Signal name and function.
  • Robot I/O address.
  • Electrical type and voltage level.
  • Source or destination device.
  • Terminal number or network mapping.
  • Normal state and active state.
  • Signal polarity.
  • Related sequence or interlock.
  • Diagnostic method.
  • Safety classification, where applicable.

5. Electrical Fundamentals of Digital I/O

5.1 Voltage and signal compatibility

Before wiring a digital input or output, verify:

  • Rated operating voltage.
  • Input ON and OFF thresholds.
  • Output current capacity.
  • Output type.
  • Common and reference connections.
  • Isolation and grounding requirements.
  • Cable routing and noise susceptibility.

A signal that appears logically correct in software may fail electrically because the output voltage, current capability, or common reference is incompatible with the receiving input.

Never assume that every industrial robot I/O point is 24 V DC. Verify the installed module specifications.

5.2 PNP and NPN sensors

PNP and NPN describe common transistor-output sensor arrangements.

  • PNP output: Typically sources current from the positive supply to the input circuit when ON.
  • NPN output: Typically sinks current toward the negative supply when ON.

The sensor output type must match the receiving input arrangement.

For example, a PNP sensor connected to an incompatible input circuit may fail to produce a valid ON state even when the sensor detects the target.

Check the sensor wiring diagram, controller input specification, and required common connections before troubleshooting the program.

5.3 Sourcing and sinking outputs

Sourcing and sinking describe how an output circuit supplies or conducts current.

The compatibility of a sensor, robot input, robot output, and PLC input depends on the electrical topology.

Do not infer compatibility from wire colours alone. Use the manufacturer's connection diagram and module specifications.

5.4 Relay and transistor outputs

Output type Characteristics Typical considerations
Relay Mechanical contacts; can switch compatible AC or DC loads within ratings Contact wear, switching frequency, inductive-load suppression
Transistor Electronic switching, commonly for DC loads Polarity, current limits, leakage current, switching characteristics
Networked output Output data transmitted through a fieldbus device Communication health, module diagnostics, update timing

An inductive load such as a solenoid valve can generate a voltage transient when switched off. Appropriate suppression must be selected for the circuit and device, following the manufacturer's instructions.

Do not add suppression components blindly because an unsuitable component can affect release time or circuit operation.

6. Robot I/O Mapping

Mapping associates a logical program signal with a physical terminal, remote I/O point, or network data location.

A signal may be represented differently at several levels:

Robot Program Signal
        ↓
Logical I/O Mapping
        ↓
Robot Controller I/O System
        ↓
Physical Module or Fieldbus Device
        ↓
External Sensor or Actuator

For example, a program may use DO_GRIP_CLOSE_CMD, while the controller maps that logical signal to a physical output channel or a bit in a fieldbus data block.

The program name does not reveal the electrical terminal automatically. Mapping documentation is essential during maintenance and troubleshooting.

6.1 Local and remote I/O

Local I/O is connected to I/O hardware installed at or near the controller.

Remote I/O is connected through distributed I/O hardware located elsewhere in the cell and communicating over an industrial network.

Remote I/O can reduce long runs of individual conductors, but introduces network configuration, device health, and communication diagnostics into the troubleshooting process.

6.2 I/O address versus signal name

A signal name describes the function. An address identifies the location used by the controller or communication system.

An address may refer to:

  • A local physical input or output channel.
  • A remote I/O channel.
  • A mapped network bit.
  • A word or register containing multiple signals.
  • A controller-specific logical I/O number.

Address formats differ between manufacturers and controller versions. Always use the actual system configuration rather than copying an address convention from another robot.

7. Robot Program Interaction With I/O

I/O commonly determines when a program can proceed, when an actuator is commanded, and whether an operation has completed successfully.

A basic pickup sequence might work as follows:

  1. Move to a safe pickup approach.
  2. Confirm that the part is present.
  3. Move to the pickup position.
  4. Command the gripper to close.
  5. Wait for valid gripper-closed feedback.
  6. Confirm that no relevant fault or timeout has occurred.
  7. Withdraw with the part.

Conceptually:

Check part present
        ↓
Move to pickup
        ↓
Command gripper close
        ↓
Wait for closed feedback
        ↓
Feedback received?
   ↙           ↘
 Yes            No
  ↓              ↓
Continue       Timeout / Fault

The real program must account for the controller's programming language, task structure, timeout handling, recovery rules, and applicable safety requirements.

7.1 Command versus feedback

The distinction between a command and feedback is one of the most important principles in robot integration.

Signal Purpose What it proves
GRIP_CLOSE_CMD Requests closure The command was asserted
GRIP_CLOSED_FB Reports closed condition The feedback circuit indicates closure
PART_HELD_FB Reports part retention, if provided The relevant detection system indicates that a part is held
GRIPPER_FAULT Reports device fault The device or associated logic indicates a fault

The feedback signal itself can also fail, so diagnostics must consider the sensor, wiring, I/O hardware, and logic.

Do not replace physical confirmation with an internal flag merely to make the sequence proceed.

8. Signal Timing, Debouncing, and Pulse Signals

8.1 Signal delay

A signal may take time to propagate from a sensor through an input module, network, controller task, and program logic.

Similarly, an output command may take time to reach an actuator and produce a physical response.

The total response time depends on the equipment and architecture.

8.2 Input filtering and debouncing

Mechanical switches and some sensors can produce brief state changes or electrical noise.

Input filtering or debouncing may be used to avoid interpreting every transient as a valid state transition.

However, excessive filtering can delay detection and affect cycle timing. Filter settings should be chosen according to the device, signal characteristics, controller capabilities, and required response time.

8.3 Pulse signals

Some signals are intended to be momentary pulses rather than sustained states.

Examples include:

  • A trigger to start a process.
  • A request to reset a device.
  • A one-time event notification.

If a pulse is too short for the receiving system to detect, the event may be missed. If the signal stays ON too long, the receiver may interpret it repeatedly, depending on its logic.

For critical sequence events, use a suitable handshake or event-capture mechanism instead of assuming both controllers will observe every brief transition.

9. Analog I/O: Scaling and Diagnostics

Analog signals require correct configuration at both ends.

For example, a 4 to 20 mA transmitter may represent a pressure range from 0 to 10 bar.

The engineering value can be calculated as:

\[ PV = \frac{I - 4}{16} \times 10 \]

Where:

  • \(PV\) is the pressure in bar.
  • \(I\) is the measured current in mA.
  • 4 mA represents the lower end of the configured measurement range.
  • 20 mA represents the upper end.

At 12 mA:

\[ PV = \frac{12 - 4}{16} \times 10 = 5\text{ bar} \]

This example assumes linear scaling and a configured 0 to 10 bar range. Real instruments may use different ranges, nonlinear scaling, or additional fault conventions.

9.1 Common analog faults

  • Incorrect range configuration.
  • Incorrect engineering-unit scaling.
  • Open circuit or wiring fault.
  • Short circuit or overload.
  • Incorrect current/voltage mode.
  • Electrical noise or grounding problems.
  • Incorrect channel configuration.
  • Sensor calibration drift.
  • Incorrect raw-data interpretation.

A reading near zero does not always mean the physical measurement is zero. For example, a current loop below its expected range may indicate a fault rather than a valid zero process value.

10. Robot I/O and PLC Integration

A robot cell commonly exchanges discrete signals with a PLC.

Typical robot-to-PLC signals include:

  • Robot ready.
  • Robot running.
  • Robot cycle complete.
  • Robot fault.
  • Robot at home or safe transfer position.
  • Part picked or part placed confirmation.

Typical PLC-to-robot signals include:

  • Start request.
  • Reset request.
  • Part available.
  • Fixture ready.
  • Station ready.
  • Recipe or operation selection.
  • Permission to enter a defined machine zone.

Signal ownership should be explicit. For each signal, the integration design should define who generates it, who consumes it, what it means, when it becomes active, and when it resets.

A signal called ROBOT_READY must have a documented meaning. It might indicate that the controller is enabled and not faulted, or it might mean that the robot is also in a particular program state and ready to accept a start request. These are different conditions.

Detailed sequencing, acknowledgements, timeouts, and recovery behaviour will be covered in the next topic, PLC handshake.

11. Safety-Related I/O

Safety-related signals must be treated differently from ordinary process I/O.

Examples may include signals associated with:

  • Emergency stops.
  • Guard doors.
  • Safety scanners.
  • Enabling devices.
  • Safety-rated monitored stops.
  • Safe speed or position functions.

The actual safety architecture depends on the installed controller, safety devices, risk assessment, and applicable standards.

Ordinary robot I/O or a normal PLC bit must not be assumed to provide a safety-rated function merely because it is named SAFE, E_STOP, or GUARD_OK.

Safety functions require the appropriate certified hardware, architecture, configuration, validation, and maintenance procedures. Never bypass a safety circuit to troubleshoot an ordinary sequence fault.

12. Troubleshooting Robot I/O

Symptom Possible causes Diagnostic approach
Input never turns ON Sensor failure, incorrect wiring, wrong polarity, missing supply, incorrect mapping Check sensor status, supply, wiring, module LED, and controller input state
Input remains ON Stuck sensor, short circuit, wrong logic polarity, incorrect input mapping Inspect physical state, wiring, and input configuration
Output command is ON but actuator does not move Output module fault, disconnected wire, missing power, valve fault, mechanical jam Compare program command, output LED, measured electrical state, and actuator response
Output will not turn ON Program condition false, output inhibited, controller state restriction, mapping issue Trace the program condition and inspect controller diagnostics
Robot sees incorrect sensor state PNP/NPN mismatch, noise, poor reference connection, wrong signal mapping Verify electrical compatibility and compare the physical input with the controller state
Intermittent I/O Loose terminals, vibration, poor connectors, network instability, electrical noise Check fault history, terminal condition, device diagnostics, and communication status
Analog reading is incorrect Scaling error, wrong range, wiring issue, sensor fault Compare raw input, configured range, and an independent measurement
PLC and robot disagree about a state Different signal definitions, stale network data, incorrect mapping, logic timing Compare both controller states and verify the documented signal ownership
Signal changes too quickly to detect Short pulse, input filtering, task timing, communication update delay Check pulse duration and receiver architecture; consider suitable event-capture or handshake logic
I/O module reports fault Module power loss, channel overload, fieldbus fault, configuration mismatch Review module diagnostics and network status before replacing components

13. Practical Maintenance Method

When an I/O fault occurs, trace the signal from the physical device to the program rather than immediately changing code.

  1. Identify the exact signal name and intended function.
  2. Confirm the actual state of the sensor or actuator.
  3. Check the electrical supply, wiring, polarity, and common connections.
  4. Inspect the I/O module status indicator and diagnostics.
  5. Verify the controller's physical or mapped I/O state.
  6. Check the logical mapping and address.
  7. Trace the program conditions that use or control the signal.
  8. For remote I/O, verify network and device health.
  9. Record the root cause, corrective action, and any configuration changes.
  10. Verify the complete operation under the approved commissioning and safety procedure.

Use approved electrical isolation and safe working procedures before touching wiring or equipment. Never disconnect or force signals without understanding their role in the machine sequence and safety architecture.

14. I/O Documentation and Backup

Maintain an I/O list for every robot cell or integrated machine.

A useful I/O list contains:

Field Purpose
Signal name Unique functional identification
Direction Robot input, robot output, or analog direction
Address Physical or logical mapping
Device Sensor, valve, PLC, drive, or other equipment
Electrical specification Voltage, current, signal type, and polarity
Normal state Expected state in the defined operating condition
Active condition Meaning of ON or the relevant analog range
Program usage Related routine or sequence
Diagnostic method How to verify the signal
Revision Controlled configuration reference

Back up relevant controller programs, I/O configuration, fieldbus mappings, and associated documentation according to the plant's change-control procedure.

A program backup without the corresponding I/O mapping may be insufficient to reconstruct the complete system after controller replacement.

15. Interview Questions and Answers

Q1. What is robot I/O?

Robot I/O is the mechanism through which a robot controller receives signals from external devices and sends commands or status signals to them.

Q2. What is the difference between digital and analog I/O?

Digital I/O represents discrete states, usually ON and OFF. Analog I/O represents a variable value within a configured range.

Q3. What is the difference between a command and feedback?

A command requests an action. Feedback indicates the reported condition or result. Commanding a gripper to close does not prove that it closed successfully.

Q4. What is the difference between local and remote I/O?

Local I/O uses hardware located at or near the controller. Remote I/O uses distributed hardware connected through an industrial communication network.

Q5. What is I/O mapping?

I/O mapping associates a logical signal used by the program with a physical channel or network data location.

Q6. Why might a PNP sensor fail to operate a robot input?

Possible causes include electrical incompatibility, incorrect wiring, missing supply, incorrect common connections, or incorrect input configuration.

Q7. Why is a signal name insufficient for troubleshooting?

A name describes the intended function but does not identify the actual electrical condition, terminal, mapping, polarity, or source of the fault.

Q8. What is the purpose of input filtering?

Filtering suppresses unwanted brief transitions or noise. Excessive filtering can delay valid state detection.

Q9. Can a normal digital input be used as an emergency-stop function?

Not unless it is part of an appropriately designed, rated, and validated safety architecture. An ordinary process signal is not automatically safety-rated.

Q10. What would you check if an output turns ON but the actuator does not move?

Check the program command, mapped output state, module diagnostics, electrical supply, wiring, output current capability, actuator or valve condition, and mechanical obstruction.

16. Practical Exercises

Exercise 1: Trace a digital input

Choose a non-safety sensor in an approved training environment.

  • Identify the sensor and its electrical output type.
  • Find the associated I/O channel.
  • Observe the physical sensor indicator.
  • Compare the module indicator with the controller's input state.
  • Confirm which program condition uses the input.

Exercise 2: Trace a digital output

Use a permitted test output or a training simulator.

  • Identify the output signal and its destination.
  • Trace the logical signal to its physical or network mapping.
  • Compare the program state with the module diagnostic state.
  • Confirm the receiving device's response.
  • Document any difference between the commanded and actual condition.

Exercise 3: Investigate an analog input

Use a simulator or approved signal source.

  • Verify the configured electrical range.
  • Inspect the raw value.
  • Apply a known test value.
  • Calculate the corresponding engineering value.
  • Compare the expected and displayed measurements.
  • Record any scaling or configuration mismatch.

Exercise 4: Build an I/O list

Create a signal list for a robot and gripper station. Include the part sensor, gripper commands, gripper feedback, robot ready status, start request, cycle-complete signal, and fault status.

For each signal, record its owner, direction, function, mapping, and diagnostic method.

17. Final Mental Model

  • Inputs tell the robot what external devices are reporting.
  • Outputs request actions or report controller states.
  • Analog I/O represents variable measurements or commands.
  • I/O mapping connects program signals to physical or networked channels.
  • Electrical compatibility determines whether signals can be transmitted and interpreted correctly.
  • Command and feedback must remain distinct.
  • Diagnostics should trace the signal from the physical device through the I/O hardware and mapping into program logic.
  • Safety-related signals require an appropriate safety-rated design and must not be treated as ordinary process bits.

Reliable robot integration depends on signals that are correctly wired, mapped, named, interpreted, and diagnosed.
