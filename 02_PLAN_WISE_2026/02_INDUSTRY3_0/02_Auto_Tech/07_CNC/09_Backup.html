09_Backup - Backup

1. Definition of CNC backup

A CNC backup is a controlled copy of a machine's programs, configuration, parameters, machine-specific data and other required information, stored so that the system can be restored after data loss, hardware replacement, controller failure or an incorrect configuration change.

A CNC machine's operation depends on more than its part programs. Its configuration may include axis parameters, servo settings, tool data, work offsets, PLC logic, machine-builder settings, communication configuration and safety-related configuration.

Losing the wrong set of data can leave a mechanically healthy machine unable to operate correctly.

Main objectives

  1. Recover from CNC controller or storage failure.
  2. Restore configuration after replacing hardware.
  3. Recover deleted or corrupted part programs.
  4. Preserve validated machine parameters and settings.
  5. Compare configuration before and after maintenance.
  6. Support root-cause analysis after unsuccessful changes.
  7. Reduce machine downtime and recovery uncertainty.
  8. Maintain traceability of approved configuration changes.

A backup is not merely a folder containing CNC programs. It is a recovery resource for the complete machine-control system.

2. What should be backed up?

The exact backup scope depends on the CNC controller, machine-tool builder and installed options.

Backup category Typical contents Why it matters
Part programs CNC machining programs, subprograms and cycles Recovers machining logic
CNC parameters Axis, spindle, machine and control configuration Restores controller behaviour
Machine data Machine-specific settings and configuration data Supports machine restoration
Tool data Tool geometry, wear values and tool management data Restores tool-related configuration
Work offsets G54-G59 and other supported coordinate offsets Restores workpiece coordinate settings
Compensation data Tool, pitch, backlash or other compensation data, as supported Preserves validated correction values
PLC program Machine sequence and interlock logic Restores machine-level control logic
PLC data Retentive data, recipes or machine-specific values where applicable Recovers necessary operating state
Drive configuration Servo and spindle drive parameters and supported backups Supports drive replacement and recovery
HMI data Screens, messages, recipes and interface configuration Restores operator-interface functionality
Network configuration Approved addresses, device configuration and topology records Supports communication recovery
OEM configuration Machine-builder-specific files and settings Preserves integration details
Safety configuration Approved safety-project files and verification records, where supported Supports authorized safety-system recovery
Documentation Electrical drawings, manuals, parameter lists and restoration procedures Enables correct recovery

Not every CNC supports every category through one backup command. Some data resides in separate controller areas, drives, PLCs, HMIs or external devices.

Important: A standard CNC archive must not be assumed to include PLC logic, drive parameters, safety configuration or all tool and offset data. Verify the actual contents.

3. CNC backup architecture

A useful backup strategy has several layers.

          |                       |
          v                       v
   Local protected copy     Maintenance server
                                  |
                                  v
                          Separate backup copy

The diagram represents logical backup ownership. The exact export methods and available data vary by machine.

Three useful backup layers

Layer 1: Machine-side recovery copy

A copy stored on approved local storage or an external medium. It can be useful when the original storage fails, but it may be lost if the machine or storage device is damaged.

Layer 2: Central maintenance repository

A controlled location containing backups organized by plant, line, machine, subsystem and date.

Layer 3: Independent recovery copy

A separate protected copy that remains available if the local machine or central repository is compromised or unavailable.

The copies should not all depend on the same physical storage device or the same failure-prone location.

4. Backup versus archive versus snapshot

These terms overlap in everyday maintenance, but their meanings are useful to distinguish.

Term Meaning Example
Backup A recoverable copy of data or configuration Exporting CNC parameters
Archive A packaged collection of files or data A controller-generated archive containing selected machine data
Snapshot A captured state at a specific point in time A documented configuration state before a drive replacement
Export Copying selected data out of a system Exporting part programs to an approved file
Restore Writing saved data back into a system Loading a valid parameter backup
Version control Tracking changes between revisions Comparing parameter files from two maintenance events
Disaster recovery The wider process of restoring service after a major failure Rebuilding the controller and restoring validated data

A snapshot is not necessarily an independent backup. If it depends on the same failed storage device, it may be useless during recovery.

Similarly, exporting part programs does not mean that the CNC machine's complete configuration has been backed up.

5. CNC parameters: Why backup is critical

CNC parameters influence how the controller interprets and executes machine operations.

Depending on the control, parameters and machine data can include:

  • Axis configuration.
  • Travel limits and monitoring.
  • Servo control configuration.
  • Encoder and feedback configuration.
  • Spindle control configuration.
  • Reference-return behaviour.
  • Machine coordinate relationships.
  • Compensation functions.
  • Communication settings.
  • Machine-specific control functions.
  • Option and machine-builder settings.

Changing these values without understanding their purpose can cause positioning errors, unexpected machine behaviour, loss of reference information or failure to operate.

Example: Incorrect axis configuration

A maintenance engineer changes an axis parameter while troubleshooting a positioning issue. The machine then behaves differently or fails to complete reference return.

If a verified pre-change backup exists, the engineer has a known reference for investigation and possible restoration.

However, restoring an old file is not automatically safe. The file must match the controller, machine, hardware configuration and intended restoration state.

Parameter backup rules

  1. Save the existing configuration before an approved parameter change.
  2. Record why the change is required.
  3. Identify the exact machine and controller.
  4. Record the date, responsible person and relevant software or firmware versions.
  5. Preserve the original copy as read-only where practical.
  6. Compare the post-change configuration with the approved baseline.
  7. Verify operation using the machine-builder's procedure.
  8. Document any change that remains in the final configuration.

Never use a parameter file from another machine simply because the model names look similar.

6. Part program backup

Part programs define machining operations and may include motion commands, tool calls, cycles, coordinate selections, spindle commands and auxiliary functions.

A useful program backup process preserves:

  • Main programs.
  • Subprograms.
  • Macro programs and variables where supported.
  • Program revisions.
  • Approved machining versions.
  • Required supporting files.
  • Program comments and naming conventions.
  • Relevant tool and work-offset dependencies.

Example: Program version control

CNC_PROGRAMS/
    MACHINE_01/
        PART_A/
            REV_001/
            REV_002/
            APPROVED_CURRENT/

This is an organizational example, not a universal file layout.

Use an approved revision identifier and change record. Avoid filenames such as FINAL, FINAL_NEW and FINAL_NEW_2, which are the natural result of letting file management evolve without supervision.

A backed-up program can still machine a part incorrectly if its required tool data, offsets, fixtures or machine configuration are missing.

7. PLC and machine-builder data backup

CNC machine operation often depends on a separate PLC program or integrated PLC functionality.

The PLC may control:

  • Tool changers.
  • Chuck and clamp sequences.
  • Coolant and lubrication.
  • Pallet changers.
  • Hydraulic and pneumatic mechanisms.
  • Machine interlocks.
  • Auxiliary axes.
  • Operator messages.
  • Communication handshakes with the CNC.

A complete recovery plan must identify how the PLC project and its relevant data are stored and restored.

PLC backup considerations

  • Obtain the correct source project where available.
  • Record the PLC hardware and firmware.
  • Record the programming software and version.
  • Preserve relevant hardware configuration.
  • Include required libraries and dependencies.
  • Capture retentive data when supported and permitted.
  • Record project passwords and access arrangements through approved secure procedures.
  • Confirm whether the available project matches the installed PLC.
  • Verify the restoration procedure with the machine builder or authorized engineering team.

An uploaded PLC program or controller image is not necessarily equivalent to a complete, editable engineering project.

Some systems permit program upload but do not contain the original comments, symbols, source structures or complete project metadata.

8. Servo and spindle drive backups

Servo and spindle drives may contain settings that affect motor control, feedback interpretation, limits and operating behaviour.

Depending on the drive, relevant data may include:

  • Motor identification and ratings.
  • Encoder configuration.
  • Control-loop settings.
  • Current and torque limits.
  • Speed limits.
  • Communication configuration.
  • Motor thermal protection settings.
  • Machine-specific tuning.
  • Drive firmware and option information.

Why this matters

Suppose a failed servo drive is replaced.

The replacement may have different factory defaults, firmware, hardware options or configuration. The CNC machine may not operate correctly until the approved drive configuration is restored and verified.

Drive replacement workflow

  1. Identify the exact failed drive and installed hardware.
  2. Preserve available diagnostic information.
  3. Locate the approved configuration for that machine and axis.
  4. Verify drive model, motor compatibility, feedback type and firmware requirements.
  5. Load configuration using the approved procedure.
  6. Complete required commissioning and verification.
  7. Verify reference return, motion, limits and machine functions as specified.
  8. Record the replacement and final configuration.

A drive backup must never be treated as permission to bypass commissioning or safety checks.

9. CNC backup methods and storage formats

Backup methods differ across controller families and machine generations.

Method Typical use Important limitation
USB export Programs and supported controller data Export scope may be limited
Ethernet transfer Programs and files over an approved network Depends on enabled services and configuration
Controller-generated archive Packaged machine data and configuration Only includes the data defined by that archive
OEM commissioning tool Controller, drive or machine-specific data May require licensed software and authorization
Engineering workstation PLC, HMI and drive projects Must retain compatible software and project dependencies
Image-based backup Supported storage devices or complete computer systems May require hardware-compatible restoration
Manual parameter report Records selected values for reference Does not automatically recreate the complete controller
Central repository Organized machine-wide backup management Requires access control and independent protection

Text files versus native archives

A parameter report in a spreadsheet or text file can help with comparison and troubleshooting.

However, a report is not necessarily loadable by the controller. A native archive may preserve structures or metadata that a manually created list cannot.

Use the controller's supported backup and restore method whenever possible, and retain readable records as supporting documentation.

10. Backup frequency and retention

There is no universal backup interval suitable for every CNC machine. Frequency should reflect the rate of change, production criticality, recovery time and consequences of data loss.

Events that should trigger a backup

  • Before an approved parameter change.
  • Before a CNC or PLC software update.
  • Before drive replacement or major repair.
  • After commissioning or reconfiguration.
  • After an approved change has been validated.
  • After a machine-builder-approved software modification.
  • Before controller or storage replacement.
  • At a defined periodic interval for important machine data.

Example maintenance policy

Event Suggested action
Commissioning completed Create and validate baseline backup
Before parameter modification Save current approved state
After validated change Create a new revision
Before controller replacement Confirm complete recovery package
Periodic maintenance review Verify backup completeness and accessibility
After recovery Create and document the restored final state

The actual interval should be set by plant policy and machine criticality.

Retention policy

Preserve at least:

  • The original validated baseline.
  • The current approved configuration.
  • Relevant prior approved revisions.
  • The backup associated with major component replacement.
  • The configuration used for a documented recovery.

Do not overwrite the only known-good copy with an unverified configuration.

A useful naming scheme contains:

  • Machine ID.
  • Controller or subsystem.
  • Data category.
  • Date.
  • Backup context or revision.

For safety-related files, access should be restricted according to the plant's policies.

12. Backup integrity and verification

A successful file export does not prove that the backup is complete, correct or restorable.

A robust process verifies the copy.

Verification checklist

  1. Confirm that the backup operation completed without errors.
  2. Confirm that the expected files or archive exist.
  3. Check file sizes and timestamps for plausibility.
  4. Review the archive or export contents when supported.
  5. Confirm the machine ID and subsystem match.
  6. Record the controller and software versions.
  7. Compare critical configuration against the approved baseline.
  8. Store the copy in its designated protected location.
  9. Confirm that authorized personnel can retrieve it.
  10. Perform a controlled restore test where supported and appropriate.

Checksums and file integrity

A checksum, such as a cryptographic hash, can help determine whether a file has changed between two points in time.

If the file's checksum matches the previously recorded value, the file contents are consistent with that recorded version.

However, a checksum does not prove that the original file was correct or that the controller can successfully restore it.

Restore testing

A restore test should use an approved test environment, spare hardware or a controlled procedure that does not put production equipment at unnecessary risk.

A complete restore test may involve checking that:

  • The correct data can be retrieved.
  • The archive can be opened or imported.
  • The target hardware and software are compatible.
  • Required dependencies are available.
  • The restored system passes the required functional checks.

Do not experiment with restoring unknown backups directly onto a production CNC machine.

13. CNC restore and recovery procedure

A restore writes saved data back to a controller, drive, PLC or other target system.

It is more consequential than simply copying files out of a machine.

Standard recovery sequence

Failure or data loss
        |
        v
Identify affected subsystem
        |
        v
Identify target hardware and version
        |
        v
Locate approved backup
        |
        v
Verify backup identity and integrity
        |
        v
Confirm compatibility and restore scope
        |
        v
Restore using approved procedure
        |
        v
Verify configuration and safety functions
        |
        v
Perform controlled functional testing
        |
        v
Document recovery and final state

Before restoring

Confirm:

  • Correct machine and controller.
  • Correct axis or drive where applicable.
  • Hardware and firmware compatibility.
  • Correct software and archive format.
  • Backup date and revision.
  • Required PLC, drive and safety configuration.
  • Any changes made since the backup.
  • Whether restoration overwrites current data.
  • Required authorization and machine isolation.

After restoring

Verify the functions specified by the OEM and plant procedure. These may include:

  • CNC startup and readiness.
  • PLC operation and machine interlocks.
  • Axis reference return.
  • Axis limits and movement.
  • Spindle operation.
  • Tool change and workholding.
  • Tool and work offsets.
  • Safety functions.
  • Communication links.
  • Approved trial operation and part inspection.

The exact tests depend on what was restored. Restoring a part program does not require the same validation as replacing a servo drive or restoring a safety project.

14. Recovery scenarios

Scenario A: CNC controller replacement

Problem: The CNC controller hardware has failed.

Potentially required recovery data:

  • CNC system and machine configuration.
  • CNC parameters and machine data.
  • Part programs.
  • PLC project and data where applicable.
  • Drive configuration.
  • Tool and work offsets.
  • OEM files and option information.
  • Required software and firmware records.

Critical point: A controller replacement may require OEM-specific commissioning, hardware compatibility checks and revalidation. Copying files alone may not restore the machine.

Scenario B: Accidental parameter change

Problem: An axis behaves incorrectly after an authorized or accidental configuration modification.

Actions:

  1. Record the current state and relevant alarms.
  2. Identify the changed parameter and change history.
  3. Compare with the approved baseline.
  4. Confirm that the baseline applies to the current machine configuration.
  5. Restore or correct the value using the approved process.
  6. Perform the required verification.

Avoid blindly loading the entire old parameter set when only one parameter has changed. Other valid configuration changes may have occurred since the baseline was created.

Scenario C: Servo drive replacement

Problem: A servo drive fails and is replaced.

Actions:

  1. Identify the original drive, motor and axis.
  2. Retrieve the correct approved drive configuration.
  3. Verify compatibility.
  4. Load and commission the drive according to the manufacturer's instructions.
  5. Verify feedback, direction, reference return, limits and motion.
  6. Document the new hardware and configuration.

Scenario D: Part program deletion

Problem: A validated machining program is deleted.

Actions:

  1. Retrieve the approved program revision.
  2. Confirm machine and part identity.
  3. Check the required subprograms and dependencies.
  4. Confirm the correct tool and work-offset setup.
  5. Verify the program using the plant's approved procedure before production.

A correct program on the wrong machine or with the wrong offsets is still a recipe for scrap.

Scenario E: PLC project unavailable

Problem: The installed machine's PLC project is missing from the engineering workstation.

Actions:

  1. Identify the installed PLC and firmware.
  2. Search the controlled project repository.
  3. Check whether the available source matches the installed machine.
  4. Verify required libraries, hardware configuration and dependencies.
  5. Preserve the existing controller state before any authorized transfer.
  6. Restore only through the approved engineering procedure.
  7. Verify all machine sequences and safety-related functions as required.

An online PLC upload may not reconstruct the complete original engineering project. Verify what information is actually available.

15. Controller-family considerations

Backup procedures depend on the CNC platform and machine builder.

Controller family Typical backup considerations
FANUC CNC parameters, programs, offsets, PMC-related data and system-specific files, as supported
Siemens SINUMERIK CNC data, machine data, part programs, PLC data and system archives, depending on generation and configuration
Mitsubishi CNC Programs, parameters, PLC data and controller-specific backup functions
Older CNC generations May rely on specific transfer tools, serial connections or legacy media
PC-based CNC systems May require controller archives, project files, supported disk images and software-version records

The available functions differ across model, generation, installed options, permissions and OEM integration.

For example, the restore process for a SINUMERIK 840D should not be assumed to match that of a SINUMERIK 828D. Even within one product family, the supported archive scope and commissioning process can differ.

Use the exact controller manual and machine-builder procedure. Do not rely on a generic key sequence or an assumed parameter number.

16. Backup security and configuration control

CNC backups contain operational information that can affect machine performance and safety.

Protect them against:

  • Unauthorized changes.
  • Accidental deletion.
  • Malware and ransomware.
  • Uncontrolled copying.
  • Incorrect restoration.
  • Loss of access credentials.
  • Confusion between approved and experimental versions.

Recommended controls

  • Use access-controlled repositories.
  • Separate approved backups from working copies.
  • Restrict write access to authorized personnel.
  • Keep an independent protected copy.
  • Record who created or approved each revision.
  • Preserve the original baseline.
  • Maintain version and restoration history.
  • Store passwords and credentials using approved secure methods.
  • Scan transfer media according to plant cybersecurity procedures.
  • Use approved software and communication methods.

A backup repository should not be a shared folder where everyone can overwrite the machine's known-good configuration. That is collaboration in the same sense that a loose bolt is a fastening strategy.

17. Backup versus maintenance records

A backup and a maintenance report solve different problems.

Backup Maintenance record
Preserves recoverable data Records what happened
May restore configuration Explains the fault and corrective action
Contains files or structured data Contains observations, decisions and verification
Supports recovery Supports traceability and root-cause analysis

Both are necessary for reliable recovery.

For example, a parameter backup might show the approved configuration, while the maintenance record explains why a particular setting was changed and what tests validated it.

18. Measuring backup effectiveness

Backup quality should be assessed by recoverability, not merely by the number of files stored.

Useful measures include:

  • Backup completion rate.
  • Percentage of critical CNC machines with current approved backups.
  • Percentage of backups with verified contents.
  • Successful restore-test rate.
  • Time required to locate the correct backup.
  • Time required to restore service.
  • Number of failures caused by missing or incorrect configuration.
  • Number of configuration changes without a recorded backup.
  • Recovery time after controller or drive replacement.

RPO and RTO

Two useful disaster-recovery terms are:

Recovery Point Objective (RPO): The maximum acceptable amount of data loss, expressed as a time interval.

Recovery Time Objective (RTO): The target time within which the affected system or service should be restored.

Example:

  • RPO = 24 hours: the organization aims to limit data loss to no more than one day's worth of changes.
  • RTO = 4 hours: the organization targets restoring the service within four hours.

These are example targets, not universal CNC requirements. Production-critical machines may need different targets.

19. Practical backup checklist

Before declaring a CNC machine's backup complete, confirm the applicable items below.

  • Machine ID and CNC model recorded.
  • CNC programs exported.
  • CNC parameters and machine data saved.
  • Tool and work offsets included where supported.
  • PLC source project and relevant data preserved.
  • Servo and spindle drive configurations preserved.
  • HMI and network configuration recorded where required.
  • Safety-related configuration handled through the approved process.
  • OEM manuals, drawings and software versions recorded.
  • Backup files or archives checked for completeness.
  • Approved baseline retained separately.
  • Central and independent copies stored.
  • Access permissions and revision history controlled.
  • Restore method documented.
  • Restore verification completed where appropriate.
  • Backup date and responsible person recorded.

Some items may be stored in separate engineering systems. The important requirement is that the recovery plan identifies them and confirms their availability.

20. Interview questions and answers

Q1. What is a CNC backup?

A recoverable copy of CNC programs, parameters, machine data and other required configuration used to restore the machine after data loss or hardware failure.

Q2. Why is backing up only part programs insufficient?

Because the machine may also require controller parameters, PLC logic, drive configuration, offsets and OEM-specific data.

Q3. What is the difference between backup and restore?

Backup copies data to a recovery location. Restore writes saved data back to the target system.

Q4. Why should a backup be created before a parameter change?

It preserves the prior configuration as a reference for investigation and approved recovery.

Q5. What is a known-good backup?

A backup associated with a verified, approved machine configuration.

Q6. Why should backups be version-controlled?

To identify the correct revision, track changes and avoid restoring obsolete or unapproved data.

Q7. Does a successful export guarantee a successful restore?

No. The backup may be incomplete, incompatible, corrupted or dependent on missing software and hardware.

Q8. What is the purpose of a checksum?

It helps detect changes to file contents by comparing a calculated value with a previously recorded value.

Q9. What is the difference between RPO and RTO?

RPO concerns acceptable data loss. RTO concerns the target time to restore service.

Q10. Why must drive configuration be backed up separately in some systems?

Drive settings may reside in the drive or a separate engineering tool and may not be included in the CNC controller's standard archive.

Q11. What is the risk of restoring parameters from another machine?

The machines may differ in hardware, axis configuration, feedback, options or OEM settings, causing incorrect operation or damage.

Q12. Why should a baseline backup be preserved?

It provides a stable reference for configuration comparison and recovery.

Q13. What should be checked before restoring a backup?

Machine identity, controller and firmware compatibility, backup integrity, restoration scope, current configuration and authorization.

Q14. Why is PLC source-project preservation important?

It supports future maintenance, modification and recovery. A controller upload may not contain the complete original source project.

Q15. What should be done after restoring a CNC configuration?

Perform the required startup, configuration, safety and functional checks before releasing the machine for production.

Q16. Why keep an independent backup copy?

It reduces the risk of losing all recovery data when the machine-side or central storage fails.

Q17. Is a backup of safety-related configuration sufficient to prove that the safety system is safe?

No. The restored configuration must undergo the required verification and validation procedures.

Q18. How can backup effectiveness be measured?

By checking completeness, integrity, successful restore tests, retrieval time and actual recovery performance.

Q19. Why retain maintenance records alongside backups?

They explain the reasons for configuration changes and provide evidence of the validation performed.

Q20. What is the most important principle of CNC backup management?

Maintain a verified, compatible and retrievable recovery package, then prove that the approved restoration procedure works.

21. Practical exercises

Exercise 1: Build a backup inventory

Choose a CNC machine and create an inventory of all required recovery items.

Include controller data, programs, PLC project, drives, offsets, HMI, OEM files, safety configuration and documentation as applicable.

For each item, record its storage location, file format, software requirement, owner and last verification date.

Exercise 2: Plan for controller replacement

Assume the CNC controller fails and must be replaced.

Prepare a recovery plan containing:

  • Required backup categories.
  • Hardware and software compatibility checks.
  • Restoration order.
  • OEM support requirements.
  • Functional verification.
  • Safety validation.
  • Production-release criteria.

Exercise 3: Compare two parameter backups

Given an approved baseline and a newer parameter export, identify:

  • Changed values.
  • Missing parameters.
  • Differences in file format or scope.
  • Potentially intentional changes.
  • Changes requiring investigation or authorization.

Do not assume every difference is a fault. Establish the reason for each meaningful change.

Exercise 4: Create a backup register

Build a register with these fields:

Field Purpose
Machine ID Identifies the equipment
CNC model Identifies the controller family
Subsystem CNC, PLC, drive, HMI or other
Backup revision Identifies the saved version
Backup date Establishes the recovery point
Change reference Links the backup to maintenance work
Storage location Enables retrieval
Integrity status Records verification
Restore-test status Records recovery evidence
Approval status Identifies the authorized baseline
Responsible person Provides accountability

Exercise 5: Define a recovery test

Design a safe test that proves the backup can be retrieved, opened and restored in an appropriate test environment or through an approved controlled process.

Define the expected results before testing, including compatibility, data integrity and functional verification.

Exercise 6: Develop a machine backup standard

Create a standard operating procedure defining:

  • When a backup is required.
  • Which data must be included.
  • How the backup is named.
  • Where it is stored.
  • Who can approve or modify it.
  • How integrity is checked.
  • How recovery is performed.
  • What must be validated after restoration.
  • How the final configuration is documented.

22. Final mental model

A reliable CNC backup system follows this sequence:

Identify machine and subsystems
             |
             v
Determine required recovery data
             |
             v
Capture approved configuration
             |
             v
Verify contents and integrity
             |
             v
Store controlled independent copies
             |
             v
Track revisions and changes
             |
             v
Test the approved recovery method
             |
             v
Restore and validate when required

Remember these principles:

  • Part programs alone do not constitute a complete machine backup.
  • Controller, PLC, drive and safety data may require separate procedures.
  • A backup must match the target machine and its hardware/software configuration.
  • Never overwrite the only verified baseline with an untested revision.
  • A successful file copy does not prove that the data can be restored.
  • Recovery must include the appropriate functional and safety verification.
  • Backup quality is measured by recoverability, not file count.

The purpose of backup is to turn a future failure from an improvised engineering emergency into a controlled recovery process.
