Topic: VFD Diagnostics

1. Definition

VFD diagnostics is the systematic process of identifying, investigating, and confirming faults or abnormal operating conditions in a variable-frequency drive system.

Diagnostics uses fault codes, operating measurements, parameter values, event history, status indicators, and physical inspection to determine why a drive or its connected equipment is not operating correctly.

The purpose is not merely to reset the drive. It is to identify the root cause, restore reliable operation, and prevent recurrence.

For example, if a conveyor VFD trips on overcurrent, the fault code identifies the detected condition. Further investigation may reveal a jammed conveyor, an aggressive acceleration ramp, a motor-cable short circuit, or an incorrect drive configuration.

These causes require different corrective actions. Replacing the VFD immediately would be an expensive way to avoid thinking.

Diagnostics covers the complete application, not just the drive's electronics. A VFD can report a genuine fault caused by a mechanical problem, an upstream supply issue, a motor defect, a control command, or an incorrect parameter.

3. Main categories of VFD diagnostics

Diagnostic category What it identifies Examples
Fault diagnostics A detected condition that causes or may cause a trip Overcurrent, earth fault, undervoltage
Warning diagnostics A condition that needs attention but may not stop operation High temperature, maintenance warning
Status diagnostics Current operating state Ready, running, stopped, faulted
Electrical diagnostics Electrical measurements and supply conditions Output current, DC-bus voltage, input phase loss
Thermal diagnostics Temperature and thermal loading Heat-sink temperature, motor thermal load
Control diagnostics Command and reference problems Missing run command, wrong speed reference
Communication diagnostics Network and control-connection problems Fieldbus timeout, PLC communication loss
Historical diagnostics Previous events and fault sequences Fault log, event history, trip frequency
Parameter diagnostics Configuration errors or mismatches Wrong motor current, control-source mismatch

Different manufacturers use different menu names and fault classifications. Always interpret the code using the documentation for the exact drive model and firmware.

4. Essential diagnostic parameters

A technician should know which live values help explain the machine's behavior.

Parameter What it tells you Diagnostic use
Output current Current delivered by the drive Load changes, overload and current-limit investigation
Output frequency Frequency commanded or produced by the drive Speed-reference and operating-point checks
Actual motor speed Estimated or measured speed, where available Determine whether the motor follows the command
Speed reference Requested speed Check PLC/HMI reference and scaling
Torque estimate Estimated motor torque, where supported Identify high mechanical demand
DC-bus voltage Voltage on the drive's DC link Investigate undervoltage, overvoltage and regenerative conditions
Heat-sink temperature Internal drive temperature Investigate cooling and thermal trips
Motor thermal load Estimated thermal utilization, where supported Assess accumulated motor heating
Drive operating state Ready, running, stopping, faulted, etc. Understand why the drive is not running
Run command status Whether a valid run request is present Separate command problems from power-stage faults
Current-limit status Whether the drive is limiting current Investigate acceleration and excessive torque demand
Fault code and subcode Specific detected failure or condition Direct the investigation
Last fault frequency/current Operating values captured at the fault, if supported Reconstruct the failure conditions

Important: A requested frequency and actual output frequency may not be the same. Likewise, estimated motor speed may differ from actual speed. Check what the particular parameter represents before drawing conclusions.

5. Fault code versus root cause

A fault code tells you what condition the drive detected. It does not always tell you why that condition occurred.

Fault indication Possible underlying causes
Overcurrent Mechanical jam, excessive acceleration demand, short circuit or incorrect configuration
Overvoltage Rapid deceleration, regenerative energy or supply abnormality
Undervoltage Supply dip, phase loss or DC-bus power problem
Overtemperature Blocked cooling, failed fan, high ambient temperature or excessive loading
Earth fault Motor/cable insulation fault or other unintended path to earth
Overload Excessive sustained torque demand, poor cooling, incorrect motor data or undersized drive
Communication fault Network interruption, configuration mismatch, missing controller or timeout
External fault An assigned digital input or external protective circuit reports a fault
Motor stall or speed deviation Excessive load, insufficient torque, incorrect settings or feedback problems

A fault code should initiate a structured investigation, not trigger an automatic parts-replacement decision.

6. Diagnostic workflow: From symptom to confirmed cause

Step 1: Confirm the reported symptom

Clarify what actually happened:

  • Does the drive fail to start?
  • Does it trip immediately after the RUN command?
  • Does it trip during acceleration?
  • Does it run for a period and then trip?
  • Does the motor run but fail to reach the expected speed?
  • Does the PLC report a fault while the VFD itself appears healthy?

These scenarios point toward different diagnostic paths.

Step 2: Record the exact fault

Capture:

  • Fault code and displayed text.
  • Subcode, if available.
  • Time and operating conditions.
  • Drive status before the trip.
  • Output current, frequency and thermal values, if recorded.
  • PLC/HMI alarm messages.
  • Recent maintenance or parameter changes.

Take a photograph or save the diagnostic record before resetting the drive.

Step 3: Check the event history

If the drive supports fault and event logs, examine the sequence rather than looking only at the last event.

For example:

14:22:10  Speed reference increased
14:22:11  Output current increased
14:22:12  Current limit became active
14:22:13  Overcurrent trip

This hypothetical sequence suggests investigating the acceleration demand, load and current-limit behavior. It does not, by itself, rule out an electrical fault.

Check whether the drive stores operating values at the instant of the trip. Some models retain only the code and timestamp.

Step 4: Inspect the control command

Confirm:

  • Is the drive in Local or Remote mode?
  • Is the selected command source correct?
  • Is the RUN command actually present?
  • Is the speed reference valid?
  • Is an interlock or permissive preventing operation?
  • Is an external fault input active?
  • Is the PLC waiting for a drive-ready or running signal?

If the drive is healthy but receives no valid RUN command, replacing the power module is unlikely to improve the situation.

Step 5: Examine live electrical and operating values

Compare the values with normal operation and manufacturer specifications.

For example:

  • Rising current may indicate increasing load or friction.
  • A speed reference of 50 Hz with an actual output frequency of 0 Hz may indicate that the drive is not enabled, has an active inhibit, or has not accepted the command.
  • A rising heat-sink temperature may indicate a cooling or loading problem.
  • DC-bus voltage changing during deceleration may help explain an overvoltage trip.

These are investigation clues, not universal one-to-one diagnoses.

Step 6: Inspect the physical system

When electrical isolation and machine-safety procedures permit, inspect:

  • Motor and power cables.
  • Motor terminal box.
  • Protective-earth connections.
  • Cooling fans and filters.
  • Mechanical load and couplings.
  • Supply connections and approved supply measurements.
  • Control wiring, connectors and network cabling.

Do not inspect or probe energized drive internals unless the work is specifically authorized and performed by qualified personnel under the applicable electrical-safety procedure.

Step 7: Confirm the root cause

A root cause should be supported by evidence.

For example:

  • Observation: Output current increased before each trip.
  • Inspection: Conveyor bearing was seized.
  • Corrective action: Bearing replaced.
  • Verification: Conveyor operated under representative load without recurring overload.

This is stronger evidence than recording “VFD faulty” simply because the VFD displayed the alarm.

Step 8: Verify the repair

After correction:

  1. Restore covers, guards and connections.
  2. Confirm that the parameter configuration is correct.
  3. Clear the fault according to the approved procedure.
  4. Test the machine through the relevant operating sequence.
  5. Compare current, speed and temperature behavior with the expected values.
  6. Review the fault history to confirm that the original failure does not recur.

7. Local diagnostics versus PLC/HMI diagnostics

A drive may be healthy internally but unavailable to the machine because of a control or communication problem.

Check VFD keypad/display PLC/HMI
Fault code Usually provides the drive's local fault indication May display a mapped fault number or message
Operating state Shows the drive's internal state Shows the state received or interpreted by the controller
RUN command May show the accepted command or control source Shows the command being issued by the PLC
Speed reference Shows the drive's reference parameter Shows the commanded value and any PLC-side scaling
Communication May display a communication fault Shows timeout, connection or data-quality status if programmed
Parameter configuration Shows the drive's stored values May show configured values or values written by the PLC
Fault history Often includes the drive's event history May have a separate machine alarm history

The two views should be compared. A PLC command bit being ON does not necessarily mean the drive has accepted the command, and an HMI alarm does not always originate inside the VFD.

8. Communication diagnostics

In automated manufacturing, the PLC may command a VFD over a fieldbus or industrial Ethernet network.

Typical problems include:

  • Incorrect IP address or node address.
  • Incorrect communication configuration.
  • Loose or damaged network cable.
  • Switch or port failure.
  • Controller-to-drive connection timeout.
  • Incorrect telegram, assembly or data mapping.
  • PLC program using the wrong status bit.
  • A drive in Local mode while the PLC expects Remote control.

A useful diagnostic sequence is:

  1. Confirm the VFD itself is powered and ready.
  2. Check the drive's communication status and fault log.
  3. Check the PLC connection status and communication diagnostics.
  4. Verify addressing, configuration and data mapping.
  5. Compare the command and feedback values at both ends.
  6. Check physical network connections and topology under the site's approved procedure.

Do not assume a communication fault means the motor power circuit is defective.

9. Parameter and configuration diagnostics

A VFD's parameters determine how it interprets commands, controls the motor and applies protection.

Important settings include:

  • Motor nameplate data.
  • Control mode.
  • Start/stop command source.
  • Speed-reference source.
  • Minimum and maximum frequency.
  • Acceleration and deceleration times.
  • Current and torque limits.
  • Motor overload protection.
  • Switching frequency.
  • Communication configuration.
  • Digital input assignments.
  • Fault reset behavior.

When a fault begins after a parameter change, compare the current configuration with the approved baseline or last known-good backup.

Do not reset all parameters to factory defaults as a first troubleshooting step. Doing so may erase the configuration required for safe machine operation.

10. Diagnostic examples from automotive production

Example A: Conveyor drive will not start

Observation: The HMI indicates that the conveyor has received a start command, but the motor does not rotate.

Diagnostic sequence:

  1. Check the drive's displayed status and active faults.
  2. Verify Local/Remote selection and the configured command source.
  3. Confirm that the drive has actually received a RUN command.
  4. Check interlocks, safety conditions and permissives through the approved control-system diagnostics.
  5. Check the speed reference and any active inhibit.
  6. Investigate the output stage only if the evidence supports an electrical or drive fault.

Lesson: A valid operator request is not the same as an accepted drive command.

Example B: Drive trips during acceleration

Observation: The motor starts, accelerates briefly and trips on overcurrent.

Diagnostic sequence:

  1. Capture the fault code and event sequence.
  2. Review current, frequency and current-limit status.
  3. Inspect the load for obstruction or excessive friction.
  4. Verify motor parameters and drive sizing.
  5. Check acceleration settings and the application's inertia requirements.
  6. Investigate the motor cable and power stage if electrical evidence points that way.

Lesson: Use the values immediately before the trip to narrow the investigation.

Example C: PLC reports a VFD fault, but the drive is ready

Observation: The VFD keypad shows Ready, while the PLC/HMI indicates a drive fault.

Possible causes:

  • Incorrect PLC status-bit mapping.
  • Stale communication data.
  • Incorrect fault-word interpretation.
  • Wrong drive address or tag mapping.
  • PLC alarm logic that does not match the drive's actual status.

Investigation: Compare the actual drive status, communication data, PLC tags and HMI alarm logic.

Lesson: Verify the complete signal path before replacing hardware.

Example D: Repeated thermal trips

Observation: A drive operates normally after a reset but trips again after several cycles.

Possible causes:

  • Progressive thermal accumulation.
  • Blocked cooling.
  • Excessive repeated acceleration.
  • Increasing mechanical friction.
  • Incorrect duty or drive sizing.

Investigation: Correlate trip timing with thermal load, current, machine cycle and ambient conditions.

Lesson: A reset clears the trip condition from the drive's active state; it does not necessarily remove the underlying cause.

11. Fault logs and maintenance records

A useful diagnostic record should contain enough information for the next technician to continue the investigation without repeating every test.

Field Information to record
Machine/station Machine ID and location
Drive identification Manufacturer, model, rating and firmware where relevant
Fault Exact code, text and subcode
Date/time When the fault occurred
Operating condition Startup, acceleration, steady running, deceleration or stop
Electrical data Current, DC-bus voltage and other relevant captured values
Control data Command source, run request and speed reference
History Previous faults and sequence
Inspection Physical and configuration findings
Root cause Confirmed cause supported by evidence
Corrective action Repair or parameter change
Verification Test performed and result

For recurring faults, trends can be more useful than isolated snapshots. A gradually increasing current trend, for instance, may reveal a developing mechanical problem before the drive finally trips.

12. Preventive diagnostic practices

  • Record and review recurring fault codes.
  • Preserve approved drive parameter backups.
  • Compare actual configurations with known-good settings after repairs.
  • Trend relevant current, thermal and speed data where available.
  • Inspect drive cooling and cabinet conditions.
  • Verify motor and drive nameplate/configuration compatibility.
  • Maintain clear PLC/HMI fault descriptions and status-bit mappings.
  • Record root causes and corrective actions in maintenance history.
  • Confirm faults are genuinely resolved before returning equipment to production.

A useful maintenance objective is to move from reactive resets toward early detection and evidence-based fault analysis.

13. Interview questions and answers

Q1. What is VFD diagnostics?

The systematic use of fault codes, status information, measurements, event history and inspection to identify the cause of abnormal drive or motor operation.

Q2. What is the difference between a fault code and a root cause?

A fault code identifies a condition detected by the drive. The root cause is the underlying problem that produced that condition.

Q3. Why should fault history be recorded before resetting the drive?

Resetting may clear active indications, and some diagnostic information may be lost or become harder to retrieve. Recording the fault preserves evidence about the failure.

Q4. What parameters would you check for an overcurrent trip?

Output current, output frequency, current-limit status, torque estimate where available, acceleration time, motor parameters and fault history.

Q5. How would you diagnose a drive that does not start?

Check the active fault, operating state, control source, RUN command, speed reference, permissives, interlocks and communication status before investigating the power stage.

Q6. How do you distinguish a VFD fault from a PLC communication problem?

Compare the drive's local status and fault history with the PLC connection status, received data, commands and feedback. Establish where the discrepancy begins.

Q7. Why is restoring factory defaults a poor first troubleshooting step?

It may erase motor data, control assignments, limits, communication settings and other machine-specific configuration.

Q8. Why are trends useful in diagnostics?

Trends reveal gradual changes and the sequence leading to a fault, helping distinguish an isolated event from a developing mechanical, thermal or electrical problem.

Q9. What should be included in a good fault report?

The exact fault, operating condition, relevant measurements, history, inspection findings, confirmed root cause, corrective action and verification results.

Q10. When should the VFD itself be suspected?

When evidence from the supply, motor, cable, load, control commands, parameters and cooling has been checked and the remaining findings support a drive-internal problem.

14. Practice exercises

Exercise 1: Overcurrent after a speed command

A conveyor receives a speed command, accelerates, and trips on overcurrent.

Determine:

  • Which values should be captured before resetting?
  • Which mechanical and electrical causes should be investigated?
  • How would you establish that the repair corrected the actual cause?

Exercise 2: Ready at the VFD, fault at the HMI

The local VFD display indicates Ready, but the PLC/HMI reports a drive fault.

Determine:

  • Which signals should be compared?
  • How would stale communication data be identified?
  • How would you verify the PLC's fault-word and status-bit mapping?

Exercise 3: Repeated trips after resetting

A drive trips on overtemperature after several production cycles but runs again after cooling.

Determine:

  • Which temperature and thermal-load trends should be reviewed?
  • Which cooling and loading conditions should be inspected?
  • What evidence would distinguish a cooling problem from excessive duty?

Exercise 4: Build a diagnostic sequence

Create a short investigation record for a real or simulated VFD fault. Include the exact code, machine condition, measurements, likely causes, tests performed, confirmed root cause, repair and verification.

The aim is to produce a record that another technician can use without relying on assumptions or undocumented knowledge.

15. Final mental model

  • Fault code: What the drive detected.
  • Live values: What the drive was doing.
  • Fault history: What happened before the trip.
  • PLC/HMI diagnostics: What the control system commanded and received.
  • Physical inspection: What is actually happening in the equipment.
  • Root-cause analysis: Why the failure occurred.
  • Verification: Evidence that the corrective action worked.

The core principle is simple: capture evidence, isolate the problem, confirm the cause, repair it, and verify the result.
