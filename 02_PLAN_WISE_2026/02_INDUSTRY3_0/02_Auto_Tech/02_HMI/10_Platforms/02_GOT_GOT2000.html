1. Definition

GOT stands for Graphic Operation Terminal. It is Mitsubishi Electric's operator-interface product family used to monitor, operate, and diagnose industrial machines and automation systems.

The GOT2000 series is a family of Mitsubishi operator terminals designed to communicate with compatible PLCs and other supported automation devices.

A GOT2000 HMI can provide:

  • Machine status and operating modes.
  • Manual and automatic operation screens.
  • Alarm messages and alarm history.
  • Process values and trends.
  • Recipe and parameter entry.
  • Maintenance and diagnostic screens.
  • Operator login and access restrictions.
  • PLC data monitoring and controlled writing of values.

For example, a GOT2000 installed at an automotive robotic station might display robot-ready status, clamp feedback, cycle status, fault messages, and selected process parameters.

The HMI is the operator's interface to the machine. It does not replace the PLC's control logic or the machine's safety system.

2. GOT and GOT2000 Terminology

Term Meaning
GOT Graphic Operation Terminal, Mitsubishi's operator-terminal product family
GOT2000 A generation of Mitsubishi GOT HMIs
HMI Human-Machine Interface, the general category of operator interface
PLC Programmable Logic Controller, which executes the control program
GT Designer3 Mitsubishi engineering software used to create and configure supported GOT projects
GT Works3 Mitsubishi engineering software suite that includes GT Designer3
GOT runtime The operating environment that executes the HMI project on the terminal
Device/PLC connection The configured communication path between the GOT and the controller

Important distinction: GOT2000 is the HMI hardware family, while GT Designer3 is engineering software. They are related, but they are not interchangeable terms.

The exact GOT2000 features, communication interfaces, and supported project functions depend on the specific terminal model and its firmware.

4. Main GOT2000 Hardware Considerations

Before troubleshooting or replacing a GOT, identify its exact model and hardware configuration.

Check the following:

  • Model number: Establishes the terminal type and supported capabilities.
  • Display size and resolution: Affects the layout and usability of the project.
  • Touchscreen: Used for operator interaction.
  • Ethernet interface: Used for supported network communication.
  • Serial interfaces: Available only where supported by the particular model.
  • USB interfaces: May support specified engineering, storage, or peripheral functions.
  • Power supply: Confirm the model's specified supply voltage and wiring requirements.
  • Mounting and environmental ratings: Important for panel replacement in industrial conditions.
  • Firmware and project compatibility: Confirm that the intended project can run on the target terminal.

A replacement terminal with a similar screen size is not automatically compatible. Hardware interfaces, firmware, project settings, and licensing or feature limitations may differ.

5. GOT2000 and Mitsubishi PLC Communication

A GOT2000 commonly exchanges data with Mitsubishi PLCs using supported Mitsubishi communication methods.

Depending on the model and configuration, this may include Ethernet-based communication and Mitsubishi-specific protocols such as SLMP, as well as supported serial connections.

The PLC provides the process data, and the GOT uses configured device references or tags to display and interact with it.

Mitsubishi device examples

Device General purpose
X Input device
Y Output device
M Internal relay
D Data register

C Counter device

These are common Mitsubishi PLC device designations. Their exact addressing, availability, and behavior depend on the PLC family and configuration.

Example references:

M100   Machine ready status

M102   Automatic mode status
D100   Actual process value
D110   Selected recipe number

These are illustrative addresses, not universal GOT2000 defaults.

Example of data flow

Suppose a Mitsubishi PLC uses M100 to indicate that a station is ready.

PLC M100
   |
   v

   |
   v

   |

If the indicator does not change, verify the PLC device value first, then the GOT's device reference, communication status, and object configuration.

A screen object can be configured correctly while the PLC device reference is wrong. Industrial systems enjoy this sort of distinction far more than anyone needs.

6. GOT2000 Screens and Operator Interface

A GOT2000 project typically contains several screens designed for different operator and maintenance tasks.

Screen design principles

A useful GOT2000 interface should make the machine's condition understandable without forcing the operator to inspect every screen.

Use consistent terminology, clear labels, sensible navigation, and unambiguous status indicators.

For example, a robot station overview might show:

STATION: FR1010

Operating mode:     AUTOMATIC
PLC communication:  HEALTHY
Robot ready:        YES
Clamp closed:       YES
Cycle active:       NO
Station fault:      NO

Active alarm:
NONE

The values above are illustrative. Actual status information must come from correctly configured PLC devices or other supported data sources.

Do not use color as the only indication of a condition. Combine colors with readable text, symbols, or other clear visual cues.

7. GOT Device References and Data Types

The HMI must know which PLC data to read or write.

Depending on the project and supported configuration, GOT projects may use direct device references, labels, or other configured data references.

7.1 Boolean status

Example: M100

Used for a binary condition such as:

  • Robot ready.
  • Clamp closed.
  • Station fault.
  • Automatic mode active.

A lamp or status object can reflect the value of the configured device.

7.2 Numeric data

Example: D100

Used for values such as:

  • Temperature.
  • Pressure.
  • Position.
  • Cycle count.
  • Recipe number.

Numeric values must be interpreted correctly. A PLC register might hold a raw integer rather than a value in engineering units.

For example, if D100 = 235 represents temperature scaled by a factor of 10, the displayed temperature should be 23.5 °C, assuming that scaling is how the PLC program defines the value.

The HMI must not invent the scaling factor. Verify it against the PLC program and process specification.

7.3 Command and feedback separation

A fundamental design principle is to distinguish between an operator's command and the equipment's actual state.

Example Meaning
M200 Illustrative clamp-close command
M201 Illustrative clamp-open command
X10 Illustrative clamp-closed sensor input
X11 Illustrative clamp-open sensor input

The GOT might display a close command as active, but the clamp is not confirmed closed until the appropriate feedback is received.

Operator presses CLOSE
          |
          v
Authorized command request
          |
          v
PLC checks operating conditions
          |
          v
PLC executes permitted sequence
          |
          v
Clamp moves
          |
          v
Closed sensor feedback
          |
          v
GOT indicates CLOSED

Actual commands and feedback must be mapped to the real PLC logic. A button press is not proof that an actuator moved.

8. Alarms and Alarm History

GOT2000 projects can display configured alarms and, depending on the model and project configuration, provide alarm history and related functions.

Typical alarm categories include:

  • Equipment faults.
  • Actuator timeout.
  • Missing sensor feedback.
  • Drive fault.
  • Process limit exceeded.
  • PLC communication failure.
  • Machine not ready.
  • Maintenance notification.

Example: clamp closing timeout

Suppose the PLC issues a clamp-close command but does not receive closed-position feedback within the configured timeout.

The HMI might display:

ALARM: CLAMP CLOSE TIMEOUT

Close command:       ON
Closed feedback:     OFF
Timeout:             EXPIRED
PLC communication:   HEALTHY

The PLC should detect and manage the machine condition. The GOT presents the alarm and associated diagnostic information to the operator.

Alarm acknowledgement versus fault reset

These are different operations.

  • Acknowledgement: Confirms that the operator has recognized the alarm.
  • Fault reset: Requests or initiates a defined recovery action, subject to the machine's logic and conditions.
  • Fault clearance: The underlying abnormal condition is no longer present.

Acknowledging an alarm does not necessarily remove the fault. Resetting a fault should not bypass the original cause or the machine's required permissives.

9. Trends, Recipes, and Data Logging

9.1 Trends

Trend displays help operators and maintenance engineers understand how process values change over time.

Examples include:

  • Temperature during a production cycle.
  • Pressure during clamping.
  • Cycle time over successive cycles.
  • Actual value versus target value.
  • Selected equipment performance values.

Trend availability, historical retention, sampling behavior, and storage options depend on the GOT model and project configuration.

A trend is useful only if the relevant data is being acquired correctly and the time scale is suitable for the problem being investigated.

9.2 Recipes

A recipe is a group of process parameters associated with a product variant or operating condition.

For example, an assembly station might use separate parameter sets for two approved product variants.

A controlled recipe workflow is:

  1. Select the intended recipe.
  2. Load the configured values.
  3. Validate the values and recipe identity.
  4. Transfer the parameters to the intended PLC destination.
  5. Confirm successful transfer.
  6. Allow the machine to use the parameters only under the required operating conditions.

Recipe storage and transfer functions vary by GOT model and project configuration. Validate the actual implementation rather than assuming every GOT2000 supports identical features.

9.3 Data logging

Where supported and configured, data logging can retain selected process values for later review.

For maintenance, useful values may include cycle time, process pressure, temperature, fault counts, and selected machine states.

Do not assume that a live trend automatically creates a permanent historical record. Acquisition, logging, storage, and retention must be configured appropriately.

10. GOT2000 Diagnostics

When troubleshooting a GOT2000, separate the problem into four layers.

Layer 1: HMI hardware

Check:

  • Power supply.
  • Display and touch response.
  • Physical damage.
  • Status indicators.
  • Network and communication cables.
  • Connector condition.

Layer 2: GOT project and runtime

Check:

  • Correct project loaded.
  • Correct screen and object configuration.
  • Correct device references.
  • Correct display and data formats.
  • Correct project and terminal compatibility.
  • Relevant runtime errors or diagnostic indications.

Layer 3: Communication

Check:

  • GOT IP address and subnet.
  • PLC IP address and subnet.
  • Communication path and interface.
  • Device selection and connection configuration.
  • Network cable and switch port.
  • PLC communication status.
  • Duplicate IP addresses or incorrect network settings.

Layer 4: PLC and machine

Check:

  • PLC mode and controller health.
  • Actual device or label value.
  • Program logic and permissives.
  • Input and output states.
  • Sensor and actuator feedback.
  • Equipment faults and safety-related status.

Troubleshooting rule: Start by determining whether the value is wrong in the PLC, wrong in the communication path, or merely displayed incorrectly on the GOT. This avoids changing a working HMI project to compensate for a PLC or field-device fault.

11. GOT2000 Project Transfer and Backup

Project transfer is an important maintenance task when replacing a terminal, restoring a project, or modifying an existing machine interface.

The usual workflow is:

  1. Identify the exact GOT model.
  2. Identify the project engineering software and version.
  3. Obtain the approved source project and latest backup.
  4. Verify compatibility with the target terminal.
  5. Compile or validate the project as supported.
  6. Transfer the project using the supported method.
  7. Verify communication with the PLC.
  8. Test screens, alarms, and permitted operator functions.
  9. Archive the final approved project and record its revision.

Upload versus download

  • Download: Transfers the engineering project or configured application to the target terminal.
  • Upload: Retrieves supported project or data from the terminal, where the device and configuration permit it.
  • Backup: Preserves the required project, device data, and recovery information.
  • Restore: Returns the system to an appropriate saved state.

Do not assume that a GOT can always reconstruct the complete original engineering source from a deployed terminal. Upload support and recoverable content depend on the device, project, and transfer method.

Before modifying a production terminal, preserve the existing approved project and establish a practical rollback procedure.

12. GOT2000 Versus Siemens WinCC

Both platforms serve industrial visualization needs, but they belong to different automation ecosystems.

Aspect Mitsubishi GOT2000 Siemens WinCC
Product role Mitsubishi operator-terminal family Siemens HMI and SCADA software family
Typical engineering software GT Designer3 WinCC engineering tools, commonly through TIA Portal for supported products
Common PLC ecosystem Mitsubishi PLCs Siemens PLCs
PLC references Mitsubishi devices, labels, or supported references Siemens tags and supported device references
Runtime target Supported GOT terminal Supported panel or PC runtime
Main application Machine-level operator interface Machine-level HMI through larger SCADA applications
Communication Supported interfaces and device drivers Supported interfaces and communication drivers
Compatibility Depends on GOT model, project, and firmware Depends on WinCC product, runtime, target, and version

A GOT2000 can support certain non-Mitsubishi devices, and WinCC can support certain non-Siemens devices. However, support must be confirmed for the exact product and connection type.

Neither platform is universally superior. The right choice depends on the existing control system, required functions, hardware, engineering standards, and support arrangements.

14. Best Practices for Industrial Maintenance

  1. Record the GOT model, firmware, engineering software version, and PLC connection settings.
  2. Maintain a verified backup of the engineering source.
  3. Use consistent names for machine states, commands, and feedback.
  4. Clearly distinguish command requests from confirmed equipment states.
  5. Verify device references against the PLC program.
  6. Use clear alarms that describe the abnormal condition.
  7. Configure appropriate access restrictions for protected operations.
  8. Confirm communication recovery behavior after network interruptions.
  9. Test project changes on an approved system before production deployment.
  10. Record the project revision and maintain a recovery procedure.

For automotive production lines, also verify that any HMI change preserves the required operating sequence, operator permissions, fault handling, and safety-related boundaries.

The GOT should never be treated as a replacement for the PLC's safety functions or validated machine-control logic.

15. Interview Questions and Answers

Q1. What is GOT2000?

GOT2000 is a Mitsubishi Electric family of graphic operator terminals used for industrial machine visualization, operation, and diagnostics.

Q2. What does GOT stand for?

Graphic Operation Terminal.

Q3. Which software is used to engineer GOT2000 projects?

GT Designer3 is Mitsubishi's engineering software for creating and configuring supported GOT projects.

Q4. What is the difference between a GOT and a PLC?

The GOT provides the operator interface. The PLC executes the control program and manages the programmed machine sequence and I/O.

Q5. What are Mitsubishi PLC devices X, Y, M, and D?

They commonly represent input devices, output devices, internal relays, and data registers, respectively. Exact details depend on the PLC family.

Q6. Why might a GOT display incorrect PLC data?

Possible causes include an incorrect device reference, incorrect data type, incorrect scaling, communication problems, or a mismatch between the HMI project and the PLC program.

Q7. What is the difference between alarm acknowledgement and reset?

Acknowledgement indicates that the operator has recognized the alarm. Reset requests a recovery action according to the configured machine logic. They are not equivalent.

Q8. What should be checked before replacing a GOT2000 terminal?

Check the exact model, project compatibility, firmware requirements, communication configuration, available backup, physical interfaces, and recovery procedure.

Q9. Can GOT2000 communicate with a non-Mitsubishi PLC?

Some configurations support other manufacturers' devices. Compatibility depends on the terminal model, communication driver, and supported protocol.

Q10. Why should an HMI button not directly prove an actuator's state?

The button indicates an operator command or request. Actual equipment state must be established through suitable feedback and PLC logic.

16. Practical Exercises

Use a simulator or approved non-production system.

  1. Identify a GOT2000 terminal's exact model and communication interfaces.
  2. Identify the engineering software and project version used by the terminal.
  3. Create a screen containing a machine-ready indicator and a fault indicator.
  4. Configure a numeric display for a PLC register.
  5. Verify a displayed device reference against the PLC program.
  6. Create an alarm for a simulated actuator timeout.
  7. Configure a trend for a simulated process value, where supported.
  8. Inspect how a recipe is selected, transferred, and validated, where supported.
  9. Simulate a communication interruption and observe the HMI response.
  10. Back up the project and document how it would be restored.
  11. Compare the PLC command value with the actual feedback value.
  12. Document the diagnostic checks needed when a GOT displays stale data.

Remember the distinctions:

  • GOT: Mitsubishi operator-terminal family.
  • GOT2000: A specific generation of Mitsubishi GOT terminals.
  • GT Designer3: Engineering software used to create supported GOT projects.
  • PLC device: A reference to PLC data, such as M100 or D100.
  • Alarm: An indication of a configured abnormal condition.
  • Recipe: A group of process parameters used for an application.
  • Project transfer: Deployment or retrieval of supported project content.
  • Diagnostics: A systematic investigation of hardware, project configuration, communication, PLC logic, and field equipment.

The core maintenance skill is tracing a displayed value back to its actual PLC source and then determining whether the problem is in the PLC, communication path, GOT project, or physical machine.
