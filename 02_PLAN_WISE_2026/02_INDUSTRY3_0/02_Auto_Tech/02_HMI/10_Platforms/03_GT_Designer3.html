1. Definition

GT Designer3 is Mitsubishi Electric's HMI engineering software used to create, configure, test, and maintain projects for supported GOT operator terminals. It is commonly associated with the GT Works3 engineering software suite.

GT Designer3 is used to build the screens and functions that operators interact with on a Mitsubishi GOT, including supported GOT2000 models.

It allows an engineer to configure:

  • HMI screens and screen navigation.
  • Switches, buttons, lamps, and indicators.
  • PLC device references and data displays.
  • Numeric inputs and outputs.
  • Alarm displays and alarm history.
  • Trends and data logging, where supported.
  • Recipes and parameter entry, where supported.
  • User permissions and protected operations.
  • Communication settings.
  • Project validation, simulation, and terminal transfer, where supported.

For an industrial maintenance engineer, GT Designer3 is important when diagnosing an existing HMI project, modifying operator screens, replacing a GOT terminal, or maintaining the relationship between the HMI and PLC.

Key distinction: GT Designer3 creates and configures the HMI project. The GOT executes the deployed project, while the PLC remains responsible for its programmed machine-control logic.

GT Designer3 does not automatically contain the PLC's complete control logic. It contains the HMI configuration, including the device references and behaviors configured for its objects.

3. What Is an HMI Project?

An HMI project is the engineering configuration that defines what the operator sees and how the terminal interacts with the automation system.

A typical project can include the following elements:

Project element Purpose
Target GOT model Defines the intended terminal and its supported capabilities
Communication configuration Defines the connection to the PLC or other supported device
Screens Defines the visual pages shown to operators
Screen objects Buttons, lamps, numeric displays, text, graphs, and other interface elements
Device references Identifies PLC data used by screen objects
Alarm configuration Defines alarm conditions, messages, and related displays
Trend configuration Defines process values to display or log
Recipe configuration Defines supported parameter groups and their transfer behavior
Security configuration Restricts access to protected operations, where supported
Project resources Includes text, graphics, fonts, and other configured resources

The exact project structure and available features depend on the GT Designer3 version and selected GOT model.

4. GT Designer3 Engineering Workflow

A practical workflow for creating or modifying a project is as follows.

Step 1: Identify the target GOT

Confirm the terminal model, display resolution, communication interfaces, and supported functions.

Selecting an incorrect target can create compatibility problems or prevent the project from using the intended hardware features.

Step 2: Create or open the project

Start a project for the intended GOT model or open the approved existing project.

For an existing production machine, use the correct engineering source rather than rebuilding the entire project from screenshots.

Step 3: Configure communication

Set the supported PLC connection and relevant communication parameters.

Depending on the system, these may include:

  • PLC family or device type.
  • Communication driver or protocol.
  • Ethernet or serial interface.
  • IP address and subnet settings.
  • Serial communication parameters, where applicable.
  • Device addressing and connection-specific settings.

The GOT and PLC must agree on the communication configuration. An Ethernet cable alone does not establish that the application can access the intended PLC devices.

Step 4: Build the screens

Create the required screens and arrange the objects according to the operator's needs.

A typical machine project may contain an overview, automatic operation, manual operation, alarms, diagnostics, and maintenance screens.

Step 5: Link screen objects to PLC data

Assign the correct PLC device references to lamps, numeric displays, switches, and other objects.

For example, an indicator might read M100, while a numeric display reads D100. These addresses are illustrative and must be verified against the actual PLC program.

Step 6: Configure supported HMI functions

Set up alarms, trends, recipes, logging, navigation, and access restrictions as required by the application and target GOT.

Step 7: Validate the project

Check for configuration errors, incorrect references, unsupported features, and inconsistent screen behavior. Use available simulation or testing features where appropriate.

Step 8: Transfer and verify

Back up the existing project before making production changes. Transfer the approved project using an interface supported by the target GOT, then verify the deployed behavior on the actual terminal.

Do not consider a successful transfer sufficient proof that the HMI is functioning correctly.

5. Screen Objects and Their Configuration

Screen objects are the components used to create the operator interface. Correct object configuration is just as important as correct screen design.

Object Typical purpose Important configuration
Switch/button Sends a command or changes a configured device Write target, operation, permissions
Lamp/indicator Displays a binary state Read device, ON/OFF appearance
Numeric display Displays a numerical value Device, data type, format, scaling
Numeric input Allows an operator to enter a value Write target, limits, format, access control
Text object Displays labels or instructions Text, language, readability
Alarm object Displays configured alarm information Alarm configuration, display behavior
Trend/graph Displays process values over time Data source, time range, scale
Navigation object Opens another screen Target screen and navigation behavior

Example: configuring a status lamp

Suppose a Mitsubishi PLC uses M100 as a station-ready status.

  1. Open the intended screen in GT Designer3.
  2. Insert a suitable indicator or lamp object.
  3. Configure the object to read M100.
  4. Configure its visual states.
  5. Validate the device reference and object behavior.
  6. Test against the actual PLC value or a suitable simulation.

Expected behavior:

M100 = OFF  ->  Station not ready
M100 = ON   ->  Station ready

The exact meaning of M100 must be defined by the PLC program. The HMI cannot determine what a bit means merely by staring at it, despite the optimism of some engineering projects.

Example: configuring numeric display

Suppose D100 contains a process value.

Before configuring the display, determine:

  • Whether the value is an integer or another supported data type.
  • Whether it is signed or unsigned.
  • Whether the PLC uses a scaling factor.
  • Whether the displayed value requires decimal places.
  • What units the value represents.
  • Whether the value is valid during startup or communication loss.

If the PLC stores 235 to represent 23.5 °C, the HMI display must use the agreed scaling convention. Otherwise, it may show 235 °C, which is a display problem with potentially unpleasant consequences if someone trusts it.

6. PLC Device References and Data Mapping

GT Designer3 projects commonly use Mitsubishi PLC device references, subject to the selected PLC family and communication configuration.

Example reference Illustrative use
X0 Read an input state
Y0 Read an output state
M100 Read a station-ready status
M110 Read or write a configured internal command/request bit
D100 Display a process value
D110 Display a selected recipe number

These addresses are examples only. They must not be copied into a production project without checking the actual PLC program and device allocation.

Mapping errors to avoid

  • Referencing the wrong PLC device.
  • Using a bit device where a word device is required.
  • Configuring the wrong data format.
  • Applying incorrect scaling.
  • Writing to a device that is not intended for operator control.
  • Using a device reference that is unsupported by the selected PLC or driver.
  • Assuming the HMI and PLC projects use the same naming conventions.

A useful maintenance practice is to maintain a device-mapping list that records the HMI object, PLC device or tag, description, data type, access mode, and engineering units.

7. Read Operations Versus Write Operations

An HMI object may read PLC data, write PLC data, or perform both functions, depending on its configuration.

Read operation

The HMI obtains data from the PLC and presents it to the operator.

Examples:

  • Station ready.
  • Robot faulted.
  • Actual pressure.
  • Cycle counter.
  • Clamp closed feedback.

Write operation

The HMI changes a configured PLC device or sends a configured request.

Examples:

  • Request manual mode.
  • Request a cycle start.
  • Enter a process setpoint.
  • Select a recipe.

Important: Do not design an operator button to bypass the PLC's sequence, permissives, interlocks, or safety functions.

A preferred arrangement is:

HMI operator action
        |
        v
PLC command request
        |
        v
PLC validates conditions
        |
        v
PLC controls the sequence
        |
        v
Field equipment operates
        |
        v
Feedback confirms the result
        |
        v
HMI displays actual status

The PLC should determine whether a command is permitted and manage the machine response. The HMI provides the operator interface, not an alternative control system.

8. Communication Configuration and Troubleshooting

When a project cannot communicate with a PLC, distinguish between network connectivity and successful PLC data exchange.

A device may be reachable on the network while the configured HMI driver, protocol, addressing, or PLC connection remains incorrect.

Check the following in order:

  1. Confirm the GOT model and PLC family.
  2. Verify the selected communication driver and connection settings.
  3. Check the GOT and PLC IP addresses, subnet settings, and network path for Ethernet connections.
  4. Check the serial settings if a supported serial connection is used.
  5. Confirm that the PLC is running as expected and that the intended device exists.
  6. Test a known, safe-to-read PLC device.
  7. Check whether the issue affects all devices or only selected references.
  8. Verify object configuration, data types, and access permissions.
  9. Review available communication diagnostics and error indications.

Example: the HMI opens, but all values are invalid

This suggests that the terminal and its project may be running, while the PLC data path is not working correctly.

Possible causes include:

  • Incorrect PLC connection settings.
  • Incorrect IP address or network configuration.
  • Wrong PLC driver or target selection.
  • Incorrect device references.
  • An unsupported connection configuration.
  • PLC-side or network-side communication faults.

Do not immediately redesign the screens. First establish whether the GOT is successfully exchanging data with the PLC.

9. Project Validation, Simulation, and Testing

Validation should cover more than whether the project compiles or transfers.

Engineering checks

  • Correct target GOT model.
  • Correct communication configuration.
  • Valid screen navigation.
  • Correct device references.
  • Correct data formats and scaling.
  • Appropriate read/write behavior.
  • Appropriate alarm configuration.
  • Correct access restrictions.
  • No unintended command paths.

Functional checks

  • Status indicators match PLC states.
  • Numeric displays match the source data.
  • Numeric inputs behave within the specified limits.
  • Operator commands are accepted or rejected as expected.
  • Alarms appear under the intended conditions.
  • Communication-loss behavior is clear.
  • Screen navigation behaves correctly.
  • Recovery after a communication interruption is verified.

Simulation can help test supported aspects of a project, but it does not prove that the deployed GOT, physical network, PLC, and machine will behave correctly. Hardware-level verification is still required.

10. Version Control, Backup, and Restoration

GT Designer3 project management is an important maintenance responsibility.

For each approved revision, record:

  • Machine or station identification.
  • GOT model.
  • PLC model and relevant connection details.
  • GT Designer3 version.
  • Project revision and date.
  • Reason for the change.
  • Approved source project location.
  • Transfer and test results.
  • Recovery or rollback procedure.

Keep the engineering source separate from any deployed copy and preserve the approved baseline before making changes.

Example revision record

Field Example
Station FR1010
Change Added diagnostic status screen
Project revision R03
Target Confirmed GOT model
Test Screen, device mapping, and communication verified
Approval Recorded according to site procedure
Backup Saved approved project and revision record

The station and revision information above are illustrative.

Upload and download considerations

  • Download: Transfers supported project content from the engineering environment to the GOT.
  • Upload: Retrieves project content from the terminal where supported.
  • Backup: Preserves the source project and necessary recovery information.
  • Restore: Returns the system to a saved, appropriate configuration.

Do not assume that uploading from a deployed GOT will always recover the complete original editable source. Recovery capabilities depend on the model, project, and transfer configuration.

11. GT Designer3 Compared With Other HMI Engineering Tools

Tool Vendor/ecosystem Typical target
GT Designer3 Mitsubishi Electric Supported Mitsubishi GOT terminals
WinCC engineering tools Siemens Supported Siemens HMI and SCADA products
FactoryTalk View Studio Rockwell Automation Supported PanelView and FactoryTalk View applications

The software tools differ in project structure, supported hardware, device addressing, runtime behavior, and communication drivers.

A project created in GT Designer3 cannot simply be loaded into Siemens WinCC or Rockwell FactoryTalk View. Moving between platforms requires engineering work, including rebuilding screens and objects, mapping PLC data, recreating alarms and other functions, and testing the resulting application.

12. Common Engineering Mistakes

  1. Editing the wrong project revision.
  2. Selecting an incorrect GOT model.
  3. Changing communication settings without documenting the original configuration.
  4. Using the wrong PLC device reference.
  5. Mixing up command status and actual equipment feedback.
  6. Writing directly to a physical output without a properly designed PLC control path.
  7. Ignoring numeric scaling and data formats.
  8. Assuming simulation proves physical communication.
  9. Downloading without a verified backup.
  10. Failing to test alarms, operator permissions, and communication recovery after a change.

For production equipment, use the site's approved change-management and machine-safety procedures before deploying changes.

13. Practical Automotive Example

Consider a robotic station with a Mitsubishi PLC and a GOT2000 operator terminal.

The maintenance team wants to add a diagnostic screen using GT Designer3.

Required screen

Item Example PLC reference HMI behavior
Station ready M100 Displays readiness
Station fault M101 Displays fault status
Part present X0 Displays sensor state
Clamp-close request M110 Displays request state
Clamp-closed feedback X1 Displays actual feedback
Cycle count D100 Displays cycle count

All references are illustrative.

Engineering procedure

  1. Open the approved GT Designer3 project.
  2. Create a diagnostic screen.
  3. Add status indicators and a numeric display.
  4. Assign the correct PLC references.
  5. Use separate objects for command requests and physical feedback.
  6. Validate the project and available simulation behavior.
  7. Back up the existing approved project.
  8. Transfer the revised project using the supported method.
  9. Verify the screen against actual PLC states.
  10. Document the revision and test results.

Example fault investigation

The HMI shows:

Station ready:       ON
Clamp-close request: ON
Clamp-closed feedback: OFF
Station fault:       ON

This tells the maintenance engineer that the command request is active but the expected feedback is absent. It does not, by itself, prove whether the cause is a sensor fault, actuator fault, mechanical obstruction, wiring issue, or PLC sequence condition.

The next step is to investigate the PLC logic, relevant I/O states, alarms, and physical equipment. The HMI provides evidence, not a magical diagnosis.

14. Interview Questions and Answers

Q1. What is GT Designer3?

GT Designer3 is Mitsubishi Electric engineering software used to create and configure HMI projects for supported GOT terminals.

Q2. What is the difference between GT Designer3 and GOT2000?

GT Designer3 is the engineering software. GOT2000 is an HMI terminal family that runs compatible deployed projects.

Q3. What is the purpose of a device reference in an HMI project?

It identifies the PLC data that an HMI object reads or writes.

Q4. Why can an HMI project compile successfully but fail to display correct values?

The project may contain incorrect device references, communication settings, data types, scaling, or PLC mappings even if its engineering configuration is valid.

Q5. What is the difference between an HMI command and feedback?

A command requests an action. Feedback indicates the reported state of the equipment. They should be represented and interpreted separately.

Q6. Why should an approved project be backed up before modification?

A verified backup provides a known baseline and supports recovery if the modified project introduces faults or compatibility problems.

Q7. Does simulation prove the HMI will work on the actual machine?

No. Simulation can test supported project behavior, but actual hardware, communication, PLC logic, and field-device behavior require appropriate verification.

Q8. What should be checked before downloading a project?

Confirm the target GOT model, project compatibility, communication settings, approved source, backup, transfer method, and post-transfer test plan.

Q9. What is the purpose of alarm configuration?

It defines how specified abnormal conditions are presented to operators and, where supported, how alarm history and related information are handled.

Q10. Can a GT Designer3 project be directly reused in FactoryTalk View?

No. The project must be migrated or recreated for the target platform, with appropriate mapping and testing of screens, data, alarms, and other functions.

15. Practical Exercises

Use an approved test environment or simulator where available.

  1. Identify the GT Designer3 version and supported target GOT models.
  2. Open an existing project and inspect its target model and communication configuration.
  3. Find a screen object and trace its PLC device reference.
  4. Create a status indicator linked to a test PLC bit.
  5. Create a numeric display linked to a test PLC register.
  6. Verify the scaling and data type of the numeric display.
  7. Build a diagnostic screen showing command and feedback separately.
  8. Inspect the project's alarm configuration.
  9. Test screen navigation and protected operations.
  10. Review the project transfer procedure and backup location.
  11. Create a revision record for a hypothetical screen modification.
  12. Prepare a troubleshooting checklist for a GOT that runs its project but cannot read PLC values.
