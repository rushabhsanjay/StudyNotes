1. Definition

HMI project transfer is the process of moving an HMI application between engineering software, a computer, an HMI panel, or a backup location.

It is used during commissioning, maintenance, troubleshooting, project modification, panel replacement, and system recovery.

For example, if an HMI panel on an automotive production line fails, maintenance may need to retrieve an existing project backup, transfer the correct application to a replacement panel, restore its configuration, and verify communication with the PLC.

The key operations are:

  • Upload: Retrieve a project or supported data from a target device to an engineering computer.
  • Download: Transfer an engineering project or application to a target HMI device.
  • Backup: Save a recoverable copy of the project or device configuration.
  • Restore: Recover a project or configuration from a backup.
  • Archive: Package a project and its required resources for storage or transfer.

These terms can vary by manufacturer and software. In some engineering environments, upload and download describe different directions depending on the selected device or object. Always verify the direction shown by the specific software.

2. Why HMI Project Transfer Is Important

HMI project transfer is required in several practical situations.

Situation Required operation
New HMI installation Download the approved project
Existing panel needs modification Retrieve the available source, or locate the maintained engineering project
HMI panel replacement Restore or download the compatible project and configuration
Engineering changes Modify, validate, archive, and download the revised project
Accidental project loss Recover from a valid backup
HMI hardware upgrade Convert or migrate the project if supported, then download
Firmware upgrade Verify compatibility and follow the manufacturer's migration procedure
Project documentation Archive the source project and related resources
Commissioning Transfer and verify the application on the target device

A reliable transfer process reduces downtime and helps prevent the loss of project configuration, graphics, scripts, communication settings, and other application resources.

4. Source Project Versus Runtime Application

This distinction is one of the most important concepts in HMI maintenance.

4.1 Engineering Source Project

The engineering source is the project used to create or modify the HMI application.

Depending on the platform, it may contain:

  • Screens and graphical objects.
  • HMI tags.
  • PLC communication configuration.
  • Alarms and event configuration.
  • Trends and logging configuration.
  • Recipes.
  • Scripts.
  • User management settings.
  • Language resources.
  • Fonts, graphics, and other external resources.
  • Runtime settings.
  • Device and hardware configuration.

The exact contents depend on the engineering software and project type.

4.2 Runtime Application

The runtime application is the deployed application executed by the HMI device.

It may contain compiled or generated resources, runtime configuration, and other platform-specific files.

A runtime application may not provide the complete editable source project.

4.3 Why the distinction matters

Suppose an HMI panel is operating normally, but the original engineering computer has failed.

The panel may still run the application, yet the maintenance engineer may be unable to retrieve a fully editable project from it.

Some platforms support uploading an editable project or retrieving selected configuration data. Others may permit only a runtime backup or limited recovery.

Never assume that a working HMI panel contains a complete, editable copy of its original project.

5. Upload, Download, Backup, Restore and Archive

Restore Recover from a previously saved copy Recovered project or device configuration

Migration Adapt a project to a different software version, device, or platform Converted project, if supported

Important terminology note

The word upload is not used identically across all engineering tools. Some tools use different labels for retrieving a project, transferring a runtime backup, or reading configuration from a device.

Before performing the operation, confirm:

  1. The source.
  2. The destination.
  3. Whether the operation retrieves editable source or runtime data.
  4. Whether existing data on the destination may be overwritten.

6. Uploading an HMI Project

Uploading attempts to retrieve project or configuration data from a target device to an engineering computer.

Common reasons for uploading

  • The original project is unavailable.
  • The panel contains a newer configuration than the available engineering copy.
  • The project needs to be recovered for maintenance.
  • A supported device configuration needs to be inspected.

General procedure

  1. Identify the exact HMI model and firmware.
  2. Identify the engineering software and supported project format.
  3. Connect to the correct HMI using an approved transfer interface.
  4. Verify the target device identity.
  5. Check whether project upload is supported for that device and application.
  6. Select the appropriate upload or retrieval operation.
  7. Save the retrieved data in a controlled project directory.
  8. Open or validate the retrieved project using compatible engineering software.
  9. Check screens, tags, scripts, communication settings, and required external resources.
  10. Archive the recovered project and record its origin.

Possible upload limitations

Upload may be unavailable or incomplete because:

  • The project was configured to prevent source retrieval.
  • The panel contains only a compiled runtime application.
  • The engineering software does not support reverse conversion.
  • The source project is protected.
  • The project version is incompatible with the installed engineering software.
  • External resources or original files are missing.
  • The device supports only a particular backup or recovery mechanism.

If upload is unavailable, locate the maintained source project or a verified backup rather than assuming the runtime can be converted into the original source.

7. Downloading an HMI Project

Downloading transfers a project or runtime application from the engineering computer to the target HMI.

This is commonly required during initial installation, project updates, and panel replacement.

General procedure

  1. Confirm the target HMI model and supported firmware.
  2. Open the correct engineering project.
  3. Verify that the project matches the intended machine or station.
  4. Compile or validate the project where required.
  5. Resolve relevant errors and warnings.
  6. Verify PLC communication settings.
  7. Confirm that required graphics, scripts, recipes, and external resources are available.
  8. Back up the existing application and configuration as appropriate.
  9. Connect to the intended HMI.
  10. Verify the target device identity.
  11. Download the application using the manufacturer's supported procedure.
  12. Follow the tool's instructions concerning runtime stop, restart, or replacement of existing application data.
  13. Confirm that the application starts correctly.
  14. Verify communication, displays, alarms, commands, and required functions.
  15. Record the project revision and commissioning result.

Critical precautions

Downloading may replace the currently deployed application and may interrupt production.

Before proceeding, confirm:

  • The machine is in an approved state for the transfer.
  • The correct panel and project are selected.
  • The current application can be recovered.
  • Required user settings, recipes, and configuration data are preserved where necessary.
  • The download will not unintentionally modify the PLC project or another device.

The exact effects of downloading depend on the HMI platform and transfer method.

8. Backing Up an HMI Project

A backup is a recoverable copy of the project or device configuration.

A useful backup strategy distinguishes several types of data.

Backup type What it may contain
Engineering project backup Editable project files and project resources
Project archive Packaged project and supported dependencies
Runtime backup Deployed application or supported runtime data
Device configuration backup Supported panel-specific settings
Recipe backup Recipe records and parameter sets
User and security backup Supported user accounts, roles, or security configuration
Communication documentation Device addresses, paths, and connection settings

Not every HMI platform supports every backup type.

Recommended backup practices

  • Keep an approved copy of the editable source project.
  • Store a project archive when supported.
  • Record the HMI model and software version.
  • Record the project revision and backup date.
  • Include required external resources and dependencies.
  • Keep a known-good version separate from the latest working copy.
  • Store backups in an approved location with suitable access controls.
  • Maintain a documented naming convention.
  • Verify that the backup can actually be opened or restored.
  • Keep recovery instructions with the backup.

A file that exists is not automatically a usable backup. The project must be compatible, complete enough for its intended purpose, and recoverable.

9. Restoring an HMI Project

Restoring means recovering a project, application, or supported device configuration from a previously saved copy.

Restoration is commonly required after:

  • HMI hardware failure.
  • Accidental deletion.
  • Project corruption.
  • An unsuccessful software update.
  • Incorrect project modification.
  • Replacement of an obsolete panel.

General restore procedure

  1. Identify the failed or replacement HMI.
  2. Confirm the exact hardware model and compatibility requirements.
  3. Locate the latest known-good backup.
  4. Verify its project revision and source.
  5. Confirm the required engineering software and firmware compatibility.
  6. Inspect the backup for missing dependencies or resources.
  7. Back up any recoverable information from the existing device, where appropriate.
  8. Prepare the target panel according to the manufacturer's procedure.
  9. Restore or download the compatible application and required configuration.
  10. Verify communication with the PLC and connected systems.
  11. Check recipes, alarms, trends, security, and other relevant features.
  12. Test required operations under approved commissioning conditions.
  13. Document the recovery and retain the restored project as required.

Restore does not always mean full system recovery

A runtime backup may not include all original source files. A project archive may not include current device-side data, such as recipes or logs, unless the platform includes them in the archive.

Therefore, determine what the backup actually contains before relying on it for full recovery.

10. Project Version and Compatibility

HMI projects depend on software versions, device families, firmware, and runtime capabilities.

A project created in one engineering software version may not open or deploy directly to a different version.

Compatibility checks may include:

  • Engineering software version.
  • HMI hardware model.
  • Runtime version.
  • Firmware revision.
  • Supported communication drivers.
  • Project format.
  • Required libraries or add-ons.
  • External resources.
  • Security settings.

Example

An existing HMI project may have been developed for an older panel generation. A replacement panel may use a newer runtime or different hardware family.

The project may require migration, conversion, or redesign rather than a direct download.

Migration can also change object behavior, available functions, or communication configuration. A successful conversion does not automatically prove that the machine interface works correctly.

13. Practical Example: Replacing an Automotive HMI Panel

Suppose an HMI panel on station FR1010 fails and needs replacement.

Step 1: Identify the original system

Record the panel model, runtime version, engineering software version, PLC address, communication driver, and relevant project revision.

Step 2: Find the approved source

Locate the released engineering project or a verified project archive.

Do not automatically assume the failed panel can supply the editable source.

Step 3: Check replacement compatibility

Confirm that the replacement panel supports the project or determine whether migration is required.

Step 4: Prepare the project

Validate the project, confirm the target device configuration, and ensure that required graphics, scripts, tags, and communication settings are present.

Step 5: Preserve recoverable information

Where possible, preserve required recipes, settings, or other device-side data using the platform's supported backup methods.

Step 6: Transfer the application

Download or restore the compatible project using the approved engineering procedure.

Step 7: Verify communication

Confirm that the replacement HMI communicates with the correct PLC and displays current values.

Step 8: Test functions

Verify machine-state indications, alarms, diagnostics, recipes, permitted commands, and other required functions.

Step 9: Release the recovered panel

Document the project revision, transfer result, verification results, and any differences from the original system.

The aim is not merely to make the screen appear. The aim is to restore the intended, verified HMI functionality.

14. Project Transfer and Production Safety

HMI project transfer can affect production, operator controls, and machine behavior.

Before changing a live system:

  1. Obtain the required authorization.
  2. Follow the plant's change-control procedure.
  3. Confirm the machine's approved transfer state.
  4. Back up the current project and relevant device data.
  5. Verify the correct target and project revision.
  6. Avoid unapproved changes to PLC logic or safety-related configuration.
  7. Follow applicable isolation and safety procedures for physical work.
  8. Test the restored application before releasing the machine.
  9. Document the change and rollback method.

A project transfer must not be used to bypass safety functions, defeat interlocks, or introduce unapproved machine behavior.

15. Interview Questions and Answers

Q1. What is HMI project transfer?

It is the process of moving an HMI project, application, or supported configuration between engineering software, storage, and a target HMI device.

Q2. What is the difference between upload and download?

Generally, upload retrieves data from a target device to the engineering computer, while download transfers an application from the engineering computer to the target. Specific software terminology may differ.

Q3. Can every HMI runtime application be uploaded as an editable project?

No. Upload capability depends on the platform, project configuration, and device. A runtime application may not contain the original editable source.

Q4. What is the difference between backup and archive?

A backup preserves data for recovery. An archive packages a project and supported resources for storage or transfer. Some platforms use these terms differently, so the actual contents must be verified.

Q5. Why is a backup necessary before downloading?

Downloading may replace the existing application. A verified backup provides a recovery path if the transfer or subsequent testing fails.

Q6. Why might a project fail on a replacement HMI?

The project may be incompatible with the new hardware, firmware, runtime, engineering software, or required resources.

Q7. What is project migration?

Migration adapts a project to a different supported software version, device generation, or platform. It may require conversion and functional retesting.

Q8. Why might PLC communication fail after a successful download?

The project may contain an incorrect PLC address, driver, communication path, tag configuration, or security setting.

Q9. What should be verified after restoring an HMI?

Verify runtime startup, PLC communication, current data, alarms, diagnostics, recipes, permissions, and the required operator functions.

Q10. What is the difference between the engineering source and runtime application?

The engineering source is used to modify the project. The runtime application is deployed to execute on the HMI. They may not contain the same information.

Q11. Why is revision control important?

It helps ensure that the correct, approved project is transferred to the correct device and supports traceability and recovery.

Q12. What is the most important precaution before project transfer?

Verify the target device, project revision, compatibility, current backup, and approved transfer conditions before replacing the deployed application.

16. Practical Exercises

Use a simulator or approved non-production HMI.

  1. Create a small HMI project with several screens and PLC tags.
  2. Save the editable engineering source.
  3. Create an archive or backup using the supported software function.
  4. Record the engineering software and target-device versions.
  5. Perform a download to a test HMI or simulator.
  6. Verify runtime startup and tag communication.
  7. Make a controlled project change and create a new revision.
  8. Compare the working revision with the released revision.
  9. Restore the earlier backup in the test environment.
  10. Verify that the restored project contains the expected screens and configuration.
  11. Determine whether the selected platform supports source upload, runtime backup, or both.
  12. Document what each backup type actually contains.
  13. Write a recovery procedure for a failed HMI panel.
  14. Create a pre-download checklist and post-download verification checklist.

  • Migration: Adapt a project to another supported version or device.

A reliable transfer process preserves the ability to recover, verifies compatibility, and confirms that the deployed HMI behaves as intended.
