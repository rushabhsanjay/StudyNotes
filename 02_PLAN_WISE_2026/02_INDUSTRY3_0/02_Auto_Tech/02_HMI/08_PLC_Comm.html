1. Definition

PLC communication is the exchange of data between a Human-Machine Interface (HMI) and a Programmable Logic Controller (PLC) so that the operator can monitor machine conditions, enter permitted commands, and interact with the control system.

The HMI typically reads PLC tags to display machine status, sensor states, alarms, process values, and diagnostic information. It may also write permitted values or commands to PLC tags.

For example, on an automotive robotic station, the HMI may display:

  • Automatic or manual mode.
  • Robot-ready status.
  • Clamp-open and clamp-closed feedback.
  • Active alarms.
  • Cycle count.
  • Recipe selection.
  • Station cycle state.
  • Drive or controller fault status.

The PLC executes the control logic and manages machine behavior. The HMI provides the operator interface.

Core principle: The HMI requests or displays information. The PLC remains responsible for validating commands and executing the machine's control logic.

2. Why PLC Communication Is Important

Without working communication, the HMI may not be able to display current PLC values or send permitted operator commands.

Typical communication-related problems include:

  • HMI displays stale values.
  • PLC tags show question marks or communication errors.
  • Buttons do not affect the intended PLC tags.
  • Alarms fail to update.
  • Recipe parameters are not transferred.
  • PLC values update slowly.
  • HMI and PLC use different tag names or data types.
  • A controller's IP address or communication path is incorrect.

Understanding communication helps maintenance personnel distinguish a communication fault from a genuine machine or device fault.

The PLC also sends tag values and status information back to the HMI.

The communication path may include Ethernet switches, network gateways, communication modules, or routing between networks.

In some systems, the HMI communicates directly with the PLC. In others, communication passes through an intermediary such as an OPC server or SCADA platform.

4. Read and Write Communication

HMI communication commonly involves two categories of data operations.

4.1 Read Operations

The HMI reads values from the PLC and displays them.

Examples:

PLC tag Example value HMI use
Machine_Ready TRUE Ready indicator
Robot_Faulted FALSE Robot status
Clamp_Closed_FB TRUE Clamp feedback
Cycle_Count 1250 Production counter
Actual_Temperature 178.5 Numeric display
Active_Recipe_ID MODEL_A Active recipe display

Read communication is normally used for monitoring.

However, a displayed value should be trusted only when its communication quality and freshness are acceptable.

4.2 Write Operations

The HMI writes a permitted value to a PLC tag.

Examples include:

  • Operator start request.
  • Stop request.
  • Alarm acknowledgement request.
  • Recipe selection.
  • Permitted setpoint change.
  • Manual-operation request.

Example:

HMI_Start_Request = TRUE

This indicates that the HMI has issued a request. It does not prove that the machine has started.

The PLC must evaluate the request against the machine state, operating mode, permissives, interlocks, and other applicable conditions.

For safety-related functions, an ordinary HMI command is not a substitute for the required safety-rated control architecture.

5. PLC Tags and Addressing

The HMI must reference the correct PLC data item. Depending on the platform, this may be a symbolic tag, a memory address, a data-block member, or a device register.

Siemens PLCs

In Siemens systems, HMI communication commonly uses symbolic PLC tags.

Examples of underlying PLC addresses include:

Address Typical meaning
I0.0 Digital input bit
Q0.0 Digital output bit
M10.0 Memory bit
DB10.DBX0.0 Bit in a data block
DB10.DBD4 Four-byte value in a data block

Actual accessibility depends on the CPU, data-block configuration, communication settings, and HMI driver.

Allen-Bradley PLCs

Modern Logix controllers commonly use symbolic tags.

Examples:

Machine_Ready
Robot_Ready
Station_Faulted
Clamp_Closed_FB
Cycle_Count

An HMI using EtherNet/IP may read these tags through a supported communication driver.

Older Allen-Bradley controllers may use data-file addressing, such as N7:0 or B3:0/0, depending on the controller family.

Do not assume that an addressing method used by an older controller also applies to ControlLogix or CompactLogix.

Mitsubishi PLCs

Common Mitsubishi device names include:

Device Typical use
X0 Input
Y0 Output
M10 Internal relay
D100 Data register

The available devices and addressing conventions depend on the Mitsubishi PLC series and communication configuration.

Practical rule: Confirm the PLC family, tag or address, data type, and HMI driver before troubleshooting a tag that does not update.

6. Communication Protocols and Drivers

A communication protocol defines how devices exchange information. An HMI driver implements the communication method required to access a particular controller or device.

Common industrial communication technologies include:

Protocol or technology Common context
PROFINET Siemens and other compatible industrial Ethernet devices
EtherNet/IP Rockwell Automation and other compatible industrial devices
Modbus TCP Ethernet-based communication with compatible devices
Modbus RTU Serial communication with compatible devices
Mitsubishi SLMP Communication with supported Mitsubishi controllers
OPC UA Standardized data access and information exchange
Vendor-specific HMI drivers Communication with particular PLC families

These technologies are not interchangeable merely because some use Ethernet.

For example, an HMI cannot communicate with a PLC simply by knowing its IP address if the configured driver, protocol, addressing, or access permissions are wrong.

7. Essential Communication Settings

Several settings must agree for communication to work.

7.1 PLC IP Address

The HMI must target the correct PLC address when the communication method uses IP networking.

Example:

PLC IP: 192.168.1.10
HMI IP: 192.168.1.20
Subnet: 255.255.255.0

These are illustrative addresses, not a recommendation for a live plant network.

The PLC and HMI normally need compatible network configurations. Communication across different subnets may require routing and suitable network configuration.

7.2 Communication Driver

The HMI must use a driver compatible with the PLC and its communication interface.

Examples include a Siemens driver, a Rockwell Logix driver, or a Mitsubishi driver.

An incorrect driver may prevent connection even when basic network connectivity exists.

7.3 PLC Path or Device Configuration

Some systems require a communication path, controller selection, rack or slot information, or other device-specific settings.

For example, a Rockwell installation may use a path through an Ethernet communication module to reach a controller in a chassis.

The exact path depends on the topology and software.

7.4 Tag Configuration

The HMI tag must refer to a valid PLC tag or address with a compatible data type.

A connection can be healthy while an individual tag remains invalid.

7.5 Access and Security

The PLC and network may restrict access based on user permissions, controller configuration, network segmentation, or security policies.

Successful network connectivity does not automatically mean the HMI is authorized to read or write every tag.

8. Communication Timing: Scan Time, Polling and Refresh

Communication timing is often misunderstood because several different intervals are involved.

Term Meaning
PLC scan or task cycle Time taken by the relevant controller task to execute
HMI polling interval How often the HMI requests or checks tag data, depending on the driver
Screen refresh How often the interface redraws displayed objects
Device update interval How often the device or controller updates its source data
Network latency Time taken for communication data to travel between endpoints
Logging interval How often values are recorded for trends or historical storage

These intervals are related but not identical.

For example, an HMI may refresh a numeric display every 250 ms while the underlying tag is polled at a different rate.

Changing the screen refresh interval does not necessarily change the PLC task cycle or the actual data acquisition rate.

Why excessively fast polling can be a problem

Polling every tag at an unnecessarily high rate can increase communication traffic, controller communication workload, and HMI processing load.

The appropriate update rate depends on the data's purpose.

  • Fast-changing process values may need relatively frequent updates.
  • Machine status and interlocks need an update strategy suitable for the operational requirements.
  • Slow-changing configuration data generally does not need rapid polling.
  • Historical logging should use an interval appropriate to the process and analysis requirement.

Do not assume that a fast HMI refresh makes a control system respond faster. The PLC's control logic and the actual communication path determine the control response.

9. Communication Quality and Stale Data

A displayed PLC value is useful only if the HMI can determine whether it is current and valid.

Consider this situation:

Last received value:
Robot_Ready = TRUE

Communication then fails.

If the HMI continues to display Robot_Ready = TRUE without showing the communication problem, an operator might incorrectly assume that the robot is currently ready.

A well-designed interface should distinguish:

  • Current valid data.
  • Communication failure.
  • Stale data.
  • Invalid or unavailable tags.
  • Unknown state.

The exact mechanisms for detecting these conditions depend on the HMI platform and driver.

Important: The last value received is not necessarily the current state of the machine.

10. HMI-to-PLC Communication Handshake

For some commands, especially multi-step operations such as recipe loading, a handshake provides explicit request and result information.

A basic example is:

HMI_Request
     |
     v
PLC detects request
     |
     v
PLC validates conditions
     |
     +-------> Reject and report error
     |
     v
PLC performs permitted operation
     |
     v
PLC reports completion
     |
     v
HMI displays result

Example tags:

Tag Typical owner Purpose
HMI_Command_Request HMI Requests an operation
PLC_Command_Busy PLC Indicates processing is in progress
PLC_Command_Accepted PLC Indicates the request was accepted
PLC_Command_Complete PLC Indicates completion
PLC_Command_Error PLC Indicates an error or rejection

Ownership and clearing rules must be defined for each signal.

For example, the request may be held until the PLC acknowledges it, or the system may use a sequence number to distinguish consecutive requests.

The handshake must also handle timeouts, repeated requests, communication interruptions, and stale acknowledgement bits.

Not every tag needs a handshake. Simple monitoring values often use ordinary reads, while important commands and multi-parameter transfers may need explicit confirmation.

11. Troubleshooting PLC Communication

A useful troubleshooting method separates network problems, driver problems, tag problems, and machine-logic problems.

Step 1: Check the HMI communication status

Determine whether the HMI reports a connected state, timeout, driver error, or unavailable controller.

Step 2: Verify the target device

Confirm the PLC IP address, controller selection, communication path, and configured driver.

Step 3: Check network connectivity

Where permitted, verify network settings and use approved diagnostic tools to test connectivity.

A successful ping only proves a limited level of IP reachability. It does not prove that the industrial protocol, PLC driver, or tag access is working.

Step 4: Verify protocol and device settings

Confirm that the configured protocol and communication interface match the PLC and network architecture.

Step 5: Test a known-good PLC tag

Use a simple, known-valid tag with a compatible data type.

If this works but another tag does not, investigate that tag's name, address, data type, access permissions, and configuration.

Step 6: Compare HMI and PLC values

If a tag reads correctly but a command does not work, monitor the target PLC tag and determine whether the HMI write reaches it.

Step 7: Check PLC logic

If the command reaches the PLC but the machine does not respond, inspect the PLC logic, machine state, permissives, interlocks, and command-handling sequence.

Step 8: Check communication loading and timing

Investigate excessive polling, large tag counts, slow updates, communication errors, or network congestion when the problem is intermittent or affects many tags.

Step 9: Check security and access restrictions

Verify whether the HMI is authorized to access the controller and whether the relevant tags permit the required operation.

Step 10: Verify the actual machine condition

When communication works but the expected process result does not occur, investigate the field devices and control sequence using approved procedures.

12. Common Communication Faults

Symptom Possible cause Investigation
All PLC tags are unavailable Wrong IP, network failure, incorrect driver, or invalid communication path Check connection status and network/device configuration
Only some tags fail Invalid tag names, addresses, types, or access restrictions Compare the failing tags with known-good tags
HMI reads values but writes fail Write permissions, incorrect write mapping, or PLC logic rejecting the command Monitor the destination tag and relevant permissions
Values update intermittently Network instability, communication load, or device interruptions Review timeouts, device status, and traffic
HMI displays old values Communication failure or missing stale-data indication Check connection status and update freshness
HMI buttons do not work Button configuration, tag mapping, permissions, or command logic Monitor the target PLC tag while testing
Connection works after restart but later fails Intermittent network or device issue, session problems, or resource limits Review diagnostic logs and connection behavior
PLC is reachable but HMI cannot connect Wrong driver, protocol, port, path, or access configuration Verify application-level communication settings
One screen updates slowly Excessive tag polling, object configuration, or screen-specific workload Inspect update rates and tag usage
HMI command arrives but machine does not start PLC interlock, invalid state, or command rejection Inspect the machine state and start permissives

13. Practical Example: Allen-Bradley Robotic Station

Consider a ControlLogix-based robotic station with an HMI displaying robot readiness, clamp status, and cycle state.

Illustrative tags include:

FR1010.R1.M130
FR1010_Robot_Ready
FR1010_Station_Faulted
FR1010_Clamp_Closed_FB
FR1010_Cycle_Start_Request
FR1010_Cycle_State

These names are examples. Actual tag names and their meanings must be confirmed from the controller project.

Suppose the HMI shows that the robot is not ready.

A systematic investigation would be:

  1. Check whether the HMI-to-PLC connection is healthy.
  2. Verify that the relevant robot-ready tag is updating.
  3. Compare the HMI value with the actual PLC tag value.
  4. If the PLC tag is also false, investigate the robot status and the PLC logic that derives readiness.
  5. If the PLC tag is true but the HMI shows false, investigate HMI tag mapping, update quality, or display configuration.
  6. If the PLC cannot obtain current robot status, investigate the PLC-to-robot communication path separately.

This example highlights a critical distinction: HMI-to-PLC communication and PLC-to-robot communication are separate links. A healthy HMI connection does not guarantee that the PLC is receiving current data from the robot.

14. Communication Testing and Commissioning Checklist

Before commissioning an HMI-to-PLC connection, verify the following:

  • Correct PLC model and firmware compatibility.
  • Correct HMI driver and protocol.
  • Correct PLC IP address and network settings.
  • Correct device path or controller configuration.
  • Correct PLC tag names and addresses.
  • Compatible data types and engineering units.
  • Correct read and write permissions.
  • Appropriate tag update rates.
  • Clear communication-error indications.
  • Suitable handling of stale or invalid data.
  • Correct command-handshake behavior where required.
  • Timeout and recovery behavior tested.
  • No unintended writes to physical outputs.
  • No reliance on the HMI as the sole safety control.
  • Communication restored and data verified after a simulated interruption.
  • The approved project and configuration are documented.

Testing should be performed within the plant's approved commissioning and change-control procedures.

15. Interview Questions and Answers

Q1. What is HMI-to-PLC communication?

It is the exchange of tag values, status information, and permitted commands between an HMI and a PLC.

Q2. What is the difference between reading and writing a PLC tag?

Reading retrieves a value from the PLC. Writing sends a value or command to a PLC tag.

Q3. Can an HMI directly control a machine output?

An HMI can write to configured PLC tags, but machine outputs should be controlled through appropriate PLC logic and interlocks. An HMI command should not bypass the intended control architecture.

Q4. What is the difference between a protocol and a driver?

A protocol defines how communication is performed. A driver implements the communication method needed by the HMI to interact with a supported device.

Q5. Why can a PLC respond to ping while the HMI cannot communicate with it?

Ping tests basic IP reachability. The HMI may still have an incorrect driver, protocol, device path, port, or access configuration.

Q6. What is stale data?

Data that has not been refreshed within the defined period and may no longer represent the current device state.

Q7. Why is a communication handshake useful?

It allows systems to coordinate commands and confirm whether an operation was accepted, completed, or rejected.

Q8. Why might HMI values update slowly?

Possible causes include polling intervals, communication load, network latency, controller communication workload, and HMI processing.

Q9. If the HMI command reaches the PLC but the machine does not start, what should be checked?

Inspect PLC command handling, operating mode, machine state, permissives, interlocks, and any rejection or timeout status.

Q10. Does successful HMI-to-PLC communication prove that the whole machine network is healthy?

No. Communication between the HMI and PLC is separate from communication between the PLC and robots, drives, remote I/O, or other devices.

16. Practical Exercises

Use a simulator or approved non-production setup.

  1. Configure an HMI connection to a test PLC.
  2. Read a Boolean tag and display it as an indicator.
  3. Read an integer and a floating-point tag.
  4. Configure a permitted command request and monitor it in the PLC.
  5. Test what happens when an HMI tag name is incorrect.
  6. Test the response to an unavailable PLC.
  7. Distinguish a communication failure from a PLC tag whose value is genuinely false.
  8. Implement a basic request-and-completion handshake.
  9. Test a timeout when no acknowledgement arrives.
  10. Verify that a rejected command is reported correctly.
  11. Observe the effect of changing polling intervals in the test environment.
  12. Document the complete communication path from HMI to PLC.

17. Final Mental Model

HMI-to-PLC communication is the data link that connects the operator interface to the control system.

Remember these distinctions:

  • Network connectivity: Can the endpoints reach each other at the network level?
  • Protocol communication: Can the HMI and PLC exchange data using the configured method?
  • Tag access: Can the HMI read or write the intended PLC data item?
  • Command acceptance: Did the PLC accept the requested operation?
  • Machine response: Did the equipment actually perform the intended action?
  • Feedback: Does the available evidence confirm the resulting condition?

These are separate stages. A failure at one stage can look similar to a failure at another, so troubleshoot them in order rather than changing random settings.
