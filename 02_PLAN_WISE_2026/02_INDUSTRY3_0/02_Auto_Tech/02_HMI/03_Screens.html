1. Definition and Purpose

An HMI screen is a graphical interface through which an operator or maintenance engineer monitors and interacts with an industrial machine, production station, or process.

An HMI screen organizes information from PLC tags and other configured data sources into visual elements such as:

  • Equipment symbols and status indicators.
  • Push buttons and command controls.
  • Numeric values and setpoints.
  • Alarm summaries.
  • Trend graphs and process measurements.
  • Navigation menus and diagnostic information.
  • User login and access-controlled functions.

The primary purpose of an HMI screen is to help personnel understand the current state of a machine, identify abnormal conditions, and perform authorized operations.

A well-designed screen answers three important questions:

  1. What is the machine doing?
  2. Is the machine operating normally?
  3. If something is wrong, where should the operator or maintenance engineer investigate?

An HMI screen is not the control logic itself. It displays information and submits operator requests, while the PLC or appropriate control system executes and validates the machine-control logic.

2. Basic HMI Screen Architecture

An HMI screen typically contains graphical objects connected to HMI tags.

             PLC / Data Source
                    |
                    v
                HMI Tags
                    |
                    v
             HMI Screen Objects
                    |
        +-----------+-----------+
        |           |           |
        v           v           v
     Indicators   Values      Buttons
        |           |           |
        v           v           v
    Show status  Show data   Send requests
                                |
                                v
                              PLC

For example, a motor symbol may be linked to Motor_Running_FB. When the tag changes, the symbol's appearance may change to indicate running or stopped status.

A Start button may write to Motor_Start_Request. The PLC checks the relevant operating conditions and decides whether to start the motor.

The button press itself is not proof that the motor has started.

3. Main Types of HMI Screens

Industrial HMI applications often use several screen types. The exact names and capabilities depend on the software platform.

3.1 Overview Screen

The overview screen provides a high-level view of the machine, production line, or process.

Typical contents:

  • Machine or station status.
  • Production count.
  • Automatic, manual, or fault state.
  • Major equipment running status.
  • Current active alarms.
  • Navigation to detailed screens.

For an automotive robotic line, an overview might display stations such as FR1010, FR1030, and FR1050, each with its current state.

The overview should emphasize important information rather than attempting to display every available PLC tag.

3.2 Machine or Station Screen

This screen shows the equipment within one machine or station in greater detail.

Typical contents:

  • Motors and drives.
  • Cylinders and actuators.
  • Sensors and limit switches.
  • Robot status.
  • Sequence step.
  • Interlocks and permissives.
  • Relevant operator commands.

Example: a conveyor station screen may display the conveyor motor, part-present sensor, drive-ready status, and cycle state.

3.3 Manual Operation Screen

The manual screen provides authorized controls for individual equipment or actuators.

Typical functions:

  • Jog forward and reverse.
  • Extend and retract.
  • Open and close.
  • Manual motor start and stop requests.
  • Individual actuator status.

Manual operation requires careful design. The PLC must still enforce the applicable interlocks, operating modes, motion limits, and safety conditions.

A screen should not expose unrestricted actuator commands simply because the controls are useful during maintenance.

3.4 Automatic Operation Screen

This screen displays the machine's automatic sequence and operating progress.

Typical contents:

  • Automatic mode status.
  • Current sequence step.
  • Cycle-start readiness.
  • Cycle active status.
  • Cycle complete status.
  • Sequence hold or fault status.
  • Relevant cycle-time information.

For example, a robotic station might show:

Station: FR1010
Mode: AUTO
Robot Ready: TRUE
Cycle Active: TRUE
Current Step: 120
Cycle Complete: FALSE
Fault Active: FALSE

These values are illustrative. Actual sequence numbers, modes, and signal meanings depend on the PLC program.

3.5 Alarm Screen

The alarm screen displays abnormal conditions requiring attention.

Typical contents:

  • Alarm description.
  • Equipment or station identifier.
  • Alarm activation time.
  • Active or cleared state.
  • Acknowledgement status.
  • Alarm priority.
  • Available diagnostic guidance.

Example alarm messages:

  • FR1010: Robot Not Ready
  • FR1010: Clamp Extend Timeout
  • FR1010: Drive Fault Active
  • FR1010: Safety Circuit Not Healthy

The alarm screen helps personnel identify the condition, but the underlying alarm logic and event handling must be configured separately.

Detailed alarm design is covered in the next topic, 04_Alarms - Alarms.

3.6 Trend Screen

A trend screen displays how process values change over time.

Typical data:

  • Motor speed.
  • Temperature.
  • Pressure.
  • Cycle time.
  • Analog process values.
  • Production rate.

Trends help identify intermittent problems, unstable processes, slow degradation, and abnormal operating patterns.

A trend can display live values, historical values, or both, depending on the HMI system and its data-storage configuration.

3.7 Diagnostic Screen

The diagnostic screen supports troubleshooting by displaying technical information about the equipment.

Typical contents:

  • PLC communication status.
  • Sensor and actuator feedback.
  • Drive-ready and drive-fault status.
  • Robot interface signals.
  • Sequence step and transition conditions.
  • Interlock and permissive status.
  • Communication error details.
  • Equipment-specific fault information.

For maintenance engineers, a useful diagnostic screen should help trace a symptom back to the relevant signal or condition.

For example, instead of displaying only Machine Not Ready, a diagnostic screen might show:

Condition State
Robot ready TRUE
Clamp retracted TRUE
Part present TRUE
Guard closed feedback FALSE
Start permissive FALSE

The table is illustrative. The actual conditions must match the machine's approved control design.

3.8 Settings and Recipe Screen

Settings screens display or configure approved operating parameters.

Examples:

  • Speed setpoint.
  • Process temperature target.
  • Timer preset.
  • Product selection.
  • Recipe parameters.
  • Production quantity target.

These screens should apply appropriate access control, range validation, units, and confirmation steps where needed.

A recipe is a coordinated group of process parameters, not merely a collection of unvalidated numbers.

3.9 Maintenance Screen

A maintenance screen may include:

  • Equipment status.
  • Operating-hour counters.
  • Cycle counters.
  • Drive diagnostics.
  • Sensor status.
  • Maintenance-related parameters.
  • Approved manual test functions.
  • Relevant fault history.

Maintenance screens should distinguish diagnostic visibility from permission to operate equipment.

3.10 Login and User Management Screen

Where supported, login screens allow users to authenticate and receive role-based access.

Typical roles include:

  • Operator.
  • Maintenance technician.
  • Engineer.
  • Administrator.

Permissions should match the responsibilities of each role. A higher access level should not automatically override PLC interlocks or safety requirements.

4. HMI Screen Hierarchy

A well-organized HMI application usually follows a predictable navigation structure.

Main Overview
    |
    +-- Line Overview
    |      |
    |      +-- Station FR1010
    |      |      |
    |      |      +-- Automatic
    |      |      +-- Manual
    |      |      +-- Diagnostics
    |      |
    |      +-- Station FR1030
    |             |
    |             +-- Automatic
    |             +-- Manual
    |             +-- Diagnostics
    |
    +-- Alarms
    |
    +-- Trends
    |
    +-- Maintenance
    |
    +-- Settings

This is a conceptual hierarchy, not a mandatory screen structure.

The navigation should follow how operators and maintenance engineers think about the equipment: plant or line, station, subsystem, and individual device.

A user should be able to reach important information without navigating through an unnecessarily large number of screens.

5. Common Screen Objects

An HMI screen is assembled from graphical objects. Each object has a visual purpose and may be linked to tags or configured actions.

Object Purpose Example
Text label Identifies equipment or information Conveyor Motor
Status indicator Shows a Boolean or state value Running or stopped
Numeric display Shows a numeric tag Motor speed
Push button Initiates a configured action Start request
Selector Selects an available option Operating mode request
Input field Accepts a value Speed setpoint
Bar graph Displays a value relative to a range Tank level
Trend chart Displays values over time Cycle-time history
Alarm summary Lists configured alarms Active station faults
Navigation button Opens another screen Station diagnostics
Text list Converts codes into descriptions Fault code message
Animation or symbol Visually represents equipment state Cylinder position
Date/time display Shows time information Current system time

The exact object names differ between platforms such as Siemens WinCC, Rockwell FactoryTalk View, and Mitsubishi GOT environments.

6. Screen Objects and Tag Connections

A graphical object becomes useful when its properties are correctly configured.

For a motor status indicator, the configuration might be:

Property Example
Object Motor symbol
Connected tag Motor_Running_FB
Data type Boolean
False appearance Stopped
True appearance Running
Communication fault behavior Show unknown or communication-fault state, where supported

For a numeric display:

Property Example
Object Numeric display
Connected tag Motor_Speed_PV
Data type Floating point
Engineering unit RPM
Decimal places 1
Display range Defined by equipment requirements

The display range and decimal places are presentation settings. They do not necessarily constrain the underlying PLC value.

For a command button:

Property Example
Object Start button
Connected tag Motor_Start_Request
Write behavior Momentary request, where supported
Access Authorized users
PLC validation Required
Actual running indication Separate feedback tag

The HMI object, tag, and PLC logic must agree on the signal's meaning and behavior.

7. Screen Navigation

Navigation is the mechanism used to move between screens.

Common navigation methods include:

  • Fixed navigation menus.
  • Station selection buttons.
  • Home and Back controls.
  • Tabs.
  • Pop-up windows.
  • Context-sensitive diagnostic links.
  • Alarm-to-equipment navigation.

Good navigation practices

  1. Keep important navigation controls in consistent locations.
  2. Use recognizable labels.
  3. Make the current station or screen clear.
  4. Provide a predictable path back to the overview.
  5. Avoid excessive nesting.
  6. Do not rely only on color to indicate the selected screen.
  7. Ensure pop-up windows can be closed or exited appropriately.

For example, selecting an alarm for station FR1010 could open the corresponding station diagnostic screen, where the operator can inspect the relevant conditions.

This reduces the time spent searching for the correct screen during a breakdown.

8. HMI Screen Design Principles

8.1 Show Important Information First

An overview should prioritize:

  • Machine state.
  • Production state.
  • Active abnormal conditions.
  • Important process values.
  • Equipment availability.

Detailed PLC information belongs on diagnostic screens unless it is immediately necessary for operation.

8.2 Use Consistent Visual Meaning

Use consistent symbols, labels, units, and state representations throughout the application.

For example, if a particular symbol represents a motor in one screen, it should not represent a cylinder in another without a clear distinction.

Color conventions should follow plant standards. Colors such as red, green, yellow, and grey may have established meanings, but those meanings must be consistent and documented.

Do not communicate critical state using color alone. Add text, symbols, or another distinguishable indication.

8.3 Distinguish Normal, Abnormal and Unknown States

A screen should distinguish between:

  • Equipment operating normally.
  • Equipment stopped normally.
  • An active fault.
  • An unavailable or disconnected data source.
  • A state that cannot currently be determined.

For example, a communication failure should not automatically make a motor appear stopped if the HMI simply no longer receives its running feedback.

A grey symbol can mean stopped in one project and communication loss in another. Use explicit status text or a separate communication indicator to avoid ambiguity.

8.4 Display Units and Valid Ranges

Numeric values should have meaningful units.

Examples:

  • Speed: RPM.
  • Pressure: bar.
  • Temperature: °C.
  • Time: seconds.
  • Production count: parts.
  • Distance: millimetres.

If a setpoint is displayed as 120, the operator should know whether it means 120 RPM, 120 °C, 120 bar, or something else.

8.5 Avoid Screen Clutter

Too many objects make important information difficult to identify.

A screen should contain the information needed for its intended task. Detailed diagnostic data, configuration parameters, and rarely used controls can be placed on separate screens.

8.6 Design for the Actual Display

Consider:

  • Screen resolution.
  • Panel size.
  • Viewing distance.
  • Touchscreen accuracy.
  • Font readability.
  • Glare and lighting.
  • Gloves and operator working conditions.

Small buttons and densely packed controls are especially problematic on industrial touch panels.

8.7 Prevent Accidental Commands

For consequential operations, use appropriate protections such as:

  • Role-based permissions.
  • Deliberate button placement.
  • Confirmation for selected high-impact actions.
  • Command timeout handling.
  • PLC-side validation.
  • Separate request and feedback indications.

Confirmation dialogs are not a substitute for proper control logic. Adding one to every routine action only teaches operators to dismiss dialogs without reading them.

9. HMI Screen Versus PLC Program

The HMI and PLC have different responsibilities.

Function HMI PLC
Display motor status Yes Supplies or calculates status
Display sensor state Yes Reads and processes sensor data
Present alarm information Displays configured alarms May evaluate the conditions that trigger alarms
Accept operator request Yes Receives and validates request
Execute machine sequence Normally no Yes
Enforce control interlocks Displays their status Implements the required control logic
Control physical outputs Normally through a request to the PLC Controls outputs according to its logic
Implement safety functions Not as the safety control authority Appropriate safety system performs required safety functions

The exact allocation of some functions depends on the system architecture, but the HMI should not be treated as a replacement for PLC logic or safety control.

10. HMI Screen Versus SCADA Screen

These terms overlap, but they often describe different levels of application.

Feature Machine HMI SCADA application
Typical scope Individual machine or station Multiple stations, lines, or processes
Main purpose Local operation and diagnosis Supervisory monitoring and coordination
Typical content Equipment symbols, commands, interlocks Plant overview, trends, alarms, reports
Data sources Commonly a local PLC Multiple PLCs, devices, servers, or gateways
Historical data May be available Often more extensive
Deployment Panel or machine-side PC Central or distributed supervisory system

These are common patterns, not strict definitions. Modern PC-based HMIs can have substantial SCADA-like functionality, while a SCADA application may provide detailed control screens.

11. Screen Design Example: Automotive Robot Station

Consider an automotive robotic station identified as FR1010.

The main station screen might display:

Screen item Example source or value Purpose
Robot ready Robot_Ready Indicates readiness
Robot running Robot_Running_FB Indicates running feedback
Robot fault Robot_Fault Indicates a reported fault
Cycle active Cycle_Active Shows whether the cycle is active
Cycle complete Cycle_Complete Indicates cycle completion
Current sequence step Sequence_Step Helps diagnose sequence progress
Start request Cycle_Start_Request Requests cycle start
Active alarm count Alarm subsystem Shows outstanding alarm conditions

A sensible navigation layout would provide access to:

  • Station overview.
  • Automatic operation.
  • Manual operation.
  • Robot diagnostics.
  • PLC and communication diagnostics.
  • Alarms.
  • Cycle-time trends.
  • Maintenance information.

Example diagnostic situation

An operator reports that the robot will not start.

The maintenance engineer checks the station screen and finds:

Condition Display
Robot ready TRUE
Cycle active FALSE
Start request TRUE
Start permissive FALSE
Active fault FALSE

The screen indicates that the start request exists but the permissive is false. The engineer then opens the diagnostic screen to identify which required condition is missing.

This is a useful HMI design pattern: show the overall symptom on the main screen and provide enough diagnostic detail to locate the cause without cluttering the overview.

12. Common HMI Screen Problems

Problem Possible cause Investigation
Screen shows incorrect status Wrong tag mapping or incorrect state interpretation Compare the object with the source PLC variable
Button appears to work but machine does not start Request rejected by PLC logic or required condition missing Monitor request, permissives and PLC response
Screen loads slowly Too many objects, heavy scripts, excessive communication requests Review screen complexity and update configuration
Numeric value is incorrect Wrong scaling, unit, format or data type Verify the source value and engineering conversion
Alarm appears but no useful diagnosis is available Poor alarm description or insufficient diagnostic navigation Improve alarm text and related diagnostic screen
Touch controls are difficult to use Small targets or poor layout Review panel dimensions and control spacing
Screen freezes or values stop changing Runtime problem or communication failure Check runtime, PLC connection and tag quality
Pop-up hides important information Poor window placement or navigation design Review pop-up behavior and screen layout
Wrong user can change a setting Incorrect access configuration Review user roles and write permissions
Stopped equipment appears healthy State definitions are ambiguous Separate stopped, running, fault and unknown states

13. Practical Screen Development Workflow

A disciplined workflow makes HMI projects easier to develop, test, and maintain.

  1. Define the screen purpose. Identify the operator or maintenance task the screen supports.
  2. Identify required information. List the status values, commands, measurements, alarms, and diagnostics.
  3. Identify tag sources. Map each screen element to the correct HMI tag and PLC variable.
  4. Design the layout. Group related equipment and information logically.
  5. Configure screen objects. Set tag connections, visual states, formatting, and actions.
  6. Configure navigation. Provide predictable paths between overview, operation, alarms, and diagnostics.
  7. Configure access controls. Restrict write operations and sensitive functions.
  8. Test normal states. Verify that all displayed values and indications are correct.
  9. Test abnormal states. Verify faults, communication loss, unavailable data, and rejected commands.
  10. Validate on the target panel. Check readability, touch accuracy, runtime behavior, and performance.
  11. Document the project. Record screen purposes, tag mappings, navigation structure, and relevant configuration.
  12. Control revisions. Back up and version the project before making production changes.

Testing should be performed in a simulator or approved test environment whenever possible. Production machine commands must be tested only under the site's authorized procedures.

14. Interview Questions and Answers

Q1. What is an HMI screen?

An HMI screen is a graphical interface that displays process information and allows authorized users to interact with an industrial control system.

Q2. What is the difference between an overview screen and a diagnostic screen?

An overview screen summarizes the operating state of a machine or line. A diagnostic screen exposes more detailed information used to investigate abnormal conditions.

Q3. How does an HMI screen display a PLC variable?

A screen object is connected to an HMI tag, which is mapped to a PLC variable or another configured data source. The HMI updates the object according to its communication and runtime configuration.

Q4. Why should command and feedback be displayed separately?

A command indicates a request, while feedback indicates the reported equipment state. Showing both helps identify whether a command was accepted and whether the expected result occurred.

Q5. What is screen navigation?

Screen navigation is the mechanism that allows users to move between related views, such as a line overview, station screen, alarm screen, and diagnostics.

Q6. Why is screen consistency important?

Consistent layouts, labels, symbols, and state indications reduce operator confusion and help maintenance personnel diagnose faults more quickly.

Q7. What is the purpose of a diagnostic screen?

It provides detailed status, interlock, feedback, sequence, and communication information to help locate the cause of a problem.

Q8. Can an HMI screen enforce machine safety by itself?

No. HMI permissions and display logic do not replace the appropriate safety system. Required safety functions must be implemented and validated in the designated safety architecture.

Q9. What is the difference between an HMI and SCADA?

A machine HMI commonly focuses on local operation, while SCADA commonly supervises multiple devices or processes and may provide centralized alarms, trends, and historical records. Their capabilities can overlap.

Q10. How would you troubleshoot an incorrect HMI indication?

Identify the screen object and tag, verify its source mapping and data type, compare it with the live PLC variable, check communication quality, and then inspect the object's state configuration and formatting.

15. Practical Study Exercises

Use a simulator or a non-production training project.

  1. Create a main overview screen for three stations.
  2. Create one detailed station screen containing motor, sensor, and robot status indicators.
  3. Link a status indicator to a Boolean tag.
  4. Add a numeric display with an engineering unit.
  5. Create separate start-request and running-feedback indicators.
  6. Add navigation buttons for Overview, Manual, Diagnostics, and Alarms.
  7. Design a diagnostic screen showing individual permissives.
  8. Create a trend screen for a sample process value.
  9. Review the appearance of running, stopped, faulted, and communication-loss states.
  10. Verify that unauthorized users cannot access restricted write functions.
  11. Test the screens at the target display resolution.
  12. Document every screen's purpose, important tags, and navigation path.

16. Final Mental Model

An HMI screen is the visual layer of an industrial automation system.

  • Tags provide the data.
  • Screen objects present the data or initiate configured actions.
  • Navigation organizes the operator's access to information.
  • Diagnostic screens help locate the cause of abnormal conditions.
  • Alarms notify users of configured abnormal conditions.
  • The PLC or appropriate control system executes and validates the machine-control logic.

A good HMI screen is not simply attractive. It presents the right information, clearly distinguishes normal and abnormal conditions, prevents avoidable operator errors, and helps maintenance personnel find the cause of a fault efficiently.
