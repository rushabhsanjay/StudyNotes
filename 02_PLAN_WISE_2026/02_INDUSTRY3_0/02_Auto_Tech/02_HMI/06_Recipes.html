1. Definition and Purpose

An HMI recipe is a predefined collection of process parameters that can be selected and applied to a machine or production process for a particular product, model, or operating condition.

Recipes allow a machine to switch between approved parameter sets without requiring an operator or engineer to enter every value individually.

In automotive manufacturing, the same production line may process different vehicle models, component variants, or product specifications. Each variant may require different parameters, such as:

  • Welding current and weld duration.
  • Clamp positions or timing values.
  • Conveyor speed.
  • Robot program or approved job selection.
  • Process temperature and pressure.
  • Torque targets.
  • Inspection limits.
  • Cycle timing parameters.

A recipe groups the relevant values into a named configuration.

For example, a station might have these recipes:

  • MODEL_A
  • MODEL_B
  • MODEL_C

Each recipe contains the parameters required for its supported production variant.

Important: A recipe is a set of data, not the machine sequence itself. The PLC or other appropriate control system remains responsible for validating parameters and executing the process safely.

2. Why Recipes Are Used

Without a recipe system, an operator may need to change several individual settings whenever the product changes.

For example, switching from one component variant to another could require updating:

  • Clamp timing.
  • Conveyor speed.
  • Weld parameters.
  • Inspection limits.
  • Product identification.
  • Other approved process settings.

Manual entry creates opportunities for typing errors, inconsistent settings, incomplete changes, and incorrect product-to-parameter combinations.

A recipe system helps by providing a predefined, identifiable set of parameters that can be selected and transferred in a controlled way.

Main benefits include:

  1. Faster product changeovers.
  2. Reduced manual entry errors.
  3. Consistent process settings.
  4. Easier product-variant management.
  5. Improved traceability.
  6. More repeatable production.
  7. Easier comparison of approved parameter sets.
  8. Better control over recipe revisions.

A recipe does not guarantee that the selected values are correct. Recipe identification, parameter validation, transfer confirmation, and change control still matter.

3. Basic Recipe Architecture

A typical recipe workflow looks like this:

        Product / Model Selection
                  |
                  v
           HMI Recipe Selection
                  |
                  v
          Recipe Parameter Set
                  |
                  v
          Parameter Validation
                  |
                  v
          Controlled Transfer
                  |
                  v
           PLC Recipe Buffer
                  |
                  v
         Machine Logic Applies
         Approved Parameters
                  |
                  v
           Production Process

The exact arrangement depends on the HMI and PLC architecture.

Some systems store recipes in the HMI and transfer values to the PLC. Others store recipe data in a PLC, SCADA system, database, or manufacturing system.

The critical requirement is that the selected recipe and its parameters are transferred, checked, and applied in a defined manner.

4. Main Components of a Recipe System

Component Purpose

Engineering units Define the meaning of numeric values
Parameter limits Define acceptable ranges
Recipe storage Stores recipe definitions

A robust implementation should distinguish a recipe that has been selected from a recipe that has actually been validated and applied.

5. Recipe Parameters and Data Types

Recipes can contain different types of parameters.

Parameter Example Data type Unit or meaning
Conveyor speed 250 Integer or floating point RPM, if defined that way
Clamp delay 0.5 Floating point Seconds
Weld current 12.5 Floating point kA, if applicable
Target temperature 180 Integer or floating point °C
Inspection enable TRUE Boolean Enables a configured inspection function
Product variant MODEL_A String or enumeration Product identifier
Inspection limit 2.5 Floating point Depends on the measurement specification

These values are illustrative only. Actual parameters, ranges, units, and data types must come from the approved machine and process specifications.

A numeric value without a defined unit is ambiguous. For example, 250 could mean RPM, milliseconds, degrees, or another quantity.

6. Recipe Example: Automotive Production Station

Consider an automotive station that processes two component variants.

The station uses different approved settings for each variant.

Parameter Recipe A Recipe B
Product variant MODEL_A MODEL_B
Conveyor speed 250 RPM 220 RPM
Clamp delay 0.5 s 0.7 s
Target temperature 180 °C 175 °C
Inspection limit 2.5 units 2.0 units

These numbers are hypothetical and do not represent real production specifications.

When the operator selects MODEL_B, the HMI identifies the corresponding recipe. The recipe system transfers the configured values to the appropriate destination, and the control system validates them before allowing the process to use them.

The PLC should not simply trust that a parameter is valid because it came from an HMI recipe.

7. Recipe Selection, Loading, Transfer and Application

These terms should be distinguished because they describe different stages.

7.1 Recipe Selection

The operator or an authorized production system chooses the required recipe.

Example:

Selected Recipe = MODEL_B

At this point, the selection alone does not prove that the PLC is using the new parameters.

7.2 Recipe Loading

The selected recipe is retrieved from its configured storage location.

The storage may be local to the HMI, in a PLC, in a database, or in another supported system.

7.3 Recipe Transfer

The recipe parameters are transferred to the intended destination, such as a PLC recipe buffer.

The transfer should be monitored so that communication errors or incomplete transfers can be detected.

7.4 Recipe Validation

The receiving control system checks the data.

Validation may include:

  • Parameter range checks.
  • Correct product or model identification.
  • Recipe ID verification.
  • Required parameters being present.
  • Compatible parameter revision.
  • Operating mode and machine-state checks.
  • Data consistency or transfer-completion checks.

7.5 Recipe Application

After validation and satisfaction of the required conditions, the control system makes the parameters available to the process.

Depending on the machine design, application may be permitted only when the machine is stopped, idle, or in a defined changeover state.

7.6 Confirmation

The HMI displays a clear result, such as:

  • Recipe selected.
  • Recipe transfer in progress.
  • Recipe transfer failed.
  • Recipe validated.
  • Recipe applied.
  • Recipe rejected.

The exact states depend on the platform and implementation.

Key distinction: Selecting a recipe, transferring its values, validating those values, and applying them are not the same operation.

8. Recipe Handshake Between HMI and PLC

For a recipe transfer involving multiple parameters, a defined handshake can prevent the PLC from using incomplete or invalid data.

One possible pattern is:

Step HMI or PLC action Purpose
1 HMI selects the recipe Identifies the required parameter set
2 HMI writes parameters to a transfer buffer Sends the values
3 HMI indicates transfer request Signals that the parameter set is ready for checking
4 PLC checks the request and values Validates the received data
5 PLC accepts or rejects the recipe Communicates the result
6 PLC copies accepted values to active parameters Applies the validated parameter set
7 PLC reports completion and active recipe ID Confirms the result to the HMI

This is an illustrative handshake. Real projects may use sequence numbers, checksums, buffer copies, version identifiers, or other mechanisms.

Example handshake tags

HMI_Recipe_ID
HMI_Recipe_Load_Request
PLC_Recipe_Busy
PLC_Recipe_Accepted
PLC_Recipe_Rejected
PLC_Recipe_Complete
PLC_Active_Recipe_ID
PLC_Recipe_Error_Code

The tags should have clearly defined ownership and behavior.

For example, the HMI may own the request bit, while the PLC owns the accepted, rejected, busy, and completion status bits.

A proper design also defines how request bits are cleared, how timeouts are handled, and what happens if communication fails during transfer.

9. Recipe Buffer Versus Active Parameters

A recipe buffer is a temporary destination where the selected parameters can be received and checked before being applied.

Active parameters are the values currently used by the machine logic.

Separating these data sets can prevent partially transferred or invalid data from affecting a running process.

Example:

Stored Recipe
     |
     v
Transfer Buffer
     |
     v
Validation
     |
     +---- Rejected
     |        |
     |        v
     |   Active values unchanged
     |
     +---- Accepted
              |
              v
       Active Parameters
              |
              v
        Machine Process

This separation is especially useful when recipes contain many parameters.

The transfer buffer should not be treated as the active parameter set until the defined validation and application conditions are satisfied.

10. Recipe Validation and Parameter Limits

Every recipe parameter should have an approved range where applicable.

For example:

Parameter Illustrative minimum Illustrative maximum
Conveyor speed 0 RPM 300 RPM
Clamp delay 0.1 s 2.0 s
Target temperature 100 °C 200 °C

These are example limits, not real machine settings.

Validation should check that:

  • Values are within approved ranges.
  • Numeric values are finite and representable in the destination data type.
  • Required parameters are present.
  • Parameter units and scaling are correct.
  • The recipe matches the intended product.
  • The recipe revision is permitted for the machine.
  • The machine is in a state where the recipe may be applied.

For some applications, individual range checks are not enough. Two parameters may be valid separately but invalid when combined.

For example, a temperature target and process timer may need to satisfy a combined process specification.

Validation rules should reflect the actual process requirements.

11. Recipe Identification and Product Matching

Selecting the wrong recipe can produce incorrect process settings even when every individual parameter is valid.

A recipe system should make the relationship between the product and recipe clear.

Possible identifiers include:

  • Recipe name.
  • Recipe ID.
  • Product code.
  • Variant identifier.
  • Revision number.
  • Machine or station identifier.

Where integrated with production systems, the recipe selection may be linked to a barcode, product identifier, manufacturing execution system, or another approved source.

The control system should verify that the selected recipe is valid for the current product and station where such matching is required.

A recipe intended for one product variant should not be applied to another merely because the parameter values fall within numerical limits.

12. Recipe Access Control and Change Management

Recipes may contain parameters that directly affect product quality, equipment behavior, and production performance.

Access should be appropriate to the consequences of changing those values.

Common roles include:

Role Typical permissions
Operator Select approved recipes and perform permitted load operations
Maintenance technician Diagnose transfer issues and perform approved maintenance functions
Process or controls engineer Edit parameters where authorized
Administrator Manage users and application configuration where authorized

The actual role structure depends on the plant's governance and HMI configuration.

Recommended controls

  1. Restrict editing of approved production recipes.
  2. Separate recipe selection from recipe modification.
  3. Record changes where required.
  4. Maintain revision identification.
  5. Define approval and release procedures.
  6. Keep a recoverable backup of approved recipes.
  7. Verify the active recipe before production starts.
  8. Prevent unauthorized edits from silently affecting production.
  9. Validate parameters in the receiving control system.
  10. Test recipe changes in an approved environment before release.

A user permission system helps control who can change recipes. It does not replace PLC-side validation or process-quality controls.

13. Recipe Versioning and Traceability

A recipe can change over time as process requirements are updated.

Versioning helps establish which approved configuration was used during production.

For example:

Recipe: MODEL_A
Revision: 03
Approved: TRUE

The revision number is illustrative.

Useful traceability data may include:

  • Recipe ID.
  • Recipe revision.
  • Date and time of selection or application.
  • Machine or station ID.
  • Product ID or batch ID.
  • User or system that initiated the change.
  • Transfer or validation result.
  • Relevant parameter changes.

Where product quality or regulatory requirements demand traceability, the system should retain the required records for the defined period.

A simple recipe name is not always sufficient to prove which exact parameter set was applied.

14. Recipe Storage Methods

Recipes can be stored in different places, depending on the system design.

14.1 HMI-Local Storage

The HMI stores recipe definitions and transfers the selected values to the PLC.

Advantages may include simple local management and direct operator access.

Considerations include backup, device replacement, storage capacity, and synchronization between HMIs.

14.2 PLC Storage

The PLC stores recipe data in controller memory.

This can simplify access to the active values and support local machine operation, but capacity, organization, and backup behavior depend on the controller.

14.3 Database Storage

A database stores recipe records, parameters, revisions, and related information.

This can support centralized management, reporting, and integration with production systems.

It introduces additional considerations, such as database availability, communication failure, permissions, and synchronization.

14.4 Centralized Production-System Storage

A manufacturing system may manage product specifications and recipe distribution across multiple machines or production lines.

This can support centralized revision control and product-to-process matching, but requires a well-defined interface and failure-handling strategy.

Storage location Typical strength Important consideration
HMI Convenient local selection Backup and synchronization
PLC Direct access to control parameters Capacity and controller data management
Database Centralized records and revision tracking Availability and communication handling
Manufacturing system Coordinated production-wide management Integration and product matching

A system may combine these approaches. For example, a database may store approved recipes while the PLC maintains a validated active parameter set.

15. Recipe Problems and Troubleshooting

Symptom Possible cause Investigation
Recipe cannot be selected Invalid recipe, permissions, or unavailable storage Check recipe list, access rights, and storage
Recipe selected but PLC values do not change Transfer not initiated or incorrect mapping Monitor the request and destination buffer
Some parameters update but others do not Incomplete transfer, incorrect mapping, or inconsistent data types Compare every parameter in the source and destination
PLC rejects the recipe Invalid range, wrong product, incompatible revision, or machine state Inspect the rejection status and error code
HMI shows the wrong active recipe Display uses selected recipe rather than confirmed active recipe Compare the displayed ID with PLC confirmation
Recipe transfer hangs Handshake error, communication loss, or missing completion condition Check request, busy, accepted, rejected, and timeout behavior
Wrong values appear after restart Retention, initialization, or loading behavior is incorrect Check startup logic and active recipe restoration
Recipe values are correct but the process is wrong Incorrect units, scaling, parameter mapping, or process logic Verify parameter meaning and how the PLC uses it
Wrong recipe applied to product Product-to-recipe matching is missing or incorrect Verify product identity and recipe validation
Old parameters reappear Incorrect source of truth, stale storage, or unsynchronized copies Trace the stored, transferred, and active parameter sets

Recommended troubleshooting sequence

  1. Identify the selected recipe ID and revision.
  2. Verify that the selected recipe is valid for the current product and machine.
  3. Check whether the transfer request was issued.
  4. Compare the recipe source values with the PLC transfer buffer.
  5. Verify data types, scaling, units, and parameter mapping.
  6. Inspect PLC acceptance or rejection status.
  7. Compare the active parameter set with the intended recipe.
  8. Check transfer timeouts and communication quality.
  9. Review startup and retention behavior if the issue occurs after a restart.
  10. Verify the process response using approved diagnostic procedures.

Do not assume that the HMI's selected recipe name proves that the PLC has applied the corresponding parameters.

16. Practical Example: Recipe Transfer for an Automotive Station

Consider a station that processes two product variants. The station uses different approved clamp timings and conveyor settings.

The HMI provides these controls:

  • Selected recipe.
  • Load recipe.
  • Transfer status.
  • Validation result.
  • Active recipe ID.
  • Parameter display.
  • Error message.

The PLC maintains:

  • Recipe transfer buffer.
  • Active parameter set.
  • Parameter validation logic.
  • Transfer handshake.
  • Active recipe identifier.
  • Recipe error status.

Normal operation

  1. The operator selects the required product variant.
  2. The HMI retrieves the associated recipe.
  3. The HMI transfers the parameter set.
  4. The PLC checks the recipe ID and parameter values.
  5. The PLC accepts the recipe if all required checks pass.
  6. The PLC applies the parameters at the permitted point in the operating sequence.
  7. The PLC reports the active recipe ID and completion status.
  8. The HMI displays the confirmed active recipe.

Failure operation

Suppose the recipe contains a clamp delay outside the approved range.

The PLC rejects the transfer, reports the relevant error, and leaves the active parameters unchanged where that is the defined design.

The HMI should show that the recipe was rejected. It should not display the new recipe as successfully applied.

This behavior prevents the user interface from reporting success when the control system has not accepted the new parameters.

17. Recipe Testing and Commissioning Checklist

Before releasing a recipe system for production, verify:

  • Recipe names and IDs are unique and meaningful.
  • Every parameter has a documented type and unit.
  • Approved limits are defined where applicable.
  • Product-to-recipe matching works correctly.
  • Unauthorized editing is restricted.
  • Transfer requests and completion states work correctly.
  • Partial or interrupted transfers are handled safely.
  • Invalid parameters are rejected.
  • The active recipe ID is confirmed by the control system.
  • The correct parameters are applied at the permitted operating stage.
  • Communication loss does not cause false success indications.
  • Restart and recovery behavior are defined and tested.
  • Revision tracking and backups are available where required.
  • Recipe changes are tested under approved commissioning procedures.
  • Traceability requirements are satisfied.

18. Interview Questions and Answers

Q1. What is an HMI recipe?

An HMI recipe is a predefined set of process parameters used to configure a machine for a particular product, variant, or operating condition.

Q2. Why are recipes used in manufacturing?

They reduce repeated manual entry, improve consistency, speed up changeovers, and support controlled product-variant management.

Q3. What is the difference between a recipe and a PLC program?

A recipe provides parameter values. The PLC program uses validated parameters to execute the machine sequence and control logic.

Q4. What is the difference between recipe selection and recipe application?

Selection identifies the desired recipe. Application occurs after the values have been transferred and accepted according to the machine's defined procedure.

Q5. Why should recipes be validated in the PLC?

The PLC must ensure that received values are valid and permitted before using them in control logic. HMI-side checks alone are insufficient.

Q6. What is a recipe buffer?

A recipe buffer is a temporary data area used to receive or prepare recipe values before validation and application.

Q7. Why are recipe revisions important?

They identify the approved configuration and help establish which parameter set was used for a particular production run.

Q8. What is a recipe handshake?

A defined exchange of request, busy, acceptance, rejection, and completion signals used to coordinate recipe transfer between systems.

Q9. Why might an HMI show a recipe as selected while the PLC uses different values?

The selected recipe may not have been transferred, the transfer may have failed, or the displayed recipe identifier may not reflect the PLC's confirmed active recipe.

Q10. How would you troubleshoot a recipe transfer failure?

Check the recipe ID, transfer request, communication state, parameter mapping, data types, validation results, PLC error codes, and completion handshake.

Q11. Can recipes be stored in SQL databases?

Yes. A database can store recipe definitions and revisions, provided that a correctly designed interface transfers, validates, and applies the required values to the control system.

Q12. What happens if a recipe transfer is interrupted?

The system should detect the incomplete transfer and avoid treating the recipe as successfully applied. The precise recovery behavior must be defined in the control design.

19. Practical Study Exercises

Use a simulator or an approved non-production training system.

  1. Create two sample recipes for different product variants.
  2. Define the data type, unit, minimum, and maximum for each parameter.
  3. Configure recipe selection and parameter display.
  4. Transfer recipe values into a PLC buffer.
  5. Implement a request and completion handshake.
  6. Add PLC-side parameter validation.
  7. Test a recipe containing an invalid parameter.
  8. Confirm that a rejected recipe does not falsely appear as active.
  9. Simulate communication loss during a transfer.
  10. Verify that the active recipe identifier matches the accepted parameter set.
  11. Test user permissions for selecting and editing recipes.
  12. Review how recipe revisions and backups are managed.
  13. Document the normal transfer sequence and failure behavior.
  14. Confirm that recipe changes are applied only under the intended machine-state conditions.

20. Final Mental Model

A recipe system follows this general sequence:

Product identified
       |
       v
Recipe selected
       |
       v
Parameters retrieved
       |
       v
Values transferred
       |
       v
PLC validates data
       |
   +---+---+
   |       |
 Reject  Accept
   |       |
   v       v
 Report   Apply at the
 failure  permitted stage
             |
             v
       Confirm active recipe
             |
             v
        Production process

The essential concepts are:

  • Recipe: A predefined collection of process parameters.
  • Recipe selection: Identifies the required configuration.
  • Recipe transfer: Moves the parameters to the receiving system.
  • Validation: Checks whether the values and recipe are acceptable.
  • Application: Makes the validated parameters active.
  • Versioning: Identifies the approved recipe revision.
  • Traceability: Records which recipe was applied and when, where required.

A reliable recipe system makes product changeovers repeatable and controlled while preventing incomplete, invalid, or incorrect parameter sets from silently affecting production.
