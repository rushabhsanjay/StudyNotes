1. Definition

HMI diagnostics is the process of displaying and investigating information about the operating condition, faults, communication status, and performance of a machine or industrial control system through the Human-Machine Interface (HMI).

Diagnostics helps maintenance engineers and operators identify:

  • Which device has a fault.
  • What condition caused the fault.
  • Whether a PLC, HMI, drive, robot, or remote I/O device is communicating.
  • Whether the machine is ready to operate.
  • Which interlock or permissive is preventing operation.
  • Whether a fault is active, cleared, or awaiting reset.
  • What happened before a machine stopped.

For example, if an automotive robotic station fails to start, the HMI should help distinguish between a robot fault, a missing clamp confirmation, a safety-related stop, a PLC communication failure, and a drive fault.

Main purpose: HMI diagnostics reduces fault-finding time by presenting useful technical information instead of forcing maintenance personnel to investigate every device blindly.

2. Why HMI Diagnostics Is Important

Without useful diagnostics, an HMI may display only a generic message such as:

MACHINE FAULT

That tells the operator almost nothing. The maintenance engineer still needs to determine which device failed, what condition was detected, and where to begin troubleshooting.

A properly designed diagnostic system can display:

  • Fault description.
  • Device or station identification.
  • Fault code.
  • Active or cleared status.
  • Date and time.
  • Relevant process state.
  • Communication status.
  • Interlock or permissive status.
  • Suggested inspection point.
  • Reset conditions, where appropriate.

The goal is not to replace technical troubleshooting. It is to narrow the search to the most likely cause and provide reliable evidence.

4. Main Types of HMI Diagnostics

4.1 Device Diagnostics

Shows the operating or fault status of individual devices.

Examples:

  • PLC CPU status.
  • Robot controller status.
  • VFD fault code.
  • Servo drive ready or fault status.
  • Remote I/O module fault.
  • Sensor or actuator status.
  • CNC controller alarm.

Example:

Device Status Diagnostic information
PLC RUN Controller executing normally
Robot controller FAULT Controller fault present
VFD READY Drive ready for operation
Remote I/O COMMUNICATION FAULT I/O connection unavailable
Clamp sensor OFF Clamp-closed signal not detected

These are illustrative states. Actual device status values and their meanings depend on the manufacturer and configuration.

4.2 Machine-State Diagnostics

Shows the current operating state of a machine or station.

Typical states include:

  • Power off.
  • Initializing.
  • Manual mode.
  • Automatic mode.
  • Ready.
  • Running.
  • Waiting.
  • Paused.
  • Faulted.
  • Recovering.
  • Maintenance mode.

Machine-state diagnostics help identify whether the machine is functioning normally or waiting for a specific condition.

For example, a station may be in WAITING because it has not received a part-present signal.

4.3 Interlock Diagnostics

An interlock prevents an operation when a defined condition is not satisfied.

Examples:

  • Clamp not confirmed closed.
  • Part not detected.
  • Robot not at the required position.
  • Conveyor not ready.
  • Fixture not in the required state.
  • Downstream station not ready.

A useful HMI should identify the specific condition preventing the operation.

Example:

AUTO START NOT PERMITTED

Required conditions:
  [OK] PLC in RUN mode
  [OK] Robot ready
  [OK] Part present
  [X] Clamp closed confirmation missing
  [OK] Downstream ready

This is much more useful than displaying only START INTERLOCK ACTIVE.

Important distinction: An interlock is a control condition that prevents an action. It is not necessarily a device fault. The machine may be healthy but waiting for a required condition.

Safety-related functions must be implemented and validated through the appropriate safety-rated architecture. An ordinary HMI indication does not establish that a safety function is effective.

4.4 Communication Diagnostics

Shows whether devices can exchange data correctly.

Examples include:

  • HMI to PLC communication.
  • PLC to remote I/O communication.
  • PLC to robot communication.
  • PLC to VFD communication.
  • SCADA to PLC communication.
  • Controller to database or industrial gateway communication.

Typical information includes:

  • Connected or disconnected state.
  • Communication timeout.
  • Data quality.
  • Last successful update.
  • Device response status.
  • Communication error code.
  • Connection state, where available.

A communication failure can cause displayed values to become stale or unavailable. A diagnostic screen should distinguish this from a real process condition.

4.5 I/O Diagnostics

Helps determine whether input and output signals are behaving as expected.

Examples:

  • Sensor input is ON or OFF.
  • Solenoid output command is ON.
  • Actuator feedback has been received.
  • Remote I/O module is healthy.
  • A signal is not changing within the expected time.

Consider a pneumatic clamp.

Signal Meaning Example state
Clamp_Close_CMD PLC requests clamp closing ON
Clamp_Closed_FB Sensor confirms clamp closed OFF
Clamp_Open_FB Sensor confirms clamp open OFF

If the close command is ON but the closed feedback remains OFF beyond the expected time, the diagnostic system can identify a clamp-closing timeout.

Possible causes include low air pressure, a mechanical obstruction, a failed sensor, a wiring problem, a solenoid issue, or a PLC/output fault.

The command signal alone does not prove that the actuator physically moved.

4.6 Controller and Program Diagnostics

Displays information related to the PLC, CNC, robot, or other programmable controller.

Depending on the platform, information may include:

  • CPU mode.
  • Controller fault status.
  • Program execution status.
  • Task or scan-time information.
  • Controller diagnostic buffer.
  • Module faults.
  • Program-specific fault codes.
  • Controller memory or resource warnings.

For example, Siemens controllers provide diagnostic-buffer information, while Rockwell Automation controllers provide controller and module fault information through their engineering environment.

An HMI may expose selected controller diagnostics, but it does not necessarily display every detail available in the programming software.

4.7 Performance Diagnostics

Shows whether the machine is meeting expected operational targets.

Examples:

  • Excessive cycle time.
  • Frequent station waiting.
  • Repeated actuator timeouts.
  • Increasing drive temperature.
  • High number of robot faults.
  • Repeated communication interruptions.

These diagnostics can help identify developing problems that may not immediately stop production.

5. Diagnostic Information Versus Alarms

Diagnostics and alarms are related, but they serve different purposes.

Feature Diagnostics Alarms
Primary purpose Investigate machine condition Notify users of an abnormal or important condition
Typical content Detailed device and signal status Fault or abnormal-condition notification
Example Clamp command ON, closed feedback OFF Clamp closing timeout
Main user action Investigate evidence and cause Recognize, respond, acknowledge, or clear as designed
Historical information Diagnostic logs or device records, if supported Alarm history and event records
Scope Can include normal states, interlocks, and faults Usually focuses on defined alarm conditions

An alarm might state:

FR1010: CLAMP CLOSING TIMEOUT

The diagnostic screen can provide the details:

  • Close command: ON.
  • Closed feedback: OFF.
  • Open feedback: OFF.
  • Timeout elapsed: 3.0 seconds.
  • Air pressure status: Normal, if a valid pressure signal is available.
  • PLC output status: ON, if the relevant status is available.

The alarm identifies the abnormal condition. Diagnostics helps investigate it.

6. Diagnostic Status Categories

A useful HMI can classify device or machine status into understandable categories.

Status Meaning
Normal No relevant fault detected
Warning Condition requires attention but may not stop operation
Fault A defined fault condition exists
Not ready One or more operating requirements are not satisfied
Interlocked An operation is prevented by a required condition
Communication lost Expected communication is unavailable
Unknown The state cannot be determined reliably
Stale data The displayed value has not updated within the defined period

The Unknown and Stale data states are important. A communication failure should not automatically make the HMI show a device as healthy merely because its last received status was normal.

Diagnostic displays should make data freshness and validity clear wherever they affect decisions.

7. Diagnostic Screen Design

A practical diagnostic system may use several screens rather than placing everything on one page.

7.1 Machine Overview

Displays the overall state of the machine or production line.

Typical information:

  • Machine mode.
  • Machine state.
  • Active fault count.
  • Station readiness.
  • Communication status.
  • Major equipment status.

7.2 Station Diagnostics

Shows the conditions for one station or machine section.

For an automotive robotic station, this could include:

  • Robot status.
  • Fixture and clamp status.
  • Part detection.
  • Conveyor state.
  • PLC sequence state.
  • Interlock summary.

7.3 I/O Diagnostics

Shows selected input and output states, often organized by device or functional group.

It should clearly distinguish an output command from the physical feedback confirming that the device responded.

7.4 Communication Diagnostics

Shows communication status between the PLC and connected equipment.

Depending on available data, it may include connection state, timeout information, device status, or last-update time.

7.5 Fault Details

Displays the cause and context of a specific fault.

Useful fields include:

  • Fault ID.
  • Fault description.
  • Station and device.
  • First-occurrence time.
  • Current state.
  • Relevant signal conditions.
  • Possible inspection points.
  • Required reset conditions.

7.6 Maintenance Diagnostics

Provides maintenance personnel with additional information such as:

  • Device identifiers.
  • I/O addresses or PLC tags.
  • Drive fault codes.
  • Sensor state.
  • Equipment-specific diagnostic details.
  • Relevant maintenance instructions.

Sensitive controls and configuration functions should remain restricted to authorized users.

8. Designing Useful Diagnostic Messages

Diagnostic messages should describe the condition precisely.

Poor message:

ROBOT ERROR

Better message:

FR1010: ROBOT CONTROLLER FAULT ACTIVE

More useful diagnostic detail, when available:

Station: FR1010
Device: Robot controller
Status: Fault active
Controller fault code: [actual device code]
Machine state: Automatic sequence stopped
Action: Inspect the robot controller diagnostic display

Do not invent fault codes or imply that a suspected cause has been confirmed.

A good diagnostic message should answer three questions:

  1. What is abnormal?
  2. Where is the problem?
  3. What information or inspection will help locate the cause?

For complex faults, the HMI may provide a list of possible causes rather than claiming a single root cause.

9. Diagnostic Tags and Data Structure

Diagnostic information is often built from PLC tags, device status words, communication status, and calculated conditions.

Example tag structure:

Tag Purpose
Machine_State Current machine state
Station_Ready Indicates whether defined readiness conditions are satisfied
Station_Faulted Indicates that a defined station fault is active
Robot_Ready Robot readiness status
Robot_Faulted Robot fault status
Clamp_Close_CMD Clamp-closing command
Clamp_Closed_FB Clamp-closed feedback
PLC_Comm_OK PLC communication status
Robot_Comm_OK Robot communication status
Diagnostic_Error_Code Diagnostic code, if provided
Diagnostic_Update_Time Time of the most recent valid update, if implemented

The exact names are examples, not universal tag standards.

Command, feedback, and diagnostic result

These should not be confused.

  • Command: What the control system requests.
  • Feedback: What a sensor or device reports.
  • Diagnostic result: What the control logic concludes from relevant evidence.

For example:

Clamp_Close_CMD = ON
Clamp_Closed_FB = OFF
Timeout_Expired = TRUE

Together, these conditions may establish a clamp-closing timeout, assuming the sequence and signal validity checks support that conclusion.

10. Diagnostic Logic Example: Clamp Closing Timeout

Suppose a PLC commands a clamp to close and expects a closed-position sensor to activate within a defined period.

Conceptually:

Close command issued
        |
        v
Start timeout monitoring
        |
        v
Closed feedback received?
        |
    +---+---+
    |       |
   Yes      No
    |       |
    v       v
Stop timer  Timeout elapsed?
                |
            +---+---+
            |       |
           No      Yes
            |       |
            v       v
        Continue   Set diagnostic
        monitoring fault condition

This is a conceptual example, not ready-to-deploy safety or machine-control code.

A real implementation must define signal validity, expected operating states, timer behavior, recovery conditions, and the response to a detected fault.

The diagnostic message might be:

CLAMP CLOSING TIMEOUT: CLOSED FEEDBACK NOT RECEIVED

The HMI should then show the relevant command, feedback, and available supporting information.

11. Diagnostic Logic Example: Communication Failure

Suppose an HMI receives data from a PLC over an industrial network.

A robust display should distinguish between:

  • Valid and current data.
  • A communication error.
  • A stale value retained from the last successful update.
  • An unknown state.

Conceptually:

PLC data received and valid?
          |
      +---+---+
      |       |
     Yes      No
      |       |
      v       v
Update      Show communication
display     fault / unknown state
      |
      v
Track data freshness

The exact implementation depends on the HMI driver and communication interface.

A last-known value may still be useful for troubleshooting, but it must not be presented as a confirmed current condition when its freshness cannot be established.

12. Troubleshooting with HMI Diagnostics

Consider a station that refuses to enter automatic operation.

A systematic approach is more effective than randomly resetting devices.

Step 1: Check the overall machine state

Determine whether the station is stopped, waiting, faulted, or not ready.

Step 2: Review active alarms

Identify the current alarms and distinguish them from old, cleared events.

Step 3: Inspect interlocks and permissives

Find the exact condition preventing automatic operation.

Examples include missing part detection, clamp feedback, robot readiness, or downstream availability.

Step 4: Check command and feedback signals

If the PLC commands an actuator but the feedback does not change, investigate the signal path and physical device.

Step 5: Check device diagnostics

Inspect available drive, robot, CNC, remote I/O, or controller fault information.

Step 6: Verify communication

Confirm that displayed device statuses are current and that relevant PLC-to-device connections are healthy.

Step 7: Check sequence and timing information

Determine whether the machine is waiting for a condition or whether a defined timeout has expired.

Step 8: Verify the physical condition

Use approved procedures to inspect the relevant sensor, actuator, wiring, supply, mechanical condition, or device diagnostic information.

Step 9: Correct the cause and verify recovery

After the fault has been corrected, follow the machine's documented recovery and reset procedure.

Do not treat repeated resetting as troubleshooting. A reset may clear a symptom without removing the underlying fault.

Safety devices must not be bypassed to make the machine run. Follow the site's approved isolation, lockout/tagout, and safety procedures when physical intervention is required.

13. Common Diagnostic Problems

Symptom Possible cause What to check
HMI shows a device as healthy when it is disconnected Last-known value retained or communication status not linked correctly Data quality, connection state, and update freshness
Every device appears faulted simultaneously Shared communication or power problem PLC state, network, power supplies, and common modules
Interlock message is too generic Insufficient diagnostic detail Individual permissive conditions and message design
Fault clears but immediately returns Root cause remains present Physical condition, sequence logic, and fault-trigger conditions
Device fault code is missing Fault-code mapping or interface issue Controller tags, device data mapping, and driver support
I/O state does not match the physical device Sensor, wiring, mapping, module, or feedback problem Signal path from field device to displayed tag
Diagnostic screen updates slowly Polling interval, network load, controller scan, or display refresh End-to-end update behavior
Historical fault information is unavailable Logging not implemented or retention insufficient Alarm history, diagnostic logs, and storage configuration
HMI shows a stale robot status Robot communication loss or outdated data Robot connection, update timestamps, and quality state

14. Diagnostic Response and Recovery

A diagnostic system should distinguish between detecting a problem and recovering from it.

A typical sequence is:

  1. Detect the abnormal condition.
  2. Record or identify the fault.
  3. Present the diagnostic information.
  4. Stop or inhibit the affected operation as defined by the control design.
  5. Allow maintenance personnel to investigate.
  6. Correct the underlying cause.
  7. Verify that the required conditions have returned.
  8. Perform the approved reset or recovery procedure.
  9. Confirm that the equipment is ready before restarting.

The exact sequence depends on the equipment and fault category.

Not every diagnostic condition requires the entire machine to stop. Some warnings can permit continued operation, while other faults require an immediate controlled response. Safety-related responses must be designed and validated independently of ordinary HMI messaging.

15. Diagnostic Data and Maintenance Improvement

Diagnostic data becomes more valuable when it is retained and analyzed.

Useful measures include:

  • Most frequent faults.
  • Repeated faults by station.
  • Average fault duration.
  • Time between recurring faults.
  • Communication interruptions.
  • Repeated actuator timeouts.
  • Fault recurrence after reset.
  • Production downtime associated with faults.

For example, if a clamp timeout occurs repeatedly on the same station, the problem may involve the actuator, sensor alignment, air supply, wiring, or sequence timing.

Historical data helps identify patterns, but it does not prove the root cause by itself. Maintenance findings and physical verification remain necessary.

A useful architecture may connect PLC diagnostic tags to an HMI, SCADA system, database, or maintenance reporting system. Logging and retention must be configured rather than assumed to exist automatically.

16. HMI Diagnostics Versus PLC Diagnostics Software

Feature HMI diagnostics PLC engineering diagnostics
Main audience Operators and maintenance personnel Controls engineers and advanced maintenance personnel
Main purpose Present machine and device conditions Investigate controller, program, and module behavior
Typical information Interlocks, device status, fault messages Diagnostic buffers, module status, program details, controller faults
Access Available through the configured HMI interface Usually requires engineering software and suitable access
Detail level Selected and organized for the application Often more extensive and platform-specific
Use during troubleshooting Rapid initial investigation Deeper controller-level investigation

For example, an HMI might show REMOTE I/O COMMUNICATION FAULT, while the PLC engineering software reveals the specific module or connection diagnostic.

Both are useful, but they serve different purposes.

17. HMI Diagnostics Versus PLC Communication

Diagnostics and communication are closely related but not identical.

  • Diagnostics is the broader function of identifying and presenting equipment or process conditions.
  • PLC communication is the exchange of data between the PLC and other devices or systems.

Communication status is one important part of diagnostics. However, a machine can have healthy communication and still have a mechanical fault, failed sensor, incorrect sequence condition, or process abnormality.

Conversely, a communication failure can prevent the HMI from receiving the information needed to diagnose a remote device.

This distinction leads directly to the next study topic.

18. Interview Questions and Answers

Q1. What is HMI diagnostics?

HMI diagnostics presents machine, device, controller, and communication status so users can identify and investigate abnormal conditions.

Q2. What is the difference between an alarm and a diagnostic message?

An alarm notifies the user of a defined abnormal or important condition. Diagnostic information provides details that help identify and investigate the cause.

Q3. What is an interlock?

An interlock is a control condition that prevents an operation when a required condition is not satisfied.

Q4. What is the difference between a command and feedback?

A command represents the requested action. Feedback represents the reported condition or result. A command does not prove that the physical action occurred.

Q5. Why should communication status be displayed separately?

Because missing or stale data must not be mistaken for a confirmed healthy device state.

Q6. What should a useful diagnostic message contain?

A clear description, affected station or device, fault status, relevant code where available, and useful inspection information.

Q7. Why does a fault return immediately after reset?

The underlying condition may still exist, or the triggering logic may immediately detect it again.

Q8. How can HMI diagnostics reduce downtime?

It narrows the investigation by identifying the affected device, missing condition, fault code, or communication problem.

Q9. Does an HMI diagnostic indication implement a safety function?

No. An ordinary HMI indication does not replace an appropriately designed and validated safety-rated control system.

Q10. What is stale diagnostic data?

Data that has not been refreshed within the defined period and therefore may no longer represent the device's current condition.

Q11. Can an HMI display PLC module faults?

Yes, when the controller exposes the required information and the HMI project is configured to retrieve and display it.

Q12. What is the first step when a machine will not start in automatic mode?

Check the machine state, active faults, and required interlocks or permissives to identify the condition preventing operation.

19. Practical Exercises

Use an approved simulator or non-production training setup.

  1. Create a diagnostic screen showing PLC, robot, drive, and remote I/O status.
  2. Display machine mode and operating state.
  3. Create a list of individual start permissives.
  4. Display command and feedback signals for a simulated clamp.
  5. Implement a simulated timeout diagnostic.
  6. Display a communication fault separately from a device fault.
  7. Simulate stale data and show an appropriate unknown or communication-error state.
  8. Add a fault code and descriptive message.
  9. Create a diagnostic view that distinguishes active faults from cleared events.
  10. Test whether a reset is available only when the configured reset conditions are met.
  11. Document the troubleshooting sequence for one simulated station fault.
  12. If logging is available, review repeated faults and calculate which faults consume the most downtime.

20. Final Mental Model

HMI diagnostics connects the machine's actual reported conditions to information that operators and maintenance personnel can understand.

Remember these distinctions:

  • Alarm: Identifies an abnormal or important condition.
  • Diagnostic: Provides information for investigation.
  • Interlock: Prevents an operation when a required condition is not satisfied.
  • Command: Indicates what the control system requests.
  • Feedback: Indicates what the device or sensor reports.
  • Communication status: Indicates whether data exchange is working as expected.
  • Root cause: The underlying reason the problem occurred, which must be established through evidence.
