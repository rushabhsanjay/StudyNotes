RFID PLC Read/Write: Data Exchange and Errors

1. Purpose and Scope

In industrial automation, an RFID reader identifies tags and exchanges data with a PLC or controller so that the machine can make process decisions. Typical applications include carrier identification, workpiece tracking, tool identification, recipe selection, traceability, and product verification.

The complete system involves more than reading a tag. The PLC must issue the correct command, manage communication timing, detect completion, validate the returned data, handle errors, and prevent stale or incorrect identification data from affecting the process.

This topic covers:

  • RFID reader-to-PLC communication architectures.
  • Read and write operations.
  • Data formats, memory banks, and identifier handling.
  • Handshakes, triggers, status bits, and timeouts.
  • Error detection, recovery, and troubleshooting.
  • PLC integration practices for industrial production systems.

2. Overall Architecture

A typical RFID identification station contains the reader, antenna, tag, PLC, and machine-control logic.

RFID Tag
   ↕ RF communication
RFID Antenna
   ↕ RF connection
RFID Reader
   ↕ Industrial network or I/O
PLC
   ↓
Machine Sequence / HMI / Traceability System

The reader manages the RFID air interface. The PLC manages the machine sequence and decides what to do with the returned data.

The exact division of responsibilities depends on the reader. Some readers provide high-level commands and structured data, while others expose lower-level communication or require manufacturer-specific function blocks.

3. Reader-to-PLC Communication Methods

Communication method Typical use Main considerations
PROFINET Integration with Siemens and compatible PLC systems Device name, IP configuration, GSDML, cyclic and acyclic data
EtherNet/IP Integration with Allen-Bradley and compatible PLC systems EDS or device configuration, assemblies, connection settings, data mapping
Modbus TCP Register-based data exchange where supported Register mapping, data types, byte order, polling and timeouts
TCP/IP socket Custom or vendor-defined message exchange Message framing, parsing, connection handling, response validation
Digital I/O Simple trigger and status exchange Limited data capacity, timing, and separate data channel if needed
Vendor-specific function blocks Simplified read/write commands and status management Library version, supported reader models, error-code interpretation

Not every reader supports every method. The reader's communication manual defines the supported protocols and the meaning of each data field.

3.1 Cyclic and Acyclic Data

Cyclic data is exchanged repeatedly at configured intervals. It commonly carries control words, status words, commands, and a fixed-size data area.

Acyclic data is transferred on demand or through an explicit request. It is commonly used for parameter access, configuration, diagnostics, or operations that do not fit the cyclic data structure.

A reader may use cyclic communication for control and status while performing a read or write through a command interface. The exact implementation varies by manufacturer.

4. RFID Read and Write Operations

4.1 Read Operation

A read operation retrieves information from a tag or requests identification from the reader's inventory process.

A typical sequence is:

  1. The PLC confirms that the target object is in the identification position.
  2. The PLC checks that the reader is ready.
  3. The PLC issues a read command or trigger.
  4. The reader communicates with the tag.
  5. The reader returns the identifier and any requested data.
  6. The PLC checks completion and error status.
  7. The PLC validates the data before allowing the process to continue.

The returned identifier may be an EPC, UID, or another protocol-specific identifier. These terms are not interchangeable across all RFID technologies.

4.2 Write Operation

A write operation changes writable memory on a tag. It may write a product identifier, batch number, process state, or other application data.

A typical write sequence is:

  1. The PLC verifies that the correct tag is present.
  2. The PLC prepares the data and selects the required memory location.
  3. The PLC checks reader readiness and tag compatibility.
  4. The PLC issues the write command.
  5. The reader attempts to write the data to the tag.
  6. The reader returns completion or error status.
  7. The PLC performs read-back verification when supported and required.
  8. The PLC records the result and permits the next process step only after successful validation.

Important: A successful communication transaction does not necessarily prove that the intended data was written correctly. Use read-back verification or another documented verification method for critical data.

4.3 Read vs Write

Feature Read Write
Primary purpose Retrieve identification or stored data Modify writable tag memory
Main risk Wrong, missing, stale, or misinterpreted data Incorrect data, wrong memory address, incomplete or unauthorized update
Common failure Tag not detected or data unavailable Memory locked, unsupported memory, insufficient access rights, or write failure
Verification Validate identifier, length, format, and expected value Check command result and verify written data
Process control Confirm correct object identification Confirm correct target tag and successful data update

Read and write commands must be matched to the tag technology, supported memory structure, and reader interface.

5. RFID Tag Memory and Data Structure

RFID memory organization depends on the tag technology and protocol. Do not assume all tags have the same memory layout.

5.1 Common UHF EPC Memory Banks

For passive UHF RFID tags that follow the EPC Gen2 family of standards, memory is commonly organized into these banks:

Memory bank General purpose PLC application consideration
Reserved May contain access and kill passwords Handle credentials securely and follow the tag and reader documentation
EPC Stores the EPC identifier and related control information Verify the expected EPC length and encoding
TID Contains tag-identification information, often including manufacturer or chip details Useful for distinguishing tag hardware where supported
User Optional application memory Capacity, availability, and writability depend on the tag

Not every tag implements every bank or provides the same memory capacity. Memory layout and access behavior must be checked in the tag datasheet.

LF and HF tags can have entirely different memory structures and command sets. The UHF memory-bank model should not be applied to every RFID technology.

5.2 Identifier vs Application Data

An identifier identifies a tag or associated object. Application data stores information used by the production process.

For example:

  • Tag identifier: E200341201234567890ABCDE
  • Product code: PART-1042
  • Batch number: BATCH-26015
  • Process state: INSPECTED

These are illustrative values. The tag identifier may be manufacturer-assigned or application-managed, depending on the system.

A common design is to use a stable tag identifier as the key and maintain detailed production information in a database. Storing an entire product history on a tag is not automatically better: memory capacity, write endurance, security, synchronization, and data consistency all matter.

5.3 Data Representation

The reader may return tag data as:

  • Hexadecimal text.
  • ASCII or another character encoding.
  • Raw bytes.
  • A fixed-length byte array.
  • Protocol-specific structures.
  • Registers or cyclic input/output fields.

For example, the hexadecimal byte sequence 41 42 43 31 represents the ASCII characters ABC1.

A PLC must know whether a field contains a number, a byte array, a string, or a hexadecimal representation. Treating a hexadecimal string as ordinary decimal text can produce incorrect identifiers.

5.4 Byte Order and Data Length

When data crosses a PLC communication interface, the reader and PLC must agree on:

  • Byte order.
  • Word order, if applicable.
  • String encoding.
  • Data length.
  • Padding and unused bytes.
  • Whether a length field counts bytes, words, or characters.
  • Whether the reader returns the entire tag memory or only the requested section.

Do not remove leading zeros from identifiers unless the application specification explicitly requires it. 00012345 and 12345 may be different identifiers in a traceability system.

6. Read/Write Handshake Design

A handshake coordinates the PLC and reader so that commands are not missed, repeated unintentionally, or processed before the data is valid.

Typical signals or fields include:

Signal or field Typical meaning
Reader_Ready Reader can accept a command
Read_Request PLC requests a read operation
Write_Request PLC requests a write operation
Busy Operation is in progress
Done Operation has completed
Error Operation failed
Error_Code Identifies the reported failure
Data_Valid Returned data has been made available according to the interface definition
Tag_Data Identifier or requested tag data
Data_Length Number of valid bytes or another defined length unit

These names are illustrative. The actual reader may use different signals or combine several functions into one status word.

6.1 Recommended State-Based Sequence

IDLE
  ↓
Check Reader Ready
  ↓
Prepare Command and Data
  ↓
Issue Request
  ↓
Wait for Busy / Completion
  ↓
Check Done and Error
  ↓
Validate Returned Data
  ↓
Accept Result or Raise Fault
  ↓
Reset Request and Return to IDLE

A state machine is generally easier to diagnose than a collection of loosely related bits, especially when several readers or operations exist in the same machine.

6.2 Why Request Reset Matters

Some readers detect a rising edge of a request bit. Others require the request to remain asserted until acknowledgement or completion. Some function blocks manage the handshake internally.

If the PLC holds a request high indefinitely, the reader may repeat the operation or refuse the next command, depending on its interface.

The implementation must follow the manufacturer's handshake specification. Do not assume that every reader uses a rising-edge trigger.

6.3 Preventing Duplicate Commands

A robust design should:

  • Generate one command for one intended process event.
  • Avoid starting a second command while the first is active.
  • Clear or acknowledge completion according to the interface definition.
  • Prevent a held trigger from creating repeated writes.
  • Use a transaction state or sequence number if the interface supports it.
  • Ensure a reader restart does not accidentally reuse an old request.

For a write operation, duplicate execution may be harmless when writing the same value, but it can be dangerous if the operation changes process state, writes a counter, or targets the wrong tag.

7. PLC Data Exchange Example

Consider a production station that reads a carrier ID before machining.

Illustrative tag data:

Reader status: DONE
Read result:   SUCCESS
Tag ID:        CARRIER_1042
Data length:   12 characters

The PLC should not simply check whether DONE is true. It should also confirm that:

  • The operation corresponds to the current request.
  • The reader reported success.
  • The returned data is valid and complete.
  • The identifier format is correct.
  • The identifier matches the expected process context.
  • The result has not been carried over from an earlier carrier.

If the reader reports success but returns an unexpected carrier ID, the correct response is a process-validation fault, not an automatic continuation.

7.1 Example of a Result Validation Table

Reader result Data validation PLC response
Success Valid expected ID Accept identification and continue according to the machine sequence
Success Unexpected ID Reject identification and raise a traceability or process fault
Success Empty or malformed data Reject data and raise a data-validation fault
No tag No valid identifier Apply the defined timeout or no-tag handling sequence
Reader error Error code present Record the code and execute the configured recovery
Communication lost Reader status unavailable Block the dependent operation according to the risk assessment

8. PLC Read/Write Errors

RFID errors can originate in several layers. Correct troubleshooting begins by identifying which layer failed.

8.1 Error Categories

Error category Examples Diagnostic focus
RF communication Tag not detected, weak response, interference Antenna, tag, orientation, distance, RF settings
Tag memory Locked memory, invalid address, unsupported bank Tag specifications, permissions, address and length
Reader command Invalid command, wrong parameters, operation not supported Command format and reader manual
Network communication Timeout, disconnected device, connection fault Network, device configuration, communication diagnostics
PLC logic Request stuck, incorrect state transition, repeated command Handshake and state-machine logic
Data handling Incorrect byte order, truncated string, wrong encoding Mapping, length, parsing, data types
Process validation Wrong carrier, duplicate result, stale data Expected identifier, trigger context, transaction control
Configuration Wrong protocol, incorrect reader settings, firmware mismatch Approved configuration and compatibility

8.2 No Tag Detected

Possible causes:

  • Tag is absent or incompatible.
  • Tag is outside the read zone.
  • Antenna cable is disconnected or damaged.
  • Antenna placement or polarization is unsuitable.
  • The tag is mounted on metal without a suitable design.
  • RF power or inventory configuration is incorrect.
  • The reader is not executing the requested inventory operation.

Recommended diagnosis:

  1. Confirm reader communication and ready status.
  2. Verify tag frequency and protocol compatibility.
  3. Test with a known-good tag of the correct type.
  4. Check antenna port, cable, and mounting.
  5. Test with the real tag at a controlled distance.
  6. Review reader diagnostics before changing power or timing.

8.3 Read Timeout

A timeout occurs when the PLC or communication layer does not receive the expected result within the configured time.

Possible causes:

  • No tag is present.
  • The tag is difficult to read.
  • Reader inventory time is longer than expected.
  • Network response is delayed or unavailable.
  • The PLC handshake is incorrect.
  • The timeout is too short for the actual operation.

The timeout should be based on measured worst-case operating time with an appropriate margin. Increasing it blindly can hide a real fault and extend machine downtime.

8.4 Write Failure

Possible causes:

  • Tag memory is locked or protected.
  • The selected memory bank is not writable.
  • The requested address or data length is invalid.
  • The tag moves out of the read zone during the write.
  • The reader does not support the requested operation.
  • Access credentials or write permissions are incorrect.
  • RF communication is unstable.

A correct recovery sequence should identify the failed operation, preserve the intended data, avoid writing to an unverified tag, and perform verification before reporting success.

8.5 Wrong or Corrupted Data

Possible causes include:

  • Byte or word order mismatch.
  • Incorrect data-length interpretation.
  • String truncation.
  • Padding bytes included in the identifier.
  • Hexadecimal text interpreted as another data type.
  • PLC variables not refreshed after a new transaction.
  • Stale data retained after a failed read.

A useful practice is to clear or invalidate the previous result at the start of a new transaction, according to the reader interface. Only mark the new data valid after a successful operation and validation.

9. Timeout, Retry, and Recovery Strategy

Retries can improve reliability, but uncontrolled retries can cause duplicate operations, extended cycle times, and hidden faults.

9.1 Recommended Recovery Policy

Condition Recommended handling
No tag detected Retry within the allowed cycle-time budget, then report a no-tag fault
Temporary communication timeout Check communication status and retry according to the device's recovery procedure
Invalid command or parameter Correct the command configuration instead of repeatedly retrying
Memory locked or write access denied Report a write-permission fault and require the defined corrective action
Data validation failure Reject the result and prevent the dependent process step
Reader offline Execute the defined communication-loss response and recover the connection before restarting
Repeated failures Record diagnostics and escalate instead of retrying indefinitely

9.2 Retry Counter

A PLC can maintain a retry counter for an operation.

Illustrative logic:

Start operation
    ↓
Wait for completion
    ↓
Success?
  ├─ Yes → Validate data → Accept result
  └─ No  → Retry limit reached?
                ├─ No → Retry operation
                └─ Yes → Set fault and stop dependent sequence

The retry count and timing must be selected from actual cycle-time requirements and device behavior. The diagram is conceptual, not a universal reader protocol.

9.3 Idempotency and Write Recovery

An operation is idempotent when repeating it produces the same intended final state as executing it once.

For example, writing the fixed value PART-1042 to a specified memory location may be idempotent if the target tag and address are confirmed.

Incrementing a counter or writing a new process state may not be idempotent. Retrying such an operation without checking its previous result can create inconsistent data.

For important writes:

  1. Confirm the identity of the target tag.
  2. Record the intended data and transaction state.
  3. Execute the write.
  4. Check the operation result.
  5. Read back and compare the data when supported and required.
  6. Record the verified outcome.
  7. If communication fails during the write, determine the tag's actual state before repeating the operation.

10. Example PLC State Machine

The following pseudocode illustrates the control structure. It is not directly executable PLC code because reader-specific commands, data types, and handshake behavior differ.

STATE_IDLE:
    Invalidate previous result
    Wait for identification request
    If request and reader ready:
        Prepare read command
        Start timer
        STATE_READ

STATE_READ:
    Wait for reader completion
    If success:
        Validate data length and identifier
        If valid:
            Store identifier
            Set result valid
            STATE_DONE
        Else:
            STATE_DATA_ERROR
    Else if reader error:
        STATE_RETRY_OR_ERROR
    Else if timeout:
        STATE_RETRY_OR_ERROR

STATE_RETRY_OR_ERROR:
    If retry count below limit:
        Increment retry count
        Reset command according to reader protocol
        STATE_READ
    Else:
        Set identification fault
        STATE_ERROR

STATE_DONE:
    Publish validated result
    Wait for request acknowledgement or next transaction
    STATE_IDLE

STATE_DATA_ERROR:
    Record validation fault
    STATE_ERROR

STATE_ERROR:
    Preserve diagnostic information
    Require the defined recovery condition
    Return to STATE_IDLE only when recovery is complete

10.1 State-Machine Design Rules

  • Define the exact entry and exit conditions for every state.
  • Ensure each operation has a defined timeout.
  • Reset timers and retry counters at the correct transition.
  • Do not use a previous transaction's Done bit as proof that a new command completed.
  • Preserve the error code long enough for diagnostics.
  • Keep raw reader status separate from application-level success.
  • Ensure that clearing a fault does not automatically authorize an unsafe machine movement or invalid production step.

11. Siemens and Allen-Bradley PLC Integration

The communication principles are similar across PLC platforms, but the implementation details differ.

11.1 Siemens PLCs

For Siemens systems, integration may involve PROFINET cyclic data, acyclic services, TCP communication, or a manufacturer-specific library.

Typical engineering checks:

  • Correct reader device name and IP configuration.
  • Correct hardware configuration and device description.
  • Input and output addresses mapped correctly.
  • Correct interpretation of status and command words.
  • Correct byte-array and string handling.
  • Correct timeout and diagnostic behavior.
  • Compatible function-block and reader firmware versions.

In TIA Portal, monitor the mapped input and output data while testing the reader handshake. Verify that the observed data matches the communication manual before modifying PLC logic.

11.2 Allen-Bradley PLCs

For Allen-Bradley systems, integration may use EtherNet/IP assemblies, explicit messaging, TCP communication, or vendor-specific instructions.

Typical engineering checks:

  • Correct reader IP address and device configuration.
  • Correct input and output assembly sizes and mappings.
  • Correct data types and offsets.
  • Correct command and status bit definitions.
  • Correct connection status and fault handling.
  • Correct interpretation of returned byte arrays and strings.
  • Correct timeout and retry implementation.

In Studio 5000, inspect the reader's mapped input and output data while performing a controlled read. Confirm the assembly mapping and status interpretation before changing the logic.

11.3 Platform-Independent Principle

Do not copy a function block, data structure, or bit mapping from another reader without checking compatibility. Similar-looking devices can use different command sequences, data layouts, and completion semantics.

12. Commissioning and Validation Checklist

Hardware and Communication

  • Reader and tag frequency and protocol are compatible.
  • Antenna and RF connections are correct.
  • Reader is reachable over the configured interface.
  • PLC hardware and network configuration are correct.
  • Cyclic or command data mapping matches the documentation.
  • Reader status and error diagnostics are available.

Read Operation

  • Valid tag is read successfully.
  • Missing tag is handled correctly.
  • Unexpected tag is rejected.
  • Invalid or incomplete data is rejected.
  • Previous tag data cannot be mistaken for a fresh result.
  • Read timeout and retry behavior are verified.
  • Actual cycle time meets process requirements.

Write Operation

  • Correct target tag is confirmed.
  • Correct memory bank, address, and length are configured.
  • Writable memory and access permissions are confirmed.
  • Write success and failure are handled correctly.
  • Read-back verification is completed where required.
  • Interrupted or uncertain writes have a defined recovery procedure.

Recovery and Documentation

  • Network disconnection and reconnection are tested.
  • Reader restart behavior is verified.
  • Repeated requests do not create unintended operations.
  • Error codes and recovery steps are documented.
  • Reader configuration and PLC program versions are backed up.
  • Production acceptance criteria are recorded.

13. Safety, Traceability, and Data Integrity

RFID data may determine which product is machined, which recipe is selected, or whether a traceability record is created. Incorrect data can therefore cause quality and production problems.

  • Never assume that reader communication status proves the correct product has been identified.
  • Validate the identifier against the current carrier or process context.
  • Do not reuse stale data after a failed transaction.
  • Do not write to a tag until the target and memory location are confirmed.
  • Protect credentials and restricted tag-memory operations.
  • Define the machine response to missing, invalid, or conflicting identification.
  • Maintain independent safety functions where required. Ordinary RFID identification is not automatically a safety-rated function.
  • Record relevant faults and transaction outcomes for troubleshooting and traceability.

For critical applications, consider whether the RFID system alone provides adequate identification assurance or whether independent checks are required.

14. Interview Questions and Answers

1. What is the difference between an RFID read and a write command?

A read retrieves identification or stored data from a tag. A write modifies writable memory on a tag, subject to its memory layout and access permissions.

2. Why is a handshake required between the PLC and reader?

It coordinates commands, operation status, completion, and error handling so that the PLC does not process incomplete results or issue unintended repeated commands.

3. What is the difference between reader-ready and operation-done?

Reader-ready indicates that the device can accept an operation according to its interface. Operation-done indicates that a particular operation has completed. The exact meanings must be confirmed in the reader documentation.

4. Why can a reader report success while the machine still has a data error?

The RF transaction may have succeeded, but the returned identifier may be malformed, unexpected, stale, or inconsistent with the current production context.

5. What causes an RFID write failure?

Possible causes include protected memory, an invalid address or length, unsupported commands, incorrect access credentials, an incompatible tag, or unstable RF communication.

6. Why is a timeout necessary?

It prevents the PLC from waiting indefinitely when the reader or tag does not return the expected result.

7. Why should retries be limited?

Unlimited retries can stall the machine, hide recurring faults, and exceed the process cycle time. Some operations may also cause unwanted effects if repeated.

8. What is stale data in an RFID application?

Stale data is information from an earlier transaction that is mistakenly treated as the result of the current transaction.

9. Why is read-back verification useful after writing a tag?

It confirms that the intended data is present in the target memory location, subject to the reader and tag's supported verification method.

10. How would you diagnose a reader that works in its configuration software but not through the PLC?

Check the PLC interface configuration, device connection, command/status mapping, handshake timing, data format, and timeout behavior. First establish whether the reader detects the tag, then determine where the result stops reaching or being accepted by the PLC.

11. What is the difference between an RF error and a communication error?

An RF error concerns communication between reader and tag. A communication error concerns data exchange between the reader and PLC or application. The two may occur independently.

12. What should happen if the PLC loses communication during a write?

The PLC should report an uncertain transaction, establish communication again, verify the actual tag state where possible, and only then decide whether the write should be repeated.

15. Practical Exercises

Exercise 1: Map the Reader Interface

Using the documentation for an available reader, list the command fields, status fields, input/output data sizes, completion signals, and error codes. Compare these with the PLC tags or data structures.

Exercise 2: Test Read Handshake

Create a test sequence that reads a known tag, records the returned identifier, and distinguishes success, no-tag, timeout, and invalid-data conditions.

Exercise 3: Test Error Recovery

Simulate a missing tag and a communication interruption using the equipment's approved test procedure. Verify that the PLC does not wait indefinitely, accept stale data, or continue an identification-dependent operation incorrectly.

Exercise 4: Test Write Verification

On a designated test tag, write a permitted test value to a documented writable memory location. Check the reader result, read back the value, compare it with the intended data, and record the outcome. Do not modify production tags without authorization.

Exercise 5: Build a Fault Record

For each failure, record the timestamp, operation type, reader status, error code, retry count, tag identifier if valid, PLC state, and recovery action. Ensure that invalid identifiers are not logged as verified production data.

16. Final Mental Model

  • The RFID reader handles communication with tags and reports results.
  • The PLC interface exchanges commands, status, and data with the reader.
  • The handshake coordinates operation timing and completion.
  • The data-validation layer checks identifiers, lengths, formats, and process context.
  • The error-handling layer manages timeouts, retries, communication loss, and uncertain writes.
  • The traceability layer records verified outcomes and relevant diagnostic information.

A reliable RFID integration is not simply one that reads a tag. It must identify the correct tag, exchange the required data, prove that the transaction completed, handle failure predictably, and prevent invalid information from reaching the production process.
