1. Purpose and Scope

A PLC/robot link in a machine-vision system connects inspection decisions and measured positions to the machine sequence. The PLC coordinates the production cycle, the vision system acquires and evaluates images, and the robot performs the required movement or handling operation.

The link must do more than transfer a PASS or FAIL bit. It must ensure that the result belongs to the correct part, the correct inspection request, and the correct recipe, and that the result is valid before any action is taken.

Typical applications include:

  • Presence and orientation checks before robot handling.
  • Checking weld nuts, clips, holes, pins, and other assembly features.
  • Robot pick-and-place using vision-derived coordinates.
  • Verifying part identity and assembly correctness.
  • Rejecting defective components on a conveyor.
  • Measuring position, angle, dimensions, and feature offsets.
  • Sending inspection results to traceability systems.

The central engineering problem is synchronization: the camera, PLC, robot, conveyor, and communications network operate on different timing cycles. A correct result arriving at the wrong time can be just as dangerous to quality as an incorrect result.

2. System Architecture

A common architecture uses the PLC as the sequence coordinator while the vision controller performs image processing.

Part / Fixture / Conveyor
          ↓
      Photoelectric Sensor
          ↓
         PLC
          ↓ Trigger / Request
    Vision Controller
          ↓
 Camera + Lens + Lighting
          ↓
 Image Processing and Inspection
          ↓
 Result / Measurements / Coordinates
          ↓
         PLC
          ↓
   Robot or Machine Sequence
          ↓
 Move / Pick / Place / Reject
          ↓
 Result Logging / Traceability

The actual communication path depends on the equipment. A camera may connect directly to a PLC, a vision controller may communicate with both PLC and robot, or the robot controller may request vision results directly while the PLC supervises the overall sequence.

Component Primary responsibility Typical information
Sensor Detects part or capture position Part present, trigger event
PLC Coordinates machine sequence Request, busy state, result acceptance
Vision controller Executes inspection job Job status, inspection result, measurements
Camera Captures image Image data
Robot controller Executes robot program Robot ready, capture pose, target position
HMI Operator interaction Recipe, result, fault, recovery
SCADA/MES Monitoring and traceability Part ID, result, measurements, timestamp

The PLC does not necessarily process the image. It usually manages the sequence, validates the returned result, and determines what happens next.

3. Three Different Communication Relationships

Do not treat every connection as the same PLC/robot link. The direction of control and the meaning of the data differ.

3.1 PLC-to-Vision Communication

The PLC commands the vision system to perform an inspection.

Typical information sent to the vision controller:

  • Trigger or inspection request.
  • Job or recipe selection.
  • Part identifier or sequence number, if supported.
  • Inspection mode or parameter selection.
  • Reset or acknowledge command.

Typical information returned:

  • Ready or busy status.
  • Inspection complete.
  • Pass/fail result.
  • Error or fault code.
  • Measurement values and confidence indicators.
  • Job status and result-valid status.

3.2 PLC-to-Robot Communication

The PLC coordinates robot availability and machine sequence.

Typical information exchanged:

  • Robot ready and program running.
  • Start permission or cycle request.
  • Robot cycle complete.
  • Robot fault or not-ready status.
  • Part available and fixture status.
  • Request to enter a defined position, if the control architecture supports it.

The exact handshake depends on the robot controller, PLC program, and machine design.

3.3 Vision-to-Robot Communication

In robot-guided vision, the vision controller may provide coordinates directly to the robot, or the data may pass through the PLC.

Typical information includes:

  • Target X, Y, Z coordinates.
  • Target orientation, such as rotation around an axis.
  • Object angle.
  • Position confidence or match score.
  • Target-found status.
  • Coordinate frame or job identifier.

Direct communication may reduce unnecessary data routing, but it introduces additional integration and diagnostic responsibilities. The design must clearly identify which controller owns the trigger, which controller validates the result, and which controller authorizes robot movement.

4. Trigger Mechanisms

A trigger tells the vision system when to acquire an image or execute an inspection. The correct trigger method depends on part motion, cycle time, required precision, and available interfaces.

Trigger method Operating principle Advantages Limitations
Digital hardware input PLC output or sensor signal triggers acquisition Simple, predictable, widely supported Wiring and I/O timing must be managed
Fieldbus trigger PLC writes a trigger command through an industrial network Convenient diagnostics and fewer signal wires Network and controller update delays
TCP/IP command PLC or controller sends a software command Flexible data exchange Application-level timing and connection management
Encoder-based trigger Position count determines capture point Suitable for moving conveyors Requires correct encoder scaling and tracking
Robot-position trigger Robot signals that it reached a capture position Useful for robot-mounted or robot-viewed cameras Depends on robot motion and settling requirements
Continuous acquisition Camera captures continuously or at a configured rate Useful for high-speed inspection Requires image-to-part association

4.1 Hardware Trigger

A PLC output may activate a camera trigger input when the part reaches the inspection position.

Important checks include:

  • Correct voltage, polarity, and input type.
  • Pulse duration compatible with the camera input specification.
  • Correct output type and electrical isolation.
  • Input filtering and debounce settings.
  • Whether the camera detects a rising edge, falling edge, or a defined pulse.
  • Whether the camera is ready to accept a new trigger.

A trigger pulse that is too short may be missed. A signal held high may cause unexpected behavior if the device expects a new rising edge for every acquisition.

4.2 Network-Based Trigger

A PLC may set a trigger bit or send a command over PROFINET, EtherNet/IP, TCP/IP, or another supported interface.

Network triggering is not automatically equivalent to a physical trigger edge. PLC logic, communication updates, controller processing, and camera scheduling all affect the effective trigger timing.

Use a documented handshake rather than writing a trigger bit continuously and assuming the camera will interpret every PLC scan as a new request.

4.3 Encoder-Based Trigger

When parts move on a conveyor, a sensor detects the part and an encoder tracks its movement. The capture event occurs when the part reaches a defined position.

If the encoder provides \(N\) counts per revolution and the conveyor travels \(D\) millimetres per revolution, the nominal distance per count is:

\[ \text{Distance per count} = \frac{D}{N} \]

If the required trigger position is \(x\) millimetres from the reference point, the corresponding count offset is:

\[ \text{Count offset} = \frac{xN}{D} \]

These calculations assume that \(D\) and \(N\) are defined consistently and that the encoder coupling and scaling are correct. Gear ratios, quadrature counting, electronic gearing, and slip may alter the effective scale.

Encoder-based triggering is particularly useful when the conveyor speed varies, because capture position is based on movement rather than a fixed delay. It still requires reliable part tracking and a defined response to missed sensor events or encoder faults.

5. Handshake Signals

A handshake coordinates the request, processing, result transfer, and acknowledgement. It prevents the PLC from reading incomplete data or issuing a second request while the vision controller is still processing the first.

Common signal names include the following. Actual tag names vary by manufacturer and project.

Signal Typical direction Meaning
Vision_Ready Vision to PLC Vision system can accept a request
Inspect_Request PLC to vision PLC requests an inspection
Vision_Busy Vision to PLC Acquisition or processing is in progress
Inspect_Complete Vision to PLC Inspection execution has finished
Result_Valid Vision to PLC Returned result data is valid
Result_Pass Vision to PLC Inspection criteria passed
Result_Fail Vision to PLC Inspection criteria failed
Vision_Fault Vision to PLC Vision system or job has an error
Result_Acknowledge PLC to vision PLC has consumed the result
Vision_Reset PLC to vision Requests reset, if supported
Robot_Ready Robot to PLC Robot is available for the defined operation
Robot_Cycle_Complete Robot to PLC Robot sequence has completed
Robot_Fault Robot to PLC Robot reports a fault condition

Inspect_Complete and Result_Valid are not necessarily interchangeable. A system may complete an inspection but return no valid match, an invalid image, or an execution error. The device manual must define exactly what each signal means.

Likewise, Result_Fail is not the same as Vision_Fault. A defective part may produce a valid inspection result of FAIL, whereas a communication timeout or camera error means the inspection result cannot be trusted.

5.1 Request and Acknowledge Patterns

Two common patterns are used.

Pulse-based request: The PLC sends a short request pulse. This is suitable only when the vision controller reliably captures the pulse and the interface defines how the PLC knows the request was accepted.

Latched request: The PLC asserts the request and holds it until the vision controller acknowledges it. This is generally easier to diagnose over asynchronous communication, provided both sides implement the documented sequence correctly.

A common latched sequence is:

  1. PLC verifies Vision_Ready.
  2. PLC sets Inspect_Request.
  3. Vision controller acknowledges the request or sets Vision_Busy.
  4. PLC holds the request according to the interface specification.
  5. Vision completes acquisition and processing.
  6. Vision publishes result data and asserts the defined completion/valid signals.
  7. PLC validates and copies the result.
  8. PLC asserts Result_Acknowledge.
  9. Vision clears the completed result state and returns to ready.
  10. PLC clears the request and acknowledgement according to the defined reset sequence.

Do not assume every vision product uses this exact order. Some interfaces require the request to drop before the result can be cleared; others use separate command and result sequence counters.

6. Edge Detection, Level Logic, and Duplicate Triggers

A PLC typically scans its logic repeatedly. If a trigger command remains true across multiple scans, logic that reacts to the level may repeatedly issue requests.

  • Level-triggered logic: Action is based on a signal being true.
  • Rising-edge logic: Action occurs when a signal changes from false to true.
  • Falling-edge logic: Action occurs when a signal changes from true to false.
  • One-shot logic: A pulse is generated for one qualifying transition.

A rising-edge detector can prevent repeated trigger commands, but it does not solve the entire synchronization problem. The program must also ensure that a new request is not issued until the previous transaction has completed or been deliberately aborted.

Typical failure causes include:

  • The trigger bit stays high after inspection.
  • The PLC restarts while the camera retains an old request.
  • A communication reconnect causes a retained bit to be interpreted as a new command.
  • The PLC sends another trigger while the camera is busy.
  • The vision controller returns an old result that was not cleared.
  • A result is accepted more than once.
  • A part is replaced before the previous result is consumed.

A robust design uses an explicit state machine, one outstanding transaction per channel unless buffering is intentionally designed, and a defined recovery sequence for restarts.

7. Result Validity and Part Association

The result must belong to the part currently being processed. This is essential in conveyors, multi-station lines, robot cells, and high-speed inspection systems.

Imagine a conveyor with three parts:

  • Part A is triggered and inspected.
  • Part B reaches the sensor while A's result is still processing.
  • Part C arrives before the PLC has consumed B's result.

If the controller supports only one outstanding request, the PLC must prevent overlapping transactions. If it supports multiple outstanding requests, the system needs a buffer or queue that associates each result with the correct part.

Useful association fields include:

  • Part ID.
  • Trigger sequence counter.
  • Recipe or job ID.
  • Inspection result code.
  • Result-valid flag.
  • Measurement or coordinate set.
  • Timestamp or event counter where supported.

A sequence counter can help detect repeated or stale results. For example, the PLC issues request sequence 1042 and accepts only a result associated with sequence 1042. This is only possible if the interface exposes a suitable identifier or if the application implements a reliable equivalent.

Never treat a result as current solely because Result_Pass is true. Validate completion, validity, transaction identity, and the selected recipe where those fields are available.

8. Typical PLC Inspection Sequence

A robust PLC sequence can be organized into explicit states.

State Action Exit condition
IDLE Wait for part and cycle permission Part present and inspection required
CHECK_READY Verify vision is online and ready Ready, correct job, no active fault
SEND_REQUEST Issue a single inspection request Request accepted or acknowledgement received
WAIT_RESULT Wait for inspection completion Valid completion or timeout
VALIDATE_RESULT Check result validity, ID, job, and data range Data accepted or rejected
PROCESS_RESULT Determine pass, fail, or system-fault response Action selected
ACK_RESULT Acknowledge result and clear transaction Interface reset complete
RECOVERY Handle timeout, invalid data, or communication fault Explicit recovery conditions met

The sequence should not silently convert a missing or invalid result into a pass. If the inspection is required for quality, an unknown result must follow a defined fault or reject strategy.

8.1 Example Pseudocode

IF State = IDLE THEN
    IF Part_Present AND Inspection_Required THEN
        IF Vision_Ready AND Correct_Job AND NOT Vision_Fault THEN
            Request_ID := Request_ID + 1
            State := SEND_REQUEST
        ELSE
            State := RECOVERY
        END_IF
    END_IF
END_IF

IF State = SEND_REQUEST THEN
    Inspect_Request := TRUE

    IF Request_Accepted THEN
        State := WAIT_RESULT
        Start_Inspection_Timeout()
    END_IF
END_IF

IF State = WAIT_RESULT THEN
    IF Inspect_Complete THEN
        IF Result_Valid AND Result_ID = Request_ID THEN
            State := VALIDATE_RESULT
        ELSE
            State := RECOVERY
        END_IF
    ELSIF Inspection_Timeout_Expired THEN
        State := RECOVERY
    END_IF
END_IF

IF State = VALIDATE_RESULT THEN
    IF Result_Data_In_Range AND Correct_Job THEN
        IF Result_Pass THEN
            State := PROCESS_PASS
        ELSIF Result_Fail THEN
            State := PROCESS_FAIL
        ELSE
            State := RECOVERY
        END_IF
    ELSE
        State := RECOVERY
    END_IF
END_IF

This is illustrative pseudocode, not drop-in PLC code. Real implementations need explicit handling of request clearing, acknowledgement timing, timer reset, retained state after restart, mutually exclusive result bits, and the specific vendor protocol.

A request counter generated only in the PLC does not prove that a returned result belongs to that request. The vision side must echo or otherwise reliably associate the same transaction identifier for that check to work.

9. Robot Guidance Using Vision Results

A vision-guided robot uses image processing to identify a target and determine where the robot should move. The output may be a two-dimensional position and angle, a three-dimensional position and orientation, or a predefined pose identifier.

Examples include:

  • Detecting a component's centre before picking it.
  • Correcting the pick location when a part is displaced.
  • Identifying a component's rotational orientation.
  • Locating a hole or weld feature for a process operation.
  • Detecting a part's position on a moving conveyor.

9.1 Camera Coordinates Are Not Robot Coordinates

A camera initially observes features in its own image coordinate system. A pixel position such as (u, v) is not automatically a robot position such as (X, Y, Z) in millimetres.

The system may need to convert among these coordinate frames:

Coordinate frame Meaning
Image coordinates Pixel locations in the image
Camera coordinates Positions relative to the camera
Robot base frame Positions relative to the robot base
Tool frame Positions relative to the robot tool centre point
Work-object frame Positions relative to a fixture, workpiece, or defined work coordinate
Part frame Positions relative to the detected component

A calibrated 2D vision system may map image positions to a known plane. A 3D system may estimate spatial coordinates using calibrated cameras, structured light, laser profiling, or another supported technique.

9.2 Coordinate Transformation

A rigid transformation can express a point in one coordinate frame relative to another.

Using homogeneous coordinates:

\[ \mathbf{p}\_{B} = \mathbf{T}\_{BC}\mathbf{p}\_{C} \]

Where:

  • \(\mathbf{p}\_{C}\) is the point represented in camera coordinates.
  • \(\mathbf{p}\_{B}\) is the same point represented in robot-base coordinates.
  • \(\mathbf{T}\_{BC}\) is the calibrated transformation from camera frame to robot-base frame.

A homogeneous transformation matrix combines rotation and translation:

\[ \mathbf{T} = \begin{bmatrix} R\_{3\times3} & \mathbf{t}\_{3\times1}\\\ 0\ 0\ 0 & 1 \end{bmatrix} \]

Here, \(R\) represents orientation and \(\mathbf{t}\) represents translation.

The multiplication order matters. A transformation defined from camera to robot base cannot be used as if it transforms robot-base coordinates into camera coordinates.

9.3 Eye-to-Hand and Eye-in-Hand Configurations

  • Eye-to-hand: The camera is fixed to the machine or cell, while the robot moves relative to it.
  • Eye-in-hand: The camera is mounted on the robot and moves with the tool or another robot-mounted bracket.

Eye-to-hand calibration establishes the relationship between the fixed camera and the robot coordinate system. Eye-in-hand calibration must account for the relationship between the camera and robot tool, as well as the robot's pose during image acquisition.

Common integration errors include:

  • Applying the wrong coordinate transformation.
  • Using millimetres on one side and metres on the other.
  • Reversing an axis sign.
  • Mixing degrees and radians.
  • Applying a rotation in the wrong order.
  • Using a tool or work frame that differs from the calibrated frame.
  • Moving the camera, fixture, or robot mounting without recalibration.

9.4 Example Robot-Guidance Sequence

Robot reaches defined capture position
          ↓
Robot signals Vision_Trigger_Permit
          ↓
Vision captures and processes the image
          ↓
Vision returns Target_Found and target pose
          ↓
PLC or robot validates result and recipe
          ↓
Robot program transforms target into its required frame
          ↓
Robot checks permitted travel envelope and approach strategy
          ↓
Robot executes the approved movement
          ↓
Robot signals operation complete

The exact motion-planning and coordinate-conversion responsibilities depend on the system architecture. Some vision controllers return robot-ready coordinates; others return camera-frame coordinates that require additional conversion.

A successful image match does not, by itself, prove that the resulting robot target is reachable or safe. The application must validate limits, collision risks, tool orientation, approach paths, and process conditions.

10. Communication Protocols and Interfaces

No single protocol is universally correct. The interface must be supported by the PLC, vision controller, and robot controller, and it must satisfy the application's timing and diagnostic requirements.

Interface Common use Engineering considerations
Digital I/O Ready, trigger, busy, pass/fail Simple but limited data capacity
PROFINET PLC and compatible vision or robot devices Device configuration, I/O mapping, update timing
EtherNet/IP PLC and compatible vision or robot devices Assembly mapping, connection state, data layout
TCP/IP sockets Commands and structured data Message framing, parsing, connection recovery, timeouts
Modbus TCP Supported status and register exchange Register mapping, data types, transaction timing
OPC UA Supervisory data and compatible device integration Client/server support, security, subscriptions, update behavior
Vendor-specific protocol Manufacturer-defined commands and results Version compatibility and documented command semantics

OPC UA is often useful for supervisory data exchange, but its suitability for a tightly timed trigger sequence must be evaluated for the particular system. Do not assume that every protocol provides equivalent real-time behavior or that every device supports every interface.

10.1 PLC Data Mapping

Before programming, create an interface specification that documents each signal or data field.

Field Example data type Validation
Inspect_Request Boolean Correct edge or handshake behavior
Vision_Ready Boolean Device online and available
Inspect_Complete Boolean Completion state for the current transaction
Result_Code Integer Code matches documented result definitions
Part_Sequence_ID Integer Matches the current transaction
Measured_X Floating point Correct units and permitted range
Measured_Y Floating point Correct units and permitted range
Measured_Angle Floating point Correct angular units and convention
Confidence_Score Integer or floating point Correct scale and acceptance threshold
Vision_Fault_Code Integer Interpreted using the correct fault-code table

These are illustrative field names and data types. The actual interface may use a different structure.

When exchanging numeric data, verify:

  • Signed versus unsigned integer.
  • 16-bit, 32-bit, or 64-bit representation.
  • Floating-point format.
  • Byte order and word order where applicable.
  • Register alignment and packing.
  • Scaling factors.
  • Engineering units.
  • Validity of values when the device is offline.
  • Whether the PLC receives a snapshot of consistent result data.

A common mistake is interpreting a raw integer register as a measurement without applying the documented scaling. For example, a raw value of 1250 may represent 125.0 mm if the scale is 0.1 mm per count, but only the interface specification can establish that meaning.

11. Timing, Latency, and Cycle Time

The total time from trigger to usable result includes several components:

\[ T\_{\text{total}} = T\_{\text{trigger}} + T\_{\text{acquisition}} + T\_{\text{processing}} + T\_{\text{communication}} + T\_{\text{PLC}} + T\_{\text{robot response}} \]

This is a simplified budget. Some operations overlap, so actual cycle time must be measured rather than calculated by blindly adding every nominal duration.

  • Trigger delay: Time between the intended trigger event and actual acquisition.
  • Exposure time: Time during which the image sensor collects light.
  • Processing time: Time needed to execute the inspection job.
  • Communication delay: Time to deliver commands and results.
  • PLC response time: Time until the PLC detects and processes the returned state.
  • Robot response time: Time required to act on the accepted result.

Latency is the delay between an event and its corresponding response. Jitter is variation in that delay from one transaction to another.

A stable average processing time is not sufficient if occasional delays exceed the available cycle window.

11.1 Example Timing Budget

Suppose a hypothetical inspection has the following measured times:

Stage Time
Trigger and acquisition scheduling 5 ms
Image acquisition 12 ms
Image processing 65 ms
Result communication 8 ms
PLC detection and processing 10 ms
Total sequential budget 100 ms

The estimated sequential budget is 100 ms. This does not mean the entire robot cycle takes 100 ms: robot travel, part presentation, settling, and other tasks may dominate or overlap the inspection sequence.

A robust design sets a timeout based on measured worst-case behavior, documented device limits, network conditions, and the machine's actual cycle requirements. A timeout set too low causes nuisance faults; one set too high delays fault detection and may damage throughput.

11.2 Moving Conveyor Considerations

For moving parts, the image must be associated with the correct physical part even if the part moves before the result becomes available.

Possible techniques include:

  • Encoder-based position tracking.
  • Part-presence sensor events.
  • Conveyor tracking buffers.
  • Trigger-position latching.
  • Robot conveyor-tracking functions.
  • Sequence counters or unique part identifiers.

If a conveyor moves at velocity \(v\) during a delay \(t\), the approximate travel distance is:

\[ d = vt \]

For example, at \(500\text{ mm/s}\), a delay of \(0.1\text{ s}\) corresponds to \(50\text{ mm}\) of conveyor travel. A fixed camera may still inspect the correct part, but a robot pick location or reject station must account for that movement.

12. Fault Diagnosis and Troubleshooting

The most important diagnostic distinction is between a valid inspection failure and a failure of the inspection system.

Symptom Possible cause Diagnostic action
No inspection starts Trigger missing or vision not ready Check trigger input, request state, ready status, and job configuration
Trigger works intermittently Pulse too short, electrical noise, or timing conflict Inspect signal timing, input specification, grounding, and trigger mode
Vision remains busy Processing stalled, request sequence incorrect, or device fault Check controller status, job execution, and documented busy-state behavior
Inspection complete never arrives Communication loss, failed acquisition, or wrong handshake Check network diagnostics, device event log, and timeout state
Old result is accepted Result not cleared or transaction identity not checked Inspect request/acknowledge logic and result association
Pass/fail bits conflict Inconsistent mapping or transient status Validate the protocol definition and copy result data atomically where possible
Robot moves to wrong position Frame, units, axis sign, or calibration error Verify coordinate frames, calibration, scaling, and target data
Wrong part receives result Conveyor tracking or part association error Trace sensor event, trigger ID, result ID, and part buffer
PLC and vision disagree on job Recipe change not synchronized Check job ID, recipe handshake, and changeover sequence
Results fail after restart Retained bits or stale communication data Define startup initialization and transaction recovery
Random timeouts Network load, variable processing time, or insufficient timeout Measure actual timing and inspect device/network diagnostics
Result values appear corrupted Incorrect data layout or interpretation Check data types, byte/word order, scaling, and alignment

12.1 Distinguish Three Outcomes

Valid PASS: The inspection completed, result data is valid, the correct part and recipe are confirmed, and the result satisfies the acceptance criteria.

Valid FAIL: The inspection completed correctly and the part failed one or more inspection criteria. This is a quality outcome, not necessarily a system fault.

Invalid or unknown result: The camera is offline, acquisition failed, data is stale, the transaction ID does not match, or the result is incomplete. The PLC must execute the defined fault-handling strategy rather than assuming pass or fail.

The machine's quality plan determines whether a failed part is rejected, held, re-inspected, or sent to a manual verification station. The system-fault strategy must be separately defined.

13. Fault Recovery and Restart Behavior

Recovery logic is part of the communication design, not something to improvise after commissioning.

For each fault, define:

  • What state the PLC enters.
  • Whether the robot is permitted to continue.
  • Whether the current part remains traceable.
  • Whether the current result is discarded.
  • Whether the camera request and acknowledgement must be cleared.
  • Whether the vision controller needs a reset.
  • Whether a new inspection is permitted.
  • Which operator acknowledgement is required.
  • What information is recorded for troubleshooting.

After a PLC restart or network reconnection, initialize the transaction state according to the documented interface. Do not assume that the remote device has also restarted or cleared its retained signals.

For a failed transaction, the program should avoid sending repeated requests indefinitely. Use a bounded retry policy if re-inspection is allowed, and ensure that retries cannot accidentally assign a new result to an old part.

A manual recovery operation should verify the physical part's location and identity before restarting the sequence. Clearing a fault bit alone does not restore the physical and logical states of a production cell.

14. Safety Requirements

Standard machine-vision results are generally intended for process control and quality inspection. They must not be treated as personnel-safety signals unless the specific equipment and complete safety architecture are explicitly certified and designed for that function.

  • Use the designated safety system for guarding, access interlocks, emergency stops, and safety-rated stop functions.
  • Do not rely on Vision_Ready, Result_Pass, a standard PLC bit, or ordinary Ethernet communication as a substitute for safety-rated interlocking.
  • Validate robot movement permissions independently of the vision result.
  • Define safe behavior for communication loss, invalid coordinates, unexpected target positions, and robot faults.
  • Prevent automatic restart after a safety event unless the machine's approved safety design permits it and the required reset procedure is satisfied.
  • Apply lockout/tagout and site-approved isolation procedures before electrical or mechanical maintenance.
  • Ensure that test modes, manual jogging, and commissioning bypasses follow approved plant procedures.

Vision can support quality and process decisions. It does not automatically provide personnel protection merely because a camera can detect an object.

15. Commissioning Checklist

Use a controlled commissioning sequence rather than testing the entire cell at once.

15.1 Interface Verification

  • Confirm the exact PLC, vision controller, camera, and robot models.
  • Confirm supported communication protocols and firmware compatibility.
  • Verify network configuration, device names, IP addresses, and connection status.
  • Verify all mapped signals and numeric data fields against the interface specification.
  • Verify electrical wiring, signal polarity, input/output type, and trigger pulse requirements.
  • Confirm the selected vision job or recipe.
  • Verify units, scaling, signedness, and data layout.

15.2 Sequence Verification

  • Confirm that a single request produces exactly one intended inspection.
  • Confirm that a busy camera cannot accidentally accept a second request.
  • Confirm that completion and result validity are interpreted correctly.
  • Confirm that the PLC does not accept stale or mismatched results.
  • Confirm that result acknowledgement clears the transaction correctly.
  • Confirm timeout and recovery behavior.
  • Confirm startup and network-reconnection behavior.
  • Confirm correct part tracking through the entire sequence.

15.3 Robot and Quality Verification

  • Verify camera calibration and coordinate-frame definitions.
  • Check target positions using controlled test parts and approved commissioning methods.
  • Verify acceptable and defective samples.
  • Confirm the defined response to no match, invalid image, and system fault.
  • Measure trigger-to-result time and worst-case cycle behavior.
  • Confirm that robot travel limits and process interlocks remain effective.
  • Record the validated configuration and test results.

16. Preventive Maintenance and Change Control

A PLC/robot vision link may continue communicating normally while the inspection becomes unreliable. Preventive maintenance should therefore cover both communications and inspection performance.

Interval or event Recommended check
Each shift or defined production interval Review inspection faults, missed triggers, and reject trends
Scheduled PM Inspect cables, connectors, mounting, lighting, and lens condition
After camera or fixture movement Verify calibration and target positions
After PLC or vision program changes Verify handshake sequence, data mapping, and fault recovery
After network or firmware changes Verify connection stability, timing, and data integrity
After robot tool or frame changes Verify coordinate transformations and motion results
After recipe changes Verify job selection and acceptance criteria
After controller replacement Restore approved backups and revalidate the interface

Maintain controlled backups of PLC programs, robot programs, vision jobs, calibration parameters, network settings, and interface documentation. Record firmware versions and dependencies where applicable.

A backup is not proven usable merely because a file exists. Verify that the correct version can be restored using an approved procedure, and validate the resulting system before returning it to production.

17. Practical Example: PLC, Vision, and Robot in an Assembly Cell

Consider a robot that picks a component from a fixture. A camera identifies the component's position and orientation before the robot picks it.

The intended sequence is:

  1. A part-presence sensor confirms that a component is available.
  2. The PLC verifies that the robot and vision system are ready.
  3. The PLC requests an inspection.
  4. The vision controller acquires an image and finds the component.
  5. The vision controller returns target coordinates, orientation, job information, and result status.
  6. The PLC checks that the result is valid and associated with the current inspection.
  7. The robot receives the approved target data through the configured interface.
  8. The robot validates the target against its motion strategy and performs the pick.
  9. The robot signals completion.
  10. The PLC updates the part state and permits the next cycle.

If the camera returns no target, the PLC must follow the configured no-target strategy. Depending on the process, that may mean retrying, requesting operator inspection, stopping the cycle, or routing the part to a reject station.

If the camera returns a target that is outside the expected fixture region, the controller should not blindly execute the coordinates. The result must pass plausibility checks and the robot's permitted-motion constraints.

18. Interview Questions and Answers

1. Why is a handshake required between a PLC and a vision system?

A handshake coordinates request acceptance, processing, result availability, and acknowledgement. It prevents duplicate requests, premature result reads, and reuse of stale data.

2. What is the difference between Inspect_Complete and Result_Valid?

Completion indicates that an inspection operation has finished according to the interface definition. Result validity indicates whether the returned data can be used. An operation can finish without producing a usable result.

3. Why should the PLC use a timeout?

A timeout detects a missing response within a defined period. It allows the sequence to enter a controlled fault state instead of waiting indefinitely.

4. Why is a rising-edge trigger useful?

It allows one action per qualifying transition rather than repeatedly acting while a signal remains high. The application must still prevent new transactions while the previous one is outstanding.

5. Why is a sequence counter useful?

It helps associate requests and results, identify repeated responses, and detect stale or mismatched data when the protocol supports transaction identification.

6. What is the difference between an inspection FAIL and a vision-system fault?

An inspection FAIL is a valid quality result indicating that the part does not meet inspection criteria. A system fault means the inspection could not be completed or its result cannot be trusted.

7. Why can a correct camera result produce incorrect robot movement?

The coordinate frame, calibration, units, axis directions, transformation order, or robot tool definition may be incorrect. The result can be correct in camera coordinates and still be wrong when interpreted by the robot.

8. What is the difference between eye-to-hand and eye-in-hand vision?

Eye-to-hand uses a camera fixed relative to the machine or cell. Eye-in-hand mounts the camera on the robot, so the camera moves with the robot.

9. Is Ethernet communication always deterministic enough for triggering?

No. Timing depends on the protocol, device implementation, network configuration, controller scheduling, and application design. The actual behavior must be measured and validated for the required cycle.

10. What should happen if the vision system becomes disconnected during production?

The PLC should detect the loss of communication, invalidate unconfirmed results, and execute the defined machine response. It must not treat missing data as a pass or continue with an unverified robot target.

11. Why is recipe synchronization important?

The result is meaningful only if it was generated using the intended inspection job and acceptance criteria. A mismatch can cause incorrect pass/fail decisions or incorrect coordinates.

12. How would you diagnose an intermittent wrong-pick problem?

Trace the part-presence event, trigger timing, request ID, vision result, coordinate transformation, robot frame, and actual target. Compare the same transaction across PLC, vision, and robot diagnostics to locate the first incorrect value or event.

19. Practical Exercises

  1. Handshake design: Create a PLC state machine for request, busy, completion, result validation, acknowledgement, timeout, and recovery.
  2. Stale-result prevention: Design a transaction-identification method that prevents a result from one part being used for another.
  3. Fault injection: Test camera offline, trigger not accepted, missing completion, invalid result, wrong recipe, and communication interruption. Verify the expected PLC and robot behavior.
  4. Coordinate verification: Use known reference points to verify coordinate units, axis directions, transformation conventions, and calibration accuracy.
  5. Timing measurement: Record trigger time, acquisition completion, result arrival, PLC acceptance, and robot response. Determine the measured worst-case response and whether the cycle-time requirement is met.
  6. Documentation: Prepare an interface-control document containing tag names, directions, data types, ranges, handshake diagrams, timeout settings, fault codes, and restart behavior.

20. Final Mental Model

The PLC/robot vision link is a coordinated transaction, not simply a collection of communication bits.

  • The PLC coordinates the machine sequence.
  • The vision system acquires images and evaluates the requested inspection.
  • The robot executes movement based on approved and correctly interpreted target information.
  • The handshake controls when a request is accepted and when a result can be consumed.
  • The transaction identity establishes which part and request the result belongs to.
  • The validation logic prevents invalid, stale, or implausible data from being used.
  • The fault strategy defines what happens when the expected sequence breaks.
  • The safety system independently enforces personnel-protection requirements.

The most important rule is simple: never allow the machine to act on a result until its validity, identity, and meaning have been established.
