1. Purpose and Scope

Network topology documentation is the structured representation of how industrial network devices are connected, how communication flows between them, how network segments are separated, and how the system can be maintained or recovered.

In industrial automation, topology documentation helps maintenance engineers identify which switches, cables, PLCs, HMIs, CNC controllers, robots, industrial PCs, and servers depend on one another.

A network can be operating correctly while its documentation is completely wrong. That becomes a serious problem when a switch fails, a cable is disconnected, a new machine is commissioned, or an engineer needs to isolate a communication fault during production.

The objective is to maintain an accurate, usable record of the physical connections, logical architecture, addressing, communication dependencies, redundancy, and recovery paths of the industrial network.

Key outcomes include:

  • Identify every relevant network device and its location.
  • Understand physical cable paths and port-to-port connections.
  • Document IP addresses, subnets, VLANs, and gateways.
  • Understand communication paths between PLCs, HMIs, robots, CNCs, IPCs, and SCADA systems.
  • Identify single points of failure and redundant paths.
  • Support troubleshooting, replacement, configuration backup, and disaster recovery.
  • Maintain traceability for engineering changes and cybersecurity reviews.

2. What Is Network Topology?

Network topology describes the arrangement and interconnection of network devices.

Two important views must be maintained separately: physical topology and logical topology.

2.1 Physical topology

Physical topology describes the actual equipment and cabling.

It includes:

  • Switches and routers.
  • PLC Ethernet ports and communication modules.
  • Industrial PCs and servers.
  • Fiber-optic links and copper Ethernet cables.
  • Patch panels and media converters.
  • Cabinet locations and cable routes.
  • Physical port numbers and connection endpoints.
  • Redundant physical paths.

Example:

Industrial PC NIC 1
        |
        | Copper Ethernet cable NET-IPC-01
        |
Managed Switch SW-01 Port 5
        |
        | Fiber uplink NET-FIB-01
        |
Managed Switch SW-02 Port 24
        |
        | Copper Ethernet cable NET-PLC-01
        |
PLC Ethernet Interface

This is an illustrative connection chain. Actual device names, ports, cable identifiers, and media types must come from the installation.

2.2 Logical topology

Logical topology describes how communication is organized regardless of the physical cable arrangement.

It includes:

  • IP networks and subnet boundaries.
  • VLANs.
  • Routing and gateways.
  • Broadcast domains.
  • Communication protocols.
  • Firewall and access-control boundaries.
  • Redundancy and failover behavior.
  • Logical communication relationships.

For example, an IPC and a PLC can be physically connected to the same switch but assigned to different VLANs. Their physical connection exists, but communication between them may require routing or another approved network arrangement.

2.3 Why both views are necessary

Physical topology answers Logical topology answers
Which cable connects these devices? Which IP network contains the devices?
Which switch port is used? Which VLAN is assigned?
Where is the fiber routed? Which gateway routes the traffic?
Which cabinet contains the switch? Which devices are allowed to communicate?
Is there a second physical path? Is that path part of a functioning redundancy design?

A physical diagram alone cannot explain all communication failures. A logical diagram alone cannot tell a technician which cable to disconnect or replace.

3. Common Industrial Network Topologies

3.1 Star topology

In a star topology, individual devices connect to a central switch.

          PLC
           |
           |
HMI --- Managed Switch --- IPC
           |
           |
         Robot

Advantages:

  • Easy to identify individual device connections.
  • A single access cable failure usually affects only its connected device.
  • Centralized diagnostics simplify port monitoring.
  • Adding devices is straightforward when capacity is available.

Disadvantages:

  • The central switch can be a single point of failure.
  • Uplink failure can isolate the connected devices from other networks.
  • The switch must have enough ports and suitable performance.

Typical applications include machine cells, small automation networks, and cabinet-level Ethernet networks.

3.2 Line or daisy-chain topology

Devices connect sequentially through built-in Ethernet switches or supported forwarding interfaces.

PLC --- Device 1 --- Device 2 --- Device 3

Advantages:

  • Can reduce cabling requirements.
  • Useful for supported device chains and distributed equipment.

Disadvantages:

  • A failed intermediate device or link may disconnect downstream devices.
  • Troubleshooting requires understanding the chain's forwarding behavior.
  • The design must account for supported device limits, latency, and recovery behavior.

Do not assume that every device with two Ethernet ports provides transparent switching or supports a particular line topology. Verify the device design.

3.3 Ring topology

Devices or switches form a closed path, often using an industrial Ethernet redundancy mechanism.

SW-01 --- SW-02
  |          |
SW-04 --- SW-03

Advantages:

  • Can provide an alternate path after certain link or device failures.
  • May reduce recovery time compared with rebuilding the network manually.

Disadvantages:

  • Requires a supported redundancy mechanism and correct configuration.
  • Misconfiguration can create loops or unexpected traffic behavior.
  • Recovery performance depends on the protocol, hardware, topology, and fault type.

Documentation must identify the ring manager or redundancy controller where applicable, ring ports, protocol, configured roles, and expected failure behavior.

3.4 Tree or hierarchical topology

A hierarchical topology connects access switches to distribution or core switches.

             Core Switch
             /         \
      Distribution A  Distribution B
          /    \          /    \
       Cell 1  Cell 2   Cell 3  Cell 4

Advantages:

  • Supports organized expansion.
  • Separates machine-level access from higher-level aggregation.
  • Makes network boundaries and uplink dependencies easier to document.

Disadvantages:

  • Higher-level switch failures may affect multiple machine areas.
  • Poorly planned uplinks can create bottlenecks.
  • Redundancy must be designed and tested, not merely drawn.

3.5 Redundant dual-path topology

Some industrial systems use separate network paths, redundant switches, or supported device-level redundancy.

Documentation should identify:

  • Primary and secondary paths.
  • Redundant interfaces.
  • Whether paths share physical infrastructure.
  • Redundancy protocol or mechanism.
  • Expected failover behavior.
  • Known limitations and common failure points.

Two cables are not necessarily two independent paths. If both run through the same vulnerable conduit or terminate on the same failed switch, the apparent redundancy may provide little protection.

4. Industrial Network Architecture Layers

A topology document should show how the network connects different functional layers.

A simplified architecture may look like this:

Enterprise / Business Network
            |
     Approved Boundary
            |
Industrial DMZ / Controlled Services
            |
    Industrial Core Network
            |
     Distribution Switches
            |
       Machine Networks
            |
  PLC / HMI / Robot / CNC / IPC
            |
     Sensors and Actuators

This is a conceptual structure, not a universal architecture. Actual plant networks may use different segmentation and access arrangements.

Important principles:

  • Document boundaries between business IT and industrial OT.
  • Identify permitted routing paths.
  • Record firewall locations and relevant access-control boundaries.
  • Show engineering workstations and remote-access paths.
  • Identify SCADA servers, historians, and data collection systems.
  • Separate safety-related network documentation where the architecture and procedures require it.
  • Avoid publishing sensitive network details in uncontrolled locations.

5. Essential Network Documentation Types

A complete network documentation system consists of multiple related records rather than one overloaded diagram.

Document Main purpose Typical contents
Physical topology diagram Shows actual device connections Devices, ports, cable IDs, media
Logical topology diagram Shows logical network structure Subnets, VLANs, routing, network boundaries
IP address register Tracks address allocation Device, IP, subnet, gateway, MAC
Switch port map Records switch port usage Port, connected device, VLAN, speed
Cable schedule Tracks physical cabling Cable ID, origin, destination, route
Fiber schedule Tracks optical links Fiber ID, strands, polarity, endpoints
VLAN register Defines network segmentation VLAN ID, purpose, subnet, approved scope
Device inventory Identifies installed assets Model, serial number, firmware, location
Network dependency matrix Maps communication dependencies Source, destination, protocol, purpose
Redundancy diagram Shows alternate paths Ring ports, primary/secondary paths, roles
Configuration register Tracks device configurations Backup file, revision, date, firmware
Change history Records modifications Change ID, reason, approval, validation

These records should reference consistent device names and identifiers. Otherwise, the topology diagram might show SW-03, the inventory might call it SWITCH_LINE_B, and the maintenance work order might call it CABINET_7_SWITCH. Humans can reconcile these names eventually, usually during the least convenient moment.

6. Standard Device Naming Convention

A consistent naming convention helps technicians identify equipment without relying on memory or informal descriptions.

Example naming scheme:

Device type Example identifier Meaning
Core switch SW-CORE-01 Core network switch
Machine switch SW-CELL-01 Switch serving a machine cell
PLC PLC-CELL-01 Programmable logic controller
HMI HMI-CELL-01 Operator interface
Industrial PC IPC-CELL-01 Industrial computer
Robot controller ROB-CELL-01 Robot control system
CNC controller CNC-MACH-01 CNC machine controller
Fiber cable FO-CORE-01 Fiber link identifier
Copper cable ETH-CELL-01 Ethernet cable identifier

These are examples only. Follow the existing plant naming standard where one exists.

6.1 Naming rules

  • Make identifiers unique within the documented scope.
  • Avoid spaces and ambiguous abbreviations where practical.
  • Use a consistent format for equipment type, location, and sequence.
  • Do not encode frequently changing details into permanent asset identifiers.
  • Label physical equipment and cables where required.
  • Maintain a mapping between formal identifiers and manufacturer names or serial numbers.
  • Use the same identifier across diagrams, inventory, backups, and maintenance records.

7. Physical Port-to-Port Documentation

The port map is one of the most useful records during network troubleshooting.

Example:

Source device Source port Destination device Destination port Cable ID Media
SW-CELL-01 Gi1/0/1 PLC-CELL-01 Ethernet 1 ETH-001 Copper
SW-CELL-01 Gi1/0/2 HMI-CELL-01 Ethernet 1 ETH-002 Copper
SW-CELL-01 Gi1/0/3 IPC-CELL-01 NIC 1 ETH-003 Copper
SW-CELL-01 Gi1/0/24 SW-CORE-01 Gi1/0/10 FO-001 Fiber

The port names are illustrative. Manufacturers use different interface naming conventions.

7.1 What a useful port map includes

  • Source device and port.
  • Destination device and port.
  • Cable identifier.
  • Cable type and category.
  • VLAN or logical role where relevant.
  • Link speed.
  • Fiber transceiver details where applicable.
  • Cabinet or panel location.
  • Port description.
  • Redundancy role where applicable.
  • Last verification date.

7.2 Verifying a port map

Use multiple sources to verify the connection:

  1. Inspect the physical cable labels and endpoints.
  2. Check the managed-switch port description.
  3. Review the switch MAC address table.
  4. Use LLDP neighbor information where supported.
  5. Check interface status and counters.
  6. Confirm the endpoint's identity and intended function.

A switch MAC table shows where MAC addresses are learned, not necessarily a permanent device-to-port relationship. MAC movement, downstream switches, and redundancy mechanisms must be considered.

LLDP is useful for identifying directly connected compatible devices, but not every industrial device supports it or exposes complete information.

8. IP Address and VLAN Documentation

Topology documentation must clearly associate physical devices with logical network assignments.

8.1 IP address register

Include:

  • Device identifier.
  • IP address.
  • Subnet mask or prefix.
  • Default gateway where applicable.
  • MAC address.
  • VLAN or subnet.
  • Address assignment method.
  • Network interface identifier.
  • Responsible owner.
  • Approved change reference.

Example:

Device IP address Prefix VLAN Assignment
PLC-CELL-01 192.168.10.20 /24 110 Static
HMI-CELL-01 192.168.10.21 /24 110 Static
IPC-CELL-01 192.168.10.30 /24 110 Static
SW-CELL-01 192.168.10.2 /24 110 Static

These values are illustrative and do not define a real plant's approved address plan.

8.2 VLAN register

Record each VLAN's identifier, purpose, subnet, connected device classes, and approved communication boundaries.

Example:

VLAN ID Purpose Example devices Communication policy
110 Machine control PLCs and selected HMIs Only approved control and management traffic
120 Industrial data collection IPCs and gateways Approved data flows to designated services
130 Network management Managed switches and authorized tools Restricted management access

These are example VLANs. Actual VLAN identifiers and policies must match the plant's network design.

8.3 Access ports and trunk ports

A physical topology should identify uplinks and their logical role.

  • An access port typically carries traffic for a designated VLAN.
  • A trunk port carries multiple VLANs using VLAN tagging where supported and configured.
  • A routed port operates at Layer 3 rather than as a Layer 2 switching port.
  • A management interface may be in-band or physically separate, depending on the device.

The port's role must be documented according to the actual configuration. Do not label a port as a trunk solely because it connects two switches.

9. Communication Dependency Matrix

A dependency matrix records which devices communicate, why they communicate, and what functions are affected when communication fails.

Example:

Source Destination Purpose Protocol or service Impact if unavailable
HMI-CELL-01 PLC-CELL-01 Operator commands and status Vendor-specific industrial protocol Loss of HMI control or status
IPC-CELL-01 PLC-CELL-01 Production data collection Approved industrial protocol Missing or stale process data
IPC-CELL-01 SCADA server Data transmission Configured application protocol Data visibility or historian gaps
Engineering workstation PLC Programming and diagnostics Vendor-specific engineering service Engineering access unavailable
Network monitoring server Managed switch Health monitoring SNMP or approved telemetry Reduced network visibility

The actual protocols and ports must be confirmed for the equipment and software versions in use.

9.1 Why this matrix matters

When a switch or uplink fails, the dependency matrix helps answer:

  • Which machines may stop communicating?
  • Which systems will lose monitoring?
  • Which applications depend on a specific server?
  • Which connections are required for maintenance?
  • Which traffic must be restored first?

This is especially useful in mixed networks where PLC control, engineering access, and data collection share physical infrastructure but have different operational priorities.

10. Redundancy and Single Points of Failure

A topology document should identify potential single points of failure and explain what happens if each critical component fails.

Examples include:

  • One central switch serving an entire machine cell.
  • A single uplink between a machine network and the plant network.
  • A single power supply feeding all network equipment in a cabinet.
  • One fiber path routed through a vulnerable cable tray.
  • One industrial gateway required for all data exchange.
  • Two redundant switches that share a single upstream connection.

10.1 Failure impact matrix

Component Potential failure impact Documentation requirement
Access switch Loss of connectivity for connected devices List affected devices and ports
Core switch Loss of communication across multiple network segments Record dependencies and alternate paths
Uplink cable Isolation of a downstream network Identify both endpoints and cable route
Fiber transceiver Loss of optical link Record module type and spare requirements
Gateway Loss of communication between supported networks Document interfaces, routes, and dependent applications
Redundant link Reduced resilience or network isolation Record expected failover behavior and alarms

10.2 Redundancy documentation

Record:

  • Redundancy protocol or mechanism.
  • Active and standby roles where applicable.
  • Ring manager or root bridge information where relevant.
  • Primary and alternate paths.
  • Shared physical infrastructure.
  • Expected recovery behavior.
  • Relevant alarms and validation procedure.

A diagram should distinguish a verified redundant path from a planned or untested path.

11. Creating and Maintaining Topology Diagrams

A topology diagram should be readable during a breakdown, not merely attractive during a presentation.

11.1 Recommended diagram elements

  • Unique device identifiers.
  • Device type and role.
  • Physical interfaces.
  • Cable identifiers.
  • Copper and fiber links.
  • VLAN or subnet boundaries where relevant.
  • Uplink and redundancy links.
  • Firewall and routing boundaries.
  • Cabinet, machine, or area references.
  • Diagram revision and verification date.
  • Legend explaining line types and symbols.

11.2 Separate diagrams by purpose

For large networks, create multiple related diagrams rather than forcing the entire plant onto one page.

Recommended views:

  1. Plant-level network overview.
  2. Machine-cell physical topology.
  3. Logical VLAN and subnet topology.
  4. Fiber backbone topology.
  5. Redundancy and failover topology.
  6. Network-management and remote-access topology.
  7. Critical communication dependency view.

Each diagram should have a clear scope and reference related documents.

11.3 Tool selection

Common tools include:

  • Microsoft Visio.
  • Microsoft PowerPoint for simple controlled diagrams.
  • Draw.io or diagrams.net where approved.
  • CAD tools where network documentation is integrated with electrical drawings.
  • Spreadsheet-based registers for port maps, IP assignments, and cable schedules.

The choice of tool matters less than consistency, access control, versioning, and keeping the documentation accurate.

12. Discovering an Existing Network

When documentation is missing or outdated, use a controlled discovery process.

Step 1: Establish the scope

Identify the machine, cabinet, VLAN, switch, or network segment to be documented.

Step 2: Inspect physical equipment

Record device labels, model numbers, ports, cable IDs, and physical locations.

Step 3: Collect approved configuration data

For managed switches and routers, collect relevant configuration and status information through authorized management access.

Step 4: Inspect network neighbors

Where supported, review LLDP neighbor information, MAC address tables, VLAN membership, and interface descriptions.

Step 5: Verify addressing

Compare device IP configurations with the approved address register. Do not assume that a device discovered by an IP scan has been correctly identified.

Step 6: Trace connections

Use cable labels, switch-port information, and approved physical tracing methods to establish source and destination endpoints.

Step 7: Confirm logical communication

Verify the documented paths against configured VLANs, routing, and application dependencies.

Step 8: Mark uncertainties

If a connection or function cannot be verified, mark it as unknown or unverified. Do not silently convert assumptions into documented facts.

Step 9: Review with the responsible team

Validate the draft with automation, maintenance, IT/OT networking, and machine owners as applicable.

Step 10: Publish the controlled revision

Assign a revision, record the verification date, store it in the approved location, and communicate significant changes.

Safety note: Do not perform aggressive scanning, unauthorized port shutdowns, cable disconnections, or topology experiments on a live industrial network. Discovery activities must respect production, safety, cybersecurity, and change-control requirements.

13. Network Documentation Change Management

Topology documentation must be updated whenever a network change alters the installed or intended design.

Examples include:

  • Switch or router replacement.
  • PLC or IPC replacement.
  • New device commissioning.
  • IP address changes.
  • VLAN changes.
  • Cable rerouting.
  • Fiber backbone modification.
  • Redundancy redesign.
  • Firewall or gateway changes.
  • Firmware changes affecting network behavior.

13.1 Recommended change workflow

Approved Network Change
          ↓
Assess Operational Impact
          ↓
Capture Existing State
          ↓
Implement the Change
          ↓
Validate Physical and Logical Connectivity
          ↓
Update Diagrams and Registers
          ↓
Review and Approve Documentation
          ↓
Publish the New Revision

The documentation update should be part of the change closure process, not a task left for an unspecified future day.

13.2 Revision control

Each controlled document should include:

  • Document title and unique identifier.
  • Revision number.
  • Date of issue.
  • Author or responsible team.
  • Reviewer or approver where required.
  • Description of changes.
  • Verification status.
  • Location of related configuration backups.

Keep prior revisions according to the site's retention policy. Historical versions help explain why the current network differs from earlier configurations.

14. Configuration and Documentation Relationship

Topology documentation and configuration backups serve different but complementary purposes.

Configuration backup Topology documentation
Captures device settings Describes device relationships and network structure
Helps restore configuration Helps understand the intended architecture
May include VLAN and port settings Maps those settings to devices and physical connections
May be model- or firmware-specific Provides a cross-device view
Does not necessarily describe cable routes Records physical connectivity and cable IDs
Can contain sensitive information May also contain sensitive information and requires access control

For example, a switch configuration may show that Gi1/0/24 is a trunk. The topology documentation identifies which device is connected to that port, which cable is used, and which network segments depend on the uplink.

A configuration file without topology context can be difficult to apply safely. A topology diagram without configuration evidence can describe a network that no longer exists.

15. Industrial Cybersecurity and Access Control

Network topology documentation can expose sensitive operational information, including:

  • IP addresses and network boundaries.
  • Critical PLC and server locations.
  • Remote-access paths.
  • Redundant paths and single points of failure.
  • Firewall placement.
  • Device models and firmware versions.
  • Management interfaces and security boundaries.

Apply appropriate controls:

  • Store controlled diagrams in approved repositories.
  • Restrict write access to authorized personnel.
  • Limit distribution of detailed network maps.
  • Avoid including passwords, private keys, or other secrets in diagrams.
  • Reference secure configuration repositories rather than embedding credentials.
  • Maintain revision history and approved access.
  • Use redacted versions for audiences that do not need detailed operational information.

Network documentation supports cybersecurity by making the intended architecture visible, but it does not replace firewall rules, access control, network segmentation, or security monitoring.

16. Practical Case Study: Unknown Switch Port During a Breakdown

Situation: A PLC becomes unreachable, and the maintenance engineer needs to identify its physical network path. The switch has no useful port labels.

Initial investigation:

  • The PLC is powered and its Ethernet interface is active.
  • The IP address matches the register.
  • Several switch ports show active links.
  • The available topology diagram is outdated.

Diagnostic procedure:

  1. Verify the PLC's IP address and MAC address.
  2. Inspect the managed-switch MAC address table.
  3. Use LLDP where supported to identify directly connected devices.
  4. Trace the suspected cable using labels and approved methods.
  5. Confirm the connected switch port and VLAN.
  6. Check interface errors and recent link events.
  7. Update the physical port map after the actual connection is verified.

Possible finding: The PLC cable is connected to a port assigned to the wrong VLAN after an earlier maintenance activity.

Corrective action: Restore the approved port configuration, validate PLC communication, and update the controlled topology documentation.

Lesson: Accurate physical mapping and logical configuration records reduce fault-isolation time and prevent unnecessary device replacement.

17. Practical Case Study: Hidden Single Point of Failure

Situation: Two machine switches are believed to have redundant uplinks to the plant network.

Investigation:

  • The topology drawing shows two separate lines.
  • Physical inspection reveals that both cables terminate on the same upstream switch.
  • No verified alternate upstream path exists.

Finding: The network has two physical links but still depends on one upstream device.

Corrective action:

  1. Record the actual topology.
  2. Identify the operational risk.
  3. Design an approved alternate path if required.
  4. Verify that the proposed topology supports the selected redundancy mechanism.
  5. Implement and test the change under an approved procedure.
  6. Update the physical and logical diagrams.

Lesson: Redundancy must be evaluated across the entire path, including switches, power, cabling, and upstream dependencies.

18. Topology Documentation Quality Checklist

Device inventory

  • Every relevant network device has a unique identifier.
  • Manufacturer, model, location, and role are recorded.
  • Firmware and relevant interface details are recorded.
  • Replacement spares are linked to compatible device records.

Physical topology

  • Switches and endpoints are shown.
  • Cable IDs and endpoints are documented.
  • Copper and fiber links are distinguished.
  • Port numbers match the actual installation.
  • Cabinet and machine locations are identified.
  • Unverified links are clearly marked.

Logical topology

  • IP addresses and subnets are documented.
  • VLANs and network boundaries are identified.
  • Routing and gateway relationships are recorded.
  • Communication dependencies are documented.
  • Redundant paths and single points of failure are identified.

Maintenance and control

  • Configuration backups are linked to the correct device.
  • Changes are recorded with revision history.
  • Diagrams have a verification date.
  • Access to sensitive documents is controlled.
  • Relevant teams can find the current approved version.
  • Documentation is updated as part of change closure.

19. Interview Questions and Answers

1. What is network topology documentation?

It is the controlled record of network devices, physical connections, logical structure, addressing, communication dependencies, and redundancy.

2. What is the difference between physical and logical topology?

Physical topology describes actual devices, ports, and cabling. Logical topology describes IP networks, VLANs, routing, and communication relationships.

3. Why is a switch port map important?

It identifies the device and cable connected to each port, supporting faster troubleshooting, safe replacement, and accurate maintenance.

4. Why are topology diagrams insufficient on their own?

They may not include all configuration details, cable test results, current port states, or application dependencies. They must be supported by registers, configurations, and verification.

5. What is a single point of failure?

A component or dependency whose failure can interrupt a required service because no suitable independent alternate path exists.

6. How can LLDP help network discovery?

LLDP can advertise information about directly connected compatible devices, helping identify neighboring equipment and physical connections. Its availability depends on device support and configuration.

7. What should happen when a switch is replaced?

Capture the existing configuration, verify compatibility, record connections, install and configure the replacement, validate the network, and update the inventory and topology documents.

8. Why must topology documentation be access-controlled?

It may reveal critical equipment, network segmentation, management interfaces, and potential attack paths.

9. How should unknown connections be documented?

Mark them as unverified, investigate using approved methods, and update the record only when sufficient evidence confirms the connection.

10. What is the relationship between configuration backups and topology documentation?

Backups preserve device settings, while topology documents explain how the devices connect and how those settings fit into the wider network.

20. Core Principle

Network topology documentation is an operational maintenance tool, not merely a drawing.

A reliable documentation system lets an engineer answer five questions quickly:

  1. What device is involved?
  2. Where is it physically connected?
  3. What is its logical network configuration?
  4. Which systems depend on it?
  5. How can the network be restored and validated safely?

The best topology is the one that matches the actual installation, is maintained through change control, and can be used effectively during a real breakdown.
