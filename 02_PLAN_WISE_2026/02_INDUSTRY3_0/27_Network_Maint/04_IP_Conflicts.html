1. Purpose and Scope

An IP conflict occurs when two or more devices use the same IP address within the same network scope where that address must be unique. The conflict can cause intermittent communication, failed connections, incorrect device responses, or loss of access to an industrial controller or server.

In industrial automation, IP conflicts can affect:

  • PLCs and remote I/O.
  • HMIs and operator panels.
  • CNC controllers and robot controllers.
  • Industrial PCs and SCADA servers.
  • Managed switches and network gateways.
  • Engineering laptops and maintenance workstations.
  • Data collection systems, historians, and industrial gateways.

A device can appear powered on and physically connected while communication remains unreliable because its IP address is duplicated. This is why replacing a cable or rebooting a switch is not a meaningful solution until the addressing problem has been investigated.

The objective is to identify the duplicate address, determine why it occurred, restore the intended network configuration, and prevent recurrence without disrupting production unnecessarily.

2. IP Address Fundamentals

An IP address identifies a network interface at the IP layer. For IPv4, the address is 32 bits long and is usually written as four decimal octets.

Example:

192.168.10.25

The address is interpreted together with the subnet mask or prefix length, which determines the network portion and host portion.

Example:

Parameter Example value Purpose
IP address 192.168.10.25 Identifies the interface at the IP layer
Subnet mask 255.255.255.0 Defines the IPv4 subnet boundary
Prefix length /24 Alternative notation for the subnet mask
Default gateway 192.168.10.1 Routes traffic to other IP networks
DNS server 192.168.10.10 Resolves configured hostnames
MAC address 00:1A:2B:3C:4D:5E Identifies a network interface at the data-link layer

The values above are examples, not a recommended configuration for an actual plant network.

2.1 IP address versus MAC address

An IP address is a logical network-layer address. A MAC address identifies a network interface at the data-link layer.

For IPv4 communication on a local Ethernet network, devices use ARP (Address Resolution Protocol) to map an IPv4 address to a MAC address.

When two devices claim the same IP address, the network may receive competing ARP announcements or replies. Other devices can then associate the IP address with different MAC addresses at different times.

This can cause communication to reach the wrong device or become intermittent.

2.2 Duplicate address versus duplicate hostname

These are different problems:

  • Duplicate IP address: Multiple interfaces claim the same IP address in the same relevant network scope.
  • Duplicate hostname: Multiple devices use the same name, potentially causing name-resolution or management confusion.
  • Duplicate MAC address: Two interfaces present the same MAC address, which can create Layer 2 forwarding problems.
  • Incorrect subnet mask: A device interprets local and remote destinations incorrectly.
  • Incorrect gateway: A device cannot route traffic correctly to other subnets.

A ping failure alone does not prove an IP conflict. It may result from a firewall, disconnected cable, incorrect VLAN, powered-off device, or routing problem.

3. How IP Conflicts Occur

Common causes include:

  • A maintenance laptop is configured with an address already assigned to a PLC.
  • A replacement industrial PC is configured using the address of another active device.
  • A device is restored from an image containing an old static IP configuration.
  • A DHCP server leases an address that has also been assigned manually.
  • Two devices are configured manually using the same address.
  • A spare PLC or HMI is powered on with an address copied from another machine.
  • An undocumented device is connected to the plant network.
  • An IP allocation spreadsheet is outdated.
  • A machine is moved to a different VLAN or subnet without updating its configuration.
  • A cloned virtual machine or restored system retains an address already in use.
  • Multiple DHCP servers operate on the same network without coordinated scope management.

A particularly common industrial scenario is a spare controller that was configured during bench testing and then connected to the production network without restoring its correct machine-specific address.

4. Static IP Addressing and DHCP

4.1 Static addressing

A static IP address is manually configured or assigned through a controlled configuration process and remains associated with the device until changed.

Typical industrial applications include:

  • PLCs and robot controllers.
  • CNC controllers.
  • HMIs.
  • Fixed-address industrial servers.
  • Network infrastructure management interfaces.

Static addressing supports predictable access, but only when allocations are centrally documented and checked for uniqueness.

4.2 Dynamic Host Configuration Protocol

DHCP automatically supplies IP configuration to clients from a configured address pool.

DHCP commonly provides:

  • IP address.
  • Subnet mask or prefix.
  • Default gateway.
  • DNS server information.
  • Lease duration.

DHCP can reduce manual configuration errors, but it does not automatically make an industrial network safe from conflicts. Manually assigned addresses must be coordinated with DHCP scopes, exclusions, reservations, and network design.

4.3 DHCP reservations

A DHCP reservation associates a particular client identifier, commonly based on a MAC address, with a specified IP address.

Reservations can make addressing more predictable, but the reservation must be configured correctly and coordinated with static allocations. A reservation is not a substitute for an accurate IP register.

4.4 Static versus DHCP addressing

Characteristic Static addressing DHCP addressing
Configuration Manually or centrally configured Supplied by a DHCP server
Predictability High when controlled High when leases and reservations are managed
Main risk Duplicate manual assignments Scope overlap, rogue DHCP, or conflicting static assignments
Typical use Fixed industrial devices Engineering laptops, general clients, selected managed devices
Troubleshooting Inspect device configuration and IP register Inspect lease, scope, reservation, and client configuration

The correct approach depends on the industrial network design and device requirements. Do not change a production PLC from static addressing to DHCP merely to resolve a duplicate address.

5. Recognizing IP Conflict Symptoms

Symptom Possible explanation Useful check
PLC communication drops intermittently Duplicate IP, physical fault, or device restart Check ARP mappings, switch logs, and PLC diagnostics
HMI connects to the wrong endpoint Duplicate IP or incorrect project configuration Verify the intended IP and device identity
Ping replies appear inconsistent Duplicate address or changing network path Compare ARP mappings and MAC addresses
One device works only when another is disconnected Strong indication of a duplicate address Verify both configurations and their MAC addresses
Engineering software cannot maintain a session IP conflict, firewall, routing, or protocol issue Verify address uniqueness and application connectivity
Device is unreachable after replacement Incorrect IP, subnet, VLAN, or gateway Compare the replacement settings with approved records
ARP entry changes between MAC addresses Possible duplicate IP, redundancy behavior, or topology change Correlate timestamps, interface identity, and network design
Multiple devices lose connectivity simultaneously Network-wide configuration, switching, or addressing issue Check DHCP, VLANs, gateways, and infrastructure logs

Symptoms are clues, not proof. For example, some redundancy protocols intentionally move an IP address between devices. Diagnose the network architecture before declaring such behavior a conflict.

6. IPv4 Subnets and Address Allocation

An IP address must be unique within the relevant Layer 2 and IP network scope. Understanding subnetting helps prevent incorrect address assignments.

For example, consider this configuration:

  • PLC: 192.168.10.20/24
  • HMI: 192.168.10.21/24
  • Industrial PC: 192.168.10.30/24
  • Gateway: 192.168.10.1/24

With a /24 prefix, the subnet is 192.168.10.0/24. The normal usable host range is 192.168.10.1 through 192.168.10.254, excluding any addresses reserved by the network design. The network address is 192.168.10.0, and the broadcast address is 192.168.10.255.

A different device configured with 192.168.10.20/24 would create a duplicate address if it is active in the same relevant network scope.

However, two devices in separate, properly isolated networks can use the same private IP address without creating a direct local conflict. Problems arise if the networks are bridged, incorrectly connected, or routed without suitable address translation and routing design.

6.1 Address planning

Maintain an approved address allocation register containing:

Field Purpose
Device name Identifies the intended equipment
Machine or line Identifies its production location
Device type PLC, HMI, IPC, robot, switch, or other
IP address Assigned address
Subnet prefix Defines the network boundary
Gateway Identifies the configured router where applicable
MAC address Helps verify the actual network interface
VLAN or subnet Defines the intended network segment
Address method Static, DHCP, or reservation
Responsible owner Identifies the person or team controlling the allocation
Change record Links the assignment to an approved modification

An IP register is useful only when changes are recorded promptly. A beautifully formatted spreadsheet describing last year's network is still last year's network.

7. Diagnostic Workflow for an IP Conflict

Use a controlled sequence rather than changing addresses at random.

Step 1: Define the affected device and scope

Record:

  • Device name and machine location.
  • Expected IP address.
  • Subnet and VLAN.
  • Switch port, where known.
  • Observed symptoms and timestamps.
  • Whether the fault started after a replacement, maintenance activity, or network change.

Determine whether one endpoint or several devices are affected.

Step 2: Check the current device configuration

On a Windows engineering PC, open Command Prompt and run:

ipconfig /all

Review the active adapter's IPv4 address, subnet mask, gateway, DHCP status, and lease information.

Do not assume that the address displayed on the laptop is the address of the PLC or HMI being investigated.

On the affected industrial device, use the manufacturer's approved diagnostic interface or configuration utility to read its actual settings.

Step 3: Check connectivity

Use a ping test if ICMP is permitted:

ping 192.168.10.20

Replace the example address with the approved target address.

Interpret results cautiously:

  • Successful replies prove that a device at that address responded, not necessarily that it is the intended device.
  • Failed replies do not prove that the device is offline.
  • Inconsistent replies may suggest a conflict but can also arise from packet loss or other network conditions.

Step 4: Inspect the ARP cache

On Windows:

arp -a

This displays cached IPv4-to-MAC mappings for reachable or previously contacted local-network neighbors.

For a more targeted check, clear the relevant ARP cache entry if supported and permitted, generate traffic to the target, and inspect the resulting mapping. Clearing the entire ARP cache can temporarily affect other communications, so avoid doing so casually on a workstation used for active industrial maintenance.

An ARP entry is evidence of a mapping observed by that host, not conclusive proof that the address is unique. Cached entries can also become stale.

Step 5: Compare MAC addresses

Compare the MAC address associated with the disputed IP against:

  • The device's hardware label.
  • The manufacturer's configuration utility.
  • The switch MAC address table.
  • The approved network inventory.

A changing MAC mapping for the same IP is a useful clue, but account for legitimate mechanisms such as redundancy systems, virtual IPs, teaming, and failover before declaring a conflict.

Step 6: Locate the devices

Use managed-switch MAC address tables and port information to identify where the relevant MAC addresses are learned.

Check:

  • Switch and port identifiers.
  • VLAN membership.
  • Whether the MAC addresses appear on different access ports.
  • Whether one address moves between ports unexpectedly.
  • Whether the topology includes legitimate redundancy or virtual interfaces.

Do not disable a port simply because an unfamiliar MAC address appears. Confirm the device identity and production impact first.

Step 7: Correct the addressing problem

Once the duplicate assignment is confirmed:

  1. Identify the device that should retain the address.
  2. Verify the approved address for the other device.
  3. Obtain authorization for the change.
  4. Change the incorrect device through its supported configuration method.
  5. Avoid modifying a safety controller or production controller without the applicable change procedure.
  6. Verify that the corrected address is unique and that the device remains in the intended subnet and VLAN.

Step 8: Validate and document

Confirm:

  • The intended device responds at the expected address.
  • The observed MAC mapping matches the intended endpoint.
  • The correct PLC, HMI, or IPC application communicates.
  • No new duplicate-address alerts appear.
  • Relevant network counters and logs are stable.
  • The IP register and maintenance record are updated.

8. Windows Commands for IP Conflict Investigation

These commands are useful on an engineering workstation. Their output is evidence for troubleshooting, not automatic proof of root cause.

Command Purpose
ipconfig /all Shows local adapter configuration and DHCP details
ping 192.168.10.20 Tests IP reachability using ICMP
arp -a Displays cached IP-to-MAC mappings
getmac /v Displays local interface MAC addresses
route print Shows the local routing table
ipconfig /release Releases a DHCP lease on supported DHCP-enabled adapters
ipconfig /renew Requests DHCP configuration again
ipconfig /flushdns Clears the local DNS resolver cache

Important: ipconfig /release and ipconfig /renew concern the workstation's DHCP configuration. They do not resolve a duplicate static address on a PLC. Do not use these commands on a production engineering workstation without understanding their impact on its network connections.

8.1 PowerShell checks

Display local IP configuration:

Get-NetIPConfiguration

List IPv4 addresses assigned to local interfaces:

Get-NetIPAddress -AddressFamily IPv4

Display the local ARP neighbor table:

Get-NetNeighbor -AddressFamily IPv4

Test IP reachability:

Test-Connection -ComputerName 192.168.10.20 -Count 4

A successful reachability test does not verify that the responding device is the intended PLC or IPC. Correlate it with the MAC address and device identity.

9. DHCP-Related Conflicts

A common conflict occurs when an address is assigned manually to a device and also falls within a DHCP server's available allocation pool.

Example:

  • PLC static address: 192.168.10.50
  • DHCP pool: 192.168.10.20 to 192.168.10.100
  • DHCP client receives: 192.168.10.50

Both devices may then claim the same address.

Investigate:

  • DHCP scope boundaries.
  • Excluded addresses.
  • Reservations.
  • Active leases.
  • Lease history and timestamps.
  • Rogue or unintended DHCP servers.
  • Whether the static address allocation is documented.

Correct the scope, exclusion, reservation, or device assignment according to the approved network plan. Do not randomly delete active leases or restart DHCP services on a production network.

DHCP conflict detection and client behavior vary by implementation. Some conflicts are detected automatically, while others may go unnoticed.

10. ARP, Duplicate Address Detection, and Limitations

ARP allows IPv4 devices on an Ethernet LAN to discover the MAC address associated with an IP address. It does not provide a universal guarantee that all duplicate IP assignments will be detected.

Some operating systems and devices perform duplicate-address checks during configuration or startup. The methods and behavior vary by device, operating system, and network design.

Important limitations:

  • A device may not implement duplicate-address detection.
  • A conflict may exist outside the scope visible to the diagnostic workstation.
  • Cached ARP entries can hide a recently changed mapping.
  • VLAN boundaries limit which broadcasts and ARP traffic are visible.
  • Static devices may not register with a central DHCP server.
  • A virtual IP may legitimately move between redundant systems.

Therefore, use ARP observations together with device configuration, switch data, DHCP records, and physical port identification.

11. Industrial Network Safety and Change Control

Changing an IP address can disconnect an automation device from its controller, HMI, engineering software, or SCADA system. A seemingly small addressing change can therefore affect production.

Before making changes:

  • Confirm the device identity and intended address.
  • Review the approved network topology and IP allocation register.
  • Check whether the address is used by PLC logic, HMI projects, SCADA tags, robot configuration, CNC communication settings, or other integrations.
  • Determine whether the device has a redundant interface or a virtual IP.
  • Obtain the required maintenance and production authorization.
  • Preserve the original configuration and document the rollback procedure.
  • Use the manufacturer's supported configuration method.

After the change, verify application-level communication, not just ping responses.

Do not casually change IP addresses on safety PLCs, robot controllers, CNC controllers, or other production-critical equipment. Follow the relevant safety, cybersecurity, and change-management procedures.

12. Practical Case Studies

Case Study 1: PLC Becomes Intermittently Unreachable

Situation: A PLC normally communicates with its HMI, but the HMI intermittently loses communication.

Findings:

  • The PLC's expected IP address is present in the network register.
  • An engineering laptop was manually configured with the same address.
  • The ARP mapping observed by another workstation changes between two MAC addresses.

Root cause: The engineering laptop and PLC use the same IPv4 address.

Corrective action:

  1. Confirm the identity of both devices.
  2. Move the engineering laptop to an approved, unused address or its authorized DHCP configuration.
  3. Verify that the PLC retains its assigned address.
  4. Refresh the relevant neighbor information where appropriate.
  5. Test PLC-to-HMI and engineering communication.
  6. Update the laptop configuration procedure to prevent recurrence.

Lesson: A maintenance laptop is a network participant, not an invisible observer.

Case Study 2: Replacement IPC Cannot Communicate With a PLC

Situation: An industrial PC is replaced after a hardware failure. The operating system starts, but PLC communication is unreliable.

Findings:

  • The replacement IPC was restored from an old system image.
  • The restored image contains a static IP address already used by another IPC.
  • The physical Ethernet link is stable.

Root cause: The image preserved the old machine-specific network configuration.

Corrective action:

  1. Verify the replacement IPC's intended network identity.
  2. Obtain the approved IP configuration for the replacement.
  3. Assign the correct address using the approved procedure.
  4. Verify the subnet, gateway, VLAN, and relevant application configuration.
  5. Confirm PLC communication and SCADA data exchange.
  6. Update the replacement and image-restoration procedure.

Lesson: A system image restores software and settings, not necessarily the correct network identity for the new installation.

Case Study 3: Device Becomes Unreachable After Network Maintenance

Situation: A remote I/O device becomes unreachable following a switch or VLAN change.

Findings:

  • The device's configured IP address has not changed.
  • The device is connected to a different VLAN from its intended network.
  • The diagnostic workstation can no longer reach it.

Possible root cause: Incorrect VLAN assignment or an addressing and subnet mismatch rather than a duplicate IP.

Corrective action:

  1. Confirm the device's configured IP and subnet.
  2. Check switch-port VLAN membership.
  3. Compare the configuration with the approved network design.
  4. Restore the intended VLAN or correct the documented configuration.
  5. Verify reachability and actual I/O communication.

Lesson: Not every IP-related symptom is an IP conflict. Diagnose the actual network layer before changing addresses.

13. IP Conflict Prevention Strategy

A reliable prevention system combines configuration control, inventory accuracy, and repeatable replacement procedures.

13.1 Maintain a controlled IP register

Keep one authoritative record of addresses, device identities, VLANs, subnet masks, allocation methods, and responsible owners.

Avoid separate uncontrolled spreadsheets maintained by different shifts.

13.2 Define address-allocation rules

  • Reserve defined ranges for PLCs, HMIs, IPCs, switches, robots, and infrastructure where appropriate.
  • Keep DHCP pools separate from manually assigned addresses or configure exclusions and reservations correctly.
  • Document temporary engineering addresses.
  • Remove obsolete allocations only after confirming that the device is no longer using them.
  • Require address verification before commissioning replacement equipment.

13.3 Standardize equipment replacement

Every replacement workflow should include:

  1. Record the original device configuration.
  2. Confirm the replacement device's intended address.
  3. Check that the address is unique.
  4. Verify subnet, gateway, VLAN, and interface settings.
  5. Apply the approved configuration.
  6. Test the intended communication.
  7. Update the inventory and change record.

13.4 Monitor and review

Where supported, use managed-switch logs, DHCP server logs, network monitoring, and approved duplicate-address detection tools.

Investigate:

  • Repeated duplicate-address alerts.
  • Unexpected changes in IP-to-MAC mappings.
  • Unapproved DHCP servers.
  • Unknown devices on production VLANs.
  • Repeated conflicts following equipment replacement.

Monitoring should generate useful evidence without creating unnecessary alarms or disrupting production traffic.

14. IP Conflict Troubleshooting Checklist

Initial diagnosis

  • Identify the affected device and expected IP address.
  • Record the fault time and symptoms.
  • Check the physical link and switch-port status.
  • Read the device's actual IP configuration.
  • Check subnet and VLAN assignment.
  • Test reachability where permitted.
  • Inspect ARP mappings and compare MAC addresses.

Root-cause confirmation

  • Check the IP allocation register.
  • Check DHCP scopes, leases, reservations, and exclusions where relevant.
  • Identify the switch ports associated with the competing MAC addresses.
  • Consider virtual IPs, redundancy, and legitimate MAC movement.
  • Distinguish an actual duplicate address from routing, VLAN, or physical-layer faults.

Corrective action and closure

  • Obtain authorization for configuration changes.
  • Correct the duplicate assignment using the approved procedure.
  • Verify that the intended device owns the expected address.
  • Test application-level communication.
  • Confirm that the fault does not recur.
  • Update the IP register and maintenance records.
  • Record the confirmed cause and preventive action.

15. Interview Questions and Answers

1. What is an IP conflict?

An IP conflict occurs when multiple devices claim the same IP address within a network scope where that address must be unique.

2. What is the difference between an IP address and a MAC address?

An IP address is a logical network-layer address, while a MAC address identifies a network interface at the data-link layer. ARP maps IPv4 addresses to MAC addresses on a local network.

3. Can two devices use the same private IP address?

Yes, if they are in properly isolated networks. They generally cannot use the same address simultaneously in the same relevant network scope without risking a conflict.

4. Does a successful ping prove that there is no IP conflict?

No. A ping proves that a device responded at that moment. It does not establish that the intended device uniquely owns the address.

5. How does ARP help diagnose a conflict?

ARP information shows the observed mapping between an IPv4 address and a MAC address. Conflicting or changing mappings can indicate a duplicate address, but other network mechanisms must also be considered.

6. Why can a restored IPC image create an IP conflict?

The image may preserve a static address previously assigned to another device, causing the replacement IPC to duplicate an active address.

7. How can DHCP cause an IP conflict?

A DHCP server may allocate an address that is also configured manually, or multiple DHCP servers may have overlapping or uncoordinated scopes.

8. What should be checked before changing a PLC IP address?

Verify device identity, approved network records, subnet, VLAN, dependencies, production impact, authorization, and the rollback procedure.

9. How do you distinguish an IP conflict from a VLAN issue?

Compare device configuration, ARP and MAC information, switch-port VLAN membership, and the intended topology. A VLAN problem may prevent communication without any duplicate address.

10. What is the most important preventive measure?

Maintain an accurate, controlled IP allocation register and make address verification a mandatory step in commissioning, replacement, and maintenance procedures.
