1. Purpose and Scope

IP, I/O, alarm, and interlock lists are controlled engineering documents used to configure, commission, troubleshoot, maintain, and hand over industrial automation systems.

They describe different aspects of the same system:

  • IP list: Identifies devices and their industrial network addressing.
  • I/O list: Identifies signals exchanged between controllers and field devices.
  • Alarm list: Defines abnormal conditions that operators must recognize and respond to.
  • Interlock list: Defines conditions that permit, prevent, stop, or restrict equipment operation.

These lists must agree with the actual installed system, electrical drawings, PLC program, HMI/SCADA configuration, network configuration, and safety documentation.

2. IP List

2.1 Definition

An IP list is a structured register of network-connected devices, their addressing information, communication parameters, and physical or logical network locations.

It supports network commissioning, troubleshooting, cybersecurity, asset identification, and recovery after device replacement.

2.2 Typical IP List Fields

Field Purpose
Device ID Unique identifier for the device
Device name Human-readable equipment name
Device type PLC, HMI, VFD, robot, CNC, switch, PC, or remote I/O
Manufacturer Device manufacturer
Model Exact model or order code
IP address IPv4 or IPv6 address assigned to the device
Subnet mask or prefix Defines the network boundary
Default gateway Route used to reach other networks, where applicable
MAC address Network interface hardware address
VLAN Logical network segment, where applicable
Protocol EtherNet/IP, PROFINET, Modbus TCP, OPC UA, or another protocol
Port or interface Physical port or logical interface identification
Location Panel, machine, cabinet, or network segment
Hostname Configured network name, where applicable
Firmware version Relevant device firmware
Addressing method Static, DHCP, or another supported method
Source of record Configuration file, device inspection, or approved design
Revision and date Document control information

Not every device supports every field. Record what is applicable rather than filling a spreadsheet with fictional certainty.

2.4 IP Addressing Concepts

IP address: A logical address used to identify a network interface for IP communication.

Subnet mask: Defines which address bits identify the network and which identify the host. For example, 255.255.255.0 corresponds to /24.

Default gateway: The router address used to reach destinations outside the local IP subnet. A machine network may not need a default gateway if it is intentionally isolated.

MAC address: A link-layer address associated with a network interface. It is not the same as an IP address and may change when hardware is replaced.

DHCP: Dynamically assigns network settings. Industrial devices requiring predictable addresses may use static addressing or controlled DHCP reservations, depending on the design.

VLAN: Separates traffic into logical Layer 2 network segments. VLANs are not a substitute for a complete security architecture.

Duplicate IP: Two devices using the same IP address can cause intermittent or complete communication failures.

Firmware version: Can affect supported protocols, communication behavior, security features, and compatibility.

2.5 Network Verification

During commissioning or troubleshooting:

  1. Verify the device identity and physical Ethernet connection.
  2. Compare the configured IP address, subnet mask, and gateway with the approved network plan.
  3. Check for duplicate IP addresses.
  4. Verify switch-port configuration, VLAN assignment, and link status.
  5. Check the required protocol, connection path, and port configuration.
  6. Confirm the device appears in the controller or engineering software.
  7. Verify communication using the appropriate diagnostic tools.
  8. Record the final installed configuration and any approved deviations.

A successful ping proves only that a device responds to ICMP under the tested conditions. It does not prove that PLC I/O, EtherNet/IP connections, PROFINET cyclic data, HMI communication, or application-level communication is functioning correctly.

2.6 Industrial Network Design Considerations

  • Separate machine-control traffic from enterprise and guest networks according to the approved architecture.
  • Avoid undocumented changes to IP addresses, VLANs, routes, or switch configurations.
  • Document redundant network paths and ring topologies where present.
  • Record device names and addressing for remote I/O, robots, CNCs, drives, vision systems, and engineering workstations.
  • Protect configuration backups and restrict unauthorized engineering access.
  • Avoid exposing industrial devices directly to public networks.
  • Document managed-switch configurations and recovery procedures.
  • Record whether communication loss should generate an alarm, initiate a controlled stop, or trigger a defined fault response.

The required response to communication loss depends on the machine risk assessment, control design, and applicable safety requirements. An ordinary network timeout is not automatically a safety function.

3. I/O List

3.1 Definition

An Input/Output (I/O) list is an engineering register of signals exchanged between a controller and its connected equipment.

It connects the physical electrical design to the PLC configuration, logic, HMI tags, commissioning tests, and maintenance documentation.

3.2 I/O Categories

I/O type Meaning Examples
DI Digital input Limit switch, pushbutton, auxiliary contact
DO Digital output Contactor command, solenoid command, indicator lamp
AI Analog input Pressure transmitter, temperature transmitter
AO Analog output Speed reference, control-valve command
HSC High-speed counter input Encoder pulse counting
Network I/O Data exchanged over a communication network Robot ready, drive status, CNC cycle state
Safety I/O Safety-rated signals handled by appropriate safety equipment Safety gate switch, emergency-stop channel

The exact channel type and safety classification must match the selected hardware and application.

3.5 Illustrative Analog I/O List

Signal tag Type Description Range Engineering unit
PT_LINE_PRESS AI Line pressure transmitter 4–20 mA bar
TT_OVEN_TEMP AI Oven temperature transmitter 4–20 mA °C
AO_SPEED_REF AO Drive speed reference 0–10 V % reference
AO_VALVE_CMD AO Modulating valve command 4–20 mA % command

Document the raw input range, engineering range, scaling formula, filtering, alarm limits, and behavior during wire break or out-of-range conditions where applicable.

3.6 Analog Scaling Example

Suppose a pressure transmitter measures 0–10 bar and provides 4–20 mA.

The engineering value is:

\[ P = \frac{I-4}{20-4}\times 10 \]

where:

  • \(P\) is pressure in bar.
  • \(I\) is measured loop current in mA.

For a measured current of 12 mA:

\[ P = \frac{12-4}{16}\times 10 = 5\text{ bar} \]

For a controller using raw digital counts, first map the configured raw input range to the 4–20 mA signal range, then convert the normalized value into engineering units. The actual raw limits depend on the analog module and configuration.

3.7 Electrical Signal Details

Digital signals: Record the nominal voltage, sourcing or sinking arrangement, NPN/PNP compatibility, common wiring, polarity, and input filtering where relevant.

Analog signals: Record current or voltage range, active or passive transmitter arrangement, loop supply, channel isolation, scaling, grounding, and shielding requirements.

Pulse and encoder signals: Record signal type, maximum frequency, electrical interface, counting mode, direction, and resolution.

Network I/O: Record the producing and consuming devices, data type, update rate where relevant, communication configuration, and fault behavior.

Safety I/O: Record the safety device, safety controller or relay, channel arrangement, diagnostic coverage where applicable, reset behavior, and validation evidence. Do not treat ordinary PLC inputs and outputs as safety-rated merely because they are used in a safety-related sequence.

3.8 Sink/Source and NPN/PNP

For common DC discrete sensors:

  • PNP sensor: Typically sources positive voltage to the input when active.
  • NPN sensor: Typically sinks current toward 0 V when active.
  • Sourcing input: Provides current to an external load or circuit.
  • Sinking input: Accepts current from an external source.

Compatibility depends on the specific module, sensor, supply arrangement, and wiring. Verify the manufacturer's wiring diagram rather than relying only on the label.

3.9 I/O Commissioning Checks

  1. Verify the field-device tag against the electrical drawing and I/O list.
  2. Confirm supply voltage, fuse protection, common wiring, and polarity.
  3. Operate the field device and verify the correct controller channel changes state.
  4. Confirm the PLC tag and HMI indication match the physical signal.
  5. Test outputs only under an approved safe test procedure.
  6. Verify the correct field device responds to each output.
  7. Check analog scaling against a known input or calibrated simulator.
  8. Test wire-break, short-circuit, and out-of-range diagnostics where supported.
  9. Record pass/fail results, measured values, faults, and corrective actions.
  10. Update the as-built I/O list if approved changes were made.

4. Alarm List

4.1 Definition

An alarm list defines the abnormal conditions presented to operators, the information associated with each alarm, its priority, and the expected operator response.

An alarm should indicate a condition requiring attention or action. Routine status information generally belongs in a status display or event log rather than the alarm system.

4.2 Typical Alarm List Fields

Field Purpose
Alarm ID Unique alarm identifier
Alarm tag PLC or HMI tag associated with the alarm
Alarm message Clear description of the abnormal condition
Trigger condition Logic or measured condition that activates the alarm
Setpoint Configured threshold, where applicable
Priority Relative urgency
Severity Consequence or seriousness of the condition
Delay On-delay, off-delay, or persistence requirement
Deadband Hysteresis used to prevent excessive state changes
Latching behavior Whether the alarm remains active until acknowledged or reset according to design
Acknowledgment Whether operator acknowledgment is required
Operator response Required action to address the condition
Reset condition Condition required to clear the alarm
Interlock relationship Related permissive, stop, or trip function
Source equipment Device or subsystem generating the alarm
Verification method How the alarm is tested
Revision Controlled document revision

4.3 Alarm Priority

A plant may use its own approved priority scheme. One illustrative arrangement is:

Priority Meaning Example
Critical Immediate response required due to severe process or equipment consequences Critical equipment fault requiring immediate intervention
High Urgent operator action required Cooling pressure below a critical operating limit
Medium Prompt investigation or correction required Drive fault preventing production
Low Non-urgent abnormal condition requiring attention Filter service due

Priority should be assigned according to the consequence of the alarm and the time available for an effective response, not merely because the message sounds serious.

4.4 Illustrative Alarm List

Alarm ID Alarm message Trigger condition Priority Operator response
ALM-001 Motor overload trip Overload relay trip feedback active High Inspect motor load and electrical condition
ALM-002 Air pressure low Pressure below configured limit High Check air supply, leaks, and regulator
ALM-003 Drive communication lost Communication watchdog expires High Check network, power, and drive status
ALM-004 Hydraulic temperature high Temperature exceeds configured threshold Medium Inspect cooling and hydraulic condition
ALM-005 Sensor signal invalid Signal diagnostic indicates invalid value Medium Inspect sensor, wiring, and input channel

The examples are generic. Real alarm thresholds, priorities, delays, and operator actions must be engineered for the specific machine.

4.5 Alarm Logic Considerations

Setpoint: The threshold at which a condition becomes abnormal.

Deadband: A range that prevents repeated alarm activation and clearing around a threshold.

On-delay: Requires the condition to persist for a configured time before the alarm activates.

Off-delay: Keeps an alarm active for a defined period after the trigger condition clears.

Latching alarm: Remains active until the designed acknowledgment or reset conditions are met.

Acknowledgment: Records that the operator has recognized the alarm. It does not necessarily remove the fault or make the machine safe to restart.

First-out indication: Identifies the initiating fault when several alarms occur in sequence, where the system supports reliable first-out capture.

Alarm suppression: Temporarily prevents an alarm from being annunciated under approved conditions. Suppression must be controlled and visible to authorized personnel.

4.6 Alarm Design Principles

  • Use concise messages that identify the affected equipment and condition.
  • Prefer actionable messages over vague messages such as FAULT 17.
  • Distinguish the alarm condition from the operator's required response.
  • Use consistent tags, naming, priorities, and units.
  • Avoid nuisance alarms caused by noisy signals, unsuitable delays, or poor deadband selection.
  • Provide context for alarms that may appear together.
  • Record alarm activation, acknowledgment, clearing, and relevant timestamps where required.
  • Define startup, maintenance, bypass, and communication-loss behavior.
  • Test alarm activation and clearing independently.
  • Ensure alarm handling does not replace required safety functions.

5. Interlock List

5.1 Definition

An interlock list records the conditions that allow or prevent a machine, process, or individual device from performing an operation.

Interlocks are used to enforce operating sequences, protect equipment, prevent process conflicts, and support safe machine behavior.

5.2 Common Interlock Types

Permissive: A condition that must be satisfied before an operation can start.

Start interlock: Prevents starting when one or more required conditions are not satisfied.

Running interlock: Monitors conditions while equipment is operating and initiates a defined response if a condition becomes false.

Trip: A condition that causes equipment or a process to stop or enter a defined fault state.

Inhibit: Prevents a command or action under specified conditions.

Sequence interlock: Ensures that one operation occurs only after another required step or confirmation.

Mutual exclusion interlock: Prevents two incompatible actions from occurring simultaneously.

Safety interlock: A safety-related function designed and validated to reduce risk, implemented using appropriately selected safety components and architecture.

5.3 Typical Interlock List Fields

Field Purpose
Interlock ID Unique interlock identifier
Equipment tag Machine or device affected
Interlock description Functional purpose
Initiating condition Signal or condition that activates the interlock
Required state State needed for permission or continued operation
Logic condition Boolean or functional expression
Action Start inhibit, controlled stop, trip, or other defined response
Reset condition Conditions required before reset
Restart behavior Whether restart is manual or automatic under approved conditions
Alarm reference Related operator alarm
I/O references Relevant input and output tags
PLC or safety controller Controller implementing the function
Drawing reference Relevant electrical or functional drawing
Verification method Test procedure
Revision Controlled document revision

5.4 Illustrative Interlock List

Interlock ID Equipment Required condition Action if condition fails
INT-001 Conveyor motor Guard permissive and drive ready Prevent start or stop according to the validated design
INT-002 Hydraulic pump Oil level acceptable and overload healthy Inhibit start or trip as specified
INT-003 Pneumatic clamp Required pressure available Inhibit clamping sequence
INT-004 Robot cycle Robot ready and fixture in required position Prevent cycle start
INT-005 CNC automatic cycle Door status and required machine conditions valid Prevent cycle start or invoke the designed response

These examples illustrate documentation structure, not complete functional-safety specifications. Actual responses must follow the machine's approved design.

5.5 Boolean Logic Example

A basic standard-control permissive might be represented as:

\[ \text{StartPermissive} = \text{DriveReady} \land \text{PressureOK} \land \text{ProcessReady} \]

The command logic could be:

\[ \text{RunCommand} = \text{StartRequest} \land \text{StartPermissive} \]

This demonstrates ordinary Boolean logic only. It is not a complete motor-control or safety circuit. A real design may also require stop handling, seal-in logic, fault latching, restart prevention, timeout monitoring, and specific responses to communication failures.

5.6 Permissive Versus Interlock

Feature Permissive Interlock
Primary purpose Establish whether an action is allowed Restrict or terminate an action under defined conditions
Typical timing Checked before an operation starts May be checked before and during operation
Example Pressure must be adequate before starting a clamp sequence Loss of required pressure interrupts the sequence
Possible result Start is prevented Start is prevented or an operating response is initiated
Reset Depends on the condition and design Depends on the initiating condition and interlock design

Industrial terminology varies. Some plants use interlock as the umbrella term for all permissives and operating restrictions. Follow the site's approved terminology.

5.7 Safety Interlocks Versus Standard PLC Interlocks

This distinction is essential.

Standard PLC interlocks implement ordinary machine sequencing and equipment protection. A standard PLC, ordinary I/O, and conventional program logic are not automatically suitable for safety-related functions.

Safety-related interlocks implement functions required by the risk assessment, such as guard monitoring or emergency-stop response. Their design may require safety-rated sensors, safety relays or safety PLCs, suitable output devices, defined fault behavior, and documented validation.

Applicable requirements depend on the machine, jurisdiction, risk assessment, and required performance level or safety integrity level.

Never bypass a safety interlock merely to restore production. Any approved bypass or muting arrangement must be specifically designed, risk-assessed, controlled, indicated, and validated as required. A normal PLC bit forced to TRUE is not a legitimate safety strategy.

6. Relationships Between the Four Lists

The lists are separate documents, but their tags and references must be consistent.

IP List
  → Identifies network devices and addressing
  → Supports PLC, HMI, drive, robot, CNC, and remote I/O communication

I/O List
  → Identifies physical and logical signals
  → Links field devices, controller tags, and drawings

Alarm List
  → Defines abnormal conditions and operator notifications
  → References the relevant signal, device, and fault condition

Interlock List
  → Defines operating permissions and required responses
  → References relevant signals, equipment, alarms, and control logic

For example, a remote I/O adapter may appear in the IP list, while its pressure-switch channel appears in the I/O list. A low-pressure condition may generate an alarm, while the same condition prevents a clamp sequence from proceeding.

The alarm and interlock may share a triggering condition, but they are not the same function. The alarm informs the operator; the interlock controls permitted behavior.

7. Tag Naming and Cross-Referencing

7.1 Tag Naming

A consistent tag convention improves readability, searchability, troubleshooting, and integration across engineering tools.

Illustrative tags:

Tag Meaning
PLC_01 Main PLC
PT_101 Pressure transmitter
PSL_101 Low-pressure switch or low-pressure function, according to site convention
MTR_101 Motor
VFD_101 Variable-frequency drive
LS_101 Limit switch
ALM_101 Alarm identifier
INT_101 Interlock identifier

Prefixes such as PT, PSL, and LS must follow the project's defined tagging standard. Their meaning should not be assumed across all organizations.

7.2 Cross-Reference Example

Engineering item Related reference
Pressure transmitter PT_101 I/O list, analog channel, instrument drawing
Remote I/O adapter RIO_01 IP list, network topology, hardware configuration
Low-pressure alarm ALM_101 Alarm list, HMI message, pressure signal
Clamp permissive INT_101 Interlock list, PLC logic, pneumatic schematic
Clamp solenoid SV_101 I/O list, output channel, electrical and pneumatic drawings

Use unique identifiers wherever practical. Avoid assigning the same tag to different devices or changing a tag without updating all dependent records.

8. Functional Verification and Commissioning

8.1 IP List Verification

  • Confirm every relevant network device is recorded.
  • Verify IP addresses and subnet settings against the approved design.
  • Check for duplicate addresses.
  • Confirm network paths, switch ports, and VLANs where applicable.
  • Verify the actual industrial communication protocol.
  • Record final addresses, device names, and approved deviations.
  • Save network configurations and backups according to the site procedure.

8.2 I/O List Verification

  • Confirm each field device against the electrical drawing.
  • Verify channel assignments and controller configuration.
  • Test each digital input with the correct field device.
  • Verify each output using an approved safe test procedure.
  • Validate analog scaling and engineering units.
  • Verify fault diagnostics where supported.
  • Check PLC, HMI, and field-device tag consistency.
  • Record test results and unresolved defects.

8.3 Alarm List Verification

  • Test each alarm's trigger condition.
  • Verify alarm message, priority, and affected equipment.
  • Confirm delay and deadband behavior.
  • Verify acknowledgment and reset behavior.
  • Check alarm clearing and return-to-normal behavior.
  • Confirm the operator response is appropriate.
  • Test communication-loss and device-fault alarms where applicable.
  • Record any suppressed, disabled, or unavailable alarms.

8.4 Interlock List Verification

  • Test each permissive under approved conditions.
  • Verify that prohibited starts are blocked.
  • Test running-condition failures and the specified response.
  • Confirm fault latching and reset behavior.
  • Verify that reset does not cause an unexpected restart.
  • Test mutual exclusion and sequence restrictions.
  • Verify safety-related functions through their approved validation procedures.
  • Record results, deviations, and corrective actions.

8.5 Functional Test Matrix

Test ID Test condition Expected result Evidence
TST-001 Network device loses communication Defined diagnostic and process response occurs Diagnostic log and test record
TST-002 Digital input changes state Correct PLC tag changes state I/O test sheet
TST-003 Analog simulator applies a known value Displayed engineering value is within acceptance tolerance Calibration or test record
TST-004 Alarm trigger condition occurs Correct alarm appears with configured priority Alarm test record
TST-005 Start permissive is absent Start is prevented Functional test record
TST-006 Interlock condition fails during operation Defined response occurs Functional test record
TST-007 Required reset conditions are restored Reset behavior matches the approved design Reset test record

Define the actual test method, acceptance criteria, responsible person, test date, and evidence location in the project test procedure.

9. Troubleshooting Using the Lists

Symptom Useful document Checks
PLC cannot communicate with a drive IP list Addressing, subnet, switch port, protocol, connection configuration
Sensor operates but PLC input does not change I/O list Supply, wiring, polarity, channel assignment, module status
HMI shows the wrong pressure I/O list and alarm list Scaling, units, tag mapping, transmitter range
Alarm appears repeatedly Alarm list Noisy signal, deadband, delays, unstable process condition
Machine will not start Interlock list Missing permissives, active faults, sequence state
Machine stops unexpectedly Interlock and alarm lists Initiating condition, first-out evidence, controller diagnostics
Replacement device fails to communicate IP list and hardware records Address, firmware, configuration, compatibility
Field wiring differs from the documentation I/O list and electrical drawings Physical tracing, approved change records, as-built correction

Do not begin by changing PLC logic blindly. Identify the initiating condition, compare the live system with the controlled documentation, and verify the result of each diagnostic step.

10. Revision Control and Change Management

These lists must describe the approved installed configuration, not merely the original design.

Changes may arise from:

  • Device replacement or model substitution.
  • PLC rack, module, channel, or tag changes.
  • IP address or network topology changes.
  • New alarms, changed thresholds, or modified priorities.
  • Changed interlock conditions, reset behavior, or operating sequences.
  • Field wiring modifications.
  • Equipment relocation or machine retrofit.
  • Firmware, communication, or configuration changes.

For each change, record:

  1. Change request or engineering change reference.
  2. Reason for the change.
  3. Original configuration and proposed configuration.
  4. Technical review and required approvals.
  5. Affected drawings, lists, PLC logic, HMI configuration, and test procedures.
  6. Risk assessment or safety review where applicable.
  7. Test results and acceptance.
  8. Final document revision and approval date.

An undocumented change creates a gap between the physical machine and its engineering records. That gap becomes especially dangerous during fault recovery, equipment replacement, or safety validation.

13. Final Handover Acceptance Checklist

  • IP list matches the approved and installed network configuration.
  • I/O list matches the installed hardware, field wiring, and PLC configuration.
  • Alarm list matches the HMI/SCADA configuration and approved alarm philosophy.
  • Interlock list matches the implemented control logic and approved functional design.
  • Safety-related functions have the required validation evidence.
  • Cross-references and equipment tags are consistent.
  • Test results, deviations, and outstanding actions are documented.
  • As-built drawings and configuration backups reflect approved changes.
  • Revisions, approvals, dates, and document owners are recorded.
  • Required files are accessible to authorized maintenance and engineering personnel.
  • Configuration backups and access credentials are handled securely.
  • The receiving team has accepted the documentation package.

The governing principle is simple: every documented address, signal, alarm, and interlock must be traceable to the actual system, and every approved change must be reflected in the relevant records.
