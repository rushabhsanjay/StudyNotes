1. Definition and Purpose

A backup is a separate, recoverable copy of data, software, configuration, or system state that can be used to restore information or functionality after loss, corruption, accidental modification, equipment failure, cyberattack, or a planned change that fails.

In industrial automation, backups protect the information required to operate and maintain machines. This includes PLC programs, HMI and SCADA projects, industrial PC configurations, CNC parameters, robot programs, VFD settings, databases, network configurations, recipes, calibration data, and technical documentation.

A backup is useful only when the required information has been captured correctly, stored safely, kept compatible with the target system, and shown to be recoverable.

A file existing in a folder does not prove that a usable backup exists. It may be incomplete, outdated, corrupted, encrypted by malware, or incompatible with the equipment.

2. Objectives of Industrial Backup Management

  1. Restore equipment after hardware or software failure.
  2. Recover from accidental deletion or incorrect modification.
  3. Protect against ransomware and other cyber incidents.
  4. Preserve approved software and machine configurations.
  5. Reduce machine downtime during recovery.
  6. Protect production recipes, test parameters, and quality records.
  7. Preserve historical data and evidence needed for troubleshooting.
  8. Support equipment replacement, migration, and obsolescence management.
  9. Establish a known-good configuration before engineering changes.
  10. Meet plant requirements for data retention, traceability, and disaster recovery.

3. Backup Versus Related Terms

Term Meaning Industrial example
Backup Separate copy intended for recovery Approved PLC project stored in controlled backup storage
Restore Process of returning backed-up data or configuration to use Restoring an HMI project
Recovery Broader process of bringing a system back into service Rebuilding an industrial PC and reconnecting it to the line
Archive Retained record preserved for reference or long-term retention Historical approved PLC revisions
Replication Copying data between systems, often continuously or frequently Replicating SCADA database records
Synchronization Making data sets match according to defined rules Syncing an engineering folder
Snapshot Point-in-time representation of a system or data volume Virtual machine snapshot before an update
Image backup Copy of a system volume or complete computer configuration Industrial PC recovery image
Export Saving selected configuration or data in a transferable format Exporting VFD parameters
Version control Tracking changes and revisions to files Maintaining PLC source revisions in a repository

These mechanisms are not interchangeable. Replication can copy corruption or malicious encryption to another location. A snapshot may depend on the original storage system. An archive may preserve history without being ready for immediate restoration.

A robust recovery strategy combines appropriate methods rather than assuming that one copy mechanism solves every problem.

4. What Must Be Backed Up?

The required backup scope depends on the equipment, its architecture, its failure consequences, and the plant's recovery objectives.

Asset category Backup items
PLC Editable project, hardware configuration, tags, relevant device configuration
Safety PLC Approved safety project and associated configuration and validation records
HMI Engineering project, screens, tags, alarms, recipes, runtime configuration
SCADA Project, tag configuration, alarm settings, reports, interface configuration
Industrial PC System image or rebuild package, drivers, applications, configuration
SQL database Database backups, schema, required logs, recovery configuration
VFD Parameter set, motor settings, communication configuration
Servo Parameter set, feedback configuration, motion-related settings
CNC Machine parameters, approved programs, relevant machine-builder configuration
Robot Programs, frames, tool data, controller configuration and applicable recovery files
Vision system Inspection jobs, camera parameters, calibration and lighting settings
Industrial network Switch and gateway configurations, addressing records, approved network settings
Test equipment Test sequences, limits, calibration data, recipes and test software
Production systems Recipes, product definitions, relevant master data
Documentation Electrical drawings, I/O lists, manuals, software register, change history

Not every item is backed up in the same way. For example, a PLC engineering project, a controller's uploaded program, and a PLC's retained runtime values may be separate assets requiring different capture methods.

5. Backup Types

5.1 Full Backup

A full backup captures the defined scope of data in a single backup set.

Advantages:

  • Straightforward recovery structure.
  • Does not require earlier incremental backups to reconstruct the captured state.
  • Useful as a baseline before major changes.
  • Can simplify verification when the scope is well defined.

Limitations:

  • May require more time and storage.
  • Large backups can take longer to transfer or verify.
  • A full backup of a computer does not automatically include every external device configuration.

5.2 Incremental Backup

An incremental backup captures changes since the last successful backup in the backup chain, commonly the last full or incremental backup.

Advantages:

  • Usually smaller and faster than a full backup.
  • Reduces storage and transfer requirements.

Limitations:

  • Recovery may depend on the full backup and every required incremental set.
  • A missing or damaged link can prevent recovery to the desired point.
  • The complete backup chain must be managed and tested.

5.3 Differential Backup

A differential backup captures changes since the last full backup.

Advantages:

  • Recovery generally requires the full backup and the latest applicable differential backup.
  • Can simplify recovery compared with a long incremental chain.

Limitations:

  • Differential sets may grow as more changes accumulate.
  • Storage requirements may increase before the next full backup.

5.4 Image-Based Backup

An image backup captures a computer's disk or system volume, including the selected operating system, applications, and configuration.

Typical uses include industrial PCs, SCADA servers, and engineering workstations.

Important limitations:

  • Recovery may depend on compatible hardware or a supported restoration environment.
  • Some image methods do not capture external devices or separate data volumes.
  • Application licenses may require reactivation.
  • A restored image may require network, security, or device-specific adjustments.
  • Images of running systems must be created using a method that produces a consistent result.

5.5 Application-Native Backup

An application-native backup uses the manufacturer's supported export or backup method.

Examples include:

  • PLC engineering project archives.
  • Robot controller backups.
  • CNC machine configuration exports.
  • VFD parameter exports.
  • SCADA application backups.
  • Database-native backup files.

This is often essential because a generic file copy may not capture all required application metadata or produce a consistent recovery set.

5.6 Configuration Export

A configuration export captures selected settings rather than the entire system.

Examples include drive parameters, managed-switch configuration, camera settings, and device communication parameters.

A configuration export may be small and easy to store, but it may not contain firmware, licenses, application software, calibration references, or other dependencies required for full recovery.

6. Choosing the Correct Backup Method

SCADA Application backup plus database-aware backup where applicable Project and data recovery are coordinated

The method must be chosen for the actual device and software. Never assume that copying a memory card, controller file, or application folder captures everything needed for restoration.

7. The 3-2-1 Backup Rule

The 3-2-1 rule is a common backup design principle:

  • Maintain at least 3 copies of important data, including the working copy.
  • Store copies on at least 2 different types of storage or independently managed storage systems.
  • Keep at least 1 copy off-site or otherwise isolated from the primary location.

For industrial automation, this principle must be adapted to operational and cybersecurity requirements. A production PLC cannot necessarily be backed up continuously like a file server, and an offline copy of a PLC project does not replace a complete server backup.

7.1 Example for an Industrial Test Bench

  • Working copy: approved project or configuration used by the installed system.
  • Local recovery copy: controlled backup repository on a separate storage system.
  • Isolated copy: offline or independently protected copy stored in an approved location.

For critical systems, the isolated copy should not be permanently exposed to the same network credentials or write permissions as the production environment.

A backup located on a network share that ransomware can encrypt using the same compromised account may not provide meaningful isolation.

7.2 Independent Copies Matter

Three folders on the same disk are not three independent backup copies. A disk failure, fire, theft, or destructive malware event may eliminate all of them.

The storage architecture should account for common failure causes, physical separation, access control, and the time required to retrieve a recovery copy.

8. Offline, Immutable, and Off-Site Backups

These terms describe different protection mechanisms.

Method Description Main benefit
Offline backup Disconnected from the production network or powered down when not in use Reduces exposure to network-based attacks
Immutable backup Protected against modification or deletion for a defined retention period Helps resist malicious or accidental alteration
Off-site backup Stored at a separate physical location Protects against site-level disasters
Access-isolated backup Uses separate credentials, permissions, or administrative controls Limits the impact of compromised production accounts
Air-gapped backup Has no active electronic connection to the protected network during isolation Provides strong separation when correctly implemented

These methods can overlap. For example, an off-site repository may also be immutable, and a removable backup may be offline while stored securely.

For industrial systems, media handling must also consider malware scanning, chain of custody, compatibility, and the risks of introducing unapproved files to engineering workstations.

9. Backup Frequency and Scheduling

Backup frequency should reflect how often data changes, the consequences of losing changes, and the time needed to reconstruct them.

9.1 Typical Scheduling Considerations

Asset Scheduling consideration
PLC program After approved changes, commissioning milestones, and defined periodic reviews
Safety PLC project After authorized changes and required validation milestones
HMI/SCADA project After approved changes and before planned upgrades
VFD/servo parameters After commissioning or authorized parameter changes
Robot/CNC configuration After approved program or configuration changes
Industrial PC image After a known-good baseline is established and significant system changes
SQL database According to transaction volume, recovery objectives, and database architecture
Recipes and product data According to change rate, production impact, and quality requirements
Network configuration After approved changes and before network maintenance
Engineering workstation After software installation, configuration changes, and approved baseline updates

These are scheduling principles, not universal intervals. A critical production database may require frequent automated backups, while a stable PLC project may be backed up after each controlled change and periodically verified.

9.2 Event-Driven Backups

Create or verify a recoverable baseline before:

  • PLC program downloads or major logic changes.
  • HMI or SCADA upgrades.
  • Firmware updates.
  • Controller or drive replacement.
  • PC operating-system upgrades.
  • Network reconfiguration.
  • Recipe or machine-parameter changes.
  • Vendor service work.
  • Major commissioning or retrofit activities.

The backup must be taken at the correct point in the change process. A pre-change backup supports rollback, while a verified post-change backup preserves the newly approved state.

10. Recovery Objectives: RPO and RTO

Two important metrics define the business requirements for recovery.

10.1 Recovery Point Objective (RPO)

RPO is the maximum acceptable amount of data loss measured in time.

For example, an RPO of 15 minutes means the recovery strategy should limit lost data to no more than the equivalent of 15 minutes of changes under the defined failure scenario.

If a database fails at 14:00 and the latest recoverable data is from 13:50, the data-loss interval is 10 minutes.

10.2 Recovery Time Objective (RTO)

RTO is the target time within which a system or service must be restored after a disruption.

For example, if an automated inspection station has an RTO of two hours, the recovery plan should target restoration of the defined inspection function within that period.

RTO must specify what counts as restored: a computer booting is not equivalent to a machine completing a verified production cycle.

10.3 Example

System Illustrative RPO Illustrative RTO
PLC-controlled test bench Last approved software change 2 hours
SCADA database 15 minutes 4 hours
Production recipe store 15 minutes 1 hour
Engineering workstation 24 hours 8 hours

These figures are examples only. Actual objectives must be based on production impact, data criticality, technical feasibility, and plant requirements.

10.4 Practical Interpretation

A low RPO requires a method that captures changes frequently enough to meet the target. A low RTO requires prepared recovery tools, available replacement hardware where needed, documented procedures, compatible software, and trained personnel.

A backup schedule alone does not guarantee either objective.

11. Database Backups and Transaction Consistency

Databases require particular care because the files that constitute a database may be changing while a backup is running.

For systems such as SQL Server, use supported database-backup procedures and an appropriate recovery model instead of treating an arbitrary copy of live database files as a reliable backup.

11.1 Common Database Backup Types

  • Full backup: Captures the database at the backup point.
  • Differential backup: Captures changes since the relevant full backup.
  • Transaction log backup: Captures log records needed for supported recovery sequences and point-in-time recovery.

The availability and usefulness of transaction log backups depend on the database recovery model and configuration.

11.2 Database Handover and Backup Requirements

  • Record database name, server identity, and application dependencies.
  • Document the recovery model and backup schedule.
  • Define retention and storage requirements.
  • Protect database credentials.
  • Preserve schema and relevant application configuration.
  • Monitor backup-job success and failure.
  • Validate backup files and perform restore tests.
  • Document the recovery sequence and any required log chain.
  • Check application compatibility after restoration.
  • Verify data integrity and timestamps after recovery.

11.3 Example: Industrial Data Collection

A Node-RED service may collect PLC values and write them to a SQL Server database while Grafana reads the same data for dashboards.

The recovery plan must address the components separately:

  • PLC project and controller configuration.
  • Node-RED flows, required modules, and settings.
  • SQL database and applicable transaction logs.
  • Grafana configuration and dashboards.
  • Industrial PC or server environment.
  • Network configuration and communication dependencies.
  • Credentials and service-account arrangements.

Restoring the database alone may recover historical data but leave the data-collection service unable to reconnect. Restoring the Node-RED flows alone may restart collection but cannot recreate lost historical records.

12. PLC Backup and Recovery

PLC backups require platform-specific procedures because controller memory, engineering projects, firmware, retentive values, and safety configurations may be handled differently.

12.1 What to Capture

  • Complete editable engineering project.
  • Hardware configuration and module inventory.
  • Program blocks, routines, and tags.
  • Relevant communication settings.
  • Required libraries and device descriptions.
  • CPU model and firmware version.
  • Approved online/offline comparison evidence where supported.
  • Retentive data requirements, if relevant.
  • Relevant safety project and validation records.
  • Instructions for replacing the controller and restoring the application.

12.2 Before Downloading or Restoring

  • Confirm the target controller and hardware.
  • Confirm that the backup matches the machine.
  • Verify compatibility between the project, firmware, and modules.
  • Identify the impact on production and connected devices.
  • Obtain the required authorization.
  • Apply the plant's safe-state and isolation procedures.
  • Verify the approved restoration method.
  • Confirm that any retained values, calibration data, and communication settings are addressed.

Downloading a project can overwrite a functioning program or change machine behavior. Never treat a restoration as a harmless file operation.

12.3 Upload Is Not Always Equivalent to Source Backup

An upload from a PLC may not reconstruct the original engineering project completely. Comments, symbolic information, source structures, libraries, or other engineering metadata may be missing depending on the platform and how the program was downloaded.

Keep the original approved engineering project wherever required, and use controller uploads as additional verification or recovery artifacts rather than assuming they are always complete replacements.

13. HMI and SCADA Backup and Recovery

HMI and SCADA applications often depend on multiple components that must be restored in a compatible order.

13.1 HMI Backup Contents

  • Engineering project.
  • Runtime deployment files where required.
  • Tag and communication configuration.
  • Alarm and event settings.
  • Recipes and relevant operator configuration.
  • Panel-specific configuration.
  • Required runtime version and license information.

13.2 SCADA Backup Contents

  • Application project.
  • Server and client configuration.
  • Tag database and communication settings.
  • Alarm, trend, and report configuration.
  • Database configuration and backup dependencies.
  • Certificates and other required trust configuration, handled securely.
  • Service accounts and permissions, documented without exposing secrets.
  • License and runtime requirements.
  • Redundancy and failover settings where applicable.

13.3 Restoration Verification

After restoration, verify:

  • The application starts correctly.
  • PLC and device communication is functioning.
  • Tags update with valid quality or status.
  • Alarms activate and acknowledge as intended.
  • Trends and historical records behave correctly.
  • Recipes and user permissions are correct.
  • Required services restart automatically.
  • The system meets applicable production and safety requirements.

14. VFD, Servo, CNC, and Robot Backups

14.1 VFD and Servo Drives

Back up manufacturer-supported parameter exports and record the drive model, firmware, motor data, feedback configuration, communication settings, and relevant commissioning details.

Before restoring parameters, verify the target drive and motor. Settings from another application may be unsuitable even if the drive model is identical.

14.2 CNC Systems

Preserve the approved machine-specific parameters, programs, offsets where applicable, builder configuration, and supported recovery files.

Restoration must follow the CNC and machine-builder procedure. Generic controller files must not be substituted for machine-specific configuration.

14.3 Robot Systems

Use the controller manufacturer's supported backup method and preserve approved programs, frames, tool data, configuration, and relevant recovery records.

Verify the robot model, controller, software version, tooling, and workcell before restoring. Calibration, mastering, and safety-related settings may need special handling or separate validation.

14.4 Safety-Related Configuration

Never blindly restore a safety configuration from another machine or an older revision. Verify identity, revision, compatibility, required signatures or checksums, and validation status. Any change affecting a safety function must be handled under the applicable safety lifecycle and site procedures.

15. Industrial PC and Engineering Workstation Backups

An industrial PC can be difficult to rebuild if its original installation media, drivers, license activation, and configuration are unavailable.

15.1 Recommended Backup Set

  • Full system image or approved rebuild package.
  • Operating-system version and configuration.
  • Installed applications and versions.
  • Drivers and communication packages.
  • Application configuration files.
  • Engineering projects and relevant libraries.
  • Database or local data exports where applicable.
  • Network configuration records.
  • License recovery information.
  • Installation and restoration instructions.

15.2 Image Backup Versus Rebuild Procedure

A system image may allow a faster recovery when supported hardware and recovery tools are available. A rebuild procedure may be preferable where images are incompatible with replacement hardware, licensing restrictions apply, or security policy requires a fresh installation.

For critical systems, maintain a documented alternative if the preferred image cannot be restored.

15.3 Validation

  • Verify that the image or installation package is readable.
  • Record the supported hardware and operating-system requirements.
  • Confirm required licenses can be reactivated.
  • Test the restoration procedure in an appropriate environment.
  • Confirm communication with controllers, databases, and other systems.
  • Verify the application using approved functional tests.

16. Network and Communication Configuration Backups

Industrial networks depend on configuration data that may not be obvious from the equipment's physical wiring.

Relevant assets include managed switches, routers, firewalls, gateways, wireless bridges, OPC servers, protocol converters, and remote I/O adapters.

16.1 What to Preserve

  • Device identity and model.
  • Firmware and configuration versions.
  • Approved IP addresses and subnet information.
  • VLAN and routing configuration where applicable.
  • Port assignments and network topology.
  • Relevant communication and security settings.
  • Industrial protocol configuration.
  • Certificates and trust relationships where required.
  • Configuration export files.
  • Device replacement and restoration instructions.

Sensitive network information should be access-controlled. Do not publish passwords, private keys, or other secrets in ordinary backup registers.

16.2 Recovery Risks

Restoring a switch configuration to a different model or firmware version may not work as expected. Incorrect VLAN, routing, or security settings can disconnect PLCs, HMIs, remote I/O, or supervisory systems.

Before applying a network configuration, verify device compatibility, intended topology, change authorization, and the availability of a rollback method.

17. Backup Integrity and Verification

Backup verification checks whether the stored copy is intact, complete enough for its intended purpose, and suitable for recovery.

17.1 Common Verification Methods

  • Confirm the backup job completed successfully.
  • Check file size and expected file contents.
  • Verify the file can be opened by the relevant application.
  • Compare checksums where appropriate.
  • Review application-native verification results.
  • Confirm the backup corresponds to the correct asset and revision.
  • Inspect logs for warnings or incomplete operations.
  • Perform a controlled restoration test.
  • Confirm restored functionality using defined acceptance criteria.

17.2 Checksums

A cryptographic hash, such as SHA-256, can help establish whether a file has changed since the checksum was recorded.

For a file \(F\), the hash is represented as:

\[ H = \operatorname{SHA256}(F) \]

If a newly calculated hash differs from the recorded hash, the file contents differ. This does not automatically prove corruption or malicious activity, but it signals that the change must be investigated.

A matching checksum proves byte-level consistency with the recorded reference. It does not prove that the file is complete, compatible, or restorable.

17.3 Verification Record

Field Purpose
Backup ID Unique backup record
Asset ID Identifies the protected system
Backup date and time Records capture time
Source revision Identifies the captured configuration
Backup method Records native export, image, database backup, or other method
Storage location Identifies the controlled destination
Job result Records success, failure, or warnings
Integrity check Records checksum or other verification
Restore test date Records the latest restoration test
Restore result Records whether defined criteria were met
Responsible person Identifies the owner of the record

18. Restoration Testing

A backup that has never been restored is an unproven recovery mechanism.

18.1 Types of Restore Test

  • File-level test: Confirms that files can be accessed and opened.
  • Application-level test: Confirms that the relevant software can load the backup.
  • Configuration-level test: Confirms that configuration can be applied to a suitable target.
  • System-level test: Confirms that the defined system can be restored.
  • Functional test: Confirms that required behavior works after restoration.
  • Disaster-recovery exercise: Tests the wider recovery process, including personnel, hardware, access, dependencies, and time targets.

A test appropriate for a PLC engineering project differs from one appropriate for a SQL database or a full industrial PC image.

18.2 Safe Restore Testing

  • Use a suitable test environment, spare device, virtual environment, or isolated test system where feasible.
  • Obtain authorization before interacting with production equipment.
  • Prevent unintended communication with live machines during offline tests.
  • Avoid connecting restored duplicate systems to production networks without a controlled plan.
  • Apply the correct firmware and compatibility checks.
  • Protect safety-related configuration and follow its validation requirements.
  • Record the test method, outcome, defects, and corrective actions.

A test environment that unexpectedly communicates with a production PLC can create real operational consequences. Isolation is part of the test design, not an optional finishing touch.

19. Backup Retention and Storage Capacity

Retention defines how long backup copies are preserved before they may be deleted or superseded.

A retention policy should consider operational recovery, quality traceability, legal obligations, audit requirements, storage capacity, and cybersecurity incidents that may remain undetected for some time.

19.1 Retention Categories

Category Purpose
Short-term operational copies Recover from recent mistakes or failures
Periodic recovery copies Restore a previous known-good state
Approved software baselines Preserve validated machine configurations
Long-term archives Retain records for defined historical or compliance needs
Incident recovery copies Preserve selected copies for investigation and recovery

The organization should define retention periods and deletion authority. Do not delete the last known-good copy simply because a newer file has appeared.

19.2 Capacity Planning

Storage requirements depend on backup size, frequency, retention, compression, deduplication, and the number of versions retained.

A rough estimate for uncompressed full backups is:

\[ S = N \times B \]

where \(S\) is required storage, \(N\) is the number of retained copies, and \(B\) is the size of each copy.

This simple estimate excludes incremental changes, metadata, redundancy, growth, and reserved capacity. Real storage planning must include those factors.

20. Backup Security and Cybersecurity

Backup storage is a high-value target because it may contain the information needed to rebuild production systems.

20.1 Essential Controls

  • Separate backup administration from routine production administration where feasible.
  • Use unique accounts and least-privilege permissions.
  • Protect backup repositories against unauthorized deletion or modification.
  • Use offline or immutable copies for critical assets where practical.
  • Encrypt sensitive backup data in storage and transit where required.
  • Protect encryption keys separately from the data they protect.
  • Scan imported files through approved security procedures.
  • Log backup access, changes, and deletion.
  • Test recovery from isolated copies.
  • Restrict removable media and document its handling.
  • Maintain a secure record of license and credential recovery procedures.

20.2 Ransomware Considerations

A backup repository may be compromised if it uses the same administrator credentials, network access, or permissions as the production system.

Controls should therefore address identity separation, write access, administrative privileges, isolation, monitoring, and recovery copies that cannot be easily altered from the production environment.

Backups should also be protected against deliberate deletion, accidental overwriting, theft, and physical damage.

21. Backup Management in SAP and CMMS

SAP or a computerized maintenance management system may be used to record backup requirements, link backups to equipment, and track verification activities. The exact implementation depends on the organization's configuration.

21.1 Useful Equipment and Maintenance Records

  • Equipment ID and functional location.
  • Software or configuration asset ID.
  • Backup frequency and required method.
  • Storage location reference.
  • Last successful backup date.
  • Last integrity verification date.
  • Last restore test date and result.
  • Responsible owner.
  • Related maintenance order or engineering-change record.
  • Open backup-related defects.

The actual backup files may be held in an approved repository rather than directly in SAP. The maintenance record should identify the authoritative location and preserve traceability.

21.2 Practical Maintenance Workflow

  1. Identify the affected equipment and required configuration.
  2. Check the approved baseline and last successful backup.
  3. Create or verify the required pre-change backup.
  4. Perform the authorized maintenance or engineering change.
  5. Test the changed system.
  6. Capture the approved post-change configuration.
  7. Verify the stored copy and update the register.
  8. Link the evidence to the relevant maintenance or change record.

22. Backup KPIs and Performance Measurement

Backup management should be measured using defined, auditable indicators.

22.1 Backup Success Rate

\[ \text{Success Rate} = \frac{\text{Successful Backup Jobs}}{\text{Scheduled Backup Jobs}} \times 100\\% \]

The reporting period and treatment of skipped or cancelled jobs should be defined.

22.2 Restore-Test Pass Rate

\[ \text{Restore-Test Pass Rate} = \frac{\text{Passed Restore Tests}}{\text{Completed Restore Tests}} \times 100\\% \]

This measures the outcome of tested restorations, not the percentage of all backups that are recoverable.

22.3 Backup Coverage

\[ \text{Backup Coverage} = \frac{\text{Required Assets With Current Verified Backups}}{\text{Total Assets Requiring Backups}} \times 100\\% \]

The organization must define what counts as current and verified for each asset category.

22.4 Other Useful Indicators

  • Number of overdue backups.
  • Number of failed backup jobs.
  • Number of critical assets without tested recovery copies.
  • Time required to restore selected systems.
  • Percentage of backups meeting retention requirements.
  • Number of unresolved backup-related audit findings.
  • Percentage of assets with documented recovery procedures.

A 100% backup-job success rate does not guarantee recovery readiness. It must be interpreted alongside verification, restore-test results, coverage, and recovery performance.

23. Backup Handover Documentation

At project completion, the supplier or system integrator should provide the backup deliverables and enough information for the plant to manage them independently.

23.1 Required Documentation

  • Backup register covering the relevant equipment.
  • List of files, projects, and configurations included in each backup.
  • Backup method and required software tools.
  • Source equipment identity and software revision.
  • Backup date and verification status.
  • Storage locations and access requirements.
  • Retention and rotation policy.
  • Recovery procedures and dependencies.
  • Required firmware, licenses, and installation media.
  • Integrity verification records.
  • Restore-test evidence.
  • Recovery time and data-loss objectives where defined.
  • Known limitations and unresolved issues.
  • Responsible owner and approval record.

26. Practical Example: PLC and SCADA Failure

Consider a test bench with a PLC controlling a motor, an HMI displaying test status, and a SCADA system storing measurements in SQL Server.

The industrial PC fails, and the plant must recover the station.

A suitable recovery plan would proceed as follows:

  1. Identify the failure and confirm the required recovery scope.
  2. Obtain approved replacement hardware or prepare a compatible restoration environment.
  3. Restore the operating system or follow the approved rebuild procedure.
  4. Install the required drivers, engineering tools, and runtime applications.
  5. Restore the approved HMI and SCADA configuration.
  6. Restore the SQL database using the documented recovery sequence.
  7. Restore the Node-RED or other data-collection configuration if included in the architecture.
  8. Verify network settings, permissions, licenses, and communication paths.
  9. Confirm PLC communication, HMI operation, database writes, and dashboard updates.
  10. Perform the required functional and safety checks before returning the equipment to production.
  11. Record the recovery time, any lost data, deviations, and corrective actions.

If the PLC itself also failed, its recovery would require the appropriate controller-specific procedure, compatibility checks, and authorization. Restoring the PC alone does not restore the complete automation system.

27. Final Backup Acceptance Checklist

Backup Creation and Coverage

  • All required assets are identified.
  • Appropriate backup methods are defined for each asset.
  • Initial approved backups have been created.
  • Backup files are associated with the correct equipment and revision.
  • Required dependencies, licenses, and tools are documented.

Protection and Retention

  • Independent copies are maintained according to the backup strategy.
  • Critical recovery copies have appropriate isolation or immutability protections where required.
  • Access permissions and encryption requirements are addressed.
  • Retention and deletion rules are defined.
  • Backup jobs and failures are monitored.

Verification and Recovery

  • Backup integrity checks have been completed.
  • Required restoration tests have been performed.
  • Recovery instructions and dependencies are documented.
  • Recovery time and data-loss objectives are defined where applicable.
  • Safety-related configurations have appropriate controls.
  • Outstanding backup defects have owners and corrective actions.
  • Formal handover acceptance is recorded.

28. Final Principles

  • A backup is only as useful as its ability to restore the required system.
  • Different assets require different backup methods.
  • Keep independent copies, with offline or immutable protection appropriate to the risk.
  • Preserve approved software baselines and relevant historical revisions.
  • Use application-native methods when required for consistent recovery.
  • Verify backup integrity and periodically test restoration.
  • Define RPO and RTO according to operational requirements.
  • Protect backup repositories from unauthorized access, modification, and deletion.
  • Include licenses, dependencies, documentation, and recovery instructions.
  • Treat restoration of safety-related systems as a controlled engineering activity.

The objective is not simply to accumulate backup files. It is to maintain a verified, secure, and practical recovery capability that allows the plant to restore equipment and data within defined operational limits.
