1. Definition and Purpose

Software handover is the formal transfer of software, licenses, configuration information, engineering tools, project files, operating instructions, and support details required to operate, maintain, troubleshoot, modify, and recover an industrial system after project completion.

In an industrial environment, software is part of the machine's functional design. A PLC program controls sequences and interlocks; an HMI provides operator interaction; a VFD contains motor-control parameters; a robot controller stores motion programs; and a SCADA system collects and presents production data. If these assets are handed over incompletely, the machine may operate today but become difficult to recover or modify after a future failure.

Software handover is therefore not satisfied by copying a few files onto a USB drive. The receiving team must know what each file does, which version is actually installed, what tools and licenses are needed, how the system is configured, and how changes are controlled.

Core principle: deliver the correct software version, prove its relationship to the installed equipment, establish legal and technical access, and provide enough documentation for safe maintenance and recovery.

2. Objectives of Software Handover

  1. Transfer ownership or authorized access to all project-related software assets.
  2. Identify the software actually installed on each machine or system.
  3. Provide editable engineering source files where contractually required and technically available.
  4. Provide the correct tools, versions, drivers, libraries, and licenses needed to open or maintain the project.
  5. Document controller, HMI, SCADA, drive, robot, CNC, PC, and network configurations.
  6. Record dependencies between software components.
  7. Establish access permissions and password custody.
  8. Preserve software integrity through version control and file verification.
  9. Enable troubleshooting, modification, testing, and restoration by authorized personnel.
  10. Identify third-party software restrictions, subscriptions, and support limitations.
  11. Ensure the installed software and handover records agree.
  12. Establish a controlled process for future software changes.

4. Source Code, Executables, and Configuration Files

These terms describe different deliverables. Confusing them can leave maintenance with software that runs but cannot be properly modified.

Item Meaning Example
Source or editable project Engineering representation used to develop or modify the application PLC engineering project
Executable or runtime Software used to run the application HMI runtime application
Compiled or downloaded application Application loaded into the target controller or device PLC executable or controller program
Configuration file Settings that define system behavior or connections OPC UA connection configuration
Parameter file Values controlling device behavior VFD parameter export
Firmware Low-level software running inside a device PLC CPU firmware
Library or dependency Reusable code or software component required by a project PLC function library
License Authorization to use a software product or feature SCADA runtime license
Recovery image Image used to restore a supported computer configuration Industrial PC system image
Report or verification record Evidence of configuration or software status Controller comparison report

A runtime copy does not necessarily contain the complete editable engineering project. Likewise, a project file does not prove that it matches the software currently running on the machine.

For every major software asset, identify what was delivered, what was installed, what can be edited, and what is required to recreate or restore the working system.

5. The Installed Version Versus the Delivered Version

One of the most important software-handover checks is verifying that the delivered project corresponds to the installed system.

Consider a PLC-controlled test bench. An engineer may edit a project offline, download a newer version, and make further online changes during commissioning. If the final handover contains an earlier file, the maintenance team may later download incorrect logic and introduce a fault.

5.1 Required Verification

  • Identify the controller or target device.
  • Record the installed hardware model and relevant revision.
  • Record firmware and runtime versions.
  • Identify the project version used during final commissioning.
  • Compare the delivered project against the installed configuration using the manufacturer's supported comparison tools where available.
  • Identify online changes, protected sections, and unresolved differences.
  • Document any differences that cannot be automatically compared.
  • Record the verification date and responsible engineer.
  • Obtain the required approval before declaring the software baseline complete.

The verification method depends on the platform. Some devices permit detailed online/offline comparisons; others expose only partial information or restrict readback. A successful file transfer alone is not proof of equivalence.

6. Software Inventory and Version Register

A software register is the master record of software assets transferred to the plant.

6.1 Recommended Fields

Field Purpose

Use a consistent naming convention and unique identifiers. Avoid relying on filenames such as final, final_new, or final_latest; human optimism is not a version-control system.

The date format, revision system, and status values should be defined by the organization. The filename supplements formal version control; it does not replace it.

8. PLC Software Handover

PLC software is particularly important because it defines machine sequences, interlocks, I/O handling, communication, diagnostics, and parts of the safety-related control system where applicable.

8.1 Required PLC Deliverables

  • Editable engineering project.
  • Program blocks, routines, functions, and function blocks.
  • Hardware configuration.
  • I/O and tag database.
  • Symbolic names and descriptions.
  • Data types and user-defined structures.
  • Communication configuration.
  • Device network and addressing information.
  • Alarm and diagnostic logic documentation.
  • Relevant libraries and dependency versions.
  • Controller model and firmware.
  • Online/offline comparison results where supported.
  • Approved commissioning and functional test records.
  • Known issues and limitations.
  • Required engineering software version.
  • Access and protection arrangements.
  • Approved software-change procedure.

8.2 PLC Program Structure and Readability

The receiving maintenance team should be able to understand the program without reverse-engineering every rung or block from scratch.

The project should use meaningful tag names, consistent program organization, useful comments, and clear separation of machine functions where practical.

Typical functional areas include:

  • Initialization.
  • Mode selection.
  • Sequence control.
  • Manual and automatic operation.
  • Device commands and feedback.
  • Fault detection and alarm generation.
  • Interlocks and permissives.
  • Communication diagnostics.
  • Production counters and status.
  • Maintenance diagnostics.

Not every PLC uses the same program structure. The handover requirement is that the actual structure is documented and maintainable.

8.3 PLC-Specific Compatibility Risks

  • A project may require a newer engineering software release.
  • A library may be missing or incompatible.
  • Hardware modules may use different revisions.
  • Firmware may not support the selected instructions.
  • Retentive values may affect restart behavior.
  • Online changes may differ from the archived project.
  • Controller protection may limit readback or editing.
  • Communication settings may depend on the installed network configuration.

These risks should be recorded and resolved or formally accepted before handover.

9. HMI Software Handover

The HMI is the operator-facing application used to monitor equipment, issue commands, select recipes, acknowledge alarms, and display process information.

9.1 HMI Deliverables

  • Editable HMI engineering project.
  • Runtime application or deployment package, as applicable.
  • Screen and navigation structure.
  • Tag definitions and PLC connections.
  • Alarm messages and classifications.
  • Recipe configuration.
  • User roles and permissions.
  • Language and localization settings.
  • Historical data and trend configuration.
  • Communication-driver details.
  • Panel model, firmware, and runtime version.
  • License requirements.
  • Backup and restore procedure.
  • Approved screen and functional test records.

9.2 Operator and Maintenance Access

Operator access should be limited to approved operating functions. Engineering functions, configuration changes, recipe editing, and administrative functions should be restricted according to plant policy.

Do not store plaintext passwords in the software register or handover folder. Transfer credentials using the organization's approved secure method.

9.3 Alarm Configuration

Alarm handover should include:

  • Alarm ID and description.
  • Triggering condition.
  • Priority or severity.
  • Operator response instructions.
  • Reset or recovery conditions.
  • Related equipment tag.
  • Escalation requirements.
  • Any relevant latching behavior.

An alarm acknowledgement confirms that an alarm has been acknowledged; it does not necessarily remove the underlying fault. Handover documents should explain the actual behavior of the installed HMI.

10. SCADA and Data-Acquisition Software

SCADA handover covers the software used for supervisory monitoring, alarms, trends, data logging, reporting, and interfaces to other systems.

10.1 Required Deliverables

  • Editable SCADA project and approved deployment package.
  • Server and client configuration.
  • Tag database and naming conventions.
  • PLC and device communication configuration.
  • Alarm and event configuration.
  • Historical data and trend configuration.
  • Report templates and scheduled jobs.
  • User roles and authentication configuration.
  • Database schema and approved migration information.
  • OPC UA, OPC DA, or other interface configuration where applicable.
  • Redundancy and failover settings where applicable.
  • Software versions, licenses, and dependencies.
  • Data-retention settings.
  • Service accounts and access requirements.
  • Approved functional and recovery test records.

10.2 Database and Data-Integrity Considerations

The handover should document the data source, schema, key fields, timestamps, data types, and expected update behavior.

For example, an industrial data table may contain:

  • Equipment or tag identifier.
  • Value and data type.
  • Quality or status indicator.
  • Timestamp.
  • Source or asset identifier.

The exact schema must match the implemented application.

Also document database permissions, service dependencies, connection settings, retention policy, and recovery procedures. Avoid placing production credentials or database secrets in ordinary project documentation.

11. VFD, Servo, CNC, and Robot Software

Software handover must include device-specific configuration where required to restore the equipment safely and correctly.

11.1 VFD and Servo Drives

Capture the relevant model, firmware, parameter configuration, motor data, control mode, communication settings, feedback configuration, and approved commissioning records.

Parameter exports must be associated with the correct drive and application. A parameter file from another machine may contain unsuitable motor ratings, speed limits, control settings, or safety-related configuration.

11.2 CNC Systems

Handover may include:

  • CNC system model and software version.
  • Machine-builder configuration.
  • Approved machine parameters.
  • PLC and HMI-related files where included in the scope.
  • Approved part programs and revisions.
  • Tool and offset data where contractually and operationally appropriate.
  • License and option information.
  • Recovery and restoration instructions.
  • Relevant machine acceptance and verification records.

Machine-builder data can be essential to the machine's operation. It must not be replaced with generic CNC data merely because the controller model is the same.

11.3 Robot Systems

Handover may include:

  • Robot programs.
  • Controller software version.
  • Tool and work-object frames.
  • Relevant configuration and calibration information.
  • Communication settings.
  • External-axis configuration where applicable.
  • Safety configuration and validation records where included in scope.
  • Approved recovery instructions.
  • Required engineering tools and licenses.

Robot programs and configuration must be tied to the correct robot, tooling, workcell, and controller. Loading files from a different cell can cause unexpected motion or collisions.

12. Industrial PC and Operating-System Handover

An industrial PC may host SCADA, test applications, machine-builder tools, databases, gateways, and reporting software. The application itself may be only one part of the required operating environment.

12.1 Required Information

  • Computer make, model, and asset ID.
  • Operating-system edition, version, and supported status.
  • Installed application versions.
  • Required drivers and runtime packages.
  • Network configuration and hostname.
  • Storage and partition details where relevant.
  • Service configuration and startup dependencies.
  • Database and communication dependencies.
  • Recovery image or approved rebuild procedure.
  • License activation and recovery process.
  • Security controls and approved update policy.
  • Required account and permission model.

12.2 Image Versus Installer

A recovery image can restore a known operating environment, while an installer is used to install an application or operating system.

Neither should be assumed to replace the other.

The recovery approach must account for hardware differences, license activation, driver compatibility, storage requirements, and application configuration. Any image containing sensitive data or credentials must be protected appropriately.

13. Engineering Software, Versions, and Dependencies

The correct engineering environment is essential for opening, editing, compiling, downloading, and troubleshooting industrial projects.

A project may require a specific version of TIA Portal, Studio 5000, GX Works, GT Designer, WinCC, a robot engineering tool, a CNC utility, or another vendor application.

13.1 Dependency Register

Dependency Information to record
Engineering application Product name and required version
Device firmware Required or supported firmware range
Device description files Required hardware catalogs or device packages
Libraries Names, versions, and sources
Drivers Required device or communication drivers
Runtime packages Required runtime and supporting components
Operating system Supported edition and version
License Type, scope, activation method, and owner
Communication interface Required adapter, driver, or protocol support
Third-party software Product version and usage restrictions

13.2 Version Compatibility Matrix

Maintain a compatibility matrix for important assets. For example:

Asset Engineering tool Target firmware Verification status
PLC-001 Approved tool version recorded Installed CPU firmware recorded Verified or pending
HMI-001 Approved HMI tool recorded Installed runtime recorded Verified or pending
VFD-001 Approved drive tool recorded Installed drive firmware recorded Verified or pending
SCADA-001 Approved SCADA development version recorded Installed runtime version recorded Verified or pending

These are illustrative records. Populate the matrix with actual versions from the installed equipment.

14. Software Licensing and Ownership

Software licenses can restrict installation, copying, editing, transfer, or operation. A project file may be technically accessible while still being legally unusable on a replacement computer.

14.1 Licensing Information to Capture

  • Software product and edition.
  • License type.
  • License owner or registered organization.
  • License quantity and permitted installations.
  • Activation and deactivation procedure.
  • License server details, if applicable.
  • Subscription and renewal dates.
  • Transferability restrictions.
  • Support and maintenance agreement.
  • Required runtime or engineering licenses.
  • Vendor contact and recovery process.

14.2 Intellectual Property and Source-Code Rights

The handover contract should establish which items are owned by the plant, licensed to the plant, or retained by the supplier.

Clarify rights and restrictions for:

  • Custom-developed source code.
  • Vendor libraries and proprietary components.
  • Runtime applications.
  • Engineering tools.
  • Third-party drivers.
  • Software maintenance and modification.
  • Source-code escrow, where applicable.
  • Transfer to another maintenance provider.

Do not assume that payment for a machine automatically grants unrestricted rights to all engineering tools, libraries, or proprietary software.

15. Passwords, Access Control, and Cybersecurity

Software handover transfers access responsibly. It must not create uncontrolled administrator accounts, shared credentials, or undocumented remote access.

15.1 Access-Control Requirements

  • Identify authorized user roles.
  • Remove or disable temporary project accounts where appropriate.
  • Transfer administrative access through the approved secure process.
  • Rotate temporary or supplier-shared credentials when required.
  • Verify that plant personnel can access required functions.
  • Review remote-access methods and supplier connectivity.
  • Document service accounts without exposing their secrets.
  • Protect license keys and recovery credentials.
  • Record account ownership and access approval.
  • Follow the plant's account-management and cybersecurity procedures.

15.2 Industrial Cybersecurity Considerations

  • Inventory software and firmware versions.
  • Identify unsupported systems and known security exposure.
  • Document network communication paths and dependencies.
  • Review open ports and enabled services according to site policy.
  • Restrict access to engineering workstations and controllers.
  • Control removable media.
  • Apply approved patching and change-management procedures.
  • Maintain recoverable copies of authorized software.
  • Record third-party remote access and its authorization conditions.

Industrial equipment cannot always be updated like an ordinary office computer. Patches may affect timing, drivers, compatibility, or validated machine behavior. Changes must be assessed and tested through the plant's approved process.

16. Safety-Related Software and Configuration

Safety-related software requires stricter control than ordinary application software because changes can affect the machine's risk-reduction functions.

Examples include safety PLC programs, safety relay configurations, robot safety settings, safe drive functions, and safety-related communication configuration.

16.1 Handover Requirements

  • Identify safety-related controllers and devices.
  • Record the approved software and configuration revisions.
  • Provide the applicable safety project files and access arrangements.
  • Document required signatures, checksums, or change-verification mechanisms.
  • Include the relevant risk assessment and safety requirements.
  • Provide validation reports and test evidence.
  • Document authorized access and change restrictions.
  • Define the required verification and revalidation process after changes.
  • Identify unresolved safety issues and restrictions.
  • Preserve traceability between the safety configuration and the validated machine.

A standard PLC backup is not a substitute for a validated safety-system handover. The applicable safety lifecycle, manufacturer's instructions, and plant procedures must be followed.

17. Software Configuration Management

Configuration management establishes an authoritative record of what software exists, which version is approved, what changed, who authorized the change, and how the system can be returned to a known state.

Without configuration management, several different files may all claim to be the current version. Only one can be the approved baseline for a particular installation, although controlled branches and development versions may also exist.

17.1 Essential Controls

  • Assign unique software identifiers.
  • Establish a controlled approved baseline.
  • Maintain revision history.
  • Record changes and their reasons.
  • Identify the person who made and approved each change.
  • Link changes to maintenance orders or engineering-change records.
  • Preserve previous approved versions.
  • Control access to editable projects.
  • Record deployment and validation results.
  • Reconcile installed versions with the software register.

17.2 Example Change Record

Field Example
Asset TB-001
Software PLC application
Previous revision R02
New revision R03
Change reason Add approved diagnostic alarm
Change request Engineering change record
Test evidence Functional test report
Approval Authorized engineering approver
Deployment date Actual deployment date
Rollback version R02, subject to compatibility and recovery verification

The values are illustrative. A rollback version must be retained and verified, not merely named in a table.

18. Software Testing and Acceptance

The receiving team should confirm that the software is complete, accessible, and appropriate for the installed equipment.

18.1 Verification Levels

Level Purpose Example
File verification Confirm files are present and readable Open the delivered project
Version verification Confirm the required version and dependencies Compare tool and firmware records
Configuration verification Check project settings against installed hardware Review PLC hardware configuration
Functional verification Confirm intended behavior Test approved operating sequences
Interface verification Confirm connected systems communicate correctly Verify PLC-to-HMI and SCADA data
Safety validation Confirm safety functions meet their requirements Execute the approved safety validation procedure
Recovery verification Confirm restoration instructions and artifacts are usable Perform an authorized recovery test in a suitable environment

Not every test can or should be performed on a live production system. The test plan should identify the appropriate environment, permissions, isolation requirements, acceptance criteria, and production-impact controls.

18.2 Software Handover Acceptance Criteria

  • Required software files are delivered and readable.
  • Editable project files are supplied where required.
  • Installed versions and delivered versions are reconciled.
  • Required engineering tools and dependencies are identified.
  • License arrangements and access permissions are documented.
  • The project opens in the approved environment where applicable.
  • Configuration and functional verification records are available.
  • Safety-related validation evidence is available where applicable.
  • Known issues and deviations are documented.
  • Software storage and version-control arrangements are established.
  • Authorized plant personnel can access the required assets.
  • Software ownership and support responsibilities are accepted.

19. Software Handover Workflow

Inventory all software assets
             ↓
Identify installed versions and target devices
             ↓
Collect editable projects and required configurations
             ↓
Collect tools, libraries, licenses, and dependencies
             ↓
Verify compatibility and installed-versus-delivered versions
             ↓
Complete testing and resolve or record deviations
             ↓
Store approved deliverables in controlled locations
             ↓
Transfer access and ownership responsibilities
             ↓
Obtain formal acceptance
             ↓
Maintain the approved baseline and change history

The sequence may vary by project, but the acceptance criteria should remain explicit and traceable.

20. Roles and Responsibilities

Role Main responsibility
Project engineer Coordinates the software deliverables and resolves project gaps
PLC/HMI/SCADA engineer Supplies and verifies the relevant engineering projects
OEM or system integrator Provides contractually required software, configuration, and support information
Maintenance engineer Confirms maintainability, diagnostics, and recovery requirements
OT or automation engineer Reviews architecture, compatibility, access, and configuration control
IT or cybersecurity team Reviews applicable accounts, endpoints, licenses, and security requirements
Safety engineer Reviews safety-related software records and validation requirements
Production representative Confirms required operating functions and practical acceptance
Document controller Maintains document identity, revision, approval, and storage
Asset owner Accepts the deliverables and ongoing responsibilities

One person may perform multiple roles in a smaller organization. The important requirement is that technical work, approval, and ownership are clearly assigned.

21. Common Software Handover Failures

  1. Only compiled or runtime files are delivered when editable projects are required.
  2. The archived PLC program does not match the installed controller.
  3. Required engineering software versions are not recorded.
  4. Libraries, device descriptions, or drivers are missing.
  5. License activation depends on a supplier account that the plant cannot access.
  6. Administrator credentials are unknown or shared without control.
  7. Software files are stored only on an engineer's personal computer.
  8. VFD, servo, CNC, or robot parameters are not associated with the correct asset.
  9. HMI alarm descriptions and operator-response instructions are missing.
  10. SCADA database schemas and external interfaces are undocumented.
  11. Safety-related changes lack appropriate validation evidence.
  12. The system depends on obsolete software or unsupported operating systems without a mitigation plan.
  13. Supplier remote-access arrangements are not documented.
  14. Multiple conflicting files are labeled as the approved version.
  15. No one has demonstrated that the delivered project can be opened, maintained, or restored.

22. Practical Example: PLC-Controlled Industrial Test Bench

Consider a test bench consisting of a PLC, HMI, VFD-controlled motor, sensors, a barcode reader, a database connection, and a SCADA dashboard.

A complete software handover should establish the following.

PLC

  • Approved editable project.
  • CPU model and firmware.
  • Hardware configuration and I/O mapping.
  • Communication settings.
  • Sequence and diagnostic documentation.
  • Version comparison and functional test evidence.

HMI

  • Editable project and deployed runtime information.
  • Screen navigation and tag configuration.
  • Alarm definitions and operator actions.
  • Recipe configuration and access levels.
  • Panel firmware and license details.

VFD

  • Drive model and firmware.
  • Approved parameter set.
  • Motor nameplate data and applicable settings.
  • Communication configuration.
  • Replacement and commissioning instructions.

Barcode Reader and Database Interface

  • Device configuration and communication settings.
  • Tag or data-field mapping.
  • Database connection requirements.
  • Error-handling and communication-loss behavior.
  • Relevant interface test records.

SCADA and Industrial PC

  • SCADA project and runtime configuration.
  • Tag, alarm, trend, and reporting definitions.
  • PC operating-system and software versions.
  • Database schema and data-retention settings.
  • Approved recovery instructions.

Final Acceptance

The maintenance team verifies that the deliverables open in the approved engineering environment, the versions match the documented installed configuration, required licenses and permissions are available, and the relevant operating and recovery tests have passed.

Any unresolved discrepancy must be documented with its impact, owner, corrective action, and acceptance status.

23. Standards and Governance

Applicable standards and procedures depend on the system, industry, jurisdiction, and contract. Relevant frameworks may include:

Standard or framework Relevance to software handover
ISO 9001 Documented information, competence, operational control, and change-related controls
ISO 55000 series Asset management principles and lifecycle information
ISO 45001 Occupational health and safety management, competence, and operational controls
IEC 60204-1 Electrical equipment of machinery, including relevant control-system considerations
ISO 12100 Machinery risk assessment and risk reduction
ISO 13849 series Safety-related parts of control systems
IEC 62061 Functional safety of machinery control systems
IEC 62443 series Industrial automation and control system cybersecurity
IEC 61508 series Functional safety of electrical, electronic, and programmable electronic safety-related systems

These standards do not create one universal software-handover package for every industrial machine. Their applicability and specific requirements must be determined for the actual system, with the relevant legal, contractual, and plant requirements also considered.

24. Final Software Handover Checklist

Deliverables

  • Software register completed.
  • Required editable projects and runtime deliverables supplied.
  • Hardware, firmware, and software versions documented.
  • Dependencies, libraries, drivers, and engineering tools recorded.
  • License and ownership requirements resolved.
  • Required manuals, configuration records, and test reports delivered.

Integrity and Access

  • Delivered files verified and stored in controlled locations.
  • Installed and delivered versions reconciled.
  • Approved software baseline established.
  • Access permissions and credential custody confirmed.
  • Supplier remote access reviewed.
  • Known vulnerabilities, obsolete components, and support limitations recorded.

Testing and Maintenance

  • Functional and interface tests completed as required.
  • Safety-related verification and validation records available where applicable.
  • Recovery instructions documented.
  • Maintenance personnel can access the required software and tools.
  • Change-control responsibilities assigned.
  • Outstanding deviations have documented owners and actions.
  • Formal acceptance completed.

25. Final Principles

  • Software handover is a controlled transfer of technical capability, not merely a file transfer.
  • The delivered project must be reconciled with the installed system.
  • Source projects, runtime files, firmware, parameters, and configuration files serve different purposes.
  • Tool versions, dependencies, and licenses must be documented.
  • Credentials must be transferred securely, with appropriate access controls.
  • Safety-related software requires applicable change control and validation.
  • Approved software versions must be traceable and recoverable.
  • Future changes must be tested, approved, and recorded.
  • The plant must be able to maintain the software without depending unnecessarily on undocumented supplier knowledge.

A successful handover leaves the maintenance team with the correct software, the means to understand and maintain it, controlled access, verified configuration information, and a documented route to recovery.
