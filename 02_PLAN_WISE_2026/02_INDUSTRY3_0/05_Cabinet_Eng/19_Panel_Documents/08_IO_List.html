1. Definition and purpose

An I/O list (Input/Output list) is an engineering document that defines the signals exchanged between a PLC or other control system and the machine it controls.

It identifies each signal, its function, its electrical characteristics, its controller address, its field device, and the relevant wiring and engineering references.

The I/O list acts as a bridge between electrical design, PLC programming, instrumentation, commissioning, troubleshooting, and maintenance.

Its main purposes are:

  • Define every required digital and analog input and output.
  • Map field devices to PLC addresses and hardware channels.
  • Specify signal types, electrical interfaces, and operating ranges.
  • Establish consistent tag names and descriptions.
  • Support PLC hardware selection and I/O capacity planning.
  • Connect electrical schematics with PLC logic and HMI displays.
  • Support point-to-point wiring checks and commissioning.
  • Identify unused channels, spare capacity, and future expansion requirements.
  • Document safety-related signals and communication-based I/O where applicable.
  • Provide a reliable reference for fault diagnosis and machine modifications.

An I/O list should help answer these questions:

  1. What physical or logical signal is involved?
  2. What does the signal mean?
  3. Is it an input or an output from the controller's perspective?
  4. Which PLC, rack, module, channel, and address handle it?
  5. What electrical signal type and operating range does it use?
  6. Which field device, terminal, wire, and drawing reference are associated with it?
  7. How should the signal behave during normal operation, faults, and safe states?

2. What is an input and what is an output?

The words input and output are defined from the perspective of the controller being documented.

2.1 Digital input

A digital input represents a discrete state, typically ON/OFF or TRUE/FALSE.

Examples:

  • Push button pressed or released.
  • Guard door closed or open.
  • Cylinder extended or retracted.
  • Motor overload tripped or healthy.
  • Part present or absent.
  • Pressure switch activated or inactive.
  • Contactor auxiliary contact indicating feedback.

Typical signal types include 24 V DC PNP or NPN signals, dry contacts, and other supported discrete interfaces.

Example:

A proximity sensor detects a metal component and sends a 24 V DC signal to a PLC digital input. When the sensor is active, the PLC input channel changes state according to the wiring and input configuration.

2.2 Digital output

A digital output commands a discrete action.

Examples:

  • Energize a contactor coil.
  • Switch on a solenoid valve.
  • Activate a tower-light segment.
  • Command a pneumatic valve.
  • Enable an external device.
  • Operate an interposing relay.

The output can be transistor, relay, triac, or another supported interface. Its electrical characteristics must match the connected load.

A PLC output does not automatically prove that the commanded equipment physically operated. Feedback signals are often required to confirm the actual result.

2.3 Analog input

An analog input measures a variable represented by a continuously varying electrical signal.

Examples:

  • Pressure transmitter.
  • Temperature transmitter.
  • Flow transmitter.
  • Position sensor.
  • Load or force transducer.
  • Speed feedback signal.

Common industrial interfaces include:

  • 4–20 mA.
  • 0–20 mA.
  • 0–10 V.
  • 1–5 V.
  • Thermocouple and RTD interfaces supported by dedicated modules.

The list should record the actual signal type and range, not simply label every analog signal as AI.

2.4 Analog output

An analog output provides a variable reference or command.

Examples:

  • Speed reference to a VFD.
  • Position or force reference to a compatible controller.
  • Control-valve position command.
  • Pressure setpoint to a compatible external device.

Typical interfaces include 4–20 mA and 0–10 V, depending on the receiving device.

An analog output's electrical range, scaling, direction, and safe behavior must be defined.

3. I/O signal direction

Direction is determined from the perspective of the controller, not from the field device's perspective.

Signal Controller direction Example
Push button status Input Start request
Proximity sensor status Input Part detected
Pressure transmitter measurement Input Pressure feedback
Contactor command Output Motor run request
Solenoid command Output Extend cylinder
Speed reference Output VFD frequency or speed command
Drive-ready status Input Drive reports ready
Drive fault status Input Drive reports fault

A VFD can therefore have both inputs and outputs in the same application. Its run command may be a PLC output, while its ready and fault signals are PLC inputs.

The same distinction applies to robots, CNC machines, vision systems, and remote I/O stations.

4. I/O list versus related documents

The I/O list is related to several other engineering documents, but each serves a different purpose.

Document Primary purpose
I/O list Defines signals, direction, type, address, and function
Component list Identifies physical devices and their technical details
BOM Defines material requirements and quantities
Electrical schematic Shows circuits, wiring, contacts, and electrical relationships
Panel layout Shows physical device positions
Terminal plan Defines terminal numbers and connection references
Cable schedule Defines cable identities and endpoints
PLC program Implements the control behavior
HMI tag list Defines operator-interface variables and their display or control use
Network topology Defines communication links, nodes, and network structure
Alarm list Defines fault conditions, alarm text, and operator response
Cause-and-effect matrix Maps initiating conditions to required machine responses

The I/O list does not replace the PLC program or the electrical schematic. It connects their signal-level information.

5.5 Operational fields

For signals with meaningful operational requirements, consider recording:

  • Normal state and active state.
  • Expected response time.
  • Signal filtering or debounce.
  • Interlocks and permissives.
  • Alarm or diagnostic association.
  • Startup and shutdown behavior.
  • Behavior on communication loss.
  • Required state on power failure.
  • Safety function or safety assessment reference.
  • HMI display or command reference.

These fields should be used where the application requires them. The I/O list should not become an uncontrolled substitute for a complete functional specification.

6. Tag naming conventions

A consistent naming convention improves readability, searchability, and maintenance.

A tag can combine a device or process identifier with its function.

Examples:

Tag Meaning
PB_START Start push-button signal
PB_STOP Stop push-button signal
PS_AIR_OK Pneumatic pressure permissive
LS_CYL_EXT Cylinder extended limit switch
LS_CYL_RET Cylinder retracted limit switch
PE_PART_PRESENT Photoelectric part-detection signal
MTR01_RUN_CMD Motor 1 run command
MTR01_RUN_FB Motor 1 run feedback
VFD01_READY Drive ready status
VFD01_FAULT Drive fault status
PT01_PRESSURE Pressure transmitter measurement
CV01_POS_CMD Control-valve position command

These names are illustrative. Follow the plant's established tag structure, abbreviations, separators, and case conventions.

6.1 Rules for good tag names

  • Use one defined naming convention throughout the project.
  • Make the signal's meaning clear without excessive length.
  • Distinguish commands from feedback.
  • Distinguish requests from confirmed states.
  • Avoid names such as INPUT1, OUTPUT2, or TAG_NEW.
  • Avoid using the same tag for unrelated signals.
  • Keep tag names stable across electrical drawings, PLC code, HMI, and historian records.
  • Document abbreviations in a tag dictionary.
  • Avoid embedding changeable physical locations in names unless required by the plant's standard.

For example, MTR01_RUN_CMD is a command, while MTR01_RUN_FB is feedback. Treating both as MOTOR_RUNNING can cause serious confusion during commissioning.

7. Digital input design

Digital inputs must be compatible with the field device, supply, input module, and wiring arrangement.

7.1 PNP and NPN sensors

For common 24 V DC three-wire sensors:

  • A PNP sensor typically sources positive voltage to the input when active.
  • An NPN sensor typically sinks current toward 0 V when active.
  • The PLC input module must support the selected arrangement.
  • The common or reference wiring must be compatible with the module design.
  • The sensor supply and signal wiring must follow the manufacturer's terminal diagram.

A typical PNP arrangement is:

+24 V DC → Sensor supply positive
0 V DC   → Sensor supply negative
Sensor output → PLC digital input
PLC input common → 0 V DC, where required by module design

This is a conceptual example, not a universal wiring diagram. Actual terminal connections depend on the input module's design and wiring topology.

A mismatch between PNP/NPN output and the input module can result in a signal that never changes state or behaves unpredictably.

7.2 Dry contacts

A dry contact provides a switching contact without supplying its own voltage.

The input circuit must provide a compatible sensing voltage and current. Verify contact ratings, input current, common wiring, and the required contact state.

Do not assume every field contact can be connected directly to every PLC input.

7.3 Normally open and normally closed

Normally open (NO) and normally closed (NC) describe contact behavior in a defined unactuated condition.

They do not automatically define what the PLC will display as TRUE or FALSE.

For example, a closed guard-door contact may produce a TRUE input while the guard is closed. An alternative arrangement may use a different signal interpretation. The I/O list must define the actual intended behavior.

For ordinary process signals, a broken wire can sometimes look identical to an inactive device. Where fault detection matters, the circuit or diagnostic design must address this limitation.

For safety-related functions, contact arrangement, device architecture, fault detection, and validated safety behavior must follow the applicable safety design. A normal PLC I/O list alone does not establish a safety function.

8. Digital output design

Digital outputs operate loads or issue commands to other equipment.

8.1 Output types

Output type Typical characteristics Important checks
Transistor output Electronic switching, commonly DC Output polarity, current, leakage, inductive-load suppression
Relay output Mechanical contacts, can switch supported AC or DC loads Contact ratings, electrical life, switching frequency
Triac output Electronic switching for compatible AC loads Load type, leakage current, minimum load, switching constraints
Safety output Designed for defined safety-related control functions Certified architecture, diagnostics, load compatibility, validation

The exact capabilities depend on the selected module. A relay output is not automatically suitable for every load, and a transistor output is not automatically suitable for an AC coil.

8.2 Interposing relays

Interposing relays are used when an interface is needed between a PLC output and the controlled load.

Common reasons include:

  • Electrical isolation between circuits.
  • Switching loads outside the PLC output's direct capability.
  • Providing suitable contact arrangements.
  • Standardizing interfaces to field devices.

The component list should identify the relay. The I/O list should identify the PLC signal and the load or function it commands. The schematic should show the actual connection.

8.3 Output feedback

An output command is not proof of physical operation.

Example:

PLC output MTR01_RUN_CMD
    ↓
Contactor coil energizes
    ↓
Motor supply is switched
    ↓
Motor operates
    ↓
Feedback MTR01_RUN_FB confirms the expected state

The feedback may come from an auxiliary contact, drive status, encoder, or other suitable sensor.

Where operation must be confirmed, the control design should define the expected response time and fault response. The feedback method must be appropriate for the function being verified.

9. Analog signals and engineering scaling

Analog signals require more information than a simple digital state.

The I/O list should record the electrical range, engineering range, unit, scaling convention, and fault-handling requirements.

9.1 Example: 4–20 mA pressure transmitter

Suppose a transmitter measures 0 to 10 bar and provides a linear 4–20 mA signal.

The engineering value is:

\[ P = \frac{I-4}{20-4}\times 10 \]

Where:

  • \(P\) is pressure in bar.
  • \(I\) is the measured loop current in mA.
  • The lower range is 4 mA.
  • The upper range is 20 mA.

Examples:

Current Pressure
4 mA 0 bar
8 mA 2.5 bar
12 mA 5 bar
16 mA 7.5 bar
20 mA 10 bar

The 4 mA lower point is called the live zero. A current significantly below the normal operating range may indicate a broken wire or transmitter fault, depending on the transmitter's configured fault signaling and the receiving module's diagnostics.

The exact fault thresholds must come from the device and module specifications. Do not automatically treat every current below 4 mA as a broken wire.

9.2 Raw values and engineering values

An analog input module converts the electrical measurement into a digital representation. The numerical representation depends on the hardware and configuration.

A PLC may expose:

  • Raw input counts.
  • A normalized value.
  • A floating-point value.
  • A scaled engineering value.

The I/O list should specify which representation is being documented and where the conversion occurs.

If the module provides a raw value, the scaling relationship may be represented as:

\[ EU = \frac{Raw-Raw\_{min}}{Raw\_{max}-Raw\_{min}}(EU\_{max}-EU\_{min})+EU\_{min} \]

Here, \(EU\) means engineering units.

Use the actual configured raw limits. Do not assume that all PLC platforms use the same raw counts or range conventions.

9.3 Analog signal quality

For analog signals, document or verify:

  • Input range and engineering range.
  • Sensor accuracy and required process accuracy.
  • Shielding and grounding requirements.
  • Cable routing and segregation.
  • Two-wire, three-wire, or four-wire transmitter arrangement.
  • Loop power source.
  • Isolation requirements.
  • Open-circuit or under-range diagnostics.
  • Filtering and response time.
  • Scaling direction and engineering units.

A correctly scaled signal can still be inaccurate if the wiring, transmitter configuration, grounding, or input hardware is wrong.

10. Analog output design

Analog outputs provide variable commands to compatible devices.

Example: a PLC provides a 4–20 mA reference to a compatible drive or control device.

The I/O list should define:

  • The receiving device.
  • Electrical output range.
  • Engineering range.
  • Units.
  • Minimum and maximum command.
  • Direction or scaling relationship.
  • Expected response.
  • Behavior on PLC stop or communication failure.
  • Any output limits or interlocks.

For a linear 0–100% command mapped to 4–20 mA:

\[ I = 4 + \frac{Command}{100}\times16 \]

Where Command is expressed as a percentage.

The electrical interface must be verified against the receiving device's manual. Some drives use a voltage reference, while others accept current or communication-based commands.

The behavior on loss of control must be explicitly engineered. A zero output, a held output, or a configured fallback value can have different operational consequences.

11. PLC address and hardware mapping

An I/O list must connect each logical signal to the actual controller hardware or communication interface.

11.1 Physical I/O

A physical I/O mapping may contain:

  • PLC identifier.
  • Rack or chassis.
  • Local or remote I/O station.
  • Module identifier.
  • Channel number.
  • Native PLC address.
  • Symbolic tag.
  • Wiring and terminal reference.

For example, an input might be associated with a particular remote I/O adapter, digital input module, and channel. The actual address representation will depend on the controller platform and project configuration.

11.2 Symbolic and hardware identifiers

These identifiers serve different purposes:

  • Signal tag: engineering identity, such as PE_PART_PRESENT.
  • Symbolic PLC variable: name used in the program.
  • Hardware channel: physical input or output point.
  • Native PLC address: platform-specific address or channel path.
  • Device tag: physical device identity, such as a sensor.
  • Terminal reference: wiring connection point.

The values can be related, but they are not interchangeable.

11.3 Remote I/O

For distributed systems, the I/O list should identify the remote station and relevant network path.

Record information such as:

  • Remote I/O station ID.
  • Adapter or coupler model.
  • Network protocol.
  • Node name or IP address, where applicable.
  • Module and channel.
  • Communication diagnostics reference.
  • Relevant configuration revision.

If the remote I/O adapter is replaced or its network configuration changes, both the hardware configuration and related documentation may need updating.

12. Safety-related I/O

Safety-related signals require additional engineering discipline.

Examples include:

  • Emergency-stop devices.
  • Guard-door interlocks.
  • Safety light curtains.
  • Safety scanners.
  • Safe drive status or control signals.
  • Safety reset devices.

The I/O list should identify the safety-related function or the relevant safety design reference. It should not treat a safety signal as an ordinary process input without accounting for the validated architecture.

Important distinctions:

  • A standard PLC input does not become safety-rated simply because it is connected to an emergency-stop contact.
  • A normal PLC program's TRUE/FALSE logic is not, by itself, proof of a validated safety function.
  • Safety functions may require dedicated safety controllers, safety I/O, redundant channels, diagnostics, and validated programming.
  • The required safe state depends on the risk assessment and machine design.
  • Reset behavior, fault detection, and restart prevention must be designed and validated where required.

For safety I/O, document the channel allocation and safety configuration references required by the project. Detailed safety logic, validation evidence, and risk assessment records should remain in their designated controlled documents.

13. Communication-based I/O

Not every PLC signal corresponds to a physical terminal.

Many machines exchange data through industrial communication protocols.

Examples include:

  • PLC to VFD over PROFINET or EtherNet/IP.
  • PLC to robot controller over an industrial network.
  • PLC to CNC through a supported communication interface.
  • PLC to remote I/O over a fieldbus.
  • PLC to vision system using cyclic or acyclic data exchange.
  • PLC to another controller using exchanged status and command data.

For communication-based signals, the I/O list or an associated interface list should identify:

  • Producing and consuming devices.
  • Signal or data-item name.
  • Data type and length.
  • Direction from the controller's perspective.
  • Communication protocol.
  • Mapping or offset, where relevant.
  • Update rate or timeout requirement, where relevant.
  • Validity or quality status.
  • Communication-loss response.
  • Related network and interface documentation.

For example, a drive's RUN_CMD may be a bit within a network command word rather than a physical PLC output terminal. Its corresponding READY and FAULT bits may be returned in a status word.

Do not invent a physical module/channel address for a signal that exists only in a communication data mapping.

14. Spare and unused I/O channels

Spare I/O capacity supports future expansion and maintenance flexibility.

The I/O list should distinguish between:

  • Used channels.
  • Allocated but not yet commissioned channels.
  • Reserved channels.
  • Physically available spare channels.
  • Disabled or faulted channels.
  • Channels that are physically installed but not used.

These categories must not be merged into a single SPARE label.

A spare channel should be checked for electrical suitability, module capacity, addressing, terminal availability, wiring space, and compatibility with the intended future device.

For safety-related systems, spare capacity and future channel use must follow the safety architecture and approved engineering change process.

A spare channel is not automatically ready for immediate use. It may lack field wiring, terminals, configuration, testing, or the required engineering approval.

16. I/O capacity and module selection

The I/O list helps determine the quantity and type of I/O modules required.

16.1 Count signals by type

Count separately:

  • Digital inputs.
  • Digital outputs.
  • Analog inputs.
  • Analog outputs.
  • Specialized inputs, such as RTD or thermocouple channels.
  • High-speed counter or encoder channels.
  • Communication-based data points.
  • Safety-related channels.

Do not count every signal as a standard digital or analog point. Specialized devices may require dedicated hardware.

16.2 Calculate nominal channel requirements

For a simple digital input design:

\[ N\_{DI} = \sum \text{required digital input signals} \]

Similarly:

\[ N\_{DO} = \sum \text{required digital output signals} \]

The nominal module count is:

\[ N\_{modules} = \left\lceil \frac{N\_{signals}}{N\_{channels\ per\ module}} \right\rceil \]

This simple formula is only an initial capacity estimate. Actual selection must consider channel groups, electrical compatibility, spare capacity, safety requirements, module restrictions, current consumption, isolation, and expansion plans.

16.3 Example

Suppose a machine needs 25 digital inputs, and the selected module provides 16 inputs per module.

The initial module requirement is:

\[ N\_{modules} = \left\lceil \frac{25}{16} \right\rceil = 2 \]

Two modules provide 32 nominal channels, leaving seven channels beyond the immediate requirement.

That does not necessarily mean all seven are usable spares. Some may be reserved, unsuitable for the required wiring arrangement, or unavailable due to channel-group constraints.

17. Commissioning and I/O validation

The I/O list is one of the primary documents used during point-to-point testing.

17.1 Digital input testing

For each input:

  1. Confirm the field device tag and physical location.
  2. Verify the wiring and terminal references against the schematic.
  3. Apply the intended operating condition using an approved test method.
  4. Verify the electrical signal at the appropriate test point.
  5. Verify that the correct PLC hardware channel changes state.
  6. Verify that the correct symbolic variable changes state.
  7. Confirm that the PLC program interprets the signal correctly.
  8. Record the result and any discrepancy.

17.2 Digital output testing

For each output:

  1. Confirm the intended device and load.
  2. Verify the output circuit and load compatibility.
  3. Check interlocks and safe test conditions.
  4. Command the output using the approved commissioning procedure.
  5. Verify the physical output and the receiving device's response.
  6. Check feedback where provided.
  7. Confirm the expected fault behavior if the commanded response does not occur.
  8. Record the result.

Output testing must not bypass safety interlocks or energize equipment unexpectedly.

17.3 Analog input testing

For each analog input:

  1. Verify the transmitter range and electrical interface.
  2. Confirm loop wiring, supply, polarity, and terminal references.
  3. Apply a suitable calibrated test input where permitted.
  4. Compare the raw input value with the expected value.
  5. Verify the scaling and engineering unit.
  6. Confirm displayed values and alarms.
  7. Verify under-range, over-range, and signal-loss diagnostics where applicable.
  8. Record the measured results.

17.4 Analog output testing

For each analog output:

  1. Confirm the output range and receiving device configuration.
  2. Check the wiring and electrical interface.
  3. Command defined test points under approved conditions.
  4. Measure the output signal with a suitable instrument.
  5. Verify scaling and direction.
  6. Confirm the receiving device's response.
  7. Verify configured behavior on controller or communication failure.
  8. Record the test results.

17.5 I/O test status

Useful test-status values include:

  • Not checked.
  • Wiring verified.
  • Hardware channel verified.
  • PLC variable verified.
  • Functional test passed.
  • Failed.
  • Pending correction.
  • Retest required.
  • Accepted with approved deviation.

Use the project's formal acceptance terminology if it already exists.

18. I/O troubleshooting

The I/O list provides a structured path from the physical device to the PLC program.

18.1 Digital input remains OFF

Possible causes:

  • Field device is not actuated.
  • Sensor supply is missing.
  • Incorrect PNP/NPN compatibility.
  • Broken or shorted signal wire.
  • Incorrect terminal connection.
  • Incorrect input common wiring.
  • Failed sensor or PLC input channel.
  • Incorrect hardware configuration.
  • Wrong PLC address or symbolic mapping.
  • Input filtering or logic interpretation issue.

Troubleshooting sequence:

Field condition
    ↓
Sensor operation
    ↓
Sensor supply and output
    ↓
Terminal and field wiring
    ↓
PLC input channel indication
    ↓
PLC variable and address mapping
    ↓
Program logic
    ↓
HMI or diagnostic display

Verify the actual electrical signal and hardware status before assuming that the PLC program is defective.

18.2 Digital output is ON but the actuator does not operate

Possible causes:

  • Incorrect output channel mapping.
  • Output module fault or protection trip.
  • Missing field supply.
  • Failed interposing relay.
  • Open circuit or incorrect terminal wiring.
  • Incorrect actuator voltage.
  • Solenoid coil failure.
  • Mechanical obstruction.
  • Missing pneumatic or hydraulic supply.
  • Safety or equipment interlock preventing operation.
  • Incorrect device configuration.

A TRUE PLC variable does not prove that the load is energized. Trace the circuit through the output channel, interface device, field wiring, and load using the approved electrical safety procedure.

18.3 Analog input value is incorrect

Possible causes:

  • Incorrect transmitter range.
  • Wrong input module range configuration.
  • Incorrect raw-to-engineering scaling.
  • Incorrect unit conversion.
  • Reversed or incorrect wiring.
  • Grounding or shielding problems.
  • Missing loop supply.
  • Damaged transmitter.
  • Incorrect channel mapping.
  • Electrical interference.
  • Faulty or misconfigured input module.

Compare the physical signal, raw PLC value, scaled value, and displayed engineering value separately. This helps isolate whether the error originates in the instrument, wiring, hardware configuration, program scaling, or HMI presentation.

18.4 Communication-based signal is stale

Possible causes:

  • Network disconnection.
  • Incorrect device identity or IP configuration.
  • PLC-to-device mapping error.
  • Unsupported data type or layout.
  • Communication timeout.
  • Device fault.
  • Wrong update configuration.
  • Program using an old or invalid data value.

For communication-based I/O, check data validity and freshness as well as the last received value. A stale value can look plausible while no longer representing the current machine condition.

19. I/O list quality checks

A controlled I/O list should be checked for:

  • Duplicate signal tags.
  • Duplicate physical channel assignments where prohibited.
  • Missing descriptions.
  • Incorrect input/output classification.
  • Incorrect signal types.
  • Missing or inconsistent engineering units.
  • Missing scaling information for analog signals.
  • Incorrect hardware addresses.
  • Missing field-device or terminal references.
  • Signals that exist in the PLC program but not in the controlled list.
  • Signals that exist in the list but are not configured in the controller.
  • Mismatches between PLC variables and HMI tags.
  • Unused channels incorrectly shown as commissioned signals.
  • Inconsistent safety-related classifications.
  • Missing communication-loss behavior for critical networked signals.
  • Outdated drawing or configuration revisions.
  • Incomplete commissioning test records.

Automated comparison tools can help identify differences between the I/O list, PLC hardware configuration, PLC tag database, and HMI tag database. Any differences should be reviewed against the approved design rather than automatically treated as errors.

20. Managing the I/O list in Excel or a database

For a small project, Excel may be sufficient if the file is structured and controlled. For a large plant, a central database or engineering data system provides stronger traceability.

Recommended fields for data validation include:

  • Unique signal key.
  • Project and machine identifiers.
  • Signal tag and description.
  • Signal type and direction.
  • PLC and hardware channel identity.
  • Electrical range and engineering unit.
  • Device tag and physical location.
  • Drawing and terminal references.
  • Revision and approval status.
  • Commissioning test status.
  • Change reference.

Useful automated reports include:

  • I/O count by type and controller.
  • Used versus spare channel count.
  • Signals missing hardware assignments.
  • Signals missing field-device references.
  • Analog signals missing scaling information.
  • Duplicate tags or channel assignments.
  • Signals missing commissioning results.
  • Differences between released revisions.
  • Changes affecting multiple drawings or programs.

If integrated with a maintenance or ERP system, use stable identifiers to link signals to components, machines, spare parts, work orders, and failure records.

21. Relationship between I/O lists and software development

For industrial automation development, the I/O list is a foundation for designing and testing the control software.

A useful sequence is:

Functional requirements
    ↓
I/O list and signal definitions
    ↓
Electrical design and hardware configuration
    ↓
PLC tag database
    ↓
Control logic and interlocks
    ↓
HMI and alarm mapping
    ↓
I/O simulation and hardware testing
    ↓
Machine commissioning
    ↓
Verified as-built records

The actual workflow can be iterative, especially when a prototype or retrofit changes the hardware requirements.

21.1 Signal definitions before programming

Before writing logic, define:

  • Signal meaning.
  • Input/output direction.
  • Normal and active states.
  • Data type.
  • Valid range.
  • Fault behavior.
  • Dependencies and interlocks.
  • Expected response time.
  • HMI or alarm association.

For example, MTR01_RUN_CMD should be clearly distinguished from MTR01_RUN_FB, MTR01_READY, and MTR01_FAULT.

This avoids ambiguous variables and helps separate operator requests, PLC commands, equipment status, and fault conditions.

21.2 I/O simulation

When developing a retrofit or new controller program, the I/O list can support a test matrix.

For each signal, define:

  • Normal input condition.
  • Abnormal or fault condition.
  • Expected program response.
  • Expected output behavior.
  • Relevant interlocks.
  • Expected HMI indication.
  • Recovery or reset requirements.

Simulation must distinguish between ordinary process logic and safety-related behavior that requires its own approved validation process.

23. Interview questions and answers

Q1. What is an I/O list?

An I/O list defines the signals exchanged between a control system and the equipment it controls. It typically records the signal tag, function, direction, type, hardware address, field device, electrical characteristics, and wiring references.

Q2. What is the difference between a digital input and a digital output?

A digital input reports a discrete condition to the controller, such as a sensor state. A digital output commands a discrete action, such as energizing a relay or solenoid.

Q3. What is the difference between an analog input and an analog output?

An analog input measures a variable through an electrical signal, such as pressure represented by 4–20 mA. An analog output generates a variable command, such as a speed reference to a compatible drive.

Q4. Why are both command and feedback signals required?

A command represents what the controller requests. Feedback represents what the equipment reports or what a sensor measures. Comparing them helps detect failures, delays, and unexpected machine conditions.

Q5. What is the difference between an I/O address and a signal tag?

The signal tag identifies the engineering meaning of a signal. The I/O address identifies the controller hardware point or platform-specific location associated with it.

Q6. Why is PNP/NPN compatibility important?

The sensor output and PLC input must have compatible electrical switching arrangements. A mismatch can prevent correct signal detection even when the sensor itself is functioning.

Q7. What is analog scaling?

Analog scaling converts a raw or electrical measurement into a meaningful engineering value, such as converting a 4–20 mA signal into a pressure range of 0–10 bar.

Q8. Why should the I/O list include terminal and wire references?

These references help technicians trace the signal between the field device, terminal block, PLC module, and associated electrical circuit.

Q9. What is the purpose of spare I/O channels?

Spare channels provide capacity for approved future expansion or modifications. They must still be checked for electrical suitability, hardware configuration, wiring availability, and project constraints.

Q10. How do you troubleshoot an input that remains OFF?

Verify the field condition, sensor supply and output, wiring, terminal connections, PLC input-channel indication, hardware configuration, address mapping, and program logic in a systematic sequence.

Q11. What is the risk of an incorrect I/O list?

It can cause wiring errors, incorrect PLC mapping, commissioning delays, misleading HMI indications, poor fault diagnosis, and potentially unsafe behavior if safety-related design information is mishandled.

Q12. How would you maintain an I/O list during a retrofit?

Establish a controlled baseline, document proposed changes, review hardware and software impacts, implement approved changes, test the affected signals, update all related engineering records, and release a verified as-built revision.

24. Practical exercise

Develop an I/O list for a small automated cylinder station with a conveyor motor and a pressure transmitter.

Include:

  • Start push button.
  • Stop push button.
  • Part-present sensor.
  • Cylinder extended sensor.
  • Cylinder retracted sensor.
  • Motor run command.
  • Motor run feedback.
  • Cylinder extend command.
  • Cylinder retract command, if required by the valve arrangement.
  • Pressure transmitter.
  • Drive-ready status, if a drive is used.
  • Drive-fault status, if a drive is used.

For every signal, record:

  1. Signal tag and description.
  2. Direction and I/O type.
  3. Electrical interface and signal range.
  4. PLC and hardware channel assignment.
  5. Field device tag.
  6. Schematic and terminal references.
  7. Normal and active states.
  8. Required fault behavior.
  9. Commissioning test method.
  10. Test result and revision.

Then verify that every physical input can be traced to the correct PLC variable and every output can be traced from the PLC command to the intended load.

The exercise is complete when the I/O list, electrical schematic, controller hardware configuration, program tags, and commissioning results agree with the verified machine installation.
