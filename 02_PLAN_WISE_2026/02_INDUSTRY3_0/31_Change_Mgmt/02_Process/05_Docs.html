1. Purpose and Scope

Documentation is the controlled recording of a change's purpose, design, authorization, implementation, testing, operational impact, and final configuration. It provides evidence of what was changed, why it was changed, who authorized it, how it was verified, and what configuration now exists.

In industrial maintenance and automation, documentation connects engineering decisions with actual shop-floor equipment. It helps technicians troubleshoot faults, engineers understand dependencies, production teams operate machines correctly, and auditors verify that required processes were followed.

Documentation is essential when:

  • Modifying PLC, HMI, SCADA, CNC, or robot programs.
  • Replacing obsolete sensors, controllers, drives, or network devices.
  • Changing machine parameters, recipes, setpoints, or operating limits.
  • Modifying safety circuits, guarding, or interlocks.
  • Updating industrial network architecture.
  • Changing test-bed measurement ranges or acceptance criteria.
  • Modifying Node-RED flows, SQL databases, dashboards, or reports.
  • Implementing temporary workarounds or emergency repairs.
  • Transferring equipment knowledge between shifts, teams, or vendors.

The fundamental rule is that the documented configuration must correspond to the real installed configuration. A perfect drawing of yesterday's machine is not an accurate drawing of today's machine.

2. Why Change Documentation Matters

Proper documentation supports several important functions.

Purpose Practical benefit
Traceability Links the original request to the final implementation
Configuration control Identifies the approved and installed versions
Troubleshooting Helps locate faults and understand system dependencies
Safety Records hazards, safeguards, and required operating controls
Quality Demonstrates that acceptance requirements were met
Maintenance Supports future repairs, calibration, and replacement
Audit readiness Provides evidence of required reviews and decisions
Knowledge retention Preserves information beyond individual employee experience
Recovery Supports restoration and rollback
Lifecycle management Helps manage obsolescence, upgrades, and future modifications

Documentation is not just an administrative output. It is part of the technical system used to maintain the machine throughout its service life.

3. Documentation Within the Change Lifecycle

Change request
    ↓
Scope and impact assessment
    ↓
Risk assessment and approval records
    ↓
Pre-change baseline and backup records
    ↓
Design and implementation documents
    ↓
Testing and verification evidence
    ↓
As-built configuration and updated procedures
    ↓
Release and acceptance records
    ↓
Final review and change closure

Documentation is created and updated throughout the lifecycle. It should not be postponed until the end, when people are tired, the machine is running, and the exact parameter values have mysteriously vanished from everyone's memory.

4. Main Documentation Categories

4.1 Change-control documents

These establish why the change is needed and how it is governed.

Examples:

  • Change request.
  • Change description and scope.
  • Impact assessment.
  • Risk assessment.
  • Approval records.
  • Review comments and decisions.
  • Implementation schedule.
  • Change register.
  • Deviation and concession records.
  • Closure report.

4.2 Engineering documents

These describe the technical design and configuration.

Examples:

  • Electrical schematics.
  • Mechanical drawings.
  • PLC I/O lists.
  • Control architecture.
  • Functional descriptions.
  • Sequence diagrams.
  • Interlock matrices.
  • Network topology.
  • Device configuration registers.
  • Software revision records.
  • Parameter lists.
  • Instrumentation and calibration records.

4.3 Implementation documents

These describe what was done.

Examples:

  • Work orders.
  • Installation records.
  • Wiring modification sheets.
  • Software download records.
  • Hardware replacement records.
  • Configuration change logs.
  • Vendor service reports.
  • Commissioning logs.
  • Temporary modification records.

4.4 Verification and acceptance documents

These demonstrate that the implemented change meets the specified requirements.

Examples:

  • Inspection reports.
  • Functional test sheets.
  • FAT and SAT records.
  • Regression test results.
  • Safety validation records.
  • Measurement verification records.
  • Defect and corrective-action logs.
  • Acceptance sign-off.

4.5 Operational and maintenance documents

These enable the updated system to be operated and maintained correctly.

Examples:

  • Standard operating procedures.
  • Maintenance instructions.
  • Preventive maintenance schedules.
  • Troubleshooting guides.
  • Alarm-response instructions.
  • Spare-parts lists.
  • Backup and recovery procedures.
  • Training records.
  • Updated machine knowledge-base entries.

5. Document Versus Record

These terms are related but have different purposes.

Item Main purpose Example
Document Communicates controlled instructions or information Updated PLC troubleshooting procedure
Record Provides evidence of an activity or result Completed PLC functional test sheet
Drawing Describes physical or logical design Updated electrical schematic
Configuration artifact Preserves a system's actual configuration PLC project or switch configuration export
Register Tracks multiple controlled items Machine modification register
Report Summarizes findings, results, or decisions Post-modification commissioning report

A procedure tells the technician how to perform a task. A completed work record demonstrates that the task was performed. A test specification defines what must be tested; a test report records what actually happened.

One file may serve more than one purpose, but its status, revision, and intended use must remain clear.

6. Minimum Documentation Package for a Change

The required package depends on the type, complexity, risk, and applicable procedure. A typical engineering change package includes the following.

Document or record Key contents
Change request Reason, scope, owner, affected assets
Impact assessment Hardware, software, safety, quality, production, and network effects
Risk assessment Hazards, controls, residual risk, required actions
Approval record Authorized decisions, reviewers, conditions
Pre-change backup record Baseline revision, location, verification, recovery method
Technical design Drawings, logic descriptions, parameter changes, architecture
Implementation record Work performed, devices changed, versions installed
Test plan Test cases, expected results, acceptance criteria
Test evidence Actual results, deviations, defects, retests
As-built documents Final installed design and configuration
Release record Acceptance status and authorization to resume intended use
Closure record Completed actions, final versions, lessons learned

Not every change requires every item. The organization's change-control procedure should define the mandatory package for each change category.

7. Document Identification and Unique References

Every controlled document should be identifiable without relying on its filename alone.

7.1 Common identification fields

  • Document title.
  • Unique document number.
  • Machine or asset ID.
  • Department or production line.
  • Document owner.
  • Revision identifier.
  • Document status.
  • Issue date.
  • Author or preparer.
  • Reviewer and approver, where required.
  • Related change request ID.
  • Page number or section identification, where applicable.

7.2 Example

Document title: H7 Test-Bed PLC I/O List
Document number: H7-PLC-IOL-001
Asset ID: H7-TB-01
Revision: Rev 04
Status: Approved
Related change: CHG-2026-014
Issue date: 2026-10-18

These identifiers are illustrative. Follow the plant's approved numbering scheme.

7.3 Why unique IDs matter

A unique ID allows the document to be linked to:

  • The change request.
  • The asset register.
  • The approval workflow.
  • The installed software version.
  • The test evidence.
  • The maintenance history.
  • The backup package.
  • The final release record.

This creates a traceable relationship between the decision and the actual machine.

8. Revision Control

Revision control identifies which version of a document or configuration is current and which versions have been superseded.

8.1 Typical revision identifiers

An organization might use:

  • Rev 00, Rev 01, Rev 02.
  • A, B, C.
  • Controlled semantic versions such as 1.2.0.
  • Repository commit identifiers for software.
  • Vendor-specific project revision information.

Use one consistent, approved scheme for each document type.

8.2 Revision history

A revision history should explain what changed and why.

Revision Change description Prepared by Approval status
Rev 00 Initial issue Controls engineer Approved
Rev 01 Added fixture confirmation input Controls engineer Approved
Rev 02 Corrected I/O reference and updated test cases Controls engineer Approved

The names are omitted here because they depend on the actual organization.

8.3 Revision-control rules

  • Never silently overwrite a controlled revision.
  • Identify the current approved revision.
  • Record meaningful changes in the revision history.
  • Link revisions to relevant change requests.
  • Preserve superseded versions according to retention requirements.
  • Prevent obsolete copies from being mistaken for current instructions.
  • Re-review documents when a technical change affects their validity.

A filename containing the word FINAL does not establish revision control. It merely establishes that somebody felt optimistic at the time.

9. Document Status and Approval

Documents should have a clear status that indicates how they may be used.

Status Meaning
Draft Being prepared; not yet approved for controlled use
Under review Awaiting technical or other required review
Approved Authorized for the specified purpose
Released Issued for its defined operational or engineering use
Superseded Replaced by a later controlled version
Obsolete No longer valid for current use
Withdrawn Formally removed from use
As-built Records the final installed configuration, subject to the organization's approval rules

The organization should define how these statuses are applied. In particular, an as-built document may still require review and approval before becoming the controlled reference.

9.1 Approval of documents

Depending on the document, review may involve:

  • Technical correctness.
  • Safety requirements.
  • Quality requirements.
  • Production impact.
  • Maintenance usability.
  • Compliance with document-control procedures.
  • Correct references to associated revisions.

The person who prepares a document may also review it for basic completeness, but required independent technical approval must follow the site's rules.

10. Document Control: Master Copies and Distribution

A controlled master copy is the authoritative version maintained in the designated document repository or system.

Uncontrolled copies may be useful for reference, but they must not be confused with the current approved version.

10.1 Good document-control practices

  • Maintain one clearly identified authoritative copy.
  • Define who can create, review, approve, and publish revisions.
  • Restrict editing rights according to responsibility.
  • Record document issue and revision history.
  • Identify recipients or systems that need updated copies.
  • Remove or mark superseded copies.
  • Ensure shop-floor personnel can access the correct revision.
  • Provide a process for printed copies, including whether they remain controlled.
  • Maintain backups and retention according to policy.

10.2 Shop-floor application

Suppose an electrical drawing is updated after a sensor is moved to another PLC input.

The updated drawing must reach the people who use it, including relevant:

  • Maintenance technicians.
  • Electrical engineers.
  • Controls engineers.
  • Troubleshooting teams.
  • Machine documentation repositories.
  • Contractors or vendors who require access.

Updating a file on one engineer's computer does not update every copy used across the plant.

11. As-Built Documentation

As-built documentation describes the equipment as it was actually installed or configured after the work.

It should reflect the final accepted state rather than merely reproduce the original design proposal.

11.1 Examples

  • Electrical drawings showing actual terminal and wire connections.
  • PLC I/O lists showing installed device addresses.
  • Network diagrams showing actual IP addresses and switch connections.
  • HMI documentation reflecting the deployed screen and alarm changes.
  • Parameter registers showing final accepted settings.
  • Robot configuration records reflecting the applicable approved setup.
  • Test-bed drawings reflecting installed instrumentation.
  • Spare-parts lists showing the final installed model.

11.2 Why as-built accuracy matters

Inaccurate as-built records can cause:

  • Incorrect fault diagnosis.
  • Wrong replacement parts.
  • Unsafe isolation assumptions.
  • Incorrect PLC I/O identification.
  • Unplanned downtime.
  • Invalid maintenance instructions.
  • Repeated engineering work.
  • Failed audits or acceptance checks.

11.3 As-built update procedure

  1. Record the actual implementation.
  2. Compare the installed state against the approved design.
  3. Identify deviations.
  4. Resolve deviations through the applicable change-control process.
  5. Update affected drawings and configuration records.
  6. Review and approve the updated documents.
  7. Publish the controlled revision.
  8. Link the revision to the change record.

Do not hide an undocumented deviation by changing the drawing afterward without reviewing whether the actual change was authorized and acceptable.

12. PLC Documentation

PLC documentation should help another competent engineer understand the installed control system without relying on the original programmer being available.

12.1 Typical PLC documentation

  • PLC hardware configuration.
  • CPU and module model numbers.
  • Firmware versions.
  • Rack layout and slot assignments.
  • I/O list and addressing.
  • Electrical schematics.
  • Network configuration.
  • Program organization and routine descriptions.
  • Tag naming conventions.
  • Sequence and interlock descriptions.
  • Alarm and fault definitions.
  • Timer and counter functions where relevant.
  • Data structures and communications mappings.
  • Software revision and change history.
  • Backup and restoration procedure.
  • Test records.

12.2 Example I/O list

Signal tag Description Address Signal type Device
DI_FIXTURE_HOME Fixture at home position I0.0 Digital input Position sensor
DI_GUARD_CLOSED Guard closed indication I0.1 Digital input Guard switch
DO_CLAMP_EXTEND Clamp extend command Q0.0 Digital output Valve command
AI_PRESSURE Pressure measurement IW64 Analog input Pressure transmitter

These addresses are examples only. Actual addresses depend on the PLC platform and configuration.

A safety-related signal must be documented with its actual safety architecture and status. A normal PLC tag should not be presented as proof of a validated safety function.

12.3 PLC change documentation

For a logic modification, record:

  • Change ID and reason.
  • Affected routines, function blocks, or program sections.
  • Previous and new behavior.
  • I/O or tag changes.
  • Dependencies and interfaces.
  • Required tests and expected results.
  • Download or deployment record.
  • Actual deployed project revision.
  • Test evidence and known limitations.

13. HMI and SCADA Documentation

13.1 HMI documentation

Capture:

  • Screen names and navigation.
  • Tag bindings and addresses.
  • Alarm messages and priorities.
  • Operator commands and permissions.
  • Recipe and setpoint handling.
  • Communication settings.
  • Scripts and external dependencies.
  • Version and deployment information.

13.2 SCADA documentation

Capture:

  • System architecture.
  • Servers, clients, and communication paths.
  • Tag database and data sources.
  • Alarm and event configuration.
  • Historian and logging setup.
  • Scripts and scheduled tasks.
  • User roles and access controls.
  • Redundancy and recovery arrangements.
  • Reports and dashboards.
  • Interfaces with PLCs, databases, and other systems.

13.3 Change example

If an HMI alarm message changes, the documentation should identify the revised message, the triggering condition, the intended operator response, and any related PLC logic or alarm-priority changes.

Changing text without checking its operational meaning can make an alarm less useful, even if the screen looks much more polished.

14. VFD, Servo, CNC, and Robot Documentation

14.1 VFD and servo

Document:

  • Drive model and firmware.
  • Motor details.
  • Control mode.
  • Parameter values and units.
  • Ramp settings and limits.
  • Feedback and encoder configuration.
  • Communication settings.
  • Relevant protective functions.
  • Tuning and commissioning records.
  • Final tested configuration.

14.2 CNC

Document:

  • CNC model and software version.
  • Machine-builder configuration.
  • Program revisions.
  • Tool and work offsets.
  • Relevant machine parameters.
  • Compensation data.
  • PLC or PMC changes.
  • Alarm and recovery procedures.
  • Test and acceptance records.

14.3 Robotics

Document:

  • Controller and software versions.
  • Program revisions.
  • Tool center point and user-frame definitions.
  • Payload settings.
  • Motion and process parameters.
  • External-axis setup.
  • Safety configuration and validation records.
  • Fieldbus and I/O mappings.
  • Calibration and mastering records where applicable.
  • Recovery instructions and test results.

The documentation must identify machine-specific settings and distinguish approved operating values from temporary diagnostic changes.

15. Instrumentation and Test-Bed Documentation

For industrial test-beds, measurement configuration and acceptance limits are particularly important because a documentation error can produce incorrect test conclusions.

15.1 Required information

  • Instrument tag and asset ID.
  • Manufacturer and model.
  • Serial number.
  • Measurement range.
  • Output signal type.
  • Engineering units.
  • Scaling formula and PLC mapping.
  • Calibration status and applicable records.
  • Accuracy and response requirements.
  • Alarm and trip limits.
  • Test procedure revision.
  • Acceptance criteria.
  • Relevant traceability and test results.

15.2 Example: Pressure transmitter scaling

Suppose a transmitter produces 4–20 mA for a pressure range of 0–10 bar.

For a linear transmitter:

\[ P = \frac{I-4}{20-4}\times 10 \]

where \(P\) is pressure in bar and \(I\) is the measured current in mA.

At 12 mA:

\[ P = \frac{12-4}{16}\times 10 = 5\text{ bar} \]

The documentation should identify the transmitter range, signal type, scaling implementation, engineering units, relevant error limits, and verification method. The PLC raw-count scaling must also be documented where the analog module uses digital counts internally.

16. Industrial Network Documentation

A controlled network record should show the intended and installed communication arrangement.

16.1 Typical contents

  • Network topology.
  • Device names and asset identifiers.
  • IP address, subnet, and gateway.
  • VLAN assignments where used.
  • Switch model, firmware, and port configuration.
  • PLC and remote I/O connections.
  • Protocols and communication relationships.
  • Managed network redundancy.
  • Firewall and access-control rules.
  • Relevant cybersecurity controls.
  • Backup location and restoration method.
  • Approved network change history.

16.2 Documentation precautions

  • Avoid recording passwords in openly accessible diagrams.
  • Control sensitive network details.
  • Keep IP and device records consistent with the actual installation.
  • Record the configuration revision of managed devices.
  • Document communication dependencies and failure behavior.
  • Ensure that recovery instructions are available to authorized personnel.

A network diagram that omits a remote I/O adapter or an intermediate switch can turn a simple breakdown into a long exercise in guessing.

17. Parameter and Recipe Documentation

Parameters influence the behavior of machines, drives, controllers, and test processes. Their documentation must make it possible to distinguish approved values from temporary or experimental settings.

17.1 Parameter register

Field Purpose
Parameter ID Unique parameter reference
Description Explains what the parameter controls
Device or machine Identifies where it applies
Engineering unit Defines the value's meaning
Previous value Records the pre-change setting
Proposed value Records the requested setting
Final value Records the accepted setting
Permitted range Defines allowed limits
Reason for change Explains the technical objective
Approval reference Links the setting to authorization
Verification result Records the required check
Revision and date Supports traceability

17.2 Good documentation practices

  • Record units explicitly.
  • Identify the parameter address or name.
  • Distinguish requested, applied, and verified values.
  • Document dependencies and operating limits.
  • Record the final value from the actual system where practical.
  • Protect sensitive or safety-related settings.
  • Link the change to test evidence.
  • Record any temporary setting and its expiry or restoration requirement.

For example, documenting a speed setting as 1500 without specifying whether it means rpm, a raw drive value, a percentage, or another unit is an invitation to make an expensive mistake.

18. Testing and Verification Records

Test documentation establishes what was tested, under which conditions, against which requirements, and with what result.

18.1 Test record contents

  • Change ID and equipment ID.
  • Test plan revision.
  • Test case ID.
  • Preconditions and operating mode.
  • Test steps.
  • Expected result.
  • Actual result.
  • Pass/fail status.
  • Test date and personnel.
  • Instrument or test-equipment details, where relevant.
  • Defects and deviations.
  • Retest results.
  • Required approval or acceptance.

18.2 Example test record

Test ID Test condition Expected result Actual result Status
TC-01 Both fixture signals valid Cycle permissive granted Permissive granted Pass
TC-02 First fixture signal missing Cycle remains inhibited Cycle remains inhibited Pass
TC-03 Second fixture signal missing Cycle remains inhibited Cycle remains inhibited Pass
TC-04 Signal lost during sequence Defined fault response occurs Fault response recorded Pass

This example assumes those behaviors are the approved design requirements. Actual expected results must come from the applicable specification and risk assessment.

A test sheet with every row marked “OK” but no defined expected results is weak evidence. The record must show what success actually means.

19. Documentation of Deviations and Nonconformities

A deviation occurs when the actual implementation or result differs from the approved requirement, design, or procedure.

Examples:

  • A replacement component differs from the approved model.
  • A wire is connected to a different terminal than shown.
  • A software revision contains an unapproved change.
  • A test fails its acceptance criterion.
  • A drawing does not match the installed equipment.
  • A parameter differs from the approved value.

19.1 Deviation handling

  1. Record the deviation and affected equipment.
  2. Describe the expected and actual conditions.
  3. Assess safety, quality, operational, and technical implications.
  4. Determine whether the work or release must be stopped.
  5. Identify the responsible reviewer and required decision.
  6. Correct the condition or obtain a formally authorized disposition where permitted.
  7. Repeat required tests.
  8. Update affected documentation.
  9. Preserve evidence of the resolution.

Do not use a documentation correction to disguise an unauthorized physical or software change. The technical acceptability and authorization of the actual change must be addressed.

20. Change Log and Audit Trail

A change log provides a chronological record of important events.

Typical entries include:

  • Request submitted.
  • Impact assessment completed.
  • Review comments issued.
  • Approval granted or rejected.
  • Backup captured and verified.
  • Implementation started.
  • Software or hardware revision changed.
  • Testing completed.
  • Deviation recorded.
  • Release authorized.
  • Final documentation published.
  • Change closed.

20.1 Example change log

Date and time Event Reference Outcome
2026-10-18 09:00 Change request submitted CHG-2026-014 Submitted
2026-10-18 10:15 Technical review completed REV-TECH-014 Accepted
2026-10-18 11:00 Pre-change backup verified BKP-014 Verified
2026-10-18 13:30 Implementation completed IMP-014 Completed
2026-10-18 15:00 Functional tests completed TEST-014 Passed
2026-10-18 16:00 Final release recorded REL-014 Released

These entries illustrate the format, not a real change record.

20.2 Audit-trail principles

  • Preserve timestamps and responsible identities.
  • Link events to their source records.
  • Record decisions and significant revisions.
  • Prevent unauthorized alteration of records.
  • Correct mistakes using the approved correction process.
  • Preserve historical information according to retention requirements.

21. Document Storage, Access, and Retention

Documents should be stored where authorized personnel can retrieve the correct version and where the organization can protect their integrity.

21.1 Storage locations

Possible locations include:

  • Controlled engineering document-management systems.
  • Approved shared repositories.
  • Version-controlled software repositories.
  • Maintenance-management systems.
  • Asset-management systems.
  • Controlled configuration databases.
  • Approved backup storage.

The repository should be selected according to document type, access requirements, security needs, and the organization's procedures.

21.2 Access control

Define who may:

  • Read a document.
  • Create or edit a draft.
  • Review technical content.
  • Approve a revision.
  • Publish a controlled copy.
  • Supersede or withdraw a document.
  • Access sensitive configuration information.

Access should be based on legitimate job requirements. Unrestricted write access to production engineering files makes configuration control rather difficult, which is a polite way of saying that accidental edits become much easier.

21.3 Retention and archival

Retention requirements depend on organizational policy, contractual obligations, applicable law, safety requirements, and equipment lifecycle needs.

Preserve records such as:

  • Approved design revisions.
  • Change and approval history.
  • Pre-change and post-change configurations.
  • Required test and validation evidence.
  • Calibration and measurement records.
  • Maintenance and fault history.
  • Vendor documentation and recovery instructions.

Do not assume that a document can be deleted simply because a newer revision exists.

22. Electronic Document Control and Automation

Digital tools can reduce repetitive administration, but the workflow must still preserve review, authorization, and traceability.

22.1 Useful capabilities

  • Automatic document numbering.
  • Revision history.
  • Approval routing.
  • Notifications for pending actions.
  • Links to asset and change IDs.
  • Controlled templates.
  • Search and retrieval.
  • Audit logging.
  • Retention rules.
  • Dashboard reporting.

22.2 Excel, SAP, Power BI, and Power Automate

A maintenance organization might use:

  • Excel: structured registers, parameter lists, and controlled templates where permitted.
  • SAP: maintenance work orders, equipment records, material information, and linked documentation.
  • Power Automate: approval notifications and workflow tasks.
  • Power BI: status dashboards, overdue actions, and change-performance indicators.
  • Controlled file repositories: drawings, programs, test reports, and backup packages.

These systems should be integrated through approved processes. A dashboard showing that a change is approved does not itself prove that the correct program revision was downloaded.

22.3 Example automated workflow

Change request created
    ↓
Required fields checked
    ↓
Technical reviewers assigned
    ↓
Approval decision recorded
    ↓
Backup evidence attached
    ↓
Implementation and test records linked
    ↓
As-built documents reviewed
    ↓
Release and closure checks completed
    ↓
Change register and dashboard updated

Automation should prevent missing required information where practical, but it must not grant unauthorized approval or bypass required technical reviews.

23. Documentation Metrics and Management Indicators

Useful metrics should reveal whether documentation is accurate, current, complete, and usable.

Metric What it indicates
Changes with complete documentation Completeness of change records
Changes awaiting document updates Backlog after implementation
Outdated drawings identified Configuration-control weaknesses
Missing backup records Recovery readiness gaps
Missing test evidence Verification and audit gaps
Repeated documentation errors Process or training issues
Time to publish as-built revisions Speed of restoring an accurate reference
Changes closed with outstanding actions Closure discipline
Failed document retrieval attempts Accessibility or repository problems
Configuration mismatches found during audits Difference between records and actual equipment

Metrics need clear definitions. For example, “documentation complete” should mean that required documents are present, approved where necessary, correctly linked, and consistent with the actual final configuration.

Updating the program but not the I/O list Troubleshooting uses incorrect information Update all affected documents
Keeping several files labelled final Wrong version may be used Maintain a clear controlled master
Recording only requested parameter values Actual installed values remain unknown Record applied and verified values
Omitting the change ID Records cannot be traced reliably Link documents to the change register
Publishing unapproved drawings Incorrect instructions reach the shop floor Follow review and release controls

25. Practical Example: Complete Documentation for a Sensor Modification

Scenario: A pressure transmitter on an engine test-bed is replaced with a model that has a different measurement range.

Before implementation

The documentation package should identify:

  • The reason for replacement.
  • The asset and transmitter identification.
  • Existing and proposed model numbers.
  • Existing and proposed measurement ranges.
  • Electrical output and PLC analog-input compatibility.
  • Scaling and alarm-limit implications.
  • Relevant safety and quality impacts.
  • Required approvals.
  • Pre-change parameter and configuration backup.
  • Test plan and acceptance criteria.

During implementation

Record:

  • Actual transmitter model and serial number.
  • Wiring and terminal changes.
  • Installation details.
  • Actual PLC scaling and parameter changes.
  • Calibration or verification information, as required.
  • Deviations from the approved design.
  • Personnel and relevant timestamps.

After implementation

Complete:

  • Measurement-range verification.
  • Scaling verification across the required range.
  • Alarm and limit checks.
  • Functional test records.
  • Required quality acceptance.
  • Updated electrical drawings and I/O lists.
  • Updated instrument register.
  • Final configuration and backup records.
  • Release and closure records.

The documentation must establish that the installed transmitter, PLC scaling, displayed engineering units, alarm limits, and test acceptance criteria are mutually consistent. Correct wiring alone does not establish measurement accuracy.

27. Documentation Checklist

Change initiation

  • Change request and asset identification are recorded.
  • Scope and technical justification are clear.
  • Required impact and risk assessments are linked.
  • Reviewers and approvers are identified.
  • Relevant pre-change documents and backups are available.

Engineering and implementation

  • Design and configuration revisions are identifiable.
  • Required drawings, logic descriptions, and parameter registers are updated.
  • Implementation activities are recorded.
  • Actual installed models and configurations are captured.
  • Deviations and corrective actions are documented.
  • Relevant software and hardware versions are recorded.

Testing and release

  • Test procedures and acceptance criteria are defined.
  • Actual results and evidence are recorded.
  • Failed tests and retests are documented.
  • Required safety validation and quality acceptance are recorded.
  • Release authorization is documented.
  • The final accepted configuration is identified.

Closure and lifecycle control

  • As-built documents match the actual installation.
  • Superseded documents are controlled.
  • Required operating and maintenance instructions are updated.
  • Backup and recovery records are linked.
  • Required training and communication are completed.
  • Document locations and access permissions are appropriate.
  • Outstanding actions have owners and due dates.
  • Retention and closure requirements are satisfied.

28. Interview Questions and Answers

Q1. What is documentation in change management?

It is the controlled creation, revision, approval, distribution, and retention of information and records needed to describe and trace a change throughout its lifecycle.

Q2. Why must as-built drawings be updated?

They provide an accurate reference for the equipment as installed. Incorrect drawings can cause troubleshooting errors, incorrect replacements, unsafe work, and unnecessary downtime.

Q3. What is the difference between a document and a record?

A document communicates controlled information or instructions. A record provides evidence that an activity occurred or a result was obtained.

Q4. What is revision control?

Revision control identifies and manages successive versions of a document or configuration so users can determine which version is current and what changed between revisions.

Q5. What is a controlled master copy?

It is the authoritative version maintained in the designated repository or system under defined revision, access, and distribution controls.

Q6. Why should documentation be linked to a change ID?

It creates traceability between the original request, approval, implementation, backup, test results, final configuration, and closure.

Q7. What should be documented after a PLC modification?

The affected program elements, configuration and I/O changes, deployed revision, relevant backups, test results, deviations, final accepted version, and updates to associated engineering documents.

Q8. Why is a test report important?

It records the test conditions, expected and actual results, pass/fail decision, evidence, and any defects or retests. It provides objective evidence that acceptance requirements were evaluated.

Q9. What should happen when a drawing does not match the machine?

Record the discrepancy, assess its implications, establish the actual configuration, resolve any unauthorized change through the applicable process, and update and approve the controlled drawing.

Q10. Can a change be closed if documentation is incomplete?

Only if the organization's defined closure rules permit the specific outstanding items and they are formally controlled. Mandatory safety, acceptance, or release records must not be bypassed. Any permitted outstanding actions need assigned owners and deadlines.

Q11. How can documentation improve maintenance performance?

It reduces repeated investigations, supports correct fault diagnosis, improves replacement accuracy, preserves engineering knowledge, and helps technicians recover equipment more quickly.

Q12. What is the biggest documentation principle in industrial maintenance?

Maintain consistency between the authorized design, the actual installed configuration, the test evidence, and the controlled records.

29. Key Principles to Remember

  • Document the change from request through final closure.
  • Keep documents linked to the correct asset and change ID.
  • Maintain clear revision and approval status.
  • Update all affected drawings, programs, parameters, and procedures.
  • Preserve evidence of implementation, testing, deviations, and release.
  • Ensure as-built documents match the accepted physical and logical configuration.
  • Protect sensitive technical information and control access.
  • Preserve superseded revisions according to the applicable retention rules.
  • Use digital workflows to improve traceability without bypassing engineering decisions.
  • Treat documentation as part of the machine's technical lifecycle, not as paperwork added after the engineering work.

Practical objective: anyone authorized to maintain the machine should be able to identify its actual configuration, understand what changed, locate the supporting evidence, and determine how to operate, troubleshoot, and recover it safely.
