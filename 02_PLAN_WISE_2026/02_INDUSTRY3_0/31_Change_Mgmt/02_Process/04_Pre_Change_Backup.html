1. Purpose and Scope

A pre-change backup is a controlled copy of the existing machine configuration, software, parameters, settings, data, or documentation created before a modification is performed. It provides a known reference for comparison, recovery, troubleshooting, and rollback if the change fails or causes unexpected behavior.

In industrial maintenance and automation, a pre-change backup may be required before:

  • Editing PLC logic or downloading a new program.
  • Modifying HMI or SCADA applications.
  • Changing CNC or robot programs.
  • Adjusting VFD, servo, or motion-controller parameters.
  • Replacing PLC, HMI, industrial PC, or network hardware.
  • Changing switch configurations, IP addresses, or industrial network settings.
  • Updating firmware, operating systems, drivers, or application software.
  • Changing test-bed recipes, calibration-related settings, or measurement scaling.
  • Modifying SQL databases, Node-RED flows, dashboards, or reporting configurations.

The main objective is recoverability. If the change fails, the maintenance team should know what the previous state was, have a usable recovery copy, and understand how to restore it safely.

A file named BACKUP_FINAL_NEW_2 sitting on someone's desktop is not a dependable backup strategy. The backup must be identifiable, relevant, protected, and usable.

2. What a Pre-Change Backup Protects

A backup may preserve several different aspects of the existing system.

Backup category Examples Why it matters
Application software PLC, HMI, SCADA, CNC, robot programs Restore the previous application logic
Device configuration PLC hardware configuration, drive settings, robot setup Recover operating configuration
Parameters Speed, torque, pressure, scaling, tuning values Restore known parameter values
Firmware and versions Firmware revision, application version, driver version Re-establish compatibility
Network configuration IPs, VLANs, switch settings, routing Restore communication
Operating system Industrial PC image, OS settings, drivers Recover a failed computer
Data and databases SQL schema, configuration tables, critical records Recover affected data and structure
Integration configuration OPC UA settings, Node-RED flows, connection mappings Restore interfaces and data paths
Documentation Drawings, I/O lists, network diagrams, parameter registers Reconstruct the previous approved state
Machine-specific setup CNC offsets, robot frames, recipes, fixture settings Preserve application-specific configuration

Not every change requires every category. The backup scope should be based on the actual components affected, their dependencies, the risk of failure, and the available recovery method.

3. Backup, Snapshot, Archive, and Export

These terms are related but not interchangeable.

Term Meaning Example
Backup Recoverable copy of data or configuration PLC project backup
Snapshot Captured state at a particular point in time, often platform-dependent Virtual machine snapshot
Archive Preserved version for historical reference Approved PLC revision archive
Export Data or configuration extracted into a file or portable format Exported VFD parameters
Image Sector- or volume-level copy of a storage device Industrial PC disk image
Configuration capture Recorded settings and state, potentially in files or reports Managed switch configuration export
Restore point Defined state intended for recovery Approved pre-modification system state

A snapshot is not automatically a complete backup. For example, a virtual machine snapshot may depend on the original storage and may not protect against failure of the underlying storage device.

Likewise, an exported PLC project may not contain the complete running configuration or every value held in the physical controller.

4. Pre-Change Backup Within the Change Lifecycle

    ↓

    ↓

    ↓

    ↓
Existing state captured
    ↓
Backup verified and identified
    ↓
Change implementation begins
    ↓
Post-change testing
    ↓
Accept the change or initiate recovery
    ↓
Record final state and close the change

The exact sequence depends on the approved procedure. A backup should be completed before the first action that could overwrite, alter, or destroy the existing state.

For high-risk changes, approval to proceed may explicitly require a verified backup and a feasible recovery plan before implementation begins.

5. Backup Versus Rollback

A backup is the saved copy or captured state. Rollback is the controlled process of returning the affected system to a previous known state.

A successful rollback requires more than having a file.

It may require:

  • Compatible hardware.
  • Correct engineering software and licenses.
  • Access credentials and communication settings.
  • The correct firmware or runtime version.
  • A procedure to restore the program or configuration.
  • A safe machine state during restoration.
  • Verification that the restored system works correctly.
  • Recovery of dependent systems and associated data.
  • Authorization to return the system to operation.

For example, restoring a PLC program does not necessarily restore the drive parameters, HMI application, switch configuration, robot offsets, or external database that were also changed.

Backup answers “What can we restore?” Rollback answers “How will we return the system to a known state safely?”

6. Define the Backup Scope Before Starting

The first practical task is deciding exactly what must be captured.

6.1 Identify the affected assets

Record:

  • Plant, department, line, and machine.
  • Asset or equipment ID.
  • PLC, HMI, CNC, robot, drive, IPC, switch, and other affected devices.
  • Manufacturer and model.
  • Serial number or unique hardware identifier where relevant.
  • Firmware, software, and project versions.
  • Dependencies on other equipment or systems.
  • Current operating state and relevant configuration.

6.2 Identify what can change

For a PLC modification, the scope may include:

  • PLC application program.
  • Hardware and network configuration.
  • Controller-resident values and retained data, where relevant.
  • Firmware and project compatibility information.
  • HMI application and tag mapping.
  • Drive and remote I/O configurations.
  • Safety-controller project, where applicable.
  • Network settings and communication paths.
  • Current alarm and fault information.
  • Related electrical drawings and I/O lists.

For a CNC machine, the scope may include:

  • CNC program files.
  • Machine parameters.
  • Tool and work offsets.
  • Work coordinate systems.
  • Macro variables.
  • Tool-management data.
  • PLC or PMC programs.
  • Servo and spindle parameters.
  • Machine-builder settings.
  • Version information and relevant alarms.

The machine builder's recovery procedure should determine which data can safely be captured, exported, or restored. Some parameters are machine-specific and should not be replaced with generic values.

6.3 Create a dependency map

A change to one component may affect other components.

Example:

PLC logic modification
    ↓
I/O mapping and sequence behavior
    ↓
HMI tags and alarms
    ↓
Drive commands and feedback
    ↓
Industrial network communication
    ↓
Machine cycle and quality results

The backup scope should include affected dependencies when their configuration may need recovery.

7. Establish the Baseline Before the Change

A baseline is the documented reference state against which the modified system can be compared.

Capture the following where relevant:

  • Current software and configuration versions.
  • Existing parameter values.
  • Active faults and alarms.
  • Communication status.
  • Current machine operating condition.
  • Known defects or abnormal behavior.
  • Relevant production or test results.
  • Existing interlocks and operating limits.
  • Recent changes that may affect recovery.

This prevents a common troubleshooting mistake: attributing an old fault to the new change simply because it appeared during the same maintenance window.

7.1 Record known abnormalities

If a machine already has an intermittent sensor fault, record it before the change. If that fault remains after the modification, the team can compare evidence rather than debate what someone remembers from a night shift.

The baseline should distinguish:

  • Existing known faults.
  • New faults introduced during the work.
  • Unresolved faults discovered afterward.
  • Expected behavior changes caused by the approved modification.

8. Backup Quality: Capture, Verify, and Protect

A backup is not complete merely because a software tool displayed a success message.

A reliable backup process has three distinct stages:

  1. Capture: Obtain the required data or configuration from the correct source.
  2. Verification: Confirm that the copy is complete enough, readable, correctly identified, and suitable for the intended recovery method.
  3. Protection: Store it securely, preserve its integrity, and ensure it can be retrieved when required.

8.1 Verification methods

Depending on the backup type:

  • Reopen the exported project in compatible engineering software.
  • Confirm file sizes and expected file contents.
  • Check that required project files and dependencies are present.
  • Compare exported parameters against the device or approved register.
  • Confirm that the archive identifies the correct machine and revision.
  • Verify that database backup files can be read and restored using the supported method.
  • Check the result of a test restoration in a suitable environment when warranted.
  • Record the backup location and verification result.

A checksum can help detect accidental file changes. For example, SHA-256 produces a fingerprint of a file, but a matching checksum alone does not prove that the backup is complete or restorable.

8.2 Protect the backup

  • Use an approved storage location.
  • Apply access control appropriate to the system.
  • Avoid leaving the only copy on the engineering laptop being modified.
  • Maintain a separate protected copy when required by the risk and recovery policy.
  • Record the backup owner and retrieval method.
  • Protect credentials and sensitive configuration information.
  • Follow retention and cybersecurity requirements.
  • Ensure that the backup itself is not overwritten by the change.

9. PLC Pre-Change Backup

PLC backups require particular care because the project file on an engineering computer may differ from the program and configuration actually running in the controller.

9.1 What to capture

As applicable:

  • Complete engineering project.
  • Controller program and configuration.
  • Hardware and I/O configuration.
  • Network settings.
  • Controller and module firmware revisions.
  • Device-specific configuration.
  • Relevant tag and data structures.
  • Retained or recipe data required for recovery.
  • Safety-controller project and configuration, where applicable.
  • Online status and diagnostics.
  • Required passwords, certificates, licenses, or recovery dependencies, stored securely under site policy.

9.2 Offline project versus online controller

An offline project is the engineering file available on the workstation. An online upload or comparison is used, where supported, to assess the controller's current state.

These are not necessarily identical.

Possible differences include:

  • Logic changed online without the workstation project being updated.
  • Controller-resident values changed during operation.
  • Different project or firmware versions.
  • Missing comments or symbolic information.
  • Hardware configuration differences.
  • Changes not fully represented by an upload.

Before modifying a running controller, establish which project represents the actual running state and follow the vendor's approved upload, compare, and backup procedures.

9.3 PLC-specific precautions

  • Confirm the correct controller and machine before uploading or saving.
  • Verify the project identity and controller type.
  • Record the running revision and relevant firmware.
  • Understand which data values are retained and which are volatile.
  • Avoid changing controller mode merely to obtain a backup unless the procedure requires it.
  • Do not assume an upload captures every device setting or external dependency.
  • Preserve safety-related programs under their required controlled process.
  • Do not download the saved project as a casual backup test on a live machine.

A backup should not introduce a new operational risk while trying to reduce an existing one.

10. HMI and SCADA Pre-Change Backup

HMI and SCADA systems often contain configuration outside the main application project.

10.1 HMI backup contents

  • HMI project and version.
  • Screen and navigation configuration.
  • Tag definitions and addresses.
  • Alarm configuration.
  • Recipes and setpoints, where applicable.
  • User roles and access configuration.
  • Communication settings.
  • Fonts, images, scripts, and external dependencies.
  • Runtime and firmware compatibility information.

10.2 SCADA backup contents

  • Application projects.
  • Tag database and communication drivers.
  • Alarm and event configuration.
  • Historian settings and relevant data.
  • Scripts and scheduled tasks.
  • User roles and security configuration.
  • Reports and dashboards.
  • Redundancy settings.
  • Database schema and required data.
  • External interfaces and connection configuration.

A SCADA application backup may not contain the historian database or other external data stores. Each component must be handled according to its own backup and recovery requirements.

10.3 Verify the backup

  • Open the project using a compatible engineering environment.
  • Confirm the expected screens, tags, alarms, and scripts are present.
  • Record the runtime and engineering software versions.
  • Identify dependencies on external servers, databases, or file shares.
  • Confirm the approved recovery method before deploying a modified project.

11. VFD, Servo, and Motion-System Backup

Drive and motion configurations can contain critical application-specific settings.

11.1 Typical backup contents

  • Parameter export or upload.
  • Drive model and firmware.
  • Motor nameplate data.
  • Control mode.
  • Speed, torque, and current limits.
  • Acceleration and deceleration ramps.
  • Motor identification or tuning data.
  • Encoder or feedback configuration.
  • Communication settings.
  • Safety-related configuration where applicable.
  • Electronic gearing, camming, or motion settings.
  • Fault history and relevant diagnostics.

11.2 Critical precautions

  • Confirm the parameter set belongs to the correct drive and motor.
  • Record engineering units and scaling.
  • Confirm which parameters are read-only, calculated, or dependent on other settings.
  • Check whether the export includes all relevant parameters.
  • Preserve the existing motor and application data.
  • Understand the effects of restoring parameters on machine behavior.
  • Verify the required protective functions after restoration or replacement.
  • Use the approved procedure for safety-related drive configuration.

Two drives with the same model number may not use interchangeable parameter sets. Their motors, mechanical loads, feedback devices, and machine functions can differ.

12. CNC and Robot Backup

12.1 CNC systems

The required backup may include:

  • CNC part programs.
  • Machine-builder PLC or PMC program.
  • Machine parameters and compensation data.
  • Tool offsets and work offsets.
  • Macro variables and relevant persistent data.
  • Tool management and magazine configuration.
  • Servo and spindle settings.
  • Network and communication configuration.
  • HMI screens and machine-builder application data.
  • Software and firmware versions.

12.2 Robot systems

The required backup may include:

  • Robot application and program files.
  • Controller configuration.
  • Tool center point (TCP) definitions.
  • User frames and coordinate systems.
  • Payload and load data.
  • Motion and process settings.
  • Safety configuration and zones.
  • External-axis configuration.
  • Fieldbus mappings.
  • Calibration-related records.
  • Relevant controller and software versions.

12.3 Machine-specific recovery

Robot frames, mastering data, CNC compensation, and machine-builder parameters may be essential to safe and accurate operation.

Do not restore a generic or unrelated configuration merely because the controller accepts the file. Recovery must use the correct machine-specific baseline and required validation procedures.

13. Industrial Network and OT Configuration Backup

A network change may interrupt communication between controllers, drives, HMIs, remote I/O, safety systems, and supervisory applications.

13.1 What to preserve

  • Network topology.
  • IP addresses, subnet masks, and gateways.
  • VLAN and port configuration.
  • Managed-switch configuration.
  • Routing and redundancy settings.
  • Device names and protocol settings.
  • Firewall or access-control rules.
  • Industrial wireless configuration, where relevant.
  • Firmware and configuration versions.
  • Relevant network diagnostics and current fault state.

13.2 Verification and protection

  • Confirm the configuration belongs to the correct device.
  • Preserve the device identity and management access method.
  • Check whether the export includes all required settings.
  • Secure sensitive credentials and certificates.
  • Ensure a recovery route remains available if remote access is lost.
  • Document any configuration that must be restored manually.
  • Plan for communication validation after restoration.

A saved switch configuration is useful only if the replacement device or restoration method supports it. Hardware revisions, firmware differences, and licensing can affect compatibility.

14. Industrial PC, Server, and Operating-System Backup

Industrial PCs may host engineering software, machine interfaces, test applications, data collection, or vendor-specific runtime environments. Reinstalling Windows alone may not restore the machine to its original working state.

14.1 Backup contents

  • Operating-system edition and version.
  • System image or approved recovery image.
  • Installed software and versions.
  • Device drivers and firmware dependencies.
  • Application configuration.
  • License and activation information, handled securely.
  • Local databases and configuration files.
  • Network settings.
  • Scheduled tasks and services.
  • Required certificates and trust settings.
  • User access and permissions.
  • Vendor-specific recovery media and procedures.

14.2 Image backup versus file backup

A file backup preserves selected files and folders. A system image may preserve operating-system partitions, applications, boot configuration, and other selected disk structures.

A system image can help recover a failed disk or corrupted operating system, but restoration may depend on compatible hardware, disk layout, boot mode, encryption keys, and the imaging method.

For critical systems, determine whether both application-level backups and system-level recovery images are required.

15. Node-RED, SQL Server, and Grafana Backup

For an industrial data collection system, backing up only the dashboard is insufficient. The data flow may depend on Node-RED flows, credentials, SQL structures, driver settings, and Grafana configuration.

15.1 Node-RED

Capture, as applicable:

  • Flow definitions and subflows.
  • Relevant project files.
  • Node and package versions.
  • Runtime settings.
  • Required credentials and secure configuration.
  • Environment variables.
  • Connection settings.
  • Custom nodes and their dependencies.
  • Startup and service configuration.

Credential information may be encrypted or dependent on a credential secret. Preserve the required recovery information securely according to the approved procedure.

15.2 SQL Server

Capture:

  • Database backup using the supported SQL Server backup method.
  • Database name and relevant schema information.
  • Tables, views, stored procedures, and jobs where applicable.
  • Login and permission dependencies, handled securely.
  • Database configuration and recovery requirements.
  • Backup timestamp and database identity.
  • Required transaction logs and recovery-chain information where applicable.

A database backup is different from exporting a table to CSV. A CSV export may preserve selected rows but normally does not preserve the complete database structure, indexes, constraints, permissions, procedures, or transactional recovery capability.

15.3 Grafana

Capture, as applicable:

  • Dashboard definitions.
  • Data-source configuration.
  • Provisioning files.
  • Alert rules and notification settings.
  • User and access configuration where supported.
  • Plugin and version information.
  • Relevant database or application state, using the supported recovery method.

15.4 Integration dependencies

PLC and device configuration
    ↓
Node-RED flows and connection settings
    ↓
SQL Server database and schema
    ↓
Grafana data sources and dashboards
    ↓
Reports, alerts, and users

The recovery plan should identify which components must be restored together and in what order. Restoring a dashboard does not restore missing SQL data, and restoring SQL data does not repair a broken PLC communication flow.

16. Pre-Change Backup Procedure

A practical procedure for industrial maintenance should be repeatable and auditable.

Step 1: Confirm authorization

  • Verify the change request and approved scope.
  • Confirm the affected machine and equipment identifiers.
  • Identify the required backup and recovery controls.
  • Confirm that the planned work is authorized to begin.

Step 2: Identify the source of truth

Determine which version represents the actual installed or running configuration.

Possible sources include:

  • The online controller.
  • The current engineering project.
  • A controlled repository.
  • A machine-builder backup.
  • A verified parameter export.
  • A production database or server.

Resolve significant discrepancies before proceeding.

Step 3: Capture the existing state

  • Export or upload the relevant configuration using the approved method.
  • Save the current version before modifying it.
  • Record device identity, software version, and timestamp.
  • Capture relevant parameters, faults, and operating conditions.
  • Preserve associated documentation and dependencies.

Step 4: Store the backup

  • Use the approved storage location.
  • Apply the required access restrictions.
  • Use a unique name linked to the asset and change ID.
  • Preserve the previous baseline against accidental overwrite.
  • Store a separate protected copy when required.

Step 5: Verify the backup

  • Confirm the correct source was captured.
  • Check file completeness and readability.
  • Compare relevant configuration or parameter values.
  • Confirm that required dependencies are included.
  • Record the verification outcome.
  • Resolve any failed or incomplete backup before proceeding.

Step 6: Confirm recoverability

  • Review the rollback procedure.
  • Confirm required software, hardware, access, and licenses are available.
  • Check compatibility of the recovery copy.
  • Identify restoration limitations.
  • Confirm the required personnel and recovery window.
  • Test restoration in a suitable environment when warranted.

Step 7: Authorize the change to proceed

Confirm that the backup and recovery prerequisites have been satisfied and that any mandatory hold points are cleared.

Step 8: Preserve the record

Link the backup location, revision, verification evidence, and recovery method to the change request.

17. Backup Naming Convention and Folder Structure

A naming convention should make the backup identifiable without relying on memory or personal naming habits.

An illustrative pattern is:

[AssetID]_[System]_[ChangeID]_[PreChange]_[Timestamp]_[Revision]

Example:

TB105_PLC_CHG-2026-014_PRECHANGE_20261018_001

The date format above is YYYYMMDD.

A suitable folder structure could be:

Change_Management
    ↓
CHG-2026-014
    ↓
01_Request_and_Approval
    ↓
02_PreChange_Backup
    ↓
03_Implementation
    ↓
04_Test_Evidence
    ↓
05_PostChange_Baseline
    ↓
06_Closure

The folder names are examples, not mandatory standards. Use the organization's document-control and naming conventions where defined.

18. Backup Integrity, Checksums, and Version Control

Backup integrity means that the stored copy has not been unintentionally altered or corrupted and remains suitable for its intended use.

18.1 Checksums

A cryptographic hash such as SHA-256 can generate a fingerprint of a file.

If the file changes, the resulting fingerprint will normally change as well.

Checksums are useful for:

  • Detecting accidental file corruption or modification.
  • Comparing copies held in different locations.
  • Verifying that a transferred file matches the original.
  • Supporting controlled software release records.

A checksum does not establish that the original file was correct, that all required files were captured, or that the system can be restored.

18.2 Version control

For software and configuration changes:

  • Preserve the pre-change version.
  • Record the proposed and approved revisions.
  • Keep change descriptions and author information.
  • Compare revisions when supported.
  • Avoid overwriting the only known-good baseline.
  • Link deployed versions to the corresponding change record.
  • Maintain access controls for controlled repositories.

Version control is particularly useful for PLC, HMI, SCADA, scripts, configuration files, and other artifacts that change repeatedly.

18.3 Immutable or protected copies

For critical systems, use approved storage protections that prevent unauthorized modification or premature deletion. Depending on organizational policy, this may include restricted repositories, immutable retention, offline copies, or separate backup infrastructure.

These controls help reduce the risk that a malware incident, accidental deletion, or unauthorized change damages both the live system and its recovery copies.

19. Backup and Cybersecurity

Industrial backups can contain sensitive information, including network details, user configuration, proprietary logic, and credentials.

Apply the following principles:

  • Store backups in approved locations.
  • Restrict access according to job responsibilities.
  • Protect sensitive data in transit and at rest where required.
  • Use approved transfer methods and removable media.
  • Scan and validate files according to site cybersecurity procedures.
  • Protect credential secrets, certificates, and license information.
  • Avoid exposing production OT backups to uncontrolled internet-connected systems.
  • Maintain appropriate audit logs.
  • Preserve recovery access without creating unnecessary privileged accounts.

A backup may contain information that would help an attacker understand the plant. Recovery readiness and cybersecurity therefore need to be designed together.

20. Restoration Testing and Recovery Readiness

A backup that has never been tested may fail precisely when it is most needed.

Restoration testing should be proportionate to the criticality of the system and the risk of failure.

20.1 Possible restoration checks

  • Open a PLC or HMI project using compatible software.
  • Confirm that required files and dependencies are present.
  • Restore a database to a separate test instance.
  • Restore a virtual machine image in an isolated environment.
  • Validate a switch configuration against compatible hardware.
  • Verify parameter files and required device identifiers.
  • Confirm the documented recovery sequence is complete.
  • Record the test outcome and any limitations.

20.2 Avoid unsafe restoration tests

Do not test a recovery procedure by overwriting a live production controller or machine configuration without an approved test plan, appropriate authorization, and suitable safeguards.

For some equipment, a complete restoration test may require an offline controller, spare hardware, a simulator, a test bench, or a planned shutdown.

20.3 Recovery objectives

Two useful concepts are:

  • Recovery Point Objective (RPO): The maximum acceptable loss of data, expressed as a time interval.
  • Recovery Time Objective (RTO): The target time within which a system or service should be restored.

For example, a historian may require a short RPO to limit data loss, while a noncritical engineering workstation may tolerate a longer RPO. A production-critical controller may require a tightly controlled recovery process and a defined restoration target.

RPO and RTO should be set according to operational needs, not guessed after an outage has already started.

21. What to Do When a Backup Fails

If a backup cannot be captured, verified, or restored, do not treat the missing backup as a paperwork problem.

  1. Stop the affected change activity before any action that could make recovery harder, unless a separately authorized emergency procedure governs the situation.
  2. Identify the failure and its cause.
  3. Determine whether another valid baseline exists.
  4. Consult the equipment manufacturer or competent engineering personnel if required.
  5. Reassess the risks and recovery options.
  6. Document the limitation and obtain a decision from the authorized role.
  7. Proceed only if the revised plan satisfies the applicable requirements.

Examples of backup failures include:

  • The PLC upload is incomplete.
  • The engineering project differs from the running controller.
  • The drive export omits critical settings.
  • The database backup fails verification.
  • A robot backup lacks required machine-specific data.
  • The only copy is stored on the workstation scheduled for replacement.
  • The recovery file requires unavailable software or credentials.

For safety-critical or production-critical systems, the inability to establish a reliable recovery path may be a reason to postpone the change.

22. Post-Change Comparison and Final Baseline

After the modification, preserve the final accepted configuration separately from the pre-change backup.

The pre-change copy represents the original state. The post-change baseline represents the state accepted after implementation and testing.

22.1 Compare the two states

Check:

  • Intended logic and configuration changes.
  • Unexpected parameter differences.
  • Hardware and firmware revisions.
  • Communication and network settings.
  • Alarms and fault behavior.
  • Machine operating behavior.
  • Test results and acceptance criteria.
  • Required documentation updates.

Not every difference is a defect. Some differences are expected outcomes of the approved modification. The purpose of comparison is to identify and explain relevant changes, not to force the modified system to match its old state.

22.2 Preserve both versions

  • Keep the pre-change backup under the required retention policy.
  • Save the final accepted configuration as a separate controlled version.
  • Link both to the change ID.
  • Record the tests and release decision.
  • Document any known limitations or deviations.
  • Update the asset's configuration record.

Do not overwrite the original backup with the modified version. That destroys the ability to establish what existed before the change.

23. Practical Example: PLC Program Modification

Scenario: A PLC sequence is modified to add an additional fixture-position confirmation.

Before the change:

  • Identify the correct PLC and machine.
  • Confirm the actual running program and hardware configuration.
  • Save the appropriate project and required controller configuration.
  • Record the relevant I/O mapping, firmware, and parameters.
  • Capture known faults and operating conditions.
  • Verify the backup and confirm the rollback procedure.

During implementation:

  • Apply the approved program revision.
  • Record the deployed version.
  • Follow the authorized download and commissioning procedure.
  • Preserve the pre-change copy without modification.

After implementation:

  • Test both position confirmations.
  • Test missing or invalid signals.
  • Verify fault indication and recovery behavior.
  • Test relevant existing sequences for regression.
  • Compare the deployed configuration against the approved revision.
  • Save the final accepted project separately.
  • Update the change record and required documentation.

If the new sequence fails, the team should have a defined recovery method and clear evidence of the previous state. Restoring the previous program must still follow the approved procedure and must not bypass required safety controls.

24. Practical Example: Replacing an Industrial PC

Scenario: An industrial PC hosting a machine interface and data collection application must be replaced.

The backup package may need:

  • A system image or approved recovery image.
  • Application installers and versions.
  • Runtime configuration.
  • Drivers and communication settings.
  • Node-RED flows and required dependencies.
  • SQL connection configuration.
  • Grafana dashboards or provisioning files, if hosted on the PC.
  • Licenses and certificates handled securely.
  • Network configuration.
  • Recovery and acceptance procedures.

The recovery plan should distinguish what belongs to the PC from what resides on external servers. If SQL Server is hosted elsewhere, replacing the PC does not by itself restore the database.

After replacement, verify communication with the PLC, data collection, database writes, dashboard updates, alarms, and any critical reporting functions before release.

26. Pre-Change Backup Checklist

Before capturing

  • Change request and scope are confirmed.
  • Correct machine and device identities are verified.
  • Actual running configuration is identified.
  • Required backup components and dependencies are listed.
  • Current revisions, firmware, and software versions are recorded.
  • Known faults and relevant operating conditions are documented.
  • Required authorization and access are available.

During backup

  • Approved capture or export method is used.
  • Relevant programs, parameters, and configurations are included.
  • Required data and dependencies are preserved.
  • Sensitive credentials and configuration information are protected.
  • Backup files use identifiable names and revisions.
  • The original baseline is not overwritten.

Before implementation

  • Backup completeness and readability are checked.
  • Source identity and revision are confirmed.
  • Backup location and retrieval method are recorded.
  • Recovery prerequisites are available.
  • Rollback procedure is understood.
  • Restoration limitations are documented.
  • Required hold points are cleared.
  • Backup evidence is linked to the change record.

After implementation

  • Required tests and acceptance checks are complete.
  • The final configuration is saved separately.
  • Relevant differences are reviewed.
  • Recovery and rollback records are updated if needed.
  • Documentation and asset records are updated.
  • Pre-change and post-change versions are traceable.
  • Required retention and closure actions are complete.

27. Interview Questions and Answers

Q1. What is a pre-change backup?

It is a controlled copy or capture of the existing system state made before a modification so that the original configuration can be referenced or restored if necessary.

Q2. Why is a pre-change backup important in industrial maintenance?

It reduces recovery uncertainty, preserves configuration evidence, supports rollback, and helps distinguish pre-existing faults from problems introduced by the change.

Q3. Is saving a PLC project sufficient?

Not necessarily. The saved project may differ from the running controller and may not contain all required parameters, retained values, device configurations, or external dependencies. The actual backup scope must be established.

Q4. What is the difference between backup and rollback?

A backup is the saved state. Rollback is the controlled process of restoring a previous state and verifying that the system can safely return to operation.

Q5. How do you verify a backup?

Check the source identity, completeness, revision, readability, dependencies, and suitability for restoration. Where appropriate, test restoration in an isolated or otherwise suitable environment.

Q6. Why should the pre-change backup be preserved separately?

It provides an unmodified reference to the original state. Overwriting it with the modified configuration removes evidence needed for comparison and recovery.

Q7. What should be included in a VFD backup?

The required parameter set, device identity, firmware, motor data, control mode, limits, ramps, feedback configuration, communication settings, and relevant application-specific configuration. Safety-related configuration needs its prescribed control and validation.

Q8. What is the difference between a database export and a database backup?

An export generally extracts selected data into a portable format. A proper database backup, performed using the supported method, can preserve database structures and recovery information needed to restore the database.

Q9. What should happen if a verified backup cannot be obtained?

The team should assess available recovery options, document the limitation, reassess risk, and obtain an authorized decision before proceeding. The change may need to be postponed.

Q10. What are RPO and RTO?

RPO is the maximum acceptable data-loss interval. RTO is the target time to restore the system or service after a disruption.

Q11. Why is a post-change baseline necessary?

It preserves the final accepted configuration and provides a reference for future maintenance, troubleshooting, audits, and subsequent changes.

Q12. When should a backup be taken?

Before any planned action that could overwrite or alter the existing state, after the scope and required authorization have been established and early enough to verify the recovery prerequisites.

28. Key Principles to Remember

  • A backup must represent the correct machine and the actual relevant baseline.
  • Capture all affected components and dependencies, not merely the most visible file.
  • Verification is different from successful file creation.
  • A backup is useful only when it can be retrieved and restored using a feasible procedure.
  • Recovery must account for hardware, firmware, software, parameters, data, credentials, and compatibility.
  • Preserve the original baseline separately from the final accepted version.
  • Protect backups against accidental modification, unauthorized access, and loss.
  • Never use an uncontrolled restoration test on live production equipment.
  • Link backup evidence and recovery arrangements to the change-control record.
  • Treat a missing or unusable backup as a risk that requires an explicit decision.

Practical objective: before modifying any industrial system, establish what exists, preserve the relevant state, verify that the copy is usable, and define how recovery will work before the machine is placed at risk.
