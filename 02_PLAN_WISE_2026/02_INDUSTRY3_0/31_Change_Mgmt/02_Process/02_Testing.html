1. Purpose and Scope

Testing is the systematic process of checking whether equipment, software, control logic, instrumentation, processes, and integrated systems meet defined requirements under specified conditions.

In industrial maintenance and automation, testing is essential when:

  • A failed component is repaired or replaced.
  • PLC logic or HMI screens are modified.
  • A machine is retrofitted or upgraded.
  • Sensors, drives, or instruments are changed.
  • A network connection or communication interface is modified.
  • A safety-related function is installed or altered.
  • A machine is recommissioned after a breakdown.
  • A new process, product variant, or operating parameter is introduced.

The purpose of testing is to produce objective evidence that the system behaves as required, including when faults or abnormal conditions occur.

A machine starting successfully does not prove that it is correct, safe, accurate, reliable, or ready for production. It proves one narrow thing: it started. Humans have spent decades confusing that with completion, so we may as well document the distinction.

2. Testing Versus Related Activities

Activity Purpose Example
Inspection Checks condition, installation, or visible conformity Verifying a sensor mounting bracket
Testing Evaluates behavior against defined criteria Checking sensor response at specified positions
Verification Confirms specified requirements have been met Checking wiring against the approved schematic
Validation Confirms suitability for intended use Demonstrating that the modified test-bed produces valid results
Commissioning Establishes the installed system's operational readiness Bringing a retrofitted machine into controlled operation
Calibration Establishes the relationship between an instrument's indication and a reference Comparing a pressure transmitter with a calibrated reference
Adjustment Changes an instrument or system to reduce its error Correcting a permitted measurement offset
Qualification Demonstrates that equipment or a process meets specified qualification requirements Qualifying a new production process
Acceptance testing Determines whether predefined acceptance criteria have been satisfied Site acceptance of a new PLC-controlled station
Monitoring Observes performance over time Tracking machine alarms and cycle time after a modification

These activities can overlap, but they are not interchangeable. For example, calibration does not automatically prove that a complete pressure test system is suitable for its intended production test.

3. Why Testing Is Necessary

Testing helps to detect:

  • Incorrect wiring and I/O mapping.
  • Hardware compatibility problems.
  • Incorrect PLC logic or sequence transitions.
  • Faulty sensor scaling.
  • Incorrect drive parameters.
  • Communication failures.
  • Unexpected machine movement.
  • Defective or ineffective interlocks.
  • Incorrect alarms and fault recovery.
  • Measurement inaccuracies.
  • Regression defects affecting existing functions.
  • Performance shortfalls.
  • Documentation and configuration mismatches.

Testing also reduces the chance of releasing defects into production, where they may create quality problems, breakdowns, rework, safety risks, and prolonged troubleshooting.

6. Define Requirements Before Testing

A test is useful only when there is a clear basis for deciding whether the result passes or fails.

6.1 Sources of requirements

  • Approved engineering specifications.
  • Functional design documents.
  • Electrical and mechanical drawings.
  • PLC and HMI functional requirements.
  • Machine-safety requirements.
  • Instrument datasheets and calibration requirements.
  • Quality plans and control plans.
  • Production cycle-time targets.
  • Communication specifications.
  • Customer requirements.
  • Applicable legal, regulatory, and technical requirements.

6.2 Requirements must be testable

Weak requirement: “The sensor should work properly.”

Testable requirement: “The sensor shall detect the specified target within the defined operating distance and detection conditions, and the corresponding PLC input shall change state within the approved response-time limit.”

Weak requirement: “The machine must be fast.”

Testable requirement: “The machine shall complete the defined production cycle within the approved cycle-time limit under the specified test conditions.”

A testable requirement identifies what must happen, under which conditions, and how acceptance will be determined.

6.3 Acceptance criteria

Acceptance criteria may specify:

  • Correct functional sequence.
  • Permitted measurement error.
  • Maximum response time.
  • Required cycle time.
  • Allowed leakage.
  • Communication recovery behavior.
  • Required safety-function performance.
  • Acceptable defect rate.
  • Completion of required documentation and training.

Criteria should be defined before testing wherever practical. Otherwise, teams can unconsciously move the goalposts after seeing the results.

7. Types and Levels of Testing

7.1 Unit testing

Tests an individual component, function, or software module in isolation.

Examples:

  • Testing a PLC function block.
  • Checking an analog scaling calculation.
  • Verifying a data-conversion function.
  • Testing a sensor with a suitable test target.
  • Checking a motor protection relay's specified functions.

Unit testing is particularly useful when the individual function can be tested without operating the complete machine.

7.2 Integration testing

Checks whether interconnected components work correctly together.

Examples:

  • Sensor to PLC input to HMI indication.
  • PLC to VFD communication.
  • PLC to robot handshake.
  • PLC to SCADA data exchange.
  • Node-RED to SQL Server data logging.

A component may pass its individual test while the integrated system fails because of incompatible data types, incorrect addressing, timing, wiring, or interface assumptions.

7.3 System testing

Tests the complete system against its functional and operational requirements.

Examples:

  • Full automatic production sequence.
  • Complete engine test-bed operating cycle.
  • CNC machining sequence from loading through unloading.
  • Conveyor transfer across multiple stations.
  • End-to-end production data collection.

7.4 Acceptance testing

Determines whether the equipment meets predefined acceptance requirements.

Common forms include:

  • Factory Acceptance Testing (FAT).
  • Site Acceptance Testing (SAT).
  • User Acceptance Testing (UAT), where relevant.
  • Contractual performance or reliability acceptance tests.

7.5 Regression testing

Repeats selected tests after a change to confirm that existing functionality has not been adversely affected.

Examples:

  • Testing all affected automatic sequences after a PLC change.
  • Verifying existing recipes after an HMI update.
  • Checking robot handshakes after a network modification.
  • Confirming existing alarms after a controller migration.

Regression testing should be based on change impact and risk. It may need to cover far more than the newly added function.

7.6 Performance testing

Measures performance against quantitative requirements.

Examples:

  • Machine cycle time.
  • Sensor response time.
  • Communication latency.
  • Data acquisition rate.
  • Pressure stability.
  • Measurement accuracy.
  • Production throughput.
  • Recovery time after a defined fault.

7.7 Stress and endurance testing

  • Stress testing: Evaluates behavior under demanding but defined operating conditions.
  • Endurance testing: Evaluates behavior over an extended period or number of cycles.
  • Load testing: Evaluates performance under a specified load or demand.
  • Soak testing: Operates a system for a defined period to identify issues such as thermal instability, memory leaks, or intermittent faults.

These tests must remain within approved operating and safety limits. Testing a machine beyond its safe design envelope is not a legitimate shortcut to understanding its limits.

8. Factory Acceptance Testing and Site Acceptance Testing

8.1 Factory Acceptance Testing (FAT)

FAT is performed before delivery or site installation, when the equipment arrangement and contract allow testing at the manufacturer's or integrator's facility.

Typical checks include:

  • Hardware configuration.
  • Software version.
  • I/O simulation.
  • Functional sequences.
  • Alarms and diagnostics.
  • Communication interfaces.
  • Defined performance requirements.
  • Documentation and backup availability.

FAT can identify defects before shipment, reducing site commissioning time.

8.2 Site Acceptance Testing (SAT)

SAT verifies the installed system in its actual operating environment.

Typical checks include:

  • Correct installation and wiring.
  • Site utilities and interfaces.
  • Actual sensors and actuators.
  • Network connectivity.
  • Upstream and downstream equipment.
  • Safety devices and protective functions.
  • Production process behavior.
  • Site-specific acceptance criteria.

8.3 FAT versus SAT

Aspect FAT SAT
Location Supplier or integration facility Actual installation site
Main purpose Verify the prepared system before delivery Verify the installed system in its real environment
Interfaces May use simulation or test equipment Uses actual site interfaces where practical
Installation May not represent final installation Includes installed equipment and site conditions
Defect detection Design, software, and integration issues Installation, interface, and site-integration issues
Final readiness Usually not sufficient alone Supports site acceptance and release

FAT does not eliminate the need for site testing. A system can pass FAT and still fail at the site because of wiring errors, incorrect utilities, network settings, installation conditions, or interface differences.

9. Test Planning and Test Cases

A test plan defines what will be tested, how it will be tested, who will perform it, and how the results will be accepted.

9.1 Test plan contents

  • Test scope and objectives.
  • System under test.
  • Applicable requirements and revisions.
  • Test environment and configuration.
  • Test methods and procedures.
  • Required tools and calibration status.
  • Personnel and responsibilities.
  • Preconditions and safety precautions.
  • Test sequence and dependencies.
  • Acceptance criteria.
  • Defect reporting process.
  • Retesting and regression requirements.
  • Required evidence and approvals.

9.2 Test case template

Field Example
Test ID TC-SEN-001
Requirement ID REQ-SEN-004
Test objective Verify sensor detection
Preconditions Machine in the approved test state
Input or action Present the specified target
Expected result Sensor and corresponding PLC input change state correctly
Acceptance criterion Detection occurs within the specified operating limits
Actual result Recorded during test execution
Status Pass, fail, blocked, or not run
Evidence Test log, measurement, or approved screenshot
Tester and date Authorized person and execution date

Each test should be reproducible. A test case such as “check sensor” lacks enough information to establish what was actually verified.

10. Positive, Negative, and Boundary Testing

10.1 Positive testing

Checks expected behavior under valid conditions.

Examples:

  • Sensor detects a correctly positioned component.
  • PLC executes the normal production sequence.
  • VFD reaches the commanded speed.
  • HMI displays the correct pressure reading.

10.2 Negative testing

Checks behavior under invalid, missing, or abnormal conditions.

Examples:

  • Sensor signal is lost.
  • Communication is interrupted.
  • An invalid recipe is selected.
  • A required permissive is absent.
  • A measurement exceeds a defined limit.

Negative testing verifies that the system detects and handles abnormal conditions as specified.

10.3 Boundary testing

Checks behavior near specified limits.

Examples:

  • Pressure at the lower and upper acceptance limits.
  • Analog signal near a defined alarm threshold.
  • Sensor operating distance near its specified detection limit.
  • Cycle time near its maximum permitted value.
  • Counter values near a defined overflow boundary.

Boundary testing should use approved limits and safe test methods. Where the boundary involves a safety limit, the test procedure must account for the relevant hazard.

10.4 Example: Pressure alarm

Suppose a test-bed has an approved high-pressure alarm threshold of 8 bar.

A suitable test plan may verify:

  • A pressure safely below the threshold does not generate an unintended high-pressure alarm.
  • The alarm activates when the configured threshold and specified triggering conditions are met.
  • The alarm indication is correct on the HMI.
  • The alarm response and recovery match the approved functional specification.
  • Sensor failure is handled according to the defined fault strategy.

The actual test values, tolerances, and method must follow the approved specification. Do not deliberately create hazardous overpressure merely to prove an alarm.

11. Testing Strategy for PLC Systems

PLC testing must consider logic correctness, I/O behavior, sequence transitions, abnormal conditions, and interactions with the physical process.

11.1 I/O testing

Verify:

  • Physical input corresponds to the correct PLC tag.
  • Input polarity and logic state are correct.
  • Output commands reach the intended device.
  • Field wiring matches the approved drawings.
  • Analog ranges and scaling are correct.
  • Diagnostics identify relevant signal faults.
  • I/O behavior remains correct during required operating modes.

11.2 Sequence testing

Test each relevant state and transition.

For example:

Idle
  ↓
Ready checks
  ↓
Start accepted
  ↓
Clamping
  ↓
Process operation
  ↓
Completion checks
  ↓
Cycle complete
  ↓
Return to idle

For every transition, verify:

  • Required permissives.
  • Triggering conditions.
  • Expected outputs.
  • Timing requirements.
  • Timeout behavior.
  • Fault response.
  • Recovery conditions.

11.3 Interlock testing

An interlock prevents an operation unless specified conditions are satisfied.

Examples:

  • Prevent cycle start when the required fixture position is not confirmed.
  • Prevent spindle operation unless required conditions are met.
  • Prevent a transfer until the receiving station is ready.
  • Prevent a test sequence when required instrumentation is unavailable.

Verify both the normal interlock behavior and the defined response to missing or invalid signals.

Important: Ordinary process interlocks and safety-related interlocks are not necessarily equivalent. Safety functions require the appropriate design, components, and validation for their intended risk-reduction role.

11.4 PLC fault testing

Depending on the design and approved test method, verify:

  • Loss of a required input.
  • Sensor disagreement.
  • Communication timeout.
  • Device fault indication.
  • Sequence timeout.
  • Invalid mode transition.
  • Recovery after a defined fault.
  • Correct alarm reset conditions.

Never force live outputs or bypass safety logic casually to simulate a fault. Use an approved test method, simulation environment, or controlled commissioning procedure appropriate to the hazard.

12. Testing HMI and SCADA Systems

HMI and SCADA testing covers operator interaction, displays, commands, alarms, historical data, access permissions, and recovery.

12.1 Display testing

  • Correct tag names and descriptions.
  • Correct units and scaling.
  • Correct status indication.
  • Appropriate display of invalid or stale data.
  • Correct recipe and mode information.
  • Clear indication of equipment faults.

12.2 Command testing

  • Start and stop commands operate as specified.
  • Commands are rejected when required permissives are absent.
  • Mode changes follow the approved sequence.
  • Unauthorized commands are prevented.
  • Reset commands do not bypass required fault conditions.

12.3 Alarm testing

  • Alarm triggers at the defined condition.
  • Alarm text identifies the relevant equipment and problem.
  • Priority and acknowledgement behavior are correct.
  • Alarm timestamps are meaningful.
  • Clearing conditions are correctly defined.
  • Alarm history is retained where required.

12.4 Historian and data testing

  • Correct tags are recorded.
  • Values and units are accurate.
  • Timestamps and time synchronization are handled correctly.
  • Missing data is detectable.
  • Data is stored at the specified interval.
  • Reports and trends use the correct data.
  • Access permissions and retention behavior meet requirements.

A dashboard showing a number does not establish that the number is correct. Verify the full path from the original signal to the displayed value.

13. Testing Sensors and Analog Measurements

13.1 Digital sensor testing

Verify:

  • Sensor model and wiring.
  • PNP/NPN compatibility where relevant.
  • Normally open or normally closed behavior.
  • Detection distance and target compatibility.
  • Response time.
  • Repeatability.
  • Switching stability.
  • PLC input mapping.
  • Fault behavior where specified.

13.2 Analog signal testing

Common industrial signal ranges include 4–20 mA and 0–10 V. The correct range depends on the installed transmitter and receiving input.

For a linear transmitter, scaling can be calculated as:

\[ PV = LRV + \frac{I-I\_{\min}}{I\_{\max}-I\_{\min}}(URV-LRV) \]

Where:

  • \(PV\) is the calculated process value.
  • \(LRV\) and \(URV\) are the lower and upper engineering-range values.
  • \(I\) is the measured input signal.
  • \(I\_{\min}\) and \(I\_{\max}\) are the corresponding signal limits.

For a 4–20 mA pressure transmitter measuring 0–10 bar:

\[ PV = \frac{I-4}{20-4}\times 10 \]

At 12 mA:

\[ PV = \frac{12-4}{16}\times 10 = 5\text{ bar} \]

This calculation assumes correct wiring, a linear transmitter, and correct input configuration. Actual acceptance also depends on instrument accuracy, input accuracy, calibration status, and specified tolerances.

13.3 Calibration and measurement verification

Testing may include:

  • Reference instrument verification.
  • Multiple points across the operating range.
  • Increasing and decreasing measurements where appropriate.
  • Repeatability checks.
  • Alarm and threshold checks.
  • Confirmation of units and scaling.
  • Recording as-found and as-left results when required.

Calibration and functional testing answer different questions. An instrument can be calibrated correctly while the PLC scaling, wiring, or HMI display remains wrong.

14. Testing VFDs, Servos, and Motors

Testing must cover electrical installation, configuration, commanded behavior, protection, and interactions with the machine.

14.1 VFD testing

  • Verify motor and drive identification.
  • Confirm approved parameter settings.
  • Verify direction of rotation using the approved procedure.
  • Check commanded and actual speed.
  • Check acceleration and deceleration behavior.
  • Verify relevant fault indications.
  • Test required communication and control modes.
  • Confirm that protective functions and machine interlocks behave as specified.

14.2 Servo testing

  • Verify motor, drive, encoder, and feedback compatibility.
  • Confirm homing behavior.
  • Check direction and coordinate conventions.
  • Verify travel limits and permitted motion.
  • Confirm positioning accuracy and repeatability.
  • Check following-error detection and fault recovery.
  • Verify interactions with mechanical stops and machine tooling.

14.3 Motor and electrical tests

Depending on the equipment and approved procedure, checks may include:

  • Insulation resistance where applicable.
  • Winding resistance where appropriate.
  • Protective-earth continuity.
  • Connection and terminal inspection.
  • Supply and phase verification.
  • Rotation and operating current.
  • Overload and protection configuration.

Use test methods suitable for the connected electronics. Insulation testing, for example, must not expose sensitive drives or control devices to inappropriate test voltages.

15. Testing CNC and Robot Systems

15.1 CNC testing

  • Verify the correct program revision.
  • Confirm tool offsets and work coordinate settings.
  • Check tool and fixture compatibility.
  • Verify axis direction and travel limits.
  • Check spindle and feed behavior.
  • Confirm interlocks and alarms.
  • Validate machining or test results against acceptance criteria.
  • Verify recovery behavior after a defined fault.

15.2 Robot testing

  • Verify program and tool data revisions.
  • Check the intended path and target positions.
  • Confirm gripper and fixture interactions.
  • Verify handshakes with PLCs and adjacent equipment.
  • Check recovery and restart behavior.
  • Validate relevant protective functions.
  • Confirm that the approved test conditions and access controls are in place.

Testing should begin in the safest suitable environment, such as simulation or controlled commissioning mode, before moving to more demanding operating conditions.

16. Testing Industrial Networks and Communications

Communication testing should evaluate both normal operation and defined failure conditions.

16.1 Basic checks

  • Correct device addresses.
  • Correct subnet and network configuration.
  • Correct protocol and configuration.
  • Correct tag or data mapping.
  • Expected communication update rate.
  • Correct timeout and diagnostic behavior.
  • Recovery after an interruption.
  • No unintended impact on critical control functions.

16.2 Protocol examples

Technology Typical testing focus
PROFINET Device configuration, cyclic data, diagnostics
EtherNet/IP Connection status, assemblies, data mapping
Modbus TCP Register mapping, data types, timeouts
OPC UA Endpoint, certificates, permissions, data quality
MQTT Broker connectivity, topic mapping, delivery behavior
Serial communication Baud rate, parity, addressing, framing, error handling

The test strategy must match the protocol and application. A successful network ping is not proof that industrial data exchange is correct.

17. Safety Function Testing and Validation

Safety-related testing requires more than checking whether a device changes state.

17.1 Examples of safety-related functions

  • Emergency-stop response.
  • Guard interlocking.
  • Light curtain response.
  • Safe motion functions.
  • Prevention of unexpected restart.
  • Safety-related speed monitoring.
  • Defined safe-state response after a fault.

17.2 Validation considerations

  • Confirm the intended safety function and requirements.
  • Verify the installed architecture and component suitability.
  • Check wiring, configuration, and diagnostics.
  • Test relevant normal and fault conditions.
  • Verify the required response and timing.
  • Confirm that reset and restart behavior match the design.
  • Record results and unresolved deviations.
  • Obtain the required competent-person review and authorization.

A reset must not automatically initiate hazardous motion unless that behavior is explicitly intended, appropriately controlled, and permitted by the applicable requirements.

Safety validation should be planned by competent personnel using the applicable standards and the actual system design. Do not treat an ordinary functional test as a substitute for required validation.

18. Test Equipment and Calibration Control

Test results are only as trustworthy as the measurement method and equipment used to obtain them.

18.1 Common test equipment

Equipment Typical application
Digital multimeter Voltage, resistance, and current checks within its ratings
Clamp meter Current measurement
Insulation resistance tester Insulation assessment where suitable
Oscilloscope Signal shape, noise, and timing analysis
Process calibrator Simulating or measuring industrial process signals
Pressure calibrator Pressure measurement verification
Tachometer Rotational speed measurement
Thermal camera Temperature distribution and hot-spot inspection
Network diagnostic tools Communication and network analysis
PLC simulation software Testing logic without full physical operation
Reference sensor or instrument Comparison against a suitable measurement reference

18.2 Test equipment controls

Before testing:

  • Confirm equipment is suitable for the measurement and environment.
  • Check calibration status where required.
  • Verify range, accuracy, and resolution.
  • Inspect leads, probes, connectors, and accessories.
  • Confirm appropriate electrical safety ratings.
  • Record equipment identification when required by the test procedure.

After testing, record any abnormal behavior or suspected measurement error. If a test instrument is found to be out of calibration, assess whether previously accepted results may have been affected.

19. Defect Management and Retesting

A failed test must lead to a controlled decision, not simply another attempt until the result looks better.

19.1 Defect classification

Defects may be classified according to:

  • Safety impact.
  • Functional impact.
  • Quality impact.
  • Performance impact.
  • Documentation impact.
  • Severity and urgency.
  • Effect on release or acceptance.

A defect that compromises a required safety function must be handled according to the applicable safety and escalation procedures, regardless of how small the software or hardware change appears.

19.2 Defect lifecycle

Test failure identified
    ↓
Record evidence and actual conditions
    ↓
Classify severity and impact
    ↓
Investigate the cause
    ↓
Implement an approved correction
    ↓
Retest the failed function
    ↓
Perform affected regression tests
    ↓
Verify acceptance criteria
    ↓
Close the defect with evidence

19.3 Failure investigation

Record:

  • Test case and requirement ID.
  • Expected and actual results.
  • Time and conditions of failure.
  • Software and hardware revision.
  • Relevant alarms or diagnostic information.
  • Reproduction steps.
  • Suspected and confirmed causes.
  • Corrective action.
  • Retest and regression results.

Where a failure indicates a broader design problem, update the risk assessment, test plan, and other affected documentation.

20. Test Evidence and Traceability

Test evidence demonstrates what was tested, under which conditions, and what the result was.

20.1 Useful evidence

  • Signed test sheets.
  • Measured values and instrument identification.
  • Approved test logs.
  • Software revision records.
  • Configuration comparisons.
  • Alarm and event records.
  • Photographs of installation details where appropriate.
  • Calibration certificates.
  • Functional test results.
  • Defect records and closure evidence.
  • Required validation reports.

Screenshots can support a test record, but they may not prove the underlying behavior or measurement accuracy on their own.

20.2 Requirements traceability

Maintain a link between each requirement and the evidence demonstrating its satisfaction.

Requirement
    ↓
Design element
    ↓
Test case
    ↓
Observed result
    ↓
Defect and corrective action, if applicable
    ↓
Acceptance decision

Traceability helps identify requirements that were never tested and tests that do not clearly support any defined requirement.

21. Risk-Based Test Coverage

Not every function requires identical testing effort. Testing should be prioritized according to consequences, complexity, change impact, and the reliability of existing evidence.

21.1 High-priority areas

  • Safety-related functions.
  • Critical quality measurements.
  • Machine motion and stopping behavior.
  • Changes affecting shared PLC logic.
  • High-energy equipment.
  • Communication dependencies that affect control.
  • Fault recovery and restart.
  • Functions with repeated failures.
  • New or unproven technologies.
  • Changes with limited rollback options.

21.2 Coverage considerations

Test coverage can be evaluated by examining:

  • Requirements tested.
  • Functions exercised.
  • Operating modes covered.
  • Fault conditions considered.
  • Interfaces verified.
  • Relevant boundary conditions tested.
  • Regression scope completed.

A high percentage of executed test cases does not necessarily mean high test quality. Ten tests of the same normal sequence do not compensate for never testing a critical fault condition.

22. Testing After Maintenance and Breakdown Repairs

After repair, testing should demonstrate that the equipment has been restored to its required condition.

22.1 Example: Replacing a VFD

The test plan may include:

  1. Verify the replacement model and installation.
  2. Confirm wiring, protective earthing, and relevant electrical checks.
  3. Load or verify the approved parameter set.
  4. Check motor identification and configuration.
  5. Verify direction of rotation under approved conditions.
  6. Check relevant operating speed and load behavior.
  7. Verify alarms, interlocks, and fault response.
  8. Test integration with the PLC and HMI.
  9. Confirm affected machine functions.
  10. Record results and authorize return to service.

The exact tests depend on the equipment, repair scope, and applicable procedures.

22.2 Example: Replacing a PLC input module

  • Verify the module model and compatibility.
  • Confirm slot configuration and hardware recognition.
  • Verify field wiring and channel mapping.
  • Test each affected input.
  • Check diagnostics and fault indication.
  • Verify related PLC logic.
  • Test affected machine sequences.
  • Confirm that the correct approved project is installed.
  • Update the maintenance record if required.

Replacing hardware does not automatically prove that the complete function has been restored.

23. Testing and Release After Machine Modifications

Testing is a major part of Management of Change (MOC), but it does not independently authorize every change.

23.1 Required sequence

  • Confirm the approved modification scope.
  • Verify that the installed work matches the design.
  • Confirm that required inspections are complete.
  • Execute the approved test plan.
  • Resolve or formally disposition defects according to the applicable rules.
  • Complete regression testing.
  • Verify performance and quality criteria.
  • Complete safety validation where required.
  • Update drawings, programs, parameters, and procedures.
  • Obtain the required technical and operational approvals.

23.2 Release decision

The release decision should consider:

  • Whether mandatory requirements are satisfied.
  • Whether acceptance criteria have been met.
  • Whether unresolved defects affect safety, quality, or intended operation.
  • Whether the machine can be maintained and recovered.
  • Whether required documentation and training are complete.
  • Whether residual risks are controlled and accepted by the appropriate authority.

Do not conceal a failed test by changing the acceptance criterion after execution unless a formal engineering review establishes and approves a legitimate revised requirement.

24. Practical Example: PLC Modification on an Engine Test-Bed

Scenario: A PLC program is modified to add a pressure validation step before a test cycle begins.

Requirements

  • The pressure measurement must be valid.
  • The pressure must fall within the approved operating window.
  • The test cycle must not proceed if required conditions are absent.
  • The HMI must indicate the relevant fault.
  • The system must recover according to the approved procedure.

Test cases

Test Input condition Expected result
TC-01 Valid pressure and all required permissives Cycle start is permitted
TC-02 Pressure below the approved window Cycle start is inhibited
TC-03 Pressure above the approved window Cycle start is inhibited and the defined fault response occurs
TC-04 Required pressure signal unavailable System detects the invalid condition and follows the specified response
TC-05 Pressure becomes invalid during the relevant phase Behavior matches the approved functional specification
TC-06 Fault condition clears Recovery follows the defined reset and restart logic
TC-07 Existing test sequence is executed Existing functions continue to meet their requirements

The precise response during an active cycle must be defined by the machine's design and safety requirements. It should not be improvised during testing.

Evidence to record

  • PLC project revision.
  • Test case results.
  • Actual pressure values.
  • Instrument identification where required.
  • Relevant alarms and timestamps.
  • Defects and corrective actions.
  • Regression test results.
  • Required approval and release status.

25. Practical Example: Node-RED, SQL Server, and Grafana Testing

Scenario: A local data acquisition system reads PLC tags, stores values in SQL Server, and displays them in Grafana.

Test layers

PLC data acquisition

  • Verify the selected PLC tags.
  • Confirm data types, values, and units.
  • Check update rate.
  • Confirm behavior when communication is lost.

Node-RED

  • Verify the flow configuration.
  • Check handling of invalid, missing, or stale values.
  • Confirm error logging and reconnection behavior.
  • Ensure unexpected input does not cause unintended write operations.

SQL Server

  • Verify table mapping and field types.
  • Confirm timestamp behavior.
  • Check duplicate and missing records.
  • Verify database permissions.
  • Confirm the defined behavior when the database is unavailable.

Grafana

  • Verify query logic.
  • Check displayed values and units.
  • Confirm time ranges and timestamps.
  • Verify that missing data is not misleadingly displayed as valid zero values.
  • Confirm user access permissions.

Integration testing

Compare the same known value at the source and at each downstream stage:

PLC tag
    ↓
Node-RED received value
    ↓
SQL Server stored record
    ↓
Grafana displayed value

The values should agree within the defined data-handling and measurement requirements. Differences may arise from scaling, conversion, timestamps, sampling, or query logic.

Also test loss of communication, database downtime, and recovery. Monitoring failures should be visible and handled according to the intended design without creating an unintended dependency on the production control system.

26. Testing Checklist

Preparation

  • Requirements and scope are defined.
  • Acceptance criteria are measurable.
  • Relevant risks and safety precautions are reviewed.
  • Correct hardware, software, and configuration revisions are identified.
  • Test procedures and cases are approved where required.
  • Test equipment is suitable and in calibration where required.
  • The test environment is ready.
  • Personnel and responsibilities are defined.

Execution

  • Installation and prerequisite checks are complete.
  • Actual results are recorded.
  • Positive and negative tests are performed as applicable.
  • Boundary conditions are tested where required.
  • Relevant fault and recovery behavior is verified.
  • Safety-related tests follow the approved procedure.
  • Defects are recorded and classified.
  • Unexpected behavior is investigated.

Completion

  • Failed tests are resolved or formally dispositioned.
  • Retesting is complete.
  • Regression testing is complete.
  • Acceptance criteria are satisfied.
  • Required validation evidence is available.
  • Software and configuration records are updated.
  • Test reports are complete.
  • Required approvals are obtained.
  • Release and monitoring arrangements are defined.

27. Interview Questions and Answers

Q1. What is the difference between testing and commissioning?

Testing evaluates specified functions and requirements. Commissioning establishes that the installed system is correctly configured, integrated, and ready for its intended operation. Testing is usually one part of commissioning.

Q2. What is the difference between FAT and SAT?

FAT checks the prepared system at the supplier or integration facility. SAT checks the installed system in its actual site environment, including real interfaces and site-specific conditions.

Q3. What is regression testing?

Regression testing verifies that existing functions continue to work after a modification, repair, or software update.

Q4. What is the difference between positive and negative testing?

Positive testing verifies expected operation under valid conditions. Negative testing checks the system's behavior when inputs, communications, or operating conditions are invalid or abnormal.

Q5. Why are acceptance criteria defined before testing?

They provide an objective basis for pass/fail decisions, prevent arbitrary judgments, and ensure that the required performance is known before results are observed.

Q6. What is test traceability?

It is the ability to link requirements to test cases, results, defects, corrective actions, and acceptance decisions.

Q7. Why can a PLC input test pass while the machine function still fails?

The physical input may work while the PLC mapping, logic, sequence timing, HMI indication, or downstream interface is incorrect. Integration and system testing are needed to verify the complete function.

Q8. Is calibration sufficient to validate a pressure measurement system?

No. Calibration evaluates the instrument against a suitable reference. Complete system verification may also require checks of wiring, input configuration, scaling, displayed units, alarm logic, and measurement performance.

Q9. What should happen when a test fails?

Record the actual result and evidence, assess the impact, investigate the cause, implement an approved correction, retest the affected function, perform appropriate regression tests, and document closure.

Q10. Why is a successful normal cycle insufficient?

It does not demonstrate correct behavior under faults, invalid inputs, communication loss, boundary conditions, or recovery scenarios. The required test scope must cover relevant normal and abnormal conditions.

Q11. What is the purpose of test evidence?

Evidence demonstrates what was tested, the conditions and configuration used, the observed result, and whether the acceptance criteria were met.

Q12. Who should authorize release after testing?

The person or role designated by the organization's change-control, quality, safety, and operational procedures. Technical test completion does not automatically replace required release authorization.

28. Key Principles to Remember

  • Define the requirements before designing the tests.
  • Make acceptance criteria measurable and unambiguous.
  • Test individual components, interfaces, and the complete system.
  • Include abnormal conditions and recovery behavior.
  • Perform regression testing after changes.
  • Use suitable and verified measurement equipment.
  • Distinguish calibration, testing, verification, and validation.
  • Record actual results rather than relying on memory.
  • Investigate failures instead of repeatedly attempting a pass.
  • Treat safety-related testing and validation with the required engineering rigor.
  • Keep software and configuration revisions traceable.
  • Release equipment only when required acceptance conditions and approvals are satisfied.

Testing converts engineering requirements into evidence. The real objective is not to produce a stack of completed checkboxes, but to establish that the machine behaves correctly under the conditions that matter.
