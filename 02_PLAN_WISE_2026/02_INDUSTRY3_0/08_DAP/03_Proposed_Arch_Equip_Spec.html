1. Purpose and scope

Proposed automation architecture and equipment specification define how an existing machine or production system should be modified, upgraded, or automated and what hardware, software, interfaces, and supporting infrastructure are required to implement that solution.

In a Detailed Automation Proposal (DAP), this topic converts the requirements and existing-machine study into a technically defined, implementable solution.

The proposed architecture answers:

  • What system components will be used?
  • How will those components communicate?
  • Where will control logic execute?
  • How will the existing machine interface with the new system?
  • How will safety, diagnostics, recovery, and maintenance be handled?
  • How will production data be collected, stored, and exchanged?
  • How can the system be expanded, repaired, and supported throughout its lifecycle?

The equipment specification answers:

  • What exact function must each component perform?
  • What electrical, mechanical, environmental, communication, and safety requirements must it satisfy?
  • How many units are required?
  • What compatibility constraints exist?
  • What documentation, software, testing, and commissioning deliverables must the supplier provide?

The architecture and specification must agree with each other. An architecture that shows a remote I/O system but specifies no compatible remote I/O hardware is incomplete. A component list containing a PLC, HMI, and network switch without explaining their responsibilities is merely a shopping list with industrial aspirations.

2. Position in the automation project lifecycle

The architecture and equipment specification are developed using the outputs of earlier DAP activities.

Input document or activity Information used
Customer requirements Production targets, functionality, acceptance criteria
Existing-machine study Existing hardware, software, interfaces, limitations
Process study Process sequence, cycle time, machine operating conditions
Functional requirements Required automatic, manual, setup, and recovery behavior
Control philosophy Control ownership, operating modes, permissives, interlocks
Sequence description State transitions, handshakes, timeout behavior
I/O estimation Digital, analog, communication, and safety signals
Hardware selection Candidate hardware families and compatibility
Network architecture Topology, protocols, addressing, segmentation
Safety concept Required safety functions and architecture constraints
Electrical design Supply voltages, protection, cabinet, wiring, earthing
Procurement information Approved makes, availability, lifecycle support, budget

The proposed solution should resolve uncertainties left by these inputs. If the existing machine's PLC program is unavailable, for example, the proposal should identify how the interface and modification risks will be controlled rather than silently assuming unrestricted access.

3. Difference between architecture, equipment specification, and BOM

Item Main purpose Typical output
Automation architecture Defines the structure and interaction of the system Architecture diagram, network diagram, interface boundaries
Equipment specification Defines the required characteristics of each component Technical specification sheets and compliance requirements
Bill of Materials (BOM) Lists the items needed to build the system Part numbers, quantities, descriptions
I/O list Defines signals and their interface requirements Tag names, addresses, types, descriptions
Interface matrix Defines exchanges between systems and ownership Source, destination, protocol, handshake, fault response
Technical justification Explains why the selected solution is appropriate Alternatives, comparison, risk and cost rationale

These documents support one another but are not interchangeable.

A BOM might say 24 V DC power supply, 10 A. The equipment specification defines the required input range, output regulation, protection, environmental suitability, diagnostics, and approved alternatives. The architecture explains which equipment receives power and how control power is separated or distributed.

4. Define the architecture before selecting every part number

Architecture decisions should be made before detailed part numbers are frozen.

The normal engineering sequence is:

  1. Confirm functional requirements and constraints.
  2. Identify existing equipment that will be retained, replaced, or modified.
  3. Define system boundaries and control ownership.
  4. Select the broad control and communication architecture.
  5. Define interfaces, safety boundaries, and failure behavior.
  6. Establish I/O, performance, availability, and environmental requirements.
  7. Select compatible equipment.
  8. Verify power, space, network, compatibility, and lifecycle constraints.
  9. Create the equipment specifications and BOM.
  10. Verify that the complete design satisfies the requirements.

A selected PLC model can influence the I/O family, programming software, network interfaces, spare parts, and vendor support requirements. Conversely, an existing servo drive or machine-builder interface can constrain the PLC family. Engineering is iterative, so the sequence may need revision when a compatibility issue is discovered.

5. Define system boundaries and responsibilities

A system boundary establishes what is included in the proposed modification and what remains outside its scope.

Typical boundaries include:

  • New automation panel.
  • Existing machine control panel.
  • PLC and remote I/O.
  • HMI and operator stations.
  • Drives, servos, robots, and CNC systems.
  • Sensors, actuators, and process instruments.
  • Safety PLC, safety relay, guards, and emergency-stop circuits.
  • Plant network, SCADA, historian, MES, or other higher-level systems.
  • Mechanical equipment and utilities.
  • Vendor-supplied and customer-supplied equipment.

For every boundary, identify ownership and responsibility.

Function Example responsibility Required clarification
Sequence control Main PLC Who owns the machine sequence?
Motion control PLC or dedicated motion controller Who commands and supervises motion?
Robot execution Robot controller Who selects the job and verifies completion?
Machine safety Safety-related control system Who designs and validates safety functions?
Operator interface HMI Which system owns each displayed status?
Production data PLC, edge device, or SCADA Which component is the authoritative data source?
Remote support Approved engineering access Who authorizes and audits access?

Avoid multiple controllers independently issuing commands to the same equipment without a clearly defined authority model. This creates conflicting commands, unpredictable recovery behavior, and the industrial equivalent of several people steering the same vehicle.

6. Select the appropriate control architecture

6.1 Centralized PLC architecture

A central PLC executes most machine logic. Field devices are connected through local I/O, with communication links to drives, HMIs, robots, or other controllers.

Sensors and actuators
        |
        v
Local I/O
        |
        v
Central PLC <----> HMI
        |
        +---------> Drives
        |
        +---------> Robot controller
        |
        +---------> CNC / machine controller
        |
        +---------> SCADA / data system

Advantages:

  • Centralized sequence logic.
  • Relatively simple troubleshooting for compact machines.
  • Clear control ownership when designed properly.
  • Straightforward commissioning for small systems.

Limitations:

  • Large wiring volume for geographically distributed devices.
  • Central controller or network failures can affect many functions.
  • Expansion may require significant cabinet and I/O modifications.
  • Large programs can become difficult to maintain without modular software architecture.

Suitable applications include compact machines, simple stations, and retrofits where a central controller is practical.

6.2 Distributed I/O architecture

A central PLC communicates with remote I/O stations positioned near machine equipment.

Field devices
     |
     v
Remote I/O station
     |
     v
Industrial Ethernet network
     |
     v
PLC
     |
     +---------> HMI
     +---------> Drives
     +---------> Other controllers

Advantages:

  • Reduced long-distance field wiring.
  • Easier modular expansion.
  • Better organization around machine zones.
  • Potentially reduced installation effort.

Limitations:

  • Remote I/O stations require appropriate power, protection, and environmental suitability.
  • Network faults can disable an entire remote station.
  • Device replacement and configuration management require discipline.
  • Network loading, update times, and fault diagnostics must be considered.

Distributed I/O does not automatically mean distributed control logic. The PLC may still execute all sequence logic centrally.

6.3 Distributed control architecture

Control logic is divided among multiple controllers, such as station PLCs, robot controllers, CNC controllers, or dedicated motion controllers.

Station PLC A <----> Station PLC B
      |                    |
      v                    v
Station A devices      Station B devices

      PLC A / PLC B
             |
             v
       Supervisory HMI
             |
             v
      SCADA / plant data

Advantages:

  • Functional separation between machine stations.
  • Local autonomy where explicitly designed.
  • Easier independent development and commissioning of modules.
  • Potentially better fault containment.

Limitations:

  • More complicated inter-controller communication.
  • Greater need for interface specifications and version control.
  • Sequence recovery across station boundaries requires careful design.
  • Fault diagnosis may require tools and knowledge from several platforms.

Distributed control should be chosen because it improves modularity, availability, maintainability, or performance, not merely because more controllers make an architecture diagram look impressive.

6.4 PC-based and hybrid architectures

Industrial PCs can provide data processing, machine vision, advanced algorithms, or supervisory applications. A hybrid design may combine PLC-based deterministic machine control with PC-based analysis and visualization.

Use a clear separation between:

  • Time-critical machine control.
  • Supervisory operations.
  • Data processing and analytics.
  • Engineering and maintenance access.
  • Business-system integration.

Do not make a production-critical control function dependent on an ordinary database, cloud connection, or general-purpose PC application unless the architecture explicitly addresses determinism, failure behavior, availability, and recovery.

7. Select architecture according to application needs

Requirement Architectural consideration
Very short response time Controller scan, I/O update, network cycle, device response
Many distributed sensors Remote I/O or suitable fieldbus devices
Multiple independent stations Modular PLCs and defined inter-station handshakes
Robot or CNC integration Supported interface, job selection, status, fault, recovery
Existing PLC must remain Compatible interface or bounded program modification
High availability Failure analysis, redundancy where justified, recovery strategy
Production traceability Reliable data acquisition, timestamps, identifiers, storage
Frequent product changes Recipe management, parameter validation, version control
Limited panel space Remote I/O, compact equipment, thermal and service-access review
Obsolete equipment Migration strategy, successor compatibility, software availability
Restricted downtime Offline preparation, backups, staged installation, rollback plan

There is no universally best architecture. A small machine can be poorly served by a complex distributed system, while a large line can become unmanageable if every function is forced into one controller and one enormous program.

8. Define the automation architecture by layers

A useful logical architecture separates equipment by function.

Level 4: Business systems
ERP / planning / enterprise reporting
             ^
             |
Level 3: Manufacturing operations
MES / production tracking / historian / SCADA
             ^
             |
Level 2: Supervisory control
HMI / station supervision / engineering diagnostics
             ^
             |
Level 1: Machine control
PLC / motion controller / robot controller / CNC
             ^
             |
Level 0: Process and field devices
Sensors / actuators / motors / valves / instruments

This is a conceptual view, not a mandatory network topology. Actual installations may combine levels or separate them further.

Safety-related functions require their own defined safety architecture and validated interfaces. They must not be treated as ordinary PLC logic merely because both systems exchange signals.

For each layer, define:

  • Responsibilities.
  • Hardware and software.
  • Communication interfaces.
  • Data ownership.
  • Performance requirements.
  • Failure behavior.
  • Cybersecurity boundaries.
  • Maintenance and engineering access.

9. Design the field-device and I/O architecture

Field devices include proximity sensors, photoelectric sensors, pressure switches, temperature sensors, encoders, solenoid valves, contactors, and process instruments.

Determine whether each signal is handled through:

  • Hardwired digital I/O.
  • Analog I/O.
  • High-speed counter or encoder interface.
  • Dedicated motion interface.
  • Industrial communication.
  • Safety-rated I/O or a safety network.
  • A controller-specific interface.

9.1 Digital inputs

Examples:

  • Part present.
  • Clamp extended.
  • Guard closed.
  • Drive ready.
  • Robot cycle complete.
  • Machine alarm active.

Specify the voltage level, electrical polarity, source/sink compatibility, isolation requirements, input filtering, diagnostic needs, and required response time.

9.2 Digital outputs

Examples:

  • Solenoid command.
  • Contactor command.
  • Indicator lamp.
  • Reset request.
  • Robot start request.

Specify the output type, load current, inductive-load suppression, switching frequency, protection, and required de-energized state.

An output command does not prove that the commanded device operated. Where required, use feedback to verify the physical result.

9.3 Analog inputs and outputs

Common industrial interfaces include:

  • 4–20 mA.
  • 0–10 V.
  • Other ranges required by the instrument or equipment.

For analog signals, specify the electrical range, engineering range, resolution, accuracy, isolation, update rate, fault detection, shielding, grounding, and scaling.

For a linear signal, the engineering value can be calculated as:

\[ PV = LRV + \frac{Raw-Raw\_{\min}}{Raw\_{\max}-Raw\_{\min}}(URV-LRV) \]

Where:

  • \(PV\) is the engineering process value.
  • \(LRV\) is the lower engineering range value.
  • \(URV\) is the upper engineering range value.
  • \(Raw\_{\min}\) and \(Raw\_{\max}\) are the raw values corresponding to the engineering range limits.

For a 4–20 mA pressure transmitter scaled from 0 to 10 bar, 12 mA corresponds to 5 bar under ideal linear scaling.

The specification must also state what happens when the signal is below or above its valid range, disconnected, unstable, or otherwise diagnosed as faulty.

10. Define the PLC specification

The PLC specification should be performance- and application-based, not limited to a preferred catalogue number.

Parameter Specification requirement
Controller capacity Program size, memory, task capacity, communication load
Processing performance Maximum acceptable scan or task execution time
I/O capacity Required local and remote I/O with justified expansion allowance
Communication Required protocols, ports, supported device connections
Motion support Axis count, synchronization, motion functions if applicable
Diagnostics Fault records, module diagnostics, online monitoring
Reliability Availability requirements and recovery expectations
Environment Operating temperature, vibration, contamination constraints
Programming Supported engineering software and version compatibility
Lifecycle Availability, support period, migration options
Security Access control, engineering permissions, approved connectivity
Documentation Program, tag list, configuration, backup, and recovery instructions

Confirm compatibility between the CPU, firmware, I/O modules, communication modules, engineering software, and any existing devices.

Also define:

  • Program organization and naming conventions.
  • Retentive data policy.
  • Startup and restart behavior.
  • Communication-loss handling.
  • Time synchronization.
  • Fault diagnostics and alarm structure.
  • Source-code delivery and access rights.
  • Backup and restoration procedure.

Do not specify only the PLC CPU and assume everything else will somehow align. Firmware and engineering-tool compatibility can turn an apparently correct hardware selection into an expensive commissioning problem.

11. Define HMI and operator-interface equipment

The HMI specification should include:

  • Screen size and resolution.
  • Touchscreen or physical-key requirements.
  • Mounting arrangement and environmental protection.
  • Communication with the PLC and other controllers.
  • Number of screens, alarms, trends, recipes, and diagnostics.
  • User roles and access permissions.
  • Language requirements.
  • Historical data requirements, if applicable.
  • Backup, restoration, and project-file delivery.
  • Software licensing and compatibility.
  • Display behavior during communication loss.

Specify functional screens rather than simply requesting a particular display size.

Typical screens include:

  • Machine overview.
  • Manual operation.
  • Automatic cycle.
  • I/O diagnostics.
  • Alarm history.
  • Drive and actuator diagnostics.
  • Recipe and parameter management.
  • Maintenance information.
  • Production counts and cycle-time information.

Commands that can create hazardous movement must be protected by the machine's control and safety design. Hiding a button on an HMI is not a safety function.

12. Specify drives, servo systems, robots, and CNC interfaces

12.1 Variable-frequency drives

Specify:

  • Motor rating and operating duty.
  • Supply voltage and frequency.
  • Required overload capability.
  • Control mode and speed range.
  • Braking requirements.
  • Encoder or feedback requirements, if applicable.
  • Communication protocol.
  • Safe torque off or other safety functions where required.
  • Environmental conditions and cooling.
  • Parameter backup and recovery.
  • Fault diagnostics and replacement procedure.

Verify motor compatibility, cable requirements, electromagnetic compatibility, protective-device coordination, and the manufacturer's installation recommendations.

12.2 Servo systems

Specify:

  • Axis type and mechanical load.
  • Required travel, speed, acceleration, and positioning accuracy.
  • Motor and drive ratings.
  • Encoder and feedback requirements.
  • Homing and reference behavior.
  • Positioning interface and communication cycle.
  • Braking and power-loss behavior.
  • Required safety functions.
  • Tuning and commissioning deliverables.

The drive's nominal rating alone does not establish that the complete axis can meet the required positioning performance.

12.3 Robot controller interface

Define:

  • Robot controller ownership and operating modes.
  • Robot ready, busy, fault, and cycle-complete status.
  • Program or job selection.
  • Start request and acknowledgement.
  • Part data and position exchange, if applicable.
  • Fault reset authorization.
  • Zone, fixture, and machine interlocks.
  • Safety interface and responsibility boundaries.
  • Timeout and recovery behavior.

Use a documented handshake with clear signal definitions, expected transitions, and fault handling. A single Robot_Start bit is not an integration design.

12.4 CNC or machine-tool interface

Define:

  • PLC-to-CNC or PMC-to-PLC signals.
  • Machine ready, cycle active, alarm, and cycle complete.
  • M-code or auxiliary-function handshakes.
  • Tool, program, and recipe information exchanges.
  • Permissives and interlocks.
  • Fault recovery and reset authority.
  • Communication method and supported interface.

The selected interface must be verified against the actual CNC control model, machine-builder implementation, and available documentation.

13. Define industrial network architecture

The network design must specify physical connections, logical segmentation, protocols, addressing, diagnostics, and recovery.

PLC -------- Industrial switch -------- Remote I/O
 |                    |
 |                    +--------------- HMI
 |
 +------------------------------------ Drive network
 |
 +------------------------------------ Robot / CNC interface
 |
 +---- Controlled boundary ---- SCADA / plant systems

The diagram is illustrative. A real design must show the actual ports, network segments, connection types, and any required separation between traffic classes.

13.1 Network design parameters

Specify:

  • Ethernet or fieldbus technology.
  • Supported application protocols.
  • Switch port count and media type.
  • Cable type and maximum applicable segment length.
  • Required bandwidth and update time.
  • IP addressing and naming convention.
  • VLANs and routing boundaries where applicable.
  • Ring or redundant topology, if justified.
  • Time synchronization.
  • Device discovery and diagnostics.
  • Access restrictions and approved remote access.
  • Network configuration backup.
  • Spare ports and expansion provisions.

13.2 Communication protocol selection

Protocol or interface Typical application Key consideration
PROFINET PLC, remote I/O, drives Device compatibility, update time, topology
EtherNet/IP PLC, I/O, drives, devices Connection capacity, RPI, compatibility
Modbus TCP Instruments, gateways, controllers Register mapping, data types, error handling
OPC UA Structured industrial data exchange Certificates, authentication, access control
Serial communication Legacy devices and instruments Baud rate, parity, wiring, timeout behavior
Vendor-specific protocol Specialized equipment integration Software support, licensing, documentation

Do not choose a protocol only because a device advertises support for it. Confirm the exact functions exposed, data types, timing, diagnostics, licensing, and supported operating modes.

14. Define data architecture and traceability

For systems requiring production monitoring, specify where data originates, how it is validated, and which system owns it.

Possible data include:

  • Machine state.
  • Cycle start and completion timestamps.
  • Part or batch identification.
  • Recipe and program number.
  • Production count.
  • Reject count.
  • Alarm and fault codes.
  • Cycle duration.
  • Quality measurement results.
  • Operator or shift identifiers, where authorized.

A typical data path is:

Machine sensors and controller tags
                |
                v
PLC / machine controller
                |
                v
Industrial data interface
                |
                v
Edge gateway / SCADA
                |
                v
Historian / SQL database
                |
                v
Dashboards / reports / MES

The architecture should define:

  • Tag names and data types.
  • Sampling or event-triggering strategy.
  • Timestamp source and time synchronization.
  • Data quality and invalid-value handling.
  • Buffering during network or server outages.
  • Store-and-forward behavior, if required.
  • Duplicate-event prevention.
  • Data retention and access permissions.
  • Database and network ownership.
  • Recovery after communication is restored.

A dashboard is not a substitute for a reliable data acquisition design. If the source data is missing, delayed, duplicated, or incorrectly timestamped, attractive graphs simply display the problem with better graphics.

15. Define safety architecture separately

Safety requirements must originate from the machine risk assessment and applicable standards, not from a convenient PLC model or an assumed standard wiring practice.

Possible components include:

  • Safety relays.
  • Safety PLCs.
  • Safety-rated remote I/O.
  • Guard switches and interlocks.
  • Emergency-stop devices.
  • Light curtains and scanners.
  • Safety-rated drive functions.
  • Safety communication networks.

The specification should identify:

  • Required safety functions.
  • Required Performance Level (PLr) or Safety Integrity Level (SIL), as applicable.
  • Safety input and output requirements.
  • Required response and stopping behavior.
  • Reset and restart conditions.
  • Fault detection and diagnostics.
  • Required validation and evidence.
  • Boundaries between safety systems and standard control.

PLr and SIL are not interchangeable labels. The applicable risk assessment and standards determine which method is appropriate.

Standard PLC logic may coordinate production behavior, but it must not be treated as a replacement for a required safety function. Safety validation must verify the complete implemented function, including sensors, logic, final switching elements, drive behavior, and reset behavior.

16. Specify electrical panels and power distribution

Equipment selection must be consistent with the electrical design.

Consider:

  • Incoming supply voltage, frequency, and fault level.
  • Control voltage and power-supply capacity.
  • PLC, I/O, network, HMI, sensor, and actuator loads.
  • Drive and motor power requirements.
  • Protective devices and short-circuit coordination.
  • Terminal blocks and wiring capacity.
  • Earthing and bonding.
  • Shielding and electromagnetic compatibility.
  • Panel ventilation or cooling.
  • Heat dissipation and cabinet temperature.
  • Cable entry and segregation.
  • IP rating and environmental exposure.
  • Maintenance clearance and component replacement access.
  • Spare terminals, ports, and mounting space.

A basic power budget is:

\[ P\_{\text{total}} = \sum\_{i=1}^{n} P_i \]

For a DC supply, estimate the load current using the specified device currents:

\[ I\_{\text{total}} = \sum\_{i=1}^{n} I_i \]

The selected supply must account for actual operating conditions, simultaneous loads, transient requirements, manufacturer derating, expansion needs, and the required reliability margin. Do not apply an arbitrary percentage without checking the plant standard and equipment data.

For drive installations, separately consider motor power, drive losses, braking energy, cable routing, and applicable protection requirements. Control-power sizing is not the same calculation as motor-power sizing.

17. Specify sensors, actuators, and field accessories

17.1 Sensors

Define:

  • Sensing principle.
  • Detection range and target material.
  • Output type and supply voltage.
  • Switching frequency or response time.
  • Repeatability and accuracy where relevant.
  • Mounting arrangement and sensing direction.
  • Environmental rating.
  • Connector and cable requirements.
  • Diagnostic capability.
  • Compatibility with the input module.

For example, selecting a proximity sensor requires more than specifying its sensing distance. Target material, mounting clearance, switching frequency, ambient conditions, output polarity, and cable arrangement can all affect suitability.

17.2 Actuators and solenoid valves

Define:

  • Supply voltage or pneumatic/hydraulic requirements.
  • Required force, torque, flow, or operating speed.
  • Duty cycle.
  • Position feedback.
  • Normal and failure state.
  • Manual override requirements.
  • Environmental suitability.
  • Connector and interface type.
  • Required isolation and protection.

The failure state must be considered in relation to process hazards. Do not assume that de-energized always means safe.

17.3 Cables and connectors

Specify cable type, conductor size, shielding, length, connector type, bend radius, drag-chain suitability, temperature rating, and segregation requirements.

For analog, encoder, communication, and drive cables, follow the relevant manufacturer's routing and shielding recommendations. Improvised shield termination and shared routing with noisy power conductors can cause intermittent faults that are difficult to reproduce.

18. Select industrial switches, gateways, and edge computers

For industrial network equipment, define:

  • Port count and port speeds.
  • Copper or fiber interfaces.
  • Environmental rating.
  • Operating temperature.
  • Power supply and redundancy requirements.
  • Managed-switch features.
  • VLAN, diagnostics, and security functions.
  • Ring or redundancy protocol support where required.
  • Configuration backup and replacement method.
  • Firmware support and lifecycle availability.

For gateways or industrial PCs, also define:

  • Processor and memory capacity.
  • Storage type and capacity.
  • Required operating system.
  • Application software and licensing.
  • Supported interfaces and drivers.
  • Time synchronization.
  • Backup and recovery.
  • Cybersecurity controls.
  • Data buffering requirements.
  • Vendor support and patching policy.

Avoid using an unmanaged office switch in a critical industrial network without confirming that its capabilities and environmental characteristics satisfy the application.

19. Equipment specification format

A standard equipment specification should be consistent across all components.

Field Required content
Tag or item number Unique identifier
Equipment description Function and application
Quantity Required number of units
Technical requirements Performance, electrical, mechanical, communication characteristics
Environment Temperature, humidity, vibration, contamination, IP requirements
Interfaces Electrical, mechanical, network, software
Compatibility Existing system and selected platform requirements
Safety Required safety-related properties, if applicable
Diagnostics Fault indication, status reporting, maintenance access
Lifecycle Availability, support, migration options
Documentation Datasheets, manuals, drawings, certificates
Software deliverables Project files, configuration, licenses, versions
Testing FAT, SAT, commissioning and acceptance requirements
Spares Recommended critical spares and replacement approach
Deviations Permitted exceptions and approval process

Specifications should distinguish mandatory requirements from preferences. For example, a particular communication protocol may be mandatory because the existing PLC supports only that interface, while the manufacturer's brand may remain open if equivalent compatibility and performance can be demonstrated.

20. Example equipment specification: PLC retrofit

Assume an existing machine needs a PLC retrofit while retaining its sensors, actuators, drive, and operator interface where feasible.

The example below is illustrative. Actual quantities and ratings must come from the machine survey and calculations.

Item Example requirement Verification method
PLC CPU Supports required program, tasks, communications, and diagnostics Capacity review and configuration check
Digital input modules Match field voltage and input type I/O compatibility review
Digital output modules Match load type, current, and protection needs Load calculation and datasheet review
Analog modules Support actual transmitter signal ranges Signal-range and scaling check
Network interface Supports required protocol and device connections Compatibility test
Engineering software Compatible with selected CPU firmware Project creation and download test
HMI Provides required screens, alarms, and access control Functional test
Power supply Supports calculated load and transient requirements Power budget and load verification
Network switch Meets port, topology, and environmental requirements Network design review
Enclosure Meets electrical, thermal, and environmental requirements Panel design review
Documentation Includes source program, I/O list, drawings, and backup Deliverable checklist

The specification must also identify whether the original program will be migrated, rewritten, or interfaced through a defined boundary. These are different engineering strategies with different risks and commissioning requirements.

21. I/O estimation and spare-capacity planning

Equipment sizing must use a verified I/O list rather than an approximate count of sensors seen during a quick machine walkdown.

For each signal, record:

  • Tag and description.
  • Source and destination.
  • Signal type.
  • Electrical range or protocol.
  • Normal state and fault interpretation.
  • Required response time.
  • Safety classification, where applicable.
  • Cable and terminal information.
  • Diagnostic and feedback requirements.

For a simple preliminary estimate:

\[ N\_{\text{DI}} = \sum \text{required digital input points} \]
\[ N\_{\text{DO}} = \sum \text{required digital output points} \]

Analog and specialized interfaces should be counted separately. Module selection must then consider channel grouping, isolation, channel type, terminal requirements, and compatibility.

Spare capacity should be established according to project scope, expansion expectations, plant standards, and the cost of future modifications. There is no universal spare percentage suitable for every machine.

Physical spare terminals, spare module channels, spare communication ports, and spare CPU capacity are different things. A design can have spare I/O channels but still lack cabinet space or network capacity for expansion.

22. Interface specification and ownership

Each interface should be defined between a source system and a destination system.

Interface Information exchanged Required definition
PLC to drive Run command, speed reference, reset request Command authority, scaling, fault handling
Drive to PLC Ready, running, fault, actual speed Status definitions, update rate, invalid data
PLC to robot Start request, program number, part data Handshake, job validation, timeout
Robot to PLC Ready, busy, complete, fault Signal ownership, completion criteria
PLC to CNC Cycle request, auxiliary function Supported interface, acknowledgement
CNC to PLC Ready, cycle state, alarm Signal mapping and recovery
PLC to HMI Machine state, alarms, parameters Tag ownership, access permissions
PLC to SCADA Production state and counters Data model, sampling, timestamps
Safety system to standard PLC Safety status information Defined monitoring role and limitations

For each interface, record the communication method, signal list, data types, update timing, error behavior, ownership, and acceptance test.

Where a handshake is required, define what happens if the receiver does not acknowledge, the request remains active, communication is interrupted, or a controller restarts mid-cycle.

23. Design for faults and recovery

The architecture must define how the machine behaves when equipment or communication fails.

Typical cases include:

  • PLC stops executing.
  • Remote I/O becomes unavailable.
  • Network switch or cable fails.
  • Drive faults or loses communication.
  • Robot fails to acknowledge a request.
  • CNC reports an alarm.
  • HMI loses communication.
  • Data server or historian becomes unavailable.
  • Power is interrupted and restored.
  • A replacement component has different firmware or configuration.

For each failure, specify:

  1. How the failure is detected.
  2. Which controller or device reports it.
  3. Whether the machine stops, holds, or continues in a defined degraded mode.
  4. Which commands are inhibited.
  5. What the operator sees.
  6. Whether automatic restart is permitted.
  7. What conditions are required for reset and recovery.
  8. How data loss or incomplete production records are handled.
  9. How maintenance personnel restore the system.

The correct response depends on the process and risk assessment. Automatic recovery should not be assumed safe merely because it reduces downtime.

24. Cybersecurity and access architecture

Industrial automation equipment must be specified with the plant's OT cybersecurity requirements in mind.

Consider:

  • Separation between control networks and enterprise networks.
  • Controlled routing and firewall rules.
  • Approved remote-access methods.
  • User accounts and role-based permissions.
  • Restrictions on engineering workstations.
  • Firmware and software update policy.
  • Malware protection appropriate to the system.
  • Backup protection and recovery testing.
  • Configuration and change logs.
  • Time synchronization.
  • Vendor access control and session logging.
  • Secure protocols and certificate management where supported.

Cloud connectivity is not automatically required for a SCADA or data collection project. The design should meet the actual operational objective while respecting plant policy and data restrictions.

Do not expose PLCs, HMIs, or engineering interfaces directly to the public internet. Remote support should use approved, controlled access mechanisms.

25. Lifecycle, obsolescence, and maintainability

An equipment choice should consider the entire useful life of the machine, not only purchase price.

Evaluate:

  • Product availability and expected support.
  • Firmware and software compatibility.
  • Replacement part lead time.
  • Local service capability.
  • Technician familiarity.
  • Required licenses and engineering tools.
  • Backup and restore capability.
  • Successor model compatibility.
  • Migration effort.
  • Spare-parts strategy.
  • Vendor dependency.
  • Documentation quality.

For existing equipment, identify whether it will be retained, repaired, replaced, or isolated behind an interface. Retaining an obsolete controller can reduce initial cost but increase long-term recovery risk. Replacing every existing component can simplify standardization but increase commissioning time, cost, and production risk.

A migration plan should explicitly state how the original system can be restored if the retrofit fails, where practical and safe.

26. Vendor-neutral versus brand-specific specifications

A technical specification can be written in either a performance-based or a brand-specific form.

A performance-based specification describes the required functions and characteristics while permitting equivalent solutions.

A brand-specific specification names a manufacturer or model where there is a justified compatibility, standardization, lifecycle, or support reason.

Use brand-specific requirements only when the reason is documented, such as:

  • Compatibility with installed hardware and software.
  • Approved plant standard.
  • Required integration with an existing controller.
  • Mandatory service or lifecycle arrangement.
  • Proven technical constraint.

If equivalents are permitted, define how equivalence will be evaluated. Similar catalogue descriptions do not prove equal performance, firmware compatibility, communication behavior, or engineering-tool support.

27. Compliance and deviation management

A compliance matrix allows supplier proposals to be compared against the same requirements.

Requirement ID Requirement Supplier response Evidence Status
PLC-001 Supports required communication protocol Compliant or deviation Datasheet and compatibility evidence Open until verified
IO-001 Supports required input signal type Compliant or deviation Module specification Open until verified
NET-001 Meets required network topology Compliant or deviation Network proposal Open until verified
SAF-001 Meets specified safety requirements Compliant or deviation Safety documentation Open until validated
DOC-001 Provides editable project files Compliant or deviation Deliverable commitment Open until received

Typical response categories include compliant, partially compliant, non-compliant, and clarification required.

A supplier deviation should state the affected requirement, technical difference, operational impact, cost impact, and required approval. Silence should not be treated as evidence of compliance.

28. Verification of the proposed architecture

Before releasing the DAP, verify the proposed design against the requirements.

Functional verification

  • Every required machine function has an identified implementation.
  • Manual, automatic, setup, and recovery modes are addressed.
  • Control ownership is unambiguous.
  • All inter-machine handshakes are defined.
  • Timeout and communication-loss behavior is documented.

Hardware verification

  • PLC, I/O, HMI, drives, and other devices are compatible.
  • I/O quantities and signal types match the I/O list.
  • Power-supply sizing and electrical protection are checked.
  • Panel space, thermal performance, and access are acceptable.
  • Network ports, bandwidth, and topology are sufficient.
  • Environmental ratings match the installation location.

Safety and cybersecurity verification

  • Safety functions are derived from the risk assessment.
  • Safety architecture and standard-control interfaces are defined.
  • Required safety validation is included.
  • Network boundaries and remote-access controls are documented.
  • User access and configuration backup requirements are defined.

Lifecycle and delivery verification

  • Equipment availability and support are reviewed.
  • Obsolescence and migration risks are identified.
  • Critical spares and replacement procedures are considered.
  • Software, firmware, and licenses are identified.
  • Editable programs and configuration backups are included.
  • FAT, SAT, commissioning, and acceptance criteria are defined.
  • Supplier deviations are recorded and approved.

29. FAT, SAT, and commissioning implications

The equipment specification should make it possible to prove that the delivered system meets its requirements.

Factory Acceptance Test (FAT) typically verifies equipment and software before installation. Depending on project scope, it may include:

  • Hardware and configuration verification.
  • I/O simulation.
  • Sequence testing.
  • Alarm and diagnostic testing.
  • Communication and handshake testing.
  • Recipe and parameter validation.
  • Recovery and restart testing.
  • Backup and restoration checks.
  • Documentation review.

Site Acceptance Test (SAT) verifies the installed system under site conditions. It may include:

  • Actual field I/O checks.
  • Wiring and polarity verification.
  • Device communication checks.
  • Safety validation and required functional tests.
  • Inter-machine integration.
  • Cycle-time and process-performance checks.
  • Production trial and quality validation.
  • Fault recovery.
  • Operator and maintenance handover.

The exact scope depends on the contract, process, and risk. A successful simulated FAT does not establish that field wiring, mechanical interfaces, or the complete installed safety system are correct.

30. Common architecture and specification mistakes

Mistake Consequence Prevention
Selecting hardware before defining interfaces Compatibility problems Freeze interface requirements before final selection
Copying an old BOM without verification Wrong or obsolete components Validate part numbers, lifecycle, and actual machine needs
Ignoring existing program ownership Integration delays Confirm source access, permissions, and modification strategy
Treating network connectivity as full integration Missing status and recovery logic Define data and handshake semantics
Specifying only nominal component ratings Unsuitable performance under real conditions Check duty, load, environment, and transient conditions
Ignoring firmware and software versions Commissioning and compatibility failures Record and verify version compatibility
Omitting failure behavior Uncontrolled stops or difficult recovery Define failure modes and expected responses
Treating HMI restrictions as safety Unsafe assumptions Use the validated safety architecture
Ignoring backup and restoration Extended downtime after failure Require tested recovery deliverables
Overengineering a small application Unnecessary cost and complexity Justify each architectural feature
Underengineering a large system Poor modularity and maintainability Define modules, boundaries, and communication ownership
Omitting supplier deviations Hidden technical and commercial risk Use a controlled compliance matrix

31. Practical retrofit example

Consider an existing automated station that uses a PLC, HMI, VFD, sensors, and pneumatic actuators. The objective is to improve diagnostics, retain suitable existing equipment, and transfer production data to a plant monitoring system.

A possible proposed architecture is:

Sensors / actuators
        |
        v
Existing field wiring
        |
        v
PLC with verified I/O
        |
        +---------> Existing VFD
        |
        +---------> Existing HMI
        |
        +---------> Industrial Ethernet switch
                           |
                           v
                    Edge data interface
                           |
                           v
                    Plant SCADA / historian

Before approving this architecture, verify:

  1. Whether the existing PLC supports the required communication protocol.
  2. Whether the PLC has adequate memory, communication capacity, and spare interfaces.
  3. Whether the HMI and VFD can be retained with the selected firmware and protocol.
  4. Whether the new network connection can be added without violating plant network rules.
  5. Whether the data interface can read the required tags without interfering with machine control.
  6. Whether data acquisition continues safely when the SCADA server is unavailable.
  7. Whether the existing program can be backed up and restored.
  8. Whether additional diagnostics require changes to PLC logic, HMI screens, or field wiring.
  9. Whether a maintenance bypass or commissioning mode introduces additional safety risks.
  10. Whether the FAT and SAT prove both machine functionality and data integrity.

The equipment specification would then define the exact controller interface, switch, gateway, cables, software, licenses, and deliverables based on the verified site conditions. It should not assume that all existing hardware can be reused simply because it is currently operational.

32. Architecture and equipment deliverables

A complete DAP package for this topic may include:

  • Proposed automation architecture diagram.
  • Control and communication topology.
  • System boundary and responsibility definition.
  • Equipment specification sheets.
  • Preliminary or detailed BOM, depending on design maturity.
  • I/O capacity and signal-type summary.
  • PLC, HMI, drive, robot, and CNC interface definitions.
  • Network addressing and protocol requirements.
  • Electrical power and panel requirements.
  • Safety architecture and interface definition.
  • Data collection and traceability design.
  • Equipment lifecycle and spare-parts considerations.
  • Compliance and deviation matrix.
  • FAT, SAT, commissioning, and acceptance requirements.
  • Risk register and unresolved assumptions.
  • Software, configuration, backup, and handover deliverables.

The level of detail should match the DAP's purpose. A preliminary proposal may define functional specifications and candidate equipment families, while a detailed engineering package may require exact part numbers, wiring interfaces, addresses, and verified configurations.

33. Interview questions and answers

1. What is the difference between automation architecture and equipment specification?

Architecture defines the system structure, responsibilities, interfaces, communication, and behavior. Equipment specification defines the technical characteristics and acceptance requirements of the components used to implement that structure.

2. Why should architecture be defined before final equipment selection?

Because architecture establishes controller responsibilities, interface requirements, network needs, performance constraints, and safety boundaries. Hardware selected without these constraints may be incompatible or unnecessarily expensive.

3. When would you choose remote I/O instead of local I/O?

Remote I/O is useful when field devices are distributed across a large machine or line, reducing long-distance wiring and supporting modular expansion. The decision must also consider network reliability, environment, diagnostics, and installation cost.

4. What must be checked before replacing an existing PLC?

I/O compatibility, program access, sequence behavior, communication protocols, HMI and drive integration, safety interfaces, firmware and software compatibility, downtime, backups, testing, and rollback feasibility.

5. Why is a BOM not a complete equipment specification?

A BOM identifies items and quantities but may not define their required performance, compatibility, environmental suitability, safety properties, documentation, testing, or acceptance criteria.

6. How do you prevent integration problems between a PLC and a robot?

Define signal ownership, program selection, start and acknowledgement handshakes, busy and complete states, fault behavior, timeouts, communication loss, safety interfaces, and recovery conditions. Verify them during integration testing.

7. How should you choose a communication protocol?

Evaluate compatibility, required data, timing, diagnostics, network topology, cybersecurity, device support, lifecycle, engineering effort, and plant standards.

8. Why must safety architecture be treated separately from standard PLC control?

Safety functions require risk-based design and appropriate safety-related components, implementation, and validation. Standard PLC logic is not automatically suitable for safety functions.

9. What is the difference between FAT and SAT?

FAT verifies the system before installation, often using simulation and controlled test conditions. SAT verifies the installed system at the site, including real field devices, wiring, mechanical interfaces, integration, and site-specific performance.

10. How do you justify a brand-specific requirement?

Document the technical reason, such as existing-system compatibility, approved plant standards, required service support, or lifecycle constraints. If equivalent equipment is allowed, define objective equivalence criteria.

11. How would you design an architecture for future expansion?

Provide justified spare I/O and network capacity, modular software, clear interfaces, documented naming conventions, sufficient panel space, compatible hardware, and a controlled configuration-management process.

12. How do you verify that an equipment specification is complete?

Trace each requirement to the selected equipment and interface, verify ratings and compatibility, check environmental and safety requirements, confirm documentation and software deliverables, and define tests that prove compliance.

34. Final engineering principle

A sound proposed automation architecture must be functionally complete, technically compatible, safe, supportable, and testable. Every selected component must serve a defined requirement, and every critical requirement must have a clear implementation and verification method.

The strongest DAP is not the one containing the most equipment or the most elaborate diagram. It is the one that allows engineering, procurement, installation, commissioning, maintenance, and production teams to understand exactly what will be built, how it will behave, and how its performance will be proven.
