1. Purpose and Scope

Program version management is the practice of identifying, preserving, comparing, approving, and recovering different versions of software programs that control industrial machines and production processes.

In industrial automation, a program version represents a particular state of the machine's control logic or application code. This can include PLC programs, robot programs, CNC programs, HMI projects, SCADA applications, vision inspection jobs, and test-bench software.

A machine may continue operating after a program modification, yet the change could introduce intermittent faults, alter cycle timing, bypass an expected sequence, or affect product quality. Without controlled program history, identifying the exact change and recovering the last approved version becomes difficult.

The objective is to know which program version belongs to which machine, which version is approved, what changed between versions, and which version can be restored safely.

This topic covers:

  • Program version identification and numbering.
  • Differences between program versions, software versions, and parameter versions.
  • Historical program backups.
  • Version naming and repository organization.
  • Program comparison and change tracking.
  • Approved, working, deployed, and historical versions.
  • Program compilation, download, and verification.
  • Recovery and rollback planning.
  • Version control for PLC, HMI, CNC, robot, vision, and industrial PC applications.
  • Vendor changes, audits, and cybersecurity.

2. What Is a Program Version?

A program version is an identifiable revision of a program or application at a particular stage of its development, approval, or deployment.

For example, a PLC program might progress through the following revisions:

  • R001: Initial commissioned program.
  • R002: Added sensor diagnostics.
  • R003: Corrected a sequence fault.
  • R004: Modified a timeout after an approved engineering change.

These labels are illustrative. The revision number does not automatically prove that a change was approved, tested, or downloaded to the machine.

A program version should be associated with its machine, device, change record, software environment, and validation status.

3. Program Version vs. Other Version Types

Version type What it identifies Example
Program version Revision of the application logic or code PLC application R004
Engineering software version Release of the tool used to edit the program TIA Portal V19
Firmware version Embedded software running on the device PLC CPU firmware
Hardware revision Physical device revision CPU hardware revision
Parameter version Revision of configurable device values Drive parameter set R006
HMI project version Revision of operator-interface screens and logic HMI project R003
Recipe version Revision of a product-specific setting set Recipe PRODUCT-A-R02
Release version Version formally released for deployment Release 1.4.0
Build version Identifier for a generated executable or package Build 10482

These versions must be recorded separately because they answer different questions.

For example, the PLC application can change from R003 to R004 while the PLC firmware and engineering software remain unchanged.

4. Why Program Version Control Matters in Industrial Maintenance

Program version control supports:

  1. Breakdown recovery: Restore a known, suitable program after a failed or incorrect modification.
  2. Root cause analysis: Determine whether a program change contributed to a failure.
  3. Change traceability: Identify who changed the program, why, and under which authorization.
  4. Production stability: Prevent unapproved modifications from becoming the new reference configuration.
  5. Quality control: Track changes that influence test sequences, measurements, and acceptance criteria.
  6. Vendor management: Require vendors to deliver the final source project and a clear change record.
  7. Obsolescence management: Preserve source files and the software environment needed to work with older programs.
  8. Audit readiness: Demonstrate that deployed programs are controlled and appropriately validated.
  9. Cybersecurity: Detect unexpected program changes and restrict unauthorized downloads.
  10. Engineering improvement: Compare revisions to understand how the machine's logic evolved.

A file called PLC_FINAL_NEW_LATEST.project is not a version-control system. It is a future investigation waiting to happen.

5. Types of Industrial Programs

Program type Typical content Important version-control concern

HMI program Screens, buttons, alarms, recipes Screen logic, tag mapping, operator permissions
SCADA application Tags, alarms, scripts, trends, communication Runtime dependencies and configuration changes
CNC program Machining instructions and associated program data Part revision, machine compatibility, tool and offset dependencies
Robot program Motion sequences, paths, positions, process instructions Robot model, tool frames, work frames, external axes
Vision program Inspection logic, regions, thresholds Calibration, lighting, inspection validation

A system may contain several independently versioned programs. The overall machine configuration should record the relevant versions together.

6. Program Version Identification

Every program should have a unique and understandable identity.

Recommended fields include:

  • Machine ID.
  • Device ID.
  • Program or project name.
  • Program type.
  • Program revision.
  • Source file or package name.
  • Engineering software version.
  • Target device model.
  • Target firmware version.
  • Creation or modification date.
  • Backup capture date.
  • Author or responsible team.
  • Change request or work order.
  • Approval status.
  • Validation status.
  • Deployment status.
  • Integrity checksum, where supported.
  • Previous version reference.

Example:

Field Example
Machine ID TB-014
Device ID PLC-TB014-CPU01
Program name TB014_MainSequence
Program revision R004
Engineering software Exact installed tool version
Target CPU Exact CPU catalog number
Firmware Actual installed firmware version
Change reference WO-EXAMPLE
Approval status Approved
Validation status Passed
Deployment status Deployed
Capture date 2026-10-17

Example identifiers are illustrative. Real records must contain the values read from the actual machine and engineering environment.

7. Program Revision Numbering

A revision scheme should be consistent, readable, and appropriate for the system.

7.1 Sequential Revision Scheme

Examples:

  • R001
  • R002
  • R003
  • R004

This scheme works well for maintenance-controlled PLC projects, device configurations, and machine-specific source programs.

Advantages:

  • Simple to understand.
  • Easy to sort when fixed-width numbering is used.
  • Suitable for a controlled revision register.

Limitation: the number alone does not describe the type or significance of the change.

7.2 Semantic Versioning

Some software applications use a scheme such as MAJOR.MINOR.PATCH.

Example: 2.4.1

  • 2: Major release.
  • 4: Minor release.
  • 1: Patch release.

This is useful when a project follows a defined release policy, but it should not be imposed blindly on vendor-specific engineering projects.

Industrial engineering tools may have their own versioning rules. Preserve the original tool version and any native project revision metadata in addition to the plant's revision identifier.

7.3 Revision and Approval Are Separate

A revision number identifies a particular program state. It does not establish whether the state is approved.

For example:

Revision Status Meaning
R001 Approved Initial released program
R002 Working Under engineering modification
R003 Tested Functional tests passed, approval pending
R004 Approved Formally authorized release
R005 Rejected Failed validation; not approved for deployment

A rejected or failed revision should remain traceable according to the retention policy rather than being silently overwritten.

8. Recommended Program Filename Convention

Use a naming convention that identifies the machine, device, program, revision, and capture date.

Recommended pattern:

MACHINE_ID_DEVICE_ID_PROGRAM_NAME_REVISION_YYYY-MM-DD_STATUS.EXT

Example:

TB-014_PLC-TB014-CPU01_MainSequence_R004_2026-10-17_APPROVED.project

Another example for an HMI:

TB-014_HMI-TB014-01_OperatorPanel_R003_2026-10-17_APPROVED.project

The extension must match the actual engineering software's native project or export format.

Avoid ambiguous names such as:

  • final.project
  • final_latest.project
  • new_program.project
  • backup_good.project
  • program_fixed_again.project

A clear filename supports discovery, but the repository metadata remains the authoritative record for approval, compatibility, and deployment.

9. Program Version Lifecycle

A controlled program normally passes through defined stages.

Existing Approved Program
    ↓
Capture and Preserve Baseline
    ↓
Create Working Copy
    ↓
Modify Program Under Change Control
    ↓
Review and Compare Changes
    ↓
Compile or Validate Where Supported
    ↓
Test Using Approved Procedures
    ↓
Obtain Required Approval
    ↓
Deploy to the Target Machine
    ↓
Verify Actual Deployed State
    ↓
Archive Release and Update Version Register

Not every system has a compiler or supports a reliable online comparison. In those cases, use the available manufacturer-supported validation methods and document their limitations.

10. Approved Master, Working Copy, Deployed Version, and Historical Version

These states must be distinguished.

State Meaning Main purpose
Approved master Controlled reference version Baseline for authorized work
Working copy Version under modification Engineering and troubleshooting
Tested candidate Version that has passed specified tests Review before release
Approved release Version authorized for deployment Controlled production use
Deployed version Program recorded as installed or running on the device Actual machine configuration
Historical version Earlier retained version Traceability and recovery
Rejected version Version that failed review or testing Investigation and audit trail

The deployed version may differ from the approved master if an authorized release has not yet been installed or if an actual-state capture identifies an unexpected difference.

Never assume that the newest file in the repository is the version currently running on the machine.

11. Program Capture: Offline and Online Sources

Industrial engineering tools commonly distinguish between offline projects and the program or configuration currently held by a physical device.

11.1 Offline Project

An offline project is the engineering copy stored on a computer or repository.

It may contain:

  • Logic and program blocks.
  • Hardware configuration.
  • Symbolic tags.
  • Comments and documentation.
  • Libraries and dependencies.
  • Network settings.
  • HMI screens or related application files.

The offline project may not match the program running on the machine.

11.2 Online Device State

An online capture is obtained from the physical device using an appropriate supported tool.

It may reveal differences between the deployed program and the offline project.

However, an upload may not recover every original source artifact. Depending on the device, it may omit comments, symbolic names, source code, external libraries, or other engineering metadata.

11.3 Practical Rule

Maintain separate records for:

  • The approved engineering master.
  • The actual-state capture from the device.
  • The working copy used for modifications.
  • The final deployed release.

Record the source of every capture. Do not label an offline file as the actual running version unless its identity has been verified through an appropriate method.

12. Program Comparison and Difference Analysis

Program comparison identifies changes between two revisions.

Changes can include:

  • Added, deleted, or modified logic.
  • Changed timer presets or constants.
  • Modified interlocks.
  • Changed alarm conditions.
  • Altered I/O mappings.
  • New or removed function blocks.
  • Changed motion sequences.
  • Modified HMI tags or scripts.
  • Updated CNC instructions.
  • Changed vision inspection regions or thresholds.
  • Updated communication settings embedded in a project.

A comparison should identify the affected functionality, not merely report that the files differ.

12.1 Comparison Procedure

  1. Confirm that both files belong to the correct machine and device.
  2. Verify project format and engineering software compatibility.
  3. Confirm whether the comparison is source-to-source, offline-to-upload, or release-to-release.
  4. Use the vendor's supported comparison tools where available.
  5. Review added, removed, and modified objects.
  6. Identify safety, quality, sequence, timing, and communication impacts.
  7. Link the differences to the approved change request.
  8. Record the comparison result and reviewer.
  9. Preserve the comparison report where required.

A binary file comparison may show that two files differ without explaining the engineering significance. Conversely, some tools normalize or regenerate project files, so file-level differences may include metadata unrelated to functional changes.

13. Program Version Control for PLCs

For PLC projects, version control should cover more than ladder logic.

Record relevant items such as:

  • Main program and subroutines.
  • Function blocks and functions.
  • Data types and structures.
  • I/O configuration.
  • Controller and communication-module configuration.
  • Tag databases and symbols.
  • Safety-related program components.
  • Hardware configuration.
  • Required libraries.
  • Controller firmware.
  • Engineering software version.
  • Relevant retentive-data handling and configuration.

For safety PLCs, preserve the required safety signatures, validation records, and manufacturer-specific safety information where applicable. Safety application changes require the appropriate authorization and validation process.

PLC Example

A PLC program revision R004 changes a sensor timeout from its previous value to a new approved value.

The record should identify:

  • The exact program and machine.
  • The previous and new behavior.
  • The change reference.
  • The reviewer and approver.
  • The test cases performed.
  • The actual deployed version.
  • The previous approved version retained for recovery.

If the timeout is stored in a separate parameter set, record that parameter change as well. Program revision and parameter revision should not be confused.

14. Program Version Control for HMI and SCADA

HMI and SCADA changes can affect both operators and machine behavior.

Record changes to:

  • Screens and navigation.
  • Alarm messages and priorities.
  • PLC tag mappings.
  • Operator commands.
  • User roles and permissions.
  • Recipe handling.
  • Trends and data logging.
  • Communication drivers.
  • Scripts and expressions.
  • Runtime configuration.
  • Database connectivity and application dependencies.

After a change, verify not only that the project opens but also that the relevant runtime functions behave correctly.

For example, a screen button may display correctly while writing to the wrong PLC tag. Visual appearance alone is not proof of correct function.

15. Program Version Control for CNC and Robot Systems

15.1 CNC Programs

Preserve relevant identifiers and dependencies, including:

  • Program number or name.
  • Part or process revision.
  • Machine ID.
  • CNC control model.
  • Program revision and capture date.
  • Tooling and offset dependencies where required.
  • Subprograms and macros.
  • Relevant machine-builder configuration.
  • Validation and first-piece inspection results.

A CNC program may be syntactically valid but unsuitable for a particular machine, tool setup, or material. Program recovery must follow the machine builder's procedures and the plant's controlled verification process.

15.2 Robot Programs

Preserve:

  • Robot controller identity.
  • Robot model and configuration.
  • Application program revision.
  • Tool and work-frame definitions.
  • External-axis configuration.
  • Required technology packages.
  • Relevant communication configuration.
  • Safety-related configuration records.
  • Program validation and commissioning results.

Changes to motion paths or frames can affect clearances and collision risk. Restoration should not proceed directly to unrestricted automatic production without the required checks.

16. Version Control for Vision and Test-Bench Programs

16.1 Vision Applications

Historical versions may include the inspection program, camera settings, calibration data, region definitions, thresholds, and product-specific jobs.

Record the camera and lighting configuration where it affects repeatability. After restoring a program, verify performance against suitable known-good and known-defective samples using the approved quality process.

16.2 Test-Bench Applications

Preserve the test sequence, measurement calculations, communication mappings, acceptance limits, report format, and required software dependencies.

When a program change affects a test limit or calculation, establish whether revalidation or calibration is required. A successful execution of the new software does not prove that the measurement system remains accurate.

17. Release Notes and Program Change Summaries

Each approved release should have a concise change summary.

Recommended fields:

Field Purpose
Release ID Identifies the controlled release
Previous revision Identifies the version being replaced
New revision Identifies the released version
Change reference Links to the approved work order or request
Change summary Describes the modification
Reason Explains why the change was required
Affected functions Identifies the impacted behavior
Compatibility notes Records tool, firmware, or hardware requirements
Test summary Describes validation performed
Known limitations Documents unresolved issues or constraints
Approval Records authorization
Deployment result Records actual installation outcome

A useful change summary explains what changed and why, not merely that a program was “updated.”

18. Rollback and Recovery Planning

Rollback means returning to a suitable previous state. It does not mean blindly downloading the oldest available program.

Before rollback, verify:

  • The selected revision belongs to the correct machine and device.
  • The target hardware and firmware are compatible.
  • The version was previously approved or is otherwise authorized for recovery.
  • Related parameters and recipes are compatible.
  • The program does not reintroduce a known defect.
  • Current data that must be retained has been handled appropriately.
  • The rollback procedure is authorized and technically supported.
  • Required post-restoration checks are defined.

Some device changes cannot be reversed simply by restoring the program. Firmware changes, hardware substitutions, database migrations, or altered parameter formats may require separate recovery procedures.

Rollback Example

A new PLC release introduces an unexpected sequence fault.

The maintenance team should preserve the failed version and its diagnostic evidence, identify the last suitable approved release, assess compatibility, and follow the approved recovery process. After rollback, the team must verify the actual program state and perform the required functional checks.

The failed release should remain traceable for root cause analysis rather than being overwritten or deleted.

19. Integrity, Access Control, and Cybersecurity

Program files are operationally sensitive assets. Unauthorized changes can disrupt production, compromise quality, or affect machine safety.

Recommended controls include:

  • Role-based access to engineering projects.
  • Controlled write access to approved masters.
  • Separate review and approval for significant changes.
  • Audit logs for downloads and releases.
  • Cryptographic hashes for detecting file changes.
  • Protected historical repositories.
  • Offline or immutable copies for critical systems.
  • Secure handling of credentials and licenses.
  • Controlled access to engineering workstations.
  • Documented recovery and restoration tests.

A checksum can help establish whether a file's contents match a previously recorded value. It does not prove that the program is correct, safe, approved, or the program currently running on the device.

Where supported, compare the deployed state against the approved release using a manufacturer-supported method.

20. Practical Program Repository Structure

A practical repository can separate approved masters, working files, releases, and historical records.

BACKUP_REPOSITORY
    MACHINE_ID
        DEVICE_ID
            01_APPROVED_MASTER
            02_WORKING
            03_TESTED_CANDIDATES
            04_RELEASED_PROGRAMS
            05_ACTUAL_STATE_CAPTURES
            06_HISTORICAL_VERSIONS
            07_CHANGE_RECORDS
            08_VALIDATION_REPORTS

The exact structure can vary, but access permissions and naming rules should remain consistent.

Do not allow working files to overwrite approved masters automatically. A release should be promoted through the required review and approval process.

21. Common Program Version Management Mistakes

  1. Keeping only one copy of the latest program.
  2. Overwriting the approved master during troubleshooting.
  3. Confusing program revision with engineering software version.
  4. Assuming the offline project matches the running device.
  5. Failing to record which machine or device a program belongs to.
  6. Keeping a program without required libraries or dependencies.
  7. Recording a revision number without approval or validation status.
  8. Downloading an old program without checking compatibility.
  9. Deleting failed versions needed for investigation.
  10. Treating a successful compilation as proof of correct operation.
  11. Treating a successful download as proof of production readiness.
  12. Accepting a vendor handover without source files or a change summary.
  13. Ignoring parameter or recipe changes associated with a program release.
  14. Failing to preserve a tested recovery version.
  15. Storing sensitive credentials inside ordinary project archives without suitable protection.

22. Program Version Audit Checklist

  • Every program has a unique machine and device identity.
  • Program revisions are distinguishable and traceable.
  • Engineering software and target firmware versions are recorded.
  • Approved masters are protected against accidental modification.
  • Working copies are separated from released versions.
  • Actual-state captures are identified by their source.
  • Significant changes have review and approval records.
  • Program comparisons are performed where supported and required.
  • Dependencies and required libraries are documented.
  • Test results are linked to the release.
  • Deployment status is recorded separately from approval status.
  • Previous suitable versions are retained according to policy.
  • Rollback compatibility and prerequisites are documented.
  • Program integrity and repository access are controlled.
  • Vendor modifications include source files and handover records.
  • Restoration and functional validation are periodically tested where required.

23. Interview Questions and Answers

Q1. What is program version control?

It is the systematic identification, storage, comparison, approval, and recovery of different revisions of an industrial program.

Q2. What is the difference between a program version and a firmware version?

A program version identifies the revision of application logic or code. A firmware version identifies the embedded software running on the device.

Q3. Why maintain an approved master?

It provides a controlled reference for engineering changes, comparisons, audits, and recovery.

Q4. Does the latest program file necessarily match the running PLC?

No. The latest file may be a working copy, a tested candidate, or an approved release that has not been deployed.

Q5. Why capture the program from the physical device?

An actual-state capture can help identify differences between the installed configuration and the offline engineering project, subject to the device's upload capabilities.

Q6. What is a program comparison?

A comparison identifies differences between program versions so engineers can assess the technical and operational impact of changes.

Q7. What information should a program release contain?

At minimum, the program identity, revision, change summary, compatibility context, validation result, approval status, and deployment outcome.

Q8. Can a program be restored without checking its parameters?

Not safely by default. The program may depend on particular parameters, recipes, firmware, hardware, or other configuration data.

Q9. What is the purpose of a rollback plan?

It defines how to return to a suitable previous configuration if a change fails, including compatibility checks and post-restoration validation.

Q10. What proves that a program is production-ready?

The required technical reviews, compatibility checks, authorization, deployment verification, and applicable functional, quality, and safety validation. A revision number alone proves none of these.

24. Final Principles

  • Every industrial program should have a traceable identity and revision.
  • Program revision, engineering software version, firmware, hardware, and parameters are separate records.
  • Preserve approved masters, working copies, released versions, and actual-state captures distinctly.
  • Record why a change was made and how it was validated.
  • Verify the actual deployed state rather than assuming the repository is authoritative.
  • Preserve dependencies and compatibility information.
  • Retain failed and superseded versions according to the applicable policy.
  • Treat rollback as a controlled recovery operation.
  • Protect programs against unauthorized modification.
  • Validate machine behavior after restoration or deployment.
