1. Purpose and Scope

Software, firmware, and hardware version management is the practice of recording the exact software applications, embedded programs, physical components, and hardware revisions associated with an industrial machine at a specific point in time.

In industrial maintenance, a backup file alone is not enough. A PLC project may be preserved perfectly, but restoration can still fail if the engineering software is incompatible, the controller firmware differs, or the replacement hardware has a different revision.

The objective is to preserve not just the backup file, but the technical environment required to understand, validate, and recover it.

This topic covers:

  • Software versions and engineering-tool compatibility.
  • Firmware versions and controller compatibility.
  • Hardware models, revisions, and installed configurations.
  • Dependencies between software, firmware, and hardware.
  • Version recording in historical backup repositories.
  • Upgrade, downgrade, replacement, and migration considerations.
  • Compatibility verification and recovery testing.
  • Practical industrial examples involving PLCs, HMIs, CNCs, robots, drives, IPCs, and network devices.

2. Understanding the Three Version Categories

2.1 Software Version

Software is the application or tool that executes on a computer, engineering workstation, HMI, industrial PC, or other computing platform.

Examples include:

  • PLC engineering software.
  • HMI development software.
  • SCADA applications.
  • CNC programming and service software.
  • Robot programming software.
  • Vision configuration software.
  • VFD and servo configuration utilities.
  • Database servers and application runtimes.
  • Industrial PC operating systems and drivers.

Example record:

Engineering Software: TIA Portal V19

This identifies the engineering-tool version, not necessarily the PLC firmware or the version of the project itself.

2.2 Firmware Version

Firmware is software stored in a device that controls its internal operation. It commonly runs on PLC CPUs, communication modules, drives, HMIs, network switches, robots, and other embedded devices.

Examples include:

  • PLC CPU firmware.
  • Ethernet communication module firmware.
  • VFD control firmware.
  • Servo-drive firmware.
  • HMI operating firmware.
  • Robot controller firmware.
  • Industrial switch firmware.
  • Vision-controller firmware.

Example record:

PLC Firmware: V3.x

This is an illustrative format. The actual firmware version must be read from the installed device or verified through the manufacturer's supported tools.

Firmware is not the same as the application program running on the device. A PLC can retain the same firmware while its control logic changes several times.

2.3 Hardware Version

Hardware version identifies the physical device model, product revision, or hardware variant.

Examples include:

  • PLC CPU catalog number and hardware revision.
  • I/O module model and revision.
  • Communication adapter model.
  • HMI panel model.
  • VFD or servo-drive model.
  • Robot controller generation.
  • Industrial PC motherboard or network adapter revision.
  • Network switch model and hardware revision.

Example record:

PLC CPU: 1756-L73S, installed hardware revision recorded separately

The model identifies the product type. The hardware revision distinguishes particular design or manufacturing revisions of that product.

3. Comparison of Software, Firmware, and Hardware

Attribute Software Firmware Hardware
Nature Application or engineering program Embedded device software Physical equipment
Typical location PC, engineering workstation, IPC, server PLC, drive, HMI, controller, network device CPU, module, panel, drive, board
Example TIA Portal PLC CPU firmware S7-1500 CPU model and revision
How it changes Installation, upgrade, patch, project modification Supported firmware update or replacement Physical replacement or hardware revision
Main compatibility concern Operating system, project format, libraries, drivers Device model, hardware revision, application support Firmware support, electrical interfaces, module compatibility
Backup concern Installer, license, project, dependencies Firmware package or recovery method where permitted Model, revision, serial number, module arrangement
Typical failure consequence Project cannot be opened or runtime cannot execute Device behavior or compatibility changes Replacement may not support the original configuration

The three categories are related, but they are not interchangeable. Recording only one leaves gaps in the recovery record.

5. Why Version Information Must Be Part of Historical Backups

A historical backup without version information can be difficult or impossible to restore reliably.

Consider a PLC project created with a newer engineering-software release than the workstation currently available. The project may not open in the installed tool, or conversion may be required. Conversion can introduce changes that need review and validation.

Similarly, a replacement PLC may have a different firmware level. Even if the controller model appears similar, the original project may require a feature or configuration unsupported by the replacement's firmware.

A complete recovery record should help answer:

  1. Which physical machine and device does the backup belong to?
  2. Which hardware model and revision were installed?
  3. Which firmware version was active?
  4. Which software version created, opened, compiled, or downloaded the project?
  5. Which project or application revision was running?
  6. Which libraries, drivers, device descriptions, and runtime components were required?
  7. Was the version combination supported by the manufacturer?
  8. Was the configuration successfully validated after restoration?

6. Version Identification for Industrial Equipment

6.1 PLC Systems

For a PLC-based machine, record the following wherever applicable:

  • PLC manufacturer and exact CPU catalog number.
  • CPU hardware revision and serial number.
  • CPU firmware version.
  • Engineering software name and version.
  • Project revision and project conversion history.
  • I/O module models and hardware revisions.
  • Communication module models and firmware.
  • Required libraries and device-description packages.
  • Safety-related application and firmware information, where applicable.
  • Runtime, communication, and configuration dependencies.

Example:

Parameter Example record
Machine ID TB-014
PLC Device ID PLC-TB014-CPU01
PLC model 1756-L73S
Hardware revision Record actual installed revision
Firmware version Record actual installed version
Engineering software Record exact product and release
Application revision R003
Backup date 2026-10-17
Validation status Pending

A model number alone is not a complete compatibility record. The CPU, firmware, communication modules, I/O configuration, and application dependencies must all be considered.

6.2 HMI and SCADA Systems

For HMI and SCADA, capture:

  • Panel or server hardware model.
  • Operating system and version.
  • Engineering software version.
  • Runtime software version.
  • HMI or SCADA project revision.
  • Communication drivers and versions.
  • Required libraries, fonts, controls, and plugins.
  • Database engine and version where applicable.
  • License type and license-management requirements.
  • Communication settings and dependencies.

For example, a Mitsubishi GOT project may depend on the GOT model, its supported firmware, GT Designer version, communication drivers, and PLC connection settings.

A project that opens successfully in the engineering software is not necessarily ready to run on the target panel. Runtime compatibility must also be checked.

6.3 CNC Systems

CNC machines may involve multiple software and firmware layers:

  • CNC control software.
  • CNC system software version.
  • PLC or PMC program revision.
  • Servo and spindle drive firmware.
  • Operator panel software.
  • Machine-builder application and parameters.
  • Option packages and enabled functions.
  • Engineering and service-tool versions.
  • Hardware and interface-board revisions.

A CNC system's compatibility cannot be judged from the control-family name alone. Machine-builder integration, installed options, servo systems, and supported parameters may differ between machines.

6.4 Robots

For industrial robots, record:

  • Robot controller model and generation.
  • Controller system software version.
  • Robot application program revision.
  • Robot model and mechanical configuration.
  • Installed options and technology packages.
  • External-axis configuration.
  • Fieldbus and communication software.
  • Engineering software version.
  • Safety configuration and validation records, where applicable.

A program developed for one controller generation may not be directly transferable to another. Migration may require conversion, option verification, and testing under the manufacturer's procedures.

6.5 VFD and Servo Drives

For drives, preserve:

  • Drive model and power rating.
  • Hardware revision.
  • Firmware version.
  • Configuration-tool version.
  • Parameter-set revision or capture date.
  • Motor nameplate data.
  • Encoder and feedback configuration.
  • Fieldbus or communication options.
  • Application-specific settings.
  • Required commissioning and validation records.

A drive parameter file is not necessarily interchangeable between different drive models or firmware releases. Verify the target model, supported parameter set, motor configuration, and manufacturer's migration instructions before applying it.

6.6 Industrial PCs and Network Devices

For an industrial PC, capture the operating system edition and build, installed applications, drivers, runtime dependencies, database components, hardware details, and license requirements.

For industrial network devices, capture the hardware model, hardware revision, firmware, configuration format, supported features, and management-tool version where relevant.

A configuration may depend on features introduced in a newer firmware release. Applying it to an older device can cause rejected commands, missing features, or unintended behavior.

7. Compatibility Between Software, Firmware, and Hardware

Compatibility is a relationship between components, not a single version number.

For example, a PLC engineering project may depend on all of the following:

Engineering Software Version
    ↓
Supported Project Format
    ↓
Controller Model and Hardware Revision
    ↓
Compatible CPU Firmware
    ↓
Supported I/O and Communication Modules
    ↓
Required Libraries and Device Descriptions
    ↓
Compilation and Configuration Validation
    ↓
Approved Download and Commissioning

The exact requirements depend on the product family and application.

7.1 Compatibility Matrix

A compatibility matrix records the combinations that are known or approved to work.

Component Recorded version Compatibility question
Engineering software Exact release Can it open and edit the project?
Controller model Exact catalog number Is the target device supported?
Controller firmware Exact release Does it support the project's required features?
I/O modules Models and revisions Are the modules supported by the controller and project?
Libraries Exact versions Are required blocks or functions available?
Operating system Edition and build Is the engineering or runtime software supported?
Communication driver Exact version Can it communicate with the installed hardware?
Runtime software Exact release Can the application execute on the target?

Use the manufacturer's compatibility documentation and release notes for the exact product versions. Do not infer compatibility merely because two versions are close numerically.

8. Version Number Interpretation

Version numbering differs across manufacturers, so always preserve the full identifier displayed by the device or software.

Common patterns include:

  • Major.Minor.Patch, such as 4.2.1.
  • A release designation such as V19.
  • A build identifier such as Build 10482.
  • A hardware revision such as Rev C.
  • A manufacturer-specific firmware identifier.

A simplified semantic-versioning example is:

3.5.2

  • 3: Major version.
  • 5: Minor version.
  • 2: Patch version.

However, this interpretation is valid only when the product follows that numbering convention. Many industrial products use proprietary version schemes.

8.1 Never Record Only the Major Version

Recording only V3 may be insufficient when the device actually reports V3.1.4, a build number, or a separate hardware revision.

Capture the complete version string, including suffixes, service packs, build numbers, and revision identifiers where applicable.

8.2 Version Comparison Is Not Always Numeric

For example, release identifiers such as V2.10 and V2.9 should not automatically be compared as decimal numbers. In ordinary component-based version numbering, minor release 10 is later than minor release 9.

Use the manufacturer's version-comparison rules rather than relying on filename sorting or simple numeric conversion.

9. Historical Version Records and Naming

The version information should be visible in both the backup index and, where practical, the backup metadata.

Recommended filename pattern:

MACHINE_ID_DEVICE_ID_SYSTEM_SWVERSION_FWVERSION_HWREV_YYYY-MM-DD_REV.EXT

Example:

TB-014_PLC-TB014-CPU01_PLC_ENGV19_FWV3.1_HWREV02_2026-10-17_R003.project

This is illustrative. Actual version identifiers should be used, and filenames should be shortened if the software or filesystem imposes length restrictions.

Because filenames cannot conveniently hold every dependency, maintain a metadata record alongside the file or in a controlled backup database.

Recommended metadata fields:

Field Purpose
Machine ID Identifies the physical machine
Device ID Identifies the specific installed device
Device model Identifies the hardware product
Hardware revision Identifies the physical revision
Firmware version Records embedded software
Engineering software Records the tool used to create or manage the project
Runtime version Records the execution environment, where applicable
Application revision Identifies the machine-specific project revision
Library versions Records required dependencies
Operating system Records the host environment where relevant
Capture date Establishes when the backup was captured
Source Identifies the origin of the backup
Compatibility status Records the outcome of compatibility review
Validation status Records whether required tests passed
Change reference Links the backup to the approved modification

10. Version Changes During Maintenance

Any modification that changes software, firmware, hardware, or a dependency should trigger a review of the historical backup record.

10.1 Before an Upgrade

  1. Identify the exact machine and target device.
  2. Capture the existing configuration using the approved method.
  3. Record current hardware, firmware, and software versions.
  4. Confirm the proposed target versions are supported.
  5. Review release notes, known issues, and migration instructions.
  6. Check licensing, dependencies, storage, and recovery requirements.
  7. Obtain required change approval.
  8. Preserve a recovery path before starting the change.

10.2 After an Upgrade

  1. Record the actual installed versions.
  2. Save the approved new configuration.
  3. Record the project revision and change reference.
  4. Verify communication and application behavior.
  5. Test the required machine functions.
  6. Perform applicable safety and quality validation.
  7. Capture the post-change state.
  8. Update the asset register and compatibility records.
  9. Retain the previous version according to policy.

A planned upgrade and a completed upgrade are different events. Record the version actually installed, not merely the version that was intended to be installed.

11. Firmware Upgrade and Downgrade Risks

Firmware changes require particular care because they may alter device behavior, supported features, compatibility, and recovery options.

Potential risks include:

  • Loss of compatibility with an existing engineering project.
  • Changed communication behavior.
  • Unsupported module combinations.
  • Changed parameter interpretation.
  • Loss or reset of device settings.
  • Required intermediate upgrade steps.
  • Inability to downgrade to an earlier firmware.
  • Loss of vendor support for a particular combination.
  • Safety or validation requirements after the change.
  • A device becoming unusable if an update is interrupted.

Before changing firmware, verify the exact model and hardware revision, approved firmware package, manufacturer's instructions, required tools, power stability, and recovery procedure.

Do not assume that a newer firmware version is automatically better for an established production machine. A supported, validated configuration may be preferable to an untested upgrade.

12. Hardware Revision and Replacement Management

Two devices with the same product family can have different hardware revisions or options.

During replacement, verify:

  • Exact catalog or order number.
  • Hardware revision.
  • Electrical ratings and interfaces.
  • Firmware compatibility.
  • Supported modules and accessories.
  • Required configuration or conversion steps.
  • Manufacturer guidance for substitution.
  • Required functional and safety validation.

Example

An obsolete PLC CPU is replaced with a newer compatible unit.

The technician should preserve the old CPU's historical record and document the new CPU's identity, hardware revision, firmware, and commissioning details. The original project may require a conversion or hardware-configuration change before it can be downloaded.

The replacement is not complete merely because the CPU powers up and communicates. Required I/O, sequences, diagnostics, safety functions, and production-quality checks must also be completed.

13. Software Dependencies and Environment Preservation

A project may rely on components that are not contained in its main file.

Examples include:

  • Vendor libraries.
  • Custom function blocks.
  • Device-description files.
  • Communication drivers.
  • Runtime packages.
  • Compiler versions.
  • Database connectors.
  • Operating-system components.
  • Licensed options.
  • Third-party applications.
  • Custom scripts and configuration files.

Preserve the dependency information and, where licensing and vendor policy permit, retain approved installers or package references.

Do not copy license keys or secrets into ordinary backup metadata. Store them through approved credential and license-management processes.

For critical systems, document a tested engineering environment or maintain an approved recovery workstation or virtual-machine image, subject to licensing and cybersecurity requirements.

14. Version Control for Vendor Modifications

Vendor engineers may modify PLC logic, HMI screens, robot programs, CNC parameters, or firmware during maintenance.

A controlled process should record:

  • Machine and device IDs.
  • Vendor or responsible engineer.
  • Work order or change reference.
  • Pre-change software, firmware, and hardware versions.
  • Pre-change backup location.
  • Description of the requested modification.
  • Actual changes performed.
  • Post-change versions.
  • Post-change backup location.
  • Functional test and acceptance results.
  • Approval and handover status.

Do not accept an undocumented “updated backup” as the only handover deliverable. The plant should know what changed, which versions are installed, and how to recover if the modification fails.

15. Obsolescence and Migration Planning

Software, firmware, and hardware version records are valuable for planning migrations before failures occur.

The maintenance team should identify:

  • Products no longer manufactured.
  • Firmware no longer supported.
  • Engineering software that cannot run on current workstations.
  • Unsupported operating systems.
  • Discontinued communication modules.
  • Projects requiring obsolete libraries or drivers.
  • Licenses that may become unavailable.
  • Hardware revisions with limited replacement options.
  • Dependencies that prevent migration to a supported platform.

A migration plan should link the old configuration to the new one.

Existing Machine Configuration
    ↓
Capture Current Software, Firmware, and Hardware
    ↓
Preserve Historical Backup and Dependencies
    ↓
Assess Compatibility and Obsolescence
    ↓
Design and Test Migration
    ↓
Deploy Under Change Control
    ↓
Validate and Document New Configuration
    ↓
Retain Old and New Baselines

The old version should remain available for historical reference and recovery planning, subject to policy and technical limitations. It should not be restored automatically to new hardware without a compatibility review.

16. Version Validation and Recovery Testing

A recorded version combination is useful only when the organization understands whether it can be recovered.

Validation can include:

  • Opening the archived project in the approved engineering tool.
  • Confirming that required libraries are available.
  • Checking project compilation or configuration validity where supported.
  • Verifying hardware and firmware compatibility.
  • Confirming that required runtime software and licenses are available.
  • Testing restoration in a controlled environment where feasible.
  • Recording known limitations and untested dependencies.

For safety-related and production-critical equipment, validation must follow the manufacturer's instructions and the plant's approved procedures.

Distinguish these statuses clearly:

Status Meaning
Captured A backup file or export was obtained
Integrity verified The file matches its recorded integrity value
Opened successfully The relevant software can open the project
Compatibility reviewed Required versions and dependencies have been assessed
Restore tested A controlled restoration test has been completed
Functionally validated Required functional checks passed
Approved The configuration has received the required authorization

Passing one status does not automatically imply that all subsequent statuses have been achieved.

17. Common Version-Management Mistakes

  1. Recording the software version but not the firmware.
  2. Recording the firmware but not the hardware revision.
  3. Assuming the same model number guarantees compatibility.
  4. Keeping only the latest project and deleting the earlier baseline.
  5. Failing to preserve project dependencies or libraries.
  6. Upgrading firmware without a verified recovery plan.
  7. Recording intended versions instead of the versions actually installed.
  8. Confusing a project revision with a software product version.
  9. Failing to document conversion or migration.
  10. Restoring a project without checking target hardware.
  11. Treating a successful project download as proof of correct machine operation.
  12. Retaining files without verifying that the required software and licensing are available.
  13. Storing passwords and license secrets in unprotected metadata.
  14. Assuming that a backup file's integrity proves that it is functionally correct.

18. Practical Industrial Example

A test bench develops a communication fault after a planned PLC upgrade.

The historical record shows:

  • The previous PLC firmware version.
  • The new installed firmware version.
  • The engineering software used.
  • The PLC project revision before the change.
  • The new project revision.
  • The communication module firmware.
  • The change reference and test results.

The engineer captures the current state and compares it with the previous approved configuration. The investigation identifies that the controller and communication module combination requires additional compatibility verification.

The team reviews the manufacturer's documentation, validates the supported configuration, and tests the corrective action under the approved procedure. The historical versions make it possible to establish what changed and to preserve a recovery reference without assuming that the newest version is necessarily the correct one.

19. Version-Management Audit Checklist

  • Exact software product versions are recorded.
  • Firmware versions are recorded for relevant devices.
  • Hardware models and revisions are documented.
  • Machine IDs and Device IDs are correct.
  • Project revisions are distinguished from product versions.
  • Required libraries, drivers, and dependencies are documented.
  • Operating-system and runtime dependencies are captured where relevant.
  • Manufacturer compatibility requirements are checked.
  • Pre-change backups are preserved.
  • Post-change versions are recorded as actually installed.
  • Firmware upgrades and downgrades follow approved procedures.
  • Migration and conversion history is retained.
  • Backup integrity and restoration status are recorded separately.
  • Functional and safety validation is documented where required.
  • Obsolete dependencies and unsupported systems are tracked.
  • Vendor modifications include technical handover records.
  • Historical configurations are protected against unauthorized changes.

20. Interview Questions and Answers

Q1. What is the difference between software and firmware?

Software generally refers to applications and engineering tools running in a computing environment. Firmware is embedded software that controls the operation of a device. The exact boundary varies by product.

Q2. What is the difference between firmware and hardware revision?

Firmware is the device's embedded software version. Hardware revision identifies a physical product revision.

Q3. Why record all three version categories in a historical backup?

Because recovery depends on the combination of physical hardware, device firmware, engineering tools, application software, and dependencies.

Q4. Can a project be compatible with one PLC CPU firmware version but not another?

Yes. Projects may use features, instructions, or configurations that require particular firmware versions.

Q5. Is a higher firmware version always preferable?

No. The selected version must be supported, compatible, and validated for the application.

Q6. Why record the engineering software version?

It helps determine whether the archived project can be opened, edited, compiled, converted, or downloaded correctly.

Q7. What should be checked before replacing an obsolete controller?

Verify the replacement model, hardware revision, firmware support, I/O compatibility, communication interfaces, project requirements, and manufacturer's substitution guidance.

Q8. What is a compatibility matrix?

A record of supported combinations of hardware, firmware, engineering software, runtime components, and dependencies.

Q9. What is the difference between a project revision and a software version?

A software version identifies the engineering product or runtime release. A project revision identifies a particular version of the machine-specific application or configuration.

Q10. Does a successful download prove the machine is ready for production?

No. The machine must pass the applicable functional, communication, quality, and safety validation procedures.

21. Final Principles

  • Record exact software, firmware, and hardware identifiers.
  • Preserve the machine-specific project revision separately from product versions.
  • Capture dependencies and compatibility requirements.
  • Verify manufacturer guidance before upgrades, downgrades, and hardware substitutions.
  • Preserve pre-change and post-change configurations.
  • Document the actual installed versions and validation results.
  • Keep historical backups distinguishable from approved masters and working copies.
  • Treat integrity verification, compatibility review, restoration testing, and functional validation as separate controls.
