1. Purpose and Scope

In industrial maintenance, automation, and disaster recovery, Master Backup vs Working Backup is the practice of separating an approved, protected reference copy from the copy used for routine engineering, troubleshooting, testing, and operational changes.

This distinction is important for PLCs, HMIs, SCADA systems, CNC machines, robots, vision systems, industrial PCs, network devices, drives, test benches, and other programmable equipment.

The core principle is simple:

  • Master Backup: The controlled, approved reference version that can be used to recover a known-good system.
  • Working Backup: A copy used for ongoing work, investigation, testing, or modification. It may contain changes that have not yet been approved.

The terms are not universal industry standards. An organization may use names such as golden copy, baseline, released version, engineering copy, or working project. The important thing is to define the purpose, status, ownership, and permissions for each copy.

2. Master Backup

A Master Backup is the protected reference copy of an asset's approved configuration at a known point in time.

It should represent a configuration that has been validated and accepted for the intended application.

Examples include:

  • Approved PLC program and hardware configuration.
  • Released HMI project and runtime configuration.
  • Validated SCADA application and tag configuration.
  • Approved robot program and machine parameters.
  • Released CNC configuration and supported parameter exports.
  • Validated vision inspection jobs and calibration records.
  • Approved industrial PC system image.
  • Approved network switch or firewall configuration.
  • Validated drive parameters and application settings.
  • Approved test-bench software, test sequences, and limits.

2.1 Characteristics of a Master Backup

  • Approved by the designated authority.
  • Identified by a revision or release number.
  • Linked to the correct machine or asset.
  • Protected against unauthorized modification and deletion.
  • Stored in a controlled repository.
  • Supported by a known restore procedure.
  • Associated with validation or acceptance evidence.
  • Retained according to the organization's backup and change-control policy.

A Master Backup is not necessarily the newest file. It is the latest approved reference version, or another specifically designated release.

2.2 Example

A PLC program controls a production test bench. An engineer changes a timer during troubleshooting and saves the project.

The modified project is not automatically the new Master Backup. It becomes a new master only after the change is reviewed, tested, approved, and released under the applicable procedure.

3. Working Backup

A Working Backup is a copy used during engineering, troubleshooting, modification, testing, or analysis.

It may be based on the Master Backup, a verified upload from the actual machine, or another documented starting point.

Examples include:

  • A PLC project being modified to correct a sequence.
  • A copy of an HMI project being updated for a new alarm.
  • A SCADA project being tested with new tags.
  • A robot program being evaluated offline.
  • A vision job being adjusted to investigate false rejects.
  • A network configuration being tested before an approved change.
  • A CNC parameter export used during a controlled diagnostic activity.

3.1 Characteristics of a Working Backup

  • May change frequently.
  • May contain unapproved changes.
  • Can be used for experimentation within authorized boundaries.
  • Should be identifiable by owner, date, and purpose.
  • Should not silently replace the approved master.
  • Should be stored separately from protected master copies.
  • Should have a documented route for approval and release.

A Working Backup is not automatically safe to deploy. Its status must be clear, especially when several engineers or vendors are involved.

5. Relationship Between the Copies

Approved Existing Configuration
        ↓
Create Verified Working Copy
        ↓
Engineering / Troubleshooting / Modification
        ↓
Offline Review and Testing
        ↓
Controlled Deployment, Where Required
        ↓

        ↓
Review and Formal Approval
        ↓
Release New Master Backup
        ↓

This is a general lifecycle, not a requirement that every change must follow precisely the same sequence. Emergency work, safety-related changes, and vendor-controlled equipment may require special procedures.

Important: The Master Backup and the actual running configuration can differ. Before restoring or changing a machine, determine what is actually installed and running, whether that state is approved, and whether a more recent valid configuration exists.

6. Why Both Copies Are Necessary

Keeping only a Master Backup can make engineering work inconvenient or encourage engineers to modify the protected reference directly.

Keeping only a Working Backup creates a different problem: nobody can confidently identify which version is approved and safe to restore.

Separating the two supports:

  • Recovery from failed modifications.
  • Comparison between approved and actual configurations.
  • Controlled software development.
  • Easier investigation of intermittent faults.
  • Vendor and maintenance collaboration.
  • Traceability of production changes.
  • Prevention of accidental overwriting.
  • Safer rollback after unsuccessful updates.
  • Better audit and change-management evidence.

The two-copy approach is a configuration-control practice. It does not replace independent backup copies, off-site or offline protection, or a complete disaster recovery strategy.

7. Master Backup Creation Procedure

Step 1: Identify the Asset

Record:

  • Plant asset ID.
  • Machine or line.
  • Controller or device model.
  • Hardware revision.
  • Firmware version.
  • Software version.
  • Network identity where applicable.
  • Relevant project or configuration name.

Step 2: Capture the Actual State

Determine whether the backup is being created from:

  • The current project used by engineering.
  • An upload or export from the physical device.
  • An approved existing release.
  • A restored and validated system image.

These sources are not automatically equivalent.

For example, a PLC project on an engineering laptop may differ from the program currently running in the PLC. Where supported, compare the project with the controller's actual program and configuration before designating it as the master.

Step 3: Validate the Configuration

Verify the relevant behavior for the asset.

For a PLC, this may include:

  • Program and hardware configuration.
  • I/O mapping.
  • Communication settings.
  • Safety-related configuration, where applicable.
  • Required data and retentive-value handling.
  • Version and compatibility checks.

For a network switch, it may include:

  • VLAN and port configuration.
  • Routing and redundancy.
  • Security settings.
  • Connectivity and network stability.

For a vision system, it may include:

  • Inspection job.
  • Camera configuration.
  • Calibration.
  • Inspection limits.
  • Reference samples and validation results.

Step 4: Approve and Identify

Assign a controlled revision and status.

Example:

Asset_ID: TB-PLC-014
System: End-of-Line Test Bench
Backup_Type: MASTER
Revision: R003
Status: APPROVED
Source: Verified controller project
Software_Version: Recorded in asset register
Approval_Record: Linked work order or change record
Created_On: YYYY-MM-DD

These fields are an example template. Replace them with the organization's actual asset and document-control identifiers.

Step 5: Protect the Master

  • Store it in the approved repository.
  • Restrict write access.
  • Preserve earlier approved versions according to retention policy.
  • Record integrity information where appropriate.
  • Keep required recovery documentation with the backup.
  • Ensure that recovery access is available to authorized personnel.

Step 6: Test Recoverability

Confirm that the backup can be opened or restored using the supported tools and process. Where practical, test restoration on a suitable spare device, test environment, or isolated system.

Do not experiment by restoring an unverified backup onto a live production controller.

8. Working Backup Creation Procedure

  1. Select the correct approved master or verified actual-state capture.
  2. Copy it into the controlled working area.
  3. Record the source revision and asset identity.
  4. Assign an owner and change purpose.
  5. Make authorized changes in the working copy.
  6. Save meaningful intermediate versions.
  7. Test changes using the appropriate offline or controlled environment.
  8. Document differences from the source.
  9. Follow the approved deployment procedure if the change must reach production.
  10. Submit the completed change for review and release.

A working copy should not be named merely latest, final, or new_final. Those names describe the engineer's emotional relationship with the file, not its technical status.

The ACTUAL_STATE_CAPTURE folder is useful because the configuration found on the machine may not match the approved master. Preserving that state can support troubleshooting and incident investigation.

Access control should distinguish between reading a master, proposing a change, approving a release, and modifying protected repository contents.

10. Naming Convention

A useful filename should identify the asset, configuration type, revision, status, and capture date where relevant.

Example:

TB-PLC-014_PLC_MASTER_R003_APPROVED_2026-10-17.project
TB-PLC-014_PLC_WORKING_CHG042_2026-10-18.project
TB-PLC-014_PLC_ACTUAL_STATE_2026-10-18.project

Use the actual extension required by the software. Do not rename proprietary files to extensions that imply a different file format.

A filename is not a substitute for access control, approval records, or version history. Anyone can type APPROVED into a filename; the repository must establish whether the release really is approved.

11. Version and Revision Management

A practical approach distinguishes three concepts:

  • Revision: The controlled identifier for a released configuration.
  • Working version: An intermediate engineering state that may change repeatedly.
  • Actual-state capture: A documented copy or export representing what was present on the physical device at a specific time.

Example:

Version Description Status
R001 Initial approved PLC project Master
CHG042-W01 First working copy for timer modification Working
CHG042-W02 Revised logic after offline testing Working
R002 Approved timer modification after validation Master
ACT-20261018 Capture from controller during a later investigation Actual-state capture

The actual-state capture is not automatically approved just because it was uploaded from the device. It records what was present, which may include unauthorized or unintended changes.

12. Change Control and Release Process

A new Master Backup should be released only when the applicable change-control requirements are satisfied.

Typical stages include:

  1. Raise or reference an approved change request.
  2. Identify the current master and actual device state.
  3. Create and modify a working copy.
  4. Perform offline checks and risk assessment.
  5. Review the changes.
  6. Obtain required approvals.
  7. Deploy under the authorized maintenance or commissioning procedure.
  8. Validate the actual machine or system.
  9. Capture the resulting approved configuration.
  10. Release the new master and retain the previous master as required.
  11. Update the revision register and recovery instructions.

Not every routine action requires the same level of approval. The process should be proportional to risk, with stronger controls for safety systems, production-critical controls, cybersecurity boundaries, and changes that affect product quality.

13. Rollback Procedure

Rollback returns the system to a previously approved and compatible state after a change fails or produces unacceptable behavior.

Before rollback:

  • Identify the change that caused the problem.
  • Determine whether the previous master is compatible with the current hardware and firmware.
  • Consider whether database or process data changed after the backup.
  • Check whether rollback would overwrite valid new data.
  • Obtain the required authorization.
  • Preserve the failed state and diagnostic evidence where practical.

Then:

  1. Place the equipment into the approved safe state.
  2. Capture the current state if it is safe and technically possible.
  3. Select the correct previous master.
  4. Restore it using the approved method.
  5. Validate system behavior and communication.
  6. Confirm any required parameter, recipe, or data recovery.
  7. Document the rollback and its outcome.

Rollback is not always a simple file replacement. A PLC program, robot program, database schema, or CNC configuration may depend on other versions or data. Compatibility must be checked before restoration.

14. Handling Emergency Changes

During a breakdown, a technician may need to make an urgent change to restore production.

Emergency work should not eliminate configuration control.

Recommended practice:

  • Record the reason for the emergency change.
  • Capture the pre-change state where feasible.
  • Preserve the working version.
  • Document the exact change and affected asset.
  • Validate the result under the applicable safety and production procedure.
  • Obtain retrospective review or approval where the emergency process permits it.
  • Release a new master only after the required verification and authorization.

An emergency working copy must not become the permanent master merely because production restarted. Restored availability and approved configuration are related, but they are not identical.

16. Security and Access Control

Master and Working Backups have different permissions because they have different roles.

A useful access model is:

  • Read access: Personnel who need to inspect an approved master.
  • Working-copy write access: Authorized engineers performing assigned tasks.
  • Release approval: Designated reviewers or authorities.
  • Master-repository write access: Restricted to the release process or authorized custodians.
  • Repository administration: Separately controlled where practical.

Additional controls include:

  • Authentication and audit logging.
  • Protected storage and independent backup copies.
  • Encryption for sensitive files.
  • Integrity verification.
  • Retention of previous approved versions.
  • Secure storage of credentials, certificates, and recovery keys.

A master file should be difficult to alter accidentally and possible to recover if the repository itself is damaged.

17. Common Mistakes

  1. Editing the master directly during troubleshooting.
  2. Treating the latest modified file as the approved version.
  3. Assuming a project on the engineering PC matches the controller.
  4. Overwriting the master before validation is complete.
  5. Keeping the only master on a laptop or USB drive.
  6. Failing to retain a previous approved revision.
  7. Confusing an actual-state capture with an approved master.
  8. Restoring an older version without checking compatibility.
  9. Failing to record the change that led to a new release.
  10. Using unclear filenames and undocumented folder structures.
  11. Allowing working copies to be deployed without review.
  12. Failing to test the backup restoration procedure.

18. Practical Industrial Example

A production test bench uses a PLC and HMI. The approved master PLC program is revision R006.

A recurring timeout fault occurs. The maintenance engineer copies R006 into the working area and changes a timer for diagnostic purposes.

The engineer tests the change and temporarily deploys it under the approved procedure. The fault frequency decreases, but the change has not yet completed its validation.

The correct configuration status is:

  • R006: Previous approved master.
  • CHG057-W01: Working copy containing the timer modification.
  • Actual PLC state: The configuration currently running on the physical controller, which must be captured or compared where supported.

After further testing, engineering determines the correct timer and updates the working copy. The required review, functional testing, and approvals are completed. The new release becomes R007.

The previous master remains available according to the retention policy, while R007 becomes the current approved master.

This preserves the ability to investigate the original problem, reproduce the modification, and roll back if necessary.

19. Master vs Working Backup Audit Checklist

  • Each critical asset has a clearly identified master.
  • Master revisions have approval or release evidence.
  • Master copies are protected against unauthorized modification.
  • Working copies identify their source revision.
  • Actual-state captures are distinguishable from approved masters.
  • Filenames and repository structure are consistent.
  • Changes have a traceable owner and purpose.
  • Production deployment follows the approved change process.
  • Previous approved versions are retained according to policy.
  • Backup integrity and recoverability are tested.
  • Recovery instructions identify software, hardware, and compatibility requirements.
  • Repository access and sensitive information are controlled.

20. Interview Questions and Answers

Q1. What is a Master Backup?

A protected, approved reference copy of a system configuration used for controlled recovery and as a baseline for future changes.

Q2. What is a Working Backup?

A copy used for engineering, testing, troubleshooting, or modification that may contain changes not yet approved for release.

Q3. Why should the master not be edited directly?

Direct editing can destroy the known-good reference and make rollback, comparison, and auditability difficult.

Q4. Is the latest backup always the master?

No. The latest file may be an untested working copy or an unapproved capture from the actual device.

Q5. What is an actual-state capture?

A record or copy of the configuration present on a physical device at a particular time. It is not automatically approved.

Q6. When does a working backup become a master?

When the applicable review, testing, approval, and release requirements have been completed.

Q7. Why retain previous master revisions?

They provide recovery and comparison options if a newer release causes problems or an investigation requires an earlier known-good state.

Q8. Can a master backup replace a disaster recovery plan?

No. A master is one controlled reference copy. Disaster recovery also requires independent backup protection, compatible hardware or recovery tools, documented procedures, and tested restoration.

Q9. What is configuration drift in this context?

A difference between the actual running configuration and the approved master or other designated baseline.

Q10. What is the key principle of master-working separation?

Protect the approved reference while allowing controlled engineering work to proceed independently, then promote changes through a traceable release process.

21. Final Principles

  • Maintain a protected, approved Master Backup for each critical asset.
  • Perform modifications in controlled Working Backups.
  • Distinguish approved master, working copy, and actual-state capture.
  • Record source revision, owner, purpose, and change history.
  • Validate changes before releasing a new master.
  • Preserve previous approved versions according to retention policy.
  • Protect the repository and test the recovery process.
  • Treat backup status as a controlled engineering decision, not a filename.
