1. Purpose and scope

A PLC backup is a controlled, verified copy of the controller's program, configuration, and other required recovery information. Disaster recovery (DR) is the complete process of restoring a PLC-controlled machine or system after a failure, corruption, accidental modification, hardware replacement, cyber incident, or other disruptive event.

The objective is not merely to possess a backup file. The objective is to restore the correct controller configuration safely, within an acceptable time, with the required functionality and traceability.

In industrial maintenance, a PLC backup must support recovery from situations such as:

  • PLC CPU failure requiring replacement.
  • Accidental online program modification.
  • Program corruption or loss.
  • Replacement of a discontinued PLC with a compatible or upgraded model.
  • Memory-card or battery failure affecting retained information.
  • Communication configuration changes that prevent access.
  • Engineering-PC failure or loss of the original project.
  • Cybersecurity incidents affecting controllers or engineering systems.
  • Recovery following an approved software upgrade or migration.

A PLC backup is not automatically a complete machine backup. The PLC program may depend on HMI projects, drive parameters, remote I/O configuration, robot programs, CNC parameters, network settings, safety-controller projects, recipes, and other assets.

The backup process must be repeatable and documented. A folder full of files named final, final_new, and final_latest is not a recovery strategy.

4. What must be backed up?

4.1 PLC program and engineering project

The backup scope depends on the PLC platform and the machine's architecture.

Asset Typical contents Recovery purpose
PLC application Logic blocks, routines, functions, and program organization Restore machine control logic
Symbols and comments Tag names, descriptions, and engineering annotations Support troubleshooting and maintainability
Hardware configuration CPU, racks, modules, I/O assignments, and hardware properties Reconstruct the intended controller configuration
Network configuration Addresses, communication parameters, and network assignments Restore connectivity
Device configuration Remote I/O, fieldbus, and supported device settings Re-establish field device communication
Controller data Retained values or supported data blocks, where required Recover approved operating data
Firmware information CPU and module firmware versions Confirm compatibility during restoration
Safety project Safety logic and safety configuration, where applicable Support controlled safety-system recovery
Motion configuration Motion objects, axes, drive interfaces, and related settings Restore supported motion functionality
Project dependencies Libraries, custom blocks, hardware descriptions, and required software packages Reopen and maintain the project
Documentation Electrical drawings, I/O lists, network diagrams, and functional descriptions Support recovery and verification
Recovery records Upload/download history, revision, checksum, and approvals Establish traceability

Do not assume that all these items are contained in one project file. Some platforms store them separately, and certain configuration or runtime data may require dedicated export or backup procedures.

5. Backup methods

5.1 Original engineering-project backup

This is generally the preferred starting point because it preserves the editable project and engineering information.

Procedure:

  1. Locate the approved project on the engineering PC or controlled repository.
  2. Confirm the project belongs to the intended machine and PLC.
  3. Open it in the appropriate engineering software.
  4. Verify the CPU model, firmware, hardware configuration, and project revision.
  5. Compare its identity and content with the installed controller using approved methods.
  6. Save or archive a new backup revision without overwriting the approved original.
  7. Record the backup date, engineer, software version, and reason for capture.
  8. Store the resulting package in controlled storage.

An engineering project that was last modified several months ago must not automatically be treated as the current production backup.

5.2 Upload from the running PLC

An upload can help recover controller information when the engineering project is missing or uncertain.

However, the available upload data depends on the controller, programming software, access protection, and project state.

Before uploading:

  • Confirm the correct PLC and machine.
  • Establish whether an upload operation is supported.
  • Record the controller identity and current operating state.
  • Check whether online changes or unsaved edits exist.
  • Follow plant authorization procedures.
  • Avoid operations that could change controller mode or disrupt production.
  • Preserve the original project separately if it is available.

After uploading, verify the resulting project. An uploaded project may not contain all comments, symbolic information, libraries, source code, or configuration records necessary for long-term maintenance.

5.3 Memory card and removable media backup

Some PLC families support memory cards or removable storage for program transfer, restoration, or system recovery.

The exact behavior varies by platform. A memory card may contain a boot project, application data, firmware-related files, or other supported content, but it should not be assumed to contain a complete editable engineering project.

Record:

  • Card type and compatibility.
  • Supported backup and restoration procedure.
  • Contents and revision.
  • Whether the card is intended for normal operation or recovery.
  • Required CPU and firmware compatibility.
  • Storage location and physical protection.

A memory card should be labeled and controlled like a recovery asset, not treated as an anonymous spare that can be swapped between machines.

5.4 Online data and retained values

Some applications depend on retained counters, setpoints, recipes, calibration values, or other runtime data.

These values may not be preserved by an ordinary project archive. Determine whether they must be captured separately and whether restoring them is appropriate.

For example, restoring an old production counter, calibration value, or recipe can create operational or quality problems even when the PLC logic itself is correct.

Never restore runtime data blindly. Confirm the data's purpose, validity, retention requirements, and approved recovery point.

6. Backup frequency and recovery objectives

Backup frequency should be based on equipment criticality, rate of engineering change, production impact, and the time required to reconstruct the system.

6.1 Recommended backup triggers

Event Required action
New machine commissioning Create and verify the initial released backup
Approved PLC program change Capture the released revision after testing
Hardware replacement Back up the configuration before and after the change, where practical
Firmware upgrade Preserve the pre-upgrade state and create a verified post-upgrade backup
Obsolescence migration Preserve source and target projects separately
Major parameter change Back up affected configuration and required runtime data
Safety program modification Follow the approved safety lifecycle and backup process
Cybersecurity incident Preserve evidence and recover from a verified trusted copy
Periodic maintenance review Confirm that backups remain current and accessible
Engineering-PC replacement Verify that required projects and software dependencies remain recoverable

A practical starting policy for critical production equipment is to back up after every approved program or configuration change, perform scheduled reviews, and test restoration periodically. The precise frequency should follow plant policy and risk assessment.

6.2 RPO and RTO

Recovery Point Objective (RPO) defines how much recent data or engineering change the plant can afford to lose.

Recovery Time Objective (RTO) defines the target time within which the affected service should be restored.

For example:

  • RPO: No approved PLC change may be lost after release.
  • RTO: Restore the control system within four hours of a qualifying failure.

These are example targets, not universal standards. A critical bottleneck machine may need a shorter RTO than a noncritical utility system.

The required recovery time includes more than downloading a program:

\[ T\_{\text{recovery}} = T\_{\text{diagnosis}} + T\_{\text{hardware}} + T\_{\text{restore}} + T\_{\text{verification}} + T\_{\text{release}} \]

A backup that downloads in ten minutes is of limited use if the correct engineering software takes two days to obtain.

7. Backup validation and integrity

7.1 What does a valid backup mean?

A backup should be assessed against several independent criteria.

Validation level What it establishes What it does not establish
File existence The expected file is present That it is complete or usable
File integrity The file has not changed unexpectedly since the checksum was calculated That it contains the correct program
Project opening The engineering software can read the project That the project matches the installed PLC
Configuration verification The project identifies the expected CPU and hardware That all runtime behavior is correct
Version comparison The backup matches the intended released revision That every dependency is available
Restore test The recovery procedure works in the tested environment That every field condition has been tested
Functional verification Required control functions behave as intended That every possible failure mode has been eliminated

A checksum such as SHA-256 can help detect unexpected file changes.

Backup file
    ↓
Calculate SHA-256 checksum
    ↓
Store checksum in backup manifest
    ↓
Recalculate checksum when retrieving the file
    ↓
Compare values
    ↓
Match: file integrity confirmed
Mismatch: investigate corruption or unexpected modification

A checksum does not prove that the project is correct, current, or safe to restore. It verifies file integrity relative to the recorded checksum.

7.2 Backup manifest

Maintain a manifest with each released backup.

Field Example or requirement
Asset ID Plant-approved machine identifier
PLC manufacturer Actual manufacturer
PLC model Exact CPU model
Firmware Installed or approved version
Project revision Controlled revision identifier
Backup timestamp Actual capture date and time
Backup type Engineering archive, upload, or supported memory image
Engineering software Exact product and version
Source identity Machine and controller identity
Checksum Calculated SHA-256 or approved equivalent
Storage location Controlled repository identifier
Change reference Approved change or work-order number
Validation status Not tested, verified, or restore-tested
Responsible person Actual engineer or authorized owner

8. Storage strategy and the 3-2-1 principle

The 3-2-1 backup principle is a useful baseline:

  • Maintain at least 3 copies of important data.
  • Use at least 2 different storage types or platforms, where practical.
  • Keep at least 1 copy off-site or otherwise isolated from the primary failure domain.

For industrial control systems, independence matters more than simply counting copies. Three folders on the same engineering PC do not provide meaningful resilience against disk failure, ransomware, theft, or accidental deletion.

Example:

Primary copy
    ↓
Controlled engineering repository
    ↓
Independent backup repository
    ↓
Offline or isolated recovery copy

8.1 Recommended storage locations

Storage location Advantages Main risk
Engineering PC Fast access for maintenance PC failure, theft, or malware
Central engineering server Shared access and revision management Server failure or compromised permissions
Isolated backup storage Reduced exposure to routine network incidents Requires controlled access and periodic checks
Offline removable media Can remain disconnected from the production network Physical damage, loss, or outdated contents
Approved off-site storage Supports site-level disaster recovery Access delays or storage policy failures

Use encryption, access controls, and retention policies appropriate to the plant's cybersecurity requirements. Recovery copies should not remain permanently writable by every account that can modify production systems.

9. Restore procedure

Restoration is a controlled engineering operation. Downloading the wrong program to the right CPU can be more damaging than having no backup at all.

9.1 Before restoration

  • Confirm the failure and determine whether restoration is necessary.
  • Identify the exact PLC and machine.
  • Confirm the replacement CPU and module compatibility.
  • Select the correct approved backup revision.
  • Verify the checksum or equivalent integrity record.
  • Confirm the engineering software and firmware compatibility.
  • Identify required parameters, retained data, and device configuration.
  • Obtain the required maintenance and production authorization.
  • Review the machine's safe-state and isolation procedures.
  • Confirm that the restoration method will not cause an unexpected machine start.

9.2 Restoration sequence

  1. Diagnose the fault and establish the actual recovery scope.
  2. Place the equipment in the approved safe state.
  3. Record the installed hardware, CPU identity, firmware, and communication configuration.
  4. Verify the backup revision and its compatibility with the target controller.
  5. Install or replace hardware using approved isolation and installation procedures.
  6. Connect using the supported engineering interface.
  7. Restore the required application and configuration using the manufacturer's documented procedure.
  8. Restore only the approved runtime data that is required.
  9. Verify controller mode, hardware diagnostics, and communication status.
  10. Compare the restored configuration with the approved baseline.
  11. Execute the required functional and safety verification procedures.
  12. Obtain authorization before returning the equipment to production.
  13. Create a new verified backup if the restored system becomes the new approved baseline.

Some restoration procedures require a controller mode change or power cycle. The exact steps depend on the PLC family, so use the relevant vendor instructions rather than applying a generic sequence to every controller.

9.3 Verification after restoration

Confirm all relevant items, not just whether the CPU enters RUN mode.

  • Correct CPU and module configuration.
  • Expected application revision.
  • No unexplained hardware or communication faults.
  • Correct remote I/O and network communication.
  • Correct HMI data and operator commands.
  • Correct drive, robot, and CNC interfaces where relevant.
  • Expected retained values, counters, setpoints, and recipes.
  • Correct startup behavior and interlock status.
  • Verified response to representative machine conditions.
  • Required safety validation completed by authorized personnel.

Safety-critical systems: Restoring a safety PLC project requires the platform-specific safety procedure, verification of the correct approved safety application, and any required validation or proof testing. An ordinary standard PLC backup and a successful download are not substitutes for safety-system validation.

10. PLC backup and change management

Every approved PLC modification should have a traceable relationship between the engineering change, the tested program, and the released backup.

10.1 Recommended change-control workflow

Change request or breakdown
    ↓
Identify current approved PLC revision
    ↓
Create pre-change backup
    ↓
Authorize and implement the change
    ↓
Test the changed program
    ↓
Obtain required approval
    ↓
Release the new revision
    ↓
Create and validate post-change backup
    ↓
Update change records and backup manifest

10.2 Revision naming

Use a consistent naming convention that identifies the asset, controller, revision, and capture date.

Example:

MACHINE_ID_PLC_CPU_REVISION_DATE
LINE1059_PLC01_R012_20261017

The example is illustrative. Follow the plant's actual asset-identification and document-control standards.

Avoid names such as latest, final_final, or new_program. They describe the emotional state of the person saving the file, not its engineering status.

10.3 Change record requirements

Field Purpose
Change ID Links the change to an approved record
Reason Documents the breakdown, improvement, or modification
Previous revision Identifies the pre-change baseline
New revision Identifies the released result
Change description Summarizes modified logic or configuration
Risk assessment Identifies production and safety implications
Test evidence Demonstrates that the change was verified
Approval Records the required authorization
Backup location Identifies the released recovery copy
Rollback method Describes how to restore the previous approved state

For emergency breakdown changes, use the plant's emergency change procedure. Document the modification and create the required verified backup as soon as the system has been safely stabilized.

11. Disaster-recovery scenarios

11.1 PLC CPU failure

Situation: The controller will not start or has a hardware failure.

Recovery approach:

  1. Verify the fault using diagnostics and approved troubleshooting.
  2. Confirm whether the CPU itself has failed.
  3. Identify an approved replacement CPU and check compatibility.
  4. Retrieve the latest verified project and required configuration.
  5. Replace hardware under approved isolation procedures.
  6. Restore the program and parameters.
  7. Verify I/O, communications, retained data, and machine operation.
  8. Complete the required release checks.

A CPU with the same product family name may still require a compatible firmware version, memory configuration, or hardware configuration.

11.2 Accidental PLC modification

Situation: An online change causes unexpected machine behavior.

Recovery approach:

  1. Place the equipment in a safe state.
  2. Determine what changed and whether a known-good revision exists.
  3. Preserve available diagnostic evidence and the current project.
  4. Obtain authorization to restore the previous approved revision.
  5. Restore the appropriate program and configuration.
  6. Verify the original function and test affected interfaces.
  7. Document the event and implement corrective actions.

Do not automatically overwrite the controller with an old backup before understanding the change. Recent approved improvements or important retained data could otherwise be lost.

11.3 Engineering PC failure

Situation: The programming PC is unavailable or its storage has failed.

Recovery approach:

  • Retrieve the project from the independent repository.
  • Verify the project revision and integrity.
  • Reinstall the supported engineering software if necessary.
  • Recover required licenses, drivers, hardware descriptions, and dependencies through authorized procedures.
  • Confirm connectivity and controller compatibility.
  • Verify that the recovered project opens correctly.

A PLC backup without the required engineering environment may not support timely recovery. Record the software version, installation media availability, license recovery method, and required dependencies.

11.4 Cybersecurity incident

Situation: An engineering PC or control-system server may have been compromised.

Recovery approach:

  1. Follow the plant's incident-response procedure.
  2. Coordinate with the authorized OT/IT cybersecurity team.
  3. Isolate affected systems where directed by the response plan.
  4. Preserve relevant logs and evidence.
  5. Identify a known-good backup from before the compromise.
  6. Verify the backup's integrity and provenance.
  7. Restore into an approved, trusted environment.
  8. Validate the controller application and communications.
  9. Reconnect to production only after the required security and engineering approvals.

A backup created after a compromise may contain malicious or unauthorized changes. A matching checksum only establishes consistency with the recorded file, not trustworthiness.

11.5 Firmware or PLC migration

Situation: An obsolete PLC is replaced with a newer controller generation.

The recovery package must distinguish the original system from the migrated system.

  • Preserve the source project and original hardware configuration.
  • Record source CPU model and firmware.
  • Create a separate target project for the new controller.
  • Document converted logic and changed instructions.
  • Verify I/O mapping, communications, timing, and data handling.
  • Perform the required migration tests.
  • Retain both source and target backups with clear revision identifiers.

A migrated project is not a substitute for the original backup. The source project may be required for rollback, historical troubleshooting, or comparison.

13.2 Maintenance workflow integration

A practical process for a breakdown or planned intervention is:

  1. Identify the affected PLC and verify the current approved revision.
  2. Check whether a recent verified backup exists.
  3. Capture a pre-change backup before an authorized modification, where practical.
  4. Complete the repair or approved program change.
  5. Perform the required functional checks.
  6. Create the released post-change backup.
  7. Update the backup register and link the change to the work order.
  8. Record any new hardware, firmware, or software dependency.
  9. Confirm that the independent recovery copy has been updated.

This provides traceability between the physical machine, PLC program, maintenance work, and recoverable engineering state.

14. Recovery drill and periodic audit

A backup policy should be tested through controlled recovery exercises. A backup that has never been restored is an unverified assumption.

14.1 Recovery drill procedure

  1. Select a representative nonproduction controller or approved test environment.
  2. Choose a backup from the controlled repository.
  3. Verify the manifest and checksum.
  4. Confirm software, firmware, hardware, and licensing prerequisites.
  5. Follow the documented recovery procedure.
  6. Measure the elapsed recovery time.
  7. Verify controller configuration and representative application behavior.
  8. Record missing dependencies, errors, and deviations.
  9. Correct the recovery documentation.
  10. Repeat the test when significant issues are identified.

Do not perform an experimental restore on a live production controller merely to prove that a backup works. Use an appropriate test environment or a formally approved shutdown and recovery exercise.

14.2 Audit checklist

  • All critical PLCs are identified in the installed-base register.
  • Each critical PLC has an approved backup requirement.
  • Backups reflect the released program revisions.
  • Required configuration and dependencies are included.
  • Primary and independent recovery copies exist.
  • Access permissions and retention are appropriate.
  • Backup integrity is checked.
  • Restore procedures are documented.
  • Restore tests are performed at the defined interval.
  • Recovery times are measured against approved targets.
  • Engineering changes trigger the required backup updates.
  • Obsolete PLCs have documented recovery and migration strategies.

15. Key performance indicators for backup management

Backup management can be measured using practical maintenance and reliability indicators.

KPI Calculation or measurement Purpose
Backup coverage PLCs with required backups divided by PLCs requiring backups, multiplied by 100% Measures coverage
Backup currency PLCs with backups matching approved revisions divided by PLCs requiring backups, multiplied by 100% Measures revision accuracy
Restore-test success Successful restore tests divided by completed restore tests, multiplied by 100% Measures demonstrated recoverability
Backup compliance Backups completed on time divided by backups scheduled, multiplied by 100% Measures process adherence
Average recovery time Total measured recovery time divided by recovery events Measures recovery performance
Missing dependency rate Recovery packages missing required dependencies divided by packages audited, multiplied by 100% Identifies incomplete recovery packages

For example, if 95 out of 100 PLCs requiring backups have current, verified backups, backup coverage is 95%.

\[ \text{Backup coverage}=\frac{95}{100}\times100=95\\% \]

Define each KPI carefully. Backup coverage and backup currency measure different things, and neither alone proves that the restoration process works.

16. Interview questions and technical answers

1. What is the difference between a PLC backup and disaster recovery?

A PLC backup preserves the required program and configuration data. Disaster recovery includes identifying the failure, preparing compatible hardware and software, restoring the data, validating the system, and returning it to service safely.

2. Why is uploading the PLC not always sufficient?

The upload may not recover the original engineering project structure, comments, symbols, libraries, or all configuration information. The exact limitations depend on the PLC platform.

3. What is a golden backup?

A golden backup is a controlled, approved reference version of a defined system state. It should be associated with a known revision, verified configuration, and appropriate validation records.

4. What is the difference between RPO and RTO?

RPO defines the maximum acceptable loss of recent data or changes. RTO defines the target time for restoring the affected service.

5. Why should backups be stored independently from the engineering PC?

An independent copy protects against local disk failure, accidental deletion, theft, and some cybersecurity incidents. A copy that shares the same failure domain may be lost along with the original.

6. Does a checksum prove that a PLC backup is correct?

No. A checksum helps detect changes to a file relative to its recorded checksum. It does not establish that the project belongs to the correct machine, matches the approved revision, or functions correctly.

7. What must be checked after replacing a PLC CPU?

Verify CPU compatibility, firmware, hardware configuration, application revision, I/O mapping, communications, retained data, diagnostics, and machine functionality. Apply the required safety validation before release.

8. Why must retained data be considered separately?

Counters, recipes, calibration values, and other runtime values may not be included in a standard project archive. Restoring incorrect or outdated values can affect production, quality, and machine operation.

9. How should a PLC backup be handled after a cybersecurity incident?

Follow the incident-response process, preserve evidence, identify a trusted pre-incident backup, verify its integrity and provenance, restore in an approved environment, and obtain authorization before reconnecting to production.

10. What is the most important test of a backup system?

A controlled restoration test that demonstrates the backup, required dependencies, and recovery procedure can restore the intended system within the approved recovery objectives.

17. Final engineering principles

  • Maintain an editable engineering project whenever the platform supports it.
  • Back up before significant changes and after approved changes are released.
  • Preserve source and migrated projects separately.
  • Verify project identity, revision, integrity, and dependencies.
  • Store independent recovery copies with appropriate access controls.
  • Treat retained data and safety-system backups as distinct recovery requirements where applicable.
  • Test restoration periodically rather than relying on file existence.
  • Document recovery procedures so that another authorized engineer can execute them.
  • Measure recovery performance against defined RPO and RTO targets.
  • Release restored equipment only after the required engineering, functional, and safety checks.
