1. Purpose and scope

An HMI backup preserves the engineering project, configuration, and other required data needed to restore an operator interface after hardware failure, accidental modification, software corruption, replacement, or a cybersecurity incident.

An HMI is not merely a display. It may contain the operator's access to machine commands, alarms, recipes, production counts, maintenance screens, trends, and communication settings. Losing the HMI project can therefore affect both production recovery and the ability to operate equipment correctly.

The objective is to ensure that the HMI can be restored to a known, approved state using compatible hardware, software, configuration, and supporting data.

Common recovery scenarios include:

  • HMI panel failure requiring replacement.
  • Corrupted project or failed firmware update.
  • Accidental modification of screens, scripts, or device addresses.
  • Loss of the engineering PC or original project.
  • HMI replacement during obsolescence migration.
  • Loss of recipe or logging configuration.
  • Communication failure after a network or PLC change.
  • Cybersecurity incidents affecting the panel or engineering system.

Core principle: A backup file is not a proven recovery solution until its identity, integrity, dependencies, and restoration procedure have been verified.

3. What must be backed up?

A complete HMI recovery package may contain several independent items. Their availability depends on the HMI family, software version, storage method, and project design.

Backup item Contents Why it matters
Editable project Screens, objects, tags, and application configuration Allows engineering changes and restoration
Communication configuration PLC drivers, station settings, IP addresses, and port parameters Restores PLC connectivity
Screen resources Graphics, icons, fonts, and reusable objects Preserves screen appearance and readability
Scripts and macros Calculations, event actions, and custom behavior Restores functions beyond basic screen objects
Alarm configuration Alarm triggers, messages, priorities, and acknowledgement behavior Restores fault indication
Recipe configuration Recipe structures, device mapping, and transfer rules Preserves parameter handling
Logging configuration Sampling, storage, retention, and export settings Restores historical-data collection
Security configuration User roles, permissions, and protected functions Preserves authorized access controls
Firmware information Panel system version and compatibility details Supports compatible replacement
Hardware information Model number, ports, display characteristics, and options Identifies a suitable replacement panel
Runtime data Recipes, histories, counters, or stored values where required Supports data recovery when the data is not in the project archive
Documentation Screen lists, device mapping, network configuration, and test records Supports troubleshooting and validation
Dependencies Required engineering software, libraries, drivers, and licenses Allows the project to be opened and maintained

Do not assume that the editable project contains all runtime data. Historical alarms, recipe values, logged measurements, and user settings may require separate export or backup procedures.

The backup must preserve the relationship between the HMI project, its connected PLC, the machine, and the approved revision. A perfectly valid project for the wrong machine is still a bad recovery asset.

5. HMI backup methods

5.1 Original engineering-project backup

The preferred method is to preserve the original editable project maintained in the appropriate engineering software.

Procedure:

  1. Identify the HMI and its installed machine.
  2. Locate the latest approved project.
  3. Confirm the project model, revision, and software version.
  4. Compare the project with the installed configuration using approved methods.
  5. Save or archive a new revision without overwriting the released source.
  6. Include the required communication settings and project dependencies.
  7. Capture runtime data separately if it is needed for recovery.
  8. Record the backup location, revision, date, and responsible engineer.
  9. Verify that the archived project can be reopened in the required software.

This method normally provides better engineering traceability than relying exclusively on an upload from the panel.

5.2 Upload from the HMI

Uploading can help recover available project information when the original engineering project is missing.

However, an HMI upload is not guaranteed to reproduce the complete original editable project. Depending on the platform and protection settings, it may omit comments, reusable libraries, source resources, scripts, or other engineering information.

Before attempting an upload:

  • Confirm that the panel and software support the operation.
  • Verify that the correct HMI is selected.
  • Record the current model and firmware.
  • Check whether the upload can affect production operation.
  • Follow access-control and authorization procedures.
  • Preserve the resulting files as a recovered project, not automatically as the approved golden backup.

After uploading, compare the recovered information with the installed application and other available records.

5.3 Removable storage and runtime backup

Some HMIs support USB storage, SD cards, or other media for project transfer, data export, or backup.

The exact capabilities are model-specific. Removable storage may contain a project, recipes, logs, screenshots, or only selected data. Do not assume that one card contains everything needed for complete restoration.

Document:

  • Supported storage type and capacity.
  • Backup or export method.
  • Contents and revision.
  • Whether the media contains project data or runtime data.
  • Compatibility with the replacement panel.
  • Storage location and physical protection.
  • Required passwords or permissions, stored under approved security procedures.

5.4 Screenshots and documentation

Screenshots can preserve visual evidence of screen layouts, alarm messages, and settings. They do not replace the editable engineering project.

Use screenshots to supplement the backup, particularly when recovering an undocumented legacy HMI. Record the screen name, purpose, relevant PLC devices, and expected behavior.

A screenshot of a recipe screen cannot restore its recipe-transfer logic, device assignments, validation rules, or stored values. Humans keep inventing new ways to confuse a picture of a system with the system itself.

7. Backup frequency and triggers

The backup schedule should reflect equipment criticality, project change frequency, and the cost of losing HMI functionality.

Trigger Required backup action
New machine commissioning Create the initial approved project backup
Approved screen modification Save and archive the released project revision
PLC device-address change Back up the updated project and communication mapping
HMI replacement Preserve the old project and create a separate target project
Firmware update Preserve the pre-update state and verify the post-update state
Recipe modification Back up the configuration and required recipe data
Security or permission change Preserve the approved security configuration
Network modification Record and back up relevant communication settings
Engineering-PC replacement Verify that the project and required dependencies are recoverable
Cybersecurity incident Preserve evidence and recover only from a trusted source
Periodic maintenance audit Check backup currency, integrity, and recoverability

For critical equipment, a practical baseline is to create a backup after every approved engineering change and perform scheduled verification. The exact schedule should follow plant policy and the risk assessment.

8. HMI data integrity and version control

8.1 Backup validation levels

Validation level What it confirms Remaining limitation
File existence Expected backup files are present Files may be incomplete
File integrity Files match their recorded checksums Correctness is not proven
Project opening Engineering software can open the project Runtime behavior is not proven
Model compatibility Project supports the intended target panel Communication and functions still require testing
Revision verification Project matches the approved release Required runtime data may be missing
Restore test The recovery procedure works in the tested setup Untested field conditions may remain
Functional test Required HMI functions behave correctly Does not replace machine safety validation

A checksum such as SHA-256 can detect unexpected changes to a file after its checksum was recorded.

Approved project archive
        ↓
Calculate SHA-256 checksum
        ↓
Store checksum in backup manifest
        ↓
Retrieve archive during recovery
        ↓
Calculate checksum again
        ↓
Compare with recorded value
        ↓
Match: integrity check passes
Mismatch: investigate before use

A checksum cannot determine whether the backup is the latest approved project or whether it contains the correct machine configuration.

8.2 Revision-control procedure

Use a controlled revision identifier rather than relying on the file's modification date alone.

Example:

MACHINE_ID_HMI_REVISION_DATE
LINE1059_HMI01_R008_20261017

The example is illustrative. Use the plant's actual asset identifiers and document-control rules.

Each released revision should identify:

  • HMI model and machine.
  • Engineering software version.
  • Project revision.
  • Change or work-order reference.
  • Approval status.
  • Backup timestamp.
  • Integrity-check result.
  • Storage location.
  • Required runtime-data backup.
  • Verification status.

Preserve the original project and each required released revision. Do not overwrite the only known-good backup with an untested engineering change.

9. Storage strategy and cybersecurity

HMI backups should be protected against accidental deletion, hardware failure, unauthorized modification, and ransomware.

A useful baseline is the 3-2-1 backup principle:

  • Maintain at least three copies of important data.
  • Use at least two different storage types or platforms where practical.
  • Keep at least one copy off-site or otherwise isolated from the primary failure domain.

Example:

Primary engineering repository
        ↓
Independent backup repository
        ↓
Offline or isolated recovery copy

Three folders on one engineering PC are not three independent backups. If the PC fails or is compromised, all three may disappear together.

Recommended controls include:

  • Role-based access to approved project repositories.
  • Separate permissions for reading and modifying released backups.
  • Offline or isolated copies for critical systems.
  • Encryption where required by plant policy.
  • Controlled retention and deletion rules.
  • Audit records for changes to released projects.
  • Secure handling of passwords, certificates, and recovery credentials.
  • Malware checks and integrity verification according to approved procedures.

Do not expose HMI engineering systems directly to untrusted networks merely to simplify backup access. Recovery convenience must not undermine the plant's OT security controls.

10. HMI restoration procedure

Restoration must reinstate the correct application and required configuration without introducing unintended machine behavior.

10.1 Pre-restoration checklist

  • Identify the exact HMI and connected machine.
  • Determine the failure and required recovery scope.
  • Confirm the replacement panel model and compatibility.
  • Select the approved backup revision.
  • Verify project integrity and provenance.
  • Confirm the required engineering software and license.
  • Record firmware and communication settings.
  • Identify required recipes, logs, and other runtime data.
  • Confirm the safe-state and isolation requirements.
  • Obtain the required maintenance and production authorization.
  • Preserve diagnostic evidence when relevant.
  • Confirm that the recovery procedure will not cause unexpected machine startup.

10.2 Restoration sequence

  1. Diagnose the HMI failure and determine whether the panel, project, network, or PLC connection is responsible.
  2. Place the equipment in the approved state for restoration.
  3. Record the existing panel model, firmware, communication settings, and project identity where available.
  4. Retrieve and verify the approved backup.
  5. Install compatible replacement hardware if necessary.
  6. Install or access the required engineering software.
  7. Configure the target model and communication parameters.
  8. Transfer the project using the manufacturer's supported procedure.
  9. Restore separately backed-up runtime data where required and approved.
  10. Verify startup behavior, screen navigation, and communication.
  11. Test critical operator functions, alarms, recipes, and permissions.
  12. Complete required functional and safety-related verification.
  13. Obtain authorization before releasing the equipment.
  14. Update the backup register and preserve the final verified project.

The precise download and restoration steps depend on the HMI family. Some operations can restart the panel, overwrite an existing application, or alter settings. Follow the applicable manufacturer's documentation.

10.3 Post-restoration verification

Verify more than the presence of the home screen.

  • Correct panel model and project revision.
  • Correct PLC driver and communication settings.
  • Correct device addresses and displayed values.
  • Correct operator commands and numeric-entry limits.
  • Correct alarm indication, acknowledgement, and history behavior.
  • Correct recipe selection and transfer.
  • Correct trends, logging, and data retention where required.
  • Correct user permissions and protected functions.
  • Correct restart and power-recovery behavior.
  • Correct interaction with drives, robots, CNCs, and other connected equipment.
  • No unexplained communication or system errors.
  • Required machine safety verification completed under approved procedures.

An HMI is an interface to the control system. Testing the HMI does not independently prove that the PLC logic, safety system, or physical machine is safe.

11. Recovery scenarios

11.1 HMI hardware failure

Situation: The HMI panel fails to start or has a defective display or touch interface.

Recovery procedure:

  1. Confirm that the fault is actually in the HMI and not its power supply, wiring, or network connection.
  2. Record the panel model and installed configuration.
  3. Identify a compatible replacement.
  4. Retrieve the approved project and required runtime data.
  5. Install the replacement using approved electrical isolation procedures.
  6. Transfer the project and configure communication.
  7. Verify all critical screens and machine interfaces.
  8. Obtain release approval and update the installed-base record.

A replacement panel with the same screen size may still have different interfaces, firmware requirements, or software compatibility.

11.2 Corrupted HMI project

Situation: A project change causes missing screens, broken scripts, or unexpected operation.

Recovery procedure:

  • Preserve the current project and available diagnostic evidence.
  • Identify the last approved revision.
  • Compare the current revision with the released baseline.
  • Restore the approved revision under change-control procedures.
  • Verify communication, commands, alarms, and other affected functions.
  • Document the cause and corrective action.

Do not overwrite the only copy of the corrupted project before preserving it. It may contain evidence needed to identify the failure.

11.3 Lost engineering PC

Situation: The PC containing the HMI engineering software and project is unavailable.

Recovery procedure:

  1. Retrieve the project from the independent repository.
  2. Verify its integrity and revision.
  3. Install the required supported engineering software.
  4. Recover the necessary licenses, drivers, libraries, and dependencies through authorized channels.
  5. Confirm that the project opens.
  6. Verify access to the replacement HMI.
  7. Conduct the required transfer and functional checks.

A project archive alone may not be enough. The engineering software version, hardware descriptions, license requirements, and project dependencies can determine how quickly recovery is possible.

11.4 Cybersecurity incident

Situation: The HMI or engineering system may have been modified by unauthorized software or an attacker.

Recovery procedure:

  1. Follow the approved incident-response process.
  2. Coordinate with authorized OT/IT cybersecurity personnel.
  3. Preserve relevant logs and evidence.
  4. Identify a trusted backup from before the incident.
  5. Verify the backup's integrity and provenance.
  6. Restore in an approved, trusted environment.
  7. Validate the project and required communications.
  8. Reconnect the system only after the required security and engineering approvals.

Do not assume that the most recent backup is trustworthy. A recent copy can preserve unauthorized changes along with the legitimate project.

11.5 HMI obsolescence migration

Situation: A legacy HMI is being replaced with a newer generation.

Recovery and migration require separate source and target records.

  • Preserve the original editable project.
  • Record the source panel model, software version, and firmware.
  • Confirm the target panel's supported features.
  • Convert the project using the documented procedure.
  • Revalidate screens, communication, alarms, scripts, and recipes.
  • Test the migrated project on the target panel.
  • Retain the source project for rollback and historical troubleshooting.
  • Create a new approved backup after migration acceptance.

A converted project must not silently replace the original legacy project. The two serve different recovery purposes.

12. Common backup and restoration failures

Screens appear different Display resolution, font, or object compatibility changed Compare with approved layouts and correct the target project
Recipe values are missing Runtime data was not backed up separately Recover the approved recipe dataset
Alarm history is missing Historical records were not included in the project archive Restore from a supported separate data backup if available

Recovery is delayed Missing software, licenses, cables, or dependencies Improve the recovery package and test the procedure
Backup checksum fails File corruption or unexpected modification Retrieve a verified copy and investigate the discrepancy

13.3 Maintenance work-order integration

For a planned HMI modification or breakdown replacement:

  1. Identify the HMI tag and the connected PLC.
  2. Check the latest approved project revision.
  3. Create a pre-change backup where practical.
  4. Perform the authorized repair or project modification.
  5. Verify the required operator and communication functions.
  6. Save and archive the released project.
  7. Back up separately required runtime data.
  8. Update the asset register and link the change to the work order.
  9. Verify that the independent recovery copy is current.
  10. Record outstanding issues and obtain the required approval.

This creates a traceable relationship between the physical panel, the engineering project, the maintenance activity, and the recovery package.

14. Recovery drills and audit

14.1 Recovery drill

A recovery drill confirms that the HMI project, software, dependencies, and procedure can restore the required service.

  1. Select a suitable nonproduction panel or approved test environment.
  2. Retrieve a released backup from the controlled repository.
  3. Verify the manifest and file integrity.
  4. Confirm software and target-model compatibility.
  5. Follow the documented restoration procedure.
  6. Verify startup, screens, communications, alarms, and other required functions.
  7. Measure elapsed recovery time.
  8. Document missing dependencies and failures.
  9. Correct the procedure and backup package.
  10. Repeat the test when necessary.

Do not perform an experimental restoration on a live production panel without authorization and an approved recovery plan.

14.2 Audit checklist

  • All critical HMIs are included in the installed-base register.
  • Each HMI has an approved backup requirement.
  • The original editable project is preserved where available.
  • Backup revisions match approved engineering releases.
  • Required runtime data is backed up separately.
  • Engineering software and dependencies are documented.
  • Independent recovery copies are maintained.
  • Access control and retention rules are enforced.
  • Backup integrity is checked.
  • Restoration procedures are documented.
  • Restore tests are completed at the defined interval.
  • Recovery times are checked against approved targets.
  • HMI changes trigger the required backup updates.
  • Obsolete HMIs have documented migration and rollback plans.

15. Backup management KPIs

KPI Calculation Purpose
Backup coverage HMIs with required backups divided by HMIs requiring backups, multiplied by 100% Measures backup availability
Backup currency HMIs with current approved backups divided by HMIs requiring backups, multiplied by 100% Measures revision accuracy
Restore-test success Successful restore tests divided by completed restore tests, multiplied by 100% Measures demonstrated recoverability
Backup compliance Backups completed on time divided by backups scheduled, multiplied by 100% Measures process compliance
Mean recovery time Total measured recovery time divided by recovery events Measures recovery performance
Missing-dependency rate Packages missing required dependencies divided by packages audited, multiplied by 100% Identifies incomplete recovery packages

For example, if 48 of 50 required HMIs have current, verified backups:

\[ \text{Backup coverage}=\frac{48}{50}\times100=96\\% \]

Coverage alone does not prove recoverability. A complete program archive may still fail to restore because of missing software, incompatible firmware, unavailable licenses, or missing runtime data.

16. Interview questions and technical answers

1. What is the difference between an HMI project backup and runtime data backup?

The project backup preserves the engineering configuration, screens, objects, and supported application logic. Runtime data backup preserves required data generated or stored during operation, such as recipes, historical alarms, and logged measurements.

2. Why is uploading an HMI not always sufficient?

The upload may not contain the complete editable engineering project, original resources, comments, libraries, or all runtime data. Limitations depend on the panel and engineering software.

3. What is a golden backup?

A golden backup is the controlled, approved reference version of the HMI project for a defined machine state. It should have a known revision, compatibility information, and verification records.

4. What should be checked before downloading a project to a replacement HMI?

Verify the target model, project revision, software compatibility, communication settings, required runtime data, and approved transfer procedure. Confirm that the operation will not cause unexpected machine behavior.

5. Why should alarm history and recipes be backed up separately?

They may be stored in runtime storage rather than the editable project. Restoring the project alone may therefore restore the configuration without restoring the historical records or required recipe values.

6. What is the difference between RPO and RTO?

RPO defines the maximum acceptable loss of recent changes or data. RTO defines the target time for restoring the affected service.

7. Why should the original HMI project be retained after an obsolescence migration?

It supports rollback, historical troubleshooting, comparison with the converted project, and recovery of the original configuration.

8. How can HMI backup integrity be verified?

Use checksums, revision records, project-opening checks, compatibility checks, and controlled restoration tests. Each validates a different aspect of the backup.

9. Does a successful HMI restoration prove that the machine is safe?

No. HMI restoration must be followed by the required functional checks and separate verification of relevant machine safety functions under approved procedures.

10. What is the most important proof that an HMI backup is useful?

A controlled restoration test demonstrating that the correct project and required dependencies can restore the required functions within the approved recovery objectives.

17. Final engineering principles

  • Preserve the editable HMI project and its dependencies.
  • Back up separately stored runtime data when required.
  • Keep released backups distinct from working and converted projects.
  • Verify model compatibility, revision, integrity, and communication settings.
  • Maintain independent recovery copies with appropriate security controls.
  • Test restoration instead of relying only on file existence.
  • Record backups and changes against the machine asset and maintenance work order.
  • Include software availability and licensing in recovery planning.
  • Verify operator functions and machine interfaces before production release.
  • Maintain a documented rollback procedure for replacement and migration work.
