1. Purpose and Scope

Industrial network devices connect PLCs, HMIs, SCADA servers, CNC machines, robots, vision systems, industrial PCs, drives, remote I/O, and enterprise systems. Their configuration determines how devices communicate, how traffic moves, which systems can access each other, and how the network recovers from faults.

Network device backup and disaster recovery is the process of preserving configuration, firmware information, network topology, security settings, and required recovery files so that a failed, reset, damaged, or obsolete device can be restored to an approved operational state.

Typical devices include:

  • Managed and unmanaged industrial Ethernet switches.
  • Industrial routers and Layer 3 switches.
  • Firewalls and industrial security gateways.
  • Wireless access points and wireless bridges.
  • VPN gateways and remote-access devices.
  • Media converters and fiber-optic network devices.
  • Serial-to-Ethernet gateways.
  • Protocol gateways, such as Modbus TCP-to-serial gateways.
  • Network management appliances and controllers.
  • Time-synchronization devices, where network configuration is critical.

Examples of industrial network equipment include Siemens SCALANCE, Rockwell Stratix, Cisco industrial networking equipment, Moxa switches and gateways, Hirschmann industrial switches, and Phoenix Contact networking products.

The exact backup procedure depends on the manufacturer's platform, firmware version, management method, and device capabilities.

This is a simplified architecture. Actual plants may use ring topologies, redundant links, separate safety networks, multiple VLANs, routed cells, wireless segments, or vendor-specific real-time Ethernet networks.

Network devices may store configuration for:

  • IP addresses and subnet masks.
  • VLANs and trunk ports.
  • Routing and gateway settings.
  • Managed switch port assignments.
  • Link aggregation and redundancy.
  • Spanning Tree Protocol settings.
  • Industrial ring protocols.
  • Quality of Service (QoS).
  • Multicast filtering and IGMP snooping.
  • Firewall rules and access-control lists.
  • DHCP, DNS, and time-synchronization services.
  • SNMP monitoring.
  • User accounts and authentication.
  • Certificates, VPNs, and security policies.
  • Industrial protocol gateways.

A backup must preserve the settings needed to reconstruct the intended network behavior, not simply the device's IP address.

4. What Must Be Backed Up?

4.1 Device Identification

Record the information needed to identify and replace the device.

  • Asset ID and plant location.
  • Manufacturer and exact model.
  • Serial number and hardware revision.
  • Firmware version.
  • Bootloader version, if applicable.
  • License and feature entitlement details.
  • Power supply and accessory requirements.
  • Available ports, port types, and module configuration.
  • Warranty and vendor support details.
  • Device role in the network.

A model name alone may be insufficient. Different hardware revisions can have different firmware compatibility, interfaces, or supported features.

4.2 Configuration Files

Preserve the complete configuration supported by the device.

Typical items include:

  • Device hostname.
  • Management IP address and subnet.
  • Default gateway and routing configuration.
  • VLAN IDs and VLAN membership.
  • Access and trunk port settings.
  • Port speed, duplex, and negotiation settings where configured.
  • Link aggregation groups.
  • STP/RSTP configuration.
  • Ring-redundancy configuration.
  • QoS policies.
  • IGMP snooping and multicast settings.
  • Static routes.
  • DHCP relay or server configuration, where applicable.
  • DNS and NTP settings.
  • Port mirroring or diagnostic settings.
  • SNMP and syslog configuration.
  • Firewall rules and ACLs.
  • NAT configuration, if used.
  • VPN settings and supported certificate dependencies.
  • User roles and authentication configuration.
  • Industrial protocol gateway mappings.

Not every device supports all these features. Record only the relevant settings for the specific platform.

4.3 Network Topology and Port Mapping

A configuration file may not explain the physical purpose of every port. Maintain a separate port map.

Device port Connected equipment Purpose Important configuration
Port 1 PLC Machine control network Assigned industrial VLAN
Port 2 HMI Operator interface Approved cell VLAN
Port 3 Robot controller Robot communication Approved IP and port policy
Port 4 Vision IPC Inspection and results Required application traffic
Port 5 Upstream switch Backbone uplink Trunk and redundancy settings
Port 6 Spare port Reserved maintenance use Disabled or restricted according to policy

These are illustrative entries. Use the actual plant wiring and approved network configuration.

Maintain:

  • Physical port labels.
  • Cable and patch-panel identifiers.
  • Fiber type and connector details.
  • SFP or transceiver models.
  • Redundant-link connections.
  • Ring direction or ring-port assignments.
  • Network cabinet and switch location.
  • Connected-device IP addresses and names.

A correct configuration loaded onto the wrong physical connections can still leave a machine network nonfunctional.

4.4 Security Configuration

Preserve security configuration using approved and secure methods.

  • Administrator and operator roles.
  • Authentication and authorization settings.
  • RADIUS, TACACS+, LDAP, or other supported authentication dependencies.
  • ACLs and firewall rules.
  • Port-security settings.
  • Management access restrictions.
  • SNMP version and access controls.
  • SSH and HTTPS configuration.
  • Certificates and required private keys.
  • VPN configuration and cryptographic dependencies.
  • Approved firmware and security baseline.
  • Audit logs where required.
  • Configuration of secure management protocols.

Do not store plaintext passwords, private keys, or shared secrets in ordinary backup folders. Some device exports deliberately omit secrets or store them in encrypted form. Record the recovery process and ensure the required credentials can be retrieved through the approved secret-management system.

4.5 Firmware and Software Information

Maintain:

  • Current firmware version.
  • Approved firmware version.
  • Firmware image and cryptographic verification information, where available.
  • Bootloader version if relevant.
  • Firmware release notes.
  • Hardware compatibility requirements.
  • License or feature activation requirements.
  • Upgrade and downgrade restrictions.
  • Required intermediate firmware versions.
  • Known issues affecting industrial protocols or redundancy.

Do not automatically install the newest firmware during recovery. New firmware may alter supported features, protocol behavior, security settings, or compatibility with the existing industrial network.

Use the version approved for the plant's hardware and application.

5. Types of Network Device Backup

Backup type What it preserves Main limitation

Plain-text configuration Readable settings on supported platforms May expose sensitive information
Binary configuration backup Vendor-specific configuration representation May require matching software or hardware

A readable configuration report and a native device backup serve different purposes. The native file may support restoration, while the report helps engineers understand and validate what is being restored.

6. Running Configuration vs. Startup Configuration

Some network platforms distinguish between active settings and settings saved for the next restart.

  • Running configuration: Settings currently active in the device's operational memory.
  • Startup configuration: Persistent settings loaded during startup.
  • Candidate configuration: Proposed changes that have not yet been committed, on platforms that support candidate-based configuration.

The exact terminology depends on the vendor.

A common failure is to change a port's VLAN or redundancy settings, observe that communication works, and forget to save the configuration. After a power interruption, the device may return to the previous settings.

Recommended practice:

  1. Capture the approved baseline before changes.
  2. Make the authorized change.
  3. Validate connectivity and required behavior.
  4. Save or commit the configuration using the platform's supported method.
  5. Export a new backup.
  6. Record the change, reason, approval, and timestamp.
  7. Verify that the saved configuration matches the intended active configuration.

Do not assume that every device saves configuration changes automatically.

7. Backup Methods and Transfer Protocols

The available method depends on the manufacturer, firmware, management system, and plant security requirements.

7.1 Local Export

A technician connects through an approved console, web interface, or management tool and exports the configuration to controlled storage.

Advantages:

  • Straightforward for isolated devices.
  • Useful during commissioning or maintenance.
  • Can support a controlled pre-change backup.

Limitations:

  • Manual steps can be missed.
  • File naming and version control may be inconsistent.
  • It may be difficult to maintain frequent backups across many devices.

7.2 Centralized Network Management

A supported management platform may collect configurations from many devices, maintain revisions, compare changes, and support restoration.

Advantages:

  • Centralized backup visibility.
  • Change tracking.
  • Standardized naming and retention.
  • Reduced manual effort.
  • Easier identification of configuration drift.

Limitations:

  • The management system becomes another critical dependency.
  • Device support and licensing vary.
  • Credentials and access to the management platform require strong protection.
  • Centralized collection must not violate OT network segmentation.

7.3 File Transfer

Depending on the device, supported protocols may include:

  • SFTP or SCP for encrypted file transfer.
  • HTTPS-based export or management APIs.
  • TFTP on legacy or restricted devices.
  • Vendor-specific transfer mechanisms.
  • Removable storage for devices that support local backup media.

Prefer authenticated and encrypted transfer methods where supported.

TFTP does not provide the same authentication and encryption protections as secure transfer protocols. If it is required by a legacy device, restrict it to an approved isolated management segment and use the plant's compensating controls.

Never assume that a device supports a protocol simply because another model from the same manufacturer does.

8. Network Device Backup Strategy

8.1 Backup Design

Industrial Network Device
        ↓
Native Configuration Export
        ↓
Validation and Version Identification
        ↓
Controlled Backup Repository
        ↓
Independent Protected Copy
        ↓
Integrity Verification
        ↓
Periodic Restore Test
        ↓
Approved Recovery Procedure

The process should produce a usable, identifiable backup rather than a folder of files with names such as backup_new_final2.

8.2 The 3-2-1 Principle

Maintain:

  • Three copies of important configuration data, including the operational copy.
  • Two different storage systems or media where practical.
  • One independent off-site or isolated copy.

For OT systems, the independent copy may be an offline backup or an immutable repository approved by plant cybersecurity.

Network configuration files are small, so storage capacity is rarely the main problem. Version control, secure access, correct device identification, and tested restoration matter much more.

8.3 Protect the Repository

  • Restrict write and delete access.
  • Separate backup-administration permissions from ordinary network-management permissions where practical.
  • Keep a protected copy that a compromised network device cannot modify.
  • Encrypt sensitive backups in storage and transit.
  • Verify file integrity.
  • Retain approved historical versions.
  • Log backup and restore activities.
  • Test recovery using a suitable spare or isolated test environment.
  • Avoid using shared administrator credentials across all devices.

9. Backup Scheduling and Change Management

Backup frequency depends on device criticality and how often its configuration changes.

Event or condition Recommended action
New device commissioning Capture a complete approved baseline
Network configuration change Export a new backup after validation
Firmware upgrade Back up first and capture the resulting approved configuration
VLAN or routing change Back up and update network documentation
Security policy change Back up affected settings and record approval
Switch replacement Preserve the failed device's configuration if possible and validate compatibility
Network redesign Capture affected configurations and updated topology
Routine schedule Run periodic backups according to criticality and policy
Suspected unauthorized change Preserve current state and logs before corrective action where feasible
Disaster recovery test Record the tested version and the restoration result

For highly critical devices, event-triggered backups may be more important than a calendar-only schedule.

A backup captured before a firmware update is useful, but the post-update configuration must also be saved if the upgrade changes or migrates configuration data.

10. Network Device Disaster Recovery Procedure

Step 1: Assess the Impact

Determine which systems have lost communication.

Check:

  • PLC-to-HMI communication.
  • Robot and CNC communication.
  • Vision and traceability data paths.
  • SCADA and historian connectivity.
  • Upstream network connections.
  • Redundant links or ring status.
  • Power and link indicators.
  • Whether the failure affects a single device or an entire network segment.

Use approved machine and network safety procedures. Do not make uncontrolled changes to a live network simply to see what happens.

Step 2: Protect Production

  • Inform the relevant production and maintenance teams.
  • Determine the effect on machine operation and quality.
  • Apply the approved safe-state or contingency procedure.
  • Isolate suspected compromised devices where required.
  • Preserve diagnostic information before resetting or replacing hardware.
  • Avoid interrupting healthy redundant paths without authorization.

A network switch may carry control traffic for multiple machines. Replacing or restarting it without understanding its role can expand a local fault into a line-wide outage.

Step 3: Identify the Failed Device

Record:

  • Asset ID and model.
  • Serial number and hardware revision.
  • Firmware version if accessible.
  • Power and status indicators.
  • Connected ports and observed link states.
  • Error logs and recent configuration changes.
  • Network topology and redundancy role.
  • Last known-good configuration backup.

Determine whether the problem is caused by the device itself, its power supply, fiber or copper link, connected equipment, configuration, firmware, or upstream infrastructure.

Step 4: Select the Recovery Method

  • Configuration corruption: Restore a verified configuration using the supported method.
  • Device hardware failure: Replace with a compatible unit and restore the approved configuration.
  • Firmware problem: Use the approved recovery or downgrade procedure.
  • Network loop: Contain the loop using the approved troubleshooting procedure and verify redundancy behavior.
  • Firewall or routing error: Restore or correct the relevant approved policies and routes.
  • Cybersecurity incident: Isolate the affected area and follow incident-response procedures before restoring configurations.

A configuration restore is not a substitute for diagnosing a faulty power supply, damaged fiber, or failed switch hardware.

Step 5: Validate the Replacement

Check:

  • Exact model and hardware compatibility.
  • Supported firmware version.
  • License or feature entitlement.
  • Port count and port type.
  • SFP or transceiver compatibility.
  • Power requirements.
  • Redundancy protocol support.
  • VLAN and routing feature support.
  • Security configuration requirements.

A physically similar switch may not support the same ring protocol, VLAN features, management options, or configuration syntax.

Step 6: Restore the Configuration

  1. Verify the identity and timestamp of the backup.
  2. Confirm that it belongs to the correct device or approved equivalent.
  3. Check firmware and hardware compatibility.
  4. Restore using the manufacturer's supported method.
  5. Apply the approved device identity and management settings.
  6. Verify persistent configuration storage.
  7. Review security settings and credentials.
  8. Compare the resulting configuration against the approved baseline.
  9. Document any required deviations.

Some platforms require configuration conversion when moving between firmware versions or hardware families. Use the vendor-supported conversion procedure instead of assuming that the file can be loaded directly.

Step 7: Reconnect and Test

  • Connect management access first where practical.
  • Verify management reachability.
  • Confirm VLAN membership and trunk settings.
  • Check routing and firewall policies.
  • Validate link aggregation and redundancy.
  • Check spanning-tree or ring-recovery status.
  • Test required communication paths.
  • Confirm that only intended ports are active.
  • Verify logging and monitoring.
  • Check that no unauthorized or duplicate device identity exists.

Reconnect the production network according to the approved change and commissioning procedure.

Step 8: Confirm Production Function

Verify the actual process:

  • PLC communication and remote I/O status.
  • HMI and SCADA visibility.
  • Robot and CNC network connectivity.
  • Vision, barcode, and traceability communications.
  • Alarm and event reporting.
  • Redundancy operation where required.
  • Production data flow and timestamps.

Do not declare the network recovered merely because every switch responds to a ping.

Step 9: Close the Incident

  • Capture the restored configuration.
  • Update the approved backup baseline.
  • Record hardware and firmware changes.
  • Document the root cause and corrective actions.
  • Review whether backup frequency or monitoring should change.
  • Confirm that the recovery procedure remains accurate.

12. Configuration Comparison and Change Control

A configuration backup becomes more valuable when it can be compared against the current device state.

Useful comparisons include:

  • Current configuration versus last approved backup.
  • Configuration before and after a firmware upgrade.
  • Configuration before and after a switch replacement.
  • Port assignments versus the approved port map.
  • VLAN membership versus the network design.
  • Firewall rules versus the approved security baseline.
  • Firmware version versus the plant-approved version.

Configuration differences should be reviewed in context. Some values, such as counters, timestamps, or dynamic neighbor information, may change during normal operation and do not necessarily indicate unauthorized changes.

Use a controlled change record containing:

  • Change request or work-order number.
  • Device asset ID.
  • Reason for change.
  • Previous and new configuration versions.
  • Person performing the change.
  • Required approvals.
  • Functional test results.
  • Rollback procedure.
  • Final backup location.

15. Recovery Objectives and Criticality

RTO and RPO should be assigned based on production impact, available redundancy, and the difficulty of restoring the network.

  • RTO: Target time within which network service must be restored.
  • RPO: Maximum acceptable loss of configuration changes measured as time.

For network configurations, the RPO may effectively be tied to the last approved configuration change rather than the last scheduled backup. If an important VLAN change occurred after the previous backup, restoring that older file may reproduce the wrong network design.

Device category Potential impact Recovery planning focus
Noncritical access switch Limited equipment may lose connectivity Maintain a verified configuration and compatible spare
Line-level managed switch Multiple machine devices may lose communication Prioritize recovery and validate VLANs and redundancy
Core or distribution switch Multiple production areas may be affected Maintain high-quality backups and tested replacement procedures
Industrial firewall Required traffic may be blocked or exposed Preserve approved rules and validate security before release
Protocol gateway Communication between different interfaces may stop Preserve protocol mappings and serial/network parameters
Redundancy manager or ring device Network resilience may be reduced Restore redundancy behavior and confirm stable operation

Redundancy can keep a network operating during a hardware failure, but it does not replace backups. An incorrect configuration can propagate across redundant devices and affect the entire network.

16. Restore Testing and Audit

16.1 Restore-Test Checklist

  • Device inventory and model are documented.
  • Backup belongs to the correct device or validated equivalent.
  • Firmware compatibility is confirmed.
  • Configuration export is readable or accepted by the recovery tool.
  • Integrity checks pass where supported.
  • Credentials and required security dependencies are available securely.
  • Recovery procedure is current.
  • A spare or suitable test environment is available where required.
  • Configuration restore completes successfully.
  • VLANs, trunks, routing, and port settings are validated.
  • Redundancy behavior is tested where applicable.
  • Required PLC, HMI, SCADA, and IPC communications are verified.
  • Firewall and security rules are checked.
  • Monitoring and event logging operate correctly.
  • Actual recovery duration is recorded.
  • Final configuration and test results are saved.

16.2 Useful KPIs

17. OT Cybersecurity Precautions

Industrial network equipment is a security boundary as well as a connectivity component.

  • Restrict management access to approved network segments.
  • Use unique, authorized administrator credentials.
  • Prefer secure management protocols supported by the device.
  • Disable unused ports and services according to the approved baseline.
  • Protect configuration backups from unauthorized access.
  • Treat configuration files as potentially sensitive.
  • Validate firmware integrity and compatibility before installation.
  • Preserve logs during suspected cyber incidents.
  • Do not restore a known-compromised configuration without reviewing it.
  • Avoid uncontrolled remote access to industrial devices.
  • Verify firewall and ACL behavior after restoration.
  • Follow change-control procedures for production network modifications.
  • Keep an independent, protected copy of recovery data.

Configuration files can reveal network topology, device addresses, security policies, and sometimes credential-related information. They should be handled as controlled operational assets.

18. Common Mistakes

  1. Backing up only the switch's IP address instead of the full supported configuration.
  2. Forgetting to save running changes to persistent storage.
  3. Restoring a configuration to an incompatible model or firmware version.
  4. Ignoring VLANs, trunk ports, routing, and redundancy settings.
  5. Treating screenshots as a replacement for a native configuration backup.
  6. Keeping backups only on the network device or a connected management PC.
  7. Assuming a redundant switch automatically contains a valid independent recovery configuration.
  8. Ignoring physical port mapping and cable topology.
  9. Using insecure transfer methods without appropriate isolation and compensating controls.
  10. Reconnecting a restored device before validating its security and identity.
  11. Replacing a firewall without testing the approved traffic policy.
  12. Declaring success after a ping test without verifying industrial application communication.

19. Practical Industrial Example

A managed industrial Ethernet switch connects a PLC, HMI, robot controller, vision IPC, and an upstream plant switch. Its configuration includes VLAN membership, a trunk uplink, QoS, and ring-redundancy settings.

The switch fails after a power event.

A replacement switch is installed, but the PLC and HMI cannot communicate. The replacement's default configuration places all ports in a default VLAN and does not contain the original redundancy settings.

A correct recovery procedure is:

  1. Confirm the production impact and apply the approved machine contingency.
  2. Identify the failed switch and its approved replacement.
  3. Retrieve the latest verified configuration and network port map.
  4. Confirm model, firmware, port, and redundancy compatibility.
  5. Restore the configuration using the supported method.
  6. Verify VLAN membership, trunk settings, and ring configuration.
  7. Confirm management access and security policies.
  8. Reconnect the required network links according to the approved topology.
  9. Verify PLC, HMI, robot, vision, and upstream communications.
  10. Check redundancy and network stability.
  11. Save the restored configuration and document the incident.

The lesson is simple: a network device is restored only when its approved configuration and required communication paths work correctly, not merely when its status LEDs turn green.

20. Interview Questions and Answers

Q1. Why should industrial network devices be backed up?

To restore approved configuration after hardware failure, accidental reset, configuration corruption, unauthorized changes, or replacement.

Q2. What is the difference between running and startup configuration?

Running configuration represents the currently active settings on platforms that distinguish it from persistent configuration. Startup configuration is loaded during startup. Unsaved changes may be lost after a restart.

Q3. What should be included in a managed switch backup?

The supported configuration, firmware and hardware information, VLANs, port assignments, trunks, redundancy, management settings, security configuration, and recovery documentation.

Q4. Is an unmanaged switch configuration normally backed up?

Many unmanaged switches have little or no configurable state. Inventory, port mapping, hardware details, and replacement compatibility are still important.

Q5. Why is firmware compatibility important during recovery?

Different firmware versions or hardware models may support different features or configuration formats. Incompatible combinations can prevent restoration or change network behavior.

Q6. What is configuration drift?

Configuration drift is the difference between the actual device configuration and its approved baseline.

Q7. Why is a port map necessary if a configuration file exists?

The configuration may describe logical ports without identifying their physical cable destinations or machine connections.

Q8. Why is TFTP a concern?

TFTP does not provide the same authentication and encryption protections as secure transfer protocols. Where legacy requirements make it necessary, its use should be restricted and controlled.

Q9. Does network redundancy eliminate the need for backups?

No. Redundancy can maintain service after selected failures, but it cannot guarantee recovery from configuration corruption, unauthorized changes, or loss of all relevant devices.

Q10. What should be tested after replacing a managed switch?

Management access, VLANs, trunks, routing if applicable, security policies, redundancy, monitoring, and required communication between industrial systems.

Q11. Why should a firewall backup receive special protection?

It can contain sensitive network architecture and security policy information, and unauthorized changes can either interrupt production or expose industrial systems.

Q12. What is the most important test of a network backup?

A controlled restore followed by verification that the required network paths, security policies, and industrial communications operate correctly.

21. Final Principles

  • Maintain a verified configuration backup for every critical managed network device.
  • Record firmware, hardware revision, network topology, port mapping, and security dependencies.
  • Save configuration changes after approval and functional validation.
  • Keep protected copies outside the device and its immediate management environment.
  • Validate model and firmware compatibility before restoration.
  • Test the restored configuration against actual industrial communication requirements.
  • Update documentation and backup baselines after successful changes.
  • Treat network recovery as a controlled production restoration activity, not a file-copying exercise.
