1. Purpose and Scope

Testing is the systematic verification that a recovered industrial device, application, or machine has been restored correctly and can perform its required functions within approved operating limits.

In industrial backup and disaster recovery, testing is the evidence that recovery has worked. Installing software, restoring a PLC program, matching firmware, or downloading a configuration does not prove that the complete machine is ready for operation.

For example, a PLC may enter RUN mode after restoration, but its remote I/O, HMI communication, VFD commands, interlocks, or production data collection may still be incorrect. Testing must detect these failures before the equipment is returned to production.

The objective is to demonstrate that the recovered system matches its approved configuration, performs its intended functions, and satisfies the required safety, quality, and operational acceptance criteria.

This topic covers:

  • Testing principles and test levels.
  • Recovery verification and acceptance criteria.
  • PLC, HMI, VFD, servo, CNC, robot, vision, and network testing.
  • Static checks, functional tests, and integrated testing.
  • Safety and quality verification.
  • Fault diagnosis and regression testing.
  • Test documentation, evidence, and sign-off.
  • Practical industrial recovery scenarios and checklists.

2. Why Testing Is Necessary After Recovery

Recovery can introduce errors even when each individual recovery step appears successful.

Typical causes include:

  • Incorrect backup selected.
  • Incompatible firmware or engineering software.
  • Missing configuration or parameters.
  • Incorrect hardware assignments.
  • Communication drivers not installed correctly.
  • Wrong IP address or device name.
  • Changed default settings.
  • Missing libraries or application dependencies.
  • Incorrect license or runtime configuration.
  • Unverified safety or quality settings.
  • Unintended modifications during troubleshooting.

Testing identifies these problems before they affect production.

2.1 Examples of Recovery Failures

Recovered component Possible hidden problem Required verification
PLC Program runs but an I/O module is missing Hardware and I/O checks
HMI Screens load but commands reference incorrect tags Tag and command verification
VFD Drive communicates but uses the wrong command source Parameter and control-source checks
Servo Drive is ready but feedback scaling is incorrect Feedback and motion validation
CNC Control starts but machine-specific settings are incorrect Machine-builder checks and approved functional tests
Robot Program loads but tool or work frames differ Frame, calibration, and controlled motion verification
Vision system Inspection job loads but the inspection result has changed Reference-part and inspection validation
Network switch Management access works but an industrial network path is unavailable Connectivity and topology checks
SCADA Screens open but historical data is not recorded Tag, alarm, and database tests

3. Testing vs. Related Activities

Activity Purpose
Verification Checks whether the recovered system matches specified requirements
Validation Checks whether the system is suitable for its intended operational purpose
Functional testing Checks whether specific functions work as required
Integration testing Checks whether connected components work together
Regression testing Checks whether previously working functions remain correct after changes
Acceptance testing Determines whether predefined acceptance criteria are satisfied
Commissioning Establishes that equipment is installed, configured, and ready for its intended service
Safety validation Provides documented evidence that applicable safety requirements are satisfied

These activities overlap, but they are not identical. A device can pass an isolated functional test and still fail an integrated machine test.

For example, a VFD may operate correctly from its local keypad but fail to accept commands from the PLC. The drive's basic function works, but the machine's intended control path does not.

4. Testing Principles

A good recovery test process follows several principles.

4.1 Define Acceptance Criteria Before Testing

Acceptance criteria specify the expected result and the conditions under which the result is considered acceptable.

Examples:

  • PLC firmware matches the approved version.
  • Required I/O modules are healthy and correctly identified.
  • HMI displays the correct PLC values.
  • Drive communication is established without relevant faults.
  • Safety functions pass their prescribed validation.
  • Vision inspection correctly classifies approved reference samples.
  • SCADA records the expected data in the intended database.
  • The machine completes its approved functional test sequence.

Avoid vague criteria such as machine working fine. Criteria should identify what must work and how the result will be demonstrated.

4.2 Test From Simple to Complex

Start with identity and configuration checks before performing integrated operation.

A common progression is:

Device Identity and Version Checks
             ↓
Static Configuration Checks
             ↓
Power-Up and Diagnostic Checks
             ↓
Individual Function Tests
             ↓
Communication and Integration Tests
             ↓
Controlled Machine Functional Tests
             ↓
Safety and Quality Validation
             ↓
Acceptance and Release Decision

The actual order must follow the machine's approved procedures. Safety-critical verification may need to occur before any motion or production-related testing.

4.3 Use a Known Baseline

Compare the recovered system against the approved backup, configuration record, commissioning data, and acceptance criteria.

A system that merely behaves similarly to the previous system has not necessarily been restored correctly.

4.4 Preserve Test Evidence

Record actual results, not assumptions. Evidence may include diagnostic logs, software version records, parameter comparisons, test sheets, screenshots, and approved measurements.

4.5 Do Not Bypass Faults to Pass a Test

A test should identify whether the recovered system meets its requirements. Disabling an interlock, ignoring an alarm, or forcing an output can conceal the exact defect the test is supposed to find.

Any temporary test configuration must follow an approved procedure, be controlled, and be restored and verified before release.

5. Test Planning and Preparation

Before starting tests, define the test scope and prepare the equipment.

5.1 Establish the Test Scope

Identify:

  • Machine and device IDs.
  • Recovery reason.
  • Equipment replaced or restored.
  • Firmware and software versions.
  • Configuration and application versions.
  • Affected interfaces and connected equipment.
  • Safety-related functions.
  • Quality-critical functions.
  • Required production tests.
  • Acceptance criteria and approval requirements.

The scope should reflect the recovery impact. Replacing a network switch may require extensive communication and integration checks, while restoring a single non-critical workstation setting may require a narrower test plan.

5.2 Prepare Test Resources

Depending on the system, resources may include:

  • Approved recovery test procedure.
  • Engineering workstation.
  • Device diagnostic tools.
  • Calibrated measuring instruments.
  • Approved reference parts or test signals.
  • Network diagnostic tools.
  • Test cables and communication adapters.
  • Required PPE and safety equipment.
  • Test data and expected values.
  • Access to relevant backup and configuration records.

Check the calibration status of measuring instruments whenever measurements are used to demonstrate acceptance.

5.3 Confirm Safe Test Conditions

Before testing:

  • Confirm the required machine state.
  • Coordinate with production and affected teams.
  • Identify hazardous energy and motion risks.
  • Apply applicable isolation and safe-work procedures.
  • Confirm that guards and safety systems are in the required state.
  • Identify who is authorized to conduct each test.
  • Establish the permitted test boundaries.
  • Confirm emergency response arrangements.

Testing must not create an uncontrolled machine movement or expose personnel to hazardous energy.

6. Levels of Testing

6.1 Level 1: Identity and Version Verification

Confirm that the recovered equipment matches the intended configuration.

Check:

  • Device model and hardware revision.
  • Firmware version.
  • Engineering software version.
  • Application program version.
  • Configuration revision.
  • Installed options and licenses.
  • Required libraries and drivers.

This level catches basic compatibility errors before deeper tests begin.

6.2 Level 2: Static Configuration Verification

Compare the restored settings against the approved baseline without relying solely on machine operation.

Examples:

  • PLC hardware configuration.
  • I/O assignments.
  • Device addresses.
  • VFD parameters.
  • HMI tag mappings.
  • Robot frame records.
  • CNC machine data.
  • Switch VLAN and port settings.

A comparison should distinguish approved differences from unexplained deviations.

6.3 Level 3: Power-Up and Diagnostic Testing

Check whether devices start correctly and report an acceptable status.

Examples:

  • PLC reaches its required operating state.
  • HMI runtime starts without critical errors.
  • VFD reports an expected ready status.
  • Network devices establish their required links.
  • SCADA services start correctly.
  • Vision sensors initialize without relevant faults.

A normal startup is necessary but not sufficient for acceptance.

6.4 Level 4: Individual Functional Testing

Test each affected device or function independently where possible.

Examples:

  • Verify PLC inputs and outputs.
  • Verify HMI indications.
  • Verify VFD status and control modes.
  • Verify servo feedback.
  • Verify robot diagnostics.
  • Verify scanner reading.
  • Verify vision inspection.
  • Verify database connectivity.

6.5 Level 5: Integration Testing

Verify that the restored components communicate and function together.

Examples:

  • PLC to remote I/O.
  • PLC to HMI.
  • PLC to VFD.
  • PLC to servo drive.
  • PLC to robot controller.
  • Vision system to PLC.
  • Scanner to PLC or industrial PC.
  • SCADA to PLC and database.

6.6 Level 6: End-to-End Functional Testing

Test the complete intended function from input to output or from data acquisition to final record.

For example, a production test bench may require:

  1. A valid start request.
  2. Correct interlock evaluation.
  3. Correct actuator sequence.
  4. Correct measurement acquisition.
  5. Correct result evaluation.
  6. Correct pass/fail indication.
  7. Correct result storage and traceability.

The test must use approved conditions and reference values.

7. PLC Testing After Recovery

PLC testing verifies that the controller, application, I/O, and communication configuration work as intended.

7.1 Static Checks

  • Confirm CPU model and firmware.
  • Confirm the approved program revision.
  • Check hardware configuration.
  • Verify I/O module status.
  • Review diagnostic buffers and relevant alarms.
  • Compare critical configuration settings.
  • Confirm the intended operating mode.
  • Verify communication device configuration.

7.2 Functional Checks

  • Verify required inputs change correctly.
  • Verify expected output status under approved test conditions.
  • Confirm sequence transitions.
  • Verify timers, counters, and state logic where relevant.
  • Confirm alarm generation and reset behavior.
  • Check communication with connected devices.
  • Confirm that restored data and retained values are handled correctly.

7.3 Input and Output Verification

I/O verification must be performed safely and according to the approved procedure.

For inputs, compare the physical condition or approved test stimulus with the PLC's reported state.

For outputs, verify the command state and the corresponding physical response where it is safe and permitted.

A PLC output bit changing state does not prove that the field device moved. The output module, wiring, interlocks, power supply, actuator, and feedback path may still be faulty.

7.4 PLC Recovery Acceptance

A PLC should not be accepted solely because it enters RUN mode. Verify the required program, hardware, I/O, communications, diagnostics, interlocks, and application behavior.

8. HMI and SCADA Testing

8.1 HMI Testing

Verify:

  • Correct project and runtime versions.
  • Successful startup.
  • Correct communication paths.
  • Accurate tag values.
  • Correct button and command behavior.
  • Alarm indications and acknowledgements.
  • Recipe and setpoint behavior.
  • User permissions.
  • Screen navigation.
  • Required data logging.

Operator commands must be tested under controlled conditions. A button that changes color when pressed is not proof that the corresponding machine command reached the correct device.

8.2 SCADA Testing

Verify:

  • Data-source connectivity.
  • Tag quality and expected values.
  • Alarm generation and acknowledgement.
  • Historical data collection.
  • Trend display.
  • Database connectivity.
  • User authentication and access control.
  • Required communication redundancy.
  • Time synchronization where relevant.
  • Application behavior after restart.

8.3 Data Integrity Testing

Where data is stored, verify that the correct data reaches the intended destination.

For example, a recovered test bench may need to store measurement values, machine identifiers, timestamps, and pass/fail results.

Check that records are associated with the correct test cycle and that timestamps, data types, and required fields are valid.

A successful database connection does not prove that the application is writing correct records.

9. VFD and Servo Testing

Drive testing must consider both electrical behavior and the control path used by the machine.

9.1 VFD Tests

  • Verify the exact drive model and firmware.
  • Check motor data and approved parameters.
  • Confirm control and speed-reference sources.
  • Check communication status.
  • Verify relevant alarms and diagnostics.
  • Perform prescribed start/stop checks.
  • Confirm direction and speed behavior where authorized.
  • Verify required feedback and interlocks.
  • Check the relevant protection functions.

9.2 Servo Tests

  • Verify drive, motor, and feedback compatibility.
  • Check encoder or feedback status.
  • Verify scaling and gearing configuration.
  • Confirm communication with the motion controller.
  • Verify required motion limits and homing configuration.
  • Perform approved low-risk functional checks.
  • Confirm position feedback and expected response.
  • Verify applicable safety functions.

9.3 Important Distinction

A drive that runs from its local keypad may still fail in automatic mode because the PLC command source, communication mapping, or interlocks are incorrect.

Testing should verify the actual control path required by the machine, not only local device operation.

10. CNC and Robot Testing

10.1 CNC Testing

Following recovery, verify:

  • Correct control system version.
  • Correct machine-builder software and configuration.
  • Required axis and spindle data.
  • Servo and feedback status.
  • Tool and machine data where applicable.
  • Machine-specific functions.
  • Communication with peripheral devices.
  • Required alarms and interlocks.
  • Applicable measurement and accuracy checks.

Use the machine builder's approved recovery and acceptance procedures. Do not run a production program simply to see whether the control appears operational.

10.2 Robot Testing

Verify:

  • Correct controller and system software.
  • Robot model and installed options.
  • Application program version.
  • Tool and work frames.
  • Calibration or mastering status.
  • External-axis configuration, where applicable.
  • Fieldbus communication.
  • Safety configuration and required validation.
  • Controlled movement and application behavior.

Robot motion tests must follow the approved safety procedure, with the required operating mode, personnel positioning, speed limits, guarding, and supervision.

11. Vision, Scanner, and Network Testing

11.1 Vision System Testing

Verify:

  • Correct device and firmware.
  • Correct inspection job.
  • Camera and lighting configuration.
  • Calibration status.
  • Trigger and communication behavior.
  • Reference-part results.
  • Pass/fail classification.
  • Data transfer to the controller or application.

Use approved reference samples and acceptance criteria. A live image alone does not prove inspection accuracy.

11.2 Scanner Testing

Verify:

  • Correct scanner configuration.
  • Successful acquisition of known test codes or position references.
  • Correct decoded data or position values.
  • Communication with the receiving device.
  • Expected behavior for invalid or missing readings.
  • Correct handling of timeouts and diagnostics.

11.3 Network Device Testing

Verify:

  • Device identity and firmware.
  • Port status and link state.
  • IP addressing and device names.
  • Required VLANs and port assignments.
  • Communication between intended endpoints.
  • Redundancy and recovery behavior where applicable.
  • Management access and security configuration.
  • Required industrial communication protocols.

Network tests should confirm the intended communication path. A successful ping to one device does not prove that all required industrial protocols, I/O connections, or application services are functioning.

12. Safety Testing and Validation

Safety-related functions require specific procedures and acceptance criteria.

Depending on the machine, testing may involve:

  • Emergency stop function.
  • Guard interlocks.
  • Safety door monitoring.
  • Light curtains or other protective devices.
  • Safe torque off.
  • Safety PLC logic.
  • Robot safety zones.
  • Safe speed or position functions.
  • Required reset and restart behavior.

The exact test scope depends on the safety design, risk assessment, applicable standards, and changes made during recovery.

12.1 Safety Testing Rules

  • Use authorized personnel and approved procedures.
  • Do not bypass safety devices to obtain a passing result.
  • Confirm the correct hardware and configuration.
  • Test each affected safety function as required.
  • Verify that faults and resets behave correctly.
  • Record the result and required evidence.
  • Revalidate affected safety functions after relevant changes.
  • Do not release the machine if required safety verification remains incomplete.

A backup file can restore a safety configuration, but it cannot prove that the physical wiring, installed hardware, or complete safety function is correct.

13. Quality and Process Validation

Testing must also confirm that the recovered system produces the intended quality result.

Examples include:

  • Correct measurement scaling.
  • Correct pass/fail thresholds.
  • Correct inspection recipe.
  • Correct motor or actuator behavior.
  • Correct torque or pressure values.
  • Correct product identification.
  • Correct data association and traceability.
  • Correct measurement result storage.

For a test bench, compare the recovered system's readings against approved reference standards or test samples.

If calibration is required, perform it according to the relevant procedure. Do not compensate for an unknown configuration error by adjusting quality thresholds until the results appear acceptable.

14. Regression Testing

Regression testing checks that previously working functions remain correct after a recovery or change.

A recovery may fix one fault while introducing another. For example, restoring a PLC project may recover the primary sequence but alter a communication setting used by a secondary station.

14.1 Regression Test Selection

Include:

  • Functions directly affected by the recovery.
  • Functions that depend on the restored device.
  • Safety and interlock functions affected by the change.
  • Critical production sequences.
  • Alarm and diagnostic behavior.
  • Communication and data logging.
  • Quality-critical measurement and inspection functions.

The scope should be risk-based. A change affecting a central PLC or network switch may require broader regression testing than a change isolated to one non-critical device.

15. Fault Injection and Negative Testing

Negative testing checks how the system responds to defined abnormal conditions. Fault injection deliberately introduces a fault or simulated fault to verify expected behavior.

Examples include:

  • Simulating a communication timeout using an approved test method.
  • Applying a defined invalid test code to a scanner.
  • Verifying the alarm response to a missing device.
  • Testing the approved response to invalid measurement data.
  • Confirming a system detects an unavailable data source.

Fault injection must only be performed under an approved test plan and in a controlled environment. Do not deliberately interrupt production communications, remove safety devices, force hazardous outputs, or induce uncontrolled motion.

For some industrial systems, simulated inputs or test modes are more appropriate than introducing a physical fault.

16. Test Result Classification

Use defined result categories so that acceptance decisions are consistent.

Result Meaning Required action
Pass Acceptance criteria satisfied Record evidence
Fail Acceptance criteria not satisfied Diagnose and correct the fault
Blocked Test cannot be completed because a prerequisite is missing Resolve the prerequisite
Not tested Test was not performed Assess impact and complete or formally disposition
Conditional pass Limited acceptance under an explicitly approved condition Record restrictions and approval

A conditional pass must not be used to conceal an unresolved safety-critical or quality-critical failure. Some failures require the system to remain unavailable until corrected.

17. Testing Failure Diagnosis

When a test fails, record the observed condition before making changes.

17.1 Diagnostic Sequence

Test Failure Observed
          ↓
Record Actual Result and Evidence
          ↓
Identify the Affected Component
          ↓
Compare Against Approved Baseline
          ↓
Check Hardware, Firmware, Software, and Configuration
          ↓
Determine the Root Cause
          ↓
Apply an Approved Correction
          ↓
Repeat the Failed Test
          ↓
Perform Relevant Regression Tests
          ↓
Record Final Result

17.2 Common Root-Cause Categories

  • Incorrect backup or project version.
  • Hardware incompatibility.
  • Firmware mismatch.
  • Software or driver dependency.
  • Configuration or parameter mismatch.
  • Network or communication fault.
  • Electrical or mechanical fault.
  • Incorrect test setup.
  • Calibration or measurement issue.
  • Unrecorded change.
  • Missing prerequisite or license.

17.3 Retesting

After correction:

  1. Repeat the failed test.
  2. Confirm that the original fault is resolved.
  3. Check related functions that may have been affected.
  4. Repeat required regression tests.
  5. Record the correction and new evidence.
  6. Obtain any required reapproval.

A test should not be marked as passed based on an assumption that the corrective action probably worked.

18. Test Documentation

A test record establishes what was tested, how it was tested, and whether the result met the acceptance criteria.

18.1 Recommended Test Record

18.2 Evidence Quality

Useful evidence is:

  • Traceable to the correct machine and device.
  • Recorded at the time of testing.
  • Clear enough for another technician to interpret.
  • Associated with an exact test case.
  • Linked to the relevant configuration and software versions.
  • Preserved according to the plant's retention policy.

Screenshots alone are often insufficient if they do not show the device identity, test conditions, or expected result.

19. Practical Example: Testing a Recovered Production Test Bench

A PLC CPU has been replaced, its approved program and configuration restored, and the engineering software installed. The test bench must be verified before production resumes.

Phase 1: Static Verification

Confirm the controller identity, firmware, program version, hardware configuration, I/O assignments, and approved parameter records.

Phase 2: Startup Verification

Check controller status, device diagnostics, HMI startup, drive readiness, communication status, and relevant alarms.

Phase 3: I/O Verification

Verify the required sensor inputs, actuator commands, and feedback signals using the approved test procedure.

Phase 4: Functional Verification

Run the approved sequence in the required safe test mode. Confirm correct interlocks, timing, actuator response, and sequence transitions.

Phase 5: Measurement Verification

Use the approved reference method to verify that measurement acquisition, scaling, result evaluation, and pass/fail classification are correct.

Phase 6: Data Verification

Confirm that the test result is associated with the correct machine or product identifier and that required values and timestamps are stored correctly.

Phase 7: Safety and Quality Validation

Complete the required safety checks and quality acceptance tests, including any checks affected by the recovery.

Phase 8: Documentation and Acceptance

Record all results, resolve failures, complete required regression tests, and obtain the required approval.

The test bench is ready for release only when its required acceptance criteria have been satisfied and the responsible authority has approved the return to service.

21. Testing Checklist

Before Testing

  • Define the recovery scope and acceptance criteria.
  • Identify the affected devices and machine.
  • Confirm approved hardware, firmware, software, and configuration versions.
  • Prepare the required test procedure and evidence records.
  • Verify test equipment and calibration status where applicable.
  • Confirm the required safe state and work authorization.
  • Identify affected safety and quality functions.
  • Notify relevant production and maintenance personnel.

During Testing

  • Verify device identity and configuration.
  • Check startup and diagnostic status.
  • Test individual functions.
  • Verify communication and integration.
  • Test affected safety functions according to approved procedures.
  • Verify quality-critical measurements and results.
  • Record actual results and evidence.
  • Record and investigate failures.
  • Avoid uncontrolled forcing, bypasses, or fault injection.

After Testing

  • Repeat failed tests after approved corrections.
  • Perform relevant regression tests.
  • Confirm all mandatory acceptance criteria are satisfied.
  • Resolve or formally disposition outstanding deviations.
  • Complete required safety and quality validation.
  • Update recovery and configuration records.
  • Obtain required acceptance and release approvals.
  • Preserve the test evidence for future audits and recovery.

22. Interview Questions and Answers

Q1. Why is testing required after backup restoration?

Restoration can introduce incompatibilities or configuration errors. Testing provides evidence that the recovered system meets its operational requirements.

Q2. What is the difference between verification and validation?

Verification checks whether specified requirements have been met. Validation checks whether the system is suitable for its intended use.

Q3. What is integration testing?

Integration testing verifies that connected devices and applications operate together correctly.

Q4. What is regression testing?

Regression testing checks that existing functions remain correct after a change or recovery.

Q5. Is a PLC in RUN mode proof of successful recovery?

No. The program, hardware configuration, I/O, communication, interlocks, and required application behavior must also be verified.

Q6. Why is I/O testing important?

It verifies the relationship between physical signals, I/O modules, controller logic, output commands, and field-device response.

Q7. What is an acceptance criterion?

It is a defined condition or measurable result that determines whether a test passes.

Q8. Why should actual results be recorded?

Actual results provide evidence for troubleshooting, auditability, acceptance decisions, and future recovery.

Q9. What should happen after a failed test?

Capture the evidence, investigate the cause, apply an approved correction, repeat the failed test, and perform relevant regression tests.

Q10. Why is safety validation separate from normal functional testing?

Safety functions have specific requirements and risks. Normal device operation does not prove that protective functions satisfy their required safety behavior.

Q11. What is end-to-end testing?

It verifies a complete function across all relevant system components, from the initiating input to the expected output or recorded result.

Q12. When is a recovered system ready for production?

When the required acceptance criteria have been satisfied, mandatory failures are resolved, required validation is complete, and the authorized release decision has been made.

23. Final Principles

  • Recovery is incomplete until the required tests demonstrate acceptable operation.
  • Define acceptance criteria before testing.
  • Test identity, configuration, individual functions, communications, and integrated behavior.
  • Include safety and quality verification according to the recovery scope.
  • Use approved test methods and controlled operating conditions.
  • Record actual results and preserve evidence.
  • Diagnose failures instead of repeatedly changing settings without a clear cause.
  • Retest corrected functions and perform relevant regression testing.
  • Do not treat a successful download, startup, or communication check as proof of complete recovery.
  • Obtain the required acceptance and release approval before returning equipment to production.
