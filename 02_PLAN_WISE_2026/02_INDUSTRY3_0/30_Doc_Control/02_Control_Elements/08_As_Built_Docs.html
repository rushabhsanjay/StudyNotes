1. Purpose and Scope

As-built documentation records the actual installed, connected, configured, and commissioned condition of a machine, electrical system, automation system, or industrial facility after installation and approved modifications.

The essential principle is that as-built documents must describe what is physically and functionally installed, not merely what was originally designed or intended to be installed.

In industrial maintenance, the distinction matters because equipment changes throughout its life. A technician may replace a PLC module, reroute a cable, change a sensor, modify a robot interface, or retrofit a drive. If the documents are not updated, the next technician inherits a system whose records describe a machine that no longer exists.

This topic covers:

  • As-designed, as-installed, as-commissioned, and as-built states.
  • Electrical, mechanical, pneumatic, hydraulic, and automation documentation.
  • PLC, HMI, CNC, robot, VFD, servo, and industrial network configurations.
  • Redlines, verification, approval, revision control, and document release.
  • Asset-level traceability and maintenance troubleshooting.
  • Practical registers, checklists, examples, and interview questions.

2. Essential Terminology

Term Meaning
As-designed The configuration defined by the approved design
As-installed The physical arrangement actually installed at the site
As-commissioned The configuration verified during commissioning and functional testing
As-built The controlled documentation updated to represent the actual accepted configuration
Redline drawing A drawing marked to record a proposed or actual field change before formal document revision
Field modification A change made at the installation or operating site
Design intent The intended function or arrangement specified by the design
Configuration baseline The approved reference state of a system at a defined point in time
Engineering change A controlled change to equipment, design, software, hardware, or process
Commissioning record Evidence that installation and functional checks were performed
I/O list A record of PLC or control-system inputs and outputs and their assignments
Cable schedule A record of cable identifiers, endpoints, types, and related details
Software backup A saved version of a software project or device configuration
Configuration deviation A difference between the documented configuration and the actual or approved configuration
Document owner The role accountable for the accuracy and control of a document

An as-built drawing is not simply a drawing with handwritten corrections. It is the result of a controlled process that verifies the actual configuration, incorporates authorized changes, and releases the updated record.

3. Why As-Built Documentation Matters

3.1 Maintenance troubleshooting

A technician investigating a failed sensor needs to know its actual terminal, cable route, PLC address, and interconnection.

If the drawing shows the original installation, troubleshooting may follow the wrong circuit and waste time or create additional faults.

3.2 Electrical safety

Accurate drawings help identify supplies, isolation points, control circuits, protective devices, and interconnected equipment.

However, drawings do not replace approved isolation procedures, lockout/tagout requirements, or verification of the absence of hazardous energy.

3.3 PLC and automation reliability

An accurate I/O list, network diagram, and controller configuration help engineers distinguish between a hardware failure, wiring error, addressing problem, and software issue.

3.4 Production recovery

After a major failure, maintenance may need to restore a known-good program or parameter set. The correct backup must match the installed hardware, firmware, machine configuration, and approved application.

3.5 Quality and traceability

Test-bed configurations, measurement channels, calibration interfaces, and process settings may influence the validity of test results. Incorrect documentation can make it difficult to determine whether a system was configured correctly when a particular product was tested.

3.6 Lifecycle and future modifications

As-built records support retrofits, spare-parts planning, obsolescence management, safety assessments, energy audits, and future engineering work.

4. The Difference Between Design and As-Built

Aspect As-designed As-built
Purpose Defines the intended system Records the actual accepted system
Timing Before or during implementation After installation and relevant changes are verified
Hardware Planned components Components actually installed
Wiring Intended connections Verified actual connections
PLC I/O Planned assignments Actual approved assignments
Network Planned topology and addresses Verified installed topology and configuration
Mechanical layout Intended arrangement Actual installed arrangement
Software Intended program or configuration Verified approved program or configuration
Deviations May not include field changes Incorporates authorized deviations and changes
Maintenance use Design reference Primary configuration reference, subject to document scope and status

The as-built state must not silently legitimize an unauthorized modification. If the physical installation differs from the approved design, the difference must be assessed and authorized through the applicable engineering-change process before the final records are released.

5. As-Built Documentation Lifecycle

Approved design released
    ↓
Equipment installed
    ↓
Installation inspected and tested
    ↓
Field deviations identified
    ↓
Redlines and change records prepared
    ↓
Engineering and safety reviews completed
    ↓
Required modifications authorized and implemented
    ↓
Actual configuration verified
    ↓
As-built documents updated
    ↓
Documents reviewed and approved
    ↓
Controlled revision released
    ↓
Old versions withdrawn from current use
    ↓
Records linked to the equipment asset

Not every project follows the same sequence. For example, a minor modification on an operating machine may use a local engineering-change workflow, while a new production line may require formal handover and commissioning packages.

The governing principle remains the same: document the verified state, obtain the required approvals, and maintain traceability.

6. What Must Be Included in As-Built Documentation?

The exact package depends on the machine, project, risk, and organizational requirements.

6.1 Electrical documentation

  • Electrical schematics and circuit diagrams.
  • Panel layout and component arrangement.
  • Terminal plans and terminal schedules.
  • Cable schedules and cable identification.
  • Power distribution and control-circuit details.
  • Protective devices and earthing arrangements.
  • Safety relay or safety-controller connections.
  • Motor connections and drive interfaces.
  • Updated wire numbers and device tags.
  • Relevant electrical test and inspection records.

6.2 Mechanical documentation

  • Assembly and general arrangement drawings.
  • Installed component and part identification.
  • Mechanical interfaces and mounting arrangements.
  • Pneumatic and hydraulic circuit diagrams.
  • Actual sensor and actuator locations.
  • Guarding and access arrangements.
  • Relevant dimensions and approved deviations.
  • Updated bills of materials where required.

6.3 PLC and automation documentation

  • PLC hardware configuration.
  • Rack, slot, module, and channel assignments.
  • I/O list and signal descriptions.
  • Network topology and device addresses.
  • Communication mappings and interface details.
  • Approved PLC project and revision identification.
  • HMI screen, tag, and alarm configuration.
  • Safety-system documentation.
  • Relevant software and firmware versions.
  • Backup identification and restoration requirements.

6.4 CNC, robot, servo, and drive documentation

  • Installed controller and drive models.
  • Relevant firmware and software versions.
  • Approved machine and robot interface details.
  • Drive and servo configuration records.
  • Motor and feedback-device details.
  • Relevant tool, axis, or machine configuration data.
  • Robot external-axis and peripheral interfaces where applicable.
  • Approved parameter backups and program baselines.
  • Applicable safety and commissioning records.

6.5 Industrial network documentation

  • Network topology.
  • Switch and gateway identification.
  • IP addresses, subnet information, and VLAN assignments where applicable.
  • PLC, HMI, CNC, robot, drive, and PC endpoints.
  • Communication protocols and relevant ports.
  • Redundancy arrangements.
  • Approved firewall or access-control configuration references.
  • Backup and recovery information.
  • Relevant cybersecurity restrictions.

Sensitive credentials, passwords, and secret keys should not be embedded in ordinary drawings or broadly distributed as-built packages. They should be managed through approved secure systems.

7. Redline Drawings and Field Markups

A redline records a difference discovered or implemented in the field before the formal controlled document has been updated.

Redlines may use colored annotations, revision clouds, handwritten notes, digital markups, or a controlled change form. The specific method depends on the organization's procedure.

7.1 Example

An installed photoelectric sensor is relocated to improve detection reliability. The cable route and PLC input assignment also change.

The original drawing shows the sensor at the previous location.

The redline should identify:

  • Original sensor location.
  • Actual sensor location.
  • Cable route or cable identifier changes.
  • Relevant terminal and I/O changes.
  • Reason for the change.
  • Change authorization reference.
  • Person recording the change and date.
  • Verification status.
  • Required follow-up documentation.

7.2 Redline limitations

A redline is not automatically an approved as-built drawing.

It is a temporary or intermediate record whose authority depends on the applicable procedure. It must not be used to bypass engineering approval, electrical safety requirements, or required validation.

7.3 Redline closure

A redline is closed when the required engineering review, implementation verification, formal drawing update, approval, and release steps are complete.

The organization should track unresolved redlines so they do not remain indefinitely as the only record of important changes.

8. Verification of the Actual Installed Condition

As-built accuracy requires more than copying information from an old drawing.

Verification should compare the documentation against the physical installation and, where relevant, the actual software and device configuration.

8.1 Physical verification

  • Confirm installed equipment and model numbers.
  • Verify component tags and locations.
  • Check cable and terminal identifiers.
  • Confirm circuit connections against approved requirements.
  • Check actual network device locations and connections.
  • Confirm mechanical and pneumatic interfaces.
  • Verify relevant protective and safety-system arrangements.

8.2 Functional verification

Where applicable, confirm that:

  • Inputs respond to the intended field devices.
  • Outputs operate the intended actuators.
  • HMI tags correspond to the correct signals.
  • Alarms and interlocks behave as intended.
  • Drive and servo interfaces match the approved design.
  • Communication paths operate correctly.
  • Required safety functions pass their specified validation.
  • Test results and commissioning evidence are recorded.

Functional verification must use approved test methods and must not bypass safety functions to make a system appear operational.

8.3 Software and configuration verification

Compare the saved project or parameter file against the approved baseline and, using appropriate tools, the installed system.

Record relevant differences and determine whether they are authorized.

A project file existing on a maintenance computer does not prove that it matches the running PLC, CNC, robot, or drive.

9. PLC As-Built Documentation

PLC documentation is especially important because a small hardware or addressing change can affect multiple machine functions.

9.1 Hardware configuration

Record relevant details such as:

  • Controller family and catalog number.
  • Firmware revision.
  • Rack or chassis arrangement.
  • Module type and slot.
  • I/O channel assignments.
  • Communication modules.
  • Network interfaces.
  • Power supplies and relevant redundancy arrangements.
  • Safety-controller or safety-I/O configuration where applicable.

9.2 I/O list

A useful I/O record may include:

Field Example
Asset H7 test-bed
PLC PLC-01
Module Local rack input module
Channel Input channel 03
Tag PS_HYD_001
Description Hydraulic pressure switch
Signal type Digital input
Field location Hydraulic power unit
Electrical reference Drawing and terminal reference
Status Approved installed configuration

The values above are illustrative. Actual addresses, signal types, and terminal numbers must be verified against the installed equipment.

9.3 Program baseline

The as-built package should identify the approved program revision and its associated controller and hardware configuration.

Depending on the system, record:

  • Project filename and unique identifier.
  • Approved revision or release identifier.
  • Controller type and firmware.
  • Applicable engineering-change reference.
  • Relevant communication configuration.
  • Date and responsible approver.
  • Backup location and integrity information.
  • Known restrictions or dependencies.

Avoid treating a timestamp alone as a reliable revision identifier. Files may be copied, restored, or modified without a meaningful timestamp change.

10. HMI and SCADA As-Built Documentation

HMI and SCADA documentation must reflect the actual relationship between operator displays and the underlying control system.

Record, where applicable:

  • Screen and navigation structure.
  • Tag names and PLC address mappings.
  • Alarm definitions and priorities.
  • Alarm acknowledgements and reset behavior.
  • Trend configurations.
  • Data-logging and historian mappings.
  • Communication drivers and endpoints.
  • User roles and access-control arrangements.
  • Server, client, and runtime versions.
  • Relevant redundancy and recovery arrangements.

If a PLC tag is renamed or an address is changed, related HMI screens, alarms, historian tags, reports, and external integrations may also require updates.

A PLC drawing can be correct while the HMI configuration is wrong. As-built control must cover the complete relevant system, not just the most visible component.

11. CNC, Robot, Servo, and VFD As-Built Records

11.1 CNC machines

Maintain applicable records for:

  • CNC model and software version.
  • Machine-builder configuration.
  • Axis and drive arrangements.
  • I/O interfaces.
  • Tool and machine configuration references.
  • Approved parameter backups.
  • Relevant machine-specific programs and recovery procedures.
  • Applicable calibration and acceptance records.

Machine parameters and offsets can influence accuracy and safe operation. Do not replace them with generic values or assume that a file from another machine is compatible.

11.2 Industrial robots

Record relevant information about:

  • Robot model and controller.
  • Robot and external-axis configuration.
  • Tool and work-object references where applicable.
  • PLC communication and I/O mappings.
  • End-of-arm tooling interfaces.
  • Safety-zone and interlock arrangements.
  • Approved program baselines.
  • Relevant calibration and commissioning records.

Changes to robot frames, payload data, external axes, or safety-related configuration can affect actual motion. The documentation must correspond to the verified installed setup.

11.3 VFD and servo systems

Record relevant details for:

  • Drive model and firmware.
  • Motor identification and ratings.
  • Control mode.
  • Feedback-device type.
  • Communication and I/O assignments.
  • Relevant parameter sets.
  • Fault-response configuration.
  • Safety-related functions where applicable.
  • Commissioning and validation evidence.

A backup is useful only when its applicability and compatibility are established.

12. Network and OT Configuration As-Built Records

Industrial networks often change when machines are retrofitted, controllers are replaced, or new monitoring systems are added.

As-built network documentation should identify:

  • Installed devices and their network interfaces.
  • Physical and logical topology.
  • IP addresses and relevant network segments.
  • Switch ports and uplinks where required.
  • Communication paths and protocol dependencies.
  • Redundant connections and failover arrangements.
  • Relevant access-control boundaries.
  • Approved remote-access paths.
  • Configuration backup locations.
  • Responsible owners and change references.

If a PLC, HMI, or industrial PC is moved to another switch port or subnet, update the relevant network records after verification.

Do not publish credentials or other sensitive security information in general-purpose network drawings. Use approved secure storage and access controls.

13. Engineering Change and As-Built Updates

As-built documentation is closely connected to engineering change management.

A modification is not fully documented merely because the hardware works after installation.

The change process should determine which records are affected, who must approve them, how the modified system will be verified, and when the revised documents will be released.

13.1 Example: Replacing a PLC I/O module

A discontinued module is replaced with a compatible successor.

The change may affect:

  • Hardware configuration.
  • Module catalog number.
  • Slot and channel mapping.
  • Electrical schematic.
  • Terminal schedule.
  • PLC project.
  • I/O list.
  • Spare-parts record.
  • Firmware compatibility.
  • Commissioning and validation records.
  • Maintenance procedures.

The exact scope depends on the replacement and its compatibility assessment.

13.2 Change-to-document relationship

Engineering change approved
    ↓
Affected documents identified
    ↓
Modification implemented
    ↓
Actual configuration verified
    ↓
Affected drawings and configuration records updated
    ↓
Required testing and approval completed
    ↓
As-built revision released
    ↓
Old revisions withdrawn from current use
    ↓
Asset documentation register updated

The change reference should connect the physical modification, test evidence, approved software baseline, and revised documents.

14. As-Built Document Register

A document register provides traceability and helps maintenance locate the right information for the right asset.

Recommended fields include:

Field Purpose
Asset ID Identifies the machine or system
Document ID Unique document identifier
Document title Describes the document
Document type Drawing, I/O list, software baseline, network diagram, or other type
Current revision Latest approved revision
Document status Draft, approved, released, or another defined status
Applicable asset or scope Defines where the document applies
Last verification date Records the latest verification activity where applicable
Change reference Links the document to an approved modification
Approval reference Identifies required approval evidence
Repository location Identifies the controlled storage location
Document owner Identifies the responsible role
Related documents Links associated drawings and configuration records
Remarks or restrictions Records relevant limitations or unresolved issues

For software baselines, additional fields may include controller model, firmware version, file identifier, checksum, and backup location.

15. Practical Example: Updating a Test-Bed After a Retrofit

Assume a test-bed has an existing PLC, a pressure sensor, a VFD, and an HMI. A retrofit replaces the sensor and changes the PLC input assignment. The HMI alarm mapping is also modified.

The equipment runs successfully after the work, but the original drawings and backup files remain unchanged.

Problems created

  • The electrical drawing points to the old terminal assignment.
  • The I/O list identifies the previous signal mapping.
  • The HMI documentation does not reflect the updated alarm mapping.
  • The backup may not represent the installed program.
  • Future troubleshooting may follow an incorrect signal path.

Correct closeout

  1. Confirm that the retrofit was authorized.
  2. Record the installed sensor, wiring, and PLC input assignment.
  3. Verify the physical wiring and relevant signal behavior.
  4. Update the electrical drawing and I/O list.
  5. Update and verify the HMI tag and alarm configuration.
  6. Identify and preserve the approved PLC and HMI project baselines.
  7. Record the relevant controller and device versions.
  8. Complete required functional and safety checks.
  9. Obtain required review and approval.
  10. Release the revised as-built documents.
  11. Update the asset register and backup references.
  12. Withdraw obsolete documents from current use.

The objective is not merely to make the machine work today. It is to make tomorrow's maintenance work possible without guessing what somebody changed.

16. As-Built Documentation and Machine Knowledge Systems

For a maintenance organization, as-built records are a core component of machine knowledge management.

A useful asset-level structure may be:

Machine Asset
    ↓
Mechanical and Electrical Drawings
    ↓
PLC / HMI / CNC / Robot / Drive Configuration
    ↓
Network and Communication Records
    ↓
Safety and Interlock Documentation
    ↓
Commissioning and Verification Evidence
    ↓
Approved Change History
    ↓
Maintenance Procedures and Troubleshooting Records
    ↓
Spare Parts and Obsolescence Information

This structure can support a searchable maintenance knowledge base and connect technical documentation with CMMS or SAP asset records.

For example, a technician investigating a failed analog input should be able to trace the asset to its current electrical schematic, field instrument, terminal, PLC module and channel, scaling configuration, and relevant maintenance history.

The relationship between these records is often more valuable than any individual document.

17. Digital Document Control and Industry 4.0

As-built records can be integrated into digital maintenance workflows.

17.1 Practical applications

  • Search documents by equipment tag or SAP functional location.
  • Link current drawings to work orders.
  • Track engineering changes and document revisions.
  • Associate PLC backups with the correct controller and machine.
  • Monitor missing as-built documents through Power BI.
  • Use Power Automate for approval reminders or overdue-document notifications.
  • Maintain controlled repository links rather than distributing uncontrolled file copies.
  • Track documentation completeness during machine handover.

17.2 Example completeness indicators

A maintenance dashboard could monitor:

  • Percentage of critical assets with approved electrical drawings.
  • Percentage of PLC-controlled assets with verified current backups.
  • Number of open redlines.
  • Number of overdue as-built updates.
  • Percentage of critical assets with current network documentation.
  • Number of assets with unresolved configuration discrepancies.

These indicators measure documentation control, not necessarily the technical correctness of every drawing. Sampling and field verification remain necessary.

18. Common Mistakes

Mistake Consequence Correct approach
Treating the original design as the as-built record Field changes remain undocumented Verify and update actual conditions
Updating drawings without checking the installation Incorrect records become formally released Perform appropriate physical verification
Recording unauthorized changes as accepted facts Safety and design requirements may be bypassed Assess and authorize changes through the proper process
Updating drawings but not PLC or HMI records Different layers of the system become inconsistent Review all affected documents and configurations
Saving a backup without asset identification Wrong files may be restored Link baselines to the exact asset and configuration
Leaving redlines open indefinitely Temporary notes become the de facto documentation Track closure and release the controlled revision
Failing to withdraw previous revisions Technicians may use obsolete instructions Apply revision and obsolete-document controls
Ignoring network changes Troubleshooting and cybersecurity records become unreliable Update verified network records
Storing credentials in drawings Sensitive information becomes widely exposed Use approved secure credential management
Failing to retain commissioning evidence The basis for acceptance becomes unclear Preserve required verification and approval records

19. Practical As-Built Verification Checklist

Design and change control

  • Relevant engineering changes are approved.
  • Deviations are identified and resolved or formally controlled.
  • Affected documents and configurations are identified.
  • The required technical and safety reviews are completed.

Physical installation

  • Installed components match the recorded configuration.
  • Equipment tags and model numbers are verified.
  • Wiring, terminals, and cable identifiers are checked.
  • Mechanical, pneumatic, and hydraulic changes are recorded.
  • Network connections and addresses are verified where applicable.

Automation and software

  • PLC hardware and I/O assignments are documented.
  • HMI and SCADA mappings are checked.
  • CNC, robot, drive, and servo configurations are identified where applicable.
  • Approved software baselines are linked to the correct assets.
  • Relevant firmware and compatibility information is recorded.
  • Required functional and safety validation is completed.

Document release

  • Redlines are resolved or formally tracked.
  • As-built revisions are reviewed and approved.
  • Revision history and change references are updated.
  • Obsolete documents are withdrawn from current use.
  • Controlled repository links point to the correct revision.
  • Required historical records are preserved.

Maintenance handover

  • Current documents are accessible at the point of use.
  • Maintenance personnel are informed of significant changes.
  • Backup and recovery information is available to authorized personnel.
  • Asset and spare-parts records are updated where required.
  • Outstanding actions have an owner and due date.

20. Interview Questions and Answers

Q1. What is an as-built document?

It is a controlled document updated and verified to represent the actual accepted installed or configured condition of a machine, system, or facility.

Q2. What is the difference between as-designed and as-built?

As-designed describes the intended configuration. As-built describes the verified actual configuration after installation and authorized changes.

Q3. What is a redline drawing?

A redline drawing records a field change or discrepancy before the formal controlled document is updated and released. It must be managed according to the applicable procedure.

Q4. Why are as-built documents important for maintenance?

They provide reliable information for troubleshooting, isolation planning, component replacement, configuration recovery, engineering changes, and future modifications.

Q5. What should happen when a machine is modified?

The modification must be authorized, affected records identified, the actual configuration verified, relevant documents updated and approved, and obsolete revisions withdrawn from current use.

Q6. Is a working PLC backup automatically an as-built backup?

No. It must be identified, assessed for applicability, compared with the installed and approved configuration where required, and retained under controlled revision and asset-identification rules.

Q7. What is the risk of missing as-built updates after a retrofit?

Maintenance may rely on incorrect wiring, I/O assignments, network addresses, component identities, software versions, or parameter records.

Q8. Who is responsible for as-built documentation?

Responsibility depends on the organization's procedure. Engineering, project teams, commissioning personnel, contractors, maintenance, and document control may have defined responsibilities. The owner and required approvers should be clear.

Q9. How are as-built documents connected to engineering change management?

The change record identifies the approved modification and affected documentation. The as-built package records the verified resulting configuration and provides traceability to the change and its validation evidence.

Q10. How can as-built documentation completeness be measured?

Track the availability and approval status of required documents, open redlines, overdue updates, backup coverage, unresolved discrepancies, and verification results for critical assets.

Q11. Can a drawing be correct while the machine is different?

Yes. The drawing may accurately represent the original design but not the current installation. It is not a reliable as-built record until the actual configuration has been verified and the required updates completed.

Q12. What is the most important principle of as-built documentation?

Maintain traceable, approved records that represent the actual accepted configuration, so future work can be performed safely and accurately.

21. Key Principles to Remember

  • As-built means the verified actual condition, not the original intended design.
  • Field changes must follow the applicable authorization and safety processes.
  • Redlines are controlled inputs to document updates, not automatic substitutes for released documents.
  • Physical installation, software, hardware, network, and safety records may all need revision.
  • Backups must be associated with the correct asset and configuration.
  • Engineering changes must be traceable to affected documents and verification evidence.
  • Obsolete revisions must not be confused with current approved records.
  • As-built documentation should be accessible to authorized personnel where maintenance and operations need it.
  • The documentation package must evolve with the equipment throughout its lifecycle.

For an industrial maintenance team, accurate as-built documentation converts undocumented machine modifications into traceable engineering knowledge. It reduces troubleshooting uncertainty and makes future maintenance, retrofits, and recovery work substantially more reliable.
