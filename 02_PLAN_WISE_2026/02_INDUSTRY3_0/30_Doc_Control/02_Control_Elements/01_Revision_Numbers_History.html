1. Purpose and Scope

Revision numbers and revision history are document-control mechanisms used to identify the exact state of a controlled document, preserve its change record, and establish which issue is valid for use.

In industrial maintenance and automation, controlled items include:

  • Electrical schematics, wiring diagrams, panel layouts, and loop diagrams.
  • PLC, HMI, CNC, robot, and drive programs.
  • Machine manuals, operating instructions, SOPs, and maintenance procedures.
  • Risk assessments, safety circuits, inspection formats, and test reports.
  • Network drawings, IP address lists, backups, configuration files, and machine knowledge-base records.
  • Process parameters, quality standards, calibration procedures, and commissioning documents.

The objective is not merely to put a new number on a drawing. It is to ensure that the correct, reviewed, approved, and applicable version reaches the people and systems that depend on it.

A document without reliable revision control can be technically correct in isolation but operationally dangerous when someone uses an obsolete copy.

3. Revision, Version, Issue, and Status Are Not Automatically the Same

These terms are often used interchangeably in casual conversation, which creates confusion in controlled environments.

Attribute Main question answered Example
Document number Which document is this? EL-PLC-017
Revision Which controlled state is this? Rev C
Version Which named state under the defined versioning scheme? 2.4.1
Issue Which formal issue or publication is this? Issue 03
Status What is its current lifecycle state? Approved, Released, Superseded
Effective date When does it apply? 18-Oct-2026
Applicability Where or to what does it apply? Line 2, station 05

A document can be revision C and still be in draft status. A released document can later become superseded. A document can have the latest revision number but not yet be approved for use.

Critical rule: A higher revision identifier does not automatically mean the document is approved, effective, or applicable to every machine.

4. Common Revision Numbering Systems

4.1 Alphabetic numbering

Example:

Rev A
Rev B
Rev C
Rev D

Commonly used for drawings, electrical schematics, mechanical designs, and engineering documents.

Advantages:

  • Compact and easy to identify.
  • Visually distinguishes a revision from a document number.
  • Familiar in many engineering environments.

Limitations:

  • Organizations differ on whether the initial release is A, 0, or another identifier.
  • Rules for revisions after Z must be defined.
  • Letters such as I and O may be avoided to prevent confusion with 1 and 0.
  • Some systems use double-letter sequences, while others switch to numeric identifiers.

Never assume that Rev A always means the first released version. The document-control procedure determines the rule.

4.2 Numeric numbering

Example:

Rev 00
Rev 01
Rev 02
Rev 03

Common in controlled procedures, forms, technical specifications, and industrial documentation systems.

Advantages:

  • Easy to sort when identifiers use consistent width.
  • Simple to automate in registers and document-management systems.
  • Clear sequence for change tracking.

Limitations:

  • The number alone does not communicate the significance of the change.
  • Numeric revisions may be confused with software versions or issue numbers if labels are omitted.

Use zero-padding, such as 00, 01, and 02, when required by the organization's naming and sorting convention.

4.3 Major and minor revision numbering

Example:

Version 1.0
Version 1.1
Version 1.2
Version 2.0

A typical convention is:

  • Major revision: substantial functional, architectural, safety, or compatibility change.
  • Minor revision: limited enhancement or controlled change that remains within the defined compatibility rules.

This is a convention, not a universal engineering law. An organization may define major and minor changes differently.

4.4 Semantic versioning for software

A common software convention uses:

MAJOR.MINOR.PATCH

Example: 2.4.1

  • 2: major version.
  • 4: minor version.
  • 1: patch version.

Under semantic versioning, these fields have specific rules related to compatibility and the nature of changes. Those rules should not be automatically imposed on PLC or CNC projects unless the organization has adopted them.

Industrial controller software may need additional identifiers such as controller type, firmware, project checksum, safety signature, hardware configuration, and approved machine applicability.

4.5 Date-based identifiers

Example:

PLC_Project_2026-10-18

Dates are useful for identifying backups, exports, test reports, and snapshots. However, a date by itself is not a reliable substitute for a controlled revision scheme.

A file saved on a later date might be an unapproved experiment rather than the current authorized program.

4.6 Hybrid numbering

Example:

Document: EL-PLC-017
Revision: C
Issue: 02
Change reference: CR-2026-041

Hybrid schemes can support complex document-control systems, but each field must have a defined purpose. Avoid maintaining multiple overlapping revision counters without a clear reason.

5. Initial Release and Subsequent Revisions

The first released issue establishes the initial controlled baseline. The identifier depends on the company's procedure.

Example:

Document: EL-PLC-017
Title: H7 Test-Bed Interlock Logic

Draft     → A0
Review    → A0
Approval  → A0
Release   → Rev A

Modification request
    ↓
Impact assessment
    ↓
Approved change
    ↓
Updated document and validation
    ↓
Review and approval
    ↓
Release Rev B
    ↓
Rev A marked superseded where applicable

A0 is only an illustrative draft convention, not a universal requirement.

The following controls should be defined:

  • Whether drafts have revision identifiers.
  • Whether the first released issue is A, 00, 01, or another identifier.
  • Whether editorial corrections require a revision increment.
  • Whether emergency changes receive a temporary identifier.
  • Who authorizes a revision.
  • How release and effective dates are assigned.
  • How the previous revision is retained and marked.
  • How affected users and systems are notified.

A revision increment should represent a controlled state change, not simply a file being saved.

6. What Belongs in Revision History?

A useful revision-history entry should allow another engineer or auditor to understand what changed, why it changed, who authorized it, and where it applies.

Recommended fields include:

Field Purpose
Revision Identifies the new document state
Date Records the relevant change or release date according to procedure
Change description Summarizes the actual technical or administrative change
Reason Explains the problem, requirement, or improvement driving the change
Change reference Links to the change request, work order, deviation, or engineering change
Originator Identifies who prepared the change
Reviewer Identifies who checked the change
Approver Identifies who authorized the applicable release
Applicability Identifies affected machines, stations, models, or locations
Validation reference Links to tests, inspection records, or verification evidence where applicable
Release status Shows whether the revision is draft, approved, released, or otherwise controlled

Not every organization places every field directly in the revision table. Some fields may live in a linked document-management record. The essential requirement is traceability.

6.1 Weak versus strong change descriptions

Weak entry:

Rev C - Updated PLC program.

This tells the reader almost nothing.

Stronger entry:

Rev C - Added conveyor overload feedback monitoring and alarm
reset permissive. Change CR-2026-041. Verified under test
record TR-2026-092. Applicable to H7 test-bed TB-04.

The stronger entry identifies the functional change, its traceability, the verification record, and its applicability.

6.2 Record the change, not just the activity

"Drawing updated" describes an activity. It does not describe the engineering change.

Prefer descriptions such as:

  • Added fuse protection to the 24 VDC sensor supply.
  • Corrected terminal numbers to match the installed panel wiring.
  • Updated the PLC input address following hardware replacement.
  • Changed the alarm threshold following approved process validation.
  • Added a safety relay feedback diagnostic.
  • Corrected the CNC tool-offset procedure following a controlled process review.

Avoid vague descriptions such as "modified," "revised," "as discussed," or "latest changes" unless supported by a meaningful technical summary.

7. Revision History for Different Industrial Documents

The revision method should reflect the item being controlled. A wiring drawing, PLC program, safety procedure, and machine parameter backup do not necessarily require identical revision fields.

7.1 Electrical drawings

Record changes such as:

  • New or removed components.
  • Changes to wire numbers, terminal numbers, cable routes, and I/O addresses.
  • Updated fuse, circuit-breaker, overload, and protective-device ratings.
  • Changes to safety circuits or interlock logic.
  • Corrections made after site installation.
  • Differences between the previous drawing and the verified as-built condition.

Example:

Revision Change description Reference
A Initial release DRW-101
B Added overload auxiliary contact feedback CR-014
C Corrected terminal numbering to match panel wiring WO-208

7.2 PLC and HMI programs

A PLC project needs more than a filename and revision number. Capture enough information to identify and reproduce the approved state.

Recommended control fields:

  • Project name and controlled revision.
  • PLC model, catalog number, and firmware.
  • Engineering software and version.
  • Hardware configuration and I/O mapping.
  • Program or project checksum where supported.
  • Safety signature or equivalent safety validation identifier, where applicable.
  • HMI project revision and compatibility information.
  • Change request and related test report.
  • Backup location, access restrictions, and recovery instructions.
  • Machine or line applicability.
  • Approval and deployment records.

Example:

Project: H7_TB04_PLC
Revision: C
Controller: GuardLogix 1756-L73S
Engineering environment: Record exact software version
Change: Added overload feedback diagnostics
Validation: TR-2026-092
Applicability: Test-bed TB-04
Status: Released after required validation and approval

The controller details above are illustrative. Actual firmware, project version, safety signature, and validation results must be recorded from the real system.

Important: A project file can have the correct revision label but still differ from the program running in the controller. Where permitted, verify the online/offline comparison, controller identity, applicable signature, and approved deployment record.

7.3 CNC programs and machine parameters

Control the following where relevant:

  • Part program number and revision.
  • Machine model and control type.
  • Tool-offset and work-offset assumptions.
  • Approved process parameters.
  • Postprocessor and program-generation software version.
  • Fixture, tooling, and workholding configuration.
  • Prove-out and validation results.
  • Applicability to the machine, product, and process variant.

A program that works on one CNC machine is not automatically approved for another machine with a different configuration.

7.4 SOPs and maintenance procedures

A procedure revision should record changes affecting:

  • Work sequence and acceptance criteria.
  • Safety precautions, isolation requirements, and PPE.
  • Tools, instruments, and required competencies.
  • Inspection frequency and maintenance intervals.
  • Escalation, abnormal-condition handling, and restoration steps.
  • Forms, checklists, and records generated during execution.
  • Training or communication requirements for affected users.

When a revision changes a critical work instruction, document distribution and training requirements should be assessed before implementation.

7.5 Backups and configuration files

Use a controlled record that links the backup to the actual asset.

Example:

Asset ID: H7-TB-04-PLC
Backup ID: BKP-H7-TB04-PLC-20261018
Controlled revision: C
Capture date: 2026-10-18
Controller identity: Verified asset identifier
Firmware: Actual recorded firmware
Checksum: Recorded value, if supported
Source: Authorized controller upload or approved project
Validation status: Recorded verification result
Storage: Approved restricted backup repository

A backup date is not proof that the backup is correct. Record its origin, identity, integrity, and restoration suitability.

8. Revision Control Versus Change Control

Revision control identifies and preserves document states. Change control governs whether a change may be proposed, assessed, approved, implemented, and released.

They are related but distinct.

Revision control Change control
Identifies document states Authorizes and governs changes
Maintains revision history Maintains change request and approval records
Identifies current and superseded issues Assesses technical, safety, quality, and operational impact
Supports retrieval and traceability Controls implementation and validation
Helps prevent use of obsolete information Helps prevent unauthorized modifications

Typical sequence:

Change request
    ↓
Impact and risk assessment
    ↓
Authorization to implement
    ↓
Engineering modification
    ↓
Verification and validation
    ↓
Document revision updated
    ↓
Review and approval
    ↓
Controlled release
    ↓
Distribution and implementation
    ↓
Previous issue retained and status updated

The actual sequence may vary by the organization's procedure and the risk of the change. Some urgent changes require a controlled emergency process, followed by retrospective documentation and review where the procedure permits it.

9. Revision History and As-Built Documentation

An as-built document records the verified installed condition. A revision history records how the controlled document changed over time.

These functions overlap, but they are not interchangeable.

Consider a machine retrofit:

  1. An engineer proposes a change to the electrical circuit.
  2. The change is reviewed and approved.
  3. The wiring is modified on the machine.
  4. The installation is inspected and tested.
  5. The drawing is updated to reflect the verified installation.
  6. The updated drawing receives its controlled revision and approval.
  7. The previous drawing is retained as a historical record and withdrawn from normal use where applicable.

If the installation changes but the drawing remains unchanged, the documentation may no longer represent the machine. If the drawing changes before the installation is verified, it may represent an intended design rather than the as-built condition.

Document status and actual implementation status should therefore be tracked separately when necessary.

10. Revision Applicability and Effective Dates

A newer revision is not always applicable to every asset.

For example, a modification may apply only to:

  • One machine or test-bed.
  • Machines manufactured after a particular date.
  • A particular product variant.
  • A specific PLC hardware configuration.
  • A selected group of production lines.
  • Machines that have completed a defined retrofit.

A controlled revision record should identify these boundaries.

Example:

Revision: D
Effective date: 2026-10-25
Applicability: H7 test-beds TB-04 and TB-05
Condition: Only after installation of the approved feedback module
Implementation evidence: Retrofit work orders and verification records

Before using a revision, verify:

  • The document identity matches the equipment.
  • The revision is approved and released for the intended use.
  • The effective date or implementation condition has been met.
  • The machine configuration falls within the stated applicability.
  • Any prerequisite modifications have been completed.
  • Required training, testing, or safety validation is complete.

11. Superseded Revisions, Obsolete Copies, and Archiving

Historical revisions should normally remain traceable, but they must not be mistaken for current instructions.

A controlled system should distinguish between:

  • Current: Authorized for the intended use.
  • Superseded: Replaced by a later applicable revision.
  • Obsolete: No longer authorized for the intended purpose.
  • Archived: Retained for historical, legal, engineering, or audit purposes.
  • Draft: Not authorized for operational use unless a specifically controlled process permits it.
  • Withdrawn: Removed from active use through a defined control process.

Recommended controls:

  • Retain revision history and supporting approvals.
  • Prevent obsolete files from appearing as the default current document.
  • Clearly label or segregate superseded copies.
  • Restrict editing of released originals.
  • Withdraw controlled paper copies according to procedure.
  • Keep archival retention periods aligned with applicable legal, contractual, quality, and company requirements.
  • Preserve the relationship between the original document, each revision, and the change that created it.

Never delete the previous revision simply because the newest one exists. Historical evidence may be necessary to understand a past failure, investigate a production event, or reproduce an earlier machine configuration.

12. Revision Control in Excel, SharePoint, PLM, or a Document Register

A spreadsheet-based register can provide useful visibility, but a spreadsheet alone does not guarantee document control.

A practical document register can include:

Field Example
Document ID EL-PLC-017
Document title H7 Test-Bed Interlock Logic
Document type PLC program
Current revision C
Status Released
Effective date 2026-10-18
Change reference CR-2026-041
Owner Central Maintenance
Approver Authorized engineering role
Applicability H7 test-bed TB-04
Controlled file location Approved repository path
Validation record TR-2026-092
Previous revision B
Superseded date Recorded when applicable

A robust implementation should also consider:

  • Unique document identifiers.
  • Controlled permissions and separation of duties.
  • Approval records and timestamps.
  • Version history or immutable audit logs.
  • Required-field validation.
  • Notifications when a relevant revision is released.
  • Links to work orders, change requests, and test reports.
  • Backup and recovery arrangements.
  • A clearly identified source of truth.

12.1 Example register logic

IF document status is not Released
    → Do not treat it as the normal operational issue.

IF revision is superseded
    → Direct the user to the current applicable revision.

IF asset configuration does not match applicability
    → Verify the correct document before use.

IF approval or validation evidence is missing
    → Escalate according to the document-control procedure.

These are governance rules, not universal automatic decisions. Safety-critical and production-critical documents may require additional authorization checks.

14. Practical Revision-Control Workflow for Maintenance

For a real maintenance or retrofit job, use the following checklist.

  • Identify the controlled document or configuration item.
  • Confirm its current revision, status, and applicability.
  • Record the reason for the proposed change.
  • Link the change to a change request, work order, deviation, or approved instruction.
  • Assess impacts on safety, quality, production, hardware, software, and related documents.
  • Obtain authorization before implementation, except where an approved emergency procedure governs the action.
  • Make the change and preserve the prior approved state.
  • Verify the technical result and complete the required validation.
  • Update the revision identifier and revision history.
  • Complete independent review and formal approval as required.
  • Release the document through the controlled process.
  • Update affected drawings, programs, SOPs, backups, and knowledge-base records.
  • Notify affected users and complete required training.
  • Mark previous revisions as superseded or otherwise control them.
  • Record implementation evidence and close the change process.

Not every change requires every step to have the same depth. The level of control should reflect risk, regulatory requirements, company procedures, and the consequences of an incorrect change.

15. Key Metrics for Revision-Control Effectiveness

Revision control can be measured instead of being treated as paperwork that everyone promises to improve next quarter.

Useful indicators include:

  • Obsolete-document findings: Number of audits or jobs where superseded documents were found in active use.
  • Revision traceability: Percentage of sampled revisions linked to complete change and approval records.
  • Release lead time: Time between an approved change being ready for release and controlled publication.
  • Implementation completion: Percentage of applicable assets updated within the defined period.
  • Uncontrolled-change incidents: Changes made without required authorization.
  • Configuration mismatch rate: Frequency of differences between approved documentation and actual installed or running configurations.
  • Document retrieval time: Time needed to identify the current approved document for a given asset.

Each metric needs a defined scope, data source, calculation method, target, and owner. A low number of reported incidents does not automatically prove good control if nobody is checking.

16. Interview Questions and Answers

Q1. What is revision control?

Revision control is the controlled identification, recording, approval, release, and preservation of successive states of a document or configuration item.

Q2. What is the purpose of revision history?

It provides traceability of what changed, when it changed, why it changed, who reviewed or approved it, and which equipment or process is affected.

Q3. What is the difference between revision and revision history?

A revision identifies a specific state of a document. Revision history records the sequence of changes that produced successive states.

Q4. Is the latest revision always the correct revision to use?

No. It must also be approved, released, effective, and applicable to the asset or process.

Q5. Why must obsolete revisions be retained?

They may be needed for historical investigations, audits, legal or contractual retention, engineering comparisons, and reconstruction of earlier machine configurations.

Q6. What should a revision-history entry contain?

At minimum, the revision identifier, date, and meaningful change description, supported by the applicable approval and traceability records required by the organization's procedure.

Q7. What is the difference between document revision control and software version control?

Document revision control governs the identity and authorized use of controlled documents. Software version control can additionally track source-code changes, branches, merges, build outputs, and code history. Industrial projects may require both software-development controls and formal engineering release controls.

Q8. What would you do if the PLC program did not match the approved backup?

Confirm controller identity, access authorization, machine operating state, and applicable change records. Preserve evidence, avoid overwriting either state prematurely, investigate the difference, and follow the approved recovery and change-control process. Any restoration must be authorized and validated for the specific machine.

Q9. How do revision control and as-built documentation work together?

Revision control records the controlled document state and its changes. As-built documentation records the verified installed condition. After a physical modification, the controlled documentation should be reconciled with the verified installation.

Q10. Can a minor change avoid formal approval?

Only if the organization's documented procedure explicitly permits a simplified process for that type of change. A change that appears minor may still affect safety, quality, or compatibility.

17. Final Operating Principles

  • One document identity should have an unambiguous controlled history.
  • Revision identifiers must follow a defined organizational convention.
  • A revision number is not proof of approval, validation, or applicability.
  • Change descriptions must explain the technical change, not merely state that the file was updated.
  • Software backups must be traceable to the actual asset and approved configuration.
  • The current controlled issue must be easy to identify; obsolete copies must be prevented from accidental use.
  • Released documents and configurations must not be modified outside the approved change process.
  • Revision history, change records, approvals, and verification evidence should form a traceable chain.
  • The final test of revision control is whether the correct authorized information is available and used on the correct equipment.
