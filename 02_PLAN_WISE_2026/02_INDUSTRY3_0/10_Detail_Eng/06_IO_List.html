1. Definition and purpose

An I/O list (Input/Output list) is a structured engineering register of the signals exchanged between field devices, electrical equipment, PLCs, remote I/O stations, HMI/SCADA systems, and other machine controllers.

It defines what each signal represents, where it originates, how it is electrically interfaced, where it is connected, how it is processed, and what operational behavior is expected.

The I/O list is the practical connection between machine requirements and the actual control system implementation. A PLC program can contain perfectly written logic and still fail because a sensor was allocated to the wrong channel, an analog range was configured incorrectly, or a signal's intended behavior was never documented. Engineering has many ways to turn one missing spreadsheet field into a production breakdown.

Main purposes

  • Define all required control and monitoring signals before hardware selection and software development.
  • Allocate each physical signal to the correct PLC or remote I/O channel.
  • Define electrical interfaces, signal ranges, engineering units, and normal/fault behavior.
  • Coordinate electrical drawings, terminal plans, cable schedules, PLC tags, HMI objects, alarms, interlocks, and safety requirements.
  • Estimate I/O module quantities, spare capacity, field power, terminal requirements, and cabinet space.
  • Support design reviews, software development, FAT, SAT, commissioning, troubleshooting, and as-built documentation.
  • Maintain traceability when equipment, signals, PLC hardware, or control logic changes.

A single physical device can appear in several documents. The important requirement is that its identity, signal meaning, and interface remain consistent across all of them.

4. Signal classifications

4.1 Digital input (DI)

A digital input represents a discrete state, commonly ON/OFF, TRUE/FALSE, or 1/0.

Examples:

  • Proximity sensor detects a component.
  • Limit switch confirms cylinder extension.
  • Motor starter auxiliary contact indicates running.
  • VFD relay output indicates fault.
  • Pressure switch indicates low pressure.
  • Guard switch reports a guard state.
  • Robot reports ready or fault.
  • Emergency-stop circuit reports status to a safety controller, where the design supports such monitoring.

Typical electrical interfaces include 24 VDC discrete signals, dry contacts, and appropriately rated AC inputs where required.

The I/O list should define the signal's active state and expected behavior when the circuit is open, shorted, unpowered, or disconnected where relevant.

4.2 Digital output (DO)

A digital output commands a discrete action or state.

Examples:

  • Energize a solenoid valve.
  • Start a motor starter.
  • Reset a permitted drive fault.
  • Turn on a stack light.
  • Enable a machine sequence.
  • Operate an interposing relay.

The list should specify the output type, load requirements, voltage, current, electrical isolation, and what happens when the output is de-energized or the controller loses power.

A PLC output is not automatically suitable for every load. A large contactor coil, inductive load, or field device may require an interposing relay, suppression, or a separate power interface.

4.3 Analog input (AI)

An analog input represents a continuously varying measurement.

Examples:

  • Pressure transmitter: 4–20 mA.
  • Temperature transmitter: 4–20 mA or 0–10 V.
  • Position transducer: 0–10 V.
  • Flow transmitter: 4–20 mA.
  • Load cell amplifier: voltage or current output.
  • Differential pressure transmitter: 4–20 mA.

The I/O list should include signal range, engineering range, units, scaling, accuracy requirements where applicable, and fault detection expectations.

4.4 Analog output (AO)

An analog output sends a continuously varying command to another device.

Examples:

  • Speed reference to a VFD.
  • Position reference to a compatible servo interface.
  • Valve position command to a proportional control valve.
  • Pressure setpoint to a compatible controller.

Specify output range, engineering range, units, destination, and behavior on communication failure or controller fault.

Where a drive accepts a network-based speed reference instead of an analog input, document the communication interface rather than incorrectly counting the command as a physical AO.

4.5 Special and communication-based signals

Signal category Examples Important design information

Temperature input RTD, thermocouple Sensor type, wiring method, compensation, range

Important: A communication tag is not necessarily a physical PLC I/O channel. Keep physical I/O, internal software tags, and network data points distinguishable in the register.

Use controlled values for fields such as signal type, electrical interface, status, and safety classification. Free-text entries such as Analog, AI, Analogue Input, and 4-20mA input should not be allowed to proliferate in the same column.

5.2 Additional fields where needed

  • Signal polarity and active level.
  • PNP/NPN or sourcing/sinking interface.
  • Normally open (NO) or normally closed (NC) contact details.
  • Two-wire, three-wire, or four-wire transmitter arrangement.
  • Channel isolation and common-terminal grouping.
  • Output load current and protection requirements.
  • Analog scaling limits, resolution, filtering, and diagnostic thresholds.
  • Alarm limits, priority, deadband, delay, and latching behavior.
  • Interlock or permissive reference.
  • PLC tag name, data type, and software reference.
  • HMI screen, faceplate, or alarm identifier.
  • Device manufacturer and model where necessary for interface compatibility.
  • FAT/SAT test reference and commissioning status.
  • Change request, revision, approver, and verification evidence.

Not every project needs every field. The minimum schema should be defined by project complexity and company standards, while the required safety and interface information must never be omitted merely to make the spreadsheet look tidy.

6. Tag naming and unique identification

A signal tag should identify the device or function unambiguously. The convention must be consistent with the project's equipment-tagging and software-naming standards.

Illustrative examples:

Tag Meaning Typical category
LSH-101 High-level switch DI
PT-101_PV Pressure transmitter process value AI or communication tag
MTR-101_RUN_FB Motor running feedback DI or network status
MTR-101_START_CMD Motor start command DO or network command
XV-101_OPEN_CMD Valve open command DO or network command
XV-101_OPEN_FB Valve-open feedback DI
VFD-101_SPEED_REF Drive speed reference AO or network command
VFD-101_FAULT Drive fault indication DI or network status
ROBOT-01_READY Robot ready status Network or DI
CNC-01_CYCLE_ACTIVE CNC cycle active Network or DI
ESTOP_ZONE1_STATUS Emergency-stop zone status Safety-system status or approved diagnostic interface

Suffixes such as _CMD, _FB, _PV, _SP, _ALM, and _STS are common conventions, not universal standards. Define them in the project naming standard.

Do not reuse a single tag for different physical signals just because they refer to the same machine. For example, motor start command, motor running feedback, and motor fault are three distinct signals with different origins and meanings.

A robust identifier system distinguishes:

  • Equipment identity: the physical motor, valve, sensor, robot, or machine.
  • Signal identity: a specific command, measurement, status, or fault.
  • Hardware identity: controller, I/O station, module, and channel.
  • Software identity: PLC tag or network data point.
  • Document identity: drawing, cable, terminal, alarm, or test reference.

7. Electrical interface definitions

7.1 Digital input circuits

For a 24 VDC input, the design must establish how field power and the input module detect the signal. Common arrangements include PNP and NPN sensors, sourcing and sinking interfaces, and dry-contact inputs.

Interface Typical behavior Design check
PNP sensor Sources positive voltage to the input when active Confirm input common and current path
NPN sensor Sinks the input toward 0 V when active Confirm module compatibility and current path
Dry contact Opens or closes a circuit without generating its own voltage Confirm external sensing voltage and wiring
Two-wire electronic sensor Uses two conductors for supply and switching behavior Check leakage current and input compatibility
Three-wire electronic sensor Usually has supply, common, and output conductors Confirm polarity and output type

PNP/NPN and sourcing/sinking terminology is often confused. Verify the actual current path and the manufacturer's wiring diagram rather than relying on the words alone.

The list or linked interface documentation should make clear:

  • Supply voltage and polarity.
  • Active electrical state.
  • Input current and threshold compatibility.
  • Common-terminal arrangement.
  • Cable shield and grounding requirements where relevant.
  • Open-circuit and short-circuit diagnostic behavior if supported.

7.2 Digital outputs

Output type Common application Important limitation
Relay output Switching compatible AC or DC loads Contact life, switching frequency, load rating
Transistor output Fast DC switching Polarity, current limit, short-circuit protection
Triac output Certain AC switching applications AC-only behavior and leakage considerations
Isolated output Applications requiring channel or group isolation Isolation rating and group configuration

The output type must match the field device and power circuit. An output module's nominal current rating does not automatically establish suitability for an inductive coil or a load with high inrush current.

Document external protection, interposing relays, suppression, and field power arrangements in the relevant drawings and design records.

7.3 Analog inputs and outputs

The I/O list should distinguish electrical range from engineering range.

Example:

Parameter Example value
Signal tag PT-101_PV
Signal type AI
Electrical range 4–20 mA
Engineering range 0–10 bar
Engineering unit bar
Lower electrical limit 4 mA
Upper electrical limit 20 mA
Lower engineering value 0 bar
Upper engineering value 10 bar
Fault handling Detect under-range according to module and transmitter diagnostics

For a linear signal, the engineering value can be calculated using:

\[ PV = EU\_{\min} + \frac{I-I\_{\min}}{I\_{\max}-I\_{\min}}(EU\_{\max}-EU\_{\min}) \]

Where:

  • \(PV\) is the engineering process value.
  • \(I\) is the measured electrical current.
  • \(I\_{\min}\) and \(I\_{\max}\) are the configured electrical limits.
  • \(EU\_{\min}\) and \(EU\_{\max}\) are the engineering limits.

For a 4–20 mA transmitter representing 0–10 bar, a measured current of 12 mA corresponds to 5 bar, assuming correct configuration and linear scaling.

\[ PV = 0 + \frac{12-4}{20-4}(10-0) = 5\ \text{bar} \]

A 4–20 mA signal uses a live zero, allowing the system to distinguish the normal zero measurement at 4 mA from certain fault conditions below the expected range. Exact fault thresholds depend on the transmitter, input module, configuration, and applicable standard.

For an output, reverse the calculation to determine the electrical command corresponding to the required engineering setpoint. Confirm that the PLC, module, field device, and software all use the same range.

7.4 RTD and thermocouple signals

For temperature measurement, specify the sensor type and interface explicitly.

  • RTD: identify the sensor standard and element type, such as Pt100, plus two-wire, three-wire, or four-wire connection.
  • Thermocouple: identify the type, such as K or J, and ensure appropriate extension wire, polarity, and cold-junction compensation.
  • Transmitter-based measurement: document the transmitter's electrical output range and its configured temperature span.

Do not list an RTD input as a generic 4–20 mA signal unless the RTD is actually connected through a transmitter that produces 4–20 mA.

The exact order and hardware arrangement depend on the design. Some devices connect directly to a distributed I/O block; others communicate over an industrial network and have no dedicated physical PLC channel.

8.1 Physical address versus symbolic tag

  • Physical address: identifies a hardware location, such as a particular module and channel.
  • Symbolic tag: identifies the signal by meaning, such as PT_101_PV.
  • Network address or data mapping: identifies a device or data element communicated over a network.
  • Internal logic tag: represents calculated, latched, simulated, or derived information rather than a direct field connection.

These are related but not interchangeable. An address can change when hardware is rearranged, while a well-designed symbolic tag can remain stable.

8.2 Platform considerations

Platform Common allocation approach Important control
Siemens Hardware configuration plus symbolic PLC tags Confirm device configuration, module channels, and symbolic mapping
Allen-Bradley Module-defined tags and controller/application tags Confirm module configuration, connection status, and tag mapping
Mitsubishi PLC parameter/hardware configuration and device or label mapping Confirm module assignments, device addresses, and label mapping
Remote I/O Adapter or network node plus module and channel Confirm network configuration and channel-to-tag mapping
Networked drive or robot Network device and structured data mapping Confirm command/status words, bit definitions, scaling, and timeout behavior

Addressing syntax differs by controller family, model, and software version. The project-specific hardware configuration is the authoritative source for actual addresses; generic examples must not be copied blindly into a live machine.

8.3 Channel allocation rules

  • Assign each physical signal to one unique intended channel unless the approved design explicitly uses shared or multiplexed interfaces.
  • Confirm module type and electrical compatibility before allocation.
  • Document channel numbers, module references, terminal references, and field device tags.
  • Respect channel groups, common terminals, isolation limits, and power segmentation.
  • Separate standard and safety-related I/O according to the approved safety architecture.
  • Consider module diagnostic capabilities and how channel faults will be detected.
  • Record reserved channels and their intended purpose.
  • Keep the I/O list synchronized with the hardware configuration and electrical drawings.

9. I/O sizing and spare capacity

I/O sizing translates the signal register into a hardware requirement. Count channels by signal type, interface, and any special electrical or functional constraints.

Example: a machine requires 36 DI, 22 DO, 8 AI, and 4 AO. If the selected modules provide 16 DI, 16 DO, 8 AI, and 4 AO channels respectively, the initial module count is:

Signal type Required channels Channels per module Modules required Installed capacity
DI 36 16 3 48
DO 22 16 2 32
AI 8 8 1 8
AO 4 4 1 4

The module count is calculated by rounding the required channel count up to the next whole module:

\[ N\_{\text{modules}}=\left\lceil\frac{N\_{\text{required}}}{N\_{\text{channels per module}}}\right\rceil \]

Installed spare capacity is the difference between installed channels and required channels. In this example, there are 12 spare DI channels and 10 spare DO channels, but no spare AI or AO channels.

This is a preliminary count, not final hardware approval. Actual selection must also account for:

  • Required spare percentage or reserved expansion capacity.
  • Channel isolation and permissible grouping.
  • Electrical interface compatibility.
  • Safety-rated channel requirements.
  • Module diagnostic and accuracy requirements.
  • Power budget, cabinet heat dissipation, and available mounting space.
  • Network adapter capacity, update time, and connection limits.
  • Availability of terminals, fuses, distribution points, and field wiring capacity.
  • Required redundancy or availability architecture.

Do not assume that all unused channels are interchangeable. A spare 24 VDC DI channel does not replace an analog input channel, a high-speed counter, or a safety-rated channel.

10. Normal state, fault state, and fail-safe behavior

Every important signal should have a clearly defined expected state and response to abnormal conditions. The I/O list should not rely on an ambiguous description such as OFF = fault without explaining the circuit and functional meaning.

Signal example Normal condition Abnormal condition to consider
Cylinder extended sensor Extended position confirmed Sensor absent, broken wire, cylinder not reaching position
Motor running feedback Motor starter or drive confirms running Command present but feedback absent
Pressure transmitter Value within operating range Under-range, over-range, wire break, implausible reading
Valve open feedback Open position confirmed Command issued but feedback absent
Remote I/O status Communication healthy Adapter or network communication loss
Guard status Guard closed and safety system healthy, as designed Guard opened, channel fault, discrepancy
Drive fault status No active drive fault Fault asserted or device unavailable

Key principles

  • Distinguish the process's normal state from the electrical state of the input.
  • Document NO/NC contacts and their intended de-energized behavior.
  • Specify wire-break or short-circuit diagnostics where the hardware supports them.
  • Define what the PLC should do when a measurement becomes invalid or stale.
  • Identify whether the signal is used for an alarm, permissive, interlock, sequence transition, or status indication.
  • Specify communication timeout behavior for networked devices.
  • Do not assume that 0, OFF, or a missing signal means a safe condition.

A safety-related function must be designed and validated according to its risk assessment and applicable safety requirements. A normal PLC input displaying an emergency-stop status is not, by itself, a safety function.

11. Signal relationships: commands, feedback, permissives, and interlocks

An I/O list should make the role of each signal clear, particularly for actuators and sequence-controlled equipment.

  • Command: the controller's request to perform an action.
  • Feedback: confirmation from the device that a physical or operational state exists.
  • Permissive: a condition that must be satisfied before an action is allowed.
  • Interlock: a condition that inhibits or stops an action according to defined logic.
  • Alarm: an operator notification requiring awareness or response.
  • Status: an indication of current equipment or process state.
  • Sequence signal: a signal used to coordinate a step or transition.
  • Safety function: a defined risk-reduction function implemented in an appropriate safety-related architecture.

Example for a motor:

Start request
     |
     v
Check permissives
     |
     v
Issue start command
     |
     v
Motor starter / VFD
     |
     v
Running feedback
     |
     +----> Running status
     |
     +----> Feedback timeout alarm if expected feedback is absent

The precise timeout, permissive conditions, and fault response must come from the approved functional specification, not from an arbitrary default in the I/O spreadsheet.

12. Worked example: I/O list for a small automated machine

Consider a machine with a pneumatic cylinder, a conveyor motor, a pressure transmitter, and a VFD.

I/O ID Signal tag Description Type Interface PLC allocation Functional role
IO-001 PART_PRESENT Part detected at station DI 24 VDC PNP DI module, Ch 0 Sequence input
IO-002 CYL_EXTENDED Cylinder fully extended DI 24 VDC PNP DI module, Ch 1 Position feedback
IO-003 CYL_RETRACTED Cylinder fully retracted DI 24 VDC PNP DI module, Ch 2 Position feedback
IO-004 CONV_START_CMD Conveyor start command DO 24 VDC transistor DO module, Ch 0 Actuator command
IO-005 CYL_EXTEND_CMD Extend solenoid command DO 24 VDC, via suitable interface DO module, Ch 1 Actuator command
IO-006 CYL_RETRACT_CMD Retract solenoid command DO 24 VDC, via suitable interface DO module, Ch 2 Actuator command
IO-007 AIR_PRESSURE_PV Pneumatic supply pressure AI 4–20 mA AI module, Ch 0 Process measurement
IO-008 VFD_SPEED_REF Conveyor speed reference AO 0–10 V AO module, Ch 0 Speed command
IO-009 VFD_RUNNING Conveyor running status DI 24 VDC from suitable drive output DI module, Ch 3 Status feedback
IO-010 VFD_FAULT VFD fault status DI 24 VDC from suitable drive output DI module, Ch 4 Fault monitoring

These channel assignments are illustrative, not universal. The final allocation must match the actual PLC hardware configuration, module type, wiring design, and project addressing convention.

The example also demonstrates why signal names must be precise. CONV_START_CMD is a command; VFD_RUNNING is feedback. The first does not prove the second occurred.

13. Engineering workflow for developing the I/O list

Step 1: Establish the functional requirements

Identify machine operations, equipment, process measurements, required statuses, alarms, permissives, interlocks, and interfaces with other machines.

Use the functional specification, machine sequence, process drawings, equipment list, and approved safety requirements as inputs.

Step 2: Identify every required signal

For each device, determine whether it requires:

  • A physical DI, DO, AI, or AO.
  • A special interface such as encoder, RTD, or high-speed counter.
  • A network-based command, status, or measurement.
  • An internal PLC variable derived from other signals.
  • A safety-related interface requiring a dedicated safety design.

Do not create a physical I/O point for every software variable. Calculated values, timers, sequence states, and internal flags may not require field channels.

Step 3: Define electrical and functional behavior

Record electrical interface, operating range, engineering units, active state, normal condition, fault detection, and required response.

Resolve ambiguities with the equipment supplier, instrumentation engineer, electrical designer, PLC programmer, and safety engineer as applicable.

Step 4: Allocate hardware

Assign the controller, local or remote station, module, channel, and relevant address or network data mapping.

Check channel compatibility, group commoning, power requirements, isolation, spare capacity, and hardware diagnostics.

Step 5: Cross-reference engineering documents

Verify consistency with:

  • Electrical schematics and terminal plans.
  • Cable schedule and field-device wiring.
  • Instrument list and equipment list.
  • PLC tag database and hardware configuration.
  • HMI screen and alarm definitions.
  • Cause-and-effect matrix and functional specification.
  • Network architecture and device configuration.
  • BOM and panel layout.

Step 6: Review and release

Run automated validation checks, resolve comments, document approved changes, and release the correct revision to the engineering and commissioning teams.

Step 7: Verify during FAT and SAT

Test the actual signal from field device or test source through wiring and I/O hardware into the PLC software. Confirm displayed values, commands, feedback, alarms, and expected fault behavior.

Step 8: Update the as-built register

Record actual hardware allocation, wiring changes, validated behavior, and approved deviations. The released I/O list should describe the installed system, not just the original design intent.

14. Design verification checklist

  • Every required field signal has a unique identifier.
  • Every signal has a clear description and functional purpose.
  • Signal types match the actual field-device interfaces.
  • Electrical ranges and engineering ranges are specified correctly.
  • Analog engineering units and scaling limits are documented.
  • PNP/NPN, sourcing/sinking, polarity, and common-terminal requirements are compatible.
  • Output load requirements and interposing interfaces are checked.
  • Controller, I/O station, module, channel, and address assignments match the hardware configuration.
  • No channel is unintentionally assigned to multiple signals.
  • Spare channels are identified and distinguished from assigned channels.
  • Normal state, fault state, and diagnostic behavior are documented where relevant.
  • Commands, feedback, permissives, alarms, and interlocks are distinguished.
  • Safety-related signals are identified and routed according to the approved safety architecture.
  • Cable, terminal, drawing, equipment, and software references are consistent.
  • HMI visibility, alarm requirements, and network data mapping are verified.
  • Revision status, approvals, and commissioning evidence are controlled.

15. Commissioning and loop checking

A loop check proves that the intended field signal reaches the correct destination and is interpreted correctly. A channel that appears in the PLC online view is not automatically a verified loop.

15.1 Physical digital input checks

  1. Verify the field device identity and wiring against the schematic.
  2. Confirm supply voltage, polarity, and the intended input common.
  3. Operate the sensor or simulate its contact using an approved test method.
  4. Verify the correct module channel changes state.
  5. Confirm the corresponding PLC tag changes state.
  6. Verify the expected sequence, indication, or alarm behavior.
  7. Restore normal conditions and record the result.

15.2 Digital output checks

  1. Verify that the correct output channel and field device are mapped.
  2. Confirm that the output load, power source, and protective devices are suitable.
  3. Use an approved commissioning mode and check required permissives.
  4. Command the output and verify the physical response.
  5. Confirm feedback independently where available.
  6. Check output de-energization and fault response according to the approved design.
  7. Record the test result and restore normal operating conditions.

Do not force outputs or bypass interlocks on a live machine without an approved procedure, authorization, and the required risk controls.

15.3 Analog input checks

  1. Confirm the transmitter type, range, wiring, and channel configuration.
  2. Apply a calibrated test signal or use an approved process simulation method.
  3. Verify the raw input value and engineering-unit scaling.
  4. Check multiple points, such as the lower limit, midpoint, and upper limit.
  5. Verify underrange, overrange, and bad-quality diagnostics where supported.
  6. Confirm HMI display, alarm thresholds, filtering, and trend behavior.
  7. Record the applied test value, observed value, tolerance, and result.

For a 4–20 mA signal scaled to 0–10 bar, the expected values are:

Test current Expected pressure
4 mA 0 bar
8 mA 2.5 bar
12 mA 5 bar
16 mA 7.5 bar
20 mA 10 bar

The acceptable deviation must be defined by the instrument, module, process, and project accuracy requirements.

15.4 Analog output checks

  • Confirm the intended engineering command and output range.
  • Verify the raw output value and measured electrical signal.
  • Test multiple points across the configured range.
  • Confirm the receiving device interprets the signal correctly.
  • Verify the response to controller faults or communication loss according to the approved design.
  • Ensure that test procedures cannot cause hazardous or unexpected machine movement.

15.5 Safety-related testing

Safety I/O and safety functions require the applicable verification and validation procedures, including proof of the intended safety response and relevant diagnostics. A standard PLC force or ordinary I/O loop check is not a substitute for safety validation.

16. Common faults and troubleshooting

Symptom Likely causes Verification
DI never turns ON Missing supply, wrong polarity, broken wire, incorrect sensor type, wrong channel Measure field voltage and trace the signal to the assigned channel
DI stays ON continuously Short circuit, incorrect common, sensor misalignment, wrong active-state assumption Inspect wiring and verify sensor state against module indication
PNP sensor does not work Incompatible input common or wiring arrangement Check the manufacturer's wiring diagram and current path

A useful troubleshooting sequence is to trace the signal from its source toward the destination: field device, field wiring, terminal, I/O channel, PLC tag, logic, and HMI/SCADA representation. This avoids changing PLC code to compensate for a wiring fault, one of industry's more expensive forms of guesswork.

17. Managing the I/O list with Excel or a database

For a large machine or plant, maintain one controlled register and generate views or reports from it rather than keeping separate, manually edited copies for every discipline.

Useful automated checks

  • Duplicate I/O IDs and duplicate signal tags.
  • Missing descriptions, signal types, units, or destinations.
  • Analog signals without electrical and engineering ranges.
  • Incompatible module type and signal type.
  • Duplicate controller/channel assignments.
  • Unallocated or invalid hardware channels.
  • Mismatch between the I/O list and PLC tag export.
  • Mismatch between device tags, cable references, and terminal references.
  • Required alarms or interlocks without associated functional references.
  • Safety-related points assigned to unsuitable standard hardware.
  • Spare capacity by I/O type and installed module.
  • Changes between revisions and unverified field modifications.

Suggested workbook structure

Worksheet Purpose
I/O_REGISTER Authoritative signal records
PLC_HARDWARE Controllers, stations, modules, and channel capacities
TAG_STANDARDS Naming rules and approved signal classifications
CROSS_REFERENCE Cable, terminal, drawing, alarm, and PLC tag references
VALIDATION Duplicate checks, missing fields, and compatibility checks
CHANGE_LOG Revision history, change reason, approvals, and status
LOOP_CHECK Test values, results, dates, and verification records

Use data validation lists for controlled fields and formulas or scripts for repeatable checks. If Excel is used, protect the released register and record who approved changes. If the register is database-backed, use stable IDs, defined relationships, and revision control.

The I/O list should have a declared owner and a defined source-of-truth policy. The electrical drawing, PLC project, and register may contain different representations of the same signal, but none should be silently edited in isolation.

18. Revision control and change management

Any change affecting a signal should trigger an impact review. Examples include replacing a sensor with a different output type, moving a signal to another I/O module, changing a transmitter range, migrating a PLC, adding an alarm, or changing a robot handshake.

A controlled change process should:

  1. Identify the affected equipment and signal tags.
  2. Determine the impact on electrical design, module allocation, software, HMI, alarms, networks, safety, and commissioning.
  3. Obtain the required technical review and approval.
  4. Update the affected engineering records and software configuration.
  5. Verify the change through the appropriate tests.
  6. Update the as-built register and retain the evidence.

A revision number alone does not prove that a change was reviewed or tested. The record should capture what changed, why it changed, who approved it, and how it was verified.

19. Interview questions and answers

Q1. What is an I/O list?

An I/O list is a structured register defining field and communication signals, their functional meaning, electrical interface, controller allocation, and relevant software and documentation references.

Q2. Why is an I/O list required before PLC programming?

It establishes the signal definitions, expected behavior, and hardware mapping that the PLC program must use. It reduces ambiguity and exposes missing or incompatible signals before commissioning.

Q3. What is the difference between an I/O list and a PLC tag database?

The I/O list coordinates signal definitions across engineering disciplines and documents physical interfaces and references. The PLC tag database defines software variables and their data types and references. The two must remain consistent.

Q4. Can every PLC tag be counted as one physical I/O point?

No. Internal flags, timers, calculations, sequence states, and derived values may be software-only. Networked signals also need to be distinguished from physical module channels.

Q5. What is the difference between DI and DO?

A DI receives a discrete status or condition from the field. A DO sends a discrete command to a field device or interface.

Q6. Why use 4–20 mA instead of 0–20 mA for an analog transmitter?

The 4 mA live zero allows a zero process measurement to be distinguished from certain below-range fault conditions. Actual fault detection depends on the transmitter and input configuration.

Q7. What is the difference between a command and feedback?

A command requests an action. Feedback indicates the reported state or result. A motor start command does not prove the motor is running.

Q8. How do you calculate the number of I/O modules required?

Divide the required channel count by the usable channels per module and round up. Then check interface compatibility, isolation, channel grouping, safety requirements, power, space, and spare capacity.

Q9. What causes an incorrect analog value even when the PLC input is changing?

Possible causes include incorrect scaling limits, wrong transmitter configuration, mismatched units, wiring faults, calibration error, incorrect module settings, or double scaling in software or HMI.

Q10. How would you troubleshoot a sensor that works electrically but does not operate the sequence?

Verify the correct field device, terminal, module channel, PLC tag mapping, program conditions, permissives, interlocks, and sequence state. Confirm that the software is using the intended tag and polarity.

Q11. How is a safety-related signal different from a standard DI?

A safety-related signal is part of a defined safety function and must use an appropriate safety architecture and validated implementation. A standard DI may provide diagnostic status but does not automatically satisfy safety requirements.

Q12. What makes an I/O list ready for commissioning?

The signal definitions and hardware allocations are approved, electrical and software references are consistent, required fault behavior is defined, and the team has a controlled test procedure and acceptance criteria.

Q13. What are the most important automated I/O list checks?

Duplicate identifiers, missing required fields, channel conflicts, signal-to-module incompatibility, inconsistent scaling, invalid references, unallocated signals, and differences from the PLC hardware configuration.

Q14. Why should the I/O list be updated after commissioning?

The as-built record must reflect actual installed wiring, final channel assignments, approved design changes, and verified signal behavior. Otherwise, future maintenance starts from incorrect information.

Q15. What is the practical value of a well-maintained I/O list in industrial maintenance?

It accelerates fault tracing, helps identify the correct spare module or field device, reduces undocumented changes, supports migration and retrofit work, and preserves signal-level knowledge of the machine.

20. Final engineering principles

  • Treat the I/O list as a controlled engineering register, not merely a spreadsheet of addresses.
  • Define each signal's meaning, interface, allocation, and expected behavior.
  • Keep physical channels, network data, and internal software variables distinct.
  • Coordinate the register with electrical drawings, instrumentation data, PLC tags, HMI/SCADA, alarms, safety requirements, and commissioning records.
  • Validate electrical compatibility and signal scaling before assuming the PLC program is at fault.
  • Maintain traceability from the field device through the hardware and software to the operator interface.
  • Release an accurate as-built register so the next engineer can troubleshoot or modify the machine without reconstructing its design from scratch.
