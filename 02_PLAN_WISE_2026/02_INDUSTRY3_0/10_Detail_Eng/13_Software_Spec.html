1. Definition and purpose

A software specification is a controlled technical document that defines what the automation software must do, how its functions are organized, how it interacts with other systems, and how compliance will be verified.

It converts the approved machine requirements, control philosophy, sequence descriptions, interlocks, alarm definitions, and interface requirements into precise, implementable, and testable software requirements.

The specification should define the expected behavior without necessarily prescribing every line of PLC code. It establishes the contract against which software development, FAT, SAT, commissioning, and future modifications are evaluated.

1.1 Primary objectives

  • Define software functionality before programming begins.
  • Establish consistent programming and naming standards.
  • Specify machine states, operating modes, commands, permissives, interlocks, alarms, and recovery behavior.
  • Define PLC, HMI, SCADA, robot, CNC, drive, and external-system interfaces.
  • Ensure predictable behavior during faults, communication loss, power interruption, and controller restart.
  • Make every important requirement testable.
  • Maintain traceability from the original requirement through implementation and acceptance testing.
  • Reduce commissioning time, troubleshooting effort, and dependence on undocumented programmer knowledge.

1.2 What a software specification is not

A software specification is not merely a PLC program description, a list of I/O addresses, a collection of ladder diagrams, or a programming-style guide.

A specification describes required behavior. The actual implementation may use ladder logic, structured text, function blocks, state machines, or a combination of programming languages.

2. Position within detailed engineering

The software specification connects engineering design documents to the software implementation and its verification.

Machine requirements and process requirements
                    ↓
          Control philosophy
                    ↓
      Sequence and interface definitions
                    ↓
  I/O list, interlocks, alarms, cause/effect
                    ↓
          Software specification
                    ↓
     PLC / HMI / robot / drive software
                    ↓
           FAT and SAT verification
                    ↓
        Approved software baseline

The actual engineering workflow is iterative. Software development may expose missing requirements, incorrect I/O assumptions, or conflicts that require approved updates to earlier documents.

2.1 Relationship with other documents

Document Main question answered Relationship to software specification
Control philosophy How should the machine be controlled? Establishes overall control principles
Functional design specification What functions must the machine perform? Defines detailed functional behavior
Sequence description What happens and in what order? Provides operating sequences and transitions
I/O list What signals exist? Defines signal identities and characteristics
Interlock list What conditions prevent or stop an action? Defines interlock requirements
Alarm list What faults must be reported? Defines alarm identity and operator response
Cause-and-effect matrix What happens when a specified event occurs? Defines required reactions to events
HMI specification What must operators see and control? Defines screens, commands, indications, and navigation
Safety requirements specification What safety functions are required? Defines safety-related behavior and performance requirements
Software specification What must the software implement and how will it be verified? Consolidates implementable, testable software requirements

The software specification should reference authoritative source documents rather than independently duplicating them without revision control.

3. Software requirement lifecycle

Each requirement should progress through a controlled lifecycle.

  1. Identify: Assign a unique requirement ID.
  2. Define: Describe the required behavior precisely.
  3. Review: Check technical feasibility, safety, consistency, and completeness.
  4. Approve: Obtain authorization from the responsible engineering stakeholders.
  5. Implement: Map the requirement to software modules, routines, tags, and configuration.
  6. Verify: Execute tests that demonstrate compliance.
  7. Resolve deviations: Record defects, corrective actions, and retest results.
  8. Baseline: Freeze the approved version for release or shipment.
  9. Maintain: Control future changes through impact assessment and revalidation.

A requirement is not complete merely because a programmer says the feature is finished. It is complete when the approved acceptance criteria have been satisfied and the evidence has been recorded.

3.1 Requirement quality

A useful software requirement should be:

  • Unambiguous: One reasonable interpretation.
  • Complete: Includes relevant preconditions, action, and expected result.
  • Consistent: Does not conflict with other requirements.
  • Feasible: Can be implemented on the selected platform.
  • Verifiable: Can be demonstrated by inspection, analysis, or testing.
  • Traceable: Has links to its origin, implementation, and verification evidence.
  • Controlled: Has an owner, revision history, and approval status.

Avoid vague requirements such as “the machine should stop quickly” or “the alarm should work properly.”

Prefer measurable requirements such as “when the configured axis-position deviation exceeds the approved limit during automatic operation, the controller shall inhibit the next cycle and generate alarm ALM-AXIS-004.”

The actual threshold, response time, operating conditions, and required stop behavior must come from approved engineering requirements, not assumptions introduced by the programmer.

4. Scope and boundaries

The specification should clearly state which software components are included.

Typical scope includes:

  • PLC application logic.
  • HMI application and operator commands.
  • SCADA interfaces and production data exchange.
  • Robot and CNC communication or program-selection interfaces.
  • VFD, servo, and motion-control interfaces.
  • Barcode, RFID, vision, gauging, and inspection-system interfaces.
  • Industrial network communication.
  • Recipe, parameter, and product-variant management.
  • Diagnostics, alarms, event logging, and maintenance functions.
  • Data collection, traceability, and integration with MES or other higher-level systems.

It should also identify excluded functions and the responsible external system. For example, the PLC may issue a robot-start request and monitor the robot's completion handshake, while the robot controller owns the robot motion program.

An interface must have an explicit owner. Otherwise, both systems may assume that the other one is responsible for a command, reset, timeout, or fault recovery.

5. Software architecture specification

The architecture defines how the application is divided into logical components and how those components interact.

5.1 Example architecture

Application
    ↓
Equipment modules
    ├── Motors and VFDs
    ├── Servo axes
    ├── Cylinders and valves
    ├── Robots and CNC interfaces
    └── Sensors and inspection devices
    ↓
Sequence and coordination layer
    ↓
Mode, command, permissive and fault management
    ↓
I/O and communication layer
    ↓
Physical devices and external controllers

Safety functions should be architected separately according to their required safety integrity and validated interfaces. A standard PLC application does not become safety-rated merely because its logic contains an emergency-stop condition.

5.2 Program organization

A software specification may define the following components.

Component Responsibility Example
Main task or cyclic routine Executes the primary application structure MAIN_TASK
I/O mapping Converts physical signals into application-level data IO_MAPPING
Equipment function block Reusable device behavior FB_MOTOR
Sequence module Controls a process step or machine cycle FB_LOAD_SEQUENCE
Mode manager Controls operating-mode selection and authority FB_MODE_MANAGER
Alarm manager Evaluates and organizes alarm conditions FB_ALARM_MANAGER
Communication manager Monitors external connections and data validity FB_COMM_MANAGER
Diagnostics module Provides fault context and maintenance data FB_DIAGNOSTICS
HMI interface module Exchanges commands and status with the HMI HMI_INTERFACE

These are illustrative names. The final organization must follow the chosen PLC platform, project conventions, and approved engineering standards.

5.3 Modularity and reusable equipment blocks

Reusable function blocks reduce duplicated logic and make behavior more consistent across machines.

For example, a motor function block could contain:

  • Start and stop requests.
  • Run feedback monitoring.
  • Ready and fault status.
  • Permissive evaluation.
  • Start timeout and running-feedback timeout.
  • Fault acknowledgement handling.
  • Manual and automatic command interfaces.
  • Diagnostic status and alarm identification.

The block should not silently take ownership of process sequencing that belongs in a higher-level sequence module.

A reusable block also needs clearly defined behavior when commands conflict, feedback is invalid, communication is lost, or the controller restarts.

6. Naming conventions and data standards

Naming standards make software readable, searchable, maintainable, and easier to integrate with HMI and SCADA systems.

6.1 Example naming convention

Object Example Meaning
Digital input DI_CLAMP_EXTENDED Clamp extended sensor
Digital output DO_CLAMP_EXTEND Clamp extension command
Analog input AI_PRESSURE_BAR Pressure measurement
Internal status ST_AUTO_MODE Automatic mode active
Command CMD_CYCLE_START Cycle-start request
Permissive PRM_CYCLE_START All required start conditions satisfied
Interlock ILK_GUARD_CLOSED Guard-closure condition
Alarm ALM_CLAMP_TIMEOUT Clamp movement timeout

Prefix conventions vary between organizations. Consistency matters more than any particular prefix.

6.2 Data type requirements

Specify suitable data types and their intended meaning.

Data type Typical use Important consideration
BOOL Binary status or command Define whether it is a pulse, maintained request, or latched condition
INT / DINT Counts, state numbers, integer values Define valid range and overflow behavior
REAL Analog values and engineering calculations Define units, precision, and invalid-value behavior
TIME Delays and timeout settings Define units, limits, and configurable versus fixed values
ENUM or named constants Modes and sequence states Use explicit state names rather than unexplained numeric values
STRUCT / UDT Grouped equipment data Define field names, ownership, and interface compatibility
STRING Recipe names, identifiers, messages Define maximum length, encoding, and validation rules

Avoid unexplained numeric constants scattered throughout logic. Use named constants or approved parameters so that the meaning and permitted range are explicit.

6.3 Engineering units and scaling

Analog data must have documented raw ranges, engineering ranges, units, and invalid-signal handling.

For linear scaling:

\[ EU = EU\_{\min} + \frac{Raw-Raw\_{\min}}{Raw\_{\max}-Raw\_{\min}} (EU\_{\max}-EU\_{\min}) \]

Where:

  • \(Raw\) is the measured raw input.
  • \(EU\) is the scaled engineering value.
  • \(Raw\_{\min}\) and \(Raw\_{\max}\) define the raw measurement range.
  • \(EU\_{\min}\) and \(EU\_{\max}\) define the engineering range.

For example, a configured 4–20 mA pressure transmitter may represent 0–10 bar. The software must distinguish valid measurements from under-range, over-range, wire-break, or module-diagnostic conditions where supported.

A numerically plausible value does not necessarily represent a valid measurement.

7. Functional software requirements

Functional requirements describe observable behavior, including normal operation, abnormal conditions, and recovery.

7.1 Operating modes

The specification should define the available modes, how each mode is selected, which commands are allowed, and how transitions are controlled.

Mode Typical purpose Required restrictions
Automatic Execute the production sequence All required automatic permissives must be satisfied
Manual Operate individual equipment under controlled conditions Command ownership and movement restrictions must be explicit
Setup Perform tooling, teaching, or setup operations Only approved setup functions are available
Maintenance Support authorized service activity Defined access and energy-control procedures apply
Recovery Return the machine to a known state after a fault Recovery steps and completion conditions must be defined
Local Give authority to a local device or station Remote commands must be inhibited as specified
Remote Accept commands from an authorized external controller Remote ownership and communication validity must be established

Not every machine requires all these modes. The specification must also define whether a mode change is permitted during movement, during an active cycle, or while a fault is present.

Software mode selection does not replace lockout/tagout, safe isolation, or other required energy-control procedures.

7.2 Command arbitration

The software must define what happens when multiple sources request control.

Possible command sources include:

  • Local pushbuttons.
  • HMI commands.
  • Automatic sequence logic.
  • Robot or CNC interfaces.
  • SCADA or MES commands.
  • Maintenance tools.

A command-arbitration requirement should identify the permitted command owner, authority precedence, behavior when ownership changes, and how rejected commands are reported.

Example: a remote cycle-start command shall be rejected when local control owns the station, and the HMI shall indicate that remote start is unavailable because local authority is active.

Never allow two independent command sources to write directly to the same physical output without a defined arbitration mechanism.

7.3 Start, stop, reset, and restart

These commands have different purposes and must not be treated as interchangeable.

  • Start: Requests a defined operation when all required conditions are satisfied.
  • Stop: Requests the specified stopping behavior.
  • Reset: Clears eligible faults or latches after the underlying conditions have been addressed.
  • Restart: Reinitiates a defined activity after a stop, fault, or interruption, subject to the applicable rules.

The specification should define command pulse duration or maintained behavior, acceptance conditions, rejection feedback, priority, and expected state changes.

Reset should not automatically initiate motion unless that behavior is explicitly justified, approved, and compatible with the machine's safety requirements. A reset is not proof that the machine is safe to restart.

7.4 Permissives, interlocks, and fault responses

A permissive establishes that required conditions are satisfied before an action can begin. An interlock restricts an action or requires a specified reaction when a condition is violated. A fault represents a detected abnormal condition requiring a defined response.

For every important condition, specify:

  • The originating signal or calculation.
  • The affected equipment or operation.
  • Whether it prevents starting, stops an active operation, or both.
  • Whether the condition is latched.
  • Whether operator acknowledgement is required.
  • The conditions for clearing it.
  • The diagnostic message and test method.

An interlock must be implemented at the appropriate control layer. Safety-related interlocks must use the required safety architecture, not merely a standard PLC bit.

7.5 Timers and timeout handling

Every monitored movement or communication exchange should have an explicit timeout requirement where a timeout is necessary.

Specify:

  • The event that starts the timer.
  • The event that stops or resets it.
  • The allowed duration and its source.
  • The fault generated on expiration.
  • The action taken on timeout.
  • Whether the timeout is adjustable and how changes are authorized.
  • The conditions for retry or recovery.

A timer should monitor an expected transition, not simply delay the next instruction without verifying that the required action actually occurred.

7.6 Retentive and non-retentive data

Define which data survives a power cycle, controller restart, or download.

Potentially retentive data includes approved recipes, calibration settings, production counters, or selected configuration values. Transient commands, sequence-in-progress flags, and temporary handshake requests often require deliberate clearing or reconciliation after restart.

The specification must state which values are retained, their storage mechanism, integrity requirements, default behavior, and validation procedure. Retention must never be assumed to mean that an interrupted operation can safely resume automatically.

8. Sequence and state-machine requirements

Complex processes should have defined states and explicit transition conditions.

A typical sequence may include:

  • IDLE
  • CHECK_PERMISSIVES
  • CLAMP
  • PROCESS
  • UNCLAMP
  • COMPLETE
  • FAULT
  • RECOVERY

For each state, define entry conditions, actions, exit conditions, timeout behavior, and behavior when an unexpected event occurs.

8.1 Example state transition logic

STATE: IDLE
  Accept cycle start only when start permissives are valid.
  On accepted start, move to CHECK_PERMISSIVES.

STATE: CHECK_PERMISSIVES
  Verify guards, equipment readiness, required communication,
  and other approved start conditions.
  If valid, move to CLAMP.
  If invalid, remain inhibited and report the blocking condition.

STATE: CLAMP
  Command clamp extension.
  Confirm the required position before timeout.
  If confirmed, move to PROCESS.
  If timeout expires, enter FAULT.

STATE: PROCESS
  Execute the approved process.
  Verify process completion and required quality conditions.
  If successful, move to UNCLAMP.
  If a defined fault occurs, execute the specified fault response.

STATE: UNCLAMP
  Command unclamping.
  Confirm the required position.
  If confirmed, move to COMPLETE.
  If timeout expires, enter FAULT.

STATE: COMPLETE
  Report cycle completion and update approved production records.
  Return to IDLE when the completion handshake is satisfied.

STATE: FAULT
  Apply the defined response.
  Preserve diagnostic information as required.
  Allow recovery only under the approved recovery conditions.

This example is conceptual. Real sequences must define exact transitions, state entry behavior, command ownership, fault priorities, and safety-related responses.

8.2 State-machine design rules

  • Define every state and every permitted transition.
  • Avoid multiple unrelated states being represented by the same unexplained integer.
  • Define what happens when an unexpected transition request occurs.
  • Ensure that commands cannot remain unintentionally active after a state change.
  • Define behavior when a sensor is already active before the sequence begins.
  • Prevent repeated entry actions from causing duplicate physical commands.
  • Provide diagnostic visibility of the current state and the reason for a blocked transition.
  • Define recovery from every state in which recovery is permitted.

9. Handshake and equipment interface specification

Machine-to-machine communication requires a documented contract for requests, acknowledgements, completion, and faults.

9.1 Example robot handshake

Signal Owner Meaning
PLC_ROBOT_START_REQ PLC PLC requests robot cycle start
ROBOT_START_ACK Robot Robot accepts the request
ROBOT_BUSY Robot Robot is executing the operation
ROBOT_CYCLE_COMPLETE Robot Robot reports completion
ROBOT_FAULT Robot Robot reports a fault condition
PLC_ROBOT_RESET_REQ PLC PLC requests the defined reset action

Define whether each signal is pulsed or maintained, which event clears it, the timeout limits, and what happens after communication loss.

A robust request/acknowledge pattern may work as follows:

PLC validates start conditions
    ↓
PLC raises start request
    ↓
Robot accepts request and raises acknowledgement
    ↓
Robot reports busy
    ↓
Robot reports completion
    ↓
PLC verifies completion and clears the request
    ↓
Both systems return to the defined handshake-ready condition

The handshake must avoid duplicate execution if one controller restarts while the other retains an old request. If a request identifier or sequence counter is used, its behavior during restart must also be defined.

10. Alarm and diagnostic software requirements

The software specification should reference the approved alarm list and define how alarm conditions are evaluated and presented.

For each alarm, identify:

  • Alarm ID and descriptive text.
  • Trigger condition.
  • Affected equipment and operation.
  • Severity or priority.
  • Whether it is latched or automatically clears.
  • Acknowledgement requirements.
  • Reset requirements.
  • Required operator action.
  • Diagnostic data to preserve.
  • Alarm history and timestamp behavior.
  • FAT test conditions.

10.1 Example alarm requirement

Field Example
Requirement ID SWR-ALM-014
Alarm ID ALM-CLAMP-EXT-TMO
Trigger Clamp extension feedback is not confirmed before the approved timeout
Required response Inhibit process progression and execute the defined machine response
Operator message Clamp extension timeout
Diagnostic detail Requested state, feedback state, timer status, and sequence state
Reset condition Timeout condition cleared and approved reset conditions satisfied
Verification Simulate missing extension feedback and verify the response

An alarm message should describe the fault in a way that helps the operator or maintenance technician identify the next diagnostic step.

10.2 First-out fault capture

Where several faults can occur together, define whether the software records the first detected fault, subsequent faults, or both.

First-out information can help identify the initiating event rather than a downstream symptom. For reliable diagnostics, define timestamp resolution, event ordering, data retention, and how the record behaves after a controller restart.

11. HMI and SCADA requirements

The specification should define the required operator interface and the relationship between displayed values and PLC data.

11.1 HMI requirements

Specify:

  • Required screens and navigation.
  • Machine overview and equipment detail screens.
  • Automatic, manual, setup, and recovery controls.
  • Command enable and rejection indications.
  • Current sequence state and active step.
  • Permissive and interlock status.
  • Alarm summary and alarm history.
  • Maintenance diagnostics and I/O monitoring.
  • Recipe selection and parameter entry.
  • User roles and command permissions.
  • Units, display precision, and value ranges.
  • Behavior when PLC communication is lost.

An HMI button should not appear available when its command cannot be accepted, unless there is a clear reason to show the command and explain its rejection.

11.2 HMI command specification

Each operator command should define:

  • Command tag and data type.
  • Authorized user role.
  • Required machine mode.
  • Preconditions.
  • Pulse or maintained-command behavior.
  • PLC acceptance feedback.
  • Rejection reason.
  • Timeout and communication-loss behavior.
  • Event logging requirements where applicable.

HMI permissions are not a substitute for PLC-side authorization and permissive checks. Critical restrictions must be enforced at the appropriate controller or safety layer.

11.3 SCADA, historian, and production data

For each exchanged tag, define the tag name, data type, engineering units, source, update behavior, quality status, and retention requirements.

Examples include:

  • Cycle start and completion timestamps.
  • Machine mode and equipment state.
  • Fault and alarm events.
  • Good, rejected, and total part counts.
  • Recipe or product identifier.
  • Process measurements and quality results.
  • Equipment availability and downtime reasons.

Distinguish live status from historical records. If a value is stale because of communication loss, the display should not continue presenting it as a valid current measurement.

12. Communication requirements

The software specification should define the communication interfaces between controllers, drives, robots, HMIs, and higher-level systems.

12.1 Required interface details

  • Protocol and supported version.
  • Device identity, network address, and port where applicable.
  • Producer and consumer of each data item.
  • Data type, byte order, and scaling where relevant.
  • Update rate or maximum permitted data age.
  • Connection and data-validity monitoring.
  • Timeout and watchdog requirements.
  • Startup and reconnection behavior.
  • Error reporting and diagnostic information.
  • Behavior when communication fails or returns.

Do not confuse a successful network connection with valid application data. A connection may be established while individual tags are stale, incorrectly mapped, or carrying invalid status.

12.2 Communication-loss behavior

For each interface, define what happens if communication is interrupted during idle, active movement, process execution, and recovery.

The response may differ by equipment and operation. For example, a lost production-data connection may allow a controlled local process to continue under an approved policy, while loss of a required robot handshake may require the sequence to stop progressing.

The correct response must come from the approved machine and safety requirements.

13. Safety-related software requirements

Safety-related software must be designed and validated according to the required safety architecture, risk assessment, and applicable standards.

Relevant standards may include ISO 12100 for machinery risk assessment and risk reduction, ISO 13849-1 for safety-related control systems, IEC 62061 for functional safety of machinery control systems, and IEC 60204-1 for electrical equipment of machines. The applicable edition and jurisdictional requirements must be confirmed for the project.

The software specification should identify:

  • Required safety functions and their originating requirements.
  • The responsible safety controller, safety relay, or other safety-rated device.
  • Required performance level or safety integrity level where applicable.
  • Safety input and output behavior.
  • Reset and restart conditions.
  • Diagnostic coverage and fault reactions as required by the design.
  • Interfaces between safety-related and standard control.
  • Verification, validation, and required evidence.
  • Restrictions on software changes and bypasses.

A standard PLC bit indicating that a guard is closed is not automatically a safety-rated guard-monitoring function. The complete safety function, including sensing, logic, output elements, architecture, and validation, must meet its specified requirements.

Safety bypasses, where permitted by the approved design, require controlled authorization, clear indication, time or condition limits where applicable, and a defined return-to-normal procedure. Software bypasses must not defeat mandatory safety functions.

14. Startup, restart, and recovery behavior

Power interruption and controller restart are important specification scenarios because retained data and physical equipment states may no longer agree.

The software should define:

  • Initial state after cold start and warm restart.
  • Initialization of transient commands and internal flags.
  • Validation of retained parameters and recipes.
  • Reconciliation of PLC state with physical sensor feedback.
  • Re-establishment of communication and handshake status.
  • Behavior when an actuator is in an unexpected position.
  • Conditions that require operator intervention.
  • Conditions under which automatic operation may resume.
  • Preservation of relevant alarms and diagnostic information.

A common design error is to restore the previous sequence number and continue operating without checking the actual machine state. Retaining a software state does not prove that the corresponding physical action completed.

15. Performance and reliability requirements

Performance requirements should be measurable and derived from process needs and platform capabilities.

Potential requirements include:

  • Maximum time from a valid command to the expected software response.
  • Maximum data age for critical communications.
  • Sequence timeout limits.
  • HMI update behavior.
  • Alarm detection and reporting latency.
  • Controller task execution and watchdog constraints.
  • Startup initialization time.
  • Required data retention and recovery.
  • Maximum supported device, tag, recipe, or alarm counts.

Do not impose arbitrary scan-time targets without considering the controller, application size, communication load, motion requirements, and vendor guidance.

Time-critical motion and safety functions require their own suitable architecture and timing analysis. An ordinary HMI refresh rate is not an acceptable basis for a safety response-time calculation.

16. Software cybersecurity and change control

The software specification should define appropriate controls for access, configuration, and modification of industrial automation systems.

Requirements may include:

  • Authorized engineering access to PLC, HMI, robot, CNC, and drive configurations.
  • Unique user accounts where supported and appropriate.
  • Role-based permissions and controlled remote access.
  • Approved network paths and communication services.
  • Backup and restoration procedures.
  • Version identification for source code and released binaries.
  • Change approval and impact assessment.
  • Records of software downloads and configuration changes where supported.
  • Recovery procedures for corrupted or unavailable project files.
  • Protection of credentials and sensitive configuration data.

Use a version-control system where practical. A released software baseline should be identifiable by project version, controller target, applicable hardware configuration, and relevant parameter or recipe versions.

A backup is not fully verified until restoration has been tested on the intended platform or an appropriately representative environment.

17. Software verification and testability

Every requirement should be connected to one or more verification methods.

17.1 Verification methods

  • Inspection: Review code, configuration, naming, or documentation.
  • Analysis: Demonstrate compliance through engineering calculations or technical analysis.
  • Demonstration: Observe the function under defined operating conditions.
  • Test: Apply controlled inputs and verify measured results against acceptance criteria.

17.2 Requirement traceability matrix

Requirement ID Requirement Software location Test ID Acceptance evidence
SWR-MODE-001 Reject automatic start when required permissives are false Mode manager and sequence module FAT-MODE-001 Start is rejected and blocking condition is visible
SWR-SEQ-004 Advance to processing only after clamp extension is confirmed Clamp sequence state FAT-SEQ-004 Sequence advances only after valid feedback
SWR-ALM-014 Generate clamp timeout alarm if feedback is not confirmed Alarm manager and clamp module FAT-ALM-014 Correct alarm and defined response occur
SWR-COM-003 Inhibit sequence progression when required robot data becomes invalid Communication manager FAT-COM-003 Sequence does not progress using invalid data
SWR-REC-002 Do not resume an interrupted cycle until approved restart conditions are satisfied Startup and recovery modules FAT-REC-002 Restart follows the specified recovery process

The IDs and examples are illustrative. Real project IDs must be unique and consistent across the specification, implementation records, and test documents.

17.3 Test coverage

Testing should include more than normal operation.

  • Normal operating conditions.
  • Minimum and maximum permitted values.
  • Invalid or contradictory sensor combinations.
  • Missing feedback and timeout conditions.
  • Repeated or held commands.
  • Conflicting command sources.
  • Communication interruption and restoration.
  • Controller restart and power interruption.
  • Alarm acknowledgement and reset behavior.
  • Unauthorized command attempts.
  • Recovery from each permitted fault state.
  • Safety-function validation under the applicable safety plan.

For software-controlled safety functions, ordinary functional FAT tests do not replace the required safety validation.

18. Example software requirement set

Consider a machine that loads a component, clamps it, performs an operation, and unloads it.

Requirement ID Requirement statement Verification
SWR-START-001 The PLC shall accept an automatic cycle-start request only when all specified start permissives are valid Test start with each required permissive satisfied and violated
SWR-CLAMP-001 The clamp command shall be issued only after the sequence enters the approved clamp state Inspect logic and monitor the output during sequence testing
SWR-CLAMP-002 The sequence shall not enter the process state until valid clamp-extended feedback is confirmed Test valid feedback, missing feedback, and timeout
SWR-PROC-001 The process-complete transition shall require the approved completion condition Test completion and incomplete-process conditions
SWR-ALARM-001 A clamp timeout shall produce the specified alarm and prevent further sequence progression Remove feedback and verify alarm and state
SWR-COM-001 Invalid robot handshake data shall prevent dependent sequence transitions Interrupt or invalidate the required interface
SWR-REC-001 An interrupted sequence shall enter the specified restart or recovery behavior rather than resuming blindly Interrupt operation and perform the approved restart test
SWR-HMI-001 The HMI shall display the current sequence state and relevant blocking conditions Compare HMI indications with controller status

Each requirement should be specific enough that two independent testers can execute the test and reach the same pass/fail conclusion.

19. FAT and SAT software deliverables

The software specification should establish the software-related deliverables expected at acceptance.

Typical deliverables include:

  • Approved software specification.
  • PLC and HMI application source files.
  • Robot, CNC, drive, and other configuration files within project scope.
  • Hardware and software version inventory.
  • Tag and interface mapping.
  • Alarm, interlock, and sequence references.
  • Test procedures and completed test records.
  • Requirement traceability matrix.
  • Open-issue and deviation register.
  • Backup and restoration instructions.
  • Parameter and recipe configuration records.
  • Software revision and change history.
  • Recovery, maintenance, and troubleshooting documentation.
  • Final released software baseline.

The FAT should verify the defined behavior before shipment to the extent possible. The SAT should verify the functions that depend on actual site installation, field wiring, production interfaces, utilities, and real operating conditions.

A test that cannot be completed during FAT should have a documented reason, a responsible owner, and an agreed SAT or later verification activity.

20. Common software specification mistakes

  • Writing requirements such as “logic should be correct” without acceptance criteria.
  • Copying the control philosophy without adding software-level precision.
  • Defining sequence states but omitting timeout and fault transitions.
  • Defining alarms without specifying reset and recovery behavior.
  • Leaving command ownership between PLC, HMI, robot, and SCADA ambiguous.
  • Using raw I/O addresses directly throughout the program without a consistent mapping strategy.
  • Allowing multiple modules to control the same output without arbitration.
  • Failing to define valid, invalid, stale, and unavailable data states.
  • Assuming communication recovery means the process is ready to resume.
  • Retaining sequence state without reconciling it against the physical machine.
  • Using HMI permissions as the only enforcement of command restrictions.
  • Treating standard PLC logic as a replacement for safety-rated functions.
  • Changing timers or process parameters without approval and traceability.
  • Releasing software without an identified version, verified backup, and test evidence.
  • Writing test cases that merely demonstrate the expected successful cycle while ignoring failure scenarios.

21. Practical review checklist

Before software development

  • Scope, exclusions, assumptions, and system boundaries are documented.
  • Source requirements and referenced documents have approved revisions.
  • PLC, HMI, robot, CNC, drive, and external interfaces are defined.
  • Program structure and naming conventions are approved.
  • Modes, commands, ownership, permissives, interlocks, and fault responses are defined.
  • Sequence states, transitions, timeouts, and recovery behavior are defined.
  • Safety-related requirements and their responsible systems are identified.
  • Requirements have measurable acceptance criteria.

Before FAT

  • Every applicable requirement has an implementation and verification reference.
  • Normal and abnormal operating scenarios are covered.
  • Communication-loss and restart behaviors have been tested.
  • Alarm, acknowledgement, reset, and recovery behavior has been verified.
  • HMI indications and controller behavior agree.
  • Open deviations have owners and agreed dispositions.
  • Software versions and test evidence are recorded.

Before shipment and handover

  • Released software matches the approved baseline.
  • Source files and configuration backups are available.
  • Restoration procedures have been verified.
  • Known limitations and open issues are documented.
  • Required FAT evidence and traceability records are complete.
  • Site-dependent verification activities are identified for SAT.
  • Changes after testing have been assessed and appropriately retested.

22. Interview questions and answers

1. What is the purpose of a software specification?

It defines the software behavior, architecture, interfaces, constraints, and verification criteria required to implement the approved machine design consistently.

2. What is the difference between a control philosophy and a software specification?

The control philosophy defines the overall principles of machine operation. The software specification translates those principles and related engineering requirements into specific, implementable, and verifiable software requirements.

3. Why must requirements be traceable?

Traceability demonstrates that each requirement has been implemented and verified. It also supports impact analysis when a requirement changes.

4. What is the difference between a permissive and an interlock?

A permissive establishes whether an operation is allowed to start or proceed. An interlock restricts an action or triggers a defined reaction when a condition is not satisfied. Exact usage depends on the project's terminology and approved design.

5. Why should a machine use state-based sequencing?

State-based sequencing makes operating phases and transitions explicit. It improves diagnostics, timeout handling, testability, and controlled recovery from abnormal conditions.

6. Why is a communication watchdog insufficient on its own?

A watchdog may indicate that a connection or heartbeat has failed, but it does not necessarily prove that individual application values are current, correctly mapped, or valid. The application must define data-validity and failure behavior.

7. What should happen after a PLC restart during an active cycle?

The software should follow the approved startup and recovery requirements, initialize transient commands appropriately, reconcile controller data with physical feedback, and prevent uncontrolled continuation until the required conditions are satisfied.

8. What is a requirement traceability matrix?

It links requirements to their software implementation and verification evidence, allowing reviewers to identify missing implementation, missing tests, and the impact of changes.

9. Does successful FAT prove that a machine is safe?

No. FAT provides evidence against the tests and scope performed. Safety validation must separately demonstrate that the specified safety functions satisfy the applicable safety requirements, and site-dependent conditions may require SAT verification.

10. How should a software change be controlled?

Record the change request, assess technical and safety impacts, obtain approval, update the relevant specification and software baseline, execute the required regression tests, and preserve the release and test records.

11. What makes a requirement testable?

It specifies the relevant conditions, expected behavior, and objective acceptance criteria so that the result can be judged consistently.

12. Why are recovery requirements as important as normal sequences?

Faults, interrupted operations, and communication failures are inevitable possibilities in industrial systems. Defined recovery behavior prevents ambiguous states, uncontrolled motion, repeated commands, and misleading production status.

23. Final engineering principle

A strong software specification is a bridge between design intent and verified machine behavior. It must be detailed enough to guide implementation, precise enough to eliminate ambiguous interpretations, and structured enough to prove compliance during testing and future maintenance.

The key deliverable is not merely a program that runs. It is a controlled software system whose normal behavior, abnormal responses, interfaces, recovery mechanisms, and limitations are documented and verifiable.
