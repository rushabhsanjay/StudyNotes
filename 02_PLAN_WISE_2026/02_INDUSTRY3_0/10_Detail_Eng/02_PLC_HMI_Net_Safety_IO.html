1. Purpose and Scope

PLC, HMI, network, safety, and I/O architecture defines how an industrial machine senses its physical condition, processes control logic, communicates information, interacts with operators, and achieves required safe behavior.

It establishes the functional boundaries and interfaces between the main automation components before detailed wiring, panel construction, programming, and commissioning begin.

The architecture must answer five fundamental questions:

  • PLC: Which controller executes the machine's sequence, interlocks, and process logic?
  • HMI: How do operators command, monitor, diagnose, and configure the machine?
  • Network: How do controllers, drives, robots, HMIs, remote I/O, and supervisory systems exchange information?
  • Safety: How are identified hazards controlled through appropriately designed and validated safety functions?
  • I/O: How are field sensors, actuators, and electrical signals connected to the control system?

These five areas are interdependent. A change in one can affect the others. For example, replacing a drive with a different model may change the communication protocol, I/O requirements, fault diagnostics, safety interface, network loading, and PLC programming.

The goal is not merely to select components. It is to establish a coherent, verifiable, maintainable automation system.

2. Overall Automation Architecture

A typical industrial automation system contains field devices, control equipment, operator interfaces, industrial networks, and supervisory systems.

Production process and machine
        ↓
Sensors, switches, transmitters and actuators
        ↓
Local I/O and distributed remote I/O
        ↓
PLC / motion controller / machine controller
        ↓
        +-------------------------------+
        |               |               |
       HMI         Drives and robots   Machine interfaces
        |               |               |
        +---------------+---------------+
                        ↓
             Industrial control network
                        ↓
               SCADA / historian / MES
                        ↓
                Production reporting

Safety-related sensors and devices
        ↓
Safety PLC / safety relays / safety-rated control
        ↓
Safety outputs and applicable safety functions

This is a functional overview. A real architecture may use integrated safety controllers, safety communication networks, dedicated motion controllers, CNC controllers, redundant PLCs, or separate OT network zones.

The safety-related architecture must be derived from the machine risk assessment. It cannot be determined simply by drawing a separate safety box.

3. PLC Architecture

A Programmable Logic Controller (PLC) is an industrial controller designed to execute control logic and interact with physical processes.

Typical responsibilities include:

  • Sequence control.
  • Machine state management.
  • Permissive and interlock evaluation.
  • Motor and actuator commands.
  • Sensor monitoring.
  • Fault detection and recovery logic.
  • Communication with other controllers.
  • Production counters and process data.
  • HMI data exchange.
  • Diagnostics and maintenance information.

Examples of PLC platforms include Siemens SIMATIC S7-1200/S7-1500, Rockwell Automation CompactLogix/ControlLogix, and Mitsubishi MELSEC.

3.1 PLC System Components

Component Function Design consideration
CPU Executes the control program Scan performance, memory, communications and lifecycle
Power supply Powers the controller system where required Load capacity and supply reliability
Local I/O Interfaces with nearby field signals Channel count and signal compatibility
Remote I/O Interfaces with distributed field devices Network behavior and installation conditions
Communication module Provides additional network or serial interfaces Required protocols and device compatibility
Memory Stores program and relevant data Capacity, retention and backup requirements
Engineering interface Supports programming and diagnostics Software versions, licenses and access control
Redundancy hardware Supports specified availability objectives Supported topology, failover behavior and testing

Not every PLC requires every component. Hardware selection depends on the application and the platform's capabilities.

3.2 PLC Selection Criteria

PLC selection should consider:

  • Total digital and analog I/O.
  • Required spare capacity.
  • Number of communication connections.
  • Scan-time and response-time requirements.
  • Motion-control requirements.
  • High-speed counting and positioning.
  • Data storage and program size.
  • Safety requirements.
  • Redundancy requirements.
  • Environmental conditions.
  • Programming software and engineering licenses.
  • Plant standardization.
  • Spare availability and lifecycle status.
  • Integration with existing equipment.

Selecting a PLC solely because it has enough I/O points is inadequate. It must also meet the performance, communication, diagnostic, safety, and lifecycle requirements.

3.3 PLC Program Organization

A well-structured PLC program separates functions into understandable sections.

PLC application
    ↓
System initialization
    ↓
Input acquisition and validation
    ↓
Mode and state management
    ↓
Permissives and interlocks
    ↓
Sequence execution
    ↓
Equipment control blocks
    ↓
Alarm and diagnostic processing
    ↓
Output command processing
    ↓
Data exchange and monitoring

The actual execution order depends on the PLC platform, task configuration, and program design.

A modular program may contain reusable motor, valve, drive, axis, alarm, and communication function blocks. Each block should have a defined interface and documented behavior.

3.4 Scan Time and Response Time

PLC scan time is the time taken to execute the relevant cyclic processing. Actual response time also depends on input filtering, I/O update behavior, task scheduling, network delays, output processing, and the physical device.

For ordinary cyclic control, the response time may be approximated as:

\[ T\_{\text{response}} = T\_{\text{input}} + T\_{\text{logic}} + T\_{\text{output}} \]

For distributed systems, communication and device response delays must also be included.

The approximation is useful for understanding the response path, but it is not a complete worst-case timing model. Safety-related response times require specific calculations and verification.

4. HMI Architecture

A Human-Machine Interface (HMI) provides the operator with a visual and interactive interface to the machine.

It can display machine states, alarms, process values, recipes, diagnostics, and production information. It can also allow authorized commands and parameter changes.

4.1 HMI Responsibilities

  • Display machine operating state.
  • Show alarms and fault descriptions.
  • Provide manual and automatic operating interfaces.
  • Display sensor and actuator states.
  • Show drive and communication diagnostics.
  • Display counters, cycle times, and process values.
  • Support authorized recipe and setpoint entry.
  • Provide maintenance screens.
  • Record events where supported.
  • Display instructions and operating restrictions.

An HMI is not a replacement for physical safeguards or a safety-rated control system.

4.2 HMI Screen Architecture

Screen Main purpose
Overview Display overall machine state and major equipment
Manual operation Provide controlled manual commands
Automatic operation Show automatic cycle state and sequence progress
Alarm summary Show active alarms requiring attention
Alarm history Review recorded faults and events
Diagnostics Show I/O, device, and communication status
Drive and motion Display drive status, faults and permitted parameters
Production Show counters, cycle time and production results
Maintenance Provide maintenance status and approved service functions
Recipe management Manage process parameters where applicable
User management Apply access permissions and accountability

The exact screens should follow operator tasks rather than the internal organization of the PLC program.

4.3 HMI Design Principles

  • Use consistent navigation.
  • Use clear device names and units.
  • Distinguish actual values from setpoints.
  • Show the machine's current operating state.
  • Provide useful alarm descriptions and recovery guidance.
  • Avoid excessive colors and decorative graphics.
  • Restrict commands and configuration changes according to user roles.
  • Validate numeric entries and permissible ranges.
  • Display stale data or communication failure clearly.
  • Provide confirmation for high-impact commands where appropriate.

Alarm colors, priorities, and acknowledgment behavior should follow the plant's alarm philosophy.

4.4 HMI and PLC Tag Mapping

HMI objects are linked to PLC tags or other supported data sources.

For example:

HMI object PLC tag Purpose
Conveyor status indicator CV01_Running Shows run feedback
Start command CV01_StartReq Requests conveyor start
Drive fault indicator CV01_DriveFault Displays drive fault status
Actual speed display CV01_SpeedActual Shows measured or reported speed
Cycle counter Machine_CycleCount Shows completed cycles

These names are illustrative. A production project should use its approved naming convention.

Commands should be handled through a defined control interface that validates the operating mode, permissives, and required interlocks. An HMI button should not directly bypass those conditions.

5. I/O Architecture

Input/output (I/O) is the interface between the control system and physical equipment.

The architecture defines where signals are connected, how they are electrically represented, how they are transmitted, and how failures are detected.

5.1 Digital Inputs

Digital inputs represent discrete states, usually corresponding to ON/OFF conditions.

Examples include:

  • Proximity sensors.
  • Photoelectric sensors.
  • Limit switches.
  • Push buttons.
  • Pressure switches.
  • Drive-ready signals.
  • Drive fault contacts.
  • Contactor auxiliary contacts.

The design must specify the voltage level, electrical polarity, input type, common arrangement, isolation, filtering, and expected state.

5.2 Digital Outputs

Digital outputs command devices or indicate machine states.

Examples include:

  • Interposing relay coils.
  • Contactor commands.
  • Solenoid valves.
  • Indicator lamps.
  • Buzzers.
  • Non-safety drive commands.
  • External equipment requests.

The output design must consider current rating, inrush current, inductive loads, suppression, short-circuit behavior, channel grouping, and the need for interposing relays.

5.3 Analog Inputs

Analog inputs represent continuously varying values.

Examples include:

  • Pressure transmitters.
  • Temperature transmitters.
  • Flow transmitters.
  • Load cells with suitable signal conditioning.
  • Position sensors.
  • Analog drive feedback.

Common industrial signal ranges include 4–20 mA and 0–10 V, but the correct range depends on the instrument and receiving module.

5.4 Analog Outputs

Analog outputs provide a variable command or reference.

Examples include:

  • Speed references.
  • Valve position commands.
  • Process setpoints.
  • Actuator references.
  • Analog control signals to compatible equipment.

The design must verify output range, load impedance, signal isolation, grounding, resolution, and the behavior on controller or signal failure.

5.5 Pulse, High-Speed, and Specialized I/O

Some applications require more than ordinary digital and analog signals.

Examples include:

  • High-speed counter inputs.
  • Encoder interfaces.
  • Pulse-train outputs.
  • Thermocouple inputs.
  • RTD inputs.
  • Weighing modules.
  • Specialized motion interfaces.

These signals require compatible modules, suitable wiring, correct filtering, and sufficient timing performance.

6. Local I/O Versus Remote I/O

Local I/O

Local I/O is installed within or close to the main controller assembly.

Advantages include:

  • Simple architecture for compact machines.
  • Fewer remote communication dependencies.
  • Convenient access to the main control panel.

Limitations include longer field cable runs when devices are distributed across a large machine.

Remote I/O

Remote I/O is installed near field devices and communicates with the controller over an industrial network or supported bus.

Advantages include:

  • Reduced long-distance field wiring.
  • Modular expansion.
  • Easier distribution across machine sections.
  • Improved organization of field interfaces.

Considerations include network reliability, node addressing, power distribution, environmental ratings, diagnostic coverage, and recovery behavior after communication loss.

Selection factor Local I/O Remote I/O
Compact machine Often suitable Suitable where justified
Widely distributed devices May require extensive wiring Often advantageous
Network dependency Lower for local signals Higher
Expansion Depends on rack capacity Depends on network and node capacity
Fault diagnosis Centralized access Requires network and node diagnostics
Installation cost Can be higher for distant devices Can reduce cable and termination costs

Remote I/O does not automatically improve availability. The result depends on network design, power arrangements, topology, device diagnostics, and failure handling.

7. I/O Estimation and Capacity Planning

I/O estimation begins with the process requirements and equipment list.

A useful sequence is:

  1. Identify every sensor, actuator, command, feedback, and interface.
  2. Classify each signal by type.
  3. Determine electrical characteristics.
  4. Identify safety-related signals separately.
  5. Determine local versus remote location.
  6. Assign candidate modules and channels.
  7. Calculate current and planned spare capacity.
  8. Verify compatibility and network requirements.
  9. Cross-check against the PLC program and electrical drawings.

A simple capacity estimate is:

\[ N\_{\text{planned}} = N\_{\text{required}} + N\_{\text{spare}} \]

Suppose a machine requires 72 digital inputs and the design reserves 18 additional channels.

\[ N\_{\text{planned}} = 72 + 18 = 90 \]

The architecture must provide at least 90 usable digital input channels, subject to actual module channel counts, spare-channel policy, electrical grouping, and other design constraints.

7.1 I/O Estimation Table

Signal type Required channels Spare channels Planned channels
Digital inputs 72 18 90
Digital outputs 40 10 50
Analog inputs 12 4 16
Analog outputs 4 2 6

These values are illustrative. Module selection should also account for channel isolation, input filtering, output current, signal range, safety classification, and physical distribution.

8. Electrical Signal Characteristics

I/O architecture must account for the actual electrical behavior of field devices.

8.1 Sourcing and Sinking

Sourcing and sinking describe current direction in a DC circuit.

In common 24 V DC industrial applications:

  • A PNP sensor typically sources positive voltage to the input when active.
  • An NPN sensor typically sinks current toward 0 V when active.

The sensor output type must be compatible with the input module and wiring arrangement.

PNP sensor example

+24 V DC
   ↓
Sensor electronics
   ↓
PNP output
   ↓
PLC digital input
   ↓
Input reference / 0 V

This is a conceptual illustration. Actual connections depend on the sensor's wiring diagram, input-module common arrangement, and electrical specifications.

8.2 Analog Scaling

For a linear 4–20 mA transmitter representing 0–100 bar, the process value can be calculated as:

\[ PV = \frac{I - 4}{20 - 4} \times 100 \]

Where \(I\) is the measured current in mA and \(PV\) is pressure in bar.

At 12 mA:

\[ PV = \frac{12 - 4}{16} \times 100 = 50\text{ bar} \]

The PLC must also handle out-of-range signals, wire breaks where detectable, engineering limits, and sensor diagnostic behavior.

8.3 Signal Failure Behavior

For each important signal, define what happens when it becomes invalid.

Examples include:

  • Sensor wire break.
  • Stuck input.
  • Loss of analog signal.
  • Communication timeout.
  • Remote I/O loss.
  • Contradictory sensor states.
  • Invalid position feedback.

The response must be based on process requirements and risk assessment. A failed signal should not automatically be interpreted as a safe condition.

9. Industrial Network Architecture

The network connects automation components and provides communication for control, diagnostics, and data exchange.

9.1 Common Protocols

Protocol Common application Important consideration
PROFINET PLCs, remote I/O, drives and automation devices Device compatibility and real-time configuration
EtherNet/IP PLCs, drives, I/O and industrial devices Connection resources and network configuration
Modbus TCP Controllers, meters and compatible instruments Data mapping and communication diagnostics
Modbus RTU Serial communication with compatible devices Baud rate, parity, wiring and termination
PROFIBUS DP Legacy and supported distributed automation Bus configuration and diagnostics
EtherCAT Motion and distributed real-time control Timing and topology requirements
OPC UA Structured industrial data exchange Security, certificates and data modeling

These protocols are not interchangeable merely because some use Ethernet or carry similar data. The chosen controller, device, software, and network design must support the required protocol and functionality.

9.2 Network Topology

Common arrangements include star, line, ring, and redundant-path designs.

Star topology

             PLC
              |
        Managed switch
         /    |     \
       HMI   Drive  Remote I/O

A star topology provides straightforward organization and fault isolation, but the central switch may become a single point of failure unless suitable redundancy is provided.

A ring can support link-failure recovery when the devices and protocol support the required ring mechanism and are correctly configured.

9.3 Network Planning

Document:

  • Network topology.
  • Device names.
  • IP addresses and subnets.
  • Switch locations and port assignments.
  • Protocols and connection requirements.
  • Required communication performance.
  • Redundancy behavior.
  • Remote-access requirements.
  • Network segmentation.
  • Time synchronization where required.
  • Diagnostic and recovery procedures.
  • Configuration backups.

Network addresses and device names should be centrally controlled to prevent duplicate assignments and commissioning conflicts.

10. Network Performance and Reliability

Network design should match the application's timing and availability requirements.

Consider:

  • Number of devices.
  • Traffic volume.
  • Cyclic I/O update rates.
  • Packet and connection behavior.
  • Switch forwarding capability.
  • Multicast handling where applicable.
  • Network recovery time.
  • Communication-loss response.
  • Cable lengths and media.
  • Electromagnetic environment.
  • Supported redundancy mechanisms.

A network may appear healthy during light-load testing but fail under production conditions if the design ignores actual traffic, update rates, or device limitations.

For motion applications, deterministic timing and synchronization may be critical. A network that is adequate for monitoring data may be unsuitable for tightly coordinated motion.

11. OT Cybersecurity Architecture

Operational technology (OT) cybersecurity protects the availability, integrity, and authorized operation of industrial systems.

It must be designed without compromising machine safety or production requirements.

11.1 Key Design Controls

  • Separate industrial control networks from general enterprise networks where appropriate.
  • Define controlled communication paths between network zones.
  • Restrict engineering access.
  • Use unique accounts and suitable authentication.
  • Disable unnecessary services.
  • Control removable media.
  • Maintain approved software and firmware versions.
  • Back up controller and device configurations.
  • Monitor relevant network events.
  • Define remote-access approval and expiry.
  • Maintain recovery procedures.
  • Assess changes before applying patches to production equipment.

11.2 Purdue-Style Functional Separation

The Purdue model is one useful reference for organizing industrial system functions. It is not a mandatory physical architecture for every plant.

Enterprise business systems
        ↓
Site operations and planning
        ↓
SCADA / historians / supervisory applications
        ↓
PLC / HMI / machine supervisory control
        ↓
Field control and I/O
        ↓
Sensors and actuators

Actual designs may introduce additional security zones, conduits, industrial DMZs, or separate networks. Critical machine-to-machine traffic may require carefully controlled paths that do not follow a simple vertical hierarchy.

Security controls should be based on risk, operational requirements, and the plant's approved architecture.

12. Safety Architecture

Safety architecture defines how required safety functions are implemented using safety-related sensors, logic, outputs, and final control elements.

Examples of components include:

  • Guard switches.
  • Safety light curtains.
  • Safety laser scanners.
  • Emergency-stop devices.
  • Safety relays.
  • Safety PLCs.
  • Safety-rated drive functions.
  • Guard locking devices.
  • Safety-rated contactors or other suitable final elements.

The architecture must follow the machine risk assessment and applicable standards.

12.1 Safety Function Structure

Hazardous situation detected
        ↓
Safety-related input device
        ↓
Safety logic solver
        ↓
Safety-related output or drive function
        ↓
Required risk-reduction action
        ↓
Defined safe condition

The safe condition depends on the hazard. Removing motor torque may be appropriate in one case, while controlled stopping, mechanical restraint, guard locking, or other measures may be necessary in another.

12.2 Safety Performance

The required safety performance is established by the risk assessment and the applicable design method.

Relevant standards may include:

  • ISO 12100 for machinery risk assessment and risk reduction.
  • ISO 13849-1 for safety-related parts of control systems.
  • IEC 62061 for functional safety of machinery control systems.
  • IEC 60204-1 for electrical equipment of machines.

The applicable editions and legal requirements must be confirmed for the project.

A safety architecture should document:

  • Identified hazards.
  • Required safety functions.
  • Required performance level or integrity target.
  • Input devices and logic solver.
  • Final control elements.
  • Diagnostic measures.
  • Fault reaction.
  • Reset and restart conditions.
  • Validation method.
  • Test intervals where applicable.

12.3 Safety PLC Versus Standard PLC

A standard PLC executes ordinary machine control. A safety PLC is designed and certified for specified safety-related applications when used within its approved conditions.

Aspect Standard PLC Safety PLC
Main purpose Process and sequence control Safety-related control functions
Hardware and diagnostics Application-dependent Designed for specified safety integrity capabilities
Program requirements Standard control engineering Safety engineering and approved development constraints
Validation Functional verification Safety-function validation against requirements
Use in safety functions Only where specifically suitable and permitted Within the certified application and design limits

A safety PLC does not make the entire machine safe by itself. Sensors, logic, outputs, wiring, configuration, mechanical behavior, and validation all matter.

12.4 STO and Other Drive Safety Functions

Safe Torque Off (STO) prevents the drive from generating torque through its specified safety function.

STO does not automatically:

  • Electrically isolate the drive from the supply.
  • Stop a freely rotating load immediately.
  • Prevent a gravity-loaded axis from moving.
  • Replace lockout/tagout procedures.
  • Satisfy every machine safety requirement.

The required stopping category and additional safety measures must be selected from the risk assessment and verified against the drive's documented capabilities.

12.5 Reset and Restart Behavior

Resetting a safety device should not automatically restart hazardous motion unless the complete design explicitly permits and safely manages that behavior.

A typical sequence may require:

  1. Hazardous condition is removed.
  2. Guard or safety device is restored.
  3. Safety system confirms its required conditions.
  4. Authorized reset is performed.
  5. Separate start command initiates operation.

The exact sequence depends on the machine risk assessment, applicable standards, and safety-function design.

13. Safety and Standard Control Integration

Safety-related and standard control systems often exchange status information, but the distinction between their responsibilities must remain clear.

Examples of standard PLC status tags include:

  • GuardClosedStatus
  • SafetySystemReady
  • EmergencyStopStatus
  • DriveSTOStatus

These are illustrative status names. A standard PLC may use safety-system status for diagnostics or sequence coordination, but the status must not be used to bypass the safety function.

The safety system should perform the required risk-reduction action independently of ordinary process logic wherever the safety architecture requires it.

The HMI can display safety faults and reset instructions, but it must not replace the physical and logical safeguards.

14. Machine Modes and Control Authority

The architecture should define how the machine behaves in each operating mode.

Common modes include:

  • Automatic.
  • Manual.
  • Setup.
  • Maintenance.
  • Jog.
  • Local.
  • Remote.
  • Recovery.

Not every machine requires every mode.

The design should establish:

  • Who can select each mode.
  • Which commands are available in each mode.
  • Which interlocks remain active.
  • Whether reduced speed or enabling devices are required.
  • How mode changes affect ongoing operations.
  • How local and remote command authority is resolved.
  • What happens after power or communication loss.

A mode selector is not a safety function by itself. Mode-dependent safety requirements must be implemented and validated as part of the safety design.

15. Interlocks and Permissives

An interlock prevents an operation when a required condition is not satisfied or prevents an unsafe or invalid sequence.

A permissive is a condition that must be true before an operation is allowed to proceed.

For example, a conveyor start request may require:

  • Drive ready.
  • No active drive fault.
  • Correct operating mode.
  • Downstream equipment available.
  • Required process conditions satisfied.
  • Required safety conditions established.

These conditions may be implemented in standard control logic, safety-related control, or both, depending on their purpose.

Do not mix ordinary process interlocks with safety functions without documenting the distinction. A PLC permissive may protect equipment or process quality without being a safety-rated measure.

16. Inter-Machine Communication

Production lines frequently require communication between adjacent machines.

Common handshake signals include:

  • Ready.
  • Start request.
  • Start acknowledgment.
  • Busy.
  • Complete.
  • Fault.
  • Reset request.
  • Product present.
  • Transfer permitted.

16.1 Handshake Example

Machine A requests transfer
        ↓
Machine B confirms ready
        ↓
Machine A initiates transfer
        ↓
Machine B detects product
        ↓
Machine B acknowledges receipt
        ↓
Machine A confirms transfer complete

The real sequence must define timeouts, fault handling, signal ownership, reset behavior, and recovery from partial transfers.

For network-based handshakes, communication loss and stale data must be handled explicitly. A stale Ready bit should not be treated as proof that the receiving machine is still ready.

17. Device Diagnostics and Failure Handling

Architecture should provide enough diagnostic information to identify where a failure occurred.

Useful diagnostic categories include:

  • PLC fault.
  • I/O module fault.
  • Sensor fault or implausible state.
  • Drive fault.
  • Network communication loss.
  • Remote I/O station loss.
  • Safety-system fault.
  • HMI communication failure.
  • Robot or CNC interface fault.
  • Data-transfer failure.

Each significant failure should have a defined response, which may include stopping a sequence, inhibiting a start, entering a controlled state, raising an alarm, or allowing continued operation under documented conditions.

The response must depend on the actual hazard and process requirements.

17.1 Diagnostic Design

A useful diagnostic record includes:

  • Device or function identifier.
  • Fault description.
  • Detection condition.
  • Severity or priority.
  • Required machine response.
  • Operator or maintenance action.
  • Reset conditions.
  • Relevant alarm history.
  • Diagnostic information from the device.

A generic alarm such as "PLC fault" is less useful than a specific alarm that identifies the affected device and the likely cause.

18. Data Exchange With SCADA and MES

The PLC and HMI may exchange data with SCADA, historians, manufacturing execution systems (MES), or production databases.

Typical data includes:

  • Machine state.
  • Cycle count.
  • Cycle time.
  • Production quantity.
  • Reject count.
  • Alarm history.
  • Recipe identifier.
  • Process measurements.
  • Downtime reason.
  • Equipment availability.
  • Test results.

The architecture should define:

  • Data ownership.
  • Tag names and data types.
  • Update rates.
  • Timestamp source.
  • Data-quality indicators.
  • Communication-loss behavior.
  • Buffering and recovery requirements.
  • Access permissions.
  • Data retention responsibilities.

A supervisory data connection should not introduce an unnecessary dependency into critical machine control. Loss of a reporting database should not stop a machine unless that dependency is explicitly required by the process or safety design.

19. Redundancy and Availability

Redundancy is used when the cost or consequence of downtime justifies additional hardware and design complexity.

Potential redundant components include:

  • PLC controllers.
  • Power supplies.
  • Network paths.
  • Industrial switches.
  • Communication interfaces.
  • Supervisory servers.

Redundancy should be based on the required availability objective and failure analysis.

Important questions include:

  • What failure must the system tolerate?
  • What is the expected recovery time?
  • Does switchover interrupt the process?
  • Are controller states synchronized?
  • Are all field devices covered by the redundant path?
  • Can common-cause failures disable both paths?
  • How is redundancy tested?
  • What happens during maintenance?

Redundancy does not automatically make a system safe, and a safety-rated system does not automatically require redundant hardware. Safety and availability are different engineering objectives.

20. Engineering Deliverables

The architecture package should define the system sufficiently for detailed design, procurement, programming, integration, and verification.

Typical deliverables include:

  • Automation architecture diagram.
  • PLC hardware configuration.
  • I/O list and channel allocation.
  • HMI functional specification.
  • Network topology and addressing plan.
  • Device communication matrix.
  • Safety requirements specification where applicable.
  • Safety architecture and validation plan.
  • Machine mode and state definitions.
  • Interlock and permissive matrix.
  • Inter-machine handshake specification.
  • Alarm philosophy and alarm list.
  • Data interface specification.
  • Hardware bill of materials.
  • Firmware and software version list.
  • Backup and restore requirements.
  • FAT and SAT test requirements.
  • Design-deviation register.

The required documents depend on the project size, complexity, risk, and company standards.

21. Verification and Review Checklist

PLC

  • Controller capacity and performance are adequate.
  • Required communication interfaces are supported.
  • I/O capacity and spare allocation are verified.
  • Program organization and diagnostic requirements are defined.
  • Failure and restart behavior are documented.
  • Software backup and recovery requirements are specified.

HMI

  • Required screens and operator workflows are defined.
  • Command permissions are specified.
  • Alarm priorities and descriptions are established.
  • Numeric ranges and units are verified.
  • Communication-loss behavior is defined.
  • Critical commands follow the approved control logic.

I/O

  • Every field device has a unique tag.
  • Signal types and electrical characteristics are documented.
  • Channel allocation matches the hardware configuration.
  • Field wiring and terminal references are traceable.
  • Analog scaling and signal failure behavior are defined.
  • Safety-related signals are clearly identified.

Network

  • Topology and device addressing are documented.
  • Protocol compatibility is verified.
  • Timing and loading requirements are checked.
  • Failure and recovery behavior are specified.
  • OT access and segmentation requirements are defined.
  • Configuration backups are included.

Safety

  • The machine risk assessment is available.
  • Required safety functions are identified.
  • Required safety performance is established.
  • Sensors, logic, and final control elements are suitable.
  • Reset and restart behavior is defined.
  • Safety validation and records are planned.

Integration

  • Drive, robot, CNC, and upstream/downstream interfaces are documented.
  • Handshake signals have defined ownership and timing.
  • SCADA or MES interfaces have clear data definitions.
  • FAT and SAT cover important failure conditions.
  • Handover requirements include verified backups and configuration records.

22. Practical Troubleshooting Example

Consider a machine in which the HMI displays a conveyor start command, but the motor does not run.

The architecture should make it possible to separate the possible causes.

Diagnostic stage What to verify Possible finding
Operator interface Command accepted and correct mode selected Wrong mode or rejected command
PLC logic Start request and permissives Interlock not satisfied
Safety system Required safety conditions and status Safety function has inhibited operation
Network Drive communication and device status Lost connection or invalid control source
Drive Ready state, fault status and configuration Drive fault or disabled command source
Electrical circuit Required supply and command interface Missing supply, wiring defect or faulty interface
Motor and mechanism Motor circuit and mechanical condition Electrical or mechanical fault

Testing must follow the machine's approved safety procedures. Do not bypass guards or force outputs to make the machine run.

The architecture is effective when each layer exposes enough status information to isolate the cause without guesswork.

23. Common Architecture Mistakes

Selecting hardware before defining requirements: This creates avoidable redesign when the actual I/O count, timing, safety needs, or communication requirements become clear.

Treating all I/O as ordinary signals: Safety-related, high-speed, analog, and specialized signals may require different hardware and verification methods.

Ignoring communication failure: A machine may behave unpredictably if a remote I/O station, drive, or network connection disappears.

Using HMI logic as a substitute for safety: HMI restrictions do not provide the required safety integrity or replace safety-related control functions.

Leaving interfaces undefined: PLC, robot, CNC, and machine-builder teams may disagree about signal ownership, timeouts, and fault recovery.

Overusing redundancy: Redundancy increases cost and complexity when it is not connected to a defined availability requirement.

Insufficient diagnostics: Poor device tags, generic alarms, and missing fault states make maintenance unnecessarily slow.

Ignoring lifecycle and cybersecurity: Unsupported hardware, inaccessible backups, uncontrolled engineering access, and undocumented firmware changes can create long-term operational risks.

24. Interview Questions and Answers

Q1. What is automation architecture?

It defines the functional arrangement of controllers, I/O, operator interfaces, drives, safety systems, networks, and supervisory systems and specifies how they interact.

Q2. What is the difference between PLC and HMI?

The PLC executes control logic and interacts with the process. The HMI provides operator interaction, monitoring, alarms, and authorized commands.

Q3. What is the difference between local I/O and remote I/O?

Local I/O is located with or near the controller assembly. Remote I/O is distributed near field devices and communicates with the controller through a supported network or bus.

Q4. What determines PLC selection?

I/O capacity, processing requirements, communications, motion, safety, redundancy, environment, engineering tools, standardization, and lifecycle support.

Q5. Why is a network topology important?

It determines connectivity, cable requirements, fault isolation, communication paths, expansion, and possible redundancy behavior.

Q6. What is the difference between standard and safety PLCs?

A standard PLC handles ordinary machine control. A safety PLC is designed for specified safety-related functions when implemented within its approved limits and validated as part of the complete safety system.

Q7. What is an interlock?

An interlock prevents an operation when a required condition is absent or when continuing an operation would violate the defined process or control requirements.

Q8. What is a machine handshake?

A handshake is an agreed exchange of signals or data between machines to coordinate readiness, requests, execution, completion, and fault handling.

Q9. Why must analog signals be scaled?

Scaling converts raw electrical measurements into meaningful engineering values such as bar, degrees Celsius, millimeters, or liters per minute.

Q10. Why is network segmentation important in OT?

It limits unnecessary communication paths, helps control access between zones, and reduces the exposure of industrial equipment to unrelated systems.

Q11. Does STO electrically isolate a motor drive?

No. STO is a safety-related torque-prevention function. Electrical isolation and lockout requirements must be handled separately.

Q12. Why are as-built architecture and configuration records important?

They preserve the actual system design, support troubleshooting and recovery, and reduce the risk of incorrect changes during maintenance or expansion.

25. Final Engineering Principle

A robust PLC, HMI, network, safety, and I/O architecture must define not only how the machine operates normally, but also how it behaves when sensors fail, communication is lost, a drive faults, an operator changes mode, or a safety condition is triggered.

The strongest architecture has clear responsibilities, defined interfaces, suitable hardware, controlled access, meaningful diagnostics, verified safety functions, and documented recovery behavior.

Design the system around required machine behavior and failure handling first. Select the components to implement that design, rather than forcing the machine requirements to fit whatever hardware happens to be available.
