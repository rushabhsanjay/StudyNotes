1. Purpose of Industrial Ethernet Network Diagnostics

Network diagnostics is the systematic process of identifying, isolating, verifying, and correcting faults that affect communication between industrial devices.

In a manufacturing environment, Ethernet communication may connect PLCs, remote I/O, robot controllers, HMIs, CNC machines, drives, vision systems, SCADA servers, engineering workstations, and production databases. A network fault can therefore appear as a machine fault, a controller fault, an HMI alarm, a robot handshake timeout, or a production-data failure.

The objective is not merely to restore a connection. It is to identify the actual failure point, verify the correction, and prevent recurrence.

Typical diagnostic goals include:

  • Determine whether the problem is physical, Layer 2, Layer 3, transport-layer, protocol-specific, or application-related.
  • Identify the affected device, network segment, switch port, VLAN, or communication path.
  • Distinguish a complete communication failure from delay, packet loss, intermittent faults, or excessive traffic.
  • Use switch counters, device logs, packet captures, and endpoint tools to collect evidence.
  • Restore operation with minimal disruption to production.
  • Document root cause, corrective action, and verification results.

2. Industrial Ethernet Communication Stack

A useful starting point is to divide communication into layers. Each layer has different failure modes and diagnostic methods.

Application
    ↓
Industrial protocol and application behavior
    ↓
Transport layer: TCP or UDP
    ↓
Network layer: IP addressing and routing
    ↓
Data link layer: Ethernet frames, MAC, VLAN, switching
    ↓
Physical layer: copper, fiber, connectors, transceivers

This is a simplified diagnostic model. Industrial protocols do not all use the same stack. Some use TCP, some use UDP, some use both, and some use specialized Layer 2 mechanisms.

Layer or area Typical fault Useful checks
Physical Broken cable, poor connector, faulty transceiver Link LEDs, port state, cable tester, error counters
Data link VLAN mismatch, switching loop, MAC learning issue VLAN tables, MAC address table, spanning-tree status
Network Duplicate IP, wrong subnet, missing route IP configuration, ARP, ping, route inspection
Transport TCP connection failure, blocked port, retransmissions TCP connection state, firewall rules, packet capture
Industrial protocol Incorrect device path, connection limit, timeout Protocol diagnostics, controller configuration, device logs
Application Wrong tag mapping, invalid data, handshake logic PLC logic, HMI tags, application logs, data validation

Core rule: A successful test at one layer does not prove that every higher layer is working.

For example, a successful ping indicates that an ICMP echo exchange succeeded. It does not prove that EtherNet/IP I/O, PROFINET cyclic data, Modbus TCP registers, or an HMI application is operating correctly.

3. Establish the Baseline Before Troubleshooting

Before changing configuration, determine what normal operation should look like.

Record:

  • Device name, IP address, subnet mask, and MAC address where available.
  • Switch name, physical port, VLAN, and connection path.
  • Expected communication protocol and configured connection parameters.
  • Normal update rate, timeout behavior, and expected response.
  • Normal switch-port speed, duplex, utilization, and error counters.
  • Relevant PLC, HMI, robot, drive, and switch diagnostics.
  • The last known working state and the time the fault started.

A baseline helps distinguish a new fault from an existing configuration condition.

For production-critical systems, avoid rebooting devices or clearing diagnostic counters before recording useful evidence. Reboots can temporarily hide intermittent faults and erase information needed for root-cause analysis.

4. The Diagnostic Sequence

Use a repeatable sequence instead of randomly changing settings.

Define the symptom
    ↓
Identify affected devices and communication path
    ↓
Check power, physical link, and port status
    ↓
Check Ethernet errors and switch behavior
    ↓
Verify VLAN and Layer 2 connectivity
    ↓
Verify IP addressing and routing
    ↓
Check TCP/UDP and firewall behavior
    ↓
Check industrial protocol diagnostics
    ↓
Check application logic and data
    ↓
Correct one confirmed cause
    ↓
Verify normal operation and document

The sequence is a guide, not an absolute rule. If controller diagnostics clearly identify a protocol configuration fault, investigate that evidence directly rather than completing every possible lower-layer test first.

5. Physical-Layer Diagnostics

Physical faults are among the first things to investigate because no higher-layer communication can work reliably without a functional physical link.

5.1 Link LEDs

Check the switch and endpoint Ethernet indicators.

Common meanings include:

  • Link indicator off: no link detected, port disabled, endpoint powered off, incompatible interface, or cabling problem.
  • Link indicator on: a physical link has been established.
  • Activity indicator flashing: traffic is being transmitted or received.

LED meanings vary by manufacturer. A link light is evidence of link establishment, not proof of correct VLAN configuration or application communication.

5.2 Cable and connector inspection

Check for:

  • Damaged cable jackets.
  • Loose or incorrectly seated connectors.
  • Incorrect copper or fiber type.
  • Incorrect fiber polarity or transceiver type.
  • Excessive cable length.
  • Poorly terminated twisted pairs.
  • Inappropriate patching or unexpected intermediate couplers.
  • Routing near high-interference equipment where the installation requires separation.

Industrial cable selection, shielding, bonding, and routing should follow the equipment specifications and plant standards.

5.3 Link-state monitoring

A port that repeatedly transitions between up and down may indicate:

  • Cable or connector movement.
  • Failing transceiver or interface.
  • Endpoint power cycling.
  • An unstable industrial switch.
  • Negotiation problems.
  • Environmental or electrical interference.

Check switch event logs and link-flap counters where available. Correlate the timestamps with machine alarms and power events.

5.4 CRC/FCS errors

CRC or Frame Check Sequence errors indicate that received frames failed an integrity check. They can be associated with cable faults, connectors, transceivers, electrical interference, or other physical-layer problems.

Record the counter, operate under normal conditions, and check whether the count increases. A large historical count without any recent increase may not indicate an active fault.

6. Ethernet Switch Diagnostics

Managed switches provide information that ordinary endpoint tools cannot show.

Important diagnostic features include:

  • Administrative and operational port status.
  • Negotiated speed and duplex.
  • VLAN membership and tagging configuration.
  • MAC address learning tables.
  • Interface traffic counters.
  • CRC/FCS errors and packet drops.
  • Broadcast and multicast statistics.
  • Link-up and link-down logs.
  • Spanning-tree or ring status.
  • Link aggregation state.
  • LLDP neighbor information.
  • Port mirroring for packet capture.
  • SNMP monitoring, if supported and configured.

6.1 MAC address table

The switch MAC address table associates learned MAC addresses with VLANs and switch ports.

If a PLC's MAC address is expected on one port but appears on another, investigate:

  • Incorrect physical patching.
  • A downstream switch or bridge.
  • MAC address movement caused by a topology change.
  • A Layer 2 loop.
  • A replacement device.
  • Virtual interfaces or duplicated MAC addresses.

A MAC address appearing on an unexpected port is a clue, not automatic proof of a network loop.

6.2 Interface counters

Observe counter changes over a defined time period.

Counter Diagnostic value
RX and TX packets Confirms whether traffic is passing through the interface
CRC/FCS errors Helps identify receive-side frame-integrity problems
Input drops May indicate receive-side resource limits or policy drops
Output drops May indicate queue congestion or forwarding limits
Broadcast packets Helps identify excessive broadcast activity
Multicast packets Helps identify multicast load or subscription behavior
Link transitions Helps identify unstable physical links
Utilization Helps identify unusually high traffic load

Counter definitions differ between platforms. Interpret them using the relevant switch documentation and other evidence.

6.3 LLDP neighbor discovery

LLDP can reveal the identity and port information of directly connected devices that support it.

Use it to compare the physical network against the topology drawing. Missing LLDP information does not necessarily indicate a fault because many endpoints do not advertise LLDP information, and some networks intentionally restrict it.

7. Layer 2 Diagnostics

Layer 2 diagnostics focuses on Ethernet frames, MAC addresses, VLANs, switching behavior, and loop prevention.

7.1 VLAN mismatch

Symptoms may include:

  • Devices on the same physical switch cannot communicate.
  • A PLC is reachable locally but not from another switch.
  • Communication stops after a switch replacement or port configuration change.
  • HMI and PLC connections work intermittently after network changes.

Checks:

  1. Verify the access VLAN or PVID on endpoint-facing ports.
  2. Check trunk configuration on switch-to-switch links.
  3. Confirm that required VLANs exist and are permitted along the complete path.
  4. Verify tagged and untagged frame handling.
  5. Check native VLAN settings where applicable.
  6. Confirm whether routing is required between the endpoint subnets.

7.2 MAC address learning problems

A switch normally learns source MAC addresses from incoming Ethernet frames and uses its MAC address table to forward traffic.

If the expected MAC address is missing, possible causes include:

  • The endpoint is not transmitting.
  • The physical link is down.
  • The endpoint is assigned to a different VLAN.
  • The MAC address table entry has aged out.
  • The switch port is blocked or traffic is being filtered.
  • The device communicates only occasionally.

Generate traffic through an approved diagnostic action and inspect the relevant VLAN and MAC address table. An absent entry is not necessarily a fault if the device has not recently transmitted.

7.3 Broadcast storms and switching loops

A Layer 2 loop can cause repeated frame circulation, excessive broadcasts, unstable MAC learning, and widespread communication failures.

Possible symptoms include:

  • High switch utilization.
  • Large increases in broadcast counters.
  • MAC addresses repeatedly moving between ports.
  • Several devices losing communication at the same time.
  • Switch CPU load or management responsiveness deteriorating.
  • Multiple machines experiencing faults simultaneously.

Check spanning-tree status, ring protocol status, switch logs, and recent cabling changes. Do not disconnect arbitrary network cables in a live redundant network: removing the wrong link may isolate production equipment or disrupt the redundancy mechanism.

7.4 Multicast traffic

Industrial protocols may use multicast for particular discovery, cyclic-data, or coordination functions.

Excessive or incorrectly distributed multicast traffic can affect network performance. Check multicast forwarding behavior, IGMP snooping where applicable, querier configuration where required, and protocol-specific network requirements.

Do not block multicast traffic indiscriminately. Some industrial devices rely on it for normal operation.

8. Layer 3 Diagnostics: IP Addressing and Routing

Layer 3 diagnostics investigates IP addresses, subnet masks, gateways, and routed paths.

8.1 Verify IP configuration

On a Windows workstation, use:

ipconfig /all

Inspect:

  • IPv4 address.
  • Subnet mask or prefix length.
  • Default gateway.
  • Interface status.
  • DHCP status, if applicable.
  • DNS settings where hostnames are used.

For PLCs and industrial endpoints, inspect the actual device configuration through its approved engineering tool or diagnostic interface.

8.2 Duplicate IP addresses

A duplicate IP address occurs when multiple devices use the same address on a network where the addresses are expected to be unique.

Symptoms can include:

  • Intermittent communication.
  • Communication working for one device but failing for another.
  • ARP entries changing between MAC addresses.
  • HMI or SCADA connections unexpectedly reaching the wrong device.

Useful checks include:

arp -a
ping 192.168.10.20

Replace the example address with the actual target address.

A ping response alone does not prove that an address is unique. If a duplicate is suspected, correlate ARP information, switch MAC tables, device configuration, and approved network monitoring.

Avoid assigning a different IP address to a production controller merely to test a theory. Verify the approved address plan first.

8.3 Subnet mask errors

A wrong subnet mask can cause an endpoint to treat a destination as local when it should use a router, or treat a local destination as remote.

Example:

PLC:
IP address: 192.168.10.20
Mask:       255.255.255.0

HMI:
IP address: 192.168.10.30
Mask:       255.255.255.0

These example endpoints are in the same IPv4 subnet.

If one endpoint is incorrectly configured with a different subnet mask, communication may behave unexpectedly even when the IP addresses appear reasonable.

8.4 Default gateway and routing

A default gateway is generally needed when a device must communicate with destinations outside its local IP subnet.

Checks include:

  • Whether the target is in the same subnet.
  • Whether a default gateway is configured when required.
  • Whether the router or Layer 3 switch has the correct routes.
  • Whether routing and firewall policies permit the traffic.
  • Whether the return path is valid.

A default gateway is not normally needed for communication between devices in the same IP subnet on the same bridged network. Some systems have additional vendor-specific requirements, so follow the device documentation.

8.5 Ping and its limitations

Example:

ping 192.168.10.20

Ping uses ICMP echo requests and replies. It is useful for testing IP reachability when the endpoint and network permit ICMP.

Interpret results carefully:

Result Possible meaning
Replies received ICMP reachability exists at that time
Request timed out Packet loss, filtering, unavailable endpoint, routing issue, or ICMP disabled
Destination unreachable A host or router indicates that the destination cannot be reached
Intermittent replies Possible packet loss, congestion, unstable link, or endpoint load
No reply but application works ICMP may be disabled or filtered

Some industrial controllers deliberately restrict ICMP responses. Failure to reply to ping does not, by itself, prove that the device is offline.

9. Windows Network Diagnostic Tools

Windows tools are useful for engineering workstations, SCADA PCs, servers, and supported endpoints.

Command Purpose Important limitation
ipconfig /all Shows interface addressing and configuration Does not validate industrial protocol communication
ping Tests ICMP reachability ICMP may be blocked or disabled
arp -a Displays local IPv4-to-MAC mappings Entries may be stale or incomplete
tracert Shows the routed path using probe responses Firewalls and devices may suppress responses
route print Displays local routing table Does not prove that remote routing is correct
nslookup Tests DNS name resolution Relevant only when name resolution is involved
netstat -ano Shows connections and listening endpoints Does not explain all application or protocol failures
pathping Combines route discovery with packet-loss observations Results may be affected by ICMP filtering and device behavior
Get-NetAdapter Shows Windows network adapter status Does not reveal the complete switch-side state
Get-NetTCPConnection Shows Windows TCP connection state Does not diagnose UDP or all industrial protocol traffic

9.1 Example command sequence

ipconfig /all
ping 192.168.10.20
arp -a
tracert 192.168.10.20
route print
netstat -ano

Run only the tests relevant to the symptom. A long command list is not a substitute for understanding what each result means.

9.2 Checking a TCP port

PowerShell provides Test-NetConnection for TCP connectivity tests.

Test-NetConnection 192.168.10.20 -Port 44818

This example tests TCP connectivity to port 44818, commonly associated with EtherNet/IP explicit messaging. The target must actually use that service, and firewalls or device policies may affect the result.

A successful TCP connection does not validate every protocol function. A failed TCP test does not rule out UDP-based communication on the same device.

10. TCP and UDP Diagnostics

10.1 TCP connection problems

TCP establishes a connection before exchanging application data. Troubleshooting may involve:

  • Connection refused.
  • Connection timeout.
  • Connection reset.
  • Retransmissions.
  • Connections that establish but close unexpectedly.
  • Connection limits reached on a controller or server.

Common causes include:

  • The service is not listening.
  • The wrong port is configured.
  • A firewall blocks the traffic.
  • The route is unavailable.
  • The server has reached a connection limit.
  • The client and server have incompatible application settings.

Inspect the client, server, firewall, and relevant packet capture. Do not assume every TCP timeout is a physical network fault.

10.2 UDP communication problems

UDP does not establish a connection in the same way TCP does. An application can transmit UDP datagrams without receiving a response or knowing whether the destination processed them.

Check:

  • Correct destination IP address.
  • Correct UDP port.
  • Firewall and access-control rules.
  • Multicast configuration, if applicable.
  • Application-specific timeout or acknowledgement behavior.
  • Whether packets reach the destination interface.
  • Whether the destination application processes the packets.

A successful ping does not prove that UDP traffic is permitted.

10.3 Packet loss versus application timeout

An application timeout can result from packet loss, excessive delay, endpoint processing load, protocol configuration, or an application that is not responding.

A timeout is the observed symptom, not the root cause.

Use packet captures and device diagnostics to determine whether the request was sent, whether it reached the destination, whether a response was generated, and where the response was lost or delayed.

11. Industrial Protocol Diagnostics

Industrial protocols have their own connection states, watchdogs, timeout mechanisms, device parameters, and error codes. These should be checked after establishing the relevant physical and network conditions.

11.1 EtherNet/IP

Useful diagnostic areas include:

  • Controller communication status.
  • I/O connection state.
  • Connection timeout or watchdog faults.
  • Requested Packet Interval (RPI).
  • Connection size and resource limits.
  • Adapter configuration and electronic keying.
  • IP address and device identity.
  • Multicast and switch forwarding behavior where applicable.
  • Explicit messaging versus cyclic I/O communication.

The RPI is a requested interval for data exchange, not a guaranteed end-to-end response time. An overly aggressive configuration can increase network and device processing load.

A controller may successfully exchange explicit messages while cyclic I/O connections remain faulted. Diagnose the specific connection rather than treating EtherNet/IP as a single all-or-nothing service.

11.2 PROFINET

Useful diagnostic areas include:

  • Device name and IP configuration.
  • Controller-to-device relationship.
  • Expected device identity and configuration.
  • Device availability and diagnostic status.
  • Cyclic I/O communication state.
  • Update time and watchdog configuration.
  • Switch and physical-layer errors.
  • Topology and supported diagnostic information.

A PROFINET device may have a valid IP address and still fail to establish the expected cyclic I/O relationship. Verify the configured device name, controller project, device identity, and network diagnostics.

11.3 Modbus TCP

Useful diagnostic areas include:

  • Server IP address and TCP port.
  • TCP connection status.
  • Unit Identifier where relevant.
  • Function code.
  • Register address and quantity.
  • Register data type and byte or word order.
  • Server response exceptions.
  • Timeout and polling interval.
  • Simultaneous connection limits.

A valid TCP connection does not prove that the requested register address or function code is supported. Modbus address notation can also differ between manuals and software tools, so verify the actual protocol address mapping.

11.4 OPC UA

Useful diagnostic areas include:

  • Server endpoint URL.
  • Network reachability and TCP port.
  • Application certificate trust.
  • Security policy and message security mode.
  • Authentication and user permissions.
  • Namespace and node identifiers.
  • Subscription status and publishing interval.
  • Server resource limits and logs.

If a server is reachable but a client cannot establish a secure session, investigate certificate trust and security configuration rather than repeatedly changing Ethernet port settings.

11.5 Vendor-specific communication

Some systems use proprietary services, specialized motion traffic, or vendor-specific diagnostic protocols.

Use the manufacturer's engineering tool and diagnostic documentation to identify:

  • Device state.
  • Connection status.
  • Error codes.
  • Expected data rate.
  • Connection resource usage.
  • Firmware or configuration compatibility.

Do not infer the health of an entire industrial communication system from one generic network test.

12. Packet Capture and Protocol Analysis

Packet capture provides direct evidence of traffic moving through a network interface or monitored switch port.

A common workflow is:

Identify the affected communication
    ↓
Select the correct capture point
    ↓
Start capture using an approved method
    ↓
Reproduce the fault under controlled conditions
    ↓
Inspect request and response behavior
    ↓
Correlate packet timestamps with device logs
    ↓
Identify the failing segment or endpoint

Packet captures can be collected using an approved workstation capture tool, a switch's port-mirroring feature, or supported network TAP hardware.

12.1 Useful observations

Look for:

  • Repeated TCP SYN packets without a completed connection.
  • TCP resets.
  • TCP retransmissions.
  • Duplicate acknowledgements.
  • Long delays between requests and responses.
  • Repeated application requests without corresponding replies.
  • Unexpected broadcast or multicast traffic.
  • Protocol-specific error responses.
  • Sudden changes in traffic volume.

12.2 Capture-point selection

The capture location matters.

  • A capture on the client shows what the client interface sends and receives.
  • A capture on a server shows what reaches or leaves that server interface.
  • A switch mirror can reveal traffic crossing selected switch ports.
  • A network TAP can provide a dedicated observation point, subject to its capabilities and placement.

If a request appears in the client capture but not at the server-side capture, investigate the path between the two capture points. Confirm that both captures cover the same time window and traffic direction before drawing conclusions.

12.3 Important limitations

  • A capture point may miss traffic that does not traverse it.
  • Mirror ports can drop packets under high load.
  • Hardware offloading can affect how packets appear in host captures.
  • Encrypted traffic may hide application payloads.
  • Packet timestamps from different systems may not be synchronized.
  • Capture filters can accidentally exclude the fault-related packets.

Use packet capture to test a specific hypothesis, not merely to collect enormous files and hope the network confesses.

13. Latency, Jitter, and Packet Loss

These metrics describe different aspects of communication quality.

  • Latency: The time taken for traffic to travel between defined points.
  • Jitter: Variation in packet delay over time.
  • Packet loss: Packets that fail to arrive at the observation point or are otherwise lost.
  • Throughput: The amount of data successfully transferred over a period.
  • Utilization: The fraction of available interface capacity being used.

For a request-response measurement, the observed round-trip time includes both directions and endpoint processing. It is not identical to one-way network latency.

13.1 Interpreting results

Observation Possible investigation
High and stable round-trip time Routing path, endpoint processing, congestion, or device behavior
Variable response time Queueing, competing traffic, endpoint load, or unstable link
Increasing packet loss under load Congestion, queue drops, physical errors, or endpoint limitations
Low ping latency but failed I/O Industrial protocol configuration, controller state, or application behavior
High utilization with drops Capacity, traffic bursts, QoS, and queue behavior
Latency rises after a network change Compare topology, route, VLANs, port settings, and traffic patterns

Do not apply a single universal latency or packet-loss threshold to every industrial network. Acceptable values depend on the protocol, update rate, topology, equipment, and application requirements.

14. Redundancy and Network Recovery Diagnostics

Redundant industrial networks require additional diagnostic checks.

Relevant technologies include RSTP, MSTP, MRP, DLR, PRP, HSR, and supported link aggregation mechanisms.

Check:

  • Ring or redundancy manager status.
  • Expected topology and port roles.
  • Redundant-link state.
  • Spanning-tree state and blocked ports where applicable.
  • Recovery events and timestamps.
  • Link transitions.
  • Packet loss during controlled failover tests.
  • Whether the application recovered as expected.
  • Whether multiple failures exceed the design's protection capability.

A blocked spanning-tree port may be normal. Likewise, a ring port in a designated state may be expected for the selected redundancy protocol. Do not treat every non-forwarding port as a fault without understanding the topology.

Controlled failover testing

Failover testing should be planned and approved. Before testing:

  1. Confirm the redundancy design and supported test procedure.
  2. Identify production impact and recovery expectations.
  3. Establish a baseline for controller, I/O, robot, and HMI behavior.
  4. Capture relevant switch and application diagnostics.
  5. Perform the test under the authorized conditions.
  6. Verify recovery time and application behavior.
  7. Restore the expected topology and document the result.

Do not unplug redundant links at random in a live system.

15. Time Synchronization and Event Correlation

Network troubleshooting becomes much easier when timestamps from different devices can be compared.

Potential time sources include:

  • Switch event logs.
  • PLC diagnostic buffers.
  • Robot controller logs.
  • HMI and SCADA alarms.
  • Windows event logs.
  • Packet-capture timestamps.
  • NTP or other supported time-synchronization services.

If the systems have different clocks, an event may appear to occur before its actual cause.

Record clock offsets where possible. For precise timing analysis, verify the timestamp source, time zone, and synchronization state of each system.

16. SNMP and Centralized Monitoring

Simple Network Management Protocol (SNMP) can expose supported switch status, counters, and events to monitoring systems.

Typical uses include:

  • Interface availability.
  • Port utilization.
  • Error-counter trends.
  • Link-up and link-down notifications.
  • Device inventory and uptime.
  • Temperature, power, or hardware health on supported equipment.
  • Threshold-based alerting.

SNMP polling provides periodic observations, while traps or informs can report selected events, depending on device and configuration support.

Security and reliability considerations:

  • Prefer secure, appropriately configured monitoring practices.
  • Avoid exposing management services to untrusted networks.
  • Restrict monitoring access to authorized systems.
  • Document community strings or credentials securely where applicable.
  • Consider polling intervals and device load.
  • Validate alerts against actual device conditions.

Centralized monitoring helps detect recurring faults before they become production outages, but monitoring data still needs interpretation.

18. Practical Troubleshooting Examples

Example 1: HMI cannot communicate with a PLC

Observed condition: Both devices show Ethernet link-up, but HMI tags are unavailable.

Procedure:

  1. Confirm the PLC and HMI IP addresses and subnet masks.
  2. Verify the switch ports' VLAN assignments.
  3. Check any trunk links and routed paths between the devices.
  4. Test ICMP reachability if supported.
  5. Check the HMI's configured PLC address and protocol settings.
  6. Inspect PLC communication status and HMI diagnostics.
  7. Capture traffic if the failure remains unexplained.
  8. Verify tag updates after correcting the confirmed fault.

Key point: Physical link-up is not proof of correct network or application configuration.

Example 2: Remote I/O connection drops intermittently

Observed condition: A PLC reports occasional remote I/O connection faults.

Procedure:

  1. Record fault timestamps and controller diagnostics.
  2. Check the remote I/O switch port for link transitions.
  3. Record CRC/FCS and drop-counter changes.
  4. Inspect power to the I/O adapter and nearby network equipment.
  5. Verify the configured update interval and watchdog settings.
  6. Check switch congestion, multicast behavior, and redundancy events.
  7. Use an approved capture method if the cause remains unclear.
  8. Verify stable I/O operation under normal production conditions.

Do not increase watchdog timeouts simply to suppress alarms. A longer timeout can hide the symptom while leaving the underlying fault unresolved.

Example 3: Communication fails after replacing an industrial switch

Observed condition: Devices work locally but cannot communicate across the new switch.

Check:

  1. VLAN database and port membership.
  2. Access versus trunk port modes.
  3. Allowed VLANs and tagging behavior.
  4. Speed and duplex compatibility.
  5. Spanning-tree or ring configuration.
  6. Multicast forwarding requirements.
  7. Port security and management policies.
  8. Firmware and feature compatibility.

Compare the old and new configurations rather than assuming that the replacement's default settings reproduce the previous network behavior.

Example 4: SCADA data stops updating, but PLC operation continues

Observed condition: The machine runs normally, but the SCADA dashboard shows stale values.

Investigate:

  1. Whether the PLC is still updating its internal process values.
  2. Whether the SCADA server can reach the PLC.
  3. Whether the configured protocol connection is active.
  4. Whether subscriptions, polling, or connection resources have failed.
  5. Whether a gateway, OPC server, or data collector is faulted.
  6. Whether database writes or downstream data processing have stopped.
  7. Whether the dashboard is displaying old cached data.

This separates machine control from the supervisory data path. A dashboard fault does not automatically mean that the PLC or industrial network has stopped controlling the machine.

19. Root-Cause Analysis and Documentation

A good diagnostic report distinguishes the symptom, evidence, root cause, corrective action, and verification.

Recommended structure:

Field What to record
Symptom What operators or systems observed
Start time When the problem began
Scope Devices, machines, and production areas affected
Evidence Logs, counters, captures, diagnostic codes
Root cause The confirmed technical cause
Corrective action The change or repair performed
Verification Tests demonstrating recovery
Prevention Changes intended to reduce recurrence
Follow-up Monitoring or inspection required

Avoid recording a guess as a confirmed root cause. If the evidence establishes only that replacing a cable restored communication, document that result and the supporting evidence without inventing a more specific cause.

For recurring faults, correlate the incident with cable movement, machine vibration, cabinet temperature, power events, network changes, traffic peaks, and maintenance activities.

20. Safe Diagnostic Practices

Industrial network troubleshooting must preserve both personnel safety and process stability.

  • Obtain authorization before changing production network settings.
  • Record switch configuration and diagnostic evidence before rebooting equipment.
  • Avoid rebooting PLCs, robots, managed switches, or servers unless the approved procedure permits it.
  • Do not change production IP addresses without checking the address plan.
  • Do not disable security or redundancy features merely to make a fault disappear.
  • Avoid uncontrolled cable disconnections on ring or redundant networks.
  • Use approved packet-capture and monitoring methods.
  • Protect captured traffic and device configuration backups.
  • Confirm machine behavior after restoring communication.
  • Follow lockout, machine-safety, and change-control requirements when physical work creates a hazard.

A network can appear healthy while an application is unsafe or incorrect. Confirm the required machine state and interlocks through the approved operational procedure.

21. Common Diagnostic Mistakes

  1. Assuming a ping failure proves the Ethernet cable is faulty.
  2. Assuming a successful ping proves the industrial protocol is working.
  3. Rebooting devices before recording diagnostic evidence.
  4. Changing several configuration parameters at once.
  5. Ignoring switch counters because the link LED is on.
  6. Treating historical error counts as proof of an active fault.
  7. Replacing PLC hardware before verifying VLAN and IP configuration.
  8. Ignoring return-path routing and firewall policies.
  9. Increasing communication timeouts without investigating the underlying delay.
  10. Assuming every network fault is a Layer 1 or Layer 2 issue.
  11. Treating every blocked redundancy port as a fault.
  12. Capturing packets at the wrong location and drawing conclusions from incomplete evidence.
  13. Failing to compare event timestamps across devices.
  14. Closing the fault after communication returns without documenting the verified cause.

22. Interview Questions and Answers

Q1. What is network diagnostics?

It is the systematic investigation of network behavior using configuration checks, counters, logs, endpoint tools, protocol diagnostics, and packet captures to identify and correct communication faults.

Q2. What is the difference between link-up and IP connectivity?

Link-up indicates that the physical Ethernet connection has been established. IP connectivity additionally depends on addressing, Layer 2 forwarding, routing where needed, and applicable policies.

Q3. Does ping prove that EtherNet/IP or PROFINET is working?

No. Ping tests ICMP reachability. Industrial protocol connections and cyclic I/O can fail independently.

Q4. What do CRC/FCS errors indicate?

They indicate received frames that failed an integrity check. Investigate cables, connectors, transceivers, electrical conditions, and interface behavior.

Q5. How do you diagnose a suspected duplicate IP address?

Compare device configuration, ARP observations, MAC address tables, logs, and approved monitoring. Confirm that the same IP is associated with multiple interfaces before making changes.

Q6. What is the purpose of a packet capture?

It records observable network traffic so that requests, responses, retransmissions, resets, timing, and protocol behavior can be examined.

Q7. Why can TCP fail even when ping succeeds?

ICMP and TCP are different protocols. A TCP service may be unavailable, blocked by a firewall, listening on another port, or rejecting connections even when ICMP works.

Q8. What is the difference between latency and packet loss?

Latency measures delay, while packet loss measures packets that fail to arrive at the observation point. A network can have high latency without packet loss, or packet loss without consistently high latency.

Q9. How would you diagnose an intermittent remote I/O fault?

Correlate controller fault timestamps with switch link events, error counters, endpoint power, communication settings, network load, and packet captures.

Q10. What is the role of SNMP in diagnostics?

SNMP allows monitoring systems to collect supported device status and counters and, where configured, receive event notifications.

Q11. Why is a baseline useful?

It establishes normal configuration and behavior, making it easier to identify changes and distinguish active faults from historical conditions.

Q12. What should a network fault report contain?

The symptom, time, scope, evidence, confirmed root cause, corrective action, verification results, and preventive measures.

23. Practical Exercises

Exercise 1: Layer-by-layer diagnosis

A PLC has link-up status, responds to ping, but its remote I/O connection is faulted.

  • Verify the PLC's configured I/O connection.
  • Inspect controller and adapter diagnostics.
  • Check update interval and watchdog configuration.
  • Review switch counters and link events.
  • Verify VLAN and multicast requirements where applicable.
  • Capture relevant traffic if the fault remains unexplained.

Exercise 2: Identify a physical-layer problem

A switch port shows increasing CRC/FCS errors.

  • Record the current counter.
  • Inspect connectors and cable routing.
  • Check the transceiver and interface specifications.
  • Observe the counter during a defined interval.
  • Perform a controlled cable substitution if authorized.
  • Verify whether new errors continue.

Exercise 3: Investigate a VLAN or routing fault

A workstation can reach a server locally, but a workstation on another subnet cannot.

  • Verify both endpoint IP addresses and subnet masks.
  • Inspect the default gateway and routing table.
  • Confirm VLAN membership and trunk configuration.
  • Check router routes and firewall policies.
  • Use a packet capture or approved path test to isolate the failing segment.

Exercise 4: Interpret a packet capture

A client repeatedly sends TCP SYN packets but does not complete a connection.

Investigate whether:

  • The destination IP address is correct.
  • The target service is listening.
  • The traffic reaches the destination interface.
  • A firewall or access policy blocks the connection.
  • A response is generated but fails to return.
  • The capture point and filters include the relevant traffic.

24. Final Diagnostic Mental Model

Network diagnostics is the process of turning a reported symptom into a verified technical explanation.

Symptom
    ↓
Scope and baseline
    ↓
Physical link and interface health
    ↓
Ethernet switching and VLAN behavior
    ↓
IP addressing and routing
    ↓
TCP/UDP and security policies
    ↓
Industrial protocol diagnostics
    ↓
Application behavior
    ↓
Evidence-based correction
    ↓
Verification, documentation, prevention

The most important habit is to test a hypothesis at the layer where the evidence points, then verify the result at the application level. This avoids unnecessary device replacement, risky configuration changes, and temporary fixes that allow the same fault to return.
