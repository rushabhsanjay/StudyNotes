1. Definition of an industrial Ethernet ring network

An industrial Ethernet ring network is a network topology in which switches or other network devices are connected in a closed loop, providing two potential directions for communication between devices.

In a simple linear network, a link failure can disconnect devices located beyond the failed link. In a ring network, traffic may be redirected through the other direction around the ring when a link or device fails, provided the ring uses a suitable redundancy protocol and the failure is within the protection capabilities of that design.

Ring topology is common in industrial automation because production lines often contain distributed PLCs, remote I/O, robot controllers, drives, HMIs, and other networked equipment spread across a large physical area.

A ring topology alone does not guarantee redundancy. The network must have a mechanism to prevent Ethernet loops during normal operation and restore connectivity after a failure.

2. Basic ring topology

Consider four industrial Ethernet switches connected in a ring.

          Switch A -------- Switch B
             |                  |
             |                  |
          Switch D -------- Switch C

Each switch connects to its neighboring switches, forming a closed loop.

During normal operation, a redundancy protocol prevents the physical loop from forwarding ordinary traffic indefinitely. Depending on the protocol, one link may be logically blocked or the ring may use a protocol-specific forwarding mechanism.

When a supported link fails, the redundancy protocol detects the fault and adjusts forwarding so that traffic can use the remaining path.

For example, if the link between Switch A and Switch B fails, communication may continue along the alternative path:

Switch A → Switch D → Switch C → Switch B

This assumes that the switches, links, protocol configuration, and remaining network capacity support that recovery path.

3. Why industrial plants use ring networks

Requirement How a ring can help Important limitation
Link redundancy Provides an alternate path around the ring Requires a functioning alternative path and correct protocol configuration
Reduced downtime Can restore connectivity after certain failures Recovery takes time and may interrupt time-sensitive traffic
Distributed machine connectivity Connects equipment across a production line Every device and link must be designed for the intended topology
Flexible plant layout Allows switches to be located along a line or cell Cable routes and physical damage risks still matter
Easier expansion Additional ring-capable switches may be integrated into the design Adding devices can affect recovery time, capacity, and configuration
Fault tolerance Can tolerate certain single-link failures Does not necessarily tolerate every switch, power, cable, or common-mode failure

The primary benefit is an alternative communication path, not immunity to every network failure.

4. Ring topology versus other network topologies

Topology Physical structure Main advantage Main limitation
Star Endpoints connect to a central switch Simple troubleshooting and centralized connections A central switch failure may affect all attached devices
Line or daisy chain Devices or switches connect sequentially Simple cabling for linear production layouts A link failure can isolate devices beyond the break
Ring Devices or switches form a closed loop Can provide an alternate path Requires loop prevention and redundancy management
Tree Multiple branches connect through higher-level switches Supports hierarchical plant networks Failure of an upstream device can affect an entire branch
Mesh Multiple interconnections between network nodes Can provide multiple alternative paths More complex cabling, configuration, and fault analysis

A ring is not automatically better than a star or a tree. The best topology depends on the required availability, recovery time, traffic load, physical layout, maintenance strategy, and equipment capabilities.

5. Why a ring needs a redundancy protocol

Ethernet switches learn the locations of devices by observing source MAC addresses and maintain MAC address tables to determine where frames should be forwarded.

If switches are connected in a loop without effective loop prevention, broadcast and certain unknown-destination traffic can circulate repeatedly. This can create a broadcast storm, cause MAC address-table instability, and overload the network.

A physical ring therefore needs a mechanism that controls forwarding.

Two broad approaches are used:

  • Spanning Tree-based protocols: Prevent loops by placing selected paths into a non-forwarding state and adjusting the topology when failures occur.
  • Industrial ring redundancy protocols: Use a ring-specific mechanism to manage the normal forwarding state and restore the ring after supported faults.

The appropriate protocol depends on the switches, industrial requirements, and network design. Ring protocols from different manufacturers are not necessarily interoperable.

6. Major industrial Ethernet ring protocols

Several protocols can provide ring redundancy. They differ in interoperability, configuration, recovery behavior, and supported network size.

Protocol Full name Main use
RSTP Rapid Spanning Tree Protocol General Layer 2 loop prevention and topology recovery
MSTP Multiple Spanning Tree Protocol Manages multiple spanning-tree instances for VLANs
MRP Media Redundancy Protocol Standardized industrial Ethernet ring redundancy, commonly used in PROFINET environments
DLR Device Level Ring Industrial ring protocol associated with EtherNet/IP and supported Rockwell Automation ecosystems
Turbo Ring Vendor-specific industrial ring technology Supported industrial Ethernet switches from Moxa
HiPER-Ring Vendor-specific ring redundancy technology Supported industrial Ethernet switches from Hirschmann
Other proprietary ring protocols Manufacturer-specific implementations Industrial networks using compatible hardware and software

These protocols are not interchangeable merely because they all support redundant network paths. Their configuration, compatibility, supported topologies, and recovery behavior differ.

RSTP

RSTP is defined by IEEE 802.1w and is incorporated into later revisions of the IEEE spanning-tree standards.

It detects Layer 2 loops and establishes a loop-free forwarding topology. If a link fails, the protocol can recalculate the topology and restore forwarding through an alternative path.

RSTP can support redundant topologies beyond simple rings, but its convergence behavior depends on the topology, switch configuration, link state, and protocol implementation.

MRP

MRP is standardized in IEC 62439-2 and is widely encountered in industrial Ethernet networks, particularly in PROFINET installations.

An MRP ring commonly has a designated Media Redundancy Manager (MRM) and multiple Media Redundancy Clients (MRCs).

The manager controls the ring's normal forwarding behavior and detects ring faults. Clients participate in the ring and follow the protocol's forwarding and recovery behavior.

The exact supported ring size, recovery performance, and configuration options depend on the equipment and profile.

DLR

DLR is an industrial ring redundancy protocol associated with EtherNet/IP networks.

A typical DLR network includes:

  • A Ring Supervisor, which manages ring operation and monitors ring status.
  • Ring Nodes, which participate in the ring.
  • Ring-capable ports and compatible devices or infrastructure components.

DLR can detect supported ring faults and restore communication through the remaining path. Device roles and supported configurations must match the equipment documentation.

A switch that supports ordinary Ethernet switching or RSTP does not automatically support DLR.

Vendor-specific ring technologies

Manufacturers may offer proprietary ring protocols designed for their own industrial switches.

Examples include Moxa Turbo Ring and Hirschmann HiPER-Ring. These can provide useful recovery characteristics within supported equipment configurations.

Before selecting a protocol, verify:

  • Whether all participating devices support it.
  • Whether different device models and firmware versions are compatible.
  • Whether the protocol can coexist with the plant's VLAN and redundancy architecture.
  • What happens when a device is replaced with another model.
  • Whether recovery performance meets the application's requirements.

7. How a ring behaves during normal operation and failure

A ring redundancy protocol must manage two different states: normal operation and fault recovery.

Normal operation

The physical cables form a closed loop, but the protocol controls forwarding to prevent an uncontrolled Layer 2 loop.

Depending on the protocol, a particular link may be blocked for ordinary data traffic, or the protocol may use another defined mechanism to maintain a loop-free forwarding state.

Network management systems may display the ring as healthy even when one physical link is logically blocked by design.

Link failure

Suppose the ring contains Switch A, Switch B, Switch C, and Switch D. The link between Switch A and Switch B fails.

The redundancy protocol detects the fault and changes the forwarding state so that communication can travel through the other direction around the ring, if the network remains connected.

Normal physical topology:

Switch A -------- Switch B
   |                  |
   |                  |
Switch D -------- Switch C

After A-B link failure:

Switch A     X    Switch B
   |                  |
   |                  |
Switch D -------- Switch C

Alternative path:

Switch A → Switch D → Switch C → Switch B

The diagram illustrates the physical path, not the complete protocol state. The exact forwarding transition depends on the selected ring protocol.

Recovery sequence

A typical recovery process includes:

  1. A physical link or device failure occurs.
  2. The affected interface detects loss of link or the protocol detects the fault.
  3. The redundancy protocol communicates or processes the fault information.
  4. The forwarding state changes to use the available alternative path.
  5. Traffic resumes through the recovered topology.
  6. Monitoring systems may record the event or raise an alarm.

Not every failure is detected at the same speed. Physical link-down detection is usually different from detecting a device that remains powered but stops forwarding traffic correctly.

8. Recovery time and network availability

Recovery time is the interval between a failure and restoration of the required communication service.

Recovery time is important in industrial networks because communication interruptions can affect PLC I/O, robot coordination, drive commands, HMI updates, SCADA monitoring, and other production functions.

The recovery time depends on factors such as:

  • Redundancy protocol and configuration.
  • Switch and device capabilities.
  • Number of ring nodes.
  • Failure detection method.
  • Link state and fault type.
  • Traffic load and application timeout settings.
  • Device behavior during topology changes.

Some industrial ring implementations advertise recovery in tens of milliseconds under specified conditions. That figure must not be treated as a universal guarantee for all rings or all fault types.

A recovery time that appears short on a network diagram may still be long enough to trigger an application timeout.

Recovery time versus application interruption

These are related but different measurements.

Measurement Meaning
Physical detection time Time taken to detect the physical link failure
Protocol recovery time Time taken for the redundancy mechanism to restore its intended forwarding state
Packet loss interval Period during which some traffic is lost or delayed
Application interruption Period during which the application cannot perform its required communication
Process interruption Actual effect on machine or production operation

For example, a network might recover after a brief interruption, but a PLC connection timeout may already have occurred. The application may require a reconnect, fault reset, or sequence recovery even after Ethernet communication returns.

Network recovery alone does not guarantee uninterrupted machine operation.

9. Ring sizing and performance

A ring should be sized for the actual traffic and fault conditions expected in the plant.

Important design factors include:

  • Number of switches and endpoints.
  • Ethernet port speeds.
  • Link bandwidth and utilization.
  • PLC I/O update requirements.
  • EtherNet/IP or PROFINET traffic patterns.
  • Multicast traffic and IGMP snooping configuration.
  • VLAN membership and trunk configuration.
  • Expected recovery behavior.
  • Cable distance, medium, and environmental conditions.
  • Device limitations and protocol-supported ring size.

Traffic loading

A ring's links may carry traffic from multiple machines. After a failure, traffic that previously used one path may be redirected through the remaining path.

The surviving links must have sufficient capacity for the resulting traffic.

A network that operates comfortably under normal conditions may become congested during a failure if its design does not account for the alternate path's load.

Number of nodes

More nodes may increase the total number of connections and potential fault points. The effect on recovery time and supported network size depends on the protocol and equipment.

Never assume that every ring protocol supports an unlimited number of nodes or the same maximum ring size.

10. Ring networks and VLANs

VLANs and ring redundancy solve different problems.

  • VLANs divide a switching infrastructure into separate Layer 2 broadcast domains.
  • Ring redundancy provides an alternate path and controls forwarding during normal and fault conditions.
  • Trunks carry configured VLANs between switches.
  • QoS controls how traffic is handled under congestion.

A network can use VLANs and ring redundancy together, provided the selected equipment and protocol support the intended configuration.

Example

A production line uses VLAN 10 for PLC/HMI traffic, VLAN 20 for robotics, and VLAN 30 for SCADA.

The switches are connected in an industrial ring. The ring links must carry the required VLANs, and the redundancy protocol must be configured consistently.

If VLAN 10 is missing from one trunk or switch, the ring may still appear operational while PLC/HMI communication fails across that part of the network.

Likewise, a correctly configured VLAN does not prevent a physical link failure from interrupting traffic unless the topology and redundancy mechanism provide a working alternative path.

11. Ring networks in PLC, remote I/O, and robotics systems

Industrial Ethernet rings may connect:

  • PLCs and distributed I/O.
  • Robot controllers and robot-cell switches.
  • HMI panels and engineering stations.
  • CNC systems and industrial PCs.
  • SCADA or supervisory infrastructure.
  • Industrial cameras and inspection systems.
  • Drives and other Ethernet-enabled devices.

The supported topology depends on the devices and the communication protocol.

For example, some EtherNet/IP architectures support DLR with compatible devices or ring-capable infrastructure. Some PROFINET architectures support MRP with appropriately configured devices.

Do not assume that every endpoint can be connected directly into any industrial ring. A device might support only ordinary Ethernet communication and may need to connect through a compatible switch.

Also, distinguish between a ring of switches and a ring that includes end devices. Their capabilities and failure behavior can differ.

12. Common ring network failures

Broken cable or disconnected port

A damaged cable, loose connector, or disconnected port breaks one section of the ring.

Expected behavior: A correctly configured redundancy protocol should detect the supported failure and use the remaining path.

Checks:

  • Port link status.
  • Cable and connector condition.
  • Optical transceiver status, if applicable.
  • Protocol ring status.
  • Port error counters.

Switch power failure

If a switch loses power, all ports on that switch may go down.

Expected behavior: The ring may recover if the remaining topology provides a path around the failed device. If the failed switch separates the network into disconnected sections, some devices may remain unreachable.

A redundant cable path cannot restore a device that has itself lost power.

Switch failure with links still appearing active

A switch can experience a forwarding or software fault without every physical link going down.

Expected behavior: Recovery depends on what the redundancy protocol can detect and how the failure manifests. A link-based mechanism may not detect every failure that affects forwarding.

Checks:

  • Switch health and CPU status, where available.
  • Ring manager or supervisor diagnostics.
  • MAC address learning.
  • Neighbor reachability.
  • Port counters and logs.
  • Firmware and known device issues.

Ring supervisor or manager failure

Some ring protocols depend on a manager or supervisor role.

Expected behavior: The network's response depends on whether the protocol and implementation support manager redundancy, role election, or recovery from manager failure.

Do not assume that a ring can recover from the loss of its manager in the same way it recovers from a broken cable.

Duplicate ring connection or configuration error

Incorrect cabling, incompatible redundancy protocols, or mismatched ring configuration can create a loop or prevent redundancy from operating correctly.

Checks:

  • Ring role and status.
  • Protocol compatibility.
  • Ring-port assignment.
  • Spanning-tree status.
  • VLAN and trunk settings.
  • MAC address-table instability.
  • Broadcast or multicast traffic spikes.

13. Ring network troubleshooting

Use a structured process rather than randomly disconnecting cables on a running production line.

Step 1: Establish the scope

Determine whether the issue affects:

  • One endpoint.
  • One switch.
  • One section of the ring.
  • An entire VLAN.
  • Multiple VLANs.
  • The whole production network.

Check whether the machine has stopped, only monitoring is affected, or the network has recovered while an application remains faulted.

Step 2: Check physical status

Inspect switch port LEDs and diagnostics.

Look for:

  • Link down.
  • Repeated link flapping.
  • Incorrect speed or duplex where configurable.
  • CRC/FCS errors.
  • Fiber signal or transceiver alarms.
  • Cable or connector damage.
  • Power supply or switch health alarms.

Step 3: Check ring status

Use the switch's management interface or vendor software to verify:

  • Ring status.
  • Manager or supervisor state.
  • Participating nodes.
  • Detected ring faults.
  • Active and blocked ports, where applicable.
  • Recovery events and timestamps.

The labels and commands differ by vendor and protocol.

Step 4: Check Layer 2 forwarding

Verify:

  • MAC address-table entries.
  • VLAN membership.
  • Trunk configuration.
  • Allowed VLANs.
  • Native VLAN and PVID behavior.
  • Spanning-tree state, if used.
  • Multicast configuration where relevant.

Step 5: Check application communication

Confirm whether the required PLC, robot, remote I/O, or SCADA connection has recovered.

A successful ping does not prove that cyclic I/O or time-sensitive industrial communication is operating correctly.

Step 6: Preserve evidence

Record the fault time, port state, alarms, switch logs, ring status, and observed application symptoms before resetting equipment or changing configuration.

Evidence helps identify whether the fault originated in the physical network, redundancy protocol, switch hardware, application configuration, or another subsystem.

14. Troubleshooting matrix

Symptom Possible cause Diagnostic action
Whole ring or major section unreachable Multiple link failures, power loss, or protocol failure Check switch power, physical links, and ring status
One link fails but the network does not recover Incorrect ring configuration or unsupported topology Verify protocol roles, compatibility, and fault alarms
Network repeatedly switches paths Intermittent cable, transceiver, or port Check link flapping logs and physical media
PLC I/O faults during ring recovery Recovery interruption exceeds application tolerance Correlate ring events with PLC diagnostics and I/O timeouts
Ring status healthy but a device is unreachable Endpoint fault, VLAN issue, or forwarding problem Check MAC learning, IP settings, VLAN membership, and device status
Broadcast traffic increases sharply Layer 2 loop or redundancy misconfiguration Check ring state, spanning tree, and traffic counters
SCADA communication fails but local control continues Supervisory path or VLAN/routing issue Check the SCADA communication path and inter-VLAN policies
Problems appear after a switch replacement Wrong protocol, firmware, port assignment, or VLAN configuration Compare replacement configuration with the approved baseline
Ring recovers but a machine stays faulted Application timeout or protocol session failure Check PLC, robot, or application fault history and recovery procedure
Communication fails only under heavy traffic Congestion or insufficient alternate-path capacity Review utilization, QoS, multicast, and traffic distribution

15. Commissioning a ring network

Ring commissioning should confirm both normal operation and fault recovery.

Before energizing or changing the network

  • Confirm switch models, firmware, and supported redundancy protocols.
  • Review the approved physical topology and port map.
  • Confirm ring manager, supervisor, or node roles as applicable.
  • Verify VLANs, trunk links, and allowed VLAN lists.
  • Confirm IP addressing and required communication paths.
  • Record the baseline configuration and recovery requirements.
  • Establish an approved test and rollback plan.

During commissioning

  • Verify every physical link and switch port.
  • Confirm that the ring reports the expected healthy state.
  • Check MAC address learning and VLAN forwarding.
  • Verify PLC, HMI, remote I/O, robot, and SCADA communication.
  • Record baseline traffic utilization and port error counters.
  • Test the approved redundancy scenarios under controlled conditions.
  • Measure recovery time using appropriate monitoring or test equipment.
  • Confirm that the application behaves acceptably during recovery.

After commissioning

  • Save the validated switch configurations.
  • Record protocol versions, device models, and firmware.
  • Document normal forwarding behavior and expected blocked ports where applicable.
  • Record measured recovery results and test conditions.
  • Update the network diagram and maintenance instructions.
  • Confirm that production and safety procedures remain satisfied.

16. Preventive maintenance

Ring networks need routine inspection even when no communication alarms are active.

Maintenance item What to verify
Physical cabling Cable condition, connectors, strain relief, and routing
Fiber links Transceiver health, optical diagnostics where supported, and connector cleanliness
Switch power Supply health, redundancy where fitted, and alarm status
Port health Link flapping, CRC/FCS errors, discards, and speed changes
Ring health Protocol status, node participation, and recent topology changes
Configuration VLANs, trunk links, ring roles, and loop-prevention settings
Firmware Approved versions, known defects, and change-control requirements
Documentation Port map, IP plan, ring diagram, and configuration backups
Recovery readiness Approved procedures and evidence that redundancy has been tested

Do not routinely unplug a ring link merely to see whether the network survives. Fault-injection testing belongs in a controlled, approved test plan because even a redundant network may interrupt production traffic.

17. Ring network design mistakes to avoid

  1. Assuming a ring is automatically redundant. A physical loop without a working redundancy mechanism can create a broadcast storm.
  2. Mixing incompatible ring protocols. Similar names or purposes do not guarantee interoperability.
  3. Ignoring power failure. Redundant network links do not keep an unpowered switch operating.
  4. Ignoring application timeouts. Network recovery can occur after a PLC or I/O connection has already faulted.
  5. Allowing unnecessary VLANs across ring links. Unneeded traffic complicates segmentation and increases the scope of accidental propagation.
  6. Failing to document ring roles. Replacing a manager or supervisor with an incorrectly configured switch can affect network recovery.
  7. Assuming every device is ring-capable. Some endpoints require a compatible switch or specific supported topology.
  8. Testing only the healthy state. A green status indicator does not prove that recovery will work during a fault.
  9. Ignoring alternate-path capacity. The surviving path must handle the traffic redirected during a failure.
  10. Changing production cabling without a rollback plan. A simple port move can interrupt a critical communication path.

18. Interview questions and answers

1. What is an industrial Ethernet ring?

A network topology in which switches or devices form a closed loop and a suitable redundancy mechanism manages forwarding and restores communication after supported failures.

2. Why can a physical Ethernet loop be dangerous?

Without effective loop prevention, frames can circulate repeatedly, creating broadcast storms, duplicate traffic, and unstable MAC address learning.

3. What is the purpose of a ring redundancy protocol?

It controls forwarding during normal operation and adjusts the network after a detected fault so that traffic can use an available alternative path.

4. What is the difference between RSTP and MRP?

RSTP is a general spanning-tree protocol for loop prevention and topology recovery. MRP is a standardized industrial Ethernet ring redundancy protocol with defined ring roles and behavior.

5. What are MRM and MRC in MRP?

MRM means Media Redundancy Manager, and MRC means Media Redundancy Client. The manager coordinates ring behavior, while clients participate in the ring.

6. What are the Ring Supervisor and Ring Nodes in DLR?

The Ring Supervisor manages and monitors DLR ring operation, while Ring Nodes participate in the ring according to the supported DLR configuration.

7. Does a ring prevent downtime?

It can reduce downtime for supported failures, but it does not eliminate every outage. Recovery delay, multiple failures, device failures, application timeouts, and common-mode failures can still interrupt service.

8. What happens when a ring link breaks?

The redundancy mechanism detects the fault and changes forwarding to use the remaining path if the topology and protocol support recovery from that failure.

9. Can all industrial switches be connected into any ring?

No. The switches, firmware, ring protocol, supported topology, and configuration must be compatible.

10. Why can PLC communication fail even after the ring recovers?

The interruption may have exceeded the application's timeout, the PLC connection may require re-establishment, or a separate VLAN, routing, or device fault may remain.

11. What should be checked first during a ring fault?

Check physical link and switch status, then ring protocol diagnostics, VLAN and trunk configuration, MAC address learning, and the affected application's communication state.

12. How should ring recovery time be verified?

Use a controlled fault test and appropriate monitoring to measure the interruption under the actual network configuration and traffic conditions. Do not rely solely on a manufacturer's best-case figure.

19. Practical exercises

Exercise 1: Single-link failure

A four-switch ring loses the link between Switch A and Switch B. All switches remain powered, and the redundancy protocol is correctly configured.

Expected analysis: The network should attempt to restore connectivity using the remaining path. Verify protocol recovery and confirm that required applications resume communication.

Exercise 2: Switch power loss

Switch C loses power. It connects two portions of the ring.

Expected analysis: Devices directly attached to Switch C lose connectivity. Other devices may remain connected or may become partitioned, depending on the physical topology and remaining paths. Ring redundancy cannot restore connectivity through an unpowered switch to its directly attached endpoints.

Exercise 3: Ring healthy, PLC unreachable

The switch reports a healthy ring, but a PLC cannot communicate with the SCADA server.

Expected analysis: Check endpoint status, IP configuration, VLAN membership, trunk links, routing, access-control policies, and the SCADA communication path. A healthy ring only confirms the relevant redundancy status, not every application connection.

Exercise 4: Recovery causes an I/O fault

The ring recovers from a link failure, but a remote I/O connection remains faulted.

Expected analysis: Correlate network recovery time with the I/O connection timeout and PLC diagnostics. Determine whether the connection should recover automatically or requires a defined application recovery procedure.

Exercise 5: Select an appropriate protocol

A plant uses PROFINET equipment and is planning an industrial ring.

Expected analysis: Check whether the switches and devices support MRP and whether the selected topology, manager/client roles, and recovery requirements are supported. Do not select a protocol solely because it is available on another switch family.

20. Final mental model

A reliable industrial ring has four essential elements:

  • Physical topology: The switches and links form the intended ring.
  • Redundancy protocol: Forwarding remains loop-free and adjusts after supported faults.
  • Compatible configuration: Ring roles, VLANs, trunk settings, and firmware are correct.
  • Application validation: PLCs, remote I/O, robots, drives, HMIs, and SCADA recover within acceptable limits.

The key engineering principle is that network redundancy and machine availability are not the same thing. A ring may restore Ethernet forwarding successfully while a PLC connection, robot handshake, or remote I/O session still requires recovery. Commission the network and the application together.
