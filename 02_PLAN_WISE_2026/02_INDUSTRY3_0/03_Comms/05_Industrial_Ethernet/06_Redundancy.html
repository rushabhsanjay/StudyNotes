1. Definition of network redundancy

Network redundancy is the use of additional communication paths, devices, power sources, or network services to maintain or restore communication when a component fails.

In industrial automation, redundancy helps reduce production interruptions caused by Ethernet link failures, switch faults, communication equipment failures, or selected infrastructure problems.

A redundant network is not simply a network with extra cables. The additional components must be arranged, configured, and monitored so that the system can continue operating or recover when a failure occurs.

Examples include:

  • Two Ethernet paths between network devices.
  • Ring networks using MRP, DLR, or another supported redundancy protocol.
  • Two network switches serving redundant communication paths.
  • Redundant PLC controllers or communication interfaces.
  • Redundant power supplies for critical switches.
  • Redundant SCADA servers or communication gateways.

Important distinction: Network redundancy protects communication infrastructure. It does not automatically provide redundant control logic, redundant I/O, redundant power, or uninterrupted machine operation.

2. Why redundancy matters in industrial automation

Industrial communication often supports functions that must remain available for production, monitoring, diagnostics, and coordination.

Application Potential effect of communication failure
PLC to remote I/O I/O connection faults or loss of remote signals
PLC to robot controller Loss of handshake or interruption of coordinated operations
PLC to HMI Missing status, commands, alarms, or operator visibility
PLC to drive Loss of cyclic control or diagnostic communication, depending on architecture
SCADA to PLC Loss of monitoring, supervisory commands, or historical data
Engineering workstation to PLC Loss of programming, diagnostics, or online monitoring access
Safety-related communication May cause a defined safety response depending on the certified system design
Industrial data collection Gaps in production, quality, or machine-condition data

The consequence depends on the application. A short interruption in a monitoring connection may only create a data gap, while an interruption in cyclic I/O communication may stop a machine.

Redundancy requirements should therefore be derived from the process impact, required recovery time, and consequences of a failure.

3. Main types of redundancy

Redundancy can be implemented at several layers of an industrial system.

Redundancy type What is duplicated or protected Example
Link redundancy Physical communication path Two Ethernet links with a supported redundancy mechanism
Ring redundancy Alternative path around a network loop MRP or DLR
Switch redundancy Network switching equipment Two switches in an appropriately designed redundant architecture
Network-interface redundancy Communication interfaces Dual network interfaces with supported failover
Controller redundancy Control hardware or controller execution Supported hot-standby PLC system
I/O redundancy I/O modules, interfaces, or communication paths Redundant I/O architecture supported by the control platform
Power redundancy Power supply path Dual power inputs or redundant DC supplies
Server redundancy Supervisory or application services Redundant SCADA servers
Communication gateway redundancy Gateway hardware or service Primary and standby protocol gateways
Data redundancy Stored data or replicated records Replicated historian data

These forms of redundancy solve different problems. Two Ethernet links do not protect against a PLC CPU failure, and two PLC CPUs do not necessarily protect against a common network switch failure.

4. Single points of failure

A single point of failure (SPOF) is a component whose failure can interrupt the required service because no adequate alternative is available.

Consider this architecture:

PLC ───── Switch A ───── SCADA Server

If Switch A fails, the communication path between the PLC and SCADA server is lost.

Adding a second cable to the same failed switch does not remove the switch itself as a single point of failure.

A better design must identify which components are shared by both paths and whether those components can independently fail.

             ┌── Switch A ──┐
PLC ─────────┤              ├──────── SCADA
             └── Switch B ──┘

This simplified drawing indicates two possible switching paths, but it does not establish that the design will work. The actual architecture needs suitable interfaces, physical connections, forwarding behavior, IP configuration, and a supported redundancy mechanism.

Common single points of failure

  • One central switch.
  • One power supply feeding all network equipment.
  • One cable route exposed to the same physical hazard.
  • One network interface in a critical device.
  • One ring manager with no supported recovery mechanism for its failure.
  • One router or firewall between control and supervisory networks.
  • One gateway serving multiple critical devices.
  • One SCADA server with no standby or recovery arrangement.

A useful redundancy review asks not only what has been duplicated, but also what failure can still disable both paths at once.

5. Link redundancy

Link redundancy provides more than one communication path between devices or network segments.

For example, two switches might have two physical links between them. However, simply connecting the cables can create a Layer 2 loop.

A supported protocol or architecture must control how the links are used.

Common approaches include:

  • RSTP or MSTP, which manage Layer 2 forwarding topology.
  • MRP or another compatible industrial ring protocol.
  • Link aggregation, where supported, to combine compatible links into a logical link.
  • Application or device-level path redundancy.
  • Dual-homed architectures supported by the connected equipment.

The correct approach depends on whether the goal is path recovery, increased bandwidth, interface redundancy, or application-level continuity.

6. Active and standby redundancy

Redundant components can operate in active/standby or active/active arrangements.

Active/standby

One component carries the primary workload while another remains ready to take over.

Primary path ─── Active
                    |
                Failover
                    |
Standby path ─── Ready

The standby path may require detection, state changes, or application reconnection before it becomes operational.

Examples include standby SCADA servers and supported controller redundancy systems.

Active/active

Two or more components perform work simultaneously, potentially sharing traffic or serving different traffic flows.

             ┌── Path A ──┐
Traffic ─────┤            ├──── Destination
             └── Path B ──┘

Active/active operation requires appropriate traffic distribution, routing, protocol support, or application design. It does not necessarily mean that every packet is duplicated over both paths.

Comparison

Feature Active/standby Active/active
Normal operation Primary handles the designated workload Multiple components handle traffic or tasks
Failure response Standby takes over Remaining active components continue according to the design
Resource utilization Standby capacity may be underused Resources may be used concurrently
Configuration Requires standby readiness and failover logic Requires coordination, traffic distribution, or state management
Main concern Failover delay and standby readiness Consistency, traffic handling, and shared failure risks

Neither approach is universally better. The choice depends on the supported technology and the required service behavior.

7. Ethernet redundancy protocols

Several protocols provide network redundancy, but they operate differently and are intended for different architectures.

Protocol or mechanism Main function Key consideration
RSTP Prevents Layer 2 loops and restores forwarding after topology changes Recovery depends on topology and configuration
MSTP Manages multiple spanning-tree instances Requires compatible configuration across the intended network
MRP Industrial Ethernet ring redundancy Requires compatible devices and correct manager/client configuration
DLR EtherNet/IP-associated device-level ring redundancy Requires DLR-compatible devices and supported roles
PRP Parallel Redundancy Protocol Sends duplicate frames over two independent LANs for supported zero-recovery-time communication
HSR High-availability Seamless Redundancy Uses a ring-oriented architecture with frame duplication and duplicate handling
Link aggregation Combines compatible physical links into a logical link Protects supported link failures but does not automatically protect against switch failure
Vendor-specific protocols Provide redundancy within supported product families Verify interoperability, limits, and recovery behavior

These mechanisms are not interchangeable. Some restore forwarding after a failure, while others are designed to deliver duplicate frames over independent paths so that a single path failure does not require conventional failover.

8. PRP: Parallel Redundancy Protocol

PRP is defined in IEC 62439-3. It provides seamless redundancy by sending duplicate frames through two independent LANs.

A typical PRP-capable device, called a Doubly Attached Node for PRP (DANP), connects to LAN A and LAN B. A compatible device sends the same frame over both networks, and the receiving device accepts the first valid copy and discards the duplicate.

                  ┌── LAN A ──┐
PRP-capable node ─┤            ├─ PRP-capable node
                  └── LAN B ──┘

The two LANs should be designed with sufficient independence to avoid common failures.

Main characteristics

  • Frames are transmitted over both LANs.
  • The receiving node processes the first valid copy.
  • Duplicate copies are discarded by compatible receiving equipment.
  • A failure of one LAN can be tolerated without conventional path-switching delay, assuming the other LAN remains operational and the endpoints support the required behavior.

Important limitations

  • Both communication paths must be available and correctly configured during normal operation.
  • The endpoints must support PRP or use an appropriate compatible RedBox arrangement.
  • The two LANs should not share avoidable single points of failure.
  • PRP increases network traffic because frames are duplicated.
  • Device compatibility and network capacity must be checked.

PRP is particularly relevant where seamless communication is required and even a brief recovery interval is unacceptable for the intended application.

9. HSR: High-availability Seamless Redundancy

HSR is also defined in IEC 62439-3. It is designed for seamless redundancy in supported ring-based architectures.

In a typical HSR arrangement, compatible nodes forward frames around the ring in both directions. The destination receives duplicate copies and discards duplicates according to the protocol.

       Node A -------- Node B
         |                |
         |                |
       Node D -------- Node C

The physical ring provides two directions for frame delivery. A supported link failure can leave a path available in the opposite direction.

Main characteristics

  • Supports duplicate frame transmission around the ring.
  • Can provide seamless recovery for supported single-path failures.
  • Requires HSR-capable nodes or compatible interconnection equipment.
  • Increases traffic and processing requirements because duplicate frames are handled.
  • Requires careful attention to network size, traffic load, and device capabilities.

HSR is not the same as an ordinary Ethernet ring using RSTP or MRP. Its frame-handling behavior and device requirements are different.

10. MRP and DLR versus PRP and HSR

These technologies address redundancy differently.

Feature MRP DLR PRP HSR
Typical architecture Industrial Ethernet ring EtherNet/IP-associated ring Two independent LANs Redundant ring
Normal operation Ring protocol manages forwarding Ring supervisor manages ring behavior Duplicate frames traverse both LANs Duplicate frames traverse ring paths
Recovery approach Changes ring forwarding after a fault Changes ring forwarding after a fault Continues over the surviving LAN Continues over the surviving path
Seamless redundancy by frame duplication No, not its standard mechanism No, not its standard mechanism Yes, for supported configurations Yes, for supported configurations
Main requirement Compatible MRP-capable devices Compatible DLR-capable devices PRP-capable endpoints or compatible RedBoxes HSR-capable devices or compatible interconnection equipment

Recovery times for MRP and DLR depend on implementation and configuration. PRP and HSR are designed to avoid conventional switchover interruption for supported faults, but this does not mean every application is guaranteed to experience zero disruption under every failure condition.

11. Link aggregation and redundancy

Link aggregation combines multiple physical Ethernet links into one logical link. A common standardized mechanism is LACP, defined by IEEE 802.1AX.

A simplified example:

Switch A ══ Link 1 ══ Switch B
         ══ Link 2 ══

When properly configured, multiple links can carry traffic as one logical aggregate. The aggregate can provide additional capacity and tolerate certain individual member-link failures.

What link aggregation can protect against

  • Failure of an individual member link, provided sufficient members remain active.
  • Some forms of link congestion by distributing traffic across available members.
  • Selected cable or port failures.

What it does not automatically protect against

  • Failure of Switch A or Switch B.
  • Failure of a shared power source.
  • Failure of a single upstream router or firewall.
  • Application or controller failure.
  • Every possible traffic interruption during a change in aggregate membership.

Both ends must support and correctly configure the selected aggregation mechanism. Traffic distribution depends on the implementation and hashing method, so one individual communication flow may not use all links simultaneously.

Do not confuse link aggregation with a ring redundancy protocol. They solve related but different problems.

12. Switch redundancy

Switch redundancy seeks to prevent the failure of one switching device from interrupting the required communication service.

Possible designs include:

  • Two switches connected through a supported redundant topology.
  • Dual-homed devices with independent network interfaces.
  • PRP or HSR architectures where supported.
  • Redundant industrial Ethernet rings.
  • Redundant distribution switches with appropriate Layer 3 and Layer 2 design.

Two switches alone do not establish redundancy. The endpoints must have a usable alternative path, and the network must be able to forward traffic correctly after a failure.

Questions to ask when reviewing a design

  • Are the two switches connected through genuinely independent paths?
  • Does the endpoint have one network interface or two?
  • Can the endpoint change paths or use redundant interfaces?
  • Are both switches dependent on the same power supply?
  • Do both paths share the same cable tray or physical route?
  • Is the required VLAN available on both paths?
  • How are duplicate packets or loops prevented?
  • What happens to active application sessions during a failure?
  • How is the failure detected and alarmed?

A redundant switching architecture should be assessed as a complete system, not just by counting switches.

13. Power redundancy

Communication redundancy can be defeated by a shared power failure.

For example, two industrial switches may use separate Ethernet paths but share one DC power supply. If that supply fails, both switches can become unavailable.

Possible approaches include:

  • Switches with dual power inputs.
  • Independent power supplies.
  • Separate protected power distribution branches.
  • Monitoring of power input and supply alarms.
  • Physical separation of power feeds where justified.

Dual power inputs do not necessarily imply fully independent power systems. The actual design must consider upstream power sources, circuit protection, common distribution equipment, and the manufacturer's requirements.

For critical installations, verify that the power arrangement is supported by the equipment and that failure of one feed does not violate the required operating behavior.

14. Redundancy and VLANs

Redundancy mechanisms and VLAN segmentation must be configured together.

For example, suppose VLAN 10 carries PLC traffic and VLAN 30 carries SCADA traffic over a redundant network.

Both paths may need to support the required VLANs, and the Layer 3 gateway arrangement must remain available if inter-VLAN communication is required.

Check the following:

  • VLAN membership on every relevant switch.
  • Trunk allowed VLANs on each path.
  • Consistent native VLAN and PVID behavior where applicable.
  • Spanning-tree or ring protocol compatibility.
  • Multicast handling and IGMP snooping where required.
  • Routing and gateway redundancy where needed.
  • Firewall and ACL behavior after path changes.

A redundant physical network can still fail to carry a particular VLAN if its configuration is incomplete.

15. Redundancy and industrial application behavior

The network may recover correctly while the industrial application remains interrupted.

This distinction is particularly important for PLCs, remote I/O, robots, drives, and time-sensitive control applications.

PLC and remote I/O

The communication system may have a defined connection timeout. If the interruption exceeds that timeout, the controller may declare an I/O connection fault even after Ethernet forwarding resumes.

Robot-to-PLC communication

A brief interruption may cause a handshake timeout or application fault. The recovery procedure depends on the robot controller, PLC logic, and application design.

HMI and SCADA

The user interface may lose live data or show communication alarms. Some applications reconnect automatically; others require a session or service to recover.

Drives and motion systems

Communication interruption can trigger defined drive behavior, including a controlled stop or another configured response. The result depends on the drive, protocol, and machine design.

Safety-related communication

Redundancy must be implemented within the applicable certified safety architecture. An ordinary redundant Ethernet path does not automatically make a safety function compliant or guarantee safe operation.

For every critical application, document:

  • Maximum acceptable communication interruption.
  • Expected device behavior during loss of communication.
  • Whether reconnection is automatic.
  • Whether an operator or maintenance action is required.
  • The required machine state after a fault.
  • The test method used to verify recovery.

16. Common redundancy design mistakes

  1. Duplicating links but not equipment. Two cables connected to one switch do not protect against that switch failing.
  2. Sharing a common power source. Two switches can fail together if their power infrastructure is not sufficiently independent.
  3. Using incompatible protocols. Similar redundancy features do not guarantee that devices can participate in the same redundancy domain.
  4. Ignoring network capacity. The surviving path must carry the required traffic after a failure.
  5. Assuming redundancy means zero packet loss. Some protocols restore forwarding after a detection and recovery interval.
  6. Ignoring application timeouts. PLC or I/O connections may fault before the network recovers.
  7. Using redundant paths that share the same physical risk. Two cables in one exposed route can be damaged by the same event.
  8. Failing to test real faults. A healthy status display does not prove that a backup path works.
  9. Ignoring configuration backups. Replacement equipment may not reproduce the intended redundancy configuration without a verified baseline.
  10. Failing to monitor degraded operation. A network can continue operating on one path while no longer being fully redundant.

17. Redundancy troubleshooting

When a supposedly redundant network fails, determine whether the problem is in the physical path, redundancy protocol, endpoint behavior, or application.

Step 1: Identify the failure scope

Determine which devices, VLANs, and applications are affected.

Check whether the fault involves one link, one switch, an entire network segment, or only one application.

Step 2: Check physical links and power

Inspect link status, transceivers, cable condition, switch power, and hardware alarms.

Step 3: Check the redundancy mechanism

Review the protocol state, active and standby paths, ring roles, aggregation status, or PRP/HSR diagnostics as applicable.

Step 4: Check Layer 2 and Layer 3 configuration

Verify VLANs, trunks, MAC address learning, routing, gateway availability, and security policies.

Step 5: Check application behavior

Review PLC diagnostics, I/O connection status, robot alarms, SCADA communication events, and device timeout settings.

Step 6: Preserve evidence

Record timestamps, switch logs, port counters, protocol state, and application alarms before making changes.

Troubleshooting matrix

Symptom Possible cause What to check
Backup path does not take over Incorrect protocol configuration or incompatible equipment Redundancy roles, supported topology, and fault logs
Communication fails after one link breaks No usable alternative path or incorrect VLAN configuration Physical topology, trunk VLANs, and protocol status
One switch failure disconnects the network Shared dependency or incomplete switch redundancy Endpoint interfaces, alternate paths, and common components
Both switches fail together Shared power or common physical infrastructure Power distribution, upstream equipment, and cable routing
Ring remains operational but PLC I/O faults Application timeout or reconnection problem PLC diagnostics and measured recovery interval
Aggregated link loses capacity Member link failure or inconsistent configuration LACP state, member status, and remaining bandwidth
Network recovers but SCADA stays disconnected Application session or routing problem Gateway reachability, server logs, and session recovery
Frequent path changes occur Intermittent links or unstable redundancy state Link logs, port counters, cable condition, and protocol events
PRP or HSR reports degraded redundancy One network path or redundant node interface has failed Both LANs, endpoint interfaces, and protocol diagnostics
Network works until heavy traffic occurs Insufficient bandwidth or poor traffic handling Utilization, queue drops, QoS, and alternate-path capacity

18. Commissioning and redundancy testing

Redundancy must be tested under controlled conditions. Do not create faults on a production network without authorization, risk assessment, and a recovery plan.

Pre-test checklist

  • Confirm the intended redundancy protocol and supported equipment.
  • Document the normal network topology.
  • Record the approved configuration and backup files.
  • Identify critical PLC, remote I/O, robot, drive, and SCADA connections.
  • Confirm acceptable interruption and recovery requirements.
  • Prepare the approved fault-injection and rollback procedure.
  • Ensure production and safety requirements permit the test.

Test checklist

  • Verify the normal operating state.
  • Record baseline traffic, link state, and protocol diagnostics.
  • Test the approved single-link failure scenario.
  • Measure the network interruption and recovery behavior.
  • Confirm application communication and machine behavior.
  • Test additional failure scenarios only where the design and procedure permit them.
  • Verify that the system reports degraded redundancy.
  • Restore the intended configuration and verify normal operation.

Post-test checklist

  • Save test results and timestamps.
  • Document measured recovery and observed packet loss.
  • Record application alarms and recovery behavior.
  • Update the network diagram and maintenance documentation.
  • Confirm that all redundant paths are healthy again.
  • Escalate any mismatch between expected and measured behavior.

19. Preventive maintenance and monitoring

Redundant systems require monitoring because a network may continue operating after losing its backup path.

Useful maintenance activities include:

  • Monitoring switch, port, and power supply alarms.
  • Checking ring, spanning-tree, aggregation, PRP, or HSR status as applicable.
  • Reviewing link-flapping and error-counter history.
  • Monitoring network utilization and packet drops.
  • Maintaining approved firmware and configuration backups.
  • Verifying redundancy alarms are visible to maintenance personnel.
  • Periodically validating recovery procedures under approved conditions.
  • Keeping physical cable routes and power dependencies documented.

A degraded redundant network is still running, but one or more protections may no longer be available. Detecting this state before another failure occurs is a major reason to monitor redundancy status.

20. Interview questions and answers

1. What is network redundancy?

It is the use of additional paths, devices, or services to maintain or restore communication when a component fails.

2. What is a single point of failure?

A component whose failure interrupts the required service because no adequate alternative is available.

3. What is the difference between RSTP and PRP?

RSTP manages a loop-free Layer 2 forwarding topology and restores forwarding after topology changes. PRP sends duplicate frames over two independent LANs so that a receiving device can accept the first valid copy without conventional path switchover for supported failures.

4. What is the difference between MRP and DLR?

Both provide industrial ring redundancy, but they belong to different protocol ecosystems and have different device requirements and configurations. MRP is standardized for industrial Ethernet ring redundancy, while DLR is associated with EtherNet/IP environments.

5. What is the purpose of link aggregation?

It combines compatible physical links into a logical link, potentially increasing aggregate capacity and tolerating certain member-link failures.

6. Does link aggregation protect against switch failure?

Not by itself. Switch-level protection requires an architecture that provides a supported alternative path and appropriate failover behavior.

7. Why can redundant Ethernet still cause a PLC fault?

The network interruption may exceed the PLC or I/O connection timeout, or the application may require reconnection after communication returns.

8. Why is power redundancy important?

Redundant network paths cannot compensate for multiple critical devices losing power through a shared failed supply.

9. What is seamless redundancy?

A design intended to continue communication without conventional failover interruption for supported failures, often through duplicate frame transmission over independent paths.

10. How do you prove that redundancy works?

Perform an approved fault test, observe network protocol behavior, measure interruption or packet loss, and verify the actual application response.

11. What is degraded redundancy?

The system is still operating, but a backup path or component is unavailable, leaving the network more vulnerable to another failure.

12. Why should redundant paths be physically independent?

If both paths share a cable route, power source, switch, or other common dependency, one event can disable both and defeat the purpose of redundancy.

21. Practical exercises

Exercise 1: Two cables, one switch

A PLC has two Ethernet cables connected to the same switch. The switch fails.

Answer: The two cables do not protect against the switch failure. A supported architecture must provide an alternative switching path, and the PLC must support the relevant connection arrangement.

Exercise 2: Redundant ring with I/O timeout

A ring recovers after a link failure, but the PLC reports remote I/O connection faults.

Answer: Compare the measured interruption with the I/O timeout and inspect controller diagnostics. Confirm whether the connection recovers automatically and whether the application requires a recovery procedure.

Exercise 3: PRP network degradation

A PRP-capable device continues communicating after LAN A fails.

Answer: Communication may continue over LAN B, but the system is now operating with degraded redundancy. Investigate and restore LAN A before a second failure removes the remaining path.

Exercise 4: LACP member failure

A two-link aggregate loses one member link.

Answer: The aggregate may continue operating over the remaining member if the configuration and link state are correct. Available capacity is reduced, and the impact on individual flows depends on traffic distribution and remaining bandwidth.

Exercise 5: Common power failure

Two redundant switches lose power simultaneously.

Answer: Investigate the shared power infrastructure. Redundant network topology is insufficient if both paths depend on a single vulnerable power source.

22. Final mental model

When designing or troubleshooting redundancy, evaluate five questions:

  1. What must remain available? Identify the critical device, communication path, or application.
  2. What can fail? Consider cables, switches, power, interfaces, gateways, controllers, and services.
  3. What provides the alternative? Identify the actual redundant path or standby component.
  4. How does recovery occur? Understand the protocol, application behavior, and acceptable interruption.
  5. How is failure detected? Confirm that monitoring identifies both complete failures and degraded redundancy.

The core engineering principle is that redundancy is an end-to-end property. Duplicate hardware alone does not guarantee availability. The paths must be usable, the configuration must support recovery, common failure points must be addressed, and the complete application must be tested.
