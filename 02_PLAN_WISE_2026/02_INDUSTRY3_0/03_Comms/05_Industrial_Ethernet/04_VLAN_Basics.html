1. Definition and purpose of a VLAN

A Virtual Local Area Network (VLAN) is a logical Layer 2 network that divides a physical Ethernet switching infrastructure into separate broadcast domains.

Without VLANs, devices connected to the same Layer 2 network may belong to the same broadcast domain, depending on the physical and logical configuration. VLANs allow a managed switch or group of managed switches to separate traffic logically without requiring a dedicated physical switch for every network segment.

For example, a manufacturing plant might use the same physical switch infrastructure for PLCs, robot controllers, SCADA servers, engineering workstations, and network management. VLANs can separate these device groups into different logical networks.

Physical Ethernet switching infrastructure
                    |
        +-----------+-----------+
        |           |           |
     VLAN 10      VLAN 20     VLAN 30
     PLC/HMI      Robotics     SCADA
        |           |           |
    Devices      Devices      Servers

The devices share physical infrastructure, but their Layer 2 broadcast traffic is separated by VLAN.

2. Why VLANs are used in industrial automation

VLANs are useful for organizing industrial networks, controlling broadcast domains, and supporting security architecture.

Purpose Explanation Industrial example
Network segmentation Separates groups of devices logically Separate robot cells
Broadcast control Limits Layer 2 broadcasts to the relevant VLAN Prevent unnecessary broadcast traffic reaching unrelated cells
Network organization Creates a consistent logical structure Separate PLC, SCADA, and management networks
Security architecture Supports controlled communication between network zones Restrict engineering workstation access to selected controllers
Troubleshooting Helps isolate network faults and traffic Identify whether a problem affects one cell or several VLANs
Traffic management Supports VLAN-based QoS and priority handling Prioritize time-sensitive industrial traffic where supported
Address management Helps organize IP subnets and gateways Assign a dedicated IP subnet to each VLAN

A VLAN does not automatically make the network secure. It separates Layer 2 broadcast domains, but traffic can still pass between VLANs through a router or Layer 3 switch if routing and security policies permit it.

3. VLAN, subnet, and broadcast domain

These terms are related, but they are not interchangeable.

VLAN

A VLAN is a logical Layer 2 network. Ethernet switching and VLAN membership determine which devices belong to the same Layer 2 broadcast domain.

IP subnet

An IP subnet is a logical Layer 3 address range defined by an IP address and subnet mask or prefix length.

For example, 192.168.10.0/24 is an IPv4 subnet.

Broadcast domain

A broadcast domain is the set of devices that receive a particular Layer 2 broadcast within the relevant bridged network.

A VLAN normally defines a separate Layer 2 broadcast domain.

Common relationship

Industrial networks commonly use one IP subnet per VLAN, although VLANs and subnets are different concepts.

Concept Layer Main purpose Example
VLAN Layer 2 Logical Ethernet segmentation VLAN 10
IPv4 subnet Layer 3 IP address organization and routing 192.168.10.0/24
Broadcast domain Layer 2 Defines where Layer 2 broadcasts propagate Devices in VLAN 10
Default gateway Layer 3 Provides a next hop for off-subnet communication 192.168.10.1

A correctly configured Layer 2 switch does not automatically route traffic between VLAN 10 and VLAN 20. Inter-VLAN communication requires Layer 3 routing, such as a router or Layer 3 switch, together with appropriate IP addressing and routing configuration.

4. VLAN ID and IEEE 802.1Q

VLANs are commonly identified by VLAN IDs. IEEE 802.1Q defines a standard method for carrying VLAN information in Ethernet frames.

VLAN ID range

VLAN ID General meaning
0 Priority-tagged frame; does not identify an ordinary VLAN membership in the usual way
1 Common default VLAN on many switches; platform behavior varies
2–4094 Available for ordinary VLAN IDs, subject to platform restrictions and configuration
4095 Reserved; not an ordinary configurable VLAN ID

Although VLAN IDs 1–4094 are within the ordinary usable range, some vendors reserve specific IDs or apply special behavior. Always check the switch model and software documentation.

IEEE 802.1Q tag structure

An 802.1Q tag is inserted into an Ethernet frame to carry VLAN and priority information.

Field Size Function
TPID 16 bits Identifies the VLAN tag protocol; commonly 0x8100
PCP 3 bits Priority Code Point for traffic prioritization
DEI 1 bit Drop Eligible Indicator
VID 12 bits VLAN identifier field

The VLAN identifier occupies 12 bits, allowing 4096 encoded values. Special values such as 0 and 4095 have reserved meanings, so they are not ordinary VLAN IDs for device membership.

The PCP field supports eight priority code points, from 0 to 7. Actual traffic treatment depends on the switch's QoS configuration and the network design.

Why the VLAN tag matters

When a frame travels over a trunk link, the 802.1Q tag lets the receiving switch identify the VLAN to which the frame belongs.

Without the correct VLAN information and matching port configuration, traffic may enter the wrong VLAN, be discarded, or fail to reach its destination.

5. Access ports and trunk ports

Understanding access and trunk ports is essential for configuring VLANs correctly.

Access port

An access port is generally assigned to one data VLAN and is typically used to connect an endpoint that sends and receives ordinary untagged Ethernet frames.

Examples include:

  • PLC Ethernet ports.
  • HMI panels.
  • Robot controllers.
  • Industrial PCs.
  • Printers and engineering laptops when connected to a designated access port.

The switch associates incoming untagged frames with the port's configured access VLAN. Frames sent to a normal endpoint are typically transmitted without an 802.1Q tag.

Some industrial devices can generate or expect tagged traffic, but they require explicit support and matching configuration.

Trunk port

A trunk port carries traffic for multiple VLANs across one physical Ethernet link.

Typical uses include:

  • Switch-to-switch uplinks.
  • Switch-to-router connections.
  • Switch-to-Layer 3 switch connections.
  • Connections to virtualization hosts or servers that explicitly support VLAN tagging.

A trunk normally uses 802.1Q tags to identify VLANs. Its allowed VLAN list determines which VLANs can traverse the link.

Access versus trunk

Feature Access port Trunk port
Typical purpose Endpoint connection Network infrastructure link
VLAN membership Usually one data VLAN Multiple VLANs
Frame tagging Typically untagged toward the endpoint Tagged for most VLANs
Configuration Access VLAN Allowed VLAN list and tagging behavior
Typical connection PLC, HMI, robot controller Switch uplink
Main risk Incorrect access VLAN Missing VLAN, tagging mismatch, or native VLAN mismatch

The terms and exact commands vary by vendor. Do not assume that every switch implements access and trunk behavior identically.

6. Port VLAN ID (PVID) and native VLAN

Two related concepts frequently cause industrial Ethernet problems.

PVID

The Port VLAN ID (PVID) is the VLAN classification applied to incoming untagged frames on a port in common VLAN-aware switch implementations.

For example, if a port has PVID 10, an incoming untagged frame will typically be classified into VLAN 10.

The exact relationship between PVID and access VLAN configuration depends on the switch platform.

Native VLAN

On many 802.1Q trunk implementations, the native VLAN identifies the VLAN whose traffic is transmitted untagged over the trunk.

The receiving switch must interpret those untagged frames consistently. A native VLAN mismatch can cause traffic to be classified into the wrong VLAN and can create security or connectivity problems.

Some platforms support different native VLAN or untagged VLAN configuration models. Check the device documentation rather than assuming that all switches behave alike.

Example

Suppose two switches connect through a trunk:

  • Switch A uses VLAN 99 as the native VLAN.
  • Switch B uses VLAN 10 as the native VLAN.

If untagged traffic is transmitted over that trunk, the switches may classify the traffic differently. The result can be unexpected connectivity, traffic leakage between intended segments, or a configuration warning.

A good practice is to configure trunk tagging consistently at both ends and use an explicitly documented native VLAN policy.

7. Designing an industrial VLAN plan

A VLAN plan should reflect machine dependencies, network architecture, availability requirements, and security boundaries.

Consider a hypothetical manufacturing cell.

VLAN ID VLAN name Example subnet Intended devices
10 PLC_HMI 192.168.10.0/24 PLCs and HMIs requiring direct Layer 2 communication
20 ROBOTICS 192.168.20.0/24 Robot controllers and related devices
30 SCADA 192.168.30.0/24 SCADA servers and authorized interfaces
40 ENGINEERING 192.168.40.0/24 Engineering workstations
50 NET_MGMT 192.168.50.0/24 Managed switch management interfaces

These are illustrative addresses, not a recommended production addressing scheme for every plant.

Important design decisions

  1. Identify which devices must communicate directly at Layer 2.
  2. Document existing IP addresses, subnet masks, gateways, protocols, and dependencies.
  3. Assign VLAN IDs and names consistently across switches.
  4. Determine which VLANs need to cross each trunk.
  5. Plan Layer 3 gateways and access-control rules for required inter-VLAN communication.
  6. Verify industrial protocol behavior, multicast requirements, redundancy, and device configuration before changing a live network.
  7. Document VLAN membership, subnet assignments, switch ports, and approved communication paths.

Do not separate a PLC and its HMI merely because separating them looks tidy on a diagram. If their existing communication depends on the same Layer 2 network, moving one device into another VLAN may break communication unless routing and the relevant application configuration support the change.

8. Configuring VLANs on managed switches

The following workflow is vendor-neutral. The command syntax and configuration order differ between Cisco, Siemens, Allen-Bradley, Hirschmann, Moxa, and other platforms.

Step 1: Record the existing configuration

Before changing a production switch, record:

  • Switch model, firmware, and management IP.
  • Port-to-device mapping.
  • Existing VLANs and VLAN membership.
  • Trunk links and allowed VLANs.
  • Native VLAN or PVID configuration.
  • Redundancy configuration.
  • IP addressing and gateways.
  • Relevant PLC, HMI, robot, and SCADA communication paths.

Back up the current configuration where supported.

Step 2: Create the VLANs

Create the required VLAN IDs and assign meaningful names.

For example:

VLAN 10  PLC_HMI
VLAN 20  ROBOTICS
VLAN 30  SCADA
VLAN 40  ENGINEERING
VLAN 50  NET_MGMT

A VLAN must exist and be active according to the platform's configuration model before ports can reliably use it.

Step 3: Assign endpoint ports

Assign each endpoint-facing port to its intended VLAN.

Example:

Switch port 1 -> PLC       -> VLAN 10
Switch port 2 -> HMI       -> VLAN 10
Switch port 3 -> Robot     -> VLAN 20
Switch port 4 -> SCADA PC  -> VLAN 30

These assignments are illustrative. Actual assignments must be based on documented communication requirements.

Step 4: Configure trunk links

For a switch-to-switch uplink:

  • Configure the link as a trunk at both ends.
  • Allow only the VLANs required across the link.
  • Verify consistent tagging and native VLAN behavior.
  • Confirm that all required VLANs exist on the relevant switches.
  • Preserve the configured redundancy protocol and loop-prevention settings.

Example allowed VLAN list:

Switch A ===== trunk ===== Switch B
               VLAN 10
               VLAN 20
               VLAN 30
               VLAN 50

VLAN 40 should not cross this trunk unless the network design requires it.

Restricting trunk VLANs reduces unnecessary Layer 2 propagation and makes troubleshooting easier.

Step 5: Configure Layer 3 routing if needed

If devices in different VLANs must communicate, configure the appropriate Layer 3 interfaces or gateway arrangement.

For example:

VLAN 10: 192.168.10.0/24
Gateway: 192.168.10.1

VLAN 20: 192.168.20.0/24
Gateway: 192.168.20.1

The gateway addresses must actually exist on the router or Layer 3 switch, and the devices must be configured with suitable IP settings.

Routing alone does not guarantee communication. Firewalls, ACLs, endpoint firewalls, protocol requirements, and return routes may also affect connectivity.

Step 6: Save and verify

After applying the configuration:

  • Confirm the intended VLAN membership on each port.
  • Confirm trunk state and allowed VLANs.
  • Check endpoint link status.
  • Verify IP reachability and application communication.
  • Confirm that required industrial protocols still work.
  • Check redundancy and recovery behavior.
  • Save the validated configuration using the platform's supported procedure.

9. VLANs across multiple switches

A VLAN can extend across multiple switches when the Layer 2 connections between those switches are configured to carry that VLAN.

For example:

PLC -- access VLAN 10 -- Switch A
                            |
                       Trunk link
                       VLAN 10, 20
                            |
HMI -- access VLAN 10 -- Switch B
Robot -- access VLAN 20 -- Switch B

The PLC and HMI can communicate within VLAN 10 if their addressing and other settings are correct. The robot belongs to VLAN 20 and does not become a member of VLAN 10 simply because both devices connect to Switch B.

For VLAN 10 to span the switches:

  • VLAN 10 must be configured and active on the required switches.
  • The inter-switch link must carry VLAN 10.
  • Port tagging and untagged VLAN behavior must be consistent.
  • Spanning Tree or the configured industrial redundancy mechanism must prevent Layer 2 loops.
  • Any required IP and application settings must remain correct.

A VLAN configured on Switch A does not automatically become available across every switch in the plant. VLAN propagation depends on the switching technology and configuration.

10. Inter-VLAN communication

Devices in different VLANs generally cannot communicate directly at Layer 2. Their traffic must be routed through a Layer 3 device if communication is required.

Example

A PLC is in VLAN 10, while a SCADA server is in VLAN 30.

PLC in VLAN 10
      |
   Switch
      |
Layer 3 gateway
      |
   Switch
      |
SCADA server in VLAN 30

The Layer 3 gateway receives traffic destined for another subnet and routes it according to its routing table and security policy.

The network design must account for:

  • Correct IP address and subnet mask.
  • Correct default gateway on endpoints that communicate off-subnet.
  • Routing interfaces for the relevant VLANs.
  • ACLs or firewall rules allowing required traffic.
  • Return routes and endpoint firewall settings.
  • Industrial protocol discovery, multicast, broadcast, and timing requirements.

Important distinction

A Layer 2 managed switch can support VLANs without supporting inter-VLAN routing. A Layer 3 switch can provide routing functionality, but that capability must be configured.

Do not assume that assigning two ports to different VLANs automatically enables communication between them.

11. VLANs and industrial protocols

VLAN configuration can affect industrial communications in ways that are not obvious from a simple ping test.

Protocol or traffic type VLAN consideration
EtherNet/IP Verify controller, adapter, HMI, and multicast traffic paths
PROFINET Preserve required real-time communication and device discovery behavior
Modbus TCP Ensure the client and server have a valid Layer 2 or routed path
OPC UA Verify IP reachability, server endpoints, security settings, and firewall rules
PLC-to-HMI traffic Preserve existing addressing and communication dependencies
Robot-to-PLC communication Confirm both network membership and required routing or protocol configuration
DHCP Ensure DHCP broadcasts or relay configuration reach the intended server
DNS Ensure clients can reach the configured DNS server across any VLAN boundary
SNMP and management traffic Permit access only from authorized management systems
Multicast traffic Verify IGMP snooping, querier configuration, and multicast routing where needed

The required behavior depends on the protocol, equipment, and architecture. VLAN separation must be tested against the actual application, not just basic IP connectivity.

12. VLANs, QoS, and industrial traffic priority

VLANs and Quality of Service (QoS) are related but perform different jobs.

  • VLANs separate Layer 2 broadcast domains.
  • QoS controls how traffic is classified, queued, and transmitted under congestion.
  • The 802.1Q PCP field can carry a Layer 2 priority value.
  • Switches may map PCP, DSCP, or other classification criteria to internal traffic queues.

Creating a separate VLAN does not automatically give its traffic higher priority.

For industrial networks, QoS should be designed around measured traffic requirements, supported device behavior, and the relevant real-time or latency constraints. Incorrect priority policies can starve other traffic or fail to improve the traffic that actually needs protection.

13. VLANs and network redundancy

VLAN configuration must work with the network's loop-prevention and redundancy design.

Ethernet Layer 2 loops can create broadcast storms, duplicate frames, and unstable MAC address learning. VLANs do not inherently prevent these problems.

Depending on the equipment and design, the network may use:

  • Spanning Tree Protocol (STP).
  • Rapid Spanning Tree Protocol (RSTP).
  • Multiple Spanning Tree Protocol (MSTP).
  • Media Redundancy Protocol (MRP).
  • Vendor-specific industrial ring protocols.

Not every protocol operates in the same way or supports the same topology. VLAN membership, trunk configuration, spanning-tree settings, and industrial redundancy configuration must be validated together.

After a VLAN or trunk change, verify that the intended redundant paths remain operational and that the network recovers correctly from the loss of a link.

14. VLAN troubleshooting

When a device loses communication after a VLAN change, check the simplest Layer 2 configuration errors before assuming that the PLC or application has failed.

Troubleshooting sequence

  1. Confirm physical link status and cable condition.
  2. Check the device's IP address, subnet mask, and gateway.
  3. Confirm the VLAN assigned to the endpoint port.
  4. Verify that the VLAN exists and is active on the switch.
  5. Check the trunk configuration and allowed VLAN list.
  6. Check tagging, PVID, and native VLAN behavior.
  7. Check the MAC address table to confirm where the device is learned.
  8. Test communication within the same VLAN.
  9. If communication crosses VLANs, check routing, gateways, ACLs, and firewalls.
  10. Verify industrial protocol-specific requirements, multicast behavior, and redundancy status.
  11. Review switch logs, port counters, and configuration changes.

Troubleshooting table

Symptom Possible cause What to check
PLC cannot communicate with HMI Ports assigned to different VLANs Access VLAN and actual communication design
Devices on the same VLAN but different switches cannot communicate VLAN missing from trunk VLAN existence and allowed VLAN list at both ends
Device cannot reach its gateway Wrong VLAN, IP settings, or gateway Port membership, subnet mask, gateway, and gateway interface
Communication fails only across VLANs Routing or policy problem Layer 3 interfaces, routes, ACLs, and firewalls
Communication works intermittently Loop, link flapping, or inconsistent configuration Redundancy status, logs, and port counters
Some traffic passes but other traffic fails Multicast, QoS, ACL, or application issue Protocol behavior, multicast configuration, and traffic policies
Untagged traffic reaches an unexpected network PVID or native VLAN mismatch Port VLAN classification and trunk settings
Switch management becomes unreachable Management VLAN or IP path changed Management interface VLAN, address, gateway, and access rules
Device appears on the wrong switch port Incorrect cabling or unexpected MAC learning MAC address table, LLDP where available, and port mapping
VLAN works on one switch but not another VLAN not configured or inactive on a downstream switch VLAN database and inter-switch configuration

Useful diagnostic information

Managed switches commonly expose the following information through a web interface, CLI, or vendor software:

  • VLAN database and port membership.
  • Access/trunk mode and allowed VLAN list.
  • PVID or native VLAN settings.
  • MAC address table.
  • Port status, speed, and duplex.
  • CRC/FCS errors, discards, and link flaps.
  • Spanning Tree or ring redundancy status.
  • Configuration change logs.
  • Packet counters and port mirroring capabilities.

Generic CLI examples on platforms that support similar commands include:

show vlan
show interfaces status
show interfaces trunk
show mac address-table
show spanning-tree

These commands are examples, not universal commands. Siemens, Rockwell, Moxa, Hirschmann, and other switch families may use different interfaces and terminology.

15. VLAN security and industrial network segmentation

VLANs are useful building blocks for industrial cybersecurity, but they are not a complete security solution.

Good practices

  • Separate control, supervisory, engineering, and management traffic according to operational requirements.
  • Use dedicated management VLANs where appropriate.
  • Restrict inter-VLAN routing with explicit ACLs or firewalls.
  • Allow only the industrial protocols and endpoints that are required.
  • Restrict switch administration to authorized management workstations.
  • Disable unused ports where operationally safe.
  • Use documented port assignments and configuration backups.
  • Avoid unnecessary VLANs on trunk links.
  • Monitor unexpected MAC addresses, configuration changes, and traffic patterns.
  • Validate cybersecurity changes with production and safety requirements.

VLANs do not replace firewalls

A VLAN separates Layer 2 traffic, but a router or Layer 3 switch may still route between VLANs. If routing is enabled without suitable access controls, devices in separate VLANs may still communicate.

Security therefore requires a combination of segmentation, controlled routing, firewall policies, secure management, monitoring, and appropriate operational procedures.

Do not make untested segmentation changes on a production machine. A VLAN change can interrupt PLC I/O, robot handshakes, SCADA communication, engineering access, or switch management even when the physical network remains healthy.

16. Commissioning and maintenance checklist

Use this checklist when commissioning or modifying VLANs.

  • Record the existing configuration and create a recoverable backup.
  • Document the purpose, ID, and name of each VLAN.
  • Record the intended IP subnet and gateway for each VLAN where applicable.
  • Map every endpoint port to the correct VLAN.
  • Identify all trunk links and their required VLANs.
  • Verify PVID, native VLAN, and tagged/untagged behavior.
  • Verify that VLANs exist and are active on all required switches.
  • Test communication between devices that should share a VLAN.
  • Test routed communication between VLANs where required.
  • Verify firewall rules, ACLs, multicast, and industrial protocol requirements.
  • Check spanning-tree or industrial ring redundancy status.
  • Verify switch management access after changes.
  • Confirm machine operation, alarms, robot handshakes, and SCADA visibility.
  • Save the validated configuration and update network documentation.

For maintenance, keep a port-to-device mapping, VLAN table, IP addressing plan, trunk inventory, and configuration backup. These records reduce recovery time when a switch must be replaced or a machine is retrofitted.

17. Practical example

A managed switch connects a PLC, HMI, robot controller, and SCADA server. The network engineer creates VLAN 10 for PLC/HMI, VLAN 20 for robotics, and VLAN 30 for SCADA.

The PLC and HMI are assigned to access ports in VLAN 10. The robot controller is assigned to VLAN 20. The SCADA server is assigned to VLAN 30. An uplink trunk carries VLANs 10, 20, and 30 to another switch.

The expected behavior is:

  1. The PLC and HMI can communicate at Layer 2 if their IP configuration and application requirements are correct.
  2. The robot controller remains in VLAN 20 and is isolated from VLAN 10 at Layer 2.
  3. The SCADA server cannot automatically communicate with the PLC merely because both connect to the same physical switching infrastructure.
  4. If SCADA needs to communicate with the PLC across VLANs, the network needs suitable Layer 3 routing and permitted traffic.
  5. If VLAN 10 is missing from the uplink's allowed VLAN list, PLC/HMI traffic may fail when it needs to cross that link.
  6. If the management VLAN is changed incorrectly, engineers may lose remote access to the switch even though some production traffic continues.

This example demonstrates why VLAN configuration must be treated as part of the complete network architecture rather than as an isolated switch setting.

18. Interview questions and answers

1. What is a VLAN?

A VLAN is a logical Layer 2 network that creates a separate broadcast domain within a VLAN-aware switching infrastructure.

2. What is the difference between a VLAN and a subnet?

A VLAN is a Layer 2 construct, while an IP subnet is a Layer 3 addressing construct. Industrial networks commonly map one subnet to one VLAN, but the concepts are not identical.

3. What is the difference between an access port and a trunk port?

An access port typically connects an endpoint to one data VLAN. A trunk carries traffic for multiple VLANs, normally using 802.1Q tags.

4. What is an 802.1Q tag?

It is a VLAN tag inserted into an Ethernet frame to carry VLAN identification and priority-related information.

5. What is a PVID?

The Port VLAN ID is commonly used to classify incoming untagged frames into a VLAN on a VLAN-aware switch port.

6. What is a native VLAN?

On many 802.1Q trunk implementations, the native VLAN identifies the VLAN transmitted untagged over the trunk.

7. Can two devices in different VLANs communicate directly?

Not through ordinary Layer 2 switching alone. Communication between different IP subnets generally requires Layer 3 routing and suitable security policies.

8. Does a VLAN improve security?

VLANs provide segmentation, but they do not automatically block all communication between segments. Routing policies, ACLs, firewalls, and secure management are also important.

9. Why can a VLAN work on one switch but fail across another?

The VLAN may be absent or inactive on the other switch, the trunk may not allow it, or tagging and native VLAN settings may be inconsistent.

10. Why should VLAN changes be carefully controlled on production equipment?

Incorrect configuration can interrupt PLC-to-HMI communication, robot coordination, SCADA access, engineering access, and switch management without any physical cable failure.

11. What is the relationship between VLANs and QoS?

VLANs separate traffic into Layer 2 broadcast domains. QoS controls traffic classification and handling under congestion. VLAN tagging can carry a priority value, but priority treatment depends on configuration.

12. How would you troubleshoot a PLC that becomes unreachable after a VLAN change?

Check physical link status, port VLAN membership, VLAN existence, trunk configuration, PVID/native VLAN behavior, IP settings, routing, access-control rules, and protocol-specific requirements.

19. Practical exercises

Exercise 1: Identify the correct port type

A PLC connects to port 1, and a second managed switch connects to port 24. The PLC should belong to VLAN 10, while the uplink must carry VLANs 10 and 20.

Expected configuration:

  • Port 1: access port in VLAN 10.
  • Port 24: trunk carrying VLANs 10 and 20, configured consistently at both ends.

Exercise 2: Diagnose a missing VLAN

A PLC communicates with an HMI connected to the same switch, but communication fails when the HMI is moved to a different switch.

The likely checks are:

  1. Confirm that the PLC and HMI still belong to the intended VLAN.
  2. Confirm that the VLAN exists on both switches.
  3. Verify that the inter-switch trunk carries that VLAN.
  4. Check trunk tagging and native VLAN behavior.
  5. Verify IP settings and industrial application requirements.

Exercise 3: Determine whether routing is needed

A PLC belongs to VLAN 10 with address 192.168.10.20/24. A SCADA server belongs to VLAN 30 with address 192.168.30.50/24.

These addresses belong to different IP subnets. Communication generally requires a Layer 3 routing path, suitable gateway configuration, and policies that permit the required traffic.

Exercise 4: Explain the security limitation

An engineering PC belongs to VLAN 40 and a PLC belongs to VLAN 10. Both VLANs have interfaces on the same Layer 3 switch, and unrestricted inter-VLAN routing is enabled.

The two devices may still communicate if their IP configuration and endpoint policies permit it. VLAN separation alone does not block the routed traffic.

20. Final mental model

Remember these distinctions:

  • VLAN: Which logical Layer 2 network does this Ethernet traffic belong to?
  • Access port: Which VLAN should receive the endpoint's untagged traffic?
  • Trunk port: Which VLANs can cross this infrastructure link?
  • PVID/native VLAN: How is untagged traffic classified or carried?
  • Subnet: Which IP address range does the device belong to?
  • Gateway and routing: How can traffic reach another IP subnet?
  • ACL/firewall: Which routed communications are allowed?
  • QoS: How should traffic be handled when resources are contested?
  • Redundancy: How does the network recover from a link or path failure?

The practical rule is to design VLANs around real communication dependencies, configure each port and trunk deliberately, and verify the entire application path after every change. In industrial automation, a network diagram is only useful when the running machine agrees with it.
