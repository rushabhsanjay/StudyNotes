1. Definition and purpose

Ethernet is a family of networking technologies used to connect computers, PLCs, HMIs, industrial PCs, switches, servers, remote I/O devices, and other equipment over a wired network.

In industrial automation, Ethernet enables communication between machine controllers, engineering workstations, SCADA systems, manufacturing databases, and plant-level applications.

Typical uses include:

  • PLC-to-PLC data exchange.
  • PLC-to-HMI communication.
  • PLC programming, diagnostics, and firmware maintenance.
  • SCADA data collection and supervisory control.
  • Industrial PC and server connectivity.
  • Remote I/O, motion systems, and machine vision.
  • Data exchange with MES, historians, SQL databases, and analytics platforms.
  • Integration of shop-floor equipment with Industry 4.0 applications.

Ethernet is not one specific protocol. It provides networking mechanisms at the data-link and physical layers, while IP, TCP, UDP, and industrial protocols provide additional communication functions.

2. Ethernet in the industrial communication stack

Application
    ↓
Industrial or application protocol
    OPC UA, EtherNet/IP, PROFINET, Modbus TCP, HTTP
    ↓
Transport layer
    TCP or UDP
    ↓
Network layer
    IPv4 or IPv6
    ↓
Data-link layer
    Ethernet frames, MAC addresses, VLANs
    ↓
Physical layer
    Copper twisted pair or optical fiber

This is a simplified view. Not every industrial protocol uses every layer in exactly the same way. For example, PROFINET and EtherNet/IP have different protocol architectures, even though both can use Ethernet infrastructure.

The important distinction is that Ethernet is the network foundation, not the complete meaning of the data being exchanged.

A PLC can communicate over Ethernet using a proprietary protocol, Modbus TCP, OPC UA, EtherNet/IP, or another supported protocol. Simply connecting two devices to the same Ethernet switch does not guarantee that they can exchange meaningful application data.

4. Ethernet speeds and cable categories

Common Ethernet rates include 10 Mbps, 100 Mbps, 1 Gbps, and higher rates. Industrial devices may support only one or a subset of these speeds.

Ethernet rate Common designation Typical application
10 Mbps 10BASE-T Legacy equipment
100 Mbps 100BASE-TX Many PLCs and industrial devices
1 Gbps 1000BASE-T Industrial PCs, servers, and uplinks
1 Gbps over fiber 1000BASE-SX or 1000BASE-LX Fiber uplinks and backbone connections
10 Gbps 10GBASE variants High-bandwidth backbones and servers

These designations are not interchangeable. Copper and fiber variants use different media and physical interfaces, even when they operate at the same nominal data rate.

Copper cable categories

Cable category General characteristics Practical considerations
Cat 5e Commonly supports 1 Gbps over compliant channels Often sufficient for many industrial connections
Cat 6 Improved performance characteristics relative to Cat 5e Useful for higher-performance structured cabling
Cat 6A Designed for 10 Gbps up to the specified channel length Consider for high-bandwidth installations
Industrial Ethernet cable May include industrial-grade jackets, shielding, flex ratings, or environmental protection Select for oil, vibration, temperature, and installation conditions

For conventional twisted-pair Ethernet, the standard channel length is generally up to 100 metres for supported copper Ethernet variants, subject to the applicable cabling and link specifications.

Do not select a cable solely by its category label. Connector quality, installation workmanship, bend radius, environmental rating, electromagnetic compatibility, and channel length all matter.

5. MAC addresses, IP addresses, and ports

These three concepts solve different problems.

MAC address

A MAC address is used for delivery on the local Ethernet network. Ethernet switches learn which MAC addresses are reachable through which switch ports and use that information to forward frames.

IP address

An IP address identifies a device's network-layer endpoint and helps route packets between IP networks.

For example:

  • PLC: 192.168.10.10
  • HMI: 192.168.10.20
  • Engineering PC: 192.168.10.30

These are illustrative private IPv4 addresses. Their suitability depends on the site's actual addressing plan.

TCP or UDP port

A transport-layer port identifies an application endpoint on a host. For example, a particular application may listen on a TCP port to receive requests.

A port number is not a physical Ethernet connector and is not the same thing as a PLC I/O address.

A simplified example:

Ethernet frame
    ↓
MAC address: local network delivery
    ↓
IP packet
    ↓
IP address: network destination
    ↓
TCP or UDP segment
    ↓
Port number: application endpoint
    ↓
Industrial application protocol

6. IP addressing and subnet masks

Devices communicating on an IP network need compatible addressing and routing configuration.

An IPv4 address contains 32 bits, commonly written as four decimal octets. A subnet mask or prefix identifies the network portion and the host portion of the address.

Example:

  • PLC address: 192.168.10.10
  • HMI address: 192.168.10.20
  • Subnet mask: 255.255.255.0, equivalent to /24

Both devices are in the same IPv4 subnet in this example. They can normally communicate directly over the local network if the physical link and relevant firewall or device settings permit it.

A different example:

  • PLC address: 192.168.10.10/24
  • HMI address: 192.168.20.20/24

These addresses belong to different subnets. Communication between them generally requires appropriate routing and compatible gateway configuration.

Default gateway

A default gateway is used when a device needs to send IP traffic to a destination outside its local subnet. A device communicating only with equipment on its own subnet may not need a default gateway for that local communication.

DHCP versus static addressing

  • DHCP: A server assigns network configuration dynamically.
  • Static addressing: An administrator configures the address manually or reserves it through an approved management process.

Industrial control devices often use planned static addresses because predictable addressing simplifies machine configuration, diagnostics, and maintenance. DHCP can still be appropriate in managed industrial architectures, depending on the device and design.

Never change a PLC or drive IP address casually on a live line. Duplicate addresses, wrong subnets, and accidental loss of engineering connectivity can disrupt production.

7. Ethernet switches and network forwarding

An Ethernet switch connects multiple devices within a local network. It learns source MAC addresses from incoming frames and builds a forwarding table that associates addresses with switch ports.

When a frame arrives, the switch uses its forwarding information to decide where to send it. Unknown unicast traffic may be flooded within the applicable VLAN, and broadcast traffic is forwarded within that VLAN according to normal switching rules.

Unmanaged versus managed switches

Feature Unmanaged switch Managed switch
Basic Ethernet forwarding Yes Yes
Configuration interface Usually none Web, CLI, software, or management protocol
VLAN configuration Generally unavailable Commonly supported
Port diagnostics Limited More detailed
Port mirroring Usually unavailable Often supported
Redundancy features Model-dependent and usually limited May support industrial ring or other redundancy protocols
SNMP monitoring Usually unavailable Often supported
Typical use Simple, small networks Industrial networks requiring monitoring and control

Managed switches are especially useful for maintenance because they can expose link status, speed, duplex, error counters, port utilization, VLAN configuration, and redundancy state.

Store-and-forward switching

A common switch architecture receives an Ethernet frame, checks it for errors, and forwards it through the appropriate port. Switching behavior and latency depend on the hardware and forwarding architecture.

A switch does not automatically make every connected device part of the same IP subnet. VLANs, IP addressing, and routing still determine logical connectivity.

Full-duplex and half-duplex

Modern switched Ethernet links typically operate in full-duplex mode, allowing simultaneous transmission and reception. Half-duplex operation is associated with older shared-media environments and legacy links.

Speed and duplex mismatches can produce poor performance, collisions in applicable legacy environments, or errors. Most modern links negotiate their settings automatically, but industrial equipment may require specific settings or have limited negotiation support.

Do not force speed and duplex settings without checking both ends and the device documentation.

8. Ethernet topology in industrial automation

Star topology

A common industrial arrangement connects each device to a central switch.

                  [Engineering PC]
                         |
[HMI] ─────────── [Managed Switch] ─────────── [PLC]
                         |
                      [SCADA PC]
                         |
                       [VFD]

Advantages include straightforward expansion, easier port-level fault isolation, and the ability to disconnect one link without necessarily disrupting unrelated links.

The central switch is a potential single point of failure unless redundancy is designed into the network.

Line or daisy-chain topology

Some industrial devices include two Ethernet ports and support a line topology. Traffic may pass through intermediate devices, depending on their internal switching design.

Advantages include reduced cabling and fewer external switches. Limitations include potential disruption if an intermediate device or link fails, unless a supported redundancy mechanism is used.

Two Ethernet ports do not automatically imply a supported ring or redundant network. Check the device's architecture and manual.

Ring topology

A ring connects network devices in a loop. A supported redundancy mechanism prevents a normal loop from causing persistent Ethernet forwarding loops and can restore connectivity after certain failures.

Examples include vendor-specific industrial ring protocols and standards-based mechanisms such as the Media Redundancy Protocol (MRP) in supported PROFINET environments.

Never create a physical Ethernet ring without ensuring that a compatible loop-prevention or redundancy protocol is configured and functioning. A raw switching loop can cause a broadcast storm and widespread communication failure.

9. Ethernet frames, MTU, and communication errors

An Ethernet frame carries a payload along with addressing and error-detection information. Standard Ethernet frames include destination and source MAC addresses, a type/length field, payload data, and a frame check sequence.

The maximum transmission unit (MTU) for conventional Ethernet IP traffic is commonly 1500 bytes of IP packet data. Larger jumbo frames may be supported in some networks, but they require compatible configuration across the relevant path.

A mismatched MTU can cause fragmentation, dropped packets, or communication problems depending on the protocol and network path.

Frame check sequence

Ethernet uses a frame check sequence based on a cyclic redundancy check to detect corruption of a received frame. A frame with a failed check is normally discarded by the receiving Ethernet interface.

Switches and network interfaces may expose error counters that help identify physical-layer or link-quality problems.

Common Ethernet link symptoms

  • CRC or frame errors can indicate cable damage, interference, connector problems, or faulty hardware.
  • Link flapping can indicate loose connections, power problems, damaged cables, or a failing port.
  • High utilization can produce congestion and delay.
  • Packet loss can result from congestion, physical faults, filtering, or endpoint limitations.
  • Duplicate IP addresses can cause intermittent or misleading connectivity symptoms.

One counter rarely identifies the root cause by itself. Compare counters over time and correlate them with machine events and physical inspection.

10. Industrial Ethernet protocols

Industrial Ethernet uses standard Ethernet networking infrastructure with protocols designed for particular automation requirements.

Protocol General purpose Common context
PROFINET Industrial automation communication, including real-time functions Siemens and compatible automation systems
EtherNet/IP Industrial communication using the Common Industrial Protocol (CIP) Rockwell Automation and compatible devices
Modbus TCP Client/server industrial data exchange over TCP/IP PLCs, meters, VFDs, gateways
OPC UA Structured information exchange with security and interoperability features SCADA, MES, historians, industrial applications
EtherCAT High-performance real-time Ethernet-based control Motion control and distributed I/O
HTTP/HTTPS Web-based interfaces and application integration Device configuration pages, APIs, dashboards

These protocols are not equivalent. They differ in data models, communication patterns, timing behavior, configuration tools, and supported services.

PROFINET

PROFINET is commonly used for PLC communication with distributed I/O, drives, and other automation devices. It supports different communication mechanisms, including real-time communication for appropriate control applications.

Engineering tools may require device descriptions, such as GSDML files, to configure compatible field devices.

EtherNet/IP

EtherNet/IP uses CIP services over standard Ethernet and IP networking. It supports industrial communication such as I/O data exchange, explicit messaging, and device configuration.

Rockwell Automation systems commonly use EtherNet/IP for controller-to-device communication, with configuration and behavior dependent on the controller, module, and target device.

Modbus TCP

Modbus TCP carries Modbus application messages over TCP/IP. It is often used to read and write registers in PLCs, meters, VFDs, and gateways.

The device's IP address identifies the network endpoint. Modbus addressing and register mapping identify the data within the application.

OPC UA

OPC UA provides a structured way to exchange industrial information, including values, data types, status, timestamps, and metadata. It can support secure client/server communication and other communication models depending on the implementation.

OPC UA is useful for connecting automation systems to supervisory applications, historians, and enterprise systems, but its security and permissions must be configured properly.

Important distinction

A device supporting Ethernet does not necessarily support PROFINET, EtherNet/IP, Modbus TCP, or OPC UA. Verify protocol support explicitly in the device manual.

11. Real-time behavior and deterministic communication

Ordinary Ethernet connectivity does not guarantee deterministic timing. Application latency and jitter can vary due to endpoint processing, network congestion, switching behavior, protocol design, and operating-system scheduling.

For control applications, distinguish between:

  • Ordinary TCP/IP communication: Often appropriate for configuration, monitoring, reports, and non-time-critical data exchange.
  • Industrial real-time communication: Uses protocol-specific mechanisms to meet timing requirements.
  • Motion-control communication: May require tightly synchronized updates, bounded latency, and specialized hardware or protocol features.

A dashboard updating a motor temperature every second has very different timing requirements from a coordinated motion system updating control data at millisecond or sub-millisecond intervals.

When selecting a network, evaluate the actual control requirement rather than assuming that a higher Ethernet speed automatically makes the system deterministic.

12. VLANs, routing, and industrial network segmentation

A VLAN logically separates Ethernet traffic into distinct Layer 2 broadcast domains. Devices in different VLANs generally need routing to communicate with each other.

Industrial networks may separate:

  • Machine control devices.
  • Engineering workstations.
  • SCADA and historian servers.
  • Plant information systems.
  • Corporate IT systems.
  • Remote access infrastructure.

A simplified architecture:

Machine VLAN
    PLCs, HMIs, drives, remote I/O
          ↓
Managed industrial switch
          ↓
Controlled Layer 3 boundary or firewall
          ↓
SCADA / Historian VLAN
          ↓
Approved plant information services

This is a logical example, not a universal plant architecture. The correct arrangement depends on operational requirements, safety, availability, security policies, and the organization's network design.

VLANs are not a complete security boundary

VLANs separate Layer 2 traffic, but they do not replace firewall rules, access control, secure configuration, or monitoring.

Security measures may include:

  • Restricting which systems can communicate with PLCs.
  • Separating engineering access from routine monitoring.
  • Limiting unnecessary services and open ports.
  • Using approved remote-access mechanisms.
  • Protecting switch and device management interfaces.
  • Maintaining configuration backups and change records.
  • Monitoring unusual communication patterns.
  • Applying controlled patching and firmware-management procedures.

Avoid connecting a production PLC network directly to an untrusted network simply because both use Ethernet.

13. Ethernet troubleshooting in industrial maintenance

Ethernet faults should be diagnosed by separating physical connectivity, IP networking, transport communication, protocol configuration, and application behavior.

Symptom Possible causes Diagnostic action
No link indication Cable disconnected, damaged cable, failed port, incompatible physical interface Inspect link LEDs, connectors, cable, and port specifications
Link is up but device is unreachable Wrong IP address, subnet mismatch, duplicate IP, firewall rules Verify IP configuration and test connectivity
Ping works but PLC data is unavailable Wrong protocol, incorrect port, application stopped, permissions or firewall restrictions Test the required service and inspect device diagnostics
Intermittent connection Loose connector, cable damage, power instability, duplicate IP Inspect cabling, power, address conflicts, and link logs
Slow communication Congestion, excessive polling, endpoint overload, retransmissions Check switch utilization, packet loss, polling rate, and endpoint performance
CRC or frame errors increase Cable or connector defects, interference, physical-layer problems Check switch counters, cable condition, routing, and connectors
One device fails but others work Device-specific settings, faulty NIC, incorrect VLAN, device power issue Test the affected port and verify the endpoint configuration
Entire machine network fails Switch power loss, failed uplink, loop, configuration error Check switch power, topology, redundancy state, and recent changes
PLC discovery fails Wrong subnet, blocked discovery traffic, unsupported discovery method Verify engineering-PC interface, VLAN, and discovery requirements
Communication fails after replacement Incorrect IP, device name, firmware, port settings, or saved configuration Compare the replacement against the approved device configuration
Network works locally but not across subnets Missing route, incorrect gateway, ACL or firewall rule Check routing and permitted traffic at the network boundary
High latency during production Traffic bursts, excessive broadcasts, overloaded endpoints, faulty links Inspect utilization, error counters, traffic patterns, and application load

A systematic diagnostic sequence

  1. Check the physical link. Confirm device power, link LEDs, cable seating, and switch-port status.
  2. Check the Ethernet interface. Verify the negotiated speed, duplex, error counters, and port configuration.
  3. Check IP configuration. Verify IP address, subnet mask, gateway, and duplicate-address risks.
  4. Test local reachability. Use approved tools such as ping, where ICMP is permitted.
  5. Test the required application service. A successful ping does not prove that a PLC protocol or application service is working.
  6. Check the protocol. Verify device identity, protocol support, addressing, connection configuration, and required ports.
  7. Check network infrastructure. Review VLANs, routing, firewall rules, switch logs, and redundancy status.
  8. Check application data. Confirm tag mapping, register addresses, data types, update rates, and timestamps.
  9. Correlate events. Compare communication errors with VFD operation, machine starts, switch reboots, or recent engineering changes.
  10. Document the root cause. Record the fault, evidence, corrective action, and verification result.

Useful Windows commands

Run these from an authorized engineering workstation.

Command Purpose
ipconfig /all Displays interface addresses, subnet masks, gateways, and other IP configuration
ping 192.168.10.10 Tests IP reachability if ICMP is allowed
arp -a Displays the local ARP cache for IPv4 neighbors
tracert 192.168.20.20 Traces the IP route toward a destination
route print Displays the workstation's IP routing table
nslookup hostname Tests DNS resolution for a hostname
netstat -ano Displays network connections and listening ports on supported Windows versions

Replace example addresses with approved addresses from the actual network plan.

Do not interpret a failed ping as conclusive proof that a device is offline. Some devices block ICMP while continuing to provide their industrial communication services.

14. Packet capture and network analysis

When ordinary diagnostics are insufficient, packet capture can reveal what is happening on the network.

Tools such as Wireshark can help inspect:

  • Source and destination IP addresses.
  • TCP connection establishment and resets.
  • Retransmissions and timeouts.
  • Modbus TCP requests and responses.
  • Broadcast and multicast traffic.
  • Unexpected connection attempts.
  • Timing differences between requests and responses.

For a switched network, a computer connected to an arbitrary switch port normally cannot see all traffic between other devices. Port mirroring, a network TAP, or a suitable capture point may be required.

Packet captures can contain operationally sensitive information. Follow plant authorization and data-handling procedures before collecting or sharing them.

Example: Modbus TCP failure

Suppose a PLC communicates with a power meter using Modbus TCP.

  1. Confirm that the meter is powered and its Ethernet link is active.
  2. Verify the configured IP address and subnet.
  3. Confirm that the PLC is targeting the correct device and TCP port, commonly port 502 for Modbus TCP.
  4. Check whether TCP connections are established and remain stable.
  5. Inspect the Modbus request and response, including function code and exception responses.
  6. Verify register mapping, data type, scaling, and byte or word order where applicable.
  7. Check whether the PLC program handles timeouts and invalid values correctly.

If TCP establishes successfully but the meter returns a Modbus exception, the fault may be in the application request rather than the Ethernet connection.

15. Commissioning checklist

Hardware and cabling

  • Confirm the Ethernet interface type and supported speed.
  • Verify the cable category, length, environmental rating, and connector type.
  • Check routing and separation from electrical noise sources.
  • Confirm that copper and fiber interfaces match the connected equipment.
  • Verify link status and negotiated speed and duplex.
  • Label both ends of each cable and identify the connected switch ports.

Network configuration

  • Record MAC addresses and approved IP addresses.
  • Verify subnet masks, gateways, and VLAN assignments.
  • Check for duplicate IP addresses.
  • Confirm that required routes and firewall rules are in place.
  • Verify that the intended industrial protocol is supported.
  • Confirm that device names, firmware, and configuration match the approved design where relevant.

Functional verification

  • Test connectivity between intended endpoints.
  • Verify actual protocol exchanges rather than relying only on ping.
  • Confirm that PLC tags, registers, or I/O data are correct.
  • Check update rates, timeouts, and data-quality indicators.
  • Verify behavior during communication loss and recovery.
  • Test redundancy only using an approved procedure.
  • Save switch, PLC, HMI, and network-device configurations.
  • Update network drawings, IP lists, and maintenance records.

16. Preventive maintenance and configuration management

Ethernet maintenance should include more than checking whether the link LED is green.

  • Review switch logs for link flapping, port errors, and unexpected restarts.
  • Monitor CRC errors, dropped frames, utilization, and abnormal traffic where supported.
  • Inspect cable jackets, connectors, panel penetrations, and strain relief.
  • Verify cabinet temperature, ventilation, and switch power-supply condition.
  • Maintain backups of managed-switch configurations and network-device settings.
  • Keep an approved IP address register and port-to-device mapping.
  • Document VLANs, uplinks, redundancy configuration, and firewall rules.
  • Record firmware versions and approved replacement models.
  • Investigate recurring communication alarms rather than simply increasing timeout values.
  • Make configuration changes through controlled maintenance procedures.

A useful machine-level network record should identify the device, port, MAC address, IP address, subnet, protocol, firmware, cable route, and approved configuration backup.

17. Industrial Ethernet and Industry 4.0 integration

Ethernet can provide the communication foundation for collecting machine data and delivering it to higher-level systems.

A typical architecture may look like this:

Shop-floor sensors and actuators
          ↓
PLC / CNC / Robot controller
          ↓
Industrial Ethernet network
          ↓
Industrial PC / Edge gateway
          ↓
OPC UA / MQTT / Database connector
          ↓
Historian / SQL database / SCADA
          ↓
Dashboards / Analytics / MES

This is an example architecture. The actual interfaces depend on the equipment and software.

For example, an edge computer may read approved PLC tags, normalize timestamps and data types, store selected values in a database, and expose production information to a dashboard.

Important design considerations include:

  • Read-only access where write access is not required.
  • Clear separation between control logic and reporting applications.
  • Buffering data during temporary network or server failures.
  • Data-quality flags and timestamps.
  • Controlled polling rates to avoid overloading PLCs.
  • Authentication, encryption, and authorization where supported.
  • Recovery behavior after communications are restored.
  • Clear ownership of the interface and its configuration.

Connecting a PLC to a database does not automatically make the architecture reliable. The data path needs error handling, security controls, monitoring, and a defined response to loss of connectivity.

18. Common Ethernet misconceptions

Misconception 1: If two devices have Ethernet ports, they can communicate.

They also need compatible protocols, addressing, configuration, and permitted network paths.

Misconception 2: If ping works, the PLC application is working.

Ping tests IP reachability using ICMP. It does not validate the PLC protocol, application service, or data mapping.

Misconception 3: A managed switch is automatically secure.

Security depends on configuration, access controls, segmentation, firmware, and operational practices.

Misconception 4: Higher bandwidth always means faster control.

Control performance also depends on protocol timing, endpoint processing, congestion, scheduling, and network architecture.

Misconception 5: VLANs completely isolate devices.

VLANs separate Layer 2 domains, but routing and security policy determine whether traffic can cross between them.

Misconception 6: All industrial Ethernet protocols are interchangeable.

They may share Ethernet hardware while differing significantly in application behavior, configuration, timing, and device compatibility.

Misconception 7: Replacing a cable is always the solution to intermittent communication.

Intermittent faults can also arise from duplicate IP addresses, switch configuration, grounding, power instability, firmware, or application timeouts.

19. Interview questions and answers

Q1. What is Ethernet?

Ethernet is a family of wired networking technologies used to transmit frames between devices on a local network.

Q2. What is the difference between a MAC address and an IP address?

A MAC address supports delivery on the local Ethernet network, while an IP address supports network-layer addressing and routing.

Q3. What is the difference between a switch and a router?

A switch forwards traffic within Layer 2 networks using MAC addresses. A router forwards IP traffic between networks using IP routing information.

Q4. What is the difference between TCP and UDP?

TCP provides a connection-oriented byte stream with delivery and ordering mechanisms. UDP sends independent datagrams without TCP's built-in delivery and ordering guarantees.

Q5. What is a subnet mask?

A subnet mask identifies the network portion of an IPv4 address and helps determine whether a destination is local or requires routing.

Q6. What is a VLAN?

A VLAN logically separates a switched Ethernet network into distinct Layer 2 broadcast domains.

Q7. What is the difference between PROFINET and EtherNet/IP?

Both are industrial networking technologies that use Ethernet infrastructure, but they have different protocol architectures, configuration models, and communication mechanisms.

Q8. Why might a PLC respond to ping but fail to exchange process data?

The industrial protocol may be misconfigured, blocked, unsupported, or experiencing an application-level error even though IP reachability exists.

Q9. What causes CRC errors on an Ethernet switch port?

Possible causes include damaged cabling, poor terminations, electromagnetic interference, or faulty interface hardware.

Q10. Why use fiber instead of copper Ethernet?

Fiber can support longer distances for the relevant optical standard and provides electrical isolation between endpoints, making it useful across buildings or electrically noisy areas.

Q11. What is the purpose of a managed switch in a plant?

It enables network configuration, monitoring, diagnostics, segmentation, and supported redundancy features.

Q12. How should a technician approach a complete machine-network failure?

Check switch power and link status, inspect uplinks and recent changes, review port and redundancy diagnostics, then verify IP connectivity and application communication.

Q13. What is deterministic communication?

Deterministic communication provides sufficiently predictable timing for a defined application requirement. Ordinary Ethernet connectivity alone does not guarantee deterministic behavior.

Q14. Why should PLC network configuration be backed up?

A backup helps restore addressing, VLANs, redundancy, access settings, and other configuration after device replacement or a configuration error.

20. Final mental model

Ethernet in industrial automation is best understood as a system of interconnected layers:

  1. Physical connectivity: Copper cable, fiber, connectors, and transceivers.
  2. Local network delivery: Ethernet frames, MAC addresses, and switches.
  3. IP networking: IP addresses, subnet masks, gateways, and routing.
  4. Transport and application communication: TCP, UDP, and industrial protocols.
  5. Control and information behavior: PLC logic, real-time requirements, SCADA data, diagnostics, and security.

When troubleshooting, identify which layer is failing before replacing hardware or changing configuration. A healthy physical link, a reachable IP address, a working industrial protocol, and correct application data are four separate things that must all be verified.
