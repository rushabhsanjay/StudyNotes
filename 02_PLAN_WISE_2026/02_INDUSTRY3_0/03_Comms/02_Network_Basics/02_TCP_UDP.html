1. Purpose and scope

TCP and UDP are two transport-layer protocols used to transfer data between applications over IP networks. They determine how application data is packaged, addressed to an application endpoint, and delivered or handled when network problems occur.

In industrial automation, understanding TCP and UDP helps diagnose PLC communication failures, SCADA connection timeouts, HMI communication errors, OPC UA connectivity, EtherNet/IP traffic, and problems involving firewalls or network configuration.

The key distinction is not simply reliable versus fast. TCP provides built-in mechanisms for reliable, ordered delivery of a byte stream. UDP provides a lightweight datagram service without built-in delivery, ordering, or retransmission guarantees. The better choice depends on the application's requirements.

2. Position in the network architecture

TCP and UDP operate at the transport layer of the TCP/IP networking model. They use IP to move packets between network endpoints.

Application layer
  PLC software, SCADA, HMI, OPC UA, Modbus TCP
                    ↓
Transport layer
  TCP or UDP
                    ↓
Internet layer
  IPv4 or IPv6
                    ↓
Network access layer
  Ethernet, Wi-Fi, and other link technologies
                    ↓
Physical medium
  Copper, fiber, radio

The OSI model calls this Layer 4, the transport layer.

Protocol or technology Main responsibility
Application protocol Defines message meaning and application behavior
TCP Reliable, ordered byte-stream transport
UDP Connectionless datagram transport
IP Addressing and routing between IP networks
Ethernet Local-link framing and MAC addressing
Physical medium Carries electrical, optical, or radio signals

Important: TCP and UDP do not replace IP or Ethernet. They operate above IP, which operates above the network's link technology.

3. TCP: Transmission Control Protocol

TCP is a connection-oriented transport protocol. Before normal data exchange, the endpoints establish a logical connection. TCP then uses sequence numbers, acknowledgements, retransmissions, and other mechanisms to provide a reliable, ordered byte stream.

3.1 Main characteristics

  • Connection-oriented: A connection is established before normal data transfer.
  • Reliable delivery: Lost data can be retransmitted.
  • Ordered delivery: Data is presented to the receiving application in the correct sequence.
  • Error detection: A checksum helps detect corruption in the TCP segment.
  • Flow control: The receiver can limit how much unacknowledged data the sender transmits.
  • Congestion control: The sender adjusts its transmission behavior in response to signs of network congestion.
  • Full-duplex communication: Both endpoints can send and receive data during the same connection.
  • Byte-stream service: TCP delivers a continuous stream of bytes, not a sequence of application messages.

TCP's reliability applies to delivery between TCP endpoints. It does not guarantee that an application has correctly processed a command, that a PLC has completed a movement, or that a physical machine is safe.

3.2 TCP connection establishment: three-way handshake

A typical TCP connection begins with a three-way handshake.

Client                                      Server
  |                                            |
  | -------- SYN ----------------------------> |
  | <------- SYN + ACK ----------------------- |
  | -------- ACK ----------------------------> |
  |                                            |
  |       Connection established               |
  |                                            |
  | <====== Application data both ways ======> |
  1. SYN: The client requests a TCP connection and proposes an initial sequence number.
  2. SYN-ACK: The server acknowledges the request and supplies its own initial sequence number.
  3. ACK: The client acknowledges the server's response.

After the handshake, the endpoints can exchange application data.

A successful handshake confirms that the endpoints could establish a TCP connection at that time. It does not prove that the application protocol is configured correctly or that the requested machine operation will succeed.

3.3 TCP sequence numbers and acknowledgements

TCP numbers the bytes in its data stream. The receiver acknowledges received data, and the sender uses those acknowledgements to determine which bytes have been received.

For example:

Sender                                  Receiver
  | -------- Data bytes 100-199 -------> |
  | <------- ACK 200 ------------------- |
  |                                      |
  | -------- Data bytes 200-299 -------> |
  | <------- ACK 300 ------------------- |

In this simplified example, ACK 200 means the receiver expects byte 200 next. It cumulatively acknowledges the bytes before that point.

If data is lost, TCP may retransmit it. The exact retransmission behavior depends on acknowledgement patterns, retransmission timers, and other TCP mechanisms.

3.4 Retransmission and head-of-line blocking

Suppose a TCP stream is divided across multiple segments, and one segment is lost.

  • The receiver may receive later segments, but it cannot present missing earlier bytes as though the stream were complete.
  • TCP may retransmit the missing data.
  • The application can experience additional delay while the missing bytes are recovered.

This is known as head-of-line blocking at the TCP stream level.

For a SCADA configuration or PLC programming session, reliable ordered delivery is usually valuable. For time-sensitive data where a newer measurement makes an older one irrelevant, waiting for retransmission may be undesirable.

TCP does not automatically make every application slow. On a healthy network, it can deliver data efficiently. The extra delay becomes especially relevant when there is loss, congestion, a timeout, or a stalled endpoint.

3.5 Flow control versus congestion control

These mechanisms solve different problems.

Mechanism Protects against Typical operation
Flow control Overwhelming the receiver Receiver advertises an available receive window
Congestion control Overloading the network Sender adjusts its sending rate or amount of outstanding data

For example, a slow industrial PC may not process incoming data quickly enough. TCP flow control helps prevent its receive buffer from being overwhelmed. If the network itself becomes congested, TCP congestion control helps regulate the sender's traffic.

3.6 TCP connection termination

TCP commonly closes a connection through an exchange of FIN and ACK segments. Each direction of the connection can be closed independently, so a normal shutdown may involve more than two segments.

A RST, or reset, indicates an abrupt termination or rejection of a connection. It can occur when a service is not accepting the connection, an endpoint has no matching connection state, or an application or network component actively resets the session.

Do not assume every RST means the same fault. Capture the traffic and inspect which endpoint sent it and what happened immediately beforehand.

4. UDP: User Datagram Protocol

UDP is a connectionless transport protocol. It sends independent datagrams without establishing a TCP-style connection or providing built-in acknowledgements and retransmissions.

4.1 Main characteristics

  • Connectionless: No TCP-style handshake is required before sending a datagram.
  • No built-in delivery guarantee: A datagram may be lost.
  • No built-in ordering guarantee: Datagrams may arrive out of order.
  • No built-in retransmission: The application must implement recovery if required.
  • Message-oriented: Each UDP datagram preserves its own message boundary.
  • Low protocol overhead: The UDP header is only 8 bytes.
  • Supports unicast, broadcast, and multicast where the network and application support them: UDP itself does not guarantee that a broadcast or multicast message reaches every intended receiver.

UDP has fewer transport mechanisms than TCP, but that does not guarantee lower latency in every situation. Actual performance depends on the network, traffic load, packet size, application implementation, and required recovery behavior.

4.2 UDP operation

Sender                                  Receiver
  | -------- Datagram A --------------> |
  | -------- Datagram B --------------> |
  | -------- Datagram C ----X           |
  |                                      |
  |    No built-in ACK or retry          |

In this example, Datagram C is lost. UDP itself does not resend it. The application may never notice the loss, or it may detect the gap and request or perform recovery.

UDP is useful when the application prefers timely delivery of available data over waiting for every earlier message. That trade-off must be deliberate.

4.3 Where UDP reliability comes from

UDP applications can implement their own reliability mechanisms, including:

  • Sequence numbers to detect missing or reordered messages.
  • Application acknowledgements.
  • Retry timers and retransmission requests.
  • Duplicate detection.
  • Checksums or application-level integrity checks.
  • Timeouts and stale-data rejection.

For example, an application that transmits a sensor value every 10 ms might prefer to discard an old lost measurement and use the next one. An application sending a critical configuration change may instead require explicit confirmation and recovery.

UDP's minimal transport behavior does not prevent a protocol built on top of UDP from implementing reliability.

5. TCP versus UDP

Feature TCP UDP
Connection setup Three-way handshake normally used No transport handshake
Data model Ordered byte stream Individual datagrams
Delivery guarantee Retransmission and acknowledgements No built-in guarantee
Ordering Preserves stream order No built-in ordering
Duplicate handling TCP manages duplicate segments for stream delivery Application may need duplicate handling
Flow control Built in Not built in
Congestion control Built in Not built in at the UDP layer
Header size Minimum 20 bytes, excluding options 8 bytes
Broadcast and multicast Not provided as TCP connection delivery modes Supported through IP/network facilities
Typical use Sessions, commands, configuration, file transfer Time-sensitive updates, discovery, streaming, selected cyclic traffic
Main trade-off Recovery and ordering can add delay Application must handle loss and ordering if needed

TCP is not automatically the right choice whenever data matters, and UDP is not automatically the right choice whenever speed matters. The application protocol and its failure-handling design determine whether the transport is suitable.

6. TCP and UDP headers

Both protocols add a transport header to application data. IP then adds its own header, and the link layer adds framing appropriate to the network technology.

6.1 TCP header fields

The TCP header is at least 20 bytes long, excluding optional fields.

Field Purpose
Source port Identifies the sending application endpoint
Destination port Identifies the receiving application endpoint
Sequence number Identifies the position of data bytes in the stream
Acknowledgement number Indicates the next byte expected from the peer
Data offset Indicates the TCP header length
Control flags Include SYN, ACK, FIN, RST, PSH, and other flags
Window size Advertises the receiver's available TCP receive window
Checksum Detects corruption in the TCP segment
Urgent pointer Supports the TCP urgent-data mechanism
Options May negotiate capabilities such as maximum segment size and window scaling
Payload Application data carried by the segment

6.2 UDP header fields

The UDP header is 8 bytes long.

Field Purpose
Source port Identifies the sending endpoint; it can be zero when not used
Destination port Identifies the receiving application endpoint
Length Specifies the length of the UDP header and payload
Checksum Provides error detection for the UDP datagram, with IPv4 and IPv6 differences

UDP has no sequence number, acknowledgement number, receive window, or transport-level retransmission timer.

6.3 Encapsulation

Consider a PLC sending an application message to a SCADA computer.

Ethernet frame
└── IP packet
    └── TCP segment or UDP datagram
        └── Application data

Each layer adds information required by that layer. At the receiving endpoint, the headers are interpreted and removed as the data moves upward through the protocol stack.

A packet capture may show an Ethernet frame containing an IP packet, which contains a TCP segment, which contains an application protocol message.

Terminology matters: TCP technically carries a byte stream in segments, while UDP carries datagrams. Engineers often casually call all network traffic "packets," but distinguishing these terms helps when troubleshooting captures.

7. Ports, sockets, and client-server communication

An IP address identifies a network interface or endpoint at the IP layer. A transport port identifies an application endpoint within that host.

For example:

PLC IP:       192.168.10.20
PLC port:     502

SCADA IP:     192.168.10.50
SCADA port:   51524

A SCADA client could initiate a TCP connection from its local port 51524 to a PLC service listening on TCP port 502.

The combination of transport protocol, IP addresses, and ports identifies the communication endpoints. A TCP connection is commonly identified by its source IP, source port, destination IP, and destination port, together with the transport protocol.

A socket is an operating-system networking endpoint used by an application. A listening TCP socket waits for incoming connections. A UDP socket can receive datagrams addressed to its local endpoint without maintaining a TCP-style connection.

7.1 Common port examples

Application or service Common transport and port Practical note
Modbus TCP TCP 502 Common PLC and SCADA communication
DNS UDP 53 and TCP 53 TCP is used in cases including some large responses and zone transfers
DHCP for IPv4 UDP 67 and 68 Used for address configuration
NTP UDP 123 Used for time synchronization
HTTPS TCP 443 traditionally; QUIC commonly uses UDP 443 The actual transport depends on the protocol implementation
OPC UA Client/Server Commonly TCP 4840 The configured endpoint may use another port
EtherNet/IP explicit messaging Commonly TCP 44818 Used for connection establishment and explicit message exchange
EtherNet/IP implicit I/O Commonly UDP 2222 Used for cyclic I/O traffic in common implementations
SNMP Commonly UDP 161 and 162 Monitoring requests and notifications; configurations can differ

Ports are conventions, not proof of application identity. A service can use a configured non-default port, and traffic on a familiar port may not actually be the expected application.

EtherNet/IP is an especially useful industrial example: the same technology commonly uses TCP for explicit messaging and UDP for implicit I/O. Therefore, saying "EtherNet/IP uses TCP" without considering the traffic type is incomplete.

8. Practical use in industrial automation

8.1 PLC programming and configuration

Engineering software commonly establishes TCP connections to communicate with controllers or supporting services.

TCP's ordered, reliable stream is useful when transferring program data, configuration, diagnostics, or other information that must arrive intact and in sequence.

Typical failure symptoms include:

  • Connection attempts timing out.
  • The engineering tool reporting that the controller is unreachable.
  • A connection being reset after it was established.
  • Data exchange stopping because the endpoint or application becomes unavailable.

Do not immediately blame the PLC. The cause may be a firewall rule, wrong IP address, duplicate address, disabled service, route problem, or configuration mismatch.

8.2 SCADA and HMI communication

A SCADA application may use TCP to communicate with a PLC using Modbus TCP or another client-server protocol.

The connection may work at the network level but fail at the application level. For example:

  • The TCP connection succeeds, but the PLC rejects a request.
  • The requested register address is invalid.
  • The data type or byte order is configured incorrectly.
  • A request timeout is too short for the application.
  • The connection is established, but the application stops polling.

A successful TCP connection only proves that the TCP endpoint accepted a connection. It does not prove that register mapping, PLC logic, scaling, or application semantics are correct.

8.3 Real-time and cyclic I/O

Some industrial protocols use UDP for cyclic I/O because the application needs frequent, time-sensitive updates. EtherNet/IP implicit I/O is a common example.

If a new I/O update arrives after the application has already moved on to a newer update, retransmitting the old update may not be useful. The application can instead use the next scheduled update, depending on the protocol's design.

However, UDP alone does not provide determinism. Predictable industrial communication depends on factors such as:

  • Network design and traffic load.
  • Update interval and timeout configuration.
  • Switch performance and queueing.
  • Multicast handling and filtering, where applicable.
  • Application scheduling and device processing time.
  • Protocol-specific sequence checking, connection supervision, and fault reactions.

Do not replace a validated industrial control protocol with arbitrary UDP messaging just because it has a smaller header. The protocol's timing and failure behavior are part of the control-system design.

9. Network performance concepts

9.1 Latency

Latency is the time required for data to travel from one endpoint to another or, for a round-trip measurement, to go to the destination and return.

High latency can be caused by propagation delay, congestion, queueing, processing, retransmission, or application delays.

9.2 Throughput

Throughput is the rate at which useful data is transferred.

A protocol with lower header overhead does not necessarily achieve higher application throughput. Link speed, packet size, loss, acknowledgement traffic, application behavior, and congestion all affect performance.

9.3 Packet loss and jitter

  • Packet loss: Data packets or datagrams fail to reach the intended endpoint.
  • Jitter: Variation in packet delay or arrival timing.
  • Timeout: The application or protocol does not receive an expected event within its configured time.
  • Retransmission: TCP resends data when its recovery mechanisms determine that recovery is necessary.

TCP may recover lost data but introduce delay. UDP may avoid transport-level retransmission delays, but the application may receive incomplete or outdated information.

9.4 A useful diagnostic distinction

A network can have low packet loss but still suffer from high application latency. Likewise, a ping test can succeed while an application is unable to connect.

Diagnose the specific layer and failure mode instead of treating every communication problem as a generic "network issue."

10. Troubleshooting TCP connections

Use this sequence to isolate a TCP problem.

10.1 Step 1: Check basic IP connectivity

On a Windows computer:

ping 192.168.10.20

Replace the example address with the authorized target device's IP address.

A successful ping shows that an ICMP echo request received a reply. It does not prove that the required TCP port is open.

A failed ping does not necessarily prove the device is offline. ICMP may be blocked while the application service remains available.

10.2 Step 2: Test the specific TCP port

For a Modbus TCP service on a known PLC address:

Test-NetConnection 192.168.10.20 -Port 502

Check the TcpTestSucceeded field.

  • True indicates that the TCP connection test succeeded.
  • False means the test could not establish the connection. Possible causes include a closed port, firewall filtering, routing problems, an unavailable device, or other connection failures.

This command tests TCP connectivity. It does not validate Modbus requests, register addresses, or the correctness of PLC data.

10.3 Step 3: Check local TCP connections

netstat -ano

Useful columns include:

  • Local address and port.
  • Foreign address and port.
  • Connection state.
  • Process ID (PID).

Common TCP states include:

State Meaning
LISTENING A local TCP endpoint is waiting for incoming connections
ESTABLISHED A TCP connection is established
SYN_SENT A connection attempt has been sent and is awaiting progress
SYN_RECEIVED A connection request has been received and is awaiting completion
TIME_WAIT The endpoint is retaining state after connection closure to handle delayed segments and protect new connections
CLOSE_WAIT The remote endpoint has closed its sending direction, and the local application has not yet completed its close

State interpretation depends on which endpoint and direction are being inspected. A single snapshot is not enough to establish root cause.

10.4 Step 4: Inspect the application service

Confirm the following:

  • The intended application or driver is running.
  • It is configured to use the expected IP address and port.
  • The target is listening on the correct interface.
  • The firewall allows the required traffic.
  • The application protocol settings match on both ends.
  • The correct PLC, server, or device is being addressed.

A service may listen only on a loopback interface or a particular network interface, making it unavailable from other machines.

10.5 Step 5: Inspect packets when necessary

Wireshark can help identify the point of failure.

Capture observation Possible interpretation
SYN followed by SYN-ACK and ACK TCP handshake completed
Repeated SYN with no reply Packet filtering, unreachable endpoint, or no response from the target
RST from the target Connection rejected or reset by the target or a component acting on its behalf
Repeated retransmissions Possible packet loss, congestion, or missing acknowledgements
TCP connection succeeds, application request fails Application protocol or configuration problem may be present
FIN exchange Normal or orderly connection shutdown may be occurring

A packet trace provides evidence, not automatic root-cause identification. Correlate it with device logs, application errors, switch counters, and the timing of the failure.

Only capture or test systems that you are authorized to inspect, especially on live operational technology networks.

11. Troubleshooting UDP communication

UDP has no TCP-style handshake, so a missing response can be harder to interpret.

11.1 Typical causes

  • The sender is using the wrong destination IP address or port.
  • The receiving application is not bound to the intended port or interface.
  • A firewall or network ACL is dropping datagrams.
  • The return path is blocked, even though the outgoing datagram reaches the target.
  • The application expects a different message format.
  • Multicast membership or network configuration is incorrect.
  • Datagrams are being dropped because of congestion, receiver limitations, or filtering.
  • A message exceeds a path's usable packet size and is fragmented or dropped.

11.2 Practical inspection

Inspect local UDP endpoints:

Get-NetUDPEndpoint

To narrow the output to a known local port:

Get-NetUDPEndpoint -LocalPort 123

The example port is NTP's common UDP port. Change it to the service being investigated.

For a capture in Wireshark, useful display filters include:

udp

udp.port == 2222

ip.addr == 192.168.10.20 && udp

These filters display UDP traffic, traffic using the example port, or UDP traffic involving the example IP address.

Seeing an outgoing UDP datagram does not prove that the receiver got it. Seeing a reply does not prove that the application accepted or correctly processed the message. Compare captures at both ends when possible.

12. Common misconceptions

Misconception 1: UDP is always faster than TCP.

UDP has less transport overhead and does not provide TCP's built-in stream recovery mechanisms. But actual performance depends on the network and application. A poorly designed UDP application with excessive retries can perform worse than a well-designed TCP application.

Misconception 2: TCP guarantees that a command was executed.

TCP provides reliable, ordered delivery between transport endpoints. The receiving application may reject the command, fail to execute it, or lose power after receiving it. Applications requiring execution confirmation must implement suitable acknowledgements and state verification.

Misconception 3: A successful ping proves that a PLC service is working.

Ping tests ICMP reachability, not the health of a TCP or UDP application service.

Misconception 4: UDP has no error detection.

UDP includes a checksum mechanism, with different rules for IPv4 and IPv6. Error detection does not provide delivery guarantees or automatic recovery.

Misconception 5: TCP and UDP use separate IP networks.

They can use the same IP network interfaces and routes. The IP protocol identifies whether the payload is TCP or UDP, and transport ports distinguish application endpoints.

Misconception 6: Opening a port fixes every communication problem.

A firewall rule cannot correct an invalid application request, wrong device configuration, incompatible protocol settings, duplicate IP address, or faulty physical link.

13. Security and maintenance considerations

Transport ports are important when controlling access to industrial devices.

  • Permit only the required protocols and ports between approved systems.
  • Avoid exposing PLC, HMI, SCADA, and engineering services to untrusted networks.
  • Use network segmentation and firewall rules appropriate to the plant's architecture.
  • Document device IP addresses, service ports, communication direction, and application owners.
  • Review unexpected listeners and connections before disabling services.
  • Avoid changing ports or firewall rules on production equipment without authorization and a rollback plan.
  • Preserve known-good configurations and record changes that affect communication.
  • Do not assume that TCP reliability or UDP checksums provide authentication, confidentiality, or protection against malicious traffic.

A port being open is not itself a security defect. The relevant question is whether the service is necessary, appropriately configured, and accessible only to the intended systems.

14. Practical exercises

Perform these exercises on a lab network or systems where testing is authorized.

Exercise 1: Compare ICMP and TCP reachability

  1. Ping a known lab device.
  2. Test a TCP port that should be open.
  3. Test a TCP port that should be closed.
  4. Compare the results and identify what each test actually proves.

Exercise 2: Identify a TCP handshake

  1. Capture traffic while an authorized client connects to a test server.
  2. Filter for tcp.
  3. Identify SYN, SYN-ACK, and ACK.
  4. Close the client connection and inspect the termination exchange.

Exercise 3: Inspect an application port

  1. Run netstat -ano.
  2. Identify a known listening port.
  3. Record the PID.
  4. Correlate the PID with the responsible application using approved Windows tools.
  5. Confirm whether the listener is bound to the expected interface.

Exercise 4: Compare TCP and UDP captures

  1. Use a controlled test application that supports both transports.
  2. Capture traffic for each mode.
  3. Compare the headers and message boundaries.
  4. Observe how the application responds when packets are intentionally lost in the lab.

Do not deliberately inject loss or interrupt communications on a production control network.

15. Interview questions and answers

Q1. What is the primary difference between TCP and UDP?

TCP provides a reliable, ordered byte stream using connection state, acknowledgements, and retransmission. UDP sends independent datagrams without built-in delivery or ordering guarantees.

Q2. Why is TCP called connection-oriented?

The endpoints establish and maintain connection state, normally beginning with a three-way handshake.

Q3. What is the purpose of the TCP three-way handshake?

It establishes the connection and synchronizes initial sequence numbers between the endpoints.

Q4. What is the difference between flow control and congestion control?

Flow control protects the receiver from excessive incoming data. Congestion control regulates transmission in response to network congestion.

Q5. Why might UDP be suitable for cyclic I/O?

Some control protocols prefer timely updates over retransmitting outdated data. UDP can support this design, but protocol-specific timing and fault-handling mechanisms remain essential.

Q6. Does TCP guarantee that a PLC has executed a command?

No. TCP confirms transport-level delivery behavior, not successful application execution or physical machine action.

Q7. Why can ping succeed while Modbus TCP fails?

ICMP reachability may work even when TCP port 502 is closed, filtered, or unavailable, or when the Modbus application is incorrectly configured.

Q8. What does a TCP RST indicate?

It indicates a connection reset or rejection. The source and surrounding packet sequence help determine the likely cause.

Q9. Can UDP packets arrive out of order?

Yes. UDP does not guarantee ordering. Applications that need ordering must implement or use an appropriate higher-level mechanism.

Q10. Why can EtherNet/IP use both TCP and UDP?

TCP is commonly used for connection establishment and explicit messaging, while UDP is commonly used for implicit cyclic I/O traffic.

Q11. What is head-of-line blocking in TCP?

Missing earlier stream data can delay delivery of later received data to the application until the missing bytes are recovered.

Q12. How do you confirm whether a TCP service is reachable on Windows?

Use Test-NetConnection <IP-address> -Port <port> and inspect TcpTestSucceeded. This tests connectivity to the specified TCP endpoint, not the correctness of its application protocol.

16. Final mental model

  • TCP: Establish a connection, deliver an ordered byte stream, recover from loss, and regulate transmission. Useful when complete, ordered delivery matters.
  • UDP: Send individual datagrams with low transport overhead and no built-in delivery recovery. Useful when the application can tolerate loss or manages recovery itself.
  • Ports: Identify transport-layer application endpoints.
  • IP: Moves traffic between IP endpoints.
  • Application protocol: Defines what the data means and whether the requested operation succeeded.
  • Troubleshooting: Separate network reachability, transport connectivity, application-protocol correctness, and actual machine behavior.

The practical rule is to identify the protocol and port first, test the relevant endpoint, and then inspect application behavior. That is much more useful than restarting random devices until the fault temporarily disappears.
