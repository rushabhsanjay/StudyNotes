1. Definition and purpose

The OSI model (Open Systems Interconnection model) is a seven-layer conceptual framework used to understand how data moves between communicating systems over a network.

It separates network communication into layers, with each layer performing a defined set of functions and interacting with the layers above and below it.

In industrial automation, the OSI model is useful when troubleshooting communication between PLCs, HMIs, CNC controllers, industrial PCs, managed switches, SCADA servers, VFDs, and remote I/O systems.

For example, suppose a PLC is connected to an industrial PC through an Ethernet switch, but the SCADA application cannot read PLC data. The OSI model helps narrow down whether the problem is related to:

  • Physical connectivity, cabling, or electrical signaling.
  • Ethernet framing, MAC addresses, or switching.
  • IP addressing, subnetting, or routing.
  • TCP or UDP transport.
  • Application protocols such as Modbus TCP or EtherNet/IP.
  • Configuration, services, or application logic.

The main purpose is not to force every fault into exactly one layer. It is to provide a structured method for isolating faults without replacing hardware or changing configuration randomly.

2. The seven OSI layers

The layers are numbered from Layer 1, closest to the physical transmission medium, to Layer 7, closest to the user application.

Layer 7  Application       → Network services used by applications
Layer 6  Presentation      → Data representation and transformation
Layer 5  Session           → Communication sessions and coordination
Layer 4  Transport         → End-to-end transport, ports, reliability
Layer 3  Network           → Logical addressing and routing
Layer 2  Data Link         → Frames, MAC addresses, switching
Layer 1  Physical          → Signals, cables, connectors, transceivers

When data is sent, each layer provides services to the layer above it and passes information toward the lower layers. At the receiving endpoint, the process is reversed.

3. Layer 1: Physical layer

3.1 Purpose

The Physical layer defines how raw bits are transmitted across a physical medium.

It deals with electrical, optical, mechanical, and signaling characteristics rather than the meaning of the data.

Typical elements include:

  • Copper Ethernet cables and connectors.
  • Fiber-optic cables and optical transceivers.
  • Ethernet PHY chips.
  • RS-232 and RS-485 electrical interfaces.
  • Ethernet port link status.
  • Signal timing and supported transmission rates.
  • Cable length and physical installation quality.

3.2 Industrial examples

  • A PLC Ethernet cable is disconnected.
  • A switch port is disabled or the connected device is powered off.
  • A fiber connector is dirty.
  • An SFP module is incompatible with the fiber type.
  • An RS-485 cable has an open conductor.
  • A damaged RJ45 connector causes intermittent connectivity.

3.3 Symptoms

  • Link LED is off.
  • Ethernet link repeatedly drops.
  • Communication works only when a cable is moved.
  • Fiber link does not establish.
  • Serial communication receives no electrical response.
  • Physical errors increase due to a damaged cable or poor signal quality.

3.4 Diagnostic procedure

  1. Verify device power and port status.
  2. Inspect connectors and cable routing.
  3. Confirm cable and transceiver compatibility.
  4. Check the correct interface type and supported speed.
  5. Test with a known-good cable where permitted.
  6. For fiber, inspect and clean connectors using approved equipment.
  7. For serial wiring, verify the pinout, signal reference, and interface type.

A link LED is useful evidence, but it does not prove that the complete network or application is functioning.

4. Layer 2: Data Link layer

4.1 Purpose

The Data Link layer provides communication over a local network link. It organizes data into frames and supports link-level addressing and error detection.

For Ethernet, important concepts include:

  • Ethernet frames.
  • MAC addresses.
  • Switch forwarding tables.
  • VLANs and 802.1Q tagging.
  • Ethernet frame error detection using the Frame Check Sequence (FCS).
  • Link-level behavior and port statistics.

A common Layer 2 device is an Ethernet switch.

4.2 MAC addresses

A MAC address identifies a network interface at the Data Link layer.

An Ethernet switch learns source MAC addresses and associates them with ports. It uses its forwarding table to decide where to send frames addressed to known destinations.

If the destination MAC address is unknown, a switch generally floods the frame within the relevant VLAN, subject to filtering and other switch behavior.

4.3 VLANs

A VLAN creates a logical Layer 2 broadcast domain within a switched network.

Two devices can be connected to the same physical switch but remain unable to communicate because they belong to different VLANs and no appropriate Layer 3 routing is configured.

4.4 Industrial examples

  • A PLC port is connected to the wrong switch port or VLAN.
  • A switch learns a MAC address on an unexpected port.
  • A trunk port does not carry the required VLAN.
  • A port security rule blocks a device.
  • Ethernet FCS errors occur due to a physical link problem.
  • A switch loop causes excessive broadcast traffic or a broadcast storm.

4.5 Diagnostic procedure

  • Verify switch port status and configuration.
  • Check VLAN membership and trunk configuration.
  • Inspect MAC address tables.
  • Review port error counters and logs.
  • Check for loops, unexpected flooding, or port security violations.
  • Verify that both endpoints are connected to the intended Layer 2 network.

Important: A Layer 2 symptom does not always mean a Layer 2 root cause. FCS errors, for example, may result from cabling or physical signaling problems at Layer 1.

5. Layer 3: Network layer

5.1 Purpose

The Network layer handles logical addressing and routing between IP networks.

The most important protocol at this layer is IP, including IPv4 and IPv6.

Key concepts include:

  • IP addresses.
  • Subnet masks and prefixes.
  • Default gateways.
  • Routing tables.
  • Packet forwarding.
  • ICMP diagnostics.
  • Network Address Translation (NAT), where used.
  • IPv4 Address Resolution Protocol (ARP), which supports mapping local IPv4 addresses to link-layer addresses.

ARP is often discussed alongside Layer 2 and Layer 3 because it connects IP addressing with Ethernet delivery. It does not mean that every network function fits neatly into a single OSI layer.

5.2 IP addressing example

Suppose a PLC has this configuration:

  • IP address: 192.168.10.20
  • Subnet mask: 255.255.255.0

The SCADA PC is configured as:

  • IP address: 192.168.10.50
  • Subnet mask: 255.255.255.0

Both addresses are within the same IPv4 subnet, so they can generally communicate directly if the Layer 2 connection and device configurations permit it.

Now suppose the SCADA PC is configured as 192.168.20.50/24. It is in a different subnet. Communication then requires an appropriate Layer 3 path and any necessary gateway and security configuration.

5.3 Industrial examples

  • A PLC has an incorrect IP address.
  • Two devices use the same IP address.
  • The subnet mask is incorrect.
  • The default gateway is missing for communication with another subnet.
  • A route is missing.
  • A device is connected to the wrong network.
  • A firewall or access-control policy blocks traffic, although the exact enforcement mechanism may involve several layers.

5.4 Diagnostic procedure

  1. Check the IP address and subnet mask of each endpoint.
  2. Check for duplicate IP addresses.
  3. Confirm that both devices are in the intended subnet or have a valid routed path.
  4. Verify the default gateway where cross-subnet communication is required.
  5. Use ping where ICMP is permitted.
  6. Inspect the routing table with route print on Windows.
  7. Check ARP resolution with arp -a where appropriate.
  8. Verify routing, firewall, and network segmentation rules.

A failed ping does not prove that the PLC is offline. ICMP may be disabled or filtered while the application protocol remains available.

6. Layer 4: Transport layer

6.1 Purpose

The Transport layer provides communication between processes running on networked devices.

The main protocols encountered in ordinary industrial Ethernet networks are:

  • TCP: Connection-oriented transport with sequencing, acknowledgements, retransmission, and ordered byte-stream delivery.
  • UDP: Connectionless datagram transport with message boundaries but no built-in guarantee of delivery, ordering, or retransmission.

TCP and UDP use port numbers to identify application endpoints.

6.2 TCP

TCP is commonly used by industrial applications that need reliable, ordered delivery of a byte stream.

Examples include:

  • Modbus TCP, commonly using TCP port 502.
  • HTTP and HTTPS-based configuration or monitoring services.
  • Many engineering and supervisory applications.

A TCP connection can fail even when IP connectivity exists. Possible causes include a service that is not listening, a blocked port, a rejected connection, or an application that is not responding correctly.

6.3 UDP

UDP is commonly used when applications need datagram communication and manage timing or reliability at another layer.

Examples include selected discovery, time synchronization, real-time, and industrial communication services.

UDP does not establish a TCP-style connection. A successful IP path does not guarantee that a UDP application is listening or that the received datagram will be processed.

6.4 Diagnostic procedure

  • Identify the expected protocol and port.
  • Confirm that the target service is running.
  • Check firewall rules and access-control lists.
  • Use appropriate TCP connection tests where permitted.
  • Inspect packet captures for resets, retransmissions, missing responses, or UDP datagrams.
  • Verify application-specific timeouts and connection limits.

For example, Test-NetConnection 192.168.10.20 -Port 502 can help test TCP connectivity to a Modbus TCP endpoint from Windows PowerShell. It does not validate the Modbus request, register map, or application behavior.

7. Layer 5: Session layer

7.1 Purpose

The Session layer conceptually manages communication sessions between applications, including establishing, coordinating, and terminating interactions.

In real TCP/IP systems, session-related functions are frequently implemented within application libraries, middleware, and protocols rather than as a distinct, universal Layer 5 protocol.

7.2 Industrial examples

  • An engineering application opens a communication session with a controller.
  • A supervisory client reconnects after a network interruption.
  • An application maintains a session state or periodically renews a connection.
  • A remote access tool loses its authenticated session even though the network remains operational.

7.3 Common symptoms

  • Repeated reconnects.
  • Sessions time out despite stable physical links.
  • A stale session prevents a new connection.
  • A client and server disagree about session state.
  • Communication resumes only after an application or service restart.

7.4 Diagnostic procedure

  • Check application logs and session timeout settings.
  • Confirm whether reconnect logic is supported.
  • Check for stale sessions or connection limits.
  • Compare the behavior of multiple clients.
  • Verify whether restarting the application changes the symptom, while preserving logs first.

Do not assume every disconnect is a Layer 5 fault. TCP connection state, server resources, application logic, and lower-layer network interruptions may produce similar symptoms.

8. Layer 6: Presentation layer

8.1 Purpose

The Presentation layer describes how data is represented, encoded, transformed, compressed, or encrypted so that communicating systems interpret it correctly.

In practical networks, these responsibilities are often handled by application protocols, serialization libraries, and security protocols.

Important concepts include:

  • Character encoding.
  • Data serialization and deserialization.
  • Numeric representation and byte order.
  • Data formatting.
  • Compression.
  • Encryption and decryption, where used.
  • Conversion between application data types.

8.2 Industrial examples

  • A PLC register is interpreted as a signed integer instead of an unsigned integer.
  • Two 16-bit registers are combined into a 32-bit floating-point value using the wrong word order.
  • A SCADA application decodes a byte string using the wrong character encoding.
  • A client cannot establish a secure session because the TLS configuration is incompatible.
  • Data is received successfully but displayed with an incorrect scale or engineering unit.

8.3 Byte order and data representation

A 16-bit register contains two bytes. A 32-bit value may occupy two consecutive 16-bit registers, but the register order and byte order depend on the protocol and device implementation.

A value can therefore arrive over the network without any packet loss and still be interpreted incorrectly by the receiving application.

This is especially relevant when connecting PLCs, test equipment, energy meters, and SCADA systems from different manufacturers.

8.4 Diagnostic procedure

  • Verify the data type and signedness.
  • Confirm byte order and word order.
  • Check scaling and engineering units.
  • Verify the encoding expected by the application.
  • Check the supported encryption and certificate configuration where relevant.
  • Compare raw received bytes or registers with the decoded value.

A value that is consistently wrong may indicate a representation or application-mapping problem rather than a network transport failure.

9. Layer 7: Application layer

9.1 Purpose

The Application layer contains network services and protocols used directly by applications. It defines how applications request, exchange, and interpret data or services.

Common examples include:

  • Modbus TCP.
  • HTTP and HTTPS.
  • OPC UA.
  • DNS.
  • DHCP.
  • FTP and SFTP.
  • Industrial manufacturer-specific protocols.
  • Application services for configuration, diagnostics, and monitoring.

Not every protocol commonly described as an application protocol maps exclusively to Layer 7 in all practical implementations, but the model is useful for fault isolation.

9.2 Industrial examples

  • The PLC is reachable by IP, but the Modbus register address is incorrect.
  • An OPC UA server is running but the client uses the wrong endpoint or security policy.
  • A SCADA tag references the wrong controller address.
  • A protocol request uses an unsupported function code.
  • An engineering application uses the wrong device model or communication driver.
  • The PLC returns an exception response even though the network connection is working.

9.3 Diagnostic procedure

  1. Verify the protocol and service expected by the application.
  2. Check the server endpoint and port.
  3. Confirm device addresses, register mappings, and function codes.
  4. Inspect application logs and protocol responses.
  5. Verify authentication and authorization.
  6. Compare raw protocol data with the application's interpretation.
  7. Confirm that the application is configured for the correct PLC or controller.

Key principle: A successful ping proves neither that an industrial protocol is functioning nor that the application data is correct.

10. OSI layers, data units, and addressing

OSI layer Common data unit Important identifiers or mechanisms Typical device or function
Layer 7 Application Application data Protocol commands, services, object identifiers SCADA application, OPC UA server
Layer 6 Presentation Data representation Encoding, serialization, encryption Data conversion and security libraries
Layer 5 Session Session data Session state and coordination Application session management
Layer 4 Transport TCP segment or UDP datagram TCP/UDP ports TCP and UDP stacks
Layer 3 Network IP packet IP addresses Router and IP forwarding
Layer 2 Data Link Ethernet frame MAC addresses, VLAN tags Ethernet switch
Layer 1 Physical Bits and physical signals Voltage, light, timing, connector and medium characteristics PHY, cable, transceiver

The data-unit names are useful conventions. Actual protocol implementations do not always align perfectly with the theoretical model.

11. Encapsulation and decapsulation

When an application sends data, each networking layer adds the information needed for its part of the communication. This is called encapsulation.

Application data
       ↓
TCP or UDP header + application data
       ↓
IP header + transport data
       ↓
Ethernet header + IP packet + Ethernet trailer
       ↓
Physical signals over copper or fiber

At the receiving endpoint, the reverse process is called decapsulation. Each layer processes its relevant information and passes the remaining data upward.

For example, a Modbus TCP message is carried inside TCP, which is carried inside IP, which is carried inside an Ethernet frame on a typical Ethernet LAN.

This layered structure makes troubleshooting easier because the engineer can examine the Ethernet frame, IP packet, TCP connection, and Modbus request separately.

12. OSI model versus TCP/IP model

The OSI model is a seven-layer reference model. The TCP/IP model describes the practical architecture of Internet Protocol networking and is commonly represented using four layers, although five-layer teaching models are also used.

OSI model Common TCP/IP model equivalent Examples
Layer 7 Application Application Modbus TCP, HTTP, OPC UA
Layer 6 Presentation Application Encoding, serialization, TLS-related functions
Layer 5 Session Application Session management
Layer 4 Transport Transport TCP, UDP
Layer 3 Network Internet IPv4, IPv6, ICMP
Layer 2 Data Link Link Ethernet, Wi-Fi link functions
Layer 1 Physical Link or separately represented physical layer in five-layer models Copper signaling, optical signaling, radio transmission

The mapping is approximate. TCP/IP does not require each OSI layer to exist as a separate protocol or software module.

In practical industrial troubleshooting, the OSI model is useful as a diagnostic framework even when the actual implementation follows the TCP/IP stack.

13. Fault isolation using the OSI model

Consider this problem: a SCADA PC cannot read data from a PLC.

Instead of immediately replacing the switch or PLC, investigate from the lower layers upward.

Step Layer or area Test Interpretation
1 Physical Check power, link LEDs, cable, and transceivers No link suggests a physical or interface problem
2 Data Link Check VLAN, switch port, MAC learning, and port errors A wrong VLAN or blocked port may prevent local delivery
3 Network Check IP address, subnet, routing, and duplicate addresses Incorrect addressing or routes can prevent IP communication
4 Transport Check TCP port or relevant UDP traffic IP may work while the application transport endpoint is unavailable
5 Session Check reconnect behavior and application session logs A session may be stale or repeatedly timing out
6 Presentation Verify data types, encoding, and representation Data may arrive but be decoded incorrectly
7 Application Verify protocol, device address, commands, and mappings The network can be healthy while application communication fails

These tests are not a rigid sequence for every fault. For example, if a switch reports a port-security violation, that is already strong evidence for investigating Layer 2. The aim is to test the most likely cause efficiently while avoiding unsupported assumptions.

14. Common diagnostic tools and their limitations

Tool Main use What it does not prove
Physical inspection Finds disconnected cables, damage, and installation issues Does not prove protocol correctness
Link LEDs Indicates local interface link status Does not prove end-to-end application communication
ipconfig Shows local Windows IP configuration Does not prove the remote endpoint is reachable
ping Tests ICMP reachability where permitted Does not prove TCP, UDP, or application service availability
arp -a Displays the local IPv4 ARP cache Does not prove the complete path to a remote network
route print Shows the Windows routing table Does not prove that every remote route is functioning
Test-NetConnection Tests selected TCP connectivity and displays connection diagnostics Does not validate the application protocol or data mapping
Wireshark Captures and analyzes network packets Cannot reveal data that is never present in the capture or automatically identify every root cause
Switch diagnostics Shows port state, counters, VLANs, and MAC learning where supported Cannot independently prove that the application is correct
Protocol-specific diagnostic tool Tests protocol requests and responses May not isolate lower-layer faults without additional evidence

14.1 Useful Windows commands

Display IP configuration:

ipconfig /all

Test reachability where ICMP is allowed:

ping 192.168.10.20

Display the ARP cache:

arp -a

Display the routing table:

route print

Test a TCP port:

Test-NetConnection 192.168.10.20 -Port 502

The example IP address and port are illustrative. Use the actual authorized target address and service port in a plant environment.

15. Industrial troubleshooting case studies

Case 1: PLC link LED is off

Observed symptom: The SCADA PC cannot communicate with the PLC, and the switch port shows no link.

Possible causes:

  • Damaged or disconnected cable.
  • PLC or switch port disabled or defective.
  • PLC power failure.
  • Incompatible transceiver or media converter.
  • Incorrect copper or fiber connection.

Primary investigation: Layer 1 and interface configuration. Do not begin by changing the PLC's IP address because the physical link has not been established.

Case 2: Link is active, but ping fails

Observed symptom: Both Ethernet link LEDs are on, but the PC cannot ping the PLC.

Possible causes:

  • Incorrect IP address or subnet mask.
  • Duplicate IP address.
  • Wrong VLAN.
  • Missing route.
  • Firewall or access-control rule.
  • ICMP disabled on the endpoint.

Primary investigation: Layer 2 and Layer 3, while accounting for the possibility that ICMP is intentionally blocked.

Case 3: Ping works, but Modbus TCP fails

Observed symptom: The PLC responds to ping, but the SCADA application cannot read registers.

Possible causes:

  • Modbus TCP service unavailable.
  • TCP port 502 blocked or not listening.
  • Incorrect protocol configuration.
  • Incorrect unit identifier or register mapping.
  • Unsupported function code.
  • PLC communication limits or application-side timeout.

Primary investigation: Layer 4 and Layer 7, followed by checking the data representation and mapping where appropriate.

Case 4: Communication works, but values are incorrect

Observed symptom: The application receives data consistently, but displayed engineering values are wrong.

Possible causes:

  • Wrong register address.
  • Incorrect scaling.
  • Signed versus unsigned interpretation.
  • Incorrect byte or word order.
  • Incorrect data type.
  • Wrong engineering units.

Primary investigation: Data representation and application mapping. Replacing the Ethernet cable is unlikely to fix a consistently misinterpreted value.

Case 5: Intermittent network communication

Observed symptom: PLC communication drops for short periods and then recovers.

Possible causes:

  • Physical cable or connector faults.
  • Unstable power to a switch or converter.
  • Excessive traffic or congestion.
  • Switch loops or spanning-tree changes.
  • Duplicate IP addresses.
  • TCP retransmissions or application timeout settings.
  • Device resource limits.

Primary investigation: Capture timestamps, switch counters, event logs, packet traces, and device status. Correlate the events rather than assuming every intermittent fault is caused by electrical noise.

16. Practical exercises

Exercise 1: Map an industrial communication path

Choose an authorized communication path between a PLC and an engineering PC.

Record:

  • PLC and PC IP addresses.
  • Subnet masks and gateways.
  • Switches and VLANs along the path.
  • Copper and fiber connections.
  • Application protocol and port.
  • The tool used to verify each layer.

Expected result: a network-path record showing which layers are confirmed and which remain untested.

Exercise 2: Build a layer-based fault checklist

Create a checklist for these symptoms:

  • Link LED off.
  • Link LED on but ping fails.
  • Ping succeeds but TCP connection fails.
  • TCP connection succeeds but application requests fail.
  • Application responds but values are incorrect.

For each symptom, record the most likely layers, diagnostic tools, and next test.

Expected result: a repeatable troubleshooting procedure suitable for maintenance use.

Exercise 3: Capture and inspect an industrial protocol

Using an authorized test network and a suitable packet capture tool:

  1. Capture a known communication exchange.
  2. Identify Ethernet source and destination MAC addresses.
  3. Identify source and destination IP addresses.
  4. Identify TCP or UDP ports.
  5. Identify the application protocol, if the capture can decode it.
  6. Compare the request and response.
  7. Record the exact layer at which the observed exchange differs from expectations.

Expected result: a packet-level explanation of a communication transaction.

Exercise 4: Create a fault evidence record

Document one simulated or actual network fault using this structure:

  • Observed symptom.
  • Expected behavior.
  • Evidence collected.
  • Layers tested.
  • Tests passed.
  • Tests failed.
  • Confirmed root cause, if established.
  • Corrective action.
  • Verification after correction.

Expected result: a diagnosis supported by evidence rather than a list of parts replaced.

17. Interview questions and answers

Q1. What is the OSI model?

It is a seven-layer reference model that separates network communication into physical, data link, network, transport, session, presentation, and application functions.

Q2. Which OSI layer handles IP addresses?

Layer 3, the Network layer.

Q3. Which OSI layer handles MAC addresses and Ethernet switching?

Layer 2, the Data Link layer.

Q4. Which OSI layer handles TCP and UDP?

Layer 4, the Transport layer.

Q5. Does a successful ping prove that an application is working?

No. Ping generally tests ICMP reachability. An application service, TCP port, UDP service, protocol request, or data mapping can still fail.

Q6. What is encapsulation?

Encapsulation is the process of adding protocol information as data moves down the networking stack toward transmission.

Q7. What is the difference between a switch and a router?

A typical Layer 2 switch forwards Ethernet frames within Layer 2 networks, while a router forwards IP packets between networks using routing information.

Q8. At which layer does Modbus TCP operate?

Modbus TCP is an application protocol commonly carried over TCP. Its messages are transported using TCP, IP, and an underlying link technology such as Ethernet.

Q9. Why can a PLC be reachable by ping but unavailable to SCADA?

The IP path may work while the SCADA protocol service, TCP port, application configuration, authorization, or data mapping is incorrect.

Q10. Is every network fault limited to one OSI layer?

No. The model separates functions conceptually, but faults can cross layers. A physical fault can cause TCP retransmissions, application timeouts, and failed SCADA reads.

Q11. Which layer should be checked first?

There is no universal rule to start at Layer 1 for every fault. Use the observed symptoms and evidence to choose the most likely starting point, then test systematically.

Q12. Why is the OSI model useful for industrial maintenance?

It helps separate physical, switching, addressing, transport, and application faults so engineers can choose targeted tests and avoid unnecessary hardware replacement.

18. Final mental model

The OSI model is a troubleshooting framework, not a requirement that every network implementation contain seven separate modules.

  • Layer 1: Can the bits travel across the physical medium?
  • Layer 2: Can frames move across the local Ethernet network?
  • Layer 3: Can packets reach the correct IP destination?
  • Layer 4: Can the required transport endpoint exchange data?
  • Layer 5: Is the communication session behaving correctly?
  • Layer 6: Is the data represented and interpreted correctly?
  • Layer 7: Are the application protocol and requested operation working?

For industrial automation, the most important skill is distinguishing physical connectivity, network reachability, transport availability, protocol correctness, and application-data correctness. A successful test at one layer narrows the investigation, but it does not prove that every layer above it is functioning.
