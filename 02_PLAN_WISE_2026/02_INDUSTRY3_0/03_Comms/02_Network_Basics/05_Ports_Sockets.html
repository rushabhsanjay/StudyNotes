1. Purpose and scope

In industrial automation, successful communication requires more than knowing a device's IP address. The communicating application must use the correct transport protocol, destination port, local service, network route, and permitted firewall rules.

For example, a SCADA computer may successfully ping a PLC but still fail to read its data because the required TCP port is blocked or the PLC communication service is not available. Ping proves only a limited part of network reachability, not application communication.

This topic covers:

  • IP endpoints, TCP/UDP ports, sockets, and client-server communication.
  • Common service ports used in industrial automation and IT.
  • Firewall operation, rule design, network segmentation, and OT security.
  • Practical Windows diagnostics and fault isolation.
  • Maintenance documentation, controlled changes, and interview preparation.

2. IP addresses, ports, and endpoints

An IP address identifies a network interface or destination at the IP layer. A transport-layer port identifies a communication endpoint associated with an application or service on that device.

Consider a PLC with IP address 192.168.10.20 that provides Modbus TCP communication on port 502.

PLC IP address: 192.168.10.20
Transport:      TCP
Service port:   502

Destination endpoint:
192.168.10.20:502

The destination is identified by both its IP address and transport port. The transport protocol matters because TCP port 502 and UDP port 502 are separate transport endpoints.

Term Meaning Industrial example
IP address Identifies an IP interface or destination PLC at 192.168.10.20
Transport protocol Defines how transport-layer communication works TCP or UDP
Port number Identifies a transport endpoint associated with an application TCP 502 for Modbus TCP
Service Application function accepting or handling requests PLC Modbus TCP server
Endpoint Communication destination or endpoint, commonly represented by IP and port 192.168.10.20:502/TCP
Socket Operating-system communication abstraction, typically involving an IP address, transport protocol, and port TCP socket used by SCADA software
Connection An established transport communication relationship, such as a TCP connection SCADA connected to a PLC

A port is not a physical connector. Ethernet port 1 on a switch is a physical interface; TCP port 502 is a logical transport-layer number. Confusing these two makes troubleshooting unnecessarily entertaining for everyone involved.

3. TCP ports and UDP ports

3.1 TCP ports

TCP is connection-oriented. Before ordinary application data is exchanged, the endpoints establish a connection using the TCP handshake.

TCP provides an ordered byte stream and mechanisms for retransmission, sequencing, and flow control. Applications still need their own protocol-level error handling and timeouts.

Common TCP services include:

  • Modbus TCP.
  • Web interfaces using HTTP or HTTPS.
  • OPC UA over TCP.
  • SSH remote administration.
  • Remote Desktop.
  • Many PLC programming and engineering services, depending on manufacturer and configuration.

3.2 UDP ports

UDP sends datagrams without establishing a TCP-style connection. It does not inherently guarantee delivery, ordering, or retransmission.

UDP is useful where low overhead or application-managed timing is important. Industrial examples include EtherNet/IP implicit I/O traffic and time synchronization using NTP.

A UDP application may receive a datagram without maintaining a persistent connection in the TCP sense. The application must handle missing or invalid data as required.

3.3 Important comparison

Feature TCP UDP
Connection setup Uses a connection handshake No TCP-style connection setup
Delivery guarantee Retransmits lost data as required by TCP No inherent delivery guarantee
Ordering Ordered byte stream Datagram order is not guaranteed
Data boundaries Application defines message framing over the byte stream Each datagram preserves its message boundary
Typical use Configuration, requests, responses, web services Real-time I/O, discovery, timing, selected streaming protocols
Firewall rule Specify TCP and the required port Specify UDP and the required port
Diagnostic caution A successful TCP test does not prove application correctness A TCP-only test says nothing about UDP reachability

Key rule: TCP and UDP rules are not interchangeable. Allowing TCP port 44818 does not automatically allow UDP port 44818.

4. Port number ranges

Port numbers are 16-bit values ranging from 0 to 65535. The Internet Assigned Numbers Authority (IANA) divides them into three conventional ranges.

Range Category Practical meaning
0-1023 System or well-known ports Widely used standard services
1024-49151 User or registered ports Registered services and application-specific uses
49152-65535 Dynamic or private ports Commonly used for temporary client-side ports

These ranges describe allocation conventions, not universal operating-system behavior. Operating systems can use configurable ephemeral port ranges, and applications can bind to specific ports where permitted.

Port 0 is reserved for special use in the port-number system. Applications may request that an operating system select an available local port by binding to port 0.

4.1 Server ports and client ephemeral ports

In a typical client-server exchange, the server listens on a known service port while the client uses a local source port.

Example: a SCADA computer opens a Modbus TCP connection to a PLC.

SCADA computer                         PLC
192.168.10.50                          192.168.10.20
TCP source port: 53124                 TCP destination port: 502
          ───────── TCP connection ─────────→
          ←──────── Responses ───────────────

Client local endpoint: 192.168.10.50:53124
Server endpoint:       192.168.10.20:502

Here, 53124 is an illustrative ephemeral client port. The actual port is selected by the operating system unless the application binds to a specific one.

The response travels back over the same TCP connection. A stateful firewall typically recognizes the response as part of the permitted established connection, provided the relevant rules and network path allow it.

This does not mean every firewall should permit arbitrary inbound traffic to every ephemeral port. Rules should match the intended traffic and connection state.

5. The TCP connection tuple

A TCP connection is commonly distinguished using a five-tuple:

  1. Transport protocol.
  2. Source IP address.
  3. Source port.
  4. Destination IP address.
  5. Destination port.

Example:

Protocol:        TCP
Source IP:       192.168.10.50
Source port:     53124
Destination IP:  192.168.10.20
Destination port: 502

Changing any of these values can result in a different connection. The same server can accept connections from multiple clients because each connection has its own identifying tuple.

For UDP, a similar set of values identifies a flow or datagram context, but UDP does not establish a TCP connection.

Why this matters in troubleshooting

A firewall rule that allows the PLC IP but blocks TCP port 502 can still prevent Modbus TCP communication. Likewise, a rule for the correct port but the wrong source subnet may block the SCADA computer.

Always examine the complete traffic definition, not merely the destination IP.

6. Common service ports

The following are common defaults or conventions. Actual port usage depends on the device, software version, configuration, and vendor implementation.

Service or protocol Transport Common port Industrial use
HTTP TCP 80 Web interfaces and dashboards
HTTPS TCP 443 Encrypted web interfaces and APIs
SSH TCP 22 Secure command-line administration
DNS UDP/TCP 53 Hostname resolution and related DNS operations
NTP UDP 123 Clock synchronization
SNMP queries UDP 161 Network monitoring
SNMP traps UDP 162 Network-device event notifications
Modbus TCP TCP 502 PLC, instrument, and SCADA communication
EtherNet/IP explicit messaging TCP 44818 Configuration and request-response services
EtherNet/IP services UDP 44818 Discovery and related protocol functions, depending on service
EtherNet/IP implicit I/O UDP 2222 Cyclic or real-time I/O data
OPC UA over TCP TCP 4840 Industrial interoperability and data exchange
Remote Desktop Protocol TCP/UDP 3389 Windows remote access
DHCP server/client UDP 67/68 Dynamic IP configuration

6.1 Industrial protocol notes

Modbus TCP: TCP port 502 is the standard default. A firewall must permit the correct traffic direction between the authorized client and server. Opening the port does not provide authentication or encryption by itself.

EtherNet/IP: TCP 44818 is associated with encapsulation services. UDP 2222 is commonly used for implicit I/O. Opening TCP 44818 alone may therefore leave cyclic I/O traffic blocked.

OPC UA: TCP 4840 is a common default, but OPC UA endpoints can be configured to use different ports. Security policies, certificates, user authentication, and endpoint configuration also matter.

Siemens, Rockwell, Mitsubishi, and other automation platforms: Engineering software and controllers may use several additional ports for discovery, programming, diagnostics, time synchronization, or vendor-specific communication. Do not infer a complete firewall rule set from one familiar port number. Obtain the relevant vendor's network requirements for the actual hardware and software versions.

6.2 A port number does not prove service identity

Port numbers are conventions. A service can run on a nonstandard port, and a program can bind to a familiar port for a different purpose.

Therefore:

  • An open port does not prove that the expected service is running.
  • A listening port does not prove that the application protocol is working correctly.
  • A successful TCP handshake does not prove that the client is authorized or that useful data can be exchanged.
  • A familiar port does not prove that the service is secure.

7. What is a firewall?

A firewall applies rules to network traffic to determine whether it should be allowed, blocked, or otherwise handled.

Firewalls may be implemented in:

  • A Windows or Linux host.
  • A network router.
  • A dedicated firewall appliance.
  • An industrial security gateway.
  • A Layer 3 switch with access control lists (ACLs).
  • A virtualized or cloud network environment.

A firewall is not necessarily a separate physical box. The Windows computer running the SCADA application may block traffic before it reaches the application, even when the network infrastructure is correctly configured.

7.1 Firewall rule fields

A rule may evaluate several properties:

Rule property Purpose Example
Direction Defines the traffic direction relative to the firewall Inbound or outbound
Action Specifies the handling of matching traffic Allow or block
Protocol Identifies transport behavior TCP or UDP
Source address Restricts where traffic originates SCADA subnet
Destination address Restricts the target Specific PLC
Source port Restricts the originating transport port when relevant Usually dynamic for a client
Destination port Restricts the destination service TCP 502
Connection state Distinguishes new traffic from established or related traffic Permit established responses
Network zone or interface Limits traffic to a network or interface OT control zone
Logging Records selected traffic decisions Denied connection logs

Not every firewall supports all fields in the same way. Rule evaluation order, state handling, and conflict resolution depend on the product.

7.2 Inbound and outbound rules

Inbound and outbound are defined from the perspective of the system or firewall where the rule is applied.

For a SCADA client connecting to a PLC:

  • The SCADA computer initiates an outbound TCP connection to the PLC's service port.
  • The PLC receives inbound traffic on its service port.
  • Response traffic returns to the SCADA computer's selected client port.
  • A stateful firewall can normally recognize valid response traffic as part of the established connection.

The exact rules depend on where the firewall is installed, whether it is stateful, and whether the connection crosses multiple network boundaries.

A firewall on the SCADA computer and a firewall between the SCADA network and PLC network may need different rules for the same communication.

8. Stateful filtering, stateless ACLs, and default-deny rules

8.1 Stateful firewall

A stateful firewall tracks connection state. For TCP, it can distinguish a new connection attempt from traffic belonging to an established connection.

For example, a rule can permit authorized SCADA clients to initiate TCP connections to specified PLCs on port 502 while allowing valid responses through the same state-tracked connection.

State tracking reduces the need for separate broad rules for return traffic. It does not eliminate the need to design rules correctly.

8.2 Stateless ACL

A stateless access control list evaluates packets against configured rules without maintaining the same connection-state table used by a stateful firewall.

Return traffic may therefore need explicit consideration. A rule that allows client-to-server traffic may not automatically allow the corresponding server-to-client response packets.

8.3 Default deny and least privilege

A secure starting point is to deny traffic that has not been explicitly authorized, then add narrowly scoped rules for required communication.

Apply least privilege by limiting:

  • Source devices or subnets.
  • Destination devices.
  • Required protocols.
  • Required ports.
  • Direction of initiation.
  • Access duration where temporary rules are necessary.

Avoid rules such as "allow all traffic from any source to any destination" simply because troubleshooting is inconvenient. Such rules can conceal the original fault while creating a much larger security problem.

9. Firewalls in industrial OT networks

Industrial networks have different operational constraints from ordinary office networks. A blocked connection may stop production, while an overly permissive rule can expose controllers, engineering stations, and process data to unnecessary risk.

9.1 Recommended network zones

A typical industrial architecture may separate:

  • Enterprise IT network.
  • Industrial demilitarized zone (IDMZ).
  • Supervisory and SCADA systems.
  • PLC and machine-control networks.
  • Safety-related systems, where applicable.
  • Remote engineering access.

The exact zones depend on the plant architecture and risk assessment.

Enterprise IT
      ↓
Industrial DMZ
      ↓
SCADA / HMI / Historian
      ↓
Control network
      ↓
PLC / CNC / Robot / Drives

This is a conceptual arrangement, not a mandatory topology. Real plants may use redundant networks, separate cell zones, routed control networks, or other architectures.

9.2 Practical OT firewall principles

  • Permit only documented communication required for a defined operational purpose.
  • Restrict traffic between machine cells rather than allowing unrestricted lateral access.
  • Keep PLCs, CNCs, HMIs, robot controllers, and engineering workstations in appropriate security zones.
  • Do not expose controller services directly to the public internet.
  • Use approved remote-access paths, authentication, and authorization.
  • Coordinate changes with production, maintenance, controls engineering, and OT cybersecurity.
  • Validate firewall rules against the actual protocol requirements, including UDP traffic and any vendor-specific services.
  • Preserve approved configurations and rollback procedures.
  • Avoid unplanned firewall changes during production or safety-critical operation.

Firewalls support network security, but they do not replace application security, controller access control, backups, physical security, or functional-safety measures.

10. Port forwarding, NAT, and firewall rules

These concepts are related but not interchangeable.

Firewall rule: Determines whether matching traffic is permitted or blocked.

Network Address Translation (NAT): Translates IP addresses and, in some configurations, port numbers between network domains.

Port forwarding: A form of destination NAT that directs incoming traffic arriving at a particular address and port to another destination.

Example:

Incoming address: 203.0.113.10:1502
           ↓
NAT / port-forwarding rule
           ↓
Internal destination: 192.168.10.20:502

The addresses above are illustrative documentation addresses, not production destinations.

Port forwarding does not automatically make the traffic safe. A corresponding firewall policy must still permit the intended traffic, and the translated destination must be reachable. For industrial controllers, avoid exposing services externally merely to simplify remote troubleshooting. Use an approved secure remote-access architecture instead.

11. Practical Windows diagnostics

Run diagnostic commands only on systems and networks you are authorized to inspect. Use extra care on production OT networks because aggressive scanning and configuration changes can affect equipment availability.

11.1 Test a TCP service port

From a Windows engineering or SCADA computer, PowerShell can test whether a TCP connection to a particular destination and port can be established.

Test-NetConnection -ComputerName 192.168.10.20 -Port 502

Relevant output fields include:

  • RemoteAddress: the destination address.
  • RemotePort: the tested TCP port.
  • TcpTestSucceeded: whether the TCP connection test succeeded.

Interpretation:

  • True: A TCP connection could be established at the time of the test. This does not prove that Modbus requests will succeed.
  • False: The TCP test failed. Possible causes include routing problems, a blocked firewall rule, a service that is not listening, or a device that is unreachable.

Important: Test-NetConnection -Port tests TCP, not UDP. It cannot confirm EtherNet/IP UDP I/O on port 2222.

11.2 Check listening TCP ports and process IDs

netstat -ano -p tcp

Useful columns include:

  • Local Address.
  • Foreign Address.
  • State.
  • PID.

Common TCP states include LISTENING, ESTABLISHED, TIME_WAIT, and CLOSE_WAIT.

A LISTENING entry indicates that a local TCP endpoint is listening. It does not prove that a remote client can reach it through the network or firewall.

To inspect the process associated with a PID:

Get-Process -Id 1234

Here, 1234 is an example PID. Replace it with the PID reported by the diagnostic command.

11.3 Inspect TCP connections

Get-NetTCPConnection

To inspect listening TCP endpoints:

Get-NetTCPConnection -State Listen

To narrow the output to a particular local port:

Get-NetTCPConnection -LocalPort 502

A service may use a different port from the default, so check the actual configuration rather than assuming port 502 is correct for every Modbus-related application.

11.4 Inspect UDP endpoints

Get-NetUDPEndpoint

To filter for UDP port 2222:

Get-NetUDPEndpoint -LocalPort 2222

This shows local UDP endpoints known to Windows. It does not prove that UDP datagrams can reach the remote device or that the remote application is responding correctly.

11.5 Inspect Windows Firewall profiles

Get-NetFirewallProfile

Windows Firewall commonly has Domain, Private, and Public profiles. Different profiles can have different policies, and a network's classification can affect which policy applies.

To inspect configured rules:

Get-NetFirewallRule

For a focused investigation, filter rules by display name, direction, action, enabled state, and associated port or address filters. Avoid changing rules until the intended traffic and policy are understood.

12. A systematic troubleshooting method

When an automation application cannot communicate, isolate the fault layer by layer. Changing random firewall settings until the alarm disappears is not a diagnostic method, even if it occasionally produces results.

Step 1: Confirm the intended communication

Record:

  • Client device and IP address.
  • Server device and IP address.
  • Protocol: TCP or UDP.
  • Required destination port.
  • Expected application function.
  • Expected communication direction.
  • Vendor documentation or approved network specification.

Step 2: Check basic IP connectivity

Check the IP configuration, subnet mask, default gateway, and expected route. A successful ping can be useful, but ICMP may be blocked even when the required application port is allowed.

Likewise, a failed ping does not prove that TCP or UDP communication is impossible.

Step 3: Check the destination service

Confirm that the intended service is enabled, configured for the expected port, and listening on the correct interface. Some services listen only on loopback or a selected network adapter.

Step 4: Test the TCP port where applicable

Use Test-NetConnection for a known TCP service. For UDP, use protocol-specific diagnostics, device counters, suitable packet captures, or vendor-approved tools.

Step 5: Inspect host and network firewalls

Check both endpoints and any intervening firewalls or ACLs. Confirm source and destination addresses, transport protocol, port, direction, rule state, and network zone.

Step 6: Examine packet behavior

If permitted, capture traffic using an approved packet analyzer such as Wireshark at a suitable observation point.

Look for:

  • TCP SYN packets with no response.
  • TCP RST responses indicating rejection or absence of a listening service.
  • Successful TCP handshakes followed by application-level failures.
  • UDP requests with no observed responses.
  • Repeated retransmissions or timeouts.
  • Responses leaving one interface but not reaching the client.

A packet capture is evidence about traffic visible at that capture point. It does not automatically reveal what happened elsewhere in the network.

Step 7: Verify the application protocol

If the transport connection succeeds but communication still fails, inspect the application layer. Examples include Modbus function codes, register addressing, device configuration, OPC UA certificates and security policies, or EtherNet/IP connection configuration.

Step 8: Make a controlled change

If a rule needs modification:

  1. Record the current configuration.
  2. Define the exact required traffic.
  3. Obtain the required approval.
  4. Apply the smallest suitable change.
  5. Test both normal operation and relevant failure cases.
  6. Document the outcome and retain a rollback path.

13. Troubleshooting matrix

14. Worked example: SCADA cannot read a Modbus TCP PLC

Scenario: A SCADA PC at 192.168.10.50 must read data from a PLC at 192.168.10.20 using Modbus TCP on port 502.

The SCADA software reports a connection timeout.

Investigation

  1. Verify that the PLC's configured IP address is 192.168.10.20.
  2. Confirm that Modbus TCP is enabled and configured for TCP port 502.
  3. From the SCADA PC, run: Test-NetConnection -ComputerName 192.168.10.20 -Port 502
  4. If the test fails, verify the route, destination service, host firewall, and intervening network firewall.
  5. If the test succeeds, inspect the SCADA configuration, Modbus request parameters, PLC diagnostics, and application logs.
  6. If the connection establishes but reads fail, check unit identifiers, function codes, register addresses, data types, and device-specific addressing conventions.
  7. Capture traffic if necessary and permitted, then determine whether the request reaches the PLC and whether a response returns.
  8. Make any required configuration changes under the plant's change-control procedure.

Interpreting the evidence

Observation What it suggests What it does not prove
Ping succeeds Some IP connectivity exists TCP port 502 is open
TCP port test succeeds A TCP connection can be established Modbus requests are valid
PLC shows a listening service The service has a local listener Network firewalls permit remote access
Modbus response received The application exchanged a response Every register or data value is correct
No response in the SCADA capture No response was visible at that capture point The PLC definitely never generated one

The objective is to identify the failing layer before changing anything.

15. Practical maintenance checklist

Use this checklist when documenting industrial communication or investigating a firewall-related fault.

  • Record the client and server device names, IP addresses, and network zones.
  • Record the application protocol, TCP or UDP, destination port, and direction of initiation.
  • Verify the actual configured service port against vendor documentation.
  • Confirm the service is enabled and listening on the intended interface.
  • Check host firewall and network firewall policies.
  • Confirm that source and destination restrictions are correct.
  • Verify routing, subnet masks, gateways, and any relevant NAT translations.
  • Check application logs and device diagnostics.
  • Use an authorized packet capture if the fault remains unresolved.
  • Record the observed symptom, evidence, root cause, and corrective action.
  • Save the approved firewall rule and configuration change record.
  • Document the rollback procedure and test results.

For a recurring fault, capture the normal operating configuration and expected communication paths in the machine's technical documentation. That turns the next breakdown from an archaeological expedition into a repeatable diagnostic task.

16. Interview questions and answers

Q1. What is the difference between an IP address and a port number?

An IP address identifies an IP destination or interface. A transport port identifies an application endpoint on that destination for TCP or UDP communication.

Q2. Why can a device respond to ping while an application cannot connect?

Ping uses ICMP, whereas the application may use TCP or UDP. The application service may be disabled, configured for a different port, or blocked by a firewall.

Q3. What is an ephemeral port?

It is a temporary port commonly assigned to a client application for outgoing communication. The server generally listens on a configured service port.

Q4. What is a socket?

A socket is an operating-system communication abstraction used by applications. A network socket is associated with transport information such as an IP address, protocol, and port.

Q5. What is the difference between TCP and UDP?

TCP provides a connection-oriented, ordered byte stream with retransmission and flow-control mechanisms. UDP sends datagrams without TCP's connection setup and delivery guarantees.

Q6. What is the difference between a stateful firewall and a stateless ACL?

A stateful firewall tracks connection state and can recognize traffic belonging to an established connection. A stateless ACL evaluates packets against rules without equivalent connection tracking.

Q7. What are the common ports for Modbus TCP and EtherNet/IP?

Modbus TCP commonly uses TCP 502. EtherNet/IP commonly uses TCP 44818 for encapsulation services and UDP 2222 for implicit I/O. Additional ports may be required for other functions.

Q8. Does opening TCP port 44818 allow EtherNet/IP cyclic I/O?

Not necessarily. Cyclic I/O commonly uses UDP 2222, so the required UDP traffic must also be permitted where applicable.

Q9. What does Test-NetConnection -Port 502 test?

It tests TCP connectivity to the specified destination and port. It does not test UDP and does not validate the Modbus application exchange.

Q10. What is the difference between port forwarding and a firewall rule?

Port forwarding translates and redirects traffic to another destination, often changing the destination IP or port. A firewall rule determines whether traffic is allowed or blocked. They may be used together but perform different functions.

Q11. What is the principle of least privilege in firewall configuration?

Permit only the communication required for an authorized purpose, restricted to the necessary devices, protocols, ports, directions, and network zones.

Q12. Why is exposing a PLC service directly to the internet dangerous?

It can expose industrial control services to unauthorized access, exploitation, and operational disruption. Remote access should use an approved security architecture with appropriate access controls and monitoring.

17. Practical exercises

  1. Identify a service: On an authorized Windows PC, run Get-NetTCPConnection -State Listen. Identify the local addresses, listening ports, and owning process IDs.
  2. Test a known TCP service: Use Test-NetConnection against an approved test device and documented TCP port. Record the result and what it does or does not establish.
  3. Compare TCP and UDP: Inspect the required ports for a lab Modbus TCP or EtherNet/IP setup. Explain why a TCP test cannot validate a UDP I/O path.
  4. Build a firewall requirement: Document the source, destination, protocol, port, purpose, direction, and expected response traffic for one approved SCADA-to-PLC communication.
  5. Diagnose a simulated failure: Given a timeout, determine which evidence would distinguish a routing issue, firewall block, missing listener, and application-level failure.
  6. Create a communication register: Record each machine's approved engineering, SCADA, HMI, and controller communication requirements. Do not infer undocumented ports or change production rules without authorization.

18. Final mental model

  • IP address: Which network destination?
  • Transport protocol: TCP or UDP?
  • Destination port: Which application endpoint?
  • Socket: Which communication endpoint is used by the application?
  • Service: Is the intended application listening and functioning?
  • Firewall: Is the required traffic permitted by policy?
  • Routing and NAT: Can traffic reach the destination and return correctly?
  • Application protocol: Are requests, addressing, authentication, and responses valid?
  • Change control: Can the fix be applied, verified, documented, and reversed safely?

A reliable diagnosis proceeds from the network path to the transport endpoint, then to the service and application protocol. A port number is one piece of evidence, not a magic spell that makes two devices communicate.
