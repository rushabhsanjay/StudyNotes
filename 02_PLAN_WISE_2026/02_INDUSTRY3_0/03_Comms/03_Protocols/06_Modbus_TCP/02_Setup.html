Modbus TCP Setup: IP Address, Unit Identifier, and Register Map

1. Purpose and Scope

Modbus TCP setup is the process of configuring network connectivity, identifying the correct server, selecting the appropriate Modbus data addresses, and interpreting the returned values correctly.

A working Modbus TCP connection requires more than entering an IP address. The client and server must be configured compatibly, the Modbus service must be reachable, and the requested function codes and register addresses must be supported by the target device.

This topic covers:

  • IP addressing, subnet masks, gateways, and TCP port configuration.
  • Client and server configuration.
  • Unit Identifier configuration.
  • Register maps, function codes, and address offsets.
  • Data types, scaling, byte order, and word order.
  • Practical PLC-to-VFD setup.
  • Validation, commissioning, and maintenance documentation.

2. Overall Setup Architecture

PLC / SCADA / Industrial PC
        |
        | Modbus TCP Client
        |
        | Target IP + TCP Port
        ↓
Industrial Ethernet Switch
        |
        ↓
Modbus TCP Server
        |
        | Unit Identifier, where applicable
        |
        ↓
Supported Function Code
        |
        ↓
Register Address + Quantity
        |
        ↓
Response Data
        |
        ↓
Data Type Conversion + Scaling
        |
        ↓
PLC Tag / HMI Display / SCADA Database

Each layer has a separate purpose. The IP address identifies the network endpoint, the TCP port identifies the service, the Unit Identifier identifies a logical unit where required, and the register address identifies the requested data within that unit.

3. IP Address Configuration

3.1 Essential Network Parameters

Parameter Purpose Example
IP address Identifies the device on the IP network 192.168.10.20
Subnet mask Defines the local IPv4 subnet 255.255.255.0
Default gateway Routes traffic to other networks 192.168.10.1
TCP port Identifies the Modbus TCP service 502
Device role Determines whether the device initiates requests or serves them Server
Network interface Ethernet port used for communication Ethernet 1

These are example settings. Use the actual plant network plan and device documentation rather than copying example addresses into production equipment.

3.2 Example Network Plan

Assume a PLC reads data from a VFD and an energy meter.

Device IP address Subnet mask Communication role
PLC 192.168.10.10 255.255.255.0 Modbus TCP client
VFD 192.168.10.20 255.255.255.0 Modbus TCP server
Energy meter 192.168.10.30 255.255.255.0 Modbus TCP server
SCADA PC 192.168.10.40 255.255.255.0 Modbus TCP client

All devices are in the same IPv4 subnet in this example.

The IP addresses must be unique on the network. Duplicate IP addresses can cause intermittent connectivity, unexpected responses, or communication failures that are difficult to reproduce.

3.3 IP Address and Subnet Mask

For a subnet mask of 255.255.255.0, the first three octets identify the network portion of the IPv4 address.

For example:

  • PLC: 192.168.10.10
  • VFD: 192.168.10.20

Both belong to the 192.168.10.0/24 subnet.

If the client and server are on different subnets, a router or Layer 3 switch and appropriate routing configuration are normally required.

Do not change the subnet mask merely because communication fails. First compare the device configuration with the approved network plan.

3.4 Default Gateway

A default gateway is normally required when a device needs to communicate outside its local subnet.

If the PLC and VFD are on the same subnet, communication may work without a configured default gateway. If the target server is on another subnet, routing and gateway configuration become important.

A wrong gateway can prevent communication with remote networks while leaving local-subnet communication unaffected.

3.5 Static and Dynamic IP Addresses

Industrial devices commonly use static IP addresses because controllers and SCADA systems need predictable endpoint addresses.

Some devices also support DHCP, where an address is assigned dynamically.

For fixed automation equipment, address planning should account for:

  • Device replacement.
  • PLC configuration backups.
  • SCADA server configuration.
  • Network segmentation.
  • Duplicate address prevention.
  • Approved IP allocation and change control.

If DHCP is used, ensure that address assignment is controlled and predictable. Do not assume that a device will always receive the same address unless the network design provides that behavior.

4. TCP Port and Server Configuration

Modbus TCP normally uses TCP port 502.

The client typically requires:

  • Server IP address.
  • Server TCP port.
  • Connection timeout.
  • Request timeout.
  • Polling interval.
  • Supported Modbus function code.
  • Unit Identifier, if applicable.
  • Register address and quantity.

The server typically requires:

  • Correct IP configuration.
  • Modbus TCP service enabled.
  • Correct listening port.
  • Supported function codes and register map.
  • Appropriate connection and access settings.

Some devices allow the service port to be changed. If a nonstandard port is configured, the client must use the same port.

A working Ethernet link does not prove that the Modbus TCP service is enabled. Similarly, a successful ping does not prove that TCP port 502 is reachable.

5. Unit Identifier

5.1 What Is the Unit Identifier?

The Unit Identifier is a one-byte field in the Modbus TCP MBAP header. It can identify a downstream device or logical unit when the communication architecture requires it.

Its importance depends on the target device.

  • A native Modbus TCP server may ignore the Unit Identifier or expect a fixed value.
  • A TCP-to-RTU gateway may use it to select a downstream Modbus RTU slave.
  • Some devices document a specific Unit Identifier for their supported interface.

The Unit Identifier is not the same as the server's IP address, TCP port, or Modbus register address.

5.2 Native Modbus TCP Example

Suppose a PLC communicates directly with a VFD.

Parameter Example
Client IP 192.168.10.10
Server IP 192.168.10.20
TCP port 502
Unit Identifier 1, if required by the VFD
Function code 03
Register offset 0, if specified by the device map

The Unit Identifier value is illustrative. Use the VFD manual to determine whether the field is meaningful and what value is expected.

5.3 TCP-to-RTU Gateway Example

PLC Client
    |
    | Modbus TCP
    ↓
Gateway IP: 192.168.10.50
TCP Port: 502
    |
    | Unit Identifier selects downstream device
    ↓
RS-485 Network
    |
    +---- RTU Slave 1
    |
    +---- RTU Slave 2
    |
    +---- RTU Slave 3

In this arrangement, the PLC connects to the gateway's IP address. The gateway may use the Unit Identifier to determine which serial slave should receive the request.

For example, the gateway may map Unit Identifier 2 to RTU slave address 2. That mapping is gateway-dependent, not a universal Modbus TCP rule.

5.4 Common Unit Identifier Mistakes

  • Assuming the Unit Identifier must always equal the final octet of the IP address.
  • Entering the gateway's IP address as the Unit Identifier.
  • Assuming every native Modbus TCP server requires the same Unit Identifier.
  • Confusing the Unit Identifier with the RTU slave address without checking gateway behavior.
  • Changing the Unit Identifier to troubleshoot an unrelated IP or TCP problem.

Configure it according to the actual device or gateway documentation.

6. Understanding the Register Map

A register map describes the data exposed by a Modbus device. It is one of the most important documents for commissioning and maintenance.

A typical register map specifies:

  • Register reference or offset.
  • Data area.
  • Function code.
  • Parameter name.
  • Data type.
  • Read/write permissions.
  • Scaling factor.
  • Engineering unit.
  • Valid range.
  • Byte order or word order for multi-register values.
  • Device-specific operating conditions.

Example register map:

Parameter Documented reference Example offset Function Data format
Output frequency 40001 0 03 Unsigned 16-bit, scaled
Output current 40002 1 03 Unsigned 16-bit, scaled
DC bus voltage 40003 2 03 Unsigned 16-bit, scaled
Drive status 40004 3 03 Status word
Speed reference 40010 9 06 or 10, if supported Unsigned 16-bit, scaled

The offsets and meanings above are illustrative only. The real device map may use different references, functions, scaling, and permissions.

6.1 Register References vs. Wire Addresses

A common source of errors is the difference between the register number printed in a manual and the address transmitted in a Modbus request.

For example, a manual may show holding register 40001. Some client software expects the zero-based offset 0; other software accepts a displayed reference or uses a different configuration convention.

Documentation convention Possible client input
Holding register 40001 Offset 0
Holding register 40002 Offset 1
Holding register 40101 Offset 100

This example assumes the conventional mapping where 40001 corresponds to offset zero. Not all vendors use the same notation.

Practical rule: Read the register-addressing section of both the device manual and the client software manual. Never blindly subtract one from every register address.

6.2 Function Code and Data Area Must Match

A register address alone does not fully describe a Modbus request.

The client must also select the appropriate function code.

For example:

  • Function 01: Read Coils.
  • Function 02: Read Discrete Inputs.
  • Function 03: Read Holding Registers.
  • Function 04: Read Input Registers.
  • Function 06: Write Single Register.
  • Function 16 hexadecimal: Write Multiple Registers.

A manual may describe a parameter as a holding register, meaning function 03 is normally used to read it. Requesting the same offset with function 04 is not equivalent.

7. Modbus Data Types and Scaling

Modbus registers are 16 bits wide. A register map may interpret them as different logical data types.

7.1 Common Data Types

Data type Size Typical interpretation
Boolean or bit 1 bit On/off or status flag
Unsigned 16-bit integer 16 bits Nonnegative integer
Signed 16-bit integer 16 bits Positive or negative integer
Unsigned 32-bit integer 32 bits Two consecutive registers
Signed 32-bit integer 32 bits Two consecutive registers
IEEE 754 float Usually 32 bits Floating-point value across two registers
Bit field or status word 16 or 32 bits Multiple encoded states

The data type must come from the device documentation. Two devices may expose similar-looking parameters using different encodings.

7.2 Scaling Factors

Many devices return scaled integers instead of floating-point values.

Suppose the register returns 253, and the register map specifies a scale factor of 0.1 Hz per count.

\[ \text{Engineering value} = \text{Raw value} \times \text{Scale factor} \]
\[ 253 \times 0.1 = 25.3\ \text{Hz} \]

The displayed frequency should therefore be 25.3 Hz.

Other devices may specify a divisor, a different multiplier, or an offset. Follow the manufacturer's exact formula.

7.3 Signed and Unsigned Values

An unsigned 16-bit value ranges from 0 to 65535.

A signed 16-bit two's-complement value ranges from -32768 to 32767.

For example, the bit pattern 0xFFFF can be interpreted as:

  • Unsigned 16-bit integer: 65535
  • Signed 16-bit integer: -1

The raw bits are identical. The interpretation changes according to the configured data type.

7.4 Multi-Register Values and Word Order

A 32-bit value occupies two consecutive 16-bit registers. The order in which the high and low words are stored is device-dependent.

Suppose a 32-bit value contains these words:

  • High word: 0x4120
  • Low word: 0x0000

Combining them in high-word-first order gives 0x41200000, which is the IEEE 754 floating-point representation of 10.0.

If the words are swapped, the resulting value is different and may be nonsensical.

For a 32-bit value, verify:

  • Register sequence.
  • Byte order within each register, as relevant to the interface and implementation.
  • Word order across registers.
  • Signedness or floating-point format.

Do not assume all Modbus TCP devices use the same word order. Modbus defines the 16-bit register structure, while many 32-bit data representations are device-specific conventions.

8. Setting Up a Modbus TCP Client

The exact software steps depend on the PLC platform, HMI, SCADA package, or industrial PC application. The general configuration sequence is similar.

Step 1: Identify the Target Server

Record:

  • Device manufacturer and model.
  • Firmware version, where relevant.
  • IP address.
  • TCP port.
  • Whether the device is a native Modbus TCP server or a gateway.
  • Supported function codes.

Step 2: Configure Network Connectivity

Verify that the client and server use compatible IP settings.

Check:

  • Unique IP addresses.
  • Subnet masks.
  • Routing and gateways when necessary.
  • Correct Ethernet interface.
  • Approved VLAN and firewall rules.

Step 3: Create the Modbus TCP Connection

Configure the server IP address and TCP port, normally 502.

Set connection and request timeouts according to the software and device documentation. Avoid using unnecessarily large values to hide an unstable network.

Step 4: Configure the Unit Identifier

Use the required value for the native server or downstream device. If a gateway is involved, verify the gateway's Unit Identifier mapping.

Step 5: Configure the Request

Enter:

  • Function code.
  • Starting register offset.
  • Number of registers or bits.
  • Polling interval.
  • Data type and decoding rules.

Ensure that the requested range is valid for the selected function code and supported by the device.

Step 6: Decode the Response

Convert the returned data according to the register map.

For numerical parameters, check scaling, signedness, byte order, word order, and engineering units.

Step 7: Validate the Result

Compare the value received by the client with a trusted reference, such as the device's local display or diagnostic software.

A successful request is not enough if the value is interpreted incorrectly.

9. Worked Example: PLC Reading a VFD

Assume a PLC must read the output frequency from a VFD over Modbus TCP.

The VFD manual specifies:

  • Server IP: 192.168.10.20
  • TCP port: 502
  • Function code: 03
  • Holding register reference: 40001
  • Register data type: Unsigned 16-bit integer
  • Scaling: Raw value multiplied by 0.1 Hz
  • Unit Identifier: 1, if required by the device

These values are hypothetical and illustrate the setup process.

Client configuration

Setting Configured value
Server IP 192.168.10.20
TCP port 502
Unit Identifier 1, subject to device requirements
Function code 03
Starting offset 0, if the client uses zero-based addressing
Quantity 1 register
Data type Unsigned 16-bit integer
Scale 0.1 Hz per count

Example response

Suppose the returned raw register value is 253.

\[ f = 253 \times 0.1 = 25.3\ \text{Hz} \]

The PLC can then store the scaled value in an internal tag, such as VFD_Output_Frequency_Hz, and expose it to the HMI or SCADA system.

Validation

  1. Confirm that the TCP connection is established.
  2. Confirm that the request uses function 03.
  3. Confirm that the register address convention is correct.
  4. Confirm that the server returns a valid response.
  5. Compare the raw and scaled values with the VFD display.
  6. Repeat the check at another operating point.

If the PLC returns 253 while the drive display shows approximately 25.3 Hz, the scaling appears consistent. If the values differ, check the address, scale factor, update timing, and device operating conditions before changing unrelated network settings.

10. Read and Write Configuration

Read and write operations require different considerations.

10.1 Read Operations

Typical read requests include:

  • Reading output frequency.
  • Reading current and voltage.
  • Reading a status word.
  • Reading digital inputs.
  • Reading alarm information.

The requested address range and quantity must be supported by the server.

10.2 Write Operations

Write requests can change device settings or operating commands.

Examples include:

  • Writing a speed reference.
  • Writing a setpoint.
  • Writing a control word.
  • Changing an operating mode.

Before configuring writes, verify:

  • The register is writable.
  • The function code is supported.
  • The device is in the correct operating mode.
  • The requested value is within the documented range.
  • The write is authorized by the plant control design.
  • The PLC has appropriate interlocks and command validation.

Do not experiment with unknown write registers on production equipment. An undocumented write may change a parameter or trigger an operation with real machine consequences.

11. Polling Interval and Request Quantity

The polling interval determines how frequently the client requests updated data. The appropriate interval depends on the process, the device's response capability, the network, and the number of requested data items.

For example:

  • Fast-changing control data may need frequent updates.
  • Energy totals may not need rapid polling.
  • Diagnostic values may be read at longer intervals.
  • A large register block may be more efficient than many individual requests if the device supports it.

Avoid excessive polling. It can increase server load, connection traffic, and application latency.

Also consider device-specific limits on the number of registers per request. The protocol's maximums do not guarantee that every device supports the maximum quantity.

12. Commissioning and Verification Checklist

Network configuration

  • Confirm the device model and communication capabilities.
  • Verify unique IP addresses.
  • Check subnet mask and routing.
  • Confirm the correct Ethernet interface.
  • Verify the intended TCP port, normally 502.
  • Confirm that network policy permits the connection.

Modbus configuration

  • Identify the server's supported function codes.
  • Configure the correct Unit Identifier when required.
  • Confirm the register map version and addressing convention.
  • Verify the starting offset and requested quantity.
  • Confirm data type, scaling, signedness, and word order.
  • Verify read and write permissions.

Functional validation

  • Establish the TCP connection.
  • Read a known, valid register.
  • Compare raw data with a trusted reference.
  • Confirm the engineering value after scaling.
  • Test the expected polling interval and response time.
  • Verify writes only when authorized and safe.
  • Record the final configuration and test results.

13. Common Setup Errors

Error Result Corrective action
Incorrect server IP Connection fails or reaches the wrong device Verify the approved IP plan
Duplicate IP address Intermittent or inconsistent communication Assign unique addresses and verify network records
Wrong TCP port TCP connection fails Check the server's configured service port
Incorrect Unit Identifier Gateway selects the wrong downstream unit or rejects the request Check the device or gateway mapping
Wrong function code Exception response or failed request Match the function to the data area
Incorrect offset Wrong data or invalid-address exception Confirm the manual's address convention
Wrong quantity Request rejected or exceeds device limits Use a supported register range
Incorrect scaling Engineering value is incorrect Apply the manufacturer's conversion formula
Incorrect word order 32-bit values are incorrect Verify register ordering
Polling too frequently Excessive traffic or timeouts Optimize request quantity and polling interval
Attempting an unsupported write Write rejected or no change occurs Verify permissions and supported write functions

14. Maintenance Documentation

For each Modbus TCP device, maintain a record containing:

  • Device name, manufacturer, model, and firmware.
  • Physical location and connected machine.
  • IP address, subnet mask, gateway, and TCP port.
  • Client/server relationship.
  • Unit Identifier behavior.
  • Register map and document revision.
  • Function codes used.
  • Register offsets and quantities.
  • Data types, scaling, signedness, and word order.
  • Polling interval and timeout settings.
  • Read/write permissions and relevant interlocks.
  • Known-good test values.
  • Configuration backup location and revision history.

This documentation makes device replacement, PLC modification, SCADA integration, and fault diagnosis significantly more predictable.

15. Interview Questions and Answers

Q1. What information is required to configure a Modbus TCP client?

At minimum, the server IP address, TCP port, supported function code, register address, and requested quantity. Depending on the device, the configuration may also require a Unit Identifier, timeout settings, and data-decoding parameters.

Q2. What is the purpose of the Unit Identifier?

It identifies a logical unit where required, especially when a gateway forwards Modbus TCP requests to downstream serial devices. Native TCP devices may ignore it or require a device-specific value.

Q3. Why might register 40001 be configured as offset 0?

Some manuals use human-readable reference numbers, while the protocol request contains a zero-based register offset. The actual client convention must be verified rather than assumed.

Q4. What is the difference between a holding register and an input register?

Holding registers are conventionally accessed with function 03 for reading and may support writes. Input registers are conventionally read with function 04. Actual access permissions depend on the device.

Q5. Why is the value from a Modbus register sometimes incorrect even when communication succeeds?

Possible causes include an incorrect offset, wrong data type, signedness, scaling, byte order, word order, or an incorrect interpretation of a status word.

Q6. What is the difference between the IP address and the register address?

The IP address identifies the network endpoint. The register address identifies a data location exposed by the Modbus server.

Q7. Why should a device's register map be checked before configuring writes?

The map identifies writable locations, supported functions, valid ranges, and the meaning of each parameter. An incorrect write can change device behavior or be rejected.

Q8. Why is excessive polling undesirable?

It can increase network traffic, server load, response latency, and timeouts. Polling frequency should match the process's data-update requirements.

Q9. Does a successful TCP connection prove that the Modbus setup is correct?

No. The server may be reachable while the requested function code, register address, Unit Identifier, or data interpretation is incorrect.

Q10. What should be verified when replacing a Modbus TCP device?

Confirm the replacement's network settings, supported functions, register map, firmware behavior, Unit Identifier requirements, data format, access permissions, and compatibility with the existing client configuration.

16. Practical Exercises

  • Create an IP address plan for one PLC, two VFDs, one energy meter, and one SCADA PC.
  • Extract five useful parameters from an actual device's Modbus register map.
  • Record the function code, reference number, client offset, data type, scale factor, and unit for each parameter.
  • Configure a read-only test for one known register.
  • Compare the raw value with the device display.
  • Calculate the engineering value using the documented scaling formula.
  • Identify whether a gateway requires a Unit Identifier and how it maps that value to a downstream device.
  • Document the final connection parameters and the evidence used to validate the setup.

17. Final Mental Model

A correct Modbus TCP setup requires four distinct decisions:

  1. Where is the server? Configure the correct IP address, network path, and TCP port.
  2. Which logical device should respond? Configure the Unit Identifier where the device or gateway requires it.
  3. Which data should be accessed? Select the correct function code, register offset, and quantity.
  4. How should the response be interpreted? Apply the correct data type, signedness, word order, scaling, and engineering unit.

When these four areas are configured correctly and verified against the device documentation, the resulting data can be integrated reliably into PLC logic, HMI displays, SCADA systems, historians, and maintenance dashboards.
