Modbus TCP Basics: Modbus over Ethernet, Client/Server

1. Purpose and Scope

Modbus TCP is an industrial communication protocol that allows PLCs, HMIs, SCADA systems, industrial PCs, energy meters, VFDs, and other automation devices to exchange data over Ethernet networks.

It uses the Modbus application protocol to read and write device data, while TCP/IP provides transport and network communication.

The key difference from Modbus RTU is the communication transport:

  • Modbus RTU: Typically uses serial communication such as RS-485, with frames protected by a CRC.
  • Modbus TCP: Uses TCP/IP over Ethernet, with Modbus messages carried inside TCP segments and IP packets.

Modbus TCP is widely used when devices need to communicate over an industrial Ethernet network rather than a serial bus.

2. What Modbus TCP Actually Does

Modbus TCP defines how a client requests data and how a server responds.

Typical operations include:

  • Reading digital input states.
  • Reading PLC coils and internal bits.
  • Reading holding registers and input registers.
  • Writing individual coils or holding registers.
  • Writing multiple coils or holding registers.
  • Exchanging status, measurements, setpoints, and commands between compatible systems.

Modbus TCP does not automatically define what a register means. The device manufacturer provides the register map that explains the data addresses, data types, scaling, access permissions, and functions supported by the device.

For example, a VFD might expose its output frequency through a holding register and its running status through a status register. The PLC must know the correct addresses and decoding rules to interpret these values.

3. Modbus TCP Architecture

        Industrial Ethernet Network
                    |
       +------------+------------+
       |                         |
       ↓                         ↓
  Modbus Client             Modbus Server
  PLC / SCADA               VFD / Meter
  Industrial PC             Remote I/O
       |                         |
       |---- TCP/IP Request ---->|
       |<--- TCP/IP Response ----|

A typical implementation includes:

  • Client: Initiates requests to read or write data.
  • Server: Listens for requests and returns responses.
  • Ethernet interface: Provides physical network connectivity.
  • IP addressing: Identifies the device on the IP network.
  • TCP connection: Provides a reliable transport connection.
  • Modbus application message: Specifies the requested operation and its data.

A PLC can be a client when reading a VFD's registers. The same PLC can also be a server when another system reads data from it. Client and server roles depend on the particular communication relationship, not permanently on the device type.

4. Client and Server Roles

4.1 Modbus TCP Client

The client initiates a Modbus transaction.

Typical examples include:

  • A PLC reading actual speed from a VFD.
  • A SCADA server reading measurements from an energy meter.
  • An industrial PC polling a PLC for production values.
  • A PLC writing a speed reference to a drive.
  • A data acquisition application reading process registers.

The client typically needs the server's IP address, TCP port, unit identifier when applicable, function code, register address, and requested quantity.

4.2 Modbus TCP Server

The server listens for incoming TCP connections and processes supported Modbus requests.

Typical examples include:

  • A VFD exposing its operating parameters.
  • A PLC exposing data to SCADA.
  • An energy meter providing measurements.
  • A remote I/O device exposing input and output states.

A server may reject unsupported function codes, invalid addresses, or writes to read-only registers.

4.3 Client vs. Server Comparison

Feature Modbus TCP Client Modbus TCP Server
Main responsibility Initiates requests Receives and processes requests
Starts a transaction Yes Normally responds to client requests
Needs target IP Yes Has its own IP address
TCP port Connects to server port Listens on a server port
Reads data Requests data Supplies supported data
Writes data Sends write requests Processes supported writes
Typical example PLC polling a meter Meter serving register data

Some devices support both roles, while others support only one. Confirm the capability in the device manual.

5. Modbus TCP Protocol Stack

Application Layer
    Modbus Function Codes
    Register Addresses and Data
              ↓
Transport Layer
    TCP
    Default Port: 502
              ↓
Network Layer
    IPv4 or IPv6, depending on implementation
              ↓
Data Link Layer
    Ethernet
              ↓
Physical Layer
    Copper Ethernet or Fiber Ethernet

Modbus TCP commonly uses TCP port 502.

Port 502 is the standard Modbus TCP service port, but a device may support additional configuration options. A firewall or network security policy can block the connection even when the physical Ethernet link is healthy.

Modbus TCP normally uses a TCP connection, which provides ordered delivery and retransmission of lost TCP segments. However, reliable TCP delivery does not guarantee that the requested register exists, that its value is correct, or that the machine is operating safely.

6. Modbus TCP vs. Modbus RTU

Feature Modbus RTU Modbus TCP
Common physical network RS-485 or RS-232 interfaces Ethernet
Transport Serial communication TCP/IP
Default communication details Baud rate and serial framing IP address and TCP port
Typical port Not applicable TCP port 502
Device identification Serial slave address IP address plus possible Unit Identifier
Frame integrity RTU CRC TCP checksum and Ethernet/IP integrity mechanisms
Frame boundary Serial timing and silence Modbus TCP message length in the MBAP header
Typical network layout Serial bus Switched Ethernet
Multiple devices Shared serial bus or supported serial arrangement IP-connected devices across the network
Typical faults Polarity, termination, baud rate, CRC IP configuration, TCP connectivity, firewall, routing, register mapping

Modbus TCP does not use the RTU frame's CRC field. It uses a Modbus TCP message structure containing an MBAP header followed by the Modbus function code and data.

Do not confuse the fact that both protocols use Modbus function codes with the idea that their complete message formats are identical.

7. Modbus TCP Message Structure

A Modbus TCP application message contains an MBAP header and the Modbus protocol data unit.

Modbus TCP ADU
    |
    +-- MBAP Header: 7 bytes
    |      Transaction Identifier: 2 bytes
    |      Protocol Identifier:    2 bytes
    |      Length:                 2 bytes
    |      Unit Identifier:        1 byte
    |
    +-- Modbus PDU
           Function Code:           1 byte
           Data:                    Variable length

ADU means Application Data Unit. PDU means Protocol Data Unit.

7.1 MBAP Header Fields

Field Size Purpose
Transaction Identifier 2 bytes Associates a response with the corresponding request
Protocol Identifier 2 bytes Normally 0 for Modbus
Length 2 bytes Specifies the number of following bytes, including the Unit Identifier and PDU
Unit Identifier 1 byte Identifies a downstream or logical unit when required

The MBAP header allows the receiver to identify message boundaries without relying on the serial timing rules used by Modbus RTU.

7.2 Transaction Identifier

The client assigns a transaction identifier to a request. The server normally returns the same identifier in the response.

This helps a client match responses to requests, particularly when multiple transactions are outstanding on a TCP connection.

The transaction identifier is not the IP address, the TCP port, or the Unit Identifier. Each serves a different purpose.

7.3 Protocol Identifier

The protocol identifier is normally zero for standard Modbus TCP messages.

A nonzero value may indicate a different encapsulated protocol or an invalid message in a standard Modbus TCP context.

7.4 Length Field

The length field specifies how many bytes follow the first six bytes of the MBAP header.

It includes:

  • The one-byte Unit Identifier.
  • The complete Modbus PDU.

The length field is important because TCP is a byte stream, not a message-preserving transport. One TCP read operation is not guaranteed to return exactly one complete Modbus message.

Software must use the MBAP length field to determine whether a complete Modbus TCP message has arrived.

8. Modbus TCP Function Codes

Modbus TCP uses the same principal Modbus function codes as Modbus RTU. The transport and message encapsulation differ, but the application operations are familiar.

Function code Operation Typical use
01 Read Coils Read writable digital bits
02 Read Discrete Inputs Read digital input bits
03 Read Holding Registers Read 16-bit holding registers
04 Read Input Registers Read 16-bit input registers
05 Write Single Coil Write one digital bit
06 Write Single Register Write one 16-bit holding register
0F / 15 hex Write Multiple Coils Write several digital bits
10 / 16 hex Write Multiple Registers Write several holding registers
17 / 23 hex Read/Write Multiple Registers Perform a combined register read/write operation

The hexadecimal representations are shown where applicable. For example, function code 03 is hexadecimal 0x03.

The device may support only a subset of these functions. Always verify the supported functions in the device's Modbus documentation.

9. Modbus Data Areas

Modbus defines logical data areas. The actual memory implementation depends on the server device.

Data area Common reference convention Typical function Data type
Coils 0xxxx 01, 05, 0F Single bits
Discrete Inputs 1xxxx 02 Single bits
Input Registers 3xxxx 04 16-bit registers
Holding Registers 4xxxx 03, 06, 10 16-bit registers

These reference conventions are common in documentation, not universal wire-level addresses. The client software may ask for a zero-based offset rather than the displayed reference number.

For example, a manual may describe a holding register as 40001, while a client configuration expects address 0. Another client may display or accept the full reference. Use the address convention specified by the software and device manual.

9.1 Coils and Discrete Inputs

Coils and discrete inputs represent single-bit values.

Typical examples include:

  • Motor run command.
  • Ready status.
  • Fault status.
  • Digital input state.
  • Remote enable command.

A coil is generally treated as a writable bit area. A discrete input is generally treated as a read-only bit area. The actual implementation and write permissions remain device-dependent.

9.2 Holding Registers and Input Registers

Holding registers and input registers are 16-bit values.

Typical applications include:

  • Actual speed.
  • Frequency reference.
  • Motor current.
  • DC bus voltage.
  • Temperature.
  • Energy consumption.
  • Alarm codes.
  • Operating modes.

A register can hold an unsigned integer, signed integer, part of a larger value, or encoded data. The register itself does not automatically specify its engineering unit or scaling.

For example, a raw register value of 253 could represent 25.3 Hz if the manufacturer specifies a scale factor of 0.1. Without the register map, the raw value alone is not enough.

10. IP Addressing and Ethernet Communication

Each Ethernet-connected Modbus TCP device needs a valid network configuration.

Common parameters include:

  • IP address.
  • Subnet mask.
  • Default gateway, where routing is required.
  • TCP port.
  • Device-specific network settings.

Example:

Device IP address Subnet mask Role
PLC 192.168.10.10 255.255.255.0 Client
VFD 192.168.10.20 255.255.255.0 Server
Energy meter 192.168.10.30 255.255.255.0 Server
SCADA PC 192.168.10.40 255.255.255.0 Client

These are illustrative private-network addresses, not a recommended configuration for every plant.

10.1 Same-Subnet Communication

With the example subnet mask, devices on 192.168.10.0/24 are in the same IPv4 subnet.

A client at 192.168.10.10 can normally reach a server at 192.168.10.20 directly through the Ethernet network, assuming correct configuration and no blocking network policy.

10.2 Different Subnets

If the client and server are on different subnets, routing is normally required. The default gateway and routing configuration must support the path.

A successful ping does not prove that Modbus TCP is working. Ping tests ICMP reachability, not whether a server accepts TCP connections on port 502 or supports the requested Modbus operation.

Likewise, a failed ping does not always prove that Modbus TCP is unreachable because ICMP traffic may be blocked while TCP communication is permitted.

11. TCP Connection and Port 502

A typical Modbus TCP client establishes a TCP connection to the server's IP address and port 502.

Client PLC
    |
    | TCP connection to server IP, port 502
    ↓
Ethernet Switch
    |
    ↓
Modbus TCP Server
    |
    | Request accepted
    ↓
Modbus TCP Response

The connection uses TCP's normal connection-management behavior. The client and server exchange application messages over that connection.

11.1 Important TCP Concepts

  • TCP connection: A logical transport connection between two endpoints.
  • Client source port: Usually an ephemeral port selected by the client operating system or stack.
  • Server destination port: Normally TCP 502 for Modbus TCP.
  • TCP retransmission: TCP may retransmit lost segments.
  • Connection timeout: The connection may fail or be closed if the endpoint becomes unreachable or a configured timer expires.
  • Application timeout: The Modbus client may stop waiting for a response even while the TCP connection remains established.

These timeout types are not interchangeable. A TCP connection can remain open while an individual Modbus request times out.

12. Example: PLC Reading a VFD Over Modbus TCP

Consider a PLC that must read the output frequency and drive status from a VFD.

System configuration

  • PLC IP: 192.168.10.10
  • VFD IP: 192.168.10.20
  • TCP port: 502
  • Client: PLC
  • Server: VFD
  • Function code: 03 for holding-register reads, if supported by the VFD
  • Register addresses: Obtained from the VFD register map

Communication sequence

  1. The PLC checks its communication configuration and target server address.
  2. The PLC establishes or uses a TCP connection to the VFD.
  3. The PLC sends a Modbus TCP request for the specified register range.
  4. The VFD validates the request.
  5. The VFD returns the requested register values or a Modbus exception.
  6. The PLC associates the response with the transaction and decodes the register values.
  7. The PLC applies the manufacturer's scaling and data-format rules.
  8. The PLC updates the corresponding internal tags.

Example logical data:

Register meaning Raw value Example scaling Engineering value
Output frequency 253 Raw value × 0.1 25.3 Hz
Motor current 47 Raw value × 0.1 4.7 A
Drive status 3 Device-specific bit map Depends on bit definitions

These values are illustrative only. Real register addresses, scaling factors, and status definitions must come from the actual VFD manual.

13. Modbus TCP Through a Gateway

Some systems use a gateway to connect an Ethernet-based Modbus TCP client to serial Modbus RTU devices.

PLC / SCADA Client
        |
        | Modbus TCP
        ↓
Ethernet Switch
        |
        ↓
Modbus TCP-to-RTU Gateway
        |
        | Modbus RTU over RS-485
        ↓
    +---+---+---+
    |   |   |   |
  Slave 1  Slave 2  Slave 3

In this arrangement:

  • The client communicates with the gateway over Ethernet.
  • The gateway converts or forwards the Modbus request to the serial network.
  • The Unit Identifier can be used to identify the intended downstream serial device, depending on the gateway implementation.
  • The gateway returns the resulting response to the TCP client.

The Unit Identifier is not necessarily the same as the gateway's IP address. It serves a different purpose.

Some native Modbus TCP devices ignore the Unit Identifier or use a fixed value. Other devices and gateways rely on it. Confirm the behavior in the relevant device documentation.

14. Common Modbus TCP Faults

Symptom Potential cause Diagnostic direction
Server cannot be reached Incorrect IP, subnet, routing, cable, or power Check Ethernet link, IP settings, and network path
Ping works but Modbus fails TCP port blocked, service disabled, wrong port, server limit Test TCP connectivity and server diagnostics
TCP connection succeeds but requests fail Unsupported function, invalid register, malformed request Check function code, address, and request parameters
All registers return errors Wrong server, incorrect address convention, incompatible request Confirm IP and register map
One register range fails Unsupported or restricted register range Verify supported addresses and access permissions
Values are incorrect Scaling, signedness, byte order, or word order Decode against the register map
Intermittent communication Network congestion, unstable link, overloaded server, application timing Inspect switch counters, device load, and timeout logs
Connection repeatedly closes Server policy, connection limit, idle timeout, network interruption Check server settings and TCP diagnostics
Gateway reaches Ethernet but serial devices fail RTU-side wiring, serial settings, address, termination, or gateway mapping Troubleshoot the downstream serial network
Read works but write fails Read-only register, write protection, unsupported write function Check register permissions and device configuration

15. Security and Industrial Network Considerations

Standard Modbus TCP does not inherently provide modern application-level authentication or encryption. A reachable server may therefore expose data or control operations to unauthorized clients if the network is poorly protected.

Industrial deployment should include:

  • Network segmentation between control systems and less-trusted networks.
  • Firewall rules limiting access to approved clients and server ports.
  • Restriction of unnecessary remote access.
  • Controlled engineering access and change management.
  • Monitoring for unexpected Modbus requests.
  • Device-specific security controls where supported.
  • Validation of write access and control authority.

Do not expose port 502 directly to the public internet. Remote access should use an approved secure architecture, such as properly managed VPN access and controlled industrial network boundaries.

Modbus TCP communication should not be treated as a safety-rated communication mechanism unless the specific system and protocol implementation have been designed and certified for that purpose.

16. Maintenance and Diagnostic Checklist

When a Modbus TCP device fails to communicate, work through this checklist.

  • Verify that the server is powered and the Ethernet link is active.
  • Confirm the target IP address and TCP port.
  • Verify subnet mask and routing configuration.
  • Check for duplicate IP addresses.
  • Confirm that the Modbus TCP service is enabled.
  • Check that TCP port 502 is permitted along the network path.
  • Establish whether the TCP connection succeeds.
  • Confirm that the client sends a valid request.
  • Check the function code and register address.
  • Verify the Unit Identifier when the device or gateway uses it.
  • Inspect the response, including any exception code.
  • Validate register offsets, data types, byte order, word order, and scaling.
  • Check connection limits, polling load, and application timeouts.
  • Record the root cause and the final verified configuration.

17. Interview Questions and Answers

Q1. What is Modbus TCP?

Modbus TCP is an implementation of the Modbus application protocol over TCP/IP networks, commonly using Ethernet and TCP port 502.

Q2. What is the difference between Modbus TCP and Modbus RTU?

Modbus RTU commonly communicates over serial interfaces and uses RTU framing with CRC. Modbus TCP carries Modbus messages over TCP/IP and uses the MBAP header without the RTU CRC field.

Q3. What is the default Modbus TCP port?

TCP port 502.

Q4. What is the difference between a client and a server?

The client initiates Modbus requests. The server listens for requests, processes supported operations, and returns responses.

Q5. What is the MBAP header?

It is the seven-byte Modbus TCP header containing the Transaction Identifier, Protocol Identifier, Length, and Unit Identifier.

Q6. Why does Modbus TCP need a Length field?

TCP delivers an ordered byte stream, not guaranteed one-message-per-read packets. The MBAP Length field allows software to identify the complete Modbus message.

Q7. Is the Unit Identifier the same as the IP address?

No. The IP address identifies the network endpoint. The Unit Identifier identifies a logical unit or downstream serial device where applicable.

Q8. Can ping succeed while Modbus TCP fails?

Yes. Ping checks ICMP reachability, while Modbus TCP requires a working TCP connection and a functioning Modbus service that accepts the request.

Q9. Does Modbus TCP automatically define register scaling?

No. The device register map defines the meaning, format, scaling, and access permissions of its data.

Q10. Does Modbus TCP guarantee that a machine command is safe?

No. Modbus TCP transports requests and responses. Machine safety must be provided by the machine's appropriate safety architecture and control design.

18. Practical Exercises

  • Draw the communication architecture for a PLC reading an energy meter using Modbus TCP.
  • Identify the client, server, IP addresses, TCP port, and relevant register map.
  • Explain the purpose of each MBAP header field.
  • Compare Modbus RTU and Modbus TCP frame structures.
  • Identify function codes 01, 02, 03, 04, 05, 06, 0F, and 10.
  • Determine whether a device's manual uses zero-based offsets or displayed reference addresses.
  • Explain why a successful ping does not prove that Modbus TCP requests will succeed.
  • Trace a Modbus TCP request from a PLC to a native TCP server and then through a TCP-to-RTU gateway.
  • Create a diagnostic record separating Ethernet connectivity, TCP connection, Modbus request validity, and register decoding.

19. Final Mental Model

Modbus TCP is easiest to understand as three cooperating layers:

  1. Ethernet and IP provide network connectivity and endpoint addressing.
  2. TCP provides a reliable ordered transport connection, normally to port 502.
  3. Modbus defines the requested operation, data address, quantity, and response.

A healthy Ethernet link does not prove that TCP port 502 is available. A successful TCP connection does not prove that a register request is valid. A valid Modbus response does not guarantee that the returned value has been decoded correctly.

Keep those distinctions clear, and troubleshooting becomes a structured engineering process rather than a ritual of restarting devices.
