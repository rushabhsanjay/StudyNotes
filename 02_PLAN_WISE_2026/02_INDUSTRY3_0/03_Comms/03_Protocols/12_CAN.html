Controller Area Network (CAN)

1. Introduction to CAN

Controller Area Network (CAN) is a serial communication protocol designed to allow electronic control units (ECUs) and embedded devices to exchange information over a shared communication bus without requiring a dedicated communication wire between every pair of devices.

CAN was originally developed by Bosch for automotive applications. It is now widely used in vehicles, industrial equipment, mobile machinery, drives, sensors, embedded controllers and machine subsystems.

In industrial maintenance, CAN is relevant when troubleshooting communication between electronic control units, motor controllers, embedded devices, sensors, and higher-level networks such as CANopen or DeviceNet.

CAN is the underlying communication technology. CANopen and DeviceNet are higher-level communication systems built on CAN. They define additional rules for device identity, data organization, network management and application behavior.

1.1 Why CAN was developed

A system with many electronic controllers can become complicated if every controller requires separate point-to-point communication wiring.

CAN addresses this by providing:

  • A shared communication bus.
  • Message-based communication rather than communication addressed only to a particular receiver.
  • Arbitration that allows multiple nodes to request bus access.
  • Error detection and fault confinement.
  • Real-time communication suitable for embedded control.
  • Reduced wiring complexity compared with extensive point-to-point connections.

1.2 Typical applications

  • Automotive engine, transmission, braking and body controllers.
  • Industrial motor controllers and embedded drives.
  • Mobile hydraulic machinery and off-highway vehicles.
  • Battery management systems and energy equipment.
  • Electronic sensors and distributed embedded controllers.
  • CANopen-based industrial motion and automation devices.
  • DeviceNet industrial I/O and automation equipment.

CAN is not inherently an Ethernet protocol. It uses its own physical signaling and frame format.

2. CAN Architecture

A typical CAN network connects multiple nodes to the same bus.

                 CAN Bus
  120 Ω ─────── CAN_H / CAN_L ─────── 120 Ω
                 |       |
              Node 1   Node 2
                 |       |
              Node 3   Node 4

The drawing is conceptual. In a real installation, the bus is a continuous trunk with nodes connected through short stubs, and termination resistors are fitted at the two physical ends.

2.1 Main components

Component Function
CAN controller Implements CAN protocol logic, frame handling, arbitration and error detection
CAN transceiver Converts controller logic signals into differential CAN bus signals and back
Microcontroller or processor Executes the device application and supplies or consumes CAN data
CAN_H One conductor of the differential bus
CAN_L The other conductor of the differential bus
Twisted-pair cable Carries differential signals and improves noise immunity
Termination resistors Reduce signal reflections at the two ends of the bus
Connectors and stubs Connect nodes to the main bus
Power supply Powers each node and its interface electronics

The CAN controller and transceiver may be integrated into a single device or implemented as separate components.

2.2 CAN controller versus CAN transceiver

These are different components, and confusing them can waste a considerable amount of troubleshooting time.

  • CAN controller: Handles protocol functions such as frame construction, arbitration, acknowledgment, error checking and message filtering.
  • CAN transceiver: Handles the electrical interface between the controller and the physical bus.

A controller may generate correct CAN data internally while a damaged transceiver prevents that data from reaching the bus.

Similarly, a healthy transceiver cannot compensate for an incorrectly configured controller.

3. CAN Physical Layer

The most common conventional CAN physical layer uses a two-wire differential bus, typically called high-speed CAN or ISO 11898-2 CAN.

3.1 Differential signaling

CAN uses the voltage difference between CAN_H and CAN_L to represent bus states. This helps reject electrical noise that affects both conductors similarly.

The two principal bus states are:

  • Dominant: Represents logical 0.
  • Recessive: Represents logical 1.

A dominant bit overrides a recessive bit on the shared bus. This electrical behavior is fundamental to CAN arbitration.

For conventional high-speed CAN, typical nominal values are:

Parameter Typical value
Recessive CAN_H Approximately 2.5 V
Recessive CAN_L Approximately 2.5 V
Dominant CAN_H Approximately 3.5 V
Dominant CAN_L Approximately 1.5 V
Dominant differential voltage Approximately 2 V
Nominal termination 120 Ω at each physical bus end

These are representative values, not universal acceptance limits. Actual voltages depend on the transceiver, network loading, measurement reference and operating conditions. Consult the applicable device and physical-layer specifications before diagnosing a borderline reading.

3.2 CAN_H and CAN_L wiring

Correct polarity is essential.

  • CAN_H connects to CAN_H.
  • CAN_L connects to CAN_L.
  • The bus topology and termination must match the network specification.
  • Shielding and grounding must follow the equipment manufacturer's requirements.

Reversed CAN_H and CAN_L conductors commonly prevent reliable communication.

Do not assume that all connectors use the same pin assignments. Verify the pinout from the actual device documentation.

3.3 Cable topology

High-speed CAN normally uses a linear bus with short stubs.

120 Ω                                          120 Ω
  |                                                |
  +────── Main trunk cable ───────────────────────+
           |              |              |
         Node 1         Node 2         Node 3

A star-shaped layout with long branches can create signal reflections and degrade communication.

Important physical-layer practices include:

  • Use cable suitable for the specified CAN physical layer.
  • Keep stubs short.
  • Avoid unnecessary branches.
  • Fit termination only at the two physical ends of a conventional terminated bus.
  • Keep cable lengths within the limits for the selected bit rate.
  • Route communication wiring appropriately around high-noise equipment.

Other CAN physical layers exist, including low-speed fault-tolerant CAN. Their wiring and termination rules may differ from high-speed CAN.

4. CAN Termination

Termination reduces signal reflections caused by impedance discontinuities at the ends of the transmission line.

For a conventional high-speed CAN bus, the standard arrangement is one 120 Ω resistor at each physical end.

The equivalent resistance measured across CAN_H and CAN_L with the network powered down is approximately:

\[ R\_{\text{measured}} = 120 \parallel 120 \]
\[ R\_{\text{measured}} = \frac{120 \times 120}{120 + 120} = 60\ \Omega \]

Therefore, approximately 60 Ω is a common expected measurement for a correctly terminated high-speed CAN network containing two 120 Ω end resistors.

4.1 Interpreting resistance measurements

Resistance across CAN_H and CAN_L Possible interpretation
Approximately 60 Ω Two 120 Ω terminations may be present
Approximately 120 Ω Only one 120 Ω termination may be present
Very high or open circuit Termination missing, broken wiring or open bus
Significantly below 60 Ω Extra termination, short circuit or another loading condition
Unstable or unexpected value Connected electronics, wiring fault or measurement conditions affecting the reading

These readings are diagnostic clues, not definitive proof. Disconnecting devices, built-in termination switches, split termination networks and other circuit arrangements can affect the measurement.

4.2 Safe termination checks

  1. Follow the equipment's isolation procedure.
  2. Power down the network as required by the manufacturer.
  3. Confirm that the meter and test points are suitable.
  4. Measure across CAN_H and CAN_L.
  5. Compare the result with the network design.
  6. Identify the physical termination points before adding or removing resistors.
  7. Restore the approved configuration and validate communication.

Never add a third termination resistor simply because the network appears unreliable. More termination is not automatically better.

5. CAN Data Rates and Cable Length

CAN bit rate and cable length are interdependent. Higher bit rates generally require shorter network lengths because signal propagation and timing margins become more restrictive.

Common classic CAN bit rates include:

  • 125 kbit/s
  • 250 kbit/s
  • 500 kbit/s
  • 1 Mbit/s

These are common configurations, not a guarantee that every CAN device supports all of them.

Approximate engineering examples for conventional high-speed CAN include:

Bit rate Illustrative bus length
1 Mbit/s Up to approximately 40 m
500 kbit/s Up to approximately 100 m
250 kbit/s Up to approximately 250 m
125 kbit/s Up to approximately 500 m

These are approximate reference values, not universal maximums. The achievable length depends on the transceivers, cable characteristics, node count, stub lengths, propagation delay and system timing requirements. Use the applicable standard and device specifications for final design.

5.1 Why bit-rate mismatches cause faults

All nodes communicating on a conventional CAN segment must use compatible communication timing.

If one node is configured for 250 kbit/s while the rest use 500 kbit/s, that node will generally fail to decode frames correctly and may generate error frames.

Typical symptoms include:

  • No valid communication.
  • Repeated error frames.
  • Increasing error counters.
  • Nodes entering a bus-off state.
  • Intermittent operation when settings are changed or power is cycled.

A healthy electrical connection does not compensate for an incorrect bit rate.

6. CAN Frame Structure

CAN is message-oriented. A transmitted frame carries an identifier and data rather than simply addressing one specific receiver.

In classic CAN, the principal frame fields include:

  • Start of frame.
  • Arbitration field.
  • Control field.
  • Data field.
  • Cyclic redundancy check (CRC).
  • Acknowledgment field.
  • End of frame.

6.1 Standard and extended identifiers

Classic CAN supports two main identifier formats.

Format Identifier width Number of possible identifiers
Standard CAN 11 bits 2,048
Extended CAN 29 bits 536,870,912

The identifier is not necessarily a unique device address. Its meaning depends on the application protocol and network design.

In conventional CAN arbitration, a numerically lower identifier has higher priority because its bit pattern wins arbitration earlier when competing messages differ.

6.2 Classic CAN data length

Classic CAN supports up to 8 data bytes per data frame.

For example:

CAN ID: 0x180
DLC:    8
Data:   11 22 33 44 55 66 77 88

This example shows a frame with an identifier, a data length of eight bytes and eight payload bytes. The actual interpretation of those bytes depends on the application protocol.

A CAN analyzer may display identifiers in hexadecimal, but the displayed identifier alone does not tell you the engineering meaning of the payload.

6.3 CAN FD distinction

CAN FD (Flexible Data-Rate) extends CAN with a larger data payload and the ability to use a faster data phase where supported.

Classic CAN and CAN FD should not be treated as interchangeable. All nodes and controllers involved must support compatible frame formats and operating modes.

A classic CAN controller may not accept CAN FD frames. Verify the hardware, controller configuration and protocol requirements before diagnosing a mixed network.

7. Arbitration and Message Priority

Multiple CAN nodes can attempt to transmit at the same time. CAN uses nondestructive bitwise arbitration to determine which message continues.

A dominant bit overrides a recessive bit. A transmitting node monitors the bus while transmitting. If it transmits recessive but observes dominant at an arbitration position, it withdraws from arbitration and retries later.

The winning message is not corrupted merely because multiple nodes attempted to transmit.

7.1 Example

Suppose two nodes attempt to transmit:

Node A identifier: 0x100
Node B identifier: 0x200

Under conventional CAN arbitration, Node A has higher priority because its identifier is numerically lower.

Node B loses arbitration, stops transmitting its frame and retries when the bus becomes available.

7.2 Why arbitration matters in industry

  • Critical messages can receive higher priority.
  • Multiple controllers can share the bus without a central token-passing mechanism.
  • High-priority traffic can be delivered predictably when the network is correctly engineered.
  • Excessive high-priority traffic can delay lower-priority messages.
  • Poor message scheduling can cause deadline violations even when the physical network is healthy.

CAN is not automatically deterministic in every application. Worst-case message latency depends on bit rate, message priorities, bus load, frame lengths, error recovery and retransmissions.

8. CAN Communication Model

CAN itself does not prescribe one universal device-addressing or application-data model. It provides the data-link and physical communication mechanisms, while higher-level protocols define how the data is organized and interpreted.

A CAN message is generally available to all nodes on the segment. Nodes use identifiers, acceptance filters and application rules to determine which messages matter to them.

8.1 Producer and consumer behavior

A node produces a message, and one or more other nodes may consume it.

For example:

  • A temperature controller publishes a measured value.
  • A motor controller receives a command or status message.
  • A diagnostic tool listens for selected identifiers.
  • Several devices may monitor the same broadcast message.

This shared-bus model reduces the need for separate point-to-point connections, but the message identifier and payload must be understood consistently by the participating devices.

8.2 CAN identifier versus IP address

Property CAN identifier IP address
Primary role Identifies a message and its arbitration priority Identifies a network interface at the IP layer
Typical width 11 or 29 bits for classic CAN 32 bits for IPv4
Device addressing Not inherently a unique node address Identifies an IP endpoint or interface within its addressing context
Priority Built into conventional CAN arbitration Not inherently determined by IPv4 address
Payload interpretation Defined by the application or higher-level protocol Defined by the transport and application protocols

Do not interpret a CAN identifier as if it were an IP address or a universal device number.

9. Error Detection and Fault Confinement

CAN includes several mechanisms to detect transmission errors and limit the impact of faulty nodes.

Important error-detection mechanisms include:

  • Bit monitoring.
  • Bit stuffing checks.
  • Frame format checks.
  • CRC checks.
  • Acknowledgment checks.

9.1 Bit monitoring

A transmitting node monitors the bus to verify that the observed bus state is consistent with the transmitted bit, except where protocol rules permit otherwise.

A mismatch can indicate a transmission error or another protocol-related condition.

9.2 Bit stuffing

In conventional CAN frame encoding, bit stuffing helps maintain synchronization. After five consecutive bits of the same polarity in the relevant frame region, the transmitter inserts a bit of the opposite polarity.

Receivers check for compliance with the stuffing rules. A violation can trigger an error.

9.3 CRC

The CRC provides error detection for the transmitted frame. The receiver checks the calculated CRC against the transmitted value.

A CRC error indicates that the received frame failed the integrity check. Possible causes include electrical noise, signal-integrity problems or other transmission disturbances.

9.4 Acknowledgment

A receiving node that correctly receives a frame can acknowledge it by asserting the acknowledgment bit.

If the transmitter does not observe the expected acknowledgment, it may detect an ACK error and retransmit the frame.

An ACK does not necessarily mean that the intended application processed the message. It indicates acknowledgment at the CAN protocol level.

9.5 Error frames and retransmission

When a node detects certain protocol errors, it can transmit an error frame. The affected transmission may then be retried according to CAN protocol behavior.

Repeated errors can consume bus capacity and interfere with timely delivery, even when some messages continue to get through.

10. Error Counters and Bus-Off

CAN controllers commonly maintain transmit and receive error counters. These counters contribute to error-active, error-passive and bus-off behavior.

10.1 Error-active

An error-active node participates normally and can signal detected errors using active error flags.

10.2 Error-passive

A node becomes error-passive when its error counters exceed specified thresholds. It can continue communicating under the protocol's error-passive restrictions.

Error-passive behavior is an important warning that the node has experienced substantial communication errors.

10.3 Bus-off

A node enters bus-off when its transmit error counter reaches the protocol-defined bus-off threshold.

A bus-off node stops participating in ordinary CAN bus communication until recovery conditions are satisfied.

Common underlying causes include:

  • Incorrect bit rate or timing.
  • Missing or incorrect termination.
  • Reversed CAN_H and CAN_L wiring.
  • Shorted bus conductors.
  • Poor grounding or electrical noise.
  • Faulty transceiver.
  • A disconnected or incorrectly configured network.
  • Another node or physical-layer problem that prevents successful transmission.

Bus-off is a state, not a root cause. Resetting the node may restore communication temporarily without correcting the actual problem.

Recovery behavior depends on the CAN controller, firmware and application configuration. Follow the device manufacturer's specified recovery procedure.

11. CAN Network Commissioning

A CAN network should be commissioned using a known topology, verified bit rate, correct termination and documented device configuration.

11.1 Pre-commissioning checklist

  • Identify the physical CAN variant and applicable standard.
  • Confirm supported bit rates for all nodes.
  • Confirm CAN_H and CAN_L pin assignments.
  • Verify the cable type and bus topology.
  • Confirm the two physical termination points where required.
  • Check stub lengths and overall bus length.
  • Verify node power and transceiver supply.
  • Confirm that controller timing settings are compatible.
  • Verify device configuration and application-protocol settings.
  • Record the original configuration and network layout.

11.2 First communication test

A controlled commissioning sequence is:

  1. Verify wiring and termination while the network is safely isolated as required.
  2. Confirm that the installed nodes use the intended bit rate.
  3. Power up the system using the approved procedure.
  4. Check controller and transceiver status indicators.
  5. Use a suitable CAN analyzer or diagnostic tool to observe traffic.
  6. Confirm that expected identifiers and payloads appear.
  7. Review error counters and bus-off indications.
  8. Validate application behavior against the system design.

A network showing traffic is not necessarily healthy. Verify that the required messages are present, timely and error-free enough for the application's requirements.

12. CAN Troubleshooting in Industrial Maintenance

Troubleshooting should distinguish electrical faults from configuration errors and application-level problems.

12.1 Symptom-to-cause matrix

Symptom Possible cause Recommended check
No communication on any node Missing power, open bus, wrong bit rate or wiring fault Verify power, topology, transceiver status and bit rate
One node is missing Node power, branch wiring, transceiver or configuration issue Check the individual node and its stub
Repeated CRC or frame errors Noise, signal integrity or timing problem Inspect wiring, termination, routing and timing
Several nodes enter error states Shared bus fault, wrong bit rate or major physical-layer problem Check common wiring, termination and controller settings
Node enters bus-off Excessive transmit errors Inspect error counters and physical-layer conditions before recovery
Communication fails after adding a node Incorrect wiring, extra termination, incompatible timing or excessive loading Review the new branch, termination and network design
Communication works at a lower bit rate only Marginal signal integrity, excessive length or timing mismatch Verify cable, topology, timing and transceiver specifications
Data is received but interpreted incorrectly Wrong identifier mapping, payload definition or byte order Verify the application protocol and data interpretation
Fault appears after replacing a controller Configuration, bit rate, timing or hardware compatibility issue Compare the old and replacement device settings

12.2 Practical diagnostic sequence

Step 1: Determine the scope.

Establish whether the fault affects the entire bus, one node, one branch or only one message.

Step 2: Check physical wiring.

Inspect connectors, polarity, cable damage, grounding and termination.

Step 3: Verify communication settings.

Confirm bit rate, timing parameters, frame format and any controller-specific configuration.

Step 4: Observe bus traffic.

Use an appropriate CAN analyzer or controller diagnostics to inspect identifiers, message frequency, errors and bus activity.

Step 5: Check controller error counters.

Determine whether a node is error-active, error-passive or bus-off, where the controller exposes these states.

Step 6: Isolate the cause under an approved procedure.

Use an authorized test bench or controlled maintenance window to investigate suspect cables, transceivers or nodes. Avoid disconnecting random devices from an operating machine.

Step 7: Validate the repair.

Confirm that expected messages are present, communication errors have stopped or returned to acceptable levels, and the application functions correctly.

13. CAN Analyzer and Diagnostic Tools

A CAN analyzer captures and decodes bus traffic. Depending on the tool, it may display timestamps, identifiers, data bytes, error frames, bus load and error statistics.

Typical tool categories include:

  • USB-to-CAN interfaces.
  • CAN protocol analyzers.
  • Oscilloscopes with suitable differential probes.
  • CAN controller diagnostic registers.
  • Vendor-specific commissioning and diagnostic software.
  • Embedded development tools that expose CAN controller status.

13.1 What to inspect in a trace

  • Identifier and frame format.
  • Data length and payload.
  • Message frequency.
  • Unexpected gaps in periodic messages.
  • Error frames and retransmissions.
  • Sudden changes in bus load.
  • Whether the expected sender is publishing the message.
  • Whether the received payload changes in a way consistent with the application.

A trace is only useful when interpreted against the network's expected behavior. Seeing an identifier repeatedly does not prove that its payload is correct.

13.2 Oscilloscope use

An oscilloscope can help identify:

  • Differential signal amplitude.
  • Distorted edges.
  • Reflections.
  • Noise and ringing.
  • Abnormal common-mode voltage.
  • Physical-layer problems that a software trace cannot fully explain.

Use probes, grounding arrangements and measurement procedures appropriate for the system. Incorrect probing can introduce misleading results or create electrical hazards.

14. CAN Versus CANopen and DeviceNet

CAN, CANopen and DeviceNet are related but distinct technologies.

Feature CAN CANopen DeviceNet
Main role Communication protocol and physical/data-link foundation Higher-level industrial communication protocol Higher-level industrial automation network
Foundation CAN physical and data-link mechanisms Commonly based on classic CAN Based on CAN
Device model No single universal application object model Object dictionary and standardized communication mechanisms Defined industrial device and connection model
Network management Defined by the selected CAN implementation and application Includes standardized network-management mechanisms Includes defined network and connection behavior
Typical use Embedded controllers and custom communication systems Drives, motion, sensors and industrial embedded devices Industrial I/O and automation devices
Configuration Application-specific unless a higher-level protocol defines more Device profiles, object dictionary and communication parameters Device configuration and EDS-based integration are common

CAN is the underlying technology in these systems, but learning CAN alone does not teach all the configuration and application rules of CANopen or DeviceNet.

CANopen is the next topic in this study sequence.

15. Common Misconceptions

Misconception 1: CAN is the same as CANopen.

CAN provides the underlying communication mechanisms. CANopen defines additional communication and device behavior.

Misconception 2: A CAN identifier is a device address.

A CAN identifier primarily identifies a message and participates in arbitration. Higher-level protocols may assign specific meanings to identifiers.

Misconception 3: Every CAN network requires exactly 60 Ω.

Approximately 60 Ω is a common unpowered measurement for a conventional high-speed CAN network with two 120 Ω terminations. Other physical layers and termination designs can differ.

Misconception 4: Bus-off means the controller is defective.

Bus-off indicates that the controller has reached a protocol-defined error condition. The underlying cause may be wiring, timing, noise, termination or another network fault.

Misconception 5: More termination resistors improve reliability.

Incorrect termination can degrade signal quality. Conventional high-speed CAN normally requires termination at the two physical ends, not at every node.

Misconception 6: Seeing CAN traffic proves the network is healthy.

The traffic may contain errors, missing messages, incorrect payloads or timing violations. Health must be assessed against the application's communication requirements.

16. Interview Questions and Answers

Q1. What is CAN?

CAN is a serial, message-oriented communication protocol that allows multiple electronic controllers to communicate over a shared bus.

Q2. Why does CAN use differential signaling?

Differential signaling improves noise immunity by interpreting the voltage difference between CAN_H and CAN_L rather than relying on one conductor's voltage alone.

Q3. What are dominant and recessive states?

They are the two bus states used by CAN. A dominant bit represents logical 0 and overrides a recessive bit, which represents logical 1.

Q4. Why is CAN arbitration called nondestructive?

Competing nodes resolve access based on identifier priority. Nodes that lose arbitration withdraw without corrupting the winning message.

Q5. Why are two 120 Ω resistors used in conventional high-speed CAN?

They terminate the physical bus at its two ends. Measured in parallel, they produce approximately 60 Ω across CAN_H and CAN_L when the network is appropriately powered down and isolated for measurement.

Q6. What is the difference between CAN controller and CAN transceiver?

The controller implements the communication protocol. The transceiver converts between the controller's logic signals and the electrical bus signals.

Q7. What causes a CAN bus-off condition?

A controller enters bus-off after its transmit error counter reaches the protocol-defined threshold. Incorrect timing, wiring faults, noise, transceiver faults or other communication problems can cause the underlying errors.

Q8. What is the difference between standard and extended CAN identifiers?

Standard identifiers are 11 bits wide, while extended identifiers are 29 bits wide.

Q9. What is the maximum classic CAN payload?

Classic CAN supports up to 8 data bytes per frame. CAN FD supports larger payloads when the controller and network support it.

Q10. How would you troubleshoot a CAN network with no communication?

I would verify power, physical wiring, CAN_H/CAN_L polarity, termination, bit rate and timing, then inspect controller status and bus traffic with suitable diagnostic tools.

Q11. Does an ACK mean that the receiving application accepted the data?

No. An ACK indicates acknowledgment at the CAN protocol level. It does not prove that the application processed the message correctly.

Q12. What is the difference between CAN and Ethernet?

CAN uses a shared bus with CAN-specific framing and arbitration. Ethernet uses different physical and data-link mechanisms and commonly carries IP-based communication in industrial networks.

17. Practical Exercises

Perform these exercises on a training bench or an authorized non-production network.

  • Exercise 1: Identify the CAN controller, transceiver, connector and bus conductors on a development board or industrial device.
  • Exercise 2: Draw a linear CAN bus and mark the two physical termination points.
  • Exercise 3: Calculate the equivalent resistance of two 120 Ω termination resistors connected in parallel.
  • Exercise 4: Read a CAN trace and identify standard versus extended identifiers.
  • Exercise 5: Interpret the identifier, data length and payload of a classic CAN frame.
  • Exercise 6: Compare communication traces at two supported bit rates using a controlled test setup.
  • Exercise 7: Inspect a CAN controller's error counters and identify error-active, error-passive and bus-off states where available.
  • Exercise 8: Prepare a troubleshooting report for a simulated communication fault, including symptoms, measurements, verified cause and corrective action.

18. Final Mental Model

Remember the relationship between the layers:

  • Physical layer: CAN_H, CAN_L, transceivers, cable, topology and termination.
  • Data-link layer: Frame format, identifiers, arbitration, CRC, acknowledgment and error handling.
  • Controller behavior: Bit timing, message filtering, error counters and bus-off handling.
  • Higher-level protocol: Device identity, data meaning, network management and application-specific behavior.
  • Application: Correct values, update rates, control decisions and machine behavior.

When a CAN network fails, start with the physical bus and communication timing, then inspect controller diagnostics and decoded traffic. Finally, verify the higher-level protocol and application data. This separation makes faults easier to isolate and prevents configuration changes from being mistaken for root-cause fixes.
