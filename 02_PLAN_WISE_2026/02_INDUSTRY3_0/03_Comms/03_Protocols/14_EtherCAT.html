1. What Is EtherCAT?

EtherCAT (Ethernet for Control Automation Technology) is a real-time industrial Ethernet communication technology designed for fast, deterministic communication between a controller and distributed automation devices.

It is commonly used in:

  • Servo drives and coordinated motion-control systems.
  • High-speed digital and analog I/O.
  • Robotics and machine automation.
  • Packaging, assembly, and production machinery.
  • Precision synchronization between multiple axes.
  • Industrial systems that need predictable cyclic data exchange.

EtherCAT was developed by Beckhoff and is standardized and maintained through the EtherCAT Technology Group (ETG).

Its key innovation is processing Ethernet frames on the fly. Instead of every device receiving a complete frame, processing it independently, and then sending a new frame, EtherCAT slaves can read or insert their assigned data while the frame passes through them.

2. The Core Operating Principle

In a conventional communication arrangement, a controller may send a request to a device and wait for the device to process and respond. EtherCAT uses a more efficient approach for cyclic process data.

The master sends a frame through the EtherCAT network. Each slave processes the relevant portion of that frame as it passes through the device, and the frame returns to the master with the collected input data.

EtherCAT Master
      |
      | Ethernet frame with output data
      v
   Slave 1  ---> Reads assigned output data
      |
      v
   Slave 2  ---> Inserts its input data
      |
      v
   Slave 3  ---> Reads outputs and inserts inputs
      |
      v
   Slave 4
      |
      v
 Frame returns to the master with input data

The arrows illustrate a logical example. Actual frame paths depend on the physical topology and device ports.

Why processing on the fly matters

  • The master can exchange data with multiple devices using efficient cyclic frames.
  • Each slave accesses only its assigned data fields.
  • Communication overhead is reduced compared with repeatedly addressing each device through separate request-response transactions.
  • Distributed clocks can synchronize devices very precisely.
  • Predictable cyclic communication supports demanding motion-control applications.

EtherCAT is still based on Ethernet technology, but it does not operate like ordinary office Ethernet with a conventional TCP/IP transaction between the controller and every field device.

4. EtherCAT Versus Ordinary Ethernet

Feature Ordinary Ethernet network EtherCAT network
Main purpose General data communication Deterministic industrial control
Typical communication Ethernet frames carrying protocols such as IP, TCP, or UDP EtherCAT-specific frames for cyclic process data
Intermediate device behavior Switches typically receive and forward frames Slaves can process relevant data while frames pass through
Timing Depends on network load, architecture, and protocol Designed for predictable cyclic communication
Typical field devices PCs, printers, servers, network cameras EtherCAT I/O, servo drives, encoders
Network equipment Standard Ethernet switches are common Standard slave paths use EtherCAT-capable ports and supported topologies
Synchronization Depends on the protocols and equipment used Distributed clocks are a core capability
Configuration IP addresses and higher-level network settings are common Master configuration, slave identity, process data, states, and timing are central

EtherCAT is not simply another name for EtherNet/IP. EtherNet/IP uses standard Ethernet and IP networking, commonly with CIP over TCP and UDP. EtherCAT has its own frame-processing mechanism for real-time control.

5. Physical Network and Topology

EtherCAT commonly uses standard Ethernet physical-layer components, including twisted-pair cabling and suitable connectors. A widely used implementation is 100 Mbit/s full-duplex Ethernet at individual links, though exact physical interfaces depend on the equipment.

Common topology arrangements include:

  • Line: Slaves connected sequentially.
  • Tree: Branching through suitable EtherCAT junctions or devices.
  • Star: Branches connected through an EtherCAT junction or supported multiport device.
  • Ring: A topology that can support cable-redundancy arrangements when the master and devices are designed and configured for it.
Line:
Master → Slave 1 → Slave 2 → Slave 3

Tree:
                 → Slave 2
Master → Junction
                 → Slave 3 → Slave 4

Can an ordinary Ethernet switch be inserted?

Do not assume so. A normal Ethernet switch is not interchangeable with an EtherCAT junction in a conventional EtherCAT slave path. The network must use a topology and components supported by the EtherCAT implementation.

An ordinary switch may be used for a separate engineering, supervisory, or IP network. That does not mean it can be inserted into the real-time EtherCAT path without affecting operation.

Physical-layer checks

  • Confirm the specified cable type and length.
  • Inspect connectors, pin condition, shielding, and cable routing.
  • Check slave port and link/activity indicators.
  • Look for intermittent links caused by vibration or damaged cables.
  • Keep communication wiring separated from high-noise power wiring according to installation requirements.
  • Confirm that the actual cable topology matches the master configuration.

6. EtherCAT Addressing and Frame Processing

EtherCAT supports several addressing methods. The master and engineering environment determine which are appropriate for a particular operation.

Addressing method Purpose
Auto-increment addressing Identifies devices by their position in the EtherCAT traversal sequence during discovery or configuration operations
Configured station addressing Accesses a slave using a configured station address
Logical addressing Accesses a logical process-data region that can map data across multiple slaves
Broadcast addressing Sends a command or access to multiple devices, where supported by the operation

Logical addressing is particularly important for cyclic process data. The master can map a contiguous logical data region onto the relevant memory areas of several slaves. Each slave processes the portions assigned to it.

Working Counter (WKC)

The Working Counter is a critical diagnostic value in EtherCAT. It helps the master verify that the expected devices or memory operations actually processed a datagram.

  • A correct WKC suggests that the expected processing occurred.
  • A lower-than-expected WKC can indicate a missing slave, a configuration mismatch, an unavailable device, or a communication problem.
  • The meaning of a WKC value depends on the datagram command and the expected operations. It is not a universal count of connected slaves.

For example, a WKC mismatch on a cyclic process-data datagram can help narrow the fault to the affected communication segment or configured data access. It does not, by itself, identify the exact failed component.

7. EtherCAT Process Data and Application Protocols

EtherCAT defines the transport and real-time frame-processing mechanism. Additional protocols can provide application-level data models and services.

Process data

Process data is the information exchanged cyclically between the controller and slaves.

Examples include:

  • Digital input states from sensors.
  • Digital output commands to solenoid valves.
  • Analog values from pressure or position sensors.
  • Servo target position, velocity, or torque commands.
  • Actual position, velocity, torque, and drive status.
  • Device status and control words.

The master maps the data to a process image that the PLC or motion application can read and write.

The application usually works with named variables or structured data rather than manually constructing every Ethernet frame.

Important EtherCAT protocols

Protocol Full name Purpose
CoE CAN application protocol over EtherCAT Object dictionary access and CANopen-style device profiles
FoE File access over EtherCAT Transfers files to or from supported devices
EoE Ethernet over EtherCAT Tunnels Ethernet frames through EtherCAT where supported
SoE Servo drive profile over EtherCAT Supports the SERCOS servo-drive profile
AoE ADS over EtherCAT Supports ADS communication through EtherCAT in applicable systems

Do not confuse CoE with CANopen running directly over a physical CAN network. CoE carries CANopen-style application concepts over EtherCAT.

CoE, PDOs, and SDOs

CoE devices may expose an object dictionary containing parameters, status information, and configuration values.

  • PDO (Process Data Object): Cyclic process data mapped for efficient real-time exchange.
  • SDO (Service Data Object): Acyclic access to object-dictionary entries, commonly used for configuration and parameter access.

For example, a servo drive might receive a target position cyclically through mapped process data while a drive parameter is read or changed through an acyclic object-dictionary transaction.

The exact object indices, subindices, PDO mappings, and supported services depend on the device and its profile.

8. EtherCAT Slave States

EtherCAT devices use a defined state machine. The state determines which communication and application functions are permitted.

State Meaning Typical behavior
INIT Initial state Basic initialization; normal mailbox communication is not yet available
PRE-OP Pre-Operational Mailbox communication can be available for configuration, but normal cyclic process data is not active
SAFE-OP Safe-Operational Input process data is generally available; outputs are maintained in the device's defined safe state or configured behavior
OP Operational Normal process-data exchange is active, including output updates where supported and enabled

The normal progression is:

INIT
  ↓
PRE-OP
  ↓
SAFE-OP
  ↓
OP

Some transitions can go through intermediate states or require additional configuration and validation. The master requests state changes, and the slave can reject a transition if requirements are not met.

Why a slave may refuse to reach OP

Common causes include:

  • Incorrect or incomplete PDO configuration.
  • Invalid Sync Manager or FMMU configuration.
  • Missing required startup parameters.
  • Process-data watchdog or synchronization problems.
  • Incorrect distributed-clock configuration.
  • Unsupported configuration from the master.
  • Device-specific application or hardware faults.

A slave that remains in SAFE-OP is not necessarily physically defective. Its diagnostic status and AL status code should be checked before replacing hardware.

Application Layer (AL) status codes

The EtherCAT Application Layer provides status and error information associated with state transitions and configuration. The exact AL status code and any additional status information should be captured from the engineering tool or master diagnostics.

Record the code before resetting or repeatedly cycling power. An intermittent fault that disappears after a reset is still a fault, just one that has learned to hide when maintenance arrives.

9. Distributed Clocks and Motion Synchronization

Distributed Clocks (DC) synchronize the local clocks of supported EtherCAT devices. A configured reference clock provides a timing reference, and other devices synchronize to it.

This is especially useful when multiple devices must act at coordinated times.

Examples:

  • Multiple servo axes following a coordinated motion profile.
  • Synchronized sampling of sensors.
  • Consistent timing between drive commands and feedback.
  • Applications requiring low timing variation between devices.

Key terms

  • Reference clock: The clock selected as the synchronization reference.
  • Sync signal: A timing event generated or used by a device for synchronized operations.
  • Jitter: Variation in the timing of an event from its intended time.
  • Cycle time: The interval between successive cyclic communication or application updates.
  • Synchronization error: The difference between the actual timing relationship and the configured or expected relationship.

Distributed clocks improve timing coordination, but they do not automatically make every connected device perfectly synchronized. The device must support the required functions, and the master, clock configuration, application cycle, and hardware must be compatible.

If distributed-clock synchronization fails

Check the following:

  1. Whether the relevant slave supports DC.
  2. Whether the correct reference clock is selected.
  3. Whether synchronization parameters match the device's requirements.
  4. Whether the configured cycle time is supported.
  5. Whether the device reports clock, synchronization, or watchdog errors.
  6. Whether the physical network has intermittent links or topology problems.
  7. Whether the application task and EtherCAT cycle are configured consistently.

Do not randomly change cycle time or synchronization parameters on a running production machine. Such changes can affect motion and process timing.

10. ESI Files, ENI Files, and Engineering Configuration

Two configuration artifacts are particularly important in EtherCAT engineering.

Item Meaning Role
ESI EtherCAT Slave Information, typically XML Describes a slave's identity, capabilities, communication options, and supported configurations
ENI EtherCAT Network Information Describes a configured EtherCAT network for masters and tools that use this configuration format

ESI file

The ESI file is generally supplied by the device manufacturer. It helps engineering software identify the slave and determine which features and configuration options are available.

An incorrect, missing, or outdated ESI file can cause device-identification or configuration difficulties. Installing an ESI file does not itself prove that the physical device is compatible or healthy.

ENI file

An ENI file is a network configuration artifact used by compatible master implementations. It can contain information about the configured network, process data, and communication settings.

Not every EtherCAT master uses the same configuration workflow or exposes an ENI file to the user. Some engineering environments manage the equivalent configuration internally.

Common engineering tools

Examples include:

  • Beckhoff TwinCAT.
  • CODESYS-based EtherCAT master environments.
  • Manufacturer-specific PLC, motion-control, and drive engineering software.
  • EtherCAT master diagnostics and network-scanning tools.

Always use the tool and configuration format supported by the actual controller.

11. Commissioning an EtherCAT Network

Commissioning should be systematic. Connecting cables and seeing link LEDs is not proof that cyclic process data is working.

Step 1: Confirm the hardware

  • Verify the controller and its EtherCAT master capability.
  • Confirm that each field device supports EtherCAT.
  • Check device models, firmware, connectors, and supply requirements.
  • Verify the intended topology and cable layout.
  • Confirm the manufacturer's requirements for grounding and shielding.

Step 2: Prepare the engineering environment

  • Install the required engineering software and compatible device descriptions.
  • Confirm that the master software and operating system support the intended NIC or interface.
  • Install the correct ESI files where required.
  • Back up the existing project before making changes.

Step 3: Scan and identify devices

  • Connect the network according to the supported topology.
  • Scan for connected slaves using the engineering tool.
  • Compare discovered devices with the physical machine layout.
  • Confirm device identity, revision, and order where the configuration depends on them.
  • Investigate missing, unexpected, or incorrectly identified devices.

Step 4: Configure process data

  • Select supported input and output mappings.
  • Confirm data sizes and expected variable assignments.
  • Configure required startup parameters and mailbox settings.
  • Check device-specific requirements for PDO assignment and mapping.
  • Verify that PLC variables correspond to the intended physical signals.

Step 5: Configure timing and synchronization

  • Set the intended communication cycle.
  • Configure distributed clocks if required.
  • Check that the master task, slave capabilities, and application timing are compatible.
  • Confirm watchdog behavior and any device-specific timing constraints.

Step 6: Transition to OP

  • Review all configuration and startup errors.
  • Request the expected state transitions.
  • Confirm that each required slave reaches OP.
  • Verify the expected WKC and process-data updates.
  • Check that physical input changes are reflected correctly and output commands operate as designed.

Step 7: Validate the machine

  • Test input and output functions under an approved commissioning procedure.
  • Validate drive feedback and command behavior.
  • Verify coordinated motion and synchronization if applicable.
  • Confirm that alarms and communication-loss reactions work correctly.
  • Record the final configuration and test results.

Production rule: Changes to a live control network must follow the plant's authorization, safety, and change-management process. A configuration scan or state transition can affect real outputs and machine motion.

12. EtherCAT Troubleshooting

Troubleshooting should separate physical-layer faults, configuration faults, timing faults, and application faults. Replacing the slave first and investigating later is an expensive diagnostic philosophy.

Diagnostic sequence

  1. Check the physical network. Inspect link LEDs, cable connections, connectors, power supplies, and the topology.
  2. Identify the first missing or abnormal slave. Compare the discovered network with the expected device order and configuration.
  3. Read the slave state. Identify whether the device is in INIT, PRE-OP, SAFE-OP, or OP.
  4. Capture the AL status code. Use the code and device diagnostics to narrow down the reason for a failed transition.
  5. Check the WKC. Compare the observed value with the expected value for the relevant datagram.
  6. Inspect configuration. Verify the ESI/device revision, process-data mapping, startup parameters, and master configuration.
  7. Inspect timing. Check the cycle time, distributed-clock configuration, synchronization status, and watchdog errors.
  8. Verify the application. Confirm that the correct process-data variables are mapped and that the PLC logic is using them correctly.

Symptom-to-cause table

Symptom Possible causes Recommended checks
No slaves detected Cable disconnected, slave unpowered, wrong master interface, unsupported topology Check power, link LEDs, physical wiring, and selected NIC
One slave missing Failed device, bad cable or port, power fault, topology mismatch Inspect the affected link and compare the physical sequence
Slave stuck in PRE-OP Configuration incomplete, mailbox or startup issue, invalid device setup Read AL status and inspect startup configuration
Slave stuck in SAFE-OP Process-data mismatch, watchdog, synchronization issue, invalid configuration Check AL status, PDO mapping, timing, and device diagnostics
WKC lower than expected Missing slave, incorrect datagram processing, configuration mismatch Compare expected WKC and identify the affected communication operation
Intermittent communication Loose connector, damaged cable, power instability, electrical interference Inspect physical connections and review diagnostic history
Distributed-clock error Incorrect reference clock, unsupported timing, synchronization problem Check DC settings and device-specific requirements
Inputs update but outputs do not Output mapping error, incorrect state, application logic issue, output inhibited by device Verify OP state, process image, mapping, and device status
Device fails after replacement Wrong model or revision, missing device description, parameter mismatch Compare identity, firmware, ESI, and startup parameters
Communication fails after a project change Incorrect network configuration, altered mapping, unsupported settings Compare the current project with the approved backup

Example: A slave remains in SAFE-OP

Suppose an EtherCAT servo drive is detected, but it does not reach OP.

A disciplined investigation would be:

  • Confirm that the drive is powered and its physical link is healthy.
  • Record the exact AL status code and any associated diagnostic text.
  • Compare the configured device identity and revision with the actual drive.
  • Check the process-data mapping and startup parameters.
  • Review the drive's synchronization and watchdog diagnostics.
  • Correct the identified cause and retry the state transition under the approved machine procedure.

Do not conclude that the drive is defective merely because it cannot reach OP.

13. EtherCAT Safety Considerations

Standard EtherCAT communication is not automatically safety-rated. Safety functions require an appropriate safety architecture and compatible, certified components.

FSoE (Fail Safe over EtherCAT) is a safety communication protocol used in suitable safety systems. Its use requires compatible hardware, appropriate safety engineering, and validation against the applicable safety requirements.

Important distinctions:

  • Standard EtherCAT process data is not a substitute for a validated safety function.
  • A normal EtherCAT slave is not automatically a safety device.
  • Emergency stops, guard interlocks, and other safety functions must be implemented and validated using the machine's approved safety design.
  • Communication-loss behavior and output reactions must be verified as part of the safety and risk-assessment process.
  • Safety configuration changes require the prescribed authorization and validation.

Never bypass a safety interlock or force a drive into an operational state simply to clear a communication fault.

15. Maintenance, Backups, and Device Replacement

EtherCAT maintenance should preserve both the physical network and its engineering configuration.

Recommended maintenance records

  • Master/controller model, firmware, and software version.
  • EtherCAT slave inventory, model, revision, and physical location.
  • Approved network topology and device order.
  • ESI files and relevant engineering configuration.
  • Process-data mappings and startup parameters.
  • Cycle-time and distributed-clock settings.
  • Known-good project backup and change history.
  • Communication alarms, WKC anomalies, AL status codes, and corrective actions.
  • Spare-device compatibility and replacement procedures.

Replacing a slave

Before replacement:

  1. Identify the exact device and revision.
  2. Record its current diagnostic state and relevant parameters.
  3. Confirm the approved isolation and machine-safety procedure.
  4. Verify the replacement device's compatibility and configuration requirements.
  5. Restore the required configuration using the approved engineering procedure.
  6. Confirm the expected topology, slave state, WKC, and process-data behavior.
  7. Validate machine functions before returning the equipment to production.

Some devices can recover configuration automatically through supported mechanisms, while others require explicit parameterization. Do not assume that a replacement will work simply because its model number looks similar.

Preventive maintenance checklist

  • Inspect EtherCAT cables, connectors, and routing.
  • Check slave power supplies and status indicators.
  • Review communication and state-transition alarms.
  • Investigate recurring WKC mismatches.
  • Review intermittent link and synchronization faults.
  • Verify configuration backups and revision records.
  • Confirm that spare devices and required device descriptions are available.
  • Document all approved changes and post-maintenance validation.

16. Interview Questions and Answers

1. What is EtherCAT?

EtherCAT is a real-time industrial Ethernet technology designed for deterministic communication between a master and distributed slave devices.

2. What is the main principle behind EtherCAT?

Processing on the fly. Slaves can read or insert assigned data while the Ethernet frame passes through them.

3. What is an EtherCAT master?

The controller or software responsible for network configuration, cyclic communication, process-data exchange, and device-state management.

4. What is an EtherCAT Slave Controller?

The hardware or compliant implementation that handles EtherCAT-specific frame processing and slave communication functions.

5. What is an ESI file?

An XML-based EtherCAT Slave Information file describing a device's identity, capabilities, and supported configuration options.

6. What is the difference between ESI and ENI?

ESI describes a slave device. ENI describes a configured EtherCAT network for master implementations that use that format.

7. What are the EtherCAT states?

INIT, PRE-OP, SAFE-OP, and OP. They control which communication and application functions are available.

8. What is the Working Counter?

The WKC is a value used to verify whether the expected EtherCAT datagram operations were processed. An unexpected value is a diagnostic clue, not a complete fault diagnosis.

9. What are Distributed Clocks?

A mechanism for synchronizing the timing of supported EtherCAT devices, particularly useful for coordinated motion and synchronized sampling.

10. What is CoE?

CAN application protocol over EtherCAT. It provides CANopen-style application concepts and object-dictionary access over EtherCAT.

11. Why might a slave remain in SAFE-OP?

Possible causes include invalid process-data mapping, startup configuration errors, watchdog conditions, or synchronization problems. The AL status code is an important starting point.

12. Is EtherCAT the same as EtherNet/IP?

No. Both use Ethernet physical technology, but they use different communication mechanisms, configuration models, and diagnostics.

13. Can an ordinary Ethernet switch be used anywhere in an EtherCAT network?

Not indiscriminately. Standard EtherCAT slave paths require a supported topology and appropriate devices or junctions. An ordinary switch should not be assumed compatible with the real-time slave path.

14. Does EtherCAT automatically provide functional safety?

No. Safety functions require a suitable safety design and compatible, validated safety technology, such as FSoE where applicable.

15. What should be checked first when EtherCAT communication fails?

Start with physical connectivity and power, then inspect the slave state, AL status, WKC, configuration, and timing diagnostics.

17. Practical Exercises

Use a training rig, simulator, or approved non-production setup.

Exercise 1: Identify the network

  • Identify the EtherCAT master and all slaves.
  • Record the model, revision, and function of each device.
  • Draw the physical topology.
  • Compare the discovered device sequence with the engineering configuration.

Exercise 2: Inspect the process image

  • Identify several input and output variables.
  • Trace each variable from the application to its corresponding device.
  • Verify its data type, mapping, and expected physical behavior.
  • Confirm that the actual signal matches the engineering display.

Exercise 3: Diagnose a state-transition failure

  • Select a documented training fault or use a simulator.
  • Record the affected slave's state and AL status code.
  • Identify the configuration or device requirement involved.
  • Correct the fault and verify the transition to OP.

Exercise 4: Investigate a WKC mismatch

  • Observe the expected and actual WKC in the diagnostic tool.
  • Determine which datagram or process-data operation is affected.
  • Compare the physical topology and configuration.
  • Document the evidence supporting the identified cause.

Exercise 5: Document a replacement procedure

  • Record the device identity and required configuration.
  • Identify the applicable ESI and engineering project versions.
  • Define the required safety and isolation steps.
  • Specify the post-replacement checks for state, WKC, process data, and machine function.

18. Final Mental Model

Remember EtherCAT as five connected concepts:

  1. Master: Controls the network and cyclic communication.
  2. Slaves: Perform I/O, drive, sensing, or other machine functions.
  3. Processing on the fly: Devices access their assigned data while frames pass through.
  4. Distributed clocks: Supported devices can synchronize their timing for coordinated operations.
  5. Diagnostics: Slave states, AL status codes, WKC, link status, configuration, and synchronization data help locate faults.

For industrial maintenance, the practical skill is not merely getting every slave to OP. It is understanding how physical wiring, device configuration, process-data mapping, timing, and application logic combine to produce reliable machine behavior.
