Modbus RTU Basics: Serial Master/Slave Protocol

1. Purpose and scope

Modbus RTU is a serial industrial communication protocol used to exchange data between controllers, instruments, drives, remote I/O modules, energy meters, temperature controllers, and other automation devices.

It is widely used because it is relatively simple, supported by many manufacturers, and suitable for transferring small amounts of structured process data over serial links.

Examples from industrial maintenance include:

  • Reading current, voltage, power, energy, temperature, and pressure from instruments.
  • Reading drive status, speed feedback, current, and fault codes.
  • Writing a speed reference or an approved control command to a drive.
  • Collecting data from remote I/O modules and temperature controllers.
  • Integrating older serial equipment with a PLC, gateway, SCADA system, or industrial PC.

Modbus RTU is a communication protocol, not a physical cable standard. It commonly operates over RS-485 and can also be used over RS-232 in suitable point-to-point applications.

2. What does Modbus RTU mean?

  • Modbus: Defines how devices request, address, and exchange data.
  • RTU: Remote Terminal Unit mode. Messages use compact binary encoding and include a CRC for error detection.
  • Serial: Bits are transmitted sequentially over a communication link.
  • Master/slave: Traditional Modbus serial terminology describing who initiates requests and who responds.

In modern Modbus documentation, the terms client and server are also used. The client initiates a request; the server processes it and returns a response. For the conventional serial architecture, master/slave is still common in equipment manuals.

The important rule is that a standard Modbus serial slave does not independently initiate ordinary application messages. It responds to requests from the master.

3. Basic architecture

                 PLC / Modbus Master
                         |
                    RS-485 bus
                         |
            +------------+------------+
            |            |            |
            v            v            v
        Slave 1       Slave 2       Slave 3
        Energy        VFD            Remote I/O
        meter

A typical system consists of:

  • Master: PLC, controller, serial communication module, gateway, or industrial PC that initiates requests.
  • Slave: Meter, drive, remote I/O, or other device that responds to requests addressed to it.
  • Serial interface: Commonly RS-485, sometimes RS-232.
  • Communication parameters: Baud rate, parity, data bits, and stop bits.
  • Device address: Identifies the intended slave on the serial network.
  • Register map: Defines which data values can be read or written and how to interpret them.

The exact architecture depends on the equipment. Some devices support multiple communication interfaces, and some gateways expose serial Modbus devices to Ethernet-based systems.

4. Master/slave operating principle

The master controls the communication sequence by sending a request. An addressed slave processes the request and sends a response if the request is valid and the operation is supported.

Master                         Slave
  |                              |
  |---- Request ---------------->|
  |                              | Validate request
  |                              | Process function
  |<--- Response ----------------|
  |                              |
  |---- Next request ----------->|

A request typically specifies:

  • The slave address.
  • A function code.
  • A register or data address, where required.
  • The number of registers or the data to write.
  • A CRC for error detection.

A normal response contains the slave address, function code, requested data or acknowledgement, and CRC.

4.1 Request and response example

Suppose a PLC requests two holding registers from slave address 5.

The conceptual request contains:

Field Example Purpose
Slave address 05 Selects device 5
Function code 03 Reads holding registers
Starting address 00 10 Illustrative protocol address
Quantity 00 02 Requests two registers
CRC Calculated value Detects transmission errors

This is a field-level illustration, not a complete transmitted frame. The actual CRC depends on the complete message bytes.

The slave returns the register data if the request is valid and the addresses are supported. The master interprets the returned values using the device's register map.

4.2 What happens if a slave does not respond?

Possible causes include:

  • Incorrect slave address.
  • Wrong baud rate or serial framing.
  • A/B wiring or polarity problem on RS-485.
  • Missing device power.
  • Incorrect register address or unsupported function code.
  • CRC errors caused by noise or signal problems.
  • Incorrect termination or biasing.
  • A failed serial port or interface.
  • Excessive response delay or timeout settings.
  • Another device interfering with the bus.

The master normally detects a timeout, reports a communication error, or retries according to its configuration. It should not assume that missing data means the process value is zero.

5. Modbus RTU versus RS-485

These terms describe different parts of the system.

Feature Modbus RTU RS-485
What it defines Message format, addressing, function codes, data access Electrical characteristics of a serial interface
Main purpose Exchange structured application data Transmit electrical signals between devices
Defines registers Yes, through device-specific data models and register maps No
Defines CRC in Modbus messages Yes No
Defines slave addresses Yes No
Common industrial use Protocol between a PLC and field devices Physical layer for a multidrop serial bus

A device can support RS-485 without supporting Modbus RTU. RS-485 may be used with other protocols, including vendor-specific serial protocols.

Likewise, Modbus RTU does not require RS-485 in every implementation. Modbus RTU can operate over other suitable serial interfaces, including RS-232.

5.1 RS-485 two-wire communication

Two-wire RS-485 commonly uses a differential pair. Many devices label the terminals A and B, but vendor naming conventions are not perfectly consistent. Confirm the manufacturer's wiring diagram rather than relying on terminal letters alone.

Important installation points:

  • Use the specified twisted-pair cable.
  • Follow the manufacturer's polarity convention.
  • Connect the bus in the supported topology, normally a trunk with short stubs.
  • Use termination at the appropriate physical ends of the transmission line.
  • Apply biasing where required by the network design.
  • Follow the device manufacturer's shielding and grounding instructions.
  • Avoid star wiring unless the equipment and network design explicitly support it.

For a typical two-wire RS-485 bus, devices share the differential pair and transmit in turn. The master/slave request-response method helps prevent multiple slaves from transmitting simultaneously.

6. RTU message framing

Modbus RTU transmits data as binary bytes. It relies on both the serial framing settings and timing between messages to identify message boundaries.

A typical RTU frame has this structure:

+-------------+--------------+----------------+-------------+
| Slave       | Function     | Data           | CRC         |
| Address     | Code         |                | 16 bits     |
+-------------+--------------+----------------+-------------+
     1 byte       1 byte       Variable          2 bytes

The exact data field depends on the function code. For a read request, it includes a starting register address and quantity. For a write request, it contains the address and the value or values being written.

6.1 Important frame fields

Slave address

Identifies the intended device. In standard Modbus serial addressing, addresses 1 through 247 are individual device addresses. Address 0 is the broadcast address, and addresses 248 through 255 are reserved.

Function code

Specifies the requested operation, such as reading holding registers or writing a single register.

Data field

Contains the register address, quantity, values, or other function-specific information.

CRC

The cyclic redundancy check is used to detect corruption of the transmitted message. Modbus RTU uses a 16-bit CRC. The CRC is transmitted low byte first.

A valid CRC does not prove that the data has the correct engineering meaning. It only indicates that the received message passes this error-detection check.

6.2 RTU timing and message boundaries

RTU framing uses silent intervals on the serial line. A gap of at least 3.5 character times separates frames under the standard timing rules. A gap exceeding 1.5 character times within a frame can indicate a broken frame.

At higher baud rates, implementations may use defined fixed timing values according to the Modbus serial-line specification. Follow the protocol specification and device implementation rather than assuming every device handles timing identically.

Communication problems may occur when:

  • The master sends requests too quickly for the device.
  • The slave response timeout is too short.
  • The device has a long internal processing delay.
  • Serial framing parameters do not match.
  • Noise corrupts characters or creates invalid frames.

7. Common Modbus function codes

Function codes determine what data operation the master requests. The device's implementation determines which functions it supports.

Function code Operation Typical use
01 Read Coils Read digital output states
02 Read Discrete Inputs Read digital input states
03 Read Holding Registers Read configuration, command, or measurement registers
04 Read Input Registers Read measurement or status registers
05 Write Single Coil Write one digital output
06 Write Single Register Write one 16-bit register
0F / 15 hex Write Multiple Coils Write several digital outputs
10 / 16 hex Write Multiple Registers Write several registers

The codes in the first column are hexadecimal. For example, 10 hex is decimal 16, while 03 hex is decimal 3.

Not all devices support all function codes. A device may permit reading a register but prohibit writing it, or may implement only a subset of the protocol.

7.1 Coils, discrete inputs, and registers

Modbus distinguishes between single-bit data and 16-bit registers.

Data type Logical size Common interpretation
Coil 1 bit Writable digital state
Discrete input 1 bit Read-only digital state
Input register 16 bits Read-only value
Holding register 16 bits Readable and potentially writable value

These are protocol data categories, not necessarily direct descriptions of the physical hardware. For example, a holding register may represent a drive speed reference, a configuration setting, or a scaled measurement.

A register's access permissions and meaning must be confirmed from the specific device manual.

8. Understanding the register map

A register map is the device manufacturer's description of the data exposed through Modbus. It explains what each address means, how the data is encoded, and whether it can be read or written.

A register-map entry may contain:

  • Register name and description.
  • Address or protocol offset.
  • Supported function code.
  • Data type and width.
  • Units and scaling.
  • Minimum and maximum values.
  • Access permissions.
  • Byte order and word order for multiregister values.
  • Notes about device operating state or prerequisites.

Illustrative register map:

Register description Example address Data type Example interpretation
Output frequency 40001 in a reference-style notation 16-bit unsigned Frequency scaled by 0.01 Hz
Motor current 40002 in a reference-style notation 16-bit unsigned Current scaled by 0.1 A
Drive status word 40003 in a reference-style notation 16-bit bit field Bit meanings defined by manufacturer
Speed reference 40004 in a reference-style notation 16-bit signed or unsigned Permitted command range defined by manufacturer

These addresses and values are examples only. They are not universal Modbus register assignments.

8.1 Register notation versus transmitted address

One of the most common integration errors is confusing a manual's reference notation with the address sent in a Modbus request.

A manual may label a holding register as 40001, while the protocol request uses a zero-based address offset of 0. Another device or software tool may present addresses differently.

Manual notation Possible protocol offset Important caution
40001 0 Common reference-style convention
40002 1 Common reference-style convention
30001 0 for the first input register Depends on the manual's convention and supported function
40101 100 Only if the manual uses the same one-based reference convention

Always confirm the addressing convention in the equipment manual and the software interface. Do not subtract one blindly without first checking how the particular device and software represent addresses.

8.2 Scaling and engineering units

A register does not always contain a value in directly usable engineering units.

Suppose a device reports a raw integer of 2534, and its manual defines a scaling factor of 0.1 A.

The engineering value is:

\[ 2534 \times 0.1 = 253.4\text{ A} \]

The scaling factor is device-specific. Some values use multiplication, others use division, signed interpretation, offsets, or more complex encoding.

8.3 Signed and unsigned values

A 16-bit unsigned register represents values from 0 to 65535.

A 16-bit signed two's-complement register represents values from -32768 to 32767.

For example, the bit pattern 0xFFFF represents 65535 as an unsigned 16-bit value, but -1 as a signed 16-bit value.

If the signedness is interpreted incorrectly, negative measurements or commands may appear as very large positive numbers.

8.4 Values requiring multiple registers

A 32-bit integer or floating-point value typically requires two 16-bit registers. The protocol provides the individual register values, but the device documentation determines how to combine them.

Possible arrangements include:

  • High word followed by low word.
  • Low word followed by high word.
  • Different byte arrangements within each word, depending on the device's data representation.

Do not assume that every device uses the same word order. Incorrect interpretation can produce implausible measurements even when communication is otherwise healthy.

9. Serial communication parameters

The master and slave must use compatible serial settings.

Parameter Meaning Example
Baud rate Serial signaling speed 9600 bit/s
Data bits Number of data bits in each character 8
Parity Optional error-checking bit Even
Stop bits Character-ending bits 1
Slave address Device address on the bus 5
Response timeout Time the master waits for a response Application-specific
Inter-request delay Delay between requests when required Application-specific

A common configuration is 9600, 8, E, 1, meaning 9600 bit/s, 8 data bits, even parity, and 1 stop bit. This is only an example, not a universal default.

If one device uses even parity and another expects no parity, communication will generally fail or produce framing errors. The baud rate, data bits, parity, and stop-bit configuration must be compatible at both ends.

The next topic, Modbus RTU setup, will cover these parameters in greater detail alongside device addressing and register-map configuration.

10. Polling, response time, and bus utilization

In a typical Modbus RTU serial network, the master polls devices by sending requests and receiving responses.

For example:

PLC Master
    |
    | Request to meter 1
    v
Meter 1
    |
    | Response
    v
PLC Master
    |
    | Request to drive 2
    v
Drive 2
    |
    | Response
    v
PLC Master

The master generally waits for the response or timeout before proceeding according to its polling strategy. The bus is shared, so requests must be scheduled to avoid conflicting transmissions.

10.1 Factors affecting update time

  • Baud rate and the number of transmitted bytes.
  • Number of devices being polled.
  • Number of registers requested per transaction.
  • Device processing and response delays.
  • Timeout and retry settings.
  • Inter-request delays.
  • Errors and retransmissions.
  • PLC communication-task scheduling.

A higher baud rate can reduce transmission time, but it does not automatically guarantee a faster application update. Device response time, polling design, and timeouts also matter.

10.2 Polling strategy

A practical strategy is to group related registers into efficient reads when the device supports contiguous access.

For example, reading ten consecutive holding registers in one request is often more efficient than sending ten separate requests for individual registers.

However, do not combine registers merely to reduce request count if the device has restrictions on address ranges, supported quantities, or register grouping.

For a PLC integration, separate data by practical update requirements:

  • Fast-changing values, such as speed feedback.
  • Slower-changing values, such as energy counters.
  • Diagnostic data, such as fault codes.
  • Configuration parameters that rarely change.

This avoids wasting communication time repeatedly polling data that does not need frequent updates.

11. Error responses and communication failures

Modbus distinguishes between a request that cannot be completed because of an application-level error and a request that receives no valid response.

11.1 Exception responses

When a slave receives a validly framed request but cannot perform the requested operation, it may return a Modbus exception response.

Common exception codes include:

Exception code Meaning Example cause
01 Illegal Function Requested function is unsupported
02 Illegal Data Address Requested register address is invalid
03 Illegal Data Value A request parameter is outside the permitted range
04 Server Device Failure Device encountered an error while attempting the operation
06 Server Device Busy Device is temporarily unable to process the request

Support for specific exception responses varies by device. Codes and behavior should be checked against the relevant protocol and equipment documentation.

A Modbus exception response is useful diagnostic evidence because it indicates that a response was received, unlike a complete timeout.

11.2 Common fault symptoms

Symptom Possible cause First check
No response from any device Master configuration, serial interface, bus wiring, common power issue Check master port, communication settings, and bus wiring
No response from one device Incorrect address, device power, branch wiring, failed interface Check the individual device and its physical connection
CRC errors Electrical noise, poor wiring, signal integrity, incompatible settings Check cabling, grounding, termination, and serial parameters
Illegal Data Address Incorrect register offset or unsupported register Check the register map and address convention
Values are consistently incorrect Wrong scaling, signedness, byte order, or word order Verify data interpretation against the manual
Values update too slowly Excessive polling, low baud rate, long timeouts, retries Review poll cycle and transaction timing
Intermittent communication Loose wiring, poor termination, noise, conflicting transmissions Inspect the physical bus and review error history
Multiple devices respond unexpectedly Duplicate addresses or incorrect wiring Verify unique slave addresses and bus topology
Writes are rejected Read-only register, unsupported function, invalid value, device state restriction Check write permissions and device-specific requirements

12. Practical commissioning checklist

Use this checklist when integrating a Modbus RTU instrument, VFD, energy meter, or remote I/O module.

  • Confirm that the device supports Modbus RTU and identify its physical interface.
  • Obtain the correct manufacturer's communication manual and register map.
  • Confirm the intended master/slave architecture.
  • Verify the physical interface and wiring, including RS-485 polarity where applicable.
  • Verify that slave addresses are unique on the serial bus.
  • Match the baud rate, data bits, parity, and stop bits.
  • Confirm termination and biasing requirements for the actual network.
  • Read a documented, known register using the correct function code.
  • Verify the register offset and address convention.
  • Confirm data type, signedness, scaling, units, and word order.
  • Check communication timeouts and error counters.
  • Test the required update rate under normal operating conditions.
  • Back up the configuration and document the final settings.
  • Test write operations only where authorized and under the required safe conditions.

13. Safety and control considerations

Modbus RTU is often used for monitoring, but it can also support writes that affect equipment operation.

Examples include changing a speed reference, resetting a fault, or issuing a start/stop command. The availability of such commands depends on the device and its configuration.

Follow these rules:

  • Do not write undocumented registers.
  • Do not assume that a register address has the same meaning across different manufacturers.
  • Confirm write permissions, value ranges, and operating-state restrictions.
  • Use an approved test procedure before writing control values to a live drive or process.
  • Treat communication loss as a distinct condition, not as a valid process value.
  • Define appropriate PLC behavior for timeouts, stale data, and device recovery.
  • Do not use ordinary Modbus RTU communication as a substitute for a certified safety communication system.
  • Ensure that network or serial faults cannot cause an unsafe machine state under the intended system design.

A successful write acknowledgement does not prove that the machine executed the intended action. The actual device state and relevant feedback should also be verified.

14. Modbus RTU compared with other industrial protocols

Feature Modbus RTU Modbus TCP PROFINET IO
Common transport Serial, often RS-485 Ethernet with TCP/IP Industrial Ethernet
Typical communication model Master/slave or client/server Client/server IO controller and IO device
Device identification Serial address IP addressing and protocol-specific addressing Device identification and configured IO relationship
Data model Coils, discrete inputs, input registers, holding registers Similar Modbus data model Configured process data and device-specific structures
Cyclic real-time IO Polling-based serial transactions Request/response transactions Designed for cyclic industrial IO exchange
Typical applications Meters, drives, instruments, legacy equipment Ethernet-connected instruments and gateways PLC-to-remote-I/O, drives, and automation devices

The right protocol depends on the equipment, required update rate, network architecture, existing standards, and integration requirements. Modbus RTU remains useful precisely because many industrial devices support it, including equipment that does not provide an industrial Ethernet interface.

15. Interview questions and answers

Q1. What is Modbus RTU?

A serial industrial communication protocol that uses binary messages, function codes, device addressing, and CRC error detection to exchange data.

Q2. What is the role of the master?

The master initiates requests, addresses the intended slave, processes responses, and typically schedules communication with the devices on the serial bus.

Q3. Can a normal Modbus RTU slave initiate a request whenever it wants?

No. In the traditional serial master/slave model, the slave responds to requests rather than independently initiating normal application transactions.

Q4. What is the difference between Modbus RTU and RS-485?

Modbus RTU defines the application message format and operations. RS-485 defines electrical characteristics for serial signaling.

Q5. What is a CRC?

A cyclic redundancy check used to detect corruption in a transmitted message.

Q6. What is the difference between a coil and a holding register?

A coil represents a single-bit value, while a holding register represents a 16-bit data value. Their actual meaning and access permissions depend on the device.

Q7. Why might a register return a very large number instead of a negative value?

The PLC or software may be interpreting a signed 16-bit value as unsigned.

Q8. Why can communication work while the displayed measurement is incorrect?

The register may be decoded with the wrong address offset, scaling factor, data type, or byte/word order.

Q9. What does an Illegal Data Address exception usually indicate?

The request references a data address that the device does not support or permit for that operation.

Q10. Why should slave addresses be unique?

On a shared serial bus, duplicate addresses can cause ambiguous responses and communication collisions.

Q11. What is the purpose of termination on an RS-485 bus?

Termination reduces signal reflections on the transmission line. It should be installed according to the physical network design and manufacturer instructions, normally at the appropriate line ends.

Q12. How would you troubleshoot a Modbus RTU drive that is not responding?

Check device power, the master's serial port, slave address, serial parameters, RS-485 wiring and polarity, termination and biasing, timeout settings, and the drive's communication diagnostics. Then test a known supported register and inspect any exception response.

16. Practical exercises

Exercise 1: Read a measurement from an energy meter

  • Identify a documented measurement register.
  • Determine its function code and address convention.
  • Read the register using the configured master.
  • Apply the documented scaling factor.
  • Compare the result with the meter display.

Exercise 2: Diagnose an incorrect value

  • Read a known register.
  • Record the raw value.
  • Check whether the register is signed or unsigned.
  • Verify scaling and units.
  • If the value spans two registers, verify byte and word order.

Exercise 3: Diagnose a no-response fault

  • Confirm device power and communication indicators.
  • Verify the slave address and serial parameters.
  • Check wiring and the bus topology.
  • Inspect timeout and CRC diagnostics.
  • Test a documented, supported read request.

Exercise 4: Optimize polling

  • Record the current polling cycle.
  • Identify consecutive registers that can be read together.
  • Group reads where the device supports them.
  • Avoid repeatedly polling slow-changing data at unnecessarily high frequency.
  • Confirm that the revised update rate meets the application requirements.

17. Final mental model

Modbus RTU can be understood through five questions:

  1. Who is communicating? The master and the addressed slave.
  2. How are bits transmitted? Through a serial interface such as RS-485.
  3. What operation is requested? The function code determines whether the request reads or writes supported data.
  4. What does the returned data mean? The register map defines its address, type, scaling, and interpretation.
  5. How is an error identified? Timeouts, exception responses, CRC errors, and incorrect data interpretation point toward different fault categories.

The essential distinction is that successful serial communication does not guarantee correct data interpretation. Reliable integration requires the physical wiring, serial parameters, device addressing, request functions, and register map to agree.
