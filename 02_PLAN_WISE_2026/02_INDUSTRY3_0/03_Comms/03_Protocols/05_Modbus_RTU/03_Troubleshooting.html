Modbus RTU Troubleshooting: Wiring, Termination, and Timeouts

1. Purpose and Scope

Modbus RTU troubleshooting is the systematic process of identifying why a serial Modbus device fails to communicate, responds intermittently, returns errors, or provides incorrect data.

In industrial maintenance, Modbus RTU is commonly used between PLCs, VFDs, energy meters, temperature controllers, remote I/O modules, weighing systems, and other field devices over serial communication links.

A communication fault does not automatically mean the device is defective. The cause may be wiring, RS-485 bus topology, termination, biasing, serial settings, addressing, message timing, or an incorrect register map.

The goal is to identify the actual failure layer instead of randomly replacing hardware or changing settings until the fault disappears temporarily.

2. Troubleshooting Architecture

A Modbus RTU communication path can be divided into several diagnostic layers.

PLC / HMI / SCADA / Modbus Master
              ↓
Master Serial Port Configuration
              ↓
RS-232 / RS-485 Interface or Converter
              ↓
Cable, Terminals, Polarity, Shield
              ↓
RS-485 Bus: Termination and Biasing
              ↓
Slave Device Serial Configuration
              ↓
Modbus RTU Frame and CRC
              ↓
Slave Address and Function Code
              ↓
Register Address, Data Type, Scaling
              ↓
Application Value in PLC / HMI / SCADA

A failure at one layer may look similar to a failure at another. For example, a master timeout may be caused by an open cable, incorrect slave address, mismatched baud rate, or a slave that is not powered.

3. Understand the Main Fault Categories

Fault category Typical symptoms Primary checks
Physical wiring No communication, intermittent responses Cable continuity, terminals, polarity
RS-485 signal integrity CRC errors, intermittent communication Topology, stubs, cable quality, termination
Serial configuration No response or framing errors Baud rate, parity, data bits, stop bits
Addressing One device does not respond Slave address and duplicate addresses
Timing Intermittent timeouts Response timeout, turnaround delay, polling interval
Modbus request Exception response or no useful data Function code and register map
Application mapping Communication succeeds but values are wrong Register offset, data format, scaling
Hardware Fault persists after configuration and wiring checks Interface, transceiver, device power, port health

A useful distinction is whether the master receives a valid Modbus response, an exception response, a corrupted response, or no response at all.

4. RS-485 Wiring Troubleshooting

4.1 Two-Wire Half-Duplex RS-485

Modbus RTU installations commonly use two-wire, half-duplex RS-485. The same differential pair carries transmitted and received data, with devices taking turns transmitting.

PLC / Master RS-485
      D+ / D-
          ↓
      Twisted Pair
          ↓
    Slave 1 RS-485
          ↓
    Slave 2 RS-485
          ↓
    Slave 3 RS-485

The drawing represents a linear bus. In a properly designed network, devices connect along a trunk, with short branches where possible.

4.2 Check A/B or D+/D- Polarity

RS-485 devices use different naming conventions. One manufacturer's A terminal may not correspond to another manufacturer's A terminal. Never assume polarity solely from the letters.

Check the actual device manual for terminal definitions such as:

  • D+ and D-
  • Data+ and Data-
  • B and A
  • + and -

A reversed differential pair can cause complete communication failure on many devices. Some transceivers or interfaces have different labeling conventions, so verify the electrical definitions before changing wires.

Practical method:

  1. Record the master and slave terminal labels.
  2. Check the manuals for the corresponding signal definitions.
  3. Confirm the cable lands on the intended differential pair.
  4. If polarity is suspected, isolate the change to a controlled test.
  5. Recheck communication after the change and document the verified mapping.

Do not reverse wires repeatedly without recording the original arrangement. That is not diagnosis; it is an uncontrolled experiment.

4.3 Cable Type and Routing

For industrial RS-485, use cable suitable for the interface and installation environment, commonly a shielded twisted pair with appropriate characteristic impedance and capacitance.

Inspect for:

  • Broken conductors or loose terminal blocks.
  • Incorrect cable joints or poor-quality splices.
  • Long parallel runs near motor power cables, VFD output cables, contactors, or high-current conductors.
  • Damaged insulation, moisture ingress, oil exposure, and mechanical damage.
  • Excessive cable length or too many devices for the selected baud rate and network design.
  • Incorrect use of ordinary unscreened wire for a demanding industrial environment.

Twisting helps reject common-mode electrical noise. Shielding can reduce interference when implemented according to the equipment and plant grounding design. Neither compensates for bad routing, poor termination, or an incorrectly designed network.

4.4 Common or Reference Connection

RS-485 uses differential signaling, but transceivers still have limits on the common-mode voltage they can tolerate.

Depending on the devices and installation design, a signal reference or common connection may be required. Follow the manufacturer's instructions. Do not casually connect signal common, protective earth, cable shield, and DC negative together at arbitrary points.

Uncontrolled grounding can create ground loops, noise, or equipment damage. Where significant ground-potential differences exist, evaluate isolation and the approved grounding design.

4.5 Shield and Earthing

Shielding practices depend on the equipment, cable, grounding system, and plant standards.

Check that:

  • The shield is connected as specified by the device and network design.
  • Shield continuity is maintained where required.
  • The shield is not accidentally shorted to a data conductor.
  • Shield termination does not create an unintended ground loop.
  • Protective earth connections remain intact.

Do not remove protective earth or defeat electrical safety measures to make communication work.

5. RS-485 Bus Topology

5.1 Preferred Linear Bus

[Master] ===== [Slave 1] ===== [Slave 2] ===== [Slave 3]
  End                                              End

A linear trunk is generally preferred because it provides a predictable signal path and makes termination easier to design.

5.2 Star Topology and Long Stubs

                 [Slave 1]
                     |
[Master] ======== Junction ======== [Slave 2]
                     |
                 [Slave 3]

A star topology creates multiple branches. Long branches can cause signal reflections and degrade communication, particularly at higher baud rates or with longer cables.

If a network works when only one slave is connected but becomes unreliable when all devices are connected, inspect:

  • Long stubs and star-shaped branches.
  • Incorrect termination locations.
  • Total cable length and device loading.
  • Multiple bias networks.
  • Noise coupling and grounding.
  • Device transceiver loading or a defective interface.

Do not assume every star arrangement must fail. The actual result depends on cable length, baud rate, transceiver characteristics, and network design. However, a linear trunk with short stubs is usually the safer starting point.

6. Termination Resistors

6.1 Purpose

Termination reduces signal reflections caused by impedance discontinuities on the transmission line.

Reflections can distort signal transitions, making bits difficult for receivers to interpret. The problem becomes more important as cable length and signaling speed increase.

A commonly encountered RS-485 termination value is approximately \(120\ \Omega\), but the correct value must match the cable and equipment design.

6.2 Correct Termination Placement

For a conventional linear RS-485 trunk, termination is normally installed at the two physical ends of the main bus.

[120 Ω] ==== Master ==== Slave 1 ==== Slave 2 ==== [120 Ω]
  End                                                    End

The diagram is conceptual. The master is not necessarily at one end in every installation, and the actual termination value and placement must follow the network design.

Do not add a termination resistor at every slave. Excessive termination loads the differential driver and may reduce the signal amplitude enough to cause communication failure.

6.3 Built-In Termination

Some devices and serial interfaces include selectable termination resistors controlled by:

  • DIP switches.
  • Slide switches.
  • Jumper links.
  • Software settings.
  • Connector-specific termination options.

Check the documentation and the physical switch settings. A resistor may already be enabled inside the master or a converter.

6.4 Checking Termination with a Multimeter

A resistance measurement can sometimes help identify incorrect termination, but it must be interpreted in context.

For a conventional bus with two \(120\ \Omega\) termination resistors in parallel:

\[ R\_{\text{equivalent}} = \frac{120 \times 120}{120 + 120} = 60\ \Omega \]

A reading near \(60\ \Omega\) across the differential pair may therefore be expected in that particular arrangement.

However, the measured value can differ because of:

  • Built-in bias resistors.
  • Additional circuitry connected to the bus.
  • Different termination values.
  • Devices remaining connected to the line.
  • The measurement point and circuit design.

Safety: Only perform resistance checks with the circuit safely de-energized and isolated as required by the equipment instructions. Never use an ohmmeter on an energized circuit. Do not disconnect a live communication network without considering machine behavior and production consequences.

6.5 Symptoms of Termination Problems

Symptom Possible explanation
Communication works at low baud rate but fails at higher baud rate Reflections or insufficient signal margin
Communication fails when the cable becomes longer Signal integrity or topology problem
CRC errors occur intermittently Reflections, noise, poor connections, or other signal issues
Network works with one slave but fails with several Loading, topology, termination, biasing, or wiring issue
Communication becomes worse after adding resistors Excessive termination or incorrect placement

These symptoms are clues, not proof. A baud-rate reduction can help isolate a signal-integrity problem, but it does not repair a defective installation.

7. Biasing and Idle Bus State

7.1 Why Biasing Matters

When no device is transmitting, the RS-485 differential pair can become electrically undefined if the network has no effective failsafe mechanism. Noise or ambiguous receiver thresholds may then produce false transitions.

Biasing establishes a defined idle state. It may be provided by the master, a serial interface, a converter, or another designed component of the network.

7.2 Troubleshooting Biasing

Check:

  • Whether the interface already provides biasing.
  • Whether external bias resistors are required by the network design.
  • Whether multiple devices have enabled competing bias networks.
  • Whether the network has been modified without updating the termination and biasing design.
  • Whether the receiver supports internal failsafe behavior.

Do not install additional pull-up and pull-down resistors just because they appear in an online circuit. Their values and placement depend on the bus design, termination, device loading, and transceiver specifications.

8. Serial Communication Settings

Both ends must use compatible serial settings. For a conventional Modbus RTU link, verify all relevant parameters.

Parameter What to verify Typical failure symptom
Baud rate Same configured rate at both ends No response or corrupted frames
Data bits Usually 8 for Modbus RTU implementations Framing or decoding errors
Parity Even, odd, or none as supported Invalid frames or no response
Stop bits Compatible with the selected format Framing errors or failed communication
Slave address Correct address for the target device Timeout or response from the wrong device
RTU mode RTU selected instead of ASCII or another protocol No valid RTU response
Serial interface Correct port and physical interface No communication
Master request format Correct function code and data fields Exception response or rejected request

Many Modbus RTU implementations use 8 data bits and a format such as 8E1 or 8N2. The correct format is device-dependent. Do not change a working slave configuration to match a guessed default.

8.1 Example: Mismatched Parity

Suppose the master is configured for 9600 baud, even parity, 8 data bits, and 1 stop bit, while the slave is configured for 9600 baud, no parity, 8 data bits, and 2 stop bits.

The baud rate matches, but the serial framing does not. The slave may reject the request, fail to recognize it, or produce communication errors depending on the hardware and configuration.

The correct solution is to establish a compatible format supported by both devices and configure both ends accordingly.

9. Slave Addresses and Duplicate Devices

Modbus RTU uses slave addresses to identify which device should respond to a request.

For standard serial Modbus addressing, addresses 1 through 247 are generally used for individual devices. Address 0 is the broadcast address for applicable write requests and does not receive a normal response. Address 248 through 255 are reserved in the conventional addressing model.

Always confirm the actual addressing rules of the device and master implementation.

9.1 Common Addressing Faults

  • The configured slave address differs from the device's actual address.
  • The address was changed in software but not saved to the device.
  • Two devices share the same address.
  • The master is polling a device that is disconnected or unpowered.
  • A parameter was changed on the wrong device.
  • The master is using an invalid address or unsupported request.

Duplicate addresses are especially troublesome. Two devices may respond simultaneously, causing corrupted frames or apparently random communication failures.

9.2 Isolation Method

  1. Place the machine or process in a safe state if communication changes could affect operation.
  2. Disconnect or isolate devices only through an approved procedure.
  3. Test one known device with a verified address and serial configuration.
  4. Add devices back one at a time.
  5. Confirm that each device has a unique address.
  6. Re-test the complete network under its normal polling load.

Never use broadcast writes casually on a production network. Broadcast requests can affect multiple devices and generally do not provide individual acknowledgements.

10. Modbus RTU Timing and Timeouts

10.1 What a Timeout Means

A timeout occurs when the master does not receive an acceptable response within the configured waiting period.

It does not, by itself, prove that the slave is defective. Possible causes include:

  • The slave is not powered.
  • The slave address is incorrect.
  • The request is corrupted or rejected.
  • The slave is busy or responding slowly.
  • The physical interface is faulty.
  • The master is using incompatible serial settings.
  • The response arrives after the master's timeout expires.
  • Another device is transmitting or the bus is incorrectly controlled.

10.2 Types of Timing Parameters

Parameter Meaning Why it matters
Response timeout Maximum time the master waits for a response Too short causes false timeouts
Inter-frame silence Idle time used to distinguish RTU frames Too little separation can make frames ambiguous
Slave processing delay Time required by a slave to execute a request Some devices need longer to respond
Turnaround delay Time for the bus to switch from request transmission to response transmission Incorrect handling may truncate or miss responses
Polling interval Time between requests or polling cycles Excessive polling can overload devices or lengthen the overall scan
Retry count Number of repeated attempts after failure More retries may improve recovery but increase data latency

These settings serve different purposes. Increasing the response timeout does not fix incorrect RTU frame separation, bad wiring, or mismatched serial settings.

10.3 RTU Inter-Frame Timing

Modbus RTU identifies frame boundaries using silence on the serial line. For baud rates up to 19,200 bit/s, the protocol's character-time-based timing rules are commonly applied. At higher rates, a fixed timing recommendation is commonly used by implementations.

The precise implementation and device documentation matter, especially for older serial interfaces, USB-to-serial converters, and software-based masters.

For a typical 11-bit character format:

\[ T\_{\text{character}} = \frac{11}{\text{baud rate}} \]

At 9600 bit/s:

\[ T\_{\text{character}} = \frac{11}{9600} \approx 1.146\ \text{ms} \]

A three-and-a-half-character interval is approximately:

\[ T\_{3.5} = 3.5 \times 1.146 \approx 4.01\ \text{ms} \]

This is an illustrative calculation for that character format. Actual framing and timing depend on the configured serial format and implementation.

10.4 Setting a Response Timeout

Use a timeout that accommodates the device's documented response time, request length, baud rate, processing delay, and interface behavior.

A practical approach is:

  1. Start with the manufacturer's recommended settings.
  2. Test one known request to a single device.
  3. Observe response times and error logs.
  4. Increase the timeout only if measurements show the slave needs more time.
  5. Confirm that the resulting polling cycle still meets process requirements.
  6. Check whether retries are causing the PLC or HMI to receive stale data.

An excessively large timeout can hide a communication problem while making the overall system sluggish. An excessively short timeout can make a healthy network appear faulty.

11. CRC Errors and Frame Corruption

Modbus RTU frames include a 16-bit CRC for detecting transmission errors.

A CRC error means the received frame failed its integrity check. It does not identify the precise physical cause.

Potential causes include:

  • Electrical noise.
  • Poor shielding or cable routing.
  • Signal reflections.
  • Loose or corroded terminals.
  • Incorrect termination.
  • Incorrect baud rate or framing.
  • A faulty transceiver or serial converter.
  • More than one device transmitting simultaneously.
  • Ground-potential problems or common-mode voltage outside the interface's tolerance.

11.1 CRC Error vs. Timeout

Observation Interpretation
No response before timeout The master received no acceptable response in time
Response received but CRC invalid Data was received but failed integrity validation
Valid exception response The slave received and processed the request sufficiently to return a protocol exception
Valid response with incorrect value Communication may be healthy; inspect address mapping, data type, byte order, and scaling
Intermittent CRC errors Investigate signal quality, wiring, topology, and electrical interference

A valid Modbus exception is useful diagnostic evidence. It suggests the slave recognized enough of the request to reject it for a defined reason, unlike a complete absence of response.

12. Exception Responses vs. Communication Failures

A Modbus exception response is not the same as a timeout.

Exception code Meaning Diagnostic direction
01 Illegal Function The device does not support the requested function
02 Illegal Data Address The requested register or range is invalid for the device
03 Illegal Data Value A field in the request contains an unacceptable value
04 Slave Device Failure The slave encountered an error while attempting the operation
06 Slave Device Busy The device cannot process the request at that time

Not every device implements or returns every exception in the same way. Use the manufacturer's register map and diagnostic documentation.

For example, if a slave returns exception 02, changing the termination resistors is unlikely to solve the problem. Verify the register address, requested quantity, supported function code, and device-specific register map.

13. Troubleshooting by Symptom

Symptom Likely causes First actions
No device responds Wrong port, no power, polarity error, settings mismatch, disconnected cable Verify master port, device power, wiring, and serial settings
Only one slave fails Wrong address, local wiring fault, device fault, unsupported request Test that slave individually and verify its address and register map
All devices fail after a change Master settings changed, common cable fault, interface problem Review the latest change and restore a known-good configuration
CRC errors occur intermittently Noise, poor connections, reflections, grounding, duplicate addresses Inspect cable routing, terminals, topology, termination, and device addresses
Communication works only at low baud rate Marginal signal integrity, long cable, excessive stubs, poor termination Check bus design, cable, and termination before selecting the final baud rate
Network works with one device but fails with several Duplicate address, bus loading, incorrect topology, termination or biasing issue Add devices one at a time and verify the bus design
Slave responds with exception 01 Unsupported function code Check the device's supported Modbus functions
Slave responds with exception 02 Invalid register address or quantity Verify the register map and zero-based versus one-based addressing
Values are consistently incorrect Wrong offset, word order, data type, or scaling Decode a known register and compare it with the device display
Communication fails after a USB converter is installed Driver, port selection, converter settings, polarity, or timing behavior Verify the OS port, converter configuration, and supported interface
Writes fail while reads work Read-only register, wrong function code, write protection, access restrictions Check register permissions and the exact write procedure
Timeout occurs only during heavy polling Slow slave, excessive request rate, long timeout/retry cycle, overloaded master Measure response time and optimize polling without violating device limits

14. A Disciplined Troubleshooting Workflow

Use the following sequence to minimize unnecessary changes.

Step 1: Establish a Safe Test Condition

  • Determine whether the communication fault affects machine sequencing, safety-related functions, production, or quality.
  • Follow plant procedures for placing the equipment in a safe state.
  • Obtain required authorization before disconnecting field devices or changing communication settings.
  • Preserve the original configuration and record the symptoms.

Modbus communication should not be assumed to be a safety-rated control channel. Safety functions must remain independent and compliant with the machine's safety design.

Step 2: Check Device Power and Status

  • Verify that the master, converter, and slave are powered.
  • Inspect device LEDs and diagnostic displays.
  • Check relevant fault codes.
  • Confirm that the serial interface is enabled.
  • Check for blown fuses, loose supply terminals, or a failed power supply where appropriate.

Step 3: Verify Master and Slave Settings

Compare baud rate, parity, data bits, stop bits, RTU mode, and slave address.

Do not change multiple parameters simultaneously. Change one variable, test, record the result, and continue only when the result is understood.

Step 4: Inspect the Physical Bus

  • Verify the correct interface type.
  • Inspect terminal tightness and conductor condition.
  • Verify polarity using device documentation.
  • Check the cable path and any joints or intermediate terminals.
  • Review the topology and stub lengths.
  • Confirm termination and biasing against the intended design.
  • Check shielding and reference connections.

Step 5: Test One Known Request

Use a known-good register and a supported function code. Confirm the exact address convention used by the master software.

For example, a register shown in a manual as holding register 40001 might be represented by some software as offset 0. Other software uses the displayed reference number directly. Follow the specific master's convention rather than assuming one universal rule.

Step 6: Examine Communication Diagnostics

Look for:

  • Request count and response count.
  • Timeouts and retry counts.
  • CRC or framing errors.
  • Slave exception codes.
  • Response times.
  • The exact address and function code being polled.
  • Whether errors affect one device or the entire bus.

Step 7: Isolate the Fault

If the network remains unreliable:

  1. Test one slave on a short, known-good connection if an approved test setup is available.
  2. Verify the device with known-good serial settings.
  3. Reintroduce the existing cable and network components methodically.
  4. Add other devices one at a time.
  5. Identify the change that causes the failure to return.

This helps distinguish a defective device from a network-level issue.

Step 8: Validate the Repair

  • Confirm stable polling under normal operating conditions.
  • Verify that data values match the device display or a trusted reference.
  • Confirm read and write operations only where authorized and safe.
  • Check communication during normal machine activity.
  • Confirm that the fault does not return after a restart or normal operating cycle.
  • Update the maintenance record and configuration backup.

15. Practical Case Study: Modbus RTU VFD Communication Failure

System

A PLC communicates with three VFDs over a two-wire RS-485 bus. All three drives were communicating before a new drive was added.

Observed Symptoms

  • Communication with the original drives becomes intermittent.
  • CRC errors and timeouts increase.
  • Communication becomes more stable when the new drive is disconnected.

Investigation

  1. Confirm that all drives have unique slave addresses.
  2. Compare the serial settings of all three drives and the PLC.
  3. Inspect the new drive's branch cable and terminal connections.
  4. Verify the intended trunk topology and the length of the new branch.
  5. Check whether the new drive has internal termination enabled.
  6. Confirm that termination is installed only at the intended physical ends of the trunk.
  7. Check whether additional biasing was introduced.
  8. Test the network after correcting the identified configuration or wiring issue.

Possible Root Causes

  • The new drive duplicates an existing slave address.
  • Its internal termination was enabled even though it is not at a bus end.
  • The branch cable is too long for the installation's signal conditions.
  • Its polarity is reversed.
  • Its serial settings do not match the PLC configuration.

The symptom narrows the investigation but does not identify one cause automatically. The correct repair is the one supported by measurements and controlled testing.

16. Useful Diagnostic Tools

Tool Purpose Limitation
Digital multimeter Check power, continuity, and resistance in a safe, de-energized circuit Cannot fully characterize signal quality
USB-to-RS-485 adapter Test a device independently from the PLC master Must support the correct interface and serial settings
Modbus test software Send controlled requests and inspect responses Incorrect requests can produce misleading results
Oscilloscope with suitable differential measurement Observe signal levels, reflections, and noise Requires correct probing technique and electrical safety precautions
Serial protocol analyzer Inspect frames, timing, CRC failures, and response delays Must be compatible with the interface and bus
PLC diagnostics or communication logs Identify timeouts, retries, and error patterns May not expose the underlying electrical cause
Device parameter software Verify slave address and serial configuration Access may require vendor software or authorization

Do not connect a grounded oscilloscope probe directly across RS-485 conductors without understanding the instrument's grounding and measurement arrangement. Use a suitable differential probe or approved isolated measurement method.

17. Preventive Maintenance and Documentation

A reliable network should have a record of its intended configuration. Without one, every future fault becomes a small archaeological expedition through old terminal changes.

Maintain the following information:

  • Network drawing showing the master, slaves, converters, and cable route.
  • Device address list and unique-address verification.
  • Baud rate, parity, data bits, and stop bits.
  • Cable type, approximate length, and topology.
  • Termination and biasing locations.
  • Register maps and the master's register-address convention.
  • Response timeout, retry count, and polling interval.
  • Known-good communication test results.
  • Device firmware and parameter backups where available.
  • Fault history, root cause, corrective action, and verification results.

After maintenance, record what changed and why. This is particularly important when multiple maintenance shifts, vendors, or automation teams work on the same equipment.

18. Interview Questions and Answers

Q1. What is the first thing to check when Modbus RTU stops responding?

Check the complete communication path: device power, master port, serial settings, slave address, physical wiring, and diagnostic logs. Use the symptoms to narrow the fault rather than assuming the cable or slave is defective.

Q2. Why are termination resistors used in RS-485?

They reduce signal reflections at the ends of the transmission line. In a conventional linear bus, termination is normally provided at the two physical ends, with values selected according to the cable and network design.

Q3. Why should termination not be added to every slave?

Every termination resistor adds electrical loading. Too many can reduce the signal amplitude and cause unreliable communication.

Q4. What does a Modbus RTU CRC error indicate?

The received frame failed its CRC integrity check. Noise, reflections, bad connections, incorrect serial configuration, competing transmissions, or a defective interface may be responsible.

Q5. What is the difference between a timeout and an exception response?

A timeout means no acceptable response arrived within the configured waiting period. An exception response is a valid protocol response indicating that the slave rejected or could not complete the request for a defined reason.

Q6. Why can reducing baud rate improve communication?

Lower baud rates can provide more signal timing margin in a marginal installation. However, this should be treated as a diagnostic clue, not a substitute for correcting poor wiring, termination, or grounding.

Q7. What causes a Modbus RTU slave to return exception 02?

The requested data address or range is invalid for that device or request. Check the register map, supported address range, requested quantity, and the software's address-offset convention.

Q8. What causes intermittent communication when multiple slaves are connected?

Potential causes include duplicate addresses, excessive stubs, incorrect termination, poor biasing, excessive bus loading, noise, and wiring defects. Add devices methodically and inspect the network design.

Q9. Why is increasing the timeout not always the right solution?

It may mask a slow or faulty response without fixing the cause. Longer timeouts and retries also increase data latency and may cause PLC or HMI values to become stale.

Q10. How would you prove that a communication repair is successful?

Verify stable responses, low or absent error counts, correct register values, and reliable operation under normal machine conditions. Confirm the result after an appropriate operating cycle and document the final settings.

19. Practical Exercises

  • Draw an RS-485 network with one master and three slaves. Mark the two physical ends, termination locations, and any branches.
  • Create a communication settings sheet for a PLC and a VFD, including baud rate, parity, data bits, stop bits, and slave address.
  • Build a symptom matrix for no response, CRC error, exception response, and incorrect data.
  • Calculate the equivalent resistance of two \(120\ \Omega\) resistors connected in parallel.
  • Using a device manual, identify one valid holding register and the function code needed to read it.
  • Record the difference between the register reference number in the manual and the address convention used by the chosen master software.
  • Review an actual communication fault log and distinguish physical-layer symptoms from protocol and register-map errors.
  • Write a root-cause report that records the symptom, evidence, cause, corrective action, and post-repair verification.

20. Final Mental Model

  • No response: Start with power, port, wiring, serial settings, and slave address.
  • CRC errors: Investigate signal integrity, noise, framing, topology, and competing transmissions.
  • Intermittent failures after adding devices: Check duplicate addresses, termination, biasing, stubs, and bus loading.
  • Exception response: Read the exception code and verify the requested function or register range.
  • Correct communication but wrong value: Check register offset, data type, byte/word order, and scaling.
  • Timeouts during heavy polling: Measure response times and review polling intervals, retries, and processing delays.

The central troubleshooting rule is to separate the physical communication layer from the Modbus protocol layer and the application-data layer. Identify which layer is failing before making changes.
