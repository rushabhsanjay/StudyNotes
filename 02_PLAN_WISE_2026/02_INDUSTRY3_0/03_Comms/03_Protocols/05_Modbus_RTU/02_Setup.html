Modbus RTU Setup: Device Address, Baud Rate, Parity, and Register Map

1. Purpose and scope

Setting up Modbus RTU requires more than connecting two wires and selecting a COM port. The master and slave must agree on serial communication parameters, the device must have the correct address, the wiring must follow the physical interface requirements, and the master must request the correct registers using the correct function codes.

This topic covers configuring a Modbus RTU device for integration with a PLC, serial communication module, industrial PC, gateway, or SCADA system.

The main objectives are to:

  • Configure a unique slave address.
  • Match baud rate, data bits, parity, and stop bits.
  • Select and wire the correct serial interface.
  • Interpret the manufacturer's register map.
  • Configure function codes, addresses, data types, and scaling.
  • Verify communication before connecting the data to machine logic or dashboards.

The master sends requests to one device at a time in the conventional serial master/slave model. Each slave must have a unique address on the shared bus, and every device must use compatible serial settings.

A device's supported functions, register addresses, scaling, and write permissions come from its own documentation. Modbus standardization does not mean that every manufacturer uses identical register assignments.

3. Configure the slave address

The slave address identifies a specific device on the serial network.

Standard Modbus serial addressing uses:

Address Meaning
0 Broadcast address for supported write operations
1 to 247 Individual slave addresses
248 to 255 Reserved

For normal polling, assign a unique address to every device on the same serial bus.

Example:

Device Slave address
Energy meter 1
VFD 2
Temperature controller 3
Remote I/O module 4

These are illustrative assignments. Use the actual address range and configuration method supported by each device.

3.1 How the address is configured

Depending on the device, its address may be configured through:

  • DIP switches.
  • Rotary switches.
  • A front-panel keypad or display.
  • Manufacturer configuration software.
  • A parameter written through Modbus.
  • A device-specific commissioning utility.

Some devices apply address changes immediately. Others require a restart or communication reinitialization. Follow the manufacturer's instructions.

3.2 Duplicate-address problem

Suppose two energy meters are both assigned address 1.

When the master sends a request to address 1, both devices may attempt to respond. Their responses can overlap, causing corrupted data, CRC errors, timeouts, or inconsistent communication.

The correct procedure is to:

  1. Record the address assigned to each physical device.
  2. Verify that each address is unique.
  3. Confirm the master's configured target address.
  4. Test each device individually where practical.
  5. Document the final address-to-device mapping.

Do not use address 0 for ordinary polling. Broadcast requests do not identify an individual slave, and broadcast operations generally do not receive a normal response. Only use broadcast functions where the device and operation explicitly support them.

4. Configure baud rate

The baud rate specifies the serial signaling speed. Common Modbus RTU rates include 1200, 2400, 4800, 9600, 19200, 38400, 57600, and 115200 bit/s, although supported rates vary by device.

The master and slave must use compatible settings.

Baud rate General consideration
9600 bit/s Common in established industrial serial installations
19200 bit/s Higher throughput where all devices support it
38400 bit/s Useful for faster polling if the bus and devices support it
57600 or 115200 bit/s Higher signaling rates requiring careful attention to cable quality, topology, and device support

These are common examples, not a ranking of what is best for every installation.

4.1 How to select a baud rate

Consider:

  • The rates supported by every slave on the bus.
  • The baud rate supported by the PLC serial module or converter.
  • The required data-update interval.
  • Cable length, topology, and electrical conditions.
  • Device response times and processing delays.
  • The existing plant standard and approved configuration.

On a shared serial bus, devices generally need the same serial framing configuration. If one device is configured for 9600 bit/s and the master uses 19200 bit/s, the master will usually receive no valid response.

Increasing the baud rate does not automatically solve slow updates. Long timeouts, excessive polling, device processing delays, and retries may still dominate the cycle time.

5. Configure data bits, parity, and stop bits

Serial framing determines how individual characters are transmitted and checked.

The configuration is often written as a compact string, such as 9600, 8, E, 1.

Parameter Meaning Common example
Baud rate Signaling speed 9600
Data bits Number of data bits per character 8
Parity Optional character-level error check Even
Stop bits Character-ending bits 1

5.1 Parity options

  • Even parity (E): The parity bit is selected so the total number of 1 bits in the data plus parity bit is even.
  • Odd parity (O): The total number of 1 bits in the data plus parity bit is odd.
  • No parity (N): No parity bit is transmitted.

Parity provides limited character-level error detection. Modbus RTU also uses a message-level CRC.

Common configurations include 8E1, 8N1, and 8O1. The actual permitted settings depend on the device and implementation.

5.2 Worked configuration example

Suppose the device manual specifies:

  • Baud rate: 9600
  • Data bits: 8
  • Parity: Even
  • Stop bits: 1
  • Slave address: 5

The master must be configured to use the compatible serial framing and address the device using slave address 5.

If the master uses 9600, 8, N, 1 while the slave expects 9600, 8, E, 1, the communication may fail because the character framing is incompatible.

5.3 Character transmission time

For a common configuration of 8 data bits, even parity, and 1 stop bit, each character requires:

  • 1 start bit.
  • 8 data bits.
  • 1 parity bit.
  • 1 stop bit.

That is 11 transmitted bits per character.

At 9600 bit/s, the approximate time to transmit one character is:

\[ t = \frac{11}{9600} \approx 1.146\text{ ms} \]

A request and response each contain multiple characters, so the total transaction time includes transmission time, required inter-frame silence, device processing, and any master delays.

6. Select and verify the serial interface

Before configuring registers, verify the physical interface and the connection path.

6.1 RS-485 versus RS-232

Feature RS-485 RS-232
Typical industrial arrangement Multidrop bus Point-to-point
Signaling Differential Single-ended relative to signal ground
Common Modbus RTU use Multiple meters, drives, or remote devices One device connected to a compatible serial port
Wiring Commonly a two-wire differential pair, sometimes with additional conductors Transmit, receive, and signal ground as required
Main concern Polarity, termination, biasing, topology Correct transmit/receive wiring and signal compatibility

A USB-to-RS-485 converter is not the same as a USB-to-RS-232 converter. Choose the converter that matches the device interface and the required electrical signaling.

6.2 RS-485 wiring basics

For a two-wire bus, use the terminal definitions and polarity specified by the manufacturers of the master interface and slave devices.

Master RS-485                  Slave 1             Slave 2
D+ / A  ---------------------- D+ / A ------------ D+ / A
D- / B  ---------------------- D- / B ------------ D- / B
Reference, if required -------- Reference -------- Reference

The A and B labels are not interpreted consistently across all manufacturers. Verify the signal names and wiring diagram instead of assuming that matching letters always indicate matching polarity.

For a typical RS-485 trunk:

  • Use the specified twisted-pair cable.
  • Keep stubs short.
  • Install termination at the appropriate physical ends of the bus.
  • Apply biasing according to the network design.
  • Follow manufacturer instructions for shield connection and grounding.
  • Avoid connecting devices in an unsupported star topology.

The detailed diagnosis of wiring, termination, and timeouts belongs to the next topic.

7. Understand the register map before programming

The register map is the most important document for translating raw Modbus data into meaningful engineering values.

Before configuring a read or write, identify:

  1. The register description.
  2. The address notation used by the manual.
  3. The supported function code.
  4. The register width and data type.
  5. Whether the register is read-only or writable.
  6. The scaling factor and engineering unit.
  7. The signedness of the value.
  8. The byte order and word order for multiregister data.
  9. Any restrictions related to the device's operating state.

Do not assume that a register named Speed represents RPM, Hz, percentage, or another unit without checking the documentation.

7.1 The four standard data areas

Data area Typical function code General access
Coils 01 read, 05 or 0F write Single-bit data
Discrete inputs 02 read Single-bit read-only data
Input registers 04 read 16-bit read-only data
Holding registers 03 read, 06 or 10 write 16-bit values, potentially writable

The function codes listed are hexadecimal. A device may support only some of these functions or impose additional restrictions.

7.2 Address offsets and reference numbers

Manufacturers and software packages do not always display addresses in the same way.

For example, a manual may identify the first holding register as 40001, while a request interface expects the zero-based protocol offset 0.

Reference-style notation Possible protocol offset Interpretation
40001 0 First holding register under a common convention
40002 1 Second holding register under the same convention
40010 9 Tenth holding register under the same convention
30001 0 First input register under a common convention

These are examples of a common convention, not a universal rule. Some software accepts reference-style addresses; other software expects the protocol offset. The manufacturer's manual and software documentation determine the correct interpretation.

If the wrong convention is used, a request may return an illegal-address exception or read a different register that happens to exist.

7.3 Register width and data type

A single Modbus register contains 16 bits. That does not mean every value is a 16-bit unsigned integer.

Common interpretations include:

  • Unsigned 16-bit integer.
  • Signed 16-bit integer.
  • Bit field containing status flags.
  • Part of a 32-bit integer.
  • Part of a 32-bit floating-point value.
  • Encoded value requiring device-specific interpretation.

For a signed 16-bit value, the raw pattern 0xFFFF represents -1. If the same pattern is interpreted as unsigned, it represents 65535.

7.4 Scaling and engineering units

Suppose a VFD manual defines its output-frequency register as an unsigned integer in units of 0.01 Hz.

If the raw register value is 5000, then:

\[ 5000 \times 0.01 = 50.00\text{ Hz} \]

If a meter's current register uses a factor of 0.1 A, a raw value of 253 represents:

\[ 253 \times 0.1 = 25.3\text{ A} \]

The scaling factors above are illustrative. Always use the factor and unit defined for the actual register.

7.5 Two-register values

A 32-bit value generally occupies two consecutive 16-bit registers, but the correct order must be verified.

For example, a 32-bit value may be represented as:

Register N     = High 16 bits
Register N + 1 = Low 16 bits

Another device may reverse the word order. The register bytes may also need a specific ordering when decoded into a floating-point number.

If a reading produces an implausibly large number or a floating-point value that changes wildly, check the documented byte order, word order, and data type before assuming the communication is faulty.

8. Configure the Modbus master

The master may be a PLC's built-in serial port, a serial communication module, a gateway, or an industrial PC running SCADA software. The configuration screens differ, but the required information is similar.

8.1 Typical master configuration

Setting Example Source of setting
Physical interface RS-485, two-wire Hardware manual
Protocol mode Modbus RTU master Communication module documentation
Baud rate 9600 bit/s Device communication manual
Data bits 8 Device communication manual
Parity Even Device communication manual
Stop bits 1 Device communication manual
Slave address 5 Device configuration
Function code 03 Register map
Starting address 0 Address convention in the manual and software
Quantity 2 registers Register map and supported read range
Response timeout Application-specific Device response time and network conditions
Retry count Application-specific Reliability and timing requirements

The example values are not a universal configuration. Use the settings documented for the actual equipment.

8.2 Typical setup sequence

  1. Identify the PLC serial port or communication module and confirm that it supports Modbus RTU master operation.
  2. Configure the serial framing to match the slave.
  3. Assign or verify the slave address.
  4. Confirm the physical wiring and interface type.
  5. Obtain the device register map.
  6. Configure a read request for one known, documented register.
  7. Verify the raw response and the interpreted value.
  8. Add the remaining required registers.
  9. Configure suitable timeouts, retries, and polling intervals.
  10. Test communication loss and recovery according to the approved test procedure.
  11. Save the final configuration and document the device settings.

Begin with a simple read request. Adding dozens of registers before proving the basic communication settings only creates a larger collection of things that can be wrong.

9. Worked example: Reading a VFD register

Consider a hypothetical VFD with the following documented parameters:

  • Slave address: 2
  • Baud rate: 19200
  • Data bits: 8
  • Parity: Even
  • Stop bits: 1
  • Output-frequency register: holding-register reference 40001
  • Scaling: 0.01 Hz
  • Read function: 03

Assume the engineering software expects zero-based protocol offsets.

9.1 Configure the serial connection

Set the master to 19200, 8, E, 1 and configure the device address as 2.

Confirm that the physical connection uses the supported serial interface and that the wiring follows the manufacturer's diagram.

9.2 Configure the read request

The request uses function code 03 and starting offset 0 to read one holding register.

Conceptually, the request contains:

Field Value
Slave address 2
Function code 03
Starting offset 0
Quantity 1 register

The master communication library or PLC instruction normally constructs the complete RTU frame, including its CRC.

9.3 Interpret the response

Suppose the raw register value is 4750.

Using the documented scaling:

\[ 4750 \times 0.01 = 47.50\text{ Hz} \]

The interpreted output frequency is 47.50 Hz.

This example demonstrates the setup process. The register address, scale factor, and raw value are hypothetical and must not be copied into a real VFD project without checking its manual.

10. Read versus write operations

Reading a value is generally the safest first step during commissioning. Writing values can change device behavior and requires more careful validation.

Read examples

  • Read drive output frequency.
  • Read motor current.
  • Read energy-meter measurements.
  • Read remote I/O input status.
  • Read device fault or status words.

Write examples

  • Write a speed reference.
  • Change an approved parameter.
  • Set a supported digital output.
  • Issue a command through a documented control register.

Before writing, verify:

  • The register is writable.
  • The function code is supported.
  • The value is within the documented range.
  • The device is in the required operating mode.
  • The operation is permitted under the site's safety and change-control rules.
  • The effect can be verified from feedback or status data.

A write acknowledgement indicates that the protocol request was accepted at the relevant communication level. It does not necessarily prove that the commanded physical action occurred.

11. Validate the setup

Do not mark a Modbus integration complete just because the master reports a successful transaction. Verify the data from end to end.

11.1 Communication validation

  • Master and slave use compatible baud rate and serial framing.
  • Slave address is correct and unique.
  • Correct physical interface is selected.
  • Wiring and connector termination follow the design.
  • A documented register can be read successfully.
  • No unexplained CRC errors or timeouts are present.
  • The response matches the requested function and address.

11.2 Data validation

  • Register offset matches the software's addressing convention.
  • Data type and signedness are correct.
  • Scaling and engineering units match the manual.
  • Byte and word order are correct for multiregister values.
  • Read values are plausible compared with the device display or an independent measurement.
  • Bit fields are decoded according to the documented definitions.

11.3 Operational validation

  • Polling interval meets the application requirement.
  • Communication loss is detected and reported.
  • Stale values are not silently treated as fresh measurements.
  • Recovery after communication loss is verified.
  • Write operations are tested only where authorized.
  • Configuration and test results are recorded.

12. Common setup mistakes

Mistake Result Corrective action
Wrong slave address Timeout or response from another device Verify physical device address and master target
Duplicate slave addresses Conflicting or corrupted responses Assign unique addresses
Baud-rate mismatch No valid response or framing errors Match the documented serial settings
Parity mismatch Framing errors or invalid communication Configure compatible parity and stop bits
RS-232 converter used for an RS-485 device Electrical incompatibility and no communication Use a converter matching the device interface
Wrong function code Exception response or unsupported operation Use the function documented for the register
Wrong register offset Illegal-address response or incorrect data Check reference notation and zero-based addressing
Wrong data type Incorrect or implausible values Verify signedness, width, and representation
Wrong scaling factor Values are consistently too high or low Apply the documented engineering conversion
Wrong word order Incorrect 32-bit values Verify the manufacturer's data representation
Timeout set too low False communication failures Use realistic device response timing
Too many individual requests Slow update cycle Group supported contiguous register reads

13. Configuration records and maintenance

For each Modbus RTU device, keep a configuration record that allows another technician to reproduce the setup without guesswork.

Record:

  • Machine, cabinet, and device tag.
  • Manufacturer, model, and firmware where relevant.
  • Serial interface type.
  • Slave address.
  • Baud rate, data bits, parity, and stop bits.
  • Wiring diagram and cable identification.
  • Master port or communication module.
  • Register map document and revision.
  • Register addresses, function codes, data types, and scaling.
  • Polling interval, timeout, and retry settings.
  • Known limitations and approved write operations.
  • Test results and date of last verified change.

For replacement devices, verify compatibility before installation. A replacement may support Modbus RTU but use a different address configuration, register map, scaling scheme, or firmware-dependent behavior.

14. Interview questions and answers

Q1. Which parameters must match between a Modbus RTU master and slave?

The baud rate, data bits, parity, and stop-bit configuration must be compatible. The master must also address the correct slave.

Q2. What happens if two devices have the same slave address?

They may both respond to a request addressed to that number, causing overlapping responses and communication errors.

Q3. Why is the register map necessary?

It defines the meaning of each register, the address convention, supported function codes, data types, scaling, access permissions, and any device-specific restrictions.

Q4. Why might register 40001 be entered as address 0 in software?

Some manuals use one-based reference notation, while the protocol request uses a zero-based address offset. Software conventions vary, so the actual mapping must be verified.

Q5. What is the difference between baud rate and parity?

Baud rate describes the serial signaling speed. Parity is an optional character-level error-checking bit.

Q6. Why can a successful read still produce an incorrect measurement?

The address may be valid while the value is interpreted using the wrong data type, scaling factor, unit, or byte/word order.

Q7. How should a technician commission a new Modbus RTU device?

Confirm the interface and documentation, configure the address and serial parameters, verify wiring, read a known register, validate data interpretation, test error handling, and document the final configuration.

Q8. Why should a technician avoid writing undocumented registers?

An undocumented register may alter configuration or operating behavior, have a different meaning, or be reserved. Incorrect writes can disrupt equipment operation.

15. Final mental model

A working Modbus RTU setup requires four layers to agree:

  1. Physical connection: The master and slave use compatible interfaces and correctly installed wiring.
  2. Serial communication: Baud rate, data bits, parity, and stop bits are compatible.
  3. Protocol request: The correct slave address, function code, and register offset are used.
  4. Data interpretation: Register width, signedness, scaling, units, and word order are correct.

If communication fails, begin with the physical connection and serial parameters before investigating the register map. If communication succeeds but the value is wrong, focus on addressing conventions and data interpretation.
