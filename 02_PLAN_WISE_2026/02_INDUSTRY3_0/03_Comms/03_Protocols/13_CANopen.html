CANopen: Industrial Communication Protocol Based on CAN

1. Introduction to CANopen

CANopen is a higher-level communication protocol built on the Controller Area Network (CAN). It defines how devices identify themselves, organize data, exchange commands, report status, and manage network communication.

CAN defines the underlying frame transmission, arbitration, and error handling. CANopen builds on that foundation by defining standardized communication objects, device profiles, network management, and application-level behavior.

CANopen is commonly used in:

  • Servo drives and motion-control systems.
  • Encoders and position sensors.
  • Distributed I/O modules.
  • Embedded industrial controllers.
  • Mobile machinery and hydraulic control systems.
  • Battery and energy-management equipment.
  • Specialized machines requiring compact, deterministic communication.

For industrial maintenance, CANopen is particularly relevant when a controller communicates with a drive, encoder, or remote I/O module through a CAN interface.

2. CANopen Architecture

A typical CANopen network contains a managing controller and several CANopen devices connected through a CAN bus.

        PLC / Industrial Controller
             CANopen Manager
                    |
                    |
             CAN_H / CAN_L
                    |
       +------------+------------+
       |            |            |
   Servo Drive   Encoder      Remote I/O
   CANopen Node  CANopen Node  CANopen Node
       |            |            |
    Motor        Position     Sensors /
    Control      Feedback     Actuators

The controller may perform network-management functions, configure devices, exchange process data, and monitor faults. The actual capabilities depend on the controller, device implementation, and selected CANopen profile.

2.1 Main components

Component Function
CAN physical layer Provides the electrical communication bus
CAN controller Handles CAN frame transmission and reception
CANopen protocol stack Implements CANopen communication and device behavior
CANopen manager Coordinates network management and may configure devices
CANopen device or node Provides application functions such as drive control or measurement
Object dictionary Organizes device parameters and application data
EDS file Describes supported device objects and configuration information
Configuration tool Configures communication settings, parameters, and process data
CAN interface or analyzer Provides communication access and diagnostic visibility

A CANopen manager may be implemented in a PLC, industrial controller, or dedicated device. Not every CANopen network requires the same management arrangement.

3. CAN Versus CANopen

Understanding this distinction is essential before configuring or troubleshooting a CANopen device.

Feature CAN CANopen
Technology level Physical and data-link communication foundation Higher-level communication protocol
Message identifiers Used for message identification and arbitration Assigned according to CANopen communication rules
Data interpretation Application-specific unless defined elsewhere Standardized communication objects and profiles
Device parameters No universal CAN parameter model Organized through an object dictionary
Network management Not universally defined by CAN itself Defines network-management mechanisms
Process data Application-specific Commonly exchanged using PDOs
Parameter access Depends on the application Commonly provided through SDOs
Device interoperability Requires compatible application definitions Improved through standardized profiles and object definitions

CANopen does not replace CAN. It uses CAN frames to implement a more structured device communication system.

4. CANopen Communication Model

CANopen defines several communication mechanisms, each intended for a different purpose.

The main ones are:

  • PDO: Process Data Object.
  • SDO: Service Data Object.
  • NMT: Network Management.
  • SYNC: Synchronization message.
  • EMCY: Emergency message.
  • Heartbeat: Node availability and state monitoring.
  • TIME: Time information, where supported and used.

These mechanisms use CAN frames with identifiers and payloads defined by CANopen conventions and device configuration.

5. Object Dictionary

The object dictionary (OD) is the central data structure of a CANopen device. It organizes communication parameters, configuration values, device identity information, and application data.

Objects are identified using a 16-bit index and, where applicable, an 8-bit sub-index.

For example:

Object index: 0x6040
Sub-index:    0x00
Meaning:      Controlword in the CiA 402 drive profile

The meaning of an index depends on the applicable CANopen specification and device profile. Do not assume that every index has a universal meaning across all CANopen devices.

5.1 Index and sub-index

  • Index: Identifies an object in the object dictionary.
  • Sub-index: Identifies an element within a structured object or array.
  • Data type: Defines how the value is represented.
  • Access type: Indicates whether the value is readable, writable, or subject to other access restrictions.
  • Default value: The manufacturer's initial or specified value, where defined.
  • Mapping properties: Determine whether an object can be included in a PDO.

An object may be read-only, write-only, read/write, or conditionally accessible. Some values may require a specific device state before they can be modified.

5.2 Common object dictionary areas

Index range Typical purpose
0x1000–0x1FFF Communication and device-related parameters
0x2000–0x5FFF Manufacturer-specific objects and application parameters
0x6000–0x9FFF Standardized device-profile objects, depending on the profile
0xA000–0xBFFF Additional standardized areas in applicable specifications

These ranges are a practical overview, not a substitute for the relevant CANopen specification and device documentation.

5.3 Important objects

Index Common meaning
0x1000 Device type
0x1001 Error register
0x1003 Pre-defined error field, where supported
0x1005 SYNC COB-ID
0x1008 Manufacturer device name, where supported
0x100A Manufacturer software version, where supported
0x1017 Producer heartbeat time
0x1018 Identity object
0x1400 onward Receive PDO communication parameters
0x1600 onward Receive PDO mapping parameters
0x1800 onward Transmit PDO communication parameters
0x1A00 onward Transmit PDO mapping parameters

The exact number of supported PDOs and available objects varies by device. Always check the device's EDS file and manual.

6. EDS Files

An Electronic Data Sheet (EDS) describes a CANopen device's communication capabilities and object dictionary information in a format that compatible engineering tools can interpret.

An EDS file may describe:

  • Vendor and product identity.
  • Supported communication objects.
  • Data types and access attributes.
  • Supported PDO communication parameters.
  • PDO-mappable objects.
  • Default values and configuration information.

An EDS file helps an engineering tool understand how to configure a device. It does not prove that the connected hardware is healthy, nor does it guarantee that every parameter in the project is valid for the actual device revision.

6.1 EDS versus actual device configuration

The EDS describes the device's supported capabilities. The active device configuration determines how the device is currently operating.

A mismatch may occur when:

  • The wrong EDS file is selected.
  • The EDS is intended for a different product or firmware revision.
  • The device supports fewer PDOs than the project expects.
  • The selected mapping is unsupported.
  • The configuration tool has stale device information.

For replacement devices, confirm the manufacturer, product code, revision and supported communication parameters before applying a saved configuration.

7. COB-IDs and CANopen Identifiers

CANopen uses Communication Object Identifiers (COB-IDs) to identify communication objects transmitted over CAN.

A COB-ID is associated with a CAN identifier and communication behavior. It is not simply the IP-style address of a device.

For conventional pre-defined CANopen communication, the identifier often depends on a function code and node ID.

The common simplified relationship is:

\[ \text{CAN identifier} = \text{Function code} + \text{Node ID} \]

This formula applies to the relevant pre-defined identifier arrangements, not every configurable CANopen COB-ID.

7.1 Common default identifier examples

For classic CANopen pre-defined connection sets, common identifier ranges include:

Communication object Typical identifier pattern
NMT 0x000
SYNC 0x080
EMCY 0x080 + Node ID
TPDO1 0x180 + Node ID
RPDO1 0x200 + Node ID
TPDO2 0x280 + Node ID
RPDO2 0x300 + Node ID
TPDO3 0x380 + Node ID
RPDO3 0x400 + Node ID
TPDO4 0x480 + Node ID
RPDO4 0x500 + Node ID
SDO server-to-client response 0x580 + Node ID
SDO client-to-server request 0x600 + Node ID
Heartbeat 0x700 + Node ID

These are common default arrangements for classic CANopen. Configurable COB-IDs, extended features, device profiles, and CANopen variants can use different assignments.

7.2 Example

For node ID 5:

  • TPDO1 commonly uses 0x185.
  • RPDO1 commonly uses 0x205.
  • SDO request commonly uses 0x605.
  • SDO response commonly uses 0x585.
  • Heartbeat commonly uses 0x705.

A CAN analyzer can use these patterns to help identify likely CANopen traffic. The observed identifier should still be checked against the actual network configuration.

8. Process Data Objects (PDOs)

A Process Data Object (PDO) transfers process data efficiently between CANopen devices.

PDOs are commonly used for frequently exchanged values such as:

  • Drive statusword.
  • Drive controlword.
  • Actual motor speed.
  • Target speed.
  • Encoder position.
  • Digital input and output states.
  • Application-specific measurement values.

PDO communication avoids the overhead of individually requesting every parameter through SDO transactions.

8.1 TPDO and RPDO

The terms are relative to the device being configured.

  • TPDO: Transmit Process Data Object. The device transmits the PDO.
  • RPDO: Receive Process Data Object. The device receives the PDO.

For a PLC communicating with a drive:

  • The drive's TPDO may contain statusword and actual speed.
  • The drive's RPDO may contain controlword and target speed.

From the drive's perspective, the first PDO is transmitted and the second is received.

8.2 PDO mapping

PDO mapping defines which object dictionary entries are carried in a PDO and how many bits each mapped value occupies.

For example, a drive's TPDO might contain:

Mapped object Example data size
Statusword 16 bits
Actual speed 32 bits
Total 48 bits

The payload uses 6 bytes, assuming those two objects are mapped consecutively with the stated sizes.

The exact mapping and data types depend on the device profile and configuration. Not every object is PDO-mappable.

8.3 Mapping configuration objects

Common PDO-related object areas include:

  • 0x1400 onward: RPDO communication parameters.
  • 0x1600 onward: RPDO mapping parameters.
  • 0x1800 onward: TPDO communication parameters.
  • 0x1A00 onward: TPDO mapping parameters.

Configuration procedures vary by device. Some devices require a PDO to be disabled before mapping changes are accepted, and others restrict which objects may be mapped.

8.4 PDO transmission types

PDOs may be configured for different transmission behaviors.

Transmission behavior Purpose
Synchronous cyclic Transmits at a configured interval of SYNC cycles
Synchronous acyclic Transmits in relation to SYNC when the relevant event occurs
Event-driven Transmits when a configured event occurs
Change-of-state Transmits when relevant data changes, subject to device configuration
Asynchronous Operates without depending on a SYNC cycle

Exact options and their semantics depend on the CANopen version and device implementation.

8.5 PDO troubleshooting

If a PDO is missing or contains incorrect data, verify:

  1. The expected COB-ID.
  2. The producer's node ID and communication state.
  3. The PDO's enabled or disabled state.
  4. Transmission type and event timing.
  5. The mapped object indices and sub-indices.
  6. Total mapped data length.
  7. The consumer's expected layout.
  8. Whether the device permits the configured mapping.
  9. Whether the producer is actually generating the required data.

A valid CAN frame can still contain data that the receiving controller interprets incorrectly.

9. Service Data Objects (SDOs)

An SDO provides access to an individual object dictionary entry. It is commonly used for device configuration, parameter reading, diagnostics, and non-cyclic data exchange.

Examples include:

  • Reading device identity.
  • Reading an error register.
  • Setting a communication parameter.
  • Configuring PDO mappings.
  • Adjusting a drive parameter.
  • Reading diagnostic information.

9.1 SDO client and server

The SDO client initiates an access request, and the SDO server responds.

For example:

PLC / CANopen Manager
        |
        | SDO read request
        v
CANopen Drive
        |
        | SDO response with value
        v
PLC / CANopen Manager

The PLC may act as an SDO client while the drive acts as an SDO server. The role depends on which device initiates the transaction.

9.2 Expedited and segmented transfers

  • Expedited transfer: Used for small values that fit within the expedited SDO transfer format.
  • Segmented transfer: Transfers data through multiple segments when required.
  • Block transfer: Supported by applicable CANopen implementations for more efficient larger transfers.

Support for particular transfer modes depends on the device and CANopen implementation.

9.3 SDO versus PDO

Property SDO PDO
Primary purpose Parameter access and configuration Process data exchange
Typical pattern Request and response Producer-to-consumer data transfer
Common use Read or write an object dictionary entry Exchange status, commands and measurements
Overhead Higher for repeated individual accesses Lower for cyclic process data
Timing Usually non-cyclic and transaction-based Often cyclic or event-driven
Object access Identifies an object index and sub-index Carries configured mapped objects

Use SDOs for parameter access and PDOs for process data. Repeatedly reading every fast-changing signal through SDOs is generally inefficient and can interfere with timely communication.

10. Network Management (NMT)

Network Management (NMT) controls the communication state of CANopen devices.

A device's NMT state determines which communication services are permitted. A device may be powered and visible on the bus while not being in the state required for ordinary process data exchange.

10.1 Main NMT states

State General behavior
Initializing Device performs startup initialization
Pre-operational SDO communication is available; ordinary PDO operation is generally not active
Operational PDO and other permitted communication services can operate
Stopped Most normal communication services are restricted, while specified management behavior may remain available

The exact permitted services must be checked against the applicable CANopen specification and device implementation.

10.2 Typical state transitions

A CANopen manager can request a device to enter a different NMT state using the applicable NMT command.

A typical commissioning sequence is:

  1. Device powers up and initializes.
  2. Device reaches pre-operational state.
  3. Manager configures parameters and PDOs as needed.
  4. Manager commands the device into operational state.
  5. The manager monitors node availability and application status.

Not every system uses exactly this sequence. Some devices apply stored configurations automatically or use other supported mechanisms.

10.3 NMT commands

Common NMT commands include:

  • Start remote node.
  • Stop remote node.
  • Enter pre-operational state.
  • Reset node.
  • Reset communication.

Reset commands can interrupt communication and affect machine behavior. Use them only when authorized and when the consequences are understood.

11. SYNC and Synchronous Communication

The SYNC message provides a timing reference for synchronous CANopen communication.

A manager or configured producer may transmit SYNC messages periodically. Devices configured for synchronous operation use this timing reference to coordinate selected PDO transmissions or application updates.

11.1 Why SYNC is useful

  • Coordinates updates across multiple devices.
  • Supports periodic process-data exchange.
  • Helps align drive commands and feedback.
  • Can improve timing consistency in distributed control applications.

SYNC does not by itself guarantee that every application task executes simultaneously. Device processing, bus arbitration, configured transmission behavior and controller scheduling still matter.

11.2 Troubleshooting SYNC

Check:

  • Whether the expected SYNC producer is active.
  • Whether the configured COB-ID matches the network design.
  • Whether the SYNC interval is correct.
  • Whether the devices are configured for synchronous operation.
  • Whether the relevant PDO transmission types are correct.
  • Whether the bus is experiencing errors or excessive load.

If synchronous PDOs are not updating, check SYNC behavior before assuming that the drive or I/O device has failed.

12. Emergency Messages (EMCY)

An EMCY message reports an error condition detected by a CANopen device.

Examples include:

  • Internal hardware faults.
  • Voltage-related faults.
  • Temperature faults.
  • Communication-related errors.
  • Device-profile-specific application errors.

The precise error code and associated data depend on the device and applicable profile.

12.1 EMCY versus ordinary status data

An EMCY message is intended to report an error condition. It is different from ordinary PDO status data, which may continuously report a device's operating state.

EMCY reporting is useful for fault diagnosis, but receiving no EMCY does not prove that the device is healthy. A device may be disconnected, unable to transmit, or configured differently.

12.2 Diagnostic approach

  1. Capture the EMCY identifier and payload.
  2. Identify the node that transmitted the message.
  3. Decode the error code using the applicable device documentation.
  4. Check the device's own diagnostic registers and status.
  5. Determine whether the fault is active, historical or application-specific.
  6. Correct the underlying problem before clearing or resetting the device.

Do not assume that the same manufacturer-specific error code means the same thing across unrelated devices.

13. Heartbeat and Node Guarding

CANopen provides mechanisms for monitoring whether a node is communicating and what state it reports.

13.1 Heartbeat

Heartbeat allows a producer to periodically report its NMT state. A consumer monitors the expected heartbeat behavior and can detect when a node stops reporting within the configured timing requirements.

Relevant configuration includes:

  • Producer heartbeat time, commonly associated with object 0x1017.
  • Consumer heartbeat configuration, commonly associated with object 0x1016.
  • Expected node identity.
  • Monitoring timeout.

Heartbeat monitoring can reveal node unavailability, but it does not prove that every application function or PDO is correct.

13.2 Node guarding

Node guarding is an older node-monitoring mechanism supported by some CANopen implementations. It uses request/response behavior and toggle information to monitor a node.

Heartbeat is widely used in newer CANopen systems, while node guarding may remain relevant in legacy equipment.

Do not assume that every device supports both mechanisms or that they are configured simultaneously.

13.3 Heartbeat fault diagnosis

If a heartbeat consumer reports a node timeout:

  1. Verify that the expected node ID is correct.
  2. Confirm that the producer's heartbeat is enabled.
  3. Check the configured producer interval and consumer timeout.
  4. Inspect bus traffic for the expected heartbeat identifier.
  5. Check whether the node is powered and in a valid communication state.
  6. Review the physical bus and communication error counters.
  7. Confirm that timing and monitoring parameters are compatible.

A heartbeat timeout can be caused by a disconnected device, an incorrect node ID, a missing producer configuration, bus errors or an inappropriate timeout.

14. CANopen Device Profiles and CiA 402

CANopen profiles define standardized behavior for particular classes of devices.

Examples include profiles for drives, encoders, measurement devices and I/O equipment. One important profile in industrial automation is CiA 402, used for drives and motion-control devices.

14.1 CiA 402 overview

CiA 402 standardizes important drive-related objects and operating behavior, including:

  • Controlword.
  • Statusword.
  • Modes of operation.
  • Target values.
  • Actual values.
  • Drive state-machine behavior.
  • Fault and operating-state reporting.

The exact supported functions and operating modes depend on the drive.

14.2 Common CiA 402 objects

Index Common meaning
0x6040 Controlword
0x6041 Statusword
0x6060 Modes of operation
0x6061 Modes of operation display
0x6064 Position actual value
0x606C Velocity actual value
0x607A Target position
0x60FF Target velocity

Not every drive supports every listed object or mode. Verify the device's CiA 402 implementation and documentation.

14.3 Drive state machine

A CiA 402 drive follows a defined state machine. Common states include:

  • Not ready to switch on.
  • Switch on disabled.
  • Ready to switch on.
  • Switched on.
  • Operation enabled.
  • Quick stop active.
  • Fault reaction active.
  • Fault.

The controlword requests transitions, and the statusword reports the resulting state.

A drive may be communicating correctly while remaining disabled because the required state transition conditions have not been satisfied.

14.4 Drive troubleshooting example

Symptom: A PLC can read the drive's statusword, but the motor does not run.

Check:

  1. Whether the drive is in a fault state.
  2. Whether the controlword is requesting the intended transition.
  3. Whether the statusword confirms the expected state.
  4. Whether the selected operating mode is supported and active.
  5. Whether the target value is mapped and updated correctly.
  6. Whether hardware enable, safety functions and drive interlocks permit operation.
  7. Whether the drive reports a separate application or power-stage fault.

Do not force the drive into an operating state by bypassing safety conditions. A successful communication test does not establish that the machine is safe to move.

15. CANopen Configuration and Commissioning

A typical CANopen commissioning process includes network settings, device identity, object configuration, PDO mapping and application validation.

15.1 Configuration parameters

Parameter Purpose
Node ID Identifies a node within the applicable CANopen network conventions
Bit rate Sets CAN communication timing
EDS file Describes device capabilities for configuration tools
COB-ID Identifies a communication object on the CAN network
PDO mapping Defines the process data carried by a PDO
Transmission type Determines when a PDO is transmitted
SYNC configuration Defines synchronization behavior
Heartbeat producer time Sets the node's heartbeat reporting interval
Heartbeat consumer time Sets monitoring behavior for other nodes
Device profile Defines standardized application behavior

15.2 Commissioning checklist

  • Confirm the CAN physical layer and wiring.
  • Verify termination and cable topology.
  • Confirm compatible bit rates and timing.
  • Assign unique node IDs where required.
  • Load the correct EDS file into the engineering tool.
  • Verify device identity and supported profile.
  • Configure and verify the object dictionary parameters.
  • Configure PDO communication parameters and mappings.
  • Confirm NMT state transitions.
  • Verify SYNC behavior if synchronous communication is used.
  • Configure heartbeat or another supported monitoring method.
  • Check EMCY and device diagnostic behavior.
  • Validate the application's actual data and control behavior.
  • Save the configuration and document the final network.

15.3 Configuration backups

Save:

  • The PLC or CANopen manager project.
  • Device parameter backups.
  • EDS files and version information.
  • PDO mappings and communication parameters.
  • Node ID and bit-rate records.
  • Device firmware information.
  • Network topology and wiring records.
  • A known-good commissioning baseline.

A replacement device may have the same model but a different firmware revision, supported object set or default configuration. A saved project should be verified against the actual hardware before use.

17. Practical Industrial Example: PLC and CANopen Servo Drive

Consider a PLC controlling a servo drive over CANopen.

The PLC needs to:

  • Enable the drive through the appropriate state-machine sequence.
  • Send a target value.
  • Receive status information.
  • Monitor communication health.
  • Detect device errors.

A conceptual communication arrangement is:

PLC / CANopen Manager
        |
        | RPDO: Controlword, target value
        v
CANopen Servo Drive
        |
        | TPDO: Statusword, actual value
        v
PLC / CANopen Manager

Additional communication:
SDO    → Parameter access and configuration
NMT    → Device communication-state management
SYNC   → Synchronization when configured
EMCY   → Error reporting
Heartbeat → Node availability monitoring

The exact mapping, PDO transmission types, drive state transitions and timing must be taken from the drive's supported profile and the machine's control design.

17.1 Fault scenario: drive communicates but does not enable

Observation: SDO communication works, and the PLC can read the statusword, but the drive never reaches Operation Enabled.

Diagnostic process:

  1. Read the current statusword and identify the reported state.
  2. Check the controlword being sent by the PLC.
  3. Confirm that the PDO mapping matches the controlword object.
  4. Verify that the PDO is actually transmitted and received.
  5. Confirm that the selected mode of operation is supported.
  6. Inspect drive alarms and fault history.
  7. Check hardware enable and applicable safety conditions.
  8. Follow the manufacturer's prescribed state-transition sequence.
  9. Validate the response under the approved commissioning procedure.

Key lesson: Communication availability and application readiness are different conditions.

18. CANopen Versus EtherNet/IP and EtherCAT

Feature CANopen EtherNet/IP EtherCAT
Underlying network CAN Standard Ethernet with CIP Ethernet-based real-time fieldbus
Typical topology Shared CAN bus Switched Ethernet networks Commonly line, tree or other supported EtherCAT topologies
Device configuration Object dictionary and EDS Device profiles, EDS and controller configuration Device descriptions and EtherCAT master configuration
Process data PDOs I/O connections and assemblies Process data mapped through the EtherCAT process image
Parameter access SDOs Explicit messaging and device-specific services Mailbox protocols and supported services
Synchronization SYNC and profile-specific mechanisms Connection and application timing mechanisms Distributed Clocks and other EtherCAT timing mechanisms
Typical use Embedded devices, drives and compact distributed control PLC, remote I/O, drives and industrial automation High-performance motion and real-time automation

These technologies have overlapping applications but different physical layers, configuration models and timing characteristics.

CANopen is often suitable for embedded and compact distributed systems. EtherCAT is often selected when high-performance synchronized control and fast process-data exchange are central design requirements.

19. Common Misconceptions

Misconception 1: CANopen is only CAN with a different name.

CANopen adds standardized communication services, an object dictionary, network management and device-profile behavior.

Misconception 2: An SDO is the best way to transmit every process value.

SDOs are useful for parameter access. PDOs are generally better suited to repeated process-data exchange.

Misconception 3: A heartbeat proves that the device is healthy.

Heartbeat confirms that a node is reporting its communication state. It does not prove that its application, outputs or physical functions are correct.

Misconception 4: A correct node ID guarantees communication.

The node also needs compatible bit-rate settings, wiring, termination, configuration and an appropriate communication state.

Misconception 5: A device that is pre-operational is necessarily faulty.

A device may be deliberately left pre-operational while the manager configures parameters. The correct expected state depends on the system's startup design.

Misconception 6: Every CANopen device implements the same objects.

Standardized profiles define common objects and behavior, but device capabilities and manufacturer-specific extensions vary.

20. Interview Questions and Answers

Q1. What is CANopen?

CANopen is a higher-level communication protocol built on CAN. It standardizes device communication, parameter organization, process-data exchange and network management.

Q2. What is an object dictionary?

It is the structured collection of a CANopen device's communication parameters, identity information, configuration objects and application data.

Q3. What is the difference between PDO and SDO?

PDOs exchange process data efficiently, often cyclically or in response to events. SDOs access object dictionary entries through request-and-response transactions.

Q4. What are TPDO and RPDO?

TPDO means Transmit Process Data Object, and RPDO means Receive Process Data Object, from the perspective of the configured device.

Q5. What is a COB-ID?

A COB-ID identifies a CANopen communication object on the CAN network. Common default identifier patterns depend on the function and node ID, but configurable assignments are also possible.

Q6. What is NMT?

Network Management controls CANopen device communication states, including pre-operational, operational and stopped states.

Q7. What is SYNC used for?

SYNC provides a timing reference for devices configured for synchronous communication, helping coordinate selected process-data updates.

Q8. What is an EMCY message?

It is a CANopen emergency message used to report a detected error condition. Its payload must be decoded using the applicable specification and device documentation.

Q9. What is heartbeat monitoring?

A heartbeat producer periodically reports its NMT state. A consumer monitors the reports and can detect when the expected node communication stops.

Q10. What is CiA 402?

CiA 402 is a CANopen device profile used for drives and motion-control devices. It defines common objects and state-machine behavior for drive control.

Q11. Why can an SDO work while PDO communication fails?

The device may be reachable for parameter access while its PDO is disabled, incorrectly mapped, configured with the wrong COB-ID, or restricted by its NMT state.

Q12. How would you troubleshoot a CANopen drive that is visible but not operational?

I would verify the node ID and bit rate, inspect its NMT state, check SDO access and PDO configuration, decode the statusword and EMCY information, then investigate the drive state machine, interlocks and applicable safety conditions.

22. Final Mental Model

CANopen becomes easier to understand when its responsibilities are separated:

  • CAN: Provides the underlying frame transmission, arbitration and error handling.
  • Object dictionary: Defines how parameters and application data are organized.
  • PDO: Transfers mapped process data.
  • SDO: Reads and writes object dictionary entries.
  • NMT: Manages device communication states.
  • SYNC: Coordinates configured synchronous communication.
  • EMCY: Reports device error conditions.
  • Heartbeat: Monitors node availability and communication state.
  • Device profiles: Standardize application behavior, such as drive control under CiA 402.

When diagnosing CANopen, first establish physical CAN communication, then verify node identity and NMT state, inspect the object dictionary and PDO/SDO configuration, and finally validate application behavior. A healthy CAN bus is only the foundation; the protocol configuration and device state determine whether the automation system actually works.
