CC-Link IE: Industrial Ethernet Networking

1. Purpose and scope

CC-Link IE is a family of industrial Ethernet-based communication technologies developed within the CC-Link ecosystem. It extends the CC-Link automation ecosystem beyond classic fieldbus communication and supports high-performance communication between controllers, distributed devices, and industrial systems.

CC-Link IE is relevant to factory automation involving PLCs, remote I/O, motion control, intelligent devices, and coordinated machine systems. It is particularly important in Mitsubishi-oriented automation environments, although compatible products are available from multiple manufacturers.

The name CC-Link IE does not refer to just one network variant. Different versions have different architectures, purposes, performance characteristics, and supported devices. It is therefore important to identify the exact variant before configuring or troubleshooting a network.

This topic covers the overall CC-Link IE family, its major variants, architecture, configuration concepts, diagnostics, maintenance, and industrial applications.

2. Where CC-Link IE fits in industrial automation

SCADA / MES / Industrial applications

                 |

               devices    field devices

The actual architecture depends on the CC-Link IE variant and equipment used. Some variants are designed for controller-to-controller communication, some for high-speed I/O and motion applications, and others for broader industrial Ethernet connectivity.

Common applications include:

  • High-speed cyclic data exchange between controllers and distributed I/O.
  • Coordinated control of multiple machine sections.
  • Motion-control systems requiring predictable communication timing.
  • Communication between PLCs and intelligent automation devices.
  • Integration of networked equipment into larger factory automation systems.
  • Data exchange between production machines and supervisory systems through appropriate network interfaces.

CC-Link IE is a control-network technology, not a synonym for ordinary office Ethernet. A network can use Ethernet technology while still requiring specific industrial hardware, configuration, topology, and engineering practices.

3. Understand the CC-Link IE family

The following variants are important to distinguish. Product names and available features depend on the generation and specification.

Variant General purpose Key distinction
CC-Link IE Control Controller-level communication Designed for high-capacity communication between controllers
CC-Link IE Field Field-level industrial communication Connects controllers with distributed field devices
CC-Link IE Field Network Basic Ethernet-based communication using a simpler implementation model Intended to make compatible field-level communication possible on supported Ethernet interfaces
CC-Link IE TSN Time-Sensitive Networking-based industrial communication Uses TSN technology to support converged, time-aware industrial communication

These names are related but not interchangeable. A device supporting CC-Link IE Field does not automatically support CC-Link IE TSN or CC-Link IE Control.

3.1 CC-Link IE Control

CC-Link IE Control is intended for communication at the controller level, such as data exchange between PLCs or other supported controllers.

Typical applications include:

  • Communication between coordinated production-line controllers.
  • Exchange of controller-level process data.
  • Integration of machine groups within a larger automation system.

Its network architecture, supported devices, and configuration requirements must be verified against the specific generation of controller and network equipment.

3.2 CC-Link IE Field

CC-Link IE Field is intended for field-level communication between controllers and supported field devices.

Typical applications include:

  • Remote I/O.
  • Networked drives and other intelligent devices.
  • Machine-level control and distributed data exchange.
  • Industrial systems requiring cyclic communication with field equipment.

The exact topology and hardware requirements depend on the specification and equipment generation.

3.3 CC-Link IE Field Network Basic

CC-Link IE Field Network Basic provides a more accessible implementation model for supported Ethernet interfaces and devices.

It should not be treated as identical to full CC-Link IE Field. Device support, timing, configuration, topology, and performance capabilities can differ.

When selecting this variant, verify the device's supported protocol implementation, PLC or controller compatibility, update-time requirements, and engineering software support.

3.4 CC-Link IE TSN

CC-Link IE TSN combines CC-Link IE technology with Time-Sensitive Networking (TSN), a set of IEEE 802.1 standards intended to support time-aware and coordinated Ethernet traffic.

Depending on the supported implementation, TSN can help coordinate time-critical control traffic with other network traffic and support more integrated industrial network designs.

TSN does not automatically make every Ethernet device time-sensitive or deterministic. The devices, switches, configuration, traffic scheduling, synchronization, and engineering design must all support the required functionality.

4. Ethernet-based network architecture

Unlike classic CC-Link, which uses a dedicated fieldbus physical layer, CC-Link IE uses Ethernet-based network technology. However, the exact physical and logical architecture varies by variant.

A simplified field-level architecture may look like this:

PLC CPU
   |
   v
CC-Link IE network interface
   |
   v
Industrial Ethernet network
   |
   +------ Remote I/O station
   |
   +------ Networked drive
   |
   +------ Intelligent device
   |
   +------ Compatible controller

A controller-level network may instead connect multiple controllers, while a TSN-based network may be designed to coordinate time-critical control traffic with other supported Ethernet traffic.

4.1 Main components

Controller or PLC CPU: Executes the machine logic and consumes data received from the network.

Network interface: Connects the controller to the selected CC-Link IE network. It may be integrated into the controller or provided by a communication module.

Industrial Ethernet switch: Connects network nodes in supported switched Ethernet topologies. The required switch capabilities depend on the variant, topology, redundancy design, and TSN requirements.

Remote I/O station: Exchanges input, output, status, and other supported cyclic data with the controller.

Networked drive or motion device: Exchanges control commands, status, references, and feedback according to its supported communication profile.

Engineering software: Configures network parameters, device assignments, data mapping, diagnostics, and controller communication settings.

Network cabling: Uses the specified Ethernet cable and connectors for the installation environment, distance, and required data rate.

5. Network topology and redundancy

Topology describes how network devices and links are physically connected. A suitable topology must be selected for the specific CC-Link IE variant and equipment.

Common industrial Ethernet arrangements include line, star, and ring structures, but not every CC-Link IE variant supports every arrangement in the same way.

5.1 Line topology

Controller → Device 1 → Device 2 → Device 3

Advantages:

  • Can reduce the number of separate home-run cables.
  • May be suitable for compact machine layouts.
  • Can simplify cabling when supported by the devices.

Considerations:

  • A cable break or failure at an intermediate device may disconnect downstream devices.
  • Device forwarding capabilities and supported connection arrangements must be verified.
  • The actual failure impact depends on the topology and equipment.

5.2 Star topology

               Device 1
                  |
Controller → Ethernet switch → Device 2
                  |
               Device 3

Advantages:

  • Centralized connection management.
  • Easier isolation of some individual link faults.
  • Convenient for equipment distributed around a machine or cabinet.

Considerations:

  • The central switch is a possible common failure point.
  • Switch specifications must match the intended network.
  • Traffic load, port count, and redundancy requirements must be considered.

5.3 Ring topology

Controller → Device 1 → Device 2
     ↑                       |
     +-----------------------+

A supported ring architecture can provide an alternate communication path when a link fails. The recovery mechanism and allowable topology depend on the network specification and devices.

A ring should not be assumed to provide redundancy merely because the cables form a physical loop. The selected network must support the intended ring operation, and the topology must be configured correctly.

5.4 Redundancy considerations

When designing redundancy, verify:

  • Whether the exact CC-Link IE variant supports the intended redundancy method.
  • Which devices or switches support it.
  • Whether additional configuration is required.
  • Expected recovery behavior after a link or device failure.
  • Whether the control application tolerates the recovery interval.
  • Whether a common power supply, switch, cabinet, or cable route remains a single point of failure.

Redundancy reduces some failure risks but does not eliminate every possible network outage.

6. Cyclic communication and process data

Cyclic communication is the repeated exchange of configured data between controllers and network devices.

For example, a PLC can receive a remote I/O status word, evaluate it in its control program, and send a command to another network device. The data exchange repeats as part of the configured communication process.

Remote device data
        ↓
CC-Link IE network
        ↓
Controller communication memory
        ↓
PLC program logic
        ↓
Output or command data
        ↓
CC-Link IE network
        ↓
Remote device

The precise implementation of communication memory and data refresh depends on the controller and network variant.

6.1 Types of exchanged data

Data category Examples Typical purpose
Discrete status Ready, running, alarm, interlock Sequence control and status monitoring
Discrete commands Start request, reset request, mode command Control requests
Numeric references Speed, position, torque reference Drive or motion control
Feedback values Actual speed, position, current Monitoring and closed-loop functions where supported
Diagnostic data Fault code, warning status, device health Troubleshooting and maintenance
Parameter data Device configuration values Setup or on-demand access where supported

The supported data types, sizes, and transfer mechanisms depend on the device profile and network implementation.

6.2 Update time and response time

Network update time is not the same as the total machine response time.

The complete response can include:

  • Sensor response and input filtering.
  • Network data update.
  • Controller communication refresh.
  • PLC program execution.
  • Output update.
  • Drive or actuator processing time.

When a machine exhibits a timing problem, measure the complete signal path. Increasing network speed alone may not solve a delay caused by slow input filtering, a long PLC task, or actuator response.

7. Configuration and engineering

CC-Link IE configuration must match the installed controller, network interfaces, connected devices, and chosen variant.

7.1 Configuration elements

Typical configuration work includes:

  • Selecting the correct CC-Link IE variant.
  • Confirming the supported network interface and firmware.
  • Assigning station or device identities as required.
  • Configuring network parameters and topology.
  • Defining device connections and cyclic data assignments.
  • Setting controller communication and refresh parameters.
  • Configuring any supported redundancy or synchronization features.
  • Checking the device compatibility and configuration diagnostics.
  • Saving the project and documenting the approved configuration.

The exact parameter names and configuration process vary by product generation. Use the engineering software and manual appropriate to the installed hardware.

7.2 Mitsubishi engineering software

Mitsubishi engineering environments commonly used in factory automation include GX Works2 and GX Works3, depending on the PLC family and supported network hardware.

The engineering workflow may involve configuring the network in the project, assigning devices, defining data exchange, transferring the configuration, and checking diagnostics.

Do not assume that every CC-Link IE variant is configured through the same menu or supports every PLC generation. Confirm compatibility before selecting the software workflow.

7.3 Device replacement and configuration backups

Before replacing a network interface or station:

  1. Record the exact model, hardware revision, and firmware where available.
  2. Back up the PLC project and applicable network configuration.
  3. Record the current network identity, device assignments, and data mapping.
  4. Verify the replacement device supports the same variant and required features.
  5. Restore or recreate the configuration using the approved procedure.
  6. Validate communication and process behavior after replacement.

A physically compatible Ethernet connector does not guarantee protocol compatibility.

8. Addressing, device identity, and data mapping

CC-Link IE devices must be correctly identified and configured in the network. The exact addressing model depends on the variant and the engineering environment.

Do not automatically apply classic CC-Link station-number rules or RX, RY, RWr, and RWw link-device conventions to every CC-Link IE implementation. Those conventions are associated with particular classic CC-Link configurations and may not describe the data mapping used by another CC-Link IE variant.

8.1 Common mapping mistakes

  • Configuring a device under the wrong network variant.
  • Selecting an incompatible device profile or model.
  • Assigning the wrong cyclic data size.
  • Mapping a status word to the wrong PLC memory area.
  • Using the wrong bit offset or word offset.
  • Interpreting a signed value as unsigned.
  • Misinterpreting a multiword value's byte or word order.
  • Changing the device configuration without updating the PLC program.
  • Restoring an older project with assignments that no longer match the installed devices.

8.2 Trace a data point end to end

For a networked drive, trace a status value through the full path:

  1. Identify the actual drive status or monitoring parameter.
  2. Confirm how the drive exposes that parameter over the selected network.
  3. Verify the configured cyclic data assignment.
  4. Find the corresponding PLC memory or communication data location.
  5. Check the PLC logic that interprets the value.
  6. Compare the PLC value against the drive's local display or diagnostic screen.
  7. Confirm that the HMI or SCADA application reads the correct PLC tag.

This method is particularly useful during machine retrofits because it distinguishes a network fault from a mapping or application fault.

9. CC-Link IE and time-sensitive control

Some CC-Link IE variants are intended for high-performance control communication. CC-Link IE TSN adds technologies designed to coordinate traffic according to timing requirements.

9.1 What TSN contributes

Time-Sensitive Networking is a family of IEEE 802.1 Ethernet standards. Depending on the features implemented, TSN can provide capabilities such as:

  • Time synchronization between supported network devices.
  • Scheduling or prioritization of time-sensitive traffic.
  • Traffic shaping and coordinated transmission.
  • Improved coexistence between suitable control traffic and other Ethernet traffic.
  • Mechanisms that help meet defined latency and timing requirements.

Not every TSN device implements every TSN feature. The network must be engineered around the capabilities shared by the participating devices.

9.2 Determinism is an end-to-end property

Predictable communication depends on more than the network label. Relevant factors include:

  • Controller task configuration.
  • Network cycle and traffic scheduling.
  • Switch and endpoint capabilities.
  • Time synchronization.
  • Data volume and message patterns.
  • Topology and network load.
  • Application processing time.
  • Device firmware and supported protocol functions.

For a motion-control application, verify the manufacturer's timing and synchronization requirements rather than assuming ordinary Ethernet performance is sufficient.

10. Troubleshooting CC-Link IE

Troubleshooting should proceed from physical connectivity to network configuration, cyclic data, and application behavior.

10.1 Diagnostic sequence

  1. Identify the exact CC-Link IE variant and hardware models.
  2. Check controller, communication module, switch, and device power.
  3. Inspect link indicators and network port status.
  4. Verify cable connections, cable type, and topology.
  5. Review network diagnostics and device error codes.
  6. Confirm that configured devices match the installed hardware.
  7. Verify device identities, network parameters, and supported topology.
  8. Check cyclic data assignments and controller memory mapping.
  9. Compare received data with the source device's actual status.
  10. Inspect controller diagnostics, program execution, and application tags.
  11. Test recovery using the approved procedure.
  12. Record the cause, correction, and validation evidence.

10.2 Symptom-to-cause matrix

Symptom Possible cause First checks
Controller cannot establish network communication Incorrect configuration, interface fault, cable problem Module status, port status, network parameters
One device is missing Device power, cable fault, identity mismatch, incompatible hardware Local device diagnostics, connection, configuration
Multiple devices fail together Common cable path, switch, controller interface, shared configuration issue Master/controller diagnostics, switch, shared links
Network communication works but data is wrong Mapping, data type, or application logic error Data assignments, offsets, source-device values
Intermittent communication Cable or connector problem, electrical noise, switch issue, device fault Error counters, event history, physical inspection
Communication degrades under load Network design, traffic load, configuration, device resource limits Network diagnostics, update timing, traffic pattern
Link failure causes prolonged outage Unsupported or misconfigured redundancy, recovery limitations Topology, supported recovery method, device logs
Device communicates but motion or operation does not occur Command mapping, permissives, control-source settings, safety interlocks PLC logic, drive status, machine conditions
Fault appears after device replacement Configuration mismatch, firmware or variant incompatibility Model, revision, device assignments, saved project
HMI shows stale data PLC tag update, application communication, stale-value handling PLC value, HMI tag, timestamps, data-quality indication

A healthy Ethernet link does not prove that the CC-Link IE application is operating correctly. Similarly, successful network communication does not prove that the PLC program is interpreting the received data correctly.

10.3 Distinguish network faults from application faults

If the device is present and network diagnostics are healthy but an HMI value is incorrect, investigate the data path before replacing network hardware.

For example:

Drive status is correct locally
          ↓
Network communication is healthy
          ↓
PLC receives the wrong mapped word
          ↓
PLC logic interprets the wrong data
          ↓
HMI displays incorrect status

The fault in this example is in the data mapping or interpretation, not necessarily in the Ethernet network.

11. Physical network and electrical considerations

Although CC-Link IE uses Ethernet technology, installation practices must suit the industrial environment.

  • Use the cable category and connector type specified for the network's data rate and installation conditions.
  • Respect the maximum permitted cable lengths for the selected Ethernet segment and equipment.
  • Use industrial-rated switches and connectors where required by vibration, temperature, contamination, or electromagnetic conditions.
  • Separate communication cables from high-noise power wiring where practical.
  • Apply the manufacturer's grounding, bonding, and shielding requirements.
  • Inspect cable strain, connector locking, cabinet entry points, and routing.
  • Check switch diagnostics for link flaps, port errors, and packet drops.
  • Verify that any required network redundancy is configured and tested.

Ethernet cable limits are segment-specific and depend on the physical Ethernet standard. Do not assume that the maximum distance of one CC-Link IE variant applies to every other variant or media type.

12. Maintenance and retrofit checklist

For ongoing maintenance, maintain a documented record of the network and its dependencies.

  • Record the exact CC-Link IE variant used by each network.
  • Record PLC CPU, communication module, switch, and field-device models.
  • Document network topology, cable routes, and port connections.
  • Maintain device and configuration inventories.
  • Back up PLC programs and network configuration files.
  • Record device identities and cyclic data mappings.
  • Document firmware revisions and compatibility constraints.
  • Record normal diagnostic states and known-good network performance.
  • Review network errors and intermittent fault history.
  • Test recovery and application behavior after approved maintenance.
  • Update documentation after module replacement or network changes.
  • Maintain an approved replacement strategy for obsolete hardware.

For a retrofit, first determine whether the requirement is a like-for-like replacement, an upgrade to a different CC-Link IE variant, or migration to another industrial network. These are different engineering tasks with different compatibility and commissioning risks.

13. CC-Link IE versus classic CC-Link

Feature Classic CC-Link CC-Link IE
Network technology Dedicated fieldbus physical layer Ethernet-based technologies
Typical cable Specified CC-Link fieldbus cable Ethernet cabling or other supported media, depending on variant
Common architecture Master and configured field stations Depends on variant; may connect controllers, field devices, or TSN-capable systems
Data exchange Cyclic communication and supported transient services Cyclic and other supported communication services, depending on variant
Network topology Defined by the classic CC-Link specification Depends on the specific CC-Link IE variant
Device compatibility Classic CC-Link-compatible equipment Compatibility must be verified for the specific IE variant
Engineering Classic CC-Link configuration and link assignments Variant-specific network configuration and data mapping
Migration Requires compatible classic CC-Link hardware May require new interfaces, devices, cabling, and configuration

The key takeaway is that CC-Link IE is not simply classic CC-Link operating over a different cable. Its variants have different network architectures, hardware requirements, and configuration models.

14. CC-Link IE versus PROFINET and EtherNet/IP

Technology Ecosystem Typical industrial role
CC-Link IE CC-Link ecosystem, strongly associated with Mitsubishi automation Controller and field-level industrial Ethernet communication
PROFINET Common in Siemens and multi-vendor automation environments PLC communication, distributed I/O, drives, and industrial control
EtherNet/IP Common in Rockwell Automation and multi-vendor systems Controller-to-device communication, I/O, and industrial automation

All three use Ethernet technology, but they differ in protocol behavior, engineering configuration, supported device profiles, and diagnostics.

An Ethernet port alone does not establish protocol compatibility. A migration between these networks may require new communication modules, device replacements, data mapping changes, and application testing.

15. Interview questions and answers

Q1. What is CC-Link IE?

CC-Link IE is a family of Ethernet-based industrial communication technologies used for controller-level and field-level automation, depending on the variant.

Q2. What is the difference between CC-Link and CC-Link IE?

Classic CC-Link uses a dedicated fieldbus physical layer. CC-Link IE uses Ethernet-based networking technologies and has several variants with different capabilities and architectures.

Q3. What is the difference between CC-Link IE Control and CC-Link IE Field?

CC-Link IE Control is intended primarily for controller-level communication, while CC-Link IE Field is intended for field-level communication between controllers and compatible devices.

Q4. What is CC-Link IE TSN?

It is a CC-Link IE family technology that incorporates Time-Sensitive Networking to support time-aware industrial Ethernet communication when the network components and configuration support the required features.

Q5. Does every CC-Link IE device support TSN?

No. TSN support depends on the device, network interface, firmware, and specified variant. Compatibility must be checked explicitly.

Q6. Can CC-Link IE devices be connected to any ordinary Ethernet switch?

Not automatically. Switch compatibility depends on the CC-Link IE variant, required topology, redundancy behavior, timing requirements, and supported TSN features. Verify the manufacturer's requirements.

Q7. What causes a CC-Link IE communication fault?

Possible causes include cable or connector faults, incompatible hardware, incorrect network configuration, switch problems, device power loss, and network-interface errors.

Q8. Why might a networked drive communicate correctly but fail to operate?

The network may be healthy while the command mapping, drive control-source configuration, permissives, interlocks, or machine safety conditions prevent operation.

Q9. How would you troubleshoot incorrect data on CC-Link IE?

Trace the value from the source device through the network assignment, controller memory, PLC logic, and HMI tag. Verify data type, offset, scaling, and word order.

Q10. What should be checked before migrating from classic CC-Link to CC-Link IE?

Check controller compatibility, the target network variant, communication modules, field devices, topology, cable requirements, data mapping, engineering software, timing requirements, and the required commissioning tests.

16. Practical exercises

  • Identify which CC-Link IE variant is used in a real or example automation system.
  • Identify the PLC CPU, network interface, connected devices, and switch models.
  • Draw the network topology and label every physical link.
  • Locate the network configuration and device assignment in the engineering project.
  • Trace one drive status value from the drive to the PLC program and HMI.
  • Identify the configured cyclic data exchanged with a remote I/O station.
  • Review network diagnostics and document the meaning of each relevant status indicator.
  • Compare a healthy station's configuration with that of a simulated faulty station.
  • Review the network's cable specifications, topology restrictions, and redundancy requirements.
  • Prepare a backup and recovery checklist for a network-interface replacement.
  • Write a sample fault report that separates the physical, network, mapping, and application causes.

17. Final mental model

Think of CC-Link IE as an industrial Ethernet family rather than a single protocol configuration.

  • Identify the variant first. Control, Field, Field Network Basic, and TSN have different requirements.
  • Understand the topology. The permitted physical arrangement and redundancy behavior depend on the selected variant.
  • Verify cyclic data mapping. Correct communication is not enough if the PLC reads the wrong data.
  • Separate network health from machine behavior. A healthy network cannot correct incorrect PLC logic, drive settings, or interlocks.
  • Maintain configuration and compatibility records. These are essential for reliable troubleshooting, replacement, and migration.

The most useful maintenance skill is tracing a signal across the complete system, from the field device through the network and PLC to the final application, without assuming the first visible fault is the root cause.
