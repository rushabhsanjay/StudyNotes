1. What Is OPC?

OPC is a family of industrial interoperability standards designed to exchange data between automation devices, control systems, software applications, and higher-level information systems.

In a manufacturing environment, a PLC may control a machine, SCADA may monitor its operation, a historian may store its measurements, and an IT application may analyze production performance. These systems often come from different vendors and use different communication interfaces.

OPC provides a standardized way for compatible applications to exchange information without requiring every pair of systems to have a unique, custom communication implementation.

OPC UA (OPC Unified Architecture) is the modern, platform-independent OPC architecture. It supports structured information models, security, discovery, and multiple communication patterns.

Common uses include:

  • Exchanging PLC tags with SCADA or HMI software.
  • Reading machine status and production counters.
  • Sending process values to historians and dashboards.
  • Exposing industrial data to manufacturing execution systems (MES).
  • Connecting operational technology (OT) data to information technology (IT) applications.
  • Integrating equipment from different manufacturers.
  • Sharing structured machine, production, and diagnostic information.

OPC UA is not a PLC programming language and does not replace the PLC's control logic. It provides a standardized communication and information layer around the control system.

2. Why OPC UA Is Needed

Consider a production line containing PLCs from different manufacturers, a SCADA application, a database, and a production reporting system.

Without a suitable interoperability layer, each application may require its own driver, protocol implementation, or custom data mapping.

OPC UA can provide a common interface between these systems.

PLC / CNC / Machine Controller
              |
              v
         OPC UA Server
              |
              v
         OPC UA Client
              |
       +------+------+
       |      |      |
       v      v      v
     SCADA  Historian MES / IT

This is a logical architecture. The OPC UA server may run inside a controller, on a gateway, or on an industrial PC. A client may be integrated into SCADA, a historian, or another application.

Example from industrial maintenance

Suppose a PLC exposes these values:

  • Machine_Running
  • Cycle_Count
  • Fault_Code
  • Motor_Current
  • Station_Ready

An OPC UA server can expose selected values to authorized clients. SCADA may display the current state, a historian may store trends, and a maintenance dashboard may calculate recurring faults.

The PLC remains responsible for its local control logic. OPC UA transports the selected information to other systems.

3. OPC Classic Versus OPC UA

OPC UA was designed to address important limitations of earlier OPC technologies while retaining the broader goal of industrial interoperability.

Feature OPC Classic OPC UA
Technology foundation Windows-oriented technologies, commonly COM/DCOM Platform-independent architecture
Common variants OPC DA, HDA, A&E Unified architecture supporting data, events, methods, and structured information
Operating-system dependency Historically tied to Microsoft Windows technology Supports multiple operating systems and platforms
Information model Often focused on tags and specific data-access functions Rich object, variable, type, and reference models
Security Depends on the particular Classic technology and Windows security configuration Defined security mechanisms including certificates, authentication, and message protection
Communication Often based on COM/DCOM Client-server and publish-subscribe communication patterns
Integration Widely used in legacy industrial systems Designed for modern and cross-platform interoperability

Important: OPC Classic remains relevant in existing factories. OPC UA does not mean every older OPC installation must be replaced immediately.

5. OPC UA Client and Server

The client-server model is one of the most common OPC UA arrangements.

OPC UA server

A server exposes data and services. It may:

  • Read data from a PLC using a vendor protocol.
  • Publish selected PLC tags as OPC UA variables.
  • Expose device identity and diagnostic information.
  • Provide data access, event, and method services.
  • Enforce client authentication and access permissions.

An OPC UA server does not necessarily control the machine. It may simply act as a data gateway between a PLC and external applications.

OPC UA client

A client connects to the server and uses its available services.

Examples include:

  • SCADA reading process variables.
  • A historian subscribing to production data.
  • An engineering tool browsing available tags.
  • An analytics application reading machine state.
  • An authorized client calling a supported server method.

A client must support the relevant OPC UA features and security settings. A server being available does not guarantee that every client can connect to it.

Typical communication sequence

  | Discover or select endpoint

Client and Server

  | Read / Write / Subscribe / Call

Actual connection establishment may involve endpoint discovery, security-policy selection, certificate checks, session creation, and user authentication.

6. OPC UA Address Space and Nodes

One of the most important differences between OPC UA and a simple tag-reading protocol is its Address Space.

The Address Space is a structured representation of the information a server makes available to clients. It is not merely a flat list of tag names.

For example:

Objects
  |
  +---- Factory
          |
          +---- Assembly_Line_1
                  |
                  +---- Station_10
                          |
                          +---- Machine_Status
                          +---- Cycle_Count
                          +---- Fault_Code
                          +---- Motor
                                  |
                                  +---- Current
                                  +---- Temperature

The actual node hierarchy depends on the server's information model and configuration. The example illustrates a possible organization.

Important node types

Node class Purpose Example
Object Represents an entity or functional grouping Station_10
Variable Holds a value or data property Motor_Current
Method Represents an operation that can be called Reset_Statistics, if implemented and authorized
ObjectType Defines the structure or behavior of object instances A reusable machine type
VariableType Defines properties of variable nodes A specific type of measurement variable
DataType Defines the type of a value Boolean, integer, floating-point, or structured data
Reference Defines relationships between nodes A motor belonging to a station

NodeId and BrowseName

OPC UA uses identifiers to distinguish nodes.

  • NodeId: Identifies a node within a server's address space.
  • BrowseName: Helps clients navigate and identify nodes during browsing.
  • DisplayName: A human-readable name intended for display.
  • Namespace: Helps distinguish identifiers belonging to different information models or naming domains.

A BrowseName is not guaranteed to be unique across the entire address space. A client should use the appropriate node identity and namespace information rather than assuming that a visible tag name uniquely identifies a variable.

Why this matters in practice

Two servers may expose a variable called Temperature, but the variables may represent completely different things.

One could be motor winding temperature, while the other is coolant temperature. A useful information model identifies the equipment, variable meaning, units, and relationships so that clients can interpret the data correctly.

7. Reading, Writing, and Calling Methods

OPC UA provides several kinds of interaction. Reading a value, changing a value, subscribing to updates, and calling a method are different operations with different implications.

Read

A client requests the current value or attributes of a node.

Examples:

  • Read machine running status.
  • Read a cycle counter.
  • Read a measured motor current.
  • Read a device's reported status.

Write

A client requests a change to a writable node.

Examples might include changing an authorized setpoint or updating an approved configuration value.

A successful write request does not automatically prove that the machine acted on the value. The server may accept a value while the PLC logic rejects it, a permissive remains false, or a physical device fails to respond.

Method call

A client requests execution of a method exposed by the server.

Examples might include requesting a supported diagnostic operation or resetting a software statistic. Whether a method exists and whether the client is authorized to invoke it are implementation-dependent.

Industrial rule: Treat remote writes and method calls as control-capable operations. Use least-privilege access, explicit authorization, appropriate interlocks, and validation. Do not expose unrestricted control commands to ordinary IT clients.

8. Data Types, Quality, and Timestamps

A process value is more useful when the receiving application knows its data type, quality, and time context.

OPC UA data values can include:

  • Value: The actual data, such as a number or Boolean.
  • StatusCode: Indicates the quality or status associated with the value.
  • SourceTimestamp: The time associated with the value at its source, when available.
  • ServerTimestamp: The time associated with the value at the server, when available.

A timestamp may be absent, and timestamp semantics depend on the data source and implementation.

Example

Suppose a PLC tag reports a motor current of 8.4 A.

A receiving application should not assume that the number alone tells the whole story. It should also consider whether the value is good, uncertain, or bad, and whether it is recent enough for the intended use.

Information Example Why it matters
Value 8.4 The measured or reported current
Data type Float Determines how the number is interpreted
Engineering unit A Prevents confusion with another unit
StatusCode Good Indicates the reported quality status
Source timestamp Time of the source measurement Helps establish data freshness
Server timestamp Time associated with server processing Helps diagnose delay and data-flow behavior

The examples are illustrative. A server may expose units as engineering properties or through an information model rather than as part of a simple tag display.

Why quality matters

If a communication link fails, a server might retain a previous value, report an error status, or handle the loss of data in another documented way.

A dashboard that displays a stale number without showing its status can mislead an operator into believing that a machine is still operating normally.

For critical monitoring, consider both the value and its quality, timestamp, and communication state.

9. Subscriptions and Monitored Items

A client does not need to repeatedly request every value individually. OPC UA supports subscriptions, which allow clients to receive notifications about monitored data changes and events.

A simplified relationship is:

OPC UA Client
      |
      v
 Subscription
      |
      +---- Monitored Item: Machine_Status
      |
      +---- Monitored Item: Cycle_Count
      |
      +---- Monitored Item: Motor_Current
      |
      v
 Notifications from Server

A subscription can contain multiple monitored items. The server evaluates monitored items according to their configuration and supported behavior, and notifications are delivered according to subscription parameters.

Important concepts

  • Subscription: Manages notification delivery to a client.
  • Monitored item: Represents a node or event source being monitored.
  • Sampling interval: The interval at which the server samples the monitored item, subject to implementation and configuration.
  • Publishing interval: The interval at which the subscription publishes notifications.
  • Deadband: A filter that can suppress insignificant changes for supported numeric monitoring configurations.
  • Queue size: Determines how many notifications can be queued for a monitored item.
  • Keep-alive: Helps the client determine that the subscription remains active even when no notification is due.

Sampling and publishing intervals are not guarantees that the underlying PLC or sensor updates at that rate. The server's data source and implementation impose their own limits.

Example: Monitoring machine current

Suppose a SCADA client subscribes to Motor_Current.

  • The server monitors the variable.
  • The value changes as the motor load changes.
  • Notifications are delivered according to the monitored-item and subscription configuration.
  • SCADA updates its display or historian record.
  • If notifications are delayed or lost, the client should use its communication and data-quality mechanisms to detect the problem.

Subscriptions can reduce unnecessary repeated reads, but they still require correct configuration and suitable server and client resources.

10. OPC UA Events and Alarms

OPC UA can also expose events rather than only values.

An event represents something that occurred or was reported, such as:

  • A machine fault.
  • A device status change.
  • A process alarm.
  • A maintenance-related notification.
  • A condition becoming active or returning to normal.

Some OPC UA implementations support richer alarm-and-condition models, including states and acknowledgement-related functions. Availability depends on the server, information model, and client.

Data versus event

Data variable Event
Represents a value or state Represents an occurrence or notification
Example: Motor_Current = 8.4 A Example: motor overload condition became active
Can be monitored for changes Can be received through event subscriptions
Useful for trends and live values Useful for alarm and event histories

A PLC may already generate its own alarms. OPC UA can expose selected information, but the client should not assume that every PLC alarm automatically becomes an OPC UA alarm with identical semantics.

Alarm priorities, acknowledgement rules, and operator response remain part of the application design.

11. OPC UA Security

OPC UA provides security mechanisms, but they must be configured correctly. Installing OPC UA software does not automatically secure an industrial network.

Main security mechanisms

  • Application certificates: Help establish the identity of client and server applications.
  • Secure communication channels: Can provide message integrity and confidentiality, depending on the selected security configuration.
  • Security policies and message modes: Define supported cryptographic and message-protection behavior.
  • User authentication: May use supported methods such as username/password or certificate-based user identity.
  • Authorization: Controls which operations and nodes a client can access.
  • Audit and logging: May record security-related events and actions, depending on implementation.

Application certificate versus user authentication

These serve different purposes.

  • An application certificate helps establish the identity of the software application.
  • User authentication identifies the user or account associated with a session.
  • Authorization determines which actions the authenticated identity is permitted to perform.

A trusted application is not automatically authorized to modify every machine parameter.

Security checklist

  • Use supported secure endpoints and approved security policies.
  • Avoid anonymous access unless it is explicitly justified and restricted.
  • Maintain application certificates and their trust lists.
  • Review certificate expiration and renewal procedures.
  • Use unique accounts and least-privilege permissions where supported.
  • Restrict network access to required hosts and ports.
  • Protect server configuration and private keys.
  • Monitor failed logins, unexpected clients, and unauthorized write attempts.
  • Disable unused endpoints and services where appropriate.
  • Keep software and security configurations under controlled change management.

Do not solve a certificate or connection problem by permanently disabling security on a production system. Diagnose trust, identity, time, endpoint, and policy configuration instead.

12. OPC UA Transport and Ports

OPC UA supports different communication mappings. The most familiar client-server arrangement uses the OPC UA TCP transport with a configured endpoint, commonly on TCP port 4840.

For example:

opc.tcp://192.168.1.50:4840

This is an illustrative endpoint. The actual hostname, IP address, port, path, and security settings must come from the server configuration.

OPC UA also supports publish-subscribe communication with appropriate transport mappings. Its capabilities are not limited to a single TCP endpoint or communication pattern.

Network troubleshooting checks

  • Confirm the server's configured endpoint.
  • Verify hostname or IP address resolution.
  • Confirm that the server is listening on the expected interface and port.
  • Check routing, VLANs, firewalls, and permitted network paths.
  • Confirm that the client and server support compatible security policies.
  • Verify application certificate trust.
  • Check that the server exposes the required nodes and services.
  • Review session and subscription diagnostics.

A successful TCP connection proves only that a network connection was established. It does not prove that the client is authenticated, authorized, or able to read the required process variables.

14. OPC UA Commissioning Procedure

A successful commissioning process verifies the full path from the source data to the client application.

Step 1: Identify the data source

  • Identify the PLC, CNC, gateway, or SCADA system that owns the data.
  • Confirm the protocol used between the source and OPC UA server.
  • Verify that the source tags update correctly.
  • Select only the variables required by the intended application.

Step 2: Configure the OPC UA server

  • Enable the supported OPC UA server functionality.
  • Configure the endpoint and listening interface.
  • Define which nodes or tags are exposed.
  • Confirm the required data types, units, and access permissions.
  • Configure certificates, security policies, and user authentication.
  • Check whether a restart or controlled download is required.

Step 3: Configure the client

  • Enter the server endpoint.
  • Discover or select the endpoint's supported security settings.
  • Establish application certificate trust through the approved process.
  • Configure user authentication if required.
  • Browse the server's Address Space.
  • Identify the required NodeIds and data types.

Step 4: Test read access

  • Read a known Boolean variable.
  • Read a known numeric variable.
  • Verify value, status quality, and timestamps where available.
  • Compare the values with the PLC or source application.
  • Confirm that the client can distinguish a valid value from a bad or stale value.

Step 5: Configure subscriptions

  • Create monitored items for the required variables.
  • Set appropriate sampling and publishing intervals.
  • Configure deadbands and queues where needed.
  • Verify that changes arrive as expected.
  • Check client behavior during temporary communication loss.

Step 6: Validate writes, if required

  • Confirm that the target node is writable.
  • Verify the user's authorization.
  • Test only approved variables in a safe test environment.
  • Confirm how the PLC or application validates and acts on the written value.
  • Verify feedback from the actual system rather than assuming the write succeeded at the machine level.

Step 7: Complete documentation

  • Record endpoint configuration and security settings.
  • Back up the server and client configuration.
  • Document the node mappings and data types.
  • Record certificate ownership and renewal responsibilities.
  • Document expected behavior during server or network failure.
  • Perform the approved operational and security validation.

15. Troubleshooting OPC UA

Use a layered diagnostic approach. Separate the source PLC, the OPC UA server, the network, the security handshake, and the client application.

Troubleshooting matrix

Symptom Possible causes Recommended checks
Client cannot connect Incorrect endpoint, server stopped, firewall or routing issue Verify endpoint, server status, listening interface, and network path
TCP connection works but session fails Certificate rejection, unsupported security policy, authentication problem Review client/server security configuration and logs
Client connects but cannot browse tags Insufficient permissions, incorrect server configuration, unsupported browse access Check namespace, access permissions, and server Address Space
Node is found but read fails Invalid NodeId, access restriction, bad source status Verify NodeId, data source, and returned StatusCode
Value remains unchanged Source PLC tag is static, incorrect mapping, stale cache, subscription problem Compare source tag with server value and inspect monitoring configuration
Value has bad quality Source communication failure, unavailable device, server data-source error Check the source protocol, PLC connection, and returned status
Subscription stops updating Session timeout, subscription failure, network interruption, client resource issue Inspect subscription state, keep-alive behavior, and reconnect handling
Numeric value is incorrect Wrong data type, scaling, units, or source mapping Compare raw source data, engineering units, and client interpretation
Write request is rejected Read-only node, access denial, type mismatch, invalid value, or application restriction Check access level, permissions, data type, range, and server diagnostics
Certificate trust error Untrusted or expired certificate, hostname mismatch, certificate configuration issue Check certificate identity, validity, trust lists, and endpoint configuration
Server works locally but not remotely Listening only on a local interface, firewall, routing, or hostname issue Check interface binding, network rules, routing, and DNS
Server becomes overloaded Excessive monitored items, high update demand, insufficient resources Review subscription configuration, server limits, and resource usage

Example: Client connects, but a PLC value is wrong

Suppose a SCADA client connects successfully, but Motor_Current displays 0 A while the PLC shows 8.4 A.

Investigate in this order:

  1. Confirm the PLC tag actually contains 8.4 A.
  2. Verify the tag mapped to the OPC UA node.
  3. Read the node directly using a suitable OPC UA diagnostic client.
  4. Check the node's data type, status, and timestamp.
  5. Verify that the SCADA client uses the correct NodeId and namespace.
  6. Inspect scaling, unit conversion, and display formatting.
  7. Compare the results and correct the first identified mismatch.

If the OPC UA server itself returns 0 A, investigate its data source and mapping. If the server returns 8.4 A but SCADA displays 0 A, investigate the client-side configuration.

16. OPC UA Reliability and Failure Handling

OPC UA improves interoperability, but it does not eliminate failures in the source controller, network, server, or client.

A production system should define what happens when:

  • A PLC stops responding.
  • An OPC UA server restarts.
  • A network connection is lost.
  • A certificate expires.
  • A client loses its session or subscription.
  • The data source becomes unavailable.
  • A client receives bad-quality or stale data.

Recommended design practices

  • Make communication state visible in the consuming application.
  • Use quality and timestamp information where appropriate.
  • Define how clients reconnect and recreate subscriptions.
  • Avoid interpreting an old value as a live measurement.
  • Set update intervals based on application requirements and system capacity.
  • Monitor server health and resource usage.
  • Back up server, client, and gateway configuration.
  • Test failure recovery under controlled conditions.

Control-system boundary: Do not make a machine's safety function or fast deterministic control loop dependent on an ordinary OPC UA connection unless the complete design specifically supports the required function and has been appropriately validated. OPC UA is often well suited to monitoring, integration, and supervisory data exchange, while time-critical local control remains in the appropriate controller.

17. OPC UA and OT/IT Integration

OPC UA is useful for bridging operational technology and information technology, but the integration should be deliberately designed.

Machine Sensors and Drives
           |
           v
       PLC / CNC
           |
           v
     OPC UA Server
           |
           v
     OT Integration Layer
           |
           v
 Historian / SCADA / MES
           |
           v
 Reporting / Analytics / IT

This architecture is illustrative. A real deployment may use gateways, brokers, historians, or additional network boundaries.

Data flow example

A PLC records a production cycle counter. An OPC UA server exposes the counter, a historian records changes, and a reporting application calculates production totals.

The reporting application does not need direct access to every PLC if it can obtain the required information through the approved integration layer.

OT/IT design considerations

  • Define which machine data may be exposed outside the control network.
  • Separate networks according to the plant's security architecture.
  • Permit only the necessary communication paths.
  • Use authenticated and authorized clients.
  • Minimize write access from analytics and reporting applications.
  • Document data ownership and tag semantics.
  • Monitor data freshness and communication status.
  • Avoid exposing PLC control interfaces directly to untrusted networks.

For many applications, a read-only OPC UA integration provides most of the reporting benefit with less operational risk than unrestricted bidirectional access.

18. OPC UA Client-Server Versus Publish-Subscribe

OPC UA supports both client-server communication and publish-subscribe (PubSub) communication.

Client-server

A client connects to a server and requests data, subscribes to monitored items, or invokes supported services.

Typical uses include:

  • SCADA browsing and reading tags.
  • Device configuration and diagnostics.
  • Historian subscriptions.
  • Reading structured machine data.

Publish-subscribe

In a PubSub arrangement, a publisher distributes data to subscribers through a configured messaging arrangement. Depending on the implementation, transport mappings can include UDP-based communication or message brokers such as MQTT.

The exact PubSub transport, message encoding, discovery, and security capabilities depend on the selected profile and products.

Feature Client-server Publish-subscribe
Communication model Client interacts with a server Publisher distributes data to subscribers
Data access Browsing, reads, writes, methods, subscriptions, and supported services Data published according to configured datasets and publishing rules
Typical use SCADA and device integration Data distribution to multiple consumers
Connection pattern Client establishes a session with a server Publishers and subscribers use a configured distribution mechanism
Configuration focus Endpoints, sessions, security, NodeIds, subscriptions Published datasets, transport, topics or groups, timing, and subscriber configuration
Main diagnostic focus Endpoint, session, certificates, node access Publisher configuration, transport delivery, subscriber configuration, and message compatibility

PubSub is not automatically faster or more reliable than client-server. Performance and determinism depend on the selected transport, implementation, network, configuration, and application requirements.

Common use PLC-to-SCADA, historian, MES, and IT integration Simple PLC, meter, and instrument communication PLC, I/O, and drive control networks Telemetry distribution and system integration
Main diagnostic focus Endpoint, certificates, NodeIds, status, and subscriptions IP connectivity, register mapping, and timeouts Connections, assemblies, device state, and network configuration Broker connectivity, topics, permissions, and message delivery

These protocols are not mutually exclusive. For example, an OPC UA gateway may read data from a Modbus TCP device and expose the values through a structured OPC UA Address Space. Another system might publish selected production data through MQTT.

The important question is which protocol and architecture best fit the actual data source, timing, security, and application requirements.

20. Maintenance, Configuration Backups, and Documentation

An OPC UA integration should be maintained like any other industrial communication system.

Recommended records

  • OPC UA server and client software versions.
  • PLC, gateway, and controller versions.
  • Endpoint addresses, ports, and interface configuration.
  • Security policies and authentication arrangements.
  • Application certificates, trust relationships, and renewal responsibilities.
  • NodeId mappings and namespace information.
  • Data types, engineering units, and source-variable assignments.
  • Subscription and update-rate configuration.
  • Server and client configuration backups.
  • Known-good configuration revisions and change history.
  • Communication alarms, quality failures, and corrective actions.

Preventive maintenance checklist

  • Confirm that required OPC UA endpoints are available.
  • Verify certificate validity and approved trust relationships.
  • Check server and client communication logs.
  • Confirm that critical nodes return expected values and status.
  • Check for stale data and failed subscriptions.
  • Review unauthorized access attempts and unexpected clients.
  • Verify the PLC-to-server tag mapping.
  • Back up approved configurations and document revisions.
  • Test recovery from communication loss in an approved test environment.
  • Review client permissions and remove obsolete access.

Change-management example

If a PLC tag is renamed or its data type changes, an OPC UA client may no longer interpret the node as expected.

Before making such a change:

  1. Identify all clients using the affected node.
  2. Record the current mapping and expected data type.
  3. Make the change in the approved environment.
  4. Test client browsing, reads, subscriptions, and any permitted writes.
  5. Verify that SCADA and downstream applications display correct values.
  6. Update documentation and retain the known-good configuration.

A change that appears harmless in the PLC program can affect several downstream applications. Data interfaces need ownership and change control just like control logic.

21. Interview Questions and Answers

1. What does OPC stand for?

Historically, OPC stood for OLE for Process Control. The modern OPC organization uses the name OPC to represent its broader interoperability standards.

2. What is OPC UA?

OPC Unified Architecture is a platform-independent industrial communication architecture supporting structured information models, secure communication, and data exchange between compatible systems.

3. What is the difference between an OPC UA client and server?

The server exposes data and services. The client connects to the server and uses the available services.

4. What is an OPC UA endpoint?

An endpoint identifies a communication address and associated configuration through which a server offers OPC UA services.

5. What is an OPC UA Address Space?

It is the structured collection of nodes and relationships exposed by an OPC UA server.

6. What is a NodeId?

A NodeId identifies a node within the server's Address Space. Clients should use the correct identifier and namespace information.

7. What is the difference between Read and Subscribe?

Read requests a value or attribute at a particular time. Subscribe configures notifications for monitored data or events according to the subscription settings.

8. What is a StatusCode?

It indicates the status or quality associated with an operation or data value. Clients should not treat every returned numeric value as valid without considering its status.

9. What is the purpose of an OPC UA certificate?

An application certificate helps establish application identity and supports secure communication arrangements. Trust and authorization must still be configured correctly.

10. What is the difference between OPC Classic and OPC UA?

OPC Classic uses older Windows-oriented technologies such as COM/DCOM. OPC UA is designed for cross-platform interoperability and provides a unified architecture with structured information modeling and modern security mechanisms.

11. What is OPC UA PubSub?

It is a communication model in which publishers distribute configured datasets to subscribers through supported transport mechanisms.

12. Does OPC UA replace PLC communication protocols?

Not necessarily. An OPC UA server may read PLC data using a native vendor protocol and expose selected data to clients. OPC UA often complements the PLC's existing communication system.

13. Why can a client connect but fail to read a tag?

Possible causes include an incorrect NodeId, namespace mismatch, access restrictions, bad source status, or incorrect server mapping.

14. Why might an OPC UA value be stale?

The source PLC may have stopped updating, the server may have lost its source connection, or the client subscription may not be receiving current data. Status and timestamp information help distinguish these conditions.

15. Does OPC UA automatically make a plant secure?

No. Security depends on appropriate endpoint configuration, certificates, authentication, authorization, network controls, monitoring, and maintenance.

16. What is the difference between OPC UA and MQTT?

OPC UA provides industrial information modeling and communication services. MQTT is a messaging protocol commonly used for publish-subscribe data distribution. They can be used together.

17. Can OPC UA be used for machine control?

OPC UA supports writes and methods where implemented, but its suitability for control depends on the complete system design and timing requirements. Local deterministic and safety-critical control should remain in an appropriately designed control architecture.

18. What should be checked first when OPC UA communication fails?

Verify the endpoint, server status, network connectivity, security configuration, certificate trust, authentication, and then the relevant node or subscription diagnostics.

22. Practical Exercises

Use a training PLC, simulator, or non-production environment.

Exercise 1: Browse an OPC UA server

  • Connect a compatible OPC UA client to a test server.
  • Identify the endpoint and supported security settings.
  • Browse the Address Space.
  • Locate a Boolean, integer, and floating-point variable.
  • Record each NodeId, data type, and displayed value.
  • Verify the values against the source application.

Exercise 2: Build a PLC-to-SCADA data path

  • Select a small set of PLC tags.
  • Expose the tags through a supported OPC UA server or gateway.
  • Configure a client to read the required nodes.
  • Display the values in a test SCADA screen.
  • Compare the PLC, server, and SCADA values.
  • Record any mapping or scaling differences.

Exercise 3: Configure a subscription

  • Subscribe to a machine-status variable.
  • Change the source variable in the test environment.
  • Observe notification delivery.
  • Test different supported sampling and publishing intervals.
  • Review behavior during temporary communication loss.
  • Confirm that stale or bad-quality data is not mistaken for a live value.

Exercise 4: Diagnose a security failure

  • Use a test server with a controlled certificate-trust configuration.
  • Attempt a connection with an untrusted client certificate.
  • Record the connection result and server diagnostic information.
  • Establish trust through the approved configuration process.
  • Reconnect and verify the intended authentication and access permissions.

Do not disable production security to perform this exercise.

Exercise 5: Trace a data-quality problem

  • Use a simulated or documented case where a source value stops updating.
  • Compare the source tag with the OPC UA value.
  • Inspect the returned StatusCode and timestamps where available.
  • Determine whether the fault lies in the source, server, network, or client.
  • Document the evidence and corrective action.

23. Final Mental Model

OPC UA is best understood as a standardized bridge between industrial data sources and consuming applications.

  • Server: Exposes data and services.
  • Client: Reads, monitors, or invokes supported services.
  • Address Space: Organizes data into identifiable nodes and relationships.
  • Subscriptions: Deliver monitored-data and event notifications.
  • Status and timestamps: Help clients judge data validity and freshness.
  • Security: Uses configured application identity, authentication, authorization, and message protection.
  • Integration: Connects PLCs and other industrial systems to SCADA, historians, MES, and IT applications.
  • Maintenance: Requires correct mapping, reliable communication, configuration backups, and controlled changes.

For your industrial automation work, the most useful practical skill is tracing a value end-to-end: from the PLC tag, through the OPC UA server and its NodeId, into the client application, and finally to the displayed or stored result. That is how you distinguish a PLC fault from a data-interface fault without randomly changing settings across three systems.
