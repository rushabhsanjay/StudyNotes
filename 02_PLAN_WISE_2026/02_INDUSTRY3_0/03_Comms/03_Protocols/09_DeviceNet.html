DeviceNet: CAN-Based Industrial Device Communication

1. Purpose and scope

DeviceNet is an industrial communication network based on Controller Area Network (CAN). It was developed for communication between industrial controllers and field-level devices such as sensors, actuators, motor starters, drives, and remote I/O.

DeviceNet is associated with the ODVA industrial networking ecosystem and is based on the CAN data-link and physical-layer technologies, with an application-layer protocol defining device identity, object access, connections, and I/O data exchange.

It was widely used in Rockwell Automation and other industrial systems, especially for distributed device control. Although it is an older technology compared with many modern industrial Ethernet systems, it remains relevant when maintaining legacy machines, replacing obsolete modules, diagnosing fieldbus faults, or planning a migration.

The main idea is to connect multiple industrial devices on a shared communication trunk, reducing individual point-to-point control wiring and allowing a controller to exchange status and commands with many devices.

2. Where DeviceNet fits in industrial automation

PLC / Scanner module
        |
        | DeviceNet network
        |
        +------ Remote I/O
        |
        +------ Motor starter
        |
        +------ Variable-frequency drive
        |
        +------ Sensor / actuator device
        |
        +------ Intelligent field device

A DeviceNet system may be used to:

  • Read input and status data from distributed devices.
  • Send output and control commands to compatible devices.
  • Monitor drive or motor-starter status.
  • Retrieve device identity and diagnostic information.
  • Reduce conventional hardwired I/O wiring.
  • Connect devices to a PLC through a DeviceNet scanner or supported interface.

DeviceNet is not Ethernet. Its communication physical layer is based on CAN and uses a different cable system, signaling arrangement, network speed, addressing method, and diagnostic approach.

4. DeviceNet architecture

DeviceNet uses a CAN-based network with a trunk-and-drop cable arrangement. The scanner communicates with configured devices, and the PLC program uses the resulting input and output data.

PLC CPU

Remote I/O  Drive      Starter     Sensor
adapter     interface  interface   interface

The network typically carries both communication signals and DC power for compatible network electronics over the DeviceNet cable. The network power supply and the power required by the actual field loads must be considered separately.

A remote I/O device may use network power for its communication electronics while requiring a separate field supply for sensors or actuators.

5. Physical layer and cable system

DeviceNet uses a specified multi-conductor cable system. Common DeviceNet cable arrangements provide:

  • CAN communication conductors.
  • A DC network power conductor.
  • A network common or return conductor.
  • Shielding, according to the cable type.

The actual conductor colors, cable type, and connector pin assignments must be verified against the device and cable documentation.

5.1 Trunk and drop topology

The trunk line is the main network cable. Drop lines connect individual devices to the trunk.

This structure differs from ordinary Ethernet star wiring. Do not wire DeviceNet as if it were a typical switched Ethernet network.

The diagram illustrates the general arrangement. Actual wiring must follow the supported topology, cable-length limits, drop-length rules, and termination requirements.

5.2 Termination

DeviceNet requires appropriate termination at the two physical ends of the trunk.

The commonly specified CAN termination value is 121 ohms at each end, subject to the applicable DeviceNet cable and specification requirements.

The two terminating resistors are installed across the CAN signal pair at the trunk endpoints. They are not installed at every node and are not a substitute for correct cable layout.

Incorrect termination can cause:

  • Intermittent communication.
  • Communication errors that increase with network speed.
  • Devices disappearing from the scanner.
  • Faults that occur only when several devices communicate.
  • Poor signal integrity on long cable runs.

Do not add or remove termination resistors without verifying the existing physical layout.

5.3 Cable length and network speed

DeviceNet commonly supports communication rates of 125 kbps, 250 kbps, and 500 kbps. The maximum permitted cable lengths depend on the rate, cable type, trunk-and-drop arrangement, and installation.

Baud rate Typical maximum thick-trunk length
125 kbps 500 m
250 kbps 250 m
500 kbps 100 m

These figures are common reference limits for a specified thick-trunk configuration, not universal limits for every cable type or topology. Thin cable, drop lengths, cumulative drop length, and other installation rules can reduce the permissible distance.

Always use the applicable DeviceNet specification and hardware manuals when designing or modifying a network.

6. DeviceNet network power

DeviceNet commonly distributes nominal 24 V DC network power along the cable for communication electronics and supported devices. The actual acceptable voltage range and current requirements must be checked against the specification and connected equipment.

Network power is a frequent source of faults because a network can have correct communication settings but insufficient voltage at distant devices.

6.1 Power-supply design

Consider the following:

  • Supply voltage and current rating.
  • Total current consumed by all connected nodes.
  • Cable resistance and voltage drop.
  • Distance between the power supply and the devices.
  • Power-feed location and network grounding arrangement.
  • Device startup current and any permitted inrush.
  • Manufacturer requirements for multiple power supplies or isolated sections.

A power supply rated for the total nominal load may still produce excessive voltage drop at the far end of a long trunk.

6.2 Voltage-drop diagnosis

Measure the network voltage at the supply and at representative remote locations using an approved procedure.

If the voltage is healthy near the supply but too low at a distant node, possible causes include cable resistance, excessive load, a loose connection, or poor power-feed placement.

Do not assume the communication conductors are faulty just because several nodes disappear simultaneously. Shared network power problems can produce the same symptom.

6.3 Grounding and shielding

Follow the cable and device manufacturer's requirements for shield bonding, network common, protective earth, and grounding. These are related but not interchangeable electrical functions.

Incorrect grounding can introduce common-mode voltage or noise, while an improperly connected shield can reduce immunity to electrical interference.

Avoid creating unintended ground loops or connecting network conductors to protective earth based on guesswork.

7. Node addressing and MAC ID

DeviceNet uses a MAC ID, also called the node address, to identify each node on the network.

The valid node-address range is normally 0 through 63. Each node on the same network must have a unique MAC ID.

The address may be set using rotary switches, DIP switches, hardware configuration, or software, depending on the device.

7.1 Addressing faults

Fault Possible result Corrective action
Duplicate MAC ID Nodes may fail to communicate or appear inconsistently Identify and correct the duplicate address
Wrong MAC ID in scanner configuration Scanner cannot connect to the intended device Compare configured and physical addresses
Unsupported baud rate Device does not communicate correctly Match the node's rate to the network configuration
Incorrect device identity Scanner configuration does not match the installed hardware Verify vendor ID, device type, product code, and revision
Incorrect EDS or device profile Configuration options may be missing or wrong Obtain the correct file for the exact device

A duplicate MAC ID can be difficult to diagnose because the devices may not provide a clear indication of which node has the conflicting address. Compare the physical settings and configuration records systematically.

7.2 MAC ID versus IP address

DeviceNet does not use IP addresses to identify its nodes. Its MAC ID is a network-level node address within the DeviceNet system.

This is different from Ethernet-based systems such as EtherNet/IP, where IP configuration is part of the communication path.

8. Scanner, adapter, and device configuration

8.1 Scanner

The scanner is the controller-side interface responsible for communicating with configured DeviceNet nodes. It establishes the supported I/O connections and makes received data available to the controller through the scanner's assigned data interface.

The scanner's configuration commonly includes:

  • Node MAC ID.
  • Baud rate.
  • Device identity and revision.
  • I/O connection type.
  • Input and output data sizes.
  • Polling, COS, or cyclic behavior where supported.
  • Connection paths and parameter settings.
  • Scanner memory mapping and status information.

8.2 Adapter

An adapter is the device-side interface that communicates with the scanner. It may be integrated into a remote I/O block, drive, motor starter, or other intelligent device.

Its supported data and configuration depend on the device. Two devices with similar functions may use different I/O sizes, connection options, or parameter layouts.

8.3 EDS files

An Electronic Data Sheet (EDS) describes a device's identity and supported configuration information for compatible configuration tools.

An EDS file may provide information such as:

  • Vendor and device identity.
  • Product type and code.
  • Supported parameters.
  • Communication options.
  • I/O connection information.
  • Configuration choices exposed by the tool.

An EDS file is not the device's complete runtime configuration or a backup of the PLC program. It describes the device for engineering and configuration purposes.

When a configuration tool reports an unknown device, first verify the exact model and revision, then obtain the appropriate EDS file from the manufacturer or approved engineering archive.

9. DeviceNet data exchange

DeviceNet supports I/O communication for control data and explicit messaging for configuration and parameter access.

9.1 Polled I/O

In polled communication, the scanner sends a request to a device and receives its response.

Typical uses include:

  • Reading device status.
  • Sending output commands.
  • Exchanging discrete I/O.
  • Exchanging selected numeric data.

The communication timing depends on the scanner, node count, data size, baud rate, and configuration.

9.2 Change of State (COS)

In COS communication, the device can transmit data when the supported conditions for a change are met. The implementation may also include a heartbeat or other mechanism to indicate that communication remains active.

COS can reduce unnecessary repeated transmission when values remain unchanged. However, it must be configured correctly, and the device and scanner must support the required behavior.

9.3 Cyclic communication

Cyclic communication exchanges data at configured intervals. It is useful when the application expects periodic updates regardless of whether the value has changed.

The configured interval and actual communication behavior must be verified for the device and scanner combination.

9.4 Explicit messaging

Explicit messaging is generally used for on-demand requests involving configuration, parameters, identity, and other object data supported by the device.

Examples include:

  • Reading a drive parameter.
  • Retrieving a diagnostic code.
  • Checking device identity.
  • Writing a supported configuration parameter.

Explicit messaging is not a substitute for appropriately configured cyclic I/O where regular control updates are required.

9.5 Choosing a communication type

Communication type Main purpose Important consideration
Polled I/O Scanner-requested data exchange Request and response timing
COS Transmit data when supported change conditions occur Heartbeat and change configuration
Cyclic I/O Repeated data updates Configured update interval and network load
Explicit messaging On-demand parameters and device services Request handling, response time, and supported objects

Not every device supports all communication types. Confirm the device's capabilities and the scanner's supported connection options.

10. CAN fundamentals behind DeviceNet

DeviceNet uses CAN for its underlying data-link communication. Understanding a few CAN concepts helps explain why termination, bus wiring, baud rate, and electrical noise matter so much.

10.1 Differential signaling

CAN communication uses two signal conductors, commonly identified as CAN_H and CAN_L. The receiver interprets the differential voltage between the conductors rather than relying only on the voltage of one conductor relative to ground.

This improves noise immunity, but it does not make the network immune to wiring faults, poor termination, excessive common-mode voltage, or severe electrical interference.

10.2 Dominant and recessive states

CAN uses dominant and recessive bus states. The dominant state overrides the recessive state when multiple nodes transmit at the same time.

This behavior supports CAN's non-destructive arbitration mechanism. A node that loses arbitration stops transmitting and can try again later.

DeviceNet uses CAN communication rules, but troubleshooting should focus on the DeviceNet network specification and the diagnostics exposed by the scanner and devices.

10.3 CAN identifiers and DeviceNet addressing

CAN frames contain an identifier that participates in message arbitration and identifies the message according to the protocol. DeviceNet uses defined communication and addressing conventions on top of CAN.

Do not confuse a CAN frame identifier with a DeviceNet node's MAC ID. They are related to communication but serve different roles.

10.4 Error detection

CAN includes mechanisms for detecting transmission errors. Depending on the fault and the implementation, errors can result in retransmissions, error counters increasing, or a node entering a fault state such as bus-off.

In DeviceNet, persistent electrical or wiring problems may therefore appear as communication instability or nodes disappearing from the scanner rather than as a clean, single application error.

11. DeviceNet integration with Allen-Bradley systems

DeviceNet was widely used in Rockwell Automation environments, including PLC systems with dedicated scanner modules.

The exact hardware and software depend on the controller generation. Legacy installations may use scanner modules configured through RSNetWorx for DeviceNet and integrated with a PLC project in the relevant programming environment.

11.1 Typical engineering workflow

  1. Identify the controller, scanner module, and all connected DeviceNet devices.
  2. Confirm the network baud rate and physical topology.
  3. Assign unique MAC IDs to all nodes.
  4. Install the correct EDS files in the engineering environment.
  5. Configure the network and supported I/O connections.
  6. Assign scanner input and output data to the controller's expected memory areas.
  7. Download the approved configuration using the supported procedure.
  8. Confirm that every expected node is present and communicating.
  9. Verify actual input data and output commands under controlled conditions.
  10. Save the project and configuration backups.

The specific configuration workflow depends on the scanner, PLC family, software revision, and device support. Some legacy systems require older engineering tools or operating environments, so compatibility should be checked before making changes.

11.2 Scanner input and output data

The scanner makes device I/O data available to the controller through its configured data interface. The precise memory layout depends on the module and PLC architecture.

For example, a drive might expose a command word and a reference value to the scanner while returning a status word and actual-value data.

Before modifying the PLC logic, establish which bits and words correspond to the actual device parameters. A command bit in the wrong location can be interpreted as an unrelated operation.

11.3 Device replacement

When replacing a DeviceNet device, check more than the connector and physical dimensions.

Verify:

  • Manufacturer and product identity.
  • Supported revision and EDS compatibility.
  • MAC ID and baud rate.
  • Input and output sizes.
  • Supported I/O connection type.
  • Parameter configuration.
  • Scanner compatibility.
  • Control and status data mapping.

A replacement may communicate successfully but expose a different data layout. Validate every critical status and command before returning the machine to production.

12. DeviceNet troubleshooting

DeviceNet faults commonly involve physical wiring, network power, termination, addressing, configuration, or communication capacity.

12.1 Symptom-to-cause matrix

Symptom Possible cause First checks
All nodes fail Scanner fault, network power failure, trunk wiring issue, incorrect baud rate Scanner status, supply voltage, trunk cable, configuration
One node is missing Device power, cable fault, duplicate MAC ID, wrong address Local device status, address setting, connection
Multiple nodes disappear intermittently Poor termination, voltage drop, noise, loose trunk connection Termination, power measurements, cable inspection
Scanner detects node but I/O does not update Wrong connection type, I/O size, or configuration Scanner configuration and device profile
Communication fails after adding a device Duplicate MAC ID, excessive load, incorrect cable layout, incompatible configuration Address inventory, topology, scanner capacity
Remote device repeatedly resets Low voltage, excessive load, power interruption, device fault Voltage at the node, supply current, local diagnostics
Fault appears only at higher baud rates Marginal cable quality, excessive length, topology or termination issue Baud rate, cable limits, termination
Device works locally but not over the network Adapter configuration, scanner mapping, network connection failure Adapter status, scanner diagnostics, I/O assignment
Explicit messages fail but I/O works Unsupported parameter, incorrect path, permission or service issue Object support, message path, parameter definition
Drive receives data but does not run Incorrect command mapping, drive mode, permissive, or fault condition Drive parameters, command/status words, interlocks

12.2 Step-by-step fault isolation

Step 1: Identify the scope. Determine whether the problem affects the entire network, a group of nodes, one node, or only a particular data value.

Step 2: Check network power. Measure the supply and representative node voltages using the approved procedure. Look for voltage drop or unstable supply conditions.

Step 3: Check scanner diagnostics. Record the scanner's network status, fault codes, and the nodes reported as missing or failed.

Step 4: Inspect the physical layer. Verify trunk and drop wiring, connectors, termination, cable type, and permitted cable lengths.

Step 5: Verify baud rate and MAC IDs. Compare the configured rate and unique node addresses against the actual devices.

Step 6: Check configuration files. Verify device identity, EDS file, I/O connection type, data sizes, and scanner configuration.

Step 7: Validate the data mapping. Trace the affected bit or word from the device through the scanner to the PLC program.

Step 8: Inspect the application. Confirm that the PLC logic, drive control mode, permissives, and interlocks allow the expected operation.

Step 9: Confirm stable recovery. Check all expected nodes, verify actual process behavior, and monitor for recurring communication faults.

Step 10: Record the root cause. Document the measured evidence, correction, validation, and preventive action.

Do not begin by replacing the scanner simply because multiple devices have failed. A single shared trunk fault or network-power problem can produce the same symptoms.

Device status indicators Shows device power and local communication state LED meanings vary by model
Multimeter Measures network supply voltage and voltage drop Does not decode CAN messages
Oscilloscope or suitable CAN analyzer Examines signal quality and electrical behavior Requires correct probing technique and equipment

For difficult intermittent faults, an appropriate CAN or DeviceNet analyzer can help identify error frames, abnormal signal levels, or repeated communication attempts. Use equipment compatible with the network and follow the manufacturer's connection procedure.

14. Safety and maintenance considerations

  • Follow the machine's electrical safety and lockout procedures before altering wiring or removing modules.
  • Confirm network power requirements before connecting or replacing devices.
  • Do not short the CAN signal conductors or network power conductors during testing.
  • Verify termination and cable layout against the approved design.
  • Back up the scanner configuration and PLC project before changes.
  • Do not assume that standard DeviceNet communication is safety-rated.
  • Verify the machine's behavior on loss and recovery of network communication.
  • Test output commands only under approved safe conditions.
  • Document replacement-device identity, configuration, and test results.
  • Plan for the lifecycle limitations of legacy DeviceNet hardware, including availability of compatible replacement parts and engineering tools.

If a network fault affects a drive or actuator, communication recovery may cause previously unavailable commands to become active. Confirm restart behavior and interlocks before restoring operation.

15. DeviceNet versus other industrial networks

Feature DeviceNet ControlNet EtherNet/IP
Underlying technology CAN-based fieldbus Scheduled industrial network based on ControlNet technology Standard Ethernet with CIP
Physical medium Specified DeviceNet trunk-and-drop cable Coaxial cable in classic implementations, with supported network hardware Ethernet cabling and compatible network devices
Typical role Field devices, remote I/O, drives, starters Controller and I/O communication requiring scheduled data transfer Controller, I/O, drives, and industrial device communication
Addressing MAC ID, normally 0 to 63 Network-specific node addressing IP addressing plus CIP device identity
Network power Commonly carries DC power for compatible network electronics Separate power arrangements depending on hardware Typically separate device power
Common diagnostics Scanner status, node status, CAN and wiring faults Network status, scheduled communication and media faults Link status, IP connectivity, CIP connection and device diagnostics

These networks belong to different communication architectures. A DeviceNet device cannot be connected directly to an ordinary Ethernet port and expected to communicate. Migration usually requires a compatible gateway, interface, or replacement device, along with configuration and application changes.

16. Interview questions and answers

Q1. What is DeviceNet?

DeviceNet is a CAN-based industrial communication network used to connect controllers with field devices such as remote I/O, drives, motor starters, and sensors.

Q2. What is the function of the scanner?

The scanner manages communication with configured DeviceNet nodes and makes their I/O data available to the controller through the supported interface.

Q3. What is a MAC ID in DeviceNet?

It is the node address used to identify a DeviceNet device. The normal valid range is 0 to 63, and each node on the same network must have a unique address.

Q4. Why is termination important?

Termination reduces signal reflections on the CAN communication pair. Incorrect termination can cause communication errors and intermittent node failures.

Q5. What is the difference between trunk and drop cable?

The trunk is the main network cable. Drop cables connect individual devices to the trunk within the permitted topology and cable-length limits.

Q6. What is an EDS file?

An Electronic Data Sheet describes a device's identity and supported configuration information for compatible engineering tools.

Q7. What is the difference between polled I/O and explicit messaging?

Polled I/O is used for scanner-requested operational data exchange. Explicit messaging is generally used for on-demand parameters, configuration, and other supported device services.

Q8. Why can several nodes fail at once?

A shared fault such as network-power loss, a damaged trunk cable, incorrect termination, or a scanner problem can affect multiple nodes simultaneously.

Q9. Why might a node communicate but provide incorrect I/O data?

The connection may be working while the configured I/O size, device profile, data mapping, or PLC interpretation is incorrect.

Q10. What should be checked before replacing a DeviceNet scanner?

Check network power, trunk wiring, termination, baud rate, node addresses, scanner diagnostics, device configuration, and the scanner's compatibility with the PLC system.

17. Practical exercises

  • Identify the scanner model and all connected DeviceNet nodes in an existing or example machine.
  • Prepare a node inventory with MAC ID, device model, baud rate, and EDS revision.
  • Trace the physical trunk and drop cables and mark both termination points.
  • Review the network-power supply rating and calculate the expected connected load.
  • Measure network voltage at the supply and at a representative remote node under an approved procedure.
  • Locate the scanner's network diagnostics and record the meaning of the relevant status indicators.
  • Trace one remote input bit from the field terminal through the scanner to the PLC logic.
  • Trace one drive command word and its corresponding status word.
  • Review the configured I/O size and compare it with the device documentation.
  • Prepare a recovery plan for a missing node that separates power, wiring, addressing, and configuration checks.
  • Write a sample root-cause report for an intermittent DeviceNet fault.

18. Final mental model

DeviceNet is a CAN-based fieldbus that combines communication, device addressing, and a specified trunk-and-drop physical network.

When troubleshooting it, keep five areas separate:

  1. Power: Are the scanner and nodes receiving suitable power?
  2. Physical network: Are the cable, topology, signal pair, and termination correct?
  3. Addressing: Does every node have the correct unique MAC ID and baud rate?
  4. Configuration: Does the scanner have the correct device identity, connection type, and I/O size?
  5. Application: Does the PLC interpret the device data correctly and issue the intended commands?

This layered approach is especially useful when maintaining legacy automation equipment, where a configuration problem, a network-power fault, and an aging cable can produce deceptively similar symptoms.
