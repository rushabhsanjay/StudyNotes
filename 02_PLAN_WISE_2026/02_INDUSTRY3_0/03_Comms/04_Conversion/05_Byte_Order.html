1. Definition and purpose

Byte order describes the sequence in which the bytes of a multi-byte data value are arranged or interpreted when the value is stored, transmitted, or reconstructed.

Industrial communication systems frequently exchange values larger than one byte. A PLC, energy meter, VFD, CNC controller, SCADA system, or communication gateway may exchange 16-bit integers, 32-bit integers, floating-point values, or 64-bit values. If the sender and receiver interpret the byte sequence differently, the communication may appear healthy while the displayed value is completely wrong. Machines have many ways to misbehave, and perfectly delivered incorrect data is one of the more irritating ones.

Byte order is particularly important when integrating equipment from different manufacturers through Modbus RTU, Modbus TCP, Ethernet-based gateways, serial links, OPC servers, and custom software.

2. Understand bits, bytes, and multi-byte values

A bit represents a binary digit, 0 or 1. A byte contains eight bits.

Data unit Size Typical use
Bit 1 bit Boolean status, alarm, command
Byte 8 bits Character, packed status, part of a number
16-bit word 2 bytes Register, small integer, status word
32-bit value 4 bytes Large integer, IEEE 754 float
64-bit value 8 bytes Double-precision float, large counter

Consider the following 32-bit value represented by four bytes:

Byte position:   B0    B1    B2    B3
Hexadecimal:     12    34    56    78

The same four bytes can be interpreted or arranged differently depending on the byte-order convention. To understand the problem, separate three concepts:

  • Byte order: The arrangement of bytes within a multi-byte value.
  • Word order: The arrangement of 16-bit words within a value spanning multiple words.
  • Bit order: The ordering of bits within a byte or the transmission order of individual bits. This is a separate issue from byte order.

A 16-bit word contains two bytes. A 32-bit value contains two 16-bit words. A 64-bit value contains four 16-bit words. Therefore, a system can agree on the size of a value and still disagree on how its parts are arranged.

3. Big-endian and little-endian byte order

3.1 Big-endian

In big-endian representation, the most significant byte (MSB) comes first, followed by progressively less significant bytes.

For the 32-bit hexadecimal value 0x12345678:

Value:          0x12345678

Byte sequence:  12 34 56 78
                 ↑        ↑
                MSB      LSB

Here, 0x12 is the most significant byte and 0x78 is the least significant byte.

3.2 Little-endian

In little-endian representation, the least significant byte (LSB) comes first.

For the same numeric value:

Value:          0x12345678

Byte sequence:  78 56 34 12
                 ↑        ↑
                LSB      MSB

The underlying numeric value is unchanged. Only the order of the bytes in the representation differs.

Property Big-endian Little-endian
First byte Most significant byte Least significant byte
Example for 0x12345678 12 34 56 78 78 56 34 12
Common association Network byte order conventions Many common processor memory representations
Industrial implication Receiver must interpret bytes accordingly Receiver must interpret bytes accordingly

Important: Do not assume that a device's CPU byte order automatically determines its protocol's byte order. A protocol, device firmware, driver, or gateway can define a different representation for exchanged data.

4. Byte order in 16-bit registers

A 16-bit register contains two bytes. For example:

Register value: 0x1234

High byte:      0x12
Low byte:       0x34

For Modbus, the 16-bit register value is transmitted with its most significant byte first. This is part of Modbus's defined representation of a register. However, the ordering of multiple registers used to form a 32-bit or 64-bit value may vary by device or manufacturer.

For a register value of 0x1234, the two data bytes are:

12 34

If a receiver incorrectly reverses the two bytes, it may interpret the value as 0x3412.

Intended register Correct interpretation Reversed-byte interpretation
0x1234 4660 13330
0x0001 1 256
0x0100 256 1
0x0064 100 25600

The final row illustrates why testing with values that contain different bytes matters. Values such as 0x0000 or 0xFFFF are poor tests for byte swapping because reversing their bytes does not change the value.

5. Identifying byte arrangements in a 32-bit value

Suppose a device defines a 32-bit value using four logical bytes:

A = 0x12
B = 0x34
C = 0x56
D = 0x78

Common byte arrangements include:

Arrangement Byte sequence Meaning
ABCD 12 34 56 78 Original sequence
BADC 34 12 78 56 Swap bytes within each 16-bit word
CDAB 56 78 12 34 Swap the two 16-bit words
DCBA 78 56 34 12 Reverse the full byte sequence

These labels are commonly used when discussing 32-bit values across industrial devices. They are descriptive arrangements, not a guarantee that every manufacturer uses the same terminology.

5.1 How the arrangements relate to registers

Assume the logical 32-bit value is split into two 16-bit words:

Logical value:  0x12345678

Word 1:         0x1234
Word 2:         0x5678

If each register is transmitted with its high byte first, the byte sequence is:

Register 1:  12 34
Register 2:  56 78

Combined:    12 34 56 78

If the register order is reversed, the sequence becomes:

Register 1:  56 78
Register 2:  12 34

Combined:    56 78 12 34

If the bytes within each register are reversed, the sequence becomes:

Register 1:  34 12
Register 2:  78 56

Combined:    34 12 78 56

This distinction is essential: reversing bytes inside registers is not the same operation as reversing the order of registers. They can produce different incorrect values and require different configuration settings.

6. Byte order with floating-point values

Industrial equipment often transmits measurements as IEEE 754 floating-point values. Examples include motor current, torque, speed, pressure, temperature, energy, and process measurements.

A common format is 32-bit floating point, also called REAL in many PLC environments and FLOAT32 in communication specifications.

6.1 Worked example: FLOAT32 value 1.0

The IEEE 754 single-precision representation of 1.0 is:

Decimal:          1.0
32-bit hex:       0x3F800000

Byte A:           0x3F
Byte B:           0x80
Byte C:           0x00
Byte D:           0x00

Assume each Modbus register contains two bytes, with the most significant byte transmitted first within each register.

Arrangement Register 1 Register 2 Combined bytes
ABCD 0x3F80 0x0000 3F 80 00 00
BADC 0x803F 0x0000 80 3F 00 00
CDAB 0x0000 0x3F80 00 00 3F 80
DCBA 0x0000 0x803F 00 00 80 3F

Only the correct arrangement reconstructs the intended floating-point representation of 1.0. Other arrangements may decode to a different number, potentially a tiny value, a huge value, or a special floating-point value.

6.2 Why floating-point errors can look strange

Consider a device measuring motor current and reporting 12.5 A as a FLOAT32.

If the receiver uses the wrong byte arrangement, the display might show:

  • 0.0000007 A
  • An unexpectedly large number
  • A negative number
  • A number that changes erratically as the measurement changes

These are illustrative possibilities, not fixed outputs. The actual result depends on the exact bit pattern and the incorrect interpretation.

Diagnostic rule: When a float is clearly unreasonable, check the data type, byte order, word order, register addresses, and scaling before concluding that the instrument or PLC is defective.

7. Byte order versus data type, signedness, and scaling

These are separate properties. Correcting one does not automatically correct the others.

Property Question it answers Example
Data type How many bits and what representation? UINT16, INT32, FLOAT32
Byte order In what order are the bytes arranged? ABCD or DCBA
Word order In what order are the 16-bit words arranged? First word or second word first
Signedness Can the integer represent negative values? INT16 versus UINT16
Scaling How is the raw value converted into engineering units? Raw 125 represents 12.5 A
Unit What physical quantity does it represent? A, V, bar, rpm

7.1 Signed and unsigned integers

A 16-bit unsigned integer has a range of \(0\) to \(65535\).

A 16-bit signed two's-complement integer has a range of \(-32768\) to \(32767\).

For example, the 16-bit bit pattern 0xFFFF represents:

  • 65535 as UINT16.
  • -1 as INT16.

The bits are identical. The interpretation differs because the data types differ.

7.2 Scaling example

Suppose a VFD reports motor current as an unsigned integer scaled by 10:

Raw register:       125
Scale factor:       0.1
Engineering value:  12.5 A

If the raw value is read correctly but the scale factor is wrong, the result may be 125 A instead of 12.5 A. Byte swapping will not solve a scaling error.

7.3 64-bit values

A 64-bit value contains eight bytes, often represented as four 16-bit registers in Modbus applications.

Potential formats include:

  • UINT64 and INT64 for integers.
  • FLOAT64 or DOUBLE for IEEE 754 double-precision floating-point values.
  • Vendor-defined counters or packed data structures.

The register order and byte-order rules must be obtained from the device's documentation. Do not assume that the arrangement used for a 32-bit float also applies to a 64-bit counter.

8. Configuring byte order in industrial systems

Byte-order settings may appear in PLC instructions, communication drivers, SCADA tag definitions, gateway configuration, or software libraries.

Common labels include:

Setting label Typical operation Important caution
Byte swap Exchanges two bytes within a word or defined data unit Confirm the exact scope
Word swap Exchanges 16-bit words in a multi-word value Does not necessarily reverse bytes inside each word
Byte and word swap Applies both operations Verify the resulting sequence
Little-endian Uses least-significant-byte-first representation May describe memory or data representation, depending on the software
Big-endian Uses most-significant-byte-first representation May not define multi-register ordering by itself
ABCD / BADC / CDAB / DCBA Selects a documented byte arrangement Confirm how the vendor defines each label

A configuration label alone is not enough. One driver may define byte swapping within each register, while another may define swapping across a larger data value.

8.1 PLC integration

When a PLC reads data from an external device:

  1. Identify the source register or tag.
  2. Confirm whether the source is an integer, floating-point value, or packed bitfield.
  3. Determine how many registers represent the value.
  4. Obtain the device's byte-order and word-order definitions.
  5. Check the PLC communication instruction or driver settings.
  6. Verify the reconstructed value against a known source value.

For example, a PLC may read two Modbus holding registers and combine them into a REAL. The communication instruction may return the raw registers correctly, while the conversion logic assembles them incorrectly.

8.2 SCADA and gateway integration

A gateway may convert Modbus data into OPC UA tags, MQTT messages, database records, or dashboard values.

Field device
    ↓
Modbus registers
    ↓
Gateway or communication driver
    ↓
Data type and byte-order conversion
    ↓
OPC UA / MQTT / SCADA tag
    ↓
Database / dashboard / historian

If the conversion is wrong at the gateway, downstream systems may store and display incorrect values consistently. A database can preserve bad data with remarkable efficiency.

The best approach is to identify the first point where the value differs from the source, rather than adjusting every downstream layer.

9. Practical example: Reading a Modbus energy meter

Suppose an energy meter exposes a 32-bit floating-point voltage measurement across two holding registers.

The meter documentation specifies:

  • Starting register: 40001 in the manufacturer's notation.
  • Data type: FLOAT32.
  • Register count: 2.
  • Byte order within each register: most significant byte first.
  • Word order: the second 16-bit word is sent before the first 16-bit word.

The address notation 40001 is not universal across software. Some Modbus libraries use zero-based offsets, while some manuals use one-based reference numbers. Verify the addressing convention separately.

Assume the expected float is 230.0 V. The IEEE 754 representation is 0x43660000.

With the specified word order, the registers would be:

Logical 32-bit value: 0x43660000

Normal word split:
Word 1: 0x4366
Word 2: 0x0000

Specified transmission order:
Register 1: 0x0000
Register 2: 0x4366

A practical verification procedure is:

  1. Read both registers using a Modbus diagnostic tool.
  2. Record their raw hexadecimal values, not just decimal values.
  3. Confirm the register addressing convention.
  4. Assemble the bytes according to the manufacturer's specification.
  5. Decode the result as FLOAT32.
  6. Compare the result with the meter's local display or another trusted measurement.
  7. Document the final settings in the SCADA tag configuration.

If the source display reads 230.0 V and the SCADA system reads an implausible value, first check the documented register mapping and representation. Do not randomly toggle swap settings until something looks convincing.

10. Troubleshooting byte-order problems

Symptom Possible cause Verification
A 16-bit value is incorrect by a large factor Byte order reversed Compare raw hex with expected register value
A FLOAT32 value is extremely small or large Incorrect byte or word arrangement Decode all documented arrangements
A value is negative when it should be positive Wrong data type or incorrect bit interpretation Verify signedness and raw bit pattern
A 32-bit counter is incorrect but each register looks reasonable Word order reversed or incorrect register pairing Verify both registers and their sequence
Values are correct in a vendor tool but wrong in SCADA Driver conversion or tag configuration mismatch Compare raw values at each layer
A displayed value is consistently ten times too large Scaling or decimal placement error Check scale factor and units
A value changes erratically Wrong register pair, inconsistent reads, invalid data, or incorrect conversion Check register addresses, data consistency, and communication quality
Values are correct for some devices but wrong for others Device-specific data formats Compare each model's communication manual
A 64-bit counter is incorrect Incorrect register order, data type, or register count Verify the complete eight-byte representation

10.1 A disciplined diagnostic sequence

Follow this order:

  1. Confirm communication: Check device identity, response status, timeouts, and register addresses.
  2. Capture raw data: Record the actual register values in hexadecimal.
  3. Confirm the data type: Determine whether the source is INT16, UINT32, FLOAT32, or another type.
  4. Check the byte order: Determine how bytes within each word are interpreted.
  5. Check the word order: Determine how multiple registers form the complete value.
  6. Check signedness and scaling: Verify signed versus unsigned interpretation, engineering units, and scale factors.
  7. Compare against a known value: Use a source display, simulator, or documented test value.
  8. Validate the complete path: Confirm that PLC, gateway, SCADA, database, and dashboard values agree.

For a stable known test value, this sequence helps isolate the fault without introducing unrelated changes.

11. Commissioning, maintenance, and retrofit practices

Byte order should be documented as part of the communication interface specification, particularly when replacing obsolete instruments or changing PLCs, gateways, SCADA drivers, or software libraries.

Record at least the following for each multi-register value:

Documentation field Example
Device and model Energy meter model
Protocol Modbus TCP
Register reference Manufacturer's holding-register address
Software offset Verified driver address
Data type FLOAT32
Register count 2
Byte order within register MSB first
Register or word order Word 2 before Word 1
Scaling 1.0
Engineering unit V
Valid range Per instrument specification
Verification method Compare against local display

Before changing a live system:

  • Back up the current PLC, gateway, and SCADA configuration.
  • Record the existing raw register values and displayed values.
  • Test conversion changes offline or during an approved maintenance window.
  • Avoid using production outputs or write commands merely to test a read-only data representation.
  • Verify alarm thresholds, trends, database calculations, and reports after the change.
  • Update the interface specification and handover documentation.

A retrofit that changes only the communication driver can still alter how values are interpreted. Preserve the old and new configurations and verify the resulting engineering values before accepting the change.

12. Interview questions and answers

Q1. What is byte order?

Byte order is the sequence in which the bytes of a multi-byte value are arranged or interpreted.

Q2. What is the difference between big-endian and little-endian?

Big-endian places the most significant byte first. Little-endian places the least significant byte first.

Q3. Does Modbus always use big-endian for every multi-register value?

No. Modbus defines the transmission order of bytes within a 16-bit register, but the ordering of multiple registers that represent a larger value can depend on the device's specification.

Q4. What is the difference between byte swapping and word swapping?

Byte swapping exchanges bytes within a defined unit. Word swapping exchanges the order of 16-bit words in a multi-word value.

Q5. Why can a FLOAT32 value appear as a very small number?

The receiver may be interpreting the bits in the wrong byte or word order, or it may be using the wrong data type or register mapping.

Q6. If a register reads correctly but the displayed value is wrong, what should be checked?

Check the complete register mapping, data type, byte order, word order, signedness, scaling, and units.

Q7. How can the correct arrangement be identified?

Use the device's communication manual and compare the raw hexadecimal data with a known source value. Do not rely on guessing based on which output appears plausible.

Q8. Is byte order the same as bit order?

No. Byte order describes the arrangement of bytes in a multi-byte value. Bit order describes the ordering of bits within a byte or their transmission sequence.

Q9. Does changing byte order fix every incorrect numerical value?

No. Incorrect addressing, scaling, signedness, data types, stale data, and inconsistent register reads can produce similar symptoms.

Q10. Why is byte-order documentation important during a retrofit?

A replacement device, driver, or gateway may represent multi-register values differently. Documenting the representation prevents silent numerical errors after migration.

Exercise 3: Decode a float

An instrument's expected value is 1.0, whose FLOAT32 representation is 0x3F800000.

  • Identify the two 16-bit words in normal order.
  • Reverse their order.
  • Explain why the receiving system must reconstruct the correct bit sequence before interpreting the result as a floating-point number.

Exercise 4: Plan a production diagnosis

A VFD's local display shows 1500 rpm, but the SCADA tag displays an extremely large value.

Write a diagnostic checklist that separates:

  • Register-address errors.
  • Data-type errors.
  • Byte-order and word-order errors.
  • Scaling errors.
  • Gateway or SCADA conversion errors.

14. Final mental model

Remember the processing sequence:

Raw bytes
    ↓
Bytes grouped into registers or words
    ↓
Correct byte and word ordering
    ↓
Correct data type and signedness
    ↓
Scaling and engineering units
    ↓
Validated process value

The key principle is simple: successful communication does not guarantee correct interpretation. Verify the raw bytes, register order, data type, and scaling independently before trusting a numerical value in an industrial system.
