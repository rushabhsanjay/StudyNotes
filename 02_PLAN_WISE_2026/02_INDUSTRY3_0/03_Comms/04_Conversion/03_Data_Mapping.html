1. What Is Data Mapping?

Data mapping is the process of defining how data from a source system corresponds to data in a destination system, including its meaning, format, type, units, scaling, structure, and update behavior.

In industrial automation, different devices may represent the same physical measurement in different ways. A PLC may store a temperature as an integer, an instrument may transmit it as a Modbus register, and a SCADA system may expect a floating-point value in degrees Celsius.

Data mapping establishes the relationship that allows these systems to exchange meaningful information.

For example:

  • A PLC tag Motor_Speed_RPM maps to an SCADA tag Line1_Motor_Speed.
  • A Modbus register containing a temperature value maps to a PLC variable.
  • A CNC machine's cycle-complete signal maps to a manufacturing dashboard status.
  • A robot's fault code maps to a diagnostic description in a maintenance application.
  • A PLC production counter maps to a database field used for reporting.

Core principle: Data mapping determines what a source value means at the destination, not merely where the bytes are copied.

2. Why Data Mapping Is Required

Industrial systems often come from different manufacturers and generations. They use different naming conventions, data types, units, addresses, status codes, and representations.

Without correct mapping, a communication link may be healthy while the information displayed or recorded is wrong.

Common reasons for data mapping include:

  • Connecting PLCs to SCADA or HMI systems.
  • Integrating CNCs, robots, VFDs, instruments, and barcode readers.
  • Exchanging information between PLCs from different manufacturers.
  • Sending shop-floor data to SQL databases, historians, MES, or dashboards.
  • Converting engineering units and raw instrument values.
  • Standardizing machine tags across production lines.
  • Associating machine signals with production orders, products, and quality results.
  • Replacing obsolete devices while retaining existing supervisory software.

Example: Same value, different representations

Suppose a temperature transmitter provides a raw integer value of 253, representing \(25.3\\,^\circ C\).

The PLC, SCADA, and database may represent the measurement differently.

System Representation Meaning
Transmitter Raw integer 253 Temperature encoded in tenths of a degree
PLC Integer 253 Raw measurement
SCADA Floating-point 25.3 Temperature in degrees Celsius
SQL database Decimal 25.3 Stored engineering value
Dashboard Text 25.3 °C Operator-facing presentation

The mapping must explicitly define the scale factor and engineering unit. Otherwise, the SCADA screen could display 253 °C, a technically valid number that is spectacularly wrong.

Where mapping can happen

5. Data Types and Type Conversion

The source and destination systems must agree on how a value is represented.

Common industrial data types

Data type Typical use Important consideration
BOOL Digital states, permissives, status bits Usually represents true or false
SINT / INT8 Small signed integers Limited numeric range
USINT / UINT8 Small unsigned integers No negative values
INT / INT16 Signed integer measurements or counts Check the range and signedness
UINT / UINT16 Unsigned values, often 16-bit registers Do not interpret as signed without justification
DINT / INT32 Counters, positions, integer values Check 32-bit representation
UDINT / UINT32 Unsigned counters or values Check overflow and destination support
REAL / FLOAT32 Analog values and calculations Floating-point precision is limited
LREAL / FLOAT64 Higher-precision calculations Destination may not support the same type
STRING Names, messages, serial data Length and encoding may differ
ARRAY Multiple related values Indexing and element types must match
STRUCT / UDT Grouped industrial data Member names, order, and structure may differ
ENUM Named states or modes Numeric codes require consistent definitions
DATE / TIME Dates, timestamps, durations Epoch, time zone, and unit conventions matter

Different PLC manufacturers use different type names. Confirm the actual data width and representation in the source and destination systems.

Signed versus unsigned interpretation

A 16-bit register can be interpreted as a signed or unsigned integer.

For the same 16-bit bit pattern, the numerical result may differ depending on the interpretation.

For example, the hexadecimal pattern 0xFFFF represents:

  • Unsigned 16-bit integer: 65535.
  • Signed 16-bit two's-complement integer: -1.

A signedness mismatch can produce large, seemingly random values even when communication is working perfectly.

Integer versus floating-point values

A PLC may store a measurement as an integer scaled by a constant, while SCADA expects a floating-point value.

For example:

\[ \text{Engineering Value}=\frac{\text{Raw Integer}}{10} \]

If the raw value is 253, the engineering value is 25.3.

The scale factor must come from the instrument manual, PLC logic, register map, or validated engineering specification.

6. Scaling and Engineering Units

Scaling converts raw data into a meaningful engineering quantity.

Common examples include:

  • Analog input counts to temperature.
  • Analog output counts to valve position.
  • Integer speed values to rpm.
  • Pressure values to bar or kPa.
  • Distance values to millimeters.
  • Energy counters to kWh.
  • Encoder counts to angular position.

Linear scaling

For a linear relationship between raw input and engineering value:

\[ EU=EU\_{\min}+ \frac{Raw-Raw\_{\min}}{Raw\_{\max}-Raw\_{\min}} (EU\_{\max}-EU\_{\min}) \]

Where:

  • \(EU\) is the engineering value.
  • \(Raw\) is the raw input.
  • \(Raw\_{\min}\) and \(Raw\_{\max}\) are the raw range limits.
  • \(EU\_{\min}\) and \(EU\_{\max}\) are the engineering range limits.

Example: Analog input scaling

Assume a transmitter uses a raw input range of 0 to 27648 to represent 0 to 100 bar.

If the raw input is 13824, then:

\[ EU=0+\frac{13824-0}{27648-0}(100-0) \]
\[ EU=50\text{ bar} \]

This example assumes that the selected PLC's analog module actually uses that raw range. Raw ranges vary by manufacturer, module, configuration, and input mode.

Scaling mistakes

  • Applying a scale factor twice.
  • Using the wrong raw range.
  • Confusing percentages with engineering units.
  • Reversing the minimum and maximum limits.
  • Ignoring negative ranges.
  • Using integer division where floating-point arithmetic is required.
  • Treating an invalid sensor value as a legitimate measurement.
  • Assuming every 4–20 mA input uses the same digital counts.

Unit conversion

Data mapping may also require conversion between units.

For temperature:

\[ ^\circ F=\frac{9}{5}(^\circ C)+32 \]

For pressure:

\[ 1\text{ bar}=100\text{ kPa} \]

For rotational speed, the mapping must preserve whether the source reports rpm, revolutions per second, or another unit.

Unit conversion must be documented separately from raw-value scaling so that each transformation can be tested.

7. Mapping Digital Signals and Machine States

Digital signals often require semantic mapping rather than numeric scaling.

A PLC bit may indicate that a machine cycle is complete. The destination application may use a standardized state called CycleComplete.

Example:

Source signal Source meaning Destination tag Destination meaning
I0.0 Sensor input active PartPresent Part detected
M10.0 Cycle completion bit CycleComplete Cycle finished
M10.1 Fault flag MachineFault Fault condition active
M10.2 Automatic mode flag AutoMode Automatic operating mode selected
M10.3 Safety circuit status SafetyStatus Status supplied by the safety system

The address examples are illustrative. A status tag must reflect the actual signal meaning and logic.

Polarity and inversion

Some devices use active-low signals. A raw 0 can mean active, while a raw 1 can mean inactive.

The mapping must document whether the signal is inverted.

However, do not infer a safety condition from a single ordinary PLC bit. Emergency stops, guard circuits, and safety functions require their designed safety architecture and validated status interpretation. A mapped status signal must not replace the certified safety function.

Machine-state mapping

A machine may have source states represented as integers:

Source code Source state Standardized destination state
0 Stopped Stopped
1 Running Running
2 Faulted Fault
3 Setup mode Setup
4 Waiting for material Waiting

This table is only an example. The source machine's documented state definitions take precedence.

If an unknown code arrives, map it to an explicit state such as Unknown rather than silently treating it as Stopped.

8. Mapping Structured Data

Industrial controllers frequently expose arrays, structures, and user-defined data types.

A source PLC may group a motor's data into a structure, while SCADA exposes each member as a separate tag.

Example source structure:

MotorData
  Running       : BOOL
  Faulted       : BOOL
  SpeedRaw      : INT
  CurrentRaw    : INT
  FaultCode     : UINT

A destination mapping might expose:

Line1.Motor.Running
Line1.Motor.Faulted
Line1.Motor.SpeedRPM
Line1.Motor.CurrentA
Line1.Motor.FaultCode

The mapping should document the conversion for SpeedRaw and CurrentRaw, not just rename them.

Arrays and indexing

If a source array contains data for several stations, verify:

  • Array length.
  • Index origin and bounds.
  • Element data type.
  • Element ordering.
  • Whether unused positions are reserved.
  • Whether the destination expects zero-based or one-based indexing.

A one-position offset can associate a measurement with the wrong station or machine.

Structures and version changes

When a PLC user-defined data type changes, downstream systems may be affected.

For example, adding a member to a structure may change its layout or alter the interface contract, depending on the platform and access method.

Document the data structure version and retest downstream mappings after approved changes.

10. Metadata, Quality, and Timestamps

A numeric value alone may be insufficient for reliable industrial monitoring.

Metadata

Metadata describes the data item itself.

Useful fields include:

  • Tag name and description.
  • Engineering unit.
  • Equipment and process location.
  • Source device.
  • Data type.
  • Valid range.
  • Update interval.
  • Read/write permissions.
  • Alarm limits where applicable.
  • Mapping version.

Data quality

A communication system may expose quality information indicating whether a value is good, uncertain, or bad.

Examples of invalid conditions include:

  • Communication loss.
  • Device fault.
  • Out-of-range measurement.
  • Stale value.
  • Uninitialized variable.
  • Unsupported or invalid source status.

Do not automatically convert an invalid value to zero. Zero may be a valid measurement, and replacing a communication failure with zero can create false production or quality conclusions.

A robust mapping preserves or translates the source quality state and makes the destination behavior explicit.

Timestamps

Different systems may timestamp data at different points:

  • At the instrument's measurement time.
  • At the PLC scan or data update.
  • At the gateway reception.
  • At the SCADA acquisition.
  • At the database insertion.

These times are not necessarily identical.

Record whether the timestamp represents source time or receive time. Synchronize relevant device clocks where possible, and document time zone and timestamp format conventions.

11. Data Mapping Versus Related Concepts

These concepts are related but not interchangeable.

Concept Main purpose Example
Data mapping Defines source-to-destination relationships and meaning PLC tag to SCADA tag
Register mapping Defines how protocol registers correspond to application values Modbus holding register to temperature
Protocol conversion Translates one protocol into another Modbus RTU to Modbus TCP
Data transformation Changes a value or structure Raw counts to degrees Celsius
Data normalization Makes representations consistent across systems Standardized equipment and tag names
Data acquisition Reads or receives source data Polling a Modbus instrument
Data validation Checks whether data meets defined rules Rejecting an impossible temperature
Data historian integration Stores time-series operational values Recording motor speed over time

A single integration may use all these functions. Keeping their responsibilities separate makes fault diagnosis and change control much easier.

12. Data Mapping Design Principles

Use consistent naming

Choose names that describe the equipment, measurement, and meaning.

For example:

Plant.Area.Machine.Motor.Speed
Plant.Area.Machine.Motor.Current
Plant.Area.Machine.Motor.Running
Plant.Area.Machine.Motor.FaultCode

A naming standard should define separators, abbreviations, units, equipment identifiers, and reserved words.

Avoid ambiguous names such as DATA1, VALUE, or TEMP2 unless they are part of a defined interface specification.

Preserve the source meaning

A tag named MotorSpeed is incomplete if the unit and representation are unknown.

Record whether it represents:

  • Commanded speed.
  • Actual measured speed.
  • Speed reference percentage.
  • Encoder feedback.
  • A raw register value.

These values may differ significantly during acceleration, deceleration, or a fault.

Separate raw and engineering values

Where practical, keep raw data separate from scaled engineering values.

For example:

MotorSpeedRaw
MotorSpeedRPM

This makes troubleshooting easier because the raw value can be compared with the engineering conversion.

Do not duplicate raw values everywhere without a reason. Maintain a clear source of truth.

Make transformations explicit

Document every operation that changes the value:

  • Scaling.
  • Offset correction.
  • Unit conversion.
  • Boolean inversion.
  • Enumeration translation.
  • Bit extraction.
  • Byte or word reordering.
  • String parsing.
  • Timestamp conversion.
  • Filtering or aggregation.

Define update behavior

A mapping must clarify whether data is updated cyclically, on change, on request, or when an event occurs.

Also define what happens when the source stops updating. Holding the last value indefinitely without a stale-data indication can mislead operators.

13. Commissioning a Data Map

A disciplined commissioning process verifies each mapping from source to destination.

  1. Collect the source specification. Obtain PLC tag lists, instrument manuals, protocol maps, data structures, and approved drawings.
  2. Identify the destination. Record the destination tag, field, or node and its required data type.
  3. Define the transformation. Specify scaling, units, signedness, bit interpretation, state translation, and data validation.
  4. Document quality and timing. Define update rate, timeout behavior, stale-data handling, and timestamp meaning.
  5. Check access rights. Identify read-only values and approved writable commands.
  6. Build the mapping table. Record source, destination, data type, unit, conversion, and validation rules.
  7. Verify representative values. Test low, typical, high, boundary, and invalid values as appropriate.
  8. Test failure behavior. Simulate or safely reproduce communication loss and invalid source data in a controlled environment.
  9. Compare source and destination. Confirm that both the value and its meaning are preserved.
  10. Approve and version the mapping. Save the final map, test results, and configuration backup.

Example validation table

Test case Source value Expected destination Result to verify
Low value Raw 0 0.0 bar Lower limit
Midpoint Raw 13824 50.0 bar Scaling
Full-scale value Raw 27648 100.0 bar Upper limit
Invalid source Bad quality Invalid or bad-quality destination No false valid reading
Communication loss No new data Stale or bad status according to design Failure visibility

The numerical example assumes a raw range of 0 to 27648 mapped to 0 to 100 bar. Use the actual device and module specifications in production.

15. Data Mapping in Maintenance and Manufacturing

For a maintenance engineer, data mapping is useful beyond establishing communication.

Equipment standardization

A production line may contain machines from different manufacturers, each using different tag names and state codes.

A common mapping standard can normalize them into shared concepts such as:

  • Machine.Running
  • Machine.Faulted
  • Machine.Mode
  • Production.GoodCount
  • Production.RejectCount
  • Cycle.Time
  • Motor.Speed
  • Motor.Current

The common model makes dashboards and reports easier to build, while the original source mapping preserves traceability to each machine.

Fault diagnosis

Suppose a dashboard shows that a machine has stopped.

A well-designed mapping allows the engineer to trace:

  1. The dashboard status.
  2. The SCADA tag.
  3. The source PLC variable.
  4. The underlying logic or physical input.
  5. The quality state and timestamp.

Without this traceability, a displayed fault can be mistaken for an actual machine condition when the real problem is a stale or incorrectly mapped value.

Spare parts and retrofit work

When replacing an obsolete controller or instrument, preserve the existing external interface where practical.

Create a migration map that compares:

  • Old source address and data type.
  • New source address and data type.
  • Units and scaling.
  • State codes and alarm behavior.
  • Update rates and timeouts.
  • Destination tags and application dependencies.

A replacement device may use different addresses or data representations even when its physical measurement is identical. Retesting the full mapping prevents hidden integration failures after commissioning.

16. Data Mapping Security and Change Control

Data mapping can include writable values, commands, and operational state information. Errors may affect equipment behavior, reporting, and production decisions.

Apply these controls:

  • Maintain approved mapping specifications and version history.
  • Restrict write access to authorized applications and users.
  • Separate monitoring data from control commands where practical.
  • Validate command ranges and permitted states.
  • Do not allow untrusted data to directly trigger hazardous machine actions.
  • Preserve data quality and stale-state indicators.
  • Test changes in a controlled environment before production deployment.
  • Back up PLC programs, gateway configurations, SCADA databases, and mapping files.
  • Review mappings after controller replacement, firmware changes, or software upgrades.
  • Record who approved and implemented each change.

Important: Mapping a safety-related status into SCADA is for visibility and diagnostics. It does not replace the designed safety function, safety-rated communications, or required validation.

18. Interview Questions and Answers

1. What is data mapping in industrial automation?

Data mapping defines the relationship between source data and destination data, including names, types, units, scaling, meaning, and update behavior.

2. What is the difference between data mapping and protocol conversion?

Data mapping defines how data items correspond and how their meaning is preserved. Protocol conversion translates messages between supported communication protocols.

3. Why is scaling required?

Raw values may represent counts or encoded measurements. Scaling converts them into meaningful engineering values such as bar, degrees Celsius, or rpm.

4. What is a signedness mismatch?

It occurs when a bit pattern is interpreted using the wrong signed or unsigned numeric type, causing the displayed value to differ from the intended value.

5. Why must engineering units be included in a data map?

The same numerical value can represent different physical quantities or scales. Units prevent incorrect interpretation and support valid comparisons.

6. What is enumeration mapping?

It translates numeric state codes into standardized destination states, such as 0 = Stopped and 1 = Running, based on the source system's documented definitions.

7. What is stale data?

Stale data is a value that has not been refreshed within the expected time. It may still look valid numerically even though it no longer represents the current process.

8. Why should bad quality not automatically become zero?

Zero may be a valid process measurement. Replacing bad data with zero can create false alarms, incorrect reports, or misleading production metrics.

9. What is the purpose of a data dictionary?

A data dictionary defines tag names, meanings, data types, units, ownership, valid ranges, and other metadata so that different applications interpret data consistently.

10. What should be checked when a value is correct in the PLC but wrong in SCADA?

Trace the source tag, acquisition configuration, data type, signedness, scaling, unit conversion, state mapping, and destination tag configuration.

11. Why does timestamp meaning matter?

A source timestamp describes when the measurement was produced, while a receive timestamp describes when another system received it. The difference affects latency analysis and time-series correlation.

12. What should be tested after a PLC retrofit?

Retest source addresses, data types, scaling, units, state codes, quality handling, timestamps, update behavior, alarms, and downstream dependencies.

19. Practical Exercises

Exercise 1: Build a basic analog data map

Use a test signal with a raw range of 0 to 27648 representing 0 to 100 bar.

  • Define the source tag and data type.
  • Define the destination tag and engineering unit.
  • Calculate the midpoint conversion.
  • Test lower and upper limits.
  • Record the conversion formula and assumptions.

Exercise 2: Map machine states

Use a simulated machine with documented source codes for stopped, running, faulted, and setup.

  • Create a source-to-destination state table.
  • Define the behavior for unknown codes.
  • Test every supported state.
  • Confirm that the SCADA display matches the source status.

Exercise 3: Diagnose an incorrect value

Use a non-production environment and introduce one controlled mapping error, such as an incorrect scale factor.

  • Compare the raw source value with the destination value.
  • Trace every transformation.
  • Identify the incorrect conversion.
  • Correct the mapping.
  • Record the root cause and verification results.

Exercise 4: Map PLC data into a SQL table

Define a mapping for:

  • Machine identifier.
  • Running state.
  • Actual motor speed.
  • Production counter.
  • Fault code.
  • Timestamp.
  • Data quality.

Specify whether the integration stores periodic snapshots, changes only, or one record per production event. Test that invalid data cannot be mistaken for valid zero-valued measurements.

20. Final Mental Model

Think of data mapping as an explicit contract between industrial systems.

For every mapped item, be able to answer:

  1. Where does the value originate?
  2. What does the source value actually mean?
  3. What are its data type, units, and valid range?
  4. Does it require scaling, conversion, or state translation?
  5. Where is the value delivered?
  6. How are quality, timestamps, and stale data handled?
  7. How will the mapping be verified after a change?

When these answers are documented and tested, data mapping becomes a controlled engineering activity rather than a collection of mysterious tags that nobody wants to touch after commissioning.
