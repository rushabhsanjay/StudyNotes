1. What Is Register Mapping?

Register mapping is the process of identifying which communication registers correspond to particular parameters, measurements, commands, and status values in an industrial device.

Registers are commonly used by PLCs, VFDs, energy meters, temperature controllers, CNC equipment, and other devices to expose data through communication protocols such as Modbus RTU and Modbus TCP.

A register map typically specifies:

  • Register address.
  • Register type or address space.
  • Read/write permissions.
  • Data type and width.
  • Engineering meaning.
  • Units and scaling.
  • Byte order and word order.
  • Valid ranges and special values.
  • Supported function codes.
  • Device-specific restrictions.

For example, a VFD may expose motor frequency, output current, operating status, fault code, and speed reference through different registers. A PLC or SCADA application must access the correct registers and interpret their contents according to the drive manufacturer's documentation.

Core principle: A register address identifies where data can be accessed. The register map explains what that data means and how it must be interpreted.

2. Why Register Mapping Matters in Industrial Automation

Industrial devices often expose their internal parameters through communication registers instead of directly exposing meaningful tag names.

A register might contain the number 500, but its meaning depends on the device documentation. It could represent 50.0 Hz, 500 rpm, a status code, or a command value.

Incorrect register mapping can cause:

  • Incorrect measurements on HMI or SCADA screens.
  • Wrong VFD speed references.
  • Incorrect energy consumption reports.
  • Fault codes being interpreted as normal values.
  • PLC communication timeouts or exception responses.
  • Incorrect machine-state detection.
  • Unintended parameter changes when writing to the wrong register.
  • Misleading production and maintenance dashboards.

A healthy network connection does not prove that the correct register is being accessed.

The device manufacturer defines the register behavior. The communication client must use the correct address, access method, data representation, and conversion rules.

Register mapping may be configured in a PLC communication instruction, SCADA driver, gateway, OPC server, or application-specific integration layer.

4. Understanding Modbus Register Types

Modbus defines four primary data categories in its traditional data model.

Data category Typical notation Access Data representation
Coils 0xxxx Read and write, subject to device support Single-bit values
Discrete inputs 1xxxx Read-only Single-bit values
Input registers 3xxxx Read-only 16-bit registers
Holding registers 4xxxx Read and/or write, subject to device support 16-bit registers

These traditional reference prefixes are documentation conventions. They are not necessarily literal addresses transmitted in a Modbus message.

For example, a manual might identify a holding register as 40001, while the protocol request uses zero-based address 0. Another software package might display the same register using a one-based reference.

Never assume that a printed reference number can be entered directly into every Modbus client.

Function codes commonly used

Function code Name Purpose
01 Read Coils Read coil states
02 Read Discrete Inputs Read discrete input states
03 Read Holding Registers Read holding registers
04 Read Input Registers Read input registers
05 Write Single Coil Write one coil
06 Write Single Register Write one holding register
0F Write Multiple Coils Write several coils
10 Write Multiple Registers Write several holding registers
16 / 0x16 Mask Write Register Modify selected bits of a holding register, where supported
17 / 0x17 Read/Write Multiple Registers Read and write holding registers in one transaction, where supported

Actual device support varies. A register being listed in a manual does not guarantee that every function code is supported for that register.

5. Register Addresses Versus Reference Numbers

One of the most common Modbus commissioning mistakes is confusing a reference number with the actual protocol address.

Consider an illustrative manual entry:

Manual reference Register type Protocol address under a zero-based convention
40001 Holding register 0
40002 Holding register 1
40010 Holding register 9
40101 Holding register 100

This example assumes the manual uses the conventional one-based 4xxxx reference notation.

Some manufacturers and software tools use zero-based addresses directly, and others use different reference conventions. Always follow the specific manual and client software documentation.

How to determine the correct address

  1. Find the parameter in the device's register map.
  2. Identify its register type and documented address notation.
  3. Determine whether the address is zero-based or one-based.
  4. Select the correct Modbus function code.
  5. Enter the address in the form expected by the software.
  6. Read a known, safe register and compare the result with the device display or documented value.

If the device returns an illegal data address, verify the address convention and register support before assuming that the communication hardware is faulty.

6. Register Width and Data Types

A Modbus register is 16 bits wide. Larger data types may occupy multiple consecutive registers.

Data type Typical width Registers required
Boolean or bit field 1 bit or selected bits One register may contain multiple bits
UINT16 16 bits 1
INT16 16 bits 1
UINT32 32 bits 2
INT32 32 bits 2
IEEE 754 FLOAT32 32 bits 2
UINT64 64 bits 4
IEEE 754 FLOAT64 64 bits 4

The table shows common representations, not a guarantee that every device supports them.

Example: A 32-bit value

Suppose a device stores a 32-bit counter across two consecutive 16-bit registers:

  • Register 100: high-order word.
  • Register 101: low-order word.

The combined value is:

\[ Value=(HighWord \times 65536)+LowWord \]

If the high word is 1 and the low word is 1000:

\[ Value=(1 \times 65536)+1000=66536 \]

This is correct only if the device defines the value as an unsigned 32-bit integer with the stated word order.

If the device uses a signed integer or a different word order, the interpretation changes.

7. Scaling and Engineering Values

Registers frequently store raw integers rather than directly storing engineering values.

For example, a register may represent output frequency in tenths of a hertz.

If the raw register value is 503, then:

\[ Frequency=\frac{503}{10}=50.3\text{ Hz} \]

A register map must document:

  • Raw register value.
  • Engineering unit.
  • Scale factor.
  • Offset, if applicable.
  • Valid operating range.
  • Special values indicating faults or invalid data.

Scaling formula

For a simple scale factor:

\[ EngineeringValue=RawValue \times ScaleFactor \]

For a linear transformation:

\[ EngineeringValue=(RawValue \times ScaleFactor)+Offset \]

Not every device uses linear scaling. Some use enumerations, packed bits, floating-point formats, or device-specific encoding.

Common scaling mistakes

  • Forgetting a factor of 10 or 100.
  • Applying scaling twice.
  • Treating a percentage as an engineering unit.
  • Using the wrong signedness.
  • Assuming a value is always valid.
  • Ignoring a register's special-value definitions.
  • Confusing a command reference with actual measured feedback.

For a VFD, SpeedReference and ActualSpeed are different data points even if both are expressed in rpm or hertz.

8. Bit-Level Register Mapping

A single 16-bit register can contain multiple Boolean states.

For example, a drive status register may encode:

  • Bit 0: Ready.
  • Bit 1: Running.
  • Bit 2: Faulted.
  • Bit 3: Warning.
  • Bit 4: Direction status.

These assignments are illustrative. The manufacturer's documented bit definitions must be used.

Extracting a bit

For bit position \(n\):

\[ Bit_n=(Register \gg n)\ \&\ 1 \]

This is a conceptual bitwise expression. In a programming environment, the equivalent operation depends on the language and data type.

If a status register contains the binary pattern:

0000 0000 0000 0110

Then bits 1 and 2 are set.

Using the example definitions above, the drive would report running and faulted simultaneously. That combination might be possible, transient, or invalid depending on the drive's state model. The interpretation must follow the manufacturer's documentation.

Bit masks

A bit mask selects specific bits without interpreting the entire register as one number.

For example:

  • Mask 0x0001 selects bit 0.
  • Mask 0x0002 selects bit 1.
  • Mask 0x0004 selects bit 2.
  • Mask 0x0008 selects bit 3.

Bit masks are useful when several status signals share one holding or input register.

9. Read-Only, Writable, and Command Registers

Not all registers have the same access permissions or operational consequences.

Read-only registers

Common uses include:

  • Actual motor speed.
  • Output current.
  • DC bus voltage.
  • Energy consumption.
  • Device status.
  • Fault code.
  • Temperature measurements.

Writable registers

Common uses include:

  • Speed references.
  • Operating mode selection.
  • Configuration parameters.
  • Reset commands.
  • Start and stop commands, where the device supports them.

A writable register may require a particular function code, enable condition, operating mode, password, or sequence of operations.

Command registers

Some registers are not ordinary storage locations. Writing a specific value may initiate an action, acknowledge an event, reset a fault, or trigger a state transition.

Before writing to a register:

  1. Confirm the exact register and its documented purpose.
  2. Verify the permitted range and allowed values.
  3. Check whether the write changes persistent configuration.
  4. Determine whether the machine must be stopped or placed in a specific mode.
  5. Confirm any interlocks and required permissions.
  6. Test only through an approved procedure and controlled environment.

Do not experiment with unknown writable registers on live production equipment. A successful write response proves only that the device accepted the request, not that the resulting machine behavior is safe.

11. Register Maps in PLC, SCADA, and Gateways

PLC mapping

A PLC may read a block of registers and copy their contents into internal tags.

For example:

Modbus Register 40002
        |
        v
Raw Integer Tag
        |
        v
Scale Conversion
        |
        v
ActualFrequency_Hz

A good implementation preserves the raw value when useful for diagnostics and separates it from the engineering value.

SCADA mapping

SCADA drivers may allow a user to configure:

  • Device or slave address.
  • Function code or register type.
  • Starting address.
  • Data type.
  • Number of registers.
  • Scaling.
  • Polling interval.
  • Timeout and retry behavior.

The precise fields depend on the SCADA product and communication driver.

Gateway mapping

A gateway may read source registers and expose the results through another interface, such as OPC UA or a database integration.

The gateway configuration must preserve the original register meaning, data type, scaling, quality, and access permissions.

If scaling is applied in the gateway, the destination should not apply the same transformation again unless explicitly intended.

12. Reading Multiple Registers Efficiently

Modbus supports reading multiple consecutive registers in a single request through supported function codes.

For example, if a device exposes actual frequency, current, voltage, and status in a contiguous register block, one request may retrieve several values.

Advantages include:

  • Reduced request overhead.
  • Lower network transaction count.
  • More efficient polling.
  • Potentially more consistent acquisition timing for adjacent values.

However, reading a block also requires care.

  • The entire address range must be valid.
  • The requested quantity must be within protocol limits.
  • The device must support the requested function.
  • Register values may update internally at different times.
  • Some devices restrict reads across parameter groups or memory boundaries.

Do not assume that all registers between two known addresses are valid or readable.

Example

Suppose a device provides four consecutive 16-bit registers starting at protocol address 100.

A read of four holding registers may retrieve addresses 100 through 103, if the device supports that range.

The client must then interpret each register according to its individual definition. A contiguous read does not mean all values have the same data type or scale.

13. Polling Rate and Communication Load

Register mapping includes decisions about how frequently each value is read.

A fast-changing status bit may require a faster update rate than a slowly changing energy counter.

Consider:

  • Required process response time.
  • Number of devices.
  • Number of requests.
  • Registers per request.
  • Device processing time.
  • Network latency.
  • Retry and timeout settings.
  • PLC scan time and communication-task capacity.
  • SCADA or gateway acquisition limits.

Excessive polling can increase communication load and cause timeouts or delayed updates.

Group compatible contiguous registers where appropriate, but avoid reading unnecessary data merely because it is nearby in the address space.

A slower update interval may be appropriate for a cumulative energy counter, while a drive status or production-cycle state may need faster acquisition.

The correct rate depends on the process requirement and device capabilities.

15. A Structured Register Mapping Diagnostic Procedure

Step 1: Confirm device identity

Record the manufacturer, model, firmware version, and communication interface.

Use the register map corresponding to the actual device and firmware where available.

Step 2: Verify the communication path

Confirm that the device responds to a known valid request.

For Modbus, check the slave address, serial settings for RTU, IP and port for TCP, and the relevant function code.

Step 3: Verify address convention

Determine whether the software expects:

  • A zero-based protocol address.
  • A one-based register number.
  • A traditional 3xxxx or 4xxxx reference.
  • A vendor-specific address notation.

Do not convert addresses by guesswork.

Step 4: Read a known register

Select a documented read-only register with a known or easily verified value.

Compare the raw response with the expected value.

Step 5: Verify interpretation

Check:

  • Register type.
  • Signedness.
  • Data width.
  • Number of registers.
  • Byte order and word order.
  • Scale factor and offset.
  • Engineering unit.
  • Special values and enumeration definitions.

Step 6: Verify application mapping

Trace the value from the communication driver into the PLC tag, SCADA tag, or database field.

Check whether any layer changes the value again.

Step 7: Test failure behavior

In a controlled environment, verify how the application handles timeouts, invalid values, communication loss, and unsupported registers.

Ensure that the system does not silently present failed communication as a valid zero measurement.

Step 8: Document and approve

Record the tested register map, device settings, validation results, and approved configuration changes.

17. Register Mapping and Retrofit Projects

Register mapping is particularly important when replacing obsolete automation equipment or integrating different manufacturers.

Before replacing a device, compare the old and new register maps.

Item to compare Why it matters
Register address The same parameter may move to a different address
Function code The new device may support different access methods
Data type An integer may become a floating-point value or vice versa
Register count A value may occupy one, two, or four registers
Scaling Engineering values may use different multipliers or offsets
Units Frequency, speed, current, and pressure may use different units
Bit definitions Status and fault bits may have different meanings
Enumerations Mode and fault codes may change
Write behavior Commands may require different conditions or sequences
Update timing Polling limits and device response times may differ
Firmware compatibility Register definitions may vary between firmware versions

Do not assume that matching parameter names imply compatible register addresses or semantics.

For a retrofit, the new device should be validated against the complete destination interface, including alarms, trends, reports, and any control logic that consumes the mapped values.

18. Interview Questions and Answers

1. What is register mapping?

Register mapping defines how communication registers correspond to device parameters, measurements, status information, and commands.

2. What is the difference between a coil and a holding register?

A coil represents a single-bit value and is commonly readable and writable. A holding register represents a 16-bit value and may be readable or writable, depending on device support.

3. What is the difference between input registers and holding registers?

In the traditional Modbus model, input registers are read-only and holding registers are readable and potentially writable. The device manual defines which values are actually available.

4. Why might register 40001 be entered as address 0 in a Modbus client?

The manual may use one-based reference notation, while the client expects a zero-based protocol address. The exact convention must be verified.

5. How many Modbus registers are required for a 32-bit integer?

Two consecutive 16-bit registers are required.

6. Why can the same register produce different values in two applications?

The applications may use different address conventions, signedness, data types, byte or word order, scaling, or offsets.

7. What is a status word?

A status word is a numeric value whose individual bits represent different status conditions, such as ready, running, warning, or faulted.

8. Why should raw register values be retained for troubleshooting?

They allow engineers to distinguish communication and addressing problems from scaling and interpretation errors.

9. What causes an illegal data address exception?

The requested address or range may be unsupported, incorrect, or invalid for the selected function code.

10. Why can reading several registers in one request be useful?

It can reduce transaction overhead and improve acquisition efficiency, provided the requested range is valid and the device supports the operation.

11. What should be checked before writing to a register?

Confirm the address, function code, data type, valid range, permissions, operating conditions, and potential machine consequences.

12. What should be reviewed when replacing a VFD?

Compare the old and new register maps, scaling, status bits, fault codes, command behavior, update timing, and destination tag mappings.

19. Practical Exercises

Exercise 1: Interpret a holding register

A training instrument documents a holding register with a raw value of 725. The manual states that the scale factor is 0.1.

  • Calculate the engineering value.
  • Record the data type and unit from the manual.
  • Identify the destination PLC or SCADA tag.
  • Specify how invalid or stale values should be handled.

Expected numerical result: 72.5 in the documented engineering unit.

Exercise 2: Identify an addressing error

A manual lists a holding register as 40010. The client may use zero-based addressing.

  • Determine the corresponding protocol address under the conventional one-based reference notation.
  • Verify the client software's addressing convention.
  • Read the documented register.
  • Compare the result with the expected value.

Under that convention, the protocol address would be 9. Do not apply this conversion without verifying the actual manual and software.

Exercise 3: Decode a status word

Use a training status word with documented bit assignments.

  • Record the raw 16-bit value.
  • Convert it to binary or hexadecimal.
  • Extract the required bits.
  • Translate each bit into its documented meaning.
  • Test an unknown or reserved bit condition.

Do not invent bit meanings for undocumented positions.

Exercise 4: Validate a two-register counter

Use a simulated 32-bit counter exposed through two consecutive registers.

  • Read both registers.
  • Determine the documented word order.
  • Combine the words.
  • Check whether the data is signed or unsigned.
  • Compare the result with the simulated source counter.

Exercise 5: Build a VFD register map

Using a real VFD manual in a training environment, document:

  • Actual frequency.
  • Output current.
  • Status word.
  • Fault code.
  • Speed or frequency reference.

Include the actual addresses, supported function codes, data types, scaling, units, permissions, and verification procedure. Do not use the illustrative addresses in this note as a real drive configuration.

20. Final Mental Model

Register mapping is the bridge between a device's communication memory and the engineering meaning of its parameters.

For each register, establish:

  1. Address: Where is the data?
  2. Access: Can it be read, written, or both?
  3. Type: How many bits or registers represent it?
  4. Interpretation: Is it an integer, floating-point value, bit field, or enumeration?
  5. Conversion: What scaling, offset, unit, or word ordering applies?
  6. Meaning: What machine condition or measurement does it represent?
  7. Validation: How can the value be independently verified?
  8. Protection: What could happen if the wrong register is written?

Once these are documented, register-level communication becomes easier to commission, troubleshoot, standardize, and migrate during machine retrofits.
