1. Definition and Purpose

A backup procedure is a documented, repeatable method for creating, storing, protecting, validating, and restoring copies of equipment data, software, configurations, and other information required to recover an industrial system after failure, corruption, accidental modification, cyber incident, or hardware replacement.

In industrial maintenance, a backup is not merely a file saved on a laptop. It must be identifiable, complete enough for its intended purpose, compatible with the target equipment, protected against unauthorized changes, and restorable within the required recovery time.

For PLCs, HMIs, CNC machines, robots, VFDs, test systems, SCADA servers, and industrial PCs, backups help preserve:

  • Control logic and application programs.
  • Hardware configuration and I/O mapping.
  • Device parameters and tuning values.
  • HMI screens, alarms, recipes, and user settings.
  • CNC and robot programs, offsets, and relevant configuration data.
  • Communication settings and network configuration.
  • SCADA applications, tag databases, historian settings, and reports.
  • Industrial PC operating-system images and application configurations.
  • Database structures, records, and required transaction history.
  • Licenses, firmware information, recovery media, and dependency records.

Core principle: A backup is useful only when the correct data can be restored successfully and the recovered system can be verified safely.

Term Meaning

Immutable backup A backup protected against alteration or deletion for a defined retention period
Checksum A calculated value used to detect changes or corruption in data
Recovery Point Objective (RPO) The maximum acceptable amount of data loss expressed as a time interval

A checksum can help detect accidental corruption or unexpected changes. It does not, by itself, prove that a file is correct, safe, or the approved version.

3. Backup Versus Restore Versus Recovery

Activity Main question Example
Backup Do we have a recoverable copy? Upload and save the PLC project
Restore Can we put the saved data back? Download the approved project to a replacement PLC
Verification Does the restored copy match expectations? Compare project version and hardware configuration
Functional validation Does the equipment work correctly? Verify I/O, interlocks, sequence, and machine operation
Recovery Can the overall system return to service? Restore PLC, HMI, communications, and associated configuration

A file can exist without being a valid backup. A restore can complete without producing a working machine. These distinctions are important because industrial systems contain dependencies beyond a single application file.

4. What Must Be Backed Up?

Backup scope should be determined by the equipment's recovery requirements, OEM documentation, site procedures, and risk assessment.

System Typical backup items
PLC Project, logic, hardware configuration, I/O configuration, relevant controller settings
HMI Application project, screens, alarms, recipes, user settings where supported
SCADA Application files, tag configuration, alarm settings, historian configuration
VFD Parameters, motor data, control settings, communication configuration
Servo Drive parameters, motor/encoder configuration, tuning and scaling settings
CNC Machine parameters, programs, tool data, offsets, compensation and OEM-specific configuration
Robot Programs, frames, tools, mastering-related records, configuration and approved recovery data

SQL Server Databases, transaction logs where applicable, database configuration and recovery metadata
Node-RED Flows, settings, credentials handled according to the platform's security requirements, installed nodes and version details

Not every device exposes all its configuration in a transferable backup. Some settings may be stored in hardware, proprietary memory, removable media, licensing systems, or OEM-managed files. Document these limitations explicitly.

5. Types of Backup

5.1 Full backup

A full backup captures the complete defined dataset or system scope.

Advantages:

  • Easier to identify as a standalone recovery set.
  • Useful as a baseline before major modifications.
  • Reduces dependency on earlier backup sets for some restore methods.

Limitations:

  • Can require more storage and time.
  • Does not automatically guarantee application consistency or a successful restore.

5.2 Incremental backup

An incremental backup captures changes since the most recent backup in the relevant incremental chain, according to the backup system's design.

Advantages:

  • Often uses less storage.
  • Can reduce backup duration.

Limitations:

  • Recovery may depend on the full backup and every required incremental backup in the chain.
  • Missing or corrupted chain components can prevent complete recovery.

5.3 Differential backup

A differential backup captures changes since the last full backup.

Advantages:

  • Restoration commonly requires the full backup and the latest applicable differential backup.
  • Can simplify recovery compared with long incremental chains.

Limitations:

  • Differential size can grow until the next full backup.
  • Exact behavior depends on the backup product.

5.4 Image backup

An image backup captures a disk, partition, or system in a form that can be restored using compatible imaging software.

Common uses include:

  • Industrial PCs running SCADA or test applications.
  • Legacy systems with difficult-to-reinstall software.
  • Engineering workstations with specific drivers and vendor applications.
  • Servers where rebuilding the operating environment would take significant time.

Image restoration may depend on compatible storage, boot configuration, hardware drivers, licensing, and imaging software. An image of an industrial PC does not automatically back up every external database, controller, or network device connected to it.

5.5 Application-level backup

An application-level backup uses the application's own export, archive, or backup functionality.

Examples include PLC project archives, HMI project exports, SQL Server database backups, and supported configuration exports from network devices.

This is often preferable to copying live application files because the application may need to preserve internal consistency, dependencies, or metadata.

5.6 Offline and immutable copies

An offline backup is disconnected from the production system or network while stored. An immutable backup is protected against modification or deletion for a specified period.

These approaches can reduce the impact of ransomware, accidental deletion, compromised credentials, and unauthorized changes. They do not eliminate the need for access control, retention management, and restore testing.

6. The 3-2-1 Backup Principle

A widely used backup strategy is the 3-2-1 principle:

  • Maintain at least 3 copies of important data, including the production copy.
  • Store copies on 2 different types of storage.
  • Keep at least 1 copy off-site or in an appropriately isolated location.

For industrial control systems, this principle must be adapted to operational constraints. A remote copy may be useful for disaster recovery, while a validated local recovery copy may be needed to restore equipment during a network outage.

A stronger strategy may include an offline or immutable copy and routine restore tests. Multiple copies are not independent protection if they are all accessible using the same compromised account or are continuously synchronized with corrupted data.

The architecture should define who can create, approve, modify, access, restore, and delete backups.

For high-impact assets, use a controlled repository rather than relying on individual technicians' laptops, personal USB drives, or untracked folders.

8. Backup Planning and Asset Prioritization

Not every asset requires the same backup frequency or recovery method.

Prioritize assets based on:

  • Safety and environmental impact.
  • Production criticality and bottleneck status.
  • Availability of replacement hardware.
  • Time required to rebuild the system.
  • Complexity of OEM configuration.
  • Risk of losing recipes, offsets, parameters, or traceability.
  • Consequences of incorrect restoration.
  • Availability of vendor support and recovery media.
  • Software licensing and activation requirements.
  • Exposure to cyber incidents or accidental modification.

A machine with a standard PLC program and readily available spare hardware may have different recovery needs from a specialized test bed whose application, instrumentation settings, and calibration-related records require OEM support.

9. Standard Backup Procedure

9.1 Before creating a backup

  1. Confirm the asset identity and the exact target system.
  2. Review the OEM and site-approved backup instructions.
  3. Determine whether the backup operation is online, offline, or requires a controlled stop.
  4. Confirm that the chosen tool supports the device and firmware version.
  5. Identify the intended backup scope and required dependencies.
  6. Verify that the destination is approved, available, and has sufficient capacity.
  7. Confirm access authorization and any required change or work permit.
  8. Record the existing project version and relevant hardware/firmware details.
  9. Identify any machine-specific risks, including potential changes to the running application.
  10. Notify affected personnel if the procedure may affect production or monitoring.

Never assume that uploading or exporting a running controller project is harmless in every environment. Some operations are read-only, while others may involve state changes or require specific operating conditions.

9.2 Create the backup

  1. Connect using the approved engineering tool and communication method.
  2. Confirm the connected device's identity before transferring data.
  3. Retrieve or export the required project, configuration, or data using the supported method.
  4. Capture required parameters and settings that are not included in the main project.
  5. Preserve associated files, libraries, hardware descriptions, and dependencies.
  6. Record any settings that cannot be exported automatically.
  7. Save the backup to the controlled repository using the approved naming convention.
  8. Calculate or verify a checksum when supported and required.
  9. Preserve the original source copy until the new backup has been validated.

9.3 Validate and close the backup activity

  1. Confirm that the expected files exist and have plausible sizes.
  2. Verify that the archive opens or the export can be imported using the supported software.
  3. Check the project identity, version, asset ID, and configuration details.
  4. Compare the saved project with the intended source where the tools support comparison.
  5. Confirm that critical dependencies and separate parameter exports are included.
  6. Record any limitations or unresolved warnings.
  7. Store the secondary copy according to the backup policy.
  8. Update the backup register.
  9. Obtain approval where required.
  10. Schedule a restore test according to the asset's risk and recovery requirements.

A file listing alone is not enough. The archive must be usable for the intended recovery purpose.

10. Backup Naming Convention and Folder Structure

A consistent naming convention prevents technicians from restoring the wrong project to the wrong machine. A filename such as PLC_Final_New_Updated_2 is a cry for help, not a version-control strategy.

10.1 Recommended naming convention

[Plant]_[Area]_[AssetID]_[System]_[Version]_[BackupType]_[YYYYMMDD]

Example:

PUNE_BIW_ST045_PLC_v03_2_FULL_20261018

The exact format should follow the site's document-control standard. Use a clear version identifier and date, and avoid ambiguous labels such as final, latest, or new.

10.2 Example folder structure

    │   ├── ST045
    │   │   ├── PLC
    │   │   │   ├── Approved
    │   │   │   ├── PreChange

    │   │   │   └── RestoreTest
    │   │   ├── HMI
    │   │   ├── VFD

    ├── TEST_BEDS
    ├── CNC
    ├── ROBOTS
    ├── SCADA_SERVERS
    └── BACKUP_REGISTER

10.3 Folder-control rules

  • Separate approved backups from working copies.
  • Preserve pre-change and post-change versions.
  • Restrict write and delete permissions on approved copies.
  • Keep project files, exported parameters, dependency files, and recovery instructions together or linked through the register.
  • Store passwords and secrets only in approved secure systems, not in ordinary filenames or unsecured text files.
  • Do not overwrite the last known-good backup before validating a replacement.
  • Retain obsolete versions according to the applicable retention policy.

11. PLC Backup: Practical Procedure

A PLC backup is especially important because the project may contain control logic, hardware configuration, I/O mapping, communication settings, and technology configuration.

However, the source project on an engineering computer and the program currently running in the PLC may not be identical. The technician must establish which version is actually required.

11.1 What to capture

  • PLC manufacturer, model, catalog number, and serial number where relevant.
  • CPU firmware and project software version.
  • Hardware configuration and module arrangement.
  • PLC program and associated routines, blocks, or program files.
  • I/O mapping and communication configuration.
  • Relevant device configuration and technology objects.
  • Required libraries and hardware-description files.
  • Safety-controller project and required safety documentation, where applicable.
  • Retentive data or values that the approved backup method supports and that are needed for recovery.
  • Password, access, and licensing recovery requirements through approved secure storage.
  • Known differences between the saved engineering project and the running controller.

Safety PLCs require additional controls. A standard logic export may not be sufficient to recover a validated safety application, its signatures, configuration, or associated safety documentation.

11.2 General PLC backup workflow

Identify the correct PLC
        ↓
Verify CPU and firmware details
        ↓
Retrieve the project using the approved method
        ↓
Capture required hardware and device configuration
        ↓
Save project and dependencies
        ↓
Compare and validate the saved version
        ↓
Record differences and limitations
        ↓
Store approved copies securely
        ↓
Update the backup register

11.3 Siemens, Allen-Bradley, and Mitsubishi considerations

Platform Typical engineering environment Backup considerations
Siemens S7-1200/S7-1500 TIA Portal Project version, CPU firmware, hardware configuration, device descriptions, technology objects, protection settings
Allen-Bradley ControlLogix/CompactLogix Studio 5000 Logix Designer Controller type and revision, ACD project, module configuration, electronic keying, add-on instructions, safety-related artifacts
Mitsubishi FX/Q/L/iQ-R GX Works family, depending on series CPU series, project version, parameters, program, device configuration, communication settings

Exact capabilities depend on the controller, firmware, software version, access permissions, and project configuration. A project upload may not reconstruct every original engineering artifact or external dependency.

11.4 Online project versus offline project

  • Online project: The application or configuration currently present in the controller.
  • Offline project: The engineering project saved in the programming environment.

Before using either as the backup source, determine whether it matches the required approved version. Compare online and offline content using supported tools and procedures.

Do not download a saved project merely to make the controller match the file. A download can alter machine behavior and may require a controlled shutdown, change approval, safety review, and post-change validation.

12. HMI, CNC, Robot, and Drive Backups

12.1 HMI backup

Capture the HMI project, screens, tags, alarms, recipes, communication settings, user configuration, and required runtime dependencies where supported.

Verify whether runtime data, user accounts, recipe records, and historical data are included in the export. They may require separate backup procedures.

12.2 CNC backup

CNC systems may contain machine-builder-specific parameters and configuration that are not fully recoverable from the ordinary part-program directory.

Depending on the system, capture:

  • Part programs and subprograms.
  • Machine parameters and configuration.
  • Tool and work offsets.
  • Compensation tables.
  • Custom macros and cycles.
  • Machine-builder data.
  • Servo and spindle configuration where supported.
  • Relevant OEM recovery instructions.

Some machine-specific values are highly sensitive to the machine's mechanical configuration. Never restore a parameter set from a similar-looking machine without confirming compatibility and authorization.

12.3 Robot backup

Capture the robot program, tools, frames, relevant controller configuration, external-axis configuration, and OEM-supported recovery artifacts.

For robot systems, mastering and calibration-related information may be critical. A program backup does not necessarily preserve every datum required to recover accurate physical positioning.

12.4 VFD and servo backup

Capture parameters using the drive manufacturer's supported method. Record:

  • Drive model and firmware.
  • Motor nameplate data.
  • Control mode and command source.
  • Speed, torque, acceleration, and deceleration settings.
  • Feedback configuration and scaling.
  • Communication settings.
  • Protection limits and relevant tuning parameters.
  • Any machine-specific parameters that cannot be exported.

Verify the target drive model and application before restoring parameters. Parameter compatibility is not guaranteed across different models, firmware revisions, or motor and feedback configurations.

13. SCADA, Node-RED, SQL Server, and Grafana Backups

An industrial monitoring system is a collection of dependent components, not one application folder.

13.1 SCADA and Node-RED

For SCADA and Node-RED, consider backing up:

  • Application projects and flow definitions.
  • Tag configuration and communication settings.
  • Required custom nodes, libraries, and package versions.
  • Environment and deployment configuration.
  • Runtime settings and relevant service definitions.
  • Credentials using the platform's supported secure backup method.
  • Certificates and keys, protected according to security policy.
  • Connection details and dependency documentation.
  • Installation packages and compatible runtime versions.

For Node-RED, a copy of the flow definitions alone may not be sufficient. The settings file, installed nodes, credentials, runtime version, and relevant environment configuration may also be needed. Credential data may be encrypted and dependent on a credential secret or key that must be preserved securely through an approved method.

13.2 SQL Server

Database recovery should use SQL Server-supported backup methods and a defined recovery strategy.

Typical considerations include:

  • Full database backups.
  • Differential backups where used.
  • Transaction-log backups where the recovery model supports them.
  • Database recovery model and relevant configuration.
  • SQL Server version and compatibility details.
  • Login, permissions, job, and server-level configuration requirements.
  • Backup verification and periodic restore testing.

A database backup does not automatically include every server-level object or external application configuration. Identify dependencies separately.

13.3 Grafana

Capture dashboards, provisioning files, data-source configuration, alert rules, and other required settings using supported export or backup methods.

Also document:

  • Grafana version.
  • Authentication and authorization configuration.
  • Plugin dependencies.
  • Data-source endpoints.
  • Certificates and relevant secure settings.
  • Whether historical data resides in an external database or time-series platform.

Exporting a dashboard does not back up the database from which its data is obtained.

13.4 Example dependency chain

PLC data source
      ↓
Node-RED or SCADA acquisition
      ↓
SQL Server / historian storage
      ↓
Grafana visualization
      ↓
Operator or maintenance dashboard

Recovery should consider the dependency chain. A dashboard may load successfully while showing stale data because its data source or upstream acquisition service has not recovered.

14. Restore Procedures

Restoration must be treated as a controlled engineering activity because incorrect data can change machine behavior.

14.1 Before restoring

  1. Confirm the failed component and required recovery scope.
  2. Verify the target asset ID, model, firmware, and hardware revision.
  3. Identify the approved backup that matches the target.
  4. Check file integrity and confirm the backup is usable.
  5. Review the backup date and any changes made since it was created.
  6. Identify the existing target configuration and preserve it if safe and practical.
  7. Obtain required work permits, approvals, and change authorization.
  8. Plan the safe machine state and required energy isolation.
  9. Confirm the availability of compatible software, licenses, cables, and recovery tools.
  10. Determine the post-restore validation and acceptance criteria.

14.2 Restore execution

  • Place the equipment in the approved state for the operation.
  • Follow the OEM's restore instructions.
  • Verify the target identity immediately before loading data.
  • Restore the correct backup using the supported method.
  • Avoid mixing files or parameters from incompatible versions.
  • Record any warnings, conversion steps, or differences.
  • Confirm the restore operation completed successfully.
  • Preserve the original backup and the pre-restore state where appropriate.

14.3 Post-restore verification

  • Confirm hardware and software identity.
  • Verify project or configuration version.
  • Check module and device diagnostics.
  • Verify relevant communication links.
  • Confirm required I/O and device status.
  • Verify parameters, scaling, and configuration.
  • Check safety-related functions using the approved validation procedure.
  • Test functions under controlled conditions.
  • Verify process and product quality requirements.
  • Confirm data logging and traceability where applicable.
  • Obtain the required return-to-service authorization.
  • Record the restore activity and outcome.

A successful transfer is not proof of a successful recovery. The final acceptance criteria must include the relevant functional and safety requirements.

15. Restore Testing and Recovery Drills

Restore testing demonstrates that a backup can actually be used for its intended recovery purpose. It is one of the most important parts of backup management.

A backup file that has never been restored is an assumption about recoverability, not proof of recoverability.

15.1 Types of restore tests

Test type Purpose
File integrity check Confirms the stored file is readable and has not unexpectedly changed
Archive validation Confirms the backup archive opens or can be imported
Configuration comparison Checks whether the restored project matches the approved configuration
Test-environment restore Tests recovery without changing the production machine
Functional restore test Confirms that the restored application performs its required functions
Disaster-recovery drill Exercises the complete recovery process, including personnel and dependencies

15.2 Recommended testing approach

  1. Select a representative backup based on asset criticality and risk.
  2. Use a test environment or spare equipment where practical.
  3. Confirm compatibility between the backup and the target.
  4. Restore using the documented procedure.
  5. Verify application integrity, configuration, and dependencies.
  6. Perform the required functional tests.
  7. Record the time taken and any problems encountered.
  8. Correct deficiencies in the backup or recovery procedure.
  9. Update the restore-test record.

For safety PLCs, robots, CNC machines, and other equipment with machine-specific calibration or safety configuration, a test restore must follow the applicable OEM and site requirements. Do not experiment on a production machine simply to prove that a backup works.

16. Recovery Point Objective and Recovery Time Objective

Two important measures help determine backup frequency and recovery readiness.

16.1 Recovery Point Objective (RPO)

RPO is the maximum acceptable period of data loss measured backward from a disruptive event.

For example, if a database has an RPO of 15 minutes, the backup and log-management strategy must support recovery to a point no more than 15 minutes before the event, subject to the database's supported recovery capabilities.

16.2 Recovery Time Objective (RTO)

RTO is the target time within which the required system or service must be restored.

For example, if a critical station has an RTO of two hours, the recovery plan should account for diagnosis, obtaining hardware, restoring software, validating functionality, and completing the required release process.

Requirement Example Design implication
RPO Maximum 15 minutes of acceptable data loss Backup frequency or transaction-log strategy must support the requirement
RTO Restore within two hours Recovery tools, compatible spares, documentation, and trained personnel must be available
Retention Keep approved copies for a defined period Storage capacity and lifecycle controls must support the policy
Validation Prove the restored system is usable Schedule restore tests and document acceptance results

These targets must be established by the business and engineering risk assessment. They are not universal values for every industrial machine.

17. Backup Frequency and Retention

Backup frequency should reflect the rate of change, business impact, and cost of recreating the data.

Event or asset condition Typical backup trigger
Initial machine commissioning Create and validate a baseline backup
Approved PLC or HMI modification Capture pre-change and validated post-change versions
Drive or servo parameter changes Back up the approved parameter set
CNC or robot program modification Save and control the revised program and related data
Industrial PC rebuild Create an approved image after validation
SCADA configuration change Back up the revised application and configuration
Database operation Follow the defined database backup and recovery schedule
Firmware upgrade Create a pre-upgrade recovery point and validate the post-upgrade state
Major machine retrofit Capture affected controller, device, documentation, and configuration baselines
Periodic maintenance review Verify backup currency, accessibility, and restore readiness

17.1 Retention principles

  • Keep the last known-good version until its replacement is validated.
  • Retain pre-change backups long enough to support rollback and investigation.
  • Preserve required records according to company, contractual, quality, and legal requirements.
  • Protect backups from unauthorized deletion.
  • Avoid retaining uncontrolled copies indefinitely when they create security or version-selection risks.
  • Periodically review obsolete versions and dispose of them only under the approved retention process.

18. Backup Security and Industrial Cybersecurity

Backups are valuable targets during ransomware incidents and unauthorized engineering changes. Protecting the backup repository is part of maintaining industrial resilience.

18.1 Required controls

  • Restrict access according to job responsibility.
  • Use individual accounts and appropriate authentication.
  • Separate backup administration from ordinary production-system access where practical.
  • Maintain offline or immutable copies for critical systems.
  • Encrypt sensitive backups where supported and required.
  • Protect encryption keys, credentials, and recovery secrets separately.
  • Log backup creation, access, modification, restore, and deletion activities where supported.
  • Scan imported files according to site cybersecurity procedures.
  • Preserve trusted copies of required installation media and software.
  • Validate restored software and configurations before connecting them to production networks.

18.2 Firmware and software integrity

A backup can faithfully preserve a compromised configuration. Therefore, recovery planning should distinguish between:

  • A known-good approved configuration.
  • A recent backup that may contain an unwanted change.
  • A historical archive retained for investigation.
  • A recovery image that has been validated for the intended hardware.

After a cybersecurity incident, do not blindly restore the most recent copy. Determine the likely compromise window, select a trusted recovery point, verify software integrity, and follow the site's incident-response procedure.

19. Common Backup and Restore Failures

Mistake Risk Better practice
Backing up the wrong PLC Incorrect machine configuration may be restored later Verify asset identity and controller details
Saving only the program Hardware configuration or dependencies may be missing Define and capture the full recovery scope
Keeping one copy on a laptop Loss, damage, or compromise can destroy the only copy Use a controlled repository and independent secondary copy
Overwriting the last good version Rollback capability is lost Preserve validated versions
Never testing restoration Backup may be unusable or incomplete Conduct risk-based restore tests
Ignoring firmware compatibility Restore may fail or produce unexpected behavior Verify target and source compatibility
Forgetting licenses and dependencies Application may not run after recovery Record and protect required dependencies
Backing up live database files by simple copying The resulting data may be inconsistent Use supported database backup methods
Storing passwords in backup filenames Credentials may be exposed Use approved secret-management systems
Restoring parameters from a similar machine Incorrect motion, process, or protection settings Verify exact equipment compatibility
Failing to capture post-change versions Approved improvements may be lost Back up after successful validation
Assuming a dashboard export contains historical data Required history may be missing Back up the actual data store separately
Treating a successful upload as functional proof Machine may still fail after restoration Verify function and required safety performance

20. Practical Example: PLC Replacement on a Production Line

Scenario: A PLC CPU fails, and maintenance must replace it.

Before replacement

  • Identify the failed CPU, catalog number, firmware, and project revision.
  • Locate the latest approved backup and verify its identity.
  • Review the previous backup and change history.
  • Confirm that the backup includes the required hardware configuration and dependencies.
  • Check the replacement CPU's compatibility.
  • Obtain the required maintenance and production authorization.
  • Follow the machine-specific isolation and replacement procedure.

During replacement

  • Install the approved replacement hardware using the applicable procedure.
  • Confirm module placement, wiring, addressing, and hardware compatibility.
  • Restore the approved project using the correct engineering software.
  • Apply required configuration and parameters.
  • Resolve diagnostics using the OEM procedure.
  • Avoid initiating automatic production before verification is complete.

After replacement

  • Verify CPU identity, firmware, project revision, and module status.
  • Check I/O states and communications.
  • Validate required safety functions according to the approved safety procedure.
  • Perform controlled functional tests.
  • Verify sequence behavior and connected device responses.
  • Confirm product and process acceptance criteria.
  • Obtain the required return-to-service approval.
  • Save a validated post-replacement backup.
  • Update the asset record and maintenance work order.

Key lesson: Replacing the CPU is only the hardware task. Recovering the approved application, proving compatibility, validating machine behavior, and documenting the result complete the recovery process.

23. Interview Questions and Answers

Q1. What is the difference between a backup and an archive?

A backup is intended to restore data or a system after a failure. An archive primarily preserves information for historical, compliance, engineering, or traceability purposes. One copy can serve both roles only if it satisfies the requirements of each.

Q2. What is the 3-2-1 backup principle?

Keep at least three copies of important data, on two different storage types, with at least one copy off-site or appropriately isolated.

Q3. Why is a PLC upload not always a complete backup?

The uploaded data may not include the original source project, libraries, comments, external device configurations, all parameters, or every artifact required for a complete recovery.

Q4. Why should a backup be tested?

Testing verifies that the copy is readable, compatible, restorable, and suitable for its intended purpose. A file's existence alone does not prove recoverability.

Q5. What is the difference between RPO and RTO?

RPO specifies the acceptable amount of data loss expressed as a time interval. RTO specifies the target time for restoring the required system or service.

Q6. Why maintain pre-change and post-change backups?

The pre-change copy supports rollback if a modification fails. The validated post-change copy preserves the approved new configuration.

Q7. Can an HMI backup recover the PLC?

Not normally. The HMI and PLC generally have separate applications and configurations. Both require their own appropriate backups unless a documented recovery package explicitly covers both.

Q8. Why is restoring a drive parameter set risky?

Incorrect parameters can produce unexpected motor behavior, incorrect scaling, unsuitable protection settings, or communication problems. Compatibility with the exact drive, motor, feedback, and application must be verified.

Q9. Does a database backup include Grafana dashboards?

Not necessarily. Database content and Grafana configuration are separate recovery scopes and must be backed up according to their respective methods.

Q10. What makes a backup industrially useful?

Correct asset identification, sufficient scope, compatibility, integrity, secure storage, clear restore instructions, validated recovery, and controlled documentation.

24. Final Principles

  • Back up the system that actually exists, not merely the project someone believes is running.
  • Include dependencies and configuration required for recovery.
  • Keep validated versions and protect them from unauthorized changes.
  • Use OEM-supported backup and restore methods.
  • Verify compatibility before restoring any PLC, drive, CNC, robot, or other controller.
  • Protect backup copies against cyber incidents and accidental deletion.
  • Test restoration according to equipment criticality and risk.
  • Define acceptable data loss and recovery time for critical systems.
  • Validate the restored equipment before production release.
  • Maintain records that connect the backup to the correct asset, version, approval, and recovery test.
