1. Purpose and Scope

HMI (Human-Machine Interface) component replacement is the controlled replacement of a failed, damaged, obsolete, or unsuitable operator-interface component while preserving the machine's approved operating functions, communication, alarm visibility, process settings, and required safety controls.

An HMI provides an operator-facing interface to a control system. It may display machine status, alarms, trends, recipes, production information, and operator commands. Depending on the architecture, the HMI may be a dedicated panel, an industrial PC running runtime software, or a client connected to a SCADA server.

HMI replacement can involve:

  • Replacing a complete touchscreen or operator panel.
  • Replacing an HMI display, power supply, communication interface, or other serviceable component.
  • Replacing an industrial PC used as an HMI.
  • Migrating to a successor HMI model.
  • Reinstalling runtime software and restoring the approved project.
  • Reconfiguring communication, user access, recipes, and other supported settings.

Core principle: A replacement HMI must not only power up and display screens. It must communicate with the correct controller, display valid data, issue only the intended commands, preserve required security and operating controls, and pass the applicable functional tests before return to service.

2. What an HMI Does

An HMI provides a visual and interactive layer between the operator and the automation system.

Typical functions include:

  • Displaying machine state and operating mode.
  • Showing PLC tags, sensor values, and actuator status.
  • Presenting alarms and fault messages.
  • Allowing authorized commands and setpoint entry.
  • Displaying process trends and operating history.
  • Managing recipes and production settings.
  • Showing maintenance diagnostics.
  • Providing user authentication and role-based access.
  • Displaying production counts and selected quality information.
  • Supporting manual, automatic, setup, or maintenance operations where designed.

The HMI is not necessarily the device that executes the machine's control logic. In a typical architecture, the PLC performs the control logic while the HMI presents information and sends permitted commands.

Operator
   ↓
HMI panel or industrial PC
   ↓
Industrial communication network
   ↓
PLC or controller
   ↓
I/O modules and field devices

The exact architecture depends on the machine. Some HMIs also communicate with drives, databases, SCADA servers, or other devices.

3. HMI Types and Replacement Considerations

HMI type Description Important replacement considerations
Dedicated operator panel Integrated display, processor, and runtime Panel model, project compatibility, firmware, communication
Touchscreen HMI Operator interface controlled by touch Screen size, touch technology, resolution, calibration
Keypad HMI Interface with physical function keys or keypad Key mapping, panel layout, application compatibility
Industrial PC HMI PC running HMI runtime software Operating system, drivers, licenses, runtime version, image recovery
SCADA client Client application connected to a server Client version, server connection, authentication, graphics
Remote HMI client Interface accessed through a supported remote connection Network configuration, access permissions, session behavior
Obsolete HMI replacement Newer model replacing an unsupported device Migration, screen resolution, fonts, tags, communication drivers
HMI display or serviceable module Repair or replacement of a supported subassembly OEM serviceability, part compatibility, calibration, warranty

Not every HMI supports field-level repair. Many sealed operator panels are designed for replacement as a complete unit. Follow the manufacturer's service instructions rather than opening an assembly that is not intended to be repaired on site.

4. Common HMI Faults and Their Causes

Symptom Possible causes
HMI does not power on Missing supply, faulty power connector, internal power fault, damaged panel
Screen is blank Display or backlight fault, failed startup, incorrect brightness, runtime issue
Touchscreen does not respond Touch hardware fault, calibration issue, damaged surface, software or driver problem
HMI boots but shows no machine data Communication failure, incorrect controller address, driver mismatch, PLC fault
Tags show stale or invalid values Lost connection, incorrect tag mapping, update failure, controller unavailable
Alarm screen is empty Alarm configuration problem, tag mismatch, database issue, incorrect time or filter settings
Recipe data is missing Local data loss, incomplete restore, database or storage failure
HMI restarts repeatedly Unstable supply, overheating, storage or operating-system problem
Application fails to start Runtime incompatibility, missing files, license problem, corrupted project
Screen layout is incorrect Resolution mismatch, model migration issue, font or scaling differences

HMI communicates intermittently Network faults, damaged cable, duplicate address, switch or driver issue

A blank or frozen screen does not automatically prove that the HMI hardware has failed. Diagnose the power supply, operating system, runtime application, network, and PLC status before replacing the panel.

5. Safety and Operational Risks

An HMI replacement can change the way operators interact with the machine. Incorrect screen configuration or tag mapping may cause an operator to see misleading information or issue an unintended command.

5.1 Main risks

  • Loss of operator visibility during the replacement.
  • Incorrect PLC or device connection.
  • Incorrect command-to-tag mapping.
  • Missing or misleading alarms.
  • Wrong recipe or setpoint values.
  • Unauthorized access due to missing user roles or changed authentication.
  • Loss of production history or local data.
  • Unexpected commands during startup or reconnection.
  • Incorrect screen scaling that hides important information.
  • Loss of required safety-related information or control functions.

An ordinary HMI is not a substitute for a certified safety system. Replacing an HMI must not bypass, weaken, or replace safety-rated hardware and logic.

5.2 Required controls

  • Obtain authorization and identify the affected machine.
  • Inform operations and maintenance personnel.
  • Establish the approved machine state before disconnecting the HMI.
  • Follow the applicable energy-isolation procedure for electrical work.
  • Verify the relevant electrical hazards have been controlled.
  • Preserve the approved project and required data.
  • Verify the replacement model and communication compatibility.
  • Prevent unintended commands during startup and testing.
  • Restore access controls and security settings.
  • Validate alarms, commands, interlocks, and relevant operator functions.
  • Obtain return-to-service approval.

An HMI's STOP button or an on-screen machine mode selection is not, by itself, proof of a safe electrical or mechanical condition.

6. Pre-Replacement Identification

Correct identification prevents installation of an incompatible panel or restoration of the wrong project.

6.1 Information to record

  • Plant, area, machine, and asset ID.
  • HMI manufacturer and complete model number.
  • Hardware revision and serial number where relevant.
  • Screen size, resolution, touch type, and mounting dimensions.
  • Supply voltage and current requirements.
  • Communication ports and supported protocols.
  • IP address, subnet, gateway, and device name where applicable.
  • Runtime software and firmware versions.
  • Engineering software version used to create the project.
  • Project name and approved revision.
  • PLC identity and communication path.
  • License and activation requirements.
  • User authentication method and role configuration.
  • Recipe, alarm, and historical-data storage locations.
  • Existing diagnostic messages and observed fault behavior.

6.2 Replacement compatibility matrix

Compatibility factor Verification requirement
Hardware model Exact model or approved successor identified
Supply requirements Voltage, current, connector, and grounding requirements match
Mounting Cutout, dimensions, fixing method, and environmental rating are suitable
Display Resolution, aspect ratio, screen orientation, and readability are acceptable
Touch interface Touch type and supported calibration method are compatible
Runtime software Required runtime is supported on the target panel or PC
Project format Engineering project can be transferred or migrated correctly
Communication Required drivers, protocols, ports, and connection types are supported
Controller interface Correct PLC or device is identified
Licensing Runtime and engineering licenses are available and valid
Data storage Required recipes, logs, and configuration can be recovered

A physically compatible replacement may still be functionally incompatible. For example, a newer panel may use a different runtime version, communication driver, or screen resolution.

7. Backup and Data Preservation

Before replacing an HMI, determine what information must be retained and where it is stored. The HMI project is only one part of the recovery scope.

7.1 Items to preserve

Item Purpose
HMI engineering project Preserves screens, navigation, tags, and application configuration
Runtime application Supports deployment to the replacement panel where required
Firmware and runtime versions Helps establish compatibility
Communication configuration Preserves controller addresses, drivers, and connection settings
Alarm configuration Preserves alarm definitions, priorities, and display behavior
Recipe configuration and data Preserves approved process settings and stored recipes
User and role configuration Preserves authorized access and operator permissions
Scripts and custom components Preserves application dependencies
Fonts and graphics Prevents missing or incorrectly displayed interface elements
Historical data configuration Preserves logging, retention, and data-source settings
License and activation information Supports authorized runtime operation
Certificates and security settings Supports secure communications where used
PC system image Supports recovery of an industrial PC with complex dependencies
Backup and restore instructions Enables repeatable recovery

7.2 Understand where the data resides

HMI-related information may be stored in different locations:

  • Engineering workstation.
  • HMI internal flash or other local storage.
  • Removable memory card or USB storage, where supported.
  • PLC or controller memory.
  • SCADA server.
  • SQL database or historian.
  • Network file server.
  • External recipe or production-management system.

Replacing the HMI does not automatically recover data held in the PLC, a database, or a remote server.

7.3 Backup validation

Before proceeding, verify that:

  1. The backup belongs to the correct machine and HMI.
  2. The project can be opened or imported using the supported engineering software.
  3. Required runtime versions and dependencies are available.
  4. Recipes, scripts, and other required data are accounted for.
  5. Communication configuration is documented.
  6. User access and licensing requirements are understood.
  7. The recovery procedure is available and appropriate for the replacement model.

A project archive may contain the engineering application but not live historical records, current recipe data, passwords, certificates, or other separately stored information.

8. Standard HMI Replacement Procedure

The following is a general procedure. Apply the exact OEM instructions and site-approved SOP for the equipment being serviced.

8.1 Phase A: Prepare

  1. Confirm the reported fault and diagnose whether the issue is hardware, software, communication, or power-related.
  2. Identify the HMI and the proposed replacement model.
  3. Verify compatibility with the PLC, engineering project, runtime, and communication method.
  4. Back up the required project and separately stored data.
  5. Record the existing communication settings and configuration.
  6. Confirm the availability of the engineering software, licenses, cables, and recovery tools.
  7. Obtain the required maintenance and production approvals.
  8. Establish the approved machine state and electrical isolation requirements.
  9. Prepare suitable tools, labels, ESD controls, and the replacement hardware.

8.2 Phase B: Record the existing installation

Before disconnecting anything:

  • Photograph the panel and connections where permitted.
  • Record the panel orientation and mounting arrangement.
  • Identify each communication cable and connector.
  • Record the power supply and grounding connections.
  • Record the IP address and device name where applicable.
  • Record the PLC or server to which the HMI connects.
  • Capture diagnostic messages and the existing fault condition.
  • Note any external memory devices and connected peripherals.

Photographs are supporting evidence, not a substitute for approved electrical drawings and connector identification.

8.3 Phase C: Remove the faulty HMI

  1. Confirm the required safe state and isolation.
  2. Verify the correct panel before disconnecting it.
  3. Follow the OEM instructions for removing the panel.
  4. Disconnect power and communication cables using the approved method.
  5. Label and secure cables to prevent damage or misconnection.
  6. Remove mounting hardware without damaging the panel cutout or enclosure.
  7. Protect exposed connectors against contamination.
  8. Inspect the panel, mounting area, wiring, and connectors for damage.
  9. Record the removed component's identity and condition.

Do not assume that the panel's power connector is isolated simply because the screen is blank.

8.4 Phase D: Install the replacement HMI

  1. Verify the replacement model and its electrical requirements.
  2. Inspect the replacement for transport damage.
  3. Confirm mounting dimensions, sealing, and environmental suitability.
  4. Install the panel according to the OEM instructions.
  5. Reconnect the correct power and communication connections.
  6. Verify polarity, grounding, connector seating, and cable routing.
  7. Confirm that the enclosure sealing and mounting are restored.
  8. Check that no wires are trapped or strained.
  9. Verify the installation against the approved drawings.
  10. Complete the required inspection before restoring power.

Incorrect mounting or poor sealing can allow contamination or moisture to enter the enclosure even when the replacement HMI itself has a suitable environmental rating.

8.5 Phase E: Configure and restore the application

  1. Verify the panel model, firmware, and runtime compatibility.
  2. Apply the approved configuration using the manufacturer's method.
  3. Install or restore the correct runtime application.
  4. Restore the approved project and required dependencies.
  5. Configure the intended communication settings.
  6. Verify the PLC or server identity.
  7. Restore required recipes and local settings using the approved method.
  8. Configure user authentication, permissions, and security settings.
  9. Confirm that licensing and activation are valid.
  10. Review startup messages and diagnostic status.

Do not transfer a project blindly from an older panel to a newer one. Project migration may require changes to screen layout, tags, scripts, drivers, or runtime settings.

8.6 Phase F: Test and release

  1. Confirm normal HMI startup.
  2. Verify communication with the correct controller.
  3. Check representative tags and process values.
  4. Validate alarm display and acknowledgment behavior.
  5. Test navigation, buttons, setpoint entry, and permitted commands.
  6. Verify recipes and required data storage.
  7. Check user roles and access restrictions.
  8. Confirm relevant interlocks and machine-mode behavior.
  9. Validate the affected process functions under controlled conditions.
  10. Obtain return-to-service approval.
  11. Update the maintenance record and backup register.

9. Project Download, Upload, and Migration

HMI engineering tools commonly support project transfer, but the exact capabilities depend on the manufacturer, model, runtime, and protection settings.

9.1 Engineering project versus runtime application

Item Meaning
Engineering project Editable application used to design and configure the HMI
Runtime application Deployed application executed on the panel or PC
Project upload Retrieving supported project data from a device
Project download Transferring an application or configuration to a device
Project migration Converting a project to a different panel model, runtime, or software version
Runtime update Updating the software environment that executes the application

A runtime application may not contain all original engineering source files, comments, reusable objects, or editable design information. Uploading from an existing panel may therefore fail to reconstruct the original engineering project.

9.2 Migration risks

When replacing an obsolete HMI with a successor model, assess:

  • Screen resolution and aspect ratio.
  • Font availability and text rendering.
  • Touch target size and placement.
  • Navigation and screen transitions.
  • Tag addressing and data types.
  • Communication drivers and protocols.
  • Scripts, macros, and custom controls.
  • Alarm and event configuration.
  • Recipe structures and storage locations.
  • User-management features.
  • Runtime performance and memory limits.
  • Licensing and operating-system requirements.

A project that compiles successfully can still have functional problems on the new panel. Migration is not complete until the application has been tested on the target hardware or an appropriately representative environment.

10. Communication and PLC Integration

An HMI can operate locally while failing to exchange data with the PLC. The panel's startup status and its communication status must be checked separately.

10.1 Communication parameters

Verify the settings relevant to the selected protocol:

  • HMI IP address.
  • Subnet mask and gateway.
  • PLC IP address or node identity.
  • Device name where required.
  • Protocol and communication driver.
  • Port and connection configuration where applicable.
  • PLC connection path or routing information.
  • Network switch port and VLAN configuration.
  • Redundancy or failover configuration where used.
  • Security credentials and certificates where required.

10.2 Common communication faults

Symptom Possible cause Check
HMI cannot connect to PLC Incorrect address or cable issue Verify addressing, link status, and physical connections
Intermittent communication Network congestion, cabling, switch, or device issue Review network diagnostics and error counters
Correct network link but no data Wrong driver, protocol, or connection path Verify the HMI communication configuration
Some tags work but others fail Incorrect tag addresses or access permissions Compare affected tags with the approved PLC project
Duplicate address warning Two devices use the same network identity Verify the network address allocation and active devices
Data appears stale Connection loss or stalled updates Verify timestamps, quality indicators, and communication status
HMI connects to the wrong controller Incorrect target address or routing Confirm the actual controller identity before enabling commands

Network reachability alone does not prove that the correct PLC is connected or that application data is valid.

10.3 Data validation

After communication is restored, verify several representative values:

  • Digital status signals.
  • Analog process values.
  • Machine operating mode.
  • Fault and alarm indicators.
  • Production counters where applicable.
  • Setpoints and permitted command states.

Compare displayed values with the PLC's actual data and relevant field indications. Verify scaling, data types, signedness, units, and update behavior where applicable.

11. HMI Alarms, Recipes, and User Access

11.1 Alarms

Verify:

  • Alarm tag mapping.
  • Alarm descriptions and priorities.
  • Active, cleared, and acknowledged states.
  • Alarm timestamps and time synchronization.
  • Audible or visual indications where used.
  • Alarm history and retention.
  • Filtering and display behavior.
  • Required operator response instructions.

A missing alarm can be more serious than a visible communication error because it may hide a fault from the operator.

11.2 Recipes and setpoints

Recipes and process settings can affect product quality and equipment behavior. After replacement:

  • Verify the approved recipe structure.
  • Confirm that required recipe records are present.
  • Compare critical values with the approved baseline.
  • Check units, ranges, and validation limits.
  • Confirm that recipe selection and transfer behavior are correct.
  • Verify that only authorized users can modify protected settings.
  • Confirm that the HMI and PLC agree on the intended active values.

Do not assume that recipe data was included in the HMI project backup. It may be stored separately.

11.3 User access and security

Restore the required access-control configuration:

  • User accounts or approved authentication integration.
  • User roles and permissions.
  • Password policies where applicable.
  • Session timeout and lock behavior.
  • Remote-access permissions.
  • Certificates and secure communication settings where used.
  • Audit logging or operator-action records where required.

Avoid default or shared credentials unless explicitly permitted by the site's approved design. Do not disable authentication merely to make the replacement easier to commission.

12. HMI-Specific Replacement Scenarios

12.1 Replacing a dedicated operator panel

Main concerns include model compatibility, screen resolution, runtime support, project transfer, network configuration, and recipe recovery.

The replacement may require a project conversion even when the new panel belongs to the same product family.

12.2 Replacing an industrial PC

An industrial PC may host several components beyond the HMI runtime, including drivers, Windows services, databases, communication middleware, and data-collection applications.

Before replacement, document:

  • Operating system and version.
  • Hardware architecture and storage requirements.
  • HMI runtime and engineering software dependencies.
  • Communication drivers.
  • Network adapters and addressing.
  • Installed services and scheduled tasks.
  • Licensing and activation.
  • Certificates and secure settings.
  • Application configuration and data locations.
  • Required system image and recovery media.

After installation, verify startup behavior, system time, network configuration, application services, storage health, and communications with the PLC and other systems.

12.3 Replacing an obsolete HMI

Obsolescence may require a migration project rather than a direct swap.

Engineering should identify the successor panel, supported software version, project-conversion method, mounting requirements, communication compatibility, and required acceptance tests.

If the replacement changes the interface layout or operator workflow, update the relevant work instructions and training material.

12.4 Replacing a touch display or other serviceable part

First confirm that the manufacturer permits field-level repair. Replacing a display or touch assembly may require specific parts, calibration, seals, firmware procedures, or specialist service.

If the OEM treats the HMI as a sealed unit, replace the complete approved assembly rather than attempting an undocumented repair.

13. Troubleshooting After HMI Replacement

Symptom Possible cause Diagnostic approach
No power Supply, connector, fuse, or internal hardware fault Verify the supply and connections using the approved method
Panel boots but application is absent Runtime or project not installed Check the runtime deployment and startup configuration
Application opens with missing graphics Incomplete project or dependency files Compare the restored project with the approved source
PLC connection fails Incorrect address, driver, or protocol Verify communication configuration and controller identity
Incorrect values displayed Wrong tags, data types, scaling, or stale data Compare the displayed values with the PLC and approved tag mapping
Touch input is inaccurate Calibration, hardware, or screen configuration issue Follow the OEM touch calibration and diagnostic procedure
Alarms do not appear Alarm configuration or tag mapping problem Check alarm definitions, source tags, and runtime diagnostics
Recipes are missing Local storage was not restored Check the approved recipe source and recovery procedure
Login fails User settings or authentication configuration missing Verify approved account and role configuration
Panel restarts repeatedly Supply instability, overheating, storage, or software issue Review system diagnostics and environmental conditions
New panel shows a different layout Resolution or migration issue Verify display settings, scaling, and migrated graphics
HMI sends unexpected commands Wrong tag mapping, retained state, or startup behavior Stop affected operation safely and investigate before production release

Troubleshooting discipline

  1. Record the symptom and diagnostic evidence.
  2. Confirm the exact HMI and PLC identities.
  3. Separate hardware, runtime, communication, and project problems.
  4. Compare the restored configuration with the approved baseline.
  5. Check the affected tags, alarms, recipes, and user roles.
  6. Investigate external dependencies such as network switches and servers.
  7. Correct the root cause and repeat the affected validation tests.
  8. Document any unresolved issue and restrict operation as required by the risk assessment.

14. Functional Validation and Acceptance

Validation should be proportional to the replacement scope. A display repair may require a different test set from a complete HMI migration.

14.1 Hardware and startup checks

  • Correct model and revision installed.
  • Mounting, sealing, and electrical connections verified.
  • Panel starts without unexpected diagnostics.
  • Runtime application launches correctly.
  • Display resolution and touch operation are acceptable.
  • Required network links are active.
  • Correct PLC or server identity is confirmed.

14.2 Application checks

  • Main screens and navigation operate correctly.
  • Representative tags display correct values.
  • Digital states and analog scaling are verified.
  • Alarms appear, clear, and acknowledge correctly.
  • Recipes and critical setpoints match approved values.
  • Operator commands map to the intended functions.
  • User roles and protected settings behave correctly.
  • Historical data and reports operate where required.
  • Date, time, and timestamps are correct.
  • Communication-loss indications behave as intended.

14.3 Machine and production checks

  • Required interlocks and permissives are respected.
  • Manual and automatic operating functions are validated as applicable.
  • Startup and reconnection behavior are acceptable.
  • Relevant safety functions are validated through approved procedures.
  • Product quality and process acceptance criteria are met.
  • Operations personnel confirm the interface is usable.
  • Required return-to-service authorization is recorded.

Testing must not create hazardous motion or unintended outputs. Conduct command and sequence testing under the machine-specific approved conditions.

15. Documentation and Change Control

Every HMI replacement should leave a traceable record of the removed hardware, replacement hardware, software state, tests, and approval.

15.1 Minimum replacement record

Fault description Reported symptom and diagnostic evidence
Removed HMI Manufacturer, model, revision, and serial number where available
Replacement HMI Manufacturer, model, revision, and serial number where available
Project version Approved application revision
Runtime and firmware Installed software versions
Communication settings Approved device identity and relevant network configuration
Backup reference Project and data backup identifiers
Changes made Project conversion, configuration changes, or other modifications

Final status Returned to service, restricted operation, or pending work

Follow-up actions Documentation, training, spare stock, or additional investigation

15.2 Change-control requirements

A replacement may require formal change control when it involves:

  • A different HMI model or hardware platform.
  • A new runtime or firmware version.
  • Project conversion or screen redesign.
  • Changed communication drivers or protocols.
  • Changes to tag mapping or command behavior.
  • Changes to alarm configuration.
  • Changes to access control or security.
  • Changes to recipe structures or process limits.
  • Changes to the operator workflow.

Record the approved baseline, the reason for change, the new version, the validation evidence, and the rollback method.

16. Common Mistakes to Avoid

  • Replacing the HMI without diagnosing the original fault.
  • Assuming a working display means the PLC communication is healthy.
  • Installing an incompatible panel because it fits the same cutout.
  • Assuming the HMI project includes recipes and historical data.
  • Restoring an incomplete project without checking dependencies.
  • Ignoring runtime licensing or firmware requirements.
  • Copying network settings without confirming the intended controller.
  • Failing to restore user roles and security settings.
  • Assuming a migrated project will display correctly on a different resolution.
  • Testing operator commands without controlling machine risk.
  • Returning the machine to production before checking alarms and tags.
  • Failing to update the project backup, asset record, or operator instructions.

17. Practical Example: Replacing an HMI on a PLC-Controlled Test Bed

Scenario: The operator panel powers on intermittently and eventually becomes unusable. The PLC continues to run, but operators lose normal visibility and control through the HMI.

Step 1: Diagnose the fault

  • Check the HMI supply and connectors using the approved safe method.
  • Review the panel's diagnostic messages.
  • Determine whether the fault is caused by supply instability, hardware failure, runtime corruption, or communication loss.
  • Confirm whether the PLC and process remain in an acceptable state.
  • Determine whether the HMI can be safely removed while preserving required machine control.

Step 2: Prepare the replacement

  • Record the original panel model and configuration.
  • Verify the approved replacement model.
  • Back up the engineering project and required data.
  • Record the PLC address, HMI address, and communication driver.
  • Confirm the required software, licenses, and runtime.
  • Obtain the necessary maintenance and production approvals.

Step 3: Replace and configure

  • Apply the approved safe-state and isolation procedure.
  • Remove the faulty panel and label its connections.
  • Install the compatible replacement.
  • Restore the approved application.
  • Configure the correct network identity and controller connection.
  • Restore the required user settings and recipe data.

Step 4: Validate

  • Confirm normal startup and correct PLC communication.
  • Compare displayed values with actual PLC data.
  • Check test-bed status, alarms, and measurement values.
  • Verify setpoint entry and permitted operator commands.
  • Confirm that test recipes and acceptance limits match the approved version.
  • Validate the required test sequence under controlled conditions.
  • Confirm data logging and traceability where applicable.
  • Obtain return-to-service approval.

Step 5: Close the maintenance activity

  • Record the removed and installed panel.
  • Record the project and runtime versions.
  • Document test results and any configuration changes.
  • Update the approved backup and asset records.
  • Record the root cause and follow-up actions.

Key lesson: On a test bed, an HMI can display plausible values while using incorrect tags or scaling. Verify the displayed measurements and test parameters against the approved source before trusting the interface for product acceptance.

18. Key Performance Indicators

KPI Purpose
HMI-related downtime Measures production interruption associated with HMI failures
Mean Time to Repair (MTTR) Measures repair duration using the site's defined measurement method
Repeat HMI failure rate Identifies recurring hardware, software, or environmental issues
First-time fix rate Measures repairs completed successfully without repeat intervention
Backup availability Measures whether required HMI projects and data are accessible
Restore-test success rate Measures successful restoration against defined acceptance criteria
Migration defect rate Tracks defects discovered after an HMI model or software migration
Documentation compliance Measures completeness of required replacement and change records

KPIs are useful only when definitions remain consistent. For example, MTTR may include diagnosis, waiting time, configuration, testing, and production release, or may measure active repair time only.

19. Interview Questions and Answers

Q1. What is the difference between an HMI and a PLC?

The PLC executes control logic and manages machine inputs and outputs. The HMI provides the operator interface for viewing information and issuing permitted commands.

Q2. What should be backed up before HMI replacement?

The approved engineering project, required runtime configuration, communication settings, recipes, user settings, dependencies, licenses, and any separate data needed for recovery.

Q3. Why might a new HMI display incorrect values even when communication is working?

Possible causes include incorrect tag mapping, data types, scaling, engineering units, stale data, or connection to the wrong controller.

Q4. Why is an HMI upload not always a complete engineering backup?

The device may contain only the deployed runtime application or a limited export, not the original editable project, reusable objects, comments, or all dependencies.

Q5. What is the main risk of HMI project migration?

The project may not behave identically on the new panel because of changes in runtime, screen resolution, communication drivers, scripts, tags, or hardware capabilities.

Q6. Why must alarms be tested after replacement?

Incorrect or missing alarms can prevent operators from recognizing faults and responding appropriately.

Q7. Does replacing an HMI require a PLC program download?

Not normally. An HMI replacement generally requires restoring and configuring the HMI application. A PLC download should occur only when a separately justified, approved engineering change requires it.

Q8. Why should user roles be validated?

The replacement must preserve the intended permissions for operators, maintenance personnel, and engineering staff. Missing or excessive privileges can create operational and security risks.

Q9. What should be checked if an HMI connects but shows stale values?

Verify the correct controller identity, communication diagnostics, tag quality or timestamps, data-update behavior, and any intermediate communication services.

Q10. When is HMI replacement complete?

When the approved hardware and application are installed, communications and data are correct, required operator functions and security controls are validated, records are complete, and the required authority approves return to service.

20. Final HMI Replacement Checklist

  • Fault diagnosed and replacement justified.
  • Correct replacement model and compatibility confirmed.
  • Project and required data backed up.
  • Existing connections and settings documented.
  • Safe-state and electrical isolation requirements satisfied.
  • HMI installed and sealed according to OEM instructions.
  • Runtime, project, drivers, and licenses verified.
  • Correct PLC or server connection confirmed.
  • Tags, alarms, recipes, and setpoints validated.
  • User access and security settings verified.
  • Required functional, safety, and quality tests completed.
  • Return-to-service authorization obtained.
  • Backup, asset history, and maintenance records updated.
  • Root cause and follow-up actions documented.
