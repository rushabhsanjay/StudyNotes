1. Definition and Purpose

A robot program is a set of instructions that controls an industrial robot's movement, tool operation, sequence logic, and interaction with other machines to perform a defined manufacturing task.

In site execution and commissioning, robot programming involves more than creating a path. It includes loading the approved program, configuring motion and tool data, validating coordinate frames, integrating PLC handshakes, checking interlocks, performing controlled dry runs, and confirming the production cycle.

Typical applications include:

  • Robotic welding, sealing, painting, and adhesive dispensing.
  • Material handling, pick-and-place, and palletizing.
  • Machine tending for CNC machines and test equipment.
  • Assembly, fastening, and inspection.
  • Transfer operations between conveyors, fixtures, and stations.

A robot may have valid motion instructions but still fail to complete its task because the tool frame, workpiece frame, external axis, PLC handshake, or peripheral equipment is incorrectly configured.

2. Robot Program Versus Robot Configuration

These terms are related but not interchangeable.

Item Robot program Robot configuration
Primary purpose Defines the task and sequence Defines the controller and robot operating environment
Typical contents Motion instructions, waits, calls, process commands Tool data, frames, motion limits, I/O mapping
Example Move to a weld point and execute welding Define the weld gun tool-center point
Typical failure Incorrect sequence or target Incorrect frame, mastering, or system setup
Verification Program logic and cycle testing Configuration checks and calibration verification

Robot commissioning often requires both program-level and configuration-level checks.

3. Robot Control Architecture

A typical industrial robot cell contains the following elements.

Robot Engineering Software
        ↓
Robot Controller and Robot Program
        ↓
Motion Planner and Servo Control
        ↓
Robot Arms, Axes and End-of-Arm Tooling
        ↕
Robot I/O and Industrial Communication
        ↕
Cell PLC, Safety System and Peripheral Equipment
        ↓
Production Sequence and Quality Verification

The robot controller manages robot motion and program execution. The PLC coordinates the robot with the cell, including conveyors, fixtures, clamps, CNC machines, and other robots.

The safety system manages designated safety functions independently of ordinary production sequencing. Standard program instructions and ordinary PLC bits must not be treated as substitutes for validated safety functions.

4. Robot Program Structure

The exact structure depends on the manufacturer and programming language, but a production program commonly contains:

  • Program initialization.
  • Tool and coordinate-frame selection.
  • Robot status and process readiness checks.
  • Movement to a safe or approach position.
  • Movement to the process or pick position.
  • Tool or process operation.
  • Confirmation of successful completion.
  • Movement to the next target or exit position.
  • Communication with the cell PLC.
  • Error handling and recovery logic.
  • Completion status and return to the appropriate program state.

A simplified sequence is:

Start
  ↓
Check robot and cell readiness
  ↓
Select tool and coordinate frame
  ↓
Move to approach position
  ↓
Move to process position
  ↓
Execute operation
  ↓
Verify operation completion
  ↓
Move to exit position
  ↓
Send completion status to PLC
  ↓
Return or continue the cycle

This is a logical example, not a universal program template. Real sequences must follow the machine builder's validated design.

Programming features vary with controller generation, installed options, and software version. Never assume a program written for one controller can be transferred directly to another.

6. Robot Motion Types

Robot programs typically use joint motion, linear motion, and circular motion. The available commands and their precise behavior depend on the controller.

6.1 Joint motion

Joint motion moves the robot's axes toward a target joint configuration. The TCP generally follows a curved path through space.

Typical uses include:

  • Moving between stations.
  • Approaching a work area.
  • Moving to a home or park position.
  • Performing transitions where a straight TCP path is unnecessary.

6.2 Linear motion

Linear motion attempts to move the tool center point along a straight Cartesian path between specified positions, subject to the controller's motion-planning constraints.

Typical uses include:

  • Insertion and extraction.
  • Welding or dispensing paths.
  • Approaching fixtures.
  • Moving tools through restricted spaces.

The robot's joints may move simultaneously in complex ways to maintain the required TCP path.

6.3 Circular motion

Circular motion follows a defined circular or arc path using the controller's required target points and motion definitions.

Typical uses include:

  • Curved welding paths.
  • Circular dispensing.
  • Arc-shaped finishing operations.
Motion type TCP path Typical application Main consideration
Joint Generally curved Transit movement Robot configuration and clearance
Linear Straight Cartesian path Insertion or process movement Singularities, speed and clearance
Circular Circular arc Curved process path Arc geometry and valid target points

The selected motion type must be appropriate for the process and the physical geometry of the cell.

7. Robot Targets and Position Data

A robot target describes a desired position and, where applicable, orientation or joint configuration.

Depending on the controller, target data may contain:

  • Cartesian position coordinates.
  • Tool orientation.
  • Joint angles or a robot configuration identifier.
  • External-axis positions.
  • Coordinate-frame references.
  • Additional motion attributes.

For a Cartesian target, the position is commonly expressed using three translational coordinates and three orientation parameters. The specific orientation convention differs between controllers.

A robot can sometimes reach the same Cartesian position using different joint configurations. These alternatives may produce different elbow positions, wrist orientations, clearances, and singularity risks.

Practical rule: Do not verify a target using only its displayed XYZ coordinates. Also verify orientation, robot configuration, tool, workpiece frame, external axes, and the complete path to the target.

8. Tool Center Point and Tool Data

The Tool Center Point (TCP) is the defined reference point of the robot's tool. It may represent a welding-wire tip, gripper center, dispensing nozzle, or another process-specific point.

TCP configuration describes the position and orientation of this reference relative to the robot flange or another defined tool reference.

Examples include:

  • Welding gun TCP.
  • Gripper TCP.
  • Adhesive nozzle TCP.
  • Inspection sensor TCP.
  • Machine-loading tool TCP.

If the TCP is incorrect, the robot may reach the expected flange position while the actual tool tip misses the workpiece.

Common TCP problems

Symptom Possible cause Verification
Tool misses the target Incorrect TCP translation Check approved tool-calibration data
Tool orientation is incorrect Incorrect TCP orientation Verify the tool coordinate definition
Paths shift after tool replacement Wrong tool data selected Verify tool assignment and tool identity
Accuracy varies with robot posture Calibration, mechanical, or load-related issue Perform the approved accuracy and calibration checks
Program works with one tool but not another Tool data or tool-specific process configuration mismatch Compare the tool definitions and program selections

Tool calibration must follow the controller manufacturer's procedure. Do not compensate for an incorrect TCP by casually moving every program target.

9. Work Objects and Coordinate Frames

A robot commonly operates using several coordinate systems.

  • World frame: A reference coordinate system for the robot or cell.
  • Base frame: A reference associated with the robot base.
  • Tool frame: A reference associated with the defined tool and TCP.
  • Workpiece or user frame: A reference associated with the fixture, component, or work area.
  • External-axis frame: A reference used when additional coordinated axes are present.

Names and exact relationships differ between robot platforms.

Coordinate transformations relate a point represented in one frame to another. In general form:

\[ {}^{A}T\_{B} \]

represents the transformation from frame B to frame A under the adopted convention.

For a homogeneous transformation, the matrix contains rotation and translation information:

\[ T = \begin{bmatrix} R & p \\\ 0 & 1 \end{bmatrix} \]

Here, \(R\) is a \(3 \times 3\) rotation matrix and \(p\) is a three-dimensional translation vector.

Incorrect frame selection can shift or rotate an entire trajectory. This is why a robot program that worked before fixture maintenance may no longer reach the intended process locations.

10. Speed, Acceleration and Blending

Robot motion parameters influence cycle time, accuracy, vibration, and equipment life.

10.1 Speed

Speed may be specified in different forms depending on the controller and motion type. Joint speed and TCP speed are not interchangeable.

For process paths, TCP speed often affects the quality of welding, dispensing, painting, or other continuous operations.

10.2 Acceleration and deceleration

Acceleration determines how quickly the robot changes velocity. Excessive acceleration can produce vibration, increase mechanical loading, destabilize the tool or workpiece, and affect process quality.

The acceptable settings depend on robot payload, center of gravity, tool geometry, posture, and the process requirements.

10.3 Blending and corner transitions

Blending allows the controller to transition between consecutive targets without necessarily stopping exactly at every intermediate point.

Motion behavior Effect Typical use
Exact stop Robot reaches the programmed target before proceeding Accurate placement or process transition
Blended transition Robot rounds or smooths the transition within permitted constraints Faster transit movement
Reduced process speed Lowers movement speed in a designated process region Process quality or controlled approach
Fine positioning Uses the controller's specified precise endpoint behavior Final positioning or insertion

Blending must not compromise process requirements or clearance. A transition that is acceptable for a free-space transit path may be unacceptable for welding, insertion, or fixture engagement.

11. Payload and Center of Gravity

Robot payload data describes the load carried by the robot, including the tool and applicable carried components.

Important information includes:

  • Total payload mass.
  • Center of gravity relative to the specified reference.
  • Inertia values where required.
  • Tool and workpiece mass, as applicable.
  • External-axis or application-specific load information.

Incorrect payload data can degrade motion performance and may cause overloads, vibration, or reduced accuracy.

For example, a gripper carrying a heavy component has a different effective load from the same gripper operating empty. Some applications therefore require load data to be selected or managed according to the process state.

Use the manufacturer's approved payload-identification and configuration procedure. Do not enter approximate values merely to clear an overload warning.

12. Robot I/O and PLC Handshake

Robot I/O connects the robot controller to cell-level logic and peripheral equipment.

Typical signals include:

  • Robot ready.
  • Robot running.
  • Robot fault.
  • Cycle start request.
  • Cycle complete.
  • Gripper open and closed.
  • Part present.
  • Fixture clamped and unclamped.
  • Weld or dispensing process ready.
  • CNC ready or cycle complete.
  • Robot program number or program selection status.

A simplified request-and-acknowledgement sequence is:

PLC verifies cell permissives
        ↓
PLC sends robot start request
        ↓
Robot validates its own start conditions
        ↓
Robot executes the assigned program
        ↓
Robot verifies the operation result
        ↓
Robot sends cycle-complete status
        ↓
PLC verifies completion and advances the sequence

The handshake must define signal ownership, signal polarity, timeout behavior, reset behavior, and recovery from interrupted cycles.

Example: CNC machine tending

Step PLC or CNC condition Robot action
1 CNC reports ready for loading Confirm robot and cell readiness
2 Fixture and access conditions are valid Move to the approved approach position
3 Loading access is permitted Load the component
4 Part position is verified Signal loading completion
5 CNC confirms clamp and readiness Leave the machine work area
6 Robot is outside the required zone Confirm robot clear
7 CNC cycle completes Wait for the next permitted request

Actual signals and interlocks depend on the cell design. Robot clearance must be confirmed using the approved machine interface and safety architecture.

13. Program Selection and Execution

Robot programs may be started from the teach pendant, controller interface, PLC, or a supervisory system, depending on the application.

Before enabling automatic execution, verify:

  • Correct robot program and revision.
  • Correct tool and workpiece frame.
  • Correct payload and applicable load data.
  • Correct external-axis and peripheral configuration.
  • Valid program start position.
  • Required PLC permissives and process-ready conditions.
  • No unresolved controller or drive faults.
  • Correct operating mode and safety conditions.
  • Expected program-end and recovery behavior.

A program can start at a valid instruction yet fail because the robot is not at the expected physical position or because a required initialization routine has not run.

Program selection and start logic must follow the robot manufacturer's and machine builder's approved procedure.

14. Program Loading, Backup and Version Control

Robot programs and their associated data must be managed as controlled engineering assets.

A program package may include:

  • Main program.
  • Subprograms and reusable routines.
  • Position or target data.
  • Tool and workpiece frame data.
  • Process parameters.
  • Robot configuration or system files where relevant.
  • PLC interface documentation.
  • Applicable external-axis and peripheral configuration.
  • Revision history and commissioning test records.

Before loading a program, check controller compatibility, required dependencies, target-data consistency, and whether the program references files or routines that are absent.

After loading, verify the program identity and revision on the controller. Do not assume that the file selected on the engineering computer is the file currently executing on the robot.

A practical change record includes the previous revision, new revision, reason for change, affected targets or routines, approval, test results, and recovery backup.

15. Offline Programming and Simulation

Offline programming creates or modifies robot programs using a virtual representation of the robot and work cell.

Potential benefits include:

  • Reduced commissioning time.
  • Early detection of reach and clearance problems.
  • Cycle-time estimation.
  • Program development before the physical cell is available.
  • Improved planning for tooling and fixture access.

However, simulation depends on the accuracy of the virtual model.

Common differences between simulation and the real cell include:

  • Incorrect fixture or robot-base coordinates.
  • Inaccurate TCP or payload data.
  • Missing cables, hoses, clamps, and nearby equipment.
  • Incorrect external-axis configuration.
  • Differences in controller software or motion behavior.
  • Mechanical tolerances and real-world deflection.
  • Unmodeled process timing and peripheral delays.

Offline simulation is a useful verification stage, not proof that a robot program is safe or production-ready.

16. Robot Program Commissioning Procedure

Preparation

  1. Identify the robot manufacturer, controller, software version, and cell.
  2. Collect approved drawings, robot programs, target data, and interface documents.
  3. Confirm the robot program revision and its dependencies.
  4. Back up the existing program and associated configuration.
  5. Verify the tool, workpiece frame, payload, and external-axis definitions.
  6. Review the risk assessment and commissioning procedure.

Initial validation

  1. Check controller diagnostics and unresolved faults.
  2. Verify the required I/O states and communication with the PLC.
  3. Confirm that the robot's actual position and program start conditions are valid.
  4. Validate the tool and workpiece coordinate definitions.
  5. Review target reachability, orientation, and robot configuration.
  6. Confirm the approved test mode and required protective measures.

Controlled execution

  1. Follow the machine builder's approved initial-movement procedure.
  2. Validate the path under the prescribed reduced-risk conditions.
  3. Check clearances, approach directions, and tool orientation.
  4. Test process outputs and peripheral handshakes individually where the procedure permits.
  5. Verify completion signals, timeouts, and expected fault handling.
  6. Conduct cycle testing under the approved conditions.
  7. Record cycle behavior, process results, and any deviations.

Release and handover

  1. Resolve or formally document outstanding defects.
  2. Confirm the accepted program and configuration revisions.
  3. Save the final approved backup.
  4. Record test results and any approved parameter changes.
  5. Complete the required acceptance and handover documentation.

Never improvise a safety bypass or assume that reduced speed alone makes a robot test safe. Use the validated safety measures, authorized personnel, and manufacturer-approved commissioning process.

17. Troubleshooting Robot Programs

Symptom Possible causes Diagnostic approach
Program will not start Incorrect mode, missing start conditions, active fault Identify the first unmet start condition
Robot stops at a wait instruction Expected input never arrives Check signal source, mapping, sequence, and timeout
Robot reaches the wrong location Incorrect target, tool frame, or workpiece frame Compare active frames and approved target data
Path is unexpectedly curved Joint motion selected, blending active, or different target configuration Review motion type, targets, and transition settings
Robot reports unreachable target Joint limits, orientation, collision, or configuration constraints Inspect target reachability and path feasibility
Gripper fails to pick a part Pneumatic or electrical fault, missing part, timing issue Check tool I/O and physical feedback
Program completes but PLC does not advance Completion handshake missing or incorrect Trace output mapping and PLC transition conditions
Cycle time increases Reduced speed, waits, excessive exact stops, peripheral delays Measure sequence timing and identify the dominant delay
Quality varies between cycles TCP, payload, fixture, process, or mechanical variation Compare calibration, load data, and process records
Fault appears after program update Changed targets, missing subprogram, altered I/O, or incompatible data Compare revisions and restore the known-good version if required

Troubleshooting should start with the first unexpected state or alarm. Repeatedly resetting a robot without recording the initial fault can erase useful diagnostic evidence.

18. Robot Program Optimization

Optimization should improve cycle time, quality, reliability, or maintainability without compromising safety or process requirements.

Common methods include:

  • Removing unnecessary transit movements.
  • Selecting suitable motion types for each segment.
  • Reducing unnecessary stops where blending is acceptable.
  • Improving approach and exit paths.
  • Eliminating redundant waits while preserving required handshakes.
  • Coordinating robot and peripheral operations where the validated sequence permits.
  • Standardizing reusable subprograms.
  • Improving fault messages and recovery routines.
  • Verifying payload and process settings.
  • Measuring cycle time before and after changes.

A simplified cycle-time model is:

\[ T\_{\text{cycle}} = T\_{\text{motion}} + T\_{\text{process}} + T\_{\text{waiting}} + T\_{\text{handling}} \]

The terms must be defined consistently for the application. Some activities overlap, so their durations cannot always be added directly. A timing study should identify which operations run sequentially and which run concurrently.

The best optimization target is usually the dominant source of delay, not the most visually obvious movement.

19. Safety and Quality Considerations

Robot program validation must consider the entire cell, including tools, fixtures, conveyors, external axes, and connected machinery.

Important controls include:

  • Approved risk assessment and safety validation.
  • Verified protective devices and safety-related functions.
  • Controlled access during commissioning.
  • Approved operating modes and speed restrictions.
  • Safe tool and payload configuration.
  • Collision and clearance checks.
  • Defined recovery procedures after interruptions.
  • Validated process interlocks.
  • Quality checks for the completed operation.
  • Controlled software changes and recoverable backups.

A robot program's ordinary logic cannot replace safety-rated monitoring or protection. For example, a normal program condition that checks whether a door signal is active is not automatically equivalent to a validated safety interlock.

Quality verification depends on the process. Welding may require weld-quality checks; dispensing may require bead inspection; machine tending may require part-presence, orientation, and clamping verification.

A complete handover package should make the robot system understandable and recoverable by the maintenance team.

For maintenance, the key is to preserve the relationship between the program revision, controller configuration, tooling, PLC interface, and physical machine setup.

21. Common Mistakes to Avoid

  • Loading a program without confirming its revision and controller compatibility.
  • Assuming target coordinates are correct without verifying active frames.
  • Changing TCP data to compensate for incorrectly taught targets.
  • Increasing speed before validating the complete path.
  • Treating simulation as a substitute for controlled physical commissioning.
  • Editing PLC handshake logic without understanding signal ownership.
  • Ignoring external axes and peripheral equipment.
  • Clearing faults repeatedly without recording the first fault.
  • Modifying programs without preserving the previous accepted revision.
  • Optimizing cycle time without measuring the actual bottleneck.
  • Treating ordinary program logic as a safety function.
  • Releasing the robot without final backup and handover records.

22. Interview Questions and Answers

Q1. What is a robot program?

A sequence of instructions defining robot motion, process actions, program flow, and interaction with other equipment to perform a manufacturing task.

Q2. What is the difference between joint and linear motion?

Joint motion controls movement toward a target joint configuration, so the TCP generally follows a curved path. Linear motion attempts to maintain a straight Cartesian TCP path.

Q3. What is TCP?

The Tool Center Point is the defined reference point of the robot tool, used to control and describe tool position and orientation.

Q4. Why is a workpiece coordinate frame important?

It relates programmed targets to the actual workpiece or fixture. Incorrect frame data can shift or rotate the entire programmed trajectory.

Q5. What is a robot-PLC handshake?

It is an agreed exchange of requests, acknowledgements, status signals, and completion signals used to coordinate robot actions with the rest of the cell.

Q6. Why might a robot wait indefinitely during a program?

A required input may never arrive, the signal may be mapped incorrectly, a peripheral may be unavailable, or the sequence may be waiting for a condition that cannot become true.

Q7. What is the purpose of payload configuration?

It tells the controller about the robot's carried load and related mechanical properties so motion can be controlled within the applicable limits.

Q8. What is offline programming?

It is the development and simulation of robot programs using a virtual robot and cell model before or alongside physical commissioning.

Q9. How can robot cycle time be improved?

Measure the cycle, identify the dominant delay, optimize suitable motion paths and transitions, reduce unnecessary waiting, and validate the changes against process and safety requirements.

Q10. What should be backed up before editing a robot program?

The accepted program revision and all required associated data, including subprograms, targets, tool and frame data, relevant configuration, and required interface documentation.

Q11. Why can a program work in simulation but fail on the real robot?

The virtual model may not accurately represent the real geometry, frames, payload, controller behavior, external axes, peripherals, or physical tolerances.

Q12. What is the most important commissioning principle?

Verify the complete robot-cell behavior using the approved procedure, preserve a known-good baseline, and document the accepted configuration and test evidence.

23. Final Checklist

  • Robot and controller model identified.
  • Approved program revision confirmed.
  • Program backup and associated data preserved.
  • Tool, workpiece frames, and payload verified.
  • Targets, orientation, and path clearances checked.
  • Robot I/O and PLC handshake verified.
  • Peripheral equipment and process conditions checked.
  • Initial movement and cycle testing completed under approved conditions.
  • Fault handling and recovery behavior verified.
  • Cycle time and process quality validated.
  • Safety validation and acceptance requirements completed.
  • Final program, configuration, and handover records updated.
