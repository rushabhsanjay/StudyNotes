1. Definition and Purpose

PLC/HMI loading is the process of transferring an approved control program, configuration, or project from an engineering computer into a PLC (Programmable Logic Controller), HMI (Human-Machine Interface), or related automation device.

In industrial site execution, loading is commonly performed during machine installation, commissioning, replacement of hardware, software upgrades, troubleshooting, and recovery after a device failure.

The objective is not merely to transfer a file. The loaded application must match the installed hardware, firmware, machine configuration, safety architecture, and approved software revision, and it must be verified before the machine is released for operation.

PLC/HMI loading typically involves:

  • Identifying the correct PLC, HMI, and engineering software.
  • Verifying the approved project version and backup.
  • Checking hardware compatibility and firmware requirements.
  • Establishing a programming or communication connection.
  • Uploading from a device or downloading to a device, as appropriate.
  • Resolving compatibility or configuration differences.
  • Verifying the loaded program and device configuration.
  • Testing I/O, communication, interlocks, alarms, and machine functions.
  • Recording the final software revision and backup.

Critical distinction: Downloading generally means transferring a project from the engineering computer to the device. Uploading generally means retrieving project data from the device to the engineering computer. Exact terminology and available functions vary by manufacturer and software platform.

2. Why PLC/HMI Loading Matters During Site Execution

A machine may be mechanically installed and electrically connected but still be unable to operate because the required software has not been loaded or verified.

Typical situations include:

  • A new PLC CPU has been installed.
  • An HMI has been replaced following a display or hardware failure.
  • A controller requires the approved application after a hardware replacement.
  • A machine has been relocated and its communication configuration needs updating.
  • An engineering change has modified sequence logic, alarms, or interlocks.
  • The existing software backup must be restored.
  • A firmware or hardware revision requires an approved compatibility change.
  • A project must be transferred from the machine builder's engineering system to the plant's maintenance system.

Incorrect loading can cause machine downtime, unexpected actuator movement, communication failures, loss of HMI functionality, or loss of an existing configuration.

3. PLC and HMI: Different Loading Requirements

Feature PLC loading HMI loading
Main purpose Load machine-control logic and controller configuration Load operator screens and HMI application configuration
Typical content Logic, hardware configuration, I/O assignments, tags, communication settings Screens, navigation, tags, alarms, recipes, trends, scripts
Main risk Incorrect sequence, outputs, interlocks, or controller configuration Incorrect commands, misleading status, missing alarms, or communication failure
Typical verification Controller status, I/O, sequence, interlocks, diagnostics Screen operation, tag communication, alarms, navigation, and commands
Hardware dependency CPU model, modules, firmware, and network configuration HMI model, resolution, firmware/runtime, and communication drivers
Backup concerns Source project, controller configuration, firmware and safety-related data where applicable Editable HMI project, runtime application, settings, and any required data files

The PLC and HMI are separate devices. Loading one does not automatically load the other unless the engineering environment explicitly supports a coordinated workflow.

A successful compile does not prove that a project is safe, correct, or compatible with the actual machine. It only establishes that the engineering tool's applicable checks have passed.

6. Pre-Loading Preparation

Preparation is the most important stage because the wrong project can overwrite a working machine. A few minutes of verification can prevent hours of recovery work.

6.1 Identify the target device

Record the following information before connecting:

Item What to verify
Machine Correct machine number, station, or equipment ID
PLC Manufacturer, exact CPU model, order number, and installed modules
HMI Manufacturer, exact model, display resolution, and runtime platform
Firmware Installed and required firmware versions
Engineering software Software version, installed packages, and required licenses
Communication Ethernet address, USB/serial connection, or approved programming path
Project File name, revision, date, and engineering approval
Safety system Safety CPU, safety application revision, signatures, and authorization requirements where applicable
Operating state Current production state, active faults, and machine-safe condition
Backup Verified recovery copy and relevant device configuration

Never select a PLC based only on its IP address or a familiar device name. Confirm its identity using the engineering software and available hardware identification.

6.2 Project compatibility checks

Verify that the project matches the installed equipment.

  • CPU type and firmware compatibility.
  • Installed I/O module types and hardware configuration.
  • Communication modules and network topology.
  • PLC program and library versions.
  • HMI hardware model and runtime version.
  • HMI-to-PLC tag references and communication drivers.
  • Required technology objects, add-on instructions, or function libraries.
  • Safety-related configuration and required validation.
  • Retentive data and machine-specific parameters.
  • Required passwords, access permissions, and project protection.

A project can compile successfully yet still be inappropriate for the target machine. Compatibility is a technical requirement, not an administrative formality.

7. Backups Before Loading

Before modifying an operating machine, establish a recovery point.

7.1 What to back up

PLC

  • The original engineering project.
  • The currently available controller application.
  • Hardware and network configuration.
  • Firmware and hardware identification records.
  • Retentive data or machine-specific values that must be preserved.
  • Safety-related application and associated verification records, where applicable.

HMI

  • The editable HMI engineering project.
  • The current runtime application, where retrievable.
  • Communication settings and controller references.
  • Recipes, user-management configuration, and required data files.
  • Relevant language, font, image, and library assets.
  • Device-specific configuration that may not be included in the application project.

Machine records

  • Existing alarms and fault conditions.
  • Current software revisions.
  • Active machine settings that may be affected.
  • Approved change request and rollback procedure.

7.2 Upload is not always a complete backup

An upload from a PLC or HMI may not recover the original editable project in full.

Possible limitations include:

  • Missing source comments, symbolic names, or project organization.
  • Password-protected or know-how-protected program sections.
  • Missing external libraries and engineering dependencies.
  • Missing HMI source assets or editable screen definitions.
  • Device-specific data stored outside the main application.
  • Differences between the original project and the installed application.

For this reason, maintain the approved source project separately from device uploads. Verify what the chosen platform can actually recover.

7.3 Backup naming convention

Use a consistent naming format.

MachineID_Device_ProjectRevision_Date

Example:

M105_PLC_R03_2026-10-16
M105_HMI_R03_2026-10-16

These are illustrative names. Use the plant's controlled naming and revision system where one exists.

Keep the original backup unchanged. Perform engineering modifications on a separate working copy, and retain an identifiable record of the version approved for loading.

8. PLC Loading Procedure

The following procedure is generic. The exact menu names and device behavior vary by engineering software, CPU family, and firmware.

Step 1: Establish machine safety

  • Obtain authorization for the software change.
  • Inform production and relevant maintenance personnel.
  • Stop the machine using the approved operating procedure.
  • Place actuators and mechanical systems in the required safe state.
  • Isolate hazardous energy where the work requires it.
  • Prevent unexpected movement during testing.
  • Identify whether the download may stop or restart the CPU.
  • Confirm that safety-related systems and bypasses are handled under approved procedures.

A PLC download can alter output behavior or restart control execution. Never assume that the machine will remain in its current physical state during the transfer.

Step 2: Open the approved project

  1. Start the correct engineering software.
  2. Open the approved project or a controlled working copy.
  3. Verify the machine identifier and revision.
  4. Confirm the intended CPU and module configuration.
  5. Check project dependencies, libraries, and firmware requirements.
  6. Confirm that the project is not an unverified file from another machine.

Step 3: Compile or build

Run the appropriate compile or build operation.

Check for:

  • Syntax errors.
  • Invalid data types or references.
  • Hardware configuration errors.
  • Unsupported instructions or features.
  • Missing libraries.
  • Firmware or device compatibility issues.
  • Communication configuration problems.
  • Safety application errors where relevant.

Resolve errors before downloading. Review warnings rather than dismissing them automatically.

Step 4: Connect to the controller

Establish the programming connection through the approved interface, such as Ethernet, USB, or a supported programming adapter.

Verify:

  • The correct network interface is selected.
  • The target device is the intended controller.
  • The IP address or communication path is correct.
  • The controller's reported identity matches the project.
  • No unintended device is selected through an address conflict or duplicate network configuration.

Do not change the IP address of an operating machine without checking network dependencies and obtaining authorization.

Step 5: Compare and inspect the download preview

Where the platform provides a comparison or load-preview function, inspect it before confirming the transfer.

Check whether the proposed operation changes:

  • Program blocks or routines.
  • Hardware configuration.
  • I/O assignments.
  • Network addresses or communication settings.
  • Firmware or system data.
  • Retentive values.
  • Safety-related configuration.
  • Operating mode or controller state.

Determine whether the operation requires stopping the CPU. If the proposed changes are unexpected, cancel the operation and investigate.

Step 6: Download the project

  1. Confirm that the approved target and project are selected.
  2. Review all warnings and prompts.
  3. Confirm the expected controller state during transfer.
  4. Start the download only after the required authorization.
  5. Monitor the transfer and check for errors.
  6. Complete any required restart or mode transition under the approved procedure.

Do not disconnect the programming cable, interrupt power, or close the engineering software during a transfer unless the manufacturer's recovery instructions explicitly require it.

Step 7: Verify controller status

After loading:

  • Confirm the controller has reached the intended operating state.
  • Check diagnostics and fault buffers.
  • Verify that the expected program and configuration are present.
  • Confirm communication with remote I/O and other devices.
  • Check for module faults and missing hardware.
  • Verify that required data has been preserved or restored.
  • Confirm that the program revision matches the approved release.

A successful transfer message alone is insufficient.

Step 8: Perform functional testing

Test the machine using the approved commissioning or change-validation plan.

  • Check PLC inputs against actual field-device states.
  • Verify output commands under controlled conditions.
  • Confirm interlocks and permissives.
  • Check the machine sequence.
  • Verify alarm generation and reset behavior.
  • Confirm drive and robot interface signals where relevant.
  • Test required fault-recovery behavior.
  • Validate safety functions using the approved safety validation process.

Do not force outputs or bypass interlocks to make a test pass. Any diagnostic forcing must be authorized, controlled, recorded, and removed before release.

9. HMI Loading Procedure

An HMI project is more than a collection of screens. It may include communication configuration, alarm definitions, recipes, user access, scripts, trends, and runtime settings.

Step 1: Verify the HMI project

Confirm:

  • Correct machine and project revision.
  • Correct HMI hardware model.
  • Correct screen dimensions and resolution.
  • Runtime compatibility.
  • Correct PLC controller reference.
  • Correct tag names and addresses.
  • Correct alarm, recipe, and trend configuration.
  • Required external assets and libraries.
  • User roles and access permissions.

Step 2: Build or compile the HMI application

Run the relevant validation or build operation.

Investigate:

  • Invalid tags.
  • Missing PLC references.
  • Unsupported objects.
  • Script errors.
  • Invalid expressions.
  • Missing fonts or graphic assets.
  • Runtime compatibility warnings.
  • Alarm or recipe configuration errors.

Resolve relevant errors before transferring the application.

Step 3: Connect to the HMI

Verify the target device and the intended transfer path. Depending on the platform, this may use Ethernet, USB, removable storage, or a vendor-specific transfer mechanism.

Confirm that the transfer will not affect a different HMI on the same network.

Step 4: Transfer the runtime application

Use the manufacturer's approved transfer procedure.

Check the target device, transfer status, runtime version, and any prompts about overwriting the existing application.

Some systems build the runtime application on the engineering computer before transferring it. Others use a different packaging or installation process.

Step 5: Start and verify the runtime

After the transfer:

  • Confirm that the HMI runtime starts correctly.
  • Verify the startup screen and navigation.
  • Confirm PLC communication.
  • Check that displayed states match the actual machine.
  • Verify alarms, acknowledgements, and alarm history.
  • Check recipe handling and relevant operator permissions.
  • Confirm that trends and data logging work if configured.
  • Test command buttons under safe conditions.
  • Verify screen behavior after communication loss and recovery.

A screen that displays values is not necessarily communicating correctly. Confirm that values are current, correctly mapped, and consistent with the controller.

11. PLC Loading: Important Siemens Concepts

For Siemens S7 systems, the engineering workflow commonly involves TIA Portal and STEP 7 for supported controller families.

Important concepts include:

  • Device configuration: The configured CPU and modules must match the installed hardware.
  • Compile: The engineering software checks and prepares the project data.
  • Download to device: Transfers applicable project data to the controller.
  • Load preview: Helps identify the proposed changes and their implications.
  • Online diagnostics: Helps identify CPU, module, and communication problems.
  • Firmware compatibility: The CPU firmware and engineering project must support each other.

For supported S7-1200 and S7-1500 configurations, downloads may include related program blocks, tags, and other dependent data. The exact scope depends on the selected operation and project changes.

An online connection does not guarantee that the offline project is identical to the running controller. Use the supported comparison functions when verifying differences.

Official documentation: Siemens STEP 7 compiling and downloading.

12. PLC Loading: Allen-Bradley Concepts

For applicable Allen-Bradley Logix controllers, Studio 5000 Logix Designer is used to engineer and manage the controller project.

Important concepts include:

  • Controller catalog number and revision.
  • Project compatibility with the target controller.
  • Communication path and controller identification.
  • Controller mode and the impact of switching modes.
  • Controller tags, routines, tasks, and I/O configuration.
  • Electronic keying and module compatibility, where configured.
  • Online edits and their approval requirements.
  • Retentive data and controller-specific settings.

The controller's current state matters. A download can replace the application and change the controller's operating state, so it must be planned around the machine's safe state and production requirements.

Do not confuse upload, download, and online edit. An online edit is a distinct workflow with its own acceptance, testing, and operational risks.

13. PLC Loading: Mitsubishi Concepts

For Mitsubishi MELSEC controllers, the appropriate engineering software depends on the PLC series. GX Works2 and GX Works3 are not interchangeable for every model.

Verify:

  • PLC series and CPU model.
  • Project and device parameters.
  • Program and parameter compatibility.
  • Network configuration.
  • Special modules and their settings.
  • Device values that must be retained.
  • Whether the transfer changes the controller's operating state.

For HMI applications, confirm compatibility between the HMI model, GT Designer version, project, and PLC communication settings.

14. HMI Loading: Important Technical Details

14.1 Editable project versus runtime

An editable HMI project is used for engineering changes. A runtime application is the deployed application executed on the target HMI.

These are not necessarily equivalent files.

Item Editable project Runtime application
Purpose Engineering and modification Execution on the HMI
Screen objects Usually available in editable form Deployed in runtime form
Tag definitions Used to configure application communication Used by the deployed application
Source scripts and assets May include editable source and dependencies May contain compiled or packaged resources
Future engineering Normally the preferred starting point May not be sufficient for full reconstruction

Preserve the editable project and its dependencies. Do not assume that a runtime upload will reproduce the original project completely.

14.2 PLC communication configuration

An HMI may communicate with a PLC through Ethernet, serial communication, or another supported network.

Verify:

  • PLC address and HMI connection settings.
  • Correct communication driver.
  • Correct controller and tag references.
  • Data types and addressing.
  • Network accessibility.
  • Required protocol settings.
  • Device-specific communication limits.

If the HMI shows communication errors after loading, check the physical network, addressing, driver, controller reference, and device diagnostics before changing the PLC logic.

14.3 Recipes and runtime data

Recipes, operator settings, alarm history, and trends may be stored in the HMI, PLC, or an external system.

Before replacement or download, identify which data must be preserved and where it is stored. A successful application transfer does not guarantee that this runtime data has been retained.

15. Firmware and Version Compatibility

Firmware is the device-level software that supports the hardware's operation. It is distinct from the PLC application or HMI project.

Potential compatibility problems include:

  • A project created for a newer CPU firmware.
  • An engineering tool that does not support the installed device.
  • A hardware module that is missing from the project's hardware catalog.
  • A runtime application that is incompatible with the HMI firmware.
  • A library or instruction that requires a newer software version.
  • A project conversion that changes configuration or application behavior.

Compatibility verification sequence

  1. Record the actual device model and firmware.
  2. Identify the engineering software version.
  3. Check the project version and required device support.
  4. Review manufacturer compatibility documentation.
  5. Identify any required project conversion or firmware change.
  6. Evaluate the effect on existing application behavior and backups.
  7. Obtain approval before performing a firmware update.
  8. Validate the application after the change.

Do not update firmware merely to eliminate a compatibility warning. Firmware updates can affect existing projects, modules, communications, and recovery procedures.

16. Safety-Related PLC and HMI Loading

Safety-related automation requires a stricter process than ordinary application loading.

Examples include safety PLCs, fail-safe I/O, safety relays, and safety-rated drive functions.

Key requirements may include:

  • Authorized personnel and controlled access.
  • Approved safety application and revision.
  • Correct safety hardware configuration.
  • Appropriate safety signature or equivalent verification.
  • Required password or access protection.
  • Documented change approval.
  • Validation of the safety functions affected by the change.
  • Formal recording of test results and acceptance.

An HMI emergency-stop graphic or software button is not automatically a safety-rated emergency-stop function.

A safety function must be implemented and validated through the designed safety architecture. Never bypass safety logic or modify safety parameters merely to make the machine run.

17. Cybersecurity and Change Control

PLC and HMI engineering stations can modify production equipment. Access and software handling should therefore be controlled.

Recommended practices include:

  • Use approved engineering laptops and software versions.
  • Maintain authorized access to controllers and projects.
  • Verify the source of received project files.
  • Scan files according to plant cybersecurity procedures.
  • Store backups in approved locations with suitable access control.
  • Avoid unapproved internet connections to production networks.
  • Use approved removable media and transfer methods.
  • Record who performed the change and when.
  • Keep an auditable revision history.
  • Avoid sharing passwords in project comments or general maintenance records.
  • Restore normal access controls after commissioning.

An approved change should have a traceable link between the request, engineering revision, downloaded application, validation results, and handover record.

19. Troubleshooting Method

Use a structured method instead of repeatedly downloading the project and hoping the controller eventually develops a sense of cooperation.

  1. Identify the symptom: Record the exact error message, diagnostic code, and device state.
  2. Confirm the target: Verify the CPU or HMI model and communication path.
  3. Check the project: Confirm the file, revision, compile status, and compatibility.
  4. Check the connection: Inspect network settings, cables, ports, and access restrictions.
  5. Review device diagnostics: Determine whether the problem is related to hardware, firmware, configuration, or application logic.
  6. Check the transfer stage: Identify whether the failure occurred during connection, validation, download, startup, or runtime operation.
  7. Protect the existing state: Avoid unnecessary resets, firmware changes, or repeated downloads.
  8. Recover methodically: Use the approved backup and manufacturer procedure.
  9. Validate the result: Repeat the required functional and safety checks.
  10. Document the cause: Record the actual root cause and corrective action.

Do not treat a communication failure as proof that the PLC program is faulty. The problem may be in the network path, engineering software, access configuration, or device compatibility.

20. Software Loading Records and Handover

After loading, record the configuration that was actually installed.

A useful record includes:

Record field Example or expected content
Machine ID Unique machine or station identifier
Device ID PLC or HMI tag
Hardware model Actual installed model
Firmware/runtime Actual installed version
Engineering software Tool and version used
Project name Approved source project
Project revision Released software revision
Transfer date Date of loading
Technician/engineer Authorized person who performed the change
Change reference Work order, change request, or approval number
Verification result Compile, diagnostics, and functional-test results
Backup location Controlled storage path or repository reference
Outstanding defects Remaining issues and operational restrictions

The final record should identify the version loaded, not merely the file that was intended to be loaded.

21. Practical Site Example: PLC Replacement

A machine has an S7-1500 PLC. The original CPU has failed, and a replacement CPU is being installed.

Procedure

  1. Confirm the replacement CPU model and supported firmware.
  2. Identify the approved machine project and last known-good revision.
  3. Review the hardware configuration and required modules.
  4. Check whether IP addresses, device names, protection settings, and communication parameters must be restored.
  5. Establish the approved safe state and obtain authorization.
  6. Connect to the replacement CPU and verify its identity.
  7. Compile the project for the target configuration.
  8. Inspect the load preview and any compatibility warnings.
  9. Download using the manufacturer-approved procedure.
  10. Verify CPU status, module diagnostics, and remote I/O communication.
  11. Confirm that required retentive or machine-specific data has been restored appropriately.
  12. Test inputs, outputs, interlocks, sequence behavior, and communications.
  13. Validate all affected safety functions under the approved procedure.
  14. Save the verified project and record the installed revision.

The replacement CPU may require configuration beyond the application logic. Do not assume that transferring the program alone restores every device setting or machine-specific value.

22. Practical Site Example: HMI Replacement

An operator HMI has failed and is replaced with a compatible unit.

Procedure

  1. Confirm the exact replacement model and display specifications.
  2. Retrieve the approved editable HMI project.
  3. Verify its revision and runtime compatibility.
  4. Check PLC communication settings and tag references.
  5. Identify recipes, user settings, and runtime data that must be preserved.
  6. Build and validate the application.
  7. Transfer it using the approved method.
  8. Start the HMI runtime and verify startup behavior.
  9. Check PLC communication and compare displayed values against actual controller data.
  10. Test navigation, alarms, acknowledgements, recipes, and permitted commands.
  11. Verify user permissions and required security settings.
  12. Record the new HMI model, software version, project revision, and test results.

If the HMI powers up but displays stale or incorrect values, do not assume that the PLC program needs to be reloaded. First investigate the HMI communication configuration, tag mapping, and runtime diagnostics.

23. PLC/HMI Loading Checklist

Before loading

  • Approved project and revision identified.
  • Actual target device verified.
  • Hardware and firmware compatibility checked.
  • Engineering software and required libraries verified.
  • Existing application and relevant data backed up.
  • Machine safe state and required authorization established.
  • Production and maintenance personnel informed as required.
  • Download impact and rollback procedure reviewed.

During loading

  • Correct communication interface selected.
  • Target device identity verified.
  • Project compiled or validated.
  • Download preview and warnings reviewed.
  • Expected controller state confirmed.
  • Transfer completed without unresolved errors.

After loading

  • CPU and HMI status verified.
  • Hardware and communication diagnostics checked.
  • Program and project revisions recorded.
  • PLC inputs and outputs verified.
  • HMI tags, alarms, and commands tested.
  • Interlocks and affected safety functions validated.
  • Retentive data and required runtime data verified.
  • Final backup stored in the approved location.
  • Handover records updated and defects documented.

24. Interview Questions and Answers

Q1. What is PLC loading?

It is the process of transferring an approved PLC application and relevant configuration from the engineering environment to the target controller.

Q2. What is the difference between uploading and downloading?

Downloading generally transfers engineering data to the device. Uploading generally retrieves available device data into the engineering environment.

Q3. Why must a project be compiled before downloading?

Compilation checks the project for errors and prepares the relevant data for the target platform. It does not replace compatibility checks or machine validation.

Q4. Why is a backup required before loading?

A backup provides a recovery point and helps preserve the previous application, configuration, and required machine data.

Q5. Why can the uploaded PLC project differ from the original source project?

The device may not contain all editable source information, comments, libraries, external assets, or engineering metadata.

Q6. What is firmware compatibility?

It is the requirement that the controller's device-level software, engineering tool, project, and supported hardware configuration work together.

Q7. Why should the PLC identity be verified before download?

To prevent overwriting the wrong controller, particularly when multiple machines share the same network or similar device names.

Q8. What should be checked after PLC loading?

Controller status, diagnostics, I/O, communication, program revision, interlocks, sequence behavior, and affected safety functions.

Q9. Why is HMI loading different from PLC loading?

The HMI runs an operator-interface application, while the PLC executes machine-control logic. Their application formats, runtimes, and verification requirements differ.

Q10. Why might an HMI display a communication error after loading?

The PLC address, driver, tag mapping, network path, or communication settings may be incorrect or incompatible.

Q11. What is an as-loaded software record?

It is a controlled record of the actual application revision and device configuration installed on the machine, together with the transfer and verification results.

Q12. Can a successful download prove that a machine is ready for production?

No. The transfer must be followed by the required diagnostics, functional checks, and safety validation before the machine is released.

Q13. What is the difference between an online edit and a full download?

An online edit changes supported parts of a running controller's application through a controlled online workflow. A full download transfers the applicable project data and may require a controller state change.

Q14. What should be done if the wrong project is downloaded?

Follow the machine's approved recovery procedure, establish the safe state, restore the correct verified project and required data, validate the affected functions, and document the incident. Do not assume that reloading the previous file automatically restores all operating data.

25. Key Takeaways

  • PLC/HMI loading is a controlled engineering and commissioning activity, not just a file transfer.
  • Correct device identification, revision control, compatibility checks, and backups are essential.
  • An uploaded application may not reconstruct the original editable project.
  • PLC and HMI applications require separate, appropriate verification.
  • Firmware, hardware configuration, retentive data, and safety-related settings must be considered.
  • A successful download does not prove that the machine operates correctly.
  • Functional testing, safety validation, and controlled handover complete the loading process.
