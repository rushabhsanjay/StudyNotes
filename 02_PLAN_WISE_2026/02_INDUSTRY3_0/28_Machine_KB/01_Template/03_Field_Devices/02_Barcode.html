1. Purpose of Barcode Scanner Documentation

Industrial barcode scanners identify parts, assemblies, containers, tools, labels, and production orders by reading encoded information. In automated production, the decoded value may be used to select a process recipe, verify component identity, associate traceability records, control routing, or confirm that the correct part has reached a station.

Barcode documentation must cover more than the scanner's make and model. A scanner can power up and communicate correctly while failing to decode labels, reading the wrong code, sending data in the wrong format, or returning a valid-looking string that the PLC rejects.

A useful machine knowledge base should answer these questions:

  • What scanner is installed, and what is its exact part number?
  • Where is it mounted, and which code does it read?
  • What barcode symbology and code format are expected?
  • How is the scanner triggered?
  • How are decoded data and status information sent to the PLC or PC?
  • Which communication settings, parameters, recipes, and backups are required?
  • How is a failed read distinguished from a communication failure or an incorrect part?
  • What replacement model and recovery procedure are approved?

2. Barcode System Architecture

A typical industrial barcode reading system follows this path:

Part, component, pallet, or label
          ↓
Printed or marked barcode
          ↓
Scanner optics and image sensor
          ↓
Image processing and decoding
          ↓
Decoded data and read status
          ↓
Scanner interface or communication network
          ↓
PLC, industrial PC, or controller
          ↓
Data validation and sequence logic
          ↓
HMI result, traceability system, or production database

The architecture varies by device. A scanner may connect through discrete I/O, serial communication, Ethernet TCP/IP, EtherNet/IP, PROFINET, or another supported interface. Some systems use a scanner-specific controller, multi-reader network, or industrial PC.

The scanner's internal status, communication status, decode result, and process acceptance are separate conditions. A machine knowledge base should document each one.

3. Barcode Fundamentals

A barcode represents data using a pattern that a reader can interpret. The pattern may use bars and spaces, geometric modules, or a two-dimensional arrangement of dark and light regions.

Main barcode categories

Category Examples Typical characteristics
1D linear barcode Code 128, Code 39, EAN-13, UPC-A, Interleaved 2 of 5 Data encoded along one dimension
2D matrix barcode Data Matrix, QR Code, Micro QR Data encoded in a two-dimensional pattern
Stacked barcode PDF417 Multiple stacked rows of encoded data
Direct Part Marking (DPM) Data Matrix marked by laser, dot peen, or chemical etching Code marked directly on the component surface

Not every scanner supports every symbology. A reader configured for a particular 1D code may not read a Data Matrix code until the appropriate symbology is supported and enabled.

Common industrial applications

  • Part identification before assembly.
  • Component verification against the production order.
  • Engine, transmission, chassis, or vehicle traceability.
  • Pallet and container tracking.
  • Fixture and tool identification.
  • Work-in-progress tracking.
  • Recipe or program selection.
  • Recording serial numbers and manufacturing history.

4. Barcode Symbologies and Data Format

The barcode symbology defines how data is encoded. The data format defines what the decoded characters mean to the application.

Symbology Common use Documentation and setup checks
Code 128 General industrial identification Character set, length, check character handling
Code 39 Industrial labels and legacy identification Allowed characters, optional check character
EAN-13 Retail and product identification Fixed structure and check digit
UPC-A Retail product identification Fixed structure and check digit
Interleaved 2 of 5 Labels containing numeric data Numeric format and length constraints
Data Matrix ECC 200 Compact industrial part identification and DPM Module size, marking quality, supported reader capability
QR Code Identification and data exchange Version, error correction, data length, supported reader capability
PDF417 Documents and selected logistics applications Stacked symbol support and data capacity

A scanner's ability to decode a symbology does not mean the PLC application will accept every value encoded in it. The controller may require a particular prefix, length, serial number format, or product identifier.

Decoded data example

A hypothetical scanner may return:

PART=ABC123;SERIAL=00004567;REV=B

The PLC or PC application may need to extract and validate the part number, serial number, and revision. This example is an application-specific string, not a universal barcode format.

Leading zeros, delimiters, prefixes, suffixes, and character encoding must be preserved where the production system expects them. Converting a numeric-looking identifier into an integer can remove leading zeros and corrupt traceability.

5. Scanner Technologies

Laser barcode scanners

Laser scanners use a laser beam and optical detection to read supported linear barcodes. They are commonly associated with 1D reading applications.

Important considerations include code orientation, scan line coverage, label quality, distance, and whether the specific scanner supports the required barcode type. A conventional laser scanner should not be assumed suitable for 2D matrix codes or direct part marking.

CCD and linear-image scanners

CCD or linear-image readers use image-sensing technology to capture barcode patterns. Depending on the device, they may support selected 1D codes and other applications.

Check the supported symbologies, optical range, field of view, illumination, and code orientation requirements in the model's documentation.

Area-image barcode scanners

Area-image scanners capture an image of the target and decode the barcode using image-processing algorithms. Many industrial readers in this category can read both 1D and 2D symbols.

They are used for applications such as Data Matrix identification, multi-code reading, and codes presented at varying orientations. Performance depends on optics, resolution, focus, illumination, exposure, and the actual marking quality.

Fixed-mount industrial scanners

Fixed-mount readers are installed at a defined station and triggered by a sensor, PLC, encoder, or internal operating mode. They may include configurable lighting, lenses, digital I/O, and industrial communication interfaces.

Document the mounting geometry and operating conditions because changing the distance or angle can affect reading performance even when the scanner's electrical configuration remains unchanged.

Handheld scanners

Handheld readers are used for manual identification, maintenance, rework, and operator-assisted traceability. Depending on the model, they may connect through USB, serial communication, Bluetooth, or an industrial interface.

Document the charging or power arrangement, communication cradle, pairing configuration, operator workflow, and the system that receives the decoded data.

6. Scanner Manufacturers and Model Identification

Industrial barcode readers are available from several manufacturers. The product families and interfaces vary, so the exact installed model must be recorded rather than inferred from appearance.

Manufacturer Product family or example Typical documentation focus
Cognex DataMan series Reader configuration, acquisition settings, industrial communication, job backup
KEYENCE SR series Reading setup, trigger settings, communication and I/O
SICK Lector series Reading configuration, interface setup, diagnostics

Panasonic Barcode reader families Model-specific optical and communication setup

These are examples of manufacturers and product families, not a list of interchangeable devices. Product availability, features, firmware, and interface support differ between models and generations.

Minimum model register

Record the following for each installed scanner:

  • Manufacturer and exact model number.
  • Full ordering code and hardware variant.
  • Serial number, where useful.
  • Firmware version.
  • Scanner type and supported symbologies.
  • Lens, lighting, filter, and accessory details.
  • Supply voltage and current requirements.
  • Connector type and pinout.
  • Communication interface and protocol.
  • Scanner IP address, device name, or serial settings, where applicable.
  • Installed configuration or job name.
  • PLC or PC mapping.
  • Backup location and approved spare part.

A photograph of the nameplate is useful, but it should supplement the typed model number rather than replace it. Photographs can be blurry, inaccessible, or difficult to search.

7. Optical Setup and Mounting

A scanner must be positioned so that the barcode appears within its supported reading field and at an appropriate size, focus, and angle.

Key optical parameters

  • Working distance: Distance from the reader to the target within the specified operating range.
  • Field of view (FOV): The area visible to the reader at the installed distance.
  • Resolution: The reader's ability to distinguish the barcode's smallest relevant features, influenced by the imaging system and configuration.
  • Depth of field: The range of distances over which the reader can maintain suitable image quality.
  • Exposure: The image capture duration, which can affect brightness and motion blur.
  • Illumination: Light supplied by the reader or external lighting.
  • Reading angle: The orientation of the reader relative to the barcode surface.
  • Polarization and filters: Optical features that may help with glare or surface reflections when supported.

The exact performance limits are model-specific. Use the manufacturer's setup guide and validate the actual production code rather than relying on a generic distance or angle.

Mounting and alignment checks

  • Verify the bracket is rigid and does not move during machine vibration.
  • Confirm the code passes through the reader's usable field of view.
  • Check that the lens and illumination are not obstructed.
  • Inspect for glare from polished metal, glass, or reflective labels.
  • Confirm the target distance remains within the reader's specified range.
  • Check that moving parts cannot strike the reader or its cable.
  • Confirm the reader can access the code throughout the intended cycle.
  • Record the final mounting position and approved settings.

If a scanner reads correctly during manual testing but fails during automatic cycling, investigate target motion, vibration, trigger timing, exposure, and the actual code presentation before replacing the reader.

8. Barcode Quality and Direct Part Marking

A barcode's appearance strongly affects read reliability. The reader cannot recover information that is missing or indistinguishable in the captured image.

Common causes of poor readability include:

  • Low print contrast.
  • Blurred, incomplete, or damaged bars and modules.
  • Incorrect quiet zones where required by the symbology.
  • Labels that are wrinkled, curved, dirty, or reflective.
  • Codes that are too small for the reader's optical setup.
  • Excessive motion blur.
  • Surface glare or uneven illumination.
  • Poorly marked Data Matrix codes on metal or plastic components.
  • Code damage caused by abrasion, coolant, oil, heat, or handling.

Direct Part Marking requires particular care because the code may be produced by laser marking, dot peen, or another process directly on the component. Marking quality, material, surface finish, module geometry, and illumination all affect readability.

When recurring read failures occur, compare failed codes with known-good samples. Determine whether the issue is the code, the scanner setup, or both. Changing scanner sensitivity may help in some cases, but it does not repair a damaged or incorrectly generated code.

9. Triggering and Read Timing

A trigger tells the scanner when to acquire an image or begin a reading operation. Depending on the model, triggering may be continuous, sensor-based, PLC-controlled, encoder-based, or initiated through a communication command.

Common trigger methods

Trigger method Typical use Main checks
Continuous reading Manual testing or applications needing repeated reads Duplicate reads, data filtering, processing load
Discrete input trigger Part presence sensor initiates reading Input wiring, polarity, pulse width
PLC command PLC initiates the reading step Command timing, handshake, reset behavior
Network command Controller sends a software trigger Protocol, command format, acknowledgement
Encoder or position trigger Reading tied to object movement Position reference, timing, speed, trigger window

Trigger and result sequence

Part enters reading position
          ↓
Part-presence condition becomes valid
          ↓
PLC or sensor issues trigger
          ↓
Scanner acquires image and attempts decode
          ↓
Scanner returns result and status
          ↓
PLC receives and validates the data
          ↓
PLC accepts, rejects, or raises a fault
          ↓
Result is recorded and the sequence continues

The exact handshake may be more complex and may include busy, trigger acknowledgement, result-ready, new-data, read-complete, no-read, or reset signals.

A trigger that is too early may capture an absent or partially presented code. A trigger that is too late may occur after the target has moved out of the reading field. The setup must be tested at the real production speed and with realistic part-position variation.

10. Scanner Communication Interfaces

Barcode scanners may provide a decoded result through discrete I/O, serial communication, Ethernet, or an industrial network.

Interface Typical data exchange Documentation requirements
Discrete I/O Trigger, ready, good read, no read, error Wiring, signal polarity, pulse behavior
RS-232 Serial character data and control signals Baud rate, data bits, parity, stop bits, termination characters
RS-485 Serial communication over a differential interface Supported protocol, wiring, termination, addressing
USB Host connection, sometimes keyboard-emulation or serial modes Operating mode, host driver, device mapping
Ethernet TCP/IP Data over a network socket or supported application protocol IP configuration, ports, message framing, connection recovery
EtherNet/IP Industrial data exchange with supported devices Device integration, assembly or data mapping, connection configuration
PROFINET Industrial cyclic and acyclic data exchange where supported Device name, GSDML, module and data configuration
IO-Link Process data and diagnostics through a compatible master Port configuration, IODD, process-data mapping
Vendor-specific protocol Reader configuration and data exchange Supported commands, software version, recovery procedure

A scanner supporting Ethernet does not automatically support every industrial protocol. Confirm the exact model and firmware capabilities.

Serial communication parameters

For serial-connected readers, document:

  • Baud rate.
  • Data bits.
  • Parity.
  • Stop bits.
  • Flow control, if used.
  • Message termination characters.
  • Character encoding.
  • Command and response format.
  • Timeout and error handling.

For example, a reader might send decoded data followed by a carriage return. If the receiving application expects a different delimiter, it may wait indefinitely, combine multiple reads, or parse the string incorrectly.

Ethernet configuration

For Ethernet-connected readers, document:

  • Device IP address and subnet configuration.
  • Device name, where relevant.
  • Supported protocol and connection mode.
  • TCP or UDP behavior, if applicable.
  • Port and message framing, as documented by the manufacturer.
  • PLC or PC connection settings.
  • Network switch and port identification.
  • Recovery behavior after a power cycle or communication loss.

Follow plant network-management and cybersecurity requirements. Avoid undocumented IP changes or ad hoc network connections to production equipment.

11. PLC Integration and Handshake

A scanner's decoded string must be transferred and interpreted correctly by the PLC or PC. The precise implementation depends on the scanner protocol and controller platform.

A typical integration may use these logical states:

Signal or data field Purpose
Trigger request Requests a new reading
Ready Indicates the scanner can accept a trigger
Busy Indicates a reading operation is in progress
Read complete Indicates that a reading attempt has finished
Read success Indicates that a code was decoded
No-read status Indicates that no acceptable code was decoded
Data valid or new data Indicates that received data should be processed
Decoded data Contains the barcode string or structured result
Acknowledge or reset Confirms processing or prepares the next reading cycle
Communication health Indicates whether communication with the reader is functioning

These are conceptual signal names. The real device may use different names, data structures, bit assignments, or protocol semantics.

Example of a controlled read sequence

  1. Confirm that the scanner is ready and the part is in the required position.
  2. Issue a trigger according to the scanner's documented interface.
  3. Wait for the completion or result indication.
  4. Check the read-success or no-read status.
  5. Validate the decoded data against the required format and expected part.
  6. Acknowledge or reset the result as required by the interface.
  7. Record the result and permit the next operation only when the defined conditions are satisfied.

A robust application should have a timeout and a defined fault response. It should not wait forever if the scanner never completes the reading operation.

Important distinction

  • Read success: The scanner decoded a symbol.
  • Data valid: The received data is complete and ready for processing.
  • Part accepted: The application confirms that the data matches the expected product or process requirement.
  • Process complete: The machine has completed the associated operation.

These conditions must not be treated as equivalent.

12. Data Validation and Traceability

A decoded string may be technically readable but incorrect for the current production operation. Validation should therefore be designed separately from optical reading.

Possible checks include:

  • Expected symbology or reader-reported code type.
  • Minimum and maximum data length.
  • Prefix, suffix, delimiter, and character format.
  • Part number or product-family validity.
  • Serial number uniqueness, where required.
  • Revision or variant consistency.
  • Order, route, or recipe matching.
  • Duplicate-read handling.
  • Data completeness and communication quality.
  • Whether the identifier is already recorded in the traceability system.

A typical decision might be:

Decoded barcode received
          ↓
Is the result complete and correctly formatted?
          ↓
Does the identifier match the expected part or order?
          ↓
Is the identifier acceptable under traceability rules?
          ↓
Accept the part or generate the defined fault response

This is a conceptual validation sequence, not a ready-to-deploy PLC program.

Traceability considerations

If the decoded value is written to a production database, document the relationship between the barcode and the production record. Relevant fields may include machine ID, station, part number, serial number, timestamp, read status, process result, and the source device.

Define how the system handles:

  • No-read events.
  • Invalid or unexpected identifiers.
  • Duplicate scans.
  • Network outages.
  • Database failures.
  • Retried operations.
  • Part rework and re-entry.
  • Data buffering and recovery after disconnection.

Do not silently substitute an old barcode result when the current reading fails. A stale identifier can associate a valid process result with the wrong physical component.

13. Scanner Configuration and Job Management

Many fixed-mount readers have configurable jobs or profiles. A job may include symbologies, exposure, illumination, focus, triggering, filters, output formatting, and communication settings.

The exact parameters depend on the scanner family and model.

Configuration items to document

  • Configuration or job name and revision.
  • Supported and enabled symbologies.
  • Optical settings, focus, exposure, and illumination.
  • Trigger source, timing, and timeout settings.
  • Data formatting, prefixes, suffixes, and delimiters.
  • Communication protocol and interface parameters.
  • PLC mapping and status interpretation.
  • Result-handling and error behavior.
  • Firmware and configuration-software versions.
  • Approved backup file location.
  • Restore and verification procedure.

Configuration backup procedure

  1. Identify the installed scanner and firmware.
  2. Use the approved manufacturer software or documented device interface.
  3. Read the current configuration from the installed device where supported.
  4. Save the configuration in the approved repository using the site's naming and revision convention.
  5. Record the date, device ID, model, firmware, and change reference.
  6. Verify that the saved file can be identified and restored using the supported procedure.
  7. Protect access to the configuration according to plant controls.

A saved file is not automatically a valid recovery package. Some systems also require firmware compatibility, device-specific settings, calibration data, licenses, or external project files. Confirm the manufacturer's recovery requirements.

14. Scanner Diagnostics and Troubleshooting

Troubleshooting should distinguish among optical failure, trigger failure, communication failure, configuration error, and application rejection.

Diagnostic path

Confirm the machine fault and expected barcode
          ↓
Check scanner power and device status
          ↓
Check target presence, code quality, and alignment
          ↓
Confirm trigger request reaches the scanner
          ↓
Check decode status and diagnostic information
          ↓
Check communication and data transfer
          ↓
Compare received data with the PLC or PC data field
          ↓
Check validation logic and traceability response
          ↓
Correct the root cause and verify repeated operation

Common failure symptoms

Symptom Possible causes Diagnostic checks
Scanner has no power Supply fault, damaged cable, incorrect voltage Verify rated supply, connector, protection device, and wiring
Scanner powered but never triggered Trigger signal absent, wrong trigger source, incorrect input mapping Check trigger condition, wiring, and configuration
No-read with correct trigger Dirty lens, poor label, wrong symbology, poor focus or alignment Inspect code and optics; review reader diagnostics
Reads intermittently Vibration, variable part position, glare, marginal code quality Check mounting, target path, lighting, and actual production conditions
Reads the wrong code Multiple codes in field of view, selection rules incorrect Review field of view and code-selection configuration
Data appears truncated Incorrect message framing, buffer length, delimiter or protocol mapping Compare raw received data with the expected message
Extra characters appear Prefix/suffix settings, terminator handling, host formatting Inspect scanner output configuration and receiver parsing
Scanner reads but PLC does not receive data Network or serial fault, incorrect mapping, PLC communication setup Check interface status, configuration, data mapping, and connection diagnostics
PLC receives data but rejects part Wrong product, format mismatch, stale data, incorrect validation logic Inspect the exact decoded string and application rules
Repeated duplicate reads Continuous mode, trigger retriggering, missing deduplication Check trigger behavior, result acknowledgement, and application design
Communication drops after restart Incorrect network settings, connection recovery issue, device startup order Check address configuration, connection status, and recovery sequence
Good-read indication but traceability record missing Database or application failure, failed write, incorrect transaction logic Trace the result through the controller, application, and database

The scanner's diagnostic display or configuration software may expose useful values such as decode quality, exposure, image acquisition status, trigger count, read count, no-read count, and communication status. The available diagnostics vary by model.

15. Distinguishing Optical, Electrical, and Software Faults

Use evidence from each layer before deciding that the reader needs replacement.

Layer Evidence to collect Typical fault examples
Barcode or label Actual code image, print quality, marking condition Damaged label, poor contrast, incomplete marking
Optical setup Distance, focus, alignment, illumination Wrong mounting, glare, blocked lens
Scanner configuration Job, symbologies, trigger mode, result settings Wrong code type, incorrect trigger configuration
Electrical interface Supply, trigger input, output wiring Missing supply, broken trigger cable
Communication Link status, serial settings, protocol state Incorrect IP, framing mismatch, disconnected network
PLC integration Received bytes, mapped data, status bits Wrong tag mapping, buffer or handshake error
Application Expected identifier, validation, transaction result Incorrect part, format rejection, duplicate rule
Traceability system Record creation and transaction status Database unavailable, failed write, invalid transaction

A useful troubleshooting record includes the exact symptom, test condition, observed data, root cause, corrective action, and verification result. "Scanner checked OK" is not a diagnostic result unless the test and acceptance criteria are documented.

16. Practical Case: Scanner Reads Correctly but the PLC Rejects the Part

Assume the scanner successfully reads a code, but the PLC displays an invalid-part alarm.

A disciplined investigation would proceed as follows:

  1. Capture the exact string produced by the scanner.
  2. Compare it with the expected format and product identifier.
  3. Check whether the scanner adds a prefix, suffix, carriage return, line feed, or other delimiter.
  4. Verify that the receiving data buffer can hold the complete result.
  5. Check character encoding and whether leading zeros are preserved.
  6. Verify the PLC's string length and parsing logic.
  7. Confirm that the identifier is expected for the current order, recipe, or station.
  8. Verify whether the result belongs to the current trigger or a previous cycle.
  9. Correct the cause and test multiple valid and invalid identifiers.

If the scanner output is correct but the PLC's received string is different, focus on the communication and parsing layers. If the received string is correct but rejected, focus on the application's validation rules.

17. Practical Case: Intermittent No-Read on a Moving Part

A reader works when a part is stationary but fails during automatic production.

Possible causes include:

  • The part enters the field of view at a different position during movement.
  • Vibration changes the reader-to-target distance or angle.
  • The trigger occurs before the code is fully presented.
  • Motion blur reduces image quality.
  • Illumination produces glare at a particular angle.
  • The label is curved or partly obscured.
  • Exposure or acquisition timing is unsuitable for the production speed.
  • The trigger pulse or handshake is too short or incorrectly sequenced.

Investigate using actual production movement and representative parts. Check scanner diagnostics and, if supported, captured images from both successful and failed reads. Make changes within the manufacturer's documented operating limits and validate the result over repeated cycles.

18. Practical Case: Scanner Communication Lost After a Power Cycle

A reader communicates normally before shutdown but does not reconnect after a machine restart.

Check:

  1. Whether the scanner has completed startup and reports a healthy state.
  2. Whether its IP address or device name matches the approved configuration.
  3. Whether the PLC or PC is attempting the correct connection.
  4. Whether the industrial switch and cable link are healthy.
  5. Whether device startup order or connection timeout affects recovery.
  6. Whether the application retries a failed connection correctly.
  7. Whether the restored scanner configuration matches the approved version.

Do not resolve the issue by assigning an arbitrary address or changing network parameters without coordination. An address conflict can create intermittent failures that affect more than one device.

19. Barcode Scanner Replacement and Obsolescence

A replacement reader must satisfy the application's functional, optical, electrical, and communication requirements.

Check the following before approving a replacement:

  • Supported barcode symbologies and code formats.
  • Required reading distance and field of view.
  • Resolution and suitability for the smallest code.
  • Performance with the actual label or direct part marking.
  • Illumination, lens, focus, and accessory requirements.
  • Trigger input and output behavior.
  • Supply voltage and connector pinout.
  • Supported serial, Ethernet, or industrial protocol.
  • PLC data format and status mapping.
  • Configuration backup and restore compatibility.
  • Firmware and configuration software support.
  • Environmental and ingress protection requirements.
  • Approved mounting dimensions and replacement accessories.

A newer reader may offer better optical performance but require a different configuration tool, communication setup, or PLC integration. Treat it as a controlled engineering change if the substitution affects wiring, data format, software, safety, or validated process behavior.

20. Preventive Maintenance Checklist

Maintenance intervals should follow manufacturer guidance, operating environment, observed failure history, and site procedures.

  • Inspect the reader housing, lens, window, and illumination area.
  • Clean optical surfaces using an approved method.
  • Check the mounting bracket and fasteners for looseness.
  • Inspect cables, connectors, and strain relief.
  • Verify the reader's supply and communication status.
  • Check the target distance, orientation, and field of view.
  • Test representative good-quality production codes.
  • Check read-success and no-read diagnostics.
  • Verify trigger timing and the result-handshake sequence.
  • Confirm the decoded string is transferred intact.
  • Check that valid and invalid identifiers are handled correctly.
  • Review recurring no-read and communication faults.
  • Confirm the approved configuration backup is available.
  • Review spare-part availability and obsolescence status.
  • Record changes and perform a controlled functional verification.

Avoid changing multiple optical or communication parameters at once without recording the original values. Otherwise, a successful adjustment becomes difficult to reproduce and a failed adjustment difficult to reverse.

22. Machine Knowledge Base Acceptance Checklist

Before closing the barcode documentation topic, verify that:

  • Each reader has an identifiable tag, make, model, and location.
  • Supported symbologies and expected data formats are documented.
  • Optical mounting and trigger conditions are recorded.
  • Electrical supply and connector details are available.
  • Communication interface and configuration are documented.
  • PLC or PC data mapping and status handling are traceable.
  • Data validation and no-read behavior are understood.
  • Configuration backups and recovery procedures are accessible.
  • Troubleshooting checks cover optical, electrical, communication, and application faults.
  • Approved replacement parts and compatibility requirements are recorded.
  • Changes are controlled and verified under the relevant plant procedures.
