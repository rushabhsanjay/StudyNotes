1. Purpose of Industrial Network Documentation

Modern industrial machines connect PLCs, HMIs, drives, robots, CNC controllers, barcode scanners, printers, industrial PCs, remote I/O, cameras, and diagnostic systems through industrial communication networks. A machine may contain several separate networks with different protocols, addressing rules, performance requirements, and security boundaries.

The purpose of network documentation in a machine knowledge base is to make the installed network understandable, diagnosable, recoverable, and maintainable without relying on undocumented knowledge held by one engineer.

A complete network record should answer:

  • Which devices are connected to the machine network?
  • What is the IP address, subnet, device name, and communication protocol of each device?
  • Which switch, port, cable, and network segment connect each device?
  • Which devices communicate with one another, and for what purpose?
  • Where are the PLC, HMI, robot, CNC, drive, and engineering computer connections?
  • Which IP addresses are static, dynamically assigned, or reserved?
  • Which devices are safety-related or production-critical?
  • Where are the network configuration backups and approved topology drawings?
  • How can a network fault be isolated without disrupting unrelated equipment?

A network drawing without an IP list is incomplete. An IP list without physical connectivity and communication relationships is also incomplete. Both must be maintained together.

2. Industrial Network Architecture

A simplified machine network may contain several logical and physical layers.

Plant / Enterprise Systems
          ↓
Plant Industrial Network
          ↓
Managed Industrial Switch
          ↓
Machine Network
          ↓
PLC ─── HMI ─── Remote I/O
  │
  ├──── Robot Controller
  ├──── CNC Controller
  ├──── Drives and Motion Devices
  ├──── Barcode Scanner
  ├──── Industrial Printer
  └──── Industrial PC / Data Gateway

This is a conceptual example, not a recommended universal wiring arrangement. Actual machine networks may use multiple switches, separate VLANs, redundant paths, dedicated motion networks, serial links, or isolated safety communication.

The topology should reflect the installed system, not an idealized diagram.

A device's Ethernet port does not establish which protocol it supports. Ethernet is the communication medium and framing foundation for many technologies; protocols define how devices exchange and interpret data.

4. Essential Network Terminology

Subnet mask or prefix Defines the local IP network boundary Helps determine whether traffic is local or routed
Default gateway Router used to reach destinations outside the local subnet Required when communication must cross routed networks
MAC address Link-layer address of a network interface Useful for device identification and switch diagnostics
Hostname Human-readable device name Helps identify devices, subject to naming and resolution configuration
TCP Connection-oriented transport protocol Used by many configuration and application services
UDP Connectionless transport protocol Used by some industrial discovery, real-time, and application services

VLAN Logical separation of Ethernet traffic on managed infrastructure Supports segmentation and traffic control
Managed switch Switch with configurable monitoring and network features Provides port status, diagnostics, and sometimes VLAN or redundancy functions

A device can have a valid IP address and still be unreachable because of incorrect subnet configuration, duplicate addresses, VLAN separation, firewall rules, disabled ports, protocol incompatibility, or application-level faults.

5. IPv4 Addressing and Subnetting

Most industrial Ethernet devices use IPv4 addressing, although IPv6 may be present in some systems. Each interface must have a valid configuration for the network to which it is connected.

An IPv4 address contains 32 bits and is commonly written as four decimal octets, such as 192.168.10.25.

A typical configuration contains:

  • IP address.
  • Subnet mask or prefix length.
  • Default gateway, if routing is required.
  • DNS settings, if name resolution is required.
  • DHCP or static-address configuration.
  • Device hostname, where supported.

Example subnet

Consider this illustrative machine subnet:

  • Network: 192.168.10.0/24
  • Subnet mask: 255.255.255.0
  • Example PLC: 192.168.10.10
  • Example HMI: 192.168.10.20
  • Example robot: 192.168.10.30

For a conventional IPv4 /24 subnet, the network address is 192.168.10.0 and the broadcast address is 192.168.10.255. The usual assignable host range is 192.168.10.1 through 192.168.10.254, subject to the network's actual addressing policy.

These addresses are examples only. Never apply them to a production machine without checking the approved plant network plan.

Same-subnet communication

Devices within the same IPv4 subnet can normally exchange local traffic directly at Layer 2, provided that they are on compatible network segments and no relevant isolation or filtering prevents communication.

Devices in different subnets generally require routing for IP communication between them. A gateway setting alone does not create connectivity: the routing path and required access rules must also exist.

Static and dynamic addressing

Method Description Industrial considerations
Static configuration Address entered directly on the device Requires controlled records and duplicate-address prevention
DHCP Address and related settings assigned by a DHCP server Device identity and lease management must be understood
DHCP reservation Server assigns a planned address to a defined client identity Depends on server configuration and the device's network identity
Link-local addressing Device selects an address within a defined local range when supported Usually unsuitable as an assumed substitute for an approved machine addressing plan

Many PLCs, HMIs, robots, CNCs, and fixed industrial devices use static addressing. Other devices may use DHCP reservations or manufacturer-specific addressing methods.

Document the actual configuration and do not assume that a device always keeps the same address after a factory reset, firmware update, or controller replacement.

6. IP Address List: Master Register

The IP list should be a controlled record of every relevant network interface, not merely a list of equipment names.

Recommended fields include:

Field Information to record
Asset ID Unique machine or equipment identifier
Device name Recognizable device name
Device type PLC, HMI, robot, CNC, switch, scanner, printer, IPC, or other
Manufacturer and model Exact device make and model
Machine and station Physical machine, line, and station
Network interface Interface name, port, or module
IP address Assigned IPv4 or IPv6 address
Subnet or prefix Subnet mask or prefix length
Default gateway Configured gateway, if applicable
MAC address Interface MAC address where available
Hostname Configured hostname where relevant
Address method Static, DHCP, reservation, or other
VLAN or segment Approved logical network assignment
Protocols EtherNet/IP, PROFINET, TCP/IP, or other supported protocols
Connected switch and port Physical network connection
Communication peers Systems the device is expected to communicate with
Criticality Production, quality, safety-related, or support classification
Configuration backup Approved location of device settings
Change reference Change request, revision, and approval details

Use one record per network interface. A PLC may have several Ethernet interfaces with different purposes, and treating them as one device-level address can hide critical configuration differences.

For devices with multiple interfaces, record the relationship between each interface and its network segment.

7. IP Address Allocation Strategy

An approved addressing plan prevents collisions and makes troubleshooting faster.

A site may allocate addresses by machine, subnet, device category, or another controlled scheme. There is no universally correct address pattern for every plant.

An illustrative allocation scheme could be:

Device category Example address range Allocation principle
PLCs 192.168.10.10 to 192.168.10.29 Reserved for controller interfaces
HMIs 192.168.10.30 to 192.168.10.49 Reserved for operator interfaces
Robots and CNCs 192.168.10.50 to 192.168.10.79 Reserved for machine controllers
Scanners and printers 192.168.10.80 to 192.168.10.109 Reserved for identification devices
Industrial PCs 192.168.10.110 to 192.168.10.129 Reserved for local computing devices
Network infrastructure 192.168.10.200 to 192.168.10.219 Reserved for switches and infrastructure where appropriate

This example is only an illustration of the concept. It is not a recommendation to readdress an existing network. The real plant scheme may use separate subnets for each machine or device class.

Address allocation rules

  • Maintain a single approved source of truth.
  • Reserve addresses before commissioning a new device.
  • Check existing assignments before using an address.
  • Record the address method and the responsible administrator.
  • Keep production, engineering, and plant-level networks separated according to the approved design.
  • Document every address change and its dependencies.
  • Prevent unauthorized DHCP servers or unmanaged devices from entering production networks.
  • Keep an approved recovery method for devices whose addressing configuration is lost.

8. Duplicate IP Addresses

A duplicate IP occurs when more than one device on the relevant network segment uses the same address. It can cause intermittent or confusing failures because traffic may reach different devices depending on address resolution and network behavior.

Common symptoms include:

  • Communication works intermittently.
  • PLC or HMI connections drop unexpectedly.
  • A device appears online but responds incorrectly.
  • Diagnostic tools show an unexpected MAC address for an IP.
  • An address-conflict warning appears on a device or computer.
  • A recently connected replacement device disrupts an existing machine.

Investigation approach

  1. Identify the affected IP address and devices expected to use it.
  2. Check the approved IP register.
  3. Compare observed MAC addresses with documented interface MAC addresses.
  4. Inspect switch and device diagnostics using approved tools.
  5. Identify whether a replacement, laptop, DHCP assignment, or configuration change introduced the conflict.
  6. Coordinate correction with the network owner.
  7. Verify that the correct device is reachable and that all required machine communications recover.

Do not simply change an address at random. The address may be referenced in PLC hardware configuration, HMI settings, robot communication tables, printer jobs, SCADA connections, or other systems.

9. Physical Network Topology

Physical topology describes how network devices are connected by cables, switches, ports, and other physical links.

Common patterns include:

  • Star: Devices connect to a central switch.
  • Line or daisy chain: Devices connect in sequence where the equipment and protocol support it.
  • Ring: Devices form a ring, often with a supported redundancy mechanism.
  • Redundant paths: Devices have multiple network paths designed to preserve connectivity after selected failures.
  • Hybrid: A combination of multiple topologies.

A topology diagram should match the actual installed arrangement and identify relevant switch ports, cable IDs, and redundant paths.

Example physical topology

Plant Network Uplink
        |
   SW-MACHINE-01
        |
        +---- Port 1: PLC-01
        |
        +---- Port 2: HMI-01
        |
        +---- Port 3: ROBOT-01
        |
        +---- Port 4: CNC-01
        |
        +---- Port 5: SCANNER-01
        |
        +---- Port 6: IPC-01

This is a simple star-topology example. A real machine may contain multiple switches, managed uplinks, separate motion networks, redundant connections, or isolated interfaces. Document all relevant paths rather than forcing the network into a simplified drawing.

Cable and port register

Record the following for each physical connection:

  • Cable ID.
  • Source device and interface.
  • Source switch and port.
  • Destination device and interface.
  • Destination switch and port, if applicable.
  • Cable type and category where relevant.
  • Connector type.
  • Approximate route or cabinet location.
  • Link speed and duplex where relevant.
  • VLAN or logical segment where applicable.
  • Redundancy role, if present.
  • Label and drawing reference.

Cable identification is especially useful when multiple Ethernet cables enter the same control cabinet. A correct IP list cannot tell a technician which physical cable to inspect.

10. Logical Network Topology

Logical topology describes how devices communicate, regardless of their physical cable arrangement.

It should show:

  • IP subnets and VLANs.
  • Routing boundaries and gateways.
  • PLC-to-HMI communication.
  • PLC-to-robot or PLC-to-CNC communication.
  • PLC-to-drive and remote-I/O communication.
  • Scanner and printer data paths.
  • Engineering workstation access.
  • SCADA, historian, MES, and other plant-system connections.
  • Firewalls and approved security boundaries.
  • Redundant communication paths and network dependencies.

Two devices may be connected to the same physical switch but separated by VLANs. Conversely, two devices may communicate through several switches and a router while belonging to different subnets.

Document physical and logical topology separately when a single drawing would become difficult to read.

Communication matrix

An IP list tells you where devices are addressed. A communication matrix tells you what communication is expected.

Source Destination Purpose Protocol or interface
PLC-01 HMI-01 Operator data and machine status Approved controller communication
PLC-01 ROBOT-01 Robot commands and status Supported industrial protocol
PLC-01 SCANNER-01 Trigger, decode status, and result data Model-specific interface
IPC-01 PRINTER-01 Label jobs and printer status Supported print interface
IPC-01 SCADA-SERVER Production data collection Approved application protocol
ENG-PC-01 PLC-01 Programming and diagnostics Vendor engineering protocol

These are illustrative relationships. Record only communication paths that actually exist and are authorized on the machine.

For each critical connection, document the endpoint addresses, purpose, protocol, direction of initiation, required ports where applicable, and diagnostic method. Avoid opening broad network access simply to make an unverified connection work.

11. Industrial Ethernet Switches

A switch connects devices within an Ethernet network. Industrial managed switches may provide diagnostics and configuration capabilities that are important for production availability.

Switch documentation

Record:

  • Manufacturer and exact model.
  • Serial number and firmware where available.
  • Management IP address, if configured.
  • MAC address and hostname, if used.
  • Port count and port numbering.
  • Device and cable connected to each port.
  • Link speed and duplex where relevant.
  • VLAN configuration.
  • Redundancy protocol and ring configuration where used.
  • Port mirroring or diagnostic configuration where approved.
  • Management access method and authorized ownership.
  • Configuration backup location.
  • Power supply and redundant power arrangement where fitted.
  • Cabinet location and environmental conditions.

A switch may operate without an IP address if it is unmanaged or if its management interface is not configured. Do not confuse a switch's management address with the addresses of devices connected to it.

Managed versus unmanaged switches

Feature Unmanaged switch Managed switch
Basic Ethernet forwarding Yes Yes
Port-level diagnostics Limited or absent Typically more extensive
VLAN configuration Generally unavailable Supported on applicable models
Redundancy configuration Model-dependent, often limited Available on supported models
Configuration backup Usually not applicable Available on many models
Traffic monitoring Limited May include statistics, mirroring, and diagnostic features

Use the installed switch's manual to establish supported functions. A managed switch is not automatically configured correctly simply because it is capable of advanced features.

12. Industrial Network Protocol Awareness

Industrial protocols differ in data models, timing, configuration, and diagnostic behavior.

Protocol Typical application Key documentation item
EtherNet/IP Controller and device communication Device configuration, connection data, and supported assemblies
PROFINET Controller and distributed device communication Device name, device description file, and module mapping
Modbus TCP Register-based industrial data exchange Register map, addressing, data types, and byte order
OPC UA Structured data exchange between compatible systems Endpoint, certificates, security policy, and namespace mapping
EtherCAT Real-time communication for supported automation and motion systems Network order, device configuration, and timing requirements
MQTT Publish/subscribe data exchange for supported monitoring architectures Broker, topic design, authentication, and data format
PROFIBUS DP Fieldbus communication with distributed devices Bus address, configuration, and segment details
DeviceNet CAN-based industrial device communication Node address, network rate, and configuration

This is not a protocol-selection guide. The machine's hardware and validated control design determine which protocol is used.

Device description files

Industrial devices may require vendor-supplied configuration files, such as:

  • GSD or GSDML for supported PROFIBUS or PROFINET devices.
  • EDS files for supported EtherNet/IP or DeviceNet devices.
  • ESI files for EtherCAT devices.
  • IODD files for IO-Link devices.

Record the file name, version, device model, software compatibility, and approved storage location where these files are required. Using the wrong device description file can cause incorrect configuration or prevent the engineering software from representing the installed device properly.

13. Network Configuration Backups

Network recovery may require backups from multiple components, not just the PLC.

Potential configuration items include:

  • Managed switch configurations.
  • Router and firewall settings under the responsible network team's controls.
  • PLC Ethernet interface settings.
  • HMI network and communication settings.
  • Robot and CNC network settings.
  • Scanner and printer network configurations.
  • Industrial PC adapter and application settings.
  • VLAN, routing, redundancy, and addressing records.
  • Device description files and engineering project dependencies.

Backup control

For every backup, record:

  • Device ID and model.
  • Firmware or software version.
  • Backup date and revision.
  • Source device or interface.
  • Approved file location.
  • Change reference and responsible person or team.
  • Known dependencies.
  • Restore procedure and verification requirements.

Do not assume that a screenshot is an adequate configuration backup. A screenshot may help with documentation but generally cannot restore a device configuration.

Some network devices contain credentials, certificates, keys, or other sensitive settings. Store these using the approved secure method and do not place passwords or private keys in an ordinary IP list.

14. Network Troubleshooting Method

Troubleshoot from the simplest observable facts toward the more complex communication layers. Confirm the symptom before changing configuration.

Step 1: Identify the scope

Determine whether the failure affects:

  • One device.
  • One network link.
  • Several devices on one switch.
  • An entire machine subnet.
  • Communication between subnets.
  • One protocol or application while other communication remains healthy.

This helps distinguish a local cable or device fault from a wider network issue.

Step 2: Check physical connectivity

Inspect the link indicators, cable condition, connector seating, switch port status, and approved network diagnostics. Check whether the expected port is enabled and whether its link state matches the device's operating state.

Do not unplug random cables to see what happens. On an industrial machine, that is an impressively efficient way to create a second fault while investigating the first.

Step 3: Verify addressing

Compare the actual IP address, subnet, gateway, and address method with the approved register. Check for duplicate addresses and incorrect network-segment assignments.

Step 4: Test basic reachability

Where authorized, use appropriate diagnostic tools such as:

  • ipconfig or ip addr to inspect local interface configuration.
  • ping to test basic IP reachability where ICMP is permitted.
  • arp -a to inspect IPv4-to-MAC mappings on the local host.
  • tracert or traceroute to examine a routed path where supported.
  • Manufacturer engineering software to inspect device-specific communication status.

A successful ping does not prove that the industrial application or protocol is functioning. A failed ping also does not prove that the device is offline because ICMP may be disabled or filtered.

Step 5: Verify the protocol and application

If basic reachability exists, check the required protocol, service, connection state, data mapping, device configuration, and application diagnostics.

A printer may respond to network diagnostics while its print queue is paused. A PLC may be reachable while an HMI data connection is misconfigured. A scanner may be online while its trigger and result exchange is broken.

Step 6: Verify recovery

After correcting the root cause, verify the expected communication and production behavior. Record the actual cause, corrective action, test conditions, and result.

15. Common Network Faults and Diagnostic Checks

Symptom Possible cause Diagnostic approach
Device unreachable Power, cable, switch port, address, or device fault Check power, link status, addressing, and device diagnostics
Intermittent communication Loose connection, duplicate IP, EMI, congestion, or device instability Review link events, address mappings, error counters, and fault timing
Ping works but PLC communication fails Protocol configuration, connection limits, service filtering, or application fault Check protocol-specific diagnostics and controller configuration
HMI loses PLC data Wrong address, driver configuration, controller state, or communication path Verify endpoint settings and HMI/PLC diagnostics
Robot communication fails Incorrect endpoint, protocol mapping, controller state, or interface configuration Check the approved robot-to-PLC interface and device status
Scanner online but data missing Trigger, protocol, data mapping, or handshake fault Inspect trigger status, decode status, and received data
Printer reachable but jobs fail Print service, queue, driver, command language, or application issue Check the print queue, job format, and printer diagnostics
Several devices fail together Shared switch, uplink, power supply, or network configuration issue Inspect common infrastructure and recent changes
Communication fails across subnets Gateway, routing, ACL, firewall, or return-path issue Verify the approved routed path and access rules
Device has unexpected IP DHCP assignment, reset, configuration change, or duplicate device Check the IP register, address source, and change history
Network slows during production Excessive traffic, faulty device, broadcast issue, or topology problem Review switch counters and authorized network monitoring
Connection fails after restart Startup order, address recovery, connection timeout, or service failure Review startup diagnostics and recovery behavior
Redundant path fails to recover Redundancy misconfiguration, unsupported topology, or physical fault Check the documented redundancy design and switch diagnostics

Root-cause documentation

A useful fault report records:

  • Time and machine operating condition.
  • Devices and communication paths affected.
  • Exact alarms or diagnostic messages.
  • Physical link and addressing observations.
  • Relevant switch or controller diagnostics.
  • Recent configuration or hardware changes.
  • Root cause, not merely the symptom.
  • Corrective action and verification results.
  • Preventive action where a recurring risk exists.

"Network problem" is a symptom category, not a root cause. Narrow it to the actual failed component, configuration, link, or communication dependency.

16. Network Segmentation and Cybersecurity

Industrial networks should be designed and maintained to limit unnecessary communication and reduce the consequences of a compromised or misconfigured device.

Important practices include:

  • Separate networks according to the approved industrial architecture.
  • Control communication between machine, plant, engineering, and enterprise systems.
  • Use approved firewalls and access rules at defined boundaries.
  • Restrict engineering access to authorized systems and personnel.
  • Avoid connecting unknown laptops, USB Ethernet adapters, wireless access points, or unmanaged switches to production networks.
  • Maintain supported firmware and configuration backups under change control.
  • Remove obsolete access paths according to the site's approved process.
  • Monitor network changes and relevant device events.
  • Protect credentials, certificates, and configuration files.
  • Follow the site's incident-response and recovery procedures.

VLANs provide logical segmentation, but a VLAN alone is not a complete security boundary. Appropriate routing controls, access rules, management protections, and architecture are also important.

Do not disable a firewall, bypass an access control, or connect a machine network directly to a corporate or public network merely to test connectivity. Use approved diagnostic paths and involve the network owner when required.

17. Network Changes and Change Management

Even a seemingly minor network change can interrupt multiple systems. A new address may affect PLC hardware configuration, HMI drivers, robot connections, printer queues, SCADA tags, and engineering access.

Before a change, document:

  • The reason and scope of the change.
  • The affected devices, interfaces, and communication paths.
  • Current and proposed configuration.
  • Dependencies and expected production impact.
  • Required approvals and outage window.
  • Backup and rollback procedure.
  • Test plan and acceptance criteria.
  • Responsible person or team.

After the change:

  1. Verify the new configuration against the approved plan.
  2. Confirm required communication paths.
  3. Test relevant machine sequences and data exchanges.
  4. Check for duplicate addresses or unexpected device behavior.
  5. Update the IP list, topology, and configuration backups.
  6. Record the change reference and verification results.

A change is not complete until the documentation matches the installed network.

18. Industrial PC and Engineering Access

Industrial PCs may host HMI applications, SCADA clients, label software, robot interfaces, data gateways, or vendor engineering tools. They may have multiple network adapters for separate functions.

Record each interface independently:

  • Adapter name and hardware identity.
  • IP address and subnet.
  • Gateway and DNS settings where applicable.
  • Physical connection and switch port.
  • Network purpose.
  • Software services and communication dependencies.
  • Approved remote-access method.
  • Relevant firewall or endpoint controls.
  • Backup and recovery requirements.

Do not bridge two networks or enable Internet Connection Sharing without authorization. A dual-homed industrial PC can unintentionally create a path between otherwise separated networks.

Engineering access should be controlled and documented. Record which tools and routes are approved for PLC, robot, CNC, HMI, drive, and network-device diagnostics.

19. Network Reliability and Redundancy

Some industrial networks use redundant switches, ring protocols, dual network interfaces, redundant controllers, or alternate communication paths to reduce downtime.

The documentation should identify:

  • Which devices and links are redundant.
  • The supported redundancy protocol or mechanism.
  • The primary and alternate paths.
  • Expected behavior after a link or switch failure.
  • Which failures are not covered by redundancy.
  • Configuration dependencies and compatibility requirements.
  • Approved test method and maintenance restrictions.
  • Recovery and verification procedure.

Redundancy does not mean that every failure is automatically tolerated. A dual cable may not provide meaningful protection if both cables depend on the same switch, power supply, or physical route.

Do not test redundancy by disconnecting live production links without an approved procedure and appropriate authorization. Validate the documented design through controlled tests or existing diagnostic evidence.

20. Network Obsolescence and Spare Strategy

Network components can become difficult to maintain when manufacturers discontinue switch models, interface modules, firmware support, or engineering tools.

For each critical component, document:

  • Manufacturer and exact model.
  • Hardware revision and firmware.
  • Supported protocols and relevant capabilities.
  • Power supply and mounting requirements.
  • Port count, port type, and speed.
  • VLAN, redundancy, and management requirements.
  • Approved successor or replacement model.
  • Configuration migration requirements.
  • Device description files and engineering software dependencies.
  • Availability of a compatible spare.
  • Validation required before replacement.

A replacement switch with the same number of ports may still differ in VLAN behavior, redundancy support, firmware compatibility, or industrial protocol requirements. Treat changes as engineering changes when they can affect validated machine communication.

22. Practical Case: PLC Reachable but HMI Shows Communication Error

Suppose a PLC responds to a basic reachability test, but the HMI reports that controller data is unavailable.

Investigate in this order:

  1. Confirm the PLC and HMI IP addresses and subnet configurations.
  2. Verify that both devices are connected to the intended network segments.
  3. Confirm the HMI is configured with the correct PLC address and controller path.
  4. Check the controller communication driver and required protocol.
  5. Review HMI and PLC diagnostics for connection or session errors.
  6. Check switch port status and relevant network access controls.
  7. Verify that the PLC is in the expected operating state and that the required interface is enabled.
  8. Confirm that the HMI can read the required data after the fault is corrected.

A successful ping confirms only a limited form of IP reachability. It does not establish that the required PLC application connection is configured correctly or that the HMI can read its tags.

23. Practical Case: Several Devices Fail at the Same Time

Suppose the PLC loses communication with a robot, scanner, and printer within the same minute.

Instead of immediately investigating three unrelated devices, identify shared dependencies:

  • Common switch or uplink.
  • Shared network power supply.
  • Cable or port changes during maintenance.
  • Network loop or topology change.
  • Address conflict or unintended DHCP activity.
  • VLAN or switch configuration change.
  • Shared industrial PC or gateway.
  • Common controller or application event.

Compare fault timestamps and network diagnostics. If the devices share an infrastructure component, investigate that common dependency first. Restore the approved network configuration and verify each affected communication path individually.

24. Network Maintenance Checklist

  • Verify the IP register matches the installed devices.
  • Confirm network topology drawings reflect the actual connections.
  • Check switch, uplink, and relevant device link status.
  • Inspect accessible network cables, connectors, and labels.
  • Review recurring communication faults and device diagnostics.
  • Confirm approved switch and device configuration backups exist.
  • Verify device addresses and allocation records after approved changes.
  • Review critical network components for obsolescence.
  • Confirm redundant links and recovery arrangements are documented.
  • Check that unauthorized devices or connections have not been introduced.
  • Verify engineering access follows plant controls.
  • Update the IP register, topology, and change log after modifications.

Routine checks should be selected according to the machine's criticality, network design, failure history, and site maintenance requirements.

25. Machine Knowledge Base Acceptance Checklist

The network documentation is complete when a technician can identify the installed network, locate devices and cables, verify expected communication, and recover from a documented failure without guessing.

  • Every relevant device and network interface is identified.
  • IP addresses, subnet masks, gateways, and address methods are recorded.
  • Device names, MAC addresses, and VLAN assignments are recorded where applicable.
  • Physical topology identifies switches, ports, cables, and uplinks.
  • Logical topology shows relevant communication relationships and network boundaries.
  • PLC, HMI, robot, CNC, drive, scanner, printer, and IPC dependencies are documented.
  • Critical protocols and device configuration dependencies are identified.
  • Network-device configuration backups are accessible through approved procedures.
  • Troubleshooting procedures distinguish physical, addressing, protocol, and application faults.
  • Security boundaries and engineering access arrangements are documented.
  • Critical switches and network components have an obsolescence and spare strategy.
  • Network changes are controlled, verified, and reflected in the documentation.
