1. Purpose of HMI Documentation

A Human-Machine Interface (HMI) is the operator-facing interface used to monitor machine conditions, issue permitted commands, view alarms, acknowledge faults, and interact with the automated process.

In a machine knowledge base, HMI documentation records the available screens, their purpose, navigation structure, displayed parameters, operator controls, alarm behavior, and relationships with the PLC or other control systems.

The objective is not merely to document what the screen looks like. It is to establish what each screen allows the operator to observe or command, what conditions the screen represents, and how the interface supports troubleshooting.

For industrial maintenance, HMI documentation helps with:

  • Understanding the machine's operating sequence.
  • Identifying the correct screen for a fault or abnormal condition.
  • Tracing displayed alarms to PLC tags, drive diagnostics, or field devices.
  • Recovering from faults using approved operating procedures.
  • Identifying obsolete screens, unused controls, and misleading indications.
  • Supporting HMI replacement, migration, and software backups.
  • Preventing unauthorized changes to machine parameters.
  • Maintaining consistent operator information across shifts.

Core principle: An HMI displays information and provides an interface to the control system. It is not necessarily the source of the machine's control logic, and an HMI indication alone does not prove that the physical equipment is in the displayed condition.

2. HMI Architecture and Data Flow

A typical industrial HMI communicates with a PLC or another controller to obtain process data and issue authorized operator commands.

Physical Machine
      ↓
Sensors, Switches, Drives, Actuators
      ↓
PLC / Controller
      ↓
Communication Network
      ↓
HMI Runtime
      ↓
Screens, Status, Trends, Alarms
      ↓
Operator Command
      ↓
HMI Tag / Command Interface
      ↓
PLC Logic and Permissive Checks
      ↓
Machine Response

The architecture varies by application. An HMI may communicate directly with a PLC, through an industrial gateway, or with a SCADA or supervisory system.

The HMI usually does not directly energize a motor simply because an operator presses a screen button. The command is processed by the control system, which must apply the appropriate operating conditions and interlocks.

Safety-related functions must use the designed safety system. A normal HMI button or software alarm is not a substitute for a safety-rated device or function.

3. HMI Versus Related Systems

System Primary role Example
HMI Operator interaction with a machine Start request, status display, alarm screen
PLC Executes control logic and manages I/O Sequence control, interlocks, actuator commands
SCADA Supervisory monitoring across equipment or processes Plant-wide alarms and production trends
Historian Stores process data over time Temperature and pressure history
MES Manages manufacturing operations Production orders and traceability
Safety PLC Executes safety-related logic according to its design Safety interlocks and monitored safety functions
Drive keypad or software Local configuration, diagnostics, and control where permitted VFD fault code and parameter display

An HMI can be integrated into a SCADA system, but the terms are not interchangeable.

4. HMI Identification and Configuration

The knowledge base should identify each HMI instance installed on the machine.

4.1 HMI identity fields

Field What to record

Manufacturer Siemens, Mitsubishi, Rockwell Automation, or another manufacturer
Model Exact installed panel or industrial PC model
Serial number Equipment identity, where available
Location Main cabinet, operator station, remote station, or other location
Display size Screen size and resolution, if relevant

Examples of common HMI platforms include Siemens WinCC, Mitsubishi GOT with GT Designer, and Rockwell Automation PanelView with FactoryTalk View. Exact product families, versions, and supported features must be recorded from the installed system.

4.2 Why exact model and software versions matter

Two HMIs from the same manufacturer may differ in:

  • Display resolution and supported graphics.
  • Communication drivers.
  • Firmware compatibility.
  • Runtime capabilities.
  • Supported security features.
  • Available engineering software.
  • Backup and restore procedures.
  • Supported operating systems for PC-based HMIs.

Never assume that a project can be transferred directly between two HMI models simply because both belong to the same product family.

6. Screen Navigation and Operator Workflow

Screen navigation describes how operators move between pages and access machine functions.

Document:

  • The home screen and its normal entry point.
  • Navigation buttons and their destinations.
  • How alarms lead to relevant diagnostic screens.
  • How operators select automatic or manual operation.
  • Where approved parameter or recipe changes are performed.
  • Which actions require elevated authorization.
  • Whether a screen is available only in a particular machine mode.
  • How the interface behaves when PLC communication is lost.

A useful navigation record should explain both the destination and its operational purpose.

For example, an alarm summary might allow the operator to select a fault and navigate to the related subsystem diagnostic screen. That diagnostic screen may display the sensor state, actuator feedback, or drive status needed to investigate the condition.

The HMI should not be documented as if navigation alone confirms a fault's root cause. The displayed information must be interpreted alongside PLC logic, electrical drawings, and actual machine conditions.

7. HMI Tags and Data Binding

An HMI tag connects an on-screen object to a data item, such as a PLC variable, internal HMI variable, or process value.

7.1 Common tag types

Tag type Example Purpose
Boolean Machine_Ready Represents a true/false condition
Integer Current_Step Represents a sequence step or count
Real or floating-point Measured_Pressure Represents a continuous numerical value
String Active_Recipe_Name Displays text
Enumeration or coded state Machine_Mode Represents a state selected from defined values
Internal HMI tag Selected_Screen Stores an HMI-side value
Command tag Start_Request Requests an action through the control system
Alarm tag or expression Guard_Open_Alarm Represents a condition associated with an alarm

Exact tag behavior depends on the platform and application design.

7.2 HMI tag documentation

For important tags, record:

  • HMI tag name.
  • PLC tag or source address.
  • Data type.
  • Read or write behavior.
  • Engineering units.
  • Display scaling.
  • Valid operating range.
  • Associated screen or object.
  • Alarm or command relationship.
  • Communication status behavior.

Example:

HMI tag Source Type Use Access
Machine_Ready PLC status tag Boolean Shows readiness Read-only
Current_Step PLC sequence tag Integer Displays current sequence step Read-only
Pressure_PV PLC analog tag Real Displays measured pressure Read-only
Start_Request PLC command interface Boolean Requests automatic cycle start Restricted command

These names are illustrative and do not imply a particular PLC address.

7.3 Scaling and engineering units

An HMI may display a raw PLC value in engineering units. The conversion may occur in the PLC, the HMI, a communication driver, or a combination of these.

For example, an analog input might represent a pressure transmitter's signal. The displayed pressure must use the correct scaling, units, decimal precision, and valid range.

Incorrect scaling can produce a convincing but false value. A display showing 120.0 bar is not useful if the actual instrument range is 0 to 10 bar.

Document where the scaling is implemented and verify it against the approved instrumentation and PLC documentation.

8. HMI Commands and Operating Modes

HMI commands can affect real machinery, so their behavior must be documented carefully.

8.1 Common commands

  • Start or cycle-start request.
  • Stop request.
  • Reset request.
  • Manual jog command.
  • Actuator extend or retract request.
  • Recipe selection.
  • Parameter entry.
  • Maintenance counter reset.
  • Mode selection.
  • Alarm acknowledgment.

The actual command set depends on the machine's design.

8.2 Command versus physical action

A command is a request. It is not proof that the requested action occurred.

For example, pressing a cylinder-extend button may set a PLC request bit. The PLC may reject the request because:

  • The machine is not in manual mode.
  • Another motion is in progress.
  • The required permissive is absent.
  • A process interlock is active.
  • A fault prevents the motion.
  • The actuator's safety conditions are not satisfied.

The HMI should ideally distinguish between the command request, the PLC's acceptance of that request, and the physical feedback indicating that the action occurred.

8.3 Document command behavior

Item What to record
Command name Operator-visible function
Command tag PLC or HMI tag receiving the request
Preconditions Required mode, permissives, and interlocks
Expected response Expected machine or controller behavior
Feedback Tag or device state confirming the response
Timeout behavior Expected response if feedback is not received
Access level Authorized operator or maintenance role
Reset or recovery Approved recovery procedure
Safety dependency Relevant safety function or interlock reference

Safety-critical functions must be implemented and validated according to the applicable safety design. HMI access controls and screen logic alone are not safety measures.

9. Alarm Management Fundamentals

An alarm indicates an abnormal condition that requires operator attention or action. An event records something that happened, whether or not operator intervention is required.

These concepts should be separated in the machine knowledge base.

9.1 Alarm versus event versus status

Item Meaning Example
Alarm Abnormal condition requiring attention Low hydraulic pressure
Event Recorded occurrence or action Recipe selected
Status Current operating condition Automatic mode active
Warning Condition requiring awareness or planned attention Filter service approaching
Trip or fault Condition that has stopped or inhibited equipment Drive overcurrent fault

A trip may also generate an alarm. The categories describe different aspects of the event and may overlap according to the application's design.

9.2 Alarm lifecycle

A common alarm lifecycle is:

Normal Condition
      ↓
Alarm Condition Becomes True
      ↓
Alarm Becomes Active
      ↓
Operator Investigates
      ↓
Cause Is Corrected
      ↓
Alarm Condition Clears
      ↓
Acknowledgment or Reset, as Designed
      ↓
Normal Operation Permitted When Conditions Are Satisfied

The exact sequence depends on the HMI and controller configuration. Some systems allow acknowledgment while an alarm remains active. Others latch the alarm or require a separate reset after the initiating condition has cleared.

Acknowledging an alarm does not necessarily clear the condition, reset a drive, or make the machine safe to restart.

10. Alarm List and Alarm Record Structure

A structured alarm register is one of the most valuable HMI records.

10.1 Alarm register fields

Field Purpose
Alarm ID Stable identifier
Alarm text Message displayed to the operator
Alarm source PLC tag, device diagnostic, or application logic
Trigger condition Condition that activates the alarm
Severity or priority Relative urgency according to the approved scheme
Machine subsystem Area or equipment affected
Operator response Immediate approved response
Diagnostic guidance Safe checks that help locate the cause
Recovery condition Condition required for clearing or recovery
Acknowledgment behavior Whether and when acknowledgment is required
Latching behavior Whether the alarm remains active after the trigger clears
Related PLC tag Controller signal associated with the alarm
Related screen Screen providing useful diagnostic information
Related procedure Approved troubleshooting or recovery instruction
Alarm history retention Configured retention behavior, if known

Alarm IDs should remain stable across screen changes and application revisions wherever possible. Stable IDs make fault analysis, shift handover, and historical comparison much easier.

10.2 Alarm message quality

A useful alarm message tells the operator what is wrong and, where practical, identifies the affected subsystem.

Weak alarm text:

  • Error
  • Fault 12
  • Not OK
  • Sequence Failed

More useful alarm text:

  • Hydraulic Pressure Below Minimum
  • Robot Controller Communication Lost
  • Clamp Closed Feedback Not Received
  • Spindle Drive Overtemperature
  • Remote I/O Station 03 Communication Fault

Alarm text should be concise and consistent with the actual detection logic. Do not claim that a component has failed if the controller only knows that its expected feedback was not received.

For example, Clamp Closed Feedback Not Received is often more accurate than Clamp Sensor Failed, because the missing feedback could result from wiring, sensor power, mechanical movement, PLC input issues, or another cause.

11. Alarm Priority and Response

Alarm priority should reflect the consequence of the condition and the urgency of the required response. The machine's approved alarm philosophy should define the levels and their meanings.

An illustrative scheme is:

Priority General meaning Example
Critical Immediate action according to the defined emergency or safety procedure A condition associated with an immediate hazardous situation
High Significant process interruption requiring prompt attention Machine drive fault stopping the production cycle
Medium Abnormal condition requiring investigation or corrective action A subsystem fault that prevents a particular operation
Low Advisory or maintenance attention Service interval approaching

These are illustrative categories, not a universal standard. Safety-related conditions must be handled by the designed safety system and applicable procedures, not by assigning a color or priority to an HMI message.

11.1 Alarm flood

An alarm flood occurs when many alarms appear within a short period, making it difficult to identify the initiating fault.

For example, loss of one remote I/O network connection may cause several downstream alarms:

  • Remote I/O communication lost.
  • Sensor feedback unavailable.
  • Actuator confirmation missing.
  • Automatic sequence timeout.
  • Production cycle aborted.

The first alarm may identify the initiating condition, while the remaining alarms may be consequences. However, timestamps and ordering alone do not prove causality.

Document alarm dependencies and investigate the originating fault before treating every secondary alarm as an independent component failure.

12. Alarm Acknowledgment, Reset, and Clearing

These actions are distinct.

Action Meaning
Acknowledge Records that an operator has recognized an alarm
Clear The alarm's activation condition is no longer present, according to the configured logic
Reset Requests a defined recovery or fault-reset operation
Silence Stops or mutes an audible notification where supported
Inhibit or suppress Prevents an alarm from being presented under an authorized configuration

The exact behavior must be verified in the actual application.

An alarm can be acknowledged while its condition remains active. A reset may be rejected if the initiating condition has not cleared. Silencing an audible signal does not remove the abnormal condition.

Alarm inhibition and suppression must be controlled and documented because they can conceal important process conditions.

13. Alarm Troubleshooting Workflow

A practical alarm investigation should connect the HMI message to the controller signal, physical device, and machine sequence.

  1. Record the exact alarm text, alarm ID, timestamp, and machine state.
  2. Determine whether the alarm is active, acknowledged, cleared, or latched.
  3. Open the associated diagnostic screen and identify the affected subsystem.
  4. Check the relevant PLC tag and diagnostic information using approved access.
  5. Compare the indicated condition with the actual machine condition.
  6. Consult the electrical schematic, I/O list, drive documentation, or process record as applicable.
  7. Follow the approved fault-finding and isolation procedure.
  8. Correct the verified cause rather than repeatedly resetting the alarm.
  9. Verify the feedback and operating conditions required for recovery.
  10. Confirm that the machine returns to the intended state.
  11. Record the root cause, corrective action, and any recurring symptom.

Do not bypass an interlock or safety function merely to make an alarm disappear. A quiet HMI is not the same thing as a healthy machine.

14. Trends and Historical Data

HMI trend screens show how process values change over time. They can help identify gradual degradation, unstable control, intermittent failures, and abnormal operating patterns.

Common trend variables include:

  • Hydraulic and pneumatic pressure.
  • Temperature.
  • Motor current.
  • Spindle speed.
  • Cycle time.
  • Axis position.
  • Torque or force.
  • Flow rate.
  • Analog sensor values.

For each important trend, record the tag source, engineering units, sampling or update behavior, time range, retention configuration, and relevant operating limits.

14.1 Trend interpretation

A trend may reveal:

  • Pressure declining before a low-pressure alarm.
  • Temperature rising over several production cycles.
  • Motor current increasing under comparable operating conditions.
  • Cycle time increasing because of a slower operation.
  • Intermittent feedback loss.

Trends provide evidence, not automatic proof of root cause. Compare data with production conditions, sensor calibration, operating mode, and the actual sequence.

14.2 Sampling and timestamps

A trend may appear smooth while missing short-lived events if the acquisition rate is too slow. Communication interruptions can also create gaps or stale values.

Document whether timestamps originate from the HMI, PLC, server, or another source. Time synchronization matters when comparing alarms with PLC logs, drive histories, or SCADA records.

15. HMI Communication and Data Quality

An HMI can display incorrect, stale, or unavailable data when communication or data binding is faulty.

Important conditions to document include:

  • PLC communication loss.
  • Invalid or unavailable tag values.
  • Stale data.
  • Driver or protocol errors.
  • Incorrect IP address or device identity.
  • Mismatched data types or addresses.
  • Unsupported firmware or driver combinations.
  • Incorrect scaling or engineering units.
  • Time synchronization problems.

The application should make communication failure distinguishable from a valid process value wherever practicable.

For example, a pressure display retaining its last valid value after communication is lost can mislead an operator into believing the pressure is still current. The communication status and data freshness behavior must be understood.

Do not assume that a frozen display means the physical process has stopped changing.

16. User Access and Change Control

HMI applications may provide different levels of access for operators, maintenance technicians, engineers, and administrators.

Document the actual roles and permitted actions.

Role Typical access pattern
Operator Monitoring, routine commands, permitted alarm acknowledgment
Maintenance technician Diagnostics and approved maintenance functions
Controls engineer Authorized engineering and configuration functions
Administrator User management and system administration where applicable

This table is a general model. Actual permissions must match the plant's approved access-control design.

Good practice includes:

  • Using individual accounts where supported.
  • Applying least-privilege access.
  • Restricting engineering changes.
  • Protecting credentials.
  • Recording parameter and application changes.
  • Backing up the approved project before authorized modifications.
  • Validating the modified application before release.
  • Maintaining a rollback path.
  • Recording the installed version and responsible approver.

A password-protected screen is not a substitute for electrical isolation or machine safeguarding.

17. HMI Backup and Restoration

An HMI backup should preserve the information needed to recover the approved application and return it to service.

Depending on the platform, the backup may need to include:

  • Editable engineering project.
  • Runtime application.
  • HMI firmware or compatibility information.
  • Device configuration.
  • Communication driver configuration.
  • Tag and alarm configuration.
  • Recipes and approved parameter sets.
  • User and role configuration, where permitted.
  • Fonts, graphics, scripts, and external dependencies.
  • Version and change records.

A runtime upload may not recover the complete editable project. Some platforms restrict reverse transfer or omit engineering-only objects.

17.1 Backup verification

  • Confirm the exact HMI model and firmware.
  • Identify the engineering software and version.
  • Save the approved editable project where available.
  • Preserve required dependencies and configuration.
  • Record the project version and date.
  • Verify file integrity and access permissions.
  • Keep the backup in the approved storage location.
  • Record the recovery method.
  • Validate restoration compatibility in an approved environment.
  • Keep a known-good version and rollback plan.

Never perform a live application download or restore on a production machine without the required authorization, impact assessment, backup, and recovery plan.

18. HMI Migration and Replacement

When replacing an HMI, the objective is to preserve the required operator behavior and the integrity of the control interface, not simply to copy the screen graphics.

Assess the following:

  • Existing HMI model and lifecycle status.
  • Replacement model and display dimensions.
  • Resolution and object scaling.
  • Supported communication drivers.
  • PLC tag compatibility.
  • Alarm and event behavior.
  • User permissions.
  • Scripts and external dependencies.
  • Recipe and parameter retention.
  • Trend and history retention.
  • Startup behavior after power restoration.
  • Network configuration and security.
  • Backup, rollback, and validation requirements.

A visually identical screen can still be functionally wrong if a tag address, command type, scaling rule, or alarm trigger changes during migration.

18.1 Migration validation

Validate each important screen and function against approved requirements.

  • Confirm that displayed tags use the correct sources.
  • Confirm engineering units and scaling.
  • Test operator commands under authorized conditions.
  • Verify alarm triggering, acknowledgment, clearing, and reset behavior.
  • Verify communication-loss indications.
  • Verify access restrictions.
  • Check navigation and diagnostic links.
  • Confirm recipe and parameter handling.
  • Test the required startup and recovery behavior.
  • Record results and obtain the required approval before release.

Safety-related functions must be validated under the applicable safety process, independently of ordinary HMI screen testing.

20. Practical Case Studies

Case 1: HMI shows a pressure alarm

Situation: The operator sees Hydraulic Pressure Below Minimum.

Investigation: Check the alarm state and associated PLC tag. Compare the pressure value and its freshness with the actual instrument condition. Review the process sequence and the relevant electrical and hydraulic documentation.

Possible causes: Actual low pressure, sensor failure, lost sensor supply, analog input fault, incorrect scaling, or communication loss.

Correct approach: Establish which condition is actually present, follow the approved troubleshooting procedure, and correct the verified cause.

Lesson: An alarm describes the condition detected by the application. It does not automatically identify the failed component.

Case 2: Operator presses Start but the machine does not cycle

Situation: The Start button responds on the HMI, but automatic operation does not begin.

Investigation: Determine whether the HMI command reaches the PLC. Review the machine mode, start permissives, active interlocks, and sequence state.

Possible causes: The machine is not in the correct mode, a required condition is missing, an interlock is active, or the command interface is faulty.

Correct approach: Use the documented command and feedback relationship to identify the blocked condition. Do not bypass interlocks to force a cycle.

Lesson: An HMI command is a request, not proof that the PLC accepted it or that the machine is ready.

Case 3: HMI values freeze while the machine continues operating

Situation: Process values stop updating, but the machine appears to continue its cycle.

Investigation: Check communication status, tag freshness, PLC diagnostics, and the network path.

Possible causes: HMI communication loss, driver failure, a stale connection, or an application problem.

Correct approach: Follow the approved operating response for loss of visibility, restore communication safely, and verify data accuracy before relying on the displays.

Lesson: A frozen value must not be treated as a current measurement.

Case 4: A migrated HMI displays incorrect values

Situation: After an HMI replacement, an analog value is displayed in the wrong range.

Investigation: Compare the new tag mapping, data type, scaling, units, and decimal precision against the approved PLC and instrumentation documentation.

Correct approach: Correct the configuration through change control, validate the value against an approved reference, and document the revised application version.

Lesson: Screen appearance does not establish data correctness.

21. Common HMI Documentation Mistakes

Mistake Consequence Correct practice
Recording screen names without purpose Technicians cannot identify the right diagnostic page Record screen function and related subsystem
Omitting tag sources Display faults are difficult to trace Map important tags to PLC or data sources
Treating acknowledgment as fault clearance Operators may assume the problem is resolved Document acknowledgment, clearing, and reset separately
Using vague alarm messages Fault investigation takes longer Use specific, evidence-based alarm text
Ignoring communication-loss behavior Stale data may appear valid Document quality and freshness indications
Allowing uncontrolled parameter changes Process quality or equipment behavior may change Apply role-based access and change control
Saving only screenshots Editable application and configuration may be lost Preserve the supported engineering project and dependencies
Replacing hardware without compatibility checks Application or communication failures may occur Verify model, firmware, drivers, and project compatibility
Resetting alarms repeatedly Root causes remain unresolved Diagnose the initiating condition
Treating HMI logic as a safety function Required risk reduction may not be achieved Use the designed and validated safety system

22. Final Verification Checklist

  • HMI model, firmware, runtime, and application version are recorded.
  • Every important screen has an ID and documented purpose.
  • Screen navigation and diagnostic relationships are documented.
  • Important HMI tags are mapped to their data sources.
  • Data types, scaling, and engineering units are verified.
  • Operator commands and their PLC-side behavior are documented.
  • Preconditions, feedback, and recovery behavior are identified.
  • Alarm IDs, trigger conditions, and priorities are recorded.
  • Acknowledgment, clearing, reset, and suppression behavior are understood.
  • Communication-loss and stale-data behavior are documented.
  • Access permissions and engineering-change controls are recorded.
  • The approved editable project and required dependencies are backed up.
  • Migration or replacement validation requirements are documented.
  • The knowledge base points to the approved PLC, electrical, and network documents.
  • The record is updated after an approved HMI modification.
