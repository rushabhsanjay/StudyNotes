1. Purpose of PLC Documentation in a Machine Knowledge Base

A Programmable Logic Controller (PLC) is an industrial controller that executes a control program to operate machinery based on input signals, internal logic, communication data, and configured operating conditions.

In a machine knowledge base, the PLC record must answer five essential questions:

  • Identity: Which PLC is installed, and where is it located?
  • Hardware: What CPU, I/O modules, communication modules, and expansion units are installed?
  • Program: Which application is running, what software and firmware does it require, and where is its approved backup?
  • I/O: Which physical signals enter and leave the PLC, and which machine devices do they represent?
  • Recovery: How can the controller and its program be restored safely if hardware fails or data is lost?

A PLC record should allow a maintenance engineer to identify the installed controller, understand its relationship to the machine, locate the correct program and drawings, troubleshoot signals, and plan a controlled recovery.

Important distinction: A PLC model number alone is not enough to identify a machine's control system. Two controllers of the same model may run different programs, use different firmware, have different I/O configurations, and control entirely different processes.

2. PLC System Architecture

A typical PLC-based machine contains a controller, input and output modules, a power supply, communication interfaces, field devices, and engineering software.

Sensors and Field Inputs
          ↓
Input Modules / Remote I/O
          ↓
       PLC CPU
          ↓
Control Program and Logic
          ↓
Output Modules / Communication
          ↓
Contactors, Valves, Drives, Robots
          ↓
Machine Process
          ↓
Feedback from Sensors and Devices

The exact architecture varies. Some machines use local I/O mounted beside the CPU. Others use distributed I/O over industrial networks, communication-based drives, remote controllers, or integrated safety controllers.

The machine knowledge base should document the actual installed architecture rather than assuming every signal is wired directly to the main PLC.

3. PLC Identification and Model

The first task is to identify the installed PLC accurately.

Do not record passwords, private keys, or other authentication secrets in an ordinary machine knowledge base. Store credentials only in the plant's approved secure credential-management system.

3.2 Model versus firmware versus software

These are different attributes.

  • Model: Identifies the controller hardware family or exact product.
  • Firmware: The internal software version running on the PLC CPU.
  • Engineering software: The tool used to configure, program, diagnose, and maintain the PLC.
  • Application program: The machine-specific logic executed by the controller.
  • Hardware configuration: The configured CPU, modules, addresses, communication interfaces, and related settings.

A controller can have a compatible hardware model but still be incompatible with a project because of firmware, software version, library, or configuration differences.

4. PLC Hardware Configuration

The CPU is only one part of a PLC system. A controller rack or station may contain several modules that collectively implement the machine's control functions.

4.1 Common hardware components

Digital input module Receives ON/OFF signals Model, channel count, addressing
Digital output module Commands discrete devices Model, channel count, output type
Analog input module Measures analog signals Model, range, resolution, channel mapping
Analog output module Produces analog command signals Model, range, channel mapping

Not every system contains every component. Record only the modules installed in the actual machine.

4.2 Rack, slot, and module identification

For modular PLCs, document the rack or station arrangement and each module's position.

Example:

Rack or station Slot or position Device Purpose
Main rack CPU position PLC CPU Executes machine program
Main rack Slot 1 Digital input module Receives discrete field signals
Main rack Slot 2 Digital output module Commands discrete devices
Main rack Slot 3 Analog input module Receives process measurements
Remote station Adapter position Remote I/O adapter Exchanges data with main controller

The entries above are illustrative. Actual slot numbers, module order, and addressing must be copied from the installed configuration and controlled drawings.

A module replacement can affect addressing, channel mapping, configuration compatibility, and diagnostics. Replacing a failed module with a visually similar unit without checking its exact catalog number and configuration can introduce additional faults.

5. PLC Program Documentation

The PLC application program contains the logic that determines how the machine responds to inputs, internal states, commands, timers, counters, alarms, and feedback.

A program backup is useful only when its identity, compatibility, integrity, and relationship to the installed machine are known.

5.1 Program information to capture

Field Purpose
Project name Identifies the engineering project
Application name Identifies the machine-control application
Project revision Records the approved version or revision
Last approved change Links the program to a controlled modification
Controller target Identifies the intended PLC model
Firmware requirement Records the compatible or required firmware
Engineering software version Identifies the tool used to open and maintain the project
Backup location Identifies the approved storage location
Backup date Records when the backup was created
Backup type Project source, upload, archive, or other defined package
Validation status Records whether the backup has been checked
Change history Records approved modifications and their reasons
Restore procedure References the approved recovery instructions

Use the plant's approved naming and version-control conventions. A filename such as PLC_FINAL_NEW_LATEST_2 is not a dependable version-control system, despite humanity's ongoing efforts to make it one.

5.2 Source project versus uploaded controller image

An engineering project saved on a computer and a program uploaded from a PLC are not always equivalent.

Depending on the platform, an upload may not contain all original source information, comments, symbolic names, external libraries, source files, or documentation needed for full engineering maintenance.

For this reason, record the backup type explicitly:

  • Native engineering project: The maintained project used by the engineering software.
  • Controller upload or extracted project: A copy obtained from the installed controller, subject to platform limitations.
  • Controller memory or firmware backup: A platform-specific recovery image or data set, where supported.
  • Archive package: A packaged project containing the required configuration and associated files.
  • Exported source or reports: Individual program blocks, tag lists, configuration exports, or reports.

Do not assume that every PLC supports every backup method. Confirm the manufacturer's instructions and the installed platform's capabilities.

5.3 Backup verification

A reliable PLC backup process should include:

  1. Identify the machine and controller.
  2. Confirm the running controller model, firmware, and project identity where available.
  3. Follow the approved procedure to obtain the backup.
  4. Save the backup in the controlled location using the required naming convention.
  5. Record the backup date, source, version, and responsible person or role.
  6. Verify file integrity using the organization's approved method.
  7. Confirm that the backup can be opened with the required engineering software, where this can be checked safely.
  8. Verify that associated hardware configuration, libraries, device descriptions, and required project dependencies are available.
  9. Record whether the backup has been tested for recovery or merely archived.
  10. Protect the backup against unauthorized changes and accidental deletion.

Opening a project successfully does not prove that it can be restored to the installed controller or that the restored program will operate the machine correctly.

5.4 Uploading and downloading programs

  • Upload: Transfers available program or configuration data from the controller to an engineering environment, subject to platform limitations.
  • Download: Transfers a project, configuration, or program from the engineering environment to the controller.
  • Online monitoring: Allows the engineer to observe supported controller states, variables, or logic execution.
  • Compare: Identifies differences between available project and controller data, within the comparison capabilities of the platform.

Downloading can change machine behavior and interrupt production. It must follow the approved change-control procedure, with the required permissions, backups, machine-state controls, validation, and rollback plan.

Never download an unverified project to a production PLC merely to see whether it works.

6. PLC Programming Languages and Program Structure

PLC programs may use one or more languages defined by IEC 61131-3 and supported by the specific controller.

Language Abbreviation Typical use
Ladder Diagram LD Relay-like logic, permissives, interlocks, maintenance troubleshooting
Function Block Diagram FBD Connecting functional blocks for control and signal processing
Structured Text ST Calculations, complex conditions, data processing, reusable logic
Sequential Function Chart SFC Organizing processes into steps and transitions, where supported
Instruction List IL Legacy instruction-based programming on platforms that support it

Language availability and implementation vary by platform and software version. Instruction List is a legacy language and is not supported as a standard programming language by many modern environments.

6.1 Common program components

A PLC project may contain:

  • Main or cyclic program routines.
  • Subroutines and reusable functions.
  • Function blocks and associated data.
  • Global and local variables.
  • Input/output mappings.
  • Timers and counters.
  • Alarm and fault-handling logic.
  • Machine sequence logic.
  • Communication routines.
  • Motion or drive interfaces.
  • Diagnostic and maintenance functions.
  • Safety-related logic, where applicable and supported by the safety architecture.

6.2 Document the program structure

For maintainability, record the names and purposes of the important program components rather than documenting only the project filename.

Program component Purpose to record
Main routine Overall execution structure
Auto sequence Automatic operating sequence
Manual mode Authorized manual operation logic
I/O mapping Relationship between physical signals and program variables
Alarm handling Fault detection, alarm generation, and reset conditions
Communication logic Data exchange with HMIs, drives, robots, or other controllers
Diagnostics Health monitoring and fault identification
Motion control Axis commands, feedback, and motion-state handling
Safety interface Interface with the approved safety system
Data handling Recipes, production counters, measurement values, or retained data

A safety interface routine in a standard PLC program does not automatically make that PLC safety-rated. Safety functions must be implemented and validated using the designated safety architecture and applicable requirements.

7. PLC I/O Fundamentals

I/O means input/output. It describes how the controller receives information from the machine and sends commands to equipment.

  • Inputs report conditions, measurements, or device states to the PLC.
  • Outputs transmit commands or control signals from the PLC to devices.
  • Internal variables store or calculate values within the controller.
  • Network variables exchange data with other controllers, drives, HMIs, robots, and industrial devices.

A critical maintenance task is mapping each relevant signal to its physical device, controller address, program variable, and machine function.

8. Digital Inputs

Digital inputs represent discrete states, commonly ON/OFF or TRUE/FALSE.

Typical examples include:

  • Proximity sensors.
  • Limit switches.
  • Pushbuttons.
  • Pressure switches.
  • Part-present sensors.
  • Contactor feedback contacts.
  • Drive-ready and fault signals.
  • Guard-door status signals.

8.1 Digital input record

Field Description
Signal ID Unique identifier for the signal

Physical address Actual module and channel address

Normal state Expected state under the documented condition
Electrical type PNP, NPN, dry contact, or other applicable type

Drawing reference Electrical schematic reference
Diagnostic notes Expected behavior and fault checks

8.2 PNP and NPN sensors

PNP and NPN describe common transistor output arrangements used in industrial sensors.

  • PNP output: Commonly sources current toward the positive supply when ON.
  • NPN output: Commonly sinks current toward the zero-volt reference when ON.

The PLC input module and field device must be electrically compatible. The wiring arrangement must match the manufacturer's specifications.

Do not identify a sensor's output type from its housing or wire colors alone. Verify the model, wiring diagram, and installed circuit.

8.3 Interpreting a digital input

Suppose a sensor detects a component at a fixture.

The PLC input may indicate that the component is present. However, the signal alone does not prove that the component is correctly positioned, clamped, identified, or safe to process.

The control program may require several signals and additional conditions before allowing the next sequence step.

When troubleshooting, distinguish between:

  1. The physical condition.
  2. The sensor's electrical output.
  3. The signal received at the PLC channel.
  4. The program variable representing that signal.
  5. The logic conditions that use the variable.

This separation helps locate the fault instead of replacing the sensor whenever the machine refuses to cycle.

9. Digital Outputs

Digital outputs command discrete devices through the applicable output module, interface relay, or connected control system.

Typical loads include:

  • Solenoid valves.
  • Interposing relays.
  • Contactor coils.
  • Indicator lamps.
  • Buzzer circuits.
  • Pneumatic clamp commands.
  • Drive enable or reset interfaces, where designed.
  • Digital command interfaces to other equipment.

9.1 Digital output record

Field Description
Signal ID Unique output identifier
PLC tag Program variable name
Physical address Output module and channel
Device tag Actuator, relay, or interface identifier
Function Intended machine action
Electrical type Relay, transistor, or other applicable output type
Rated output Manufacturer-specified electrical limits
Interposing device Relay, contactor, or interface module, if fitted
Feedback signal Relevant confirmation of the commanded action
Drawing reference Wiring and circuit reference

A PLC output turning ON does not prove that the connected actuator operated.

For example, an output may energize a relay command, but the relay may have failed, the downstream fuse may be open, the valve coil may be defective, or the actuator may be mechanically stuck.

Where applicable, document both the command and its feedback.

9.2 Output troubleshooting

For a command that does not produce the expected machine action, examine the following using approved diagnostic and electrical procedures:

  • Whether the program conditions permit the output.
  • Whether the output variable is being commanded.
  • Whether the output channel indicates the expected state.
  • Whether the module has diagnostic faults.
  • Whether the field supply and protective device are healthy.
  • Whether the interface relay or contactor operates as designed.
  • Whether the actuator receives the correct command and can move.
  • Whether the feedback signal confirms the action.

Do not force an output or bypass an interlock merely to test an actuator. Such actions can create unexpected movement or hazardous conditions.

10. Analog Inputs and Outputs

Analog I/O handles continuously varying measurements or commands.

Common industrial signal ranges include:

  • 4–20 mA.
  • 0–20 mA.
  • 0–10 V.
  • Other voltage or current ranges supported by the installed module.

Examples include pressure transmitters, temperature transmitters, position feedback, flow measurement, and speed references.

10.1 Analog input record

Field Description

Device tag Transmitter or measurement device

10.2 Scaling example for a 4–20 mA transmitter

Assume a pressure transmitter is configured for 0–10 bar over a 4–20 mA signal range.

The engineering value can be calculated using:

\[ PV = \frac{I-4}{20-4}\times 10 \]

Where:

  • \(PV\) is the pressure in bar.
  • \(I\) is the measured current in milliamperes.

If the measured signal is 12 mA:

\[ PV = \frac{12-4}{16}\times 10 = 5\text{ bar} \]

This example assumes linear scaling and a correctly configured transmitter and analog input channel.

In a real PLC, the raw input may be represented by a manufacturer-specific digital count rather than a direct current value. The program must convert the raw count into the engineering range using the configured module characteristics.

10.3 Why analog signal records matter

An incorrect scaling range can produce an incorrect displayed value even when the sensor and wiring are functioning properly.

For example, a pressure transmitter may generate a valid current signal, but an incorrect raw-count conversion could cause the HMI to display an incorrect pressure.

The knowledge base should link the transmitter's model and range, the PLC channel configuration, the scaling logic, and the HMI tag.

11.2 Symbolic tags

A symbolic tag gives a signal a meaningful name.

For example:

  • DI_Clamp_Extended
  • DI_Part_Present
  • DO_Clamp_Extend
  • AI_Hydraulic_Pressure
  • PLC_Auto_Mode_Active

Good tags should be readable, unique within their required scope, and consistent with the plant's naming convention.

Avoid ambiguous names such as M1, BIT_12, or SENSOR_NEW unless they are formally defined by the established naming standard.

Not every system uses a direct physical PLC channel. A networked drive, remote I/O station, or another controller may provide the signal. Document the actual route.

13. PLC Operating Modes and Execution

A PLC's operating mode affects how it executes its application and responds to program changes.

Common concepts include:

  • Run: The controller executes the application according to the platform's operating rules.
  • Program or Stop: Application execution is stopped or restricted, depending on the platform and mode.
  • Remote mode: The controller may accept certain commands from an authorized engineering system, depending on configuration.
  • Faulted state: The controller has encountered a condition affecting its operation.
  • Startup or recovery state: The controller is starting, restoring, or validating its operating condition.

Names and behavior vary between manufacturers. Always use the installed platform's documentation.

13.1 Scan cycle concept

Many PLCs execute application logic in repeated processing cycles. A simplified model is:

  1. Acquire or update input data according to the platform's I/O architecture.
  2. Execute the applicable program logic.
  3. Update outputs according to the execution model.
  4. Perform communication, diagnostics, and system tasks as scheduled.
  5. Repeat the applicable execution cycle.

Actual execution can involve multiple tasks, asynchronous communication, interrupts, distributed I/O updates, motion tasks, and safety-related processing. Not every controller follows a single simple scan sequence.

13.2 Why execution behavior matters

A sensor may change state between input updates, a task may execute at a configured interval, or communication data may arrive asynchronously.

These timing effects can influence:

  • Short pulses.
  • High-speed counting.
  • Motion control.
  • Networked device status.
  • Timer behavior.
  • Sequence transitions.
  • Alarm response.

Document special tasks, periodic execution, high-speed inputs, and communication dependencies when they are important to machine behavior.

14. PLC Interlocks and Permissives

A permissive is a condition that must be satisfied before an operation is allowed. An interlock prevents or restricts an operation when a specified condition is not satisfied.

Examples include:

  • A clamp must be confirmed in the required position before machining.
  • A drive must report ready before a motion command is accepted.
  • A part must be present before a process cycle begins.
  • A machine must be in an approved operating mode before automatic operation is enabled.
  • A process measurement must be within an approved range before a sequence advances.

Record the relevant signal, its purpose, the condition it affects, and the diagnostic method.

Do not document an interlock merely as "PLC condition." State the actual functional requirement.

Safety distinction: Ordinary PLC interlocks are not automatically safety-rated functions. Personnel protection must rely on the designated safety system and validated safety measures, not on an assumption that standard PLC logic will prevent hazardous motion.

15. PLC Communication and Connected Devices

A PLC may communicate with:

  • HMIs and industrial PCs.
  • Remote I/O stations.
  • VFDs and servo drives.
  • Robots and CNC controllers.
  • Industrial Ethernet switches.
  • SCADA systems and historians.
  • Barcode readers and vision systems.
  • Measurement and test equipment.
  • Other PLCs or supervisory controllers.

The machine knowledge base should identify each important connection and its role.

16. PLC Alarms and Diagnostics

A useful PLC knowledge base records how the controller and program identify abnormal conditions.

Examples include:

  • CPU or hardware faults.
  • I/O module faults.
  • Communication timeouts.
  • Sensor plausibility errors.
  • Drive faults.
  • Sequence timeouts.
  • Unexpected feedback states.
  • Analog values outside configured limits.
  • Controller memory or application faults.

For each important alarm, record:

  • Alarm ID and description.
  • Trigger condition.
  • Relevant PLC tag or diagnostic reference.
  • Machine function affected.
  • Required checks.
  • Approved reset or recovery procedure.
  • Whether the fault requires engineering support.

Avoid recording only the HMI alarm text. The alarm should be traceable to the PLC logic, physical signal, connected equipment, or diagnostic source that produces it.

Do not reset a fault without understanding whether it indicates a hazardous condition or a failed process step.

17. PLC Change Management

PLC modifications can affect machine timing, motion, product quality, safety interfaces, and communication with other equipment.

A controlled change should include:

  1. A defined problem statement or engineering requirement.
  2. Authorization under the plant's change-control process.
  3. Identification of the affected controller and application.
  4. A verified pre-change backup.
  5. Review of hardware, firmware, software, and library compatibility.
  6. Assessment of production and safety risks.
  7. An approved test and validation plan.
  8. A defined rollback or recovery plan.
  9. Controlled implementation by authorized personnel.
  10. Functional verification and required safety validation.
  11. Updated project files, drawings, and machine knowledge base.
  12. Recorded revision, date, approval, and change description.

The backup and final project should be clearly distinguished. A pre-change backup must not be silently overwritten by the modified version.

18. PLC Fault-Diagnosis Method

Use a structured process that separates symptoms, electrical conditions, communication, and program logic.

18.1 Controller not communicating

  1. Confirm the actual symptom and which devices are affected.
  2. Check available CPU status and diagnostic information.
  3. Verify the relevant power supply and controller status through approved methods.
  4. Check the network path, link status, addressing, and communication configuration.
  5. Determine whether the fault affects the controller itself or only a connected device.
  6. Compare the observed configuration with the approved record.
  7. Correct the verified fault and confirm communication recovery.
  8. Record the cause and action.

18.2 Input signal is not changing

  1. Identify the physical device and intended process condition.
  2. Check whether the device is mechanically able to detect the condition.
  3. Confirm the device's supply and output using approved procedures.
  4. Trace the signal through the wiring, terminal, and I/O channel.
  5. Check module diagnostics and the program variable.
  6. Verify the logic that consumes the input.
  7. Restore normal operation and validate the relevant sequence.

18.3 Output command is active but the actuator does not operate

  1. Confirm the intended command and operating conditions.
  2. Check whether the PLC program is commanding the output.
  3. Check module status and relevant diagnostics.
  4. Identify the downstream interface and electrical supply.
  5. Follow approved isolation and verification procedures before physical inspection or electrical testing.
  6. Check the actuator and feedback path using the approved method.
  7. Confirm that the machine returns to its expected state after the repair.

Never bypass safety functions or force outputs to make the machine move during diagnosis.

19. Practical PLC Case Studies

Case 1: Sensor is healthy, but the PLC input remains OFF

Situation: A part-present sensor's indicator changes when the part is positioned, but the PLC program variable remains OFF.

Investigation: The technician verifies the configured input channel, sensor output type, terminal assignment, wiring, and input module diagnostics.

Possible findings: An open conductor, incorrect terminal assignment, incompatible sensor output, incorrect module configuration, or a failed channel.

Lesson: A sensor indicator does not prove that the PLC is receiving the signal.

Case 2: PLC output is ON, but a pneumatic clamp does not extend

Situation: The PLC command is active, but the clamp does not move.

Investigation: The output channel, interface relay, field supply, valve circuit, pneumatic supply, and relevant feedback are examined under the approved procedure.

Possible findings: Failed interface relay, open circuit, faulty valve coil, inadequate pneumatic supply, mechanical obstruction, or missing required conditions.

Lesson: The output command and the physical machine response are separate points in the control chain.

Case 3: Replacement PLC has the same model but will not accept the project

Situation: A replacement CPU has the same general model family, but the engineering project reports compatibility issues.

Investigation: The technician checks the exact catalog number, firmware, engineering software version, hardware configuration, and required libraries.

Possible findings: Incompatible firmware, a different hardware revision, missing project dependencies, or a configuration mismatch.

Lesson: Hardware-family similarity does not guarantee project compatibility.

Case 4: A backup exists but cannot support recovery

Situation: The stored PLC backup opens, but required symbols, configuration files, or project dependencies are missing.

Investigation: The backup type and completeness were never recorded, and no recovery validation had been performed.

Corrective action: Establish a controlled backup package that includes all required supported project files, version information, compatibility details, and recovery instructions. Test recovery using an approved non-production environment or procedure where feasible.

Lesson: An archived file is not automatically a recoverable machine-control system.

22. Final PLC Documentation Checklist

  • Exact CPU model and installed firmware are recorded.
  • Controller identity and physical location are confirmed.
  • Power supply, racks, slots, modules, and remote I/O are documented.
  • Engineering software and version requirements are recorded.
  • The running application and approved project revision are identified.
  • Backup type, location, date, and verification status are recorded.
  • Required libraries and hardware configuration dependencies are identified.
  • Digital and analog I/O are mapped to devices and physical addresses.
  • Signal names follow a consistent naming convention.
  • Analog scaling ranges and engineering units are documented.
  • Important program routines and machine sequences are identified.
  • Communication links and connected equipment are documented.
  • Alarms and diagnostic references are traceable.
  • Safety-related functions are distinguished from ordinary PLC logic.
  • Program changes follow approved change control.
  • Recovery instructions and validation requirements are available.
  • The knowledge base matches the installed machine and controlled drawings.

The objective is not merely to list the PLC model. It is to create a reliable link between the physical controller, its program, every important signal, the machine function, and the recovery process.
