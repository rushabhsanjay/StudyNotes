1. Purpose of Software and Version Documentation

Industrial machines depend on software at multiple levels: PLC programming environments, HMI configuration tools, CNC programming and commissioning software, robot engineering tools, drive configuration utilities, safety configuration environments, industrial communication utilities, and supporting PC applications.

The purpose of a software register is to identify exactly which software is needed to access, maintain, troubleshoot, configure, restore, and modify a machine.

A software name alone is not enough. The same product may have multiple major versions, service packs, firmware dependencies, licensing requirements, communication drivers, and project-file compatibility restrictions.

For example, knowing that a machine uses Siemens TIA Portal does not establish which TIA Portal version can open its PLC project, which device firmware is installed, which engineering license is available, or whether the project can be downloaded safely to the controller.

The software register must answer these questions:

  • What software is installed or required?
  • Which exact version and build are approved for the machine?
  • Which hardware or controller does it support?
  • Where is the installer or approved installation package stored?
  • Which license, activation, driver, or runtime dependency is required?
  • Which project or configuration file is associated with it?
  • Which engineering PC or virtual machine is known to work?
  • What compatibility restrictions apply?
  • Who owns the software, license, and technical approval?
  • How can the environment be restored if the engineering computer fails?

Core principle: Record the software environment that is verified to work with the machine, not merely the newest software available.

2. Industrial Software Architecture

A typical machine may contain several layers of software and configuration.

Machine Knowledge Base
        ↓
Engineering Workstation / Virtual Machine
        ↓
Engineering Software and Supporting Utilities
        ↓
Project Files, Libraries and Configuration
        ↓
Communication Drivers and Interfaces
        ↓
Controller Firmware / Device Firmware
        ↓
PLC / HMI / CNC / Robot / Drives / Safety Devices
        ↓
Machine Process and Production Operation

Each layer can have a separate version. Compatibility across layers is critical.

For example, an engineering application may open a project but still require a particular hardware support package, device description, firmware version, library revision, or communication driver before the project can be fully compiled, validated, or transferred.

2.1 Software categories

Category Purpose Typical examples
PLC engineering Create, monitor, diagnose and maintain PLC programs TIA Portal, Studio 5000 Logix Designer, GX Works
HMI engineering Configure operator screens, alarms, trends and recipes WinCC, FactoryTalk View, GT Designer
CNC engineering Configure and diagnose CNC controls and machine parameters Manufacturer-specific CNC engineering and service utilities
Robot engineering Configure robot systems, programs, tooling and communication KUKA WorkVisual, FANUC engineering tools
Drive configuration Configure VFDs, servo drives and motion systems Drive-specific commissioning software
Safety engineering Configure and validate supported safety controllers and devices Vendor-specific safety engineering environments
SCADA and historian Supervise equipment, alarms, trends and production data SCADA platforms and historian applications
Communication utilities Diagnose industrial networks and protocols Vendor network tools, OPC utilities and approved packet diagnostics
Electrical CAD Create and maintain electrical schematics and component references EPLAN and other approved electrical CAD tools
Database and reporting Store, query and report machine or maintenance data SQL Server tools, Power BI and approved reporting applications
Operating system and runtime Provide the environment in which engineering or production software runs Windows editions, runtime packages and approved system components
Licensing and activation Manage authorized software entitlement Vendor license managers and activation utilities
File and image management Store installers, engineering projects and approved workstation images Version-controlled repositories and managed backup systems

A machine may use only some of these categories. Record what is actually installed, used, or required rather than filling the register with every software product found in the plant.

3. Software Identification: Name, Version and Build

3.1 The difference between product name and version

Field Meaning Example
Software name Product identity TIA Portal
Major version Major release generation V17
Minor version Feature or maintenance release within a generation Product-specific release value
Update or service pack Vendor-issued update level Update 5, if applicable
Build number Exact software build where available Record the displayed build
Edition Product edition or package Basic, Professional, or another licensed edition
Installed components Additional packages actually installed Safety, motion or device support packages
Project version Version or format associated with the engineering project Project-specific version
Controller firmware Firmware running on the physical device Exact CPU or device firmware
Operating system Host OS and release Approved Windows edition and build
License type Entitlement or licensing model Named-user, floating, perpetual or subscription, as applicable
Verification date Date the version was checked Actual verification date

Do not assume that the major version alone uniquely identifies the installed environment. Updates, builds, optional packages, and device support can affect compatibility.

3.2 Why exact versions matter

Version mismatches can cause:

  • Project files to be rejected or migrated.
  • Libraries or instructions to be unavailable.
  • Hardware configurations to be unsupported.
  • Firmware downloads to be blocked or require an upgrade.
  • HMI screens, alarms, recipes, or communication drivers to behave differently.
  • PLC compilation results to change.
  • Safety signatures or validated configurations to become invalid.
  • Runtime services or operating-system dependencies to fail.
  • License activation or communication functions to stop working.
  • Restoration attempts to fail because the original installer or required update is missing.

A project that opens successfully is not necessarily a project that can be safely downloaded to the machine.

5. Software and Hardware Compatibility

Compatibility must be evaluated across the engineering application, project, controller hardware, device firmware, operating system, communication drivers, libraries, and license.

5.1 Compatibility matrix

Compatibility layer What to verify Typical failure if incompatible
Engineering software ↔ project Project format and supported migration path Project cannot open or requires conversion
Engineering software ↔ controller Supported controller family and catalog revision Device cannot be configured or recognized
Project ↔ firmware Required firmware and supported instructions or features Compile errors, transfer rejection or changed behavior
HMI software ↔ runtime Runtime version and supported screen features Display, alarm or runtime errors
Engineering software ↔ OS Supported Windows edition, build and dependencies Installation failure or unstable operation
Software ↔ license Required edition and valid entitlement Restricted functions or activation failure
Software ↔ communication driver Driver version, protocol and interface support Controller cannot be reached
Project ↔ libraries Library version and dependencies Missing blocks, incompatible objects or compile errors
Safety software ↔ safety controller Supported versions, signatures and validation requirements Safety configuration cannot be validated or transferred
SCADA ↔ data source Driver, OPC interface, tag mapping and protocol support Missing, stale or incorrectly mapped data
Backup ↔ restore environment Required application versions, packages and project dependencies Project cannot be restored to a usable engineering state

5.2 Compatibility status definitions

Use controlled values rather than free-text guesses.

  • Verified: Compatibility has been confirmed using documented evidence and the required test procedure.
  • Verified with restrictions: Works only under documented conditions, such as a particular OS, firmware, driver or license.
  • Pending verification: Available information is insufficient to approve the combination.
  • Unsupported: The vendor or responsible technical authority does not support the combination.
  • Retired: No longer approved for new work, but retained for legacy machine support.
  • Prohibited for production: Must not be used to modify or operate production equipment under current site rules.

A software combination should not be marked verified solely because it installed successfully.

5.3 Project migration and conversion

Opening an older project in a newer engineering tool may trigger a conversion or migration process. This can change project format and sometimes requires changes to libraries, hardware configurations, instructions, or other objects.

Before migrating a production project:

  1. Identify the original project version and its dependencies.
  2. Preserve an untouched copy of the original project.
  3. Confirm the target software and device firmware are supported.
  4. Review vendor migration notes and known restrictions.
  5. Perform the conversion in a controlled environment.
  6. Compile and review the converted project.
  7. Test using an approved simulation, offline validation, or suitable test setup.
  8. Complete the machine-specific validation and authorization process before any production download.
  9. Record the old and new versions, conversion results, approvals and rollback method.

Never migrate the only usable copy of a production project. A conversion may be one-way or may prevent older engineering software from opening the resulting project.

6. Software Inventory by Industrial System

6.1 PLC engineering software

For each PLC family, record:

  • Engineering software product and exact version.
  • Installed updates, device support packages and relevant libraries.
  • PLC manufacturer, model, catalog number and firmware.
  • Programming language or project features used, where relevant.
  • Communication driver and interface requirements.
  • Required license edition.
  • Project format and last successful compilation information.
  • Approved programming cable, Ethernet interface or other connection method.
  • Supported upload, comparison, monitoring and restore methods.
  • Any restrictions on firmware upgrades, online changes or project migration.

Examples of vendor ecosystems include Siemens TIA Portal, Rockwell Studio 5000 Logix Designer, Mitsubishi GX Works, and other vendor-specific PLC tools. Record the actual product used on each machine.

6.2 HMI engineering software

Document the tool used to create or maintain the operator interface and the runtime environment installed on the panel or industrial PC.

Important fields include:

  • HMI make, model and firmware or runtime version.
  • Engineering software version and installed packages.
  • Screen, alarm, trend, recipe and user-management features used.
  • PLC communication driver and protocol.
  • Fonts, graphics, external libraries and scripts required.
  • Runtime installation package and activation requirements.
  • Project file and approved export or restore procedure.
  • Display resolution and target hardware configuration.
  • Dependencies on shared folders, databases, network services or external applications.

A project can open in the engineering tool but still fail on the actual panel because of runtime, font, library, communication, or target-hardware differences.

6.3 CNC engineering and service software

CNC systems may use separate tools for program transfer, parameter backup, diagnostics, ladder editing, servo adjustment, and controller configuration.

Record the exact tool and version for each task. Also document:

  • CNC controller model and software/firmware revision.
  • Machine-builder-specific utilities and OEM packages.
  • Parameter, offset, tool-data and compensation-file formats.
  • Communication method and required interface hardware.
  • License or authorization requirements.
  • Restrictions on editing machine-builder PLC/PMC logic.
  • Dependencies on OEM-specific macros, cycles or libraries.
  • Approved backup and restoration method.

CNC parameters and compensation values can directly affect machine motion, geometry and process quality. Do not change them simply because a newer tool offers additional functions.

6.4 Robot engineering software

For industrial robots, record the controller generation, software release, engineering environment, robot options, fieldbus packages, and relevant safety configuration tools.

Examples of information to capture include:

  • Robot manufacturer, controller model and installed software revision.
  • Engineering software version.
  • Robot programs and system configuration references.
  • Tool, base, payload and frame data dependencies.
  • External-axis and fieldbus configuration packages.
  • Option licenses and required activation.
  • Safety configuration and validation references.
  • Approved upload, comparison, backup and restore procedures.

Robot controller software and safety-related configuration must be handled under the applicable OEM and site procedures. A project that transfers successfully is not proof that safety functions are correctly validated.

6.5 VFD and servo configuration software

For drives, record:

  • Drive manufacturer, model and firmware.
  • Engineering or commissioning software version.
  • Parameter-file format and version.
  • Required USB, serial, Ethernet or vendor-specific interface.
  • Drive communication packages and device-description files.
  • License or option requirements.
  • Motor data and feedback-device configuration dependencies.
  • Approved parameter backup and restoration method.
  • Restrictions on changing tuning, safety, braking or motor-control settings.

A parameter file may be specific to a drive family, firmware generation, motor, feedback device, or machine application. Never assume that a file from a visually similar drive is compatible.

6.6 SCADA, database and reporting software

Document the software involved in data acquisition, storage, visualization, reporting and communication.

System layer Information to capture
SCADA platform Product, version, runtime version, license and project reference
OPC or communication server Product version, driver, device mapping and connection configuration
Database Engine edition, version, instance reference, schema and dependencies
Dashboard platform Version, plugins, data-source configuration and dashboard export
Data acquisition Protocol, polling or update settings, tag mapping and error handling
Reporting tools Product version, data-source dependencies and refresh configuration
Operating system Host OS, installed runtime dependencies and patch baseline
Network dependencies Hostnames, ports, certificates and approved access rules

Passwords, private keys, license secrets, and other credentials must be stored in approved secure systems rather than embedded in a general-purpose machine knowledge base.

7. Engineering Workstation and Software Environment

A machine's software may depend on the specific computer used for maintenance. An engineering workstation is therefore part of the technical configuration, not merely a convenient laptop.

7.1 Workstation register

Field What to record
Workstation ID Unique asset identifier
Hostname Computer name
Machine coverage Machines and controllers supported
Operating system Edition, version, build and support status
Processor and memory Relevant hardware requirements
Storage Capacity, health and available space
Installed engineering tools Product, version, build and edition
Communication interfaces Ethernet adapters, serial ports and vendor-specific interfaces
Drivers Driver names, versions and installation sources
Runtime dependencies Required frameworks, runtimes and system packages
Network configuration Approved interfaces, routes and access restrictions
License configuration License manager and managed license reference
Recovery method Approved system image or workstation rebuild procedure
Backup status Latest verified image and project-backup status
Owner Responsible department or technical owner

7.2 Why separate engineering environments may be necessary

Different machine generations may require incompatible software versions. Installing every available engineering tool on one workstation can introduce driver conflicts, runtime conflicts, licensing complications, and operating-system restrictions.

A controlled strategy may use:

  • Dedicated engineering workstations for critical legacy equipment.
  • Separate virtual machines for isolated software environments.
  • A documented multi-version installation where the vendor supports it.
  • Offline installation packages for approved legacy tools.
  • Restricted access to production networks.
  • A validated recovery image for each critical engineering environment.

Virtualization is not automatically compatible with every vendor tool, license mechanism, communication interface, or real-time requirement. Verify the complete setup before relying on it for maintenance.

7.3 Standard workstation baseline

A controlled engineering workstation baseline should specify:

  • Approved operating-system edition and patch policy.
  • Approved engineering applications and exact versions.
  • Required communication drivers and interface settings.
  • Required vendor libraries and device support packages.
  • License availability and activation method.
  • Antivirus and endpoint-security exclusions only where formally approved.
  • User privileges and software installation permissions.
  • Network access restrictions.
  • Approved installers and checksums where available.
  • Backup, recovery and periodic restore-test requirements.

Do not disable security controls or use unauthorized software simply to make an old engineering package run. Legacy compatibility should be managed through an approved isolation and risk-control strategy.

8. Software Installers, Dependencies and Installation Media

The software register is useful only if the required software can actually be recovered. A version number without an available installer, license, and dependency package can leave a machine difficult to maintain after an engineering PC failure.

8.1 Installer register

Field Purpose
Installer ID Unique package identifier
Product name Exact software product
Version and build Exact installer release
File name Original installer filename
Package location Approved repository path
File size Basic package integrity check
Checksum SHA-256 or another approved integrity hash where available
Digital signature Signature status and publisher where applicable
License requirement Required entitlement or activation type
Dependencies Required frameworks, drivers, runtimes and support packages
Installation instructions Approved procedure and configuration
OS compatibility Verified supported operating systems
Security status Known vulnerabilities, restrictions and approval status
Verification record Date, method and responsible person

A checksum can help confirm that a package matches a known file, but it does not prove that the software is safe or authorized. Obtain installers from approved vendor or organizational sources and verify signatures and integrity as required by site policy.

8.2 Dependency checklist

Before approving an installation package, check for:

  • Required operating-system features and updates.
  • Supported runtime packages and frameworks.
  • Vendor communication drivers.
  • Hardware catalogues and device-description files.
  • Libraries and optional modules.
  • Licensing services and activation components.
  • Required database engines or runtime services.
  • Certificates and trusted communication endpoints where applicable.
  • Configuration files and environment variables.
  • Vendor-approved installation order and restart requirements.

Record dependencies explicitly. "Installer available" is not the same as "installation environment recoverable."

8.3 Installation validation

After installation, verify more than whether the application launches.

  • Confirm product version, update and build.
  • Confirm all required packages and libraries are installed.
  • Confirm license status and permitted functions.
  • Confirm the engineering project opens without unexpected conversion.
  • Confirm the target hardware and firmware are recognized.
  • Confirm the required communication interface is detected.
  • Confirm the intended project can be compiled or validated where appropriate.
  • Record any warnings, unsupported features or restrictions.
  • Preserve the validated installer and configuration details.
  • Update the software register and workstation baseline.

Production download or commissioning tests must be performed only under the approved machine-specific procedure.

9. Software Licensing and Entitlements

Industrial software licensing can depend on the product edition, named user, floating license server, activation key, hardware identifier, dongle, subscription, or another vendor-defined method.

9.1 License register

Field Purpose
License record ID Internal tracking identifier
Software product Product covered by the entitlement
Edition or feature Functions and modules licensed
License type Named user, floating, perpetual, subscription or other type
Entitlement reference Non-secret reference to the managed record
License manager Application or server managing the entitlement
License host Approved workstation or server, if applicable
Expiry or renewal date Applicable renewal or expiry details
Assigned owner Responsible person or department
Recovery method Vendor-approved recovery or reassignment procedure
Availability status Available, assigned, unavailable or requiring action
Compliance status Verified against organizational licensing requirements

Do not place full license keys, passwords, private activation tokens, or other secrets in the general machine knowledge base.

9.2 Licensing failure scenarios

Common problems include:

  • License unavailable from a network license server.
  • License assigned to an unavailable or failed workstation.
  • Activation lost after hardware replacement.
  • Expired subscription or maintenance entitlement.
  • Incorrect software edition installed.
  • License service stopped or blocked by a network rule.
  • License dongle unavailable or not detected.
  • Offline machine unable to reach the approved activation mechanism.

The recovery procedure should identify the license owner, approved vendor process, required entitlement evidence, and expected recovery path.

Never assume that a copied license file or an old activation record is sufficient to restore a valid entitlement.

10. Software Version Control and Change Management

Software changes can alter project formats, device support, program behavior, runtime behavior, and cybersecurity exposure. Treat them as controlled technical changes.

10.1 What counts as a software change?

  • Installing a new engineering software version.
  • Applying an update or service pack.
  • Updating PLC, HMI, CNC, robot or drive firmware.
  • Changing a communication driver.
  • Installing a new library or device package.
  • Migrating a project to a new file format.
  • Changing a runtime, database or operating-system version.
  • Modifying licenses or activation services.
  • Updating network services or security certificates.
  • Changing a virtual machine, workstation image or system configuration.

10.2 Change record

Field Required information
Change ID Unique change reference
Machine or system Affected asset
Current configuration Existing approved software and firmware
Proposed configuration Target software and firmware
Reason Fault correction, security, compatibility or improvement
Risk assessment Production, safety, compatibility and recovery risks
Dependencies Required drivers, libraries, licenses and OS changes
Test plan Compile, functional, communication and machine-specific tests
Backup reference Verified recovery point before the change
Approval Authorized technical and operational approval
Implementation Date, responsible person and procedure
Result Pass, fail, partial completion or rollback
Rollback method Approved return to the previous working state
Updated records Register, diagrams, project versions and instructions

10.3 Controlled change process

        ↓

        ↓

        ↓

Do not update a production engineering workstation simply because a new version is available. Confirm that the upgrade is necessary, supported, tested, licensed, recoverable, and approved.

11. Legacy Software and Obsolescence

Older industrial machines may depend on software that is no longer sold, supported, or compatible with modern operating systems. Removing the old environment before securing a recovery method can turn a routine fault into a major restoration problem.

11.1 Obsolescence indicators

  • Vendor support has ended.
  • The required installer is unavailable from approved sources.
  • The software depends on an unsupported operating system.
  • The license mechanism no longer works with available hardware.
  • Required interface cards, cables or drivers are unavailable.
  • Project conversion to a supported version is unverified.
  • Security vulnerabilities cannot be addressed in the current environment.
  • The vendor no longer provides required firmware or compatibility packages.
  • Only one working engineering workstation remains.
  • No validated backup of the workstation or project exists.

11.2 Obsolescence register

Field Description
Software ID Link to the software register
Machine dependency Machine or controller that requires it
Support status Supported, limited support or end of support
Replacement candidate Proposed successor, if one exists
Compatibility evidence Documented migration or support information
Migration risk Program, firmware, runtime and process risks
Recovery status Whether the current environment can be restored
Workaround Approved temporary support arrangement
Business impact Consequence of losing the software
Required action Retain, isolate, migrate, replace or investigate
Owner Responsible person or department
Target date Approved action target

11.3 Migration strategy

A migration should consider more than the replacement software's name.

  • Determine whether the replacement tool can read and convert the existing project.
  • Identify unsupported instructions, objects, libraries, drivers and hardware.
  • Verify target firmware and hardware support.
  • Determine whether licenses, interfaces, or programming cables must change.
  • Test the migrated project offline or on a suitable test system.
  • Validate the machine functions, alarms, communications, and relevant safety functions according to approved procedures.
  • Preserve the original project and its known-working environment.
  • Document the migration decision, evidence, risks, and rollback route.

Where migration is not yet justified or feasible, an approved isolated legacy environment may be the safer interim support option.

12. Cybersecurity and Software Integrity

Engineering software is part of the industrial control environment. Compromised installers, unauthorized remote access, unmanaged updates, or infected removable media can affect both production and machine availability.

12.1 Basic controls

  • Use approved software sources and managed installation packages.
  • Maintain an inventory of installed software and versions.
  • Restrict software installation to authorized personnel.
  • Apply security updates according to an approved compatibility and change process.
  • Review vendor advisories and organizational vulnerability assessments.
  • Limit engineering workstation access to required systems.
  • Control USB devices and removable media according to site policy.
  • Use approved remote-access methods with appropriate authentication and logging.
  • Protect engineering projects and configuration files from unauthorized changes.
  • Store credentials and activation secrets in approved secure systems.
  • Maintain verified recovery images and offline or otherwise protected backups where required.
  • Record unsupported software and compensating controls.

12.2 Legacy systems and security updates

Applying a security update without compatibility testing can disrupt a legacy engineering environment. Leaving a known vulnerability unaddressed also creates risk.

Use a documented decision process that considers:

  • The vulnerability and realistic exposure.
  • Whether the engineering PC is connected to production networks.
  • Vendor compatibility statements and known issues.
  • Availability of a tested patch or supported replacement.
  • Isolation, access restrictions and monitoring.
  • Recovery capability if the update fails.
  • Approval by the responsible technical and cybersecurity authorities.

Do not connect an isolated legacy engineering PC to external networks simply to download a missing installer or activate software. Follow the organization's approved transfer and security process.

13. Software Verification and Audit

The software register should be supported by evidence. The goal is to establish that the documented environment matches the real one and can perform the required engineering task.

13.1 Evidence sources

Evidence What it establishes
Application About screen Product name, version and sometimes build
Installed applications inventory Packages reported as installed on the host
Vendor license manager License availability and activation status
Device diagnostic screen Controller or device firmware information
Project properties Project format and stored project metadata
Successful compilation record Compilation result for the documented environment
Compatibility documentation Vendor-stated supported combinations
Controlled functional test Observed behavior under defined test conditions
Installer checksum and signature File-integrity evidence and publisher verification
Workstation image record Identity and recovery point for the approved environment
Change record Approval and history of software modifications

No single evidence source proves every aspect of compatibility. For example, a successful compilation does not establish that the program is safe to download to the physical machine.

13.2 Verification status

Use a defined verification outcome:

  • Verified: Required checks passed and evidence is recorded.
  • Verified with restrictions: Checks passed under documented limitations.
  • Pending: Evidence or required tests remain incomplete.
  • Failed: One or more required checks failed.
  • Expired review: Previously verified information needs reassessment due to a defined trigger, such as a change or an elapsed review period.

A periodic review should be combined with event-driven review after software upgrades, workstation replacement, controller firmware changes, license changes, or a major machine modification.

14. Software Register Maintenance Workflow

A register becomes unreliable when nobody owns it, installed versions are never rechecked, or project changes are not reflected in the documentation.

14.1 Initial inventory

  1. Identify each machine and its engineering workstation.
  2. Identify the installed PLC, HMI, CNC, robot, drive, safety, SCADA and other relevant software.
  3. Record exact versions, builds, installed packages and operating-system details.
  4. Identify the physical controller and firmware associated with each project.
  5. Locate approved installers, licenses, project files and vendor manuals.
  6. Verify compatibility using vendor documentation and controlled tests where required.
  7. Identify missing dependencies, unavailable installers and unsupported legacy environments.
  8. Assign an owner and verification status to each record.
  9. Link the register to the relevant machine documentation and backup records.
  10. Record gaps as actions rather than silently assuming the environment is complete.

14.2 Ongoing maintenance

  • Update the register after an approved software installation, upgrade, migration or rollback.
  • Recheck versions after engineering workstation replacement or recovery.
  • Review dependencies when a controller or device firmware is changed.
  • Confirm that required licenses remain available and valid.
  • Verify that installers and recovery images remain accessible.
  • Reassess compatibility when vendor support ends or a security issue emerges.
  • Keep retired software records for legacy traceability when required.
  • Review high-criticality machine environments more frequently according to the site's risk and maintenance plan.

14.3 Ownership and responsibility

Role Typical responsibility
Automation engineer Verify engineering tools, controller compatibility and project dependencies
Electrical maintenance Maintain software information relevant to drives, motion and electrical equipment
CNC or robot specialist Maintain controller-specific tools, firmware and OEM dependencies
IT support Maintain approved operating systems, workstation images and endpoint controls
License administrator Track entitlements, activation and renewal requirements
Cybersecurity team Assess software risks, vulnerability exposure and security controls
Technical owner Approve changes and confirm the register remains accurate

Responsibilities may overlap. The machine knowledge base should identify one accountable owner for each record even when several teams contribute.

15. Acceptance Checklist for the Machine Knowledge Base

The software documentation is complete enough for maintenance when another authorized engineer can identify the correct engineering environment and determine how to recover it.

  • Every relevant software product has a unique record.
  • Exact version, update and build information is recorded where available.
  • Associated machine, controller and engineering workstation are identified.
  • Controller and device firmware are recorded separately from engineering software versions.
  • Required libraries, device packages, communication drivers and runtime dependencies are documented.
  • Required license types and managed entitlement references are recorded.
  • Approved installer packages can be located and their integrity can be checked where required.
  • Project-file locations and associated backup records are linked.
  • Compatibility status is supported by evidence.
  • Unsupported and obsolete software has a documented risk and support plan.
  • Software changes have an approval, validation and rollback record.
  • Workstation recovery requirements are documented.
  • Security restrictions and approved access methods are recorded.
  • The record has an owner and a verification date.
  • No passwords, private keys or sensitive activation secrets are exposed in the register.

16. Common Mistakes

  • Recording only the software product name without the version.
  • Confusing the engineering software version with controller firmware.
  • Assuming the latest software release is automatically compatible with an old machine.
  • Keeping installers without recording their dependencies.
  • Assuming a project that opens will compile, transfer and operate correctly.
  • Migrating the only copy of an engineering project.
  • Assuming software licensing can be restored by copying a folder.
  • Installing every vendor's engineering package on one workstation without checking compatibility.
  • Updating an operating system without assessing legacy engineering tools.
  • Ignoring vendor-specific CNC, robot or drive utilities.
  • Storing credentials or activation secrets in ordinary documentation.
  • Treating an undocumented temporary software change as an approved baseline.
  • Marking a software environment verified without recording evidence.
  • Failing to test the recovery process until the engineering workstation has already failed.

  9. Why should an engineering workstation's drivers and operating system be documented?
  10. Why does successful compilation not prove that a production download is safe?

Practical exercise

Select one machine and create a verified software inventory.

  • Identify its PLC, HMI, CNC, robot, drive and safety tools as applicable.
  • Record the exact software versions and controller firmware.
  • Identify the engineering PC and its operating-system build.
  • Record required communication drivers, libraries and device packages.
  • Locate the approved installers and record their versions.
  • Identify license requirements without exposing secret activation data.
  • Link each software entry to its project and backup record.
  • Verify compatibility using available documentation and approved tests.
  • Identify unsupported software, missing dependencies and single points of failure.
  • Create a controlled recovery plan for the engineering workstation.
  • Record the evidence, owner, review date and outstanding actions.

The key outcome is a verified and recoverable software environment. The machine knowledge base should establish not just which tools exist, but which versions are approved, which dependencies they require, which projects they support, and how the environment can be restored without guessing.
