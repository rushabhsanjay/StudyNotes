1. Purpose of Industrial Automation Backups

A backup is a controlled, recoverable copy of a machine's software, configuration, parameters, or supporting system state. Its purpose is to restore the machine after program corruption, controller replacement, engineering mistakes, hardware failure, unauthorized changes, or a failed modification.

In industrial maintenance, having a file named backup_latest is not enough. The file could be incomplete, outdated, incompatible with the controller, or impossible to restore because the required engineering software and dependencies are missing. Naming conventions, apparently, cannot substitute for evidence.

A reliable backup system must answer these questions:

  • What exactly has been backed up?
  • Which machine, controller, and device does the backup belong to?
  • When was the backup captured, and what was the machine's state at that time?
  • Is it the approved baseline or merely a working copy?
  • Which software and firmware versions are required to open or restore it?
  • Where is the original backup stored, and is another protected copy available?
  • Has the backup been verified for integrity and tested for restoration?
  • Who captured it, who approved it, and what changes occurred afterward?
  • Can the machine be recovered within the required production recovery time?

Core principle: A backup is not proven useful merely because a file exists. Its integrity, completeness, compatibility, provenance, and recoverability must be established.

2. What Must Be Backed Up?

Industrial equipment contains several layers of information. Saving only the PLC program can leave a machine impossible to restore correctly.

2.1 Backup scope by system

System Important backup items Important limitation
PLC Application project, hardware configuration, controller configuration, required libraries and supported documentation A source project may not capture every runtime state or controller-specific setting
HMI Screens, alarms, recipes, scripts, communication configuration, user configuration where permitted and runtime dependencies Runtime files may differ from the original engineering project
CNC Machine parameters, NC programs, offsets, compensation data, PLC/PMC logic, OEM configuration and applicable system data Files and restore methods vary significantly by controller and machine builder
Robot Robot programs, system configuration, tool/base data, payload data, external-axis configuration and approved safety-related configuration records Restoring programs alone may not restore the complete robot system
VFD Parameter set, motor data, control mode, communication settings and relevant safety configuration records Compatibility may depend on the exact drive model, firmware and options
Servo and motion Drive parameters, motor/feedback configuration, axis data, tuning records and supported motion configuration Incorrect restoration can cause unexpected motion or poor control performance
Safety controller Approved safety project, configuration, validation evidence and required version or signature information Restoration and revalidation must follow the safety manufacturer's and site's procedures
SCADA Project files, tag database, screens, alarms, scripts, runtime configuration and required drivers A project backup may not include external database contents or server configuration
Database Database backup, schema, required configuration and recovery metadata Application-consistent backup and transaction recovery requirements depend on the database system
Engineering workstation Approved system image, installed software inventory, drivers, configuration and recovery instructions Image restoration may require compatible hardware, licenses and activation
Industrial PC OS recovery image, application files, service configuration, network settings and relevant application data Credentials and secrets require separate secure handling
CNC/robot peripherals Applicable tool data, device settings, fieldbus configuration and supported parameter records Peripheral data may be stored separately from the main controller project

Backup scope must be determined from the actual machine architecture, OEM documentation, recovery requirements, and site policy.

2.2 Source project versus controller upload

A source project and a controller upload are not necessarily identical.

  • Source project: The engineering file maintained in the programming or configuration environment.
  • Controller upload: Data retrieved from the physical controller using the supported upload procedure.
  • Compiled or executable data: The form of the program or configuration used by the controller or runtime.
  • Parameter backup: Stored configuration values for a controller, drive, CNC, robot, or other device.
  • System image: A recoverable representation of an operating system and its installed environment.
  • Operational data: Recipes, counters, production records, logs, or other data that may change during operation.

Some controllers cannot reconstruct the original source project from an upload. Comments, symbolic names, libraries, source files, and offline-only information may be missing.

For this reason, preserve the approved source project and, where supported and authorized, a separately identified upload or comparison record from the physical controller.

3. Backup Architecture

A practical backup arrangement separates the original engineering environment, the primary backup repository, and additional protected copies.

Physical Machine / Controller
        ↓
Approved Upload or Source Project
        ↓
Validation and Metadata Recording
        ↓
Primary Controlled Backup Repository
        ↓
Independent Protected Copy
        ↓
Periodic Restore Test
        ↓
Verified Recovery Package

The diagram describes a general process. Some systems require additional vendor-specific steps, especially CNC, robot, safety, and motion controllers.

3.1 Backup storage locations

Location Purpose Main risk to manage
Engineering PC Convenient working copy for authorized maintenance PC failure, malware, accidental overwrite
Controlled local repository Managed storage for approved machine backups Local hardware failure or unauthorized changes
Network repository Centralized backup and access control Network outage, permissions errors or ransomware
Offline or isolated copy Protection from connected-system compromise Physical damage, loss, or failure to update
Separate-site or protected storage Disaster recovery after site-level events Recovery delay and access dependencies
Vendor service media OEM recovery packages and required installation tools Media deterioration, obsolete versions and availability

A USB drive containing the only copy is not a reliable backup strategy. Removable media can be lost, damaged, infected, or overwritten.

3.2 Backup resilience

The widely used 3-2-1 backup principle means:

  • Keep at least three copies of important data.
  • Store them on at least two different storage types or systems.
  • Keep at least one copy off-site or otherwise sufficiently isolated from the primary failure domain.

For industrial control systems, the implementation must account for operational technology constraints, network segmentation, removable-media policies, vendor restrictions, and the need to recover older engineering environments.

The principle does not replace a site-specific risk assessment. Multiple copies on the same storage device or within the same compromised network may fail together.

4. Backup Register and File Naming

A backup repository should be searchable by machine, controller, component, date, version, and purpose.

4.1 Recommended backup register fields

Field Purpose
Backup ID Unique identifier for the backup record
Machine ID Asset or machine reference
Device ID PLC, HMI, CNC, robot, drive or other component identifier
Backup type Source project, upload, parameter set, system image or database backup
File name Exact stored file name
Version Project version or associated software version
Firmware Controller or device firmware where applicable
Capture date and time When the backup was created
Machine state Production, maintenance, commissioning or other relevant condition
Change reference Work order, change request or modification reference
Backup owner Person or team responsible for capture
Approval status Draft, verified, approved, superseded or rejected
Repository location Controlled storage path or repository reference
Integrity hash Checksum such as SHA-256 where used
Verification result Integrity and content checks performed
Restore-test status Not tested, passed, failed or restricted
Recovery notes Dependencies, special restore steps and limitations
Previous version Link to the preceding approved backup
Retention category Applicable retention rule or classification

4.2 File naming convention

A practical convention is:

MACHINEID_DEVICE_BACKUPTYPE_VERSION_YYYYMMDD_HHMM_STATUS

Example:

M105_PLC01_SOURCE_V17_20261017_1430_VERIFIED

This example illustrates the format only. Use the actual machine ID, controller identity, software version, timestamp and verification status.

Recommended rules:

  • Use a unique machine and device identifier.
  • Record date and time in a consistent format.
  • Use a consistent timezone or document the timezone used.
  • Separate source projects, controller uploads, parameter sets and system images.
  • Avoid ambiguous names such as new, final, latest, final_latest2 or working.
  • Do not overwrite the previous approved baseline during a new capture.
  • Use the repository's version history or immutable identifiers where available.
  • Keep sensitive credentials and secrets out of filenames and ordinary metadata.

A file's name is a label, not proof that its contents are valid.

5. Types of Backup and Their Differences

5.1 Source project backup

A source project is the editable engineering representation of a program or configuration. It may contain symbolic names, comments, reusable libraries, hardware configuration, and other information not fully recoverable from the controller.

Best practice: Preserve the original approved project and create a separate working copy for modifications. Record the engineering software version and dependencies required to open it.

5.2 Controller upload backup

An upload captures the data that the controller can provide through its supported upload mechanism.

It can help establish what is currently present in the physical device, but it may not contain all original source information. Some devices restrict uploads, omit source details, or require vendor-specific access and permissions.

Record whether the upload was complete, which connection and procedure were used, and what could not be retrieved.

5.3 Parameter backup

A parameter backup captures configurable values for a device such as a VFD, servo drive, CNC controller, robot, or other industrial component.

Examples include:

  • Motor ratings and control mode.
  • Acceleration and deceleration settings.
  • Speed, torque, current and limit values.
  • Communication addresses and protocol settings.
  • Encoder or feedback configuration.
  • Axis and motion parameters.
  • Process-specific configuration values.
  • Approved safety-related configuration records, where supported.

Parameter files must be associated with the exact device model and relevant firmware. Do not assume a parameter set is interchangeable between different ratings, firmware versions, options, or machine applications.

5.4 System image backup

A system image preserves an operating-system environment and selected installed applications and settings. It may be useful for recovering an engineering PC or industrial PC after storage failure or software corruption.

A system image does not automatically guarantee recovery of:

  • Hardware-bound or unavailable software licenses.
  • External databases or files stored on another volume.
  • Network services and external servers.
  • USB or hardware-dongle dependencies.
  • Application-specific data that was excluded from the image.
  • Configuration stored inside a separate PLC, drive, CNC or robot controller.

Document what the image includes and what must be recovered separately.

5.5 Database backup

A database backup must use the database platform's supported backup and recovery procedures. The method may need to account for transaction consistency, database logs, external dependencies, permissions, encryption keys and recovery objectives.

A copy of database files taken while the database is active is not automatically a valid backup.

For SCADA and production databases, record the database name, engine version, backup type, completion status, retention policy, and restoration procedure. Protect credentials and encryption keys separately through approved secure mechanisms.

6. The Difference Between Latest, Approved and Known-Good

These labels describe different properties and must not be treated as synonyms.

Term Meaning What it does not prove
Latest capture Most recent backup created It may contain an incomplete or faulty configuration
Approved baseline Authorized reference configuration It may not represent the current physical controller
Known-good backup A backup with evidence of correct behavior under defined conditions It may not contain later approved changes
Current controller capture Data retrieved from the physical device at a documented time It may not be the approved or correct operating configuration
Pre-change backup Recovery point created before a modification It does not guarantee that restoration will succeed
Verified backup A backup that passed specified integrity and content checks Verification alone does not prove full machine restoration
Restore-tested backup A backup successfully restored and tested within a defined scope The test may not cover every machine function

For a critical machine, retain both the latest approved baseline and a separately identified pre-change recovery point. If a newer capture is found to contain an unintended change, the last approved version must remain available.

6.1 Backup state model

Captured
   ↓
Integrity Checked
   ↓
Content and Compatibility Verified
   ↓
Reviewed and Approved
   ↓
Stored in Controlled Repository
   ↓
Restore Tested According to Risk
   ↓
Retained as Approved Recovery Point

Not every backup needs the same validation depth. Define the required checks according to the component, machine criticality, recovery consequences and applicable safety requirements.

7. Backup Frequency and Triggers

Backup frequency should be based on change frequency, equipment criticality, data loss tolerance, recovery time requirements and the difficulty of recreating the configuration.

7.1 Event-driven backup triggers

Create or update a backup when:

  • A new machine is commissioned.
  • A controller, drive, HMI, CNC, robot or other device is replaced.
  • A program or parameter set is modified.
  • A firmware or engineering software update is performed.
  • A validated machine improvement is released.
  • A fault investigation requires preservation of the current state.
  • A production issue may have been caused by an unauthorized or accidental change.
  • An approved baseline is established or revised.
  • A system image or engineering workstation is rebuilt.
  • A major process, communication or safety configuration is changed.

Where feasible and authorized, capture the current state before making a change. A pre-change backup is especially important when the existing configuration may be difficult to reconstruct.

7.2 Frequency planning

Asset or data type Suggested planning approach Main consideration
PLC and HMI projects After approved changes and at defined intervals Program change frequency and production criticality
CNC and robot configuration After approved program, parameter or configuration changes Machine-builder dependencies and restoration complexity
Drive and servo parameters Before and after approved parameter changes Risk of incorrect motor or motion configuration
SCADA configuration After approved changes and according to the data recovery plan Runtime, tags, alarms, databases and external dependencies
Database records According to the approved database recovery policy Data-loss tolerance and transaction consistency
Engineering workstation image After validated environment changes and on a defined schedule Software, drivers, licenses and recovery time
Safety-related configuration According to the approved safety lifecycle and change process Validation, authorization and configuration integrity
Legacy systems Based on criticality, recoverability and obsolescence risk Scarce software, interfaces and specialist knowledge

These are planning categories, not fixed intervals. The machine-specific maintenance strategy and site policy determine actual frequencies.

8. Backup Verification

Verification must establish that the backup is identifiable, readable, complete enough for its intended purpose, and compatible with the intended recovery process.

8.1 Verification levels

Level Verification activity What it establishes
Level 1: Existence Confirm file or backup record exists A backup artifact is present
Level 2: Integrity Verify checksum, archive integrity or platform validation The stored artifact matches the expected integrity evidence
Level 3: Content Inspect required project files, metadata and included components The backup contains the expected items
Level 4: Compatibility Confirm supported software, firmware and hardware dependencies The backup can be processed in the intended environment
Level 5: Restoration Restore into a suitable test or recovery environment The documented recovery procedure works within the tested scope
Level 6: Functional validation Perform approved tests against defined acceptance criteria The restored system behaves as expected within the test scope

A successful file copy verifies very little beyond the transfer itself. A checksum verifies integrity relative to a trusted reference, but it does not prove that the original contents were correct.

8.2 Checksum verification

A cryptographic hash such as SHA-256 can be used to detect unexpected changes in a file.

For example, on an approved Windows engineering workstation, PowerShell can calculate a file hash:

Get-FileHash "D:\MachineBackups\M105_PLC01_SOURCE.zip" -Algorithm SHA256

Record the resulting hash in the backup metadata or controlled repository when the procedure requires it.

To compare copies, calculate the hash of each copy and confirm that the values match. A matching hash supports the conclusion that the copies contain identical bytes, assuming the hash reference itself is trustworthy.

A hash does not verify the project logic, the controller compatibility, or the success of a restoration.

8.3 Content verification examples

For a PLC project:

  • Confirm the project opens in the required engineering software.
  • Confirm required libraries and hardware descriptions are available.
  • Compile or validate the project where appropriate.
  • Record unresolved warnings and errors.
  • Compare against the approved baseline or controller capture where supported.

For a drive parameter set:

  • Confirm the file is readable by the supported tool.
  • Verify the target drive model and firmware.
  • Check that motor and application data are identified.
  • Confirm the approved parameter values can be inspected.
  • Do not download parameters to a live drive simply to prove that the file opens.

For a workstation image:

  • Verify the image's integrity and documented contents.
  • Confirm that required recovery media and hardware drivers are available.
  • Restore to a suitable test environment where feasible.
  • Check application launch, license recovery, project access and required interfaces.
  • Record limitations, including hardware-bound licensing or unavailable peripherals.

9. Backup Restoration and Recovery Planning

A restoration procedure describes how to recover the required system state from a known backup. Restoration may involve rebuilding an engineering workstation, loading a controller project, restoring drive parameters, recovering an HMI runtime, or rebuilding a database.

Restoration is not a single universal operation. Each device type has different constraints and risks.

9.1 Recovery sequence

Identify Failure and Recovery Objective
        ↓
Identify Approved Recovery Point
        ↓
Confirm Machine, Device and Version Compatibility
        ↓
Isolate Equipment and Obtain Required Authorization
        ↓
Prepare the Correct Software, Interfaces and Licenses
        ↓
Restore Using the Approved Procedure
        ↓
Verify Configuration and Device Status
        ↓
Perform Required Functional and Safety Validation
        ↓
Authorize Return to Production
        ↓
Record Recovery Results and Update Documentation

The sequence must be adapted to the device and machine. Some restoration operations require OEM involvement, specific service modes, or additional commissioning steps.

9.2 Restoration checklist

  • Confirm the affected machine and exact device identity.
  • Identify the approved recovery objective and backup.
  • Confirm the backup date, version, integrity status and known limitations.
  • Verify the required engineering software, firmware, dependencies and license.
  • Confirm the correct communication interface and connection method.
  • Review machine-specific isolation, access and safety requirements.
  • Preserve the failed or current state when technically possible and authorized.
  • Follow the approved OEM or site restoration procedure.
  • Confirm the expected configuration is present after restoration.
  • Check alarms, communication, interlocks and relevant feedback.
  • Perform required functional tests and safety validation.
  • Obtain authorization before returning the equipment to production.
  • Record actual restoration time, results, deviations and corrective actions.

9.3 Recovery time and data loss objectives

Two important planning measures are:

  • Recovery Time Objective (RTO): The target time within which the system or process must be restored.
  • Recovery Point Objective (RPO): The maximum acceptable amount of data loss expressed as a time interval or defined recovery point.

For example, an RPO of 24 hours means the recovery plan aims to limit lost changes or data to no more than the preceding 24-hour period. It does not mean the restoration itself must take 24 hours.

A machine may have a very recent backup but a long RTO if the required engineering software, license, communication hardware, or specialist is unavailable.

9.4 Recovery time breakdown

A useful recovery estimate separates the major activities:

Activity What to measure
Fault identification Time to identify the failed device or system
Backup selection Time to locate and verify the correct recovery point
Environment preparation Time to prepare software, hardware interfaces and licenses
Restoration Time required to transfer or rebuild the configuration
Validation Time required for functional and required safety checks
Release Time required for authorization and controlled production restart

Use measured recovery exercises rather than guesses to establish realistic recovery targets.

10. Controller-Specific Backup Considerations

10.1 PLC backups

A complete PLC recovery package may require:

  • Original engineering project.
  • Hardware and network configuration.
  • Required libraries and reusable code.
  • Controller model and firmware.
  • Relevant communication and module configuration.
  • Associated HMI or external-device dependencies.
  • Program comparison or verification evidence.
  • Approved download and commissioning procedure.

Where supported, compare the controller's current state against the approved project before making changes. Investigate unexplained differences rather than automatically overwriting the controller.

A download may stop or alter machine operation, change output states, or affect interlocks. Only perform it under the authorized machine-specific procedure.

10.2 HMI backups

Capture the editable HMI project, associated resources, runtime requirements, communication configuration, and any separately stored recipes or data that fall within the recovery scope.

Record the HMI model, firmware or runtime version, screen resolution, communication driver and external dependencies. Confirm whether restoration requires a project download, runtime installation, device-specific conversion, or another method.

Do not assume that downloading an HMI project restores production databases or all data stored on the panel.

10.3 CNC backups

CNC recovery packages may include:

  • NC part programs.
  • Machine parameters.
  • Tool offsets and tool data.
  • Work-coordinate offsets.
  • Compensation data.
  • PLC/PMC logic and related configuration.
  • Machine-builder-specific files.
  • Controller system information and supported recovery media.

Separate machine-specific parameters from transferable NC programs. A program that can run on one machine may not be safe on another machine with different tooling, fixtures, offsets, axis configuration or machine-builder logic.

Protect machine parameters and compensation values as controlled configuration. Validate them according to the machine builder's procedure before releasing the machine.

10.4 Robot backups

Robot backups may include application programs, system configuration, tool and base data, payload settings, external-axis information, communication configuration and safety-related records.

Record the controller model, software release, options, robot model, external equipment dependencies and approved restoration method.

After restoration, follow the applicable OEM procedure for verification of frames, payloads, external axes, motion limits, interlocks and safety functions. Program restoration alone is not sufficient evidence that the complete robot cell is ready for production.

10.5 VFD and servo backups

Before restoring a drive, confirm:

  • Exact model, rating and firmware.
  • Motor nameplate data and motor type.
  • Control mode and feedback-device configuration.
  • Acceleration, deceleration and operating limits.
  • Communication address and network configuration.
  • Safety-related options and required validation.
  • Parameter-file compatibility and approved restore procedure.

After restoration, verify that the drive has the intended motor and application configuration. Unexpected movement, incorrect speed, torque behavior or communication settings can damage equipment or create hazards.

10.6 Safety controller backups

Safety-related configurations require stricter controls because an incorrect restore can undermine risk-reduction functions.

Preserve the approved safety project, version and signature information where applicable, validation records, device identity, and the procedure required to restore and validate the configuration.

Do not treat a successful file transfer or matching program name as proof of safety integrity. Required verification, validation, approvals and functional tests must follow the safety design, OEM instructions and site procedures.

11. Versioning, Baselines and Change History

Backup versioning makes it possible to distinguish a known-approved state from later modifications and temporary experiments.

11.1 Recommended baseline structure

Backup class Purpose Typical handling
Commissioning baseline Records the approved state at initial handover Preserve as a historical reference
Approved production baseline Records the authorized operating configuration Retain under controlled access
Pre-change recovery point Preserves the state immediately before a modification Retain through change validation and according to policy
Post-change candidate Records the new state after an approved change Verify before promoting to approved baseline
Current-state capture Records the state observed on the physical device Keep separate from the approved baseline until differences are assessed
Emergency recovery copy Supports an urgent restoration Record the reason, approval and subsequent review
Superseded baseline Preserves a previous approved state Retain according to risk and retention policy

11.2 Change log fields

Record the backup ID, previous backup ID, change reference, date and time, person responsible, reason for change, affected device, software version, summary of differences, verification results, approval, and rollback decision.

Where supported, use version-control tools or repository history to compare source files and maintain traceable revisions. Binary project files may require vendor tools or specialized comparison methods.

Do not rely on filenames alone to establish the sequence of changes.

11.3 Comparing current and approved states

A discrepancy review should answer:

  • Does the physical controller match the approved project?
  • Are differences expected and authorized?
  • Could differences be caused by a legitimate online change, firmware update or configuration action?
  • Is the available upload complete enough to make the comparison meaningful?
  • Does the difference affect process behavior, safety, communication or recovery?
  • Which state is authorized to become the new baseline?

Record the findings and obtain approval before replacing an approved baseline with a newly captured state.

12. Backup Security and Access Control

Backup files may expose machine logic, process knowledge, network configuration, production recipes and other sensitive operational information. Some files may also contain credentials or other secrets.

12.1 Required controls

  • Restrict write access to authorized personnel.
  • Use separate permissions for reading, modifying, approving and deleting backups where supported.
  • Protect important recovery copies from accidental overwrite and ransomware.
  • Keep a protected copy outside the primary failure domain.
  • Record backup creation, modification, deletion and restoration events where possible.
  • Use approved encryption and key-management methods when required.
  • Store credentials and secrets separately in an approved secure system.
  • Scan transferred files using approved security controls without disrupting isolated legacy environments.
  • Verify removable media and transfer procedures before use on OT equipment.
  • Define retention and secure disposal requirements.
  • Test recovery access without weakening production-network security.

12.2 Immutable and offline backups

An immutable backup is protected from modification or deletion for a defined period by the storage system's controls. An offline backup is disconnected from the relevant systems when not in use.

These protections reduce the risk that an attacker or accidental operation will destroy every recovery copy. Neither approach removes the need for access controls, integrity checks, appropriate retention, and restoration testing.

12.3 Backup access register

For critical machine backups, document the repository owner, authorized roles, access approval process, retention policy, recovery access method, and responsible team. Avoid recording passwords or private keys in the register.

A backup that exists but cannot be accessed during a plant emergency is an availability failure, even if the file itself is intact.

13. Common Backup Failure Scenarios

Failure scenario Why recovery fails Preventive control
Wrong machine backup selected Similar machine names or copied projects cause confusion Unique machine and device IDs with compatibility checks
Latest file is corrupted Copy or storage failure was not detected Integrity checks and protected copies
Source project is missing Only a controller upload was preserved Maintain the approved editable project where supported
Required engineering software is unavailable Installer or license dependency was not recorded Preserve approved installers and dependency records
Backup is incompatible with firmware Controller or device version changed Record firmware and verify restoration compatibility
Only one copy exists A single disk or workstation failure destroys recovery data Maintain independent protected copies
Backup contains unauthorized changes The latest capture was assumed to be correct Separate current-state captures from approved baselines
Restore fails on a replacement PC Drivers, interfaces, runtime packages or licenses are missing Maintain a validated workstation recovery package
CNC machine runs incorrectly after restore Offsets, parameters or machine-specific data are wrong Use OEM procedures and validate machine configuration
Robot motion differs after restoration Frames, payloads, external axes or configuration are inconsistent Validate complete cell configuration before production
Safety configuration is not validated File transfer was treated as proof of safety Follow the required safety validation and approval process
Database recovery loses recent records Backup and transaction-recovery strategy was incomplete Define and test database-specific recovery procedures
Recovery copy is deleted or encrypted All copies share the same failure domain Use isolated or immutable storage and controlled retention
Backup is outdated No change-triggered capture or review occurred Define backup triggers and monitor record freshness

14. Backup Performance Indicators

A backup process can be measured rather than judged by the number of files stored.

KPI Calculation or definition What it reveals
Backup coverage Devices with required backups divided by devices requiring backups, multiplied by 100 Coverage gaps
Verification compliance Backups passing required verification divided by backups due for verification, multiplied by 100 Integrity and validation discipline
Restore-test success rate Successful restore tests divided by completed restore tests, multiplied by 100 Recovery readiness within the tested scope
Backup freshness Time elapsed since the last required successful capture Risk of missing recent changes
Recovery time Elapsed time from recovery initiation to the defined restored state Actual recovery performance
Recovery-point gap Time between the failure or required recovery point and the latest usable backup Potential loss of changes or data
Missing dependency count Number of required software, license, driver or interface dependencies unavailable Recovery obstacles
Unapproved discrepancy count Number of unresolved differences between the controller and approved baseline Configuration-control risk
Critical asset coverage Critical devices with verified recovery packages divided by critical devices requiring them, multiplied by 100 Exposure among high-impact assets

Define the denominator, measurement period and acceptance target for each KPI. A high restore-test success rate does not prove that every machine can be restored if critical devices were excluded from testing.

15. Practical Exercise: Build a Machine Backup Register

Choose one machine and create a controlled backup record using the actual machine documentation and approved procedures.

  • Identify the machine, controller, HMI, CNC, robot, drive and other relevant devices.
  • Locate the approved source projects and available controller uploads.
  • Identify parameter sets and other machine-specific configuration files.
  • Record software versions, firmware, dependencies and license requirements.
  • Record capture dates, machine states and associated change references.
  • Separate the latest capture from the approved production baseline.
  • Verify file integrity and expected contents.
  • Identify the primary repository and independent protected copy.
  • Document the approved restoration procedure for each critical device.
  • Identify any missing installers, licenses, interfaces or dependencies.
  • Record the required RTO and RPO according to the machine's recovery requirements.
  • Verify that the recovery package can be accessed by authorized personnel.
  • Arrange an approved restore test where practical and safe.
  • Record test scope, result, limitations, corrective actions and next review date.

16. Final Acceptance Checklist

The backup documentation is complete enough for maintenance when an authorized engineer can locate the correct recovery point, establish what it contains, determine whether it is compatible, and follow a documented restoration procedure.

  • Each critical controller and software component has a defined backup scope.
  • The approved source project is distinguished from controller uploads and parameter files.
  • Backup names and register records uniquely identify the machine and device.
  • Versions, firmware, capture timestamps and change references are recorded.
  • Latest captures and approved baselines are clearly distinguished.
  • Integrity and content verification results are documented.
  • Required installers, drivers, libraries, licenses and interfaces are identified.
  • Primary and independent protected backup locations are documented.
  • Access permissions and retention rules are defined.
  • Restoration procedures and required approvals are documented.
  • Restore-test status and known limitations are recorded.
  • Safety-related configurations have the required validation evidence.
  • Recovery objectives and responsible owners are identified.
  • Backup changes and discrepancies are traceable.
  • Missing dependencies and recovery risks have assigned corrective actions.

Expected outcome: The machine knowledge base should provide a traceable, protected and recoverable collection of approved programs and parameter sets. The aim is not merely to save files, but to restore the correct machine configuration with verified compatibility, controlled risk and documented results.
