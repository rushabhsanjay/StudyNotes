1. Purpose of Machine Process Documentation

A machine process record describes what a machine does, in what sequence it operates, what conditions permit each step, what outputs it produces, and how it responds when the process cannot continue.

The machine overview identifies the machine. The process record explains its operational behavior.

For industrial maintenance, this distinction matters because troubleshooting requires more than knowing which PLC, sensor, or motor is installed. The technician must understand what the machine is supposed to do when the equipment is healthy.

For example, if an engine test bench fails to start a test, the fault could involve part identification, fixture clamping, safety permissives, instrumentation readiness, a PLC sequence condition, or test-software authorization. Knowing the process sequence narrows the investigation.

The purpose of this record is to establish a common technical reference for maintenance, production, controls engineering, quality, and safety.

2. What Is a Machine Process?

A machine process is the sequence of operations through which equipment transforms an input into an intended output.

Inputs may include:

  • Raw materials, workpieces, assemblies, or engines.
  • Operator commands and production orders.
  • Electrical power, compressed air, hydraulic pressure, and other utilities.
  • Sensor signals, identification data, and process parameters.
  • Safety conditions and control-system permissives.

Outputs may include:

  • A machined, assembled, tested, inspected, or processed product.
  • Measurements and quality results.
  • Production status and traceability records.
  • Reject decisions or fault indications.
  • Data transferred to PLCs, HMIs, SCADA, MES, or other systems.

A process record should explain the actual operation rather than merely list the machine's installed components.

For example, “PLC reads sensor” is a control action. “The machine confirms that the workpiece is correctly positioned before enabling clamping” explains the purpose of that action within the process.

3. Process Documentation Versus Other Machine Records

Record type Main question answered Example
Machine overview What is the machine, and where is it? Engine Test Bench 03 in the engine test area
Process description What steps does the machine perform? Identify engine, connect test interfaces, execute test, record results
Electrical architecture How is electrical power distributed and controlled? Incoming supply, main isolator, distribution, drives, control power
Control architecture How are the operations controlled? PLC, remote I/O, HMI, CNC, robot controller
Sequence specification What conditions and transitions govern each step? Clamp confirmation must be true before the cycle advances
Safety documentation How are hazards controlled and safety functions validated? Guard interlocks, emergency stops, safety controller
Maintenance procedure How is the equipment inspected, serviced, or repaired? Sensor inspection, calibration checks, drive diagnostics
Quality specification What determines whether the output is acceptable? Dimensional limits, torque window, leak-rate limit

These records are related but not interchangeable. A process description should link to detailed sequence, safety, electrical, and quality documents rather than attempting to replace all of them.

4. Process Boundaries

Before documenting the sequence, define where the machine process begins and ends.

A typical process boundary includes:

  • The conditions required to accept a new workpiece or production order.
  • The operations performed by the machine.
  • The checks performed during those operations.
  • The criteria for accepting, rejecting, or stopping the process.
  • The final output and the conditions for releasing the workpiece.

A machine may depend on systems outside its boundary, such as an upstream conveyor, plant network, shared hydraulic power unit, or production database.

Record these dependencies separately so that external conditions are not incorrectly described as internal machine operations.

4.1 Example: CNC machining centre

Input workpiece
→ Confirm machine ready
→ Load and identify workpiece
→ Clamp and verify fixture
→ Confirm required tool and program
→ Execute machining cycle
→ Perform required checks
→ Release or unload workpiece
→ Record cycle status and result

This is a simplified functional sequence. The actual machine may perform probing, tool measurement, coolant checks, door interlocking, chip removal, in-process measurement, and other operations.

The approved machine sequence and OEM documentation determine the real order and conditions.

5. Standard Structure of a Process Record

A useful process record should contain the following sections.

5.1 Process identification

  • Machine ID and machine name.
  • Process name and process ID, if used.
  • Production or testing purpose.
  • Applicable product or workpiece type.
  • Revision and approval status.
  • Related work instructions, drawings, quality specifications, and safety documents.

5.2 Process inputs

Document what must be available before the process can run.

Examples:

  • Correct workpiece or assembly.
  • Production order or approved test recipe.
  • Required utilities and energy supplies.
  • Valid sensor signals and feedback.
  • Correct tooling, fixture, or test adapter.
  • Required communication with other equipment.
  • Safety conditions and machine-ready status.

5.3 Process steps

For every significant step, identify:

  • Step number and name.
  • What the machine does.
  • Required entry conditions.
  • Actuator or subsystem involved.
  • Feedback confirming completion.
  • Expected result.
  • Timeout, fault, or abnormal condition.
  • Next step or recovery path.

5.4 Process outputs

Record the expected outputs, including product condition, test results, process measurements, production status, and traceability data.

5.5 Abnormal conditions

Describe how the process responds to missing feedback, invalid inputs, failed quality checks, utility loss, communication failures, and safety-related interruptions.

Do not invent recovery actions. Use approved procedures and OEM or engineering documentation for actual recovery behavior.

6. Process Step, Transition, Permissive, and Interlock

These terms describe different parts of automated operation.

Term Meaning Example
Process step An operation being performed Clamp the workpiece
Entry condition Condition required before entering a step Workpiece detected at the station
Permissive Condition that must be satisfied to allow an operation Required air pressure is available
Transition condition Condition that advances the sequence Clamp-closed feedback is confirmed
Interlock Condition that inhibits an operation to prevent an unacceptable state Guard condition prevents hazardous motion
Timeout Maximum permitted time for an expected action Clamp confirmation not received within the approved limit
Fault response Defined response when a step cannot proceed normally Stop sequence and report a clamp fault
Recovery condition Required condition before the sequence can resume Fault cleared and machine returned to an approved state

A permissive, transition, and safety interlock are not necessarily the same thing. Their exact implementation and safety significance depend on the machine design.

A standard PLC bit must not be assumed to provide a safety-rated function merely because it prevents an operation.

7. Example Process Record: Automated Clamping and Machining

The following example illustrates the documentation structure. It is not a machine-specific control specification.

Step Operation Required condition Completion evidence
1 Accept workpiece Correct station state and workpiece present Presence and identification confirmed
2 Verify readiness Required utilities and machine conditions available Ready status confirmed
3 Clamp workpiece Clamping operation permitted Approved clamp feedback received
4 Verify machining readiness Correct program and required tooling available Readiness checks passed
5 Execute machining All required cycle-entry conditions satisfied Machining sequence completes
6 Perform required checks Measurement system ready, where applicable Check result available
7 Release workpiece Process complete and release permitted Clamp-open feedback confirmed
8 Record result Required result and traceability fields available Record stored and cycle status updated

The table describes the intended process at a high level. Actual PLC step numbers, sensor addresses, timer values, alarm numbers, and safety conditions belong in controlled technical documents.

8. Process Sequence and State Management

Automated machines often use a state-based sequence rather than relying on one long, loosely defined chain of logic.

Common states include:

  • Stopped: The machine is not executing the automatic process.
  • Not ready: One or more required conditions are not satisfied.
  • Ready: Required conditions for starting the process are satisfied.
  • Starting: The machine is preparing to begin the cycle.
  • Running: The process is executing.
  • Holding or paused: The process is temporarily prevented from progressing.
  • Complete: The process has reached its defined successful end.
  • Faulted: An abnormal condition requires a defined response.
  • Recovery: The machine is being returned to an approved operating state.

The names and transitions vary by machine. These are conceptual categories, not a requirement to use a particular PLC programming standard.

8.1 Why state documentation matters

Suppose a machine is stopped because the workpiece clamp does not confirm closure.

Without process-state documentation, the fault may be described simply as “cycle not starting.”

With process-state documentation, maintenance can determine whether the machine is:

  • Waiting for workpiece detection.
  • Waiting for a clamp command to be accepted.
  • Waiting for clamp-closed feedback.
  • Blocked by an independent permissive.
  • Faulted because the approved timeout was exceeded.

That distinction prevents indiscriminate replacement of sensors, valves, or PLC hardware.

9. Documenting Sensors, Actuators, and Feedback

Each process step should identify the functional devices involved. Detailed addresses can be maintained in the I/O list.

Device type Role in the process Example
Proximity sensor Detects object presence or position Workpiece present
Photoelectric sensor Detects an object or position using light Part at conveyor stop
Limit switch Confirms a mechanical position Fixture at end position
Pressure switch or transmitter Confirms or measures pressure Required clamping pressure
Solenoid valve Controls a pneumatic or hydraulic action Extend clamp cylinder
Motor or drive Produces mechanical motion Conveyor movement
Servo system Controls position, speed, or torque Indexing table
Encoder Provides motion or position feedback Axis position
Vision system Inspects defined product features Part orientation or defect check
Barcode reader Identifies the workpiece Part number or serial number
Temperature or pressure instrument Measures process conditions Engine test parameter
PLC or controller Coordinates the sequence Automatic cycle control
HMI Displays status and accepts authorized commands Cycle start and alarm display

The record should distinguish the command from the confirmed result.

For example:

  • Command: Extend the clamping cylinder.
  • Feedback: Clamp-closed sensor indicates the required position.
  • Process conclusion: Clamping position has been confirmed, subject to the machine's specified checks.

A valve command does not prove that the cylinder moved. A motor-run command does not prove that the conveyor moved. Industrial machinery is full of devices that can be told to do something without actually doing it.

10. Timing, Counters, and Process Parameters

Where timing or quantitative limits affect the process, reference the approved parameter specification.

Relevant parameters may include:

  • Maximum permitted operation time.
  • Pressure or force range.
  • Temperature range.
  • Torque and angle limits.
  • Position tolerance.
  • Spindle speed and feed rate.
  • Test duration and sampling rate.
  • Permitted retry count.
  • Measurement acceptance limits.
  • Cycle count and production quantity.

Do not insert guessed values into the machine knowledge base. Record the parameter name, engineering unit, approved source, and applicable revision.

10.1 Cycle time

Cycle time is the elapsed time for a defined cycle boundary, such as from cycle start to cycle completion.

\[ T\_{\text{cycle}}=t\_{\text{completion}}-t\_{\text{start}} \]

The start and end events must be defined consistently. If one report measures from workpiece detection and another from the PLC's cycle-start event, their values may differ even when both calculations are correct.

Document whether the recorded cycle time includes loading, unloading, automatic inspection, and result transfer.

11. Abnormal Conditions and Fault Responses

A process record should explain the main ways a cycle can fail and identify the appropriate reference for recovery.

Abnormal condition Possible process effect Documentation requirement
Workpiece not detected Sequence cannot begin Record detection condition and approved response
Clamp feedback missing Machine cannot confirm required fixture state Reference diagnostic and recovery procedure
Required pressure unavailable Operation may be inhibited Record relevant pressure permissive
Tool or program mismatch Machining may be blocked Reference approved tool and program verification
Communication loss Required device or data becomes unavailable Identify affected interface and expected response
Quality result outside limits Product may be rejected or quarantined Reference quality disposition procedure
Utility supply loss Operation may stop or become unavailable Reference machine-specific response
Safety function activated Hazardous operation may be inhibited or stopped Follow the validated safety design and recovery procedure
Result storage failure Traceability or cycle completion may be affected Record data-handling and recovery requirements

The process record should distinguish between a machine fault, a process-quality failure, and a safety-related interruption. They may occur at the same time but require different responses.

12. Process Documentation for Different Machine Types

12.1 CNC machine tool

Typical sequence:

  1. Confirm machine readiness.
  2. Load and identify the workpiece.
  3. Verify fixture and clamping state.
  4. Confirm the approved program and tooling.
  5. Execute the machining cycle.
  6. Perform required probing or measurement.
  7. Release the workpiece.
  8. Store required production or quality information.

Document the relationship between the CNC, PLC, drives, tooling system, coolant system, probing equipment, and operator interface.

12.2 Robotic welding cell

Typical sequence:

  1. Confirm the cell is in the required operating state.
  2. Detect and identify the workpiece.
  3. Verify fixture and clamping conditions.
  4. Confirm required equipment and process readiness.
  5. Execute the approved robot and welding sequence.
  6. Check process-completion status.
  7. Release the part or transfer it to the next station.
  8. Record the cycle result and any required traceability data.

Robot motion, welding equipment, fixture logic, and safety functions may be controlled by different systems. Document their functional interaction and reference the approved safety and welding specifications.

12.3 Engine test bench

Typical sequence:

  1. Identify the engine and test requirement.
  2. Confirm test-bench readiness and required utilities.
  3. Connect or verify required mechanical and electrical interfaces.
  4. Verify instrumentation and test-system readiness.
  5. Execute the approved test procedure.
  6. Acquire and evaluate required measurements.
  7. Determine the result against approved acceptance criteria.
  8. Store test data and release the equipment or engine according to the approved process.

The record should identify the responsible control system, measurement system, test application, and result-storage path.

12.4 Automated assembly or torque station

Typical sequence:

  1. Identify the workpiece and fastening requirement.
  2. Verify positioning and clamping.
  3. Confirm the required tool and fastening program.
  4. Execute the fastening operation.
  5. Collect torque, angle, or other specified result data.
  6. Evaluate the result against approved limits.
  7. Mark or record the result as required.
  8. Release the part or route it to the defined reject process.

The process record should reference the approved torque specification, tool program, traceability requirement, and reject-handling procedure.

13. Relationship Between Process and PLC Logic

Process documentation should describe intended behavior independently of a particular PLC address or programming language.

A useful separation is:

  • Process description: What must happen and why.
  • Sequence specification: Conditions and transitions for each step.
  • I/O list: Signal names, addresses, types, and descriptions.
  • PLC program documentation: How the control logic implements the sequence.
  • Alarm list: Fault conditions, messages, and priorities.
  • Safety documentation: Validated safety functions and required behavior.

For example, the process record can state that clamping must be confirmed before machining starts. The I/O list identifies the actual clamp sensor signal, and the PLC documentation shows how the signal is evaluated.

This structure makes the process record useful even when a PLC is replaced or its program is reorganized.

14. Process Validation and Change Control

The documented process must reflect the approved machine behavior. It should not be rewritten solely because someone observes a different sequence during a fault.

Validate the process against:

  • OEM manuals and approved machine specifications.
  • Electrical and pneumatic/hydraulic schematics.
  • Approved sequence and control descriptions.
  • Production work instructions.
  • Quality acceptance criteria.
  • Validated safety documentation.
  • Controlled software versions and approved engineering changes.

If the actual machine differs from the documentation, record the discrepancy and have it reviewed by the responsible engineering authority.

A process change may affect cycle time, quality, traceability, interlocks, maintenance procedures, and risk controls. It therefore requires the applicable approval and validation process.

16. Common Process Documentation Mistakes

Mistake Consequence Correct practice
Recording only the normal sequence Troubleshooting information is incomplete Include abnormal conditions and recovery references
Listing components instead of operations Process behavior remains unclear Describe actions, conditions, and results
Confusing command with feedback False assumptions about completed motion Record independent completion evidence
Using vague step names Different technicians interpret the sequence differently Use specific, observable actions
Guessing timers or acceptance limits Unsafe or incorrect troubleshooting Reference approved specifications
Mixing safety logic with ordinary permissives Safety significance can be misunderstood Reference validated safety documentation
Embedding PLC addresses everywhere Documentation becomes fragile after program changes Separate process, I/O, and program records
Ignoring quality disposition Failed parts may be handled incorrectly Reference the approved reject and containment procedure
Omitting external dependencies Troubleshooting remains confined to the machine Record shared utilities and communication dependencies
Failing to control revisions Maintenance may use outdated process behavior Maintain approval and revision history

17. Knowledge Check and Interview Questions

1. What is the purpose of a machine process record?

It describes the machine's operational sequence, required conditions, expected outputs, and abnormal behavior.

2. What is the difference between a process step and a transition condition?

A process step describes the operation being performed. A transition condition determines when the sequence may move to another step.

3. Why must commands and feedback be documented separately?

A command only requests an action. Feedback provides evidence that the expected condition occurred.

4. What is the difference between a permissive and a safety interlock?

A permissive allows an operation when required conditions are met. A safety interlock is part of a design intended to control a hazard and must be implemented and validated according to the applicable safety requirements.

5. Why should timer values and quality limits not be guessed?

Incorrect values can cause false faults, defective products, process deviations, or unsafe machine behavior.

6. How does process documentation help PLC troubleshooting?

It identifies the expected step, entry conditions, completion evidence, and relevant dependencies, helping the technician find where actual behavior diverges from intended behavior.

7. Should a process record contain every PLC address?

Not usually. Detailed signal addresses belong in the controlled I/O list and program documentation, with references from the process record.

8. Why document abnormal conditions?

They help technicians distinguish between failed devices, unmet process conditions, quality failures, and communication problems.

9. How is cycle time defined?

It is the elapsed time between clearly defined start and completion events. The chosen boundaries must remain consistent when comparing results.

10. What should happen if the documented sequence differs from actual machine behavior?

Record the discrepancy and investigate it against approved specifications, control logic, safety documentation, and engineering change records before revising the process documentation.

18. Final Verification Checklist

  • Process purpose and boundaries are clearly defined.
  • Inputs, outputs, and required utilities are documented.
  • Each major process step is described in the correct order.
  • Entry conditions and completion evidence are identified.
  • Commands are distinguished from feedback.
  • Timers, limits, and parameters reference approved specifications.
  • Major abnormal conditions and recovery references are included.
  • Quality decisions and traceability requirements are documented.
  • Dependencies on other machines and shared systems are identified.
  • PLC, I/O, alarm, safety, and quality records are cross-referenced.
  • Actual behavior has been checked against approved documentation.
  • Document revision and approval status are controlled.
