1. Definition

PLC-scanner communication commissioning is the process of configuring, integrating, and validating communication between a PLC and an industrial scanner or scanning system so that the PLC receives the correct identification, measurement, position, or inspection data and can use it reliably in the machine sequence.

In industrial automation, the term scanner can refer to several different devices:

  • Barcode scanner: Reads 1D barcodes and 2D codes such as QR codes or Data Matrix.
  • Industrial identification reader: Reads product, component, or traceability codes.
  • Laser measurement scanner: Measures distance, dimensions, profiles, or object geometry.
  • Vision scanner or code reader: Uses an imaging sensor to identify codes or inspect features.
  • Safety laser scanner: Detects people or objects within configured protective fields and provides safety-related outputs.
  • Area or 3D scanner: Detects object presence, shape, position, or volume.

These devices do not all communicate in the same way. A barcode reader returning a product ID is fundamentally different from a safety laser scanner protecting access to a robot cell. Commissioning must begin by identifying the device type and its intended function.

2. Objectives and Scope

The main objectives are to verify that:

  • The scanner is installed and configured correctly.
  • The PLC can communicate with the scanner using the intended interface.
  • Scanner data reaches the correct PLC variables.
  • Data formatting, byte order, scaling, and validity are correct.
  • Successful reads, failed reads, and communication faults are distinguished.
  • The machine sequence responds correctly to scanner results.
  • Invalid or stale data cannot accidentally authorize the wrong operation.
  • Diagnostic information is available to maintenance personnel.
  • Required safety functions are validated separately where a safety scanner is used.

Typical applications include part identification, model selection, barcode-based traceability, robot guidance, dimensional inspection, presence detection, and protective-field monitoring.

3. Typical PLC-Scanner Architecture

For an ordinary industrial identification scanner, a typical architecture is:

Barcode / Data Matrix / QR Code
             ↓
Industrial Scanner
             ↓
Ethernet / PROFINET / EtherNet/IP / Serial / Digital I/O
             ↓
PLC Communication Interface
             ↓
Data Validation and Decoding
             ↓
Part Identification and Sequence Logic
             ↓
HMI / MES / Traceability Database / Machine Control

A safety laser scanner follows a different architecture because its protective function must be implemented through an appropriate safety-rated system.

Protective Field and Scanner Sensors
             ↓
Safety Laser Scanner
             ↓
Safety Outputs or Safety Communication
             ↓
Safety Relay / Safety PLC / Compatible Safety Controller
             ↓
Validated Machine Safety Function

A standard PLC may monitor diagnostic or status information from a safety scanner, but ordinary PLC logic must not replace the validated safety function.

4. Identify the Scanner Before Commissioning

Before connecting or configuring the scanner, identify its function and interface.

Scanner type Typical output Common use
Barcode or code reader Text, code bytes, result status Product identification and traceability
Laser displacement scanner Distance or measurement values Position and dimensional checks
Profile scanner Point cloud, profile, or measurement data Geometry and quality inspection
Vision-based reader Code, image result, or inspection status Identification and visual inspection
Safety laser scanner Safety outputs, protective-field status, diagnostics Personnel protection
Presence scanner Object-present or detection data Part detection and machine sequencing

The device manual and machine-builder specification determine the actual capabilities. A scanner may support several interfaces, but only one or a limited combination may be configured for the machine.

5. Common Communication Interfaces

Interface Typical application Commissioning checks
Discrete digital I/O Trigger, busy, result-valid, good-read, fault Wiring, polarity, voltage, pulse timing, and feedback
Serial RS-232 Barcode data and simple device commands Baud rate, parity, data bits, stop bits, and termination
Serial RS-485 Industrial serial communication Wiring topology, termination, biasing, and protocol configuration
TCP/IP Ethernet Scanner commands and result data IP address, port, connection behavior, and message framing
PROFINET Cyclic industrial data exchange Device name, IP configuration, hardware configuration, and I/O mapping
EtherNet/IP Cyclic or configured industrial data exchange Device identity, connection settings, and assembly mapping

A scanner may use Ethernet for configuration but provide its production result through PROFINET, TCP sockets, or digital outputs. Do not assume that the configuration interface is also the production interface.

6. Pre-Commissioning Requirements

Collect the following before changing the system:

  • Scanner manufacturer, model, serial number, and firmware.
  • Scanner application and intended function.
  • PLC model, firmware, and engineering software version.
  • Scanner configuration backup or configuration export.
  • Electrical drawings and I/O list.
  • Network topology, IP addresses, device names, and port assignments.
  • Communication protocol and data-format specification.
  • Trigger conditions and expected reading rate.
  • Expected code format, measurement range, or detection behavior.
  • PLC tag mapping and machine sequence description.
  • Safety documentation and risk assessment if a safety scanner is involved.
  • Existing fault logs and the approved recovery procedure.

The scanner's optical setup also matters. A perfectly configured PLC cannot compensate for an unreadable label, unsuitable working distance, excessive glare, poor mounting, or a damaged lens.

7. Physical Installation and Optical Setup

7.1 Mounting and alignment

For a barcode or identification scanner, verify:

  • The scanner is rigidly mounted.
  • The working distance is within the manufacturer's specified range.
  • The reading angle and field of view are suitable.
  • The entire code can be seen under normal operating conditions.
  • The label or code is positioned consistently.
  • Vibration does not move the scanner or blur the image.
  • Ambient light and reflective surfaces do not interfere with reading.
  • The lens and protective window are clean.
  • Cables are routed away from sources of electrical interference where required.

For a measurement scanner, also verify the specified reference plane, measurement range, mounting geometry, calibration status, and environmental limits.

7.2 Code quality and application setup

For identification systems, confirm:

  • Correct symbology, such as Code 128 or Data Matrix.
  • Expected code length and character set.
  • Prefixes, suffixes, separators, and terminators.
  • Check-digit handling, if applicable.
  • Duplicate-code behavior.
  • Multiple-code selection rules.
  • Read timeout and retry policy.
  • Good-read and no-read reporting.

A reader that successfully decodes a code is not necessarily proving that the code belongs to the correct product. PLC logic must validate the result against the expected production sequence and permitted values.

8. Network Configuration and Communication Verification

8.1 Ethernet configuration

Verify:

  • Correct scanner IP address.
  • Correct subnet mask and any required gateway.
  • Unique addresses within the network.
  • Correct Ethernet port and cable.
  • Correct PLC hardware configuration.
  • Correct protocol and connection settings.
  • No duplicate IP address or unexpected routing issue.
  • Stable communication during normal machine operation.
  • Correct scanner startup behavior after power cycling.

A ping response proves only basic IP reachability. It does not prove that a PLC connection is established, that process data is valid, or that the scanner is returning current results.

8.2 PROFINET and EtherNet/IP

For PROFINET, verify the configured device identity, device name, network parameters, module configuration, and input/output mapping.

For EtherNet/IP, verify the device identity, connection configuration, requested packet interval where applicable, input/output assembly layout, and connection status.

For both protocols:

  1. Compare the configured device with the installed scanner.
  2. Confirm the expected cyclic data length.
  3. Monitor raw input and output data.
  4. Confirm the intended trigger and result bits.
  5. Validate the data format and interpretation.
  6. Check connection-loss diagnostics and recovery behavior.

The exact device configuration depends on the scanner model, PLC platform, and supported protocol options.

9. PLC-Scanner Signal Mapping

Signal mapping links a physical or communication-interface signal to its intended PLC variable and machine function.

A typical identification scanner may use the following signals.

Signal Typical direction Purpose
Trigger request PLC to scanner Requests a new read
Trigger accepted or ready Scanner to PLC Indicates readiness or acceptance, depending on the interface
Busy Scanner to PLC Indicates an operation is in progress
Good read Scanner to PLC Indicates a successful decode
No read Scanner to PLC Indicates that no valid code was decoded
Result valid Scanner to PLC Indicates that result data is available
Result data Scanner to PLC Contains the decoded value
Acknowledge or result clear PLC to scanner Clears or acknowledges a result when supported
Scanner fault Scanner to PLC Indicates a device or application fault
Communication status Interface to PLC Indicates communication health
Quality or confidence value Scanner to PLC Provides a reading-quality measure where supported

These signals are examples, not a universal interface definition. Some scanners provide a single result status; others use handshakes or structured data records.

9.1 Mapping verification procedure

For each signal:

  1. Identify the source and destination.
  2. Verify the physical I/O address or communication-data offset.
  3. Confirm the expected active state.
  4. Monitor the raw value.
  5. Compare the raw value with the mapped PLC variable.
  6. Trigger a controlled test.
  7. Confirm that the intended state or data changes.
  8. Verify that unrelated signals do not change unexpectedly.
  9. Record the result and restore normal operation.

For structured data, also check the field length, byte order, character encoding, signedness, and validity indicators.

10. Scanner Trigger and Read Handshake

A trigger is the command that starts a reading or measurement operation. It may be initiated by a PLC output, an Ethernet command, a sensor input, or an internal scanner event.

A typical PLC-triggered barcode-read sequence is:

PLC confirms correct part is present
             ↓
PLC confirms scanner is ready
             ↓
PLC issues trigger request
             ↓
Scanner accepts trigger and starts reading
             ↓
Scanner reports result or no-read
             ↓
PLC validates result status and data
             ↓
PLC acknowledges or clears result if required
             ↓
PLC permits the next sequence step

10.1 Handshake design considerations

The interface specification must define:

  • Whether the trigger is a pulse or maintained signal.
  • Whether the scanner requires a rising edge.
  • How trigger acceptance is confirmed.
  • How busy status is interpreted.
  • When result data becomes valid.
  • Whether result-valid remains active until acknowledgement.
  • How a no-read condition is reported.
  • Whether the result must be copied before acknowledgement.
  • How the trigger is reset.
  • What happens if the scanner never responds.
  • Whether multiple triggers can be queued or must be separated.

Do not assume that every scanner uses TRIGGER, BUSY, GOOD_READ, and RESULT_VALID as separate signals. Some interfaces use a command-response message, while others exchange cyclic status and data.

10.2 Avoid repeated triggering

If the PLC maintains a trigger signal continuously when the scanner expects a rising edge, the scanner may execute only one read. Conversely, if the scanner treats a maintained signal as repeated triggering, it may perform multiple reads.

The PLC should generate the trigger behavior required by the scanner manual and verify that one intended event produces one intended reading.

11. Data Capture and Validation

A decoded string is only one part of a valid result. The PLC should verify the status, content, and context of the result.

For a code reader, validation may include:

  • Good-read status is active.
  • Result-valid is active or a valid response has been received.
  • Data length is within the allowed range.
  • Character set and format are correct.
  • Prefixes and suffixes are handled correctly.
  • The decoded identifier is valid for the current product or production step.
  • The result belongs to the current trigger event.
  • The result has not already been consumed by the sequence.
  • The data is not stale from a previous read.

11.1 Example validation logic

The following pseudocode illustrates the concept:

IF New_Result_Received THEN
    IF Result_Status = GOOD_READ
       AND Result_Data_Valid
       AND Result_Length_Is_Valid
       AND Result_Belongs_To_Current_Part
    THEN
        Store_Result
        Set_Identification_Complete
    ELSE
        Set_Read_Validation_Fault
        Inhibit_Dependent_Operation
    END_IF
END_IF

This is conceptual logic. Actual PLC implementation must handle data copying, string representation, status clearing, and handshake sequencing according to the selected platform.

11.2 Data freshness

A common error is accepting a previous successful read after the current read has failed.

To prevent this:

  • Clear or invalidate the previous result at the correct point in the sequence.
  • Associate the result with the current trigger or transaction.
  • Wait for a new valid response.
  • Reject stale data after timeout or communication loss.
  • Do not treat a retained good-read bit as proof of a new successful read.

The exact method may use a result handshake, sequence counter, timestamp, transaction ID, or explicit clear operation, depending on the interface.

12. No-Read and Retry Handling

A no-read condition can result from a damaged label, poor alignment, incorrect focus, insufficient illumination, contamination, unsupported symbology, or an invalid trigger sequence.

A robust sequence should distinguish:

  • Scanner did not accept the trigger.
  • Scanner is still busy.
  • Scanner completed a read but found no valid code.
  • Scanner returned a code that failed PLC validation.
  • Scanner communication failed.
  • Scanner hardware or application reported a fault.

These conditions require different responses.

12.1 Retry strategy

A controlled retry strategy may include:

  1. Detect a no-read result.
  2. Verify that the current part is still in the reading position.
  3. Check whether a retry is permitted.
  4. Re-trigger according to the scanner's interface requirements.
  5. Apply the configured retry limit.
  6. If retries fail, stop the dependent sequence and generate a clear diagnostic.
  7. Require the approved operator or maintenance recovery procedure.

Repeated retries should not conceal poor optical setup or unreliable labels. Record the no-read frequency and investigate recurring patterns.

13. Scanner Integration With Machine Sequence

The PLC often uses scanner results to select the next production operation.

Examples include:

  • Identifying a vehicle component before assembly.
  • Selecting the correct CNC program based on a validated part identifier.
  • Confirming a serial number before marking or inspection.
  • Associating a test result with the correct component.
  • Confirming a label after packaging.
  • Checking the identity of a tool, fixture, pallet, or container.

A typical sequence is:

Part arrives at identification station
             ↓
Part-present condition verified
             ↓
PLC triggers scanner
             ↓
Scanner returns result
             ↓
PLC validates code and production context
             ↓
Correct product or recipe selected
             ↓
Required machine permissives checked
             ↓
Operation permitted

The scanner should not directly authorize an operation merely because it returns a syntactically valid string. The PLC must check that the identifier is permitted for the current station, product, recipe, and process state.

14. PLC-Scanner Integration for Measurement Systems

A measurement scanner may return a distance, dimension, profile, or position value rather than a text string.

Commissioning should verify:

  • Measurement range and units.
  • Reference plane and coordinate system.
  • Sensor-to-part geometry.
  • Data type and scaling.
  • Validity and error indicators.
  • Calibration and reference checks.
  • Measurement update rate.
  • Filtering and averaging behavior.
  • Tolerance limits and boundary handling.
  • Response to missing, invalid, or out-of-range measurements.

For example, a scanner might return a distance in millimetres as a floating-point value. The PLC must verify that the received number is interpreted correctly and compared with the correct engineering tolerance.

If a scanner reports a raw integer, scaling may be required. The scaling equation depends on the device specification and must not be assumed.

A measurement scanner used for quality inspection also requires a defined response to invalid data. Invalid measurement data must not automatically be treated as a passing result.

15. Safety Laser Scanner Integration

A safety laser scanner detects objects or people within configured protective fields and may be used to initiate a safety-related stop or other protective response.

Its commissioning is fundamentally different from that of a barcode reader.

15.1 Required checks

  • Confirm the scanner model and its intended safety function.
  • Verify protective-field geometry and configuration.
  • Confirm mounting height, orientation, and blind spots.
  • Verify the configured warning and protective fields.
  • Check required safety outputs or safety communication.
  • Verify the safety controller configuration and diagnostics.
  • Test the protective response using the approved safety-validation procedure.
  • Verify reset conditions and restart interlocks.
  • Document the safety configuration and validation results.

15.2 Safety boundary

A safety laser scanner must be integrated into a validated safety architecture appropriate to the machine's risk assessment and required safety performance.

Do not use a normal PLC input from a standard scanner as a replacement for a required safety-rated output. Similarly, do not assume that a standard Ethernet connection carries safety-rated data simply because the device is marketed as an industrial scanner.

The actual safety behavior, reset method, muting behavior, protective-field switching, and stopping response must be verified against the approved design.

16. Troubleshooting Guide

Symptom Possible cause Verification
Scanner does not respond to trigger Incorrect trigger mapping, scanner not ready, or wrong trigger mode Monitor the trigger output, scanner status, and device diagnostics
Scanner remains busy Read operation not completed, blocked acquisition, or incorrect handshake Check acquisition status, result handling, and reset or acknowledgement behavior
Good-read status appears but data is empty Incorrect data mapping, incomplete transfer, or wrong result-handling sequence Inspect raw data, data length, and result-valid behavior
Data contains unexpected characters Incorrect framing, terminator handling, character encoding, or serial settings Compare the received byte sequence with the scanner output
PLC receives only part of the code Incorrect buffer length, message parsing, or data-transfer handling Inspect full received data and configured maximum length
PLC uses the previous part's code Stale result not cleared or new-result event not detected Verify result reset, transaction handling, and data freshness
Intermittent no-read faults Poor alignment, vibration, contamination, glare, or unsuitable exposure Check optical setup and read-quality diagnostics
Ethernet connection works but PLC data is unavailable Wrong protocol, connection configuration, mapping, or data format Check connection status and raw cyclic or message data
Scanner reads correctly in its configuration tool but not in PLC Configuration interface differs from production interface Verify the selected output channel and PLC communication method

Safety scanner does not permit operation Protective field interrupted, configuration mismatch, safety fault, or reset condition not satisfied Follow the approved safety diagnostic and validation procedure

17. Fault Recovery and Communication Loss

For an ordinary identification or measurement scanner, communication loss should be handled explicitly.

The PLC should:

  • Detect loss of communication or invalid process data.
  • Invalidate results that cannot be confirmed as current.
  • Prevent dependent operations from using missing or stale data.
  • Record the fault and relevant sequence state.
  • Avoid issuing uncontrolled repeated triggers.
  • Restore communication and confirm valid current data.
  • Require the defined recovery sequence before resuming the process.

For a safety scanner, follow the validated safety architecture and manufacturer-defined recovery behavior. A standard PLC recovery sequence cannot override a safety fault or substitute for a required safety reset.

A useful recovery sequence is:

Communication fault detected
             ↓
Apply the defined machine response
             ↓
Invalidate uncertain or stale data
             ↓
Diagnose scanner, wiring, network, or configuration
             ↓
Restore communication
             ↓
Verify current status and valid results
             ↓
Confirm machine permissives and recovery conditions
             ↓
Resume only through the approved sequence

18. Performance and Reliability Testing

Commissioning should verify more than whether the scanner works once.

Measure or record:

  • Read success rate under representative operating conditions.
  • No-read frequency.
  • Trigger-to-result time.
  • Communication update time.
  • Measurement stability and repeatability, where applicable.
  • Data-validation failures.
  • Duplicate or stale result events.
  • Response to scanner power cycling.
  • Response to communication interruption.
  • Performance under normal production speed and environmental conditions.

A read-success percentage can be calculated as:

\[ \text{Read Success Rate} = \frac{\text{Successful Valid Reads}}{\text{Total Read Attempts}} \times 100\\% \]

The acceptance threshold must be defined by the application requirements. A high average success rate may still be unacceptable if failures occur on a critical part or cause incorrect product selection.

19. FAT and SAT

FAT verifies the scanner interface and logic under factory test conditions. SAT verifies the complete installed system under actual site conditions.

Test item FAT focus SAT focus
Device configuration Verify scanner settings and saved configuration Verify installed device and final configuration
Communication Verify configured protocol and data mapping Verify actual cables, network, and production data
Trigger sequence Verify trigger and result handshake Verify real part detection and scanner timing
Data validation Test valid, invalid, and malformed results Verify actual product identification and process decisions
No-read handling Simulate or test failed reads Test representative labels and site conditions
Measurement accuracy Use known references where available Verify actual installation geometry and reference measurements
Fault recovery Verify designed timeout and reset behavior Verify recovery with installed equipment
Safety functions Verify the designed safety integration within the approved test scope Complete the required on-site safety validation
Performance Verify test-case timing and behavior Verify performance under representative production conditions
Documentation Review settings, I/O mapping, and test records Confirm final backups, as-built configuration, and handover

20. Acceptance Criteria

Define acceptance criteria before testing. Typical requirements include:

  • Correct scanner identity and configuration.
  • Stable communication through the intended production interface.
  • Correct signal and data mapping.
  • Correct trigger, busy, result-valid, and acknowledgement behavior where supported.
  • Correct handling of valid reads, no-reads, invalid codes, and malformed data.
  • No acceptance of stale data as a new result.
  • Correct product or recipe selection.
  • Correct response to communication loss and device faults.
  • Measurement results within the defined accuracy and repeatability limits, where applicable.
  • Read performance within the agreed requirements.
  • Safety functions validated separately when applicable.
  • No unresolved critical defects.
  • Final configuration, backups, and commissioning records handed over.

Do not invent a universal read-success threshold, maximum latency, or measurement tolerance. These values depend on the scanner, application, product, and production requirements.

21. Documentation and Handover

The final commissioning package should contain:

  • Scanner make, model, serial number, and firmware.
  • Scanner configuration backup.
  • PLC program version and final backup.
  • Electrical drawings and verified I/O list.
  • Network topology and communication configuration.
  • Data format and signal-mapping document.
  • Trigger, result, acknowledgement, and timeout definitions.
  • Product-code or measurement-validation rules.
  • Fault list and recovery instructions.
  • FAT/SAT test results.
  • Safety validation records where applicable.
  • As-built changes and approval records.
  • Maintenance troubleshooting instructions.

For maintenance teams, include the exact scanner diagnostic method, how to perform an approved test read, how to inspect raw PLC data, and how to distinguish a scanner fault from a PLC mapping or machine-sequence fault.

22. Common Commissioning Mistakes

  • Treating every scanner as a barcode reader.
  • Confusing a safety laser scanner with a standard industrial scanner.
  • Assuming the configuration-tool connection is the production communication interface.
  • Using the wrong data length, byte order, or character format.
  • Failing to handle message terminators or serial communication settings.
  • Keeping old result data valid after a failed read.
  • Treating GOOD_READ as proof that the code belongs to the correct part.
  • Re-triggering continuously without understanding the scanner handshake.
  • Ignoring optical alignment, label quality, and contamination.
  • Accepting invalid measurement data as a passing result.
  • Using arbitrary retry counts or timeouts.
  • Allowing automatic restart after communication recovery without validating the machine state.
  • Treating standard PLC logic as a replacement for a required safety function.
  • Failing to save the final scanner configuration and document the verified mapping.

23. Interview Questions and Answers

1. What is PLC-scanner communication commissioning?

It is the configuration and validation of the scanner interface, data mapping, trigger sequence, result handling, diagnostics, and machine response.

2. What is the difference between a good read and a valid production result?

A good read means the scanner decoded a code successfully according to its configured criteria. A valid production result also requires PLC validation of the data, current part, expected format, and process context.

3. Why is a trigger handshake necessary?

It coordinates the read request, scanner response, result availability, and result clearing so that readings are not missed, duplicated, or associated with the wrong part.

4. Why might a scanner work in its configuration software but fail in the PLC?

The configuration tool may use a separate interface from the production connection. The PLC may also have incorrect protocol settings, data mapping, framing, or result-handling logic.

5. How can stale scanner data cause a production problem?

The PLC might reuse the previous part's identifier after a failed read and select an incorrect recipe or operation. Result freshness and transaction association must therefore be verified.

6. How would you troubleshoot intermittent no-reads?

Check optical alignment, working distance, label quality, contamination, lighting, vibration, trigger timing, read-quality diagnostics, and the scanner's acquisition settings.

7. What is the difference between a barcode scanner and a safety laser scanner?

A barcode scanner identifies encoded information. A safety laser scanner detects objects or people within configured protective fields and participates in a safety-related protective function.

8. Why is data validation required even after communication is established?

Communication can deliver incorrect, stale, truncated, or incorrectly interpreted data. The PLC must verify data integrity and application-specific validity.

9. What should happen when scanner communication is lost?

The system should apply the defined fault response, reject uncertain data, prevent dependent operations from proceeding incorrectly, diagnose the fault, and resume only after valid communication and recovery conditions are confirmed.

10. What evidence demonstrates successful commissioning?

Verified mapping, correct trigger and result handling, successful valid and invalid test cases, appropriate fault recovery, performance within requirements, and complete handover documentation.

24. Final Commissioning Checklist

  • Scanner type, model, firmware, and application confirmed.
  • Physical installation, alignment, and optical conditions verified.
  • Correct communication interface configured.
  • Network or serial parameters verified.
  • PLC signal and data mapping validated.
  • Trigger and acknowledgement behavior tested.
  • Good-read, no-read, busy, and fault conditions verified where supported.
  • Data format, length, encoding, and scaling verified.
  • Stale and invalid data handling verified.
  • Machine sequence and product validation tested.
  • Communication-loss detection and recovery tested.
  • Measurement accuracy and repeatability verified where applicable.
  • Safety functions separately validated if a safety scanner is used.
  • FAT/SAT results recorded.
  • Final configuration, backups, and troubleshooting documents handed over.
