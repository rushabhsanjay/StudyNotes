1. Definition and Purpose

PLC-Robot communication commissioning is the process of configuring, testing, and validating data exchange between a Programmable Logic Controller (PLC) and an industrial robot controller so that both systems coordinate machine operations correctly, exchange commands and status information, handle faults predictably, and recover safely from communication interruptions.

In an automated production line, the PLC typically coordinates the overall machine sequence, conveyors, fixtures, sensors, safety interfaces, and peripheral equipment. The robot controller manages robot motion, robot programs, tool paths, and robot-specific operating states.

The commissioning objective is to prove that the PLC and robot agree on what operation is requested, whether it is permitted, whether it has started, whether it has completed, and whether a fault has occurred.

A communication connection alone does not prove that the robot is executing the correct program or that the machine sequence is safe.

2. Scope of PLC-Robot Commissioning

PLC-Robot commissioning includes:

  • Physical network and communication interface verification.
  • Protocol and device configuration.
  • PLC and robot-controller addressing.
  • Signal mapping and data exchange.
  • Robot program selection and execution requests.
  • Cycle-start, busy, complete, ready, and fault handshakes.
  • Robot-to-PLC status feedback.
  • Workpiece, fixture, clamp, and peripheral coordination.
  • Fault detection, recovery, and restart prevention.
  • Safety-system integration and validation.
  • Cycle timing, diagnostics, testing, and handover documentation.

It also requires checking robot-specific conditions such as the selected program, tool, work object or frame, operating mode, and applicable motion permissions.

3. PLC-Robot System Architecture

A typical industrial robot cell uses the following architecture:

HMI / Operator
      ↓
PLC Sequence and Cell Coordination
      ↓
Industrial Communication Network
      ↓
Robot Controller
      ↓
Robot Motion Program
      ↓
Robot Manipulator and Tool
      ↓
Workpiece Operation

Additional equipment may exchange signals with the PLC or robot controller:

Sensors / Fixture / Clamps / Conveyors
      ↓
PLC Inputs and Sequence Logic
      ↓
PLC-Robot Handshake
      ↓
Robot Controller
      ↓
Robot Motion and Tool Operation
      ↓
Robot Status and Process Feedback
      ↓
PLC Sequence Continuation

The exact architecture depends on the robot manufacturer, PLC, communication protocol, and cell design. Some cells connect the robot directly to the PLC over industrial Ethernet. Others use hardwired digital I/O, a fieldbus, a gateway, or a combination of these.

4. Responsibilities of the PLC and Robot Controller

The division of responsibility must be clearly defined before testing.

Function Typical PLC responsibility Typical robot-controller responsibility
Cell sequence Coordinates the complete station Executes the requested robot operation
Program selection Requests an approved program or job Validates and selects the available program
Cycle start Sends a permitted start request Checks robot-specific start conditions
Robot motion Coordinates external equipment and sequence Executes trajectory and motion instructions
Fixture control Controls clamps and verifies feedback Uses agreed signals to coordinate with the fixture
Robot status Monitors robot-ready and cycle states Reports ready, busy, complete, and fault states
Fault handling Coordinates cell-level response Reports robot faults and provides robot diagnostics
Safety coordination Integrates cell safety according to design Responds to configured robot safety functions

This division is typical, not universal. The approved functional specification determines the final ownership of each signal and function.

5. Communication Methods and Protocols

Method Typical application Commissioning checks
Hardwired digital I/O Basic ready, start, complete, and fault signals Wiring, polarity, signal voltage, mapping
PROFINET Siemens PLC and compatible robot controller Device name, IP configuration, GSDML, I/O mapping
EtherNet/IP Allen-Bradley PLC and compatible robot controller Device identity, EDS/profile, assembly and data mapping
PROFIBUS DP Existing or legacy automation installations Node address, GSD configuration, bus termination
CC-Link or CC-Link IE Compatible Mitsubishi and other industrial systems Network settings, station configuration, cyclic data
OPC UA Supervisory or structured data exchange where supported Endpoint, certificates, access permissions, data model
Manufacturer-specific interfaces Robot-specific PLC integration Supported protocol, driver, signal definitions

Protocol support depends on the exact robot controller, firmware, communication option, and PLC hardware. For example, the availability of PROFINET or EtherNet/IP may depend on an installed option or licensed feature.

5.1 Hardwired versus network communication

Hardwired I/O is often used for simple handshake signals and can be straightforward to troubleshoot electrically. Network communication can support more signals, richer diagnostic data, and easier expansion.

However, a network connection introduces configuration requirements such as addressing, device descriptions, process-data sizes, and communication-loss handling.

Some installations use network communication for ordinary control data and a separate safety-rated system for protective functions. Ordinary PLC-Robot communication must not be assumed to be safety-rated.

6. Network and Device Configuration

6.1 IP addressing

For Ethernet-based communication, verify:

  • Correct IP addresses and subnet masks.
  • No duplicate IP addresses.
  • Correct device name where required.
  • Correct communication interface and protocol configuration.
  • Correct PLC hardware configuration.
  • Correct robot communication option and device profile.
  • Correct process-data size and mapping.
  • Required network paths, switches, and VLAN settings.

Example addressing:

Device Example IP address Subnet mask
PLC 192.168.30.10 255.255.255.0
Robot controller 192.168.30.20 255.255.255.0
HMI 192.168.30.30 255.255.255.0
Engineering PC 192.168.30.40 255.255.255.0

These addresses are illustrative. Use the approved plant network plan for the actual machine.

6.2 Network verification

Useful checks on an authorized engineering PC include:

ipconfig /all
ping 192.168.30.20
arp -a

ipconfig /all verifies the PC network configuration. ping tests IP reachability if ICMP is permitted. arp -a displays known IP-to-MAC address mappings.

A successful ping does not prove that robot process data is being exchanged correctly. A failed ping does not conclusively prove the robot controller is offline because ICMP traffic may be disabled or filtered.

6.3 Protocol-specific configuration

For PROFINET, verify the device name, IP configuration, GSDML version, module configuration, and cyclic input/output mapping.

For EtherNet/IP, verify the device identity, supported profile, input and output assembly instances, data sizes, and connection configuration.

For any protocol, compare the configured data layout with the actual PLC and robot signal definitions. A connection can fail because the configuration is incompatible even when the physical network is correct.

7. PLC-Robot Signal Mapping

The signal list is the central commissioning document for the handshake. Every signal should have a clear source, destination, data type, meaning, and reset rule.

Typical PLC-to-robot signals include:

  • Cell_Start_Permit
  • Program_Select
  • Cycle_Start_Request
  • Part_Present
  • Fixture_Clamped
  • External_Device_Ready
  • Fault_Reset_Request

Typical robot-to-PLC signals include:

  • Robot_Ready
  • Robot_Busy
  • Program_Active
  • Cycle_Complete
  • Robot_Fault
  • Robot_At_Home
  • Robot_At_Load_Position
  • Robot_At_Unload_Position

These are illustrative names. Actual signal names and meanings must follow the robot interface specification.

Signal Direction Purpose Verification
Cycle_Start_Request PLC to robot Requests program execution Correct trigger and acknowledgement
Robot_Ready Robot to PLC Indicates readiness for the defined operation Matches the specified robot state
Robot_Busy Robot to PLC Indicates execution is in progress Active during the intended interval
Cycle_Complete Robot to PLC Reports completion of the defined operation Set only after the required completion conditions
Robot_Fault Robot to PLC Reports a robot fault condition Matches controller diagnostic state
Fixture_Clamped PLC to robot or cell interface Indicates fixture confirmation Correct signal ownership and feedback source
Fault_Reset_Request PLC to robot Requests an authorized fault acknowledgement Accepted only under specified conditions

A signal named Robot_Ready does not have a universal meaning. It might mean the controller is powered and ready, that a program is selected, that automatic operation is available, or that the robot is ready for a particular cycle. Its definition must be explicit.

8. Robot Handshake Fundamentals

A handshake is an agreed sequence of requests, acknowledgements, and status signals that allows the PLC and robot controller to coordinate operations.

A basic handshake commonly includes:

  • Request: The PLC asks the robot to perform an operation.
  • Acceptance or start feedback: The robot indicates that the request has been accepted or execution has started.
  • Busy: The robot reports that the operation is in progress.
  • Completion: The robot reports that the defined operation has completed.
  • Reset or clear: The request and acknowledgement return to their specified inactive states.

The exact signals and sequence vary by robot manufacturer and application.

8.1 Example of a basic cycle handshake

PLC verifies cell permissives
        ↓
PLC sends Cycle_Start_Request
        ↓
Robot validates program and start conditions
        ↓
Robot reports Busy / Program Active
        ↓
Robot executes the programmed operation
        ↓
Robot reports Cycle_Complete
        ↓
PLC verifies completion and continues the cell sequence
        ↓
Handshake signals return to the defined idle state

The PLC should not infer completion merely because Robot_Busy turns off. Busy may turn off due to a fault, abort, program termination, or other condition. Completion should be confirmed using the specified signal or state combination.

9. Request, Acknowledgement, and Reset Rules

A handshake can fail even when all individual signals are mapped correctly if the two controllers disagree about when signals should turn on and off.

For every handshake, define:

  • Which controller sets each signal.
  • Which controller clears each signal.
  • Whether the signal is pulse-based or maintained.
  • Whether acknowledgement is required.
  • Whether a timeout is required.
  • What happens if the expected response never arrives.
  • What happens if the robot faults during execution.
  • What happens if the PLC or robot restarts.
  • Whether an aborted cycle requires manual recovery.

9.1 Edge-triggered requests

An edge-triggered request is detected when a signal changes from false to true. If the PLC holds the request true and the robot expects a new rising edge, the next cycle may not start.

Conversely, a level-sensitive request may repeatedly trigger an operation if it is not cleared correctly.

Use the request pattern defined by the robot interface. Test multiple consecutive cycles, not just the first start.

9.2 Example handshake truth table

This is a simplified conceptual example, not a universal robot interface.

PLC start request Robot busy Robot complete Interpretation
0 0 0 Idle or ready for a new request, subject to other conditions
1 0 0 Request pending or awaiting acceptance
1 1 0 Operation in progress
0 1 0 Operation in progress after request was cleared, if the interface permits this
0 0 1 Operation complete, subject to defined reset rules
Any Any Any with robot fault Fault handling takes priority according to the specified sequence

The project must define the legal combinations. An unexpected combination should generate a diagnostic rather than leave the PLC sequence waiting indefinitely.

10. Program Selection and Job Management

Many robot applications require the PLC to select a robot program, job, or process routine before requesting execution.

Commissioning must verify:

  • Correct program number or selection code.
  • Correct mapping of selection bits or data values.
  • Correct interpretation of binary or integer selection data.
  • Validity of the selected program.
  • Confirmation that the intended program is loaded or active.
  • Correct behavior for an invalid program number.
  • Required robot mode and program-start conditions.
  • Correct program completion and reset behavior.

10.1 Binary program selection example

Suppose a robot interface uses four selection bits to represent a program number in binary. If the interface defines the least significant bit as the first bit, the value can be represented as:

\[ N = b_0 + 2b_1 + 4b_2 + 8b_3 \]

Where each bit \(b_i\) is either 0 or 1.

For \(b_3b_2b_1b_0 = 0101\), the selected value is:

\[ N = 1 + 0 + 4 + 0 = 5 \]

This example assumes a standard binary encoding and that the interface uses program number 5 for that bit pattern. Actual robot interfaces may use different encoding, offsets, or selection rules.

11. Robot Modes and Start Conditions

Robot controllers typically distinguish operating modes such as manual, teach, and automatic. The exact names and behaviors depend on the controller and safety configuration.

A remote PLC start request may be accepted only when the robot is in an appropriate operating mode and all required conditions are satisfied.

Check:

  • Correct operating mode.
  • Program selection and program state.
  • Robot-controller readiness.
  • No active fault preventing operation.
  • Required external equipment ready.
  • Required safety conditions satisfied.
  • Required tooling, workpiece, and fixture conditions satisfied.
  • Appropriate restart behavior after an interruption.

The PLC should provide clear diagnostics for a blocked start, where supported by the design. A start request should not be treated as proof that all robot start conditions are met.

12. PLC-Robot Coordination With Fixtures and Peripherals

In a manufacturing cell, robot movement often depends on fixture and peripheral states.

Examples include:

  • Part present and correctly oriented.
  • Fixture closed and clamped.
  • Clamp pressure or position confirmed.
  • Conveyor stopped at the correct location.
  • Welding gun ready.
  • Gripper open or closed.
  • Tool changer confirmed in the required state.
  • External axis or positioner ready.
  • Process equipment ready.

A typical operation might be:

Part arrives
      ↓
PLC confirms part position
      ↓
PLC commands fixture clamping
      ↓
PLC verifies clamp feedback
      ↓
PLC permits robot operation
      ↓
Robot performs the task
      ↓
Robot reports completion
      ↓
PLC verifies process and fixture conditions
      ↓
PLC releases the part when permitted

Commands and feedback must be separated. A PLC output requesting a clamp to close is not proof that the clamp has physically closed. The robot should rely on the required confirmed state, not merely the command signal.

13. Safety Integration

Robot-cell safety requires particular care because the robot can produce hazardous movement and may interact with external equipment.

Normal PLC-Robot communication generally handles ordinary control coordination. It must not be assumed to provide a safety-rated stop or protective function.

Safety functions may include:

  • Emergency stop.
  • Guard-door monitoring and interlocking.
  • Safety-rated robot stop functions.
  • Safe speed or safe position functions where provided.
  • Enabling devices for manual operation.
  • Safe torque removal or equivalent drive-level safety functions.
  • Safety-rated communication where explicitly designed and supported.

The required architecture depends on the machine risk assessment, applicable standards, and installed equipment.

13.1 Safety commissioning principles

  • Verify the approved safety design and wiring.
  • Confirm safety functions are configured and validated by authorized personnel.
  • Test protective devices according to the approved safety validation procedure.
  • Confirm that ordinary start requests cannot bypass required safety conditions.
  • Verify restart prevention after a safety event.
  • Verify reset behavior and operator visibility.
  • Record the validation results.

Do not use a normal Robot_Ready, Robot_Busy, or Cycle_Start_Request bit as a substitute for a safety-rated signal. Do not bypass guards or safety circuits to make communication testing easier.

14. Fault Handling and Recovery

Typical PLC-Robot faults include:

  • Communication loss.
  • Robot controller fault.
  • Program-selection error.
  • Invalid or missing start acknowledgement.
  • Cycle timeout.
  • Fixture or peripheral not ready.
  • Robot not reaching the expected position.
  • Tool or process fault.
  • Robot safety-system event.
  • PLC restart during an active robot cycle.

14.1 Fault-handling requirements

For each fault, define:

  • Detection condition.
  • Fault priority and message.
  • Required machine response.
  • Whether the robot must stop, finish a controlled sequence, or enter another defined state.
  • Whether the PLC must inhibit downstream equipment.
  • Reset conditions.
  • Recovery sequence.
  • Whether operator intervention is required.
  • How the cycle is reconciled after recovery.

The correct response depends on the specific process and risk assessment. Do not assume every fault requires the same immediate stop, and do not allow an ordinary communication fault to compromise a required safety function.

14.2 Timeouts

A timeout detects that an expected state has not occurred within the allowed interval.

Examples include:

  • Robot did not acknowledge a start request.
  • Robot did not report busy within the expected interval.
  • Robot did not complete the cycle.
  • Robot did not reach the expected station or process state.

A timeout should generate a meaningful diagnostic. It should not automatically trigger repeated start commands or blind retries that could create duplicate operations.

Timeout values should be based on the approved sequence timing, measured performance, and expected process variation.

15. Communication Loss and Recovery Testing

Communication loss may occur because of cable failure, switch power loss, incorrect network configuration, controller restart, or a communication-module fault.

Commissioning should verify:

  • How the PLC detects loss of robot data.
  • How the robot responds to loss of PLC commands, where applicable.
  • Whether process data is marked invalid or stale.
  • Whether the cell enters the specified state.
  • Whether pending commands are cleared, retained, or rejected.
  • Whether the HMI displays the communication fault.
  • How reconnection is detected.
  • Whether the robot requires explicit operator recovery.
  • Whether any unintended program start can occur after reconnection.

15.1 Controlled test procedure

  1. Obtain authorization and establish the approved safe test state.
  2. Record the PLC, robot, and cell states.
  3. Interrupt the intended communication path using the approved test method.
  4. Verify the specified fault detection and machine response.
  5. Confirm that the sequence does not advance on invalid or stale status.
  6. Restore communication.
  7. Verify the data exchange and state reconciliation.
  8. Confirm that no unintended start or duplicate operation occurs.
  9. Record the results and correct any defects.

Do not deliberately disconnect a production robot network without the required risk controls and authorization.

16. Robot Position and Process Feedback

Some PLC-Robot interfaces exchange only discrete status signals. More advanced systems may exchange position, speed, tool, process, or diagnostic data.

If position values are exchanged, verify:

  • Coordinate system and reference frame.
  • Units, such as millimetres or degrees.
  • Sign convention and axis order.
  • Numeric data type and scaling.
  • Position validity and update timing.
  • Whether the value represents commanded or actual position.
  • Whether the value is robot-base, tool, work-object, or another coordinate frame.

A value called Robot_X_Position is not meaningful without knowing its reference frame and units.

For process feedback, such as welding status or dispensing completion, verify the exact definition of success. A robot reaching the end of its motion program does not necessarily prove that the process itself met quality requirements.

17. Performance and Cycle-Time Verification

PLC-Robot commissioning must confirm that the handshake supports the required cell cycle time without compromising safe sequencing.

Relevant timing measurements include:

  • PLC start request to robot acknowledgement.
  • Robot acknowledgement to motion start.
  • Robot motion duration.
  • Robot completion to PLC sequence continuation.
  • Peripheral response time.
  • Fixture clamping and release time.
  • Communication fault detection time.
  • Recovery time after the specified fault.

Measure these intervals under representative operating conditions.

Do not reduce timeouts simply to improve a cycle-time number. A timeout that is too short can create nuisance faults; one that is too long can delay fault detection. The correct setting must reflect the actual machine requirements.

18. PLC-Robot Commissioning Procedure

Stage 1: Documentation and preparation

  • Obtain the approved PLC and robot-controller projects.
  • Review the cell sequence and functional specification.
  • Obtain the PLC-Robot signal list.
  • Confirm the robot model, controller, firmware, and communication options.
  • Confirm protocol compatibility.
  • Review the robot program-selection and start sequence.
  • Review fixture and peripheral dependencies.
  • Review the safety design and test authorization.
  • Back up the existing PLC and robot configuration.

Stage 2: Physical and network checks

  • Inspect communication cables and connectors.
  • Confirm switch and controller link status.
  • Verify IP addresses, device names, and network configuration.
  • Confirm that the correct PLC and robot are connected.
  • Verify device descriptions and hardware configuration.
  • Confirm cyclic input/output sizes and mappings.
  • Check for network or configuration diagnostics.

Stage 3: Signal verification

  • Verify PLC-to-robot command signals.
  • Verify robot-to-PLC status signals.
  • Check bit order and data types.
  • Confirm program-selection values.
  • Test ready, busy, complete, and fault indications.
  • Verify signal ownership and reset rules.
  • Check that unexpected signal combinations are diagnosed.

Stage 4: Handshake testing

  • Verify the idle state.
  • Verify program selection.
  • Verify the start request.
  • Verify robot acknowledgement or busy feedback.
  • Verify completion feedback.
  • Verify request clearing and acknowledgement reset.
  • Test multiple consecutive cycles.
  • Test rejected requests and missing permissives.
  • Verify timeout and fault behavior.

Stage 5: Cell functional testing

  • Verify fixture and peripheral coordination.
  • Confirm required feedback before permitting robot motion.
  • Test the intended robot program under controlled conditions.
  • Verify process and position feedback where applicable.
  • Confirm the PLC sequence continues only after the specified completion conditions.
  • Measure relevant cycle-time intervals.
  • Verify HMI status and alarm presentation.

Stage 6: Fault and recovery testing

  • Test approved robot faults and diagnostic conditions.
  • Test communication loss and recovery.
  • Verify behavior after PLC or robot restart where required.
  • Confirm no unintended program restart.
  • Confirm pending commands are handled correctly.
  • Verify restart prevention after faults and safety events.
  • Record defects and retest corrected functions.

Stage 7: Handover

  • Save final PLC and robot-controller backups.
  • Record firmware, program versions, and network settings.
  • Update the signal list and network diagram.
  • Complete FAT/SAT and commissioning records.
  • Document outstanding issues and approved deviations.
  • Obtain the required sign-offs.

19. Troubleshooting Guide

Symptom Likely causes Diagnostic action
Robot not detected by PLC Network, addressing, device configuration, or communication option issue Check link, address, device identity, and controller diagnostics
Communication healthy but robot will not start Wrong mode, invalid program, missing permissive, or start sequence issue Check robot state, program selection, and start conditions
Start request remains active Handshake reset defect or missing acknowledgement Trace request and acknowledgement transitions
Robot starts only once Request edge not recreated or handshake not reset Check the defined request and reset sequence
PLC waits indefinitely Missing completion signal, timeout defect, or incorrect signal mapping Monitor busy, complete, fault, and timeout logic
Robot reports complete but PLC does not advance Completion tag incorrect or PLC sequence condition false Compare actual robot status with PLC logic
Wrong program executes Incorrect selection mapping or program-number encoding Verify selection data and active program identity
Robot moves before fixture is ready Missing or incorrect permissive Check clamp command and confirmed feedback logic
Robot fault not visible on HMI Incorrect mapping, alarm configuration, or stale data Check robot diagnostic source and HMI tag
Intermittent communication faults Cable, switch, network configuration, or controller issue Inspect physical connections and network diagnostics
Duplicate cycle after reconnection Pending request retained or restart logic incorrect Check request clearing and recovery-state handling
Robot position displayed incorrectly Wrong coordinate frame, units, scaling, or data type Compare robot diagnostic values with PLC interpretation
Cycle time is inconsistent Peripheral delays, network load, robot program variation, or handshake timing Measure each sequence interval separately

19.1 Diagnostic order

1. Physical connections and network status
      ↓
2. Protocol and device configuration
      ↓
3. Signal mapping and data validity
      ↓
4. Robot mode and program selection
      ↓
5. Handshake and sequence logic
      ↓
6. Fixture, peripheral, and process conditions
      ↓
7. Fault recovery and cycle performance

Record the exact signal states and fault codes before making changes. A timestamped trace of the request, acknowledgement, busy, complete, and fault signals is often far more useful than watching the HMI and guessing.

20. FAT and SAT for PLC-Robot Communication

Factory Acceptance Testing (FAT) verifies the integrated control design before shipment. Site Acceptance Testing (SAT) verifies the installed system and its actual equipment interactions.

Test item FAT focus SAT focus
Communication Device configuration and data exchange Installed network and controller communication
Signal mapping Simulated or bench-tested signals Actual cell signals
Program selection Correct program-selection logic Correct installed robot program
Handshake Request, acknowledgement, busy, complete Real sequence execution
Peripheral coordination Simulated device states Actual fixtures, tools, and conveyors
Fault handling Simulated or approved fault conditions Installed fault and recovery behavior
Communication loss Controlled simulation Approved site-specific test
Cycle time Expected sequence timing Measured production-representative timing
Safety functions Design verification and planned testing Site validation under the approved safety plan
Documentation Approved configuration and test records As-built records and final acceptance

FAT may not prove the behavior of the final mechanical fixture or installed safety devices. SAT must verify those site-dependent elements.

21. Acceptance Criteria

Acceptance criteria must be defined in the approved project specification. Typical criteria include:

  • PLC and robot exchange the required data reliably.
  • All critical commands and status signals are correctly mapped.
  • Program selection identifies the intended robot program.
  • Start, busy, completion, and reset handshakes follow the specified sequence.
  • Invalid requests are rejected or diagnosed as designed.
  • Fixture and peripheral permissives are correctly enforced.
  • Faults are reported and handled according to the functional specification.
  • Communication loss is detected and handled within specified limits.
  • Recovery does not cause unintended movement or duplicate cycles.
  • Cycle timing meets the approved requirement.
  • Safety functions pass their separate validation.
  • Final backups, test evidence, and handover records are complete.

Do not assume a universal handshake timeout or cycle-time limit. Values depend on the robot program, process, communication architecture, and project requirements.

22. Practical Example: Robot Loading a CNC Machine

Consider a robot that loads a workpiece into a CNC machine. The PLC coordinates the robot, CNC, fixture, and cell sequence.

22.1 Example sequence

PLC confirms CNC is ready for loading
        ↓
PLC confirms CNC door and fixture conditions
        ↓
PLC selects the robot loading program
        ↓
PLC requests robot cycle start
        ↓
Robot reports execution in progress
        ↓
Robot loads the workpiece and confirms placement
        ↓
PLC verifies required loading and fixture conditions
        ↓
CNC receives permission to begin its cycle
        ↓
CNC reports machining complete
        ↓
PLC coordinates robot unloading

The actual order depends on the CNC and robot interface design. For example, the CNC may own its door sequence, or the robot may control an external door actuator through the PLC.

22.2 Important commissioning tests

  1. Verify the CNC-ready signal.
  2. Confirm the correct robot program is selected.
  3. Verify the robot start handshake.
  4. Confirm the robot cannot load when required CNC or fixture conditions are absent.
  5. Verify workpiece placement and the required confirmation signals.
  6. Confirm the CNC cannot start until all required loading conditions are satisfied.
  7. Verify that a robot fault blocks the appropriate next sequence step.
  8. Test recovery from an interrupted loading cycle.
  9. Confirm that the system does not assume a part is loaded solely because the robot program ended.

This example demonstrates why a PLC-Robot interface must coordinate the complete cell state, not just transfer a start bit.

23. Common Commissioning Mistakes

  • Assuming network connectivity proves the handshake is correct.
  • Using an undocumented or incorrect signal list.
  • Confusing Robot_Ready, Robot_Busy, and Cycle_Complete.
  • Ignoring the robot's operating mode and program-selection state.
  • Failing to reset request and acknowledgement signals correctly.
  • Treating a dropped busy signal as proof of successful completion.
  • Allowing the PLC to advance without confirmed fixture or peripheral feedback.
  • Ignoring stale data after communication loss.
  • Allowing pending start requests to trigger after reconnection.
  • Using normal control signals as substitutes for safety functions.
  • Failing to test multiple consecutive cycles.
  • Making online changes without saving backups or recording revisions.

24. Interview Questions and Answers

Q1. What is PLC-Robot communication commissioning?

It is the verification of communication, signal mapping, program selection, handshake behavior, fault handling, and cell coordination between a PLC and robot controller.

Q2. What is a PLC-Robot handshake?

It is an agreed sequence of request, acknowledgement, execution status, completion, and reset signals used to coordinate the two controllers.

Q3. What is the difference between robot ready, busy, and complete?

Ready indicates that specified conditions for an operation are satisfied. Busy indicates execution is in progress. Complete indicates that the defined operation has completed. Their exact meanings must follow the interface specification.

Q4. Why might a robot not start even when communication is healthy?

The robot may be in the wrong mode, the selected program may be invalid, required permissives may be absent, or the start request may not follow the required sequence.

Q5. Why should the PLC verify fixture feedback before permitting robot motion?

A command to close a fixture does not prove it physically closed. The required feedback confirms the specified process condition before the next operation is permitted.

Q6. Why must handshake reset behavior be tested?

Incorrect reset behavior can prevent subsequent cycles, cause repeated starts, or leave the PLC and robot in inconsistent states.

Q7. Why is robot communication not automatically a safety function?

Ordinary control communication is not necessarily safety-rated and must not replace the validated safety architecture required for hazardous motion.

Q8. What is the difference between FAT and SAT?

FAT verifies the integrated design before shipment. SAT verifies the installed system, real equipment interactions, and site-dependent behavior.

Q9. How should a PLC-Robot communication fault be diagnosed?

Check the physical network, protocol configuration, data mapping, robot state, program selection, handshake transitions, and relevant fixture or process conditions in that order.

Q10. What proves successful PLC-Robot commissioning?

Correct data exchange, verified handshake behavior, correct program execution, tested fault and recovery behavior, validated safety functions, and completed commissioning records.

25. Final PLC-Robot Commissioning Checklist

  • Approved PLC and robot projects identified and backed up.
  • Robot model, firmware, and communication options confirmed.
  • Physical network and addressing verified.
  • Protocol and device configuration verified.
  • PLC-to-robot and robot-to-PLC signals checked.
  • Program selection and encoding verified.
  • Ready, busy, start, complete, and fault behavior tested.
  • Request and acknowledgement reset rules verified.
  • Fixture and peripheral permissives tested.
  • Robot mode and restart conditions verified.
  • Communication loss and recovery tested.
  • Cycle timing and diagnostics verified.
  • Safety functions separately validated as required.
  • FAT/SAT results and final configuration records completed.

The final objective is a predictable, diagnosable robot cell in which the PLC and robot agree on every important transition. Correct communication is the foundation; correct sequence behavior, process feedback, fault recovery, and validated safety are what make the cell production-ready.
