1. Definition and Purpose

PLC-Drive communication commissioning is the process of configuring, testing, and validating data exchange between a Programmable Logic Controller (PLC) and a motor drive, such as a Variable Frequency Drive (VFD), servo drive, or other networked drive.

The objective is to ensure that the PLC can send the intended commands and reference values to the drive, receive correct status and feedback, detect faults, and coordinate machine operation reliably.

A drive may be controlled through hardwired digital and analog signals, an industrial communication network, or a combination of both. Commissioning must verify the actual control method implemented in the machine.

Core principle: A PLC communication status showing healthy does not prove that the drive is ready, the motor rotates in the correct direction, the speed reference is interpreted correctly, or the machine is safe to operate.

2. Scope of PLC-Drive Commissioning

PLC-Drive commissioning includes:

  • Physical connections and communication hardware.
  • Drive network configuration and addressing.
  • Protocol, device profile, and PLC hardware configuration.
  • PLC-to-drive command and reference mapping.
  • Drive-to-PLC status and feedback mapping.
  • Start, stop, enable, reset, speed, torque, and direction commands.
  • Drive permissives, interlocks, and fault handling.
  • Motor nameplate data and drive parameter verification.
  • Communication timeout, fault response, and recovery behavior.
  • Controlled functional tests, performance checks, and handover records.

It also requires coordination with electrical installation, motor commissioning, machine sequencing, and safety validation. Communication commissioning does not replace those activities.

3. PLC-Drive System Architecture

A typical network-controlled drive system has the following structure:

Operator / HMI
      ↓
PLC Program and Sequence Logic
      ↓
PLC Communication Interface
      ↓
Industrial Network
      ↓
Drive Communication Interface
      ↓
VFD / Servo Drive
      ↓
Motor
      ↓
Machine Load

Feedback travels in the reverse direction:

Motor / Drive
      ↓
Speed, Current, Torque, Status, Faults
      ↓
Drive Communication Interface
      ↓
Industrial Network
      ↓
PLC Input Data
      ↓
PLC Sequence and Diagnostic Logic
      ↓
HMI / SCADA

In some systems, the PLC uses hardwired signals for enable, run, or fault status while communication carries speed references, actual values, and diagnostics. This hybrid arrangement must be documented and tested according to the actual design.

5. Common PLC-Drive Control Methods

5.1 Hardwired control

Commands and feedback use discrete or analog electrical signals.

Typical signals include:

  • Digital output: run or enable command.
  • Digital input: drive ready or drive fault.
  • Analog output: speed reference.
  • Analog input: actual speed or another measured value.

Advantages include simple interfaces and straightforward testing. Limitations include additional wiring and fewer available diagnostic details.

Commissioning must check signal polarity, voltage/current ranges, analog scaling, common references, isolation, and wiring against the approved drawings.

5.2 Industrial network control

The PLC exchanges commands, references, status words, actual values, and diagnostic information over a communication network.

Advantages include reduced point-to-point wiring, richer diagnostics, and easier integration with HMI and SCADA systems.

Potential failure points include incorrect device addresses, incompatible profiles, incorrect process-data mapping, configuration mismatches, network interruptions, and stale feedback.

5.3 Hybrid control

A system may use network communication for speed reference and monitoring but retain hardwired signals for selected enables, interlocks, or fault indications.

The commissioning engineer must establish which channel owns each function. Two conflicting command paths can cause confusing or unpredictable behavior if the drive's command-source configuration is not understood.

The supported protocols depend on the exact PLC, drive model, communication module, firmware, and device profile. A protocol name alone does not establish compatibility.

7. Cyclic Process Data and Acyclic Parameter Access

Many industrial drive networks use two broad categories of data exchange.

Cyclic process data is exchanged repeatedly during normal operation. It commonly includes control words, speed references, status words, and actual speed values.

Acyclic parameter access reads or writes configuration and diagnostic parameters on demand. Examples include reading a fault history or accessing a drive parameter through a supported engineering interface.

Cyclic data is typically used for time-sensitive operational commands. Acyclic access is commonly used for setup and diagnostics, although the exact implementation depends on the protocol and device.

A drive may have a healthy cyclic connection while parameter access fails, or vice versa. Commission both separately when both are required.

8. Drive Control Word and Status Word

A control word is a bit field sent to the drive to request operating states or actions. A status word is a bit field returned by the drive to report its state.

Typical control-word functions may include:

  • Enable or disable operation.
  • Request a run state.
  • Select direction.
  • Acknowledge a fault.
  • Request a defined state transition.

Typical status-word information may include:

  • Ready to switch on.
  • Ready to operate.
  • Operation enabled.
  • Running or at speed.
  • Fault active.
  • Warning active.
  • Reference reached.

Important: There is no universal control-word bit layout for every drive. Bit meanings, sequencing, and required combinations depend on the drive manufacturer, protocol, and supported profile.

8.1 Example of a simplified control interface

PLC-to-drive data Purpose Required verification

9. Drive State Machine and Enable Sequence

Many drives implement a defined state machine. A command to run may be ignored if the drive is not in the required state.

A simplified operating sequence is:

Drive Powered
      ↓
Initialization Complete
      ↓
Ready State
      ↓
Enable Conditions Satisfied
      ↓
Operation Enabled
      ↓
Run Command Accepted
      ↓
Motor Accelerates
      ↓
Target Operating Condition Reached

Faults, missing permissives, or an invalid control-word sequence may prevent a transition.

Commissioning must verify both the commands sent by the PLC and the actual states reported by the drive. Do not assume that setting a single PLC bit is sufficient to enable every drive model.

10. Network Addressing and Device Configuration

10.1 IP-based drives

For Ethernet-based communication, confirm:

  • Correct PLC and drive IP addresses.
  • Correct subnet mask and any required gateway.
  • No duplicate IP addresses.
  • Correct device name where required by the protocol.
  • Correct communication module and firmware compatibility.
  • Correct drive device description or hardware configuration.
  • Correct cyclic data size and mapping.
  • Required switch and network settings.

Example addressing:

Device Example IP address Subnet mask
PLC 192.168.20.10 255.255.255.0
Drive 1 192.168.20.21 255.255.255.0
Drive 2 192.168.20.22 255.255.255.0
Engineering PC 192.168.20.30 255.255.255.0

These addresses are examples only. Always use the approved plant network plan.

10.2 PROFINET-specific checks

For a PROFINET drive, verify:

  • Correct device name.
  • Correct IP configuration.
  • Correct GSDML file and device version.
  • Correct module or submodule configuration.
  • Correct input and output process-data lengths.
  • Correct PLC hardware configuration and downloaded project.
  • Correct assignment of process data to PLC tags.

A device name or configuration mismatch can prevent the drive from entering data exchange even when the cable and IP address appear correct.

10.3 EtherNet/IP-specific checks

For an EtherNet/IP drive, verify:

  • Correct device profile or electronic data sheet.
  • Correct IP address and device identity.
  • Correct input and output assembly instances.
  • Correct assembly data sizes.
  • Correct connection parameters and supported connection type.
  • Correct PLC tag mapping to the drive's process data.

Incorrect assembly sizes or instances can prevent a connection or result in incorrect process data.

11. PLC Tag Mapping and Data Types

The PLC program must map communication data to meaningful engineering variables.

Typical signals include:

  • Command bits and control words.
  • Speed, torque, or position references.
  • Drive status and fault words.
  • Actual speed, torque, current, and position.
  • Warning codes and diagnostic data.
Signal Common representation Common mistake
Run request BOOL or control-word bit Wrong bit or incorrect command sequence
Control word UINT or WORD Incorrect bit layout or signed interpretation
Speed reference INT, DINT, REAL, or profile-specific value Wrong scaling or range
Status word UINT or WORD Incorrect bit decoding
Actual speed Integer or floating-point value Incorrect unit or sign
Fault code Integer or structured diagnostic data Incorrect interpretation of code
Position feedback Integer, DINT, or REAL Wrong counts-per-unit conversion

Use the exact data types specified by the drive's communication profile.

11.1 Reference scaling

A drive may represent its speed reference as a percentage of a configured reference value, as an engineering-unit value, or through a manufacturer-specific raw scale.

For example, if the drive documentation defines a raw value of 16384 as 100% reference, a 50% command would be:

\[ N = \frac{50}{100}\times 16384 = 8192 \]

This relationship is valid only for that assumed scaling definition. Other drives may use different ranges, signed values, or direct engineering units.

11.2 Actual speed conversion

Suppose a hypothetical drive defines 100% reference as 1500 rpm and reports actual speed as a signed percentage of that reference.

\[ n = \frac{N}{16384}\times 1500 \]

If the returned value is 8192:

\[ n = \frac{8192}{16384}\times 1500 = 750\text{ rpm} \]

This example assumes the drive uses the stated raw range and reference convention. Confirm the actual parameterization and sign convention before applying a conversion.

12. Pre-Commissioning Electrical and Mechanical Checks

Communication should not be used to conceal incorrect installation or unsafe machine conditions.

Before commanding motion, verify the approved installation requirements.

Electrical checks

  • Drive supply voltage and phase configuration match the specification.
  • Protective earth and bonding are correct.
  • Motor cable and terminals match the electrical drawings.
  • Motor nameplate data has been entered correctly.
  • Control and feedback wiring are correct.
  • Encoder wiring and feedback configuration are verified where applicable.
  • Shielding and cable separation meet the manufacturer's requirements.
  • Emergency stop and safety functions are installed and validated as specified.

Mechanical checks

  • Machine and motor installation are complete.
  • Couplings, guards, and mechanical restraints are checked.
  • The load can be moved safely during testing.
  • Rotation direction can be checked under controlled conditions.
  • Brakes and holding devices are configured correctly where fitted.
  • The test area is clear and personnel are outside hazardous zones.

Perform electrical isolation and lockout/tagout where required. Never handle motor power terminals, feedback wiring, or rotating equipment under unsafe energized conditions.

13. Drive Parameter Verification

14. Controlled Functional Commissioning

Stage 1: Verify communication without motion

  1. Confirm the correct drive identity.
  2. Confirm the network connection and process-data exchange.
  3. Read the drive status word and actual-value data.
  4. Verify fault and warning information.
  5. Confirm that the PLC maps each signal correctly.
  6. Check whether the drive is in the intended command and reference mode.

Stage 2: Verify command behavior

  1. Confirm the drive is in the specified safe test state.
  2. Verify that the PLC's enable request follows the required sequence.
  3. Confirm that the drive reports the expected state.
  4. Test a stop request and verify the specified response.
  5. Test fault acknowledgement only under approved conditions.
  6. Confirm the PLC handles rejected commands and missing permissives correctly.

Stage 3: Verify reference handling

  1. Apply a low, approved reference value.
  2. Confirm the value received by the drive.
  3. Confirm the actual value reported to the PLC.
  4. Verify scaling, sign, limits, and units.
  5. Check reference changes and ramp behavior.
  6. Verify the response to an out-of-range request.

Stage 4: Verify motor operation

  1. Confirm the test area and load conditions are safe.
  2. Start the motor under the approved procedure.
  3. Check rotation direction.
  4. Verify actual speed and current.
  5. Check acceleration, deceleration, and stop behavior.
  6. Verify the expected drive status and PLC sequence feedback.
  7. Record results and investigate any deviation.

Stage 5: Verify faults and recovery

  1. Use approved methods to create or simulate the specified fault conditions.
  2. Verify the PLC detects the fault and displays the correct status.
  3. Confirm the configured stop response.
  4. Restore the fault condition safely.
  5. Verify acknowledgement and restart permissives.
  6. Confirm that communication recovery does not generate unintended motion.

15. Start, Stop, Direction, and Speed Commands

15.1 Start command

The PLC should request operation only when the required conditions are satisfied. These can include automatic mode, drive ready, no active fault, valid machine sequence, and process permissives.

The precise permissives depend on the machine design. Safety functions must remain independent of ordinary HMI or PLC communication commands where required by the safety architecture.

15.2 Stop command

The required stop behavior depends on the application and risk assessment. It may involve a controlled deceleration, a coast stop, a defined drive stop function, or a safety-related stop function.

Do not assume that every stop command is equivalent. Verify the configured stopping behavior, including what happens when communication is lost.

15.3 Direction command

Check:

  • Motor wiring and phase sequence where applicable.
  • Drive direction configuration.
  • PLC direction mapping.
  • Mechanical restrictions.
  • Whether reversal is permitted while running.
  • Whether the drive requires a stop before reversal.

Never assume that a positive reference necessarily means clockwise rotation. Direction conventions depend on wiring, motor orientation, and application configuration.

15.4 Speed command

Verify the complete signal chain:

PLC Speed Request
      ↓
Engineering-Unit Conversion
      ↓
Drive Reference Data
      ↓
Drive Internal Limits and Ramps
      ↓
Motor Actual Speed
      ↓
Drive Feedback Data
      ↓
PLC Actual-Speed Tag

A difference between commanded speed and actual speed may be normal during acceleration or under load. Commissioning should compare actual behavior against the specified limits and response profile.

16. Interlocks and Permissives

An interlock prevents an operation when a defined condition is not satisfied. A permissive indicates that the conditions required for an operation are met.

Examples include:

  • Guard or access conditions.
  • Machine sequence state.
  • Motor overload or drive fault state.
  • Brake release confirmation.
  • Cooling or lubrication availability.
  • Process equipment ready status.
  • Required upstream or downstream machine conditions.
  • Valid operating mode.

The PLC must enforce its intended control conditions rather than assuming the drive or HMI will enforce every machine-level requirement.

16.1 Interlock commissioning test

For each interlock:

  1. Identify the input condition and the affected command.
  2. Confirm the normal permitted state.
  3. Create the specified non-permissive state under safe test conditions.
  4. Verify the PLC prevents or stops the intended operation.
  5. Confirm the operator receives the correct diagnostic.
  6. Restore the condition.
  7. Verify that the machine does not restart unexpectedly.
  8. Record the result.

Safety-related interlocks must be tested according to the approved safety validation procedure.

17. Communication Loss and Fault Response

Possible communication failure causes include:

  • Network cable or switch failure.
  • Incorrect device address.
  • Drive communication module fault.
  • PLC or drive restart.
  • Incorrect process-data configuration.
  • Network congestion or connection timeout.
  • Protocol configuration mismatch.
  • Power interruption.

The drive and PLC may have different responses to a lost connection. The PLC may detect that data is invalid while the drive executes its configured communication-loss reaction.

17.1 Required checks

  • Confirm how communication loss is detected.
  • Verify the drive's configured communication-loss reaction.
  • Verify the PLC detects invalid or stale drive data.
  • Confirm the machine enters the specified state.
  • Confirm the HMI shows the correct fault or communication warning.
  • Verify the response to PLC restart and drive restart.
  • Verify reconnection without unintended motion.
  • Confirm commands are not replayed unexpectedly.
  • Verify fault reset and restart permissives.

The safe response cannot be generalized to “always stop immediately.” The appropriate reaction depends on the drive application, process, risk assessment, and designed stop function. It must be explicitly specified and validated.

Use the drive's diagnostic buffer and fault history. Record the actual fault code and its operating context before resetting it. Repeatedly resetting a drive without identifying the cause is a reliable way to turn a diagnosable fault into an intermittent one.

19. Performance and Data Update Verification

Check the timing and consistency of:

  • PLC command updates.
  • Drive control-word changes.
  • Drive status-word updates.
  • Speed-reference changes.
  • Actual-speed feedback.
  • Fault detection.
  • Stop response.
  • Communication-loss detection and recovery.

The acceptable response time depends on the application and communication design.

Ordinary networked drive communication should not be assumed to provide deterministic safety response. Safety-related communication and timing require an appropriate certified architecture and validation.

20. Special Considerations for Servo Drives

Servo systems require additional commissioning beyond basic run and speed control.

Verify:

  • Motor and drive compatibility.
  • Encoder or resolver type and feedback wiring.
  • Feedback polarity and scaling.
  • Motor identification and commutation where applicable.
  • Position and velocity units.
  • Electronic gearing and gear ratios.
  • Homing sequence and reference sensors.
  • Software travel limits.
  • Following-error limits.
  • Torque limits.
  • Motion profile and tuning.
  • Brake sequencing where applicable.
  • Safe motion functions where fitted.

20.1 Position scaling example

Suppose a machine axis uses a configured conversion of 10,000 encoder counts per millimetre. A measured change of 50,000 counts corresponds to:

\[ x = \frac{50000}{10000} = 5\text{ mm} \]

This assumes the configured scale is valid and the feedback is expressed in the stated counts. Actual servo systems may use internal units, electronic gearing, encoder interpolation, or other scaling conventions.

Servo tuning and motion tests should follow the drive and machine manufacturer's procedures. Do not run aggressive tuning or high-speed positioning on an unverified mechanical axis.

21. Safety Considerations

PLC-Drive communication is part of the control system, but normal communication alone is not a safety-rated means of stopping hazardous motion.

Relevant concepts include:

  • STO: Safe Torque Off, which prevents the drive from producing torque under the specified conditions. It does not necessarily bring a moving load to a controlled stop.
  • SS1: Safe Stop 1, a safety function that generally initiates a controlled stop followed by torque removal, subject to the implemented system.
  • SS2: Safe Stop 2, a safety function that brings the drive to a controlled stop and maintains a defined safe operating state according to the implementation.
  • Safety-rated fieldbus: A certified communication method designed for specified safety-related functions, when used with compatible equipment and an appropriately engineered safety system.

Availability and exact behavior depend on the drive, safety hardware, configuration, and applicable standards.

Commissioning must verify:

  • Correct safety circuit wiring and configuration.
  • Correct safety function selection.
  • Correct stopping behavior.
  • Required feedback and diagnostics.
  • Reset and restart behavior.
  • Validation records and authorized sign-off.

Never bypass a safety circuit to make communication commissioning easier.

23. Acceptance Criteria

The project specification should define measurable acceptance limits. Typical criteria include:

  • PLC and drive exchange the required process data.
  • All required control and status bits are correctly mapped.
  • Reference and feedback values use correct scaling, units, and sign conventions.
  • The drive responds to permitted commands as specified.
  • The drive rejects or blocks commands when required conditions are absent.
  • The correct fault and warning information reaches the PLC and HMI.
  • Communication loss produces the specified response.
  • Reconnection does not cause unintended operation.
  • Motor direction, speed range, ramp behavior, and performance meet requirements.
  • Required safety functions pass their separate validation tests.
  • Configuration backups, test records, and defect disposition are complete.

Do not assume a universal network response time, speed tolerance, or stopping time. These values must come from the approved application requirements and the relevant drive and machine specifications.

24. Example: PLC-Controlled Conveyor VFD

Consider a conveyor controlled by a PLC through an Ethernet-connected VFD.

The PLC sends a run request and speed reference. The drive returns ready status, running status, actual speed, and fault information.

24.1 Commissioning sequence

  1. Confirm the drive identity, address, and network connection.
  2. Verify the motor nameplate data and configured control mode.
  3. Confirm the PLC control word and status word mapping.
  4. Check that the drive uses the intended network command and reference sources.
  5. Verify the run permissives, including required machine and safety conditions.
  6. Apply a low, approved speed reference.
  7. Verify actual speed and direction.
  8. Test controlled stopping and the required deceleration.
  9. Test an approved drive fault condition and verify PLC diagnostics.
  10. Test communication loss under controlled conditions.
  11. Restore communication and confirm no unintended restart.
  12. Record the final settings and results.

25. Common Commissioning Mistakes

  • Assuming network connectivity means the drive is ready to run.
  • Using the wrong device profile, process-data layout, or assembly size.
  • Mapping the control word or status word incorrectly.
  • Ignoring the drive's command-source selection.
  • Using the wrong motor nameplate values.
  • Applying incorrect speed scaling or signedness.
  • Resetting faults before recording diagnostic information.
  • Testing direction without confirming mechanical safety.
  • Allowing conflicting hardwired and network command sources.
  • Treating an ordinary network stop as a safety-rated stop.
  • Ignoring communication-loss behavior and restart conditions.
  • Failing to back up the final PLC and drive configurations.

26. Interview Questions and Answers

Q1. What is PLC-Drive communication commissioning?

It is the verification of communication, command and feedback mapping, drive state transitions, reference scaling, fault handling, and controlled motor operation between a PLC and a drive.

Q2. What is the difference between a control word and a status word?

The control word carries commands from the PLC to the drive. The status word reports the drive's current state and selected diagnostic conditions back to the PLC.

Q3. Why might a drive communicate correctly but refuse to run?

The drive may not be enabled, a fault may be active, the command source may be incorrect, or a required permissive or state transition may be missing.

Q4. What is cyclic process data?

It is data exchanged repeatedly during normal operation, typically including commands, references, status, and actual values.

Q5. Why is reference scaling important?

The PLC and drive must interpret the reference consistently. Incorrect scaling can cause the motor to run at an unintended speed or position.

Q6. Why must the communication-loss reaction be checked?

The PLC and drive may react differently to a lost connection. Testing verifies the specified fault response, stale-data handling, and recovery behavior.

Q7. What is STO?

Safe Torque Off is a safety function that prevents the drive from producing torque under its specified conditions. It does not necessarily stop a moving load in a controlled manner.

Q8. Why should the drive fault code be recorded before resetting?

The diagnostic record provides evidence for root-cause analysis. Resetting may clear or obscure the information needed to identify the original failure.

Q9. What additional checks are required for servo drives?

Encoder feedback, position scaling, homing, travel limits, following error, torque limits, motion tuning, and any applicable safety-related motion functions.

Q10. What proves that PLC-Drive commissioning is complete?

Verified process-data mapping, correct command and feedback behavior, successful functional and fault-recovery tests, required safety validation, and completed configuration and handover records.

27. Final PLC-Drive Commissioning Checklist

  • Electrical and mechanical installation verified.
  • PLC and drive models, firmware, and configurations confirmed.
  • Communication interface and protocol configured.
  • Device addressing and process-data layout verified.
  • Control word and status word mapping checked.
  • Speed, torque, or position reference scaling verified.
  • Drive command and reference sources confirmed.
  • Motor nameplate and critical drive parameters verified.
  • Enable, start, stop, direction, and reset behavior tested.
  • Permissives and interlocks tested.
  • Faults, warnings, and diagnostics verified.
  • Communication loss and recovery tested.
  • Motor operation and performance verified.
  • Safety functions validated separately as required.
  • Final settings, backups, and test records saved.
