1. Definition and Purpose

PLC-HMI communication commissioning is the systematic process of configuring, verifying, testing, and documenting data exchange between a Programmable Logic Controller (PLC) and a Human-Machine Interface (HMI) so that operators can monitor machine conditions, issue permitted commands, acknowledge alarms, and interact with the automation system reliably.

Commissioning must verify more than whether the HMI connects to the PLC. It must establish that the correct data is exchanged, displayed, interpreted, and acted upon under normal conditions, faults, communication interruptions, and recovery.

Core principle: A communication indicator showing green proves neither correct tag mapping nor correct machine behavior. Networks are excellent at delivering the wrong value exactly as configured.

2. Scope of PLC-HMI Communication

PLC-HMI commissioning covers these areas:

  • Physical communication media, switches, connectors, and network topology.
  • PLC and HMI interface configuration, including IP addresses and protocols.
  • Device connections, driver configuration, tag mapping, and data types.
  • Reading PLC values and writing operator commands.
  • Command handshakes, permissives, interlocks, and status feedback.
  • Alarms, events, trends, recipes, and diagnostic information.
  • Communication failure detection, timeout handling, and recovery.
  • Access control, operational safety, testing, and acceptance documentation.

It does not replace PLC logic validation, machine safety validation, or a complete machine risk assessment. Those activities must be coordinated with communication testing.

3. PLC-HMI Communication Architecture

A typical industrial architecture is:

Operator
   ↓
HMI Runtime
   ↓
HMI Communication Driver
   ↓
Industrial Ethernet / Field Network
   ↓
Industrial Switches
   ↓
PLC Ethernet Interface
   ↓
PLC Tags and Program Logic
   ↓
Sensors, Actuators, Drives, and Machine Sequence

The return path carries PLC values and status information back to the HMI for display.

In a real installation, the HMI may communicate with the PLC through a managed switch, an integrated switch, a remote I/O network, or a routed industrial network. The exact design depends on the machine architecture.

3.1 Main components

Component Purpose Commissioning focus
PLC CPU Executes machine logic and exposes data CPU state, tag availability, communication services
PLC Ethernet module Provides network connectivity Link status, IP settings, firmware compatibility
HMI panel or PC Displays data and accepts operator input Runtime, project version, touch/input functionality
HMI driver Implements communication with the PLC Correct driver, protocol, device selection
Industrial switch Connects network devices Port status, VLANs, link speed, network faults
Ethernet cable Physical data transmission Correct wiring, connector condition, shielding where required
PLC tag database Defines process variables Data type, scope, address, permissions
HMI tag database Associates displayed objects with PLC data Tag mapping, scaling, read/write access

4. Communication Protocols and Interfaces

A protocol defines how devices identify each other, request information, exchange data, and interpret messages.

Protocol or interface Typical application Important checks
EtherNet/IP Allen-Bradley PLCs and compatible devices Controller path, device identity, supported data access
PROFINET Siemens PLCs and compatible devices Device name, IP configuration, network topology
Modbus TCP PLCs, meters, gateways, and third-party equipment Unit ID where applicable, register addresses, data format
OPC UA Structured data exchange between supported industrial systems Endpoint, certificates, security policy, namespaces
Mitsubishi MC Protocol Mitsubishi PLC data access Supported frame, connection settings, device addressing
Siemens S7 communication HMI access to compatible Siemens PLCs CPU compatibility, connection path, access configuration
Serial communication Legacy or serial-based HMI-PLC links RS-232/RS-485 wiring, baud rate, parity, stop bits, protocol

These technologies are not interchangeable merely because they all exchange data. A driver supporting a protocol does not guarantee that every PLC model, data type, or firmware version is supported.

4.1 Choosing the communication method

Confirm the following before configuring anything:

  1. PLC manufacturer, model, CPU, firmware, and communication interface.
  2. HMI manufacturer, model, runtime version, and supported drivers.
  3. Required protocol and any licensing requirements.
  4. Whether the PLC exposes symbolic tags, absolute addresses, or both.
  5. Whether a gateway, protocol converter, or routed connection is required.
  6. Whether the selected method supports all required data types and write operations.

For an existing machine, inspect the approved electrical drawings and project configuration before changing network settings. A working production system is not the ideal place to conduct an experiment in addressing.

5. IP Addressing and Network Configuration

5.1 Basic IPv4 concepts

An IPv4 address identifies a network interface. The subnet mask identifies which part of the address represents the local network.

Example:

Device IP address Subnet mask
PLC 192.168.10.10 255.255.255.0
HMI 192.168.10.20 255.255.255.0
Engineering PC 192.168.10.30 255.255.255.0

These example addresses place the devices on the same IPv4 subnet. They are illustrative only and must not be copied into a running plant network without checking its approved addressing plan.

5.2 IP address and subnet verification

Check the following:

  • Each device has the intended IP address.
  • No two devices use the same IP address on the same network.
  • The subnet mask matches the approved design.
  • The default gateway is configured only when required by the network design.
  • VLANs, access-control lists, and routing rules permit the required traffic.
  • The HMI is communicating with the intended PLC, not another PLC with a copied project.
  • Any required DNS names, routes, or gateway settings are correct.

Two devices can be physically connected and still be unable to communicate because their addressing or network configuration is wrong.

5.3 Useful Windows commands

Run these from an authorized engineering PC connected to the relevant network.

ipconfig /all
ping 192.168.10.10
arp -a
tracert 192.168.10.10

Interpretation:

  • ipconfig /all shows the PC's IP configuration.
  • ping checks IP reachability when ICMP is permitted.
  • arp -a shows known IP-to-MAC address mappings.
  • tracert helps investigate routed paths.

Important: A failed ping does not prove the PLC is offline. ICMP may be disabled, filtered, or deprioritized. A successful ping does not prove that the PLC communication protocol or HMI tag access is working.

Do not scan production networks or change switch configurations without authorization.

6. Communication Settings and Connection Parameters

The HMI project typically defines a connection to one or more PLC devices.

Common parameters include:

  • PLC device type and model.
  • Communication driver or protocol.
  • PLC IP address or network path.
  • Rack, slot, station number, or CPU selection where applicable.
  • Port number or serial settings.
  • Connection timeout and retry behavior.
  • Polling or subscription settings.
  • Tag addressing mode.
  • Security credentials or certificates where required.

6.1 Connection timeout and retry behavior

A timeout determines how long the HMI waits for a response before treating an operation as unsuccessful. Retry behavior determines how the client attempts communication again.

Timeouts that are too short can produce nuisance communication alarms during brief delays. Excessively long timeouts can make faults slow to appear to the operator.

Choose settings based on the PLC, protocol, network design, HMI workload, and required fault-detection time. Do not tune timeouts merely to hide an underlying network problem.

7. PLC Tags and HMI Tag Mapping

A tag is a named variable or data point used to represent a machine condition, measurement, command, or status.

The PLC tag and HMI object must refer to the same intended data.

Example:

PLC tag Data type Intended HMI use Access
Machine_Ready BOOL Ready indicator Read
Cycle_Active BOOL Cycle-running indicator Read
Fault_Active BOOL Fault indicator Read
Part_Count DINT Production counter Read
Pressure_PV REAL Pressure display Read
Start_Request BOOL Operator start request Write, with PLC validation
Reset_Request BOOL Operator reset request Write, with PLC validation

The names are illustrative. Actual tag names and data types must match the deployed PLC program.

7.1 Symbolic versus absolute addressing

Symbolic addressing uses named variables, such as Machine_Ready.

Advantages include easier maintenance, clearer diagnostics, and reduced dependence on raw memory locations. Its availability depends on the PLC, protocol, driver, and access configuration.

Absolute addressing uses physical or logical locations, such as a register, data block offset, or memory address.

Absolute addressing requires careful checking of address conventions, offsets, array layouts, and data sizes. Different software packages may display addresses differently, so verify the manufacturer's addressing rules.

7.2 Tag mapping checklist

  • The HMI tag points to the correct PLC device.
  • The tag name or address exists in the deployed PLC program.
  • The data type matches the PLC variable.
  • The read/write permissions are appropriate.
  • Array indexes and structure members are correct.
  • The HMI object references the intended HMI tag.
  • Scaling, units, and display formatting are correct.
  • No obsolete or duplicate tags are used unintentionally.
  • The downloaded PLC and HMI projects match the approved versions.

8. Data Types, Byte Order, and Data Interpretation

A communication link may successfully transfer bytes while the HMI displays a completely incorrect value. The cause can be a data type mismatch, incorrect word order, wrong scaling, or an incorrect address.

Data type Common purpose Common error
BOOL Single true/false condition Wrong bit or inverted interpretation
INT Signed 16-bit integer Incorrect signedness or range
UINT Unsigned 16-bit integer Negative-looking or oversized value
DINT Signed 32-bit integer Incorrect word mapping or size
REAL 32-bit floating-point value Incorrect format or word order
STRING Text or identifiers Different string length or encoding conventions
ARRAY Repeated data values Incorrect index, length, or element type
STRUCT/UDT Grouped related variables Incompatible layout or unsupported access

Data sizes and formats depend on the specific controller and communication interface. For example, an IEEE 754 32-bit floating-point value occupies four bytes, but interpreting those bytes correctly also requires the expected byte and word order.

8.1 Scaling and engineering units

Suppose a PLC provides an integer value from 0 to 27648 representing a pressure transmitter's 0 to 10 bar range.

The engineering value can be calculated as:

\[ P = \frac{N}{27648}\times 10 \]

Where:

  • \(P\) is pressure in bar.
  • \(N\) is the raw PLC value.

At \(N = 13824\):

\[ P = \frac{13824}{27648}\times 10 = 5\text{ bar} \]

This example assumes the raw range and scaling are actually configured that way. Other systems use different raw ranges, direct engineering units, or different analog input representations.

Check that scaling is applied exactly once. If the PLC already supplies pressure in bar and the HMI scales it again, the displayed value will be wrong even though communication is functioning.

8.2 Units and precision

Verify:

  • Pressure: bar, kPa, or MPa.
  • Temperature: °C or °F.
  • Speed: rpm or another specified unit.
  • Position: mm, degrees, or encoder counts.
  • Time: milliseconds, seconds, or minutes.
  • Counters: integer range, rollover behavior, and reset behavior.
  • Display precision: enough to be useful without implying false measurement accuracy.

9. Read and Write Operations

HMI communication commonly has two directions.

Read operations: The HMI receives PLC data for indicators, numeric displays, alarms, trends, and status screens.

Write operations: The HMI sends permitted operator inputs to PLC variables, such as setpoints, command requests, recipe values, or reset requests.

Read access and write access must be considered separately. A tag can read correctly but reject writes because of access settings, driver limitations, PLC permissions, or application logic.

9.1 Read verification

For each critical read tag:

  1. Identify the actual PLC variable or address.
  2. Establish its expected value using approved online monitoring or a controlled machine condition.
  3. Observe the same value on the HMI.
  4. Confirm the value updates as the PLC variable changes.
  5. Check the units, scaling, sign, precision, and update behavior.
  6. Confirm that communication loss does not leave a misleading stale value presented as current.

9.2 Write verification

For each writable tag:

  1. Confirm that the write operation is approved for commissioning.
  2. Identify the expected operating mode and permissives.
  3. Verify the correct target tag and permitted value range.
  4. Apply a controlled test input.
  5. Confirm the PLC receives the request.
  6. Confirm that PLC logic accepts or rejects it according to the specified conditions.
  7. Verify the resulting machine status or feedback.
  8. Confirm that unauthorized or out-of-range inputs are rejected.

Do not test start, motion, reset, pressure, speed, or other consequential commands on a live machine without the required authorization, risk controls, and safe operating conditions.

10. Command Handshake Design

For important operator commands, a handshake is usually more robust than treating a momentary HMI button as proof that an action occurred.

A command interface may include:

  • Start_Request: HMI asks the PLC to start.
  • Start_Accepted: PLC confirms that the request was accepted.
  • Cycle_Active: PLC indicates that the sequence is running.
  • Start_Reject: PLC indicates that the request was rejected.
  • Reject_Code: PLC provides the reason.
  • Command_Busy: PLC indicates that a command is being processed.

A typical logical sequence is:

Operator presses Start
        ↓
HMI sends Start_Request
        ↓
PLC checks mode, permissives, interlocks, and faults
        ↓
PLC accepts or rejects the request
        ↓
HMI displays accepted, rejected, or busy status
        ↓
PLC reports actual machine state

The HMI must distinguish a request from a successful outcome. A button press is not proof that the machine started.

10.1 Momentary and maintained commands

A momentary command is active for a limited period or until the PLC acknowledges it. A maintained command remains active until it is explicitly cleared or its holding condition ends.

For a request/acknowledgement handshake, define:

  • Who sets the request bit.
  • Who clears the request bit.
  • How acknowledgement is generated.
  • What happens if acknowledgement never arrives.
  • What happens if communication fails during the command.
  • Whether a duplicate command can be accepted.
  • How the interface behaves after an HMI restart.

Avoid a request bit that remains permanently true after a communication interruption unless that behavior is explicitly required and safely handled.

10.2 Edge detection and duplicate commands

If the PLC detects only a rising edge, a request that remains true may not trigger again after the first event. Conversely, a poorly designed level-sensitive command can retrigger repeatedly.

Use the command pattern specified by the PLC application, such as:

  • Rising-edge request with PLC-side edge detection.
  • Request/acknowledgement handshake.
  • Sequence number or transaction identifier for systems requiring stronger duplicate detection.

Test the actual behavior instead of assuming that the HMI button animation reflects the PLC's command logic.

11. HMI Screens and Object Commissioning

Every interactive HMI object should be checked against its intended function.

HMI object Commissioning test
Status indicator Correct PLC condition drives the correct visual state
Numeric display Correct value, unit, sign, precision, and scaling
Numeric input Valid entries are accepted and invalid entries rejected
Start button Sends the intended request and shows the resulting state
Reset button Resets only the intended fault or sequence under approved conditions
Mode selector Displays and requests the correct mode with PLC validation
Alarm banner Correct alarm appears, clears, and retains required information
Trend Correct tag, time axis, sampling behavior, and engineering scale
Recipe interface Correct parameters, limits, selection, and transfer verification
Navigation button Opens the intended screen and respects access restrictions
Login/logout Enforces the configured user roles and session behavior

Test screen transitions, pop-up dialogs, overlapping objects, touch response, numeric keypad behavior, language settings, and screen readability under actual operating conditions.

12. Alarms, Events, and Trends

12.1 Alarm verification

For each configured alarm, verify:

  • Trigger condition.
  • Alarm text and equipment identification.
  • Priority or severity.
  • Active and cleared state.
  • Timestamp behavior.
  • Acknowledgement behavior.
  • Latching and reset conditions.
  • Required historical recording.
  • Behavior during communication loss.

Acknowledging an alarm generally means the operator has recognized it. It does not necessarily clear the underlying fault or make the machine safe to operate.

12.2 Alarm state versus communication fault

A PLC alarm and a communication alarm are different conditions.

If the HMI loses communication, it may be unable to receive new PLC alarms. The HMI should indicate that the data source is unavailable rather than displaying old values as if they were current.

Where the application requires it, define a separate communication-health status, stale-data indication, or timestamp/quality check.

12.3 Trend verification

Check:

  • Correct tag assignment.
  • Correct engineering units and scale.
  • Correct time base and sampling interval.
  • Behavior during value changes.
  • Historical retention and retrieval.
  • Handling of missing data.
  • Clock synchronization and timestamp interpretation.
  • Whether the sampling rate is appropriate for the process.

An HMI trend is not necessarily a high-speed data recorder. Fast transient capture may require PLC trace functionality or a dedicated data acquisition system.

13. Communication Loading and Performance

The HMI may read many tags across several screens. Poorly planned communication can increase network traffic, controller communication workload, or display latency.

Relevant factors include:

  • Number of connected HMI clients.
  • Total tag count.
  • Polling interval or subscription rate.
  • Number of simultaneously visible screens.
  • Array and structure read sizes.
  • Alarm and event subscriptions.
  • Trend sampling.
  • PLC communication capacity.
  • Network topology and other devices sharing the network.

13.1 Practical optimization

  • Read only the tags needed by the application.
  • Use reasonable update rates for each class of data.
  • Avoid unnecessarily rapid polling of slow-changing values.
  • Prefer efficient grouped reads where supported and appropriate.
  • Avoid repeatedly reading large structures for a single value.
  • Verify that background screens do not create excessive traffic.
  • Monitor actual communication performance under expected operating load.

Do not optimize solely for the smallest update interval. A counter updated every few seconds may be adequate, while a rapidly changing control-related display may require different handling. HMI communication should not replace deterministic control logic in the PLC.

14. Communication Loss and Recovery

Communication failure must be tested deliberately in a controlled commissioning environment.

Possible causes include:

  • Broken or disconnected cable.
  • Switch power loss.
  • Incorrect IP configuration.
  • PLC stop or power loss.
  • HMI restart.
  • Driver or protocol failure.
  • Network congestion.
  • Routing, VLAN, or firewall changes.
  • PLC connection resource exhaustion.

14.1 Expected failure behavior

The application specification should define:

  • How quickly the HMI detects communication loss.
  • What warning or fault appears.
  • Whether numeric values are blanked, marked invalid, or shown with a stale-data indicator.
  • Whether operator writes are disabled during the failure.
  • How the HMI behaves when the PLC returns.
  • Whether a command can be unintentionally replayed after reconnection.
  • Whether alarms, trends, and timestamps recover correctly.
  • Whether the operator must explicitly reissue a command.

A lost HMI connection must not be treated as a safety function. Machine motion and hazardous energy must be controlled by the designed PLC logic, safety system, and hardware architecture.

14.2 Controlled communication-loss test

  1. Confirm the test is authorized and the machine is in a safe state.
  2. Record the initial PLC state and HMI indications.
  3. Interrupt the intended communication path using an approved method.
  4. Confirm the HMI identifies the failure within the specified time.
  5. Verify that stale data and operator controls behave as specified.
  6. Restore the connection.
  7. Verify reconnection and correct tag updates.
  8. Confirm that no unintended command executes during recovery.
  9. Record the outcome and any defect.

Never disconnect a live production network simply to see what happens. That is not a test strategy; it is an incident with paperwork.

15. Cybersecurity and Access Control

PLC-HMI networks are operational technology networks. Availability, integrity, and safe operation matter alongside confidentiality.

Commissioning checks should include:

  • Unique and approved device addresses.
  • Controlled engineering access.
  • Role-based HMI permissions.
  • Strong credentials and removal of default passwords where applicable.
  • Restricted network paths and unnecessary services.
  • Approved firewall rules and VLAN configuration.
  • Secure protocol configuration where supported.
  • Certificate validation for systems using OPC UA or similar security mechanisms.
  • Controlled software and project backups.
  • Change records for IP, driver, firmware, and project modifications.
  • A recovery plan for corrupted projects or failed updates.

Do not expose PLC or HMI interfaces directly to public networks. Remote access should follow the plant's approved architecture, authentication, logging, and authorization requirements.

16. PLC-HMI Commissioning Procedure

Stage 1: Documentation and preparation

  • Obtain approved PLC and HMI project versions.
  • Review electrical drawings and network architecture.
  • Confirm the PLC model, firmware, and HMI model.
  • Verify protocol and driver compatibility.
  • Prepare an IP address and device register.
  • Obtain the tag list, alarm list, and HMI screen specifications.
  • Review machine risk controls and test permissions.
  • Back up the current working PLC and HMI projects.

Stage 2: Physical inspection

  • Inspect network cables, connectors, and ports.
  • Verify switch power and link indicators.
  • Confirm cable routing and separation from sources of electrical interference according to the design.
  • Check shield termination and grounding where specified.
  • Confirm that the HMI and PLC interfaces are connected to the intended network.
  • Check that labels match the electrical drawings.

Stage 3: Network verification

  • Verify IP address, subnet mask, and required gateway.
  • Check for duplicate addresses.
  • Verify link speed and duplex where relevant.
  • Confirm VLAN and routing configuration.
  • Check basic network reachability where permitted.
  • Confirm the intended PLC identity.
  • Verify that required protocol traffic is permitted.

Stage 4: PLC and HMI configuration

  • Verify PLC communication services and interface configuration.
  • Configure the HMI device connection and driver.
  • Confirm device path, slot, station, or other protocol-specific parameters.
  • Verify PLC tag access permissions.
  • Download only the approved project version.
  • Confirm the HMI runtime is running the intended application.
  • Verify that the connection status is healthy.

Stage 5: Data verification

  • Test representative BOOL, integer, floating-point, and structured values where used.
  • Verify addresses and tag names.
  • Confirm numeric scaling, units, and display precision.
  • Test read-only tags.
  • Test writable tags under approved conditions.
  • Confirm command handshakes and PLC-side interlocks.
  • Verify alarm and event behavior.
  • Verify trends and historical data where required.

Stage 6: Fault and recovery testing

  • Test the specified communication-loss scenario.
  • Verify alarm and stale-data indication.
  • Verify command handling during loss of communication.
  • Restore communication and confirm recovery.
  • Confirm no unintended commands are replayed.
  • Verify behavior after an HMI restart if required.
  • Record deviations and retest corrected defects.

Stage 7: Final handover

  • Complete the approved test records.
  • Resolve or formally disposition defects.
  • Save final PLC and HMI backups.
  • Record firmware, project versions, and communication settings.
  • Update the network diagram and tag documentation.
  • Obtain required commissioning and customer sign-offs.

17. Troubleshooting Guide

Symptom Likely causes Diagnostic action
HMI shows disconnected Cable, IP, driver, PLC state, or routing issue Check physical link, addressing, PLC status, and driver diagnostics
Ping works but HMI is disconnected Protocol service, port, driver, or access issue Verify protocol settings and communication diagnostics
Some tags work and others fail Incorrect address, unsupported data type, or access restriction Compare failed tags with PLC declarations and driver support
BOOL value is inverted Incorrect logic polarity or wrong bit mapping Monitor the actual PLC bit and verify HMI tag configuration
Numeric value is incorrect Wrong data type, address, scaling, or byte order Compare raw PLC value with HMI interpretation
Value freezes Polling problem, stale cache, lost connection, or tag update issue Check quality status, timestamps, driver diagnostics, and PLC updates
Writes fail but reads work Write permission, mode restriction, unsupported access, or PLC logic rejection Check write diagnostics, tag permissions, and command acceptance feedback
HMI updates slowly Excessive polling, large reads, network congestion, or PLC workload Review communication load and update rates
Repeated communication alarms Intermittent cable, switch port, power, or network fault Inspect physical layer and switch diagnostics
Values become wrong after project update Inconsistent project versions or changed tag definitions Compare deployed versions and validate the mapping
HMI reconnects but command behavior is wrong Stale request state, retry behavior, or handshake defect Test request/acknowledgement logic and reconnection handling
Alarms appear late Polling delay, alarm configuration, or PLC logic timing Measure the full detection and display path

17.1 Diagnostic order

Use a layered approach instead of changing random settings until the fault disappears.

1. Physical layer
   ↓
2. IP addressing and network path
   ↓
3. Protocol and driver configuration
   ↓
4. PLC access and tag availability
   ↓
5. HMI tag mapping and data types
   ↓
6. PLC logic, handshake, and permissives
   ↓
7. Display behavior, alarms, and performance

Change one variable at a time where practical and record the original setting. If several parameters are changed simultaneously, the root cause becomes harder to identify.

18. FAT and SAT for PLC-HMI Communication

Factory Acceptance Testing (FAT) checks the integrated system before shipment or site deployment. Site Acceptance Testing (SAT) confirms operation under the installed site's actual network, hardware, and operating conditions.

Test item FAT focus SAT focus
PLC-HMI connection Correct configured connection Correct installed network path
Tag mapping Simulated or bench-verified values Actual machine values
Data scaling Known test values Real sensor and process values
Operator commands Controlled logic testing Controlled machine testing
Alarms Trigger, acknowledgement, and reset Actual installed alarm behavior
Network loss Simulated disconnection Approved site-specific failure test
Performance Expected bench workload Installed operating workload
Security Roles and access configuration Actual deployed access controls
Documentation Approved project and test records As-built configuration and final sign-off

FAT cannot fully prove site network performance when the production switch, routed path, or final machine hardware is not present. SAT must close that gap.

19. Acceptance Criteria

Acceptance criteria must be defined before testing and aligned with the project specification.

Typical criteria include:

  • HMI connects to the correct PLC using the approved communication method.
  • Required tags update within specified time limits.
  • All tested values match PLC values and intended engineering units.
  • All writable controls enforce the required limits, modes, permissives, and interlocks.
  • Commands receive appropriate acknowledgement or rejection feedback.
  • Alarms display the correct message, priority, and state.
  • Communication loss is detected within the specified time.
  • Stale data is not misleadingly presented as current.
  • Reconnection does not trigger unintended commands.
  • HMI response time and communication loading meet the specified requirements.
  • Access controls behave according to the approved design.
  • Final project backups, configuration records, and test evidence are available.

Do not invent a universal response-time limit. A project's required timing depends on the process, protocol, display function, and contractual specification. Safety-related response times require separate analysis and validation.

20. Example: PLC-HMI Commissioning for a Hydraulic Clamping Station

Consider a station with a PLC controlling a hydraulic clamp and an HMI displaying pressure, clamp status, machine mode, and alarms.

20.1 Required tags

Tag Type HMI purpose
Clamp_Closed BOOL Clamp-closed status
Clamp_Open BOOL Clamp-open status
Hydraulic_Pressure REAL Pressure display
Auto_Mode BOOL Mode indication
Clamp_Request BOOL Operator command request
Clamp_Sequence_Active BOOL Sequence feedback
Hydraulic_Fault BOOL Fault indication
Communication_Healthy BOOL Communication or data-quality indication

Communication_Healthy must be designed carefully. If the PLC itself supplies this tag, it cannot independently prove that communication is healthy when the link carrying that tag is lost. The HMI should also use the driver's connection or data-quality diagnostics.

20.2 Commissioning tests

  1. Confirm the HMI pressure display matches the PLC's pressure variable.
  2. Apply an approved test condition and verify pressure scaling.
  3. Confirm Clamp_Closed and Clamp_Open match the actual position feedback.
  4. Request clamp operation only under the specified safe conditions.
  5. Verify that the PLC rejects the command when required permissives are absent.
  6. Verify that the HMI displays sequence feedback rather than assuming the clamp moved merely because a request was sent.
  7. Trigger an approved fault condition and verify the alarm.
  8. Test communication loss in a controlled condition.
  9. Restore communication and verify correct state reporting without unintended movement.

The HMI must not bypass the PLC's process interlocks or replace the machine's designed safety functions.

21. Common Commissioning Mistakes

  • Assuming a successful ping proves the application works.
  • Assuming a green connection indicator proves every tag is correct.
  • Using duplicate IP addresses or undocumented network settings.
  • Mapping a tag to the wrong PLC variable or bit.
  • Mixing signed and unsigned integers.
  • Applying scaling twice.
  • Ignoring byte and word ordering for multi-byte values.
  • Testing commands without checking machine mode and permissives.
  • Treating a button press as confirmation that the operation completed.
  • Allowing old values to appear current during communication failure.
  • Ignoring command bits that remain active after reconnection.
  • Changing PLC, HMI, or switch configuration without a backup.
  • Testing only normal operation and never checking fault recovery.
  • Failing to document final IP addresses, versions, and test results.

22. Interview Questions and Answers

Q1. What is PLC-HMI communication commissioning?

It is the verification of the physical connection, network configuration, communication protocol, tag mapping, read/write operations, command feedback, alarms, performance, and recovery behavior between a PLC and HMI.

Q2. Why can an HMI connect successfully but display incorrect values?

The connection may be healthy while individual tags have incorrect addresses, data types, scaling, units, or byte ordering.

Q3. What is the difference between PLC communication and HMI application logic?

Communication transfers data between systems. HMI application logic defines how that data is displayed and how operator inputs are handled. Both must be verified.

Q4. Why is a command handshake useful?

It distinguishes a command request from acceptance and completion, supports timeout handling, and reduces ambiguity during communication faults.

Q5. Why should the PLC validate HMI commands?

The HMI is an operator interface, not the final authority on machine permissives. The PLC must validate the command against its control logic, operating mode, and applicable interlocks.

Q6. What is the difference between a communication alarm and a process alarm?

A communication alarm indicates that data exchange is unavailable or degraded. A process alarm indicates an equipment or process condition reported by the automation system.

Q7. Does a successful ping prove that the HMI can communicate with the PLC?

No. Ping verifies IP reachability when ICMP is allowed. The required application protocol, driver, device path, and tag access may still be incorrect.

Q8. Why must communication-loss recovery be tested?

A system may reconnect while retaining stale values, pending requests, or incorrect quality states. Recovery testing verifies that the HMI returns to a valid state without unintended actions.

Q9. What is the difference between FAT and SAT for PLC-HMI communication?

FAT verifies the integrated design before deployment. SAT verifies the installed system using the actual site network and machine conditions.

Q10. Why is HMI communication not a safety function by itself?

Communication can fail, be delayed, or deliver stale data. Safety functions require an appropriately designed and validated safety architecture, not reliance on ordinary HMI communication.

23. Final Commissioning Checklist

  • Approved PLC and HMI versions identified and backed up.
  • Physical network inspected and verified.
  • IP addressing and network configuration confirmed.
  • Correct PLC device and communication driver selected.
  • PLC-HMI connection verified.
  • Required tags and data types validated.
  • Scaling, units, and numeric displays checked.
  • Read and write operations tested.
  • Command handshake, rejection, and timeout behavior checked.
  • Alarms, trends, and navigation verified.
  • Communication loss and recovery tested.
  • Stale-data behavior verified.
  • Network loading and response time meet specifications.
  • Access controls checked.
  • Defects resolved or formally dispositioned.
  • Final configuration, test evidence, and handover records saved.

The commissioning objective is not simply to make the HMI talk to the PLC. It is to prove that the information is correct, operator commands are handled predictably, faults are visible, and the system recovers in the intended state.
