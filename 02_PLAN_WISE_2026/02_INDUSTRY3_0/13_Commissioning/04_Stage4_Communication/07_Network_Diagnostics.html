1. Definition and Purpose

Industrial network diagnostics is the systematic process of identifying, isolating, verifying, and documenting faults that affect communication between PLCs, remote I/O, HMIs, SCADA systems, CNC machines, robots, drives, vision systems, barcode readers, printers, and other industrial devices.

The objective is not merely to establish that a device is connected. The objective is to prove that communication is stable, timely, correct, and suitable for the machine's control requirements.

For example, a robot may respond to a ping from an engineering PC while its PLC cyclic I/O connection remains faulted. A network can therefore appear operational to an IT technician while the production machine is stopped. Computers are very good at declaring success based on the wrong measurement.

Industrial network diagnostics answers these questions:

  • Is the physical communication path intact?
  • Are devices configured with compatible network parameters?
  • Can the endpoints establish the required communication sessions?
  • Is the industrial protocol exchanging valid cyclic or acyclic data?
  • Are data values fresh, correctly mapped, and updated within the required time?
  • Are packet loss, latency, jitter, congestion, or device faults affecting the process?
  • Does the fault originate in the network, device configuration, PLC program, machine sequence, or safety system?
  • Can the network recover correctly after a communication interruption?

2. Where Network Diagnostics Fits in Commissioning

Network diagnostics is part of Stage 4 communication commissioning. It verifies that the communication infrastructure established during installation and device integration is suitable for the following sequence and production tests.

Electrical and mechanical installation
                ↓
Physical network inspection
                ↓
IP addressing and device configuration
                ↓
Switch ports, links, and topology verification
                ↓
Industrial protocol and connection diagnostics
                ↓
PLC I/O and application data verification
                ↓
Timing, stability, and fault-recovery tests
                ↓
Communication acceptance and documentation
                ↓
Stage 5 sequence commissioning

Network commissioning should be completed before relying on automatic machine sequences. Otherwise, a communication fault may appear to be a sequence-programming defect, and troubleshooting turns into an expensive guessing contest.

3. The Network Diagnostic Layers

Troubleshoot from the lowest relevant layer upward. A higher-level failure may be caused by a lower-level fault, and changing PLC logic will not repair a damaged cable.

Layer or area What must be verified Typical faults
Physical Cable, connector, shielding, power, fiber, link LEDs Broken cable, loose connector, damaged fiber
Ethernet link Link speed, duplex, switch port, MAC learning CRC errors, port flapping, duplex mismatch
Network addressing IP address, subnet, VLAN, routing Duplicate IP, wrong subnet, incorrect VLAN
Transport TCP/UDP connectivity, ports, sessions Connection refused, timeout, blocked port
Industrial protocol PROFINET, EtherNet/IP, Modbus TCP, OPC UA Failed device connection, incompatible configuration
Application data Tag mapping, I/O status, data type, freshness Stale data, incorrect scaling, wrong byte order
Machine sequence Handshake, permissives, state transitions Missing ready bit, timeout, incorrect sequence logic

Not every protocol uses every layer in the same way. For example, PROFINET RT uses Ethernet-based real-time communication, while EtherNet/IP commonly uses CIP over TCP and UDP. Diagnostics must match the protocol and communication mode being used.

5. Ethernet Fundamentals for Troubleshooting

5.1 MAC address

A Media Access Control (MAC) address identifies a network interface at the Ethernet link layer.

Example format: 00:1A:2B:3C:4D:5E

Useful for:

  • Confirming which physical device is connected to a switch port.
  • Checking the switch's MAC address table.
  • Investigating unexpected device movement between ports.
  • Identifying duplicate or unexpected devices when supported evidence is available.

A MAC address is not the same as an IP address. The MAC address is used for local Ethernet delivery, while the IP address supports logical addressing.

5.2 IP address and subnet mask

An IP address identifies a device's logical network interface.

Example:

  • PLC: 192.168.10.10
  • Robot: 192.168.10.21
  • Subnet mask: 255.255.255.0

With this subnet mask, both devices are in the same IPv4 subnet, 192.168.10.0/24. They can normally communicate directly at Layer 2 if the ports and VLAN configuration permit it.

Common faults include:

  • Two devices configured with the same IP address.
  • Incorrect subnet mask.
  • A device configured for a different subnet.
  • A device retaining an old address after replacement.
  • An address assigned outside the approved plant range.

Duplicate IP symptoms may include intermittent connectivity, changing ARP entries, communication errors, or a device that becomes reachable only sometimes. Confirm the duplicate using approved switch, device, or network-management diagnostics rather than assuming that one failed ping proves the cause.

5.3 Default gateway

The default gateway is used when a device needs to communicate with an IP destination outside its local subnet.

Devices in the same subnet generally do not need a gateway for direct communication. A wrong gateway can therefore leave local communication working while communication to another routed subnet fails.

Do not add or modify gateways arbitrarily on isolated machine networks. Follow the approved addressing and segmentation design.

5.4 VLAN

A Virtual LAN (VLAN) separates Ethernet traffic into logical Layer 2 broadcast domains.

A PLC and robot can have apparently correct IP addresses yet fail to communicate if their switch ports are assigned to incompatible VLANs.

Check:

  • The intended VLAN for each endpoint.
  • Access-port versus trunk-port configuration.
  • Permitted VLANs on trunks.
  • Native VLAN configuration where applicable.
  • Whether routing between VLANs is required and authorized.

Do not change VLAN membership on a production switch without authorization and a rollback plan. A single wrong port setting can disconnect an entire cell.

5.5 Static addressing and DHCP

Industrial devices commonly use static addressing or an approved industrial device-addressing method.

Method Meaning Diagnostic risk
Static IP Address configured manually Incorrect manual entry or duplicate assignment
DHCP Address assigned by a DHCP server Address may change or lease may fail
DHCP reservation Server assigns a reserved address to a known client Incorrect reservation or client identity
Protocol-specific assignment Device identity and addressing managed by an industrial protocol or engineering tool Device name, identity, or assignment mismatch

Do not assume that all devices use DHCP. Some industrial devices use a configured IP address, some use protocol-specific device naming and assignment, and some support multiple methods.

5.6 ARP, DNS, and routing

  • ARP resolves an IPv4 address to a MAC address on the local network.
  • DNS resolves hostnames to IP addresses where hostname resolution is used.
  • Routing forwards traffic between IP networks.

Useful distinctions:

  • If a PLC communicates with a robot using a fixed IP address, DNS may be irrelevant to that communication.
  • If the IP address is correct but ARP resolution is inconsistent, investigate local Layer 2 reachability and duplicate addressing.
  • If devices communicate within a subnet but not across subnets, investigate routing, gateway configuration, ACLs, and firewall rules.
  • If hostname access fails but direct IP access works, investigate name resolution rather than assuming the Ethernet connection is broken.

6. Physical-Layer Diagnostics

Physical faults should be investigated before advanced protocol troubleshooting.

6.1 Inspection checklist

  • Verify that the correct cable type is installed.
  • Check connector seating, locking mechanisms, and strain relief.
  • Inspect for crushed cables, sharp bends, damaged insulation, and contamination.
  • Check industrial Ethernet connectors for damage and contamination.
  • Verify fiber type, connector cleanliness, polarity, and transceiver compatibility where fiber is used.
  • Confirm device power and network interface status.
  • Check link LEDs at both ends where available.
  • Inspect grounding and shield termination against the approved design.
  • Confirm that cables are routed and separated according to the plant's electrical-noise and installation requirements.
  • Verify that any cable repair or replacement uses an approved component and method.

Never disconnect a live production network cable merely to see what happens. That is not a diagnostic technique; it is an unplanned production interruption.

6.2 Link LEDs

LED meanings vary by manufacturer, so use the device or switch manual.

LED behavior Possible meaning Verification
No link indication No physical link or inactive interface Check power, cable, connector, port enablement
Link on, activity flashing Link established and traffic present Check protocol and application data if faults remain
Link repeatedly drops and returns Intermittent physical connection or port/device issue Check event logs, cable, connector, power, port counters
Link present but no expected data Higher-layer or configuration problem Check addressing, VLAN, protocol, and PLC diagnostics

A link LED confirms only limited information. It does not prove that cyclic I/O is healthy or that the application data is correct.

6.3 Cable testing

Use a suitable, approved cable tester or certification tool when required.

A basic wire-map test can detect open conductors, shorts, crossed pairs, and some wiring errors. Certification equipment can measure additional transmission characteristics.

For fiber, use appropriate optical inspection and testing equipment.

A cable tester cannot prove that the PLC's protocol configuration is correct, and a successful wire-map test does not prove that an installed link will meet every performance requirement.

7. Switch-Level Diagnostics

A managed industrial switch is a valuable diagnostic source because it provides information beyond basic link status.

7.1 Port status and counters

Check the following where supported:

  • Administrative state: enabled or disabled.
  • Operational state: up or down.
  • Negotiated speed and duplex.
  • Input and output packet counts.
  • CRC or FCS errors.
  • Alignment errors and malformed frames.
  • Dropped packets and output queue drops.
  • Interface resets and link-flap events.
  • Broadcast, multicast, and unknown-unicast traffic.
  • Port utilization and error-counter changes over time.

Counter interpretation matters. A high cumulative error count may be historical. Record the counter, observe the rate of change during a controlled period, and correlate it with the machine fault timestamp.

7.2 CRC/FCS errors

CRC/FCS errors indicate that received Ethernet frames failed their frame-integrity check.

Possible causes include:

  • Damaged cables or connectors.
  • Electrical interference or poor installation.
  • Faulty transceivers or interfaces.
  • Physical-layer incompatibility.
  • Less commonly, other hardware or link problems.

If errors rise continuously on one port, inspect the connected link and endpoints first. If errors appear across multiple ports, investigate shared infrastructure and common environmental causes.

Do not assume every CRC error is caused by electrical noise. Diagnose using the location, frequency, and correlation of errors.

7.3 Speed and duplex

Modern industrial Ethernet links commonly use auto-negotiation, but configuration requirements depend on the hardware.

A speed or duplex mismatch can cause poor performance, retransmissions, and frame errors. Check both ends of the link and follow the manufacturer's recommendations. Do not force speed or duplex on one side without confirming the required configuration at the other end.

7.4 Broadcast storms and excessive traffic

A broadcast storm or uncontrolled traffic increase can consume network resources and affect communication performance.

Possible clues include:

  • Unexpectedly high broadcast rates.
  • High switch utilization.
  • Packet drops.
  • Communication faults across multiple devices.
  • A sudden change after connecting a device or changing a network path.

Potential causes include Layer 2 loops, misconfigured devices, excessive discovery traffic, or faulty applications.

Use switch diagnostics and approved monitoring to identify the source. Do not disable random ports or introduce test traffic on a live OT network without an approved isolation plan.

7.5 Port mirroring

A managed switch may support port mirroring, which copies selected traffic to a monitoring port for packet capture.

Use it to inspect traffic without placing an ordinary laptop inline with the production connection. Confirm the switch's mirroring capabilities and expected monitoring-port load, because mirrored traffic can exceed the capacity of the destination port.

8. Industrial Protocol Diagnostics

A healthy Ethernet link does not guarantee that an industrial protocol is communicating correctly.

8.1 PROFINET

PROFINET is an industrial Ethernet technology commonly used for controller-to-device communication and real-time I/O.

Check:

  • The configured PROFINET device name.
  • IP address and subnet.
  • Controller configuration and expected device identity.
  • Device availability and diagnostic status.
  • Module and submodule configuration.
  • Input/output data consistency.
  • Update time and communication health.
  • Topology and port diagnostics where supported.
  • Device replacement and parameter-assignment procedures.

A device may have an IP address and still fail to establish the expected PROFINET application relationship because its name, identity, module configuration, or controller project is incorrect.

Use the PLC engineering software's device diagnostics and online hardware view to identify the exact failing component.

8.2 EtherNet/IP

EtherNet/IP uses the Common Industrial Protocol (CIP) over standard Ethernet and IP networks. It commonly uses TCP for explicit messaging and UDP for implicit I/O connections.

Check:

  • Correct device IP address and identity.
  • Electronic keying and device compatibility settings.
  • Controller I/O-tree configuration.
  • Assembly instances and data sizes where applicable.
  • Connection ownership and connection status.
  • Requested packet interval (RPI).
  • Connection timeout and device diagnostics.
  • Produced/consumed tag configuration where used.
  • Multicast, unicast, and switch behavior as applicable.

A successful ping does not prove that an EtherNet/IP I/O connection is established. A connection can fail because of an incorrect assembly configuration, incompatible device definition, connection-resource limits, or application configuration.

8.3 Modbus TCP

Modbus TCP commonly exchanges data using a client/server request-response model.

Check:

  • Correct device IP address.
  • TCP port, commonly 502 unless configured otherwise.
  • Server availability and connection limits.
  • Unit identifier where relevant to the gateway or device.
  • Register and coil addresses.
  • Function codes.
  • Register count and data types.
  • Byte and word order for multi-register values.
  • Response timeouts and exception responses.

Be careful with register numbering conventions. A documentation reference such as 40001 may map to protocol address zero in one implementation, while another tool may use a different notation. Confirm the exact addressing convention instead of shifting every address by one until something works.

8.4 OPC UA

OPC UA commonly provides structured, client/server industrial data access and can also support other communication models.

Check:

  • Server endpoint URL.
  • Network reachability and server service status.
  • Security policy and message security mode.
  • Certificates, trust lists, and certificate expiry.
  • User authentication and permissions.
  • Namespace and node identifiers.
  • Data type, status code, and source/server timestamps.
  • Subscription configuration and publishing behavior.

A reachable OPC UA server may still reject a client because of certificate trust, authentication, endpoint mismatch, or security-policy configuration.

Do not solve certificate problems by indiscriminately disabling security. Correct the trust and configuration problem.

8.5 TCP and UDP

Characteristic TCP UDP
Connection model Connection-oriented Connectionless
Delivery handling Acknowledgment and retransmission mechanisms No inherent delivery acknowledgment
Typical industrial use Explicit requests, configuration, sessions Time-sensitive cyclic I/O or datagrams in supported protocols
Diagnostic focus Connection establishment, resets, retransmissions, timeouts Packet rate, loss, timing, destination, protocol-specific health

These are transport-layer characteristics, not guarantees about the entire application. Industrial protocols add their own connection management, sequence handling, timeout behavior, and data-validity rules.

8.6 Serial and fieldbus connections

Not every communication fault is Ethernet-based. A cell may also use RS-232, RS-485, Modbus RTU, PROFIBUS, CAN-based networks, or vendor-specific fieldbus links.

Check the interface type, cable and termination requirements, baud rate, parity, stop bits, node address, bus topology, grounding, and device diagnostics as applicable. A serial gateway can introduce an additional failure point between the PLC and the final device.

9. PLC-Level Communication Diagnostics

The PLC is often the best starting point for determining whether a communication failure affects the control system.

9.1 What to check online

  • Controller diagnostic buffer or fault log.
  • Hardware configuration and device status.
  • Remote I/O adapter or head-station status.
  • Module fault and channel diagnostic information.
  • Connection status for robots, CNCs, drives, and other controllers.
  • Communication watchdog and timeout faults.
  • Input and output data validity.
  • Task execution and scan-time trends.
  • Network-related diagnostics available in the PLC platform.
  • Device configuration differences between the approved project and the installed hardware.

Use the correct engineering software and the actual controller model. Siemens TIA Portal, Rockwell Studio 5000, and Mitsubishi GX Works provide different diagnostic views and terminology.

9.2 Validity versus value

A displayed value is not necessarily a current, valid value.

For example, a robot's READY tag may remain 1 in a supervisory display after the underlying communication has failed, if the display retains the last received value. Another system may force the value to a default or mark the data invalid.

Evaluate at least these properties:

  • Value: What is the bit, word, or tag currently showing?
  • Validity: Is the source or communication channel reporting valid data?
  • Freshness: Has the value updated within the permitted age?
  • Timestamp: When was the value sampled or received, if timestamps are available?
  • State: Does the value make sense in the current machine state?

Do not treat stale data as proof that a device is healthy.

9.3 Watchdogs and timeouts

A watchdog or timeout detects a missing expected event, update, or response within a configured interval.

The exact meaning depends on the device and protocol. A communication watchdog may indicate a failed connection, while an application watchdog may indicate that expected data or a heartbeat has stopped changing.

When a timeout occurs, establish:

  1. Which connection or event timed out?
  2. Which device recorded the fault?
  3. What was the configured timeout?
  4. Did the physical link fail, or did only the application exchange stop?
  5. Did the fault occur once or repeatedly?
  6. Did the system recover automatically?
  7. Was data validity handled safely during the interruption?

Do not increase timeout values just to suppress alarms. First determine whether the timeout is correctly configured and whether the underlying delay is acceptable.

10. Diagnostic Tools and Commands

Use only approved tools and methods on the relevant OT network.

10.1 Windows command-line tools

Check the local IP configuration:

ipconfig /all

Useful for checking the engineering PC's IP address, subnet mask, gateway, DNS settings, and interface configuration.

Check basic IP reachability:

ping 192.168.10.21

This sends ICMP echo requests. A reply indicates that the endpoint responded to ICMP at that time. A failed reply does not necessarily prove the endpoint is offline, because ICMP may be blocked or deprioritized.

Inspect the local ARP cache:

arp -a

Useful for inspecting cached IPv4-to-MAC mappings. It is not a complete device inventory and does not guarantee that each entry is current.

Inspect the route table:

route print

Useful when the engineering PC has multiple network interfaces or routes that may send traffic through an unexpected interface.

Trace the IP route where permitted:

tracert 192.168.20.21

This can help investigate routed paths, but intermediate devices may not respond to traceroute probes. It is less useful on a flat Layer 2 machine network.

Inspect TCP connections on a permitted engineering PC:

netstat -ano

This shows local connection information, including TCP states and process identifiers where available. It does not by itself explain the health of every industrial protocol.

10.2 Interpreting ping results

Result What it establishes What it does not establish
Replies received The endpoint responded to ICMP probes Correct industrial protocol or valid PLC I/O
No replies No ICMP reply was received That the device is definitely powered off
Intermittent replies ICMP reachability is inconsistent The exact cause of the inconsistency
Low average response time ICMP responses were relatively quick Deterministic cyclic I/O timing
Replies from an unexpected address Traffic may be reaching an unexpected endpoint The exact cause without further investigation

Do not use ping frequency as a substitute for industrial protocol diagnostics. Some control networks use real-time communication behavior that ordinary ICMP tests cannot measure.

10.3 Wireshark packet capture

Wireshark can capture and decode network traffic when used on an approved monitoring interface or a correctly configured switch mirror port.

Typical diagnostic uses:

  • Confirming whether requests and responses are present.
  • Identifying TCP connection attempts, resets, and retransmissions.
  • Inspecting protocol-specific messages when supported.
  • Reviewing timing between packets.
  • Identifying unexpected traffic or communication bursts.
  • Correlating packet activity with PLC or switch diagnostic timestamps.

A safe workflow is:

  1. Obtain permission and identify the exact network and endpoints.
  2. Define the fault, capture location, and short capture window.
  3. Configure an approved mirror port or use an authorized capture method.
  4. Start the capture before the controlled test or observed fault.
  5. Record the machine state and exact fault time.
  6. Stop the capture and save the file securely.
  7. Filter and inspect only the relevant traffic.
  8. Correlate observations with PLC, device, and switch logs.
  9. Store or dispose of capture files according to plant policy.

Packet captures can contain production data, device identifiers, and sometimes sensitive information. Protect them accordingly.

Do not inject packets, run aggressive discovery scans, flood the network, or perform unapproved active tests on production OT equipment.

11. Network Performance: Latency, Jitter, Loss, and Update Time

Network performance must be judged against the actual application's requirements.

  • Latency: Time taken for traffic to travel between endpoints or for an exchange to complete, depending on the measurement method.
  • Jitter: Variation in packet delay or update timing.
  • Packet loss: Traffic that fails to reach its destination or is otherwise lost from the observed exchange.
  • Throughput: Amount of data transferred per unit of time.
  • Update time: Configured or observed interval at which data is updated.
  • Connection timeout: Maximum allowed delay before a communication exchange is considered unsuccessful.
  • Recovery time: Time required for the system to restore the required communication behavior after a fault.

11.1 Why average latency is insufficient

A low average does not reveal occasional large delays. For example, an average response time of 2 ms could coexist with rare delays of 100 ms. Those rare delays may matter to an application with a tight timing requirement.

Measure relevant percentiles, maximum observed delay, error rates, and fault frequency where the available tools support reliable measurements.

11.2 Update intervals and network load

For a cyclic I/O connection, the update interval and timeout requirements must align with:

  • The control task's timing requirements.
  • The device's supported connection parameters.
  • The protocol's communication behavior.
  • The number of connected devices.
  • Switch capacity and traffic load.
  • The machine's response requirements.

A shorter update interval can increase network traffic and controller/device load. It should not be reduced blindly to make a display look more responsive.

11.3 Acceptance limits

There is no universal acceptable latency, jitter, packet-loss rate, or recovery time for every industrial network.

Use the following priority:

  1. Safety and machine risk assessment requirements.
  2. Equipment and protocol manufacturer specifications.
  3. Approved network design and control-system specifications.
  4. Project FAT/SAT acceptance criteria.
  5. A documented, measured baseline where the preceding documents do not define a value.

Do not invent a numerical acceptance limit when the actual system requirement is unknown.

12. Structured Troubleshooting Method

The goal is to isolate the fault without changing unrelated parts of a working system.

Step 1: Define the symptom

Record:

  • Which machine or device is affected.
  • Exact fault text or diagnostic code.
  • Time of occurrence.
  • Whether the fault is permanent or intermittent.
  • Whether one device, one branch, or the entire cell is affected.
  • Whether production, manual operation, or startup triggers the fault.
  • Recent changes to hardware, software, wiring, addressing, or network configuration.

Step 2: Check the physical path

Inspect device power, link LEDs, cables, connectors, and relevant switch-port status. Review link-flap and port-error counters.

Step 3: Check addressing and topology

Compare actual device settings against the approved network drawing and configuration records. Verify IP address, subnet, VLAN, route, device name, and physical switch-port assignment as applicable.

Step 4: Check protocol-specific diagnostics

Use the relevant PLC engineering software, device diagnostics, and switch tools. Verify the required communication relationship, connection state, data sizes, update parameters, and protocol configuration.

Step 5: Check application data

Compare source-device values with PLC tags and HMI/SCADA values. Check data types, word order, scaling, timestamps, validity, and handshake transitions.

Step 6: Check timing and event correlation

Correlate PLC logs, device fault history, switch counters, and packet capture data using synchronized or otherwise reconciled timestamps.

Step 7: Make one controlled change

Use a specific hypothesis and a reversible change. Record the original configuration and obtain the required authorization before changing production settings.

Step 8: Verify recovery

Confirm that communication is stable, values are valid and fresh, the expected machine behavior is restored, and the original fault no longer occurs under the defined test conditions.

Step 9: Document the result

Record the root cause, evidence, correction, validation result, configuration change, and any preventive action.

13. Common Faults and Diagnostic Approach

Symptom Likely causes First diagnostic action
Device has no link Power, cable, connector, disabled port Check device power, LEDs, and switch-port state
Device responds to ping but PLC reports a fault Protocol configuration, connection failure, I/O mapping Inspect PLC connection and device diagnostics
Intermittent communication Loose cable, port flaps, duplicate IP, congestion, device reboot Correlate timestamps with switch counters and device logs
One device fails after replacement Wrong IP, device name, identity, or configuration Compare replacement configuration with the approved record
All devices on one branch fail Shared switch, uplink, power, VLAN, or upstream link Inspect the common infrastructure point
PLC inputs remain unchanged Failed I/O connection, frozen source, stale data, program logic Compare device status, raw input data, and data freshness
Modbus values are incorrect Register offset, function code, data type, byte/word order Verify register map and compare with the device's documented representation
OPC UA client cannot connect Endpoint, certificate, authentication, security policy Check server diagnostics and client trust configuration
Network fault appears during startup Power sequencing, device startup timing, connection establishment Compare startup sequence with device and controller logs
Errors increase on one switch port Cable, connector, interface, physical interference Record counter changes and inspect the affected link
Communication fails across subnets Routing, gateway, VLAN, ACL or firewall Verify the approved network path and rules
Recovery does not occur automatically Fault latch, reconnect policy, device state, PLC recovery logic Check the defined recovery behavior and reset conditions

These are diagnostic hypotheses, not proof. Confirm the cause using evidence before changing equipment or code.

14. Communication Fault Handling and Recovery

A robust industrial system must handle communication loss deliberately. It must not depend on the operator guessing what to reset.

14.1 Define the fault response

For each important connection, specify:

  • What constitutes a communication fault.
  • How the fault is detected.
  • Whether the fault is immediate or requires a timeout.
  • Which data becomes invalid when communication is lost.
  • What happens to automatic sequencing.
  • What outputs or motion commands are inhibited.
  • What the operator sees on the HMI.
  • Whether reconnection is automatic or requires a deliberate reset.
  • Which conditions must be revalidated before operation resumes.
  • How the fault is logged and acknowledged.

The correct response depends on the device and risk assessment. A robot communication failure, a vision-result timeout, and a safety-device fault must not automatically receive identical recovery logic.

14.2 Example: Robot communication loss

Assume a PLC exchanges status and command data with a robot controller over EtherNet/IP.

PLC exchanges robot I/O
          ↓
Connection status becomes unhealthy
          ↓
PLC identifies communication fault
          ↓
Automatic sequence is inhibited
          ↓
Commands and status are treated as invalid
          ↓
HMI displays fault and diagnostic context
          ↓
Communication is restored
          ↓
Robot status and required permissives are revalidated
          ↓
Defined reset/restart procedure is followed

The exact response must follow the approved machine design. Do not assume that reconnecting Ethernet makes the robot safe to restart or proves that the robot's physical state matches the PLC's expected state.

Important: Ordinary PLC communication is not a substitute for a certified safety function. Safety-related communication, safe torque off, emergency stop, guard monitoring, and other safety functions must be designed and validated according to the applicable safety architecture and standards.

15. Network Diagnostics During Commissioning

15.1 Before energization or network startup

  • Approved network architecture and IP-address plan are available.
  • Device inventory and communication matrix are complete.
  • Switch and device models match the design.
  • Network cables and connectors are inspected.
  • Fiber connections and transceivers are compatible where applicable.
  • Power supplies and network equipment are correctly installed.
  • Shielding, grounding, and cable routing follow the approved design.
  • VLANs, redundancy, and switch configurations are reviewed.
  • The approved PLC and device configuration backups are available.
  • Changes to shared plant infrastructure are authorized.

15.2 During network startup

  • Expected switch ports establish links.
  • Actual device identities match the inventory.
  • IP addresses and protocol-specific device names are correct.
  • Duplicate-address indications are investigated.
  • PLC online diagnostics show expected device and connection states.
  • Required communication sessions are established.
  • Input/output data types and sizes match the approved mapping.
  • Data changes correctly when the source device changes.
  • Data validity and timeout behavior are verified.
  • No unexplained link flapping or rapidly increasing error counters are present.

15.3 During functional testing

  • Commands and feedback signals are verified in both directions.
  • Required handshakes complete within approved timing limits.
  • Communication faults are displayed and logged correctly.
  • Stale or invalid data cannot be mistaken for current healthy data.
  • Defined communication-loss behavior is verified.
  • Recovery follows the approved procedure.
  • The network remains stable during representative machine operation.
  • No unapproved network load or disruptive diagnostic activity is introduced.

15.4 During FAT and SAT

Factory Acceptance Testing (FAT) verifies the network configuration and communication behavior under the agreed factory test conditions.

Site Acceptance Testing (SAT) verifies that the installed network and integrated machine work correctly under actual site conditions.

Test area FAT focus SAT focus
Device configuration Approved configuration and compatibility Installed devices match the approved configuration
Addressing IP plan and device identity Actual site addressing and routing
Physical network Representative wiring and switch setup Installed cables, connectors, and environmental conditions
Communication Protocol connection and data mapping End-to-end communication in the actual cell
Timing Defined test conditions and expected update behavior Actual network load and machine operating conditions
Fault response Simulated or controlled fault behavior Approved site test of fault detection and recovery
Documentation Configuration and test records As-built drawings, final settings, and site sign-off

Fault-injection tests must be planned, authorized, and risk-assessed. Do not interrupt production networks or disconnect live control links without an approved test method and safe operating condition.

16. Acceptance Criteria

A network should not be accepted merely because all devices show green status icons.

Acceptance should demonstrate that:

  1. All required devices are correctly identified and configured.
  2. The physical network matches the approved topology.
  3. Required protocol connections establish successfully.
  4. PLC input and output data are correctly mapped and validated.
  5. Data updates within the specified application timing requirements.
  6. No unexplained communication faults occur during the defined test period.
  7. Switch and device diagnostics show no unresolved errors that violate the project requirements.
  8. Communication loss produces the documented machine response.
  9. Recovery works according to the approved restart and reset procedure.
  10. Required safety functions remain independent, effective, and validated according to the approved safety design.
  11. Configuration backups, network drawings, test records, and fault logs are retained.
  12. Deviations are documented, assigned, and resolved or formally accepted.

Where the project specifies numerical limits for response time, jitter, packet errors, or recovery time, test against those limits. If limits are not defined, obtain engineering approval rather than inventing an acceptance threshold.

17. Practical Factory Example: Intermittent Robot Communication

Scenario

A robotic welding cell occasionally stops because the PLC reports a communication fault with Robot 02. The robot controller is powered, and the engineering PC can usually ping it.

Investigation

Observation 1: The fault is intermittent.

The problem is not a permanent configuration failure. Record the exact fault times and check whether the problem correlates with robot startup, welding operation, or other machine events.

Observation 2: The PLC reports a connection fault.

The ping test alone is insufficient. Inspect the PLC's EtherNet/IP connection status, controller diagnostics, and robot communication diagnostics.

Observation 3: The switch shows increasing errors on the robot's port.

Record the error-counter values, monitor their rate of change, and compare the timestamps with the PLC faults. A rising error count supports investigating the physical link, but the counter alone does not identify the exact failed component.

Observation 4: The approved test identifies an intermittent cable fault.

With the cell placed in the required safe condition and the work authorized, the cable is inspected and tested. An approved replacement cable is installed.

Observation 5: The network is retested.

The team confirms:

  • The switch link remains stable.
  • The relevant error counters no longer increase abnormally during the test.
  • The PLC connection remains healthy.
  • Robot I/O data updates correctly.
  • The machine completes representative operating cycles.
  • The communication-loss and recovery behavior remain consistent with the approved design.

Root-cause record

Field Example entry
Fault Intermittent robot communication
Confirmed cause Intermittent Ethernet cable fault
Evidence Correlated PLC faults, switch-port diagnostics, cable test
Corrective action Approved cable replacement
Verification Stable link, healthy connection, valid I/O, successful functional test
Preventive action Inspect cable routing and strain relief; update maintenance records

This example illustrates the diagnostic method. In an actual breakdown, record only the cause established by the evidence.

19. Common Mistakes

  • Treating a successful ping as proof that PLC I/O communication is healthy.
  • Changing IP addresses before confirming the addressing plan.
  • Ignoring switch-port counters because the link LED is on.
  • Replacing a PLC or robot controller before checking the cable, switch, and configuration.
  • Increasing communication timeouts to hide an unresolved network problem.
  • Ignoring device identity, module configuration, assembly instances, or register maps.
  • Treating stale HMI values as current feedback.
  • Using unapproved active scans or traffic-generation tools on production networks.
  • Changing VLANs, switch ports, or routing without authorization and a rollback plan.
  • Disabling security controls to bypass a connection problem.
  • Assuming every communication fault is caused by the network rather than device configuration or application logic.
  • Closing a breakdown without recording evidence, corrective action, and verification results.

20. Interview Questions and Answers

Q1. What is industrial network diagnostics?

It is the systematic verification and troubleshooting of physical connectivity, addressing, network infrastructure, industrial protocols, application data, timing, and communication-fault behavior.

Q2. A device responds to ping, but the PLC reports a communication fault. Why?

Ping verifies ICMP reachability, not the health of the required industrial communication relationship. The protocol connection, device configuration, data assembly, connection parameters, or PLC configuration may still be incorrect.

Q3. What is the difference between latency and jitter?

Latency is a delay measurement for a defined communication event. Jitter is variation in that delay or in packet/update timing.

Q4. What do CRC errors indicate?

They indicate frames that failed an Ethernet frame-integrity check. Cable, connector, interface, transceiver, and physical-link problems are possible causes.

Q5. What is a duplicate IP address?

It occurs when more than one device uses the same IP address within the relevant network. It can cause inconsistent reachability and incorrect address-to-device resolution.

Q6. What is the difference between a MAC address and an IP address?

A MAC address supports Ethernet link-layer delivery. An IP address provides logical addressing at the network layer.

Q7. Why might a replacement PROFINET device fail to connect?

Possible causes include an incorrect device name, incorrect IP settings, mismatched device identity, incorrect module configuration, or controller configuration differences.

Q8. Why might EtherNet/IP I/O fail even when TCP communication appears available?

EtherNet/IP commonly uses TCP for explicit messaging and UDP for implicit I/O. A successful TCP connection or ping does not prove that the required cyclic I/O connection is correctly established.

Q9. What is the purpose of switch-port mirroring?

It copies selected network traffic to a monitoring port for analysis, enabling packet capture without placing an ordinary capture device inline with the production connection.

Q10. Why should communication timeouts not be increased blindly?

A larger timeout may delay fault detection without fixing the cause. The existing timeout may be correct, and the real issue may be packet loss, device failure, incorrect configuration, or excessive delay.

Q11. What is the difference between a network fault and an application fault?

A network fault affects the communication path or exchange. An application fault can occur even when communication is healthy, such as incorrect tag mapping, invalid scaling, an unchanging source value, or a missing handshake transition.

Q12. How do you prove that a communication repair is successful?

Verify the original symptom is resolved, the relevant connection and data are healthy, the network remains stable under defined test conditions, fault recovery behaves correctly, and the results are documented.

Q13. What is a network baseline?

It is a record of normal network conditions, such as device status, port counters, expected traffic, communication timing, and known operating behavior. It provides a comparison point for future troubleshooting.

Q14. Why is an industrial network different from an ordinary office network?

Industrial networks must support specific control timing, deterministic or bounded communication behavior where required, device compatibility, availability, and safe machine responses. General network reachability alone is insufficient.

Q15. What should be checked first when several devices fail simultaneously?

Investigate common dependencies such as shared switch power, uplinks, VLAN configuration, network segmentation, and shared infrastructure before changing the configuration of each endpoint individually.

21. Final Checklist

  • Network topology and device inventory are available.
  • IP addresses, subnet masks, VLANs, and device identities match approved records.
  • Cables, connectors, power, and link status are verified.
  • Switch-port counters and event logs have been checked.
  • No unresolved duplicate-address or topology issues remain.
  • PLC and device diagnostics show healthy required connections.
  • Protocol configuration and I/O mappings are correct.
  • Data is valid, fresh, and correctly interpreted.
  • Timing and stability meet the approved requirements.
  • Communication-loss and recovery behavior have been tested appropriately.
  • Safety-related behavior has been validated through its approved design and test process.
  • FAT/SAT results and deviations are recorded.
  • Approved configurations, backups, and as-built records are retained.

Core principle: Diagnose from evidence, isolate the failing layer, change only what the evidence justifies, and verify the entire communication path after correction. Network diagnostics is complete when the required industrial communication works reliably and its failure behavior is understood, not merely when the network icon turns green.
