1. Definition

PLC-CNC communication commissioning is the process of verifying, configuring, testing, and validating the exchange of signals and data between a Programmable Logic Controller (PLC) and a Computer Numerical Control (CNC) system so that the machine operates in the correct sequence, under valid interlocks, and with predictable fault handling.

The PLC and CNC have different responsibilities. The CNC primarily executes machining programs and controls axes and spindle motion, while the PLC manages machine sequencing, auxiliary equipment, and interlocks. The exact division depends on the machine builder, CNC platform, and machine software architecture.

The objective is not merely to establish communication. It is to prove that both controllers interpret commands and status information correctly, including during faults, interruptions, resets, and recovery.

2. Scope and Objectives

PLC-CNC commissioning typically covers:

  • Physical interface wiring and communication-network configuration.
  • Signal and data mapping between PLC and CNC.
  • CNC ready, alarm, cycle start, cycle active, cycle complete, and reset signals.
  • Operating-mode, program-selection, and machining-permission interlocks.
  • Coordination of doors, chucks, fixtures, tool changers, coolant, lubrication, and chip conveyors.
  • Alarm exchange, diagnostics, communication-loss detection, and recovery.
  • Functional testing, cycle-time verification, and FAT/SAT acceptance.

The commissioning scope must identify whether the interface uses hardwired I/O, fieldbus communication, a CNC-specific data interface, or a combination of these methods.

3. PLC and CNC Responsibilities

Function PLC responsibility CNC responsibility
Machine sequence Coordinates machine-level sequence Executes the machining sequence assigned to the CNC
Axis motion Requests or permits motion through the defined interface Controls CNC axes and interpolated motion
Spindle Coordinates machine-level spindle permissives and auxiliary functions Executes spindle commands and relevant CNC functions
Cycle start Issues a valid start request after checking interlocks Accepts the request when its internal conditions permit
Cycle status Monitors and coordinates machine state Reports program execution and CNC state
Tool change Coordinates the machine-side tool-change mechanism Coordinates tool-change requests and tool data according to the configuration
Door and chuck Controls or monitors machine-side devices May require valid door, clamping, or fixture status before machining
Alarms Handles machine-level faults and displays or forwards relevant information Reports CNC alarms and motion or program faults
Emergency stop Participates in the machine safety architecture where assigned Responds through its defined safety interface and configuration
Recovery Coordinates safe machine-level recovery Restores CNC operation according to CNC state and recovery rules

A machine builder may implement some of these functions inside the CNC's integrated PLC rather than an external PLC. Always establish which controller owns each function before changing logic.

4. Typical PLC-CNC Architecture

A common machine architecture is:

Operator Panel / HMI
         ↓
External Machine PLC
         ↓
Machine Interface
         ↓
CNC Controller
         ↓
Axis Drives and Spindle Drive
         ↓
Motors and Machine Motion

External Machine PLC
         ↓
Sensors, Valves, Contactors, Pumps, Fixtures,
Doors, Tool Changer and Other Auxiliary Devices

The machine interface may consist of discrete I/O, a fieldbus, a manufacturer-specific communication interface, or multiple interfaces working together.

For example, the PLC might send a cycle-start request through discrete I/O while obtaining detailed CNC status and alarm information through an Ethernet-based interface.

4.1 Common interface methods

Interface method Typical application Commissioning concern
Hardwired digital I/O Ready, start request, cycle active, alarm, reset Wiring, polarity, voltage, common reference, and signal timing
PROFINET Cyclic exchange between compatible controllers and devices Device name, IP configuration, device identity, I/O mapping, and network diagnostics
EtherNet/IP Cyclic I/O exchange between compatible industrial devices Device configuration, connection parameters, assembly mapping, and connection status
PROFIBUS DP Cyclic fieldbus I/O on supported equipment Node address, baud rate, bus termination, and diagnostics
CC-Link Cyclic communication on supported platforms Network parameters, station configuration, and data mapping
Manufacturer-specific CNC interface CNC status, commands, program data, and diagnostics Supported API, options, access permissions, data definitions, and controller compatibility

Not every CNC supports every protocol natively. A communication module, gateway, licensed option, or machine-builder-specific interface may be required.

5. Identify the Actual Machine Interface

Before commissioning, collect the following information:

  • CNC manufacturer, model, software version, and installed options.
  • External PLC manufacturer, CPU model, firmware, and project version.
  • Machine-builder electrical drawings and I/O lists.
  • CNC interface documentation and signal definitions.
  • Network topology, IP addresses, device names, and protocol configuration.
  • CNC parameter backup and PLC program backup.
  • Machine operating sequence and interface timing requirements.
  • Safety architecture and the approved risk assessment.
  • Existing fault history and machine recovery procedure.

Common CNC platforms include Siemens SINUMERIK, FANUC CNC, Mitsubishi CNC, and other manufacturer-specific systems. Their interface signals, PLC integration methods, diagnostic screens, and configuration procedures differ.

Important: Do not assume that a signal named CNC_READY, CYCLE_START, or MACHINE_ALARM has identical meaning across machine builders. Confirm the exact meaning, active state, reset conditions, and timing from the approved interface documentation.

6. Communication Commissioning: Physical Layer

6.1 Hardwired interfaces

For a discrete interface, verify:

  1. The CNC output is wired to the intended PLC input.
  2. The PLC output is wired to the intended CNC input.
  3. The signal voltage and electrical characteristics are compatible.
  4. The common reference, polarity, and isolation arrangement are correct.
  5. The input and output addresses match the electrical drawings and PLC configuration.
  6. The input filter and signal-processing delay are appropriate.
  7. No unintended cross-connection, short circuit, or forced signal exists.

For a typical 24 V DC digital interface, check the actual voltage at the receiving terminal rather than relying solely on an indicator LED.

A PLC input showing TRUE proves that the input channel is active. It does not prove that the receiving CNC interprets that signal as the intended command.

6.2 Ethernet and fieldbus interfaces

For a network interface, verify:

  • Correct physical ports, cables, switches, and link status.
  • Unique and correct IP addresses where applicable.
  • Correct subnet configuration.
  • Correct device name and device identity where the protocol requires them.
  • Matching PLC hardware configuration and actual device configuration.
  • Correct cyclic input/output data lengths and mapping.
  • No duplicate IP addresses or unexpected network routes.
  • Healthy communication diagnostics and acceptable update performance.
  • Correct device startup behavior after a power cycle.

Basic checks may include:

1. Verify physical link.
2. Verify device identity and network parameters.
3. Verify communication connection status.
4. Monitor raw input and output data.
5. Confirm each mapped bit and data field.
6. Test valid command and status transitions.
7. Test communication interruption under an approved test procedure.

A successful ping does not prove that the industrial communication connection is healthy. ICMP reachability and cyclic control-data exchange are different things, because networking apparently needed another opportunity to be misunderstood.

7. Signal Mapping and Data Validation

Signal mapping connects a documented machine-interface function to its actual electrical address, PLC variable, CNC variable, or communication-data location.

A signal map should include the signal name, source, destination, data type, active state, purpose, operating conditions, reset behavior, and verification method.

Signal Typical direction Meaning
CNC ready CNC to PLC CNC reports readiness according to the interface definition
CNC alarm active CNC to PLC One or more CNC alarm conditions are present
Cycle start request PLC to CNC PLC requests program execution
Cycle active CNC to PLC CNC reports that the machining cycle is active
Cycle complete CNC to PLC CNC reports the defined completion condition
CNC reset request PLC to CNC Requests reset through the approved interface
Feed hold request PLC to CNC Requests a controlled feed hold, if supported
Program number or selection data PLC to CNC Identifies a program or selection value when supported
Door closed Machine sensor or safety system to PLC/CNC Reports a door state; its use depends on the safety architecture
Chuck clamped Machine sensor to PLC/CNC Reports the defined clamping state
CNC fault code CNC to PLC or diagnostic system Provides diagnostic information when supported

The direction shown is typical, not universal. The actual interface specification takes precedence.

7.1 Verify every mapped signal

For each signal:

  1. Record its expected normal state.
  2. Observe the raw electrical or communication value.
  3. Observe the PLC variable.
  4. Observe the corresponding CNC indication or diagnostic value.
  5. Change the source condition using an approved test.
  6. Verify that the intended destination changes.
  7. Confirm that unrelated signals remain unaffected.
  8. Restore the original condition and verify normal operation.

This checks the entire path instead of trusting one screen and hoping the rest of the system shares its interpretation.

7.2 Data types and byte mapping

For cyclic communication, check:

  • Boolean bit positions.
  • Byte offsets and word offsets.
  • Signed versus unsigned integer interpretation.
  • Integer scaling and engineering units.
  • Floating-point representation.
  • Byte ordering where relevant.
  • String length and character encoding if strings are exchanged.
  • Valid ranges, reserved values, and timeout behavior.

A value displayed as 256 by one controller and 1 by another may indicate incorrect byte or word mapping. A value that changes correctly but has the wrong meaning can be more dangerous than a complete communication failure because it may look valid during a quick inspection.

8. CNC State and Handshake Design

A handshake is a defined exchange of requests, acknowledgements, and status signals between the PLC and CNC. Its purpose is to prevent commands from being missed, repeated unexpectedly, or executed in the wrong sequence.

8.1 Typical operating states

A machine interface may distinguish the following states:

  • Not ready: CNC startup, an active fault, an unavailable mode, or another readiness condition prevents operation.
  • Ready: CNC reports readiness under the agreed interface definition.
  • Cycle requested: PLC has issued a start request.
  • Cycle active: CNC confirms program execution.
  • Cycle complete: CNC reports completion according to the interface contract.
  • Faulted: A CNC or machine condition requires fault handling.
  • Recovery: The system is restoring an approved state after an interruption.

These states are not interchangeable. In particular, READY does not necessarily mean that every machine-level permissive is satisfied, and CYCLE COMPLETE does not necessarily mean that unloading can safely begin.

8.2 Example cycle-start handshake

The following is a generic conceptual sequence. Actual edge-triggering, acknowledgement, and reset rules must follow the CNC and machine-builder interface specification.

PLC confirms machine permissives
         ↓
PLC verifies CNC ready and correct operating mode
         ↓
PLC issues cycle-start request
         ↓
CNC accepts the request
         ↓
CNC reports cycle active
         ↓
PLC monitors cycle and machine conditions
         ↓
CNC reports cycle complete
         ↓
PLC verifies completion and required safe conditions
         ↓
PLC starts the next machine sequence

8.3 Handshake rules

A reliable handshake should define:

  • Which controller owns each request.
  • Whether the request is a pulse, a maintained level, or a rising-edge command.
  • The required acknowledgement.
  • The timeout for receiving that acknowledgement.
  • How long a request remains active.
  • When the request must be removed.
  • What happens if the acknowledgement never arrives.
  • What happens if a signal is already active when the sequence begins.
  • How a restart is prevented after a power interruption.
  • How an interrupted cycle is recovered without duplicating an operation.

Do not use an arbitrary pulse width. Determine the required duration from the controller interface specification, scan behavior, communication update interval, and any input filtering.

8.4 Timeout handling

A PLC should supervise expected state transitions.

For example:

IF Start_Request = TRUE
AND CNC_Cycle_Active does not arrive before the configured timeout
THEN
    Cancel or inhibit the start request according to the interface design
    Set a diagnostic fault
    Prevent automatic repeated starts
    Require the defined recovery procedure
END_IF

This is illustrative logic, not a complete PLC program. The timeout must be justified by the machine's documented sequence and normal operating time. An arbitrary timeout can create nuisance trips or conceal a genuine fault.

9. Operating Modes and Program Selection

A CNC may support automatic, manual, jog, reference-return, setup, and other operating modes. Availability and naming depend on the controller.

The PLC must distinguish a valid automatic production condition from a setup or maintenance condition where automatic cycle initiation is not permitted.

Typical checks include:

  • Correct CNC operating mode.
  • Correct program selected and loaded.
  • Program selection acknowledged, where supported.
  • No active alarm preventing execution.
  • CNC and required axes in the appropriate state.
  • Required reference-return or homing conditions satisfied.
  • Door, fixture, chuck, and other required machine conditions satisfied.
  • No conflicting manual command or active sequence.
  • No safety-system condition prohibiting the requested operation.

Program-selection interfaces vary considerably. A CNC may use a program number, a dedicated data interface, an external request, or a machine-builder-defined sequence. Verify whether program selection means requested, loaded, selected, or currently executing. Those are different states.

Do not assume that a cycle-start signal automatically selects the correct program.

10. CNC Functions and M-Codes

G-codes generally define machining or motion commands, while M-codes generally invoke auxiliary or machine-specific functions. The exact implementation depends on the CNC configuration and machine builder.

Examples of auxiliary functions include:

  • Spindle start and stop.
  • Coolant control.
  • Tool-change requests.
  • Chuck or fixture operations.
  • Door or pallet functions.
  • Chip conveyor control.

The PLC may execute some M-code-related machine functions, while the CNC controls the machining program and its execution sequence. Some functions use an acknowledgement or completion signal before the CNC continues.

10.1 M-code commissioning checks

  1. Identify the M-code and its documented machine-builder function.
  2. Verify which controller processes the request.
  3. Confirm the mapped request and acknowledgement signals.
  4. Verify the physical output and feedback sensor, if applicable.
  5. Confirm that the CNC waits for the required completion condition.
  6. Test timeout and fault behavior.
  7. Verify that reset or recovery does not cause an unintended repeated action.

Never infer an M-code's meaning from its number alone. The same M-code can have different machine-specific behavior across CNC platforms and machine builders.

11. Coordination With Machine Auxiliaries

PLC-CNC communication is only one part of the machine sequence. The PLC must coordinate CNC requests with the actual state of machine auxiliaries.

Equipment Typical permissive or feedback Commissioning concern
Machine door Closed and locked state, where applicable Confirm the required interlock and safety function
Chuck Clamped/unclamped feedback Verify sensor state, command sequence, and workpiece retention requirements
Fixture Located, clamped, or pressure-valid feedback Prevent machining without the required workholding state
Tool changer Ready, tool-change complete, or fault state Verify position feedback and correct completion acknowledgement
Coolant Pump status or flow/pressure feedback, if required Prevent continuation where process requirements demand coolant
Lubrication Pressure or system-ready feedback, if required Protect equipment and enforce manufacturer requirements
Chip conveyor Running or fault feedback Verify sequencing and overload response
Robot interface Part present, load complete, door status, or transfer-ready signals Prevent conflicting commands and unsafe simultaneous actions

A command being issued does not prove that the physical action completed. For example, CHUCK_CLAMP_CMD is not equivalent to CHUCK_CLAMPED_FB.

Use the feedback needed to prove the intended machine state.

12. Safety and Interlock Boundaries

Safety functions must be designed and validated according to the machine risk assessment and applicable safety standards. Ordinary PLC-CNC communication should not be treated as a substitute for a validated safety function.

Important distinctions:

  • A standard PLC interlock can prevent a cycle from starting, but may not provide the required safety integrity.
  • A normal CNC alarm is not equivalent to a safety-rated stop.
  • Feed hold is not equivalent to emergency stop.
  • A door-closed status bit does not by itself prove that the door safety function is correctly implemented.
  • A communication timeout is not automatically a safe stopping function.
  • Restoring communication must not automatically restart motion unless the approved design explicitly permits the behavior and all restart conditions are satisfied.

12.1 Feed hold, stop, reset, and emergency stop

Function Purpose Key limitation
Feed hold Requests a controlled pause in feed motion Does not necessarily stop every machine function or remove hazardous energy
Program stop Stops program progression according to CNC behavior Does not necessarily make the machine safe for intervention
CNC reset Clears or resets specified CNC states May cancel program execution and change machine state
Emergency stop Initiates the designed emergency-stop response Must use the validated safety architecture, not an ordinary communications bit alone
Safe torque off (STO) Prevents drive torque production when correctly implemented Does not necessarily stop motion immediately or isolate electrical energy

Commissioning must validate each function separately against the machine design.

13. Alarm Handling and Diagnostics

A useful PLC-CNC interface should make faults distinguishable rather than reducing every problem to “CNC not ready.”

Typical diagnostic categories include:

  • CNC not ready.
  • CNC alarm active.
  • Start request not acknowledged.
  • Cycle-active feedback timeout.
  • Cycle-complete feedback missing.
  • Invalid or unavailable program selection.
  • Required machine permissive missing.
  • Fieldbus or network connection lost.
  • Invalid or stale process data.
  • Auxiliary equipment failed to reach its commanded state.
  • Unexpected state transition.
  • Fault reset attempted while the original fault remains active.

13.1 Diagnostic design

For each fault, document:

  • Fault identifier and description.
  • Detection condition.
  • Relevant PLC and CNC signals.
  • Whether the fault is latched.
  • Reset requirements.
  • Safe machine response.
  • Operator instructions.
  • Required maintenance investigation.
  • Whether automatic recovery is permitted.

When available, record a timestamp, CNC alarm number, PLC sequence state, relevant signal snapshot, and last accepted command. This information can turn a recurring intermittent failure into a diagnosable event.

14. Communication-Loss Detection and Recovery

Communication loss may occur because of a cable or switch fault, device restart, network configuration error, fieldbus failure, controller fault, or software issue.

The correct response depends on the process and machine safety design.

14.1 Required behavior

  • Detect communication loss using the protocol's connection status, watchdog, data-validity indicator, or approved diagnostic method.
  • Inhibit new commands that depend on valid CNC data.
  • Apply the machine's approved response to the current operating state.
  • Prevent stale input values from being treated as valid current status.
  • Avoid automatic repeated cycle-start commands.
  • Record the fault and relevant operating state.
  • Require appropriate validation before resuming the sequence.

Do not blindly force every communication-related output to FALSE. Some signals may need a specific fail-safe state, while others require a coordinated controlled stop. The required response must be derived from the machine risk assessment and interface design.

14.2 Recovery sequence

Communication fault detected
         ↓
Apply the defined fault response
         ↓
Prevent unintended new cycle commands
         ↓
Identify and correct the network or controller fault
         ↓
Confirm communication and valid current data
         ↓
Verify CNC state and machine permissives
         ↓
Perform the approved reset or recovery sequence
         ↓
Resume operation only when restart conditions are satisfied

The recovery logic must account for an interruption that occurs mid-cycle. Restoring communication does not prove that the CNC program, part position, tool state, or machine sequence is ready to resume automatically.

15. Commissioning Procedure

Phase 1: Documentation and preparation

  • Obtain current PLC and CNC backups.
  • Verify electrical drawings, I/O lists, interface specification, and network topology.
  • Confirm firmware, software versions, and required communication options.
  • Identify command ownership and acknowledgement behavior.
  • Identify safety functions and approved test methods.
  • Review machine-builder commissioning and recovery procedures.

Phase 2: Physical and network verification

  • Verify wiring, terminal references, polarity, and voltage.
  • Verify communication cabling, port selection, and link status.
  • Confirm IP addresses, device names, and protocol configuration.
  • Confirm device identity and cyclic I/O mapping.
  • Check for duplicate addresses, bus errors, and connection faults.
  • Verify communication diagnostics before enabling automatic operation.

Phase 3: Signal-by-signal verification

  • Test each PLC-to-CNC command.
  • Test each CNC-to-PLC status signal.
  • Verify bit positions, data types, and scaling.
  • Verify active-high or active-low behavior.
  • Confirm feedback corresponds to the actual machine condition.
  • Verify each signal's reset and recovery behavior.
  • Record expected and actual results.

Phase 4: Sequence and interlock verification

  • Verify CNC-ready handling.
  • Verify program selection and acknowledgement.
  • Verify operating-mode restrictions.
  • Verify cycle-start request and acknowledgement.
  • Verify cycle-active and cycle-complete transitions.
  • Verify door, chuck, fixture, tool changer, and auxiliary interlocks.
  • Verify alarms and invalid command handling.
  • Verify timeouts and prevention of repeated starts.

Phase 5: Fault and recovery verification

  • Test a missing acknowledgement using an approved method.
  • Test an unavailable permissive.
  • Test CNC alarm handling.
  • Test communication loss and restoration using an approved method.
  • Verify no unintended automatic restart occurs.
  • Verify the defined mid-cycle recovery procedure.
  • Confirm that safety functions are tested separately under the approved safety-validation procedure.

Phase 6: Production validation

  • Execute an approved dry run or simulation.
  • Verify the complete machine sequence.
  • Run a controlled production trial.
  • Check cycle time and sequence stability.
  • Verify part and tool handling, where applicable.
  • Record unresolved defects and obtain the required sign-off.

16. Troubleshooting Guide

Symptom Possible cause Verification
CNC never reports ready CNC alarm, incorrect mode, startup incomplete, or missing permissive Inspect CNC diagnostics and the documented readiness conditions
PLC sends start but CNC does not start Incorrect signal mapping, invalid mode, wrong program, or missing interlock Trace the request from PLC logic to the CNC input and check CNC status
Start works intermittently Pulse too short, incorrect edge logic, or timing mismatch Review the interface specification, scan timing, filtering, and acknowledgement sequence
CNC starts but PLC does not detect cycle active Wrong mapping, polarity, data offset, or transition timing Monitor raw interface data and the mapped PLC tag
Cycle completes but next sequence does not start Completion signal not cleared, missing auxiliary feedback, or sequence condition false Inspect the PLC sequence state and all next-step permissives
PLC and CNC display different values Data type, scaling, bit offset, or byte-order mismatch Compare raw transmitted data with the decoded values
Network appears connected but data is stale Cyclic exchange failure, invalid data status, or application-level problem Check connection state, update diagnostics, and data-validity indicators
CNC alarm does not clear Fault cause persists or reset conditions are not met Identify the original alarm and use the approved reset sequence
Machine restarts unexpectedly after reconnection Inadequate restart inhibition or retained command state Inspect command latching, startup initialization, and recovery logic
Chuck or door condition blocks cycle Missing or inconsistent feedback, incorrect sensor adjustment, or interlock mismatch Verify physical condition, feedback signal, and documented permissive
M-code sequence hangs Missing PLC acknowledgement or auxiliary completion feedback Trace the M-code request, PLC sequence, device action, and completion signal
Cycle time is inconsistent Excessive handshake delays, repeated polling, network load, or sequence logic Timestamp state transitions and identify the actual source of delay

Troubleshoot from the physical condition toward the application state: device → sensor or output → wiring/network → raw I/O → mapped variable → sequence logic → CNC response. This narrows the search instead of encouraging random edits to working equipment.

17. Timing and Performance Validation

Communication and handshake timing can affect machine cycle time. Record actual transition timestamps instead of assuming that a delay is caused by the network.

Useful measurements include:

  • Time from start request to acknowledgement.
  • Time from start request to cycle-active feedback.
  • Time from the end of the CNC program to cycle-complete feedback.
  • Time spent waiting for doors, chucks, fixtures, or other equipment.
  • Time between a command and the corresponding physical feedback.
  • Communication update time and observed data freshness.
  • Frequency of timeouts and unexpected state transitions.

A simple cycle-time model is:

\[ T\_{\text{cycle}} = T\_{\text{machining}} + T\_{\text{handling}} + T\_{\text{interlocks}} + T\_{\text{communication waits}} \]

This is a simplified accounting model. Some operations overlap, so the terms cannot always be added directly without considering the actual sequence.

Do not shorten delays merely to improve cycle time. First determine whether each delay is required for signal stability, device movement, process completion, or safety. Optimize only after the underlying timing requirements are understood and validated.

18. FAT and SAT for PLC-CNC Communication

FAT (Factory Acceptance Test) verifies the system under factory test conditions. SAT (Site Acceptance Test) verifies it after installation and integration at the destination site.

Test item FAT emphasis SAT emphasis
Signal mapping Verify configured data and simulated or available I/O Verify actual field wiring and installed device behavior
Network Verify device configuration and communication Verify installed network, topology, and site-specific configuration
Handshake Verify requests, acknowledgements, and state transitions Verify complete operation with the real machine
Interlocks Verify documented sequence behavior Verify actual sensors, actuators, fixtures, and installed safety arrangements
Alarms Verify detection, display, and reset behavior Verify real fault diagnostics and maintenance access
Recovery Verify designed fault and restart logic Verify recovery from representative site faults
Cycle performance Verify sequence timing under test conditions Verify production cycle time and repeatability
Documentation Review interface documents and test records Confirm final as-built records, backups, and handover

FAT does not replace SAT. A correct factory configuration can still fail at site because of incorrect field wiring, device differences, network configuration, or machine integration.

19. Acceptance Criteria

Acceptance criteria should be agreed before testing and should be measurable.

Typical criteria include:

  • All required interface signals are mapped correctly and verified.
  • All required commands and acknowledgements follow the approved sequence.
  • CNC readiness, alarm, active-cycle, and completion states are correctly interpreted.
  • Program selection and operating-mode restrictions behave as specified.
  • Required machine permissives prevent invalid cycle initiation.
  • Communication faults are detected within the defined limits.
  • Fault recovery does not cause unintended movement or repeated cycle initiation.
  • Safety functions pass their separate validation requirements.
  • Cycle performance meets the agreed machine requirements.
  • No unresolved critical defects remain.
  • Test records, final backups, interface documents, and recovery instructions are handed over.

The acceptable response time, timeout values, cycle time, and fault-recovery limits must come from the approved machine requirements. They should not be invented during commissioning to make a failed test appear successful.

20. Practical Example: PLC-Controlled CNC Loading

Consider an automated CNC machine that receives a component from a robot. An external PLC coordinates the robot, machine door, chuck, and CNC cycle.

A simplified sequence is:

PLC verifies CNC ready and robot transfer permission
         ↓
PLC requests door opening under the approved machine sequence
         ↓
Door-open confirmation received
         ↓
Robot loads the component
         ↓
Robot confirms loading complete and clears the loading zone
         ↓
PLC commands chuck clamping
         ↓
Chuck-clamped feedback confirmed
         ↓
PLC verifies required door and machine conditions
         ↓
Door closes and the required closed/locked conditions are confirmed
         ↓
PLC issues CNC cycle-start request
         ↓
CNC acknowledges and reports cycle active
         ↓
CNC completes machining and reports completion
         ↓
PLC verifies the required completion and machine states
         ↓
PLC requests the next approved unloading sequence

The exact sequence varies by machine design. Door, chuck, and robot operations must follow the validated safety architecture, and CNC program completion must not be treated as proof that every unloading condition is satisfied.

Example fault: CNC does not start

Suppose the PLC issues CNC_START_REQ, but CNC_CYCLE_ACTIVE remains false.

A disciplined investigation checks:

  1. Does the PLC sequence actually issue the request?
  2. Is the request present at the physical interface or in the correct communication output data?
  3. Does the CNC receive the request in its mapped interface variable?
  4. Is the request edge or pulse behavior correct?
  5. Is the CNC in the correct operating mode?
  6. Is the intended program selected and ready to run?
  7. Is an alarm or machine permissive preventing acceptance?
  8. Does the CNC interface require an additional enable or acknowledgement?
  9. Does the PLC detect a timeout and inhibit unintended retries?
  10. After the cause is corrected, does the approved recovery procedure restore normal operation?

This approach identifies whether the fault is in the command source, communication path, CNC acceptance conditions, or machine sequence.

21. Common Commissioning Mistakes

  • Assuming all CNC brands use the same signal definitions.
  • Treating network link status as proof of healthy cyclic communication.
  • Using the wrong I/O offset or data type.
  • Ignoring active-low signals or inverted logic.
  • Confusing a start request with cycle-start acceptance.
  • Treating CNC ready as proof that all machine permissives are satisfied.
  • Assuming a cycle-complete bit guarantees safe unloading.
  • Using arbitrary pulse widths or timeout values.
  • Clearing alarms without identifying the original cause.
  • Allowing stale status data to remain valid after communication loss.
  • Automatically restarting after communication recovery.
  • Using standard PLC bits as substitutes for required safety functions.
  • Changing CNC parameters or machine-builder interface logic without a backup and approved change process.
  • Failing to document the final configuration and signal mapping.

22. Documentation and Handover

The commissioning package should include:

  • Final PLC and CNC backups, with version identification.
  • Electrical drawings and the verified I/O list.
  • Network topology and device configuration.
  • PLC-CNC signal and data mapping.
  • Handshake sequence and timing requirements.
  • Alarm and timeout definitions.
  • Fault-recovery and restart procedures.
  • FAT/SAT records and outstanding-defect status.
  • Safety-validation records where applicable.
  • As-built changes and approvals.
  • Maintenance troubleshooting instructions.

For production maintenance, a concise signal map and a documented state-transition sequence are particularly valuable. They let another engineer determine whether the fault is caused by the CNC, PLC logic, communication path, or machine hardware without reconstructing the entire interface from scratch.

23. Interview Questions and Answers

1. What is PLC-CNC communication commissioning?

It is the verification and validation of commands, status signals, data exchange, handshakes, interlocks, diagnostics, and recovery between the PLC and CNC.

2. What is the difference between CNC ready and CNC cycle active?

CNC ready indicates readiness under the interface definition. CNC cycle active indicates that program execution has entered the defined active state. Readiness does not prove that a cycle has started.

3. Why is a handshake necessary?

It coordinates command acceptance and status confirmation, preventing missed commands, incorrect sequencing, and unintended repeated operations.

4. Why can a start request be present while the CNC does not start?

The CNC may be in the wrong mode, have an active alarm, lack a required permissive, have an invalid program selection, or receive an incorrectly mapped or timed command.

5. What is the difference between a command and feedback?

A command requests an action. Feedback confirms the reported state or completion condition. A physical action should not be assumed complete solely because its command was issued.

6. Why can Ethernet connectivity exist while PLC-CNC data exchange fails?

Physical link or ping success does not guarantee correct protocol configuration, valid cyclic connections, correct data mapping, or application-level operation.

7. How should communication loss be handled?

Detect the fault, apply the defined machine response, inhibit unsafe or invalid new commands, diagnose and restore communication, validate current machine state, and follow the approved recovery procedure.

8. Is feed hold equivalent to emergency stop?

No. Feed hold requests a controlled pause in feed motion. Emergency stop is a safety function with a defined response implemented and validated through the machine's safety architecture.

9. Why are M-code functions important in commissioning?

They often coordinate auxiliary machine functions. The request, PLC action, completion acknowledgement, and fault behavior must be verified according to the machine-specific definition.

10. How would you diagnose a CNC cycle that hangs during an M-code?

Trace the M-code request, identify the controller responsible for the action, inspect the PLC sequence, verify the physical action and feedback, and check the required acknowledgement and timeout.

11. What is the difference between FAT and SAT?

FAT verifies the system under factory test conditions. SAT verifies the installed system, including real field wiring, equipment, site network, and integrated machine behavior.

12. What evidence demonstrates successful commissioning?

Verified signal mappings, successful sequence tests, validated interlocks and fault handling, measured performance, completed acceptance records, and an approved final configuration.

24. Final Commissioning Checklist

  • CNC and PLC models, software versions, and interface options confirmed.
  • Correct interface method and architecture documented.
  • Electrical wiring or network configuration verified.
  • Every required signal and data field mapped and tested.
  • Data types, offsets, polarity, and scaling verified.
  • CNC-ready and cycle-start handshakes validated.
  • Program selection and operating-mode conditions verified.
  • Auxiliary equipment and required feedback validated.
  • Alarm handling, timeouts, and reset behavior verified.
  • Communication-loss behavior and recovery tested.
  • No unintended restart occurs after fault recovery.
  • Safety functions validated separately under the approved procedure.
  • Production sequence and cycle performance verified.
  • FAT/SAT records, backups, and as-built documentation completed.
  • Acceptance criteria satisfied and handover approved.
