1. Definition and Purpose

Auto-cycle operation is a machine operating mode in which the control system repeatedly executes the defined production cycle without requiring a separate operator start command for every cycle, provided the required operating conditions remain satisfied.

After one cycle finishes, the controller evaluates whether the next cycle can begin. If automatic operation remains enabled, the machine is ready for the next cycle, and all required permissives are valid, the sequence starts again according to the machine's programmed logic.

Auto-cycle commissioning verifies that the machine can repeatedly execute its production sequence with correct timing, feedback, device coordination, fault handling, and end-state management.

Typical applications include:

  • Automotive assembly and component-processing stations.
  • Robotic welding, material handling, and machine tending.
  • CNC loading and unloading cells.
  • Conveyor transfer and indexing systems.
  • Automated inspection and testing stations.
  • Pneumatic and hydraulic assembly machines.
  • Automated fastening, pressing, and dispensing systems.
  • Packaging and high-volume production equipment.

The central difference from single-cycle operation is the automatic initiation of subsequent cycles. A single-cycle machine normally waits for another start request after one completed cycle. An auto-cycle machine continues initiating cycles while the automatic-run conditions remain satisfied.

2. Position in the Commissioning Sequence

Auto-cycle commissioning normally follows successful manual, jog, and single-cycle commissioning.

Mechanical and electrical installation
                 ↓
Device and I/O commissioning
                 ↓
Communication verification
                 ↓
Manual function commissioning
                 ↓
Jog movement commissioning
                 ↓
Single-cycle commissioning
                 ↓
Auto-cycle commissioning
                 ↓
Continuous operation and endurance testing
                 ↓
Production performance verification
                 ↓
Final acceptance and handover

The exact commissioning order depends on the project, but repeated automatic operation should not be treated as a substitute for verifying individual functions and the complete single-cycle sequence first.

3. Single Cycle vs Auto Cycle vs Continuous Operation

Terminology varies between machine builders. Some systems use auto cycle and continuous cycle almost interchangeably, while others distinguish them.

Operating mode Cycle initiation Expected behavior
Manual Individual operator command Executes a selected function
Jog Directional or incremental command Performs controlled movement
Single cycle One accepted start request Executes one complete cycle and waits
Auto cycle Automatic-run command or mode selection Repeats cycles while required conditions remain valid
Continuous operation Defined continuous-run command Maintains ongoing operation, potentially without a discrete cycle boundary
Recovery Approved recovery command Restores a valid machine state

For a machine with discrete workpieces, auto-cycle operation commonly means repeating the complete sequence for each part. For a conveyor, pump, fan, or continuous process, continuous operation may instead maintain an operating condition without a distinct start-to-finish cycle for every unit.

The commissioning engineer must establish the project's exact definition rather than assume that the names are universal.

4. Auto-Cycle Operating Principle

A typical discrete production station follows this pattern:

Automatic mode selected
          ↓
Automatic-run request accepted
          ↓
Initial state and start permissives verified
          ↓
Cycle begins
          ↓
Production sequence executes
          ↓
Process result and completion verified
          ↓
Workpiece released or transferred
          ↓
Cycle-end conditions verified
          ↓
Next-cycle conditions evaluated
          ↓
Conditions valid and auto-run still enabled?
          ↓
Start next cycle automatically

If the required conditions are not satisfied, the controller must follow the specified behavior. It may wait for a part, pause at a defined boundary, inhibit the next cycle, or enter a fault state.

The behavior must be explicitly defined. An auto-cycle machine should not repeatedly restart just because its sequence has returned to Step 0.

5. Auto-Cycle Control Architecture

The control system coordinates the machine sequence, devices, workpiece flow, process validation, and automatic restart logic.

HMI / automatic-run command
              ↓
Mode and command validation
              ↓
Auto-run state management
              ↓
Start permissives and initial-state checks
              ↓
PLC sequence controller
              ↓
Actuators, drives, robots, CNCs, process devices
              ↓
Physical feedback and device handshakes
              ↓
Process completion and result validation
              ↓
Part release / transfer / next-part readiness
              ↓
Cycle-end evaluation
              ↓
Next-cycle decision
              ↓
Repeat, wait, pause, or fault

The auto-run state and the individual cycle state should be distinguishable. For example, the machine can remain in auto-run mode while temporarily waiting for the next workpiece.

This distinction makes diagnostics clearer:

  • AUTO_MODE_ACTIVE indicates the selected operating mode.
  • AUTO_RUN_ACTIVE indicates that automatic operation has been authorized and remains active.
  • CYCLE_ACTIVE indicates that a particular production cycle is executing.
  • WAITING_FOR_PART indicates that the machine is waiting for material.
  • CYCLE_COMPLETE indicates that the current cycle has met its defined completion criteria.

These are illustrative names, not universal standards.

6. Auto-Cycle Start Conditions

Before accepting automatic operation, the controller should validate the required conditions defined in the functional specification.

Typical conditions include:

  • Automatic mode is selected.
  • The automatic-run request is valid.
  • The machine is in the required initial state.
  • No blocking fault is active.
  • Required safety conditions are satisfied.
  • Required axes, drives, robots, and devices are ready.
  • Required utilities are available.
  • Workpiece and tooling conditions are valid.
  • The required program, recipe, or job is selected.
  • Required communications are healthy.
  • The previous cycle has completed and its state has been cleared appropriately.
  • No conflicting operation is active.

The required conditions depend on the machine's process and design.

6.1 Auto-run request vs cycle-start request

These commands serve different purposes.

Command Meaning
Auto-run request Requests or enables automatic production operation
Cycle-start request Requests the initiation of a particular cycle
Cycle active Indicates that a cycle is currently executing
Cycle complete Indicates that the current cycle has satisfied its completion conditions
Auto-run stopped Indicates that automatic repetition has been cancelled or stopped according to the design

Some PLC programs combine auto-run and cycle-start logic, but their functional meanings should remain clear.

6.2 Start acceptance and restart prevention

The PLC must define exactly when a cycle can begin. A typical design requires the sequence to be idle or at its defined initial state, the previous cycle to be complete, and the required start conditions to be valid.

It should also prevent:

  • Starting while a previous cycle remains active.
  • Starting with an unresolved blocking fault.
  • Starting with an invalid workpiece state.
  • Reusing a stale device-complete signal.
  • Repeating a cycle after auto-run has been cancelled.
  • Initiating a cycle because an old HMI start command remains latched.

7. Sequence Architecture for Repeated Cycles

An auto-cycle machine usually contains two related control layers.

Layer 1: Cycle sequence

Controls the operations for one workpiece or one production cycle.

Layer 2: Auto-run manager

Determines whether the machine should begin another cycle, wait, pause, or stop repeating.

AUTO-RUN MANAGER
      ↓
Validate machine readiness
      ↓
Start one production cycle
      ↓
CYCLE SEQUENCE
      ↓
Execute operations
      ↓
Verify completion and process result
      ↓
Release or transfer workpiece
      ↓
Return to cycle-end state
      ↓
AUTO-RUN MANAGER
      ↓
Repeat / Wait / Pause / Stop / Fault

Separating these responsibilities can simplify troubleshooting and reduce unintended restarts.

8. Example Auto-Cycle State Model

A conceptual state model for a discrete production station is shown below.

IDLE
  ↓ Auto-run accepted
AUTO-READY
  ↓ Cycle-start conditions satisfied
CYCLE-START
  ↓
EXECUTE PROCESS SEQUENCE
  ↓
VALIDATE PROCESS RESULT
  ↓
RELEASE / TRANSFER PART
  ↓
CYCLE-END VALIDATION
  ↓
AUTO-RUN STILL ENABLED?
  ├─ Yes, next cycle permitted → AUTO-READY / NEXT CYCLE
  ├─ Yes, but part unavailable → WAIT FOR PART
  ├─ No → STOPPED AT DEFINED STATE
  └─ Fault detected → FAULT HANDLING

This is illustrative. Some systems remain in an auto-ready state while waiting for the next part; others include separate states for material loading, downstream clearance, or operator confirmation.

The important requirement is that every transition has a defined condition and that the machine does not enter an ambiguous state.

These signals must have documented set, reset, and retention behavior. For example, the cycle counter should increment at a clearly defined event, not simply when the start command is accepted.

Standard PLC status signals do not replace safety-related control functions.

10. Next-Cycle Conditions

A completed cycle does not automatically mean the next cycle can start.

Typical next-cycle conditions include:

  • The previous cycle has completed.
  • The previous workpiece has been released or transferred as required.
  • The next workpiece is available, if the process requires one.
  • The fixture is in the required state.
  • The next device operation is permitted.
  • Downstream equipment is ready where required.
  • Required process data has been recorded.
  • No blocking fault is active.
  • Auto-run remains enabled.
  • The sequence is in the defined state for starting another cycle.

A machine may be ready to continue automatic operation but temporarily unable to start the next cycle because the downstream conveyor is blocked or the next workpiece has not arrived.

That condition should be represented as a defined wait or inhibit state rather than misreported as a machine fault unless the functional specification says otherwise.

11. Auto-Cycle Commissioning Procedure

Step 1: Confirm single-cycle performance

Before enabling repeated automatic operation, verify that the individual cycle has passed its required tests.

Confirm:

  • All sequence steps execute correctly.
  • Required feedback is valid.
  • Device handshakes work.
  • Cycle-end conditions are correct.
  • Fault handling has been tested.
  • The machine returns to its expected state.

Step 2: Verify auto-run activation

Select automatic mode and issue the approved auto-run command.

Check that:

  • The correct mode is active.
  • The auto-run request is accepted only under valid conditions.
  • The HMI shows the correct operating state.
  • The machine does not start if required permissives are missing.
  • A stale command cannot initiate an unintended cycle.

Step 3: Observe the first automatically initiated cycle

Monitor the sequence from the initial state through cycle completion.

Verify every command, feedback, transition, device handshake, process result, and end condition.

Do not focus exclusively on the first actuator movement. The entire cycle must be evaluated.

Step 4: Verify automatic repetition

After the first cycle completes, confirm that the controller evaluates the next-cycle conditions correctly.

If conditions are satisfied, the next cycle should start according to the specified design without requiring another individual cycle-start command.

Verify that:

  • The previous cycle is fully complete.
  • Previous-cycle flags and results are handled correctly.
  • The next cycle begins at the correct state.
  • Workpiece identity and process data are updated correctly.
  • Counters increment at the defined event.
  • No operation is skipped or repeated unintentionally.

Step 5: Verify material-flow behavior

Test the normal material-flow conditions specified by the project:

  • Part available at cycle end.
  • Part unavailable at cycle end.
  • Downstream equipment ready.
  • Downstream equipment blocked.
  • Required fixture or nest occupied.
  • Workpiece transfer incomplete.

The machine must respond according to the approved sequence and material-handling design.

Step 6: Verify stop behavior

Test the approved auto-stop command and other specified stop conditions.

Confirm whether the machine:

  • Finishes the current cycle and then stops.
  • Stops at a defined sequence boundary.
  • Stops immediately through the appropriate control function.
  • Waits in a defined state for operator action.

Do not assume all stop commands behave identically. Their behavior must be defined by the functional and safety requirements.

Step 7: Verify fault behavior during repeated operation

Using approved test methods, verify relevant faults during cycle execution and at cycle boundaries.

Examples include:

  • Actuator timeout.
  • Robot or CNC fault.
  • Device communication loss.
  • Missing workpiece.
  • Invalid process result.
  • Downstream blockage.
  • Sensor disagreement.

Confirm that the machine does not start another cycle when a blocking fault is active.

Step 8: Verify restart after stopping

After an approved stop, confirm that the machine follows the specified restart procedure.

Verify the current cycle state, workpiece state, device status, and any required operator acknowledgement.

A stopped machine must not unexpectedly restart merely because the stop condition clears.

Step 9: Perform repeated-cycle testing

Run the number of cycles specified by the commissioning plan.

Record cycle results, cycle times, faults, interruptions, and any operator intervention. Include the operating conditions required by the acceptance criteria.

12. Practical Example: Robotic Automotive Assembly Station

12.1 System description

Consider a robotic station with:

  • Part-present sensors.
  • Pneumatic clamping fixture.
  • Industrial robot.
  • Assembly or welding process equipment.
  • PLC and HMI.
  • Upstream part supply.
  • Downstream conveyor.
  • Process result and traceability recording.

The machine must repeatedly process workpieces while automatic operation remains authorized.

12.2 Example sequence

Step Operation Completion condition
0 Wait for automatic-run conditions Auto-run active and start permissives valid
10 Confirm part availability Required part-presence condition valid
20 Clamp workpiece Clamp feedback verified
30 Request robot operation Robot accepts the request
40 Execute robot process Robot and process-device completion verified
50 Validate process result Required result is valid
60 Release workpiece Clamp-open feedback verified
70 Transfer part Transfer completion verified if required
80 Record cycle completion Required production data recorded
90 Evaluate next cycle Next-cycle conditions evaluated

The sequence is illustrative. Real machines may use different step orders, overlap operations, or include additional checks.

12.3 Example: Downstream conveyor blocked

Suppose the robot completes its process successfully, but the downstream conveyor cannot accept the finished workpiece.

A correct response depends on the machine design. The PLC may keep the workpiece in the fixture, hold the station at a transfer step, or move it to an approved buffer position.

The machine should not blindly initiate the next cycle if doing so would cause a collision, overwrite workpiece data, or violate the material-flow design.

The commissioning engineer should verify:

  1. The downstream-ready signal is received correctly.
  2. The blocked condition prevents the prohibited transfer or next-cycle transition.
  3. The HMI identifies the waiting condition.
  4. The current workpiece remains correctly tracked.
  5. The machine resumes only when the defined conditions are restored.
  6. The completed process result is not lost or assigned to the next workpiece.

13. Cycle-Time Analysis and Throughput

Auto-cycle commissioning also evaluates repeated production performance.

The cycle time is:

\[ T\_{\text{cycle}} = t\_{\text{cycle end}} - t\_{\text{cycle start}} \]

For a repeated sequence, average cycle time can be calculated as:

\[ T\_{\text{avg}} = \frac{\sum\_{i=1}^{n} T_i}{n} \]

where \(T_i\) is the measured duration of cycle \(i\), and \(n\) is the number of measured cycles.

For a stable process where one part is completed per cycle, idealized output rate is:

\[ Q = \frac{3600}{T\_{\text{cycle}}} \]

where cycle time is measured in seconds and \(Q\) is in parts per hour. This represents ideal output before accounting for downtime, rejects, changeovers, and other losses.

For parallel stations, buffered lines, or overlapping operations, actual line throughput depends on the bottleneck and system-level synchronization rather than the cycle time of any one station alone.

13.1 What to measure

  • Average cycle time.
  • Minimum and maximum cycle time.
  • Step-by-step duration.
  • Waiting time for upstream material.
  • Waiting time for downstream clearance.
  • Robot and CNC execution time.
  • Process and inspection duration.
  • Fault-related delays.
  • Manual interventions.
  • Good-part and reject counts.

13.2 Diagnosing inconsistent cycle times

If cycle times vary significantly, investigate:

  • Sensor response and filtering.
  • Network communication delays.
  • Robot or CNC program execution time.
  • Variable process duration.
  • Device handshakes.
  • Unnecessary sequential operations.
  • Upstream and downstream material availability.
  • HMI or data-recording delays if they affect sequence progression.
  • Incorrect timer or transition logic.

Do not optimize by bypassing feedback or reducing necessary safety margins. Performance improvements should come from verified process analysis.

14. Auto-Cycle Fault Handling

14.1 Missing workpiece

The controller should prevent a new cycle from starting when the required workpiece is absent.

Depending on the specification, the machine may wait for material, request replenishment, or enter a fault state after a defined condition or timeout.

14.2 Device not ready

If a robot, CNC, drive, or process device is not ready, the PLC should prevent the dependent operation from starting.

If readiness is lost during execution, the response must follow the device interface and fault-handling design.

14.3 Communication loss

A communication fault may invalidate device status, commands, or process results.

The sequence should not treat stale values as current confirmation. The design should define communication-loss detection, timeout behavior, command handling, and recovery.

14.4 Process result invalid

A completed operation is not necessarily a successful operation.

For example, a fastening tool may complete its cycle but report torque outside the acceptable range. The PLC must distinguish operation completion from process acceptance.

The workpiece disposition, traceability record, and next-cycle behavior must follow the quality specification.

14.5 Stop request during a cycle

The machine's response depends on the type of stop request and the approved control and safety design.

A normal production stop may request completion of the current cycle before stopping. A fault or safety-related event may require a different response.

Never assume that all stop requests can be handled by the same PLC bit or that a normal auto-stop command replaces a safety function.

15. Auto-Stop, Pause, Fault, and Safety Stop

These conditions should be clearly distinguished in the control design.

Condition Typical meaning Expected behavior
Auto-stop request Stop further automatic repetition Follows the specified cycle-boundary or stop behavior
Pause Temporarily suspend a process where supported Follows the defined pause and resume sequence
Process fault A process or device operation has failed Executes the defined fault response
Communication fault Required communication or data is unavailable Prevents invalid progression and follows the defined fault strategy
Safety-related stop A safety function has demanded a stop Response is determined by the validated safety design

The exact response must come from the machine's functional specification and risk assessment.

Auto-cycle mode is not inherently safe. Guarding, emergency stops, interlocks, safe motion functions, and other safety measures must remain effective as designed. Standard sequence logic and HMI indications do not substitute for validated safety-related control functions.

17. FAT and SAT Acceptance Criteria

FAT: Factory Acceptance Test

Verify the control logic and simulated or available equipment against the agreed requirements.

  • Auto-run activation and rejection conditions.
  • Correct sequence progression.
  • Automatic initiation of subsequent cycles.
  • Start and stop command behavior.
  • Cycle-completion and counter logic.
  • Device handshake and stale-signal handling.
  • Fault, timeout, and recovery behavior.
  • Waiting states and material-flow conditions.
  • Process result and traceability handling.
  • Compliance with specified cycle-time targets where measurable.

SAT: Site Acceptance Test

Verify the installed machine under actual site conditions.

  • Physical device and sensor behavior.
  • Installed network and communication performance.
  • Actual upstream and downstream handshakes.
  • Repeated automatic operation with production materials.
  • Cycle-time performance and variation.
  • Correct handling of missing material and blocked transfer.
  • Fault handling and restart behavior.
  • Safety-function validation according to the approved test plan.
  • Production data, reject handling, and traceability.
  • Documentation of deviations and corrective actions.

Acceptance criteria

Acceptance criteria should be measurable and agreed in advance. Examples include:

  • Required sequence completes in the correct order.
  • Automatic repetition occurs only when permitted.
  • The machine does not restart unintentionally.
  • All specified fault tests produce the expected response.
  • Required process results are correctly classified and recorded.
  • Cycle time meets the approved target under defined test conditions.
  • Required safety validation is completed.
  • Test records and outstanding deviations are documented.

A few successful cycles do not establish long-term reliability. The duration and number of cycles for repeatability or endurance testing must be defined by the project.

18. Common Auto-Cycle Commissioning Mistakes

  • Treating auto-run activation as proof that the machine is ready to produce.
  • Confusing auto-run state with cycle-active state.
  • Starting the next cycle before the previous cycle's end conditions are satisfied.
  • Failing to clear previous-cycle flags and device handshakes.
  • Accepting stale sensor or completion data.
  • Ignoring upstream or downstream material-flow conditions.
  • Counting a cycle as good before its process result is validated.
  • Allowing a stopped machine to restart automatically without the required authorization.
  • Treating every wait condition as a fault, or every fault as a normal wait condition.
  • Increasing timeouts without finding the underlying cause.
  • Testing only a short sequence of cycles.
  • Optimizing throughput before confirming correct operation and safety.
  • Failing to record the tested software version, parameter changes, and commissioning results.

19. Interview Questions and Answers

Q1. What is auto-cycle operation?

Auto-cycle operation repeatedly executes the machine's production cycle while automatic-run authorization and the required cycle-start conditions remain valid.

Q2. How is auto-cycle different from single-cycle operation?

Single-cycle operation executes one cycle for each accepted start request. Auto-cycle operation initiates subsequent cycles automatically when the defined conditions are satisfied.

Q3. Why should the auto-run manager be distinguished from the cycle sequence?

The auto-run manager decides whether the machine should repeat, wait, pause, or stop. The cycle sequence controls the operations performed during one cycle. Separating them improves clarity and fault diagnosis.

Q4. Why might a machine complete its first cycle but fail on the second?

Possible causes include stale completion signals, retained flags, incomplete reset logic, incorrect cycle-end transitions, invalid workpiece state, or missing next-cycle permissives.

Q5. What is a next-cycle permissive?

It is the set of conditions that must be satisfied before another production cycle can begin, such as part availability, device readiness, a valid previous-cycle end state, and the absence of blocking faults.

Q6. Should every device-complete signal immediately start the next operation?

No. The controller must verify that the signal is valid for the current operation and evaluate all required transition conditions.

Q7. How should a blocked downstream conveyor affect auto-cycle operation?

The machine should follow the specified material-flow strategy, such as waiting at a defined transfer step or using an approved buffer. It should not perform an unsafe or invalid next-cycle transition.

Q8. How is cycle time measured?

It is measured between the defined cycle-start and cycle-end events. Step-level timing helps identify where delays occur.

Q9. Why is process completion different from process acceptance?

A device can finish an operation while producing an unacceptable result. Quality validation must determine whether the part is good, rejected, or requires further action.

Q10. How should the machine respond to an auto-stop command?

According to the defined stop behavior. It may finish the current cycle before stopping or follow another specified stop strategy. The command must not be confused with a safety-related stop.

Q11. Why is repeated-cycle testing necessary?

It exposes issues involving state retention, repeated starts, stale feedback, counter handling, timing variation, material flow, and device coordination that may not appear during a single cycle.

Q12. What proves that auto-cycle commissioning is complete?

Documented verification of automatic repetition, next-cycle permissives, correct sequence and process results, stop and fault handling, recovery, cycle-time criteria, repeatability, and required safety validation.

20. Final Auto-Cycle Commissioning Checklist

  • Single-cycle operation has passed its required tests.
  • Automatic mode and auto-run authorization are verified.
  • Start permissives are complete and correct.
  • Auto-run and cycle-active states are clearly distinguished.
  • Every cycle step and transition has been verified.
  • Device handshakes and completion signals are valid.
  • Previous-cycle flags and results are handled correctly.
  • Next-cycle conditions are verified.
  • Missing material and blocked-transfer behavior are correct.
  • Cycle counters and traceability data are correct.
  • Process completion is distinguished from quality acceptance.
  • Auto-stop, pause, fault, and restart behavior are verified.
  • Communication loss and device timeouts are handled correctly.
  • Repeated-cycle timing meets the approved criteria.
  • Required repeatability or endurance tests are completed.
  • Safety-related functions are validated according to the approved plan.
  • Temporary commissioning changes are removed or formally controlled.
  • FAT/SAT records, deviations, and corrective actions are documented.

Core principle: Auto-cycle commissioning proves that the machine can repeatedly execute its production sequence, initiate each new cycle only when permitted, maintain correct workpiece and process tracking, and respond predictably to stops, faults, and changing production conditions.
