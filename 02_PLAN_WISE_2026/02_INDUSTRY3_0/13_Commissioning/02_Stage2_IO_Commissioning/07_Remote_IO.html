1. Definition and Scope

Remote I/O (Remote Input/Output) is a distributed input/output system that allows field devices to connect to I/O modules located away from the main PLC or central controller. The remote I/O station communicates with the controller over an industrial communication network.

Instead of routing every field signal back to a central control panel, the signals can be terminated at a local remote I/O station near the machine or process. The controller exchanges input and output data with that station over the network.

Remote I/O is commonly used in:

  • Automotive assembly and body-in-white lines.
  • Robot cells and welding stations.
  • Conveyor and material-handling systems.
  • CNC machine auxiliary equipment.
  • Distributed machine skids.
  • Large production lines with multiple electrical panels.
  • Process plants with widely distributed instruments and actuators.
  • Industry 4.0 systems requiring distributed acquisition of machine data.

Remote I/O commissioning verifies the complete path from field device to remote I/O channel, through the communication network, to the controller and HMI. For output signals, it also verifies the path in the opposite direction and the physical response of the connected equipment.

A remote I/O station can have healthy network communication while individual channels remain incorrectly wired, misconfigured, or faulty. Therefore, network status alone is never sufficient evidence of successful commissioning.

2. Remote I/O System Architecture

A typical remote I/O architecture is:

Field Sensors and Switches
    ↓
Remote Digital Input Modules
    ↓
Remote I/O Adapter / Bus Coupler
    ↓
Industrial Ethernet or Fieldbus
    ↓
PLC / Controller
    ↓
Control Logic and Interlocks
    ↓
Industrial Network
    ↓
Remote I/O Adapter
    ↓
Remote Digital Output Modules
    ↓
Contactors / Solenoid Valves / Actuators

Analog signals and specialized devices follow the same general architecture but use suitable analog, temperature, high-speed, or other specialized modules.

A typical remote I/O station contains:

  • Network adapter or bus coupler.
  • Digital input modules.
  • Digital output modules.
  • Analog input and output modules.
  • Specialized modules, where required.
  • Power supply or field power distribution.
  • Terminal bases and wiring connectors.
  • Network and module status indicators.
  • Configuration and diagnostic information.

The exact hardware arrangement depends on the manufacturer and system design.

3. Centralized I/O versus Remote I/O

Characteristic Centralized I/O Remote I/O
I/O location Usually near the central controller Distributed near machines or process equipment
Field wiring Often returns to the central panel Usually terminates at local remote stations
Controller communication Backplane or local rack communication Industrial network to remote adapters
Network dependency Less dependent on a separate field I/O network Depends on the remote I/O communication path
Expansion Depends on rack and panel capacity Additional stations may be added within system limits
Troubleshooting Concentrated around the main panel Requires checking field channels, station hardware, and network
Typical advantage Simple architecture for compact machines Reduced long field-cable runs and improved modularity
Typical challenge Large cable bundles and centralized panel space Network configuration, station diagnostics, and communication faults

Remote I/O does not automatically make a system more reliable. It changes the architecture and fault boundaries. Reliability depends on design, network quality, power distribution, component selection, environmental conditions, and maintenance practices.

4. Remote I/O versus Distributed Control

Remote I/O is not the same thing as a distributed controller.

A conventional remote I/O station primarily provides input/output interfaces. The PLC or another controller executes the main control program.

A distributed control architecture may contain multiple controllers, each executing its own logic and communicating with other controllers.

Feature Remote I/O Distributed controller
Main function Collects inputs and drives outputs Executes local control logic
Control program Normally executed in the PLC or controller Executed by the local controller
Network role Transfers I/O data and diagnostics Transfers data, commands, status, and coordination information
Local autonomy Usually limited, depending on adapter and device capabilities Can continue supported local control independently
Failure behavior Depends on communication-loss configuration and output design Depends on local control capability and inter-controller dependencies

Some advanced remote I/O platforms support local logic or specialized processing. Do not assume this is available in every remote station.

Terminology varies between platforms. For example, a PROFINET device name and an IP address are separate configuration items, and one does not necessarily substitute for the other.

6. Major Remote I/O Network Types

6.1 PROFINET

PROFINET is an industrial Ethernet communication technology widely used in Siemens-based automation systems and supported by equipment from multiple manufacturers.

Typical commissioning tasks include:

  • Importing the correct device description.
  • Configuring the remote I/O device and its module arrangement.
  • Assigning the required device name.
  • Configuring IP parameters as required.
  • Verifying controller-device relationships.
  • Checking module order and channel configuration.
  • Confirming input/output data exchange.
  • Reviewing device and module diagnostics.

The configured hardware arrangement must match the installed remote I/O station. A device that is physically present but configured with the wrong module order may report configuration errors or fail to exchange the expected process data.

6.2 EtherNet/IP

EtherNet/IP is an industrial Ethernet network technology commonly used with Rockwell Automation systems and compatible third-party devices.

Typical commissioning tasks include:

  • Selecting the correct device profile or EDS.
  • Configuring the adapter IP address.
  • Matching the installed module configuration.
  • Configuring input and output assemblies where required.
  • Setting the requested packet interval within supported limits.
  • Verifying the controller connection and data mapping.
  • Checking connection faults and adapter diagnostics.

The requested packet interval affects communication update behavior. A shorter interval may improve update frequency but increases network and processing demands. The correct value depends on the application and device capabilities.

6.3 EtherCAT

EtherCAT is an industrial Ethernet technology designed for deterministic communication, commonly used in motion and machine automation systems.

Commissioning may involve:

  • Verifying master and slave compatibility.
  • Checking the physical network sequence.
  • Confirming device discovery and configuration.
  • Verifying the expected I/O layout.
  • Checking distributed-clock configuration where required.
  • Confirming network state and diagnostic information.

Do not assume every remote I/O adapter supports every EtherCAT feature. Verify the device documentation.

6.4 PROFIBUS DP

PROFIBUS DP is a fieldbus technology used in many established industrial installations.

Commissioning commonly includes:

  • Checking the bus address.
  • Verifying baud rate and network configuration.
  • Confirming termination and segment topology.
  • Checking cable and connector condition.
  • Matching the configured station and module layout.
  • Verifying communication diagnostics.

Incorrect termination, incorrect station addresses, or wiring faults can prevent communication or cause intermittent errors.

6.5 Modbus TCP and Modbus RTU

Modbus TCP uses TCP/IP communication, commonly over Ethernet. Modbus RTU typically uses serial communication, often over RS-485.

Commissioning depends on the implementation and may include:

  • Verifying IP settings or serial parameters.
  • Confirming device addresses and supported function codes.
  • Checking register maps.
  • Verifying data types, byte order, word order, and scaling.
  • Confirming timeout and communication-loss behavior.

Modbus devices do not necessarily behave like cyclic remote I/O adapters. Some exchange data through explicit polling or register transactions. The controller program and communication configuration must reflect the actual implementation.

7. Remote I/O Power Architecture

Remote I/O stations may use separate supplies for electronics, field devices, and output loads.

Common arrangements include:

  • 24 VDC supply for adapter and module electronics.
  • Separate 24 VDC field supply for sensors.
  • Separate output supply for actuators and solenoid valves.
  • Isolated or separately fused supply groups.
  • Redundant power supplies in supported architectures.

Do not assume that powering the adapter also powers every field output. Some modules require an external field supply, and certain station designs divide power across module groups.

7.1 Power commissioning checklist

  • Verify the supply voltage and polarity.
  • Check the power-supply rating and expected load.
  • Verify protective devices and fuses.
  • Confirm field power is present at the relevant terminals.
  • Check the supply arrangement against the station manual.
  • Verify common/reference connections where required.
  • Inspect voltage drop under load.
  • Check module power and diagnostic indicators.
  • Confirm whether output groups share or separate their supply.
  • Verify behavior after loss and restoration of power.

A remote I/O station can appear online while its field supply is missing. In that case, input electronics or communications may be healthy even though sensors or output devices cannot operate correctly.

8. Remote I/O Network Configuration

8.1 IP addressing

For IP-based systems, verify that each device has a valid address for its intended network.

Check:

  • IP address.
  • Subnet mask.
  • Gateway, where required.
  • Duplicate IP addresses.
  • Correct network interface and physical port.
  • VLAN and switch configuration, where applicable.
  • Device name or identity, where required by the protocol.
  • Controller communication settings.
  • Firewall or routing restrictions where applicable.

Two devices with the same IP address can produce intermittent and confusing behavior. A successful ping is useful for basic network diagnosis but does not prove that the industrial I/O connection is established.

8.2 Network topology

Common industrial Ethernet topologies include:

  • Line or daisy-chain.
  • Star.
  • Ring.
  • Redundant arrangements supported by the selected protocol and hardware.

The topology must be supported by the actual network devices and protocol configuration.

A line topology can make a cable or downstream-device failure affect devices further along the line. A star topology may isolate individual branch failures more effectively, but depends on the switch and overall architecture. Ring redundancy works only when the required devices and protocol mechanisms are correctly configured.

8.3 Network commissioning checklist

  • Verify cable type and connector suitability.
  • Inspect connector locking and cable strain relief.
  • Confirm port link status and expected link speed.
  • Check the station identity and network address.
  • Verify controller-to-device configuration.
  • Confirm the expected topology.
  • Review diagnostic counters and communication errors.
  • Check for duplicate addressing or incorrect network segmentation.
  • Confirm the I/O update rate is appropriate.
  • Verify the communication-loss response.
  • Test the approved recovery procedure.

9. Remote I/O Module Configuration

The hardware configuration must match the installed modules.

For each station, confirm:

  • Adapter or coupler model.
  • Module order and slot position.
  • Module type and firmware compatibility where relevant.
  • Channel count and channel mode.
  • Digital input voltage and polarity.
  • Digital output type and current rating.
  • Analog input/output range.
  • Temperature input type, if applicable.
  • High-speed or specialized module settings.
  • Process data size and mapping.
  • Diagnostic and substitute-value configuration.

A project may compile successfully while the installed station still has a different physical module arrangement. Hardware comparison and online diagnostics are necessary to detect this class of mismatch.

10. Remote I/O Input Commissioning

Remote digital inputs receive signals from field sensors and switches.

Examples include:

  • Proximity sensors.
  • Photoelectric sensors.
  • Limit switches.
  • Pressure switches.
  • Valve-position feedback.
  • Contactor auxiliary contacts.
  • Robot-ready and machine-ready signals.

10.1 Input commissioning procedure

  1. Confirm the field device tag and the remote I/O station address.
  2. Verify the module type, channel number, and controller tag mapping.
  3. Check the field supply and wiring.
  4. Operate the sensor or apply the approved test condition.
  5. Verify the physical input indicator.
  6. Confirm the corresponding remote I/O process-data bit changes.
  7. Confirm the PLC tag changes as expected.
  8. Verify HMI indication and sequence logic where applicable.
  9. Check the input state after communication interruption, if required.
  10. Record the result.

The physical channel indicator, controller input bit, and HMI display are three separate observations. Comparing them helps isolate the faulty section.

10.2 Example: Proximity sensor

A proximity sensor detects a conveyor component and connects to remote input channel 3.

Expected path:

Component Detected
    ↓
Proximity Sensor Output Turns ON
    ↓
Remote Input Channel 3 Turns ON
    ↓
Remote I/O Process Data Updates
    ↓
PLC Input Tag Turns ON
    ↓
HMI Shows Component Detected

If the sensor indicator changes but the remote input LED does not, investigate the field wiring, supply, module configuration, and input circuit.

If the remote input LED changes but the PLC tag does not, investigate station communication, channel mapping, hardware configuration, and the application tag assignment.

11. Remote I/O Output Commissioning

Remote outputs drive devices such as:

  • Interposing relays.
  • Contactors.
  • Solenoid valves.
  • Indicator lamps.
  • Pneumatic valve manifolds.
  • Compatible actuator interfaces.

Output testing requires greater caution because changing a software bit can create physical movement.

11.1 Output commissioning procedure

  1. Confirm the output tag, station, module, channel, and connected device.
  2. Review the machine sequence, interlocks, and safe test conditions.
  3. Verify output supply, polarity, and load wiring.
  4. Confirm the output type and current rating are suitable.
  5. Use the approved commissioning mode to command the output.
  6. Verify the controller command and remote I/O output indicator.
  7. Check the electrical output at the approved measurement point.
  8. Verify the physical device response.
  9. Check feedback signals and expected timing.
  10. Remove temporary forces or test commands.
  11. Verify the normal sequence and record the result.

Do not force a remote output simply because the HMI button is convenient. First establish that the device cannot move unexpectedly and that all required permits and safeguards are in place.

12. Remote Analog I/O Commissioning

Remote analog modules measure or generate continuous signals, such as 4–20 mA and 0–10 V.

Typical applications include pressure, flow, temperature transmitters, valve positioners, and VFD speed references.

For each remote analog channel, verify:

  • Correct module and channel.
  • Correct input or output mode.
  • Correct electrical range.
  • Correct transmitter or receiving-device range.
  • Correct scaling and engineering units.
  • Correct data mapping between adapter and PLC.
  • Correct signal-quality and diagnostic handling.
  • Correct alarm thresholds.
  • Correct behavior during communication loss.

12.1 Example: Remote pressure transmitter

Assume a 4–20 mA transmitter measures 0–10 bar.

At 12 mA, the expected pressure is:

\[ P = \frac{12-4}{20-4}\times10 = 5\text{ bar} \]

Commissioning should verify the electrical signal at the appropriate test point, the remote module's raw value or diagnostic representation, the PLC engineering value, and the HMI display.

If the module reads correctly but the HMI shows 2.5 bar, investigate the scaling and tag mapping rather than immediately replacing the transmitter.

13. Communication Watchdogs and Fault Behavior

Remote I/O depends on a communication path between the controller and the remote station. The system must define what happens when communication is lost.

A watchdog or connection timeout can detect missing or delayed data exchange.

Possible system responses include:

  • Set outputs to a configured substitute state.
  • Hold the last output state, if explicitly configured and permitted.
  • De-energize outputs.
  • Enter a predefined fault state.
  • Generate a controller alarm.
  • Inhibit automatic operation.
  • Require communication recovery and a deliberate restart.

The correct behavior depends on the process, device, module, and risk assessment. Holding the last output value is not inherently safe, and de-energizing every output is not universally safe either. A pneumatic valve, a clamping device, and a conveyor motor can have very different safe states.

13.1 Communication-loss test

A planned communication-loss test should verify:

  1. The approved test conditions and risk controls.
  2. The intended loss-detection time.
  3. The remote adapter's diagnostic indication.
  4. The controller's communication-fault status.
  5. The configured output substitute or fallback behavior.
  6. The HMI alarm and operator indication.
  7. The recovery sequence after communication returns.
  8. Whether manual acknowledgement or reset is required.
  9. That no unexpected restart or motion occurs.
  10. The recorded test result.

Do not unplug a live industrial network cable on a running machine without an approved test procedure. A small cable is fully capable of creating a large production incident.

14. Diagnostics and Fault Isolation

Remote I/O troubleshooting should follow the data path from the field device toward the controller.

Field Device
    ↓
Field Wiring and Supply
    ↓
Remote I/O Channel
    ↓
Remote I/O Module
    ↓
Station Adapter
    ↓
Industrial Network
    ↓
PLC Hardware Configuration
    ↓
PLC Tag Mapping
    ↓
HMI / SCADA

The objective is to identify the first point where actual behavior differs from expected behavior.

14.1 Common status indicators

Indicator or status Possible meaning Required check
Power LED OFF Missing or incorrect supply Verify supply, fuse, polarity, and terminals
Network link LED OFF No physical network link Check cable, connector, port, and switch
Adapter status fault Configuration, communication, or hardware problem Read device diagnostics and controller status
Module status fault Module-specific configuration or hardware issue Verify module type, slot, and channel diagnostics
Input LED ON but PLC bit OFF Mapping or communication issue Compare process data, module configuration, and PLC tag
Output command ON but output LED OFF Output data not reaching the module or channel fault Check adapter state, output mapping, module diagnostics, and supply
Output LED ON but device inactive Missing load power, wiring fault, failed device, or insufficient output capacity Measure at the approved point and inspect the load circuit
Intermittent station loss Cable, connector, switch, power, EMI, or network configuration issue Review diagnostic counters and inspect the complete network path
Station online but analog value wrong Channel configuration, scaling, wiring, or instrument fault Compare field signal, raw data, and engineering value

LED colors and blink patterns differ between manufacturers. Use the device manual instead of assuming every red light means the same thing across all industrial equipment.

15. Common Remote I/O Faults

Symptom Likely causes Corrective actions
Remote station does not appear online Wrong address, missing device name, wiring fault, no power, configuration mismatch Verify supply, physical link, addressing, identity, and controller configuration
Station is online but I/O data is invalid Incorrect module layout, wrong data mapping, channel configuration fault Compare installed modules with the engineering project
Inputs do not update Field supply missing, wrong channel, wiring fault, communication issue Check sensor, terminal, module LED, adapter diagnostics, and PLC mapping
Outputs do not operate Missing output power, wrong output mapping, interlock, channel fault Verify command path, supply, output type, load, and sequence permissives
Station repeatedly disconnects Cable damage, unstable power, network fault, environmental interference Check power quality, connectors, switch diagnostics, and cable routing
Multiple stations fail together Common switch, power supply, network uplink, or controller issue Identify shared dependencies and inspect the common failure point
Only one module fails Incorrect module, module fault, backplane issue, or local power problem Check module diagnostics and approved replacement procedure
Incorrect analog readings Wrong range, scaling, signal wiring, or field instrument fault Test the complete measurement chain
Device returns online but outputs remain inactive Configured recovery behavior, interlocks, manual reset, or output substitute state Verify the approved recovery sequence and fault-reset requirements
Network appears healthy but response is delayed Excessive communication load, unsuitable update settings, controller load, or device-specific timing Review network and controller diagnostics and configured update intervals

16. Remote I/O Network Capacity and Update Time

The remote I/O communication design must support the required data volume, update rate, and response time.

Factors affecting performance include:

  • Number of remote stations.
  • Total input and output data volume.
  • Network topology.
  • Configured update intervals.
  • Switch performance and network loading.
  • Protocol overhead.
  • Controller task execution time.
  • Device diagnostics and acyclic communication traffic.
  • Motion or time-critical application requirements.

Remote I/O response time is not necessarily equal to the configured network update interval.

A simplified end-to-end response path may include:

\[ T\_{\text{response}} = T\_{\text{input}} + T\_{\text{network,in}} + T\_{\text{controller}} + T\_{\text{network,out}} + T\_{\text{output}} \]

Where each term represents a relevant delay in the signal path. Actual behavior also depends on task scheduling, filtering, protocol behavior, device update timing, and hardware implementation.

For time-critical control, use the manufacturer's timing documentation and the machine's validated response-time requirements rather than relying on a simple estimate.

17. Remote I/O in Automotive Manufacturing

Consider an automotive body-in-white robot cell containing:

  • Proximity sensors for fixture and part detection.
  • Pneumatic clamp valves.
  • Clamp-closed feedback sensors.
  • Pressure transmitters.
  • Robot-ready and station-ready signals.
  • Indicator lamps and auxiliary devices.

A remote I/O station mounted near the fixture can reduce the number of long field cables routed back to the main PLC cabinet.

The PLC receives the sensor data, evaluates permissives and interlocks, and commands the appropriate outputs through the remote station.

17.1 Example operating sequence

Part Detected
    ↓
Fixture Position Confirmed
    ↓
Required Safety and Process Permissives Validated
    ↓
Clamp Command Issued
    ↓
Remote Output Energizes Valve
    ↓
Clamp-Closed Feedback Received
    ↓
Pressure and Process Conditions Verified
    ↓
Station Ready Signal Permitted

The remote I/O station transports input and output data. It does not automatically provide the complete machine sequence or safety logic.

Where safety-related sensors and actuators are involved, the required safety functions must be implemented through an appropriate validated safety architecture. Standard remote I/O must not be assumed to replace safety-rated I/O or safety controllers.

18. Safety-Related Remote I/O

Some remote I/O platforms provide safety-rated modules or safety communication mechanisms. These must be distinguished from standard remote I/O.

Safety-related commissioning may require verification of:

  • Approved safety hardware and firmware.
  • Safety network configuration.
  • Safety addresses or device identifiers.
  • Safety signatures or configuration checksums where applicable.
  • Required diagnostic coverage and fault response.
  • Safe-state behavior.
  • Validation of the complete safety function.
  • Required proof tests and records.

Examples of safety-related functions include emergency-stop response, guard-door monitoring, safe speed monitoring, and prevention of hazardous motion.

The exact requirements depend on the applicable standards, risk assessment, machine architecture, and device certification. A normal network heartbeat is not proof that a safety function is valid.

19. Remote I/O Replacement and Configuration Control

Replacing a remote I/O adapter or module can affect network identity, process-data layout, configuration, and machine behavior.

Before replacement, verify:

  • Exact manufacturer and part number.
  • Hardware revision and supported firmware.
  • Module compatibility.
  • Terminal base and wiring compatibility.
  • Device identity and address requirements.
  • Required configuration files and device descriptions.
  • Input/output data mapping.
  • Channel configuration and diagnostic settings.
  • Power and communication-loss behavior.
  • Required parameters, firmware, and backup files.

After replacement:

  1. Verify the replacement part against the approved configuration.
  2. Apply the correct network identity and configuration.
  3. Confirm the expected module arrangement.
  4. Check adapter and module diagnostics.
  5. Verify input channels individually.
  6. Verify output channels under approved safe conditions.
  7. Confirm analog scaling and specialized functions where applicable.
  8. Test communication-loss and recovery behavior where required.
  9. Confirm normal machine sequence and interlocks.
  10. Record the replacement, configuration changes, and commissioning results.

A station returning online is only one acceptance criterion. The individual I/O channels still require functional verification.

21. Practical Interview Questions and Answers

Q1. What is remote I/O?

Remote I/O is a distributed I/O system in which field signals connect to I/O modules located away from the central controller, with data exchanged over an industrial network.

Q2. What is the difference between remote I/O and a remote PLC?

Remote I/O primarily provides input/output interfaces, while a remote PLC executes a control program. A remote I/O station normally relies on the main controller for its application logic.

Q3. Does an online remote I/O station prove that all channels work?

No. It proves only that the station has reached the relevant communication state. Individual channels, wiring, scaling, data mapping, and device response must be checked separately.

Q4. What is the difference between an IP address and a PROFINET device name?

An IP address is used for IP communication. A PROFINET device name identifies the device within PROFINET configuration and commissioning. Both may be required, and their roles are not interchangeable.

Q5. Why can the input LED turn ON while the PLC input tag remains OFF?

Possible causes include incorrect module configuration, channel-to-tag mapping errors, stale or invalid process data, or a communication problem between the adapter and controller.

Q6. Why might a remote output LED be ON while the actuator does not operate?

The logic command may have reached the output channel, but the field supply may be missing, the wiring may be open, the load may be faulty, or the output may not support the required load.

Q7. What is a communication watchdog?

A watchdog detects missing or delayed communication according to configured timing. Its associated fault behavior determines what the controller and remote outputs do when communication is lost.

Q8. What is GSDML?

GSDML is an XML-based device description format used by PROFINET engineering tools to describe supported device characteristics and configuration options.

Q9. What is an EDS file?

An Electronic Data Sheet describes supported device information and configuration characteristics for compatible EtherNet/IP engineering environments.

Q10. Why must communication-loss behavior be commissioned?

Because the machine must respond predictably when the controller can no longer exchange data with a remote station. The correct response depends on the hazards, process, and approved control design.

Q11. What is the first step when multiple remote stations go offline together?

Investigate common dependencies such as the network switch, uplink, shared power supply, controller interface, and common network configuration before assuming that several stations have independently failed.

Q12. Why is remote I/O useful in automotive manufacturing?

It can reduce long field-cable runs, simplify modular expansion, and place I/O closer to sensors and actuators in robot cells, fixtures, conveyors, and assembly stations.

22. Final Remote I/O Commissioning Checklist

  • Remote I/O adapter and all installed modules match the approved hardware configuration.
  • Supply voltage, field power, polarity, protection, and grounding are verified.
  • Network cabling, connectors, addressing, device identity, and topology are correct.
  • Controller communication is established without relevant active diagnostics.
  • Module order, channel configuration, and process-data mapping are correct.
  • Digital inputs are tested from the field device through to the PLC and HMI.
  • Digital outputs are tested under approved safe conditions.
  • Analog inputs and outputs are checked for electrical range, scaling, and functional response.
  • Network update timing and input/output response meet application requirements.
  • Communication-loss and recovery behavior are verified where required.
  • Safety-related functions are validated through the appropriate safety architecture.
  • Temporary forces, bypasses, and test arrangements are removed.
  • The machine returns to its normal operating state.
  • Commissioning results, deviations, corrective actions, and handover are documented.

Core principle: Remote I/O commissioning verifies both the communication infrastructure and the actual field signal paths. A healthy network, correct module configuration, valid channel data, correct PLC mapping, and predictable fault behavior are all necessary for a reliable distributed automation system.
