1. Definition and purpose

Industrial network documentation is the structured record of a communication network's physical installation, logical configuration, device connections, addressing, protocols, dependencies, test results, and maintenance requirements.

In an industrial automation environment, network documentation connects the electrical installation, PLC programming, IT infrastructure, machine commissioning, maintenance, and troubleshooting activities.

A network may be functioning correctly today but become difficult to maintain when a switch fails, a PLC is replaced, a machine is relocated, or the original engineer leaves. Documentation preserves the knowledge needed to restore or modify the system safely.

The main objectives are:

  • Identify every network device, cable, port, and connection.
  • Record IP addresses, subnet masks, gateways, VLANs, and communication parameters.
  • Understand the relationship between PLCs, HMIs, robots, remote I/O, drives, SCADA servers, and engineering computers.
  • Support breakdown troubleshooting and fault isolation.
  • Maintain network configuration backups and recovery procedures.
  • Control changes and prevent configuration drift.
  • Support commissioning, audits, cybersecurity, and machine handover.
  • Reduce downtime caused by missing or inaccurate technical information.

2. Types of network documentation

Network documentation should describe both the physical network and its logical behaviour.

Document Main purpose Typical contents
Network architecture diagram Shows the overall system structure PLCs, switches, servers, routers, firewalls, network segments
Physical topology diagram Shows actual connections Device ports, cables, patch panels, uplinks
Logical network diagram Shows network relationships Subnets, VLANs, routing, communication zones
IP address register Tracks network addressing Device name, IP, subnet, gateway, MAC address
Cable schedule Tracks physical cables Cable ID, source, destination, type, route
Switch port map Identifies connected endpoints Switch name, port number, VLAN, connected device
Device register Maintains the device inventory Manufacturer, model, serial number, firmware
Protocol register Records industrial communication Protocol, endpoints, ports, configuration
Configuration backup register Tracks recoverable configurations Filename, version, date, checksum, storage location
Commissioning report Records installation verification Tests, results, defects, corrective actions
Change log Tracks approved modifications Previous state, new state, reason, approver
Troubleshooting log Preserves fault history Symptoms, evidence, root cause, corrective action
Recovery procedure Guides restoration after failure Backup location, replacement steps, verification
Network access register Controls administrative access Account ownership, access level, approved storage reference

These documents should be linked by stable device names, cable IDs, switch names, and port identifiers rather than relying on informal labels such as "PLC near the panel."

4. Physical network topology documentation

A physical topology diagram shows how network equipment is connected.

It should identify:

  • Industrial switches and their locations.
  • PLCs, HMIs, robots, CNCs, drives, and remote I/O.
  • Servers, engineering workstations, gateways, and firewalls.
  • Uplink and backbone connections.
  • Fibre-optic connections and transceivers.
  • Switch port numbers.
  • Cable IDs.
  • Redundant paths and ring connections.
  • Connections between control panels and machine stations.

4.1 Example

                 Plant Network
                      |
                 Core Switch
                      |
                Fibre Uplink
                      |
              Industrial Switch SW-01
                 /      |       \
                /       |        \
          Port 01   Port 02    Port 03
             |         |          |
           PLC-01    HMI-01     Robot-01
             |
         Port/Module
             |
          Remote IO

This is a simplified illustration. A real drawing should show the actual interfaces, intermediate devices, cable IDs, and redundant links where present.

4.2 Why physical topology matters

Suppose PLC-01 loses communication with HMI-01. A physical topology diagram helps determine whether they share a switch, depend on an uplink, or connect through another network device.

It also helps distinguish an endpoint fault from a switch, cable, fibre, or backbone fault.

5. Logical network documentation

A logical diagram explains how devices communicate regardless of their physical placement.

It should document:

  • IP subnets and address ranges.
  • VLAN assignments.
  • Layer 3 gateways and routing boundaries.
  • Communication zones.
  • Firewall boundaries and permitted traffic.
  • Remote-access paths.
  • Industrial protocols and dependencies.
  • Redundant logical paths, where applicable.
  • Network management and monitoring systems.

5.1 Example of logical segmentation

Plant IT Network
       |
   Firewall
       |
Industrial DMZ
       |
Controlled Industrial Firewall
       |
Control Network VLAN
       |
   PLC / HMI
       |
Machine Network VLAN
       |
Remote I/O / Robot / Drive

This is an illustrative architecture, not a universal design. Some machine networks are flat, while others use routed VLANs, cell-zone boundaries, or separate safety and control network arrangements.

Important: VLANs provide logical separation, but VLAN membership alone is not a complete security boundary. Routing, access-control rules, switch configuration, and the overall security design determine what traffic can pass.

7. IP address register

The IP address register should make addressing conflicts and device replacement errors easier to detect.

Recommended fields include:

  • Device ID.
  • Device name.
  • IPv4 address or IPv6 address, where used.
  • Subnet mask or prefix length.
  • Default gateway, where applicable.
  • VLAN.
  • MAC address.
  • Address assignment method.
  • DHCP reservation or static assignment details.
  • DNS hostname, where applicable.
  • Approved address range.
  • Address owner or responsible team.
  • Verification date.

7.1 Example

Device ID IP address Subnet mask VLAN Assignment
PLC-01 10.20.1.10 255.255.255.0 101 Static
HMI-01 10.20.1.20 255.255.255.0 101 Static
ENG-PC-01 10.20.1.30 255.255.255.0 101 Approved static
SCADA-01 10.20.2.10 255.255.255.0 102 Static

These are example addresses only. Use the actual approved site addressing plan.

7.2 Address assignment methods

  • Static addressing: The address is configured directly on the device.
  • DHCP: The address is assigned dynamically by a DHCP server.
  • DHCP reservation: A server assigns a planned address based on a defined client identity, often a MAC address.
  • Link-local addressing: A device uses an address from a link-local range when supported and applicable.

Document the actual method. A device that appears to have a fixed address may actually depend on a reservation, vendor configuration tool, or another address-assignment mechanism.

7.3 Avoid duplicate IP addresses

A duplicate address can cause intermittent or persistent communication failures.

Before assigning or changing an address:

  1. Check the approved address register.
  2. Confirm the correct subnet and VLAN.
  3. Verify the intended address is available using approved network tools.
  4. Check DHCP scopes and reservations where relevant.
  5. Apply the change under the site's change-control procedure.
  6. Verify the device and update the register.

A successful ping does not guarantee that an address is unique or that every relevant endpoint is reachable.

8. Cable schedule and port mapping

The cable schedule records physical connectivity. The port map records where each cable terminates on network equipment.

These records should be consistent with the physical topology drawing.

8.1 Example cable schedule

Cable ID Source Destination Cable type Purpose

NET-002 SW-01 Port 02 HMI-01 Ethernet 1 Industrial Cat 6 HMI connection
NET-003 SW-01 Port 03 Robot-01 Port 1 Industrial Ethernet Robot connection
NET-004 SW-01 SFP 1 SW-02 SFP 1 Fibre optic Switch uplink

The cable types in this example are illustrative. Record the actual cable category, fibre type, connector, length, and other required characteristics.

8.2 Example switch port map

Switch Port Connected device VLAN Link status
SW-01 01 PLC-01 101 Verified up
SW-01 02 HMI-01 101 Verified up
SW-01 03 Robot-01 101 Verified up
SW-01 SFP 1 SW-02 Trunk as configured Verified up

Record the actual configuration rather than assuming every device port is an access port or every uplink is a trunk. A link-state value should include the date or verification context if it may change.

9. VLAN and subnet documentation

VLANs and IP subnets are related but different concepts.

  • A VLAN defines a Layer 2 broadcast domain.
  • An IP subnet defines an IP addressing range and associated network boundary.
  • A trunk carries traffic for multiple VLANs using a configured tagging method.
  • An access port typically carries traffic for one assigned data VLAN, subject to the switch configuration.
  • A gateway provides Layer 3 forwarding between networks when configured and permitted.

A network register should record VLAN ID, VLAN name, purpose, subnet, gateway, DHCP scope if used, routed interfaces, and approved communication paths.

Do not assume that the VLAN number must equal part of the IP address. Some organisations choose a naming convention that links them, but it is not a technical requirement.

10. Industrial protocol register

Industrial networks often carry multiple protocols. Documentation should identify which endpoints communicate, which protocol is used, and what the communication depends on.

Protocol Typical use Documentation items
EtherNet/IP PLCs, drives, remote I/O, industrial devices Controller, adapter, connection configuration, RPI where applicable
PROFINET PLCs and distributed field devices Controller, device name, IP configuration, topology, update settings
Modbus TCP PLCs, instruments, gateways Client/server roles, unit identifiers where relevant, register mapping
OPC UA Data exchange between automation and supervisory systems Endpoint, security policy, certificates, authentication, namespace
SNMP Network monitoring and device management Version, permitted managers, access policy, monitored objects
NTP Time synchronisation Time source, clients, time zone and clock policy
DNS Hostname resolution DNS servers, hostnames, required records
DHCP Dynamic IP configuration Scope, reservations, lease policy, authorised server

Do not record passwords, private keys, or other secrets directly in an ordinary protocol register. Record the approved credential vault or secure repository reference instead.

11. Switch configuration documentation

Managed switches can contain important configuration that is not visible from a simple physical diagram.

Document the relevant settings, including:

  • Hostname and asset ID.
  • Management IP address and subnet.
  • Firmware version.
  • VLAN definitions.
  • Port mode and VLAN membership.
  • Trunk allowed-VLAN configuration.
  • Link speed and duplex settings where configured.
  • Spanning Tree configuration.
  • Ring or redundancy protocol configuration.
  • Link aggregation configuration.
  • Port security and access-control settings.
  • SNMP and management access restrictions.
  • Syslog, NTP, and monitoring destinations.
  • Configuration backup filename and version.
  • Recovery and replacement procedure.

Store the actual configuration export when the switch supports it. A summary spreadsheet is useful for searching but cannot replace the full configuration backup.

11.1 Switch configuration backup procedure

  1. Identify the switch and confirm administrative authorisation.
  2. Record the model, serial number, firmware, and management address.
  3. Export the configuration using the vendor-supported method.
  4. Confirm that the export completed successfully.
  5. Store the file in the approved access-controlled repository.
  6. Record the filename, date, version, and checksum if required.
  7. Verify that the backup can be retrieved and interpreted.
  8. Test restoration only through an approved procedure and suitable test environment.

A backup that exists but cannot be restored is merely an optimistic file.

12. PLC, HMI, robot, and drive network settings

Network documentation should capture the communication settings relevant to each automation device.

PLC

  • Controller model and firmware.
  • Ethernet interface identification.
  • IP address and subnet.
  • Device name, where applicable.
  • Configured connections and communication dependencies.
  • Remote I/O and drive endpoints.
  • Relevant network modules and firmware.
  • Approved project backup reference.

HMI and SCADA

  • IP address and subnet.
  • PLC or server endpoints.
  • Communication driver and protocol.
  • Redundant server configuration, if present.
  • DNS and time synchronisation dependencies.
  • Alarm and data logging dependencies where network services are involved.

Industrial robot

  • Controller model and software version.
  • Network interface and IP configuration.
  • PLC communication protocol.
  • I/O mapping reference.
  • Safety-related communication configuration where applicable.
  • Approved backup and recovery reference.

VFD and servo drive

  • Drive model and firmware.
  • Ethernet interface or communication module.
  • IP address and device name where applicable.
  • PLC connection details.
  • Cyclic I/O or parameter-access configuration.
  • Required update rates and timeouts.
  • Configuration backup reference.

Network documentation must distinguish ordinary control communication from safety-related communication. Safety functions require the applicable design, validation, and change-control records; an IP address register is not sufficient evidence of safety compliance.

13. Network architecture and segmentation records

For larger production systems, record the network's functional zones and the permitted connections between them.

Examples of zones include:

  • Enterprise IT.
  • Industrial DMZ.
  • Supervisory systems.
  • Manufacturing operations.
  • Machine control.
  • Engineering and maintenance access.
  • Network management.

The documentation should identify:

  • Which devices belong to each zone.
  • Which devices route between zones.
  • Where firewalls are installed.
  • Which traffic is permitted and why.
  • Which remote-access methods are approved.
  • Which services are exposed to other networks.
  • Who owns and reviews each access rule.

A useful rule record includes the source zone, destination zone, source and destination endpoints, protocol, port where applicable, purpose, owner, approval, and review date.

14. Network backup and recovery documentation

Industrial network recovery is not limited to restoring a switch configuration. It may require restoring dependencies across several systems.

A recovery package may include:

  • Network topology drawings.
  • IP and VLAN registers.
  • Switch configuration exports.
  • Firewall configuration backups where authorised.
  • PLC, HMI, robot, and drive backup references.
  • Firmware and hardware compatibility details.
  • Device replacement procedures.
  • Required engineering software versions.
  • Approved licences and installation media references.
  • Recovery and commissioning checklists.
  • Escalation contacts and vendor support details.

14.1 Recovery sequence example

Identify failed device
        ↓
Verify the fault and affected connections
        ↓
Obtain approved replacement hardware
        ↓
Confirm model and firmware compatibility
        ↓
Restore approved configuration
        ↓
Verify physical and logical network settings
        ↓
Test device and protocol communication
        ↓
Run machine functional checks
        ↓
Record recovery and update asset records

The exact sequence depends on the failed device and the machine's risk controls. Do not restore configurations or reconnect equipment to a live production network without appropriate approval.

15. Change management and configuration control

Every network change that can affect production should be controlled and traceable.

Examples include:

  • Changing a PLC or HMI IP address.
  • Replacing an industrial switch.
  • Adding a VLAN.
  • Modifying a trunk or access port.
  • Changing a firewall rule.
  • Updating switch firmware.
  • Moving a cable to a different port.
  • Replacing a robot communication module.
  • Changing an industrial protocol connection or update setting.

15.1 Minimum change record

Field Required information
Change ID Unique reference
Requester Person or team requesting the change
Reason Fault correction, upgrade, expansion, or security
Affected assets Devices, ports, cables, and applications
Previous state Verified existing configuration
Proposed state Exact intended modification
Risk and impact Production, safety, security, and recovery impact
Approval Required authorised approvals
Implementation Actual action and completion time
Verification Tests and results
Rollback Approved recovery method
Documentation update Drawings, registers, and backups revised

Record the actual final state, including any deviation from the original plan.

15.2 As-designed versus as-built documentation

  • As-designed: The approved intended design.
  • As-built: The verified installation after implementation.

The as-built record must reflect what is actually installed. If a contractor moves a connection to another switch port during commissioning, the final documentation must be updated rather than leaving the planned drawing unchanged.

16. Network documentation for troubleshooting

Documentation is most valuable when it helps isolate a fault quickly.

Example: Remote I/O communication failure

A PLC reports a communication fault with remote I/O.

Use the documentation to determine:

  1. The remote I/O device's identity and physical location.
  2. Its expected IP address and subnet.
  3. Its switch and port connection.
  4. The cable ID and route.
  5. The relevant VLAN and switch port configuration.
  6. The expected protocol and connection settings.
  7. The last known configuration and recent changes.
  8. The approved backup and replacement procedure.

Then check physical link status, switch port counters, device diagnostics, IP reachability where applicable, and protocol-specific status.

A successful ping does not prove that an industrial protocol connection is healthy. Conversely, a failed ping does not always prove that the device is unavailable, because some devices restrict or disable ICMP responses.

17. Documentation quality and revision control

Documentation becomes unreliable when files are duplicated, outdated, inconsistently named, or edited without traceability.

Recommended controls include:

  • One approved repository for controlled documents.
  • Consistent asset names and cable identifiers.
  • Document numbers and revision identifiers.
  • Revision history and approval records.
  • Read access for relevant maintenance personnel.
  • Restricted write access for controlled configurations.
  • Periodic verification of high-criticality assets.
  • Backup and retention policies.
  • Clear identification of obsolete documents.
  • Traceable links between drawings, device registers, and change records.

17.1 Example file naming convention

AREA_DOCUMENTTYPE_ASSET_REVISION_DATE

LINE01_NETWORK_TOPOLOGY_ALL_R03_20261015
LINE01_IP_REGISTER_ALL_R02_20261015
LINE01_SWITCH_CONFIG_SW01_R04_20261015
LINE01_COMMISSIONING_REPORT_ALL_R01_20261015

This is an example naming convention. Follow the organisation's formal document-control rules where they already exist.

Avoid ambiguous filenames such as final_new_latest2.xlsx. Humans have somehow made file naming a recurring industrial hazard.

18. Cybersecurity and sensitive information

Network documentation is operationally valuable, but it can also reveal information useful to an attacker.

Protect sensitive details such as:

  • Detailed network diagrams.
  • Management interfaces and administrative addresses.
  • Firewall rules and remote-access paths.
  • Firmware versions and known vulnerabilities.
  • Configuration exports.
  • Credentials, keys, and certificates.
  • Production device inventories.

Use access control, secure storage, approved transfer methods, and appropriate retention policies.

Never place passwords, private keys, recovery codes, or other authentication secrets in an ordinary spreadsheet or unprotected drawing. Use the approved secret-management system and reference it securely.

For configuration backups, consider integrity checks, version history, access logs, and offline or otherwise protected copies where required by site policy.

20. Integrating documentation with maintenance systems

For a maintenance team, network records become more useful when connected to equipment and breakdown history.

A practical integration can link:

  • Equipment ID.
  • Network device ID.
  • Switch and port.
  • Cable ID.
  • SAP functional location or equipment record.
  • Breakdown notification.
  • Work order.
  • Spare part and approved replacement model.
  • Configuration backup.
  • Latest test result.
  • Root-cause analysis.
  • Corrective action.
  • Change request.

Example:

A robot controller loses communication because of a damaged Ethernet cable. The maintenance record should identify the controller, switch port, cable ID, fault symptoms, test evidence, corrective action, replacement cable specification, and final verification.

Where SAP or another CMMS is used, avoid maintaining conflicting versions of the same asset identity across disconnected spreadsheets. Define which system is authoritative for each data type.

21. Useful network documentation KPIs

Documentation quality can be measured rather than judged by how impressive the folder structure looks.

KPI Calculation or measurement Purpose
Asset documentation coverage Documented in-scope assets / Total in-scope assets × 100% Measures inventory completeness
Port mapping coverage Verified mapped ports / In-scope ports × 100% Measures connectivity traceability
Backup coverage Devices with valid required backups / Devices requiring backups × 100% Measures recovery readiness
Backup restore verification Backups successfully restore-tested / Backups selected for restore testing × 100% Measures recoverability
Documentation freshness Records verified within the required interval / Records due for verification × 100% Measures currency
Change update compliance Completed changes with updated records / Completed changes requiring updates × 100% Measures change traceability
Mean time to identify network fault Average elapsed time from fault report to fault isolation Measures troubleshooting effectiveness

Define the population, target, and measurement interval before comparing KPI values. A high documentation coverage percentage does not prove that the records are accurate.

22. Practical implementation plan

For a production line with PLCs, HMIs, robots, drives, and managed switches, build the documentation in a sequence that reduces rework.

  1. Establish unique names for network assets.
  2. Create the device register.
  3. Verify the actual IP addresses, subnets, VLANs, and device names.
  4. Walk down the installation and map switch ports.
  5. Identify cable IDs and verify both endpoints.
  6. Draw the physical topology.
  7. Draw the logical topology and network zones.
  8. Record relevant industrial protocols and communication dependencies.
  9. Collect approved switch and device configuration backups.
  10. Record commissioning and cable-test results.
  11. Define recovery procedures for critical devices.
  12. Establish change-control and revision-management rules.
  13. Review the records with maintenance, automation, IT/OT, and relevant equipment owners.
  14. Store the approved documents in the controlled repository.
  15. Periodically verify the highest-risk and most critical records.

During an initial survey, distinguish verified facts from assumptions. Mark unknown connections as unverified and resolve them using approved inspections and tests.

23. Network documentation handover checklist

Inventory and addressing

  • All in-scope network devices are recorded.
  • Device IDs and locations are unique and unambiguous.
  • IP addresses, subnet masks, gateways, and VLANs are verified.
  • Static addresses, reservations, and DHCP dependencies are documented.
  • Firmware and hardware details are recorded where required.

Physical and logical connectivity

  • Physical topology matches the installed network.
  • Logical topology shows relevant subnets and communication boundaries.
  • Cable IDs and both endpoints are recorded.
  • Switch port maps are verified.
  • Fibre paths, transceivers, and polarity are documented where applicable.
  • Redundant links and network dependencies are shown.

Configuration and recovery

  • Relevant switch configurations are backed up.
  • PLC, HMI, robot, and drive backup references are available.
  • Backup dates, versions, and storage locations are recorded.
  • Recovery procedures identify compatible replacement hardware.
  • Required restoration and verification steps are documented.
  • Sensitive configuration data is stored securely.

Testing and control

  • Required commissioning tests are recorded.
  • Outstanding defects and deviations are listed.
  • Approved changes are reflected in the as-built records.
  • Document revisions and approvals are traceable.
  • Maintenance personnel can access the approved documents.
  • Ownership and periodic review responsibilities are assigned.

24. Interview questions and answers

1. What is industrial network documentation?

It is the controlled record of network devices, cabling, addressing, topology, protocols, configurations, testing, backups, and changes required to operate and maintain an industrial communication network.

2. What is the difference between a physical and logical topology?

A physical topology shows the actual devices, ports, and cable connections. A logical topology shows network relationships such as subnets, VLANs, routing, and communication boundaries.

3. What is the purpose of an IP address register?

It provides a verified record of device addresses and related network settings, helping prevent duplicate addresses and supporting troubleshooting and device replacement.

4. Why are cable schedules and port maps important?

They allow maintenance personnel to trace a connection from an endpoint to the relevant cable and switch port without relying on guesswork or unnecessary disconnections.

5. What is the difference between as-designed and as-built documentation?

As-designed documentation records the approved intended design. As-built documentation records the verified installation after commissioning and modifications.

6. Why should switch configurations be backed up?

They preserve settings such as VLANs, port modes, redundancy, management access, and monitoring configuration, reducing recovery time after device failure or configuration loss.

7. Does a successful ping prove that an industrial network is healthy?

No. Ping primarily checks IP-level reachability using ICMP when supported and permitted. It does not prove that the required industrial protocol, cyclic I/O, application data, or real-time performance is functioning correctly.

8. Why must network changes be documented?

Changes can affect production communication, security, redundancy, and recovery. A traceable change record supports verification, troubleshooting, and rollback.

9. What is a network configuration baseline?

It is the approved reference configuration for a defined network device or system, against which subsequent changes and configuration drift can be assessed.

10. What makes network documentation useful during a breakdown?

It must be accurate, accessible, current, and linked to the installed devices. It should identify endpoints, ports, addressing, dependencies, recent changes, backups, and verification procedures.

25. Final engineering principles

  • Document the installed network, not merely the original design.
  • Use consistent device IDs, cable IDs, switch names, and port identifiers.
  • Keep physical topology, logical topology, IP registers, and port maps consistent.
  • Record protocol dependencies and configuration details needed for troubleshooting.
  • Maintain approved configuration backups and practical recovery procedures.
  • Protect sensitive network information and authentication secrets.
  • Update documentation after every approved change that affects the network.
  • Verify records physically and logically instead of assuming that old documents remain correct.
  • Measure documentation quality through completeness, accuracy, freshness, and recoverability.
  • Treat network documentation as a living maintenance asset, not a commissioning formality.

Core principle: A well-documented industrial network makes every important connection traceable, every critical configuration recoverable, and every network change verifiable.
