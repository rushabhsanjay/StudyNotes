1. Definition and purpose

Port mapping in industrial Ethernet installation is the systematic identification and documentation of which physical network port connects to which device, cable, network segment, or communication partner.

In a factory automation system, port mapping helps maintenance engineers determine where a PLC, HMI, robot controller, remote I/O adapter, industrial PC, VFD, or SCADA connection is physically connected and how that connection is configured.

The term has several meanings depending on context:

  • Physical switch port mapping: Identifying which device is connected to each switch port.
  • Network topology mapping: Recording how switches, devices, and links connect.
  • VLAN and configuration mapping: Recording the VLAN, speed, duplex, redundancy role, and other relevant settings associated with a port.
  • Application port mapping: Identifying TCP or UDP port numbers used by a service, such as an industrial communication protocol.
  • NAT or port forwarding: Translating network addresses or transport-layer ports between network boundaries.

This topic primarily covers physical Ethernet port mapping and its relationship to network configuration, with application port mapping and NAT explained separately to avoid confusing unrelated concepts.

The objectives are to:

  • Trace connections quickly during breakdowns.
  • Prevent accidental disconnection of the wrong device.
  • Verify installation against network drawings.
  • Support commissioning and acceptance testing.
  • Identify unused, incorrectly connected, or misconfigured ports.
  • Improve fault diagnosis and equipment replacement.
  • Maintain accurate as-built documentation.

2. Basic port mapping terminology

Term Meaning
Physical port A physical Ethernet interface or connector
Switch port An Ethernet interface on a network switch
Device interface A network interface on a PLC, HMI, PC, or other device
Port map A record of connections and relevant port configuration
Uplink A connection from a switch toward another switch or network device
Downlink A connection from a switch toward an endpoint or lower-level network
Patch panel port A numbered termination point used to organise cabling
VLAN A logical Layer 2 network segment
Access port A switch port configured to carry traffic for an assigned VLAN in a typical VLAN design
Trunk port A switch port configured to carry multiple VLANs using a supported tagging arrangement
MAC address table A switch table associating learned MAC addresses with switch ports and VLANs
TCP/UDP port A transport-layer endpoint number used by network applications
NAT Network Address Translation
Port forwarding A rule that directs matching traffic to a specified destination, commonly using NAT
LLDP Link Layer Discovery Protocol, used by compatible devices to advertise and discover neighbouring devices
SPAN or port mirroring A switch feature that copies selected traffic to a monitoring port, where supported

A physical Ethernet port and a TCP/UDP port number are not the same thing. A switch port labelled 05 is a physical interface; TCP port 44818 is a transport-layer port number commonly associated with EtherNet/IP explicit messaging.

3. Physical port mapping architecture

A typical industrial network may contain several layers of physical connections.

PLC Ethernet interface
        ↓
Machine cabinet switch port
        ↓
Managed industrial switch
        ↓
Uplink or fibre connection
        ↓
Line-level switch
        ↓
Plant network or approved gateway
        ↓
SCADA or monitoring system

The physical path should be recorded along with the relevant device tags and interface names.

For a simple machine cell, the port map might include:

  • PLC Ethernet port to switch port 1.
  • HMI Ethernet port to switch port 2.
  • Robot controller port to switch port 3.
  • Remote I/O adapter to switch port 4.
  • Uplink to another switch through port 8.

These assignments are examples only. The actual map must reflect the installed equipment and the approved network design.

4. Physical switch port mapping

A switch port map records which device is connected to each physical switch interface.

Example:

Switch tag Port Connected device Device interface Cable ID
SW-C01-01 1 PLC-C01 X1 NET-C01-001
SW-C01-01 2 HMI-C01 LAN1 NET-C01-002
SW-C01-01 3 ROBOT-C01 Ethernet port 1 NET-C01-003
SW-C01-01 4 RIO-C01 Ethernet port 1 NET-C01-004
SW-C01-01 8 SW-LINE-01 Uplink interface NET-C01-008

This table should be updated whenever an approved physical connection changes.

Important practices

  • Use the switch's actual printed port numbering.
  • Record both endpoints of every important link.
  • Distinguish copper ports from fibre transceiver interfaces.
  • Record the actual interface names on PLCs and other devices.
  • Identify uplinks and redundant links clearly.
  • Record unused ports where required by site policy.
  • Keep the port map consistent with the cable schedule and network diagram.

Do not assume that the switch's port numbering starts at zero or that fibre interfaces are numbered in the same sequence as copper ports. Verify the manufacturer's physical layout.

5. Why port mapping matters in industrial maintenance

Port mapping is particularly valuable when multiple machines and automation devices share a cabinet or network.

Consider a PLC that has lost communication with a remote I/O adapter. The fault could involve the cable, switch port, VLAN, remote I/O configuration, device power, or a protocol-specific issue.

A correct port map lets the engineer identify the intended connection and investigate the right components without disconnecting unrelated equipment.

Common applications include:

  • PLC and remote I/O communication failures.
  • HMI-to-PLC connection faults.
  • Robot-controller network issues.
  • VFD and servo-drive communication problems.
  • Switch replacement and network expansion.
  • Fibre uplink faults.
  • Commissioning and machine relocation.
  • Network segmentation changes.
  • Network configuration audits.

Port mapping does not itself prove that communication is working. It establishes what should be connected and provides a reliable starting point for testing.

6. Mapping PLC, HMI, robot, and remote I/O connections

Industrial devices may contain more than one Ethernet interface. Each interface should be mapped individually where the distinction matters.

Device Interface information to record Important consideration
PLC CPU port or communication module and interface name Some controllers have embedded switches or multiple logical interfaces
HMI Physical LAN interface Confirm the PLC destination and any separate service interface
Robot controller Interface and assigned network role Separate robot-control and plant-monitoring interfaces where provided
Remote I/O Adapter port or integrated switch ports Confirm whether ports support line topology or device-level ring features
VFD Ethernet interface or communication adapter Verify supported protocol and network configuration
Industrial PC NIC name and physical port Multiple NICs can connect to different subnets
Managed switch Physical port number and management interface The management IP is separate from the physical port mapping
Firewall or gateway Interface names and network zones Record permitted paths and routing relationships as appropriate

Multiple ports on one device

Some devices offer two Ethernet ports with an integrated switch. These ports may support a line topology or protocol-specific redundancy arrangement.

Other devices have separate interfaces that serve different networks.

Never assume that two Ethernet ports on the same device are interchangeable. Check the hardware documentation, project configuration, and network design.

7. Port mapping and VLAN configuration

A port map should capture VLAN configuration when VLANs are used.

An Ethernet switch can physically connect devices while preventing the intended communication because the ports are assigned to incompatible VLANs or the trunk configuration is incorrect.

Example:

Switch port Connected device Port mode VLAN
1 PLC-C01 Access 10
2 HMI-C01 Access 10
3 ROBOT-C01 Access 10
8 SW-LINE-01 Trunk 10, 20

The VLAN IDs and port modes are illustrative. The correct configuration depends on the approved design and switch capabilities.

Access port

An access port typically carries traffic for one assigned VLAN. The connected endpoint generally sends and receives ordinary untagged Ethernet frames unless the design specifies otherwise.

Trunk port

A trunk carries traffic for multiple VLANs using VLAN tagging where configured and supported. Native VLAN behaviour and allowed VLAN lists vary by switch configuration.

Troubleshooting VLAN-related failures

Check:

  • Whether both endpoints belong to the intended Layer 2 network.
  • The VLAN assigned to each access port.
  • The allowed VLAN list on trunk ports.
  • Native VLAN settings where applicable.
  • Whether the connected device sends tagged or untagged frames as expected.
  • Whether routing is available when communication crosses subnets.
  • Whether access-control policies permit the required traffic.

VLANs do not automatically provide complete security. Their effectiveness depends on correct configuration and the surrounding network architecture.

8. Port mapping and managed switch diagnostics

Managed switches provide useful information for comparing the documented port map with the actual network.

Depending on the model, the switch may provide:

  • Link state.
  • Link speed and duplex.
  • Traffic counters.
  • Error and discard counters.
  • Learned MAC addresses.
  • VLAN membership.
  • LLDP neighbour information.
  • Redundancy protocol status.
  • Port mirroring or packet capture support.
  • Event and diagnostic logs.

8.1 Link state

A port may report states such as:

  • Up: A physical link has been established.
  • Down: No active physical link is detected.
  • Disabled or administratively down: The port has been disabled through configuration.
  • Blocked or alternate: A redundancy or loop-prevention mechanism may prevent normal forwarding.

The exact status names vary by vendor and feature.

8.2 Link speed and duplex

A port may negotiate at 10, 100, or 1000 Mbps, or another supported rate. Duplex and negotiation capabilities depend on the interfaces and configuration.

If a port operates at an unexpected speed, investigate the endpoint capabilities, cable quality, transceiver compatibility, and port settings.

Do not force speed or duplex settings without checking both ends and the equipment requirements.

8.3 Error counters

Error counters may reveal:

  • Physical-layer problems.
  • Cable or connector faults.
  • Transceiver issues.
  • Duplex mismatches on equipment that permits them.
  • Congestion-related drops.
  • Interface or hardware faults.

Counters should be interpreted with their definitions and trend over time. A nonzero lifetime counter alone does not establish that a fault is currently active.

9. MAC address tables and port identification

Managed Ethernet switches commonly learn source MAC addresses and associate them with switch ports within a VLAN.

This table can help identify which port currently reaches a device.

Example:

VLAN Learned MAC address Switch port
10 00:11:22:33:44:55 1
10 00:11:22:33:44:66 2
10 00:11:22:33:44:77 3

These MAC addresses are illustrative.

How to use the table

  1. Obtain the expected device MAC address from the device configuration or label.
  2. Locate the address in the switch's MAC table.
  3. Confirm the VLAN associated with the entry.
  4. Identify the physical port where the address was learned.
  5. Compare the result with the port map.
  6. Investigate unexpected differences.

Limitations

  • The table may age out inactive entries.
  • A device behind another switch may appear through an uplink rather than an endpoint port.
  • Multiple MAC addresses may appear on a port connected to another switch or a device with an integrated bridge.
  • A virtualised PC or multi-interface device may expose multiple MAC addresses.
  • MAC addresses can move when cabling or network topology changes.

A MAC table provides evidence of observed Layer 2 learning, not a complete and permanent inventory of all devices.

10. LLDP and automatic neighbour discovery

LLDP is a Layer 2 protocol that allows compatible network devices to advertise information about themselves and discover directly connected neighbours.

A managed switch may display neighbour information such as:

  • Device identity.
  • Port identity.
  • System name.
  • Supported capabilities.
  • Management address, if advertised.

This can help compare the actual connection with the documented port map.

However, LLDP support and visibility depend on the connected device, firmware, configuration, and network policy. Some industrial devices may use vendor-specific discovery mechanisms instead.

Do not assume that the absence of LLDP information means the cable or device is faulty.

11. Physical port mapping versus TCP/UDP port mapping

These concepts must be kept separate.

Aspect Physical switch port mapping TCP/UDP port mapping
Example Switch port 5 connects to PLC Ethernet port X1 TCP destination port 44818
Layer Physical and data-link aspects of the network Transport layer
Identifies A physical network connection An application endpoint on a host
Common tool Switch interface status, cable schedule, LLDP Firewall rules, socket diagnostics, application configuration
Typical fault Wrong cable or switch port Blocked port, unavailable service, wrong destination port
Documentation Switch port map and cable schedule Protocol and service matrix

A device can have a correct physical connection but still fail to communicate because the required TCP or UDP service is blocked or unavailable.

Conversely, an application service may be configured correctly while the physical cable is connected to the wrong switch port or VLAN.

12. Common industrial protocol port awareness

Some industrial protocols use recognisable TCP or UDP port numbers. These can be useful during troubleshooting, but they must be verified against the specific implementation and configuration.

Protocol or service Common port Transport Notes
EtherNet/IP explicit messaging 44818 TCP and UDP usage depends on function UDP is also used for discovery and other protocol functions
EtherNet/IP I/O messaging 2222 UDP Commonly used for implicit I/O traffic
Modbus TCP 502 TCP Confirm the server and client configuration
PROFINET No single universal TCP/UDP port Multiple Ethernet and IP-related mechanisms Real-time communication includes Layer 2 mechanisms
OPC UA 4840 TCP commonly The configured endpoint can use a different port
HTTP 80 TCP Use only where permitted and required
HTTPS 443 TCP Common secure web service port
DNS 53 UDP and TCP Usage depends on query type and response behaviour
DHCPv4 67 and 68 UDP Server and client ports, respectively

These are common defaults, not a complete protocol specification. Industrial protocols may use additional ports, multicast, broadcast, or Layer 2 traffic that ordinary TCP/UDP port filtering does not fully describe.

Do not open every listed port by default. Permit only the traffic required by the approved architecture.

13. NAT and port forwarding awareness

NAT changes IP addressing information as traffic passes through a network device. Port forwarding is a common form of destination translation that directs matching traffic to a specified internal host and service.

These concepts are not the same as physical switch port mapping.

In industrial environments, NAT may be used to connect machine networks that reuse address ranges or to provide controlled access through a gateway. The design must account for routing, return traffic, application behaviour, and security.

Potential issues include:

  • Incorrect translation rules.
  • Overlapping subnets.
  • Applications embedding IP addresses in payloads.
  • Protocols that use dynamically negotiated connections.
  • Inbound access rules that expose equipment unnecessarily.
  • Return traffic taking an unexpected route.

Do not create ad hoc port-forwarding rules to make a PLC or robot accessible from a wider network. Use an approved architecture with access control, monitoring, and appropriate remote-access protections.

14. Port mapping and network redundancy

Industrial networks may use redundant links or protocols to improve availability.

Examples include:

  • Rapid Spanning Tree Protocol (RSTP).
  • Media Redundancy Protocol (MRP), where supported.
  • Device Level Ring (DLR), where supported.
  • Vendor-specific redundancy mechanisms.

The port map should identify redundant links and their roles when relevant.

Example:

PLC-C01
   ↓
SW-C01-01 port 1
   ↓
Primary network path

SW-C01-01 port 8
   ↓
Redundant ring or uplink connection

This simplified example does not define a complete redundancy topology.

Important precautions

  • Confirm which ports are intended for redundant links.
  • Record the relevant redundancy protocol and configuration.
  • Do not create an unplanned loop by connecting an extra cable.
  • Confirm that the switch and endpoints support the intended redundancy method.
  • Verify failover behaviour during an approved test.
  • Record recovery behaviour and any remaining single points of failure.

A second cable does not automatically provide redundancy. The network must be designed and configured to handle it safely.

15. Commissioning procedure for port mapping

Step 1: Review the design

Collect the network topology, cable schedule, device list, IP register, and switch configuration.

Step 2: Identify the hardware

Record the switch model, switch tag, port count, interface types, and relevant device interfaces.

Step 3: Trace physical connections

Use the endpoint labels, cable IDs, and physical route to identify the source and destination of each cable.

Step 4: Verify switch-port assignment

Compare the actual connected device with the planned port map. Use switch diagnostics where available.

Step 5: Record configuration

Capture relevant port properties such as:

  • VLAN and port mode.
  • Speed and duplex.
  • Link status.
  • Redundancy role.
  • Port security or access restrictions.
  • Fibre transceiver and media details where applicable.

Step 6: Test communication

Verify physical link, local network reachability, and the required application communication.

A link LED or successful ping is not sufficient to prove that every application requirement is satisfied.

Step 7: Correct discrepancies

Investigate incorrect connections and configuration differences. Obtain the required approval before making changes to production equipment.

Step 8: Update documentation

Update the port map, cable schedule, network diagram, and change record.

Step 9: Handover

Confirm that the final documentation matches the verified installation and that unresolved defects are recorded.

16. Troubleshooting using port mapping

Symptom Checks Possible causes
Switch port is down Cable, connector, endpoint power, port configuration Broken cable, disconnected endpoint, disabled port
Link is up but PLC is unreachable IP, subnet, VLAN, routing, device status Incorrect addressing or logical network configuration
Device appears on an unexpected port Cable labels, MAC table, LLDP, physical route Incorrect patching or outdated port map
Communication is intermittent Error counters, cable quality, duplicate IP, topology Physical faults, address conflict, unstable link, network loop
PLC communicates locally but not with SCADA Gateway, routes, ACLs, firewall, application service Routing or security policy issue
Fibre uplink is down Transceiver compatibility, fibre type, polarity, connector cleanliness Optical link or transceiver issue
One protocol fails but ping succeeds Service configuration, TCP/UDP rules, application diagnostics Blocked port or application-level fault
Redundant network fails to recover Redundancy status, ring configuration, blocked ports Incorrect redundancy setup or unsupported topology

Recommended diagnostic order

Verify device identity and cable label
          ↓
Verify physical port and link status
          ↓
Inspect switch diagnostics and counters
          ↓
Check VLAN and Layer 2 connectivity
          ↓
Check IP addressing and routing
          ↓
Check TCP/UDP services or industrial protocol
          ↓
Verify application operation
          ↓
Document root cause and corrective action

This order helps separate physical, data-link, network-layer, transport, and application faults instead of changing several unrelated settings at once.

18. Port mapping and change management

Port mapping must be updated whenever a physical or logical change affects the documented connection.

Examples include:

  • Replacing a managed switch.
  • Moving a PLC or HMI to another port.
  • Installing a new robot or remote I/O adapter.
  • Changing VLAN assignments.
  • Reconfiguring a trunk or uplink.
  • Adding a redundant network connection.
  • Replacing a fibre transceiver or changing fibre patching.
  • Changing a firewall or gateway interface.
  • Connecting a previously isolated machine to a plant network.

A controlled change should include the intended configuration, the implementation steps, verification tests, rollback plan where appropriate, and updates to the as-built documentation.

This is particularly important when a physical port has a special role, such as a trunk, redundant ring connection, or restricted engineering interface.

19. Safety and cybersecurity considerations

Port mapping supports safe maintenance, but it does not replace approved isolation or change procedures.

  • Identify the equipment and communication path before disconnecting anything.
  • Follow the site's authorisation and production-impact requirements.
  • Avoid disconnecting safety-related or critical control connections without the approved procedure.
  • Protect switch management interfaces from unauthorised access.
  • Do not mirror production traffic or perform packet captures without authorisation.
  • Avoid connecting unknown devices to production switch ports.
  • Keep port maps and network diagrams controlled and current.
  • Record unused ports and apply the site's approved unused-port security policy.
  • Avoid exposing industrial services through uncontrolled NAT or port forwarding.
  • Verify communication after any approved port or cable change.

Network labeling and port mapping reduce uncertainty, but a label is not proof that a connection is safe to disconnect.

20. Practical example: incorrect HMI connection

An HMI loses communication with its PLC after maintenance. The physical link LED is on, and the HMI can communicate with other network devices.

The port map states that:

  • HMI-C01 should connect to SW-C01-01 port 2.
  • PLC-C01 should connect to port 1.
  • Both devices should be in the approved machine VLAN.

During inspection, the engineer finds that the HMI cable is connected to port 6, which belongs to a different VLAN.

The correct procedure is to:

  1. Verify the HMI, PLC, cable IDs, and switch tag.
  2. Confirm the actual switch port through physical tracing and switch diagnostics.
  3. Check the configured VLAN on port 6.
  4. Compare the actual connection with the approved design.
  5. Obtain approval to restore the intended connection or correct the approved configuration.
  6. Verify HMI-to-PLC communication.
  7. Check for any resulting alarms or application faults.
  8. Update the port map and maintenance record if a documented discrepancy was corrected.

The link LED only indicated a physical link. It did not prove that the HMI was connected to the correct logical network.

21. Interview questions and answers

1. What is port mapping?

Port mapping is the identification and documentation of network connections between physical device interfaces, switch ports, and relevant network configurations.

2. What is the difference between a port map and a network topology diagram?

A topology diagram shows the overall network structure. A port map provides more detailed information about individual ports, cable IDs, connected devices, and relevant port settings.

3. How can a managed switch help identify an unknown connection?

Its MAC address table, LLDP information, link status, VLAN configuration, and port counters can help identify connected devices and investigate the connection.

4. What does it mean when a switch port is up but communication fails?

The physical link exists, but the fault may involve VLAN configuration, IP addressing, routing, protocol settings, firewall rules, or the application itself.

5. What is the difference between a physical switch port and a TCP port?

A physical switch port is an Ethernet interface. A TCP port is a transport-layer number used by an application service on a network host.

6. Why should VLANs be included in the port map?

VLAN information helps engineers verify logical network membership and diagnose cases where devices are physically connected but cannot communicate as intended.

7. What is LLDP used for?

LLDP allows compatible devices to advertise and discover directly connected neighbours, helping verify physical connectivity and device identity.

8. Why can several MAC addresses appear on one switch port?

The port may connect to another switch, an integrated Ethernet bridge, a virtualised system, or another device that presents multiple MAC addresses.

9. What should be checked before moving a cable to another switch port?

Check the intended connection, VLAN, port mode, redundancy role, access restrictions, and the potential effect on production communication.

10. Why must port maps be updated after a switch replacement?

The new switch may use different physical numbering, configuration, or interface capabilities. The records must match the actual installed system.

22. Final engineering checklist

  • Every relevant switch has a unique device tag.
  • Physical port numbering matches the manufacturer's interface layout.
  • Each important port is mapped to its connected device and cable ID.
  • Device interface names are recorded correctly.
  • Uplinks, fibre connections, and redundant links are identified.
  • VLAN and port-mode information is recorded where applicable.
  • Link status and relevant diagnostics have been verified.
  • The port map matches the cable schedule and network drawing.
  • Application port numbers are documented separately from physical ports.
  • NAT and port forwarding are documented where present.
  • Changes are authorised, tested, and reflected in the as-built records.
  • The final map allows another engineer to trace the connection without guessing.

Core principle: A useful port map describes not just where a cable is plugged in, but which device and interface it connects to, what role the port serves, and how the connection fits into the approved network design.
