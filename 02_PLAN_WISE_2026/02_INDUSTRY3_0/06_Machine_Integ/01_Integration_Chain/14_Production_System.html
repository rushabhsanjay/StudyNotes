1. Purpose of a production system

A production system connects machine-level activity with the manufacturing decisions, records, and performance information needed to operate a plant. It links what the equipment physically does with what the production order requires, what quality rules permit, and what the business needs to know.

For example, on an automotive component line, a PLC may report that a part has completed a machining cycle. A barcode reader identifies the part, a measurement station records its test results, and the Manufacturing Execution System (MES) associates these events with the correct serial number and production order. The resulting record can show which machine processed the part, when it was processed, which recipe was active, and whether it passed inspection.

Without this integration, the machine may operate correctly while the factory still struggles with missing traceability, incorrect production counts, delayed reports, and unreliable downtime analysis. Machines are very good at doing exactly what they were programmed to do, including producing beautifully formatted bad data.

These functions may exist in separate products or be combined into a single platform. The name of a software package does not reliably tell you every capability it contains. Verify the actual interfaces, data ownership, and responsibilities.

3. Manufacturing architecture and system hierarchy

A common architecture separates real-time control, supervisory monitoring, production execution, and enterprise planning.

Enterprise business systems
    ERP / Planning / Materials / Customer orders
                    ↕
Manufacturing execution
    MES / Production orders / Traceability / WIP / Quality
                    ↕
Supervisory and data collection
    SCADA / Historian / Edge gateway / Line monitoring
                    ↕
Cell and machine control
    PLC / CNC / Robot controller / Vision / Test equipment
                    ↕
Physical process
    Motors / Drives / Sensors / Actuators / Tools / Parts
                    ↓
        Manufacturing operations
                    ↓
      Feedback and production records

The architecture is logical, not a requirement that every system must communicate directly with the layer immediately above it. For example, a machine may send events to an edge gateway, which buffers and forwards them to MES. MES may exchange order information with ERP through an integration service rather than a direct connection.

3.1 Typical ISA-95 / IEC 62264 view

ISA-95, also known internationally as IEC 62264, provides a framework for integrating enterprise and manufacturing operations.

Level Typical function Example
Level 4 Business planning and logistics ERP production planning and material requirements
Level 3 Manufacturing operations management MES, dispatching, tracking, production performance
Level 2 Monitoring and supervisory control SCADA, HMI supervision, process monitoring
Level 1 Basic control PLC logic, CNC control, drive and robot control
Level 0 Physical process Actual cutting, welding, pressing, assembly, measurement

The levels describe functional responsibilities rather than a mandatory hardware layout. Modern systems can distribute functions across edge devices, virtual servers, and cloud platforms.

Important distinction: MES does not normally replace deterministic PLC control. A PLC must continue to enforce machine sequencing and safety-related control independently of ordinary MES availability. Any exception must be explicitly engineered and validated for the application.

4. What MES does in a production line

An MES coordinates production execution and maintains a contextual record of what happened.

5. Production data sources

Production data comes from both automated equipment and business systems. Reliable integration requires knowing which source is authoritative for each field.

Source Typical data Integration consideration
PLC Machine state, cycle complete, faults, counters Define tag meaning, data type, and update behavior
CNC Program, tool, cycle, alarms, machining results Interpret controller-specific data correctly
Robot controller Program state, cycle events, faults Coordinate events with cell sequence and part identity
Barcode/RFID Serial, lot, carrier, pallet ID Validate scan quality and uniqueness
Vision system Inspection results, defect classifications Associate result with the correct part and inspection
Torque tool Torque, angle, program, OK/NOK Capture tool result and serial context
Test bench Test values, limits, pass/fail, recipe Preserve units, limits, and test-program revision
Scale or measuring instrument Weight, dimension, measurement status Validate scaling, calibration, and units
Operator terminal Downtime reason, rework disposition, confirmation Control permissions and standardize selections

MES Routing, serial, WIP, operation disposition Use authoritative production context

A PLC counter can tell you that 100 cycles occurred. It cannot necessarily tell you that 100 distinct acceptable products were manufactured. A cycle may run without a part, a part may be rejected, or a signal may be counted twice after a communication restart. Production meaning must be engineered, not guessed.

6. Production data flow

A typical sequence for an automotive machining and inspection line is:

1. ERP creates or schedules a production order
                ↓
2. MES receives the order and validates routing and material
                ↓
3. MES authorizes the next production operation
                ↓
4. PLC executes the machine cycle
                ↓
5. Scanner identifies the part or carrier
                ↓
6. Machine and inspection equipment generate events/results
                ↓
7. Edge or integration service collects and buffers the data
                ↓
8. MES validates context, sequence, and quality disposition
                ↓
9. MES updates WIP, traceability, and production quantities
                ↓
10. Results are sent to ERP, historian, or BI as required

The PLC should not need to know how the business calculates monthly production performance. It needs a clear and reliable interface to the execution system, with defined commands, acknowledgements, status, and failure behavior.

6.1 Separate commands, status, and results

These are different categories of information and should not be treated as interchangeable.

  • Command: An authorized request to perform an action, such as load an order or select a recipe.
  • Acknowledgement: Confirmation that the receiving system has accepted or rejected the request.
  • Status: Current state, such as ready, busy, running, faulted, or complete.
  • Event: Something that happened at a particular time, such as cycle started or part unloaded.
  • Result: An outcome associated with an operation, such as measured torque or inspection pass/fail.
  • Master data: Relatively stable definitions, such as part number, routing, station ID, and ideal cycle time.

A single Boolean called MES_OK is not a sufficient interface definition for a complex production system. It does not identify which order was accepted, whether the acknowledgement belongs to the latest request, or whether the result has been saved.

8. Machine states and production events

Production reporting depends on interpreting machine states consistently. Different PLC programs often use different bit names for similar conditions, so a common state model is useful.

Typical states include:

  • Running: Equipment is actively performing its defined production function.
  • Idle: Equipment is available but not producing.
  • Setup/changeover: Equipment is being prepared for a different product, tool, or process.
  • Faulted: A fault prevents normal production.
  • Starved: A station cannot produce because the required input is unavailable.
  • Blocked: A station cannot release output because the downstream path is unavailable.
  • Planned downtime: Equipment is intentionally unavailable under the plant's defined production calendar.
  • Unknown/communication loss: The system cannot establish the equipment state reliably.

Do not map every non-running state to breakdown. That turns a useful downtime report into fiction with a database.

8.1 State model versus event model

A state model describes the condition of the equipment over an interval. An event model records discrete occurrences.

For example:

10:00:00  RUNNING
10:04:15  FAULTED
10:06:40  RUNNING

The fault duration is the interval between the fault start and recovery, subject to the plant's precise event and state rules.

A state transition log is usually more useful for downtime analysis than a repeatedly sampled status bit alone. However, sampling can still be appropriate for selected process values and monitoring applications.

8.2 Reason-code governance

A reason code should describe a meaningful, agreed loss category.

Examples include:

  • Equipment breakdown
  • Tool change or tool failure
  • Material shortage
  • Upstream starvation
  • Downstream blockage
  • Quality hold
  • Changeover
  • Planned maintenance
  • No operator or staffing constraint

Define who can assign or change a reason code, when manual confirmation is required, and how unknown or unclassified time is reported. Avoid hundreds of overlapping codes that operators cannot distinguish.

9. OEE and production performance

Overall Equipment Effectiveness (OEE) combines three dimensions: availability, performance, and quality.

9.1 Availability

Availability measures the proportion of planned production time during which the equipment was operating under the agreed definition.

\[ \text{Availability} = \frac{\text{Operating Time}}{\text{Planned Production Time}} \]

Operating time is generally planned production time minus the downtime counted against availability.

9.2 Performance

Performance compares actual output with the output theoretically possible at the ideal cycle time.

\[ \text{Performance} = \frac{\text{Ideal Cycle Time} \times \text{Total Count}} {\text{Operating Time}} \]

Use consistent time units. If ideal cycle time is expressed in seconds per part, operating time must be converted to seconds before calculation.

9.3 Quality

Quality measures the fraction of produced units that meet the defined good-output criteria.

\[ \text{Quality} = \frac{\text{Good Count}}{\text{Total Count}} \]

Define how rework, retest, scrap, and partially completed units are treated. Otherwise, different reports can calculate different quality rates from the same production history.

9.4 Overall Equipment Effectiveness

\[ \text{OEE} = \text{Availability} \times \text{Performance} \times \text{Quality} \]

If the three factors are represented as percentages, convert them to fractions before multiplying, then convert the result back to a percentage.

9.5 Worked example

Assume a machine has the following values for one production period:

Parameter Value
Planned production time 420 minutes
Downtime counted against availability 42 minutes
Operating time 378 minutes
Ideal cycle time 0.5 minutes per part
Total count 700 parts
Good count 672 parts

Availability:

\[ A = \frac{378}{420} = 0.90 = 90\\% \]

Performance:

\[ P = \frac{0.5 \times 700}{378} = 0.9259 \approx 92.59\\% \]

Quality:

\[ Q = \frac{672}{700} = 0.96 = 96\\% \]

OEE:

\[ \text{OEE} = 0.90 \times 0.9259 \times 0.96 \approx 0.80 = 80\\% \]

The machine has an OEE of approximately 80% under these definitions. That number is meaningful only if planned time, ideal cycle time, downtime rules, and good-count logic are consistently defined.

9.6 OEE implementation pitfalls

  • Using a cycle time from the wrong part variant.
  • Counting a single physical part multiple times.
  • Including unplanned time in one report but excluding it in another.
  • Treating every stopped minute as equipment breakdown.
  • Counting reworked parts as good before final acceptance.
  • Using a nominal cycle time that is no longer achievable.
  • Calculating performance above 100% without investigating the cycle-time standard, time units, counts, and operating-time definitions.
  • Comparing different machines without accounting for product mix and different operating rules.

OEE is not a direct measure of profit, customer satisfaction, labor productivity, or total factory effectiveness. It is one operational indicator within a wider performance system.

10. Takt time, cycle time, throughput, and bottlenecks

These terms describe different aspects of production and should not be used interchangeably.

Metric Definition Practical use
Takt time Available production time divided by customer demand Determines the required production pace
Cycle time Time required to complete one defined cycle Measures actual or standard station cycle duration
Throughput Number of units completed per unit of time Measures output rate
Lead time Elapsed time from a defined start to a defined finish Measures total time through a process
WIP Units currently between process start and completion Indicates material tied up in the process
Changeover time Time required to change from one production setup to another Measures setup losses
Bottleneck Constraint that limits overall line throughput Identifies where improvement has the greatest effect

10.1 Takt time calculation

Suppose a shift has 420 minutes available for production after defined breaks, and demand is 600 parts.

\[ \text{Takt Time} = \frac{420 \times 60}{600} = 42 \text{ seconds per part} \]

The line must deliver one acceptable part approximately every 42 seconds to meet demand under those assumptions.

Takt time is demand-driven. Cycle time is process-driven. A station with a 50-second cycle cannot independently meet a 42-second takt unless the process is improved, parallelized, or otherwise redesigned.

10.2 Line balancing

For a line with sequential stations, the slowest constrained operation often determines the maximum sustainable output rate. Actual performance also depends on buffers, failures, product mix, changeovers, operator availability, and interactions between stations.

Station 10 → Station 20 → Station 30 → Station 40
  30 sec       35 sec       52 sec       32 sec
                              ↑
                         Bottleneck

In this example, Station 30 has the longest cycle. Improving a non-bottleneck station may reduce local cycle time without increasing total line throughput.

10.3 Starved and blocked analysis

  • A station is starved when it cannot start because required input is unavailable.
  • A station is blocked when it cannot transfer its output because the downstream process or buffer is unavailable.

The distinction matters because the corrective action differs. A starved station may need upstream reliability or material-flow improvement; a blocked station may need downstream capacity or buffer management.

11. Production order lifecycle and handshake design

An order handshake defines how MES and machine control exchange production instructions and status without ambiguity.

A typical order lifecycle is:

MES creates or releases order
              ↓
Machine requests order or receives dispatch
              ↓
Machine validates order and recipe
              ↓
Machine sends ACCEPTED or REJECTED
              ↓
MES confirms authorization and tracking
              ↓
Machine executes production
              ↓
Machine reports completion and results
              ↓
MES validates records and updates order quantity
              ↓
Machine and MES close or prepare the next operation

This is a conceptual sequence. The actual state transitions must be specified for the machine and MES products involved.

11.1 Example interface signals

Signal or field Direction Meaning
OrderRequest Machine to MES Machine requests production authorization
OrderID MES to machine Identifier of the requested or dispatched order
PartNumber MES to machine Product to be manufactured
RecipeID MES to machine Required recipe or process program
OrderAccepted MES to machine Order has passed interface validation
OrderRejected MES to machine Request cannot be accepted
RejectCode MES to machine Reason for rejection
CycleStarted Machine to MES Production cycle has started
CycleComplete Machine to MES Defined cycle has completed
ResultStatus Machine to MES Production or inspection outcome
EventID Machine or integration service to MES Unique event identifier
Acknowledgement Receiving system to sender Message has been received or processed according to the specified contract

11.2 Handshake design rules

  • Define the owner of every field and which system may write it.
  • Include an order ID or request ID so acknowledgements can be associated with the correct request.
  • Define when data becomes valid and how long it remains valid.
  • Specify timeout, retry, rejection, and recovery behavior.
  • Prevent one old acknowledgement from being interpreted as confirmation of a new order.
  • Define what happens if communications fail during an active cycle.
  • Keep safety interlocks local to the validated control and safety architecture.
  • Distinguish message receipt from successful business processing.
  • Ensure the same production event cannot accidentally increment a quantity multiple times.

A communication bit changing state is not proof that an order has been accepted and correctly recorded. That requires an agreed handshake and, where necessary, application-level confirmation.

12. Industrial communication and integration interfaces

The interface should match the type of data, latency requirements, reliability needs, and security boundaries.

Technology Common use Engineering consideration
OPC UA Structured industrial data access and information models Define namespaces, security, certificates, and data quality
MQTT Publish/subscribe event and telemetry transport Define topics, payloads, delivery behavior, and retained-message policy
Sparkplug Industrial MQTT conventions for state and metric management Validate namespace, birth/death behavior, and implementation compatibility
REST API Application-to-application requests and records Define authentication, versioning, error handling, and rate limits
SQL Structured database queries and reporting Control access, transactions, schema changes, and data ownership
Vendor API Controller- or equipment-specific integration Verify supported versions and licensing
File exchange Batch imports, exports, and legacy integration Define file format, naming, acknowledgement, retries, and duplicate handling
Industrial Ethernet protocol Real-time or cyclic equipment communication Use the protocol appropriate to the control task and network design

12.1 Select the correct communication method

For deterministic machine control, use the control architecture and industrial protocols engineered for the required timing and safety. An ordinary enterprise API is not a substitute for a real-time interlock.

For production events, OPC UA, MQTT, vendor interfaces, or a suitable integration service may be used, depending on requirements. For reporting, SQL views, APIs, historians, or a data platform may be appropriate.

Do not choose a protocol merely because a library exists for it. Confirm:

  • Required latency and update rate.
  • Whether data is sampled or event-driven.
  • Reconnection and recovery behavior.
  • Authentication and authorization.
  • Data quality and timestamp support.
  • Supported payload and data types.
  • Buffering and store-and-forward capability.
  • Vendor support, licensing, and maintenance requirements.

12.2 Avoid uncontrolled PLC-to-database connections

Direct PLC writes into enterprise databases can create fragile coupling between control logic and business software. Schema changes, database outages, credentials, connection limits, and poorly managed retries can affect production integration.

A more maintainable architecture is:

PLC / CNC / Test equipment
            ↓
Industrial data collector or edge gateway
            ↓
Validated event and message processing
            ↓
MES / Historian / Integration service
            ↓
Enterprise database and reporting

This is not an absolute prohibition on every direct connection. It is a design principle: isolate control from enterprise data services unless a direct interface is explicitly supported, secured, and engineered.

13. Event reliability and data integrity

A production record is useful only if it is correct, complete, attributable, and associated with the right part and operation.

13.1 Duplicate events

A message may be delivered again after a timeout or reconnection. If the receiving system increments production quantity every time it sees the message, one part can become two recorded parts.

Use a unique event ID or another well-defined idempotency key. The receiver should recognize repeated submissions and avoid applying the same production event twice.

Idempotency means that repeating the same request or event does not unintentionally repeat its business effect.

13.2 Missing or out-of-order events

A cycle-complete event might arrive before a delayed cycle-start event, or a network interruption may leave a gap.

Mitigations include:

  • Sequence numbers or unique event IDs.
  • Source timestamps and receiver timestamps.
  • A defined buffering and replay mechanism.
  • Event validation and reconciliation against machine counters or MES records.
  • Explicit handling of missing, late, and out-of-order events.
  • Alerts when a data source becomes stale or unavailable.

Do not silently manufacture missing records to make a dashboard appear complete.

13.3 Clock synchronization

Machine controllers, edge computers, MES servers, and databases may have different clocks. Even a small offset can make events appear in the wrong order.

Use a controlled time-synchronization strategy, commonly based on NTP or, where justified, PTP. Record the source timestamp and the collection or receipt timestamp when useful. Define time zones consistently and preserve unambiguous timestamps in stored records.

13.4 Units and scaling

A value of 124 could represent 124 mm, 12.4 mm after scaling, a raw analog count, or a value in another unit. The numeric value alone is insufficient.

Document:

  • Raw data type and range.
  • Engineering-unit conversion.
  • Scale and offset.
  • Valid operating range.
  • Rounding and precision rules.
  • Sensor or instrument calibration requirements.
  • Behavior for invalid, substituted, or stale values.

Never combine measurements from different sources until their units and interpretation have been verified.

13.5 Data quality states

Use an explicit data-quality field where supported. Typical conditions include:

  • Good: valid and current under the defined rules.
  • Uncertain: available but subject to a known limitation.
  • Bad: invalid, failed, or not trustworthy.
  • Stale: last value is older than the permitted update interval.
  • Missing: no valid value or event was received.

A dashboard should not display a frozen value as if it were current. A number with no indication of freshness can be more misleading than a blank field.

14. Product traceability and genealogy

Traceability answers questions such as:

  • Which component lots were used in this finished assembly?
  • Which machine and process program performed the operation?
  • Which measurement values were recorded?
  • Which products were affected by a known tool or material problem?
  • Was a part reworked, retested, or scrapped?
  • Which production order and operation produced the item?

14.1 Serial-level traceability

For individually identified products, the record may include:

  • Unique serial number.
  • Part number and variant.
  • Production order.
  • Machine and station.
  • Operation sequence.
  • Component serial numbers or material lots.
  • Recipe and program revision.
  • Measurement results and limits.
  • Operator or authorized user, where required.
  • Timestamps and final disposition.
  • Rework history and retest results.

14.2 Lot-level traceability

Where individual serial numbers are not practical, traceability may be maintained by batch, lot, pallet, container, or another defined production unit. The selected level must satisfy quality, regulatory, customer, and business requirements.

14.3 Prevent incorrect product association

The most dangerous traceability error is not necessarily missing data. It is valid-looking data associated with the wrong part.

Controls may include:

  1. Scan or verify the part identity at a defined process point.
  2. Validate that the part is permitted at the current station and operation.
  3. Confirm that the selected recipe matches the part variant.
  4. Associate the measurement result with the verified serial number.
  5. Reject duplicate, unknown, or incorrectly routed identities according to approved rules.
  6. Record rework and retest as additional linked events rather than overwriting the original history.

A passing test result attached to the wrong serial number is not a successful traceability system. It is an expensive mystery.

15. Production dashboards and operational reporting

Dashboards should help users take a defined action. Showing every available tag on one screen is not information architecture.

Dashboard or report Useful measures Typical user
Live line status Running, stopped, blocked, starved, current order Operator and shift leader
Production progress Planned quantity, actual quantity, remaining quantity Production supervisor
Downtime Pareto Downtime duration and count by reason Maintenance and production
OEE report Availability, performance, quality, OEE Production engineering
Quality report Scrap, first-pass yield, defects, retest rate Quality engineering
Cycle-time report Actual cycle distribution and cycle-time losses Process engineering
Traceability view Serial history, genealogy, test results Quality and service teams
Maintenance report Failure history, MTBF, MTTR, repeat faults Maintenance engineering
Data-health dashboard Communication state, stale tags, missing events, buffer health Controls and IT/OT teams

15.1 First-pass yield

First-pass yield measures the fraction of units that pass the defined process the first time, without rework or repeated attempts, according to the agreed counting rules.

\[ \text{First-Pass Yield} = \frac{\text{Units Passing First Attempt}} {\text{Units Entering the Process}} \]

Define the process boundary carefully. If a unit passes only after rework, it may be good at final disposition while still being a first-pass failure.

15.2 MTBF and MTTR

Mean Time Between Failures (MTBF) and Mean Time To Repair (MTTR) help characterize equipment reliability and maintainability.

A common MTBF definition for repairable equipment is:

\[ \text{MTBF} = \frac{\text{Defined Operating Time}} {\text{Number of Counted Failures}} \]

A common MTTR definition is:

\[ \text{MTTR} = \frac{\text{Total Defined Repair Time}} {\text{Number of Counted Repairs}} \]

The time basis, failure definition, and repair boundary must be consistent. Some organizations use different conventions for repair time, restoration time, and downtime, so reports should explicitly state the chosen definition.

15.3 Live monitoring versus historical analysis

Live monitoring is used to understand what is happening now. Historical analysis is used to understand patterns over shifts, days, weeks, product variants, or equipment populations.

They have different requirements. A live screen may need fast updates and clear stale-data indicators, while historical analysis needs durable records, consistent timestamps, reliable event classification, and a stable data model.

Do not assume a screen that updates every second is automatically a trustworthy historical record.

16. Production-system commissioning

Commissioning verifies that the complete information flow works correctly, not merely that a network connection exists.

16.1 Pre-commissioning checklist

  • Confirm the production architecture and system boundaries.
  • Identify the authoritative source for each production field.
  • Approve the tag list, data dictionary, asset hierarchy, and interface specification.
  • Verify part-number, serial-number, order, routing, and recipe mappings.
  • Define state transitions, event triggers, counters, and downtime classifications.
  • Define acknowledgements, timeout behavior, retries, and communication-loss handling.
  • Confirm time synchronization and timestamp conventions.
  • Verify accounts, permissions, certificates, network segmentation, and firewall rules.
  • Define data retention, buffering, backup, recovery, and reconciliation requirements.
  • Establish test cases and acceptance criteria with production, maintenance, quality, and IT/OT teams.

16.2 Functional test cases

Test Expected behavior
Valid production order Correct order and product information are accepted
Invalid order Request is rejected with a defined reason
Wrong product variant Incorrect recipe or routing is blocked according to approved rules
Normal production cycle Cycle and result events are associated with the correct part
Failed inspection Failure is recorded and disposition follows quality rules
Duplicate event Production quantity is not incremented twice
Network interruption Defined local behavior occurs and data is buffered or recovered as specified
MES unavailable Machine follows the approved degraded-mode policy
Recovery after interruption Events are reconciled without losing or duplicating production records
Clock offset Time-quality issue is detected or handled under the defined rules
Stale data source Dashboard reports stale or unavailable data rather than implying normal operation
Order completion MES and ERP quantities reconcile according to their respective business rules

16.3 Acceptance criteria

Do not accept a production interface based solely on a green communication indicator. Define measurable acceptance criteria, such as:

  • Required event completeness and permitted data loss.
  • Maximum permitted event latency.
  • Correct part and order association.
  • No unintended duplicate production counts.
  • Correct handling of rejects, rework, and scrap.
  • Correct machine-state and downtime classification.
  • Recovery behavior after communication failure.
  • Verified permissions and security configuration.
  • Reconciled counts between equipment, MES, and approved production reports.

The exact numerical limits depend on the process, customer requirements, and system design. They must be agreed before commissioning rather than invented after a failed test.

17. Troubleshooting production-system integration

Troubleshooting should proceed from the physical event to the control signal, collection layer, interface, receiving application, and final report.

Symptom Likely causes Investigation
Machine produces parts but MES count is low Missing cycle events, failed communication, incorrect trigger Compare physical output, PLC counter, event log, and MES count
MES count is too high Duplicate messages, incorrect counter reset, repeated trigger Inspect event IDs, counter logic, retries, and transaction handling
Wrong part number appears Incorrect order mapping, stale recipe, wrong barcode association Verify identity source, order context, and recipe validation
Measurements appear against the wrong serial Scan timing issue, buffered result, incorrect part context Trace the sequence from scan through result acknowledgement
Line is stopped but dashboard shows running Stale tag, wrong state mapping, missing communication-health logic Inspect source timestamps, tag updates, and state-model rules
Downtime is classified incorrectly Poor reason-code mapping or unclear state definitions Compare PLC transitions with approved downtime logic

Duplicate serial rejected unexpectedly Scanner repeats a scan, stale identity, legitimate re-entry not handled Check scan events and approved rework or retry behavior

17.1 Recommended diagnostic sequence

  1. Confirm the physical production event actually occurred.
  2. Check the source controller's status, counter, or event trigger.
  3. Verify that the data collector received the correct value or event.
  4. Inspect the outgoing message or interface record.
  5. Check communication, authentication, and application logs.
  6. Verify that the receiving system accepted and processed the event.
  7. Trace the event ID, order ID, serial number, and timestamps across each layer.
  8. Reconcile source counts against MES records and investigate discrepancies.
  9. Correct the underlying issue and verify the fix using a repeatable test.
  10. Record the root cause, affected production range, corrective action, and validation evidence.

Do not immediately reset counters, delete duplicate records, or manually edit production quantities to make reports agree. Preserve evidence first, then apply the authorized correction and audit process.

18. Data buffering and degraded operation

Production equipment may need to continue operating when MES or the plant network becomes temporarily unavailable. Whether it may do so depends on process risk, traceability requirements, quality rules, and the approved production policy.

18.1 Store-and-forward

A store-and-forward design retains events locally during a temporary connection failure and transmits them when communication recovers.

Machine event
     ↓
Local collector validates event
     ↓
Persistent local queue
     ↓
Connection available?
     ├── No  → Keep event queued and monitor capacity
     └── Yes → Send event to receiving system
                         ↓
                  Receive acknowledgement
                         ↓
                  Mark event processed

The implementation must define when an event can be removed from the queue. Sending a message is not necessarily equivalent to successful processing by MES.

18.2 Buffer design considerations

  • Use persistent storage when events must survive a computer restart.
  • Define maximum queue size and the response to capacity limits.
  • Monitor queue depth, oldest event age, and failed transmissions.
  • Use unique event identifiers and duplicate protection.
  • Define message ordering requirements.
  • Define replay behavior after recovery.
  • Avoid silently discarding events when storage fills.
  • Secure locally stored production data.
  • Test power loss, service restart, and network interruption.
  • Reconcile buffered events against receiving-system records.

A buffer cannot fix an incorrect data model, a wrong serial number, or an event that was never generated. It preserves what it receives, including mistakes.

18.3 Degraded-mode production policy

Document which operations are permitted during MES outages. Possible policies include stopping production, allowing limited production with local records, or allowing operation only when required identity and quality controls remain available.

The policy should specify authorization, operating limits, record capture, quality holds, traceability requirements, and reconciliation before normal operation resumes. Never bypass safety controls or required quality interlocks merely to keep the line moving.

19. Cybersecurity and OT/IT boundaries

Production integration creates pathways between machine networks and enterprise systems. Each pathway must be controlled.

Key practices include:

  • Segment control networks, supervisory networks, and enterprise networks according to the plant's risk assessment.
  • Use firewalls and explicitly approved communication flows.
  • Apply least-privilege access and individual or managed service identities.
  • Avoid shared administrator credentials and hard-coded secrets.
  • Protect credentials, certificates, API tokens, and database connections.
  • Restrict write access to PLCs, recipes, production orders, and configuration data.
  • Separate read-only data collection from authorized command channels where practical.
  • Log administrative actions, configuration changes, and significant interface failures.
  • Maintain supported software versions, backups, recovery procedures, and change control.
  • Validate vendor remote access and remove access that is no longer needed.
  • Assess data integrity and availability risks, not only confidentiality.
  • Test security changes so they do not unintentionally interrupt production or safety-related functions.

Do not expose PLCs or controllers directly to the public internet for convenient dashboard access. Remote access should use an approved, authenticated, monitored architecture with clearly defined permissions.

20. Production data governance and documentation

A maintainable production system needs controlled definitions and ownership. Without them, the same machine may have three names, two cycle-time standards, and four definitions of downtime. Humans are exceptionally good at creating that situation.

Essential documentation includes:

Document Contents

Equipment hierarchy Plant, area, line, cell, machine, station, and device identifiers
Interface control document Message formats, fields, ownership, states, acknowledgements, and error handling

Data dictionary Meaning, type, unit, source, validity, and update behavior of each field

Master-data mapping Part numbers, variants, routes, recipes, orders, and equipment IDs

20.1 Ownership and change management

Every critical data field and interface should have an owner. Production, controls engineering, quality, maintenance, and IT/OT teams may have different responsibilities.

For example, controls engineering may own the definition of a PLC event, while the MES team owns its processing rules and quality engineering owns the acceptance criteria for the associated test result.

A change to a PLC tag, recipe identifier, routing rule, or event format should be assessed for downstream impact. Versioning, approval, testing, deployment, and rollback plans help prevent small changes from silently breaking production reporting.

20.2 Data retention and auditability

Retention periods depend on customer contracts, applicable regulations, quality requirements, and company policy. Define retention for raw events, measurements, genealogy, state transitions, audit logs, and derived reports separately where needed.

If a production record must be corrected, preserve the original record and the authorized correction history when the applicable system and requirements demand it. Do not overwrite historical results without traceability.

21. Practical automotive production-line example

Consider an automated line that machines and inspects a component before sending it to assembly.

21.1 End-to-end operation

  1. ERP releases an order for a defined part variant and quantity.
  2. MES validates the order, material availability, and required routing.
  3. The line receives the authorized order and recipe.
  4. A barcode reader identifies the component entering the station.
  5. The PLC validates the sequence and executes the machine cycle.
  6. The CNC or test system generates process data and completion results.
  7. An edge collector captures relevant events and forwards them through the approved interface.
  8. MES associates the result with the correct order, serial number, operation, and equipment.
  9. Quality rules determine whether the part passes, fails, or requires an authorized disposition.
  10. MES updates production progress and traceability, while ERP and reporting systems receive the information they require.

21.3 Engineering checks

  • Does the serial number belong to the expected part and order?
  • Is the operation valid for this station?
  • Does the recipe match the approved product variant?
  • Was the measurement captured with the correct unit and calibration status?
  • Is the result attached to the correct cycle and serial?
  • Is the event unique and correctly timestamped?
  • Does MES update the count only once?
  • Can the record be retrieved later for quality investigation?
  • What happens if MES is unavailable immediately after the machine finishes its cycle?
  • Can the team reconcile PLC counts, MES counts, accepted output, and scrap?

These checks turn a working machine connection into a dependable production integration.

22. Interview questions and answers

1. What is MES?

MES is a manufacturing execution system that coordinates and records shop-floor production. Common functions include order dispatching, WIP tracking, routing, traceability, quality data, and production performance.

2. What is the difference between MES and ERP?

ERP primarily manages enterprise planning and business processes, while MES manages production execution and detailed shop-floor records. They exchange information, but neither automatically replaces the other.

3. What is the difference between MES and SCADA?

SCADA primarily provides supervisory monitoring, process visualization, alarms, and data acquisition. MES focuses on production execution, order tracking, routing, traceability, and related manufacturing records. Their actual capabilities may overlap.

4. What is ISA-95?

ISA-95, aligned with IEC 62264, provides a framework and terminology for integrating enterprise systems with manufacturing operations and control systems.

5. Why is a production data dictionary important?

It establishes the exact meaning, type, unit, source, and validity of exchanged fields. This prevents systems from interpreting the same signal differently.

6. Why should cycle-complete events have unique identifiers?

Unique identifiers help detect duplicate submissions and support reconciliation when communications retry or recover after an interruption.

7. What is the difference between a state and an event?

A state describes a condition over time, such as running or faulted. An event records an occurrence, such as a cycle completion or a fault transition.

8. How do you calculate OEE?

OEE is availability multiplied by performance multiplied by quality. The time boundaries, ideal cycle time, total count, and good-count definitions must be consistent.

9. Why might OEE exceed expected levels or show performance above 100%?

Possible causes include an incorrect ideal cycle time, wrong time units, duplicate counts, inconsistent operating-time calculations, or a product-mix mismatch.

10. What is product genealogy?

Genealogy links a product to its components, material lots, process operations, equipment, recipes, and inspection results, according to the required traceability level.

11. How should production data be handled when MES is unavailable?

Follow the approved degraded-mode policy. Where permitted, buffer events persistently, maintain required local controls and quality checks, and reconcile events after recovery. Do not bypass required safety or quality controls.

12. How do you prevent duplicate production counts?

Use unique event IDs or idempotency keys, receiver-side duplicate protection, defined counter behavior, and reconciliation between source and receiving systems.

13. What is the difference between takt time and cycle time?

Takt time represents the required production pace based on available time and demand. Cycle time is the time taken by a process to complete its defined cycle.

14. What is the purpose of a store-and-forward gateway?

It collects and buffers data locally when the receiving system is temporarily unavailable, then forwards events after communication recovers, subject to the designed acknowledgement and recovery rules.

15. Why is direct PLC-to-enterprise-database integration often avoided?

It can tightly couple machine control to database availability, credentials, schema changes, and transaction behavior. A supported gateway or integration service often provides better isolation, buffering, validation, and security.

16. How would you investigate an MES count mismatch?

Compare actual production with PLC counters, event logs, edge records, and MES transactions. Check duplicate events, missing events, identity mapping, resets, communication recovery, and the count definitions used by each system.

17. What is first-pass yield?

It is the proportion of units that pass the defined process on the first attempt, according to the agreed process boundary and counting rules.

18. Why is time synchronization important?

It allows events from different controllers and systems to be ordered and correlated reliably. Clock offsets can distort cycle times, downtime durations, and traceability investigations.

19. Does a green communication status prove production integration is correct?

No. It proves only that a defined connection or health condition is satisfied. Correct order handling, event integrity, serial association, data processing, and production reconciliation require separate validation.

20. What is the most important principle in production-system integration?

Every production record must have a defined meaning, authoritative source, correct context, reliable delivery behavior, and verifiable relationship to the actual manufacturing process.

23. Final engineering checklist

Before treating a production integration as complete, verify the following:

  • The responsibility of PLC, SCADA, MES, ERP, historian, and reporting systems is clearly defined.
  • Every critical field has an authoritative source and documented meaning.
  • Asset, order, product, operation, and serial identifiers are consistent.
  • The production-state model distinguishes running, idle, setup, fault, starved, blocked, and unknown states as required.
  • Cycle counts, accepted output, scrap, rework, and retest are handled correctly.
  • Events have reliable timestamps and suitable duplicate protection.
  • Communication loss, buffering, retry, and recovery behavior have been tested.
  • OEE, cycle time, downtime, and quality calculations use approved definitions.
  • Traceability records connect the correct part to its actual process and test results.
  • Network segmentation, authentication, authorization, and configuration control are implemented.
  • Production and MES records can be reconciled during investigations.
  • Documentation, backups, recovery procedures, ownership, and acceptance evidence are maintained.

The core engineering principle is simple: machine control, production execution, and business reporting must agree on what happened, which product it happened to, when it happened, and whether the result is valid. That agreement must be designed, tested, and maintained rather than assumed.
