1. Purpose of an Industrial Network

An industrial network connects automation devices so they can exchange commands, status, measurements, configuration data, alarms, and production information.

A modern automated machine may contain a PLC, HMI, remote I/O, VFDs, servo drives, robots, CNC controllers, vision systems, barcode readers, printers, engineering computers, and supervisory systems. The network allows these devices to work as one coordinated production system.

The network is not merely a collection of cables. It is a communication system whose architecture, timing, addressing, configuration, security, and diagnostic capability directly affect machine availability.

1.1 Typical network functions

  • Exchange sensor states, process values, and actuator commands.
  • Transfer production recipes, job parameters, and machine settings.
  • Communicate between PLCs, robots, CNCs, and inspection systems.
  • Transfer barcode data, inspection results, and traceability records.
  • Display machine status, alarms, trends, and diagnostic information on HMIs.
  • Send production information to SCADA, MES, historians, and databases.
  • Support engineering, programming, configuration, and maintenance.
  • Enable controlled remote diagnostics and approved software updates.

1.2 Example: Automated machining station

Consider a station that scans a component barcode, loads the correct recipe, machines the part, checks quality, and prints a traceability label.

Barcode Scanner ----\
CNC Controller ------\
Robot Controller -----+---- Industrial Ethernet Switch
Vision System -------/                 |
Printer -------------/                 |
                                       |
                                  PLC Controller
                                       |
                                      HMI
                                       |
                               Supervisory Network
                                       |
                                SCADA / MES / SQL

This is a conceptual architecture. The actual physical topology and protocol connections depend on the machine design. Some devices may connect directly to the PLC, while others communicate through a dedicated switch, gateway, or controller interface.

The PLC may coordinate station sequencing, while the CNC executes machining, the robot handles components, the vision system inspects quality, and the MES records production information.

Important: A device appearing as connected on the network does not prove that the application data is valid, current, correctly mapped, or safe to use.

2. Industrial Network Architecture

Industrial communication is commonly organized into levels according to function, timing, and security requirements.

Level 4: Enterprise / Business
         ERP, Business Analytics, Planning
                    |
Level 3: Manufacturing Operations
         MES, Historian, Production Reporting
                    |
Level 2: Supervisory Control
         SCADA, HMI Servers, Engineering Stations
                    |
Level 1: Machine Control
         PLCs, CNCs, Robot Controllers, Motion Controllers
                    |
Level 0: Field Devices
         Remote I/O, Sensors, Drives, Instruments

This is a functional model, not a rule that every device must occupy a separate physical network or subnet. Actual implementations vary.

2.1 Field-level network

Connects sensors, actuators, instruments, remote I/O, drives, and other equipment close to the process.

Typical technologies include IO-Link, PROFIBUS, DeviceNet, Modbus RTU, EtherNet/IP, and PROFINET, depending on device capabilities.

2.2 Control-level network

Connects PLCs, motion controllers, robots, CNCs, remote I/O, and industrial devices.

Its requirements can include predictable update times, low communication delays, diagnostic information, and reliable cyclic data exchange.

2.3 Supervisory network

Connects SCADA systems, HMI servers, engineering stations, historians, and monitoring computers.

It generally carries alarms, production data, operator commands, configuration traffic, and diagnostic information.

2.4 Enterprise network

Connects manufacturing information systems to business applications, reporting, planning, and analytics.

Business connectivity should not automatically grant unrestricted access to machine controllers. Segmentation and controlled data pathways are essential.

3.1 Switch versus router

A switch normally forwards Ethernet frames within a local Layer 2 network using MAC addresses. A router forwards IP packets between different IP networks.

A managed switch can provide VLANs, port diagnostics, traffic statistics, redundancy features, and access controls. An unmanaged switch usually provides fewer monitoring and configuration capabilities.

A gateway may mean a protocol converter, an IP router, or a device connecting different application systems. Always identify its actual function instead of assuming every gateway performs protocol translation.

4. OSI Model and TCP/IP Fundamentals

The OSI model helps separate physical communication problems from addressing, transport, and application problems.

OSI layer Function Industrial example
7. Application Defines application messages and services OPC UA, HTTP, industrial protocol services
6. Presentation Data representation and encoding Numeric encoding, serialization
5. Session Manages communication sessions conceptually Application session handling
4. Transport End-to-end transport TCP, UDP
3. Network IP addressing and routing IPv4, routers
2. Data Link Local frame delivery and MAC addressing Ethernet switching
1. Physical Electrical or optical signaling Copper cable, fiber, connectors

Industrial troubleshooting does not always map neatly to one OSI layer, but the model provides a useful starting point.

4.1 MAC address

A MAC address identifies a network interface at the data-link layer. Ethernet switches learn MAC addresses and associate them with switch ports.

A MAC address is not a substitute for an IP address. IP addressing supports logical communication between networks, while MAC addressing is used for local Ethernet delivery.

4.2 IP address

An IP address identifies a logical network interface. Devices communicating through IP must have appropriate addressing and routing.

Example:

PLC:          192.168.10.10
HMI:          192.168.10.20
Robot:        192.168.10.30
CNC:          192.168.10.40
Subnet mask:  255.255.255.0

These devices are in the same IPv4 subnet if configured with the listed addresses and subnet mask. They can normally communicate directly at the IP layer without a router, provided no other configuration or network fault prevents communication.

Every address must be unique within the relevant network. Duplicate IP addresses can produce intermittent or misleading communication faults.

4.3 Subnet mask

A subnet mask defines which bits of an IP address identify the network and which identify the host.

For example, 255.255.255.0 is equivalent to /24.

For 192.168.10.10/24:

  • Network address: 192.168.10.0
  • Typical usable host range: 192.168.10.1 to 192.168.10.254
  • Broadcast address: 192.168.10.255

The network address and broadcast address are not ordinarily assigned to individual hosts in this subnet.

4.4 Default gateway

A default gateway provides a next hop for traffic destined for IP networks outside the local subnet.

A machine operating entirely within an isolated local subnet may not require a default gateway for local communication. A gateway is required when a device must reach a different routed network, subject to the routing design.

An incorrect gateway may allow local PLC-to-HMI communication while preventing communication with SCADA or a remote engineering station.

4.5 DHCP and static addressing

  • Static addressing: The device is manually assigned an IP configuration.
  • DHCP: A server dynamically supplies network configuration.
  • DHCP reservation: A server assigns a predictable address to a device based on its identity.

Fixed-address industrial devices commonly use documented static addressing or managed reservations. The correct choice depends on the plant's approved addressing policy.

Do not change a production device's IP address without checking the PLC configuration, HMI settings, device configuration, engineering records, and network ownership.

4.6 DNS

DNS resolves hostnames to IP addresses. Industrial devices may communicate directly by IP, or use hostnames where supported.

A DNS failure may affect hostname-based connections even when basic IP connectivity remains functional.

5. TCP, UDP, Ports, and Communication Sessions

TCP and UDP are transport protocols. They serve different purposes.

Feature TCP UDP
Connection model Connection-oriented Connectionless
Delivery behavior Reliable, ordered byte stream No built-in delivery guarantee
Retransmission Supported by TCP Must be handled by the application if needed
Overhead Generally higher Generally lower
Common industrial uses Configuration, web services, many data exchanges Cyclic I/O, discovery, time-sensitive messaging in supported protocols

The use of TCP or UDP depends on the industrial protocol and its communication mode. A single protocol may use both.

5.1 Port numbers

A port identifies a service or application endpoint on a host. IP address plus transport protocol and port helps identify the destination service.

Examples of commonly encountered ports include:

Service or protocol Common port Notes
HTTP TCP 80 Unencrypted web service
HTTPS TCP 443 Encrypted web service
Modbus TCP TCP 502 Modbus application protocol
OPC UA TCP 4840 Common default, configurable
EtherNet/IP explicit messaging TCP 44818 CIP messaging
EtherNet/IP I/O messaging UDP 2222 Common I/O transport
PROFINET discovery Layer 2 protocols Not all discovery uses TCP or UDP

These are common defaults, not proof that a particular device uses them. Device configuration, vendor implementation, and network policy determine the actual communication.

5.2 Bandwidth, latency, jitter, and packet loss

  • Bandwidth: The capacity of a communication link, often expressed in bits per second.
  • Latency: The time taken for data to travel from source to destination.
  • Jitter: Variation in packet or message delay.
  • Packet loss: Failure of packets to reach their destination.
  • Throughput: The actual rate of successful data transfer.
  • Availability: The proportion of time a service or network is operational.

A high-bandwidth network can still have poor real-time behavior because of congestion, excessive jitter, device processing delays, retransmissions, or unsuitable topology.

6. Industrial Ethernet and Legacy Networks

An Ethernet connector does not guarantee compatibility between industrial protocols. Two devices may both have RJ45 ports and still be unable to exchange the required application data.

6.1 Common industrial communication protocols

Protocol Typical ecosystem or use Important consideration
EtherNet/IP Rockwell Automation and compatible devices Uses CIP; supports explicit and implicit messaging
PROFINET Siemens and compatible devices Supports cyclic process data and real-time communication
Modbus TCP Multi-vendor industrial integration Simple register-based data exchange
OPC UA Industrial data exchange between systems Structured information model and security capabilities
EtherCAT Distributed motion and control Specialized real-time Ethernet architecture
POWERLINK Real-time industrial automation Requires compatible implementation
Sercos III Motion control Designed for synchronized, real-time communication
MQTT Telemetry and data distribution Usually used for supervisory, edge, or IIoT data
HTTP/HTTPS Web interfaces and application integration Not inherently a deterministic motion-control protocol

Protocol selection must account for controller support, device compatibility, performance requirements, diagnostics, security, engineering tools, and lifecycle support.

6.2 EtherNet/IP

EtherNet/IP uses the Common Industrial Protocol (CIP).

Common communication types include:

  • Explicit messaging for configuration, diagnostics, and non-cyclic data access.
  • Implicit messaging for cyclic I/O data exchange.
  • Produced/consumed data where supported by the controller architecture.

Typical integration tasks include assigning device addresses, installing or selecting the correct EDS device description where applicable, configuring assemblies and connection parameters, setting Requested Packet Interval (RPI), and verifying connection status.

An EDS file describes device capabilities and configuration information. It does not replace correct controller configuration or guarantee that the device is compatible with a particular application.

6.3 PROFINET

PROFINET provides industrial communication between controllers and field devices.

Important concepts include:

  • Device name and IP configuration.
  • Controller and device roles.
  • GSDML device description files.
  • Cyclic input/output data.
  • Real-time communication classes.
  • Diagnostics and topology information.
  • Network redundancy where supported.

A device may have a valid IP address yet remain unavailable to the configured PROFINET controller because its assigned device name, project configuration, or expected device identity is incorrect.

6.4 Modbus TCP

Modbus TCP transfers data using a client-server model and a register-oriented data structure.

Typical data areas include coils, discrete inputs, input registers, and holding registers. The exact data access depends on the device's implementation.

Common integration problems include:

  • Incorrect register addresses or addressing conventions.
  • Incorrect function codes.
  • Wrong data types or register word order.
  • Incorrect scaling.
  • Incorrect polling intervals.
  • Multiple clients exceeding the device's supported connection capacity.

A register returning a number does not prove that the engineering units, sign, byte order, or meaning are correct.

6.5 OPC UA

OPC UA is used to exchange structured industrial information between compatible systems.

Its capabilities can include:

  • Client-server communication.
  • Browsing of structured address spaces.
  • Data values, status codes, and timestamps.
  • Subscriptions and monitored items.
  • Authentication and encryption when correctly configured.

Successful TCP connectivity does not prove OPC UA session establishment. Certificate trust, endpoint configuration, authentication, permissions, security policies, and namespace mapping can all prevent successful data exchange.

6.6 MQTT

MQTT uses a publish-subscribe communication model.

PLC / Edge Gateway
        |
     Publisher
        |
    MQTT Broker
        |
   +----+-----+
   |          |
SCADA       Historian
Subscriber  Subscriber

MQTT is useful for telemetry, event distribution, and IIoT integration. It should not automatically replace deterministic PLC-to-drive or motion-control communication.

Important parameters include broker address, port, client identity, topic naming, quality of service, retained messages, keepalive, authentication, and encryption.

6.7 Legacy and serial networks

Technology Typical use Key consideration
RS-232 Point-to-point serial communication Limited distance and normally one transmitter/receiver pair
RS-485 Differential serial communication Bus topology, termination, biasing, and node loading matter
Modbus RTU Serial register communication Address, baud rate, parity, stop bits, and timing must match
PROFIBUS DP Distributed field I/O Requires correct bus parameters and termination
DeviceNet CAN-based industrial device network Requires correct power, termination, addressing, and network configuration
CANopen CAN-based device communication Uses object dictionaries and defined network management
IO-Link Point-to-point sensor/actuator communication Requires compatible master and device configuration

When migrating a legacy network to Ethernet, check data mapping, response timing, fault handling, wiring, addressing, diagnostic behavior, and controller program changes. A protocol gateway does not automatically preserve every behavior of the original network.

7. Physical Network Design

Network reliability begins with physical design. Incorrect cable routing, poor terminations, unsuitable components, or inadequate grounding can cause intermittent faults that appear to be software problems.

7.1 Copper Ethernet

Industrial copper Ethernet commonly uses twisted-pair cabling with suitable connectors and environmental ratings.

Common cable categories include Cat 5e and Cat 6. The correct cable must meet the required speed, distance, installation environment, and vendor specifications.

A typical copper Ethernet channel supports a maximum length of 100 m under the applicable structured-cabling rules. Actual industrial installations must account for the permitted cable and connector configuration, environmental rating, and protocol-specific requirements.

7.2 Fiber-optic Ethernet

Fiber is useful where longer distances, electrical isolation, or immunity to electromagnetic interference are required.

Consider:

  • Single-mode versus multimode fiber.
  • Supported optical transceiver type.
  • Connector type and polarity.
  • Link budget and permitted distance.
  • Bend radius and mechanical protection.
  • Cleanliness of fiber connectors.
  • Compatibility of transceivers at both ends.

Fiber avoids conductive electrical paths between endpoints, but the connected equipment still needs appropriate power, grounding, and protection.

7.3 Industrial connectors

Common connection types include RJ45, M12 D-coded, and M12 X-coded, depending on application and data rate.

Do not assume connectors are interchangeable because they look similar. Verify coding, pinout, shielding, speed rating, environmental rating, and device compatibility.

7.4 Electromagnetic interference

Common sources of interference include VFD output cables, servo power cables, contactors, welding equipment, high-current conductors, and poorly installed switching equipment.

Good practices include:

  • Separate communication cables from power and motor cables according to applicable installation requirements.
  • Cross power and signal cables at right angles where crossings are unavoidable.
  • Use appropriate shielded cable and connectors.
  • Follow the equipment manufacturer's shielding and bonding instructions.
  • Avoid improvised shield connections.
  • Maintain cabinet bonding and protective earthing.
  • Inspect cable routing, connector condition, and strain relief.
  • Use fiber where electrical isolation or distance makes it appropriate.

Shielding is not a substitute for correct cable selection, routing, grounding, or termination.

7.5 Network topology

Topology Description Advantages Limitations
Star Devices connect to a central switch Easy fault isolation and expansion Central switch can be a single point of failure
Line Devices are connected in sequence Less cabling in supported designs Intermediate failure may affect downstream devices
Ring Devices form a closed loop Can support recovery after a link failure Requires compatible redundancy configuration
Tree Multiple branches connect through switches Suitable for hierarchical systems Upstream faults may affect multiple branches
Mesh Multiple interconnections between devices Multiple potential paths More complex configuration and troubleshooting

A physical topology does not by itself establish redundancy. The devices, switches, protocols, and recovery mechanism must all support the chosen design.

8. Real-Time Communication and Determinism

Ordinary office Ethernet is designed primarily for general-purpose data communication. Industrial control may require predictable delivery intervals and bounded communication delays.

Determinism means that communication behavior is sufficiently predictable for the intended control task.

8.1 Cyclic I/O

In cyclic communication, a controller exchanges data with devices at configured intervals.

For example:

PLC sends output data
        |
Drive receives command
        |
Drive updates its control interface
        |
Drive returns status and feedback
        |
PLC processes received data

The exact sequence and timing depend on the protocol, device implementation, controller task, and drive control architecture.

8.2 Requested Packet Interval

In EtherNet/IP, the Requested Packet Interval (RPI) specifies the requested rate for a cyclic I/O connection.

A 10 ms RPI corresponds to a nominal update interval of 100 updates per second.

\[ f = \frac{1}{T} \]

where \(f\) is the update frequency and \(T\) is the interval in seconds.

An RPI of 10 ms does not mean that the complete machine response time is exactly 10 ms. Controller task execution, network delivery, device processing, and actuator response also contribute.

8.3 PROFINET update time

PROFINET devices exchange cyclic process data according to the configured communication settings and supported real-time class.

A shorter update time may improve responsiveness but increases communication load and may increase resource demand. Select the update time according to the application requirements and supported device capabilities.

8.4 Bandwidth example

Suppose 20 devices each exchange 200 bytes of process data in each direction every 10 ms.

The raw payload calculation for one direction is:

\[ \frac{20 \times 200 \times 8}{0.01} = 3{,}200{,}000\ \text{bits/s} \]

This is 3.2 Mbit/s in one direction, before accounting for Ethernet frames, protocol headers, acknowledgments where applicable, discovery traffic, diagnostics, and other network overhead.

This estimate is not a complete switch-capacity or real-time-performance calculation. Actual traffic depends on the protocol, frame size, packet rate, communication model, and traffic patterns.

8.5 Multicast and broadcast

  • Unicast: Traffic sent from one source to one destination.
  • Multicast: Traffic sent to a subscribed group of destinations.
  • Broadcast: Traffic delivered to all devices in a local broadcast domain.

Excessive multicast traffic can burden devices that receive or process traffic they do not need.

Managed switches may support IGMP snooping to constrain multicast forwarding to relevant ports. The correct configuration depends on the protocol and network design. Incorrect multicast filtering can itself disrupt industrial communication.

8.6 Quality of Service

Quality of Service (QoS) allows supported network equipment to prioritize selected traffic classes.

QoS can help manage congestion, but it cannot fix incorrect addressing, a failed link, poor cabling, unsupported protocols, or overloaded controllers. Priority markings must be supported and configured consistently throughout the path.

9. Redundancy and Network Recovery

Redundancy reduces the effect of selected network failures. It does not eliminate all failure modes.

9.1 Common redundancy mechanisms

Mechanism Purpose Consideration
RSTP Prevents Layer 2 loops and supports topology recovery Recovery time may not suit every real-time requirement
MRP Media Redundancy Protocol used in supported industrial ring networks Requires compatible devices and configuration
DLR Device Level Ring used by supported EtherNet/IP devices Requires compatible ring nodes and supervisor behavior
PRP Parallel Redundancy Protocol Uses parallel paths in supported designs
HSR High-availability Seamless Redundancy Used in specific supported architectures
Redundant switches Provides alternate switching paths Must be designed and tested as a complete system
Redundant controllers Maintains control availability in supported systems Requires controller-specific redundancy architecture

Do not enable multiple ring or spanning-tree mechanisms without understanding their interaction. Incorrect redundancy configuration can cause loops, blocked links, or communication outages.

9.2 Redundancy commissioning tests

  • Verify the approved topology and device compatibility.
  • Confirm ring or redundancy status.
  • Record normal link and device status.
  • Test the approved failure scenario during a controlled maintenance window.
  • Measure recovery behavior against the system requirement.
  • Verify that PLC, HMI, robot, CNC, and drive communication recover correctly.
  • Check for alarms, stale data, and unexpected machine transitions.
  • Restore the approved configuration and document the result.

Never intentionally disconnect a production network link without authorization, a risk assessment, and a defined recovery plan.

10. Integrating PLCs, HMIs, Robots, CNCs, Drives, and Other Devices

Network integration must define both communication and application behavior.

10.1 PLC and remote I/O

The PLC may exchange cyclic input and output data with remote I/O modules.

Verify:

  • Correct device identity and configuration.
  • Correct IP address or fieldbus address.
  • Input and output module configuration.
  • Assembly or process-data mapping.
  • Update interval and watchdog settings.
  • Diagnostic status and communication-loss behavior.
  • Safe output behavior when communication fails.

A network fault must not cause outputs to remain in an unsafe state. The appropriate response depends on the control design, risk assessment, and device capabilities.

10.2 PLC and HMI

An HMI typically reads selected PLC tags and writes operator commands or parameters.

Check:

  • PLC address and communication driver.
  • Tag names, data types, and addresses.
  • Read/write permissions.
  • Scaling and engineering units.
  • Alarm and status logic.
  • Stale-data detection.
  • Behavior when communication is interrupted.
  • Recipe validation and operator authorization.

A connected HMI can still display wrong values if tags are mapped incorrectly or scaling is wrong.

10.3 PLC and VFD or servo drive

Depending on the drive and protocol, the network may carry:

  • Start/stop or enable commands.
  • Speed or torque references.
  • Operating mode requests.
  • Actual speed or position feedback.
  • Ready, running, warning, and fault status.
  • Diagnostic codes and parameters.

Verify the correct control mode, cyclic data mapping, reference scaling, communication-loss action, drive state machine, and hardware safety architecture.

Do not assume a network stop command is equivalent to a safety-rated stop function. Safety functions must use the approved safety architecture.

10.4 PLC and robot controller

Common exchanged information includes:

  • Robot ready and fault status.
  • Program or job selection.
  • Start request and cycle status.
  • Part present and gripper status.
  • Robot position or process data where supported.
  • Handshake states and completion results.

A robust handshake distinguishes command requests, acknowledgments, execution states, completion, and fault conditions.

Example:

PLC                         Robot
 |                            |
 |---- Job Request ---------->|
 |<--- Job Accepted ----------|
 |                            |
 |---- Start Request -------->|
 |<--- Cycle Running ---------|
 |<--- Cycle Complete --------|
 |                            |
 |---- Reset Request -------->|

This is illustrative. The real sequence must follow the robot and PLC interface specification. Handshake signals need defined timeouts, reset behavior, and recovery rules.

10.5 PLC and CNC

Common data includes machine ready, cycle start, cycle complete, alarm state, part counter, program selection, and machining results.

Check whether the CNC interface supports the intended protocol and whether any data exchange requires a licensed option, vendor gateway, or dedicated interface.

Program selection and cycle-start permissions must be validated against the machine's interlocks and operating procedures.

10.6 PLC and barcode scanner

A scanner may transmit data through industrial Ethernet, TCP sockets, serial communication, or a vendor-specific protocol.

Verify:

  • Trigger behavior.
  • Message framing and end-of-message delimiter.
  • Character encoding.
  • Timeout and retry rules.
  • No-read behavior.
  • Duplicate-scan handling.
  • Data validation.
  • Correct association of the scanned ID with the current part.

A scanner returning a string does not prove that the string belongs to the correct component or that it matches the required production order.

10.7 PLC and printer

A printer may use a raw TCP connection, a vendor protocol, a print server, or a separate application interface.

Check the message format, print command, label selection, data validation, printer readiness, buffer behavior, and print-complete or error feedback.

A print command being transmitted is not proof that a label was physically printed correctly. Where traceability requires it, confirm print status and use an appropriate label verification process.

10.8 PLC and vision system

A vision system may exchange trigger commands, job selection, busy status, result-ready status, pass/fail results, and measurement values.

Verify trigger-to-result association, job configuration, timeout handling, data freshness, and behavior after a missed trigger or incomplete inspection.

The PLC must not accidentally associate an old result with a new component.

11. Addressing Plan and Network Segmentation

A documented addressing plan reduces duplicate IP addresses, integration errors, and recovery time after hardware replacement.

11.1 Example machine subnet

Device Example IP address Subnet mask Purpose
PLC 192.168.10.10 255.255.255.0 Main machine controller
HMI 192.168.10.20 255.255.255.0 Operator interface

These are illustrative addresses, not a recommendation to use them on a live plant network. Actual addresses must follow the site's IP management policy.

11.2 Why segmentation matters

Segmentation divides a network into smaller logical or physical areas to control communication and limit the effect of faults or security incidents.

Methods include:

  • VLANs.
  • Separate IP subnets.
  • Layer 3 routing.
  • Industrial firewalls.
  • Dedicated control networks.
  • Industrial demilitarized zones (IDMZs).
  • Access-control lists and application-specific rules.

A VLAN alone is not a complete security boundary if routing and access policies allow unrestricted communication between VLANs.

11.3 Example segmented architecture

Enterprise IT
     |
Enterprise Firewall
     |
Industrial DMZ
     |
OT Firewall / Controlled Routing
     |
Supervisory Network
     |
Machine Cell Network
     |
PLC / HMI / Robot / CNC / Drives

The industrial DMZ can host approved intermediate services such as data brokers, replication services, remote-access gateways, and other controlled interfaces.

Direct unrestricted connectivity from enterprise devices to PLCs should be avoided. Communication paths should be explicitly justified, restricted, monitored, and documented.

12. VLANs, Routing, and Firewalls

12.1 VLAN

A Virtual LAN divides a Layer 2 network into logical broadcast domains.

VLANs can separate machine cells, supervisory systems, and engineering access. Correct VLAN configuration requires appropriate switch port settings, trunk configuration where needed, and routing or firewall rules for cross-VLAN communication.

12.2 Routing

Routing allows traffic to move between IP networks.

A route must exist along the communication path, and return traffic must also have a valid route. Asymmetric routing, incorrect subnet masks, and missing return routes can create one-way communication failures.

12.3 Firewall rules

Firewall rules should permit only required communication between approved source and destination systems.

A rule should define, as applicable:

  • Source address or subnet.
  • Destination address or subnet.
  • Protocol and port.
  • Direction of initiation.
  • Required response traffic.
  • Business or operational purpose.
  • Owner and review date.

Some industrial protocols use dynamic connections, multicast, discovery traffic, or multiple ports. A firewall policy must account for the actual protocol behavior rather than permitting one guessed port and assuming the job is finished.

12.4 Remote access

Remote access should use approved, authenticated, monitored mechanisms.

Good practices include:

  • VPN or an approved secure remote-access gateway.
  • Multi-factor authentication where supported.
  • Time-limited access and named accounts.
  • Least-privilege permissions.
  • Session logging.
  • Vendor access approval.
  • Controlled file transfer.
  • Removal or disabling of unused accounts.
  • Clear procedures for emergency access.

Do not connect an unapproved laptop, Wi-Fi bridge, modem, or remote-access device to an operational control network.

13. Industrial Network Cybersecurity

Industrial cybersecurity protects machine availability, process integrity, personnel safety, production data, and equipment configuration.

13.1 Main risks

  • Unauthorized PLC or robot program changes.
  • Malware spreading from engineering computers.
  • Unapproved remote access.
  • Default or shared passwords.
  • Uncontrolled USB usage.
  • Unsupported operating systems and devices.
  • Exposed industrial services.
  • Untracked configuration changes.
  • Compromised vendor accounts.
  • Inadequate backup and recovery procedures.

13.2 Defense in depth

A layered approach may include:

  1. Asset inventory and network documentation.
  2. Network segmentation and controlled routing.
  3. Firewall rules and access control.
  4. Secure engineering workstations.
  5. Strong authentication and account management.
  6. Approved patch and vulnerability management.
  7. Configuration backups and recovery tests.
  8. Monitoring, logging, and incident response.
  9. Vendor access control and periodic review.
  10. Physical security of cabinets, switches, and communication ports.

An air gap can reduce some risks, but it does not eliminate malware introduced through removable media, maintenance laptops, or configuration tools.

13.3 Change management

Before a network change:

  • Record the current configuration.
  • Identify affected devices and dependencies.
  • Obtain required approval.
  • Back up relevant configurations.
  • Assess safety, availability, and cybersecurity impact.
  • Define a rollback plan.
  • Make the change within the approved window.
  • Test communication and application behavior.
  • Update drawings, address tables, and change records.

14. Network Diagnostics and Troubleshooting Tools

Tools must be used with authorization and according to plant procedures. Passive monitoring is generally preferable when active testing could affect production.

14.1 Windows command-line tools

Command Purpose Limitation
ipconfig /all Displays interface addressing and configuration Does not prove application communication
ping 192.168.10.10 Tests ICMP reachability where permitted A device may block ICMP while its application works
arp -a Displays learned IPv4-to-MAC mappings Entries can be stale or incomplete
route print Displays the local routing table Does not prove that remote routing works
tracert 192.168.10.10 Traces the IP path using TTL behavior Intermediate devices may not reply
nslookup hostname Tests DNS name resolution Not relevant when the application uses only fixed IPs

Example:

ipconfig /all
ping 192.168.10.10
arp -a
route print
tracert 192.168.10.10

These commands are starting points, not a complete diagnosis. Do not assume that a failed ping means a PLC is offline.

14.2 Wireshark

Wireshark captures and analyzes network packets. It can help identify:

  • Failed TCP connection attempts.
  • TCP retransmissions and resets.
  • Duplicate-address symptoms.
  • Unexpected broadcast or multicast traffic.
  • Protocol discovery messages.
  • Incorrect application requests or responses.
  • Timing differences between requests and replies.

Capture traffic only through approved methods. A switch mirror port or network TAP is generally preferable to inserting an unapproved device inline.

A packet capture may contain machine information, credentials in unencrypted protocols, production data, or proprietary information. Handle capture files as controlled operational data.

14.3 Managed switch diagnostics

Inspect:

  • Link state and negotiated speed.
  • Duplex configuration.
  • CRC/FCS errors.
  • Input and output drops.
  • Port utilization.
  • Interface resets and link flaps.
  • Broadcast and multicast counters.
  • VLAN assignment.
  • Spanning-tree or ring status.
  • PoE status where relevant.

Counter names vary by switch vendor. A rising error counter is more useful than a historical total that may have accumulated over years.

14.4 Vendor diagnostic tools

Depending on the installed equipment, use approved tools for:

  • PLC communication diagnostics.
  • EtherNet/IP connection status.
  • PROFINET device discovery and diagnostics.
  • Robot controller network status.
  • CNC interface diagnostics.
  • Drive communication fault logs.
  • OPC UA client/server diagnostics.
  • Industrial switch management.

Use the version and configuration tools supported by the installed device and plant standards.

15. Practical Troubleshooting Method

Troubleshoot from the physical connection toward the application. Changing multiple parameters at once creates uncertainty and can turn a small fault into a long maintenance incident.

15.1 Step-by-step sequence

  1. Confirm the affected function and operational impact.
  2. Check whether one device, a whole machine cell, or multiple cells are affected.
  3. Review controller alarms, HMI messages, device status, and event logs.
  4. Check power, link LEDs, cable condition, connector seating, and switch-port status.
  5. Verify the device's IP address, subnet mask, and expected network.
  6. Check for duplicate IP addresses and incorrect addressing.
  7. Verify VLAN membership, routing, firewall policy, and required ports.
  8. Check protocol-specific settings, device identity, data mapping, and connection state.
  9. Examine switch counters and approved packet captures if the fault persists.
  10. Compare the configuration against the last known good record.
  11. Make one approved change at a time and record its effect.
  12. Verify the complete application function, not merely the network link.
  13. Document the root cause, corrective action, and recurrence-prevention measure.

15.2 Common faults

Symptom Possible cause Verification
No link LED Power loss, bad cable, wrong port, damaged interface Check device power, cable, port, and interface
Link present, no IP communication Wrong IP, mask, VLAN, or duplicate IP Verify address plan and switch configuration
PLC reachable, I/O connection fault Wrong protocol settings, device identity, assembly, or configuration Inspect controller and device diagnostics
Intermittent connection Loose cable, EMI, link flaps, overload, or power issue Check switch counters, cable route, and event logs
HMI values incorrect Wrong tag mapping, scaling, data type, or stale values Compare raw PLC data with displayed values
Robot handshake times out Logic mismatch, delayed data, wrong state, or controller fault Trace request, acknowledgment, execution, and completion
Slow SCADA updates Polling load, database delay, network congestion, or server load Measure update paths and inspect resource usage
One-way communication Firewall rule, routing asymmetry, or application configuration Check both traffic directions and return routes
High packet loss Physical errors, congestion, overloaded equipment, or link problems Check interface counters and traffic load
Communication fails after replacement Wrong firmware, address, device configuration, or protocol options Compare replacement against the approved configuration
Random machine stops Watchdog expiration, power interruption, network recovery, or application timeout Correlate PLC, switch, drive, and device timestamps

15.3 Distinguishing network failure from application failure

Consider a PLC that reports a robot communication fault.

  • If the physical link is down, investigate power, cable, port, and interface.
  • If the link is up but IP communication fails, investigate addressing, VLANs, routing, and firewall rules.
  • If IP communication works but the industrial connection is faulted, investigate protocol configuration and device compatibility.
  • If the connection is healthy but the handshake times out, investigate application logic, state transitions, data mapping, and timeout assumptions.
  • If the handshake completes but the process result is wrong, investigate data integrity, sequence association, and application semantics.

This separation prevents unnecessary replacement of network hardware when the actual fault is in the application logic.

16. Communication Watchdogs and Failure Behavior

A watchdog detects that expected communication or progress has not occurred within a defined period.

Examples include:

  • PLC connection watchdogs.
  • Drive communication-loss timers.
  • Robot handshake timeouts.
  • HMI stale-data timers.
  • SCADA data-quality monitoring.
  • Application-level heartbeats.

A watchdog timeout should produce a defined response. That response might include an alarm, stopping a sequence, rejecting a part, disabling a command, or entering a controlled fault state.

The correct behavior depends on the hazard analysis, control architecture, equipment requirements, and applicable safety standards.

Do not use a generic network timeout as a replacement for a safety-rated function.

17. Time Synchronization and Event Correlation

Correct timestamps help maintenance teams reconstruct failures across PLCs, robots, CNCs, switches, servers, and historians.

17.1 NTP and PTP

  • NTP: Network Time Protocol, commonly used to synchronize computers, servers, and many industrial devices.
  • PTP: Precision Time Protocol, used where supported for more precise clock synchronization.

PTP performance depends on device support, network design, hardware timestamping where required, and correct configuration.

17.2 Why synchronized time matters

Suppose a robot fault occurs at 14:05:10, a PLC timeout at 14:05:11, and a switch link flap is recorded at 14:05:09. If the device clocks differ by several minutes, the events may appear unrelated.

Maintain a documented time source, time zone policy, synchronization configuration, and clock health monitoring.

Time synchronization improves diagnosis but does not itself guarantee deterministic control communication.

18. Network Commissioning Checklist

18.1 Design verification

  • Approved network architecture and topology are available.
  • IP addresses and subnet masks are documented.
  • Device communication requirements are identified.
  • Protocol compatibility is verified.
  • Switch capacity, port count, and link speed are adequate.
  • Redundancy and recovery requirements are defined.
  • OT segmentation and firewall rules are approved.
  • Cable types, connectors, and installation routes meet requirements.

18.2 Installation verification

  • Cable labels match the drawings.
  • Connectors are correctly terminated and secured.
  • Cable routing and separation meet installation requirements.
  • Shielding and bonding follow manufacturer instructions.
  • Fiber connectors and optical components are compatible.
  • Switch ports are assigned to the correct network or VLAN.
  • Spare ports and cables are identified where required.

18.3 Configuration verification

  • No unintended duplicate IP addresses exist.
  • Device names and protocol identities are correct.
  • Required device description files are installed where applicable.
  • Controller connections and data mappings are verified.
  • Update intervals and watchdogs meet the design requirements.
  • Firewall rules permit only required traffic.
  • Device access controls are configured.
  • Configuration backups are available.

18.4 Functional verification

  • PLC-to-I/O communication works.
  • PLC-to-HMI data and command handling are correct.
  • PLC-to-drive communication and fault behavior are verified.
  • Robot and CNC handshakes are tested.
  • Barcode, vision, and printer data are correctly associated with the current part.
  • Communication-loss behavior is tested under controlled conditions.
  • Redundancy recovery is tested if required.
  • SCADA and historian values are checked against source data.
  • Alarms, timestamps, and diagnostic information are verified.

18.5 Handover

  • Network topology and cable schedules are updated.
  • IP address and device inventories are complete.
  • Switch and firewall configurations are backed up.
  • Controller and device configuration backups are available.
  • Vendor manuals and recovery procedures are stored.
  • Fault response and escalation contacts are documented.
  • Commissioning results and deviations are recorded.
  • Ownership of future changes is defined.

19. Preventive Maintenance and Network Health Monitoring

Industrial networks need routine inspection, not just emergency attention after production stops.

19.1 Suggested inspection activities

Frequency Activity Purpose
Per shift or daily Review active communication alarms and recurring faults Detect emerging issues
Weekly Review switch alarms and notable link events Identify intermittent failures
Monthly Review port errors, utilization, and device inventory changes Detect degradation and unauthorized changes
Quarterly Verify backups, access permissions, and configuration records Improve recoverability and security
During planned shutdowns Inspect selected cabling, connectors, cabinet conditions, and redundancy Detect physical and architectural weaknesses
After any change Verify communication, application behavior, and documentation Prevent configuration drift

The actual frequency should be based on plant standards, equipment criticality, environmental conditions, failure history, and risk.

19.2 Useful health indicators

  • Link-up and link-down events.
  • Increasing CRC/FCS errors.
  • Port drops and interface resets.
  • Communication timeouts.
  • Rising packet loss or latency.
  • Excessive broadcast or multicast traffic.
  • Unexpected device discovery or address changes.
  • Firmware and configuration changes.
  • Device temperature and power status where available.
  • Backup age and restore-test status.

A single high traffic reading does not necessarily indicate a fault. Trends, device limits, communication requirements, and correlated machine symptoms matter.

Before replacing a switch or controller, preserve the current configuration and verify the replacement requirements.

Check:

  • Port count and link speed.
  • Managed-switch feature support.
  • VLAN and redundancy compatibility.
  • Firmware compatibility.
  • Power supply and environmental rating.

A physically compatible replacement is not necessarily a functionally compatible replacement.

21. Network Performance and Troubleshooting Calculations

21.1 Update frequency

For a configured update interval of 20 ms:

\[ f = \frac{1}{0.020} = 50\ \text{updates/s} \]

This describes the nominal update rate, not the full process response time.

21.2 End-to-end response time

A simplified response-time model is:

\[ T\_{\text{total}} = T\_{\text{input}} + T\_{\text{network}} + T\_{\text{controller}} + T\_{\text{output}} + T\_{\text{actuator}} \]

The terms represent the relevant input acquisition, communication, control execution, output delivery, and actuator response delays. Some delays overlap, so an actual system analysis must account for the architecture and scheduling.

21.3 Data size and transfer time

For a payload of 1,000 bytes on a 100 Mbit/s link, the idealized payload-only transmission time is:

\[ T = \frac{1000 \times 8}{100{,}000{,}000} = 0.00008\ \text{s} \]

That equals 80 microseconds, excluding protocol overhead, inter-frame gaps, switching, queuing, processing, retransmission, and any application delays.

This explains why raw link speed alone cannot predict end-to-end control response.

21.4 Error rate interpretation

A rising CRC/FCS error count often suggests a physical-layer issue such as a damaged cable, connector problem, interference, or interface fault.

However, CRC/FCS errors do not identify the exact cause. Compare counters at both ends, check whether errors are increasing, and correlate them with link events and machine symptoms.

22. Common Engineering Mistakes

  • Assuming that every Ethernet device supports the same industrial protocol.
  • Assuming that successful ping proves application-level communication.
  • Assigning duplicate IP addresses.
  • Using the wrong subnet mask or default gateway.
  • Changing a live IP address without documenting dependencies.
  • Treating a VLAN as a complete security boundary.
  • Ignoring switch port errors because the link LED is on.
  • Selecting very short update intervals without calculating system load.
  • Using unmanaged switches where diagnostics or redundancy management are required.
  • Assuming that a ring is redundant merely because the cables form a ring.
  • Ignoring multicast behavior in industrial protocols.
  • Using a network stop command as a substitute for a safety-rated stop function.
  • Capturing production traffic without authorization.
  • Replacing a device without preserving its network and application configuration.
  • Failing to test application behavior after restoring connectivity.
  • Leaving remote access enabled after maintenance.
  • Neglecting timestamp synchronization when correlating faults.

23. Practical Interview Questions and Answers

Q1. What is the difference between a switch and a router?

A switch normally forwards Ethernet frames within a Layer 2 network using MAC addresses. A router forwards IP packets between different IP networks.

Q2. What is the difference between IP and MAC addresses?

An IP address provides logical network addressing, while a MAC address identifies a network interface at the data-link layer. They serve different purposes.

Q3. Why can a PLC respond to ping while its remote I/O connection is faulted?

Ping tests IP reachability using ICMP. The industrial I/O connection may still fail because of incorrect device configuration, incompatible protocols, invalid connection parameters, blocked protocol traffic, or a device fault.

Q4. What is the difference between EtherNet/IP and PROFINET?

Both are industrial Ethernet technologies, but they use different communication architectures, device descriptions, configuration tools, and protocol mechanisms. Compatibility must be verified at the controller and device level.

Q5. What is RPI?

Requested Packet Interval is an EtherNet/IP parameter specifying the requested interval for a cyclic I/O connection. It affects communication timing but is not the same as total machine response time.

Q6. What is the purpose of a subnet mask?

It identifies which part of an IP address represents the network and which part represents the host. It helps a device determine whether a destination is local or requires routing.

Q7. Why is an industrial managed switch useful?

It provides visibility and control through features such as port diagnostics, traffic counters, VLANs, redundancy support, and management interfaces. The exact features depend on the model.

Q8. What is the difference between TCP and UDP?

TCP provides a reliable, ordered byte stream. UDP sends datagrams without built-in delivery or ordering guarantees. Industrial protocols select the transport according to their communication requirements.

Q9. Why might a network be connected but slow?

Possible causes include congestion, excessive multicast or broadcast traffic, high device load, retransmissions, overloaded servers, inefficient polling, or slow application processing.

Q10. What is the purpose of VLANs in an industrial network?

VLANs separate Layer 2 broadcast domains, helping organize traffic and support segmentation. Routing and access-control policies are still needed to control communication between VLANs.

Q11. What is the difference between NTP and PTP?

NTP synchronizes clocks across networks and is common for general industrial timestamping. PTP supports more precise synchronization in compatible systems, depending on the implementation and network design.

Q12. What is a duplicate IP address fault?

Two devices use the same IP address, causing ambiguous or unstable address resolution and intermittent communication. The remedy is to identify both devices and restore the approved unique addressing configuration.

Q13. What is the difference between a network fault and an application fault?

A network fault prevents or degrades communication delivery. An application fault can occur even when communication is healthy, such as incorrect tag mapping, a failed handshake, invalid data scaling, or a sequence timeout.

Q14. Why is network redundancy not sufficient by itself?

Redundancy protects against specific failures only when the complete design supports recovery. Incorrect configuration, common power failures, controller faults, software errors, or application problems may still interrupt operation.

Q15. What should be checked before replacing an industrial switch?

Verify its industrial rating, port requirements, speed, VLAN configuration, redundancy support, firmware, power requirements, mounting, configuration backup, and compatibility with the existing architecture.

Q16. Why is a network diagram important for maintenance?

It identifies device relationships, physical connections, addresses, switch ports, communication paths, and dependencies. This reduces diagnostic time and prevents unsafe or disruptive changes.

Q17. What is an industrial DMZ?

An industrial demilitarized zone is a controlled network area between enterprise IT and operational technology. It provides a place for approved intermediary services while limiting direct access to control systems.

Q18. Why can a barcode scanner return data that is still incorrect?

The data may be malformed, incomplete, stale, duplicated, associated with the wrong part, or interpreted with the wrong message framing. Application-level validation is required.

Q19. What is the difference between bandwidth and latency?

Bandwidth describes communication capacity, while latency describes the time taken for data to travel between endpoints. High bandwidth does not guarantee low latency or predictable timing.

Q20. How should an intermittent communication fault be investigated?

Correlate device logs, PLC diagnostics, switch counters, link events, addressing, and protocol status. Check physical connections and configuration, use approved packet capture where needed, change one variable at a time, and verify the complete machine function after correction.

24. Final Engineering Principles

  • Design the network around the required machine function, timing, availability, and security.
  • Document every device, address, connection, protocol, and relevant configuration.
  • Treat physical connectivity, IP connectivity, protocol connectivity, and application correctness as separate diagnostic layers.
  • Use industrial protocols according to their intended capabilities and verified compatibility.
  • Protect control networks through segmentation, controlled access, backups, and disciplined change management.
  • Monitor error counters, link events, communication faults, and data quality instead of waiting for a machine stoppage.
  • Test recovery behavior under controlled conditions.
  • Verify the actual production result after any network repair or configuration change.
