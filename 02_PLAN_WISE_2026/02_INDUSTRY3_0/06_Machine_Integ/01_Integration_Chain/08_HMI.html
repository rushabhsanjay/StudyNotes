1. Purpose of an HMI

An HMI (Human-Machine Interface) is the interface through which an operator monitors machine conditions, issues authorized commands, changes permitted settings, responds to alarms, and interacts with an automated system.

In industrial automation, the HMI connects human decisions with machine control. It does not necessarily perform the actual control logic. That responsibility normally belongs to a PLC, CNC controller, robot controller, or dedicated drive controller.

Examples include:

  • Starting and stopping an authorized production sequence.
  • Monitoring motor speed, pressure, temperature, position, and cycle status.
  • Displaying active alarms and historical alarm events.
  • Selecting automatic, manual, setup, or maintenance modes.
  • Entering recipes, production quantities, and process setpoints.
  • Displaying maintenance counters, diagnostics, and communication faults.
  • Showing machine readiness, interlocks, and reasons for a sequence not starting.

An HMI is not merely a screen with buttons. It is an operator-facing layer of the machine's control, diagnostic, and information architecture.

2. Position of HMI in the automation architecture

Operator / Maintenance Technician
              ↓
             HMI
              ↓
PLC / CNC / Robot Controller
              ↓
Output Modules / Drive Commands
              ↓
Motors / Valves / Actuators
              ↓
Machine Process
              ↓
Sensors / Encoders / Process Feedback
              ↓
PLC / CNC / Robot Controller
              ↓
Updated Machine Status
              ↓
             HMI

The HMI displays controller data and sends operator requests. The controller validates those requests against machine logic, operating modes, permissives, and interlocks before commanding the equipment.

For example, pressing START on an HMI should not directly energize a motor output without the required control logic. The HMI requests a start; the PLC determines whether starting is permitted.

3. HMI, PLC, SCADA, and other interfaces

System Primary responsibility Typical application
HMI Local operator interaction with a machine Machine control panel
PLC Deterministic machine logic and I/O control Sequence execution and interlocks
SCADA Supervisory monitoring and control across multiple assets Production line or plant monitoring
MES Production execution and manufacturing records Orders, traceability, production reporting
CNC interface Operator interaction with machining operations Program selection, offsets, machine status
Robot teach pendant Robot jogging, programming, and setup Robot commissioning and maintenance
Safety HMI or safety-related interface Indication and interaction within a validated safety design Safety status and permitted reset functions

These categories can overlap. A SCADA system may contain HMI screens, and a machine HMI may display production information from higher-level systems. The underlying control responsibilities must still be defined clearly.

4. Types of industrial HMI

4.1 Basic operator panel

A basic panel displays machine status and provides a limited number of controls.

Typical features:

  • Start and stop requests.
  • Manual and automatic selection.
  • Running, stopped, and fault indications.
  • Basic numerical process values.
  • A small alarm list.

Suitable for simple machines with limited operator interaction.

4.2 Text-based HMI

Uses character-based displays to show messages, values, and menus.

Typical limitations include limited graphics, reduced visualization, and less convenient navigation. These panels may still be suitable for compact equipment and legacy installations.

4.3 Graphic touchscreen HMI

Uses graphical screens, buttons, numerical displays, trends, alarm lists, and equipment illustrations.

Typical applications include PLC-controlled assembly stations, conveyors, leak-testing machines, CNC auxiliaries, and automated inspection systems.

4.4 Industrial PC-based HMI

Runs visualization software on an industrial computer. It may support more complex graphics, extensive historical data, database connectivity, user management, and integration with industrial networks.

Its reliability depends on the hardware, operating system, application software, storage, network, and recovery strategy.

4.5 Web-based HMI

Provides an operator interface through a supported web browser or web client. The underlying server may communicate with PLCs through an industrial communication layer.

Considerations include authentication, session management, network segmentation, browser compatibility, latency, and loss-of-connection behavior.

A browser interface should not be assumed to be suitable for every time-critical machine operation.

5. Hardware architecture and components

A typical panel HMI contains:

  • Display and touchscreen or physical keys.
  • Processor and memory.
  • Communication interfaces such as Ethernet, serial ports, or USB.
  • Power supply input, commonly 24 V DC for industrial panels.
  • Nonvolatile storage for the operating environment and project.
  • Mounting hardware, seals, and a suitable front-panel ingress-protection rating.
  • Optional audio, indicator, or removable-storage interfaces.

The HMI may communicate with the PLC over Ethernet, a serial protocol, or a vendor-specific network.

Before selecting or replacing a panel, verify the required supply voltage, power consumption, mounting cutout, environmental rating, protocol support, PLC compatibility, firmware, project compatibility, and licensing.

A visually identical replacement panel may not support the original runtime project or communication driver.

6. Communication between HMI and PLC

The HMI exchanges data with the controller using a communication driver or protocol.

Common industrial communication technologies include:

  • PROFINET.
  • EtherNet/IP.
  • Modbus TCP and Modbus RTU.
  • OPC UA, commonly used for structured data exchange and supervisory integration.
  • Vendor-specific protocols for Siemens, Rockwell Automation, Mitsubishi, and other platforms.

The exact support depends on the HMI model, firmware, software version, and PLC configuration.

6.1 Tag-based communication

A tag represents a named variable or data item used by the HMI application.

Examples:

HMI tag Example PLC variable Purpose
Machine_Running Machine.Running Running indication
Start_Request HMI.StartRequest Operator start request
Actual_Speed Drive.ActualSpeed Actual speed display
Target_Speed Drive.SpeedSetpoint Permitted speed setpoint
Alarm_Code Machine.AlarmCode Active fault identification
Auto_Mode Machine.AutoMode Operating-mode indication

Names and addressing conventions vary by PLC family. Symbolic addressing is generally easier to maintain than undocumented absolute addresses.

6.2 Polling and update rates

An HMI periodically reads selected tags and writes values when the operator interacts with controls or when the application requires it.

The update interval depends on the driver, communication load, controller, and HMI configuration.

Not every tag needs the same update rate. A rapidly changing speed display may need frequent updates, while a maintenance counter may only need occasional updates.

Excessively fast polling can increase network and controller communication load without providing a meaningful improvement in the operator's experience.

6.3 Communication fault behavior

The application must distinguish valid current data from stale or unavailable data.

Useful indications include:

  • PLC communication healthy.
  • Last successful data update, where supported.
  • Controller unavailable.
  • Tag quality invalid or uncertain.
  • Command response timeout.

When communication fails, the HMI must not present an old value as if it were current. Critical commands must be designed so that loss of communication does not create an unsafe machine condition.

The PLC must retain responsibility for machine safety and deterministic control.

7. HMI screen design and navigation

A well-designed HMI helps the operator understand the current machine condition and take the correct action quickly.

7.1 Common screen structure

+------------------------------------------------------+
| MACHINE NAME | MODE | PLC STATUS | USER | TIME       |
+------------------------------------------------------+
| Navigation                                           |
|                                                      |
| MAIN OVERVIEW                                        |
|                                                      |
| Machine graphic       Process values                 |
| Running / Stopped     Actual speed                   |
| Current station       Temperature                    |
| Sequence status       Production count               |
|                                                      |
+------------------------------------------------------+
| Active alarm / Operator message                       |
+------------------------------------------------------+

A common structure includes:

  • Header: machine identity, mode, communication state, user, and time.
  • Navigation: overview, manual operation, alarms, recipes, diagnostics, and maintenance.
  • Main work area: machine graphics, status, values, and permitted controls.
  • Alarm or message area: active fault, warning, or operator instruction.
  • Footer: contextual information, where useful.

The layout should remain consistent between screens so that operators do not need to relearn navigation for each station.

7.2 Typical screen hierarchy

Machine Overview
    ↓
Station Overview
    ↓
Equipment Detail
    ↓
Manual Controls / Diagnostics
    ↓
Maintenance Information

The hierarchy should follow the physical machine and the operator's workflow rather than the internal structure of the PLC program.

7.3 Navigation design principles

  • Keep frequently used functions easy to locate.
  • Use consistent labels and navigation positions.
  • Provide a clear way to return to the overview.
  • Avoid excessive nested menus.
  • Clearly distinguish navigation buttons from commands that operate machinery.
  • Display the currently selected station, mode, and equipment where relevant.
  • Prevent accidental actions through suitable confirmation and command logic.
  • Do not rely on color alone to communicate meaning.
  • Ensure text, symbols, and touch targets are readable from the normal operator position.

8. Operator commands and PLC validation

An HMI button should normally write a request to the controller. The PLC then evaluates whether that request can be accepted.

For example, a start request might require:

  • Emergency-stop circuit and other safety functions in their required state.
  • Machine in the correct operating mode.
  • No active fault preventing operation.
  • Guards and other required permissives satisfied.
  • Downstream equipment ready.
  • Correct recipe or program selected.
  • Required utilities available.

These are examples of machine-dependent conditions. The actual permissives must come from the machine risk assessment and control design.

8.1 Momentary command versus maintained command

A momentary command generates a short request. A maintained command remains active while a condition is true or until it is explicitly cleared.

Command type Behavior Typical use
Momentary request Short pulse or event Start request, acknowledge request
Maintained request Remains active until cleared A mode request or selected operating state
Numeric entry Writes a value within permitted limits Speed or temperature setpoint
Selection Chooses one item from a defined set Recipe or station selection
Reset request Asks the PLC to clear an eligible fault Fault recovery

A momentary touchscreen button may not behave exactly like a physical pushbutton. HMI communication delays, screen changes, and runtime behavior can affect how the PLC observes a request.

For robust logic, the PLC should handle command edge detection, request clearing, and invalid or repeated commands explicitly.

8.2 Command and confirmation are different

An HMI command indicates what the operator requested. Feedback indicates what the machine actually did.

For example:

Operator presses START
        ↓
HMI sets Start_Request
        ↓
PLC validates permissives
        ↓
PLC issues motor start command
        ↓
Drive receives command
        ↓
Drive reports running status
        ↓
PLC validates running feedback
        ↓
HMI displays RUNNING

The HMI should not display a confirmed RUNNING state merely because the operator pressed Start.

A motor may fail to start because of a drive fault, missing power, an interlock, a communication failure, or a mechanical problem.

9. Manual, automatic, setup, and maintenance modes

Operating modes determine which actions are permitted.

9.1 Automatic mode

The PLC executes the configured sequence. The HMI typically displays step status, cycle progress, current station, faults, and production counts.

Manual commands that conflict with the automatic sequence should be rejected or disabled according to the control design.

9.2 Manual mode

An authorized operator or technician can request individual movements or functions.

Manual mode does not automatically bypass safety functions, interlocks, travel limits, or other required protections.

9.3 Setup mode

Used for tasks such as tool changes, alignment, adjustment, and machine preparation. Movement and speed restrictions depend on the equipment design and risk assessment.

9.4 Maintenance mode

Provides diagnostic information and maintenance-specific functions, which may include permitted jog operations, component testing, or counters.

Maintenance mode must not become a generic method for bypassing safety requirements.

9.5 Mode transition management

The control design should define:

  • Who can change the mode.
  • Whether the machine must be stopped before changing modes.
  • What happens to active requests during a transition.
  • Whether the current sequence can resume or must restart.
  • Which commands are permitted in each mode.
  • How mode selection is displayed and confirmed.

The HMI can present mode controls, but the PLC or appropriate controller must enforce the mode-dependent rules.

10. Alarms, warnings, and events

Alarms communicate abnormal conditions requiring operator attention. Warnings indicate conditions that may require attention but do not necessarily prevent operation. Events record notable actions or changes.

10.1 Alarm classification

Category Meaning Example
Fault A condition prevents or interrupts operation Drive fault
Warning A condition needs attention Low lubrication level
Process alarm A process variable is outside an acceptable range Pressure too high
Communication alarm A device or data link is unavailable PLC communication lost
Maintenance alert Service is due or a component is approaching a limit Filter service counter reached
Safety-related indication Reports a safety-system condition Guard circuit not satisfied

An HMI alarm display is not itself a safety function.

10.2 Alarm lifecycle

A useful alarm system distinguishes between:

  • Active: the alarm condition currently exists.
  • Acknowledged: the operator has recognized the alarm.
  • Cleared or returned to normal: the underlying condition no longer exists.
  • Reset: a permitted action that clears a latched fault when the reset conditions are satisfied.

Acknowledgement does not mean the machine fault has been repaired. Reset should not automatically restart hazardous movement.

10.3 Alarm quality

A good alarm identifies:

  • What happened.
  • Where it happened.
  • Why it may have happened, where known.
  • What the operator should check.
  • Whether production can continue.
  • Whether a qualified maintenance intervention is required.

Poor message: Fault 27

Better message: Station 2 clamp failed to reach closed position within 3 s. Check air supply, clamp mechanism, sensor alignment, and input status.

The suggested checks must match the actual equipment and diagnostic design.

10.4 Alarm priorities

Priorities should reflect urgency, consequences, and required response time rather than simply making every alarm red.

Too many nuisance alarms lead operators to ignore the alarm system. Alarm rationalization should remove duplicates, clarify causes, and distinguish actionable conditions from informational events.

11. HMI data types and engineering units

HMI tags may use Boolean, integer, floating-point, string, enumerated, or structured data.

Data type Example Common use
Boolean TRUE / FALSE Status, permissive, command
Integer 125 Counts, codes, recipe index
Floating point 24.75 Pressure, temperature, speed
String "Drive Fault" Messages and identifiers
Enumeration 0 = Stop, 1 = Run Modes and state values
Structured data Multiple named fields Equipment status or diagnostic record

The HMI must interpret PLC data using the correct type, signedness, word size, byte order, and scaling.

A data-type mismatch can produce incorrect values, invalid commands, or corrupted displays.

11.1 Scaling analog values

Suppose a transmitter measures 0–100 bar and provides a 4–20 mA signal.

The engineering value is:

\[ PV = \frac{I-4}{20-4}\times100 \]

where \(I\) is the measured current in milliamps and \(PV\) is pressure in bar.

At 12 mA:

\[ PV = \frac{12-4}{16}\times100 = 50\text{ bar} \]

The PLC may already convert the raw analog input into engineering units. Confirm where scaling occurs to avoid scaling twice.

The HMI should show the intended engineering value and units, not undocumented raw counts.

11.2 Numeric entry validation

For a setpoint, define:

  • Minimum and maximum permitted values.
  • Engineering units.
  • Decimal precision.
  • Rate-of-change restrictions, if required.
  • Mode and operating conditions in which changes are permitted.
  • Behavior when the entered value is invalid.

The HMI should provide convenient validation, but the controller must independently enforce safety-critical or process-critical limits.

12. Recipes and parameter management

Recipes group related settings for a product, machine setup, or process.

A recipe may include:

  • Speed setpoints.
  • Pressure and temperature targets.
  • Dwell times.
  • Motion positions.
  • Tool or program identifiers.
  • Inspection limits.
  • Sequence options.

12.1 Recipe handling

A robust recipe workflow should define:

  1. Select the intended recipe.
  2. Validate the recipe identifier and data.
  3. Display the selected recipe and revision.
  4. Verify the machine is in a permitted state for loading.
  5. Transfer values to the controller.
  6. Confirm the controller accepted the values.
  7. Record the active recipe and any required audit information.

Do not assume that selecting a recipe on the HMI means the PLC has accepted and activated it.

12.2 Recipe integrity

Useful controls include:

  • User authorization.
  • Approved value ranges.
  • Recipe revision management.
  • Validation of required parameters.
  • Controlled editing and release.
  • Backup and restore.
  • Logging of relevant changes.

For quality-critical processes, a recipe change may need to be associated with the operator, product, production order, and timestamp.

13. User access and security

Not every operator should have access to every setting.

A role-based structure might include:

Role Typical permissions
Operator Operate the machine within approved limits
Line supervisor Approved production settings and selected overrides
Maintenance technician Diagnostics and authorized maintenance functions
Controls engineer Engineering parameters and commissioning functions
Administrator User management and system configuration

The exact permissions must be based on company policy and machine requirements.

Good practices include:

  • Unique user accounts where supported.
  • Strong authentication and managed credentials.
  • Least-privilege access.
  • Automatic session timeout where appropriate.
  • Logging of critical parameter changes.
  • Restricted access to engineering and operating-system functions.
  • Controlled use of USB storage and remote access.
  • Removal or disabling of unnecessary default accounts.

Passwords should not be embedded in PLC logic, exposed on screens, or stored in plain text in project files.

14. HMI and safety engineering

A standard HMI is generally not a safety-rated controller. A screen button, red graphic, warning message, or software interlock must not be treated as a substitute for a required safety function.

Safety functions may use safety relays, safety PLCs, safety-rated drives, and certified input devices, depending on the machine risk assessment and applicable standards.

Examples of safety-related functions include:

  • Emergency stop.
  • Guard interlocking.
  • Safe torque off.
  • Safe speed monitoring.
  • Safety-related access control.

The HMI may display safety status or provide a reset request where the validated design permits it. The safety system must independently enforce the required behavior.

Important principles:

  • Loss of HMI power must not defeat a required safety function.
  • Loss of communication must not bypass safety logic.
  • Resetting an alarm must not automatically cause hazardous motion unless the design explicitly permits and validates that behavior.
  • Safety bypasses must not be casually implemented as HMI buttons.
  • Any safety-related HMI or reset function must meet the requirements of the safety architecture and risk assessment.

Relevant standards may include ISO 13849-1, IEC 62061, and IEC 60204-1, depending on scope and applicability.

15. HMI software engineering and project management

HMI projects contain screens, tags, communication settings, scripts, alarms, recipes, user roles, and runtime configuration.

A maintainable project should use consistent naming and reusable screen patterns.

15.1 Naming conventions

Examples:

Object Example name
Screen SCR_MainOverview
Alarm ALM_ClampCloseTimeout
Navigation button BTN_OpenAlarmScreen
Start request CMD_MachineStart
Running status STS_MachineRunning
Process value PV_LinePressure
Setpoint SP_LinePressure
Recipe identifier CFG_RecipeID

Prefixes are conventions, not universal requirements. The important point is consistency and clear separation between commands, statuses, setpoints, and configuration data.

15.2 Reusable objects

Reusable screen templates, faceplates, and equipment objects reduce duplication.

For example, a motor faceplate can display:

  • Motor identification.
  • Start and stop availability.
  • Running and fault status.
  • Local or remote state.
  • Speed command and actual speed.
  • Drive fault code.
  • Relevant permissives.

The object can be reused across multiple motors with different tag assignments.

15.3 Version control and backup

Maintain controlled copies of:

  • Editable HMI project.
  • PLC project and hardware configuration.
  • HMI runtime or installation files, where available.
  • Firmware and software version records.
  • Communication settings.
  • License and activation information.
  • Approved tag and alarm lists.
  • Change history and commissioning records.

A compiled runtime file may not contain the complete editable engineering project. Back up the original source project, not only the files currently running on the panel.

16. Commissioning and validation

Commissioning should confirm that the HMI communicates correctly, displays accurate information, and behaves properly under normal and abnormal conditions.

16.1 Pre-commissioning checklist

  • Verify the HMI model and power requirements.
  • Confirm panel cutout, mounting, sealing, and environmental suitability.
  • Verify firmware and engineering software compatibility.
  • Confirm PLC address, communication driver, and network configuration.
  • Check tag names, data types, addresses, and scaling.
  • Verify screen navigation and access permissions.
  • Check alarm messages, priorities, acknowledgement, and reset behavior.
  • Verify numeric entry limits and recipe handling.
  • Confirm the project has been backed up.

16.2 Functional test checklist

  • Verify that displayed status matches actual PLC state.
  • Confirm every command has the intended effect and cannot bypass PLC permissives.
  • Verify mode-dependent command restrictions.
  • Test alarm activation, acknowledgement, clearing, and reset.
  • Verify stale-data and communication-loss indications.
  • Check values at minimum, midpoint, and maximum expected ranges.
  • Confirm operator instructions are understandable.
  • Verify user roles and engineering access restrictions.
  • Validate the defined response to HMI restart and power loss.
  • Confirm that required safety functions remain independent of the standard HMI.

16.3 Factory acceptance and site acceptance testing

FAT (Factory Acceptance Test) validates the system before installation or shipment. SAT (Site Acceptance Test) verifies the installed system in its actual operating environment.

Both should use documented test cases, expected results, actual results, deviations, corrective actions, and approval records.

A screen that opens successfully is not proof that the control system works correctly.

17. Troubleshooting HMI problems

17.1 HMI cannot communicate with PLC

Possible causes:

  • Incorrect IP address or subnet mask.
  • Duplicate IP address.
  • Wrong PLC address or communication driver.
  • Incorrect rack, slot, station, or protocol settings.
  • Disconnected cable or faulty switch port.
  • Firewall or network segmentation issue.
  • Unsupported firmware or protocol configuration.
  • PLC or HMI communication service fault.

Troubleshooting sequence:

  1. Check the HMI's displayed communication status.
  2. Verify physical link and switch-port status.
  3. Confirm IP configuration and network reachability where supported.
  4. Verify the PLC address and driver configuration.
  5. Inspect PLC diagnostics and communication counters.
  6. Check whether all tags fail or only a subset.
  7. Review HMI diagnostics and controller error logs.
  8. Restore the approved configuration after testing.

A successful network ping does not prove that the HMI driver can read or write PLC tags.

17.2 HMI values are incorrect

Check:

  • Tag address and data type.
  • Signed versus unsigned interpretation.
  • Scaling and engineering units.
  • Decimal placement.
  • Word or byte order for multiword data.
  • Whether scaling is already performed in the PLC.
  • Whether the displayed tag is stale.
  • Whether the HMI is reading the correct PLC or controller instance.

Compare the value at each layer: sensor, analog input, PLC variable, communication tag, and HMI display.

17.3 HMI button does not work

Possible causes:

  • Button object is disabled or hidden.
  • User lacks the required permission.
  • PLC is in an incompatible mode.
  • An interlock or permissive is false.
  • The HMI writes to the wrong tag.
  • A momentary pulse is too short or is not detected.
  • Communication is unavailable.
  • PLC logic clears or rejects the request.
  • Another control station has command authority.

Observe the sequence from the operator action to the PLC request, permissive evaluation, output command, and actual feedback. Do not assume that the button graphic itself is the fault.

17.4 HMI is slow or freezes

Investigate:

  • Excessive tag polling.
  • Too many animated objects.
  • Complex screen scripts.
  • Large historical data requests.
  • Slow database or network communication.
  • Insufficient HMI resources.
  • Storage problems or excessive logging.
  • Runtime software or firmware issues.

Reduce unnecessary polling and animation, optimize scripts, and separate high-frequency machine data from lower-frequency reporting data.

17.5 Alarm does not appear

Check:

  • Whether the PLC alarm condition is true.
  • Whether the HMI tag is mapped correctly.
  • Alarm thresholds and comparison logic.
  • Alarm enable conditions.
  • Alarm class filters and display settings.
  • Acknowledgement and latching logic.
  • Communication status and tag quality.
  • Alarm history and timestamp configuration.

For a critical alarm, verify the actual detection path rather than relying only on the screen display.

18. HMI cybersecurity and network reliability

HMIs can provide access to machine commands and engineering functions, making them important assets in operational technology (OT) security.

Recommended practices include:

  • Place HMIs and PLCs in appropriately segmented industrial network zones.
  • Restrict remote access to approved and monitored pathways.
  • Limit unnecessary internet connectivity.
  • Apply approved security updates and firmware changes under change control.
  • Disable unused services and ports where supported.
  • Restrict engineering software and operating-system access.
  • Maintain tested backups and a recovery procedure.
  • Monitor unauthorized configuration changes.
  • Synchronize timestamps where event correlation is required.
  • Avoid connecting untrusted removable media.

Do not casually update a production HMI's operating system or firmware. Compatibility with the runtime, PLC driver, project, and validated machine behavior must be checked first.

19. Maintenance and lifecycle management

HMI maintenance includes more than cleaning the touchscreen.

19.1 Preventive maintenance

  • Inspect the display for damage, discoloration, dead pixels, or reduced readability.
  • Check touch accuracy and physical keys.
  • Inspect mounting, seals, and connectors.
  • Check supply voltage and grounding according to the manufacturer's instructions.
  • Review communication diagnostics and error logs.
  • Verify time synchronization and event timestamps.
  • Check storage capacity and runtime stability.
  • Confirm backups are current and recoverable.
  • Review spare-part availability and obsolescence.

19.2 Replacement planning

Before replacing a failed HMI, identify:

  • Exact model and hardware revision.
  • Firmware and runtime version.
  • Editable source project and compiled runtime.
  • Communication drivers and PLC compatibility.
  • Display resolution and panel dimensions.
  • Licensing and activation requirements.
  • Network settings and security configuration.
  • Recipe, alarm, and user-data backup requirements.

A newer model may require project conversion or changes to communication configuration. Test the converted project before deployment.

19.3 Obsolescence register

A practical maintenance register can include:

Field Purpose
Machine ID Identifies the equipment
HMI manufacturer and model Identifies the installed panel
Hardware and firmware revision Supports compatibility checks
Engineering software version Identifies the development environment
PLC communication driver Supports connectivity and replacement
Project backup location Enables restoration
Spare availability Supports downtime planning
Successor model Supports migration planning
Known compatibility risks Prevents unplanned replacement failures

20. Practical example: conveyor HMI

Consider a conveyor controlled by a PLC and a variable-frequency drive.

The HMI contains:

  • Start and stop requests.
  • Auto/manual mode indication.
  • Drive-ready and drive-fault status.
  • Running feedback.
  • Speed setpoint and actual speed.
  • Conveyor permissives.
  • Active alarms and diagnostic details.
  • Production count.

The operator selects automatic mode and presses Start.

The HMI writes a start request. The PLC checks the required permissives, issues the drive command, and waits for running feedback. If the drive does not report running within the configured timeout, the PLC generates a fault. The HMI displays the fault and the relevant diagnostic information.

The operator presses Reset only after the fault condition has been addressed and the controller's reset conditions are satisfied. Resetting the fault does not automatically restart the conveyor unless the approved machine design explicitly allows that behavior.

This example illustrates the essential distinction between operator intent, controller decisions, actuator commands, and actual machine feedback.

21. Practical example: process setpoint entry

Suppose a heating process uses an HMI setpoint for a temperature controller.

The HMI permits entry of a temperature within a defined range. It validates the entry format and displays the unit. The PLC independently checks the value, operating mode, and process conditions before accepting it.

The PLC or dedicated controller compares the measured temperature with the setpoint and adjusts the heating output.

The HMI displays:

  • Target temperature.
  • Actual temperature.
  • Heater output percentage.
  • Temperature trend.
  • Active process alarms.
  • Sensor or controller fault status.

If the sensor fails, the system should follow the engineered fault response. The HMI must not continue presenting an invalid sensor value as a trustworthy process measurement.

22. Documentation required for a maintainable HMI

A complete HMI handover should include:

  • Screen list and navigation structure.
  • HMI tag database and PLC tag mapping.
  • Communication settings and network architecture.
  • Alarm list, messages, priorities, and reset conditions.
  • Recipe and parameter definitions.
  • User roles and permission matrix.
  • Software, firmware, and runtime versions.
  • Editable project and approved runtime backup.
  • FAT/SAT test records.
  • Known issues and troubleshooting instructions.
  • Recovery and replacement procedure.
  • Change history and approval records.

The documentation should allow another controls engineer to diagnose, restore, modify, and validate the HMI without depending entirely on the original developer.

23. Common HMI engineering mistakes

  • Treating an HMI command as proof that a machine action occurred.
  • Implementing essential machine logic only in HMI scripts.
  • Failing to display communication loss or stale data.
  • Allowing unlimited numeric setpoint entry.
  • Using unclear alarm messages.
  • Making every alarm the highest priority.
  • Displaying raw counts without engineering units.
  • Using color as the only indicator of a machine state.
  • Allowing unauthorized users to change critical settings.
  • Assuming an HMI reset is equivalent to repairing a fault.
  • Treating a standard touchscreen as a safety-rated control.
  • Saving only a compiled runtime instead of the editable project.
  • Failing to test power loss, restart, communication loss, and invalid inputs.

25. Interview questions and answers

Q1. What is an HMI?

An HMI is an operator interface used to monitor machine conditions, issue authorized commands, adjust permitted parameters, view alarms, and diagnose faults.

Q2. What is the difference between an HMI and a PLC?

The HMI presents information and accepts operator requests. The PLC executes control logic, evaluates permissives, manages sequences, and controls outputs.

Q3. Does pressing Start on an HMI mean the motor has started?

No. It means a start request was issued. The actual state must be confirmed through appropriate PLC or drive feedback.

Q4. What happens when HMI-to-PLC communication fails?

The HMI should indicate communication loss and avoid presenting stale data as current. The machine must follow its engineered communication-loss response, with required safety functions remaining effective.

Q5. What is an HMI tag?

A tag is a named data item representing a value or state, such as motor status, pressure, speed setpoint, or an operator request.

Q6. Why should commands and status tags be separate?

A command expresses intent, while a status reports the controller's or equipment's actual state. Keeping them separate prevents false confirmation and simplifies diagnostics.

Q7. What is a faceplate?

A faceplate is a reusable screen object that presents the status, controls, and diagnostics for an equipment item such as a motor, valve, or drive.

Q8. What is the difference between an alarm and an event?

An alarm indicates an abnormal condition that may require action. An event records a relevant occurrence, such as a mode change or recipe selection, whether or not a fault exists.

Q9. Why should the PLC validate HMI setpoints?

HMI-side validation can be bypassed or fail. The PLC must independently enforce permitted limits and operating conditions before applying a value.

Q10. Can an HMI replace a safety relay or safety PLC?

Not when a safety-rated function is required. A standard HMI is not a substitute for a properly designed and validated safety system.

Q11. Why can an HMI display the wrong analog value?

Possible causes include incorrect scaling, wrong tag mapping, data-type mismatch, invalid engineering units, incorrect signedness, or stale data.

Q12. What is the difference between HMI engineering software and runtime?

Engineering software is used to develop and configure the application. Runtime is the deployed application executing on the HMI device.

Q13. How would you troubleshoot an HMI button that does not start a machine?

Trace the complete path: operator action, HMI tag write, PLC request, operating mode, permissives, PLC output command, drive response, and actual feedback.

Q14. Why is an editable project backup important?

It enables future engineering changes and controlled restoration. A compiled runtime alone may not contain the complete source project.

Q15. What should be checked before replacing an obsolete HMI?

Check model compatibility, screen resolution, communication drivers, project conversion, firmware, licensing, network configuration, and availability of the editable source project.

Q16. What makes an HMI good for maintenance?

Clear diagnostics, actionable alarms, visible permissives, accurate feedback, consistent navigation, appropriate access control, and complete engineering documentation.

26. Final practical checklist

Before declaring an HMI ready for production, confirm:

  • Every displayed value has a known source, data type, scale, and unit.
  • Commands are requests, and actual machine status is confirmed independently.
  • PLC permissives and interlocks cannot be bypassed through ordinary HMI controls.
  • Alarms provide useful information and have defined acknowledgement and reset behavior.
  • Communication failures and stale data are clearly indicated.
  • User permissions and parameter limits are tested.
  • Power-loss, restart, and recovery behavior are documented.
  • Required safety functions remain independent of the standard HMI.
  • The editable project, configuration, and recovery files are backed up.
  • FAT/SAT results, versions, and final handover records are complete.

The central engineering principle is that an HMI should make the machine's real state understandable, provide controlled operator interaction, and support diagnosis. It should never create a false impression that a requested action succeeded when the controller and machine feedback say otherwise.
