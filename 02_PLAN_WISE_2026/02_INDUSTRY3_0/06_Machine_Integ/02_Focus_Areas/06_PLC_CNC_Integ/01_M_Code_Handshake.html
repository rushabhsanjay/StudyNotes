1. Purpose of M-code handshaking

M-code handshaking is the exchange of requests and acknowledgements between a CNC program and the machine's PLC or PMC so that auxiliary machine functions execute in the correct sequence.

A CNC program primarily defines machining operations, tool movements, feeds, spindle commands, and related machining instructions. However, many machine functions depend on external mechanisms controlled by the machine PLC or PMC.

Examples include:

  • Tool clamping and unclamping.
  • Pallet changes.
  • Automatic door operation.
  • Fixture clamping and unclamping.
  • Coolant control.
  • Chip conveyor operation.
  • Spindle orientation.
  • Parts loading and unloading.
  • Machine-specific auxiliary sequences.

An M-code may initiate one of these functions, but the actual meaning of the code depends on the CNC configuration and machine-builder implementation.

An M-code is not a universal command with identical behavior on every CNC machine. The machine builder defines the supported M-codes, their PLC/PMC logic, required interlocks, completion conditions, and alarm behavior.

2. CNC, PLC/PMC, and machine-function architecture

CNC part program
       ↓
CNC interpreter encounters M-code
       ↓
CNC-to-PLC/PMC interface
       ↓
PLC/PMC validates interlocks
       ↓
Machine sequence executes
       ↓
Sensors confirm required condition
       ↓
PLC/PMC reports completion
       ↓
CNC receives acknowledgement
       ↓
Program continues when permitted

The CNC and PLC/PMC have different responsibilities.

  • CNC: Interprets the machining program and coordinates CNC-controlled motion and program execution.
  • PLC/PMC: Controls machine auxiliary functions, evaluates interlocks, operates outputs, monitors sensors, and reports sequence status.
  • Drive and actuator systems: Execute actions such as motor rotation, clamping, or axis movement.
  • Feedback devices: Confirm conditions such as clamp position, tool presence, pressure, or door state.

On FANUC systems, the PMC performs the programmable machine-control functions. Other CNC platforms use different terminology and interfaces, but the general handshake concept remains similar.

3. What is an M-code?

An M-code is a miscellaneous or auxiliary program command used to request a machine or program-related function.

Common examples include:

M-code Common interpretation Important qualification
M03 Spindle clockwise Direction and behavior depend on the configured spindle
M04 Spindle counterclockwise May be restricted by machine or process configuration
M05 Spindle stop Actual stopping behavior depends on the machine
M06 Tool change Implementation is machine-builder dependent
M08 Coolant on Exact coolant function depends on machine configuration
M09 Coolant off May control multiple coolant functions
M19 Spindle orientation Availability and behavior vary by controller and machine
M30 Program end or reset Exact end-of-program behavior varies
M00 Program stop Requires the operator or control to resume as designed
M01 Optional stop Behavior depends on optional-stop enablement

These are common interpretations, not a substitute for the machine's programming manual.

Machine-specific codes such as pallet change, door control, fixture clamping, or probing cycles may use entirely different M-code assignments.

Before troubleshooting an M-code, verify its actual assignment in the CNC documentation and machine-builder electrical or PLC/PMC documentation.

4. Why acknowledgement is required

Many auxiliary functions take time to complete.

For example, a tool changer may need to:

  1. Verify that the spindle is stopped.
  2. Confirm the required tool-change position.
  3. Release the current tool.
  4. Move the tool changer.
  5. Grip the new tool.
  6. Return the mechanism to its operating position.
  7. Confirm that the tool is clamped and the mechanism is clear.

The CNC must not continue into a machining block that assumes the new tool is available before the machine has completed the tool change.

The acknowledgement therefore represents a defined completion condition.

A robust handshake distinguishes:

  • Request: The CNC requests the function.
  • Accepted or active: The PLC/PMC has accepted or started the operation, where the interface provides this state.
  • Complete: The required physical or logical condition has been confirmed.
  • Fault: The operation failed or did not complete as expected.

A request bit becoming active does not prove that the machine function completed successfully.

5. Typical M-code request and completion handshake

A common implementation uses an M-code request from the CNC and a completion signal from the PLC/PMC.

Conceptual signals:

Signal Typical direction Purpose
M-code request CNC to PLC/PMC Indicates the requested auxiliary function
M-code number or decode CNC to PLC/PMC Identifies the requested function
Function active PLC/PMC internal or to CNC Indicates that the machine sequence is executing
M-code complete PLC/PMC to CNC Releases the CNC to continue according to the interface
Function fault PLC/PMC to CNC or HMI Indicates that the function failed
Interlock status PLC/PMC internal Determines whether the function is permitted
Sensor feedback Field device to PLC/PMC Confirms physical conditions

The exact signal names and implementation vary by CNC platform. Some interfaces use a request-and-complete handshake, while others use decoded M-code values, interface relays, or controller-specific mechanisms.

A typical sequence is:

CNC encounters M-code
          ↓
CNC presents function request
          ↓
PLC/PMC recognizes the request
          ↓
PLC/PMC checks interlocks
          ↓
Machine function executes
          ↓
Feedback confirms completion
          ↓
PLC/PMC asserts completion acknowledgement
          ↓
CNC continues the program

If the PLC/PMC never generates the expected acknowledgement, the CNC may remain waiting at the M-code block. This is often called an M-code wait or auxiliary-function wait.

6. Request, acknowledgement, and completion are different

These terms should not be used interchangeably.

State Meaning Example
Request A function has been commanded CNC requests tool unclamping
Accepted The control has accepted the request PLC/PMC starts the unclamp sequence
In progress The mechanism is operating Hydraulic or pneumatic actuator moves
Complete The required condition is confirmed Unclamp sensor becomes active
Rejected The request cannot proceed Spindle is not stopped
Faulted The sequence failed Unclamp timeout expires

Some machine interfaces expose only request and complete. The PLC/PMC may maintain the other states internally.

Completion should represent the condition needed for the next operation, not merely the fact that an output was switched on.

For example, Clamp_Output = TRUE does not prove that the fixture is physically clamped. A suitable feedback signal or validated confirmation mechanism is needed.

7. Example: Tool-change M-code

A tool change is a useful example because it involves multiple interlocks and mechanical operations.

The following is a conceptual sequence. Actual tool-change logic varies significantly between machines.

CNC executes tool-change command
              ↓
PLC/PMC recognizes request
              ↓
Verify spindle stopped
              ↓
Verify tool-change position
              ↓
Verify tool changer ready
              ↓
Execute tool-change sequence
              ↓
Confirm old tool released
              ↓
Exchange tools
              ↓
Confirm new tool seated and clamped
              ↓
Confirm changer returned to safe operating position
              ↓
Assert M-code completion
              ↓
CNC continues machining program

Potential interlocks include:

  • Spindle stopped.
  • CNC axes at the required position.
  • Tool changer ready.
  • Magazine or arm in the correct state.
  • Pneumatic or hydraulic pressure available.
  • Tool presence confirmed.
  • Tool clamp and unclamp feedback valid.
  • No blocking machine fault active.

The precise order depends on the machine design. Never apply a generic tool-change sequence to a machine without checking the builder's documentation.

8. Example: Fixture clamp and unclamp

A CNC program may request fixture clamping before machining and unclamping after machining.

A conceptual cycle is:

CNC requests fixture clamp
              ↓
PLC/PMC checks clamp permissives
              ↓
Clamp actuator operates
              ↓
Clamp feedback is verified
              ↓
PLC/PMC reports clamp complete
              ↓
CNC proceeds with machining

For unclamping, the machine may first need to verify that the spindle is stopped, the tool is clear, and the relevant axis is in a permitted position.

Important considerations include:

  • Clamp and unclamp commands should not conflict.
  • Feedback should confirm the required physical state.
  • Pressure or force conditions may need monitoring.
  • Clamp completion should have a timeout.
  • A failed clamp must inhibit the relevant machining operation.
  • Recovery must account for the actual clamp state.

Where fixture clamping is safety-related, the required protective functions must be implemented through the validated safety architecture. An ordinary M-code acknowledgement is not proof of a safety-rated clamp condition.

9. PLC/PMC state-machine design

A state machine makes auxiliary-function sequences easier to diagnose and maintain.

For a generic machine function, states might include:

  • IDLE
  • REQUEST_RECEIVED
  • INTERLOCK_CHECK
  • EXECUTING
  • VERIFYING
  • COMPLETE
  • FAULT

Conceptual sequence:

IDLE
  ↓ Request detected
REQUEST_RECEIVED
  ↓ Request accepted
INTERLOCK_CHECK
  ↓ Conditions satisfied
EXECUTING
  ↓ Actuator action completed
VERIFYING
  ↓ Feedback confirmed
COMPLETE
  ↓ Handshake released
IDLE

Any applicable state
  ↓ Fault or timeout
FAULT
  ↓ Approved recovery
IDLE

A production implementation should define how each state is entered and exited, how outputs behave during faults, and how the CNC request and completion signals are released.

Avoid logic in which an acknowledgement remains active indefinitely and unintentionally satisfies a later M-code request.

10. M-code request decoding

In some CNC systems, the PLC/PMC receives a decoded M-code number or a combination of interface signals representing the requested function.

The PLC/PMC uses this information to execute the corresponding machine sequence.

Conceptual mapping:

M-code identifier Machine function Required completion condition
Configured code A Fixture clamp Clamp condition confirmed
Configured code B Fixture unclamp Unclamp condition confirmed
Configured code C Pallet change Pallet transfer and positioning confirmed
Configured code D Machine door operation Door reaches the commanded state
Configured code E Auxiliary cleaning cycle Defined cleaning sequence completes

The identifiers are placeholders, not actual M-code assignments.

The implementation should consider how requests are decoded, whether the code is accompanied by a request signal, how simultaneous or repeated requests are handled, and how the completion acknowledgement is associated with the correct function.

Do not assume that an M-code number is transmitted as an ordinary binary value unless the controller's interface documentation confirms it.

11. Modal and non-modal machine functions

M-codes may behave differently depending on their programming semantics.

Some commands affect a state that remains active until another command changes it. Others initiate a discrete action or event.

For example, spindle direction and coolant state commonly behave as persistent operating states, whereas a machine-builder-defined pallet-change command typically initiates a sequence that must complete.

The precise behavior depends on the controller and machine configuration.

This distinction matters because a persistent command state is not always suitable for a request/acknowledgement handshake. The interface must follow the actual CNC command semantics and the PLC/PMC implementation.

12. Timeout handling

Every auxiliary sequence that can wait for a physical condition should have suitable timeout handling.

For example, a clamp command may energize an actuator, but the clamp-confirmation sensor never changes state.

A timeout detects that the expected completion condition did not occur within the permitted interval.

Typical timeout categories include:

Timeout What it monitors Diagnostic focus
Request timeout Time to recognize or accept an M-code request Request mapping and interface state
Actuation timeout Time for the mechanism to move Actuator, pressure, obstruction, or output fault
Feedback timeout Time to receive the expected confirmation Sensor state, wiring, or mechanical condition
Completion timeout Time until the overall function is complete Sequence logic or an unmet interlock
Handshake-release timeout Time for the request or acknowledgement to return to the expected state Interface release logic or CNC state

Timeout values should be based on actual mechanism behavior, controller timing, and machine requirements.

When a timeout occurs, the PLC/PMC should preserve diagnostic information and execute the defined fault response. Repeatedly resetting the timeout without identifying the cause can create additional faults or unsafe machine conditions.

Symptom Possible cause Diagnostic action
CNC remains waiting at an M-code Completion acknowledgement never arrives Monitor the request, PLC/PMC sequence state, and completion signal
M-code executes the wrong function Incorrect decoding or machine-specific mapping Verify the configured M-code assignment
Function starts but never completes Missing feedback or mechanical failure Inspect the actuator and associated sensors
CNC continues before the mechanism finishes Completion condition is incorrect or asserted too early Verify the acknowledgement logic and physical completion criteria
M-code works intermittently Timing race or unstable feedback Monitor request transitions and feedback timing
Function is rejected immediately Required interlock is false Identify the exact failed permissive
A previous acknowledgement releases a new request Handshake not cleared correctly Review request and completion release behavior
Tool-change sequence stops midway Tool changer, clamp, sensor, or sequence-state fault Check the current state and tool-change diagnostics
Clamp command is active but clamp feedback is absent Actuator, pressure, sensor, or wiring problem Check outputs, physical movement, pressure, and sensor status
CNC reports an auxiliary-function alarm PLC/PMC sequence timeout or controller-specific error Read the alarm details and inspect the related interface signals

M-code works in one program but not another Different modal state, sequence context, or program assumptions Compare the program blocks and machine prerequisites

14. Troubleshooting method

When the CNC stops at an M-code, troubleshoot in a defined order rather than randomly forcing outputs.

  1. Identify the actual M-code. Check the CNC program block and the machine-builder's M-code assignment.
  2. Confirm the request. Determine whether the CNC has issued the expected request and whether the PLC/PMC recognizes it.
  3. Inspect interlocks. Check every condition required to start the machine function.
  4. Identify the current sequence state. Determine whether the PLC/PMC is idle, executing, verifying, or faulted.
  5. Check output commands. Verify that the correct actuator command is being issued.
  6. Check physical feedback. Confirm that the mechanism and sensors behave as expected.
  7. Inspect timers and diagnostics. Find which expected condition failed to arrive.
  8. Verify completion logic. Confirm that acknowledgement is issued only when the required completion condition is satisfied.
  9. Recover according to procedure. Correct the cause and restore the sequence without bypassing interlocks.

Use CNC diagnostic pages, PLC/PMC monitoring, electrical drawings, sensor indicators, and the machine-builder's documentation together. Any signal forcing or controlled test must follow the approved procedure and account for machine hazards.

15. Commissioning checklist

Interface verification

  • Confirm the M-code's actual machine-specific meaning.
  • Verify CNC-to-PLC/PMC request mapping.
  • Verify completion acknowledgement mapping.
  • Confirm request and acknowledgement release behavior.
  • Identify all interlocks and feedback conditions.
  • Verify the intended CNC program behavior when the function is incomplete.

Functional testing

  • Test the function under approved commissioning conditions.
  • Verify that required interlocks prevent an invalid operation.
  • Confirm that completion follows the required feedback.
  • Test timeout behavior using an approved test method.
  • Verify fault and alarm messages.
  • Confirm that the CNC does not continue prematurely.
  • Check for duplicate requests and stale acknowledgements.
  • Verify the defined recovery procedure.

Documentation

  • Maintain the M-code assignment list.
  • Document the request and acknowledgement signals.
  • Record interlocks, timers, and expected feedback.
  • Document the sequence states and fault responses.
  • Preserve the approved PLC/PMC and CNC configurations.
  • Record commissioning results and known machine-specific behavior.

16. Interview questions and answers

1. What is an M-code handshake?

It is the coordinated exchange between a CNC program and the PLC/PMC that allows a machine function to be requested, executed, and acknowledged before the CNC proceeds.

2. Why does a CNC sometimes stop at an M-code?

The CNC may be waiting for the PLC/PMC to complete the requested function and return the expected acknowledgement. A missing request decode, unmet interlock, failed mechanism, or timeout can prevent completion.

3. What is the difference between an M-code request and its acknowledgement?

The request identifies the desired action. The acknowledgement indicates that the required completion condition has been satisfied according to the interface definition.

4. Is M06 implemented identically on every CNC?

No. Although it commonly represents a tool change, the detailed sequence and interface are machine-builder dependent.

5. Why is sensor feedback important in an M-code sequence?

It confirms the required physical condition rather than merely confirming that an output command was issued.

6. What is an M-code timeout?

It is a time limit for an expected event, such as request acceptance, actuator movement, feedback confirmation, or completion acknowledgement.

7. How should an M-code wait be diagnosed?

Identify the code, monitor the request, check the PLC/PMC state and interlocks, inspect actuator outputs and feedback, and determine why the completion condition was not reached.

8. Why must acknowledgements be cleared correctly?

A stale acknowledgement may release a later request before its associated machine function has completed.

9. What is the role of the PLC/PMC in tool changing?

It typically coordinates the machine-specific tool-change sequence, checks interlocks, operates the mechanism, monitors feedback, and reports completion to the CNC.

10. Why is an output command not sufficient proof of completion?

An actuator can fail to move despite receiving a command. Completion must be based on the required feedback or another validated confirmation mechanism.

11. What is the difference between a persistent M-code state and a discrete auxiliary action?

A persistent state remains in effect until changed, while a discrete action initiates a sequence or event. Their implementation and handshake requirements differ.

12. What is the most important M-code handshake design principle?

The CNC should continue only when the defined machine-function completion condition has been satisfied and the associated acknowledgement has been correctly generated.

17. Final engineering principles

  • Verify machine-specific M-code assignments before diagnosing or changing logic.
  • Separate the CNC request from the PLC/PMC completion acknowledgement.
  • Check interlocks before actuating machine mechanisms.
  • Confirm physical completion using appropriate feedback.
  • Implement timeouts and meaningful diagnostic messages.
  • Prevent stale acknowledgements and duplicate requests.
  • Preserve the machine's intended sequence and recovery behavior.
  • Do not bypass protective functions to force an M-code to complete.

M-code handshaking connects the CNC program to the physical machine. The essential requirement is to ensure that the machine function actually reaches its required state before the CNC is allowed to continue.
