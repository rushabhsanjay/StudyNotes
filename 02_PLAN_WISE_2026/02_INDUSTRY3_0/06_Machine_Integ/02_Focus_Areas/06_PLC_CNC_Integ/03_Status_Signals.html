1. Purpose of CNC status signals

CNC status signals communicate the current operating condition of a CNC machine to the PLC/PMC, HMI, operator, and connected systems. They help determine whether the machine is ready for operation, executing a cycle, waiting for a condition, experiencing an alarm, or recovering from a fault.

Status signals are essential for:

  • Machine sequencing and interlocks.
  • Automatic cycle control.
  • CNC-to-PLC/PMC coordination.
  • HMI indication and operator guidance.
  • Alarm handling and recovery.
  • Production monitoring and downtime analysis.
  • Cycle-time measurement and OEE calculations.
  • Data collection by SCADA, MES, or other production systems.

A status signal is useful only when its meaning is defined precisely. For example, Machine_Ready should not automatically mean that the machine is powered on, that the CNC is in automatic mode, or that a new cycle can start. Those are different conditions.

2. Status-signal architecture

CNC internal state and diagnostics
              ↓
CNC interface signals
              ↓
PLC/PMC reads and interprets status
              ↓
Machine-state logic and interlocks
              ↓
HMI / operator indication / production data
              ↓
SCADA / MES / historian / reporting

The machine PLC/PMC may also combine CNC status with physical feedback and machine-specific conditions before generating a machine-level status.

For example, CNC readiness may be true while a machine-level permissive remains false because hydraulic pressure is low or a fixture is not ready.

CNC ready status -----------+
Hydraulic pressure OK ------+
Tool system ready ----------+--> Machine readiness logic
No blocking machine fault --+
Required interlocks OK -----+
                                      ↓
                              Machine ready status

This is a conceptual example. The actual conditions must follow the machine-builder's design.

3. Main categories of CNC status signals

Category Typical signals Purpose
Readiness CNC ready, machine ready, drive ready Indicates whether defined operating conditions are satisfied
Operating mode Auto, MDI, manual, reference return Identifies the selected operating mode
Cycle state Cycle active, cycle complete, cycle stopped Reports the current machining or machine-cycle condition
Execution state Program running, feed hold, single block Describes CNC program execution
Alarm state CNC alarm, machine alarm, drive fault Indicates a detected abnormal condition
Motion state Axis moving, spindle running, axis in position Reports motion-related conditions
Auxiliary-function state Tool change active, M-code complete Supports machine-function sequencing
Communication state CNC communication healthy, interface valid Indicates whether status information can be trusted
Recovery state Reset active, recovery required Indicates a reset or recovery-related condition

Not every controller exposes every signal in the same form. Some states may be available as individual bits, diagnostic variables, numeric codes, or controller-specific status words.

4. Ready status

4.1 What does CNC ready mean?

A CNC-ready signal indicates that the CNC has reached a defined state in which the relevant control functions are available. The exact meaning depends on the controller and interface specification.

A separate machine-ready signal may indicate that the broader machine system satisfies the conditions required for a particular operation.

Possible readiness conditions include:

  • CNC control initialized.
  • Required drives ready.
  • No blocking CNC alarm.
  • Required reference-return or homing conditions satisfied.
  • Machine sequence initialized.
  • Necessary hydraulic or pneumatic systems available.
  • Required tool or fixture conditions satisfied.
  • Safety-related permissives satisfied through the applicable safety system.

These conditions are examples, not a universal checklist. A machine may be CNC-ready but not ready to start automatic production.

4.2 Distinguish related readiness signals

Signal Typical meaning What it does not automatically prove
Control powered Control power is available CNC is initialized or ready
CNC ready Defined CNC readiness conditions are met All machine auxiliary systems are ready
Drive ready A drive reports its defined ready state The machine can start a complete cycle
Machine ready Defined machine-level permissives are satisfied Production will necessarily complete successfully
Cycle start permitted Conditions for a particular start request are satisfied A cycle is already running
Safety system healthy Safety system reports its defined healthy state Every normal machine permissive is satisfied

The status definitions must be documented separately even if an HMI displays them together.

4.3 Example readiness logic

A conceptual machine-level readiness condition can be represented as:

\[ \text{MachineReady} = \text{CNCReady} \land \text{DriveReady} \land \text{AuxiliarySystemsReady} \land \text{NoBlockingFault} \land \text{RequiredPermissives} \]

The expression illustrates logical combination only. A production design must explicitly define the relevant permissives, signal validity, startup behavior, and fault handling.

4.4 Readiness troubleshooting

If CNC ready is false, investigate the CNC diagnostics and controller-specific readiness conditions.

If CNC ready is true but machine ready is false, inspect the PLC/PMC readiness logic and identify the failed permissive.

A practical diagnostic sequence is:

  1. Confirm control power and initialization.
  2. Check CNC alarms and diagnostic status.
  3. Inspect drive-ready and reference-return conditions where relevant.
  4. Check machine auxiliary-system feedback.
  5. Identify the exact permissive preventing readiness.
  6. Verify the signal at its source and destination.
  7. Correct the cause and confirm that readiness returns normally.

Do not force the ready signal to bypass the condition that prevented it from becoming true.

5. Alarm status

5.1 What is an alarm?

An alarm reports a condition that requires attention, intervention, or a defined response. Depending on the machine, it may originate from the CNC, PLC/PMC, drive system, tool changer, hydraulic system, pneumatic system, or another subsystem.

Examples include:

  • CNC program or configuration errors.
  • Servo or spindle drive faults.
  • Axis overtravel conditions.
  • Tool-change failure.
  • Low hydraulic pressure.
  • Missing fixture feedback.
  • Door or guarding faults.
  • Communication failures.
  • Auxiliary-function timeouts.

An alarm signal may be a single summary bit, a numeric alarm identifier, or a combination of status and diagnostic information.

5.2 Alarm categories

Alarm category Example Typical diagnostic source
CNC alarm Program or control-related error CNC alarm display and diagnostics
Servo alarm Drive fault or following error Servo drive and CNC diagnostics
Spindle alarm Spindle drive or orientation fault Spindle drive and CNC diagnostics
Machine alarm Failed machine sequence or missing permissive PLC/PMC logic and HMI
Auxiliary-function alarm M-code sequence timeout CNC interface and PLC/PMC sequence
Communication alarm Loss of communication or invalid data Network diagnostics and interface status
Process alarm Process condition outside defined limits Machine sensors and process logic

The alarm category helps identify where to start investigating, but the alarm source and root cause are not always the same. A CNC may report a timeout caused by a mechanical obstruction or a failed sensor.

5.3 Alarm present versus alarm history

These concepts must be separated:

  • Active alarm: The abnormal condition is currently present according to the alarm logic.
  • Latched alarm: The alarm remains recorded until its defined reset or acknowledgement conditions are met.
  • Alarm history: A record of previous alarm events.
  • Alarm acknowledgement: An operator or control action that acknowledges the displayed alarm.
  • Fault recovery: The actions needed to restore the machine to a valid operating state.

Acknowledging an alarm does not necessarily clear the underlying fault. Resetting an alarm does not prove that the machine is ready to operate.

5.4 Alarm signal design

A good alarm interface should provide more than a generic Alarm = TRUE signal where the controller supports richer information.

Useful fields include:

  • Alarm-present status.
  • Alarm identifier or number.
  • Alarm source or subsystem.
  • Timestamp or event time.
  • Alarm severity or classification, if supported.
  • Acknowledgement status, if relevant.
  • Recovery state or reset requirement.

The exact available fields depend on the CNC, PLC/PMC, and machine-builder implementation.

6. Cycle-state signals

Cycle-state signals describe the progression of a machining or machine sequence. They are critical for sequencing, production reporting, cycle-time analysis, and fault diagnosis.

Common states include:

  • Idle.
  • Ready to start.
  • Cycle starting.
  • Cycle active.
  • Feed hold or paused.
  • Waiting for an auxiliary function.
  • Cycle completed.
  • Cycle stopped or aborted.
  • Recovery required.

These states should be explicitly defined because different controllers may expose different signals and transition behavior.

6.1 Cycle active

A cycle-active signal typically indicates that a defined machine cycle is in progress. However, the exact definition matters.

It might indicate that:

  • The CNC program is executing.
  • An automatic machine sequence is active.
  • The overall production cycle has started and has not yet completed.
  • A particular machine operation is in progress.

These meanings are not equivalent. A CNC program may be executing while the machine waits for an auxiliary function. Conversely, a machine-level sequence may remain active while CNC program execution is temporarily paused.

6.2 Cycle complete

Cycle complete indicates that the defined cycle has reached its completion condition.

The completion condition might require:

  • CNC program completion.
  • Completion of required auxiliary functions.
  • Return to a defined machine state.
  • Completion of part unloading or other machine-specific actions.

A program-end indication is not automatically equivalent to a finished production part. The production system must define which event marks completion of the entire manufacturing cycle.

6.3 Cycle stopped or aborted

A cycle may stop because of:

  • Operator stop request.
  • Feed hold.
  • CNC or machine alarm.
  • Emergency-stop event.
  • Interlock violation.
  • Program end.
  • A machine-specific abort condition.

The system should distinguish a normal cycle completion from an interrupted or aborted cycle. Otherwise, production reports can count incomplete parts as completed production.

7. CNC execution states versus machine-cycle states

The CNC program execution state and the machine's production-cycle state are related, but they should not be treated as the same variable.

Condition CNC program execution Machine cycle interpretation
Automatic program executing Running Usually active
Feed hold Paused or held Cycle may remain active
Waiting for M-code completion Program may be waiting Machine cycle may still be active
Program ended normally Execution completed or ended Machine cycle may require further completion checks
Alarm interrupts execution Stopped, interrupted, or alarmed Cycle may be aborted or require recovery
Manual jog No automatic program execution required Usually not a production cycle
MDI execution A command or block is executing Depends on machine-cycle definition

The mapping must use the actual controller signals and define the intended production semantics.

8. Cycle-state model

A simple conceptual machine-cycle state model is:

IDLE
  ↓ Valid start request
STARTING
  ↓ Start conditions confirmed
ACTIVE
  ↓ Temporary hold or wait
PAUSED_OR_WAITING
  ↓ Conditions restored
ACTIVE
  ↓ Normal completion condition
COMPLETE
  ↓ Cycle reset or next-cycle preparation
IDLE

ACTIVE / STARTING / PAUSED_OR_WAITING
  ↓ Blocking fault or abort
STOPPED_OR_FAULTED
  ↓ Approved recovery
IDLE or RECOVERY

This is an example state model, not a universal CNC state sequence. The actual machine may require additional states for loading, clamping, tool changing, probing, unloading, or safety-related recovery.

A robust implementation should define:

  • Entry conditions for every state.
  • Exit conditions for every state.
  • Priority between normal completion and faults.
  • Behavior when a signal becomes invalid.
  • Reset and recovery rules.
  • How state changes are logged.
  • How the state is communicated to the CNC, HMI, and production systems.

9. State transition logic and signal quality

A status bit should not be interpreted in isolation if its meaning depends on sequence context.

For example, Cycle_Active = FALSE might mean the machine is idle, the cycle has completed, the cycle has been aborted, or the status communication has failed.

For this reason, useful implementations combine status signals with a defined state model and fault handling.

A numeric state identifier can sometimes provide clearer information than multiple overlapping Boolean bits. However, its numeric values must be documented and interpreted consistently by all consumers.

Example conceptual state definitions:

State value Meaning Production interpretation
0 Idle No production cycle active
1 Starting Cycle initiation in progress
2 Active Production cycle executing
3 Paused or waiting Cycle has not completed
4 Complete Defined cycle completion condition met
5 Faulted or aborted Cycle did not complete normally
6 Recovery Machine requires a defined recovery sequence

These values are illustrative only. They must not be assumed to match a real controller or machine.

10. Signal timing, latching, and reset behavior

Status signals may be levels, pulses, latched conditions, or values updated through a communication interface.

A short Cycle_Complete pulse may be missed by a receiving system if the pulse is shorter than its effective sampling interval. A latched completion state may be easier to consume, but it needs a clearly defined clearing condition.

For each important status signal, document:

  • When it becomes active.
  • Whether it remains active while the condition persists.
  • Whether it is latched.
  • Who clears it.
  • Whether it is cleared automatically or by an explicit reset.
  • What happens after controller startup or a communication interruption.
  • Whether the receiving system can detect stale data.

Do not use an arbitrary delay as a substitute for a properly defined handshake or state transition.

11. Alarm priority and machine-state interaction

Alarm logic and cycle-state logic must be coordinated.

For example, a blocking fault during a cycle may require the machine to leave the normal active state and enter a faulted state. The cycle must not be marked complete merely because the program stopped executing.

A conceptual priority order might be:

  1. Validated safety-related response.
  2. Blocking fault or abort handling.
  3. Required recovery state.
  4. Normal cycle progression.
  5. Idle or ready indication.

This is a general design consideration, not a substitute for the machine's approved safety and control design.

The system should distinguish faults that stop production from warnings that permit continued operation, where the machine design supports that distinction.

12. Mapping CNC status to an HMI

The HMI should communicate the machine state in a way that helps the operator decide what action is required.

Useful HMI indications include:

  • CNC ready or not ready.
  • Machine ready or start inhibited.
  • Current operating mode.
  • Cycle active, paused, complete, or faulted.
  • Active alarm and alarm description.
  • Required operator action.
  • Machine recovery status.

Avoid presenting a single green READY indicator when the underlying system contains several independent readiness conditions. If the machine is not ready, the HMI should help identify the condition preventing operation.

Example:

HMI message Supporting status Operator value
CNC not ready CNC-ready status false Directs attention to CNC diagnostics
Machine not ready Machine-ready status false Directs attention to machine permissives
Cycle paused Cycle active with hold condition Indicates the cycle has not completed
Auxiliary function waiting M-code request active without completion Directs attention to the machine sequence
Machine faulted Blocking machine fault active Indicates that recovery is required
Cycle complete Defined cycle-completion condition met Supports unloading or next-cycle preparation

13. Status signals for SCADA and production reporting

Status signals often feed higher-level systems for production monitoring and downtime analysis.

Typical collected data includes:

  • Machine state.
  • Cycle-start and cycle-complete events.
  • Active alarm identifier.
  • Alarm occurrence and clear times.
  • Automatic, manual, or setup mode.
  • Cycle duration.
  • Idle duration.
  • Downtime duration.
  • Communication-health state.

The meaning of every collected state must be standardized before it is used for reporting.

For example, if one machine reports Cycle_Active during feed hold while another machine clears it during feed hold, comparing their cycle times without normalization can produce misleading results.

Cycle-time measurement

A basic elapsed cycle-time measurement is:

\[ T\_{\text{cycle}} = t\_{\text{complete}} - t\_{\text{start}} \]

The equation is useful only when start and completion events have consistent definitions.

A production cycle may include loading, clamping, machining, tool changing, unloading, and other machine-specific operations. Define whether these operations are included in the measured cycle.

Downtime measurement

A simple downtime interval can be calculated as:

\[ T\_{\text{downtime}} = t\_{\text{restored}} - t\_{\text{stop}} \]

The reporting system must define which stops count as downtime, when the downtime interval begins, and which event marks restoration.

Alarm occurrence alone may not be the correct downtime start event, especially when the machine is already idle.

14. Common status-signal faults

Symptom Possible cause Diagnostic approach
CNC ready remains false CNC alarm, drive not ready, or initialization incomplete Inspect CNC diagnostics and readiness conditions
CNC ready is true but machine ready is false Machine-level permissive is missing Find the false permissive in PLC/PMC logic
Cycle active remains true after a stop State transition or reset logic is incomplete Review stop handling and state-release conditions
Cycle complete appears too early Completion criteria are incomplete Verify all required machine-function completion conditions
Alarm remains active after correction Latched alarm or reset condition not satisfied Inspect the alarm reset and acknowledgement logic
HMI shows idle during a paused cycle Incorrect mapping between execution and cycle states Compare CNC execution state with machine-cycle state
SCADA records duplicate cycle starts Event logic or edge detection is incorrect Inspect the start event generation and state transitions
Production count increments after an aborted cycle Count logic is tied to program stop rather than valid completion Link counting to the approved production-completion event
Status flickers between states Signal timing, unstable feedback, or inconsistent state logic Trend raw signals and inspect state transitions
Status is frozen after network failure Stale data is treated as valid Add communication-health and data-validity handling
Alarm bit is active but no useful alarm appears Alarm identifier or HMI mapping is incorrect Verify alarm number, source, and display mapping
Machine appears ready despite an unsafe condition Readiness logic is incorrect or safety-state assumptions are invalid Stop operation and verify the approved control and safety design

15. Troubleshooting procedure

When a CNC status indication is incorrect, follow the signal path from the source to the final display or consuming logic.

  1. Identify the exact status signal and its documented definition.
  2. Check the CNC diagnostic page or native status variable.
  3. Verify the interface mapping to the PLC/PMC.
  4. Confirm the raw signal value and polarity.
  5. Inspect PLC/PMC logic that combines the signal with other conditions.
  6. Check the resulting machine-state or HMI variable.
  7. Review active alarms and relevant state transitions.
  8. Trend the signals if the issue is intermittent.
  9. Verify startup, reset, and communication-loss behavior.
  10. Correct the underlying mapping or logic and retest the affected operation.

For an incorrect readiness signal, identify the exact unmet permissive. For a cycle-state problem, examine the transitions into and out of each state. For an alarm problem, distinguish the active condition from its latch, acknowledgement, and history behavior.

Do not force readiness or suppress a blocking alarm merely to make the HMI look correct.

16. Commissioning checklist

Ready status

  • Confirm the meaning of CNC ready and machine ready separately.
  • Verify all required readiness conditions.
  • Confirm behavior when a required drive or auxiliary system is unavailable.
  • Verify that blocking faults prevent the appropriate operation.
  • Confirm startup and reset behavior.

Alarm status

  • Verify alarm sources and identifiers.
  • Confirm active, latched, acknowledged, and cleared behavior.
  • Check alarm messages and operator guidance.
  • Confirm that fault recovery does not bypass required interlocks.
  • Verify alarm history or event logging where required.

Cycle state

  • Define idle, starting, active, paused, complete, and faulted states as applicable.
  • Verify each state transition.
  • Confirm that feed hold and auxiliary-function waits are interpreted correctly.
  • Verify that an aborted cycle is not counted as normally completed.
  • Check state reset and recovery behavior.
  • Confirm consistency between CNC, PLC/PMC, HMI, and production reporting.

Data collection

  • Define cycle-start and cycle-complete events.
  • Standardize state definitions across machines.
  • Verify timestamps and event ordering.
  • Check communication-health and stale-data handling.
  • Validate cycle-time and downtime calculations against actual machine behavior.

17. Interview questions and answers

1. What is a CNC-ready signal?

It indicates that the CNC satisfies its defined readiness conditions. It does not automatically mean that all machine auxiliary systems are ready for production.

2. What is the difference between CNC ready and machine ready?

CNC ready describes the CNC's readiness according to its interface definition. Machine ready usually represents a broader set of conditions involving the CNC, PLC/PMC, auxiliary systems, and machine permissives.

3. What is the difference between an active alarm and alarm history?

An active alarm represents a current or latched alarm condition according to the controller's logic. Alarm history records previous events, including alarms that may no longer be active.

4. Does acknowledging an alarm clear the fault?

Not necessarily. Acknowledgement and fault correction are different operations. The underlying condition and required reset procedure must be addressed.

5. What does cycle active mean?

It indicates that the defined machine or production cycle is in progress. Its exact meaning must specify how pauses, waits, and recovery states are handled.

6. Is cycle complete the same as program end?

Not always. The machine may require additional auxiliary operations or part-handling steps before the complete production cycle has finished.

7. Why distinguish feed hold from cycle completion?

Feed hold generally pauses execution without proving that the production cycle is finished. Treating it as completion can corrupt production counts and cycle-time reporting.

8. How should a machine-ready signal be generated?

It should be derived from documented readiness conditions and valid interlocks, with explicit handling of faults, initialization, and invalid data.

9. Why is state-machine logic useful?

It defines the machine's operating states and transitions, making abnormal transitions, incomplete sequences, and recovery conditions easier to diagnose.

10. How do status signals support OEE?

Consistently defined machine states and production events can support availability, performance, and quality calculations. The definitions must be standardized and validated before comparing results.

11. How do you troubleshoot a false machine-ready indication?

Trace the signal from its source through CNC and PLC/PMC logic to the consuming interface, then inspect the actual permissives and their physical feedback.

12. What is the risk of stale status data?

A receiving system may continue to display an old ready or cycle state after communication has failed. Communication health and data validity must therefore be monitored.

18. Key engineering principles

  • Define CNC readiness separately from machine readiness.
  • Distinguish active alarms, latched alarms, acknowledgements, and alarm history.
  • Separate CNC program execution state from the overall machine-cycle state.
  • Define cycle-start, cycle-complete, and abort conditions precisely.
  • Ensure status transitions are consistent across CNC, PLC/PMC, HMI, and SCADA.
  • Detect invalid or stale data instead of treating it as a valid machine state.
  • Use actual feedback and approved interlocks to determine readiness.
  • Never bypass safety functions to manipulate a normal status bit.
  • Validate reporting logic against real machine operation before using the data for OEE or production decisions.

Reliable status signals provide a consistent picture of what the CNC and machine are actually doing. Their value comes from clear definitions, correct mapping, dependable timing, and properly designed state transitions.
