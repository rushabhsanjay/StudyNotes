1. Purpose of PLC/PMC-to-CNC I/O mapping

PLC/PMC-to-CNC I/O mapping defines how signals are exchanged between the machine-control logic and the CNC controller. It establishes which signals the CNC receives from the PLC/PMC, which signals the PLC/PMC receives from the CNC, how those signals are represented, and what each signal means.

In CNC machine integration, the CNC and PLC/PMC perform different but closely coordinated jobs.

  • CNC: Executes the part program, coordinates machining axes, manages spindle functions, and evaluates CNC operating conditions.
  • PLC/PMC: Controls machine sequences, auxiliary devices, interlocks, actuators, and machine-level logic.
  • Physical I/O: Connects field sensors, switches, actuators, drives, and other devices to the control system.
  • CNC interface: Exchanges internal status, commands, requests, and acknowledgements between the CNC and PLC/PMC.

A signal can be logically exchanged between the CNC and PLC/PMC without being connected to a physical terminal. Many interfaces use internal memory, interface relays, data areas, or controller-specific communication mechanisms.

The central engineering question is: Which control owns the signal, where is it represented, and what does the signal mean at the point where it is consumed?

2. Overall signal architecture

Physical sensors and switches
          ↓
Remote I/O or local PLC/PMC inputs
          ↓
PLC/PMC logic and machine sequence
          ↓
PLC/PMC-to-CNC interface
          ↓
CNC interface logic
          ↓
CNC program, motion, or status logic

The reverse direction follows the corresponding path:

CNC program or CNC internal state
          ↓
CNC-to-PLC/PMC interface
          ↓
PLC/PMC input data or interface signals
          ↓
PLC/PMC sequence and interlock logic
          ↓
PLC/PMC outputs or internal commands
          ↓
Actuators, drives, and machine mechanisms

This is a conceptual architecture. Actual signal paths depend on the CNC platform, PLC/PMC implementation, fieldbus arrangement, and machine-builder design.

3. Understand the different meanings of I/O

The word I/O can refer to several different layers. Mixing them up leads to incorrect wiring assumptions and difficult troubleshooting.

I/O category Meaning Example
Physical input Signal entering a controller from a field device Door-closed sensor
Physical output Signal leaving a controller to operate a device Hydraulic valve command
Internal PLC/PMC bit Logical state used within the control program Clamp sequence active
CNC interface signal Signal exchanged between CNC and PLC/PMC CNC cycle-start request
Data interface Numeric or structured information exchanged between controls M-code number or tool data
Network I/O Cyclic or acyclic data transferred over an industrial network Remote I/O status word

A CNC interface bit is not automatically a physical PLC input. For example, the CNC may publish a cycle-start request through an internal interface area. The PLC/PMC reads that signal in its logic, checks the permissives, and then initiates the machine sequence.

4. Signal direction and ownership

Every mapped signal should have a clearly defined producer and consumer.

  • CNC to PLC/PMC: CNC-originated commands, requests, program state, or operation information.
  • PLC/PMC to CNC: Machine readiness, interlock status, completion acknowledgements, and machine conditions required by CNC logic.

Signal direction must be documented from the perspective of the interface, not assumed from a physical input/output address.

Signal example Producer Consumer Typical purpose
Cycle-start request CNC or operator interface, depending on design PLC/PMC Requests a machine cycle
Machine-ready status PLC/PMC CNC Indicates required machine conditions are satisfied
M-code request CNC PLC/PMC Requests an auxiliary machine function
M-code completion PLC/PMC CNC Indicates the configured function-completion condition
Spindle-stop status Spindle control or CNC logic PLC/PMC Supports a sequence requiring a stopped spindle
Door-closed status Door sensor through the assigned control CNC and/or PLC/PMC logic Indicates the door's reported state
Tool-change active PLC/PMC CNC or HMI Reports that a tool-change sequence is active
Machine alarm status PLC/PMC CNC or HMI Reports a machine-side fault

These are functional examples. The actual source, destination, signal names, and safety significance must be verified against the machine's documentation.

5. Signal mapping table

A signal mapping table is the primary engineering document for controlling the interface.

A useful mapping record includes:

  • Unique signal identifier.
  • Functional name and description.
  • Signal producer and consumer.
  • Direction.
  • Data type and representation.
  • Source and destination address or interface location.
  • Normal and active states.
  • Update behavior.
  • Preconditions and interlocks.
  • Alarm response and diagnostic notes.

Example mapping table:

Signal ID Function Direction Type Active meaning
CNC_REQ_START Cycle-start request CNC to PLC/PMC Boolean Start request is present
PLC_MACHINE_READY Machine ready PLC/PMC to CNC Boolean Defined readiness conditions are satisfied
CNC_M_CODE_REQ Auxiliary-function request CNC to PLC/PMC Boolean or interface-specific An M-function request is active
CNC_M_CODE_NUM M-code identifier CNC to PLC/PMC Numeric or encoded data Identifies the requested M-code
PLC_M_CODE_FIN M-function completion PLC/PMC to CNC Boolean or interface-specific Defined completion condition is satisfied
PLC_MACHINE_ALARM Machine alarm PLC/PMC to CNC Boolean or status data A machine fault is reported
PLC_CYCLE_ACTIVE Machine cycle active PLC/PMC to CNC Boolean The defined cycle-active condition is present
PLC_DOOR_CLOSED Door-closed status Assigned sensor/control to consumer Boolean Door-closed feedback is active

The identifiers above are illustrative names, not standard CNC interface labels. Do not copy them into a real project without defining the signal mapping and confirming the platform-specific interface.

6. Addressing and interface representation

CNC and PLC/PMC platforms use different methods to represent interface signals. Depending on the system, a signal may be accessed through:

  • Named PLC/PMC variables.
  • Internal relay or memory addresses.
  • CNC interface data areas.
  • Byte, word, or double-word data.
  • Structured or symbolic tags.
  • Fieldbus input/output assemblies.
  • OEM-defined interface blocks or data structures.

The address format and meaning are controller-specific.

For example, a FANUC PMC ladder may use controller-specific relay areas and interface signals. Siemens CNC systems may use PLC interface signals and OEM-defined data areas. Other CNC platforms have their own interface conventions.

Never assume that an address from one CNC model, series, or machine builder is valid on another. Confirm the controller model, software version, machine-builder interface documentation, and actual PLC/PMC project.

Boolean signals

A Boolean signal represents a logical state, typically true or false.

Examples include:

  • Machine ready.
  • M-code request active.
  • Door closed.
  • Tool clamped.
  • Alarm active.

However, the electrical state and logical state are not necessarily identical. Normally closed circuits, inverted logic, active-low inputs, and software negation can change the relationship between voltage and the interpreted Boolean value.

Numeric and encoded data

Some interfaces carry more than one bit of information. Examples include:

  • M-code identifiers.
  • Selected tool number.
  • Program or job number.
  • Axis or machine status values.
  • Numeric parameters used by a machine sequence.

For numeric data, document the data width, signedness, encoding, valid range, and update rules. If a value is encoded across multiple bits, document the bit order and interpretation.

7. Bit, byte, word, and structured-data mapping

A bit represents one binary state. Multiple bits may be grouped into a byte, word, or larger data structure.

A word may contain a collection of independent status flags or represent a numeric value. The interpretation must come from the interface definition, not the size of the data alone.

Example of a conceptual status word:

Status word
Bit 0 -> Machine ready
Bit 1 -> Machine cycle active
Bit 2 -> Machine alarm active
Bit 3 -> Tool changer busy
Bit 4 -> Auxiliary function complete
Bits 5-15 -> Other defined states or reserved bits

This is an illustrative layout only. A real controller may assign completely different meanings to the bits, use a different word size, or expose individual signals rather than a packed word.

For every packed data field, document:

  • Bit number and meaning.
  • Active polarity.
  • Whether the bit is read-only or writable.
  • Whether multiple bits may be active simultaneously.
  • Whether the data is cyclic, event-driven, or updated under another rule.
  • Behavior during startup, reset, communication loss, and faults.
  • Reserved bits and permitted write behavior.

Do not overwrite an entire status word when only one bit is intended to change. In a shared data area, doing so can unintentionally alter unrelated commands or states.

8. Mapping signal polarity and active states

Signal polarity determines how the electrical or logical state is interpreted.

For example, a door sensor may be wired or configured so that a healthy closed door produces a logical TRUE. Another implementation may use inverted logic. Both are possible, but the convention must be explicit.

Logical signal Normal interpretation Engineering check
Door_Closed = TRUE Door is reported closed Verify sensor and polarity
Machine_Ready = TRUE Defined ready conditions are met Verify every required permissive
Alarm_Active = TRUE A machine alarm is present Verify active-high or inverted interpretation
Clamp_OK = TRUE Clamp condition is confirmed Verify the actual feedback source
Cycle_Active = TRUE Defined cycle-active state is present Confirm when the state is set and cleared

A signal named OK, READY, or CLOSED is not self-explanatory. Its precise meaning must be defined.

For safety-related signals, do not infer safety status from a single ordinary PLC bit. Safety functions require the appropriate validated safety system and architecture.

9. Signal timing and update behavior

A correct signal map must define not only what a signal means, but also when it becomes valid.

Possible update behaviors include:

  • Cyclic: Updated repeatedly as part of a control or communication cycle.
  • Event-driven: Updated when a defined event occurs.
  • Request/acknowledgement: One control presents a request, and the other responds according to a handshake.
  • Latched: A state remains set until a defined reset or release condition.
  • Pulse-based: A short transition indicates an event.
  • State-based: The signal remains active while a condition is true.

These behaviors are not interchangeable.

For example, a pulse may be missed if the receiving logic does not sample it at the right time. A level-based request may be processed repeatedly if the receiving logic does not track whether it has already accepted the request.

For handshaked signals, document:

  1. Who sets the request.
  2. Who detects it.
  3. Whether the request must remain active until acknowledgement.
  4. Who sets and clears the acknowledgement.
  5. What happens if the request or acknowledgement is already active.
  6. What happens after a timeout or communication failure.

10. CNC-to-PLC/PMC mapping examples

Example A: CNC requests an auxiliary function

CNC program
    ↓
M-code request and identifier
    ↓
PLC/PMC reads request
    ↓
PLC/PMC checks machine conditions
    ↓
Auxiliary function executes
    ↓
Required feedback is verified
    ↓
Completion acknowledgement is returned

The mapping must identify the request signal, M-code identifier representation, completion signal, and any additional status or fault signals.

Example B: PLC/PMC reports machine readiness

Machine permissives
    ↓
PLC/PMC readiness logic
    ↓
Machine-ready interface signal
    ↓
CNC reads readiness status
    ↓
CNC permits the relevant operation

Readiness is usually a defined logical condition, not merely a powered-on indication. Depending on the machine, it may require valid pressure, completed initialization, no blocking alarms, correct mode, and other permissives.

Example C: CNC and PLC/PMC exchange numeric data

CNC selects a function or identifier
    ↓
Numeric value is placed in interface data
    ↓
PLC/PMC reads and validates the value
    ↓
PLC/PMC executes the matching sequence
    ↓
Completion or result status is returned

The interface specification must define the value range, representation, validation rules, and what happens if the received value is unsupported.

11. Signal ownership and duplicate logic

A common design problem is allowing more than one logic block or controller to command the same function without a clearly defined ownership model.

For example, a tool-clamp output should have a defined controlling sequence. If multiple routines independently write the output, one routine may clamp while another attempts to unclamp.

Use clear ownership rules:

  • Assign one authoritative owner for each command output.
  • Define which controller owns each state and each physical actuator.
  • Use explicit requests between control layers.
  • Keep feedback separate from command signals.
  • Avoid circular dependencies in which two controls each wait for the other to establish readiness.
  • Define what happens when command and feedback disagree.
  • Prevent unrelated logic from modifying shared interface data.

For each signal, distinguish command, status, feedback, acknowledgement, and fault. Similar names do not make these concepts equivalent.

12. PLC/PMC-to-CNC mapping examples

The PLC/PMC often reports machine conditions that the CNC needs for sequencing, program continuation, or operator information.

Examples include:

  • Machine-ready status.
  • Machine-side alarm or alarm code.
  • Tool-change completion.
  • Auxiliary-function completion.
  • Spindle or machine sequence status.
  • Door state.
  • Cycle-active status.
  • Machine mode or operating-condition information.

These signals may be represented by individual bits, status words, or controller-specific interface structures.

A machine-ready signal should be derived from explicitly defined permissives. A machine-alarm signal should be tied to the intended alarm semantics. A tool-change-complete signal should represent the documented completion condition, not just a timer expiring.

13. Interlocks and signal mapping

An interlock prevents an operation from proceeding until required conditions are satisfied.

Examples include:

  • Spindle stopped before a tool change.
  • Required axis position reached before fixture operation.
  • Tool clamped before machining.
  • Correct pressure available before a pneumatic sequence.
  • Door and guarding conditions satisfied before the relevant operation.
  • Machine initialization completed before cycle start.

The signal map should identify the source and meaning of each interlock input. The logic documentation should explain how the interlocks combine to permit or inhibit a function.

A simplified logical expression might be:

\[ \text{CyclePermitted} = \text{MachineReady} \land \text{NoBlockingAlarm} \land \text{RequiredInterlocksSatisfied} \]

This expression illustrates the concept only. Actual machine permissives and their safety requirements must come from the approved machine design.

Important: Ordinary PLC/PMC interface signals are not automatically safety-rated. Emergency stops, guard locking, safe motion, and other safety functions must use the appropriate safety architecture. Do not create or bypass safety functions merely by changing normal CNC interface bits.

14. Commissioning and verification

I/O mapping must be tested systematically before the machine is released for production.

Mapping verification

  • Confirm the CNC model, PLC/PMC platform, and machine-builder interface specification.
  • Verify the source and destination of every mapped signal.
  • Confirm address formats and data types.
  • Check active polarity and logical interpretation.
  • Confirm numeric data representation and valid ranges.
  • Verify reserved bits and shared data ownership.
  • Confirm request, acknowledgement, and release behavior.

Functional verification

  • Monitor the signal at its source.
  • Confirm that the destination receives the intended value.
  • Verify the response in the consuming logic.
  • Check relevant field feedback where applicable.
  • Confirm that each command causes only its intended action.
  • Test invalid or unsupported requests using an approved method.
  • Verify timeout and communication-loss behavior.
  • Confirm correct initialization after controller startup or reset.
  • Record the observed behavior and any deviations.

Documentation and change control

  • Maintain the signal mapping table.
  • Record all machine-specific signal assignments.
  • Document dependencies, interlocks, and alarm responses.
  • Keep PLC/PMC and CNC backups under revision control.
  • Record the reason and approval for every mapping change.
  • Revalidate affected functions after modifications.
  • Update electrical drawings and commissioning records where required.

15. Troubleshooting signal-mapping faults

Symptom Possible cause Diagnostic approach
CNC does not see machine ready Wrong destination, polarity, or readiness logic Trace the signal from producer to consumer
PLC/PMC does not recognize an M-code request Incorrect mapping or request decode Monitor the request and identifier at the interface
Wrong machine function starts Incorrect M-code assignment or data interpretation Compare the received identifier with the approved mapping
CNC remains waiting for completion Completion signal is missing or mapped incorrectly Inspect sequence state, feedback, and acknowledgement path
Signal appears inverted Active polarity or logic inversion mismatch Compare the raw state with the interpreted state
Numeric value is incorrect Wrong data width, encoding, or bit order Inspect the raw interface data and decode method
Command works intermittently Pulse too short, timing issue, or unstable communication Capture transitions and inspect update behavior
Multiple functions activate unexpectedly Shared-word overwrite or duplicate output ownership Check all writers and data masks
Signal is correct online but machine behavior is wrong Incorrect consumer logic or incorrect signal meaning Trace the entire logic path and verify semantics
Status remains active after reset Latch not cleared or initialization sequence incomplete Inspect startup, reset, and release conditions
Communication fault creates misleading status Stale data or undefined failure behavior Verify communication-health handling and fallback states

16. Practical diagnostic sequence

When a CNC or PLC/PMC signal does not behave as expected, follow the signal path in order.

  1. Identify the exact signal and the expected behavior.
  2. Find its producer and authoritative source.
  3. Observe the source value in the relevant diagnostic interface.
  4. Check the interface address, data type, polarity, and encoding.
  5. Observe the value at the consumer.
  6. Verify that the receiving logic interprets the signal correctly.
  7. Check dependent interlocks, sequence states, and timers.
  8. Verify the resulting command and physical feedback.
  9. Check whether startup, reset, or communication-loss behavior affects the signal.
  10. Correct the underlying cause and retest the affected function.

Avoid changing addresses or forcing signals before understanding the complete signal path. A forced bit can hide a mapping error while allowing the machine to operate with incorrect assumptions.

17. Documentation template for a real machine

Use one row per signal, or one row per explicitly documented data field.

Field Required content
Signal name Unique, descriptive identifier
Function What the signal means
Producer Controller, logic block, or field device generating it
Consumer Logic or device using the signal
Direction CNC to PLC/PMC or PLC/PMC to CNC
Address Verified platform-specific interface location
Data type Boolean, integer, word, structured data, or other defined type
Polarity Active-high, active-low, or other defined interpretation
Update behavior Cyclic, event-driven, pulsed, latched, or handshaked
Preconditions Conditions required before use
Fault behavior Expected response to invalid or missing data
Verification Method used to confirm correct operation

For production use, add revision history, machine identifier, software version, drawing reference, and test evidence according to the site's documentation process.

18. Interview questions and answers

1. What is PLC/PMC-to-CNC I/O mapping?

It defines the signals and data exchanged between the machine-control logic and the CNC, including direction, representation, address, meaning, and behavior.

2. Are all CNC interface signals physical I/O?

No. Many are internal interface bits, memory areas, variables, or data structures. Physical I/O is only one layer of the overall control architecture.

3. What is the difference between a command and feedback?

A command requests an action. Feedback reports a condition or result. A command being active does not prove that the requested physical action succeeded.

4. Why is signal polarity important?

A polarity mismatch can make an available condition appear unavailable, or make a fault appear normal. Polarity must be verified from the actual interface and logic.

5. Why must data width and encoding be documented?

Because the same raw bits can represent different values depending on width, bit order, signedness, and encoding. Incorrect interpretation can select the wrong function or produce an invalid value.

6. What is a packed status word?

It is a data word containing multiple status bits or a numeric value. Its interpretation depends on the documented bit assignment and data format.

7. How do you troubleshoot a missing CNC-ready signal?

Trace the signal from its producer through the interface to the CNC consumer, checking address, polarity, readiness logic, and all required permissives.

8. Why should one authoritative owner control an output?

It prevents conflicting commands from multiple logic blocks and makes the machine sequence easier to diagnose and maintain.

9. What should happen if communication is lost?

The machine must follow its defined fault response. Stale or invalid data must not be treated as proof that required conditions remain satisfied.

10. Is a normal PLC/PMC bit sufficient for an emergency-stop function?

Not by itself. Safety functions must be implemented and validated using the required safety-rated architecture.

11. What is the difference between CNC-to-PLC and PLC-to-CNC signals?

CNC-to-PLC signals commonly communicate requests and CNC states. PLC-to-CNC signals commonly communicate machine readiness, completion, alarms, and other machine conditions.

12. What is the most important mapping document?

A controlled signal mapping table that identifies each signal's producer, consumer, direction, address, data type, polarity, timing behavior, and fault response.

19. Key engineering principles

  • Treat signal mapping as an interface specification, not merely an address list.
  • Verify the exact CNC and PLC/PMC platform before using address references.
  • Document signal meaning, ownership, polarity, and timing.
  • Separate requests from feedback and completion acknowledgements.
  • Validate numeric data and packed status fields explicitly.
  • Define communication-loss, startup, reset, and fault behavior.
  • Prevent duplicate ownership and unintended writes to shared data.
  • Keep safety functions within the validated safety architecture.
  • Test the complete signal path, including physical behavior where relevant.

Reliable CNC integration depends on signals being interpreted consistently at both ends. Correct addresses alone are not enough; the producer, consumer, timing, polarity, and functional meaning must all agree.
