1. Purpose of robot program selection

Robot program selection is the process of identifying which robot job, routine, or production program the robot controller should execute when commanded by the machine PLC or another supervisory controller.

In an automated manufacturing cell, the same robot may perform different operations depending on the product, variant, station, process requirement, or production sequence. For example, a robot may load several CNC machines, handle different component variants, perform multiple welding patterns, or pick parts from different fixtures.

The PLC must communicate the intended operation to the robot controller, and the robot controller must interpret and validate that selection before execution.

Program selection answers the question:

Which operation should the robot execute?

Program start answers a different question:

When should the robot begin executing the selected operation?

These operations must be coordinated but should not be treated as the same command.

2. Why program selection is required

Common reasons for selecting different robot programs include:

  • Different product models or variants.
  • Different machining or assembly operations.
  • Different pickup and placement locations.
  • Different tooling or end-effector configurations.
  • Different production recipes.
  • Different station assignments.
  • Different process sequences or quality requirements.
  • Different recovery, inspection, or maintenance routines.

Example: a robot handles three component variants.

Product variant PLC selection value Robot operation
Variant A 1 Load component A
Variant B 2 Load component B
Variant C 3 Load component C

The numbers are illustrative. The actual values depend on the robot controller, PLC interface, and machine program specification.

The PLC should determine the intended variant from validated production data, fixture identification, barcode reading, or the machine's configured production sequence. The robot should not execute an unintended default program when the selection is missing or invalid.

3. Common program-selection methods

3.1 Binary program selection using digital inputs

The PLC represents a program number using multiple digital signals. Each input represents a bit in a binary value.

For \(n\) binary selection bits, the number of representable values is:

\[ N = 2^n \]

For example, three bits can represent eight binary combinations, from 0 to 7.

Selection bit 2 Selection bit 1 Selection bit 0 Binary value
0 0 0 0
0 0 1 1
0 1 0 2
0 1 1 3
1 0 0 4
1 0 1 5
1 1 0 6
1 1 1 7

The receiving controller may use zero-based or one-based program numbering. Do not assume that the binary value directly matches the displayed program number.

For instance, selection value 3 might map to a particular job through a controller-specific mapping table rather than directly identifying a file named 3.

Advantages

  • Simple hardware interface.
  • Easy to inspect through PLC and robot I/O diagnostics.
  • Useful for relatively small program libraries.

Limitations

  • Requires enough physical or mapped digital inputs.
  • Signal transitions can produce temporary intermediate combinations.
  • Program mapping can become difficult to maintain as variants increase.
  • Selection and acceptance must be coordinated to avoid interpreting an unstable value.

3.2 Binary-coded selection and input stabilization

When multiple selection bits change simultaneously, the robot may briefly observe an intermediate combination if the bits are not updated together.

For example:

Previous selection: 011
New selection:      100

Possible intermediate observations:
011 → 000 → 100

The intermediate values depend on the electrical or network update timing. They should not be treated as valid commands during the transition.

A robust interface can use a selection handshake:

  1. PLC writes the selection value.
  2. PLC indicates that the selection is valid.
  3. Robot reads and validates the value.
  4. Robot acknowledges the accepted selection.
  5. PLC verifies the acknowledgement and then issues start.

The exact signals and sequence depend on the controller interface.

3.3 Numeric program selection over an industrial network

A fieldbus or industrial Ethernet connection may provide a numeric value, command structure, or mapped data field for program selection.

Examples of network technologies include PROFINET and EtherNet/IP.

The selection may be represented as:

  • An integer program number.
  • A job identifier.
  • A program index.
  • A structured command containing a program number and request bit.
  • A controller-specific command interface.

Important engineering details include data type, signedness, byte order where applicable, valid ranges, command timing, and communication status.

A PLC value of 12 must not be assumed to select program 12 unless the robot interface documentation confirms that interpretation.

3.4 Direct program call from robot logic

In some systems, the robot controller owns program selection and the PLC provides a higher-level request, such as a product type, process code, or operation identifier.

The robot's main program interprets that request and calls the corresponding routine.

Conceptual example:

Robot main program
        ↓
Read validated operation code
        ↓
Check supported operation
        ↓
Select matching routine
        ↓
Execute selected routine
        ↓
Report completion or fault

This arrangement can reduce the number of PLC-to-robot selection signals, but it requires a well-defined interface and disciplined program management.

3.5 Program selection through a recipe or production-data structure

More complex cells may transfer a group of production parameters rather than just one program number.

A production record might contain:

  • Product or variant identifier.
  • Robot job identifier.
  • Tool identifier.
  • Fixture identifier.
  • Process parameters.
  • Expected station or destination.
  • Recipe revision.
  • Data-validity or version information.

The robot may use the selected program together with validated parameters to perform the operation.

The PLC and robot must agree on the structure, version, data types, and validation rules. A valid program number does not guarantee that its associated process data is correct.

4. Program number versus program name

A program number is a value used by an interface. A program name is often the identifier used by the controller's programming environment or file system.

Concept Example Purpose
PLC selection value 12 Transmitted selection code
Robot job identifier JOB_12 Logical operation identifier
Robot program name LOAD_VARIANT_B Program or routine identifier
Product identifier PART_B Identifies the component being processed
Recipe revision R03 Identifies the approved parameter revision

These identifiers may be related through a mapping table, but they are not automatically equivalent.

For example, program number 12 may map to LOAD_VARIANT_B, while the program file itself may have a different internal name.

Document the mapping so maintenance personnel can trace a PLC value to the actual robot program.

5. Recommended selection handshake

A reliable program-selection handshake separates the requested value from the accepted value.

Typical signals include:

Signal Direction Purpose
PLC_ProgramNumber PLC to robot Requested program identifier
PLC_ProgramSelectReq PLC to robot Indicates a new selection request
Robot_ProgramSelectAck Robot to PLC Indicates the request was processed
Robot_ProgramAccepted Robot to PLC Indicates the selected program is valid and accepted
Robot_AcceptedProgramNumber Robot to PLC Reports the accepted program number where supported
Robot_ProgramSelectFault Robot to PLC Indicates a rejected or invalid selection
Robot_Running Robot to PLC Indicates program execution
Robot_CycleComplete Robot to PLC Indicates completion of the defined operation

The acknowledgement and accepted-program signals may be combined in some interfaces. Their meanings must be explicitly defined.

A typical handshake is:

PLC determines required program
              ↓
PLC validates program number
              ↓
PLC transmits program selection
              ↓
PLC asserts selection request
              ↓
Robot validates selection
              ↓
Robot acknowledges selection
              ↓
PLC verifies accepted program
              ↓
PLC verifies start permissives
              ↓
PLC issues start request
              ↓
Robot executes selected program

The PLC must not assume that a request was accepted merely because it transmitted a number.

6. Selection acknowledgement versus program acceptance

These two concepts are related but not always identical.

Selection acknowledgement may mean the robot received or processed the request.

Program acceptance means the requested program passed the controller's applicable validation and is the selected program.

A controller could acknowledge receipt and then reject the selection because the requested program does not exist or cannot be selected in the current state.

The PLC should use the actual controller signals to determine whether an operation is ready to start.

Where supported, comparing the requested program number against the accepted program number provides additional protection against incorrect mapping or stale feedback.

7. Program selection and PLC sequence control

Program selection should be integrated into a defined machine sequence rather than performed independently of the cycle state.

A typical sequence is:

STATE 0: IDLE
    ↓
STATE 10: Validate product and operation
    ↓
STATE 20: Transmit program selection
    ↓
STATE 30: Wait for selection acknowledgement
    ↓
STATE 40: Verify accepted program
    ↓
STATE 50: Verify robot and machine permissives
    ↓
STATE 60: Issue start request
    ↓
STATE 70: Verify robot running
    ↓
STATE 80: Wait for cycle completion
    ↓
STATE 90: Verify result and advance sequence

Each transition should have:

  • An entry condition.
  • A success condition.
  • A timeout where appropriate.
  • A defined error response.
  • A documented recovery path.

Program selection should normally be prevented or restricted while the robot is executing an operation if the controller does not support safe selection changes during execution.

8. Program validation before execution

Before authorizing a start, the PLC should verify that the selected program matches the intended production operation.

Validation may include:

  • Program number is within the configured range.
  • Program identifier is present in the approved mapping table.
  • Robot has accepted the requested program.
  • Accepted program matches the requested program.
  • Product variant matches the selected program.
  • Required tool and fixture are available.
  • Required process data has been validated.
  • Robot is in the correct operating mode.
  • No blocking robot fault is active.
  • Interface communication is healthy.
  • The current machine sequence permits the operation.

Example conceptual condition:

\[ \text{ProgramStartPermissive} = \text{ProgramValid} \land \text{ProgramAccepted} \land \text{ProgramMatch} \land \text{RobotReady} \land \text{MachinePermissives} \]

This condition is illustrative. Use the actual signals available in the installed system.

9. Handling invalid program numbers

An invalid program number must not silently trigger an unintended operation.

Possible invalid-selection causes include:

  • Number outside the allowed range.
  • Unsupported product variant.
  • Program missing from the robot controller.
  • Incorrect PLC-to-robot mapping.
  • Incorrect data type or byte order.
  • Program selection attempted while the controller is in an incompatible state.
  • Stale selection value retained from the previous cycle.

Recommended response:

  1. Reject the selection.
  2. Keep the start sequence inhibited.
  3. Record the requested and accepted program identifiers.
  4. Display a clear HMI alarm.
  5. Require correction of the production data or program mapping.
  6. Allow recovery only after the correct selection is verified.

Do not automatically replace an invalid program with program 1 or another default unless the machine design explicitly defines and validates that behavior.

10. Program selection timing

Selection timing matters because the PLC and robot controller execute independently.

The PLC may update the selection value while the robot is still reading the previous value. If the interface does not provide a defined handshake, the robot might interpret an unstable or unintended value.

A robust design defines:

  • When the selection value becomes valid.
  • How long it must remain stable.
  • When the request is asserted.
  • How the robot acknowledges the selection.
  • When the PLC may release the request.
  • Whether the selected value is retained.
  • When another selection is permitted.

A simple conceptual timing sequence is:

Select request:  _________|‾‾‾‾‾|___________________

This diagram illustrates the ordering only. Actual signal timing, pulse duration, and acknowledgement behavior must follow the controller's interface specification.

11. Program selection during automatic production

In a multi-variant production line, the PLC may obtain product identity from a barcode reader, RFID system, upstream station, MES, or operator-approved recipe.

The selection path could be:

Product identification
          ↓
PLC validates product identity
          ↓
Production mapping table
          ↓
Required robot operation
          ↓
Robot program selection
          ↓
Robot confirms accepted program
          ↓
PLC authorizes operation

Important controls include:

  • Rejecting unknown product identifiers.
  • Preventing the previous product's selection from being reused unintentionally.
  • Ensuring the selected program matches the physical component.
  • Confirming the required fixture and tooling.
  • Maintaining traceability between product, program, and result.
  • Handling product changes during a fault or interrupted cycle.

If the robot performs different operations for different variants, program selection must be consistent with the machine's validated product-routing logic.

12. Multi-robot and multi-station systems

A machine may contain multiple robots, each with a separate program library and interface.

For example:

  • Robot 1 loads a component.
  • Robot 2 performs an assembly operation.
  • Robot 3 unloads the finished component.

The PLC should maintain separate program-selection states and accepted-program feedback for each robot.

Design concern Engineering requirement
Robot identity Map each selection to the correct robot controller
Program mapping Maintain separate mappings where program libraries differ
Cycle coordination Confirm required station and robot states
Shared equipment Coordinate fixture, conveyor, and tooling ownership
Fault handling Identify which robot rejected or failed the selection
Recovery Restore the correct program and sequence state before restart

Do not reuse a program-selection value across robots merely because both controllers accept the same numeric range.

13. Program version and change management

Program selection becomes a production-quality concern when different program revisions can produce different motion paths, process parameters, or results.

A mature integration may track:

  • Program identifier.
  • Program revision.
  • Approved release status.
  • Tool or fixture compatibility.
  • Product variant compatibility.
  • Date of validation.
  • Change authorization.
  • Backup or restore reference.

The PLC may not be able to read the complete robot program revision directly. If so, use the available controller data or a controlled verification process rather than assuming that the correct number guarantees the correct program contents.

Changes to program mappings should be reviewed and tested because a small mapping error can route a valid production command to the wrong operation.

14. Fault diagnosis and troubleshooting

Symptom Possible cause Diagnostic action
Robot executes the wrong operation Incorrect mapping or wrong selection value Compare requested value, accepted value, and actual program
Program selection is not acknowledged Incorrect signal mapping or controller not accepting requests Check communication and controller state
Selection is acknowledged but rejected Program unavailable or selection invalid Read controller diagnostics and validate the identifier
PLC waits indefinitely for acceptance Missing acknowledgement, incorrect edge handling, or timeout logic error Monitor request and acknowledgement transitions
Robot starts with the previous program New selection not accepted or start issued too early Require accepted-program verification before start
Selection works intermittently Timing race or unstable selection bits Review signal stability and handshake timing
Correct program number produces wrong result Wrong program mapping, wrong program revision, or invalid process data Verify program identity and recipe configuration
Robot accepts program but refuses to run Start permissives or operating mode are not satisfied Check readiness, mode, and fault status
Program selection fails after controller restart Retained state or initialization sequence is incomplete Reinitialize and validate the selection handshake
One robot selects correctly but another does not Different interface configuration or mapping Compare controller-specific settings and signal assignments
Wrong program after product change Previous selection retained or product identity changed unexpectedly Revalidate product identity and selected program at the transition
Program number appears corrupted Incorrect data type, byte order, or word mapping Compare PLC and robot raw values

15. HMI design and operator diagnostics

The HMI should present enough information to identify a selection problem without requiring the operator to inspect PLC code.

Useful information includes:

  • Current product or variant.
  • Requested robot program.
  • Robot-accepted program.
  • Selection request status.
  • Selection acknowledgement status.
  • Program acceptance or rejection status.
  • Robot running status.
  • Robot cycle-complete status.
  • Relevant fault code and description.
  • Communication health.
  • Recovery instructions.

Example alarm messages:

Alarm Suggested operator message
Program selection timeout Robot did not acknowledge the requested program
Invalid program selection Requested robot program is not configured or valid
Program mismatch Robot-accepted program does not match the requested program
Program unavailable Robot controller cannot select the requested program
Program start inhibited Robot program is selected, but start permissives are not satisfied
Program mapping error PLC production mapping and robot program configuration disagree

Alarm messages should describe the detected condition and give a useful next diagnostic action. Avoid generic messages such as Robot Error when more precise information is available.

16. Commissioning checklist

Interface configuration

  • Confirm the robot controller's supported program-selection method.
  • Verify digital-input bit assignments or network data mapping.
  • Confirm numeric data types, valid ranges, and numbering conventions.
  • Verify program-number-to-program-name mapping.
  • Confirm request, acknowledgement, acceptance, and rejection semantics.
  • Verify signal timing and handshake requirements.

Functional testing

  • Test every supported program-selection value.
  • Verify the correct program is accepted for each value.
  • Test an invalid selection and confirm that start remains inhibited.
  • Confirm the robot does not start before selection acceptance.
  • Verify the selected program matches the production variant.
  • Test communication interruption and recovery using the approved procedure.
  • Verify timeout and alarm behavior.
  • Test selection after controller restart.
  • Confirm recovery does not trigger an unintended program execution.

Documentation and release

  • Record the PLC-to-robot program mapping.
  • Document program identifiers and revisions.
  • Save the interface configuration and relevant backups.
  • Record commissioning results and known limitations.
  • Define ownership and approval for mapping changes.
  • Include program selection in the machine recovery procedure.

17. Interview questions and answers

1. What is robot program selection?

It is the process of identifying the robot job or routine required for a specific production operation.

2. What is the difference between program selection and program start?

Program selection identifies the operation to execute. Program start requests execution of that operation after the required conditions are satisfied.

3. How many values can three binary selection bits represent?

Three bits represent \(2^3 = 8\) combinations, from binary 000 to 111. The actual program-number mapping depends on the controller.

4. Why is selection acknowledgement necessary?

It confirms that the robot has processed the selection request. A separate acceptance signal may be required to confirm that the program is valid and selected.

5. Why should the PLC compare requested and accepted program numbers?

It helps detect incorrect mappings, rejected requests, stale feedback, or cases where the robot has retained a different selection.

6. What happens if an invalid program number is received?

The robot or PLC should reject the selection, inhibit the start sequence, report a diagnostic, and require correction before proceeding.

7. Why can binary program selection be unreliable without a handshake?

Multiple bits may change at slightly different times, allowing the receiver to observe a temporary intermediate value.

8. Why should program selection normally be restricted during execution?

Changing the selection during execution can create ambiguous behavior or affect the next operation. Whether it is permitted depends on the controller interface and validated machine design.

9. What is the difference between a program number and a program name?

A program number is an interface value. A program name identifies a job or routine in the controller's programming environment. A mapping may connect them.

10. What should be checked when the robot selects the correct program but performs the wrong operation?

Verify the program mapping, actual program identity, program revision, product variant, tool and fixture compatibility, and associated process data.

11. How should program selection be handled in a multi-robot cell?

Each robot should have its own correctly mapped selection, acceptance feedback, sequence state, and diagnostic information.

12. What is the most important rule for PLC-robot program selection?

Do not issue the start command until the intended program has been validated and its acceptance has been confirmed according to the actual interface design.

18. Final engineering principles

  • Program selection and program start are separate operations.
  • A transmitted program number is not proof of acceptance.
  • The PLC must validate the selected program against the intended production operation.
  • The robot controller must reject invalid or unavailable programs according to its interface behavior.
  • Selection timing, data mapping, and acknowledgement semantics must be documented.
  • Program identity and revision should be controlled when they affect product quality or machine behavior.
  • Recovery after a fault or restart must revalidate the selection before execution.
  • Program-selection logic must be tested alongside the machine's sequence, fault handling, and safety architecture.

The objective is not merely to send a job number. It is to ensure that the correct robot executes the correct approved operation for the correct product, at the correct point in the machine sequence.
