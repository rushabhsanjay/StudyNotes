1. Purpose of PLC-robot signal integration

PLC-robot signal integration establishes a reliable handshake between the machine PLC and the robot controller. It allows the PLC to coordinate robot operations with conveyors, fixtures, clamps, sensors, safety systems, and other equipment.

The PLC and robot controller are separate control systems. Each has its own program execution, operating states, diagnostics, and command logic. Their signals must communicate not just what action is requested, but also whether the receiving system can accept it and whether the action has completed.

The primary signal groups are:

  • Start: Requests execution of a robot operation or cycle.
  • Stop: Requests the defined stopping behavior.
  • Ready: Reports a particular state in which the robot can accept or perform an operation.
  • Fault: Reports an abnormal condition that prevents or interrupts the intended operation.

A production-ready interface usually needs additional signals for program selection, cycle running, cycle complete, robot at home, robot at position, automatic mode, external control, and communication or interface health.

A PLC start command is a request, not proof that the robot has started or completed its task. The PLC must use the appropriate feedback to coordinate the rest of the machine.

2. Typical PLC-robot integration architecture

        HMI / Operator / MES
                 ↓
            Machine PLC
                 ↓
      Robot interface handshake
                 ↓
          Robot controller
                 ↓
       Robot motion program
                 ↓
          Robot mechanics
                 ↓
       Position and process status
                 ↓
          Robot controller
                 ↓
       PLC feedback and sequence

The interface can use hardwired digital I/O, industrial Ethernet, or a combination of both.

Common technologies include:

  • PROFINET.
  • EtherNet/IP.
  • EtherCAT, where supported by the architecture.
  • PROFIBUS in legacy installations.
  • Hardwired 24 V DC digital I/O.
  • Safety-rated communication or dedicated safety wiring for safety-related functions.

The selected protocol determines how signals are mapped, updated, diagnosed, and recovered after communication interruptions.

3. Signal direction and ownership

Every interface signal should have a clearly defined source, destination, meaning, and behavior.

Signal Typical direction Purpose
Robot start request PLC to robot Requests a defined operation or cycle
Robot stop request PLC to robot Requests the configured stop behavior
Robot reset request PLC to robot Requests acknowledgement or reset of a resettable fault
Program selection PLC to robot Selects a job or program, where supported
Robot ready Robot to PLC Reports a defined readiness condition
Robot running Robot to PLC Indicates that the relevant program or operation is executing
Robot cycle complete Robot to PLC Reports completion of a defined cycle
Robot fault Robot to PLC Reports a robot fault or configured fault state
Robot at home Robot to PLC Reports a defined home or reference position
Robot at position Robot to PLC Reports arrival at a defined process position
Automatic mode active Robot to PLC Reports the robot's operating mode
External control active Robot to PLC Reports that external control is enabled, where supported

These are typical interface concepts, not universal signal names. The robot manufacturer's interface documentation defines the actual meanings.

For each signal, document whether it is level-sensitive, edge-triggered, pulsed, latched, or updated through cyclic data.

4. Ready signal: what does robot ready mean?

The word Ready is dangerously vague unless its meaning is defined.

Depending on the robot interface, ready may indicate that:

  • The robot controller is initialized.
  • The robot is in a valid operating mode.
  • No blocking robot fault is active.
  • External control is enabled.
  • The controller can accept a start request.
  • The robot is in a state suitable for the next operation.

These conditions are not interchangeable. A robot can be powered and free of faults but not ready for an external start because it is in manual mode, a local-control mode, or another state that does not permit the requested operation.

Similarly, a robot may be ready to accept a program command while a particular process movement is still prohibited by a machine interlock.

A robust PLC should use separate feedback signals for important conditions when available.

Example conceptual readiness condition:

\[ \text{RobotStartPermissive} = \text{RobotReady} \land \text{AutoMode} \land \text{ExternalControl} \land \text{NoBlockingFault} \land \text{InterfaceHealthy} \]

This is illustrative. Some of these conditions may already be included in the robot's ready signal. Verify the interface definition to avoid both missing and redundant conditions.

5. Start request and start acknowledgement

A start request asks the robot to begin a specified operation. The robot controller may reject the request if its program state, mode, selected job, or interface conditions are invalid.

The PLC should distinguish:

  1. Start requested.
  2. Start accepted or operation started.
  3. Robot program running.
  4. Robot cycle completed.

A typical handshake is:

PLC validates start permissives
              ↓
PLC selects the required operation
              ↓
PLC issues start request
              ↓
Robot accepts request
              ↓
Robot running feedback becomes active
              ↓
Robot executes the operation
              ↓
Robot cycle-complete feedback becomes active
              ↓
PLC validates completion and advances sequence

A robot may expose separate start acknowledgement and running signals, or it may provide only running feedback. Use the signals available from the actual controller.

Do not infer that the robot accepted a start merely because the PLC output is TRUE.

6. Level-triggered versus edge-triggered start

A level-triggered request remains active while the initiating condition is true. An edge-triggered request is detected when the signal changes from FALSE to TRUE.

Robot interfaces differ in how they interpret start commands. Some use a maintained input, some require a pulse, and others use protocol-specific command handshakes.

Example of a rising edge

Start request: ____|‾‾‾‾|____
                     ↑
                 Rising edge

If the robot expects a rising edge, leaving the start signal permanently TRUE may prevent a subsequent start from being recognized.

If the robot expects a maintained input, releasing it too early may prevent the operation from starting or continuing as intended.

The PLC must follow the documented command semantics.

A typical pulse-based sequence is:

  1. Verify all start conditions.
  2. Ensure the start request is inactive.
  3. Assert the start request.
  4. Hold it for the documented interface duration or until the required acknowledgement.
  5. Deassert the request.
  6. Verify the expected running or acceptance feedback.
  7. Raise a start timeout if the expected feedback does not occur.

Do not issue repeated start pulses simply because the robot has not started. First determine whether the program is waiting for another condition or whether the command was rejected.

7. Stop signals and stop behavior

A robot stop signal can have different meanings depending on the controller and machine design.

Possible stop concepts include:

  • Controlled program stop.
  • Motion stop with deceleration.
  • Program interruption.
  • Cycle cancellation.
  • Protective stop.
  • Emergency stop through the appropriate safety system.

A standard PLC stop request is not automatically an emergency stop or a safety-rated stop function.

The interface must define:

  • Whether the stop affects the current motion, program, or complete cycle.
  • Whether the robot retains the current program state.
  • Whether restart requires a reset, resume, or a new start command.
  • How the PLC confirms that the robot has stopped.
  • Whether the robot may continue a recovery or retraction sequence.
  • What happens if communication is lost while stop is requested.

The PLC should not assume that deasserting Start is equivalent to stopping the robot.

8. Fault signal and fault reset

The robot fault signal informs the PLC that a defined fault condition is active. The signal may represent any fault, a blocking fault, or a controller-specific summary.

A robust interface should distinguish the robot fault indication from other conditions such as:

  • Warning active.
  • Program error.
  • Safety stop.
  • External-control unavailable.
  • Communication fault.
  • Robot not ready.

A typical fault-handling sequence is:

Robot fault detected
          ↓
PLC blocks normal cycle progression
          ↓
Capture robot fault code and state
          ↓
Operator / maintenance investigates cause
          ↓
Cause corrected and reset permitted
          ↓
PLC issues documented reset request
          ↓
Robot fault clears?
     ├── No → Keep sequence inhibited
     └── Yes
            ↓
      Verify robot ready
            ↓
      Verify program and position state
            ↓
      Authorize restart separately

A fault reset is not the same as a start request. Clearing a fault must not automatically restart the robot program unless a specifically designed and validated recovery sequence permits it.

9. Recommended PLC-robot handshake signals

A practical interface often needs more than four signals.

Signal Direction Typical purpose
PLC_RobotStartReq PLC to robot Requests the selected operation
PLC_RobotStopReq PLC to robot Requests the defined stop behavior
PLC_RobotResetReq PLC to robot Requests fault reset or acknowledgement
PLC_RobotProgramNumber PLC to robot Selects the requested program where supported
Robot_Ready Robot to PLC Reports readiness according to the interface definition
Robot_Running Robot to PLC Reports active execution
Robot_CycleComplete Robot to PLC Reports completion of the defined cycle
Robot_FaultActive Robot to PLC Reports an active robot fault
Robot_WarningActive Robot to PLC Reports a warning condition
Robot_AutoMode Robot to PLC Reports automatic mode
Robot_ExternalControl Robot to PLC Reports external-control status
Robot_HomePosition Robot to PLC Reports the defined home position
Robot_InterfaceHealthy Robot to PLC or derived Indicates that interface data is valid and usable

The names are illustrative. Follow the project's naming standard and actual signal mapping.

Where supported, retain detailed robot diagnostic codes in addition to summary bits. A single fault bit is useful for sequencing but insufficient for effective troubleshooting.

10. Handshake sequence for automatic operation

A typical PLC-controlled robot cycle may follow these stages:

IDLE
  ↓
Verify robot ready and interface healthy
  ↓
Select required program
  ↓
Verify program selection accepted
  ↓
Check machine and robot permissives
  ↓
Issue start request
  ↓
Verify robot running
  ↓
Wait for cycle complete
  ↓
Verify completion and required position
  ↓
Advance machine sequence
  ↓
Return to IDLE

This is a conceptual sequence. Some robots require additional steps, such as program-number validation, external-start enable, motion-start acknowledgement, or explicit reset of a cycle-complete latch.

The PLC should use a state machine or equivalent structured sequence so each transition has explicit entry conditions, timeout behavior, and fault handling.

11. Start timeout and running timeout

A start timeout detects when the robot does not report the expected response after a start request.

For example:

  • Start request issued.
  • The controller expects Robot_Running to become TRUE.
  • If running feedback does not arrive within the configured interval, the PLC raises a start timeout.

A separate cycle timeout may detect a robot operation that takes longer than expected.

These timeouts serve different purposes.

Timeout Monitors Typical diagnostic focus
Start timeout Time from start request to start acknowledgement or running feedback Mode, program selection, readiness, command mapping
Cycle timeout Time from cycle start to completion Robot program, blocked process, missing fixture signal, unexpected path
Stop timeout Time from stop request to confirmed stopped state Stop semantics, controller state, communication
Reset timeout Time from reset request to expected fault-clear state Reset requirements and persistent fault cause
Communication timeout Time without valid communication or expected data update Network health, controller state, connection configuration

Timeout values should be based on documented response behavior and realistic process timing. Avoid using one generic timeout for every operation.

12. PLC sequence logic example

A simplified start-permissive condition may be:

RobotStartPermissive :=
    RobotReady
    AND RobotAutoMode
    AND RobotExternalControl
    AND RobotInterfaceHealthy
    AND NOT RobotFaultActive
    AND MachinePermissivesValid;

The PLC should issue a start request only when the selected operation and required machine conditions are valid.

After issuing the request, it should wait for the defined acknowledgement.

Conceptual logic:

IF StartRequest
   AND RobotStartPermissive
   AND RobotProgramSelected THEN

    RobotStartCmd := TRUE;
ELSE
    RobotStartCmd := FALSE;
END_IF;

This is illustrative rather than a complete implementation. The actual logic must account for whether the robot expects a pulse or maintained input, how start acknowledgement is represented, and how duplicate requests are prevented.

A robust implementation should also prevent a held HMI button or a stale PLC request from unintentionally starting another cycle after the robot becomes ready again.

13. Communication health and stale signals

Robot signals may be exchanged over cyclic industrial Ethernet or hardwired I/O.

With networked communication, the PLC must determine whether the received data is valid and current. A communication interruption can leave the application with unavailable, invalid, or stale status information depending on the system.

Important considerations include:

  • Connection state.
  • Data-validity indication.
  • Communication watchdog behavior.
  • Expected update interval.
  • Controller restart behavior.
  • I/O substitution or fallback values.
  • Command behavior during network recovery.

A signal that remains TRUE after a communication fault must not automatically be treated as current proof that the robot is ready or running.

After communication recovery, revalidate the robot state and interface data before continuing the sequence.

14. Robot mode and external control

A robot can be powered and fault-free but still reject PLC commands because it is not in the required operating mode.

Common conditions include:

  • Manual or teach mode active.
  • Automatic mode inactive.
  • External control not enabled.
  • Local controller has command ownership.
  • Program not selected or not valid.
  • Program paused or stopped in an incompatible state.
  • Required operator confirmation missing.

The PLC should monitor the mode and control-ownership signals provided by the robot interface.

Mode selection and enabling external control must follow the robot manufacturer's procedures and the machine's safety design. The PLC should not attempt to bypass mode restrictions merely to force an automatic cycle.

15. Robot home, position, and cycle complete

These feedback signals describe different conditions.

Robot home indicates that the robot is at a defined home or reference position according to the configured program or controller status.

Robot at position indicates that a specified process-position condition has been achieved.

Cycle complete indicates that a defined operation has reached its completion point.

A robot may finish a process operation without returning to home. Conversely, it may be at a home position without having completed the required production cycle.

For example, a robot might:

  1. Start at home.
  2. Move to a fixture.
  3. Pick a component.
  4. Perform an operation.
  5. Place the component at another station.
  6. Return to home.

The PLC should use the signal that matches the actual sequence requirement. Do not use Robot_HomePosition as a universal substitute for Robot_CycleComplete.

16. Safety-related robot integration

Robot safety functions must be distinguished from ordinary PLC interface signals.

Standard signals such as Robot_StartReq, Robot_Ready, and Robot_FaultActive generally support normal sequencing. They do not, by themselves, establish that entry into the robot work envelope is safe.

Depending on the machine risk assessment, the safety architecture may include:

  • Emergency-stop functions.
  • Guard-door interlocking.
  • Safety-rated robot stop functions.
  • Safe torque or drive-related functions.
  • Enabling devices for manual operation.
  • Safety-rated communication.
  • Safe speed or position monitoring where required.

The applicable safety design must follow the robot manufacturer's instructions and relevant machinery and robot safety requirements.

Do not treat a standard PLC stop bit as a substitute for the required safety function. Likewise, a standard robot-ready bit does not authorize a person to enter the robot cell.

17. Common PLC-robot signal faults

Symptom Possible cause Diagnostic action
PLC start command is TRUE but robot does not start Wrong mode, external control disabled, invalid program, or missing permissive Check robot state and interface diagnostics
Robot is ready but start is rejected Ready does not include every start condition Check program selection, command ownership, and required interlocks
Robot starts twice Start signal held, duplicate pulse, or restart logic issue Check edge handling and cycle-state transitions
Robot running never becomes TRUE Start not accepted, feedback mapping wrong, or acknowledgement expectation incorrect Verify robot program state and signal mapping
Cycle-complete signal never appears Program did not reach completion, signal is not mapped, or completion definition is wrong Inspect robot program execution and completion logic
Fault bit remains active after reset Underlying fault persists or reset behavior is incorrect Read the robot's diagnostic code and reset requirements
PLC continues sequence after robot fault Fault signal omitted from transition conditions Review sequence interlocks and fault-state priority
Robot appears ready after communication loss Data is stale or interface health is not checked Validate connection state and data validity
Stop request does not stop robot as expected Stop signal semantics misunderstood Verify the documented stop behavior and feedback
PLC and robot disagree about cycle state Incomplete handshake, retained bits, or restart recovery issue Compare both controllers' states and handshake history
Robot does not accept program selection Invalid number, wrong format, or selection attempted at an invalid state Verify the program-selection interface and timing
Robot moves in the wrong sequence Incorrect job or signal mapping Verify program identity and handshake sequence

18. Commissioning checklist

Before testing

  • Confirm the robot controller model, interface, and protocol.
  • Verify PLC and robot signal mapping.
  • Document the meaning and direction of every signal.
  • Confirm whether start and reset are edge-triggered or level-triggered.
  • Verify robot mode and external-control requirements.
  • Confirm program selection and cycle-complete semantics.
  • Verify communication health and stale-data handling.
  • Review the approved safety architecture and operating procedure.

During controlled testing

  • Verify robot-ready feedback under the required conditions.
  • Confirm that start is rejected when required permissives are missing.
  • Verify that an accepted start produces the expected running feedback.
  • Confirm cycle completion at the correct program point.
  • Test the defined stop behavior.
  • Test reset behavior with approved, controlled fault conditions.
  • Verify start, stop, reset, and cycle timeouts.
  • Confirm that a fault blocks normal sequence progression.
  • Test communication loss and recovery using the approved procedure.
  • Confirm that recovery does not automatically initiate unintended movement.

Documentation

  • Save the interface signal list.
  • Record signal polarity, pulse duration, and handshake semantics.
  • Document robot program identifiers and completion conditions.
  • Record timeout values and fault responses.
  • Save relevant PLC and robot diagnostics.
  • Document recovery and restart procedures.

19. Interview questions and answers

1. What is PLC-robot handshake integration?

It is the exchange of commands and status signals between the machine PLC and robot controller to coordinate robot operations with the overall machine sequence.

2. What is the difference between robot ready and robot running?

Ready indicates that the robot satisfies the interface's defined readiness conditions. Running indicates that the relevant program or operation is executing.

3. Why should the PLC wait for running feedback after start?

Because the start request may be rejected or not yet accepted. Running feedback confirms the expected execution state, subject to the interface's documented meaning.

4. Is robot cycle complete the same as robot at home?

No. Cycle complete indicates that a defined operation has completed. Home indicates a defined position or home-state condition.

5. Why might a robot not start even when it has no fault?

It may be in the wrong mode, lack external-control permission, have an invalid program selection, or be missing another required permissive.

6. Why distinguish start timeout from cycle timeout?

A start timeout detects failure to begin. A cycle timeout detects an operation that takes longer than expected after starting.

7. Why is communication health important?

The PLC must know whether robot status is current and valid. Stale feedback can cause incorrect sequence decisions.

8. Why should fault reset and start be separate?

Clearing a fault does not prove that the robot is ready for the intended operation or that restarting is safe.

9. What is the purpose of a cycle-complete handshake?

It gives the PLC a defined condition for advancing the machine sequence after the robot has completed the required operation.

10. Can a standard PLC stop bit serve as an emergency stop?

No. A standard control signal is not automatically a safety-rated function. The required safety response must be implemented through the appropriate validated safety architecture.

11. What should happen if the robot faults during an automatic cycle?

The PLC should execute the defined fault response, capture diagnostics, inhibit inappropriate sequence progression, and require the documented recovery process.

12. What is the most important design principle for robot signals?

Every command must have a defined meaning and expected feedback, with explicit state transitions, timeout handling, and recovery behavior.

20. Final engineering checklist

  • Define all command and feedback signals.
  • Distinguish ready, running, complete, fault, and home.
  • Verify start and reset signal semantics.
  • Confirm program selection before starting.
  • Use acknowledgement and timeout logic.
  • Check robot mode and external-control status.
  • Monitor communication validity.
  • Prevent duplicate starts and conflicting commands.
  • Separate fault reset from restart authorization.
  • Distinguish normal stop commands from safety functions.
  • Record signal mappings and commissioning results.

The central principle is that PLC-robot integration must coordinate requests, acknowledgements, execution states, and completion states explicitly. A collection of digital bits is not a reliable handshake until each signal has a defined meaning and every expected transition has a verified response.
