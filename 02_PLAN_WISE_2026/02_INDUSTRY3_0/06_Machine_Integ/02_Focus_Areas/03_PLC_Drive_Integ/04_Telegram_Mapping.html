1. Purpose of telegram mapping

In industrial automation, a telegram is a defined arrangement of data exchanged between devices over a communication interface. In PLC-drive integration, telegram mapping determines how command words, status words, speed references, actual values, and other cyclic data are organized and interpreted.

A telegram is not merely a collection of bytes. It defines the meaning, order, size, and representation of the data exchanged between the PLC and the drive.

For example, a PLC might send a control word and speed reference to a VFD, while receiving a status word and actual speed in return.

Typical applications include:

  • PLC-to-VFD communication over PROFINET, PROFIBUS, EtherNet/IP, or another supported industrial network.
  • PLC-to-servo-drive communication using a supported cyclic process-data profile.
  • Transmitting start, stop, enable, reset, and direction commands.
  • Sending speed or torque references.
  • Receiving drive status, fault information, and actual values.
  • Integrating multiple drives into a machine or production line.

The key engineering task is to ensure that the PLC and drive agree on the cyclic data layout. If the PLC writes a speed reference into a field that the drive interprets as something else, the network can be healthy while the machine behaves incorrectly.

2. What is cyclic data?

Cyclic data is process data exchanged repeatedly at a configured communication interval. It carries the current commands and feedback needed for normal machine operation.

In a typical PLC-drive arrangement, there are two directions of data transfer.

PLC → Drive
    Control word
    Speed reference
    Torque reference, if configured
    Additional command values

Drive → PLC
    Status word
    Actual speed
    Actual torque or current, if configured
    Additional feedback values

The exact fields depend on the selected telegram, device profile, drive firmware, and configuration.

Cyclic communication is distinct from acyclic communication, which is typically used to read or write parameters, retrieve diagnostics, or access data that is not part of the continuously exchanged process-data image.

Property Cyclic data Acyclic data
Main purpose Real-time commands and feedback Parameters, diagnostics, and configuration
Update behavior Repeated at configured intervals Requested when needed
Typical contents Control word, reference, status, actual value Parameter values, detailed diagnostics
Timing Designed for regular process updates Timing depends on the service and network
Typical use Start a drive and monitor its speed Read a parameter or retrieve a detailed fault record

Acyclic access can be important for diagnostics, but it should not be confused with the cyclic data used to control normal drive operation.

3. Telegram architecture

A typical PLC-drive communication architecture looks like this:

PLC application
      ↓
PLC process-data output image
      ↓
Communication interface
      ↓
Industrial network
      ↓
Drive communication interface
      ↓
Drive control and reference processing
      ↓
Motor operation

Drive status and actual values
      ↓
Drive communication interface
      ↓
Industrial network
      ↓
PLC process-data input image
      ↓
PLC feedback and diagnostic logic

The PLC application generally works with mapped input and output data, symbolic tags, or hardware-defined process-image addresses.

The communication system transfers these data fields according to the configured layout. The drive interprets the received fields according to its selected profile and telegram.

Correct operation therefore depends on several layers:

  • Network connection and device configuration.
  • Correct selected telegram or process-data profile.
  • Matching input and output lengths.
  • Correct field offsets and data types.
  • Correct scaling and signedness.
  • Correct control-word and status-word interpretation.
  • Valid operating-state and fault-handling logic.

A healthy Ethernet connection proves only that some level of communication exists. It does not prove that the cyclic data mapping is correct.

4. PLC-to-drive and drive-to-PLC data

Telegram data is often described using two directions.

PLC-to-drive data is the output process data from the PLC's perspective. It contains the commands and references sent to the drive.

Drive-to-PLC data is the input process data from the PLC's perspective. It contains the status and actual values returned by the drive.

The word input or output must always be understood from the perspective of the device or software being discussed. This prevents a common documentation mistake where the PLC output is confused with the drive output.

Direction from PLC perspective Common fields Purpose
PLC outputs to drive Control word Commands and operating-state requests
PLC outputs to drive Speed reference Requested speed
PLC outputs to drive Torque reference Requested torque, where supported
PLC inputs from drive Status word Drive state and status flags
PLC inputs from drive Actual speed Reported speed feedback
PLC inputs from drive Actual torque or current Operating feedback, if supported

Not every telegram contains all these fields. Some telegrams contain only a basic command and feedback pair, while others include additional words or specialized motion-control information.

5. Telegram structure and data offsets

A telegram is typically defined as a sequence of fields. Each field occupies a defined number of bits or bytes.

Consider this hypothetical cyclic layout:

Direction Offset Field Example representation
PLC to drive Byte 0–1 Control word 16-bit word
PLC to drive Byte 2–3 Speed reference 16-bit signed integer
Drive to PLC Byte 0–1 Status word 16-bit word
Drive to PLC Byte 2–3 Actual speed 16-bit signed integer

This is an illustrative four-byte layout in each direction. It is not a universal drive telegram.

In this example, the control word begins at byte 0 and occupies two bytes. The speed reference begins at byte 2 and occupies the next two bytes.

The drive-to-PLC data uses its own input layout. Its offsets may resemble the output layout, but the meanings are different.

5.1 Byte offsets and word offsets

A byte is eight bits. A 16-bit word occupies two bytes, while a 32-bit value typically occupies four bytes.

For example:

PLC output process data

Byte 0       Byte 1       Byte 2       Byte 3
+------------+------------+------------+------------+
| Control word            | Speed reference        |
+------------+------------+------------+------------+
     16 bits                    16 bits

When a manual specifies offsets in bytes, do not automatically treat them as word indexes. Byte offsets, word indexes, bit numbers, and PLC addresses are different ways of identifying data locations.

6. Telegrams, profiles, and vendor-specific layouts

The available telegrams depend on the drive family, firmware, fieldbus, and supported communication profile.

Different manufacturers may use different names for their process-data layouts. Some profiles standardize a basic control and status structure, while vendor-specific telegrams extend it with additional values.

A selected telegram can determine:

  • Number of cyclic input and output bytes.
  • Number and position of control and status words.
  • Speed-reference and actual-value representation.
  • Availability of torque or other feedback.
  • Supported scaling conventions.
  • Additional command or diagnostic fields.
  • Whether specialized motion-control information is available.

A telegram number is not a universal identifier across all manufacturers. A telegram called a particular number on one drive may not have the same structure on another product family.

Always use the documentation for the exact drive, communication option, firmware, and selected profile.

7. Common standardized and vendor-specific concepts

In drive integration, several related terms are often used.

Term Meaning
Telegram Defined arrangement of cyclic data fields
Process data Data exchanged for ongoing control and feedback
Control word Bit field containing commands to the drive
Status word Bit field reporting the drive's state
Reference value Commanded quantity such as speed or torque
Actual value Feedback quantity reported by the drive
PZD Process data in common PROFIBUS and PROFIdrive terminology
PDO Process Data Object, commonly used in CANopen and related drive communication
Assembly A defined collection of input or output data in protocols such as EtherNet/IP
I/O image PLC memory representation of mapped input or output process data

These terms are related, but they are not interchangeable in every protocol.

For example, a PROFINET drive configured with a PROFIdrive telegram may use control and status words and process-data values. An EtherNet/IP drive may instead expose input and output assemblies. A CANopen drive may use PDO mapping.

The same engineering principles apply, but the configuration screens, terminology, and data structures differ.

8. Control word and status word inside a telegram

The control word and status word are often the most important fields in a basic drive telegram.

The control word is sent from the PLC to the drive. Individual bits may request functions such as enabling operation, starting, stopping, or resetting a fault.

The status word is sent from the drive to the PLC. Individual bits may indicate readiness, enabled operation, running state, fault status, or other conditions.

The exact bit meanings depend on the selected profile and drive configuration.

For example, a hypothetical layout might contain:

PLC → Drive
Word 0: Control word
Word 1: Speed reference

Drive → PLC
Word 0: Status word
Word 1: Actual speed

The field order above is illustrative only. Do not use it as a real device mapping without checking the drive manual.

The PLC should decode the status word separately from the raw communication transfer. This creates a clear boundary between communication mapping and application logic.

9. Scaling and representation of cyclic values

A telegram specifies where a value is located, but the selected interface specification must also define how that value is interpreted.

A speed reference might be represented as:

  • A signed 16-bit integer.
  • An unsigned integer.
  • A normalized percentage.
  • A fixed-point value.
  • A 32-bit integer.
  • A floating-point value, if the interface supports it.

For example, a hypothetical interface may define a raw value of 10000 as 50 Hz.

The conversion is:

\[ f\_{\text{ref}} = \frac{R\_{\text{raw}}}{10000}\times50 \]

If the PLC transmits 6000:

\[ f\_{\text{ref}} = \frac{6000}{10000}\times50 = 30\text{ Hz} \]

The calculation is valid only if the selected interface defines that raw range and frequency base.

Telegram mapping and scaling are separate tasks:

  • Mapping determines where the value is located.
  • Data interpretation determines its type and signedness.
  • Scaling converts the represented value into engineering units.
  • Application logic determines whether the value is valid and appropriate for the machine state.

All four must be correct.

10. Signed and unsigned data

Signedness determines whether a numeric representation can express negative values.

An unsigned 16-bit integer represents values from 0 to 65535. A signed 16-bit two's-complement integer represents values from -32768 to 32767.

For example, the 16-bit pattern 16#FFFF represents 65535 when interpreted as an unsigned integer, but -1 when interpreted as a signed 16-bit integer.

This distinction matters when a drive uses signed speed references or actual-speed feedback to represent direction.

If the PLC treats signed feedback as unsigned, a small negative value may appear as a very large positive value.

Before decoding a field, verify:

  • Data width.
  • Signedness.
  • Byte order.
  • Word order for multiword values.
  • Scaling convention.
  • Whether the sign indicates direction or another quantity.

11. Byte order and word order

A multi-byte value occupies more than one byte. The receiving system must interpret those bytes in the correct order.

For example, a 16-bit value can be represented as two bytes:

Example 16-bit value: 16#1234

High byte: 16#12
Low byte:  16#34

A protocol or device may define the byte order explicitly. PLC hardware configuration and communication drivers usually handle the protocol's normal representation, but custom mappings or application-level data manipulation can introduce errors.

For a 32-bit value, the order of the two 16-bit words may also matter. A word-order mismatch can produce a very different numeric value even when every byte is present.

Troubleshooting should distinguish between:

  • Byte swap within a word.
  • Word swap within a multiword value.
  • Incorrect data type.
  • Incorrect offset.
  • Incorrect scaling.

Do not add byte-swapping logic unless the actual mapping requires it. Unnecessary conversion can create a second error while attempting to fix the first.

12. Configuring a telegram in the engineering environment

The exact procedure varies by manufacturer, but a typical workflow is:

  1. Identify the drive model, communication interface, and firmware.
  2. Confirm that the PLC supports the required protocol and device description.
  3. Add or configure the drive in the PLC engineering project.
  4. Select the required telegram, profile, assembly, or process-data layout.
  5. Confirm the number of input and output bytes.
  6. Assign the correct PLC process-image addresses or symbolic tags.
  7. Verify the field offsets and data types.
  8. Configure reference and feedback scaling.
  9. Download the configuration according to the approved procedure.
  10. Verify cyclic data exchange and drive diagnostics.
  11. Test commands and feedback under controlled conditions.
  12. Save the verified mapping and configuration revision.

For example, in a Siemens TIA Portal environment, a drive may be configured using its device description and supported telegram selection. In an EtherNet/IP environment, the integration may require selecting compatible input and output assemblies and their data sizes.

The terminology differs, but the essential requirement is the same: the PLC's configured data structure must match the drive's configured interface.

13. Mapping documentation

Every integrated drive should have a documented process-data map.

A practical mapping table can include:

Field Direction Offset Data type Engineering meaning
Control word PLC to drive As configured WORD Command bits
Speed reference PLC to drive As configured INT or defined type Requested speed
Status word Drive to PLC As configured WORD Drive status bits
Actual speed Drive to PLC As configured INT or defined type Speed feedback
Fault code Drive to PLC If available Defined type Diagnostic information

The table above is a template, not a real mapping. Replace every illustrative offset and type with verified device-specific information.

A complete mapping document should record:

  • Drive manufacturer, model, and firmware.
  • PLC model and communication interface.
  • Network protocol and device name or address.
  • Selected telegram or process-data profile.
  • Input and output data lengths.
  • Field offsets and data types.
  • Bit-level definitions for control and status words.
  • Scaling formulas and units.
  • Signedness and byte or word ordering.
  • Communication update interval and watchdog behavior.
  • Fault and communication-loss response.
  • Configuration revision and commissioning results.

This document becomes particularly valuable during drive replacement, PLC migration, troubleshooting, and machine retrofit.

14. Cyclic update time and consistency

Cyclic data is transferred repeatedly, but it is not necessarily updated instantaneously.

The effective response depends on several factors:

  • PLC task and scan time.
  • Network update interval.
  • Drive control-cycle timing.
  • Process-image update behavior.
  • Filtering and ramp settings.
  • Communication scheduling and load.

A command written by the PLC may be transmitted on a later network update and processed by the drive in a subsequent control cycle.

Similarly, feedback may describe a state from an earlier point in time rather than the exact moment the PLC executes its logic.

For ordinary speed control, this behavior is usually handled by the designed update rates and feedback logic. For demanding motion applications, timing and synchronization requirements may be much stricter.

If a system requires synchronized motion or tightly coordinated axes, use the supported real-time or motion-control architecture rather than assuming that ordinary cyclic I/O alone guarantees synchronization.

15. Communication failure and watchdog behavior

Cyclic data exchange must include a defined response to lost or invalid communication.

Possible causes include:

  • Network cable or connector failure.
  • Switch or network-interface failure.
  • Incorrect device name, IP configuration, or connection parameters.
  • PLC or drive restart.
  • Watchdog timeout.
  • Incorrect input/output data size.
  • Incompatible device configuration.
  • Network overload or excessive update-time requirements.

A drive may be configured to stop, coast, hold a value temporarily, or use another defined response when cyclic commands are lost. The correct behavior depends on the drive, application, and safety design.

The PLC must not assume that a disconnected drive will always stop in the same way.

Commissioning should verify:

  • How communication loss is detected.
  • What happens to the last speed reference.
  • Whether the drive trips or follows another configured response.
  • Whether the PLC receives a valid diagnostic indication.
  • How the system recovers after communication returns.
  • Whether restart authorization is required.

Do not treat a communication watchdog or ordinary network response as a safety-rated stop unless the entire function is designed and validated for that purpose.

17. Practical commissioning example

Consider a hypothetical VFD interface with the following defined process-data fields:

  • PLC output word 0: control word.
  • PLC output word 1: speed reference.
  • PLC input word 0: status word.
  • PLC input word 1: actual frequency.
  • Speed reference scaling: 0–10000 corresponds to 0–50 Hz.
  • Actual frequency scaling: 0–10000 corresponds to 0–50 Hz.

These details are assumed solely for this example.

Step 1: Verify the configured layout

Confirm that the PLC and drive agree on the four fields, their direction, their offsets, and their data types.

Step 2: Send a controlled reference

For a 25 Hz command:

\[ R\_{\text{ref}} = \frac{25}{50}\times10000 = 5000 \]

The PLC writes 5000 into the configured speed-reference field.

Step 3: Verify the returned status

Decode the status word using the actual manufacturer's mapping. Confirm the expected transition through the drive's operating states.

Step 4: Verify actual frequency

If the actual-frequency field returns 4800:

\[ f\_{\text{actual}} = \frac{4800}{10000}\times50 = 24\text{ Hz} \]

The drive is reporting 24 Hz under the assumed scaling.

Step 5: Determine whether the response is acceptable

Compare actual frequency with the commanded reference, taking account of acceleration time, load, operating mode, and the configured tolerance.

Step 6: Record the result

Document the raw values, decoded values, drive configuration, and test conditions. If the values disagree with the drive display, investigate the mapping and scaling before modifying application sequence logic.

18. Safety and change management

Telegram changes can affect the meaning of commands and feedback. Changing a selected telegram, data length, field order, or scaling convention may break existing logic even if the drive remains visible on the network.

Before changing a mapping:

  • Review the current configuration and backup.
  • Identify all PLC logic that consumes or writes the affected data.
  • Confirm the new field definitions against the device documentation.
  • Update tags, scaling, diagnostics, and HMI displays.
  • Review fault, stop, and communication-loss behavior.
  • Test under controlled commissioning conditions.
  • Update the documentation and approved revision.

If a telegram contains safety-related data, its handling must follow the applicable certified safety communication and device requirements. Ordinary cyclic process data is not automatically safety-related.

19. Interview questions and answers

1. What is a telegram in drive integration?

A defined arrangement of cyclic data exchanged between the PLC and drive, including fields such as control words, status words, references, and actual values.

2. What is the difference between cyclic and acyclic communication?

Cyclic communication repeatedly transfers process data for ongoing control. Acyclic communication is generally used for parameter access, diagnostics, and configuration.

3. Why must the PLC and drive use matching telegram configurations?

They must agree on the data length, field order, offsets, and interpretation. A mismatch can cause incorrect commands or feedback even when the network connection is active.

4. What is a process-data offset?

It identifies the location of a field within the configured input or output data layout, usually expressed in bytes, words, or bits.

5. Is a telegram number universal across manufacturers?

No. Telegram identifiers and supported layouts depend on the device family, profile, firmware, and communication interface.

6. What is the difference between mapping and scaling?

Mapping identifies where a value is located and how it is represented. Scaling converts that representation into engineering units such as Hz or rpm.

7. Why is signedness important?

The same bit pattern can represent different numbers when interpreted as signed or unsigned. A mismatch can produce incorrect speed values or direction interpretation.

8. Why can communication be healthy while drive control still fails?

The connection may be active while the telegram layout, scaling, control-word bits, reference source, or operating sequence is incorrect.

9. What should be checked when replacing a drive?

Verify the supported process-data layout, data sizes, offsets, scaling, control and status mappings, firmware compatibility, communication behavior, and all dependent PLC logic.

10. What is the purpose of a communication watchdog?

It detects missing or delayed cyclic communication and enables the system to apply its configured fault response rather than treating old commands or feedback as current.

20. Final engineering checklist

  • Identify the exact drive model, firmware, and communication interface.
  • Confirm the selected telegram, profile, assembly, or process-data layout.
  • Verify input and output data sizes.
  • Record each field's direction, offset, type, and meaning.
  • Confirm control-word and status-word bit definitions.
  • Verify scaling, signedness, and byte or word ordering.
  • Validate the mapping against raw values and the drive display.
  • Confirm update-time and watchdog requirements.
  • Define communication-loss and recovery behavior.
  • Test start, stop, speed-reference, feedback, and fault scenarios.
  • Save the approved configuration and mapping document.
  • Revalidate the complete interface after any telegram change.

The central principle is that telegram mapping defines the structure of the exchanged data, while scaling and application logic define how that data is interpreted and used. A dependable drive interface requires all three to agree.
