1. Purpose of drive status and feedback

A PLC must know more than the command it has sent to a VFD or servo drive. It must determine whether the drive has accepted the command, whether the motor is operating, whether a fault exists, and whether the actual speed matches the requested speed.

Status and feedback are the information returned by a drive to the PLC, HMI, supervisory system, or machine controller.

Typical information includes:

  • Drive ready and available for operation.
  • Drive enabled or operation permitted.
  • Start command accepted.
  • Motor running or stopped.
  • Fault active and fault code.
  • Warning active.
  • Actual output frequency or motor speed.
  • Direction of rotation.
  • Current, torque, voltage, or other diagnostic values.
  • Communication health and data validity.

The PLC uses this information to sequence machine operations, control interlocks, detect faults, report alarms, and verify whether commanded actions have produced the expected result.

A command is a request. Feedback is evidence of what the drive reports or what the machine actually does. Confusing the two is a reliable way to create automation that looks correct on a screen while doing something else in the real world.

2. Drive status and feedback architecture

PLC command logic
    ↓
Control word and speed reference
    ↓
VFD / Servo drive
    ↓
Drive state, status word, diagnostics
    ↓
Cyclic communication or hardwired signals
    ↓
PLC input data
    ↓
Status decoding and validity checks
    ↓
Machine sequence, interlocks, alarms, HMI

Feedback can be obtained through several interfaces:

  • Fieldbus or industrial Ethernet: Status words, actual values, and diagnostic data.
  • Hardwired digital outputs: Signals such as ready, running, fault, or at speed.
  • Analog outputs: A scaled representation of frequency, speed, current, or another quantity.
  • Encoder or motion feedback: Position and speed measured by an encoder or feedback device.
  • Drive diagnostics: Detailed fault codes, warning codes, and parameter values read through the communication interface.

The selected interface determines the available detail, update rate, diagnostic quality, and failure modes.

3. Command, status, and feedback are different

Signal Meaning Example
Run command PLC requests operation Drive_StartCmd = TRUE
Drive ready Drive reports that it can accept operation Drive_Ready = TRUE
Drive enabled Drive reports an enabled operating state Drive_Enabled = TRUE
Running status Drive reports an operating or running condition Drive_Running = TRUE
Fault status Drive reports an active fault condition Drive_Fault = TRUE
Speed reference Requested operating speed SpeedRef_Hz = 35.0
Actual frequency Drive-reported output frequency ActualFreq_Hz = 34.8
Actual motor speed Drive-reported or measured rotational speed ActualSpeed_RPM = 1015
At-speed status Speed is within a defined target tolerance Drive_AtSpeed = TRUE
Communication valid PLC considers received data current and usable Drive_DataValid = TRUE

The exact meaning of Ready, Enabled, and Running varies by drive and interface. They are not interchangeable universal states.

For example, a drive may report that its power electronics are ready while the motor remains stopped because no run command has been accepted.

Likewise, a drive can be enabled but still accelerating toward its reference. A running bit does not necessarily mean that the motor has reached the target speed.

4. Common status signals

4.1 Ready

The ready signal usually indicates that the drive is in a state where operation can be accepted, subject to its configured conditions.

Depending on the manufacturer, readiness may depend on:

  • Control power and power-stage availability.
  • Initialization and parameter validity.
  • No blocking fault.
  • Required enable conditions.
  • Communication or command-source configuration.
  • External interlocks.

Do not assume that Ready = TRUE proves every machine-level safety condition is satisfied. Read the drive documentation to establish the exact definition.

4.2 Enabled

Enabled indicates that the drive's operating state permits motion or operation under the configured control mode.

A drive may be ready but not enabled. For example, a run-permission command may not have been received.

Some drives distinguish between power-stage enable, operation enable, torque enable, and motion enable. Servo drives often have additional state transitions before movement can occur.

4.3 Running

Running usually indicates that the drive is operating or has entered a defined run state. The precise behavior depends on the manufacturer.

Possible implementations include:

  • Run command accepted.
  • Drive operating state active.
  • Output frequency above a threshold.
  • Motor control active.
  • A configured digital output condition.

Therefore, a Running status bit may not mean that the motor is rotating at a nonzero speed. Confirm the manufacturer's definition.

For a machine sequence that requires actual movement, combine suitable drive status with actual-speed feedback or independent motion detection.

4.4 Stopped

Stopped may mean the drive has completed its stop sequence, its output frequency is below a threshold, or the drive is in a stopped state.

A stopped drive is not necessarily isolated from electrical power. A motor may also coast or move because of external mechanical forces.

If the process requires confirmation of zero speed, use a defined speed threshold, a suitable feedback source, and a validated detection time. If safety requires a safety-rated standstill function, ordinary PLC status alone is not sufficient.

4.5 Fault and warning

A fault generally indicates a condition that prevents or interrupts normal operation. A warning indicates an abnormal or approaching limit that may not yet stop the drive.

Examples include:

  • Overcurrent or overload.
  • DC-bus overvoltage or undervoltage.
  • Motor overtemperature.
  • Drive overtemperature.
  • Encoder or feedback failure.
  • Communication loss.
  • Ground fault.
  • Parameter or configuration error.
  • Motor stall or excessive following error.

A warning does not necessarily mean that a fault will follow, and a fault code may remain stored after the active fault condition clears. Distinguish active fault state, historical fault record, and fault-reset request.

5. Status word fundamentals

In network-controlled drives, multiple status flags are often packed into a status word. A status word is a numerical value whose individual bits represent conditions or states.

A hypothetical 16-bit status word could be represented as follows:

Bit Illustrative meaning
0 Ready
1 Enabled
2 Running
3 Fault active
4 Warning active
5 At speed
6 Forward direction
7 Reverse direction
8 Reference accepted
9 Communication or interface-specific status
10–15 Other manufacturer-defined states

This is an illustrative mapping only. There is no universal drive status-word bit assignment. Real mappings depend on the drive, protocol, telegram, control profile, and configuration.

Before decoding a status word, obtain the manufacturer's mapping and verify whether bit numbering begins at bit 0 or bit 1 in the documentation.

5.1 Extracting an individual bit

Suppose a status word is stored in StatusWord. To check bit 3, a PLC can use a bitwise AND operation with a mask of 8:

\[ \text{Mask} = 2^3 = 8 \]
\[ \text{FaultActive} = (\text{StatusWord} \mathbin{\&} 8) \ne 0 \]

If the result is nonzero, bit 3 is set.

Illustrative Structured Text:

FaultActive := (StatusWord AND 16#0008) <> 0;
Ready       := (StatusWord AND 16#0001) <> 0;
Running     := (StatusWord AND 16#0004) <> 0;
Warning     := (StatusWord AND 16#0010) <> 0;

These masks are valid only for the hypothetical bit assignment above. Replace them with the correct masks from the actual drive documentation.

Some PLC environments use different syntax for bitwise operations, masks, or hexadecimal constants.

5.2 Why bit decoding errors occur

Common mistakes include:

  • Using the wrong bit number.
  • Confusing bit numbering with a displayed hexadecimal mask.
  • Reading a signed integer when the interface defines an unsigned word.
  • Decoding a different telegram layout than the drive transmits.
  • Applying a byte swap or word swap incorrectly.
  • Treating a reserved bit as a meaningful status.
  • Using stale communication data.
  • Assuming a bit's meaning from another manufacturer's drive.

A status word that changes numerically is not automatically decoded correctly. Validate each important bit against the drive display, documentation, and controlled commissioning tests.

6. Actual speed feedback

Actual speed feedback is the reported or measured speed of the motor or axis. It is used to verify acceleration, confirm process conditions, detect stalls, and compare actual motion with the commanded reference.

The feedback may be represented in:

  • Hz.
  • rpm.
  • Percentage of nominal or maximum speed.
  • A normalized integer.
  • Encoder counts per time interval.
  • Engineering units per second for a servo axis.

The source matters. A drive may report estimated motor speed, encoder-measured speed, or output frequency. Those values do not always represent the same physical quantity.

6.1 Actual frequency versus actual rpm

If a drive reports 40 Hz, that does not directly prove that the motor shaft is rotating at a particular rpm.

For a synchronous-speed estimate:

\[ n_s = \frac{120f}{P} \]

For a four-pole motor at 40 Hz:

\[ n_s = \frac{120 \times 40}{4} = 1200\text{ rpm} \]

An induction motor normally rotates below synchronous speed under load because of slip. A servo motor's speed depends on its commanded electrical operation, motor characteristics, and feedback control.

When accurate shaft speed matters, use the appropriate speed feedback rather than converting frequency and treating the result as measured rpm.

6.2 Scaling raw speed feedback

Suppose a hypothetical drive interface reports a raw value from 0 to 10000 corresponding to 0 to 50 Hz.

The conversion is:

\[ f\_{\text{actual}} = \frac{R\_{\text{raw}}}{10000}\times50 \]

If the received value is 7200:

\[ f\_{\text{actual}} = \frac{7200}{10000}\times50 = 36\text{ Hz} \]

The raw value must be interpreted according to the configured interface. Some drives use signed values, a percentage base, a different normalization constant, or different units.

For signed feedback, direction may be encoded in the sign, or it may be conveyed through a separate status bit. Confirm the interface definition before converting or displaying the value.

7. Speed deviation and at-speed detection

The PLC often needs to determine whether the actual speed is sufficiently close to the requested speed.

Define speed error as:

\[ e = n\_{\text{ref}} - n\_{\text{actual}} \]

Where:

  • \(n\_{\text{ref}}\) is the commanded speed.
  • \(n\_{\text{actual}}\) is the actual speed feedback.
  • \(e\) is the speed error.

A basic at-speed condition is:

\[ |e| \leq \Delta n \]

Where \(\Delta n\) is the allowed speed tolerance.

For example, if the target is 1000 rpm and the permitted deviation is 30 rpm, the at-speed range is 970–1030 rpm.

Reference Actual speed Error Within 30 rpm?
1000 rpm 1000 rpm 0 rpm Yes
1000 rpm 985 rpm 15 rpm Yes
1000 rpm 970 rpm 30 rpm Yes
1000 rpm 950 rpm 50 rpm No
1000 rpm 1040 rpm -40 rpm No

An actual-speed tolerance should be combined with a settling time or stability requirement where appropriate. Otherwise, a brief crossing through the target speed may be mistaken for stable operation.

7.1 Absolute versus percentage tolerance

An absolute tolerance uses a fixed value, such as ±30 rpm.

A percentage tolerance scales with the reference:

\[ \Delta n = \frac{p}{100}|n\_{\text{ref}}| \]

For a 3% tolerance at 1000 rpm:

\[ \Delta n = \frac{3}{100}\times1000 = 30\text{ rpm} \]

Percentage tolerance can be unsuitable near zero because the permitted range becomes extremely small. Applications may need a minimum absolute tolerance in addition to a percentage tolerance.

7.2 Avoid unstable at-speed signals

If actual speed fluctuates around the tolerance boundary, the at-speed flag may repeatedly switch on and off.

Useful techniques include:

  • Applying a defined settling timer.
  • Using a suitable filtered feedback value for process logic.
  • Applying hysteresis with separate enter and exit thresholds.
  • Validating feedback quality before evaluating the comparison.
  • Resetting the at-speed condition when the reference changes significantly.

Do not filter away a genuine dangerous or fault condition. Process filtering and safety-related monitoring have different requirements.

8. Drive running confirmation in a PLC sequence

A typical sequence may issue a start command and wait for confirmation before proceeding.

Sequence requests start
        ↓
Check operating permissives
        ↓
Send run command and speed reference
        ↓
Confirm drive ready and enabled as required
        ↓
Wait for running feedback
        ↓
Wait for actual speed within tolerance
        ↓
Continue machine sequence

The precise order depends on the drive state machine and application.

For example, a conveyor sequence might require:

  1. Safety and process permissives are satisfied.
  2. The PLC sends the run command.
  3. The drive reports that operation is enabled.
  4. Running feedback becomes active.
  5. Actual speed enters the permitted range.
  6. The PLC allows the next process step.

Each waiting stage should have a defined timeout and failure response. A timeout should not automatically cause repeated start commands without checking the drive's current state.

9. Timeout monitoring

A drive may fail to start, fail to reach the requested speed, or fail to stop within the expected time.

Examples of useful timers include:

  • Ready confirmation timeout.
  • Start-to-running timeout.
  • Acceleration or at-speed timeout.
  • Stop confirmation timeout.
  • Communication data-validity timeout.
  • Fault-clear or reset-response timeout.

A start timeout can be implemented conceptually as:

IF StartSequenceActive AND NOT DriveRunning THEN
    StartTimeoutTimer(IN := TRUE);
ELSE
    StartTimeoutTimer(IN := FALSE);
END_IF;

IF StartTimeoutTimer.Q THEN
    StartFailure := TRUE;
END_IF;

This is illustrative pseudocode. The actual implementation must account for PLC scan behavior, timer syntax, sequence-state transitions, and the correct definition of running.

The timeout should be based on the expected drive response, configured ramps, mechanical load, and process requirements. A value that is too short creates nuisance faults; one that is too long delays fault detection.

10. Fault feedback and fault codes

A drive fault signal tells the PLC that a fault condition exists, but the fault code identifies the reported cause.

The PLC should distinguish:

  • Active fault bit.
  • Current fault code.
  • Warning code.
  • Historical fault record.
  • Fault-reset command.
  • Fault-clear confirmation.
  • Drive-ready recovery state.

A fault bit alone may not identify the underlying problem. The PLC should capture the associated code and relevant operating data when practical.

Useful diagnostic information includes:

  • Drive fault and warning codes.
  • Speed reference and actual speed at fault time.
  • Drive status word.
  • Control word sent by the PLC.
  • Communication health.
  • Motor current or torque, if available.
  • Sequence step and machine operating mode.
  • Timestamp and recent command transitions.

10.1 Fault reset logic

A fault-reset command should follow the drive's documented reset behavior. Some drives require a rising edge, some require the command to be held for a specified interval, and others use a different recovery procedure.

A robust sequence is:

  1. Detect and record the fault.
  2. Remove or resolve the initiating condition where required.
  3. Confirm that reset is permitted.
  4. Issue the reset command using the required signal pattern.
  5. Remove the reset request as specified.
  6. Confirm that the fault is cleared.
  7. Confirm that the drive returns to the required ready state.
  8. Require the appropriate restart authorization.

Fault reset must not automatically mean restart. The machine should not resume hazardous movement merely because a fault bit cleared.

Some faults cannot be reset until the underlying cause is removed, and some require a manual inspection or power-cycle procedure specified by the manufacturer.

11. Communication health and data validity

A drive's last received status can remain in PLC memory even after communication is lost. Without data-validity handling, the PLC may treat old feedback as current.

Communication health should be monitored independently of the decoded drive status.

Useful checks include:

  • Connection or device-health status.
  • Communication timeout or watchdog.
  • Data-update counter, if available.
  • Quality or validity flags.
  • Timestamp or age of last valid data.
  • Expected update rate.
  • Module or network diagnostics.

Conceptual logic:

IF DriveCommunicationHealthy AND StatusDataFresh THEN
    DriveDataValid := TRUE;
ELSE
    DriveDataValid := FALSE;
END_IF;

The exact logic depends on the communication platform and drive interface.

When data becomes invalid, the PLC should not silently substitute stale values for live feedback. It should apply a defined response based on the machine risk assessment and operating requirements.

For example, a lost status connection may prevent a sequence from proceeding or trigger a controlled stop. The correct response depends on the application and its safety design.

12. Hardwired status versus network status

Characteristic Hardwired signal Network feedback
Typical data Ready, running, fault Multiple states, values, and diagnostic codes
Wiring Dedicated signal wiring Industrial network connection
Diagnostic detail Usually limited Often extensive
Update behavior Depends on signal and input module Depends on network and configured update cycle
Common failure modes Broken wire, short circuit, wrong polarity Connection loss, mapping error, stale data
Commissioning focus Electrical state and polarity Data mapping, scaling, profile, and connection health
Typical advantage Simple independent indication Rich status and feedback in one interface

A hardwired fault output may be useful even when a network interface carries detailed diagnostic data. However, an ordinary hardwired signal is not automatically safety-rated.

The choice should be based on required diagnostics, response time, system architecture, and the machine's safety requirements.

13. Analog status feedback

Some drives provide actual frequency or speed through an analog output.

For example, a drive may be configured so that 0–10 V corresponds to 0–50 Hz.

The PLC can convert the measured voltage into frequency:

\[ f\_{\text{actual}} = \frac{V}{10}\times50 \]

If the measured voltage is 7.2 V:

\[ f\_{\text{actual}} = \frac{7.2}{10}\times50 = 36\text{ Hz} \]

Analog feedback requires checking:

  • Drive analog-output assignment.
  • Output scaling.
  • PLC analog-input scaling.
  • Signal type and range.
  • Common reference and grounding.
  • Shielding and noise.
  • Input and output resolution.
  • Broken-wire detection where supported.
  • Whether the output represents frequency, estimated speed, or measured speed.

An analog feedback value may be less informative than a digital network value because it normally provides one scaled quantity at a time and may have limited diagnostic capability.

14. PLC tag design

Use tag names that describe the meaning and unit of each value.

Tag name Data type example Purpose
Drive_Ready BOOL Drive-ready status
Drive_Enabled BOOL Drive-enabled status
Drive_Running BOOL Running feedback
Drive_FaultActive BOOL Active fault indication
Drive_WarningActive BOOL Active warning indication
Drive_AtSpeed BOOL Speed within tolerance
Drive_DataValid BOOL Received data is usable
Drive_StatusWord WORD or UINT Raw status word
Drive_FaultCode UINT or defined code type Current fault code
Drive_SpeedRef_Hz REAL Requested frequency
Drive_ActualFreq_Hz REAL Reported actual frequency
Drive_ActualSpeed_RPM REAL or DINT Reported or measured motor speed
Drive_SpeedError_RPM REAL Reference minus actual speed

These are example names and data types. Select types according to the PLC platform and drive interface.

Maintain both raw and decoded values where practical. Raw data helps diagnose mapping problems, while decoded tags make application logic easier to understand.

15. HMI and alarm presentation

An HMI should distinguish operating state, fault state, feedback values, and data validity.

Useful display elements include:

  • Drive state: ready, enabled, running, stopped, or faulted.
  • Commanded speed and actual speed with units.
  • At-speed indication.
  • Active fault code and readable fault description.
  • Warning status.
  • Communication-health indication.
  • Relevant reset or recovery instructions.
  • Last fault timestamp, if recorded.

Avoid displaying a plausible numeric speed when the data is invalid. Show a clear unavailable or communication-fault indication rather than letting an old value appear current.

Alarm messages should describe the detected condition and guide troubleshooting without concealing the actual drive fault code.

For example, distinguish between:

  • Drive fault active: code 1234.
  • Drive failed to reach speed within timeout.
  • Drive status communication lost.
  • Actual speed feedback invalid.

These conditions can require different corrective actions.

16. Troubleshooting scenarios

Symptom Possible cause Diagnostic action
PLC commands start but running feedback remains false Drive not ready, enable missing, command source mismatch Check drive state, control word, permissives, and command-source configuration
Running is true but actual speed is zero Running bit definition differs, motor not rotating, or feedback mapping is wrong Check the drive's running definition and independent speed feedback
Drive shows a fault but PLC fault bit is false Incorrect status-word mapping, stale data, or wrong polarity Compare the raw status word with the drive display and manual
PLC shows a fault after the drive has recovered Fault bit is latched in PLC logic or data is stale Check latching logic, communication validity, and reset conditions
Speed display is ten times too high Incorrect scale factor or decimal interpretation Verify raw-value range, engineering units, and conversion formula
Speed feedback changes in the wrong direction Signedness or direction mapping is incorrect Check sign convention and separate direction bits
At-speed flickers Tight tolerance, noise, or insufficient settling logic Review tolerance, filtering, hysteresis, and timer settings
Sequence times out even though the motor runs PLC checks the wrong status or speed threshold Validate status semantics, feedback scaling, and sequence conditions
Drive status freezes at its last value Communication failure without validity monitoring Inspect connection health, watchdog, and data age
Fault reset does not clear the fault Cause remains active or reset sequence is incorrect Read the exact fault code and verify reset requirements
Fault clears and the machine starts unexpectedly Reset logic also reissues a run command or sequence resumes automatically Separate fault reset, restart authorization, and start command logic
Drive reports zero speed but the mechanism is moving Feedback source or zero-speed threshold is unsuitable, or the mechanism is externally driven Verify actual motion sensing and the required safety function

17. Commissioning procedure

17.1 Before energizing or testing motion

  • Confirm the drive model, communication interface, and configured telegram or data profile.
  • Verify status-word and feedback mappings against the documentation.
  • Check input data types, signedness, byte order, and scaling.
  • Confirm the meaning of ready, enabled, running, stopped, and fault.
  • Verify the required communication-health checks.
  • Confirm the machine's approved test conditions and motion safeguards.
  • Verify that reset and restart logic are separate.

17.2 During controlled testing

  • Compare the PLC status with the drive display.
  • Verify ready, enabled, running, stopped, and fault indications where practical.
  • Compare the transmitted reference with the drive-interpreted reference.
  • Compare actual-speed feedback with a suitable independent measurement when required.
  • Test at-speed detection across the approved operating range.
  • Confirm that start and stop timeouts behave correctly.
  • Verify fault capture and the documented reset procedure.
  • Confirm the PLC detects invalid or stale communication data.
  • Verify that clearing a fault does not cause an unintended restart.
  • Record the results and retain the approved configuration.

Fault injection or communication-loss testing must be conducted using an approved commissioning method. Do not create uncontrolled motion or defeat protective functions merely to test a status bit.

18. Safety considerations

Ordinary drive status bits and PLC feedback are useful for machine control, but they are not automatically safety-rated.

Important distinctions include:

  • Drive_Ready does not prove that a machine is safe to move.
  • Drive_Running = FALSE does not prove electrical isolation.
  • A zero-speed display does not necessarily prove physical standstill.
  • A normal communication network may not provide the safety integrity required for a safety function.
  • A standard fault reset does not authorize a restart after a safety-related stop.
  • An ordinary speed limit in PLC logic is not equivalent to a validated safety-rated speed-limiting function.

Where the risk assessment requires safety-related monitoring, use appropriate safety-rated devices and functions, designed and validated for the required performance level or safety integrity level.

Maintenance work must follow the site's isolation and lockout procedures. Status feedback must never be treated as a substitute for verifying safe isolation.

19. Interview questions and answers

1. What is the difference between a control word and a status word?

A control word contains commands sent to the drive. A status word contains information returned by the drive about its state and conditions.

2. What is the difference between ready and running?

Ready generally means the drive can accept operation under its configured conditions. Running indicates a defined operating or run state. Exact semantics depend on the drive.

3. Why is actual-speed feedback needed if the PLC already knows the speed reference?

The reference only describes the target. Feedback helps confirm the response, detect speed deviations, identify stalls, and determine whether a sequence may proceed.

4. How do you decode a status word?

Use the manufacturer's documented bit mapping and masks, then validate the decoded results against actual drive states during commissioning.

5. Why should communication health be separate from the drive fault bit?

Communication can fail while the last received fault bit remains false or stale. A separate validity check detects whether the status data can still be trusted.

6. What is an at-speed condition?

It is a condition indicating that actual speed is within a configured tolerance of the reference, often maintained for a defined settling time.

7. Why can a running bit be true when the motor is not at the target speed?

Running may indicate an enabled or active drive state rather than target-speed attainment. The speed feedback and at-speed condition must be evaluated separately.

8. Why should fault reset and restart be separate?

Clearing a fault does not automatically mean that the machine is ready or authorized to resume motion. Separate logic prevents unexpected restarts.

9. How would you diagnose incorrect actual-speed feedback?

Check the raw received value, data mapping, scaling, units, signedness, source selection, and drive display. Compare with a suitable independent measurement if needed.

10. Can a standard PLC running bit be used to prove safe standstill?

Not unless the complete function uses suitable safety-rated components and is designed and validated for the required safety performance. A normal status bit alone is insufficient.

20. Final engineering checklist

  • Separate commands, status, and measured feedback.
  • Decode status bits using the exact drive documentation.
  • Confirm the meanings of ready, enabled, running, stopped, warning, and fault.
  • Scale actual speed correctly and identify its physical meaning.
  • Compare reference and feedback using a defined tolerance.
  • Add suitable settling times and sequence timeouts.
  • Monitor communication health and data freshness.
  • Capture fault codes and relevant operating values.
  • Keep fault reset separate from restart authorization.
  • Display invalid feedback clearly on the HMI.
  • Validate all important states during controlled commissioning.
  • Never treat ordinary status feedback as proof of safety or isolation.

The core principle is that a drive integration is not complete when commands are transmitted. It is complete only when the returned state is correctly interpreted, the feedback is validated, and the machine responds appropriately when the expected result does not occur.
