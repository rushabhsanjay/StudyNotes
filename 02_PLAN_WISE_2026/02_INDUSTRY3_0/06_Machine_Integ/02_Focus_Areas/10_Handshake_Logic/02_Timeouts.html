1. Purpose of timeouts in industrial automation

A timeout is a defined time limit for an expected event, response, or operation. If the event does not occur within the allowed period, the controller detects an abnormal condition and executes the specified fault-handling logic.

In machine integration, timeouts help detect situations where one machine is waiting indefinitely for another machine, a communication partner has stopped responding, a sensor has not changed state, or an operation has taken longer than expected.

Typical examples include:

  • A robot sends Load_Request, but the CNC never acknowledges it.
  • A PLC sends a command to a VFD, but the drive never reports ready.
  • A CNC requests a fixture clamp, but the clamp-closed sensor does not activate.
  • A test station starts a measurement, but no result arrives.
  • A PLC communication connection is interrupted.
  • A machine reports Busy but never reports Complete.

Core principle: A timeout detects that an expected condition did not occur within a defined time. It does not automatically identify the root cause, prove that the machine is unsafe, or guarantee that stopping is the correct response.

The required response depends on the machine state, process requirements, hazards, and approved control design.

2. Basic timeout operation

A typical timeout has four parts:

  1. Trigger condition: The event that starts timing.
  2. Expected condition: The event that should occur before the deadline.
  3. Time limit: The maximum permitted waiting duration.
  4. Timeout response: The defined action if the deadline expires without the expected event.

Example: PLC A requests a component transfer from PLC B.

PLC A issues Transfer_Request
             ↓
Start timeout timer
             ↓
PLC B returns Transfer_Acknowledge?
       ↙                 ↘
     YES                  NO
      ↓                   ↓
Cancel timeout       Deadline expires
      ↓                   ↓
Continue sequence    Set timeout fault
                          ↓
                   Execute defined
                   fault response

The timer should run only while the relevant request is outstanding. If the request is withdrawn, the operation completes, or the system enters a fault state, the timer should be handled according to the defined state-machine design.

3. Essential timeout terminology

Term Meaning
Timeout preset Configured time limit for an expected event
Elapsed time Time measured since the timer started
Timeout condition The deadline has expired while the expected event remains unmet
Response window The allowed period for a response
Communication timeout The expected communication update or response did not occur within the permitted period
Operation timeout A machine operation exceeded its allowed duration
Watchdog A mechanism that monitors whether a task or system is progressing within expected limits
Retry Another attempt after an unsuccessful or timed-out transaction
Fault latch A stored fault condition that remains active until the defined clearing conditions are met
Recovery The controlled process of resolving the fault and restoring an acceptable machine state

A timeout preset is not the same as the measured stopping time of a machine. Communication timing and safety-related stopping performance are different engineering concerns.

4. Types of timeouts

4.1 Handshake timeout

Used when one controller expects a response from another controller.

Examples:

  • Request to Acknowledge.
  • Start_Command to Running.
  • Unload_Request to Unload_Complete.
  • Reset_Request to Reset_Accepted.

The timer starts when the request becomes active and stops when the required response is detected.

4.2 Communication timeout

Used when communication health or incoming data updates are expected within a defined interval.

Examples:

  • PLC-to-PLC cyclic connection stops updating.
  • A robot controller loses its communication connection.
  • A remote I/O adapter stops responding.
  • A supervisory gateway stops delivering valid updates.

Communication timeouts should use the connection diagnostics and timing behavior supported by the actual communication system wherever possible.

4.3 Operation timeout

Used when a physical or process operation is expected to finish within a defined duration.

Examples:

  • A pneumatic cylinder does not reach its extended position.
  • A fixture does not complete clamping.
  • A CNC cycle exceeds an expected duration.
  • A robot takes too long to complete a transfer.
  • A test instrument does not complete a measurement.

An operation timeout should be based on realistic operating conditions and verified against actual machine behavior.

4.4 Sensor-transition timeout

Used when a sensor is expected to change state after an action.

Example:

A PLC energizes a valve and expects the cylinder-extended sensor to become active within the allowed time.

If the sensor does not activate, possible causes include insufficient air pressure, a mechanical obstruction, a failed valve, incorrect wiring, a faulty sensor, or a logic problem.

The timeout detects the missing transition. Additional diagnostics are required to distinguish the cause.

4.5 Startup and readiness timeout

Used when a machine is expected to become ready after power-up, reset, initialization, or mode change.

Examples:

  • Drive fails to report ready.
  • Robot controller does not complete initialization.
  • CNC does not reach the expected operating state.
  • Remote device fails to establish communication.

4.6 Watchdog timeout

A watchdog monitors whether a controller task, software process, or communication partner is making expected progress.

The term can refer to different mechanisms, including a hardware watchdog, task watchdog, application heartbeat, or communication watchdog. Their purposes and failure responses must not be confused.

5. Selecting a timeout preset

Timeout values should be engineered from actual behavior and requirements rather than chosen arbitrarily.

Consider:

  • Normal response time.
  • Worst-case response time under valid operating conditions.
  • PLC scan time and task scheduling.
  • Network update interval and communication variation.
  • Device response time.
  • Mechanical movement time.
  • Process variation, temperature, load, and pressure.
  • Required fault-detection speed.
  • Consequences of waiting too long.
  • False-timeout risk during legitimate operation.

A useful conceptual relationship is:

\[ T\_{\text{preset}} > T\_{\text{expected,max}} + T\_{\text{margin}} \]

Where:

  • \(T\_{\text{preset}}\) is the configured timeout.
  • \(T\_{\text{expected,max}}\) is the justified maximum expected response time.
  • \(T\_{\text{margin}}\) accounts for documented timing variation and measurement uncertainty.

This is a design principle, not a universal formula. The margin must be justified for the specific operation.

Example

Suppose a transfer acknowledgement normally arrives within 150 ms, and verified worst-case valid operation takes 280 ms. The design team allows an additional 120 ms for documented variation.

\[ T\_{\text{preset}} = 280 + 120 = 400\text{ ms} \]

A 400 ms timeout may be a reasonable candidate for testing, provided the timing assumptions are valid and the fault-detection requirement permits it.

A timeout of several seconds would unnecessarily delay fault detection in this example. A timeout of 200 ms could generate false faults during legitimate operation.

The final value should be confirmed through commissioning tests and operating data.

6. Timer behavior in a PLC

A common IEC 61131-3 timer is TON, an on-delay timer.

Its general behavior is:

  • When IN becomes true, elapsed timing begins.
  • When the elapsed time reaches preset PT, output Q becomes true.
  • When IN becomes false, a standard non-retentive TON resets its elapsed time and output.

Exact behavior, timer resolution, and supported data types depend on the PLC platform and implementation.

Typical variables include:

Variable Purpose
IN Enables the timer
PT Preset time
ET Elapsed time
Q Indicates that the preset has elapsed while the timer remains enabled

A timer is not a complete timeout strategy by itself. The application must decide what event enables the timer, what event cancels it, whether the fault is latched, and how recovery is handled.

7. Structured Text example: acknowledgement timeout

The following example monitors a request until acknowledgement arrives.

AckTimer(
    IN := RequestActive AND NOT Acknowledge,
    PT := T#500ms
);

IF RequestActive AND Acknowledge THEN
    AckTimer(IN := FALSE, PT := T#500ms);
    AckTimeoutFault := FALSE;
END_IF;

IF RequestActive AND NOT Acknowledge AND AckTimer.Q THEN
    AckTimeoutFault := TRUE;
END_IF;

This illustrates the basic timing concept, but it is not a complete production implementation. In particular, the fault-clearing behavior, timer invocation pattern, state transitions, and restart conditions must be designed consistently with the PLC platform and application requirements.

For a robust implementation:

  • Invoke the timer consistently in the program task.
  • Define when the request becomes active.
  • Define exactly which acknowledgement completes the wait.
  • Prevent a stale acknowledgement from satisfying a new request.
  • Latch the timeout if required by the fault-handling specification.
  • Do not clear the fault merely because a late acknowledgement arrives unless that behavior is explicitly intended.
  • Define how the active transaction is resolved after the timeout.

8. Better approach: state-specific timeout logic

A machine often has multiple waiting states, each with different timing requirements.

For example:

State Expected event Timeout purpose
WAIT_READY Remote machine becomes ready Detect unavailable machine
WAIT_ACK Request is acknowledged Detect missing response
WAIT_START Operation begins Detect accepted command that does not initiate activity
WAIT_COMPLETE Operation completes Detect stalled process
WAIT_RELEASE Handshake returns to idle Detect incomplete release sequence

Separate timeout definitions improve diagnostics. A single timer covering an entire sequence may identify that something went wrong without revealing which stage failed.

Conceptual state logic:

WAIT_ACK
   ↓ Acknowledge received
WAIT_COMPLETE
   ↓ Operation complete
WAIT_RELEASE
   ↓ Handshake returned to idle
IDLE

WAIT_ACK + deadline expired
   ↓
ACK_TIMEOUT fault

WAIT_COMPLETE + deadline expired
   ↓
OPERATION_TIMEOUT fault

Each state should have one clearly defined expected event and a corresponding timeout response.

9. Rising edges, timer resets, and stale acknowledgements

A frequent problem occurs when a previous transaction leaves Acknowledge = TRUE.

The next request starts, and the PLC immediately sees the old acknowledgement. The timer never detects the missing response because the logic incorrectly assumes that the new request has been accepted.

Prevent this by defining a clean transaction boundary.

Possible strategies include:

  • Require the previous acknowledgement to return low before accepting a new request.
  • Require a known idle state before beginning a transaction.
  • Use a request identifier or transaction counter.
  • Validate that acknowledgement corresponds to the active request.
  • Track state transitions rather than relying only on raw signal levels.

For networked PLCs, cyclic data may update asynchronously relative to each controller's program scan. The handshake must tolerate that behavior.

10. Timeout faults versus communication faults

A timeout does not always mean communication has failed.

Observation Possible interpretation
No acknowledgement, connection healthy Receiver is busy, request conditions are unmet, or receiver logic is blocked
No acknowledgement, connection unhealthy Communication failure is a likely cause
Acknowledgement arrives, completion does not Operation is stalled or completion conditions are not met
Completion arrives after timeout The transaction's outcome requires reconciliation
Heartbeat changes but process data is unchanged Communication may be alive while the process state is not progressing
Process data changes but heartbeat does not Heartbeat mapping, update behavior, or application logic may be incorrect

A useful diagnostic system records both the timeout state and communication-health state.

For example, ACK_TIMEOUT and COMM_LOSS should not automatically be the same fault code because they indicate different failure categories and may require different troubleshooting steps.

11. Retry logic

A retry is another attempt to obtain a response after a failed attempt or timeout.

Retries can help when a failure is temporary, but they can create duplicate operations if the first request was accepted and the acknowledgement was lost.

Before retrying, determine whether the operation is safe to repeat and whether the previous transaction's outcome is known.

A retry policy should define:

  • Which faults permit retries.
  • Maximum retry count.
  • Delay between attempts.
  • Whether the request must be released before retrying.
  • How duplicates are identified.
  • What happens when all retries fail.
  • Whether operator intervention is required.

Example policy:

Issue request
     ↓
Wait for acknowledgement
     ↓
Timeout?
  ↙       ↘
 No        Yes
 ↓          ↓
Continue   Is retry permitted?
           ↙             ↘
         Yes              No
          ↓                ↓
   Check transaction    Latch fault
   and retry limit      and hold sequence
          ↓
   Retry if safe

A retry counter must not wrap silently or allow endless retries. The system should eventually reach a clearly defined fault state.

12. Timeout fault latching

A latched timeout remains recorded until the defined reset conditions are satisfied.

This is useful when an operator or maintenance technician needs to investigate why an operation failed.

A typical fault record includes:

  • Fault code.
  • Machine and station identification.
  • Handshake state at the time of failure.
  • Expected signal.
  • Actual signal state.
  • Configured timeout.
  • Elapsed time, where available.
  • Communication health.
  • Transaction identifier.
  • Timestamp and recovery history.

The fault-clear procedure should be separate from the detection logic. Otherwise, a condition that briefly clears may erase useful diagnostic information before anyone can investigate it.

13. Fault response and machine-state handling

When a timeout occurs, the controller should not simply set a generic fault bit and continue the sequence.

It should determine which actions are valid in the current state.

Possible responses include:

  • Preventing a new operation from starting.
  • Holding the sequence at the current state.
  • Marking the active transaction as unresolved.
  • Requesting a controlled process stop where specified.
  • Preventing automatic retry until the cause is known.
  • Raising an operator alarm.
  • Recording diagnostic information.
  • Requiring a defined recovery procedure.

For example, if a part-transfer timeout occurs after a robot has entered a shared workspace, immediately repeating the transfer command could be dangerous or could damage the part. The system needs to determine the actual physical state before resuming.

Safety distinction: A standard application timeout is not a substitute for a safety-rated response. If a delay or loss of response can create a hazard, the required protective behavior must be implemented and validated through the appropriate safety-related design.

14. Practical timeout examples

Example A: PLC-to-PLC acknowledgement

Machine A issues Transfer_Request. Machine B must acknowledge it within the configured time.

If no acknowledgement arrives:

  • Record ACK_TIMEOUT.
  • Capture the request and communication states.
  • Hold the transaction according to the interface specification.
  • Avoid generating a duplicate request until the transaction status is resolved.

Example B: Pneumatic cylinder

The PLC energizes a valve and expects Cylinder_Extended within a defined time.

If the sensor does not activate:

  • Record CYL_EXTEND_TIMEOUT.
  • Inspect air pressure, valve operation, mechanical obstruction, sensor alignment, and wiring.
  • Determine whether the cylinder is partially extended or remains in its initial position.
  • Follow the approved recovery procedure before commanding further movement.

Example C: Drive readiness

The PLC sends a drive enable command and expects Drive_Ready.

If the timeout expires:

  • Check the drive's local fault status.
  • Verify control mode and enable conditions.
  • Inspect the fieldbus connection and status-word mapping.
  • Check whether an interlock or parameter configuration prevents readiness.

Example D: Test-station result

The PLC starts a measurement and expects a valid result.

If no result arrives:

  • Determine whether the test was started successfully.
  • Check the test instrument's status and communication diagnostics.
  • Verify that the response belongs to the current part and transaction.
  • Do not classify the part as passed simply because the test timed out.

15. Commissioning and testing checklist

Configuration

  • Define the start condition for every timeout.
  • Define the expected response or completion condition.
  • Set justified time presets for each waiting state.
  • Confirm timer resolution and PLC task behavior.
  • Define timer cancellation and reset conditions.
  • Separate communication faults from operation timeouts.

Functional tests

  • Verify normal responses complete before the deadline.
  • Confirm that a missing acknowledgement generates the expected fault.
  • Test delayed responses near the configured deadline.
  • Verify stale acknowledgements cannot satisfy a new request.
  • Test communication loss during an active transaction.
  • Verify retry limits and duplicate-operation prevention.
  • Test a late completion after a timeout.
  • Confirm fault records retain useful diagnostic information.
  • Verify recovery does not resume an uncertain transaction blindly.

Documentation

  • Record timeout values and their justification.
  • Document fault codes and expected operator actions.
  • Record retry rules and maximum attempts.
  • Define reset and restart behavior.
  • Retain commissioning results and relevant timing measurements.

16. Interview questions and answers

1. What is a timeout in PLC programming?

It is a time-based condition used to detect when an expected event, response, or operation does not occur within a defined period.

2. What is the difference between a handshake timeout and an operation timeout?

A handshake timeout detects a missing response such as acknowledgement. An operation timeout detects that a physical or process operation has exceeded its allowed duration.

3. How do you select a timeout preset?

Use justified worst-case response times, communication variation, scan timing, process conditions, and the required fault-detection time. Verify the selected value during commissioning.

4. Why should each handshake state have its own timeout?

Different states wait for different events. State-specific timeouts identify the stage that failed and provide more useful diagnostics.

5. Can a timeout prove that communication has failed?

No. The receiving machine may be busy, blocked by an interlock, or unable to complete the operation. Communication-health diagnostics help distinguish these conditions.

6. Why can retries cause problems?

The original request may have been accepted even though its acknowledgement was lost. Repeating the operation without checking transaction status can cause duplicate processing or unintended movement.

7. What is a stale acknowledgement?

It is an acknowledgement left over from a previous transaction or otherwise unrelated to the active request. It can incorrectly satisfy a new handshake if the protocol does not validate transaction state.

8. Why latch timeout faults?

Fault latching preserves the event for investigation and prevents a transient change in signal state from silently erasing the failure.

9. What should happen when a response arrives after a timeout?

The controller should reconcile the actual transaction and machine state. It should not automatically assume that the operation failed or succeeded.

10. Is a PLC timeout a safety function?

Not by itself. A standard timeout can support normal fault handling, but any required safety-related response must be implemented using an appropriate validated safety architecture.

17. Key engineering principles

  • Define the event that starts each timer.
  • Define the exact response that cancels it.
  • Use state-specific timeouts with meaningful diagnostics.
  • Select presets from measured or justified operating behavior.
  • Detect stale acknowledgements and invalid transaction states.
  • Distinguish communication loss from a machine-operation timeout.
  • Limit retries and prevent duplicate operations.
  • Preserve fault information for maintenance.
  • Define what happens when completion arrives late.
  • Validate fault response and recovery before production release.

Timeouts are a basic but essential diagnostic mechanism. A well-designed timeout does more than detect a delay: it identifies the failed stage, preserves the transaction state, and moves the machine into a defined response instead of leaving it waiting indefinitely.
