1. Purpose of sequence steps and interlocks

A sequence is an ordered set of machine operations executed according to defined conditions. Each step represents a particular operation or phase, while interlocks determine whether that operation is permitted to begin or continue.

In an automated production line, a sequence may include loading a part, clamping it, confirming its position, machining it, inspecting the result, releasing the fixture, and transferring the part to the next machine.

The sequence controller must ensure that these actions occur in the correct order and that each transition happens only when the required conditions are satisfied.

Sequence control answers: What operation should happen next?

Interlocks answer: Is that operation permitted under the current conditions?

For example, a CNC cycle-start command may require the workpiece to be clamped, the correct program to be selected, the door to be in its required state, the drive system to be ready, and all applicable safety conditions to be satisfied.

A sequence step alone does not guarantee that these conditions are valid. They must be evaluated explicitly.

2. Fundamental terminology

Term Meaning Example
Sequence Ordered set of machine operations Load, clamp, machine, unload
Step Defined phase of a sequence STEP_20_CLAMP
Transition Condition that allows movement to another step Clamp confirmation received
Interlock Condition that permits or prevents an operation Door closed and process ready
Permissive Positive condition required to enable an action Drive reports ready
Completion condition Evidence that the current operation has finished Cylinder extended sensor is active
Timeout Maximum permitted waiting period for an event Clamp confirmation within 3 seconds
Fault state State used when the sequence cannot proceed normally Clamp timeout
Initial state Defined starting point for a sequence Machine idle and ready
Recovery step Controlled procedure for restoring a valid state Reconcile part position after a fault
Hold condition Condition that prevents progression or requests a defined pause Downstream machine unavailable
Abort condition Condition that terminates or diverts an operation according to the design Process fault requiring sequence cancellation

Terminology varies between PLC platforms and machine builders. The underlying control principles remain the same.

3. Basic sequence architecture

A typical machine sequence contains initialization, execution, completion, and fault handling.

INITIALIZATION
      ↓
IDLE / READY
      ↓ Start request and permissives valid
STEP 10: PREPARE
      ↓ Preparation complete
STEP 20: LOAD PART
      ↓ Part-position confirmation
STEP 30: CLAMP PART
      ↓ Clamp confirmation
STEP 40: EXECUTE PROCESS
      ↓ Process completion
STEP 50: UNCLAMP / UNLOAD
      ↓ Unload confirmation
STEP 60: COMPLETE CYCLE
      ↓
IDLE / READY

Any active step
      ↓ Fault or invalid condition
DEFINED HOLD / FAULT HANDLING
      ↓
DIAGNOSIS AND RECOVERY

This is a conceptual example. Real machines may contain parallel operations, multiple substates, conditional branches, quality checks, and separate manual and automatic sequences.

4. Step numbering and organization

Step numbers provide a consistent way to identify the current operation and diagnose sequence behavior.

Example:

Step Name Main action Completion condition
0 IDLE Wait for a cycle request Valid start request
10 PRECHECK Verify process conditions All required permissives valid
20 LOAD_PART Load workpiece Part-position confirmation
30 CLAMP_PART Clamp workpiece Clamp confirmation
40 PROCESS Execute production operation Process-complete confirmation
50 UNCLAMP_PART Release workpiece Unclamp confirmation
60 UNLOAD_PART Transfer workpiece Destination confirmation
70 CYCLE_COMPLETE Record cycle completion Completion handling finished
900 FAULT Stop normal sequence progression Defined recovery conditions satisfied

The numbers are illustrative, not a universal standard.

Using intervals such as 10, 20, 30, and 40 can make modifications easier because additional steps may be inserted between existing steps. However, meaningful state names are more important than the numbering scheme.

5. Step activation and transition logic

A step is active when the sequence controller identifies it as the current operating phase.

In a simple sequential implementation:

CASE SequenceStep OF

    0: (* IDLE *)
        IF StartRequest AND StartPermissivesOK THEN
            SequenceStep := 10;
        END_IF;

    10: (* PRECHECK *)
        IF PrecheckComplete THEN
            SequenceStep := 20;
        END_IF;

    20: (* LOAD PART *)
        IF LoadComplete THEN
            SequenceStep := 30;
        END_IF;

    30: (* CLAMP PART *)
        IF ClampConfirmed THEN
            SequenceStep := 40;
        END_IF;

    40: (* PROCESS *)
        IF ProcessComplete THEN
            SequenceStep := 50;
        END_IF;

    50: (* UNCLAMP *)
        IF UnclampConfirmed THEN
            SequenceStep := 60;
        END_IF;

    60: (* UNLOAD *)
        IF UnloadComplete THEN
            SequenceStep := 70;
        END_IF;

    70: (* COMPLETE *)
        IF CycleCompletionHandled THEN
            SequenceStep := 0;
        END_IF;

END_CASE;

This example illustrates the structure only. It does not implement complete fault handling, output control, transition timeouts, restart rules, or safety functions.

A production implementation must define what happens if a completion signal never arrives, an interlock becomes invalid, or a fault occurs during an active operation.

6. Interlocks and permissives

Interlocks are used to prevent an operation from proceeding when its required conditions are not satisfied.

For example, a clamp operation might require:

  • The machine is in an allowed operating mode.
  • The workpiece is present.
  • The fixture is in the required position.
  • The clamping system is available.
  • The requested operation is valid for the current sequence step.
  • No conflicting operation is active.
  • The applicable safety-related conditions are satisfied.

A conceptual permissive expression is:

\[ \text{ClampPermissive} = \text{PartPresent} \land \text{FixturePositionOK} \land \text{ClampSystemReady} \land \text{CorrectSequenceStep} \land \text{NoConflictingCommand} \]

The actual expression must include the conditions appropriate to the equipment and its risk assessment.

Interlock categories

Category Example Purpose
Process Correct recipe selected Prevents an invalid process
Position Axis at required position Prevents an operation at an incorrect location
Device readiness Drive ready Confirms equipment availability
Material Part present Prevents processing without the required workpiece
Sequence Current step is CLAMP_PART Prevents commands from unrelated steps
Mutual exclusion Robot and CNC do not occupy a shared zone simultaneously Prevents conflicting movements
Communication Receiving machine is ready Prevents invalid machine-to-machine commands
Quality Previous inspection passed Prevents unauthorized progression of rejected parts
Safety-related Validated protective conditions satisfied Supports the required risk-reduction function

Ordinary PLC interlocks and safety-related functions are not interchangeable. Safety-related functions must use the validated safety architecture, suitable components, and required verification.

7. Difference between a transition condition and an interlock

A transition condition determines when the sequence moves to the next step. An interlock determines whether an operation is allowed.

They may use some of the same signals, but they serve different purposes.

Example: during clamping, the sequence may transition to the machining step when clamp confirmation is received. The machining operation must also be inhibited whenever the required clamping condition is not valid.

Feature Transition condition Interlock
Main question Is the current step complete? Is the operation permitted?
Typical use Advance sequence state Enable or inhibit an action
Example Clamp confirmed Clamp condition valid before machining
Behavior when false Sequence waits or times out Operation remains inhibited
Evaluation period Usually associated with a particular transition May need continuous evaluation during the operation

A common programming error is checking an interlock only when entering a step, then assuming it remains valid. Conditions that must remain true throughout an operation need appropriate ongoing monitoring and defined fault or hold behavior.

8. Entry actions, continuous actions, and exit actions

Each step can be organized into three functional parts.

Entry actions execute when a step becomes active. Examples include recording a timestamp, clearing a step-specific timer, or issuing a one-time request.

Continuous actions apply while the step remains active. Examples include maintaining an authorized command, monitoring a sensor, and checking a timeout.

Exit actions execute when the step ends. Examples include withdrawing a request, recording completion, or preparing the next operation.

Step becomes active
       ↓
Execute entry actions
       ↓
Execute continuous actions
       ↓
Evaluate completion and fault conditions
       ↓
Transition permitted?
       ├── No → Remain in step
       └── Yes → Execute exit actions
                    ↓
                Activate next step

Not every PLC requires a dedicated entry-action framework. However, explicitly distinguishing one-time and continuous behavior prevents repeated command pulses, unintended timer resets, and inconsistent request handling.

9. Step-entry detection

In cyclic PLC execution, a step can remain active for many scans. Therefore, an action intended to execute once should not be written as an unrestricted action that repeats every scan.

For example, a new request may need to be issued once when entering STEP_20, then remain active until the handshake protocol completes.

Conceptually:

Step20Active := SequenceStep = 20;

Step20Entry := Step20Active AND NOT Step20ActivePrevious;

Step20ActivePrevious := Step20Active;

This is a simplified rising-edge pattern. Its implementation must account for initialization, retained state, task execution order, and restart behavior.

An alternative is to use a platform-supported rising-edge instruction or an explicit step-entry flag.

The request itself should follow the agreed interface protocol. Some interfaces require a one-scan pulse; others require the request to remain asserted until acknowledged.

10. Interlocks for machine-to-machine sequences

In integrated production lines, each machine may have its own sequence controller. The machines must coordinate their steps through defined interface signals.

Example: Machine A transfers a workpiece to Machine B.

Machine A: Verify part available
             ↓
Machine A: Send transfer request
             ↓
Machine B: Check receiving permissives
             ↓
Machine B: Send ready / acknowledge
             ↓
Both machines: Perform coordinated transfer
             ↓
Receiving position confirmed
             ↓
Both machines: Complete transaction
             ↓
Return handshake to defined idle state

The exact handshake depends on the interface contract. A single acknowledgement does not necessarily mean the transfer is complete. The protocol may require separate ready, accepted, in-progress, and complete states.

Important interlocks include:

  • Receiving machine is available.
  • Transfer area is clear.
  • Source part is present.
  • Destination can accept the part.
  • The robot or transfer device is in the required state.
  • No conflicting machine sequence is active.
  • The active transaction is valid.
  • Completion is confirmed by appropriate feedback.

The two machines should agree on what each signal means and when it may change.

11. Mutual-exclusion interlocks

Mutual exclusion prevents incompatible operations from occurring simultaneously.

For example, if a robot and a CNC axis share a restricted workspace, the control design may require one device to have access while the other remains in a defined permitted state.

Conceptually:

\[ \text{RobotMotionPermitted} = \text{ZoneGrantedToRobot} \land \text{RobotMotionConditionsOK} \]
\[ \text{CNCMotionPermitted} = \text{ZoneGrantedToCNC} \land \text{CNCMotionConditionsOK} \]

The zone-allocation mechanism must prevent conflicting grants and define how a grant is released, recovered, and reassigned after a fault.

Where collision avoidance or personnel protection requires a safety-rated function, ordinary mutual-exclusion logic is not sufficient by itself. The required safety architecture must be designed and validated separately.

12. Interlock priority and fault handling

When multiple conditions fail at once, the controller needs a clear response strategy.

For example, if a clamp-confirmation timeout occurs while the receiving machine also loses communication, the controller should record both relevant events and preserve the information needed to identify the initiating failure.

A useful priority structure is:

  1. Apply the required safety-related response through the validated safety system.
  2. Prevent or stop normal sequence progression according to the machine's defined control behavior.
  3. Capture the initiating fault, active step, and relevant status information.
  4. Determine whether the condition requires a hold, fault state, controlled stop, or another defined response.
  5. Permit recovery only when the required conditions have been verified.

The normal PLC should not override or bypass safety-related functions. A safety demand may require a specific stop response, and the correct response depends on the validated design.

Avoid a generic rule such as “any fault sets the step to zero.” Returning to idle can erase the context of an incomplete operation and may leave the physical machine in an unexpected state.

13. Timeouts within sequence steps

A timeout detects that an expected event has not occurred within the permitted interval.

For a clamp step, the timer may start when the clamp command is issued and stop when the required confirmation is received.

Conceptual logic:

ClampTimeoutTimer(
    IN := SequenceStep = 30 AND NOT ClampConfirmed,
    PT := T#3s
);

IF SequenceStep = 30 AND ClampTimeoutTimer.Q THEN
    ClampFault := TRUE;
END_IF;

This is illustrative IEC 61131-3 Structured Text style. The correct timer instance declaration, invocation order, reset behavior, and signal qualification depend on the PLC platform.

Timeouts should be based on actual equipment behavior, process requirements, and validated acceptance criteria rather than arbitrary values.

For each timed step, define:

  • When timing starts.
  • What event ends timing.
  • The allowed duration.
  • What happens when the duration expires.
  • Which diagnostics are recorded.
  • Whether retry is permitted.
  • What conditions are required for recovery.

A timeout does not prove that an actuator failed. It indicates that the expected event was not observed in time. Diagnosis must distinguish a physical failure, a sensor issue, a communication issue, and an incorrect sequence condition.

14. Sequence hold, stop, abort, and fault

These terms should have explicit definitions in the machine specification.

Behavior Meaning Typical handling
Hold Pause or inhibit progression according to the defined process behavior Preserve relevant state and wait for the permitted resume condition
Normal stop End or stop the sequence through the designed normal stopping procedure Complete required stopping actions
Abort Terminate or divert an operation under defined conditions Apply the specified abort and cleanup procedure
Fault A detected abnormal condition requiring defined handling Capture diagnostics and enter the appropriate fault behavior
Emergency stop A safety-related response initiated through the emergency-stop function Follow the validated safety design and reset procedure

A hold command must not be assumed to stop all physical movement immediately. Similarly, an ordinary stop command must not be treated as equivalent to an emergency stop.

For operations that cannot be interrupted arbitrarily, such as certain machining, material-handling, or process steps, the machine design must specify the appropriate response to a stop or fault.

15. Avoiding common sequence-programming errors

Unconditional output commands

If a clamp command remains active outside the intended step, the actuator may operate unexpectedly during another sequence phase.

Use explicit command ownership, step conditions, and appropriate device-level interlocks.

Incorrect transition ordering

If the program transitions to the next step before confirming completion, later operations may start while the previous action is still active.

Require the defined completion evidence before advancing.

Stale completion signals

A completion bit left active from a previous transaction may cause the next step to advance immediately.

Clear or reinitialize transaction state according to the interface protocol, and use sequence identifiers or fresh-event validation where necessary.

Repeated one-shot commands

An operation such as a program-selection request may be issued every scan instead of once on step entry.

Use suitable edge detection, command-state tracking, and acknowledgement handling.

Resetting a timer every scan

If a timer is unintentionally reinitialized while a step remains active, the timeout may never occur.

Use a persistent timer instance and verify its invocation and reset conditions.

Skipping steps during recovery

Forcing the current step directly to a later state may bypass required physical actions or confirmations.

Use a defined recovery sequence that verifies actual machine conditions before allowing a transition.

Treating an HMI button as an interlock

An operator button expresses a request. It does not prove that the operation is permissible.

Evaluate the required interlocks independently of the HMI request.

16. Commissioning and testing sequence logic

Sequence testing should verify normal operation and abnormal transitions, not merely demonstrate one successful production cycle.

  • Confirm every step has a defined purpose and exit condition.
  • Verify each transition condition independently.
  • Verify each operation's required permissives.
  • Confirm commands are active only in the intended states.
  • Test missing, delayed, and contradictory feedback.
  • Test timeout behavior for each timed operation.
  • Verify fault logging preserves the active step and first relevant fault.
  • Confirm communication loss does not create an invalid transition.
  • Test reset and restart behavior from every relevant interruption point.
  • Verify that stale acknowledgements cannot complete a new transaction.
  • Check manual, setup, and automatic mode behavior.
  • Verify recovery cannot bypass required safety-related conditions.
  • Confirm machine-to-machine signals follow the interface specification.
  • Record test results, program revision, and approved deviations.

Testing should be carried out under an approved commissioning plan with appropriate safeguards, especially when deliberately creating faults or interrupting motion.

18. Documentation and maintainability

A well-designed sequence should be understandable by someone who did not originally write the program.

Maintain the following documentation:

  • Sequence-step list with state names and descriptions.
  • State-transition table.
  • Interlock and permissive matrix.
  • I/O and device-command mapping.
  • Handshake signal definitions.
  • Timeout settings and justification.
  • Fault-response and recovery procedures.
  • Operating-mode restrictions.
  • Machine-to-machine interface contract.
  • Commissioning test cases and results.
  • Software version and change history.

A transition table is particularly useful during development and troubleshooting.

Current step Required condition Next step Failure response
IDLE Valid start and permissives PRECHECK Remain idle
PRECHECK All required conditions verified LOAD_PART Hold or fault according to design
LOAD_PART Part-position confirmation CLAMP_PART Load timeout handling
CLAMP_PART Clamp confirmation PROCESS Clamp fault handling
PROCESS Process complete and acceptable UNCLAMP_PART Process fault handling
UNCLAMP_PART Unclamp confirmation UNLOAD_PART Unclamp timeout handling
UNLOAD_PART Transfer complete CYCLE_COMPLETE Transfer fault handling
CYCLE_COMPLETE Completion handling finished IDLE Completion fault handling

This table is an example. Actual conditions and failure responses must reflect the specific machine's requirements.

19. Interview questions and answers

1. What is a sequence step?

A sequence step is a defined phase of an automated operation with specific actions, monitoring conditions, and transition criteria.

2. What is an interlock?

An interlock is a condition or set of conditions that prevents an operation from occurring when the required conditions are not satisfied.

3. What is the difference between a permissive and a transition condition?

A permissive determines whether an operation is allowed. A transition condition determines whether the sequence may advance to another step.

4. Why should commands be controlled by sequence state?

State-based command control prevents unrelated steps from issuing conflicting commands and makes machine behavior easier to understand and troubleshoot.

5. Why can a stale acknowledgement cause problems?

It can make a new transaction appear complete before the current operation has actually occurred.

6. Why are timeouts needed?

Timeouts detect missing or delayed expected events and prevent the sequence from waiting indefinitely without a defined fault response.

7. What is the purpose of mutual exclusion?

It prevents incompatible operations from occurring simultaneously, such as two devices attempting to occupy a shared restricted workspace.

8. Should every fault return the sequence to idle?

No. The physical machine may be in an intermediate state. The controller should preserve relevant diagnostics and enter the defined fault or recovery state.

9. Why is step-entry detection useful?

It enables one-time actions when a step becomes active, preventing commands or initialization actions from repeating every PLC scan.

10. How do you troubleshoot a sequence that will not advance?

Identify the active step, inspect its transition condition, monitor each required input and permissive, check timer status, and verify that no fault or communication condition is blocking progression.

11. Can an ordinary PLC interlock replace a safety-rated function?

No. Where risk reduction requires a safety-related function, it must be implemented and validated using the required safety architecture.

12. What makes sequence logic maintainable?

Clear state names, explicit transitions, well-defined interlocks, consistent timeout and fault handling, transaction-aware communication, and accurate documentation.

20. Key engineering principles

  • Define each step by its intended operation and completion criteria.
  • Separate sequence progression from permission to operate.
  • Continuously monitor conditions that must remain valid during an operation.
  • Use explicit entry actions for commands that should occur once.
  • Define timeout and fault behavior for every important wait condition.
  • Prevent stale signals from completing new operations.
  • Coordinate machine-to-machine sequences through a documented interface.
  • Preserve diagnostic information when a fault occurs.
  • Do not skip required physical checks during recovery.
  • Keep safety-related functions separate from ordinary sequence logic and validate them according to the applicable requirements.

Reliable sequence control is not simply a list of commands executed in order. It is a controlled state model in which every operation has defined prerequisites, every transition has valid evidence, and every abnormal condition has a deliberate response.
