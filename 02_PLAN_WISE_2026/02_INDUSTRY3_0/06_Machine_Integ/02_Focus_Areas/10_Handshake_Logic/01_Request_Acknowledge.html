1. Purpose of request and acknowledge

Request-and-acknowledge is a communication pattern in which one automation system requests an operation and another system explicitly confirms that it has received or accepted the request.

It is widely used in PLC-to-PLC communication, robot-to-CNC integration, conveyor transfers, automated fixtures, test stations, and production-line coordination.

The purpose is to prevent one machine from assuming that another machine has completed an operation merely because a command was sent.

For example, a robot requests permission to load a CNC machine. The CNC confirms that it has accepted the request, performs or coordinates the required operation, and provides the defined completion indication. The robot proceeds according to the agreed sequence.

Core principle: A request is not an acknowledgement, an acknowledgement is not completion, and completion is not necessarily permission to begin the next operation.

2. Basic handshake architecture

A handshake typically uses two or more signals exchanged between two controllers.

Machine A / Requesting PLC             Machine B / Receiving PLC

Request = TRUE ----------------------->
                                  Check conditions
                                  Accept request
<----------------------- Acknowledge = TRUE
Perform coordinated operation
<----------------------- Complete = TRUE
Request = FALSE --------------------->
<----------------------- Acknowledge = FALSE
<----------------------- Complete = FALSE

This is a conceptual sequence. Actual implementations may use additional signals, state numbers, transaction identifiers, or different reset sequences.

A handshake must define the exact meaning and ownership of every signal. Without that agreement, two PLC programs can each behave correctly according to their own assumptions and still deadlock the production line.

3. Essential handshake signals

Signal Typical owner Meaning
Request Requesting machine Requests a defined operation
Acknowledge Receiving machine Confirms that the request has been received or accepted, as explicitly defined
Busy Receiving machine Indicates that the operation is in progress
Complete Receiving machine Indicates that the defined operation has finished
Ready Receiving machine Indicates that the machine is available to accept the operation
Fault Relevant machine Indicates that a fault prevents normal operation
Reset_Request Defined by interface contract Requests a reset or recovery action
Comm_Healthy Communication layer or application Indicates that communication is considered valid
Data_Valid Producer or interface logic Indicates that associated data is valid for use

A minimal handshake may use only Request and Acknowledge, but this is appropriate only when the operation's start, completion, and recovery behavior are otherwise unambiguous.

For longer operations, separate acceptance and completion signals are generally easier to diagnose and maintain.

4. Understand the difference between handshake states

State Meaning What the requester should infer
Idle No active transaction No operation is currently being requested
Request active Requesting machine has issued a request The request has been presented
Accepted Receiving machine has accepted the request The operation may proceed according to the agreed protocol
Busy Operation is in progress Do not assume completion
Complete Defined operation has finished The completion condition has been met
Release Requesting machine releases the request The transaction is being cleared
Reset to idle Both sides return to the agreed initial state A new transaction may begin if all conditions permit
Fault Operation cannot proceed normally Follow the defined fault and recovery procedure

Important distinction: Acknowledge must have a precise definition. It may mean request received, request accepted, or operation completed. These meanings should not be combined in one signal unless the interface is intentionally designed around that simplified behavior.

5. Four-phase request-and-acknowledge handshake

A common implementation uses a four-phase sequence in which each signal returns to its inactive state before the next transaction.

The following example defines Acknowledge as acceptance, while Complete indicates the end of the operation.

Phase 1: Request

Machine A confirms that it has a valid operation to request and sets Request = TRUE.

Machine B monitors the request and checks whether it is ready, whether the data is valid, and whether the operation is permitted by its normal control conditions.

Phase 2: Acknowledge

If the request is accepted, Machine B sets Acknowledge = TRUE.

Machine A detects the acknowledgement and knows that the request has been accepted. It must not interpret this as proof that the operation is complete.

Phase 3: Completion and request release

Machine B executes the operation and sets Complete = TRUE when the specified completion conditions are met.

Machine A detects completion and sets Request = FALSE.

Phase 4: Acknowledge release

Machine B detects that the request has been released and clears Acknowledge and Complete according to the interface definition.

Machine A waits until the handshake returns to idle before initiating another transaction.

Machine A: Request
       ────────┐                 ┌────────
               └─────────────────┘

Machine B: Acknowledge
                 ┌─────────────┐
       ──────────┘             └──────────

Machine B: Complete
                       ┌───────┐
       ────────────────┘       └──────────

This waveform is illustrative. Actual timing depends on the implementation, communication update rate, PLC scan cycle, and agreed signal-reset sequence.

6. Why holding a request matters

In a cyclic PLC program, a request may need to remain active until the receiving controller has acknowledged it.

A one-scan pulse can be missed if the communication path updates more slowly than the producer's PLC task or if the receiver samples the signal after the pulse has disappeared.

A level-based request is often more robust:

  • Set the request when the operation is ready to be issued.
  • Keep it active until the required acknowledgement is observed.
  • Do not generate a new request while the previous transaction is unresolved.
  • Release the request according to the protocol.
  • Wait for the defined return-to-idle condition before starting another transaction.

A pulse-based protocol can also work when both sides explicitly support event capture, buffering, or another reliable mechanism. The key is to design for the actual communication behavior rather than assuming every signal transition will be observed.

7. State-machine implementation

A state machine makes the handshake sequence explicit and prevents unrelated conditions from advancing the transaction unpredictably.

Example states:

State number State name Main behavior
0 IDLE Wait for a valid new request condition
10 WAIT_ACK Hold request and wait for acceptance
20 WAIT_COMPLETE Monitor the operation until completion
30 RELEASE_REQUEST Clear the request after completion
40 WAIT_IDLE Wait for acknowledgement and completion signals to clear
90 FAULT Record the fault and execute the defined recovery behavior

Conceptual sequence:

IDLE
  ↓ Valid request conditions
WAIT_ACK
  ↓ Acknowledge
WAIT_COMPLETE
  ↓ Complete
RELEASE_REQUEST
  ↓ Request cleared
WAIT_IDLE
  ↓ Acknowledge and Complete cleared
IDLE

Any active state
  ↓ Defined fault condition
FAULT

The state machine must define what happens when a fault occurs at each stage, including whether the current part's status becomes uncertain and whether operator intervention is required.

8. Example PLC logic

The following Structured Text example demonstrates the requester side of a handshake. It assumes that Acknowledge means request acceptance and Complete means operation completion.

The timeout logic is deliberately not included here because it is the next study topic. In a real application, each waiting state must have the required timeout and fault handling.

CASE HandshakeState OF

    0: (* IDLE *)
        Request := FALSE;

        IF StartRequest
           AND RemoteReady
           AND CommHealthy
           AND DataValid
           AND NOT RemoteFault THEN

            Request := TRUE;
            HandshakeState := 10;
        END_IF;

    10: (* WAIT_ACK *)
        Request := TRUE;

        IF RemoteFault OR NOT CommHealthy THEN
            HandshakeState := 90;

        ELSIF Acknowledge THEN
            HandshakeState := 20;
        END_IF;

    20: (* WAIT_COMPLETE *)
        Request := TRUE;

        IF RemoteFault OR NOT CommHealthy THEN
            HandshakeState := 90;

        ELSIF Complete THEN
            Request := FALSE;
            HandshakeState := 40;
        END_IF;

    40: (* WAIT_IDLE *)
        Request := FALSE;

        IF NOT Acknowledge AND NOT Complete THEN
            HandshakeState := 0;
        END_IF;

    90: (* FAULT *)
        Request := FALSE;

        (* Latch fault information and follow the
           application's approved recovery procedure. *)

END_CASE;

This is an instructional example, not drop-in machine code. Its implementation must address PLC scan behavior, variable initialization, state retention, communication-loss handling, fault latching, and the receiving controller's exact handshake protocol.

The receiving PLC must also implement its own compatible state machine. Both sides need to agree on the sequence and reset behavior.

9. Receiving PLC logic

The receiver must not acknowledge every request unconditionally. It should validate the request and accept it only when the defined conditions are met.

Typical conditions include:

  • The receiving machine is in an allowed operating state.
  • The required resources are available.
  • The requested operation is supported.
  • Associated data is valid and belongs to the current transaction.
  • No blocking fault exists.
  • Communication data is current and valid.
  • Any required safety conditions are satisfied through the appropriate safety architecture.

Conceptual logic:

IF Request
   AND ReceiverReady
   AND DataValid
   AND CommHealthy
   AND NOT ReceiverFault
   AND OperationPermitted THEN

    Acknowledge := TRUE;
    OperationActive := TRUE;

END_IF;

This simplified fragment shows acceptance conditions only. A complete receiver must also define when acknowledgement is cleared, how completion is generated, how repeated requests are handled, and what happens during faults or power recovery.

Do not place safety-critical decisions solely in ordinary handshake logic. Safety-related conditions must be enforced by the validated safety system where required.

10. Edge detection versus level detection

A level-based request remains active until the required handshake condition occurs.

An edge-based request is recognized when the signal changes from FALSE to TRUE, often using a rising-edge detector.

Property Level-based request Edge-based request
Request representation Signal remains active Signal transition represents the event
Missed update risk Reduced when the receiver samples a sustained request Higher if the transition is not captured reliably
Repeated processing risk Requires transaction-state control Requires event identity or reliable edge handling
Recovery after communication loss Must reconcile the active request Must determine whether the event was received
Typical use PLC-to-PLC handshakes Event-oriented interfaces with reliable event handling

Neither method is universally superior. The correct design depends on the communication mechanism, transaction requirements, and fault-recovery strategy.

11. Preventing duplicate operations

Suppose Machine A issues a request to load a part. Machine B accepts it, but the acknowledgement is delayed or temporarily lost. Machine A may incorrectly assume the request failed and issue it again.

If Machine B interprets the repeated request as a new operation, the part may be processed twice or a mechanism may move unexpectedly.

Useful controls include:

  • Maintain an active transaction state.
  • Do not issue a new request while an earlier transaction remains unresolved.
  • Use a transaction counter or unique request identifier where appropriate.
  • Associate completion and process results with the correct transaction.
  • Define behavior after controller restart or communication recovery.
  • Determine whether a repeated request is a duplicate, a continuation, or a new operation.

A request bit alone may be insufficient when transactions carry important production data or when the operation cannot safely be repeated.

12. Handshake with part data

In automotive production, a handshake may include a part number, variant code, recipe number, or process parameters.

A robust sequence is:

  1. The requester prepares the data.
  2. The requester confirms that the data is valid.
  3. The requester presents the request.
  4. The receiver accepts the request only after validating the data.
  5. The receiver associates the accepted data with the active transaction.
  6. The receiver reports completion and the relevant result.
  7. The requester verifies that the completion belongs to the expected transaction.
  8. Both sides clear the transaction according to the agreed protocol.

If data can change while the request is active, the receiver may process a mixture of old and new values. The protocol should therefore define when data becomes stable and how the receiver confirms that it has accepted the correct data set.

13. Faults and abnormal handshake conditions

Condition Possible cause Required design response
Request remains active indefinitely Receiver never accepts it Detect the abnormal waiting condition and follow the defined fault procedure
Acknowledgement stays active Request release was not detected or reset behavior differs Inspect both state machines and the signal-reset sequence
Completion arrives before acceptance Incorrect logic, stale data, or protocol mismatch Reject or diagnose the unexpected state transition
Request is processed twice Repeated request interpreted as a new transaction Add transaction-state control and duplicate detection
Both machines wait indefinitely Each side is waiting for a signal the other will not generate Review the protocol and recovery sequence
Acknowledgement is lost during a network interruption Communication loss or data invalidation Reconcile transaction state before retrying
Complete remains active into the next cycle Completion-reset sequence is incomplete Require the defined return-to-idle condition
Request is accepted but operation cannot finish Machine fault, resource loss, or process failure Report a defined failure state and preserve transaction status
PLC restarts while a handshake is active State and signal retention differ Define initialization and transaction-recovery behavior
Request is accepted with invalid product data Missing or incorrect data validation Validate data before acceptance and record the rejection reason

14. Testing and commissioning checklist

Interface definition

  • Define the meaning of request, acknowledgement, busy, complete, and fault.
  • Assign ownership and direction to each signal.
  • Define when the request is asserted and released.
  • Define when acknowledgement is asserted and released.
  • Define the exact completion condition.
  • Specify the initial and idle states.
  • Define handling for invalid data and communication loss.

Functional testing

  • Test a normal transaction from idle through completion.
  • Confirm the request remains active as required.
  • Verify that acknowledgement occurs only when the receiver accepts the request.
  • Verify that completion represents the defined operation result.
  • Confirm that the next transaction cannot start prematurely.
  • Test a request while the receiver is busy.
  • Test a request while the receiver has a fault.
  • Test repeated requests and duplicate transactions.
  • Test interrupted communication and recovery.
  • Test controller initialization during an active transaction.
  • Verify diagnostic messages and event logging.

Documentation

  • Save the interface signal list and state definitions.
  • Record timing expectations and abnormal-state behavior.
  • Document recovery and operator intervention requirements.
  • Store test results and approved controller versions.
  • Record changes to handshake behavior and validate both endpoints.

15. Practical example: Robot and CNC loading handshake

Consider a robot that loads a component into a CNC machine.

Step Robot-side behavior CNC-side behavior
1 Checks that a valid component is available Confirms it is in a state that permits loading
2 Issues Load_Request Monitors the request
3 Holds the request active Validates readiness and accepts the request
4 Waits for Load_Acknowledge Sets acknowledgement according to the agreed protocol
5 Executes the coordinated loading sequence Coordinates the required machine state
6 Reports transfer completion Confirms the required loading condition
7 Releases the request and waits for the handshake to clear Clears acknowledgement and completion according to the protocol
8 Returns to its next sequence state Returns to the defined state for the next operation

The actual design must define whether the robot or CNC owns each physical movement, how part presence is verified, and what happens if the part is not correctly seated.

An acknowledgement must not be used as proof of physical part transfer unless that is explicitly what the signal represents and the required condition is verified.

16. Interview questions and answers

1. What is a request-and-acknowledge handshake?

It is a protocol in which one controller requests an operation and another controller explicitly confirms receipt or acceptance according to a defined interface contract.

2. Why should a request remain active until acknowledgement?

A sustained request reduces the chance that the receiving controller will miss a short pulse due to scan timing or communication update behavior.

3. Is acknowledgement the same as completion?

No. Acknowledgement normally indicates that the request has been received or accepted. Completion indicates that the defined operation has finished.

4. Why use a state machine for a handshake?

A state machine makes transaction progression explicit and helps prevent premature transitions, duplicate operations, and ambiguous recovery behavior.

5. What is the difference between level-triggered and edge-triggered requests?

A level-triggered request remains active while the transaction is pending. An edge-triggered request is recognized from a signal transition and requires reliable event capture.

6. How do you prevent a repeated request from executing twice?

Track the active transaction, prevent new transactions while one remains unresolved, and use transaction identifiers or duplicate-detection logic where appropriate.

7. What happens if acknowledgement never arrives?

The requester must detect that the expected response has not occurred and execute the defined fault-handling procedure. The precise timeout behavior is covered in the next topic.

8. Why must the two PLC programs be designed together?

Both controllers must agree on signal ownership, acceptance conditions, timing expectations, state transitions, reset behavior, and fault recovery.

9. How should a handshake recover after communication returns?

Both sides should reconcile their current transaction states, validate the data, and return to an agreed state before proceeding. They should not blindly repeat an operation whose outcome is uncertain.

10. Can a handshake replace a safety system?

No. Standard handshake logic coordinates normal machine operations. Required safety functions must be implemented using an appropriate safety-related architecture and validated independently.

17. Key engineering principles

  • Define each handshake signal precisely.
  • Separate request, acceptance, execution, and completion.
  • Keep requests active according to the protocol.
  • Use explicit state transitions instead of loosely connected conditions.
  • Ensure both controllers agree on the release and idle sequence.
  • Prevent duplicate processing and premature new requests.
  • Validate process data before accepting a transaction.
  • Define fault handling and recovery for every active state.
  • Treat communication loss and controller restart as explicit design cases.
  • Validate the complete transaction on both controllers before production release.

A reliable handshake makes the transaction state unambiguous to both machines. That is the difference between coordinated automation and two controllers exchanging hopeful Boolean values.
