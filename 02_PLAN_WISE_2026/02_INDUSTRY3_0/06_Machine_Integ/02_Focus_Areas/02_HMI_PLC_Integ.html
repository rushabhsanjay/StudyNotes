1. Purpose of HMI-PLC integration

HMI-PLC integration connects the operator interface to the PLC so operators can monitor machine conditions, enter authorized commands, select permitted operating modes, adjust approved parameters, and respond to alarms.

The HMI (Human-Machine Interface) provides the interaction layer. The PLC (Programmable Logic Controller) executes the machine logic, evaluates permissives and interlocks, and controls the physical process.

A well-engineered HMI does not merely display PLC bits. It presents the correct process context, communicates the current machine state, prevents ambiguous operator actions, and provides enough diagnostic information to support safe operation and efficient troubleshooting.

Typical HMI functions include:

  • Displaying machine status, sequence steps, sensor states, and production counts.
  • Providing Start, Stop, Reset, Acknowledge, and mode-selection commands where authorized.
  • Displaying alarms, alarm history, and relevant recovery instructions.
  • Allowing controlled changes to setpoints, recipes, timers, and production parameters.
  • Displaying actual values, target values, trends, and process limits.
  • Showing device diagnostics, communication status, and data validity.
  • Supporting operator login, permissions, audit trails, and production records where required.

The HMI is not a substitute for PLC interlocks or a safety-rated control system. A button that is disabled on the screen is only a user-interface restriction. The PLC and the approved safety architecture must independently enforce the relevant control conditions.

2. HMI-PLC architecture

A typical architecture connects the HMI runtime to the PLC through an industrial communication interface.

Operator
   ↕
HMI screen objects
   ↕
HMI tags and command logic
   ↕
Communication driver / industrial network
   ↕
PLC tags and data blocks
   ↕
PLC sequence, permissives, interlocks, diagnostics
   ↕
I/O modules and field devices
   ↕
Physical machine

For example, an operator presses the HMI Start button. The HMI sends a request to the PLC. The PLC checks the operating mode, safety-system status, device readiness, fault state, and other required permissives. If the conditions are satisfied, the PLC starts its sequence and publishes the resulting state. The HMI then displays the actual state reported by the PLC.

The button press is a request, not proof that the machine has started.

2.1 Responsibilities of each layer

Function HMI responsibility PLC responsibility
Machine status Display the received status Determine and publish the actual status
Start command Submit an authorized request Validate permissives and execute the sequence
Stop command Submit the configured stop request Perform the defined stop behavior
Fault reset Submit a reset request Validate reset conditions and reset eligible faults
Mode selection Present permitted choices Validate and apply mode-transition rules
Setpoint entry Validate basic input format and range Validate the value and its effect on the process
Alarm display Present alarm state and details Detect and report the relevant machine condition
Recipe selection Present available choices Validate and apply approved parameters
Safety function Display safety status where appropriate Participate only as specified by the validated safety architecture

Some functions may be split across an HMI, PLC, recipe manager, safety controller, or supervisory system. The interface specification should make ownership explicit.

3. HMI tags and PLC tag mapping

An HMI tag is a variable the HMI uses to access information from a PLC or another data source. Depending on the platform, the tag may reference a PLC symbol directly, an address, a data-block field, or a communication-driver mapping.

Common tag categories include:

Tag category Example Purpose
Status Machine_Running Displays the actual operating state
Command Start_Request Requests a defined action
Feedback Drive_Ready Displays a device-reported condition
Fault Machine_Faulted Indicates a defined fault state
Setpoint Pressure_Setpoint Holds an operator-adjustable target
Actual value Pressure_Actual Displays the measured process value
Mode Machine_Mode Represents the selected operating mode
Alarm Low_Pressure_Alarm Reports a defined alarm condition
Diagnostic PLC_Communication_OK Indicates a communication-health condition
Data quality Pressure_Data_Valid Indicates whether the value is valid for use

3.1 Naming conventions

Use names that describe the equipment, action, and meaning. For example:

  • Clamp_Extend_Request
  • Clamp_Extended_Feedback
  • Clamp_Extend_Timeout
  • Conveyor_Speed_Setpoint
  • Conveyor_Speed_Actual
  • Drive_Fault_Code
  • Auto_Mode_Active

Avoid ambiguous names such as M1, B12, Start2, or Value unless they are clearly defined by a documented naming standard.

For larger systems, group tags by machine, station, device, and function. Consistent naming improves navigation, alarm configuration, maintenance, and future upgrades.

3.2 Match the data types

The HMI and PLC must agree on the type and representation of each tag.

PLC data type Typical HMI use Main concern
BOOL Buttons, indicators, status lamps Correct polarity and request behavior
INT Small signed numeric values Range and signedness
DINT Counters and larger integer values Range and overflow
REAL Measurements and setpoints Precision, scaling, and invalid values
WORD Packed status or command bits Correct bit interpretation
STRING Messages, serial numbers, recipe names Length, encoding, and data consistency
TIME or duration type Timers and durations Units, conversion, and supported display format
Structured data Device status, commands, and diagnostics Compatible field layout and data-block mapping

The supported types and memory layouts vary by PLC and HMI platform. Do not assume that similarly named types always have identical representations across different vendors.

3.3 Scaling and engineering units

If the PLC stores a raw analog count but the HMI displays engineering units, define where conversion occurs and apply it consistently.

For example, if a PLC tag already contains pressure in bar, the HMI should display that value with the correct unit and formatting. It should not scale the value again.

If the PLC stores a raw integer that represents a pressure value multiplied by 100, the HMI may need to divide by 100 for display, depending on the chosen architecture.

Document:

  • Raw and engineering ranges.
  • Units and decimal precision.
  • Valid operating limits.
  • Display limits versus permitted entry limits.
  • Behavior for stale, invalid, or out-of-range data.

A visually plausible number is not evidence that the mapping is correct.

4. HMI communication configuration

The HMI must communicate with the correct PLC using a supported driver and compatible connection settings.

4.1 Configuration items

  • PLC model and communication interface.
  • HMI model or runtime version.
  • Communication driver and supported protocol.
  • PLC IP address or other required network identity.
  • Subnet and routing configuration, where applicable.
  • PLC connection path, rack, slot, or device name as required by the platform.
  • Correct PLC tag names, addresses, and data-block references.
  • Access permissions and security configuration.
  • Polling or subscription behavior and update rates.
  • Supported firmware and software versions.

4.2 Common connection arrangements

PLC ecosystem Typical HMI integration approach
Siemens WinCC with supported S7 communication and PLC tag access
Rockwell Automation FactoryTalk View or supported HMI communication with Logix controllers
Mitsubishi GOT and GT Works/GT Designer communication with supported Mitsubishi PLCs
Modbus-compatible equipment HMI driver using Modbus TCP or RTU where supported
OPC UA-enabled systems HMI or supervisory client accessing an OPC UA server with configured security

These are examples, not universal compatibility guarantees. Verify the exact controller, HMI, firmware, driver, license, and protocol support before designing the interface.

4.3 Communication status

Display communication health separately from machine state. A stopped machine and an HMI that cannot communicate with the PLC are not the same condition.

Useful indicators include:

  • PLC connection healthy.
  • Last valid update or data freshness.
  • Communication fault or timeout.
  • Data validity where the driver exposes it.
  • HMI runtime or server availability, if relevant.

If communication fails, the HMI must not present an old status value as though it were current. A clear indication such as COMMUNICATION LOST is preferable to a frozen green RUNNING indicator.

5. Designing command buttons correctly

HMI command buttons are one of the most important parts of the integration because they translate operator actions into machine-control requests.

Common commands include:

  • Start.
  • Stop.
  • Reset.
  • Alarm acknowledge.
  • Auto/Manual mode selection.
  • Cycle start or single-cycle request.
  • Recipe selection.
  • Jog or manual movement commands where authorized.

The correct implementation depends on the command semantics. A momentary request, a maintained command, and a toggle are not interchangeable.

5.1 Momentary command

A momentary command is active for a defined short period or until the receiving logic acknowledges it. It is useful for actions such as Start Request or Reset Request.

A basic request/acknowledgement pattern is:

Operator presses Start
          ↓
HMI sets Start_Request
          ↓
PLC detects the request
          ↓
PLC validates permissives
          ↓
PLC accepts or rejects the request
          ↓
PLC updates status and acknowledgement
          ↓
HMI displays the result

The request must have a defined clearing mechanism. Depending on the platform, this may be a momentary HMI write, a PLC-cleared request, or a request/acknowledgement handshake.

5.2 Maintained command

A maintained command remains active until the operator releases it or the control logic changes its state. Some manual functions require this behavior, such as a jog command that is permitted only while a button is held.

For movement-related commands, define what happens if the HMI loses communication while the command is active. The required behavior depends on the machine design and risk assessment. A stale maintained command must not cause unintended motion.

5.3 Toggle command

A toggle changes a stored state from OFF to ON or ON to OFF. It can be confusing for commands such as Start or Reset because the displayed state may not correspond to the actual machine state.

Prefer explicit requests such as Start_Request and Stop_Request, with separate feedback such as Machine_Running, rather than a single ambiguous Start bit that alternates between states.

5.4 Avoid direct control of internal machine state

The HMI should generally request an action rather than directly writing internal sequence states or arbitrary PLC memory.

For example, the HMI should request a mode change through a defined interface. The PLC should decide whether the transition is valid and perform the transition according to the sequence rules.

Writing directly to a step number, state-machine variable, or internal latch can bypass required logic and leave the machine in an inconsistent condition.

6. Start, Stop, Reset, and Acknowledge

These commands serve different purposes and must have clearly defined behavior.

Command Intended purpose What it must not imply
Start Requests production or sequence initiation Does not prove the machine has started
Stop Requests the configured operational stop Does not automatically mean emergency stop
Reset Requests clearing of eligible latched faults Does not guarantee the fault cause has disappeared
Acknowledge Confirms that an alarm or message has been recognized Does not necessarily clear the fault
Mode change Requests a transition between permitted operating modes Does not automatically make the transition valid
Cancel/Abort Requests cancellation or abortion of a defined operation Must not bypass required safe-state behavior

6.1 Start command design

The PLC should evaluate the relevant permissives before accepting a start request. Examples include:

  • Correct operating mode.
  • Safety system in the required state.
  • No blocking fault.
  • Required devices ready.
  • Material or part available where required.
  • Correct recipe and production context.
  • Machine sequence in an allowed starting state.
  • No conflicting manual or automatic command.

The exact list depends on the equipment and risk assessment.

The HMI should distinguish among Start Requested, Start Accepted, Starting, and Running when those distinctions matter operationally. Otherwise, an operator may press Start repeatedly because the screen does not explain why nothing appears to happen.

6.2 Stop command design

A normal stop typically requests a controlled cessation of operation. The PLC must implement the machine's defined stopping sequence, such as completing a permitted step, stopping a conveyor, or bringing a process to its required state.

An emergency stop is a separate safety function designed and validated according to the machine's risk assessment and safety architecture. A standard HMI Stop button must not be presented as a replacement for an emergency-stop device.

6.3 Reset command design

A reset request should be accepted only when the relevant reset conditions are met. Depending on the machine, this may require the fault cause to be removed, devices to be in valid states, and the sequence to be in an allowed condition.

Resetting a fault should not silently initiate production or motion. Reset and Start should remain distinct actions unless a specific, justified, and validated design explicitly requires otherwise.

6.4 Alarm acknowledgement

Acknowledgement means that an alarm has been recognized by the operator. It does not necessarily mean that the underlying condition has cleared.

For example, a low-pressure alarm may be acknowledged while the pressure remains low. The alarm state should continue to reflect the condition according to the configured alarm philosophy.

7. PLC logic for HMI requests

A robust design separates the operator's request, PLC validation, accepted action, actual state, and diagnostic response.

A simplified conceptual example:

HMI:
    Start_Request

PLC:
    Start_Permissives_OK
    Start_Accepted
    Start_Rejected
    Start_Reject_Code
    Machine_Running

Start request handling:
    Detect new Start_Request
    Validate machine mode and permissives
    If valid:
        Accept request
        Initiate approved sequence
    Else:
        Reject request
        Set diagnostic reason
    Publish actual machine state

This is a design illustration, not vendor-specific executable code. The exact implementation depends on the PLC platform and the required request-handling mechanism.

7.1 One-shot processing

If the HMI holds a request bit ON for several PLC scans, the PLC should not accidentally execute the action multiple times.

Possible methods include:

  • Rising-edge detection.
  • A request/acknowledgement handshake.
  • A command sequence number.
  • A transaction identifier for more complex interfaces.

The appropriate method depends on the HMI write behavior, communication update rate, and application requirements.

7.2 Request and acknowledgement handshake

For a more controlled interface, use a request that remains valid until the PLC responds.

HMI sets Request
        ↓
PLC detects new request
        ↓
PLC validates request
        ↓
PLC returns Accepted or Rejected
        ↓
HMI recognizes response
        ↓
Request is cleared according to protocol
        ↓
PLC completes the defined action

Specify how a new request is distinguished from an old one, how timeouts are handled, and when the interface is ready for the next request.

For systems with multiple HMI clients, shared command tags require additional coordination. Two operators must not unknowingly overwrite one another's commands.

8. Manual, Auto, and Setup modes

Operating modes change which commands are permitted and how the machine sequence behaves.

Typical modes include:

  • Automatic: The PLC executes the approved production sequence.
  • Manual: The operator commands permitted functions individually.
  • Setup: The machine supports defined adjustment or preparation activities.
  • Maintenance: Restricted functions are available to authorized personnel under the approved procedure.
  • Jog: A specific movement is requested under defined control conditions.

The names and behavior vary by machine.

8.1 Mode-selection design

The HMI should display the active mode reported by the PLC, not merely the last button pressed.

The PLC should validate each requested mode transition. For example, changing from Automatic to Manual while a cycle is active may require the cycle to stop or reach a defined transition point.

8.2 Manual controls

Manual commands can cause physical movement and require deliberate design. Each command should have a clear purpose, visible status, and defined release or cancellation behavior.

Consider:

  • Is the command permitted in the current mode?
  • Are required interlocks satisfied?
  • Is the relevant device ready?
  • Is the command momentary or maintained?
  • What happens when the button is released?
  • What happens when HMI communication fails?
  • Is separate authorization required?
  • Does the action affect a safety-related function?

HMI visibility and user permissions do not replace the required machine interlocks or safety controls.

9. Setpoints, recipes, and parameter entry

HMI screens often allow operators or authorized engineers to enter values such as speed, pressure, temperature, timing, position, or quantity.

Setpoint entry requires more than displaying a numeric field.

9.1 Setpoint validation

Validate the value at the appropriate control layers:

  1. Input format: Is the entered value numeric and correctly formatted?
  2. Engineering range: Is it within the permitted range?
  3. Process constraints: Is it valid for the selected product and machine state?
  4. Authorization: Is the user permitted to change it?
  5. Application timing: Can the value be applied immediately, or only when stopped or in setup?
  6. Acceptance feedback: Did the PLC or authorized parameter manager accept the value?
  7. Persistence: Does the value survive a restart, and is that behavior intended?

The HMI may perform early validation for usability, but the PLC or authoritative parameter-management layer must enforce the actual permitted range and operating conditions.

9.2 Entered value versus applied value

Display these separately when the distinction matters:

  • Requested setpoint.
  • Accepted or active setpoint.
  • Actual process value.

For example, an operator may enter a conveyor speed of 30 Hz, but the PLC or drive may reject the request due to a configured limit or operating mode. The HMI should not display the requested value as if it were already active.

9.3 Recipe management

A recipe can contain a coordinated group of parameters for a product variant or process.

A robust recipe workflow may include:

  • Recipe identification and revision.
  • Validation against the machine and product variant.
  • Authorized loading.
  • Range and compatibility checks.
  • Application confirmation.
  • Audit history where required.
  • Recovery to an approved recipe if loading fails.

Avoid silently changing recipe values while a cycle is using them. Define whether recipe changes take effect immediately, at the next cycle, or only after a controlled machine-state transition.

10. Alarm design and presentation

Alarms help operators recognize abnormal conditions and determine the appropriate response. Poor alarm design produces excessive noise and makes important faults harder to identify.

10.1 Alarm categories

Category Example Purpose
Process alarm Pressure below permitted range Indicates a process condition outside defined limits
Equipment fault Drive reports an overcurrent fault Indicates equipment cannot operate normally
Sequence alarm Cylinder did not reach position before timeout Identifies a failed sequence transition
Communication alarm Remote I/O or PLC connection lost Indicates unavailable or unreliable data
Quality alarm Inspection result rejected Indicates a product or process quality issue
Maintenance warning Filter service interval reached Indicates a maintenance action may be required
Safety-system status Guard circuit or safety controller reports a condition Displays safety-related status as defined by the safety design

The presentation of safety-system information does not make the ordinary HMI an independent safety function.

10.2 Alarm fields

A useful alarm record may include:

  • Alarm ID.
  • Equipment or station.
  • Clear description.
  • Occurrence timestamp.
  • Active or cleared state.
  • Acknowledgement state.
  • Severity or priority.
  • Relevant measured value.
  • Likely cause or diagnostic context.
  • Approved operator response.
  • Related fault code.

10.3 Alarm state distinctions

An alarm can be active and unacknowledged, active and acknowledged, cleared but unacknowledged, or cleared and acknowledged, depending on the alarm system's behavior.

Do not assume that acknowledging an alarm clears it or that a cleared alarm no longer needs to appear in history.

10.4 Alarm quality

Good alarms should be actionable, distinguishable, and relevant to the operator's responsibilities.

Avoid:

  • Repeating the same alarm continuously for one underlying fault.
  • Alarm messages such as ERROR 5 without useful context.
  • Alarms triggered by expected transitions.
  • Alarms that cannot be distinguished from communication loss.
  • Alarm floods caused by one failed upstream device.
  • Reset buttons that clear diagnostic evidence without resolving the cause.

Use the plant's alarm philosophy to define priorities, deadbands, delays, latching, acknowledgement, shelving where supported, and escalation behavior.

11. HMI screen design and navigation

Screen design affects troubleshooting speed, operator workload, and the likelihood of mistakes.

A useful hierarchy separates overview, equipment detail, operation, diagnostics, alarms, trends, and authorized configuration.

Plant or line overview
        ↓
Machine overview
        ↓
Station or equipment detail
        ↓
Device diagnostics and I/O status

Common navigation:
    Alarms / Alarm history / Trends / Recipes / Maintenance

11.1 Overview screen

Show the information needed to understand the current production condition:

  • Machine or line state.
  • Active operating mode.
  • Current order or product, where relevant.
  • Production count and target.
  • Active alarms and blocking faults.
  • Communication-health indicators.
  • Important process values.
  • Clear navigation to the affected station.

Avoid filling the overview with every available PLC tag. Detailed information belongs on the appropriate equipment screen.

11.2 Equipment detail screen

For a station or machine, consider showing:

  • Sequence state or current step.
  • Sensor states.
  • Actuator commands and feedback.
  • Drive status and relevant actual values.
  • Permissives that prevent operation.
  • Active fault and diagnostic code.
  • Expected versus actual position or process state.
  • Device communication and data-validity status.

The screen should make it possible to answer, "What is the machine waiting for?" without opening several unrelated pages.

11.3 Navigation principles

  • Use consistent navigation across screens.
  • Keep important alarms visible or readily accessible.
  • Label units beside numeric values.
  • Use clear, unambiguous button labels.
  • Distinguish commands from status indicators.
  • Avoid changing the meaning of a color between screens.
  • Provide confirmation for consequential actions where appropriate.
  • Avoid excessive pop-ups that hide important process information.
  • Keep maintenance and engineering functions separate from ordinary operator functions where required.

12. Color, indicators, and operator feedback

Color should reinforce meaning rather than carry meaning by itself. Use text, symbols, and position so that the interface remains understandable when viewed on different displays or by users with color-vision deficiencies.

A possible convention is:

Visual state Example meaning Design consideration
Neutral Stopped or inactive Make the state explicit in text
Green Running or normal Use only where the plant standard defines this meaning
Yellow or amber Warning or attention required Distinguish warning from fault
Red Fault or abnormal condition Use according to the approved alarm philosophy
Grey or crossed-out Disabled or unavailable Explain why the function is unavailable
Flashing indicator Urgent attention or transition Use sparingly and consistently

These are common conventions, not universal rules. Follow the plant's HMI standard and applicable requirements.

12.1 Show why a command is unavailable

Instead of merely disabling the Start button, the HMI should ideally display the blocking condition, such as:

  • Drive not ready.
  • Active blocking fault.
  • Incorrect operating mode.
  • Required guard or safety-system status not satisfied.
  • Part not present.
  • Recipe not validated.
  • Downstream station unavailable.

Show only conditions that are valid, relevant, and understandable. A list of raw internal PLC bits is rarely useful to an operator.

13. Trends and numeric displays

Trends help operators and engineers understand process behavior over time. They are especially useful for temperature, pressure, speed, force, vibration, cycle time, and analog measurements.

13.1 Trend configuration

Define:

  • Tag or measurement source.
  • Engineering units.
  • Time range and update interval.
  • Sampling or event-capture method.
  • Minimum and maximum display scales.
  • Alarm limits or reference values where appropriate.
  • Data quality and communication-loss behavior.
  • Whether the data is live, buffered, or historical.

A live HMI trend and a long-term historian trend may use different storage and sampling methods. A screen trend should not be assumed to provide a permanent audit record.

13.2 Numeric display checks

  • Use the correct engineering unit.
  • Display an appropriate number of decimal places.
  • Avoid implying more precision than the instrument supports.
  • Indicate invalid or stale data.
  • Distinguish zero from unavailable data.
  • Verify sign, scaling, rounding, and range limits.
  • Avoid clipping values outside the displayed scale without an indication.

A pressure display showing 0.0 bar because the communication driver failed is fundamentally different from a valid measurement of zero pressure.

14. HMI security and user permissions

HMI permissions control which users may view or execute particular functions. The exact capabilities depend on the HMI platform and the plant's identity-management design.

Typical roles might include:

Role Example permitted functions
Operator View process, issue normal operating commands, acknowledge alarms
Shift leader Operator functions plus approved production-level actions
Maintenance Access maintenance diagnostics and authorized manual functions
Controls engineer Access engineering diagnostics and controlled configuration functions
Administrator Manage authorized accounts and system configuration

These roles are illustrative. Actual access must follow company policy, risk assessment, and the principle of least privilege.

14.1 Security controls

  • Use individual accounts or managed identities where supported.
  • Avoid shared accounts with broad privileges.
  • Require authentication for restricted functions.
  • Limit parameter changes to authorized users.
  • Record significant actions and changes where required.
  • Apply password and session policies according to plant standards.
  • Protect engineering and runtime communications.
  • Secure remote access and maintenance connections.
  • Remove obsolete accounts and permissions.
  • Back up approved HMI projects and configuration securely.

HMI authorization is only one layer of control. The PLC and other authoritative systems must validate critical commands and parameter values independently of the screen's permissions.

14.2 Audit trail

For controlled changes, an audit record may include:

  • User identity.
  • Timestamp.
  • Parameter or setting changed.
  • Previous and new values.
  • Reason or work reference, where required.
  • Acceptance or rejection outcome.

An audit trail should be protected against unauthorized alteration according to the applicable requirements. Merely displaying the current value does not provide historical accountability.

15. HMI-PLC integration across common platforms

The basic engineering principles are similar across vendors, but project structures, communication drivers, tag models, and diagnostic tools differ.

Platform Common HMI ecosystem Integration points to verify
Siemens S7-1200/S7-1500 WinCC in supported engineering environments PLC connection, optimized data access compatibility, tag mapping, access protection, and runtime version
Rockwell ControlLogix/CompactLogix FactoryTalk View and supported HMI clients Controller path, tag scope, communication services, controller tag names, and access permissions
Mitsubishi PLC families GOT and GT Works/GT Designer environments PLC driver, device addresses, communication settings, and supported CPU/HMI combination
Modbus-compatible PLCs HMI with a supported Modbus driver Register map, address offsets, function codes, data type, byte order, and scaling
OPC UA-based systems HMI or supervisory client with OPC UA support Endpoint, certificates, security policy, namespace, permissions, and data quality

15.1 Siemens integration considerations

For an S7-1200 or S7-1500 with WinCC:

  • Verify that the selected HMI connection matches the CPU and runtime configuration.
  • Confirm whether the PLC data is exposed through symbolic tags or absolute addresses.
  • Check data-block access settings and compatibility with the selected HMI connection.
  • Verify array, string, structured-data, and optimized-access behavior.
  • Use meaningful symbolic names and consistent data organization.
  • Confirm CPU protection settings and permitted communication access.

Do not assume that every data-block address or access method works identically across CPU generations and software versions.

15.2 Rockwell integration considerations

For a Logix controller with a supported FactoryTalk View configuration:

  • Verify the communication path to the correct controller.
  • Confirm the tag scope and exact controller/program tag names.
  • Check controller data types and array indexing.
  • Verify the required communication services and permissions.
  • Confirm that the HMI uses the correct tag references after program changes.
  • Check the effect of controller replacement, project download, or firmware changes.

A tag that exists in the PLC project may still fail to resolve if the HMI path, scope, permissions, or configuration is incorrect.

15.3 Modbus integration considerations

For Modbus TCP or RTU, confirm:

  • Register and coil addresses.
  • Whether documentation uses zero-based or one-based notation.
  • Function code and read/write capability.
  • Register data type and signedness.
  • Byte order and word order for multi-register values.
  • Scaling and engineering units.
  • Exception responses and timeout behavior.

Modbus register maps are especially prone to address-offset mistakes. Verify a known value against the device display or another trusted reference before mapping the full interface.

16. Performance and communication loading

An HMI can generate significant communication traffic when many screens poll many tags at high frequency. Excessive polling can increase network load, PLC communication workload, and screen-update delays.

16.1 Update-rate planning

Choose update rates based on the operational purpose of the data.

  • Fast-changing status needed for immediate operator awareness may require faster updates.
  • Slowly changing temperatures or tank levels generally do not require the same rate as a motion-status display.
  • Historical trends may use a separate sampling strategy.
  • Infrequently changed configuration values may be read only when needed.
  • Alarm events should use a reliable mechanism appropriate to the platform rather than depending solely on slow screen polling.

Exact rates depend on the HMI, controller, network, tag count, communication driver, and application requirements.

16.2 Practical optimization

  • Remove unused HMI tags and obsolete screens.
  • Avoid repeated polling of the same data when the platform supports efficient shared subscriptions.
  • Group related values logically where appropriate.
  • Avoid unnecessarily fast updates for large arrays or complex structures.
  • Check communication diagnostics and update latency.
  • Test worst-case screen navigation and alarm activity.
  • Separate high-priority operator information from low-priority reporting data where the architecture supports it.

Do not optimize by slowing every update indiscriminately. The target is reliable responsiveness within the actual operational requirements.

17. Backup, version control, and change management

The HMI project is part of the machine-control system. A project backup should be restorable and compatible with the required runtime and PLC interface.

Maintain:

  • Source project files.
  • Runtime and engineering-software versions.
  • HMI model and firmware.
  • PLC connection configuration.
  • Tag mapping and data types.
  • Screen and alarm configuration.
  • User-role and security configuration, handled securely.
  • Recipe and parameter-management definitions where applicable.
  • Change history and approved release records.
  • Recovery instructions and verified backups.

17.1 Change impact assessment

Before changing an HMI tag or screen, consider whether the change affects:

  • PLC symbol names or addresses.
  • Data-block structure or access settings.
  • Command-handshake logic.
  • Setpoint validation.
  • Alarm conditions and acknowledgement.
  • User permissions.
  • Runtime compatibility.
  • Network loading.
  • Operator procedures and training.

Test the revised HMI against the intended PLC version and interface. A screen that compiles successfully can still issue the wrong command or display the wrong engineering value.

18. HMI-PLC commissioning checklist

18.1 Configuration verification

  • Confirm the PLC and HMI model, firmware, software version, and compatibility.
  • Verify the communication path and connection parameters.
  • Confirm all critical tags, data types, addresses, and scopes.
  • Verify scaling, units, ranges, and display precision.
  • Confirm the command-handshake design and feedback mapping.
  • Verify alarm conditions, priorities, latching, and acknowledgement behavior.
  • Confirm mode-selection and parameter-entry permissions.
  • Check screen navigation and diagnostic information.
  • Verify backup, restoration, and approved project version.

18.2 Functional testing

  • Confirm actual machine status matches the HMI display.
  • Test Start request acceptance and rejection.
  • Test normal Stop behavior.
  • Test Reset separately from Start.
  • Verify alarm occurrence, acknowledgement, clearing, and history.
  • Test valid and invalid setpoint entry.
  • Confirm displayed values against known PLC values or approved references.
  • Test communication-loss indication and recovery.
  • Verify stale data cannot be mistaken for current data.
  • Test user permissions for restricted functions.
  • Verify that HMI changes do not bypass PLC interlocks.
  • Confirm all required safety functions remain independent and validated.

18.3 Operator acceptance

The operator should be able to determine:

  • What state the machine is actually in.
  • Whether a command has been requested, accepted, or rejected.
  • Why the machine cannot start when applicable.
  • Which alarm or fault needs attention.
  • Which values are active and which are only requested.
  • Whether the displayed data is current.
  • Which actions are available in the current mode and under the user's permissions.

20. Systematic troubleshooting procedure

When an HMI function does not behave correctly, investigate the entire command or data path rather than changing random screen properties.

  1. Confirm the symptom. Record the exact screen, tag, command, operating mode, and time of occurrence.
  2. Check communication. Verify the correct PLC connection and whether current data is being received.
  3. Inspect the HMI tag. Confirm its source, type, address, scope, scaling, and access configuration.
  4. Check the PLC value. Compare the HMI tag with the corresponding variable in the PLC engineering environment.
  5. Trace the command path. For a button, verify the request is generated, received, evaluated, and acknowledged.
  6. Inspect PLC logic. Identify active permissives, interlocks, sequence conditions, fault latches, and rejection reasons.
  7. Verify physical feedback. Confirm the actual device state agrees with the PLC feedback.
  8. Review timing and data freshness. Check polling, communication delays, stale values, and timeout behavior.
  9. Test the correction. Repeat the original scenario and verify normal operation and fault handling.
  10. Document the cause. Record the root cause, corrective action, affected functions, and validation results.

Do not force PLC bits or bypass interlocks simply to prove that an HMI button works. Use an approved test method and preserve the original fault evidence.

21. Practical example: HMI-controlled conveyor

Consider an automated conveyor controlled by a PLC, with a VFD driving the motor and an HMI providing Start, Stop, Reset, mode selection, and speed entry.

Tag Direction Purpose
Conveyor_Start_Request HMI to PLC Requests conveyor startup
Conveyor_Stop_Request HMI to PLC Requests the defined normal stop
Conveyor_Reset_Request HMI to PLC Requests reset of eligible latched faults
Conveyor_Mode_Request HMI to PLC Requests a permitted operating mode
Conveyor_Speed_Request HMI to PLC Requests a speed setpoint
Conveyor_Start_Accepted PLC to HMI Confirms acceptance of the start request

21.3 Test scenarios

  • Start when all required conditions are satisfied.
  • Start while the drive is faulted.
  • Start in an incompatible operating mode.
  • Start while a required permissive is absent.
  • Press Start repeatedly before the first request is acknowledged.
  • Disconnect HMI communication during a command.

  • Restore communication and confirm that stale commands are not unexpectedly executed.

22. Interview questions and answers

1. What is HMI-PLC integration?

It is the configuration and engineering of communication, tags, commands, feedback, alarms, parameters, and operator screens between an HMI and a PLC.

2. What is the difference between an HMI command and PLC feedback?

A command requests an action. Feedback reports the state or result. The HMI should display the actual state rather than assume the command succeeded.

3. Why should Start and Running be separate tags?

Start represents an operator request, while Running represents an actual machine condition. Keeping them separate makes rejection, startup delay, and faults easier to diagnose.

4. What is a request/acknowledgement handshake?

It is an interface pattern in which one system submits a request and the receiving system returns a defined response. It helps prevent repeated execution and ambiguous command handling.

5. Why should the PLC validate HMI setpoints?

The HMI can improve usability, but the PLC or authoritative control layer must enforce valid ranges and operating conditions. HMI-side restrictions alone can be bypassed or misconfigured.

6. What is the difference between alarm acknowledgement and fault reset?

Acknowledgement confirms that the alarm has been recognized. Reset requests clearing an eligible latched fault. Neither action necessarily means the machine is ready to restart.

7. Why is communication-health monitoring important?

Without it, the HMI may continue showing an old value as if it were current. A separate communication or data-quality indication helps operators distinguish a real process state from unavailable data.

8. How do you troubleshoot a button that does not work?

Check communication, the HMI tag, request generation, PLC tag mapping, permissives, sequence logic, rejection status, and physical feedback.

9. What is the difference between Manual and Auto modes?

Auto generally runs the approved sequence, while Manual permits individually commanded functions under defined conditions. The PLC must validate mode transitions and permitted actions.

10. Why should the HMI avoid writing directly to sequence-state variables?

Directly changing internal states can bypass required transitions and leave the machine inconsistent. The HMI should request actions through a defined interface, allowing the PLC to control the transition.

11. How should recipes be handled?

Recipes should have clear identity and revision, authorized selection, parameter validation, application confirmation, and defined behavior when loading fails or production is active.

12. How do you prevent repeated execution from one button press?

Use an appropriate request-clearing mechanism, edge detection, or request/acknowledgement handshake. For more complex interfaces, request identifiers can distinguish new commands from retries.

13. Why can a numeric HMI display be incorrect even when communication is healthy?

The tag may have the wrong address, data type, scaling, unit, signedness, or register mapping. A working connection does not prove the data interpretation is correct.

14. What is the difference between a normal Stop button and an emergency stop?

A normal Stop requests the machine's defined operational stopping behavior. An emergency stop is a safety function implemented and validated according to the risk assessment and safety architecture.

15. What should be tested after an HMI project change?

Test communication, critical tags, commands, alarms, setpoints, permissions, screen navigation, stale-data behavior, fault handling, and compatibility with the deployed PLC and runtime versions.

23. Final engineering checklist

  • HMI and PLC responsibilities are clearly separated.
  • Communication settings and device compatibility are verified.
  • Tags use correct addresses, scopes, data types, units, and scaling.
  • Commands are distinct from actual-state feedback.
  • Request handling prevents unintended repeated execution.
  • Start, Stop, Reset, and Acknowledge have separate, defined meanings.
  • The PLC validates operating modes, setpoints, and command permissives.
  • Alarms distinguish active conditions from acknowledgement state.
  • Communication failure and stale data are clearly indicated.
  • Screen navigation and operator feedback support troubleshooting.
  • User permissions and audit requirements are enforced.
  • HMI actions do not bypass PLC interlocks or the validated safety architecture.
  • Commissioning, fault tests, project backups, and change records are complete.

Core principle: The HMI requests and explains. The PLC validates and controls. The feedback confirms what actually happened. Reliable HMI-PLC integration depends on keeping those three responsibilities distinct.
