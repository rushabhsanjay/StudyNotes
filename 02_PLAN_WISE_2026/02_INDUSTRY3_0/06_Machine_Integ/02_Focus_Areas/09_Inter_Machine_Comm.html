1. Purpose of inter-machine communication

Inter-machine communication is the exchange of commands, status, process data, diagnostics, and coordination signals between two or more machines or automation systems.

In manufacturing, machines rarely operate as completely independent units. A robot may load a CNC machine, a conveyor may transfer parts between stations, a leak tester may receive a workpiece from an assembly station, and a downstream machine may need to know whether the upstream process has completed successfully.

Inter-machine communication allows these systems to coordinate production without relying entirely on manual intervention.

The main objectives are:

  • Exchange machine-ready, busy, complete, fault, and availability information.
  • Coordinate material transfer between upstream and downstream machines.
  • Transfer recipe numbers, product identifiers, process parameters, and results.
  • Prevent conflicting actions and incorrect sequence execution.
  • Detect communication loss, stale data, and incomplete transactions.
  • Support diagnostics, traceability, production monitoring, and recovery.
  • Keep communication architecture maintainable as machines are added or modified.

Core principle: Communication delivers information. The receiving machine must still validate that information, check its own conditions, and decide whether the requested action is permitted.

2. Where inter-machine communication is used

Typical manufacturing examples include:

  • PLC-to-PLC communication between production stations.
  • Robot-to-machine communication for loading and unloading.
  • CNC-to-line-controller communication.
  • PLC-to-test-equipment communication.
  • Conveyor-to-station coordination.
  • Machine-to-MES communication for production orders and traceability.
  • Machine-to-SCADA communication for monitoring and diagnostics.
  • Communication between line controllers and cell controllers.

A typical automotive manufacturing example is a robotic loading station supplying components to a CNC machine. The robot must know whether the CNC is ready to receive a component, and the CNC must know whether the robot has completed the transfer.

Without a defined interface, both systems might assume the other is ready. Industrial automation has many ways to turn a simple assumption into an expensive collision.

3. Basic communication architecture

                 Line Controller / MES
                           ↕
                    Industrial Network
                           ↕
        +------------------+------------------+
        ↕                  ↕                  ↕
    Machine A           Machine B          Machine C
      PLC                 PLC                PLC
        ↕                  ↕                  ↕
   Sensors/Drives       Robot/CNC         Conveyor/Test

The architecture may use direct PLC-to-PLC connections, industrial Ethernet, fieldbus networks, gateways, or a supervisory layer. The appropriate choice depends on required response time, data volume, reliability, equipment compatibility, and maintainability.

Not every machine needs to communicate directly with every other machine. A line controller or cell controller can coordinate shared production information where that architecture is appropriate.

4. Types of information exchanged

Information category Examples Typical purpose
Readiness Machine_Ready, Robot_Ready Indicates whether a machine can accept a task
Commands Load_Request, Unload_Request Requests a defined operation
Acknowledgements Request_Accepted, Command_Ack Confirms that a request was received or accepted
Execution status Busy, In_Cycle, Transfer_Active Indicates current operating state
Completion Cycle_Complete, Part_Transferred Indicates completion of a defined operation
Fault status Machine_Fault, Robot_Fault Reports a fault or unavailable condition
Product data Part_ID, Recipe_ID, Variant_Code Identifies the product or process
Process results Torque_Result, Leak_Result, Dimension_Result Shares inspection or production outcomes
Resource availability Buffer_Free, Fixture_Empty Coordinates shared resources
Diagnostics Comm_Healthy, Last_Error_Code Helps identify interface failures
Timing information Sequence number, timestamp, transaction age Helps detect stale or mismatched data

A signal's name alone does not define its meaning. Every interface needs an agreed description of the signal's owner, data type, update method, validity, and behavior during faults.

5. Communication methods

5.1 Hardwired digital I/O

Separate electrical signals connect outputs from one machine to inputs on another.

Examples include:

  • Machine A ready.
  • Machine A fault.
  • Machine B request.
  • Machine B acknowledge.
  • Transfer complete.

Advantages:

  • Simple and easy to troubleshoot.
  • Clear electrical signal states.
  • Useful for a small number of deterministic interface signals.
  • Can operate without complex network configuration.

Limitations:

  • Requires physical wiring for every signal.
  • Signal count grows as the interface becomes more complex.
  • Large data sets and recipes are inconvenient to exchange.
  • Electrical isolation, common references, voltage compatibility, and input/output loading must be considered.

Hardwired I/O is still useful for simple interfaces, but it becomes cumbersome when many machines exchange numerous states and parameters.

5.2 Industrial Ethernet and fieldbus

Industrial networks exchange multiple data items through a configured communication relationship.

Common technologies include:

  • PROFINET.
  • EtherNet/IP.
  • EtherCAT.
  • Modbus TCP.
  • PROFIBUS.
  • CC-Link and CC-Link IE.
  • Other manufacturer-specific or standards-based industrial protocols.

Selection depends on controller support, topology, update requirements, diagnostics, interoperability, and project standards.

A network being physically connected does not guarantee that the application data is correct. Both endpoints must agree on connection parameters, data layout, update behavior, and interpretation.

5.3 Explicit or message-based communication

Some systems exchange data through requests and responses rather than continuously updated cyclic I/O.

Examples include:

  • Reading a parameter from another controller.
  • Writing a recipe number.
  • Retrieving a test result.
  • Requesting machine diagnostics.
  • Transferring production-order information.

Message-based communication is useful for non-cyclic data, configuration, and larger data structures. It may have different timing and retry behavior from cyclic process data, so it should not be treated as interchangeable with fast control I/O.

5.4 Supervisory and information-level communication

Higher-level systems may exchange information using technologies such as OPC UA, MQTT, database interfaces, or APIs.

Typical uses include:

  • Production reporting.
  • Traceability.
  • Process-result collection.
  • Machine-state monitoring.
  • Recipe distribution.
  • Energy and performance dashboards.

These technologies are not automatically suitable for time-critical machine control or safety functions. Use them according to their supported timing, reliability, and security characteristics.

6. Cyclic data versus message-based data

Feature Cyclic data exchange Message-based exchange
Update behavior Repeated at configured intervals Triggered by a request, event, or transaction
Typical content Machine status and control words Recipes, diagnostics, records, parameters
Timing Usually more predictable when properly configured Depends on request handling, processing, and network behavior
Data volume Often a defined process-data layout May support larger or variable data structures
Failure handling Monitor connection health and data validity Handle timeouts, negative responses, retries, and duplicates
Common use Ready, busy, fault, transfer states Recipe read, result upload, parameter exchange

Cyclic communication does not automatically mean real-time behavior is guaranteed. The controller, network, configuration, and application must all support the required timing.

7. Define the interface contract

An interface contract is the agreement between the sending and receiving systems about the information being exchanged.

It should define:

  • Signal or tag name.
  • Description and operational meaning.
  • Data type and size.
  • Producer and consumer.
  • Direction of data flow.
  • Normal and fault-state behavior.
  • Update method and expected timing.
  • Data-validity rules.
  • Reset and recovery behavior.
  • Ownership of each writable value.
  • Version and change-control requirements.

Example interface table:

Signal Producer Consumer Meaning
A_Ready Machine A Machine B Machine A can accept the defined operation
B_Request Machine B Machine A Machine B requests the operation
A_Accepted Machine A Machine B Machine A accepted the request
A_Busy Machine A Machine B Machine A is executing the operation
A_Complete Machine A Machine B The defined operation is complete
A_Fault Machine A Machine B Machine A reports a fault condition
Comm_Healthy Communication layer or controller logic Application Communication is currently considered healthy

The exact meaning of each signal must be documented. For example, A_Ready may mean ready for a new part, ready to unload, or ready to start a process. Those meanings are not interchangeable.

8. Signal ownership and direction

Every interface value should have a clearly defined owner.

For example:

Machine A PLC
    A_Ready ---------> Machine B PLC
    A_Complete ------> Machine B PLC
    A_Fault ---------> Machine B PLC

Machine B PLC
    B_Request -------> Machine A PLC
    B_Reset_Request -> Machine A PLC

In a networked system, the data may be exchanged in a configured data block rather than through individual wires. The ownership principle remains the same.

Avoid multiple controllers writing the same command or status variable without a deliberate arbitration design. Conflicting writers can cause unstable behavior and make troubleshooting difficult.

A useful rule is:

  • The producer owns the meaning and generation of its status.
  • The consumer owns its decision to act on that status.
  • The interface specification defines how both sides handle invalid or unavailable data.

9. Communication health and data validity

A communication link can fail in several ways:

  • Physical cable or switch failure.
  • Incorrect IP address or subnet.
  • Incorrect connection configuration.
  • Controller stop or power loss.
  • Communication task failure.
  • Network congestion or excessive load.
  • Data-layout mismatch.
  • Gateway failure.
  • Stale or frozen data.
  • Incorrect interpretation of a received value.

A robust interface distinguishes between a received value and a valid, current value.

For example, if the last received Machine_Ready value was TRUE before a network failure, the receiving machine must not assume that the machine remains ready indefinitely.

Typical communication diagnostics

  • Connection established.
  • Connection lost.
  • Last successful update time.
  • Data-valid flag.
  • Communication timeout.
  • Sequence number or transaction identifier.
  • Last error code.
  • Reconnection status.

The timeout must be selected based on the communication method, update rate, machine response requirements, and acceptable risk. A single arbitrary timeout should not be copied across all interfaces.

10. Stale data and heartbeat monitoring

A heartbeat is a changing value or periodically updated signal used to determine whether the expected communication or application task is still active.

One implementation uses a counter that increments at the producer and is monitored at the consumer.

Machine A:
    Heartbeat_Count = Heartbeat_Count + 1

Machine B:
    Monitor changes in Heartbeat_Count
    Measure elapsed time since last change
    If the defined timeout expires:
        Mark communication or application health invalid
        Apply the specified fault response

The counter must be transferred and observed reliably. Its rollover behavior, update rate, and timeout logic must be defined.

A heartbeat can show that a producer or communication path is active, but it does not prove that every data value is correct. Combine it with connection diagnostics, data-validity checks, and appropriate application monitoring.

11. Data mapping and type compatibility

The two systems must agree on the exact data representation.

Important properties include:

  • Data type.
  • Signed versus unsigned values.
  • Bit order and byte order where applicable.
  • Structure layout.
  • Array length.
  • String encoding and maximum length.
  • Scaling and engineering units.
  • Valid ranges and enumerated values.
  • Version of the interface definition.

Example:

Parameter Machine A Machine B Risk if mismatched
Speed reference REAL, rpm INT, raw count Incorrect speed interpretation
Part number String, 20 characters String, 12 characters Truncation or mismatch
Cycle state Enumerated integer Boolean Loss of state meaning
Temperature Degrees Celsius Degrees Fahrenheit Incorrect process decision
Result value Signed integer Unsigned integer Incorrect interpretation of negative values

Do not assume that two variables with the same name have the same representation.

Where scaling is required, document the conversion. For a linear conversion:

\[ Y = Y\_{\min} + \frac{X-X\_{\min}}{X\_{\max}-X\_{\min}}(Y\_{\max}-Y\_{\min}) \]

Here, \(X\) is the incoming value, and \(Y\) is the converted value. Validate the input range and handle invalid values before using the result in machine logic.

12. Coordinating upstream and downstream machines

Consider an upstream station supplying parts to a downstream station.

The upstream machine must know when the downstream machine can accept a part. The downstream machine must know whether a valid part is available and whether its own conditions permit processing.

Typical coordination signals include:

  • Upstream available.
  • Downstream ready.
  • Transfer request.
  • Transfer accepted.
  • Transfer active.
  • Part transferred.
  • Part received.
  • Buffer full.
  • Buffer empty.
  • Transfer fault.

A conceptual sequence is:

Upstream has a completed part
             ↓
Downstream reports ready
             ↓
Transfer request is issued
             ↓
Request is accepted
             ↓
Transfer mechanism operates
             ↓
Part arrival is verified
             ↓
Transfer is declared complete
             ↓
Both machines return to the defined next state

The actual sequence depends on the mechanism and interface design. A transfer-complete signal should represent a verified event, not merely the expiration of an arbitrary timer.

13. Fault handling and recovery

The receiving machine should have a defined response when communication becomes invalid.

Possible responses include:

  • Preventing a new cycle from starting.
  • Completing an operation that can safely finish.
  • Stopping or holding a transfer at a defined point.
  • Marking the current part or transaction as uncertain.
  • Raising an alarm with a clear diagnostic.
  • Requiring operator inspection or controlled recovery.
  • Re-establishing communication before resuming coordination.

There is no universal rule that every communication failure must immediately stop every machine. The response depends on the hazards, process state, stored energy, material position, and documented machine behavior.

Safety-critical distinction: Standard communication fault handling must not replace a required safety-rated communication or safety function. If loss of communication can create a hazard, the required safe response must be implemented through the appropriate validated architecture.

14. Troubleshooting inter-machine communication

Symptom Possible cause Investigation
Connection cannot be established Incorrect addressing, configuration, cable, switch, or controller state Check physical link, addressing, diagnostics, and connection settings
Connection is healthy but data is incorrect Mapping, type, scaling, or offset mismatch Compare both endpoints' data definitions
Machine B never sees A_Ready Wrong mapping, producer logic condition false, or stale data Inspect the source tag and the received tag separately
Request is visible but never accepted Receiver interlocks not satisfied or request protocol incomplete Check the receiver state, permissives, and acknowledgement rules
Signals work intermittently Electrical noise, network faults, timing issues, or unstable logic Examine diagnostics, event logs, wiring, and timing
Machine continues using an old status after a fault Missing validity monitoring or stale-data handling Check connection-loss behavior and data-validity logic
Recipe is loaded incorrectly Wrong identifier, type conversion, stale transaction, or version mismatch Verify transaction ID, recipe version, range, and acknowledgement
Duplicate part processing occurs Repeated request or completion event interpreted as a new transaction Review edge detection, transaction identity, and duplicate handling
Communication returns but machines remain blocked Recovery states are not synchronized Inspect reset, reconciliation, and re-entry logic
One controller reports complete while the other remains busy Different definitions of completion or incorrect sequence timing Compare interface contract and state transitions

Practical diagnostic order

  1. Confirm the physical and network connection.
  2. Check controller and communication diagnostics.
  3. Verify the producer's source tag.
  4. Verify the received value at the consumer.
  5. Check data types, mapping, scaling, and update behavior.
  6. Inspect machine permissives and state-machine logic.
  7. Check timeout and retry behavior.
  8. Reproduce the fault under controlled conditions.
  9. Correct the root cause and validate the complete transaction.
  10. Document the change and test result.

15. Commissioning checklist

Network and configuration

  • Confirm compatible communication protocols and hardware.
  • Verify addressing, subnet, routing, and network topology as applicable.
  • Confirm connection configuration and data layout.
  • Check controller versions and required configuration files.
  • Verify network diagnostics and expected update behavior.

Interface definition

  • Document every exchanged signal and parameter.
  • Define producer, consumer, direction, and ownership.
  • Verify data types, units, scaling, and ranges.
  • Define data-validity and stale-data behavior.
  • Establish timeout and retry rules.
  • Define the response to communication loss.

Functional testing

  • Test normal requests and acknowledgements.
  • Verify ready, busy, complete, and fault transitions.
  • Test invalid and out-of-range data.
  • Test connection loss and recovery.
  • Verify that duplicate or stale transactions are handled correctly.
  • Check machine restart and recovery after interruption.
  • Verify that a communication failure cannot bypass safety functions.
  • Record test results and correct identified defects.

16. Documentation and maintenance

Maintain the following records for each interface:

  • Network architecture and topology.
  • Controller and device identification.
  • IP addresses and communication settings where applicable.
  • Signal list and interface contract.
  • Data-block or message structure.
  • Data types, units, scaling, and valid ranges.
  • Timing, timeout, retry, and recovery rules.
  • Alarm and diagnostic mapping.
  • Version and change history.
  • Commissioning and fault-injection test records.
  • Approved backup and restoration procedure.

For plant maintenance, record which machines depend on each interface. This helps assess the impact of replacing a PLC, changing a network switch, updating a controller program, or modifying an interface data structure.

17. Interview questions and answers

1. What is inter-machine communication?

It is the exchange of commands, status, process data, and diagnostics between separate machines or automation systems to coordinate production.

2. What is the difference between hardwired I/O and network communication?

Hardwired I/O uses dedicated electrical signals. Network communication exchanges multiple data items over a configured communication connection and can support more complex interfaces.

3. What is an interface contract?

It is the documented agreement defining signal meanings, ownership, direction, data types, validity, timing, and fault behavior between communicating systems.

4. Why is communication health different from machine readiness?

Communication health indicates whether information can be exchanged and trusted. Machine readiness indicates whether the machine's own defined conditions permit a particular operation.

5. What is a heartbeat?

It is a periodically changing signal or value used to monitor whether a communication partner or application task is active. It does not, by itself, prove that all process data is correct.

6. Why must stale data be detected?

A value received before a communication failure may no longer represent the machine's current condition. Acting on it can cause incorrect sequencing or material-handling errors.

7. What is the difference between cyclic and message-based communication?

Cyclic communication repeatedly exchanges configured process data. Message-based communication exchanges information through individual requests, responses, or events.

8. Why can a request be received but not accepted?

The receiving machine may be in the wrong state, have unmet permissives, detect invalid data, or require a different request sequence.

9. How should a communication timeout be selected?

It should reflect the update method, expected timing variation, process requirements, and fault-response needs. It must be validated for the application rather than chosen arbitrarily.

10. How do you troubleshoot a healthy connection with incorrect data?

Compare the producer's source value with the consumer's received value, then check mapping, data types, scaling, structure layout, update behavior, and application logic.

11. Why is a transaction identifier useful?

It helps the receiving system associate acknowledgements and results with the correct request, detect duplicates, and avoid mixing data from different production cycles.

12. Can standard Ethernet communication be used for a safety function?

Only when the complete implementation uses an appropriate safety-rated architecture and meets the applicable requirements. Ordinary Ethernet communication alone does not establish safety integrity.

18. Key engineering principles

  • Define the communication interface before programming both endpoints.
  • Assign one clear owner to each signal and writable data item.
  • Distinguish machine readiness from communication health.
  • Validate data types, units, scaling, and data-layout compatibility.
  • Detect stale data and communication loss.
  • Use explicit request, acceptance, execution, and completion states.
  • Design retry and recovery logic to avoid duplicate operations.
  • Coordinate machines according to the actual process and risk assessment.
  • Keep ordinary process communication separate from validated safety functions.
  • Maintain interface documentation and test it after relevant modifications.

Inter-machine communication is reliable when both endpoints agree on what the data means, when it is valid, how transactions progress, and what happens when the expected exchange fails.
