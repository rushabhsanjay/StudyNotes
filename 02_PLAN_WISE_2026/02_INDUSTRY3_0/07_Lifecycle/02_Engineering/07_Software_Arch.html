1. What is software architecture?

Software architecture is the high-level design of how automation software is organized, how its components interact, how responsibilities are separated, and how the complete system achieves the required machine behavior.

In industrial automation, software architecture defines the organization of PLC programs, function blocks, device-control logic, sequence management, HMI communication, alarms, diagnostics, data handling, motion control, and external equipment interfaces.

It establishes the structure before detailed programming begins.

For example, a PLC application that controls conveyors, pneumatic fixtures, a robot, and an inspection station should not be designed as one enormous program containing every command, timer, alarm, and interlock. The software should be organized into understandable components with defined responsibilities and interfaces.

Good software architecture makes the system easier to develop, test, commission, troubleshoot, retrofit, and maintain.

2. Objectives of software architecture

Software architecture should:

  • Translate functional requirements into an implementable software structure.
  • Separate machine sequences from individual device-control functions.
  • Define reusable program components.
  • Establish interfaces between PLCs, HMIs, drives, robots, CNCs, and other devices.
  • Standardize operating modes, state handling, alarms, and diagnostics.
  • Define how data is exchanged and validated.
  • Support deterministic control and appropriate execution timing.
  • Prevent unintended interactions between program sections.
  • Improve software testing and commissioning.
  • Support future modifications without rewriting unrelated functions.
  • Establish consistent naming, documentation, and version-control practices.

Architecture is not just a programming preference. It determines how safely and efficiently the system can be changed over its service life.

The software architecture must be consistent with the selected hardware. A design that assumes unlimited controller memory, unrestricted communication, or unsupported multitasking is not a valid architecture.

4. Architecture hierarchy

A typical machine-control application can be organized into several logical layers.

Industrial Automation Software
        ↓
Application and Operating Modes
        ↓
Sequence and Process Coordination
        ↓
Equipment and Device Control
        ↓
I/O and Communication Abstraction
        ↓
PLC Hardware and Field Devices

Supporting functions across the application:
Alarms | Diagnostics | Data Handling | Configuration

These are logical responsibilities, not necessarily separate processors or physical devices. Several layers may execute within one PLC project.

4.1 Application and operating-mode layer

Manages machine-level behavior such as:

  • Manual and automatic modes.
  • Production-cycle start and stop.
  • Machine readiness.
  • Operating-state management.
  • Production completion.
  • High-level fault handling.

4.2 Sequence and process-coordination layer

Coordinates the order of operations.

Examples include:

  • Conveyor transfer sequence.
  • Robot loading sequence.
  • CNC cycle coordination.
  • Inspection sequence.
  • Part routing.
  • Inter-machine handshakes.

4.3 Equipment-control layer

Controls individual devices or equipment modules.

Examples include:

  • Motor control.
  • Cylinder control.
  • Valve control.
  • Drive control.
  • Robot interface control.
  • Sensor evaluation.
  • Positioning and motion commands.

4.4 I/O and communication abstraction layer

Provides a consistent way for the application to access physical signals and communication data.

It may include:

  • Input normalization.
  • Output mapping.
  • Device status mapping.
  • Communication data conversion.
  • Quality and validity flags.
  • Device-interface diagnostics.

This separation reduces dependence on raw hardware addresses throughout the application.

5. Program organization: tasks, programs, routines, and function blocks

PLC platforms use different terminology, but many share similar concepts.

Element General purpose
Task Defines when and how a group of code executes
Program Organizes a logical section of application code
Routine or function Implements a particular operation or algorithm
Function block Encapsulates behavior, data, and state
Data block or structure Stores related configuration and runtime data
Global data Holds information shared between selected components
Local data Holds information private to a program component

Exact capabilities vary between platforms. For example, Siemens uses organization blocks, functions, function blocks, and data blocks. Rockwell Automation Logix platforms organize execution through tasks, programs, routines, and controller- or program-scoped tags.

The architecture should use the concepts supported by the target platform rather than forcing identical implementation details across different PLC families.

6. Choosing an appropriate program structure

Three common approaches are unstructured logic, function-oriented logic, and modular architecture.

Approach Characteristics Suitability
Unstructured Large routines with mixed responsibilities Small or legacy applications, with limitations
Function-oriented Logic grouped by purpose Small and medium applications
Modular Independent equipment and process components with defined interfaces Medium and large applications, especially maintainable systems

A modular architecture is often preferable for complex machines because device control, sequences, diagnostics, and interfaces can be understood and tested separately.

However, modularity should not become unnecessary fragmentation. Creating dozens of tiny blocks with unclear responsibilities merely relocates complexity.

7. Modular programming

A software module is a defined component responsible for a particular function.

Examples:

  • FB_Motor
  • FB_Cylinder
  • FB_VFD
  • FB_RobotInterface
  • FB_CNCInterface
  • FB_AlarmManager
  • FB_SequenceManager

The names are illustrative and should follow the project's naming standard.

A well-designed module has:

  • One clear responsibility.
  • Defined inputs and outputs.
  • Internal state where required.
  • Documented operating assumptions.
  • Predictable behavior.
  • Defined fault responses.
  • Minimal unnecessary dependencies on other modules.

For example, a motor-control module may process start requests, readiness feedback, running status, and fault information. The production sequence requests the motor to run without needing to reproduce the motor's entire control logic.

8. Device abstraction

Device abstraction separates the application from the electrical details and manufacturer-specific interface of a device.

Consider a motor controlled by a VFD.

Without abstraction, multiple sequences might directly manipulate raw drive bits, communication words, and status registers.

With abstraction, the sequence interacts with a defined interface such as:

Motor01.StartRequest
Motor01.StopRequest
Motor01.ResetRequest
Motor01.Ready
Motor01.Running
Motor01.Faulted
Motor01.ActualSpeed

A motor-control module translates these logical requests into the appropriate hardwired or network-based commands.

Benefits include:

  • Easier troubleshooting.
  • Reduced duplicate logic.
  • Easier replacement of a device or interface.
  • Consistent fault handling.
  • Simpler sequence programming.
  • Easier simulation and testing.

Abstraction must not hide important device-specific behavior. For example, a servo axis requires different readiness, positioning, and feedback handling from a basic conveyor motor.

9. Separation of sequence logic and device logic

This is one of the most important architecture principles.

Device logic determines how an individual device behaves.

Sequence logic determines when the process requests that device to perform an operation.

Example:

  • The cylinder module manages extend and retract requests, position feedback, and motion timeouts.
  • The sequence module decides when the cylinder should extend during a production cycle.

A conceptual structure is:

Sequence Manager
      ↓
Cylinder Extend Request
      ↓
Cylinder Control Module
      ↓
Output Mapping
      ↓
Solenoid Valve

Position Sensors
      ↓
Input Mapping
      ↓
Cylinder Control Module
      ↓
Extended / Retracted Status
      ↓
Sequence Manager

This structure prevents every sequence from independently implementing the same cylinder timeout, fault handling, and feedback interpretation.

It also makes device-level testing possible without running the entire production sequence.

10. Operating-mode architecture

A machine commonly has multiple operating modes.

Examples include:

  • Automatic.
  • Manual.
  • Setup.
  • Maintenance.
  • Recovery.
  • Cleaning or service mode, where applicable.

The software architecture must define which functions are permitted in each mode and how mode changes affect active operations.

Function Automatic mode Manual or setup mode
Automatic sequence progression Permitted under defined conditions Normally inhibited
Individual device command Sequence-controlled Operator request subject to permissives
Device diagnostics Active Active
Alarm processing Active Active
Production counting Based on defined production events Depends on approved process rules
Safety functions Active as designed Remain active as designed
Recovery operations Defined automatic or assisted behavior Controlled recovery actions as permitted

Manual mode must not bypass required safety functions. Maintenance and setup actions require the applicable risk controls and operating procedures.

10.1 Mode transition rules

Define:

  • How a mode is selected.
  • Whether the machine must be stopped first.
  • What happens to active sequence states.
  • Whether device commands are retained or cleared.
  • Which operator permissions are required.
  • How the machine returns to automatic operation.
  • Whether a new start command is required after the transition.

Mode changes should be intentional, observable, and testable.

11. State and sequence management

The sequence manager implements the process behavior defined in the sequence description.

Typical machine states include:

  • Initializing.
  • Idle.
  • Ready.
  • Running.
  • Waiting.
  • Completing.
  • Stopped.
  • Faulted.
  • Recovery required.

A state should have a clear meaning. Avoid using one state bit to represent unrelated conditions such as ready, running, faulted, and awaiting operator confirmation.

The sequence manager should define:

  • Entry conditions.
  • Actions performed in each state.
  • Transition conditions.
  • Timeout handling.
  • Fault transitions.
  • Stop behavior.
  • Restart conditions.
  • State initialization after power-up.

Example of a conceptual state structure:

CASE MachineState OF

    IDLE:
        IF StartPermitted THEN
            MachineState := RUNNING
        END_IF

    RUNNING:
        IF CycleComplete THEN
            MachineState := COMPLETING
        ELSIF SequenceFault THEN
            MachineState := FAULTED
        END_IF

    COMPLETING:
        IF CompletionActionsDone THEN
            MachineState := IDLE
        END_IF

    FAULTED:
        IF FaultCleared AND RecoveryPermitted THEN
            MachineState := RECOVERY_REQUIRED
        END_IF

END_CASE

This is illustrative pseudocode. Production logic must explicitly define stop priority, state initialization, command management, recovery, and all required transitions.

12. Alarm and diagnostic architecture

Alarm processing should be designed as a consistent application service rather than implemented independently in every sequence.

The architecture may separate:

  • Fault detection.
  • Fault classification.
  • Alarm generation.
  • Alarm latching.
  • Acknowledgment.
  • Fault-clear conditions.
  • HMI presentation.
  • Event logging.
  • Diagnostic context.

A useful alarm record may include:

Field Purpose
Alarm ID Unique identifier
Source tag Device or subsystem reporting the condition
Description Clear operator-facing message
Trigger condition Condition that generates the alarm
Severity Priority based on the alarm philosophy
Timestamp Time the event occurred
Active status Whether the triggering condition remains present
Acknowledgment status Whether the operator acknowledged it
Recovery guidance Required checks or actions

Acknowledgment must not be confused with fault clearance. An operator can acknowledge an alarm while the underlying fault remains active.

Fault-reset and restart behavior must be defined by the functional requirements. Clearing an alarm must not automatically initiate unexpected machine movement.

13. Data and tag architecture

A consistent tag structure makes the application easier to understand and maintain.

Example device structure:

Cylinder01
    Command
        ExtendRequest
        RetractRequest
        ResetRequest
    Status
        Extended
        Retracted
        Moving
        Faulted
        Ready
    Diagnostics
        Timeout
        FeedbackConflict
        LastFaultCode

The exact implementation may use PLC structures, data blocks, user-defined types, or platform-specific tags.

A good data architecture distinguishes:

  • Commands.
  • Physical feedback.
  • Derived status.
  • Configuration parameters.
  • Runtime values.
  • Fault information.
  • Historical or production data.
  • Communication validity.

Do not allow multiple unrelated program sections to write the same command tag without a defined ownership rule. Conflicting writers create unpredictable behavior and make troubleshooting unnecessarily difficult.

14. Single ownership of commands

Every important output or command should have a clear owner.

For example, a conveyor run command may be requested by the automatic sequence, but the final command is determined by the conveyor-control module after evaluating the relevant permissives, operating mode, stop conditions, and fault state.

Conceptually:

Sequence Request
        ↓
Device Control Module
        ↓
Mode and Permissive Evaluation
        ↓
Final Device Command
        ↓
Output Mapping
        ↓
Physical Output

This architecture prevents separate sequence routines, HMI controls, and maintenance functions from directly competing to control the same output.

For devices with several command sources, define priorities and arbitration explicitly.

15. Execution tasks and scan-time considerations

PLC execution behavior affects the architecture.

Depending on the platform, code may execute in cyclic tasks, periodic tasks, event-triggered tasks, or other supported execution contexts.

Important considerations include:

  • Task period and priority.
  • Maximum execution time.
  • Watchdog limits.
  • I/O update timing.
  • Communication update timing.
  • Interrupt or event handling.
  • Shared-data consistency.
  • Execution dependencies between tasks.
  • Motion-control cycle requirements.

Not all code needs to run at the same rate. Fast motion-related logic may have different timing requirements from HMI updates or production reporting.

For a cyclic task, the approximate execution time can be considered as:

\[ T\_{\text{execution}} = \sum\_{i=1}^{n} T_i \]

Where \(T_i\) represents the execution time of each relevant component during the cycle.

Actual task timing also depends on platform scheduling, communications, interruptions, and other system activity. The architecture must remain within the controller's documented execution limits.

16. Determinism and timing

Determinism means the system's behavior and timing are sufficiently predictable for the intended control task.

Industrial control architecture must account for:

  • PLC task scheduling.
  • I/O image updates.
  • Network cycle time.
  • Remote device response.
  • Communication retries and timeouts.
  • HMI polling and asynchronous services.
  • Motion synchronization.
  • External controller execution.

A PLC scan time alone does not represent the total response time from a physical sensor change to a physical actuator response.

The complete timing path may include input filtering, input updates, task execution, output updates, network transmission, device processing, and actuator response.

Time-critical control should use the platform's appropriate task and motion facilities rather than depend on incidental execution order.

17. Communication abstraction and data validation

The software architecture should separate the communication mechanism from the application behavior wherever practical.

For example, a robot interface module may expose:

  • Communication healthy.
  • Robot ready.
  • Robot busy.
  • Robot fault.
  • Program number.
  • Start request.
  • Program complete.
  • Result data valid.

The module handles the underlying data mapping and communication-specific behavior.

The application should not treat received data as valid merely because a communication connection exists. It should evaluate the relevant status, freshness, range, and consistency conditions.

For cyclic network data, consider:

  • Connection status.
  • Data update rate.
  • Stale-data detection.
  • Device status.
  • Invalid or inconsistent values.
  • Startup initialization.
  • Recovery after reconnection.
  • Duplicate or repeated transactions.

A connected device can still provide invalid process data, and a healthy network does not prove that the device completed the requested operation.

18. HMI software architecture

The HMI should present machine status and provide authorized operator commands without duplicating the machine's control authority.

Typical HMI functions include:

  • Overview and station screens.
  • Manual controls.
  • Automatic-cycle status.
  • Alarm display and acknowledgment.
  • Diagnostic information.
  • Parameter management.
  • Recipe selection.
  • Production counts.
  • Maintenance information.
  • User authentication and access control.

The PLC or designated controller should enforce the relevant process permissives. Hiding a button on the HMI is not a substitute for validating the command in the controller.

HMI architecture should define:

  • Tag naming and mapping.
  • Screen navigation.
  • Alarm presentation.
  • User roles.
  • Command confirmation where needed.
  • Parameter limits and validation.
  • Communication-loss behavior.
  • Startup and reconnect behavior.

19. Recipe and parameter management

Recipe data and machine parameters should be handled separately from sequence-state variables.

Examples of recipe values include:

  • Target position.
  • Inspection limits.
  • Process speed.
  • Pressure setpoint.
  • Selected production program.
  • Timing parameters.

The architecture should define:

  • Which controller owns the authoritative value.
  • Permitted parameter ranges.
  • Who can change the value.
  • When a new value becomes active.
  • How values are validated.
  • How changes are recorded.
  • How recipes are selected and identified.
  • How invalid or incomplete data is handled.

A parameter change during an active sequence can affect machine behavior. The software should define whether the change is rejected, queued, or applied immediately.

20. Data logging and traceability

Where production data is required, software architecture should separate real-time control from non-critical reporting functions.

Potential data includes:

  • Part identity.
  • Cycle start and completion.
  • Inspection results.
  • Machine states.
  • Alarm events.
  • Process values.
  • Recipe identifiers.
  • Operator actions.
  • Device diagnostics.

Define:

  • The source of each value.
  • When it is captured.
  • How it is associated with a part or cycle.
  • The destination system.
  • Required data quality.
  • Buffering and retry behavior.
  • Handling of communication loss.
  • Duplicate-record prevention.
  • Retention and access requirements.

Database or reporting delays should not unintentionally block time-critical control. If production cannot continue without a required traceability record, that dependency must be explicit in the functional requirements and sequence.

21. Error handling and recovery architecture

Error handling should be consistent across device modules and sequences.

A useful structure distinguishes:

  • Device faults.
  • Sequence timeouts.
  • Communication faults.
  • Invalid process data.
  • Operator errors.
  • Configuration errors.
  • Controller or system faults.

Each category should have defined detection, reporting, and recovery behavior.

A common pattern is:

Fault Detection
      ↓
Fault Classification
      ↓
Affected Operation Inhibited
      ↓
Diagnostic Information Recorded
      ↓
Required Fault Condition Cleared
      ↓
Recovery Conditions Verified
      ↓
Authorized Restart

The required response depends on the fault. Some faults permit a controlled retry; others require operator intervention, equipment inspection, or a complete reinitialization.

Safety-related fault handling must follow the approved safety architecture and must not rely on ordinary alarm or recovery logic as a substitute.

22. Cybersecurity and access control

Industrial software architecture should consider cybersecurity from the beginning.

Relevant controls include:

  • Role-based access.
  • Separation of engineering and operator permissions.
  • Protection of controller programming access.
  • Controlled remote access.
  • Approved firmware and software versions.
  • Backup and restoration procedures.
  • Change logging.
  • Network segmentation.
  • Secure credential management.
  • Restriction of unnecessary services.
  • Validation of configuration changes.
  • Recovery from unauthorized or accidental modifications.

Operational requirements and security controls must be balanced carefully. For example, an engineering workstation should not have unrestricted access to every production device merely because troubleshooting would be more convenient.

23. Software version control and change management

A maintainable automation system needs a controlled method for managing software revisions.

Document:

  • Project identifier.
  • Controller type and firmware.
  • Engineering software version.
  • Source-code revision.
  • Change description.
  • Author or responsible engineer.
  • Approval status.
  • Test results.
  • Deployment date.
  • Backup location.
  • Recovery procedure.

A practical change workflow is:

  1. Record the requested change.
  2. Identify affected requirements, modules, and sequences.
  3. Review risks and dependencies.
  4. Modify the controlled source project.
  5. Test the change in a suitable environment.
  6. Perform the required machine validation.
  7. Back up the approved version.
  8. Record the deployed revision and release details.

Online edits and undocumented changes can create a mismatch between the running controller and the approved engineering project. The architecture and maintenance process should make that mismatch detectable.

24. Software testing and commissioning architecture

Software should be structured so that components can be tested independently before being integrated.

Typical testing stages include:

  • Code and logic review.
  • Function-block testing.
  • Device simulation.
  • Sequence testing.
  • Interface testing.
  • Factory acceptance testing.
  • Site acceptance testing.
  • Production validation.

For example, a cylinder module can be tested with simulated position feedback before it is integrated into the complete machine sequence.

Useful test cases include:

  • Normal device operation.
  • Missing feedback.
  • Contradictory sensor states.
  • Timeout conditions.
  • Invalid communication data.
  • Mode changes during operation.
  • Fault reset.
  • Power interruption.
  • Restart after interrupted operation.
  • Incorrect or missing recipe data.
  • Multiple simultaneous faults.

Architecture should expose enough status and diagnostic information to make the result of each test observable.

25. Software architecture example: conveyor and robot station

Consider a station with a conveyor, pneumatic fixture, robot, and inspection device.

A possible software structure is:

MAIN APPLICATION
    |
    +-- Mode Manager
    |
    +-- Sequence Manager
    |      |
    |      +-- Part Arrival Sequence
    |      +-- Fixture Sequence
    |      +-- Robot Loading Sequence
    |      +-- Inspection Sequence
    |      +-- Part Transfer Sequence
    |
    +-- Device Control
    |      |
    |      +-- Conveyor Module
    |      +-- Cylinder Module
    |      +-- Robot Interface
    |      +-- Inspection Interface
    |
    +-- I/O and Communication Mapping
    |
    +-- Alarm and Diagnostic Manager
    |
    +-- Production Data Manager
    |
    +-- HMI Interface

This is a logical arrangement. The actual implementation may combine some functions or separate them further according to controller capabilities and project complexity.

25.1 Example of operation

  1. The sequence manager requests conveyor movement.
  2. The conveyor module evaluates the request and required permissives.
  3. The I/O or communication layer issues the command.
  4. Feedback is processed and exposed through the conveyor module.
  5. The sequence manager evaluates the completion condition.
  6. The fixture sequence starts only when its required conditions are satisfied.
  7. The robot interface handles the program request, acknowledgment, completion, and diagnostics.
  8. The inspection interface validates the result before the sequence permits transfer.
  9. The alarm manager records faults and presents relevant diagnostic information.
  10. The production data manager records the defined cycle results.

This architecture gives each component a clear responsibility and reduces duplicate control logic.

26. Selecting the right architecture for project size

Architecture should match the complexity and expected lifetime of the system.

Project type Appropriate approach
Simple standalone machine Structured routines with clear device and sequence separation
Medium machine Modular device blocks, sequence management, alarm handling, and HMI interface
Complex assembly station Multiple coordinated sequences, interface modules, shared diagnostics, and traceability
Multi-station production line Station-level modules, line coordination, defined inter-machine interfaces, and centralized reporting
High-availability process Additional attention to redundancy, fault recovery, data consistency, and change control

A small machine does not need an elaborate software framework. A large production line should not depend on a single monolithic routine with undocumented cross-references.

27. Common software architecture mistakes

  • Writing the entire application in one large routine.
  • Mixing device control, sequence progression, and HMI logic.
  • Allowing multiple routines to control the same output.
  • Using inconsistent naming conventions.
  • Duplicating device-control logic.
  • Ignoring task priorities and execution-time limits.
  • Assuming communication status guarantees valid data.
  • Mixing safety logic with ordinary process control without a defined safety architecture.
  • Allowing HMI commands to bypass controller-side permissives.
  • Failing to define startup and restart behavior.
  • Treating alarm acknowledgment as fault clearance.
  • Allowing reporting or database delays to block time-critical control unintentionally.
  • Using global variables without clear ownership.
  • Failing to document interfaces between software modules.
  • Making changes without controlled source versions and tested backups.

28. Software architecture review checklist

  • Requirements and sequence descriptions have been reviewed.
  • The architecture is compatible with the selected controller.
  • Program modules have clear responsibilities.
  • Device control is separated from sequence control.
  • Commands have defined ownership and arbitration.
  • Operating modes and transitions are defined.
  • State initialization and recovery are documented.
  • I/O and communication interfaces are clearly mapped.
  • Data validity and stale-data handling are addressed.
  • Alarm and diagnostic behavior is consistent.
  • Task execution and timing limits are considered.
  • HMI permissions and controller-side validation are defined.
  • Safety-related functions follow the approved safety design.
  • Recipe, parameter, and production-data handling are defined.
  • Testing can be performed at module and sequence levels.
  • Software versioning, backup, and change management are established.
  • Cybersecurity and access control are addressed.
  • Future modifications can be made without unnecessary redesign.

29. Interview questions and answers

Q1. What is software architecture in industrial automation?

It is the high-level organization of control software, including modules, tasks, interfaces, data ownership, sequence management, diagnostics, and communication responsibilities.

Q2. Why separate device logic from sequence logic?

Device logic manages the behavior of an individual device, while sequence logic coordinates when the process uses it. Separating them improves reuse, testing, and troubleshooting.

Q3. What is device abstraction?

It provides a consistent logical interface to a device while hiding unnecessary details of its physical wiring or communication implementation.

Q4. What is the purpose of modular programming?

It divides the application into components with clear responsibilities and interfaces, reducing duplication and limiting the impact of changes.

Q5. Why is command ownership important?

It prevents competing program sections from issuing conflicting commands to the same device and makes control priorities predictable.

Q6. What is the difference between a task and a routine?

A task defines execution scheduling or triggering, while a routine contains a portion of program logic. Exact terminology and behavior depend on the PLC platform.

Q7. Why is a communication abstraction layer useful?

It isolates device-specific data mapping and communication diagnostics from the process sequence, making the application easier to maintain and modify.

Q8. How should alarms be handled architecturally?

Use consistent fault detection, classification, presentation, acknowledgment, clearing, and recovery rules while preserving the distinction between an acknowledged alarm and a cleared fault.

Q9. Why should database logging be separated from real-time control?

Reporting and database operations may introduce variable delays. Separating them prevents non-critical data operations from unexpectedly disrupting deterministic control, unless the approved process requirements explicitly require successful data storage before proceeding.

Q10. What is determinism?

It is the predictability of control behavior and execution timing within the requirements of the application.

Q11. How does software architecture help with retrofits?

Well-defined modules and interfaces allow engineers to replace or improve a device, communication method, or process function without unnecessarily rewriting the entire application.

Q12. What documents should result from software architecture?

Typical outputs include a software architecture specification, module breakdown, task and execution model, interface definitions, data structure conventions, alarm strategy, recovery strategy, and testing approach.

30. Practical engineering deliverables

A complete software architecture activity should produce:

  1. Software architecture specification.
  2. Program and module hierarchy.
  3. Device-control and sequence-management design.
  4. Task and execution model.
  5. Command ownership and interface definitions.
  6. I/O and communication mapping strategy.
  7. State, alarm, and diagnostic conventions.
  8. Data and tag naming standards.
  9. HMI, recipe, and production-data interfaces.
  10. Error handling and recovery rules.
  11. Safety-software boundaries aligned with the safety design.
  12. Software testing and commissioning strategy.
  13. Version-control, backup, and change-management requirements.

The central principle is that software architecture defines how the control application is divided, how its components interact, and how predictable behavior is maintained as the machine evolves.
