1. What is hardware selection?

Hardware selection is the engineering process of choosing the physical and electronic components required to implement an automation system according to its functional requirements, sequence description, I/O estimate, performance targets, safety requirements, operating environment, maintainability needs, and budget.

It converts preliminary engineering requirements into a technically compatible hardware architecture and a defined list of components.

Hardware selection is not simply choosing a PLC with enough I/O points. The selected hardware must work together electrically, mechanically, functionally, and communicatively throughout the intended operating conditions.

For an industrial automation system, hardware selection may include:

  • PLC or PAC controller.
  • Local and remote I/O modules.
  • Industrial communication modules and switches.
  • HMI panels and industrial PCs.
  • Sensors and measurement devices.
  • Motor starters, contactors, VFDs, and servo systems.
  • Robots and CNC interface hardware.
  • Safety PLCs, safety relays, and safety I/O.
  • Power supplies, circuit protection, and distribution.
  • Control panels, enclosures, cooling, and wiring accessories.
  • Network cables, connectors, terminals, and interface relays.

2. Objectives of hardware selection

The purpose is to ensure that the proposed hardware:

  • Meets all functional requirements.
  • Supports the required sequence and control strategy.
  • Has sufficient I/O and communication capacity.
  • Is electrically compatible with connected devices.
  • Meets required performance and response-time targets.
  • Satisfies applicable safety requirements.
  • Operates reliably in the intended environment.
  • Can be maintained and diagnosed efficiently.
  • Supports future expansion and lifecycle requirements.
  • Can be procured, installed, commissioned, and supported within the project constraints.

A component can be technically capable in isolation but unsuitable for the overall system. For example, a PLC may support the required number of I/O points but lack the necessary communication protocol, motion-control performance, or safety capabilities.

3. Inputs required before hardware selection

Hardware selection should use the outputs of earlier engineering activities rather than begin with a preferred product catalogue.

Engineering input How it affects selection
User requirements Establishes the required machine functions and outcomes
Functional requirements Defines controller, device, diagnostic, and performance needs
Control philosophy Defines control ownership, modes, and operating principles
Sequence description Identifies commands, feedback, timing, and coordination requirements
I/O estimate Establishes signal counts and interface types
Site survey Identifies environmental, electrical, and installation constraints
Existing-system assessment Identifies reusable hardware and compatibility limitations
Safety requirements Establishes required safety architecture and hardware capabilities
Network architecture Defines communication protocols, topology, and capacity
Cost estimate Establishes the available project budget
Maintenance requirements Establishes serviceability, spare parts, and support needs

Any unresolved requirement that could materially affect hardware selection should be recorded as an assumption or open engineering item.

The process is iterative. A selected PLC may force changes to module layout, network architecture, cabinet dimensions, or the selection of connected devices.

5. Selecting the PLC or controller

The PLC is often the central controller for machine automation, although some systems use PACs, industrial PCs, distributed controllers, or a combination.

5.1 Key selection criteria

  • Number of required DI, DO, AI, and AO channels.
  • Local and remote I/O expansion capability.
  • Program memory and data memory.
  • Processor performance and execution time.
  • Number of supported tasks and execution priorities.
  • Supported communication protocols.
  • Maximum supported network connections and devices.
  • Motion-control requirements.
  • High-speed counter and interrupt requirements.
  • Retentive memory and data-handling needs.
  • Diagnostics and troubleshooting features.
  • Programming software and licensing.
  • Controller redundancy requirements.
  • Safety certification and capabilities, if required.
  • Product lifecycle, availability, and support.

The correct controller is the smallest suitable platform that satisfies the complete application with adequate engineering margin, not necessarily the cheapest controller or the most powerful model available.

5.2 Controller selection example

Suppose a machine requires:

  • 96 DI points.
  • 48 DO points.
  • 12 AI points.
  • 4 AO points.
  • One VFD network.
  • One robot interface.
  • A future expansion allowance.

A controller should not be selected solely from the total of 160 signal points. The engineer must also determine:

  • Whether the I/O is local or distributed.
  • Which communication protocols are needed.
  • Whether the robot interface requires cyclic data, explicit messages, or hardwired signals.
  • Whether motion control is required.
  • How many network devices and connections are expected.
  • Whether safety functions require a separate or integrated safety controller.
  • Whether sufficient memory, processing capacity, and diagnostics are available.

The final controller selection must be checked against the manufacturer's specifications for the exact model and firmware.

6. Selecting I/O modules

I/O module selection converts the I/O estimate into a physical hardware arrangement.

6.1 Digital input modules

Check:

  • Rated input voltage.
  • Input current and switching thresholds.
  • PNP/NPN compatibility.
  • Common-terminal arrangement.
  • Channel isolation.
  • Input filtering and response time.
  • Supported diagnostic functions.
  • Number of channels per module.
  • Required safety rating, where applicable.

6.2 Digital output modules

Check:

  • Transistor or relay output technology.
  • Output voltage and current rating.
  • Per-channel and per-group current limits.
  • Inductive-load compatibility.
  • Short-circuit protection.
  • Switching frequency.
  • Leakage current and load behavior.
  • Required interposing relays.
  • Safety rating, where applicable.

6.3 Analog input and output modules

Check:

  • Current and voltage ranges.
  • Channel count and isolation.
  • Resolution and accuracy.
  • Conversion and update times.
  • Open-wire and out-of-range diagnostics.
  • Engineering scaling requirements.
  • Input impedance or permissible output load.
  • Sensor compatibility.
  • Required shielding and grounding arrangements.

6.4 Specialized modules

Some applications need dedicated modules for:

  • RTD and thermocouple measurements.
  • High-speed counters.
  • Encoder interfaces.
  • Weighing systems.
  • Motion control.
  • Serial communication.
  • Specialized industrial networks.
  • Safety functions.

A standard analog input module should not be assumed to support every temperature sensor or high-speed measurement device.

7. Module quantity and capacity calculations

The initial number of modules can be estimated by dividing the required channel count by the usable channels per module.

\[ N\_{\text{modules}}=\left\lceil\frac{N\_{\text{required}}}{C\_{\text{usable}}}\right\rceil \]

Where:

  • \(N\_{\text{required}}\) is the required number of signal channels.
  • \(C\_{\text{usable}}\) is the number of channels suitable for the intended application.
  • The ceiling operation rounds up to the next whole module.

Example: 50 digital inputs with 16 usable channels per module require:

\[ N\_{\text{modules}}=\left\lceil\frac{50}{16}\right\rceil=4 \]

Four modules provide 64 channels, leaving 14 unallocated channels before any additional design constraints are considered.

The final arrangement must also satisfy rack or bus limits, module compatibility, power budgets, slot availability, and spare-capacity requirements.

8. Selecting VFDs and motor-control hardware

Drive selection begins with the motor and application requirements.

Important factors include:

  • Motor rated power and current.
  • Supply voltage and frequency.
  • Motor type and control requirements.
  • Starting torque and acceleration needs.
  • Overload capability.
  • Duty cycle and expected load profile.
  • Required speed range.
  • Braking and regenerative requirements.
  • Environmental conditions.
  • Motor cable length and installation constraints.
  • Communication protocol.
  • Required digital and analog interfaces.
  • Safety functions, such as safe torque off, where required.
  • EMC and harmonic considerations.
  • Cooling and mounting arrangements.

The drive should be selected according to the manufacturer's application and derating rules. Matching only the motor's kilowatt rating is insufficient when current, overload, ambient temperature, altitude, switching frequency, or load characteristics impose additional constraints.

For a simple conveyor, a general-purpose VFD may be sufficient. For precise positioning, coordinated motion, or demanding dynamic performance, a servo system or more advanced drive architecture may be necessary.

9. Selecting servo and motion-control hardware

Motion applications require a coordinated selection of controller, drive, motor, feedback device, and mechanical system.

Check:

  • Required travel or rotation.
  • Speed and acceleration.
  • Required positioning accuracy and repeatability.
  • Load inertia and reflected inertia.
  • Required torque throughout the motion profile.
  • Peak and continuous torque.
  • Feedback type and resolution.
  • Motor and drive compatibility.
  • Mechanical transmission and backlash.
  • Regenerative energy handling.
  • Communication and synchronization requirements.
  • Homing and limit-switch arrangements.
  • Required motion-control cycle time.
  • Safety functions and stopping behavior.

The mechanical load calculation is essential. A servo motor should not be selected only because its rated power appears similar to that of the existing motor.

For positioning applications, verify both the required torque and the motion profile against the manufacturer's sizing tools or engineering calculations.

10. Selecting sensors and field devices

Sensor selection should be based on the actual physical detection task.

Application Possible device Main selection considerations
Metal-part detection Inductive proximity sensor Sensing distance, target material, mounting
General object detection Photoelectric sensor Object reflectivity, background, contamination
Cylinder position Magnetic or compatible position sensor Cylinder construction and mounting
Distance measurement Laser or other displacement sensor Range, accuracy, surface properties
Pressure measurement Pressure transmitter or switch Range, process connection, output
Temperature measurement RTD or thermocouple Range, accuracy, response time
Position feedback Encoder or linear scale Resolution, accuracy, interface
Part identification Barcode or RFID reader Code type, read distance, cycle time

Also consider IP rating, temperature range, vibration, chemical exposure, cable length, connector type, maintenance access, and spare-part availability.

A sensor that works reliably in a clean laboratory may fail quickly in an environment containing coolant, weld spatter, oil mist, metal chips, or repeated mechanical impact.

11. Selecting HMI and industrial PCs

HMI and industrial PC selection depends on the information operators and maintenance personnel need to access.

Consider:

  • Screen size and resolution.
  • Required process graphics.
  • Number of tags and alarms.
  • Historical trends and data logging.
  • Recipe and parameter management.
  • User roles and access control.
  • Communication protocols.
  • Response time.
  • Environmental rating.
  • Mounting and panel cutout.
  • Remote access requirements.
  • Software licensing and runtime limits.
  • Operating-system support and lifecycle.
  • Backup and recovery arrangements.

For an HMI, the physical display and software runtime must be compatible with the selected PLC and network architecture.

For an industrial PC, also check CPU, memory, storage endurance, operating-system support, cybersecurity, backup strategy, and whether the application requires continuous operation.

12. Selecting industrial communication hardware

Communication hardware should match the required protocols, topology, performance, and operating environment.

Typical technologies include:

  • PROFINET.
  • EtherNet/IP.
  • EtherCAT.
  • Modbus TCP.
  • Modbus RTU.
  • PROFIBUS.
  • CAN-based networks.
  • IO-Link.
  • Serial interfaces such as RS-232 and RS-485.

Selection criteria include:

  • Compatibility with both endpoints.
  • Required data-update time.
  • Number of nodes and connections.
  • Network topology.
  • Cable and connector requirements.
  • Maximum supported segment length.
  • Network diagnostics.
  • Redundancy requirements.
  • Electromagnetic environment.
  • Managed-switch features, where required.
  • Segmentation and cybersecurity.
  • Vendor support and lifecycle.

A protocol name alone does not guarantee compatibility. Check the exact device implementation, supported profiles, data mapping, firmware, and configuration requirements.

13. Selecting power supplies and protection

The control system's power architecture must support the expected load under normal and abnormal operating conditions.

Consider:

  • Input supply voltage and frequency.
  • Required DC output voltage.
  • Continuous and transient load current.
  • Startup current.
  • Simultaneous actuator operation.
  • Temperature derating.
  • Short-circuit protection.
  • Branch-circuit protection.
  • Selectivity and coordination.
  • Redundancy requirements.
  • Hold-up time, if required.
  • Grounding and bonding.
  • Separation of power groups.
  • Availability of replacement units.

A 24 V DC power supply should not be sized by counting devices alone. Use actual current consumption, duty cycle, startup characteristics, and the manufacturer's derating requirements.

For a preliminary estimate, the load current can be represented as:

\[ I\_{\text{load}}=\sum\_{i=1}^{n} I_i \]

The design must then account for the applicable simultaneous-load assumptions, transient conditions, and engineering margin.

14. Selecting safety hardware

Safety hardware must be selected from the approved risk assessment and safety requirements.

Possible components include:

  • Safety relays.
  • Safety PLCs.
  • Safety I/O modules.
  • Guard interlocks.
  • Emergency-stop devices.
  • Safety light curtains.
  • Safety laser scanners.
  • Safety-rated drive functions.
  • Safety valves and monitoring devices.

Check:

  • Required performance level or safety integrity level.
  • Architecture and diagnostic requirements.
  • Device safety ratings.
  • Compatibility of the complete safety chain.
  • Reset and restart behavior.
  • Feedback monitoring.
  • Safety communication capability, where used.
  • Response times and stopping-distance requirements.
  • Validation and proof-test requirements.

A safety-rated component does not automatically make the complete machine safety-rated. The system architecture, configuration, wiring, software, and validation must satisfy the applicable safety requirements.

15. Control panel and enclosure selection

Panel selection must consider the physical arrangement and operating environment.

Important factors include:

  • Required IP or other enclosure protection rating.
  • Panel dimensions and mounting arrangement.
  • Available internal space.
  • Heat dissipation and cooling.
  • Dust, oil, coolant, and chemical exposure.
  • Vibration and shock.
  • Electrical clearances.
  • Cable entry and routing.
  • Separation of power, control, and communication wiring.
  • EMC requirements.
  • Earthing and bonding.
  • Maintenance access.
  • Spare module space.
  • Applicable electrical and machinery standards.

15.1 Thermal design

Heat generated by drives, power supplies, controllers, and other equipment may require ventilation, heat exchangers, or air-conditioning.

The panel heat-load estimate should use manufacturer power-loss data rather than simply adding the electrical power ratings of the connected loads.

An enclosure may have adequate physical space but still be unsuitable if internal temperatures exceed component limits.

16. Environmental and installation requirements

The operating environment can eliminate otherwise suitable hardware choices.

Assess:

  • Ambient temperature and humidity.
  • Dust and liquid ingress.
  • Corrosive gases or chemicals.
  • Vibration and mechanical shock.
  • Electrical noise.
  • Altitude and derating.
  • Hazardous-area classification, if applicable.
  • Washdown requirements.
  • Outdoor exposure.
  • Cable routing and installation distances.
  • Maintenance access and safe replacement.

The chosen protection rating must be appropriate for the actual exposure. IP ratings describe specified ingress protection conditions; they do not by themselves establish resistance to every chemical, impact, or corrosion hazard.

Before finalizing the selection, verify that the components work together.

18. Lifecycle, standardization, and maintainability

Hardware should be evaluated across its expected service life, not only at purchase.

Consider:

  • Product lifecycle status.
  • Availability of replacement parts.
  • Manufacturer support.
  • Software and firmware support.
  • Repair and replacement lead times.
  • Compatibility with existing plant standards.
  • Training requirements.
  • Availability of local technical support.
  • Migration path for obsolete components.
  • Commonality with installed equipment.
  • Spare-parts inventory.
  • Diagnostic and configuration backup capability.

Standardizing on an approved hardware family can simplify training, spares, troubleshooting, and long-term maintenance. However, standardization should not override a genuine technical requirement.

For retrofit projects, confirm the exact part number and hardware revision of existing equipment. A product that looks similar may have different firmware requirements, connector pinouts, electrical characteristics, or supported communication features.

19. Cost comparison and total cost of ownership

Hardware selection should consider total lifecycle cost rather than purchase price alone.

A useful comparison includes:

Cost element Examples
Purchase Controllers, modules, drives, sensors
Engineering Configuration, programming, design effort
Installation Panels, wiring, connectors, commissioning
Licensing Engineering tools and runtime licenses
Operation Power consumption, cooling, consumables
Maintenance Inspection, repair, calibration, replacement
Downtime Production loss due to component or system failure
Lifecycle Migration, obsolescence, and future upgrades

A lower-cost component may be more expensive over time if it causes longer troubleshooting, requires specialized spares, or has limited manufacturer support.

Where downtime has a high production impact, maintainability and diagnostic capability can justify a higher initial investment.

20. Vendor and product evaluation

A structured evaluation helps avoid selecting products based on familiarity or sales claims alone.

Typical steps include:

  1. Define mandatory technical requirements.
  2. Identify compatible products from approved manufacturers.
  3. Compare specifications against the requirements.
  4. Verify compatibility with the existing architecture.
  5. Assess product lifecycle and support.
  6. Compare purchase and lifecycle costs.
  7. Record deviations and unresolved risks.
  8. Obtain technical and commercial approval.

A simple scoring model may be used when several technically acceptable options exist.

For example:

\[ S\_{\text{total}}=\sum\_{i=1}^{n} w_i s_i \]

Where \(w_i\) is the assigned weight for a criterion and \(s_i\) is the score of a candidate product for that criterion.

Weights should be defined consistently. Mandatory requirements, especially safety and electrical compatibility, should be pass/fail gates rather than weaknesses that can be offset by a high commercial score.

21. Bill of materials (BOM)

The BOM records the hardware required to build the system.

Typical fields include:

  • Item number.
  • Manufacturer.
  • Manufacturer part number.
  • Description.
  • Quantity.
  • Technical specification.
  • Installation location.
  • Approved alternative, if any.
  • Firmware or revision constraints, where relevant.
  • Lifecycle status.
  • Unit cost and extended cost.
  • Procurement status.
  • Criticality or spare-parts classification.

Example:

Item Description Quantity Selection note
PLC CPU Main controller 1 Sized for program, I/O, and communication needs
DI module Digital input module 4 Compatible voltage and field wiring
DO module Digital output module 3 Suitable load and group-current rating
AI module Analog input module 1 Supports required current signals
AO module Analog output module 1 Supports required reference range
24 V DC supply Control power supply 2 Quantity and redundancy depend on power architecture
Managed switch Industrial Ethernet switch 1 Port count and network features verified
HMI Operator interface 1 Compatible runtime and communications

This is an illustrative structure, not a project-specific procurement list. Final quantities and part numbers must be based on approved calculations and manufacturer documentation.

22. Design margins and engineering assumptions

Engineering margins are necessary, but they should be explicit.

Examples include:

  • Spare I/O channels.
  • Spare module slots.
  • Spare network ports.
  • Power-supply capacity margin.
  • Cabinet space allowance.
  • Thermal margin.
  • Controller performance margin.
  • Communication bandwidth margin.

The margin should reflect the risk and expected future change. A blanket percentage applied to every component may waste money in one area while leaving a critical limitation elsewhere.

Document assumptions such as expected simultaneous loads, future station additions, maximum network nodes, and whether a proposed spare is installed or only reserved.

23. Hardware selection example: automated production station

Consider a station containing a conveyor, pneumatic fixture, robot interface, and inspection device.

Step 1: Establish functional needs

  • Detect the incoming part.
  • Clamp and confirm the part.
  • Coordinate with the robot.
  • Trigger inspection.
  • Receive and evaluate results.
  • Release the part after required conditions are met.

Step 2: Derive interface requirements

  • Digital inputs for part and clamp feedback.
  • Digital outputs for valve and conveyor commands.
  • Communication interface for the robot.
  • Appropriate interface for the inspection device.
  • HMI for status and fault diagnosis.
  • Safety hardware according to the approved risk assessment.

Step 3: Define the architecture

Sensors and actuators
        ↓
Local or remote I/O
        ↓
PLC / Controller
        ├── HMI
        ├── Robot controller
        ├── Inspection device
        └── Industrial network

Step 4: Verify compatibility

  • Confirm field-device electrical characteristics.
  • Verify PLC support for the required I/O and protocols.
  • Check the robot handshake and inspection data interface.
  • Calculate power and output loading.
  • Verify safety hardware and required stopping behavior.
  • Confirm cabinet space, cooling, and wiring requirements.

Step 5: Finalize documentation

Produce the hardware specification, compatibility matrix, module allocation, BOM, network architecture, power budget, and open-item register.

The result should be a buildable, maintainable design rather than a list of products that happen to fit the budget.

24. Common hardware selection mistakes

  • Selecting the PLC before defining the control requirements.
  • Choosing hardware based only on purchase price.
  • Ignoring I/O electrical compatibility.
  • Selecting a drive only by motor power rating.
  • Underestimating output current or power-supply requirements.
  • Assuming all products using the same network protocol are fully compatible.
  • Ignoring safety architecture.
  • Overlooking thermal and environmental constraints.
  • Forgetting software licensing and firmware compatibility.
  • Selecting discontinued hardware without a migration plan.
  • Failing to check local spares and service support.
  • Ignoring cabinet space and cable-routing requirements.
  • Treating spare channels as equivalent to spare modules or network capacity.
  • Failing to record deviations from plant standards.
  • Releasing the BOM before resolving major technical assumptions.

25. Hardware selection review checklist

  • Functional and performance requirements are defined.
  • Sequence descriptions and I/O estimates are reviewed.
  • Controller capacity and communication limits are verified.
  • I/O modules match the field-device interfaces.
  • Drive and motion hardware meet application requirements.
  • Sensor specifications match the physical detection task.
  • HMI and industrial PC requirements are satisfied.
  • Network protocols and topology are compatible.
  • Safety hardware matches the approved safety design.
  • Power supply, protection, and load calculations are complete.
  • Panel dimensions, thermal design, and environmental requirements are checked.
  • Product lifecycle and support have been assessed.
  • Spare capacity and expansion provisions are documented.
  • Firmware, software, and licensing constraints are recorded.
  • The BOM contains exact part numbers and quantities.
  • Technical deviations and assumptions are documented.
  • Engineering and procurement approvals are completed.

26. Interview questions and answers

Q1. What is hardware selection in automation?

It is the process of choosing compatible controllers, I/O, field devices, drives, networks, power equipment, safety hardware, and supporting components to meet defined functional and engineering requirements.

Q2. What is the relationship between I/O estimation and hardware selection?

I/O estimation identifies required signal types and counts. Hardware selection converts those requirements into compatible physical modules, interfaces, and system architecture.

Q3. How do you select a PLC?

Evaluate I/O capacity, processor performance, memory, communication protocols, motion requirements, diagnostics, safety needs, expansion, lifecycle, and software support.

Q4. Why is module compatibility important?

Modules may differ in voltage, current, signal range, isolation, bus compatibility, firmware support, and load capacity. An incorrect module can make a technically adequate design unusable.

Q5. What should be considered when selecting a VFD?

Motor current and voltage, load characteristics, overload requirements, speed range, braking, environment, communication, EMC, and required safety functions.

Q6. What is the difference between hardware capacity and usable capacity?

Hardware capacity is the nominal capability stated for the equipment. Usable capacity is what remains available after accounting for electrical compatibility, architecture limits, performance constraints, reserved resources, and application requirements.

Q7. Why is product lifecycle status important?

Obsolete or unsupported hardware can create procurement delays, repair difficulties, software compatibility issues, and expensive migration work.

Q8. What is total cost of ownership?

It is the combined cost of purchasing, engineering, installing, operating, maintaining, and eventually replacing or upgrading the hardware.

Q9. Why should safety hardware be selected separately from ordinary control hardware?

Safety functions have specific performance, architecture, diagnostic, and validation requirements. Ordinary control components cannot be assumed to meet those requirements.

Q10. What documents should be available after hardware selection?

Typically, a hardware specification, BOM, module allocation, compatibility matrix, network architecture, power budget, panel requirements, and list of technical assumptions and deviations.

Q11. How do you compare two technically acceptable PLC platforms?

First verify all mandatory requirements. Then compare lifecycle support, integration effort, diagnostics, maintainability, software ecosystem, available spares, engineering cost, and total cost of ownership.

Q12. Why must hardware selection be reviewed after software architecture is developed?

The software architecture may expose additional requirements for communication, controller performance, redundancy, diagnostics, data handling, and interfaces. Hardware selection and software architecture should therefore be checked iteratively.

27. Practical engineering deliverables

A complete hardware selection activity should produce:

  1. Approved hardware selection criteria.
  2. Controller and I/O architecture.
  3. Detailed module allocation and capacity calculations.
  4. Field-device and interface specifications.
  5. Drive, motion, network, and HMI selection records.
  6. Safety hardware selection aligned with the safety design.
  7. Power and thermal calculations.
  8. Network and communication compatibility checks.
  9. A complete BOM with manufacturer part numbers.
  10. Lifecycle, spares, and obsolescence considerations.
  11. Documented assumptions, deviations, and open engineering items.
  12. An approved hardware specification ready for detailed software and electrical engineering.

The key principle is that hardware selection must produce a compatible, supportable, and maintainable system that satisfies the actual application requirements. Correct component selection depends on the entire system, not on individual datasheet ratings in isolation.
