1. What is I/O estimation?

I/O estimation is the engineering process of identifying, classifying, counting, and validating the input and output signals required for a machine, automated station, or production line.

It establishes the approximate and then refined requirements for PLC input/output modules, remote I/O stations, field wiring, communication interfaces, panel space, power supplies, and related hardware.

The purpose is not simply to count sensors and actuators. It is to determine how each device communicates with the control system, what information is required, where the signal terminates, and what capacity is needed for present and future operation.

For example, a pneumatic cylinder may require two digital inputs for retracted and extended feedback and one digital output for a solenoid valve. However, a double-solenoid valve, additional diagnostic sensors, or a safety-rated valve arrangement could change the I/O requirement.

I/O estimation is therefore a functional engineering activity that supports hardware selection, electrical design, PLC architecture, costing, and commissioning.

2. Objectives of I/O estimation

I/O estimation helps engineers:

  • Determine the number and types of required PLC signals.
  • Identify suitable local and remote I/O architectures.
  • Select digital, analog, temperature, pulse, and specialized I/O modules.
  • Estimate terminal blocks, field wiring, cables, and panel space.
  • Identify devices that communicate through industrial networks rather than hardwired I/O.
  • Identify safety-related signals and specialized safety interfaces.
  • Estimate PLC memory, channel capacity, and interface requirements.
  • Calculate preliminary panel and system costs.
  • Reserve capacity for future modifications.
  • Prevent missing signals during detailed engineering and commissioning.

A reliable I/O estimate reduces redesign, wiring changes, procurement delays, and commissioning problems.

3. Basic input and output concepts

An I/O signal transfers information between a controller and the physical process.

Input: Information received by the controller.

Examples include a proximity sensor, push button, pressure switch, motor-running feedback, analog pressure transmitter, or fault contact.

Output: A command or control value sent by the controller.

Examples include a solenoid valve command, contactor command, stack-light command, analog speed reference, or valve-position command.

The classification depends on the controller's perspective, not the physical device's name.

Device or signal Typical PLC classification Example
Proximity sensor Digital input Part detected
Limit switch Digital input Cylinder extended
Push button Digital input Cycle start
Pressure transmitter Analog input Pressure in bar
Temperature transmitter Analog input Temperature in °C
Solenoid valve command Digital output Extend cylinder
Contactor coil command Digital output Start motor
Speed reference Analog output or network data Drive speed command
Encoder pulse signal High-speed input or specialized interface Position and speed
Drive status over fieldbus Network data Ready, running, fault

The table shows typical arrangements. Actual classification depends on the selected device, electrical interface, controller, and communication architecture.

4. Main I/O signal categories

4.1 Digital inputs (DI)

Digital inputs represent discrete states, typically ON/OFF.

Examples:

  • Sensor detected or not detected.
  • Guard-closed status.
  • Cylinder extended or retracted.
  • Motor running or stopped.
  • Drive ready or fault.
  • Start and stop push buttons.
  • Relay auxiliary contacts.
  • Part-present sensors.

Digital inputs must be counted according to the required independent signals, not merely by the number of physical devices.

A sensor providing both a normal output and a separate diagnostic output may require two input channels if both signals are needed.

4.2 Digital outputs (DO)

Digital outputs issue discrete commands.

Examples:

  • Solenoid valve energization.
  • Contactor or interposing relay command.
  • Indicator lamp.
  • Buzzer.
  • Pneumatic valve command.
  • External device trigger.
  • Stack-light color commands.

The output technology must be checked. Transistor, relay, and other output types have different switching characteristics and load limitations.

A DO count alone does not prove that the selected module can drive the connected load.

4.3 Analog inputs (AI)

Analog inputs measure continuously varying quantities.

Common signals include:

  • 4–20 mA.
  • 0–20 mA.
  • 0–10 V.
  • Other voltage or current ranges supported by the selected module.
  • Resistance or thermocouple signals through compatible input modules.

Examples include pressure, temperature, flow, force, displacement, and level measurements.

The estimate must record the required range, signal type, engineering units, resolution, accuracy, isolation requirements, and any special diagnostics.

4.4 Analog outputs (AO)

Analog outputs generate continuously varying control references.

Examples include:

  • Drive speed references.
  • Proportional valve commands.
  • Pressure-controller references.
  • Flow-control commands.
  • Position references for compatible analog interfaces.

The required signal range, output load, resolution, accuracy, and isolation must match the receiving device.

If a drive accepts a digital network speed reference, a dedicated analog output may not be necessary.

4.5 Specialized I/O

Some applications require specialized modules or interfaces.

Signal or function Possible interface
High-speed pulse counting High-speed counter module
Incremental encoder Encoder-capable module
Absolute encoder Supported encoder interface or industrial network
RTD temperature sensor RTD input module
Thermocouple Thermocouple input module
Load cell Dedicated weighing or measurement module
Strain gauge Compatible bridge-measurement module
Servo feedback Drive or motion-control interface
Safety sensor Safety I/O or approved safety interface
IO-Link sensor IO-Link master and associated network
RFID reader Digital I/O or supported communication interface
Barcode scanner Digital I/O, serial interface, or industrial network

Specialized signals should not be forced into standard DI, DO, AI, or AO counts without confirming compatibility.

5. Establishing the scope before counting

Before preparing the I/O estimate, define the system boundary.

Clarify:

  • Which machines and stations are included.
  • Which devices are supplied by the machine builder.
  • Which devices are supplied by the plant.
  • Which signals are exchanged between machines.
  • Which equipment is controlled by the PLC.
  • Which functions belong to a drive, robot, CNC, or dedicated controller.
  • Which safety functions are included.
  • Which signals are hardwired and which use networks.
  • Which future expansions are expected.
  • Which existing signals or modules will be reused.

For a multi-machine production line, define the boundary between each station and the line-level controller. Otherwise, the same interface signals can be counted twice or omitted entirely.

6. Sources used to prepare the I/O estimate

The I/O estimate should be based on the available engineering information.

Source Information obtained
User requirements Required functions and operating behavior
Process study Sequence actions and necessary feedback
Sequence description Commands, transitions, and completion signals
Control philosophy Operating modes, permissives, and control responsibilities
Mechanical drawings Cylinders, grippers, clamps, and position sensors
Electrical schematics Existing and planned hardwired signals
Pneumatic diagrams Valve commands and feedback devices
Device datasheets Signal types, ranges, and interface details
Robot interface documentation Handshakes, status bits, and program selection
CNC interface documentation Machine functions and PLC/PMC signals
Drive documentation Control words, status words, and reference interfaces
Network architecture Remote I/O, fieldbus, and device communication
Safety design Safety inputs, outputs, and required safety interfaces

An estimate developed before the sequence and device interfaces are understood should be treated as preliminary, not as a final procurement specification.

7. The correct method for counting I/O

A practical estimation process follows a repeatable sequence.

Define system boundary
        ↓
Review process and sequence descriptions
        ↓
Identify field devices and interface signals
        ↓
Classify DI, DO, AI, AO, and specialized signals
        ↓
Identify hardwired versus network-based data
        ↓
Count channels and validate device interfaces
        ↓
Separate standard and safety-related I/O
        ↓
Apply documented spare-capacity rules
        ↓
Select preliminary module architecture
        ↓
Verify channel capacity, electrical compatibility, and cost
        ↓
Review and release the I/O estimate

The estimate should be revised whenever the sequence, equipment selection, or interface architecture changes.

8. Counting devices versus counting signal channels

One of the most common mistakes is assuming one device equals one I/O point.

A single device may use multiple channels, while several device functions may be communicated through one network interface.

Device Possible signal requirements Typical channel count
Simple proximity sensor One switching output 1 DI
Cylinder with two position sensors Retracted and extended feedback 2 DI
Single-solenoid valve One coil command 1 DO
Double-solenoid valve Two independent coil commands 2 DO
Motor starter with feedback Start command and running feedback 1 DO + 1 DI
Motor starter with additional fault contact Start, running, and fault 1 DO + 2 DI
Analog pressure transmitter One analog measurement 1 AI
Drive using hardwired control Start, reset, ready, running, fault, speed reference, actual speed Multiple DI/DO and possibly AI/AO
Drive using fieldbus Cyclic command and status data Network data plus any separately hardwired signals
IO-Link master with sensors Master communication and device data Network interface, not necessarily one PLC channel per sensor

These examples are illustrative. Actual requirements depend on the chosen hardware and control strategy.

9. Digital I/O counting examples

9.1 Pneumatic cylinder

Suppose a cylinder has:

  • One retracted-position sensor.
  • One extended-position sensor.
  • One solenoid valve coil.

The basic signal requirement is:

Signal tag Description Type
DI_CYL01_RET Cylinder retracted DI
DI_CYL01_EXT Cylinder extended DI
DO_CYL01_EXT Extend command DO

Total: 2 DI and 1 DO.

If the valve uses separate extend and retract coils, the DO count becomes 2. If additional pressure confirmation or valve diagnostics are required, the estimate must include those signals too.

9.2 Motor starter

Suppose a motor is controlled by a contactor and monitored through auxiliary contacts.

Signal tag Description Type
DO_MTR01_START Motor contactor command DO
DI_MTR01_RUN Motor running feedback DI
DI_MTR01_FAULT Overload trip feedback DI

Total: 1 DO and 2 DI.

This is a simplified arrangement. Actual starter design may use a combined trip contact, additional status signals, a safety interface, or a network-connected motor-management device.

9.3 Sensor group

Suppose a fixture requires:

  • Four part-present sensors.
  • Two clamp-position sensors.
  • One door-closed status.
  • One station-ready push button.

Total digital inputs:

\[ DI = 4 + 2 + 1 + 1 = 8 \]

If the fixture has three solenoid outputs and two indicator outputs:

\[ DO = 3 + 2 = 5 \]

The resulting requirement is 8 DI and 5 DO before applying spare-capacity rules.

10. Analog signal estimation

Analog signals require more than a count. Each channel must be characterized.

Important information includes:

  • Measurement or command variable.
  • Signal type and electrical range.
  • Engineering range and units.
  • Required accuracy and resolution.
  • Sampling or update-rate requirement.
  • Wiring method and cable length.
  • Isolation and grounding requirements.
  • Open-wire or out-of-range diagnostics.
  • Hazardous-area or environmental requirements, where applicable.
  • Device power requirements.

10.1 Example: pressure transmitter

Suppose a pressure transmitter measures 0–10 bar and produces a 4–20 mA signal.

The input estimate should record:

Field Value
Tag AI_PRES01
Variable Pressure
Signal 4–20 mA
Engineering range 0–10 bar
PLC channel type Compatible analog current input
Diagnostics Open-loop and out-of-range behavior as supported
Engineering units bar

For a linear transmitter, pressure can be calculated from current using:

\[ P = \frac{I - 4}{16} \times 10 \]

Where \(P\) is pressure in bar and \(I\) is measured current in mA.

At 12 mA, the indicated pressure is 5 bar, assuming a linear 4–20 mA mapping and correct scaling.

The estimate must also distinguish normal process values from fault indications such as a current below the configured valid range.

10.2 Analog input versus network measurement

If a device exposes its measurement through an industrial network, a separate analog input may not be required.

However, check whether the application also needs:

  • A hardwired fallback.
  • Independent analog monitoring.
  • A separate diagnostic contact.
  • A dedicated safety-rated signal.
  • High-speed measurement behavior.
  • Compatibility with existing control standards.

The interface should be selected deliberately rather than counted twice.

11. Hardwired I/O versus network data

A device may communicate through discrete wiring, analog wiring, or an industrial network.

Consideration Hardwired I/O Network communication
Data type Individual electrical signals Multiple data items in a communication exchange
Physical connection Individual field circuits or signal pairs Network cable or supported medium
Expansion Often requires additional channels and wiring May require additional device or network capacity
Diagnostics Depends on signal design and module capability Can provide device and communication diagnostics
Timing Depends on input/output updates and controller execution Depends on network cycle, device updates, and controller execution
Engineering Channel assignment and electrical design Network configuration, mapping, and data validation
Failure behavior Open circuit, short circuit, module or power failure Communication loss, stale data, device fault
Safety Requires suitable safety-rated architecture where needed Requires a suitable safety communication system when used for safety

A network-connected device does not automatically eliminate all hardwired signals. Emergency-stop functions, safety interfaces, or selected independent status signals may require separate arrangements according to the design.

12. Counting PLC-to-device interface signals

For devices such as drives, robots, and CNC controllers, identify the complete interface rather than counting the device as one I/O point.

For a drive, the interface might include:

  • Start and stop requests.
  • Reset request.
  • Drive-ready feedback.
  • Running feedback.
  • Fault status.
  • Speed reference.
  • Actual speed feedback.

If a network is selected, these items may be represented as fields in cyclic command and status data rather than individual physical channels.

For a robot, interface data may include:

  • Robot ready.
  • Robot fault.
  • Program selected.
  • Start request.
  • Busy.
  • Program complete.
  • Part-gripped status.
  • Part-released status.
  • Position or result data.

For a CNC, the interface may include cycle start, machine-ready status, alarm status, cycle-complete feedback, M-code requests, and acknowledgments.

The I/O estimate should document whether each item is hardwired, network-based, or provided by a separate interface module.

13. Safety-related I/O estimation

Safety-related I/O must be estimated separately from ordinary process I/O.

Potential signals include:

  • Emergency-stop devices.
  • Guard interlocks.
  • Safety light curtains.
  • Safety scanner outputs.
  • Safety relay feedback.
  • Safety valve monitoring.
  • Safe drive status and control interfaces.
  • Safety reset devices.
  • Safety-zone status and inter-controller safety data.

The estimate must reflect the approved safety architecture and required safety performance.

Important considerations include:

  • Required safety integrity or performance level.
  • Safety input and output channel requirements.
  • Dual-channel wiring where specified.
  • Test-pulse and discrepancy-monitoring requirements.
  • Required safety controller or safety relay.
  • Safe communication interfaces.
  • Feedback monitoring.
  • Diagnostic coverage and fault response.
  • Segregation and identification of safety circuits.

A standard PLC input module must not be treated as a safety input module merely because it can read the same voltage.

Safety design must be validated against the applicable machinery risk assessment, standards, and project requirements.

14. I/O allocation and module sizing

After counting signals, assign them to suitable modules.

Suppose a preliminary station requires:

  • 47 digital inputs.
  • 29 digital outputs.
  • 7 analog inputs.
  • 3 analog outputs.

The estimated demand is:

Type Required points
DI 47
DO 29
AI 7
AO 3

Assume, for illustration, that the selected architecture uses modules with these capacities:

  • 16-channel DI modules.
  • 16-channel DO modules.
  • 8-channel AI modules.
  • 4-channel AO modules.

The number of modules before spare capacity is:

\[ N\_{\text{modules}} = \left\lceil \frac{N\_{\text{required}}}{C\_{\text{module}}} \right\rceil \]

Applying the formula:

  • DI: \(\lceil 47/16 \rceil = 3\) modules, giving 48 channels.
  • DO: \(\lceil 29/16 \rceil = 2\) modules, giving 32 channels.
  • AI: \(\lceil 7/8 \rceil = 1\) module, giving 8 channels.
  • AO: \(\lceil 3/4 \rceil = 1\) module, giving 4 channels.

The unused channels are not automatically approved spare capacity. They are the result of module granularity and must be assessed for actual availability, electrical compatibility, and future allocation.

15. Calculating spare capacity

Spare capacity is reserved for future changes, unforeseen requirements, and maintainability.

A common preliminary calculation is:

\[ N\_{\text{planned}} = \left\lceil N\_{\text{required}}(1+r) \right\rceil \]

Where:

  • \(N\_{\text{required}}\) is the estimated number of signal points.
  • \(r\) is the selected spare fraction.
  • \(N\_{\text{planned}}\) is the target capacity before rounding to whole modules.

For example, if a project has 80 digital input points and specifies 20% spare capacity:

\[ N\_{\text{planned}} = \lceil 80 \times 1.20 \rceil = 96 \]

This gives a target of 96 DI channels before module-level rounding.

A percentage alone does not guarantee useful spare capacity. Spare channels must also be accessible, electrically compatible, and appropriately distributed across module types and locations.

A project may specify separate spare requirements for installed channels, module slots, remote I/O stations, network capacity, or cabinet space.

16. Installed spare channels versus spare modules

These are different forms of reserve capacity.

Spare channels are unused channels on installed modules.

Spare modules are installed or reserved modules that can be used for additional signals or replacement capacity.

Spare module slots are physical positions available for future module installation.

Spare remote I/O capacity includes available node, bus, power, and network capacity for future expansion.

A project can have spare channels but no free module slots. It can also have free slots but insufficient power-supply capacity or no available network address capacity.

A good I/O estimate records the different forms of spare capacity separately.

17. Physical and electrical compatibility checks

Before finalizing module quantities, verify the field-device electrical characteristics.

For digital inputs, check:

  • Nominal input voltage.
  • Sink/source compatibility.
  • PNP or NPN sensor output type.
  • Input current and thresholds.
  • Common-terminal arrangement.
  • Isolation between groups.
  • Input filtering and response time.

For digital outputs, check:

  • Transistor or relay technology.
  • Output voltage and current rating.
  • Inductive-load requirements.
  • Short-circuit and overload protection.
  • Group-level current limits.
  • Leakage current where relevant.
  • Required interposing relays.

For analog channels, check:

  • Current or voltage range.
  • Channel isolation.
  • Common-mode limitations.
  • Resolution and accuracy.
  • Input impedance or output load.
  • Wiring and shielding requirements.
  • Diagnostics and channel configuration.

A module with enough channels can still be the wrong module if its electrical properties do not match the connected devices.

18. Power supply and loading considerations

I/O estimation should identify the power demands created by the proposed interface.

Consider:

  • PLC and I/O module consumption.
  • Sensor supply current.
  • Solenoid coil current.
  • Interposing relay coil current.
  • Output group limits.
  • Remote I/O station consumption.
  • Network-device consumption.
  • Startup and simultaneous-load conditions.
  • Segmentation of power groups.
  • Required protection and isolation.

For example, a group of solenoid valves may exceed the permissible output-group current even when every individual output is within its channel rating.

The detailed design must calculate the relevant current and power budgets from actual datasheets. Do not size a power supply using only the number of I/O points.

19. Remote I/O estimation

Remote I/O places I/O modules closer to field devices and connects them to a controller over an industrial network.

It may be suitable when:

  • Sensors and actuators are spread across a large machine.
  • Wiring home-runs to the main control cabinet would be excessive.
  • A modular station architecture is preferred.
  • Several machines share a defined network architecture.
  • Local diagnostics and maintenance access are beneficial.

Estimate the following:

  • Number and location of remote I/O stations.
  • DI, DO, AI, AO, and specialized module counts at each station.
  • Network interface or adapter capacity.
  • Network protocol compatibility.
  • Required update time.
  • Power-supply and load capacity.
  • Network topology and cable requirements.
  • Environmental and enclosure requirements.
  • Communication-loss behavior.
  • Spare module and channel capacity.

Remote I/O reduces some field wiring distances but introduces network, power, and configuration dependencies.

20. Distributed intelligence and smart devices

Not every field device needs a dedicated PLC I/O channel for every available data item.

Examples include:

  • IO-Link sensors.
  • Smart valve manifolds.
  • Networked motor starters.
  • Intelligent drives.
  • Robot controllers.
  • CNC controllers.
  • Vision systems.
  • Barcode readers.
  • Weighing systems.

A smart device can expose multiple values, diagnostics, and status bits through a communication interface. The estimate should count the required data and interface capacity, not pretend every network data bit is an individual physical I/O channel.

However, separate physical outputs, independent safety signals, and hardwired interlocks may still be necessary.

21. Creating an I/O list

An I/O list is the detailed register of identified signals. It is one of the most important outputs of I/O estimation.

Recommended fields include:

Field Purpose
Signal tag Unique identifier
Description Functional meaning
Equipment tag Associated machine or device
Signal type DI, DO, AI, AO, safety, or network data
Electrical interface Voltage, current, contact, or protocol
Normal state Expected state during normal operation
Active state Electrical or logical condition representing activation
Device location Machine, station, or cabinet
PLC or interface Intended controller or communication endpoint
Module and channel Proposed hardware assignment

For an early concept, the module and channel columns may remain unassigned until hardware selection. For detailed engineering, they should be resolved and cross-checked against the electrical drawings and PLC configuration.

22. Tag naming and signal identification

Signal tags should be unique, readable, and consistent with the project's naming convention.

Example:

Tag Description Type
DI_CV01_PART_PRESENT Conveyor 1 part present DI
DI_CYL01_EXTENDED Cylinder 1 extended DI
DI_MTR01_FAULT Motor 1 fault feedback DI
DO_CYL01_EXTEND Extend cylinder 1 DO
DO_CV01_RUN Conveyor 1 run command DO
AI_PRES01_BAR Pressure transmitter 1 AI
AO_VFD01_SPEED_REF Drive 1 speed reference AO

The exact convention depends on the site's standards. The critical requirements are uniqueness, consistency, traceability, and clear meaning.

23. Signal polarity and normal-state definition

The estimate and I/O list should identify how signals behave in normal operation.

For example, a normally closed contact may provide a healthy-state signal while its circuit is intact. A normally open contact may become active only when a particular condition occurs.

Document:

  • The electrical contact or output behavior.
  • The logical meaning of the PLC tag.
  • The healthy and fault states, where applicable.
  • The response to open circuits or communication loss.
  • Whether the signal is energized-to-run or de-energized-to-run.

Avoid ambiguous descriptions such as Sensor ON = OK unless the physical and logical meaning is explicitly defined.

For safety-related signals, the approved safety design determines the required monitoring and response.

24. Estimating I/O for a complete machine

Consider a simplified automated fixture station.

Assumptions:

  • Six part-present sensors.
  • Four cylinder-position sensors.
  • Two pressure-switch signals.
  • One guard-closed process-status signal.
  • One cycle-start push button.
  • Four solenoid outputs.
  • One conveyor-run output.
  • Two indicator outputs.
  • Two analog pressure measurements.
  • One analog control reference.

The preliminary estimate is:

Signal group Calculation Total
Digital inputs 6 + 4 + 2 + 1 + 1 14 DI
Digital outputs 4 + 1 + 2 7 DO
Analog inputs 2 measurements 2 AI
Analog outputs 1 control reference 1 AO

This is an illustrative process I/O estimate, not a complete safety or electrical design.

Before release, verify whether the guard signal belongs to a safety system, whether pressure switches are separate devices, whether the control reference is truly analog, and whether additional feedback or diagnostics are required.

25. Common I/O estimation errors

  • Counting devices rather than independent signals.
  • Omitting cylinder-position feedback.
  • Counting network data as hardwired channels.
  • Counting the same signal in both a device interface and a separate I/O list.
  • Missing drive, robot, and CNC handshakes.
  • Omitting fault-reset or diagnostic signals.
  • Assuming every analog transmitter uses 4–20 mA.
  • Ignoring output current limits.
  • Selecting modules without checking PNP/NPN compatibility.
  • Failing to separate safety-related I/O.
  • Applying spare percentages without checking module granularity.
  • Forgetting remote I/O power and communication requirements.
  • Ignoring signal locations and cable distances.
  • Leaving signals without unique tags.
  • Failing to update the estimate after sequence changes.
  • Treating preliminary counts as final hardware quantities.

26. I/O estimate verification checklist

  • System boundary and machine ownership are defined.
  • Sequence descriptions and functional requirements have been reviewed.
  • Every identified device has been checked for its actual interface.
  • DI, DO, AI, AO, and specialized signals are classified.
  • Hardwired signals are separated from network data.
  • Drive, robot, CNC, scanner, and inspection interfaces are included.
  • Safety-related signals are separately identified.
  • Electrical compatibility is checked.
  • Analog ranges and engineering units are documented.
  • Required diagnostics and feedback are included.
  • Module capacity and unused-channel allocation are calculated.
  • Spare capacity is documented by type and location.
  • Power supply and output loading requirements are considered.
  • Remote I/O stations and network capacity are considered.
  • Tags are unique and traceable.
  • Signal ownership and physical locations are identified.
  • Assumptions and unresolved items are documented.
  • I/O lists, schematics, and software requirements are cross-checked.

27. Interview questions and answers

Q1. What is I/O estimation?

It is the process of identifying and quantifying the input, output, and specialized interface signals required for an automation system.

Q2. What is the difference between DI and DO?

DI receives discrete information from field devices, while DO sends discrete commands to devices.

Q3. What is the difference between AI and AO?

AI measures a varying input quantity, while AO generates a varying control signal for another device.

Q4. Why is one device not always equal to one I/O point?

A device may require several independent commands and feedback signals, or it may communicate many data items through one network interface.

Q5. How is the number of modules calculated?

Divide the required number of channels by the usable channel capacity per module and round up to the next whole module. Then check electrical compatibility, spare capacity, and architectural constraints.

Q6. What is spare I/O capacity?

It is reserved capacity for future additions or changes. It may consist of unused channels, spare modules, free slots, or available remote I/O and network capacity.

Q7. Why must safety I/O be estimated separately?

Safety functions may require certified hardware, specific channel arrangements, diagnostics, and validated architectures that ordinary I/O modules cannot provide.

Q8. Does using a fieldbus eliminate hardwired I/O?

No. It can replace many ordinary control and status connections, but separate hardwired signals may still be required by the interface or safety design.

Q9. What is the relationship between a sequence description and an I/O list?

The sequence description identifies required actions and feedback. The I/O list translates those requirements into defined signals and interfaces that can be engineered, assigned, tested, and maintained.

Q10. Why can a module with enough channels still be unsuitable?

Its electrical characteristics, signal range, isolation, load capacity, response time, or supported protocol may not match the application.

Q11. What is the difference between a spare channel and a spare module slot?

A spare channel is an unused point on an installed module. A spare module slot is a physical position for a future module. Neither guarantees that the system has sufficient power or network capacity.

Q12. What should be checked before releasing an I/O estimate?

Verify scope, signal classification, interface ownership, electrical compatibility, safety requirements, module capacity, spare allocation, power, networks, traceability, and consistency with the sequence description.

28. Practical engineering deliverables

A completed I/O estimation activity should normally produce:

  1. An I/O summary showing point counts by type.
  2. A detailed I/O list with tags, descriptions, and interface requirements.
  3. A hardwired-versus-network interface summary.
  4. A safety-related I/O summary linked to the safety design.
  5. A preliminary module and remote I/O allocation.
  6. A spare-capacity calculation.
  7. A power and electrical compatibility review.
  8. A list of assumptions, open items, and design risks.
  9. A traceability link to sequence steps and functional requirements.
  10. A revision-controlled estimate ready to support hardware selection.

The key principle is that I/O estimation converts process behavior into measurable interface and hardware requirements. Accurate counting comes from understanding the complete function of each device, not from counting components on a drawing.
