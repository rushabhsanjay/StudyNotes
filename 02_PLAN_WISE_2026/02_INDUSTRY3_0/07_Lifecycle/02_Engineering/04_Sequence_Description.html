1. What is a sequence description?

A sequence description is an engineering document that explains, step by step, how a machine, process station, or automated production line must operate from its initial state through normal production, completion, fault handling, and recovery.

It defines the order of operations, conditions that allow transitions, actions performed at each step, feedback required to confirm completion, timeouts, and responses to abnormal conditions.

The sequence description converts the functional requirements and control philosophy into a detailed, testable description of process behavior.

For example, a robot loading station might follow this sequence:

  1. Confirm automatic mode and station readiness.
  2. Confirm that a part is present at the loading position.
  3. Request the robot to execute the loading program.
  4. Wait for robot acknowledgment and completion feedback.
  5. Confirm that the part is positioned correctly.
  6. Update the process state and permit the next operation.

Every step must have defined entry conditions, expected actions, completion criteria, and abnormal responses. Otherwise, the sequence is merely a happy-path story, and machines have a remarkable talent for finding every omitted condition.

2. Why sequence descriptions are necessary

A sequence description provides a common understanding of how equipment is expected to behave before the software is programmed.

It helps engineers:

  • Develop PLC sequence logic consistently.
  • Coordinate PLCs, robots, CNCs, drives, scanners, and inspection devices.
  • Identify missing sensors, feedback signals, and interlocks.
  • Define timeouts and recovery behavior.
  • Prevent skipped, repeated, or out-of-order operations.
  • Support HMI design and fault diagnostics.
  • Prepare FAT and SAT test cases.
  • Troubleshoot abnormal production behavior.
  • Maintain the system when the original programmer is unavailable.

A sequence description is particularly valuable for retrofit work because existing equipment may contain undocumented assumptions about signal timing, part location, or recovery after a failed operation.

3. Relationship to other engineering documents

Document Main purpose
URS Defines the user's needs and expected outcomes
Functional requirements Defines required system functions and responses
Control philosophy Establishes overall operating rules and control priorities
Sequence description Defines step-by-step process behavior
I/O list Identifies required inputs, outputs, and interface signals
Electrical design Defines wiring, devices, and physical implementation
Software design Defines program structure and implementation rules
Test specification Defines test procedures and acceptance criteria

The sequence description should be consistent with the control philosophy and functional requirements. It should not introduce unexplained behavior that contradicts the approved requirements.

4. Main components of a sequence description

A complete sequence description typically includes:

  • Sequence name and purpose.
  • Initial and idle states.
  • Start conditions and permissives.
  • Step numbers or state identifiers.
  • Actions performed in each step.
  • Transition conditions.
  • Required feedback signals.
  • Timeouts and timeout responses.
  • Fault handling and recovery paths.
  • Stop and abort behavior.
  • Manual-mode interactions.
  • Power-loss and restart behavior.
  • HMI messages and operator actions.
  • Equipment interfaces and handshakes.
  • Completion criteria.
  • Verification and test references.

For each sequence step, the reader should be able to determine what starts it, what the machine does, how successful completion is confirmed, and what happens when completion does not occur.

5. Understanding steps, states, and transitions

These terms are related but not identical.

Step: A defined stage of a process sequence. It may specify actions to perform and conditions to evaluate.

State: A representation of the current operating condition of the system or equipment. A state can persist while the system waits for a condition.

Transition: A defined condition or event that permits movement from one step or state to another.

For example, WAIT_FOR_PART may be a state in which the controller waits for a part-present signal. When the signal becomes valid and the remaining conditions are satisfied, the controller transitions to IDENTIFY_PART.

A step should not advance merely because a timer has elapsed unless elapsed time is itself the intended completion criterion.

6. Basic sequence structure

Consider a simple automated inspection station.

IDLE
  ↓ Start conditions satisfied
WAIT_FOR_PART
  ↓ Part detected
IDENTIFY_PART
  ↓ Valid identifier received
START_INSPECTION
  ↓ Inspection accepted
WAIT_FOR_RESULT
  ↓ Valid result received
EVALUATE_RESULT
  ↓ Result recorded
COMPLETE
  ↓ Transfer permitted
TRANSFER_PART
  ↓ Transfer confirmed
IDLE

This represents the normal path only. A production-ready sequence must also define what happens when identification fails, the inspection device is unavailable, a result times out, the database cannot accept a required record, or transfer feedback is missing.

7. Defining each sequence step

Each step should be documented using a consistent structure.

Field Description
Step ID Unique step or state identifier
Step name Short, meaningful description
Entry conditions Conditions required to enter the step
Actions Commands or operations performed in the step
Completion conditions Conditions required to leave the step
Timeout Maximum permitted waiting time, where applicable
Fault response Required response if the step fails
Recovery Conditions and procedure for resuming operation
HMI indication Relevant status or diagnostic message
Test reference Verification procedure for the step

Example:

Field Example
Step ID ST-020
Step name Confirm robot readiness
Entry conditions Loading request accepted and robot interface available
Actions Monitor robot-ready and robot-fault status
Completion conditions Robot ready is active and no blocking robot fault is present
Timeout 3 seconds after entering the step
Fault response Inhibit loading and generate the defined readiness-timeout fault
Recovery Re-establish robot readiness and satisfy the approved reset conditions
HMI indication Waiting for robot ready
Test reference FAT-ROB-020

The timeout value is illustrative. It must be justified by the actual robot interface, process timing, and approved requirements.

8. Entry conditions, actions, and exit conditions

These three elements are fundamental to a reliable sequence.

8.1 Entry conditions

Entry conditions establish whether the sequence is allowed to enter a step.

Examples:

  • Automatic mode is active.
  • The previous step completed successfully.
  • The relevant equipment is ready.
  • No blocking fault is active.
  • Required part data is valid.
  • The receiving station is available.

Entry conditions should not be confused with conditions that must remain true throughout the step. A device may be ready when a step starts and then become unavailable while the action is in progress.

8.2 Actions

Actions define what the controller requests or performs while the step is active.

Examples:

  • Set a transfer request.
  • Issue a robot program-start command.
  • Trigger an inspection.
  • Write a production record.
  • Command a drive to run.
  • Display a waiting message.

The description should clarify whether an action is issued once, held active throughout the step, or repeated under defined conditions.

8.3 Exit conditions

Exit conditions determine when the current step is complete.

Examples:

  • Required position feedback is confirmed.
  • A robot reports successful program completion.
  • The inspection result is valid.
  • A handshake reaches its completion state.
  • The required data record is acknowledged.
  • An operator confirms a defined action.

A command being issued is not normally sufficient proof that the physical action completed successfully.

9. Sequential versus parallel operations

Not every machine performs one operation at a time.

Sequential operation means one operation must reach its defined completion condition before the next operation begins.

Parallel operation means two or more operations can proceed simultaneously, subject to their dependencies and interlocks.

For example, after a part is clamped, the station might start a measurement and collect traceability data in parallel.

CLAMP_PART
     ↓
CONFIRM_CLAMP
     ↓
START_PARALLEL_TASKS
     ├── Run measurement
     └── Acquire production data
               ↓
       WAIT_FOR_REQUIRED_RESULTS
               ↓
         EVALUATE_RESULTS

The sequence must define whether all tasks are required to complete, whether some tasks can fail independently, and what happens if one finishes while another times out.

Parallel execution can improve throughput, but it introduces synchronization and failure-handling requirements. Simply starting two tasks together does not guarantee that their results will be ready together.

10. Permissives and interlocks in a sequence

A sequence description should identify conditions that allow or prevent each important action.

For example, a conveyor-transfer step may require:

  • The station is in the correct operating mode.
  • The drive is ready.
  • The downstream station is available.
  • The transfer path is clear.
  • The part is correctly identified.
  • No relevant fault is active.

A conceptual permissive expression is:

TransferPermitted =
    AutomaticMode
    AND DriveReady
    AND DownstreamAvailable
    AND TransferPathClear
    AND PartIdentityValid
    AND NoBlockingFault

The actual permissives must be derived from the approved functional requirements and equipment design.

The sequence description should also specify what happens if a permissive becomes false after the step begins. Some conditions prevent entry; others require an action to stop, hold, or transition to a fault state.

Safety-related functions must be designed and validated through the appropriate safety-engineering process. A standard PLC permissive is not automatically a safety function.

11. Feedback and completion confirmation

Feedback establishes whether an action has achieved the required result.

Command Possible completion feedback
Start conveyor Running status or defined motion confirmation
Extend cylinder Extended-position sensor
Move servo Target position reached within the approved tolerance
Start robot program Defined robot program-complete status
Start CNC cycle Defined cycle-complete indication
Trigger inspection Valid inspection-complete response
Read barcode Valid identifier received
Store production result Required storage acknowledgment
Transfer part Defined transfer-complete condition

The sequence should identify which feedback is authoritative and whether multiple signals must agree.

For example, a cylinder extend command may be active while the cylinder is mechanically jammed. Without position confirmation or a defined timeout, the sequence may wait indefinitely or progress incorrectly.

12. Timeouts

A timeout detects that a required event has not occurred within an allowed period.

Common examples include:

  • Part detection timeout.
  • Drive-ready timeout.
  • Cylinder-position timeout.
  • Robot acknowledgment timeout.
  • CNC cycle-completion timeout.
  • Scanner response timeout.
  • Inspection-result timeout.
  • Data-storage acknowledgment timeout.
  • Transfer-completion timeout.

For each timeout, define:

  • The event that starts the timer.
  • The condition that stops the timer.
  • The permitted duration.
  • The fault or response generated when time expires.
  • Whether retry is permitted.
  • Whether the sequence step is retained or abandoned.
  • The required recovery conditions.

Example:

Step: WAIT_FOR_ROBOT_COMPLETE

Entry:
Robot program-start request has been accepted.

Expected event:
Robot reports the defined program-complete status.

Timeout:
The approved maximum execution time is exceeded.

Response:
Inhibit progression to the next sequence step.
Generate the specified robot-completion-timeout fault.
Retain enough diagnostic information to identify the failed operation.

Recovery:
Establish the actual robot and workpiece state before permitting
the defined recovery or restart procedure.

A timeout should be based on actual device behavior and process requirements. An excessively short timeout creates nuisance faults; an excessively long timeout delays fault detection and recovery.

13. Fault paths and abnormal transitions

The sequence description must cover important failure paths, not only successful operation.

For example:

WAIT_FOR_INSPECTION_RESULT
        ↓
Result received?
   ├── Yes, valid → EVALUATE_RESULT
   ├── No, timeout → INSPECTION_TIMEOUT
   └── Invalid data → INVALID_RESULT

Each fault path should define:

  • The detection condition.
  • The affected process.
  • Whether motion or other commands must stop or be inhibited.
  • The required alarm or diagnostic.
  • Whether the fault is latched.
  • Whether automatic retry is permitted.
  • Whether the part must be quarantined or reprocessed.
  • How the sequence returns to a valid state.

Different faults may require different responses. A missing scanner response may allow a controlled retry, while an ambiguous part-location condition after a robot interruption may require operator-assisted recovery.

14. Reset, restart, and recovery

These are three separate activities.

  • Reset: Clears or acknowledges a fault when the defined clearing conditions are satisfied.
  • Restart: Initiates or resumes operation after the required conditions are satisfied.
  • Recovery: Establishes a valid equipment and process state after an interruption or abnormal event.

A cleared alarm does not prove that the machine is ready to continue.

For example, a robot may have stopped during a part transfer. The controller may clear the communication fault after the network reconnects, but the part could still be in the robot gripper, on the fixture, or in an unexpected location.

The recovery procedure must establish the actual equipment and part state before automatic production resumes.

A sequence description should specify whether recovery:

  • Returns to the interrupted step.
  • Returns to a defined earlier step.
  • Requires the part to be removed or re-identified.
  • Requires homing or position confirmation.
  • Requires operator confirmation.
  • Reconciles production records.
  • Restarts from a known idle state.

15. Stop behavior within a sequence

The sequence description should explain what happens when different stop requests occur during operation.

Stop condition Sequence consideration
Normal stop Complete the current operation or stop at the defined safe process boundary
Cycle stop Prevent a new cycle or follow the approved current-cycle completion rule
Fault stop Inhibit affected progression and execute the specified fault response
Protective stop Follow the designed safety response and required restart conditions
Emergency stop Follow the validated emergency-stop behavior
Power interruption Reconcile physical state, retained data, and incomplete work

The correct response depends on the process and approved design. A cycle stop may allow inspection to finish, while a transfer fault may require the sequence to hold until the physical part location is confirmed.

Sequence logic must not override a safety-related stop or create an unsafe restart path.

16. Handshake sequences between devices

A handshake coordinates actions between two controllers or devices.

A basic request-and-acknowledge pattern may be represented as:

PLC / Controller                    Device
       |                               |
       |------ Request = 1 ----------->|
       |                               |
       |<----- Acknowledge = 1 --------|
       |                               |
       |<----- Operation complete -----|
       |                               |
       |------ Request = 0 ----------->|
       |                               |
       |<----- Acknowledge = 0 --------|

The exact sequence depends on the interface. Some devices use a busy state, a separate complete signal, a result-valid flag, or sequence numbers.

The sequence description should define:

  • Request assertion and removal.
  • Acknowledgment conditions.
  • Operation-start confirmation.
  • Completion conditions.
  • Timeout behavior.
  • Handling of a stuck signal.
  • Duplicate-request prevention.
  • Data validity.
  • Recovery after communication loss.

The PLC should not assume that acknowledgment and operation completion are the same event unless the device interface explicitly defines them that way.

17. Sequence description for PLC, robot, and CNC integration

17.1 PLC-to-robot sequence

A typical robot-loading sequence may include:

  1. Confirm robot readiness.
  2. Validate the requested program or job identifier.
  3. Confirm that the required station and process conditions are satisfied.
  4. Issue the robot-start request.
  5. Wait for the defined acknowledgment.
  6. Monitor execution status.
  7. Wait for successful completion.
  8. Confirm required part or fixture feedback.
  9. Update the station state.
  10. Handle faults and recovery according to the approved requirements.

The exact sequence depends on whether the robot loads parts, performs machining, handles inspection, or exchanges workpieces between stations.

17.2 PLC-to-CNC sequence

A CNC loading or machining sequence may require:

  1. Confirm CNC readiness.
  2. Verify the required machine state and selected program.
  3. Confirm required fixture, part, and process conditions.
  4. Issue the defined cycle-start or machine-function request.
  5. Monitor the relevant acknowledgment or execution state.
  6. Wait for cycle completion.
  7. Check for alarms and required completion conditions.
  8. Confirm the next permitted process action.
  9. Record the result and update production state.

CNC M-code handshakes and machine-specific PLC/PMC signals must follow the actual controller and machine-builder interface definitions.

17.3 PLC-to-drive sequence

A drive-related sequence may require:

  1. Verify operating mode and start permissives.
  2. Confirm drive readiness.
  3. Provide the approved reference.
  4. Issue the start request.
  5. Confirm running or required operating status.
  6. Monitor fault and feedback conditions.
  7. Confirm the required stopping state when the operation ends.

The actual feedback depends on the application. A simple conveyor may require running feedback, while a positioning axis may need position and motion-completion confirmation.

18. Part tracking and process-state consistency

Sequence logic often needs to track a part through multiple operations.

The sequence description should define:

  • When a part enters the process.
  • When its identity becomes valid.
  • Which station or operation currently owns the part.
  • When the part changes physical location.
  • When the operation is considered complete.
  • How quality results are associated with the part.
  • What happens when a part is removed unexpectedly.
  • How duplicate processing is prevented.
  • How records are reconciled after interruption.

For example, the controller should not increment the count of successfully inspected parts when the inspection trigger is issued. The count should be tied to the approved successful-completion event.

Likewise, if a part-transfer acknowledgment is missing, the sequence should not assume that the part is absent from the source and present at the destination simultaneously.

19. HMI indications and operator actions

The sequence description should identify the operator-facing information needed to understand the current step.

Useful indications include:

  • Current sequence state.
  • Current operating mode.
  • Waiting condition.
  • Active fault.
  • Failed transition or timeout.
  • Required operator action.
  • Recovery status.
  • Whether automatic restart is permitted.
  • Relevant equipment readiness and feedback.

Example:

Sequence state HMI indication
Waiting for part Waiting for part at loading position
Identification Reading part identifier
Waiting for robot Waiting for robot ready
Inspection Inspection in progress
Result evaluation Validating inspection result
Transfer Waiting for transfer confirmation
Faulted Transfer confirmation timeout
Recovery required Confirm part location before recovery

A useful indication explains what the controller is waiting for or why the sequence cannot continue. It should not claim an unverified root cause.

20. Parallel operations and synchronization

Some sequences require several independent operations to finish before the next step begins.

For example, after a fixture is clamped, the system may start a measurement operation and a data-record preparation operation in parallel.

The sequence description should define:

  • Which operations start together.
  • Which operations depend on another operation.
  • Whether each result is mandatory.
  • How completion is determined.
  • What happens if one operation fails.
  • Whether completed tasks can be repeated.
  • How the system handles a late result.
  • Whether the sequence can be safely paused during parallel execution.

A typical completion condition is:

ParallelTasksComplete =
    MeasurementComplete
    AND DataPreparationComplete
    AND RequiredDeviceStatusValid

This is conceptual logic. Actual conditions must be defined from the process requirements.

If one task fails, the system must follow the specified fault behavior rather than continuing simply because the other task completed successfully.

21. Sequence documentation formats

A sequence can be documented in several useful forms.

Format Best use Limitation
Step table Detailed actions, conditions, feedback, timeouts Can become lengthy for complex sequences
State-transition table State changes and transition conditions May not fully explain operator-facing behavior
Flowchart High-level understanding of process progression Can become difficult to maintain for large systems
State diagram Complex states, transitions, and fault handling Requires consistent notation and careful review
Structured text or pseudocode Clarifying logical conditions Can be mistaken for final implementation
Timing diagram Handshakes and timing relationships Covers only selected signals and events

For your converter, tables and fenced code blocks are suitable for documenting the sequence without relying on specialized diagram markup.

23. Turning a sequence description into PLC logic

The sequence description should guide implementation rather than imitate a particular programming language.

A common implementation approach uses a state variable and a state-specific set of actions and transition conditions.

Conceptual pseudocode:

CASE SequenceState OF

    IDLE:
        ClearTransientRequests()

        IF StartPermitted THEN
            SequenceState := DETECT_PART
        END_IF

    DETECT_PART:
        IF PartPresent THEN
            SequenceState := IDENTIFY_PART
        ELSIF PartDetectionTimeout THEN
            RaiseFault(PART_DETECTION_TIMEOUT)
        END_IF

    IDENTIFY_PART:
        RequestIdentifier()

        IF IdentifierValid THEN
            SequenceState := CHECK_INSPECTION_READY
        ELSIF IdentifierTimeout THEN
            RaiseFault(IDENTIFIER_TIMEOUT)
        END_IF

    CHECK_INSPECTION_READY:
        IF InspectionReady THEN
            SequenceState := START_INSPECTION
        ELSIF InspectionReadyTimeout THEN
            RaiseFault(INSPECTION_NOT_READY)
        END_IF

END_CASE

This is illustrative pseudocode, not a complete deployable program. Production implementation must define timer execution, request lifetimes, state initialization, fault priority, reset behavior, data validity, output management, and all relevant transitions.

23.1 Implementation principles

  • Use meaningful state identifiers.
  • Separate sequence progression from device-control functions where appropriate.
  • Define which actions are maintained and which are one-shot requests.
  • Prevent unintended multiple command triggers.
  • Define how timeouts are reset and evaluated.
  • Make transitions explicit.
  • Handle invalid states and unexpected feedback.
  • Keep fault handling and recovery understandable.
  • Ensure that mode changes have defined effects.
  • Validate the actual physical state before resuming an interrupted sequence.

The right implementation structure depends on the PLC platform, application complexity, and engineering standards.

24. Testing a sequence description

Every important step and transition should have a corresponding verification method.

Testing should cover:

  • Normal progression through every state.
  • Missing entry conditions.
  • Invalid or contradictory feedback.
  • Delayed responses.
  • Timeout handling.
  • Fault reset and recovery.
  • Manual-mode behavior.
  • Stop behavior during an active step.
  • Power interruption and restoration.
  • Communication loss and recovery.
  • Duplicate commands or results.
  • Part-tracking consistency.
  • HMI indications.
  • Parallel-task synchronization.

A useful test case defines the initial state, input conditions, action, expected transition, expected outputs, and pass criteria.

For example, a robot-completion timeout test should verify not only that the fault appears, but also that the sequence does not advance, the correct diagnostic is shown, the required commands are handled appropriately, and recovery is restricted until the required conditions are satisfied.

25. Common sequence-description mistakes

  • Describing only the normal operating path.
  • Failing to define entry and exit conditions.
  • Advancing the sequence based on commands instead of required feedback.
  • Omitting timeouts.
  • Using one generic fault path for unrelated failures.
  • Failing to define recovery from interrupted operations.
  • Assuming retained PLC state matches the physical machine state.
  • Ignoring manual actions that invalidate the sequence.
  • Allowing duplicate commands or repeated result processing.
  • Failing to define handshake signal lifetimes.
  • Ignoring part location and traceability during transfer failures.
  • Leaving parallel-task synchronization ambiguous.
  • Omitting HMI messages and operator actions.
  • Failing to link steps and transitions to functional requirements and tests.
  • Allowing reset to trigger unexpected motion or production restart.

26. Sequence-description review checklist

  • The sequence purpose and boundaries are defined.
  • Initial, idle, and completion states are defined.
  • Every step has a unique identifier.
  • Entry conditions and actions are documented.
  • Completion feedback and transition conditions are explicit.
  • Permissives and interlocks are identified.
  • Timeouts and abnormal transitions are defined.
  • Fault responses and recovery conditions are documented.
  • Stop behavior is defined for active sequences.
  • Manual and automatic mode interactions are addressed.
  • Handshakes and external interfaces are defined.
  • Parallel operations and synchronization are documented.
  • Part tracking and result association are addressed.
  • Power-loss and restart behavior are defined.
  • HMI indications and required operator actions are identified.
  • The sequence is traceable to functional requirements.
  • Test cases cover normal and abnormal behavior.
  • Safety-related requirements remain consistent with the approved safety design.

27. Interview questions and answers

Q1. What is a sequence description?

It is a document that describes the ordered steps, actions, transition conditions, feedback, timeouts, and fault responses required for an automated process to operate correctly.

Q2. What is the difference between a sequence description and a control philosophy?

The control philosophy establishes the overall operating principles. The sequence description defines the detailed step-by-step process behavior.

Q3. Why should every sequence step have completion feedback?

Feedback provides evidence that the required action occurred. Without it, the controller may progress even when the device has failed to perform the action.

Q4. What is a state transition?

A state transition occurs when the defined condition or event permits the sequence to move from one state to another.

Q5. What is the purpose of a timeout?

A timeout detects that an expected event has not occurred within the permitted period and triggers the defined fault response.

Q6. What is the difference between sequential and parallel operations?

Sequential operations depend on completion of earlier steps before progressing. Parallel operations can execute simultaneously, subject to their dependencies and synchronization rules.

Q7. How should a sequence recover after a robot fault?

The system should establish the actual robot state and workpiece location, satisfy the required recovery conditions, and resume only through the approved recovery procedure.

Q8. Why is resetting a fault not enough to resume production?

The fault may be cleared while the physical machine state, part location, or process record remains uncertain. Recovery must restore a valid process state before restart.

Q9. How does a sequence description help with I/O estimation?

It identifies the sensor feedback, commands, acknowledgments, device-status signals, and interface information needed to execute and verify each step. These requirements form an important input to the I/O estimate.

Q10. What is the most common sequence-design mistake?

Defining the successful path without specifying what happens when a required condition is missing, delayed, invalid, or lost.

Q11. Can one sequence have parallel operations?

Yes. The description must define which tasks execute concurrently, which completion conditions are mandatory, and how failures or delayed results affect progression.

Q12. What makes a sequence description ready for implementation?

The steps, actions, preconditions, completion feedback, transitions, timing, fault responses, recovery behavior, and test criteria are sufficiently clear for engineers to implement and verify without relying on major undocumented assumptions.
