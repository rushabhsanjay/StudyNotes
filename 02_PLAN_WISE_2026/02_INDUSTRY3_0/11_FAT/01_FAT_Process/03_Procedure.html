1. Definition of a FAT procedure

A Factory Acceptance Test (FAT) procedure is a controlled document that defines the exact steps for executing a test, the conditions under which it must be performed, the expected results, the acceptance criteria, and the evidence that must be recorded.

The FAT plan establishes the overall scope, schedule, team, and resources. The FAT procedure tells the test engineer precisely how to execute each test and determine whether it passes.

A proper procedure eliminates guesswork and ensures that different engineers can perform the same test under comparable conditions and reach consistent conclusions.

2. Objectives of the FAT procedure

  • Execute approved tests in a repeatable and controlled manner.
  • Verify that the machine meets its specified requirements.
  • Establish the initial conditions before each test.
  • Define the required actions, inputs, and fault simulations.
  • Specify expected behavior and objective pass/fail criteria.
  • Record actual results and supporting evidence.
  • Control test deviations, corrections, and retesting.
  • Preserve traceability between requirements, software versions, tests, and results.
  • Support the formal acceptance decision before shipment.

3. Overall test execution workflow

Approved FAT plan and test procedure
                 ↓
Confirm machine and software configuration
                 ↓
Verify safety controls and test prerequisites
                 ↓
Establish initial test conditions
                 ↓
Execute the defined test steps
                 ↓
Observe and measure actual behavior
                 ↓
Compare actual results with acceptance criteria
                 ↓
Record result and supporting evidence
                 ↓
Pass → Close test
Fail → Log deviation → Correct → Retest
Blocked → Record reason → Resolve prerequisite
                 ↓
Review completed test records
                 ↓
Compile FAT report and acceptance status

Every test must follow the approved procedure. If a step cannot be executed as written, the tester should stop at the appropriate safe point, record the issue, and obtain the required authorization before changing the procedure.

4. Structure of a FAT test procedure

Each test procedure should contain the following information.

Field Purpose Example
Project and machine ID Identifies the equipment under test CELL-01
Test ID Provides a unique test reference FAT-IO-001
Requirement reference Links the test to the approved requirement SWR-IO-004
Test objective Defines what must be demonstrated Verify clamp sensor input mapping
Test configuration Identifies hardware, software, and relevant settings PLC revision and I/O module configuration
Preconditions Defines what must be true before execution Machine isolated from production and test mode authorized
Safety precautions Identifies hazards and required controls Approved method for sensor simulation
Test equipment Lists instruments, fixtures, and software tools Multimeter or approved I/O simulator
Procedure steps Specifies the ordered actions Activate the approved test input
Expected result Defines required behavior Correct PLC tag changes state
Acceptance criteria Defines the pass/fail threshold Observed state matches the approved signal definition
Actual result Records what happened Input changed from false to true
Evidence Provides objective verification records Tag capture, test log, or measurement
Status Records the test outcome Pass, fail, blocked, or not applicable
Sign-off Establishes accountability Tester, witness where required, date

5. Pre-test verification

Before executing a test, verify that the machine and test setup are suitable for the intended activity.

5.1 Configuration checks

  • Confirm the machine identification and test location.
  • Record the PLC, HMI, robot, CNC, and relevant drive software versions.
  • Confirm that the approved test configuration is loaded.
  • Check that the required engineering tools and communication connections are available.
  • Verify the applicable drawing, specification, and procedure revisions.
  • Confirm that no unrecorded software changes have been made since the last approved test.

5.2 Safety checks

  • Confirm that the test has an approved procedure and risk controls.
  • Identify hazardous movements and stored energy.
  • Establish who is authorized to operate and modify the system.
  • Confirm the required guarding and protective functions.
  • Verify that test simulations, forcing, and bypasses are explicitly permitted and controlled.
  • Ensure that people are clear of hazardous areas before initiating movement.

If a precondition is not satisfied, do not proceed as though the test is valid. Record the blocker and resolve it through the defined process.

6. Establishing initial conditions

A test result is meaningful only when its starting conditions are known.

Initial conditions may include:

  • Machine operating mode.
  • Current sequence state.
  • Relevant sensor and actuator states.
  • PLC input and output values.
  • HMI command status.
  • Robot or CNC operating state.
  • Communication status and data validity.
  • Alarm and fault status.
  • Recipe, program, or parameter set.
  • Test part identity.
  • Environmental conditions where relevant.

For example, testing automatic start rejection while the machine is already in an active cycle does not verify the same requirement as testing from the ready state.

The procedure must state the intended starting state and how to establish it safely.

7. Executing test steps

Each step should contain one clear action or a logically grouped set of actions with a defined expected result.

A good test step identifies:

  1. The action to perform.
  2. The condition to observe.
  3. The expected response.
  4. The applicable time limit, if any.
  5. The evidence to capture.

Avoid instructions such as “check that the machine works correctly.” Such wording provides neither a repeatable procedure nor an objective acceptance criterion.

7.1 Example

Test ID: FAT-SEQ-004

Objective: Verify that the processing sequence cannot start before clamp-extended feedback is confirmed.

Preconditions:

  • The machine is in the approved test mode.
  • The sequence is at the specified ready state.
  • Required safety conditions are satisfied.
  • Clamp feedback and sequence state are observable.

Procedure:

  1. Initiate the cycle using the approved test method.
  2. Observe the clamp-extension command.
  3. Using an approved test arrangement, prevent the expected clamp feedback from being confirmed.
  4. Monitor the sequence state and timeout behavior.
  5. Record the alarm and relevant status information.
  6. Restore the test arrangement and complete the approved recovery procedure.

Expected result:

  • The sequence does not enter the processing state without valid clamp confirmation.
  • The defined timeout response occurs if confirmation remains absent.
  • The specified diagnostic indication is generated.
  • The sequence cannot resume until the approved recovery conditions are satisfied.

Acceptance criterion: All specified responses occur within the approved timing and functional requirements.

8. Recording actual results

The actual result must describe what was observed, not what the tester expected to observe.

A test record should capture:

  • Test ID and requirement ID.
  • Date and time.
  • Machine and software configuration.
  • Initial conditions.
  • Actions performed.
  • Actual behavior and measured values.
  • Expected behavior and acceptance criteria.
  • Pass/fail status.
  • Relevant screenshots, logs, or instrument readings.
  • Tester and witness details, where required.
  • Related defect or deviation ID.

8.1 Example test record

Field Recorded value
Test ID FAT-SEQ-004
Requirement SWR-CLAMP-002
Initial state READY
Test condition Clamp feedback not confirmed
Expected result Processing state must remain inhibited
Actual result Processing state remained inhibited; timeout alarm appeared
Timing result Within the approved timeout criterion
Evidence PLC tag capture and alarm log
Status Pass
Tester Recorded in the controlled FAT record
Deviation ID None

The example illustrates the required record structure. In an actual FAT, the result must be based on observed evidence rather than a pre-filled expected outcome.

9. Pass, fail, blocked, and not applicable

Every test should receive an explicit status.

Status Definition Required action
Pass Actual result satisfies all acceptance criteria Record evidence and close the test
Fail Actual result violates one or more acceptance criteria Raise a deviation and assess corrective action
Blocked A prerequisite prevents valid execution Record the blocker, owner, and resolution plan
Not applicable The approved scope excludes the test for a documented reason Record the rationale and obtain required approval
Not tested The test has not been executed Keep it open and assign a verification plan

A test must not be marked passed merely because the machine eventually completed the cycle after an undocumented manual intervention.

Likewise, a test that has not been performed cannot be treated as compliant simply because the engineering team expects it to work.

10. Handling failed tests

A failed test is a finding that must be investigated and controlled.

10.1 Failure-handling process

  1. Stop the test at a safe point.
  2. Preserve the actual state, logs, measurements, and relevant diagnostic information.
  3. Record the expected and observed behavior.
  4. Assign a unique deviation ID.
  5. Assess the severity, safety impact, and affected requirements.
  6. Investigate the cause.
  7. Approve and implement the corrective action.
  8. Identify the changed software or hardware configuration.
  9. Repeat the failed test.
  10. Perform regression testing on related functions.
  11. Record the retest result and close the deviation only after the defined closure criteria are met.

Safety-related failures must be controlled immediately according to the approved safety process. They must not be deferred as ordinary cosmetic defects.

10.2 Example deviation record

Field Example
Deviation ID DEV-027
Test reference FAT-SEQ-004
Problem Processing state advanced without confirmed clamp feedback
Expected result Processing state remains inhibited
Severity Assigned according to project criteria
Possible impact Incorrect process progression and potential equipment risk
Root cause To be established through investigation
Corrective action Approved after impact assessment
Retest Repeat the original test and affected regression tests
Closure Approved only after satisfactory evidence is recorded

Do not invent a root cause before investigation. “PLC programming issue” is a category, not a root-cause analysis.

11. Retesting and regression testing

Retesting verifies that the specific failed test passes after correction.

Regression testing verifies that the correction has not broken related functions that previously worked.

For example, changing a clamp timeout may affect:

  • Clamp fault detection.
  • Automatic sequence transitions.
  • HMI alarm indications.
  • Robot synchronization.
  • Recovery behavior.
  • Cycle-time performance.

The scope of regression testing should be based on the change-impact assessment, not on convenience.

Every retest should reference the original test and deviation, record the changed configuration, and preserve the previous failure result. The original failure should not be overwritten as if it never occurred.

12. Test evidence and data integrity

Evidence must be adequate to support the test conclusion.

Possible evidence includes:

  • PLC tag captures and diagnostic logs.
  • HMI screenshots.
  • Time-stamped event records.
  • Instrument readings.
  • Network diagnostics.
  • Inspection results and measurement reports.
  • Video recordings where permitted.
  • Signed test sheets.
  • Configuration exports and software revision records.

Evidence should be identifiable, legible, time-correlated where necessary, and linked to the relevant test.

If a screenshot is used, it should show enough context to establish what was tested. A screenshot showing only a green status indicator may not prove the required behavior.

For time-critical tests, use a suitable measurement method with adequate resolution and accuracy. A human-operated stopwatch may be sufficient for some cycle-time checks but unsuitable for a short controller response-time requirement.

13. FAT document and configuration control

Test results are only useful if the tested system can be identified.

Maintain a controlled record of:

  • Machine serial number or project equipment ID.
  • PLC, HMI, robot, CNC, and drive software revisions.
  • Relevant firmware and hardware revisions.
  • Recipe and parameter versions.
  • Drawing and specification revisions.
  • Test procedure revisions.
  • Approved deviations and modifications.
  • Final release configuration.

If a software download occurs midway through FAT, the affected tests must be evaluated against the new revision. Earlier results remain valid only when the impact assessment supports that conclusion.

A released software baseline should be backed up and identifiable. A folder containing files named final, final_new, and final_really_latest is not a configuration-management strategy.

14. Managing test deviations and blocked tests

A blocked test differs from a failed test.

A test fails when the system has been validly tested and does not meet the acceptance criteria. A test is blocked when the required conditions for valid execution are unavailable.

Examples of blockers include:

  • Required supplier equipment is unavailable.
  • A test fixture is damaged.
  • The approved software revision is not loaded.
  • A required interface is unavailable.
  • Test materials have not arrived.
  • A required safety procedure has not been approved.

For each blocked test, record:

  • Affected requirement and test ID.
  • Reason the test cannot proceed.
  • Required action or resource.
  • Responsible owner.
  • Planned completion date or verification stage.
  • Acceptance authority for any proposed scope change.

A blocked test remains outstanding until it is executed or receives an approved disposition consistent with the contract and applicable requirements.

15. FAT completion and final report

At the end of the FAT, the test team should reconcile all planned tests against their final status.

The FAT report should summarize:

  • Scope and exclusions.
  • Test dates and participants.
  • Machine and software configuration.
  • Tests planned and executed.
  • Pass, fail, blocked, and not-tested counts.
  • Failed tests and corrective actions.
  • Retest and regression-test evidence.
  • Safety-related test records required by the project.
  • Performance and measurement results.
  • Open deviations and agreed dispositions.
  • Document and backup status.
  • Acceptance recommendation and required approvals.

A simple completion metric can be calculated as:

\[ \text{Test execution rate} = \frac{\text{Number of tests executed}}{\text{Number of tests planned}} \times 100\\% \]

This measures execution progress, not compliance. A machine can have a 100% test execution rate and still fail FAT if some tests fail or required acceptance conditions remain unmet.

A pass rate may also be useful, but it must have a clearly defined denominator and should never conceal blocked, failed, or excluded tests.

16. Example: end-to-end FAT execution for a clamp station

Consider a PLC-controlled clamp station with an HMI, two position sensors, a pneumatic valve, and a cycle-complete output.

The planned tests may include:

  1. Verify the input mapping for both position sensors.
  2. Verify the clamp-extension command and physical movement.
  3. Confirm that extension feedback is detected.
  4. Confirm that the sequence waits for feedback before proceeding.
  5. Simulate missing feedback using the approved test method.
  6. Verify timeout detection and the defined fault response.
  7. Verify alarm acknowledgement and recovery behavior.
  8. Confirm that cycle completion occurs only after all required conditions are satisfied.
  9. Record the software revision, test results, and supporting evidence.
  10. Correct any failures, repeat affected tests, and perform regression testing.

This sequence verifies not only that the clamp moves, but also that the software correctly interprets feedback, handles failures, and controls progression.

17. Common mistakes during FAT execution

  • Skipping preconditions because the machine was working earlier.
  • Executing steps in a different order without approval.
  • Recording only “OK” without actual results or evidence.
  • Using acceptance criteria that were not approved before testing.
  • Treating a blocked test as a pass.
  • Changing software without recording the new revision.
  • Correcting a fault without repeating the failed test.
  • Failing to test related functions after a software change.
  • Overwriting the original failure record.
  • Leaving PLC forcing or temporary bypasses active after testing.
  • Accepting a test result based on operator intervention not allowed by the procedure.
  • Closing deviations without objective evidence.
  • Reporting 100% test execution as proof of 100% compliance.

18. Interview questions and answers

1. What is a FAT procedure?

It is a controlled document that specifies the test objective, prerequisites, safety controls, execution steps, expected results, acceptance criteria, and evidence requirements for a particular test.

2. What is the difference between expected and actual results?

Expected results define the required behavior. Actual results record what was observed or measured during execution.

3. What should you do if a FAT test fails?

Stop safely, preserve evidence, record the deviation, investigate the cause, implement an approved correction, repeat the failed test, and perform the necessary regression tests.

4. What is the difference between retesting and regression testing?

Retesting verifies that a specific failure has been corrected. Regression testing verifies that the change has not adversely affected related functions.

5. Why must software revisions be recorded during FAT?

The revision identifies the configuration to which the test evidence applies and establishes whether the tested software matches the intended release.

6. Can a blocked test be marked passed?

No. A blocked test has not produced valid verification evidence. It must be completed later or receive an approved disposition under the applicable acceptance process.

7. What is objective test evidence?

It is a record that supports the conclusion, such as measured values, logs, tag captures, inspection reports, or controlled test records.

8. What is the purpose of a deviation register?

It tracks failed tests and other discrepancies through assessment, ownership, correction, retesting, and formal closure.

9. Why is regression testing necessary?

A correction can introduce new faults or alter related behavior. Regression testing verifies that affected functions continue to satisfy their requirements.

10. Does completing every test mean the machine has passed FAT?

No. All tests may have been executed, but the acceptance criteria must still be satisfied, deviations must be appropriately dispositioned, and required approvals must be obtained.

19. FAT execution checklist

Before testing

  • Confirm the approved procedure and revision.
  • Verify machine and software configuration.
  • Confirm preconditions, utilities, and test equipment.
  • Review safety controls and authorized test methods.
  • Confirm expected results and acceptance criteria.

During testing

  • Follow the approved procedure.
  • Record actual results and measured values.
  • Capture relevant evidence.
  • Record pass, fail, blocked, or not-applicable status.
  • Raise deviations when acceptance criteria are not met.
  • Preserve the original results and configuration history.

After testing

  • Retest corrected failures.
  • Complete required regression testing.
  • Confirm temporary test configurations and forces are removed.
  • Reconcile all test statuses and outstanding items.
  • Verify the final software and documentation baseline.
  • Compile the FAT report and obtain the required approvals.

A sound FAT procedure creates a defensible chain of evidence from the approved requirement to the observed result. It makes the acceptance decision repeatable, technically justified, and useful for future commissioning and maintenance.
