1. Purpose of Communication Testing During FAT

Communication testing during Factory Acceptance Testing (FAT) verifies that PLCs, HMIs, robots, drives, CNC machines, remote I/O stations, SCADA systems, gateways, and other connected devices exchange data correctly and respond appropriately when communication is interrupted or degraded.

The objective is not merely to establish a network connection. The complete communication path must transfer the correct data, at the correct rate, with the correct interpretation, diagnostics, and recovery behavior.

For example, a robot controller may show Connected on its HMI while the PLC is reading an outdated robot status word. The network may appear healthy even though the application-level handshake is defective.

A successful ping or an illuminated Ethernet link LED does not prove that application-level communication is correct.

2. Scope of Communication FAT

Communication FAT typically verifies the following areas:

  • Physical connectivity between devices and network infrastructure.
  • Correct network configuration and device identification.
  • Protocol compatibility and successful session establishment.
  • Correct data exchange, mapping, scaling, and interpretation.
  • Communication update rates, timeouts, and stale-data detection.
  • Alarm generation and diagnostic information during faults.
  • Recovery after a device, cable, switch, or controller restarts.
  • Correct machine behavior when required communication is unavailable.
  • Approved communication interfaces to supervisory systems and external equipment.
  • Relevant communication records, configuration backups, and test evidence.

Communication FAT does not automatically establish that the machine is safe. Safety-related communication and functional safety require their own approved validation activities.

The actual topology depends on the machine design. Devices may share a network, use separate VLANs, connect through managed switches, or communicate through gateways between different protocols.

The FAT engineer must test the approved architecture, not assume that every device belongs on the same network.

Important terminology distinction: EtherNet/IP is an industrial communication protocol that runs over standard Ethernet and IP networking. It is not simply another name for assigning IP addresses to devices.

Similarly, PROFINET is an industrial automation communication technology, not merely ordinary Ethernet connectivity.

5. Network Configuration and Device Inventory

Before testing, establish a controlled inventory of the devices and interfaces included in the FAT.

Parameter What must be verified

Default gateway Correct where routing is required

Not every device needs a default gateway. Devices communicating only within the same subnet may not require one. Do not add network settings simply because a configuration screen provides a field for them.

For serial communication, the inventory should additionally record baud rate, data bits, parity, stop bits, addressing, wiring, and termination requirements.

6. Data Mapping and Interpretation

A connection can be established successfully while the application transfers incorrect values. Therefore, data mapping is a central part of communication FAT.

6.1 Verify data types and addresses

Check that the transmitting and receiving devices agree on:

  • Tag or register address.
  • Boolean, integer, floating-point, or structured data type.
  • Signed versus unsigned representation.
  • Array dimensions and structure layout.
  • Bit numbering and word boundaries.
  • Byte order and word order for multi-byte values.
  • Engineering units and scaling.
  • Valid value ranges and reserved values.

For example, a 32-bit floating-point measurement may occupy two 16-bit Modbus registers. If the receiving system uses the wrong register order, the displayed value may be completely incorrect even though data is being exchanged continuously.

6.2 Verify scaling

Suppose an analog transmitter uses a raw range of 0 to 27648 to represent 0 to 100 bar.

The engineering value is calculated as:

\[ PV = \frac{Raw - Raw\_{min}}{Raw\_{max} - Raw\_{min}} \times (EU\_{max} - EU\_{min}) + EU\_{min} \]

For a raw value of 13824:

\[ PV = \frac{13824}{27648} \times 100 = 50\text{ bar} \]

Verify the raw value, engineering value, units, limits, and behavior outside the normal range. The numerical range is only an example; use the actual scaling configured for the machine.

6.3 Verify command and response handshakes

Commands exchanged between controllers should have a defined request, acknowledgment, completion, and error behavior.

Example:

PLC sets Robot_Start_Request
             |
             v
Robot validates readiness
             |
             v
Robot sets Start_Acknowledge
             |
             v
Robot executes approved operation
             |
             v
Robot sets Cycle_Complete
             |
             v
PLC validates completion and advances sequence

The exact sequence depends on the interface specification.

Test that a command is not accepted twice unintentionally, a stale acknowledgment cannot falsely complete a new request, and a failed operation generates the specified response.

7. Communication Update Rate, Timeout, and Data Quality

7.1 Update rate

Verify how frequently data is exchanged and refreshed.

Relevant timing values include:

  • PLC task execution period.
  • Cyclic I/O update interval.
  • Requested packet interval or equivalent protocol update setting.
  • HMI polling or refresh period.
  • SCADA acquisition interval.
  • Supervisory data logging interval.

These values are not interchangeable. A fast PLC task does not guarantee equally fast HMI or SCADA updates.

Acceptance limits must be defined in the approved specification. A communication update rate that is acceptable for a production dashboard may be unacceptable for a machine sequence handshake.

7.2 Timeout behavior

A timeout defines how the application identifies missing or excessively delayed communication.

Test:

  • Normal response within the specified time.
  • Delayed response.
  • No response.
  • Recovery after the connection returns.
  • Behavior when data is received but no longer considered valid.

Do not select arbitrary timeout values during FAT. Verify the configured values against the design requirements and consider the device response time, network loading, and application task period.

7.3 Stale-data detection

A last-known value can remain visible after a device disconnects. This is dangerous if operators or PLC logic interpret it as current information.

The system should implement the behavior specified by the design, such as:

  • A communication-quality flag.
  • A stale-data indicator.
  • A timeout or device-fault alarm.
  • A timestamp showing the last valid update.
  • Inhibition of commands that require fresh feedback.
  • A defined fallback or safe response.

Do not assume that replacing every failed communication value with zero is correct. Zero might be a valid process value.

8. Communication FAT Test Preparation

Before executing test cases:

  1. Review the approved electrical drawings, network architecture, interface-control documents, and device lists.
  2. Identify every device and communication path within the FAT scope.
  3. Obtain the approved IP plan, protocol settings, tag mappings, and communication timing requirements.
  4. Verify hardware, firmware, software, and configuration revisions.
  5. Back up PLC, robot, CNC, drive, HMI, and network-device configurations as applicable.
  6. Confirm that the test environment and devices are in an authorized condition for fault injection.
  7. Ensure that required safety systems remain effective and that test activities cannot create an uncontrolled machine movement.
  8. Prepare test sheets containing test IDs, expected results, actual results, evidence, deviations, and retest status.
  9. Establish who is authorized to disconnect devices, change network settings, restart controllers, or modify configurations.
  10. Confirm the approved recovery procedure before deliberately interrupting any communication link.

Testing should use simulated signals, test networks, or approved maintenance conditions where possible. Do not disconnect production or safety-related communications without authorization and a documented risk assessment.

10. Communication Fault Response and Machine Behavior

Communication failure must lead to a defined application response rather than an ambiguous condition.

The response depends on the function of the communication link and the machine risk assessment.

Examples include:

  • Loss of noncritical reporting data may generate a supervisory alarm while the machine continues operating, if the design permits.
  • Loss of a required robot handshake may inhibit the next sequence transition.
  • Loss of a drive connection may trigger the configured drive or controller fault response.
  • Loss of required remote I/O may cause the controller to enter its specified fault state.
  • Loss of a safety-related communication channel must be handled according to the certified safety architecture and approved safety validation procedure.

A communication alarm alone is not sufficient if the design requires a particular machine response. Verify both the alarm and the actual response.

The FAT must also establish whether reconnection permits automatic continuation, requires operator acknowledgment, or requires a controlled restart. Automatic restart must never occur unexpectedly or contrary to the machine's approved design.

11. Time Synchronization and Data Consistency

Where multiple controllers and supervisory systems exchange timestamps, verify:

  • The configured time source.
  • Time zone and daylight-saving configuration where applicable.
  • Clock synchronization status.
  • Timestamp format and resolution.
  • Event ordering across devices.
  • Handling of a lost time source.
  • Correct correlation between alarms, machine cycles, and historian records.

A machine may communicate successfully while generating misleading event sequences because its clocks are not synchronized.

For traceability, verify that an event recorded by the PLC can be correlated with the corresponding HMI, SCADA, robot, or historian record within the specified tolerance.

13. Acceptance Criteria

Communication FAT passes only when the relevant requirements have been demonstrated with recorded evidence.

Typical acceptance criteria include:

  • All required communication links establish successfully.
  • Device identities and network configurations match the approved design.
  • Required data points are mapped correctly.
  • Numeric values, Boolean states, data types, and scaling are correct.
  • Command and acknowledgment sequences behave as specified.
  • Data update rates and timeout limits meet defined requirements.
  • Communication faults produce the required alarms, status changes, and machine responses.
  • Stale data is identified and handled correctly.
  • Recovery behavior matches the approved restart and resumption procedure.
  • Required timestamps and supervisory data are consistent within the specified tolerance.
  • No unresolved critical communication defects remain.
  • All deviations are documented and dispositioned according to the FAT procedure.

Do not invent numerical acceptance limits when the specification does not provide them. Record the missing requirement as an issue to be resolved by the responsible engineering authority.

14. FAT Records and Documentation

Maintain the following records as applicable:

  • Approved network architecture and communication drawings.
  • Device and interface inventory.
  • IP address, subnet, VLAN, and port configuration records.
  • Protocol settings and device configuration backups.
  • PLC tag, robot interface, drive, CNC, and gateway mappings.
  • Communication timing and timeout settings.
  • FAT test cases and expected results.
  • Actual results and evidence, including diagnostic logs or screenshots.
  • Fault injection and recovery records.
  • Defect reports, root-cause analysis, corrective actions, and retest results.
  • Configuration revision history and approved changes.
  • Outstanding deviations and their closure status.
  • Final FAT communication acceptance record.

For each failed test, record the original symptom, conditions, evidence, identified cause, corrective action, configuration changes, and retest result. A statement such as "communication checked OK" is not a useful test record because it establishes almost nothing.

15. Common Mistakes During Communication FAT

  • Treating ping success as proof that PLC-to-device data exchange is correct.
  • Checking only a few tags instead of the complete agreed interface list.
  • Ignoring signedness, byte order, word order, and scaling.
  • Failing to verify data freshness after a communication interruption.
  • Testing normal operation without testing timeout and recovery behavior.
  • Assuming a communication alarm guarantees the required machine response.
  • Changing IP addresses or protocol settings without recording the original configuration.
  • Restarting controllers without following the approved procedure.
  • Using unapproved fault injection on live equipment.
  • Failing to distinguish ordinary communication testing from functional safety validation.
  • Accepting unresolved interface mismatches because the individual devices appear healthy.
  • Closing a test without retaining evidence or completing the retest record.

16. Interview Questions and Answers

Q1. What is the purpose of communication FAT?

To verify that connected industrial devices exchange the correct data with the required timing, diagnostics, fault response, and recovery behavior according to the approved interface specification.

Q2. Is a successful ping sufficient to pass communication FAT?

No. Ping verifies IP-level reachability under the conditions tested. It does not prove that the required protocol session, tag mapping, data exchange, command handshake, or application behavior is correct.

Q3. What is the difference between EtherNet/IP and ordinary IP networking?

IP networking provides addressing and packet delivery. EtherNet/IP uses Ethernet and IP infrastructure together with industrial application protocols and connection mechanisms for automation data exchange.

Q4. Why can communication be healthy while a displayed value is wrong?

Possible causes include incorrect tag mapping, signedness, byte order, word order, data type, scaling, stale data, or an incorrect engineering-unit conversion.

Q5. What is stale data?

Stale data is a previously received value that is no longer confirmed to be current. The application must detect or otherwise account for its invalidity according to the system design.

Q6. What should happen when PLC-to-robot communication fails?

The system should detect the failure, generate the specified diagnostics, prevent invalid sequence progression, and follow the approved machine response. Recovery must follow the designed handshake and restart behavior.

Q7. Why must communication recovery be tested separately from communication loss?

A system may detect disconnection correctly but fail to restore the application session, refresh data, reset diagnostics, or re-establish a valid handshake after reconnection.

Q8. How would you troubleshoot intermittent communication?

Start with physical connectivity and device diagnostics, then inspect network configuration, connection statistics, protocol errors, timing, device loading, and application logic. Correlate events with timestamps and change one controlled variable at a time.

Q9. What is the difference between communication timeout and application timeout?

A communication timeout detects missing or delayed communication according to the protocol or connection configuration. An application timeout detects that an expected application event, response, or handshake has not occurred within the defined period. They may be related but are not necessarily the same.

Q10. Does successful communication testing prove functional safety?

No. Safety-related communication must be assessed within the approved safety architecture and functional safety validation. Ordinary network connectivity tests cannot establish the required safety integrity.

Q11. What evidence should be retained for a failed communication test?

The test conditions, source and destination values, timestamps, controller and device diagnostics, observed alarms, machine response, root cause, corrective action, configuration changes, and successful retest results.

Q12. Why are interface-control documents important?

They define the data exchanged, ownership, addresses or tags, data types, command and status meanings, timing requirements, fault behavior, and recovery rules. Without a controlled interface definition, acceptance becomes subjective.

17. Practical Communication FAT Checklist

  • Network architecture and device inventory reviewed.
  • IP addresses, device names, VLANs, and protocol settings verified.
  • Configuration backups and revisions recorded.
  • All required communication paths established.
  • Tag and register mappings verified.
  • Data types, byte order, scaling, and engineering units checked.
  • Command and acknowledgment handshakes tested.
  • Update rates, timeout behavior, and data quality verified.
  • Approved disconnection and recovery tests completed.
  • Required alarms and machine responses verified.
  • Supervisory timestamps and data consistency checked where applicable.
  • Safety-related communication validation handled through the approved safety process.
  • Deviations, corrective actions, and retests documented.
  • Acceptance evidence reviewed and archived.
