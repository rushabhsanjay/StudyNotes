1. Purpose of Performance Testing During FAT

Performance testing during Factory Acceptance Testing (FAT) verifies whether a machine, automation system, or production line meets its specified performance requirements under defined operating conditions.

A machine can execute every sequence correctly and still fail FAT performance testing because it operates too slowly, produces inconsistent results, generates excessive rejects, or cannot sustain the required production rate. Correct operation and acceptable performance are separate requirements, because apparently humans enjoy discovering problems one acceptance criterion at a time.

The purpose is to establish measurable evidence that the equipment can deliver the required production output, quality, speed, stability, and operational consistency before shipment or final acceptance.

1.1 Main objectives

  • Verify the specified machine cycle time and production throughput.
  • Confirm stable operation at the required production rate.
  • Identify bottlenecks, waiting periods, unnecessary movements, and process delays.
  • Verify repeatability and quality over multiple production cycles.
  • Evaluate operation under nominal and approved worst-case conditions.
  • Identify performance limitations in PLC logic, robot motion, CNC machining, drives, sensors, communication, and mechanical systems.
  • Verify performance-related alarms, recovery behavior, and restart characteristics.
  • Record objective results against approved specifications.
  • Identify deviations requiring correction before FAT acceptance.

1.2 Performance testing versus other FAT activities

Test type Primary objective Example
Functional testing Verify intended functions Clamp opens and closes correctly
Sequence testing Verify operation order Clamp confirmation precedes machining
Interlock testing Prevent invalid operation Machining cannot start without clamping confirmation
Safety testing Verify protective functions Guard opening initiates the specified safety response
Performance testing Verify speed, output, and stability Required good parts are produced within the specified cycle time
Reliability testing Evaluate operation over time Machine completes an extended run without unacceptable failures
Capability testing Evaluate process consistency against defined quality limits Machined dimensions remain within specification

These categories can overlap. For example, an extended production run can provide evidence about performance and reliability, but it does not automatically constitute a complete reliability or statistical process-capability study.

2. Define Performance Requirements Before Testing

Performance testing must begin with approved, measurable requirements. A statement such as "the machine should run fast" is not an acceptance criterion. It is an invitation to argue about what fast means.

Each requirement should identify the parameter, measurement method, operating conditions, acceptance limit, sample size or test duration, and applicable exclusions.

2.1 Typical performance parameters

Parameter Meaning Typical unit
Cycle time Time required to complete a defined machine cycle s/cycle
Throughput Units produced per unit time parts/hour
Takt time Available production time divided by customer demand s/part
Availability Fraction of defined time during which equipment is available for production %
First-pass yield Percentage of units accepted without rework %
Reject rate Percentage of produced units rejected %
Repeatability Consistency of repeated results under specified conditions mm, s, or other relevant unit
Positioning accuracy Difference between commanded and actual position mm, degrees
Changeover time Time to switch between defined products or recipes min
Response time Time between a defined input or event and the required response ms, s
Energy consumption Energy used over a defined operating basis kWh/part, kWh/cycle
MTBF Mean time between failures under an agreed definition h
MTTR Mean time to repair under an agreed definition min, h

Not every FAT needs every parameter. The approved User Requirements Specification (URS), technical specification, purchase order, and acceptance protocol determine which parameters are applicable.

2.2 Build a performance acceptance matrix

ID Parameter Test condition Measurement method Acceptance criterion
PT-01 Cycle time Approved nominal product PLC timestamps Approved maximum cycle time
PT-02 Throughput Production-like operation Good-part counter and elapsed time Approved minimum output
PT-03 Quality yield Approved sample run Inspection records Approved minimum yield
PT-04 Position repeatability Repeated positioning cycles Approved measurement instrument Approved tolerance
PT-05 Sustained operation Defined continuous run Event log and production counters Approved stability and output criteria
PT-06 Recovery performance Defined stoppage and restart Timestamped event records Approved recovery requirements

The acceptance values must come from the approved project documents. Do not invent limits during the test simply because the machine appears to be running acceptably.

3. Cycle Time, Takt Time, and Throughput

These three parameters are related but not interchangeable.

3.1 Machine cycle time

Cycle time is the elapsed time between equivalent points in consecutive cycles, provided those points are defined consistently.

For example:

  • Start: the cycle-start event is accepted by the PLC.
  • End: the machine completes the cycle and reaches the defined ready condition.
  • The next cycle begins from the same reference point.

If the measured cycle begins when a workpiece enters a station and ends when the next workpiece enters, loading and unloading may be included. If the measurement covers only the machining operation, those activities may be excluded. The test definition must make this distinction explicit.

For a single cycle:

\[ T\_{\text{cycle}}=t\_{\text{end}}-t\_{\text{start}} \]

For \(N\) consecutive cycles, the mean cycle time is:

\[ T\_{\text{avg}}=\frac{\sum\_{i=1}^{N}T_i}{N} \]

Where:

  • \(T_i\) is the measured duration of cycle \(i\).
  • \(N\) is the number of valid measured cycles.

The average must not conceal excessive variation. Record the minimum, maximum, mean, and, where required, standard deviation or percentile values.

3.2 Takt time

Takt time represents the production pace required to meet demand.

\[ T\_{\text{takt}}=\frac{T\_{\text{available}}}{D} \]

Where:

  • \(T\_{\text{available}}\) is the net production time available during the defined period.
  • \(D\) is the required number of good units during that period.

For example, if the net available production time is 7.5 hours and demand is 450 good parts:

\[ T\_{\text{takt}}=\frac{7.5\times3600}{450}=60\text{ s/part} \]

This means one good part is required every 60 seconds on average. It does not mean every individual machine must have a cycle time of exactly 60 seconds. The production system may contain parallel machines, buffers, multiple cavities, or several stations operating concurrently.

3.3 Theoretical throughput

For a single process producing one part per cycle:

\[ Q\_{\text{theoretical}}=\frac{3600}{T\_{\text{cycle}}} \]

If cycle time is 45 seconds:

\[ Q\_{\text{theoretical}}=\frac{3600}{45}=80\text{ parts/hour} \]

This calculation assumes uninterrupted operation, one part per cycle, and no losses. It is a theoretical rate, not proof that the equipment can sustain 80 good parts per hour.

If a cycle produces \(k\) parts:

\[ Q\_{\text{theoretical}}=\frac{3600k}{T\_{\text{cycle}}} \]

Use the correct unit and account for actual good output, downtime, rejects, and other losses when evaluating real production performance.

3.4 Actual throughput

\[ Q\_{\text{actual}}=\frac{N\_{\text{good parts}}}{T\_{\text{elapsed}}} \]

For parts per hour:

\[ Q\_{\text{actual,h}}=\frac{3600N\_{\text{good parts}}}{T\_{\text{elapsed,s}}} \]

If 680 good parts are produced during 10 hours:

\[ Q\_{\text{actual}}=\frac{680}{10}=68\text{ good parts/hour} \]

The reporting method must state whether elapsed time includes planned breaks, changeovers, planned stops, and unplanned downtime.

4. Preparing the FAT Performance Test

A poor test setup can make a good machine appear defective or make a defective machine appear acceptable. Preparation is part of the test, not administrative decoration.

4.1 Preconditions checklist

  • Approved URS, performance specification, and FAT protocol are available.
  • Acceptance criteria and calculation methods are agreed upon.
  • PLC, HMI, robot, CNC, drive, and other relevant software versions are recorded.
  • Approved machine parameters, recipes, and process programs are loaded.
  • Representative workpieces, materials, tooling, and fixtures are available.
  • Utilities are stable and within specified limits.
  • Lubrication, pneumatic pressure, hydraulic pressure, cooling, and other required conditions are verified.
  • Equipment has reached the defined warm-up or stabilization condition.
  • Sensors, counters, and measurement instruments are checked for suitability.
  • Measurement equipment is calibrated where required.
  • PLC, HMI, SCADA, robot, and external measurement timestamps are synchronized where cross-system timing is used.
  • Required guarding and safety functions are operational.
  • Test personnel, responsibilities, stop conditions, and recording formats are defined.
  • The method for handling invalid cycles, rejects, interruptions, and retests is agreed upon.

4.2 Define the measurement boundary

For every timing test, specify exactly what starts and ends the measurement.

Example:

Start event:
PLC accepts the automatic cycle-start request

Measured interval:
Loading + clamping + processing + inspection + unloading

End event:
Finished part is discharged and the station returns to ready

Recorded data:
Cycle number, start timestamp, end timestamp, cycle duration,
recipe, result status, alarm events, and downtime classification

If the project specification excludes loading or manual inspection, document those exclusions explicitly. Do not compare results measured using different boundaries.

5. Breaking Down the Machine Cycle

The purpose of cycle breakdown is to determine where time is consumed and identify the actual bottleneck.

5.1 Typical cycle elements

Element Example activity Performance concern
Load Operator or robot loads the workpiece Manual delay, robot approach time
Locate and clamp Fixture positions and secures the workpiece Slow actuation, confirmation delay
Position Axes or robot move to a working position Excessive travel, conservative speed
Process Machining, welding, assembly, or inspection Process duration and quality
Tool change CNC tool exchange or end-effector change Tool-change duration
Inspect Sensor or measurement system checks the part Inspection latency or retries
Unload Workpiece is removed Gripper delay, discharge obstruction
Index Rotary table or transfer mechanism advances Indexing time and settling
Wait Equipment waits for another station or condition Blocking, starvation, handshake delays
Reset to ready Sequence completes and ready conditions are restored Unnecessary return movements or logic delays

5.2 Sequential and parallel operations

For strictly sequential operations:

\[ T\_{\text{cycle}}=\sum\_{i=1}^{n}T_i \]

For operations that genuinely execute in parallel, the duration of the overlapping section is determined by the longest concurrent activity, not the sum of every activity.

For example, if robot unloading takes 8 seconds while another independent operation takes 12 seconds, the combined elapsed interval may be 12 seconds if both start together and neither blocks the other.

Do not assume operations are parallel merely because their timestamps overlap. Confirm that they are functionally independent and that the required safety and process conditions remain valid.

5.3 Identify waiting time

Waiting time can originate from:

  • Upstream station not supplying a part.
  • Downstream station not ready to receive a part.
  • Missing sensor confirmation.
  • PLC handshake delays.
  • Robot waiting for a permissive.
  • CNC cycle-complete signal arriving later than expected.
  • Network or device communication delay.
  • Excessive timers or unnecessary sequence states.
  • Mechanical settling or process stabilization.
  • Operator-dependent activity.

Separate productive process time from waiting time. If the machine's internal cycle time is acceptable but actual throughput is poor, blocked or starved time may be the real cause.

6. Measurement Methods and Data Collection

Choose a method appropriate to the timing resolution, traceability, and acceptance requirement.

6.1 Common measurement methods

Method Suitable use Limitations
PLC timestamps Cycle events, sequence duration, event intervals Scan resolution, timestamp resolution, clock configuration
HMI or SCADA historian Trends, long-duration monitoring, event correlation Sampling interval, buffering, time synchronization
High-speed data logger Short events and precise signal transitions Requires correct setup and channel configuration
CNC or robot logs Program execution and motion-related timing Logged boundaries may differ from the FAT definition
Production counters Output and throughput Must distinguish total, good, reject, and reworked units
Stopwatch Simple, slow, observable activities Human reaction time and limited resolution
Calibrated external instrument Precision measurement where required Setup, calibration status, measurement uncertainty

Use PLC timestamps or suitable external instrumentation for short automated cycles. A stopwatch may be adequate for long manual changeovers but is generally unsuitable for verifying millisecond-level events.

6.2 Timestamp-based cycle measurement

Example pseudocode:

ON cycle_start:
    start_time = timestamp()

ON cycle_complete:
    end_time = timestamp()
    cycle_time = end_time - start_time
    record(cycle_number, start_time, end_time, cycle_time, result)

The implementation must handle abnormal cases, including:

  • A new start event before the previous cycle is closed.
  • A cycle that aborts before completion.
  • PLC restart during measurement.
  • Counter rollover or timestamp discontinuity.
  • Duplicate or missed event records.
  • Invalid or missing workpiece results.

An aborted cycle should not silently disappear from the performance report. Classify it according to the agreed test protocol.

6.3 Required data fields

A useful test record can contain:

Field Purpose
Test ID Identifies the test case
Cycle number Identifies each cycle
Date and time Establishes when the cycle occurred
Product or recipe Defines the operating condition
Software revision Identifies the tested configuration
Start timestamp Records cycle start
End timestamp Records cycle completion
Cycle duration Quantifies elapsed time
Result status Good, reject, rework, aborted, or invalid
Stop or alarm code Helps explain abnormal duration
Operator or test engineer Identifies test responsibility
Remarks Captures deviations or unusual conditions

7. Average, Variation, and Stability

A satisfactory average does not necessarily mean the machine is stable.

7.1 Minimum statistical measures

For repeated cycle-time measurements, evaluate:

  • Number of valid cycles.
  • Mean cycle time.
  • Minimum and maximum cycle time.
  • Range.
  • Standard deviation, where required.
  • Percentiles, where required by the specification.
  • Number and classification of abnormal cycles.

The range is:

\[ R=T\_{\max}-T\_{\min} \]

For a sample of \(N\) observations, sample standard deviation is:

\[ s=\sqrt{\frac{\sum\_{i=1}^{N}(T_i-\bar{T})^2}{N-1}} \]

Where \(\bar{T}\) is the sample mean.

Do not discard slow cycles merely because they are inconvenient. Exclusions must follow a documented rule and retain a traceable record.

7.2 Example

Suppose five consecutive cycles take 42, 43, 42, 44, and 49 seconds.

\[ T\_{\text{avg}}=\frac{42+43+42+44+49}{5}=44\text{ s} \]

The average is 44 seconds, but the 49-second cycle deserves investigation. Possible causes include an inspection retry, robot waiting, intermittent sensor confirmation, or a communication delay.

Five cycles are only an illustration of the calculation. The required sample size must be defined by the approved FAT protocol and the performance characteristic being tested.

8. Throughput, Yield, and Reject Rate

Cycle time alone does not establish production performance. A fast process producing defective parts may deliver less usable output than a slower, stable process.

8.1 First-pass yield

\[ \text{First-pass yield}=\frac{N\_{\text{accepted without rework}}}{N\_{\text{processed}}}\times100\\% \]

Count each processed unit according to the agreed production and quality definitions.

8.2 Reject rate

\[ \text{Reject rate}=\frac{N\_{\text{rejected}}}{N\_{\text{processed}}}\times100\\% \]

Clearly distinguish rejected units from units awaiting inspection, units undergoing rework, and units that have not completed the process.

8.3 Good-part throughput

\[ Q\_{\text{good}}=\frac{N\_{\text{good parts}}}{T\_{\text{defined observation period}}} \]

For production-line FAT, the observation period must be stated. If the test excludes setup or planned breaks, the report should distinguish the measured running rate from the rate achieved over the full scheduled period.

9. Availability, MTBF, and MTTR

These measures are relevant when the FAT scope includes equipment uptime or sustained operation.

9.1 Availability

A commonly used operational definition is:

\[ A=\frac{T\_{\text{operating}}}{T\_{\text{operating}}+T\_{\text{downtime}}}\times100\\% \]

The definitions of operating time and downtime must be agreed upon. Planned maintenance, planned breaks, changeovers, external supply failures, and operator delays may be treated differently under different specifications.

Do not compare availability values calculated with different downtime classifications.

9.2 Mean time between failures

For an applicable operating period with a defined set of failures:

\[ MTBF=\frac{T\_{\text{operating}}}{N\_{\text{failures}}} \]

MTBF is meaningful only when operating time and the failure population are defined consistently. A short FAT run with zero failures cannot establish an infinite or proven MTBF. It only establishes that no qualifying failure was observed during the recorded test period.

9.3 Mean time to repair

Where repair duration is defined as the relevant corrective maintenance time:

\[ MTTR=\frac{T\_{\text{repair}}}{N\_{\text{repairs}}} \]

State whether MTTR includes diagnosis, waiting for spares, authorization, and verification. Different definitions produce different results.

A short FAT test may demonstrate fault recovery and repair procedures, but it cannot independently establish long-term reliability from limited observations.

10. Performance Test Scenarios

A useful FAT plan tests both nominal operation and relevant challenging conditions. Each scenario must remain within the equipment's approved operating envelope.

Scenario Purpose Typical evidence
Nominal production Verify normal performance Cycle-time records and good-part count
Approved product variants Verify variation across products or recipes Results by variant
Minimum and maximum approved operating conditions Verify performance at defined limits Measurements for each condition
Repeated cycles Evaluate consistency Cycle-time distribution and result status
Sustained production run Evaluate stability over time Time series, alarms, output, rejects
Startup after planned stop Verify restart behavior Recovery time and successful cycle records
Recovery after defined fault Verify return to normal operation Fault, reset, recovery, and restart timestamps
Concurrent station operation Verify integrated system performance Station timing and line throughput
Communication loading Verify relevant data and handshake behavior under specified conditions Latency, timeouts, errors, and production results
Product changeover Verify transition between approved products Changeover duration and first acceptable part

Do not introduce artificial faults or alter process parameters without an approved test procedure. Fault injection must be controlled, risk-assessed, and compatible with the machine's safety design.

11. Sustained Run Testing

A sustained run checks whether the equipment can maintain the required output and quality over a defined period, rather than achieving a good result for a handful of cycles.

11.1 Test procedure

  1. Record the approved machine configuration, recipe, tooling, workpiece, and utility conditions.
  2. Complete required startup and stabilization activities.
  3. Reset or record production counters according to the protocol.
  4. Record the test start timestamp.
  5. Run the equipment under the specified production conditions.
  6. Capture cycle times, total output, good parts, rejects, alarms, stops, and relevant process measurements.
  7. Classify each interruption according to the agreed downtime rules.
  8. Record the end timestamp and final counter values.
  9. Calculate actual throughput, quality yield, availability where applicable, and other required measures.
  10. Compare results against acceptance criteria and document deviations.

11.2 What to monitor during the run

  • Unexpected sequence pauses.
  • Repeated sensor or actuator faults.
  • PLC, robot, CNC, drive, or network alarms.
  • Temperature or pressure drift.
  • Increasing cycle time.
  • Repeated inspection retries.
  • Tool wear or process-quality changes.
  • Communication timeouts.
  • Counter mismatches between PLC, HMI, and external systems.
  • Excessive manual intervention.
  • Reject-rate changes over time.

A successful run must meet the specified output and quality requirements for the required period. A machine that reaches the target rate briefly and then slows down has not demonstrated sustained performance.

12. Performance Testing in Industrial Automation Systems

12.1 PLC and sequence performance

Verify:

  • Execution time of relevant sequence stages.
  • Consistent transitions between states.
  • Appropriate timer and timeout settings.
  • No unintended waiting caused by missing or delayed permissives.
  • Correct handling of simultaneous requests.
  • Stable counters and event timestamps.
  • No repeated or skipped cycle events.

PLC scan time is not the same as machine cycle time. Reducing scan time will not necessarily improve production throughput if the bottleneck is machining, robot motion, clamping, or downstream availability.

12.2 HMI and SCADA performance

Verify:

  • Required screens open and refresh within the specified limits.
  • Commands and status indications are updated correctly.
  • Alarm and event timestamps are sufficiently accurate for the test.
  • Historical trends capture relevant changes.
  • Production counters reconcile with the source system.
  • HMI or SCADA loading does not interfere with the required control performance.
  • Communication failures are visible and handled according to the specification.

An HMI display that updates slowly may indicate a display, network, polling, or data-processing issue. It does not automatically mean the PLC control loop itself is slow.

12.3 Robot performance

Verify the approved program's cycle duration, repeatability, approach and retract movements, handshakes, and interactions with other equipment.

Observe:

  • Excessive travel distance.
  • Unnecessary intermediate positions.
  • Waiting for fixture or CNC confirmation.
  • Gripper or end-effector delays.
  • Positioning or settling delays.
  • Collisions, near misses, or prohibited path conditions.
  • Variations between nominal and approved challenging workpieces.

Do not increase robot speed or alter motion settings solely to achieve cycle time. Confirm that changes preserve safety, path clearance, process quality, and equipment limits.

12.4 CNC performance

Verify:

  • Program execution time under the specified conditions.
  • Tool-change duration where applicable.
  • Axis positioning and settling.
  • Spindle acceleration and deceleration behavior.
  • Coolant and auxiliary-function timing.
  • Workpiece dimensions and surface quality.
  • Alarm frequency and recovery behavior.
  • Cycle consistency across the approved sample.

A shorter CNC cycle is not acceptable if it degrades part quality, exceeds tool or machine limits, or violates the approved process.

12.5 VFD, servo, and motion-system performance

Verify:

  • Acceleration and deceleration profiles.
  • Commanded versus actual speed.
  • Positioning time and settling behavior.
  • Relevant torque, current, or following-error limits.
  • Repeatability of motion.
  • Drive alarms and fault recovery.
  • Thermal stability where required.
  • Coordination between motion commands and PLC sequence transitions.

Motion performance must be evaluated using the correct measurement reference. A drive reaching its commanded speed does not prove that the entire machine cycle meets the required production rate.

13. Troubleshooting Performance Failures

Troubleshooting should begin with evidence. Changing timers, motion speeds, or PLC code without establishing the cause can hide the symptom while creating another problem.

Observed problem Possible cause Evidence to collect Corrective direction
Cycle time consistently too high Long process duration or excessive motion Stage-level timestamps Review the actual bottleneck and approved process settings
Cycle time varies significantly Intermittent waits or unstable process conditions Cycle distribution and event logs Correlate outliers with alarms, waits, and process data
PLC sequence waits unexpectedly Missing permissive or delayed handshake State transitions and I/O timestamps Correct the underlying signal or sequence issue
Robot cycle is slow Excess travel or unnecessary waiting Robot logs and handshake timing Review path and coordination under approved constraints
CNC cycle is slow Program, tool change, or process duration CNC execution records Review program and process settings with the responsible specialist
Actual output is below theoretical output Downtime, rejects, blocked or starved stations Good-part count and stop records Separate speed loss, downtime, and quality loss
Reject rate rises during sustained run Thermal drift, tooling wear, or process variation Quality measurements and time trends Investigate process stability and tooling condition
HMI appears slow Polling, rendering, or communication delays Update timestamps and communication diagnostics Correct the relevant display or data path
Production counters disagree Duplicate events, missed events, or reset mismatch PLC counters and historian records Reconcile event logic and counter definitions
Performance degrades over time Heating, wear, accumulating errors, or resource loading Time-based trends and diagnostics Identify the trend's source and verify corrective action

14. Bottleneck Analysis and Performance Improvement

A bottleneck is the process or resource that constrains overall production output under the defined operating conditions.

14.1 Improvement sequence

  1. Measure the overall production cycle and identify its exact boundaries.
  2. Break the cycle into individual activities and waiting intervals.
  3. Compare measured durations against the approved targets.
  4. Identify the largest constraint on achievable throughput.
  5. Determine whether the loss comes from processing, motion, coordination, downtime, or quality.
  6. Propose a controlled corrective action.
  7. Evaluate safety, quality, equipment limits, and downstream effects.
  8. Repeat the same measurement method after the change.
  9. Compare the before-and-after results using equivalent conditions.
  10. Record the approved software, parameter, or mechanical changes.

14.2 Common improvement opportunities

  • Remove unnecessary sequence waits while preserving required permissives.
  • Optimize robot paths without compromising safe clearance or process quality.
  • Reduce avoidable transfer or fixture delays.
  • Improve synchronization between stations.
  • Correct unreliable sensors and intermittent handshakes.
  • Optimize approved process settings.
  • Reduce inspection retries caused by an identified measurement problem.
  • Improve material supply and downstream discharge.
  • Correct communication faults that cause unnecessary interruptions.

Do not optimize a non-bottleneck operation and expect the entire line to improve automatically. If a station completes its work well before the constrained station, reducing its cycle time further may produce no increase in line throughput.

15. Performance Test Results and Acceptance

Every test result must be traceable to a test case, defined conditions, actual measurements, and an approved acceptance criterion.

15.1 Example results table

Test ID Parameter Required value Actual result Status
PT-01 Mean cycle time Approved maximum Recorded mean Pass or fail
PT-02 Good-part throughput Approved minimum Calculated actual rate Pass or fail
PT-03 First-pass yield Approved minimum Calculated yield Pass or fail
PT-04 Repeatability Approved tolerance Measured variation Pass or fail
PT-05 Sustained run Approved duration and conditions Recorded duration Pass or fail

This is a reporting template. Actual values and status must come from the executed test, not from assumptions.

15.2 Pass/fail principles

A test passes only when:

  • The correct approved configuration was tested.
  • The test conditions match the defined protocol.
  • The required measurements are available and valid.
  • The measured results satisfy the approved acceptance criteria.
  • Any required quality checks pass.
  • Deviations have been handled according to the acceptance procedure.

A missing measurement is not automatically a pass. An invalid test must be identified and repeated under controlled conditions when required.

15.3 Handling failures and deviations

For each failed or inconclusive test, record:

  • Test case and requirement ID.
  • Expected and actual results.
  • Date, time, and operating conditions.
  • Relevant alarm history and machine state.
  • Suspected cause and supporting evidence.
  • Immediate containment action.
  • Corrective action and responsible person.
  • Configuration or software changes.
  • Retest method and results.
  • Final disposition and authorized approval.

If a corrective action changes the PLC program, robot path, CNC program, drive parameters, or other controlled configuration, verify the affected functions and any dependent performance requirements. A successful retest does not remove the need for configuration control.

16. Safety and Quality Considerations

Performance testing must never compromise the safety functions or process-quality requirements to achieve a target cycle time.

  • Never bypass guards, interlocks, emergency stops, safety PLC functions, or other protective measures to improve throughput.
  • Use approved operating modes and risk-assessed test procedures.
  • Keep personnel outside hazardous areas during automatic operation.
  • Follow lockout/tagout or the applicable energy-isolation procedure when intervention requires it.
  • Do not alter robot, CNC, or drive limits without the required authorization and validation.
  • Use approved materials, fixtures, tooling, and process parameters.
  • Maintain traceability of inspected workpieces and rejected parts.
  • Stop the test if unsafe behavior, equipment damage, or uncontrolled process conditions occur.
  • Treat safety validation as its own required activity, even when safety-related behavior is observed during performance testing.

Performance improvement is acceptable only when the equipment continues to meet the applicable safety, quality, and technical requirements.

17. Documentation and Deliverables

The FAT performance-testing package should contain the following records, as applicable:

  • Approved performance test protocol.
  • Requirement-to-test traceability matrix.
  • Test setup and configuration records.
  • Software and parameter revision records.
  • Instrument identification and calibration records.
  • Raw cycle-time and event data.
  • Throughput, yield, availability, and variation calculations.
  • Sustained-run logs.
  • Quality inspection results.
  • Alarm and downtime classifications.
  • Failed-test and deviation reports.
  • Root-cause analysis and corrective-action records.
  • Retest results.
  • Approved final performance summary.
  • Outstanding actions and acceptance disposition.

Raw data should be retained alongside calculated summaries so that results can be independently checked. The report should identify any exclusions, assumptions, unavailable measurements, and deviations from the planned method.

18. Common Mistakes During FAT Performance Testing

  • Measuring only the fastest cycle instead of the required sample.
  • Reporting theoretical output as actual production output.
  • Counting all processed parts as good parts.
  • Ignoring blocked and starved conditions.
  • Excluding stoppages without an approved rule.
  • Using inconsistent start and end events for cycle-time measurements.
  • Testing before the machine has reached the defined operating condition.
  • Comparing results obtained with different recipes, workpieces, or software revisions.
  • Using a small sample to claim long-term reliability.
  • Ignoring variation because the average meets the target.
  • Using stopwatch measurements where higher timing resolution is required.
  • Changing PLC timers or motion settings before identifying the root cause.
  • Declaring acceptance without checking quality and the complete acceptance criteria.
  • Failing to record the exact configuration that produced the result.

19. Practical FAT Performance Test Example

Assume a hypothetical machine has an approved maximum mean cycle time of 45 seconds and must demonstrate a defined minimum good-part throughput during a specified test period. These values illustrate the calculation only and are not universal acceptance limits.

Test execution

  1. Verify the approved recipe, tooling, machine configuration, and utilities.
  2. Confirm the cycle-start and cycle-complete timestamp definitions.
  3. Run the specified number of valid cycles and retain individual cycle records.
  4. Calculate mean, minimum, maximum, and any required variation measures.
  5. Conduct the specified sustained production run.
  6. Record total parts, good parts, rejects, downtime, and interruptions.
  7. Calculate actual good-part throughput and quality yield.
  8. Compare each result with the applicable approved criterion.
  9. Document deviations and investigate any failure.
  10. Retest affected requirements after corrective action.

Illustrative result

Parameter Requirement Measured result Interpretation
Mean cycle time Maximum 45 s 44 s Meets this illustrative criterion
Slowest cycle Defined variation limit 51 s Investigate against the actual variation requirement
Good-part throughput Approved minimum 74 parts/hour Compare with the approved minimum
First-pass yield Approved minimum 98.5% Compare with the approved minimum
Sustained run Defined duration Completed Check output, quality, and interruptions

The machine cannot be declared fully accepted from the mean cycle time alone. The outlier, throughput, yield, sustained-run requirements, and any other mandatory criteria must also be evaluated.

20. Interview Questions and Answers

1. What is the purpose of performance testing during FAT?

To demonstrate, using defined measurement methods and objective records, that the equipment meets its specified speed, output, quality, repeatability, and sustained-operation requirements.

2. What is the difference between cycle time and takt time?

Cycle time is the time required for a defined process cycle. Takt time is the available production time divided by customer demand. Cycle time describes process performance; takt time describes the required production pace.

3. How do you calculate theoretical throughput?

For one part per cycle, theoretical throughput in parts per hour is \(3600/T\_{\text{cycle}}\), with cycle time expressed in seconds. Actual throughput must account for the agreed observation period and the number of good parts produced.

4. Why can a machine meet its cycle-time target but fail the throughput requirement?

Downtime, rejects, blocked or starved stations, manual delays, changeovers, and recovery time can reduce actual good-part output even when individual cycles meet the target.

5. Why is the average cycle time insufficient by itself?

The average can conceal intermittent long cycles, unstable performance, and abnormal events. Variation and individual cycle records may be necessary to demonstrate consistency.

6. How would you identify a bottleneck?

Measure the complete cycle, break it into stages, correlate timestamps with machine states, and determine which operation or constraint limits overall output.

7. How do you measure PLC sequence performance?

Use consistent event timestamps, relevant state transitions, and diagnostic logs. Verify timestamp resolution and synchronization, and distinguish PLC execution time from the duration of physical machine operations.

8. Can a short FAT run prove the machine's MTBF?

No. A short run provides evidence only for the observed period. A defensible MTBF estimate requires an appropriate operating-time and failure dataset with consistent definitions.

9. What should happen when a performance test fails?

Record the actual result, conditions, and evidence; identify the cause; document corrective action; control configuration changes; and repeat the affected test under the approved procedure.

10. Would you increase robot speed to resolve a cycle-time failure?

Not without identifying the bottleneck and checking safety, path clearance, settling, process quality, mechanical limits, and coordination with other equipment. The change must be controlled and the relevant requirements retested.

11. What is the difference between machine availability and throughput?

Availability measures the proportion of defined time the machine is available for production. Throughput measures output per unit time. A machine can be highly available but produce slowly, or run quickly while losing substantial time to downtime.

12. What is the most important principle in FAT performance testing?

Define the requirement and measurement method before the test, capture traceable evidence under controlled conditions, and judge acceptance against approved criteria rather than subjective impressions.
