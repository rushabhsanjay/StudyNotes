1. Definition of HMI testing during FAT

HMI (Human-Machine Interface) testing verifies that the operator interface correctly displays machine conditions, accepts authorized commands, communicates with the control system, and provides the information needed to operate and diagnose the machine.

During Factory Acceptance Testing (FAT), HMI testing establishes that screens, buttons, indicators, setpoints, navigation, permissions, diagnostics, and displayed values behave according to the approved functional specification.

An HMI can look polished and still be functionally wrong. A green indicator may display the wrong PLC tag, a start button may accept an invalid command, or a displayed pressure value may use incorrect scaling. HMI testing must therefore verify both what the operator sees and how the interface interacts with the underlying control logic.

2. Objectives of HMI testing

  • Verify screen layout, navigation, and consistency.
  • Confirm that displayed values correspond to the correct PLC tags.
  • Verify digital and analog value presentation.
  • Test start, stop, reset, acknowledgement, and other operator commands.
  • Verify command permissives and rejection messages.
  • Check operating modes and role-based permissions.
  • Verify alarm indications and alarm-history access.
  • Check trends, counters, recipes, and setpoint entry where applicable.
  • Verify communication-loss indications and stale-data handling.
  • Test screen behavior during startup, faults, recovery, and controller restart.
  • Confirm that safety-related information is presented correctly without treating the HMI as a substitute for safety functions.
  • Record evidence against the approved HMI requirements.

3. HMI architecture and test boundary

A typical industrial HMI communicates with a PLC or other controller through a configured industrial network.

Operator
   ↓
HMI screen and user interaction
   ↓
HMI tags, commands, and display logic
   ↓
Industrial communication interface
   ↓
PLC tags and control logic
   ↓
I/O modules and field devices
   ↓
Machine response

The reverse path carries feedback, status, alarms, and process values back to the operator.

HMI FAT should distinguish between the following:

  • Presentation verification: Does the screen display the intended text, units, colors, and values?
  • Tag-mapping verification: Does each displayed object use the correct data source?
  • Command verification: Does an operator action generate the intended request?
  • PLC response verification: Does the control system accept or reject the request correctly?
  • Physical-function verification: Does the machine perform the intended action?

A successful screen interaction does not automatically prove that the physical machine function works. Each verification layer needs evidence appropriate to the requirement.

4. HMI test preparation

Before testing, confirm the approved HMI design, software configuration, and expected behavior.

4.1 Required documents

  • Approved HMI screen list and screen designs.
  • Functional specification and operating philosophy.
  • PLC tag list and HMI tag database.
  • Alarm list and alarm-priority definitions.
  • User-role and access-permission matrix.
  • Setpoint and recipe specifications.
  • Communication architecture and network configuration.
  • Applicable FAT test cases and acceptance criteria.
  • Current HMI and PLC software revisions.
  • Applicable language, units, and formatting requirements.

4.2 Configuration checks

  • Verify that the correct HMI project is loaded.
  • Confirm the target PLC or controller connection.
  • Verify tag names, data types, addresses, and scaling.
  • Check screen resolution and intended display hardware.
  • Confirm the intended runtime user account and permissions.
  • Record the software versions and test environment.
  • Establish a safe machine state for command testing.

If a simulated PLC or test database is used, record that fact. It may validate screen behavior and tag handling without proving communication with the actual production controller.

5. Screen navigation testing

Navigation testing verifies that operators can reach the required information and return to the appropriate operating screen without confusion.

Typical screens include:

  • Main overview.
  • Manual operation.
  • Automatic cycle.
  • I/O diagnostics.
  • Alarm summary.
  • Alarm history.
  • Trends.
  • Recipe or parameter management.
  • Maintenance diagnostics.
  • Communication status.
  • User login and access management.

5.1 Navigation test cases

Test ID Test action Expected result
FAT-HMI-001 Open the main overview Correct machine overview appears
FAT-HMI-002 Select the manual-operation screen Correct manual screen opens
FAT-HMI-003 Navigate to alarm summary Current alarm information is displayed
FAT-HMI-004 Return to the main overview Correct overview is restored
FAT-HMI-005 Open a restricted maintenance screen Access follows the configured permission rules
FAT-HMI-006 Open each screen using the defined navigation paths No missing screens, incorrect links, or unintended navigation occurs

Check that navigation labels are understandable, page titles are correct, and the current operating context is visible where needed.

For larger machines, test navigation from the perspective of an operator responding to a fault, not just an engineer browsing screens.

6. Status indicators and tag mapping

An HMI indicator must represent the intended machine signal.

Examples include:

  • Clamp extended.
  • Clamp retracted.
  • Part present.
  • Drive ready.
  • Robot busy.
  • Cycle running.
  • Cycle complete.
  • Guard status.
  • Pressure healthy.
  • Communication healthy.

6.1 Verification method

  1. Identify the indicator and its approved PLC tag.
  2. Record the initial tag value and displayed state.
  3. Change the signal using an approved test method.
  4. Confirm that the HMI changes to the correct state.
  5. Verify any defined text, color, or animation.
  6. Restore the signal and verify the reverse transition.
  7. Confirm that unrelated indicators remain correct.
  8. Record the actual result and evidence.

6.2 Example

PLC value Expected HMI indication Verification
Part_Present = FALSE Part absent Indicator and text match the specification
Part_Present = TRUE Part present Indicator and text change correctly
Drive_Ready = FALSE Drive not ready Correct status appears
Drive_Ready = TRUE Drive ready Correct status appears
Communication data invalid Defined invalid or communication-loss indication HMI does not falsely present invalid data as healthy

Color alone is not sufficient for critical status identification. Where specified, use clear text or symbols as well, so the indication remains understandable under different display conditions or for users with color-vision deficiencies.

7. Digital and analog value display testing

HMI values must match the intended data source and engineering interpretation.

7.1 Digital values

Verify:

  • Correct tag mapping.
  • Correct ON/OFF interpretation.
  • Correct state text.
  • Correct indication during transitions.
  • Correct handling of invalid or unavailable data.
  • Consistency between overview and diagnostic screens.

7.2 Analog values

Verify:

  • Correct data type and source.
  • Correct raw-to-engineering scaling.
  • Correct units.
  • Decimal places and rounding.
  • Minimum and maximum display behavior.
  • Negative or out-of-range values where relevant.
  • Invalid-data handling.
  • Alarm threshold presentation where specified.

For a pressure signal configured as 4–20 mA representing 0–100 bar, the engineering value is:

\[ P = \frac{I - 4}{20 - 4}\times 100 \]

At 12 mA, the nominal pressure is 50 bar.

The FAT should compare the HMI value against the expected engineering value and the approved tolerance. If the PLC already performs scaling, verify that the HMI does not apply the same scaling a second time.

7.3 Example display test

Simulated current Expected engineering value HMI acceptance check
4 mA 0 bar Displays the lower-range value within tolerance
8 mA 25 bar Displays the correct intermediate value
12 mA 50 bar Displays the correct midpoint
16 mA 75 bar Displays the correct intermediate value
20 mA 100 bar Displays the upper-range value within tolerance

8. Operator command testing

HMI buttons commonly generate requests to the PLC. These requests must be checked for correct mapping, authorization, and behavior.

Typical commands include:

  • Cycle start.
  • Normal stop.
  • Cycle abort.
  • Fault reset.
  • Alarm acknowledgement.
  • Manual actuator request.
  • Recipe selection.
  • Setpoint modification.
  • Maintenance-mode request.

8.1 Command test method

  1. Confirm the required operating mode and initial machine state.
  2. Identify the HMI command object and corresponding PLC tag.
  3. Execute the command under the approved test conditions.
  4. Verify that the intended request is generated.
  5. Observe whether the PLC accepts or rejects it.
  6. Verify the resulting status, message, or sequence response.
  7. Test the command under prohibited conditions.
  8. Confirm that repeated clicks do not cause unintended duplicate requests.
  9. Record the result.

8.2 Start-button testing

Condition Expected behavior
All required start conditions satisfied Start request may be accepted
Required permissive absent Start is rejected or inhibited as specified
Machine in an incompatible mode Start is rejected or inhibited as specified
Active fault prevents starting Start is rejected or inhibited as specified
Communication unavailable Command behavior follows the approved failure response
Operator lacks permission Command is unavailable or rejected according to the access design

The HMI should not be the only layer enforcing essential operating restrictions. The PLC or relevant control system must enforce the specified logic independently of the appearance of the button.

9. Momentary commands, maintained commands, and edge detection

HMI commands can use different interaction models.

Command type Typical behavior FAT check
Momentary command Request is active while the defined interaction is active Verify activation and release behavior
Pulse command Request is generated for a defined pulse or event Verify one valid event per intended action
Maintained command Value remains selected until changed Verify persistence and permitted reset behavior
Toggle command Alternates between two states Verify state indication and permitted transitions
Acknowledgement command Requests acknowledgement of an alarm or event Verify the correct acknowledgement behavior
Reset command Requests clearing of an eligible fault or latch Verify required conditions and no unintended restart

The actual implementation must follow the approved control design. A button's visual appearance does not reveal whether its PLC command is momentary, maintained, or pulsed.

Test repeated presses, screen changes during a command, and communication interruption where relevant.

10. Setpoint entry and parameter modification

Setpoint testing verifies that an operator can enter permitted values and that invalid or unauthorized changes are handled correctly.

Examples include:

  • Pressure setpoint.
  • Temperature target.
  • Conveyor speed.
  • Clamp timeout.
  • Production quantity.
  • Process duration.
  • Recipe parameters.

10.1 Required tests

  • Verify the displayed current value.
  • Enter a valid value within the allowed range.
  • Confirm the correct value reaches the intended controller tag.
  • Test the lower and upper limits.
  • Enter a value below the minimum.
  • Enter a value above the maximum.
  • Enter invalid text or an unsupported numeric format if the interface permits it.
  • Verify decimal precision and unit presentation.
  • Test unauthorized modification attempts.
  • Verify any required confirmation before applying the change.
  • Check whether a change takes effect immediately or only after a specified condition.
  • Verify that rejected values do not overwrite the last valid value.

10.2 Example

Suppose a speed setpoint permits values from 10 to 100 units.

Entered value Expected behavior
10 Accepted if the lower limit is inclusive
55 Accepted
100 Accepted if the upper limit is inclusive
5 Rejected or handled according to the specified limit behavior
110 Rejected or handled according to the specified limit behavior
Invalid text Prevented or rejected with suitable feedback

Do not assume that a rejected entry must always display the same message or preserve the input field in the same way. Verify the approved design.

11. User access and permissions

Industrial HMIs may provide different permissions for operators, maintenance personnel, engineers, and administrators.

Access control should limit actions according to the approved role matrix.

11.1 Typical permission levels

Role Typical permitted activities
Operator Monitor machine status, run permitted cycles, and acknowledge eligible alarms
Maintenance Access approved diagnostics and maintenance commands
Engineer Modify approved engineering parameters and perform authorized configuration tasks
Administrator Manage accounts and permissions where assigned

These are illustrative roles. The project-specific access matrix determines actual privileges.

11.2 FAT checks

  • Verify login and logout behavior.
  • Test each defined user role.
  • Attempt restricted actions with an unauthorized role.
  • Confirm that protected parameters cannot be modified without authorization.
  • Verify session timeout or automatic logout if required.
  • Check that logout removes the previous user's privileges.
  • Verify password handling against the approved security requirements.
  • Confirm that account or permission changes are traceable where required.

A hidden button is not a complete security boundary. The underlying command and configuration mechanisms must enforce the intended permissions.

12. HMI alarm and event integration

HMI alarm testing verifies that the interface presents alarm information correctly and supports the specified operator response.

Check:

  • Alarm text and identifier.
  • Alarm priority and classification.
  • Activation and clearing behavior.
  • Timestamp presentation.
  • Acknowledgement behavior.
  • Active-alarm list.
  • Historical alarm list.
  • Sorting and filtering.
  • Alarm details and diagnostic guidance.
  • Communication-loss indication.
  • Retention of event history where specified.

Alarm logic and alarm behavior deserve their own detailed FAT tests. HMI testing should focus on whether the interface correctly presents and handles the alarm information supplied by the control system.

13. Trends, counters, and production information

Where the HMI provides trends or production statistics, verify that the displayed information is correct and useful.

Trends

  • Correct tag source.
  • Correct engineering units.
  • Correct time axis and time range.
  • Correct sampling or update behavior.
  • Correct scaling and displayed range.
  • Correct handling of missing or invalid samples.
  • Appropriate history retention where specified.

Counters and production totals

  • Correct initial value.
  • Correct increment or decrement behavior.
  • Correct reset permissions.
  • Correct retention across restart if required.
  • Correct handling of counter limits and overflow.
  • Consistency with the PLC source.

Production and cycle information

  • Current cycle state.
  • Cycle time.
  • Good and rejected part counts.
  • Machine availability or status.
  • Recipe or product identification.
  • Relevant fault and stop information.

A trend that draws a smooth line is not necessarily correct. Verify the source tag, units, time base, and update behavior.

14. Communication-loss and stale-data testing

A communication failure can leave an HMI displaying an old value that appears current.

The interface should handle invalid or stale data according to the approved design.

Test cases

  1. Record the normal communication state and displayed values.
  2. Introduce an approved communication interruption.
  3. Observe the HMI connection status.
  4. Verify that invalid or stale data is identified as required.
  5. Check the behavior of commands during the interruption.
  6. Restore communication.
  7. Verify reconnection and data refresh.
  8. Confirm that no unintended command is executed during recovery.
  9. Record the evidence.

The correct response depends on the architecture and requirements. A value may need to be marked invalid, frozen with a clear stale-data indication, or replaced with a defined unavailable state. The HMI must not imply that an old value is a current measurement when it cannot establish validity.

15. HMI usability and display consistency

Functional correctness is essential, but the interface must also allow operators to interpret information reliably.

Check:

  • Consistent terminology and tag descriptions.
  • Readable text and units.
  • Consistent navigation and screen layouts.
  • Clear separation between commands and status indications.
  • Appropriate contrast and color use.
  • No clipped text or hidden values.
  • No overlapping objects.
  • Consistent alarm and fault presentation.
  • Clear indication of operating mode.
  • Appropriate confirmation for consequential actions where required.
  • Clear distinction between requested state and actual state.

For example, a button labeled CLAMP EXTEND may represent a command, while an indicator labeled CLAMP EXTENDED should represent feedback. Combining both into one ambiguous indicator can mislead an operator about whether the clamp was merely commanded or has actually reached its position.

16. HMI testing with simulated PLC tags

During FAT, the complete machine may not be available. HMI behavior can be tested using an approved PLC simulation, test controller, or controlled signal simulation arrangement.

The test method must preserve the distinction between interface verification and physical machine verification.

Example: clamp status display

  1. Open the clamp diagnostic screen.
  2. Record the initial PLC tag values and HMI indications.
  3. Apply the approved simulation for clamp-extended feedback.
  4. Verify the PLC tag and HMI indication.
  5. Apply the approved simulation for clamp-retracted feedback.
  6. Verify the corresponding indication.
  7. Test the defined contradictory-signal condition if applicable.
  8. Verify that the HMI presents the correct diagnostic or fault state.
  9. Restore all simulated values and confirm the final state.

If both clamp-extended and clamp-retracted feedback are active simultaneously, the expected response must be based on the approved machine logic. The HMI should present the defined fault or diagnostic behavior rather than inventing a valid physical position.

17. Worked example: HMI cycle-start test

Test ID: FAT-HMI-010

Objective: Verify that the cycle-start button generates the correct request and reflects the control system's acceptance or rejection.

Preconditions:

  • Approved HMI and PLC versions are loaded.
  • The machine is in the specified initial state.
  • Required safety conditions are satisfied.
  • Start permissives and PLC command tags can be observed.
  • The approved test method is available.

Procedure:

  1. Open the main operation screen.
  2. Verify the displayed machine mode and status.
  3. Confirm that all required start permissives are satisfied.
  4. Press the cycle-start button.
  5. Observe the HMI command tag and PLC response.
  6. Verify the expected transition into the starting sequence.
  7. Restore the initial state using the approved method.
  8. Make one required permissive unavailable.
  9. Press the cycle-start button again.
  10. Verify that the command is rejected or inhibited as specified.
  11. Record both test results and their evidence.

Expected results:

  • With valid conditions, the command is handled according to the specified start logic.
  • With a required permissive absent, the machine does not enter an unauthorized starting state.
  • The HMI displays the correct status or rejection feedback.
  • Repeated button interaction does not produce unintended operation.
  • The final machine state is known and documented.

19. Common HMI testing mistakes

  • Verifying appearance without checking tag mapping.
  • Checking only normal operating conditions.
  • Assuming a command was accepted because the button changed color.
  • Confusing command status with actual device feedback.
  • Ignoring invalid, stale, or unavailable data.
  • Failing to test unauthorized actions.
  • Allowing setpoints outside the permitted range.
  • Testing alarms only on the PLC and not on the HMI display.
  • Ignoring timestamp, unit, scaling, and rounding errors.
  • Assuming that a hidden button provides sufficient access control.
  • Failing to test communication loss and recovery.
  • Ignoring retained values and counters after restart.
  • Testing screens with simulated data but reporting physical-device verification as complete.
  • Failing to record the software revision used for the test.

20. Troubleshooting HMI test failures

Symptom Possible causes Investigation
Indicator does not change Wrong tag, communication issue, stale data, or incorrect object configuration Compare the source tag, PLC value, and HMI binding
Displayed value is incorrect Wrong scaling, data type, units, or decimal formatting Compare raw and engineering values
Button does not issue a command Incorrect binding, disabled object, permission restriction, or communication fault Check the object configuration and command tag
Command appears accepted but machine does not start Missing permissive, PLC rejection, active fault, or incorrect mode Inspect PLC acceptance logic and status feedback
Alarm does not appear Incorrect alarm mapping, trigger condition, priority configuration, or communication issue Compare the alarm source with the HMI alarm configuration
Old values remain on screen Communication failure or missing stale-data handling Check connection diagnostics and invalid-data presentation
Unauthorized user can change a parameter Incorrect role configuration or insufficient command-side enforcement Verify access controls at both interface and underlying command levels
Trend appears incorrect Wrong tag, units, time base, sampling, or scaling Compare the source data with recorded trend values
HMI does not refresh after reconnection Session, subscription, communication, or runtime issue Check reconnection diagnostics and value refresh behavior

21. Interview questions and answers

1. What is HMI testing during FAT?

It verifies screen behavior, tag mapping, operator commands, displayed values, access permissions, alarms, trends, and communication handling against approved requirements.

2. What is the difference between a command and feedback?

A command requests an action. Feedback indicates the observed or reported state of the system. A command being issued does not prove that the action completed.

3. How do you verify an HMI analog value?

Compare the source signal, PLC engineering value, HMI-displayed value, units, and accepted tolerance across representative test points.

4. How should HMI communication loss be tested?

Introduce an approved interruption, verify the connection and data-validity indications, test command behavior, restore communication, and confirm safe and correct recovery.

5. Why is role-based access testing necessary?

It verifies that operators and maintenance personnel can perform only the actions authorized for their roles and that unauthorized changes are prevented.

6. Can an HMI be used as the sole enforcement mechanism for a machine interlock?

Essential control restrictions must be enforced by the relevant control system, and safety-related functions by the appropriately designed and validated safety system. The HMI should not be the sole safeguard.

7. What is the difference between an HMI alarm and an alarm-history entry?

The active-alarm presentation indicates current alarm conditions according to the configured logic. Alarm history records events over time, subject to the system's recording and retention configuration.

8. Why should stale-data handling be tested?

Because an old value can appear plausible while no longer representing the current machine condition, potentially leading to incorrect operator decisions.

9. What evidence is required for an HMI test pass?

A record of the test action, relevant source values, observed display or command behavior, acceptance criteria, software configuration, and supporting screenshots or logs as appropriate.

10. Does passing HMI FAT prove that the machine works correctly?

No. It verifies the tested interface requirements. Sequence logic, I/O, physical actuators, safety functions, and machine performance require their own appropriate tests.

22. Final HMI FAT checklist

  • Approved HMI design and software revisions are confirmed.
  • All required screens and navigation paths are tested.
  • Indicators and displayed values match the correct tags.
  • Analog scaling, units, formatting, and limits are verified.
  • Start, stop, reset, acknowledgement, and other commands are tested.
  • Command acceptance and rejection behavior is verified.
  • User roles and protected parameters are tested.
  • Alarms, event history, and diagnostic displays are checked.
  • Trends, counters, recipes, and setpoints are tested where applicable.
  • Communication-loss, stale-data, and reconnection behavior is verified.
  • Screen usability and display consistency are reviewed.
  • Simulated-data tests are distinguished from physical-function tests.
  • Failures, evidence, retests, and software revisions are documented.
  • The final configuration and machine state are confirmed.

HMI FAT verifies that the operator receives accurate information and can issue authorized commands with predictable results. The central principle is to verify the full path from operator interaction to controller response and, where required, physical machine feedback, without claiming that one layer proves the others.
