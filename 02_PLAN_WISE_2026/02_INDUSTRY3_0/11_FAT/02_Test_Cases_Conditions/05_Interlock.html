1. Purpose of Interlock Testing in FAT

Interlock testing during Factory Acceptance Testing (FAT) verifies that a machine or automated process permits, prevents, or stops an operation according to defined equipment states, process conditions, feedback signals, and operating requirements.

An interlock prevents an operation from proceeding when a required condition is not satisfied. It may also stop an operation when a previously satisfied condition becomes false.

For example, a hydraulic clamp may be permitted to extend only when the machine is in automatic mode, the required guarding conditions are satisfied, the hydraulic system is healthy, and the sequence is in the correct state.

If any required condition is absent, the PLC must prevent the command or execute the specified response.

Interlock FAT verifies the complete functional chain:

  • The correct input or equipment state is detected.
  • The interlock condition is evaluated correctly.
  • The affected command is permitted or blocked as specified.
  • The correct equipment response occurs.
  • The operator receives the required status or diagnostic indication.
  • The interlock behaves correctly during recovery, reset, and restart.
  • The test result is traceable to the approved design requirement.

The central objective is to prove both sides of the logic: the operation is allowed when all required conditions are satisfied, and it is prevented when any required condition is not satisfied.

Testing only the blocked condition is insufficient. An interlock that permanently blocks an operation is not functioning correctly either.

2. What Is an Interlock?

An interlock is a logical or hardware-based condition that restricts an operation based on defined requirements.

Interlocks may be implemented in PLC logic, relay circuits, drive controllers, robot controllers, dedicated safety controllers, or combinations of these systems.

Typical examples include:

  • A motor cannot start when its overload fault is active.
  • A clamp cannot extend when the machine is in the wrong sequence state.
  • A CNC cycle cannot start unless the required hydraulic pressure is available.
  • A robot cannot enter a shared work area while another device occupies the protected zone.
  • A conveyor cannot transfer a component unless the downstream station is ready.
  • A drive cannot start until the required enable and permissive conditions are satisfied.

Interlocks are not limited to fault conditions. Some enforce the correct operating sequence, prevent equipment conflicts, and ensure that one operation cannot interfere with another.

3. Interlock, Permissive, Interlock Alarm, and Safety Function

These concepts must be distinguished because they can appear together in the same machine logic.

Concept Purpose Example
Permissive Condition required before an operation can start Lubrication pressure healthy before spindle start
Start interlock Prevents a start command when a required condition is false Motor start blocked while overload is active
Running interlock Initiates a defined response if a required condition becomes false during operation Conveyor stops if required downstream readiness is lost
Sequence interlock Prevents an operation from occurring in the wrong sequence state Clamp extension blocked until part presence is confirmed
Mutual exclusion Prevents incompatible operations from occurring simultaneously Two transfer mechanisms cannot enter the same shared zone
Interlock alarm Informs the operator that an interlock condition is preventing or affecting an operation Start blocked because air pressure is low
Safety function Reduces risk through a safety-related function designed and validated for that purpose Guard opening initiates the specified safety-related stop

A permissive is often part of the interlock logic, but the terminology varies between projects. Some designs use the terms interchangeably. The approved functional specification must define the intended meaning.

An interlock alarm does not perform the interlock function. It reports the condition. The actual control logic must independently enforce the required restriction.

A standard PLC interlock must not be assumed to provide personnel protection merely because it prevents machine motion. Safety-related functions require the appropriate safety architecture and separate verification and validation.

The architecture may be more distributed. For example, a PLC may issue a start request while a drive or robot controller independently checks its own enable conditions.

FAT must identify where each condition is evaluated and where the final command is authorized. A PLC command bit becoming true does not necessarily mean the motor, drive, or robot has accepted the command.

The test must verify the specified end-to-end behavior.

5. Interlock Categories

5.1 Start permissive interlocks

These prevent equipment from starting until the required conditions are satisfied.

Examples:

  • Motor overload healthy.
  • Emergency-stop system in the required state.
  • Machine in the correct operating mode.
  • Guarding conditions satisfied.
  • Lubrication pressure healthy.
  • Drive ready.
  • No active fault that prohibits starting.

FAT must verify that each required condition independently blocks the start request when false and that the operation becomes available when all required conditions are restored.

5.2 Running interlocks

These govern equipment that is already operating.

Examples:

  • Cooling flow lost during operation.
  • Lubrication pressure falls below the required limit.
  • Downstream equipment becomes unavailable.
  • A required feedback signal is lost.
  • An equipment fault occurs while the machine is running.

The required response may be a controlled stop, immediate command removal, sequence abort, or another defined action. It must come from the approved design rather than an assumption that every interlock should stop everything immediately.

5.3 Sequence interlocks

Sequence interlocks enforce the correct order of operations.

For example, a component transfer may require:

  1. Part presence confirmed.
  2. Clamp closed and feedback confirmed.
  3. Required station conditions satisfied.
  4. Transfer command permitted.
  5. Transfer completion feedback confirmed.

If the clamp feedback is absent, the transfer command must remain blocked when the specification requires that condition.

Sequence interlocks should be evaluated in the correct machine state. A condition that is relevant during one sequence step may be irrelevant during another.

5.4 Equipment and process interlocks

These enforce equipment-specific or process-specific conditions.

Examples include:

  • VFD ready before motor start.
  • CNC spindle stopped before a specified tool-change operation.
  • Hydraulic pressure within the permitted operating range.
  • Robot at the required position before a handover.
  • Temperature within the allowed range before process initiation.
  • Downstream station ready before part release.

Each interlock must reference the correct source signal, equipment, and operating condition.

5.5 Mutual-exclusion interlocks

Mutual exclusion prevents incompatible actions from occurring simultaneously.

Examples:

  • Two robots cannot enter a shared restricted operating zone at the same time.
  • Two transfer mechanisms cannot occupy the same physical space simultaneously.
  • Forward and reverse contactor commands cannot be energized together.
  • Conflicting hydraulic or pneumatic actions cannot be commanded concurrently where the design prohibits them.

FAT must test both the initial authorization and the conflict that arises when another operation requests the same resource.

For shared-zone applications, the approved coordination logic must prevent conflicting grants, including during communication loss and recovery.

5.6 Fault and recovery interlocks

These prevent restart or continued operation after certain faults until the required recovery conditions are satisfied.

Examples:

  • Drive fault must be cleared before restart.
  • A required home position must be confirmed before automatic operation.
  • A sequence abort must be reset before a new cycle.
  • Equipment must be reinitialized after a communication interruption.

FAT must verify that clearing the original fault does not automatically bypass any required reset, re-homing, or restart authorization.

6. Understanding Interlock Logic

Interlock logic is usually built from Boolean conditions, timers, equipment states, and command relationships.

6.1 AND logic

When all conditions must be true, the interlock uses AND logic.

Example:

Motor_Start_Permitted =
    Drive_Ready
    AND Overload_Healthy
    AND Lubrication_Healthy
    AND Correct_Operating_Mode
    AND No_Start_Inhibit

If any required condition is false, the start permissive becomes false.

FAT must test each condition individually. Testing only the case in which all conditions are false may not identify a missing or incorrectly connected condition.

6.2 OR logic

OR logic is used when any one of several conditions can prohibit an operation.

Example:

Motor_Start_Inhibited =
    Drive_Fault
    OR Overload_Trip
    OR Maintenance_Inhibit

The start command must be blocked if any of these conditions is true.

For FAT, activate each condition independently and verify that each produces the specified result.

6.3 Combined logic

Real interlocks commonly combine AND, OR, and NOT operations.

Example:

Clamp_Extend_Permitted =
    Automatic_Mode
    AND Part_Present
    AND Air_Pressure_Healthy
    AND NOT Clamp_Extend_Limit
    AND Sequence_State_Is_Clamp_Extending

The exact expression depends on the equipment design. The key requirement is that every condition has a defined meaning and is evaluated in the intended context.

6.4 Truth-table testing

A truth table provides a systematic way to verify the logic.

For a start permissive requiring three conditions, the expected behavior is:

Drive ready Overload healthy Lubrication healthy Start permitted
TRUE TRUE TRUE TRUE
FALSE TRUE TRUE FALSE
TRUE FALSE TRUE FALSE
TRUE TRUE FALSE FALSE
FALSE FALSE TRUE FALSE
FALSE TRUE FALSE FALSE
TRUE FALSE FALSE FALSE
FALSE FALSE FALSE FALSE

This table assumes all three conditions are mandatory and that no additional start restrictions exist. Real FAT must include all relevant conditions and any separately specified mode or sequence restrictions.

Truth-table testing is particularly useful when several permissives are combined in a single PLC rung, function block, or state transition.

7. Interlock Matrix and Cause-and-Effect Documentation

An interlock matrix defines which conditions affect which commands or equipment actions.

A simplified example:

Condition Conveyor start Clamp extend Automatic cycle start
Drive fault Blocked No effect unless specified Blocked if conveyor is required
Air pressure low No effect unless specified Blocked Blocked if clamp operation is required
Part absent No effect unless specified Blocked if required by design Blocked
Wrong sequence state Blocked where applicable Blocked Blocked
Maintenance inhibit active Blocked according to scope Blocked according to scope Blocked according to scope

The phrase "no effect unless specified" is intentional. A fault affecting one mechanism should not automatically be assumed to affect every machine function.

An interlock matrix may be maintained as part of a cause-and-effect matrix, functional specification, control narrative, or separate interlock list.

The FAT engineer should compare the approved matrix against:

  • PLC logic.
  • HMI status indications.
  • Equipment command paths.
  • Alarm and diagnostic behavior.
  • Reset and restart conditions.
  • Relevant safety documentation.

A mismatch between these documents must be resolved through the approved change process, not silently corrected during testing.

8. Interlock Register

The interlock register identifies each interlock and its intended behavior.

Field Purpose
Interlock ID Unique reference
Equipment tag Affected machine or mechanism
Interlock description Clear explanation of the restriction
Trigger condition Signal or logical condition that activates the interlock
Affected command Command or operation that is blocked or interrupted
Required response Block start, stop operation, abort sequence, or other defined response
Operating mode Modes in which the interlock applies
Recovery condition Condition required before normal operation can resume
Reset requirement Whether reset is required and under what conditions
HMI indication Status message or indication
Alarm reference Related alarm ID, if applicable
Requirement reference Approved specification or matrix reference
Safety classification Identifies whether separate safety requirements apply
Test case ID Associated FAT test case
Test result Actual result and status

Every interlock should have a clear source, a defined effect, and a verifiable expected result.

Ambiguous descriptions such as Machine protection active are not sufficient unless the register also defines the actual conditions and affected actions.

9. Interlock FAT Preparation

9.1 Required documents

Before testing, obtain the relevant approved revisions of:

  • Functional specification or control narrative.
  • Interlock register.
  • Interlock matrix or cause-and-effect matrix.
  • PLC I/O list.
  • Electrical schematics.
  • Equipment sequence diagrams or state descriptions.
  • Drive and robot interface definitions.
  • HMI status and alarm lists.
  • Reset and restart philosophy.
  • Communication architecture.
  • Applicable safety requirements and validation procedures.
  • FAT test procedure and acceptance criteria.

9.2 Pre-test checklist

  • Confirm PLC, HMI, drive, and robot software revisions where applicable.
  • Confirm the interlock matrix matches the approved specification.
  • Identify each command affected by the interlock.
  • Confirm input and feedback signal mapping.
  • Establish the approved simulation method.
  • Confirm the initial machine state and test mode.
  • Verify that simulated commands cannot cause unexpected motion.
  • Identify interlocks that belong to safety-related functions.
  • Confirm required authorization for overrides or temporary inhibits.
  • Record the original configuration and test setup.

9.3 Safe test conditions

Use approved test modes, simulation tags, controller simulation, or other authorized methods.

Do not defeat guards, bypass safety-rated circuits, or disable protective devices casually to test a standard interlock. Where a safety-related condition must be verified, use the approved safety test procedure and authorized personnel.

If the test involves real equipment, define how motion, stored energy, unexpected starts, and personnel access will be controlled.

10. Step-by-Step Interlock FAT Procedure

Step 1: Select the interlock

Identify the interlock ID, affected equipment, trigger conditions, affected command, expected response, operating mode, and recovery requirements.

Step 2: Establish the normal state

Set all relevant conditions to the required healthy state.

Confirm that the equipment is eligible to operate according to the approved specification. If the command remains blocked, investigate the initial state before proceeding.

Step 3: Request the operation

Issue the relevant command through the approved simulation or test interface.

Confirm that the command is accepted when the required permissives are satisfied.

Where relevant, distinguish between:

  • HMI command request.
  • PLC command output.
  • Drive or robot command acceptance.
  • Equipment feedback confirming operation.

These are separate points in the control chain.

Step 4: Introduce the interlock condition

Change one trigger condition to the abnormal or prohibited state.

For example, set Drive_Ready to FALSE while leaving other conditions healthy.

Step 5: Verify the affected operation

Check whether the operation is blocked or interrupted exactly as specified.

For a start interlock, verify that the start command is not accepted. For a running interlock, verify the defined response to the loss of the required condition.

Do not assume every interlock must immediately stop every machine movement.

Step 6: Verify status and diagnostics

Confirm that the HMI shows the correct interlock status, affected equipment, and explanatory message if required.

Verify the related alarm separately if the design includes one.

Step 7: Test recovery

Restore the trigger condition to normal.

Confirm whether the interlock clears automatically or requires acknowledgement, reset, re-homing, or a new start request.

Verify that clearing the condition does not produce an unintended automatic restart.

Step 8: Test boundary and combination conditions

Where applicable, test timers, thresholds, mode changes, conflicting requests, and combinations of multiple interlock conditions.

For analog permissives, verify the specified threshold and hysteresis. For sequence interlocks, test the relevant transitions.

Step 9: Record evidence

Record the actual inputs, command states, equipment feedback, HMI indication, response timing, and final state.

Step 10: Restore the system

Remove temporary forces and test overrides. Confirm that all relevant conditions, modes, and commands have returned to the approved state.

12. Practical Example: Motor Start Interlock

Consider a motor that requires the following conditions before starting:

  • Drive ready.
  • Overload healthy.
  • Lubrication pressure healthy.
  • Correct operating mode.
  • No active start inhibit.

Conceptual logic:

Motor_Start_Permitted =
    Drive_Ready
    AND Overload_Healthy
    AND Lubrication_Healthy
    AND Correct_Operating_Mode
    AND NOT Start_Inhibit

Motor_Start_Command =
    Start_Request
    AND Motor_Start_Permitted

The exact logic may differ depending on the design, drive interface, and control architecture.

FAT execution

  1. Set all permissives to healthy.
  2. Issue the start request and verify that the command is permitted.
  3. Remove the drive-ready condition and issue the start request again.
  4. Verify that the start command remains blocked.
  5. Restore drive readiness.
  6. Set overload healthy to FALSE and verify that the start is blocked.
  7. Repeat for lubrication pressure, operating mode, and start inhibit.
  8. Restore all conditions and verify the expected recovery behavior.
  9. If the motor is simulated, verify the simulated run feedback and command-state relationship.
  10. Record each individual result.

The critical point is that every mandatory permissive must be independently verified. If the PLC logic accidentally omits the lubrication condition, a test that only checks the drive-ready condition will not detect the defect.

13. Practical Example: Clamp and Transfer Interlock

Assume a station must confirm part presence and clamp closure before transferring the component.

The approved logic may require:

Transfer_Permitted =
    Part_Present
    AND Clamp_Closed_Feedback
    AND Downstream_Ready
    AND Correct_Sequence_State
    AND NOT Transfer_Inhibit

FAT execution

  1. Set part presence, clamp feedback, downstream readiness, and sequence state to their required values.
  2. Request transfer and verify that the command is permitted.
  3. Set Part_Present to FALSE and verify that transfer is blocked.
  4. Restore part presence and set Clamp_Closed_Feedback to FALSE.
  5. Verify that transfer remains blocked.
  6. Restore clamp feedback and set Downstream_Ready to FALSE.
  7. Verify that transfer remains blocked.
  8. Restore all conditions and verify that transfer becomes eligible again.
  9. Test the wrong sequence state and the transfer inhibit separately.
  10. Verify HMI indication and any associated alarm.

The exact response must match the machine design. For example, downstream unavailability might block only the transfer request rather than stopping the current station immediately.

14. Start Interlocks Versus Running Interlocks

One of the most important FAT distinctions is whether an interlock applies only to starting or also to continued operation.

Question Start interlock Running interlock
When is it evaluated? Before or during command acceptance During operation, and sometimes before start as well
Primary purpose Prevent an invalid start Prevent continued operation under a prohibited condition
Typical example Drive not ready Required lubrication pressure lost during operation
Expected response Start blocked Defined stop, abort, or other specified response
Recovery test Verify that starting becomes available when conditions are restored Verify safe recovery and the required restart procedure

Some interlocks apply in both states. The specification must define whether a condition prevents starting, interrupts operation, or does both.

For a running interlock, FAT should verify the response time if specified. It should also verify the final state, fault indication, and restart restrictions.

15. Sequence Interlocks and State Machines

Sequence interlocks are commonly implemented using state machines, step logic, or sequence control blocks.

For example:

IDLE
  |
  | Start accepted and initial permissives healthy
  v
CLAMPING
  |
  | Clamp-closed feedback confirmed
  v
TRANSFER_READY
  |
  | Downstream ready and transfer permitted
  v
TRANSFERRING
  |
  | Transfer-complete feedback confirmed
  v
COMPLETE

The interlock logic must prevent transitions when required conditions are not satisfied.

FAT should verify:

  • Each transition occurs only from the permitted state.
  • Required feedback is checked before advancing.
  • Commands cannot be issued out of sequence.
  • A timeout or missing feedback produces the specified response.
  • Recovery after a sequence abort follows the approved reset or reinitialization procedure.
  • A stale feedback signal cannot incorrectly satisfy a new step.
  • Repeated start requests do not cause duplicated or conflicting commands.

A sequence interlock test is incomplete if it checks only whether a command is blocked. The associated state transition and feedback handling must also be verified.

16. Interlock Recovery, Reset, and Restart

Interlock recovery is a major source of defects because the trigger condition may clear while the machine remains in an abnormal state.

The design may require one or more of the following:

  • Automatic removal of the interlock when the condition becomes healthy.
  • Operator acknowledgement.
  • Manual reset.
  • Re-homing of a mechanism.
  • Sequence reinitialization.
  • A fresh start request.
  • Verification that all restart permissives are satisfied.

These actions are not interchangeable.

Required recovery tests

  1. Activate the interlock.
  2. Confirm the expected restriction.
  3. Restore the initiating condition.
  4. Verify whether the interlock clears automatically.
  5. If reset is required, attempt reset before satisfying the conditions and verify the expected rejection.
  6. Satisfy the required reset conditions and perform the approved reset.
  7. Confirm the correct final state.
  8. Verify that equipment does not restart unexpectedly.
  9. Issue a new start request where required.
  10. Confirm that the operation proceeds only when all conditions are satisfied.

A machine that resumes motion immediately when a fault signal disappears may violate the approved restart philosophy. Recovery behavior must be explicitly tested rather than inferred from normal operation.

17. Mode-Dependent Interlocks

Interlocks may apply differently in automatic, manual, setup, maintenance, and service modes.

For example, automatic mode may require all sequence conditions, while a maintenance mode may allow a restricted manual operation under separately defined controls.

FAT must not assume that a mode change automatically disables an interlock.

Test the approved behavior for each applicable mode:

  • Automatic operation.
  • Manual operation.
  • Setup or teach mode.
  • Maintenance mode.
  • Fault recovery mode.

Verify mode selection, command authorization, and transitions between modes. Check that a command requested in one mode cannot be executed unexpectedly after the mode changes.

Any exception to a normal interlock must be explicitly defined, authorized, and verified. Safety-related requirements remain applicable regardless of a standard PLC operating mode.

18. Communication Failure and Stale Feedback

Interlocks often depend on feedback from remote I/O, drives, robots, or other controllers. Communication loss can make a signal invalid or stale.

For example, a transfer permissive may depend on Downstream_Ready. If communication is lost while the last received value is TRUE, the system must not silently treat that old value as reliable indefinitely.

FAT should verify:

  • How communication failure is detected.
  • Whether the affected feedback becomes invalid or unavailable.
  • Whether the relevant command is blocked.
  • Whether a running operation receives the defined response.
  • Whether the HMI indicates the fault.
  • Whether recovery restores normal behavior.
  • Whether reset or reinitialization is required.
  • Whether stale values can accidentally authorize an operation.

The expected response depends on the equipment and risk assessment. A communication fault must not be treated as equivalent to a healthy feedback signal unless that behavior is explicitly justified by the approved design.

19. Interlock Alarm and HMI Verification

The interlock logic and its HMI indication must be tested separately.

A typical HMI may display:

  • Operation blocked.
  • Required permissive missing.
  • Interlock active.
  • Equipment fault.
  • Reset required.
  • Equipment unavailable.
  • Sequence transition inhibited.

For every relevant interlock, verify:

  • The correct equipment is identified.
  • The active condition is accurately displayed.
  • The message explains why the operation is blocked, where required.
  • The status updates when the condition changes.
  • The HMI does not indicate permission when the PLC interlock is active.
  • Any related alarm is generated according to the approved alarm configuration.
  • Reset and acknowledgement controls behave correctly.
  • Restricted controls are available only to authorized users.

An HMI indication is not proof of effective command blocking. Verify the actual control behavior as well as the display.

21. Pass, Fail, Blocked, and Not Applicable

Result Meaning Required action
Pass All specified interlock criteria are satisfied Record evidence and close the test
Fail Actual behavior violates a requirement Raise a deviation and correct the defect
Blocked A prerequisite prevents test execution Document the reason and dependency
Not Applicable The test does not apply to the approved configuration Record justification and obtain approval where required

Examples of failure include:

  • A command is accepted despite a mandatory permissive being false.
  • The wrong equipment is blocked.
  • A running interlock fails to initiate the required response.
  • Reset is accepted while prohibited conditions remain.
  • The HMI indicates a healthy permissive when the source is invalid.
  • A mode change bypasses a restriction that must remain effective.

Do not classify an interlock as Pass simply because an alarm appeared. The required command restriction or equipment response must also be demonstrated.

22. Deviation Management and Regression Testing

When an interlock test fails, document the discrepancy against the approved requirement.

Record the interlock ID, affected equipment, input states, command request, expected response, actual response, software revision, evidence, corrective action, and retest result.

Common causes include:

  • Missing PLC logic condition.
  • Incorrect Boolean operator.
  • Wrong signal mapping.
  • Incorrect normal-state assumption.
  • Wrong sequence-state reference.
  • Inadequate handling of invalid communication data.
  • Incorrect reset logic.
  • Inconsistent HMI status mapping.

After correcting the defect, repeat the failed test and the relevant regression tests.

For example, if a shared function block is changed to correct start-permissive logic, test the other equipment instances that use the same block. If the mutual-exclusion logic is modified, retest the competing commands and the relevant recovery scenarios.

Only the corrected and approved configuration should be used for the final FAT acceptance record.

23. Common Interlock FAT Mistakes

  • Testing only the blocked condition and not the permitted condition.
  • Failing to test each permissive independently.
  • Confusing the HMI command request with the actual equipment command.
  • Treating an alarm as proof that the interlock works.
  • Ignoring running interlocks.
  • Assuming all interlocks should stop the entire machine.
  • Ignoring sequence state and operating mode.
  • Failing to test reset and restart behavior.
  • Assuming restored feedback automatically makes restart permissible.
  • Using stale feedback to simulate a healthy condition.
  • Treating standard PLC logic as a safety-rated function.
  • Disabling protective devices without approved authorization.
  • Failing to restore temporary forces or overrides.
  • Accepting undocumented changes to the interlock matrix.
  • Closing a failed test without regression testing affected logic.

24. Troubleshooting Interlock Failures

Symptom Possible cause Investigation
Operation remains blocked with all conditions healthy Another permissive is false, incorrect mode, stale state, or wrong signal mapping Check all permissives, operating state, and source values
Operation proceeds despite an interlock Missing logic condition, incorrect Boolean expression, alternate command path Trace the command path and test each trigger independently
Wrong equipment is blocked Incorrect tag mapping or shared logic reference Compare the matrix, PLC logic, and equipment tags
Interlock activates in the wrong sequence step Incorrect state condition or sequence-state mapping Check state transitions and the relevant condition
Interlock does not respond to feedback loss Incorrect signal handling, missing timeout, or stale data Inspect communication quality, feedback logic, and timeout behavior
Interlock clears but restart remains blocked Reset or reinitialization requirement remains unsatisfied Check the recovery specification and reset conditions
Equipment restarts unexpectedly Incorrect automatic-restart behavior or retained command Review restart philosophy, command retention, and state transitions
HMI says ready while start is blocked Incorrect status mapping or missing diagnostic Compare HMI indication with actual PLC permissive states
Interlock blocks too many functions Shared permissive or overly broad inhibit logic Trace the affected command scope against the approved matrix
Conflicting mechanisms operate together Incomplete mutual-exclusion logic or race condition Test simultaneous requests and resource-grant logic
Fault persists after communication recovery Stale fault state or reset requirement Verify source recovery, state restoration, and reset logic

The most effective troubleshooting method is to trace the interlock from its source condition through the logic to the affected command, then verify the expected equipment response.

25. Interlock FAT Completion Checklist

Design and configuration

  • Approved interlock register and matrix are available.
  • PLC logic matches the approved requirements.
  • Each interlock has a defined trigger and affected operation.
  • Required operating modes and sequence states are identified.
  • Related alarms and HMI indications are defined.

Functional testing

  • Operations are permitted when all required conditions are healthy.
  • Each mandatory permissive has been tested independently.
  • Start and running interlocks have been tested as applicable.
  • Sequence interlocks are verified at the relevant state transitions.
  • Mutual-exclusion behavior is tested where applicable.
  • Communication loss and invalid feedback are tested where applicable.
  • Reset, recovery, and restart behavior are verified.

Safety and closure

  • Safety-related functions are identified and handled under their approved validation process.
  • Test simulation and override methods are authorized.
  • No unintended motion or unsafe restart occurs during testing.
  • Temporary forces and overrides are removed.
  • Deviations and regression tests are complete.
  • Evidence and software revisions are retained.
  • Final test results are reviewed and approved.

26. Interview Questions and Answers

Q1. What is an interlock in industrial automation?

An interlock is a condition or logic function that prevents or restricts an operation when defined requirements are not satisfied. It can also initiate a specified response when a required condition is lost during operation.

Q2. What is the difference between a permissive and an interlock?

A permissive is a condition required to allow an operation. An interlock is the restriction or control function that prevents or limits the operation when its requirements are not met. Project terminology may use these terms differently.

Q3. How do you test an interlock during FAT?

Identify the approved requirement, establish the normal state, verify operation is permitted, activate each interlock condition independently, verify the required restriction, restore the condition, test reset and restart behavior, and record the results.

Q4. Why must every permissive be tested independently?

A combined test may fail to reveal a missing or incorrectly mapped condition. Independent testing confirms that each mandatory condition has the intended effect.

Q5. What is the difference between a start interlock and a running interlock?

A start interlock prevents an operation from starting. A running interlock governs what happens if a required condition becomes false while equipment is already operating.

Q6. What is a mutual-exclusion interlock?

It prevents incompatible operations from occurring simultaneously, such as two mechanisms entering the same shared physical zone.

Q7. What happens when an interlock condition becomes healthy again?

The result depends on the approved recovery philosophy. The interlock may clear automatically or require reset, re-homing, sequence reinitialization, or a new start request.

Q8. How do you test a sequence interlock?

Place the sequence in the relevant state, attempt the operation with the required condition absent, and verify that the command or transition is blocked. Restore the condition and verify the intended transition and recovery behavior.

Q9. Why is communication failure important in interlock testing?

Communication failure can make feedback unavailable or stale. FAT must prove that invalid data cannot incorrectly authorize an operation and that the specified fault response occurs.

Q10. Does a PLC interlock provide personnel safety?

Not automatically. Personnel protection requires appropriately designed and validated safety-related functions. A standard PLC interlock should not be treated as equivalent to a safety function without evidence that the applicable safety requirements are met.

Q11. What is an interlock matrix?

It is a structured document mapping triggering conditions to affected commands, equipment responses, and related indications. It provides a traceable reference for implementation and FAT.

Q12. Why test reset and restart behavior separately?

Removing the initiating fault does not necessarily satisfy every recovery condition. Separate tests verify that reset permissions, reinitialization, and restart restrictions work as designed.

Q13. How do you handle an interlock FAT failure?

Record the expected and actual behavior, identify the affected requirement and software revision, raise a deviation, correct the defect through change control, and repeat the failed test plus relevant regression tests.

27. Final Engineering Principle

An interlock is effective only when the correct condition reliably controls the correct operation under the correct operating circumstances.

FAT must prove that required operations are permitted, prohibited operations remain blocked, running equipment responds as specified, and recovery does not bypass the intended restrictions. The PLC logic, interlock matrix, equipment behavior, HMI status, and approved documentation must all agree.
