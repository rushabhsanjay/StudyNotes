1. Definition of I/O simulation

I/O simulation is the controlled generation or substitution of input and output signals during testing to verify that a machine's control system responds correctly without necessarily requiring the complete production process to run.

In a PLC-controlled machine, the control program receives signals from sensors and other devices, processes logic, and commands actuators. During FAT, some field devices may be unavailable because the machine is still at the supplier's facility, connected equipment has not arrived, or operating the actual mechanism would be unsafe or impractical.

I/O simulation allows the engineer to verify signal mapping, logic response, interlocks, alarms, diagnostics, and selected sequence conditions under controlled test conditions.

The critical distinction is that simulating an I/O signal does not automatically prove that the physical device, wiring, or complete machine function works correctly.

For example, forcing a PLC input tag to TRUE may prove that the program responds to that value. It does not prove that the installed sensor detects the target, that the cable is intact, or that the actual input module receives the correct electrical signal.

2. Why I/O simulation is used during FAT

  • Verify PLC input mapping and output command logic.
  • Test machine behavior when a sensor changes state.
  • Verify permissives, interlocks, alarms, and fault handling.
  • Simulate unavailable external equipment and interface signals.
  • Verify HMI indications and diagnostic messages.
  • Test signal-loss and abnormal-input scenarios.
  • Verify analog scaling and threshold logic.
  • Exercise control logic before the complete mechanical system is available.
  • Reduce unnecessary physical movement during early testing.
  • Identify control-system defects before shipment.

I/O simulation is especially valuable when a machine has many sensors, pneumatic actuators, drives, robots, or upstream and downstream equipment that cannot all operate together during FAT.

3. The I/O signal path

A typical industrial signal passes through several layers. The simulation method determines which layers are actually being tested.

Physical field device
        ↓
Field wiring and electrical signal
        ↓
PLC input module or communication interface
        ↓
PLC input image or process data
        ↓
Control logic and interlocks
        ↓
PLC output command
        ↓
Output module or communication interface
        ↓
Field wiring and actuator
        ↓
Physical machine response

Different simulation methods bypass different portions of this path.

For example:

  • A PLC software force can bypass the physical sensor and its electrical signal path.
  • An electrical signal simulator can test the input circuit and module, but may bypass the installed field sensor.
  • A simulated output load may verify output behavior without proving actual actuator movement.
  • A virtual device model may simulate several related signals but cannot independently prove physical wiring or mechanical performance.

The test record must identify the simulation method so the acceptance evidence is not overstated.

4. Types of I/O simulation

Method What is simulated What can be verified Main limitation
PLC software forcing A selected PLC variable or I/O value Logic response to the forced value May bypass field wiring and input hardware
Electrical input simulation An electrical signal at an approved test point Selected input circuit and module behavior Does not prove the installed sensor itself
Physical device actuation Actual sensor or switch operation Device response, wiring, input module, and logic Requires suitable physical access and safe conditions
Output simulation An output command or substitute load Output logic and selected electrical behavior May not prove actuator movement
Communication-based simulation Data exchanged with another controller or device Interface mapping, status handling, and communication logic Depends on simulator fidelity and interface coverage
Virtual device simulation A modeled device or process Coordinated logic and selected process scenarios Accuracy depends on model completeness
Analog signal simulation A controlled voltage, current, or numerical value Scaling, thresholds, range checks, and alarms May bypass the actual transmitter or sensor

The appropriate method depends on the requirement being verified. A software-only test may be sufficient for a logic requirement, while an electrical or physical test is needed for requirements concerning wiring, sensor operation, or actuator response.

5. Digital input simulation

A digital input typically represents two logical states, such as ON/OFF, OPEN/CLOSED, or PRESENT/ABSENT.

Examples include:

  • Clamp extended.
  • Clamp retracted.
  • Part present.
  • Door closed.
  • Drive ready.
  • Robot cycle complete.
  • Pressure switch healthy.
  • Guard locking confirmed.

5.1 Example: part-present sensor

Assume a photoelectric sensor indicates whether a component is present.

Test condition Expected PLC state Expected control behavior
Part absent Part_Present = FALSE Cycle start remains inhibited if part presence is required
Part present Part_Present = TRUE Part-presence permissive becomes satisfied
Signal remains absent Part_Present = FALSE Defined timeout or missing-part response occurs if specified
Signal changes unexpectedly during the cycle Depends on the approved sequence Defined fault response or controlled stop occurs

The precise response must come from the approved functional specification. Not every input changing unexpectedly should trigger the same alarm or stop behavior.

5.2 Test procedure

  1. Identify the physical signal, PLC address, tag name, and relevant requirement.
  2. Confirm the approved simulation method and safe operating mode.
  3. Record the initial input state and sequence state.
  4. Apply the test condition using the authorized method.
  5. Observe the raw input, processed tag, permissive, and sequence response.
  6. Compare actual behavior with the expected result.
  7. Capture the relevant values and diagnostic evidence.
  8. Restore the input to its normal state.
  9. Confirm that no temporary force or test override remains.
  10. Record the result and any deviations.

6. Digital output simulation

Digital outputs command devices such as solenoid valves, contactors, indicator lamps, and relay interfaces.

Examples include:

  • Clamp extend valve.
  • Conveyor motor run request.
  • Tower lamp output.
  • Part-eject solenoid.
  • Robot start request.
  • Fixture release command.

Output testing must distinguish between a logical command and a physical response.

For example, if Clamp_Extend_Cmd = TRUE, the PLC may have issued the intended command. However, this alone does not prove that the output module switched, the wiring carried the signal, the solenoid energized, or the clamp moved.

6.1 Output verification layers

Verification layer Observation What it demonstrates
Control logic PLC command tag Logic generated the intended command
Output hardware Module channel indication or suitable measurement Selected output-channel behavior
Electrical circuit Approved voltage or current measurement Electrical signal at the measured point
Actuator Solenoid or motor response Physical device response
Mechanism Actual clamp or conveyor movement Mechanical behavior under test conditions

6.2 Safe output simulation

  • Verify the risk assessment and approved test arrangement before energizing an output.
  • Prevent unintended movement using the approved isolation, guarding, or controlled test setup.
  • Confirm that the selected output is connected to the intended device.
  • Use an approved substitute load when appropriate.
  • Verify electrical ratings and circuit protection before connecting test equipment.
  • Do not disconnect or bypass safety-related circuits merely to make a test easier.
  • Restore normal connections and verify the final state before release.

An output can be logically correct and physically dangerous. The test method must account for both facts.

7. Analog input simulation

Analog signals represent continuously varying quantities, such as pressure, temperature, position, flow, or force.

Common industrial signal ranges include:

  • 4–20 mA
  • 0–20 mA
  • 0–10 V
  • 1–5 V

The correct range depends on the instrument and input module specification.

For a transmitter configured to represent 0 to 100 bar over a 4–20 mA range, the engineering value is calculated as:

\[ P = \frac{I - 4}{20 - 4}\times 100 \]

Where:

  • \(P\) is the calculated pressure in bar.
  • \(I\) is the measured current in mA.
  • The transmitter's lower range value is 0 bar.
  • The transmitter's upper range value is 100 bar.

Example values:

Input current Expected engineering value
4 mA 0 bar
8 mA 25 bar
12 mA 50 bar
16 mA 75 bar
20 mA 100 bar

These values assume ideal linear scaling. Actual acceptance criteria must account for the specified accuracy, module resolution, transmitter tolerances, and any documented calibration offsets.

7.1 Analog I/O FAT checks

  • Verify the configured input range.
  • Verify raw input representation.
  • Verify engineering-unit scaling.
  • Check the lower and upper range values.
  • Test representative intermediate values.
  • Verify alarm thresholds and hysteresis where specified.
  • Test out-of-range and wire-break diagnostics where supported.
  • Confirm filtering and response-time behavior if required.
  • Check units, decimal places, and displayed values on the HMI.
  • Record the simulator or instrument used and its calibration status when applicable.

7.2 Example: pressure alarm

Suppose a pressure alarm must activate when pressure falls below 20 bar.

The test should apply a series of controlled input values around the specified threshold and verify the actual alarm behavior.

Simulated pressure Expected behavior
30 bar Low-pressure alarm inactive
22 bar Low-pressure alarm inactive
19 bar Low-pressure alarm active if the configured threshold is 20 bar and no delay or hysteresis changes the result
15 bar Low-pressure alarm active
25 bar after recovery Alarm behavior follows the defined reset threshold and acknowledgement rules

If the design specifies hysteresis, a delay, or a latching alarm, the expected results must include those details. Otherwise, a test may incorrectly classify valid behavior as a failure.

8. Analog output simulation

Analog outputs command devices such as control valves, speed references, positioners, and other process-control equipment.

For example, a 4–20 mA output may represent a 0–100% valve command.

\[ \text{Command percentage} = \frac{I - 4}{20 - 4}\times 100 \]
Output current Nominal command
4 mA 0%
8 mA 25%
12 mA 50%
16 mA 75%
20 mA 100%

During FAT, verify the requested command, configured output range, measured electrical output where required, and correct scaling.

A 100% command does not prove that the physical valve reaches 100% travel. That requires appropriate feedback or a physical stroke test.

9. PLC forcing: purpose, controls, and limitations

A PLC force overrides the normal value of a selected variable or I/O point, depending on the controller and programming environment.

Forces can help test rare conditions, missing feedback, fault recovery, or external signals that are unavailable during FAT. They can also produce misleading results or unexpected machine movement if used carelessly.

9.1 Force-control requirements

Before applying a force:

  1. Confirm that forcing is permitted by the project procedure.
  2. Identify the exact controller, tag or address, and signal function.
  3. Review the logic that consumes the signal and any related output behavior.
  4. Confirm the machine state and required safety controls.
  5. Obtain the required authorization.
  6. Record the reason, expected duration, and responsible person.
  7. Apply the force only through the approved engineering workflow.
  8. Monitor the expected response and record evidence.
  9. Remove the force immediately when it is no longer needed.
  10. Verify the controller's force status and document the final state.

The exact implementation of forcing differs by PLC family and software version. Follow the manufacturer's documentation and site procedures.

9.2 Critical limitations

  • A forced input may not reproduce the electrical behavior of a real sensor.
  • Forcing a raw input may not test field wiring or module diagnostics.
  • Forcing a processed program tag may bypass multiple layers of logic.
  • A force may remain active beyond the intended test if it is not removed and verified.
  • A forced permissive can conceal a genuine defect.
  • A forced safety-related signal can create severe risk and must never be treated as an ordinary troubleshooting shortcut.

Never use an I/O force to claim that a safety function has passed. Safety-function verification requires the approved validation method, appropriate test conditions, and competent personnel. Safety PLCs and safety circuits must be handled under their applicable procedures.

10. Simulating external equipment and inter-machine signals

Machines often exchange signals with robots, conveyors, leak testers, vision systems, or upstream and downstream stations.

Typical handshake signals include:

  • Request
  • Ready
  • Busy
  • Complete
  • Fault
  • Acknowledge
  • Part_Present
  • Cycle_Allowed

During FAT, the actual external equipment may be unavailable. A simulator can provide the expected interface behavior.

10.1 Example: robot handshake

A simplified exchange may follow this order:

PLC confirms station ready
        ↓
PLC sends Robot_Start_Request
        ↓
Robot simulator acknowledges request
        ↓
Robot simulator sets Robot_Busy
        ↓
Robot simulator completes the modeled operation
        ↓
Robot simulator clears Robot_Busy
        ↓
Robot simulator sets Robot_Complete
        ↓
PLC verifies completion and continues the sequence

The actual interface contract may require additional signals, edge detection, timeouts, reset rules, and fault handling.

10.2 Required handshake tests

  • Normal request and acknowledgement.
  • Delayed acknowledgement.
  • Missing acknowledgement.
  • Completion signal arriving too early.
  • Busy signal remaining active too long.
  • Communication loss during a request.
  • Fault signal during operation.
  • Reset and recovery after timeout.
  • Repeated requests and duplicate messages.
  • Restart with signals in an unexpected state.

For every case, define the expected sequence state, timeout behavior, alarm, and recovery requirement.

A simulator must not automatically generate perfect responses for every request if the purpose of the test is to verify failure handling.

11. Signal mapping and I/O list verification

An I/O list connects engineering intent to the configured control-system signals.

A typical entry includes:

  • Signal tag.
  • Signal description.
  • Signal type.
  • PLC or remote I/O address.
  • Module and channel.
  • Electrical characteristics.
  • Normal state.
  • Fail-safe or fault-state definition where applicable.
  • HMI indication.
  • Alarm association.
  • Test method.
  • Requirement reference.

11.1 Example I/O verification record

Signal tag Signal type Expected mapping Test observation
DI_CLAMP_EXT Digital input Clamp extended feedback Correct PLC tag changes state
DI_CLAMP_RET Digital input Clamp retracted feedback Correct PLC tag changes state
DO_CLAMP_EXT Digital output Clamp extend command Correct output command is generated
AI_PRESSURE Analog input Pressure transmitter Engineering value matches test input within tolerance
DO_LAMP_RED Digital output Red fault indicator Indicator command and physical response verified as required

The precise address and module/channel mapping must come from the approved drawings and I/O list. Never infer a PLC address from a tag name alone.

12. Fault and abnormal-condition simulation

I/O simulation is particularly useful for testing how the control system handles abnormal conditions.

Possible scenarios include:

  • Sensor signal permanently OFF.
  • Sensor signal permanently ON.
  • Sensor chatter or repeated state changes.
  • Invalid analog range.
  • Broken-wire indication.
  • Loss of communication.
  • Missing device-ready signal.
  • Unexpected feedback.
  • Conflicting sensor states.
  • Signal becoming invalid during a cycle.

For each scenario, specify:

  1. The fault condition.
  2. How the condition is introduced safely.
  3. The initial machine state.
  4. The expected detection mechanism.
  5. The expected alarm or diagnostic.
  6. The expected machine response.
  7. The required recovery method.
  8. The evidence and acceptance criteria.

Fault simulation should test the defined fault response, not merely prove that an alarm text can be displayed.

13. Test setup and equipment

Depending on the signal type and test scope, the setup may require:

  • PLC programming software.
  • HMI engineering or runtime software.
  • Approved signal generators.
  • Calibrated process meters or loop calibrators.
  • Multimeters rated for the intended circuit.
  • Approved test fixtures and substitute loads.
  • Network diagnostics and communication simulators.
  • Current electrical drawings and I/O lists.
  • Controller backups and approved software revisions.
  • Test sheets or electronic result-recording tools.

Before using an instrument, verify its suitability, range, resolution, connection method, and calibration status where required.

Do not connect a current source, voltage source, or substitute load directly to an unknown circuit. Confirm the module and device specifications first.

15. Worked example: digital input mapping

Objective: Verify that the simulated clamp-extended input is correctly mapped and interpreted by the PLC program.

Test identification: FAT-IO-001

Preconditions:

  • Approved test configuration is loaded.
  • Machine is in the authorized test mode.
  • The correct signal is identified in the I/O list.
  • The approved simulation method is available.
  • Relevant outputs are controlled to prevent unintended movement.

Procedure:

  1. Record the initial raw input and processed tag values.
  2. Apply the approved test condition representing clamp extended.
  3. Observe the input module or controller input representation, as applicable.
  4. Observe the associated program tag.
  5. Observe the related permissive or sequence condition.
  6. Compare all observations against the approved signal definition.
  7. Capture evidence and record the result.
  8. Restore the input and verify the expected normal-state behavior.
  9. Confirm that no force or temporary override remains.

Acceptance criteria:

  • The intended signal changes state correctly.
  • The correct program tag responds.
  • The associated logic responds as specified.
  • No unrelated signal is unintentionally affected.
  • The system is restored to the defined final state.

If the test uses software forcing, the result proves the relevant logic response to the forced value. It does not independently verify the installed sensor or electrical input circuit.

16. Worked example: analog scaling

Objective: Verify the scaling of a 4–20 mA pressure input configured for 0–100 bar.

Preconditions:

  • The analog input channel is configured for the correct range.
  • The engineering range and units are approved.
  • The selected current simulator is suitable for the circuit.
  • The machine is in a safe state for the test.

Procedure:

  1. Record the raw input and displayed engineering value.
  2. Apply 4 mA using the approved test setup.
  3. Record the observed pressure.
  4. Repeat at 8, 12, 16, and 20 mA.
  5. Compare each result with the expected value and tolerance.
  6. Test the specified abnormal-range behavior if included in scope.
  7. Restore the normal connection and verify the final configuration.

The expected nominal values are 0, 25, 50, 75, and 100 bar, respectively. Acceptance must use the specified tolerance rather than assuming every reading must equal the theoretical value exactly.

17. Common mistakes in I/O simulation

  • Treating a software force as proof of physical sensor operation.
  • Testing only the ON state and ignoring the OFF state.
  • Testing normal values without testing specified fault conditions.
  • Failing to check raw input values and processed tags separately.
  • Testing output commands without verifying the required physical response.
  • Using incorrect electrical signal ranges.
  • Ignoring engineering-unit scaling and measurement tolerance.
  • Failing to verify alarm delays, hysteresis, and latching behavior.
  • Simulating external equipment with unrealistically perfect responses.
  • Leaving forces, temporary overrides, or disconnected test wiring in place.
  • Failing to record the exact simulation method.
  • Claiming that safety functions have passed based on ordinary PLC forcing.
  • Recording “I/O OK” without identifying the signals and evidence tested.

18. Troubleshooting I/O simulation failures

Symptom Possible causes Checks
PLC input does not change Incorrect address, wrong channel, wiring issue, module configuration, or unsuitable simulation method Verify the I/O list, module status, and approved test setup
Raw input changes but program tag does not Incorrect mapping, program logic, data conversion, or stale data Trace the tag mapping and program execution
Program tag changes but sequence does not respond Missing permissive, wrong operating mode, additional interlock, or incorrect sequence state Check permissives and transition conditions
Output command is ON but device does not operate Output hardware fault, wiring problem, power loss, actuator fault, or interlock Verify the required electrical and physical layers
Analog value is incorrect Wrong range, incorrect scaling, wrong units, simulator configuration, or calibration error Check configuration and compare measured input with calculated value
Alarm does not activate Incorrect threshold, delay, hysteresis, alarm enable condition, or mapping Inspect the approved alarm definition and relevant logic
Signal behaves intermittently Contact chatter, noise, poor connection, unstable simulation, or communication issues Check signal quality, wiring, filtering, and diagnostics
Signal remains forced after testing Incomplete restoration or overlooked force status Check controller force indications and the approved final-state checklist

Troubleshooting should proceed from the signal source through the input mapping, control logic, output command, and physical device. This approach separates electrical, configuration, programming, communication, and mechanical faults instead of changing several things at once.

19. Interview questions and answers

1. What is I/O simulation?

It is the controlled substitution or generation of input and output conditions to verify control-system behavior during testing.

2. What is the difference between software forcing and electrical input simulation?

Software forcing overrides a selected controller value. Electrical input simulation applies an electrical signal through an approved test arrangement, allowing additional verification of the input circuit and module.

3. Can a forced input prove that a sensor is working?

No. A force can bypass the sensor and its wiring. Physical sensor verification requires an appropriate test of the actual device and signal path.

4. Why is output simulation important?

It helps verify output commands and selected electrical behavior without necessarily operating the complete machine. The test must clearly identify which layers have actually been verified.

5. How do you test a 4–20 mA signal?

Apply controlled current values across the specified range, record raw and engineering values, verify scaling and tolerances, and test defined abnormal conditions where required.

6. How do you simulate a robot during FAT?

Use an approved interface simulator to generate the required handshake states, including normal operation, delayed acknowledgement, missing completion, faults, and communication-loss scenarios.

7. Why must forces be removed after testing?

A remaining force can conceal real faults or cause unexpected machine behavior during subsequent tests or operation.

8. Does successful I/O simulation prove the complete machine is ready for shipment?

No. It proves only the tested requirements and layers. Physical wiring, device operation, machine sequences, safety functions, performance, and other acceptance requirements need their own appropriate verification.

9. What evidence should be recorded during I/O simulation?

The test ID, signal identity, simulation method, initial and final values, actual response, acceptance criteria, relevant logs or measurements, status, and restoration confirmation.

10. Why should abnormal signal states be tested?

They reveal how the system behaves when feedback is missing, invalid, delayed, contradictory, or lost, which is often where significant control-system defects appear.

20. Final I/O simulation checklist

  • Approved test procedure and I/O list are available.
  • Correct controller, module, channel, and tag are identified.
  • Simulation method is suitable for the requirement being verified.
  • Machine state and safety controls are confirmed.
  • Initial and expected values are documented.
  • Both normal and specified abnormal conditions are tested.
  • Analog scaling, units, thresholds, and tolerances are checked where applicable.
  • Output commands are distinguished from physical actuator responses.
  • Evidence is linked to the correct test ID.
  • Failures and blocked tests are recorded accurately.
  • All forces, temporary overrides, and test connections are restored or removed.
  • Final configuration and outstanding deviations are documented.

I/O simulation establishes whether selected control-system signals and logic behave as specified under controlled test conditions. Its value depends on choosing the correct simulation method, recording the limits of what was verified, and never confusing a simulated signal with proof of complete physical functionality.
