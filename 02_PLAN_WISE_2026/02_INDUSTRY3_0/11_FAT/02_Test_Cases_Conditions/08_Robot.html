1. Purpose of Robot Testing During FAT

Robot testing during Factory Acceptance Testing (FAT) verifies that an industrial robot, its controller, tooling, peripherals, PLC interface, and safety-related systems perform according to the approved machine design.

The objective is to demonstrate that the robot can execute the required operations accurately, repeatedly, and safely under the specified test conditions.

A robot reaching a programmed position does not, by itself, prove that the complete robotic cell is ready. The robot may move correctly while the gripper fails to hold a part, the PLC handshake is incorrect, a fixture is misaligned, or the recovery procedure creates an unexpected movement.

Robot FAT must therefore verify the complete application, including robot motion, sequence logic, tooling, interlocks, communication, fault handling, and documented acceptance criteria.

2. Scope of Robot FAT

Robot FAT typically covers:

  • Robot hardware, controller, teach pendant, and software configuration.
  • Robot program structure, motion instructions, and process sequence.
  • Programmed positions, approach points, retract points, and path clearances.
  • Tool Center Point (TCP), payload, center of gravity, and tool orientation.
  • Robot-to-PLC communication and handshake signals.
  • Grippers, welding guns, dispensing tools, sensors, and other end effectors.
  • Workpiece pickup, placement, orientation, and process execution.
  • Automatic, manual, teaching, and recovery modes as applicable.
  • Collision detection, protective stops, emergency stops, and safety interlocks.
  • Fault recovery, restart behavior, and abnormal-condition handling.
  • Cycle time, repeatability, process quality, and acceptance documentation.

The exact scope depends on the robot application, the contractual specification, and the approved FAT plan.

5. Robot Coordinate Systems and Motion Fundamentals

Understanding coordinate systems is essential for testing programmed positions and diagnosing movement errors.

5.1 Joint coordinates

Joint-coordinate movement commands individual robot axes to specified joint positions.

Typical checks include:

  • Correct joint direction and axis identification.
  • Motion within approved joint limits.
  • Correct response to commanded joint positions.
  • No unexpected axis movement or interference.
  • Correct behavior of configured external axes.

Joint movement is useful for setup and diagnosis, but it does not automatically guarantee that the tool follows a desired straight-line path.

5.2 Cartesian coordinates

Cartesian movement specifies the tool position and orientation relative to a defined coordinate frame.

The relevant coordinates commonly include \(X\), \(Y\), \(Z\), and orientation components such as \(W\), \(P\), \(R\), or controller-specific equivalents.

Verify that the robot reaches the intended position and orientation relative to the correct frame.

5.3 Coordinate frames

Frame Meaning FAT verification
World or base frame Reference associated with the robot installation Verify robot mounting and base reference
Joint coordinates Individual robot-axis positions Verify joint movement and limits
Tool frame Reference defined by the tool geometry Verify TCP and tool orientation
User or work frame Reference associated with a fixture or workpiece Verify frame origin, orientation, and calibration
External-axis frame Reference for positioners or coordinated equipment Verify configuration and synchronization where applicable

A position can appear correct numerically while the physical tool is displaced because the wrong tool or work frame is active.

6. Tool Center Point, Payload, and Calibration

6.1 Tool Center Point

The Tool Center Point is the defined reference point of the tool used by the robot motion system. For a welding gun, it may correspond to the process point; for a gripper, it may be the defined pickup reference.

Verify:

  • Correct TCP selection in the program.
  • Calibration according to the approved procedure.
  • Correct tool orientation.
  • Agreement between programmed and physical approach positions.
  • Consistency of the TCP after tool replacement or mechanical adjustment.

A TCP error can create systematic position deviations throughout the robot path.

6.2 Payload configuration

Payload configuration typically includes:

  • Tool and workpiece mass.
  • Center of gravity relative to the flange.
  • Inertia parameters where required.
  • Payload selection for different tool or part conditions.

Incorrect payload settings may degrade motion performance, affect collision monitoring, or cause controller warnings. They can also create excessive mechanical loading.

Verify payload data against approved calculations, measurements, or manufacturer procedures. Do not estimate payload parameters by guesswork.

6.3 Calibration and position accuracy

Robot position verification should use the method and tolerance defined by the application specification.

Possible methods include:

  • Calibrated gauges or fixtures.
  • Measurement of known reference points.
  • Approved laser-tracking or metrology systems.
  • Vision-based measurements.
  • Dedicated tool-center-point calibration procedures.
  • Verification against a known workpiece or process reference.

Distinguish programmed positioning performance from the accuracy of the entire manufacturing process. Robot repeatability alone does not account for fixture error, workpiece variation, tool deflection, or sensor uncertainty.

7. Robot Program and Motion Testing

Robot program testing verifies that the intended path and sequence are implemented correctly.

7.1 Program structure

Review the program for:

  • Correct program and subprogram selection.
  • Correct initialization and reference handling.
  • Correct tool and work-frame selection.
  • Valid approach, process, and retract positions.
  • Correct motion instructions and speed settings.
  • Correct branching, loops, and conditional logic.
  • Correct fault handling and program termination.
  • Correct handling of interrupted cycles and restart points.

7.2 Motion instructions

Different manufacturers use different programming syntax. Common motion concepts include:

Motion concept Purpose FAT verification
Joint movement Move axes to a target joint configuration Correct target and joint path
Linear movement Move the TCP along a linear path Path clearance and endpoint
Circular movement Follow a specified circular arc Arc geometry and intermediate clearance
Fine or exact positioning Reach the target without the configured path blending Endpoint accuracy within specified limits
Blended movement Smooth motion through a programmed region Correct path blending and process suitability
Speed override Adjust permitted motion speed Correct response within authorized test conditions

Do not assume that similarly named instructions have identical behavior across robot brands or controller generations.

7.3 Path verification procedure

  1. Confirm the correct program, tool, work frame, and payload configuration.
  2. Inspect the path in the robot simulation or offline programming environment where available.
  3. Verify approach and retract positions around fixtures, clamps, conveyors, and adjacent equipment.
  4. Conduct the approved initial motion test under controlled conditions.
  5. Compare actual motion with the intended path.
  6. Check for unexpected wrist rotation, singularity-related behavior, axis-limit issues, or unnecessary motion.
  7. Verify that the tool remains clear of the workpiece and fixtures except where intended.
  8. Record any deviations and repeat the test after approved correction.

Reduced-speed teaching or verification is not a substitute for a complete risk assessment or effective safeguarding.

8. Robot-to-PLC Handshake Testing

The robot and PLC typically exchange status, command, acknowledgment, and fault information.

A generic interface may contain the following signals:

Signal Direction Typical meaning
Robot_Ready Robot to PLC Robot is available under defined conditions
Robot_Busy Robot to PLC Robot is executing an operation
Robot_Fault Robot to PLC Robot has an active fault
Program_Selected Robot to PLC Required program or job is selected
Start_Request PLC to robot PLC requests an operation
Start_Acknowledge Robot to PLC Request has been accepted
Cycle_Complete Robot to PLC Programmed operation has completed
Reset_Request PLC to robot Reset request under approved conditions
Part_Present Sensor or PLC interface Part-presence information
Gripper_Closed Tool sensor to controller or PLC Gripper closed-state feedback
Gripper_Open Tool sensor to controller or PLC Gripper open-state feedback

These are example names, not universal signal definitions. The approved interface-control document takes precedence.

8.2 Handshake FAT checks

Verify that:

  • The correct program or job is selected.
  • Start commands are accepted only under defined conditions.
  • A request is not unintentionally executed more than once.
  • Acknowledgment and completion signals have the correct meaning.
  • Busy and ready statuses change at the expected points.
  • Faults prevent inappropriate sequence advancement.
  • A stale completion signal cannot falsely complete a new cycle.
  • Reset behavior is controlled and does not initiate unexpected movement.
  • Loss of communication produces the specified machine response.
  • Restart after an interruption follows the approved recovery procedure.

A common defect is a completion bit that remains active after one cycle and causes the PLC to treat the next cycle as already completed. FAT should test the transition behavior, not only the steady-state signal values.

9. End-of-Arm Tooling and Peripheral Testing

The robot tool must perform its intended task reliably. Tooling tests depend on the application and may include grippers, vacuum systems, welding guns, dispensing equipment, screwdrivers, or other process devices.

9.1 Gripper testing

Verify:

  • Open and close commands.
  • Open and closed position feedback.
  • Grip confirmation or part-present sensing.
  • Correct behavior when the part is absent.
  • Correct response when grip confirmation fails.
  • Release confirmation where required.
  • Pneumatic pressure or electrical supply within specified limits.
  • Part retention throughout the approved movement.
  • Correct response to loss of power or air according to the design.

Do not assume a gripper retains a part after loss of energy. Its actual behavior depends on the gripper design and any holding mechanism.

9.2 Vacuum tooling

Verify:

  • Vacuum generation and release.
  • Vacuum pressure or level feedback.
  • Part pickup confirmation.
  • Leak or insufficient-vacuum detection where provided.
  • Response to loss of vacuum during a permitted test.
  • Correct release at the intended station.
  • Fault reporting and recovery.

9.3 Welding or process tooling

For welding robots, dispensing robots, and similar applications, verify the applicable process interface:

  • Process controller ready and fault status.
  • Correct job or recipe selection.
  • Correct initiation and completion signals.
  • Required process permissives.
  • Tool status and feedback.
  • Process parameter selection.
  • Required process-quality checks.
  • Fault handling when the process equipment is unavailable.

The exact process parameters and quality acceptance limits must come from the approved process specification.

10. Part Handling and Workpiece Verification

For pick-and-place applications, test the complete material-handling sequence.

Typical checks include:

  1. Correct identification of the pickup location.
  2. Correct approach and pickup path.
  3. Correct part-presence verification.
  4. Correct gripping or vacuum confirmation.
  5. Correct movement with the workpiece.
  6. Correct clearance from fixtures and surrounding equipment.
  7. Correct placement position and orientation.
  8. Correct release confirmation.
  9. Correct completion signal to the PLC.
  10. Correct response when pickup or placement fails.

Include approved variations such as missing parts, incorrect orientation, or failed sensor feedback where these cases are part of the test specification.

Do not deliberately drop parts or create hazardous conditions to test failure handling. Use a controlled simulation or approved test method.

11. Safety and Protective-Function Verification

Robot-cell safety must be assessed against the approved risk assessment, safety design, and applicable standards. Ordinary robot motion testing does not replace formal safety validation.

Relevant standards may include ISO 10218 for industrial robot and robot-application safety, ISO 13849-1 for safety-related control-system design, and IEC 60204-1 for electrical equipment of machinery. The applicable editions, legal requirements, and contractual standards must be confirmed for the project.

Depending on the cell design, safety-related functions may include:

  • Emergency-stop functions.
  • Guard-door interlocks.
  • Presence-sensing devices.
  • Protective stops.
  • Safety-rated monitored stop or other specified motion-related safety functions.
  • Enabling-device behavior during teaching.
  • Mode selection and associated speed restrictions.
  • Safety-rated communication where implemented.
  • Safe behavior after a safety fault or power interruption.

For each function, verify the approved test method, expected state, response time where specified, reset conditions, and required evidence.

Critical distinction: A standard PLC bit, ordinary Ethernet connection, or HMI message is not automatically a safety-rated function. Safety validation must use the approved safety architecture and authorized test procedures.

Do not bypass guards, defeat interlocks, or improvise protective-function tests. Where a test requires access to the safeguarded space, follow the documented procedure and the site's authorized safety controls.

12. Robot Fault Handling and Recovery

Robot FAT must verify not only how faults are detected but also how the system returns to a valid state.

Fault condition Expected verification
Robot controller fault Correct fault indication and defined machine response
Program execution error Correct program-stop behavior and diagnostic information
Gripper confirmation failure Sequence is inhibited or handled according to design
Part missing Pickup or process is prevented or handled as specified
PLC communication loss Defined timeout, status, and sequence response
External equipment not ready Robot operation is inhibited where required
Robot collision or overload fault Manufacturer-defined fault response and controlled recovery
Protective stop Specified protective response and authorized reset procedure
Power interruption Defined restart state and recovery behavior
Invalid program selection Start request is rejected or faulted as specified

12.1 Recovery procedure verification

For each applicable fault:

  1. Establish the fault under approved test conditions.
  2. Record the robot and PLC status before and after the fault.
  3. Verify the alarm text, code, and diagnostic information.
  4. Confirm that the machine does not advance into an invalid sequence state.
  5. Correct the underlying fault using the approved procedure.
  6. Verify the reset and restart conditions.
  7. Confirm that the robot resumes only from the permitted state.
  8. Check that no unintended tool actuation or motion occurs.
  9. Record the outcome and retest any affected functions.

A fault reset should not be treated as proof that the original fault has been corrected. The cause must be addressed and the affected function revalidated.

13. Cycle Time and Production Performance

Cycle-time testing establishes whether the robot application meets its specified production target.

A cycle-time measurement should define:

  • The start event.
  • The end event.
  • The included robot and peripheral operations.
  • The number of repeated cycles.
  • The handling of planned delays and process waits.
  • The operating conditions and speed settings.
  • The required acceptance limit.

For example, a handling cycle may include pickup, transfer, placement, release, and confirmation. If the specification includes PLC or conveyor waiting time, those delays must be included in the measurement.

13.1 Cycle-time calculation

For a defined measurement interval:

\[ T\_{cycle} = t\_{end} - t\_{start} \]

For \(N\) measured cycles, the mean cycle time is:

\[ T\_{avg} = \frac{\sum\_{i=1}^{N} T_i}{N} \]

Record individual measurements as well as the average. An acceptable average can conceal occasional long cycles, so the FAT plan may also specify maximum cycle time, variability, or percentile limits.

13.2 Performance optimization

If cycle time exceeds the requirement, investigate:

  • Excessive travel distance.
  • Unnecessary approach and retract motions.
  • Conservative or inconsistent speed settings.
  • Excessive waiting for PLC or peripheral handshakes.
  • Inefficient sequence ordering.
  • Poorly selected blending or positioning instructions.
  • Unnecessary tool operations.
  • External-axis synchronization.
  • Process equipment delays.

Do not increase speed blindly. Any optimization must preserve path clearance, process quality, approved motion limits, and safety requirements. Revalidate all affected tests after changing a program or motion parameter.

14. Repeatability and Process Quality

Robot repeatability describes the ability to return to the same position under defined conditions. It is not identical to absolute positioning accuracy or complete process quality.

Verify the characteristic specified for the application, such as:

  • Repeatability at a reference position.
  • Positioning relative to a calibrated fixture.
  • Part placement accuracy.
  • Weld location or weld quality.
  • Dispensing path and bead characteristics.
  • Fastener position and tightening results.
  • Tool orientation and process approach.
  • Consistency over the defined number of cycles.

The measurement method must account for fixture variation, workpiece variation, tool calibration, measurement uncertainty, and environmental conditions where relevant.

Do not claim that a robot meets a numerical repeatability specification merely because a few manually observed movements appear consistent.

17. FAT Acceptance and Documentation

A robot FAT should be accepted only when the agreed tests have passed and the results are traceable.

Typical records include:

  • Robot and controller identification.
  • Software, firmware, and program revisions.
  • Tool, TCP, payload, and work-frame configuration.
  • Robot program backups and approved change history.
  • Position and path verification results.
  • PLC interface and handshake test records.
  • Tooling and process test results.
  • Cycle-time measurements and defined measurement conditions.
  • Repeatability or process-quality measurements where required.
  • Safety validation records for the applicable protective functions.
  • Fault injection and recovery evidence.
  • Defect reports, root-cause analysis, and retest results.
  • Outstanding deviations and their approved disposition.
  • Final FAT acceptance and sign-off.

Each test record should identify the test condition, expected result, actual result, pass/fail status, evidence, tester, and relevant configuration revision.

18. Common Robot FAT Mistakes

  • Testing the robot alone without verifying PLC and peripheral integration.
  • Using the wrong tool or work frame during position verification.
  • Ignoring TCP calibration and payload configuration.
  • Testing only the normal production cycle.
  • Failing to test missing-part, failed-grip, and handshake-timeout conditions.
  • Measuring cycle time without defining its start and end events.
  • Treating repeatability as proof of absolute accuracy.
  • Increasing motion speed without evaluating path clearance and process quality.
  • Assuming an ordinary PLC signal is an adequate safety function.
  • Resetting faults without identifying their cause.
  • Changing programs without revision control or backup.
  • Accepting the cell without documented results and evidence.

19. Interview Questions and Answers

Q1. What is the purpose of robot FAT?

To verify the robot's configuration, motion, application program, tooling, PLC interface, process sequence, fault handling, performance, and required protective functions against the approved design.

Q2. What is the difference between TCP and a work frame?

The TCP defines the tool reference point and orientation relative to the robot flange. A work frame defines the reference coordinate system for the workpiece or fixture. Incorrect data in either can cause positioning errors.

Q3. What is the difference between robot accuracy and repeatability?

Accuracy concerns how closely the achieved position matches the intended position. Repeatability concerns how consistently the robot returns to the same position under defined conditions.

Q4. Why is payload configuration important?

The controller uses payload information to account for tool and workpiece mass and, where applicable, center of gravity and inertia. Incorrect settings can degrade motion performance and affect monitoring or mechanical loading.

Q5. Why must PLC-to-robot handshakes be tested?

They coordinate command acceptance, execution, status, and completion. Incorrect handshakes can cause missed commands, duplicate actions, premature sequence transitions, or deadlocks.

Q6. What is the difference between joint and linear movement?

Joint movement commands robot-axis positions, while linear movement specifies a linear TCP path in the relevant Cartesian frame. Their paths and clearance characteristics are different.

Q7. How would you troubleshoot a robot that does not start in automatic mode?

Check the active fault, selected mode, program selection, required permissives, protective-device status, controller readiness, PLC command, and handshake signals. Follow the approved diagnostic and recovery procedure without bypassing safety functions.

Q8. Why must cycle time be measured over repeated cycles?

Repeated measurements reveal variability and intermittent delays that a single successful cycle may hide. Acceptance should use the measurement method and limits defined by the FAT specification.

Q9. What must be verified after changing a robot position?

Recheck the affected path, approach and retract clearance, tool orientation, interference risk, cycle time, process quality, and any affected handshake or recovery behavior. Record the change and repeat relevant tests.

Q10. Does successful robot motion prove the robotic cell is safe?

No. Safety depends on the complete application, including safeguarding, protective functions, control-system architecture, installation, and validated behavior. Required safety validation must be completed separately according to the approved plan.

Q11. How should a robot recover after communication loss?

It should detect the fault, enter the defined application state, report diagnostics, and resume only according to the approved recovery logic. The exact response depends on the interface and machine design.

Q12. What evidence is required to close a robot FAT defect?

Document the observed fault, test conditions, root cause, corrective action, program or configuration revision, retest procedure, measured result, and supporting evidence.

20. Practical Robot FAT Checklist

  • Robot model, controller, and software revisions verified.
  • Approved program backup completed.
  • Tool, TCP, payload, and work frames verified.
  • Joint and Cartesian motions tested.
  • Approach, process, and retract paths verified.
  • PLC handshake signals and sequence transitions tested.
  • Gripper, vacuum, and process tooling tested.
  • Part-presence and failed-pick conditions verified.
  • Communication faults and recovery tested where specified.
  • Required safety validation completed under the approved procedure.
  • Cycle time measured against the specified criteria.
  • Repeatability or process quality verified where required.
  • Fault recovery and restart behavior verified.
  • Deviations corrected or formally dispositioned.
  • FAT evidence and final configuration records archived.
