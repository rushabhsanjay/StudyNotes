1. Definition of sequence testing

Sequence testing is the systematic verification of the ordered steps, transitions, permissives, interlocks, timing conditions, and recovery behavior that control a machine or automated process.

An industrial machine rarely performs its complete operation in one uninterrupted instruction. It moves through defined states, such as IDLE, READY, CLAMPING, PROCESSING, UNCLAMPING, and COMPLETE. Each transition should occur only when the required conditions are satisfied.

During Factory Acceptance Testing (FAT), sequence testing verifies that the machine follows its approved functional specification under normal operating conditions, abnormal conditions, and defined recovery scenarios.

The purpose is not merely to demonstrate one successful cycle. It is to establish that the machine behaves correctly across the relevant operating states and transitions, including when feedback is missing, commands arrive unexpectedly, or faults occur.

2. Objectives of sequence testing

  • Verify the correct order of machine operations.
  • Confirm that each state transition uses the specified conditions.
  • Verify permissives and interlocks.
  • Check command, acknowledgement, and feedback relationships.
  • Validate timeouts and fault responses.
  • Verify cycle-start, cycle-complete, abort, reset, and recovery behavior.
  • Test manual, automatic, setup, and maintenance modes where applicable.
  • Verify behavior when signals arrive early, late, or not at all.
  • Confirm that repeated cycles work without stale flags or unintended state retention.
  • Verify sequence behavior after communication loss, controller restart, or power restoration where required.
  • Record objective evidence against approved requirements.

3. Sequence, state, step, and transition

These terms are related but should not be treated as interchangeable.

Term Meaning Example
Sequence The complete ordered machine operation Automated clamping and drilling cycle
State The current operating condition of the control system WAITING_FOR_CLAMP
Step A defined operation within the sequence Command clamp extension
Transition The condition that permits movement to another state Clamp-extended feedback confirmed
Permissive A condition required before an operation is allowed Guard closed and pressure healthy
Interlock A condition that inhibits or stops an operation when required Prevent spindle operation without clamp confirmation
Timeout A maximum permitted waiting period for an expected condition Clamp feedback must arrive within the specified time
Recovery The controlled method of returning from a fault or interruption Clear the fault and return to a defined safe state

A step is not complete merely because its output command has been issued. Where the specification requires feedback confirmation, the sequence must verify that feedback before proceeding.

4. Example machine sequence

Consider an automated station that clamps a component, performs a process, and then releases the component.

IDLE
  ↓ Start request accepted
PRECHECK
  ↓ All required permissives satisfied
CLAMPING
  ↓ Clamp-extended feedback confirmed
PROCESSING
  ↓ Process-complete feedback confirmed
UNCLAMPING
  ↓ Clamp-retracted feedback confirmed
CYCLE_COMPLETE
  ↓ Completion handled and next cycle permitted
IDLE

Any applicable fault condition
  ↓
FAULT / CONTROLLED STOP
  ↓
Fault cause removed and recovery conditions satisfied
  ↓
RECOVERY / READY

This is a simplified illustration. The actual machine may include separate states for robot loading, part verification, spindle startup, quality inspection, unloading, or other operations.

A safety-related event may require a different response from an ordinary process fault. The required behavior must follow the machine risk assessment and safety design.

5. Sequence test preparation

Before executing sequence tests, establish the baseline against which the results will be judged.

5.1 Documents and configuration

  • Approved functional specification.
  • Sequence description or state-transition table.
  • Electrical drawings and I/O list.
  • Interlock list and cause-and-effect matrix.
  • PLC and HMI software revisions.
  • Robot, CNC, drive, and external-device interface specifications where applicable.
  • Approved FAT test cases and acceptance criteria.
  • Relevant safety requirements and risk controls.
  • Previous defects and outstanding deviations.

5.2 Test setup

  • Confirm the machine identification and software baseline.
  • Verify that the required signals are available for observation.
  • Confirm the approved simulation method for unavailable devices.
  • Establish a safe test mode and control unintended movement.
  • Confirm the required test equipment and communication links.
  • Identify the initial state and reset procedure.
  • Ensure that temporary forces and overrides are controlled and recorded.

Do not begin a sequence test by arbitrarily setting internal flags until the machine appears ready. Doing so can bypass the exact transitions that the test is supposed to verify.

6. Building a sequence test matrix

A sequence test matrix connects the defined sequence steps to the test cases needed to verify them.

Test ID State or transition Test condition Expected result
FAT-SEQ-001 IDLE to PRECHECK Valid start request Start request is accepted under the specified conditions
FAT-SEQ-002 PRECHECK to CLAMPING All required permissives healthy Clamp command is issued
FAT-SEQ-003 PRECHECK to CLAMPING One required permissive absent Transition is inhibited
FAT-SEQ-004 CLAMPING to PROCESSING Clamp feedback confirmed Processing may start if all other required conditions are satisfied
FAT-SEQ-005 CLAMPING timeout Feedback not received in time Defined timeout response occurs
FAT-SEQ-006 PROCESSING to UNCLAMPING Process complete Unclamp operation starts according to the specified logic
FAT-SEQ-007 UNCLAMPING to CYCLE_COMPLETE Retracted feedback confirmed Completion state is reached
FAT-SEQ-008 Fault recovery Fault removed but reset not accepted Sequence remains in the specified fault or recovery state

The matrix should cover normal transitions, inhibited transitions, timeouts, invalid signals, recovery, and repeated operation according to the project's requirements.

7. Testing normal sequence operation

A normal sequence test verifies the intended operating path with all required conditions satisfied.

Procedure

  1. Establish the specified initial state.
  2. Confirm the required permissives.
  3. Issue the approved start command.
  4. Observe the sequence state and relevant output commands.
  5. Verify the required feedback at each transition.
  6. Record transition order and relevant timing measurements.
  7. Confirm that no prohibited state is entered.
  8. Verify the defined completion condition.
  9. Record the result and evidence.
  10. Repeat the cycle as required by the approved test plan.

Acceptance criteria

  • Each operation occurs in the specified order.
  • Required conditions are satisfied before transitions occur.
  • Outputs behave according to the sequence specification.
  • Feedback is interpreted correctly.
  • No unexpected state transition occurs.
  • Required alarms remain inactive during normal operation.
  • Completion is declared only when the specified completion conditions are satisfied.
  • Timing meets the defined acceptance limits.

A machine completing one cycle does not prove that every transition is correct. For example, an incorrect transition might be hidden because a sensor is already active before the test begins.

8. Testing permissives and interlocks

A permissive allows an operation when required conditions are satisfied. An interlock inhibits an operation or enforces a defined response when a prohibited condition exists.

Typical sequence permissives include:

  • Guard system indicates the required safe condition.
  • Emergency-stop system is reset and the required safety conditions are satisfied.
  • Required air or hydraulic pressure is available.
  • Drive reports ready.
  • Robot reports available.
  • Correct part or fixture is detected.
  • Required clamp feedback is confirmed.
  • Downstream equipment is ready to receive the part.

The actual conditions depend on the machine design. A software permissive must not be confused with a validated safety function.

8.1 One-condition-at-a-time testing

Suppose automatic start requires three conditions:

  • Guard_Ready
  • Air_Pressure_OK
  • Drive_Ready

The test should establish the baseline, then test each condition individually.

Guard ready Pressure healthy Drive ready Expected start behavior
TRUE TRUE TRUE Start may be accepted if all other requirements are satisfied
FALSE TRUE TRUE Start inhibited
TRUE FALSE TRUE Start inhibited
TRUE TRUE FALSE Start inhibited
FALSE FALSE TRUE Start inhibited

Additional combinations should be tested when they reveal behavior not covered by individual-condition tests.

Record the state of the inputs, the start request, the sequence state, the relevant output commands, and any specified diagnostic response.

9. Testing timeouts

A timeout detects a condition that has not occurred within the permitted period.

Examples include:

  • Clamp feedback not received.
  • Robot acknowledgement missing.
  • Drive not ready.
  • Part transfer not completed.
  • Communication response missing.
  • Process completion signal not received.

9.1 Timeout test method

  1. Identify the transition and its configured timeout requirement.
  2. Establish the initial state.
  3. Initiate the operation that starts the timer.
  4. Prevent the expected feedback using an approved simulation method.
  5. Observe elapsed time, sequence state, and alarm behavior.
  6. Verify the specified timeout response.
  7. Restore the signal and follow the defined recovery procedure.
  8. Record the measured result and evidence.

For a requirement specifying a maximum response time \(T\_{\max}\), the observed time must satisfy the defined tolerance and measurement rules.

\[ T\_{\text{observed}} \leq T\_{\max} \]

This comparison is appropriate only when the requirement defines a simple maximum limit. If the specification includes a tolerance band, debounce period, or separate detection and response limits, apply those criteria instead.

Do not assume that every timeout should immediately de-energize every output. The required response depends on the function, risk assessment, and approved design.

10. Testing early, late, and missing feedback

Sequence defects often appear when feedback arrives at an unexpected time.

10.1 Early feedback

Verify behavior when feedback is already active before the command is issued.

Questions to test:

  • Is the feedback valid in the current state?
  • Does the logic incorrectly skip a required operation?
  • Is the signal required to change state after the command?
  • Does the specification permit the sequence to proceed from the existing condition?

Some feedback may legitimately be active at the start of a cycle. Other transitions require a new event or a specific state change. The specification determines which behavior is correct.

10.2 Late feedback

Verify that the sequence remains in the correct waiting state until feedback arrives or the timeout expires.

Check that:

  • The next operation does not start prematurely.
  • The timeout is handled consistently.
  • Late feedback does not incorrectly clear a latched fault.
  • Recovery follows the defined procedure.

10.3 Missing feedback

Verify the specified response when feedback never arrives.

Record:

  • State before the command.
  • Command activation time.
  • Expected feedback.
  • Timeout duration.
  • Alarm or fault response.
  • Output behavior.
  • Recovery conditions.

11. Testing sequence abort, stop, and reset

These actions may have different meanings and must be tested according to the approved control philosophy.

Action General purpose FAT verification focus
Normal stop Stop operation according to the defined sequence Controlled completion or stopping behavior
Cycle abort Terminate the current operation according to the specified abort logic Outputs, state transition, and part-handling consequences
Fault reset Acknowledge or clear an eligible fault after the cause is addressed Fault clearance and prevention of unintended restart
Sequence restart Initiate operation again under valid conditions Correct initial state and valid start conditions
Emergency stop Invoke the designed safety-related stopping function Verification under the approved safety validation procedure

An emergency stop is not simply a PLC sequence reset. Its function, reset behavior, and restart prevention requirements must be validated using the applicable safety procedures.

Example tests

  • Request normal stop during a permitted sequence phase.
  • Request abort during processing.
  • Attempt reset while the fault cause remains present.
  • Clear a fault without issuing a new start command.
  • Restore power or communication and verify the specified restart behavior.
  • Confirm that a reset does not itself initiate hazardous motion unless explicitly allowed by the validated design.

12. Testing manual, automatic, and setup modes

Machines often provide multiple operating modes. The same command may have different permissions depending on the active mode.

Manual mode

Verify that individual movements or commands require the specified conditions and operator actions. Confirm that automatic sequence progression does not occur unless permitted.

Automatic mode

Verify that the sequence executes its approved state transitions and that operator commands cannot bypass required conditions.

Setup or maintenance mode

Verify the specified restrictions, reduced-speed behavior where applicable, access controls, and other protective measures.

Mode selection alone does not establish that a machine is safe. The relevant safety-related functions must be validated independently according to their design.

Test mode transitions at appropriate points in the sequence, including any required restrictions on changing mode during active motion or processing.

13. Testing repeated cycles and state retention

A sequence may work correctly during the first cycle but fail on subsequent cycles because flags, timers, counters, or completion bits are not reset correctly.

Test repeated cycles to verify:

  • State initialization.
  • Timer reset behavior.
  • Counter handling.
  • Completion flag clearing.
  • Alarm reset rules.
  • Correct interpretation of new start requests.
  • Removal of stale handshake signals.
  • Correct handling of parts remaining in the station.
  • No unintended double-triggering.
  • No premature completion of the next cycle.

Where the test plan requires endurance or repeated-cycle testing, record the number of cycles, any interruptions, and all observed failures.

14. Testing communication-dependent sequences

When a sequence depends on another controller or device, test the interface behavior as part of the sequence.

Examples include PLC-to-robot handshakes, PLC-to-CNC coordination, conveyor transfers, and upstream/downstream station exchanges.

Test cases may include:

  • Normal request and acknowledgement.
  • Acknowledgement delayed beyond the allowed limit.
  • Completion received without a valid request.
  • Busy state remaining active.
  • Communication loss during an operation.
  • Communication restoration after a timeout.
  • Device fault during an active sequence.
  • Controller restart while a request is pending.

The expected result must define whether the sequence waits, faults, retries, aborts, or requires operator recovery.

Do not assume that restoring communication means the sequence should automatically continue. The approved restart and recovery logic determines whether continuation is permitted.

15. Timing and cycle-time verification

Sequence testing may include individual transition times and complete machine cycle time.

Typical measurements include:

  • Command-to-feedback time.
  • Feedback-to-next-command time.
  • Robot handshake duration.
  • Processing duration.
  • Fault detection time.
  • Alarm generation time.
  • Total cycle time.

Define measurement start and end events clearly. For example, cycle time might be measured from accepted cycle start to the completion condition, not from the moment an operator presses a button if the machine has a separate start-acceptance phase.

\[ T\_{\text{cycle}} = t\_{\text{completion}} - t\_{\text{accepted start}} \]

Use suitable timestamp resolution and measurement tools. When multiple controllers are involved, clock synchronization and event-source differences may affect measured timing.

Record actual results against the approved limit and test conditions. Cycle-time compliance should not be established by averaging away a failure if the requirement also specifies a maximum permitted individual cycle time.

16. Sequence state-transition table

A state-transition table provides a structured way to inspect and test the sequence logic.

Current state Transition condition Next state Expected action
IDLE Valid start accepted PRECHECK Evaluate required conditions
PRECHECK All permissives satisfied CLAMPING Issue clamp command
PRECHECK Required permissive absent PRECHECK or defined fault state Inhibit start or respond as specified
CLAMPING Clamp feedback confirmed PROCESSING Permit process start if other conditions are satisfied
CLAMPING Timeout expires Defined fault state Execute specified timeout response
PROCESSING Process complete UNCLAMPING Begin release operation
UNCLAMPING Retracted feedback confirmed CYCLE_COMPLETE Record completion
Fault state Recovery conditions satisfied and reset accepted Defined recovery state Clear eligible fault and restore the approved state

This is an illustrative model, not a universal machine sequence. The actual state names, transitions, outputs, and recovery behavior must come from the approved functional specification.

17. Worked example: clamp and process sequence

Objective: Verify that a process cannot start before clamp confirmation and that missing feedback produces the specified fault response.

Test ID: FAT-SEQ-010

Preconditions:

  • Approved PLC and HMI versions are loaded.
  • The sequence is in the specified ready state.
  • The approved test arrangement is established.
  • Required safety conditions are satisfied.
  • The relevant input tags, state indicators, timers, and alarms can be observed.

Test A: Normal sequence

  1. Issue the approved cycle-start request.
  2. Verify that the clamp command is issued.
  3. Confirm that the process remains inhibited while clamp feedback is absent.
  4. Apply the expected clamp feedback using the approved test method.
  5. Verify that the sequence advances to the processing state.
  6. Apply the process-complete condition.
  7. Verify the specified unclamping operation and completion state.
  8. Record all required observations.

Expected result: The process begins only after the required clamp feedback and other specified permissives are satisfied.

Test B: Missing clamp feedback

  1. Return the machine to the specified initial state.
  2. Initiate the cycle.
  3. Prevent clamp feedback from being confirmed using the approved test method.
  4. Observe the sequence and timeout.
  5. Verify the defined alarm and fault response.
  6. Restore the test condition and follow the approved recovery procedure.

Expected result: The process remains inhibited, the specified timeout response occurs, and recovery follows the defined rules.

Evidence: State-transition log, relevant PLC tag captures, timeout measurement, alarm record, software revision, and completed test sheet.

18. Recording sequence test results

A sequence test record should include:

  • Test ID and linked requirement.
  • Machine and software revision.
  • Initial state and input conditions.
  • Step-by-step actions.
  • Expected state transitions.
  • Actual states and observed outputs.
  • Timing measurements where required.
  • Alarm and fault behavior.
  • Evidence references.
  • Test status.
  • Deviation ID and retest history, if applicable.
  • Tester and required witness sign-off.

A result such as “sequence OK” is insufficient. Record which transitions were tested and what evidence demonstrates that they satisfied the acceptance criteria.

19. Common sequence-testing mistakes

  • Testing only the normal cycle.
  • Skipping individual permissive checks.
  • Assuming output activation proves physical movement.
  • Allowing a sequence to advance without required feedback.
  • Ignoring early or stale feedback signals.
  • Failing to test timeouts and communication loss.
  • Using internal forces that bypass the transition under test.
  • Ignoring mode-dependent restrictions.
  • Resetting a fault without checking the original cause.
  • Allowing a reset to trigger an unintended restart.
  • Failing to check state and timer initialization across repeated cycles.
  • Testing cycle time without defining the measurement boundaries.
  • Treating an emergency-stop test as an ordinary sequence test.
  • Closing a failed test without retesting the correction and affected functions.

20. Troubleshooting sequence failures

Symptom Possible causes Investigation
Sequence will not start Missing permissive, incorrect mode, active fault, or invalid start request Check start acceptance conditions and interlocks
Sequence skips a step Stale feedback, incorrect transition logic, or improperly initialized state Inspect state transitions and signal history
Sequence waits indefinitely Missing feedback, timer not enabled, incorrect timeout logic, or invalid input mapping Check command, feedback, timer activation, and timeout response
Alarm appears too early Incorrect timer preset, wrong timer start condition, or signal debounce issue Verify the specified timing behavior and timer logic
Fault cannot be reset Cause remains active, reset condition is invalid, or fault is latched by design Check reset permissives and fault-clear rules
Next cycle starts incorrectly Completion flag not cleared, stale request, or improper state initialization Inspect end-of-cycle logic and handshake reset
Sequence resumes unexpectedly Restart logic, retained state, or automatic continuation after communication recovery Verify restart requirements and recovery conditions
Cycle time exceeds limit Slow device response, handshake delays, excessive waits, or timing measurement error Analyze event timestamps and individual transition durations

Troubleshooting should follow the state-transition chain. Identify the last correct state, the transition that failed, its required conditions, and the actual values at that point. This usually narrows the fault faster than browsing the entire PLC program and hoping the guilty rung confesses.

21. Interview questions and answers

1. What is sequence testing in FAT?

It verifies the ordered operations, states, transitions, permissives, interlocks, timing, and recovery behavior of a machine against its approved requirements.

2. What is the difference between a state and a transition?

A state describes the current operating condition. A transition defines the condition under which the control system moves from one state to another.

3. How do you verify a permissive?

Establish the required initial conditions, test the permissive both satisfied and unsatisfied, issue the relevant command, and verify the expected transition or inhibition.

4. How do you test a timeout?

Start the relevant operation, prevent the expected feedback using an approved method, measure the response time, and verify the specified alarm and fault behavior.

5. Why should early feedback be tested?

It can reveal logic that incorrectly skips a required operation or treats an existing signal state as proof that a new action has completed.

6. What is the difference between a process fault and a safety-related event?

A process fault is handled according to the machine's control and fault-management design. A safety-related event invokes the designed safety response and requires verification under the applicable safety procedures.

7. Why is repeated-cycle testing important?

It reveals stale flags, uncleared timers, retained handshake states, and initialization defects that may not appear during the first cycle.

8. How do you test a PLC-to-robot sequence without the robot?

Use an approved interface simulator to generate the required handshake states and abnormal conditions, then verify the PLC sequence response. Physical robot operation still requires its own appropriate verification.

9. What is the difference between sequence completion and cycle completion?

Sequence completion means the defined sequence has reached its specified completion condition. Cycle completion is whatever the approved machine design defines as the end of the production cycle, which may include additional checks or handshakes.

10. What evidence supports a sequence test pass?

Recorded state transitions, signal values, outputs, alarms, timing measurements, relevant software configuration, and documented comparison against the acceptance criteria.

22. Final sequence-testing checklist

  • Approved sequence specification and test cases are available.
  • Initial state and test conditions are established.
  • Normal operating transitions are verified.
  • Each required permissive and interlock is tested.
  • Missing, delayed, and unexpected feedback scenarios are tested as specified.
  • Timeout and alarm behavior is verified.
  • Stop, abort, reset, and recovery behavior is checked.
  • Manual, automatic, and setup-mode restrictions are tested where applicable.
  • Repeated-cycle and state-initialization behavior is checked.
  • Communication-dependent sequence behavior is tested.
  • Cycle-time and transition-time results meet the approved criteria.
  • Safety-related functions are verified through their applicable procedures.
  • Results, evidence, failures, and retests are documented.
  • Temporary test conditions are removed and the final configuration is verified.

Sequence testing establishes whether the machine progresses through the correct states under the correct conditions, and whether it responds predictably when those conditions are absent or abnormal. The strongest FAT evidence covers both successful operation and the failure paths that prevent incorrect operation.
