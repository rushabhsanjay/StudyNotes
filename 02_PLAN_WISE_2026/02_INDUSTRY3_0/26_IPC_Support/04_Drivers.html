1. Purpose of Device Drivers

A device driver is software that allows an operating system to communicate with and control a hardware device through a defined interface.

An industrial PC may contain Ethernet adapters, serial ports, USB controllers, graphics hardware, audio devices, storage controllers, touchscreens, data-acquisition cards, and specialized industrial communication hardware. The operating system needs compatible drivers to use these devices correctly.

A driver problem can make an otherwise healthy hardware component appear defective. For example, an Ethernet adapter may be physically functional but fail to establish reliable communication because its driver is incompatible, corrupted, incorrectly configured, or affected by a software update.

Industrial application
        ↓
Operating system and system services
        ↓
Device driver
        ↓
Hardware interface and controller
        ↓
Physical device

This is a simplified model. Actual communication may also involve firmware, kernel components, runtime libraries, vendor services, and application-specific protocols.

2. Why Drivers Matter in Industrial Automation

Drivers are particularly important in industrial systems because the IPC often supports several interconnected functions.

Device or subsystem Driver responsibility Possible industrial impact of failure
Ethernet adapter Network communication and adapter control PLC communication loss, SCADA disconnection
Serial port COM-port communication Loss of communication with instruments or legacy devices
USB controller USB device connectivity Scanner, license dongle, or peripheral failure
Graphics adapter Display rendering and graphics acceleration Display faults, reduced performance, application issues
Touchscreen Touch input and calibration interface Operator touch failure or inaccurate input
Storage controller Communication with supported storage devices Storage detection problems or boot failures
Industrial fieldbus card Hardware access for supported industrial communication Loss of communication with connected equipment
Data-acquisition card Access to measurement and control hardware Missing or incorrect measurement acquisition
Audio device Audio input and output Loss of required audible notifications
Chipset/system devices Platform-level hardware functions Device initialization failures or reduced functionality

A driver failure does not automatically mean that the device is damaged. The diagnostic process must distinguish hardware faults from driver, configuration, operating-system, firmware, and application problems.

3. Driver Fundamentals and Terminology

3.1 Driver

Software that allows the operating system to use a hardware device or a defined virtual device.

3.2 Device instance

A specific detected instance of a device. For example, two identical Ethernet adapters may appear as separate device instances.

3.3 Driver package

A collection of files and metadata used to install a driver. It may contain driver binaries, configuration information, catalogs, and installation instructions.

3.4 INF file

On Windows, an .inf file describes how a driver package is installed and which devices it supports. It is not normally the executable driver itself.

3.5 SYS file

A Windows .sys file may contain a kernel-mode driver or another system component. Not every .sys file is a device driver, and manually copying one into a system directory is not a valid general installation method.

3.6 Firmware

Firmware runs within a hardware device or controller. A driver and firmware serve different purposes, although they may need to be compatible with each other.

3.7 Driver version

A version identifier used to distinguish driver releases. The newest version is not necessarily the best choice for an industrial IPC. Compatibility and vendor validation matter more than version number alone.

3.8 Plug and Play (PnP)

A mechanism through which an operating system detects, enumerates, and configures supported hardware devices.

3.9 Kernel-mode and user-mode drivers

  • Kernel-mode drivers run in a privileged operating-system environment and can affect system stability if they malfunction.
  • User-mode drivers run with more isolation in supported architectures, reducing some risks to the operating system.

Industrial hardware may use either model, sometimes together with vendor services and runtime software.

4. Types of Drivers Found in an IPC

Driver category Typical devices or functions Maintenance consideration
Chipset Platform controllers and system interfaces Install the package approved for the motherboard
Ethernet Integrated or add-on network adapters Preserve IP configuration and industrial network behavior
Serial/COM UARTs and serial communication adapters Confirm port number, electrical interface, and settings
USB USB host controllers and supported devices Check device recognition and power-related symptoms
Graphics Integrated or discrete graphics adapters Confirm display resolution and application compatibility
Audio Sound controllers Usually low criticality unless audio alerts are required
Storage Storage controllers and supported drive interfaces High caution because incorrect changes may prevent booting
Touchscreen Touch input hardware Validate touch mapping and calibration
Fieldbus Specialized industrial communication cards Confirm exact hardware, firmware, runtime, and driver compatibility
DAQ Measurement and data-acquisition devices Verify channels, sampling, timing, and vendor libraries

Some devices use inbox drivers supplied with the operating system. Others require a vendor package. A device appearing in Device Manager does not necessarily mean all required vendor functionality is installed.

5. Windows Driver Architecture and Dependencies

Windows driver installation and operation can involve multiple components:

  • Operating-system kernel and driver framework.
  • Device-specific driver package.
  • Hardware firmware.
  • Vendor services or background processes.
  • Runtime libraries and application programming interfaces.
  • Application software that consumes the device's functionality.

For example, a machine-vision application may depend on the camera driver, a vendor runtime, a compatible graphics driver, and a particular application release. Installing the camera driver alone may not restore the complete function.

Vision application
        ↓
Vendor runtime / SDK
        ↓
Camera device driver
        ↓
Camera interface hardware
        ↓
Industrial camera

The actual architecture depends on the device and vendor. Document dependencies instead of assuming that every industrial device follows one universal arrangement.

6. Identifying Installed Drivers

6.1 Device Manager

Run:

devmgmt.msc

Use Device Manager to inspect:

  • Device name and category.
  • Device status and error codes.
  • Driver provider.
  • Driver date and version.
  • Hardware IDs and compatible IDs.
  • Driver details and associated files.
  • Device resources and supported settings.

An unknown device or a yellow warning icon indicates that the device requires investigation. It does not independently establish whether the cause is a missing driver, incorrect driver, hardware fault, or configuration issue.

6.2 System Information

Run:

msinfo32

System Information can help establish the IPC model, operating-system details, hardware resources, and conflicting devices.

6.3 PowerShell: List signed driver inventory

Run PowerShell as an authorized user:

Get-CimInstance Win32_PnPSignedDriver |
    Select-Object DeviceName, Manufacturer, DriverVersion, DriverDate, InfName, IsSigned |
    Sort-Object DeviceName |
    Format-Table -AutoSize

This provides a useful inventory of reported Plug and Play signed-driver information. It is not a complete inventory of every kernel component, application dependency, firmware version, or software package.

6.4 Identify a particular device

For example, to inspect reported Ethernet-related driver entries:

Get-CimInstance Win32_PnPSignedDriver |
    Where-Object { $_.DeviceName -match 'Ethernet|Network' } |
    Select-Object DeviceName, Manufacturer, DriverVersion, DriverDate, InfName |
    Format-Table -AutoSize

Device names vary by manufacturer, and this filter may omit adapters whose names do not contain the specified terms.

6.5 Driver Store inventory

On supported Windows versions, run:

pnputil /enum-drivers

This lists third-party driver packages in the Windows Driver Store.

The Driver Store is not simply a folder of interchangeable driver files. Windows uses package metadata, signing, compatibility information, and installation mechanisms to manage drivers. Do not delete package files manually.

7. Driver Installation Methods

7.1 Windows Update

Windows Update may deliver drivers approved for the operating system and hardware.

Advantages:

  • Convenient installation.
  • Integration with Windows servicing.
  • Potential security and compatibility improvements.

Limitations in industrial systems:

  • A generic or newer driver may behave differently from the vendor-validated release.
  • An update may affect communication, graphics, timing, or peripheral behavior.
  • Availability depends on the device, operating system, update policy, and manufacturer.

Production IPCs should follow the site's approved update process rather than automatically installing every offered driver.

7.2 OEM support package

The IPC or motherboard manufacturer may provide a tested package for a particular hardware model and operating-system release.

This is often the preferred source because it can account for board-specific hardware, firmware, and configuration.

7.3 Device manufacturer package

A hardware manufacturer may provide a driver for a particular network adapter, fieldbus card, camera, serial adapter, or other component.

Confirm the exact device model and hardware revision. Similar product names may represent different hardware revisions.

7.4 Approved offline installation

Industrial IPCs may be isolated from the internet. In such cases, use a controlled offline package stored in an approved software repository.

Record the package source, version, checksum where available, digital signature status, target device, and approval record.

7.5 Manual INF installation

On supported Windows systems, an authorized administrator can install a suitable driver package using Windows' supported driver-management mechanisms.

Example:

pnputil /add-driver "D:\Approved_Drivers\Device\driver.inf" /install

Use this only after confirming that the package is intended for the device and operating system. The command does not guarantee that Windows will replace a currently installed driver if package ranking, compatibility, or policy prevents it.

Do not install an arbitrary INF file simply because its name looks relevant.

8. Driver Compatibility

A driver must be compatible with several parts of the system.

Compatibility dimension What to verify
Operating system Supported Windows or Linux release
Architecture x64, ARM64, or another supported architecture
Hardware model Exact device model and revision
Hardware ID Device identifier supported by the package
Firmware Required or supported device firmware
Application Vendor runtime and application version
Dependency Required libraries, services, or frameworks
Signing and security policy Package signing and applicable platform restrictions
OEM validation Tested configuration for the IPC
Operational requirements Performance, communication, and timing behavior

8.1 Hardware IDs

Windows hardware IDs help identify a device and match it with a suitable driver package.

In Device Manager:

  1. Open the device's Properties.
  2. Select the Details tab.
  3. Select Hardware Ids from the property list.
  4. Record the identifiers for the maintenance report.

Use these identifiers to confirm driver compatibility with the hardware manufacturer's documentation.

8.2 Operating-system architecture

A driver built for one architecture or operating-system environment cannot automatically be used in another.

For example, a legacy 32-bit driver may not work on a 64-bit Windows installation. Kernel-mode driver signing and security requirements also vary by platform and configuration.

8.3 Legacy industrial equipment

Older IPCs may rely on discontinued drivers, older operating systems, or vendor-specific packages.

Do not replace a functioning legacy driver merely because a newer release exists for another device revision. Preserve the validated configuration, maintain installation media, and evaluate migration risk before changing it.

9. Driver Failure Symptoms

Symptom Possible explanation Initial check
Device shown as Unknown Missing or unmatched driver Inspect hardware IDs
Device Manager error code Driver, device, resource, or configuration issue Record exact error code and device status
Ethernet adapter missing Driver failure, disabled device, hardware fault Check Device Manager, BIOS settings, and hardware
Ethernet link present but no communication IP configuration, routing, switch, protocol, firewall, or driver issue Separate physical link from network communication
Serial port missing Driver, BIOS setting, adapter, or port configuration Inspect COM-port enumeration and hardware
USB device repeatedly disconnects Driver, cable, connector, power, or device fault Test using the approved procedure
Graphics glitches Driver, application, display hardware, or temperature issue Check logs, version, and OEM diagnostics
Blue screen after driver update Incompatible or defective driver, or another hardware/software fault Preserve stop code and crash evidence

A successful device enumeration is not proof that the device functions correctly under production load.

10. Windows Device Manager Error Codes

Common Windows Device Manager codes provide diagnostic direction, but their meaning should be confirmed against the exact Windows version and error message.

Code General meaning Practical response
Code 10 Device cannot start Check driver compatibility, device status, resources, and hardware
Code 28 Drivers are not installed Identify hardware IDs and install a suitable package
Code 31 Windows cannot load required drivers Inspect driver dependencies, package integrity, and logs
Code 43 Device reported a problem and Windows stopped it Investigate driver, firmware, and hardware
Code 45 Device is not currently connected Check physical connection, power, and device presence
Code 39 Driver may be missing or damaged, or Windows cannot load it Inspect package, configuration, and relevant system logs

Do not treat an error code as a definitive diagnosis. For example, Code 43 does not always mean the physical device is defective.

11. Driver Rollback and Recovery

A driver change may introduce instability or remove required functionality. A controlled rollback restores a previously validated version when the rollback package and operating-system support permit it.

11.1 Before changing a driver

  • Record the current version, provider, and INF/package information.
  • Record device settings and network configuration where relevant.
  • Confirm that the original package is available.
  • Preserve the IPC system image or approved recovery backup where required.
  • Record the reason for the change and expected result.
  • Obtain authorization and arrange a maintenance window.
  • Confirm a recovery method if the device or operating system becomes unusable.

11.2 Rollback procedure

  1. Identify the exact device and current driver.
  2. Review the change record and confirm which version previously worked.
  3. Use the supported Device Manager rollback option when available, or reinstall the validated package through an approved process.
  4. Restart only if required and authorized.
  5. Confirm the reported driver version.
  6. Test the affected hardware and all dependent applications.
  7. Review logs and monitor stability.
  8. Record the result and close or escalate the change.

A rollback option may be unavailable if Windows no longer retains the previous driver package. Maintain a separate approved copy of the validated package.

11.3 Why System Restore is not a complete driver recovery plan

System Restore can help recover some system configuration changes, but it is not a substitute for a verified system image, driver repository, application installer set, and documented recovery procedure.

For production IPCs, the recovery strategy should account for operating-system bootability, hardware drivers, application dependencies, and required configuration.

12. Driver Update Risk Management

Driver updates should be treated as controlled technical changes rather than routine cosmetic upgrades.

Potential risks include:

  • Loss of compatibility with an older industrial application.
  • Network adapter behavior changes.
  • Communication instability with PLCs or industrial devices.
  • Touchscreen or display behavior changes.
  • Failure of legacy software or kernel-level components.
  • Increased CPU usage or reduced performance.
  • Operating-system instability.
  • Changes to device settings or resource allocation.

12.1 Recommended change sequence

Identify the issue or required update
        ↓
Record current configuration
        ↓
Verify OEM compatibility and dependencies
        ↓
Preserve rollback and recovery options
        ↓
Test on a representative system where possible
        ↓
Approve and install during a controlled window
        ↓
Validate hardware and application functions
        ↓
Monitor, document, and close the change

A driver should not be updated solely because its displayed date is old. Older validated drivers may be necessary for stable operation of legacy equipment.

13. Ethernet Drivers in Industrial Automation

Ethernet drivers are especially important where an IPC communicates with PLCs, HMIs, vision systems, SCADA servers, or other networked equipment.

13.1 Typical Ethernet fault layers

Application or industrial protocol
        ↓
IP address, subnet, route and firewall configuration
        ↓
Operating-system network stack
        ↓
Ethernet adapter driver
        ↓
Network interface hardware
        ↓
Cable, switch and connected device

A fault at any layer can interrupt communication.

13.2 Troubleshooting sequence

  1. Confirm the Ethernet adapter appears correctly in the operating system.
  2. Inspect Device Manager for driver errors.
  3. Check the physical link indicators and switch port status.
  4. Review the assigned IP address, subnet mask, gateway, and required routes.
  5. Confirm that the intended industrial network adapter is being used.
  6. Test basic IP connectivity where applicable.
  7. Check the required industrial protocol, application service, firewall rules, and port configuration.
  8. Review adapter settings, power management, and vendor-specific options against the validated configuration.
  9. Compare the current driver with the approved baseline.
  10. Change one variable at a time and retest.

A successful ping does not prove that PLC communication or the industrial application is functioning correctly. It only verifies a limited part of the network path.

13.3 Industrial network configuration protection

Before replacing an Ethernet driver or adapter, document:

  • Adapter name and hardware identifier.
  • Driver version.
  • IP address and subnet mask.
  • Gateway and required routes.
  • VLAN or switch-port requirements, where applicable.
  • DNS settings if used.
  • Required protocol bindings and firewall rules.
  • Adapter-specific settings required by the application.
  • Network role, such as plant network, machine network, or engineering network.

Do not change an industrial IPC's IP address or network binding casually. The system may depend on a specific adapter for communication with the machine controller.

14. Driver Dependencies in HMI, SCADA and Machine Applications

Industrial applications frequently depend on more than one driver.

For example, an IPC-based data-acquisition application may require:

  • A compatible device driver.
  • A vendor runtime or SDK.
  • A supported operating-system release.
  • Correct device configuration.
  • A compatible application version.
  • Required services and permissions.

If the driver is installed correctly but the application still cannot access the device, investigate the complete dependency chain rather than reinstalling the same driver repeatedly.

14.1 Practical diagnostic distinctions

Observation Diagnostic direction
Device missing from operating system Hardware detection, driver installation, connection, firmware
Device appears correctly but vendor utility fails Vendor runtime, permissions, firmware, device configuration
Vendor utility works but application fails Application configuration, runtime compatibility, application permissions
Application works until reboot Startup services, persistent configuration, permissions, device initialization
Device fails only under load Performance, power, thermal behavior, driver defect, application workload

15. Driver Backup and Documentation

A driver inventory alone is not sufficient for disaster recovery. The maintenance team should preserve the actual installation packages and the configuration information needed to restore the device.

Recommended records include:

  • IPC model, asset ID, and hardware revision.
  • Operating-system edition, version, build, and architecture.
  • Device name and hardware IDs.
  • Driver provider, version, date, and package identifier.
  • OEM source and package location.
  • Digital signature or integrity information where available.
  • Firmware and runtime dependencies.
  • Device-specific settings.
  • Installation and rollback instructions.
  • Test results and approval record.

Store packages in a controlled repository with appropriate access permissions and backups. Keep known-good packages separate from untested or newly downloaded versions.

15.1 Driver inventory versus driver backup

Activity Purpose
Driver inventory Identifies installed drivers and versions
Package backup Preserves installation files for later use
System image backup Captures the system state within the image's scope
Configuration backup Preserves settings that may not be stored in the driver package
Recovery test Confirms the required components can actually be restored

A successful inventory command does not prove that all packages needed for a complete recovery are available.

16. Example: Backing Up Third-Party Driver Packages

On supported Windows systems, an authorized administrator can export third-party driver packages to a designated backup folder.

Example:

mkdir D:\IPC_Backup\Drivers
pnputil /export-driver * D:\IPC_Backup\Drivers

Before execution, confirm that the destination exists on the intended backup volume and that the required space and permissions are available.

This command exports eligible third-party packages from the Driver Store. It does not guarantee a complete backup of every inbox driver, vendor application, firmware component, application runtime, or device configuration.

After export:

  1. Verify that the expected packages are present.
  2. Record the source IPC and operating-system build.
  3. Maintain a separate driver inventory.
  4. Store the backup in the approved repository.
  5. Test restoration on compatible hardware or a representative recovery environment where practical.

Do not assume a package exported from one IPC is suitable for a different IPC model.

17. Driver Maintenance in Linux-Based IPCs

Linux industrial PCs also use device drivers, although the management mechanisms differ from Windows.

Important concepts include:

  • Kernel modules.
  • Kernel-version compatibility.
  • Firmware files loaded by supported devices.
  • Distribution packages and repositories.
  • Device-tree and hardware configuration on supported platforms.
  • Vendor libraries and application dependencies.

Useful diagnostic commands include:

lspci -nnk

Lists PCI devices and reports associated kernel drivers where available.

lsusb

Lists USB devices detected by the system.

lsmod

Lists currently loaded kernel modules.

uname -r

Displays the running kernel version.

dmesg

Displays kernel messages, subject to system permissions and logging configuration.

For systems using systemd, the following can help inspect the current boot's kernel messages:

journalctl -k -b

A device may be physically detected while the required kernel module, firmware, or vendor userspace component is missing. Confirm all dependencies before declaring the device operational.

18. Driver Security and Change Control

Drivers often run with significant system privileges. An incompatible or malicious driver can compromise operating-system stability or security.

Maintenance controls should include:

  • Obtaining packages from the IPC OEM or hardware manufacturer's approved source.
  • Verifying digital signatures where supported.
  • Applying organizational software approval procedures.
  • Avoiding unknown driver-download websites and repackaged installers.
  • Restricting unauthorized driver installation.
  • Preserving a known-good package and recovery plan.
  • Testing security updates against application and hardware requirements.
  • Recording changes and approving production deployment.
  • Avoiding permanent disabling of driver-signing or platform security protections to force an installation.

Security requirements must be balanced with validated industrial compatibility. If a legacy device cannot operate under the current security policy, document the risk and plan a controlled mitigation or migration rather than making an undocumented exception.

19. Preventive Maintenance Checklist

Routine review

  • Maintain a driver inventory for each critical IPC.
  • Preserve validated installation packages.
  • Record operating-system and driver versions.
  • Review recurring device errors and system crash records.
  • Check for unauthorized driver or configuration changes.
  • Confirm network and peripheral settings against the approved baseline.
  • Maintain a rollback and recovery procedure.
  • Keep vendor runtimes and application dependencies documented.

After any driver change

  • Verify that the intended package and version are installed.
  • Check Device Manager or the equivalent operating-system diagnostics.
  • Confirm hardware detection and basic functionality.
  • Test dependent applications and industrial communication.
  • Verify relevant machine functions using the approved procedure.
  • Review logs for new warnings or errors.
  • Confirm the recovery package remains available.
  • Update the maintenance record.

Before returning to production

  • Obtain the required production or maintenance authorization.
  • Confirm HMI, SCADA, PLC communication, and applicable peripherals function correctly.
  • Confirm alarms, data logging, and required application services work.
  • Validate machine interlocks and safety-related functions according to the approved procedure.
  • Record the final test result and responsible personnel.

20. Practical Case Study: PLC Communication Lost After a Driver Update

Situation: An IPC communicates with a PLC through an Ethernet adapter. After a driver update and restart, the HMI launches but cannot connect to the PLC.

Initial evidence:

  • The Ethernet adapter appears in Device Manager.
  • The HMI starts normally.
  • PLC communication is unavailable.
  • The problem began after a documented software change.

Investigation:

  1. Record the current adapter driver version and compare it with the approved baseline.
  2. Check the physical link and switch port.
  3. Verify the adapter's IP address, subnet mask, routes, and required bindings.
  4. Confirm that the HMI uses the intended network adapter and destination address.
  5. Check the industrial communication service, protocol configuration, firewall settings, and application logs.
  6. Determine whether the driver update changed adapter behavior or settings.
  7. If evidence supports a regression, use the approved rollback procedure to restore the previously validated package.
  8. Recheck basic network connectivity and then validate actual PLC communication and HMI data exchange.

Possible conclusion: If the validated driver restores communication without other configuration changes, the update is a strong candidate for the cause. Record the evidence and prevent uncontrolled redeployment until the compatibility issue is resolved.

If rollback does not restore communication, continue investigating other layers. Temporal association is useful evidence, but it is not proof of causation.

22. Interview Questions and Answers

1. What is a device driver?

A device driver is software that enables an operating system to communicate with and control a hardware device through a supported interface.

2. Can a faulty driver cause a blue screen?

Yes. A defective or incompatible kernel-mode driver can cause system crashes. Hardware faults and other software issues can also cause blue screens.

3. What is the difference between a driver and firmware?

A driver is software used by the operating system to communicate with a device. Firmware runs on the device or controller itself. They may need compatible versions but serve different roles.

4. Why should the latest driver not always be installed on a production IPC?

The latest release may not be validated for the specific IPC, operating system, firmware, or industrial application. A known-good compatible release may be safer until an update is tested.

5. What is an INF file?

An INF file is a Windows driver-installation information file that describes device matching and installation details. It is normally part of a driver package.

6. What is the Windows Driver Store?

It is a managed repository of driver packages used by Windows for installation and driver management. Packages should be managed through supported tools rather than by manually deleting files.

7. How would you troubleshoot a missing Ethernet adapter?

Check Device Manager, hardware detection, BIOS settings, hardware connections, driver status, hardware IDs, and OEM diagnostics. Then test the network path after confirming that the adapter is functional.

8. What is a driver rollback?

Rollback restores a previously working driver version when supported and when the prior package is available. The result must be verified through hardware and application testing.

9. Does a successful ping prove that PLC communication works?

No. A ping tests basic IP reachability. The required industrial protocol, application configuration, port, service, and data exchange must also be validated.

10. What should be included in an IPC driver backup?

An inventory of installed drivers, actual installation packages, hardware identifiers, OS details, configuration settings, dependency information, and tested restoration instructions.

11. Why can a device appear correctly in Device Manager but still fail in an application?

The device may have a functional base driver but lack a vendor runtime, required service, application-compatible library, permission, or correct configuration.

12. What is the safest way to change a critical industrial driver?

Record the baseline, verify compatibility, preserve the previous package and recovery method, obtain authorization, test the change in a controlled window, validate the full application, and document the outcome.

23. Key Maintenance Principles

  • Identify the exact hardware before selecting a driver.
  • Preserve the validated driver version and installation package.
  • Treat driver changes as controlled changes to a production system.
  • Diagnose the complete dependency chain, not only the driver file.
  • Separate device detection, basic connectivity, and application-level operation.
  • Maintain tested rollback and recovery options.
  • Validate industrial communication and machine functions before returning the IPC to production.
