1. Purpose of Software Licensing

Software licensing defines the legal and technical conditions under which software may be installed, activated, used, maintained, transferred, or upgraded.

In an industrial environment, licensing is part of equipment availability and recovery planning. An IPC may be physically healthy, Windows may boot correctly, and all drivers may work, yet a machine application may refuse to start because its license is missing, expired, invalid, bound to different hardware, or unable to reach its license server.

Examples of industrial software that may require licensing include:

  • Windows operating systems.
  • PLC programming and engineering software.
  • HMI and SCADA development or runtime software.
  • CNC programming and machine-tool applications.
  • Robot programming and simulation software.
  • Machine-vision software and inspection runtimes.
  • Industrial communication drivers and protocol libraries.
  • Database platforms and reporting tools.
  • Remote-access, backup, and cybersecurity applications.

Licensing must be managed alongside software versions, hardware details, installation packages, configuration backups, and recovery procedures.

2. Why Licensing Matters in Industrial Maintenance

Consider an IPC that runs a machine-vision inspection system. The SSD fails and is replaced. The operating system and application are restored from backup, but the application license was tied to the original hardware or was stored separately from the backup.

The software may now install correctly but refuse to run. Production recovery is delayed while the license is recovered or rehosted through the vendor's approved process.

This is not necessarily a hardware failure or a defective backup. It is a software entitlement and recovery-planning failure.

Licensing issue Possible operational impact
Missing license Application will not start or enters a restricted mode
Expired license Functions stop or become restricted, depending on the license
Incorrect edition Required features are unavailable
License bound to replaced hardware Reactivation or rehosting may be required
License server unavailable Network-dependent software may fail to authorize use
Lost activation credentials Recovery is delayed
Wrong software version License may not support the installed release
Exhausted floating-license pool New users or applications cannot obtain a license
Missing runtime license Development tools may work, but the deployed application may not run
Unauthorized use Legal, contractual, audit, and operational risks

A license failure can resemble an application defect. Check the licensing status before repeatedly reinstalling software or replacing healthy hardware.

3. Essential Licensing Terminology

3.1 License

The legal and technical authorization to use software under specified conditions.

3.2 Activation

A process through which software or a licensing service verifies that the installation is authorized. Activation may be online, offline, device-bound, account-based, or managed through an organizational server.

3.3 Product key

A code used by certain software products to install, activate, or identify a license. A product key is not necessarily the complete license entitlement, and possessing a key does not automatically prove that the software is correctly licensed.

3.4 License entitlement

The right to use a product or feature under a contract, subscription, purchase, or other authorization.

3.5 License certificate or proof of purchase

Documentation supporting the license entitlement. The exact evidence required depends on the vendor and license agreement.

3.6 License server

A server that manages or distributes licenses to authorized clients, often for concurrent use.

3.7 License manager

Software that manages activation, entitlements, license files, or communication with a license server.

3.8 License dongle

A physical hardware token, commonly connected through USB or another supported interface, that participates in license authorization.

3.9 Rehosting

A vendor-authorized process for transferring a license from one machine or license host to another.

3.10 Deactivation

A supported process for releasing or removing an activation so that it may be used elsewhere, where the license terms permit this.

3.11 Subscription

A license arrangement that typically grants use for a defined period, often with renewal requirements.

3.12 Perpetual license

A license arrangement that permits ongoing use under its terms, generally without a fixed subscription end date. It does not necessarily include unlimited updates, maintenance, or technical support.

3.13 Runtime license

Authorization to execute deployed software, such as an HMI runtime or machine-vision inspection application.

3.14 Engineering license

Authorization to develop, edit, configure, or troubleshoot a system using engineering software.

An engineering license does not automatically include permission to deploy or run the resulting application on a production machine.

4. Common License Models

License model How it works Industrial maintenance consideration
Device-bound Associated with a specific PC or hardware identity Hardware replacement may require reactivation
Node-locked Assigned to a particular authorized machine or host Verify transfer and recovery conditions
Floating or concurrent Shared pool of licenses managed by a license server Server availability and license-pool capacity matter
Named-user Assigned to an authorized user User identity and account access must be maintained
Subscription Authorization remains valid during the subscription period Track renewal dates and payment or contract status
Perpetual Continued use is permitted under the license terms Confirm supported versions and update rights
USB-dongle-based Uses a physical token for authorization Protect the dongle and verify replacement policy
Network or site license Covers a defined organization, site, or deployment scope Confirm scope, permitted installations, and concurrency
Feature-based Unlocks specified functions or modules Confirm that all required machine features are licensed

Vendors use different terminology, and license models may be combined. A dongle, for example, may provide a node-locked or network-managed entitlement depending on the product.

Never infer the legal scope of a license from its technical activation method alone.

5. Windows Licensing in Industrial PCs

Windows licensing should be considered separately from the licenses for the machine applications installed on Windows.

Common licensing arrangements include OEM, retail, and volume licensing, subject to the relevant product terms.

License arrangement General characteristic IPC maintenance consideration
OEM Supplied with a particular computer or by an OEM under applicable terms Transfer and reactivation rights may be restricted
Retail Purchased separately under its applicable license terms Transfer rights depend on the agreement and product
Volume licensing Managed under an organization's licensing agreement Follow organizational activation and compliance processes
Subscription-based Windows entitlement Authorization depends on the applicable subscription and conditions Track account, subscription, and activation status

5.1 Windows activation is not the same as application licensing

An IPC can have activated Windows while its HMI or SCADA application remains unlicensed.

Likewise, a licensed machine application does not establish that the underlying Windows installation is properly licensed.

Track the operating-system entitlement and each important application entitlement separately.

5.2 Check Windows activation status

On supported Windows systems, open:

Settings > System > Activation

The exact navigation and displayed information vary by Windows version and edition.

An authorized administrator can also run:

slmgr /xpr

This displays Windows activation expiration information where applicable. The result should be interpreted according to the Windows edition and licensing channel. It does not verify every aspect of legal compliance.

Another command is:

slmgr /dlv

This displays detailed Windows licensing information. Treat the output as administrative information and do not publish sensitive identifiers or activation details unnecessarily.

Important: Windows activation status alone is not a complete audit of license entitlement, permitted use, or organizational compliance.

6. Industrial Automation Software Licensing

Automation software often separates engineering functionality from runtime functionality.

Examples include PLC programming software, HMI development tools, SCADA platforms, CNC-related engineering tools, robot software, and machine-vision suites.

A single vendor product may offer separate entitlements for:

  • Basic programming.
  • Advanced programming.
  • Simulation.
  • Online connection or troubleshooting.
  • HMI or SCADA runtime.
  • Number of runtime tags.
  • Number of clients or servers.
  • Specific communication drivers.
  • Machine-vision tools or algorithm modules.
  • Historical data, reporting, or database connectors.
  • Optional advanced features.

6.1 Engineering versus runtime licensing

Function Engineering license Runtime license
Create or edit projects Usually included when permitted by the license Not necessarily included
Download or configure a controller Depends on the product and entitlement Not necessarily included
Execute a deployed HMI Not necessarily included Commonly the runtime entitlement's purpose
Run a production SCADA application Not necessarily included Often requires separate authorization
Access advanced modules Depends on the selected engineering edition May require separate runtime features

Do not assume that a project can run in production merely because it opens in the engineering environment.

6.2 PLC software example

An engineer may have a licensed engineering workstation with the appropriate PLC programming software. The production IPC, however, may use a separate runtime or communication component.

When recovering the workstation or IPC, verify:

  • Exact software edition and version.
  • Supported operating-system version.
  • Required engineering or runtime license.
  • Communication drivers and runtime dependencies.
  • License activation or server connectivity.
  • Project compatibility.
  • Required authorization for online access.

Do not modify PLC logic or machine configuration merely to work around a licensing problem.

7. License Storage and Activation Mechanisms

Licensing information may be stored or managed in different ways.

Mechanism Description Recovery concern
Local activation data Stored locally by the software or licensing service May be lost or invalidated after system changes
Hardware fingerprint Derived from selected hardware characteristics Hardware replacement may trigger reactivation
USB dongle Physical token used for authorization Token damage, loss, or driver failure
License file File containing license data or authorization information File integrity, location, permissions, and host binding
License server Centralized license allocation and validation Server, network, time, and client configuration
Vendor account Authorization linked to a user or organization account Account access, MFA, and organizational ownership
Embedded or OEM entitlement License supplied as part of the equipment OEM recovery procedure and transfer terms
Cloud entitlement Authorization checked through a vendor's online service Internet access, account status, and service availability

A license file may be sensitive or cryptographically protected. Do not edit it, copy it to unauthorized systems, or distribute it without checking the vendor's instructions and the applicable license terms.

8. Hardware Replacement and License Rehosting

Hardware replacement is a major licensing risk when software uses device-bound activation.

Potential triggers include:

  • Replacing an IPC.
  • Replacing a motherboard.
  • Changing a network adapter or other hardware used in the licensing fingerprint.
  • Restoring a system image to different hardware.
  • Reinstalling the operating system.
  • Changing the license server or its identity.
  • Replacing a physical license dongle.

The impact depends on the vendor's licensing design. A RAM or SSD replacement may have no licensing effect in one product and may trigger reactivation in another. Never assume that a specific hardware change is harmless to every license.

8.1 Before replacing an IPC

  1. Identify every licensed application and component on the original IPC.
  2. Record product name, edition, version, license model, and current status.
  3. Locate proof of entitlement, vendor account details, and the approved license administrator.
  4. Review vendor-specific transfer, deactivation, and rehosting instructions.
  5. Confirm that the replacement IPC supports the required software version.
  6. Preserve approved installation packages and configuration backups.
  7. Determine whether a license server, dongle, or vendor authorization is required.
  8. Obtain authorization for deactivation or transfer before removing the original system, where applicable.

8.2 Controlled rehosting procedure

  1. Confirm that the entitlement permits the proposed transfer.
  2. Verify the identity of the old and replacement systems.
  3. Back up the relevant application configuration and preserve recovery evidence.
  4. Use the vendor-approved deactivation or rehosting procedure.
  5. Activate the license on the intended replacement system.
  6. Confirm the reported license status and enabled features.
  7. Test the actual application and its required hardware interfaces.
  8. Update the asset and license register.
  9. Retain the vendor transaction or support reference.

Some licenses require vendor intervention, while others support self-service transfers. If the original IPC has failed, do not repeatedly attempt activation or alter system identity values. Follow the vendor's failed-hardware recovery process.

9. Floating Licenses and License Servers

A floating license permits authorized clients to use licenses from a shared pool, subject to the vendor's rules and concurrent-use limits.

For example, an organization may have five concurrent engineering licenses shared among several engineering workstations. If all five are in use, another user may be unable to obtain a license until one is released.

9.1 Typical architecture

Engineering workstation A ─┐
Engineering workstation B ─┼→ License server → License pool
Engineering workstation C ─┘

This is a simplified model. Actual licensing systems may use redundant servers, vendor-specific ports, authentication, and other services.

9.2 Common license-server failures

  • Server powered off or unavailable.
  • Network routing or firewall problems.
  • Incorrect server address or port configuration.
  • License service stopped.
  • License file invalid or expired.
  • All concurrent licenses in use.
  • Server identity changed after hardware replacement.
  • DNS or time-related problems.
  • Client configuration points to the wrong server.

9.3 Troubleshooting sequence

  1. Confirm the client's exact licensing error.
  2. Verify the configured license-server address.
  3. Confirm basic network reachability.
  4. Check that the vendor's license service is running.
  5. Verify that the required port and protocol are permitted by the approved network policy.
  6. Check license availability and current usage through the vendor's administration tool.
  7. Review server and client logs.
  8. Confirm the license file or entitlement is valid for the installed software version.
  9. Test with an authorized client and record the result.

A successful ping does not prove that the license service is listening or that the client is authorized to obtain a license.

10. USB License Dongles

Some industrial software uses a physical dongle as part of its license mechanism.

The dongle may depend on a compatible driver or licensing runtime. A working USB port alone does not prove that the application can access the license token.

10.1 Common symptoms

  • Software reports that the license dongle is missing.
  • The dongle appears inconsistently.
  • The licensing service cannot detect the token.
  • The application works on one IPC but not another.
  • A driver update causes license detection problems.

10.2 Diagnostic checks

  • Confirm the dongle's asset identifier where available.
  • Inspect the USB device in Device Manager or the relevant operating-system tools.
  • Verify the required vendor licensing runtime and driver.
  • Check application compatibility and permissions.
  • Follow the vendor's approved port and hub requirements.
  • Test the dongle using the vendor's diagnostic utility.
  • Verify that the license entitlement matches the required software.

Do not clone a dongle, modify its contents, or attempt to bypass its authorization mechanism. If the dongle is damaged or lost, use the vendor's replacement process.

11. License Expiry and Subscription Management

Licenses may expire, subscriptions may lapse, maintenance agreements may end, and temporary licenses may reach their defined limit.

These are different conditions and may have different effects.

Condition Meaning Maintenance response
Subscription expired The subscription period has ended Confirm renewal and entitlement status
Temporary license expired A time-limited authorization has ended Obtain an authorized extension or permanent entitlement
Maintenance contract expired Support or upgrade rights may have ended Verify the contract's scope and applicable rights
License file expired A license artifact has reached its specified end date Confirm renewal or replacement with the vendor
License server unavailable Authorization cannot be obtained from the server Restore the service or approved connectivity
Concurrent pool exhausted Available licenses are currently allocated Review legitimate usage and pool capacity
Activation limit reached The system refuses another activation under current conditions Follow the vendor's rehosting or activation-limit process

A perpetual license may continue to permit use after a support agreement expires, depending on its terms. Conversely, a subscription-based runtime may stop functioning or become restricted after expiry. Always check the actual agreement and vendor behavior.

11.1 Expiry tracking

Maintain an advance-notification process for time-limited licenses. The lead time should account for purchasing, vendor approval, payment processing, testing, and the production maintenance window.

Do not wait until the software refuses to start before discovering that renewal takes several weeks.

13. Licensing and Backup/Disaster Recovery

A system backup may contain application files and settings but still fail to restore a usable licensed application.

Recovery planning should address both technical restoration and authorization restoration.

13.1 What should be preserved

  • Approved software installers and required runtime packages.
  • Supported operating-system edition and version.
  • Application version and configuration backup.
  • License model and entitlement information.
  • License-server address and approved configuration.
  • Dongle identification and storage location.
  • Vendor account ownership and authorized administrator details.
  • Deactivation and rehosting instructions.
  • Renewal or expiry details.
  • Proof of purchase or applicable entitlement documentation.
  • Vendor support or recovery case references.

Some license activations cannot be backed up and restored by copying files. Their recovery depends on the vendor's authorization system. A system image alone does not guarantee that the application will reactivate.

13.2 Recovery test

A useful recovery test should confirm:

  1. The operating system can be restored on the intended hardware.
  2. The application can be installed at a supported version.
  3. Required drivers and runtimes are present.
  4. The license can be restored, reactivated, or rehosted through the approved process.
  5. Required features are enabled.
  6. The application communicates with the required hardware.
  7. The system passes its functional acceptance checks.

For critical systems, record the recovery time and any dependency on vendor support.

14. Software Licensing Compliance

Licensing is both a technical and contractual responsibility.

Typical compliance risks include:

  • Installing more copies than permitted.
  • Using one node-locked license on multiple systems contrary to its terms.
  • Sharing credentials between unauthorized users.
  • Installing software from unapproved or modified packages.
  • Continuing use after a license has expired when the terms do not permit it.
  • Using a development license for production runtime without authorization.
  • Transferring an OEM-bound license to another system without permission.
  • Bypassing license checks or altering license files.

14.1 Good compliance practices

  • Maintain a software inventory and license register.
  • Use approved procurement and installation processes.
  • Assign a responsible license owner.
  • Restrict access to license administration and activation credentials.
  • Track subscription, maintenance, and renewal dates.
  • Reconcile installed software against permitted entitlements.
  • Preserve proof of purchase and vendor correspondence.
  • Remove or retire software according to the organization's approved process.
  • Review license terms before transfer, rehosting, or repurposing an IPC.

An application being technically capable of running on several machines does not mean its license permits installation or simultaneous use on all of them.

15. Troubleshooting Common Licensing Problems

Symptom Possible cause Diagnostic approach
Application reports no valid license Missing activation, license file, dongle, or server Identify the exact license mechanism and inspect its status
License invalid after IPC replacement Hardware-bound activation Verify entitlement and vendor-approved rehosting procedure
License service unavailable Service failure or configuration problem Check service status and logs
License server cannot be reached Network, DNS, firewall, or server issue Test the required service path, not only ping
Application runs with restricted features Wrong edition, missing module, or incomplete entitlement Compare enabled features with the licensed edition
License unexpectedly expired Time-limited license or incorrect system time Verify vendor records, system time, and license validity
Only one user can launch the software Concurrent license limit or allocation issue Check pool capacity and current usage
Dongle not detected USB connection, driver, runtime, or token fault Use the vendor's diagnostic tools

Software launches but machine function is unavailable Missing runtime feature, communication driver, or configuration Validate the complete application dependency chain

Always record the exact error message. A vague note such as "license problem" is not enough for effective troubleshooting or vendor escalation.

16. Practical Case Study: License Lost After SSD Replacement

Situation: An IPC runs an industrial HMI application. Its SSD fails and is replaced. Windows and the HMI application are restored, but the HMI reports that no valid license is available.

Initial checks

  • Confirm that the application version is correct.
  • Verify that the expected license mechanism is present.
  • Check whether the license depends on the original hardware identity.
  • Verify the presence of any dongle, license service, license file, or server configuration.
  • Check system time and the exact licensing error.
  • Review the recovery documentation and vendor entitlement record.

Corrective action

If the license is bound to a hardware identity, follow the vendor's authorized reactivation or rehosting process. If it is server-based, restore the correct client configuration and verify server availability. If it uses a dongle, check the token and required licensing runtime.

Validation

  • Confirm that the license manager reports the expected entitlement.
  • Verify that all required features are available.
  • Launch the HMI runtime.
  • Check communication with the PLC and required machine interfaces.
  • Verify alarms, screens, data logging, and other required functions.
  • Complete the authorized production-readiness checks.
  • Update the license register and recovery record.

Lesson

A backup is not fully proven until the licensed application can be restored under the applicable license terms. License recovery must be planned before hardware failure, not improvised while production waits.

17. Preventive Maintenance Checklist

Routine licensing checks

  • Maintain a current inventory of installed licensed software.
  • Confirm the license model for each critical application.
  • Record software editions and versions.
  • Verify the activation or license-server status according to the site's schedule.
  • Track subscription and renewal dates.
  • Confirm ownership of vendor accounts and license administration.
  • Preserve installation packages and entitlement evidence.
  • Maintain approved rehosting and recovery instructions.
  • Review license-server health and capacity where applicable.
  • Verify dongle storage and assignment where applicable.
  • Restrict sensitive activation information.
  • Test recovery for critical licensed applications.

Before hardware or software changes

  • Identify license dependencies before replacing hardware.
  • Confirm transfer and reactivation rights.
  • Record the existing license status.
  • Preserve required configuration and backups.
  • Obtain the required authorization.
  • Confirm that the replacement platform supports the required software version.
  • Follow the vendor's deactivation or rehosting procedure where applicable.
  • Validate the application and production functions after the change.

19. Interview Questions and Answers

1. What is software activation?

Activation is a process used to verify that a software installation is authorized under the applicable licensing arrangement. Its mechanism depends on the vendor and license model.

2. What is the difference between a product key and a license entitlement?

A product key is a technical code used by certain licensing systems. An entitlement is the underlying authorization to use the software. A key alone does not establish every aspect of license compliance.

3. What is the difference between engineering and runtime licenses?

An engineering license permits specified development or configuration activities. A runtime license permits specified execution of deployed software. The actual permissions depend on the vendor's terms.

4. What is a floating license?

A floating license is allocated from a shared license pool, often through a license server. The number of simultaneous users or instances is limited by the applicable entitlement.

5. Why can an application lose its license after IPC replacement?

The license may be associated with the original hardware identity, activation record, dongle, or license-server configuration. The replacement may require authorized reactivation or rehosting.

6. Does a Windows system image guarantee license recovery?

No. The image may restore the operating system and applications, but activation may depend on hardware identity, external servers, accounts, or vendor-controlled processes.

7. What is license rehosting?

Rehosting is a vendor-authorized process for transferring a license to a new machine or license host, where the licensing terms permit it.

8. What should be checked when a floating license is unavailable?

Check server availability, client configuration, network connectivity, the licensing service, required ports, entitlement validity, and whether the license pool is exhausted.

9. Can a perpetual license expire?

A perpetual license generally permits ongoing use under its terms, but support, maintenance, upgrades, or separately licensed subscriptions may expire. The actual agreement determines the rights.

10. What should be included in a license register?

Record the product, edition, version, license model, associated asset or host, entitlement reference, status, renewal requirements, recovery procedure, owner, and evidence location.

11. Why is licensing important in disaster recovery?

A technically restored application may still be unusable if its activation or entitlement cannot be restored. License recovery must be included in the recovery plan and tested where practical.

12. What is the safest response to a license failure on a production IPC?

Record the exact error, verify the licensing mechanism and entitlement, preserve the system state, follow the approved vendor procedure, and validate the complete application before returning the IPC to production.

20. Key Maintenance Principles

  • Maintain license records alongside IPC asset and software inventories.
  • Separate Windows activation from application licensing.
  • Understand the difference between engineering, runtime, subscription, perpetual, and floating entitlements.
  • Verify transfer and rehosting rights before replacing hardware.
  • Protect license keys, dongles, files, and administrative credentials.
  • Include license recovery in backup and disaster-recovery planning.
  • Treat activation failures as a distinct diagnostic category, not automatically as hardware or application defects.
  • Confirm licensed features and machine functionality before returning equipment to production.
