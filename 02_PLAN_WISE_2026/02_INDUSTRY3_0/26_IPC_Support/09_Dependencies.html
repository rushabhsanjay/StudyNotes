1. Purpose of Dependency Management

A software dependency is any component, resource, service, configuration, or external system that an application requires to operate correctly.

An industrial PC rarely runs a single independent program. An HMI may depend on Windows services, communication drivers, runtime libraries, license services, project files, network interfaces, and a PLC. A SCADA application may additionally depend on an OPC server, a database engine, network shares, certificates, and scheduled tasks.

If one dependency fails, the main application may fail to launch, operate partially, or display incorrect or stale data even though Windows appears healthy.

The maintenance objective is to identify, document, verify, and recover the complete dependency chain rather than repeatedly restarting the application and hoping that Windows develops better manners.

2. Types of Dependencies

Dependency type Description Industrial example

Dependencies may be direct or indirect. An HMI may depend directly on an OPC server, while that OPC server depends on a communication driver and network interface. The HMI therefore has an indirect dependency on the network interface as well.

3. Direct and Indirect Dependencies

A direct dependency is something the application uses directly. An indirect dependency is something required by another dependency.

Example:

HMI Runtime
    ↓
OPC Client Interface
    ↓
OPC Server
    ↓
PLC Communication Driver
    ↓
Windows Network Stack
    ↓
Ethernet Adapter
    ↓
Industrial Network
    ↓
PLC

The exact architecture depends on the software. Some HMIs communicate directly with a PLC and do not use OPC.

If the HMI loses PLC data, each component in the actual communication path becomes a possible fault location. A working HMI process does not prove that the OPC server is running, the network route is correct, or the PLC is responding.

3.1 Dependency chain vs. application process

An application can be running while a dependency is unavailable.

For example:

  • The HMI window opens.
  • The HMI runtime is active.
  • The communication driver is loaded.
  • The PLC is unreachable.
  • The HMI displays the last valid values.

In this situation, the application is running, but its operational function is degraded.

For maintenance, distinguish process availability, dependency availability, and functional readiness.

4. Dependencies vs. Startup Order

Dependencies describe what a component needs. Startup order describes when components are started.

A database-dependent application may need the database service to be running before it connects. However, a service showing Running does not always mean the database is ready to accept connections.

Condition Meaning
Component installed Required software files are present
Component enabled The component is configured to be available
Component running Its process or service is active
Component ready It can accept the required requests
Component reachable The application can access it over the required interface
Component functional It successfully performs its required operation
Dependency chain healthy All required components function together

A fixed delay after boot may temporarily hide a startup-order problem, but it does not guarantee readiness. Where supported, use service dependencies, readiness checks, bounded retries, and clear error reporting.

5. Common Windows Runtime Dependencies

Industrial applications may require particular software runtimes and shared libraries.

Examples include:

  • Microsoft .NET Framework.
  • Supported versions of modern .NET.
  • Microsoft Visual C++ Redistributable packages.
  • Java Runtime Environment for applications that require Java.
  • Vendor-specific runtime components.
  • OPC client or server components.
  • Database client libraries and drivers.
  • USB, serial, or hardware interface drivers.

5.1 Why runtime versions matter

An application may have been developed for a specific runtime version or architecture. Installing a different version does not always satisfy the requirement.

Common compatibility issues include:

  • A missing runtime.
  • Incorrect 32-bit or 64-bit components.
  • A required library that is not installed.
  • An unsupported operating-system version.
  • Conflicting or damaged runtime installations.
  • A vendor application that requires a specific patch level.

Do not remove older runtime packages simply because a newer version is present. Multiple industrial applications may depend on different versions, and side-by-side installation may be intentional.

5.2 Diagnosing missing runtime components

Typical clues include:

  • Application fails immediately at launch.
  • Error message names a missing DLL or runtime.
  • Application works on one IPC but not an apparently identical replacement.
  • Application starts after a vendor-approved runtime installation.
  • Windows event logs report application initialization failures.

Confirm the required runtime from the application's vendor documentation or installation package. Avoid downloading individual DLL files from unknown websites. Use the approved installer and validate the application after repair.

6. Windows Services and Service Dependencies

Windows services support many industrial applications, including database engines, licensing services, OPC servers, and data collection services.

A service may depend on other services or system components. The application using that service may also have its own dependencies that are not represented in Windows service configuration.

6.1 Inspect service status

Open the Services console:

services.msc

Or use PowerShell:

Get-Service |
    Select-Object Name, DisplayName, Status, StartType

This inventory is useful for reviewing services, but it does not establish whether each service is required or whether a running service is operationally healthy.

For a particular service:

Get-Service -Name "Spooler" |
    Format-List Name, DisplayName, Status, StartType

Spooler is a Windows print-spooler example, not a generic industrial service. Replace it with a verified service name when investigating an IPC.

6.2 Inspect configured dependencies

Get-Service -Name "Spooler" -RequiredServices

This shows services required by the specified service, subject to the available service information.

To inspect services that depend on a given service:

Get-Service -Name "Spooler" -DependentServices

These commands show service-level relationships, not every application-level dependency. A SCADA application may require a database or communication service without Windows explicitly declaring that relationship.

6.3 Important distinction

A service can be running but unable to perform its function because:

  • Its configuration is invalid.
  • Its license is unavailable.
  • Its required network endpoint is unreachable.
  • Its database is not ready.
  • Its account lacks permissions.
  • Its underlying device is offline.

Always test the function that matters to the application, not just the service state.

7. File, Folder, and Configuration Dependencies

Industrial software may depend on specific project files, configuration files, scripts, device maps, certificates, and data directories.

Examples include:

  • HMI or SCADA projects.
  • PLC communication configuration.
  • Camera or machine-vision recipes.
  • CNC interface settings.
  • OPC endpoint configuration.
  • Database connection settings.
  • Startup scripts.
  • License configuration files.
  • Historical data directories.

7.1 Common failure modes

Symptom Possible dependency failure
Application starts with the wrong project Incorrect project path or launch argument
Application reports missing configuration File missing, renamed, or inaccessible
Application works only when launched manually Different working directory or user context
Application cannot save records Write permissions or insufficient disk space
Application cannot load a recipe Missing file or invalid reference
Application fails after drive replacement Files or configuration not restored
Application fails under a service account Permissions differ from the interactive account

7.2 File permissions

A file may exist but remain inaccessible to the account running the application.

Check:

  • File and folder paths.
  • User or service account.
  • Read, write, and execute permissions as required.
  • Network-share permissions, if applicable.
  • File ownership and inheritance.
  • Whether the path depends on a mapped drive that is unavailable to a service.

Mapped network drives are associated with logon sessions and may not be visible to services. When supported, use the approved UNC path and service-account configuration rather than assuming a drive letter exists in every execution context.

8. Database Dependencies

An industrial application that logs production data may depend on several distinct components:

Data Collection Application
          ↓
Database Client / Driver
          ↓
Network or Local Connection
          ↓
Database Service
          ↓
Database Instance
          ↓
Database, Tables, and Permissions

A failure at any point can interrupt logging.

8.1 Common database dependency failures

  • Database service stopped.
  • Wrong server or instance name.
  • Incorrect TCP port.
  • Network or firewall issue.
  • Invalid credentials.
  • Missing database driver.
  • Database unavailable or recovery still in progress.
  • Missing table or changed schema.
  • Insufficient disk space.
  • Permission denied on the database or table.
  • Connection pool exhausted or application timeout.

8.2 Diagnostic approach

  1. Check whether the database service is running.
  2. Confirm the intended server and instance.
  3. Verify network reachability and the required database endpoint.
  4. Check the application's connection settings.
  5. Confirm authentication and permissions.
  6. Verify the database and required tables are available.
  7. Inspect application and database logs.
  8. Confirm new records are being written correctly.

Do not test by inserting or modifying production records unless the action is approved and the test method is safe.

A successful connection to SQL Server does not prove that the application is writing the correct data. End-to-end validation must confirm that expected records arrive with correct values and timestamps.

9. Communication Dependencies

A communication-dependent application can require more than a driver.

Potential dependencies include:

  • Correct Ethernet adapter.
  • IP address and subnet.
  • Routing and firewall rules.
  • Communication driver.
  • OPC server or protocol gateway.
  • Controller address and path.
  • Controller firmware compatibility.
  • Correct project configuration.
  • Authentication or certificate trust.
  • Device availability and operating state.

9.1 Example: HMI-to-PLC communication

The HMI may depend on an OPC server, which in turn depends on a PLC communication driver and an Ethernet connection.

If the PLC becomes unreachable, the HMI may continue running. If the OPC server fails, several applications may lose data simultaneously. If only one HMI tag is incorrect, the fault may be limited to the tag mapping or data type.

Use the scope of the failure to narrow the investigation:

  • One tag affected: inspect tag mapping, address, data type, and device state.
  • One application affected: inspect that application's configuration and runtime.
  • Multiple applications affected through one server: inspect the shared server.
  • Multiple devices affected on one network interface: inspect the adapter, route, switch, or shared network component.
  • All systems affected after a change: inspect the shared change or dependency.

These are diagnostic clues, not definitive proof.

10. Licensing Dependencies

Industrial software may depend on local activation, a license file, a hardware dongle, a licensing service, or a network license server.

Examples include runtime licenses for HMI software, engineering software, OPC components, machine-vision tools, and database-related software.

Potential failure causes include:

  • License service not running.
  • Dongle not detected.
  • License server unreachable.
  • Incorrect system time.
  • License expired or unavailable.
  • Wrong license edition or feature.
  • Changed hardware identity after IPC replacement.
  • Missing activation after restoring an image.

Do not assume that an application is defective when it reports a license error. Verify the licensing component, entitlement, server connectivity, and supported recovery process.

License files, credentials, and activation details should be handled securely and included in the approved recovery plan where permitted.

11. Security Dependencies

Security configuration can be a functional dependency for industrial applications.

Examples include:

  • Trusted OPC UA certificates.
  • Service-account permissions.
  • Windows firewall rules.
  • Approved endpoint-protection policies.
  • TLS certificates.
  • Authentication services.
  • Password policies.
  • Network segmentation and access-control rules.

A security change may block a previously working connection without physically damaging the system.

For example, an OPC UA client may fail after a server certificate changes. The correct response is to verify the certificate identity, trust chain, validity, and approved security configuration rather than disabling certificate validation.

Similarly, opening a firewall port may restore communication but create an unauthorized network path. Confirm the required source, destination, protocol, and port with the approved design.

12. Dependency Mapping and Inventory

A dependency map documents the components required for an IPC or application to function.

It is useful for:

  • Troubleshooting.
  • Recovery after SSD/HDD replacement.
  • Windows or application upgrades.
  • Vendor migration.
  • Cybersecurity reviews.
  • License management.
  • Change-impact assessment.
  • Obsolescence planning.
  • Standardizing multiple IPCs.

12.1 Example dependency inventory

This table is illustrative. Record the actual dependencies for each machine rather than copying a generic inventory and assuming the plant has become documented by magic.

13. Dependency Impact Analysis

Before modifying a dependency, determine what else may be affected.

For example, updating an OPC server may affect several HMI clients, SCADA applications, and data-collection services.

A dependency change can have three broad impact levels:

  • Local impact: One application or function is affected.
  • Shared impact: Multiple applications or machines rely on the same component.
  • System-wide impact: A common service, network segment, or infrastructure component affects a larger production area.

13.1 Change assessment questions

Before changing a driver, service, runtime, certificate, or shared component, establish:

  1. Which applications depend on it?
  2. Which machines or production areas are affected?
  3. What happens if the change fails?
  4. Can the previous configuration be restored?
  5. Is a vendor-supported rollback available?
  6. Are licenses, configuration files, and credentials recoverable?
  7. How will the change be validated?
  8. Who authorizes production release?

A shared component may appear unimportant on one IPC while supporting several systems elsewhere. Dependency mapping helps reveal that hidden relationship.

14. Dependency Troubleshooting Method

Use a structured procedure.

Step 1: Define the failure

Record the exact symptom, affected machine, application, timestamp, and recent changes.

Step 2: Identify the dependency chain

Determine which components the failing function requires. Start with the application's vendor documentation, configuration, logs, and known-good system records.

Step 3: Check the most direct dependency

For example, if a database logging function fails, verify the configured database endpoint and service before reinstalling the HMI application.

Step 4: Check dependency readiness

A service can be running without being ready. Verify the required function responds successfully.

Step 5: Compare with a known-good configuration

Compare software versions, paths, accounts, network settings, licenses, and configuration files with an approved reference system.

Step 6: Change one controlled variable at a time

Make authorized changes and record each one. Changing several components simultaneously makes the cause of recovery difficult to establish.

Step 7: Validate end-to-end operation

Confirm the actual industrial function works, not merely that a window opens or a service shows Running.

Step 8: Document the outcome

Record the confirmed root cause, corrective action, validation evidence, and any remaining risk.

15. Windows Event Logs and Dependency Failures

Windows and application logs can help identify failures involving services, runtimes, drivers, and startup processes.

Useful locations include:

  • Windows Logs > Application.
  • Windows Logs > System.
  • Applications and Services Logs for the relevant vendor or service.
  • Application-specific logs.
  • Database logs.
  • Centralized security or endpoint-management logs where available.

Potential clues include application crashes, service startup failures, missing-module messages, authentication failures, and communication timeouts.

Correlate timestamps across components. An application error may be a consequence of a dependency failure rather than the original fault.

For example, a SCADA application may log a database connection error at 08:10, while the database service logged a startup failure at 08:09. The earlier event may provide the more useful lead.

16. Backup and Disaster Recovery of Dependencies

A backup is useful only if the restored system can recover the dependencies needed for operation.

For a critical IPC, document:

  • Operating-system edition and version.
  • Required runtime libraries.
  • Device drivers and versions.
  • Industrial communication software.
  • Application installation packages.
  • Project files and configuration.
  • Database client configuration.
  • License and activation recovery.
  • Certificates and trust configuration.
  • Service accounts and required permissions.
  • Startup mechanisms and dependencies.
  • External server addresses and required network access.
  • Approved firewall and security configuration.
  • Recovery sequence and validation criteria.

Secrets such as passwords, private keys, and license credentials must be handled through approved secure processes rather than stored in plain-text maintenance documents.

16.1 Recovery validation

After an image restore or IPC replacement:

  1. Verify the operating system and hardware drivers.
  2. Install or validate required runtime components.
  3. Restore application files and configuration.
  4. Verify licensing.
  5. Check required services and startup tasks.
  6. Confirm network and communication configuration.
  7. Validate database access.
  8. Confirm current PLC or device data.
  9. Check alarms, logging, and other critical functions.
  10. Record the final result and any deviations from the baseline.

A restored desktop is not the same as a recovered production system.

17. Practical Case Study: SCADA Opens but Historical Data Is Missing

Situation: After an IPC restart, the SCADA application opens and displays live values, but historical data is no longer being recorded.

Initial observations:

  • Windows and SCADA start normally.
  • Live PLC values update.
  • Historical records stop at the time of restart.
  • The SCADA application reports a database-related warning.

Investigation:

  1. Verify that live data acquisition is functioning.
  2. Check the database service and configured instance.
  3. Verify the connection string and authentication.
  4. Inspect database and application logs.
  5. Confirm that the required database and tables exist.
  6. Check whether the logging account has the required permissions.
  7. Verify that the application is connected to the intended database.

Possible finding: The database service is running, but the application is configured to connect to an incorrect instance name after a configuration change.

Corrective action: Restore the approved connection configuration, then verify database access and record insertion using an authorized test method.

Validation:

  • Confirm current PLC values remain available.
  • Confirm new historical records are being written.
  • Verify timestamps and representative values.
  • Check for repeated database errors.
  • Confirm the application remains stable after a controlled restart where permitted.
  • Record the confirmed root cause and recovery steps.

This example demonstrates why dependencies must be diagnosed by function. Live data acquisition and historical data logging may rely on different components.

18. Preventive Maintenance Checklist

Routine dependency checks

  • Maintain an inventory of required software and hardware dependencies.
  • Record supported versions and vendor compatibility requirements.
  • Verify critical services and application functions.
  • Confirm license availability and recovery requirements.
  • Check communication drivers and required network interfaces.
  • Verify database access and data logging.
  • Review relevant event logs for repeated dependency failures.
  • Check configuration paths and permissions.
  • Review certificates and trust configuration where applicable.
  • Record shared components used by multiple applications.
  • Verify that required installation packages and configurations are recoverable.
  • Update dependency records after approved changes.

After a software or hardware change

  • Identify all affected applications and machines.
  • Confirm version compatibility.
  • Preserve the previous configuration or approved recovery point.
  • Validate each affected dependency.
  • Perform end-to-end application testing.
  • Confirm communication, alarms, and logging.
  • Review new warnings and errors.
  • Update the dependency inventory and recovery procedure.

20. Interview Questions and Answers

1. What is a software dependency?

A component, resource, configuration, service, or external system required for an application to operate correctly.

2. What is the difference between a direct and indirect dependency?

A direct dependency is used by the application itself. An indirect dependency is required by another component in the application's dependency chain.

3. Why can an application run while its function fails?

The main process may be active while a required service, driver, license, network connection, or database is unavailable.

4. Does a running Windows service prove that the application is ready?

No. The service may be running but unable to accept requests or perform its intended function.

5. Why should runtime libraries not be removed casually?

Different industrial applications may require different runtime versions. Removing one can break another application even if the operating system remains functional.

6. What is dependency impact analysis?

It identifies the applications, machines, and functions affected by changing or losing a shared component.

7. Why is dependency mapping important for disaster recovery?

It helps ensure that the restored IPC includes the required drivers, runtimes, services, configuration, licensing, and external connections needed for production operation.

8. What should be checked when SCADA live values work but historical logging fails?

Check the logging path, database service, connection configuration, authentication, schema, permissions, and database logs independently of live PLC communication.

9. Why can a certificate be a dependency?

Certificate-based communication may require a trusted, valid certificate to establish a secure session. An expired or untrusted certificate can block communication.

10. How should dependency failures be diagnosed?

Identify the failed function, map the dependency chain, check components systematically, compare with the known-good configuration, apply a controlled correction, and validate end-to-end operation.

11. Why is changing several dependencies simultaneously risky?

It makes the root cause harder to identify and complicates rollback if the system becomes less stable.

12. What is the difference between system restoration and functional recovery?

System restoration brings the operating system or image back. Functional recovery verifies that all required dependencies and industrial functions work correctly.

21. Key Maintenance Principles

  • Document both direct and indirect dependencies.
  • Distinguish installed, running, ready, reachable, and functional states.
  • Diagnose the failed function before changing shared components.
  • Preserve known-good versions and configurations.
  • Check licensing, runtime libraries, permissions, and certificates as well as drivers.
  • Assess the impact of shared dependency changes before implementation.
  • Validate end-to-end operation after recovery.
  • Keep the dependency register synchronized with the actual IPC configuration.
