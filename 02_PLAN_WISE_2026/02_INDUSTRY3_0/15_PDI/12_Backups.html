1. Definition

PDI Backups (Software/Parameter) is the systematic process of capturing, verifying, identifying, storing, and maintaining recoverable copies of the software, configuration files, machine parameters, and control-system data associated with equipment during Pre-Delivery Inspection (PDI).

The objective is to preserve the approved machine configuration so that it can be restored after hardware failure, software corruption, incorrect parameter changes, accidental deletion, or replacement of a controller or device.

In industrial automation, a backup is not simply a file copied to a USB drive. It must be identifiable, compatible with the target hardware and firmware, sufficiently complete for the intended recovery, and verified as usable.

A backup is not proven by its existence. It is proven by its integrity, traceability, and demonstrated recoverability.

2. Objectives of PDI Backups

  • Preserve the approved software and parameter configuration before delivery.
  • Establish a known-good recovery point for each relevant automation device.
  • Protect against controller failure, memory corruption, accidental edits, and configuration loss.
  • Record hardware models, firmware versions, software versions, and configuration revisions.
  • Maintain traceability between the installed equipment and its approved backup.
  • Enable faster recovery during commissioning, maintenance, and breakdowns.
  • Preserve safety-related configurations and their corresponding validation records.
  • Prevent restoration of obsolete, incompatible, or unapproved files.
  • Support machine migration, controller replacement, and planned upgrades.
  • Establish ownership, access control, retention, and periodic backup verification.

3. What Must Be Backed Up?

System Backup contents Important considerations
PLC Project/source files, hardware configuration, program blocks, tags, and applicable configuration data Verify controller model, firmware, and project compatibility
HMI Application project, screens, tags, alarms, recipes, and relevant settings Include runtime dependencies and version information
SCADA Project files, tag configuration, alarms, trends, scripts, and communication configuration Protect server settings, credentials, and dependencies appropriately
VFD Parameter set, motor data, control mode, communication settings, and applicable application data Record drive model, firmware, and parameter compatibility
Servo drive Drive parameters, motor identification, tuning values, and axis configuration Preserve approved motion and safety-related settings
CNC Machine parameters, tool and offset data where applicable, PLC programs, and configuration files Follow machine-builder and CNC-manufacturer backup procedures
Robot controller Robot programs, system configuration, mastering or calibration data where supported, and applicable safety configuration Protect calibration data and validate restoration requirements
Safety PLC Safety application, hardware configuration, signatures or checksums where supported, and validation records Use approved safety backup and change-control procedures
Industrial PC Application files, configuration, service settings, and system image where appropriate Include operating-system and application dependencies
Network devices Switch configuration, VLANs, addressing, and relevant industrial network settings Protect management credentials and network security
Database and historian Database backups, schemas, configuration, and required historical data Use database-consistent backup and recovery procedures

The exact backup contents depend on the equipment and recovery objective. Some data, such as robot mastering values or machine-specific CNC parameters, may require special procedures and cannot safely be treated as ordinary program files.

4. Types of Industrial Backups

4.1 Source Project Backup

A source project backup preserves the editable engineering project.

Examples include:

  • Siemens TIA Portal project.
  • Rockwell Studio 5000 Logix Designer project.
  • Mitsubishi GX Works project.
  • HMI engineering project.
  • Robot programming project.

Source files support engineering changes, troubleshooting, documentation, and future modifications.

However, the project saved on an engineering computer may differ from the program currently running in the controller. Uploading from the controller, when supported, and comparing configurations may be necessary to establish the actual installed state.

4.2 Controller or Device Upload

An upload retrieves supported program or configuration data from the actual device into the engineering environment.

This can help capture the installed configuration, but an upload is not automatically a complete source backup.

Depending on the platform, comments, symbolic names, source code, libraries, safety signatures, or other engineering information may be missing or unavailable.

4.3 Parameter Backup

A parameter backup preserves device settings such as:

  • Motor rated voltage, current, frequency, and speed.
  • Acceleration and deceleration times.
  • Control mode and speed limits.
  • Electronic gearing and motion settings.
  • Analog input ranges and scaling configuration.
  • Communication addresses and protocol settings.
  • Alarm thresholds and application-specific settings.

Parameter backups are especially important when replacing a drive or controller with a compatible unit.

A parameter file must be checked against the target hardware and firmware before restoration. Similar model numbers do not guarantee identical parameter structures.

4.4 Full System Image

A system image captures a broader computer environment, potentially including the operating system, installed applications, configuration, and required system partitions.

It is useful for industrial PCs and SCADA servers where rebuilding individual applications would take substantial time.

A system image does not replace separate backups of databases, licenses, encryption keys, or other data that require application-consistent handling.

4.5 Versioned Backup

A versioned backup preserves multiple identifiable configuration states.

For example:

  • R00_INITIAL
  • R01_APPROVED_PDI
  • R02_APPROVED_MODIFICATION
  • R03_POST_COMMISSIONING

Each revision should be associated with a date, reason for change, approval status, and applicable equipment identity.

Do not overwrite the only approved backup with an unverified or experimental version.

5. Backup Procedure During PDI

Step 1: Identify the equipment

Record the device and machine identity before capturing any files.

Typical information includes:

  • Project ID and machine ID.
  • Device tag and equipment location.
  • Manufacturer and exact model.
  • Serial number where relevant.
  • Firmware and engineering-software versions.
  • Existing program or parameter revision.
  • Current machine operating condition.

This prevents files from different machines or similar devices from being mixed.

Step 2: Establish the correct configuration

Determine which configuration is currently installed and whether it matches the approved project.

Compare available engineering files with the running device where supported. Investigate discrepancies before declaring the backup to be the approved configuration.

For safety-related controllers, follow the required authorization, comparison, signature, and validation procedures.

Step 3: Capture the backup

Use the manufacturer's supported engineering software or backup method.

Capture the applicable source projects, parameter files, device configuration, and additional recovery data. Record any elements that cannot be exported or backed up using the selected method.

Avoid changing the live configuration simply to create a backup unless the action is explicitly required, authorized, and controlled.

Step 4: Verify the captured files

Check that:

  • Files exist and are readable.
  • Archives can be opened without errors.
  • Required project components are present.
  • File sizes and timestamps are reasonable.
  • The correct device and revision are identified.
  • The engineering software can open the project where applicable.
  • Checksums are recorded when integrity verification is required.

A successful file copy only proves that data was copied. It does not prove that the program can be restored to the controller.

Step 5: Store the backup securely

Use the approved storage location, such as a controlled engineering repository or authorized server.

Maintain access control and, where appropriate, separate offline or immutable recovery copies.

Do not store sensitive passwords, cryptographic keys, or unrestricted safety-system configuration files in an openly accessible folder.

Step 6: Test recoverability

Where practical and authorized, validate restoration using a suitable test environment, spare controller, simulator, or controlled recovery procedure.

Verify compatibility, required dependencies, expected behavior, and any necessary post-restoration validation.

Restoration testing on production equipment must follow the approved outage, risk-assessment, and authorization process.

Step 7: Record the backup

Update the backup register with the equipment identity, revision, date, storage location, verification status, and responsible person.

Record any exclusions or limitations that could affect recovery.

A consistent naming convention makes it easier to locate the correct file during a breakdown.

Example:

7. Backup Register

A backup register provides a centralized inventory of recoverable configurations.

Field Purpose
BACKUP_ID Unique backup record identifier
PROJECT_ID Project association
MACHINE_ID Machine association
DEVICE_TAG Actual device or component tag
DEVICE_TYPE PLC, HMI, VFD, CNC, robot, etc.
MANUFACTURER Device manufacturer
MODEL Exact hardware model
SERIAL_NO Device serial number where applicable
FIRMWARE_VERSION Installed firmware version
SOFTWARE_VERSION Engineering software version
BACKUP_TYPE Source, upload, parameter, image, or database
REVISION Backup revision
BACKUP_DATE Capture date
CONFIG_STATUS Approved, working, or unverified
INTEGRITY_STATUS Verification result
RESTORE_TEST_STATUS Not tested, passed, or failed
STORAGE_PATH Controlled storage location
CHECKSUM Integrity hash where required
RESPONSIBLE_PERSON Backup owner
REMARKS Limitations and additional recovery information

For an Excel/VBA implementation, these fields can be loaded into an array and indexed through dictionaries using MACHINE_ID, DEVICE_TAG, or BACKUP_ID. This enables rapid retrieval, duplicate detection, missing-backup reports, and revision comparisons without repeatedly searching worksheet cells.

8. Backup Integrity and Verification

8.1 File Integrity

A cryptographic hash such as SHA-256 can be used to detect changes to a backup file.

If the file's hash changes after capture, the file has changed or the data differs. However, a matching hash does not prove that the backup contains the correct program or that it can be restored.

8.2 Configuration Integrity

Verify that the backup corresponds to the intended device and approved configuration.

Useful checks include:

  • Device model and firmware compatibility.
  • Project revision and controller identification.
  • Program comparison or checksum where supported.
  • Parameter comparison against the approved baseline.
  • Safety configuration identity and validation status.
  • Required libraries, licenses, and application dependencies.

8.3 Restoration Verification

A restoration test evaluates whether the backup can actually be used to recover the system.

A typical validation sequence is:

  1. Select the approved backup and compatible target hardware.
  2. Verify the backup identity, revision, and integrity.
  3. Confirm that the restoration procedure and prerequisites are available.
  4. Restore using the manufacturer's approved procedure.
  5. Compare the restored configuration with the expected baseline.
  6. Perform required functional tests and safety validation.
  7. Record the outcome and any limitations.

Not every backup can be tested through a full restoration during PDI. In such cases, record the verification performed, the remaining uncertainty, and the approved recovery plan.

9. Backup, Restore, and Version Control: Key Differences

Activity Purpose Example
Backup Preserve a recoverable configuration Save the approved PLC project
Restore Recover a system from a saved configuration Load a verified project into a replacement controller
Upload Retrieve supported configuration from a device Upload a PLC program to an engineering computer
Download Transfer a project or configuration to a device Download an approved PLC program
Version control Track changes between configuration revisions Compare approved project R01 with R02
Configuration baseline Identify the formally accepted configuration Approved PLC, HMI, and drive revisions
Archive Retain historical records for future reference Preserve superseded project releases
Recovery test Verify the practical usability of recovery data Restore a backup on compatible test hardware

These activities are related but not interchangeable. For example, downloading a project can overwrite the running machine configuration and may cause downtime or unsafe behavior if performed without the required controls.

10. Backup Frequency and Retention

Backup frequency should be based on the equipment's criticality, rate of change, recovery requirements, and applicable organizational policies.

Event Recommended backup consideration
Before initial machine modification Preserve the existing approved configuration
After an approved software change Capture and identify the new approved revision
After drive or motion tuning Record the accepted parameter configuration
Before controller replacement Capture and verify available recovery data
After commissioning Preserve the accepted commissioning configuration
After safety-related changes Follow safety change-control and validation requirements
At scheduled intervals Verify backup availability and integrity
Before planned migration or upgrade Preserve a compatible recovery point
After restoration Record the restored configuration and validation results

Retention periods should be defined by company policy, customer requirements, legal obligations, and operational needs. Critical systems may require multiple recovery points, off-site copies, or immutable storage.

11. Backup Security and Safety Considerations

  • Obtain authorization before uploading, downloading, or modifying live industrial controllers.
  • Protect backup repositories against unauthorized modification and deletion.
  • Restrict access to safety programs, machine recipes, credentials, and sensitive configuration data.
  • Follow change-control procedures for any restoration that changes the running machine.
  • Verify the target device model and firmware before loading a backup.
  • Confirm required licenses and software dependencies before a recovery operation.
  • Ensure that restoration does not unintentionally overwrite newer production data or calibration values.
  • Preserve approved safety configurations and perform required validation after relevant changes.
  • Use malware-scanned, authorized media and follow OT cybersecurity requirements.
  • Maintain a separate, verified recovery copy for critical systems where required.

A backup is a recovery asset, but it can also be a source of risk if an obsolete program, incorrect parameter set, or compromised configuration is restored without verification.

12. Common Backup Failures

Failure Consequence Preventive control
Backup taken from the wrong machine Incorrect configuration may be restored Verify machine and device identity
Only an old engineering project is saved Actual running configuration may be lost Compare against the installed device
Parameter file lacks model identification Incompatible settings may be loaded Record exact model and firmware
Backup file is corrupted Recovery may fail Verify integrity and test restoration
Only one copy exists A single storage failure destroys recovery data Maintain approved redundant copies
Backup is overwritten Previous approved state is lost Preserve versioned releases
Safety configuration is restored without validation Safety requirements may no longer be satisfied Follow safety validation procedures
Licenses or dependencies are missing Application cannot run after restoration Maintain recovery prerequisites
Storage path is incorrect or inaccessible Backup cannot be located during a breakdown Verify retrieval and access permissions
No restore test is performed Recoverability remains uncertain Record and perform appropriate recovery tests

13. PDI Backup Acceptance Checklist

  • Equipment and device identities are recorded.
  • Exact hardware models and applicable firmware versions are documented.
  • The installed configuration has been identified and compared where supported.
  • Required source projects and parameter files have been captured.
  • Safety-related configuration records are handled under the applicable controls.
  • Backup filenames and revisions follow the approved naming convention.
  • Files are readable and pass the required integrity checks.
  • Storage locations and access permissions are verified.
  • The backup register is complete.
  • Required recovery dependencies and licenses are identified.
  • Restoration procedures are documented.
  • Restoration testing is completed where required, or limitations are recorded.
  • Required post-restoration functional checks are defined.
  • The approved backup revision is clearly identified.
  • Required backup deliverables are included in the PDI handover package.

14. Practical Industrial Example

Consider an automated test station containing a Siemens PLC, HMI, servo drive, and industrial PC.

During PDI, the engineer identifies each device, records its model and firmware, captures the approved PLC and HMI projects, saves the accepted servo parameters, and creates an appropriate recovery image or application backup for the industrial PC.

The files are stored under the machine's controlled backup directory. The register identifies the approved revision, storage location, and verification status for each device.

Later, the servo drive fails. A replacement drive is installed. The engineer verifies compatibility, restores the approved parameter set using the manufacturer's procedure, checks motor and feedback configuration, and performs the required commissioning and safety checks before releasing the station.

If the parameter file had been saved without the motor identification, firmware compatibility, or revision information, the file might have existed but still been unsuitable for safe recovery.

The value of PDI backups is therefore not just preservation of data. It is controlled recovery of the correct machine configuration with evidence that the recovered system is suitable for operation.
