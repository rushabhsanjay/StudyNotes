1. Definition

PDI Documentation is the systematic preparation, verification, organization, and control of records generated during Pre-Delivery Inspection (PDI) to demonstrate that a machine, equipment package, or automation system has been inspected and evaluated against specified technical, operational, quality, and safety requirements.

Documentation provides objective evidence of the equipment's condition, inspection results, identified deviations, corrective actions, and release status before delivery or handover.

In industrial automation, PDI documentation connects the physical machine with its electrical drawings, PLC programs, HMI configurations, drive parameters, inspection reports, safety records, and acceptance approvals.

The purpose is not merely to create files. It is to ensure that another engineer can identify the equipment configuration, understand what was verified, reproduce the relevant checks, and investigate failures without depending entirely on the memory of the person who performed the work.

2. Objectives of PDI Documentation

  • Establish traceability between inspection requirements and actual test results.
  • Confirm that the equipment has been inspected against approved specifications.
  • Maintain records of PLC, HMI, CNC, robot, drive, and other automation configurations where applicable.
  • Document electrical, mechanical, instrumentation, and safety inspection results.
  • Record defects, nonconformities, root causes, corrective actions, and retest results.
  • Maintain equipment identification, serial numbers, software versions, and drawing revisions.
  • Provide evidence for customer acceptance, internal quality audits, and project handover.
  • Prevent unauthorized changes and confusion between approved and obsolete documents.
  • Support future installation, commissioning, troubleshooting, maintenance, and upgrades.
  • Establish accountability for inspection, review, approval, and release.

3. Main Categories of PDI Documentation

Category Typical documents Purpose
Project and equipment identification Equipment list, machine tag, serial number, project number Establish equipment identity
Technical specifications Approved specifications, scope of supply, technical datasheets Define acceptance requirements
Mechanical documentation Assembly drawings, layouts, tooling drawings, component lists Verify mechanical construction

Automation documentation PLC I/O lists, architecture, network topology, software versions Establish control-system configuration
HMI and SCADA documentation Screen lists, alarm lists, tag lists, communication settings Record operator-interface configuration

Not every machine requires every document. The applicable document set depends on project requirements, machine complexity, contractual obligations, and governing standards.

4. Essential Documents Explained

4.1 PDI Checklist

The PDI checklist is the controlled list of inspection points used to evaluate the equipment.

Typical fields include:

  • Project and machine identification.
  • Checklist number and revision.
  • Inspection item and acceptance criteria.
  • Inspection method.
  • Actual result and status.
  • Inspector and inspection date.
  • Remarks and nonconformity reference.
  • Reviewer or approver, where required.

Example:

No. Inspection item Acceptance criteria Result Status
1 Panel identification Matches approved drawings Verified Pass
2 Protective earthing Meets applicable requirements Recorded measurement Pass
3 Emergency-stop response Matches approved safety design Function verified Pass
4 Analog input scaling Matches approved engineering range Deviation identified Fail
5 Corrective-action retest Original acceptance criteria satisfied Pending Open

Actual measurements and evidence references should be recorded where necessary. A statement such as "checked OK" is insufficient when the acceptance criterion requires a measurable result.

4.2 Electrical Drawings

Electrical documentation establishes the intended electrical design and helps verify the installed system.

Common documents include:

  • Single-line diagrams.
  • Power and control schematics.
  • Panel layout drawings.
  • Terminal block diagrams.
  • Cable schedules.
  • Earthing and bonding diagrams.
  • PLC I/O wiring diagrams.
  • Network and communication diagrams.

Revision control is critical. The engineer must be able to distinguish the approved drawing from a superseded revision and identify any approved as-built changes.

4.3 PLC and HMI Configuration Records

Automation documentation should identify the actual software and configuration associated with the inspected machine.

Typical records include:

  • PLC manufacturer, model, firmware, and project version.
  • I/O module configuration and channel assignments.
  • HMI model, firmware, application version, and screen configuration.
  • Communication protocols, node addresses, and relevant network settings.
  • Safety PLC or safety relay configuration references, where applicable.
  • Drive, servo, and motion-controller configuration references.
  • Approved source files and their storage locations.
  • Validation status and relevant change history.

For example, a Siemens PLC project created in TIA Portal should be associated with the correct CPU, hardware configuration, firmware compatibility, and project revision. A project file existing on a laptop does not establish that it matches the machine currently being inspected.

4.4 Inspection and Test Reports

A test report records how a requirement was verified and what the test demonstrated.

A useful test record contains:

  • Test identification and objective.
  • Equipment under test.
  • Test procedure and acceptance criteria.
  • Test conditions.
  • Instrument identification and calibration status, when relevant.
  • Actual measured values or observed behavior.
  • Pass/fail result.
  • Tester, date, and supporting evidence.
  • Defects, corrective actions, and retest results.

For example, an analog input test might document the applied signal, expected engineering value, measured PLC value, permitted tolerance, and actual deviation.

4.5 Nonconformity Report

A nonconformity report records a failure to meet a specified requirement.

Typical fields include:

  • Nonconformity identification number.
  • Machine or component reference.
  • Requirement and observed failure.
  • Severity or risk classification.
  • Immediate containment action.
  • Root-cause investigation.
  • Corrective action.
  • Responsible person and target date.
  • Retest evidence and closure approval.

Correction and corrective action are different. Correction fixes the observed problem; corrective action addresses its cause to reduce the likelihood of recurrence.

4.6 Handover Documentation

Handover documentation transfers the required technical information and responsibility to the receiving team or customer.

Depending on the project, it may include:

  • Final approved document index.
  • As-built drawings.
  • Approved software and configuration records.
  • Inspection and test reports.
  • Outstanding punch-list items and their agreed disposition.
  • Operating and maintenance manuals.
  • Training records.
  • Spare-parts lists.
  • Acceptance approvals.
  • Required software backups and recovery instructions.

Handover status must accurately represent unresolved defects and limitations. Signing a document does not make an outstanding technical defect disappear, although paperwork occasionally seems determined to test that theory.

5. Document Identification and Revision Control

Every controlled document should have a unique identity and a clearly defined revision.

A document identification structure may follow this pattern:

PROJECT-MACHINE-DOCUMENTTYPE-SEQUENCE-REVISION

Example:
P1059-MCH01-ELEC-004-R02

This is an illustrative naming convention, not a universal standard.

A controlled document register can contain the following fields:

Field Purpose
Document ID Unique document identifier
Document title Description of the document
Project ID Project association
Machine ID Equipment association
Document type Drawing, checklist, test report, manual, etc.
Revision Current controlled revision
Status Draft, under review, approved, superseded
Owner Person or function responsible
Prepared date Date the document was prepared
Approval date Date of formal approval
Storage location Controlled file or repository reference
Related document Associated drawing, report, or change record

A typical document lifecycle is:

Draft
  ↓
Technical Review
  ↓
Approval
  ↓
Controlled Release
  ↓
Revision or Supersession
  ↓
Archive

The exact approval workflow depends on the organization's document-control procedure.

Important controls include:

  • Only authorized persons can approve controlled documents.
  • Released documents must have identifiable revisions.
  • Superseded revisions must not be mistaken for current instructions.
  • Changes must be traceable to an authorized change request or approved deviation.
  • As-built records must reflect the final installed configuration.
  • Archived records must remain retrievable for the required retention period.

6. Document Traceability

Traceability connects a requirement to the inspection activity, result, defect, corrective action, and approval.

Consider an analog pressure transmitter connected to a PLC.

Traceability element Example
Requirement Transmitter range: 0–10 bar
Instrument tag PT-101
PLC input AI module, channel 3
Expected signal 4–20 mA
Scaling requirement 4 mA = 0 bar; 20 mA = 10 bar
Test evidence Applied signal and recorded PLC value
Finding PLC indicates 10 bar at 18 mA
Corrective action Correct the scaling configuration
Retest Verify zero, intermediate, and full-scale points
Closure evidence Updated test record and approved configuration revision

For a linear 4–20 mA input with a 0–10 bar range, the expected pressure is:

\[ P=\frac{I-4}{20-4}\times 10 \]

where \(I\) is the input current in mA and \(P\) is the pressure in bar.

At 18 mA:

\[ P=\frac{18-4}{16}\times10=8.75\text{ bar} \]

A displayed value of 10 bar therefore indicates a scaling discrepancy under these assumptions. The finding must be investigated and corrected before the relevant acceptance requirement can be marked as passed.

7. Digital Documentation and Data Management

Digital documentation improves retrieval, consistency, comparison, and auditability when supported by controlled processes.

A practical project folder structure might be:

PDI_PROJECT
  ↓
01_Project_Requirements
  ↓
02_Mechanical
  ↓
03_Electrical
  ↓
04_Automation
  ↓
05_Safety
  ↓
06_Inspection_Test_Reports
  ↓
07_Nonconformities_CAPA
  ↓
08_Software_Configuration_Records
  ↓
09_Manuals_Spare_Parts
  ↓
10_Handover_Approval

This is an example structure. The actual arrangement should follow the organization's document-control rules.

For an Excel-based document register, useful fields include DOCUMENT_ID, PROJECT_ID, MACHINE_ID, DOCUMENT_TYPE, REVISION, STATUS, OWNER, APPROVAL_DATE, FILE_PATH, and RELATED_NCR_ID.

Such a register can be used with Excel VBA, dictionaries, arrays, Power Query, or Power BI to automate:

  • Missing-document detection.
  • Duplicate document identification.
  • Revision mismatch checks.
  • Overdue approval tracking.
  • Open nonconformity monitoring.
  • Machine-wise document retrieval.
  • Handover completeness reporting.

For larger projects, a controlled document-management system is preferable to relying on filenames and manually maintained spreadsheets alone.

8. Document Verification During PDI

Documentation itself must be inspected.

The reviewer should verify that:

  • The document belongs to the correct project and machine.
  • The revision is approved and applicable.
  • Equipment tags and component identifiers match the installed equipment.
  • Drawings correspond to the actual wiring and physical arrangement.
  • Software versions and configuration records match the inspected system.
  • Test results satisfy the stated acceptance criteria.
  • Instruments used for critical measurements have appropriate calibration status.
  • Failures are linked to nonconformity records.
  • Corrective actions include the required retest evidence.
  • Required approvals and signatures are present.
  • As-built changes have been incorporated.
  • Required deliverables are complete and accessible.

A document can be present but invalid. For example, an electrical drawing may exist in the project folder but show a superseded terminal assignment. Document availability and document correctness are separate acceptance checks.

10. PDI Documentation Deliverables Checklist

  • Approved project requirements and technical specifications.
  • Current mechanical and electrical drawings.
  • Automation architecture, I/O lists, and network documentation.
  • Applicable PLC, HMI, drive, CNC, and robot configuration records.
  • Safety inspection and validation records.
  • Completed PDI checklists.
  • Inspection and test reports with actual results.
  • Nonconformity register and corrective-action records.
  • Retest evidence for corrected defects.
  • Approved as-built drawings and configuration references.
  • Operating and maintenance manuals.
  • Spare-parts and equipment identification lists.
  • Controlled document index with revision and approval status.
  • Required handover and acceptance records.

11. Final Acceptance Criteria

PDI documentation is acceptable when the required documents are complete, correctly identified, technically consistent with the equipment, appropriately reviewed and approved, and supported by sufficient inspection and test evidence.

Any unresolved deviation must be handled according to its severity and the applicable contractual and safety requirements. Safety-critical failures must not be treated as acceptable merely because the documentation package is complete.

The final objective is configuration traceability, verified compliance, controlled technical information, and a defensible handover record.
