1. Definition of PLC/HMI System

A PLC/HMI system is an industrial automation system in which a Programmable Logic Controller (PLC) executes control logic and a Human-Machine Interface (HMI) provides operators with a visual interface for monitoring equipment, issuing authorized commands, acknowledging alarms, and viewing process information.

During Pre-Delivery Inspection (PDI), PLC/HMI verification confirms that the supplied control hardware, software, configuration, operator screens, communication interfaces, and required documentation conform to the approved design.

A PLC can operate correctly at the program level while the overall machine remains defective because of incorrect I/O wiring, wrong sensor polarity, mismatched HMI tags, incorrect scaling, missing alarms, or an unapproved software revision.

PDI must therefore verify the controller, operator interface, field connections, configuration, and their integration with the machine.

2. Objectives of PLC/HMI PDI

  • Verify PLC, HMI, remote I/O, communication modules, and associated hardware against the approved BOM.
  • Confirm CPU, module, firmware, and configuration compatibility.
  • Verify the installed PLC program and HMI application against approved revisions.
  • Check I/O assignments, channel types, addressing, and field-device mapping.
  • Verify PLC-HMI communication and required network configuration.
  • Inspect HMI screens, process values, commands, alarms, trends, and diagnostic displays.
  • Check data scaling, engineering units, limits, and status interpretation.
  • Verify user access levels and authorized operator functions.
  • Confirm that interlocks and safety-related interfaces behave according to the approved design.
  • Check backups, source files, licenses, passwords or credentials handover arrangements, and recovery documentation as required.
  • Record discrepancies and confirm closure of required defects before release.

HMI Operator Interface

The HMI normally communicates with the PLC through an approved industrial communication interface. Depending on the design, it may also communicate with drives, remote I/O, historians, or supervisory systems.

The HMI is not necessarily the device executing the machine's core control logic. In a typical PLC-controlled machine, the PLC continues executing its program independently of whether the HMI screen is visible, although loss of HMI communication may affect operator access and may trigger application-specific responses.

Safety functions must be implemented in the approved safety architecture. They must not depend solely on ordinary HMI commands or standard PLC logic unless the system has been specifically designed and validated for the required safety function.

4. PLC Hardware Inspection

4.1 CPU and controller

Verify:

  • Manufacturer and exact CPU model.
  • Hardware revision where relevant.
  • Firmware version.
  • Supply requirements.
  • Memory and performance suitability.
  • Communication ports and supported protocols.
  • Operating-mode indication.
  • Diagnostic indicators.
  • Mounting, grounding, and connector condition.
  • Program identity and approved revision.

Examples of common PLC platforms include Siemens SIMATIC, Rockwell Automation Allen-Bradley, Mitsubishi Electric, Omron, and Schneider Electric.

A CPU with a similar product name may still differ in memory, communication capability, firmware support, safety capability, or compatible expansion modules.

4.2 I/O modules

Check:

  • Digital input and output module types.
  • Analog input and output ranges.
  • Channel counts.
  • Electrical ratings.
  • Terminal bases and connector types.
  • Module slot positions.
  • Channel addressing.
  • Compatibility with the CPU and firmware.
  • Field wiring and channel labels.
  • Diagnostic status.

For example, a digital input module and an analog input module are not interchangeable simply because they fit the same rack.

4.3 Remote I/O

Verify:

  • Remote I/O coupler or adapter model.
  • Network protocol and configuration.
  • Module arrangement and addressing.
  • Supply and field-power arrangements.
  • Network cabling and connectors.
  • Required termination and grounding.
  • Communication status and diagnostics.
  • Approved configuration files.

Loss of remote I/O communication can affect multiple field devices simultaneously. PDI should verify the complete interface, not only whether the coupler's status indicator appears normal.

5. PLC Program Verification

5.1 Program identity and revision

Verify:

  • Approved project file.
  • Project name and machine identification.
  • Software version or revision.
  • Controller model and firmware compatibility.
  • Hardware configuration.
  • Required libraries and dependencies.
  • Program checksum or comparison result where the platform supports it.
  • Evidence that the installed program matches the approved version.

The project file on an engineering laptop and the program installed in the PLC are not automatically identical. Use the appropriate upload, comparison, checksum, or version-control procedure to establish the required correspondence.

Uploading a program from a controller can also overwrite or complicate source-project management if the process is not controlled. Follow the approved backup and change-control procedure.

5.2 Logic organization

Inspect the required control functions, including:

  • Startup and initialization.
  • Manual and automatic modes.
  • Sequence control.
  • Permissives and interlocks.
  • Fault detection.
  • Alarm generation.
  • Timers and counters.
  • Analog processing.
  • Communication handling.
  • Recovery and reset behavior.
  • Output-state management during faults or mode changes.

The required depth depends on the PDI specification. A source-code review does not replace functional testing of the actual machine.

5.3 Interlocks and permissives

A permissive is a condition that must be satisfied before an operation is allowed. An interlock prevents an operation when a defined condition makes it invalid or unsafe.

Example: A fixture clamp may be permitted to advance only when the machine is in the correct mode, the relevant station conditions are satisfied, and required guarding conditions are valid.

PDI should verify that the implemented behavior matches the approved functional description and risk assessment.

Do not assume that a condition is safe merely because the PLC program contains a bit named SAFE_OK. The source, validity, behavior, and role of that signal must be established.

6. PLC Input/Output Verification

6.1 Digital inputs

Typical digital inputs include:

  • Proximity sensors.
  • Photoelectric sensors.
  • Limit switches.
  • Pushbuttons.
  • Pressure switches.
  • Guard-interlock status signals.
  • Drive-ready and fault signals.

Verify:

  • Field-device identity.
  • Input channel and address.
  • Correct wiring and supply.
  • PNP/NPN compatibility where applicable.
  • Expected ON/OFF behavior.
  • Signal stability.
  • PLC tag description.
  • HMI indication, where applicable.

A physical sensor may operate correctly while the wrong PLC input is mapped to the intended function. Verify the complete path from field device to controller tag.

6.2 Digital outputs

Typical outputs operate:

  • Solenoid valves.
  • Relays and contactors.
  • Indicator lamps.
  • Buzzer circuits.
  • Drive enable signals.
  • Other control devices.

Verify:

  • Output module type and rating.
  • Channel address and wiring.
  • Required interposing relays.
  • Load current and switching suitability.
  • Output-state behavior.
  • Required feedback.
  • Fault response and reset behavior.

An output command does not prove that the connected device physically operated. Where required, verify feedback from the actuator or process.

6.3 Analog inputs

Typical analog inputs measure:

  • Pressure.
  • Temperature.
  • Flow.
  • Level.
  • Force.
  • Position.
  • Speed or process values.

Common signals include 4–20 mA, 0–10 V, and other ranges specified by the design.

Verify:

  • Sensor range and type.
  • Input module configuration.
  • Wiring and shielding.
  • Engineering-unit scaling.
  • Raw-value conversion.
  • Low- and high-limit behavior.
  • Fault detection for broken wires or out-of-range signals, where supported.
  • HMI display and alarm thresholds.

For linear scaling, the conversion may be represented as:

\[ EU = EU\_{\min} + \frac{Raw-Raw\_{\min}}{Raw\_{\max}-Raw\_{\min}}(EU\_{\max}-EU\_{\min}) \]

Where:

  • \(EU\) is the engineering-unit value.
  • \(Raw\) is the measured raw input value.
  • \(Raw\_{\min}\) and \(Raw\_{\max}\) are the configured raw limits.
  • \(EU\_{\min}\) and \(EU\_{\max}\) are the engineering-unit limits.

The actual raw limits depend on the PLC module, configuration, and data representation. They must not be assumed from a generic example.

7. HMI Hardware Inspection

Verify:

  • Manufacturer and exact model.
  • Screen size and resolution where specified.
  • Supply voltage.
  • Enclosure mounting and sealing.
  • Display condition.
  • Touchscreen response.
  • Communication interfaces.
  • Memory and storage where applicable.
  • Firmware and operating-system requirements.
  • Required licenses.
  • Backup and recovery capability.
  • Physical access and operator ergonomics.

For industrial PCs, also inspect cooling, storage health where supported, network interfaces, approved operating-system configuration, and required security controls.

8. HMI Application Verification

8.1 Screen structure

Check the required screens, which may include:

  • Main overview.
  • Machine status.
  • Manual operation.
  • Automatic sequence.
  • I/O diagnostics.
  • Alarm summary.
  • Alarm history.
  • Trend displays.
  • Recipe management.
  • Maintenance information.
  • Production data.
  • User login and access management.

The actual screen set must match the machine's functional requirements. More screens do not automatically mean a better HMI.

8.2 Tag mapping

Verify that each displayed value or command references the correct PLC tag.

Common errors include:

  • Wrong tag assigned to a screen object.
  • Incorrect data type.
  • Incorrect scaling.
  • Stale or frozen data.
  • Incorrect Boolean inversion.
  • Wrong engineering units.
  • Incorrect alarm threshold.
  • Command mapped to the wrong output or sequence request.

For example, an HMI may display a pressure value of 6.0 bar even though the actual transmitter signal represents 4.0 bar, due to incorrect scaling. The screen can look completely normal while showing the wrong value.

8.3 Operator commands

Check applicable commands such as:

  • Start and stop requests.
  • Manual/automatic mode selection.
  • Sequence initiation.
  • Alarm acknowledgement.
  • Fault reset.
  • Recipe selection.
  • Authorized setpoint changes.

Verify the conditions under which each command is accepted or rejected.

A stop button on an ordinary HMI is generally an operational command, not a substitute for an emergency-stop function. The machine's safety architecture defines the required protective behavior.

8.4 Display behavior and usability

Inspect:

  • Correct status colors and symbols.
  • Readable text and labels.
  • Consistent engineering units.
  • Clear fault messages.
  • Navigation and screen transitions.
  • Visibility of important machine states.
  • Confirmation for consequential actions where required.
  • Appropriate indication of unavailable or invalid data.
  • Avoidance of misleading stale values.

A displayed value should distinguish a valid measurement from an unavailable, stale, or invalid signal where the design requires that distinction.

9. Alarm and Event Verification

An alarm informs the operator of an abnormal condition requiring attention. An event records a change or occurrence, which may or may not require an operator response.

Verify:

  • Alarm description and tag association.
  • Trigger condition.
  • Activation and clearing behavior.
  • Priority and presentation.
  • Timestamp and history retention where required.
  • Acknowledgement behavior.
  • Reset requirements.
  • Alarm response instructions.
  • Correct behavior during communication loss.

Acknowledging an alarm generally confirms that the operator has recognized it. It does not necessarily clear the fault or make the machine safe to operate.

Example:

Alarm Trigger condition Required verification
Low air pressure Pressure falls below the defined limit Check threshold, message, activation, and recovery
Conveyor drive fault Drive fault status becomes active Verify PLC detection and HMI indication
Part not detected Required part sensor remains inactive at a sequence step Verify the sequence condition and fault message
Analog signal fault Input is outside the configured valid range Verify diagnostic detection and displayed status
PLC communication loss HMI detects loss of required PLC communication Verify the specified communication-loss indication and command behavior

The alarm list should be checked against the approved alarm specification. Do not invent alarm thresholds during inspection.

10. PLC-HMI Communication

Common industrial communication methods include:

  • PROFINET.
  • EtherNet/IP.
  • Modbus TCP.
  • Modbus RTU.
  • OPC UA.
  • Manufacturer-specific protocols.

Verify:

  • Correct protocol and device configuration.
  • IP address and subnet settings where applicable.
  • Correct PLC endpoint and connection parameters.
  • Required ports and physical connections.
  • Communication status and diagnostic messages.
  • Update rates appropriate to the application.
  • Correct tag access.
  • Behavior during communication loss and restoration.

A successful network ping does not prove that PLC-HMI application communication or tag exchange is working correctly. Network reachability, protocol connectivity, and application-level data correctness are separate checks.

11. User Access and Configuration Control

Where user authentication is required, verify:

  • Approved user roles.
  • Operator and maintenance permissions.
  • Engineering access restrictions.
  • Recipe and setpoint change permissions.
  • Audit or change history where required.
  • Password and credential handover arrangements.
  • Removal or control of temporary commissioning accounts.
  • Backup access and restoration procedures.

Passwords and credentials should be transferred and stored through the approved secure process, not embedded in an ordinary PDI report.

Configuration control should identify the approved PLC program, HMI project, firmware, hardware configuration, and required backups. Changes made during testing must be tracked and reconciled with the final approved configuration.

12. PLC/HMI Functional Verification

The functional test must prove the intended behavior of the integrated system under controlled conditions.

Typical test cases include:

  • PLC startup and normal operating status.
  • Correct I/O indication.
  • Correct manual and automatic mode behavior.
  • Permissive and interlock responses.
  • Correct sequence progression.
  • Correct actuator commands and feedback.
  • Correct analog scaling and limits.
  • HMI command acceptance and rejection.
  • Alarm activation, acknowledgement, and clearing.
  • Communication-loss detection and recovery.
  • Defined fault and restart behavior.
  • Recovery after power interruption, where specified.

Tests must follow the approved procedure and must not bypass required safety protections.

13. Fault Simulation and Safe Testing

Fault simulation can verify that the system responds correctly to abnormal conditions, but it must be planned.

Examples include:

  • Simulating a sensor state using an approved test method.
  • Using a signal calibrator to verify an analog input.
  • Disconnecting a communication link under controlled test conditions.
  • Testing alarm thresholds with a controlled input.
  • Verifying the required response to drive fault feedback.

Before a test, identify:

  • Expected behavior.
  • Safe machine state.
  • Potential effect on actuators or production equipment.
  • Required isolation or test mode.
  • Test limits and abort conditions.
  • Restoration procedure.
  • Evidence needed to confirm the result.

Never force PLC outputs, bypass interlocks, or simulate safety signals on a live machine without the approved test plan and necessary controls. Restore all temporary overrides, forces, and test connections, then independently verify their removal.

14. PLC/HMI Backup and Recovery

A proper handover may require:

  • PLC source project.
  • HMI source project.
  • Compiled or runtime files where applicable.
  • Hardware configuration.
  • Firmware and compatibility information.
  • Drive or device configuration dependencies.
  • Required libraries.
  • Licenses and installation media where applicable.
  • Network configuration records.
  • Version and checksum records where supported.
  • Restoration instructions.

A screenshot of the PLC program or an HMI screen is not a substitute for the required project backup.

The backup should be stored in the approved location, identified by machine and revision, and verified for completeness. Where required, a controlled restoration or recovery check should establish that the backup is usable.

15. PDI Versus FAT and SAT for PLC/HMI

Activity Primary purpose Typical focus
PDI Verify pre-delivery conformity and readiness Hardware, installed software identity, configuration, condition, documentation
FAT Verify the machine or system against specified requirements before shipment Logic, sequences, I/O simulation, HMI behavior, alarms, and functional requirements
SAT Verify the installed system under site conditions Actual field wiring, device interfaces, integrated operation, site communication, and acceptance tests
Routine maintenance Preserve or restore the required condition Backups, diagnostics, fault history, component replacement, and verification after work

These activities can overlap. The contract and approved test plan determine which checks belong to each stage.

16. PLC/HMI Defect Register

Record defects with enough detail to reproduce the issue and verify the correction.

Field Example
Defect ID PDI-PLC-001
Machine Automated assembly station
Component PLC / HMI
Expected behavior Pressure displayed in bar using approved scaling
Observed behavior Displayed value differs from the calibrated input reference
Impact Incorrect process indication and possible operator decision error
Evidence Recorded reference input, raw PLC value, and HMI display
Required action Verify input configuration, scaling, and tag mapping
Closure evidence Repeat test with documented input values
Status Open until verified

Record the observed symptom separately from the suspected cause. For example, an incorrect HMI value could arise from sensor calibration, analog module configuration, PLC scaling, communication data type, or HMI formatting.

17. Practical Automotive Manufacturing Example

Consider a test station that uses a PLC, HMI, pressure transmitter, barcode reader, VFD-controlled motor, and pneumatic clamps.

During PDI, the inspector finds:

  • PLC hardware matches the BOM.
  • The HMI communicates with the PLC.
  • The pressure transmitter reading is incorrect due to a scaling mismatch.
  • The barcode reader's raw data is available, but the displayed code is truncated.
  • The conveyor drive fault is detected by the PLC but does not appear in the HMI alarm list.
  • The required approved PLC backup is present, but the HMI backup is missing.

These findings must be handled individually. Correct communication does not prove that data is mapped or displayed correctly. The pressure scaling, barcode display, and alarm configuration require correction and retesting. The missing HMI backup must be supplied and verified if required by the delivery criteria.

Before release, confirm that the corrected application is the final approved revision and that temporary test conditions or overrides have been removed.

18. Common PLC/HMI PDI Mistakes

  • Checking only that the PLC is in RUN mode.
  • Assuming HMI communication proves correct tag mapping.
  • Failing to compare installed software with the approved revision.
  • Ignoring I/O polarity and signal-type mismatches.
  • Accepting analog values without checking scaling and engineering units.
  • Testing commands without verifying permissives and interlocks.
  • Treating alarm acknowledgement as fault clearance.
  • Using ordinary HMI stop commands as substitutes for safety functions.
  • Failing to test communication-loss behavior.
  • Leaving temporary forces, bypasses, or test overrides active.
  • Failing to secure source projects and configuration backups.
  • Accepting missing licenses or required documentation.
  • Closing defects without repeat testing and evidence.

19. Interview Questions and Answers

Q1. What is the role of a PLC in an industrial machine?

The PLC reads inputs, executes configured control logic, and updates outputs to control machine sequences, actuators, and process functions.

Q2. What is the role of an HMI?

The HMI provides the operator with machine status, process values, alarms, and authorized commands through a graphical interface.

Q3. Can a machine operate if the HMI fails?

Depending on the architecture, the PLC may continue executing its control logic. However, operator visibility and command capability may be lost, and the machine must respond according to its approved design.

Q4. What is the difference between an interlock and a permissive?

A permissive is a condition that must be satisfied before an operation is allowed. An interlock prevents an operation when a defined condition prohibits it. Their implementation and terminology can vary by design.

Q5. Why must PLC-HMI tag mapping be verified?

Incorrect mapping can display misleading process values, operate the wrong command, or hide a fault even when the PLC and HMI communicate successfully.

Q6. What is analog scaling?

Analog scaling converts a raw input representation into a meaningful engineering value, such as pressure in bar or temperature in degrees Celsius.

Q7. What is the difference between an alarm and an event?

An alarm indicates an abnormal condition requiring attention. An event records an occurrence or state change, which may not require immediate action.

Q8. Why is software revision control important?

It establishes which program and configuration are approved, supports reproducibility, prevents uncontrolled changes, and enables reliable recovery after a failure.

Q9. What should be verified after PLC program changes?

The change should be reviewed and approved, affected functions should be retested, the final version should be identified, and required backups and records should be updated.

Q10. Why is a PLC backup alone insufficient?

The machine may also depend on HMI projects, hardware configuration, firmware, libraries, device parameters, licenses, and network settings.

Q11. What is the difference between network connectivity and application communication?

Network connectivity confirms that devices can reach one another at a network level. Application communication verifies that the relevant protocol sessions and data exchanges operate correctly.

Q12. What is the most important PLC/HMI PDI principle?

Verify the complete chain from field signal to PLC logic, operator indication, command handling, and physical machine response, using approved requirements and safe test procedures.

20. Final PLC/HMI PDI Checklist

  • PLC CPU, modules, remote I/O, and HMI hardware match the approved design.
  • Firmware and hardware compatibility are verified.
  • Approved PLC program and HMI application revisions are identified.
  • I/O addresses, channel types, wiring, and tag mapping are verified.
  • Digital signals and analog scaling are checked as required.
  • PLC-HMI communication and diagnostic behavior are verified.
  • HMI screens, units, commands, and status indications are checked.
  • Alarm triggers, messages, acknowledgement, and clearing behavior are tested.
  • Permissives, interlocks, and sequence behavior are verified.
  • User permissions and configuration controls are checked where required.
  • Required fault simulation and communication-loss tests are completed.
  • Temporary forces, bypasses, and test conditions are removed and verified.
  • Required PLC, HMI, and configuration backups are available and identified.
  • Required licenses, manuals, and project documentation are available.
  • Defects are documented, corrected, and retested.
  • Required engineering, safety, and quality approvals are recorded.

Key principle: PLC/HMI PDI verifies that the approved control hardware and software are correctly configured, communicate accurately, present reliable information to operators, and control the machine as specified. A powered PLC and a working HMI screen are only the beginning of verification.
