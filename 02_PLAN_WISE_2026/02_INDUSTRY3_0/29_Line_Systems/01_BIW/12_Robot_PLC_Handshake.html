1. Purpose of a Robot-PLC Handshake

A robot-PLC handshake is a defined exchange of signals between a robot controller and a PLC that coordinates their actions during an automated production cycle.

In a Body-in-White (BIW) line, the PLC typically coordinates the station sequence, conveyors, fixtures, clamps, sensors, part tracking, and neighboring equipment. The robot controller manages robot motion, robot programs, motion-related status, and robot-specific faults.

The handshake makes sure that each controller knows when the other is ready, when a task has been requested, whether the task is running, and whether the task has finished successfully.

For example, a BIW welding station may require the PLC to confirm that the correct body component is present, the fixture is clamped, the area is clear, and the selected robot program matches the vehicle variant before requesting the robot to execute its weld sequence.

Without a correctly designed handshake, the PLC may release a part too early, a robot may receive a duplicate start command, or the station may wait indefinitely for a completion signal.

Core principle: A command is not proof of execution, and execution is not proof of successful process completion.

3. Interface Types

The handshake signals may be transferred through hardwired digital I/O or an industrial communication network.

Interface Typical application Maintenance considerations
Hardwired digital I/O Individual request, ready, running, and done signals Check voltage, common reference, wiring, polarity, and terminal status
PROFINET Cyclic PLC-to-robot I/O on supported systems Verify device name, IP configuration, I/O mapping, connection state, and diagnostics
EtherNet/IP Cyclic I/O between compatible PLC and robot systems Verify connection ownership, assemblies, configuration, and connection health
EtherCAT Real-time control where both systems and architecture support it Verify device compatibility, topology, and operational state
Vendor-specific fieldbus Legacy or manufacturer-specific installations Confirm supported hardware, interface modules, configuration, and signal definitions

Not every robot supports every protocol. A physical Ethernet connection does not automatically mean the correct industrial I/O connection is configured.

A successful ping only establishes a limited level of IP connectivity. It does not prove that cyclic I/O data is mapped correctly, updating, or being interpreted correctly by the application.

4. Standard Handshake Signals

Signal names differ by manufacturer and machine builder. The important point is the documented meaning, direction, active state, and sequence of each signal.

Signal Typical direction Meaning
PLC Ready PLC → Robot Station conditions permit the next operation
Robot Ready Robot → PLC Robot controller is available for the defined operation
Program Number / Program Select PLC → Robot Requests a particular robot job or program
Program Accepted Robot → PLC Confirms that the requested program selection has been accepted
Start Request PLC → Robot Requests execution of the selected operation
Robot Busy / Running Robot → PLC Robot is executing or processing the requested cycle
Cycle Complete Robot → PLC Robot program has reached its defined completion point
Operation Result OK Robot or process controller → PLC Process result meets the configured success criteria
Robot Fault Robot → PLC A robot fault or defined abnormal condition exists
Reset Request PLC → Robot Requests a permitted reset action
Reset Acknowledged Robot → PLC Indicates that the reset request was handled according to the interface design
Home / Park Position Robot → PLC Robot reports a defined position or zone condition
Part Present PLC or sensor system → Sequence Required workpiece is detected
Fixture Clamped PLC or field device → Sequence Clamp feedback confirms the defined clamp state
Heartbeat Either direction Indicates that a changing signal or counter is being updated

4.1 Ready is not the same as safe

A Robot Ready bit usually means the robot meets certain operational conditions defined by the integrator. It must not be assumed to prove that every safety condition is satisfied.

Likewise, a robot at Home or Park may still be inside a hazardous area or may not be at the exact position required for fixture release.

Safety permissions must be handled through the designed safety system and risk-assessed interlocks. Ordinary PLC bits and standard network I/O are not substitutes for safety-rated functions.

4.2 Cycle complete is not always quality OK

A robot can complete a programmed path while a weld controller reports a failed weld, a nutrunner reports an incorrect torque result, or a vision system reports a missing feature.

Separate these concepts:

  • Motion complete: The robot program or defined motion sequence finished.
  • Process complete: The required operation finished.
  • Process OK: The required process criteria passed.
  • Station complete: All conditions required to advance the station sequence are satisfied.

The PLC should only release the workpiece when the documented station logic allows it.

5. Signal Logic and Handshake Design

5.1 Maintained signals

A maintained signal remains active until a defined condition causes it to turn off.

Example:

  • The PLC asserts Start_Request.
  • The robot detects the request and starts the operation.
  • The PLC maintains the request until the interface's documented acknowledgement or state transition occurs.
  • The request is removed according to the handshake specification.

Maintained requests are useful when the receiving controller must reliably detect a command even if its scan or communication update does not coincide with the exact instant of assertion.

However, if a maintained start request remains active after completion, it may cause an unwanted retrigger in an incorrectly designed interface.

5.2 Pulse signals

A pulse is active for a limited duration. Pulse-based interfaces require careful attention to signal width, update timing, and detection logic.

A short PLC pulse can be missed if the receiving system does not sample it while it is active. For networked I/O, the behavior depends on update intervals, controller scan times, and the communication architecture.

Use pulse signals only when both sides' interface specifications define how the pulse is detected and acknowledged.

5.3 Rising-edge detection

A rising edge occurs when a signal changes from false to true.

Edge detection can prevent a continuously true request from being interpreted as a new command every scan. It does not, by itself, guarantee that a command is accepted only once across communication interruptions or controller restarts.

5.4 Acknowledgement and re-arming

A robust handshake defines:

  1. Who initiates a request.
  2. Which conditions permit the request.
  3. What acknowledgement confirms acceptance.
  4. Which state indicates execution.
  5. What proves completion.
  6. When the request must be removed.
  7. When the interface is ready for another cycle.
  8. How faults, interruptions, and restarts are handled.

The handshake must return to a defined idle or ready state before a new cycle is accepted. A stuck completion signal or stale acknowledgement must not be mistaken for the result of a new cycle.

6. Typical BIW Robot-PLC Sequence

Consider a robot that performs spot welding on a body-in-white component.

6.1 Preconditions

Before starting the robot operation, the station sequence may need to verify:

  • Correct workpiece or carrier is present.
  • Required locating pins and clamps are in the expected state.
  • Required process equipment is ready.
  • The robot is in the required operating mode.
  • The correct robot program is selected and accepted.
  • Required safety permissions are established through the designed safety system.
  • No blocking fault or active recovery condition exists.
  • The workpiece variant matches the intended operation.

These conditions are station-specific. A generic example must not be copied into a real machine without checking the approved control design.

6.2 Sequence overview

1. PLC confirms station preconditions
          ↓
2. PLC selects the required robot program
          ↓
3. Robot confirms program acceptance
          ↓
4. PLC issues Start Request
          ↓
5. Robot accepts request and reports Busy / Running
          ↓
6. Robot executes the operation
          ↓
7. Robot reports Cycle Complete
          ↓
8. PLC validates completion and process result
          ↓
9. PLC removes request and completes acknowledgement
          ↓
10. Station sequence permits the next operation

A process may require additional steps, including weld controller confirmation, nutrunner result validation, vision inspection, or traceability recording.

7. Program Selection and Variant Management

BIW stations often process multiple body styles, part variants, or product configurations. Selecting the correct robot program is therefore a production-quality requirement, not just a convenience.

The PLC may send a program number, recipe identifier, or variant code to the robot controller. The robot interface should return a defined acknowledgement and, where supported, the selected or active program identity.

Condition Required design consideration
Valid program requested Robot confirms acceptance before start
Unsupported program number Reject the request and report a fault
Program selection still in progress Prevent premature start
Requested and active program differ Inhibit operation until resolved
Variant data unavailable Hold the sequence according to the approved recovery design
Program changed during a cycle Handle only through a defined safe and controlled procedure
PLC and robot backups have different revisions Verify compatibility before returning equipment to production

Important: Never assume that a numeric program value means the same thing across different robots or projects. Program numbers and meanings must be verified against the approved mapping.

8. State Machine Design

A state machine defines which operations are permitted at each stage of the cycle and which transitions are valid.

State Meaning Example transition condition
Idle No active cycle request Required station conditions become valid
Ready Interface and station are ready A valid program request is issued
Program Selection Robot program is being selected Program acceptance is confirmed
Start Pending Start request has been issued Robot acknowledges or reports running
Running Robot operation is underway Defined completion condition is reached
Complete Required cycle completion is confirmed Completion acknowledgement and re-arm conditions are met
Fault An abnormal condition blocks normal sequence Fault is diagnosed and approved recovery conditions are satisfied
Recovery Controlled return to a valid state Recovery checks and required confirmations pass

A fault should not automatically transition directly to Running simply because a fault bit clears. The system must re-establish the correct sequence state and confirm that the workpiece and equipment are in a valid condition.

8.1 Preventing stale completion signals

Suppose Cycle_Complete remains true after the previous cycle. The PLC issues another start request and then sees Cycle_Complete already true. If the sequence does not verify a new completion transition, it could falsely declare the new cycle finished.

Common design protections include:

  • Requiring completion to be false before a new cycle starts.
  • Tracking whether the new start was accepted.
  • Requiring a valid Busy or Running transition where supported.
  • Requiring completion to occur after the current start.
  • Clearing or acknowledging completion according to the documented protocol.
  • Using cycle identifiers or sequence counters where both sides support them.
  • Rejecting impossible state combinations and reporting a diagnostic.

A sequence counter can help associate status with the current cycle, but only if both controllers implement its meaning consistently.

9. Timeouts, Watchdogs, and Heartbeats

A timeout detects that an expected event did not occur within a defined period. It does not prove the reason for the delay.

Timeout Expected event Typical diagnostic direction
Program selection timeout Program acceptance Check requested number, robot mode, program availability, and interface mapping
Start acknowledgement timeout Robot accepts start Check readiness, start edge, permissives, and controller status
Running timeout Robot reports execution Check program state, controller fault, hold condition, and I/O
Cycle timeout Operation completes Check robot program, tooling, process equipment, and obstruction or wait conditions
Communication timeout Valid network updates continue Check device connection, network diagnostics, and I/O update status
Reset acknowledgement timeout Reset request is handled Check fault cause, reset permissives, and controller-specific reset rules

Timeout values must be based on machine design, normal cycle time, controller behavior, and validated production conditions. They should not be copied blindly from another station.

When a timeout occurs, the control system should move to a defined fault or hold state and retain useful diagnostic information. It must not silently assume that the missing acknowledgement means the operation succeeded.

A heartbeat may use a toggling bit or changing counter. If it stops changing, communication or application execution may be impaired. A heartbeat is useful only when its expected update behavior and timeout handling are explicitly designed.

10. Robot Operating States and Permissives

Robot terminology varies by manufacturer, controller generation, and configuration. Maintenance personnel must distinguish operating mode, motion state, fault state, and safety state.

State or indication General meaning What to verify
Servo Ready Servo system is available under defined conditions Servo alarms, drive status, and required enabling conditions
Motors On Robot drives are enabled according to controller logic Controller mode, drive status, and safety permissions
Auto / Remote Controller is configured for automatic or remote operation Correct mode and external-start configuration
Teach Mode Robot is configured for manual teaching Teach pendant and mode-dependent restrictions
Running A program or motion operation is executing Program state and expected sequence
Hold / Paused Execution is suspended or held Hold source and conditions required to resume
Fault A controller or application fault exists Alarm number, description, and root cause
E-stop Active Emergency-stop condition is active Correct emergency-stop circuit and device status
Safety Stop A configured safety function has stopped or inhibited motion Safety diagnostics and the designed reset procedure
Home / Park A configured position or zone condition is satisfied Actual position signal definition and permitted zone

Do not treat all these states as interchangeable. For example, a robot may be powered but not permitted to move, or may be free of ordinary program faults while a safety stop remains active.

11. Safety: Separate Safety Functions from Standard Handshake

Robot-PLC handshake design must maintain a clear boundary between ordinary process coordination and safety-rated control.

Standard handshake signals such as Robot_Ready, Start_Request, and Cycle_Complete generally coordinate the production sequence. They must not be assumed to provide safety-rated protection.

Depending on the risk assessment and machine design, safety functions may include:

  • Emergency-stop circuits.
  • Guard-door and access interlocks.
  • Safety-rated monitored stops.
  • Enabling devices for manual operation.
  • Safe speed or position monitoring where required.
  • Safe Torque Off (STO) or other validated drive safety functions.
  • Safety-rated communication and safety controller diagnostics.

The exact safety architecture must follow the applicable risk assessment, machine design, manufacturer instructions, and relevant standards.

Critical maintenance rule: Never bypass an interlock, force a safety input, or bridge a safety circuit to make a handshake work. Diagnose the actual cause and restore the approved safety configuration. Clearing a standard PLC fault is not proof that the machine is safe to restart.

12. PLC and Robot I/O Mapping

A handshake can fail even when both controllers are healthy if the signal mapping is incorrect.

The PLC may call a signal Robot_Ready, while the robot interface assigns the corresponding data to a different bit or byte. A mismatch in byte order, bit position, polarity, data type, or interface direction can produce misleading status indications.

12.1 Mapping checks

Verify the following during commissioning and troubleshooting:

  1. The PLC output address matches the intended robot input.
  2. The robot output address matches the intended PLC input.
  3. Input and output directions are correct from each controller's perspective.
  4. The bit and byte offsets match the approved configuration.
  5. The data type and bit numbering match the interface specification.
  6. The active state and signal polarity are correct.
  7. The mapped data is updating at the expected rate.
  8. The PLC program uses the intended tags and not obsolete addresses.
  9. The robot program or interface logic actually uses the mapped signals.
  10. Online edits and hardware configuration changes are approved and documented.

12.2 Example signal map

The following is an illustrative logical map, not a real PLC address assignment.

Logical signal Owner / source Consumer Expected behavior
PLC_Station_Ready PLC sequence Robot interface Active when defined start conditions are satisfied
PLC_Program_Number PLC sequence Robot interface Contains the requested program identifier
PLC_Start_Request PLC sequence Robot interface Requests the current operation
Robot_Ready Robot interface PLC sequence Reports defined robot availability
Robot_Program_Accepted Robot interface PLC sequence Confirms program selection
Robot_Busy Robot interface PLC sequence Reports active execution
Robot_Cycle_Complete Robot interface PLC sequence Reports completion of the defined cycle
Robot_Fault Robot interface PLC sequence Reports a blocking robot fault condition

Keep the signal map synchronized with the actual PLC project, robot configuration, and electrical drawings. A spreadsheet that describes yesterday's I/O mapping is documentation in the same sense that an old train timetable is a transport system: technically recognizable, operationally questionable.

13. Industrial Network Diagnostics

When handshake signals are transferred over an industrial network, check both the communication layer and the application layer.

Diagnostic layer Checks
Physical Power, connectors, cable condition, port LEDs, switches, and link status
Ethernet / IP IP addresses, subnet, duplicate addresses, routing where applicable, and device reachability
Industrial protocol Device name, controller connection state, connection ownership, assembly or I/O configuration, and watchdog status
Cyclic data I/O update rate, stale data, input/output offsets, and communication error counters
PLC application Correct tag mapping, sequence state, permissive logic, and timer status
Robot application Program selection, remote-start configuration, active program state, and interface logic

Do not change IP addresses, connection parameters, or I/O assembly settings without confirming the approved network design and recording the original configuration.

If a robot responds to ping but the PLC's robot inputs remain unchanged, investigate the industrial I/O connection and data mapping. Repeatedly restarting controllers without evidence may temporarily hide the symptom while destroying useful diagnostic information.

14. Troubleshooting Common Robot-PLC Handshake Faults

Symptom Possible causes Checks
Robot Ready remains OFF Robot fault, wrong mode, drives unavailable, or incorrect mapping Check controller status, active alarms, interface signals, and readiness definition
Start request is ignored Request edge missed, program not accepted, missing permissive, or remote start disabled Check sequence state, start transition, program acknowledgement, and controller configuration
Wrong robot program runs Incorrect variant code, mapping error, or stale selection Compare requested program, accepted program, active program, and product identity
PLC waits indefinitely Missing acknowledgement, incorrect state transition, or network data not updating Identify the exact awaited condition and inspect both controllers
Robot moves but PLC never sees completion Completion mapping error, wrong completion definition, or robot program does not set the signal Check the robot program end logic and the corresponding PLC input
Cycle Complete remains ON Signal not reset, incorrect latching, or acknowledgement sequence incomplete Inspect the interface's completion-clearing and re-arm rules
Intermittent handshake failures Unstable communication, short pulses, race conditions, or timing assumptions Review I/O update behavior, signal trends, and event timing
Reset request has no effect Active fault cause, invalid reset state, or incorrect reset mapping Read the robot alarm and verify the permitted reset sequence
Fixture releases too early PLC advances on motion completion rather than the required process result Verify completion conditions and release permissives
Robot is healthy but station is blocked PLC sequence fault, missing station input, or another equipment interlock Identify the first unsatisfied sequence condition
Robot repeatedly restarts Start request remains active or re-trigger logic is incorrect Check request removal, edge detection, and re-arm conditions
Network status is healthy but data is wrong Incorrect I/O mapping, stale application tags, or mismatched configuration Compare live raw I/O data with logical tags on both controllers

14.1 Recommended diagnostic order

Use a consistent sequence instead of changing random parameters until the machine appears cooperative.

  1. Record the exact alarm, timestamp, station, robot, product variant, and cycle stage.
  2. Identify the PLC sequence state and the robot controller's current state.
  3. Determine the first expected signal that did not change.
  4. Compare the PLC's logical tag with its mapped input/output data.
  5. Compare the same signal with the robot's corresponding mapped data.
  6. Check program selection and acceptance before investigating the start request.
  7. Verify the defined operating mode, permissives, and safety status through approved diagnostics.
  8. Inspect timers, watchdogs, and sequence-transition conditions.
  9. Investigate network errors if the mapped data is missing, stale, or inconsistent.
  10. After the root cause is corrected, validate the entire sequence under the approved restart procedure.

The first missing or incorrect transition is often more useful than the final timeout alarm, which may simply be the consequence of the original problem.

15. Recovery After a Fault or Interrupted Cycle

A reset is not a recovery strategy. It is only one possible operation within a controlled recovery process.

After a communication interruption, controller restart, emergency stop, or interrupted robot cycle, the PLC and robot may disagree about the current state. For example, the robot may retain an internal completion flag while the PLC has restarted and returned its sequence state to idle.

Before resuming production:

  • Determine whether the robot is stopped and in a known state.
  • Confirm the actual workpiece position and whether the operation was completed.
  • Check whether the fixture, clamps, tools, and process equipment are in the expected state.
  • Review the active robot program and relevant fault history.
  • Confirm the handshake signals agree with the documented sequence.
  • Establish the approved recovery state and required acknowledgements.
  • Verify that a new start cannot be triggered unintentionally.
  • Perform any required inspection or quality disposition for a potentially incomplete operation.

Do not blindly restart a welding sequence or repeat a process operation. The workpiece may already contain partial welds, completed fasteners, or other irreversible process results. The recovery procedure must account for the physical process, not just the software state.

16. Maintenance and Documentation Requirements

A reliable handshake should be documented as part of the station's machine knowledge base.

Document or record Required content
Handshake signal list Signal name, direction, description, polarity, and owning controller
Sequence chart State transitions, acknowledgements, timeouts, and recovery behavior
PLC I/O map Hardware addresses, network mappings, tag names, and data types
Robot interface configuration Network settings, mapped I/O, remote-start setup, and program-selection method
Robot program register Program number, purpose, variant, revision, and approved backup
Network topology Device names, IP addresses, switches, and relevant network connections
Alarm and fault history Alarm codes, timestamps, operating state, and corrective action
Change log Approved modifications to PLC logic, robot programs, and interface mappings
Recovery SOP Controlled fault recovery, restart conditions, and quality checks
Validation record Tests performed after modifications and the results obtained

Back up the PLC program, robot programs, interface configuration, and related network settings before approved modifications. Verify that the backups are usable and identify the versions that belong together.

Any change to start logic, program selection, timeout behavior, or completion criteria should be reviewed for its effects on safety, quality, cycle time, and traceability.

17. Performance Monitoring

Handshake performance can be monitored to detect developing faults before they cause major production interruptions.

Metric Definition or use
Robot handshake timeout count Number of handshake timeout events in a defined period
Robot cycle time Time between agreed cycle start and completion events
Ready-to-start delay Time spent waiting after the station becomes eligible to start
Program selection delay Time between program request and program acceptance
Start-to-running delay Time between start request and the defined running acknowledgement
Completion acknowledgement delay Time between cycle completion and PLC acknowledgement
Communication fault count Number of recorded network or I/O communication failures
Recovery duration Time required to restore the approved operating state after a fault
Repeat-fault frequency Frequency with which the same failure recurs

Use consistent event definitions and timestamps. A cycle-time calculation is meaningless if one station records the start request while another records the first robot motion, then someone compares the numbers as though they were identical.

Where PLC events are sent to SCADA, SQL, or a production dashboard, preserve the distinction between a requested operation, an acknowledged start, actual execution, and confirmed completion.

18. Practical Exercises

Exercise 1: Robot does not start

The PLC indicates Station_Ready = TRUE, but the robot remains idle.

Investigate:

  • Whether the selected program was accepted.
  • Whether Start_Request actually reached the robot interface.
  • Whether the start request follows the required pulse or maintained-signal convention.
  • Whether the robot is configured for the expected operating mode.
  • Whether any permissive or fault prevents execution.
  • Whether the PLC is waiting for an acknowledgement that never arrives.

Expected outcome: Identify the first failed transition instead of concluding that the robot itself is defective.

Exercise 2: Completion remains ON

The robot completed the previous cycle, but Cycle_Complete remains true. A new start request is issued.

Explain how the PLC could falsely declare the new cycle complete and specify the state or acknowledgement conditions needed to prevent this.

Expected outcome: A design that associates completion with the current cycle and prevents stale completion from satisfying a new request.

Exercise 3: Wrong variant

The PLC requests program 24, but the robot reports that program 23 is active.

Define the checks that should prevent the cycle from starting. Include program acceptance, active-program verification where available, product identity, fault handling, and restart conditions.

Expected outcome: The station holds rather than executing a potentially incorrect operation.

Exercise 4: Network connected, I/O stale

The robot responds to ping, but the PLC sees no change in the robot's mapped status bits.

Develop a diagnostic sequence covering the industrial I/O connection, device configuration, data mapping, update status, and controller application logic.

Expected outcome: Separate basic IP reachability from correct cyclic data exchange.

Exercise 5: Robot complete, process failed

The robot reports that its motion program completed, but the weld controller reports a failed weld.

Determine which result the PLC must evaluate before allowing the part to advance.

Expected outcome: Station release depends on the defined process-completion and quality requirements, not merely the robot's motion status.

19. Competency Checklist

  • Explain the roles of the PLC, robot controller, and industrial network.
  • Identify handshake signal direction and meaning.
  • Distinguish maintained requests, pulses, and rising-edge detection.
  • Explain program selection, acknowledgement, start, running, and completion.
  • Identify stale signals and explain why they can cause false completion.
  • Diagnose an incorrect or missing I/O mapping.
  • Distinguish IP connectivity from working cyclic industrial I/O.
  • Explain the purpose of timeouts and watchdogs.
  • Separate standard process handshake signals from safety-rated functions.
  • Diagnose a robot that is ready but does not accept a start request.
  • Explain why motion completion does not necessarily mean process quality is acceptable.
  • Follow an approved recovery procedure after an interrupted cycle.
  • Maintain the signal map, sequence documentation, backups, and change records.

The key maintenance skill is to follow the handshake as a sequence of verifiable state transitions. When a station stops, identify what should have happened, what actually happened, and the first point where those two diverged.
