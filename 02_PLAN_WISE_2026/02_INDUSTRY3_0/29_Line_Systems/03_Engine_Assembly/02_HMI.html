1. Purpose of an HMI

A Human-Machine Interface (HMI) is the operator-facing interface used to monitor, operate, and diagnose industrial machines. In an engine-assembly line, it provides access to station status, production sequences, alarms, process values, tooling results, recipes, and maintenance diagnostics.

The HMI connects people to the automation system, but it is not necessarily the device performing the control. In a typical installation, the PLC executes machine logic while the HMI displays information and sends authorized operator commands.

Common HMI functions in engine assembly include:

  • Displaying station status, current sequence step, and production mode.
  • Showing engine identity, pallet identity, and selected recipe.
  • Displaying sensor states, actuator commands, and feedback.
  • Presenting tightening-tool, leak-test, and other quality results.
  • Showing alarms, fault descriptions, timestamps, and recovery instructions.
  • Providing authorized manual-operation screens.
  • Displaying cycle time, production counts, downtime, and reject counts.
  • Allowing controlled selection of recipes or tooling programs.
  • Showing maintenance diagnostics and device communication status.
  • Displaying trends for analog measurements and process values.
  • Supporting production traceability and quality confirmation.

A well-designed HMI helps the operator understand what the machine is doing, why it is waiting or stopped, and what action is permitted by the approved procedure.

2. HMI System Architecture

A typical engine-assembly HMI architecture looks like this:

Operator / Maintenance Technician
              ↓
           HMI Panel
              ↓
      Industrial Network
              ↓
          PLC / CPU
              ↓
      Remote I/O / Drives
              ↓
      Sensors and Actuators
              ↓
       Assembly Operation
              ↓
   Tooling / Test Equipment
              ↓
 PLC Data → HMI / Historian / MES

Depending on the design, the HMI may communicate directly with a PLC, a supervisory server, or an industrial data service.

Typical components include:

  • HMI panel or industrial PC.
  • HMI runtime software.
  • Screen and navigation configuration.
  • PLC communication driver.
  • Tag database.
  • Alarm and event configuration.
  • Trend and historical-data configuration.
  • User authentication and access permissions.
  • Recipe and parameter interfaces.
  • Data logging and traceability interfaces.

Examples of industrial HMI platforms include Siemens WinCC, Mitsubishi GOT with GT Designer, Rockwell FactoryTalk View and PanelView, and other vendor-specific systems.

The actual architecture and supported functions depend on the selected platform, version, licensing, hardware, and project configuration.

3. HMI Versus PLC, SCADA, and MES

System Main responsibility Engine-assembly example
PLC Executes machine control logic Controls the clamp sequence and checks completion feedback
HMI Provides local operator interaction Displays clamp status and the reason the station is waiting
SCADA Supervisory monitoring across equipment or production areas Monitors several assembly stations and their alarms
MES Manages manufacturing execution and production records Tracks engine identity, routing, operation completion, and production orders
Quality system Manages quality requirements and results according to the plant architecture Stores or evaluates approved inspection and test records
Tool controller Controls a specialized operation and evaluates its results Executes a tightening program and reports torque-angle results

These roles can overlap in a particular implementation. For example, an HMI runtime may provide logging or supervisory functions, and a PLC may handle some traceability transactions. The important distinction is the responsibility assigned by the system design.

An HMI display is not proof that the physical machine condition is correct. The displayed value depends on the signal source, communication status, data mapping, and screen configuration.

4. HMI Screens and Their Purpose

A practical HMI project normally organizes screens around the operator's task rather than exposing every internal PLC tag.

Screen Purpose Typical content
Overview Understand overall station status Mode, sequence state, station availability, and active fault
Process screen Monitor the current operation Sensor states, actuator status, current step, and process values
Manual operation Perform authorized individual movements Device commands, feedback, permissives, and operating instructions
Alarm screen Identify active and historical faults Alarm text, timestamp, state, and acknowledgement
Diagnostics Troubleshoot equipment I/O status, communication state, device codes, and fault details
Tooling screen Monitor specialized tools Program number, cycle status, result, and measured values
Quality screen Review process acceptance Test status, result validity, and associated engine identity
Recipe screen Manage approved process selections Recipe ID, revision, and authorized selection controls
Production screen Monitor output Cycle count, good count, reject count, and downtime
Trend screen Analyze changing values Temperature, pressure, force, timing, or other process variables
Maintenance screen Support authorized maintenance Service information, diagnostic checks, and maintenance status
User management Control access Login status, permissions, and authorized operations

Not every machine needs a separate screen for every function. Screen design should reflect actual operator needs, fault frequency, process complexity, and the available display size.

5. HMI Tags and PLC Tag Mapping

An HMI tag represents a value that the interface reads, writes, or uses internally. External tags typically connect to PLC variables or data addresses.

Common HMI tag categories include:

  • Boolean status tags.
  • Integer values and codes.
  • Floating-point process values.
  • String values, such as engine identification.
  • Command tags for authorized operator actions.
  • Alarm-related tags.
  • Internal HMI tags used for navigation or display behavior.

5.1 Example tag list

HMI tag Data type Purpose Access
HMI_Station01_Ready BOOL Displays station readiness Read-only
HMI_Station01_RunStatus BOOL Displays running status Read-only
HMI_Station01_Faulted BOOL Displays station fault status Read-only
HMI_Station01_SequenceStep INT Displays current sequence step Read-only
HMI_Station01_CycleTime REAL Displays cycle time Read-only
HMI_Engine_ID STRING Displays engine identity Read-only
HMI_Station01_StartRequest BOOL Requests a start through approved PLC logic Command
HMI_Station01_ResetRequest BOOL Requests an authorized fault reset Command

These names are illustrative. Use the site's naming convention and actual PLC tag definitions.

5.2 Read tags versus write tags

Read-only tags allow the HMI to display data without changing the PLC value. Write tags allow an authorized interface action to request a change.

Write access should be restricted to the minimum necessary. An operator should not be able to change safety limits, production-critical parameters, or engineering configuration merely because a screen contains an editable field.

5.3 Mapping errors

Common tag-mapping problems include:

  • Incorrect PLC address.
  • Wrong data type.
  • Incorrect array index or structure field.
  • Mismatched string length.
  • Wrong scaling or engineering units.
  • Incorrect read/write access.
  • Stale data due to communication loss.
  • Incorrect PLC program or HMI project revision.

A tag can exist and still be mapped incorrectly. Verify the source variable, communication path, data type, and displayed value together.

6. Operator Commands and Command Acknowledgement

HMI buttons commonly request actions such as Start, Stop, Reset, Manual, Auto, or recipe selection.

The HMI should send a request to the PLC. The PLC then evaluates operating mode, permissives, interlocks, and the approved sequence before accepting the action.

Operator Presses Button
          ↓
HMI Sends Request
          ↓
PLC Receives Request
          ↓
PLC Checks Mode and Permissives
          ↓
Request Accepted or Rejected
          ↓
PLC Executes Approved Logic
          ↓
HMI Displays Actual Status and Result

This is a conceptual sequence; the actual implementation may use momentary bits, command identifiers, structured messages, or other methods.

6.1 Request versus actual status

A command indicates what the operator has requested. A status indicates what the automation system reports is happening.

For example:

  • StartRequest = TRUE means a start has been requested.
  • RunStatus = TRUE means the system reports that the machine is running.
  • CycleComplete = TRUE means the defined cycle-completion condition has been reached.

These signals are not interchangeable.

A button that stays highlighted after a failed request may mislead the operator into thinking the machine is running. The screen should show request acceptance and actual equipment state clearly.

6.2 Momentary commands

A momentary command is intended to be active only briefly. The command may be generated by an HMI event and consumed by PLC logic.

The design must define:

  • When the command becomes active.
  • How the PLC acknowledges it.
  • How it resets.
  • What happens if communication fails during the request.
  • Whether duplicate commands can occur.
  • What happens if the operator presses the button repeatedly.

The PLC should handle requests safely and deterministically. Do not assume that every HMI platform automatically generates the correct one-shot behavior.

7. HMI Navigation and Screen Design

Navigation should allow an operator to move quickly from a general overview to the specific information needed for a task.

A typical structure is:

Main Overview
    ↓
Station Selection
    ↓
Station Process Screen
    ↓
Alarm / Diagnostics / Tooling / Quality
    ↓
Detailed Fault Information

Useful navigation principles include:

  • Keep the main production overview accessible.
  • Use consistent screen names and navigation positions.
  • Show the selected station and current operating mode.
  • Provide a clear route back to the overview.
  • Avoid hiding active faults behind multiple menus.
  • Separate operator screens from engineering configuration screens.
  • Avoid excessive pop-ups that obscure machine status.
  • Preserve relevant context when navigating to an alarm or device diagnostic.

For a maintenance technician, navigation should make it easy to trace a fault from the station overview to the relevant input, actuator, tool, or communication diagnostic.

8. HMI Modes: Auto, Manual, Setup, and Maintenance

Operating modes define the permitted behavior of a machine. The actual mode structure depends on the machine design and approved operating procedure.

Mode General purpose Important considerations
Auto Runs the approved automatic sequence Required permissives, process conditions, and interlocks must be satisfied
Manual Allows authorized individual operations Commands must be controlled by the machine's approved manual-operation logic
Setup Supports approved setup or adjustment activities May require specific access controls and operating conditions
Maintenance Supports diagnostic or maintenance tasks Does not automatically make hazardous movement safe
Recovery Supports a defined return from a fault or interrupted sequence Must reconcile machine position, part identity, and process state

An HMI button that selects Manual mode does not itself make a machine safe for access. Hazardous-energy isolation and safety requirements still apply.

8.1 Manual-operation screens

A well-designed manual screen should show:

  • The device being operated.
  • The requested direction or action.
  • Actual feedback or position.
  • Required permissives.
  • Relevant alarms.
  • The selected mode.
  • Any conditions preventing operation.

For example, a cylinder screen may show Extend Request, Extended Feedback, Retracted Feedback, and Air Pressure Healthy. This helps separate a rejected command from an actuator that failed to move.

Manual controls must not bypass the machine's engineered safety functions. Jogging, enabling, and maintenance motion must follow the approved control and risk-assessment design.

9. HMI Alarm Management

An alarm informs the operator of an abnormal condition that requires attention. Alarm design should help the operator understand the problem, its consequence, and the appropriate response.

Typical engine-assembly alarms include:

  • Component not detected.
  • Clamp failed to reach position.
  • Tightening result NOK.
  • Tool communication timeout.
  • Incorrect or missing engine identity.
  • Leak-test failure.
  • Drive fault.
  • Remote I/O communication loss.
  • Station sequence timeout.
  • Required downstream equipment unavailable.

9.1 Alarm states

State Meaning
Active The alarm condition currently exists
Acknowledged The operator has acknowledged the alarm
Returned to normal The underlying alarm condition is no longer active
Cleared or reset The system has completed the defined alarm-clearance process, where applicable
Historical The alarm event is retained in the event history

The exact behavior depends on the HMI and PLC alarm implementation. Acknowledgement should not automatically be treated as fault clearance.

9.2 Alarm priority

Alarm priority should reflect the consequence and urgency of the condition, according to the plant's alarm-management standard.

  • High-priority alarms may require immediate action to protect people, equipment, or product.
  • Medium-priority alarms may require timely intervention to restore operation or prevent quality loss.
  • Low-priority notifications may provide information or indicate conditions requiring routine attention.

Avoid assigning the highest priority to every alarm. If everything is urgent, operators have difficulty distinguishing the conditions that genuinely need immediate attention.

9.3 Alarm text quality

Poor alarm text:

Fault 27

More useful alarm text:

Station 04: Clamp-closed feedback not received within the permitted time. Check clamp movement, air supply, sensor, and input status according to the approved procedure.

Useful alarm messages identify the equipment, abnormal condition, and sensible diagnostic direction. They should not instruct operators to bypass an interlock or perform unauthorized repairs.

10. Alarm History and Event Logs

An alarm history records abnormal events over time. An event log may also record operator actions, mode changes, recipe selections, and other system events.

Useful fields include:

  • Timestamp.
  • Station or device identifier.
  • Alarm code and description.
  • Alarm activation and return-to-normal events.
  • Acknowledgement information, where supported.
  • Operating mode.
  • Sequence step.
  • Engine or pallet identity, where relevant.
  • Related device fault code.
  • Configuration or recipe revision when available.

Historical records are especially useful for intermittent faults that disappear before a technician reaches the machine.

10.1 Event sequence analysis

Suppose a station stopped during tightening. A useful timeline might show:

  1. Tool-ready status lost.
  2. Tightening request issued.
  3. Tool response timeout.
  4. Station sequence stopped.
  5. Operator acknowledged the alarm.
  6. Communication recovered.
  7. Station restarted.

This chronology helps distinguish the initial failure from events caused by the stop and recovery.

Timestamp accuracy matters. If the PLC, HMI, tool controller, and historian have different clocks, the event sequence can appear incorrect. Time synchronization should follow the plant's approved architecture.

11. HMI Trends and Historical Data

Trends show how process variables change over time. They can reveal faults that a single displayed value cannot.

Useful engine-assembly trends include:

  • Press-fit force versus position.
  • Hydraulic or pneumatic pressure.
  • Tightening torque and angle, where supported by the tooling system.
  • Leak-test pressure and leakage values.
  • Conveyor speed.
  • Cycle time.
  • Motor current.
  • Station temperature.
  • Tool-cycle duration.
  • Analog sensor values.

11.1 Live trends versus historical trends

A live trend displays recent values as they arrive. A historical trend retrieves stored data from an HMI archive, historian, or another configured data source.

Historical data may be affected by sampling intervals, deadbands, storage capacity, retention rules, communication interruptions, and timestamp quality.

A trend that stores one value every several seconds may miss a short-duration event. High-speed process analysis may require specialized acquisition in the controller or test equipment rather than ordinary HMI trending.

11.2 Trend interpretation

When analyzing a trend, compare the process variable with relevant commands and events.

For example, for a press-fit station, useful data may include:

  • Force reference.
  • Actual force.
  • Position.
  • Motion state.
  • Press cycle start and completion.
  • Alarm events.
  • Engine identity.
  • Final acceptance result.

A force curve without the associated position, tool program, and engine identity may not be sufficient to establish the cause of a rejected assembly.

12. Recipe and Parameter Management

A recipe is a controlled set of process settings associated with a product, operation, or approved manufacturing condition.

In engine assembly, a recipe may specify or select:

  • Tightening program.
  • Press-fit parameters.
  • Leak-test program.
  • Inspection settings.
  • Station-specific operating parameters.
  • Product variant or engine family.
  • Sequence options permitted by the design.

The HMI may provide recipe selection, but the system should validate the recipe before applying it.

12.1 Recipe-validation checks

  • Correct product or engine family.
  • Valid recipe identifier.
  • Approved revision.
  • Compatibility with the station and tooling.
  • Valid parameter ranges.
  • Required authorization.
  • Confirmation that the recipe is loaded into the correct equipment.
  • Acknowledgement from the receiving controller, where supported.

A displayed recipe name does not prove that the correct parameters are active in the tool controller or machine.

12.2 Parameter protection

Process-critical parameters should have suitable access controls and change records.

A useful change record includes:

  • Parameter name.
  • Original and new values.
  • Units.
  • Recipe or program revision.
  • Reason for change.
  • Authorization.
  • Date and responsible person.
  • Validation results.

Do not change tightening limits, press-fit criteria, leak-test limits, or other quality parameters merely to reduce rejection counts. Those values must follow the approved engineering and process requirements.

13. User Accounts and Access Control

HMI access levels limit which actions different users can perform.

Common roles include:

  • Operator.
  • Maintenance technician.
  • Process engineer.
  • Controls engineer.
  • Administrator.

The exact role model depends on the platform and plant policy.

Typical restrictions may apply to:

  • Manual movement.
  • Recipe selection.
  • Process parameter changes.
  • Alarm reset functions.
  • Maintenance settings.
  • PLC or controller configuration.
  • User-account administration.

13.1 Good access-control practices

  • Give users only the permissions required for their work.
  • Use individual accounts where supported by the plant policy.
  • Avoid shared engineering accounts where individual accountability is required.
  • Protect administrator credentials.
  • Record critical parameter changes and engineering actions.
  • Disable or remove accounts according to the approved access-management process.
  • Follow site cybersecurity requirements for remote access and removable media.

An HMI password is only one part of industrial cybersecurity. Network segmentation, endpoint protection, backup control, patch management, and access to engineering workstations may also be required.

14. HMI Communication and Data Quality

An HMI may communicate with a PLC over an industrial Ethernet network or another supported protocol. The displayed value depends on the communication driver, addressing, data type, update behavior, and source data.

14.1 Common communication symptoms

Symptom Possible cause Diagnostic checks
All PLC tags unavailable PLC offline, network issue, wrong connection settings, or driver fault PLC status, network path, driver diagnostics, and configuration
Only some tags incorrect Mapping, data-type, address, or program-version mismatch Compare tag definitions with the installed PLC project
Values stop updating Communication interruption, stale cache, or failed update mechanism Data-quality indicators, connection diagnostics, and timestamps
Numeric value is implausible Wrong scaling, data type, byte order, or source value Verify raw source data, conversion, and engineering units
Button request has no effect Write permission, communication issue, command logic, or missing permissive Write status, PLC tag, operating mode, and command acknowledgement
HMI disconnects intermittently Network instability, power issues, device load, or configuration problems Logs, switch diagnostics, panel health, and communication settings
Wrong device data displayed Incorrect address or tag mapping Verify device identity and complete data path

14.2 Stale data

A displayed value may remain visible after the source has stopped updating. This is dangerous if the operator assumes the value is current.

Where supported, the HMI should distinguish valid, stale, unavailable, and faulted data. Important commands should not be based solely on an old displayed value.

14.3 Read and write troubleshooting

For a read problem, trace the source value from the PLC through the communication driver to the HMI display.

For a write problem, trace the command from the HMI through the communication path to the PLC variable, then inspect whether the PLC accepted or rejected the request.

This prevents unnecessary PLC changes when the actual problem is an HMI tag mapping or permission issue.

15. HMI Design Standards and Usability

An HMI should make abnormal conditions easy to recognize and routine operation predictable. Decorative complexity is not a substitute for useful information.

15.1 Screen-design principles

  • Use consistent colors, symbols, and navigation across similar stations.
  • Display important process values with clear units.
  • Distinguish commands, actual status, alarms, and feedback.
  • Make the current station, operating mode, and sequence state visible.
  • Use readable text and suitable contrast.
  • Avoid unnecessary animation and excessive decorative graphics.
  • Provide clear alarm descriptions and useful diagnostics.
  • Show communication faults rather than presenting stale values as current.
  • Prevent accidental activation of important commands.
  • Use confirmation steps for high-impact actions where appropriate.
  • Keep engineering settings separate from routine operator controls.

15.2 Color conventions

Color meanings should follow the plant's HMI standard and be applied consistently. For example, a site may use red for abnormal or fault states, green for running or healthy states, and amber for warnings or attention conditions.

Color must not be the only means of communicating status. Text, symbols, and clear state labels help prevent misinterpretation, including for users with color-vision differences.

15.3 Alarm visibility

An active fault that prevents production should be visible without forcing the operator to search through unrelated screens. The interface should also show whether the fault is still active, has returned to normal, or has merely been acknowledged.

16. HMI Integration with Nutrunner and Tool Controllers

The HMI is often the operator's window into the tightening system, while the nutrunner controller executes the tightening cycle and evaluates the result.

Typical HMI data may include:

  • Tool readiness.
  • Selected program.
  • Current cycle state.
  • Actual torque and angle.
  • Tightening result.
  • Fault or reject code.
  • Engine identity.
  • Cycle history.
  • Calibration or maintenance status, where available.

The HMI should make it clear whether a displayed result is current, valid, and associated with the correct engine.

For example, Cycle Complete does not necessarily mean Tightening OK. The screen should distinguish cycle completion from quality acceptance.

If a tool result is missing, check the tool controller's status and result history, the PLC handshake, communication diagnostics, and the engine-tracking association. Changing the HMI display alone will not correct an underlying data-transfer problem.

17. HMI Integration with Leak-Test and Press-Fit Systems

17.1 Leak-test displays

A leak-test screen may show:

  • Test program.
  • Test status.
  • Pressure or vacuum.
  • Stabilization status.
  • Measured leakage or pressure decay.
  • Result validity.
  • Pass/fail result.
  • Fault code.
  • Engine identity.

The interface must distinguish an incomplete test, an invalid test, a completed NOK result, and a completed acceptable result where the system provides these states.

17.2 Press-fit displays

A press-fit screen may show:

  • Target position or force profile.
  • Actual position.
  • Actual force.
  • Maximum force.
  • End position.
  • Cycle state.
  • Final acceptance result.

Force-versus-position curves can be useful for diagnosing interference, component misalignment, incorrect parts, lubrication issues, or tooling degradation. The interpretation must follow the validated process specification.

A final pass/fail indicator is useful for the operator, but detailed curves and diagnostic data may be needed by process engineering and maintenance.

18. HMI Integration with PLC, SCADA, and MES

An HMI may exchange data with other systems to support production reporting, traceability, quality analysis, and maintenance.

Typical information includes:

  • Engine or pallet identity.
  • Production order.
  • Station operation status.
  • Recipe or program revision.
  • Test result.
  • Reject reason.
  • Production count.
  • Alarm and downtime events.
  • Cycle start and completion timestamps.

A useful data path is:

Machine Signals
      ↓
      PLC
      ↓
HMI / Local Operator Interface
      ↓
SCADA / Historian / MES Interfaces
      ↓
Production Reports and Quality Records

The exact arrangement varies. Some HMIs communicate with SCADA or MES through a server or gateway rather than connecting directly.

18.1 Data consistency

The system should define when an operation becomes complete, when a result is accepted, and when its record is considered successfully stored.

Potential failures include:

  • PLC cycle complete but MES record not stored.
  • Result received but linked to an incorrect engine.
  • HMI shows a new recipe while the tool still uses the previous program.
  • Communication interruption causes duplicate or missing records.
  • Different clocks produce inconsistent event order.

A robust implementation uses explicit status, identity checks, acknowledgements, and error handling appropriate to the interface.

19. HMI Backup, Restore, and Version Control

An HMI project contains more than screen graphics. It may also contain tag definitions, communication settings, scripts, alarm configuration, recipes, user roles, and data-logging settings.

A useful backup package may include:

  • Editable HMI engineering project.
  • Runtime or deployment package, where applicable.
  • PLC communication configuration.
  • Tag database and address mappings.
  • Screen and navigation configuration.
  • Alarm definitions.
  • Trend and logging configuration.
  • Recipe data and approved revisions.
  • User and access configuration, handled securely.
  • Required software versions and licenses.
  • Panel model and firmware details.
  • Deployment and restoration instructions.
  • Change history and validation records.

19.1 Important backup distinction

A copy of a runtime project may not contain the complete editable engineering source. Likewise, a project file may not include all external data, licenses, runtime components, or device-specific settings.

A reliable backup procedure should establish which files are needed to restore the actual installed system.

19.2 Restore precautions

Before downloading or restoring an HMI project:

  1. Identify the target panel or industrial PC.
  2. Verify the approved project revision.
  3. Confirm software and runtime compatibility.
  4. Preserve the current configuration and required data.
  5. Confirm communication settings and device addresses.
  6. Follow the approved deployment procedure.
  7. Verify navigation, tags, alarms, commands, and displayed values.
  8. Confirm that the HMI communicates with the intended PLC and devices.
  9. Record the final installed revision and validation results.

Do not assume that a successful download proves the HMI is fully functional. A screen can load correctly while its PLC tags point to the wrong device.

Maintenance frequency should follow the OEM instructions, plant procedures, operating environment, and risk assessment.

Avoid uncontrolled operating-system updates, firmware changes, or software installations on production HMI systems. Changes must follow the plant's approved industrial-control-system change-management process.

21. Common HMI Faults and Troubleshooting

21.1 HMI screen is frozen

Possible causes include runtime software failure, resource exhaustion, panel hardware problems, operating-system issues, or a blocked application.

Diagnostic approach:

  1. Determine whether only one screen is affected or the entire HMI is unresponsive.
  2. Check whether PLC control continues independently, using approved observations.
  3. Review runtime, system, and application diagnostics.
  4. Check panel resource usage and hardware condition where supported.
  5. Verify whether the issue is reproducible and whether a recent change preceded it.
  6. Follow the approved recovery procedure and preserve relevant logs.

Do not assume the machine is stopped safely just because the HMI is frozen. The PLC and physical equipment may continue operating.

21.2 HMI displays the wrong value

Possible causes include incorrect tag mapping, wrong data type, scaling error, wrong engineering units, stale data, or an incorrect PLC source value.

Compare the physical measurement, PLC source tag, communication configuration, HMI tag, and displayed engineering value. Change only the component shown to be incorrect.

21.3 HMI button does not work

Check:

  • Whether the button is enabled under the current mode and access level.
  • Whether the click generates the intended request.
  • Whether the PLC receives the request.
  • Whether communication is healthy.
  • Whether the PLC rejects the request because a permissive is missing.
  • Whether the request resets or is consumed correctly.
  • Whether the interface displays the rejection reason.

The correct diagnosis may be a missing machine permissive rather than an HMI fault.

21.4 Alarm remains active after the fault is corrected

Possible causes include a latched PLC alarm, a reset condition that has not been satisfied, an HMI alarm configuration issue, or a communication problem.

Verify the source alarm condition, PLC latch and reset logic, alarm acknowledgement state, and HMI alarm configuration. Acknowledging an alarm should not be used to conceal an unresolved process or safety condition.

21.5 HMI and PLC disagree about machine state

Check the source tag, update status, communication path, data mapping, state definitions, and program revision. Determine whether the HMI is displaying a command, a request, or actual feedback.

For example, a button may remain visually selected because it reflects the operator's last request rather than the PLC's actual run status.

22. Human Factors and Operator Error Prevention

HMI design influences the way people interpret faults and operate machines. Clear interfaces can reduce mistakes, but they cannot replace appropriate training, procedures, and safety design.

Useful design practices include:

  • Use consistent names for equipment across HMI screens and electrical drawings.
  • Display the actual machine mode.
  • Explain why a command is inhibited.
  • Make the current sequence step visible.
  • Clearly separate quality acceptance from cycle completion.
  • Show engine identity when displaying product-specific results.
  • Avoid ambiguous buttons with unclear consequences.
  • Require appropriate confirmation for high-impact changes.
  • Use controlled access for recipes and engineering parameters.
  • Provide recovery guidance that follows the approved procedure.
  • Keep critical warnings visible during the relevant operation.
  • Avoid relying on color alone to indicate a condition.

The objective is to reduce ambiguity. If an operator must guess whether a tool result belongs to the current engine, the interface and traceability design need improvement.

23. HMI Change Management and Validation

HMI modifications can affect operator actions, process parameters, data interpretation, and production records.

Examples of controlled changes include:

  • Adding or modifying a screen.
  • Changing a tag address.
  • Changing a button action.
  • Modifying an alarm message or priority.
  • Changing recipe selection behavior.
  • Changing units or scaling.
  • Modifying user permissions.
  • Altering data logging or historian interfaces.
  • Changing scripts or runtime configuration.

A controlled change should include:

  1. A documented reason and scope.
  2. Review of potential operational, quality, and safety effects.
  3. An approved backup of the existing project.
  4. Review and approval of the proposed revision.
  5. Testing of affected screens and tag mappings.
  6. Verification of read and write behavior.
  7. Verification of alarms, navigation, and access permissions.
  8. Validation of relevant traceability and data logging.
  9. Controlled deployment and rollback readiness.
  10. Final documentation of the installed revision.

Where an HMI change affects a safety-related function or safety-relevant operator action, the required safety engineering and validation process must also be followed.

24. Practical HMI Study Exercises

Exercise 1: Tag mapping

Choose one PLC input and one PLC status tag. Trace each from the source address or variable through the HMI communication configuration to the displayed value. Verify that the HMI and PLC agree.

Exercise 2: Command versus feedback

A Start button is activated, but the station does not run.

Identify the HMI request, PLC command handling, permissives, actual run status, and feedback needed to diagnose the problem.

Exercise 3: Alarm analysis

A clamp timeout appears intermittently.

Review the alarm timestamp, sequence step, clamp command, feedback transition, pressure condition, and recent fault history. Separate the initiating failure from any secondary alarms.

Exercise 4: Quality-result display

A tightening controller reports a completed cycle, but the HMI displays no result.

Identify the tool data, PLC handshake, result-valid condition, communication status, and engine identity needed to determine where the result was lost.

Exercise 5: Historical trend analysis

Review a pressure or force trend from a failed assembly operation. Identify the relevant reference values, operation start and completion events, alarm timestamps, and quality result. Explain what additional evidence is needed before declaring a root cause.

Exercise 6: Recipe validation

A new recipe is selected on the HMI, but the machine appears to run with old parameters.

Determine whether the HMI selection was accepted, the PLC validated the recipe, the receiving device acknowledged the program, and the active parameters match the approved revision.

Exercise 7: Backup and recovery

Prepare an HMI restoration checklist that includes the editable project, runtime version, panel hardware, communication settings, tag mapping, alarms, recipes, user access, and post-deployment verification.

25. HMI Competency Checklist

  • Explain the difference between HMI, PLC, SCADA, MES, and specialized tool controllers.
  • Navigate overview, process, alarm, diagnostics, and maintenance screens.
  • Understand HMI tags, data types, addressing, and scaling.
  • Distinguish commands, requests, acknowledgements, and actual feedback.
  • Interpret active, acknowledged, returned-to-normal, and historical alarms.
  • Analyze trends and correlate them with machine events.
  • Understand recipe selection, validation, and revision control.
  • Diagnose HMI-to-PLC communication and tag-mapping faults.
  • Interpret tool, leak-test, and press-fit result displays.
  • Understand user roles and industrial access control.
  • Maintain HMI backups and approved project revisions.
  • Verify screen, tag, alarm, and command behavior after changes.
  • Preserve traceability and timestamp consistency.
  • Troubleshoot using evidence rather than changing displays to hide faults.

26. Final Technical Summary

In engine assembly, the HMI is the operator's main interface to machine status, process execution, alarms, tooling, quality results, and production traceability. Its reliability depends on accurate tag mapping, clear separation of commands and feedback, useful alarm design, valid communication, controlled access, and disciplined configuration management.

The most effective troubleshooting approach is to trace the information path from the physical process or PLC source through the communication layer and HMI configuration to the displayed value or operator command. This identifies whether the problem lies in the interface, PLC logic, communication, field device, or process itself.

An HMI is a window into the automation system, not proof that every displayed condition is physically correct. Good engineering makes that distinction clear to operators and maintenance teams.
