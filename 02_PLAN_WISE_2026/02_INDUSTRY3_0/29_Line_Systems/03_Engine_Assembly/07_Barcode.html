1. Purpose of Barcode Systems

Barcode systems identify components, subassemblies, finished engines, containers, tools, and production records by reading machine-readable symbols. In automotive engine assembly, they help ensure that the correct part, process recipe, inspection result, and production history are associated with the correct engine.

Barcode identification is a key part of production traceability. A barcode reader can identify an engine or component, but the PLC or manufacturing system must still validate the decoded value and decide whether the identified item is permitted to proceed.

Typical applications include:

  • Engine serial number identification.
  • Component and subassembly identification.
  • Variant verification before assembly.
  • Selection of the correct PLC, nutrunner, or press recipe.
  • Tracking engine movement between stations.
  • Linking torque, angle, force, displacement, and inspection results to an engine.
  • Tracking rework, repair, and retesting.
  • Identifying material batches and supplier lots.
  • Printing and verifying labels.
  • Supporting genealogy, warranty investigations, and quality audits.

Core principle: A successfully decoded barcode proves that a readable code was obtained. It does not, by itself, prove that the code is correct, genuine, unique, authorized, or associated with the physically correct component.

2. Barcode System Architecture

A typical automated identification system contains a barcode label or direct-marked code, an optical reader, a communication interface, PLC logic, and a production database or manufacturing execution system.

Engine / Component / Container
             ↓
      Barcode or 2D Code
             ↓
       Barcode Reader
             ↓
    Ethernet / Serial / I/O
             ↓
       PLC / Station Logic
             ↓
    Code Validation and Routing
             ↓
 MES / Production Database
             ↓
 Recipe Selection / Traceability
             ↓
     Process Authorization

The actual architecture varies by station. Some readers communicate directly with a PLC over industrial Ethernet. Others communicate with an industrial PC, an edge gateway, or an MES application. Some simple readers provide discrete outputs, although those outputs cannot carry a complete serial number without another data interface.

3. Barcode Fundamentals

A barcode encodes data into a pattern that a reader can detect and decode. Traditional linear barcodes use bars and spaces. Two-dimensional codes use a matrix or other two-dimensional pattern.

The decoded data may represent a serial number, part number, batch, production order, or an identifier used to retrieve a database record.

The reader typically performs several stages:

  1. Illuminate or capture the marked symbol.
  2. Acquire an image or optical signal.
  3. Detect the symbol boundaries and pattern.
  4. Decode the encoded data.
  5. Apply configured formatting or validation rules, where supported.
  6. Transmit the result through the configured interface.
  7. Allow the receiving system to validate the identifier against the production process.

The reader's successful decode and the manufacturing system's acceptance are two separate decisions.

4. Linear Barcodes and Two-Dimensional Codes

Code type Structure Common applications Main considerations
Code 128 Linear barcode Labels, serial numbers, logistics Requires sufficient label width and suitable print quality
Code 39 Linear barcode Industrial labels and legacy systems Can require more space for a given amount of data
EAN/UPC Linear barcode Retail and standardized product identification Uses defined data structures and is not a universal engine-traceability format
Interleaved 2 of 5 Linear barcode Certain packaging and logistics applications Requires correct format and data-length configuration
QR Code Two-dimensional matrix Identification, data access, logistics Can encode different character sets and data structures
Data Matrix Two-dimensional matrix Industrial component marking and direct part marking Suitable for compact codes, subject to marking quality and reader capability
PDF417 Stacked two-dimensional barcode Documents and selected identification systems Requires compatible reader support and adequate symbol dimensions

The best code depends on the data requirements, available marking area, reader capability, environmental conditions, print or marking method, and applicable customer or plant specifications.

For compact industrial parts, Data Matrix is frequently useful. For labels and broader information sharing, QR Code may be appropriate. Neither should be selected without confirming the actual traceability and equipment requirements.

5. Barcode and RFID: Key Difference

Barcode systems use optical reading. RFID systems use radio-frequency communication with a compatible tag.

Property Barcode RFID
Reading method Optical Radio frequency
Line of sight Generally required for optical reading Not necessarily required
Tag or label cost Often low Depends on tag and system
Environmental sensitivity Affected by dirt, damage, contrast, and surface condition Affected by tag design, metal, liquids, frequency, and installation
Multiple-item reading Usually individual or image-based, depending on the system Some systems support multiple tags within a read zone
Data storage Encoded in the symbol May be stored in the tag or retrieved using an identifier
Typical industrial use Labels, component identification, engine serial numbers Reusable carriers, pallets, tool tracking, and selected production systems

RFID is not automatically superior. A barcode system may be simpler and more economical when labels are visible and readable. RFID may be advantageous where optical access is difficult or automatic carrier identification is required.

6. Barcode Reader Types

6.1 Laser scanners

Laser scanners read suitable linear barcodes by scanning a light beam across the symbol.

Common characteristics:

  • Suitable for supported linear barcode formats.
  • Can read labels at appropriate distances and angles.
  • Depend on adequate symbol quality and optical conditions.
  • Are not suitable for every two-dimensional code type.

A laser scanner should not be assumed to read QR Code or Data Matrix unless its specifications explicitly support the required code format.

6.2 CCD and area-imaging readers

Imaging readers capture reflected light using an image sensor and decode the resulting image.

They can support linear and two-dimensional symbols, depending on the model and configuration.

Common applications include:

  • Engine serial labels.
  • Data Matrix marks on components.
  • QR codes on production carriers.
  • Direct part marking.
  • Identification where symbol orientation varies.

6.3 Fixed-mount industrial readers

Fixed-mount readers are installed at production stations and triggered by a PLC input, internal sensor, encoder event, or communication command.

Typical features include:

  • Configurable acquisition and decoding.
  • Industrial Ethernet or serial communication.
  • Discrete trigger and status inputs or outputs.
  • Read-result data and diagnostic information.
  • Configuration backup and remote diagnostics, depending on the model.

The reader's exact capabilities depend on its model and firmware. A configuration suitable for one station may not work reliably at another because the label size, marking process, distance, lighting, and cycle time differ.

7. Barcode Reader Selection

Important selection parameters include:

  • Supported symbologies: Code 128, Code 39, Data Matrix, QR Code, and others as required.
  • Minimum and maximum symbol dimensions.
  • Reading distance and field of view.
  • Required resolution and optical performance.
  • Supported character set and maximum data length.
  • Required decoding speed.
  • Communication interface and supported industrial protocols.
  • Triggering method.
  • Environmental protection and temperature rating.
  • Lighting and illumination capability.
  • Support for the actual label or direct-marking surface.
  • Diagnostics, configuration backup, and maintenance support.

A reader with a high headline resolution may still fail on a poorly marked symbol. The complete application must be tested using representative production parts, including worst-case marking quality and operating conditions.

8. Barcode Quality and Readability

Barcode readability depends on the symbol's physical or printed quality, the reader's optical performance, and the surrounding environment.

Important factors include:

  • Contrast between the symbol and background.
  • Bar width or module size.
  • Quiet zones and symbol boundaries.
  • Print resolution and ink or ribbon condition.
  • Label wrinkles, scratches, or abrasion.
  • Oil, coolant, dust, and metal chips.
  • Curved or reflective surfaces.
  • Symbol orientation and perspective.
  • Focus, exposure, and illumination.
  • Direct part marking quality.
  • Motion blur and vibration.
  • Reader distance and angle.

8.1 Print contrast and surface condition

A high-contrast printed label is often easier to read than a low-contrast or damaged label. Direct part marking can be more challenging because the surface may be curved, reflective, textured, machined, or affected by the marking process.

A mark that looks clear to a person is not necessarily easy for an industrial reader to decode.

8.2 Quiet zones

Some barcode formats require a clear area around the symbol. Nearby text, borders, graphics, or another code may interfere with detection if the required clear region is not preserved.

The exact requirements depend on the code type and applicable specification.

8.3 Symbol grading

For quality-critical identification, a barcode verifier may be used to evaluate symbol quality against an applicable standard or customer requirement. A verifier is not the same as a normal production reader.

A production reader answers whether it can decode a symbol under its operating conditions. A verifier assesses defined symbol-quality characteristics using a controlled method.

Where the process requires symbol grading, follow the approved specification and verifier procedure rather than relying solely on successful reads.

9. Barcode Triggering and Read Timing

A barcode reader must acquire the symbol at the correct time. Triggering may be initiated by:

  • A PLC digital output.
  • An integrated photoelectric sensor.
  • An internal presentation or motion trigger.
  • An industrial network command.
  • An encoder or position-based event.
  • A configured continuous-reading mode.

In an automated engine assembly station, the PLC may trigger the reader after a part reaches a known position and the station is ready.

The control sequence should define:

  • When reading is permitted.
  • Which part or carrier is expected.
  • How the read timeout is handled.
  • How many reads are permitted.
  • How duplicate or multiple codes are handled.
  • What happens when no code is found.
  • How a valid result is associated with the current engine.
  • Whether the part must remain stationary during reading.

Repeatedly triggering the reader without controlling the station state can result in duplicate reads, stale data, or a valid code being assigned to the wrong engine.

10. PLC Integration

The PLC may control the reader through discrete I/O, serial communication, or an industrial network. The exact interface determines how trigger commands, read status, decoded strings, and errors are exchanged.

10.1 Discrete I/O interface

A simple reader interface may provide signals such as:

  • Trigger.
  • Busy.
  • Good read.
  • No read.
  • Error.

The decoded barcode itself generally requires a data interface unless the reader provides a specialized encoded output arrangement.

10.2 Network or serial interface

A data interface can transfer the decoded string, status, and other information supported by the reader.

Potential interfaces include:

  • Ethernet TCP/IP.
  • EtherNet/IP.
  • PROFINET.
  • RS-232.
  • RS-485 where supported.
  • Vendor-specific industrial protocols.

These protocols are not interchangeable. Confirm the reader, PLC, network configuration, data representation, and supported protocol before integration.

10.3 Typical PLC handshake

Station ready
     ↓
Confirm expected part or carrier
     ↓
Trigger barcode reader
     ↓
Wait for read completion
     ↓
Receive decoded data and status
     ↓
Check current-cycle result validity
     ↓
Validate format and production authorization
     ↓
Correct identifier?
  ├── Yes → Continue approved process
  └── No  → Reject, stop, or request recovery

This sequence illustrates the control concept, not a complete program. Actual fault handling, safety interlocks, and production authorization must follow the approved machine design.

10.4 Important handshake signals

Signal or data item Purpose Important consideration
Reader ready Indicates the reader can accept a request Confirm communication and device health
Trigger request Starts an acquisition or read operation Use the required trigger timing
Busy Indicates acquisition or decoding is active Avoid unintended overlapping triggers
Good read Indicates successful decoding Does not prove the identifier is authorized
No read Indicates no acceptable symbol was decoded Distinguish from a valid but rejected identifier
Decoded string Carries the identified data Check length, character set, and validity
Result valid Indicates that the data belongs to the current read Prevent reuse of stale data
Timeout Indicates the read did not complete within the defined period Use an approved recovery response
Communication status Indicates the interface state A decoded value may be unavailable or delayed
Acknowledge or reset Clears a status or permits another attempt Must not erase required diagnostic evidence

11. Identifier Validation

A decoded string should not automatically be accepted as a valid production identifier.

Validation may include:

  • Expected character length.
  • Permitted character set.
  • Prefix or format checks.
  • Check-digit verification where the identifier scheme defines one.
  • Identifier existence in the production database.
  • Correct engine or component variant.
  • Correct production order or station routing.
  • Current production status.
  • Duplicate-use detection.
  • Rework or hold status.
  • Compatibility with the next process recipe.

For example, a code may be syntactically valid but refer to an engine variant that is not permitted at the current station.

The system should distinguish between a read failure and an identifier validation failure. These conditions require different troubleshooting paths.

12. Engine Identification and Traceability

A production line may use a unique engine serial number as the primary identifier. Components, subassemblies, test results, and process records are then associated with that identifier through the manufacturing system.

Engine Serial Number
        ↓
Production Order / Variant
        ↓
Component Identification
        ↓
Assembly Station Records
        ↓
Torque / Press / Inspection Results
        ↓
Test Results and Rework History
        ↓
Completed Engine Genealogy

The barcode may contain the full identifier or a shorter key used to retrieve a database record. The data architecture must define which information is encoded directly and which information is retrieved from the manufacturing system.

12.1 Genealogy

Product genealogy records the relationship between the final product and the components, materials, operations, and results used to manufacture it.

For an engine, genealogy may include:

  • Engine serial number.
  • Production order and variant.
  • Component serial numbers or batch identifiers.
  • Supplier lot information.
  • Assembly station and timestamp.
  • Fastening and press-fit results.
  • Inspection and end-of-line test results.
  • Rework and repair history.
  • Quality holds and release status.

The required detail depends on the product, process, customer, and quality requirements.

13. Duplicate Reads and Stale Data

Duplicate and stale data are important control-system risks.

A reader may read the same symbol more than once because of repeated triggering, a part remaining in the field of view, or a communication retry. A PLC may also retain the last decoded string after a new read fails.

Potential consequences include:

  • Duplicate production records.
  • Incorrect component-to-engine association.
  • Reuse of a previous engine identifier.
  • Wrong recipe selection.
  • Incorrect station routing.
  • Traceability gaps.

13.1 Recommended controls

  • Clear or invalidate the previous result at the appropriate point in the sequence.
  • Associate each read with a current cycle or transaction identifier.
  • Require a new valid result before authorizing the next process.
  • Distinguish read completion from read success.
  • Prevent an old string from being accepted after a timeout.
  • Apply duplicate detection according to the identifier's intended uniqueness.
  • Record rejected reads and recovery actions where required.
  • Verify correct engine association before saving process results.

The exact implementation depends on the PLC and reader interface, but the principle is universal: the current cycle must be authorized by current, valid data.

Intermittent read Vibration, inconsistent label position, marginal symbol quality Review mounting, trigger timing, and read statistics

15. Structured Troubleshooting Procedure

When a barcode system fails, diagnose it in layers rather than immediately replacing the reader.

  1. Physical layer: Inspect the label, mark, mounting, distance, angle, lighting, and contamination.
  2. Reader layer: Check power, status indicators, trigger behavior, configured symbology, and decoding diagnostics.
  3. Signal layer: Verify trigger, busy, good-read, no-read, and error signals where applicable.
  4. Communication layer: Confirm Ethernet or serial connectivity, protocol settings, data mapping, and transfer status.
  5. PLC layer: Check sequence state, input/output mapping, string handling, timeouts, and current-cycle result validity.
  6. Validation layer: Verify the identifier format, variant, database record, and station authorization.
  7. Traceability layer: Confirm that the identifier and process results belong to the correct engine.
  8. Recovery layer: Follow the approved re-read, rejection, rework, or engineering recovery procedure.

Capture the fault state and diagnostic evidence before resetting the reader or PLC sequence whenever practical.

16. Network and Communication Considerations

Industrial barcode readers may use Ethernet, serial communication, or discrete I/O. Networked readers introduce configuration and communication dependencies that must be maintained.

Important checks include:

  • Correct IP address and subnet.
  • No unintended IP address conflict.
  • Correct PLC and reader communication settings.
  • Correct industrial protocol and device configuration.
  • Valid connection state and data update behavior.
  • Correct byte order, string length, and character encoding where relevant.
  • Proper handling of message termination and delimiters for serial or TCP-based protocols.
  • Network switch and cable condition.
  • Device configuration backup.
  • Appropriate access controls for configuration interfaces.

Do not assume that a successful network ping proves the reader is exchanging valid production data. Basic network reachability and application-level communication are different tests.

17. Barcode Security and Data Integrity

A barcode is a data carrier, not a security mechanism. A readable identifier may be copied, altered, or attached to the wrong physical part.

Controls may be needed to prevent unauthorized or incorrect identification, particularly where a code determines a product variant, production recipe, or quality release.

Possible controls include:

  • Database validation against the production order.
  • Duplicate-use and sequence checks.
  • Authorized label generation.
  • Controlled reprinting and label replacement.
  • Product-state verification.
  • Access control for reader and PLC configuration.
  • Audit logging of manual overrides.
  • Controlled rework and retest records.
  • Consistency checks between the physical part and its recorded identity.

A barcode's check digit, where applicable, helps detect certain data-entry or decoding errors. It does not prove authenticity or guarantee that the label belongs to the physical component.

18. Barcode Label Printing and Verification

Barcode printing is closely related to the reader because poor printing quality directly affects reading reliability.

Typical label-generation controls include:

  • Correct identifier and data format.
  • Correct symbology.
  • Suitable module size and label dimensions.
  • Required quiet zones.
  • Adequate contrast and print resolution.
  • Correct printer configuration and media.
  • Controlled label templates and revisions.
  • Verification of the printed result where required.
  • Prevention of duplicate or unauthorized serial labels.

The reader and printer should be validated together using actual production labels and realistic handling conditions.

A successful test on a freshly printed label does not necessarily prove long-term readability after oil exposure, abrasion, heat, or handling. Environmental durability requirements must be addressed by the approved label and marking specification.

19. Barcode Configuration Management

Reader configurations may include:

  • Enabled code types.
  • Minimum and maximum data length.
  • Character filtering and output formatting.
  • Trigger mode.
  • Exposure, illumination, and focus settings where configurable.
  • Communication parameters.
  • Good-read and no-read behavior.
  • Data transmission format.
  • Device identification and firmware version.

Configuration changes should be controlled and documented. Unplanned changes can affect read rate, data formatting, and PLC compatibility.

A useful backup record includes the reader model, firmware, configuration file, network settings, station location, PLC interface, approved code types, and validation results.

After replacing a reader, verify not only that it can read the code but also that it sends the expected string and status to the PLC and that the manufacturing system accepts the correct identifier.

20. Barcode System Preventive Maintenance

Routine checks

  • Inspect labels and direct marks for contamination or damage.
  • Clean the reader window according to manufacturer instructions.
  • Check reader mounting and alignment.
  • Inspect cables, connectors, and protective conduits.
  • Review read-rate and no-read diagnostics.
  • Check trigger and communication behavior.
  • Investigate recurring failures instead of repeatedly acknowledging them.

Planned maintenance

  • Verify reader configuration against the approved backup.
  • Check communication and PLC handshake diagnostics.
  • Validate correct string formatting and identifier parsing.
  • Inspect the illumination system and optics.
  • Check the condition and placement of label media where applicable.
  • Verify label print quality and marking process controls.
  • Test duplicate-read and stale-result handling using an approved test procedure.
  • Confirm traceability association with the correct engine.
  • Review firmware and configuration change history.
  • Verify recovery procedures and relevant spare parts.

After maintenance or replacement

  • Confirm the correct reader is installed.
  • Verify power, network, and I/O connections.
  • Restore the approved configuration where required.
  • Test representative symbols under actual production conditions.
  • Confirm both valid and invalid identifiers are handled correctly.
  • Verify no-read and communication-failure responses.
  • Confirm the result is associated with the correct product.
  • Record the maintenance and validation outcome before production release.

21. Barcode System KPIs

KPI Purpose Interpretation
First-pass read rate Percentage of initial reads that succeed Indicates initial identification reliability
No-read rate Frequency of unsuccessful decoding Investigate symbol quality, optics, and timing
Re-read rate Frequency of additional read attempts May indicate marginal quality or poor trigger control
False-acceptance rate Frequency of invalid data being accepted Requires defined invalid test cases and controlled evaluation
Identification cycle time Time required to obtain and validate an identifier Include communication and database latency where relevant
Duplicate-record rate Frequency of unintended duplicate transactions Check trigger logic, retries, and transaction handling
Traceability completeness Proportion of required production records successfully associated Check identity correctness, not just record existence
Reader fault downtime Downtime attributable to the identification system Separate reader faults from network, PLC, and label issues
Label verification compliance Compliance with the required print or mark verification process Successful reads alone may not satisfy quality requirements

Read-rate metrics should use a consistent definition. For example, a first-pass read and a successful read after three retries are not equivalent when evaluating production reliability.

22. RCA/CAPA Example: Intermittent Engine Serial Number Read Failure

Problem statement

An engine assembly station intermittently fails to read the engine serial number, causing production interruptions.

Evidence to collect

  • Reader diagnostics and captured images, where supported.
  • Label or direct-marking condition.
  • Reader distance, angle, focus, and mounting.
  • Trigger timing and PLC sequence state.
  • Network or serial communication logs.
  • Decoded strings and current-cycle result status.
  • Read failures by product variant, shift, or station.
  • Recent maintenance and configuration changes.

Potential causes

  • Poor print or marking quality.
  • Oil or contamination on the code.
  • Reader misalignment.
  • Incorrect trigger timing.
  • Damaged cable or unstable network connection.
  • Incorrect reader configuration.
  • Stale-result handling or incorrect PLC data parsing.

Corrective actions

  1. Contain affected products according to the approved traceability procedure.
  2. Determine whether the fault occurs during optical decoding, communication, PLC handling, or identifier validation.
  3. Correct the verified cause.
  4. Validate representative codes across the required product variants.
  5. Test no-read, invalid-code, and communication-failure handling.
  6. Confirm correct product association in the manufacturing database.
  7. Document the root cause and corrective action.
  8. Trend read failures to confirm the problem does not recur.

Do not solve repeated read failures by accepting the previous serial number or bypassing identifier validation. That merely replaces a visible stoppage with a potentially invisible traceability defect.

23. Practical Learning Exercises

Exercise 1: Identify the complete system

Select a barcode reader on an engine assembly station. Record its model, code types, mounting location, trigger method, interface, PLC address or communication mapping, and role in production traceability.

Exercise 2: Trace a serial number

Follow an engine serial number from the physical label to the reader, PLC, HMI, manufacturing database, and downstream process records.

Exercise 3: Diagnose a no-read event

Capture the reader status, label condition, trigger timing, and PLC state for a real or approved test failure. Identify which layer is responsible.

Exercise 4: Validate identifier handling

Test valid, invalid, duplicate, malformed, and missing identifiers under an approved procedure. Confirm that each condition produces the intended result.

Exercise 5: Test communication recovery

Verify how the system handles a temporary reader communication failure, timeout, and recovery. Ensure that stale data cannot authorize a new process cycle.

Exercise 6: Create a barcode maintenance register

Record reader model, firmware, location, IP address where applicable, protocol, configuration backup, supported symbologies, spare part, maintenance history, and validation status.

24. Competency Checklist

  • Explain linear barcodes and two-dimensional codes.
  • Distinguish barcode readers from barcode verifiers.
  • Understand fixed-mount readers, imaging readers, and supported symbologies.
  • Identify factors that affect barcode readability.
  • Explain reader triggering and PLC handshake logic.
  • Distinguish successful decoding from identifier authorization.
  • Prevent stale data, duplicate reads, and incorrect product association.
  • Diagnose optical, electrical, network, PLC, and database-related failures.
  • Understand engine genealogy and production traceability.
  • Maintain reader configurations and validate replacements.
  • Apply controlled label printing and verification practices.
  • Document faults, RCA/CAPA, and post-maintenance validation.

25. Final Technical Summary

Barcode systems connect physical products to their digital production records. In engine assembly, they enable engine identification, component tracking, process recipe selection, quality-data association, and manufacturing genealogy.

Reliable operation requires more than a reader that successfully decodes a symbol. The complete system must maintain readable marking, correct triggering, valid communication, robust PLC handshakes, identifier validation, correct product association, and controlled recovery from faults.

The most important maintenance principles are:

  • Diagnose optical, electrical, communication, and application layers separately.
  • Never confuse a good read with an authorized production identifier.
  • Prevent stale data and duplicate transactions from corrupting traceability.
  • Validate the reader and PLC interface together after maintenance.
  • Preserve approved configuration backups and change history.
  • Ensure barcode failures are handled without silently bypassing production controls.
  • Record the root cause and verify the corrective action.

A barcode is only as useful as the system that interprets it and associates it with the correct physical product.
