1. Definition and Purpose

Sequence troubleshooting is the process of diagnosing why an automated machine fails to advance through its intended operating steps, remains stuck in one state, skips an operation, or stops while waiting for a required condition.

In an automated production line, the PLC usually coordinates operations in a defined order. A machine may clamp a component, verify its position, start a machining operation, wait for completion, release the component, and transfer it to the next station.

Each operation depends on specific inputs, outputs, timing conditions, permissives, and completion feedback.

Common sequence faults include:

  • A sequence step remains active indefinitely.
  • The next step never becomes active.
  • A required permissive is missing.
  • A sensor never confirms the expected position.
  • A timer expires without the expected transition.
  • A completion signal arrives too early or too late.
  • A machine remains in an incorrect operating mode.
  • A fault or interlock prevents progression.
  • A sequence bit is latched or reset incorrectly.
  • The PLC advances, but the physical machine does not complete the operation.

The objective is to identify the exact transition that failed, determine why its conditions are not satisfied, correct the verified root cause, and validate the sequence without bypassing required protections.

2. Understand Sequence-Based Machine Control

A sequence is a set of defined machine states or steps. Each step represents an operation or stage of the machine cycle.

A simple machining station might follow this sequence:

Step 0: Idle
    ↓ Start request accepted
Step 10: Check machine ready
    ↓ All required permissives satisfied
Step 20: Clamp component
    ↓ Clamp-closed feedback received
Step 30: Start machining
    ↓ Machining completion received
Step 40: Retract tool
    ↓ Retracted-position feedback received
Step 50: Unclamp component
    ↓ Clamp-open feedback received
Step 60: Cycle complete
    ↓ Reset or next-cycle conditions satisfied
Step 0: Idle

This is an illustrative sequence. Actual machine logic may use state machines, step numbers, multiple parallel operations, subroutines, or vendor-specific sequence instructions.

2.1 Important sequence terms

Term Meaning
Step or state The current stage of the machine cycle
Transition The condition or event that allows movement to another step
Permissive A condition that must be satisfied before an operation is allowed
Interlock A condition that inhibits an operation to prevent an unacceptable machine state
Completion feedback A signal confirming that an operation has reached its intended result
Timeout A defined time limit for an expected operation or response
Recovery step A defined state or procedure used to restore operation after an interruption
Initialization Establishing the required starting state before normal operation
Sequence reset Returning sequence state to a defined condition according to the control design

A permissive and an interlock are related but not identical in every control design. A permissive generally allows an action when satisfied; an interlock prevents or inhibits an action when a prohibited condition exists.

3. What Is a Stuck Step?

A stuck step occurs when the sequence remains in its current state because the required transition condition is not becoming true, or because the program does not execute the expected transition.

For example, the machine remains at Step 20: Clamp component.

The expected transition may require:

  • Clamp command active.
  • Clamp-closed sensor ON.
  • Pressure or force condition satisfied.
  • No active fault.
  • Correct operating mode.

If any required condition remains false, the sequence may correctly refuse to advance.

The key diagnostic question is not simply, "Why is the machine stuck?" It is:

Which exact condition is preventing the current step from transitioning, and why is that condition not satisfied?

3.1 Common causes

  • Sensor does not detect the expected position.
  • Actuator fails to move.
  • Solenoid valve is not energized.
  • Pneumatic or hydraulic pressure is insufficient.
  • Drive is not ready.
  • Robot has not completed its operation.
  • Communication data is stale or unavailable.
  • Safety-related or process interlock is active.
  • Automatic mode is not selected.
  • Timer or counter condition is incorrect.
  • Transition logic references the wrong variable.
  • A sequence reset or initialization condition is incorrect.
  • Program changes altered the intended sequence behavior.

4. Understand Permissives and Interlocks

A machine may require several conditions to be satisfied before an operation begins.

For example, a conveyor start permissive might be represented conceptually as:

Conveyor_Start_Permissive =
    Auto_Mode
    AND Drive_Ready
    AND No_Active_Fault
    AND Upstream_Transfer_Allowed
    AND Downstream_Station_Ready

This example represents ordinary control logic only. Safety functions must be implemented and validated through the appropriate safety-related system.

If Conveyor_Start_Permissive is false, the next task is to identify which individual condition is false.

4.1 Common permissives

  • Correct operating mode selected.
  • Previous step completed.
  • Required sensor confirmed.
  • Drive ready and available.
  • Robot in the required state.
  • Workpiece detected.
  • Fixture or clamp in the required position.
  • Required pressure, vacuum, or process condition available.
  • Downstream station ready.
  • No active machine fault.
  • Required communication data valid.
  • Required process parameters within limits.

4.2 How to identify the missing permissive

  1. Find the sequence step that is currently active.
  2. Identify the logic that controls its transition.
  3. List every condition in the transition expression.
  4. Monitor the live value of each condition.
  5. Identify which condition does not match the expected state.
  6. Trace that condition to its source.
  7. Determine whether the cause is a physical device, configuration, communication issue, or program logic.
  8. Correct the actual cause and verify the transition.

Do not remove a permissive merely because it is the condition preventing the machine from running. It may exist to prevent collisions, protect tooling, maintain product quality, or enforce process order.

5. Diagnostic Method: Find the First Failed Transition

The most effective sequence diagnostic method is to work from the active state toward the next expected state.

Step 1: Confirm the current sequence state

Check the active step number, state variable, active sequence bit, or relevant function-block status.

Do not rely only on the HMI's displayed step. Verify the underlying PLC value because the display may be stale, mapped incorrectly, or showing a different sequence instance.

Step 2: Identify the expected next state

Read the sequence logic and determine which state should follow the current one.

For example:

Current_Step = 20
Expected_Next_Step = 30

These numbers are illustrative.

Step 3: Read the transition conditions

Suppose the transition from step 20 to step 30 requires:

Step_20_Complete =
    Clamp_Closed
    AND Pressure_OK
    AND Drive_Ready
    AND NOT Fault_Active

Monitor all four conditions. The first condition that is unexpectedly false becomes the starting point for deeper investigation.

Step 4: Trace the failed condition upstream

For example:

Clamp_Closed = FALSE

Investigate:

  • Is the clamp physically closed?
  • Is the sensor aligned?
  • Does the sensor indicator change?
  • Does the PLC input status change?
  • Is the input assigned to the correct tag?
  • Is the sensor signal affected by a force or override?
  • Is the clamp actuator receiving the required command?
  • Is pressure sufficient to complete the movement?

Step 5: Correct the root cause

Repair or configure the component that caused the missing condition. Do not modify sequence logic until evidence establishes that the logic itself is wrong.

Step 6: Verify normal sequence operation

Confirm that the transition occurs under the intended conditions, the next step performs correctly, and the machine handles the relevant fault and recovery conditions as designed.

6. Sensors and Completion Feedback

Many sequence faults originate from a mismatch between the physical machine and the feedback available to the PLC.

6.1 Typical sensor-related causes

  • Sensor damaged or misaligned.
  • Target not reaching the detection point.
  • Loose connector.
  • Broken cable.
  • Incorrect PNP/NPN interface.
  • Input channel fault.
  • Incorrect PLC tag mapping.
  • Sensor signal remains active due to a short circuit.
  • Sensor detects the wrong target.
  • Mechanical position does not match the expected position.
  • Feedback is delayed or intermittent.

6.2 Example: Clamp closes but sequence does not advance

The clamp appears physically closed, but the PLC remains in the clamping step.

Investigate the signal path in order:

Clamp Physical Position
          ↓
Clamp-Closed Sensor
          ↓
Field Wiring
          ↓
PLC Input Channel
          ↓
PLC Input Tag
          ↓
Sequence Transition Condition
          ↓
Next Sequence Step

The physical position alone does not prove that the PLC received the required feedback. Likewise, a sensor LED does not prove that the correct PLC input tag is changing.

6.3 Practical signal verification

Observation Likely investigation area
Clamp is not physically closed Actuator, valve, pressure, obstruction, or mechanical issue
Clamp is closed but sensor indicator is OFF Sensor alignment, target, sensor supply, or sensor fault
Sensor indicator is ON but PLC input is OFF Wiring, input supply, channel, or electrical interface
PLC input is ON but logic tag is OFF Tag mapping, inversion, alias, or program logic
Logic tag is ON but transition remains false Another permissive, incorrect transition expression, or sequence execution issue
Transition condition is true but step does not change State-update logic, competing assignments, execution order, or sequence implementation

Use the electrical drawing and actual I/O configuration to verify the signal path.

7. Timers and Sequence Timeouts

Timers are commonly used to detect operations that take too long or to introduce deliberate delays.

Examples include:

  • Waiting for a cylinder to extend.
  • Waiting for a robot operation to complete.
  • Allowing a process delay before transfer.
  • Detecting a missing sensor response.
  • Monitoring a drive's readiness.

7.1 Typical timer-related faults

  • Timer enable never becomes true.
  • Timer resets every scan.
  • Preset is incorrect.
  • Timer is using the wrong time unit.
  • Done bit is referenced incorrectly.
  • Completion feedback arrives after the timeout.
  • Timer instance is reused by multiple operations.
  • The timeout alarm is latched and not cleared by the intended reset conditions.

7.2 How to troubleshoot

  1. Identify the timer associated with the active sequence step.
  2. Check the timer's enable condition.
  3. Monitor elapsed time and preset.
  4. Confirm whether the timer accumulates, resets, or completes as expected.
  5. Check whether a timer-done signal is part of the transition.
  6. Verify the physical operation time against the machine design.
  7. Correct the actual cause of the timeout.
  8. Validate the operation and fault response.

Do not increase a timer preset simply to make a timeout disappear. The original timeout may be detecting a failing actuator, delayed feedback, or a process condition that requires intervention.

8. Actuators, Drives, and Robot Completion

A sequence may wait for a physical operation to finish even though the PLC command has already been issued.

Common examples:

  • Cylinder does not extend.
  • Clamp does not reach its closed position.
  • VFD does not achieve the expected running state.
  • Servo axis does not reach its target position.
  • Robot program does not reach the completion handshake.
  • CNC cycle-complete signal is missing.
  • Pneumatic pressure does not reach the required threshold.

Diagnostic method

  • Verify the command generated by the PLC.
  • Verify the command reaches the relevant output or communication interface.
  • Check the actuator's local state and diagnostics.
  • Verify energy supply, such as electrical power, pneumatic pressure, or hydraulic pressure.
  • Confirm that the mechanical operation is not obstructed.
  • Verify completion feedback.
  • Check whether the sequence is waiting for the correct feedback variable.
  • Confirm that the operation's timeout and fault handling are functioning as intended.

A PLC command being ON does not prove that the actuator has moved. The command path and the physical result must be investigated separately.

9. Robot and PLC Handshake Faults

Automated production lines commonly use handshake signals between a PLC and a robot controller.

Typical signals may include:

  • Robot ready.
  • Robot program selected.
  • Start request.
  • Busy.
  • Program running.
  • Cycle complete.
  • Robot fault.
  • Part-present confirmation.
  • Request to enter or leave a station.

Actual signal names and sequencing differ by integrator and robot manufacturer.

9.1 Example handshake

PLC verifies robot-ready conditions
              ↓
PLC issues start request
              ↓
Robot accepts the request
              ↓
Robot performs the programmed operation
              ↓
Robot asserts completion
              ↓
PLC verifies completion conditions
              ↓
PLC advances the machine sequence

9.2 Common handshake problems

  • Start request never reaches the robot.
  • Robot is not in the expected mode.
  • Wrong robot program is selected.
  • Robot reports busy or faulted.
  • PLC waits for the wrong completion bit.
  • Completion bit is reset before the PLC reads it.
  • PLC and robot disagree about signal timing.
  • Communication is unavailable or stale.
  • A handshake signal is retained from a previous cycle.
  • The required reset or acknowledgement sequence is incomplete.

9.3 Troubleshooting handshake faults

  1. Monitor the PLC's request signals.
  2. Check the robot's corresponding input signals.
  3. Confirm that the robot accepts the request.
  4. Monitor the robot's status and output signals.
  5. Verify that the PLC receives the expected completion feedback.
  6. Check the timing and reset behavior of each handshake signal.
  7. Confirm the expected program and operating mode.
  8. Correct the verified issue and test the full handshake cycle.

Do not force a robot-complete signal to advance the PLC sequence. That can make the PLC proceed while the robot is still moving or has not completed the operation.

10. Sequence State and Reset Problems

Some sequence faults arise because the controller's internal state does not match the machine's physical state.

Examples include:

  • PLC restarts while the machine is halfway through a cycle.
  • Retentive sequence state remains active after power loss.
  • Initialization does not execute as intended.
  • Multiple step bits remain active.
  • No step bit is active.
  • A reset clears the sequence but not the associated actuator state.
  • Recovery logic assumes the machine is in a position it has not reached.
  • A step is re-entered repeatedly.
  • Two routines write to the same state variable.

10.1 Sequence-state checks

  • Confirm the active step and expected next step.
  • Determine whether the design allows one or multiple active steps.
  • Check how the sequence initializes after startup.
  • Verify the reset conditions.
  • Compare the PLC state with the actual physical machine state.
  • Inspect retained variables and initialization logic.
  • Check for competing assignments to state variables.
  • Confirm that recovery procedures handle interrupted cycles.

Never reset a sequence solely to clear an HMI message. A sequence reset may cause outputs to change or leave the machine in a state that requires controlled recovery.

11. Manual, Automatic, and Recovery Modes

The same actuator may behave differently depending on the selected mode.

Manual mode

The operator or technician may control individual functions under defined permissives. Manual mode should not be assumed to bypass interlocks or safety functions.

Automatic mode

The PLC executes the intended sequence and requires the configured transition conditions.

Recovery mode

Recovery logic may allow a controlled return to a known state after a fault or interrupted cycle. Its exact behavior is machine-specific.

Common mode-related faults

  • Automatic mode is not selected.
  • A mode-transition condition is missing.
  • A manual command is still active.
  • The machine is waiting for an initialization or homing operation.
  • Recovery mode requires an acknowledgement.
  • The selected mode does not support the expected sequence transition.
  • A retained fault prevents automatic restart.

Check the intended mode and its conditions before changing sequence logic.

12. Parallel Operations and Synchronization

Some machine sequences allow multiple operations to occur simultaneously. The next state may require all parallel operations to finish.

Example:

Step 100: Start parallel operations
              ↓
       ┌──────┴──────┐
       ↓             ↓
   Clamp part     Move axis
       ↓             ↓
   Clamp ready    Axis in position
       └──────┬──────┘
              ↓
     Both completion signals true
              ↓
       Step 110: Continue

If one operation finishes while the other remains incomplete, the sequence may wait indefinitely.

Check:

  • Which parallel branches are active.
  • Whether each branch has a valid completion condition.
  • Whether a completion signal is reset too early.
  • Whether the transition uses AND or OR logic as intended.
  • Whether the two operations depend on each other's state.
  • Whether an operation failed without setting an alarm.
  • Whether shared resources prevent one branch from progressing.

A missing completion signal from one branch can block the entire cycle even when all other branches appear healthy.

13. Communication and Data Validity in Sequences

Sequence logic may depend on values received from a robot, VFD, CNC, remote I/O station, vision system, or another PLC.

A missing transition can therefore be a communication or data-validity problem rather than a sequence-program defect.

Check:

  • Device communication status.
  • Data freshness.
  • Device-ready and completion bits.
  • Correct mapping of incoming data.
  • Correct reset and handshake timing.
  • Device mode and fault status.
  • Whether a disconnected device leaves the last value displayed.
  • Whether the sequence validates data quality before using it.

For example, a robot-complete bit may appear ON in an HMI but represent an old value from before the current cycle. Verify that the handshake is valid for the current operation.

14. Practical Troubleshooting Case: Stuck at Clamp Step

Machine condition: A station stops after the PLC commands a fixture clamp.

Observed behavior:

  • PLC remains in RUN.
  • Clamp output command is ON.
  • Fixture does not receive a valid clamp-complete confirmation.
  • The sequence remains at the clamping step.

Investigation:

  1. Confirm the active step and expected transition.
  2. Verify the clamp output command.
  3. Check the solenoid or actuator command path.
  4. Verify pneumatic or hydraulic supply, where applicable.
  5. Check the clamp's physical position.
  6. Inspect the closed-position sensor and wiring.
  7. Monitor the corresponding PLC input and logic tag.
  8. Check for forces, incorrect mapping, or an active interlock.
  9. Correct the verified cause.
  10. Test the clamp and confirm that the sequence advances normally.

Possible root cause: The clamp reaches its mechanical end position, but a misaligned sensor fails to detect it.

Corrective action: Correct the sensor alignment according to the machine specification and verify reliable detection. Do not force the clamp-complete signal to bypass the missing feedback.

Verification: The PLC receives the correct sensor status, the sequence advances only when the required conditions are met, and the station completes the intended cycle.

15. Practical Troubleshooting Case: Robot Completion Missing

Machine condition: The PLC issues a robot start request, but the machine never advances to the transfer step.

Observed behavior:

  • Robot controller is powered.
  • PLC start request is active.
  • Robot may be running or waiting.
  • PLC's robot-complete condition remains false.

Investigation:

  1. Verify that the robot receives the start request.
  2. Check robot mode, selected program, and controller diagnostics.
  3. Confirm whether the robot accepted the request.
  4. Monitor the robot's busy, fault, and completion signals.
  5. Verify the completion-signal mapping at the PLC.
  6. Check whether the robot is waiting for another PLC handshake.
  7. Check whether a signal is being cleared prematurely.
  8. Correct the actual handshake or device fault.
  9. Run the approved recovery and functional test.

Possible root cause: The PLC and robot use mismatched handshake logic after a program revision, so the PLC waits for a completion signal that is not generated under the new sequence.

Verification: The request, acceptance, busy, completion, and reset signals follow the intended order, and the full machine sequence completes without forced signals.

17. Common Troubleshooting Mistakes

  • Resetting the sequence without confirming the physical machine state.
  • Assuming the HMI's displayed step is the actual PLC state.
  • Changing transition logic before checking the physical feedback.
  • Removing a permissive without understanding its purpose.
  • Increasing timeout values to hide slow or failed equipment.
  • Forcing completion signals to advance a sequence.
  • Ignoring stale robot or remote-device handshake signals.
  • Assuming that an output command proves an actuator moved.
  • Failing to check parallel operations.
  • Overlooking initialization and retained-state behavior.
  • Testing only the immediate operation instead of the complete cycle.
  • Ignoring recovery behavior after an interrupted cycle.
  • Making undocumented online edits during a breakdown.
  • Failing to verify safety-related functions after changes.

18. Interview Questions and Answers

Q1. What is a stuck step in a PLC sequence?

A stuck step occurs when the sequence remains in its current state because the required transition condition is not satisfied or the state-transition logic is not executing as intended.

Q2. What is a permissive?

A permissive is a condition that must be satisfied before a specified operation is allowed. Examples include drive-ready status, correct operating mode, required position feedback, or downstream station readiness.

Q3. How do you troubleshoot a stuck sequence step?

Identify the active state, determine the expected next state, monitor the transition conditions, locate the first unexpected condition, trace it to its source, correct the verified cause, and validate the complete operation.

Q4. What is the difference between a permissive and an interlock?

A permissive generally establishes that the conditions for an operation are satisfied. An interlock inhibits an operation when a prohibited condition exists. Exact terminology and implementation vary by machine and control design.

Q5. Why might a cylinder extend but the sequence fail to advance?

The completion sensor may not detect the cylinder position, the PLC may not receive the input, the tag may be incorrectly mapped, or another transition condition may remain false.

Q6. Why should a sequence not be reset blindly?

The PLC's internal state may no longer match the machine's physical state. Resetting can change outputs, interrupt recovery logic, or cause an unexpected movement.

Q7. How do you troubleshoot a robot handshake fault?

Check the PLC's request signals, the robot's received inputs, its mode and program, its status and completion outputs, the PLC's feedback mapping, and the timing and reset behavior of the handshake.

Q8. Why is a sequence timeout useful?

It detects an operation that has not completed within the defined period. It helps identify failed actuators, missing feedback, communication problems, and other conditions that prevent progression.

Q9. What should you do if a sequence advances only when a completion bit is forced?

Investigate why the real completion condition is missing. Check the physical operation, feedback sensor, mapping, communication, and program logic. Remove the force according to procedure and correct the actual cause.

Q10. When is sequence troubleshooting complete?

When the root cause has been corrected, the expected transitions occur under the intended conditions, the complete sequence and recovery behavior are verified, and the machine operates within its approved safety and process requirements.

19. Completion Checklist

  • Explain sequence states, transitions, permissives, and interlocks.
  • Identify the active step and expected next step.
  • Trace the first failed transition condition.
  • Verify sensors and field feedback against PLC input status.
  • Diagnose actuator, drive, robot, and completion-feedback faults.
  • Investigate timer and timeout behavior.
  • Verify initialization, reset, and retained-state logic.
  • Diagnose manual, automatic, and recovery-mode issues.
  • Investigate parallel operations and synchronization.
  • Verify communication and handshake data freshness.
  • Correct the root cause without bypassing required protections.
  • Test the complete sequence and relevant recovery conditions.
  • Document the fault, corrective action, and verification evidence.
