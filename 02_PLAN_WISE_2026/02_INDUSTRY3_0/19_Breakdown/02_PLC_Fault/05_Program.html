1. Definition and Purpose

A PLC program fault occurs when the controller's logic, configuration, execution state, or data produces behavior that differs from the intended machine operation.

During industrial breakdowns, the PLC may remain in RUN mode with no hardware fault while the machine refuses to start, stops unexpectedly, skips an operation, or activates an output under unexpected conditions.

Program-related troubleshooting involves investigating:

  • Recent logic changes and online edits.
  • Incorrect conditions, interlocks, and permissives.
  • Timer, counter, latch, and sequence logic.
  • Forced inputs and outputs.
  • Modified setpoints and configuration values.
  • Incorrect tag mapping or variable values.
  • Program version mismatches.
  • Unexpected changes to operating modes.
  • Logic that has been bypassed, overwritten, or unintentionally modified.

The objective is to identify the actual logic or configuration issue, restore the approved behavior, and verify the machine's operation without creating an unsafe condition.

Important distinction: A PLC being in RUN does not prove that its program is correct. The CPU can execute incorrect logic perfectly well. Computers have a talent for doing exactly what they were told, including the wrong thing.

2. Understand the PLC Scan Cycle

Most conventional PLC programs execute through a repeating scan cycle, although exact execution behavior depends on the controller and task configuration.

A simplified scan consists of:

  1. Reading or updating input data.
  2. Executing the applicable program logic.
  3. Updating outputs.
  4. Performing communication, diagnostics, and other scheduled tasks.
Physical Inputs / Received Network Data
                  ↓
          Input Data Available
                  ↓
          Execute Program Logic
                  ↓
         Update Output Commands
                  ↓
    Physical Outputs / Network Commands
                  ↓
             Repeat Scan

Modern PLCs may use periodic tasks, event-triggered tasks, asynchronous communication, distributed I/O updates, and process-image configurations that differ from this simplified model.

When diagnosing a program fault, determine where the expected behavior breaks down:

  • Is the input data correct?
  • Is the logic condition becoming true?
  • Is the expected internal bit or state changing?
  • Is the output command being generated?
  • Is the output module or network device receiving the command?
  • Is a separate interlock preventing physical operation?

This prevents unnecessary changes to working logic when the actual problem is a sensor, output module, drive, or communication fault.

3. Common Symptoms of Program-Related Faults

Symptom Possible program-related cause
Machine does not start Missing permissive, incorrect mode condition, latched fault, or incorrect start logic
Machine stops at a particular operation Incorrect transition condition, missing completion signal, or sequence logic error
Output activates unexpectedly Incorrect Boolean condition, retained bit, force, or unintended logic change
Output never activates False condition, incorrect address, overwritten value, or an output being inhibited elsewhere
Timer never completes Timer enable condition is false, timer is reset repeatedly, or preset configuration is incorrect
Counter value is incorrect Count condition, reset condition, duplicate counting, or data-mapping issue
Machine works after a restart but fails again Retentive state, initialization logic, timing dependency, or an intermittent external condition
Fault occurs after a program download Wrong program version, changed configuration, altered initial values, or incorrect target controller
HMI command has no effect Incorrect tag mapping, missing logic condition, mode restriction, or command not reaching the PLC
Machine behavior changes between manual and automatic Different mode-specific logic, permissives, or command paths

These are possible causes, not diagnoses. Always confirm the actual signal path and logic state.

4. Online Monitoring and Logic Troubleshooting

Online monitoring lets a technician observe the live state of program instructions, variables, timers, counters, and outputs while the PLC is connected.

Examples of engineering environments include:

  • Siemens TIA Portal.
  • Rockwell Studio 5000 Logix Designer.
  • Mitsubishi GX Works.
  • Other manufacturer-specific PLC programming software.

The exact features, terminology, and safety requirements vary by platform.

4.1 Diagnostic procedure

  1. Identify the exact machine symptom and affected operation.
  2. Confirm the correct PLC, project, controller, and program version.
  3. Establish an approved online connection.
  4. Read the controller status and relevant diagnostic information.
  5. Monitor the logic associated with the failed operation.
  6. Trace the condition from physical or network inputs through internal logic to the expected output.
  7. Identify the first condition that differs from the intended behavior.
  8. Check recent changes, forces, retained values, and operating modes.
  9. Correct the verified cause using the approved change procedure.
  10. Test the affected operation and relevant interlocks.
  11. Save the verified program and record the change.

4.2 Trace logic from the symptom backward

Suppose a conveyor does not start.

A simplified start condition might be:

Conveyor_Start =
    Auto_Mode
    AND Safety_OK
    AND Drive_Ready
    AND Start_Request
    AND NOT Fault_Active

If Conveyor_Start is false, inspect each contributing condition.

  • Is automatic mode selected?
  • Is the relevant safety status healthy?
  • Is the drive ready?
  • Is the start request reaching the PLC?
  • Is a fault bit active?

The expression is illustrative only. Actual safety functions must be implemented in the appropriate safety-related system and verified according to the machine design. A standard PLC bit must not be treated as proof that a safety function is effective.

Troubleshooting principle: Find the first unexpected condition in the logic path. Do not change the final output instruction merely because it is the last visible point in the chain.

5. Logic Changes and Online Edits

A logic change modifies the program's behavior. Depending on the platform, changes may be made offline and downloaded, or performed through supported online editing functions.

Common examples include:

  • Adding or removing a permissive.
  • Modifying a timer preset.
  • Changing an interlock condition.
  • Altering a counter reset.
  • Changing a sequence transition.
  • Modifying a drive command.
  • Changing a tag address or data type.
  • Adjusting initialization or retentive behavior.
  • Modifying a fault-handling routine.

5.1 Why unauthorized changes are dangerous

An undocumented logic change may:

  • Alter machine timing.
  • Allow an operation to proceed without an intended condition.
  • Disable a fault response.
  • Change the sequence order.
  • Cause unexpected output behavior.
  • Create differences between the running controller and the approved project.
  • Make future breakdowns harder to diagnose.

5.2 Verify recent program changes

Check:

  • Controller change logs, where available.
  • Online-edit status.
  • Project comparison results.
  • Program version and revision records.
  • Modified rungs, networks, blocks, or routines.
  • Changed timer and counter presets.
  • Modified tag values or initial values.
  • Changes made during the previous breakdown.
  • Download records and backup timestamps.

Not every PLC platform records a complete audit trail. If the required history is unavailable, compare the controller with a verified approved project and review maintenance records.

5.3 Program comparison

A comparison can identify differences between two program versions or between an offline project and the online controller.

Depending on the platform, compare:

  • Program logic.
  • Data structures and tag definitions.
  • Hardware configuration.
  • Network configuration.
  • Initial values.
  • Retentive settings.
  • Safety-related program elements, using the required safety validation process.
  • Firmware and project compatibility.

A difference is not automatically a fault. Some differences may be approved changes. The task is to identify whether each difference is intentional, authorized, and validated.

6. Forced Bits: Definition and Risks

A force is a controller or engineering-software feature that overrides the normal value of a supported signal or variable, depending on the platform and the object being forced.

Forces are sometimes used during controlled commissioning and troubleshooting. They can also cause severe problems if left active or applied to the wrong signal.

Examples include:

  • Forcing an input value for a test.
  • Forcing an output command.
  • Overriding a supported variable.
  • Leaving an old force active after a repair.
  • Applying a force while another technician is diagnosing the machine.

Force behavior differs across PLC manufacturers, variable types, and controller architectures. A force may override the normal logic value, the input value presented to the program, or the output value delivered to the hardware, depending on the platform.

6.1 Common symptoms of an active force

  • A sensor indication does not match the physical condition.
  • A signal remains ON or OFF despite normal field changes.
  • An output behaves differently from the monitored logic.
  • The machine operates unexpectedly after a maintenance intervention.
  • A diagnostic view indicates an active force.
  • The machine works only while a test override remains active.

6.2 Why forces are dangerous

An active force can mask a real failure or defeat the intended control logic.

For example, a forced Part_Present signal may make the PLC believe a part exists when the sensor is not detecting one. The sequence could then continue based on a false condition.

Similarly, forcing an output command may activate a device despite the normal program conditions being false. The resulting movement can cause injury, equipment damage, or product defects.

Never force safety inputs, safety outputs, emergency-stop signals, guard interlocks, or other safety-related functions as a routine troubleshooting shortcut. Any permitted safety validation or test must follow the approved safety procedure and use the appropriate safety-rated methods.

6.3 Force versus normal logic

Normal logic Forced signal or value
Value is determined by normal execution or signal acquisition Supported value may be overridden by the force mechanism
Changes according to inputs, logic, and operating conditions May remain fixed or overridden despite normal changes
Reflects the normal control path Can hide the normal control path's behavior
Expected in normal production operation Requires explicit authorization, tracking, and controlled removal

A monitored variable displaying ON does not necessarily mean the physical sensor is ON. Determine whether the value is forced, substituted, retained, or otherwise overridden.

7. How to Check Active Forces

The exact procedure depends on the PLC software and controller.

7.1 General method

  1. Establish the correct controller connection.
  2. Open the controller's force or override status view.
  3. Review all active and pending forces where the platform exposes them.
  4. Identify the affected signal, variable, channel, or output.
  5. Confirm who applied the force and why, using maintenance records.
  6. Determine the physical and operational consequences of removing it.
  7. Place the machine in the required safe condition.
  8. Remove the force using the approved procedure.
  9. Confirm the force status is cleared.
  10. Verify the real input, normal logic result, and physical output behavior.

Some platforms distinguish between enabling forces globally and individual forces on specific objects. Clearing one force may not remove all forces. Confirm the actual status in the engineering software and controller.

7.2 Important distinction: force versus bypass

A force overrides a supported value through controller or engineering functionality. A bypass may instead involve program logic, a configured maintenance mode, an external jumper, or a separate system mechanism.

Both can alter normal behavior, but they are not interchangeable terms. Investigate the actual implementation rather than assuming that a force list reveals every possible bypass.

8. Timers, Counters, and Latches

Program faults often involve internal control elements that retain or change state according to specific rules.

8.1 Timers

Common timer problems include:

  • Enable condition never becomes true.
  • Timer is reset before completion.
  • Preset value is incorrect.
  • Time unit is misunderstood.
  • Timer done bit is used incorrectly.
  • Timer instance is reused unexpectedly.
  • Scan or task timing differs from assumptions.

For a simplified non-retentive timer:

Timer_Enable = TRUE
       ↓
Elapsed_Time increases
       ↓
Elapsed_Time reaches Preset
       ↓
Timer_Done = TRUE

The actual behavior depends on the timer instruction and platform. Some timers reset when the enabling condition becomes false; others have different retention and timing semantics.

8.2 Counters

Common counter problems include:

  • Input signal remains active for multiple scans.
  • Count logic triggers on the wrong edge.
  • Reset condition activates unexpectedly.
  • Counter preset is wrong.
  • Counter value is retained unexpectedly.
  • Multiple routines modify the same count variable.
  • A communication update causes the count logic to see repeated or missing events.

8.3 Latches and retained states

A latch or set/reset instruction may retain a bit after the initiating condition disappears.

Example:

IF Fault_Detected THEN
    Fault_Latched := TRUE;
END_IF;

IF Reset_Request AND Reset_Conditions_OK THEN
    Fault_Latched := FALSE;
END_IF;

This is illustrative pseudocode, not a complete safety or machine-control implementation.

When a fault remains active after the original condition disappears, check whether the program intentionally latches the fault and what reset conditions are required. Do not clear retained states blindly because they may preserve important machine or process information.

9. Program Data, Tags, and Variable Mapping

A logic problem may originate from incorrect data rather than incorrect instructions.

Common issues include:

  • Wrong tag address.
  • Incorrect alias or mapping.
  • Incorrect data type.
  • Incorrect array index.
  • Wrong structure member.
  • Unexpected retentive value.
  • Incorrect initialization.
  • Incorrect scaling.
  • Data overwritten by another routine.
  • HMI writing to the wrong variable.
  • Network data being mapped to an incorrect PLC tag.

9.1 Example: Incorrect speed reference

Suppose the HMI requests a speed of 1,200 RPM, but the drive receives a reference corresponding to 120 RPM.

Potential causes include:

  • Incorrect scaling.
  • Wrong engineering units.
  • Wrong register or tag.
  • Incorrect numeric data type.
  • Incorrect reference range.
  • Different scaling assumptions between the PLC and drive.

The right approach is to trace the requested value from the HMI through the PLC logic and communication mapping to the drive's interpreted reference.

Do not assume that a displayed value and the value received by the final device use the same units or scale.

10. Operating Modes and Program Paths

Many machines have separate logic paths for:

  • Manual mode.
  • Automatic mode.
  • Setup or maintenance mode.
  • Jog operation.
  • Single-cycle operation.
  • Recovery mode.
  • Homing or initialization.
  • Fault-reset and restart operations.

An output may behave correctly in one mode and remain inactive in another because different conditions govern each path.

Diagnostic approach

  1. Verify the selected operating mode.
  2. Identify the logic path for that mode.
  3. Confirm the expected start conditions.
  4. Check mode-transition logic.
  5. Check whether the mode is inhibited by a fault or permissive.
  6. Verify that the mode change is allowed by the machine's control design.
  7. Test each affected mode using the approved procedure.

Never change a mode or bypass a permissive solely to make the machine move. The permissive may be preventing an unsafe or damaging operation.

11. Distinguish a Program Fault from an I/O Fault

Observation Program-related possibility Hardware or signal possibility
Input LED is ON but PLC logic shows OFF Incorrect address or mapping Input channel or configuration issue
Logic condition is true but output does not activate Output command overwritten or inhibited elsewhere Output module, wiring, power, or actuator fault
Physical sensor changes but program value does not Incorrect tag or input mapping Sensor wiring or input channel fault
Output command is OFF but actuator remains active Another logic path or force may be involved Welded contact, short circuit, or actuator fault
PLC is in RUN but sequence does not advance Missing transition condition or wrong state Missing field feedback or communication data
Behavior changed after a download Changed logic or configuration Hardware configuration mismatch or changed device settings

The table gives investigation directions, not definitive diagnoses. Use the actual circuit, logic, and controller diagnostics to determine the cause.

12. Controlled Program Modification Procedure

A production PLC program must be treated as controlled machine configuration, not as a scratchpad.

Before changing logic

  • Identify the fault and its evidence.
  • Confirm the correct PLC and project.
  • Check whether the current project is the approved version.
  • Save or verify a recoverable backup.
  • Review the proposed change with the responsible person.
  • Identify affected machine functions and interlocks.
  • Assess the risk of online edits or downloading.
  • Establish the required machine state and isolation procedure.
  • Record the existing values and relevant logic.

During the change

  • Modify only the approved logic.
  • Avoid unrelated cleanup or optimization.
  • Confirm the target controller and program.
  • Follow the platform's online-edit or download procedure.
  • Observe any required transition or controller-state restrictions.
  • Keep the change traceable.

After the change

  • Compare the modified logic against the approved intent.
  • Confirm that no unintended forces or overrides remain.
  • Test the affected function.
  • Verify permissives and interlocks.
  • Test normal and fault-recovery behavior.
  • Check adjacent machine operations for side effects.
  • Save the verified project.
  • Record the change, reason, test results, and approval.

A change that fixes one symptom but creates another is not a completed repair. It is just a fault that moved to a different address.

13. Recovery and Verification

After correcting a program-related issue, verify more than the original symptom.

  • Confirm the PLC's operating state.
  • Confirm the intended program version is running.
  • Confirm no unauthorized forces or overrides remain.
  • Verify the original failed condition.
  • Check the related inputs and outputs.
  • Test required permissives and interlocks.
  • Confirm the expected sequence and timing.
  • Check manual and automatic operation where applicable.
  • Verify fault handling and reset behavior.
  • Confirm HMI values and alarms are consistent with the PLC.
  • Check for new diagnostic faults.
  • Document the result and restore the approved machine configuration.

If a program download or controller restart is required, follow the approved procedure. It may reset outputs, alter retained data, interrupt communications, or affect the machine's recovery state.

14. Practical Breakdown Example: Output Will Not Activate

Machine condition: A conveyor does not start even though the PLC CPU is in RUN.

Observations:

  • Start request is present.
  • The HMI shows no active fault.
  • The conveyor output remains OFF.
  • The drive is powered.

Investigation:

  1. Monitor the start request in the PLC.
  2. Trace the logic conditions for the conveyor start command.
  3. Check automatic mode, drive-ready status, fault conditions, and required permissives.
  4. Identify which condition remains false.
  5. Compare the relevant tags with actual device status.
  6. Check whether a force, latch, or recent logic change is affecting the signal.
  7. Confirm the output mapping and drive command path.
  8. Correct the verified fault and test the operation.

Possible root cause: A recent logic edit added a permissive tied to a status tag that is not being updated correctly.

Corrective action: Verify the intended permissive, repair the underlying mapping or configuration, and restore the approved logic behavior. Do not simply delete the permissive to force the conveyor to start.

Verification: Confirm the conveyor starts only when the intended conditions are satisfied, stops as designed, and responds correctly to relevant faults and interlocks.

15. Practical Breakdown Example: Machine Works Only When a Bit Is Forced

Machine condition: A station operates during maintenance testing but stops working when normal logic is restored.

Observations:

  • An internal status bit was forced during earlier troubleshooting.
  • The machine operated while the force was active.
  • After the force was removed, the expected condition remained false.

Investigation:

  1. Identify the forced object and the reason it was forced.
  2. Verify the actual physical input or data source.
  3. Trace the normal logic that should generate the bit.
  4. Check whether the upstream condition is missing, incorrectly mapped, or blocked.
  5. Review recent changes and maintenance records.
  6. Correct the actual fault instead of reinstating the force.
  7. Verify the bit changes naturally under the correct operating conditions.
  8. Confirm that all forces are cleared and the machine operates normally.

Possible root cause: The forced bit had been masking a failed sensor or incorrect signal mapping.

Verification: The real signal changes correctly, the program responds without overrides, and the machine passes the approved functional test.

16. Common Mistakes During PLC Program Troubleshooting

  • Changing logic before identifying the first incorrect condition.
  • Assuming that RUN status means the program is healthy.
  • Downloading a project without confirming the target controller.
  • Treating every program difference as an error.
  • Removing a permissive without understanding its purpose.
  • Leaving forces active after testing.
  • Forcing a signal to hide a failed sensor or communication link.
  • Resetting latches without investigating why they activated.
  • Changing timer presets to compensate for a mechanical or sensor fault.
  • Editing unrelated logic during a breakdown.
  • Failing to save the verified program after a repair.
  • Testing only the immediate symptom and ignoring adjacent operations.
  • Assuming the online project and approved backup are identical.
  • Ignoring safety validation when changes affect safety-related functions.

18. Interview Questions and Answers

Q1. Why can a PLC be in RUN while the machine does not operate?

RUN indicates that the controller is executing its program, not that every machine condition is satisfied. The cause may be a missing permissive, incorrect logic, unavailable input, active fault, force, or downstream device problem.

Q2. What is an online edit?

An online edit is a supported method of modifying program logic while connected to a controller, potentially without a full offline download. Its availability and execution behavior depend on the PLC platform and the type of change.

Q3. What is a forced bit?

A forced bit is a supported signal or variable whose normal value is overridden by an engineering or controller force mechanism. The exact point of override depends on the platform and object type.

Q4. Why are active forces dangerous?

They can conceal failed signals or override normal logic behavior, potentially causing unexpected machine operation. Forces must be authorized, tracked, and removed according to the approved procedure.

Q5. How do you investigate a machine that stops at the same sequence step every time?

Monitor the active sequence state and transition conditions. Identify the first condition that remains false, then verify the associated physical signal, communication data, timer, counter, and program logic.

Q6. How do you determine whether a fault is in the PLC program or field hardware?

Compare the physical signal, input status, program variable, logic result, output command, and physical output response. The first point where actual behavior differs from the expected signal path narrows the investigation.

Q7. Why is program comparison useful?

It identifies differences between program versions or between the online controller and an offline project. The differences must then be evaluated against approved changes and machine requirements.

Q8. What should be done after a logic change?

Verify the change, confirm that no unintended forces remain, test the affected operation and relevant interlocks, check adjacent functions, save the approved program, and document the change and test results.

Q9. Why should a permissive not be removed just to make a machine run?

The permissive may protect equipment, product quality, sequence integrity, or safe operation. Its purpose and dependencies must be understood before any approved modification is considered.

Q10. What is the difference between a latched bit and a forced bit?

A latched bit retains its state according to the program's set/reset or retention logic. A forced bit is overridden by a force mechanism that takes precedence over normal value determination according to the platform's behavior.

19. Completion Checklist

  • Explain the PLC scan cycle and trace the signal path.
  • Diagnose a machine that fails to start despite PLC RUN status.
  • Monitor live logic and identify the first unexpected condition.
  • Investigate recent online edits and program changes.
  • Compare the running program with an approved project.
  • Identify and safely remove authorized test forces.
  • Distinguish forces, latches, and bypasses.
  • Diagnose timer, counter, and retained-state problems.
  • Verify tag mapping and data interpretation.
  • Distinguish program faults from I/O and communication faults.
  • Follow controlled program-change and backup procedures.
  • Verify the repaired operation and relevant interlocks.
  • Document the root cause, changes, and test evidence.
