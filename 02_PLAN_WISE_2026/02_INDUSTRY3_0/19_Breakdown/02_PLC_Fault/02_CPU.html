1. Definition and Purpose

The PLC Central Processing Unit (CPU) executes the control program, processes input data, updates outputs, manages communication, and monitors the controller's operating condition.

When a PLC-related machine breakdown occurs, the CPU's operating mode, status indicators, diagnostic information, and memory condition provide important evidence about the fault.

The objective is to determine whether the CPU is operating normally, has stopped executing the program, has entered a fault state, has lost required configuration or program data, or is experiencing a hardware or firmware problem.

This topic covers:

  • PLC operating modes and transitions.
  • CPU status and fault LEDs.
  • Diagnostic buffers and fault codes.
  • Program execution and scan-cycle behavior.
  • Memory types, retention, and program integrity.
  • Watchdog and execution faults.
  • Communication and configuration faults that appear to be CPU problems.
  • Safe recovery, program backup, and post-repair verification.

2. Understand the PLC CPU's Role

A PLC CPU performs several major functions.

  • Reads input states from local or remote I/O.
  • Executes logic, function blocks, instructions, and sequence operations.
  • Updates output commands according to the program and configured behavior.
  • Handles communication with HMIs, drives, remote I/O, and other controllers.
  • Monitors system diagnostics, execution timing, and certain hardware conditions.
  • Maintains program, configuration, and data according to the controller's memory architecture.

A simplified execution model is:

Power-Up and Startup Checks
    ↓
Load or Validate Required Configuration
    ↓
Initialize the Controller
    ↓
Read or Update Input Data
    ↓
Execute Control Program
    ↓
Update Output Data
    ↓
Perform System and Communication Tasks
    ↓
Repeat According to the Controller Architecture

This is a conceptual model. Some PLCs use cyclic scans, while others support scheduled tasks, event-driven execution, asynchronous communications, process-image updates, and other execution mechanisms.

A CPU may be powered and communicating while its program is not executing normally. Therefore, power ON, communication established, and CPU running are three different conditions.

3. PLC Operating Modes

Operating modes determine whether the controller executes its application program, permits modifications, or remains in a diagnostic or stopped condition.

Exact mode names and behavior depend on the manufacturer, CPU model, firmware, and project configuration.

Mode or state General meaning Maintenance consideration
RUN The application executes according to the controller's configured execution model Confirm that the relevant tasks and program sections are executing without faults
STOP Normal application execution is stopped Outputs may change state according to configuration and hardware behavior
PROGRAM Common programming or editing state on some PLC platforms Do not assume outputs or sequences behave as they do in RUN
REMOTE RUN Controller can operate in RUN through an engineering tool or authorized remote command Confirm mode ownership and authorization before making changes
REMOTE STOP Controller has been commanded to stop through a supported interface Identify why it stopped and who or what issued the command
STARTUP Controller is initializing after power-up or a restart Startup may be delayed by configuration, hardware, or program-related issues
FAULT A detected condition prevents normal execution or affects controller operation Read diagnostics before attempting recovery
MAINTENANCE or diagnostic state A manufacturer-specific state associated with service or recovery Follow the exact CPU documentation

Some platforms do not use all these mode names. For example, Siemens commonly uses RUN and STOP, Rockwell Automation uses controller modes such as Run and Program, and Mitsubishi terminology depends on the PLC family and engineering environment.

3.1 Why a PLC enters STOP

Possible reasons include:

  • A serious program execution error.
  • A configured startup or hardware diagnostic failure.
  • A watchdog timeout.
  • Invalid or incompatible configuration.
  • A memory or program integrity problem.
  • An explicit STOP command.
  • A mode change initiated by an authorized programming device.
  • A controller-specific fault requiring recovery.

Do not assume every STOP condition is a hardware failure. A PLC may be healthy but stopped because of an engineering command, commissioning procedure, or configured operating policy.

3.2 RUN mode does not guarantee correct machine operation

A PLC can remain in RUN while the machine malfunctions because of:

  • Incorrect sequence conditions.
  • Sensor faults.
  • Missing field power.
  • I/O module faults.
  • Communication loss to a remote device.
  • A drive or servo fault.
  • Incorrect setpoints or configuration.
  • A permissive or interlock that remains unsatisfied.
  • A logic error that does not cause a CPU-level fault.

If the CPU is in RUN, continue investigating the program, I/O, communications, field devices, and machine conditions instead of replacing the CPU without evidence.

4. CPU Status LEDs

Status LEDs provide a fast initial indication of controller condition. They must be interpreted using the documentation for the exact hardware model.

Common indicators include:

LED or indicator General purpose What to investigate
POWER or PWR Indicates a power-related condition Supply voltage, power module, backplane, or device-specific power status
RUN Indicates execution or operating state Controller mode and whether the application is executing
STOP or PROG Indicates a stopped or programming state on supported models Mode selection, engineering command, and diagnostic information
ERROR or ERR Indicates a detected error on supported models Fault code, diagnostic buffer, configuration, or program error
FAULT Indicates a controller fault on supported models Fault type, severity, and required recovery procedure
SF or system fault Indicates a system-level diagnostic condition on certain platforms Hardware diagnostics, configuration, module status, and diagnostic buffer
BF or bus fault Indicates a bus or communication-related condition on certain platforms Network topology, bus configuration, remote I/O, and device status
MAINT or maintenance Indicates a maintenance-related condition on supported hardware Manufacturer-specific maintenance information
LINK or ACT Indicates network link or traffic activity Physical network connection and communication diagnostics

The names and meanings are not universal. A red LED on one device may indicate a specific fault, while another model may use the same color for a different condition.

4.1 Steady versus flashing indications

A steady LED may indicate a persistent state or fault, while flashing may indicate startup, a warning, communication activity, or a particular fault code.

The meaning depends on:

  • LED name.
  • Color.
  • Steady or flashing state.
  • Flashing pattern and frequency.
  • CPU model.
  • Firmware version.
  • Other simultaneously active indicators.

Record the exact indication before resetting the PLC. A restart may remove temporary evidence that would otherwise help identify the original fault.

5. Diagnostic Buffer and Fault Information

The diagnostic buffer or controller log stores events and diagnostic information generated by the CPU and associated system components.

Depending on the platform, it may contain:

  • Startup and shutdown events.
  • CPU mode changes.
  • Module faults.
  • Hardware configuration errors.
  • Communication errors.
  • Program execution faults.
  • Watchdog events.
  • Memory or integrity-related errors.
  • Time-stamped diagnostic messages.
  • Information about the affected instruction, task, or module.

5.1 Why diagnostic history matters

Suppose a machine stops and the CPU is found in STOP. Restarting it immediately may restore production, but it can also erase or obscure important evidence.

A better approach is to capture:

  1. The current CPU mode.
  2. All relevant LED states.
  3. The diagnostic buffer or fault log.
  4. The exact fault code and description.
  5. The time of the first fault.
  6. Any preceding warnings or events.
  7. The machine condition when the fault occurred.
  8. Recent program, hardware, or wiring changes.

The first recorded event may be more important than the final alarm. For example, a remote I/O communication fault may appear before the sequence timeout that ultimately stops the machine.

5.2 Fault, warning, and alarm are different

  • Fault: A detected condition that may prevent normal operation or affect a component.
  • Warning: A condition requiring attention that may not stop execution.
  • Alarm: A message generated by a controller, HMI, drive, or supervisory system to communicate a condition.

An HMI alarm does not automatically identify the underlying root cause. The message may describe the consequence of a different fault.

6. Program Execution and Scan-Cycle Problems

Many PLCs repeatedly process inputs, execute application logic, and update outputs. However, task scheduling and I/O updates vary by platform.

6.1 Scan time

Scan time is the time associated with a controller's execution cycle or a particular program task, depending on the platform.

It can be affected by:

  • Program size and complexity.
  • Instruction execution time.
  • Communication and system overhead.
  • Interrupts and higher-priority tasks.
  • Data processing and indirect addressing.
  • Diagnostic operations.
  • Task configuration.
  • Controller loading.

A longer scan time is not automatically a fault. The key is whether execution remains within the applicable timing requirements and whether deadlines or watchdog limits are exceeded.

6.2 Watchdog timer

A watchdog monitors whether the controller or a program task completes within a configured time limit.

If execution exceeds the permitted time, the controller may generate a fault, stop a task, or take another configured action.

Possible causes include:

  • Unexpectedly long loops.
  • Excessive program execution.
  • Incorrect task configuration.
  • Recursion or repetitive execution in systems that support it.
  • Unexpected instruction behavior.
  • High-priority task interference.
  • A programming change that increases execution time.

6.3 Watchdog troubleshooting

  1. Record the exact watchdog or task fault.
  2. Identify the affected task and execution context.
  3. Review recent logic changes.
  4. Examine scan-time or task-time diagnostics.
  5. Identify loops, repetitive processing, or computationally expensive routines.
  6. Compare execution time with the controller's documented limits.
  7. Correct the verified cause.
  8. Test the program under representative operating conditions.

Do not simply increase the watchdog setting to suppress a fault. The configured limit may protect the process from unsafe or unacceptable control delays.

7. PLC Memory Fundamentals

PLC memory holds the application program, hardware configuration, working data, and other information required for controller operation.

The actual architecture depends on the PLC family.

7.1 Common memory categories

Memory type Typical contents Maintenance significance
Program memory Application logic, functions, and program organization Program corruption, missing code, or an incorrect download may affect operation
Working memory Data used during program execution Volatile data may be lost when power is removed, depending on the platform
Retentive memory Data configured to survive certain restarts or power losses Retention behavior must be confirmed from the controller configuration
Nonvolatile memory Data stored so it can persist without continuous power May store programs, configuration, or selected data depending on the hardware
Load memory Stored program and configuration data on supported platforms May be located on internal or removable storage
Process image or I/O data Cached or organized representation of input and output states Stale or unexpected values may result from I/O updates, configuration, or communication issues
Diagnostic memory Fault history and diagnostic information Valuable for troubleshooting and root-cause analysis
Clock and system data Time, counters, status information, or system variables Incorrect settings may affect timestamps, scheduling, or program behavior

These categories are conceptual and do not map one-to-one onto every manufacturer's physical memory architecture.

7.2 Volatile and nonvolatile memory

Volatile memory generally requires power to retain its contents unless the platform provides an additional retention mechanism.

Nonvolatile memory retains stored data without continuous power, subject to the device's storage technology and specifications.

A PLC may use a combination of internal memory, removable memory cards, battery-backed retention, capacitor-backed retention, or other mechanisms.

Never assume that all PLC data is retained after power loss.

7.3 Retentive versus non-retentive data

Retentive data may include selected counters, recipe values, accumulated production counts, or machine state variables, depending on the application.

Non-retentive data may include temporary sequence flags, intermediate calculation values, or startup-initialized variables.

The actual behavior depends on the program, controller, variable configuration, and restart type.

Before replacing a CPU, downloading a program, or performing a memory reset, establish which data must be preserved.

8. Memory-Related Faults

Memory-related issues can cause startup errors, program integrity faults, missing configuration, or unexpected machine behavior.

Potential causes include:

  • Corrupted or invalid program data.
  • Incompatible project or firmware version.
  • Incomplete or incorrect download.
  • Unsupported hardware configuration.
  • Missing or defective memory card where required.
  • Failed retention battery on hardware that uses one.
  • Insufficient memory capacity.
  • Invalid retentive-data configuration.
  • Hardware deterioration.
  • Incorrect program or configuration loaded during maintenance.

8.1 Symptoms to investigate

  • CPU fails to complete startup.
  • Program cannot be loaded or verified.
  • Controller reports a memory or integrity error.
  • A memory card is not recognized.
  • Retentive values are unexpectedly lost.
  • Controller configuration differs from the approved project.
  • A recent download coincides with the first failure.
  • The controller repeatedly enters a fault state.

Do not immediately clear memory or reload a program. First capture the error and determine whether the original program and required data are available for recovery.

9. Program Backup and Integrity

A reliable PLC backup is a core maintenance control, not an optional administrative task.

A useful backup strategy should preserve the approved application, relevant configuration, and recovery information according to site policy.

9.1 What to preserve

  • Correct PLC project file.
  • Hardware configuration.
  • CPU and I/O configuration.
  • Program blocks and supporting libraries.
  • Relevant device configurations.
  • Firmware and engineering-software compatibility information.
  • Retentive-data handling requirements.
  • Approved communication settings, stored securely.
  • Version history and change records.
  • Date and result of the last verified backup.

Do not store passwords or other secrets in ordinary maintenance notes. Use approved credential-management procedures.

9.2 Source project versus upload

A project uploaded from a PLC is not always equivalent to the original engineering project.

Depending on the platform and access rights, an upload may omit comments, symbolic information, source files, libraries, or other engineering metadata. Some controllers may not permit a complete source recovery from the running hardware.

For this reason, preserve the approved engineering project and verify that it is usable for recovery.

9.3 Before downloading a project

  • Confirm the target PLC identity and model.
  • Confirm the correct machine and project version.
  • Check firmware and hardware compatibility.
  • Preserve the current program and diagnostic evidence.
  • Assess the machine's safe state and required downtime.
  • Understand whether the download will stop execution or change outputs.
  • Obtain the required authorization.
  • Confirm the backup and rollback plan.

A wrong download can create a second breakdown while attempting to repair the first one.

10. CPU Fault Troubleshooting Workflow

Step 1: Make the machine safe

Determine whether the machine must be stopped or isolated. Follow the site's safety procedures, especially where unexpected movement or loss of control could create a hazard.

Step 2: Observe without disturbing evidence

Record the CPU mode, LEDs, alarms, and fault timestamps. Avoid a power cycle or reset before collecting the available diagnostics unless immediate action is required for safety.

Step 3: Confirm the supply

Check the CPU's required supply and relevant power-module status. A CPU that appears faulty may simply be receiving an incorrect or unstable supply.

Step 4: Read the diagnostics

Use the supported engineering tool or controller interface to read fault codes, diagnostic buffers, task status, and module diagnostics.

Step 5: Identify the fault category

Determine whether the evidence points toward:

  • Power or hardware.
  • CPU operating mode.
  • Program execution.
  • Memory or configuration.
  • I/O or backplane.
  • Communication.
  • External field equipment.
  • An explicit operator or engineering command.

Step 6: Compare with recent changes

Review program downloads, firmware changes, module replacement, wiring work, power interruptions, and configuration modifications.

Step 7: Correct the verified cause

Apply the approved corrective action. Avoid changing multiple unrelated variables at once because this makes the actual cause difficult to establish.

Step 8: Recover according to the fault procedure

Use the manufacturer's recovery procedure for the exact CPU and fault. Acknowledging a fault, resetting a controller, changing mode, and cycling power are different actions with different consequences.

Step 9: Verify operation

Confirm the controller mode, diagnostic state, I/O operation, communications, sequence behavior, and required machine interlocks.

Step 10: Document the outcome

Record the original fault, evidence, root cause, corrective action, program or configuration changes, and verification results.

11. Platform-Specific Considerations

Different PLC families provide different operating modes, LED patterns, memory arrangements, and diagnostic tools.

PLC platform Engineering environment Areas to investigate
Siemens S7-1500 TIA Portal CPU diagnostics, diagnostic buffer, operating mode, module status, startup behavior, and project compatibility
Siemens S7-1200 TIA Portal CPU status, diagnostic information, program and hardware configuration, and supported memory-card behavior
Rockwell CompactLogix Studio 5000 Logix Designer Controller mode, major and minor faults, controller properties, task diagnostics, and project compatibility
Rockwell ControlLogix Studio 5000 Logix Designer Controller fault information, chassis and module status, task execution, and redundancy-related conditions where applicable
Mitsubishi FX family GX Works2 or GX Works3, depending on model CPU status, error codes, program execution, memory configuration, and supported diagnostic functions
Mitsubishi iQ-R GX Works3 CPU diagnostics, module diagnostics, program execution, system configuration, and fault history

Exact functions and procedures depend on the model, firmware, software version, and installed modules. Do not apply an LED interpretation or recovery sequence from a different CPU merely because it belongs to the same manufacturer.

12. Practical Breakdown Example: PLC in STOP

Machine condition: An automated assembly station stops, and the HMI displays a sequence fault.

Initial observations:

  • PLC CPU is powered.
  • CPU is in STOP.
  • A system error indicator is active.
  • Several downstream outputs are inactive.
  • The HMI records a sequence timeout.

Incorrect response: Immediately switch the PLC to RUN and assume the problem is solved if the machine restarts.

Correct investigation:

  1. Record the CPU model, mode, and LED indications.
  2. Capture the diagnostic buffer and exact fault description.
  3. Check whether a recent download or hardware change occurred.
  4. Determine whether the first fault is a CPU execution fault, configuration fault, module fault, or another condition.
  5. Follow the documented diagnostic procedure for that fault.
  6. Correct the verified cause.
  7. Return the CPU to service only through the authorized procedure.
  8. Verify the required inputs, outputs, interlocks, communications, and machine sequence.
  9. Record the root cause and the verification evidence.

Possible conclusion: If diagnostics identify an unsupported or inconsistent hardware configuration following a module replacement, the issue may be configuration-related rather than a defective CPU. The appropriate correction is to restore a compatible, approved configuration and verify the system.

The actual cause must come from the recorded diagnostic evidence, not from the symptom alone.

13. Practical Breakdown Example: Retentive Data Lost

Machine condition: After a power interruption, a production counter or machine state value returns to an unexpected value.

Possible causes:

  • The variable was configured as non-retentive.
  • The restart behavior initializes the value.
  • The program contains startup logic that resets it.
  • Retention hardware or settings have failed.
  • The wrong program or configuration was loaded.
  • The application stores the value externally and the external data was unavailable.

Diagnostic procedure:

  1. Identify the affected variable and its intended behavior.
  2. Review the program and variable retention settings.
  3. Check the controller's documented behavior for the type of restart that occurred.
  4. Inspect relevant startup logic and initialization routines.
  5. Review diagnostic history and recent changes.
  6. Verify whether an approved external record or backup contains the required value.
  7. Correct the configuration or logic through the approved change process.
  8. Test power-loss and restart behavior under a controlled, authorized procedure.

Do not change a production counter or sequence-state value manually without understanding the machine's process requirements. An apparently harmless data correction can create a tracking or sequence-integrity problem.

14. Resetting and Restarting the CPU

A reset is not a universal fix. PLC platforms provide different reset types, including fault acknowledgement, controller restart, memory reset, and restoration procedures.

Before taking action, determine:

  • Whether the machine is in a safe state.
  • Whether the diagnostic evidence has been captured.
  • Whether the program and configuration are backed up.
  • Whether the fault requires acknowledgement or a more substantial recovery.
  • Whether retentive data could be affected.
  • Whether outputs or motion devices may behave differently after restart.
  • Whether authorization is required.
  • Whether a formal restart checklist applies.

Never perform a memory reset simply to clear an error. Depending on the PLC, this may erase program or configuration data and make the machine more difficult to recover.

After a reset or restart, verify the controller's state and machine behavior rather than treating a cleared LED as proof of a successful repair.

15. Common Troubleshooting Mistakes

  • Treating every STOP state as a failed CPU.
  • Ignoring the exact fault code and diagnostic history.
  • Assuming RUN means every program task is operating correctly.
  • Restarting before recording the original fault.
  • Confusing an HMI sequence timeout with the root cause.
  • Reloading a program without confirming the target PLC and project version.
  • Assuming an uploaded program is a complete engineering backup.
  • Ignoring the distinction between retentive and non-retentive variables.
  • Performing a memory reset without understanding its consequences.
  • Increasing a watchdog limit without investigating excessive execution time.
  • Changing multiple program and hardware parameters simultaneously.
  • Returning the machine to production without testing affected interlocks and sequences.
  • Replacing the CPU without verifying supply, backplane, configuration, and module conditions.

17. Interview Questions and Answers

Q1. What is the function of a PLC CPU?

It executes the control application, processes I/O data, manages supported communication functions, and monitors controller operation and diagnostics.

Q2. What is the difference between RUN and STOP?

RUN indicates that the controller is in its running mode and executes the application according to its architecture. STOP indicates that normal application execution is stopped. The precise behavior depends on the PLC platform.

Q3. Why should the diagnostic buffer be checked before resetting the CPU?

It preserves information about the fault, its timing, and potentially preceding events. Resetting first may remove or obscure evidence needed to identify the root cause.

Q4. What is a watchdog fault?

It is a fault associated with execution exceeding a configured time limit or failing to meet a monitored timing requirement. Causes may include excessive execution time, task configuration, or program logic problems.

Q5. What is retentive memory?

It is memory or data configured to retain its contents across specified operating events, such as certain power losses or restarts. Retention behavior depends on the PLC hardware and configuration.

Q6. Can a PLC be in RUN and still have a machine breakdown?

Yes. The cause may be incorrect logic, unsatisfied interlocks, missing I/O signals, remote I/O communication loss, field power failure, or a drive or actuator fault.

Q7. What should be checked before downloading a PLC program?

Confirm the target controller, project version, hardware configuration, firmware compatibility, backup, machine-safe condition, authorization, and recovery plan.

Q8. Why is an uploaded PLC project not always a complete backup?

The upload may not contain the original source files, comments, symbolic information, libraries, or engineering metadata needed to reproduce the approved project fully.

Q9. What is the correct response to a CPU fault LED?

Record the exact indication, obtain the diagnostic information for the specific CPU model, identify the fault category, correct the verified cause, and follow the approved recovery procedure.

Q10. When should a CPU be replaced?

When diagnostic evidence and approved testing establish a hardware failure or an unrecoverable condition attributable to the CPU, after ruling out relevant supply, configuration, firmware, backplane, and connected-module problems.

18. Completion Criteria

  • Explain the purpose of the PLC CPU.
  • Distinguish RUN, STOP, startup, and fault states.
  • Interpret CPU LEDs using the correct hardware documentation.
  • Read and preserve diagnostic-buffer information.
  • Explain scan time and watchdog behavior.
  • Distinguish program memory, working memory, retentive data, and nonvolatile storage.
  • Explain why a PLC may stop after a configuration or program fault.
  • Understand the risks of reset, restart, and program download.
  • Verify backups and project compatibility before recovery.
  • Diagnose a CPU fault systematically instead of replacing parts by guesswork.
  • Verify I/O, communications, interlocks, and machine operation after recovery.
  • Record the original fault, verified root cause, corrective action, and test results.
