1. Purpose of Link-Level Troubleshooting

After checking cables and connectors, the next step is to verify whether Ethernet interfaces establish a link correctly and negotiate compatible communication settings.

In industrial automation, a PLC, remote I/O rack, HMI, CNC, robot controller, VFD, or industrial switch may have a physically connected cable but still experience communication problems because of:

  • Link not established.
  • Incorrect or unexpected link speed.
  • Speed or duplex mismatch.
  • Failed auto-negotiation.
  • Excessive interface errors.
  • Unstable link caused by a marginal cable or port.
  • Faulty Ethernet interface or transceiver.
  • Incorrect switch-port configuration.
  • Compatibility issues between older and newer network devices.

Core diagnostic principle: A link light confirms only a limited part of the communication path. It does not prove that data is flowing correctly, that the devices are using the expected speed, or that the application is communicating successfully.

2. Ethernet Link Establishment

When two Ethernet interfaces are connected, they must establish a compatible physical connection. Depending on the interface and Ethernet technology, this can involve signal detection, link establishment, and auto-negotiation.

PLC Ethernet Port
       ↓
Cable and Connectors
       ↓
Switch Ethernet Port
       ↓
Physical Link Established
       ↓
Speed / Duplex Negotiation, Where Applicable
       ↓
Ethernet Frames Exchanged
       ↓
IP Communication
       ↓
Industrial Application Communication

A failure at one stage can affect later stages. For example, an established Ethernet link does not guarantee that IP addresses are correct or that a PLC can exchange data with a remote device.

4. Understanding Link LEDs

Link LEDs are useful for quick troubleshooting, but their meaning varies by manufacturer and device model.

Common indications include:

  • Link established: A physical connection has been detected.
  • Activity: Frames are being transmitted or received.
  • Speed indication: The LED colour or combination may identify a supported link rate.
  • Fault indication: Some industrial switches provide separate diagnostic LEDs for port or device faults.

Never assume that green always means 1 Gbit/s or amber always means 100 Mbit/s. Check the specific device's documentation.

4.1 Typical observations

LED observation Possible interpretation Next check
Link LED off No established link, disabled port, or interface fault Check port enablement, cable, and both interfaces
Link LED steady Link established Verify speed, counters, and communication
Activity LED flashing Traffic is being exchanged Confirm expected traffic and application response
LED changes repeatedly Link flap or unstable physical connection Check cable, connector, power, and interface logs
LED indicates a lower speed than expected Negotiation, cable, or device capability issue Check both endpoints and cable requirements
LEDs appear normal but PLC communication fails Physical link exists, but higher-layer communication may fail Continue with IP, protocol, and application diagnostics

A port can have a valid link while receiving no useful application data. A flashing activity LED may also represent unrelated broadcast traffic rather than successful communication with the intended PLC or device.

5. Ethernet Link Speed

Link speed is the nominal Ethernet data rate established between directly connected interfaces.

Common Ethernet speeds include:

Speed Common notation Typical applications
10 Mbit/s 10BASE-T Legacy Ethernet devices
100 Mbit/s 100BASE-TX Many PLCs, HMIs, drives, and industrial devices
1 Gbit/s 1000BASE-T Engineering PCs, servers, switches, and capable industrial devices
2.5 Gbit/s 2.5GBASE-T Supported higher-performance copper networks
10 Gbit/s 10GBASE-T or applicable optical Ethernet standard Backbone, server, and higher-bandwidth networks

The supported speed depends on the device, PHY, cable, connector, transceiver, and applicable Ethernet standard.

5.1 Why link speed matters

A device designed for 100 Mbit/s may be operating correctly at 100 Mbit/s even when connected to a 1 Gbit/s switch. The switch port can negotiate a compatible speed if both interfaces support the necessary negotiation behaviour.

The important question is not whether every device runs at the highest available speed. It is whether the negotiated speed matches the device's capabilities and the intended network design.

5.2 Unexpected low speed

Possible causes include:

  • One endpoint supports only a lower speed.
  • One interface is manually configured to a lower rate.
  • Auto-negotiation does not complete as intended.
  • Cable or termination problems prevent higher-speed operation.
  • An unsuitable cable or transceiver is installed.
  • A damaged port or PHY limits operation.
  • The switch port has a configured speed restriction.

Troubleshoot the actual capability and negotiation state before replacing hardware.

6. Duplex: Half Duplex and Full Duplex

Duplex defines how an Ethernet interface transmits and receives data.

6.1 Half duplex

In half-duplex operation, a station cannot transmit and receive simultaneously on the shared medium. Traditional shared Ethernet used collision detection and backoff mechanisms.

Half duplex is uncommon in modern switched industrial Ethernet networks, but it may appear with legacy equipment or particular interface configurations.

6.2 Full duplex

In full-duplex operation, an interface can transmit and receive simultaneously. Modern switched Ethernet links commonly operate in full duplex.

Full duplex eliminates Ethernet collisions on that point-to-point link because both ends can transmit simultaneously without competing for the same shared transmission medium.

6.3 Comparison

Feature Half duplex Full duplex
Simultaneous transmit and receive No Yes
Traditional collision handling Required for applicable shared Ethernet Not used for normal operation on the full-duplex point-to-point link
Typical modern switched Ethernet use Uncommon Standard practice
Duplex mismatch risk Can cause errors when paired with full duplex Can cause errors when paired with half duplex
Troubleshooting focus Legacy or specifically supported configuration Expected mode for most modern switched links

7. Auto-Negotiation

Auto-negotiation allows connected Ethernet interfaces to exchange supported capabilities and select compatible operating parameters. Depending on the technology, these can include speed and duplex, along with other capabilities.

7.1 Normal operation

When both endpoints support auto-negotiation and are configured appropriately, they should establish a compatible link automatically.

Endpoint A
Supported Speeds / Duplex
          ↓
     Auto-Negotiation
          ↕
     Auto-Negotiation
          ↓
Endpoint B
Supported Speeds / Duplex
          ↓
Compatible Link Settings

7.2 Common auto-negotiation problems

  • One endpoint uses auto-negotiation while the other is forced to a particular setting.
  • An older device has limited negotiation support.
  • A switch port has an incorrect configuration.
  • The cable has faults that affect negotiation or higher-speed signalling.
  • A device has a firmware or PHY compatibility issue.
  • A transceiver does not support the expected negotiation or link mode.

Important distinction: Speed and duplex negotiation are related but not identical. Certain interfaces may establish a link at a forced speed while duplex information is not exchanged as expected. This can produce a duplex mismatch even though the link LED is on.

7.3 Preferred configuration

For modern Ethernet equipment, use auto-negotiation at both ends when supported and recommended by the manufacturer.

Only use forced speed or duplex when the device documentation, network design, or a controlled troubleshooting procedure specifically requires it. If one endpoint is forced, configure the other endpoint according to the documented requirements for that link.

8. Duplex Mismatch

A duplex mismatch occurs when two connected interfaces operate using different duplex modes.

A classic example is:

  • Switch port: forced to 100 Mbit/s full duplex.
  • Device port: auto-negotiation enabled and operating at 100 Mbit/s half duplex because it cannot determine the partner's duplex setting.

The physical link may remain up, but communication can suffer from collisions, late collisions, FCS errors, retransmissions at higher layers, and poor throughput.

8.1 Typical symptoms

  • Link light remains on.
  • Communication works during light traffic.
  • Errors increase when traffic rises.
  • Response times become inconsistent.
  • Packet loss or timeouts occur.
  • Switch counters report collisions or late collisions on applicable interfaces.
  • One endpoint reports receive errors or discards.

8.2 Troubleshooting procedure

  1. Check speed and duplex at both ends of the link.
  2. Confirm whether either endpoint is manually configured.
  3. Review interface counters and event logs.
  4. Verify the recommended negotiation mode for both devices.
  5. Correct the mismatch using the manufacturer's supported configuration.
  6. Clear or record the original counters, then monitor new counter increments.
  7. Test communication under normal operating load.

Do not assume every CRC or dropped-packet count indicates a duplex mismatch. Damaged cables, noise, congestion, and hardware faults can produce similar symptoms.

9. Link Flapping

Link flapping means that an interface repeatedly changes between link up and link down.

Common causes

  • Broken conductor or damaged cable.
  • Loose connector.
  • Damaged port contacts.
  • Cable strain or movement.
  • Poor termination.
  • Power instability at a connected device.
  • Faulty transceiver.
  • Switch or endpoint rebooting.
  • Port-security or configuration behaviour on some equipment.
  • Severe environmental conditions affecting the physical connection.

Diagnostic method

  1. Record the time and frequency of each link event.
  2. Identify both endpoints and the intermediate switch port.
  3. Check logs for link-up and link-down events.
  4. Inspect cable routes and connector strain points.
  5. Check whether the problem correlates with machine movement or device restart.
  6. Test using a known-good compatible cable.
  7. If necessary, test another suitable switch port according to the network maintenance procedure.
  8. Verify stability over the operating period that previously produced the fault.

Repeatedly resetting the switch may temporarily restore the connection while concealing the underlying problem. Record the event evidence before resetting equipment.

10. Ethernet Error Counters

Switches and network interfaces maintain counters that help identify link quality problems. Counter names and availability vary by vendor.

Counter Meaning Possible causes
CRC / FCS errors Received frames fail integrity checking Cable impairment, interference, bad connectors, faulty interface
Alignment errors Received frames do not align correctly according to the applicable interface reporting Physical corruption or interface-related problems
Runts Frames smaller than the expected minimum Ethernet frame size, subject to counter definition Collisions in legacy half-duplex operation or malformed traffic
Giants Frames larger than the expected limit, subject to interface configuration Oversized frames, configuration mismatch, or abnormal traffic
Late collisions Collisions detected after the normal collision window Duplex mismatch or legacy shared-medium problems
Input errors Aggregate receive-side errors May include CRC, alignment, or other error types
Output drops Transmit frames discarded, often because of congestion or resource limits Queue congestion, bandwidth demand, or device resource limits
Interface resets Interface reset events Link instability, device fault, or software issue
Link transitions Recorded changes in link state Cable, port, power, or endpoint stability problems

10.1 How to use counters correctly

  • Record the counter values before testing.
  • Observe whether counters increase during the fault.
  • Correlate errors with machine events and traffic conditions.
  • Check both endpoints where information is available.
  • Distinguish cumulative historical errors from newly occurring errors.
  • Investigate the counter definition in the device documentation.

A large counter does not necessarily indicate a current fault. It may represent errors accumulated over months. Counter growth during a controlled observation period is generally more useful than the absolute value alone.

11. Link Speed, Duplex and Cable Faults

Cable problems can affect link negotiation and communication quality in different ways.

Observation Possible explanation Diagnostic direction
Link is down Disconnection, failed interface, incompatible medium, or disabled port Check cable, port, and endpoint status
Link establishes at lower speed Capability limitation, forced setting, or transmission problem Verify supported speed and cable performance
Link is up but CRC errors rise Cable impairment, EMI, connector fault, or interface problem Inspect and test the physical link
Communication fails under load Duplex mismatch, congestion, errors, or application limitations Compare duplex, counters, and traffic
Link drops when the cable moves Intermittent conductor or connector fault Inspect and test moving sections
Link is stable but application times out IP, transport, protocol, device, or application issue Continue above the physical layer
One endpoint shows many errors Fault may be local to that receiver or its incoming signal path Check the incoming cable, partner transmitter, and interface
Link speed varies after reconnection Auto-negotiation, port configuration, or marginal physical path Check both endpoints and the cable

12. Step-by-Step Troubleshooting in an Industrial Network

Step 1: Identify the link

Record:

  • Device name and network port.
  • Connected switch and port number.
  • Cable type and approximate length.
  • Expected speed and duplex.
  • Current link status.
  • Time of the fault.
  • Machine condition when the fault occurred.

Step 2: Observe the link LEDs

Check the documented LED meaning on both endpoints. Determine whether the link is down, stable, or repeatedly changing state.

Step 3: Verify speed and duplex

Read the actual interface settings rather than relying on the design specification alone. Compare both endpoints.

Step 4: Inspect counters

Record CRC/FCS errors, drops, link transitions, interface resets, and other relevant counters. Monitor for new increments during the fault.

Step 5: Inspect the physical connection

Check cable condition, connector seating, strain relief, and environmental damage. If the problem is intermittent, pay particular attention to moving cable sections and vibration points.

Step 6: Verify configuration

Check whether auto-negotiation is enabled or disabled and whether any port speed or duplex settings differ from the intended design.

Step 7: Substitute a known-good component

If necessary, use a known-good cable or suitable alternate port under the approved maintenance procedure. Change one variable at a time and record the result.

Step 8: Verify under load

Check link stability, counters, and actual application communication during normal machine operation. A successful idle test alone may not reveal an intermittent fault.

13. Industrial Breakdown Scenarios

Scenario 1: PLC network link is up, but communication is slow

Observed condition: The PLC link LED is on, but HMI updates or remote device communication is unreliable.

Investigation:

  1. Check speed and duplex at both endpoints.
  2. Inspect CRC/FCS errors and drops.
  3. Confirm whether errors are increasing.
  4. Check for a duplex mismatch.
  5. Inspect cable quality and routing.
  6. Review traffic load and switch-port statistics.

Possible root causes: Duplex mismatch, marginal cable, interference, congestion, or a higher-layer communication issue.

Verification: Confirm stable data exchange and monitor counters under normal operating load.

Scenario 2: Switch port repeatedly goes up and down

Observed condition: The switch reports repeated link-down and link-up events.

Investigation:

  1. Record event timestamps.
  2. Inspect both cable ends.
  3. Check cable strain, vibration, and movement.
  4. Check whether the endpoint is rebooting or losing power.
  5. Substitute a known-good cable.
  6. If needed, test a compatible alternate port.

Possible root causes: Damaged cable, loose connector, endpoint power instability, or a defective port.

Verification: Confirm that link transitions stop under the previously affected operating conditions.

Scenario 3: Communication errors increase during heavy traffic

Observed condition: Communication is acceptable during idle operation but deteriorates when traffic increases.

Investigation:

  1. Check speed and duplex on both endpoints.
  2. Review collisions and late collisions where applicable.
  3. Check CRC/FCS errors and output drops.
  4. Verify cable integrity.
  5. Examine switch congestion and traffic demand.
  6. Check whether the fault affects one link or several devices.

Possible root causes: Duplex mismatch, physical-layer corruption, queue congestion, or insufficient network capacity.

Verification: Confirm correct duplex, acceptable error-counter behaviour, and reliable communication at the expected traffic level.

Scenario 4: Device operates at 100 Mbit/s instead of 1 Gbit/s

Observed condition: A capable device negotiates a lower speed than expected.

Investigation:

  1. Confirm the actual capabilities of both interfaces.
  2. Check configured speed and auto-negotiation settings.
  3. Verify cable category and connector termination.
  4. Check for damaged conductors or poor connections.
  5. Review switch diagnostics and test the cable where appropriate.

Possible root causes: A lower-speed endpoint, forced setting, cable or termination problem, or a faulty interface.

Verification: Confirm the negotiated speed matches the supported network design and that communication is stable.

Scenario 5: Link is normal until a robot moves

Observed condition: Ethernet communication drops at certain robot positions.

Investigation:

  1. Identify cable sections that move with the robot.
  2. Inspect dress packs and cable carriers.
  3. Check for excessive bending, twisting, or tension.
  4. Monitor switch link events during movement.
  5. Test or replace the suspected cable with the specified flex-rated type.

Possible root causes: Cable fatigue, connector strain, or damage within a moving cable section.

Verification: Run the required robot motion range while monitoring link stability and error counters.

14. Preventive Maintenance Checklist

Link status

  • Verify that important industrial network links remain stable.
  • Review recurring link-up and link-down events.
  • Confirm expected speed and duplex settings.
  • Check for disabled or unexpectedly restricted ports.
  • Record abnormal interface resets.

Error counters

  • Review CRC/FCS and other receive-error counters.
  • Check for late collisions on applicable interfaces.
  • Monitor output drops and congestion indicators.
  • Record baseline counters where required.
  • Investigate counter growth rather than relying only on historical totals.

Physical connections

  • Inspect connector seating and locking mechanisms.
  • Check cables for strain, abrasion, and damage.
  • Inspect moving cable sections.
  • Check environmental protection and cable routing.
  • Replace defective components with compatible, specified parts.

Configuration and records

  • Maintain a record of expected port speed and duplex.
  • Document approved forced settings, if any.
  • Record switch-port assignments and connected devices.
  • Document confirmed causes and corrective actions.
  • Verify network communication under normal operating conditions after maintenance.

16. Interview Questions and Answers

Q1. What does a link light indicate?

It generally indicates that a physical Ethernet link has been established. The exact meaning depends on the equipment. A link light does not prove that IP communication or the industrial application is working.

Q2. What is the difference between speed and duplex?

Speed is the nominal data rate of the Ethernet link. Duplex determines whether transmission and reception can occur simultaneously or must share the medium.

Q3. What is auto-negotiation?

It is a process by which compatible Ethernet interfaces exchange capabilities and select supported link parameters.

Q4. What is a duplex mismatch?

It occurs when connected interfaces use different duplex modes. It can cause poor performance, errors, and communication timeouts even when the physical link remains up.

Q5. What is link flapping?

It is repeated switching between link-up and link-down states, often caused by cable faults, connector problems, power instability, or interface issues.

Q6. What does a CRC error indicate?

It indicates that a received frame failed its integrity check. Possible causes include physical signal corruption, EMI, cable problems, connector faults, or interface defects.

Q7. Why should interface counters be recorded before testing?

Recording a baseline allows the technician to identify new errors during the test rather than confusing historical errors with the current fault.

Q8. Why can a 1 Gbit/s-capable device operate at 100 Mbit/s?

The other endpoint may support only 100 Mbit/s, a configuration may restrict the speed, or a cable or interface problem may prevent a higher-speed link from establishing.

Q9. Should speed and duplex always be forced manually?

No. Auto-negotiation is generally preferred when supported and recommended by both endpoints. Manual settings should follow the device documentation and network design.

Q10. What should be checked if the link is up but the PLC cannot communicate?

Check link speed, duplex, error counters, and physical integrity first. If these are satisfactory, continue troubleshooting IP addressing, subnet configuration, routing, industrial protocols, and application logic.

  • Understand common Ethernet link speeds.

  • Diagnose link flapping.

  • Troubleshoot intermittent link problems systematically.
  • Verify communication under actual operating conditions.
  • Record root cause and post-repair results.
