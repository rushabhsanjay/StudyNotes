1. Purpose of IP-Level Troubleshooting

Once the physical Ethernet link is established and link speed and duplex are correct, the next step is to verify IP addressing and network-layer communication.

Industrial devices such as PLCs, remote I/O adapters, HMIs, CNC controllers, robot controllers, VFDs, engineering PCs, SCADA servers, and gateways often use IPv4 addresses to communicate over Ethernet networks.

A device may show a healthy link light while remaining unreachable because of an incorrect IP address, subnet mask, duplicate IP address, gateway configuration, routing problem, or device-specific network setting.

Common symptoms include:

  • PLC or HMI cannot connect to a device.
  • Engineering software cannot discover or connect to a controller.
  • Remote I/O reports a communication fault.
  • Robot, CNC, or drive reports a network communication alarm.
  • A device responds intermittently or becomes unreachable.
  • An IP address conflict is reported.
  • Devices in the same plant communicate inconsistently.
  • A device works from one engineering PC but not another.
  • Communication works within one subnet but fails across subnets.

Core diagnostic principle: Verify the device's actual IP configuration, the intended network design, and the communication path before changing addresses. An arbitrary IP change can create a new conflict or disconnect an otherwise healthy machine.

2. Where IP Addressing Fits in the Network

IP addressing belongs to Layer 3, the Network Layer, of the OSI model.

Layer 1: Physical
Cable / Connector / Electrical or Optical Signal
          ↓
Layer 2: Data Link
Ethernet Frames / MAC Addresses / Switching
          ↓
Layer 3: Network
IP Address / Subnet Mask / Routing
          ↓
Layer 4: Transport
TCP / UDP
          ↓
Industrial Application
PLC Communication / HMI / SCADA / Device Protocol

A successful physical link does not prove that the IP configuration is correct. Likewise, successful IP connectivity does not necessarily prove that an industrial protocol or application is working.

4. IPv4 Address Fundamentals

IPv4 addresses contain 32 bits and are normally written as four decimal octets separated by dots.

Example:

192.168.10.25

Each octet represents eight bits and can range from 0 to 255.

IPv4 Address: 192.168.10.25

Octet 1 → 192
Octet 2 → 168
Octet 3 → 10
Octet 4 → 25

Total = 32 bits

An IP address must be interpreted together with its subnet mask or prefix length. The address alone does not establish which other addresses are considered local.

4.1 Common private IPv4 ranges

These ranges are reserved for private networks and are commonly used in industrial automation.

Private range CIDR prefix Typical use
10.0.0.0 to 10.255.255.255 10.0.0.0/8 Large enterprise or industrial networks
172.16.0.0 to 172.31.255.255 172.16.0.0/12 Enterprise and segmented networks
192.168.0.0 to 192.168.255.255 192.168.0.0/16 Small networks, machines, and local equipment

Private addresses are not globally routable on the public internet by default. They can still be routed internally when the network is designed accordingly.

Important: Private address space does not automatically make a network isolated or secure. Industrial network segmentation, access controls, firewalls, and routing policy remain important.

4.2 Other useful IPv4 ranges

Range Purpose
127.0.0.0/8 IPv4 loopback
169.254.0.0/16 Link-local addressing
0.0.0.0 Unspecified address in applicable contexts
255.255.255.255 Limited broadcast address

A device using an address such as 169.254.20.10 may have assigned itself a link-local address because its normal configuration was unavailable. This is a useful clue, but it is not proof of the exact failure cause.

5. Static IP Addressing in Industrial Automation

Many industrial devices use static IP addressing because control systems often require predictable communication endpoints.

Examples include:

  • PLC Ethernet interfaces.
  • Remote I/O adapters.
  • HMI panels.
  • CNC and robot controllers.
  • Industrial switches with management interfaces.
  • VFD Ethernet modules.
  • SCADA and engineering computers.

5.1 Example industrial address plan

Device Example IP address Subnet mask Purpose
PLC 192.168.10.10 255.255.255.0 Controller
Remote I/O 192.168.10.20 255.255.255.0 Distributed I/O
HMI 192.168.10.30 255.255.255.0 Operator interface
Robot controller 192.168.10.40 255.255.255.0 Robot communication
Engineering PC 192.168.10.50 255.255.255.0 Programming and diagnostics

These are illustrative addresses only. Use the approved plant or machine address plan for real equipment.

5.2 Static addressing best practices

  • Maintain a controlled IP address register.
  • Record device name, model, MAC address, IP address, subnet mask, and gateway.
  • Document the assigned switch port and machine or line.
  • Avoid selecting addresses without checking for existing assignments.
  • Record any device replacement and its configured address.
  • Distinguish a device's maintenance address from its normal production address.
  • Document special communication interfaces separately when a device has multiple ports.

Do not assume that a replacement PLC, drive, or remote I/O adapter automatically uses the same IP address as the original device.

6. Subnet Masks and CIDR Prefixes

A subnet mask determines which portion of an IPv4 address identifies the network and which portion identifies the interface within that subnet.

For example:

  • IP address: 192.168.10.25
  • Subnet mask: 255.255.255.0
  • CIDR prefix: /24

The first 24 bits identify the network prefix.

6.1 Common subnet masks

CIDR prefix Subnet mask Total addresses Typical usable host addresses on a conventional subnet
/8 255.0.0.0 16,777,216 16,777,214
/16 255.255.0.0 65,536 65,534
/24 255.255.255.0 256 254
/25 255.255.255.128 128 126
/26 255.255.255.192 64 62
/27 255.255.255.224 32 30
/28 255.255.255.240 16 14
/30 255.255.255.252 4 2

The usable-host figures apply to conventional IPv4 subnets where the network and broadcast addresses are reserved. Special cases such as /31 point-to-point links and /32 host routes follow different rules.

6.2 Example: /24 network

Given:

  • Device IP: 192.168.10.25
  • Subnet mask: 255.255.255.0

The network is 192.168.10.0/24.

For this conventional subnet:

  • Network address: 192.168.10.0
  • Usable host range: 192.168.10.1 to 192.168.10.254
  • Broadcast address: 192.168.10.255

The network and broadcast addresses should not be assigned to ordinary device interfaces in this example.

6.3 Example: /25 network

Given:

  • Device IP: 192.168.10.25
  • Subnet mask: 255.255.255.128

The subnet is 192.168.10.0/25.

  • Network address: 192.168.10.0
  • Usable host range: 192.168.10.1 to 192.168.10.126
  • Broadcast address: 192.168.10.127

The address 192.168.10.150 belongs to a different /25 subnet, even though its first three octets match.

7. Same-Subnet and Different-Subnet Communication

Two devices can communicate directly at Layer 2 when their interfaces share the relevant local network segment or VLAN and their IP configuration identifies the destination as local.

For a simple IPv4 network:

  • PLC: 192.168.10.10/24
  • HMI: 192.168.10.30/24

Both devices belong to 192.168.10.0/24.

Now consider:

  • PLC: 192.168.10.10/24
  • HMI: 192.168.20.30/24

These addresses belong to different /24 networks. Communication between them normally requires an appropriate router or Layer 3 interface and correct routing configuration.

7.1 Why an incorrect mask causes problems

Suppose a PLC is configured as 192.168.10.10/24, while an HMI is configured as 192.168.10.30/16.

The addresses are within the same 192.168.0.0/16 range, so communication may still work in a simple flat network. However, the inconsistent masks can cause incorrect local-versus-remote decisions when other networks are involved.

A more obvious problem occurs when one device is configured as 192.168.10.10/24 and the other as 192.168.20.30/24 with no router between their networks. They will not communicate directly through ordinary Layer 2 switching.

Troubleshooting rule: Compare the full IP address and subnet mask on both devices. Matching only the first three octets is not a reliable subnet test.

8. Default Gateway

The default gateway is the router address used when a device needs to reach an IP destination outside its locally connected networks.

Example:

  • PLC: 192.168.10.10/24
  • Gateway: 192.168.10.1
  • SCADA server: 192.168.20.50/24

If routing exists between the two networks and return routing is configured correctly, the PLC may communicate with the SCADA server through the gateway.

8.1 Gateway faults

  • Gateway address is incorrect.
  • Gateway is outside the device's local subnet.
  • Router interface is down.
  • VLAN or switch configuration prevents access to the gateway.
  • No route exists to the destination network.
  • Return routing is missing.
  • Firewall rules block the traffic.

A default gateway is generally unnecessary for communication between devices on the same local subnet. However, it may be needed for remote engineering, SCADA, or enterprise connectivity.

Do not add a gateway merely to resolve every communication fault. First establish whether the destination is local or remote and how the network is intended to route traffic.

9. Duplicate IP Address Conflicts

A duplicate IP occurs when two interfaces on the same relevant IPv4 network use the same address.

For example:

  • PLC A: 192.168.10.10
  • PLC B: 192.168.10.10

The conflict may cause unpredictable communication because other devices cannot consistently associate that IP address with the intended interface's MAC address.

9.1 Common symptoms

  • Intermittent connection to a PLC or HMI.
  • Engineering software connects to the wrong device.
  • Duplicate-address warning on a PC or controller.
  • ARP entries change unexpectedly between MAC addresses.
  • Communication fails when a particular device powers on.
  • One device works when another device is disconnected.
  • Network behaviour changes after a replacement controller is installed.

Not every duplicate IP produces an obvious alarm. Some devices may silently interfere with each other.

9.2 Common causes

  • Replacement equipment retains a factory-default or old address.
  • A spare PLC or HMI was configured without checking the address register.
  • Two engineers assign the same address.
  • A device was restored from an old backup.
  • A temporary engineering laptop uses a conflicting static address.
  • DHCP assigns an address already being used by a statically configured device.
  • A duplicate device is connected to the network during maintenance.

9.3 Duplicate IP troubleshooting procedure

  1. Record the affected IP address and the devices reporting the conflict.
  2. Check the approved IP address register.
  3. Inspect ARP information on an authorized engineering PC.
  4. Check switch MAC address tables and port assignments where available.
  5. Identify which physical devices correspond to the conflicting MAC addresses.
  6. Isolate the suspect device only under the approved maintenance procedure.
  7. Correct the address on the unauthorized or incorrectly configured device.
  8. Verify the intended device is reachable and that the conflict no longer occurs.

Do not change the IP address of a running PLC or remote I/O adapter without understanding the machine's communication dependencies. A careless change can stop production or disconnect safety-related diagnostics.

10. ARP: Mapping IP Addresses to MAC Addresses

Address Resolution Protocol (ARP) is used on IPv4 networks to discover the MAC address associated with an IPv4 address on the local network.

When a device needs to send an Ethernet frame to a local IPv4 destination, it may consult its ARP cache. If no suitable mapping exists, it can broadcast an ARP request.

PLC Needs to Contact 192.168.10.30
             ↓
Check ARP Cache
             ↓
Entry Available?
       ↙           ↘
     Yes             No
      ↓               ↓
Use MAC Address   Send ARP Request
                      ↓
                Target Responds
                      ↓
                Update ARP Cache
                      ↓
                Send Ethernet Frame

For a destination outside the local subnet, the source normally resolves the MAC address of the next-hop router rather than the remote destination itself.

10.1 ARP cache inspection

On Windows, open Command Prompt and use:

arp -a

To inspect the IPv4 configuration:

ipconfig /all

To display route information:

route print

To view the local ARP cache, these commands are useful, but their output must be interpreted carefully.

Important limitation: An ARP entry is not a complete device inventory and does not prove that an application is communicating correctly. Entries can be stale, incomplete, or absent because the device has not recently needed to communicate with the target.

A single ARP entry changing does not prove a duplicate IP on its own. Confirm the MAC addresses, physical devices, timing, and network topology.

11. DHCP Versus Static IP

Static addressing

An administrator manually configures the address, subnet mask, and other settings.

Advantages:

  • Predictable address for control systems.
  • Useful for device configurations that require fixed endpoints.
  • Easier to document when an accurate address register is maintained.

Risks:

  • Duplicate addresses if the register is not maintained.
  • Address mismatch after equipment replacement.
  • Manual configuration errors.
  • Difficulties when moving equipment between networks.

DHCP addressing

A DHCP server provides IP configuration to clients according to its scope, reservations, and policies.

Advantages:

  • Centralized configuration.
  • Reduced manual effort for supported devices.
  • Easier address management for general-purpose endpoints.

Risks in industrial environments:

  • A device may fail to obtain a lease if DHCP is unavailable.
  • Addresses may change unless reservations or policies are used.
  • Incorrect scopes can provide addresses from the wrong network.
  • A statically configured device can conflict with an address distributed by DHCP if address management is poor.

Some industrial devices support DHCP, BOOTP, or manufacturer-specific address assignment tools. Verify the actual device capabilities before choosing a recovery method.

12. APIPA and Unexpected Addresses

On supported systems, an interface may assign itself an address in 169.254.0.0/16 when normal IPv4 configuration is unavailable.

For example:

169.254.18.42

This is commonly called an APIPA or IPv4 link-local address.

Possible explanations

  • DHCP server is unavailable.
  • DHCP requests are not reaching the server.
  • The device is directly connected to another device without a DHCP service.
  • The interface has been configured for link-local operation.
  • A device-specific address assignment procedure has not completed.

Diagnostic steps

  1. Inspect the actual IPv4 address and subnet mask.
  2. Determine whether the device should use static addressing or DHCP.
  3. Verify the DHCP server or approved address-assignment process if required.
  4. Check VLAN and switch connectivity.
  5. Compare the observed address with the approved network plan.
  6. Restore the intended configuration using the manufacturer-supported procedure.

Do not assume every 169.254.x.x address indicates a faulty network card. It is often a clue about how the interface obtained its configuration.

13. Windows Commands for IP Troubleshooting

13.1 Inspect configuration

ipconfig /all

Check:

  • IPv4 address.
  • Subnet mask.
  • Default gateway.
  • DHCP enabled or disabled.
  • DHCP server, if applicable.
  • MAC address, shown as Physical Address.
  • DNS servers, where relevant.

13.2 Test basic IP reachability

ping 192.168.10.10

This tests whether ICMP Echo requests and replies succeed. A failed ping does not necessarily mean that all communication is impossible because firewalls or device settings may block ICMP.

13.3 Inspect ARP entries

arp -a

Use this to examine locally known IP-to-MAC mappings.

13.4 Clear the local ARP cache

arp -d *

This command may require an elevated Command Prompt. It removes dynamic ARP entries so that mappings can be learned again.

Use it only when appropriate. Clearing the cache does not fix a duplicate IP address and can temporarily affect communication while entries are relearned.

13.5 Inspect routes

route print

Use this to inspect the routing table, interfaces, and configured routes.

13.6 Test a path to a remote destination

tracert 192.168.20.50

This helps identify responding Layer 3 hops on a route. Some routers or firewalls may not respond to traceroute probes, so missing responses do not automatically prove that the route is broken.

15. Structured IP Troubleshooting Procedure

Record Device and Communication Fault
              ↓
Verify Physical Link and Port Status
              ↓
Read Actual IP / Mask / Gateway
              ↓
Compare with Approved Address Plan
              ↓
Check Local Subnet and VLAN
              ↓
Investigate Duplicate IP / ARP Behaviour
              ↓
Test Local IP Reachability
              ↓
Check Gateway and Routes if Remote
              ↓
Test Industrial Protocol / Application
              ↓
Document Root Cause and Verify Repair

Step 1: Identify the target

Record the device name, IP address, MAC address, network port, and expected communication partner.

Step 2: Verify the actual configuration

Do not rely solely on a label or old screenshot. Read the device's current configuration using an approved method.

Step 3: Compare address and mask

Confirm that the address is assigned to the correct device and that the subnet mask matches the network design.

Step 4: Check for conflicts

Look for duplicate-address warnings, inconsistent ARP observations, or unexpected MAC addresses associated with the target IP.

Step 5: Test local connectivity

Use approved diagnostic commands and the device's own status information. Remember that ICMP may be disabled.

Step 6: Check routing when required

For destinations outside the local subnet, inspect the default gateway, routing table, VLAN design, and return path.

Step 7: Check application communication

If IP connectivity works, verify the industrial protocol, configured endpoint, service port, device state, and applicable firewall rules.

Step 8: Verify the repair

Confirm that the correct device responds, the duplicate address is resolved, and the intended industrial application works normally.

16. Practical Industrial Breakdown Scenarios

Scenario 1: PLC is unreachable after replacement

Observed condition: The replacement PLC powers up and has an Ethernet link, but engineering software cannot connect.

Investigation:

  1. Confirm the PLC model and Ethernet interface.
  2. Read its actual IP address and subnet mask.
  3. Compare them with the original controller's documented settings.
  4. Verify the engineering PC is connected to the intended subnet.
  5. Check for a duplicate address or unexpected MAC mapping.
  6. Apply the approved controller network configuration.

Possible root causes: Wrong IP address, wrong subnet mask, incorrect interface selection, or duplicate IP.

Verification: Confirm the intended controller is reachable and the engineering software connects to the correct device.

Scenario 2: HMI communication fails intermittently

Observed condition: The HMI sometimes communicates with the PLC and sometimes reports a connection fault.

Investigation:

  1. Check HMI and PLC IP configurations.
  2. Verify that neither address is duplicated.
  3. Inspect ARP observations and switch MAC address tables where available.
  4. Check link events and physical cable condition.
  5. Review HMI and PLC communication diagnostics.
  6. Check whether the fault correlates with a device restart or network change.

Possible root causes: Duplicate IP, intermittent physical connection, device reboot, or application-level timeout.

Verification: Confirm stable communication during normal production operation.

Scenario 3: Engineering PC cannot connect to the PLC

Observed condition: The PLC is running, but the programming software cannot reach it.

Investigation:

  1. Run ipconfig /all on the engineering PC.
  2. Confirm the selected network interface and its IP address.
  3. Compare the PC subnet mask with the PLC's configuration.
  4. Check VLAN and switch-port assignment.
  5. Test reachability where permitted.
  6. Check software interface selection, firewall, and protocol requirements.

Possible root causes: Wrong PC address, incorrect mask, wrong NIC selection, VLAN mismatch, or application configuration.

Verification: Confirm the programming software connects to the intended PLC without altering the controller's running program or production settings unnecessarily.

Scenario 4: Device communicates locally but not with SCADA

Observed condition: A PLC can communicate with local equipment but not with a SCADA server on another network.

Investigation:

  1. Confirm the PLC and SCADA subnet addresses.
  2. Check the PLC's default gateway or configured route.
  3. Verify the gateway is reachable from the PLC's network.
  4. Check routing and firewall policy between networks.
  5. Verify the return path from SCADA to the PLC.
  6. Confirm the required application ports and protocol settings.

Possible root causes: Missing gateway, incorrect route, firewall restriction, or missing return route.

Verification: Confirm the intended application traffic passes between the networks and remains stable.

Scenario 5: Duplicate IP after temporary laptop connection

Observed condition: An industrial device becomes intermittently unreachable after an engineering laptop is connected.

Investigation:

  1. Record the device IP and MAC address.
  2. Inspect the laptop's current IP configuration.
  3. Check for a manually configured address that overlaps with the machine's address plan.
  4. Inspect ARP observations and switch-port information.
  5. Disconnect or reconfigure the laptop using the approved procedure.
  6. Revalidate the intended device's identity and communication.

Possible root cause: The laptop was configured with an IP address already assigned to a machine device.

Verification: Confirm the laptop has a permitted address and the machine device remains reachable.

17. Preventive Maintenance Checklist

IP address management

  • Maintain a current IP address register.
  • Record IP address, subnet mask, gateway, MAC address, and device identity.
  • Document devices with multiple network interfaces separately.
  • Reserve and control addresses for industrial equipment.
  • Check for conflicts before connecting replacement or temporary devices.
  • Document address changes and approved maintenance configurations.

Configuration verification

  • Verify static or DHCP configuration as designed.
  • Confirm the subnet mask and prefix length.
  • Check the default gateway only where routing is required.
  • Confirm switch-port and VLAN assignments.
  • Verify device replacement settings against approved backups or records.

Diagnostics and recovery

  • Know how to use ipconfig /all, arp -a, ping, and route print.
  • Record baseline communication behaviour where appropriate.
  • Check duplicate-IP symptoms before changing an address.
  • Confirm correct device identity after any IP change.
  • Verify industrial application communication after recovery.

19. Interview Questions and Answers

Q1. What is an IP address?

An IP address is a logical network-layer address used to identify an interface for IP communication.

Q2. What is a subnet mask?

A subnet mask defines which bits of an IPv4 address represent the network prefix and which identify the interface within that subnet.

Q3. What is a duplicate IP conflict?

It occurs when multiple interfaces on the same relevant IPv4 network use the same address, potentially causing inconsistent address-to-MAC resolution and communication failures.

Q4. Why can two devices with similar IP addresses fail to communicate?

They may use different subnet masks, belong to different subnets or VLANs, or lack the routing required to communicate.

Q5. What is the purpose of a default gateway?

It provides the next-hop router used to reach destinations outside the device's locally connected IP network.

Q6. What is ARP?

ARP resolves an IPv4 address to a MAC address on a local network so that an Ethernet frame can be delivered to the intended next hop.

Q7. What does an address beginning with 169.254 often indicate?

It is within the IPv4 link-local range and may indicate that a device assigned itself a link-local address instead of obtaining its intended configuration.

Q8. Can a device respond to ping but still fail in PLC communication?

Yes. The application may have incorrect settings, blocked service ports, protocol incompatibility, or a device-specific communication fault.

Q9. Why should the approved address register be checked before changing a PLC address?

Changing the address without checking the network plan can create duplicate addresses, break HMI or SCADA connections, or disconnect dependent equipment.

Q10. How should a suspected duplicate IP be confirmed?

Compare the intended address register, device identities, MAC addresses, ARP observations, switch-port information, and physical devices. Do not rely on a single ping result.

  • Interpret subnet masks and CIDR prefixes.
  • Calculate basic network, host, and broadcast addresses.
  • Distinguish same-subnet and different-subnet communication.
  • Understand the purpose of a default gateway.
  • Diagnose duplicate IP address conflicts.
  • Understand ARP and inspect local ARP entries.
  • Distinguish static IP, DHCP, and link-local addressing.
  • Use basic Windows commands for IP troubleshooting.
  • Separate IP connectivity faults from application-level faults.
  • Verify device identity before applying configuration changes.
  • Document the confirmed cause and validate the complete communication path.
